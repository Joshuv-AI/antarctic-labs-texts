Abstract
. Code comprehension is essential for brownfield programming tasks, in which developers maintain and enhance legacy code bases. Generative AI (GenAI) coding assistants such as GitHub Copilot have been shown to improve developer productivity, but their impact on code understanding is less clear. We replicate and extend a previous study by exploring both performance and comprehension in GenAI-assisted brownfield programming tasks. In a within-subjects experimental study, 18 computer science graduate students completed feature implementation tasks with and without Copilot. Results show that Copilot significantly reduced task time and increased the number of test cases passed. However, comprehension scores did not differ across conditions, revealing a comprehension–performance gap: participants passed more test cases with Copilot, but did not demonstrate greater understanding of the legacy codebase. Moreover, we failed to find a correlation between comprehension and task performance. These findings suggest that while GenAI tools can accelerate programming progress in a legacy codebase, such progress may come without an improved understanding of that codebase. We consider the implications of these findings for programming education and GenAI tool design.



1.
Introduction

Code comprehension is a critical activity in software development, occupying more than half of a developer’s time during maintenance and feature enhancements
Al-Saiyd 2017
;
Koenemann & Robertson 1991
;
Xia et al. 2017
;
Qiao et al. 2025
in legacy code bases. These so-called "brownfield" programming tasks involve enhancing a code base written by others
Baley & Belcham 2010
. Many studies have explored the mental models and cognitive processes involved in brownfield programming, using frameworks such as the Block Model and Information Foraging Theory
Ko et al. 2006
;
Lawrance et al. 2010
;
Piorkowski et al. 2016
;
Storey 2006
;
Sillito et al. 2006
;
LaToza & Myers 2010
;
Roehm et al. 2012
;
Robillard et al. 2005
.

The recent emergence of Generative AI (GenAI) tools is poised to fundamentally alter this landscape. Developers are increasingly shifting their focus from writing code to comprehending and integrating GenAI-generated outputs.
While studies have shown that GenAI tools can dramatically improve developer productivity
Feng et al. 2025
;
Peng et al. 2023
;
Ng et al. 2024
, a critical question remains unanswered:

RQ
: To what degree do developers need to
understand
a code base to complete brownfield programming tasks within that code base using GenAI assistance?

Two sub-questions can help us address this question systematically:

RQ1::

How does developers’ code comprehension in brownfield programming tasks differ with and without GenAI assistance?

RQ2::

How does developers’ code comprehension in brownfield programming tasks relate to their productivity?

To address these questions, we conducted a within-subjects experimental study in which participants worked on a set of brownfield programming tasks without and with GenAI assistance. After working on each set of tasks, we administered a comprehension test to gauge their understanding of the code base on which they were working. Like the prior experimental study whose methodology we replicated
Authors 2025
, we found that participants were significantly more productive with GenAI assistance.
However, a comparison of the comprehension scores revealed no statistically significant differences between the two conditions, nor did we find a significant correlation between programming productivty and code comprehension. This finding points to a
comprehension-performance gap
, where developer productivity increases with GenAI assistance while code comprehension remains unchanged. We consider the implications of these findings for both programming education and the design of GenAI programming assistants.

2.
Related Work

2.1.
Code Comprehension

Code comprehension is a critical activity in software development, with studies showing that developers spend between 52% and 70% of their time understanding existing source code
Al-Saiyd 2017
;
Koenemann & Robertson 1991
;
Xia et al. 2017
;
Chattopadhyay et al. 2023
. To build a mental model of the software, developers generally employ a top-down approach
Brooks 1977
, a bottom-up approach
Letovsky 1987
, or an integrated strategy that combines both
Heinonen et al. 2023
.

While these models provide lenses for characterizing the comprehension process, empirical studies reveal that the actual comprehension processes are far more dynamic. In an early study, for instance, Von et al.
Von et al. 1997
observed professional developers as they worked on real-world enhancement tasks. They found that programmers often jump between different parts of a system at various levels of abstraction, leading them to conclude that program comprehension is a multi-layered, dynamic, and iterative process. More recently, Levy et al.
Levy & Feitelson 2019
interviewed experienced developers to understand how they comprehend large-scale software and reached a similar conclusion: comprehension is an iterative process requiring the construction of a layered, abstract model of the software’s structure and behavior.

A significant body of research has studied the code comprehension techniques, patterns, and processes of both professional developers
Storey 2006
;
Sillito et al. 2006
;
LaToza & Myers 2010
;
Roehm et al. 2012
;
Robillard et al. 2005
and computer science students
Shah et al. 2025
;
Shah et al. 2025a
;
Dominic et al. 2020
. In these studies, information foraging theory has been particularly influential. Information foraging theory views code comprehension as a process whereby developers act like foragers, following trails of clues or "information scents" through the code to locate and collect relevant information
Ko et al. 2006
;
Lawrance et al. 2010
;
Piorkowski et al. 2016
. For instance, a recent study applied information foraging theory to investigate how novices modify existing open-source code bases
Shah et al. 2025
. In these studies, the authors concluded that novices are unable to effectively initiate the use of documentation, employ a structurally guided comprehension process, locate all relevant code, and discard irrelevant parts.

In a similar vein, Shah et al.
Shah et al. 2025a
investigated how intermediate-level programming students understand an unfamiliar, complex code base by mapping their comprehension process to the Block Model . Dominic et al.
Dominic et al. 2020
examined whether Virtual Reality could help graduate students comprehend complex software, finding no significant difference in perceived productivity compared to traditional methods.

Another approach has been to use functional Magnetic Resonance Imaging (fMRI) to measure brain activity as students or developers perform comprehension tasks
Siegmund et al. 2017
;
Ivanova et al. 2020
. This approach aims to bridge the gap between theoretical models of program comprehension and the actual cognitive processes that happen in the brain. Building on this understanding of the cognitive process, some research has focused on specific factors and interventions that aid or impede comprehension, such as the quality of summaries and identifier names, along with various teaching strategies. For instance, one study explored whether a deep learning model can generate more effective code summaries compared with human-written ones, finding that a machine-generated summary may not effectively convey information for code comprehension
Stapleton et al. 2020
. Another study investigated whether short identifiers (e.g., the names of variables and functions) increase the cognitive load when comprehending code, finding that programmers favor descriptive, non-abbreviated identifiers over abbreviations
Hofmeister et al. 2019
. Similarly, Cates et al.
Cates et al. 2021
found that as the complexity of code increases, identifier names become the most important factor for code comprehension. Another study compared the value of actively prompting students to self-explain each line of code versus guiding them using a series of targeted questions
Tamang et al. 2021
.Researchers have also considered whether students’ intelligence and personality can affect their code comprehension performance
Wagner & Wyrich 2021
.

2.2.
Applications of GenAI in Code Comprehension

GenAI has been increasingly applied to enhance code comprehension in both academic and professional settings. In educational contexts, researchers have explored several innovative pedagogical strategies. One novel approach assesses student understanding by having them explain code in natural language; an LLM then attempts to regenerate the original code from this explanation, with the regeneration’s accuracy serving as a proxy for the student’s comprehension
Denny et al. 2024
;
Smith et al. 2024
. Other research has focused on developing standalone GenAI-based comprehension tools
Kazemitabaar et al. 2024
, embedding GenAI assistance directly into educational materials like e-books
MacNeil et al. 2023
, and automatically generating code explanations to evaluate their quality against those produced by human experts
Sarsa et al. 2022
;
Leinonen et al. 2023
. Others have investigated factors such as task goals and project context that might influence what programmers require from GenAI-generated code explanations
Brachman et al. 2025
.

Similar to pedagogical interventions, several GenAI tools have been developed to aid professional developers. For example, GILT can explain highlighted code without an explicit user prompt
Nam et al. 2024
, while Ivie generates anchored, multi-level explanations for GenAI-produced code
Tang 2024
. To overcome the input token limitations of LLMs when analyzing large code bases, Lei et al.
Lei et al. 2025
proposed a multi-agent system capable of generating explanations at the function, file, and project levels.

While much of the prior work has focused on developing new GenAI tools, our study investigates how an existing, widely used tool—GitHub Copilot—affects a developer’s understanding of a legacy code base. A similar study by Shah et al.
Shah et al. 2025a
investigated how students use prompts with Copilot to comprehend a large code base. However, our work differs in that we explicitly measure participants’ comprehension levels while they perform brownfield programming tasks, thereby assessing the impact of their use of Copilot on their cognitive grasp of unfamiliar code.

3.
Method

3.1.
Design

Replicating the methodology and materials of a prior study
Shihab et al. 2025
, we conducted a within-subjects experimental study with two treatments: No Copilot (Control) and Copilot (Experimental). In the No Copilot condition, participants completed brownfield programming tasks without the use of Copilot or any other GenAI tool; however, they were were free to search the web. In the Copilot condition, participants were allowed to use Copilot to complete the programming tasks. While the task order was counterbalanced to mitigate order effects, the treatment order was not. This was because we were interested in first observing participants’ programming activities without the use of Copilot.

We measured performance using three dependent variables: (a) task completion time, (b) number of tests passed, and (c) accuracy on comprehension questions about the legacy code base. We also used the same coding scheme as the previous study to characterize participants’ second-by-second programming behaviors. Finally, we qualitatively analyzed participants’ post-survey responses relative to Copilot’s helpfulness for both programming tasks and for understanding the code base.

3.2.
Pilot Study

Prior to the main study, we conducted a pilot study with three participants to fine-tune the study protocol and materials. Participants were recruited from the same population as was used for the main study. Because this pilot study used the same experimental protocol as the main study and uncovered only minor issues, we opted to include data from these three participants in the final sample. A key outcome of this pilot was an improvement to the way we timed participant tasks: We replaced a command-line tool with a feature integrated into the Visual Studio Code (VS Code) extension. This provided participants with greater time awareness by dynamically displaying a countdown in the interface.

3.3.
Participants

Participants were recruited from a completely online, asynchronous graduate software engineering methods course with 44 enrolled students at a large research university in the western United States. The study tasks were part of a required course assignment; however, students could choose whether to release their data for inclusion in the study.

Whereas our previous study
Authors 2025
included only high-achieving undergraduate students with no previous experience with GenAI programming assistants, this study included graduate students enrolled in a software engineering course. Since we did not filter for students with prior web development experience or GenAI programming assistant experience, the population for this study represented a more diverse sample of computer science students.

Of the 44 students enrolled in the graduate software engineering course from which we recruited participants, 26 consented to participate. After analyzing videos of participants’ study sessions, we excluded eight participants who either failed to follow the experimental protocol or did not correctly use the customized IDE (Visual Studio Code
Microsoft Corporation 2025
) extension to time their tasks. This resulted in a final sample of 18 participants (15 from main study and three from the pilot study).

The final sample consisted of 13 males and 5 females, including 17 master’s (M.S. or M.Eng.) students and one Ph.D. student in computer science. Among the master’s students, nine were in their second year and eight were in their first; the Ph.D. student was in their third year. 12 of the 18 participants had earned an A in a previous web-development course, and 15 had a GPA of 3.7 or higher (on a 4.0 scale). Furthermore, 14 of the 18 participants had prior experience with web-development projects. In terms of GenAI tool usage frequency, five participants reported using them daily, eight weekly, three monthly, and two one or a few times. Regarding proficiency, six participants indicated high proficiency, 10 indicated medium, one indicated low, and one indicated none.

3.4.
Materials and Tasks

3.4.1.
Legacy code base

Participants worked on feature implementation tasks within a 3,818-line code base, a strategic subset of a 100K-line full-stack production web app focused on sports analytics. The selected subset was a front-end web application consisting of 49% plain-vanilla JavaScript, 40% HTML, and 11% CSS. It was chosen to be manageable within the limited session time.

3.4.3.
Test Suites

To enable participants to validate their solutions for the three tasks within each feature, we used the same test suites from the previous study, comprising a total of 13 test cases (four for Task 1, four for Task 2, and five for Task 3). These test cases objectively verified each feature’s minimal user interface requirements, correct functional behavior, and data persistence in
localStorage
.

3.4.4.
Participant Instructions

Unlike our previous study
Authors 2025
, this study was conducted within the context of a completely online, asynchronous course. Hence, the participant instructions were designed to be completed independently by participants on their own time without direct supervision, with screen recordings capturing their behaviors. To that end, we developed the study instructions within a Canvas course module. At the start of the module, participants were asked to read the instructions aloud. The instructions (a) stated the two-and-a-half-hour time allocation for the study; (b) described the purpose of the study; (c) reminded participants that the study was testing GitHub Copilot, not their performance; (d) provided an overview of the session’s tasks; (e) asked participants to think aloud during the study; and (f) required them to screen and audio record their process of completing the tutorial, implementing the tasks, and answering the comprehension questions.

3.4.5.
Tutorial and Task Description

We utilized the tutorial and task descriptions from our previous study
Authors 2025
. The tutorial introduced participants to (a) the new features they would be implementing, (b) the legacy code base, and (c) the features of GitHub Copilot, including the chat and autocomplete features. We augmented this tutorial with several additions: a reminder to begin session recording, guidance on applying suggestions from Copilot, and instructions for activating the custom VS Code extension used for task timing. In addition, the task descriptions explicitly stated at the beginning of each task that participants should start their timer and recording.

3.4.6.
Experimental Computing Environment

Participants joined the study by accepting an invitation through GitHub Classroom
GitHub, Inc. 2024
, which created a unique code repository for each participant by cloning a repository with the base code. All programming tasks were completed within GitHub Codespaces
GitHub 2024
, a cloud-based development environment that was automatically configured for each participant. This environment included:

•

Node.js
, the build environment for the web application that participants worked on in the study

•

Git, for committing code changes, with the user logged in under an anonymous Git account to protect their identity

•

a fresh version of the web application source code, under Git source control, with a separate remote repository for each participant created by GitHub Classroom

•

the Canvas Learning Management System
Instructure, Inc. 2025
, where participants read and followed the study instructions within a course module.

3.5.
Procedure

As in our previous study
Authors 2025
, all participants completed the No Copilot treatment first, so that we could capture their performance without prior influence from the Copilot. However, we did counterbalance the order of the feature implementation tasks to control for potential order effects.

Each study session lasted 150 minutes. The tutorial, screening questionnaire, comprehension questions, and post-survey were administered within a Canvas module. Participants were instructed to record their screen and voice using a video recording tool (e.g., Zoom
Zoom Video Communications, Inc. 2025
or Loom
Loom, Inc. 2025
) while following the think-aloud protocol as they worked on the tutorial and implementation tasks. The implementation of each feature was divided into three sequential tasks, each set up as a separate assignment. After a participant completed a task and submitted the link to their recorded video, they could proceed to the next task. This process continued until they finished all three tasks required for the feature or time ran out.

Following each feature implementation, the participant was asked to answer eight comprehension questions through an online Qualtrics survey. To track participant data anonymously, we assigned each participant a unique ID. When they started a survey on Qualtrics, they were required to provide their unique ID.

3.6.
Data Collection and Analysis

We used a mixed methods approach to collect and analyze data on the task performance, programming processes, and comprehension levels of participants. Participants video-recorded all of their tasks and uploaded the recordings to Canvas, with comprehension surveys captured via Qualtrics. We subsequently analyzed both quantitative and qualitative data, including: (1) the number of tests passed, (2) task completion time, (3) comprehension question accuracy, (4) moment-by-moment programming behaviors, and (5) responses to the post-survey.

3.6.1.
Comprehension Questions Grading

Multiple-choice comprehension questions were first automatically graded using Qualtrics. We then manually checked the grading, deducting a half-point for each incorrect answer on questions where participants selected both correct and incorrect options. For the open-ended question, we performed qualitative grading based on the ground truth that was negotiated between the authors. For qualitative analysis, we used the three-point scale grading based on the rubric shown in Table

.

5.
Discussion and Implications

5.1.
Discussion

5.1.1.
RQ1: Comprehension Level Difference

Our analysis revealed that students had no significant differences in comprehension under the two conditions. This finding was consistent across all types of comprehension questions, indicating that the current version of Copilot did not improve computing students’ ability to understand a legacy code base. Notably, the overall comprehension levels were low in both groups, with mean scores of 61% (7.9/13) without Copilot and 55% (7.2/13) with Copilot.
This outcome suggests a potential drawback of using Generative AI tools in brownfield software development: They may enable developers to make rapid progress without obtaining a deep understanding of the system’s design and architecture. Instead of helping build a robust mental model, GenAI tools may enable developers to code with only superficial cognitive engagement with a code base. This, in turn, could place developers in a weaker position when they must later need to debug subtle, cross-cutting issues, creating a form of
human-level technical debt
that jeopardizes long-term code maintainability.

The qualitative analysis from the post-survey provided evidence that a majority of participants (10 out of 17) reported that Copilot did not help them better understand the code base. This was due to several factors: some participants primarily perceived and used Copilot as a code generator rather than as a comprehension tool, while others found that its responses were too localized, focusing on specific code snippets rather than the broader code base context. Another participant suggested that Copilot might improve their understanding if it were used differently.
These perceptions imply that even when Copilot provides explanations, they may not be sufficient for building a comprehensive understanding of complex software code bases. They also suggest that students’ usage patterns could impact their comprehension levels.

Taken together, these findings highlight a gap between Copilot’s code-generating abilities and its support for comprehending legacy code bases in brownfield programming tasks. Traditionally, understanding a legacy code base has involved finding initial focal points, understanding individual code components around those focal points, and recognizing the relationships between them
Sillito et al. 2006
. Copilot’s current design does not scaffold this comprehension process.

5.1.2.
RQ2: Correlation of Comprehension and Task Performance

Our correlational analysis did not find a statistically significant relationship between comprehension level and the number of tests passed in either condition. While previous studies have found that better understanding leads to better task performance
Shaft & Vessey 2006
, we found no such trend in either condition. Given that, with Copilot, students passed 84% more test cases, we see that Copilot introduces a
comprehension-performance gap
, facilitating significantly higher coding productivity without a parallel improvement in the comprehension of the underlying code base. This reinforces the idea that developers are taking the suggestions of the GenAI without internalizing the underlying code structure, a phenomenon also noted in other studies
Prather et al. 2024
.

5.2.
Implications

5.2.1.
Implications for Programming Education

To help programmers better comprehend code while using GenAI programming assistants, we must first determine the target comprehension level for their tasks. Previous work defines four levels of comprehension: finding an initial focus point (atom-level); building on focus points (function-level), understanding subgraphs (component-level); and understanding relationships across subgraphs (system-level)
Sillito et al. 2006
. In GenAI programming’s iterative cycle of prompting, viewing the response, and writing code, programmers spend less time on atom-level and function-level comprehension of the code base. Instead, they offload this low-level comprehension to the GenAI assistant, as evidenced by our finding of a dramatic decrease in web viewing in the Copilot condition (see Figure
4
). Indeed, by describing their task goals and receiving a generated solution, students primarily engage with the code base at the
system
and
component
levels.

Future work in programming education should focus on teaching programmers to be better systems-level thinkers, rather than focusing on low-level implementation details. For instance, educators can teach students how to write effective, context-aware prompts based on task requirements
Liang et al. 2025
;
Nam et al. 2025
, and to explicitly ask questions about the structure of the code base and the relationships between its components. More importantly, students must learn how to critically evaluate, debug, and ultimately integrate GenAI-generated code into an existing code base while understanding at least the high-level architecture and organization of that code base. Likewise, performance assessments should shift from memorizing code syntax (atom-level) or writing individual functions (function-level) to measuring a student’s ability to design and understand system architectures and debug complex interactions between components.

5.2.2.
Implications for GenAI Tool Design

The current generation of GenAI code assistants, including the Copilot tool evaluated in this study, primarily focus on code generation rather than comprehension support. This is evident in our participants’ perceptions and also corroborated by other research
Rahe & Maalej 2025
. As we have argued, next-generation computing students must become better system-level thinkers. To support this, GenAI-based code comprehension tools should be redesigned to emphasize the relationships between different components and illustrate the potential impact of GenAI-suggested code on those relationships
Siqueira et al. 2025
. A promising direction would be to develop a dedicated
Comprehension Mode
for GenAI assistants. In such a mode, the tool would not only provide code but also proactively explain the changes it is making, clarifying the context and potential impact on other parts of the system. Furthermore, instead of passively displaying a solution, GenAI tools should actively engage students with the generated response—for example, by decomposing generated responses into semantic segments and presenting them gradually to allow users time to fully interpret and understand the suggestions within the context of the existing code
Pu et al. 2025
;
Kazemitabaar et al. 2025
.

6.
Threats to Validity

6.1.
Internal Threats to Validity

One threat to internal validity is that participants recorded their own study sessions without human monitoring, which means some may not have strictly adhered to the instructions. To mitigate this threat, we developed a VS Code extension to guide participants through the programming tasks. The extension timed each task, ensured participants followed the correct sequence, and kept them within the time limit. A second threat to internal validity was that, since they did not work in a closed lab environment, some participants may not have fully focused on the study. To mitigate this threat, we asked participants to think aloud throughout the study, verbalizing their thought processes. Another internal threat is the potential shallowness of our comprehension questions. While objective, our seven questions may lack the sensitivity to reflect subtle differences in students’ comprehension of the code base. Future work should look into methods to probe for a deeper, less superficial comprehension of the code base. Lastly, participants had longer exposure to the code base in the Experimental condition, which always occurred last. This might suggest that they should have had higher comprehension in the Experimental condition, but that didn’t materialize.

6.2.
External Threats to Validity

This study has several threats to external validity. First, the findings may not generalize beyond the specific participant population: graduate-level software engineering students from a single university. Second, the study’s scope was limited by the task’s scale and duration. The code base was relatively small (3,818 lines of code), and the session lasted only 150 minutes. However, the observation that students struggled with comprehension even on this small code base suggests the problem would likely persist in larger, industry-scale legacy systems. Future studies should investigate these dynamics in more realistic settings, as work on legacy code typically spans days or weeks. Finally, the experiment focused exclusively on GitHub Copilot. The findings may not extend to other GenAI coding assistants, as their unique features could influence code comprehension differently.

7.
Conclusion

This study replicates and extends our prior work
Authors 2025
by assessing code comprehension immediately following programming tasks conducted without GitHub Copilot (Control) and with Copilot (Experimental). We observed a significant
comprehension-performance gap
when participants used Copilot: their code passed significantly more tests, but their understanding of the code base did not improve.

Our findings highlight at least three important directions for future research:

•

Investigating Expert Developers
: The
comprehension-performance gap
should be explored among expert developers engaged in "brownfield" programming tasks (i.e., tasks involving existing, complex code). Such a study could analyze how their programming activities and comprehension levels differ when using a GenAI assistant.

•

Scaling the code base
: This study should be replicated with larger and more complex code bases to test whether our findings scale to larger environments.

•

Pedagogical Strategies
: Research is needed to develop effective strategies for training computing students to use GenAI tools to foster high-level conceptual thinking and effective code integration, rather than relying on them solely for code generation.

Pursuing these research avenues will enhance the understanding of the
comprehension-performance gap
and help develop methods to mitigate it, ensuring that GenAI coding assistants become effective tools for both productivity and code comprehension.
