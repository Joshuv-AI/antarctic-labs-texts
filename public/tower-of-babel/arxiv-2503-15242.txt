BigO(Bench) - Can LLMs Generate Code with Controlled Time and Space Complexity?
Pierre Chambon, Baptiste Roziere, Benoit Sagot, Gabriel Synnaeve

Abstract
We introduce BigO(Bench) , a novel coding benchmark designed to evaluate the capabilities of generative language models in understanding and generating code with specified time and space complexities. This benchmark addresses the gap in current evaluations that often overlook the ability of models to comprehend and produce code constrained by computational complexity. BigO(Bench) includes tooling to infer the algorithmic complexity of any Python function from profiling measurements, including human- or LLM-generated solutions. BigO(Bench) also includes of set of 3,105 coding problems and 1,190,250 solutions from Code Contests annotated with inferred (synthetic) time and space complexity labels from the complexity framework, as well as corresponding runtime and memory footprint values for a large set of input sizes. We present results from evaluating multiple state-of-the-art language models on this benchmark, highlighting their strengths and weaknesses in handling complexity requirements. In particular, token-space reasoning models are unrivaled in code generation but not in complexity understanding, hinting that they may not generalize well to tasks for which no reward was given at training time.

Introduction

A junior developer writes an elegant solution to a coding challenge that passes all test cases, yet fails catastrophically in production. The issue isn’t a bug – it’s an
O(n^{2})
algorithm processing millions of records, when an
O(n\cdot\mathrm{log}(n))
solution could have handled the load effortlessly. As large language models (LLMs) increasingly assist in code generation, their ability to understand and control computational complexity becomes critical. While modern LLMs can generate syntactically correct and functional code with impressive accuracy, our new benchmark
BigO(Bench)
shows that they often struggle with the higher-level reasoning required to optimize time and space complexity – a skill that separates novice programmers from experienced engineers.

Our comprehensive evaluation of state-of-the-art code generation models reveals a concerning gap: while reasoning models like DeepSeek R1
(
DeepSeek-AI et al., 2025
)
achieve above 70% accuracy (pass@1) on programming contests (
CodeForces
1
1

1

https://codeforces.com/
), they show significantly weaker performance (4.8%) when tasked with generating solutions under specific complexity constraints (a detailed failure example is in Appendix
M
). They fare barely better than non-reasoning models at analyzing a function for its complexity, e.g. 6.8% better in complexity prediction vs. Llama 4 Maverick
(
Meta, 2025
)
. This limitation becomes particularly acute in real-world applications, where scalability and controllable, understandable, performance constraints are often as critical as functional correctness.

Our main contributions are threefold:

•

Firstly, to address the challenge mentioned above, we introduce
BigO(Bench)
, a novel benchmark for code generation that evaluates a model’s understanding of time and space complexities, including runtime and memory profiling measurements for a set of 3,105 coding problems and 1,190,250 solutions from
Code Contests

(
Li et al., 2022
)
. As shown in
fig.

1
, for a given coding challenge and human solution, the model can be queried to a. predict time-space complexities, b. generate code that solves the challenge while adhering to a specified feasible complexity, and c. on top of it ranks better than human solutions of the same challenge and complexity.

•

Secondly, we develop a complexity inference framework that takes a Python function and returns time and space complexities. It is a rule-based algorithm based on fuzzing, profiling, and regression over major complexity classes (including multi-dimensional ones). This is what we used to produce ground truth labels for
BigO(Bench)
, which are statistically significant ground truth performance profiles and not theoretical complexities. This complexity evaluation framework achieves 84% and 82% match (with human annotated theoretical complexity) respectively on time/space complexity test sets.

•

Thirdly, we evaluate 14 popular models on our benchmark along fine-tuned ones and compare performance in detail: using our
All@1
metric,
DeepSeek-R1 Llama70B

(
DeepSeek-AI et al., 2025
)
scores best on time complexity prediction (41.4%), while
Qwen3 32B
(
Team, 2025
)
leads on time complexity generation (6.5%) and
Llama 3.1 Nemotron-Ultra
(
Bercovich et al., 2025
)
on space complexity generation (5.6%).

Related Work

Benchmarks for Code Generation

As the coding skills of LLMs were still limited, benchmarks for code generation originally focused on simple functions and coding challenges, as illustrated by HumanEval
(
Chen et al., 2021
)
and MBPP
(
Austin et al., 2021
)
, probably the most famous coding benchmarks.
Today, these benchmarks are considered saturated, as top reported
pass@1
scores lean towards 90-95% success rate. A first area of work has focused on extending, improving quality and correcting these benchmarks, be it with HumanEval+, which adds more tests to pass
(
Liu et al., 2023
)
, or HumanEvalPack, which adds more tasks and programming languages
(
Muennighoff et al., 2023
)
.

A different area of research pursues scale and reasoning around code as a way to formulate benchmarks that can challenge LLMs over a longer term. SWE-Bench
(
Jimenez et al., 2023
)
and AssistantBench
(
Yoran et al., 2024
)
leverage Github as a source of large software development tasks, that do not resemble nor include obvious patterns of reproduction, therefore not solvable with simple fine-tuning on similar data. Nevertheless, the evaluation cost in time and compute is a non-negligible limitation that restrains certain teams from using these benchmarks.

BigO(Bench)
is a tentative benchmark to integrate challenging notions of reasoning around code into a simple formulation, providing a practical evaluation metric for code LLMs that can easily be used to discriminate and iterate improvements of their coding capabilities.

Time-Space Complexity Task

Coding interviews for software engineers are centered around small coding challenges to be solved and explained, typically by discussing the time-space complexity of the proposed solutions.
Only a few previous works attempted to frame the task of time-space complexity explanation for LLMs. Nevertheless, they all fall short of providing sufficient elements to build a solid benchmark: CoRCoD
(
Sikka et al., 2019
)
contains 932 Java code pieces labeled for five time complexity classes without using any LLMs;
TASTY
(
Moudgalya et al., 2023
)
uses 3000 C++/Python problems across five complexity classes, limited to classification only and just benchmarking small BERT models
(
Devlin et al., 2018
)
;
CodeComplex
(
Baik et al., 2024
)
contains 10k Python/Java programs annotated for five time complexity classes as classification only; finally RACE
(
Zheng et al., 2024a
)
contains limited test cases (
\sim
100) and only measure runtime similarity between proposed and human solutions.

Most of the work around code efficiency focuses on absolute runtime, memory, or resource measurement, scoring code as faster or lighter under a fixed execution setting
(
Qiu et al., 2024
;
Peng et al., 2025
;
Huang et al., 2024
;
Liu et al., 2024
;
Peng et al., 2024
;
Du et al., 2024
)
. More recently, this line has expanded to multi-language efficiency evaluation
(
Qing et al., 2025
)
, synthesized performance constraints
(
Yang et al., 2025b
)
, repository-level optimization for software-engineering agents
(
Shetty et al., 2025
;
He et al., 2025
;
Ma et al., 2025
;
Ren et al., 2025
)
, system-level high-performance code
(
Jing et al., 2026
)
, and optimization methods based on execution feedback, relative preferences, reusable skills, or iterative rewriting
(
Du et al., 2025
;
Hajizadeh and
Jana, 2026
;
Wang et al., 2026
;
Yang et al., 2025a
;
Wu et al., 2025
)
. Whereas absolute runtime remains context-dependent and conditioned on hardware and specific test cases being executed, code complexity reveals the intrinsic comprehension the model has of the underlying algorithmic structure of the code, measuring its efficiency at scale and its asymptotic performance.

Several recent papers have since studied closely related questions around complexity-aware and execution-grounded code evaluation. DynaCode, released in the same period, studies dynamic code-generation tasks with controlled structural and call-graph complexity, providing a complementary view of task difficulty rather than explicit time-space complexity control
(
Hu et al., 2025
)
. Other papers examine runtime behavior among correct generations, showing that solutions passing the same tests can still diverge in memory traces, opcode-level execution patterns, or stability under sampling
(
Rajput et al., 2026
;
Rajput et al., 2025
)
. SwiftSolve is a direct follow-up to the benchmark setting: it uses the work introduced in the present paper as an evaluation bed to study whether a multi-agent self-repair loop can improve generated solutions under complexity constraints
(
Singh et al., 2025
)
. These papers reinforce the same conclusion that pass/fail correctness is not sufficient, while
BigO(Bench)
specifically evaluates whether models can predict, generate, and rank solutions under explicit asymptotic time and space complexity constraints.

In order to improve on the previous attempts,
BigO(Bench)
explores not only time but also space complexity, out of an unconstrained set of classes to capture more various solutions and problems.
The benchmark not only studies the classification task but also the more challenging open-framed generation task, so to mimic the real-world thought process of designing a solution for a target complexity. Altogether, this turns out to create a challenging task that wide-used LLMs are benchmarked upon, and hopefully it provides a new perspective on the limitations of current models and their reasoning capabilities around code.

3
Dynamic Complexity Inference Framework

Throughout this study, complexity refers to worst-case complexity, finding how input growth maximally affects runtime and memory. Python is considered as the only language studied, and therefore complexity can account for python-specific optimizations (e.g. CPython
(
Python Software Foundation, 2024
)
or the compiler) that get reflected in the empirical time and space measures. In the quest of finding the worst case scenario of a snippet of code, natural language constraints on the inputs as detailed in the problem description can be ignored, as long as the program runs and does not fail;
section

B.4
explains why we scope the measurement this way rather than to the input bounds stated by the problem. The framework therefore returns an empirical estimate of these complexities rather than a proof about the source, and
appendix

B
states the conventions it follows.

Figure 2:

Outline of the dynamic complexity inference framework. The framework takes a code snippet and a single example of inputs to this code snippet. Then, it processes the code snippet and proceeds with extensive inputs generation, based on the provided example of inputs: inputs are independently or interdependently increased in size, using several expansion methods that can be the identity or random, among else. This forms a queue of synthetic inputs on which to execute the provided code snippet. These executions happen independently in sandboxes, where runtime and memory footprint measures are taken. Once all the measures are collected, the framework can model the code snippet time and space dependencies to the different inputs. Using curve fitting, the time and space complexity of the code is computed on each input separately and then altogether. The global time and space complexity over all inputs is what is being returned.

Implementation

The time-space complexity framework is a rule-based algorithm that processes Python functions to infer time and space complexities dynamically. As depicted in
fig.

2
, it takes a Python function with example inputs and corresponding dataclass (
section

4.2
), processes them, then measures runtime and memory during several executions.
From a high-level perspective, the framework increases input sizes using various strategies to assess size impact on execution metrics (runtime, memory).
For multi-argument functions, arguments can be expanded independently or together to determine overall complexity, considering interdependencies.
Prepared code and expanded inputs run in independent
Bubblewrap
sandboxes
(
Bubblewrap contributors, 2024
)
to prevent harmful side effects. While running,
Cprofiler
is used for runtime measures and
tracemalloc
for memory footprint.
Using non-negative least squares curve fitting
(
Lawson and Hanson, 1974
)
on each set of measures, the coefficients and residuals of each complexity class are computed. The gold complexity class output for a given set of measures is chosen as the minimizer of the residuals, taking into account a simplicity bias (the more simple the complexity class is, the smaller the simplicity bias).
This curve fitting is applied on each set of measures, each corresponding to a different subset of arguments being expanded with a different expansion method.
Using ensemble methods, the global complexity of the Python function is computed by aggregating the individual complexity outputs along the different set of measures.
Finally, the complexity framework also returns the coefficients of the curve of each elected complexity. These coefficients can be leveraged to rank and classify different optimized Python solutions within the same complexity class. More details are provided in
appendix

I
.

Parametrization

The framework involves three main parametrized steps. The first step,
Process Allocation
, handles the multiple
(Code,Expanded\ inputs)
pairs to be run and measured for time and space, trying to maximize the execution throughput while minimizing its variability and instability. Second,
Execution Measures
consists in leveraging various measuring tools for various ranges of input size values with more or less granularity.
Third,
Complexity Fitting
relies on the measures obtained to apply various curve fitting methods, aggregation methods and ensemble methods to form the global complexity formula across all inputs.

Parameters from each of these three groups were optimized towards three metrics of interest: pure accuracy of detecting the correct complexity class, coverage by handling as many code snippets and problems as possible, and self-consistency of outputting stable results over multiple runs and across different compute instances. How much the released labels depend on each of these parameters, and how far the compute budget can be reduced before the labels degrade, are measured in
sections

I.6
and
I.7
.

Composition

Codeforces

Codeforces
mostly (and in minority from a few other coding platforms),

(

We annotated data from

In addition, problems that have no working dataclass (see
section

4.2
), too few solutions (fewer than 50) or unusual data types are also filtered out.
This finally leads to our general

dataset, consisting of 3,105 coding problems and 1,190,250 annotated solutions. Problems are characterized by their difficulty level (A: 942; B: 682; C: 427; D+: 321; Unknown: 733), their algorithmic notions (37 different notions in total) and their inputs (1 to 11 distinct arguments across 32 different data types).

Each solution is annotated by the complexity framework and associated with time and space complexity classes, the corresponding coefficients of the complexity curves and the runtime/memory-footprint measures that were used to infer these attributes. Therefore, each problem gets associated with one or several time-space complexity classes consisting of solutions that have various complexity coefficients, corresponding to different optimization tricks within the same class of complexity. 4.2
Dataclass Generation

To infer labels with the complexity framework on
Code Contests
code snippets, code inputs must be parsable into a dataclass matching
Algorithm

1
. We define the task of dataclass generation as querying a LLM for such dataclass given the problem description and an example solution. For each generated dataclass
Input
, we introduce two metrics that measure the quality of the dataclass methods
Input.from_str
(converting string stream inputs to argument dictionaries) and
Input.__repr__
(the reverse conversion). These dataclasses let the framework expand selected arguments and rerun the original solution on new input scales, instead of being limited to raw
Code Contests
input strings. They also make input parsing a separately measured bottleneck: when no correct dataclass can be produced, the problem cannot be used for dynamic complexity inference, even if many accepted Python solutions are available.

Performance is measured by
Corr
, that accounts for the correction (executability) of the methods
Input.from_str
and
Input.__repr__
, and
BckTr
, which measures accuracy of the backtranslation
(
Edunov et al., 2018
)
:

input_ == Input.from_str(input_).__repr__()

Corr@k
and
BckTr@k
are unbiased estimators of performance of
Corr
and
BckTr
among k samples, following the definition of
Chen et al. (2021)
. Mathematical definitions of these metrics are provided in
section

A.1
.

Code Contests

4.3
Complexity Framework Performance

Accuracy
A human review measured the accuracy of the labels as output by the complexity framework (after post- processing and filtering) compared to the labels assigned by a human. The framework achieves 84% and 82% accuracy on time and space complexity test sets respectively (125 sample split each).
Appendix

C
measures how much an error rate of this size can affect the comparison between models.

Coverage

fig.

4
measures the ratio of solutions per problem for which the framework fails to predict a label. Whatever the type of complexity, approximately 84% of problems have a fail rate below 30%, and only 4.5% of problems have a fail rate above 0.9, for reasons ranging from incorrect generated dataclass to an edge case not covered by the range of tests the framework performs. Most input types are correctly covered by the framework. Exceptions (e.g. tuple and triple-nested lists) are infrequent.

Self-consistency
Relying on empirical runtime and memory measures exposes the framework to stochastic noise affecting prediction reliability. Running the framework 20 times on 10 solutions of every problem and complexity class of the candidate test set, before any filtering based precisely on stability, 91.9% (resp. 89.1%) self-consistency is achieved for time (resp. space) complexity, for a total of 10,130 (resp. 10,520) different code solutions.
Section

C.2
shares more details about the different error rates, including the human-based review, this self-consistency number and the reproducibility of the framework verdicts on model-generated code.

At a more granular level, models tend to under-perform on non-optimal complexity classes, compared to the most optimized class of every problem, as underlined in

Token-space reasoning models
Though they largely outperform other LLMs on pure program synthesis, reasoning models such as
o1-mini
,
DeepSeek-R1
and
Llama Nemotron-Ultra
are much closer in terms of performance on complexity-related tasks, and these are even outperformed by
Qwen2.5-Coder
on space complexity prediction specifically: while the latter obtains 12.6
All@1
, the former respectively only reach 8.1, 10.4 and 10.3. For this specific case, reasoning models seem to exhibit patterns of overthinking, misunderstanding the notion of extra space complexity, even if clearly described in the prompt. When explicitly prompted in order to understand their failure modes, it turns out that such models are able to recognize all classes of complexity of a problem from a prediction point of view, but when asked to generate them, they fail to return the less optimized classes of complexity, favoring the optimal solution. Not to mention that these models could just easily ‘cheat’ by tweaking the optimal solution with a dummy sort or nested for-loop, so to transform it, as any programmer could figure it out, as a less-than-optimal solution.

In general, these models struggle with the ambiguity of higher-level reasoning tasks, especially when there is no explicit verifier that they may have been confronted with during their reinforcement, such as programming tests to pass. This triggers the question of whether they really understand how to ‘think’ about notions they ‘know’, or if they only learn by heart patterns of ‘thoughts’ exhibited by human annotation efforts and training rewards. As all these complexity solutions were, in fact, in their training data, it suggests that these highly efficient search models can still fail to recover the correct data points when they were not reinforced for the specific search criteria.

Developing challenging reasoning benchmarks
As newly released benchmarks usually quickly saturate,
BigO(Bench)
aims at evaluating high-level reasoning skills that stay out-of-scope of current LLMs, bringing their performance down as displayed by
fig.

6
.
table

4
measures that the benchmark remains robust to fine-tuning. In particular, complexity prediction fine-tuning barely improves performance on the same task, and complexity generation fine-tuning even slightly hurt the performance of LLMs. This suggests that learning such high-level reasoning tasks is not effectively captured by standard fine-tuning to learn logical deduction and more convoluted patterns of thoughts.
With reasoning models topping benchmarks, new challenging benchmarks are perhaps more about finding out-of-distribution patterns of thinking rather than new data points of existing reasoning scenarios. It was especially difficult to design
BigO(Bench)
without any human labels available, as the qualification level required from annotators was not reachable. But this is also probably why the models had been underexposed to this reasoning task, therefore making it challenging for them.

Limitations
The complexity framework itself is prone to errors, as for specific problems it can potentially fall upon worst-complexity edge cases. In addition, the measures on which the complexity prediction is based remain noisy, still relying on real CPU runtimes and using statistical measuring tools; they could potentially become more reliable with the help of virtual CPU cores.
Appendix

C
quantifies how much this noise can affect the comparison between models, and
section

I.6
how much the released labels depend on the framework parameters.

Although we fine-tune
Llama
models, we did not use advanced multiturn prompting
(
Zheng et al., 2024b
)
nor further reinforcement
(
Gehring et al., 2024
)
. Proximal Policy Optimization
(
Schulman et al., 2017
)
could help refine LLMs for these tasks.
Human annotations could also help models reason better for these tasks. Finally, the coding problems and the framework remain limited to Python. Mixing other languages such as C++ and Java could measure cross-languages optimization strategies.

7
Conclusion

In this work, we introduced
BigO(Bench)
, a novel benchmark of LLMs on code generation, focusing on their understanding of time and space complexities when producing code. It consists in three tasks: first, given a coding challenge, predicting the time-space complexity of a given corresponding solution; second, for a given challenge and time or space complexity, generating a solution that solves the challenge while fulfilling the complexity requirements; third, optimizing the coefficient of the complexity cure compared to the human distribution. This benchmark is supported by time-space complexity labels corresponding to 3,105 coding problems and 1,190,250 corresponding solutions from
Code Contests
. In addition, we developed a complexity framework capable of dynamically inferring the time-space complexity of a given snippet of code, used to automatically evaluate any synthetic snippet of code and therefore the generation of LLMs conditioned on a given complexity trade-off. Finally, we benchmark 14 LLMs considered as the top coding assistants and analyse their performance.

BigO(Bench)
is a challenging benchmark with current top scores belonging to the reasoning models
DeepSeek-R1 Llama 70B
,
Qwen3 32B
and
Llama Nemotron-Ultra
, achieving up to 6.5% and 5.6%
All@1
on the time-space complexity generation tasks. Even when fine-tuning a
Llama 3.1 70B
model, performance increases only marginally, only on prediction tasks. We hope this benchmark can keep challenging upcoming models and help guide the development of new models towards better understanding of coding abstract notions beyond pure code generation.

Appendix A
Formal Metric Definitions

A.1
Dataclass Generation Metrics

In order to measure the quality of the dataclasses as generated by an LLM, we introduce two metrics
Corr
and
BckTr
, used over a test set of code problems and solutions to compare performance of LLMs on the dataclass generation task.

We introduce the following variables, and the structure of a problem dataclass:

•

P
= Problem description

•

S
= Example solution

•

D
= LLM-generated dataclass (from
P
and
S
), that has the following class template (see
Algorithm

1
):

D=\begin{cases}D\text{.from\_str}(\cdot):\text{str}\to\text{dict}\\
D\text{.\_\_repr\_\_}():\text{dict}\to\text{str}\end{cases}

•

input
= Input string, that corresponds to the input of an Input/Output test case pair of the code problem

•

D.\text{from\_str}(\text{input})
= Dictionary of parsed arguments

•

D.\_\_\text{repr}\_\_()
= String representation of parsed arguments

•

\mathcal{P}
: Distribution over problems
P

•

\mathcal{S}(P)
: Distribution over human solutions
S
for problem
P

•

\mathcal{D}_{LLM}(P,S)
: LLM’s output distribution for dataclass
D
given
P
and
S
.

•

\mathcal{I}(P)
: Set of test case inputs for problem
P
.

Based on these definitions, we define the following two metrics:

1.

Correction (Corr)
: Executability of both methods

\text{Corr}=\mathbb{E}_{P\sim\mathcal{P},\,S\sim\mathcal{S}(P),\,D\sim\mathcal{D}_{LLM}(P,S)}\mathbb{I}(D.\text{from\_str}(\cdot)\text{ and }D.\_\_\text{repr}()\text{ are executable})

2.

Backtranslation Accuracy (BckTr)
: Round-trip consistency

\text{BckTr}=\mathbb{E}_{P\sim\mathcal{P},\,S\sim\mathcal{S}(P),\,D\sim\mathcal{D}_{LLM}(P,S)}\mathbb{I}\left(\bigcap_{\text{input}\in\mathcal{I}(P)}\left(\text{input}==D.\text{from\_str}(\text{input}).\_\_\text{repr}()\right)\right)

In practice, we approximate these metrics, especially as we operate under a fixed sampling budget for the LLM. We define a sampling budget parametrized by
n
, the number of times we sample a dataclass
D
from
\mathcal{D}_{LLM}(P,S)
. Each problem is sampled with equal probability, and for the sake of limiting the compute budget only the first human solution of the attached set of solutions
\mathcal{S}(P)
is used to compute the metrics. Then, for each
(P,S)
, we use the model to generate
n
samples
D_{1},\dots,D_{n}\sim\mathcal{D}_{LLM}(P,S)
.

We generalize the above metrics to the case of
k
-success, where we record the probability that at least one of
k
generated dataclasses
\{D_{i}\}_{i=1}^{k}
satisfies the metric. We use the full compute budget of
n
possible samples (in practice we take
n=2\times k
) to compute the unbiased
pass@k
estimator from
Chen et al. (2021)
.

This leads us to the following definitions of the estimators
Corr
@k
and
BckTr
@k
:

1.

Corr
@k
estimator that at least one of k LLM attempts satisfies dataclass correction

\text{Corr}=\mathbb{E}_{\begin{subarray}{c}P\sim\mathcal{P}\\
S_{1}\in\mathcal{S}(P)\end{subarray}}\left[1-\frac{\binom{n-c}{k}}{\binom{n}{k}}\right],\quad\text{where }\begin{cases}c=\sum_{i=1}^{n}\mathbb{I}(\text{Corr is satisfied for }D_{i}),\\
D_{i}\sim\mathcal{D}_{LLM}(P,S_{1}).\end{cases}

2.

BckTr
@k
estimator that at least one of k LLM attempts satisfies backtranslation of the dataclass methods

\text{BckTr}=\mathbb{E}_{\begin{subarray}{c}P\sim\mathcal{P}\\
S_{1}\in\mathcal{S}(P)\end{subarray}}\left[1-\frac{\binom{n-c}{k}}{\binom{n}{k}}\right],\quad\text{where }\begin{cases}c=\sum_{i=1}^{n}\mathbb{I}(\text{BckTr is satisfied for }D_{i}),\\
D_{i}\sim\mathcal{D}_{LLM}(P,S_{1}).\end{cases}

A.2
Complexity Metrics

A.2.1
Complexity Prediction Metrics

The first evaluation task,
Complexity Prediction
, involves predicting the time and space complexity of a problem given its description and a human solution. The metrics for this task are defined as follows:

•

Pass@k
: Measures the accuracy of correctly predicting the complexity class for each problem, macro-averaged across complexity classes and then across problems. The unbiased estimator among
k
samples is used.

•

Best@k
: Measures accuracy only for the most optimized complexity class of each problem, using the unbiased estimator among
k
samples.

•

All@k
: Requires correct complexity output across all complexity classes simultaneously for each problem, using the unbiased estimator among
k
samples.

We share below more formal definitions of these metrics. First, we define the following setup for the task, on top of the general set up of coding problems involving problems
P\sim\mathcal{P}
and corresponding human solutions
S\sim\mathcal{S}(P)
as introduced in
section

A.1
:

•

\mathcal{C}
: Set of complexity classes (e.g., time, space).

•

For each problem
P
,
\mathcal{C}(P)\subseteq\mathcal{C}
: Subset of complexity classes relevant to
P
. This set is determined in our case using the complexity framework on the ground truth human solutions, and post-processing the distribution of complexity classes (typically to remove any obvious outlier).

•

\mathcal{H}(P,c)
: Set of human solutions for problem
P
and complexity class
c\in\mathcal{C}(P)
.

•

S^{\prime}
: LLM-generated solution containing the predicted complexity for the given human code
S
and problem
P
. This solution is generated by the LLM
S^{\prime}\sim\mathcal{D}_{LLM}(P,S)
.

•

G
is the function that extracts the ground-truth label assigned to the human code, the very same complexity that we are trying to predict using the LLM.

•

\text{parse}(S^{\prime})
: Parsing function that extracts the predicted complexity of class
c^{\prime}
from
S^{\prime}
.

•

\mathbb{I}_{\text{correct}}(S^{\prime},S,P)
: Indicator function equal to 1 if
\text{parse}(S^{\prime})=G(S)
, else 0.

That said, we define the above introduced metrics as the following:

1.

Pass@k
: Measures correctness for each complexity class of each problem independently, averaged over all classes and problems. Correctness of having at least one correct solution out of
k
attempts, using a sampling budget of
n>k
(usually using
n=2\times k
):

\text{Pass@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[\frac{1}{|\mathcal{C}(P)|}\sum_{c\in\mathcal{C}(P)}\left[1-\frac{\dbinom{n-c_{c}}{k}}{\dbinom{n}{k}}\right]\right],

where
c_{c}
is the count of times the LLM found the correct solution, that is to say labeled the complexity class of the human solution correctly:

c_{c}=\sum_{i=1}^{n}\mathbb{I}_{\text{correct}}(S^{\prime}_{i},S_{1},P),

and
S_{1}
is a human solution from the same problem and complexity class
S_{1}\in\mathcal{H}(P,c)
.

2.

Best@k
: Evaluates correctness only for the best (e.g., most efficient) complexity class per problem, in particular the probability of getting one correct answer among k answers:

\text{Best@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{c_{\text{best}}}}{k}}{\dbinom{n}{k}}\right],

where
c_{c_{\text{best}}}
is the count of times the LLM found the correct solution, that is to say labeled the complexity class of the human solution correctly, only for the best class of complexity
c_{\text{best}}
for each problem:

c_{c_{\text{best}}}=\sum_{i=1}^{n}\mathbb{I}_{\text{correct}}(S^{\prime}_{i},S_{1},P),

where
c_{\text{best}}(P)
is the most optimized complexity class for
P
, and
S_{1}\in\mathcal{H}(P,c_{\text{best}}(P))
.

3.

All@k
: Joint accuracy across all complexity classes. It requires correctness for all complexity classes simultaneously:

\text{All@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{\text{all}}}{k}}{\dbinom{n}{k}}\right],

where

c_{\text{all}}=\sum_{i=1}^{n}\mathbb{I}\left(\bigcap_{c\in\mathcal{C}(P)}\mathbb{I}_{\text{correct}}(S^{\prime}_{i},S_{c},P)\right)

with
S_{c}\in\mathcal{H}(P,c)
.

These metrics all use the unbiased estimator
1-\frac{\dbinom{n-c_{.}}{k}}{\dbinom{n}{k}}
from
Chen et al. (2021)
, where
n
is the total number of samples, and
c_{.}
is the count of valid samples, usually parametrized by a complexity class for instance.

A.2.2
Complexity Generation Metrics

The second task, Complexity Generation, involves generating solutions that meet specific complexity requirements. The metrics are defined as follows:

•

Pass@k
: Measures performance of generating a correct solution that meets each complexity class requirement independently, averaged over all classes and problems.

•

Best@k
: Measures generation correctness for the most optimized complexity class per problem.

•

All@k
: Requires the solution to meet all complexity classes simultaneously for each problem.

For each problem
P\sim\mathcal{P}
:

•

\mathcal{C}(P)
: Set of complexity classes (e.g., time and/or space) that exist for a particular problem.

•

S^{\prime}
: Generated solution by the LLM. We can write
S^{\prime}(P,c)
or
S^{\prime}\sim\mathcal{D}_{LLM}(P,c)
to specify that the generation of the LLM is conditioned on a particular problem
P
and a requested complexity class
c
for the solution.

•

\mathbb{I}_{\text{correct}}(S^{\prime},P)
: 1 if
S^{\prime}
passes all tests associated with problem
P
which means it is evaluated as a correct solution to the coding challenge, 0 otherwise (therefore this does not take into account the complexity of the generated solution).

•

\mathbb{I}_{\text{class}}(S^{\prime},c,P)
: 1 if
S^{\prime}
meets complexity class
c\in\mathcal{C}(P)
, 0 otherwise. This does not depend on the correctness of the solution with respect to the coding challenge
P
alone. So a solution that compiles, runs and produces wrong results can potentially meet the complexity requirement.

In this context, we can define the following metrics associated with the task of complexity generation:

•

Pass@k
:

\text{Pass@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[\frac{1}{|\mathcal{C}(P)|}\sum_{c\in\mathcal{C}(P)}\left(1-\frac{\dbinom{n-c_{c}}{k}}{\dbinom{n}{k}}\right)\right],

where
c_{c}=\sum_{i=1}^{n}\mathbb{I}_{\text{class}}(S^{\prime}_{i},c,P)\times\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)
.

•

Best@k
:

\text{Best@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{\text{best}}}{k}}{\dbinom{n}{k}}\right],

where
c_{\text{best}}=\sum_{i=1}^{n}\mathbb{I}_{\text{class}}(S^{\prime}_{i},c_{\text{best}}(P),P)\times\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)
, and
c_{\text{best}}(P)
is the most optimized class in
\mathcal{C}(P)
.

•

All@k
:

\text{All@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{\text{all}}}{k}}{\dbinom{n}{k}}\right],

where
c_{\text{all}}=\sum_{i=1}^{n}\prod_{c\in\mathcal{C}(P)}\mathbb{I}_{\text{correct}}(S^{\prime}_{i,c},P)\times\mathbb{I}_{\text{class}}(S^{\prime}_{i,c},c,P)
with
S^{\prime}_{i,c}\sim\mathcal{D}_{LLM}(P,c)
.

A.2.3
Complexity Ranking Metrics

Concerning the Complexity Ranking Task, as explained in the main manuscript, the prompt is modified so as to query the model for the complexity generation task, with an optimization addition: the model needs to generate correct code, with correct complexity, as optimized as possible while adhering to this complexity requirement.

To formalize the metrics of this task, we add the following elements to the formalism defined in the previous subsections:

•

\mathcal{H}(P,c)
: Set of human solutions for problem
P
and complexity class
c\in\mathcal{C}(P)
.

•

\text{coeff}(S,P,c)
: Complexity coefficient of solution
S
for problem
P
and class
c
(lower is better).

•

\text{best\_coeff}_{LLM}(P,c)
: Best coefficient from
n=20
LLM-generated solutions for
P
and
c
. This is obtained by sampling
S^{\prime}_{1},S^{\prime}_{2},\dots S^{\prime}_{n}\sim\mathcal{D}_{LLM}(P,c)
and ranking
\text{coeff}(S^{\prime}_{1},P,c),\text{coeff}(S^{\prime}_{2},P,c),\dots\text{coeff}(S^{\prime}_{n},P,c)
.

•

\mathbb{I}_{\text{correct}}(S^{\prime},P)
has the exact same definition as for the complexity generation task. It measures whether the generated solution is correct for a given problem given its I/O test cases.

•

\mathbb{I}_{\text{class}}(S^{\prime},c,P)
has the exact same definition as for the complexity generation task. It measures whether a generated solution respects the complexity class it was conditioned upon.

We now introduce the following metrics.
Pass@k
,
Best@k
and
All@k
have the same definitions as in the complexity generation task:

•

Pass@k
:

\text{Pass@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[\frac{1}{|\mathcal{C}(P)|}\sum_{c\in\mathcal{C}(P)}\left(1-\frac{\dbinom{n-c_{c}}{k}}{\dbinom{n}{k}}\right)\right],

where
c_{c}=\sum_{i=1}^{n}\mathbb{I}_{\text{class}}(S^{\prime}_{i},c,P)\times\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)
.

•

Best@k
:

\text{Best@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{\text{best}}}{k}}{\dbinom{n}{k}}\right],

where
c_{\text{best}}=\sum_{i=1}^{n}\mathbb{I}_{\text{class}}(S^{\prime}_{i},c_{\text{best}}(P),P)\times\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)
, and
c_{\text{best}}(P)
is the most optimized class in
\mathcal{C}(P)
.

•

All@k
:

\text{All@k}=\mathbb{E}_{P\sim\mathcal{P}}\left[1-\frac{\dbinom{n-c_{\text{all}}}{k}}{\dbinom{n}{k}}\right],

where
c_{\text{all}}=\sum_{i=1}^{n}\prod_{c\in\mathcal{C}(P)}\mathbb{I}_{\text{correct}}(S^{\prime}_{i,c},P)\times\mathbb{I}_{\text{class}}(S^{\prime}_{i,c},c,P)
with
S^{\prime}_{i,c}\sim\mathcal{D}_{LLM}(P,c)
.

•

COEFF
: Percentile ranking against human solutions of the same problem and complexity class. It compares the LLM’s best coefficient to human solutions in the same class. This metric uses a fixed sampling budget of size
n
(in our experiments we take
n=20
):

\text{COEFF}=\mathbb{E}_{P\sim\mathcal{P},\,c\in\mathcal{C}(P)}\left[\text{rank}_{LLM}(P,c)\right],

where:

\text{rank}_{LLM}(P,c)=\begin{cases}\frac{|\{h\in\mathcal{H}(P,c)\mid\text{coeff}(h,P,c)>\text{best\_coeff}_{LLM}(P,c)\}|}{|\mathcal{H}(P,c)|}\times 100&\text{if }\exists S^{\prime}\text{ valid},\\
0&\text{otherwise}.\end{cases}

In addition, we also introduce
\text{COEFF}_{intersect}
(and distinguish it from
COEFF
by denoting the latter one as
\text{COEFF}_{full}
) as the expectation used in the definition of
COEFF
restricted to a subset of problems and complexity classes. For the set
\mathcal{M^{*}}
of starred models of the complexity ranking table, we define the set of problems
\mathcal{P^{\prime}}
as the collection of problems
P
from
\mathcal{P}
where there exists at least one complexity class
c
associated with
P
, such that for every model
M
in the set
\mathcal{M}^{*}
, sampling
n
solutions from
M
on
P
and
c
yields at least one valid solution. Formally:

\begin{split}\mathcal{P}^{\prime}=\Bigl\{P\in\mathcal{P}\mid\exists c\in\mathcal{C}(P),\forall M\in\mathcal{M}^{*},\sum_{i=1}^{n}&\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)\times\mathbb{I}_{\text{class}}(S^{\prime}_{i},c,P)\geq 1\\
&\text{where }S^{\prime}_{i}\sim\mathcal{D}_{M}(P,c)\Bigr\}\end{split}

Similarly, we define the set of corresponding complexity classes
\mathcal{C}^{\prime}(P)
where all models are indeed producing at least one correct sample code. For any
P\in\mathcal{P}^{\prime}
, we define
\mathcal{C}^{\prime}(P)
:

\begin{split}\mathcal{C}^{\prime}(P)=\Bigl\{c\in\mathcal{C}(P)\mid\forall M\in\mathcal{M}^{*},\sum_{i=1}^{n}&\mathbb{I}_{\text{correct}}(S^{\prime}_{i},P)\times\mathbb{I}_{\text{class}}(S^{\prime}_{i},c,P)\geq 1\\
&\text{where }S^{\prime}_{i}\sim\mathcal{D}_{M}(P,c)\Bigr\}\end{split}

Based on that,
\text{COEFF}_{intersec}
can be formalized as:

\text{COEFF}_{intersect}=\mathbb{E}_{P\sim\mathcal{P^{\prime}},\,c\in\mathcal{C^{\prime}}(P)}\left[\text{rank}_{LLM}(P,c)\right]

where we are using the above definition of
\text{rank}_{LLM}(P,c)
.

Note that the COEFF metric uses the best coefficient from
n
(20 in practice) LLM attempts and ranks it against human solutions in the same complexity class. A higher percentile means the LLM’s solution is more optimized than most human solutions. The
Intersec
subset ensures comparisons are only made when all models have at least one valid solution, avoiding skewed rankings from partial failures. We are selecting models that are good enough in the first place so as to make the subset viable and interesting (it has to contain enough samples in the first place).
Finally, the unbiased estimator
1-\frac{\dbinom{n-c}{k}}{\dbinom{n}{k}}
remains consistent with prior work
(
Chen et al., 2021
)
.

Time and Space Complexity: Definitions and Conventions

\titleformat

BigO(Bench)

section

The theoretical complexity remains the target throughout, and
section

4.3

section

1
describes these labels as performance profiles and not theoretical complexities.

We first discuss the mathematical definitions of asymptotic notation and the notion of running case needed to carry them over to programs (
section

B.1
), then the convention commonly assumed in programming practice and the sense in which we adopt it (
section

B.2

section

B.3
). We then turn to the labels themselves: what
BigO(Bench)
discards from the competitive programming setting its data comes from (
section

B.4
), the finite space of classes a label is drawn from (
section

B.5
), and what a measured label does and does not pin down (

B.1
Big-O in Mathematics and Algorithmics

Big-O, big-Theta and big-Omega are defined in mathematical analysis
(
Cormen et al., 2022
;
Sipser, 2013
)
for real- or complex-valued functions on a domain that is typically the real or complex numbers, or tuples of real or complex numbers; they denote respectively an asymptotic upper bound, a tight bound and an asymptotic lower bound, each up to a constant factor. Programs can be defined on trickier domains: their inputs are integers, lists, strings, dictionaries and mixtures of these, not necessarily carrying a natural ordering or sense of growing to infinity. One can of course always fall back on the total number of bits of all the inputs, which does give an ordering and a sense of growing to infinity, but that map is not injective: many different inputs share the same bit count while costing wildly different amounts, so the cost is not a function of that size alone. Consider a function taking an integer and a dictionary, or a function taking an integer and a list, where it is not clear whether the list gets “bigger” when its elements grow in size or when the length of the list itself grows, not to mention how the content of the list may intertwine with the integer.

Running cases.

The gap between the mathematical definitions and the programming case can be closed with what we call a
running case
: a generator
g
that maps a single integer parameter
n
to an input of the program, obtained by scaling designated arguments of a given example input. The generator need not be defined at every
n
, since structural constraints on a problem’s inputs may leave some sizes unrealisable; it is enough that it be defined on an infinite set
S_{g}\subseteq\mathbb{N}
, along which the asymptotic statements below are read. The parameter is the size: a running case fixes what size means for the program at hand (we will see in
section

B.3
that in the multivariate case we can use tuples of size parameters). Write
f
for the program and
T
for the cost of the program we are interested in, either its runtime or its memory footprint, as typically recorded by a sandbox equipped with a clock and a memory profiler. Then
T(f\circ g)
is that cost as a function of
n
, for
f
run on the input
g(n)
. A running case makes it so we can apply the mathematical definitions:
T(f\circ g)
is a real-valued function of the single integer variable
n
ranging over
S_{g}
, to which
O
,
\Theta
and
\Omega
apply verbatim. The generated input is also required to grow without bound as
n
increases: a generator allowed to return the same input at every size would trace a flat curve for any program, and would give every program a best case in
O(1)
.

Writing
\mathcal{G}_{n}
for the running cases of
f
that are defined at
n
, the familiar cases are three aggregations over that set:

T_{\text{best}}(n)=\inf_{g\in\mathcal{G}_{n}}T(f\circ g)(n),\qquad T_{\text{avg}}(n)=\mathbb{E}_{g\sim\mu}\bigl[T(f\circ g)(n)\bigr],\qquad T_{\text{worst}}(n)=\sup_{g\in\mathcal{G}_{n}}T(f\circ g)(n).

(1)

Therefore
T_{\text{worst}}
is the worst cost among the possible inputs of a given size
n
when running the program on them. The expectation is different in kind, as it requires a distribution
\mu
over running cases. We do not use it. No principled
\mu
is available here, since weighting the running cases amounts to assuming a likelihood of seeing this or that shape of inputs when deploying the piece of code in real environments, and the answer depends entirely on that assumption: a distribution concentrated on random permutations gives Quick Sort
\Theta(n\cdot\mathrm{log}(n))
, while one concentrated on nearly sorted inputs gives
\Theta(n^{2})
. In general, because it takes many assumptions to reason about the average case, one estimates the best and the worst case instead, and the average is then either one of them or somewhere in between.
BigO(Bench)
uses the worst running case throughout.

Complexity analysis then amounts to characterizing how
T_{\text{worst}}
grows with
n
, applying the bounds to that cost curve rather than to the program itself. Of course, in the above definitions the growth rates of the different cases are loosely defined, depending on the exact parametrization of the generator function: the input can grow as fast as
n
, twice as fast, or along any “up to a constant factor” schedule. This is why big-O, big-Theta and big-Omega are the perfect tools for complexity analysis, characterizing growth rates “up to a constant factor”. Concretely, for a running case
g
and a growth function
h
:

•

T(f\circ g)(n)=O(h(n))
when there exist
c>0
and
n_{0}
such that
T(f\circ g)(n)\leq c\,h(n)
for every
n\geq n_{0}
, so that
h
bounds the growth of the cost along
g
from above;

•

T(f\circ g)(n)=\Omega(h(n))
when there exist
c>0
and
n_{0}
such that
T(f\circ g)(n)\geq c\,h(n)
for every
n\geq n_{0}
, so that
h
bounds it from below;

•

T(f\circ g)(n)=\Theta(h(n))
when both hold, so that
h
gives the growth of the cost exactly, up to a constant factor.

The same three definitions apply verbatim to
T_{\text{best}}
,
T_{\text{avg}}
and
T_{\text{worst}}
, which are themselves functions of
n
. Finding an
h
with
T_{\text{worst}}(n)=O(h(n))
is useful because it bounds every input at once: no input of size
n
costs more than on the order of
h(n)
. It does not say that the bound is reached, since the program may do better and a slower-growing
h
may bound it as well, so a big-O statement about the worst case leaves room above the actual behavior. Only
T_{\text{worst}}(n)=\Theta(h(n))
fixes the growth rate.

Cases and bounds are independent.

Selecting a running case determines which function of
n
is under discussion; choosing between
O
,
\Theta
and
\Omega
determines how that function is bounded. The two choices are orthogonal, and every combination of them is meaningful, as is standard in the algorithms literature
(
Cormen et al., 2022
)
and as shown in
table

5
. The lower bound on the worst case in the bottom-right cell of that table is the decision-tree bound on comparison sorting, one of the standard results of the field. Three running cases and three bounds give nine statements available about a program, not three.

B.2
Commonly Assumed Big-O Definitions in Programming

Programming practice keeps only a narrow, and kind of incorrect, version of these statements, by letting the letter determine the running case: big-O is identified with the worst case and big-Omega with the best case. In this usage, big-Theta reads as “the tight one”, which is what it means, though without saying which running case it is tight on.
Knuth (1976)
introduced big-Theta into computer science precisely to express tightness, because big-O was already being used as though it were tight, and the standard texts keep the case and the bound as separate axes.

Nevertheless, even if the popular programming practice uses big-O and the other notations in an improper manner, and it goes against the definitions we introduced in
section

B.1
, we try to adopt these conventions, for two reasons. The first is that it is the vocabulary in which the question is actually asked. Complexity is discussed among software engineers in the register of a coding interview for example, where a candidate is asked for “the complexity of this function” and is expected to answer with a single big-O expression, and
BigO(Bench)
measures how LLMs perform on the question as it is posed in practice. Restating the query in the terms of
section

B.1
would measure something else, namely how well a model follows the formal mathematical definitions, rather than what developers commonly expect.

The second reason is also that
BigO(Bench)
has to attach (within each best/worst/average case) a single label to each program, and that label has to be tight: without a tightness requirement, any program could be labeled
O(n!)
and no prediction would ever be wrong. The prompts state this directly, asking for the tightest possible upper bound in big-O notation.

These conventions can nevertheless be defined according to the precise terms of
section

B.1
:

\displaystyle O_{\text{conv}}(f)

\displaystyle=h\quad\text{such that }T_{\text{worst}}(n)=\Theta(h(n)),

\displaystyle\Omega_{\text{conv}}(f)

\displaystyle=h\quad\text{such that }T_{\text{best}}(n)=\Theta(h(n)),

\displaystyle\Theta_{\text{conv}}(f)

\displaystyle=h\quad\text{defined only when }O_{\text{conv}}(f)=\Omega_{\text{conv}}(f)=h.

Written this way the convention is self-consistent, and the sense in which it departs from the analytic definitions becomes explicit: it uses the symbol
O
to state a tight,
\Theta
-style fact about one particular running case. For big-Theta, since
T_{\text{best}}(n)\leq T(f\circ g)(n)\leq T_{\text{worst}}(n)
holds for every
g
, requiring
O_{\text{conv}}
and
\Omega_{\text{conv}}
to agree pins every running case to the same growth rate, so
\Theta_{\text{conv}}
exists exactly when the program is insensitive to which input of a given size it receives. Quick Sort, with a best running case in
\Omega(n\cdot\mathrm{log}(n))
and a worst running case in
O(n^{2})
, has no
\Theta_{\text{conv}}
, and the query “predict the big-Theta complexity of this program” becomes ill-defined.

Appendix

D
measures what changes of formulations imply, by rewriting the prompt in terms of big-Theta: the reasoning model moves from 40.3 to 39.9
All@1
on time complexity prediction, scored against the same worst-case labels. Models appear to read big-Theta as a request for a tight bound and to apply it to the same running case they would have used for big-O: being trained on data produced by developers who assume the conventions above, they probably adhere to them anyway.

B.3
Multi-Variable Complexity

Several
BigO(Bench)
classes take more than one variable, such as
O(n+m)
,
O(n\times m)
and
O((n+m)\cdot\mathrm{log}(n+m))
, and a running case as defined above would not produce them, since
T(f\circ g)
is a function of
n
alone. The input generators make it possible to grow several variables together at different rates, but in practice people find it useful, where it is defined, to recover the dependency on each variable separately. We therefore also index running cases by which arguments they grow. For a program taking arguments
a_{1},\dots,a_{k}
, a running case grows a chosen subset of them jointly at a common rate while holding the others fixed. Growing subsets one at a time gives the dependence of runtime and memory on each argument separately, and growing them together exposes interactions that the separate measurements miss, such as a loop nested over two arguments. The global label is composed from the per-subset fits, which is how a product term such as
n\times m
is told apart from a sum such as
n+m
.

Asymptotic notation over several variables carries subtleties that the single-variable definitions do not, since the domain admits several inequivalent notions of tending to infinity
(
Howell, 2008
)
. We do not dig too much into the subtleties of the multivariate cases in this paper, and stick to the above approach together with the finite label space of
section

B.5
.

B.4
Asymptotic Complexity Versus Code Competition Constraints

A code competition problem, for instance from
Code Contests
, comes with input bounds, along with a time limit. That limit exists for a practical reason: the judge has to evaluate every submission under a finite compute budget, which is only possible if each execution terminates within a reasonable bounded time. The input bounds are then chosen together with the timeout, so that a solution of the complexity the problem is designed around runs within it while a less efficient one exceeds it. A problem stating
n\leq 3\times 10^{5}
under a one-second limit is asking for an
O(n\cdot\mathrm{log}(n))
solution:
O(n^{2})
would amount to roughly
10^{11}
operations and time out, whereas
O(n\cdot\mathrm{log}(n))
comfortably fits. Asymptotic complexity is being enforced in a limited compute setting using input bounds and timeouts.

Dropping the timeout.

BigO(Bench)
gets rid of these limits, starting with the timeout. Fitting a complexity class to empirical runtime curves is already delicate, and asking the framework to also reproduce the pass or fail behavior of a problem-specific timeout would add a second and largely independent source of error. Timeouts are noisy quantities, and in code competition datasets they can even be improperly calibrated for a given problem in a given language
(
Chambon et al., 2026
)
. The framework therefore measures runtime and memory without reference to any time limit. It does bound its own executions, for the same practical reason any judge does, but those limits guard against runaway runs rather than serving as a criterion the solution is judged against.

Dropping the input bounds.

Discarding the timeout entails discarding the input bounds, since the bounds only carry information about complexity in conjunction with it: they were chosen to make a target complexity fit within a given limit, and taken alone they say nothing about how a program scales. In fact, they can only alter the complexity label being computed, and growing beyond them helps better determine the asymptotic behavior. The framework consequently grows inputs well past the stated bounds, up to
3000\times
the original input size (
appendix

J
). The cost is that the framework deliberately runs code outside the regime its author had in mind, which is why the prompts are updated to specify that inputs are assumed to potentially grow indefinitely. Code that silently relies on the stated bounds can fail once they are exceeded, which is in fact what our benchmark favors over solutions that enumerate cases to save a bit of runtime on a bounded subset of inputs, instead of achieving real asymptotic complexity improvements.

Evaluating beyond the intended complexity.

A further reason to detach a problem from its published constraints is that
BigO(Bench)
does not restrict itself to the complexity that problem was designed around. Each retained problem can carry several complexity classes among its solutions (
section

4.1
), and the prediction, generation and ranking tasks address the less efficient ones as much as the most optimized one, precisely in order to observe how models navigate between them. The generation task in particular can ask a model for a solution in a class the original competition would have rejected: a correct
O(n^{2})
program for a problem whose intended solution is
O(n\cdot\mathrm{log}(n))
is a valid answer here and a timeout for the judge. Bounds and a time limit calibrated for one target complexity cannot serve a setting that evaluates several.

Adapting the query.

The bounds affect the models as well. We noticed in preliminary experiments that, because the bounds appear in the problem description handed to the model, some LLMs treat the input as bounded and conclude that the program runs in constant time. When asked to generate, they can also ‘cheat’ in the same way, writing code that only has to handle the finite set of inputs the bounds allow, enumerating or precomputing cases rather than implementing an algorithm of the requested complexity. Since the bounds exist for the purposes of the competition, and only in conjunction with its time limit, we state explicitly in the prompt that input sizes are to be assumed unbounded, which matches what the framework does for the reasons above. This keeps the stated constraints from steering the reasoning, and leaves the model to reason about the asymptotic complexity itself.

Consequences for the benchmark.

A label and a contest verdict can then disagree. A solution accepted by the original judge because the bounds were loose enough for it to fit within the time limit is still labeled by its asymptotic behavior, so an accepted
O(n^{2})
solution is labeled
O(n^{2})
, and would be rejected in our evaluation for not matching the best complexity. That disagreement is what makes the benchmark discriminative: several complexity classes can coexist among accepted solutions to the same problem when the bounds leave enough slack for a suboptimal algorithm to pass, but
BigO(Bench)
can still differentiate them by looking at their complexity directly.

B.5
The Space of Possible Complexity Labels in
BigO(Bench)

The framework fits a fixed library of base growth functions, combined with addition and multiplication, and returns the member of the resulting finite set
\mathcal{C}
of complexity classes that minimizes the fitting residual under a simplicity bias (
appendix

I
). Multi-variable classes such as
O(n+m)
and
O(n\times m)
arise from the same construction applied across several arguments (
section

B.3
).

A
BigO(Bench)
label is a minimizer over
\mathcal{C}
, not the result of a search over all growth functions, so a program whose true growth lies outside
\mathcal{C}
receives the nearest representable class, which gets considered as a fitting error.
Appendix

I
lists growth functions that the current library does not represent. The time complexity test set exercises 11 classes and the space complexity test set 5 (
section

4.1
), though the training set is much larger and therefore covers many more classes. Model predictions are compared against these labels after normalization, so that different ways of writing a complexity, by changing letters, order or notation, do not affect the match;
section

A.2
defines the metrics computed on top of that comparison.

The classes reachable for a given problem also depend on its dataclass (
section

4.2
). The dataclass determines how the input string is decomposed into separate arguments, and the framework can only attribute growth to arguments that the dataclass exposes. A dataclass parsing a graph problem into a vertex count and an edge list allows a label in
O(n+m)
, whereas a correct but coarser dataclass returning a single argument restricts the same problem to a single-variable label. Dataclass generation therefore bounds not only which problems enter the benchmark, but also which labels those problems can receive.

B.6
What a
BigO(Bench)
Label Is

From the definition to the measurement.

Section

B.1
defines the worst running case as the upper bound over all admissible generators, whereas the framework computes the maximum over the running cases it implements, a finite subset
\mathcal{G}_{\text{impl}}\subset\mathcal{G}
. The measured label is therefore a lower bound on the true worst case, and the two coincide only when
\mathcal{G}_{\text{impl}}
is rich enough to reach the worst behavior of the program.
Section

B.7
gives the standard example of a program where this can happen.

Input size.

Complexity is expressed in terms of the size of each argument, and size is defined per argument type: for a list, a string or another sequence, its length; for a dictionary or a set, its number of entries; for an integer, its value. These are defaults rather than a fixed rule. The ambiguity raised in
section

B.1
, where a list can be said to grow either by holding more elements or by holding larger ones, is handled through the dataclass (
section

4.2
), which can either expose one growth axis or several: a list of strings can be decomposed into the length of the list and the maximum length of the strings it contains, so that growth along each is measured separately. Composite arguments are where the notion is least clear, and they are also where coverage is weakest:
section

4.3
reports nested structures such as triple-nested lists among the infrequent input types the framework fails to handle.

Cost model.

Because the label comes from running the code,
BigO(Bench)
assumes no cost model for individual Python operations: whatever CPython does at runtime is what the curve fit sees. Amortized costs, constant factors coming from C-level implementations, and interpreter-level optimizations are all reflected in the label. This can separate the measured label from the one a static reading produces, in both directions – a solution that reads as linear may pay a hidden cost inside a built-in call, and a solution that reads as quadratic may benefit from an optimization in the interpreter.
Section

B.7
gives a concrete case. The choice was made so to also reflect interesting language-specific optimizations, which are definitely playing a big role on the problems we chose to work on (from top code competitions).

Space semantics.

Space complexity in
BigO(Bench)
refers to the peak memory allocated during execution, as recorded by
tracemalloc
, not counting the initial space used by the inputs. The prompts state the convention the models are asked to follow: reading the input consumes no memory, any operation performed on top of the parsed input is counted, and printed output counts towards memory. This is the notion of
extra
space complexity, and it is the one against which the space labels, the space prediction task and the space generation task are all defined.
tracemalloc
can have limitations in accounting for all the memory a program uses, and improving the measurement tools is left for future iterations of the benchmark.

Constants and lower-order terms.

A complexity class discards constant factors and lower-order terms: an algorithm performing
2n
operations and one performing
100n
operations are both
O(n)
, and
n^{2}+n
is
O(n^{2})
, since the quadratic term dominates.
BigO(Bench)
measures the discarded constant separately. The framework returns the coefficient of the fitted curve alongside the class, and the ranking task of
section

5.3
compares solutions within a single class by that coefficient. The class captures how a solution scales, the coefficient captures what the asymptotic statement leaves out, and both contribute to what separates an optimized solution from a merely correct one.

B.7
Examples

Complexity on graphs.

Graphs are a good example to look at to illustrate complexities. They are characterized by their number of vertices
n
and of edges
m
, and running cases can take a lot of shapes.

Take a search that stops as soon as it finds what it is looking for. If the target sits right next to the starting vertex, the search costs almost nothing; if it sits as far away as possible, the search goes through the whole graph and costs
\Theta(n+m)
. Same program, two very different running cases. A full traversal is the opposite: breadth-first and depth-first search go through every vertex and every edge whatever the graph looks like, so the best and the worst running case are the same, and the program does have a
\Theta_{\text{conv}}
(
section

B.2
).

That full traversal is also where one variable stops being enough. It runs in
O(n+m)
, and we cannot drop either term. If we grow the graph keeping
m
around
n
, which is a sparse graph, the curve looks linear and we would say
O(n)
. If we grow it keeping
m
around
n^{2}
, which is a dense graph, the curve looks quadratic and we would say
O(n^{2})
. Neither answer is wrong, they just describe different running cases, and only the two-variable label describes the program.

Note that
n
and
m
are tied to each other: a simple graph has
m\leq n(n-1)/2
and a connected one has
m\geq n-1
, so on connected graphs
n=O(m)
and
O(n+m)
becomes
O(m)
. Even having two variables depends on the graphs we feed the program. This is also where the bounds of
section

B.4
play a role: a problem saying
n\leq 10^{5}
and
m\leq 2\times 10^{5}
is telling the competitor that the graph is sparse, so the traversal can be treated as linear. Drop the bounds and we are back to two variables.

Time and space do not always move together. With an adjacency matrix the graph takes
O(n^{2})
memory, checking whether an edge exists is immediate, and the traversal takes
O(n^{2})
whatever
m
is, because it reads a full row per vertex. With an adjacency list the graph takes
O(n+m)
memory and the traversal takes
O(n+m)
, but checking an edge now costs the degree of the vertex. Same algorithm from the textbook, different time and space labels, which is one reason we label both. And which of the two sizes the framework can even see depends on the dataclass (
section

B.5
).

What a measurement can tell apart also depends on the graphs it runs on. Dijkstra with a binary heap is
O((n+m)\cdot\mathrm{log}(n))
, and with a Fibonacci heap it is
O(m+n\cdot\mathrm{log}(n))
. On sparse graphs both are
O(n\cdot\mathrm{log}(n))
and nothing measured there will separate them; on dense graphs they differ by a log factor. Even when the class is the same, the coefficient of the curve is not, and that coefficient is what the ranking task of
section

5.3
looks at.

Finally, some costs only make sense over a whole sequence of operations, and some differences are too small to ever show up. A single union-find operation with path compression can cost
O(\mathrm{log}(n))
, but
m
of them cost
O(m\cdot\alpha(n))
in total, so only the amortized cost says anything useful. And
\alpha
, the inverse Ackermann function, stays below 4 for any
n
we could ever run, so no curve fitting will ever tell
O(m\cdot\alpha(n))
from
O(m)
: those two only come apart at input sizes that do not exist.

Appendix C
Robustness of the Evaluation to Label Error

The complexity labels of
BigO(Bench)
are produced by measurement, and
section

4.3
reports that they agree with human annotation on 84% of time complexity samples and 82% of space complexity samples. A natural concern is whether an error rate of that size can distort the comparison between models of
table

2
. We address it in three steps: we measure the random component of the label error, we then corrupt the labels deliberately at rates well above it, and we report what happens to the rankings.

C.1
Label Error in Benchmarks

Benchmarks whose labels are imperfect are the norm rather than the exception, and the rates they report can be larger than the error rates measured for
BigO(Bench)
.
Northcutt et al. (2021)
estimate at least 3.3% label errors on average across ten widely used test sets, including 6% of the ImageNet validation set and 10% of QuickDraw.
Beyer et al. (2020)
find that roughly 29% of re-annotated ImageNet validation images either contain several objects or fall under a category with multiple synonym labels.
Gema et al. (2024)
re-annotate 5,700 MMLU questions with 14 experts and estimate 6.49% erroneous questions overall, rising to 57% on one subject. In each case the response was to correct and continue rather than to discard:
Beyer et al. (2020)
conclude that their re-annotation reinforces ImageNet as a benchmark, and
HumanEval
remains the most cited code generation benchmark despite
HumanEval+
showing that its improved test suites cut reported
pass@k
by up to 19.3–28.9%, while the ordering of models barely moves and the few flips that do occur are confined to near-ties
(
Liu et al., 2023
)
. The same holds for
Code Contests
, which
BigO(Bench)
itself as well as a number of other code-competition test sets are built on:
Wang et al. (2025)
re-execute 1.72 million labeled submissions against its test suites and find that, among the 10,166 problems with enough submissions to score, over 4,000 have test cases that reject almost every correct solution, which they trace to incorrect test cases and to the absence of checkers for problems admitting several valid outputs. We do account for this when building the time and space complexity test sets: as described in
section

4.1
, we only keep problems with at least 50 human solutions passing the
Code Contests
tests, so a problem whose suite rejects nearly every correct submission never reaches our test sets.

Rankings can move under label error, but only under specific circumstances that are not at stake here.
Northcutt et al. (2021)
report that model rankings on the full ImageNet and CIFAR-10 test sets are unaffected by correcting the labels, and that inversions appear only once the test set is artificially enriched in the examples that had been mislabeled, all of them scored with their corrected labels: ResNet-18 overtakes ResNet-50 when those examples make up 6 points more of the test set, and VGG-11 overtakes VGG-19 at 5 points. But this happens because the models were trained in the first place on data carrying the same labels. The mechanism they identify is that higher-capacity models reproduce the distribution of
systematic
label errors they learned from that training data. That mechanism needs the model to have learned the annotator’s mistakes, which is not what we do here: the models compared in
table

2
are all directly evaluated on the test set, without ever being confronted with the labels output by the complexity framework during any training stage. Therefore, none of them is given the chance to overfit to the potential systematic errors of the labeler.

Getting human-derived labels has its own share of issues, both in annotator agreement and in scaling, and using an automatic labeler is not necessarily detrimental as long as it is clearly detailed and explained.
Gema et al. (2024)
report inter-annotator agreement between Cohen’s
\kappa=0.64
and
0.96
on the binary judgment of whether a question is erroneous, a considerably simpler call than assigning a complexity class to top code competition problems. Automatically derived labels are common wherever expert annotation does not scale: in
CheXpert
, labels extracted from radiology reports reach a macro-F1 between 0.34 and 0.44 against image-based expert annotation across 14 pathologies, against 0.65 to 0.93 when scored on the text they were derived from, and the dataset is a standard resource nonetheless
(
Chambon et al., 2024
)
.

The specific field of automated complexity analysis is itself a difficult task, which we believe also mitigates the severity of the error rates we observed in
BigO(Bench)
.
SPEED
derives complexity bounds by static analysis of the source, without ever running the program, and only manages a precise bound for “more than half of the loops that we have seen in practice”
(
Gulwani et al., 2009
)
, returning nothing usable on the rest.
GuessCompx
, an empirical estimator, reports per-algorithm accuracies from 38% to 99% over five algorithms
(
Agenis-Nevers et al., 2019
)
.
Trend-Prof
, the reference work on empirical complexity measurement, treats the divergence between measured and theoretical complexity as its contribution rather than as error, reporting programs that beat their worst-case theoretical bound and arguing that the measured curve gives “a more accurate working performance model”
(
Goldsmith et al., 2007
)
. Part of any disagreement between our framework and a human annotator could be seen as that same divergence rather than a mistake, and
appendix

B
further details what the
BigO(Bench)
labels are and how they relate to, and differ from, the theoretical target.

Label error splits into a systematic part and a random part. The systematic part – the framework consistently reading some pattern as

The 84%/82% figure is the right number for asking whether the labels are true; it is not the right number for asking whether label error can flip a ranking.

C.3
Ranking Stability Under Simulated Systematic Label Corruption

We explore two forms of label perturbations. On prediction we flip the
ground-truth
label of a (problem, class) pair; that label is a property of the test set, so the flip is
shared
across models. On generation we flip the framework’s verdict on a model’s own generated program; each model’s code gets its own framework call, so the flip is
independent
across models (on generation the target complexity is given in the prompt, so there is no hidden ground-truth label to corrupt in the first place, only the framework’s measurement of what the model produced). Flips can happen in three modes:
random
(transform into any potential class),
pessimistic
(one step slower) and
optimistic
(one step faster). Boundary classes have no neighbor in one direction and can sometimes be left uncorrupted, so the realized rate can fall below the nominal one.

Since rank inversions occur under sampling noise alone, showing that corruption causes some inversions would prove nothing. The question is whether corruption is model-dependent, and therefore biases the evaluation. We therefore use a paired bootstrap over 1000 replicates, running three experiments: experiment A resamples problems without corrupting, experiment B corrupts without resampling, and experiment C does both, with experiments A and C sharing the same problem resample within a replicate so that their difference isolates the corruption effect from sampling noise.

C.4
Sharing Label Errors Across Model Evaluations

Table

8
confirmed that a very limited number of inversions happen when corruption rates of the ground truth labels increase, even up to rates around 15%. Why? If we look at the complexity prediction task, a framework complexity label is a property of the (problem, solution) pair and not of the model being evaluated, so a wrong label is wrong for every model at once. An error of that kind is therefore a shared burden: it moves all scores down together and largely cancels in the pairwise difference that a ranking actually depends on. Sharing does not make the effect identical across models, and
table

10
is the case where it does not, but it is what keeps the residual differences at the scale of a percentage point rather than at the scale of the error rate itself.

The concern that a 16% error rate could swamp a few points between two models would be assuming the opposite, that each model draws its own set of bad labels. To get a sense of how much inflation this creates on score deviation, we also measured corruption under the independence hypothesis, and compared it with our shared-error experiments.
Table

11
reports the standard deviation of the difference between two models’ scores across replicates, with no problem resampling so that corruption is the only thing varying. Treating the error as independent per model inflates that standard deviation by a factor of 1.8 to 3.0, and comparing a per-item error rate (such as the 16% implied by the accuracy reported in
section

4.3
) directly against a gap between two models is exactly that independent reading.

In the case of the complexity generation task, the label attaches to each model’s own program, so it is not shared in the same literal sense. It is produced by the same framework, though: any systematic bias in how the framework reads a given pattern is the same bias for every model rather than an independent draw per model, and only the run-to-run randomness is genuinely independent. That randomness is the 3% measured in
section

C.2
, not the 84%/82% figure, which counts systematic and random error together. On both tasks, a per-label error rate therefore overstates the level of potential ranking errors.

Overall, the 84%/82% figure is the right number for asking whether a label is true, and the wrong one for asking whether the benchmark ranks models correctly. Label error at that scale is acceptable for a widely used benchmark, and larger rates elsewhere have rarely reordered anything. Corrupting the labels deliberately, at rates up to 20% and in three directions, scales every model by nearly the same factor and leaves at most 3 of 66 pairs inverted, the single exception being space prediction under optimistic corruption. The robustness of the benchmark comes from the fact that the error is carried by the labels and by the framework, both shared across models (not trained on the framework, and only exposed to it at test time), so it largely cancels in the differences a ranking depends on. Against the other sources of noise in the same experiment it is the smallest term on generation, and still the smaller of the two on prediction at a conservative 15%. A larger expert-annotated test set remains the way forward for future and more important efforts in this research direction, but the model comparisons of

Overall, the strongest correlations are between program synthesis and complexity generation: 0.81 for time complexity and 0.76 for space complexity, across all models in this appendix sweep. A likely explanation is that models are more frequently exposed to time optimization objectives when trained to generate code, since these objectives are more common on code competition platforms and more extensively documented than their space counterparts. Time prediction has a correlation coefficient of 0.56 with time complexity generation, suggesting that the program synthesis objective may still dominate this double-requirement task. For space generation, where we observe very low All@1 scores, the correlation between prediction and generation drops to 0.1. This is consistent with the low absolute performance on space generation: models often struggle with the space constraint and therefore behave more like generic program synthesis systems than like systems optimizing for a specified complexity target.

Finally, when comparing time and space tasks, we observe that time prediction correlates more with time generation than with space prediction. The converse does not hold: space prediction has a correlation coefficient of 0.5 with time prediction and only 0.1 with space generation. This again suggests that space generation remains dominated by the program synthesis objective, because the double objective is still too hard for most models. Time generation and space generation also correlate more strongly with one another than with their respective prediction counterparts.

Appendix H
Where Do the Differences in Complexity Prediction and Generation Come From

Table

2
shows a large gap between what models can predict and what they can generate, and
section

6
offers a qualitative explanation of why. Here we try to further refine that analysis with more measurements. Every generation attempt carries two independent bits: whether the program passes the tests, and whether the framework measures it in the requested complexity class. Separating them says what the failures are actually made of.

H.1
What Generation Failures Are Made Of

Four-way decomposition.

Crossing the two bits splits every attempt into a success and three kinds of failure: correct code in the wrong complexity class, incorrect code that happens to land in the right class (though this is limited in some sense, if the code crashes at the beginning it gets logged as
O(1)
, though from the structure of the code that’s not really what the theoretical complexity label would be), and code that is wrong on both counts. We report numbers for all of that for time complexity generation in
table

21
.

The dominant failure mode is a working program in the wrong complexity class. Its share of all failures ranges from 14% for
Codestral 22B
to 70% for
Llama 3.1 Nemotron-Ultra 253B
, and it tracks program synthesis ability: the better a model is at writing correct code, the more of its complexity failures are purely complexity failures rather than coding failures, and the space axis behaves the same way, from 17% to 68%. Complexity generation is therefore more than a correlate of program synthesis skill: for the models strongest at the latter, the
right code, wrong class
error does not diminish as fast as the purely wrong-code error. This has to be qualified, though. We cannot conclude that the best models at code synthesis are no better than the worst ones at complexity control, since the weakest models only face the complexity requirement on the problems they can solve at all, which are the easiest ones, whereas the strongest models face it on harder problems as well, precisely because they are able to write working solutions for them.

Appendix I
Framework Implementation Details

I.1
General Framework Outline

The time-space complexity framework is a rule-based algorithm that can process any Python function in order to infer its time and space complexities dynamically. The high-level principles of the framework are presented in
fig.

2
, explaining how it takes a code snippet and an input example and tries to infer a time and space complexity from it.

As inputs, it takes a Python function, its function inputs, and their corresponding dataclass, which are then processed and modified before runtime and memory footprints are measured. From a high-level perspective, the framework increases the size of inputs following various strategies, in order to assess the impact of input size on execution metrics (e.g. execution time, memory used). When the function has several arguments, they can be expanded independently or together to determine the overall complexity of the function, taking into account potential interdependencies. The prepared code, along with the various sets of expanded inputs, is queued and run in independent sandboxes, using the
Bubblewrap
library
(
Bubblewrap contributors, 2024
)
, to avoid any harmful side effects of the code being run. While running,
Cprofiler

(
Python Software Foundation, 2024
)
is used for time execution measures and
tracemalloc
for memory footprint. Using non-negative least squares curve fitting on each set of measures, the coefficients and residuals of each complexity class are computed. The selected complexity class for a given set of measures is chosen as the minimizer of the residuals, taking into account a simplicity bias (the simpler the complexity class is, the smaller the simplicity bias). This curve fitting is applied to each set of measures, each corresponding to a different subset of arguments being expanded with a different expansion method. Using ensemble methods, the global complexity of the Python function is computed by aggregating the individual complexity outputs across the different sets of measures. Finally, the complexity framework also returns the coefficients of the curve of each selected complexity. These coefficients can be leveraged to rank and classify the optimizations of different Python solutions within the same complexity class.

I.3
Fuzzing and Worst Running Cases

BigO(Bench)
focuses on worst-case time and space complexities, therefore any LLM-generated code solution is evaluated to infer its tightest upper-bound time and space complexities. To do so, any code solution input to the framework comes with a corresponding edge case input, as shared in the corresponding released dataset. Using fuzzing, this edge case input is derived into many inputs of different sizes following different generators: for example, an input pair consisting of an integer and a list can see the integer input grow independently from the list (the integer can grow linearly, with random size steps, etc, whereas the list can remain static) or on the contrary interdependently (both the integer and the list grow at a regular pace, with same size steps). In the released codebase, the input-generation module is in charge of handling the fuzzing.
Then, the sandbox and the time and memory profilers record the behavior of the code solution on all sets of inputs, a set of inputs being parametrized by a specific input generator suggesting inputs over a range of sizes. This enables to gather time execution and memory footprint curves over many input cases, and worst execution curves are used to derive the form of the associated complexity using curve fitting methods in the curve-fitting module.

Fuzzing is in itself a whole area of research, with many publications covering Java or C++ programs
(
Noller et al., 2018
;
Wang et al., 2020
)
. More recently, LLM capabilities are more and more studied as a way of making fuzzing techniques more exhaustive
(
Xia et al., 2024
;
Xu et al., 2025
)
. In our benchmark, we chose to design an evaluation framework completely independent from any machine learning model, so as to avoid biasing the evaluation. Nevertheless, the modularity of the implementation enables switching the default fuzzer so to experiment with any other fuzzer released by the computer science community, or more recently from LLM-based approaches. This would enable to measure what kind of bias can arise, and whether coverage and accuracy of the complexity evaluation are improved. Finally, without changing the fuzzer, the input edge cases example can also be interchanged easily as it is an input of the framework fuzzer: one can experiment with prompting an LLM for more edge case inputs.

Our paper provides methods to evaluate the quality of the fuzzing as performed by our evaluation framework, using ground-truth human solutions to all BigOBench benchmark problems. As detailed in
section

4.3
, we conducted a thorough review to evaluate whether our evaluation framework correctly identifies worst-case scenarios and accurately derive complexity estimates from them, using a total of 250 samples, including 125 for time complexity and 125 for space. On the time complexity test set, the framework reaches 84% accuracy, with 1000-bootstrap samples confidence interval [0.776, 0.904] (for space, 82% accuracy [75.2, 88.8]). In addition, these test sets include, for time complexity, 42% problems of difficulty A (for space 45%), 29% of B (for space 25%) and 30% of C+ (for space 30%). On hard problems C+, framework accuracy is 84% for time complexity (84% for space). Being exposed to stochastic noise when measuring runtimes and memory footprints, the evaluation framework also got evaluated for its consistency, running the framework 20 times on 10 solutions of every problem and complexity class of the candidate test set: self-consistency of the framework is measured to be at 91.9% (resp. 89.1%) for time (resp. space) complexity, for a total of 10,130 (resp. 10,520) different code solutions.

appendix

I
provides an illustration and more details concerning the methods being used in the framework in order to measure worst-case complexities.

I.4
Variance Reduction Techniques

Variance reduction techniques are important as the complexity framework relies on empirical measures of runtime and memory footprint, which are subject to noise. The framework was tested and ablated on a validation set in order to measure the effect of each design choice. Among them, each measure of runtime and memory footprint is repeated R times (in the current setting, R = 10 after ablation, trading-off accuracy with added compute cost) and then aggregated following a variance reduction technique. It turned out that the min-aggregation provided the best results for runtime measurements, improving complexity framework by 3.5% over median aggregation and 19% over max aggregation, among others. Our intuition is that runtimes are typically subject to variability caused by external factors (such as background processes, CPU throttling, system load etc.) in a way that increases runtime, creating high outliers.

The Hodges-Lehmann estimator
(
Hodges Jr. and Lehmann, 1963
;
Qiu et al., 2024
)
for example has not been specifically tested yet for the complexity framework. The codebase was designed with modularity as a core principle and any estimator can be added to the curve-fitting module as a function of a set of empirical measures.

Beyond the variance-reduction techniques that can be used on empirical noisy measures,
BigO(Bench)
also employs similar technique when aggregating scores over multi-samples.
Qiu et al. (2024)
employ a Rao-Blackwellized bootstrap estimator, while we use an unbiased estimator for @k measures by leveraging n = 20 samples for k
<=
10 with c
<=
n correct samples:

\text{pass}@k=\mathbb{E}_{p}\left[1-\frac{\dbinom{n-c}{k}}{\dbinom{n}{k}}\right]

This estimator, introduced by
Chen et al. (2021)
, is an unbiased measure of the multi-sample performance as demonstrated in the appendix A of this paper.

In general, given that as measured in
section

4.3
we measure the accuracy of the framework with human annotations at
\sim
85%, we estimated that this success rate ensured the framework was accurate enough to provide reliable conclusions on the performance of LLMs as part of the
BigO(Bench)
.

I.8
Implementation Limitations and Future Directions

The Dynamic Complexity Inference Framework can be improved in many ways. The current version is more of a proof-of-concept, trying to see whether such framework can be used reliably on this task, for evaluation purposes of reinforcement learning. The following suggestions on how to improve the performance, reliability and maintainability of the framework are listed:

1.

Refactoring the whole framework: the goal being to allow for flexible extensions. Some parts of the codebase, for instance around the input generations, are already designed to allow new methods of input generation.

2.

Fuzzing: The modularity of the codebase presents opportunities for future research directions. One potential area of investigation is the exploration of alternative fuzzers, including those leveraging large language models (LLMs), to measure the introduction of bias and evaluate their impact on coverage and accuracy of complexity evaluation. Additionally, researchers could investigate the effectiveness of using LLMs to generate input edge cases, potentially leading to improved coverage and accuracy. Furthermore, the framework’s modularity enables the study of the impact of different fuzzers on the codebase, allowing for a deeper understanding of the relationships between fuzzing strategies, input edge cases, and complexity evaluation outcomes. By experimenting with different fuzzers and input edge cases, researchers can gain insights into the strengths and limitations of various approaches, ultimately contributing to the development of more robust and effective fuzzing techniques.

3.

Noise reduction: several methods can help with noise reduction, and therefore better accuracy of the framework as well as more stable results. Deterministic CPU operations is a huge axis of improvement, but post-processing methods on the runtime and memory footprint measures is also promising. Variance reduction techniques such as Hodges-Lehmann estimator could also be used.

4.

Complexity definition: work on the definition of complexity and therefore how complexity is induced by the framework. Current assumptions may not be accurate, and maybe some choices in the framework implementation and not coherent with more widely spread definitions of complexity of a code snippet.

5.

Complexity coverage: The way we designed the framework is that it defines a set of base functions for curve fitting, and the framework can combine these functions with addition and multiplication operators to best fit the time execution and memory footprint curves.

As long as such a function is defined, it is fit by the complexity framework. In practice, currently there is a class for the cubic function, and no classes that represent
x\to\frac{x^{3}}{\log x}
,
x\to(\log x)^{6}
nor
x\to 2^{\text{polylog}(x)}

In practice, accuracy limitations may arise when two classes exhibit similar behavior over typical input sizes (1-10,000). Empirical noise from profiler measurements (runtime or memory footprint) can make fitting complexities challenging. We recommend testing the framework on labeled examples when introducing a new function class.

6.

Pure performance: the performance of the complexity framework is limited. Measurement of these limitations and their improvement is the priority goal.
