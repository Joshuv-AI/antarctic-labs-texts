ExpeRepair : Dual-Memory Enhanced LLM-based Repository-Level Program Repair
Fangwen Mu, Junjie Wang, Lin Shi, Song Wang, Shoubin Li, Qing Wang

Abstract
Automatically repairing software issues remains a fundamental challenge at the intersection of software engineering and AI. Although recent advancements in Large Language Models (LLMs) have demonstrated potential for repository-level repair tasks, current methodologies exhibit two notable limitations: (1) they often address issues in isolation, neglecting to incorporate insights from previously resolved issues, and (2) they rely on static and rigid prompting strategies, which constrain their ability to generalize across diverse and evolving issue scenarios. Inspired by the dual memory systems of human cognition, where episodic and semantic memories work synergistically to support human reasoning and decision-making, we propose ExpeRepair , a novel LLM-based approach that continuously learns from historical repair experiences through dual-channel knowledge accumulation. ExpeRepair organizes historical repair experiences into two complementary memories: an episodic memory that stores concrete repair demonstrations, and a semantic memory that encodes abstract reflective insights. At inference time, ExpeRepair activates both memory systems by retrieving relevant demonstrations from episodic memory and recalling high-level repair insights from semantic memory. It further enhances adaptability through dynamic prompt composition, synergistically integrating both memory types to replace static prompts with context-aware, experience-driven prompts. Experiments on the SWE-bench Lite benchmark demonstrate that ExpeRepair achieves a pass@1 score of 49.3% with Claude 3.7 Sonnet, outperforming all state-of-the-art open-source methods.

Introduction

Automated Program Repair (APR) aims to automatically identify and correct bugs in source code, offering the potential to significantly reduce developer effort and improve software reliability
le2019automated
. Traditional APR techniques have predominantly focused on function-level repair, targeting small, isolated code fragments
gazzola2018automatic
. However, this narrow scope diverges from real-world software maintenance practices, which typically require reasoning over large codebases, interpreting complex issue descriptions, and addressing inter-file dependencies. Recent advances in Large Language Models (LLMs) for generative tasks, particularly code generation, have shifted attention toward applying LLMs to repository-level program repair
bouzenia2024repairagent
;
zhang2024autocoderoverautonomousprogramimprovement
;
xia2024agentless
;
yang2024swe
. Unlike function-level repair, repository-level APR involves navigating large codebases, understanding intricate program logic, and identifying subtle bugs embedded across multiple files, introducing new and underexplored challenges.

To address these challenges, recent studies have explored two main categories of LLM-based APR methods: agentic and procedural. Agentic approaches
zhang2024autocoderoverautonomousprogramimprovement
;
yang2024swe
;
silva2023repairllama
;
DBLP:journals/corr/abs-2503-14269
treat the LLM as an autonomous agent capable of planning and executing actions to resolve bugs by interacting with tools, traversing repositories, modifying code, and running tests. In contrast, procedural approaches
xia2024agentless
;
ma2024alibaba
follow predefined and static pipelines,
where the LLM sequentially performs tasks such as bug localization and patch generation using fixed prompts and operation sequences, without autonomous decision-making. While both paradigms have shown promise, they still exhibit two significant limitations:

•

Neglecting Historical Repair Experience.
Current approaches treat each issue in isolation and primarily rely on feedback derived from the ongoing issue resolution process, while largely ignoring valuable historical experience accumulated from previously resolved issues within the same repository. In practice, software projects often exhibit recurring bug patterns during their evolution
livshits2005dynamine
, for example, incorrect API usage, type mismatch errors, or improper resource management. These recurring issues often follow similar fix patterns, either manifesting as syntactically similar code changes or exhibiting significant syntactic variations while sharing similar underlying correction logics.
The absence of mechanisms to capture and exploit such historical repair data results in redundant exploration and missed opportunities for accelerating successful repair.
If an APR system could systematically identify previously encountered bug patterns or contextual experience, and adapt past successful patches, it would substantially improve both repair efficiency and success rates.

•

Limited Dynamic Adaptability Due to Static Prompting.
Existing approaches rely on manually crafted, static prompts to guide models in tasks such as bug localization and patch generation. However, these generic prompts fail to account for substantial variations across real-world software projects, including differences in coding conventions, architectural patterns, issue descriptions, and project-specific practices. Manually tailoring prompts for each repository or issue type is impractical and unsustainable, particularly in large, heterogeneous software ecosystems
DBLP:conf/iclr/HuCDZLYHTC25
. Moreover, static prompts not only struggle to accommodate this diversity but also lack the capacity to evolve in response to task feedback or adapt to nuanced context shifts during multi-step repair workflows. Addressing this challenge requires a dynamic prompt generation or adaptation mechanism capable of tailoring instructions based on the repository’s characteristics, the issue’s contextual information, and insights from past repairs, thereby enabling more robust and context-aware repair strategies.

In real-world software development, human programmers continuously accumulate knowledge from past debugging and repair activities, refining their strategies and reasoning over time. Inspired by this human-like learning process
DBLP:conf/aaai/Zhao0XLLH24
;
DBLP:journals/corr/abs-2411-13941
, we make the first attempt to explicitly incorporate historical repair experiences into repository-level APR, aiming to model how developers learn, adapt, and improve across issues within a software project. To effectively capture and reuse these accumulated experiences, we draw further inspiration from cognitive science. The dual-memory system theory
evans2013dual
;
frankish2010dual
posits that human reasoning and decision-making rely on two complementary types of memory: episodic memory, which stores concrete personal experiences, and semantic memory, which captures abstract, generalizable knowledge. These two systems work synergistically, enabling individuals to recall specific events while applying broader insights to novel situations.

To this end, we propose
ExpeRepair
, a novel LLM-based program repair approach that continuously accumulates and reuses historical repair experiences through dual memory systems.
ExpeRepair
comprises two core modules: a Program Repair Module and a Memory Module. The repair module orchestrates a test agent and a patch agent, which collaboratively perform test generation, patch generation, and patch validation
for each issue. The memory module organizes repair experiences into two complementary memories: episodic memory, which stores concrete repair demonstrations, and semantic memory, which distills abstract, natural language insights from past repair trajectories. At inference time,
ExpeRepair
retrieves relevant repair demonstrations and reflective insights to generate dynamic, context-aware prompts tailored to the current issue and repository. By maintaining both episodic memory and semantic memory,
ExpeRepair
achieves synergistic benefits: specific demonstrations provide precise implementation references, while reflective insights enable generalized adaptation to new and evolving contexts.

We evaluate our method on
SWE-Bench Lite

jimenez2023swe
, a challenging benchmark comprising real-world software issues sourced from popular GitHub repositories. Experimental results show that our approach outperforms all state-of-the-art open-source baselines, achieving a 47.7% pass@1 with Claude 3.5 Sonnet V2
claude5
and a 49.3% pass @1 with Claude 3.7 Sonnet
claude7
. Further, ablation studies confirm the effectiveness of our dual-memory mechanism in improving repair performance.

Our main contributions are as follows:

•

We propose
ExpeRepair
, a LLM-based program repair method that continuously learns from historical repair experiences through dual-channel knowledge accumulation, which is the first attempt to consider the historical repair experience in program repair to the best of our knowledge. By integrating episodic and semantic memories inspired by cognitive science,
ExpeRepair
enables continuous accumulation and reuse of historical repair experiences, enhancing both the effectiveness and adaptability of program repair.

•

We design a dynamic, experience-driven prompt generation mechanism that tailors repair strategies to the specific characteristics of each issue and repository. This mechanism addresses the limitations of static, handcrafted prompts by leveraging both concrete repair demonstrations and abstract fix patterns retrieved from memory.

•

We conduct comprehensive experiments on SWE-Bench Lite, showing state-of-the-art performance and validating the individual contributions of each component through ablation studies.

Related Work

Repository-level APR has garnered increasing attention from both academia and industry

;

;

;

;
yang2024swe
;
DBLP:conf/icse/0009W0LRLW24
, driven by the growing complexity of managing bug reports and issue tracking on collaborative platforms such as GitHub. With the rapid advancement of LLMs in generative software engineering tasks, LLM-based solutions have emerged as the dominant paradigm in this problem space.

Early approaches primarily adopted Retrieval-Augmented Generation (RAG) techniques
mansur2024ragfix
, retrieving relevant code snippets to condition LLMs for patch generation. SWE-Llama
jimenez2023swe
advanced this direction by fine-tuning LLMs on code patching instructions, improving the reliability of generated fixes. More recently, agent-based frameworks such as SWE-agent

, Moatless

, and OpenHands

have gained popularity. These systems employ LLMs as planning agents that iteratively interact with external tools to perform end-to-end issue resolution, covering tasks such as bug localization, patch generation, and validation. Complementing this line of work, procedural methods such as Agentless
xia2024agentless
and PatchPilot
li2025patchpilot
adopt expert-designed, fixed workflows that sequence LLM calls and tool invocations for each issue in a rule-based manner, without dynamic agent planning.

Distinct from existing methods, which typically treat each issue in isolation, our
ExpeRepair
continuously accumulates, organizes, and reuses historical repair trajectories through the dual memory system. This enables dynamic prompt adaptation at inference time, enhancing repair performance without requiring expensive fine-tuning or complex agent orchestration.

3
Method

The primary motivation behind
ExpeRepair
is to enable LLM-based agents to continuously accumulate and leverage knowledge from past repair experiences, thereby improving their effectiveness and efficiency in addressing new software issues. As illustrated in Figure
1
,
ExpeRepair
is built upon two key modules: the Program Repair Module and the Memory Module. The program repair module comprises a test agent and a patch agent, which collaboratively perform three essential tasks: test generation, patch generation, and patch validation. Once the program repair module processes an issue, the memory module captures the corresponding repair trajectory, extracting concrete demonstrations and summarizing high-level repair insights. These are stored in episodic memory and semantic memory, respectively. In subsequent repairs,
ExpeRepair
dynamically retrieves relevant demonstrations and insights to inform and enhance its repair strategies for new issues. In this section, we first present the end-to-end workflow of
ExpeRepair
, followed by a detailed illustration of its two core modules.

3.1
Workflow of
ExpeRepair

Conventional learning approaches
DBLP:journals/corr/abs-2308-10462
;
guo2024large
;
DBLP:journals/corr/abs-2308-12950
;
DBLP:journals/corr/abs-2401-14196
typically rely on computationally expensive fine-tuning to improve the capabilities of LLM-based agents. In contrast,
ExpeRepair
equips LLM agents with the dual-memory mechanism, enabling them to continuously acquire knowledge from their own repair experiences without requiring parametric updates. However, directly deploying
ExpeRepair
introduces a cold-start problem, where no historical repair experience is initially available to populate the memory systems. To overcome this,
ExpeRepair
adopts a two-phase strategy. In the initial phase, it is applied to a seed set of software issues to generate corresponding repair trajectories. The Memory Module then organizes these trajectories into two complementary memories. During this phase,
ExpeRepair
operates without accessing prior memories, and its prompts remain static. In the inference phase,
ExpeRepair
activates both memory systems: retrieving relevant demonstrations from episodic memory and recalling reflective insights from semantic memory. This enables
ExpeRepair
to dynamically compose context-aware, experience-driven prompts, progressively enhancing its repair capabilities.

3.1.1
Initial Phase

In this phase,
ExpeRepair
is applied to a set of seed issues. The LLM agents in the program repair module use the ReAct algorithm
yao2023react
to iteratively process their respective tasks up to
Z
times. Specifically, assuming an LLM agent processes the
n
-th issue at the
z
-th trial, it is provided with a task prompt
{P}
defining its role and task (e.g., generating a patch), issue-specific context
{C}_{n}
(e.g., the issue description or relevant code snippets), and feedback
F_{n,z-1}
(e.g., execution results) from the
(z-1)
-th trial, which is initialized as empty:
F_{0}=\emptyset
. The agent then generates an output by sampling:
O_{n,z}\sim\mathrm{LLM}\left({P},C_{n},F_{n,z-1}\right)
. After all agents complete their tasks, the memory module records their produced trajectories
\tau_{n,z}=[O_{n,1},F_{n,1},O_{n,2},\dots]
, and subsequently extracts both issue-specific demonstrations and abstract natural language insights for each agent. These are stored in the episodic memory
\mathcal{M}_{\text{epi}}
and the semantic memory
\mathcal{M}_{\text{sem}}
, which together serve as a springboard for a warm start.

3.1.2
Inference Phase

In this phase, when addressing new issues,
ExpeRepair
accumulates and leverages experience to guide the repair process. Specifically, it first extracts summarized natural language insights
I
from the semantic memory
\mathcal{M}_{\text{sem}}
, and appends them to the corresponding agent’s task prompt
P
. It then identifies the top-
k
relevant demonstrations
D_{n,z}\subset\mathcal{M}_{\text{epi}}
based on their similarity to the current issue and its latest feedback (if available). As a result, for the
n
-th issue at the
z
-th trial, each LLM agent is provided with the augmented input to generate the output:
O_{n,z}\sim\mathrm{LLM}\left(P+I,D_{n,z},C_{n},F_{n,z-1}\right)
. Similarly, after all agents complete their tasks, the memory module records the resulting repair trajectories, extracts new demonstrations and insights, and updates the dual memories. Over time, this process enables
ExpeRepair
to progressively enrich its episodic and semantic memories, fostering continuous improvement in repair efficiency and success rates for future issues.

3.2
Program Repair Module

The program repair module decomposes the complex APR problem into three tasks: test generation, patch generation, and patch validation. It employs two agents, a test agent and a patch agent, to collaboratively handle these tasks, akin to how human developers triage and resolve software issues.

3.2.1
Test Generation

In practical software development, reproduction tests are essential for both demonstrating the presence of an issue and validating the correctness of candidate patches
qi2015analysis
. However, existing approaches typically prompt an LLM to generate a reproduction test script solely based on the issue description, which presents two major limitations: (1) frequent execution failures due to omitted dependencies, configurations, or environment-specific settings, and (2) inadequate issue reproduction, as such scripts often narrowly target the symptoms described in the issue without capturing the broader fault context.

ExpeRepair
addresses these limitations by enabling the test agent to iteratively generate and refine reproduction tests based on dynamic feedback and memories accumulated from past repair trajectories. Specifically, before generating a new reproduction test at trial
z
for the
n
-th issue, the test agent retrieves relevant demonstrations and extracts insights from both memories. Concretely, the agent first retrieves the top-
k
most relevant demonstrations
D_{\text{test}}
from the episodic memory
\mathcal{M}_{\text{epi}}
, based on the similarity between the current execution feedback
F_{n,z-1}
and the feedback traces
F_{d}
associated with prior demonstrations:
D^{\text{test}}_{n,z}=\text{Top-}k\left(\left\{d\in E_{\text{epi}}\mid\text{Sim}(F_{n,z-1},F_{d})\right\}\right)
. This directly addresses the limitation (1): when the current test execution encounters a failure (e.g., a missing library or configuration error), demonstrations associated with the same or similar failures provide concrete examples of how those were successfully handled in the past. Then, the agent extracts all summarized natural language insights
I_{\text{test}}
from the semantic memory
\mathcal{M}_{\text{sem}}
. These insights capture generalizable, high-level strategies distilled from prior repairs. For example: “When testing security-sensitive functionality, implement comprehensive test cases that verify proper handling of malicious inputs, edge cases, and potential attack vectors, ensuring robust validation and appropriate error responses” (a real insight summarized by
ExpeRepair
for the Sympy project). These insights help address the limitation (2) by expanding the agent’s reasoning beyond narrowly reproducing stated symptoms.

After recalling knowledge from the memories,
ExpeRepair
synthesizes the following adaptive prompt: (1) the enhanced task prompt
P^{\text{test}}+I^{\text{test}}
, (2) the issue description
C^{\text{test}}_{n}
, (3) the execution feedback
F^{\text{test}}_{n,z-1}
from the previous test trial, and (4) the retrieved demonstrations
D_{\text{test}}
. Formally, the test agent’s output at trial
z
is generated as:
O^{test}_{n,z}\sim\mathrm{LLM}\left(P^{test}+I^{test},D^{test}_{n,z},C^{test}_{n},F^{test}_{n,z-1}\right)
.
This iterative process continues until either a valid reproduction test is produced or
Z^{\text{test}}
iterations have been completed.

3.2.2
Patch Generation

Following the successful reproduction of an issue,
ExpeRepair
initiates patch generation to produce candidate repairs that resolve the fault while preserving existing functionality. Before generating patches, it is essential to first localize where the issue occurs. Accurate bug localization is critical for effective program repair, as generating correct patches is infeasible without first identifying the relevant locations in the codebase. Following previous work
yang2024swe
,
ExpeRepair
adopts a hierarchical localization strategy: first identifying suspicious files based on the issue description and repository structure, and then localizing specific faulty lines within the identified files.

As noted in previous studies
yang2024swe
;
bouzenia2024repairagent
, LLMs often generate incomplete patches, as fixing a repository-level issue typically requires coordinating changes across multiple parts of the code or performing a sequence of modifications.
To address it, similar to the test generation process,
ExpeRepair
iteratively recalls episodic and semantic memories and leverages them to generate and refine patches. At each trial
z
for the
n
-th issue, the patch agent retrieves relevant demonstrations and extracts reflective insights, following the same procedure as in the test generation phase. The agent is then prompted with: (1) the enhanced task prompt
P^{\text{patch}}+I^{\text{patch}}
, (2) the issue description and localized faulty lines
C^{\text{patch}}_{n}
, (3) the latest execution feedback
F^{\text{patch}}_{n,z-1}
, and (4) the retrieved demonstrations
D_{\text{patch}}
. A candidate patch is generated as:

O^{\text{patch}}_{n,z}\sim\mathrm{LLM}\left(P^{\text{patch}}+I^{\text{patch}},D^{\text{patch}}_{n,z},C^{\text{patch}}_{n},F^{\text{patch}}_{n,z-1}\right)
. In each iteration, we perform multiple samplings with a high temperature to generate diverse candidate patches. This process continues until at least one candidate patch passes the reproduction test (i.e., the issue is no longer triggered) or reaches
Z^{\text{patch}}
iterations.

3.2.3
Patch Validation

After a candidate patch successfully passes the reproduction test, it is not immediately accepted as the final patch. This is because we empirically observed that reproduction scripts typically focus narrowly on the specific symptoms described in the issue, leading to false positives where patches pass limited tests but fail in broader contexts. To mitigate this, we revise and augment the patch by instructing the patch agent to address concerns such as edge case handling, regression risks, and adherence to language-specific best practices. Next, we augment the reproduction test suite by generating additional validation tests. The test agent is instructed to create tests targeting boundary conditions and corner cases. This process reduces the risk of narrow, brittle fixes that only address the reported symptom without addressing the underlying defect comprehensively.

To select the final patch, we first execute all candidate patches against the expanded test suite, which includes both reproduction and validation tests. Then, we pass these candidate patches and their corresponding test results to a dedicated review agent, which selects the final patch based on criteria such as correctness, code style, and adherence to best practices.

3.3
Memory Module

The memory module systematically accumulates, organizes, and exploits historical repair trajectories. It manages two complementary memories: episodic memory, which stores concrete, reusable demonstrations of past repairs, and semantic memory, which distills higher-level, generalizable insights (e.g., repair strategies). By equipping
ExpeRepair
with the dual-memory mechanism, LLM agents not only accelerate issue resolution through effective reuse of prior knowledge but also enable dynamic prompt adaptation.

3.3.1
Memory Storage

The memory storage is responsible for persistently recording historical repair knowledge in two complementary forms, in alignment with the Dual Memory System:
episodic memory
and
semantic memory
. After the program repair module processes a new issue, the memory module collects the complete repair trajectory, which consists of all detailed artifacts associated with that specific repair instance, including the issue description, reproduction scripts, candidate patches, and the test execution results before and after each patch is applied.

Demonstration Extraction.

For each trajectory,
ExpeRepair
extracts issue-specific demonstrations for both the test agent and the patch agent. Specifically, two types of demonstrations are extracted: (1)
(input, success output)
pairs, representing effective repair attempts, and (2)
(input, failed output, feedback, success output)
tuples, which document failed attempts, their execution results, and the subsequent corrected versions. The failed/success output refers to whether the script successfully reproduces the issue or whether the patch successfully passes the reproduction script. Finally, all extracted demonstrations are stored in episodic memory.

Insight Summarization and Update.
To maintain the semantic memory, which stores high-level natural language insights,
ExpeRepair
performs a summarize-and-update process at the conclusion of each repair attempt. We instruct the LLM to analyze the full repair trajectory and explain why specific attempts to reproduce the issue or generate a patch succeeded or failed, thereby generating reflective insights that could include general repair strategies, common failure causes, and successful repair heuristics. The newly summarized insights are then compared against the existing insights stored in semantic memory, and
ExpeRepair
applies up to three operations to update the stored insights. Each operation is chosen from one of three options: (1)
ADD
, to introduce a new insight if it presents a novel or valuable observation; (2)
REMOVE
, to eliminate contradictory, outdated, or redundant insights; or (3)
EDIT
, to merge, generalize, or refine overlapping insights for greater clarity and utility. We also limit the maximum number of insight entries for each agent; if this limit is reached,
ExpeRepair
must
REMOVE
an existing insight before
ADD
ing a new one.

3.3.2
Memory Activation

ExpeRepair
performs parallel activation of episodic and semantic memories by retrieving relevant demonstrations and insights, thereby adaptively constructing LLM agents’ prompts to inform their decision-making for new issue resolution.

Episodic Memory Activation.
When resolving new issues,
ExpeRepair
retrieves the top-
k
most semantically similar past demonstrations based on the issue description and feedback (if available), using retrieval methods such as vector-based similarity (e.g., embedding search
DBLP:journals/pami/HjaltasonS03
) or term-based matching (e.g., BM25
DBLP:journals/ftir/RobertsonZ09
). These retrieved demonstrations are incorporated into the agents’ prompts as in-context examples, providing concrete precedents for constructing correct reproduction scripts or patches. This memory mechanism enables
ExpeRepair
to avoid redundant exploration and benefit from accumulated experience, allowing it to generate higher-quality reproduction scripts and patches.

Semantic Memory Activation.
Simultaneously,
ExpeRepair
activates the semantic memory by extracting all stored insights.
The insights are incorporated into the task prompts for both agents to adaptively adjust and enhance their repair strategies in response to the characteristics of the current issue. This mechanism, effectively serving as a lightweight auto-prompting technique
DBLP:conf/emnlp/WuGZZSYLDY24
;
DBLP:journals/corr/abs-2402-07927
;
DBLP:conf/emnlp/ShinRLWS20
, incrementally improves repair effectiveness by guiding agents with accumulated semantic experience.

5.2
Ablation Study

To assess the contribution of each component within
ExpeRepair
, we conduct a systematic ablation study on the SWE-Bench-Lite benchmark. Specifically, we selectively disable three key modules from the full system to measure their isolated impact: (1) w/o Experience Module: removes the experience-based knowledge retrieval mechanism, treating each issue in isolation as prior methods do; (2) w/o Demonstrations: omits the in-context demonstrations provided to LLM agents during test and patch generation; and (3) w/o Insights: removes the reflective insights offered to LLM agents during test and patch generation.

Table
2
presents the results. Removing the “Experience Module” causes a substantial performance drop, with the resolved rate falling from 47.7% to 41.3%, alongside significant decreases in both ESR and RSR. This demonstrates the critical role of experience-driven retrieval in enhancing fix quality and ensuring test execution success.

Excluding the “Demonstrations Module” results in a resolved rate of 43.7%, accompanied by moderate declines in ESR and RSR. This highlights the importance of in-context examples in guiding LLM agents to generate accurate, executable patches. In comparison, removing the Insights module causes a smaller performance drop, with the resolved rate decreasing to 46.0%. While issue-specific insights contribute to the overall effectiveness of
ExpeRepair
, their impact is somewhat less pronounced relative to experience retrieval and demonstrations.

6
Limitations

While our approach improves test generation and patch generation by leveraging accumulated episodic and semantic memories, it currently places less emphasis on optimizing bug localization, which is also a critical factor in program repair performance. The primary challenge lies in the difficulty of verifying localization correctness. Unlike test generation and patch generation, whose correctness can be directly validated through execution outcomes (e.g., triggering issues or passing test cases), bug localization lacks an automated oracle. The correctness of a localization prediction cannot be reliably determined based on the success or failure of the subsequent patch. One possible solution is to selectively accumulate localization experiences only from successful repair attempts, assuming that a correct patch implies the localization was correct. However, this conservative strategy would result in memories containing only a narrow subset of successful localization cases, limiting both diversity and coverage. We leave the integration of reliable, memory-based bug localization into our framework as an important direction for future work.

7
Conclusion

We introduced
ExpeRepair
, a novel LLM-based APR method that continuously accumulates and reuses historical repair experiences through the dual memory system. By integrating episodic and semantic memories,
ExpeRepair
enables dynamic, context-aware prompt adaptation, enhancing repair effectiveness and efficiency over time.
ExpeRepair
achieves a 47.7% pass@1 with Claude 3.5 Sonnet V2 and a 49.3% pass@1 with Claude 3.7 Sonnet on SWE-Bench Lite, indicating that leveraging past repair knowledge improves performance on challenging program repair tasks. We release our code and data to support further research

A.1
Implementation

Test and Patch Generation.

For each issue instance,
ExpeRepair
first uses the test agent to generate a reproduction script capable of triggering the issue. We set an iteration limit of 3 for script generation, producing at most one reproduction script per iteration. If a valid reproduction script is obtained (i.e., it successfully triggers the issue as confirmed by execution results), we proceed to the patch generation stage. Patch generation is also conducted iteratively, with a maximum of 3 attempts per issue. In each iteration,
ExpeRepair
generates 4 candidate patches. If none of the patches pass the reproduction script, all failed patches and their execution results are provided to the patch agent to generate new candidate patches. If at least one patch passes, we move on to the patch validation stage.

Patch Validation.

To mitigate the risk of false positives — patches that pass the reproduction script but fail comprehensive ground-truth tests —
ExpeRepair
performs an additional validation phase. We first sample 3 validation tests by prompting the LLM to generate additional edge cases and boundary conditions based on the reproduction script. Subsequently, we refine the prompt to instruct the patch agent to produce 4 augmented patches, explicitly addressing concerns such as edge case handling, regression risks, and adherence to language-specific best practices. All candidate patches are then executed against the validation tests and reviewed by an LLM to select the best-performing patch.

Memory Storage.

After completing the repair process for an issue,
ExpeRepair
persistently records the full repair trajectory into memory. For episodic memory,
ExpeRepair
extracts two types of demonstrations from each trajectory, as described in Section
3.3.1
, and stores them along with metadata such as the issue description, repair status, and timestamp. For semantic memory,
ExpeRepair
prompts the LLM to summarize key insights from the repair trajectory. These insights are compared against existing entries, and one of three update operations —
ADD
,
REMOVE
, or
EDIT
— is applied. The maximum number of stored insights per agent is capped at 15; if this limit is reached, the least recently used insight is removed before adding a new one.

Memory Activation.

When addressing a new issue,
ExpeRepair
performs parallel memory activation. For episodic memory, it retrieves the top-5 most semantically similar demonstrations based on the issue description and available feedback. In this work, we use BM25 for term-based matching. Retrieved demonstrations are incorporated into the LLM agents’ prompts as in-context examples. For semantic memory, retrieved insights are appended to the prompts as high-level repair guidelines.
