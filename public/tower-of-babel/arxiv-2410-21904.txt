Formal Analysis of Reachability, Infection and Propagation Conditions in Mutation Testing
Seyed-Hassan Mirian-Hosseinabadi

Abstract
Finding test cases to kill the alive mutants in Mutation testing needs to calculate the Reachability, Infection and Propagation(RIP) conditions and the full test specification. In this paper, a formal approach to calculate RIP conditions is proposed. The Dijkestra’s weakest precondition predicate transformer ( wp ⁡ ( Γ ​ , ​ Γ ) wp(\!|\vbox{\hrule width=3.99994pt},\vbox{\hrule width=3.99994pt}|\!) ) is used to calculate infection and propagation conditions. The rc ⁡ ( Γ ​ ​ Γ ) rc(\!|\vbox{\hrule width=3.99994pt}|\!) function is defined to calculate the reachability conditions generated by each statement. Four programs and their mutants are examined as running examples and as case studies to show the applicability of the method.

Introduction

Mutation testing is the widely used method of a category of testing methods called Syntax Based Testing. This is a method to assess the quality of test cases by killing mutants, and at the same time, to generate new test cases to kill those mutants which are alive. These new test cases can find faults in the program under test if there are still any, and can increase the level of confidence to the under test program. For those mutants which are not killed by the original set of test cases, the tester should find new test cases by the help of RIPR analysis

1.1
Mutation Testing and RIPR Analysis

Mutation Testing is the original and most widely known application of Syntax-Based Testing.
In Syntax-Based Testing a syntactic description of some data of the under test program is used to define the test cases.
In Mutation Testing, the grammar of the programming language is used as the syntactic description, the program under test (
P
). and the mutants (
M
), are valid strings of this grammar.

In Mutation Testing, Mutation Operators are selected to apply to the source program one at a time for each applicable piece of the source code.
A mutant is the result of applying one mutation operator to the under test program.
The goals of Mutation Testing are:

•

to assess the quality of the test cases which should be robust enough to kill mutants.

•

to find test cases (using RIPR analysis) to kill alive mutants.

The RIPR Analysis forces us to find following conditions:

•

Reachability: The conditions need the faulty statement to be reached,

•

Infection: The conditions need the faulty statement to result in an incorrect state,

•

Propagation: The conditions need the incorrect state propagates to incorrect output,

•

Revealability: The conditions need the tester observe part of the incorrect output (not discussed in this paper).

When the under test program is mutated to create mutants, the hope is to exhibit different behavior from the original program. Killing mutants is defined as follow:

Definition 1

Killing Mutants: Given a mutant
m\in M
for an under test program
P
and a test
t
,
t
is said to kill
m
if and only if the output of
t
on
P
is different from the output of
t
on
m
.

If all the mutants cannot be killed by the existing set of tests the testers can keep adding tests by the help of RIPR analysis until all mutants have been killed.
There are two approaches of killing mutants, namely, strongly killing mutants and weakly killing mutants.

Definition 2

Strongly Killing Mutants:
Given a mutant
m\in M
for a program
P
and a test
t
,
t
is said to strongly kill
m
if and only if the output of
t
on
P
is different from the output of
t
on
m
.

Strongly killing satisfies reachability and infection and propagation conditions.

Definition 3

Weakly Killing Mutants:
Given a mutant
m\in M
that modifies a location
L
in a program
P
, and a test
t
,
t
is said to weakly kill
m
if and only if the state of the execution of
P
on
t
is different from the state of the execution of
m
on
t
immediately after
L
.

Weakly killing satisfies reachability and infection conditions, but not propagation condition.

Consider the following notes which explain the notations used in the grammar.

•

“other statements” is indicating, other statements such as procedure calls.

•

``w"
is any list of identifiers separated by commas.

•

``E"
is any list of expressions separated by commas.

•

The semicolon (
~\mathbin{\raise 2.58334pt\hbox{\vtop{\halign{#\cr\hfil$\scriptscriptstyle\mathrm{o}$\hfil\cr\hfil$\scriptscriptstyle\mathrm{9}$\hfil\crcr}}}}~
) in this grammar is the sequential composition operator.

•

The sequential composed statements are executed successively in the
order from left to right.

•

When a guard is true its guarded list can be executed.

•

The separator
\,[]\,
is used to separate guarded commands of a guarded command list.

•

The order of guarded commands of a set is not important.

•

In the alternative
construct,
{\bf\,if\,}\ldots{\bf\,fi}
,
one of the guarded list with a true guard will be executed. If none of the
guards is true, the program will abort.

•

The repetitive construct,
{\bf\,do\,}\ldots{\bf\,od}
, will
only terminate in a state in which none of the guards
are true.

•

Assignment, skip, return, abort, and null statements are added to the original grammar given by Dijkestra
[
2
]
to be precise about the syntax of these statements. The semantics of these statements are as usual.

•

{\bf\,null\,}
is added to be used as a program which has no statements.

•

{\bf\,return\,}(E)
is treated as an assignment of
E
to the program name
PR_{n}
.

1.3
Dijkestra Weakest Precondition Predicate Transformer

Dijkestra introduced the Weakest Precondition Predicate Transformer as a tool for comparing the semantics of programs
[
2
]
.
The intuition behind this function is, if the weakest preconditions needed for executing the program
prog
and terminating in the state which is described by any post-conditions
A
can be calculated (
wp(\!|prog,A|\!)
), then the semantic of
prog
is understood. As a result, if
wp(\!|prog_{1},A|\!)\Leftrightarrow wp(\!|prog_{2},A|\!)
for any
A
, then
prog_{1}
is equivalent to
prog_{2}
.

In the rest of this subsection the definitions of weakest precondition function (
wp(\!|prog,A|\!)
) when
prog
is one of primitive programming statements are given.

1.3.1
Weakest Preconditions of Primitive Programming Statements

Definition 4

wp(\!|w:=E,A|\!)\widehat{=}A[w\backslash E]

where

means substituting all free

in
A
with
E
.

Since

will contain the value of
E
after execution, then
A
will be true after execution if and only if
A
, with the value of
w

Definition 5

wp(\!|{\bf\,skip\,},A|\!)\widehat{=}A

Execution of
{\bf\,skip\,}
does nothing, so, it is the identity transformation.

Definition 6

wp(\!|prog_{1}~\mathbin{\raise 2.58334pt\hbox{\vtop{\halign{#\cr\hfil$\scriptscriptstyle\mathrm{o}$\hfil\cr\hfil$\scriptscriptstyle\mathrm{9}$\hfil\crcr}}}}~prog_{2},A|\!)\widehat{=}wp(\!|prog_{1},wp(\!|prog_{2},A|\!)|\!)

Sequential composition is one way of composing larger program segments from smaller segments. It is executed by first executing
prog_{1}
and then executing
prog_{2}

Definition 7

wp(\!|{\bf\,null\,},A|\!)\widehat{=}A

The
{\bf\,null\,}
is another name for
{\bf\,skip\,}
to be precise about the part of the program in which nothing is written. For example the part of the program before the first statement of the program is denoted by
{\bf\,null\,}
.

Definition 8

wp(\!|{\bf\,return\,}(E),A|\!)\widehat{=}A[PR_{n}\backslash E]

where

The

is treated as an assignment to the program name.

Definition 9

The statement
{\bf\,abort\,}
should never be executed, because it can only be executed in a state satisfying
{\bf\,false\,}
and no state satisfies
{\bf\,false\,}
.

Definition 10

\begin{array}[]{l}wp(\!|{\bf\,if\,}(\,[]\,i\mathrel{\mathstrut{\bullet}}G_{i}\rightarrow prog_{i}){\bf\,fi},A|\!)\widehat{=}\\
\qquad(\mathrel{\mathstrut{\vee}}_{i}\mathrel{\mathstrut{\bullet}}G_{i})\mathrel{\mathstrut{\wedge}}(\mathrel{\mathstrut{\wedge}}_{i}\mathrel{\mathstrut{\bullet}}G_{i}\Rightarrow wp(\!|prog_{i},A|\!))\end{array}

The first conjunct indicates that the guards must be well defined, and at least one guard is true. The second conjunct indicates that execution of each program

with a true guard

1.3.2
Weakest Preconditions of
{\tt DO}
Statement

{\tt DO}
is actually not a primitive construct, however, for simplicity, it is treated primitive.

{\tt DO}\widehat{=}\begin{array}[]{l}{\bf\,do\,}G_{1}\rightarrow prog_{1}\\
\vdots\\
\,[]\,G_{j}\rightarrow prog_{j}\\
\vdots\\
\,[]\,G_{n}\rightarrow prog_{n}\\
{\bf\,od}\end{array}

A similar alternative statement can be defined with the same guarded command and
G
which is the disjunction of the guards.

{\tt IF}\widehat{=}\begin{array}[]{l}{\bf\,if\,}G_{1}\rightarrow prog_{1}\\
\vdots\\
\,[]\,G_{j}\rightarrow prog_{j}\\
\vdots\\
\,[]\,G_{n}\rightarrow prog_{n}\\
{\bf\,fi}\end{array}

It is obvious that the following iterative command is equivalent to
{\tt DO}
.

{\tt DO}\widehat{=}{\bf\,do\,}G\rightarrow\left\{\begin{array}[]{l}{\bf\,if\,}G_{1}\rightarrow prog_{1}\\
\vdots\\
\,[]\,G_{j}\rightarrow prog_{j}\\
\vdots\\
\,[]\,G_{n}\rightarrow prog_{n}\\
{\bf\,fi}\end{array}\right\}{\bf\,od}\\
{\tt DO}\widehat{=}{\bf\,do\,}G\rightarrow{\tt IF}{\bf\,od}

This means, if all the guards are false, then
G
is false and execution terminates; otherwise, the corresponding alternative command
{\tt IF}
is executed and the process is repeated. One iteration of a loop, therefore, is equivalent to finding
G
true and executing
{\tt IF}
. To formalize the weakest precondition of a loop, some terms must be defined first.

Definition 11

\begin{array}[]{l}{\tt DO}\widehat{=}{\bf\,do\,}(\,[]\,i.G_{i}\rightarrow prog_{i}){\bf\,od}\\
{\tt IF}\widehat{=}{\bf\,if\,}(\,[]\,i.G_{i}\rightarrow prog_{i}){\bf\,fi}\\
G\widehat{=}\mathrel{\mathstrut{\vee}}_{i}G_{i}\\
{\tt DO}\widehat{=}{\bf\,do\,}G\rightarrow{\tt IF}{\bf\,od}\end{array}

Definition 12

•

I
, is a predicate that is true before and after each iteration of a loop, which is called Invariant.

•

v
, is an integer function of program variables that is an upper bound on number of iterations still to be performed. Each iteration of the loop decreases
v
by at least
1
and, as long as execution of the loop has not terminated,
v
is bounded below by
0
. Hence, the loop must terminate. Function
v
has been called a variant function.

•

l
, is the list of variables modified within the loop.

•

x
, is a fresh variable.

The loop invariant

{\bf\,true\,}

•

3
The proposed method

In this section the proposed method is discussed. First, the understandings of the Reachability, Infection and Propagation conditions must be clarified.
To calculate reachability of a mutated statement, the condition generated by the execution of each one of primitive statements which are before the mutated statement must be calculated. This concept is discussed in Subsection
3.1
. To calculate the Infection condition, the semantic differences between the execution of the original statement and the execution of mutated statement must be investigated. This is done with the help of the weakest precondition function defined in Subsection
1.3
. Calculating the Propagation condition is a troublesome part of this study. It is obvious that calculating the conditions needed to reach to the end of the program under test, is not that much helpful. What is has to be known again is the semantic differences between two execution paths. One path is, starting the execution from the mutated statement to the end of program, and the other path is, starting the execution from the original statement to the end of program. This is done, again, with the help of the weakest precondition function. In Subsection
3.2
, first, two types of modification of the program in mutation testing are distinguished, and the original and mutated program templates are introduced. An algorithmic incremental method is introduced to calculate Reachability, Infection and Propagation conditions based on these templates in Subsection
3.3
.

Conclusions

In this paper the formal analysis of Reachability, Infection, and Propagation conditions in Murtation testing is investigated. The weakest precondition predicate transformer and the reachability condition generator function are used to calculate these conditions. To formalize the definitions of these conditions, two types of modifications are distinguished, namely, the
statement modification
and the
guarded command modification
. Program templates for the under test module and its mutated version are specified. Based on these templates the Reachability, Infection, and Propagation conditions are formally specified when the statement modification or the guarded command modification are applied. The results of applying the proposed method are promising. The incremental nature of the method helps the analyzer to calculate these conditions from small pices of programs to the composition of two or more statements.
