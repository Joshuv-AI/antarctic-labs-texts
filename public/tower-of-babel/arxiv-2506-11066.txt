CoQuIR: A Comprehensive Benchmark for Code Quality-Aware Information Retrieval
Jiahui Geng, Fengyu Cai, Shaobo Cui, Qing Li, Liangwei Chen, Chenyang Lyu, Haonan Li, Derui Zhu, Walter Pretschner, Heinz Koeppl, Fakhri Karray

Abstract
Code retrieval is essential in modern software development as it boosts reuse and speeds up debugging. However, current benchmarks primarily emphasize functional relevance while neglecting critical dimensions of software quality. Motivated by this gap, we introduce CoQuIR, the first large-scale, multilingual benchmark specifically designed to evaluate quality-aware code retrieval across four critical dimensions: correctness , efficiency , security , and maintainability . CoQuIR includes fine-grained quality annotations over 42,725 queries and 134,907 code snippets in 11 programming languages and is accompanied by two quality-centric evaluation metrics (Pairwise Preference Accuracy and Margin-based Ranking Score). Based on CoQuIR, we benchmark 23 retrieval models, spanning open-source and proprietary models, and find that even top-performing models often fail to distinguish buggy or insecure code from their robust counterparts. Furthermore, we conduct preliminary investigations into methods for explicitly training retrievers to recognize code quality. Through synthetic datasets, we demonstrate promising improvements in quality-aware metrics across different models without compromising semantic relevance. Downstream code generation performance further validates the effectiveness of our approach. Our work underscores the importance of incorporating quality signals into code retrieval systems, establishing a foundation for more trustworthy software development tools.

Related Work

Modern dense retrievers

Dense retrievers encode queries and documents into a shared embedding space, enabling semantic retrieval beyond lexical overlap. Early encoder-based models
karpukhin-etal-2020-dense
;
xiong2021approximate
;
cai-etal-2024-mixgr
are trained contrastively with hard negatives to capture deeper semantics. As retrieval systems are applied to increasingly complex scenarios, recent work has focused on enhancing their reasoning and instruction-following capabilities. Su et al.
su2025bright
introduced a benchmark requiring intensive reasoning, while Faltings et al.
faltings2025enhancing
proposed extracting logical structures from queries to support complex reasoning. Additionally, instruction-following retrievers are evaluated in FollowIR
followir
and further improved via GPT-generated instruction tuning
weller2025promptriever
. Zhao et al.
beyondrelevance
model latent user intent such as
support
or
oppose
, highlighting the need for nuanced intent understanding.
These works inspire us to also target more complex retrieval, but from a novel scenario, i.e., code retrieval.
We extend the focus beyond semantic or functional relevance to fine-grained distinctions among retrieved code snippets, specifically code quality in our scope.

Code retrieval benchmarks

Code retrieval datasets and benchmarks have evolved significantly to address the growing complexity of semantic matching between queries and codebases. Early efforts like CodeSearchNet
codesearchnet
focused on pairing code functions with natural language comments across six programming languages. CoSQA
cosqa
moved toward more realistic evaluation by aligning over 20,000 natural language queries with relevant code snippets, thereby simulating practical search behavior in real-world programming tasks. XcodeEval
xcodeeval
encompasses both text-to-code and code-to-code retrieval across multiple languages. More recently, CoIR
coir
unified ten existing datasets and eight retrieval tasks into a comprehensive benchmark, enabling holistic evaluation across different programming domains and query modalities.
However, these benchmarks focus primarily on functional relevance, overlooking critical software quality dimensions. To address this, we introduce the first benchmark that explicitly incorporates correctness, efficiency, security, and maintainability, covering eleven programming languages with quality-annotated code pairs for comprehensive, quality-aware retrieval evaluation.

3.1
Benchmark Construction

Our benchmark is constructed from established code-related datasets, organized across distinct quality dimensions
codenet
;
defects4j
;
safecoder
;
cvefixes
;
deprecated
;
llmr2
. These datasets have been meticulously curated through static analysis, rule-based heuristics, and expert validation. Table
1
summarizes the datasets used for each dimension, while Figure
2
shows representative examples. Additional statistics, including average query length, corpus size, and language distribution, are detailed in Appendix
A.1
.

Correctness

We construct
CodeNet-B
, a comprehensive multilingual dataset derived from CodeNet
codenet
. To ensure robust cross-lingual representation, we select 348 problems containing at least one correct and one incorrect submission across all 10 target programming languages. For each problem–language pair, we select up to three positive examples (
Accepted
submissions with minimal
cpu_time
) and three negative examples with typical failure types (e.g.,
Compile Error
,
Wrong Answer
,
Runtime Error
); fewer are used when enough examples are available. To further ensure statistical validity, we augment the dataset with contrastive examples from
Defects4J

defects4j
, matching buggy and fixed Java code. Following
safecoder
, we prompt GPT-4o-mini to generate functional summaries of the fixed implementations, which serve as natural language queries for retrieval.

Efficiency

CodeNet-E
follows the same setup as CodeNet-B but defines negative examples as
suboptimal yet correct
submissions, i.e., those code implementations with
Accepted
status and maximal
cpu_time
. We select up to three efficient and three inefficient implementations per problem-language pair, across 511 problems in 10 languages. Additionally, we include
SQLR2

llmr2
, a dataset of functionally equivalent SQL queries with improved execution efficiency. We use GPT-4o-mini to generate functional summaries of the optimized queries for retrieval.

Security

Our evaluation incorporates security-focused contrastive code examples from two high-quality datasets.
SafeCoder

safecoder
provides an instruction-tuning dataset specifically designed for secure code generation. Constructed through an automated pipeline that extracts and filters code snippets from GitHub commits, this dataset covers 23 Common Weakness Enumeration (CWE) categories across six programming languages. Each example contains functionally equivalent secure and vulnerable code pairs, alongside natural language instructions generated by GPT-4, which we utilize as queries. Additionally, we include examples from
CVEFixes

cvefixes
, a dataset of real-world vulnerability fixes in open-source projects. For each patched code sample, we leverage GPT-4o-mini to summarize its functionality and treat these summaries as queries for retrieving the related code.

Maintainability

To assess the model’s ability to retrieve maintainable code, we employ
DepreAPI

deprecated
, a recent dataset designed to evaluate LLM behavior in scenarios involving deprecated API usage. It contains 145 deprecated-to-recommended API pairs across eight widely-used Python libraries, including NumPy and Pandas, along with corresponding outdated and updated code implementations. Unlike typical code completion benchmarks, DepreAPI does not provide explicit prompts specifying the intended function, which poses additional challenges for retrieval. To construct natural language queries for our benchmark, we prompt GPT-4o-mini to generate functional summaries of the original code, explicitly excluding any references to deprecated or updated APIs.

3.2
Evaluation Metrics.

Traditional retrieval metrics

To assess the effectiveness of different retrievers, we primarily use
Normalized Discounted Cumulative Gain at rank 10
(nDCG@10) and
Mean Reciprocal Rank
(MRR), both of which emphasize
functional relevance
. nDCG@10 accounts for the graded relevance of retrieved results and their positions in the ranking, making it suitable for evaluating nuanced semantic matching. MRR complements this by measuring the rank of the first relevant result, thereby highlighting a model’s ability to retrieve functionally relevant code early in the list.

Quality-aware metrics

We introduce two metrics to assess a model’s ability to prioritize high-quality over low-quality code in a pairwise comparison setting. For each query, we consider a set of positive samples
\mathcal{P}=\{p_{1},\ldots,p_{M}\}
and negative samples
\mathcal{N}=\{n_{1},\ldots,n_{N}\}
.

Pairwise Preference Accuracy
(PPA) measures the proportion of positive-negative pairs in which the model assigns a higher score to the positive sample, using a scoring function
s(\cdot)

\text{PPA}=\frac{1}{|\mathcal{P}|\cdot|\mathcal{N}|}\sum_{p\in\mathcal{P}}\sum_{n\in\mathcal{N}}\mathbbm{1}\left(s(p)>s(n)\right).

(1)

A PPA of 1 indicates perfect preference for high-quality code, while a score of 0 indicates complete failure. Under random ranking, the expected PPA is 0.5.

Margin-based Ranking Score
(MRS) quantifies the average rank-based margin between positive and negative samples, using the reciprocal rank
r(\cdot)

\text{MRS}=\frac{1}{|\mathcal{P}|\cdot|\mathcal{N}|}\sum_{p\in\mathcal{P}}\sum_{n\in\mathcal{N}}\left(r(p)-r(n)\right).

(2)

In the context of code quality, certain code snippets, such as those containing vulnerabilities, should be avoided, even if they are functionally relevant.
MRS quantifies the extent to which a retriever prioritizes quality awareness, treating code quality as the primary ranking criterion, which is stricter than PPA.
An ideal retriever, with an MRS approaching 1, ranks high-quality code at the top and pushes low-quality code to the bottom, even below functionally irrelevant candidates.
Conversely, an MRS near -1 indicates the worst-case behavior: ranking low-quality code highest while ignoring quality altogether.
When the retriever does not have quality-awareness, MRS should be around 0.

From these results, we draw the following key findings:

(1)
Our benchmark poses challenges for both relevance and quality-aware retrieval.

We observe significant variability in dataset difficulty under relevance-based metrics. For example, most models achieve below 50% on both nDCG@10 and MRR for CodeNet-B, CodeNet-E, and SQLR2. This can be attributed to the fact that these datasets consist of full program implementations rather than isolated function-level snippets, making retrieval more complex. Moreover, as shown in Table
3
, the benchmark presents additional challenges in quality-aware retrieval. Except for Voyage-code-3, all models perform below the random baseline (highlighted in blue) on at least one dataset, underscoring the difficulty of aligning retrieval with real-world quality requirements.

(2)
Traditional relevance metrics fail to precisely capture code quality.

While nDCG@10 and MRR exhibit internal consistency across models and datasets, they fail to reflect distinctions in code quality. Several models achieve high relevance but low PPA and MRS, especially on security and maintainability tasks (e.g., SafeCoder, DepreAPI), while SQLR2 shows the opposite trend—low relevance but strong quality signals—highlighting the limits of relevance-based evaluation. Though there are some strong correlations between relevance metrics and quality-aware metrics on CodeNet-B and CVEFixes, the two measures are poorly associated on SafeCoder and DepreAPI, revealing the distinction of quality-awareness in code retrieval.

(3)
Voyage-code-3 achieves state-of-the-art performance across all benchmarks.

Voyage-code-3 consistently outperforms all other models on both relevance-based and quality-aware metrics across nearly all datasets. Notably, its MRS scores are often twice as high as those of other strong baselines, demonstrating its superior ability to prioritize high-quality over low-quality code. This performance suggests the integration of quality-aligned training objectives and high-quality supervision signals that go beyond mere semantic matching. The pronounced performance gap further underscores the importance of explicitly modeling code quality during retriever training.

(4)
Larger, instruction-tuned models exhibit stronger quality-awareness.

Model size and architectural sophistication play a significant role in quality-aware retrieval. LLM-based and instruction-following retrievers consistently outperform unsupervised and supervised models, particularly in scenarios requiring subtle quality distinctions. Instruction-tuned models with larger capacities, such as Pmpretr-8b and Repllama-8b, show a marked advantage in capturing fine-grained quality signals compared to their smaller counterparts. This trend suggests that larger models, enhanced by instruction tuning and extensive pretraining, are better at capturing deeper aspects of code quality.

6
Conclusion

In this work, we introduce CoQuIR, a new benchmark that brings code quality to the forefront of retrieval evaluation. Unlike prior datasets that focus solely on functional relevance, CoQuIR provides fine-grained annotations across four quality-centric dimensions: correctness, efficiency, security, and maintainability. Through extensive experiments on over 20 retrievers, we show that most current systems lack an explicit preference for high-quality code and often prioritize buggy or insecure implementations over their robust counterparts. To better capture this behavior, we propose two evaluation metrics that assess a model’s ability to favor high-quality over low-quality code. Finally, we demonstrate that incorporating quality-aware training signals improves the performance, underscoring the value of quality-conscious design. We believe that CoQuIR will lay the groundwork for next-generation code retrieval systems aligned with real-world software engineering needs.

Limitations

However, our study has several limitations. While we cover mainstream programming languages, other languages remain unexplored and are left for future work. Additionally, CoQuIR focuses on four quality dimensions and may not fully cover other important code properties (e.g., readability, robustness across platforms).

•

•

•

The authors should use their best judgment and recognize that individual actions in favor of transparency play an important role in developing norms that preserve the integrity of the community. Reviewers will be specifically instructed to not penalize honesty concerning limitations.

For example, if the contribution is a novel architecture, describing the architecture fully might suffice, or if the contribution is a specific model and empirical evaluation, it may be necessary to either make it possible for others to replicate the model with the same dataset, or provide access to the model. In general. releasing code and data is often one good way to accomplish this, but reproducibility can also be provided via detailed instructions for how to replicate the results, access to a hosted model (e.g., in the case of a large language model), releasing of a model checkpoint, or other means that are appropriate to the research performed.

(a)

(b)

(d)
