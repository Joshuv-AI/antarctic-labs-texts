Web Verbs: Typed Abstractions for Reliable Task Composition on the Agentic Web
Linxi Jiang, Rui Xi, Zhijie Liu, Shuo Chen, Zhiqiang Lin, Suman Nath

Abstract
. The Web is evolving from a medium that humans browse to an environment where software agents act on behalf of users. Advances in large language models (LLMs) make natural language a practical interface for goal-directed tasks, yet most current web agents operate on low-level primitives such as clicks and keystrokes. These operations are brittle, inefficient, and difficult to verify. Complementing content-oriented efforts such as NLWeb’s semantic layer for retrieval, we argue that the agentic web also requires a semantic layer for web actions. We propose Web Verbs , a web-scale set of typed, semantically documented functions that expose site capabilities through a uniform interface, whether implemented through APIs or robust client-side workflows. These verbs serve as stable and composable units that agents can discover, select, and synthesize into concise programs. This abstraction unifies API-based and browser-based paradigms, enabling LLMs to synthesize reliable and auditable workflows with explicit control and data flow. Verbs can carry preconditions, postconditions, policy tags, and logging support, which improves reliability by providing stable interfaces, efficiency by reducing dozens of steps into a few function calls, and verifiability through typed contracts and checkable traces. We present our vision, a proof-of-concept implementation, and representative case studies that demonstrate concise and robust execution compared to existing agents. Finally, we outline a roadmap for standardization to make verbs deployable and trustworthy at web scale.

Introduction

The Web is rapidly shifting from a place where people
browse
to a platform where software
acts

(

)
.
With the problem-solving capabilities of modern large language models (LLMs), it is increasingly realistic for natural language (NL) to serve as a primary user interface to online services
(
Liu et al. 2024
;
Plaat et al. 2025
)
.
Web agents interpret an NL task and operate a browser or APIs to fulfill goals such as booking trips, completing purchases, or submitting applications
(
Nakano et al. 2021
;
Yao et al. 2022
)
. This vision of an
agentic web
has catalyzed a surge of research and prototyping
(
Qin et al. 2025
;
Agashe et al. 2025a
;
Agashe et al. 2025b
)
.

Realizing this vision requires coordinated progress on two complementary directions. First, agent capabilities continue to advance, including perception, planning, tool use, and self-monitoring at web scale, as represented by recent systems and benchmarks.
Second, the Web itself must evolve to be hospitable to agents, not only to human eyes. A notable step toward the latter is NLWeb
(
Microsoft 2025
)
, an open initiative that wraps the “raw” Web with a semantic layer for agent interaction (Figure
1
). Using mechanisms such as RSS
(
Hammersley 2003
)
and Schema.org
(
Schema.org Community Group 2011
)
, website developers can create entities such as typed objects, lists, updates, and references from unstructured content. NLWeb tooling embeds these entities and ingests them into a vector database.
However, NLWeb currently focuses only on web content. It demonstrates that a semantic layer improves accuracy, completeness, freshness, and grounding for agent queries. Yet the
agentic web consists not only of content but also of actions
. In this paper, we present our vision for a semantic layer for web actions and show that it is both necessary and achievable.

Web verbs.

Our envisioned semantic layer consists of a gigantic (i.e. web-scale) set of typed functions, which we call
web verbs
. Figure
2
shows an example verb that interacts with
booking.com
to search for hotel options given a destination and dates. It is iconized as a boxed triangle. Without loss of generality, we assume the typed language is Java. There are two possible implementations: (1) if suitable web APIs exist, the verb calls them directly; (2) if the functionality requires a sequence of browser interactions, the verb uses a browser automation library such as Playwright
(
Microsoft 2020
)
to execute the sequence programmatically. Developers can ingest function signatures, types, and DocStrings from their websites into the vector database, making them part of the semantic layer.

With this layer available, a user agent can take the form of a chat interface that hides a coding agent at its core. Internally, an NL task is solved as code that interacts with the Web through composed verbs. Modern LLMs already demonstrate strong coding abilities. Our experiments show that even mid-tier LLMs can reliably produce solutions for fairly complex tasks.

Complementary to API-agents and browser-agents.

Web agents have been an active area of research. Real-world web functionality can be delivered through server-side APIs or client-side browser interactions. Researchers have therefore developed API-agents
(
Song et al. 2025
)
and browser-agents, such as browser-use
(
Müller and Žunič 2024
)
. API-agents can perform only a limited range of tasks, since many functions involving user interaction, session handling, cross-site data mashups, or redirection require browser operations. Browser-agents, while more general, are difficult to build and remain brittle and slow
(
Kara et al. 2025
)
.
They depend on computer vision, webpage analysis, scrolling, keystrokes, and other low-level steps to complete operations that could otherwise be expressed as a single web verb
(
Prabhu et al. 2025
;
Lai et al. 2024
;
Yang et al. 2025a
)
.

Our proposal of web verbs is complementary to web-agent research. Rather than focusing on building smarter agents, we advocate an abstraction layer that existing agents can exploit. This abstraction is analogous to the difference between a high-level programming language and machine code. It is easier and more reliable to compose complex programs in the former. The web-verb layer provides this higher-level interface: every verb is a function with typed inputs and outputs, well-defined semantics, and a stable callable interface. The layer abstracts away the distinction between client-side and server-side functions, so browser-agents and API-agents can be unified. Conceptually, the entire “browser+Web” system is a single gigantic object-oriented program. This uniformity allows agents to compose tasks as precise code with explicit control and data flow.

The abstraction offers agents three major advantages.
(1)
Reliability:
Verbs are packaged by developers, so agents no longer need to rediscover fragile internal steps on every run.
(2)
Efficiency:
Tasks that once required dozens of AI-driven steps reduce to a handful of normal function calls, lowering perception cycles and LLM invocations.
(3)
Verifiability:
Verbs can carry explicit preconditions and postconditions. Typed invocations can be logged, checked, and audited. Security policies and safety invariants can be attached to verb boundaries, making rigorous verification feasible.

Results.

We have implemented a prototype of the verb layer and evaluated it against two baseline web agents. In two representative real-world scenarios, travel planning and furniture shopping, the prototype reliably solved complex multi-step tasks. We constructed a benchmark of 100 diverse web tasks and achieved a 100% success rate with correct and reproducible results, while the baselines failed on such complex cross-site tasks. For clearer comparison, we selected 10 single-verb tasks. However, the baselines were still unable to complete all tasks. Even for the ones completed, the execution time was
2.7{\times}
to
8.3{\times}
that of our approach. These results demonstrate that the verb layer provides stable, efficient, and verifiable abstractions, establishing a strong foundation for the agentic web.

Our code and data are publicly available at
https://github.com/nlweb-ai/MSR-Web-Verbs

2.
Background and Motivation

2.1.
Web Agents

Most web agents today operate within a general perception-action loop: at each step the agent observes the current state of the environment, reasons about the next move, issues an action, and then receives an updated state
(
Sutton and Barto 2018
)
.
This cycle repeats until the task is complete. Within this loop, two common paradigms of interaction exist, distinguished by how actions are represented and executed.

•

Browser agents
act on the browser side, perceiving the DOM, screenshots, or both, and executing low-level interaction primitives such as click, type, scroll, and navigate
(
Deng et al. 2023
;
Zhou et al. 2024
;
de Chezelles et al. 2025
)
.

•

API agents
interact through service-defined endpoints, invoking operations over structured inputs and outputs whenever suitable APIs are available
(
Song et al. 2025
;
Lai et al. 2025
;
Yang et al. 2025b
)
.

2.2.
Weaknesses of Current Agents

Reliability.

GUI-level interactions make reliable workflow synthesis difficult because the abstraction level is too low. An agent faces too many small operations, each carrying only minimal semantics
(
Wang et al. 2025
)
.
For example, a button click may correspond to “opening a drop-down date-picker for selecting the departure date on Alaska Airlines”. This level of granularity is far below the semantics of natural task composition, such as “searching for Alaska Airlines flights with these criteria”. Composing such fine-grained operations is especially problematic when workflows span multiple sites or require long chains of actions. The probability of failure increases sharply, and sequences that initially appear valid often collapse before completion
(
Cheng et al. 2025
)
.
This limitation is evident in IBM CUGA
(
Marreed et al. 2025
)
, the system currently ranked first on the WebArena
(
Zhou et al. 2024
)
leaderboard. While it achieves an average success rate of
0.617
, performance varies widely across sites, and success on multi-site tasks falls to
0.354
despite involving fewer records.

Availability.

Many sites expose Web APIs, but coverage is typically partial. Public, read-only endpoints are common, while many browser-available actions are absent
(
Khan et al. 2021
;
Zhong and Su 2013
)
. Essential user-facing functions such as interactive login and MFA, consent and cookie dialogs, cart and checkout flows, session-bound navigation, and cross-site redirects are implemented in rich clients and cannot be completed through APIs alone
(
Balash et al. 2022
)
. In addition, many APIs are designed for server-to-server integration rather than direct user interaction. They often require keys and OAuth grants, impose quotas and rate limits, and may be locked behind subscriptions or partner agreements
(
South et al. 2025
)
. As a result, an API-only agent can access only a narrow portion of real functionality.

Efficiency.

GUI-driven agents re-perceive the page and re-plan after nearly every click or text entry. Each cycle incurs LLM inference, DOM or screenshot processing, and tool calls. Consequently, even simple goals expand into lengthy traces: bookings and checkouts often require dozens of steps
(
Zhou et al. 2024
;
Xie et al. 2024
)
, and realistic multi-site workflows can exceed one hundred. This inflates latency and compute cost while compounding error accumulation across steps.

2.3.
Necessity of a Higher Abstraction Layer

To overcome these limitations, the agentic web requires a higher-level action abstraction that aligns with user goals and spans both browser interactions and server-side APIs. At this level, each operation encapsulates the many primitive steps underlying a site capability and exposes a stable typed interface with clear inputs, outputs, and effects. The layer must provide broad coverage and strong composability so that complex multi-site tasks become short, well-structured programs rather than long reactive traces. Equally important, it cleanly separates responsibilities: website developers package and maintain these operations, while agents reason, plan, and compose above the layer of the operations. In the next section, we instantiate this abstraction with web verbs.

3.
Verb Abstraction for the Agentic Web

3.1.
Web Verbs

As introduced in §
1
, a
verb
is a high-level, typed, function-like abstraction of an operation that a website can perform. Unlike primitive actions such as text entry or mouse clicks, or raw HTTP/API calls, a verb directly names the intended operation and specifies its inputs, outputs, and effects. For agents, verbs act as stable units for planning and execution: they can be invoked programmatically and composed into workflows, avoiding the fragility and length of low-level action traces.

The verb layer
unifies
browser-side interactions and server-side APIs. Implementation details are hidden behind a common typed interface. When a site provides a suitable API, developers wrap the endpoint as a verb (for example, Spotify’s search endpoint with parameters for query, item type, and market). When functionality resides in client flows, such as adding an item to a shopping cart on Amazon, developers implement the verb by programmatically driving the browser. In both cases, agents interact only with verbs, making the distinction between API and GUI orthogonal at the call boundary.

To fulfill their purpose effectively, verbs should satisfy the following essential properties:

•

Semantic clarity.
Each verb should state its intended operation explicitly in natural language so that its role is transparent to both agents and developers.

•

Typed parameters.
Inputs should have proper names and types, ensuring unambiguous invocation and consistent integration into workflows.

•

Structured results.
Outputs should be returned as standardized objects or records so that subsequent steps can consume them directly without additional parsing.

•

Composability.
Verbs should be callable in sequence, allowing tasks to be represented as concise programs over meaningful operations rather than long traces of primitive actions.

•

Auditability.
Each invocation should produce explicit inputs and outputs that can be logged, validated, and checked, providing a basis for verification and debugging.

3.2.
Code Synthesis over Verbs

With verbs as the abstraction layer, tasks are no longer carried out as step-by-step predictions of primitive actions within the perception-action loop. Instead, the agent generates explicit programs composed of verb calls. Each verb has a precise specification of its inputs and outputs, so every invocation behaves as a well-defined function rather than an ambiguous low-level action. Within a program, the results of a verb can be transformed, combined with other data, or used as conditions for subsequent steps. This makes the logic of the task explicit in code: the synthesized program specifies not only which verbs are invoked but also how their outputs are processed and connected.

The composition of verbs is not limited to a linear flow. Programs can include control structures such as conditionals, where the next operation depends on intermediate results, or loops, where the same verb is applied repeatedly over a collection of inputs. Branching and iteration are thus expressed directly in the program rather than being decided incrementally during execution.

This stands in contrast to existing web agents, which must repeatedly observe the current state and predict the next low-level action. By operating at the level of verbs, the agent instead constructs a complete procedure in advance, with the sequence of operations and their dependencies made explicit. The role of the agent shifts from predicting primitive steps to composing structured programs that capture the semantics of the task.

4.
Prototype and Case Studies

4.1.
Prototype Overview

To implement the ideas presented in §
3
, we developed a proof-of-concept system for the verb layer. This prototype demonstrates how verbs can be created, documented, and combined into executable workflows.

We assume the role of a website developer. Wrapping a web API as a verb is straightforward. For browser-based functionality, we built a Chrome extension to support the process. The extension records details of browser actions and the targeted HTML elements while we manually operate the browser. The recorded action trace is then used to generate a function that calls the Playwright library to perform each browser operation. We test and debug the function to remove unnecessary steps and confirm the correctness of the element locators. Once the function reliably reproduces the action trace, variable elements corresponding to user input are abstracted into typed parameters, and outputs are organized into structured result objects. Each verb is paired with a concise natural language description specifying its intended behavior.

In this way, the sequence of browser operations is transformed into a stable packaged verb by the developers.

It is worth noting that some element locators, such as

6

The HTML standard should introduce a “stable-public-locator” attribute for elements intended for external reference by code or agents. Such an attribute would form part of the public interface of a website, and modifying it would constitute a breaking change.

4.2.
Case Studies

To illustrate how the prototype can be applied to realistic user goals, we present two representative case studies. The first concerns travel planning, and the second focuses on online shopping. Both involve multi-step reasoning and coordination, yet they can be expressed as concise workflows through verbs.

Travel Planning.

This case study shows how a travel planning task can be expressed concisely with the verb layer.
The user request is as follows:

User Task

"I will travel to Anchorage for three days, and I would like
to visit two museums each day. Please recommend good museums
and hotels, and then rank the hotels by the total distance
to all the selected museums."

The task is not just to recommend museums and hotels. It also asks for a specific ranking: for each candidate hotel, compute its distance to each selected museum and aggregate these distances into a single total.

With verbs, the task is expressed as a short executable procedure with explicit intermediate results.
It naturally decomposes into two steps.
First, the agent identifies candidate museums and hotels in Anchorage by invoking the NLWeb
(
Microsoft 2025
)

ask
interface wrapped as a verb, which returns structured entities with metadata such as name, description, and location.
Second, to rank hotels by total distance to the selected museums, the agent invokes the Google Maps verb
get_direction
, which returns travel time and distance as structured outputs.
Figure
6(a)
shows the agent-synthesized nested-loop procedure.
Using
get_direction
, the synthesized program loops over hotels and museums, accumulates per-pair distances into a per-hotel total, and then sorts hotels by the totals.

Furniture Shopping.

The second case study considers a user who has just moved into a new apartment and needs to purchase essential furniture, including a bed frame, mattress, desk, chair, floor lamp, air purifier, and carpet.
The user request is as follows:

User Task

"I just moved into a new home and need to buy furniture,
including a bed frame, mattress, desk, chair, floor lamp, air purifier, and carpet.
Please find three candidate products for each category, and then select a combination that maximizes overall rating while keeping the total cost within a budget of $1,000."

This request combines product search with a constrained selection problem.
The agent must choose one item per category, stay within a global budget, and maximize an objective over the entire set.

By invoking verbs, the agent retrieves candidates for each category with structured fields such as price and rating, reducing the remaining step to a standard selection problem.
The agent then synthesizes a program that searches over candidate combinations, computes the total cost and total rating, and returns the highest-scoring configuration that stays within the $1,000 budget.
Figure

shows the agent-generated loop that evaluates combinations and updates the best set as it searches.

Baseline Comparison.

To contextualize the performance of our approach, we compared it against two representative web agent baselines, both running on the same underlying model, Claude 3.7 Sonnet. The first baseline is adapted from the open-source repository
openai-cua-sample-app

(
OpenAI 2025
)
, where the model directly controls the browser step by step through the GUI without structural support. This setup illustrates a minimal agent design and serves as a model-only baseline. The second baseline is
browser-use

(
Müller and Žunič 2024
)
, an open-source framework that augments the model with explicit management of perception, memory, and control flow. Both baselines follow the paradigm of GUI agents, where tasks are executed by issuing low-level interactions with the browser interface.

As shown in Figure
7
, verb-based workflows are expressed as short programs consisting of a few well-defined function calls that reliably produce correct results, whereas GUI-based agents expand into long sequences of primitive actions that often lead to errors or inefficient execution. In the travel planning task, the baseline agent did not compute distances from each hotel to every museum. Instead, it reduced the problem to a single route by chaining the museums together as waypoints, which led to an incorrect hotel ranking. In the furniture shopping task, the baseline adopted a greedy strategy, selecting items until the budget was exceeded and then stopping. As a result, it failed to consider the remaining categories or explore alternative lower-cost combinations that would have satisfied the constraint.

Baseline agents often deviate from the intended reasoning process, either by oversimplifying the problem or by failing to explore the full solution space. These shortcomings lead to incorrect results even when individual GUI actions are executed correctly. In contrast, verb-based workflows encode the intended computation explicitly as concise programs, producing solutions that are compact, reproducible, and able to cover the complete search space.

4.3.
Task Evaluation

To further validate the effectiveness of the verb layer beyond the case studies, we conducted a larger-scale evaluation. We constructed a benchmark of 100 tasks that reflect common scenarios users might perform on the web. Examples include planning a romantic dinner that involves checking the weather, finding restaurants, shopping for supplies, and creating a playlist, or organizing a trip that requires combining information from travel, mapping, and booking services.

Across the full set of 100 tasks, our approach successfully completed every task. All outputs were manually verified for correctness, and repeated runs of a subset of tasks produced consistent results. These findings demonstrate that the verb layer, combined with program synthesis, can reliably support diverse web tasks at scale.

Consistent with the case study results, the baselines were unable to handle complex cross-website tasks that required multi-step reasoning and structured data processing. To provide a clearer comparison, we decomposed the workflows into simpler tasks and selected 10 representative single-site tasks from different websites, as summarized in Table
1
. This setup avoided cross-website coordination and reduced planning complexity, more friendly to the baseline agents.

Our method succeeded on all 10 representative tasks, whereas the two baselines failed to solve the full set. The baselines completed some relatively straightforward tasks (e.g., retrieving astronomical images from NASA or querying weather forecasts), but consistently failed on tasks requiring multi-step decision making and structured intermediate outputs. For example, they were unable to complete the furniture shopping and travel planning tasks, which require decisions across multiple steps, or tasks such as budgeting supplies on Costco and searching news articles, which require organizing and filtering intermediate results.

We observed two primary error modes. First, some tasks produced incorrect results because the baselines were unable to manage intermediate outputs consistently or perform the additional data processing required. Second, execution was hampered by memory limitations, especially for tasks with longer action sequences. For example,
browser-use
frequently generated warnings of memory breakdown when histories grew too large, as shown in Figure
8
.

5.
Why the Agentic Web Needs the Verb Layer

The case studies highlight not only the practical benefits of the verb layer but also the deeper reasons why it is necessary. We summarize these reasons along three dimensions: reliability, efficiency, and verifiability.

First, verbs improve reliability by providing stable semantics.

Each verb has a predefined implementation, so an agent does not need to infer concrete GUI actions from a combination of the task description and the current webpage structure. This design yields more stable behavior and avoids the variability that arises when reasoning step by step over raw interfaces. GUI-level actions lack semantic meaning because each click or keystroke is bound only to layout coordinates or interface styling without conveying the intended operation. By contrast, verbs expose explicit semantics through typed inputs and outputs, decoupling the agent’s reasoning from surface-level features such as page layouts or element identifiers. As a result, workflows remain robust even when interfaces evolve. For example, retrieving directions between a hotel and a museum through raw interactions would require dozens of fragile steps that could fail at any point, whereas the verb
get_direction
encapsulates the entire operation as a single stable call that works consistently across interface variations.

Second, verbs improve efficiency through structured composition.

Executing a task at the GUI level expands into long traces of clicks and keystrokes, and even API-based agents often need custom code to bridge gaps. Verbs instead expose operations as high-level building blocks that can be composed into concise programs with explicit control flow and data flow. This reduces the number of reasoning cycles and perception steps, turning tasks that once required dozens of manipulations into a handful of stable calls. The result is faster execution and better reuse of knowledge across sites.

Third, verbs enable verifiability of reasoning.

Neither GUI traces nor ad hoc APIs provide transparent evidence of what an agent has done. Verb calls, in contrast, are explicit invocations that can be logged, validated, and audited. This transparency enables correctness checks, debugging of failed executions, and enforcement of site-level policies such as authentication requirements or safety constraints. In practice, agent reasoning steps become interpretable units of computation rather than opaque sequences.

Together, these properties show that the verb layer is not merely a local optimization but a structural necessity. It equips agents with stable operations, allows them to handle complex tasks more reliably, and makes execution both efficient and verifiable.

Beyond the technical benefits, the verb layer points toward the broader vision of an
Agentic Web
. The aim is not only to
build agents for today’s web
but also to
adapt the web itself for agents
. Web verbs provide the semantic stability, compositional scalability, and verifiability required for this transition. They encapsulate low-level operations as reusable units, which agents can combine into larger workflows. In this sense, verbs supply the building blocks and agents supply the reasoning, forming a coherent ecosystem for web automation.

This relationship is closely analogous to the role of programming languages. Verbs stand in relation to primitive GUI actions much as high-level languages stand in relation to assembly instructions. Just as high-level languages allow developers to express structured programs without reasoning about every register and instruction, verbs allow agents to construct workflows without reasoning about every click and keystroke. This analogy highlights how verbs raise the level of abstraction while preserving the precision of underlying actions. The result is a more efficient and reliable mode of interaction that supports the development of the Agentic Web, moving beyond fragile traces of primitive actions toward a shared substrate of verbs as the common language between sites and agents.

6.
Standardization, Community, and Open Problems

Standardization.

Because the verb layer sits between the raw web and the agent, standards are needed to govern how HTML elements are exposed to verbs and how verbs are exposed to agents. As noted in §
4.1
, the HTML standard should introduce a new attribute, perhaps named “stable-public-locator”, to expose HTML elements in a principled manner. This locator would be similar in spirit to CSS class names, enabling elements in the DOM tree to be located through a path. However, unlike class names, the standard should specify that the “stable-public-locator” is part of a website’s public interface. Its values must remain stable, since changes would break backward compatibility. The standard may also recommend using descriptive natural language strings, which would improve code readability and make elements more directly usable by agents.

In addition, a standard should govern the registration of verbs within a global namespace, much like DNS or SSL/TLS. Each verb would have a fully qualified name, such as
amazon_com::addToCart
, under the authority of its web domain. The standard should also define how to schematize signatures, types, and DocString descriptions, along with safety specifications such as preconditions, postconditions, and permission manifests.

The developer community.

The developer community will be central to building the agentic web. A similar whole-community effort occurred when mobile computing became an evident paradigm shift. The original web was designed for PCs, so it required web developers to deliberately “wrap” it in order to support mobile applications. The shift toward the agentic web represents a comparable change.

Developers are well positioned to implement verbs because they have authoritative knowledge of their sites’ semantics and constraints. Building high-quality tools will be key. As described in §
4.1
, we developed a tool that records action sequences in the browser and converts them into functions that call Playwright. This greatly reduces the effort of implementing verbs. It is natural to envision AI-powered tools that can read a verb description, interact with the browser automatically, record the action sequence, and generate the corresponding function. In this sense, the AI techniques used to build GUI-based agents today can also empower developers to construct verbs, making the two directions complementary.

Other open problems.

Several open problems remain important for future research: (1) effective vectorization and retrieval algorithms, (2) security and permission mechanisms, and (3) curation of benchmarks.

At present we use the vectorization and retrieval functions from NLWeb, which were designed primarily for web content. Although they work correctly with the schematized verb information we created, the current scale of verbs is too small for retrieval effectiveness to matter. When the number of verbs grows to web scale, research will be needed to optimize both vectorization and retrieval.

Security and permission remain critical challenges for any web agent. The verb layer, however, provides the advantage of explicit programming abstractions. Security and permission requirements can be defined as preconditions and postconditions, and since a solution is expressed as code, it can be rigorously verified either statically or dynamically. This opens opportunities for research into modeling real-world security requirements as logic conditions.

Finally, benchmarks will be essential for advancing the field. Composing verbs allows agents to attempt complex, end-to-end tasks, but existing benchmarks were not designed for this level of abstraction. There is a clear need to curate a large collection of multi-site complex scenarios where correctness and security are critical, ensuring that evaluation reflects the true challenges of the agentic web.

7.
Conclusion

The agentic web envisions a future where agents interact with the web to access content and accomplish tasks reliably on behalf of users. NLWeb is an initiative that makes today’s web more hospitable to these agents, with its semantic layer serving as an intermediary between the agent and the raw web. Our work extends this idea from a focus on web content to web actions. We propose
web verbs
, a web-scale set of typed, semantically documented functions that expose site functionalities through a uniform interface, whether implemented via APIs or client-side workflows. This paper demonstrates that a verb layer can play a crucial role in realizing the agentic web.

As a proof of concept, we implemented verbs for 13 websites across five categories: E-commerce, Travel, Knowledge, Media, and Others.
We conducted two realistic case studies, travel planning and furniture shopping, and found that the verb-based approach reliably completed tasks with concise programs.
We also constructed a benchmark of 100 diverse web tasks. The results show that GitHub Copilot, when supplied with verbs, completed the tasks reliably, while two representative web agents,
openai-cua-sample-app
and
browser-use
, frequently failed. Even when complexity was reduced to single-verb operations, the agents succeeded only about half of the time. Moreover, their execution was 2.7× to 8.3× slower than verb-based solutions. These findings suggest that, without a verb layer, current web agents cannot scale to reliable multi-step reasoning and efficient execution.

We emphasize that building the verb layer is complementary to, not competing against, the effort of advancing web agents. A promising direction is to leverage web agents as tools to help developers implement verbs more effectively. Based on our experience, we believe that a web-scale verb layer is achievable if the community embraces this vision.
