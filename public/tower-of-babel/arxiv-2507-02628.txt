Medical Data Pecking: A Context-Aware Approach for Automated Quality Evaluation of Structured Medical Data
Irena Girshovitz, Atai Ambus, Moni Shahar, Ran Gilad-Bachrach

Abstract
Background: The use of Electronic Health Records (EHRs) for epidemiological studies and artificial intelligence (AI) training is increasing rapidly. The reliability of the results depends on the accuracy and completeness of EHR data. However, EHR data often contain significant quality issues, including misrepresentations of subpopulations, biases, and systematic errors, as they are primarily collected for clinical and billing purposes. Existing quality assessment methods remain insufficient, lacking systematic procedures to assess data fitness for research. Methods: We present the Medical Data Pecking approach, which adapts unit testing and coverage concepts from software engineering to identify data quality concerns. We demonstrate our approach using the Medical Data Pecking Tool (MDPT), which consists of two main components: (1) an automated test generator that uses large language models and grounding techniques to create a test suite from data and study descriptions, and (2) a data testing framework that executes these tests, reporting potential errors and coverage. Results: We evaluated MDPT on three datasets: All of Us (AoU), MIMIC-III, and SyntheticMass, generating 55-73 tests per cohort across four conditions. These tests correctly identified 20-43 non-aligned or non-conforming data issues. We present a detailed analysis of the LLM-generated test suites in terms of reference grounding and value accuracy. Conclusion: Our approach incorporates external medical knowledge to enable context-sensitive data quality testing as part of the data analysis workflow to improve the validity of its outcomes. Our approach tackles these challenges from a quality assurance perspective, laying the foundation for further development such as additional data modalities and improved grounding methods.

In this work, we propose a novel method for medical data quality evaluation by adapting unit testing principles originating in software engineering for use in data science workflows. The Medical Data Pecking approach, implemented through the Medical Data Pecking Tool (MDPT), uses an LLM to automatically generate unit tests tailored to the target population and dataset. Analogous to selective pecking behavior in birds, Medical Data Pecking scans structured health records to identify relevant data fields, flag inconsistencies, and exclude extraneous content. It applies the generated tests to the data, identifies potential issues, and reports untested fields to quantify test coverage.

Methods

In this section, we introduce the Medical Data Pecking approach and the methods used to evaluate its performance. We begin by describing the user-provided input, followed by the process of test generation and the procedures used to apply these tests to the data (see Figure
1
for a schematic overview of the process). We then present the datasets and evaluation metrics used to assess MDPT’s performance. Additional details are provided in the supplementary materials, Section
S1
.

Figure 1:
A schematic overview of the MDPT workflow.

User-defined study parameters are input into an LLM module that retrieves regional disease rates, contextual epidemiology, and generates
lists of diagnosis, drug, measurement, and procedure codes via vector-database search. These reference values are transformed into a test matrix, implemented as unit tests, and validated in a double-pass step to reduce LLM hallucinations. The DFtest framework then executes the suite on the target dataset, yielding binary test outcomes and statistical comparisons between observed data and expected epidemiological distributions.

2.1
Test suite generation

The Medical Data Pecking approach is designed to evaluate datasets extracted from electronic medical records for a clinical research. The user provides the studied condition, geographic region, the classification systems used to record drugs, procedures, laboratory results, and diagnoses, as well as the data schema. An example input is shown in Figure
2
.

This information is used by MDPT to retrieve contextually relevant statistics. Our implementation uses an LLM (GPT-4o, model version 2024-08-06, with a temperature of 0 and seed set to 37, accessed via the Azure OpenAI API service, API version 2024-05-01-preview). These statistics are further grounded and validated through the Bing Search API, also accessed via Azure.

The grounded statistics undergo a second validation step to reduce LLM-induced hallucinations and ensure grounding in reliable sources. In the initial grounding process, MDPT extracts pre-existing information for the studied condition such as prevalence, incidence, mortality rate, lifetime risk, and age distribution among patients. In addition, it includes comorbidity rates, expected laboratory test statistics, and commonly prescribed medications among patients.

Figure 2:
An example of user provided study parameters in JSON format
, illustrating the defined cohort, the coding system, and the reference path to the data schema (All of Us).

Next, MDPT extracts diagnosis, drug codes and procedure codes for the studied condition and its comorbidities using the user-specified classification systems. To achieve that, classification system vocabularies from the OHDSI standardized vocabularies
[
42
]
(available at
athena.ohdsi.org
) are pre-embedded using OpenAI’s
”text-embedding-3-small”
model in Azure OpenAI API and stored in Chroma open source vector database (
www.trychroma.com
). For each condition, MDPT performs a vector similarity search to retrieve appropriate codes. Demographic codes (e.g. gender, race and ethnicity), are extracted in a similar manner. However, since the evaluated dataset may use demographic codes that do not align with the specified classification system, the MDPT relies on the actual codes specified in the provided data schema.

The resulting output tables include test suggestions, derived from reference statistics. These tables undergo a second validation pass, during which the grounded LLM reviews the initially retrieved statistics. For each entry, it determines whether the value should be corrected, removed or left unchanged. Entries marked for removal are discarded, while those marked for correction are replaced with revised values. The validated tables are subsequently converted into unit tests (see example in Figure
3
), which use statistical methods to tolerate variance in the data.

2.2
Statistical methods

Unit tests compare the expected metrics, extracted by the LLM, with the empirical metrics observed in the dataset. MDPT tests the magnitude of the standardized mean difference (SMD), flagging cases where
SMD\geq 0.2
.
This approach accounts for large sample sizes, in which small differences may be statistically, but not clinically, significant.
[
43
]

In this work, we applied Welch’s t-test for unequal variances to compare the distribution of age-at-diagnosis. A p-value
\geq{0.05}
indicates no statistically significant difference between the populations.
MDPT also verifies that the ratio between the expected and observed proportions lies within 0.85-1.15, a ±15% margin established in prior EHR prevalence validation studies,
[
44
]
to distinguish between genuinely similar proportions and small but meaningful discrepancies.

2.3
Unit testing the data

Once generated, tests are executed using DFtest, a Python package we developed that is inspired by the
pytest
unit testing framework. DFtest can run independently or as an integrated component of MDPT, supporting both automatically and manually generated tests. Similar to traditional unit tests, DFtest applies test suites systematically, enabling quality checks when new data is extracted or when changes are made to the data processing pipeline, which facilitates integration into continuous software development workflows. DFtest produces both test outcome summaries and coverage reports.

2.4
Coverage

The output includes test results and the column coverage percentages in the examined dataframe, with optional visualizations of evaluated fields.
Although coverage is sometimes used as a test sufficiency metric in software testing,
[
45
]
this notion is limited in data quality contexts. A column may be considered ”covered” even if only checked at the metadata level. To address this, we expand the definition of coverage to support multi-level data inspection:

1.

Metadata level. For example, confirming field presence or non-missing values.

2.

Distribution level. For example – a specific lab test population-wide distribution should align with a theoretical distribution. In this case, even if the evaluated column is permuted, the population-wide distribution will remain unchanged.

3.

Subpopulation level. These tests analyze intra-group patterns (for example, women with a condition) and offer greater depth than population-wide checks.

Test quality validation

To assess test quality, we evaluated reference validity and grounding accuracy.
Grounding accuracy was based on source trustworthiness and correctness of the cited reference values. A source was deemed invalid if it led to a nonexistent page or was unrelated to the studied condition. Reference values were categorized as follows:

•

Accurate:
Matches the expected value from a credible source.

•

Inaccurate:
Within 2 standard deviations (SD) of the expected value, or a point estimate where a range is expected.

•

Incorrect:
Deviates by more than 2 SD from the expected value.

•

Qualitative:
Described as a trend or strength of association rather than a numeric value.

•

Irrelevant:
No relevant reference found for the required statistic.

Categories were grouped into ”correct” and ”non-correct” based on the accuracy of the reference values: the ”correct” category includes the ”accurate” group, while ”non-correct” includes all other groups.
Test outcomes were considered passed if they matched the reference, and failed otherwise. Therefore, it is important to recognize that a failed test suggests a possible flaw in the data, as it may inaccurately portray the population studied.

Results

To evaluate MDPT we generated test suites to evaluate type 2 diabetes (T2D) and chronic kidney disease (CKD) in the AoU dataset, hypertension (HTN) in SyntheticMass, and congestive heart failure (CHF) in MIMIC-III.

3.1
Test quality validation results

MDPT generated between 55 and 73 unit tests for each dataset. Notably, 20-43 tests identified deficiencies in the data, meaning there were discrepancies between the data and the reported statistics in the literature.

35-93% of tests included a valid reference. Accurate information grounding was present in 43-61% of tests, inaccurate in 7-22%, incorrect in 12-26%, and qualitative reference values in 0-4%. Up to 13% of tests lacked relevant grounding information. Table
1
summarizes test quality evaluation results across cohorts and datasets.

Manual inspection of the results revealed that many of the drug-related tests were classified as irrelevant or incorrect, as information on prescribed drug prevalence in the context of specific medical conditions is often unavailable. Therefore, Supplementary Table
S4
presents the test quality results excluding prescribed drug prevalence. The percentage of valid references slightly increased (39-98%), with higher rates of accurate information grounding (48-69%), and lower rates of irrelevant (0-7%) and incorrect (8-20%) references. Qualitative (0-5%) and inaccurate (7-25%) reference grounding remained comparable to the full test-suite evaluation.

Gender and race tests failed in the AoU dataset, reflecting its known over-representation of women and underrepresented groups (see Supplementary Report Example in the supplementary material).

Among the 60 tests generated for the T2D cohort, 6 passed (1 with correct reference values), 54 failed (34 of them used correct references), and one was a metadata test without a reference value.

For CKD, 2 out of 44 distribution-level tests passed (none with correct references), and of the 42 that failed, 31 used correct reference values. Of the 22 subpopulation-level tests, none passed (9 used correct references).

Evaluation on SyntheticMass and MIMIC-III datasets

To assess the robustness of MDPT, we evaluated the suitability of SyntheticMass for HTN, and MIMIC-III for CHF research.

Of 73 generated tests for HTN, 2 passed (both with non-correct reference values). Among the 71 failed tests, 43 used correct references. Of the 29 tests with non-correct references, 5 (7%) were inaccurate, 19 (26%) incorrect, and 5 (7%) irrelevant.

Out of 55 generated tests for CHF, 4 passed (3 with correct reference values) and 51 failed (20 with correct references). Interestingly, these tests failed due to a medical classification mismatch: this dataset instance omitted dots typically present in ICD-9 codes, leading to evaluation failures. Among tests with non-correct references, 12 (22%) were inaccurate, 11 (20%) incorrect, and 8 (15%) irrelevant.

By coverage level, the single metadata-level test failed in both cohorts.
Most distribution- and subpopulation-level tests for HTN and CHF failed, despite a substantial proportion utilizing correct reference values. Only a small number of tests passed, some of which were based on non-correct references (for full results, see Supplementary Table
S6

4
Discussion

In this study, we introduced the Medical Data Pecking approach and demonstrated it through MDPT, a context‑aware framework for automated data quality assessment in structured medical datasets. The MDPT uses AI to harness existing knowledge to assess the reliability of specified data. We evaluated MDPT by generating test suites. Suites contained 55-73 tests, 20-43 of them identified discrepancies between the data and literature-based expectations. Using unit testing principles, Medical Data Pecking introduces scalable evaluation of dataset fitness for research.

We also measured test-suite quality using different metrics such as coverage and reference validity that ranged from 93% in the HTN suite to 35% in the CHF suite. We observed that the suites for well-studied conditions, such as T2D and HTN, were better grounded than those focused on less studied conditions such as CHF. However, the percentage of tests that identified divergence from expectations based on the literature remained high for all conditions.
This highlights the potential utility of MDPT as a checkpoint prior to subsequent analyses. Furthermore, MDPT performance is expected to improve as LLMs, grounding techniques, and access to public health data continue to advance.

Moreover, all tests in the suite can be manually edited, and additional tests can be added. This flexibility ensures that even if the default test parameters or statistical thresholds are too sensitive or not sensitive enough, they can be adjusted in the code to better reflect domain-specific requirements. This feature allows users to fine-tune the test suite to better align with evolving research needs or newly available evidence.

As
[
49
]
argued, testing can be used to show the presence of bugs, but never to show their absence. Moreover, the current implementation of the Medical Data Pecking approach is still limited. The limitations include its reliance on general population benchmarks that can obscure deviations in specific subgroups and the faulty tests generated by AI mechanisms. We expect that as research on medical data expands and AI systems become more effective at extracting insights, their utility will increase, leading to improved coverage, accuracy, and grounding of the generated tests. Furthermore, the impact on the validity of the subsequent research should be studied - this could be negatively affected due to
implied truth effect
where researchers can interpret the absence of warnings as an indication of validity.
[
50
]

Despite these limitations, we argue that quality control measures for data, such as those Medical Data Pecking offers, should be further developed and become a standard tool in medical data analysis. We anticipate that this will improve the reliability of the analysis results.
