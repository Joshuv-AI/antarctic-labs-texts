Data Version Management and Machine-Actionable Reproducibility for HPC based on git and DataLad CCS: Computing methodologies Parallel computing methodologies CCS: Information systems Data management systems
Andreas Knüpfer, Timothy J. Callow

Abstract
. We present the adaptation of an existing data versioning and machine-actionable reproducibility solution for HPC. Both aspects are important for research data management and the DataLad tool provides both based on the very prevalent git version control system. However, it is incompatible with HPC batch processing. The presented extension enables DataLad’s versioning and reproducibility in conjunction with the HPC batch scheduling system Slurm. It solves a fundamental incompatibility as well as inefficient behavior patterns on parallel file systems.



1.
Introduction

Research Data Management (RDM) and reproducibility

Research data management and reproducibility are important in all fields of science, in data-intensive research even more so.
In Scientific Computing, some things should generally be easier compared to experimental science in a lab, because when all the data processing is done by computers, then it should be simple enough to record all steps and all data. However, this is not generally the case for a variety of reasons.
In High Performance Computing (HPC) in particular, the rate of data generation and the sheer volumes of data produce challenges of their own.
There are some hard challenges like practical access to old hardware, which are even more drastic in HPC.
However, there are also essentially solved problems, like regaining a precise version of a given software from its version control system.
Proper version control — most of the time through
git
— is the norm for software projects today, and is in place for the vast majority of scientific software. The same is not true for most scientific data collections, even though software is just one special kind of data, isn’t it?

The F.A.I.R. data principles

The F.A.I.R. data principles
Wilkinson et al. 2016
are prevalent goals for research data management and the foundations for more concrete standards in all fields of science. They list four core requirements — Findable, Accessible, Interoperable and Reusable — represented by the four letters of the acronym, and within those core requirements list more detailed requirements for minimal standards for research data management.

Fulfilling the F.A.I.R. requirements is in every scientist’s own interest for keeping an overview about all available data from their own past efforts. They are also in the interest of the scientific community to avoid redundant efforts and to increase confidence in scientific findings.
Furthermore, they are mandatory for most scientific institutions and funding agencies.

Reproducibility in Computational Science

This addresses the ability to repeat computations and thus recreate the results, either to check their validity, or to continue working with it. This is more valuable than just to be given access to the resulting data. Firstly, because it allows us to check if the disclosed instructions really lead to the presented data. And secondly, because some data may be too large to store or transfer, but reasonably easy to reproduce and check against.

Reproducibility ideally means bit-wise reproduction of all result files. In many cases, e.g. with iterative solvers, a close enough match according to a given metric will be good enough.
The prerequisites are that
(1) all input data is specified and retrievable,
(2) all required hardware and software as well as the execution environment are specified and available, and
(3) complete instructions for re-executions are available.
For machine-actionable reproducibility the instructions must be (4) suitable for fully automatic re-execution without human intervention. This is the key topic of this paper.

Contributions

This paper provides the following contributions:

•

Introduce the existing DataLad
Halchenko et al. 2021
data version control solution based on git, which explicitly addresses large and binary files that standard git cannot handle well via git-annex. This includes a number of benefits for HPC.

•

Introduce the machine-actionable reproducibility feature for computational workflows in DataLad and how it is incompatible with HPC processing.

•

Present an extension to make the machine-actionable reproducibility compatible with HPC environments and Slurm batch processing. Evaluate the proposed solution.

•

Present a solution to the undue stress that large git repositories may have on parallel file systems.

2.1.
The F.A.I.R. principles without versioning?

The F.A.I.R. principles are the widely accepted minimal criteria for good research data management and part of many institutional guidelines as well as national and international standards
Wilkinson et al. 2016
.

Reproducibility as part of provenance is a core aspect of the F.A.I.R. principles but versioning of data is missing. Only criterium
"A2. metadata are accessible, even when the data are no longer available"
touches versioning most rudimentary
Wilkinson et al. 2016
.
So, was versioning overlooked when the F.A.I.R. criteria were defined? Or was it seen as a mere technical detail as part of data provenance? Or deemed to much to ask back when F.A.I.R. was proposed? The authors assume the latter because access to (some) past versions of datasets would simply be too useful to be left out as a general requirement.

Very few research data management papers address version control for data as a key requirement.
Klump et.al.
Klump et al. 2020
describe the state of the art in research data versioning: Explicitly defined
data publications
are the coarse-grained version steps. They comment how it is not as fine-grained as source code versioning, still they recommend it as the minimum standard for research data.
Heinrichs et.al.
Heinrichs et al. 2022
define requirements for research data management and include versioning of data and metadata as "requirement 6". It is not clear if this refers to coarse-grained or fine-grained versioning. However,
Freund et.al.
Freund et al. 2024
recently compared a list of solutions including git-LFS and DVC for their version control capabilities for research data and found that non of them fulfilled all their defined requirements. DataLad — with or without the Slurm extension — would satisfy all of them except for the "data citation" requirement.

2.4.
Reproducibility solutions suitable for HPC

The standard solution for machine-actionable reproducibility in data-driven research are workflow automation systems like AiiDA
Huber et al. 2020
;
Uhrin et al. 2021
, Galaxy
1 1
;
Gr\"uning et al. 2018
, or similar. There are different solutions favored in different fields of science.
They offer multi-stage "workflows" or "processing pipelines" as combination of diverse processing steps from lightweight pre/postprocessing to heavyweight parallel computations.
They manage many instances for many datasets or parameter sets and aim at high-throughput computing (HTC, many independent jobs) but also integrate with HPC.

Workflow managers keep track of input / intermediate / output datasets and how the are produced from each other (provencance records). For reproducibility they can simply re-generate the original processing steps again.
They don’t include data version control, however, some integrate with community-specific research data portals which support versioned data publications.

Workflow systems are usually quite complex and have a considerable learning curve. If there is a de-facto standard in your field of science they are certainly the solution of choice.

The presented solution has the advantage to be generic and to adopt the widely familiar git know how for a shorter learning curve.

2.6.
DataLad repositories in HPC environments

Even though DataLad was not designed for HPC, there are several benefits for typical scenarios already:

Copy an HPC project to / from a cluster

Usually, access to HPC resources is granted for limited time periods. When a new project is starting, one has to bring all prerequisites in place including code, scripts, and input data.
If this was organized in a DataLad repository it would be as easy as cloning a repository from gitlab and running
datalad

get
for selected / all annexed files.
At the end, one is required to move all data away again. This becomes as easy as
datalad

push
— only transfering new / changed data.

Adapt to HPC storage quotas

In case the storage quota on the HPC file system is not enough, it is easy to
datalad

drop
some of the bulk data. DataLad will make sure that there is always at least one good copy of each file (unless
--
force
is specified) so there is no danger of deleting data by mistake.

Second-tier storages

The former can be combined with second-tier storages (like S3 or separate file systems) in a HPC center. If the fastest HPC file system has usage limits (quota and time), then DataLad can employ local second-tier storages as
additional and temporary
annex storage. During the HPC project, large binary data will be pulled / pushed from / to it. It can transfer in parallel and make use of the higher bandwidths within the HPC network.
At the end, all annexed data can be synchronized back to the primary annex storage of the DataLad repository once.

Coordinate many HPC projects at several HPC centers

If very large computing campaigns need to be distributed over several HPC centers, each granting some resources, then DataLad simplifies the integration of all results — it becomes essentially the same task as managing source code contributions from several developers.

The Slurm batch scheduler

This paper focuses on Slurm

because it is the dominating job scheduler for HPC clusters worldwide. For the problem statement, it can be understood as a synonym for all other HPC job schedulers because the same principles apply. For the implementation there are specifics, still, the presented solution should serve well as a template for corresponding extensions for other job schedulers.

Another interesting scenario would be a paper review process.

4.
Shortcomings of DataLad for HPC

DataLad and the underlying
git
and
git
-
annex
commands
work in HPC environments in principle.
However, there are two critical reasons why DataLad is incompatible with HPC and Slurm.

4.1.
Critical Shortcomings

The fundamental conflict is that
git
repositories expect no more than one
git
command to be active exclusively on a repository at one time. Concurrent
git
commands produce race conditions.
Yet Slurm is supposed to run many jobs concurrently.

While
git
implements some internal locking, it is
not safe
to run concurrent
git
commands in the same repository. In the best case, it would block and waste time. In the worst case it produces race conditions. For example if one
git
command attempts
git

commit

-
a
while another one tries
git

checkout

<
another

branch
>
.

The alternative would be the restriction to one job at a time per repository. This could either mean the serialization of Slurm jobs --- even though every job may be parallel inside, this would be a contradiction of HPC usage. Or it could be separate copies ("clones") of a repository per Slurm job. This is the best possible workaround
8
8

8

https://palma-documentation-wwuit-sys-hpc-2e4c148d26eff3e6aeffc565f2930.zivgitlabpages.uni-muenster.de/Wiki/Datalad/

and the current state of the art when combining DataLad with HPC, see Wagner
et al
.
Wagner et al. 2022
. It will run datalad commands (in their case using containerized execution with
datalad

container
-
run
) inside Slurm jobs which operate on separate clones of the same DataLad repository which were created beforehand.

This causes considerable redundancies and metadata stress for the parallel file system.
Firstly, for
N
jobs scheduled concurrently, i.e. with the potential to run concurrently,
N
separate repository clones are needed. This is not too critical w.r.t. data volumes because the large files are most probably annexed files — every job would only require its subset and simply not
git

annex

get
all the rest. But the management information for all files and versions in the repository is kept in a large number of small files, most of them hidden in the
.
git
/
subdirectory. Their number will be multiplied by
N
which is critical for large
N
. Altogether, this causes a most inconvenient usage patterns (inode usage and metadata overhead) for parallel file systems
Carns et al. 2009
. The "lean clones" idea from
Wagner et al. 2022
tries to relieve it somewhat, but cannot solve it.

4.2.
Critical Inefficiencies

In addition, there are critical inefficiencies if the existing DataLad reproducibility feature is used inside Slurm jobs.

In this case, the DataLad calls need to be part of a Slurm job script.
But
datalad
and the underlying
git
/
git

annex
commands are essentially serial commands — even though
git
-
annex
file transfers may be parallel, all bookkeeping is serial. Thus, there would be multiple serial sections inside a Slurm job which can add up to several minutes for large repositories. This would be acceptable for small-scale jobs but certainly not for large-scale parallel jobs.

4.3.
One step back in reproducibility in HPC?

There is an additional disadvantages when using the workaround from
Wagner et al. 2022
for both, DataLad itself and its aptitude for HPC.

The Slurm job script already contains required information for reproducibility.
Among others, information about
(1) which type of hardware to use (indirectly via the Slurm partition or queue name) and
(2) the parallelism (number of processes / threads, etc.).
Also the (3) memory requirements/limits,
(4) run time limits,
as well as (5) the software environment (modules or Spack packages loaded and their versions).
And finally (6) the job steps (one or multiple commands to be executed in which order and their parameters).
This will certainly be useful to know to re-execute it and it is machine-actionable.

However, there are also limitations. Slurm jobs scripts are by no means portable enough between different HPC centers or even different clusters in the same center. This is due to a lack in standardization for (1) and (5) which also affects (6) when program paths or their options change.

Still, the job script should be tracked as part of the provenance and reproducibility records. This is also in line with DataLad’s YODA guidlines (“YODAs Organigram on Data Analysis”)
Halchenko et al. 2021
.

The current state-of-the-art workaround
Wagner et al. 2022
complicates this because it calls
datalad

run
from within the job script. And it cannot re-use the job script for re-execution — instead it needs a different job script with the
datalad

rerun
command inside.

5.
The DataLad Slurm extension

The presented DataLad Slurm extension is designed to bring the advantages of DataLad for version control and machine-actionable reproducibility to HPC environments. It will solve the aforementioned problems and disadvantages and provide a true HPC solution.

It is available from
https://github.com/knuedd/datalad-slurm
as Open Source Software. It comes as a plug-in to any standard DataLad installation, without the need to replace your DataLad version. Our eventual goal is to make it standard functionality in DataLad or DataLad NEXT
9
9

9

DataLad’s staging area for new functionality
http://docs.datalad.org/projects/next/
.

5.1.
Goals

The goals of the DataLad Slurm extension are to:

•

Allow many Slurm jobs to be scheduled and to run at the same time on the same copy (clone) of a DataLad repository.

•

Track which output files get created/modified by which job and make sure that no jobs with conflicting output specifications get scheduled at the same time.

•

Generate machine-actionable reproducibility records in the
git
log such that every job is reproducible selectively.

•

Avoid running DataLad or
git
commands inside of Slurm jobs. Make the Slurm job script the subject of (re-)execution.

Notice that this will not disallow overlapping changes, where the same output file is modified by multiple concurrent jobs. This ambiguity cannot be resolved and such jobs would cause a race-condition in any case — it would be undefined behavior regardless of DataLad being involved or not.

5.4.
No wildcard output file names

The usage of wildcards or more general regular expressions when specifying outout files or directories would be convenient, either to cover sets of files/directories or when the actual file names are not known before the job but a naming pattern is.

The original
datalad

run
subcommand has the
--
expand
option which will expand the list of outputs (or inputs) with wildcards i.e., the regular expressions are matched against existing files
after the payload command was executed
. It will replace the given parameter by the list of files/directories matching and record this in the
git
log. However, this is disabled by default, where the string containing the regular expression is recorded in the
git
log.
There is no clear superior way since expanding the regular expression better reports what really happened while keeping the original information allows to re-use the regular expression.

For
datalad

slurm
-
schedule
there is no way to reliably expand the regular expressions, because output files from the job may not exist yet when
datalad

slurm
-
schedule
ends. It could partially expand file names which happen to exist already but this would be incomplete and incorrect.

It is also not an option to wait until after
datalad

slurm
-
finish
because the output specifications need to be checked for conflicts during
datalad slurm-schedule
— that is those for the current job but also against all output specifications from the currently scheduled jobs. (Their
datalad

slurm
-
finish
has not been called yet, otherwise their outputs would no longer be protected.)

Thus, wildcard names in the output specification would result in the problem of matching two regular expression for
potential conflicts
which is not feasible. Firstly, it would produce false positives because the regular expressions may conflict even though the actual output file names never would. And secondly, checking if there is a match between all possible expanded names coming from two regular expressions is a very hard problem
Backurs & Indyk 2016
.
Therefore,
datalad

slurm
-
schedule
cannot accept regular expressions as output arguments.
For input arguments
datalad

slurm
-
schedule
follows the same convention as
datalad

run
.

Array jobs

Array jobs are a special Slurm feature to create many similar jobs. A single submit operation via the

The presented approach already relieves this somewhat by using

7.
Summary and Outlook

Summary

This paper presents an extension to DataLad which enables its data versioning and machine-actionable reproducibility features for HPC and the Slurm batch scheduling system. It shows the incompatibilities of the existing approach with HPC, discusses the proposed solution, and evaluates the implementation.

The final solution is suitable for large numbers of jobs and large data repositories. It costs one to two seconds time overhead per job altogether which is slower than pure Slurm jobs but acceptable for the provided benefits. It avoids undue timing or scaling behavior with very many jobs or files on parallel file systems.

The new HPC functionality is fully compatible with the most prevalent distributed version control system
git
as well as familiar knowledge about it … from
.
gitignore
to GUI tools the presented solution integrates seamlessly.

Working with evolving data collections

The presented solution enables a new way of working with large data collections
while they are created
in a very flexible and fully F.A.I.R. manner.

Imagine the training process of DNN surrogate models from results of extensive HPC simulations, for example
Cangi et al. 2024
;
Fiedler et al. 2022
. Assume millions of CPUh are required to produce training data with standard simulation programs over the course of several months.
The DNN training will start early with a subset of the HPC simulation results to check feasibility and to optimize the hyperparameters. Then successive versions of the DNN model will be created with the moving subsets of already finished HPC simulations.

If the HPC results are handled in DataLad Slurm jobs, then they can be committed to the data repository in batches as they finish. In case a few HPC results turn out as faulty later, they can be removed or replaced. At every time, the current subset of the data collection can be identified by a git commit hash. This commit hash is sufficient provenance information for the DNN model to identify precisely which training data set was used. If needed the exact subset can be restored from the data repository with a granularity of every single commit, i.e. every single HPC job. Furthermore, this involves no redundant storage of datasets. All is possible with the widely adopted git mindset.

Outlook

We see three steps for future work.
Firstly, the
datalad

slurm
-
reschedule
functionality for array jobs should be extended so that individual jobs can be re-scheduled.
Secondly, the
--
alt
-
dir
functionality should be compared to the
git

worktree
12
12

12

https://git-scm.com/docs/git-worktree
feature. A
linked worktree
is basically a separate copy of a branch in an external path. If this behaves well on a parallel file system, then this should become another way to keep the main repository in a local file system while Slurm jobs can still access their required files on a parallel file system. This is less selective but may be more efficient when almost all files will be required for jobs.

Thirdly, the integration into DataLad NEXT and eventually standard DataLad is the most important mid-term goal.

The job execution time also plays into the total time, even though the jobs will run independently in parallel. Each test jobs runs for less than a minute. Otherwise, Slurm would reject new jobs by a user with too many pending jobs. Therefore, the total time of the test script depends on the total load of the HPC cluster. Artifact Analysis (incl. Outputs)

The output of this artifact is the example visualization of the "octopus merge". This reflects the parallel execution of the parallel Slurm jobs because no job is merged earlier or later than its counterparts.
It also reflects that the potentially concurrent jobs cannot depend on each other for inputs or outputs.

If the jobs were merged one after the other or simply committed to the current branch in an arbitrary order it would show a meaningless sequence in the git log. However, the "octopus merge" is only a cosmetic difference as long as the order of the commits is not mistaken to be relevant.
