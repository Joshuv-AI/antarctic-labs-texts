PyMigTool : a tool for end-to-end Python library migration
Mohayeminul Islam, Ajay Kumar Jha, May Mahmoud, Sarah Nadi

Abstract
Library migration is the process of replacing a library with a similar one in a software project. Manual library migration is time consuming and error prone, as it requires developers to understand the Application Programming Interfaces (API) of both libraries, map equivalent APIs, and perform the necessary code transformations. Due to the difficulty of the library migration process, most of the existing automated techniques and tooling stop at the API mapping stage or support a limited set of libraries and code transformations. In this paper, we develop an end-to-end solution that can automatically migrate code between any arbitrary pair of Python libraries that provide similar functionality. Due to the promising capabilities of Large Language Models (LLMs) in code generation and transformation, we use LLMs as the primary engine for migration. Before building the tool, we first study the capabilities of LLMs for library migration on a benchmark of 321 real-world library migrations. We find that LLMs can effectively perform library migration, but some post-processing steps can further improve the performance. Based on this, we develop PyMigTool , a command line application that combines the power of LLMs, static analysis, and dynamic analysis to provide accurate library migration. We evaluate PyMigTool on 717 real-world Python applications that are not from our benchmark. We find that PyMigTool can migrate 32% of the migrations with complete correctness. Of the remaining migrations, only 14% of the migration-related changes are left for developers to fix for more than half of the projects.

Introduction

Library migration
is the process of replacing a library with an alternative one in a software project.
The process involves identifying the library usage in the codebase, finding the corresponding Application Programming Interfaces (APIs) in the new library, and replacing the old API usage with the new API usage.
This can be tedious and error-prone, especially when the library is extensively used in a large codebase
kula2018developers
.

Researchers have proposed various techniques to automate the library migration processes. Most of these techniques, however, are limited to only finding the analogous APIs (
API mapping
)
teyton2013automatic
;
alrubaye2018automating
;
alrubaye2019use
;
miningAnalogicalAPIs
;
zhang2020deep
;
di2025deepmig
, but do not replace the old API usage in the codebase with the new one (
transformation
).
To find analogous APIs, some of these techniques mine existing migrations
teyton2013automatic
;
alrubaye2018automating
;
alrubaye2019use
while others use machine learning models
miningAnalogicalAPIs
;
di2025deepmig
and natural language processing techniques
ni2021soar
.
To the best of our knowledge, there are two techniques that perform transformation
ni2021soar
;
nikolov2025google
but both techniques evaluate their approaches on a small set of library pairs without providing a tool that can be used in practice.

In recent years, Large Language Models (LLMs) have shown that they can be effective in various software engineering tasks
ozkaya2023application
;
fan2023large
;
wang2024software
,
including the necessary upstream tasks for library migration, such as code generation
nguyen2022empirical
;
peng2023impact
;
murali2023codecompose
, code comprehension
nam2024using
, and code transformation
wei2023copiloting
;
xia2023automated
;
zhou2023hybrid
.
This suggests that LLMs may be capable of performing library migration.

In this paper, we leverage LLMs to explore and address the challenges of automating library migration in two phases.
First, we conduct an experiment using an existing library migration benchmark,
PyMigBench

pymigbench
, to determine the capability and challenges of using LLMs for library migration.
We find that LLMs are generally capable of performing migration; however, some post processing can further improve the migration results.
Second, based on our findings in first phase, we build a CLI tool,
PyMigTool
, that automates the full library migration process by combining the power of LLMs with post processing using static and dynamic program analysis.
We run an extensive evaluation of
PyMigTool
on a set of 717 new, simulated migrations.

Phase one – Explore LLMs:

In this phase, we investigate the capabilities and challenges of using LLMs for library migration.
We use LLama 3.1, GPT-4o mini, and GPT-4o to perform 321 migrations from
PyMigBench
.
We then measure the correctness of the migrations by comparing the LLM’s migrations with the original developer’s migrations.
We find that the three LLMs can correctly migrate 26%, 49%, and 57% of the migrations respectively.
Overall, we find that LLMs are capable of library migration, and as expected, the more powerful LLM (GPT-4o) performs better than the less powerful LLMs (LLama 3.1 and GPT-4o mini).
We also identify two major challenges that make solely relying on LLMs in a practical tool ineffecive:

(1)

We provide the LLM with only code files that directly use the source library. However, for a given project, there may be other files that depend on the migrated code and also require changes during the migration.

(2)

All LLMs often return only part of the code, skipping parts of the code that do not require migration.

These limitations, however, can be addressed by post-processing the LLM’s results.
We use these insights to improve the migration process in the next phase.

Phase two – Build
PyMigTool
:

In this phase, we build
PyMigTool
, a Command Line Interface (CLI) that automates the full library migration process using LLMs and post processing using static and dynamic program analysis.

PyMigTool
takes as 5 inputs from the user

(1)

A project that requires migration, with an existing test suite with high coverage.

(2)

A requirements file that lists the dependencies of the project.

(3)

A source library that is used in the project.

(4)

A target library and its version that the user wants to migrate to.

(5)

Name of an LLM that will be used for the migration.

By building a dynamic call graph,
PyMigTool
identifies all files that require migration and sends those to the LLM.

PyMigTool
then verifies the results of the migration by comparing the test results before and after migration.
If any previously passing tests now fail,
PyMigTool
performs a Post-processing round where it checks if the LLM skipped any code and merges it back.
It also detects if any of functions were made async during the migration, and if so, it finds other parts of the project that uses these functions and makes them async as well.
Finally, it runs the unit tests again and saves the results

We evaluate
PyMigTool
using a new purely test-based evaluation setup, as opposed to the benchmark based evaluation we did in the first phase.
This allows us to evaluate new migrations without the need for a ground truth developer migration.
We evaluate
PyMigTool
on a set of 717
simulated
migrations in 175 unique projects.
By simulated migrations, we mean that this migration did not exist in the project’s history; instead, we find source libraries used in a project and migrate the project to an analogous target library.
We ensure that the projects we choose have high test coverage, so that the evaluation is reliable.

We demonstrate twi different evaluation setups.
First, we measure how well
PyMigTool
perform as it is on the simulated migrations, without any manual intervention.
While the best case scenario is that
PyMigTool
can migrate the project without any issues, a more practical expectation is that
PyMigTool
would do most of the task correctly, but there are some parts that require manual intervention.
Therefore, in a second evaluation, we measure how much manual work can fix the incorrect migrations.
We randomly select a subset of 43 diverse migrations that were not fully correct, and we manually fix them.

We find that
PyMigTool
was able to successfully migrate 32% migrations without any manual intervention.
We manually fix 43 of the remaining 484 migrations, and were able to fix 21 (49%) of them. In terms of modified lines of code, the manual work is only 14% of the total migration-related changes.

To summarize, the contributions of this paper are:

1.

We conduct an initial detailed experiment to explore the use of LLMs for library migration on an existing migration benchmark that provides us a ground truth of previously performed developer migrations.

2.

Based on the insights gained from our initial experiment, we build a CLI tool,
PyMigTool
, that automates the full library migration process using a combination of LLMs and post processing using static and dynamic program analysis.

3.

We run an extensive test-based evaluation of
PyMigTool
on a set of 717 simulated migrations, and show that it works well with no or minimal manual editing for a diverse set of library pairs.

2.2

is a dataset of real-world Python library migrations

We use the latest available version, version 2.2.5

Phase one: Exploring the capabilities of LLMs for Python library migration

We use three off-the-shelf LLMs – LLama 3.1
llamapaper
, GPT-4o mini
openaimodels
, and GPT-4o
openaimodels
– to perform migrations on the
PyMigBench
dataset.
We refer to these models as LLama, Mini, and 4o in the rest of the paper, respectively.
We evaluate the correctness of the migrations in two ways. First, we compare the LLM-migrated code with the developer-migrated code in
PyMigBench
and report correctness at two granularity levels: the full migration and the individual code changes.
We use
PyMigTax
to identify which types of code changes the LLMs can/cannot handle.
Second, for the subset of migrations with available unit tests, we run the available tests to assess the correctness of the migrated code.

We answer the following research questions in this phase:

RQ-A1

How similar are the LLM migrations to the benchmark migrations?

We consider the code changes stored in
PyMigBench
as the ground truth. We automatically check if the LLM was able to correctly perform all expected changes, while accounting for refactoring and alternative correct changes through manual review.

RQ-A2

How many migrations pass unit tests?

To evaluate run-time correctness of the migrated code, we use a second evaluation strategy where we run any available unit tests.

Data preparation

At the time of conducting this experiment, two repositories from

We clone the remaining repositories containing 319 migrations.
For each migration commit, we use PyDriller

We use Python’s built-in

3.1.3
Migration

For each file having code changes, we use the LLM prompt template in
1
to migrate the code.
The prompt is designed to ensure that the LLM performs focused, controlled migrations while maintaining transparency.
By asking the LLM to explain its changes, we ensure that the LLM justifies its modifications, which can be useful for a human evaluator reviewing the migration.
The prompt also aims to restrict the LLM from making unrelated modifications such that we remain focused on the task of library migration.

Since LLMs are non-deterministic
atil2024llmstabilitydetailedanalysis
, we use a temperature of 0 and run each migration 10 times for each model.
We calculate the difference between the runs to understand the variability in the generated code.
We use git-diff

to compute a diff between each pair of the 10 runs and normalize the number of different lines by dividing it by the total number of lines in File
pre

We find that on average, two runs on the same file are only 6.6%, 4.0% and 4.8% different for LLama, Mini, and 4o, respectively.
Given this low variability and the high effort involved in manual validation, we randomly select one run for each model to evaluate the LLMs’ results.
Our artifact contains the LLM’s migrations for all 10 runs.

3.3
RQ-A2
How many migrations pass unit tests?

We now assess the same LLM
PyMigBench
migrations from RQ1 but using the unit tests available in the corresponding repositories.
A test-based evaluation that runs the code ensures that the migration achieves the expected behavior.
Note that we should not expect that an LLM migration improves the rate of passing tests; a successful migration means that each test that previously passed on code
dev
must still pass on code
llm
.
We now explain our evaluation set up.

3.3.1
Preparing the code

We make a copy of the repository after the developers’ migration (code
dev
).
We then make another copy of developer’s migration, but replace all File
dev
with File
llm
; we refer to this as code
llm
.
The idea is that code
llm
is basically the version of code
dev
where the LLM did the migration on behalf of the developer.

3.3.2
Setting up the virtual environment

To set up a virtual environment, we need to identify the Python version used in the client repository.
If this information is available in the
setup.py
file, we use that version.
Otherwise, we resolve the version based on the migration commit date as follows.
We first identify the release dates of all minor versions of Python (3.6, 3.7 etc).
Then, we find the latest release date that is before the migration commit date.
This is the latest Python version that was available at the time of the migration; we use this version to create the virtual environment.
Next, we install the code dependencies using
pyproject.toml
,
setup.py
and requirements files.
In cases where specific dependency versions are not specified in those files, we look up the version history of the dependency on PyPI and install the latest version available at the migration commit date, similar to how we resolve the Python version. This ensures that the dependencies are compatible with the code at the time of migration.

3.3.3
Running the tests and coverage

Once the virtual environment is ready, we run all the unit tests while measuring coverage in the repository on code
dev
. If the run has errors, we read the error log and try to fix the errors, and run the tests again.
We maintain a configuration file where we record any project-specific configurations or commands we used. We include this information in our artifact.

We find that 218 out of the 314 migrations have at least one test.
Among these, 172 migrations had unresolvable errors. The failures are primarily due to missing dependencies, specially for older projects.
The remaining 46 migrations have tests that we are able to successfully run on code
dev
.

However, for the tests to be useful to validate migration, they must cover the migration-related code changes.
Using the coverage report, we find that only 27 migrations have at least one test that covers the code changes, and among them, 25 migrations have at least one test that passes on code
dev
.
We run the entire test suite on code
llm
for these 25 migrations for each model using the same randomly selected LLM run used in
RQ-A1
.

3.3.4
Determining migration status

We compare the test results between code
dev
and code
llm
and assign the following statuses to the migrations:

•

Correct
: All passing tests in code
dev
also pass in code
llm
.

•

Partially correct
: Some of the tests that pass in code
dev
pass in code
llm
, but the others fail or raise run-time errors.

•

Incorrect
: None of the passing tests in code
dev
pass in code
llm
; they all fail or raise run-time errors.

3.4
Implications and discussion

3.4.1
Are LLMs suitable for library migration?

We look into some specific examples to understand the promises and limitations of LLMs for library migration.

3.4.1.1
The good

We start with the promising side of using LLMs for library migration.
In addition to the high overall correctness of individual code changes and migrations in RQ1,
our evaluation reveals that the evaluated LLMs can migrate code changes that were traditionally known as difficult to migrate
xu2019meditor
.
We discuss some examples.

As shown in RQ2, LLama, Mini, and 4o successfully migrated 70%, 79%, and 84% of the higher cardinality code changes, respectively, which the literature always viewed as complex migrations

.

3.4.1.2
The Bad

We also analyze cases where the LLMs did not correctly migrate the code and present notable observations.

Failing to handle argument transformation

Figure 5
shows an example where the source library
retrying

libretrying
expects the time arguments in milliseconds, while the target library
tenacity

libtenacity
expects them in seconds.
The dataset includes 28 instances of this transformation, and all three LLMs failed to handle it in most cases, except for 4o, which handled three instances correctly, while the other two models correctly handled one instance each.
This suggests that while the LLMs can map parameters, differences in expected format or units may not be properly managed.

Figure 5
:
Mini filing in argument transformation.

Replacing exception type

We find cases where the LLM replaces generic exception types with specific ones, which can potentially fail to catch the same exceptions as the original code.
This occurs in both migration-related and non-migration-related changes.
For example, the LLM replaces an original
Exception
with
ValueError
.
While using more specific exceptions is considered good practice
cacho2014does
, it does change the behavior of the code.
Since modern development tools are often equipped to suggest better exception handling, it may be safer for an LLM-based migration tool to avoid changing existing exception types during a migration.

3.4.1.3
The ugly

We also observe the following problematic LLM behavior.

Extra changes
LLMs are known for not always following the instructions provided in the prompt
ye2023cognitive
.
Despite our prompt explicitly asking the LLMs to avoid any refactoring or non-migration changes, we find cases where an LLM, particularly LLama, completely removes parts of the code that do not include any source APIs.
We speculate that this behavior may stem from the LLM attempting to optimize output size due to token limitations.
Silently deleting code can be dangerous for the overall functionality of the system, and led to test failures in RQ2 for many cases.

Similarly, the LLMs sometimes refactor code that is not related to the migration, adopting a different style.
While these improvements can be beneficial, they are unrelated to the migration task at hand.
Future work could explore the use of an interactive IDE plugin that confirms the code changes before applying them, potentially allowing the developer to directly edit the changes.

While less “dangerous”, we also find that the LLMs remove code comments and docstrings from the source code, even though the comments remain relevant after migration.

Large file handling

We observe that large files pose a challenge to LLama, given its smaller context size.
Additionally, we observe that even the other two models often migrate an initial part of a large file but then incorrectly state that the remaining part does not require any changes.

3.4.2
Differences in evaluation setup

While the scope of
RQ-A2
is limited due to the availability of the tests, we do find cases where the migrations are correct in
RQ-A1
but incorrect in
RQ-A2
, or vice versa.
To better understand these discrepancies, we manually inspect migrations with different results and provide some examples.

3.4.2.1
Library version compatibility

When evaluating
RQ-A1
, we mark a code change to be correct if it is correct as of the latest version of the library.
However, in
RQ-A2
, we install the version the developers specified, and if it is not available, we resolve the library based on the migration commit date (see
Section 3.3
).
Since we do not ask for a specific version number in the prompt, we notice that the LLMs usually pick APIs from the latest version of the target library.
In some cases, this version discrepancy led to runtime errors when running tests in LLM’s code, which we report as incorrect in
RQ-A2
.
Note that we consider version numbers moving forward when designing
PyMigTool
in
Section 4
.

Developer doing non-refactoring changes

Recall that in

We count this as a correct migration in

Overall, the discrepancies show that both evaluation techniques provide different perspectives on the migration correctness.

3.4.3
Understanding the cost of LLM-based migration

The 314 migrations we use in our experiments involve a total of 258,198 lines of code, or 258.0 KLOC.
The 10 runs per model makes it 2582.0 KLOC per model.
The total cost of running our experiments was approximately $15 for GPT-4o mini and $420 for GPT-4o, which equates to $0.01 and $0.16 per KLOC, respectively.
OpenAI has since reduced prices, so current costs would be lower.
LLama 3.1 is free and open-source, though we used a pro subscription of

While library migration is an infrequent task in a project’s lifetime, it requires significant developer effort when it happens.
The cost of a developer’s time can easily exceed the cost of using an LLM, even GPT-4o, which can justify the cost of LLM-based tooling.

3.5.1
Internal validity

Our evaluation involves two manual steps: validating correctness of code changes and labeling a non-migration related change as refactoring or non-refactoring.
Manual activities are inherently subjective and may contain errors.
We minimize this by having two authors independently perform the manual activities and resolving disagreements through discussion.

3.5.2
Construct validity

In
RQ-A1
, we analyze the code change categories based on Change
dev
, not on Change
llm
.
The categories can differ if the LLM produces a different code change than the developer.
Categorizing the LLM changes would require additional manual effort following the our previous work in
PyMigTax

pymigtax
, which is beyond the scope of this work.
That said, our observation is that the code/API differences in most cases are minor, and would not yield in a different
PyMigTax
category.

Tests passing may not always guarantee migration correctness (e.g., the tests do not cover certain edge cases).
We mitigate this, to the extent possible, by selecting repositories with high test coverage in
and ensuring that the tests cover the source API usages.

3.5.3
External validity

We use three off the shelf LLMs.
While using an LLM specifically tuned for the library migration task could potentially yield better results, the goal of this initial empirical study is not to develop a migration tool, but to understand the challenges and opportunities of using LLMs for library migration.
Our results may be viewed as a lower bound of the performance of potentially more specialized models.

The libraries included in
PyMigBench
are all old-enough libraries where the LLMs are likely familiar with their APIs and API usage.
This familiarity with APIs and API usage is precisely our hope when using LLMs for migration.
However, being familiar with the APIs alone does not always guarantee being able to map them to each other or apply the right transformations on all code bases, which is why our evaluation is necessary.
For newer libraries, additional information, e.g., API documentation, may be needed to guide the LLM in the migration process.
This can be an interesting avenue for future work.

4
Phase two:
PyMigTool
: a tool for end-to-end Python library migration

In
Section 3
, we showed that LLMs can perform library migrations. However, we see two major challenges that make solely relying on LLMs in a practical tool ineffective:

(1)

We provide the LLM with only code files that directly use the source library. However, for a given project, there may be other files that depend on the migrated code and also require changes during the migration.

(2)

All LLMs often return only part of the code, skipping parts of the code that do not require migration.

In this phase, we build and evaluate
PyMigTool
, a CLI tool that automates the full library migration process for a full project by combining the power of LLMs with pre and post processing to address the above challenges.

PyMigTool
first prepares the project that needs migration by setting up a virtual environment.
It then runs an LLM to migrate the code, and finally performs post processing to improve the migration results.
We run an extensive evaluation of
PyMigTool
on a set of 717 new, simulated migrations.
Overall,
PyMigTool
is able to successfully migrate 32% of the migrations without any manual intervention.
For a sample of the remaining not-fully-successful migrations, we find that a median of only 14% of the code lines in the project require manual changes to complete the migration, while the rest of the code is correctly migrated by
PyMigTool
.

4.1
Building
PyMigTool

PyMigTool
takes as input the following:

(1)

the path to a python project where the migration should happen,

(2)

the source library name,

(3)

the target library name and version,

(4)

the python version in which the code should run,

(5)

paths to one or more requirements files,

(6)

and an LLM to use for the migration.

A key criteria for the input project is that it contains tests with high coverage,
as
PyMigTool
uses the tests to identify the source library usage as well as to verify the migration.
While the migration will run regardless of the test coverage, migration results without test validation may not be as reliable.

PyMigTool
works in three main steps:
Preparation round
,
LLM migration round
, and
Post-processing round
.
The preparation round sets up a virtual environment using the requirements files, and runs the tests to get the baseline results.
The LLM migration round migrates the project to use the target library instead of the source library using the LLM the user specified.
Finally, if the LLM migration is not fully successful,
PyMigTool
performs some non-LLM post processing steps to improve the migration results.

4.1.1
Preparation round

In the preparation round,
PyMigTool
first creates a virtual environment for the provided python version using the command
python -m venv .venv
, and then installs the required libraries using the command
pip install -r <requirements-file-path>
for each of the requirements file.
It then installs the target library at the provided version using the
pip install
command.

PyMigTool
requires some additional packages, such as
pytest
,
pytest-cov
, which it also installs during this step.

Once the environment is set up,
PyMigTool
runs the tests using the command
python -m pytest
on the project and saves the test report.
We refer to this version of the test report as
TestReport
premig
, which is used as the baseline for the migration.

4.1.2
LLM migration round

In our preliminary exploration of LLMs (
Section 3
), we use
PyMigBench
where the files that require migration were already known.
However, in a real-world scenario for a full project, we do not know which files require migration.
Therefore,
PyMigTool
first identifies the files that require migration, and then uses the LLM to migrate these files.

4.1.2.1
Identifying files that require migration

PyMigTool
migrates one whole file at a time, therefore, it is sufficient to identify which files use the source library, without necessarily identifying the exact source library usage within these files.

PyMigTool
combines two techniques to identify the files that require migration: it uses static analysis to identify import statements and uses dynamic analysis to generate a run-time-generated call graph of the project using profiling data.

considers that the file uses the library, and thus require migration.
In Python, a library may be imported using a name different than the library name.
For example, the library
PyYAML
can be installed using the command
pip install pyyaml
, but it has to be imported as
import yaml
.
The former,
pyyaml
, is the library name, and the latter,
yaml
, is the import name.
Furthermore, a library can have more than one import names.

PyMigTool
only takes the source library name as input, therefore, it needs to find the import names of the source library in the project.
To do this,
PyMigTool
uses the
Johnnydep
tool
libjohnnydep
, which extracts the import names from the wheel file of the library.

Next,
PyMigTool
uses the
ast
module to parse each Python file in the project and identify the import statements.
It then compares the imported modules with the import names of the source library to identify the source library usage in the project.

In the example in
Figure 7
, the file
main.py
directly imports the library
geolib
, thus
PyMigTool
will identify this file as requiring migration.
However, the file
serialize.py
does not import the library, therefore, will not be identified as requiring migration by the static analysis.

Detecting source library calls:

In
Figure 7
, the file
serialize.py
does not import the library
geolib
,
but both the
main.py
and
serialize_test.py
pass the
geolib.Square
object to the
serialize.to_dict()
function.
That means when the code runs, the
serialize.py
file will use the
geolib
library, even though it does not import it.
This shows that, identifying the import statements alone is not sufficient to identify all of the source library usage in the project.
Accordingly,
PyMigTool
uses a run-time call graph to identify further source library usage in the project.

PyMigTool
runs the tests in the project with profiling using the
pprofile
package
libpprofile
.
The profiling data includes all the calls made during the test execution, and generates a report in the
CallGrind
format
doccallgrind
.
A call information includes the caller function and the callee function, as well as the line number where the call happened.
A function is identified by the path of the file in which the function is defined, and the qualified name which is unique within the file.

PyMigTool
uses this data to build a call graph of the project.

To know if a file requires migration,
PyMigTool
needs to determine whether any part of the file directly calls a source library function.
A function can be defined in one of the three places: in python built-in modules, in the project, or in a third-party library.
A Python system module file path is enclosed within angle brackets in the profile report; for example,
<frozen os>
indicates that the function is defined in the built-in
os
module.
If a function is defined in a file under the project path (which
PyMigTool
takes as input), it considers this function to be in the project.

PyMigTool
also knows the path of the virtual environment where the third-party libraries are installed.
Python virtual environments have a specific directory structure that
PyMigTool
leverages.
For example, in Windows systems, the import name
yaml
would be in the
<venv_path>/Lib/site-packages/yaml
directory.
Therefore, if a call is to a function that is defined in a file in this directory,
PyMigTool
can conclude that the function belongs to the
yaml
import name, i.e.
, the pyyaml library.
In the call graph, we store the
owner
of each function, which can be
project
,
system
, or the import name of the library.

Given this constructed call graph,
PyMigTool
iterates over each call.
If the caller is owned by the project and the callee is owned by the source library, then the file that contains the caller function requires migration and
PyMigTool
adds it to the list of files that will be passed to the LLM.

Overall, in
Figure 7
,
PyMigTool
will identify the file
main.py
requiring migration using static analysis, and
serialize.py
requiring migration using dynamic analysis.

4.1.3
Post-processing round

PyMigTool
performs two post-processing steps we describe below.

4.1.3.1
Merge skipped code

During the the preliminary experiments (
Section 3
), we found that it is common for the LLMs to skip some parts of the code in the response, especially if those parts do not require migration, despite being instructed to return the full migrated code (see
paragraph 3.4.1.3
).
In this post-processing step,
PyMigTool
identifies such skipped code, and merges it with the migrated code.

For each file that was migrated in the LLM migration round,

PyMigTool
generates a diff between the original file and the migrated file using python’s
difflib
module.
Then it attempts to detect which of the chunks were entirely removed from the original file.
We make the following assumption to identify skipped code:

1.

A skipped code must be mostly removal of lines. Because if the hunk has similar amount of additions and removals, it is likely that the hunk is replacing some code with other code, likely performing migration.

2.

The skipped code should not use source library APIs, because this makes the hunk migration-related otherwise.

3.

A skipped code should not be too small. This assumption avoids incorrectly considering small migration-related removals as skipped code.

We find the below specific baseline values for the above assumptions by trial-and-error to find a good balance between incorrectly merging migration related removals and incorrectly not merging skipped code:

•

Small (0-9 lines of removals): this hunk is not considered skipped irrespective of the number of additions.

•

Medium (10-19 lines of removals): if this hunk has at least one addition of line or use any source library APIs, it is not considered skipped.

•

Large (20 or more lines of removals): if this hunk has less than 90% of removed lines compared to total added+removed lines, it is not considered skipped.

The hunks contain the line numbers in the previous and new version of the file.
Using the line numbers,
PyMigTool
inserts the removed lines in the migrated file, starting with the last removed hunk and going to the first removed hunk.
The reverse order is important because inserting the lines would otherwise change the line numbers of the hunks that are inserted later.
After inserting the skipped code,
PyMigTool
runs the tests again and generates a new test report, which we refer to as
TestReport
merge
.

4.1.3.2

In Python, a call to an asynchronous function must be
awaited

, preceded by the
await
keyword.
Again, if a function call is awaited, the caller function must also be made asynchronous, i.e.
, it must be preceded by the
async
keyword.

When there is a migration from a synchronous library to an asynchronous library, some functions in the migrated code may become asynchronous, which requires their transitive calls to be awaited, and transitive callers to be made asynchronous as well.
In this step,
PyMigTool
identifies the functions that were made asynchronous by the LLM (
asynced
functions),
then find all other functions that needs to be made asynchronous (
to-async
functions) and all calls that need to be made await (
to-await
calls), and applies the changes to the project.
Additionally,
PyMigTool
also decorates the corresponding test functions with the
pytest.mark.asyncio
decorator, and installs the
pytest-asyncio
package, which are required to correctly run asynchronous tests.

Identifying asynced functions

For a given file that was migrated in the LLM migration round (
Section 4.1.2
),
PyMigTool
builds a abstract syntax tree (AST) of the code before migration and after migration.

PyMigTool
then finds the asynchronous function definitions in the code after migration.
For each such function,
PyMigTool
finds functions with the same qualified name in the AST of the code before migration.
If such a function exists in the AST before migration, but was not asynchronous, we consider the function as
asynced
.
For example, in
Figure 8
, the function
fetch_data
is asynced, because it was synchronous before migration, but is asynchronous after migration.
If a corresponding function is not found at all, it means that the function is newly added due to the migration, and we do not consider it as asynced, because it is introduced by the LLM and does not have callers in other parts of the project.

Identifying to-async functions and to-await calls

If a function
a
calls a function
b
, and
b
calls a function
c
, then
a
is said to transitively call
b
and
c
.
For a given asynced function,
PyMigTool
finds all its transitive callers using the call graph, and marks them as
to-async
.
For example, in
Figure 8
, the function
fetch_data
is asynced, and it is called by the function
test_fetch_data
, therefore,
PyMigTool
marks
test_fetch_data
as to-async.
It then again uses the call graph to find all call sites of the asynced and to-async functions, and marks them as
to-await
.
For example, in
Figure 8
, the call to
fetch_data
in the function
test_fetch_data
is marked as to-await, because it is a call to an asynced function.
The to-async functions need the
async
keyword to be added to their signature, and the to-await calls need the
await
keyword to be added to them.

Applying the changes

PyMigTool
uses LibCST
liblibcst
to parse the code, search code elements to be modified, and applies the following changes:

1.

If a function definition is marked to-async, and it is not already asynchronous, then
PyMigTool
adds the
async
keyword to the function definition, for example the function definition
test_fetch_data
in
Figure 8
.

2.

If a call is marked to-await, and it is already not awaited,
PyMigTool
adds the
await
keyword to the call, for example the call to
fetch_data
in
test_fetch_data
in
Figure 8
.

3.

If a test function is asynced or is marked to-async,
PyMigTool
decorates the test function with
pytest.mark.asyncio
decorator, and installs the
pytest-asyncio
package to the virtual environment, which is required to run asynchronous tests. For example, in
Figure 8
, the function
test_fetch_data
is decorated with
pytest.mark.asyncio
.

After finishing the async transfomations,
PyMigTool
runs the tests again and generates a new test report, which we refer to as
TestReport
async
.

4.2
Evaluating
PyMigTool

We evaluate
PyMigTool
on a set of 717
simulated
migrations in 175 unique projects.
By simulated migrations, we mean that this migration did not exist in the project’s history; instead, we find source libraries used in a project and migrate the project to an analogous target library.
We ensure that the projects we choose have high test coverage, so that the evaluation is reliable.
We run each migration just one time, unlike in
Section 3
, because we found in that section that the LLM does not produce highly divergent migration results when run multiple times on the code.
The setup we use is same as the setup in
(
), where we evaluate the LLMs on a set of migrations that were not used in training the LLMs.

We aim to answer the following research questions:

RQ-B1

How many migrations can
PyMigTool
perform correctly?
We measure how well
PyMigTool
performs on the simulated migrations without any manual intervention.

RQ-B2

How much manual effort is required to complete the incomplete migrations?
While the best case scenario is that
PyMigTool
can migrate the project without any issues, a more practical expectation is that
PyMigTool
would do most of the task correctly, but there are some parts that require manual intervention.

4.2.1
Data collection

4.2.1.1
Selecting repositories

We want to find repositories that are well covered by unit tests, so that we can automatically evaluate the migration correctness using the tests.
We start by downloading a list of 95,472 Python GitHub repository metadata using SEART
seart
service.
We use the filters to select Python repositories that have at least one commit after January 1, 2024 to discard repositories that are not actively maintained.
We also filter out repositories with less than 100 lines of code to ensure that the repositories have some code to migrate.

For each repository, SEART metadata includes many details, including the repository name, the latest commit, the lines of code in the repository and repository size in KB.
Before cloning the repository, we use some heuristics to filter out the repositories that may not be suitable for evaluation.

i.

Large repositories:
Extra-large repositories would take too long to clone and analyze, so we filter out 30,563 repositories larger than 10MB, leaving us with 64,909 repositories.

ii.

No requirements files:
We use requirements files to build the virtual environment. We filter out 39,916 repositories that do not have a
requirements.txt
file in the root directory, leaving us with 24,993 repositories. We check this by making an HTTP head request to the GitHub raw file URL. If the response code is not 200, we conclude that the file does not exist.

iii.

Filtering by test files:
Python test file names usually contain the term
test
. We use GitHub code search API
4
4

4

GitHub code search API:
https://docs.github.com/en/rest/search/search#search-code
to query files that contains the term
test
, and filter out a repository if it does not have any such files. We filter out 12,558 repositories that do not have any test files, leaving us with 12,435 repositories.

When a repository passes the above heuristics, we clone it and attempt to run the tests.
In this process, we filter out the repositories with the following criteria:

iv.

Could not run tests:
We attempt to setup a virtual environment for the repository using the requirements file and run the tests following
Section 3.3.2
.
Due to various repository specific requirements; e.g.
, python version, system requirements, incomplete requirements file; we are often unable to run the tests.
We filter out 10,104 repositories that we could not run the tests for, leaving us with 2,314 repositories.

v.

Low passing rate:
We filter out the repositories that have less than 90% of the tests passing, which filters out 957 repositories, leaving us with 1,357 repositories.

vi.

Low coverage:
We filter out repositories that have less than 80% line coverage by the tests, which filters out 557 repositories, leaving us with 800 repositories.

vii.

Tests require user interaction:
Some repositories require user interaction for the test to continue. For example, one repository requires a user to select an application to run a file. We identify 2 repositories that require manual intervention and exclude them, leaving us with 798 repositories, which we use for evaluation.
We store the commit SHA for the version of the repository we use to ensure reproducibility.

Selecting library pairs

We collect the dependencies of the 798 selected repositories by parsing their requirements files.
These dependent libraries are the potential source libraries.
Then for each source library, we find a list of candidate analogous libraries using GPT 4o mini, and then manually we manually verify them.
We describe the process below.

Collecting source libraries

For each repository, we parse the requirements file to find the dependencies.
This gives us an initial list of 1,421 unique source libraries.
We then look up the library metadata on libraries.io
libraries.io
.
We exclude 12 libraries that are not found on libraries.io, leaving us with 1,409 libraries.
To ensure that the libraries are commonly known, we filter out 602 libraries that have less than 100 dependents, and filter out 2 libraries that do not have a description, leaving us with 805 potential source libraries.

4.2.1.2
Collecting migrations

From the above process, we have a list of 798 repositories and 60 analogous library pairs.
For each of these repositories, we now find which of the source libraries from the analogous library pairs are used in the repository.
To find actual usage, not just listing in the requirements file, we parse the source code of the repository and look for import statements that use the source libraries.
We find that 175 repositories use at least one of the source libraries.
Each source library can have one or more analogous target libraries.
A repository, a commit, a source library and a target library thus form a
unique migration instance
.
We get a total of 717 unique migration instances, which is the product of 175 repositories and 48 library pairs.
These numbers are less than the 798 repositories and 60 analogous library pairs we started with, because we find many instances where a repository declares a dependency on a library, but does not actually use it in the code.

To summarize, our evaluation is based on 717 migrations between 48 library pairs in 175 repositories.
The 48 library pairs include 24 unique source libraries and 37 unique target libraries, and 55 unique libraries in total.

Number of migrations applied to is the number of migrations where this step was applicable to and got applied.
For example, not all migrations require merging unchanged code or applying async transformations.
Number of migrations improved shows the number of migrations where correctness improved in comparison to the previous step.
Average improvement in correctness is calculated for those migrations where correctness improved.

Figure 9
also shows the distribution of correctness of migrations after the each migration step.

All three violins have concentrated values at 0% and 100%, indicating that most of the migrations either pass all tests or fail all tests.
From this figure and
Table 7
, we see that the median correctness of migration increased from 65% in the LLM migration round to 80% after the merge skipped code, and further increased to 86% after the infer async transformation.
The distributions show that after post-processing, there are fewer migration with zero or low correctness, and more migrations with high correctness.
This indicates that the post-processing steps are effective in improving the correctness of migrations.

Note that the post processing steps are applied only when the migrations are not fully correct, and when that specific post processing step is applicable.
For example, merge skipped code is applied to 260 migrations, among which 88 (34%) migrations have improved correctness with an average improvement of 46% per migration.
On the other hand, infer async transformation is applied to 129 migrations, among which 45 (35%) migrations have improved correctness with an average improvement of 65% per migration.

4.2.4
RQ-B2
: How much manual effort is required to complete the incomplete migrations?

In
RQ-B1
, we see that
PyMigTool
is able to fully migrate 32% of the migrations; however, this means that 68% of the migrations would still require the developer to perform edits or fixes to complete the migrations.
In this RQ, we look into how much additional manual effort is required to correct the incomplete migrations.

4.2.4.1
RQ-B2
: Approach

RQ-B1
shows that 233 migrations are completely correct after the automated migration process.
The remaining 484 migrations will require fixes for the tests to pass.
These 484 migrations are between 46 unique library pairs in 147 repositories.
Attempting to fix all these migrations manually would be very time consuming and impractical.
Therefore, we select one random migration from each library pair, while maximizing the number of unique repositories.
This gives us a total of 43 migrations between 43 library pairs in 39 unique repositories.

For each of these migrations, we open the code using the PyCharm IDE at the version after
PyMigTool
migration.
We refer to library documents and other online resources to understand each test error and how to fix it.
After applying the edits, we runs the tests again and save the test report, which we refer to as TestReport
manual
.

We estimate the development effort required for a migration by measuring the number of lines changed for the migration.
For a migration, we compute a diff between the code before manual edit (i.e.
, the code after automating migration by
PyMigTool
) and the code after manual edits.
From the diff, we calculate the number of changed lines of code by adding number of removed lines and number of added lines.
We refer to this number as
MigLOC_{manual}
.
Now, while this number gives us the absolute number of line changed, it does not give us the relative effort in comparison to the automated migration by
PyMigTool
.
For example, a migration that required 50 changed lines where the tool performed 48 of them and we only have to edit 2 lines should not be considered the same as a migration that required 4 lines of code and we still have to edit 2 lines.
Therefore, we also measure the number of lines changed by
PyMigTool
during the automated migration from the diff between the code before automatic migration and the code after migration by
PyMigTool
.
We refer to this number as
MigLOC_{auto}
.
From these two numbers, we calculate the manual migration effort as the ratio of manual changes to the total changes.

\mathit{Effort}_{\mathit{manual}}=\frac{\mathit{MigLOC}_{\mathit{manual}}}{\mathit{MigLOC}_{\mathit{auto}}+\mathit{MigLOC}_{\mathit{manual}}}

(1)

Similarly, automatic migration effort is calculated as the ratio of automatic changes to the total changes.

\mathit{Effort}_{\mathit{auto}}=\frac{\mathit{MigLOC}_{\mathit{auto}}}{\mathit{MigLOC}_{\mathit{auto}}+\mathit{MigLOC}_{\mathit{manual}}}

(2)

Note that the total migration effort is the sum of
\mathit{Effort}_{\mathit{manual}}
and
\mathit{Effort}_{\mathit{auto}}
, i.e.
,
\mathit{Effort}_{\mathit{manual}}+\mathit{Effort}_{\mathit{auto}}=1
.

4.2.4.2
RQ-B2
: Results

Figure 10
:
Distribution of effort savings across manually fixed migrations.

The yellow dotted line shows median effort saving across all 24 migrations.

We apply manual edits to the selected 43 migrations.
The manual edit effort fixes at least one failing test for 24 (56%) migrations, including 21 (49%) migrations that were completely fixed.

For the 21 migrations that we were able to fully correct through the manual edits, we measure
\mathit{Effort}_{\mathit{manual}}
and
\mathit{Effort}_{\mathit{auto}}
using
Equation 1
and
Equation 2
, respectively.

Figure 10
shows the proportion of automatic and manual changes made for each migration.
The blue part of the stacked bar is the
\mathit{Effort}_{\mathit{auto}}
, while red part is
\mathit{Effort}_{\mathit{manual}}
.
The yellow dotted line shows the median of
\mathit{Effort}_{\mathit{auto}}
across all 21 migrations, which is 86%.
This means that for a median migration,
PyMigTool
performed 86% of the changes, while the developers only needed to perform 14% of the changes.

4.3.2
Possible extensions of
PyMigTool

The problems we discuss above can potentially be mitigated by the following extensions of
PyMigTool
:

Extension-1

Post-processing for reverse refactoring:
We can add a post processing step that detects renamed public APIs, and renames them back to the original names, potentially solving
Issue-1
.
Refactoring detection tools, such as RefactoringMiner
RefactoringMiner2
, can be used to detect such refactoring changes, and refactoring tools, such as RefMerge
refmerge
, can be used to apply the changes.

Extension-2

Including all dependant code with the prompt:
This will allow the LLMs to know whether and how the code to migrate is used in other parts of the project, including the test code, potentially resolving
Issue-2
.
This approach, however, can be impractical for the files that have a large number of dependencies, due to the LLM’s context length limitations.

Extension-3

Reprompting with test error messages:
When we manually fixed the migration in
Figure 13
related to
Issue-3
, we were able to quickly identify the issue just by looking at the test error messages.
This means, systematically reprompting
PyMigTool
with the test error messages may help it to understand the context better and produce a correct migration, similar to how SOAR
ni2021soar
uses error messages to improve their program synthesis process (see
).
While this can potentially help
PyMigTool
to produce more correct migrations, the challenge is processing the error messages and generating a meaningful prompt for the LLM. Note that SOAR considers only two pairs of libraries, and therefore the error messages are not as diverse as in our case.

Extension-4

Designing a sophisticated
merge skipped code
algorithm:
our merge skipped code algorithm only looks at the size of the skipped code and usages of source APIs (see
paragraph 4.1.3.1
).
A more sophisticated algorithm that considers the context and the structure of the code, such as removed functions/classes, may potentially improve this step reducing the effect of
Issue-4
.

While the above steps can potentially mitigate the problems we identified, the positive side is that manually fixing the incomplete migrations was also simple, so further effort in more automation may not be necessary.
For example, in
Figure 13
(
Issue-3
), we were able to catch the issue easily just by looking at test error messages, and the fix was just replacing the exception type in the code.
While reprompting with error messages may potentially fix the problem, it would also increase the cost of migration.
The skipped code cases (
Issue-4
) are also fairly simple to resolve with modern IDEs.
We use PyCharm’s change viewer during our manual fix, which allows us to easily identify the skipped code, and merge them with a click of mouse.

The case in
Figure 12
(
Issue-2
) required us to look deep into the library documentation and was time consuming.
However, the original developers are likely to be more familiar with the libraries and their behavior.
Therefore, they may have been be able to fix the issues easily.

In some cases where migrations are initially marked as incorrect, the issues are related to configuration rather than code changes.
For example, in a migration from
chardet→cchardet
, adjusting the Python version from
3.11
to
3.9
resolved the test failures.
Similarly, we made a migration from
flask→sanic
successful by installing an additional dependency,
sanic-ext
, with no changes to the migrated code.
The developers of the projects are likely to have been aware of such configuration requirements, therefore, they may be been able to fix the issues easily.

Overall, we find that
PyMigTool
automatically completes migration for a large portion of cases (32% migrations)
and does most of the complex migration work (86% changes) for the remaining migrations,
often leaving simple edits for the developers to perform (14% changes).
Further improvements in migration process may potentially help in reducing the manual effort. However, the manual effort seems fairly minimal in most cases, specially for the developers who are familiar with the libraries and the project.
We stress that the author of this thesis, who has no prior knowledge of the projects, performed all the manual edits alone without help of any other developers.
This indicates that the manual edit part can potentially be done by someone new to the project, or even be outsourced outside of the project team.

4.4
Threats to validity

This section discusses the potential threats to the validity of our study and the steps we take to mitigate them.

4.4.1
Internal validity

One author performs all manual fixes and their evaluation, which may introduce subjectivity or bias.
To mitigate this, we follow a consistent process for manual fixes and rely on objective test outcomes as the primary measure of correctness.

Configuration and environment setup also pose internal threats.
Some migrations initially fail due to environment or dependency issues rather than code errors.
We address these by adjusting configurations when possible, but environment-specific factors, such as Python and library version, operating system, may still affect the results.

4.4.2
External validity

We focus on Python projects that are well-tested and actively maintained, as selected through specific filters.
This focus may limit the generalizability of our findings to projects with less test coverage, different maintenance status, or other programming languages.
The set of library pairs and migration scenarios is also limited by the availability of analogous libraries and the manual validation process.
As a result, the observed effectiveness of
PyMigTool
may not fully generalize to all migration contexts.
That said, the size of the dataset (717 migrations) and the diversity of selected projects (175 repositories) provide a reasonable basis for evaluating the tool’s effectiveness in a variety of migration scenarios.

4.4.3
Construct validity

A key threat to construct validity is the correctness of the automated and manual evaluation process.
We use automated test suites to assess migration correctness, but these tests may not cover all possible behaviors or edge cases in the migrated projects.
To minimize this, we select projects with at least 80% lines of code covered by tests, which helps ensure that the tests are comprehensive enough to provide a reliable measure of correctness.

Our manual migration effort calculation metric (
Equation 1
) is based on lines of code changed, which may not capture all aspects of migration effort, such as time spent understanding or debugging the migration.
We use it as a measurable objective proxy for the effort required.

5
Related Work

There has been a significant amount of research aimed at automating library migration.
We discuss these techniques in this section.

The majority of the existing library migration techniques focus on identifying API mappings between two analogous libraries.
Some of these techniques use mine existing library migrations to identify the API mappings
teyton2012mining
;
teyton2013automatic
;
alrubaye2019use
;
alrubaye2019migrationminer
;
alrubaye2020learning
.
Some techniques see the requirement of existing migrations as a limitation, and therefore use other techniques, such as machine learning
alrubaye2018automating
;
miningAnalogicalAPIs
and natural language processing
ni2021soar
.
These techniques only identify the API mappings, but do not perform client code transformation, which is a separate challenge.

SOAR
ni2021soar
uses API documentation to identify API mappings, and then uses the mappings and unit tests to guide program synthesis for client code transformation.
SOAR has several limitations that prevent it from being a general solution for library migration.
SOAR is evaluated on only two pairs of deep learning libraries, focusing on their migration of neural network models.
These APIs are usually called in a sequence, where the output of one call is used as input to the next call.
The nature of these APIs allows SOAR to check the program state after each API call, which is not the case for most libraries.
Additionally, given the limited number of libraries, their technique relies on the library-specific error message format to further guide the synthesis process, requiring extensive changes and technique adaptations for running SOAR on other libraries.
SOAR supports one-to-many code changes for a small set of pre-determined APIs, whose information is hard-coded for the transformation process.
SOAR also times out for 20% of the evaluated migrations, even for small code snippets, the largest being 183 lines of code.

Zhou et al.

hapim
proposed HaPiM, which first trains an unsupervised machine learning model capable of API mapping, and then uses the API mappings to guide an LLM in code transformation.
Similar to Chen et al.

miningAnalogicalAPIs
, HaPiM learns from API usage patterns of source and target libraries in their respective client projects, therefore does not require any existing migration examples.
For the code transformation, they use the API mappings to prompt an LLM to replace source API calls with target API calls.
Their approach outperforms MigrationMapper
alrubaye2019use
and GPT-3.5 Turbo on the BLEU
bleu
and CodeBLEU
codebleu
metrics evaluated on 5 Java library pairs.
A significant limitation of HaPiM is that it works with small independent code snippets that use the source library APIs, and results in an equivalent snippet that uses the target library APIs.
This is as opposed to real-life code where the source API usages are interleaved with other types of code, such as variable declarations, control statements, and other library usages.
This means that to use HaPiM, developers need to first extract code snippets that contains only the source library API usages from the client code, then use HaPiM to replace them with target library APIs, and then re-integrate the transformed code back into the client code, which is not practical for large-scale library migrations.

Nikolov et al.

nikolov2025google
describe Google’s experiences in using LLMs for several internal code transformation tasks, including
Joda Time→Java Time
migrations.
They do not attempt to provide a general solution for library migration; rather, they use LLMs to perform the migration they need.
Therefore, their prompts contains instructions and contextual information tailored specifically for
Joda Time→Java Time
migrations.
Nonetheless, they show that using LLMs reduced migration time by at least 50% compared to manual migration.

The above shows that there have been different approaches to automate the library migration process.
However, these techniques come with one or more limitations that prevent them from being a general solution for library migration.
Our tool,
PyMigTool
, resolves these limitations and can automate the entire library migration process for any arbitrary analogous library pair (
Section 4
).
We evaluate
PyMigTool
on a large and diverse dataset of 717 migrations between 48 analogous library pairs, and show that
PyMigTool
can successfully perform most of the migration with no or minimal manual intervention from the developer.

6
conclusion

In this paper, we explore the capabilities of LLMs for automating Python library migration and build
PyMigTool
, a practical tool that combines LLMs with static and dynamic program analysis to automate the full migration process.
In the first phase of the work, we conduct an empirical study using three LLMs on the
PyMigBench
dataset to understand how well LLMs can perform library migration.
We find that the best performing LLM, 4o, correctly migrates 94% of the individual code changes.
At the migration level, it perfectly migrates 57% of the migrations, and 94% of them have at least one correctly migrated code change.
We also run unit tests for a subset of the migrations, and find that 64% of the migrations by 4o have the same sets of tests passing in the developer’s migration and the LLM’s migration.
A much lower cost LLM Mini and the free LLama also perform relatively well, with both correctly migrating 89% of code changes.
Overall, we find that LLMs can handle complex code changes, therefore, we conclude that LLMs are a promising approach for automating library migration.
However, we also identify some challenges that need to be addressed to make LLM-based migration practical.

We use these insights to build
PyMigTool
, a CLI tool that automates the full library migration process in phase two.
Our evaluation on 717 simulated migrations across 175 diverse projects and 48 library pairs shows that
PyMigTool
can fully automate a large portion of migrations (32%),
with most remaining cases requiring only minor manual intervention (median 14% changes).
The tool’s layered approach, including post-processing steps, improves LLM migration correctness (from 65% to 86%) and reduces developer effort.
While
PyMigTool
is not able to handle every migration scenario perfectly, it lowers the barrier for large-scale library migration in real-world projects.
Overall,
PyMigTool
represents a meaningful step toward making automated library migration accessible and effective for the software engineering community.
