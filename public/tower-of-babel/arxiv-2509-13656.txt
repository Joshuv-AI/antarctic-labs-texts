A Regression Testing Framework with Automated Assertion Generation for Machine Learning Notebooks
Yingao (Elaine) Yao, Vedant Nimje, Varun Viswanath, Saikat Dutta

Abstract
. Notebooks have become the de-facto choice for data scientists and machine learning engineers for prototyping and experimenting with machine learning (ML) pipelines. Notebooks provide an interactive interface for code, data, and visualization. However, notebooks provide very limited support for testing. Thus, during continuous development, many subtle bugs that do not lead to crashes often go unnoticed and cause silent errors that manifest as performance regressions. To address this, we introduce NBTest – the first regression testing framework that allows developers to write cell-level assertions in notebooks and run such notebooks in pytest or in continuous integration (CI) pipelines. NBTest offers a library of assertion APIs, and a Jupyter Lab plugin that enables executing assertions. We also develop the first automated approach for generating cell-level assertions for key components in ML notebooks, such as data processing, model building, and model evaluation. NBTest aims to improve the reliability and maintainability of ML notebooks without adding developer burden. We evaluate NBTest on 592 Kaggle notebooks. Overall, NBTest generates 21163 assertions (35.75 on average per notebook). The generated assertions obtain a mutation score of 0.57 in killing ML-specific mutations. NBTest can catch regression bugs in previous versions of the Kaggle notebooks using assertions generated for the latest versions. Because ML pipelines involve non-deterministic computations, the assertions can be flaky. Hence, we also show how NBTest leverages statistical techniques to minimize flakiness while retaining high fault-detection effectiveness. NBTest has been adopted in the CI of a popular ML library. Further, we perform a user study with 17 participants that shows that notebook users find NBTest intuitive (Rating 4.3 / 5 4.3/5 ) and useful in writing assertions and testing notebooks (Rating 4.24 / 5 4.24/5 ).

Despite their popularity, notebooks are notorious for their poor
reliability and reproducibility
(
Chattopadhyay et al. 2020
;
Huang et al. 2025
)
.
Due to their flexibility (e.g., out-of-order execution) and absence of tests,
users often end up with messy notebooks that become hard to reuse and reproduce
results with
(
Pimentel et al. 2019
;
Head et al. 2019a
)
. A recent study
analyzed 1.4 million notebooks and reported that fewer than 25% notebooks could
be executed without execution errors, while only 4% reproduced the expected
results
(
Head et al. 2019a
)
. Hence, a
working
notebook may become
unusable due to regressions caused by internal changes (such as code changes) or
external changes (e.g., changes in dependencies or datasets) across versions.
Further, regressions might manifest
within a session
leading to silent
(non-crashing) bugs (e.g., due to out-of-order execution or stale states)
without the user noticing them.
Hence, like regular programs, notebooks need a regression testing
infrastructure, akin to tools like
Pytest

(
Krekel et al. 2024
)
and
JUnit
(
Team 2020
)
.
Currently, for testing and debugging, notebook users follow ad hoc practices,
such as using print statements, writing test cases within the notebook, using a
separate test notebook for validation, or manually inspecting
results
(
Chattopadhyay et al. 2020
;
Huang et al. 2025
)
.

This challenge is especially critical in industry settings. For
example, Netflix uses Jupyter Notebooks in production for data
exploration and workflow
scheduling
(
Blog 2019
)
. PayPal has developed an enterprise-grade
Jupyter platform – PayPal Notebooks – which empowers over 1,300 internal users
to perform data analysis, machine learning, and workflow automation
(
Mehta 2018
)
. These examples highlight the
growing need for rigorous quality assurance for
notebooks.

Existing tools and their limitations.

Developers have built tools such as
nbval

(
Fangohr et al. 2020
)
,
which is a regression testing tool for Jupyter notebooks. It performs a textual
comparison of a notebook’s current output cells against saved values from prior
sessions. However, its checks are not robust to non-deterministic results
(common in ML pipelines) or fluctuations in the output string format (especially
when considering numerical outputs). Further, it can only check outputs printed
in cells. Deepchecks
(
Chorev et al. 2022
)
is a tool that
provides a library of tests for checking model and data integrity properties in
ML pipelines. However, the developers still need to manually incorporate such
checks, and the framework does not allow them to easily write custom tests.
Deequ
(
Schelter et al. 2018
)
is another tool that is designed for data
validation in production pipelines. However, none of these tools can
automatically generate tests or account for nondeterminism in ML notebooks.

1.1.
Our Work

To address this gap, we propose a novel regression testing
framework for Notebooks:
NBTest
. With NBTest, we introduce the idea that
developers can write
cell-level assertions
to check the expected behavior
of intermediate computations in a notebook. For instance, a developer may want
to check that the dataset was pre-processed correctly (e.g., no null values), if
the model training was set up correctly (e.g., model weights are initialized
randomly), or if the training accuracy was close to expectations. To support
such checks, NBTest provides simple APIs such as

nbtest.assert_true(exp)
to check if
exp
is true and

nbtest.assert_allclose(X, Y, atol, rtol)
to check if the values X and
Y are equal up to the desired tolerance. A recent study reported that notebook
users often follow
cell-based risk management
, where users test changes
in a new cell before merging with old cells to isolate any
errors
(
Huang et al. 2025
)
. Hence, cell-level assertions can potentially
improve the reliability of notebooks by mitigating regressions and nudging
developers towards better testing practices in notebooks.

1
illustrates the workflow of NBTest.

NBTest integrates with
pytest

execute with
pytest
. In addition, we developed a JupyterLab plugin
(
NBTest-lab-extension
) that provides two key features: (1) toggling the
visibility of assertions, and (2) enabling or disabling the assertions
execution. Within JupyterLab, NBTest assertions are displayed in a separate panel
on the right (Figure

focus on notebook development without being distracted by assertions, they can

via the
NBTest Asserts: ON
toggle
(Figure

directly in the notebook.
This way, developers can make edits without accidentally triggering test
failure, but validate the changes by executing
only
the related
assertions as needed.

Automated Assertion Generation.

However, writing tests manually can be cumbersome. To assist developers in
writing tests, we propose an automated assertion generation technique that
generates cell-level assertions, especially for machine learning notebooks. A
recent study showed that developers of machine learning notebooks often
implement various integrity checks for data and machine learning model-related
properties, such as data shape, model performance, and network architecture,
using assertions and print statements
(
Shome et al. 2024a
)
. Motivated
by this finding, we design an assertion generation technique that first
identifies APIs of popular libraries (e.g., PyTorch
(
Paszke et al. 2019
)
,
TensorFlow
(
Abadi et al. 2015
)
,
Scikit-Learn
(
Pedregosa et al. 2011
)
, and Pandas
(
pandas development team 2020
)
) used in a
notebook for machine learning operations,
instruments the API calls, executes the notebook to collect expected results,
and generates appropriate assertions in the notebook. A key challenge of testing
machine learning notebooks is that their execution can often be
non-deterministic due to randomness during training or batching data
– causing some assertions to be potentially
flaky

(
Dutta et al. 2020
)
. To mitigate this challenge, we execute the notebooks
multiple times to collect runtime information and estimate the variance in the
results via statistical tests. We use the collected data to generate approximate
assertions (e.g.,
assert_allclose
) to account for this variance via
tolerance bounds where needed
(
Dutta et al. 2021
)
.

We envision that cell-level assertions (both automated and manual) can enable a lot of use cases for ML notebooks, such as documenting developer assumptions of expected behavior, catching regressions during interactive sessions, improving the reproducibility of notebooks, quantifying variance in training performance or intermediate results, and identifying contracts that can be used for monitoring of ML pipelines.

1.2.
Results

We collect a corpus of 592 executable notebooks from the
Kaggle platform from popular competitions. Our test generation approach
generates a total of 21163 assertions,
35.75 assertions per notebook on average. Out of
21163 assertions, 16408 are dataset-related
assertions, 830 model architecture related assertions,
and 3925 are model performance related assertions. We
perform mutation analysis of the notebooks with assertions using domain-specific
mutation operations, such as adding outliers in data and modifying layers of
neural networks. Overall, we obtain a mutation score of 0.57 showing that our generated assertions are robust to a variety of domain-specific
mutations.

We also collect 2369 buggy versions for 592 of
Kaggle notebooks and evaluate whether our generated assertions can catch the
regressions. Our generated assertions can successfully detect
326 of the buggy versions
(out of a total of 762 versions that can run successfully), indicating that NBTest’s
assertions can also detect real-world regression bugs.

17
participants (

2

Methodology

3.1.
Notebook Dataset Curation

We collect a corpus of runnable real-world notebooks from Kaggle. Kaggle is the
world’s leading platform for machine learning competitions and contains many
high-quality and end-to-end machine learning pipelines in the form of
notebooks. Hence, like prior studies on
notebooks
(
Yang et al. 2022
)
, we also collect machine-learning related Python
notebooks from Kaggle competitions.
We select five popular Kaggle competitions
(
Kaggle 2024b
)
that
are related to machine learning tasks, namely: Titanic
(
Kaggle 2024d
)
, Housing
Prices
(
Kaggle 2024b
)
, Spaceship Titanic
(
Kaggle 2024c
)
, Jane
Street
(
Kaggle 2024a
)
, and Digit recognizer
(
Kaggle 2024a
)
.
We use the Kaggle API
(
Kaggle 2024
)
to download all notebooks related to
these competitions.
To get potentially runnable
notebooks, we filter out notebooks older than two years. We filter out notebooks with fewer than 10 votes to remove
lower-quality samples. After these steps, we obtain 1753 notebooks.
We select notebooks that use at least one of the mainstream ML libraries:
PyTorch, TensorFlow, Keras, or Scikit-learn, by checking their import
statements. We identify 1612 such notebooks. The distribution of ML frameworks among them
is 1489 (Scikit-learn), 383 (TensorFlow/Keras), and 97 (PyTorch) (non-exclusive). involve training operations and 1483 notebooks involved inference.

Notebook Execution and Dependency Management.

Notebooks are well-known to have reproducibility problems.
To mitigate this issue, we use the pipreqs
(
Korzhyk and contributors 2025
)
tool to generate the
list of dependencies (a
requirements.txt
file) for each notebook. Using
this method, we were able to generate dependencies for 862 out of 1612 notebooks. We then create a conda environment for each notebook, install the
identified dependencies, and execute the notebook. Finally, we retain notebooks
that execute without any errors. After this process, we obtain
592 Kaggle notebooks, out of which 537 use
scikit-learn, 200 use TensorFlow/Keras, and 35 use
PyTorch (some notebooks use multiple frameworks).

3.2.
Mutation Testing

To evaluate the fault-detection abilities of our generated assertions, we design
and implement 10 mutation operators that are inspired by prior studies on common
bugs found in machine learning or data science
projects
(
Zimmermann et al. 2023
;
Ma et al. 2018
;
Wiles et al. 2021
;
Liblit et al. 2023
)
.
We reviewed those mutation operators proposed for machine learning in
(
Ma et al. 2018
)

and identified two main categories: data-related and model-definition-related
operators. From these, we selected a representative subset that captures key
mutation types, including data distribution anomalies, corrupted training data,
inappropriate hyperparameters, and flawed model definitions. Our implemented
mutators subsume those from
(
Ma et al. 2018
)
, while also extending
them based on common ML development errors identified in

(
Zimmermann et al. 2023
)
,

(
Wiles et al. 2021
)
, and

(
Liblit et al. 2023
)
.

We exclude certain mutation operators and error patterns found in

(
Zimmermann et al. 2023
)
,
(
Ma et al. 2018
)
,

(
Wiles et al. 2021
)
, and

(
Liblit et al. 2023
)
, such as variable redefinition and missing data,
because they most often cause the notebook to crash. However, our goal is to
explore mutations that do not crash the notebook but lead to silent errors.
These silent errors allow us to evaluate whether NBTest assertions can
effectively detect these hard-to-detect issues.

Table
1
presents all mutation operators that we
support. We implement two categories of mutation operators: 1)

Data mutations
, which mutate the dataset associated with the notebook, for example, by adding outliers or introducing spurious data correlations, and 2)

Source code mutations
, which mutate the Python code in the notebook, for example, by modifying training hyper-parameters or removing neural network layers.
Overall, we implement
5
data-based mutations and
5
source code-based mutations.

3.3.
Collecting Kaggle Notebook Versions

There is a lack of publicly available datasets that include silently failing
bugs in Jupyter Notebooks. Unlike regular programs, developers do not frequently
commit changes in notebooks. Due to the absence of tests, even if they do
commit, they may be unaware that the notebook is buggy, or the commit may be
related to a crash fix. To mitigate this problem, we obtain old versions of
notebooks from the Kaggle platform. The Kaggle platform stores the historical
versions of each notebook. Each version of a notebook denotes a submission made
by the user to solve a competition. We posit that the older (or non-latest)
versions of these notebooks can represent real-world bugs/regressions that do
not crash but lead to sub-optimal performance. Hence, we consider the older
versions as buggy versions of the notebooks and use them for
reverse
regression testing
, i.e., considering the latest version as the
previous

correct version and each older version as the
new
buggy version of the
notebook. The intuition behind this choice is that the latest version of a
notebook is likely to be the most stable, making it a suitable
baseline for identifying regressions in older versions.

Collection and Filtering.
We develop a web scraping tool to extract all
available versions of notebooks we consider in §
3.1
. We
obtain 3660 notebook versions. We filter out notebooks with execution errors or
large diffs (more than 500 diff lines). We download 2369 notebook
versions that remain.

Evaluating notebook versions.
We generate assertions in the latest
versions of each notebook using NBTest, and then we attempt to transfer each
assertion to older versions. To map the assertions, we first identify unchanged
cells and pair the remaining cells by comparing their ASTs after removing
comments and separating logic from test assertions. We transfer assertions by
matching preceding statements, although significant changes may prevent
transfers. The process of finding the
appropriate code locations for insertion is automatic. If during the process,
it cannot identify a matching
location due to reasons such as variable renaming or code restructuring, it
skips injection for that cell to avoid incorrect placement.
Then we execute each notebook version with the transferred
assertions. A notebook version is considered
killed
, i.e., regression is
detected if at least one transferred assertion fails.

3.4.
Metrics

We define the metrics that we use to evaluate our approach.

Passrate
p
.

Given an assertion, let
N
be the total number of executions, and let
P
be the number of executions in which the assertion passes.
The
passrate

p
of the assertion is defined as:

p=\frac{P}{N}.

Mutation Score
m
.

Given an assertion, let
M
be the total number of generated mutants.
For each mutant
M_{i}
(
i\in\{1,\dots,M\}
), let
p_{i}
be the passrate of the assertion on
M_{i}
.
The
mutation score

m
of the assertion is defined as:

m=\frac{1}{M}\sum_{i=1}^{M}(1-p_{i})
.
For a type of assertion, we define its mutation score as the average mutation score of all assertions in this type.

Number of Versions Killed
K_{V}
.

Let
\mathcal{V}
denote the set of versions of a notebook.
For each version
v\in\mathcal{V}
, let
A^{v}
be the number of assertions, and let
p_{i}
be the passrate of assertion
i\in\{1,\dots,A^{v}\}
on
v
.
The
number of versions killed

K_{V}
is defined as:

K_{V}=\sum_{v\in\mathcal{V}}\mathbbm{1}_{(\exists i\in\{1,\dots,A^{v}\},\,p_{i}<1)}
,
where
\mathbbm{1}
is the indicator function.

Number of Notebooks Killed
K_{N}
.

Let
\mathcal{N}
be the set of notebooks, and let
V_{i}=|\mathcal{V}_{i}|
denote the number of versions in notebook
\mathcal{N}_{i}
.
Let
K_{V}^{(i)}
be the number of versions killed in notebook
\mathcal{N}_{i}
.
The
number of notebooks killed

K_{N}
is defined as:

K_{N}=\sum_{\mathcal{N}_{i}\in\mathcal{N}}\mathbbm{1}_{(K_{V}^{(i)}=V_{i})}
.

4.
NBTest Framework

4.1.
Design Principles of NBTest

We developed the NBTest framework based on the following design principles:

(1)

The framework should allow developers to write expressive cell-level assertions.
✓

(2)

It should be possible to run cell-level assertions with
pytest
and CI.
✓

(3)

The cell-level assertions should be non-invasive; they should not
disrupt the interactive nature of notebooks or clutter the notebook.
✓

(4)

It should serve as a plugin in the IDE (e.g., Jupyter Lab). The developers can choose to turn on and off the assertions as they want.
✓

(5)

The framework should automatically generate assertions for a given ML notebook to assist developers.
✓

(6)

When enabled, the runtime of assertions should be low.
✓

(7)

The cell-level assertions should account for randomness in machine learning code to avoid flakiness.
✓

(8)

The assertion APIs should follow common assertion patterns for the ease of adoption.
✓

(9)

It should identify developers’ intentions and only generate a few but relevant assertions.
✗

(10)

It should allow developers to run a subset of tests when needed.
✗

(11)

It should allow developers to automatically only re-run cell-level assertions affected by a change (Evolution-Aware).
✗

(12)

The assertions should be environment or configuration-aware, e.g., different assertions should be enabled for different versions of PyTorch.
✗

NBTest currently supports all features marked as
✓

via its suite of three tools, but does not support features marked as

✗
. NBTest is not evolution-aware, so it always runs all
assertions. NBTest is based on regression oracles, or requires developers to
provide a test oracle when manually writing assertions. These principles are
based on our experience and understanding of Machine Learning and the Notebook
environment, and prior studies
(
Chattopadhyay et al. 2020
;
Huang et al. 2025
)
. In
the future, we want to evolve NBTest in collaboration with ML developers.
We have started reaching out to ML project developers, have received
some positive engagements, and integrated NBTest into the CI of one ML
project.

NBTest assumes linear execution of notebooks when generating assertions, which we consider both valid and practical.
Mainstream open-source projects alreayd test notebooks in CI by executing them sequentially
(
Library 2025b
)

(
TransformerLens 2025
)

(
bionemo framework 2025
)
,
and Jupyter Notebook itself provides no mechanisms for custom execution orders.
Likewise, NBval
(
Fangohr et al. 2020
)
, a popular pytest plugin for testing notebooks,
and Kaggle platform both assume linear execution implicitly.
In practice, users often linearize notebook cell order before sharing or rerunning, to improve reproducibility,
and tools like
(
Head et al. 2019b
)
can further help with cleaning and reordering notebooks.

4.2.
Overview

Our NBTest framework provides three distinct tools:

(1)

Python library (NBTest-lib):
provides APIs for writing cell-level assertions in Jupyter notebooks
and works as a
pytest
plugin that collect these assertions like standard unit tests.

(2)

Assertion generator (NBTest-gen):
a tool that automatically generates cell-level assertions for a Jupyter notebook by identifying commonly used machine learning-related APIs.

(3)

Jupyter plugin (NBTest-lab-extension):

a JupyterLab plugin for evaluating NBTest assertions.
Assertions can be shown or hidden to improve notebook readability,
as well as enabled/disabled during execution.
When executed, each assertion displays its result inline in the notebook.

We next discuss the design and implementation of NBTest-lib and NBTest-gen.

4.3.
NBTest Python Library (NBTest-lib)

We support two categories of assertions:

(1)

Generic Assertions:
The framework provides standard assertions including
assert_equal
,

assert_allclose
,
assert_true
, and

assert_false
. These functions follow the familiar semantics of
traditional unit testing frameworks but are tailored for execution within notebooks.

(2)

Data-related Assertions:
Because data processing is common in
machine learning workflows, NBTest includes specialized assertions for
testing data-related properties. The
assert_df_var
and

assert_df_mean
functions test the statistical properties of
dataframes while handling missing values appropriately. The

assert_column_types
and
assert_column_names
assertions
verify the structural integrity of data, ensuring that schema changes or
data loading errors are detected early in the development process.

We designed NBTest’s APIs to mirror common assertions such as
Python’s
assert
and Numpy’s
assert_allclose
.
Unlike those assertions, NBTest’s assertions are inactive during normal execution,
to not interrupt development process.
NBTest integrates with Pytest through a custom plugin.
When invoked with the
--nbtest
flag,
pytest

parses the Jupyter notebook, locates cells with
NBTest assertions, executes them as tests.
Using
pytest
’s collection hooks
(
pyt 2025
)
,
each assertion is registered as an individual test with a unique identifier.
This identifier allows developers to pinpoint exactly which assertions pass or fail.
NBTest executes all notebook cells regardless of cell execution failures,
and then report results.

4.4.
Automated Assertion Generation (NBTest-gen)

We describe the challenges and our solutions for building our automated assertion generation approach, NBTest-gen.

Challenges.
First, it is well-known that ML pipelines often exhibit nondeterminism due to various operations like randomized batching, random model initialization, and parallel execution on GPUs. Assertions generated without accounting for this randomness can lead to
flaky assertions
, where repeated executions of the same notebook yield inconsistent outcomes.
Researchers have previously identified
flaky
behavior in
unit tests in ML libraries
(
Dutta et al. 2020
;
Dutta et al. 2021
;
Nejadgholi and Yang 2019
)
and ML training pipelines
(
Pham et al. 2020
)
.

Second, there is a lack of clear criteria for selecting which program variables or computations to target when generating assertions in ML notebooks.

In principle, one could add assertions for
every
intermediate result/variable in the notebook, which would provide comprehensive coverage.
However, this brute-force strategy may potentially introduce assertions that are not meaningful to the developer, cluttering the notebook interface, and reducing its readability as well as interactivity.

Conversely, a minimal approach that adds assertions only for the final outputs – such as checking the final evaluation metrics of the trained model – may preserve usability but sacrifice bug-detection capability. Bugs that manifest in intermediate computations might only be detected at the final stage or be missed completely.
Hence, an automated assertion generation approach must strike a balance between the fault detection capability, testing key properties of the ML pipeline, and preserving the notebook’s usability.

.
NBTest-gen Workflow

Approach.
To solve the first challenge, we leverage statistical
techniques to estimate the variance in the notebook outputs. To solve the second
challenge, we identify popular APIs in ML libraries such as
Scikit-Learn
(
Pedregosa et al. 2011
)
, Pandas
(
pandas development team 2020
)
,
TensorFlow
(
Abadi et al. 2015
)
, and
PyTorch
(
Paszke et al. 2019
)
that are used in the notebook to process data
and models. We then generate assertions checking the integrity properties of
such components. A prior study
(
Shome et al. 2024a
)
showed that
developers often write assertions or print statements to perform similar tasks.
NBTest-gen workflow is shown in Figure
2
. It consists of two stages:

4.4.1.
PropertyFinder

PropertyFinder extracts each notebook cell, analyzes its Abstract Syntax Tree (AST), and identifies key properties that are relevant to machine learning. A property represents a program component in the form of a variable or expression (e.g., method call).
We first identify three categories of properties based on findings from

(
Wang et al. 2024
)
, which show that Jupyter notebook failures most
commonly occur during data preparation, model training, and evaluation stages.
For each category, we identified specific properties to check by referencing data
anomalies reported in Table 1 of
(
Polyzotis et al. 2019
)
, as well as common
developer validation patterns (e.g., assertions, print statements) described in
Figure 3 of
(
Shome et al. 2024b
)
. In total, it identifies the following
kinds of properties based on popular APIs used by ML Notebooks:

•

Dataset
: We collect initialization of datasets that are from a CSV file (using
pandas.read_csv
), or imported from a library of datasets (like
sklearn.datasets
), or any intermediate datasets generated using APIs such as
scikit-learn
’s
train_test_split
.

•

Model Architecture (Model Arch.)
: We collect statements like initialization of ML models with hyperparameters. We consider models using Scikit-Learn APIs (e.g.,
LogisticRegression
) as well as Deep Neural Network models using PyTorch and TensorFlow APIs.

•

Model Performance (Model Perf.)
: We collect expressions that define metrics
using common APIs such as
accuracy_score
and
r2_score
, from

sklearn.metrics
. Sometimes, they also define custom metrics that
build on top of common numerical APIs. So, we implement a lightweight static
analysis that parses such expressions to identify custom metrics used in the
notebook.

PropertyFinder extracts properties from common contexts where developers inspect
intermediate computations, such as assignment statements, print statements, and
the last line in a cell
(
Shome et al. 2024a
)
. The last two cases
produce an output in the cell. For each detected property, we insert
instrumentation code into the notebook to record its values. To introduce
variability in the results, we assign a new random seed to each notebook run,
replacing any existing seeds.

NBTest can be easily extended to similar APIs by adding them to a configurable JSON file.
For example, to support XGBoost’s
XGBClassifier
in NBTest, we simply add the
XGBClassifier
API to the configuration file.
Since
XGBClassifier()
returns a scikit-learn compatible model, which NBTest already supports, it can automatically recognize the output type and generate model architecture assertions without further changes.

4.4.2.
Assertion Generation

This component executes each instrumented notebook for
N
iterations and collects the set of output values for each property.
Based on the kind of property, as described in
4.4.1
, we add one or more assertions to check the
integrity
of each property as follows:

•

Dataset
: For each dataset variable, we insert assertions to check properties such as the dataset’s size, column names and types, and the mean and variance of numeric columns.

•

Model Arch.
: For model definitions, we insert assertions to validate the architecture, including the number and types of layers, as well as associated hyperparameters.

•

Model Perf.
: We insert assertions to check whether evaluation metric values fall within an expected range. Given the inherent randomness in ML pipelines, we use approximate assertions (e.g.,
assert_all_close
) to allow for small numerical deviations in the results.

Test Oracle.
Because property-based oracles are scarce in the ML domain, in this work, we rely on
regression-based oracles
to check for correctness. So, we use the data from the runs of the instrumented notebook as expected values in the assertions we generate.
Naturally, this approach assumes that the current version of the notebook is correct, which may not be true. However, regression-based oracles can help document the developer’s assumptions (e.g., the dataset contains integer values), as well as capture the current state of the notebook. A violation of such assertions in the future can indicate regressions or reveal incorrect assumptions about the notebook. Regression oracles have also been proposed in prior test generation techniques
(
Xie 2006
;
Fraser and Arcuri 2011
;
Lukasczyk and Fraser 2022
)
. Further, developers can also modify the generated assertions to use manual oracles.

Assertion Bound Computation.
Chebyshev’s inequality
(
Chebyshev 1867
)
is a well-known technique in probability theory that guarantees that no more than a certain proportion of values will exceed a certain distance from the mean. Therefore, for any property with variance in outputs, we use Chebyshev’s Concentration Inequality to compute a tolerance bound for the assertion.

(1)

P_{r}(|X-\mu|\geq k\sigma)\leq 1-C,(k>0)

Given the confidence level
C
, Equation
1
shows how to compute a value such that the probability of the property exceeding it at most
1-C
, where
X
is a scalar random variable with a finite mean
\mu
and variance
\sigma^{2}
.

5.
Evaluation

We answer the following research questions in this work:

•

RQ1
: How many assertions of each kind does NBTest generate for each notebook?

•

RQ2
: How is the passing rate of generated assertions affected due to randomness?

•

RQ3
: How effective are generated assertions in detecting domain-specific mutations?

•

RQ4
: How effective are generated assertions in detecting real-world regressions notebooks?

•

RQ5
: How does configuration affect the passrate and mutation score of generated assertions?

Experimental Setup.

We run experiments on a large cluster of diverse machines with GPUs and Ubuntu
20.04 OS. To run each notebook, we set up a Conda environment with Python 3.9
and install the dependencies for the notebook. For RQ1-4, we run NBTest with
30 iterations and use the Chebyshev’s statistical method with the
confidence interval of 0.99 during assertion generation. For mutation
analysis (RQ3), we need to balance running many notebooks and reliably
estimating the mutation score. Hence, similar to prior
work
(
Dutta et al. 2020
)
, we run each notebook 30 times to compute the
mutation score.

Implementation Details.

NBTest uses NBFormat
(
Jupyter 2025
)
to parse the notebooks and Python’s AST library to
parse Python code in each notebook cell.
Specifically, NBTest uses AST’s
(
Python [n. d.]
)
visitor design pattern API to
detect the variables related to the ML-specific properties, and the transformer
design pattern API to insert the generated assertions back into the original
notebook.

5.3.
RQ3: How effective are generated assertions in detecting domain-specific mutations?

We apply the mutations described in §
3.2
to all the
notebooks. This process generates many
mutant notebooks
, each with a
single mutation, which we simply refer to as mutants hereon. Some mutations are
randomized (e.g., Add Outliers) and/or generate multiple mutants for the same
notebook (e.g., Modify Hyper-parameters). Hence, we apply such mutations multiple
times and generate a maximum of 4 mutants per mutation per notebook where
applicable. We run each mutant 30 times and compute the ratio of
runs in which the mutant is killed by an assertion.

Table

presents the results. Each row presents the mutation score for one mutation.
The second, third, and fourth columns present the number of mutants killed by each type of assertion.
One mutant may be killed by one or more assertions of a given type. So, we
consider a mutant as
killed
if at least one assertion of that type fails.
The

and

The final column

General Trends.
Overall, the assertions generated by NBTest obtain a mutation score of 0.57 across all mutations. We generate a total of 7907 dataset-related mutants. For these killed mutants, they are either killed by Dataset or Model Perf. assertions.
Because machine learning pipelines are often resilient to small data errors, we observe that corrupting the dataset does not always cause an observable degradation of the model performance. So, Model Perf. assertions only have a mutation score of 0.23 for data-based mutations. In contrast, the Dataset assertions obtain a mutation score of 0.57. They are generally stricter, e.g., they check if the mean and variance of data columns are close to expected values. Hence, they can detect data-based mutations more accurately and earlier in the ML pipeline. Model Arch. assertions are unable to detect such mutations because they only check for the integrity of the ML model architecture and its parameters.

We generate 4252 code-related mutations that either change the pipeline
components (e.g., Swap APIs), the training hyperparameters, or the model
architecture (e.g., Remove Layers). The overall mutation score is 0.35.
Expectedly, dataset assertions fail to detect most of these because
these mutations typically occur later in the pipeline. These mutations are
mostly detected by Model Arch. assertions (mutation score
0.25) or Model Perf. assertions (mutation score
0.19). The Model Arch. assertions are stricter in general, so
they can detect bugs that affect the model architecture easily.

Trends across Data-based mutants.
We observe that almost 10% of
Add Outliers and Add Nulls mutants and 5% of Repeat Data are killed by
Model Perf. assertions. In such cases, the model performance changes
significantly. For example, for one notebook
(
Firdaus [n. d.]
)

with Add Outliers mutants, the accuracy dropped to
0.197
from
0.63
after
applying the Add Outliers mutation. In another
example
(
Elbadry [n. d.]
)
, the Add Outliers caused the accuracy to
increase to
0.982
.
For Data Shift mutations, they only reorder the dataset rows, so they are also
hard to detect. In the future, one can generate assertions that check the
relationships between data columns instead of single-column properties (e.g.,
mean and variance) to detect such subtle regressions. An interesting future work
could be to generate assertions that check the correlation between data columns.

Trends across Code-based mutants.
Some mutations like
Remove Zero Grad only impact the training process by affecting how model
gradients are updated across training iterations. Hence, they often cause
non-deterministic assertion failures, where the model performance changes
drastically but only in a fraction of the cases. For Modify Hyper-parameters mutants,
around 74.7% of them are killed by Model Arch., and around 57.2% of them
are killed by Model Perf. Since most of the Modify Hyper-parameters or
Remove Hyper-parameters mutants modify the hyperparameters in the model definition
(such as choice of activation layer), the regression is detected by the
Model Arch. easily. In some other cases, a change in hyperparameters also
causes drastic changes in model performance, which is detected by
Model Perf. assertions. Among the surviving mutants, the major reason is
typically when the hyperparameter change does not alter the training results
beyond the expected range in Model Perf. assertions. We find similar
reasoning behind the lower mutation score of Swap APIs mutation. Because our
mutations are applied statically, there is no guarantee that these will alter
the pipeline behavior. An interesting future work would be to design mutations
that leverage dynamic information to generate behavior-modifying mutants.

Surviving mutants.

We manually inspect
100
surviving mutants and find
29
mutants survived
because the involved APIs are not tracked by NBTest– these can potentially be
killed by improving API coverage. The remaining
71
are equivalent mutants (36
data-based, 35 code-based) that either do not semantically modify the pipeline
or do not create an observable difference during the execution. Among the
data-based equivalent mutants,
29
Data Shift mutants did not affect
Dataset properties or model performance. Three mutants targeted
dataframes with fewer than ten columns, so 10% selection yielded no columns to
mutate. Two mutants were applied to empty dataframes and two mutants introduced
anomolies which later removed by preprocessing. Among the code-based equivalent
mutants,
28
Modify Hyper-parameters/Remove Hyper-parameters mutants only changed the
random seed. Three Remove Hyper-parameters removed explicit hyperparameters already
set to their API defaults (e.g.,
learning_rate=0.1
), and four
Modify Hyper-parameters mutants merely changed the verbosity or formatting. The
presence of equivalent mutants can underestimate NBTest’s true mutation score,
but computing the true score is generally undecidable
(
Grün et al. 2009
)

and even harder in stochastic ML pipelines. Hence, we leave this for future
work.

6.
User Study

The goal of our user study was to understand: 1) if developers of ML notebooks
find NBTest’s Python library intuitive and convenient to use in their daily
workflows, and 2) if NBTest’s generated assertions are useful compared to
manually written assertions. To fulfill this goal, we recruited
17

participants who have prior experience with writing machine learning code in
Jupyter notebooks.

Recruitment.

We recruited 17 participants (15 graduate students, 2 software
engineers) through online advertisements on social media and word-of-mouth
referrals. Overall, three participants have over five years of experience in
machine learning, and four have more than five years of experience using Jupyter
notebooks for ML-related tasks. None of the participants is an author of this
paper or contributed to this paper in any additional way.

Study Design.
For each participant, we send them a document containing
the setup instructions, a tutorial of NBTest’s different components and examples
of API usage, the assertion generator, and the JupyterLab plugin. We design four
tasks. In the first task, we provide participants with a notebook and ask them
to manually write assertions for three cases to check for data integrity, model
integrity, and model performance. They need to use NBTest’s assertion APIs, then
run the notebook using
pytest
. In the second task, we ask participants
to evaluate NBTest’s generated assertions and compare them with their manually
authored assertions. In the third task, we inject a bug in the notebook by
changing the model architecture and ask participants to detect this bug using
NBTest’s generated assertions. The third task shows that a bug can fail silently
and remain undetected during standard notebook execution, while cell-level
assertions can detect it effectively. In the fourth task, we ask participants to
use JupyterLab for the hide/show assertions features.

After the participants complete the tasks, we ask them to fill out a survey with
seven questions: (1) time taken to write assertions (in minutes with a timer);
(2) ease of writing assertions using NBTest’s APIs (1 = very difficult, 5 = very
easy); (3) whether cell-level assertions better capture developer assumptions
compared to notebooks without them (Yes/No); (4) usefulness of automatically
generated assertions (1 = not useful, 5 = very useful); (5) willingness to
integrate NBTest into their Jupyter Notebook workflow (Yes/No); and (6)
intuitiveness of using NBTest with Pytest (1 = not intuitive, 5 = very
intuitive). (7) Readability of the Jupyter Notebook with hide/show assertions
feature (1 = poor readability, 5 = very good readability). The survey also
included a text box for general feedback.

Study Results.

On average, participants spent
7.9
minutes manually writing the assertions.
The average rating for the convenience of manually writing assertions using
NBTest’s APIs was
3.94
. This suggests that while NBTest’s APIs are useful,
coming up with assertions manually might be challenging for users. All
participants agreed that the notebook with cell-level assertions provided a
better sense of developer assumptions in the notebook than without them.
Participants found the NBTest’s automatically generated assertions very useful
(average rating
4.24
, minimum
3
). Sixteen out of seventeen participants
said that they would like to integrate NBTest into their workflow. Finally, the
participants found NBTest’s interface very intuitive (average score
4.3
). As
for the readability of the notebook, the average score is
4.7
, suggesting
that the hide/show feature is highly effective in improving the readability of
notebooks with NBTest assertions. Specifically, one of the developers rated the
tool highly, with an average score of
4.8
across all questions. Overall, our
conclusion from the user study was that notebook users found NBTest’s interface
intuitive and useful, and also appreciated the usefulness of NBTest’s generated
assertions.

One participant commented,
“When I used Jupyter Notebooks to write
ML-related code, I often ran into inexplicable errors or couldn’t tell which
cell execution had overwritten a value. Having this tool makes it easy to
reliably validate the correctness of my data”
. Another participant appreciated
the generated assertions, saying:
“… I also really like this idea,
because sometimes I want to check whether my code is correct, and I’m too lazy
to manually write tests …”
. The participants also suggested many
improvements/features such as, interactive view of test results based on
code-diffs, generating assertions for a subset of dataset columns instead of all
(which is the default behavior of NBTest), and integrating the assertion
generator in JupyterLab. Two participants asked whether NBTest could be made
available as a VSCode plugin. Two participants suggested extending NBTest to
support more types of assertions. Another two participants recommended adding
inter-procedural assertions and providing explanations for the generated
assertions. Another participant pointed out that they would need to check both
the generated assertions and their code for correctness, and they wondered if
it’s possible to generate assertions that are based on the correct expected
output. Currently, NBTest’s generated assertions are regression-based. However,
in the future, we plan to consider these suggestions to improve NBTest, such as
incorporating property-based oracles.

7.
Discussion and Future Work

Limitations.

While our assertion APIs can be used by any Jupyter Notebook user, our assertion
generation technique focuses on ML-related components such as datasets, models,
and performance metrics. Hence, it may not be useful for other domains yet. Our
assertion generation relies on regression oracles, hence, they are unaware of
the expected correct outputs. In the future, we plan to integrate property-based
oracles for data and training validations.

Threats to Validity.

(1) Internal:
The internal threat comes
from the implementation of NBTest. To address this threat, multiple co-authors
carefully performed testing and code reviews to check that it was correctly
implemented.

(2) External:
The main external threat comes from our studied
notebooks. Since our findings are based on ML-focused notebooks, they may not
generalize to non-ML workflows. However, generalization beyond ML workflows is
beyond the scope of this work. Also, the studied notebooks might be limited to
the covered ML domains and frameworks. To mitigate this, we selected notebooks
from popular Kaggle competitions and included as many executable notebooks as
possible.

(3) Construct:
Mutants may not be representative of real bugs. To
mitigate this, we choose the version of notebooks in Kaggle notebooks, which
also shows slightly lower but still good mutation scores. To mitigate risk due
to non-determinism, we run the notebooks multiple times and use statistical
measures to compute passing rates and mutation scores.

(4) Corpus:
Our evaluation focused on Kaggle competition
notebooks, which may limit the generalizability of our findings to notebooks
from other sources such as GitHub. We attempted to include GitHub notebooks but
faced significant challenges in installation, such as missing or outdated
dependencies, broken docker files, and unavailable external data files.
Such challenges have also been reported in prior work
(
Wang et al. 2021
)
.

Usability.

Too many assertions may clutter the notebook. To mitigate this problem, the current NBTest JupyterLab plugin
allows users to toggle the visibility of assertions using a side-by-side layout
(Figure
1a
). This functionality allows users to hide or show
assertions as needed, improving notebook readability and reducing visual
clutter. In our user study, this hide/show feature received an average score of

4.7
, highlighting its effectiveness. Moving forward, we plan to further refine
the NBTest user interface based on ongoing feedback from the community.

Future work.

(1) Generalizing to unseen ML libraries:

Currently, NBTest supports the three most popular ML libraries and can be easily extended to similar APIs as mentioned in Section
4.4.1
.
However, NBTest cannot directly support APIs whose semantics that differ substantially.
To bridge this gap, we plan to formulate assertion generation as conditional synthesis from API-usage context and train a model that maps context to assertion templates.

(2) Evolution of the generated assertions:

NBTest does not yet support evolution-aware assertion updates.
Currently, users need to re-run NBTest after notebook changes to re-generate assertions.
We plan to add evolution-awareness by detecting modified code cells, identifying affected cells,
and re-running only those cells to update assertions accordingly.

8.
Related Work

Static analysis of Jupyter Notebooks.

Yang et al.
(
Yang et al. 2022
)
proposed a static data-flow analysis technique
to detect data leakage bugs in Jupyter Notebooks. Drobnjaković et
al.
(
Drobnjaković et al. 2024
)
developed NBLYZER, an abstract
interpretation-based approach to prove the absence of data leakages in
notebooks. Liblit et al.
(
Liblit et al. 2023
)
identified six static
analysis rules to detect various defects in notebooks such as invalid execution
order of cells, and misuses of common deep learning library APIs. Unlike these
works, NBTest focuses on dynamic validation of Jupyter Notebooks that can
potentially detect regression bugs.

Dynamic analysis tools for Jupyter Notebooks.

Many prior techniques improve the executability and reproducibility of Jupyter
Notebooks. Snifferdog
(
Wang et al. 2021
)
automatically infers
correct library dependencies for Jupyter Notebooks.
Osiris
(
Wang et al. 2020
)
identifies possibly correct execution orders
of Jupyter Notebook cells that reproduce the correct results.
NBSAFETY
(
Macke et al. 2020
)
combines dynamic and static analyses to identify
unsafe cell executions, such as out-of-order executions, often caused by
interactive nature of notebooks. NBTest plays a complementary role to these tools
by automatically generating assertions that can detect regression bugs.

Empirical analysis of notebooks.

Robinson et al.
(
Robinson et al. 2022
)
performed an exploratory study to
observe how student users debug various issues in notebooks, and found a set of
seven debugging strategies with varying success rates. Chattopadhyay et
al.
(
Chattopadhyay et al. 2020
)
interviewed data scientists and software engineers
who use notebooks and identified several pain points, which included difficulty
in debugging and reproducibility of results. De Santana et al.
(
de Santana et al. 2022
)

analyzed numerous GitHub commits and StackOverflow posts to identify common
sources of bugs in Jupyter Notebooks. The assertions generated by NBTest can
potentially improve the quality and debuggability of notebooks by pinpointing
faulty code cells.

Bug Detection for Notebooks.
Prior work has targeted specific types of
bugs in Jupyter Notebooks,
such as name-value
inconsistencies
(
Patra and Pradel 2022
)
, data
leakage
(
Yang et al. 2022
;
Subotić et al. 2022
)
, and syntax or dependency
errors
(
Grotov et al. 2024a
;
Grotov et al. 2024b
)
. In contrast, NBTest uses a
regression-based oracle, but has the potential to detect a broader range of
bugs, as shown by our mutation analysis and experiments with Kaggle versions.

Assertion Generation.

Many machine learning-based techniques have been proposed for generating
assertions for unit
tests
(
Dinella et al. 2022
;
Watson et al. 2020
;
Tufano et al. 2020
;
Ibrahimzada et al. 2022
;
White and Krinke 2020
)
.
However, these techniques focus on simpler assertions for traditional programs
like Java. In contrast, in this work we focus on ML-specific assertions that
test data pre-processing, model training, and model evaluation steps in a
typical ML or data science pipeline – which prior tools do not support.

Python Test Generation/Analysis Tools.

Pynguin
(
Lukasczyk and Fraser 2022
)
is a unit test generation tool for Python.
However, it is a general tool and not specialized for machine learning programs
or Jupyter notebooks. Pynguin is unable to generate any meaningful tests even
when the notebook is converted to Python program. DyLin
(
Eghbali et al. 2025
)

detects general Python anti-patterns, and DynaPyt
(
Eghbali and Pradel 2022
)
offers
a flexible framework for building dynamic analyses for Python. In contrast,
NBTest automatically generates assertions to detect regression bugs in Jupyter
Notebook and accounts for ML randomness.

Inline Tests.

More recently, Liu et al.
(
Liu et al. 2022
;
Liu et al. 2023
)
introduced a
new paradigm of testing, called
inline testing
, which executes tests at a
lower level of granularity (statement level) than unit tests. Inline testing
focuses on catching bugs in single-statement scenarios such as regular
expressions, bit manipulation logic, and string manipulations. Although NBTest primarily targets ML/data science programs written in notebooks, our motivation
is similar to inline testing in spirit – NBTest allows developers to write
intermediate or
cell-level
assertions instead of end-to-end tests.

9.
Conclusion

We presented NBTest, the first regression testing framework for Jupyter Notebooks that allows developers to write cell-level assertions. NBTest is specialized for machine learning-related notebooks, especially for assertion generation. Through mutation analysis and evaluating Kaggle notebook versions, we showed that NBTest can effectively detect many common classes of bugs.
We envision that our tool will encourage developers to adopt test-driven development of ML Notebooks.
NBTest has also been adopted by a popular machine learning library and integrated into its CI pipeline.
NBTest has the potential to enhaunce the reliability, reproducibility, and quality of ML notebooks.
