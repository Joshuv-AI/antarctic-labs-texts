Abstract
Automated Code Review (ACR) is crucial for software quality, yet existing benchmarks often fail to reflect real-world complexities, hindering the evaluation of modern Large Language Models (LLMs). Current benchmarks frequently focus on fine-grained code units, lack complete project context, and use inadequate evaluation metrics. To address these limitations, we introduce SWR-Bench , a new benchmark comprising 1000 manually verified Pull Requests (PRs) from GitHub, offering PR-centric review with full project context. SWR-Bench employs an objective LLM-based evaluation method that aligns strongly with human judgment ( ∼ \sim 90% agreement) by verifying if issues from a structured ground truth are covered in generated reviews. Our systematic evaluation of mainstream ACR tools and LLMs on SWR-Bench reveals that current systems underperform, and ACR tools are more adept at detecting functional errors. Subsequently, we propose and validate a simple multi-review aggregation strategy that significantly boosts ACR performance, increasing F1 scores by up to 43.67%. Our contributions include the SWR-Bench benchmark, its objective evaluation method, a comprehensive study of current ACR capabilities, and an effective enhancement approach, offering valuable insights for advancing ACR research.

III
SWR-Bench

This section details our methodology for constructing the automatic code review benchmark.

III-A

Benchmark Construction

Fig. 2
:
The
SWR-Bench
construction pipeline.

The overall construction workflow of
SWR-Bench
is depicted in Figure
2
and detailed below.

Step 1: Source Data Collection and Initial Filtering

The foundation of
SWR-Bench
lies in real-world software development practices.
To ensure authenticity and relevance, we selected 12 popular and actively maintained open-source Python projects from GitHub. These projects align with those used in the widely recognized SWE-Bench
[
38
]
, ensuring their code quality and development practices are representative.
We utilized the GitHub API to crawl all historical pull requests from these projects, collecting comprehensive metadata for each PR. This included titles, descriptions, commit histories, code diffs, review comments, discussion threads, and final PR statuses (e.g., merged, closed).
From this raw collection, we performed initial filtering to refine the candidate pool. We excluded PRs without any review comments, as they lack the necessary interaction for our analysis. We also removed PRs with large-scale changes (e.g., exceeding predefined thresholds for file changes or lines of code) or those with rebase operations in their commit history. This is because extensive changes make it challenging for the LLM in the subsequent verification stage to correctly identify and label the change-points. Furthermore, rebase operations make it difficult to construct reproducible environments.
Finally, this initial filtering yielded 21,350 PRs suitable for the subsequent LLM verification phase.

Step 2: LLM-based Change-Points Verification and Classification

In this step, we employed a LLM to identify and extract “change-points” from the filtered PRs. A change-points represents a verifiable instance where a reviewer’s suggestion led to a subsequent code modification by the developer (as described in Section
II-A
).
We provided the LLM with the PR’s review discussion, commit messages, and diffs, instructing it to identify instances corresponding to the 11 predefined change-point types detailed in Table
I
.
To ensure high-quality annotations, we employed Gemini-2.5-Pro
[
39
]
, a state-of-the-art (SOTA) LLM, for the annotation process. Beyond this, we implemented a majority voting technique, making three independent requests to the LLM for each PR to further refine the results. A PR was considered for further processing only if all three requests yielded consistent change-points extraction results; otherwise, the PR was discarded. Then, based on the LLM’s output, PRs were classified into two categories: “
Change-PRs
”, which contain at least one identified change-point, and “
Clean-PRs
”, which have no identified change-point.

Step 3: Quality Enhancement through Filtering and Sampling

To further refine the dataset quality, we performed additional filtering and sampling.
First, we applied the SZZ algorithm
[
40
]
to identify instances where issues might have been missed by human reviewers during the original PR review but were fixed later. PRs containing such missed change-points were removed. This step ensures that the change-points in our
Change-PRs
were all addressed during the review process itself, and that our
Clean-PRs
are genuinely devoid of review-relevant issues that were overlooked at the time of review.

Next, to prevent ACR tools from distinguishing
Change-PRs
and
Clean-PRs
based on superficial statistical differences, we resampled
Clean-PRs
. This aligned their statistical properties (e.g., lines of code changed, number of commits) with those of
Change-PRs
, enabling a fairer assessment of ACR tools’ code understanding capabilities rather than their knack for exploiting statistical heuristics.

Step 4: Manual Verification and Refinement

After the preceding filtering and sampling steps, approximately 3,500 PRs remained. Given the significant effort required for manual annotation, we randomly sampled 1,000
Change-PRs
and 1,000
Clean-PRs
from this pool for rigorous manual verification. This manual review, conducted by five experienced graduate students majoring in computer science, and each PR was independently annotated by at least two annotators to ensure reliability. The review aimed to verify the accuracy of LLM-identified change-points in
Change-PRs
, ensuring they conformed to our definitions; and filter out
Change-PRs
containing only trivial changes (e.g., simple documentation typos, minor formatting) to focus the benchmark on more significant review interactions. This step was crucial for further enhancing the overall data quality and reliability of
SWR-Bench
.

Dataset Statistics

The final
SWR-Bench
dataset consists of 500
Change-PRs
and 500
Clean-PRs
, randomly selected from manually verified and corrected PRs. This balanced composition is vital for robustly evaluating ACR tools, particularly their false positive rate, a common critique of existing automated review systems
[
41
,
14
]
.

Each
SWR-Bench
instance provides comprehensive information for ACR tools evaluation. Specifically, an instance includes: (1) the complete source data of the PR (metadata, diffs, comments), (2) ground truth change-point information for
Change-PRs
(including type, description, and relevant commit sha), and (3) codebase checkpoint information, allowing for the reconstruction of the full PR codebase at the relevant commit. This latter feature is particularly important for agent-based ACR tools that require an interactive environment.

Table
II
presents the overall dataset statistics. We find that, on average,
Change-PRs
have similar numbers of modified files and lines of code compared to
Clean-PRs
. These similarities underscore the effectiveness of our resampling strategy (Step 3) in ensuring that
Clean-PRs
are not trivially distinguishable from
Change-PRs
based on such coarse-grained metrics.

Furthermore, we analyzed change-point type distribution (Figure
3
). In Raw-PRs (before manual verification and filtering), functional changes (e.g., logic errors, performance issues) constituted less than 15% of all identified changes, with a predominance of more evolvability changes like documentation or style adjustments. After our manual verification process, which explicitly filtered out PRs with only trivial change-points, the proportion of functional changes in
SWR-Bench
increased to 31.8%. This balancing ensures that the benchmark adequately represents more critical and harder-to-detect functional issues, providing a more comprehensive evaluation of ACR tools’ capabilities.

III-B

Evaluation Methodology

Evaluating the output of ACR tools presents unique challenges. The report generated by a model is typically unstructured natural language text, containing various comments, or identified issues. Directly comparing this with a structured list of ground truth change-points is difficult.
As discussed (Section
II
), traditional text similarity metrics fail to capture semantic accuracy and practical value in code review comments
[
21
,
22
]
. Consequently, we turn to solutions utilizing large language models as evaluation aids (LLM-as-Judge)
[
37
,
20
]
. However, we also recognize that traditional LLM-as-Judge methods often rely on the LLM’s subjective judgment (e.g., scoring comment quality), which can introduce bias and inconsistency
[
42
,
43
,
19
,
44
]
. To mitigate this, we designed an objective LLM evaluation framework that leverages ground-truth change-points referencing. Instead of subjective scoring or ranking, our LLM performs a fact-based matching task: determining if issues in the model’s report correspond to predefined ground truth change-points.

Fig. 4
:
The objective LLM-based evaluation pipeline for predicted review report.

Our evaluation process, depicted in Figure
4
, unfolds as follows:

The inputs to the evaluation pipeline are the code review report generated by the ACR tool and the corresponding ground truth change-points from our
SWR-Bench
.
First, an evaluation LLM parses the ACR tool’s unstructured report to extract distinct predicted change-points. For each predicted change-point, the LLM is also prompted to determine its
change-type
(from 13 types in Table
I
) and assign a
severity-score
(e.g., on a scale of 1-10, from minor to critical). These latter two are subjective LLM assessments but provide useful metadata about the review report.

Next, the core objective evaluation involves the LLM performing a matching task. It compares each extracted predicted change-point against the PR’s set of ground truth change-points. The LLM determines, for each ground truth change-point, whether it has been successfully “hit” (i.e., semantically identified) by one or more predicted change-points.

Based on this explicit matching information, we can define
TP
,
FP
, and
FN
. These definitions then enable the straightforward calculation of standard performance metrics like
Precision=\frac{TP}{TP+FP}
,
Recall=\frac{TP}{TP+FN}
, and
F1=2\times\frac{Precision\times Recall}{Precision+Recall}
:

•

True Positives (TP)
:
Ground-truth change-points successfully hit by at least one predicted change-point.

•

False Positives (FP)
:
The number of predicted change-points that do not hit any ground truth change-point.

•

False Negatives (FN)
:
The number of ground truth change-points not hit by any predicted change-points.

Furthermore, as discussed in Section
III-A
, functional changes constitute a critical, but smaller portion of the change-points in
SWR-Bench
. To provide a more nuanced understanding of an ACR tool’s ability to detect these functional issues, we report performance metrics (
Precision
,
Recall
, and
F1
) specifically for functional changes in addition to the overall metrics. This specialized calculation considers only predicted change-points that the evaluation LLM has typed as functional change and ground-truth change-points with functional type.

In summary, our key evaluation metrics include overall
Precision
,
Recall
, and
F1
for all change-points, and the specific
Precision
,
Recall
, and
F1
for functional change-points. We also report descriptive statistics such as the average number of predicted change-points per PR and the average LLM-assigned severity score for the predicted report. This objective, ground-truth-referenced LLM evaluation approach allows for a more accurate and in-depth assessment of ACR tools, overcoming traditional method limitations. The reliability of this evaluation approach is further validated through manual verification in later experiments.

IV-B

Subjects of Study

IV-B
1
Large Language Models (LLMs)

To comprehensively evaluate current LLMs on ACR tasks, we selected a diverse range of models, ensuring broad representation across families, sizes, and development sources (open- and closed-source). Our selection includes closed-source LLMs like the GPT series (o3-0416, o4-mini-0416, GPT-4o-1120), Gemini series (Gemini-2.5-Pro-0325, Gemini-2.5-Flash-0427), and Claude series (Claude-3.7-Sonnet-0219, Claude-4-Sonnet-0514, Claude-4-Opus-0514). We also include open-source LLMs such as DeepSeek series (DeepSeek-R1-0120, DeepSeek-V3-0324) and Qwen2.5 series (Qwen2.5-Chat-7B/14B/32B, Qwen2.5-R1-7B/14B/32B).
This diverse set allows assessment across the current proprietary and public technology landscape. Importantly, by including base and reasoning-enhanced versions for some models (e.g., Qwen2.5-Chat and Qwen2.5-R1), we can preliminarily investigate if reasoning enhancements directly benefit complex code review tasks.

IV-B
2
Automated Code Review (ACR) Baselines

For a comprehensive evaluation, we also benchmark against representative open-source ACR tools and methodologies:

1.

LLM-Review
(Simple Prompting Baseline): Our straightforward baseline directly feeds basic PR information (title, description, commit diff) via a prompt to an LLM to generate a review report, measuring baseline LLM review capabilities without specific strategies.

2.

SWR-Agent
(Agent-based Baseline): Also our construction, inspired by SWE-Agent
[
45
]
, this baseline adapts SWE-Agent’s task from program repair to code review. SWR-Agent receives PR information and uses tools to explore the codebase, execute snippets, and gather richer context for review decisions.

3.

CR-Agent

[
27
]
: A multi-agent ACR tool. In its review process, it employs two agents to detect format-related and functional related defects in a PR, respectively. The process involves inter-agent communication and debate to produce a more comprehensive code review report.

4.

Hybrid-Review

[
46
]
: Mirroring LLM-Review’s core, Hybrid-Review additionally feeds the LLM a static analysis report as supplementary context for a more informed review.

5.

PR-Review

[
28
]
: An open-source ACR tool from which we utilize only its component for generating code review reports. While similar to LLM-Review, PR-Review uses more sophisticated prompt engineering. Specifically, it first consolidates code diffs from multiple commits to form the input. When faced with context length limitations, it prioritizes files based on importance, potentially excluding less critical files (e.g., those with only line deletions). Finally, it instructs the LLM to output the review report in a specific structured format, categorizing suggestions into areas such as test-related defects, security-related defects, and other areas for improvement.

We acknowledge that some non-LLM models (such as earlier CodeReviewer
[
13
]
or T5-Reviewer
[
12
]
) are omitted due to their function/hunk-level focus and context limitations, making PR-level adaptation on
SWR-Bench
difficult. We also excluded works
[
14
]
that are not open-source, preventing consistent and reproducible evaluation. Furthermore, tools
[
16
,
17
]
requiring specific model training were also omitted, as we aim to evaluate ACR approaches that can utilize diverse leading LLMs as backends. This permits direct comparison of foundational model performance. An in-depth comparison with these types of methods, including non-LLM techniques, will be considered as future work.

To validate the accuracy of our LLM-as-Judge evaluation methodology, we conducted a human validation experiment. Specifically, we randomly selected 100 code review reports generated in RQ2. These 100 reports were then independently annotated by three human experts and two LLMs (i.e., Gemini-2.5-Pro and Gemini-2.5-Flash). All five evaluators utilized the same evaluation prompt and followed the task definitions (identifying “hit” for ground truth change-points, assigning change-points type and severity scores to predicted points) as detailed in Section
III-B
. We then calculated the agreement percentage among these five sets of evaluations across the 100 cases. Specifically, for discrete labels like “hit” and “change type”, agreement was counted when two evaluators provided the exact same label. For continuous severity scores (ranging from 1 to 10), agreement was established if the absolute difference between the two evaluators’ scores was 1 or less. The results are presented in three matrices:
Hit-Agreement
(Figure
5
a),
Type-Agreement
(Figure
5
b), and
Severity-Agreement
(Figure
5
c).

As shown in Figure
5
a, the
Hit-Agreement
, which is based on an objective binary criterion (hit/not hit), demonstrated substantial consistency across all five evaluators. The agreement levels between any two evaluators ranged from 89.2% to 94.9%. This high degree of concordance suggests that employing LLMs to evaluate the “Hit” aspect of code review reports is reliable and yields results largely consistent with human expert assessments. Consequently, the primary quantitative evaluation metrics in this study (i.e., overall and functional
Precision
,
Recall
, and
F1
) will be calculated based on this objective “Hit” indicator.

Furthermore, regarding
Type-Agreement
(Figure
5
b), the consistency between human experts and the LLM evaluators ranged from 69.4% to 94.8%. While this is not as uniformly high as the
Hit-Agreement
, it is noteworthy that the inter-human agreement also fell within a similar range from 67.4% to 83.6%. This suggests that classifying change-point types can involve a degree of inherent variability, even among human experts, potentially because some change-points may exhibit characteristics close to multiple change types, making precise categorization challenging
[
23
]
. Given that the LLM-human agreement is comparable to human-human agreement in this context, we consider this level of consistency in
Type-Agreement
acceptable for its use as an auxiliary metric in calculating functional
Precision
,
Recall
, and
F1
in our analysis.

For the agreement of“Severity Score” (Figure
5
c), which is inherently more subjective, was notably lower across all evaluator pairs, including human-human comparisons. This highlights the subjective nature of severity scoring, making it less reliable for consistent evaluation. Therefore, while severity scores are presented as supplementary information, our main conclusions are based on the objective “Hit” metric, complemented by the “Type” metric for functional analysis.

Ultimately, both Gemini-2.5-Pro and Gemini-2.5-Flash demonstrated commendable and similar agreement levels with human evaluators, particularly for the primary “Hit” metric. Given this comparable performance, and considering that a full
SWR-Bench
evaluation (evaluating all 1000 PRs) costs approximately $1.57 using Gemini-2.5-Flash, we select it for subsequent experiments due to its balance of strong performance and cost-effectiveness.

Conclusion 1

The objective LLM-as-Judge methodology that leveraging objective “Hit” metrics, demonstrates a high degree of accuracy and reliability for evaluating the quality of code review reports, closely aligning with human expert judgment.

Performance Analysis by ACR Tools

A more granular analysis of the
F1
scores (Table
III
) reveals distinct performance tiers among the ACR techniques. PR-Review, which leverages meticulous prompt engineering, achieved the best overall results, securing a mean
Overall\text{-}F1
of 18.73% and a
Functional\text{-}F1
of 23.87%. Following by SWR-Agent and LLM-Reviewer, both achieving mean
Overall\text{-}F1
scores of approximately 12%. In contrast, CR-Agent, which is based on multi-agent interaction, attained a lower
Overall\text{-}F1
score of only 9.22%. This suggests that employing multi-agent systems for code review tasks is highly challenging. As noted in prior work
[
47
]
, the interaction overhead and potential for error propagation among agents can render the task-solving process less controllable and more error-prone, ultimately leading to diminished
F1
scores. Separately, Hybrid-Review, which incorporates static analysis reports, yielded a significantly lower mean
Overall\text{-}F1
of just 4.48%. Its performance was severely hampered by exceptionally low precision, underscoring the challenge that raw static analysis outputs need more meticulous processing and careful integration to effectively enhance the ACR tools.

Moreover, comparing PR-Review and LLM-Reviewer, both of which operate via a single-turn interaction with the LLM, PR-Review’s superior performance can be attributed to its more sophisticated prompt engineering, these refinements appear to significantly reduce false positives, thereby enhancing precision and, consequently, the
F1
score.
Further insights can be drawn from the
Avg.\text{ }Count
. PR-Review reported the fewest points on average (1.49 per review), and these points also registered the highest
Avg.\text{ }Servity
(5.70). This indicates that PR-Review not only generates fewer suggestions but also tends to identify issues that are perceived as more critical.

Collectively, these results highlight that PR-Review, with its foundation in meticulous prompt engineering, demonstrates the most promising performance among the evaluated techniques. This underscores fine-grained prompt engineering as an effective strategy for enhancing ACR capabilities. Conversely, the agent-based approaches (SWR-Agent and CR-Agent) did not yield standout results in their current form, signaling a need for further research to refine agent architectures and interaction protocols to unlock their full potential in the ACR domain.

Conclusion 3

PR-Review, leveraging meticulous prompt engineering, achieves the best performance on
SWR-Bench
, underscoring the significant promise of prompt engineering for improving efficacy. Agent-based approaches, however, require further research to overcome current limitations.

To gain a deeper understanding of how ACR tools handle different types of change-points, we further analyzed the average performance of PR-Review across various change types defined in
I
. The results, disaggregated by change type, are shown in Table
V
.

A key observation is that PR-Review demonstrates significantly stronger detection capabilities for functional change-points compared to evolutionary change-points. Specifically, for the F.2 Logic change, PR-Review achieved an
F1
score of 26.20%, with most functional change types also yielding
F1
scores above 21%. In stark contrast, the highest
F1
score for an evolutionary change type, E.3.1 Organization, was merely 16.45%.

We hypothesize that this disparity arises from the inherent nature of these change categories. Evolutionary changes often represent optional or stylistic improvements, where the criteria for what constitutes a necessary change can vary significantly between human reviewers
[
23
]
and LLMs. For instance, with E.3.2 Solution Approach, which was the most prevalent evolutionary change type, one human reviewer might suggest an alternative implementation they deem superior, while another might find the current approach acceptable. Consequently, accurately detecting such optional evolutionary changes presents a considerable challenge.

Based on these findings, we recommend that future development of ACR tools prioritize enhancing the detection capabilities for functional changes to improve the precision for functional change-points. Furthermore, ACR tools could consider presenting reports for functional and evolutionary changes separately. Such an approach could significantly improve the usability and perceived value of automated code review reports by focusing developers’ attention on more critical and less subjective issues.

Conclusion 4

ACR tools demonstrate substantially better performance in detecting functional changes compared to evolutionary ones likely due to the subjective nature of many evolutionary changes. Accordingly, future ACR development could prioritize robust detection of functional changes to enhance practical utility.

Impact of LLMs and Reasoning Enhancement

Following PR-Review’s superior performance, we evaluated its efficacy on
SWR-Bench
with diverse LLMs, including variants with and without reasoning-enhancement training (Table
IV
).

Overall, LLM performance with PR-Review remains suboptimal for practical code review (highest
Overall\text{-}F1
19%). Within this context, we first noted a significant divergence: the LLM performance ranking on
SWR-Bench
does not consistently mirror trends observed in other SE benchmarks (e.g., SWE-Bench
[
38
]
and LiveCodeBench
[
48
]
). Claude-4-Opus and Sonnet underperformed their predecessor Claude-3.7-Sonnet on
SWR-Bench
. This discrepancy underscores
SWR-Bench
’s value in capturing unique code review challenges and speculatively points to a potential misalignment between current LLM training/optimization and code review’s specific demands, where overemphasis on other SE tasks might inadvertently reduce code review proficiency.

Turning to the impact of reasoning enhancement training, we found further nuances. Models like Gemini-2.5-Pro and DeepSeek-R1, known for their reasoning capabilities, generally performed better. The Qwen-2.5 series provided a clear illustration: its standard versions (without specific reasoning enhancement) yielded lower
F1

F1
of 15.95% (Qwen-2.5-R1-7B was an exception due to output formatting issues). This strongly suggests that reasoning-enhancement training is a crucial factor for improving LLM effectiveness in code review.

Conclusion 5

Current LLMs underperform for practical review on
SWR-Bench
; however, reasoning-enhanced models perform better, highlighting reasoning-enhanced as a crucial advancement path.

RQ3: How can the performance of automated code review tools be improved?

(a)

(b)

Overlap across multiple runs of the same model.

Venn diagrams illustrating the overlap of identified change-points.

While Conclusion 5 indicate that reasoning-enhanced LLMs perform better, the overall practical utility of current ACR approaches remains limited. This prompted a closer examination of the nature of LLM-generated reviews, particularly their reliability and consistency. Specifically, we questioned whether current LLMs provide stable and consistent feedback across different invocations or when compared to other models.

To investigate this, we conducted an analysis into the overlap of specific ground true change-points identified by different LLMs and by multiple runs of the same LLM using Venn diagrams (Figures
6(a)
and
6(b)
). This analysis revealed considerable variability and instability in the sets of successfully identified defects across these models and runs. Notably, for different LLMs only 36 successfully identified change-points overlapped (Figure
6(a)
), for the same LLM over five independent runs, only 27 successfully identified change-points overlapped (Figure
6(b)
). This low consistency suggests unstable detection for most change-points, implying significant randomness in LLM identification. While this variability might partly stem from the subjective nature of many evolutionary changes, it strongly indicates that LLMs’ current grasp of code review nuances may be superficial, with detections sometimes attributable to stochastic factors rather than deep comprehension.

This observed variability and the implied limitations of single-pass reviews directly motivated our exploration into whether integrating diverse review outputs could yield a more comprehensive and reliable final report. To this end, building upon PR-Review, we propose an enhanced approach named Multi-Review. The core idea is to execute PR-Review (or another ACR tool) multiple times on the same code change to generate several independent review reports. Subsequently, these reports are intelligently aggregated using an additional LLM call. This aggregation aims to: (1) improve recall by identifying high-confidence issues consistently flagged across multiple reviews, and (2) enhance precision by filtering out low-confidence or sporadically identified issues.

To validate Multi-Review’s efficacy, we conducted experiments on
SWR-Bench
, exploring two primary aggregation strategies: 1) Multi-Agg (aggregate results from multiple distinct LLMs) and 2) Self-Agg (employing the same LLM for multiple executions and aggregation).

Fig. 7
:
Performance of Multi-Review for varying numbers of aggregated reports (
n
).

We selected Gemini-2.5-Flash as a representative LLM to investigate the impact of aggregating varying numbers of review reports (
n\in\{0,1,3,5,10\}
, where
n=0
represents the baseline PR-Review without aggregation). The results, presented in Figure
7
, demonstrate a significant performance uplift with Multi-Review. Regardless of whether aggregating results from different models or multiple runs of a single model, the
F1
scores showed marked improvement. Specifically, Gemini-2.5-Flash with Self-Agg (
n=10
) achieved an
Overall\text{ }F1
of 21.91% (a 43.67% increase) and a
Overall\text{ }Recall
of 30.44% (a 118.83% increase). This larger gain in
Recall
indicates Multi-Review’s effectiveness in identifying more true defects. However, to further boost the
F1
score, enhancing
Precision
by reducing false positives is a key priority.

To further assess the generalizability of Multi-Review, we experimented with smaller, open-source LLMs from the Qwen-2.5 series (7B, 14B, and 32B). This was to investigate whether these models, particularly in resource-constrained scenarios, could achieve significant self-performance enhancement via Multi-Review. Indeed, Multi-Review consistently boosted
F1
scores for the Qwen series. Notably, Qwen-Chat-7B Self-Agg (
n=10
) improved its
Overall\text{ }F1
by 26.13% (to 14.67%), and Qwen-Chat-32B Self-Agg (
n=10
) enhanced its
Overall\text{ }F1
by 19.25% (to 16.41%). This performance elevation allowed their aggregated results to approach or even match the baseline PR-Review performance of some larger commercial LLMs.

In summary, our proposed Multi-Review method effectively elevates the performance ceiling of existing ACR tools by integrating diverse information and reducing review stochasticity, offering valuable insights for automated code review.

Conclusion 6

Multi-Review significantly boosts code review performance, by aggregating multiple review passes. This showcases the untapped potential of existing ACR tools/LLMs via smart integration.

V
Threats to Validity

Internal Validity.
Threats to internal validity mainly arise from potential bugs in our implementation and the accuracy of manual verification. To mitigate these threats, we have conducted a detailed review of the code, and our code has been made publicly available at
[
32
]
for independent verification.

External Validity.
Threats to external validity mainly arise from the LLMs, ACR tools, and the quality of the selected projects. To mitigate these threats, we chose representative tools based on an extensive literature review and selected 12 popular, well-maintained open-source GitHub projects.

Construct Validity.
The primary threat to construct validity centers on the accuracy and reliability of our objective LLM-based evaluation method. We mitigated this through human validation, which confirmed high consistency between our method’s results and human expert evaluations.

VI
Conclusions

This paper addressed critical limitations in existing automated code review benchmarks by introducing
SWR-Bench
, a novel benchmark featuring 1,000 real-world pull requests with full project context and an objective LLM-based evaluation. Our study on
SWR-Bench
revealed that while current LLM-based ACR systems generally underperform, they show better aptitude for functional error detection. To improve performance, we proposed and validated a multi-review aggregation strategy that significantly boosts
F1
scores.
SWR-Bench
, along with our findings and proposed enhancement, provides a more realistic platform and valuable insights for advancing practical ACR research and development.
