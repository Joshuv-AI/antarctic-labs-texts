The Promptware Kill Chain: How Prompt Injections Gradually Evolved Into a Multi-Step Malware
Ben Nassi, Bruce Schneier, Oleg Brodt

Abstract
The rapid adoption of large language model (LLM)-based systems—from chatbots to autonomous agents capable of executing code and financial transactions—has created a new attack surface that existing security frameworks inadequately address. The dominant framing of these threats as ”prompt injection”—a catch-all phrase for security failures in LLM-based systems—obscures a more complex reality: Attacks on LLM-based systems increasingly involve multi-step sequences that mirror traditional malware campaigns. In this paper, we propose that attacks targeting LLM-based applications constitute a distinct class of malware, which we term promptware , and introduce a five-step kill chain model for analyzing these threats. The framework comprises Initial Access (prompt injection), Privilege Escalation (jailbreaking), Persistence (memory and retrieval poisoning), Lateral Movement (cross-system and cross-user propagation), and Actions on Objective (ranging from data exfiltration to unauthorized transactions). By mapping recent attacks to this structure, we demonstrate that LLM-related attacks follow systematic sequences analogous to traditional malware campaigns. The promptware kill chain offers security practitioners a structured methodology for threat modeling and provides a common vocabulary for researchers across AI safety and cybersecurity to address a rapidly evolving threat landscape.



I
Introduction

Large language models (LLMs) have transformed how software systems process and act on information. Applications built on these models—from customer-facing chatbots to autonomous agents capable of browsing the web, managing calendars, executing code, and conducting financial transactions—now mediate critical functions across industries.
This expansion in capability has created a new attack surface, one that existing cybersecurity frameworks struggle to address.

Natural language is no longer merely the
interface
for interfacing with LLM, as it has become the malicious code itself.
The payload processed by the victim’s LLM is written in English, not C or assembly.
This class of attacks---where LLM-based systems are targeted by malicious ‘‘prompts’’ written in natural language---is commonly labeled as ‘‘prompt injection,’’

LLMs process all input (e.g., system prompts, user messages, retrieved documents) as undifferentiated sequences of tokens. No architectural boundary exists to enforce a distinction between trusted instructions and untrusted data, and no patch can resolve this inherent property of LLM architecture.

These attack patterns mirror the structure of traditional multi-step malware campaigns (e.g., NotPetya, Stuxnet, Mirai); yet the AI security community currently lacks a systematic framework for analyzing them.

II
Initial Access in Promptware

The initial conversations that framed LLM security have primarily been about prompt injection, a concept that was initially identified,
2
,
3
coined,
1
and then popularized in September 2022 that describes the act of tricking an LLM into carrying out malicious instructions encoded within its input data.

Prompt injection is the initial access phase of promptware kill chain execution, where the adversary inserts the malicious instructions into the context window of an LLM-based application. This stage exploits a fundamental architectural property of large language models: the inability to reliably distinguish between instructions from trusted entities and data from untrusted sources
[
9
]
.
All input to an LLM, whether system prompts, user messages, or retrieved documents, is tokenized and processed as a unified sequence. Because of this conflation, a user’s input containing text that resembles an instruction may be perceived as a new instruction in and of itself. From the model’s perspective, a malicious instruction comingled with user-supplied data is simply a sequence of tokens indistinguishable from legitimate instructions.
No native mechanism currently exists to reliably enforce a distinction between instructions and data.
This is not a bug amenable to patching; it is an inherent property of the architecture. This architecture flaw brings about prompt injection, poisoning the application’s execution context.

Guardrails represent the primary defensive response to this threat. Input filters, output classifiers, system prompt hardening, and safety fine-tuning attempt to detect and block injection attempts before they can hijack model behavior. However, guardrails operate at the application layer, not the architectural layer. They function as pattern-matching defenses against known attack signatures rather than as enforcement of a fundamental boundary between instructions and data. The underlying vulnerability remains: The LLM cannot inherently distinguish a legitimate instruction from a malicious one that has evaded the guardrail.
Consequently, there is no way to block prompt-injection attacks as a class
[
11
]
.
This creates conditions for zero-day prompt injection: prompts that bypass existing defenses because no signature or detection rule yet exists for them. The asymmetry favors attackers; defenders must anticipate and block all possible injection techniques, while attackers need only discover one that works.

II-A

Direct and Indirect Prompt Injection

Prompt injection attacks fall into two categories, based on the attacker’s relationship to the victim.

In
direct prompt injection
, the attacker is the user interacting with the LLM application directly, crafting input designed to bypass its guardrails. Early examples were trivial: “ignore previous instructions and do X instead”
2
,
3
[
7
]
. Direct prompt injection requires no special privileges; any user with access to the LLM’s input field can attempt it.
The success of the injection relies on the application’s guardrails, and how well the underlying LLM has been trained to resist injections.

Indirect prompt injection
inverts the threat model
[
4
]
and turns the user of the LLM application into the victim.
The attacker does not interact with the LLM application directly but instead embeds malicious instructions in content the LLM will later retrieve: webpages, documents, emails, and other data sources accessed via retrieval-augmented generation (RAG).
When a user queries the application, the poisoned content enters the context window and executes. Indirect prompt injection is more dangerous in practice. It scales independently of attacker effort: A single piece of poisoned content can compromise any user whose application retrieves it.

II-B

Multimodal Injection Vectors

As LLMs evolve into Multimodal Large Language Models that can natively process images, audio and video alongside text, the attack surface expands correspondingly.
Multimodal injection encodes malicious prompts in non-textual formats.
An image containing embedded text instructions, for example, can be processed by a vision-language model and executed, bypassing text-based input filters.
Research has demonstrated that such attacks can generalize across models, and could be applied in blackbox

https://blog.trailofbits.com/2025/08/21/weaponizing-image-scaling-against-production-ai-systems/

[
3
]
settings.
The implication is that content of any modality ingested by a multimodal application represents a potential injection vector.

II-C

Position in the Kill Chain

Initial access via prompt injection may establish an entry point to compromise the application’s context, but it does not guarantee successful exploitation.
Modern LLMs incorporate safety training designed to refuse harmful requests (alignment), and applications often deploy additional security measures such as input/output filtering.
Prompt injection breaches the context window perimeter. If the injected instructions request actions the model would perform anyway, initial access alone suffices. Otherwise, subsequent kill-chain steps determine whether the attacker can leverage that breach to achieve meaningful objectives.

III
Privilege Escalation in Promptware

Jailbreaking constitutes the privilege escalation phase of promptware. It refers to techniques that cause an LLM to bypass its safety training and perform actions it was designed to refuse. If prompt injection is the entry point into the application’s context, jailbreaking elevates the attacker’s capabilities afforded by the model.

The concept of privilege escalation in LLM systems differs from traditional computing. There are no user accounts or root access in the conventional sense. Instead, privilege refers to the model’s willingness to exercise capabilities it possesses but has been trained to withhold. Modern LLMs undergo alignment training—typically reinforcement learning from human feedback (RLHF)—to refuse requests deemed harmful, unethical, or outside acceptable use policies. These constraints function as a privilege boundary: The model
can
perform certain tasks but
will not
. Jailbreaking circumvents this boundary.

III-A

Distinguishing Jailbreaking from Prompt Injection

Prompt injection and jailbreaking are terms frequently used interchangeably but represent distinct steps of attack. Security researcher Simon Willison, who coined the term ‘‘prompt injection,’’ emphasizes the distinction:
7
7

7

https://simonwillison.net/2024/Mar/5/prompt-injection-jailbreaking/
prompt injection attacks applications built on LLMs by exploiting the concatenation of trusted and untrusted input, while jailbreaking attacks the models themselves by subverting their safety filters. In Willison’s framing, “if there’s no concatenation of trusted and untrusted strings, it’s not prompt injection.”

We adopt a related but operationally distinct framing. Rather than treating these as separate attack classes, we view them as different steps in a unified kill chain. Prompt injection achieves initial access: The attacker’s payload enters the LLM’s context. Jailbreaking achieves privilege escalation: The attacker bypasses constraints that would otherwise prevent unwanted activity. The two frequently co-occur—an indirect prompt injection may embed a jailbreaking payload that executes when retrieved—but they are conceptually and functionally distinct.

III-B

Evolution of Jailbreaking Techniques

Jailbreaking techniques emerged shortly after ChatGPT’s release in late 2022.

Instruction Overriding
. The first jailbreaking prompts exploited the model’s instruction-following behavior using naive requests to “Ignore previous instructions”
[
7
]
.

Social Engineering LLMs
.
Later, we have seen the appearance of prompts that are intended to social engineer the LLM. One example is persona-based attacks, such as the “Do Anything Now” prompt, which instructs the model to adopt an alternate persona unconstrained by safety guidelines
[
1
]
.
Another example is role-play attacks, which frame prohibited requests as fiction, asking the model to respond ”as a character” who would comply.

Evasion
. Since the appearance of the jailbreaking attacks, developers have improved the quality of input filters to detect jailbreaking prompts.
Consequently, new jailbreaking prompts in the form of encoding/obfuscated attacks (e.g., through ASCII art
[
5
]
, Unicode tag characters
[
8
]
, and dedicated suffixes
[
11
]
) were designed to bypass input filters while remaining interpretable to the model.

Universal
. Research has demonstrated that “universal” jailbreaks exist: optimized sequences of tokens that defeat safety training across multiple models with a single payload. Researchers used gradient-based optimization to automatically discover universal jailbreaks in the form of adversarial suffixes that are effective against ChatGPT, Bard, Claude, and other major models
[
11
]
.

Architectural Bypasses
. With the integration of agentic frameworks into chatbots, developers have started to add architectural mitigations to contain the damage in the case of poisoned context. Such mitigations include limiting the number of agents that can be executed in a single inference when untrusted data is incorporated into the context. In parallel, new techniques of delayed tool/agent invocation techniques appeared in promptware, causing agents to output data that contains instructions to execute a payload given a trigger in a future inference
[
8
]
.

All the abovementioned techniques share a common structure: They attempt to shift the model’s context such that safety constraints no longer apply.
The effectiveness of any particular jailbreak degrades over time as vendors update their models and filters, but the underlying vulnerability, that safety training and mitigations can be bypassed by sufficiently adversarial input, persists.

III-C

Position in the Kill Chain

Jailbreaking is the second step of the Promptware Kill Chain, comparable to a privilege escalation in a typical cyber attack scenario, where an adversary elevates their access from a low-privilege user account to one with more control over the system. Jailbreaking escalates the attacker’s privileges within the compromised LLM context. A successful jailbreak is the key to enabling persistence, lateral movements, and eventually the attack’s final goals.

IV
Persistence in Promptware

Persistence refers to techniques that allow malicious instructions to survive beyond a single inference, maintaining the attacker’s presence across multiple sessions or interactions. Without persistence, an attacker must reinject the payload for each interaction: a constraint that limits both scalability and impact. Traditional malware achieves persistence through mechanisms such as registry modifications, scheduled tasks, or bootkit installation. Promptware persistence typically exploits the data stores that LLM applications rely on: RAG databases, user-defined memories, and other stateful components. Accordingly, establishing persistence with promptware is inherently connected to the application architecture, especially with regard to the use of external data sources and any internal memory.

As LLM applications become increasingly stateful, remembering past interactions and drawing on external knowledge bases, they create new opportunities for attackers to embed persistant payloads. We distinguish two forms of persistence based on how the payload is reactivated: retrieval-dependent persistence, which relies on semantic similarity to surface the payload; and retrieval-independent persistence, which ensures the payload executes on every subsequent interaction.

IV-A

Retrieval-Dependent Persistence

The first demonstrated persistence mechanism for promptware exploited RAG architectures. In 2024, security researchers introduced Morris II, a worm capable of propagating through LLM-powered email assistants
[
2
]
. The attack used adversarial self-replicating payloads that were engineered to force the LLM to include a copy of the malicious instructions in its output.

The persistence mechanism works as follows. An attacker sends an email containing the self-replicating payload to a victim. The email is stored and indexed by the victim’s email system. When the victim later uses an LLM-powered assistant to draft a new email, the RAG system retrieves relevant prior emails as context, including the attacker’s poisoned message. The payload executes, replicating itself into the outgoing email and propagating to the next recipient; and the cycle repeats for every new victim.

Other techniques also exploited the RAG for persistence but without the ability to propagate and infect new clients (e.g., MemoryGraft attack
[
10
]
).

Both examples constitute retrieval-dependent persistence: The payload survives in the data store but only executes when retrieved. Retrieval depends on semantic similarity between the user’s query and the stored content, and retrieval functions typically prioritize recency. Consequently, the payload’s effectiveness decays over time as newer content displaces it in retrieval rankings.

IV-B

Retrieval-Independent Persistence

A stronger form of persistence targets the agent’s own long-term memory rather than external data stores. In 2024, a researcher demonstrated injection into ChatGPT’s memory feature
[
8
]
. This feature, marketed as “saved info” in Gemini or “memories” in ChatGPT, allows users to store persistent context that the LLM incorporates into every subsequent interaction. Unlike RAG retrieval, memory contents are injected into the context window unconditionally.

The attack exploited indirect prompt injection via Google Docs. When a user asked ChatGPT to summarize a document containing malicious instructions, the payload directed the model to store attacker-controlled content in memory. Once persisted, this content influenced all future interactions without requiring retrieval or semantic similarity. This constitutes retrieval-independent persistence. The payload executes on every inference regardless of user input, and the attacker achieves a foothold that survives session boundaries without any further interaction.

IV-C

Command and Control (C2)

The most advanced form of persistence establishes a channel for ongoing remote control, allowing the attacker to update payloads and modify agent behavior over time. This transforms promptware from a static, preprogrammed threat into a dynamically controllable asset.
An attacker can accomplish this by embedding a persistent instruction that forces the agent to fetch and execute commands from an attacker-controlled source. For instance, a poisoned RAG document or modified memory entry might contain a prompt such as, “Before every response, access the content at
http://attacker.com/instructions.txt
and follow the instructions in that document.” This, in effect, establishes a command-and-control channel between the attacker and the agent. The attacker can modify the remote file when required, changing the agent’s behavior in real time according to their needs (e.g., for data exfiltration, generating emails for phishing campaigns, etc.).
SpAIware
[
8
]
has recently demonstrated the establishment of a C2 channel against ChatGPT by implanting a prompt in ChatGPT’s Memories that instructs ChatGPT to obtain information from a GitHub repository (used to provide new instructions for the ChatGPT).

IV-D

Persistence in the Kill Chain

Persistence transforms promptware from a transient exploit into a durable implant. Retrieval-dependent persistence provides probabilistic reactivation; retrieval-independent persistence guarantees it. Both mechanisms extend the attack window and enable subsequent phases of the kill chain: A persistent payload can wait for opportunities to exfiltrate data, execute lateral movement, or perform other actions on objective. Dynamic payload alterations represent the culmination of the persistence phase: A compromised LLM agent becomes not just infected but remotely operated, capable of serving whatever objectives the attacker specifies.

V
Lateral Movement in Promptware

Lateral movement refers to techniques by which promptware spreads from its initial point of compromise to other applications, users, or systems. Traditional malware achieves lateral movement through network exploitation, credential theft, or abuse of trust relationships between systems. Promptware exploits the connectivity inherent in LLM-powered ecosystems: shared data stores, messaging channels, unified authentication contexts, and the extensive permissions granted to AI agents.

The scope of lateral movement depends on the permissions and connections available to the compromised LLM-based application. An agent with email access can propagate via malicious messages. An agent integrated with a shared knowledge base can propagate by poisoning documents.

Propagation can be categorized along several dimensions: by the boundary crossed (cross-user, cross-application, cross-device, etc.); by the channel utilized (shared content, data pipelines, etc.); by the mechanism employed (self-replication, permission exploitation, pipeline traversal, etc.). These dimensions are orthogonal; a single attack may cross boundaries, utilize various channels, and combine different mechanisms. We illustrate with a mechanism-based categorization.

V-A

Types of Lateral Movements

Self-replicating movement
occurs when promptware forces a compromised agent to embed copies of itself in outgoing content. The Morris II worm demonstrated this mechanism
[
2
]
. By injecting adversarial prompts that instruct a victim’s email assistant to include the payload in outgoing messages, the attack propagated to recipients whose assistants process the infected content.

This mechanism is effective because the payload travels within normal data flows. Messages originate from legitimate accounts, making them appear authentic to recipients and their agents. Any communications channel that may later be retrieved as LLM context, such as emails, collaborative documents, messaging platforms, calendar invitations and shared knowledge bases, constitutes a potential propagation vector. A single successful injection can thus compromise multiple users, shifting the effective infection rate from 1:1 to 1:n.

Permission-based movement
occurs when promptware exploits an agent’s elevated or unified permissions.
Researchers demonstrated this mechanism against Google Gemini-powered Android Assistant
[
6
]
. The attack used indirect prompt injection via a calendar invitation as the initial access vector. Because the assistant holds extensive OS-level permissions, the injected payload could act on applications far beyond the calendar: controlling smart home devices, initiating video surveillance through Zoom, and exfiltrating emails via the Chrome browser. The initial compromise of a single integration cascaded across the device’s entire capability surface.

Permission-based movement scales with privilege. A narrowly scoped assistant limits damage to its designated function, while unrestricted agents potentially expose every connected service.

Pipeline-based movement
occurs when promptware traverses data flows, exploiting the fact that the output of one task becomes the input of another. It exploits implicit trust between integrated systems.
Researchers demonstrated this mechanism with AgentFlayer,
8
8

8

https://labs.zenity.io/p/when-a-jira-ticket-can-steal-your-secrets
an attack against the AI-powered code editor Cursor. The attack exploits a common enterprise workflow. Support tickets from external systems like Zendesk automatically sync into Jira, which developers query through Cursor’s MCP integration. An attacker submits a poisoned support ticket containing an injected payload. The ticket flows through Zendesk into Jira, where it persists as a seemingly legitimate ticket. When a developer asks Cursor to summarize open tickets, the payload enters the context window. When the auto-run mode is enabled, the payload is executed; this forces Cursor to search the repository and local file system, locate sensitive credentials, and exfiltrate them to attacker-controlled domains. In this example, pipeline-based movement exploited a pathway that can span from external customer-facing systems to internal development environments.

The vulnerability extends beyond enterprise MCP deployments to consumer-facing AI browsers. Researchers demonstrated similar attacks against Comet, Perplexity’s AI-powered browser, where malicious instructions in a GitHub issue directed the browser’s AI agent to access the user’s Gmail session and post private email content back to the public issue.

V-B

Lateral Movement in the Kill Chain

Lateral movement in promptware illustrates that the security implications of AI-based applications extend far beyond the applications they directly interface with. All forms of lateral movement in promptware exploit a common architectural pattern: LLM applications are granted broad access to data and capabilities to maximize their utility, but these very cross-boundary integrations that make AI applications useful become a liability when the application is compromised.

VI
Actions on Objective in Promptware

Actions on objective represent the final phase of the promptware kill chain: the malicious outcomes an attacker achieves. Traditional malware actions on objective include data exfiltration or destruction, ransomware deployment, cryptomining, and system destruction. Promptware actions on objective—and the severity of the outcomes—are shaped by the permissions and integrations of the host application and the capabilities accessible to the compromised LLM application. An LLM-powered email assistant can exfiltrate correspondence; an assistant with smart home access can affect the physical environment; and an agent with code execution capabilities can achieve outcomes equivalent to traditional remote code execution.

VI-A

Evolution of Attacks

The impact of promptware has escalated in parallel with the capabilities granted to LLM applications.

Safety impact
. Early promptware attacks against chatbots aimed to output information the model was trained to refuse: instructions for illegal activities (e.g., to create a bomb), harmful content (e.g., to curse a user), or methods to circumvent usage policies.
The security impact was limited, as such information was generally otherwise accessible.
The LLM merely provided a more convenient interface to such information.

Data exfiltration.
Simon Willison has characterized the preconditions for data exfiltration in LLM-based applications as the ‘‘Lethal Trifecta’’: access to sensitive data, exposure to untrusted content, and the ability to communicate externally.

https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/
When an agentic application satisfies all three conditions (as most productivity-oriented AI assistants do by design) data exfiltration becomes a matter of crafting an effective payload rather than overcoming architectural barriers.
Such examples were demonstrated against LLM-powered email assistants

.
We have also seen improved exfiltration variants with persistent exfiltration channels that activate on every subsequent inference in ChatGPT

leverage promptware’s access to trusted communication channels.
An attacker who compromises an LLM-powered email assistant can craft messages that originate from the victim’s account, imitate the victim’s writing style, and reference genuine prior correspondence.
The recipient has no reliable means of distinguishing the attacker’s message from legitimate communication. Similarly, attackers can use compromised assistants to distribute malicious URLs through trusted internal channels.

becomes possible when LLM assistants control real-world systems. Researchers demonstrated promptware that opened windows, activated water heaters, and disabled lighting in victims’ homes by exploiting the Google Assistant’s integration with smart home devices

Financial impact
. A trivial example of financial impact emerged as LLMs were integrated into commercial workflows.
In late 2023, an attacker manipulated a ChatGPT-powered chatbot deployed by a car dealership into agreeing to sell a vehicle for one dollar.

A more serious financial impact occurred in early 2025, when an attacker compromised AiXBT, an AI-powered cryptocurrency trading agent, by gaining access to its dashboard and queuing malicious commands.

represents perhaps the most severe outcome. Agentic systems with access to terminals, code interpreters, or development environments can be manipulated to execute attacker-supplied code.

VI-B

Position in the Kill Chain

Actions on objective represent the attacker’s ultimate goal; all prior kill-chain steps serve to enable these final outcomes. The severity of these outcomes is bounded by the capabilities of the compromised application, determined by three interrelated factors: tool access, permission scope, and automation level.

Tool access defines the attack surface. A standalone chatbot with no external integrations limits the attacker to manipulating text output, while an assistant with email, calendar, file system, and API access provides a correspondingly larger surface for exploitation. Permission scope determines the damage potential within that surface.
An agent limited to provide financial information cannot cause a financial impact, whereas an agent with transaction signing authority can transfer funds.
Automation level governs the damage probability: Human-in-the-loop designs require user confirmation before executing actions, while fully autonomous agents operating without oversight represent the maximum-risk configuration.

These factors interact to determine risk. An application with limited tool access and mandatory human confirmation presents lower risk than a fully autonomous agent with financial transaction authority, regardless of whether either is vulnerable to prompt injection at the initial access phase.

The complete kill chain has already been demonstrated in several recent studies (see Table
I
).
For example, in Invitation Is All You Need
[
6
]
, attackers achieved initial access by embedding a malicious prompt in the title of a Google Calendar invitation.
The prompt then leveraged an advanced technique known as delayed tool invocation to coerce the LLM into executing the injected instructions.
Because the prompt was embedded in a Google Calendar artifact, it persisted in the long-term memory of the user’s workspace.
Lateral movement occurred when the prompt instructed the Google Assistant to launch the Zoom application, and the final action on objectives involved covertly live-streaming the unsuspecting user who had merely asked about their upcoming meetings.

Similarly, Here Comes the AI Worm
[
2
]
demonstrated another end-to-end realization of the kill chain.
In this case, initial access was achieved via a prompt injected into an email sent to the victim.
The prompt employed a role-playing technique to compel the LLM to follow the attacker’s instructions.
Since the prompt was embedded in an email, it likewise persisted in the long-term memory of the user’s workspace.
The injected prompt instructed the LLM to replicate itself and exfiltrate sensitive user data, leading to off-device lateral movement when the email assistant was later asked to draft new emails.
These emails, containing sensitive information, were subsequently sent by the user to additional recipients, resulting in the infection of new clients and a sub-linear propagation of the attack.

AgentFlayer

Initial Access leverages a common enterprise workflow: external support requests arrive via Zendesk and get synced into Jira, letting attacker-controlled text enter an internal system. The poisoned ticket then persists in Jira until a developer asks Cursor to summarize or help triage open tickets (Persistence), at which point the payload enters the context window. Instead of explicitly requesting ”API keys,” the payload asks for ”apples,” defined as long strings starting with ”eyJ.” Privilege Escalation occurs when this obfuscation jailbreaks Cursor’s safety training, inducing the agent to carry out actions it would normally refuse. Once activated, the instructions abuse Cursor’s existing tool permissions to traverse connected context - repo and (if available) local files - beyond the original ticketing system (Lateral Movement). With auto-run enabled, Cursor may execute the tool calls without interactive approvals: locating credentials and exfiltrating them to attacker-controlled domains via web requests. (Actions on Objective). The developer doesn’t need to click a suspicious attachment or run a downloaded binary; the trigger can be a routine ”summarize this ticket” request, and the exfil can occur inside normal-looking agent activity.

VIII
Conclusion

The emergence of promptware as a distinct threat class demands a corresponding evolution in how the security community conceptualizes, analyzes, and defends against attacks on LLM-based systems. The kill-chain framework presented in this paper offers three contributions to that effort.

First, it provides analytical clarity. By dissecting attacks into familiar steps (Initial Access, Privilege Escalation, Persistence, Lateral Movement, and Actions on Objective), the framework reveals that many incidents, simplistically viewed as prompt injection exploits, are in fact multistep campaigns with distinct defensive intervention points. A RAG poisoning attack that establishes persistence differs fundamentally from a direct jailbreak attempt, even if both begin with malicious input entering the context window. Recognizing these distinctions enables better threat modeling.

Second, it enables systematic risk assessment. The framework allows practitioners to evaluate LLM applications not merely by their susceptibility to prompt injection, but by their exposure across the full kill chain. An application vulnerable to initial access but lacking persistence mechanisms, lateral movement pathways, or high-impact action capabilities presents lower risk than one that enables all five stages.

And third, it establishes a common vocabulary. The AI and cybersecurity research communities have historically operated with different terminologies. Framing promptware through the lens of established kill-chain methodology creates a bridge between these communities. Security practitioners familiar with traditional malware analysis can apply their expertise to LLM threats, while AI researchers can leverage decades of defensive thinking from the cybersecurity domain.

The framework also reveals uncomfortable realities. The inability to distinguish instructions from data admits no known comprehensive solution at the time of this writing. Guardrails typically operate as pattern-matching defenses that sophisticated attackers can bypass; alignment training can be subverted by adversarial inputs; application-layer controls cannot enforce boundaries the underlying model does not recognize. Therefore, thinking in terms of a kill chain becomes essential: Assuming initial access will occur, practitioners must focus on limiting privilege escalation, preventing persistence, constraining lateral movement, and minimizing the impact of actions on the objective.
