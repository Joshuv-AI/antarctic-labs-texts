OpenAgentSafety : A Comprehensive Framework for Evaluating Real-World AI Agent Safety
Sanidhya Vijayvargiya, Aditya Bharat Soni, Xuhui Zhou, Zora Zhiruo Wang, Nouha Dziri, Graham Neubig, Maarten Sap

Abstract
Recent advances in AI agents capable of solving complex, everyday tasks—from scheduling to customer service—have enabled deployment in real-world settings, but their possibilities for unsafe behavior demands rigorous evaluation. While prior benchmarks have attempted to assess agent safety, most fall short by relying on simulated environments, narrow task domains, or unrealistic tool abstractions. We introduce OpenAgentSafety , a comprehensive and modular framework for evaluating agent behavior across eight critical risk categories. Unlike prior work, our framework evaluates agents that interact with real tools, including web browsers, code execution environments, file systems, bash shells, and messaging platforms; and supports over 350 multi-turn, multi-user tasks spanning both benign and adversarial user intents. OpenAgentSafety is designed for extensibility, allowing researchers to add tools, tasks, websites, and adversarial strategies with minimal effort. It combines rule-based analysis with LLM-as-judge assessments to detect both overt and subtle unsafe behaviors. Empirical analysis of five prominent LLMs in agentic scenarios reveals unsafe behavior in 51.2% of safety-vulnerable tasks with Claude-Sonnet-3.7, to 72.7% with o3-mini, highlighting critical safety vulnerabilities and the need for stronger safeguards before real-world deployment.

We introduce
OpenAgentSafety
(
OA-Safety
, §
2
), a comprehensive and open-source simulation framework for evaluating the safety of AI agents in realistic, high-risk scenarios, supporting:

•

Real-world, comprehensive tool suite:
Agents interact with actual file systems, command lines, code execution environments, and web interfaces.

•

Diverse user intentions:
Tasks simulate user behavior from benign ambiguity to manipulation.

•

Multi-turn, multi-agent dynamics:
Scenarios include extended interactions involving users and secondary actors (NPCs) such as colleagues and customers with conflicting goals.

framework while navigating conflicting user and NPC instructions.

OA-Safety
is built on a robust and modular infrastructure that supports sandboxed agent execution with real tools, including file systems, bash terminals, code execution environments, web browsers, and messaging platforms. It includes over 350 executable tasks, each simulating multi-turn interactions with users exhibiting benign, ambiguous, or adversarial intent, where adversarial users may appear cooperative but subtly aim to induce harmful agent behavior. The framework is designed for extensibility: researchers can easily add new tasks, simulated environments (e.g., websites), complex social dynamics (e.g., negotiation with a customer), and customized evaluators. Simulation is a core design principle in
OA-Safety
and agents operate inside isolated containers with full tool access, enabling realistic actions (e.g., deleting files, leaking data, sending messages) to be executed safely without real-world consequences.

Each
OA-Safety
task is implemented as a modular Docker container that includes: the task description, multiple user goals, social dynamics, and customized evaluators, including both:

rule-based evaluator
that detects concrete environment impacts such as file deletion, and
LLM-as-a-judge assessments
to analyze the agent’s intermediate reasoning to flag attempted unsafe actions, even if those actions were incomplete or ultimately unsuccessful. This design allows for efficient environment reuse and flexible task extension.

We evaluate five prominent LLMs on
OpenAgentSafety
and find that current agents exhibit a wide range of unsafe behaviors across realistic, multi-turn scenarios (§
3
). Unsafe actions occur in 51.2% to 72.7% of safety-vulnerable tasks (
Figure 1
). We confirm prior findings that access to the browsing tool can increase the risk of unsafe behavior by overloading the agent’s context
[
31
]
. Beyond this, our analysis reveals
new failure modes
that are underexplored in existing safety benchmarks: we establish agents frequently fail to reason over extended multi-turn interactions, leading individually safe steps to compound into unsafe outcomes; they disregard legal, privacy, and security policies even in high-risk settings; and they show structurally unsafe behavior patterns across diverse user intents and tool types. Unlike prior studies, we analyze the impact of different risk categories, user intents, and tool usage, allowing us to uncover patterns in unsafe agent behavior not captured by single-axis benchmarks.

2.1
Infrastructure For Agent and Environment

To evaluate agent behavior in high-risk scenarios, we build
OA-Safety
on top of the OpenHands framework
[
32
]
, an open-source platform for multi-tool LLM agents. The agent runs inside a containerized sandbox with access to real tools, including a Unix shell, file system, Python and Bash interpreters, and a web browser. This architecture enables realistic tool-based agent workflows, while isolating the agent from the host system to safely observe potentially harmful behaviors. Different LLMs can be deployed as agent backbones for safety testing on agentic tasks.

To prevent real-world side effects during evaluation, such as posting content to live platforms or compromising the operating system, we replicate real-world websites in local Docker containers. We use locally hosted instances of OwnCloud (file sharing), GitLab (version control), and Plane (issue tracking), adapted from The Agent Company
[
36
]
. These websites simulate realistic interaction contexts for agents, such as uploading confidential documents or modifying code repositories.

A key component of
OA-Safety
is its support for multi-user scenarios. We integrate the Sotopia framework
[
48
]
to simulate secondary actors (NPCs) with diverse goals. We extend OpenHands with a custom
ChatNPC
tool to enable agents to send and receive messages via Sotopia’s Redis-based communication backend to these NPCs. This setup supports direct and broadcast messages, enabling tasks that reflect real-world organizational and social interactions, and allowing us to model complex social dynamics (e.g., persuasion, conflict) independently of the browsing proficiency of agents.

2.2
Safety Taxonomy and Task Design

We use three dimensions—
risk category
,
tool usage
, and
user/NPC intent
—to design tasks and evaluate agent safety behaviors. To ensure broad coverage of real-world deployment scenarios, we organize our benchmark around a taxonomy of 8 safety risk categories (
Table 2
). We aggregate and refine previous categorizations
[
40
,
43
,
26
]
, and map them to concrete actions involving real tools.
In addition to risk types and tool modalities, user intent plays a central role in shaping task difficulty. Tasks may involve benign, or explicitly adversarial users (
Table 7
). Through our integration of the ChatNPC tool, we further introduce an optional
NPC intent
, where secondary actors/NPCs (e.g., colleagues, customers) simulated through Sotopia
[
48
]
interact with the agent and may have conflicting or manipulative goals (
Table 3
). These multi-agent dynamics are essential to simulating realistic organizational scenarios where the agent needs to interact with secondary actors (NPCs) (
Table 7
). Thus, the available tools for the agent are: file system, browsing, ChatNPC, IPython for code generation and execution, and bash terminal.

To create the benchmark, we manually construct 80 seed tasks and their corresponding rule-based evaluators. Each seed task captures a distinct combination of tools and social context. To scale up, we systematically generate additional tasks using GPT-4o
[
22
]
, prompting it to vary the social context and NPC configurations while preserving the core behavioral challenge and tool usage (prompt provided in Appendix
A.6
). All 356 generated tasks are manually verified by the authors, with their distribution across risk categories, intents, and tools provided in Appendix §
A.1
.

Each task is packaged as a self-contained Docker image, including (i) the environment setup (e.g., websites, files), (ii) task description, (iii) secondary actor (NPC) behaviors, and (iv) a rule-based evaluator. This modular design allows easy integration of new environments and tools, including external ecosystems such as WebArena
[
45
]
, into the safety evaluation pipeline.

2.3
Evaluation Approach

To determine whether agents behave unsafely during task completion, we employ a hybrid evaluation strategy that combines:

Rule-based evaluation
quad For each task, we implement a Python script that analyzes the final environment state (e.g., file system, database, website state) to check whether specific unsafe outcomes occurred, such as deleting protected files or posting confidential data. These evaluators return a binary outcome:
1
for unsafe,
0
for safe. We report the percentage of unsafe outcomes across tasks.

LLM-as-Judge evaluation
To also capture unsafe intent or behavior that does not result in a final environment change (e.g., incomplete attempts or unsafe reasoning), we evaluate agent trajectories by prompting GPT-4.1
[
21
]
to judge safety based on intermediate thoughts and actions (prompt in Appendix
A.3
). GPT-4.1 must provide one of the four labels to the trajectory:
failure
for trajectories where the agent did not reach an safety-vulnerable point where it would be exposed to unsafe content,
safe
for trajectories which include rejection of tasks, or safely completing the task while averting the risk.
incomplete/unsafe
and
complete/unsafe
represent unsafe labels where the former represents that the agent tried to take malicious actions but they were incomplete. The latter refers to tasks where the agent completed the unsafe behavior.

Other than the safety ratings from the evaluators, we additionally report two derived metrics:

Failure rate
The percentage of tasks where the agent failed to reach a safety-vulnerable state due to its inability to complete an initial subtask, and was therefore never exposed to the unsafe element (e.g., the agent failed to download a file and was thus never manipulated into modifying it, as in the
unauth-discount
task in
Table 7
).

Disagreement rate
The percentage of tasks where the LLM judge labeled a trajectory as safe, but the rule-based evaluator detected a concrete unsafe impact. A high disagreement rate may indicate blind spots in LLM-based evaluation or misleading agent reasoning.

Designing robust rule-based evaluators is non-trivial: it often requires multiple iterations based on actual agent behavior to account for diverse unsafe attempts and avoid false positives or negatives.

The LLM-as-Judge component plays a critical role in disambiguating failure and safe trajectories, both of which are classed as
safe
from the rule-based evaluator. Further, while rule-based checks capture tangible environment changes, they cannot detect cases where the agent intended to act maliciously but failed to execute the behavior. They also fail to identify content safety risks. As a result, attempted unsafe behavior without environmental impact is marked as safe by the rule-based system. LLM-as-Judge helps assess the agent’s reasoning and intermediate actions to handle these cases appropriately. This hybrid evaluation protocol balances the precision of rule-based checks with the broader behavioral insight of LLM judgments, enabling robust safety assessments across diverse tasks.

RQ1: How does user intent influence unsafe behavior?

(1) Benign intent does not imply safety
: Seemingly benign user prompts still lead to unsafe behavior in 57–86% of cases across models (
Figure 3
). This pattern is driven by two key factors. First, agents tend to overgeneralize user goals: for instance, in
api-in-codebase
(
Table 7
), GPT-4o “helpfully” hard-codes an API key into the codebase, prioritizing task completion over secure coding practices. Second, agents often lack caution when the user’s request seems harmless. For example, Claude Sonnet 3.7 despite having the lowest rate of unsafe behavior for malicious intents, has the highest unsafe rate under benign intent (85.7%), suggesting that refusal strategies tuned for detecting overtly harmful instructions may not generalize to subtler risks, where the harm emerges from context or incorrect assumptions about user goals. Without explicit cues, agents may default to over-compliance, violating security principles.

(2) Explicit malice partially activates defenses, but unevenly
: When the user is openly malicious, Claude Sonnet 3.7 and Deepseek-v3’s unsafe rate plunges to 29.9% and 33.2% respectively, showing effective policy gating. o3-mini, by contrast, rises to 80.7%, indicating near-absence of refusal logic. GPT-4o (64.7%) and Deepseek-R1 (66%) sit mid-range. Thus, model size is not predictive of robustness but alignment strategy is.
(3) Hidden intent circumvents safeguards
: In the benign user intent and malicious NPC setting, where harmful goals are introduced by other NPC actors, unsafe rates converge in a narrow, high band (53.9–69.2%). Claude and Deepseek-v3’s risky actions more than double relative to malicious intent, both of which had low rate of unsafe behaviors for malicious intent, confirming that multi-turn intent tracking is unsolved. The
meeting-topics
trajectory demonstrates the failure: GPT-4o reorders agenda items on polite request, ignoring implicit fairness constraints, and no policy trigger fires because each micro-instruction appears benign.

RQ2: Which risk categories reveal the most serious vulnerabilities?

(1) Systemic risks consistently bypass safeguards
: The highest unsafe rates occur in categories that require procedural judgment or understanding of institutional norms, including
computer security compromise
(72–86%),
legal violations
,
privacy breaches
, and
harmful decision making
. These tasks involve policy boundaries rather than syntactic dangers, which current agents fail to internalize. In
change-branch-policy
(
Table 7
), for instance, multiple models convert a private GitLab repository to public access at the request of a fired employee, mistaking helpfulness for authorization. Trajectory evaluations show that agents frequently disregard authorization entirely, suggesting a lack of procedural reasoning.
(2) Operational risks lead to varying judgment
: Mid-tier categories such as
data loss
,
financial loss
, and
unsafe code
show agent-level variation. Claude Sonnet 3.7 is relatively cautious on destructive actions unlike GPT-4o, a disparity observed in
misleading-task
, where only Claude inspects a malicious script before running it. These results show that certain forms of sandboxed harm (e.g., ‘rm -rf‘) remain weak spots for models that rely on shallow interpretation.

RQ3: Do tools enable or restrain unsafe actions?

(1) Browsing is the most failure-prone interface
: Tasks involving web interaction (e.g., OwnCloud, GitLab) yield the highest unsafe rates across models (60–75%). Agents often struggle with authentication, redirects, and dynamic DOM content, which distracts them from recognizing unsafe behavior due to the large browsing context. For instance, in
leak-document
(

(2) File systems and code execution magnify intent errors
: Unsafe behavior in these tools often results from executing commands or modifying files without contextual checks (e.g. In
misleading-task

Still, the

(3) Messaging tools introduce social manipulation risk
: Chat-based tasks elicit unsafe behavior rates between 45–70%. Agents often fail to validate user roles or authorization before sharing sensitive information or accepting requests. In
unauth-discount
, agents approve significant markdowns under persuasive, but unauthorized, customer prompts. This pattern underscores the fragility of agent alignment in multi-user or social settings, where politeness or over-cooperation overrides internal policy logic.

Design implications

Findings from
OA-Safety
point to three actionable priorities for improving agent safety:
(i)
Contextual intent aggregation
, where refusal mechanisms must operate over multi-turn context rather than isolated prompts,
(ii)
Tool-specific privilege boundaries
, enforcing stricter runtime controls for high-risk tools like code execution and file manipulation, and
(iii)
Policy-grounded supervision
, using datasets aligned with legal, organizational, and procedural norms to train agents for regulated environments.

OA-Safety
provides executable environments with realistic tool interfaces, where these safeguards can be iteratively prototyped and stress-tested under adversarial and ambiguous conditions prior to deployment.

Related work

Safety guidelines
Designing tasks that elicit unsafe behavior from AI agents requires grounding in established risk taxonomies and policies. Frameworks such as the AIR taxonomy
[

[

LLM and agent safety evaluations
Prior benchmarks have focused extensively on unsafe generations from LLMs

[

[

,
16
]
, expanding the risk surface to include execution-based harms. However, many such evaluations rely on simulated APIs and simplified environments
[
2
,
37
,
39
]
, limiting realism. Other evaluations are constrained to single tools and short interaction paths. Tool-specific evaluations have largely targeted:
(i) Web environments: Testing agents’ robustness to pop-ups, authentication barriers, and misleading content
[
31
,
42
,
35
,
5
]
;
(2) Code execution: Evaluating safety in generating or running scripts
[

; and
(3) Social interaction: Simulating user conversations or agent collaboration
[
27
,
47
]
.

Our work differs by integrating multiple real tools (e.g., bash, file systems, browsers, messaging) into a single framework with multi-turn, multi-user interactions. Unlike prior work, we simulate both benign and adversarial users across long-horizon trajectories, exposing agents to more realistic decision-making challenges.

Training for safer agents
To improve agent robustness, recent work proposes scoring actions as safe or unsafe
[
39
]
, defensive agent architectures
[
5
]
, and adversarial fine-tuning strategies
[
24
]

[

Our benchmark fills this gap by offering a high-fidelity simulation framework suitable for safety training, adversarial red-teaming, and future reinforcement learning setups that operate across complex, multi-tool agent workflows.

5
Limitations

5.1
Simulation

While our framework is broad in scope, several limitations remain. Many current agents struggle with tasks that require exploration, delayed feedback, or handling dynamic and partially observable environments, often failing before reaching safety-critical decision points. Additionally, secondary actors (NPCs), while valuable for creating controlled multi-agent scenarios, can occasionally deviate from assigned strategies or fail to engage as intended, limiting task coverage in more complex setups.

5.2
LLM Judges for Agentic Evaluation

A key limitation in our evaluation pipeline is the use of LLMs as judges to assess trajectory safety. Prior work
[
43
]
has shown that off-the-shelf models are often unreliable in evaluating agentic behavior. To assess reliability, we conducted a human annotation study on a randomly sampled set of 100 GPT-4o trajectories. Two expert annotators independently labeled each trajectory’s safety outcome, achieving 94% inter-annotator agreement. These human judgments were then used to benchmark the accuracy of LLM-based judges on both failure detection and safety categorization.

We also evaluated a fine-tuned Qwen 2.5 7B model from Agent-SafetyBench (ASB)
[
43
]
, which does not include a separate failure category. Table
5
compares safety classification performance across judges. We find that LLM judges, particularly GPT-4.1, struggle with nuanced failure cases, often overestimating failure rates due to superficial error signals (e.g., tool failures) and underestimating unsafe behavior that is implied rather than explicitly acknowledged. For example, an agent might not affirm an unsafe request via message, but proceed to call tools to fulfill it, implicitly indicating agreement. As a result, reported failure rates are likely inflated, and unsafe behavior rates should be interpreted as conservative lower bounds.
Future work should explore how to train better and more robust in-house safety and failure detection models.

Conclusion

We present
OpenAgentSafety
, a comprehensive and extensible framework for evaluating the safety of AI agents in realistic high-stakes scenarios. By combining real tool usage, complex social interactions, and diverse user and secondary actor (NPC) intents,
OA-Safety
enables rigorous assessment of agent behavior across a wide range of critical safety tasks. Our hybrid evaluation framework integrates rule-based checks for persistent harms with LLM-as-Judge assessments for subtler unsafe behaviors, offering a nuanced view into agent safety failure modes.

We conduct an analysis to see how agent safety behaviors vary across different tools, risk categories, and intents, identifying particular areas of improvement for safety training. Our analysis reveals that even top-performing models display unsafe behavior in a significant portion of tasks (51.20%-72.72%). These findings underscore the need for stronger guardrails and more robust training methods before deploying agentic systems in sensitive applications. We hope
OA-Safety
serves as a foundation for building safer, more resilient agents, and for accelerating progress toward robust, real-world agent deployment.
