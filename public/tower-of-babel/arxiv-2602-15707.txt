Proactive Conversational Assistant for a Procedural Manual Task based on Audio and IMU
Rehana Mahfuz, Yinyi Guo, Erik Visser, Phanidhar Chinchili

Abstract
Real-time conversational assistants for procedural tasks often depend on video input, which can be computationally expensive and compromise user privacy. For the first time, we propose a real-time conversational assistant that provides comprehensive guidance for a procedural task using only lightweight privacy-preserving modalities such as audio and IMU inputs from a user’s wearable device to understand the context. This assistant proactively communicates step-by-step instructions to a user performing a furniture assembly task, and answers user questions. We construct a dataset containing conversations where the assistant guides the user in performing the task. On observing that an off-the-shelf language model is a very talkative assistant, we design a novel User Whim Agnostic (UWA) LoRA finetuning method which improves the model’s ability to suppress less informative dialogues, while maintaining its tendency to communicate important instructions. This leads to >30% improvement in the F-score. Finetuning the model also results in a 16x speedup by eliminating the need to provide in-context examples in the prompt. We further describe how such an assistant is implemented on edge devices with no dependence on the cloud.



1
Introduction

Mental load caused by the complexity of procedural manual tasks often makes people feel incapable of performing the task, even if they have the required physical ability. In industrial jobs, this necessitates training for new employees, which interferes with the tasks of experienced employees. For a layperson, this necessitates choosing between professional help and a few tedious iterations of trial and error. Video-based conversational assistants are experiencing slow adoption due to the privacy-compromising and heavy compute demanding nature of video. On-device processing of video necessitates bulky hardware, while uploading it to the cloud for processing compromises user privacy. To address this, we propose a proactive real time conversational assistant that relies only on audio and Inertial Measurement Unit (IMU) inputs from the user’s wearable device.

Our contributions are as follows:

•

The design of a real-time proactive conversational assistant that relies on only audio and IMU inputs from a lightweight wearable device, hence significantly reducing computational complexity compared to video-based assistants.

•

A novel User Whim Agnostic (UWA) LoRA finetuning method for a language model that makes it retain the tendency to communicate important instructions but limits the tendency to convey dialogues of low importance.

•

A framework to evaluate the performance of such a proactive assistant.

3
Method

We illustrate in Figure
1
how a proactive conversational assistant can guide a user in performing a procedural manual task. Audio and IMU signals captured from a smartwatch worn on the dominant wrist are used to recognize activities performed by the user. The captured audio is transcribed into text to get the user’s verbal comments and questions, if any. Recognized user activities, user comments and questions along with the assistant’s dialogues are logged into a conversation history document, from which the most recent dialogues are input into a language model to generate the assistant’s response.

3.1
Activity Recognition

Audio and IMU signals captured by a smartwatch worn on the user’s dominant wrist are input into a neural network to detect activities among drilling, hammering, sanding, screwing, unscrewing and five lifting activities: lift1 (floor-to-chest heavy), lift2 (floor-to-chest light), lift3 (chest-to-chest heavy), lift4 (knee-to-chest heavy) and lift5 (chest-to-knee heavy). The heavy weight corresponds to 20 pounds, and the light weight corresponds to 5 pounds. The training and evaluation data for the first four activities are sourced from the SAMoSA dataset
22
. The training and evaluation data for the unscrew activity were collected by the authors, and has 61 and 10 samples respectively. The training and evaluation data for the lifting activities were sourced from the BoxLift dataset
13
. All datasets have audio and IMU data from a wrist-worn device, except the BoxLift dataset, which has only IMU data.

The neural network contains a dedicated encoder for each of the two modalities, followed by a linear layer for classification. It outputs frame-by-frame probabilities for each class, with each frame roughly corresponding to a second.
For the audio encoder, we used a CNN10 PANN
15
which has four convolution layers followed by a fully connected layer. For the IMU encoder, we used an Attend&Discriminate model
5
which has four convolution layers, followed by self attention, two recurrent neural network layers and finally temporal attention. All inputs are either zero-padded or truncated to achieve a 10 second input length. All audio and IMU inputs were resampled to 32 kHz and 50 Hz respectively. For the lifting activities, a tensor consisting of all zeros was used for the audio input.
This neural network was trained for 200 epochs with a batch size of 8 and a learning rate of 0.001. The checkpoint corresponding to the highest F-score was selected.

3.2
Conversational Assistant

Conversational assistance is provided by a language model which is prompted each time an activity is recognized or the user has a comment or a question. The prompt contains a description of the procedural task the user is performing, in addition to the most five most recent dialogues form the conversation history. Older dialogues are omitted to limit the prompt size so that the delay during inference is minimal. In addition to dialogues from the assistant and the user, this conversation history also contains activities recognized by the activity recognizer as if it were being spoken by a speaker named
Wearable
. The response generated by the language model is appended to the conversation history and is communicated to the user after converting it to speech. If there is nothing informative to be conveyed, the language model is expected to produce an empty response.

A task-specific rule-based step tracker maintains counters for each recognized activity to determine which step the user is on, and provides this step information along with a suggested message to the language model in the prompt. The step tracker also identifies mistakes and suggests corrective messages. If there is no informative message to be conveyed, the step tracker does not suggest a message. An example prompt to the language model is provided in Appendix
C
. In addition, the step tracker classifies assistant-generated messages as key instructions, mistake corrections, answers and miscellaneous, which is useful for calculating the evaluation metric described in
3.5
.

3.3
Task for providing assistance

We consider a table assembly task for which the proactive conversational assistant helps the user. The task involves sanding a tabletop placed on a surface followed by flipping it, screwing in four metal frames and then screwing in four legs. The full sequence of steps is illustrated in Figure
2
. The step tracker detects a mistake and suggests a corrective message when the user starts screwing metal frames before placing all of them, or when the user starts screwing in legs before screwing all the metal frames. If the user starts drilling before placing all the screws, that is also considered a mistake.

3.3.1
Data generation

Given the sequence of activities in the procedural furniture assembly task, a rule-based activity log generator was created. Given a skill level of the user, this generator introduces some mistakes, relying on a random number generator to introduce randomness in the mistakes. It also records the list of mistakes in a separate file. We used this to generate 200 activity logs of users with varying skill levels, where the activity log is a simply a list of recognizable activities with timestamps performed during the procedural task, where the timestamps account for time each step takes as well as some pauses and rest breaks. We provided these activity logs and corresponding mistake lists along with the instructions for the task to a Large Language Model (LLM), specifically GPT-4o
25
, to generate conversations between a user and an assistant based on the activity log. We generated three conversations per activity log, resulting in 600 conversations, which were split into a set of 540 conversations for training and 60 conversations for evaluation.
While we manually wrote a rule-based activity log generator, this can be automated by carefully prompting an LLM to generate activity logs given the instruction manual, and then prompting it to add occasional mistakes.

3.4
Preparing the Language Model

From the Qwen2.5
30
set of models, we experimented with the following two language models as assistants: Qwen2.5-1.5B-Instruct and Qwen2.5-3B-Instruct.

3.4.1
Zero-shot and few-shot settings

We evaluated the ability of the pretrained off-the-shelf model, henceforth referred to simply as the pretrained model, to act as an assistant. We experimented with providing no example conversation in the prompt, one example conversation in the prompt, and four example conversations in the prompt. These are referred to as the zero-shot, one-shot, and four-shot settings respectively. The number of examples provided in the prompt involves a tradeoff between the prompt size and the amount of help provided to the language model. While a short prompt size can afford faster inference, providing more examples may be conducive to more satisfactory dialogues.

3.4.2
Finetuning

To finetune the model, we performed Low Rank Adaptation (LoRA) of both considered models for two epochs with rank 8, alpha 16, batch size 8, dropout 0.075, and learning rate 3e-5. The checkpoint with the highest F-score was selected.

As with the inference setup described in Subsection
3.2
, while finetuning the model, we prompt the model each time the user or the wearable issues a dialogue. By default, the model is trained to match its generated response with the ground truth assistant’s dialogue. However, in the ground truth conversations, the user sometimes unpredictably makes trivially informative comments such as ‘Okay done, what’s next?’ and ‘Let me start with the next step now’. Using such ground truth conversations for finetuning leads the model to convey the needful instruction only after receiving the user comment. However, since the user is not guaranteed to make such a comment, waiting for a user comment may lead the assistant to miss the window for conveying the needful instruction.

To address such unpredictability from the user, we made an adjustment in our finetuning method. We attempt to identify the instances in which an assistant’s dialogue follows a trivially informative user comment. When the language model is prompted, if the ground truth assistant’s dialogue is empty in spite of the step tracker suggesting a message, if the next speaker is the user, and if the ground truth assistant’s dialogue following the user’s comment is non-empty, then we know that the user is likely making a trivially informative comment. If this happens, then we train the model to generate the ground truth assistant’s dialogue following the user’s comment. We refer to this adjustment as
User Whim Agnostic (UWA)
finetuning.

3.5
Metrics

To understand the assistant’s strengths and weaknesses, we categorize assistant-generated responses into four types: key instruction, mistake correction, answer and miscellaneous.
Key instructions are the instructions needed by the user to perform the task correctly, even when they do not make any mistakes.
Mistake correction dialogues are the corrective statements that the assistant generates if the user is making mistakes.
Answers are responses immediately following a user comment or question, if they do not fall in the two previous categories.
All other assistant-generated responses are categorized as miscellaneous. Some examples of miscellaneous statements are encouragements and periodic reminders.
To measure how correct the assistant-generated response is with respect to the ground truth dialogue, we measure the SentenceBERT score and the BERTScore between the two. In addition, we measure the entailment of the assistant-generated response to the ground truth dialogue.

To measure the recall and precision for each type of assistant response, we consider a response as being correct with respect to the ground truth dialogue if either the SentenceBERT score exceeds 0.3 or the entailment score exceeds 0. We also measure the True Negative Rate (TNR) to check whether the assistant can stay quiet when there is no need to say something. Further, we record the time taken for the assistant to generate a response.

The roberta-large
20
model from the bert-score
38
library was used to calculate the BERTScore. The all-MiniLM-L6-v2 model from the SentenceTransformers
32
library is used to calculate the SentenceBERT score. The nli-debertav3-base
12
model from the SentenceTransformers library is used to calculate the entailment score.

3.6
On-device Implementation Details

As shown in Figure
3
, a custom Android application on a watch with a Snapdragon W5 Gen 1 processor streams audio and IMU data at 32kHz and 50 Hz respectively and inputs them into the activity recognition neural network exported to ONNX and deployed using an onnxruntime session optimized for mobile ARM processors.
Detected activities are transmitted using a REST-based interface to an edge AI box with a Dragonwing IQ9
28
processor. Specifically, the watch issues periodic HTTP PUT requests containing structured activity events. Raw audio captured by the Pixel Watch is streamed to the edge device through a Redis-based microservice
7
, enabling high-throughput, low-latency audio ingestion.

On the edge AI box, the user’s speech is transcribed into text using Whisper
-
medium
31
and is appended to the conversation history for input to the language model. The language model’s response, if any, is converted to speech using the MeloTTS-English
39
model. The resulting audio packets are streamed back to the smartwatch using a GStreamer-based service, enabling low
-
latency spoken feedback. This is illustrated in Figure
3
. All models on this edge device are run as dedicated microservices in Docker containers on the Neural Processing Unit by converting to the QNN format using the Qualcomm® AI Engine Direct SDK
29

4.2
Conversational Assistant

In Table
2
, we compare the performances of models of both sizes when used in few-shot settings as well as as after finetuning. We omitted showing the BERTScore because it does not vary much. We also omit showing results for the miscellaneous category of responses because those are the least informative responses.

The most striking change with finetuning the model is that the True Negative Rate (TNR) improves substantially. Before finetuning, even though the model was instructed to stay quiet if the user is following instructions correctly, it did not. It would generate encouraging dialogs after each detected activity. Finetuning the model taught it to stay quiet unless something informative needed to be conveyed.
Finetuning the model also conditioned it to deliver higher quality key instructions, as indicated by the meaningful improvement in the entailment of the generated key instructions with the ground truth.
As the finetuned model learns to be more quiet, its mistake correction ability gets impacted, i.e., it corrects mistakes less often as indicated by the recall, and its entailment with the ground truth also decreases, especially for the 1.5B model. Finetuning also lowered the percentage of user questions and comments answered correctly by the model. However, the quality of the answers stays high as captured by the SentenceBERT score and the entailment. Since the answer category does not distinguish between responses to user questions and comments, it is possible that the answers not provided by the finetuned model are responses to user comments which were not explicitly posing a question.

As we increase the number of examples provided to the pretrained model, it shows competitive performance to the finetuned model in all aspects except its ability to stay quiet. However, increasing the number of examples in the prompt increases the inference time, which significantly affects user experience. While considering these trade-offs, we establish that the finetuned model is the best overall candidate providing assistance, for both sizes.

5
Conclusion

We illustrate a proactive conversational assistant that guides a user step-by-step through a manual procedural task, while leveraging audio and IMU data from a wearable device to maintain context awareness. Through both automated metrics and human evaluation, it is established that finetuning the model improves its user-friendliness. Future work will involve automating enrollment of new tasks to this framework.

Appendix A
Limitations

•

Our activity detector assumes that the user’s dominant wrist is their right wrist. This holds true for only 90% of the world population
8
.

•

Our system conveys the next instruction as soon as the user is found to be performing the current step correctly, even if they have not finished the step. For example, in Table
9
, as soon as the assistant finds out that the user is sanding the table at 09:55:40 AM, it decides to convey the next instruction without allowing time to finish the sanding.
There is room for improvement in timing the instruction to account for the time it takes to finish the step. This could be done in two ways. A manual delay comparable to the average time it takes to complete the step could be added. Another way is to educate the language model about this average completion time, and to have it generate a timestamp at which to convey the dialogue, in addition to generating the dialogue itself.

•

These results show the usefulness of the assistant for only one task. To automate generalization of this framework for other procedural tasks, the two main steps would be conversation generation and implementing the rule-based step tracker.
For conversation generation, we can provide an instruction manual to an LLM and ask it to:

1.

identify which actions can be recognized using only the modalities available on a given wearable device,

2.

create some activity logs containing the recognizable actions of the task being performed without mistakes,

3.

identify common mistakes that users commonly make ( ‘Frequently Asked Questions’ section or comments from YouTube tutorial videos may be helpful in identifying these mistakes),

4.

randomly introduce some of these mistakes to the existing activity logs, and

5.

generate conversations between the assistant and the user given the Wearable’s dialogs from the activity log.

To implement the rule-based step tracker, the LLM would be asked to create a diagram of the sequence of steps for the procedural activity, using the actions recognizable from the wearable device. Then we would ask the LLM to write the corresponding code for this step tracker.
