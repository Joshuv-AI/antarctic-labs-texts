Specification-Driven Code Translation Powered by Large Language Models: How Far Are We?
Soumit Kanti Saha 1 , Fazle Rabbi 1 , Song Wang 2 , Jinqiu Yang 1

Abstract
Large Language Models (LLMs) are increasingly being applied across various domains, including code-related tasks such as code translation. Previous studies have explored using LLMs for translating code between different programming languages. Since LLMs are more effective with natural language, using natural language as an intermediate representation in code translation tasks presents a promising approach. In this work, we investigate using NL-specification as an intermediate representation for code translation. We evaluate our method using three datasets, five popular programming languages, and 29 language pair permutations. Our results show that using NL-specification alone does not lead to performance improvements. However, when combined with source code, it provides a slight improvement over the baseline in certain language pairs. Besides analyzing the performance of code translation, we also investigate the quality of the translated code and provide insights into the issues present in the translated code.



I
Introduction

Migrating legacy codebases through code translation is a challenging yet necessary step in modernizing and adapting software systems to current technologies. The process typically begins with a comprehensive analysis of the original code’s specifications, which provide a detailed blueprint of the code’s intended functionality. These specifications, along with the legacy code itself, serve as critical anchors during the translation process, offering a clear reference for understanding the existing code’s logic and design patterns. By carefully examining the legacy code, key components, such as business rules, data structures, and algorithms need to be identified, that must be accurately translated into the new language or framework.

For large software systems, the process of manually migrating code is time-consuming and prone to errors.
Hence, there is a growing need for automated approaches to generate codes to a target language from the existing codebase, such as from C to Rust.

Such code generation techniques are capable of generating correct code from natural language descriptions.

Inspired by the success of LLM code generation, we wonder if
utilizing natural language specifications (NL-specification) can boost the performance of LLM code translation
.
First, natural language is a primary training objective of LLMs, and using NL as an alternative may yield better results.
Second, NL-specifications can enhance code semantics and if combined with source code, may help LLM understand the requirements of source code better, and therefore improve code translation.
Third, as different PLs may lead to different designs for the same requirements, generating code from scratch using NL-specifications may yield better code design (i.e., fewer quality issues) compared to direct translation from one PL to another.

In this study, we investigate the use of LLM-generated NL-specification as an intermediate representation for code translation. Specifically, we explore two approaches: (1) translating using LLM-generated NL-specification only, and (2) translating using a combination of source code and LLM-generated NL-specification. In both approaches, the NL-specification is generated by an LLM from the source code.

In this work, we answer three research questions (RQs) as follows.

•

RQ1: Can LLM-generated specifications boost LLM-based code translations?

Based on evaluation results on three popular datasets (avatar

•

RQ2: When LLM-generated specifications can boost code translation and when not?

Upon examining the generated NL-specification, we identify the reasons behind and current limitations of using LLM in generating NL-specification.

•

RQ3: What is the impact of specifications on the quality of translated code?

Last, we compare the quality of translated code among
[

We present insights into the types of issues encountered in the translated code, offering a deeper understanding of the challenges in cross-language code translation.

In this paper, our contributions are as follows:

1.

We explore utilizing NL-specification as an intermediate representation for boosting code translation. We present results for both the NL-specification only approach and the approach combining NL-specificationwith source code for translation.

2.

We provide an analysis of the cases of failure and success for each approach, using representative samples to illustrate the performance.

3.

We examine and compare the quality of translated code using different approaches and offer insights into the challenges associated with using C as the source language.

III
Methodology

As shown in Fig
1
we first take a sample from our dataset and create the prompt
to generate NL-specification. Then using LLM (in our case OpenAI’s GPT-4) we generate the NL-specification for that corresponding code sample.
We examined the correctness of the generated NL-specification.
Then with approach 1, we create the prompt using only NL-specification, and with approach 2, we create the prompt using source code and NL-specification to generate the target language code. Then we generate the target language code with the prompts in
pass@1
. Then we try to compile the translated files, if we fail to compile, we create a compilation error repair prompt with the translated code and the error message from the compiler. Thus we try generating a solution with compilation error fixation in an iterative approach. We stop iteration if the compilation error is fixed or after three iterations. Then if there is no compilation error we run the test files on the generated (or fixed) translation. If all the tests pass, we consider the translation correct, otherwise incorrect. All the prompt templates are given in later in this section.

Their approach incorporates a Multi-Scale Pyramid Feature Extractor (MPFE) and a series of adaptive attention mechanisms, collectively known as AGLRepair. The MPFE component refines the encoder in the code generation phase by merging global and multi-scale local features, addressing challenges associated with long pseudocode sequences. In the repair phase, AGLRepair employs intra-line, inter-line, and bidirectional code-error message attention modules to capture contextual and diagnostic cues, enhancing error localization and correction. VII
Conclusions

In this work, we experiment with two approaches for translating source code from one programming language to another: one using NL-specification as an intermediate representation and providing it as a prompt to an LLM to generate code in the target language, and another combining NL-specification with the source code to generate target language code and also fix compilation errors using the LLM. We found that the approach combining source code with NL-specification outperforms the state of the art on certain datasets. We analyzed the reasons behind the successes and failures of both approaches, as well as the quality of the translated code, identifying issues with the translation of C language code. In the future, we aim to enhance our approaches by addressing the root causes of failures and refining the intermediate representation.
