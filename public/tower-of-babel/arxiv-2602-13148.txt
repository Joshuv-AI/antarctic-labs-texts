TrustMee : Self-Verifying Remote Attestation Evidence
Parsa Sadri Sinaki, Zainab Ahmad, Wentao Xie, Merlijn Sebrechts, Jimmy Kjällman, Lachlan J. Gunn

Abstract
Hardware-secured remote attestation is essential to establishing trust in the integrity of confidential virtual machines (cVMs), but is difficult to use in practice because verifying attestation evidence requires the use of hardware-specific cryptographic logic. This increases both maintenance costs and the verifiers’ trusted computing base. We introduce the concept of self-verifying remote attestation evidence. Each attestation bundle includes verification logic as a WebAssembly component signed by a trusted party. This approach transforms evidence verification into a standard code - signing problem: the verifier checks the signature on the embedded logic and then executes it to validate the evidence. As a result, verifiers can validate attestation evidence without any platform - specific knowledge. We implement this concept as TrustMee, a platform-agnostic verification driver for the Trustee framework. We demonstrate its functionality with self-verifying evidence for AMD SEV-SNP and Intel TDX attestations, producing attestation claims in the standard EAT Attestation Result (EAR) format.

Introduction

Figure 1
:
TrustMee
removes the need for platform-specific code in the verifier by bundling signed verification logic with the evidence. A generic verifier checks the signature and then uses the component to process the evidence, turning the problem of verification into a problem of code signing.

Remote attestation allows verifiers to assess the integrity and authenticity of a remote device. It is a key component of
Confidential Computing (CC)
, allowing sensitive workloads to run within untrusted infrastructure. It achieves this by providing cryptographically-verifiable evidence that the computation runs inside a hardware-isolated
Trusted Execution Environment (TEE)

[
20
]
, and so is isolated from other workloads as well as the hypervisor and the
Cloud Service Provider (CSP)
operational staff.

The security of remote attestation depends on a chain of trust rooted in the attester’s hardware. Each
TEE
platform has its own attestation format, protocols, and verification libraries, so verifying attestations requires hardware-dependent logic for every
TEE
platform that the verifier may interact with. As well as creating significant integration challenges
[
4
]
, hardcoding verification logic into the verifier reduces the ability of system designers to switch between or upgrade their hardware platforms, as backwards-incompatible functionality cannot be used until all possible verifiers have been upgraded.

We propose
TrustMee
, a
platform-agnostic
attestation verifier, shown in Figure
1
, that
eliminates the need for hardcoded platform-specific verification logic
without sacrificing security or performance.

TrustMee
takes advantage of WebAssembly to enable
self-verifying
attestation evidence. Instead of hardcoding the verifier with hardware-specific verification logic for each
TEE
platform, the attesting
TEE
supplies a certified WebAssembly component that implements its platform-specific verification logic,
TrustMee
then combines the component’s verification output with platform-agnostic processing to return a signed attestation result in the standard
EAT Attestation Result (EAR)
format
[
25
]
.
The verifier service then only needs to

1.

authenticate components provided by the with the attestation request (e.g., by checking a signature) and

2.

execute it inside the WebAssembly sandbox

.
All platform-specific parsing and cryptographic checks are delegated to this verification component, which is sandboxed by the runtime, thus eliminating the ability of a compromised verifier plugin to impersonate other platforms, or to compromise the attestation verifier as a whole.

Existing frameworks, such as Veraison
[
50
]
and Trustee
[
21
]
break verification into reusable
TEE
-specific plugins. In these plugin-based systems, framework authors or users write and deploy verifier plugins that run inside the verifier’s
trusted computing base (TCB)
. This has two drawbacks:

1.

verifier operators must keep these plugins up-to-date for every supported attester’s hardware platform, and

2.

any bug or backdoor in a plugin can compromise the verifier, which by its very nature must perform operations on untrusted data—e.g., certificate parsing—that have historically been a significant source of vulnerabilities
[
10
,
55
]
.

TrustMee
enables a platform-agnostic attestation mechanism that supports adding new
TEE
platforms without increasing the verifier’s
TCB
or requiring verifier modifications, shifting
TEE
-platform-specific maintenance and deployment from the verifier to the
TEE
platform developer.

•

TrustMee

•

An implementation of

•

TrustMee

TrustMee

2
Background

This section introduces preliminary knowledge of fundamental concepts involved in this work.

2.1
Remote Attestation

Remote attestation is a security mechanism in which a prover (attester) sends evidence of its state to a remote verifier
[
20
]
. In trusted computing systems, the prover collects measurements of its configuration and reports them as evidence so the verifier can assess authenticity and integrity
[
11
]
. In
CC
and
TEEs
, this is often essential to ensure the communication endpoint is a genuine node running a trusted configuration, such as specific software inside a
TEE

[
2
]
. When the prover is software running in a
TEE
, it typically derives cryptographic measurements of the code and other
TEE
-specific digests, then signs these claims with a hardware-protected key to produce evidence for verification. After successful verification, a client can safely provision secrets or sensitive workloads to the
TEE
, without needing to trust the underlying host environment to avoid unauthorized access or tampering
[
36
]
.

Remote ATtestation procedureS (RATS)
is an IETF framework that has been developed to provide a general model and terminology for remote attestation
[
12
]
.
We follow the IETF
RATS
model for remote attestation. An Attester running inside a
TEE
produces signed evidence about its configuration; a Verifier appraises this evidence using endorsements and reference values; and a Relying Party consumes the resulting appraisal. Additional roles such as Endorsers and Reference Value Providers supply trusted input to the Verifier. Verifier Owner is the entity that configures the appraisal policy for the Verifier and Relying Party Owner is the entity that manages the appraisal policy for the Relying Party.

Remote Attestation of AMD SEV-SNP
TEEs
.

In
SEV-SNP
, the guest requests a signed attestation report from the AMD Secure Processor; verifiers validate the report’s signature (VCEK/VLEK) and appraise selected fields against vendor endorsements and local policy
[
43
,
19
,
49
,
6
,
5
]
.

Remote Attestation of Intel TDX
TEEs
.

In
TDX
, a quoting enclave produces a signed
Trust Domain (TD)
Quote binding the
TD
’s measurements to an attestation key; verifiers validate the quote and using a certificate chain and compare measurements against expected values
[
32
,
19
,
49
,
26
]
.

2.2
EAT Attestation Results

The
EAT Attestation Result (EAR)

[
25
]
is a message format specified in an IETF Internet-Draft that encodes the Verifier’s appraisal of an Attester’s evidence into a secure, structured token. It embeds a normalized trustworthiness vector and contextual metadata bound to the appraisal process, making it easier for Relying Parties to interpret and enforce policies reliably and consistently.

2.3
Trustee

We build on Trustee
[
21
]
, an open-source attestation framework for confidential containers. Trustee comprises a Key Broker Service, an Attestation Service, and a
Reference Value Provider Service (RVPS)
. Attestation Service implements the
RATS
Verifier role.
In this work, we extend the Attestation Service component.
The components in Trustee and the interaction between them follow the definitions in the
RATS
architecture.

2.4
WebAssembly

WebAssembly is a compact, portable bytecode format that runs in a sandboxed execution environment with near-native performance
[
29
,
34
]
. A single WebAssembly binary can execute across different operating systems and architectures as long as a compatible runtime is available, which makes it attractive as a carrier for platform-specific verification logic
[
29
,
61
]
. Runtimes expose standard system interfaces through
WebAssembly System Interface (WASI)
, allowing controlled access to I/O (e.g., HTTP, filesystem) while preserving isolation
[
60
,
62
]
.
The WebAssembly Component Model further structures applications as components that interact via typed interfaces defined in the
Wasm Interface Type (WIT)
language
[
18
,
15
]
.
WIT
lets us describe rich data types and function signatures in a language-agnostic way, so components written in different languages can exchange structured data without ad-hoc serialization.

Prior work shows that WebAssembly provides strong isolation and near-native performance
[
38
,
30
,
51
,
37
,
64
]
; we leverage these properties to safely execute untrusted platform-specific verifiers.

3
Problem description

3.1
System model

TrustMee
functions as a
RATS

Verifier
, accepting attestation evidence produced by an
Attester
—a node running in a
TEE
—verifying its validity, checking its claims against some predefined policy, and outputting the result for use by a
Relying Party
.
A
TEE
node runs a workload (the code being attested) inside a hardware-isolated environment (e.g., a
Confidential Virtual Machine (CVM)
).

3.2
Adversary model

We consider adversaries who attempt to make
TrustMee
accept invalid attestation evidence, or who attempt to compromise
TrustMee
by using malicious or vulnerable verification logic.

Capabilities.

The adversaries may control the network and run arbitrary software inside a
TEE
node’s workload environment.
The cloud provider may control the host OS, hypervisor/VMM, and networking, but cannot manipulate the attestation functionality in such a way as to obtain attestations that do not accurately represent the state of the attester.

Assumptions.

We assume the
TEE
’s attestation mechanism is sound, meaning that the
TEE
cannot be manipulated to produce valid attestation that makes false claims, such as by signing false measurements or
TCB
information. Neither does the attestation verification code contain vulnerabilities that allow an attacker to exploit it to yield an attestation result that does not reflect the state of a real Attester. We assume also that standard cryptography is secure, as is the public key infrastructure used to certify hardware roots of trust and any code provided by the attester.

We assume that an adversary cannot compromise the verifier or relying party, nor can they escape the isolation of the WebAssembly runtime. We justify this latter assumption by noting that WebAssembly is widely deployed on the web, where users routinely download and execute untrusted code inside the sandbox without evidence of widespread exploitation.

Untrusted inputs.

We treat both

1.

the received attestation evidence and

2.

any accompanying WebAssembly verification component

as attacker-controlled.

TrustMee
only executes Verification Components signed by a key contained in the Verifier’s trust database. We discuss how this may be relaxed in
Section

7.3
.

3.3
Requirements

The goal of this research is to ensure that a Verifier can validate attestation evidence without any platform-specific code, while still supporting the current diversity in verification protocols.
Therefore, the following requirements must be fulfilled by
TrustMee
:

CR
—Compatibility
:

Any Verifier must be able to verify the attestations from any
TEE
platform, without any
TEE
-specific modifications to the Verifier, or any Verifier-specific modifications to the Attester.

TEE
-specific unsandboxed native Verifier drivers create a large and rapidly changing verifier-side
TCB
, and prevent new
TEEs
from being used until all relevant Verifiers in the wild have been updated.
Keeping the verifier platform-agnostic reduces trusted code and enables instant deployment of new
TEEs
without modifying or redeploying the Verifier.

SR
—Security
:

Attestation results as determined by the Verifier must reflect the true state of the Attester.

Verifying attestation evidence involves a number of tasks such as binary parsing of certificates that are historically error-prone, and thus platform-specific verifiers may have exploitable vulnerabilities. This is exacerbated by the fact that each
TEE
vendor must produce their own libraries supporting each of their platforms, meaning that even open-source verifier libraries will not be subject to the sustained and concentrated scrutiny that a platform-agnostic library may see.

PR
—Performance
:

When implemented in existing attestation frameworks, the design should add minimal end-to-end latency compared with existing drivers.

Attestation is often on the critical path of connection establishment or workload admission (e.g., TLS handshakes, gateway decisions, orchestrator scheduling), therefore making
low latency a key requirement for real-world adoption.

4
Self-Verifying Remote Attestation Evidence

TrustMee
serves as a
RATS
Verifier, illustrated in Figure
2
.
TrustMee
receives evidence from the Attester, interacts with Endorser, Reference Value Provider and Verifier Owner to obtain additional data needed to verify the validity of the evidence and the appropriateness of the Attester’s state, then outputs the attestation result to the Relying Party.

Figure 2
:
The
RATS
architecture data flow (adapted from
[
12
]
).

Figure
3
illustrates the design of
TrustMee
. Attestation verification involves the following steps:

•

Request Parsing (platform-agnostic code, platform-specific data): Parse the attestation request to obtain the evidence collected from the attester, the claims expected to be found in the attestation, a policy ID to specify which policy to check against, and the Verification Component to be loaded.

•

Evidence Parsing (platform-specific code, platform-specific data): Parse the evidence, which varies in format across different
TEE
platforms.

•

Endorsement Check (platform-specific code, platform-specific data): Check the signature and specific fields of the evidence against the endorsement, typically acquired from the
TEE
manufacturer.

•

Policy Check (platform-agnostic code, platform-specific data): Fetch the reference values from the
RVPS
and check the parsed claims against them according to the assigned policy from the request.
After parsing and validating the evidence, the extracted values must be appraised against trusted reference values under policy; this step is partly platform-specific because the claim set and its semantics are derived from platform-specific evidence formats, with some fields following vendor-defined conventions (e.g., Intel/AMD measurement and TCB-related fields) and others being verifier-defined.

•

Result Signing (platform-agnostic code, platform-agnostic data): Sign the attestation result with the signing key of the verifier.

TrustMee
extracts the steps with platform-specific code into a WebAssembly
Verification Component
that can be executed by a platform-agnostic
TrustMee
-enabled Verifier. The Verification Component exposes an attestation API that remains consistent across all
TEE
platforms.

Self-verifying attestation evidence consists of two parts: the Attester’s platform-specific attestation evidence, and the Verification Component. The verifier host is responsible only for authenticating the component, running it in the WebAssembly sandbox, then checking the result against a policy, and signing the result. This effectively reduces multi-platform attestation verification to a traditional code-signing and PKI problem, avoiding the need to update the Verifier as new
TEE
platforms come into being.

Figure 3
:
TrustMee
architecture for self-verifying remote attestation evidence. The platform-specific verification logic is bundled with the evidence.
TrustMee
verifies the signature of the verification logic and executes it as a WebAssembly component inside a sandboxed WebAssembly runtime to map the platform-specific attestation evidence to a JSON claims map that can be used by the platform-agnostic logic of the verifier.

This design offers several advantages:

1.

Stable verifier design.

TrustMee
uses hardcoded implementations only of request handling, policy evaluation, and result signing, all of which are platform-agnostic; evidence parsing and endorsement validation are delegated to WebAssembly components that are provided by the attester. This keeps the Verifier implementation stable as
TEE
formats and validation rules evolve, reducing maintenance effort and the need for frequent deployments.

2.

Rapid support for new
TEEs
and updates.

The verifier host can accept new or updated Verification Components as long as they implement the required interface and are properly signed. This allows verification logic to evolve with changing evidence formats or validation rules without requiring verifier-side engineering effort beyond signature verification and sandboxed execution.

3.

Stronger isolation for error-prone parsing and cryptographic operations.

Platform-specific evidence parsing and certificate processing run inside the WebAssembly sandbox behind a constrained host interface, limiting the impact of malformed evidence and vulnerabilities in verifier code.

4.

Platform-agnostic results for relying parties.

Because the host emits results in a standardized format and signs them, relying parties receive consistent attestation results independent of the underlying
TEE
platform.

4.1
Verification Component

The main tasks of the Verification Component are to parse the evidence and check that it has been endorsed by a trusted
TEE
platform. Though its internal implementation differs by
TEE
platform, the Verification Component exposes a consistent interface, without concern for its internal implementation details.

We implement Verification Components using the WebAssembly component model; since WebAssembly components are strongly isolated from the outside world and communicate only through well-defined interfaces, this allows Verification Components to be loaded and executed without concern that a vulnerable Verification Component may compromise the Verifier as a whole.

Figure 4
:
The interface between the Verification Component and
TrustMee
is defined using
WIT
to ensure interoperability.

The Verification Component’s interface is shown in
Figure

4
. The main logic of the component is the
verifier
resource, providing a handle to a single instance of the verification logic.
In addition, a component can import
WASI
interfaces to access host functionality from the runtime, such as clocks and the filesystem. The component’s
evaluate
method validates attestation evidence and returns a
claim map
in JSON format, describing the claims by the Attester to be checked against the policy.

4.2
Verifier Host

The Verification Component is loaded and executed by the Verifier Host, which implements the platform-agnostic Verifier functionality, exposing an API that accepts attestation requests. This API accepts a WebAssembly component binary, attestation evidence, and a verification policy, and returns a signed response containing the attestation result in EAR format.

Before loading a WebAssembly Verification Component, the Verifier Host authenticates it using a digital signature; this is not needed for the integrity of the verification process, but rather to prevent e.g., denial of service attacks by a component containing an infinite loop.
TrustMee
accepts a component only if its signature validates against an accepted trust anchor set configured by the Verifier Owner. Components that fail signature verification are rejected and are not compiled or instantiated.

Implementation

5.1
TrustMee
driver for Trustee

We demonstrate an implementation of
TrustMee
for the Trustee
[
21
]
open-source remote attestation framework, along with Verification Components for two
TEE
platforms, AMD
SEV-SNP
and Intel
TDX
.
Trustee is part of the Confidential Containers project, and includes an
Attestation Service
that validates attestation evidence for various other services.

Figure 5

TrustMee
adds a platform-agnostic Verifier Driver to Trustee that delegates the verification to a WebAssembly Component.

Trustee supports various
TEE
platforms by implementing a Verifier Driver for each platform, which verifies attestation evidence for that specific platform. Our work adds a
TrustMee
Verifier Driver that can verify attestation from any platform for which a Verification Component is available, as shown in Figure
5
. This eliminates platform-specific logic from the Trustee Attestation Service, as well as the need for dependency on various
TEE

Trustee then uses another service, the
RVPS
to fetch reference values that
TrustMee
’s claims are expected to match. It then uses another, the Policy Engine, to check these reference values against the claims yielded by
TrustMee
.
To demonstrate the platform-agnostic capability of our system, we developed two Verification Components supporting attestations by AMD
SEV-SNP
and Intel
TDX

TEEs
.
We add an additional API for Verification Component registration, in addition to the standard remote attestation interface.

5.2
Verification Components

As Trustee already implements the Verifier Drivers for both AMD
SEV-SNP
and Intel
TDX
, we extracted the key functionality of these drivers and ported them to the WebAssembly target, exposing the interface described in
Section

4.1
.

To port the desired functionalities from the Trustee Verifier Drivers to WebAssembly components, we implemented verifiers as standalone WebAssembly components that conform to the defined
WIT
interface. The verification components reuse the Trustee Verifier Driver code to the greatest extent possible; however, in some cases significant changes were needed in order to replace dependencies that did not support their toolchain’s WebAssembly target.

We then used wasmsign2
[
59
]
to embed a signature section into each WebAssembly component binary, allowing its source to be verified by the Verifier Host.

5.2.1
AMD SEV-SNP Verifier

For AMD
SEV-SNP
, the WebAssembly verifier parses SNP evidence, validates the embedded signature against a VCEK/VLEK certificate, checks configuration fields against expected values, and exports a claims map for policy checking.
The VCEK/VLEK certificate may be provided by the attestation request or fetched from AMD’s
Key Distribution Service (KDS)
.

The main challenges we encounter during the porting of the Trustee AMD
SEV-SNP
Verifier Driver to WebAssembly components are:

1.

OpenSSL Compatibility: We compile OpenSSL as a WebAssembly library and link the Rust openssl bindings against it, enabling signature verification inside the component (with SIMD128 enabled for speed).

2.

The HTTP library used by the driver is replaced with the waki crate
[
58
]
, which uses the
WASI
HTTP interface as a backend. This allows the Verification Component to fetch certificates from AMD’s
KDS
.

5.2.2
Intel TDX Verifier

The Intel
TDX
Verification Component parses the
TD
Quote from a
TDX
guest, validates its signature and certificate chain using Intel DCAP collateral obtained from Intel at runtime (e.g.,
Provisioning Certification Key (PCK)
certificate chain, revocation information, and
TCB
-related metadata), checks the quote’s reported measurements against expected values, and emits a claims map for policy checking.
The Trustee
TDX
Verifier Driver uses Intel’s DCAP quote verification library
[
31
]
, which cannot easily be ported to WebAssembly. We replaced this with the pure-Rust library
dcap-qvl

[
48
]
. We extended
dcap-qvl
, replacing its HTTP library with the
WASI
-backed library waki
[
58
]
, similarly to the
SEV-SNP
Verifier Driver.

5.3
Verifier Host

The
TrustMee
-enabled Trustee Attestation Agent exposes two main APIs: the Attestation API and the Component Registration API. The Attestation API is unmodified from its original implementation in Trustee. We implemented a new Component Registration API to reduce the redundant network overhead of repeatedly uploading identical WebAssembly components to the Attestation Service.

5.3.1
Attestation Service APIs

The
Attestation API
that accepts attestation evidence together with either raw WebAssembly verifier bytes or a previously-registered component ID, and outputs a signed
EAR
as the attestation result. The
Component Registration API
registers a signed WebAssembly component and returns a stable ID that can then be provided to the Attestation API. Internally, the registry maps component IDs to the SHA-256 hash of the raw bytes and the corresponding compiled WebAssembly module, enabling reuse without re-uploading or recompiling, and causing identical components to be transparently reused without recompilation.
For new components, the service loads the verifier into the Wasmtime engine, compiles it once, and adds a new record to the registry; subsequent attestation requests instantiate the compiled component from the cache.

5.3.2
Hosting the WebAssembly Component Verifier

To invoke the platform-specific verification functionality encapsulated in the WebAssembly component, the Verification Component is instantiated using the Wasmtime
[
17
]
WebAssembly runtime. Wasmtime supports a variety of
WASI
interfaces, which we configure as follows:

1.

WASI-HTTP: WASI-HTTP interface is enabled to allow the WebAssembly verification component to fetch endorsement from external sources.

2.

WASI-Filesystem: A local directory is exposed to each Verification Component instance, and a handle to that directory is made available to the WebAssembly component to enable the collateral caching we implemented for the
TDX
and
SEV-SNP
Verifiers; each verifier’s filesystem access is isolated from other instances.

6
Evaluation

6.1
Compatibility Evaluation

The primary requirement of
TrustMee
is Compatibility (CR, Section
3.3
), meaning a verifier must be able to validate attestations from different
TEEs
without integrating platform-specific verification code. We achieve this requirement by integrating
TrustMee
as a platform-agnostic Verifier Driver in Trustee and demonstrating that the same native code can verify evidence from multiple
TEEs
by dynamically loading a signed WebAssembly Verification Component provided with the attestation request. Because all Verification Components implement the same
WIT
interface, the Verifier Host invokes a uniform evaluate API and receives a claims map that can be turned into signed attestation result. Our prototype demonstrates this workflow end-to-end for Intel
TDX
and AMD
SEV-SNP
, showing that adding support for a new
TEE
reduces to validating the signature of a Verification Component rather than modifying or redeploying the verifier host.

6.2
Security Evaluation

We consider two main threats from Section
3.2
:

1.

the Attester (a
TEE
-backed node), and

2.

the
TEE
vendor operating the hardware root of trust and endorsement services.

We also assume a standard network attacker who can intercept, modify, and replay messages but cannot break standard cryptography.

The Attester may send malformed, replayed, or misbound evidence. By our assumption of the
TEE
’s security, the correct verification algorithm will either reject this evidence outright, or not yield any false claims. The Attester may also supply a Verification Component containing an incorrect verification algorithm; this will be rejected by the Verifier if the Attester has not succeeded in colluding with a
TEE
vendor to have their false Verification Component signed. The WebAssembly sandbox confines Verification Component execution, preventing access to host resources and isolating Verification Components across
TEE
types.

The
TEE
vendor is the root of trust, and we assume that the attestation mechanism of its
TEEs
cannot produce false attestation evidence that will be accepted by its verification algorithm. A malicious
TEE
vendor can still issue valid endorsements for backdoored hardware, but this limitation applies to all attestation platforms and is not specific to
TrustMee
. The
TEE
vendor might also certify a faulty Verification Component. As the component has their signature, false claims made by the Verification Component can be attributed to the
TEE
vendor. The sandboxing provided by WebAssembly component verifiers prevents the vendor from attempting to attribute their claims to another
TEE
, since the Verifier includes in its output the identity of the component that verified the attestation evidence, and the Verification Component cannot interfere with this without breaking out of the WebAssembly sandbox.

Based on this analysis,
TrustMee
satisfies our security requirement (SR, Section
3.3
) under the stated adversary model (Section
3.2
).

6.3
Performance Evaluation

To evaluate the performance overhead of integrating WebAssembly Verification Component with the Trustee Attestation Service, we measure and compare the latency of the baseline Trustee Attestation Service (implemented fully in native code) and
TrustMee
, an Attestation Service that uses WebAssembly-based Verification Components for evidence validation, under different settings.
For Intel
TDX
specifically, we further compare
TrustMee
against Trustee with native
TDX
Verifier Driver using the pure-Rust
dcap-qvl
instead of the Intel DCAP QVL, as described in Section
5.2.2
.

Latency
captures the time required to handle an attestation request and carry out its key steps. We focus on
end-to-end attestation latency
as the total time from when the HTTP request is received by the Trustee Attestation Service until the signed attestation result is returned to the client. We report
verification time
as the time spent running the Verifier Driver, including the Verification Component in the
TrustMee
case.

We report mean and standard deviation of end-to-end attestation latency and verifier-specific computation time for all experments over 100 runs per setting unless stated otherwise.

7
Discussion

In this section, we reflect on the design, implementation, and evaluation of
TrustMee
. We discuss the identified limitations in the current work and outline potential directions for future improvements based on our findings.

7.1
Cryptographic performance

Despite WebAssembly’s reputation for near-native speed, our Intel
TDX
and AMD
SEV-SNP
WebAssembly Verification Components are slower than their corresponding native x86_64 verifiers that are compiled from the same Rust codebase.
One reason for this is the lack of hardware acceleration for cryptographic operations in WebAssembly, which particularly slows certificate validation.
Both the
SEV-SNP
WebAssembly Verification Component (ECDSA via OpenSSL C code
[
46
]
) and the
TDX
WebAssembly Verification Component (ECDSA in pure Rust) are slower than their x86_64 versions.
This slowdown is also reported by
[
54
]
. While absolute latency remains low, there is nevertheless significant room for optimization.

7.2
TEE compatibility

We currently support only AMD
SEV-SNP
and Intel
TDX
via WebAssembly Verification Components, and have not yet tested other
TEEs
such as Intel
Software Guard Extensions (SGX)

[
22
]
, Arm
Confidential Compute Architecture (CCA)

[
7
]
, or ARM TrustZone
[
44
]
.
Porting the Trustee
TDX
Verifier Driver exposed WebAssembly compatibility gaps, Intel DCAP-dependent code
[
31
]
was replaced with the pure-Rust
dcap-qvl
crate
[
48
]
. Similar issues may arise for other platforms, motivating support for more
TEEs
.

7.3
Impact of malicious Verification Components

Because the Attester supplies the platform-specific WebAssembly Verification Component,
TrustMee
must treat it as attacker controlled input and currently relies on signature checking at load time to prevent malicious Verification Components from being used for denial-of-service attacks against the Verifier or amplification attacks. Our prototype uses a simple key pair to sign and verify components, which is sufficient for feasibility but unrealistic for deployment. A production system would need a
Public Key Infrastructure (PKI)
to manage trust at scale. The Verification Component also uses WASI-HTTP to fetch endorsements, but a production system must constrain its access to the network so that this cannot be abused. The runtime or the host can enforce an allowlist of trusted endorser hosts to reduce the impact of a compromised component while preserving required functionality
[
23
]
; however, this undermines the platform-agnosticism of
TrustMee
. A more flexible solution might require an opt-in from the server being accessed, e.g., with a special DNS record that includes the component’s hash.

We also observe that WebAssembly’s strong sandboxing allows the Verifier to execute a completely unauthenticated Verification Component, instead considering its identity as a generic part of the policy being checked by the Verifier. This requires even more careful control of the Verification Component’s access to both computational and external resources, e.g., by limiting the computational and network resources that it can consume so as to prevent amplification attacks, but will allow for verifier that follows a zero-trust approach, without any kind of trust database requiring ongoing maintenance.

7.4
Additional implementations

In addition to Trustee, Veraison
[
50
]
is a widely used modular framework for remote attestation verification. A
TrustMee
plugin for Veraison will allow the same Verification Component implementation to be used by multiple Verifier platforms, with the result that
TrustMee
’s self-verifying evidence is not only
TEE
-agnostic, but also Verifier-agnostic.

8
Related work

8.1
Vendor-specific attestation verification

Hardware-based attestation has evolved from early TPM-based remote attestation
[
53
]
to modern
TEEs
such as Intel
SGX
and
TDX
and AMD
SEV-SNP
. Different hardware vendors provide their own solutions for remote attestation of
TEEs
; Intel platforms have used
Enhanced Privacy ID (EPID)

[
35
]
and later DCAP-based attestation for
SGX
/
TDX

[
31
]
, ARM provides the
Platform Security Architecture (PSA)
attestation model for ARM-based IoT
[
56
]
, and for AMD there is snpguest tool for verification
[
57
]
. While these mechanisms are secure, they are vendor-specific and tightly coupled to their hardware, creating integration and compatibility challenges in heterogeneous deployments.
Major cloud providers also offer platform-specific attestation services, such as the ones for AWS Nitro Enclaves
[
3
]
, Google Cloud Confidential Computing
[
27
]
, and Microsoft Azure Confidential Computing
[
42
]
. While robust, these solutions are tightly coupled to their respective platforms. In addition, Intel Trust Authority
[
33
]
is a similar online attestation service that supports a specific set of platforms. These services ease deployment of remote attestation functionality, but do not address its platform-tied nature.

8.2
Cross-platform attestation verification

Prior work has pursued hardware-agnostic attestation verification through standards and modular verifiers. The IETF
RATS
architecture
[
12
]
defines interoperable roles and protocols, but it does not remove the need for platform-specific verifier implementations.
RATS

Entity Attestation Token (EAT)

[
40
]
, on the other hand, is a standardized format for claims about entities. Only some platforms, however, currently produce and sign their evidence in this format, and the tokens may contain, e.g., proprietary claims that the verifier needs to be able to interpret.

Systems such as plugin-based verifiers, Trustee
[
21
]
, and Veraison
[
50
]
provide a unified framework/API, yet still require per-
TEE
plugins/drivers that must be built, deployed, and maintained for every new platform. In these designs,
TEE
-specific parsing and cryptographic logic typically runs as native code inside the verifier’s
TCB
, increasing operational overhead and trusted code.

The fragmented nature of current attestation systems presents significant challenges in heterogeneous environments. Gu et al.
[
28
]
propose UniTEE, a unified attestation framework that addresses interoperability between different
TEE
platform through a microkernel-based design. While their work demonstrates the feasibility of unified attestation, it relies on native implementations of verification logic for each platform, requiring separate compilation and deployment processes.

Related efforts aim to unify
TEE
development and deployment, but attestation coverage remains limited in practice. Niemi et al.
[
45
]
survey open-source attempts. It can be noted the difficulty of achieving broad, stable multi-
TEE
support. Enarx
[
24
]
uses WebAssembly for application portability, but its attestation support is still platform-specific and currently limited (e.g.,
SGX
/
SEV-SNP
). Open Enclave
[
41
]
offers a hardware-agnostic programming model, yet real-world support is constrained (e.g.,
SGX
and limited TrustZone/OP-TEE support
[
39
]
). Veracruz
[
13
]
also supported only a small set of
TEEs
before moving to emeritus status.

8.3
Platform-agnostic attestation evidence

Another direction is to standardize the attestation report itself. Ott et al.
[
47
]
propose a universal report format in which the verifier validates signatures and compares measurements against CA-signed reference metadata, largely avoiding platform-specific logic on the verifier side. However, this shifts key trust and operational burdens to the attester ecosystem. The verifier must still decide which CAs are authorized to sign reference values and track revocation and updates, and the attester must maintain complete and up-to-date reference values for all deployed components, moving the maintenance cost from a single verifier deployment to many attesters.

In contrast, our design keeps the attestation verification platform-agnostic by moving platform-specific verification code into signed, sandboxed WebAssembly Verification Components shipped alongside the evidence. This shifts maintenance of verifier code from the attestation verifier operator to the
TEE
/platform builders, and reduces the Verifier’s
TCB
to the verifier core logic (request/response handling and policy checking), the WebAssembly runtime, the underlying
TEE
attestation infrastructure, and the
PKI
for authenticating Verification Components. We demonstrate feasibility by integrating Trustee framework with platform-specific WebAssembly Verification Components for AMD
SEV-SNP
and Intel
TDX
, porting existing implementations to components that expose a unified WIT interface.

8.4
WebAssembly for untrusted code

Originally intended for the web
[
29
]
, WebAssembly has been used to safely execute untrusted code in a sandboxed environment.

TrustMee
is subject to many of the same risks, but as an unattended system is more sensitive to denial of service attacks, since there is no human user to detect and terminate execution in a timely manner. This concern is most famously shared with smart contract platforms, which execute applications from anonymous untrusted sources simultaneously on large numbers of machines. The Ethereum
[
14
]
smart contract platform counteracts this risk with a gas mechanism that limits a contract’s computation to a level that has been paid for by the user that triggers it. The Wasmtime runtime includes a similar mechanism
[
16
,
Config::consume_fuel
]
that allows callers to limit its computation to an acceptable level, but it remains to be seen how best to do so in the absence of the financial mechanisms available to a smart contract platform integrated with a cryptocurrency.

9
Conclusion

This research presents the concept of
self-verifying remote attestation evidence
that includes signed platform-specific verification code as a WebAssembly component. This turns the platform-specific challenge of verifying evidence into a platform-agnostic problem of verifying a code signature.
TrustMee
prototypes this functionality as a platform-agnostic Trustee verification driver, and demonstrates this with self-verifying evidence for AMD
SEV-SNP
and Intel
TDX
.

Our performance evaluation compares this prototype with the native platform-specific drivers of Trustee, evaluating latency and resource usage overhead. This shows low end-to-end overhead, but also indicates there is room for optimization, due to WebAssembly’s limited support for cryptographic operations.

In conclusion, our work demonstrates the feasibility of platform-agnostic attestation verification despite distinct evidence formats and verification workflows across hardware platforms. The use of WebAssembly components enables us to encapsulate platform-specific verification logic and bundle it with the attestation evidence, thus providing the verifier with the right logic at the right time, in a platform-agnostic manner. This work lays the foundation for more unified, hardware-independent attestation systems.
