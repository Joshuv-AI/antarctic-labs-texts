CoreDPPL: Towards a Sound Composition of Differentiation, ODE Solving, and Probabilistic Programming
Oscar Eriksson, Anders Ågren Thuné, Johannes Borgström, David Broman

Abstract
. In recent years, there has been extensive research on how to extend general-purpose programming language semantics with domain-specific modeling constructs. Two areas of particular interest are (i) universal probabilistic programming where Bayesian probabilistic models are encoded as programs, and (ii) differentiable programming where differentiation operators are first class or differential equations are part of the language semantics. These kinds of languages and their language constructs are usually studied separately or composed in restrictive ways. In this paper, we study and formalize the combination of probabilistic programming constructs, first-class differentiation, and ordinary differential equations in a higher-order setting. We propose formal semantics for a core of such differentiable probabilistic programming language (DPPL), where the type system tracks random computations and rejects unsafe compositions during type checking. The semantics and its type system are formalized, mechanized, and proven sound in Agda with respect to abstract language constructs.



1.
Introduction

Mathematical modeling languages and tools are vital in science and engineering, using methods such as Bayesian probabilistic modeling and inference
(
Carpenter et al., 2017
;
Ghahramani, 2015
)
, equation-based modeling and simulation
(
Broman, 2010
;
Fritzson, 2014
)
, or differentiation as part of machine learning applications
(
Baydin et al., 2018
;
Rumelhart et al., 1986
)
.
A recent trend is to augment standard programming languages with domain-specific language constructs, thus enabling highly expressive modeling within higher-order general-purpose languages.
For instance,
probabilistic programming languages (PPLs)

(
Goodman et al., 2008
;
Murray and Schön, 2018
;
Wood et al., 2014
;
Goodman and Stuhlmüller, 2014
;
Bingham et al., 2019
;
Cusumano-Towner et al., 2019
;
Paquet and Staton, 2021
;
Lundén et al., 2022
;
Dash et al., 2023
;
Abril-Pla et al., 2023
)
is a class of modeling languages where probabilistic models can be formulated as programs.
Another direction is incorporating differentiation primitives as first-class language constructs, resulting in
differentiable programming
(cf.
Abadi and Plotkin (2019)
), which has a long history that goes back to
automatic differentiation
(AD) systems.
Differentiation in programming languages can take different forms;
in particular, machine learning and neural networks have reinvigorated research on the differentiation of programs (cf.
Baydin et al. (2018)
) as well as the inclusion of primitives for solving ordinary differential equations (ODEs) as part of the language (cf.
Benveniste et al. (2018)
).

Although the incorporation of probabilistic and differentiable primitives into general-purpose programming languages enables high modeling expressivity, a fundamental problem concerns the correctness of compositions:

how can program terms with both probabilistic and differentiation primitives be composed safely while still retaining sufficient expressivity?

For instance, taking the derivative of a function that includes randomness is generally not well-defined, and solutions to ODEs have continuity requirements on their derivatives that are easily violated when random effects appear without any restriction in the model.
Issues for differentiability include that in programs with branching, the derivative in the analytic sense is sometimes only well-defined piecewise, and realizations of, e.g., the Wiener process are not even piecewise analytic.

Traditionally, the correctness of PPLs
(
Borgström et al., 2016
;
Vákár et al., 2019
;
Lundén et al., 2021
;
Ścibior et al., 2018
)
and program differentiation
(
Mazza and Pagani, 2021
;
Abadi and Plotkin, 2019
;
Lee et al., 2020
;
Elliott, 2018
;
Krawiec et al., 2022
)
has been studied separately.
For differentiation, the notion of a derivative is either extended to piecewise analytic functions or the language restricts primitive Boolean operations to where the derivative is well-defined.
There are a few works that study the combination of differentiation and probabilistic programming in a formal setting, showing the correctness of forward-mode AD of functions returning expectations
(
Lew et al., 2023
)
, and defining an extended notion of derivatives in the context of AD transformation of PPL programs
(
Huot et al., 2023
)
.
There is, however, no comprehensive treatment on the correctness of combining the three parts (i) higher-order universal PPLs with inference operators, (ii) first-class differentiation operators, and (iii) first-class constructs for solving ODEs.

This paper studies a
differentiable probabilistic programming language (DPPL)
with (i) PPL constructs (
\mathbf{infer}
,
\mathbf{assume}
,
\mathbf{weight}
), (ii) first-class differentiation (a
\mathbf{diff}
construct), and (iii) ordinary differential equations (a
\mathbf{solve}
primitive) and how these can be composed in a higher-order language context.
Furthermore, we propose formal semantics for a higher-order DPPL calculus.
We take a different approach from previous work in that we develop a static semantics intended to separate deterministic and random parts of the program, as well as functions typed analytic, piecewise analytic, and non-differentiable.
A key idea of the static semantics is that the type system is based on effect
(
Lindley and Cheney, 2012
;
Lucassen and Gifford, 1988
;
Gaboardi et al., 2016
;
Leijen, 2014
)
and coeffect systems
(
Gaboardi et al., 2016
;
Petricek et al., 2014
;
Brunel et al., 2014
)
.
The dynamic semantics builds on previous work on PPL
(
Borgström et al., 2016
)
and AD
(
Lee et al., 2020
)
correctness, as well as ODE theory
(
Kelley and Peterson, 2010
)
.

More specifically, the contributions are as follows:

•

We illustrate key ideas of composition through a motivating example (
Section

2
).

•

We develop formal semantics with a novel type system for a core DPPL, where the type system guarantees that deterministically typed terms do not express random computations, that analytic derivatives are only taken on functions of analytic type, and that intensional derivatives are only taken on functions of piecewise analytic type (Sections
3
and
4
).

•

We formalize and mechanize proofs in Agda, proving type safety under the assumption of correct implementations of primitive operations and that deterministically typed terms cannot affect the random state (
Section

5
).

•

We implement the core DPPL for an extended subset of an existing compiled universal PPL (
Section

6
), and evaluate the implementation on several case studies (
Section

7
).

3.1.
Types, random effect modifiers, and differential coeffect modifiers

Figure

3
defines the syntax of CorePPL, where
\mathit{Var}
is the set of variable names. The main goal of the type system is to track randomness, using an effect modifier
e
on arrow types
T_{1}\to^{e}T_{2}
, and differentiability, using a co-effect modifier
c
on the real number type
\mathrm{R}_{c}
to ensure that the probabilistic and differential primitives only receive compatible arguments.

The effect modifier
e
can be either deterministic (
Det
) or random (
Rnd
), where a term typed
T_{1}\to^{\textsc{Rnd}{}}T_{2}
expresses a random function, where the return value may depend on a finite (but a priori unbounded) number of random draws from the primitive distributions discussed below.
The modifier
c
can be either analytic (
c=\textsc{A}{}
), PAP (
c=\textsc{P}{}
), or non-differentiable (
c=\textsc{N}{}
).
The types
\mathrm{R}_{\textsc{A}{}}
and
\mathrm{R}_{\textsc{P}{}}
correspond to the smooth and non-smooth types
\mathbb{R}
and
\mathbb{R}{}^{*}
, respectively, in
Lew et al. (2023)
.

Here, a term typed
\mathrm{R}_{\textsc{A}{}}\to^{\textsc{Det}{}}\mathrm{R}_{c}
expresses a scalar function typed as analytic, which naturally is deterministic.
Similarly, terms typed
\mathrm{R}_{\textsc{P}{}}\to^{\textsc{Det}{}}\mathrm{R}_{c}
and
\mathrm{R}_{\textsc{N}{}}\to^{\textsc{Det}{}}\mathrm{R}_{c}
express deterministic functions typed PAP and non-differentiable, respectively.

In the static semantics,
Section

4.1
,
e
is tracked in a lightweight effect system
(
Lucassen and Gifford, 1988
;
Lindley and Cheney, 2012
;
Leijen, 2014
)
, while
c
is tracked in a simplified coeffect system
(
Petricek et al., 2014
;
Brunel et al., 2014
;
Gaboardi et al., 2016
)
.
A key difference to standard coeffect systems is that we attach these differentiability modifiers to the base type
\mathrm{R}
rather than to arrow types and variables in the type environment.
The reason for this is two-fold: (i) differentiability is not applicable to all types, and (ii) it allows for less conservative reasoning on differentiability for functions with parameters of tuple type.

The remaining types are tuple types, where
\langle\rangle
is the empty tuple;
and distribution types, where
\mathrm{Dist}(T)
means a probability distribution whose support has type
T
.
For convenience we write a homogeneous
n
-tuple
\langle T,\dots,T\rangle
as
T^{n}
.
The syntactic sugar
\mathrm{R}_{\bar{c}}^{n}
denotes an
n
-tuple
\langle\mathrm{R}_{c_{1}},\dots,\mathrm{R}_{c_{n}}\rangle
of real numbers with
n
possibly different modifiers
(c_{1},\ldots,c_{n})\eqcolon\bar{c}
.
To reduce the notational burden, we make no distinction between
\langle T\rangle
and
T
.

3.2.
The Extended
\lambda
-calculus, Primitive Functions and Distributions, and Syntactic Sugar

For terms
t
and
f
, we reserve
f
for terms of function type. We will sometimes overload

to functions in the mathematical sense.
Terms consist of the simply typed
\lambda
-calculus extended with the standard primitive function application, where
\phi
ranges over primitive functions and

is its arity; real numbers; tuples; tuple projection, where we sometimes omit the tuple size
n
; and if-then-else-terms.
We omit boolean terms in our calculus for simplicity, but they are present in our implementation.

In our examples we use standard syntactic sugar for let expressions and sequencing, where we informally omit the type annotation.
We write
r^{n}
for an n-tuple of real numbers and also use sugar for pattern matching on tuples in both function parameters and let expressions.

Primitive functions (
\phi
) include elementary functions and probability density functions for the primitive distributions that possess them (
\texttt{D}{}^{\prime}=\{\mathcal{N},\mathcal{B}\}
).
The primitive functions also include a family
\text{wiener}_{p{}}
of realizations of the Wiener process (discussed in
section

3.4
), where
p{}
is an index into the set of all such realizations. More primitive functions can be added. We write primitive function applications with infix notation when appropriate.
Moreover, we reduce the notational burden and make no distinction between
\pi^{1}_{1}\;\;t
and
t
, and
\langle t\rangle
and
t
.

The remaining language primitives either relate to the probabilistic or the differential aspect of CoreDPPL.

3.3.
Probabilistic Terms

There are four primitives in the probabilistic aspect, beginning with primitive distributions
D
applied to a tuple of their parameters.
Primitive probability distributions
D
includes:
\mathcal{N}
, the normal distribution;
\mathcal{B}
, the beta distribution; and
\mathcal{W}
, the Wiener process. Other distributions can be added.

We model a prior distribution using
\mathbf{assume}{}\;t
, which draws a sample of type
T
from a distribution
t:\mathrm{Dist}(T)
while evidence is modeled with

\mathbf{weight}{}\;r
: a side-effecting operation that multiplies the weight of the current runtime state by

(see Definition
4.2
).
Given a probabilistic model
f:\langle\rangle\to^{\textsc{Rnd}{}}T
, the term
\mathbf{infer}{}\;f
infers a posterior distribution of type
\mathrm{Dist}(T)
.

The syntactic sugar
\mathbf{observe}\;t\;\texttt{D}^{\prime}(t_{1},\ldots,t_{|\texttt{D}^{\prime}|})\coloneq\mathbf{weight}\;\text{pdf}_{\texttt{D}^{\prime}}(t_{1},\ldots,t_{|\texttt{D}^{\prime}|},t)
conditions a probabilistic model on an observation
t
distributed according to the given distribution, where
\text{pdf}_{\texttt{D}^{\prime}}
is the probability density function of
\texttt{D}^{\prime}
.

As an example of a probabilistic term, consider the scalar regression model

, where

are observable outputs,

are known inputs,

is an unknown parameter independent of

is Gaussian measurement noise.
Moreover, assume

Then, omitting type annotation for brevity; using syntactic sugar for let bindings, tuple iteration and destruction, and sequencing; and the term

(1)

\displaystyle\mathbf{let}\;\textsc{model}=\lambda\_.

express the posterior distribution of the parameter

3.4.
Differential Terms

For simplicity we here discuss the scalar derivative
\mathbf{diff1}_{d{}}\;f\;r
, which expresses the derivative of a deterministic function
f:\mathrm{R}_{d{}}\to^{\textsc{Det}{}}\mathrm{R}_{c}
at the point
r
.
Note that the modifier
d
(
Figure

3
) is on the function argument and not the result type: it denotes that the term
\mathbf{diff1}_{d{}}
expresses the derivative of either an analytically typed function (
d
=
A
), or the intensional derivative of an PAP typed function (
d
=
P
).
The general differentiation term
\mathbf{diff}_{d{}}\;f\;r^{n}
, which expresses the total derivative.

Taking the analytic derivative of a quadratic polynomial, the term

(2)

\mathbf{let}\;y=\lambda x:\mathrm{R}_{\textsc{A}{}}.\;x\cdot x+x\;\mathbf{in}\;\mathbf{diff1}_{\textsc{A}{}}\;y\;r

is well-typed because
y
is a composition of primitive analytic functions (scalar addition (
+
) and multiplication (
\cdot
)).
In contrast, since the absolute value function does not have an analytic derivative at zero, the following term is not typeable due to the
A
annotation on the argument:

(3)

\lambda x:\mathrm{R}_{\textsc{A}{}}.\;\mathbf{if}{}\;x>0\;\mathbf{then}{}\;x\;\mathbf{else}{}\;0-x.

However, (
3
) has a well-defined intensional derivative since it has a PAP representation (and is, therefore, a PAP function)
(
Lee et al., 2020
)
.
We can show this by dividing the domain of the function into two analytic intervals,
\mathbb{R}_{\leq 0}
and
\mathbb{R}_{>0}
, associated with the analytic functions
x\mapsto-x
and
x\mapsto x
, respectively.
The notion of an intensional derivative is important because it captures the semantics of almost all derivatives expressed using AD
(
Huot et al., 2023
)
,
so

(4)

\mathbf{let}\;y=\lambda x:\mathrm{R}_{\textsc{P}{}}.\;\mathbf{if}{}\;x>0\;\mathbf{then}{}\;x\;\mathbf{else}{}\;0-x\;\mathbf{in}\;\mathbf{diff1}_{\textsc{P}{}}\;y\;r

is well-typed in our type system.
The type system also allows us to replace the modifier
A
in (
2
) with modifier
P
since an analytic function is a PAP function with one analytic interval (the whole of
\mathbb{R}
in this case), and we also allow the use of an analytically typed function in contexts that expect a PAP typed function.

Our type system distinguishes between analytically typed and PAP typed functions by propagating coeffects and constraining the comparand
t
in

\mathbf{if}{}\;t>0\;\mathbf{then}{}\;t_{1}\;\mathbf{else}{}\;t_{2}

to the type
\mathrm{R}_{\textsc{P}{}}
.
Relating the probabilistic and the differential part of CoreDPPL, the term

(5)

\mathbf{let}\;y=\mathbf{assume}{}\;t\;\mathbf{in}\;\mathbf{diff1}_{d{}}\;(\lambda x:\mathrm{R}_{d{}}.\;y)\;r

is well-typed when
t
has the appropriate type because once sampled, the sample
y
is deterministic in the body of the let term.

The primitive distributions (
Figure

3
) include the distribution
\mathcal{W}
over Wiener processes, which allows us to express so-called Random ODEs (RODEs)
(
Neckel et al., 2017
;
Imkeller and Schmalfuss, 2001
)
by composing PPL constructs and
\mathbf{solve}
(see the example in
Section

7.2
).
An interesting property of realizations of the Wiener process is that they are continuous deterministic scalar functions but nowhere differentiable, neither in the analytic nor the intensional sense.
We therefore type
\mathcal{W}()
as
\mathrm{Dist}(\mathrm{R}_{\textsc{N}{}}\to^{\textsc{Det}{}}\mathrm{R}_{\textsc{N}{}})
, which gives its samples (or realizations) the type
\mathrm{R}_{\textsc{N}{}}\to^{\textsc{Det}{}}\mathrm{R}_{\textsc{N}{}}
. This type cannot be differentiated since the modifier on the function argument must be
A
or
P
.
On the other hand, as we discuss in
Section

4.1
, because we track the coeffect modifiers
c
on the type
\mathrm{R}
, the type system allows terms like

(6)

\mathbf{let}\;w=\mathbf{assume}{}\;\mathcal{W}()\;\mathbf{in}\;\mathbf{let}\;z=\lambda\langle x,y\rangle:\langle\mathrm{R}_{\textsc{N}{}},\mathrm{R}_{\textsc{A}{}}\rangle.\;w\;x+y\;\mathbf{in}\;\mathbf{diff1}_{\textsc{A}{}}\;(\lambda u:\mathrm{R}_{\textsc{A}{}}.\;z\;\langle r,u\rangle)\;r,

even though
z
includes a realization of the Wiener process, since
z
is typed analytic in its second parameter
y
(but not the first).

There is no limitation in using terms typed
\mathrm{R}_{\textsc{N}{}}
in the comparand term of if-then-else expressions because the type system can safely coerce terms typed
\mathrm{R}_{\textsc{N}{}}
to the required type
\mathrm{R}_{\textsc{P}{}}
.

The term
\mathbf{solve}\;f\;r^{n}\;r
expresses a solution
y(x)
, at
x=r
, to the Initial Value Problem (IVP) that consists of the ODE
\frac{dy(x)}{dx}=f(x,y(x))
(we consider vector-valued ODEs because they can express systems of ODEs and refer to
x
as time) and initial values

.
CoreDPPL expects the term

The typing judgment takes the form

What is unusual is, like

A random expression will be typed with a modifier

Both these terms have the type

The effect modifiers

The treatment is strongly inspired by languages with effect systems, such as Links

and Koka

The handling of coeffects and the combination of coeffects and effects are inspired by

The rules
T-Sub
and
T-Promote
allow us to coerce between effects and coeffects safely.

T-Sub
is a form of weakening: whenever a piece of data is allowed to be used in a non-differentiable context, it can also safely be passed into a differentiable context.
Similarly, it is safe to use a deterministic function in a random context, but not vice-versa.
On the other hand,
T-Promote
is a form of strengthening, which says that a differentiable piece of data can be used in a non-differentiable context, provided that it was constructed using only non-differentiable components.

The rule

allows us to drop unused bindings from the type environment so that

Figure

4

This is essential to not make the type system overly conservative.

The rule

requires that the term we differentiate is a deterministic function. Moreover, the term
\mathbf{diff}_{d{}}
is parametrized by

The type in the conclusion is attached to the total derivative, which is a
linear function
and, therefore, typed analytic.
The rule
T-Solve
requires that ODEs are deterministic but not necessarily typed differentiable.
In
Section

4.3

We restrict

Moreover, we restrict the type of

Section

,

has the meaning of a differentiable ODE integration routine, and it is therefore not sensible to type the IVP solution as analytic w.r.t. time.

4.2.
Comparison with Other Coeffect Systems

A key feature of our presentation of coeffects, compared to, e.g.,
Petricek et al. (2014)
, is that we attach coeffect modifiers to the type
\mathrm{R}
rather than to arrow types and bindings in the typing environment. The main reason for this is that the modifier
c
only bears meaning for (vectors of) reals.
Attaching modifiers only to the base type
\mathrm{R}
also gives us more fine-grained coeffect tracking for tuple types, at the expense of additional annotations.
Consider for example the function

(9)

f=\lambda x:\mathrm{R}^{2}.\;\text{wiener}_{p{}}(\pi_{1}\;x)+\pi_{2}\;x.

A system where only the parameter
x
carries a coeffect would have to attach the modifier
N
to
x
, since it appears as an argument to
\text{wiener}_{p{}}
(cf. (abs), (app) in Figure 4 in
Petricek et al. (2014)
).
Moreover, such a system would also attach
N
to
y
in
g=\lambda y:\mathrm{R}.\;f\;\langle 0,y\rangle
, even though
y
is never passed as an argument to
\text{wiener}_{p{}}
.
For example, the term

(10)

\vdash\mathbf{diff}_{\textsc{A}{}}\;(\lambda y:\mathrm{R}_{\textsc{A}{}}.\;(\lambda x:\langle\mathrm{R}_{\textsc{N}{}},\mathrm{R}_{\textsc{A}{}}\rangle.\;\text{wiener}_{p{}}(\pi_{1}\;x)+\pi_{2}\;x)\;\langle 0,y\rangle)\;1

is well-typed in our type system, which would not be the case if
y
had a single (conservative) modifier.

Compared to
Gaboardi et al. (2016)
;
Petricek et al. (2014)
, most explicit occurrences of multiplication can be removed from the typing rules since coeffect multiplication is just the maximum in our system, and
T-Sub
allows lowering coeffects (and raising effects).
For example, the rule
T-Promote
in our system directly corresponds to the rule
pr
in the system of
Gaboardi et al. (2016)
, since having an environment
c\cdot\Gamma
in the conclusion becomes the same as having a condition
c\leq\Gamma
in the premise (and the comonad
D_{r}
in their rule corresponds to multiplication on the result type).
Finally, the distributive laws of
Gaboardi et al. (2016)
are trivial in our system since our effects and coeffects have no interesting interaction.

5.
Mechanized Semantics and Type Safety

This section presents the main theorems and summarizes the proofs from the Agda formalization
2
2

2

https://github.com/miking-lang/dppl-formalization
of the semantics in
Section

4
, based on the formalization of locally nameless sets by
Pitts (2023)
.

We consider top-level terms in a deterministic context, with typing judgments
\vdash t:^{\textsc{Det}{}}T
.
We want well-typed terms to be safe, in the sense of the standard type-safety guarantee that we can always reduce closed, well-typed terms to values.
Moreover, we want deterministically typed terms (i.e., typed with the
\Gamma\vdash t:^{\textsc{Det}{}}T
relation) to be independent of the random seed and weight when executed in a probabilistic context.

In the formalization, the semantics is parameterized on total functions for
Diff
,
Solve
, and
Infer
for differentiation, IVP solving, and sampling from inferred distributions.
The terms returned from these functions are assumed to have the appropriate type in any type environment where the arguments to the functions do.

As is common, we prove type safety via theorems of progress and preservation.
Progress guarantees that a well-typed term
t
is either a value or can be reduced one step, and preservation guarantees that reductions are type-preserving.
The deterministic reduction relation
t\rightarrow^{\textsc{Det}{}}t^{\prime}
(
Figure

7d
) internally depends on the sample-based reduction relation
(t,w,s)\to^{\textsc{Rnd}{}}(t^{\prime},w^{\prime},s^{\prime})
(
Figure

7e
) in the rule
E-Infer
.
Hence, we also prove progress and preservation for terms typed
\vdash t:^{\textsc{Rnd}{}}T
.
The theorems follow.

Theorem 5.1 (Progress
Det
).

Suppose
\vdash t:^{\textsc{Det}{}}T
holds. Then either
t
is a value or else there is some
t^{\prime}
such that
t\rightarrow^{\textsc{Det}{}}t^{\prime}
.

Theorem 5.2 (Preservation
Det
).

If
\vdash t:^{e}T
and
t\rightarrow^{\textsc{Det}{}}t^{\prime}
, then
\vdash t^{\prime}:^{e}T
.

Theorem 5.3 (Progress
Rnd
).

Suppose
\vdash t:^{e}T
holds. Then either
t
is a value or else for any
w
,
p
, and
s
, there are
t^{\prime},w^{\prime},
and
s^{\prime}
such that
(t,w,p{}::s)\rightarrow^{\textsc{Rnd}{}}(t^{\prime},w^{\prime},s^{\prime})
, where
p
in
p{}::s
denotes the head of a seed and
s
its remainder.

Theorem 5.4 (Preservation
Rnd
).

If
\vdash t:^{e}T
and
(t,w,s)\rightarrow^{\textsc{Rnd}{}}(t^{\prime},w^{\prime},s^{\prime})
, then
\vdash t^{\prime}:^{e}T
.

We are now ready to prove our main theorem on type safety.

Theorem 5.5 (Type Safety).

If
\vdash t:^{\textsc{Det}{}}T
and
t\rightarrow^{\textsc{Det}{}*}t^{\prime}
for some irreducible
t^{\prime}
, then
t^{\prime}
is a value.

To prove that deterministically typed terms are not influenced by probabilistic effects, we first show that deterministic reduction of deterministically typed terms
\Gamma\vdash t:^{\textsc{Det}{}}T
is indeed deterministic.

Theorem 5.6 (Determinism
Det
).

If
t\rightarrow^{\textsc{Det}{}}t_{1}
and
t\rightarrow^{\textsc{Det}{}}t_{2},
then
t_{1}=t_{2}
.

Similarly, given a seed, a term typed
\Gamma\vdash t:^{\textsc{Rnd}{}}T
will reduce deterministically.

Theorem 5.7 (Determinism
Rnd
).

If
(t,w,s)\rightarrow^{\textsc{Rnd}{}}(t_{1},w_{1},s_{1})
, and

(t,w,s)\rightarrow^{\textsc{Rnd}{}}(t_{2},w_{2},s_{2}),
then
t_{1}=t_{2}\land w_{1}=w_{2}\land s_{1}=s_{2}
.

As a corollary to Theorems
5.1
and
5.7
, a term typed
\vdash t:^{\textsc{Det}{}}T
will never change the seed or weight in the
\rightarrow^{\textsc{Rnd}{}}
relation.
This holds since
t
will either be a value or have a transition that does not affect the weight and seed (using rule
E-Det
), and by determinism, any other transition must give the same result.

Corollary 5.8.0.

If
\vdash t:^{\textsc{Det}{}}T
holds, then for all
w,s,t^{\prime},w^{\prime}
, and
s^{\prime}
such that
(t,w,s)\rightarrow^{\textsc{Rnd}{}*}(t^{\prime},w^{\prime},s^{\prime})
, we have
w=w^{\prime}\land s=s^{\prime}
.

We implement a prototype of CoreDPPL as an extended subset of the compiler for the universal probabilistic programming language Miking

3

7.1.
A: Two Methods of ODE Sensitivities

Figure 8
.
Sensitivities of the Lotka-Volterra model for the prey (green) and predator (red) densities w.r.t. the prey per-capita growth rate parameter, using

Gradient-based optimization techniques, such as gradient descent, require the gradient of the objective function. Suppose the objective function, in turn, solves an IVP parameterized on the variables of the objective function. In that case, the gradient of the objective function includes the derivative of the solution of the ODE w.r.t. its parameters. These are known as the sensitivities of the ODE.
A parameterized ODE model generally has
n_{y}
states and
n_{\theta}
parameters.
For now, assume the scalar case
n_{y}=n_{\theta}=1
, and we discuss the general case at the end of this example.
The composition of
\mathbf{diff}
and
\mathbf{solve}
allows us to express the sensitivities,
s_{\theta}(x)=\frac{dy(x)}{d\theta}
, w.r.t. to a single parameter
\theta\in\mathbb{R}
in two ways depending on whether we nest
\mathbf{diff}
in
\mathbf{solve}
or vice versa.

For both cases, assume a smooth parameterized scalar model
\textsc{ODE}:\mathrm{R}_{\textsc{A}{}}\to\langle\mathrm{R}_{\textsc{A}{}},\mathrm{R}_{\textsc{A}{}}\rangle\to\langle\mathrm{R}_{\textsc{A}{}}\rangle
with the initial value
y_{0}
.
We can express
s_{\theta}(x)
by differentiating
\mathbf{solve}
as

(17)

\lambda\theta:\mathrm{R}_{\textsc{A}{}}.\;\lambda x:\mathrm{R}_{\textsc{P}{}}.\;\mathbf{diff1}_{\textsc{A}{}}\;(\lambda\theta:\mathrm{R}_{\textsc{A}{}}.\;\mathbf{solve}\;({\textsc{ODE}\;\theta)}\;y_{0}\;x)\;\theta.

We may also compute the ODE sensitives by augmenting the ODE with an additional equation.
Differentiation of both sides of the ODE equation w.r.t.
\theta
gives

(18)

\frac{d}{d\theta}\frac{dy}{dx}=\frac{d}{d\theta}f\Longleftrightarrow\frac{d}{dx}\frac{dy}{d\theta}=\frac{df}{dy}\frac{dy}{d\theta}+\frac{df}{d\theta}\Longleftrightarrow\frac{ds}{dx}=\frac{df}{dy}s+\frac{df}{d\theta},

where
y=y(x)
,
s=s(x)
,
f=f(x,y(x);\theta)
,
and
\frac{df}{d\theta}
should be read as the derivative of
f({}\cdot{},{}\cdot{};\theta)
w.r.t. to its third argument
\theta
.
Hence, we can augment our ODE with (
18
) to compute the sensitivity. We can, therefore, also express the sensitivities as

(19)

\begin{array}[]{ll}\lambda\theta:\mathrm{R}_{\textsc{A}{}}.\;\lambda x:\mathrm{R}_{\textsc{P}{}}.&\mathbf{let}\;z=\lambda\langle x,\langle y,s\rangle\rangle.\\
&\quad\mathbf{let}\;\textsc{ODE}=\lambda\theta:\mathrm{R}_{\textsc{A}{}}.\;\lambda y:\mathrm{R}_{\textsc{A}{}}.\;\textsc{ODE}\;\theta\;\langle x,y\rangle\\
&\quad\mathbf{in}\;\langle\textsc{ODE}\;\theta\;y,(\mathbf{diff1}_{\textsc{A}{}}\;(\textsc{ODE}\;\theta)\;y)\cdot s+\mathbf{diff1}_{\textsc{A}{}}\;(\lambda\theta:\mathrm{R}_{\textsc{A}{}}.\;\textsc{ODE}\;\theta\;y)\;\theta\rangle\\
&\mathbf{in}\;\mathbf{let}\;\langle y,s\rangle=\mathbf{solve}\;z\;\langle y_{0},0\rangle\;x\;\mathbf{in}\;s,\end{array}

where we extend the original parameterized model,
ODE
, with the sensitivity model and project the sensitivities from the extended IVP solution.
The benefit of (
19
) is that we can get the sensitivities without requiring that
\mathbf{solve}
is differentiable, which lets us implement it using some external solver library.
The idea of differentiating the ODE solver to compute sensitivities, Equation (
17
), is not new
(
Carmichael et al., 1997
;
Eberhard and Bischof, 1999
)
, but it demonstrates the expressiveness of a language with both
\mathbf{diff}
and
\mathbf{solve}
.

Figure

8
shows the sensitivities of an example ODE for the two different methods for computing sensitivities in our implementation as generalized to non-scalar ODEs (

).

7.3.
C: Bayesian Parameter Estimation and ODE Sensitivities

As we discussed in

The parameter estimation problem for non-linear state space models consists of an ODE,

is the solution,

\theta

For example,

can model the relation between invisible internal states
y(x)

The example in

8.
Related Work

8.1.
Differentiable Programming, and IVP Solutions

Carmichael et al. (1997)
and
Eberhard and Bischof (1999)
study differentiation of ODE integration routines to compute ODE sensitivities.
More recently,
Ma et al. (2021)
compare the performance of traditional methods for computing sensitivities to solver differentiation in the
Julia
language.
Neither of these works studies the composition of IVP solutions and differentiation in a formal language context.

From a more fundamental mathematical perspective,
Gofen (2009)
studies the relation between AD and solutions to IVPs. The author discusses a wider definition of elementary functions, from the standard set of tabulated functions to solutions of a certain class of ODEs.
Because AD is driven by the differentiation of elementary functions, with this extended notion of elementary functions, IVP solving constitutes a method for AD, while at the same time, AD constitutes a method for solving IVPs via Taylor integration. Although our work is more programming language-oriented, these results illustrated interesting aspects of the composition of IVP solving and program differentiation.

As demonstrated by
Bangaru et al. (2021)
, languages that include an integration primitive
(
Bangaru et al., 2021
;
Sherman et al., 2021
)
can express solutions to separable ODEs. In contrast, the IVP
\mathbf{solve}
primitive allows the solution of both separable and non-separable ODE models.

ProbZelus

(
Baudart et al., 2020
)
extends the hybrid synchronous language
Zelus

(
Benveniste et al., 2018
)
, which extends synchronous languages with declarative ODE models, with PPL constructs.
Their formalization does not explicitly include ODE models. Their static semantics separate deterministic and non-deterministic computations by decorating the typing judgment and arrow types like CoreDPPL does with the effect modifier
e
.

ProbZelus
does not include program differentiation.

The PPL framework
PyMC

(
Abril-Pla et al., 2023
)
and the PPL
Stan

(
Carpenter et al., 2017
)
explicitly include an IVP solver primitive. In addition,
PyMC
supports differentiation through a tensor library based on
Theano

(
Al-Rfou et al., 2016
)
.
Naturally, these works are implementation-focused, while our work studies the idea of differentiable probabilistic programs in a formal language setting.
In contrast to
Stan
, our type system tracks different notions of differentiability and randomness, which allows it to reject a larger class of ill-defined programs at compile time.

PyMC
is a framework built in Python and, therefore, lacks a static type system.

8.2.
Differentiable Programming and Probabilistic Programming Languages

Borgström et al. (2016)
give an operational semantics for an untyped
\lambda
-calculus extended with probabilistic language constructs, forming a universal PPL, and we base our PPL semantics on this work.
In the traditional presentation of PPLs (as exemplified by Borgström), each program encodes a measure over result values; in other words, the whole program is probabilistic. A more recent line of work
(
Heunen et al., 2017
;
Ścibior et al., 2018
;
Vákár et al., 2019
;
Matache et al., 2022
;
Dash et al., 2023
)
describes how probability measures form a monad over quasi-Borel spaces
(
Heunen et al., 2017
)
, which gives a natural model of computation where deterministic and probabilistic programs can co-exist.

There are several works on the correctness of AD (e.g.,
(
Mazza and Pagani, 2021
;
Abadi and Plotkin, 2019
;
Huot et al., 2023
;
Lee et al., 2020
;
Krawiec et al., 2022
;
Elliott, 2018
;
Barthe et al., 2020
)
) and a large body of more implementation focused works on AD (e.g.,
(
Siskind and Pearlmutter, 2008
;
Wang et al., 2019
;
Shaikhha et al., 2019
;
Pearlmutter and Siskind, 2008
)
and
Baydin et al. (2018)
gives a survey for machine learning applications).
Our work directly uses the notion of intensional derivatives introduced by
Lee et al. (2020)
.

Huot et al. (2023)
build upon both these lines of work, extending quasi-Borel spaces into
\omega
PAP spaces to support differentiation, investigating semantic properties such as the differentiability of the density functions of probabilistic programs.
Lew et al. (2023)
go in a slightly different direction, considering automatic differentiation of expected values of probabilistic programs using a similar semantic foundation. Their type system distinguishes between smooth and non-smooth types, and the language includes a coercion operation from non-smooth to smooth types, while our language handles this coercion in the type system.
The smoothness tracking of
Lew et al. (2023)
is also present in
Becker et al. (2024)
which includes a type rule to implicitly convert non-smooth types to smooth types similar to our
T-Sub
with
T=\mathrm{R}_{\textsc{P}{}}
and
T^{\prime}=\mathrm{R}_{\textsc{A}{}}
.

Lee et al. (2023)
propose a static smoothness analysis for a formal imperative PPL based on abstract interpretation with applications toward variational inference.

Barthe et al. (2020)
demonstrates the power of open logical relations by proving continuity properties for a language with if-then-else constructs and refinement types.
We instead track smoothness via a coeffect-based type system and plan to base a future proof on the differentiability properties of our language on the technique of Barthe et al.
Neither of these works considers a first-class differentiation operator as part of the PPL syntax.

Sherman et al. (2021)
propose a higher-order differentiable programming language,
\lambda_{s}
, with a first-class derivative, root finding, optimization, and integration primitives.
The integration primitive, defined over the compact domain
[0,1]
, allows
\lambda_{s}
to express certain probability distributions.

\lambda_{s}
generalized the notion of derivatives to
Clarke
derivatives
(
Clarke, 1975
)
while our type system instead distinguishes between different notions of derivatives.

Michel et al. (2024)
extends program differentiation to correctly differentiate parametric discontinuities in a first-order language.

8.3.
Effects and Coeffects

Languages with effect systems, such as Koka
(
Leijen, 2014
)
or Links
(
Lindley and Cheney, 2012
)
, allow users to write direct-style code with multiple effects, implicitly representing a monadic computation.
More generally, the idea of using monads to model alternative notions of computation (or effects) has a long history in the field (see, e.g.,
Moggi (1991)
). These type systems can statically enforce a separation between effectful and pure code.

Complementary to effects is the notion of coeffects that allows the static reasoning about how function parameters are used in a program
(
Petricek et al., 2014
;
Brunel et al., 2014
)
.

Gaboardi et al. (2016)
develops a calculus for combining effects and coeffects via effect-graded monads, and the type system of CoreDPPL is directly inspired by these works.

9.
Conclusion

This paper studies safe composition in differentiable probabilistic programming, which combines the domains of differentiable programming, ordinary differential equations, and probabilistic programming languages.
It demonstrates the concept of differentiable probabilistic programming on a series of examples and
develops formal semantics for a core differentiable probabilistic programming language.
In particular, the static semantics track randomness through an effect-based system and different notions of differentiability through a coeffect-based system.
This ensures the type system can reject ill-defined derivatives and ordinary differential equation models.
Moreover, it provides mechanized type soundness proofs and mechanized proofs of the static separation between deterministic and random terms.

One avenue for increased expressiveness is to extend
\mathbf{solve}
to Differential-Algebraic Equations (DAEs), which are implicit ODEs with additional algebraic constraints.
DAEs allow physical modeling from first principles and are the fundamental representation of equation-based modeling languages
(
Broman, 2010
)
, but solving them typically requires systematic differentiation of their individual equations
(
Petzold, 1982
)
.
It seems possible to combine our type system with known DAE structure analysis algorithms
(
Pantelides, 1988
;
Pryce, 2001
)
to statically reject certain ill-formed DAEs combined with PPL constructs. However, further research work is needed to study this in a formal setting.

Connecting the static and dynamic semantics, it remains to be proved that well-typed functions with parameter type
\mathrm{R}_{\textsc{A}{}}^{n}
and parameter type
\mathrm{R}_{\textsc{P}{}}^{n}
are indeed analytic and PAP functions, respectively. More research is needed on a suitable domain for this proof, that also admits the semantic implementing functions
Infer
,
Diff
, and
Solve
.

Another direction of future work is coeffect and effect modifier inference. The sub-typing relation in our type system only considers these modifiers. Since they are related by simple inequalities, this would produce constraints similar to those for existing type inference algorithms for linear types
(
Matsuda, 2020
)
.
Coupled with appropriate error messages, this extension would spare the user details in the type system while retaining its static guarantees.

Appendix A
Lotka-Volterra Model

The Lotka-Volterra predator-prey model is defined as the following coupled ODEs:

(21)

\begin{cases}\frac{d}{dx}y_{1}&=\theta_{1}y_{1}-\theta_{2}y_{1}y_{2}\\
\frac{d}{dx}y_{2}&=\theta_{3}y_{1}y_{1}-\theta_{4}y_{1},\end{cases}

where
y=y(x)
;
y_{1}
and
y_{2}
are prey and predator densities, respectively;
\theta_{1}
and
\theta_{3}
are the per-capita growth rate of prey and predators, respectively;
\theta_{2}
is the prey death rate from predators; and
\theta_{4}
is the predator death rate from a lack of prey.
