A parallel pull labelling algorithm for the resource constrained shortest path problem
Bjørn Petersen, Simon Spoorendonk

Abstract
The Resource Constrained Shortest Path Problem (RCSPP) is a fundamental combinatorial optimisation problem in which the goal is to find a least-cost path in a directed graph subject to one or more resource constraints. In this paper we present a pull labelling algorithm for the RCSPP that introduces i) a highly parallelisable approach at a label bucket level, ii) an extension to bi-directional search with a dynamic midpoint, and iii) a vectorised dominance criterion that uses vector instructions to speed-up the label comparison with another level of parallelisation. Compared to a baseline version of the algorithm the optimisations result in a speed-up of around 14x on a set of hard instances and up to 200x on some of the hardest instances. The proposed algorithm demonstrates significant computational improvements that may enhance the efficiency of column generation frameworks incorporating resource constrained shortest path sub-problems, potentially enabling the efficient solution of larger-scale instances in routing, scheduling, supply chain and transportation network optimisation applications.

Pull labelling algorithms in the context of the RCSPP has to our knowledge not been studied in the literature.
A pull labelling algorithm extends paths by pulling feasible labels
from predecessor buckets, allowing for a highly structured and cache-friendly implementation that is well suited for parallelisation.
Each bucket can be pulled to independently of other buckets which allows to perform dominance checks in parallel for each bucket
without conflicting memory accesses.

Dominance checks are often performed one by one. Vector instructions can be used to perform the dominance checks in parallel.
By storing the state of the labels in a struct of arrays per resource, vectorized comparisons can be performed efficiently.

The main contribution of this paper is a pull labelling algorithm that is highly parallelisable at the label-bucket level.
It incorporates a bi-directional search with a dynamically determined midpoint and introduces a vectorised dominance criterion
that exploits vector instructions, Single Instruction Multiple Data (SIMD), to accelerate label comparisons.
The vectorised dominance test provides an additional level of parallelism within each bucket comparison, substantially reducing computational overhead.

2
Pull and Push Labelling Algorithms

The basic component in labelling algorithms is the label. A label is an object representing a (partial) path and contains properties
like the pointer to the parent label, the vertex, the cost, and the state with current resource accumulations.

The first label at the origin represents an empty path with initial values set accordingly, usually at zero cost and minimum resource accumulations.
For bi-directional labelling an additional first label is created at the target vertex with initial values set
at minimum cost and maximum resource accumulations.
REFs are reversed for backward labelling such that resource accumulation in general is decreasing when going backwards.

Labelling is an enumeration scheme where paths are grown by extending labels one edge at a time.
The extension function propagates the path over an edge by applying the REFs to the resource accumulations. For correctness it is important the
extension of labels is done according to a non-decreasing function, i.e., a REF has to monotonically increase the
resource accumulation to guarantee convergence. For graphs with negative-cost cycles the correct extension function is often the a resource
such as the time or capacity accumulation on the path.

A pull algorithm works by pulling labels into a vertex from several neighbouring vertices as opposed to a push algorithm where labels are pushed
from a vertex into its neighbouring vertices, see
Figure 1
. Extended labels are stored at the vertex
to which they are pulled or
pushed to, respectively. Pulling labels allows to update labels created at the pulling vertex independent of other vertices.
This is in contrast to pushing labels where all the neighbours must be updated. This is a key advantage for
parallelisation as it allows running the update of labels in parallel without conflicting writes.
Furthermore, it provides a control over the order of creation of labels which allows us to test if the
new labels are dominated and can be discarded or should be put into storage. Note that labels, when
created, are Pareto optimal by construction, therefore one can store labels efficiently as immutable data structures.

2.1
Buckets

Buckets are used to group labels into intervals of resource accumulation within a vertex, see
[
8
]
.
Buckets allow for the optimisation of dominance checks by only comparing with labels in relevant buckets and use
quick rejections on minimal label costs for a bucket.
In the pull labelling algorithms all labels are constructed in a way so all buckets are relevant because the pulling scheme dictates exactly
that only relevant labels are pulled to a bucket. Hence, quick
rejections are not relevant here. Buckets can be used to split up vertices into smaller chunks and in a pull
algorithm it directly allows us to do parallelisation at a bucket level.

Using buckets one can transform the original graph into a graph between buckets, this results in larger graphs, but when
buckets sizes are sufficiently small one obtains a directed acyclic graph of buckets.

It is key to have a small enough bucket size to avoid cycles in the dependency graph. Otherwise labels are not necessarily
created in the right order to ensure immutability as buckets may need to be processed and pulled several times making the storage less
efficient as constructed labels may later be dominated by other labels.
[
8
]
allows small cycles in
their labelling bucket algorithm, but the memory impact was likely smaller as they use a push approach and need to dominate created labels.

The size of the buckets can be determined by the smallest ingoing edge, then the size of the buckets is small enough to avoid cycles.
Selecting the proper bucket size gives rise to several trade-offs: i) larger buckets gives less overhead of parallelism,
ii) smaller buckets gives fewer dependencies but may result in buckets with few labels, and iii)
avoid cyclic dependencies to maintain order of creation and storage efficiency.

In practice, one seeks large buckets that are still small enough to avoid cycles between buckets.

3.1
Parallel Read/Write

The dependency graph is constructed in a way to easily allow buckets to be processed in parallel.
Buckets not released for processing are not touched, i.e., there is no read/write activity in the bucket.
Released buckets are only dependent on finished buckets and can be updated in parallel (one thread per bucket)
without issues as they only write to the bucket itself. No other bucket is concurrently reading from the bucket
before it is finished being updated.

Processed buckets are not updated again. Hence, there is no write activity in the bucket and
read can be done in parallel without implications. This is illustrated in
Figure 5
.
This allows for a simple implementation without mutexes to control the processing of buckets.
When no buckets are left for processing the algorithm is finished.

4.2
Dynamic Midpoint

To minimize the total number of labels, the midpoint should be chosen such that the number of forward and backward labels are balanced.

For the bi-directional search the algorithm stops when a label’s resources accumulation on a specified
non-decreasing resource has reached the midpoint value. The midpoint can be fixed up front, e.g., to the half
\lceil b^{t}_{r}/2\rceil

of the resource bound for resource used as the primary
extension function.

As proposed by
[
10
]
, a dynamic midpoint can be determined to avoid skewing of the number of
labels in the forward and backward propagation by extending in the direction of the fewest labels first.

Consider three distinct queues for forward, backward and splice jobs. Additionally keep track of the number of forward and backward
buckets that have been processed. When choosing the next task to process the algorithm will prioritize first the splice jobs and then the forward
or backward job with the least processing count. This ensures that the number of forward and backward labels are relatively fairly balanced.

Observe, that a specific value for the midpoint is never determined. Instead, the algorithm will continue in either direction until equally
many forward and backward buckets have been processed.

5
Vectorised Resource Comparison

An essential part of the labelling algorithm is the dominance check where a label is compared to others to
determine if it is dominated and can be pruned. Often, this is done by comparing labels individually. That is, the newly
extended label is compared to all previously created labels at a given vertex. This is a sequential process and can be parallelised by
comparing labels in parallel.

5.1
Dominance

Consider a label
L
at a given vertex where
\mathcal{E}(L)

is the set of valid extensions of the label from
v
to the target vertex. The dominance criterion can be defined as follows:

Definition 1

(Dominance)
.

Label
L_{1}
dominates label
L_{2}
if:

\exists\epsilon_{1}\in\mathcal{E}(L_{1}):cost(L_{1}+\epsilon_{1})\leq\min_{\epsilon_{2}\in\mathcal{E}(L_{2})}\{cost(L_{2}+\epsilon_{2})\}

i.e.
L_{1}
is part of a path costing no more than the least cost path containing
L_{2}
.
As not all possible extensions of a label are known, a sufficient condition is used to determine if a label is dominated.

Lemma 1

(Sufficient condition)
.

Label
L_{1}
dominates label
L_{2}
if:

\begin{aligned} v(L_{1})&=v(L_{2})\\
cost(L_{1})&\leq cost(L_{2})\\
r(L_{1})&\leq r(L_{2}):\forall r\in R\end{aligned}

Based on the sufficient condition a natural order of labels can be defined

Lemma 2

(Dominance order)
.

Given a lexicographical order of labels
L_{1}
and
L_{2}
corresponding to Lemma
1
then

L_{1}\preceq_{dom}L_{2}\Rightarrow L_{1}\leq^{lex}L_{2}

That is, if a label is dominated by another label then it is after the other label in the dominance order.
If labels are created in accordance with Lemma
2
then created labels are either dominated on
creation or will live forever and allow labels to be stored as immutable objects at a fixed position in memory.
This leaves a minimal memory footprint and ensures that moving and copying labels are avoided which would have
been the case if labels could be dominated and removed at a later point after creation.

Using vector instructions, label properties can be compared in parallel.

6.1
Instances

Instances are generated as pricing problems of the root nodes when solving the Solomon instances
for the vehicle routing problem with time windows (VRPTW) using column generation.

The 56 original instances are divided into six classes: R1, R2, C1, C2, RC1, and RC2
representing different combinations of random and clustered customer locations, as well as short and long time windows.
For each original instance we create 3 instances based on the neighbourhood size.
The N
x
in the instance name refers to the maximum size
x\in\{8,16,24\}
of the neighbourhood.

The neighbourhood size is dynamically grown until a maximum size is reached. That is, in the column generation process at each iteration
the neighbourhoods of the vertices are adjusted to remove cycles until a maximum size. When an optimal zero-cost path is found,
the column generation has reached a valid lower bound and the neighbourhoods are trimmed to correspond to the path in the current solution.
Then the process of growing neighbourhoods is repeated until the maximum size is reached or no negative-cost path can be found in which
case the neighbourhoods are expected to have a good quality. The instances we consider are taken after the trimming process within 3600 seconds
of solving the root node.

Instances are available at

]
.

7
Conclusion

In this paper, we have presented several optimisations for solving the RCSPP using a labelling algorithm.
We introduced three key improvements: a parallel pulling strategy, extension to bi-directional search with dynamic midpoint,
and vectorised dominance comparisons.

Our computational experiments on a diverse set of instances derived from Solomon’s VRPTW benchmarks
demonstrate that each optimisation provides meaningful performance gains.
The parallelisation, bi-directional search, and vectorised dominance comparison each achieve around 1.5-2x speed-up, while the combination of all optimisations
yields around to 5x improvement on average.
Most notably, the combination of all optimisations delivers around 14x speed-up compared to the baseline implementation for
a set of hard instances and maxes out at over 200x speed-up in some cases.

The performance benefits are particularly pronounced on computationally challenging
instances with larger neighbourhood sizes, where the algorithmic improvements have more
opportunity to reduce the substantial label processing overhead. This makes our enhanced
RCSPP solver especially valuable for solving difficult column generation
problems where pricing problems become a major computational bottleneck.

Future work could explore offloading dominance checks to the GPU.
For comparing large number of labels this is potentially beneficial but memory transfer overhead may be a bottleneck.

Another direction is to explore larger bucket sizes and allowing cycles in the dependency graph in a similar fashion as
[
8
]
.
This could mean less overhead of parallelism but comes with the risk of breaking the immutability of the labels and the storage efficiency.
