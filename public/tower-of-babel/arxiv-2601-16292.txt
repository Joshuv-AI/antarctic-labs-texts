AMBER: A Columnar Architecture for High-Performance Agent-Based Modeling in Python
Anh-Duy Pham

Abstract
Agent-based modeling (ABM) has emerged as an indispensable methodology for studying complex adaptive systems across the natural and social sciences. However, Python-based ABM frameworks face a fundamental tension between the accessibility that has made Python dominant in scientific computing and the performance requirements of large-scale simulations. This paper introduces AMBER, a framework that resolves this tension through a novel architectural approach: replacing the conventional object-per-agent representation with columnar state management using the Polars DataFrame library. We analyze the computational characteristics of both paradigms, present the architectural design of AMBER including its core abstractions, spatial environments, experiment management, and optimization capabilities. Empirical evaluation on three canonical benchmarks demonstrates that AMBER achieves speedups of 1.2 × \times to 93 × \times depending on workload characteristics, with the greatest advantages for models dominated by population-wide attribute operations. Memory profiling reveals 30–50% reduction in peak usage compared to object-oriented frameworks. Our results establish columnar state management as a viable architectural foundation for high-performance ABM in interpreted languages.



1
Introduction

Agent-based modeling (ABM) provides a computational methodology for studying complex systems by simulating autonomous agents whose local interactions generate emergent macro-level phenomena
(
1
)
. The methodology has become essential across disciplines: epidemiologists model disease transmission through contact networks, ecologists simulate predator-prey dynamics and species distributions, economists study market formation and financial contagion, and social scientists investigate opinion dynamics and collective behavior. The power of ABM lies in its capacity to capture agent heterogeneity, bounded rationality, spatial structure, and adaptive behavior—phenomena that aggregate equation-based models cannot adequately represent.

Python has emerged as the dominant platform for ABM in the research community. This dominance stems from Python’s gentle learning curve, which enables domain scientists to build models without extensive programming training; its rich ecosystem of libraries supporting the full research workflow from simulation to analysis; and its interpreted nature, which facilitates rapid prototyping and iterative model development. The frameworks Mesa
(
7
)
and AgentPy
(
4
)
have capitalized on these advantages to enable widespread ABM adoption.

However, Python-based ABM frameworks share an architectural assumption that fundamentally limits their scalability. In these frameworks, each agent is represented as an independent Python object with state stored in instance attributes. While this representation is cognitively natural, it incurs computational overhead that grows linearly with population size. For simulations involving thousands to tens of thousands of agents—scales common in epidemiological, ecological, and economic modeling—this overhead becomes a significant barrier to research productivity, limiting parameter space exploration, reducing Monte Carlo sample sizes, and constraining model complexity.

This paper presents AMBER (Agent-based Modeling with Blazingly Efficient Records), a framework that addresses this scalability challenge through a fundamental architectural innovation. Rather than distributing agent state across Python objects, AMBER centralizes state in a columnar DataFrame backed by Polars, a high-performance data processing library implemented in Rust
(
10
)
. This design enables vectorized operations that execute in compiled code while presenting programmers with familiar object-oriented abstractions.

1.1
Research Questions

This work investigates three primary research questions. First, we examine
architectural viability
: can columnar state management serve as an effective foundation for ABM while preserving the expressiveness that makes Python ABM frameworks accessible? Second, we analyze
performance characteristics
: what speedups does the columnar approach achieve, and how do these vary across different workload characteristics? Third, we assess
framework completeness
: can a columnar architecture support the full range of ABM requirements including spatial environments, experiment management, and model calibration?

1.2
Contributions

This work makes four principal contributions. First, we introduce columnar state management as an architectural alternative to object-oriented agent representation, analyzing the computational tradeoffs and identifying the conditions under which each approach excels. Second, we present AMBER, a comprehensive ABM framework implementing the columnar architecture with spatial environments (grid, continuous space, network), experiment management with parameter sweeps, and multiple optimization strategies including grid search, random search, Bayesian optimization, and SMAC integration. Third, we provide rigorous empirical evaluation on three canonical benchmarks, demonstrating speedups of 1.2
\times
to 93
\times
with detailed analysis of performance characteristics across agent population sizes and workload types. Fourth, we characterize the design space of ABM state management, providing guidance for researchers selecting frameworks and for developers designing next-generation ABM platforms.

Related Work

2.1
Python ABM Frameworks

The Python ABM ecosystem has evolved through several generations of frameworks, each reflecting different design priorities.

Mesa
(
7
)
established the dominant architectural pattern: agents as Python class instances with explicit
step()
methods, organized by a scheduler that controls activation order. Mesa introduced important patterns including datacollectors for systematic state recording and space modules for spatial structure. Its visualization server provides interactive model exploration. Mesa’s design prioritizes accessibility and flexibility over performance, making it well-suited for teaching and prototyping.

AgentPy
(
4
)
refines Mesa’s approach with improved ergonomics. Its
AgentList
abstraction enables batch operations over agent collections, partially addressing performance concerns. AgentPy provides tighter integration with Jupyter notebooks and built-in sensitivity analysis tools. However, its fundamental architecture remains object-per-agent, limiting scalability.

Melodie
(
14
)
separates models into distinct components—agents, environment, scenario, and calibrator—promoting modularity. It accelerates specific operations through Cython compilation, achieving partial performance improvements. ABSESpy
(
13
)
extends Mesa’s architecture with domain-specific abstractions for social-ecological systems modeling.

SimPy
(
15
)
takes a fundamentally different approach, providing discrete-event simulation focused on resource queuing rather than population-level agent dynamics. While Python-based, SimPy addresses different modeling requirements than traditional ABM. Auxiliary tools complement these frameworks: PyCX
(
11
)
provides minimal implementations for teaching complex systems concepts, and PyNetLogo
(
5
)
bridges Python with NetLogo’s established ABM environment.

High-Performance ABM Frameworks

Researchers facing performance limitations in Python frameworks typically migrate to implementations in compiled languages, accepting reduced accessibility in exchange for improved scalability.

Repast

(

Agents.jl
(

FLAME GPU 2
(

(
12
)

2.3
Columnar Data Processing

Columnar storage—organizing data by columns rather than rows—has revolutionized analytical database systems and data processing frameworks
(
2
)
. The approach provides several computational advantages relevant to ABM.

Modern CPUs achieve peak performance when accessing contiguous memory. Columnar storage places all values of a single attribute in sequential memory locations, enabling efficient cache utilization when operations access one attribute across many records. Single Instruction Multiple Data (SIMD) instructions process multiple values simultaneously, and columnar arrays enable direct application of SIMD operations, with modern processors supporting 256-bit or 512-bit vectors. Columns of similar values compress more effectively than rows of heterogeneous attributes, benefiting model checkpointing and results storage. Column operations decompose naturally for multi-threaded execution, as independent columns can be processed concurrently.

Polars
(
10
)
, built on Apache Arrow’s columnar memory format, implements these advantages in a Python-accessible library. Written in Rust, Polars provides multi-threaded execution and SIMD vectorization through a DataFrame API. AMBER applies these database-oriented techniques to the distinct requirements of agent-based simulation.

3.1.1
Object-Oriented State Management

In conventional frameworks, agent state is distributed across Python objects. Each of
N
agents corresponds to a Python object allocated on the heap, with agent attributes stored in the object’s
__dict__
dictionary. Attribute access requires dictionary lookup with string key hashing, and objects are scattered in memory according to Python’s allocator.

A population-wide update—for example, incrementing every agent’s wealth attribute—requires iterating through all
N
agent objects. Each iteration involves agent object lookup from the collection, dictionary key lookup to locate the attribute, value retrieval and modification, and value storage back to the dictionary. Each step involves Python interpreter overhead including bytecode execution, reference counting, type checking, and potential memory allocation. Profiling reveals that for simple attribute updates, interpreter overhead dominates actual computation time.

3.1.2
Columnar State Management

AMBER restructures state storage fundamentally. All agent state resides in a single
Population
object that wraps a Polars DataFrame where each attribute is a column. Column data is stored in contiguous typed arrays (for example, an Int64 array for integer attributes), with rows corresponding to agents identified by sequential integer IDs.

3.2
Performance Analysis

To understand when columnar approaches provide advantages, we analyze the time complexity of common ABM operations.

3.2.1
Population-Wide Attribute Update

Let
T_{OOP}
and
T_{col}
denote execution time for object-oriented and columnar approaches respectively.

For object-oriented frameworks:

T_{OOP}=N\cdot(c_{iter}+c_{dict}+c_{op})

where
c_{iter}
is Python iteration overhead per agent,
c_{dict}
is dictionary access cost, and
c_{op}
is the actual operation cost.

For columnar frameworks:

T_{col}=c_{call}+\frac{N}{k}\cdot c_{op}

where
c_{call}
is the fixed cost of invoking the vectorized operation, and
k
is the effective SIMD parallelism factor.

The speedup factor is:

S=\frac{T_{OOP}}{T_{col}}=\frac{N\cdot(c_{iter}+c_{dict}+c_{op})}{c_{call}+(N/k)\cdot c_{op}}

For large
N
and simple operations where
c_{iter}+c_{dict}\gg c_{op}
:

S\approx k\cdot\frac{c_{iter}+c_{dict}}{c_{op}}

This analysis predicts that columnar approaches provide the greatest advantage for simple operations (low
c_{op}
) on large populations (large
N
).

3.3
Abstraction Layer Design

A naive columnar implementation would sacrifice the intuitive agent-oriented programming model. AMBER addresses this through a carefully designed abstraction layer.

The
Agent
class provides object-oriented semantics over columnar storage. Users can write
agent.wealth += 100
with familiar semantics, while the underlying storage remains columnar. The Agent class intercepts attribute access through Python’s descriptor protocol, transparently retrieving values from the appropriate DataFrame row. This pattern incurs overhead for individual attribute access but enables gradual optimization: users start with intuitive code and selectively adopt vectorized operations for performance-critical sections.

The
Population
class provides the columnar foundation with methods for batch agent creation, columnar updates for all or filtered agents, updates for specific agents by ID, and single-agent attribute access and modification. The
BatchUpdateContext
enables efficient accumulation of individual updates within a context manager, applying all changes atomically when the context exits.

3.4
State Evolution Semantics

ABM requires mutable state evolution over simulation time. AMBER supports both synchronous and asynchronous update semantics.

In synchronous (simultaneous) updates, all agents act on a consistent state snapshot. This mode enables full vectorization, as entire columns can be transformed simultaneously based on current values without interference between agents.

In asynchronous (sequential) updates, agents observe effects of prior agents’ actions within the same time step. This mode is necessary for some model semantics but limits vectorization, as each agent’s computation may depend on modifications made by previously processed agents.

4
Framework Components

AMBER provides comprehensive infrastructure beyond the core columnar architecture.

4.1
Spatial Environments

Agent interactions frequently depend on spatial or topological structure. AMBER provides three environment types with unified interfaces.

The
GridEnvironment
implements discrete
n
-dimensional grids for models requiring lattice structure. It supports configurable dimensions from 1D through 3D or higher, with Moore neighborhoods (including diagonals) or von Neumann neighborhoods (orthogonal only). Optional torus wrapping provides periodic boundary conditions. Agent positions are stored as integer coordinates in the Population DataFrame, enabling efficient neighbor queries that leverage known grid structure.

The
SpaceEnvironment
provides continuous
n
-dimensional spaces for models with real-valued positions. It supports floating-point coordinates in arbitrary dimensions with radius-based neighbor queries using Euclidean distance. Boundary handling can be configured as bounded, wrapped, or unbounded. For large populations, integration with
SpatialIndex
provides
O(\log N)
neighbor queries via KD-tree data structures.

The
NetworkEnvironment
enables graph-based connectivity via NetworkX integration, providing full NetworkX functionality for graph construction and analysis. Built-in generators support common topologies including Erdős-Rényi random graphs, Watts-Strogatz small-world networks, and Barabási-Albert scale-free networks. The implementation supports directed or undirected graphs with weighted edges and provides access to network metrics such as degree distribution, clustering coefficient, and path lengths.

4.2
Experiment Management

Systematic parameter exploration is essential for ABM research. AMBER’s
Experiment
class provides infrastructure for defining parameter spaces using
Sample
for discrete parameter values from explicit lists and
IntRange
for integer ranges with configurable step sizes. The framework automatically generates Cartesian products of all parameter combinations and supports configurable replication counts for stochastic stability assessment. Results are aggregated directly into columnar format for seamless downstream analysis.

4.3
Optimization and Calibration

Model calibration—adjusting parameters to match empirical observations—is critical for ABM validation. AMBER provides a hierarchy of optimization strategies with increasing sophistication.

Grid search performs exhaustive evaluation of discrete parameter combinations and is suitable for low-dimensional spaces with clear parameter bounds. Random search stochastically samples the parameter space, providing more efficiency than grid search in high dimensions where grid density becomes prohibitive. Bayesian optimization employs Gaussian process-based surrogate modeling that learns the objective function shape from evaluated points, enabling sample-efficient optimization when model evaluations are expensive. For advanced applications, AMBER integrates with Sequential Model-based Algorithm Configuration (SMAC), supporting multi-fidelity optimization that varies simulation length and multi-objective optimization that simultaneously optimizes multiple metrics.

4.4
Performance Utilities

SpatialIndex
wraps scipy’s cKDTree to provide
O(\log N)
radius queries and
k
-nearest-neighbor queries for continuous space models.
ParallelRunner
enables multiprocessing-based parallel execution for independent simulations, providing near-linear speedup for parameter sweeps across CPU cores. Pre-built vectorized utilities implement common patterns including movement updates, wealth transfers, and random velocity generation.

5
Experimental Evaluation

We evaluate AMBER against Mesa and AgentPy through systematic benchmarking.

5.1
Experimental Design

5.1.1
Benchmark Models

We selected three models representing different computational patterns. The
Wealth Transfer
model has each agent transfer a fixed amount of wealth to a randomly selected other agent at each step. This workload is dominated by attribute reads and writes, representing the best case for vectorization.

The
SIR Epidemic
model places agents in continuous 2D space where they transition between Susceptible, Infected, and Recovered states based on contact with infected neighbors within a fixed radius. This workload involves spatial neighbor queries and per-agent conditional logic.

The
Random Walk
model has agents move in continuous 2D space according to random velocity vectors with boundary handling. This tests vectorized position updates.

5.1.2
Independent and Dependent Variables

The independent variables are framework (AMBER, Mesa 2.1, AgentPy 0.1.5), population size (100, 500, 1,000, 2,000, 5,000, 10,000 agents), and simulation length (100 steps). The dependent variables are execution time (wall-clock time for complete simulation), memory usage (peak resident set size during execution), and scaling exponent (empirical time complexity with respect to population size).

5.1.3
Experimental Protocol

Each configuration was executed 5 times with 2 warmup runs discarded. We report median execution time to reduce sensitivity to outliers. Experiments were conducted on an Apple M2 processor (8 cores, 16GB RAM) running Python 3.11 with AMBER 0.1.1, Mesa 2.1.0, and AgentPy 0.1.5.

5.3
Analysis

The results confirm theoretical predictions. Wealth Transfer achieves the highest speedup (93
\times
) because the workload maps directly to column operations. Each step involves reading wealth values, computing transfers, and writing updated values—all vectorizable operations.

SIR Epidemic shows modest speedup (1.7
\times
) due to inherent per-agent branching: each agent’s state transition depends on its current state and infected neighbor count, requiring conditional evaluation. AMBER’s advantage comes primarily from efficient neighbor queries via SpatialIndex and reduced memory overhead rather than vectorization.

Random Walk achieves substantial speedup (15
\times
) because position updates are fully vectorizable: new positions are computed as vector additions for all agents simultaneously, with boundary handling applied as vectorized clipping operations.

Memory reduction (38–45%) reflects the elimination of per-agent Python object overhead. Each Python object incurs approximately 56 bytes of base overhead plus dictionary storage for attributes; columnar storage eliminates this per-agent cost.

6
Discussion

6.1
Implications for Framework Design

Our results establish columnar state management as a viable architectural foundation for Python ABM. The approach’s viability depends on workload characteristics. Models with frequent population-wide operations (attribute updates, aggregations, filters) benefit substantially from vectorization; such models are common in economics, ecology, and epidemiology. Models with complex per-agent decision logic involving extensive conditional branching see smaller speedups, though AMBER still provides memory efficiency benefits.

6.2
Limitations

Several limitations constrain the applicability of columnar approaches. Some model semantics require strictly sequential agent updates where each agent observes previous agents’ actions within the same step; these models cannot exploit vectorization. Efficient agent creation and removal during simulation requires careful DataFrame management, and while AMBER supports dynamic populations, the overhead may reduce advantages for models with frequent agent turnover. Unlike Mesa, AMBER does not currently provide built-in visualization capabilities, requiring users to implement custom visualization or integrate external tools. Achieving maximum performance requires understanding when to use vectorized operations versus agent-by-agent iteration, though the abstraction layer mitigates this concern.

6.3
Future Directions

Several directions warrant investigation. Extending columnar operations to GPU via cuDF could enable million-agent simulations. Compiler techniques could potentially detect vectorizable code patterns and automatically transform agent loops into column operations. Integration with automatic differentiation frameworks could enable gradient-based model calibration. For cluster-scale simulations, columnar storage could facilitate efficient data partitioning across nodes.

7
Conclusion

This paper introduced AMBER, an agent-based modeling framework achieving high performance through columnar state management while preserving Python’s accessibility. By storing agent state in a centralized Polars DataFrame rather than distributing it across Python objects, AMBER enables vectorized operations that bypass interpreter overhead.

Empirical evaluation on three canonical benchmarks demonstrates that performance advantages depend on workload characteristics: models dominated by population-wide attribute operations achieve speedups up to 93
\times
, while models with complex per-agent logic see more modest improvements of 1.2–1.7
\times
. Memory profiling reveals consistent 38–45% reduction in peak usage across all workloads.

AMBER provides comprehensive ABM infrastructure—spatial environments, experiment management, and optimization capabilities—built on the columnar foundation. Our results establish columnar state management as a promising architectural approach for next-generation ABM platforms that must balance expressiveness with computational efficiency.
