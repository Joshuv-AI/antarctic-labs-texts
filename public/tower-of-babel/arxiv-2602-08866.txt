Abstract
. Large language models have transformed code generation, enabling unprecedented automation in software development. As mobile ecosystems evolve, HarmonyOS has emerged as a critical platform requiring robust development tools. Software development for the HarmonyOS ecosystem relies heavily on ArkTS, a statically typed extension of TypeScript. Despite its growing importance, the ecosystem lacks robust tools for automated code repair, primarily due to the absence of a high-quality benchmark for evaluation. To address this gap, we present ArkEval , a unified framework for ArkTS automated repair workflow evaluation and benchmark construction. It provides the first comprehensive benchmark specifically designed for ArkTS automated program repair. We constructed this benchmark by mining issues from a large-scale official Huawei repository containing over 400 independent ArkTS applications. Through a rigorous multi-stage filtering process, we curated 502 reproducible issues. To ensure testability, we employed a novel LLM-based test generation and voting mechanism involving Claude and other models. Furthermore, we standardized problem statements to facilitate fair evaluation. Finally, we evaluated four state-of-the-art Large Language Models (LLMs) on our benchmark using a retrieval-augmented repair workflow. Our results highlight the current capabilities and limitations of LLMs in repairing ArkTS code, paving the way for future research in this low-resource domain.



1.
Introduction

Large language models have fundamentally transformed the landscape of software development, ushering in an era of unprecedented automation in code generation. From synthesizing complex algorithms from natural language descriptions to completing entire functions with contextual awareness, LLMs have redefined what is computationally feasible in programming assistance
(
4
;
1
)
. This revolution extends beyond mere code completion—it encompasses the entire software lifecycle, including debugging, optimization, and critically, automated program repair.

The field of Automated Program Repair (APR) epitomizes this transformation, having witnessed a Cambrian explosion with the advent of LLMs. By transitioning from static constraint-based techniques to generative approaches, models like GPT-4 and DeepSeek-Coder have achieved remarkable success, effectively acting as autonomous developers for mainstream languages like Python and Java
(
6
;
2
)
. However, this technological leap has created a stark
“Digital Divide”
in intelligent software engineering. While developers in popular ecosystems enjoy powerful AI assistants, the vast “long tail” of domain-specific languages (DSLs), proprietary frameworks, and legacy systems remains largely untouched by this revolution.

This inequity is not merely an academic concern but a critical industrial bottleneck. Modern software infrastructure relies heavily on specialized languages optimized for specific runtimes—from smart contracts in Solidity to embedded control logic in proprietary C variants. These “low-resource” languages lack the massive, clean open-source corpora required to train general-purpose LLMs. Consequently, the trillions of lines of code powering critical infrastructure—banking systems, telecommunications, and IoT devices—are effectively invisible to modern AI tools.
Huawei’s HarmonyOS
presents a paradigmatic example of this challenge. As a premier operating system powering over
900 million active devices
—spanning smartphones, smartwatches, and automotive systems—it relies on
ArkTS
, a specialized static extension of TypeScript. With the transition to
HarmonyOS NEXT
, millions of applications must be rebuilt natively in ArkTS. This migration is not a simple translation; it requires adhering to strict static typing and a unique declarative UI paradigm that fundamentally differs from standard web development. Yet, despite the massive scale and economic importance of this ecosystem, there are currently
zero
dedicated benchmarks or public datasets for ArkTS automated repair.
The resulting “Benchmark Desert” means that we cannot scientifically quantify how well state-of-the-art models perform on ArkTS, nor can we train specialized models to assist the millions of developers struggling with the migration. General-purpose models, trained on permissive JavaScript/TypeScript data, frequently hallucinate valid TypeScript syntax that violates ArkTS’s strict compile-time constraints, leading to frustration rather than assistance. To bridge this divide, we introduce
ArkEval
, the first comprehensive, executable benchmark designed specifically for the ArkTS ecosystem. Recognizing that low-resource languages often lack the regression tests needed for rigorous evaluation, we pioneered a
LLM-Vote Oracle Synthesis
pipeline. By coordinating a group of LLMs to generate and validate test cases for historical bugs, we reconstructed a high-fidelity test suite from a repository of over 400 official Huawei sample applications.
Our contributions are as follows:

•

Bridging the Gap
: We present ArkEval, the first high-quality benchmark for ArkTS, comprising 502 real-world issues. This dataset specifically targeted the “long tail” problem, serving as a blueprint for evaluating AI on other low-resource DSLs.

•

Oracles for the Oracle-Less
: We propose a novel LLM-based voting protocol to synthesize execution-based test oracles for repositories that lack regression tests, a common trait in emerging ecosystems.

•

ArkFix Framework
: We investigate a Retrieval-Augmented Generation (RAG) agent tailored for strict-syntax languages, demonstrating how retrieval can compensate for the lack of pre-training data.

•

A Sobering Evaluation
: We evaluate four state-of-the-art LLMs (including models on Huawei Ascend 910B hardware). Our results reveal a “Grand Challenge”: while models excel at generic logic, their success rate on compilation-strict ArkTS repair is near zero, highlighting the immense difficulty of checking semantic correctness in the long tail.

2.
Background and Motivation

2.1.
The Code AI “Digital Divide”

While the capability of generic code models has skyrocketed, it has not distributed evenly. The training data for models like GPT-4 and DeepSeek is dominated by a few “high-resource” languages (Python, Java, JavaScript, C++). As noted by recent surveys on LLM for Code
(
40
)
, this imbalance creates a “winner-takes-all” dynamic: improved models generate more open-source code in popular languages, which in turn fuels better future models.

In contrast, “long tail” languages suffer from a double disadvantage:

(1)

Data Scarcity
: DSLs often exist in proprietary codebases (e.g., telecom control logic, banking COBOL, game scripting). Public examples are rare and often outdated.

(2)

False Friends
: Many DSLs are syntactically similar to popular languages (e.g., Solidity resembling JavaScript, ArkTS resembling TypeScript). This causes models to over-transfer knowledge, confidently generating code that looks correct to a human but is semantically invalid for the specific runtime.

2.2.
ArkTS: The Hardest Case for “False Friends”

ArkTS is designed as the native language of HarmonyOS. While it is syntactically a superset of TypeScript, semantically it enforces a much stricter “static subset” to enable ahead-of-time (AOT) compilation for high-performance mobile UI. This creates a treacherous valley for LLMs:

2.2.2.
The UI State Management Paradigm

Beyond syntax, ArkTS imposes a unique “Declarative UI State” paradigm. Unlike the Virtual DOM diffing in React, ArkTS uses a granular dependency tracking system driven by decorators:

•

@State
: Component-internal state. Changes trigger local re-render.

•

@Link
: Two-way sync with a parent component. Requires precise
$
syntax for initialization.

•

@Prop
: One-way sync from parent to child. Deep copy semantics.

A common hallucination is "Variable Mismatch." For example, passing a
@State
variable to a component expecting a standard
number
will fail, but passing it to a
@Link
requires the special
$this.variable
syntax. These nuanced “data flow” rules are not enforced by the standard TypeScript grammar learned by LLMs, making this a reasoning challenge, not just a syntax one.

For ArkTS specifically, this gap is critical. As a domain-specific language (DSL) for HarmonyOS, it lacks the decades of open-source history that Java enjoys. Consequently, there are virtually no standardized datasets of real-world bugs for researchers to test on. Without such benchmarks, it is impossible to:

•

Scientifically quantify how well current SOTA models (like GPT-4 or DeepSeek) actually perform on ArkTS.

•

Identify the specific failure modes (e.g., hallucinating non-existent APIs vs. logical errors) that prevent deployment.

•

Train or fine-tune specialized models to handle the unique constraints of the language.

This absence of evaluation infrastructure essentially blinds the research community to the needs of millions of HarmonyOS developers, leaving them without the intelligent tooling available to their peers in other ecosystems.

2.4.
Motivating Low-Resource Language Repair

Our work is motivated by a desire to democratize access to intelligent software engineering. We argue that the benefits of Automated Program Repair should not be reserved for the most popular languages but should be adaptable to any ecosystem where developers face complex challenges.

Advancing APR for ArkTS is particularly impactful because:

(1)

High Complexity Barrier
: The combination of strict static typing and declarative UI state management creates a steep learning curve. An effective APR tool acts not just as a fixer, but as a tutor for new developers.

(2)

Industrial Relevance
: Unlike toy languages, ArkTS powers a massive consumer ecosystem. Improvements here directly translate to better application quality for end-users.

(3)

Generalizability
: Solving the “low-resource” problem for ArkTS—where training data is scarce and regression tests are missing—provides a blueprint for adapting LLMs to other specialized domains (e.g., legacy banking systems, embedded firmware) that suffer from similar data constraints.

Therefore, constructing
ArkEval
is not merely about collecting data; it is a foundational step towards enabling a new generation of adaptable, domain-aware repair agents.

3.1.
Phase 1: Repository Mining and Profiling

Given the nascent state of the ArkTS open-source community, high-quality projects with well-maintained issue trackers are scarce compared to mature ecosystems like Java or Python. To mitigate data quality risks, we targeted a large-scale, authoritative repository maintained by the official Huawei HarmonyOS team. This repository serves as an aggregator for over 400 independent ArkTS sample applications, covering a diverse range of domains including media processing, native hardware interaction, and complex UI layouts. From this extensive collection, we selected 149 high-quality applications that met our complexity standards. Ideally, this provides a representative sample of real-world development patterns proposed by the language creators themselves.

3.2.
Phase 2: Constraint-Based Defect Curation

We developed a two-stage filtering protocol to extract solvable defects from the raw commit history.

3.2.1.
Automated Metric-Based Filtering

We developed a Python-based analysis tool to profile the commit history of the selected 149 applications. We enforced the following inclusion criteria for candidate issues:

•

Fix Complexity Cap
: The diff size of the developer’s patch must be fewer than 300 lines of code (LOC). This threshold excludes massive refactorings (e.g., architecture migrations) that are beyond the scope of current APR tools.

•

Language Purity
: The repository must contain at least 70% ArkTS code. This filter removes commits that primarily modify build configurations, shell scripts, or documentation resources.

This automated sweep effectively reduced the search space from thousands of commits to a focused set of potentially viable repair tasks.

3.2.2.
Manual Review and Reproducibility Check

The candidate set underwent a manual verification process by three expert reviewers. We discarded issues that:

•

Lacked a clear semantic link between the issue description and the code change.

•

Relied on proprietary, closed-source binary dependencies that prevented local compilation.

•

Were duplicates or simple version bumps.

This process yielded a curated dataset of 502 high-quality issues. However, a critical deficiency persisted: the majority of these applications lacked regression tests, a common trait in mobile UI development. Without executable test oracles, evaluating generated patches—or even confirming the existence of the bug—is impossible.

3.3.
Phase 3: LLM-Vote Test Oracle Synthesis

To address the “Oracle Problem”—the fatal lack of regression tests in low-resource repositories—we designed a novel
Ground Truth-guaranteed Test Synthesis (GTTS)
pipeline. Unlike traditional approaches that rely on existing test suites, our system synthesizes oracles by leveraging the latent reasoning capabilities of LLMs, governed by a rigorous consensus protocol.

3.3.1.
The Necessity of a Committee

Initial experiments revealed that single-agent test generation (using only GPT-4 or Claude 3.5) suffered from a high rate of "lazy assert" hallucinations—where the generated test checks for trivial properties (e.g.,
assert(true)
) or invokes non-existent UI inspection APIs. To mitigate this, we implemented a
LLM-based Review Group
consisting of three distinct state-of-the-art models: Claude 3.5 Sonnet, GPT-4o, and DeepSeek-V3.

The workflow operates as follows:

(1)

Generator
: Claude 3.5 Sonnet acts as the primary architect, drafting a reproduction test case based on the semantic diff of the issue.

(2)

Reviewers
: The draft is anonymously submitted to the committee. Each reviewer independently scores the test (0-10) on three axes: Syntax Correctness, Logic Plausibility, and API Validity.

(3)

Consensus Filter
: We apply a strict variance threshold. A test is only tentatively accepted if the standard deviation of valid scores is
<1.5
. This indicates a strong inter-model agreement. If the committee disagrees (e.g., GPT-4o spots a hallucinated API that DeepSeek missed), the test is rejected and sent back for regeneration.

3.3.2.
Ground Truth Verification Loop

Even with consensus, LLM-generated code is fallible. Therefore, every tentatively accepted test must survive a dual-execution verification:

•

Negative Verification
: The test must
FAIL
when run against the
pre-fix
(buggy) version of the codebase. This confirms the test actually catches the reported bug.

•

Positive Verification
: The test must
PASS
when run against the
post-fix
(patched) version. This confirms the test is compatible with the developer’s valid fix.

This closed-loop process ensures that our benchmark contains only "high-fidelity" oracles that are mathematically proven to distinguish between buggy and fixed states, effectively solving the test scarcity problem for the ArkTS ecosystem.

3.4.
Phase 4: Hierarchical Problem Standardization

To facilitate robust evaluation of code repair agents, we standardized the input prompts. Real-world issue reports vary wildly in quality; simply feeding raw descriptions to an agent introduces uncontrolled variance.
We employed a template-based rewriting strategy to expand each issue into three levels of information density:

•

Level 1 (Sparse)
: Contains only the core error message or a one-line summary. Simulates user reports with minimal context.

•

Level 2 (Standard)
: Includes the full problem description, stack traces (if applicable), and reproduction steps.

•

Level 3 (Rich)
: Augments the standard description with hints about the likely location or type of the bug.

This hierarchical structure allows us to evaluate not just whether a model can fix a bug, but how dependent it is on the richness of the provided specification.

3.5.
Phase 5: Taxonomy of ArkTS Defects

To better understand the challenge, we categorized the 502 curated issues into three primary defect types that are unique to the HarmonyOS ecosystem:

(1)

UI State Desynchronization (42%)
: The most prevalent and difficult category. These bugs occur when the imperative logic (e.g., specific event handlers) fails to trigger the declarative UI update. For instance, modifying a standard object property instead of a
@State
decorated variable will silently fail to re-render the UI. Fixing this requires tracing data flow across component boundaries, not just correcting local syntax.

(2)

Strict Compile-Time Violations (35%)
: These are valid TypeScript code patterns that are rejected by the ArkTS AOT compiler. Common examples include dynamic property access (
obj[’prop’]
), structural typing assignments, and using
any
. LLMs trained on web data are highly prone to introducing these regressions.

(3)

Component Lifecycle Mismanagement (23%)
: ArkTS components have specific lifecycles (
aboutToAppear
,
aboutToDisappear
). Bugs often arise when expensive operations or listeners are not correctly initialized or disposed of in these hooks, leading to memory leaks or crash-on-exit behaviors.

4.
Automated Repair Workflow and Agent Encapsulation

4.1.
Task Formulation

We formalize the Repository-Level Automated Program Repair task as follows. Given a repository
\mathcal{R}
consisting of a set of source files
\{f_{1},f_{2},...,f_{n}\}
and an issue description
D
(which may include a natural language bug report and a failure trace), the goal is to generate a patch
P
such that the patched repository
\mathcal{R}^{\prime}=\text{Apply}(P,\mathcal{R})
satisfies two conditions:

(1)

Compilability
:
\text{Compile}(\mathcal{R}^{\prime})\rightarrow\text{Success}
.

(2)

Correctness
:
\text{Test}(\mathcal{R}^{\prime},T_{repro})\rightarrow\text{Pass}
and
\text{Test}(\mathcal{R}^{\prime},T_{reg})\rightarrow\text{Pass}
, where
T_{repro}
is the reproduction test case and
T_{reg}
implies no regression on existing logic.

This formulation emphasizes the holistic view of the project, as changes in one file (e.g., a shared UI component) may ripple across dependencies.

4.2.
Repair Pipeline

We propose a specialized three-stage automated repair framework tailored for ArkTS. The pipeline consists of a
Function Locator
for semantic fault localization, a
Patch Generator
augmented by official documentation and RAG, and a
Patch Executor
for safe verification. The system uses vector embedding for retrieval and a ChromaDB knowledge base to ground patch generation in correct ArkTS syntax. This overall architecture is shown in Figure
5
.

Knowledge Base Construction

Subject matter expertise is the cornerstone of effective RAG. We constructed a specialized knowledge base following a “Hybrid-Chunking” pipeline, illustrated in Figure

.

4.3.1.
Data Ingestion & Cleaning

We crawled over 15,000 pages of official HarmonyOS documentation (API 9 to API 12) and indexed 400+ official sample applications. A critical preprocessing step was
version filtering
: since ArkTS syntax changed drastically in API 10, we discarded legacy JS-based HarmonyOS code to prevent “poisoning” the context with deprecated patterns.

4.3.2.
Hybrid-Chunking Strategy

Standard fixed-window chunking destroys code semantics. We implemented a two-tier strategy:

•

Tier 1: Semantic AST Splitting
: For code files, we use tree-sitter to parse the AST and chunk by class/function boundaries. This ensures that retrieved contexts are complete executable units.

•

Tier 2: Sliding Window with Overlap
: For unstructured documentation, we use a 512-token window with 15

4.3.3.
Vector Embedding

We utilized
Qwen3-Embedding-8B
, optimized for code retrieval. Unlike generic embeddings (e.g., text-embedding-ada-002), Qwen3 is trained on technical documentation, allowing it to better capture the semantic equivalence between a query like "how to sync state to child" and the relevant
@Link
decorator API, even if exact keywords mismatch. The vectors are stored in
ChromaDB
for sub-millisecond similarity search.

4.4.
ArkFix Agent Encapsulation

To facilitate seamless integration and autonomous execution, we encapsulated this entire repair workflow into a unified agent, named
ArkFix Agent
. This agentic system orchestrates the interactions between the Locator, Generator, and Executor modules. It autonomously parses the standardized issue description, queries the RAG knowledge base for relevant API constraints, and iteratively refines patches based on feedback from the compilation and testing phases. This modular encapsulation lays the groundwork for future integration into IDEs like DevEco Studio, where it could provide real-time, interactive repair suggestions to developers.

5.
Evaluation

To rigorously assess the performance of current LLMs on the proposed ArkEval and validate our repair workflow, we formulated the following research questions:

•

RQ1 (Fault Localization Accuracy)
: How accurate is our retrieval-based fault localization module in identifying the correct source files for repair?

•

RQ2 (Effectiveness)
: How effectively can state-of-the-art LLMs generate correct patches for real-world ArkTS defects using our RAG-enhanced workflow?

•

RQ3 (Efficiency)
: What is the computational cost and time latency associated with using different model classes (proprietary vs. open-weights) for this task?

•

RQ4 (Model Preference)
: How do different Large Language Models differ in their tendency to use specific code repair patterns (logic error fixes, UI state synchronization, and type strictness) when generating patches for the same set of code issues?

5.1.
Experimental Setup

Preliminary Workflow Validation

Before conducting the large-scale evaluation, we first validated the feasibility of our proposed workflow using the
Pangu-7B
model
(
5
)
. We selected Pangu-7B for this pilot study due to its lightweight architecture and native optimization for the Huawei Ascend 910B hardware, which ensured minimal deployment complexity. In this preliminary phase, Pangu-7B successfully executed the complete repair pipeline—from fault localization to patch generation—and achieved valid file-level repairs on a sample of ArkTS issues. This success confirmed the viability of deploying RAG-based repair agents on Ascend hardware and motivated our subsequent repository-level experiments.

For the comprehensive evaluation, we expanded our scope to include four representative Large Language Models (LLMs) spanning different architectures and access modes:

(1)

GPT-5.1-mini
: OpenAI’s latest lightweight model, accessed via API.

(2)

Claude 4.5 Sonnet
: Anthropic’s high-performance coding model, accessed via API.

(3)

Qwen3-coder-30b
: An open-weights model fine-tuned for code. We deployed this model locally on a high-performance computing cluster equipped with
8
\times
Huawei Ascend 910B NPUs
(64GB VRAM per card).

(4)

DeepSeek-R1-Distill-Qwen-32B
: The 32B parameter distilled version of the DeepSeek R1 reasoning model. This was also deployed on the same
Huawei Ascend 910B
cluster (8
\times
64GB), utilizing vLLM for optimized inference.

It is important to note that all experimental data reported in this study are based on the implementation of our RAG-enhanced workflow. Due to constraints in time and computational resources, we did not perform a separate ablation study to evaluate the models’ performance without RAG augmentation (i.e., zero-shot generation without retrieved context).

Testing Methodology

Given the complexity of the HarmonyOS ecosystem, we adopted a rigorous four-step testing process to ensure the validity of our results:

(1)

Manual Environment Configuration
: Due to the rapid iteration of HarmonyOS, different repositories rely on specific SDK versions that are often incompatible. We manually analyzed the
build-profile.json5
and README files of each repository to configure the correct API versions and dependencies.

(2)

Automated Patch Application
: We utilized scripts to checkout each repository to the commit corresponding to the issue and automatically applied the generated patches.

(3)

Compilation Verification
: We first ran the compiler to filter out patches that failed to build. Only those that passed the strict compile-time checks proceeded to the next stage.

(4)

Functionality Verification
: We employed a hybrid verification approach. The primary metric is based on the automated reproduction tests synthesized by our oracle pipeline. For qualitative analysis and UI-specific issues (e.g., layout shifts or occlusion) where automated assertions are fragile, we supplemented this with manual verification in the DevEco Studio simulator to confirm the visual correctness of the fix.

5.2.
Metrics

We employ three key metrics to quantify performance:

•

Fault Localization Accuracy
: The percentage of issues where the retrieved file list covers the ground truth files modified by developers at different intersection thresholds (e.g., 100%, 50%, 20%). This evaluates the precision of our retrieval-based localization module.

•

Patch Application Rate
: The percentage of generated patches that strictly adhere to the standard ‘git diff‘ format and can be applied via ‘git apply‘ without requiring custom fallback parsing. This measures the model’s ability to follow formatting instructions.

•

Compilation Rate (Compile@1)
: The percentage of generated patches that successfully pass the strict
hvigor
build process without syntax or type errors. This is crucial for ArkTS due to its non-permissive compiler.

•

Repair Success Rate (Pass@1)
: The percentage of patches that not only compile but also pass all reproduction test cases (generated in Section 3) and do not introduce regressions.

We identified five primary factors contributing to this low recall, often stemming from the trade-offs necessitated by our hardware constraints (8
\times
Huawei Ascend 910B server):

(1)

File Summary Quality
: To fit within the context window of our local embedding models, we truncated file summaries to the first 2000 and last 500 characters. This lossy compression often discarded key implementation details, leading to generalized summaries that failed to distinguish functionally similar files.

(2)

Embedding Semantic Gap
: We relied on cosine similarity, which often failed to capture the complex semantic relationship between the high-level issue description and the code implementation. A misalignment between the vector space of the query and the code summary resulted in lower recall.

(3)

Top-K Search Limit
: We restricted the retrieval to the Top-10 files. Correct files ranked below this threshold were ignored. While expanding this scope (e.g., Top-20) could improve recall, it was not feasible given the resource costs and time constraints of our experimental setup.

(4)

LLM Filtering Inaccuracy
: In the re-ranking phase, to ensure uniform testing within the restricted context window of our local cluster, we truncated the prompt’s issue description to 200 characters and the function code preview to 300 characters. While this prevented context overflow, the aggressive limiting caused the verification LLM to miss subtle connections or hallucinate relevance. With more abundant computational resources and larger context windows, we hypothesize that accuracy would improve significantly.

(5)

Issue Description Quality
: The majority of issues from the official Huawei repository contained extremely brief (often one-sentence) descriptions. Although we attempted prompt engineering to expand these descriptions, the inherent lack of information in the source data remained a bottleneck that no pure retrieval optimization could fully resolve.

Effectiveness: A Grand Challenge for LLMs
. The results in Table

The steep drop from Patch Application (28-39%) to Compilation (3-35%) and finally to Pass@1 underscores the complexity of the task: models struggle first to satisfy the strict type system of ArkTS, and then fail completely to handle the nuanced UI state logic required for functional correctness. This confirms that ArkTS resides in a “benchmark desert” where general-purpose code training provides insufficient transfer learning, marking this domain as a critical frontier for future research. This persistent failure mode uncovers two fundamental insights about the state of Code AI:

(1)

The Hard Road for Small Languages
: The near-zero performance on ArkTS contradicts the popular belief that LLMs have "solved" coding. It demonstrates that the impressive reasoning capabilities seen in Python or C++ are heavily reliant on massive memorization of syntactic patterns in the training data. For "long-tail" languages like ArkTS, where the training corpus is sparse, models cannot infer the strict compilation rules (e.g., AOT constraints) from first principles. This suggests that achieving universal coding competence will require a paradigm shift from data-driven statistical correlation to genuine rule-based reasoning or neuro-symbolic integration.

(2)

The Repository-Level Ceiling
: Current benchmarks often inflate model capabilities by testing self-contained functions. ArkEval’s repository-level nature reveals that models struggle significantly with cross-file context and project-wide dependencies. A high score on ArkEval represents a much more significant milestone than on HumanEval; it would indicate that a model has truly mastered the ability to navigate, understand, and modify complex, interconnected software systems, effectively solving the "last mile" problem of autonomous software engineering.

Efficiency
: As shown in the “Avg Time” column, Qwen3-coder-30b demonstrates the highest efficiency (69.95s). When comparing locally deployed open-weights models, Qwen3 significantly outperforms DeepSeek-R1-Distill-32B (199.11s), highlighting the efficiency benefits of its architecture under identical hardware conditions. For proprietary models accessed via API, both GPT-5.1-mini (265.01s) and Claude 4.5 Sonnet (181.00s) exhibit higher latency. This is primarily attributed to strict official API rate limits and network overhead, which are absent in our local high-performance cluster deployments. However, it is important to note that the recorded “Avg Time” includes the cold-start overhead for repository indexing (i.e., generating file summaries and vector embeddings). When these assets are cached, the inference latency across all models drops to approximately 20-30 seconds, narrowing the performance gap significantly.

5.4.
Qualitative Case Studies: Anatomy of Failure

To understand why the Pass@1 rates are so low despite high patch application rates, we conducted a qualitative analysis of failure modes. We present three representative cases that highlight the “False Friend” dilemma.

5.4.1.
Case 1: The “Lazy” API Hallucination

Issue #142: Fix a deprecated event listener.

•

Model Attempt (GPT-5.1-mini)
: Generated
component.on(’click’, handler)
, mirroring standard Web DOM APIs.

•

ArkTS Reality
: ArkTS requires a strictly typed
.onClick(() => {...})
method chain. The model’s training on vast amounts of JavaScript
addEventListener
overwhelmed the retrieved RAG context, leading to a confident but non-existent API call.

5.4.2.
Case 2: The Silent UI State Bug

In Issue #89, a list failed to update when an item was deleted.

•

Model Attempt (DeepSeek-R1)
: Correctly removed the item from the array:

this.list.splice(index, 1)
.

•

ArkTS Reality
: In ArkTS, array mutations on
@State
variables are observant only if the array reference changes or specific methods are used. The fix required re-assigning the array or using the
ObservedArray
wrapper. The model’s logic was algorithmic correct but framework-wrong, leading to a “zombie” UI state.

5.4.3.
Case 3: The Strict Typing Trap

In Issue #301, the model needed to process a JSON response.

•

Model Attempt (Claude 4.5)
:
let data = JSON.parse(str); console.log(data.id);

•

ArkTS Reality
: This fails compilation. ArkTS forbids access to properties on
Object
or
any
types. The developer must define a
class Response { id: number = 0 }
and explicitly cast:
let data = JSON.parse(str) as Response
. The model’s refusal to define “boilerplate” classes caused the repair to be rejected by the compiler.

6.
Discussion

6.1.
A Blueprint for the Long Tail

The “Zero Success” rate of open-weights models on ArkEval is not merely a negative result; it is a roadmap. It demonstrates that the current paradigm—train on massive GitHub dumps and hope for transfer learning—hits a hard ceiling when faced with strict AOT compilers and domain-specific paradigms.

However, our work offers a blueprint for overcoming this:

(1)

Synthetic Oracles are Key
: In the absence of human-written tests, our "Committee-Agreed" test synthesis proved that we can bootstrap quality assurance from pure logic. This approach is language-agnostic and can be applied to COBOL, Solidity, or any legacy stack.

(2)

RAG must be Syntax-Aware
: As improving from 0% to 3% showed, identifying the right API is only half the battle. The retrieval system must understand the
grammar
(via AST chunking) to provide compilable context.

6.2.
The "Cold Start" Problem in Code AI

If a language has no open-source ecosystem, how do we train the first compliant model? This “Cold Start” problem is the central challenge for the next decade of Software Engineering. ArkTS represents the extreme edge of this problem: a massive industrial ecosystem with an “empty” public internet footprint.
Our findings suggest that for such domains,
Small Language Models (SLMs)
fine-tuned on high-quality, proprietary internal data (like the Huawei sample apps) will vastly outperform massive generalized models. The future of domain-specific repair lies not in larger parameters, but in higher data density.

6.3.
Threats to Validity

We identify several threats to the validity of our study:

•

Hybrid Verification
: While our primary Pass@1 metric relies on automated tests, our qualitative analysis involves manual verification. To mitigate bias, we employed a strict confirmation protocol where a fix is only confirmed if it passes both the automated compiler check and visual inspection.

•

Retrieval Constraints
: Due to hardware limitations, we implemented aggressive truncation strategies (First-2000/Last-500 chars) and limited retrieval to Top-10 files. This may have negatively impacted the localization recall. We acknowledge that more sophisticated retrieval strategies or larger context windows could yield better results.

•

Data Contamination
: Although the Huawei sample repositories are public, our strict version filtering ensures that legacy code (which might be in training data) is excluded. Furthermore, our
Synthetic Oracle
approach generates new test cases that definitely did not exist in the training data, ensuring that the evaluation metric itself remains rigorous even if the source code has been seen.

8.
Conclusion

In this paper, we presented
ArkEval
, filling a critical void in the evaluation of automated repair tools for the HarmonyOS ecosystem. By curating 502 high-quality issues and establishing a novel LLM-voting pipeline to synthesize missing regression tests, we provide a solid foundation for future research in low-resource language repair.

Our evaluation of four advanced LLMs—including models deployed on Huawei Ascend hardware—demonstrates that while generic models like Claude 4.5 Sonnet show promise, they struggle with the specific strict typing and declarative UI constraints of ArkTS. The results demonstrate that even with the integration of RAG-enhanced workflows, effectiveness remains sub-optimal. This highlights that code generation and repair for low-resource languages like ArkTS remains an extremely challenging problem, primarily due to the scarcity of high-quality training corpora.

Future work will focus on three directions: (1) Developing specialized small language models (SLMs) fine-tuned specifically on ArkTS corpora for low-latency on-device repair, (2) Integrating this repair loop directly into the DevEco Studio IDE to provide real-time, interactive fixing suggestions for developers, and (3) Leveraging
ArkEval
as a high-quality dataset for supervised fine-tuning (SFT) or reinforcement learning (RL) to improve the pass@k metrics of code generation models on this specific domain. We hope this work inspires further exploration into democratizing intelligent software engineering tools for emerging ecosystems.
