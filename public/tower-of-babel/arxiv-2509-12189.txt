and representation on the Web (notably for Web APIs),
but is also
widely used for storing application data, and, importantly for our concern,

JSON document databases belong to the
NoSQL
family of database
management systems
Davoudian et al. 2018
;
Mavrogiorgos et al. 2021
, which relax the strict requirement of
the data complying with a predefined schema.
In contrast to XML, which is supported by the standardised XQuery
language
Koch 2006
, the JSON ecosystem lacks a universally adopted query
standard.
Several proposals have emerged--such as JMESPath
1
1

1

https://jmespath.org/
, or the JSON-supporting extensions of XPath
2
2

2

https://www.w3.org/TR/xpath-31/
and XQuery
3
3

3

https://www.w3.org/TR/xquery-31/
–but these have seen little traction within the JSON database community. Vendor-specific solutions have also appeared: N1QL by Couchbase and AQL by ArangoDB, both SQL-inspired languages adapted to handle the nested structure of JSON documents (e.g., nested arrays). However, these languages remain confined to their respective platforms.
The notable exception is the
MongoDB aggregation
framework
4
4

4

https://www.mongodb.com/docs/manual/core/aggregation-pipeline/
,
a widely adopted query language for collections of
JSON documents. Owing to its expressive pipeline model,
large developer base, and popularity among users, it has effectively become a
de-facto standard for querying JSON. The fact that major vendors–including
Amazon (DocumentDB), Oracle (Autonomous JSON), and Google (Firestore)–as well
as smaller players such as FerretDB, seek to provide compatibility with MongoDB
API further underscores the recognition of its query model as a common lingua
franca.

Despite the popularity of the MongoDB aggregation framework, currently there is
no agreed vendor-neutral standard that would ensure interoperability and
portability of document data stores, meaning that every vendor has its own
ad-hoc implementation. This situation mirrors the early years of relational
databases, before the emergence of SQL as a unifying standard, when systems
were fragmented and tightly coupled to individual vendors. As a definite sign
that the industry is ready to define such a common standard for JSON document
databases, Microsoft has recently announced an open-source release of their
DocumentDB
Abinav Rameesh 7 01
, explicitly highlighting compatibility with MongoDB
APIs, followed by an announcement that DocumentDB joined the Linux Foundation
as an open source project that would provide “an open standard for document
based applications”
Allison Stokes 9 11
.

The creation of a standard, however, is impeded by several factors.
First, the MongoDB aggregation framework lacks a well-established theoretical
foundation. Its query language is modeled on the flexible notion of a data
processing pipeline, where a query consists of multiple stages, each defining a
specific transformation applied to the set of documents produced by the
previous stage.
While this design is pragmatic and powerful,
it has not been systematically
formalized in the way relational algebra underpins SQL.
Second, the semantics of MongoDB pipelines is procedural rather than purely
declarative, in contrast to SQL. The result is a rich language that can model
complex data manipulations, including a number of map-reduce-style
transformations and user-defined functions, whose exact semantics is
implementation specific.
Third, MongoDB’s
documentation
5
5

5

https://www.mongodb.com/docs/manual/
, while
providing a comprehensive description of syntax, omits crucial semantic
details, which may lead to ambiguity when interpreting various constructs.
We illustrate this on an example.

Example 1

Assume that we have a collection of documents about music bands, similar to
the one in Figure

Syntactically, this query is very simple. Semantically, it may also seem
straightforward to compute its output, especially for collections of documents
where the value of

is a number. However, considering that
JSON databases are schemaless, what if this value is a string or, more
generally, a complex value? What is the expected semantics?

We can take this further. What if want to find all bands that released an
album before 1975? By analogy with the query above, MongoDB allows to write the
following query:

⬇

Now, what does the path

possible value would be an array. In that case, what is the result of comparing
an array to a number? Should all the values in the array satisfy the comparison
or at least one of them?

This example illustrates that the underlying semantics must necessarily take
into account complex interactions between document structure, path evaluation,
and type comparisons.
Unfortunately, these are not formally specified in MongoDB’s documentation.
This lack of formal foundations creates several problems: unpredictable query
behavior in edge cases, difficulty in query optimization, limited
interoperability with other systems, and barriers to creating industry
standards.

\qed

The challenges mentioned above motivate the need for a rigorous mathematical
framework underpinning MongoDB aggregation queries.
Without a canonical underlying formalism, reasoning about query equivalence,
development of query optimisation techniques, and achieving interoperability
becomes difficult, limiting the ability of standardisation bodies to propose a
vendor-independent specification.

The purpose of this report is twofold. First, provide a formalisation of the
MongoDB data model and the aggregation framework. Second, identify a fragment of the aggregation framework that could serve as the
starting point for an industry-wide standard for JSON document databases.
Our approach is inspired by the foundational work of Edgar Codd, whose
relational algebra provided the theoretical underpinning for SQL. Just as
relational algebra enabled rigorous reasoning about SQL queries, optimization,
and correctness, we aim to provide similar foundations for JSON document
databases.

We present in this report an abstract syntax for the MongoDB aggregation framework,
define a formal semantics for it,
and discuss how its expressive power relates to more traditional query languages, notably the ones underpinning SQL.
In some places, our semantics slightly differs from the one implemented in MongoDB.
To explain and motivate these differences,
we provide examples that justify it.
Our formalisation is largely based on an article published at ICDT
Botoeva et al. 2018
.
We extend it in several directions,
notably to

(i)
include more pipeline operators,

(ii)
relax the assumption that the JSON documents stored in the database comply to a predefined schema,

(iii)
allow objects that are either ordered or unordered sets of key-value pairs.

The rest of this document is structured as follows.

In Section

Then in Section

we present a number of algebraic
equivalences between MQueries, which could be used for query optimisation.

2
Data Model

In this section, we present a data model for database management systems that
store collections of JSON documents.
We start by introducing in Section
2.1
a more abstract syntax for
JSON values that is better-suited for a theoretical analysis.
Then, in Section
2.2
we define how a
path
–a
sequence of
keys
–is associated with a value inside a JSON object, and
in Section
2.3
we briefly mention an
alternative–unordered–semantics for JSON objects.

Before defining our model,
we briefly summarize how it differs from the
MongoDB implementation.
First, our formalisation abstracts some low-level typing details of JSON
values, essential in practice, but less relevant for the more foundational
perspective of this technical report.
More precisely,
MongoDB serialises JSON documents in the so-called BSON (for binary JSON) format for
efficient storage and retrieval.
BSON supports various datatypes, where the primitive ones include
double, string, boolean, date, and timestamp, and the complex ones include object, array, JavaScript code and binary data.
Instead, in our simplified data model, we assume that all primitive values have
the same type, regardless of whether they are doubles, strings, timestamps,
etc, and simply refer to them as
literals
, and consider only objects and arrays as complex values.

Second, we offer two alternative treatments of objects.
MongoDB interprets an object as a
sequence
of key-value pairs (with distinct keys).
This implies for instance that the JSON objects

{"title": "News of the World", "release": 1977}

and

{"release": 1977, "title": "News of the World"}

represent two different entities.
We call this first treatment the
ordered
semantics for objects.
However, in many applications, the data represented by a JSON object is instead meant to be interpreted as a
set
of key-value pairs
(similarly to the way objects and associative arrays are treated in most programming languages).
Under this view, these two objects represent the same entity.
We also consider this treatment, which we call the
unordered
semantics,
as an alternative to the ordered one.

2.1
Document Databases

In this section, we present the main building blocks of a document database. We
start by introducing an abstraction of JSON values in the form of d-values. Then,
we define collections and database instances.

D-value

We use the generic term
document value
, or

d-value
for short, to refer to a unit of data, which can be a

literal
(a primitive value), an
array
or an
object
.
We distinguish between the
syntactic
representation of a d-value (how it is written using symbols)
and its
semantic interpretation
(what computational value it denotes). This distinction will allow us later to define the unordered semantics.

Syntactically, d-values are built inductively out of two (infinite)
sets
\mathcal{K}
of
keys
and
\mathcal{L}
of
literals

Definition 1
(d-value)

A

is a finite

6

definitions of arrays and objects).

It can be either:

•

a
literal
(i.e., an element of
\mathcal{L}
), or

•

an
array

\lfloor\!\,v_{1},\dots,v_{n}\rfloor

•

an
object
–a finite sequence of
key-value
pairs of the form
k\mapsto v
where
k\in\mathcal{K}
,

v
is a d-value,
and keys are distinct.

We us

i^{\text{th}}

a

(i.e.
a[1]
is the first element of

When enumerating the key-value pairs of an object, we enclose them
in
\langle\cdot\rangle
.
For instance,
\langle{\small\textup{{title}}}\mapsto\textit{``News of the
World''},\ {\small\textup{{release}}}\mapsto 1977\rangle

the d-value corresponding to the JSON object

.
Within our set
\mathcal{K}

_​​ id

which we use for document identifiers.
It corresponds to the field

We also distinguish a special value

to represent missing fields or undefined values.
We use
\mathcal{V}
for the universe of all d-values,
i.e., all expressions that can be built (inductively) from

according to Definition

Among these, we use

The standard semantics we assume for d-values essentially interprets a d-value as itself. This corresponds to the
ordered
semantics since it interprets
objects as sequences of key-value pairs, as opposed to (unordered) sets of
key-value pairs.

Database

Document databases store collections of JSON documents. We now define all terminology required to talk about database instances.

Collections in document databases are analogous to relations in relational
databases, with objects serving as the counterparts of relational tuples.

Definition 2
(Collection)

A
collection
is a finite bag of objects.

We emphasize the generic meaning of the term ‘collection’ in this definition: a
collection may not only be stored in a database instance, but also be the
output of a (sub)query.

As in SQL, a MongoDB aggregate query refers to a stored collection via its
name. Accordingly, we assume an infinite set
\mathcal{C}
of collection names.
Finally, we can define a database instance as a way to assign collections to
such names:

Definition 3
(Database instance)

A
database instance

I
maps each collection name
C\in\mathcal{C}
to a collection
{C}^{I}
,
and finitely many to a non-empty collection.

We conclude with definitions that are specific to how MongoDB stores objects in
a database instance. Namely, every stored object necessarily has the
_​​ id
field,
whose purpose is to uniquely identify this object within the stored collection.
We refer to such objects as documents: a
document
is an object
d
that
contains a key-value pair of the form
{\small\textup{{\_\!\!\;id}}}\mapsto v
.
We say that two documents
d_{1}
and
d_{2}
have
distinct identifiers
if

d_{1}
and
d_{2}
contain key-value pairs
{\small\textup{{\_\!\!\;id}}}\mapsto\mathit{id}_{1}
and

{\small\textup{{\_\!\!\;id}}}\mapsto\mathit{id}_{2}
, respectively, and
\mathit{id}_{1}\neq\mathit{id}_{2}
.
MongoDB always treats the field
_​​ id
as the primary key of a stored collection. Therefore, for MongoDB a collection in a database instance–
source collection
–is a finite set of documents with distinct identifiers.

Note that our definition of a database instance does not impose such a
requirement on stored collections, so they may in general contain multiple
occurrences of the same object.

2.2
Objects as Interpretation Structures

A d-value object is a complex value; in general, it has a hierarchical
structure with nested objects and arrays.
In this subsection we go into more technical depth and provide definitions that
allow us to “look inside” an object.
These will be useful when formalising the semantics of
MQuery
.

We start by viewing an object as a function. Recall that an object is a
sequence of key-value pairs where all keys are distinct. Therefore, each key in
an object provides access to the corresponding d-value (e.g., in the object of
Figure
2
, the key
formation
allows us to
access the value 1975).
More generally, an object
induces
a function from keys to d-values.

Definition 4

The
function
f_{o}
induced by
an object
o=\langle k_{1}\mapsto v_{1},\dots,k_{n}\mapsto v_{n}\rangle
is defined by
f_{o}(k_{i})=v_{i}
,
for each
i\in\{1,\dots,n\}
.

For convenience, we often write
o(k)
to refer to
f_{o}(k)
,
i.e., the value associated with key
k
in object
o
.
For instance, if
o
is the object of Figure
2
,
then
o({\small\textup{{formation}}})=1975
.

The function induced by an object allows us to access the d-value associated to a key.
To access values that are nested “deeper” in an object, we consider
concatenations of keys and indices into what we call a
path

(
field
in MongoDB terminology).
Paths allow us to navigate nested JSON structures, as is done in JSONPath. For example, in the object of Figure
2
,
the path
albums.0.title
would navigate to the array
albums
, select the first element (index
0
),
and access the value of its
title
key (in this case
”A Night at the Opera”
).
Formally, paths are defined as follows:

Definition 5
(Path)

A
path
is a finite sequence of keys and indices in
\mathcal{K}\cup\mathbb{N}
.

The
empty path
is denoted with
\varepsilon
.

We represent a path as the concatenation of its elements, separated with a dot.
For instance,
albums.0.title
represents the path
({\small\textup{{albums}}},{\small\textup{{0}}},{\small\textup{{title}}})
.

Now, to specify what a path refers to in an object, we define an

evaluation function
\llbracket\cdot\rrbracket^{o}
that extends the function
f_{o}
from
keys to paths and maps a path
p
to the corresponding d-value in the object

o
(intuitively, the d-value inside
o
that
p
points to).
Furthermore, we generalise this evaluation function from objects to d-values,
in particular, to establish what a path starting with an index refers to in an
array. This will be useful when we define the semantics of
MQuery
in
Section
3
.

Definition 6
(Evaluation function)

For a d-value
v
, the
evaluation function
\llbracket\cdot\rrbracket^{v}
from paths
to d-values is defined inductively as:

•

\llbracket\varepsilon\rrbracket^{v}=v

•

\llbracket p.k\rrbracket^{v}=o^{\prime}(k)
if
\llbracket p\rrbracket^{v}
is the object
o^{\prime}
and
o^{\prime}(k)
is defined,

•

\llbracket p.i\rrbracket^{v}=a[i]
if
\llbracket p\rrbracket^{v}
is the array
a
and
a[i]
is defined,

•

otherwise,
\llbracket p\rrbracket^{v}=\mathbf{null}
.

For example, let
o
be the object in Figure
2
. Then

\llbracket{\small\textup{{albums.0}}}\rrbracket^{o}
is the object

o^{\prime}=\big\langle{\small\textup{{title}}}\mapsto\textit{``A Night at the
Opera"},\ {\small\textup{{release}}}\mapsto 1975,\ {\small\textup{{length}}}\mapsto\textit{``43:08''}\big\rangle.

As for the fallback case
\llbracket p\rrbracket^{v}=\mathbf{null}
, intuitively, the evaluation
function is not defined for paths
p
that do not appear in
o
(when starting
from the top level). To reflect this, we define
\llbracket p\rrbracket^{v}
as

\mathbf{null}
. Note that an explicit
\mathbf{null}
may be already present in an
object, in which case there would be a path that is present and evaluates to

\mathbf{null}
. This is in line with our treatment of
\mathbf{null}
as an undefined
value.
In particular,
\llbracket{\small\textup{{albums.0.labels}}}\rrbracket^{o}
is undefined since

labels
is not a key in
o^{\prime}
and
\llbracket{\small\textup{{title}}}\rrbracket^{o}
is
undefined since
title
is only a key in
o^{\prime}
, but not in
o
.

2.3
The Unordered Interpretation of d-values

As we discussed already, a JSON object can be interpreted in two ways:
as a sequence of key-value pairs,
or as a map from keys to values (like a hash table in a programming language),
where the order of keys is irrelevant.
The former interpretation is the standard one, also referred to as

ordered
semantics.
In this subsection, we formalise the latter interpretation as the

unordered
semantics.

Definition 7
(Unordered semantics)

For a d-value
v
, denote by
v^{*}
the interpretation of
v
. The

unordered semantics
interprets

•

a literal as itself,

•

an array
\lfloor\!\,v_{1},\dots,v_{n}\rfloor
as
\lfloor\!\,v_{1}^{*},\dots,v_{n}^{*}\rfloor
,
the interpretations of its elements (in the same order).

•

an object
\langle k_{1}\mapsto v_{1},\dots,k_{n}\mapsto v_{n}\rangle
as the
function
\{k_{1}\mapsto v_{1}^{*},\dots,k_{n}\mapsto v_{n}^{*}\}
.

Example 3

Under the unordered semantics, the two objects
o_{1}
and
o_{2}
from
Example
2
are interpreted as the same map

\{{\small\textup{{name}}}\mapsto\textit{``Alex Doe''},\ {\small\textup{{age}}}\mapsto 10\}
.
Whereas under the ordered semantics, they are interpreted as
different sequences of key-value pairs.

Now that we have established our data model for JSON documents and collections,
we turn to defining a query language that operates over these structures.
The next section introduces MQuery, our formalization of the MongoDB aggregation framework.

3
The Syntax and Semantics of MQuery

In this section we present a formalisation of the query language of the MongoDB
aggregation framework, which we call
MQuery
. We first define various building
blocks of MQuery, such as terms and Boolean expressions, in
Section
3.1
.
Then we define the syntax and the semantics of
MQuery
stages (representing
top-level constructs), starting with core stages in Section
3.2

and additional ones in Section
3.3
.

An
MQuery
is a pipeline of stages evaluated one after the other.

MQuery
allows for seven core types of
stages
:

(i)

match
, which selects documents according to a filtering
criterion. Such criterion is a Boolean combination of atomic conditions
expressing, e.g., the existence of a path or its equality to a d-value.

(ii)

unwind
, which flattens an array by creating a separate document
for each element of the array.

(iii)

project
, which can modify each document by removing, renaming or introducing new paths.

(iv)

group
, which can aggregate multiple documents into a
single one.

(v)

lookup
, which performs a left join with an external

(vi)

(vii)

Other stages include those integral to any practical query language such as

In this

Terms are expressions that evaluate to d-values and can be built from simpler

\displaystyle{\color[rgb]{0.3,0,0}::=}

\displaystyle\ell~\mid~p~\mid~\lfloor\!\,\tau,\dots,\tau\rfloor~\mid~\langle k\mapsto\tau,\dots,k\mapsto\tau\rangle~\mid~f(\tau)~\mid~{\varphi}?\,{\tau}{:}\,{\tau}~\mid~

(1)

Note that our terms and Boolean expressions do not cover all expressions

and

We include only those expressions that can be considered to constitute a

We now discuss terms and Boolean expressions, each in more detail.

Term
. A term
\tau
is an expression that evaluates to a d-value, and may be used in

MQuery
in a Boolean expression or to set the value of a new path.
Terms are considerably more powerful than paths in that they allow for
construction of new d-values, which may involve evaluation of conditional
statements and computable functions.
A term can be seen as a template for a d-value built
inductively
from constant
values (
\ell
) and paths
(
p
),
and then applying to them an

array
or
object constructor
(resp.,
\lfloor\!\,\tau,\dots,\tau\rfloor

and
\langle k\mapsto\tau,\dots,k\mapsto\tau\rangle
), a named function
(
f(\tau)
), a
conditional term definition

(
{\varphi}?\,{\tau}{:}\,{\tau}
), or a
map
(
\mathsf{map}({p},\>\lambda{x}\colon{\tau})
) or

filter
(
\mathsf{filter}({p},\>\lambda{x}\colon{\varphi})
) function.

We extend the evaluation function
(see Definition
6
)
from paths to terms:

Definition 8
(Evaluation function for terms)

Let
v
be a d-value. The evaluation function interprets a literal
\ell
as itself,
i.e.
\llbracket\ell\rrbracket^{v}=\ell
, while the evaluation of complex terms is defined inductively as
follows:

•

\llbracket\lfloor\!\,\tau_{1},\dots,\tau_{m}\rfloor\rrbracket^{v}=\Big\lfloor\!\,\llbracket\tau_{1}\rrbracket^{v},\dots,\llbracket\tau_{m}\rrbracket^{v}\Big\rfloor
, i.e., the array constructor

\lfloor\!\,\tau_{1},\dots,\tau_{m}\rfloor
evaluates to the array with
i
-th
element
\llbracket\tau_{i}\rrbracket^{v}
;

•

\llbracket\langle k_{1}\mapsto\tau_{1},\dots,k_{m}\mapsto\tau_{m}\rangle\rrbracket^{v}=\Big\langle k_{i}\mapsto\llbracket\tau_{i}\rrbracket^{v}\Bigm|\llbracket\tau_{i}\rrbracket^{v}\neq\mathbf{null},\ i=1,\dots,m\Big\rangle
, i.e., the
object constructor
\langle k_{1}\mapsto\tau_{1},\dots,k_{m}\mapsto\tau_{m}\rangle

evaluates to the object where the value for
k_{i}
is
\llbracket\tau_{i}\rrbracket^{v}
;

•

\llbracket f(\tau)\rrbracket^{v}=f^{*}(\llbracket\tau\rrbracket^{v})
, where
f^{*}
is the function
whose name is
f
;

•

\llbracket{\varphi}?\,{\tau_{1}}{:}\,{\tau_{2}}\rrbracket^{v}=\begin{cases}\llbracket\tau_{1}\rrbracket^{v}&\text{ if }v\models\varphi\\
\llbracket\tau_{2}\rrbracket^{v}&\text{ otherwise }\end{cases}
, i.e., a conditional term definition

{\varphi}?\,{\tau_{1}}{:}\,{\tau_{2}}
evaluates to
\llbracket\tau_{1}\rrbracket^{v}
if the
Boolean condition
\varphi
is satisfied in
v
(defined below), and to

\llbracket\tau_{2}\rrbracket^{v}
otherwise;

•

\llbracket\mathsf{map}({p},\>\lambda{x}\colon{\tau})\rrbracket^{v}=\begin{cases}\Big\lfloor\!\,\llbracket\tau\rrbracket^{\mu_{1}},\dots,\llbracket\tau\rrbracket^{\mu_{n}}\Big\rfloor&\text{if }\llbracket p\rrbracket^{v}=\lfloor\!\,v_{1},\dots,v_{n}\rfloor,\text{ with }\mu_{i}=\{x\mapsto v_{i},\ \varepsilon\mapsto v\},\\
\mathbf{null}\text{ otherwise. }\end{cases}

In other words,
\mathsf{map}({p},\>\lambda{x}\colon{\tau})
returns an array of the same size as the array
\llbracket p\rrbracket^{v}
,
where each element is the evaluation of
\tau
in the evaluation context
\mu_{i}=\{x\mapsto v_{i},\ \varepsilon\mapsto v\}
.
In this context, the variable
x
is assigned the value
v_{i}
,
while the empty path (referring to the whole value) is assigned the current d-value
v
.
The evaluation function in a context
\mu
is defined similarly
as in a d-value
v
, the only difference being the base case,
with
\llbracket x.p\rrbracket^{\mu}=\llbracket p\rrbracket^{\mu(x)}
.
This definition can be extended to nested
\mathsf{map}
and/or
\mathsf{filter}
expressions,
by defining an evaluation function for richer evaluation contexts.

•

\llbracket\mathsf{filter}({p},\>\lambda{x}\colon{\varphi})\rrbracket^{v}=\begin{cases}\Big\lfloor\!\,v_{i}\in\llbracket p\rrbracket^{v}\Bigm|v_{i}\models_{\mu_{i}}\varphi\Big\rfloor&\text{if }\llbracket p\rrbracket^{v}\text{ is an array },\text{ with }\mu_{i}=\{x\mapsto v_{i},\ \varepsilon\mapsto v\},\\
\mathbf{null}\text{ otherwise. }\end{cases}

In other word,
\mathsf{filter}({p},\>\lambda{x}\colon{\varphi})
returns a subsequence of the array
\llbracket p\rrbracket^{v}
,
which consists of the elements for which the Boolean condition
\varphi
holds,
in the same order as they appear in
\llbracket p\rrbracket^{v}
.
The role of the context
\mu_{i}
is identical to the case of
\mathsf{map}
.

Note that the term
f(\tau)
abstracts various computable functions, including
arithmetic functions, functions on strings (such as
concat
,

substr
,
toLowerCase
) and aggregate functions (such as

min
,
max
,
sum
,
count
). Here we
only assume that we know how to compute
f^{*}
. In practice, in MongoDB,
f

would need to be one of the supported function names.
For readability,
we may use an infix operator for an arithmetic function.
For instance, we may write
p+1
instead of

\mathit{incrementByOne}(p)
.

Note that the expression
\mathsf{map}({p},\>\lambda{x}\colon{\tau})
produces an array by
evaluating
\tau
over each element of the array referred to by
p
, similarly
to the
map
function in functional programming languages.
For example,
\mathsf{map}({p},\>\lambda{x}\colon{x+1})
increases by
1
the value of each element in
the array referred to by
p
, while

\mathsf{map}({p},\>\lambda{x}\colon{{x\geq 10}?\,{\mathbf{true}}{:}\,{\mathbf{false}}})
outputs a Boolean value
for each element of the referenced array, depending on whether it satisfies the
comparison or not.
In these examples
x
refers directly to the elements of the referenced array.
The expression
\mathsf{map}({p},\>\lambda{x}\colon{x.p^{\prime}})
, on the other hand, returns the value of
p^{\prime}

in each element of the referenced array, in other words, it allows to

access values nested inside an array
; while the expression

\mathsf{map}({p},\>\lambda{x}\colon{x.p^{\prime}+1})
not only accesses nested values, but also transforms
them, increasing each of them by
1
.

Note that an array constructor
\lfloor\!\,\tau_{1},\dots,\tau_{m}\rfloor
always produces
an array with
m
elements, even if
some

\tau_{i}
evaluates to

\mathbf{null}
. Similarly, a map function
\mathsf{map}({p},\>\lambda{x}\colon{\tau})
produces an array of
the same size as
\llbracket p\rrbracket^{v}
, possibly containing
\mathbf{null}
values. Such

\mathbf{null}
values, when not useful, can be removed with a
\mathsf{filter}
function such
as
\mathsf{filter}({p^{\prime}},\>\lambda{x}\colon{x\neq\mathbf{null}})
.
However, an object constructor

\langle k_{1}\mapsto\tau_{1},\dots,k_{m}\mapsto\tau_{m}\rangle
may produce a sequence of
fewer than
m
key-value pairs. In particular, there would be no pair

k_{i}\mapsto\llbracket\tau_{i}\rrbracket^{v}
if
\llbracket\tau_{i}\rrbracket^{v}
evaluates to
\mathbf{null}
.

Boolean expression
. A Boolean expression may be used as a filtering condition (in a match stage or
a
\mathsf{filter}
function), or in the conditional definition of the d-value associated
to a new path (in a project stage).
As specified in Grammar (
2
) above,
a Boolean expression
\varphi
is built using the standard Boolean operators

\neg
,
\land
from atomic formulas of the form:

•

\exists p
: path
p
evaluates to some non-
\mathbf{null}
d-value.

•

\tau_{1}=\tau_{2}
or
\tau_{1}\leq\tau_{2}
: a comparison of (the
evaluations of) two terms, e.g.,
p=5
,
p_{1}\leq p_{2}
,

\min(p_{1})=\max(p_{2})
.

•

\tau_{1}\in\tau_{2}
: the evaluation of
\tau_{2}
as an array contains the
evaluation of
\tau_{1}
.

In what follows, we may use
\neq
,
<
,
\geq
and
>
as syntactic sugar for
comparison operators, and
\varphi_{1}\lor\varphi_{2}
as syntactic sugar for

\neg(\neg\varphi_{1}\land\neg\varphi_{2})
.

Delta with MongoDB’s implementation (version
8.0.12
).

MongoDB allows using in a Boolean context expressions that strictly
speaking do not evaluate to Boolean values. Specifically,
0 and

\mathbf{null}
are interpreted as false, whereas all other values
(including
the empty string “”, empty array
[]
and empty object
\{\}
) are interpreted
as true.
However,
the evaluation of an arbitrary term
\tau
in a Boolean context can be
simulated with our syntax,
using the Boolean expressions

\neg(\tau\in[0,\mathbf{false},\mathbf{null}])
.

We define the semantics of Boolean expressions in terms of what it means for a
d-value to satisfy a Boolean expression.

Definition 9

Let
v
be a d-value and
\varphi
a Boolean expression. The

satisfaction
of
\varphi
by
v
, denoted

, is
defined inductively as follows:

\begin{array}[]{lll}v\models\exists p&\text{ if }&\llbracket p\rrbracket^{v}\neq\mathbf{null}\\
v\models\tau_{1}\mathop{\mathsf{op}}\tau_{2}&\text{ if }&\llbracket\tau_{1}\rrbracket^{v}\mathop{\mathsf{op}}{}\llbracket\tau_{2}\rrbracket^{v}\text{\hskip 10.22217ptfor }\mathop{\mathsf{op}}\in\{=,\leq\}\\
v\models\tau\in\tau^{\prime}&\text{ if }&\llbracket\tau^{\prime}\rrbracket^{v}\text{ is an array \hskip 10.22217ptand \hskip 10.22217pt$\llbracket\tau\rrbracket^{v}$ appears in $\llbracket\tau^{\prime}\rrbracket^{v}$}\\
v\models\neg\varphi&\text{ if }&v\not\models\varphi\\
v\models\varphi_{1}\land\varphi_{2}&\text{ if }&v\models\varphi_{1}\text{ and }v\models\varphi_{2}\\
\end{array}

For the semantics of
\leq
, we assume a total order over the set
\mathcal{V}
of
d-values and refer to it as the
natural order
over
\mathcal{V}
. In
Appendix

, we show how such an order can be defined
inductively out of an (underspecified) order over the set
\mathcal{L}
of literals.

A project stage

is parameterized with a sequence

If

(where

then
\mathsf{pr}_{D}
intuitively
transforms an object

associated with the

For instance, if

is the object

\langle k_{1}\mapsto\langle k_{2}\mapsto\langle k_{3}\mapsto\llbracket\tau\rrbracket^{o}\rangle\rangle\rangle.

Definition 10

Let
o
be an object,
p
an index-free path and

We denote by
\mathsf{obj}_{p\mapsto v}

For instance, if

To understand how a sequence of path definitions transforms an object, we
define what it means to merge a path-value pair into an existing object.
Let

be an object and
p\mapsto v
a path-value pair such that

does not

•

•

•

Intuitively, if path

3.2.4
Group

A group stage
\mathsf{gr}_{g\text{\bf\,:\,}A}
is parameterised with an optional
grouping
key

g
and a sequence
A
of
aggregation keys
such that
{\small\textup{{\_\!\!\;id}}}\notin A
.
The grouping key
g

specifies how the input collection should be partitioned into equivalence
classes. For each equivalence class, the stage outputs one document that
contains an array of aggregated values for each key in
A
.
Given a collection
O
of objects, the semantics of a group stage is defined as:

({O,\,I})\blacktriangleright{\mathsf{gr}_{g\text{\bf\,:\,}A}}=\big\{\!\!\big\{\ \mathsf{agg}_{A}(\gamma)\mid\gamma\in\mathsf{groups}_{g}(O)\ \big\}\!\!\big\}

where
\mathsf{group}_{g}(O)
is the set of equivalence classes induced by
g
over

O
, and
\mathsf{agg}_{A}(\gamma)
aggregates according to
A
the objects within the
equivalence class
\gamma
.

If
g
is a key, then an
equivalence class

\gamma\in\mathsf{group}_{g}(O)
is a
non-empty bag composed of all objects
o\in O
whose value of the grouping
key
g
agrees with the class identifier
\gamma_{\text{id}}
, i.e.,

o(g)=\gamma_{\text{id}}
.
If
g
is nothing (
\mathbf{null}
in MongoDB), then all objects in
O
are grouped
into one equivalence class
\gamma
with
\gamma_{\text{id}}=\mathbf{null}
, and

\mathsf{group}_{g}(O)=\{O\}
.
The object
\mathsf{agg}_{A}(\gamma)
is specified as:

\mathsf{agg}_{A}(\gamma)=\langle{\small\textup{{\_\!\!\;id}}}\mapsto\gamma_{\text{id}}\rangle\ \cdot\ \big\langle a\mapsto\mathsf{agg}_{a}(\gamma)\mid a\in A\big\rangle

where ‘
\cdot
’ stands for the concatenation of two sequences, and

\mathsf{agg}_{a}(\gamma)=\lfloor\!\,o(a)\mid o\in\gamma\rfloor
collects the values of
a

in the objects of
\gamma
(in any order).

Delta with MongoDB’s implementation (version
8.0.12
).

Our formalisation of the group stage departs from the one implemented in
MongoDB, in that we crystallise in the group stage the functionality pertaining to grouping only, while excluding the functionality associated or
realisable with the project stage.

In particular, in MongoDB the group stage may rename paths, construct objects
and arrays, evaluate arbitrary expressions (terms in our terminology), as well
as compute values of aggregate functions.
Instead, the
MQuery
group stage can only group documents according to the
value of the grouping key and collate the values of aggregation keys into
arrays.

While this affects the expressivity of the group stage, it does not change the
expressivity of
MQuery
, since every group stage can be preceded by a project
stage to rename paths and to construct values as needed. Furthermore, aggregate
functions such as
count
,
min
,
max
,

average
, etc, can be computed in a subsequent project stage.

3.2.5

A lookup stage
\mathsf{lo}^{X,t}_{p}
is parameterized with
a set
X
of variable definitions,
a so-called query template
t
over
X
, and
an output path
p
.

A
query template

t
over
X
is a query that may contain variable names
from
X
in place of terms (in path definitions and Boolean expressions); it
can be turned (‘grounded’) into an MQuery by substituting variables with
d-values.
For an object
o
, the
grounding

\mathsf{ground}_{X}(t,o)
of a query template

t

according to

X
and
o
is the query obtained by substituting in

t
the variable
x
with the d-value
\llbracket p\rrbracket^{o}
, for each
x/p\in X
.

Given an input collection
O
, the lookup stage is evaluated as

({O,\,I})\blacktriangleright{\mathsf{lo}^{X,t}_{p}}=\Big\{\!\!\Big\{\ o\oplus^{*}\big(p\mapsto\mathsf{agg}_{\varepsilon}(O_{t})\big)\Bigm|o\in O\ \Big\}\!\!\Big\}.

In other words, the lookup stage
\mathsf{lo}^{X,t}_{p}
extends each object
o
in

O
with the path-value pair
p\mapsto\mathsf{agg}_{\varepsilon}(O_{t})
, where

O_{t}={\big(\mathsf{ground}_{X}(t,o)\big)}^{I}
is the evaluation of
t
grounded
according to
X
and
o
, and

o\oplus^{*}(p\mapsto v)
stands for
o\oplus(p\mapsto v)
when
p
is not
present in
o
and for
o[p/v]
that
p
is present in
o
.
Recall that
\varepsilon
is the empty path, so
\mathsf{agg}_{\varepsilon}(O_{t})

transforms the collection
O_{t}
into an array.

analogous to the so-called

of relational databases. We
illustrate it on an example.

3.2.6
GraphLookup

The graphLookup stage performs a recursive traversal through a collection, following references between documents.
This is useful for hierarchical data like organizational charts or category trees, where one need to find all descendants of a given node.
The traversal is performed over objects of an external collection.
The grahLookup operator defines two binary relations:

S
connects objects
from the input collection to
objects of the external collection that will act as “starting points” of the traversal,
whereas
R
defines the traversal relationship itself, within the external collection.

Syntactically, a graphLookup stage
\mathsf{gl}^{p_{s},C,p_{f},p_{t}}_{p_{o}}
is parameterized with
a seed path
p_{s}
,
a
from
path
p_{f}
,
a
to
path
p_{t}
,
an output path

and
a collection name

The “seed” and “to” paths

and
p_{t}
specify the binary relation

, where
O
is the collection input to the graphLookup
stage and

the “external” collection.
Similarly, the “from” and “to” paths
p_{f}
and
p_{t}
specify the binary
relation

.
Let

denote the transitive closure of

extends each object

Formally,
the relations

and

\displaystyle S

\displaystyle=\left\{(o_{s},o_{t})\in O\,\,\times C^{I}\bigm|\llbracket p_{s}\rrbracket^{o_{s}}=\llbracket p_{t}\rrbracket^{o_{t}}\right\}

\displaystyle R

\displaystyle=\left\{(o_{f},o_{t})\in C^{I}\times C^{I}\bigm|\llbracket p_{f}\rrbracket^{o_{f}}=\llbracket p_{t}\rrbracket^{o_{t}}\right\}

The transitive closure

\{(o_{1},o_{2}),(o_{2},o_{3})\}\subseteq T\text{ implies }(o_{1},o_{3})\in T

({O,\,I})\blacktriangleright{\mathsf{gl}^{p_{s},C,p_{f},p_{t}}_{p_{o}}}=\Big\{\!\!\Big\{\ o\oplus^{*}(p_{o}\mapsto a_{o})\Bigm|o\in O\ \Big\}\!\!\Big\},

3.3
Additional Stages

In this section, we introduce additional stages of the
MQuery
language, which we excluded from the core fragment.
They are the counterparts of the MongoDB operations
$count
,
$sort
,
$skip
and
$limit
.

The stages of the core fragment, as well as the count stage,
operate on collections, which are bags (a.k.a. multisets) of objects.
In contrast,
the sort, skip and limit stages take as input or produce ordered collections.
This is why we first introduce the count stage (using bags, as we did for the core stages).
Then in Section
3.3.2
, we extend our semantics to accommodate for ordered collections,
and then only, in the sections that follow, we define the semantics of the three remaining stages.

3.3.1
Count

A count stage
\mathsf{co}_{k}
is parameterized with a key
k
.
It returns a single object with the size of the input collection as value for
k
, i.e.

({O,\,I})\blacktriangleright{\ \mathsf{co}_{k}}=\{\!\!\{\langle k\mapsto n\rangle\}\!\!\}

where
n
is the cardinality of the bag
O
.

3.3.2
Ordered Collections

If
O
is a collection (i.e. a bag of objects),
we use
\mathcal{S}(O)
for the set of all (bag) permutations of
O
,
i.e. all possible ways to order the elements of
O
(while respecting their cardinalities in
O
).
We represent each of these permutations as an array of objects.
For instance, if
O=\{\!\!\{o_{1},o_{1},o_{2}\}\!\!\}
, then

\mathcal{S}(O)=\{\lfloor\!\,o_{1},o_{1},o_{2}\rfloor,\lfloor\!\,o_{1},o_{2},o_{1}\rfloor,\lfloor\!\,o_{2},o_{1},o_{1}\rfloor\}
.
We call an element of
\mathcal{S}(O)
an
ordered collection
.

Some of the stages that we will introduce take as input or produce an ordered collection.
This contrasts with the stages that we have seen so far, which instead take as input and produce a ”regular” collection (a.k.a. bag of objects).
In order to provide a unified semantics for all (core and non-core) stages,
we first reformulate the semantics of the stages seen so far, so that it can handle ordered collections.
The definition is equivalent, but non-deterministic (therefore a little bit harder to understand, which is why we have used bags so far).

First, if
a
is an array of objects, we write
\mathsf{bag}(a)
for the bag that it induces.
For instance, if
a=\lfloor\!\,o_{1},o_{1},o_{2}\rfloor
, then
\mathsf{bag}(a)=\{\!\!\{o_{1},o_{1},o_{2}\}\!\!\}
(or equivalently
\{\!\!\{o_{1},o_{2},o_{1}\}\!\!\}
or
\{\!\!\{o_{2},o_{1},o_{1}\}\!\!\}
).
Next, recall that the evaluation of a core stage
s
over a database instance
I
and collection
O
is the bag denoted

({O,\,I})\blacktriangleright{s}
.
We adopt a nearly identical notation for ordered collections:
we write
({a,\,I})\lfloor\!\,\blacktriangleright\rfloor{s}
for the evaluation of
s
over
I
and an ordered collection (a.k.a. array of objects)
a
.

We can now adapt the semantics of our stages accordingly.
If
s
is a project, unwind, match, group, lookup, graphLookup union or count stage,
then
({a,\,I})\lfloor\!\,\blacktriangleright\rfloor{s}
is any permutation of the collection obtained by evaluating
s
over
I
and (the bag induced by)
a
.
Or in other words:

({a,\,I})\lfloor\!\,\blacktriangleright\rfloor{s}\in\mathcal{S}(({I,\mathsf{bag}(a)})\blacktriangleright{s})

With a slight abuse of notation, in what follows, we may use
\mathcal{S}(a)
(instead of
\mathcal{S}(\mathsf{bag}(a))
) to denote the set of permutations of an array
a
.

3.3.3

We call
object comparator
a expression of the form
p^{+}
or
p^{-}
, where
p
is a path.
Intuitively, the path
p
indicates values to be compared in two objects,
and the exponent (
+
or
-
) determines whether the comparison should be performed in ascending or descending order.

A sort stage
\mathsf{so}_{S}
is parameterized with a nonempty sequence
S
of object comparators,
which are combined in a lexicographic fashion to sort the input collection.
For instance, the following

(and its aggregate query counterpart on the left) sorts the bands of our collection w.r.t. their year of formation in descending order and, in case of a tie, w.r.t. their names in ascending order.

⬇

.

.
aggregate
([{

:

{

"formation"
:

"name"
:

1

}

}])

\begin{array}[]{l}\texttt{bands}\\[-1.42262pt]
\hskip 19.91684pt{}\triangleright\mathsf{so}_{\texttt{formation}^{-},\ \texttt{name}^{+}}\end{array}

Formally, the sequence
S=p_{1}^{e_{1}},\ldots,p_{n}^{e_{n}}
specifies a total preorder
\preceq_{S}

over the universe
\mathcal{O}
of all objects, defined inductively as

\displaystyle o_{1}\preceq_{S}o_{2}\text{ iff }

\displaystyle o_{1}(p_{1})<o_{2}(p_{1})\text{ and }e_{1}\text{ is }+,\text{ or }

\displaystyle o_{1}(p_{1})>o_{2}(p_{1})\text{ and }e_{1}\text{ is }-,\text{ or }

\displaystyle o_{1}(p_{1})=o_{2}(p_{1})\text{ and }o_{1}\preceq_{p_{2}^{e_{2}}\ldots,p_{n}^{e_{n}}}o_{2}

({a,\,I})\lfloor\!\,\blacktriangleright\rfloor{\ \mathsf{so}_{S}}\ \quad\text{ is any array }a_{s}\in\mathcal{S}(a)\text{ that satisfies }i\leq j\text{ implies }a_{s}[i]\preceq_{S}a_{s}[j]

is the length of

Note that the semantics of the sort stage is non-deterministic when
\preceq_{S}
is not an order, but only a preorder (for instance, if we sort our collection of bands by year of formation only, and two bands have been formed during the same year).
In other words, if two distinct objects in

In particular, we do not require stable sorting (but this may be a feature of a specific implementation).

4
Expressive Power of MQuery, Informally

In this section we show an informal correspondence between MQuery and
well-known relational query languages
Codd 1990
;
Thomas and Fischer 1986
;
Van den Bussche 2001
. In
particular, we confirm the intuition that the MongoDB aggregation framework is
very expressive: at least as expressive as full
relational algebra (RA)
.
To summarise:

•

the match, unwind, project and group fragment captures RA over a single
relation.

•

the match, unwind, project, group, and lookup fragment captures arbitrary
RA.

This means that joins are possible in MongoDB, even without lookup, the
explicit join operator.

Recall the RA operators:

•

Selection
(
\sigma
) uses a Boolean condition to filter out tuples that do
not satisfy the condition;

•

Projection
(
\pi
) can be used to project away attributes;

•

Join
(
\bowtie
) can be used to extend the tuples in one relation with tuples
in another relation;

•

Union
(
\cup
) and
difference
(
\setminus
) are standard set operators (under set semantics) or bag operators (under bag semantics).

In this report, we assume that the reader is familiar with the syntax and
semantics of relational algebra expressions.

We
illustrate
the expressive power of MQuery by showing how each relational algebra operator can be simulated. Intuitively:

•

Selection
(
\sigma
). The match stage directly
corresponds to a selection, filtering documents based on a Boolean condition.

•

Projection
(
\pi
). The project stage provides projection capabilities. More precisely, it corresponds to an
extended projection
,
as it allows to compute new values through expressions involving function calls, conditional expressions and complex value constructions.

•

Join
(
\bowtie
). Most interestingly, joins can be expressed in multiple ways:

–

explicitly using lookup stages, or

–

implicitly by combining the unwind and group operations.

•

Union
(
\cup
). Similarly to joins, unions can be expressed in multiple ways:

–

with the union stage, which provides explicit union semantics, or

–

through a combination of group and project.

•

Difference
(
\setminus
). This operation can be expressed through a combination of group, project and match.

•

Beyond Relational Algebra:
MQuery extends beyond traditional RA:

–

MQuery
subsumes
nested relational algebra (NRA)
designed to
operate over relations that are not in first normal form, i.e., where an attribute
value can be a nested relation.

*

Group corresponds to the
nest (
\nu
)
operator, which allows
creating nested relations.

*

Unwind corresponds to the
unnest (
\chi
)
operator, which allows
flattening nested relations.

–

MQuery
supports a form of linear recursion
Agrawal 1988
via graphLookup.

4.3

In traditional relational databases, join computation is recognized as one of
the primary reasons for slow query performance. To ensure efficient query
evaluation,
many NoSQL databases (including MongoDB) were initially not offering an
explicit join operator. However, owing to the expressivity of the MongoDB
aggregation framework, it was already possible to compute joins over a same
collection even before the introduction the
$lookup

explicit join operator). In what follows, we show how to simulate joins in

MQuery
without using lookup.

Assume that we want to find all pairs of bands that released an album in the
same year. A (nested) RA query would need to unnest the attribute “albums” and
join the resulting relation with itself. Before unnesting, to simplify
specification of the joining condition, we could rename the attributes “name” and
“albums”, and
project away irrelevant information, such as the year of formation or the members of the
bands

\hskip 39.83368pt\pi_{\text{name}_{1}/\text{name},\ \text{albums}_{1}/\text{albums}}\\
\hskip 59.75095pt\textit{bands}\\
\hskip 19.91684pt\chi_{\text{albums}_{2}}\\
\hskip 39.83368pt\pi_{\text{name}_{2}/\text{name},\ \text{albums}_{2}/\text{albums}}\\
\hskip 59.75095pt\textit{bands}\end{array}

\begin{array}[]{l}\texttt{bands}\\
\hskip 19.91684pt{}\triangleright\mathsf{pr}_{\texttt{rel.name}/\texttt{name},\ \texttt{rel.albums}/\texttt{albums}}\\
\hskip 19.91684pt{}\triangleright\mathsf{uw}_{\texttt{rel.albums}}\\[2.84526pt]

5
Differences with MongoDB’s Implementation

We illustrate and motivate here the main differences between the semantics defined in the previous sections and the one applied by MongoDB version
8.0.12
(for the aggregation framework).
Our depiction of MongoDB’s behavior’s is only partially based on its documentation.
In other cases, when the documentation was incomplete, we made hypotheses, tested them (via queries) and extrapolated the underlying rationale.
But as with any (black-box) reverse-engineering process, some of these hypotheses may be incorrect.

5.1
A Unified Semantics for Boolean Expressions

Two concrete syntaxes for Boolean expressions coexist within the MongoDB aggregation framework,
called “query predicates” and MongoDB “expressions” respectively,
with slightly different semantics.
This situation seems partly due to the historical development of the system.

Our proposal unifies these two syntaxes under a single grammar for Boolean expression.
This eliminates confusion about which semantics applies,
and provides a more principled foundation for query optimization.
We illustrate below these two syntaxes and their respective semantics, each in its own section.
In each case, we also explain how they compare to the Boolean expressions used in
MQueries
,
and motivate our choices.

5.1.1
Query Predicates

A Boolean expression written in the first syntax is called a
query predicate
.
For instance, in the following query,
the expression

{"origin": {$eq: "UK"}}
is a query predicate,
used to filter documents where the key
origin
has value
”UK”
.

⬇

db
.
bands
.
aggregate
([

{

$match
:

{

"origin"
:

{

$eq
:

"UK"

}

}

}

])

Note that MongoDB’s syntax also allows omitting the
$eq
operator in this context (e.g. writing
{"origin": "UK"}
),
for a (seemingly) identical behavior.

Query predicates are borrowed from so-called MongoDB
find
queries, which form a distinct,
less expressive query language that predates the introduction of the aggregation framework.
Within the aggregation framework, query predicates are used (by default) as filtering conditions in match stages,
as in this example, and possibly in lookup stages to express a joining condition.

As we can see in this query, a query predicate can make use of the operator
$eq
,
which is MongoDB’s syntax for equality.
In this case, the equality stands between the evaluation of the path
origin
and the value
”UK”
.
So one may expect this query to correspond to the following
MQuery
:

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin}=\textit{"UK"}}

This is not the case though, because query predicates rely on a looser notion of “equality” for paths that evaluate to an array.
For instance, let us assume that our collection
bands
provides values for
origin
that may be literals (e.g.
”UK”
for the band Queen) or arrays (e.g. [
”UK”, ”Japan”, ”US”
] for the band Gorillaz), as follows:

⬇

{

{

"_id"
:

1,

"name"
:

"Queen"
,

"origin"
:

"UK"

},

{

"_id"
:

2,

"name"
:

"Gorillaz"
,

"origin"
:

[
"UK"
,

"Japan"
,

"US"
]

}

}

Over this collection,
the query above would retrieve the document for Queen, as expected.
But it would also retrieve the document for Gorillaz,
which may come as a surprise.
The reason is that the array [
”UK”, ”Japan”, ”US”
] (which is the evaluation of
origin
in this document) contains
”UK”
.

So a more appropriate translation in
MQuery
would be:

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin}=\textit{"UK"}\ \lor\ \textit{"UK"}\,\in\,\texttt{origin}}

In other words,
MQueries
apply a stricter semantics than query predicates for the “equality” operator (denoted ”=” in
MQueries
),
when comparing the interpretation of a path to a value (as in this example) or comparing the interpretations of two paths:
the equality holds iff both values are identical.

The reason for this choice is algebraic: a relaxed notion of equality is not necessarily an issue,
but it should induces a so-called
equivalence relation
over compared elements.
For instance, programming and query languages often provide additional comparison operators that relax strict equality,
such as case-insensitive equality for two strings,
or separator-insensitive equality for two paths.
Let us use
a\sim b
to denote the fact that
a
and
b
are ”equal” in this relaxed sense.
Three elementary algebraic properties are normally expected from such a relation,
which together form the definition of an equivalence relation:
reflexivity (
a\sim a
),
symmetry (
a\sim b
implies
b\sim a
) and
transitivity (
a\sim b
and
b\sim c
imply
a\sim c
).
These are elementary properties for algebraic optimization,
used (among others) to simplify an expression or determine whether two expressions are equivalent.
For instance, the expression

a\sim b\land(c\sim a\lor c\sim b)

can be simplified as

a\sim b\land c\sim a
(due to transitivity),
and is equivalent to

a\sim b\land a\sim c
(due to symmetry).

Now observe that
when used inside MongoDB query predicates,
the
$eq
operator violates both symmetry and transitivity.
For instance, consider the following query,
evaluated over the same collection as above:

⬇

db
.
bands
.
aggregate
([

{

$match
:

{

"origin"
:

{

$eq
:

[
"UK"
,

"Japan"
,

"US"
]

}

}

}

])

This query returns the document for Gorillaz (as expected), but not the document for Queen.
So according to this relaxed notion of equality,

”UK”
(in the data) does not match [
”UK”, ”Japan”, ”US”
] (in the query),
but,
as we saw with the previous query,
[
”UK”, ”Japan”, ”US”
] (in the data) matches
”UK”
(in the query),
which violates symmetry.

Transitivity is also violated.
For instance,
[[
”UK”
]]
matches
[
”UK”
],
and the latter matches

”UK”
.
But

[[”UK”]]

does not match

”UK”
.
Note also that a symmetric version of MongoDB’s relaxed equality would still violate transitivity.
Precisely, if we define it (in
MQuery
’s syntax) as
a\sim b
iff

a=b\lor a\in b\lor b\in a
,
then

”UK”
matches
[
”UK”, ”Japan”
],
and the latter matches

”Japan”
.
But

”UK”

does not match

”Japan”
.

This is why we opted for a stricter notion of equality,
which does induces an equivalence relation over compared elements.
But we emphasize that this is without loss of expressivity.
As we illustrated above, the behaviour of query predicates can still be simulated in
MQuery
,
albeit with a slightly more complex syntax.
So our proposal does not technically rule out query predicates, but treats them instead as syntactic sugar rather than primitives.
We believe that this approach is better-suited to a good understanding of the algebraic properties of the language.

Before describing the second syntax (and semantics) for Boolean expressions within MongoDB,
we briefly discuss the treatment of other comparison operators within MongoDB query predicates,
which is analogous to the treatment of equality.
Let us assume that our collection contains (starting) years of tours of each band, for instance:

⬇

{

{

"_id"
:

1,

"name"
:

"Gorillaz"
,

"tours"
:

[2010,

2015]

},

}

The following query retrieves the document above, because at least one value in the array [2010, 2015] is inferior to 2012.

⬇

db
.
bands
.
aggregate
([

{

$match
:

{

"tours"
:

{

$lt
:

2012

}

}

}

])

So the array [2010, 2015] (in the data) matches the condition ¡ 2012 (in the query).
However, similarly to what we observed for equality,
2012 (in the data) does not match the condition ¿ [2010, 2015] (in the query),
thus violating one of the elementary algebraic properties expected from a total order (
a<b
implies
b>a
).

Besides, the following query also retrieves the document above, because 2015 is superior to 2012.

⬇

db
.
bands
.
aggregate
([

{

$match
:

{

"tours"
:

{

$gt
:

}

}

}

])

So the array [2010, 2015] matches not only the condition ¡ 2012, but also the condition ¿ 2012.
At the algebraic level, this means that both
a<b
and
a>b
may hold.

These two examples show that within query predicates,
similarly to the
$eq
operator,
the behaviors of

$lt
and

$gt
violate elementary properties of (total) orders (and similar observations can be made for

$lte
and

$gte
).
So once again,
in
MQueries
,
we opted for a stricter interpretation of these operators.

5.1.2

In addition to query predicates (discussed in the previous section),
the aggregation framework supports a second syntax for Boolean expressions.
Precisely, a query can use so-called MongoDB “expressions”,
which are analogous to the
terms
of Grammar (
1
)
(in the sense that an expression evaluates to a literal, array or object).
Among these, expressions that evaluate to true or false are effectively Boolean expressions.
For instance, consider the following query:

⬇

.

.

([

{

:

{

:

{

:

[

]

}

and the keyword

MongoDB expressions are also used in other stages of the aggregation framework (e.g. project, unwind or group),
without the need for the

At first sight, the query above seems very similar to the one that we used in the previous section (reproduced here for convenience):

⬇

.

([

{

:

{

"origin"
:

{

:

"UK"

}

}

}

Intuitively, both queries retrieve bands with

as origin.
However, their syntaxes differ: the former uses a MongoDB “expression” in place of a query predicate,
whereas the latter uses a query predicate directly.
This difference is reflected in their respective semantics.
For instance, let us consider the same collection as above (reproduced here for convenience):

⬇

{

{

"_id"
:

1,

"name"
:

"Queen"
,

"origin"
:

"UK"

{

In other words, the first query corresponds to the

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin}=\textit{"UK"}}

whereas the latter corresponds to

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin}=\textit{"UK"}\ \lor\ \textit{"UK"}\,\in\,\texttt{origin}}

We already highlighted in the previous section how the semantics of

In contrast, in a MongoDB Boolean “expression”

And an analogous observation can be made for the operators

and

(written

and

5.2
Interpretation of Paths

MongoDB’s interpretation of paths has subtle behaviors that can be hard to predict:
the intuitive meaning of a path may vary, depending on the document in which it is interpreted.
We already observed this behavior for atomic paths (i.e. paths that consist of a single key) in the previous section.
We saw with our running example that the path
origin
in a MongoDB “expression” (Section
5.1.2
) was interpreted ”literally”, as the value that it points to in an object.
In contrast, in a MongoDB query predicate (Section
5.1.1
),
we saw that this path could be interpreted in a more liberal way, either as the value that it points to, or, if it points to a array, as the set of values contained in this array.

We already explained above why this ambiguity may not be desirable in a Boolean condition.
This is why
MQuery
shifts away from the semantics of query predicates,
and adopts instead a semantics for expressions that is closer to MongoDB “expressions”.
However, if atomic paths in MongoDB “expressions” are indeed non-ambiguous, this is not the case of composite ones.
To illustrate this, we will use a slight variation over the example above.
Let use assume that the collection
bands
contains the following document:

⬇

{

"_id"
:

2,

"name"
:

"Gorillaz"
,

"origin"
:

{

"country"
:

[
"UK"
,

"Japan"
]

}

}

The following query uses a MongoDB “expression” to select bands where the value of the path
origin.country
is [
”UK”, ”Japan”
].

⬇

db
.
bands
.
aggregate
([

{

$match
:

{

$expr
:

{

$eq
:

[

"$origin.country"
,

[
"UK"
,

"Japan"
]

]

}

}

}

])

As expected, this query retrieves the document above.
So a naive conversion of this query into
MQuery
would be

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin.country}=[\textit{"UK"},\textit{"Japan"}]}

However, this conversion is incorrect.
To see this, let us assume that our document has instead a slightly different shape:

⬇

{

"_id"
:

2,

"name"
:

"Gorillaz"
,

"origin"
:

[

{

"country"
:

"UK"
,

"city"
:

"London"

},

{

"country"
:

"Japan"

}

]

}

The value of

is still an array, but this time it contains two objects, rather than two scalars.
Surprisingly, the query above also retrieves this document.
The reason is that
$origin.country
evaluates to
["UK", "Japan"]
in this document,
even if the document does not contain such an array.

In other words, the meaning of
$origin.country
in this query is overloaded.
It may be interpreted in two alternative ways, depending on the document
o
under consideration:

1.

the first interpretation occurs when this path points to a d-value
d
(i.e. an array, object or scalar) in
o
.
In this case,
$origin.country
evaluates to
d
.

2.

the second interpretation occurs when the prefix
$origin
points to an array
a
in
o
.
In this case,
$origin.country
evaluates to another array,
which consists of the evaluation of the suffix
$country
in each element of
a
.

In
MQuery
, we decided instead to shift away from this polysemy.
More precisely, we require using the
\mathsf{map}
operator explicitly for the latter of these two meanings.
So a more appropriate conversion of the query above into
MQuery
is

\texttt{bands}\triangleright\mathsf{ma}_{\ \texttt{origin.country}=[\textit{"UK"},\textit{"Japan"}]\ \lor\ \mathsf{map}({\texttt{origin}},\>\lambda{x}\colon{x.\texttt{country}})=[\textit{"UK"},\textit{"Japan"}]}

There are three main reasons for this choice.
The first one is practical: from a software engineering perspective, the potential drawbacks of this polysemy outweighs its benefits.
To understand this, let us first focus on the benefits, namely the fact that MongoDB’s overloaded interpretation offers a more concise syntax.
For instance, in this example, the MongoDB ”expression”

$eq: [ "$origin.country", ["UK", "Japan"]]

is sufficient to encode (the disjunction of) the two
MQuery
Boolean expressions
\texttt{origin.country}=[\textit{"UK"},\textit{"Japan"}]
and

\mathsf{map}({\texttt{origin}},\>\lambda{x}\colon{x.\texttt{country}})=[\textit{"UK"},\textit{"Japan"}]
.
However, it is hard to imagine a situation where on would want to leverage such a polysemy:
when an end-user writes
$origin.country
in a query, this is most likely with one of the two meanings in mind, not both.
And an analogous observation can be made if the query is automatically generated (either programmatically or by an agent).

The drawback of this overloaded semantics is that a query may produce results that correspond to the ”other”, unintended meaning, which, as any bug, can have a non-negligible cost.
Besides, when undesired, these results need to be filtered out explicitly, which eventually results in a syntactically more complex query.

Worse, this polysemy grows exponentially with the length of paths.
For instance, a seemingly innocuous expression of the form
$a.b.c.d.e.f
has
2^{(6-1)}=32
alternative meanings, out of which very few (most likely one) will be the intended one(s).
This can make the evaluation of a query hard to explain or predict, especially when the queried data does not follows a regular structure.
As an (artificial) illustration, predicting the evaluation of
$a.b.c
in the following object can be a puzzle (the answer is
[[1],[2,3]]
):

⬇

{

"a"
:

[

{

"b"
:

{

"c"

:

[1]

}

},

{

"b"
:

[

{

"c"

:

2

},

{

"c"

:

3

}

]

}

]

}

The second reason for our choice to deviate from MongoDB’s interpretation of paths is computational.
As we just explained, the number of alternative meanings of a path grows exponentially with its length.
So a naive evaluation of a Boolean expression that contains such a path may perform exponentially many verifications within a single object.

The third reason has to do with coherence.Paths are used not only in expressions, but also as so-called MongoDB
fields
,
to specify where the output of an operation must be stored
(in stages like project, unwind, lookup, group, etc.).
For instance, consider the following query:

⬇

db
.
bands
.
aggregate
([

{

$project

:

{

"name"

:

"$name"
,

"creation.year"

:

"$formation"
,

"creation.location"

:

"$origin"

}

}

])

This query selects the name, year of formation and origin of each band,
grouping the latter two into a nested object with (up to) two attributes
year
and
location
.
It uses three MongoDB fields (
name
,
creation.year
and
creation.location
),
two of which are composite paths.

When a path is used as a MongoDB field, its meaning is non-ambiguous, which contrasts with what we observed above for paths used in expressions.
This discrepancy may easily results in queries with unexpected behaviors.
For instance, the following query projects the name and country(ies) of each band in our collection.
Then it selects the bands with countries [
”UK”, ”Japan”
].

⬇

db
.
bands
.
aggregate
([

{

$project

:

{

"name"

:

"$name"
,

"origin.country"

:

"$origin.country"

}

},

{

$match

:

{

$expr
:

{

$eq
:

[

"$origin.country"
,

[
"UK"
,

"Japan"

]

]

}

}

}

])

At first sight, the project stage in this query seems like a plain projection (similar to a projection in relational algebra,
whose only purpose is to select some attributes).
When optimizing a query, it is common practice to postpone such an operation.
For instance, in this example, let us assume that the collection
band
has an index over the field
origin.country
.
Then it would be tempting to swap the order of the two stages, so that the selection (a.k.a. match stage) can take advantages of this index.
However, this would alter the semantics of the query.
Indeed, as we saw earlier, in a source document,
$origin.country
may evaluate to an array that was not present.

We believe that a unified semantics for paths (regardless of whether they are used as expressions or fields) is less error-prone,
in particular when performing algebraic transformations.

5.3
Ordering

MongoDB’s documentation provides information about the way BSON atomic values, arrays and objects are naturally ordered.
7
7

7

https://www.mongodb.com/docs/manual/reference/bson-type-comparison-order

This ordering is meant to determine the behavior of the sort stage,
as well as the comparison operators

$lte
,

$lt
,

$gte
and

$gt
(written
\leq
,
<
,
\geq
and
>
in
MQuery
)
used in expressions.
More precisely, MongoDB’s documentation specifies a so-called “comparison order” over atomic BSON values,
which is then lifted to arrays and objects.
However, this documentation is only partial, and (as we will see) sometimes contradicts MongoDB’s behavior.

We discuss in what follows four aspects that distinguish MongoDB and
MQueries
when it comes to ordering:

(i)
how literals are ordered,
(ii)
how this ordering is lifted to arrays and objects,
and how
(iii)
comparison operators and
(iv)
sorting operations behave when evaluating a query.

5.3.1
Literals

As we already explained,

MQuery
abstracts from concrete datatypes such as string, integer, float, etc.
When it comes to ordering, we only assume a total order
\leq
over literals, which should coincide (semantically) with the
\leq
operator used in
MQuery
expressions.

This requirement is already a slight deviation from (or more precisely, an abstraction of) what MongoDB’s documentation describes.
To understand this, we need to discuss what ”total order” precisely means.
First, a
preorder

\preceq
is a transitive and reflexive binary relation over a set.
This relation is said to the
total
if all elements of
S
can be compared with each other (i.e. if
e_{1}\preceq e_{2}
or
e_{2}\preceq e_{1}
holds for all
e_{1},e_{2}\in S
).
Intuitively, a total preorder is all we need to sort the elements of a set.

Note that a preorder does not forbid two distinct elements to be comparable (i.e.
e_{1}\preceq e_{2}
and
e_{2}\preceq e_{1}
may both hold for some
e_{1}\neq e_{2}
).
For instance,
one can sort a set of people by age, even if two of them have the same age.
An
order
is a preorder that excludes this possibility, meaning that it also satisfies antisymmetry (in addition to reflexivity and transitivity),
i.e.
e_{1}\preceq e_{2}
and
e_{2}\preceq e_{1}
imply
e_{1}=e_{2}
.
This is for instance the case of the natural order over real numbers.

In
MQuery
, we require
\leq
to be a total order (i.e. a total, reflexive, transitive and antisymmetric binary relation) over literals.
However, it is common practice in databases or programming languages to treat some values with different types (e.g. some integers and floats) as equivalent for sorting and/or comparison purposes.
For instance, the three MongoDB expressions

$eq:[1,1.0]
,

$lte:[1.0,1]
and

$gte:[1.0,1]

all evaluate to
true
.
Therefore the so-called “comparison order” described in MongoDB’s documentation is technically not an order, but a preorder.

As a consequence, the literals of
MQuery
cannot literally coincide with the atomic BSON values of MongoDB.
Instead, they must be viewed as a slight abstraction, namely the equivalence classes induced by MongoDB’s “comparison order”.
For instance,
MQuery
does not distinguish
1
and
1.0
: for all intents and purposes, they are the “same” d-value.
We made this simplification because it makes our definitions more streamlined,
and does not affect the (higher-level) properties that our study focuses on.

5.3.2
Arrays and Objects

MQuery
lifts the order
\leq
over literals to arrays and objects, as specified in Appendix
A.2
.
However, we emphasize that the choice of a specific natural ordering of d-values is irrelevant for our purpose,
as long as this is a total order.
We only defined one for the sake of completeness,
as close as possible to what is described
in the MongoDB’s documentation.

First, the order
\leq
is extended to compare an array with an object or literal,
and an object with a literal.
By convention, literals precede objects, which in turn precede arrays.
MongoDB’s documentation specifies instead a more complex precedence, which depends on concrete datatypes.
Among others, numbers precede objects, which precede arrays, which precede booleans, which precede dates.
Because
MQuery
abstracts from concrete datatypes, we could not enforce such a fine-grained ordering,
and opted instead for a best possible approximation (objects still precede arrays).

Next, the order
\leq
is lifted inductively to complex d-values, in order to compare two arrays and two objects.
Two arrays are compared by means of a standard lexicographic product, analogously to strings:
compare the first element of each array w.r.t.
\leq
,
then the second element in case of equality, etc.
The product of two total orders (resp. preorders) being a total order (resp. preorder),
this guarantees that
MQuery
’s (resp. MongoDB’s) arrays are totally ordered (resp. preordered).

As for objects, they are also compared lexicographically,
one key-value pair after the other (under the ordered semantics), in accordance with MongoDB’s documentation.
One difference here is the way two key-value pairs are compared with each other:
MongoDB first compares the types of the values, then (if identical) the keys (as strings, lexicographically), and then only (if identical) the values.
Because
MQuery
abstracts from concrete datatypes, we used once again the best possible approximation:
first comparing the d-value types of values (literal, array or object), then comparing keys, and then values.
In addition, we specify a way to compare two objects under the unordered semantics (i.e. when the order of keys in an object is semantically irrelevant), which is not supported by MongoDB.

5.3.3
Comparison Operators

The behavior of the operators
$lte
,
$lt

$lte
and
$lte
used
in MongoDB query predicates (see Section
5.1.1
)
seems based on an order (or more precisely preorder, as discussed above) over BSON values that is not total,
meaning that two values may not be comparable.
For instance, let us assume that the collection
bands
contains the following document:

⬇

{

"_id"
:

1,

"name"
:

"Gorillaz"
,

"formation"
:

"January

At first sight, the following query should retrieves all bands formed either before or strictly after 2000:

⬇

:

{

{

:

{

}

{

"formation"

{

2000

}

}

]

},

However, this query does not retrieve the document above, which shows that in this context, the string “
January 1998
” is not comparable with the integer 2000.
This contradicts MongoDB’s documentation, where numbers are said to precede strings.
Besides, this latter interpretation apparently dictates how comparison operators behave in MongoDB “expressions”.
For instance, let us use a MongoDB “expression” in place of a query predicate in the query above (thanks to the operator
$expr
,
as we also did in Section
5.1.2
):

⬇

db
.

This query does retrieve the document above, which seems in line with MongoDB’s documentation.

In

, we opted for the latter behavior.
The reason is that the semantics of MongoDB (and

) Boolean expressions is 2-valued (as opposed for instance to SQL),
so that the operator

must evaluate to

or

With a 2-valued semantics, a total order (or total preorder) guarantees that elementary Boolean properties expected from a “less than or equal” operator are enforced.
For instance,
in

, the expression
\neg(\texttt{formation}>2000)
can be simplified as
\texttt{formation}\leq 2000
,
as in most query and programming languages (and as one would intuitively expect).
However,
over the document above,
the query predicate

evaluates to

(since its negation
"formation": {$gt: 2000}

whereas the seemingly equivalent query predicate

evaluates to

.

There is another reason why the interpretation of comparison operators may differ in MongoDB query predicates and

expressions,
namely the way query predicates are evaluated against arrays.
We already explained and illustrated this in Section
5.1.1
.

The MongoDB

However, their behaviors differ when comparing objects based on arrays present in each object.
For instance, assume that the collection

\texttt{bands}\triangleright\mathsf{so}_{\texttt{tours}^{+}}

So in this example, the

The behavior of MongoDB is different.
From our (empirical) observations,

For instance, in this example the aggregate query returns the objects for the Patti Smith group, ABBA and Queen, in this order,

Besides being harder to understand, the strategy applied by MongoDB violates elementary properties expected from a

⬇

.

{

So if

{\small\textup{{\_\!\!\;id}}}\ i

Whereas according to the second aggregate query:

o_{1}\succeq o_{2}\succeq o_{3}

So in this example,
\preceq
is not the inverse of
\succeq
.

5.4
Data-independent Semantics

The semantic differences discussed above did not address another,
more fundamental question about query evaluation:

can we always reason about query behavior without examining the actual data in collections?

This question is crucial for query optimization and formal analysis.
Classical database theory strongly favors the idea that query semantics should be
determined solely by the query’s logical structure, and not adapt dynamically based on the data
encountered during execution. The principle of
data independence
allows optimizers
to apply algebraic transformations based purely on query structure,
without considering the content of a specific database instance.

MQuery
adopts the data-independent approach,
whereas MongoDB’s implementation exhibits some data-dependent behaviors,
where query semantics can change based on the actual values encountered during execution.
Specifically,
when evaluating a (syntactically valid) aggregate query,
MongoDB may throw a runtime exception if the database instance does not comply with assumptions made in this query.
This means that the query may or may not be semantically valid, depending on the current state of the database.

We provide a simple illustration where this fundamental difference may affect query reasoning and optimization.
The follow aggregate query retrieves bands for which the attribute
origin
is an array, and contains the value “Japan”.

⬇

db
.
bands
.
aggregate
([{

$match
:

{

$expr
:

{

:

[

,

⬇

"_id"
:

1,

"name"

"Gorillaz"
,

"formation"
:

1998,

"origin"
:

[
"UK"
,

"Japan"
,

"US"
]

}

Now let us add to our collection another document, for the band Queen:

⬇

"_id"
:

"name"
:

"Queen"
,

"formation"
:

:

"UK"

}

After adding this second document to the database, the query above does not retrieve the first one (for Gorillaz) anymore.
Instead, it throws an exception, because the attribute

in the second document does not evaluate to an array.

Note that in this example, the query is valid, and so is the data.
However, their combination is not.
This makes any attempt to formalize the semantics of aggregate queries significantly more complex: a query may or may not have a meaning,
depending on the context in which it is used.

We view such exceptions as potential obstacles to a good understanding of the formal properties of this language, notably how it compares (e.g. in terms of expressivity) to well-studied formalisms like (nested) relational algebra.

\displaystyle\texttt{bands}\ \triangleright

6
Algebraic Optimisation

We introduce in this section a variety of algebraic transformations that can be applied to an
MQuery
, while preserving its semantics.
Our purpose is to lay foundations for algebraic query optimisation.
For instance,
when evaluating a query,
one may want to filter documents as early as possible,
in order to reduce the size of the input to an expensive downstream operation.
For the same reason, it is usually preferable to unnest arrays as late as possible.

Algebraic optimisation may not be needed for a simple query, especially if manually crafted by an experienced user:
one may expect the structure of such a query to be already close to optimal.
However,
as the complexity of queries increases,
automated procedures to simplify or just reorganize them may become a necessity.
In particular,
MongoDB being based on JSON, it is not unrealistic to foresee an increasing
number of applications (let alone agentic workflows) rely on automatically generating and combining MongoDB aggregate queries.
And as is often the case with automatically generated ”code”, such queries may not be in a form suitable for efficient execution.

Besides, algebraic manipulations open the possibility to put queries into some
normal form
,
which can have multiple benefits for an evaluation engine.
For instance, this may ease the search for efficient query execution plans.
A normal form may also allow implementing efficient (albeit incomplete) strategies to identify redundancies or inconsistencies in a query (e.g. unsatisfiable subqueries).
MongoDB
8.0.12
already applies such transformations, some of which are (informally) documented.
8
8

8

https://www.mongodb.com/docs/manual/core/aggregation-pipeline-optimization/

In this section, we provide a precise description of a set of transformations that are possible in
MQuery
,
focusing on the core fragment of Grammar
3
(match, project, unwind, union, lookup and graphLookup).
Before we provide these transformations,
Section
6.1
introduces additional notation needed to formulate them.
The transformations themselves are described in the following sections,
each of which focuses on a type of
MQuery
stages (match , unwind, etc.).

6.1
Notation

Equivalence

Our algebraic manipulations transform a (sub)query into an equivalent one.
We will use the symbol
\equiv
to denote query equivalence.
For instance, we write

s_{1}\triangleright s_{2}\equiv s_{2}\triangleright s_{1}

to state that the stage
s_{1}
can freely be executed before or after the stage
s_{2}
.
Formally, this means that for any collection
O
and DB instance
I
,

({O,\,I})\blacktriangleright{s_{1}\triangleright s_{2}}=({O,\,I})\blacktriangleright{s_{2}\triangleright s_{1}}

Because the semantics of
MQueries
is compositional, this implies that these two stages can also commute within a more complex query.
More generally,

q\equiv q^{\prime}\ \text{ implies }\ q_{1}\triangleright q\triangleright q_{2}\equiv q_{1}\triangleright q^{\prime}\triangleright q_{2}

for any
MQueries

q,q^{\prime},q_{1}
and
q_{2}
.

Paths and prefixes

Most algebraic equivalences listed below are conditioned by properties of the paths used in the initial query (as well as prefixes of these paths).
For instance, as we will see, an unwind stage
\mathsf{uw}_{p}
may be postponed after a match stage
\mathsf{ma}_{\varphi}
if none of the paths used in
\varphi
is a prefix of
p
or extends
p
.
In order to express this, we introduce a dedicated notation to refer to paths and prefixes.

As a reminder, we say that two paths are compatible if none of them is a prefix of the other.
We will also say below that a path
p
is
compatible with a set

P
of paths if
p
is compatible with every
p^{\prime}
is
P
.

Sometimes we will only need to refer to the prefixes of a path
p
, or only to its extensions.
We use
\mathsf{prefixes}(p)
for the set of prefixes of
p
(including the empty path
\varepsilon
and
p
itself).
For instance,
\mathsf{prefixes}(\mathtt{a.b.2.c})=\{\varepsilon,\mathtt{a},\mathtt{a.b},\mathtt{a.b.2},\mathtt{a.b.2.c}\}
.
We will also use
\mathsf{extensions}(p)
for the (infinite) set of all paths that extend
p
.
For instance,
\mathsf{extensions}(\mathtt{a.b})
contains (among others) the paths
\mathtt{a.b.c}
,
\mathtt{a.b.c.2}
and
\mathtt{a.b.1.d}
.
We technically do not need both notations, since
\mathsf{extensions}(p_{1})=\{p_{2}\mid p_{1}\in\mathsf{prefixes}(p_{2})\}
.
But one may be more convenient than the other in certain contexts.
We also lift these notations to a set
P
of paths, i.e.

\displaystyle\mathsf{prefixes}(P)

\displaystyle=\bigcup_{p\in P}\mathsf{prefixes}(p)

\displaystyle\mathsf{extensions}(P)

\displaystyle=\bigcup_{p\in P}\mathsf{extensions}(p)

Note that “
p
is compatible with
P
” is a shortcut for
P\cap(\mathsf{prefixes}(p)\cup\mathsf{extensions}(p))=\emptyset
.

Next, if
\tau
is a term (which, as a reminder, may be a Boolean expression),
we use
\mathsf{paths}(\tau)
for the set of paths used in
\tau
.
For instance,

\mathsf{paths}(\mathtt{a.b}=5\land\mathtt{c}\neq\mathtt{a.c})=\{\mathtt{a.b},\mathtt{c},\mathtt{a.c}\}
.
However, we need to clarify what
\mathsf{paths}(\tau)
means when
\tau
contains the
\mathsf{map}
or the
\mathsf{filter}
operator,
because this operator can use ”relative” paths.
Intuitively,
\mathsf{paths}(\tau)
is the set of absolute paths used in
\tau
, possibly reconstructed from relative ones.
The full inductive definition of
\mathsf{paths}(\tau)
is mechanical, and provided in Appendix
A.3
.
We only reproduce here the case of the
\mathsf{map}
operator (the case of
\mathsf{filter}
is analogous):

\mathsf{paths}(\mathsf{map}({p},\>\lambda{x}\colon{\tau}))=\{p.p^{\prime}\mid p^{\prime}\in\mathsf{paths}(\tau)\}

Finally,
we use
\tau[p_{1}/p_{2}]
for the term identical to
\tau
,
but where each occurrence of the path
p_{1}
is replaced with the path
p_{2}
.

Paths definitions

As a reminder, a path definition is a pair
p/\tau
, where
p
is an index-free path and
\tau
a term.
A special case is the one where
\tau=p
.
If
D
is a sequence of path definitions, we use
\mathsf{idle}(D)
for the set of such definitions in
D
,
each represented as a single path, i.e:

\mathsf{idle}(D)=\{p\mid p/p\in D\}

We will also use
D^{\rightarrow}
for the set of paths definitions in
D
,
i.e.

\displaystyle D^{\rightarrow}

\displaystyle=\{\tau\mid p/\tau\in D\}

And similarly for a set
X
of variable definitions.

6.2
Match

Applying filters as early as possible is often desirable, for at least two reasons:

1.

when executed as the first operation of a pipeline, a filter many take advantage of indexes over the source collection,

2.

applying filters early can reduce the size of the collections input to other, potentially costly operations (such as grouping).

\hline\cr&\mathsf{ma}_{\varphi}\triangleright\mathsf{ma}_{\psi}&\mathsf{ma}_{\varphi\land\psi}\\
\begin{aligned} p\text{ is compatible with }\mathsf{paths}(\varphi)\end{aligned}&\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}&\mathsf{ma}_{\varphi}\triangleright\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\psi}\\
\begin{aligned} p\text{ is compatible with }\mathsf{paths}(\varphi)\end{aligned}\par&\mathsf{lo}^{X,t}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}&\mathsf{ma}_{\varphi}\triangleright\mathsf{lo}^{X,t}_{p}\triangleright\mathsf{ma}_{\psi}\\
\begin{aligned} \mathsf{paths}(\varphi)\subseteq\mathsf{extensions}(\mathsf{idle}(D))\end{aligned}&\mathsf{pr}_{D}\triangleright\mathsf{ma}_{\varphi\land\psi}&\mathsf{ma}_{\varphi}\triangleright\mathsf{pr}_{D}\triangleright\mathsf{ma}_{\psi}\\
\begin{aligned} \mathsf{paths}(\varphi)\subseteq\mathsf{extensions}({\small\textup{{\_\!\!\;id}}})\end{aligned}&\mathsf{gr}_{g\text{\bf\,:\,}A}\triangleright\mathsf{ma}_{\varphi\land\psi}&\mathsf{ma}_{\varphi[{\small\textup{{\_\!\!\;id}}}/g]}\triangleright\mathsf{gr}_{g\text{\bf\,:\,}A}\triangleright\mathsf{ma}_{\psi}\\
\hline\cr\hline\cr\end{array}

Accordingly,
Figure

provides a series of simple algebraic transformations that allow anticipating the execution of filters.
To explain how to read this table, we focus on the second row.
This row states that for any path
p
and Boolean expressions
\varphi
and
\psi
,
if

p
is compatible with
\mathsf{paths}(\varphi)
,
then:

\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}\equiv\mathsf{ma}_{\varphi}\triangleright\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\psi}

In practice, this means that if this pre-condition on paths and prefixes is satisfied,
then the (sub)query

\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}

can be safely transformed into

\mathsf{ma}_{\varphi}\triangleright\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\psi}
.
If
\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}
was the beginning of the initial pipeline,
then the filtering condition
\varphi
may now take advantage of indexes declared over the source collection.
If not, then this filter may be propagated further upstream, by applying the operations of this table inductively.
A specific case of this transformation is when the whole Boolean expression of the match stage satisfies the pre-condition
(or equivalently when
\psi=\mathtt{true}
).
In this case, the match and unwind stages fully commute i.e.
\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi}
can be rewritten
\mathsf{ma}_{\varphi}\triangleright\mathsf{uw}_{p}
.

We emphasize that the preconditions listed in this table (as well as in the following sections) are sufficient for the equivalence to hold, but not necessary.
For instance, in this example,
there may be
q,p,\varphi
and
\psi
such that

q\triangleright\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\varphi\land\psi}\equiv q\triangleright\mathsf{ma}_{\varphi}\triangleright\mathsf{uw}_{p}\triangleright\mathsf{ma}_{\psi}

even though the pre-condition
(
p\text{ is compatible with }\mathsf{paths}(\varphi)
)
is not met.
Deciding whether two consecutive stages can permute within a query is in general complex (the problem is intractable for most types of stages),
and may require analysing the whole query.
Instead, our objective here is to provide simple pre-conditions that can be verified locally (focusing on two stages only) and efficiently:
all these conditions can be verified in
O(n\log n)
, and this also holds in the following sections.

6.3
Unwind

It is usually preferable to unnest arrays as late as possible during the execution of a query,
so as to limit the size of intermediate collections.
Accordingly, Figure

provides transformations that postpone an unwind stage.

Note that at first sight,
the third row (swapping project with unwind)
seems to cancel out a transformation listed in the previous section (swapping unwind with project).
But this is not a contradiction: within a more general optimisation procedure, both transformations may be useful.
For instance, one may optimize a query by first pushing all project stages downstream (iteratively, until none can be),
then all unwind stages downstream, and then all match stages upstream.

6.5
Lookup

The case of the lookup stage is more nuanced.
Two possibly conflicting optimisation strategies may apply:

1.

Postponing the execution of a lookup stage is likely to reduce the size of intermediate query results.

2.

However, a lookup executed as the very first operation of a pipeline can benefit from indexes declared over a source collection.

So if a query contains a lookup stage, one may first attempt to move it upstream, to see if it can be executed as the very first operation.
And if not, then try to postpone it instead.
For this reason, Figure
8
provides transformations that allow stages to permute with lookup in both directions.

A.2
Natural Order

In this section, we instantiate the natural order
\leq
over the universe
\mathcal{V}
of d-values,
which was left underspecified in the main body of this report.
This order comes in two flavours, one for the ordered semantics, and one for the unordered semantics.
The former is meant to comply with the order defined in the MongoDB documentation (unless stated explicitly).
And the latter is an adaptation of the former, with minimal modifications to accommodate unordered objects.

A.2.1
Ordering Literals

Our set
\mathcal{L}
of literals is an abstraction.
In practice, a literal has a datatype (e.g. int, long, string or Boolean).
MongoDB’s datatypes are called
BSON types
,
and the documentation of BSON types specifies how these literals are naturally ordered.
For instance, strings are ordered lexicographically (as expected), and numbers are ordered in the natural way.
In addition, the BSON specification indicates how these orders extend to literals of seemingly incompatible types.
For instance, a number always precedes a string.

When it comes to
MQueries
, we only assume some (underspecified) natural order
\leq
over
\mathcal{L}
,
the only requirement being that
\leq
is indeed a total order (i.e. a total, reflexive, transitive and antisymmetric binary relation over
\mathcal{L}
).

A.2.2
Ordering Arrays and Objects

The natural order
\leq
over the set
\mathcal{L}
of literals can be lifted to the universe
\mathcal{V}
of all d-values.
To do so, we assume that the universe
\mathcal{K}
of keys is also equipped with a total order
\preceq_{\mathcal{K}}
.
We extend
\leq
to a total order over
\mathcal{V}
inductively,
as follows:

Across types.

If
l\in\mathcal{L}
,
o\in\mathcal{O}
and
a\in\mathcal{A}
,
then
l<o<a
.

Arrays.

\mathcal{A}
is ordered lexicographically: if
a,a^{\prime}\in\mathcal{A}
, then
a<a^{\prime}
iff either

•

a[k]<a^{\prime}[k]
, where
k
is the least index such that
a[k]\neq a^{\prime}[k]
, or

•

a
is a strict prefix of
a^{\prime}
, i.e. if
a
has length
n
, then
a^{\prime}
has length at least
n+1
and
a[i]=a^{\prime}[i]
for
i\in\{0,\ldots,n-1\}
.

Objects.

We first lift the order
\leq
to the set
\mathcal{K}\times\mathcal{V}
of key/d-value pairs,
according to the behavior of MongoDB.
Precisely,

\displaystyle(k_{1},v_{1})<(k_{2},v_{2})\text{ iff either }

\displaystyle v_{1}\text{ and }v_{2}\text{ have different types }\text{ (e.g. }v_{1}\in\mathcal{L}\text{ and }v_{2}\in\mathcal{O})\text{ and }v_{1}<v_{2},\text{ or }

\displaystyle v_{1}\text{ and }v_{2}\text{ have the same type and either }

\displaystyle\qquad k_{1}\prec_{K}k_{2},\text{ or }

\displaystyle\qquad k_{1}=_{K}k_{2}\text{ and }v_{1}<v_{2}.

Then we lift this order over
\mathcal{K}\times\mathcal{V}
to an order over
\mathcal{O}
, for each of the two semantics:

•

Under the ordered semantics (where a object is an
sequence
of key/d-value pairs),

\mathcal{O}
is ordered lexicographically, analogously to
\mathcal{A}
.

•

Under the ordered semantics (where a object is a
set
of key/d-value pairs),
when comparing two objects,
we simply compare their sorted version (under the ordered semantics).
Precisely, if
o
is an object under the unordered semantics,
let
\mathsf{sorted}(o)
denote the sorted version of
o
,
i.e. the sequence that consists of the same key/d-value pairs as
o
,
sorted according to
\leq
.
Then for
o_{1}
and
o_{2}\in\mathcal{O}
,

\displaystyle o_{1}

\displaystyle\leq o_{2}\text{ under the unordered semantics iff }

\displaystyle\mathsf{sorted}(o_{1})

\displaystyle\leq\mathsf{sorted}(o_{2})\text{ under the unordered semantics. }

A.3
Set of Paths in a Term

We lift the notation
p_{1}.p_{2}
(for paths) to a set of path on the RHS, i.e.:

p.P=\{p.p^{\prime}\mid p^{\prime}\in P\}

for a path
p
and set
P
of paths.

We can now define the set
\mathsf{paths}(\tau)
of paths in a term
\tau
, by induction on the structure of
\tau
:

•

\mathsf{paths}(\lfloor\!\,\tau_{1},\dots,\tau_{m}\rfloor)=\bigcup_{i=1}^{m}\mathsf{paths}(\tau_{i})

•

\mathsf{paths}(\langle k_{1}\mapsto\tau_{1},\dots,k_{m}\mapsto\tau_{m}\rangle)=\bigcup_{i=1}^{m}k_{i}.\mathsf{paths}(\tau_{i})

•

\mathsf{paths}(f(\tau))=\mathsf{paths}(\tau)

•

\mathsf{paths}({\varphi}?\,{\tau_{1}}{:}\,{\tau_{2}})=\mathsf{paths}(\varphi)\cup\mathsf{paths}(\tau_{1})\cup\mathsf{paths}(\tau_{2})

•

\mathsf{paths}(\mathsf{map}({p},\>\lambda{x}\colon{\tau}))=\{p.p^{\prime}\mid p^{\prime}\in\mathsf{paths}(\tau)\}

•

\mathsf{paths}(\mathsf{filter}({p},\>\lambda{x}\colon{\varphi}))=\{p.p^{\prime}\mid p^{\prime}\in\mathsf{paths}(\varphi)\}

And similarly, we define
\mathsf{paths}(\varphi)
for a Boolean expression
\varphi
:

•

\mathsf{paths}(p)=\{p\}

•

\mathsf{paths}(\exists p)=\{p\}

•

\mathsf{paths}(\tau_{1}\mathop{\mathsf{op}}\tau_{2})=\mathsf{paths}(\tau_{1})\cup\mathsf{paths}(\tau_{2})\text{ for }\mathop{\mathsf{op}}\in\{=,\leq,\in\}

•

\mathsf{paths}(\neg\varphi)=\mathsf{paths}(\varphi)

•

\mathsf{paths}(\varphi_{1}\land\varphi_{2})=\mathsf{paths}(\varphi_{1})\cup\mathsf{paths}(\varphi_{2})
