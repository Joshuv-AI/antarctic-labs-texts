TD-Orch: Scalable Load-Balancing for Distributed Systems with Applications to Graph Processing Conference: ACM SIGPLAN Annual Symposium on Principles and Practice of Parallel Programming; January 31–February 04, 2026; Sydney, Australia
Yiwei Zhao, Qiushi Lin, Hongbo Kang, Guy E. Blelloch, Laxman Dhulipala, Charles McGuffey, Phillip B. Gibbons

Abstract
. In this paper, we highlight a task-data orchestration abstraction that supports a range of distributed applications, including graph processing and key-value stores. Given a batch of tasks each requesting one or more data items, where both tasks and data are distributed across multiple machines, each task must get co-located with its target data (by moving tasks and/or data) and executed. We present TD-Orch, an efficient and scalable orchestration framework featuring a simple application developer interface. TD-Orch employs a distributed push-pull technique, leveraging the bidirectional flow of both tasks and data to achieve scalable load balance across machines even under highly skewed data requests (data hot spots), with minimal communication overhead. Experimental results show that TD-Orch achieves up to 2.7 × 2.7\times speedup over existing distributed scheduling baselines. Building on TD-Orch, we present TDO-GP, a distributed graph processing system for general graph problems, demonstrating the effectiveness of the underlying framework. We design three families of implementation techniques to fully leverage the execution flow provided by TD-Orch. Experimental results show that TDO-GP achieves an average speedup of 4.1 × 4.1\times over the best prior open-source distributed graph systems for general graph processing.

Providing such a task-data orchestration framework is challenging.

A key difficulty lies in achieving load balance in both communication and computation while keeping overhead low, thereby maximizing resource utilization and throughput.
Each task requires all its data to be co-located on the same machine, by migrating the task and/or the data.
Data targeted by many machines in a batch can become
contention hot spots
that violate load balance.

In this paper, we propose
TD-Orch
, an orchestration framework that supports Fig.
1

Our key technique is
distributed push-pull
, which exploits the bidirectional movement of pushing tasks to data and pulling data to tasks—unlike most prior approaches that only push or pull.
But judicious use of push and pull alone does not solve the hot spot problem, since neither pushing tasks to a machine holding hot data nor pulling the data to the tasks can avoid the high communication to/from that machine.
Instead, TD-Orch detects hot data in each batch and employs novel (i) randomly-mapped reduction/broadcast
communication trees
and (ii) merge-able spillover
meta-task
structures.
Together, these ensure (a) for low contention data items, requesting tasks’ contexts can be pushed directly to where the item resides (no tree hops), (b) for high contention data items, the set of machines needing the item are stored in a communication-bounded way,
and (c) load balance and minimal communication overhead are achieved.

2.
The Task-Data Orchestration Problem

In this section, we introduce an orchestration framework,
TD-Orch
, which aligns with the API in
Figure

1
.
It yields optimal computation and communication costs while achieving scalable load balance.
We will show that our design outperforms three prior methods for distributed load-balancing both in theory and in practice.

2.1.
Problem Definition

In our abstract task-data orchestration problem for distributed-memory systems, there are
P
machines, a batch of
n
tasks to be executed on these machines, and data to be accessed by the tasks.
The tasks are executed in
stages
and each task has a local context holder to store intermediate results.
Data are partitioned into constant-sized
data chunks
.
At the beginning of each stage, the tasks and the data chunks are evenly divided among the machines.

Each task requires accessing
O(1)
data chunks (could be zero) that are stored outside its local context, and the task can be completed only after all the required data chunks are accessed.
Each data chunk may be required by 0 to
n
tasks.

We allow for both tasks and data chunks to be moved between machines, and even routed through intermediate machines.
Each movement of a task or a data chunk between two machines incurs a
communication
cost charged to both the sending and receiving machines.
Executing a task incurs a
computation work
cost charged to the machine it executes on.
Our goal is to
orchestrate
the tasks and data, i.e., to find an online computation scheduling and communication scheme that enables the stage to complete, such that the communication and computation work costs are (i) low and (ii) load-balanced across the machines.

Load Balance.

A key challenge in achieving load balance across the machines is the contention for the data chunks, since up to
n
tasks may require the same data chunk.
We seek task orchestration that is highly effective in practice and also with formal guarantees on its effectiveness regardless of the degree of data chunk contention.
For the latter, we define the following goal:

Definition 1 (Load-Balanced Stage).

A stage of tasks with total computation work
W
and total communication
I
is

(asymptotically) load-balanced

iff each of the
P
machines incurs
O(W/P)
computation work and
O(I/P)
communication cost.

2.2.
Prior Scheduling Strategies

Direct Pull.

A naïve scheduling strategy would first eliminate duplicate requests for data chunks within each machine and then fetch all required data chunks to the corresponding tasks.
This approach, commonly used in single-machine von Neumann architectures, is effective when the contention on each data chunk is low.
However, data chunk contention can be high (e.g., in graph processing, where the contention may correspond to the degree of a vertex), resulting in high communication cost for machines holding “hot” data chunks and hence severe communication load imbalance.

Direct Push.

Another common strategy in distributed settings is to offload each task to the machine that stores its required data chunks.
However, machines holding “hot” data chunks incur high communication cost (for receiving the tasks) and high computation work (for executing the tasks it receives), resulting in severe load imbalance. Moreover, the
O(1)
data chunks required by a task may be spread across multiple machines, in which case there is no one machine holding all its required data chunks.

Sorting-based.

Prior work on the Massively Parallel Computing (MPC) model
(
36
)
has proposed theoretically-efficient solutions to the orchestration problem (e.g.,
(
36
;
31
)
).
The procedure begins by sorting tasks according to the addresses of their required data chunks.
Then, MPC broadcasting
(
28
)
is used to distribute each data chunk to the corresponding tasks.
After task execution, a reverse broadcasting step writes the results back to the data chunks, followed by a reverse sorting step that restores tasks to their original order.
It has been shown that the computation work is load balanced, and the communication cost per machine is
\Theta(\frac{n}{p}\log_{\frac{n}{P}}{P})

(
25
)
, which is optimal
(
61
)
.
(Note that sorting is used here solely for grouping tasks by their requested data, and hence semi-sorting would suffice.)

Although these MPC schemes are asymptotically optimal, we will show below (
Section

2.5
) that
the constant factors are non-negligible in practice.

2.3.
TD-Orch

To address the challenges of direct push or pull, we must handle potential contention.
Our method,
TD-Orch
, exploits the two directions of data flow:
push
, where (the context of) a task is sent to the machine(s) storing its required data chunks, and
pull
, where data chunks are fetched to the machine where the task resides.
Such bidirectional strategies (referred to as
distributed push-pull
) are rarely emphasized in prior work.
Only a few prior works demonstrate that this strategy can significantly improve load balance, but they are limited to PIM settings
(
39
;
40
;
81
)
and rely on an extremely powerful centralized coordinator (the host CPU).
Our goal is to develop a more widely applicable push-pull technique that does not require a centralized coordinator.

Ideally, when contention information is available on any machine on the fly, distributed push-pull merges redundant information on one side (task/data) and dynamically chooses the flow direction toward the contended end.
This dynamic decision should balance load with low communication.

Orchestration Algorithm.

TD-Orch unifies information collection and push within a single substage, where the task locations for pull are also decided.
Bounded-size messages are enabled for dynamic decisions, even when machines lack direct visibility into remote states.
Its main algorithm to enable load-balanced task-data orchestration consists of the following four substages in each stage:

(1)

Contention Detection
: The information of each task is sent to the machine storing the target data, along a communication forest (§
2.3.1
) from leaves to root.
Contention information on each data chunk is collected during this substage, in the form of a meta-task (§
2.3.2
).

(2)

Task-Data Co-location
: A meta-task inherently provides a highly-compressed tree for communication. Data copies are broadcast along this tree from root to leaves. (See §
2.3.3
.)

(3)

Task Execution
: Now that all tasks and the copies of their target data are co-located on the same machine, the tasks are executed locally.

(4)

Data Write-backs
: The updated value for any data modified by an executing task is written back to the original data location. (See §
2.3.4
.)

2.3.1.
Communication Forest

During contention detection, load balance must be preserved even before the system identifies contention.
This requires that each machine only sends or receives bounded-size information, while avoiding excessive communication or round overhead caused by these bounded sizes.
To meet these requirements, TD-Orch adopts a tree/forest organization of machines for load-balanced communication, inspired by MPC broadcast trees
(
28
)
.

A
communication tree
rooted at machine
i
is a balanced
F
-ary tree with
P
leaves, as illustrated in
Figure

2
.
Each of the
P
leaf nodes represents a different physical machine, while the internal nodes correspond to virtual transit nodes, each of which is mapped to one of the
P
machines via a hash function.
Notably, a physical machine can simultaneously serve as both a leaf and an internal node.
The hash function is globally known to all machines.

.

A
communication forest
is defined as a set of
P
communication trees, each rooted at a distinct machine.
This structure enables efficient collection of task-related information (such as counting task occurrences) across a batch with near-optimal performance.
For each task whose data resides on physical machine
i
, the current machine sends a packed message–containing the data chunk address and the task information–to its parent in the communication tree rooted at
i
.
In successive communication rounds, each parent merges the information received from its children and forwards the aggregated result to its own parent in the forest.
The stage completes when all information reach their respective roots, requiring
O(\log_{F}{P})
rounds in total.

2.3.2.
Meta-Task

Two additional goals are desirable within the same contention-detection substage.

(
i
)
Task contexts without contention should be directly pushed to their data locations, avoiding the need for an extra round.

(
ii
)
For data items with contended accesses, the system should also identify where the data must be pulled in the next substage (i.e., the locations of the contending tasks).

To meet these goals, we introduce an auxiliary structure called a
meta-task
.
Meta-tasks are bounded in size to satisfy load-balance requirements.
They carry uncontended tasks as they move between machines but exclude contended ones.
In addition, their inherent tree structure naturally guides the broadcast routes for data in the subsequent pull substage.

As illustrated in
Figure

3
, a meta-task is composed of an integer level
l
(denoted by
L_{l}
) and data contents with constant word-sizes.
Each
L_{0}
meta-task corresponds to a task in the batch and its data content holds all the local context of the task.
For
L_{l}
meta-tasks with
l\geq 1
, the data content is a physical address pointing to the memory address of some machine where a set of
L_{l-1}
meta-tasks are stored.

A
meta-task set
with chunk size
C
, as shown in
Figure

3
, is a set structure containing meta-tasks.
The number of meta-tasks inside with the same level should not exceed
C
.

A
merge
operation of two meta-task sets is supported.
A new meta-task set with chunk size
C
is generated, containing all meta-tasks in both of the original sets.
If the number of meta-tasks with certain level
l
in the new set exceeds
C
, all
L_{l}
meta-tasks will be popped out of the new set and stored locally on the current machine, and then
a new
L_{l+1}
meta-task will be pushed into the set, whose data content contains a physical pointer to where these
L_{l}
meta-tasks are stored.
The merge will execute this process from the lowest level up to highest level, until the number of meta-tasks at each level is at most
C
.
An example of merging two sets with chunk size
C=3
is illustrated in
Figure

4
.

This merging guarantees that meta-task sets remain bounded in size.
Moreover, employing multiple layers of merging ensures that broadcasting in the subsequent pull substage incurs bounded communication per machine, preventing single data from needing to broadcast to numerous children
In short, the meta-task hierarchy creates a compressed, communication-efficient broadcast/reduction tree such that (unlike
Figure

2
) the height and size of the tree adapts to the precise amount of data contention.

2.3.3.
Distributed Push-Pull

Using meta-tasks allow us to send both the counts of tasks that need particular data and implicit information about which set of machines possess such tasks over the communication forest.
During the preprocessing, each task is wrapped in an
L_{0}
meta-task, and meta-task sets are constructed for those tasks accessing the same data chunk.
In each communication round the constructed meta-task set is sent in the message in addition to the counts of the tasks.
After receiving messages in each round, each parent node merges both the task counts and the meta-task sets.
Each machine that stores a data chunk will receive the final meta-task sets and implicitly knows where these tasks are stored.

Since the size of each meta-task set is bounded (though not by constant words), the meta-task collection is still nearly perfectly load balanced.
Meanwhile, the hierarchical meta-task sets also provide an implicit tree spanning the subset of machines that possess related tasks, which we denote as the
subset tree
.
When fewer than
C
tasks target the same data chunk, these tasks are directly pushed to the corresponding machines.
If more than
C
tasks target the chunk, they must access the data copies via a broadcast over the subset tree.

2.3.4.
Write Backs

If tasks require write-backs that meet a special
merge-able
characteristic (defined in
2

Definition 2 (Merge-able Operations).

An operation
\oplus
is
merge-able
if there exist operations
\odot
and
\otimes

x
and
y_{i}(1\leq i\leq n)

x\oplus y_{1}\oplus...\oplus y_{n}=x\odot(y_{1}\otimes...\otimes y_{n})

Merge-able operations
\oplus
are commonly seen, including and not limited to (i) idempotent operations (
\odot
is
\oplus
and
\otimes
is keeping one left), (ii) set-associative operations (
\odot
and
\otimes
are both
\oplus

\odot
is
write
and
\otimes
is
randomly select

\odot
is
write
and
\otimes
is finding the value to write using the decision process).

3.1.
Main Design

Ingestion-Time Orchestration of Task-Data Flow.

A distributed graph algorithm that can be expressed using
DistEdgeMap
can also be viewed as a task–data orchestration, whereas edges correspond to tasks and vertex intermediate values correspond to data.
A key observation is that, regardless of the starting vertex, in each
DistEdgeMap
, the contention for data (vertex value) access induced by tasks (edges) is proportional to the degree of each vertex.
Since vertex degrees are intrinsic to the structure of the graph, such contention is inevitable in all
DistEdgeMap
operations, regardless of the choice of starting vertex in an algorithm.

Given this observation, TD-Orch can be applied once as a preprocessing phase when the graph is ingested, which is sufficient to resolve all future skew in the execution of arbitrary
DistEdgeMap
operations.
This one-time load balancing is particularly beneficial for highly skewed graphs, such as commonly encountered power-law graphs
(
30
)
.

The preprocessing process consists of two stages.
In the first stage, we begin by randomly placing each edge on an arbitrary machine and then execute one round of TD-Orch, which attempts to colocate all edges with their source vertices.
Edges whose sources are low-degree vertices are now placed on the same machine.
For edges with high-degree sources, a tree structure of meta-tasks (denoted as
source trees
) is created to represent their source-side communication.
We then fix the storage location of these edges and propagate future source-vertex values through the source trees.
In the second stage, another round of TD-Orch is performed, where a task is assigned to each edge to reach its destination vertices.

This again results in a tree structure of meta-tasks (denoted as
destination trees
), this time representing the paths along which the
write\_back
values to the destination vertices will be sent in a
DistEdgeMap
.

Adopting such a preprocessing provides two key benefits:

(
i
)
it organizes edge storage into chunks, ensuring balanced computation load; and

(
ii
)
it establishes a tree-shaped communication framework for both
get_value
and
write_back
, ensuring balanced communication with reduced overhead.

Sparse-Dense Execution.

Ligra
(
65
)
and GBBS
(
22
)
introduces single-machine sparse-dense execution.
We design a new dual-mode execution flow for distributed graph processing which can switch between
sparse
and
dense
execution modes to efficiently exploit the data layouts provided by TD-Orch.

The mode is determined by the size of the current
DistVertexSubset
.
Specifically, the
sparse
mode is optimized for small
DistVertexSubset
, while the
dense
mode is optimized for large ones.

In the
sparse
mode, a vertex-centric execution flow is used: each active vertex
u\in U
propagates its value down the source tree, activating all corresponding edges.
The result values are then sent and merged along the destination tree.

In contrast, the
dense
mode uses an edge-centric execution flow.
All active vertices
u\in U
broadcast their values to all machines.
Each edge
(u,v)
is then executed if
u\in U
.

The choice between sparse and dense mode is dynamically determined by the size of the active frontier in the current round.
Specifically, if
\Sigma_{u\in{U}}deg(u)=o(P\cdot|U|)
where
d(\cdot)
denotes the out-degree of inter-machine edges, the sparse mode is used; otherwise, the dense mode is employed.

This dynamic switching ensures that the execution remains both work- and communication-efficient in theory (with work and communication of
O(\Sigma_{u\in{U}}deg(u))
as in Ligra and load-balanced due to the use of TD-Orch), while also achieving high performance in practice.

3.2.
Implementation Techniques

In TDO-GP, we employ several implementation techniques, which can be grouped into three categories.
Due to space limit, we summarize only the key functionalities of each group here.
Detailed descriptions are provided in

3.2.1.
Optimized Global Communication

We adopt deduplication and destination-aware broadcasting to reduce inter-machine communication, alleviating this critical bottleneck.

3.2.2.
Work-Efficient Local Computation

Our design leverages ParlayLib
(
10
)
, a state-of-the-art parallel library, to implement work-efficient computations.
We enhance

with a concurrent hash table and a concurrent bitmap, and we further develop a lightweight implementation of local
EdgeMap

Moreover,

accepts an optional
filter_dst
function, excluding vertices that are guaranteed not to be destinations in the current round.

3.2.3.
Aligned Coordination between Components

We design tighter coordination between system components—between threads and scheduler, among threads to prevent cache thrashing, and between local and global execution.

We further conduct a single-machine experiment on a more powerful server with superior NUMA interconnects.

Conclusion

In this paper, we introduce an abstraction of the task–data orchestration problem, unifying a range of distributed applications.
We design TD-Orch to realize this orchestration with scalable load balance and low communication.
Building on TD-Orch, we develop TDO-GP, a distributed graph processing system enhanced with implementation techniques for graph workloads.
Both TD-Orch and TDO-GP are theoretically grounded and achieve high practical performance.

Appendix A
Models for Distributed Computing

In this paper, we model and analyze algorithms using the classic
Bulk-Synchronous Parallel (BSP) model
(
71
;
70
;
72
)
.
The BSP consists of
P
machines, each with a sequential processing element (PE) and a local memory.
There is no shared global memory.
All machines are connected by a point-to-point communication network.
All remote accesses to data on other machines are carried out via messages sent over this network.
The system operates in bulk-synchronous rounds (
supersteps
), where periodic barrier synchronizations separate periods of asynchronous computation and communication.

Cost Metrics.

The BSP model defines the notion of an
h
-relation of a superstep, which combines the maximum computation work, maximum communication amount and synchronization time over all machines.
Due to using
maximum
when defining
h
-relations, load balance is critical for achieving good performance.
In all our analysis, for clarity, we decouple the
computation time
and
communication time
, and do not consider the BSP parameters
g
and
L
in
(
71
;
27
)
.
Computation time
t
and communication time
h
can be combined into a formal BSP result
\Theta(gh+t)
as long as the synchronization overhead can be hidden by system communication, i.e.,
(gh+t)\in\Omega(L)
.

Other Distributed Models.

The Massively Parallel Model of Computation (MPC)
(
36
;
42
;
31
;
8
;
3
)
family of models regards synchronization as the main bottleneck in distributed systems and takes
communication rounds
as the only optimization target.
We choose the the BSP model because it differs from MPC in two ways:

(
i
)
The the BSP model accounts for the total communication among machines rather than ignoring the amount of communication in each round.

(
ii
)
The the BSP model also considers computation costs neglected by the MPC model, which turn out to be critical for real-world system designs on emerging distributed hardware
(
39
;
9
)
other than MapReduce systems
(
20
)
.

LOCAL/CONGEST models
(
49
;
50
)
are a popular model family for distributed systems.
Like the models we consider, each machine has only a local view of the computation.
These models consider network topology, which we ignore in the BSP model.
However, they have similar weaknesses to the MPC model with regards to their metrics: (i) each machine can send/receive up to its maximum allowed communication at each round, whereas we seek to minimize communication, and (ii) computation costs are not considered.

The Processing-in-Memory (PIM) model
(
38
)
is a recently proposed model for emerging compute-in-memory hardware
(
58
)
.
The model has a powerful Host CPU and
P
PIM nodes, each comprised of a PE and a memory.
It operates in bulk-synchronous rounds, but unlike the BSP model, all communication must be sent by or to the Host CPU.
Furthermore, the model decouples the computation time of the CPU from other processors, resulting in a lack of analysis of load-balance between them.

Placing weighted balls with total weight

Appendix E
Details for Implementation Techniques

We present here the implementation techniques used in our graph processing system, which efficiently exploit the data layout and execution flow provided by TD-Orch, leading to the strong performance demonstrated in
Section

4
.

E.1.
Optimized Global Communication

As we will show in
Section

4.4
, the critical bottleneck in a distributed graph system is the inter-machine communication time.
Optimizing global communication is therefore essential.
First, we apply deduplication during message passing along the meta-task trees, aggressively merging all repeated items.
Second, in dense mode, we reduce broadcast traffic by sending the values of each vertex only to the machines that store its corresponding edges.
The mapping of vertices to machines is established during the preprocessing phase.

E.2.
Work-Efficient Local Computation

For all local computations in our implementation, we employ work-efficient designs that are both theoretically optimal and practically fast.
Our design leverages ParlayLib
(
10
)
, a state-of-the-art C++ parallel library providing a wide range of work-efficient parallel algorithms as primitives.

The
DistVertexSubset
structure consists of a collection of
VertexSubset
instances, one per machine, where each
VertexSubset
can independently switch between two representation formats introduced in Ligra
(
65
)
.
We introduce two implementation improvements.

(
i
)
In the sparse representation, we replace their array of vertices with a phase-concurrent hash table with adaptive sizing, enabling more efficient lookups within
VertexSubset
.

(
ii
)
In the dense representation, we replace the original parallel C++ Boolean-map with a concurrent bitmap, improving cache efficiency.

For local edges whose source and destination vertices reside on the same machine, we bypass the global orchestration framework and instead execute a local
EdgeMap
.
We implement a lightweight
EdgeMap
entirely using ParlayLib primitives, which, as we show in
Section

4.5
, is more efficient than the ones in Ligra/GBBS for
EdgeMap
workloads.

Additionally, we allow users to provide an optional input function
filter_dst
to
DistEdgeMap
to accelerate execution by filtering out vertices that are guaranteed not to be destination vertices in the current round.
Disabling
filter_dst
does not affect correctness but may reduce efficiency.

E.3.
Aligned Coordination between Components

A distributed graph processing system involves multiple software components running across diverse hardware resources.
Ensuring a coordinated execution schema among these components is crucial.
Our implementation optimizes this coordination to achieve aligned and efficient execution.

For better alignment with the parallel thread scheduler in ParlayLib, we avoid using nested
ParallelFor
, which is commonly seen in graph algorithms but inefficient under such schedulers.
Instead, we adopt
Flattern
, assisted by
delayed
structures
(
10
)
, to transform two-dimensional nested parallelism into one-dimensional parallelism.

To better align local execution across threads and minimize cache thrashing, we design concurrent counters and other shared concurrent structures with sizes padded to a multiple of the cache-line size.
This padding prevents false sharing, ensuring that accesses from different cores do not contend on the same cache line.

We also align local computation with the load-balanced data layout across machines.
We initialize the graph with a vertex-value layout such that the total number of outgoing edges (out-degrees) assigned to each machine is approximately equal.
This ensures that most local computations are naturally load-balanced across machines, since each handles a comparable number of edges.
