Assessing Coherency and Consistency of Code Execution Reasoning by Large Language Models
Changshu Liu, Yang Chen, Reyhaneh Jabbarvand University of Illinois, Urbana-Champaign {cl144,yangc9,reyhaneh}@illinois.edu

Abstract
. This paper proposes CES , a task to evaluate the abilities of LLMs in simulating program execution and using that reasoning in programming tasks . Besides measuring the correctness of variable predictions during execution simulation, CES introduces the notion of coherence to determine whether the simulation complies with commonsense execution logic, even if the predicted values along the simulations are incorrect. This enables CES to rule out suspiciously correct output predictions due to reasoning shortcuts, hallucinations, or potential data leakage. CES also introduces a novel metric to measure reasoning consistency across tests with the same or different prime path coverage in a spectrum: strong , weak , and random . Evaluating 16 16 LLMs (including three reasoning LLMs) using CES indicates 81.42 % 81.42\% coherent execution simulation on HumanEval , 46.92 % 46.92\% and 53.08 % 53.08\% of which result in correct and incorrect output predictions. Frontier LLMs such as GPT-4 and DeepSeek-R1 have the most incoherent execution reasoning, mostly due to natural language shortcuts. Despite relatively coherent execution simulation, LLMs’ reasoning performance across different tests is inconsistent, mostly random ( 48.87 % 48.87\% ) or weak ( 45.37 % 45.37\% ), potentially explaining their weakness in programming tasks that require path-sensitive program analysis to succeed. We also compare CES with bug prediction/localization/repair, which intuitively requires control- and data-flow awareness. We observe that LLMs barely incorporate execution reasoning into their analysis for bug-related tasks, and their success is primarily due to inherent abilities in pattern matching or natural language shortcuts, if not data leakage. Without reasoning, there is a threat to the generalizability of LLMs in dealing with unseen bugs or patterns in different contexts. CES can be used to vet the suspicious success of LLMs in these tasks systematically.



1.
Introduction

Large Language Models (LLMs) have shown emerging abilities in code/test synthesis, code completion, bug/vulnerability detection, code translation, and program repair. The extent to which they can reason about different code aspects is still under investigation.

Reasoning Consistency.
Prior techniques evaluate the reasoning of LLMs per single test, failing to study the consistency of reasoning across multiple tests with different or same coverage. 3.
Code Execution Simulation (
CES
)

A program is a set of statements for variable definition or assignment, introducing recursions to the logic (e.g., loops), introducing branches in the control flow (e.g., method calls, threading, conditional, and exception handling statements), or terminating the execution.
CES
evaluates correctness of execution simulation in looping (
S_{loop}
), branching (
S_{branch}
), and returning (
S_{return}
) statements. The rationale is two-fold: (1) asking a model to predict all intermediate variable values can make the task complex, preventing proper responses and fair evaluation
(
Liu et al. 2024a
)
; (2) these statements identify the start or end of basic blocks, thereby capturing mispredictions in the assignment statements inside the block. We first formally define assessment properties (§
3.1
) and then explain how
CES
prompts models and evaluates these properties (§
3.2
).

4.
Reasoning Coherency

CES
considers execution simulations not compliant with common-sense execution logic as incoherent reasoning cases and marks anything else as coherent reasoning. It implements three coherency rules and
checks the model’s response for violations of
them.

\bullet

Rule 1.
Combining the sub-property predictions using code logic should match the compound property prediction.
That is, for a compound property
X_{y_{j}}
with
z
sub-properties, if the program is executed with predicted sub-property values
X_{y_{j_{w}}}(1\leq w\leq z)
by LLM, the value of
X_{y_{j}}
from execution should match that of prediction.
CES
can automatically instrument the code with predicted sub-property values, generating an Instrumented Program (IP), executing that, and investigating the violation of Rule 1
:

(2)

\begin{split}\exists\;j,X_{y_{j}}\in\left(\{I_{l_{j}}\}_{j=0}^{m}\cup\{P_{c_{j}}\}_{j=0}^{n}\cup\{O_{r_{j}}\}_{j=0}^{k}\right)\;\text{s.t.}\hskip 9.24994pt\hskip 9.24994pt\\
CES(P,I,X_{y_{j}})\neq IP\bigl(CES(P,I,X_{y_{j_{1}}}),\ldots,CES(P,I,X_{y_{j_{z}}})\bigr)\end{split}

Coherency concerning this rule does not imply correct prediction of all properties through simulation, but proper propagation of incorrect state. In Figure
1
-c, GPT-4 mispredicts values of
odds
variable. However, the predicted value of
zip(evens,odds)
properly combines the mispredicted value of
odds
and correctly predicted value of
evens
. Hence, the reasoning is coherent.

\bullet

Rule 2.
For a conditional statement, inconsistent conditional predicates and branch predictions demonstrate reasoning incoherence. This rule, again, is checked regardless of the ground truth values, since a mismatch between predicate values and branch decisions never happens in a real execution.
CES
detects such cases as follows:

(3)

\underset{0\leq j\leq n}{\exists}\;c_{j}\;\;\text{s.t.}\;\;CES(P,I,P_{c_{j}})\;\neq\;CES(P,I,B_{c_{j}})

\bullet

Rule 3.
The most important case of reasoning incoherence is when the output is correctly predicted, but the prediction of
at least
one of any other properties during simulation is incorrect. The illustrative example in Figure
2
shows such a case, which never happens in the real execution of the program, as the incorrect program state will be propagated to the output. As we will show (§
6.2
), LLMs are susceptible to reasoning incoherency due to hallucination, CoT shortcuts, and potential data leakage.
CES
detects
violation of Rule 3
using the following formula:

(4)

\bigl(\underset{0\leq j\leq k}{\exists}\;j\;\text{s.t.}\;CES(P,I,O_{r_{j}})=1\bigr)\;\land\;\Bigl(\prod_{f=1}^{m+n}CES(P,I,X_{y_{f}})=0\Bigr)

where
X_{y_{f}}
belongs to
\{V_{i_{f}}\}_{f=0}^{m}\cup\{I_{l_{f}}\}_{f=0}^{m}\cup\{B_{c_{f}}\}_{f=0}^{n}\cup\{P_{c_{f}}\}_{f=0}^{n}
statements that appear
before

O_{r_{j}}
.
For compound properties, Formula
4
only considers the incorrect prediction of the property, regardless of sub-property predictions. This is because a misprediction at a coarser grain is more likely to propagate to the rest of the simulation. Any incoherence between sub-properties and compound property will be captured by Rule 1.

If any of the above cases happen,
CES
marks the execution simulation reasoning as incoherent. The incoherent reasoning cases, even if the output prediction is correct, will be discarded and won’t be considered as LLM success.

4.1.
Diagnosis

CES
offers two automated diagnostic analyses: identifying where the simulation diverges from ground truth (coherent reasoning followed by incorrect output prediction) and detecting suspiciously correct output predictions (correct output prediction achieved through incoherent reasoning).

When the reasoning is

1

5.
Reasoning Consistency

LLM-generated code should be comprehensively tested across all the execution paths in the program. Otherwise, one can falsely claim an incorrect code to be correct. Similarly, an LLM cannot claim victory on code execution reasoning until it can simulate all execution paths correctly.
CES
introduces the spectrum of reasoning consistency, considering the model’s
CES
performance across different execution paths.

Figure
5

considers

in the CFG to bound the number of execution paths. A prime path in a cyclic CFG is a maximal path between two arbitrary nodes that does not visit any node more than once, except for the start and end
(
Ammann and Offutt 2017
)
.
Prime paths not only bound the number of execution paths, but cover all CFG edges and execution sequences, enabling completeness of
CES
consistency analysis. The CFG in Figure

[1,2,3,4,5]

[1,2,3,6]

[4,5,3,6]

[4,5,3,4]
, and

.

Definition 4. Weak Consistency (

An LLM achieves a weak level of code execution reasoning consistency on program

(5)

\begin{split}WC\mathrel{:=}[\underset{1\leq z,q\leq g}{\exists}z\neq q\;\;cov_{z}=cov_{q}\;\land\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\\
\forall\;z\neq q\;\;\bigl(cov_{z}=cov_{q}\bigr)\Rightarrow\bigl(CES(P,i_{z},X_{y_{j}})=CES(P,i_{q},X_{y_{j}})=1\bigr)]\end{split}

The predicate

WC

Definition 5. Strong Consistency (

An LLM achieves a strong level of code execution reasoning consistency on program

different

(6)

\begin{split}SC\mathrel{:=}[\underset{1\leq z,q\leq g}{\exists}z\neq q\;\;cov_{z}\neq cov_{q}\;\land\hskip 8.50012pt\hskip 8.50012pt\hskip 8.50012pt\\

RQ4.
CES
and Bug-Related Tasks

Figure 8
.
Prompt template of bug-related tasks. ICL stands for in-context learning

LLMs should incorporate their knowledge of programming languages and examples they have seen to solve programming tasks. Otherwise, one cannot expect them to generalize to different tasks or perform reliably in real-world settings. Concerning programming tasks, specifically bug-related tasks, we expect them to predict, localize, or repair bugs based on program analysis. Assuming execution simulation as a required step for program analysis, we can define the following expectations: (1) if an LLM can correctly simulate an execution path, it is more likely to detect, localize, and repair a bug in that specific execution path. Similarly, (2) if a model cannot correctly simulate an execution path, it either fails in bug-related tasks or the success is based on other factors, e.g., pattern matching, reasoning shortcuts, hallucination, or data leakage.

To investigate whether LLMs meet these two expectations, we evaluated the subject LLMs with three prominent bug-related tasks: bug prediction, localization, and repair. For this experiment, we used HumanEvalPack
(
Muennighoff et al. 2023
)
, a buggy version of
HumanEval
with the bugs developed and injected by humans. The dataset comes with a set of regression and error-revealing tests.

We picked a model from each family and prompted them with the templates shown in Figure
8
-a–
8
-c. Similar to
CES
, the prompt instructs LLMs for individual tasks with in-context examples. For the bug prediction, the prompt provides one buggy and one correct example. For bug localization and prediction, we provide only the buggy example. Prompt templates also include natural language specification, i.e., program docstring, and error-revealing test. We instruct LLMs to explain the execution process of the program in the CoT. The rationale for this design decision is three-fold: (1) for the sake of fairness, we want the prompts between
CES
and these tasks to be similar; (2) we wanted to see if instructed, LLMs can incorporate simulation execution into decision-making; and (3) we can check the CoT for further analysis of the results. We also prompted selected LLMs for execution simulation of the error-revealing tests used in bug-related tasks.

Related Works

A large body of work has evaluated LLMs on reasoning tasks across modalities such as language, vision, math, and code
(
Deshpande et al. 2021
;
Wu et al. 2023
;
Miceli-Barone et al. 2023
;
Bubeck et al. 2023
;
Wang et al. 2023
;
Imani et al. 2023
;
Luo et al. 2023
;
Huang et al. 2023b
;
Valmeekam et al. 2022
;
Min et al. 2023
)
. Our work relates most closely to recent efforts on code reasoning, particularly code execution.
CruxEval
and
CodeMind
introduced early benchmarks for this area:
CruxEval
included input and output prediction tasks, while
CodeMind
proposed three tasks—independent execution, dependent execution, and specification reasoning—to assess inductive code reasoning.

REval
took one step forward to include the runtime behavior in the reasoning process using four runtime prediction tasks: code coverage prediction, program state prediction, execution path prediction, and output prediction. Given that these tasks are inherently connected and sequential but are prompted separately, they proposed to measure the consistency of the models in performing these tasks sequentially as an ultimate evaluation metric for code reasoning.
CocoNut

(
Beger and Dutta 2025
)
challenges LLMs to generate a trace of line numbers executed by the program for a given set of inputs, which requires LLMs to reason about the program’s control flow.

CES
complements prior code reasoning research activities with several novel contributions. It is the first technique that discusses a systematic and formal approach to determine reasoning issues such as hallucination and reasoning shortcuts.
CES
’s novel notion of consistency across tests offers an intuitive metric to challenge LLMs truly incorporating execution reasoning in decision-making. Finally, this paper is the first to study the relationship between code reasoning and other programming tasks, which provides valuable insights into how LLMs succeed in these tasks.

Threats to Validity

Figure 13
.
Comparison between
CES
and
REval

External Validity.

The first threat is whether our results can be generalized to other experimental settings (other models and benchmarks). To mitigate this threat, we selected LLMs of different sizes and training strategies, and our tool is publicly available to evaluate code execution simulation of LLMs across other benchmarks. As prior research suggests, we expect the LLMs’ code reasoning abilities to degrade as subjects become more complex, making it infeasible to draw meaningful conclusions from the results.

Internal Validity.

LLMs’ nondeterminism poses a threat to the internal validity of our results. To mitigate this threat, we repeated the experiments per program across multiple tests and evaluated the reasoning generalizability through a novel consistency metric. Our results may be affected by potential bugs in implementing the
CES
. To address this threat, we thoroughly tested the pipeline (prompting models and processing responses) and cross-checked the results for correctness.

Construct Validity.

One construct validity threat is the mismatch between the datasets used by
CES
and
REval
.
REval
only studied a subset of
HumanEval
(
85
out of
164
programs), while we evaluated LLMs in all the programs. For the common programs, the selection of tests was also not consistent. To mitigate this threat, in comparing the
REval
and
CES
, we recompute the incremental consistency of
REval
for the programs and test inputs that overlap with
CES
.

9.
Concluding Remarks

This paper proposes
CES
, a code execution reasoning task that unifies the prediction of output and essential decision points into one prompt. This unique design, along with adaptive in-context example selection based on static analysis of the program, enables
CES
to be flow-sensitive and diagnostic. The novel reasoning consistency metric across multiple tests can assess the reasoning abilities of models in a spectrum: strong, weak, or random. Our results show that LLMs, to a reasonable extent, can simulate program execution. However, their reasoning is mostly random or, at best, weak. Our artifacts are publicly available for reproducibility and extension
(
Authors 2024a
)
. We plan to use the
CES
for a large-scale evaluation of reasoning in real-world benchmarks such as SWE-Bench.
Enabling the
CES
for real-world projects requires non-trivial efforts to account for complex objects, making it beyond the scope of this paper.
