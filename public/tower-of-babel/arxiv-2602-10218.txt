ACE-RTL: When Agentic Context Evolution Meets RTL-Specialized LLMs
Chenhui Deng, Zhongzhi Yu, Guan-Ting Liu, Nathaniel Pinckney, Haoxing Ren *

Abstract
. Recent advances in large language models (LLMs) have sparked growing interest in applying them to hardware design automation, particularly for accurate RTL code generation. Prior efforts follow two largely independent paths: (i) training domain-adapted RTL models to internalize hardware semantics, (ii) developing agentic systems that leverage frontier generic LLMs guided by simulation feedback. However, these two paths exhibit complementary strengths and weaknesses. In this work, we present ACE-RTL that unifies both directions through Agentic Context Evolution (ACE). ACE-RTL integrates an RTL-specialized LLM, trained on a large-scale dataset of 1.7 million RTL samples, with a frontier reasoning LLM through three synergistic components: the generator, reflector, and coordinator. These components iteratively refine RTL code toward functional correctness. We further introduce a parallel scaling strategy that significantly reduces the number of iterations required to reach correct solutions. On the Comprehensive Verilog Design Problems (CVDP) benchmark, ACE-RTL achieves up to a 44.87 % 44.87\% pass rate improvement over 14 14 competitive baselines while requiring only four iterations on average.

1.
Introduction

Large language models (LLMs) have shown rapid progress in software development and are increasingly explored for hardware design automation
(
18
;
10
;
6
;
22
;
11
)
. As hardware systems continue to grow in scale and complexity, developing register-transfer-level (RTL) designs remains a labor-intensive and error-prone process requiring deep domain expertise. Leveraging LLMs to translate natural-language intent into functionally correct RTL code can significantly accelerate design cycles. Moreover, accurate RTL generation is essential for downstream workflows such as performance optimization and architectural design space exploration
(
37
;
36
;
33
)
.

In parallel to this motivation, the research community has pursued two main directions, as shown in Figures
1
(a) and
1
(b), for applying LLMs to RTL code generation.
(i)
The first focuses on developing domain-specialized LLMs trained on RTL data, where models are fine-tuned to internalize RTL syntax and hardware design semantics. For instance, RTLCoder
(
26
;
25
)
develops a specialized model fine-tuned on a dedicated Verilog dataset. CraftRTL
(
24
)
further enhances RTL coding capability by training on synthetic data that capture non-textual design representations. More recently, ScaleRTL
(
12
)
scales up post-training on a large RTL reasoning corpus, yielding a strong specialized model that achieves state-of-the-art (SoTA) results on mainstream RTL benchmarks.
(ii)
The second direction centers on agentic systems that leverage frontier generic LLMs together with RTL-specific tools such as simulators and waveform analyzers. Along this line, VerilogCoder
(
14
)
introduces a multi-agent framework based on GPT4-Turbo
(
28
)
that decomposes RTL design into fine-grained sub-tasks through a task-and-circuit relation graph and repairs functional errors using a waveform tracing tool. Similarly, MAGE
(
39
)
employs multiple Claude3.5-Sonnet
(
4
)
LLM agents tightly integrated with hardware-domain toolchains to produce functionally correct RTL code.

Despite these advances, the two research directions remain largely orthogonal and exhibit complementary limitations. Training-based approaches often yield RTL-specialized models with limited general capabilities such as long-context reasoning, multi-step planning, and instruction following, reducing their effectiveness on complex design tasks. Conversely, agent-based methods lack RTL-specific knowledge learned from large-scale hardware datasets, causing the system to struggle on problems that require deep hardware semantics and domain expertise. These limitations highlight the need for a unified framework that integrates an RTL-specialized model with a frontier general-purpose LLM, enabling the system to leverage the strengths of both paradigms.

In this work, we advance LLM-based RTL coding by synergizing the complementary strengths of an RTL-specialized model and a frontier general-purpose LLM. To this end, we propose ACE-RTL, which adopts the notion of Agentic Context Evolution (ACE) through three components: the Generator, the Reflector, and the Coordinator. As illustrated in Figure
2
(a), the Generator is an RTL-specialized LLM trained on 1.7 million diverse RTL samples. When the Generator produces buggy code, the Reflector, powered by the frontier LLM Claude4-Sonnet
(
5
)
, is invoked to analyze simulation feedback, trace errors back to faulty logic, and provide high-level fix guidance.
The Coordinator then incorporates this guidance into an incrementally evolving context that guides the Generator in the next iteration of code generation.
By iteratively cycling among the Generator, Reflector, and Coordinator, ACE-RTL effectively combines domain-specific RTL expertise with strong general-purpose reasoning to produce functionally correct RTL designs.
We further introduce a parallel scaling strategy that launches multiple ACE-RTL processes simultaneously and terminates the remaining ones once any process succeeds. This significantly reduces the total number of iterations needed to obtain correct RTL implementations.

To evaluate the efficacy of ACE-RTL, we compare it against the strongest frontier LLMs, as well as SoTA RTL-specialized models. More importantly, instead of relying on prior RTL benchmarks such as VerilogEval
(
23
;
30
)
and RTLLM
(
27
)
, which primarily consist of relatively simple specification-to-RTL generation tasks (e.g., small modules or textbook-style problems), we conduct evaluations on the Comprehensive Verilog Design Problems (CVDP) benchmark
(
31
)
. CVDP encompasses hundreds of diverse and challenging RTL coding tasks, including code completion, specification-to-RTL generation, code modification, and debugging. Since earlier benchmarks have become saturated and no longer sufficiently differentiate recent approaches, we argue that evaluating on CVDP provides a more rigorous and practical assessment of model capability and more convincingly demonstrates meaningful progress in this domain. We summarize our technical contributions as follows:

\bullet
To our knowledge, this work is the first to introduce the ACE framework for RTL coding,
which jointly leverages a frontier generic LLM and an RTL-specialized model.

\bullet
Motivated by data scaling laws, we construct a 1.7M-sample RTL dataset covering diverse coding problems. Trained on this corpus, our RTL-specialized model surpasses SoTA baselines, including GPT-5 and ScaleRTL, by up to
21.45\%
.

\bullet
By integrating the RTL-specialized model with the ACE framework, our proposed ACE-RTL achieves up to a
44.87\%
improvement in pass rate over all baselines on the CVDP benchmark, demonstrating the effectiveness of ACE for complex RTL tasks.

\bullet
With parallel scaling, ACE-RTL requires only four iterations on average to produce correct RTL code, achieving up to a
3.06\times
reduction in total iterations over the non-scaled version.

2.
Background

In this section, we review prior studies on RTL-specialized LLMs, agentic systems, and RTL benchmarking, which together establish the foundation and motivation for ACE-RTL.

2.1.
Domain-Adapted LLMs for RTL Tasks

Adapting LLMs for RTL coding via model training has attracted growing attention due to their potential to improve hardware design productivity.
RTLCoder
(
26
;
25
)
develops a GPT-assisted pipeline for automated RTL data synthesis, while CraftRTL
(
24
)
generates synthetic, correct-by-construction samples derived from design artifacts. OriGen
(
9
)
adopts compiler-guided reflection and augmentation to improve functional correctness. Recently,
ScaleRTL
(
12
)
scales both training data and test-time compute by fine-tuning on billions of RTL reasoning tokens and applying iterative reasoning extension, achieving SoTA results on VerilogEval
(
30
)
and RTLLM
(
27
)
benchmarks. These efforts collectively advance the development of RTL-specialized models. However, it remains unclear how to effectively integrate such models into an agentic system that can further push the frontier of LLM-based RTL coding.

2.2.
Agentic Systems and Context Evolution

Recent agentic systems such as VerilogCoder
(
14
)
and MAGE
(
39
)
have demonstrated the potential of multi-agent collaboration for RTL code generation. VerilogCoder decomposes RTL design into fine-grained subtasks using a Task and Circuit Relation Graph (TCRG) and employs a waveform-tracing debugger to locate functional errors, while MAGE leverages multiple specialized agents for RTL generation, testbench creation, and debugging through simulator-based feedback. Despite their promising results, both methods depend heavily on complex, tool-specific planning and lack an RTL-specialized model that captures broad hardware coding logic, which makes them difficult to generalize beyond predefined task structures.
In this work, we take a different perspective: we argue that the key role of an agentic system is to dynamically construct the right context to guide the RTL generator toward correct solutions. To this end, ACE-RTL iteratively evolves contextual information such as prior attempts and feedback to progressively steer an RTL-specialized model toward functional correctness.

2.3.
RTL Benchmarks for LLM Evaluation

Prior mainstream benchmarks such as VerilogEval and RTLLM mostly evaluate small, self-contained RTL problems, emphasizing short specification-to-RTL snippets rather than sustained reasoning over realistic design contexts. RTL-Repo
(
3
)
takes a step toward practical settings by introducing GitHub-derived projects and prompting models to complete redacted regions, yet it remains limited to code completion and omits broader challenges such as specification-to-RTL generation, code modification, or debugging. We argue that rigorous assessment requires benchmarks stressing both context length and task diversity. Therefore, this work focuses on evaluating RTL methods on CVDP
(
31
)
, whose problem statements and target code are several orders of magnitude longer than those in VerilogEval. CVDP includes hundreds of complex RTL problems spanning multiple tasks and hardware domains such as arithmetic units, on-chip protocols, memory hierarchies, DSP kernels, and communication blocks. Empirically, we observe that CVDP better distinguishes model capability and more faithfully reflects the demands of practical RTL design.

3.1.
Generator: An RTL-Specialized LLM

We train an RTL-specialized model as ACE-RTL-Generator, which aims to produce correct code, conditioned on an input specification and an evolving context constructed during prior iterations.
To this end, we follow two steps to construct a large-scale RTL dataset:
(i)
collecting and filtering raw RTL scripts from public sources,
(ii)
generating diverse specification–code pairs via in-context learning.

High-Quality RTL Script Collection

Motivated by data scaling laws in LLMs
(
15
;
19
)
, we begin by collecting five million raw RTL scripts from public repositories and open hardware projects.
To ensure data quality, we perform a sequence of filtering and validation steps.
First, we remove duplicate files and eliminate machine-generated code, including netlist scripts or RTL generated from high-level synthesis. We also filter out extreme outliers by excluding scripts with fewer than
30
lines or more than
2,000
lines. Next, we apply syntax validation using the
Icarus Verilog (iverilog)

(
34
)
to discard all code samples containing syntax errors.

To prevent contamination of downstream evaluation benchmarks, we use the
Jaccard similarity
metric defined in
(
12
)
to measure the similarity between each collected RTL snippet and all benchmark golden solutions.
Any collected code whose similarity score exceeds
0.8
with respect to any golden solution is discarded. This effectively prevents overlap with test data and ensures fair evaluation. After all filtering stages, we retain 157K high-quality RTL scripts as the foundation for specification-code pair generation.

Specification and Code Pair Generation

Given the filtered RTL corpus, we employ in-context learning to automatically generate diverse specifications for each RTL design. We first manually construct a pool of 32 high-quality examples, each containing a specification paired with its RTL implementation. These examples span multiple tasks, including RTL code generation, modification, and debugging.
For each raw RTL script, we randomly sample one instance from this pool as context and prompt multiple LLMs, including open-source models such as
GPT-OSS-120B

(
1
)
and
DeepSeek-R1

(
13
)
as well as proprietary ones, to produce diverse pairs of task-specific specifications and corresponding golden RTL implementations. Since the generated RTL may deviate from the original design, we apply an additional filtering stage to remove samples with syntax errors or potential benchmark contamination, identified by high similarity to downstream evaluation benchmarks.
For modification and debugging tasks, the specification includes a simplified or intentionally faulty version of the golden code, emulating realistic design correction workflows. Through this pipeline, we curate a large-scale dataset of 1.7 million specification–RTL pairs that comprehensively cover diverse hardware design scenarios.

Using this large-scale RTL dataset, we apply supervised fine-tuning (SFT)
(
7
)
to obtain the RTL-specialized model. The resulting model internalizes hardware domain knowledge and RTL semantics, enabling it to generate correct RTL code across diverse design tasks.

3.2.
Reflector: A Frontier Reasoning LLM

While the Generator produces RTL code grounded in domain knowledge, the Reflector analyzes simulation feedback and guides refinement. Frontier generic LLMs excel at interpreting specifications, buggy code, and error reports, making them well suited for this role. In ACE-RTL, the Reflector is built upon Claude4-Sonnet to interpret verifiable feedback and generate structured fix strategies.

At each iteration, the RTL code produced by the Generator is compiled and simulated using
iverilog
to verify functional correctness. When simulation fails, the Reflector is triggered to analyze the feedback. Automated scripts invoke the simulator and convert the raw logs into a structured format that captures the error message and the expected versus actual signal behavior. Claude4-Sonnet then serves as the Reflector’s reasoning engine: it integrates this parsed information with the design specification and the buggy RTL code to produce a structured diagnostic report. The report provides a concise explanation of the root cause together with high-level fix guidance describing how to resolve the primary failure. This structured output is then passed to the Coordinator for context evolution.
Notably, the entire process depends only on
iverilog
, a lightweight and open-source simulator, rather than complex proprietary toolchains. This design choice makes the system portable, easy to maintain, and readily adaptable to diverse RTL design tasks.

3.3.
Coordinator: A Context Evolution Engine

The Coordinator in ACE-RTL serves as the memory and control center of the agentic loop, maintaining a dynamic, self-evolving context that guides the Generator in subsequent iterations. Its primary role is to provide an incrementally refined context that captures an organized record of prior attempts, enabling more informed reasoning while avoiding redundant or counterproductive fixes. This component is implemented through efficient scripts, with Claude4-Sonnet providing core reasoning support, to continuously update and restructure the evolving context based on the system’s progress.

The Coordinator performs two key functions. First, it aggregates debugging history across iterations, tracking which errors were identified, what fixes were suggested, and whether those fixes resolved the issues. This structured memory preserves useful progress and prevents regressions, allowing the Generator to focus on remaining failure cases rather than revisiting already-corrected logic.

Second, the Coordinator monitors progress across iterations. If the same error persists over multiple rounds, it recognizes that the current code trajectory may be difficult to repair and triggers a
restart mechanism
, discarding the current implementation and prompting the Generator to produce a fresh RTL design from the specification. This leverages LLM stochasticity to explore alternative implementations that is easier to correct.

By combining structured history aggregation with an adaptive restart mechanism to construct a self-evolving context, the Coordinator keeps ACE-RTL both stable and flexible. It preserves useful debugging insights when progress is made and triggers a controlled reset when stagnation occurs, enabling more efficient progress toward functionally correct RTL code.

3.4.
Parallel Scaling in ACE-RTL

Although the iterative debugging framework in ACE-RTL effectively improves code correctness, it may require a large number of iterations to converge when starting from an unfavorable initial RTL generation. To address this inefficiency, we introduce a
parallel scaling
strategy that exploits the inherent stochasticity of LLM-based code generation to accelerate convergence.

Instead of relying on a single debugging trajectory, the parallel scaling strategy launches multiple ACE-RTL processes simultaneously, as shown in Figure
2
(b). Each process begins with a distinct RTL implementation generated by the Generator from the same input specification. These processes then proceed separately through the iterative loop of the Generator, Reflector, and Coordinator components, performing debugging and refinement in parallel.

During execution, all processes are monitored concurrently. Once any process produces an RTL implementation that passes all functional test cases, the system immediately terminates all remaining processes and outputs the correct code. If none of the processes achieve functional correctness within the predefined maximum number of iterations, all are stopped automatically.

This strategy leverages the diversity introduced by LLM stochasticity, as some initial generations naturally require far fewer debugging steps than others. By exploring multiple debugging paths in parallel, the system reduces the worst-case iterations needed to reach a correct solution. Consequently, the parallel scaling strategy largely reduces the overall iteration count, as confirmed in Figure
6
.

4.2.
Main Results

As shown in Table
1
, most prior RTL-specialized models struggle on CVDP, despite their strong performance on earlier RTL benchmarks. This suggests that models trained mainly on shorter and simpler RTL data generalize poorly to the more complex and realistic design challenges posed by CVDP. In contrast, recent frontier proprietary models such as
GPT-5
and
Claude4-Sonnet
show notable improvements and set strong new baselines, benefiting from broader RTL exposure during large-scale pretraining and stronger reasoning capabilities on complex coding tasks.

Our RTL-specialized model,
ACE-RTL
-Generator, further advances the RTL coding frontier, outperforming all baselines on most tasks. It achieves a Pass@1 of
65.09\%
on
Code Modification
(cid004), surpassing the SoTA baseline GPT-5 by
21.45\%
. This strong performance stems from our high-quality modification data, created by extracting basic RTL code segments and training the model to augment them with missing features, as discussed in Section
3.1
.

By integrating our specialized Generator with the full ACE framework, ACE-RTL achieves the best overall performance on CVDP, with up to a
44.87\%
APR improvement over SoTA baselines. ACE-RTL also outperforms the ACE-RTL (Claude4) variant, showing that an RTL-specialized model is more effective than relying solely on a frontier generic LLM. Together, these results validate the effectiveness of ACE-RTL, which iteratively evolves contextual information to guide the specialized model toward accurate RTL coding.

4.3.
Case Studies

To further demonstrate the effectiveness of our approach, we present three representative case studies. The first case showcases how our RTL-specialized model (ACE-RTL-Generator) exhibits a deeper grasp of hardware design principles and canonical RTL patterns compared to generic LLMs. The second case illustrates how ACE-RTL-Reflector elevates repeated local failures into functional reasoning, enabling it to diagnose structural errors. The third case demonstrates how ACE-RTL-Coordinator identifies unproductive progress and strategically triggers restarts, enabling the system to escape local minima and reach correct RTL implementations.
Notably, the examples in the latter two case studies require the highest number of iterations to reach correct solutions in our experiments.

Case Study I —
This case study examines the RS232 Transmitter module, which performs serial data transmission driven by precise baud-rate timing. A central component is the baud-rate generator, which produces periodic pulses that step the transmitter state machine through start, data, and stop bits. Correct behavior relies on an accurate fractional clock divider to handle the non-integer ratio between the system clock and the target baud rate.

As shown in Figure
3
, Claude4-Sonnet fails to produce a functionally correct implementation due to misunderstanding a fundamental RTL design pattern. Its code couples the accumulator and pulse into a single assignment, thereby losing the overflow-based pulse signal and producing unstable timing behavior. In contrast, our RTL-specialized model (i.e., ACE-RTL-Generator) correctly implements an accumulator-based divider, updating only the lower bits and using the most significant bit as a stable pulse output. This solution reflects an understanding of canonical hardware timing structures, which our model learns from curated RTL training data.

Case Study II —
This case study analyzes the 64b/66b Decoder module, which performs bit-aligned extraction of mixed-mode data streams. Figure
6
shows that ACE-RTL quickly improves functional correctness but remains stuck for many iterations before passing the final test case.
ACE-RTL-Reflector identifies this stagnation and analyzes the discrepancies between expected and actual outputs. By comparing these discrepancies against the provided specification, the Reflector infers that the decoding logic requires an implicit alignment transformation that is not stated in the specification. It then formulates high-level guidance describing this missing behavioral requirement, which directs the Generator to update the extraction logic accordingly, after which the design immediately passes all remaining tests.

This case illustrates how ACE-RTL-Reflector interprets systematic failure signals to detect specification gaps and elevate repeated local adjustments into understanding the implied design intent, enabling the system to resolve design-level issues that cannot be addressed through isolated fixes.

Case Study III —
This case study analyzes the Clock Jitter Detection module, which evaluates clock stability by comparing measured edge intervals against a timing threshold. As shown in Figure
6
, ACE-RTL makes early progress but soon enters a long plateau where all attempts fail. The stagnation occurs because each iteration repeats the same flawed behavior: performing jitter detection before a valid baseline interval is established. Although the Generator produces many syntactic variants, they all retain this early-trigger issue and therefore cannot satisfy the required timing semantics.

ACE-RTL-Coordinator recognizes this stalled trajectory by observing that many consecutive iterations exhibit the same assertion pattern with no meaningful improvement. Consequently, the Coordinator triggers a restart and distills high-level insights from the failed attempts, such as the need to validate the first measurement interval before performing detection. It then instructs the Generator to regenerate the design from the specification using these clarified constraints.

The restart produces a simpler and more interpretable implementation that shifts the logic toward proper interval validation. After two restarts, the Generator introduces a validity flag that delays jitter detection until the first full measurement interval has been observed, which immediately restores correctness. This case shows how ACE-RTL-Coordinator identifies prolonged stagnation, extracts useful design insights, and uses
restart mechanism
to move the system toward correct RTL implementations.

Conclusion
