Lirong Yi, Gregory Gay, Philipp Leitner

Abstract
. Large Language Models (LLMs) can generate code, but can they generate fast code? In this paper, we study this question using a dataset of 65 real-world tasks mined from open-source Java programs. We specifically select tasks where developers achieved significant speedups, and employ an automated pipeline to generate patches for these issues using two leading LLMs under four prompt variations. By rigorously benchmarking the results against the baseline and human-authored solutions, we demonstrate that LLM-generated code indeed improves performance over the baseline in most cases. However, patches proposed by human developers outperform LLM fixes by a statistically significant margin, indicating that LLMs often fall short of finding truly optimal solutions. We further find that LLM solutions are semantically identical or similar to the developer optimization idea in approximately two-thirds of cases, whereas they propose a more original idea in the remaining one-third. However, these original ideas only occasionally yield substantial performance gains.



1.
Introduction

Recent advances in generative AI, and specifically Large Language Models (LLMs), have brought the idea of code synthesis — generating syntactically correct and semantically meaningful program code from (often under-specified) high-level natural language prompts — into the mainstream of software engineering. Despite questions surrounding the reliability of these models, researchers as well as practitioners have started using LLMs in various phases of the software development lifecycle, including generating requirements
(
Nouri et al. 2024
)
, test cases
(
Chen et al. 2024
)
, refactoring
(
Liu et al. 2025
)
, or to develop new features or greenfield applications entirely without programming (“vibe coding”)
(
Sarkar and Drosos 2025
)
.

However, one area that still causes concern is the performance efficiency of generated code. Previous work has shown that generated code is often inefficient
(
Niu et al. 2024
)
, and has noted that standard benchmarks such as CoderEval
(
Yu et al. 2024
)
lack performance tests to even properly assess whether generated code is efficient
(
Peng et al. 2025b
)
. Further, it has been reported in initial studies that code efficiency, unlike correctness, does not necessarily improve with larger foundation models
(
Niu et al. 2024
)
. While prior work has measured efficiency on self-contained programming challenges
(
Zheng et al. 2024
)
or verified correctness on large-scale engineering tasks
(
Jimenez et al. 2024
)
, a gap remains in evaluating performance on real-world software issues. In this paper, we ask a related question — can LLMs generate code changes (patches) that improve the performance of real-world software systems? Performance is a crucial non-functional property for many systems, and performance is often linked to energy consumption
(
Abdulsalam et al. 2015
)
. Hence, being able to improve the performance of systems using AI would not only improve end user satisfaction, but also potentially reduce the energy footprint of future software.

To this end, we conduct an experimental study on Java-based open-source systems. We collect a dataset of 65 real performance-improving changes from four large and performance-sensitive Java projects. We develop an automated end-to-end pipeline that tasks two commercial LLMs (OpenAI o4-mini
1
1

1

https://openai.com/index/introducing-o3-and-o4-mini
and Gemini 2.5 Pro
2
2

2

https://deepmind.google/models/gemini/pro/
) with optimizing the original code. This pipeline includes an error-feedback-driven repair loop to handle incorrect generation. We compare the LLM-generated code to both the original and the developer-improved versions, using developer-provided performance microbenchmarks written using the Java Microbenchmark Harness
3
3

3

https://github.com/openjdk/jmh
(JMH) to assess the performance of each version of the code. Our study answers the following research questions:

RQ1: To what extent can LLM-generated code achieve performance improvements in Java open-source projects?

This research question investigates the capacity of LLMs to produce code that achieves substantial performance enhancements in practice. In addition, we systematically evaluate how different prompt variations (which differ with regard to how much information we provide to the LLM regarding the performance issue that is to be resolved and the benchmark that will be used to assess the result) and the choice of specific LLM affect the performance of the resulting change. We find that around one-third of generated patches are implausible (i.e., the patch cannot be integrated, the patched code does not compile, or the patched code fails its tests). However, from the plausible patches, around two-thirds indeed improve the measured performance of the system under test.

RQ2: Do LLMs achieve similar performance improvements to human experts?

In this question, we compare the LLM-generated patches with the ones that human developers have originally written to determine the extent to which LLMs can produce optimizations that are comparable to, or even exceed, the performance gains achieved by human experts. Our results show that — while there are, indeed, individual cases where LLM patches outperform the human baseline — human-written solutions statistically significantly outperform LLM patches with a medium–large effect size, depending on LLM configuration.

RQ3: Do LLMs propose similar improvements to human developers?

Finally, we investigate
what kind
of performance fixes LLMs propose. We manually label all generated patches as either similar to the human fix, dissimilar, or following the same idea with a different implementation. Dissimilar (or “original”) optimizations are common only when little context (e.g., no problem description) is provided in the prompt. If context is present, the LLM solution is often very similar to the human-written fix. We also observe that dissimilar patches very rarely lead to big performance improvements.

Overall, our study shows that LLMs can be a useful tool for performance engineers, but cannot replace human expertise. Performance issues tend to be intricate
(
Jin et al. 2012
;
Han and Yu 2016
)
, leading to LLMs generating defective code more frequently than in other generation tasks. Further, and in line with other LLM research, the best performance improvements are only reached if a human developer can provide detailed context to the AI model. Based on our observations, we offer suggestions for both practitioners and researchers interested in applying LLMs to performance engineering tasks.

2.
Methodology

We conduct our research in four steps, as shown in Figure
1
. We begin by collecting a specialized dataset of real-world tasks where developers have achieved performance improvements, measuring the performance difference between the original and developer-improved code. Next, we configure two LLMs with four prompting strategies and instruct them to generate performance improvements — validating the syntactic and semantic correctness of these improvements through compilation and unit tests. We then benchmark the performance of the generated code using JMH microbenchmarks. Finally, we analyze and compare the nature and efficiency of LLM-generated patches against human-authored improvements to assess the practical potential of LLMs for performance improvement. In the following, we discuss our methods for each of these four steps in detail.

Overview of the research methods.

2.1.
Data Collection

To construct a realistic and challenging evaluation suite, we curate the
PerfOpt Dataset
, a collection of 65 performance-oriented programming tasks sourced from the commit histories of four performance-critical open-source Java projects: Apache Kafka
4
4

4

https://github.com/apache/kafka
, Netty
5
5

5

https://github.com/netty/netty
, Presto
6
6

6

https://github.com/prestodb/presto
, and RoaringBitmap
7
7

7

https://github.com/RoaringBitmap/RoaringBitmap
. The
PerfOpt
dataset is available in our online appendix
17
.

These projects were selected for their demanding high-throughput and low-latency requirements. Each task in
PerfOpt
captures a real-world optimization scenario involving issues such as algorithmic inefficiencies, suboptimal data structures, or concurrency bottlenecks. Concrete tasks were selected via purposive sampling
(
Baltes and Ralph 2022
)
, i.e., the first author manually searched for code contributions in each project that fulfilled the following acceptance criteria: (1) the contribution was fixing a performance problem, (2) the contribution included at least one JMH benchmark to demonstrate the improvement, (3) running the benchmark on the original and improved version of the code showed a performance improvement, and (4), the code changes were concise, affecting fewer than 3 files, to exclude large-scale refactoring.

Each commit that met all four of these criteria was then subjected to a two-step validation process:
functional verification
using unit tests and
performance validation
using JMH. After confirming a raw performance improvement, we formally determine if that improvement is statistically meaningful. Each execution of a benchmark yields a set of performance measurements. A task is only included in the dataset if the performance difference for that set of observations between the original code and the developer-written solution is statistically significant according to a Wilcoxon signed-rank test
(
Wilcoxon 1945
)
(
p<0.05
) and demonstrates at least a medium effect size according to the Vargha-Delaney A12
(
Vargha and Delaney 2000
)
measure (
A12\geq 0.64
). That is, we only include tasks where we know a performance improvement is possible, that have at least one developer-written benchmark that demonstrates the improvement, and where we can replicate the improvement in our measurement infrastructure.

For each task, the dataset includes the following artifacts:

(1)

Performance Issue Description:
A natural-language description of the performance problem, extracted manually from developer commit messages or issue tracker reports.

(2)

Original Code:
The Java code version prior to the patch.

(3)

Developer Solution:
The developer’s performance-improving patch.

(4)

Unit Tests:
A corresponding suite of tests to verify the plausible correctness of any applied patch. We selected test cases by identifying the corresponding unit test class (e.g.,
ClassNameTest.java
for
ClassName.java
). In cases where a direct mapping is not present, we identified the relevant tests by analyzing the project’s dependency graph to find test suites that explicitly invoke the modified class.

(5)

JMH Benchmarks:
One or more benchmarks are used to quantitatively evaluate performance. Each benchmark may contain JMH parameters, used to execute the benchmark in different configurations or to simulate different workloads. Benchmarks report either throughput (e.g., ops/
\mu
s) or execution time (e.g., ns/op).

2.2.
Generating LLM Optimizations

In this study, we apply the OpenAI o4-mini and Gemini 2.5 Pro LLMs. We selected these models because they, at the time of our experimentation (Spring 2025), achieved consistently high results on prominent benchmarks for code generation, while —at the same time— representing multiple model sizes (o4-mini is an intentionally smaller commercial model). We chose not to include open-weight models in this study, as our goal was to evaluate the performance of state-of-the-art models widely used by practitioners. Both models were accessed via their provider’s API. For both models, we applied the settings
temperature=0.3
and
top\_p=0.95
, selected via informal experimentation. As LLMs yield non-deterministic results, we repeated the entire generation process three times for each combination of task, prompting strategy, and model. We refer to these repetitions as
trials
.

2.2.1.
Prompting Strategy

To assess the impact of varying forms of context on the performance task, we formulate four distinct prompt strategies for each of the 65 tasks:

•

No-Hint Prompt:
This foundational prompt includes only a fixed persona
(
Khojah et al. 2025
)
, the source code, unit tests, and a request to improve the performance of this code. The persona directed the LLM to act as an expert Java developer tasked with improving code performance while preserving functionality. This prompt is designed to measure the LLM’s ability to optimize code with no further information on what to do precisely.

•

Prompt with Problem Description:
This prompt augmented the baseline with a natural-language hint. The hint describes the performance problem based on the performance issue description collected along with each task, and tests the model’s ability to leverage semantic clues. The problem description was manually curated for each task to provide an effective performance description without giving away the solution.

•

Prompt with Benchmark:
This prompt augmented the baseline with the source code of the JMH benchmarks that will be used to measure the improvement. This provides a direct, structural pointer to the performance-critical code paths being measured, and clarifies how exactly solutions will be judged.

•

Prompt with Both:
This prompt is the most comprehensive, augmenting the baseline with both problem description and benchmark information. This simulates an ideal scenario where a developer has thoroughly documented and benchmarked a known bottleneck.

This tiered design enables a fine-grained analysis of how different types of context information affect the models’ optimization effectiveness.

2.2.2.
Output Format

To ensure that generated patches can easily be used downstream in our experimental pipeline, we mandate in the prompt that all generated code changes are delivered in a custom, JSON-based patch format. An example is shown in Figure
2
.

Figure 2.
Automated patching with search/replace blocks generated by LLMs

We do not directly instruct the LLMs to produce complete Git-style diffs because current LLMs struggle with counting tasks
(
Ahn et al. 2024
;
Xu and Ma 2025
)
. Generating diff hunks often requires accurate line offsets and context lines, which exceed the token-level or subword-level reasoning capabilities of current-generation LLMs. Instead, we focus on extracting and replacing self-contained code blocks, which avoids introducing fragile offset dependencies and ensures that patches remain robust across minor codebase variations. This format enforces atomic, independently applicable changes and facilitates automated patching.

2.2.3.
Error-Guided Repair

Our workflow integrates an automated, iterative repair loop to handle implausible responses, a concept central to the field of automated program repair (APR)
(
Le Goues et al. 2019
)
. Following the definition of
plausibility
from APR literature
(
Qi et al. 2015
)
, a response is considered
implausible
if (a) the LLM did not produce a valid patch in the prescribed format, (b) the patched code failed to compile, or (c), the patched code did not pass the provided unit test suite. Conversely, a solution that meets all of these conditions is considered
plausible
.

When we encountered an implausible patch, we automatically construct a new repair prompt containing the original prompt, the model’s failed output, and the corresponding diagnostic message (e.g., the compilation error). This feedback loop enables the model to potentially self-correct implausible solutions. However, in our preliminary experimentation, we have seen that —if initial generation or repair attempts are unsuccessful— the model rarely manages to fix the issue on its own. Hence, we end the repair loop after a maximum of
two
attempts for integration failures and
three
for verification failures.

To ensure consistent and reliable microbenchmarking, we applied a standardized JMH configuration across all experiments, defined by Laaber et al.
(

— 10 warm-up iterations to allow the JVM to stabilize and perform runtime optimizations, followed by 50 measurement iterations for data collection. Each iteration entails a

1s

Furthermore, to address the inherent variability of virtualized, multi-tenant environments, our experimental protocol was designed based on the Multiple Consecutive Trials strategy
(
Abedi and Brecht 2017

. This approach helps mitigate the impact of transient system noise and enhances the statistical robustness and reproducibility of our findings. Using this method, we collected a large dataset of 319.300 raw performance measurements as a basis for our analysis. Collecting this dataset required approximately 1350 VM hours of computing time.

2.4.
Analysis

The final phase of our methodology involved a rigorous analysis of the collected measurement data, guided by our three RQs.

2.4.1.
Benchmark Scores

JMH benchmarks report one measurement result for each iteration (50 in our case), and it is common to interpret the arithmetic mean result of all iterations as the (individual) benchmark score.
9
9

9

https://stackoverflow.com/questions/24928922/jmh-what-does-the-score-value-mean
However, JMH supports different “modes” (e.g., throughput, execution time), and not all benchmarks in
PerfOpt
use the same mode. Additionally, individual benchmark scores in our study vary by orders of magnitude. Finally, for our RQs, we are not inherently interested in the absolute benchmark scores, but in the
change
in benchmark scores for the patched code in comparison to the original, unpatched version.

Hence, we define a metric,
patch performance score (pss)
, for a task
id
as
pss_{id}=\frac{\mu_{id,new}}{\mu_{id,orig}}
for benchmarks where higher values are better (such as throughput), and as
pss_{id}=\frac{\mu_{id,orig}}{\mu_{id,new}}
for benchmarks where lower values are better (e.g., execution time).
\mu_{id,orig}
and
\mu_{id,new}
are the average performance score of the benchmark of the original and patched code, respectively.
pss
is a ratio score in the interval
[0;\infty]
, with
pss=1.0
representing no performance change,
pss<1.0
representing a slowdown, and
pss>1.0
representing an improvement.

A further challenge in our analysis is that each task in
PerfOpt
may be associated with multiple benchmarks, and benchmarks may have multiple configurations (for practical purposes it is common to consider each distinct benchmark configuration an entirely separate benchmark
(
Samoaa and Leitner 2021
)
). Not all benchmarks will profit from an optimization, and developers often also refer to benchmarks that are not expected to change in their commits (e.g., as baselines or guardrails). Hence, we select a single benchmark and configuration for each task to serve as the basis for our analysis, referred to as the
representative benchmark
. The representative benchmark is defined as the specific benchmark configuration where the human developer’s patch achieved the highest
pss
. The performance of all other solutions (including all LLM trials) for that task is then measured and reported using their results in the representative benchmark. This is based on the intuition that this benchmark best exemplifies the improvements that the developers intended to achieve by changing the code.

2.4.2.
Plausibility and Magnitude Analysis

To answer RQ1, we first assess the
plausibility
of each generated solution, based on the definition outlined in Section
2.2.3
. Then, for each possible solution, we assess the magnitude of the
pss
score, i.e., of the change in performance.

2.4.3.
Statistical Analysis

To answer RQ2, we first select a single
representative LLM solution
from the three trials for each model-prompt combination. The representative solution is defined as follows: (a) if all three trials lead to plausible patches, we use the solution with median
pss
, (b) if two generations are plausible, we conservatively use the worse-performing patch, and (c) if only one generation is plausible, we use that patch.

We then conduct a pairwise statistical comparison using the
pss
from the representative LLM solution and the
pss
of the developer solution (or the unmodified baseline). We employ a two-step statistical procedure. First, we use a two-sided Wilcoxon signed-rank test
(
Wilcoxon 1945
)
to determine if the performance scores of two patches are statistically different. The null hypothesis (H0) is that the scores are drawn from the same distribution. If the resulting p-value is less than 0.05, we reject the null hypothesis. Second, for all pairs with a statistically significant difference, we calculate the Vargha-Delaney A12 effect size
(
Vargha and Delaney 2000
)
. This non-parametric statistic provides a probabilistic measure of the difference, where a value of
A12(X,Y)
represents the probability that a random sample from group
X
is greater than a random sample from group
Y
. An A12 value of 0.5 indicates stochastic equality, while a value of
0.50-0.55
indicates a negligible effect,
0.56-0.63
indicates a small effect,
0.64-0.70
indicates a medium effect, and
\geq 0.71
indicates a large effect. Values below
0.50
indicate that
X<Y
, with effect sizes at the same ranges in the opposite direction.

2.4.4.
Manual Patch labeling

To answer RQ3, we label all LLM-generated patches with regard to how similar they are to the improvement proposed by human developers. We use the following pre-defined codes:

•

Strategy Match:
the generated patch addresses the same issue and is functionally equivalent to the developer’s change.

•

Strategy Alignment:
the generated patch addresses the same fundamental issue, but proposes a functionally different approach.

•

Strategy Divergence:
the generated patch proposes an entirely different optimization.

Each generated patch is assigned exactly one of these codes by the first author. If multiple optimizations are contained in the same patch, the classification is based on the described primary bottleneck. Hence, even solutions assigned a "strategy match" can in practice show slight variations in performance. Fundamentally, "strategy match" and "strategy alignment" indicate that the LLM follows a similar solution approach as the human developer, whereas "strategy divergence" indicates a different (or "original") idea.

We observe from Table
4
that, in 64% of plausible cases, LLM-generated solutions are able to improve performance. LLM-based solutions led to performance degradations in only 5% of cases. This suggests that LLMs do have the potential to improve the performance of real-life performance-sensitive systems. However, there are also limitations in their effectiveness. In 31% of cases, performance did not substantially change. In addition, whereas developer-written patches achieve a massive improvement (i.e., an improvement with
pss>1.5
, or more than 50% speedup) in over 62% of cases, LLMs only offer massive improvements in 46% (Gemini) and 36% (o4-mini) of cases, and only if sufficient information about the performance problem is provided in the prompt. In the “No Hint” setting, which represents a case where no further information about the problem or benchmark is provided, only 22% and 20% of plausible patches achieve a massive performance improvement. Therefore, we can see that there are meaningful differences in the
general
effectiveness of humans versus LLMs, and between different LLMs and prompting strategies. In RQ2, we will explore these differences in more detail.

For o4-mini, providing a concise problem description is sometimes extremely valuable —indicated by a higher third quartile —whereas providing information about the benchmark does not help this model much. For Gemini, providing problem or benchmark information can be helpful, and the best results are achieved when both are present in the prompt. However, especially for o4-mini, we observe that providing a combination of both types of information sometimes leads to a decrease in performance (as also reported by Khojah et al.
(
Khojah et al. 2025
)
).

Applicability of LLMs to Performance Improvement (RQ1):
LLMs offer the potential to improve performance of source code. 62% of generated solutions were plausible. Of those, 64% yielded performance improvements. However, there are still cases where implausible patches, performance regressions, or insubstantial changes are produced, indicating limitations of current LLMs and the need for further research.

3.2.
Are LLM-Generated Solutions Human-Competitive? (RQ2)

Figure
4

We now discuss

of improvements LLMs suggest, and how similar they are to the developer baseline. To do so, we manually labeled each generated LLM solution using one of three codes (match, alignment, and divergence; see Section

Figure

presents a concrete example from our dataset. The performance task is to optimize a function that was inefficient for very small arrays (size
\leq

).

Developer-LLM Similarity (RQ3):
Developers and LLMs are most likely to implement functionally-identical changes when LLMs are prompted with problem information. Gemini is, generally, more likely to implement functionally-identical changes than o4-mini. However, the distribution of LLM-developer alignment differs somewhat between projects. The largest performance gains are yielded in cases where the developer and LLM align, while divergences lead largely to insignificant improvements.

4.
Discussion

Our findings offer several key implications for the role of LLMs in performance engineering. In this section, we discuss the practical applications for developers, the need for integrated tooling, and suggestions for future research. We also examine the limitations of our study.

4.1.
Implications

The Role of LLMs in Performance Engineering:
Our findings indicate that LLMs can propose patches that are plausible in two-thirds of cases and often beneficial to performance, but they do not yet match the effectiveness of human experts. Their solutions frequently offer suboptimal improvements or, in some cases, introduce regressions. This is particularly evident when LLMs produce solutions that diverge from the strategy followed by the developer in their own solution. Without a clear context for the underlying performance issue, LLM solutions tend to be shortsighted, sometimes applying micro-optimizations that miss the core issue. This suggests that their “creativity” may be more akin to a shallow pattern-matching of alternative code structures rather than a deep understanding of performance bottlenecks. While LLMs yielded better solutions when offered problem context as part of the prompt, this gap in deep performance reasoning is a critical area for future research.

Despite these limitations, we observed rare-but-significant instances where an LLM proposed an optimization that an experienced developer missed. This highlights the potential for LLMs as a tool for brainstorming alternative optimization strategies. Therefore, the most immediate and practical role for LLMs in this domain is as a performance co-pilot or an assistant that suggests potential optimizations, which a human developer must then critically evaluate, benchmark, and validate before integration. LLMs should be viewed as a tool to augment, not replace, human expertise.

A Blueprint for Automated Performance Co-Pilots:

Our findings suggest that applying LLMs to performance optimization requires more than just code generation. An integrated system is needed that can empirically validate non-functional properties of the generated code. The end-to-end pipeline developed for our study, which combines contextual prompting, iterative self-repair, and benchmarking, provides a potential blueprint for such a system. We envision future developer tools, from IDEs to CI/CD workflows, that embed LLMs as performance co-pilots within an automated framework. Such a tool would not merely suggest code, but would orchestrate the entire optimization lifecycle — e.g., automatically extracting context from an issue ticket, generating a candidate patch, verifying its correctness, and, crucially, running the relevant benchmarks before presenting the results to the developer for review. Such a pipeline would transform the LLM from a simple suggestion engine into a more reliable “partner” in the performance engineering process.

The Need for Realistic Performance Datasets:

Our data collection process yielded a critical lesson — real-world performance issues are fundamentally more complex and diverse than those typically found in academic or competitive programming datasets. While traditional performance benchmarks often focus on isolated, algorithmic inefficiencies
(
Niu et al. 2024
;
Peng et al. 2025b
)
, the tasks in
PerfOpt
demonstrate that real-world bottlenecks frequently arise from nuanced, context-specific problems such as concurrency issues, suboptimal API usage, or memory allocation patterns. This disparity suggests that evaluating LLMs on purely algorithmic challenges may provide a misleading picture of their capabilities when applied in practice. To meaningfully assess and improve the utility of LLMs in performance engineering, future research must prioritize the use of realistic, validated datasets that capture the multifaceted performance problems encountered by developers in the field.
PerfOpt
can serve as a starting point for such a dataset.

4.2.
Threats to Validity

External Validity:
The external validity of our findings is primarily constrained by our choice of models and dataset. Our dataset is limited to four Java projects. Therefore, our findings may not generalize to other programming languages, application domains, or projects of different scales. However, by focusing on performance-critical Java projects, we believe we have provided a realistic foundation for our experiments. Further, our results are specific to two state-of-the-art commercial models, OpenAI’s o4-mini and Google’s Gemini 2.5 Pro, and may not be representative of other open-source or commercial models. Because these models are closed-source and updated without public versioning, exact replication poses a scientific challenge. However, we chose these models for their power and practical relevance to developers, and believe that our general findings would extend to other models. Finally, we mitigated the inherent stochastic nature of these models by performing three trials per task and configuration. These trials yielded relatively consistent results.

Internal Validity:
Our approach to performance measurement carries two threats to internal validity. First, we select a single, representative benchmark for each task, which means that an LLM could improve performance on the measured workload while causing regressions in other code. Second, although our experiments were conducted in a controlled environment, the inherent transient noise of a cloud environment could have influenced some measurements. We mitigate the impact of such noise by performing multiple trials. In addition, because our experiment is based on open-source projects, there is a risk of data leakage, where the LLM’s training data already contains the developer-written solution to each task. However, based on our qualitative analysis in RQ3, we do not believe that data leakage was a significant issue in the study. Even in strategy alignment cases, there were few generations where the LLM produced the exact same solution.

Construct Validity:
We assess patch plausibility by ensuring a patch passes the provided unit test suite, rather than guaranteeing full semantic correctness. This is a common practice, but it is limited by the completeness of the test suite itself, which may not cover all edge cases. Further, when using statistical analyses, we have attempted to ensure the base assumptions behind these analyses are met. We have favored nonparametric methods, as distribution characteristics are not generally known a priori, and normality cannot be assumed.

6.
Conclusions

In this paper, we presented an experimental study to assess the capability of modern LLMs to optimize the performance of real-world software. Using
PerfOpt
, a curated dataset of 65 performance optimization tasks from Java repositories, we employed an automated pipeline to generate patches with two leading LLMs under four distinct prompting strategies. Our results show that while LLMs can improve performance over an unoptimized baseline in the majority of plausible cases, their effectiveness generally does not reach the level of human experts. We found that prompts including a problem description guide LLMs towards more human-like solutions, whereas a lack of context leads to more novel, but rarely effective, optimizations. We conclude that the immediate role of LLMs is as a performance assistant—a powerful tool for augmenting developer workflows—but LLMs still require significant human oversight.

Our work opens several avenues for future research. A critical direction is to close the
deep performance reasoning
gap, potentially through fine-tuning on performance-specific datasets like
PerfOpt
or by implementing a multi-agent system
(
Idrisov et al. 2025
)
, where additional AI agents apply tools and perform additional analyses as input to patch generation. Another avenue is to realize the
performance co-pilot
vision by building IDE and CI/DI tools that seamlessly integrate our automated generation, repair, and benchmarking pipeline. Finally, future work should broaden our study by examining additional programming languages and emerging open-weight models.
