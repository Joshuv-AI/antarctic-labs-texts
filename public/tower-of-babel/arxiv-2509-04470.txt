COCORELI: Cooperative, Compositional Reconstitution & Execution of Language Instructions
Swarnadeep Bhar Omar Naim IRIT IRIT swarnadeep.bhar@irit.fr omar.naim.docs@gmail.com Eleni Metheniti Bastien Navarri ANTI ANTI Loïc Cabannes Morteza Ezzabady ENS Paris-Saclay, France IRIT Nicholas Asher IRIT, CNRS

Abstract
We present COCORELI, a hybrid agent framework designed to tackle the limitations of large language models (LLMs) in tasks requiring: following complex instructions, minimizing hallucination, and spatial reasoning. COCORELI integrates medium-sized LLM agents with novel abstraction mechanisms and a discourse module to parse instructions to in-context learn dynamic, high-level representations of the environment. Experiments on natural collaborative construction tasks show that COCORELI outperforms single-LLM CoT and agentic LLM systems, all using larger LLMs. It manages to largely avoid hallucinations, identify missing information, ask for clarifications, and update its learned objects. COCORELI’s abstraction abilities extend beyond ENVIRONMENT, as shown in the ToolBench API completion task.



1
Introduction

The rapid rise of Large Language Models (LLMs) has increased interest in their application to complex real-world tasks. However, real-world tasks often lack the large amounts of training data needed to fine-tune LLMs on a task, and users have to rely on few-shot learning or in-context learning. Moreover, zero- and few-shot LLM prompting consists of one input and output, which may hamper LLM performance especially when planning or multiple tools are required
(
Sypherd and Belle 2024
)
.

This has led to a strategy of decomposing a complex task into subtasks and training agentic models to solve the subtasks. Agentic systems incorporate multiple agents using LLM prompts. The workflow in such a system involves intermediary stages, resulting in better performance, adaptability, versatility, interpretability, and reliability in downstream tasks
(
Sudarshan et al. 2024
)
. Agentic models may incorporate components that use and learn deterministic functions in context in a
hybrid
or
tool learning approach

(
Schick et al. 2023
;
Qin et al. 2024
)
.

We develop and test a hybrid agentic approach on a collaborative task of constructing complex structures in a 3D environment. Our system COCORELI (

Separate, subsequent agents identify what the target object is and the user’s desired location of the object. The object’s properties are either retrieved from memory for objects the model knows about or derived from the user’s instructions. COCORELI’s output is a JSON object for a situated construction.

COCORELI can learn new complex object functions by abstracting over parameters in the located object derived from interactions with the user. Thus, the system can instantiate the object with different primitive parts, different colors, and at different locations. COCORELI’s use of abstraction allows it to learn functions in many other contexts. Each agent can activate a clarification “loop” that allows the agent to ask the user for missing information, which it can then append to the instruction history. This reduces hallucinations.

We compare COCORELI, which uses Llama-3.1-8b. to two other systems: (1) a Chain-of-Thought (CoT) (using large LLMs) approach that employs one LLM with a single prompt to complete the task and (2) an agentic LLM (Llama-3.3-70b) handling subtasks with specific prompts.

2
Related Work

Prompting techniques

LLMs falter at generalization, since it requires abstraction beyond the scope of their learned representations
(
Zhang et al. 2023
)
. Approaches such as
in-context learning
(ICL) provide additional information to the LLM in the form of an analogy, thus expanding their domain knowledge, for example, in mathematical equations
(
Naim et al. 2024
;
Mirzadeh et al. 2025
;
Naim and Asher 2025
)
. However, ICL remains limited to domain adaptation without providing generalizability
(
Dong et al. 2024
)
.

Chain-of-thought (CoT) prompting
(
Wei et al. 2022
;
Wang et al. 2023
)
aims to improve performance by asking the LLM to resolve a task by documenting its solution step by step.

Ahn et al. 2022
supply an LLM with the list of simpler tasks and prompt the model to decompose a complicated task as a sequence of simpler tasks.
Press et al. 2023
introduce multi-hop questions in CoT prompting with answers that require multiple facts that are novel to the LLM.
Yao et al. 2023b
extend the CoT process by integrating information retrieval from the Wikipedia API.
Yao et al. 2023a
introduce trees of thought (ToT) in order to diversify the LLM’s decision-making process to improve performance.
Long 2023
also enhance CoT with ToT, and incorporate agents and external memories.

Agentic models

Several studies have tested single-agent LLM models on their abilities in complex interactive tasks, including games, and report weaknesses in reasoning and planning
(
Liu et al. 2024
;
Gioacchini et al. 2024
;
Wu et al. 2024
)
. Specifically on Minecraft,
Wu et al. 2024
report very low performance of multiple LLMs compared to human competencies and problems, such as with 3D spatial reasoning. Larger LLMs (GPT3.5, LLaMA-3.1 70B) still outperform smaller, novel LLMs in game benchmarks
(
tse Huang et al. 2025
)
.
Regarding multi-agent approaches,
Park et al. 2023
introduced Generative Agents, a system based on GPT-3.5 with independent agents, each able to use functions for memory retrieval, reflection generation, and sequence planning.

Rutherford et al. 2024
used multi-agent reinforcement learning (MARL), testing in a variety of tasks in experimental computational game theory.

Xu et al. 2024
assigned cognition, adaptability, rationality, and collaboration objectives to multiple agents, using probabilistic graphic modeling. They reported that the larger LLMs, such as GPT-4-turbo, had the best performance on game benchmarks.

Tool learning

Tool learning involves the use of external tools to improve problem solving and broaden the functional scope of the LLM, thus augmenting performance on specific downstream tasks
(
Parisi et al. 2022
;
Gao et al. 2023
;
Long 2023
)
. Recently, researchers have developed self-supervised tools that can support a level of abstraction and generalization, in order to render them useful across multiple applications.

Schick et al. 2023
developed Toolformer, an LLM with GPT-3 in its underlying architecture, that is capable of generating functions to use API tools from various websites.
ToolLLM
(
Qin et al. 2024
)
has a similar motivation in generating API calling functions with LLaMA-2 7B in an unsupervised manner, in addition to proposing ToolBench, a dataset for evaluating unsupervised tool learning. Gorilla
(
Patil et al. 2024
)
is also an API function generating tool that incorporates document retrieval from the target API documentation.

Tang et al. 2023
introduced ToolAlpaca, a framework to fine-tune LLMs for better tool learning of API functions.

Collaborative tasks

Approaches to object identification with LLMs and reinforcement learning have proved that the task is complex and challenging to solve, and additionally ignore the needed human feedback (e.g.
Kanitscheider et al. 2021
;
Lin et al. 2022
).
The Minecraft Collaborative Building Task and the Minecraft Dialogue Corpus
(
Narayan-Chen et al. 2019
)
formalized a game of Minecraft as a collaborative task between two human players (an Architect and a Builder) and released a dialogue corpus of interactions for the game’s tasks. Based on this work,

Jayannavar et al. 2020
developed a neural network approach that predicts the Builder’s possible actions in the Minecraft collaborative environment. Voyager
(
Wang et al. 2024
)
is a learning agent based on GPT-4 that learns to play the Minecraft game, relying on an iterative prompting mechanism to create functions for game milestones and on in-context learning to create new skills on the fly and store them in an external database for later use. However, Voyager provides limited interaction between a human and the model, which is a crucial component in a collaborative environment for learning, and also overspecifies its stored skills.
For instance, the skill “crafting a wooden axe” is a separate skill from “crafting a metal axe” and must be learned and stored separately.

3
The ENVIRONMENT task

As in the Minecraft Collaborative Task
(
Narayan-Chen et al. 2019
)
, the ENVIRONMENT task involves two agents in a collaborative task of building an object, each with different roles. The Architect has a plan for accomplishing the task and must teach the other agent (Builder) how to achieve it.

While both environments share a common Architect-Builder setup, ENVIRONMENT introduces novel objects and scenarios that LLMs have not been trained on and so must in-context learn. It also has features that make the task harder (see Figure
2
for a visual comparison). The larger grid size (
16\times 16\times 16
in ENVIRONMENT vs.
11\times 11\times 11
in Minecraft), increases the complexity of spatial reasoning. Second, unlike Minecraft, ENVIRONMENT features 9 basic objects:
nuts
(3 types),
washers
,
screws
,
bridges
(2 types),
bolts
, and
gaskets
.
Different ENVIRONMENT parts can have different types of 3-D spatial coordinates. For example, bridge parts occupy two horizontal or vertical spaces (horizontal or vertical bridges); other parts only one space.
This introduces additional constraints and complexity on decision-making, as the model must determine where to place a “two place” part given only some desired coordinates.

Finally, ENVIRONMENT introduces challenges that reflect real-world constraints in structured assembly, multi-agent collaboration, and planning under physical laws. Unlike Minecraft, which allows unconstrained placement of blocks, ENVIRONMENT enforces strict physics rules (e.g., gravity constraints), requiring agents to reason about stability and structural integrity. The gravity constraint directly impacts construction strategies, thus creating more opportunities for failure in ENVIRONMENT.

4
COCORELI, our hybrid agentic system

Motivation

As seen in Figure
1
, COCORELI has several agents:
Discourse Module, Instruction Parser, Builder, External Memory, Locator
, and
Executor
. The agents are built with the LLaMA-3.1 8b LLM
(
Grattafiori et al. 2024
)
. We describe them and their features below.

COCORELI’s architecture contains a special feature, a
discourse module
(represented as a diamond in Figure
1
), that generates clarification questions when a called function is missing information needed for execution. An effective approach to coding this type of problem is to represent each object as a JSON structure containing all its specific characteristics, initially set to
null
. As the user provides information, these fields are progressively filled. This method is advantageous because LLMs often have difficulty not hallucinating the information needed. When attributes remain unspecified, the system requests more information via
clarification question
and iterates this procedure until the missing information is specified.
Thus, the system combines agent actions iteratively to resolve ambiguities and fill in missing information. Our system collects thus avoids hallucinating a lot.

Another feature of COCORELI is that agents can use an
abstraction function
over instantiated parameters in instructions or stored objects to acquire general plans. For example, given the input “
a tower made of three red nuts at the first column, second row
’’, COCORELI extracts the features and the location of each object separately and stores them. On a future step, the system is capable of replicating the multi-object structure in a different location or with different parts and colors.

Instruction Parser

The Instruction Parser interacts with the user to extract information from the user’s instructions. In ENVIRONMENT, it searches for the objects’ properties and locations from the textual input. The Parser passes relevant information to two other agents, the
Locator
and the
Builder
, which work in parallel.

Locator

The Locator uses the information collected from the Instruction Parser to find the coordinates in the grid where the user wants to place one or more objects. If the coordinates are incomplete, the agent activates the clarification loop in the discourse module and asks for the missing coordinates.

Builder

The Builder uses the given instructions to check with an
external memory
component if the part or structure mentioned in the instruction is a known entity or not. If the input refers to a known structure, it retrieves a JSON object representation from the memory and fills in the features specified in the instructions. If the input refers to a new object and the instructions are complete, the Builder uses those instructions to make the structure. Otherwise, it invokes the discourse module to ask for clarification.

External memory

The memory stores hard-coded ENVIRONMENT functions and previously created shapes as relational graphs, with nodes as parts and edges encoding relative spatial positions. In addition to storing single situated objects, COCORELI can use the abstraction function on a concrete situated object
O
in memory to construct an abstract function in which the instantiated parameters of
O
are abstracted away. This allows the system to recreate a version of
O
in any size, color, or other specifications. Another benefit is that our function-based approach is size-agnostic, meaning that we use one function for a complex structure instead of
n
placement instructions for the
n
components of the structure.

Executor

The Executor combines information from Builder and Locator to yield a JSON object, with arguments corresponding to object properties (e.g., part type, color). The executor can then run this object as a deterministic program.

5
Experimental setup

5.1
Tasks and baselines

We set up the following ENVIRONMENT-related tasks, on which we test COCORELI and baseline approaches:

(i)

(Fully-specified) single-sentence instructions to place a single part

(ii)

(Fully-specified) sequences of instructions

(iii)

(Fully-specified) sequences to build complex shapes

(iv)

Underspecified instructions (for one or two parts) and discourse ways to complete them

(v)

Instructions to abstract from previous instruction sequences and to learn new functions from context to apply in new situations

Task (i) requires that the model parse the user input and extract all the relevant information for object properties and location. In this task, there is no need to retain previous information.
Task (ii) additionally requires serially parsing multiple objects. Task (iii) demands the creation of a complex structure composed of simple and complex parts; COCORELI achieves this composition through a sequential call of functions.
Task (iv) probes the model’s ability to deal with missing information from user input; COCORELI uses the clarification loop to find the missing information.
Task (v) is a continuation of Tasks (ii) and (iii), in which the user describes a complex shape that the system generates and then abstracts on to get a general plan that can be executed in different ways. This task not only tests the system’s memory, but also its capacity to abstract and learn from past specific instructions (e.g., place the same complex shape in different colors).

Baselines

As our first baseline, we test a
single LLM
with a CoT prompt. The model is prompted once and is asked to generate a reasoning chain and a final answer on the ENVIRONMENT tasks. This setup lacks an external memory; so for tasks requiring memory, we must repeat the instructions(s) that described the shape in the current prompt.
In this single LLM setup, we test Claude 3.5 Sonnet
(
Anthropic 2024
)
and GPT-4.1
(
OpenAI 2025
)
.
We also tested LLaMA-3.1 8b
(
Grattafiori et al. 2024
)
in preliminary experiments, but the model’s accuracy was too low for a meaningful baseline.

As a second baseline, we use an
agentic LLM approach
.
We prompt the LLM to generate a Python function that abstracts over an input sequence of placement instructions. The goal is to induce a reusable, parameterized function that captures the underlying pattern in the data. If the converted code is correct, recreating the code will reduce to just calling the created Python function.
We use LLaMA 3-70b
(
Grattafiori et al. 2024
)
for the agents of this approach. For more software and hardware details of the baselines and COCORELI, see Appendix
A
.

5.2
ENVIRONMENT task data

Single-part placement instructions

To test Task (i), we generated 20 simple, synthetic sentences containing a placement instruction of a single object, with all the needed parameters in the input. As explained in Section
3
, the ENVIRONMENT parts are three-dimensional, may occupy one or two cells in the grid, and are gravity-bound. Since there are no prior placed objects in these instructions, gravity constraints mean that we only specify the
[x,y]
coordinates in these sentences. The sentence structures are the following:

•

Place a
[COLOR]

[PART]
at the
[X]
th column,
[Y]
th row.

•

Place a
[COLOR]

[PART]
at the
[relative coordinate]
of the board.

For horizontal bridges, two columns are provided for the
[x_{1},x_{2}]
placement requirement, and, for vertical bridges, two rows for
[y_{1},y_{2}]
. The relative coordinates may be grid positions such as
top left
,
middle
, etc., to be interpreted by the LLM agents.
This data captures the two ways in which a user may fully define the placement of a part, either with absolute or relative coordinates.

Sequences of single-part instructions

For Task (ii), the objective is to extract multiple objects from the same input. The input is composed of two sentences, with the same structure as the single instruction sentences. We created 13 tuples of these sentences with three possible variations: either the two parts are independently placed from each other, or the second part’s placement is dependent on the first part’s position (either on top or adjacent).

Construction of complex shapes

Task (iii) asks for the construction of 10 complex shapes with sequences of instructions from an Architect. Each instruction includes the placement of one or more parts (standard or complex), with either absolute or relative placements (e.g. “
place a horizontal row of four purple gaskets
”).
A list of the shapes can be found in Table
3
; the shapes are constructed from 2-6 instructions. Some of these contain the same type of part, while others have a variety of parts and colors. The Moroccan Bridge structure is a very complex shape made from 18 ENVIRONMENT parts. A detailed list and a visualization of the shapes in the ENVIRONMENT environment can be found in Appendix
C.1
.

Underspecified instructions

Task (iv) tests the handling of underspecified instructions; we split this task into underspecified single instructions (as in Task (i)) and underspecified two-part instructions (as in Task (ii)).
For the former, we created 81 sentences, similar to those of Task (i), but with one piece of information missing: the part name (e.g. “it” instead of “nut”), the color, or one or all of the coordinates.
For the latter, we created 202 instructions, in which either one or both parts described in the instruction were underspecified: the first single part placement was fully specified in 40 of those, and the second part placement was fully specified in 73 of the instructions.

Learning abstract functions in context

Task (v) tests a model’s ability to learn abstract functions given a context in which we specify an instance. We give instructions to create 9 complex structures, and we then ask the models to store them and recreate them in future instructions without any explicit information on their previously mentioned components. The first 4 structures are composed of 2-3 parts and have novel names (e.g.,
A20 tower
) in order to ensure that the LLMs did not retrieve shape information from representations learned in pretraining. The other 5 structures have common names (e.g.,
square
,
skull
) but are composed of significantly more parts (16-18 for moderate complexity, up to 62 for difficult structures). See Table
6
for a list of the names and Appendix
C.2
for details.

6.2
Discussion

The easiest task of our experiments, the single-part placement instruction, proved feasible for all systems.
In addition, the next experiment (Task ii), containing two single-part instructions, proved even more challenging for the CoT baselines, whose performance on identifying the second object’s properties was significantly lower. The following experiments confirm this finding, with the models hallucinating to a greater extent on the underspecified second part’s properties in Task (iv).
On the tasks of following a series of instructions (Tasks (iii) and (v)), the CoT models were mostly successful on simple structures, with less than 18 instructions overall. However, their failure cases (see Task (iii)) were severe, and their limited success on Task (v) relied on repeating previous inputs instead of an external memory or abstraction abilities.
Moreover, it is important to highlight that, even without hallucinations, the CoT LLMs are
ad hoc
unable to resolve underspecification (Task iv), as they could not ask clarification questions. Agentic approaches do much better in the demanding ENVIRONMENT tasks, as they can parse multiple objects, exploit user feedback, and retrieve objects more efficiently.

The agentic LLM baseline and COCORELI both excel in tasks for single instruction placement (Tasks (i) and (iv)), without the hallucination pitfalls of the CoT LLMs. Concerning Task (ii), the agentic model did better than our system in identifying the two parts’ properties; however, on more complex structures, such as in Tasks (iii) and (v), COCORELI outperformed the agentic LLM, by retrieving relational graphs, reducing the task to parsing, not reasoning. Regarding the Moroccan bridge structure in Task (iii), a very complex structure that involves learning a new shape, the agentic LLM failed completely. Additionally, it was unable to recreate complex structures with more than 3 instructions in Task (v). We conclude that the agentic LLM has limited abilities compared to COCORELI, even with an LLM nine times larger than the one used by COCORELI.

Finally, concerning the tasks with underspecified instructions (Task (iv)), the superiority of the clarification loop approach was apparent. The COT systems were unable to resolve underspecifications and hallucinated. Meanwhile, the agentic LLM used the clarification loop when a single instruction was involved (Table
5
) but showed significant problems when presented with a sequence of underspecified instructions. This did not pose a problem for COCORELI, which used the clarification loop well with a series of instructions.

Learning new functions in context in ToolBench

To showcase COCORELI’s versatility, we conducted an additional experiment on in-context function learning as in Task v, but using the ToolBench data set
(
Qin et al. 2024
)
. ToolBench is a dataset for evaluating unsupervised tool learning, featuring a library of functions to access APIs of different websites and functionalities. As this task was primarily one of memory and not of task complexity, we compared COCORELI to our single-LLM CoT baselines (see Section
5.1
).

Data

We first extracted 100 workflows from the dataset, i.e., a sequence of user instructions, actions, and one or more API functions to fulfill the user’s request. We ensured that they include a descriptive user instruction and an associated API function with at least two variables (non-boolean), in order to evaluate the abstractive abilities of our systems. For example, the user input “
Schedule a meeting with Alex tomorrow at 3 pm and send a confirmation email.
” leads to the functions
create_event(q, time)
and
send_email(q, message)
. These functions are abstract and can be reused with different variables.

Methodology

We provide: (1) the complete ToolBench workflow, with the user instruction and corresponding API function, and (2) new information. We then ask the system to call the API function with the new information.
We made some adjustments to the COCORELI agent prompts: first, it parses the workflow instruction with the Instruction parser, then the Builder outputs a structured representation,
workflow_i
, along with the corresponding arguments (e.g.,
arg1: address
,
arg2: message
). The Builder is then given in the conversation a phrase
this is an XX shape
which it learns to interpret as a command to abstract and to store the abstracted
workflow
a
_i
in the External memory. Thus, COCORELI can reapply
workflow
a
_i
to new parameters. The single-LLM baseline CoT model (Claude 3.5 Sonnet) was prompted to return the API function with the new parameters.
We tested only on abstraction and generalization, since the baseline is not equipped to handle underspecification as COCORELI does.

8
Conclusion

COCORELI is a novel hybrid agentic approach built with medium-sized LLM agents with a discourse module and external memory. It efficiently parse multiple user instructions, extracts object properties and coordinates (either single objects or complex structures), and in-context learns abstract representations to reuse and adapt as needed. On the ENVIRONMENT tasks, we showed that COCORELI outperformed single-LLM CoT approaches and Agentic LLM only systems, all built with much larger LLMs. It was able to avoid hallucinations, identify missing information, ask the user for clarifications, and update its learned objects. COCORELI’s abstraction abilities extend beyond the scope of ENVIRONMENT, as it was successful in the ToolBench API completion task, unlike the baselines.

Limitations

We described a generic approach to agentic systems using abstract-apply functions that support tools through abstraction and application. While the concept is generalizable, its implementation must be tailored to each domain (e.g., ENVIRONMENT vs. ToolBench).
Nevertheless, our current system requires that the API function definitions be formatted in JSON format. Real-world APIs don’t come in this format, so this is an additional step to take into consideration.

Another limitation is that solving the ENVIRONMENT tasks ideally requires multi-modal capabilities. Our system handles only text. Our conversational component only handles one aspect of conversation. The detection of a missing feature in a function specification generates just one clarification question. We need to extend the conversational component to handle multiple
wh
-questions specifying multiple features at once. We also need to extend the system to handle other discourse moves, like correction, and longer question-answer sessions. A full system for human-AI collaborative tasks would also need a robust planning system for handling high-level instructions.
