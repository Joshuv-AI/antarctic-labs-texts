Abstract
. Exact subgraph matching on large-scale graphs remains a challenging problem due to high computational complexity and distributed system constraints. Existing GNN-based path embedding (GNN-PE) frameworks achieve efficient exact matching on single machines but lack scalability and optimization for distributed environments. To address this gap, we propose three core innovations to extend GNN-PE to distributed systems: (1) a lightweight dynamic correlation-aware load balancing and hot migration mechanism that fuses multi-dimensional metrics (CPU, communication, memory) and guarantees index consistency; (2) an online incremental learning-based multi-GPU collaborative dynamic caching strategy with heterogeneous GPU adaptation and graph-structure-aware replacement; (3) a query plan ranking method driven by dominance embedding pruning potential (PE-score) that optimizes execution order. Through METIS partitioning, parallel offline preprocessing, and lightweight metadata management, our approach achieves "minimum edge cut + load balancing + non-interruptible queries" in distributed scenarios (tens of machines), significantly improving the efficiency and stability of distributed subgraph matching.

1.
Introduction

Graph data has become ubiquitous in various domains such as social networks, biological networks, and knowledge graphs. Exact subgraph matching, which retrieves subgraphs isomorphic to a query graph from a large-scale data graph, is a fundamental operation in graph data management. However, this problem is NP-complete
(
5
)
, and scaling it to distributed environments introduces additional challenges including load imbalance, high communication overhead, inefficient caching, and suboptimal query execution order. For example, in a distributed cluster with 10 machines processing a 1B-edge social network graph, uneven shard load can lead to 40% of machines being idle while others are overloaded, increasing query latency by 3-5
\times
compared to balanced states.

Recent advances in Graph Neural Networks (GNNs) have enabled efficient exact subgraph matching. The GNN-PE framework
(
11
)
proposes a path dominance embedding technique that preserves subgraph relationships in the embedding space, ensuring no false dismissals while enabling effective pruning. Specifically, GNN-PE trains GNN models to generate path embeddings where the dominance relationship (
o(p_{q})\leq o(p_{z})
) strictly reflects the subgraph relationship between query paths
p_{q}
and data paths
p_{z}
, allowing index-level pruning with 100% recall. Despite its effectiveness on single machines (e.g., 99.5% pruning power on the US Patents dataset), GNN-PE lacks distributed optimization: (1) it cannot handle load imbalance across machines, leading to resource underutilization and query latency spikes; (2) it does not leverage heterogeneous GPU resources for caching and computation, resulting in inefficient memory management (e.g., 30% of GPU memory is idle in single-machine setups); (3) its query plan selection does not consider pruning potential in distributed partitions, leading to redundant data transmission and validation (e.g., 60% of cross-shard data is invalid candidates).

To address these limitations, we extend GNN-PE to a distributed framework with three core innovations, each addressing a critical distributed challenge:

(1)

Lightweight Dynamic Correlation-Aware Load Balancing
: A multi-dimensional load-aware migration mechanism that fuses CPU (40% weight), communication (30% weight), and memory (30% weight) metrics, combined with label and pruning potential-aware correlation calculation. This mechanism ensures load balance with
<50\text{ms}
migration overhead and guarantees aR-tree index consistency (no false negatives) via CRC32 point-to-point verification.

(2)

Multi-GPU Collaborative Dynamic Caching
: An online incremental learning-based caching strategy that adapts to heterogeneous GPUs (e.g., H100 for model inference, 3090 for feature preprocessing). It uses graph-structure-aware replacement policies (considering path matching contribution and recency) and optimizes cache access priority (master cache → master memory → slave cache → slave memory) to improve hit rates by 15-20% compared to LRU.

(3)

Pruning Potential-Driven Query Plan Ranking
: A PE-score model that quantifies path pruning potential as the product of pruning rate and inverse filtering latency. This model drives query plan ranking to minimize invalid candidate transmission, reducing cross-shard data transfer by 60-70% in distributed partitions.

Our contributions are summarized as follows:
1. We design a distributed extension of GNN-PE that addresses load balancing, caching, and query plan optimization for large-scale graphs (up to 1M vertices), with full compatibility with the original GNN-PE embedding dominance property.
2. We propose a load balancing mechanism with dynamic migration that guarantees aR-tree index consistency. It uses METIS multi-constraint partitioning (edge cut minimization + size balance) and hardware-aware initial deployment to reduce initial load variance to
<10\%
.
3. We develop a multi-GPU collaborative caching strategy with online incremental learning (no offline training). It adapts to heterogeneous GPU performance (e.g., TFLOPS
\times
VRAM normalization) and dynamic query patterns via feature decay (exponential decay with
\tau=300\text{s}
).
4. We introduce a PE-score-based query plan ranking method that optimizes execution order for distributed partitions. It uses XGBoost with adaptive tree count (50-300 trees) to predict pruning potential, ensuring
<1\text{ms}
inference latency per path.
5. Extensive experiments on real (DBLP, Youtube, US Patents) and synthetic (Newman-Watts-Strogatz) graphs validate that our method outperforms baselines by 1-2 orders of magnitude in query latency and 2-3
\times
in throughput.

The remainder of this paper is organized as follows: Section 2 reviews related work. Section 3 presents the distributed GNN-PE framework and core concepts (e.g., shard definition, load metrics). Sections 4-6 detail the three innovations, including algorithm implementations and key optimizations. Section 7 describes experimental evaluation with comprehensive parameter tuning. Section 8 concludes the paper.

2.
Related Work

2.1.
Exact Subgraph Matching

Exact subgraph matching algorithms are typically categorized into join-based
(
1
;
2
)
and backtracking-search-based
(
4
;
6
)
approaches. Join-based methods (e.g., Emptyheaded
(
1
)
) decompose the query into paths and join candidate paths using relational operators, but suffer from high intermediate result costs in distributed environments (e.g., 10
\times
more intermediate data than single-machine setups). Backtracking methods (e.g., TurboISO
(
7
)
) explore the search space recursively with adaptive matching orders, but lack scalability for large graphs (e.g., cannot handle graphs with
>100\text{K}
vertices in distributed clusters).

GNN-based methods have recently emerged for exact matching. GNN-PE
(
11
)
uses path dominance embeddings to preserve subgraph relationships, enabling efficient pruning with no false dismissals. It builds aR-tree indexes on path embeddings to reduce query latency by 80% compared to traditional methods. However, it is designed for single machines and does not address distributed challenges like load imbalance. CECI
(
3
)
uses compact embedding clusters for scalable matching, but lacks load balancing and GPU optimization—its cache hit rate is 10-15% lower than our strategy on large datasets.

2.2.
Distributed Graph Processing

Distributed graph partitioning is critical for load balancing. METIS
(
8
)
is a widely used partitioning tool that minimizes edge cuts (e.g., 30% fewer edge cuts than random partitioning), but static partitioning cannot adapt to dynamic load changes (e.g., query spikes cause load skew). Dynamic load balancing methods (e.g., Distributed Timely Dataflow
(
9
)
, Sketch Tree
(
12
)
) migrate partitions to balance load, but most ignore correlation between partitions (e.g., co-occurring shards are migrated to different machines) and index consistency (e.g., aR-tree dominance relationships are broken during migration), leading to high communication overhead (2-3
\times
more cross-shard queries) and false negatives (1-5% of valid candidates are pruned incorrectly).

GPU acceleration in distributed systems has been explored for graph processing. Hybrid
(
10
)
uses GPUs for in-memory subgraph matching, but lacks dynamic caching strategies—its GPU memory utilization is
<60\%
due to static data placement. Our work leverages heterogeneous GPUs for both computation and caching, with adaptive task allocation based on hardware performance (e.g., H100 handles 2
\times
more training tasks than 3090), improving GPU resource utilization to
>85\%
.

2.3.
Query Plan Optimization

Query plan optimization for subgraph matching focuses on minimizing execution cost. TurboISO
(
7
)
uses adaptive matching orders (e.g., high-degree vertices first) to reduce search space, but its order selection does not consider distributed partitions (e.g., paths across 3+ shards are prioritized incorrectly). GNN-PE
(
11
)
employs a cost model based on vertex degrees, but it ignores pruning potential (e.g., low-degree paths with high pruning power are deprioritized). Our work extends this by quantifying pruning potential (PE-score) to rank query paths, adapting to distributed partitions and reducing cross-partition communication by 60-70%.

3.
Preliminaries and System Model

3.1.
Graph Model

We consider a large-scale static undirected labeled data graph
G=(V(G),E(G),L(G))
, where:
-
V(G)
is a finite set of vertices (e.g., users in social networks, proteins in biological networks);
-
E(G)\subseteq V(G)\times V(G)
is a set of undirected edges (e.g., friendships, protein interactions);
-
L(G):V(G)\to\mathcal{L}
maps each vertex to a label from a finite label set
\mathcal{L}
(e.g., "database" for user skills, "enzyme" for protein functions).

A query graph
q=(V(q),E(q),L(q))
follows the same structure. We say
q
is isomorphic to a subgraph
g\subseteq G
(denoted
g\equiv q
) if there exists a bijective function
f:V(q)\to V(g)
such that:
1.
\forall v_{i}\in V(q),L(q)(v_{i})=L(G)(f(v_{i}))
(label preservation);
2.
\forall(v_{i},v_{j})\in E(q),(f(v_{i}),f(v_{j}))\in E(G)
(edge preservation)
(
11
)
.

3.2.
GNN-PE Fundamentals

GNN-PE
(
11
)
is a single-machine exact subgraph matching framework that uses GNN-based path embeddings to enable efficient pruning. Its core components include:
1. **Path Dominance Embedding**: For any path
p\in G
, a GNN model (e.g., GAT
(
Veličković2018
)
) generates a dominance embedding
o(p)\in[0,1]^{d}
(d=2 by default). The key property is: if
p_{q}
(query path) is a subgraph of
p_{z}
(data path), then
o(p_{q})\leq o(p_{z})
(element-wise dominance), ensuring no false dismissals.
2. **Path Label Embedding**: A label embedding
o_{0}(p)\in[0,1]^{d}
encodes vertex labels of
p
, used for label-based pruning (if
o_{0}(p_{q})\neq o_{0}(p_{z})
,
p_{z}
is pruned).
3. **aR-Tree Index**: An aggregate R-tree index is built on
o(p)
and
o_{0}(p)
to enable index-level pruning (e.g., pruning entire index nodes that do not intersect the query’s dominating region).

3.3.
Distributed System Model

Our distributed system consists of
n
worker machines (
n\leq 50
, typical for research prototype scenarios) and 1 central node, with the following design:
- **Worker Machines**: Each machine
C_{k}
is equipped with 1 CPU (e.g., Intel i9-12900K) and 1+ GPUs (e.g., NVIDIA RTX 4090/H100). It stores
m_{k}
shards (
\sum_{k=1}^{n}m_{k}=m
), maintains local aR-tree indexes for stored shards, and processes queries in parallel.
- **Central Node**: Responsible for load monitoring (aggregating
Load(C_{k})
from workers), migration decision-making (selecting source/target machines), and metadata synchronization (updating shard routing information). No direct communication between workers is allowed to reduce overhead.
- **Sharding Strategy**: The data graph
G
is partitioned into
m=50n\sim 100n
shards using METIS. This "ultra-fine-grained" sharding ensures that each shard’s size is small enough for in-memory storage (e.g., 100MB-1GB per shard for
n=10
) and load can be balanced at fine granularity.

4.
Innovation 1: Lightweight Dynamic Correlation-Aware Load Balancing

To address load imbalance in distributed GNN-PE, we propose a dynamic load balancing mechanism with hot migration. This mechanism is designed to be lightweight (migration overhead
<50\text{ms}
), consistent (no aR-tree false negatives), and non-interruptible (queries continue during migration), making it suitable for static undirected labeled graphs.

4.1.
Core Objectives and Design Principles

The mechanism is guided by three key principles:
1. **Multi-Dimensional Load Awareness**: Load is not just CPU utilization—we fuse CPU (40%), communication (30%), and memory (30%) metrics to avoid "single-metric bias" (e.g., a machine with low CPU but high cross-shard communication is still overloaded).
2. **Correlation Preservation**: Shards with high correlation (e.g., high label similarity + frequent co-occurrence in queries) should be co-located to reduce cross-shard queries. This is achieved via label and pruning potential-aware correlation calculation.
3. **Index Consistency Guarantee**: During migration, aR-tree dominance relationships must be preserved to avoid false negatives. We use CRC32 point-to-point verification to ensure data integrity and avoid re-computing embeddings.

4.2.
Core Workflow

The mechanism operates in two phases: offline preprocessing (initialization) and online load balancing (dynamic migration).

4.2.1.
Offline Phase: Preprocessing and Initialization

The offline phase prepares the distributed system for online query processing, with a focus on hardware-aware deployment and static correlation precomputation. This phase runs once before the system starts accepting queries.

1. **METIS Multi-Constraint Partitioning**:
We use METIS to partition
G
into
m=50n\sim 100n
shards with two key constraints:
- **Edge Cut Minimization**: Set
edge\_cut=1
in METIS parameters to minimize cross-shard edges (reduces cross-shard queries by 30-40% compared to random partitioning).
- **Size Balance**: Shard size difference is constrained to
\leq 15\%
(prevents initial load imbalance from oversized shards).
For example, a 10-machine cluster (
n=10
) results in
m=500\sim 1000
shards, each with size 100MB-1GB (for a 100GB data graph).

2. **Hardware-Aware Initial Shard Deployment**:
To ensure initial load balance, we allocate shards to machines based on CPU/GPU performance:
- **CPU Performance Quantification**: For machine
C_{k}
, CPU performance is normalized as:

CPU_{perf}(C_{k})=\frac{Core_{k}\times Freq_{k}\times Bandwidth_{k}}{\max_{t=1..n}(Core_{t}\times Freq_{t}\times Bandwidth_{t})}

where
Core_{k}
is the number of CPU cores,
Freq_{k}
is the CPU frequency (GHz), and
Bandwidth_{k}
is the memory bandwidth (GB/s). This normalization ensures
CPU_{perf}(C_{k})\in[0,1]
.
- **Shard Allocation**: The CPU performance weight of
C_{k}
is
w_{k}=\frac{CPU_{perf}(C_{k})}{\sum_{t=1}^{n}CPU_{perf}(C_{t})}
. The total shard data volume allocated to
C_{k}
is
Size_{alloc}(C_{k})=w_{k}\times TotalSize
, with the constraint:

\max_{k=1..n}Size_{alloc}(C_{k})-\min_{k=1..n}Size_{alloc}(C_{k})\leq 10\%\times TotalSize

For example, if
C_{1}
has
CPU_{perf}(C_{1})=0.2
and
TotalSize=100GB
, then
Size_{alloc}(C_{1})=20GB
—we select a set of shards with total size
\approx 20GB
for
C_{1}
.
- **Correlation-Aware Shard Selection**: During allocation, we prioritize assigning shards with high label similarity (
W_{label}(S_{i},S_{j})\geq 0.5
) to the same machine, reducing initial cross-shard queries by 20-25%.

3. **Static Correlation Precomputation**:
We precompute static correlation metrics between all shard pairs (executed once offline to avoid online overhead):
- **Static Co-Occurrence Count**:
N_{cross}(S_{i},S_{j})
is the number of cross-shard paths that involve both
S_{i}
and
S_{j}
(counted via offline graph traversal).
- **Label Similarity**:
W_{label}(S_{i},S_{j})=\frac{|L(S_{i})\cap L(S_{j})|}{|L(S_{i})\cup L(S_{j})|}
, where
L(S_{i})
is the set of vertex labels in
S_{i}
.
- **Global Statistics**: Precompute
N_{cross,total}
(total cross-shard paths),
\max_{N}N_{cross}
(maximum
N_{cross}(S_{i},S_{j})
), and
\max_{W}W_{label}
(maximum
W_{label}(S_{i},S_{j})
) for online correlation normalization.

4. **GNN Training and aR-Tree Construction**:
GNN models are trained in parallel across machines, with tasks allocated based on GPU performance:
- **GPU Performance Quantification**:
GPU_{perf}(C_{k})=\frac{TFLOPS_{k}\times VRAM_{k}}{\max_{t=1..n}(TFLOPS_{t}\times VRAM_{t})}
, where
TFLOPS_{k}
is GPU computing power and
VRAM_{k}
is GPU memory (GB).
- **Training Task Allocation**: The number of training shards for
C_{k}
is
Train_{num}(C_{k})=\lceil gpu_{w_{k}}\times m\rceil
, where
gpu_{w_{k}}=\frac{GPU_{perf}(C_{k})}{\sum_{t=1}^{n}GPU_{perf}(C_{t})}
. This ensures high-performance GPUs handle more training tasks (e.g., H100 trains 2
\times
more shards than 3090).
- **aR-Tree Construction**: For each shard
S_{i}
, after training the GNN model and generating path embeddings (
o(p)
and
o_{0}(p)
), we build an aR-tree index
I_{i}
and load it into memory. The aR-tree stores the minimum bounding rectangle (MBR) of embeddings for index-level pruning.

4.2.2.
Online Phase: Dynamic Load Balancing and Hot Migration

The online phase runs continuously during query processing, with four key steps: load monitoring, correlation update, migration decision, and hot migration.

1. **Multi-Dimensional Real-Time Load Monitoring**:
- **Worker-Side Monitoring**: Each worker machine
C_{k}
real-time monitors the three load metrics for all local shards
S_{i}\in C_{k}
:
-
U_{cpu}(S_{i})
: Average CPU utilization of
S_{i}
(sampled every 100ms).
-
Comm(S_{i})
: Number of cross-shard queries involving
S_{i}
(counted per second).
-
Mem(S_{i})
: Memory occupancy of
S_{i}
(shard size / total memory of
C_{k}
).
- **Load Aggregation**:
C_{k}
computes its total load using the weighted formula:

Load(C_{k})=0.4\times\sum_{S_{i}\in C_{k}}U_{cpu}(S_{i})+0.3\times\sum_{S_{i}\in C_{k}}\frac{Comm(S_{i})}{Comm_{max}}+0.3\times\sum_{S_{i}\in C_{k}}Mem(S_{i})

where
Comm_{max}
is the maximum
Comm(S_{i})
across all shards (updated every second to avoid magnitude discrepancy).
- **Central Aggregation**: Workers send
Load(C_{k})
to the central node every 500ms. The central node computes the cluster average load
\overline{Load}=\frac{1}{n}\sum_{k=1}^{n}Load(C_{k})
and load standard deviation
\sigma=\sqrt{\frac{1}{n}\sum_{k=1}^{n}(Load(C_{k})-\overline{Load})^{2}}
. Load balancing is triggered when
\sigma\geq 30\%
(indicating significant load imbalance).

2. **Dynamic Correlation Update**:
Correlation between shards is updated online to reflect dynamic query patterns, with a focus on lightweight computation (no global traversal):
- **Dynamic Co-Occurrence Count**:
N_{co-query}(S_{i},S_{j})
is the number of queries in the last
T_{update}=10\text{s}
that access both
S_{i}
and
S_{j}
. We exclude shards in the migration queue (
M_{mig}
) to avoid migration interference.
- **Normalization Factor**:
\eta=\frac{\max_{N}N_{cross}}{\max_{N}N_{co-query}+\epsilon}
, where
\epsilon=10^{-6}
(avoids division by zero) and
\max_{N}N_{cross}
is the offline precomputed maximum static co-occurrence count.
- **Time Decay**: To reduce the impact of outdated correlation, we introduce a time decay factor
\alpha(t)=\max\left(0.7-\frac{0.7t}{T_{decay}},0\right)
, where
t
is the online runtime (seconds) and
T_{decay}=60\text{s}
. This factor decreases from 0.7 to 0 over 60s, weighting dynamic co-occurrence more heavily as time passes.
- **Final Correlation Formula**:

Corr(S_{i},S_{j})=\frac{W_{label}(S_{i},S_{j})\times(A+B)}{C+D+1}\times I(S_{j}\notin M_{mig})

where:
-
A=\alpha(t)\cdot N_{cross}(S_{i},S_{j})
(static co-occurrence term),
-
B=(1-\alpha(t))\cdot N_{co-query}(S_{i},S_{j})\times\eta
(dynamic co-occurrence term),
-
C=\alpha(t)\cdot N_{cross,total}
(static global term),
-
D=(1-\alpha(t))\cdot\max_{N}N_{co-query}
(dynamic global term),
-
I(\cdot)
is an indicator function (1 if
S_{j}\notin M_{mig}
, 0 otherwise).
- **Correlation Threshold**: A threshold of 0.2 is used to classify correlation:
Corr(S_{i},S_{j})\geq 0.2
indicates high collaborative demand (co-locate if possible), while
Corr(S_{i},S_{j})<0.2
indicates low collaborative demand (suitable for migration).

3. **Load Balancing Decision**:
The central node makes migration decisions in four steps to ensure balance and stability:
- **Step 1: Identify Overloaded Machines**: A machine
C_{over}
is overloaded if
Load(C_{over})>L_{tho}=0.8
(machine maximum capacity
Cap=0.85
to avoid overload). The load excess is
\Delta L=Load(C_{over})-L_{tho}
(total load to migrate).
- **Step 2: Determine Migration Count**: The number of shards to migrate (
M
) is determined by the shard load distribution variance (
\sigma_{load}
) of
C_{over}
:
- If
\sigma_{load}<0.1
(shard loads are uniform): Select 75- If
0.1\leq\sigma_{load}\leq 0.3
(moderate load skew): Select 90- If
\sigma_{load}>0.3
(severe load skew): Select 95The migration count is
M=\max\left(\lceil\frac{\Delta L}{U_{quantile}}\rceil,1\right)
, ensuring at least 1 shard is migrated (avoids no-op).
- **Step 3: Rank Candidate Shards**: Shards are ranked by priority to select "migration-friendly" shards (low overhead, low impact on queries):

Priority(x)=W_{load}\times P_{corr}\times P_{size}\times P_{prune}

where:
-
W_{load}=0.5+0.5F
(F is cross-shard query ratio of
C_{over}
; higher F prioritizes high-load shards).
-
P_{corr}=\left(1-\overline{Corr}(x,C_{over}^{local})\right)^{1-F}
(lower correlation with local shards → higher priority).
-
P_{size}=\frac{1}{Size(x)+\epsilon}
(smaller shards → higher priority, reduces migration overhead).
-
P_{prune}=0.8+0.2\times Prune(x)
(lower pruning rate → higher priority, as these shards are more costly to keep).
We select the top
M
shards as the migration candidate set
M_{mig}
.
- **Step 4: Select Target Machines**: Target machines are chosen from light-load machines (
Load(C_{k})\leq\overline{Load}-0.8\sigma
) with 10

C_{target}=\underset{C_{k}}{argmax}\left(\overline{Corr}(x,C_{k}^{local})\cdot(1-Reserved-\frac{Load(C_{k})}{Cap})\cdot\overline{W_{label}}(x,C_{k}^{local})\right)

where
\overline{Corr}(x,C_{k}^{local})
is the average correlation between candidate shard
x
and
C_{k}
’s local shards, and
\overline{W_{label}}
is the average label similarity. This ensures the target machine has sufficient remaining capacity and high correlation with the candidate shard.

Innovation 2: Multi-GPU Collaborative Dynamic Caching

To optimize memory utilization and query latency in distributed GNN-PE, we propose an online incremental learning-based multi-GPU collaborative dynamic caching strategy. This strategy leverages idle heterogeneous GPUs (4
\times

5.1.
Core Objectives and Design Rationale

The strategy addresses three key limitations of existing caching methods:
1. **Heterogeneous GPU Adaptation**: Traditional caching assigns identical tasks to all GPUs, leading to underutilization of high-performance GPUs (e.g., H100 idle while 3090 is overloaded). Our strategy divides tasks by GPU performance to balance load.
2. **Dynamic Query Pattern Adaptation**: Static caching policies (e.g., LRU) cannot adapt to changing query patterns (e.g., sudden spikes in queries for specific paths), leading to low hit rates. Our strategy uses online incremental learning to update cache weights in real time.
3. **Graph Structure Awareness**: Existing methods ignore path structural properties (e.g., matching contribution, degree distribution), leading to caching of low-value paths. Our strategy fuses graph-structural features to prioritize high-value paths.

6.
Innovation 3: PE-Score Driven Query Plan Ranking

To optimize query execution order in distributed GNN-PE, we propose a query plan ranking method based on path pruning potential (PE-score). This method quantifies the "pruning effectiveness + execution efficiency" of each query path, prioritizing paths that filter invalid candidates early and reduce cross-shard data transmission.

6.1.
Core Objectives and Design Motivation

Traditional query plan optimization for subgraph matching (e.g., degree-based order) ignores pruning potential in distributed partitions, leading to two key issues:
1. **Redundant Cross-Shard Transmission**: Paths with low pruning power are executed first, transmitting large volumes of invalid candidates across shards.
2. **High Validation Overhead**: Paths with high filtering latency are executed early, increasing overall query latency.

Our PE-score model addresses these issues by:
- Quantifying pruning potential as a combination of pruning rate (effectiveness) and filtering latency (efficiency).
- Parallelizing feature extraction with GNN training to avoid additional offline time.
- Adapting to ultra-fine-grained shards by incorporating shard-level features (e.g., label diversity, degree distribution).

6.2.
Core Workflow

The method operates in two phases: offline feature extraction and PE-score model training, and online PE-score driven query plan ranking.

This phase runs in parallel with GNN training (no extra offline time), focusing on shard-level feature extraction and model training.

Conclusion

This paper proposes a distributed extension of GNN-PE for efficient exact subgraph matching, addressing three key challenges in distributed environments: load imbalance, inefficient caching, and suboptimal query plan. Our core innovations include: (1) a lightweight dynamic correlation-aware load balancing mechanism with CRC32-based consistency guarantee; (2) an online incremental learning-based multi-GPU collaborative caching strategy adapting to heterogeneous hardware; (3) a PE-score driven query plan ranking method optimizing execution order.

Future work will focus on: (1) extending to dynamic graphs (supporting vertex/edge insertion/deletion); (2) optimizing for low-latency networks (e.g., 5G-enabled clusters); (3) integrating multi-query optimization to further reduce redundant computation.
