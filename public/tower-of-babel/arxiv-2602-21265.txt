ToolMATH : A Math Tool Benchmark for Realistic Long-Horizon Multi-Tool Reasoning
Hyeonje Choi, Jeongsoo Lee, Hyojun Lee, Jay-Yoon Lee

Abstract
We introduce ToolMATH , a math-grounded benchmark that evaluates tool-augmented language models in realistic multi-tool environments where the output depends on calling schema-specified tools and sustaining multi-step execution. It turns math problems into a controlled, correctness-checkable benchmark with tool sets, enabling systematic evaluation of model reliability under (1) large, overlapping tool catalogs and (2) the absence of the intended capability. ToolMATH provides actionable diagnostic evidence of failure modes in tool-augmented agents, helping identify the control mechanisms required for robustness. ToolMATH roughly contains 8k questions and 12k tools; we provide an additional hard-set ToolMATH-Hard with 329 329 questions and 626 626 tools. Our evaluation reveals that the key failure factor is due to the inability to reason, leading to the accumulation of intermediate results’ errors and constrain later decisions. Tool-list redundancy do not simply add noise, but amplify small early deviations into irreversible execution drift. The benchmark highlights that when the intended capability is missing, distractor tools can sometimes serve as partial substitutes in solution paths, yet they can also mislead models into ungrounded tool trajectories. Finally, comparisons between tool-use protocols emphasize that improvements come less from local action selection and more from long-range plan coherence and disciplined use of observations.

Introduction

Tool-augmented language models are increasingly used as interfaces to external APIs, code, and structured utilities
(
9
;

;

;

)
.
In deployment, a model rarely operates with a small, clean tool set; instead it acts within large tool catalogs assembled by retrieval or system design, where multiple tools can appear relevant and where some required capabilities may be absent
(
4
;
6
)
.
We introduce
ToolMATH
, a math-grounded benchmark that converts human-annotated MATH solution steps into reusable Python tools (name, description, typed input schema; code hidden) and pairs each problem with a tool environment that requires multi-step tool composition
(
3
)
.
Since tools are only accessible through natural-language specifications and schemas,
ToolMATH
directly evaluates tool selection and parameterization in long-horizon execution rather than direct access to implementations.
We select mathematics for three reasons. First, its definitive correctness ensures objective automated evaluation. Second, its stepwise logic translates directly into sequential tool-use episodes, where strong logical connectivity rigorously tests the model’s precision. Third, the availability of multiple solution paths allows for diverse tool combinations, uncovering the potential to utilize tools in ways previously deemed inapplicable.

Challenge 1: Long-horizon sequential tool composition.

Realistic tool use is sequential: solving a task can require a multi-step tool-call plan whose intermediate outputs determine subsequent decisions.
This tight logical connectivity makes early tool-choice or argument errors propagate.

ToolMATH
addresses this by constructing each instance as a multi-tool episode derived from stepwise mathematical solutions, and by annotating each problem with a logical-hop measure that summarizes the depth of dependent tool use.
This enables controlled evaluation of long-horizon execution as hop complexity increases, separating short-horizon competence from brittle multi-step dependency tracking.

Challenge 2: Redundancy via overlap among candidate tools.

Real-world tool catalogs often contain many schema-specified tools with overlapping descriptions, so evaluation should reflect performance under large candidate lists with varying degrees of gold–non-gold overlap.
Prior suites often provide limited overlap or small tool lists, making the effect of large candidate pools hard to diagnose in a controlled manner
(
5
;
13
)
.

ToolMATH
addresses this by injecting schema-specified distractor tools and controlling overlap through distractor sampling levels and budgets, producing tool environments that range from category-controlled random sampling to retrieval-based similarity ranking.
This isolates how accuracy changes as the tool list grows and as gold-adjacent candidates become more prevalent.

Challenge 3: Tool insufficiency and safe behavior under missing capabilities.

Tool availability is not guaranteed for every problem: when a needed tool is missing, models must avoid unsupported calls and either solve without tools or recognize they cannot proceed safely under the given interface.
Yet many evaluations assume the gold tool is present, while deployment frequently includes missing-tool scenarios where safe behavior is central
(
6
)
.

ToolMATH
addresses this by introducing a
Distractors-only
regime, where gold tools are removed, and only non-gold tools are provided.
This allows direct measurement of behavior under tool insufficiency (e.g., unsupported tool calls vs. fallback reasoning/abstention) while keeping task correctness objectively checkable.

To make large-scale evaluation reliable,
ToolMATH
applies a sequential validation-and-repair pipeline.
Tool-wise validation checks description–implementation consistency via test-case executions, and question-wise validation retains episodes that are empirically solvable with the translated Python tools under the intended tool-use protocol.
We further perform targeted human audit and repair for ambiguous or inconsistent cases, followed by re-validation.

In summary, we provide the following: (i) A math-grounded benchmark of reusable tools and multi-step tool-composition episodes derived from MATH solutions
(
3
)
, (ii) a validation-and-repair pipeline (tool-wise and question-wise) that improves benchmark reliability at scale, (iii) controlled evaluation regimes that vary hop complexity, non-gold tool’s similarity to gold tools via distractor sampling, and tool insufficiency via Distractors-only settings.

Related Work

Prior work on tool-augmented language models spans learning to invoke tools and APIs, as well as benchmark suites that standardize function-calling formats and evaluation protocols
(

;

;

;

;

.
Another line of work studies deployment-facing failures under imperfect tool access, including missing capabilities and underspecified tasks
(

.
Separately, tool-use methods and agentic interfaces such as ReAct and controller-style systems focus on how models interleave reasoning with actions and orchestrate multi-step interactions
(

.
Finally, structured task generators explicitly model tool dependencies, e.g., via graph-based construction of tool-use tasks

Math reasoning datasets such as GSM8K and MATH provide correctness-checkable targets and naturally decomposed multi-step solution structure
(
1

3

We use MATH’s annotationed solution as a construction substrate: extracting reusable tool primitives from solution steps and forming long-horizon tool-composition episodes with deterministic scoring.

Overall, existing work addresses important aspects of tool use—function-calling standardization and benchmarks, robustness under imperfect tool access, tool-use interfaces/controllers, and structured dependency construction—but typically focuses on one or two axes at a time.

ToolMATH
is unique as a single correctness-checkable benchmark that combines (i) long-horizon multi-step tool composition with tightly coupled intermediate dependencies, (ii) reusable tools derived from ground-truth solution steps, (iii) large tool catalogs with controlled similarity structure via distractors, and (iv) tool-insufficient
Distractors-only
environments for evaluating behavior when the gold capability is absent.
This combination enables systematic analysis of how tool availability, tool-list similarity, and long-horizon execution interact under deterministic scoring.

3
The
ToolMATH
Dataset

We describe the tool set and problem instances that underlie
ToolMATH
, including how we form the final benchmark from complementary validation signals, and how we annotate each problem’s logical-hop complexity for evaluation.

3.1
Overview

Dataset definitions.

We define
ToolMATH
as a collection of tool-grounded problem instances, where each instance is a pair
(p,\mathcal{S}(p))
consisting of a MATH problem
p
and a tool environment
\mathcal{S}(p)
exposed to the model.

Tool specification.

ToolMATH
is derived from the MATH dataset
(
3
)
.
Each tool is defined by:
(i) a
name
(Python function name),
(ii) a
natural-language description
specifying semantics and parameters,
(iii) a typed
input schema
,
(iv) a deterministic
Python implementation
, and
(v) metadata linking it to source problems and solution steps.

We construct extra raw tools from MATH solution steps, then validate them to form the final evaluation set.
After validation, the main benchmark
ToolMATH
contains
12{,}369
tools and
7{,}699
questions.

3.2
Design Objectives

We design
ToolMATH
with three objectives:

Reusability and generality.

Tools should be reusable mathematical operations rather than problem-specific macros, encouraging models to learn transferable tool affordances.

Alignment between descriptions and implementations.

Natural-language descriptions must reflect Python behavior; otherwise, evaluation may misinterpret benchmark noise with model behavior.
Our tool-wise validation addresses this at scale.

Support for multi-step plans with measured hop complexity.

Tools are intentionally low-level.
Solving a problem typically requires calling multiple tools in sequence with strong logical dependence, and we explicitly annotate each problem’s logical hop count to evaluate planning difficulty (Section
3.6
).

3.3
Construction Pipeline

Figure
1
outlines the pipeline from MATH solutions to tools and tool environments.

3.3.1
From MATH Solutions to Tools

We begin from annotated MATH solutions and decompose solution steps into reusable operations.
For each step, we define a tool with (i) a typed signature, (ii) a Python implementation, and (iii) a description that is sufficient for a model to infer correct usage without seeing code.
For extracted tools that are problem-specific or underspecified, we generalize them by abstraction, clarifying constraints and edge cases, and enriching descriptions to reduce ambiguity.

3.4
Validation and Final Dataset Composition

ToolMATH
applies a sequential validation-and-repair pipeline to ensure that benchmark errors are not conflated with model errors.

Step 1: Tool-wise validation.

We validate each extracted tool in isolation to ensure that its description matches its executable behavior.
For every tool, we curate five test schema-valid arguments by trained annotators and execute the tool implementation to obtain outputs.
We then prompt a strong LLM judge (
gpt-4o
) with
only
the tool metadata (description and input schema) together with the inputs and actual outputs, and the judge decides whether each output is consistent with the described semantics.
We allow minor floating-point tolerance and benign formatting differences (e.g.,
int
vs.
float
when numerically equal).
A tool passes tool-wise validation only if it matches on all five cases; otherwise it is discarded from the tool-wise validated set and handled by the downstream repair/audit stage. The system prompt used for the LLM judge is provided in Appendix
E
.

Step 2: Question-wise validation (trace-based).

After tool-wise validation, we perform question-wise validation to identify tools that are
empirically usable
under our tool-use protocol, and to filter questions that admit at least one successful tool invocation in a correct solution.
For each MATH problem
p
, we provide each validator model with (i) the problem statement and (ii) its gold tool set
\mathcal{G}(p)
(tool name, description, and input schema; code hidden), and run the same Plan+ReAct prompt that will be further used in the main evaluation.
A tool
t\in\mathcal{G}(p)
is marked as
question-wise validated
if there exists at least one validator model that (a) produces a correct final answer for
p
and (b) successfully calls
t
at least once in its trace (i.e., selecting
t
from the provided list, supplying schema-valid arguments, and executing without runtime failure).
A question
p
is marked as
validated
if at least one tool in
\mathcal{G}(p)
becomes validated by this criterion.
This trace-based criterion reflects our intended setting where models may combine internal reasoning with tool execution, rather than relying on tools for every step.

Validator set.

We use a fixed validator set:
\mathcal{M}=
{GPT-4o-mini, Llama 3-8B, Mistral-7B, Qwen2-7B, Qwen 2.5-7B, Phi-3 Medium, and Yi 1.5-9B}.

Concretely, let
\mathcal{C}(p,m)
be the set of tools successfully executed by model
m
while solving
p
correctly.
Then the question-wise validated tool set is

\mathcal{T}_{\mathrm{qw}}\;=\;\bigcup_{p}\;\bigcup_{\begin{subarray}{c}m\in\mathcal{M}\\
\mathrm{Correct}(p,m)=1\end{subarray}}\;\mathcal{C}(p,m),

and a question is retained if
\mathcal{G}(p)\cap\mathcal{T}_{\mathrm{qw}}\neq\emptyset
.

Step 3: Targeted human audit and tool repair.

For episodes rejected by question-wise validation, we perform targeted human inspection.
If an episode is solvable, we reinstate it.
Otherwise, we revise the responsible tool(s) by editing descriptions and/or implementations, then re-run tool-wise validation for the modified tools and re-run question-wise validation for affected episodes.
Episodes that remain unsolved after this repair loop are excluded from the final release.

Implementation details.

Full prompts, thresholds, validator set details, and auditing guidelines are provided in Appendix
E
.

3.5
ToolMATH-Hard

To isolate cases where direct answering without tools is unreliable, we additionally curate a
ToolMATH-Hard
.
In such cases, the automatic conversion from solution steps to reusable tools is also more likely to be brittle: extraction can yield tools that are underspecified or misaligned with the intended usage protocol, which in turn makes it unlikely for extracted tools to become question-wise validated.
Concretely, we collect questions for which none of their extracted gold tools become question-wise validated under our trace-based criterion, even after the targeted audit/repair loop, and uniformly sample
329
questions from this set.
We also evaluate
ToolMATH
and
ToolMATH-Hard
to stress-test tool-use frameworks under intrinsically difficult, multi-step computation (Section
5.4
).

3.6
Logical-Hop Annotation

For each problem
p
, we assign a hop count
h(p)
based on the extracted solution structure.
Intuitively,
h(p)
measures how many dependent tool uses are required.
We use
h(p)
as an evaluation axis to separate failures associated with increased overlap between gold and non-gold tools from failures due to long-horizon planning under tight intermediate dependence (Section
5
).

4
Experimental Setup

4.1
Tool-Set Construction and Distractor Settings

We evaluate robustness under both
redundancy
(distractors) and
insufficiency
(Distractors-only).
For each problem
p
, let
\mathcal{G}(p)
denote its gold tool set, and let
\mathcal{U}
be the global pool of filtered and validated tools (used both as gold and distractor candidates).
For distractor–gold similarity level
\ell\in\{1,2,3,4,5\}
and distractor budget
k\in\{5,10,20,50\}
, we sample a distractor set

\mathcal{D}_{\ell,k}(p)\subseteq\mathcal{U}\setminus\mathcal{G}(p),

and expose the model to the tool environment

\mathcal{S}_{\ell,k}(p)\;=\;\mathcal{G}(p)\cup\mathcal{D}_{\ell,k}(p).

We refer to any condition where
\mathcal{G}(p)
is included as a
gold-present
condition (Gold-only and Gold + distractors).
The Distractors-only variant removes the gold tool set and provides only distractors:

\mathcal{S}^{\mathrm{do}}_{\ell,k}(p)\;=\;\mathcal{D}_{\ell,k}(p).

We refer to this as the
Distractors-only
condition: a tool-insufficient environment where the gold tool set is removed, so only distractors remain.

Similarity levels.

We define five distractor sampling levels
\ell\in\{1,\dots,5\}
, each inducing a different candidate distribution over
\mathcal{U}\setminus\mathcal{G}(p)
and thereby controlling how similar distractors are to the gold tools.
At
Level 1 (different-category random)
, we sample from tools whose source-problem category differs from
p
’s category annotated from the MATH dataset.
At
Level 2 (pure random)
, we sample uniformly from the entire pool
\mathcal{U}\setminus\mathcal{G}(p)
.
At
Level 3 (same-category random)
, we sample uniformly from tools originating from the same category as
p
.
At
Level 4 (embedding similarity retrieval)
, we rank candidates by description-embedding similarity to the gold tools.
At
Level 5 (keyword overlap + embedding)
, we rank candidates by keyword overlap with the gold tools and break ties by embedding similarity.
Higher levels, therefore, correspond to increasing semantic overlap with the gold tools, shifting from low-overlap random sampling (Levels 1–3) to retrieval-based high-overlap sampling (Levels 4–5).

Nested distractor guarantee.

For each fixed
(p,\ell)
, we precompute an ordered list of 100 distractors and define
\mathcal{D}_{\ell,k}(p)
as its first
k
elements.
This enforces
\mathcal{D}_{\ell,k_{1}}(p)\subseteq\mathcal{D}_{\ell,k_{2}}(p)
whenever
k_{1}<k_{2}
, ensuring comparisons across
k
reflect increasing distractor density rather than different samples.

Safeguards and reproducibility.

We enforce globally unique tool names by appending suffixes when base names collide (e.g.,
solve_linear_a
,
solve_linear_b
, …).
All sampling is deterministic given a fixed seed and a fixed serialized tool pool.
Full implementation details, including embedding model choice, top-100 retrieval, and the exact nested construction, are provided in Appendix
F
.

4.3
Tool-Use Protocols

Main protocol (Plan+ReAct).

Unless stated otherwise, we use a planning-augmented ReAct protocol
(
15
)
.
The model first writes a brief plan and then alternates between (i) an intermediate reasoning step and (ii) a structured tool call (tool name + JSON arguments conforming to schemas), conditioned on executed tool outputs.
For each run, we log the full tool-call trace and intermediate text.

Additional frameworks.

To evaluate how control strategies affect performance when tools are logically interdependent, we additionally report hard-set results under multiple frameworks, including ReAct - a prompting framework that interleaves intermediate reasoning steps with explicit tool actions
(
15
)
, and DFSDT - a decision-tree search style tool-use protocol via depth-first branching and restart-based backtracking,
(
8
)
, alongside Plan+ReAct.

4.4
Evaluation Conditions and Metrics

We evaluate the following three settings:
Gold-only –
the tool list is restricted to the gold tools,
Gold + distractors –
the tool list contains the gold tools plus
k\in\{5,10,20,50\}
distractors sampled at Level
\ell\in\{1,\dots,5\}
, and
Distractors-only –
the gold tools are removed and only distractors are provided.
We report exact-match answer accuracy after standard normalization.
We also analyze traces via tool-call counts and tool identity distributions.

Human Error Analysis

Beyond aggregate metrics, we perform human error analysis to characterize failure types.
For each evaluation setup, we uniformly sample
100
problems from the same underlying
ToolMATH
and manually label outcomes using the full trace (intermediate reasoning, tool calls, and tool outputs).
We categorize failures into concrete types (Table

We report results along two difficulty axes: (i) distractor–gold similarity level (Levels 1–5) and distractor density (

5.1
Gold-present settings: accuracy over hops and distractor–gold similarity

We aggregate gold-present results across distractor budgets
k

Accuracy degrades nearly monotonically as hop count increases across all similarity levels, and the same trend holds for the No tools baseline.
This confirms that hop count captures intrinsic long-horizon, multi-step difficulty beyond effects from tool-set overlap alone.
Higher similarity levels primarily amplify this degradation at higher hops: while curves are close at low hops (hop 1–2), high-overlap levels steepen the accuracy drop at hop 5+ and separate sharply in the hardest regimes (hop 7 and hop 8+).
This interaction suggests that redundancy is less a direct source of error than an amplifier of planning brittleness under long-horizon compositional dependency.

The Gold-only setting remains near the ceiling at low hops and stays above No tools at moderate hop depths, but performance still collapses for higher hops.
Thus, tool availability is a necessary but insufficient condition: long-horizon plan consistency and correct intermediate dependency tracking remain the bottleneck.
Overall, logical-hop complexity emerges as the dominant difficulty axis, with distractor similarity acting as an amplifying factor rather than the primary driver of failures.

5.2
Failure case analysis

To better understand model behaviors in a gold-present environment with many semantically overlapping candidates, we perform a human failure analysis under the same tool and distractor environment. For each model, we uniformly sample
100

The analysis identifies
Thought Error
as the primary bottleneck with a frequency exceeding 90% across all tested architectures. This prevalence indicates that failures stem from flawed internal reasoning rather than a misunderstanding of tool schemas or API syntax. Even with suitable tools available, models frequently fail to synthesize information or plan logical next steps. This suggests that a fundamental challenge for reliable agents remains underlying reasoning capability instead of execution-level knowledge.

Comparative analysis reveals distinct behavioral profiles among the models. Llama 3-8B exhibits a conservative yet fragile temperament characterized by high rates of
Plan Error
(89) and
Incomplete Execution
(59). It often loses track of long-horizon goals and halts the process prematurely. Conversely, Qwen 2.5-7B demonstrates an impulsive tendency. While it achieves the lowest
Incomplete Execution
(8) by forcing final answers, it records the highest
Observation Omission
(63). This implies that Qwen often bypasses environmental feedback to prioritize task completion over logical accuracy.

Notably, GPT-4o-mini displays a self-correction paradox despite lower overall error rates. It shows a significant vulnerability in
Repeated Call
(67) where it surpasses both open models. This failure mode points to a lack of robust self-correction mechanisms when the model falls into a loop. Despite its advanced capabilities, the model fails to recognize failing strategies and repeatedly executes identical incorrect tool calls.

Beyond model-specific traits, we observe general execution-level brittleness. High frequencies of
Wrong Parameter Value
and
Formatting Error
indicate that maintaining precise data flow remains a significant hurdle. These execution errors often trigger repetitive loops or cause models to omit necessary observations, which further compounds reasoning failures and prevents successful task completion.

For all models, the no tools baseline degrades rapidly with hop count, confirming that long-horizon regimes require effective tool-mediated execution rather than direct answering.
In contrast, tool-augmentation frameworks separate more as hop depth increases, indicating that the dominant bottleneck is how well a method maintains coherent multi-step execution as intermediate results accumulate and constrain later decisions.

A critical regime emerges at higher hops.
At low hops, ReAct, DFSDT, and Plan+ReAct are often close, suggesting that local reasoning with short traces can be sufficient when dependencies are shallow.
However, at higher hops, the gap widens sharply: Plan+ReAct most consistently achieves the strongest results across models, reflecting the value of explicit global planning when error accumulation and execution drift become dominant failure modes.
Importantly, planning does not uniformly help at low hops and can be comparable to simpler frameworks, consistent with planning overhead yielding payoff primarily in long-horizon settings.

DFSDT typically improves over ReAct at intermediate hops, but remains below Plan+ReAct in the long-horizon regime.
This pattern suggests that search-based branching can mitigate some local mistakes, yet lacks an explicit mechanism for enforcing global plan consistency across tightly coupled multi-hop tool sequences.

Finally, framework sensitivity varies by model, but the qualitative trend is stable across datasets.
Llama 3-8B shows the steepest long-hop degradation and the largest dependence on frameworks, while GPT-4o-mini degrades more gradually and exhibits smaller but consistent planning gains.
Qwen2.5-7B attains the highest absolute performance overall yet follows the same qualitative trend: explicit planning becomes increasingly decisive as hop depth grows.

6
Limitations

ToolMATH
isolates tool-use failure modes in a controlled, correctness-checkable setting, but it has the following limitations.
Since the benchmark is math-grounded, it may not capture the ambiguity, underspecification, and open-ended objectives common in other real-world problems.
Also, our tool-wise and question-wise validation reduce noise but do not guarantee correctness across all possible inputs or usage contexts, so the resulting tool and task distributions can inherit biases from the source dataset and extraction procedure, even after validation and hard-set curation.
Finally, results depend on frameworks that include implementation details such as prompting, tool-call formatting, and decoding, so behaviors may differ under other agentic interfaces.

7
Conclusion

We presented
ToolMATH
, a math-grounded benchmark for evaluating tool-augmented language models under realistic multi-tool conditions.

ToolMATH
converts MATH solution steps into a reusable toolbox of Python tools with natural-language descriptions and typed schemas, and applies complementary tool-wise and question-wise validation.
To capture deployment-like difficulty,
ToolMATH
evaluates models in distractor-rich tool environments and in Distractors-only settings, and it further annotates each problem with a logical-hop measure that exposes long-horizon planning failures separately from the effects of increased overlap between gold and non-gold tools.
Together, these design choices enable controlled, correctness-based measurement of robust multi-step tool use and provide trace artifacts that support human error analyses of tool choice, argument filling, plan execution, and fail-safe behavior when tools are missing.

Impact Statement

ToolMATH
is a benchmark for evaluating tool-augmented language models under controlled multi-tool conditions. It aims to improve the reliability and interpretability of tool-use evaluation by using correctness-checkable tasks, validating tool specifications, and stress-testing models under tool-list redundancy and long-horizon execution. This can help surface brittle behaviors and support safer deployment of tool-augmented systems.

We annotate each problem with a

Unlike a raw count of extracted tools, hop count attempts to discount steps that can be carried out in parallel.

Step extraction.

For each (problem, official solution), we first prompt a model to extract a linearized list of high-level solution steps.
These steps are written in natural language and are not tied to any single tool implementation.

Parallelization check and hop construction.

We then build hop groups iteratively.

Otherwise, we create a new hop group and increase the hop count by one.

Appendix F
Distractor Sampling Procedure and Safeguards

This appendix details how we construct distractor tool lists for each problem and difficulty level (Levels 1–5), how we enforce nested inclusion across distractor budgets
k
, and what safeguards prevent accidental gold overlap and tool-identity collisions.

F.1
Global pool and per-problem exclusions

Global pool.

All distractors are sampled from the same global pool
\mathcal{U}
, defined as the union of
filtered and validated
tools (i.e., tools that survive the tool-wise and question-wise filtering/repair pipeline). This ensures distractors are executable and description-consistent under our validation criteria.

Gold removal / self-exclusion.

For each problem
p
, let
\mathcal{G}(p)\subset\mathcal{U}
be its gold tool set.
We form an exclusion pool

\mathcal{U}_{\setminus p}\;=\;\mathcal{U}\setminus\mathcal{G}(p),

implemented by removing any tool instance whose provenance matches
p
’s gold tool instances (using a deterministic tool identifier derived from the tool’s metadata; see
Section

F.6
).
All distractor levels sample only from
\mathcal{U}_{\setminus p}
, preventing accidental inclusion of gold tools.

Problem category.

We assign each problem a broad category
c(p)
(e.g., Algebra, Geometry) using the dataset-provided
type
field.
Each tool inherits a category from its
source_problem
.
We use
c(\cdot)
only to define candidate pools for Levels 1 and 3.

F.2
Level 1–3: category-controlled random sampling

For each problem
p
, we precompute an
ordered
distractor list of length 100 for each level.
Randomness is reproducible via a fixed global seed and a fixed serialized order of
\mathcal{U}
.

Candidate pools.

We define:

\mathcal{U}^{\text{same}}_{\setminus p}\;=\;\{t\in\mathcal{U}_{\setminus p}:c(t)=c(p)\},\qquad\mathcal{U}^{\text{diff}}_{\setminus p}\;=\;\{t\in\mathcal{U}_{\setminus p}:c(t)\neq c(p)\}.

Level 1 (exclude same-category).

We sample 100 tools uniformly from
\mathcal{U}^{\text{diff}}_{\setminus p}
.
If
\mathcal{U}^{\text{diff}}_{\setminus p}
is too small, we fall back to sampling from
\mathcal{U}_{\setminus p}
to ensure a full-length list.

Level 2 (pure random).

We sample 100 tools uniformly from
\mathcal{U}_{\setminus p}
.

Level 3 (same-category).

We sample 100 tools uniformly from
\mathcal{U}^{\text{same}}_{\setminus p}
.
If
\mathcal{U}^{\text{same}}_{\setminus p}
is too small, we fall back to
\mathcal{U}_{\setminus p}
.

With/without replacement.

If the chosen pool has at least 100 candidates, we sample
without
replacement.
Otherwise, we sample
with
replacement (cycling as needed) to produce exactly 100 distractors per level.

F.3
Level 4: embedding similarity retrieval (top-100)

Level 4 selects distractors that are semantically close to the gold tools.

Embedding representation.

Each tool
t
is embedded using the OpenAI embedding model
text-embedding-3-large
.
The embedded text is the concatenation of tool name and description:

x(t)\;=\;\texttt{name}(t)\;\|\;\texttt{description}(t).

Embeddings are
\ell_{2}
-normalized, and we use a cosine similarity.

Gold-to-candidate similarity score.

For a candidate
t\in\mathcal{U}_{\setminus p}
, we define its similarity to the gold set as

s_{4}(t;p)\;=\;\max_{g\in\mathcal{G}(p)}\cos\!\big(e(t),e(g)\big),

where
e(\cdot)
is the normalized embedding.
We then rank all candidates in
\mathcal{U}_{\setminus p}
by
s_{4}(t;p)
in descending order and take the top 100 as the ordered Level-4 distractor list.
If
|\mathcal{U}_{\setminus p}|<100
, we cycle the ranked list to reach length 100.

Caching and efficiency.

We cache tool embeddings and optionally cache top-
K
nearest neighbors per tool to avoid recomputing full similarity against the entire pool.
This does not change the ranking definition above; it only accelerates computation.

F.4
Level 5: keyword overlap + embedding similarity (lexical-first ranking)

Level 5 prioritizes tools that are both lexically and semantically similar to the gold set.

Keyword extraction.

We define a fixed keyword vocabulary of common mathematical terms (optionally extended with a small manual list).
For each tool
t
, we extract keywords
K(t)
by tokenizing
\texttt{name}(t)
and
description
(t) and retaining tokens that appear in the vocabulary.
We also form the gold keyword union
K(\mathcal{G}(p))=\bigcup_{g\in\mathcal{G}(p)}K(g)
.

Lexical overlap score.

For each candidate
t\in\mathcal{U}_{\setminus p}
, define

o(t;p)\;=\;\big|K(t)\cap K(\mathcal{G}(p))\big|.

Two-stage ranking.

We rank candidates by the tuple
(o(t;p),\,s_{4}(t;p))
in descending order (lexical overlap first, embedding similarity as tie-breaker).
Candidates with zero overlap remain eligible but are ranked below candidates with positive overlap.
We then take the top 100 (cycling if needed) as the ordered Level-5 distractor list.

F.5
Nested distractor guarantee across budgets
k

For each problem
p
and level
\ell\in\{1,2,3,4,5\}
, we precompute an ordered list of 100 distractors,

\mathbf{L}_{\ell}(p)=\big[t_{1},t_{2},\dots,t_{100}\big].

For a distractor budget
k\in\{5,10,20,50\}
, we define

\mathcal{D}_{\ell,k}(p)\;=\;\{t_{1},\dots,t_{k}\}.

This construction guarantees
nested inclusion
:
if
k_{1}<k_{2}
, then
\mathcal{D}_{\ell,k_{1}}(p)\subseteq\mathcal{D}_{\ell,k_{2}}(p)
.
For Levels 1–3, the list order is fixed by a deterministic RNG seed; for Levels 4–5, the order is fixed by deterministic ranking.

F.6
Safeguards and collision handling

No accidental gold overlap.

We explicitly remove
\mathcal{G}(p)
from the candidate pool before any sampling or retrieval.
Implementation-wise, each tool instance is tracked by a deterministic identifier derived from tool metadata (including name, description, and implementation reference), and gold-instance identifiers are excluded from the distractor pool for the same problem.

Name collision safeguard (suffixing).

Some extracted tools can share the same base name.
To avoid identity collisions in tool registries and to ensure that retrieval/sampling treats tools as distinct callable actions, we enforce unique tool names by appending a suffix, e.g.,

solve_linear_a
,
solve_linear_b
, … .
This safeguard is applied before constructing distractor pools and remains consistent throughout evaluation.

Determinism and reproducibility.

All randomized sampling uses a fixed global seed and a fixed serialized ordering of the validated tool pool.
Together with cached embeddings and deterministic sorting, this makes distractor lists reproducible across runs given the same validated tool pool.

Common tool-call interface and formatting

Tool visibility.

In all protocols, the model is provided with a list of available tools, each containing

Action JSON constraints.

When a tool is called, the model must emit exactly one

Duplicate-call guardrail.

Across protocols, we disallow repeating the exact same

Answer format.

All protocols terminate by outputting a single line:

For ReAct and Plan+ReAct, we cap the solver loop at
16
model steps (i.e., up to 16 assistant generations in the tool-use loop after initialization).
Since each step permits at most one
Action
line, this also bounds the number of
executed
tool calls by 16 (duplicate calls are intercepted by a cache and do not re-execute the tool).

Wall-clock timeouts.

We enforce a per-question wall-clock timeout of
120 seconds
.
Separately, each tool execution is protected by a per-call timeout of
60 seconds
; if exceeded, the observation is set to an error message and the run continues until termination or the question timeout is reached.

Duplicate-call cache and enforcement.

We cache tool results keyed by
(\texttt{name},\texttt{arguments})
, using a canonical serialization of
arguments
(sorted keys and normalized numeric forms).
If the model repeats an identical call, the environment returns a cached observation instead of re-executing the tool and issues an explicit reminder not to repeat identical actions.
After multiple repeated identical actions, further identical actions are ignored and the model is instructed to proceed to the next reasoning step or output
ANSWER
.

Action parsing robustness.

If the emitted
Action
JSON is malformed, the environment returns an explicit error observation and continues the loop.
If the model produces repeated non-progressing steps (e.g., repeated malformed actions or repeated duplicates), the environment injects a short reminder to follow the one-
Thought
-per-turn constraint and to reuse cached observations.

LLM call retries (API robustness).

All LLM calls (planner, solver, and judge) use a retry wrapper that attempts up to
5
retries on transient API errors (e.g., rate limits or timeouts) with exponential backoff (base
0.8
) and jitter.
If retries are exhausted, the episode is terminated and counted as incorrect/no-answer depending on whether a valid final answer was produced.

DFSDT restarts and diversity.

In DFSDT, when the model emits
Finish(return_type="give_up_and_restart")
, the controller restarts from the root state under the same global budgets.
When revisiting the same search state, the controller provides the diversity prompt listing previously tried action candidates from that state and requires the next proposed action to differ from them.

G.6
Decoding, temperatures, and guardrails

Decoding / temperature.

We use near-deterministic decoding for the solver across protocols with
temperature
=0.0
to reduce variance in execution traces.
In Plan+ReAct, the planner uses
temperature
=0.2
to encourage concise but non-degenerated plan drafts, while the subsequent solver remains at
temperature
=0.0
.
The LLM-based answer grader also uses
temperature
=0.0
.

Formatting guardrails.

All protocols require strict adherence to the one-line
Thought: ...
format per step.
If a tool is needed, the model must emit exactly one additional line

Action: { "name": ..., "arguments": {...} }

and then wait for the environment
Observation
.
The environment validates that the
Action
payload is parseable (JSON-first, with a permissive fallback) and returns explicit error observations when parsing fails.

Execution guardrails.

We enforce (i) per-tool and per-question timeouts, and (ii) cache-based prevention of exact duplicate tool executions, as described in Appendix
G.5
.
