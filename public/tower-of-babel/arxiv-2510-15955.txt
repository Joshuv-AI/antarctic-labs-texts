How Good Are LLMs at Processing Tool Outputs?
Kiran Kate, Yara Rizk, Poulami Ghosh, Ashu Gulati, Tathagata Chakraborti, Zidane Wright, Mayank Agarwal

Abstract
Most realistic task automation problems require large language models (LLMs) to call tools, which often return complex JSON responses. These responses must be further processed to derive the information necessary for task completion. The ability of LLMs to do so is under-studied. In this paper, we study the tool response processing task and LLMs’ abilities to process structured (JSON) responses. We created a dataset for this task, and evaluated 15 open and closed weight models using multiple prompting approaches 1 1 1 https://github.com/LongFuncEval/toolJSONprocessing . Our results show that JSON processing remains a difficult task even for frontier models across multiple prompting strategies. The optimal response processing strategy depends on both the nature and size of the tool outputs, as well as the complexity of the required reasoning. Variations in processing approaches can lead to performance differences ranging from 3% to 50%.

Introduction

Tool-augmented large language models (LLMs)
(
Qin et al. 2023
;
Li et al. 2023
;
Xu et al. 2023
;
Lu et al. 2025
;
Shen 2024
)
can perform tasks beyond their parametric knowledge by calling external tools.
A typical multi-turn tool-calling scenario is shown in Figure
1
. Given a user’s request, an LLM may need to use multiple tools in sequence to address it. Each tool call generated by the LLM is executed and the tool returns data that contains information useful for either responding to the user or for performing the next steps leading to the final answer. Real-world enterprise tools may be existing REST APIs which return large JSON objects as their response
Qin et al. 2024
;
Zhong et al. 2025
. The process of extracting useful information from their response, then, becomes non-trivial.

A common approach is to simply append the tool response to the LLM context
(
Yao et al. 2023
)
. This works well for scenarios with small and simple tool outputs
(
Li et al. 2023
;
Liu et al. 2024b
;
Basu et al. 2025
)
. For real-world APIs with long and complex outputs, the response is either added as is or is pruned to fit in the context
(
Qin et al. 2023
;
Zhong et al. 2025
)
. Sometimes, LLMs are used to summarize the tool output
(
Aksitov et al. 2023
)
or to generate code to process it
(
Song et al. 2023
)
.

When building real-world agentic systems, it is crucial to understand which of these tool response processing approaches works best. This analysis remains a gap in the literature despite the existence of many works focused on understanding LLMs’ tool selection and end-to-end task execution abilities.
In this paper, we address this gap by isolating the tool response processing task, creating an evaluation dataset, and analyzing LLMs’ performance.

The task is formulated as question-answering (QA) on structured tool responses. Specifically, we consider the JSON response format which is popular among real-world tools
(
Qin et al. 2024
)
.
We manually create the QA dataset based on real tool responses, obtained from RapidAPI
2
2

2

https://rapidapi.com/
.
We evaluate 15 high performing LLMs across model families, model sizes, reasoning abilities and context lengths.
We compare different prompting techniques including prompting the model to generate the final answer versus to generate Python code to parse the JSON, utilizing chain of thought (CoT) reasoning, and adding various arguments (response, schema, etc.) to the prompt.
We structure our analysis across several key dimensions: response length, prompting approach, and question type.

Our experimentation and analysis led to three main conclusions: 1) JSON processing is a non-trivial task even for frontier models (GPT-4o highest accuracy is 77%), 2) models can handle this task better by generating JSON parsing code instead of deriving the answer by looking at the JSON when the processing involves reasoning over the data (ranging from +3% to +50%), 3) including a schema of the structured data in the prompt improves performance (up to +12%), and 4) including even a condensed version of the response is better than excluding the response entirely when it doesn’t fit in the model’s context window. Section
4
provides detailed results and ablation studies.

Our contributions are as follows:

•

We formulated tool response processing as a QA task and created an evaluation dataset;

•

We evaluated 15 open and closed weight models on this task with different processing approaches focusing on 4 main control points;

•

We performed an in-depth analysis of LLM performance and derived practical insights to inform real-world applications.

2
Tool Response Processing

The ability of LLMs to extract and/or derive useful information from tool responses is crucial to the success of end-to-end agentic systems. As shown in Figure
1
, our goal is to isolate the tool response processing component within an agent and evaluate the state of the art approaches for that task.

2.1
Dataset Creation

The task is formulated as a QA task on tool responses. The dataset consists of triplets (tool response, natural language (NL) question, answer) where the tool response is in JSON format and the answer to the question is based on the data in the response. The queries are categorized into one of three types: extractive (returns a value in the JSON given a key), filtering (returns multiple entries corresponding to filtering criteria) and aggregation (combines multiple entries by performing an aggregation operation). Figure
2
shows an example of these three types of questions (with additional examples in Figures
13
,
14
,
15
in the Appendix).

To perform our study, we collected multiple responses from six REST API endpoints from RapidAPI, covering domains such as hotel booking, car rentals, flight seats, SEC filings, and product search. For the travel related endpoints, we extract the API responses from the ComplexFuncBench dataset
(
Zhong et al. 2025
)
. We manually reviewed those responses to understand the JSON structure, created question templates and wrote Python code to retrieve the ground truth answers.

Our dataset contains 1298 QA-samples (Table
1
), with 580 extractive (derived from 14 templates), 394 filtering (18 templates), and 324 aggregation (18 templates) questions. The JSON responses varied in length (averaging 24,000 to 74,000 characters) and complexity.

2.2
Common Approaches

Figure 2:
Tool response processing approaches

We consider multiple processing approaches from the literature
Aksitov et al. 2023
;
Song et al. 2023
, all relying on zero-shot prompting of the LLM. The variations in the approaches, captured in Figure
2
, stem from 4 control points.
(1)
Model output type
: we can instruct the model to either generate the answer from the response (referred to as
answer generation
) or generate Python code to parse the JSON response to obtain the answer (referred to as
code generation
). The latter approach is based on the observation that LLMs are very familiar with the JSON format and are good at generating code. Such generated code is then executed to get the answer.
(2)
Prompt type
: we consider two main templates, one with reasoning instructions (CoT
Wei et al. 2022
), and one without.
(3)
Schema
: we evaluate the prompt template with and without the JSON schema of the response.
(4)
Tool response
: for code generation with schema setups, we consider the impact of including the response (whether in full or a reduced version) vs. excluding it. This enables us to study cases where the response doesn’t fit in the context of an LLM.

We include the example prompt templates in the Appendix
C.3
.
We do not consider approaches based on text summarization or RAG (retrieval augmented generation). During our preliminary testing of such approaches, we observed information loss (particularly in the relationships derived from the structure), reducing our confidence in the suitability of these approaches for JSON processing.

3
Experimental Setup

3.1
Metrics

We evaluate performance on the following three metrics: 1)
Exact match
compares the predicted answer to the ground truth answer with some relaxations such as white spaces, casing, order of elements in lists, duplicates, rounding errors. This metric is often considered the strictest as it penalizes the model for verbose outputs and semantic variations.
2)
Contains
is a disjunction between
exact match
and recall based accuracy (which checks whether the ground truth exists within the predicted answer); this gives us an upper bound on programmatic match.
3)
LLM as a judge
employs an LLM to compare the predictions to the ground truth, mostly focusing on their semantic equivalence; this metric is lenient and has a high false positive rate. We used Llama-3-3-70b-instruct as the judge (see Appendix
C.3
for the prompt).

3.2
Models

We evaluate 13 open weight high performing models (see Table
4
in the Appendix) with varying sizes (8B to 480B+ active parameters) and 2 closed weight models: GPT-4o and Claude-4-Sonnet. Inference is done using greedy decoding with the temperature set to 0 and generate a maximum of a 1000 tokens; all our prompts are zero-shot (see Appendix
C.3
). Since the tool responses in our dataset are large, we only consider models with 65K context or greater.

4
Study Findings

4.1
Impact of Response Length (RQ1)

First, we evaluated whether long responses make the task harder. We designed a controlled setup where we can create a JSON object of a given size from the dataset mentioned in Section
2.1

by merging multiple JSON records from the API responses. The size is indicated by the number of tokens (as per Llama-3-1-70b-instruct tokenizer) and exponentially increases from 10K to 80K tokens.

Figure
3
shows the performance of LLMs based on the
exact match
metric as the JSON response token size is varied. Performance generally declines as response size increases, with GPT-4o experiencing a 7% drop and Mistral-large showing the steepest decline at 91%. LLMs are known to have limitations in handling longer contexts effectively, even for simpler tasks
(
Kamradt 2023
;
Hsieh et al. 2024
)
. This finding confirms the challenge of dealing with tool responses as they become larger.

RQ1
: Does the length of the tool response impact the performance of LLMs?

Insight
: LLM performance degrades as the length of the tool responses increases.

Figure 3:
Exact match accuracy across models with increasing JSON size

4.2
Impact of Answer Location (RQ2)

Long context evaluation of LLMs also includes the impact of the position of the key in retrieval tasks. Behaviors such as lost in the middle
Liu et al. 2024a

and recency bias
Peysakhovich and
Lerer 2023

have been reported on other tasks.

To evaluate the impact of the answer’s position on LLM performance, we note that API responses are typically a list of records of some entity type (e.g., flights in flight search). The position of the answer record in the tool response from the triplets (tool response, natural language (NL) query, answer) in our dataset can be varied. For the 80K token size setting of RQ1, we vary the position of the answer record (p) from 1 to 8.

Results, in Figure
4
, indicate that recency bias was observed in answer position in the JSON (higher values of p denote more recent information). Some models suffered more than others, the performance variation based on position
ranges from 5% (GPT-4o) to 75% (Mistral-large).

RQ2
: Does the location of the answer impact the performance of LLMs?

Insight
: LLMs exhibited recency bias.

Figure 4:
Impact of response position

4.3
Impact of Model Output Type (RQ3)

In the remaining subsections, we evaluate the performance of various prompting approaches and models on the task of processing JSON tool responses. First, we study the impact of the model output type, two possibilities specifically. The first option is to prompt the model to directly process the JSON response and output the answer (termed “answer” in the Figures). The second option is to prompt the model to generate Python code that is then executed to parse the JSON response and return the answer (termed “code” in the figures).

The “answer” and “code” settings in Figure
6
capture the results of this experiment.
As seen from the results, the best performance out of these two options is close to 76%, underscoring the complexity of the task. The performance difference between the two output types ranges from 2% to 47% confirming that output type is an important factor to take into consideration and models such as GPT-oss-120b are able to work with one much better than the other.
In general, the total accuracy when generating code is better for 13 out of 15 models. However, for extractive questions, answer generation is better for 10 out of 15 models including a strong code model such as Claude-4-Sonnet. This shows that the choice of output type is not straight forward and it depends on the type of processing required. As the processing needs become more complex (filtering and aggregation), code generation is more accurate for all the models.

Furthermore, multi-turn conversations increase in length, answer generation based approaches will cause the context to grow much more quickly than code generation based approaches. As such, code generation may be more suitable for longer conversations.
Figure
5
shows the performance of both settings when considering the three metrics: exact match, contains, and LLM as a judge (as defined in section
3.1
). Exact match is a strict metric that penalizes models for any formatting discrepancies. The contains metric serves as an upper bound for the performance of specific approaches.

We observe that when generating the answer, unlike when generating code, the model is more likely to output superfluous text beyond the answer (as indicated in the gap between exact match and contains). This makes it challenging to leverage answer generation in scenarios with strict formatting requirements, such as when the output of one tool must be passed as the input to the next tool. LLM as a judge is often the most lenient of all these metrics. As can be seen, even with the most lenient semantic comparison, performance remains much below 90% across the board.

Figure 5:
Performance comparison showing different metrics. Exact match is the strictest and LLM as a judge is the most lenient.

Figure 6:
Exact match comparing model output types. Models are ordered from left to right in increasing number of active parameters.

RQ3
: How does the model output type impact the LLMs’ performance?

Insight
: Code generation performs better for filtering and aggregation while answer generation is better for extractive.

4.4
Impact of Response Schema (RQ4)

We build on the setup from RQ3 and add the API response JSON schema to determine how the schema impacts the performance of both answer and code generation approaches. The schema captures the structure of the JSON response and information such as data types, default values, and enum values of individual data fields. This experiment is to understand if models are able to use this extra knowledge and perform better. We do this by generating the schema from an API response (see the Appendix for details).

We can see from Figure
6
that both prompting for the answer and code generally benefit from adding the schema information (all 15 for code generation, 7 out of 15 for answer generation). The performance difference is more significant for code generation than answer generation.

Figure
7
shows how the distribution of correct vs. incorrect output varies when we change the setup from answer generation with schema to code generation with schema for GPT-4o (similar distribution patterns were observed for other models). Ideally, we want all the samples that were false to become true (False
\to
True column) and none of the true become false (True
\to
False column). Results show that the filtering and aggregation samples, which were problematic for answer generation, were mostly positively impacted by the change. The extractive category has a significant number of samples going from true to false which is not ideal. Therefore, if it were possible to identify whether a query is extractive, filtering or aggregation, we can route it to the appropriate approach and attain the best of both worlds.

RQ4
: Does adding response schema impact LLM performance?

Insight
: LLM performance improves with addition of schema. Higher improvement for code than answer generation.

4.5
Impact of the JSON Response (RQ5)

Next, we focus on the code generation setup and study the impact of including the API response in the prompt. Specifically, we compare three setups: using the full response (which is not always possible when the response length exceeds the context length), reducing the API response before adding it to the prompt (using a heuristic algorithm described in the Appendix), and not using the response at all (as one could argue the response schema has most of the information needed to generate code).

As seen in Figure
8
, passing the full response achieved the highest accuracy across all models. However, when that is not possible due to context length constraints, using a condensed response is better than not adding a response at all. Upon investigation, we observed that the schema does not always include all the information about the values of the keys that may require the model to include specific Python code to properly parse the API response (e.g., “price” is a string and all the values in the response start with “USD”).

Figure 8:
Response variations

Figure
9
shows the percentage of wrong answers attributed to code failures. This allows us to understand whether the code based approaches are failing at the code execution level or at the logical level. Most models are able to generate executable code, especially the more capable models like GPT-4o and Claude-4-Sonnet. However, as the context grows, so too does the probability of the wrong answers being caused by failing code.

RQ5
: How does the JSON response impact code generation?

Insight
: Adding the full JSON response, whenever the context size permits it, will lead to the best possible performance across most model families.

4.6
Impact of Reasoning Prompt (RQ6)

Another control point is the prompt we pass to the models, particularly related to whether the prompt includes reasoning-based instructions. Since some questions, especially in the filtering and aggregation categories, may require a level of reasoning for the LLM to determine the answer, we investigated the impact of using a CoT prompt.

Figure
10
reports the results for the 15 models we tested; all models are either confirmed or speculated to have been trained on reasoning traces. We also focus on the contains metric since reasoning instructions will cause models to output superfluous text that will disadvantage the exact match metric. Results show that the benefits of CoT depend on the model used. Breaking down the results further based on the type of question (reported in the Appendix) provide a better understanding of CoT’s impact: extractive doesn’t benefit but filtering and aggregation do. We also observe that combining reasoning with answer generation can be a good substitute when code generation is not possible.

Figure 10:
Reasoning-based prompting results

RQ6
: Does CoT impact performance?

Insight
: CoT improves LLM performance on filtering and aggregation questions which require more reasoning.

4.7
Error Analysis (RQ7)

4.7.1
Qualitative Analysis

To understand the kinds of errors made in both answer and code generation setups, we manually annotated 50 failures from GPT-4o and Llama-3-3-70b-instruct. Most of the errors were in 4 categories: 1) misinterpretation of the JSON structure, 2) semantic ambiguity, 3) format misalignment, and 4) code execution failure.

Misinterpretation of the JSON structure led to the model picking a value for the right key but from a wrong record. For example, when asked for area of a hotel room given the type of room, the model answered with area of a different room type.

Semantic ambiguity is common for cases when the JSON has multiple keys that have similar meaning. The hotel room availability endpoint response has three semantically similar keys: “name”, “room_name”, and “name_without_policy”. Such noise is representative of real-world APIs and existing tool evaluation datasets manually remove such ambiguity
Zhong et al. 2025
.

Format misalignment is when models fail to follow a formatting instruction from the prompt. For example, when asked to return just the value for a key, the model returns a small JSON output with the key and value. Many of the questions in the dataset contain explicit formatting instructions.
Frontier models such as GPT-4o make less formatting errors compared to Llama-3-3-70b-instruct.

Common reasons for code execution failure were wrong data type assumptions and incorrect JSON traversal. We expect information such as JSON schema to fix some of these errors and it can be confirmed from Figure
6
.

4.7.2
Simplifying the JSON

To validate our observation that complex and large JSON structures were causing a lot of LLM errors, we simplify the JSON using what we call an oracle projection. Since we have the ground truth code to generate the ground truth answer, we use that code to generate a simplified JSON structure. That projection (for both the schema and the response) is then passed to the LLMs when doing answer generation and code generation.

In Figure
11
, we compare the performance of a subset of the LLM models on the projected schema and response vs. the full schema and response. We see that the simplified JSON does in fact lead to better performance across all models for both answer and code generation settings.

The projection algorithm we used assumes the ground truth is known which is not realistic. As such this projection is an oracle and provides an upper bound on the performance gains we can achieve if we were able to simplify the JSON structure before prompting the LLM. Furthermore, the average number of characters when using full responses was 12x (60,968) higher than the average number of characters when using projected responses (5,056). Therefore, if we can simplify the response, we would also be able to reduce the inference cost while achieving higher accuracy (between 8 and 38 point improvement depending on the model).

Oracle Projection Performance

RQ7
: What are the common types errors observed when LLMs fail?

Insight
: The complexity of the JSON structure, output format and semantic ambiguity are the top three observed errors.

5
Related Work

5.1
Tool Calling Evaluation Datasets

The literature has many datasets created to study tool calling functionality in LLMs and agentic systems. Most focused on evaluating LLMs’ ability to formulate tool calls
Basu et al. 2025
;
Patil et al. 2025
;
Li et al. 2023
.
Others focused on the end-to-end task execution of agents with some data samples included tool calling
Trivedi et al. 2024
;
Zhou et al. 2023
;
Zhong et al. 2025
. None of these datasets enable the detailed evaluation of the tool response processing step.

5.2
Tool Response Processing Approaches

LLMs and tool use has been extensively studied, but most work focuses on the LLMs’ ability to plan and formulate the tool calls correctly
(
Patil et al. 2023
;
Schick et al. 2023
;
Li et al. 2023
)
. Benchmarks using real-world tools
(
Qin et al. 2024
;
Zhong et al. 2025
)
acknowledge long and complex responses;
Qin et al. 2024
uses LLMs to prune parts of a long response and truncates it further to 1024 tokens.
Song et al. 2023
has a code generation component to process API responses, however they do not evaluate that component in isolation or extensively on a large dataset.

Gu et al. 2024
evaluates LLMs on tasks on multiple structured formats including JSON, but their dataset is synthetically generated (failing to capture some properties of real-world tools), and they do not include evaluation of code generation.
Similarly,
Shorten et al. 2024
evaluate LLMs’ abilities to parse JSON responses, showing varying degrees of proficiency. However, their evaluation is restricted to one class of models and direct-prompting only.
While table processing using LLMs fits within the structured output processing space
(
Sui et al. 2024
;
Chen et al. 2024
)
,
tables exhibit flatter structures than JSON structures which are highly nested, making them quite complex for the models to understand.

6
Conclusion

Tool response processing is an important but non-trivial step in a tool-augmented LLM workflow. Understanding the characteristics of such processing and knowing when to use which approach is key to designing an effective system. This paper analyzes structured tool responses approaches and shows that even frontier models have room for improvement. Moreover, the performance varies significantly depending on the type of processing required and the prompting technique used. Our work can serve as guidance on how to approach this task and to drive future performance improvements.

Limitations

Our work deals with a specific challenge in tool-augmented LLMs and hence we focus our experiments on that task. However, it would be important to evaluate the different tool response processing approaches in an end-to-end setting. Moreover, the processing approaches we considered are limited to answer and code generation, but there are other approaches such as RAG on the API response or an agentic approach to code generation.

Ethics Statement

We do not foresee any ethical concerns or opportunities to misuse this work. Furthermore, the data we used (and modified) to evaluate models does not contain any PII or harmful language. One possible consideration is whether the generate code may cause security concerns. However, there is nothing in our task that would prompt an LLM to attempt a security breach since the prompts all related to extracting answers from JSON responses. Whenever code is generated, there is always concern.

Appendix C
Tool Response Processing Approaches

C.1
Reduced Response - Heuristic Approach

In the reduced response settings in RQ5, we reduced the length of the response using a heuristic approach. Given our observation that LLMs still benefit from the response because it includes information missing from the schema (such as sample values), we implement an algorithm that keeps one sample of each unique key. Essentially, we eliminate all lists (by keeping only one element). This allows us to present the structure of the JSON and the dependencies between keys while reducing the length.

Appendix F
Practitioner’s Guidance

The suitability of each processing approach depends on multiple factors. When tool responses are particularly large, appending them in a multi-turn setting will soon make the context run out (even for models with large context, 128K and above). Complex JSON structures such as their nesting depth or semantic similarity of their keys also impacts this decision.

Answer generation results in verbose outputs compared to code generation, so the choice depends on whether the downstream usage can tolerate verbosity. Custom parsing of LLM output will almost always outperform a generic parser. However, it may not be feasible to implement a parser for each model, especially as models improve over time and new models are created. Thus, using a generic parser (based on widely used programming languages like Python) becomes desirable.

However, there are some circumstances under which answer generation is the better approach. Namely, when most questions are extractive on simpler JSONs where formatting issues in the LLM output can be tolerated.

F.2
Best Code Generation Model

Furthermore, results show that GPT-OSS-120B was the best overall model for code generation. Thus, whenever possible, using that model to process JSON responses could lead to better results.

F.3
Sandboxing

Finally, it is important to note that we cannot provide any guarantees that the code generated for parsing the responses is safe and trusted. As a precaution against any undesirable consequences from running this code, it would be in the best interest of a practitioner to ensure that execution only happens within a sandbox.

Comparing the average length of predicted responses to the length of the golden response (in terms of number of characters), some models were very verbose despite instructions in the prompt to only return the answer to the question. This was particularly pronounced for extractive questions and certain models. For example, on about 500 samples where the average gold response had an average of 6 characters, answer generation DeepSeek-R1-distill-Llama-70B led to predictions of 1044 characters (on average).

Model output: ""20

Alright, I need to figure out the total number of available rooms of the kind "Atura King Room - Free cancellation" based on the provided JSON data.

First, I’ll look through the "available" array in the JSON. Each object in this array represents a different room type. I’m specifically interested in the rooms where the "name" field is "Atura King Room - Free cancellation".

Looking at the first object in the "available" array, I see that the "name" is indeed "Atura King Room - Free cancellation". The "room_count" for this room is 20.

I’ll check the other objects in the "available" array to see if there are any other entries with the same name. The second object has a different name, "Atura King Room - single occupancy - Free cancellation", so it doesn’t match. The third object is another variation, and the fourth and fifth also have different names.

2.

Often, REST API responses have multiple keys that are semantically similar and it is confusing for LLMs to pick the information from the exact key. For example, the Get_Room_List_With_Availability endpoint from booking.com
produces a response that has three different keys referring to the room name: name, room_name, and name_without_policy. These have different values in them and the models return wrong values due to such confusion.

3.

As mentioned earlier, aggregation operation is harder with answer generation. For example, for the question "List available rooms with gross rate less than 112.89 USD. Output a comma separated list of room names." The models fail to do the comparison in the answer generation setting but such comparison is an easy and precise task for code.

4.

In addition to the answer to the question, models regurgitate the input JSON response or output reasoning or sometimes some ambiguous answers for some questions in answer generation. For example, for the question ’Provide the number of shoes which are available in Black colour.’
The output from the model is:
’Note: The answer is based on the provided JSON data. The product with ID "13857994671980346845" has a "Color" attribute with value "Black".
However, there is another product with ID "16782429352695976508" which has a "Color" attribute with value "Burgundy" and "Maroon" and also has a thumbnail with a product ID "16782429352695976508" which is the same as the product ID of the "Burgundy" and "Maroon" color variant. This product ID "16782429352695976508" is also present in the "Color" attribute of the product with ID "2345888757619488155" with value "Burgundy" and "Maroon".
But there is no product with ID "16782429352695976508" in the provided JSON data.
So, the answer is based on the product with ID "13857994671980346845" which has a "Color" attribute with value "Black".’

5.

As described earlier, models do not follow formatting instructions. For example, for a question where we just want the exact number as output and the prompt explicitly says do not output the unit, it outputs the unit (such as USD if it is a price, LB for weight).

6.

Code generation sometimes produced different logic which led to incorrect answers, partially attributed to ambiguous or convoluted NL queries.
