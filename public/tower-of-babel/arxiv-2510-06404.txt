MuFASA - Asynchronous Checkpoint for Weakly Consistent Fully Replicated Databases
Raaghav Ravishankar, Sandeep Kulkarni, Nitin H Vaidya

Abstract
We focus on the problem of checkpointing (or snapshotting) in fully replicated weakly consistent distributed databases, which we refer to as Distributed Transaction Consistent Snapshots (DTCS). A typical example of such a system is a replicated main-memory database that provides strong eventual consistency. This problem is important and challenging for several reasons: (1) eventual consistency often creates anomalies that the users do not anticipate. Hence, frequent snapshots that can be used to ascertain desired invariants are highly beneficial in their maintenance, and (2) traditional distributed snapshots lead to significant overhead and/or inconsistencies. A key benefit of DTCS is that it summarizes the computation by a sequence of snapshots that are strongly consistent even though the underlying computation is only weakly consistent. In essence, when anomalies arise in an eventually consistent system, DTCS enables one to concentrate solely on the snapshots surrounding the time point of the anomaly. By showing that traditional distributed snapshots lead to inconsistencies and/or excessive overhead, we define the notion of size-minimal DTCS for fully replicated databases. We present MuFASA, an algorithm for a size-minimal DTCS with minimal checkpointing overhead (only O ⁡ ( n ) O(n) new messages and the addition of a single counter for existing messages). MuFASA also provides a significant benefit over existing checkpointing algorithms for distributed systems and replicated main-memory databases by being a fully asynchronous protocol.

Defining Checkpoint Consistency for a Replicated Database

3.1
Limitations of existing checkpoint approaches

A snapshot (or checkpoint) of a process saves the relevant state of the process so that its execution can resume from that point. In the most general case, it may include the entire state (memory, open files, registers, and so on). Often, a subset of this data is sufficient. In the context of a database, the relevant data is the state of the database and information about the completed (committed) transactions.

Extending the snapshot to a distributed system requires that the (local) snapshots of individual processes respect
message causality

Furthermore, the global snapshot captured must be such that (1) it can be reached from the initial state of the system, and (2) the current state of the system can be reached from the captured global state
[
3
]
.

Extending the notion of a checkpoint in the context of transactions (on a single machine) also introduces additional challenges. Specifically, the checkpoint needs to be
transaction-consistent
, i.e., the captured checkpoint is a state of the database that contains the effect of all committed transactions and none of the uncommitted transactions at the time the checkpoint was taken
[
6
]
.

Combining the requirements from
[
3
,
6
]
allows one to define a checkpoint in a distributed (multi-machine) database. By ensuring that the snapshot of each process is transaction-consistent, and that the time-ordering of: committed transactions of a checkpoint, the checkpointed time (which we will later refer to as a point of consistency), and the remaining transactions respects message causality.
In the next section, we use the above requirements to define the notion of a snapshot/checkpoint in a replicated database system.

3.3
Challenges in Checkpointing Asynchronously Replicated Distributed Databases

While the definition of a checkpoint is defined by representing a checkpoint as a set of committed transactions, storing a checkpoint as a sequence of transactions is memory-intensive.
A natural way to compress this checkpoint is to store the database state reached by executing all of these transactions. This limits the size of the checkpoint to the size of the database, and for purposes of rollback, the database system can easily revert to a pre-computed database state. Thus, a DTCS for a multi-machine database can be captured by including the state of all the machines and channels that constitute the distributed database.
However, if the database consists of multiple replicas, then a naive checkpoint will consist of multiple redundant copies of the database state (one for each replica).
The goal of this paper is to capture size-minimal DTCS where each object is maintained exactly once.

5
Asynchronous DTCS Algorithm Requirements

In this section, we motivate and identify the requirements of an asynchronous checkpointing algorithm. First, for consistency of state, the stored checkpoint must meet the distributed transaction consistency requirements of
\Cref
sec:DTCC. Second, the algorithm should be size-optimal and have a small message overhead.
Third, to be asynchronous, the database should never quiesce due to the checkpoint. Fourth, to prevent message congestion in replication channels, control messages should not compete with delivery of existing messages.
Furthermore, if it sends any additional (control) messages, then it does not affect the replication communication.
However, this could be achieved if control messages are sent on a separate channel (with eventual delivery). It could also be achieved if the control messages are sent on the same channel, although the application messages should be allowed to
overtake
these control messages.
In summary, an asynchronous checkpointing algorithm must satisfy the following:

1.

DTCS
: The captured checkpoint must satisfy the properties of DTCS. That is, there must exist a vPoGC at which the database could be said to have attained the state stored in the checkpoint captured by the algorithm.

2.

Strict Concision:
The stored checkpoint has only one copy of each object in the database (and does not store any channel states).

3.

Bounded message complexity:
The total number of extra messages sent by the DTCS algorithm and the size of any message exchanged during the DTCS algorithm do not increase with the total number of objects in the database or the number of transactions that have taken place in the system.

4.

Asynchronous:
The DTCS algorithm never quiesces the distributed database.

5.

Congestion Avoidant:
The control messages sent by the algorithm do not delay the replication messages sent by the replicas (such delays could occur if there is a need for FIFO channels or waiting for some control messages before processing replication messages).

The key idea of the algorithm is as follows: Replica

6.4
Proof

The proof of correctness is by proving that the algorithm satisfies all requirements in
\Cref
sec:Requirements.
To show the correctness of MuFASA, we need to show that MuFASA satisfies all 5 requirements listed in
\Cref
sec:Requirements. Of these, requirements 2-5 are immediately observable. Specifically,
strict concision
follows from how we initially capture the database state at
R_{1}
, then only apply the additional remote transactions on this captured state (line
3
in the algorithm). For
n
replicas, the only additional messages exchanged are the
n-1

\tt{CutForCp}
control messages from
R_{1}
and their
n-1
replies (line
3
). Hence, the
number of control messages is bounded to be
2n-2
, and does not depend on the number of objects in the database. Since we only add a bounded number of extra steps to transactions at
R_{1}
and add no additional steps at any other replica, no replica ever stops executing its transactions. Hence, the algorithm is also
asynchronous
. Since the control messages sent are through a separate channel, the algorithm is also
congestion avoidant
on the replication channels.

The proof of requirement 1, i.e., the snapshot captured by MuFASA is a DTCS requires us to show a virtual point of local consistency (
vPoLC
) at each replica that satisfies the formal definition of transaction-consistent checkpoint in
\Cref
sec:DTCC. Then, the n-tuple formed by the individual
vPoLC
at each replica should form a consistent global cut
vPoGC
, so that it can represent the logical vector time at which the snapshot had taken place. In this way, the checkpoint can be represented both as a set and as a virtual event in the distributed system, and can fully satisfy the definition of DTCS.
Due to space constraints, we provide the proof of requirement 1, i.e., the snapshot captured by MuFASA is a DTCS in
\Cref
appendix:correctness.

6.5
Rollback/Recovery

For crash recovery, all replicas start first from the last stored checkpoint. Then they collect all subsequent locally committed transactions present in
\tt{commit\mbox{--}log}
into one list of transactions to be executed by every replica. A replica resumes computation after all transactions in the combined list are committed on top of the checkpointed database. In this way, each replica will gain the effect of all transactions that have taken place up to the point of failure.

7
Discussion

In this section, we explain some interesting properties of MuFASA:

1.

Verification of Stable Properties:
As discussed in
\Cref
sec:DTCC, when DTCS is used to take multiple snapshots, it partitions the computation into
super-transactions
(that consist of transactions between consecutive snapshots) and these
super-transactions
provide strong consistency among them. In other words, DTCS emulates strong consistency in an architecture that fundamentally operates on eventual consistency.
This can be very useful for identifying bugs in the implementations of eventually consistent systems, which are known to be error-prone
[
8
]
.
Additionally, the checkpoint already contains a precomputed state (without additional logs), enabling a quicker scan for invariant checking.

2.

Message Complexity:

MuFASA is designed for checkpointing a fully replicated database.
Each channel has a lot of duplicate replicate messages of the same set of transactions. Hence, MuFASA only focuses on capturing the replicate messages sent to
R_{1}
to obtain a DTCS, avoiding message redundancy.
Moreover, the solution only involves control channels to avoid congestion in the replication channels.
Correctness of MuFASA however does not depend on whether control messages were sent on the same channel as application messages.
We note that some existing algorithms such as
[
3
]
do not work correctly if control messages were sent on a separate channel, as their correctness depends upon the (lack of) reordering between control messages and application messages.

8
Conclusion and Future Work

In this paper, we focused on the problem of checkpointing and recovery of fully replicated database systems with direct applications to main memory databases. Since maintaining strong consistency often leads to high overhead, many of these systems provide weaker consistency models.
It is well known that developing a strong and continuously consistent data store is prone to errors
[
8
]
.
One way to assist the designer in detecting these errors is to take frequent checkpoints to ensure that the desired invariant constraints are satisfied.

DTCS emulates strong consistency in an architecture that fundamentally operates on eventual consistency.
A common problem with eventual consistency is the unpredictability caused by it. One way to address this is to periodically check if certain invariant properties are satisfied. With DTCS, when the invariant is violated, it uniquely identifies the
super-transaction
(transactions since the last snapshot) that caused this inconsistency. In this way, DTCS mitigates the unpredictability of eventual consistency.

To be useful, checkpointing needs to be frequent and of low overhead. Specifically, checkpoint process should be asynchronous and not block the shared memory/database operation in any way. Our checkpointing algorithm achieves this - the overhead on an operation is only to read the color variable of the database (without any locks), temporarily perform copy on writes, and to add the color (2 bits required) to messages sent by the application.

There are hybrid main memory databases that consist of some objects that are synchronously replicated and some that are asynchronously replicated. For example, the username of a website has to be synchronously replicated to avoid duplicate usernames. However, the view count of a website can be replicated asynchronously by making the view count object a CRDT counter
[
17
]
. Our algorithm can additionally be extended to these databases by taking a local snapshot consisting of both types of objects, then taking only the asynchronous update increments upto the colored cut.

There are several future directions for this work. One is extension to partitioned databases and quorum-based replication. Our algorithm made minimal assumptions about the underlying system (e.g., eventual delivery channels, two-phase locking for transactions, etc.). Another extension is to determine if certain relaxations (e.g., loose size minimality, message complexity, etc.)
could help us solve the problem more efficiently.

Appendix A
Subsequent checkpoints

In this section, we explain how subsequent checkpoints can be taken after the first checkpoint is completed. For this, instead of attaching a color to every replicate message, we attach a checkpoint number (
cpNum
) to every message. The number starts from 1. The starting number
cpNum
indicates green color of the messages,
cpNum+1
indicates yellow color and
cpNum+2
indicates red color. For the first checkpoint, we utilize numbers 1, 2 and 3 to stand for colors green, yellow and red. Note that, at the end of the first checkpoint, all messages will contain the checkpoint number 3. Thus, for the second checkpoint, we start from 3, to stand for green (formerly red), 4 for yellow and 5 for red. The third checkpoint will alternate 5 to mean green and so on. All updates to color are instead seen as updates to
cpNum
.

To make duplicate logs have an idempotent effect, we distinguish the
\tt{CpLog}
logs using the current
cpNum
. Upon detecting a
\tt{CpLog}
of a specific
cpNum
, the
\tt{MessageSender}
skips all subsequent
\tt{CpLog}
of any smaller
cpNum
. This ensures that duplicates are not processed and that the system responds only to new checkpoint initiations. The same goes for color change detection in the
\tt{MessageReceiver}
s. When the replica is green (as detected by
cpNum
) only messages with a different
cpNum
, which is of value greater than the replica’s current
cpNum
is used for detecting this change in color. This way, the system can perform checkpoints one after another. When the checkpointer waits for the message counter values, it chooses between red and green counters depending on the current checkpoint number. if
cpNum
is 1 modulo 4, then it uses
\tt{GreenCounts}
, and if
cpNum
is 3 modulo 4, it uses
\tt{RedCounts}
. After waiting for these counters, they will not be incremented before a subsequent checkpoint. So we can safely reset the currently used counter array to 0. As for other variables, instead of resetting
stable\_status
to
not\_available
, we instead swap
not_{a}vailable
and
available
values because in one iteration of the checkpoint
stable\_status
bits of all objects are flipped, so it is faster to change the meaning of 0s and 1s.

It is also worth noting that the
cpNum
counter can be bounded by rotating checkpointing initiation responsibility to different replicas in a round robin format.

Appendix B
Correctness of MuFASA

To show the correctness of MuFASA, we need to show that MuFASA satisfies all 5 requirements listed in
\Cref
sec:Requirements. Of these, requirements 2-5 are immediately observable. Specifically,
strict concision
follows from how we initially capture the database state at
R_{1}
, then only apply the additional remote transactions on this captured state (line
3
in the algorithm). For
n
replicas, the only additional messages exchanged are the
n-1

\tt{CutForCp}
control messages from
R_{1}
and their
n-1
replies (line
3
). Hence, the
number of control messages is bounded to be
2n-2
, and does not depend on the number of objects in the database. Since we only add a bounded number of extra steps to transactions at
R_{1}
and add no additional steps at any other replica, no replica ever stops executing its transactions. Hence, the algorithm is also
asynchronous
. Since the control messages sent are through a separate channel, the algorithm is also
congestion avoidant
on the replication channels.

Next, we focus on proving that the checkpoint
CP
captured by MuFASA is DTCS. To prove this, we first identify the set of all transactions
CP_{set}
whose effects
CP
entail. We then identify a virtual point of global consistency (vPoGC) at which the event
CP_{event}
could be said to have occurred. We then argue that for any transaction T in
CP_{set}
,
T\ {\mathcal{\textbf{hb}}}\ CP_{event}
and for any transaction T not in
CP_{set}
,
CP_{event}\ {\mathcal{\textbf{hb}}}\ T
.

Observation 4
.

At the initiator replica
R_{1}
the time of switching
\tt{ReplColor}
from yellow to red marks the virtual point of local consistency at
R_{1}
, and all locally committed transactions of
R_{1}
before this time are stored in
CP_{set}
and all other transactions are not stored in
CP_{set}
.

Proof.

This is a direct consequence of the CALC
[
16
]
technique used to capture the local state of
R_{1}
.
∎

Observation 5
.

At any non-initiator replica
R_{i}
, all transactions that were committed before the appending of the first
\tt{CpLog}
to the
\tt{commit\mbox{--}log}
are in
CP_{set}
.

Proof.

Initiator Replica
R_{1}
listens to all green and yellow replicated transaction messages from
R_{i}
to include (line
3
), before ending the checkpoint (line
3
). Thus, only the red replicated transaction messages are not included in the checkpoint.
R_{i}
sends a red message only after changing its
\tt{ReplColor}
to red. Note that only the
\tt{MessageSender}
thread of
R_{i}
can do this (line
3
). This is done only after reading the first
\tt{CpLog}
of
\tt{commit\mbox{--}log}
. Hence, all transactions sent before this point are not colored red, and are processed by
R_{1}
as transactions to be included in the checkpoint. We define the logical time of the first
\tt{CpLog}
appended at
R_{i}
to be
vPoLC_{Ri}
. Thus, we have the following for any local transaction
T_{i}
in
R_{i}
:

(\text{$T_{i}$ is committed}\ \land\ T_{i}\ {\mathcal{\textbf{hb}}}\ vPoLC_{Ri})

\rightarrow T_{i}\in CP_{set}

∎

Observation 6
.

At any non-initator replica
R_{i}
, all transactions that committed after the appending of the first
\tt{CpLog}
into the
\tt{commit\mbox{--}log}
are not in
CP_{set}
.

Proof.

Since
\tt{MessageSender}
changes
\tt{ReplColor}
to red upon encountering the first
\tt{CpLog}
, all transactions that got later appended to the
\tt{commit\mbox{--}log}
are sent in red color by the
\tt{MessageSender}
. When
R_{1}
receives the replicated transaction message for these transactions,
R_{1}
will not apply these transactions on the checkpoint (as per line
3
). Mathematically this observation for any local transaction
T_{i}
in
R_{i}
can be summarized as:

(\text{$T_{i}$ is committed}\ \land\ vPoLC_{R_{i}}\ {\mathcal{\textbf{hb}}}\ T_{i})

\rightarrow T_{i}\notin CP_{set}

∎

Observation 7
.

There exists no committed transaction that committed exactly when the first
\tt{CpLog}
was appended into the
\tt{commit\mbox{--}log}
.

Proof.

This follows from the fact that even if there are concurrent
\tt{commit\mbox{--}log}
append instructions into a single file, the operating system entertains one write at a time. Thus, at any Replica
R_{i}
, any local transaction
T_{i}
has the following property:

\text{$T_{i}$ is committed}\rightarrow(T_{i}\ {\mathcal{\textbf{hb}}}\ vPoLC_{R_{i}}\ \lor\ vPoLC_{R_{i}}\ {\mathcal{\textbf{hb}}}\ T_{i})

∎

Observation 8
.

Any local transaction
T_{i}
of a non-initiator Replica
R_{i}
that is in
CP

Proof.

Transactions of
R_{i}

and are committed since they are replicated after being read from the
\tt{commit\mbox{--}log}
. This observation about any local transaction
T_{i}
from a non-initiator replica
R_{i}
can be summarized as:

T_{i}\in CP_{set}\rightarrow\text{$T_{i}$ is committed}\ \land T\ {\mathcal{\textbf{hb}}}\ vPoLC_{R_{i}}

∎

Observation 9

Any local committed transaction

committed after

If

Observation 11
.

The n-tuple formed by the vPoLC from
\Cref
obs:vpolcAtR1 for
R_{1}
and
\Cref
obs:vpolcAtRi for all
R_{i},i\neq 1
form a vPoGC, i.e., they represent a consistent cut for a global snapshot.

Proof.

To prove that it is consistent cut for a global snapshot, we show the following property:

\displaystyle\forall T_{c},T:T_{c}\in CP_{set}\land T\ {\mathcal{\textbf{hb}}}\ T_{c}\rightarrow T\in CP_{set}

We divide the above expression into 4 cases (here
T^{i}
refers to the set of all transactions whose source replica is
R_{i}
):

•

Case 1:

T_{c}\in T^{1}\land T\in T^{1}

This follows from the CALC algorithm
[
16
]
.

•

Case 2:

T_{c}\in T^{1}\land T\in T^{i},i\neq 1

Back-tracing the steps to capture the checkpoint at
vPoLC_{R_{i}}
, due to Mattern’s distributed snapshot approach, the color change of replica
R_{i}
happens only after a new colored message is sent by
R_{1}
. This in turn only happens after the local snapshot from CALC is captured (line
3
). This is in turn only after
T_{c}
is executed in
R_{1}
.

Hence we have :

T_{c}\ {\mathcal{\textbf{hb}}}\ vPoLC_{R1}\ {\mathcal{\textbf{hb}}}\ vPoLC_{Ri}

Since
T\ {\mathcal{\textbf{hb}}}\ T_{c}
,

T\ {\mathcal{\textbf{hb}}}\ vPoLC_{Ri}
,

\Rightarrow T\in CP_{set}

•

Case 3:

T_{c}\in T^{i},i\neq 1\land T\in T^{1}

Tracing the steps to execute
T_{c}
, Due to Mattern’s distributed snapshot approach, the color change of replica
R_{i}
happens from any message causality established after
vPoLC_{R1}
. So, either T happened before
vPoLC_{R_{1}}
or the first message received by
R_{i}
to capture
vPoLC_{R_{i}}
captures
vPoLC{R_{i}}
before consuming this transaction message. T can either be such that
vPoLC_{Ri}\ {\mathcal{\textbf{hb}}}\ T
or
T\ {\mathcal{\textbf{hb}}}\ vPoLC_{R1}
.

In the latter case,
T\in CP_{set}
. The former case is not possible as we have the following contradiction:

vPoLC_{Ri}\ {\mathcal{\textbf{hb}}}\ T

\Rightarrow T_{c}\ {\mathcal{\textbf{hb}}}\ T
, as against
T\ {\mathcal{\textbf{hb}}}\ T_{c}

•

Case 4:

T\in T^{j},j\neq 1\land T_{c}\in T^{i},i\neq 1

For
i=j
, Proof is straight forward, as both happened before
vPoLC_{Ri}
, hence
T\in CP_{set}
.

For
i\neq j
, Observe that every message after
vPoLC_{Ri}
are colored. Hence, when
R_{j}
receives a message after
vPoLC_{Ri}
, it first creates
vPoLC_{Rj}
before consuming this transaction.

Hence we have that:

T_{c}\ {\mathcal{\textbf{hb}}}\ vPoLC_{Ri}\ {\mathcal{\textbf{hb}}}\ vPoLC_{Rj}
.

Since
T\ {\mathcal{\textbf{hb}}}\ T_{c}
,

T\ {\mathcal{\textbf{hb}}}\ vPoLC_{Rj}

\Rightarrow T\in CP_{set}
.

Thus, we have shown that the
n
-tuple, vPoGC =
<vPoLC_{R_{1}},vPoLC_{R_{2}},\cdots vPoLC_{R_{n}}>
represents a consistent cut with respect all transactions in the database.
∎

Theorem 12
.

The checkpoint captured by MuFASA is DTCS.

Proof.

From
\Cref
obs:vpogcCut, we have a virtual point of global consistency at which the event
CP_{event}
(that happened at the vector time vPoGC) could be said to have taken place. Combining Observations
4
and
10
for all replicas
R_{i}
, each local transaction
T_{i}
in
R_{i}
satisfies: and Combining the three observations also gives the following expression for any transaction T in the system:

\displaystyle(T_{i}\in CP_{set}\leftrightarrow(\text{$T_{i}$ is committed}\land T_{i}\ {\mathcal{\textbf{hb}}}\ CP_{event})\ \land

\displaystyle(T_{i}\notin CP_{set}\ \land\text{$T_{i}$ is committed}\rightarrow(CP_{event}\ {\mathcal{\textbf{hb}}}\ T_{i}))

Since we have now shown that this property holds for all replicas, for any transaction T in the system we have:

\displaystyle(T\in CP_{set}\leftrightarrow(\text{$T$ is committed}\land T\ {\mathcal{\textbf{hb}}}\ CP_{event})\ \land

\displaystyle(T\notin CP_{set}\ \land\text{$T$ is committed}\rightarrow(CP_{event}\ {\mathcal{\textbf{hb}}}\ T))

Thus, CP satisfies the definition of DTCS.
∎
