Deployability-Centric Infrastructure-as-Code Generation: An LLM-based Iterative Framework
Tianyi Zhang a † \dagger , Shidong Pan b,c † \dagger , Zejun Zhang d , Zhenchang Xing a,e , Xiaoyu Sun a *

Abstract
Infrastructure-as-Code (IaC) generation holds significant promise for automating cloud infrastructure provisioning. Recent advances in Large Language Models (LLMs) present a promising opportunity to democratize IaC development by generating deployable infrastructure templates from natural language descriptions, but current evaluation focuses on syntactic correctness while ignoring deployability, the fatal measure of IaC template utility. We address this gap through two contributions: (1) IaCGen, an LLM-based deployability-centric framework that uses iterative feedback mechanism to generate IaC templates, and (2) DPIaC-Eval, a deployability-centric IaC template benchmark consists of 153 real-world scenarios that can evaluate syntax, deployment, user intent, and security. Our evaluation reveals that state-of-the-art LLMs initially performed poorly, with Claude-3.5 and Claude-3.7 achieving only 30.2% and 26.8% deployment success on the first attempt respectively. However, IaCGen transforms this performance dramatically: all evaluated models reach > > 90% passItr@25, with Claude-3.5 and Claude-3.7 achieving 98% success rate. Despite these improvements, critical challenges remain in user intent alignment (25.2% accuracy) and security compliance (8.4% pass rate), highlighting areas requiring continued research. Our work provides the first comprehensive assessment of deployability-centric IaC template generation and establishes a foundation for future research.

II
Background

II-A

Infrastructure-as-Code

IaC represents a paradigm for managing cloud infrastructure through declarative configuration files, enabling automated provisioning and management of cloud resources. The terms “IaC”, “IaC language”, and “IaC tool” are used interchangeably in the literature to refer to the domain-specific languages designed for infrastructure specification and deployment. Prominent examples include AWS CloudFormation, HashiCorp Terraform, and Azure Resource Manager. Each IaC language provides its own syntax and capabilities for defining infrastructure configurations.
IaC templates
are the configuration files that contain the infrastructure specifications written in a particular IaC language. These templates are typically expressed in declarative formats such as YAML, JSON, or HashiCorp Configuration Language, depending on the target IaC language.

IaC templates are structured around two fundamental components (resource and parameter).
Resources
represent the cloud services and infrastructure components to be provisioned. The term “resources” is used instead of “services” because a single cloud service may expose multiple resource types. For instance, Amazon SNS, a message delivery service, provides four distinct resource types (Topic, Subscription, TopicPolicy, and TopicInlinePolicy). In AWS CloudFormation, resources follow the hierarchical naming convention ‘AWS::ServiceName::ResourceType’, clearly delineating the service provider, service name, and specific resource type.
Parameters
enable template customization by allowing external specification of resource property values. Parameters improve template reusability and flexibility by enabling the same template to be deployed across different environments or use cases with varying configurations. Without parameters, templates would be static and require modification for each deployment scenario.
Resource properties
define the specific attributes and configurations of infrastructure components, analogous to class attributes in object-oriented programming. For example, an “AWS::SNS::Subscription” resource includes properties such as ‘Endpoint’ (specifying the notification destination) and ‘Protocol’ (defining the delivery method). These properties determine the runtime behavior and integration patterns of the provisioned resources.

II-B

Difference Between IaC Tools

Terraform (TF) and CloudFormation (CF) represent two distinct types of IaC tools, each with unique format language, design philosophy, and operational characteristics.
TF uses the HashiCorp Configuration Language (HCL), a declarative language designed with a provider-based architecture that enables multi-cloud deployments across AWS, Azure, Google Cloud, and numerous other platforms
[
17
]
.
While CF uses JSON or YAML to define resources in a hierarchical structure with deep integration into the AWS’s service ecosystem
[
18
]
.
Additionally, CF focuses exclusively on AWS, providing native integration with AWS services, security models, and deployment patterns, including features like AWS-specific intrinsic functions and cross-stack references
[
19
]
.

In addition to the syntactic validity, the program deployability fatally determines real-world IaC template utility.
TF’s stateful architecture requires explicit state management and manual resource cleanup procedures
[
19
]
, making systematic deployability evaluation across hundreds of templates impractical.
Also, TF’s lack of native rollback mechanisms means that failed deployments can leave partially created resources in indeterminate states, requiring manual intervention to restore clean testing environments
[
20
,
21
,
18
]
. These operational constraints might explain why existing TF-based benchmark limit evaluation to static analysis
[
9
]
, leaving the crucial deployability dimension unaddressed.

CF, as AWS’s native IaC language, provides unique methodological advantages that make comprehensive deployability testing feasible.
When deploying a CF template, AWS automatically creates a stack to hold the collection of resources defined in the template
[
22
]
).
Users can create, update, and delete entire resource collections by manipulating stacks, enabling systematic removal of all created resources and restoration of the cloud environment to its initial state through simple stack deletion
[
22
]
.
Therefore, to explore the automated IaC template generation especially for deployability, we focus on the CloudFormation in this paper.

III-A

Benchmark Construction

The dataset construction process (Fig.
3
) follows a systematic and reproducible workflow designed to collect high-quality AWS CloudFormation templates while ensuring adequacy and ethical compliance. Templates are initially sourced from three primary channels: (1) official AWS documentation and sample libraries, including the AWS CloudFormation Sample Templates repository
[
26
]
; (2) repositories within the AWS Samples GitHub organization containing CloudFormation templates
[
27
]
; and (3) GitHub repositories identified through a dataset containing URLs of repositories that use CloudFormation templates
[
28
]
. Ethical considerations are enforced by confirming appropriate licensing (e.g., MIT, Apache 2.0) before inclusion, ensuring that all templates are legally permissible for research purposes.
Following an initial collection of approximately 900 templates, candidates undergo automated pre-processing through a multistage filtering funnel. First, size filtering removes templates that exceed 8,000 tokens or 600 lines, ensuring compatibility with the common LLM generation capacities, resulting in 850 templates.
Next, syntax validation verifies templates for structural correctness using cfn-linter
[
29
]
, yielding 465 valid candidates.

Templates then undergo deployment testing using the AWS SDK boto3 client in a sandbox environment configured with least-privilege IAM roles, reducing the dataset to 200 templates. Finally, a rectification process addresses common deployment failures, including cross-stack dependencies, parameter value completion, missing VPC resources, outdated value references, and dependency ordering adjustments. After rectification, our final dataset comprises 153 high-quality, deployable CloudFormation templates that serve as the foundation for our subsequent IaC generation experiments.

Framework

LLMs have been widely adopted in various code and program generation tasks
[
32
,
33
,
34
,
35
,
36
]
, achieving state-of-the-art performance.
Current LLM approaches commonly treat IaC template generation as a static task
[
9
,
16
]
, failing to capture the iterative refinement process that characterizes real-world IaC development and consequently achieving poor deployment success.
Our framework, IaCGen, addresses this limitation by implementing a deployment-driven approach that enables LLMs to learn from deployment failures and iteratively improve templates until they achieve successful deployment.
As shown in Fig.
3
, IaCGen consists of two modules, Iterative IaC Generation and IaC Deployment, integrated through a tiered feedback mechanism that mirrors real DevOps workflows.
Due to the page limit, we focus on describing the high-level components and

IV-A

Iterative IaC Generation

Briefly, Iterative IaC Generation takes an IaC problem description, written in natural language, as input and produces IaC templates as output through a conversational feedback loop. The process works as follows and the numbers are indicated in Fig.
3
:

1
A problem description prompt is retrieved from the dataset and fed to the LLM.

2
The LLM generates an initial IaC template based on the problem description.

3
The generated template and original prompt are stored in memory (implemented as a variable named
conversation_history
in code).

4
This template is passed to the IaC Deployment module for multi-stage validation.

5
If errors occur in IaC Deployment module, adaptive feedback is generated based on the specific failure point. We will elaborate on the adaptive feedback in Section
IV-C
.

6
This feedback is stored in the conversation history along with previous interactions.

7
The LLM is provided with both the feedback and all previous conversation history to generate an updated IaC template. Steps 2 to 7 are repeated iteratively until either the IaC template successfully passes all three validation stages or the LLM exceeds the predetermined maximum number of allowed attempts.

IV-B

IaC Deployment

This module takes the LLM-generated IaC template as input and validates its soundness through a three-stage deployment.
Similar to manual deployment, this process typically consists of sequential validations, from format verification to schema checking to actual live deployment, with engineers iteratively refining their templates based on error messages
[
37
,
38
,
39
]
.
If an error occurs at any stage, feedback is generated and returned to the Iterative IaC Generation module.
If the template passes all three validation stages, the framework will end with the current IaC template as the final output (step
8
).

Format Verification
.
Most IaC solutions use declarative definition files to specify infrastructure configurations. The syntax for describing IaC usually depends on the requirements of the target platform, with common formats including YAML and JSON.
The first validation stage verifies whether the LLM-generated IaC template conforms to the correct format specification.
As AWS CloudFormation templates written in YAML, we employ yamllint
[
40
]
to validate basic structural correctness, including proper indentation, key-value pair formatting, and quotation usage.

Schema Checking
.
After confirming proper formatting, the second validation stage uses a static analysis tool, cfn-linter
[
29
]
, to verify if the code is correct in CloudFormation syntax.
Although most existing LLM-based IaC frameworks stop after this stage, our approach extends validation to actual deployment testing, which addresses a critical gap in operational viability assessment.

Live Deployment:
.
IaC shares a critical characteristic with traditional programming: code that passes compilation or syntax validation does not necessarily execute successfully at runtime. However, this challenge is particularly acute with IaC because of its unique properties.
Most IaC languages are declarative rather than imperative, specifying the desired end state rather than procedural steps. This fundamental difference creates a validation gap that static analysis alone cannot bridge
[
41
]
. Cloud environments impose numerous constraints that syntax validators cannot fully capture: regional service availability variations, deprecated resource identifiers, and service interdependencies. For example, a syntactically perfect Terraform template referencing an outdated Amazon Machine Image ID will pass linting but fail during actual provisioning. Thus, we employ live deployment validation with the AWS SDK boto3 client, the official toolkit developed by AWS.

IV-C

The Iterative Feedback

Previous research have shown the effectiveness of feedback mechanisms in code generation tasks
[
42
,
43
,
44
,
45
]
.
IaC deployment inherently involves continuous integration and development with cycles of validation and refinement
[
4
,
46
]
.
By integrating a feedback loop mechanism into our framework, we simulate this real-world IaC development workflow while treating LLMs as “human developers”, evaluating not only an LLM’s initial generation capability, but also its error-resolution capacity.
Our feedback design implements a progressive assistance approach that mirrors established DevOps practices for IaC development.
This iterative feedback reflects how cloud engineers typically engage with increasingly specific guidance when resolving deployment errors.

General Feedback
.
It provides high-level error indication by pointing out which validation stage the IaC template failed during the multi-stage validation process described above.
For example, when a YAML syntax error is detected, the LLM might receive: “Based on the evaluation, the template contains YAML Syntax Errors.” as feedback. This mirrors the basic error alerts that developers encounter in CI/CD pipelines, requiring the LLM to diagnose and resolve issues with minimal guidance.

Detailed Feedback
.
It offers more specific guidance by including complete error messages returned by the validation tools (yamllint, cfn-lint, and AWS SDK). For instance, instead of simply indicating a deployment error, the LLM receives the full error message: “An error occurred (ValidationError) when calling the CreateStack operation: Parameters: [KeyName] must have values.” This level of feedback approximates the detailed diagnostic information that developers typically encounter when working with IaC testing tools
[
47
]
and tests the LLM’s ability to interpret technical error information.
Considering the experimental efficiency and practicability, we constrain feedback loops to a maximum of six iterations per stage, with two attempts for general feedback and four attempts for detailed feedback.
The asymmetrical allocation strategy is consistent with the empirical observations and experimental design in previous work
[
48
]
.

Evaluation Metrics
.
The unbiased version of pass@k
[
13
]
is a standard metric used by current benchmarks
[
13
,
54
,
14
]
, which indicates the probability that at least one of the
k
generated samples yields a correct solution.
However, it does not effectively capture the performance of iterative feedback.
To address this limitation, we introduce passItr@n, where
n
represents the maximum number of iterations allowed.
passItr@n indicates the probability that the IaC template is correctly generated before or at iteration
n
.

Unlike pass@k, which evaluates an LLM’s ability to solve a problem by generating multiple independent solutions without feedback on correctness, passItr@n specifically measures how iterative feedback affects an LLM’s ability to converge on correct solutions over time.

This “Error Recurrence” phenomenon suggests that maintaining the conversation history provides a crucial context that enables the LLMs to learn from past corrections and avoid repeating similar mistakes across iterations.

User Intent Matching

•

Required Attributes: the essential configuration parameters associated with these resources, formalized using Checkov’s YAML-based custom policy format.

To manage the annotation workload, we randomly sample 51 instances from the benchmark for this evaluation. The generated IaC templates are then systematically compared against the manually crafted intent specifications to assess user intent matching to the stated requirements.

Security of IaC templates represents a critical concern in cloud computing, as insecure configurations can lead to data breaches, unauthorized access, and compliance violations

VII
Discussion

VII-A

Generalizability of IaCGen

We further test the generalizability of IaCGen on the IaC-Eval benchmark, whose templates are written in Terraform. The evaluation presents inherent methodological constraints due to fundamental differences between CloudFormation and Terraform architectures as discussed in Section
II-B
. Consequently, we limit our evaluation to syntax validation, aligning with IaC-Eval’s original assessment methodology while acknowledging this necessary constraint. We select Claude-3.5 based on its superior performance in our primary experiments.

We observe that IaCGen successfully generalizes to Terraform syntax generation. IaCGen achieves 79.7% passItr@1 accuracy, and 100% passItr@7 accuracy, and uses an average of 1.58 iterations on IaC-Eval. In contrast, IaCGen achieves 100% passItr@5 accuracy and uses an average of 2.53 iterations to generate syntactically valid CloudFormation templates on DPIaC-Eval. This discrepancy likely stems from DPIaC-Eval containing more complex problems compared to IaC-Eval, as evidenced by our benchmark’s higher average lines of code and higher number of average iterations required.
Overall, IaCGen successfully guides LLM in generating syntactically correct templates in both IaC languages, confirming its generalizability across mainstream IaC languages.

VII-B

Lesson Learnt

SE-Inspired LLM-based Framework
.

Our findings suggest that iterative, feedback-driven approaches grounded in principles of Software Engineering (SE) yield superior outcomes in IaC template generation.
Rather than employing heavy prompting engineering or relying on task-specific heuristics, our framework systematically incorporates iterative feedback to guide the model across multiple refinement stages.
This iterative structure mirrors conventional SE practices, such as progressive refinement, requirement validation, and configuration testing.
The alignment with these established methodologies not only improves model outputs but also enhances interpretability and developer trust.
Heuristics from SE may serve as a robust and generalizable research paradigm for broader AI4SE tasks, bridging the gap between LLM capabilities and practical software engineering workflows.

Vulnerability in IaC Templates
.

As demonstrated in our evaluation, current models, even when guided by structured frameworks like IaCGen, exhibit limited sensitivity to security concerns, potentially leading to vulnerabilities such as data breaches and service outages.
For researchers, this underscores the need for advancing methods that prioritize secure IaC generation.
For practitioners, it is critical to conduct security validation and expert oversight should remain integral to the deployment pipeline.

VII-C

Limitation

While we believe this study makes substantial contributions into the IaC template generation, several limitations should be acknowledged.
Our evaluation includes models available at the time of writing, but the rapid pace of LLM development means that newer models may show different performance characteristics.
Although our benchmark focuses on CloudFormation and we evaluate the generalizabiltiy, with the similar methodology, it can easily extend to other IaC languages such as Azure Resource Manager for Azure, Google Infrastructure Manager for Google and Terraform for multi-cloud environments.
As this is the first benchmark and dataset focused on IaC deployment evaluation, we chose CloudFormation because its nature supports in deployability test.
Our benchmark covers 153 tasks across 58 most commonly used AWS services, but it may not capture the full diversity of real-world infrastructure requirements.
Additionally, our difficulty categorization, while systematic, may not perfectly align with all organizations’ perspectives on complexity.

In contrast, our work focuses on IaC generation and introduces a domain-specific benchmark that emphasizes both syntactic quality and deployability.

IX
Conclusion

IaC generation holds significant promise for automating cloud infrastructure provisioning.
We present IaCGen, a novel LLM-based deployability-centric framework that uses iterative feedback mechanism to generate IaC templates, and introduce DPIaC-Eval, a deployability-centric IaC template benchmark consists of 153 real-world scenarios that can evaluate syntax, deployment, user intent, and security.
Our evaluation reveals that state-of-the-art LLMs initially performed poorly, with Claude-3.5 and Claude-3.7 achieving only 30.2% and 26.8% deployment success on the first attempt respectively.
However, IaCGen transforms this performance dramatically: all evaluated models reach
>
90% passItr@25, with Claude-3.5 and Claude-3.7 achieving 98% success rate.
Our work provides the first comprehensive assessment of deployability-centric IaC template generation and establishes a foundation for future research.
