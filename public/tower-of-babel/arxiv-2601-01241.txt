MCP-SandboxScan: WASM-based Secure Execution and Runtime Analysis for MCP Tools
Zhuoran Tan, Run Hao, Jeremy Singer, Yutian Tang, Christos Anagnostopoulos

Abstract
Tool-augmented LLM agents raise new security risks: tool executions can introduce runtime-only behaviors, including prompt injection and unintended exposure of external inputs (e.g., environment secrets or local files). While existing scanners often focus on static artifacts, analyzing runtime behavior is challenging because directly executing untrusted tools can itself be dangerous. We present MCP-SandboxScan , a lightweight framework motivated by the Model Context Protocol (MCP) that safely executes untrusted tools inside a WebAssembly/WASI sandbox and produces auditable reports of external-to-sink exposures. Our prototype (i) extracts LLM-relevant sinks from runtime outputs (prompt/messages and structured tool-return fields), (ii) instantiates external-input candidates from environment values, mounted file contents, and output-surfaced HTTP fetch intents, and (iii) links sources to sinks via snippet-based substring matching. Case studies on three representative tools show that MCP-SandboxScan can surface provenance evidence when external inputs appear in prompt/messages or tool-return payloads, and can expose filesystem capability violations as runtime evidence. We further compare against a lightweight static string-signature baseline and use a micro-benchmark to characterize false negatives under transformations and false positives from short-token collisions.

II
Background & Threat Model

II-A

MCP Tool Execution Model

We consider an MCP-style agent that invokes external tools as part of its decision loop. A tool is an executable artifact that consumes (i) the agent-provided invocation context and (ii) a set of ambient inputs such as environment variables and files, then produces textual outputs that are fed back into the agent’s prompt. Concretely, we model a tool execution as:

exec(tool,env,data\_dir)\rightarrow(stdout,stderr,exit\_code,dura.)

where stdout/stderr are interpreted by the agent as evidence for subsequent reasoning and tool selection.

A key security observation is that tool outputs are not merely “logs”: in many agents, tool outputs are incorporated into the next-step prompt template (e.g., “Tool said: …”). This creates a high-leverage channel where a tool may inject instructions, override constraints, or induce the agent to exfiltrate secrets.

II-B

Threat Model

Adversary
: We assume the tool binary may be malicious, compromised, or intentionally crafted to manipulate the agent. The goal of adversary is to influence the agent’s downstream behavior, launching prompt injection or instruction hijacking, or to exfiltrate sensitive inputs available at execution time (e.g., environment secrets, local files, or user-provided artifacts).

Attack surface
: We focus on three categories of external inputs that commonly exist in tool execution environments:

1.

Environment sources
: like API keys, user identifiers, system prompts passed via env.

2.

File sources
: a designated data directory mounted for the tool to read.

3.

Network-like intents
: strings suggesting outbound requests; in our current prototype this is treated as an observable intent signal rather than full network mediation.

Security-relevant sinks
: We define sinks as output regions that are likely to be re-inserted into the agent’s prompt or otherwise interpreted as instructions. In practice, a sink may be delimited by known markers (e.g., ”PROMPT:…”), tool schema conventions, or templated wrapper formats. The central risk we aim to detect is external-to-sink flow: data originating from an external source appears in a sink region.

Goals
. Our system aims to:

•

Execute tools under least-privilege constraints (e.g., only a preopened
/data
directory, bounded outputs).

•

Collect lightweight dynamic evidence, covering
stdout/stderr/exit/timing, and source/sink
observations.

•

Produce an explainable report that attributes risky outcomes to specific source
\rightarrow
sink flows.

We do not claim completeness against sophisticated encoding/obfuscation (e.g., encryption, compression) that breaks string-level matching. We also do not fully mediate arbitrary network behavior in the current prototype; instead, we treat network-like patterns as signals and leave full network syscall instrumentation as future work.

Pipeline

Design Rationale

MCP-SandboxScan’s design follows two principles.

(1)
Capability-first execution
. Running tools in WASM/WASI provides a structured capability boundary: file access is granted only via preopened directories, and the runtime can bound outputs to prevent output-based denial-of-service. This reduces the risk that scanning itself becomes a new attack surface.

(2)
Lightweight, explainable dynamic analysis
. Instead of heavy taint instrumentation, we collect minimal runtime signals during sandboxed execution and perform conservative string-level flow inference across observed tool interactions. While this does not guarantee completeness, it yields a practical scanner that can be deployed early and still provides actionable evidence: “which external input appeared in which prompt-sink region.”

IV
Secure Execution & Evidence-based Flow Analysis

This section describes how MCP-SandboxScan safely executes untrusted MCP tools and derives actionable, explainable evidence about runtime data exposures. Our key idea is to
observe
a tool’s interactions with its environment under a capability-restricted sandbox, and then perform
evidence-based
source-to-sink linking between observed external inputs (
sources
) and prompt construction sites (
sinks
). Importantly, our current pipeline is purely dynamic: it does not rely on static pre-screening or heavy taint instrumentation, prioritizing deployability and explainability.

IV-A

WASM-based Secure Execution

Why WASM/WASI.

MCP-SandboxScan executes MCP tools as WebAssembly (WASM) modules under a WASI-compatible runtime. This choice provides a uniform execution substrate across tools and enables the scanner to safely run untrusted code while reliably capturing runtime artifacts (outputs, exit status, and timing) needed for downstream analysis.

Execution interface and run record.

The prototype treats each tool invocation as a single WASM run and produces a structured execution record containing bounded
stdout
and
stderr
, an
exit_code
, and
duration
. This record is the primary evidence carrier used by later stages for sink extraction and intent detection.

Captured external-input candidates.

In the current prototype, external-input candidates are collected as
sources
in a lightweight and execution-driven manner, without relying on fine-grained runtime tracing.
Specifically, after execution the scanner constructs source candidates from three channels:

•

Environment variables.
The scanner treats each provided environment entry as a source candidate, enabling later checks for whether environment-derived secrets or configuration values are reflected in
LLM-relevant sinks
(e.g., prompts/messages or structured tool-return fields).

•

Mounted local files.
When a directory is mounted for the tool, the scanner recursively enumerates regular files under the mount and records their (size-capped) contents as source candidates. This reflects common deployments where tools consume local corpora or workspace artifacts.

•

HTTP fetch intents.
The prototype does not fetch remote content. Instead, it extracts
fetch intents
from runtime outputs by recognizing explicit intent markers (e.g., lines prefixed with
HTTP_FETCH:
,
FETCH:
, or
HTTP:
) and records the referenced URL as an intent-only source.

IV-B

Lightweight Dynamic Observation

The observation layer is designed to be lightweight and explainable. Instead of instrumenting program internals or collecting syscall-level traces, MCP-SandboxScan relies on a small set of boundary-visible artifacts produced by sandboxed execution and performs post-run extraction over these artifacts.

Observed artifacts.

Each run yields a structured execution record consisting of bounded standard output and error streams, an exit status, and elapsed time. These artifacts provide two critical observation channels for the current prototype:
(i) they expose
LLM-relevant payloads
that can be extracted as sinks (e.g., prompts/messages as well as structured tool-return fields), and
(ii) they expose explicit intent markers (e.g., fetch intents) that tools emit for downstream routing.

Observation workflow.

After execution, the scanner performs two lightweight passes:

•

Sink pass.
It scans standard output for (a) marker-based prompt regions and structured prompt/message payloads, and (b) structured
tool-return
payloads by extracting string leaves from JSON outputs.
The pass produces a unified list of sinks (prompt/message sinks and tool-return sinks) for later source–sink linking.

•

Evidence/intent pass.

It scans both standard output and error for explicit intent markers (e.g., HTTP fetch intents) and sandbox-relevant evidence (e.g., permission-denied or policy-violation messages), producing auditable evidence used by later modeling and reporting.

By constraining observation to bounded outputs and post-run extraction, MCP-SandboxScan keeps overhead low and avoids assumptions about tool language or framework. The cost is that it does not observe implicit flows or transformations that do not surface in outputs; however, every reported finding is grounded in concrete, auditable runtime artifacts.

IV-C

Sink Extraction

A central goal of MCP-SandboxScan is to explain
where
external inputs may surface in LLM-relevant content produced by tools. In the current prototype, we operationalize
sinks
as prompt- or prompt-equivalent payloads surfaced in the tool’s standard output during sandboxed execution. This design is intentionally lightweight: rather than intercepting model API calls, we extract sinks from output patterns that commonly encode prompts and tool returns in practice.

Sink definition.

A
sink
is any textual region extracted from standard output that is intended to represent either (i) a prompt/messages payload, or (ii) a structured tool-return field that may be incorporated into subsequent prompts by an agent.
The prototype instantiates sinks in three forms: (i) marker-based prompt lines, (ii) JSON-derived prompt/message fields, and (iii) JSON-derived tool-return string leaves.

Extraction strategy.

The extractor processes standard output line-by-line and applies two rules:

•

Marker-based sinks.
If a trimmed line contains the marker
PROMPT:
, the entire line is recorded as a sink. This captures tools that explicitly print prompt material for debugging, logging, or downstream handling.

•

JSON-derived sinks.
It a trimmed line parses as JSON, the extractor looks for two common prompt encodings:

–

a string-valued
prompt
field, which is recorded as a sink;

–

an array-valued
messages
field, where each element’s string
content
(when present) is concatenated (newline-separated) and recorded as a sink if non-empty.

•

JSON-derived tool-return sinks.
For JSON lines that do not contain
prompt
or
messages
, the extractor collects all string-valued leaf nodes and records them as tool-return sinks (with their JSONPath retained for reporting). To control noise, the prototype applies simple filters (e.g., minimum length thresholds and exclusion of metadata-like paths such as
status
/
id
).

Sink representation.

Each extracted sink retains its category (marker-based, JSON prompt/message, or tool-return leaf) and exposes a canonical textual view used by later matching. For JSON-derived sinks, the textual view is the extracted string value (either
prompt
, concatenated
messages
contents, or a tool-return leaf string); for marker-based sinks, it is the captured output line itself.

Outputs that do not match any rule are ignored. As a result, the prototype focuses on sinks that are explicitly surfaced in standard output, which is sufficient for the tool behaviors studied in our case analyses but does not cover sinks that never appear in outputs.

IV-D

Source-to-Sink Flow Detection

Given extracted sources and sinks, MCP-SandboxScan performs evidence-based linking to determine whether an external input
appears
in LLM-relevant output regions. The prototype therefore derives a small set of candidate snippets from each source string:

1.

after trimming, empty strings are ignored;

2.

if the source string length is at least 4 characters, the full string is included as a candidate;

3.

for longer strings, fixed-length prefixes are added; and

4.

for sufficiently long strings (longer than 48 characters), an additional mid-string window of up to 24 characters is extracted around the center. These snippets are then filtered to remove empty entries.

String-level matching.

For each source, the detector checks whether any generated snippet (with minimum length 4) occurs in the textual view of any sink. When a match is found for a given (source, sink) pair, the detector emits a flow record and proceeds to the next sink without reporting multiple snippets for the same pair. Because matching operates over generated snippets, the detector may flag
partial leakage
when only a substring of a source appears in a sink (e.g., fragmented across multiple tool-return fields). We treat such matches as useful evidence of exposure, and our evaluation separately reports these robustness/false-positive behaviors.

Flow record and deduplication.

Each detected link is summarized as a
FlowMatch
record containing:
(i) a source identifier,
(ii) the sink type (marker-based vs. JSON-derived),
(iii) the matched snippet, and
(iv)a coarse confidence label.
In the current prototype, confidence is
high
when the matched snippet equals the full source string (or a long-window snippet), and
low
for short or prefix-only matches; this distinction helps interpret partial matches and potential false positives.

V
Evaluation

To comprehensively evaluate MCP-SandboxScan under diverse MCP tool scenarios, we design three complementary experiment groups:
(1)
case studies
assessing coverage of LLM-relevant sinks (prompt/messages and structured tool-return fields) and evidence-based source–sink linking,
(2) a
dynamic vs. static baseline
comparison demonstrating scenarios that evade lightweight string-signature scans (obfuscated filesystem access and runtime file exfiltration), and
(3) a
micro-benchmark
probing robustness and limitations, including false negatives (encoding/truncation/filtering) and false positives (short-token collisions) under substring-based matching.

V-A

Experimental Setup

We evaluate the framework using three small WASM tools for case studies (benign prompt construction, prompt-injection-like payload surfacing, and filesystem boundary violations), plus two lightweight fixture suites for evaluation: (i) a tool-return micro-benchmark for robustness/FP-FN behaviors, and (ii) obfuscation and file-exfiltration fixtures for static-vs-dynamic comparison.

Each tool is executed inside the same WASM/WASI sandbox configuration with a bounded output budget for captured standard output and error streams. When a host directory is mounted, file-derived sources are collected with a fixed per-file size cap (64KB in the current prototype). The scanner does not fetch remote content; instead, it records HTTP fetch
intents
when explicit intent markers appear in runtime outputs.

Each run produces a structured report containing: an execution record ((exit status, elapsed time, bounded outputs), a summary (counts of extracted sources, extracted sinks (prompt/messages and tool-return sinks), and detected source-to-sink link records).
A link record is emitted only when a source-derived snippet is observed as a substring of an extracted sink, providing auditable evidence of external input reflection in prompt-like regions.

VI
Discussion & Limitations

MCP-SandboxScan is intentionally evidence-based and dynamic-only in its current form. It links external-input candidates to extracted sinks via snippet-based substring matching, which makes findings easy to audit (each reported flow corresponds to an explicit snippet observed in a sink) but does not constitute full information-flow tracking. As a result, the scanner may miss flows that involve semantic transformations (e.g., encoding, compression, encryption, hashing, or substantial templating), as well as flows that never surface in the output patterns we analyze.

Coverage in the current prototype is bounded by what it observes. Sinks are extracted solely from standard output using marker-based prompt lines and JSON
prompt
/
messages
fields; tools that construct prompts without emitting them, or that use alternative schema, may not be covered. Source modeling is likewise conservative: sources are instantiated from environment-provided values, size-capped mounted file contents, and HTTP fetch intents surfaced in outputs. The HTTP channel is intent-only (no response fetching), so attribution to remote response bodies is out of scope for the current version. Finally, substring matching can under-report when only small transformed fragments appear, and can over-report when short snippets coincide; we mitigate trivial cases with a minimum match length and deduplication.

VII
Related Work

Static MCP Scanning vs Runtime Gap

Prior work on MCP and agent tool security has largely focused on (i) pre-execution auditing of tool artifacts and (ii) orchestration-/workflow-level defenses.
Sha et al.
[
6
]
propose MCPScan, a static-first framework combining rule-based scanning, metadata inspection, and LLM-driven semantic analysis to identify risks such as tool-description poisoning, unsafe file or network access, and cross-file dataflow vulnerabilities.
Benchmark-driven studies on tool poisoning further show that malicious instructions embedded in tool metadata can induce privilege misuse without requiring execution-time exploits
[
10
]
.
At the system level, analyses of MCP highlight confused-deputy style failure modes and broader threat surfaces across the tool lifecycle
[
11
,
12
]
.
Several defenses mitigate these risks through architectural separation or workflow reasoning: CaMel
[
13
]
adopts a dual-model architecture to isolate untrusted inputs from action execution, and toxic flow analysis (TFA)
[
14
]
models attack paths via capability flow graphs over agent workflows.
Security guidelines such as OWASP also recommend trust minimization, least privilege, and sandboxed execution for MCP servers
[
15
]
.
While effective for artifact-level screening and planning-layer guardrails, these approaches cannot fully capture behaviors that arise only during tool execution (e.g., dynamically generated prompts, stdout-encoded control signals, structured tool-return payloads, and environment-dependent effects).

WASM sandboxing & secure execution

WebAssembly has been widely adopted as a lightweight and portable sandboxing mechanism for isolating untrusted code
[
8
]
. Prior work has explored WASM-based sandboxing for serverless computing, plugin isolation, and secure execution environments, leveraging WASI to provide controlled access to system resources while maintaining strong isolation guarantees
[
16
,
17
]
. These systems demonstrate that WASM offers a practical balance between performance, protability, and security.

In the context of MCP and agent tools, however, WASM sandboxing has not been systematically applied as a foundation for runtime security analysis. Existing work typically treats sandboxing as an execution containment mechanism
[
12
,
18
]
, without leveraging execution-time observability for semantic security inspection. MCP-SandboxScan builds on WASM and WASI to provide a secure execution substrate while enabling fine-grained observation of runtime outputs, forming the basis for detecting prompt injection and other execution-time behaviors specific to MCP tools.

VIII
Conclusion

We present
MCP-SandboxScan
, a lightweight framework for safely executing untrusted MCP tools inside a WASM/WASI sandbox and producing auditable, evidence-based reports about external-to-sink exposures. By extracting LLM-relevant sinks from runtime outputs (prompt/messages and structured tool-return fields) and linking them to environment-, file-, and intent-derived sources via conservative string-level matching, our prototype surfaces concrete provenance evidence when external inputs appear in prompt/messages or tool-return payloads, and provides runtime evidence of filesystem capability violations under WASI preopen enforcement. While the current design is intentionally dynamic-only and limited by output-based observation and substring matching—as reflected by the static-baseline comparison and micro-benchmark FP/FN behaviors—it offers a practical baseline for early-stage tool safety assessment. Future work includes richer sink coverage through tool-to-model request interception when available, syscall-level network mediation, and a hybrid pipeline that combines static pre-screening with targeted dynamic execution.
