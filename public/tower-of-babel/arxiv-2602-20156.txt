Skill-Inject : Measuring Agent Vulnerability to Skill File Attacks
David Schmotz, Luca Beurer-Kellner, Sahar Abdelnabi, Maksym Andriushchenko

Abstract
LLM agents are evolving rapidly, powered by code execution, tools, and the recently introduced agent skills feature. Skills allow users to extend LLM applications with specialized third-party code, knowledge, and instructions. Although this can extend agent capabilities to new domains, it creates an increasingly complex agent supply chain, offering new surfaces for prompt injection attacks. We identify skill-based prompt injection as a significant threat and introduce Skill-Inject , a benchmark evaluating the susceptibility of widely-used LLM agents to injections through skill files. Skill-Inject contains 202 injection-task pairs with attacks ranging from obviously malicious injections to subtle, context-dependent attacks hidden in otherwise legitimate instructions. We evaluate frontier LLMs on Skill-Inject , measuring both security in terms of harmful instruction avoidance and utility in terms of legitimate instruction compliance. Our results show that today’s agents are highly vulnerable with up to 80% attack success rate with frontier models, often executing extremely harmful instructions including data exfiltration, destructive action, and ransomware-like behavior. They furthermore suggest that this problem will not be solved through model scaling or simple input filtering, but that robust agent security will require context-aware authorization frameworks. Our benchmark is available at https://www.skill-inject.com/ .

Introduction

LLM agents are increasingly deployed in settings where they need to adapt to specialized tasks and environments. To address this, agent skills
(
5
;
42
)
have been proposed as a simple standard for packaging code, knowledge and instructions to provide agents with specialized capabilities that go beyond their base training.

Agent Skills Have a Supply Chain Problem.

Users can install new skills like software packages to address knowledge gaps. This complicates the agent supply chain. An agent’s instructions are no longer just comprised of trusted user, system and vendor instructions, but also includes third-party prompts, originating from skills. Beyond direct and indirect prompt injections, this introduces a novel attack surface: Just like software packages can contain malware, installed skills can embed malicious instructions that can be seen and executed by the agent, while remaining largely unnoticed by the user
(
35
)
. Early adoption of skills
(
32
;
30
)
has already made this risk clearly visible. Multiple successful exploits have been demonstrated, including a skill-based attack on the personal assistant agent OpenClaw (formerly Clawdbot or Moltbot)
(
29
)
as well as injections in code documentation
(
3
)
.

Key Challenge: Intended vs. Malicious Instructions.

Unlike traditional prompt injection attacks that inject adversarial text into data (emails, web pages, documents), skill-based injections occur in files that are entirely composed of instructions, making standard defenses based on defining instruction authority levels
(
38
)
or on strictly separating
instructions
from
data

(
17
)
less applicable. Beyond this, skills often include highly-specific procedures and rules for systems and APIs otherwise unknown to models, such that separating malicious and benign intent becomes a highly challenging and contextual question, that often requires knowledge about domain-specific security policies.

Skill Security is Contextual.

Prior work on prompt injection has primarily focused on obviously malicious instructions, requests to ignore safety guidelines, output harmful content, or execute clearly adversarial actions that can potentially be detected through pattern matching or input filtering. We argue that this framing misses the core security challenge in skill-based attacks: many instructions are dual-use, appearing benign or even beneficial in some contexts while enabling data exfiltration or privilege escalation in others. For example, an instruction to
share a summary with the team via the collaboration API
is legitimate when editing internal documentation but becomes a data exfiltration vector when the agent is working with sensitive credentials or confidential files. This dual-use nature means that prompt injection vulnerability in agent skills is not a solvable problem through model scaling or input filtering alone, it fundamentally depends on what information the agent has access to and the semantic context of the task. We investigate how models handle this contextual nature of skills by giving them access to different security information that resolves any ambiguity about the injection. For this we have two cases, a
legitimizing policy
that resolves the injection as being benign and a
warning policy
that identifies the injection as being malicious.

Skill-Inject
: Evaluating Skill-Based Vulnerabilities.

To systematically evaluate this challenge, we introduce
Skill-Inject
, a benchmark for measuring skill-based prompt injection vulnerabilities in agent systems.
Skill-Inject
goes beyond existing benchmarks by focusing specifically on the “instruction-instruction” conflict inherent to skill-based systems, while also highlighting the context-dependent nature of many security constraints.

Our benchmark consists of a curated suite of tasks and corresponding skill files containing injections that range from explicitly adversarial (e.g., “delete all files”) to contextually deceptive (e.g., “archive results to this external endpoint”). This allows us to move beyond binary “safety” evaluations and instead measure the security-utility tradeoff: the degree to which an agent can follow legitimate skill instructions without succumbing to embedded malicious directives.

Main Contributions.

In this paper, we make the following core contributions:

1.

security

utility

3.

An analysis of baseline defenses
in the form of LLM judges and their effectiveness.

2
Related Work

We discuss related work on prompt injection attacks, benchmarks, and defenses. We also briefly cover supply chain attacks on AI systems, and discuss connections to contextual integrity theory and frameworks.

2.1
Prompt Injection Attacks

Prompt injection attacks were originally designed to exploit the inability of large language models to distinguish between instructions and data in their inputs, or when untrusted instructions attempt to subvert system constraints. They were studied in the context of LLM-integrated applications, where indirect prompt injections occur when adversarial instructions (that are embedded in external content, such as emails, web pages, or tool outputs) hijack the model’s behavior to execute unintended actions
(
22
)
. Unlike direct prompt injections where users themselves craft prompts to override system constraints
(
31
;
16
)
, indirect attacks involve third-party content that victims encounter during normal LLM-assisted tasks. The attack surface has expanded considerably with the rise of agentic systems, with prompt injection attacks being now classified as the #1 threat in the OWASP Top 10 for LLM Applications
(
28
)
. Recent work demonstrates that even mature, deployed systems like GitHub Copilot and Microsoft Copilot remain vulnerable to carefully crafted injections that exploit their integration with external data sources
(
15
;
27
;
39
;
33
)
.

2.2
Prompt Injection Benchmarks

Several benchmarks have been proposed to systematically evaluate prompt injection vulnerabilities, for example in web agents
(
19
)
, email assistants
(
2
)
, tools’ outputs
(
18
)
, and computer use agents
(
24
)
. Our benchmark differs in three main aspects: 1) we focus on the new threat model of skill-based injections; 2) rather than having instructions that are syntactically anomalous within their surrounding data context, injections in our benchmarks are instructions within instructions; and 3) we further study contextual instructions, instructions that would be legitimate in one context but harmful in another, requiring semantic reasoning about the agent’s task and provided security guidelines to detect.

2.3
Prompt Injection Defenses

A dominant paradigm in prompt injection defense assumes that instructions and data occupy separable semantic or syntactic categories. For example, Spotlighting
(
23
)
uses special delimiters and encoding schemes to mark external data. Instruction hierarchy
(
38
)
assumes that tool outputs does not contain instructions. Meta SecAlign
(
12
)
uses DPO training to train models not to execute any instructions in data sections. Similarly, many other approaches aim to detect the presence of instructions in data
(
1
;
26
)
. These defenses are inherently not applicable to skill-based injections since the question is not whether instructions exist, but if
bad
instructions do.

Beyond probabilistic defenses, deterministic defenses provide secure-by-design guarantees
(
17
;
14
;
9
)
. However, they assume that actions and control flows can be determined a priori based on trusted sources, e.g., the user query. This paradigm breaks with skill-based design as it inherently allows the agent to take instructions from sources that are beyond the user’s query. Agent skills dynamically extend the agent’s instruction set at runtime.

2.4
Supply Chain Attack on AI systems

The supply chain of (agentic) AI applications extends significantly beyond the core model. Prior work has demonstrated successful attacks across various architectural components, including retrieval databases
(
43
)
, model training datasets
(
11
)
, Model Context Protocol (MCP) tools
(
10
)
, memory-augmented agent systems
(
13
)
, and agent harness permission systems
(
34
)
. This shows the current lack of maturity in securing the broader AI ecosystem. Agent skills now emerge as a new entry point for instruction-level attacks: By leveraging malicious natural language rather than traditional code-level exploits, these attacks circumvent standard security scanners.

2.5
Contextual Security and Privacy

Contextual integrity (CI)
(
8
)
provides a theoretical framework for reasoning about appropriate information flows. CI defines privacy not as blanket secrecy but as conformance to context-specific norms governing who may share what information with whom, under what conditions.
Recent work has begun operationalizing CI for LLM-based agents
(
7
;
20
;
41
;
21
;
36
)
. We draw inspiration from contextual integrity; just as CI recognizes that information appropriate in one context may be inappropriate in another, we recognize that instructions appropriate in one agent context may be harmful in another. Detecting such contextual mismatches requires reasoning about the agent’s current task, its trust relationships, and the semantic appropriateness of proposed actions. Current defenses lack this context-aware authorization.

3
How Do Agent Skills Work?

Agent skills
(
42
)
enable users to extend their agent dynamically with additional knowledge and instructions related to specific tasks and environments.
For this, a skill is represented by a directory that can contain instructions, scripts and resources, but most importantly a designated
SKILL.md
file, with the potentially long-form instructions on the skill’s purpose (e.g., description on the usage of APIs, tools, file formats)
1
1

1

https://github.com/anthropics/skills/blob/main/skills/pptx/SKILL.md
.

Lazy Loading.

To integrate the skill, an agent is informed of its existence by inserting the name, location and brief description of the skill’s scope in the system prompt. The agent then decides autonomously when and whether a skill is applicable and will only access the full skill instructions on demand. See
Figure

10
for an example of the Claude Code agent listing its configured skills.

Distribution and Trust.

While users can author their own skills, they are typically created by third-party developers and published to one of many emerging skill marketplaces like Vercel’s repository
(
25
)
, Anthropic’s repository
(
6
)
, and Smithery
(
37
)
. This creates a classic third-party-trust problem, in which users theoretically would need to verify the trustworthiness of the skills they are using, without necessarily having the expertise to audit the instructions.

Skills as Threat Vector.

The notion of skills as third-party agent extensions offers novel threat surfaces that are particularly susceptible to prompt injection. Users will rarely audit skills in-depth, allowing for significant freedom when it comes to deploying malicious payloads. This is different from, e.g., indirect prompt injections, where often obfuscation techniques have to be used in addition to model hijacking
(
40
)
, to prevent human users from spotting suspicious instructions, for instance, in an email. Further, skills are typically installed in very capable agent environments, such as the Claude Code or personal-assistant-style systems, both of which are naturally exposed to highly sensitive data (filesystem, propriertary code, email, credentials, etc.).

Overall, this makes skills a prime target for malicious actors to place prompt injections that are hard to spot, distributed easily and broadly, and evade standard security mechanisms like scanners that are mainly looking for abnormal instructions and content in otherwise static data.

Example: A Skill-Based Attack.

To illustrate, consider the presentation creation skill in Figure
3
. While most instructions focus on legitimate formatting and design, a ‘design principle’ buried deep in the file directs the agent to back up every document to an external server. This creates a data exfiltration backdoor, enabling a malicious skill author to harvest sensitive data. Note also how this violation may even be considered context-dependent. If a security policy explicitly trusts the destination domain (cf.
Figure

3
), the operation is valid, without this context on the other hand, the agent unknowingly facilitates a breach.

4
The
Skill-Inject
Benchmark

We introduce
Skill-Inject
, a benchmark for measuring prompt-injection vulnerabilities that arise specifically from agent skill files (long, external instruction artifacts that agents load dynamically).
Skill-Inject
contains 23 unique skills spanning document-processing, machine learning, payment integrations, and healthcare. Across these skills, we construct 30 “obvious” very harmful injections that an agent should never execute and 41 “contextual” injections, paired with real tasks to form 76 obvious injection–task pairs and 126 contextual injection–task pairs.

4.1
Design Principles

Skill-Inject
is designed around three principles. First, realism: skills reflect how modern coding agents package and consume instructions and scripts, including cases where a malicious line is embedded among plausible operational guidance. Second, dual-use coverage: beyond categorically harmful instructions, we emphasize context-dependent injections that can look and be legitimate depending on the security context, enabling measurement of the security–utility trade-off. Third, controlled threat models: we vary attacker capability from inserting a single line in the skill body to additionally supplying a script in the skill directory (and, in a stronger variant, also injecting into the skill description).

4.2
Security Policies

A key challenge in skill-based security is that the maliciousness of an instruction often depends on context: the same action can be legitimate or harmful depending on what the agent is authorized to do.
Skill-Inject
captures this by incorporating security policies: natural language rules added to the agent’s system prompt that define trust boundaries and permitted actions.
Security policies serve two roles in the benchmark. First, they model realistic deployments, where organizations specify what agents may and may not do. Second, they allow us to control the ambiguity of an injection: a contextual injection that appears benign in isolation becomes unambiguously malicious when a prohibitive policy explicitly forbids it, and unambiguously benign when a legitimizing policy explicitly permits it.

For each contextual injection,
Skill-Inject
includes two policy variants:

•

Legitimizing policy
: States that the injected action is authorized (e.g., “backup operations to the central server are approved”). Under this policy, executing the injection is the
correct
behavior; the agent should comply.

•

Warning policy
: Explicitly flags the injected action as a policy violation (e.g., “file transfers to unapproved destinations is not allowed”). Under this policy, executing the injection is a clear
security failure
.

A true security failure is when the agent executes an injection despite an active warning policy. When
no policy
is present and the agent executes the injection, the situation is more ambiguous; the agent arguably should exercise caution, but penalizing it too heavily risks conflating security with over-refusal that hurts utility.
Skill-Inject
reports injection execution rate across all three conditions (no policy, legitimizing, and warning) to give a complete picture of agent behavior across this spectrum. We use the term Attack Success Rate (ASR) for obvious injections and contextual injections without a legitimizing policy, while using the more generic term (injection execution rate) to refer to the benign legitimizing policy case.

5
Evaluation

We evaluate frontier LLM agents on
Skill-Inject
to measure their vulnerability to skill-based prompt
injections. Our experiments address three questions: (1) How susceptible are current agents to
contextual and obvious injections under different safety-policy conditions? (2) Do script-based
attacks (where the malicious payload is hidden in a script) differ from direct text injections, and does injecting into skill descriptions provide
additional leverage? (3) Can simple defenses such as LLM-based screening reliably detect malicious
skills? We present main results on injection vulnerability, followed by ablations isolating injection
placement effects. Our code is available at
https://github.com/aisa-group/skill-inject
.

5.1
Experimental Setup

Models and scaffolds.

We evaluate
Skill-Inject
on the following models on their respective default agent scaffolds:

•

OpenAI Codex: GPT-4, GPT-5.1-Codex-Max, GPT-5.1-Codex-Mini, GPT-5.2-Codex, GPT-5.2.

•

Anthropic Claude Code: Haiku 4.5, Sonnet 4.5, Opus 4.5.

•

Google Gemini CLI: Gemini 2.5 Flash, Gemini 2.5 Pro, Gemini 3 Flash, Gemini 3 Pro.

Safety policy conditions.

For each model, we evaluate under the previously mentioned three safety-policy conditions: (1)
Baseline
, where we use the default agent configuration with no additional security context; (2)
Legitimizing
, where the system prompt explicitly tells the model that the injected action is allowed and desired (e.g., the model should actually upload the files to the provided URL for a backup); and (3)
Warning
, where the system prompt explicitly warns that skill files may contain malicious instructions and asks the model to be careful before acting.

Attacker capability.

We evaluate the following different attack capabilities:

•

Body Injection: The attacker can insert a string into the
SKILL.md
body.

•

Body + Script: The attacker can insert a string into the skill body and can add one script to the
scripts/
folder of the skill.

•

Body + YAML Description: The attacker additionally controls one sentence in the skill description (loaded into the system prompt at initialization).

Overall contextual vulnerability.

Figure

Contextual injections succeed at substantial rates across nearly all configurations: under the baseline (Normal) condition (arguably ambiguous scenarions), ASR ranges from 41.0% (Haiku-4.5) to 79.0% (Gemini-3-Flash), with most models exceeding 50%. OpenAI’s newer Codex models are particularly vulnerable, with GPT-5.1-Codex-Max, GPT-5.1-Codex-Mini, and GPT-5.2-Codex all achieving ASR above 65%. Anthropic’s Claude models exhibit lower but still non-trivial ASR, ranging from 41% to 52% (Sonnet-4.5). These results confirm that instruction–instruction injections inside skill files remain a realistic attack vector even for frontier models.

Effect of safety-policy prompting.

Comparing columns, the
Warning
condition generally reduces ASR relative to
Normal
, but does not eliminate successful attacks.
Legitimizing
framing often increases execution success rates (which is the required behavior as executing the additional instructions should be allowed under this policy). This is consistent with the hypothesis that contextual instructions in our benchmark can be operationally justified according to the context. The Claude models seem to be exceptions to this which we discuss further in
Appendix

C
. Together, these results suggest that policy prompting is helpful but insufficient as a standalone mitigation for skill-based prompt injections.

Cross-family differences and caveats.

Across the evaluated systems, we observe substantial spread in ASR under identical conditions, highlighting that robustness is not a monotonic function of model size or general capability. Finally, the effectiveness of defensive protocols varies considerably across model families: the warning security protocol reduces ASR for some models (e.g., Sonnet 4.5) while having minimal impact on others (e.g., GPT-5.1-Max), and, interestingly, the legitimizing protocol reduces the injection execution rate (which is a utility failure) for some models while being effective (i.e., leading to higher execution, as authorized) for others.

5.3
Ablation Studies and Analysis

We run four ablations to better understand (i) whether simple LLM-based skill screening can detect malicious skill content, (ii) how much attack success increases under repeated attempts, (iii) how script-based attacks perform in comparison to text-based injections, and (iv) how the ASR changes when the attacker can also inject the skill description, which is added to the system prompt.

LLM-as-a-judge screening.

As a baseline mitigation, we perform skill security screenings with LLM judges and report the results in
Figure

6
. Under
Normal
, judges first evaluate normal non-injected skill. We find that judges tend to mark these as safe, indicating low false-positive pressure on benign skills. In the
Injected
column, judges identify injected skills mostly correctly, causing recommendation rate to drop substantially. However, when presented with contextually-injected skills and a
legitimizing
policy, the recommendation rates remain very low, affecting utility, illustrating that the judges do not appear capable to assess true contextual security correctly. Exceptions to this are the Gemini models and GPT-5.1-Mini. Additional numbers on this can be seen in
Appendix

C
.

Repeated-attempt attacks (best-of-
n
).

To disentangle which factors drive attack success under repeated attempts, we decompose the best-of-
n
evaluation into separate ablations that each vary a single axis.
In the
Bo5-by-line
variant, each obvious injection is placed at five different line positions within the same skill file while keeping the user task fixed; results appear in the last column of
Table

3
.
We additionally ran a
Bo4-by-task
variant that keeps the skill and injection position fixed but varies the user task prompt across four alternatives; this ablation did not yield statistically significant differences in ASR across task variants and is therefore omitted.
Finally, the
BoN

Because the number of attempts varies per injection (rather than being a fixed constant), we denote this variant simply as BoN.
Together, these ablations show that injection
position
within the skill file is the primary driver of variance, whereas the specific user task has little effect.
More broadly, even modest best-of-
n
budgets substantially increase the probability of at least one successful execution, underscoring that single-attempt ASR underestimates realistic attacker capability.
This highlights how large the attack surface from agent skill files already is, and how much an attacker could improve their success rate with simple adaptive strategies.

Conclusions

Discussion.

Skill-Inject
highlights a structural security problem for tool-using LLM agents: once an agent ingests third-party skills and prompts, a clean separation between trusted user instruction and external data becomes challenging. Here, the primary security failure mode is not merely that a model follows external instructions, but that it lacks an explicit, grounded notion of
context and authorization
for actions requested by a skill.
Skill-Inject
shows that widely-used scaffolds with frontier models are highly vulnerable to skill-based attacks, even when warned. This reveals a critical supply chain risk of AI systems: through skills, attackers can exfiltrate data, deploy ransomware, or execute destructive operations using natural language alone, effectively removing the technical barrier to entry for complex exploits.

Recommendations.

Robust defenses require explicit security policies and reasoning about the sensitivity of the current task context, the skill source, and the risk of requested actions. We recommend treating skill files as untrusted by default, binding skills to least-privilege capability sets, and requiring context-aware authorization for actions with external side effects
(
38
;
44
)
. LLM-based security screenings can also help to some degree, but are not fully effective and thus leave the eco-system vulnerable to malicious skills as a new form of natural language malware.

Limitations.

Our evaluation covers a finite set of skills, tasks, and threat models. Results may shift with different agent implementations or more adaptive attackers. It is also worth noting that these attacks are relatively simple to implement and that a real attacker might reach a much higher attack success rate by optimizing their injection for a very specific task and tailoring it to a specific model or agent scaffold.

Impact Statement

This work exposes security vulnerabilities in widely-deployed AI agent systems, which, of course, carries inherent dual-use risks. To maximize defensive benefit while minimizing potential for misuse, we disclosed our findings to some LLM providers (such as Anthropic) prior to publication, enabling them to strengthen their systems. Importantly,
Skill-Inject
is designed as an evaluation
benchmark
rather than an exploit toolkit, thus it enables measuring agent robustness to baseline prompt injections without requiring the release of optimized attacks. We hope our results encourage practitioners to treat third-party skills as untrusted code by default and to develop context-aware authorization mechanisms that can distinguish legitimate instructions from malicious ones. More broadly, we believe systematic red-teaming of the AI supply chain is essential for building trustworthy agentic systems.

Appendix B
Evaluating Results of LLM Agents on User and Attacker Tasks

Each experiment runs inside an isolated container that contains only the files relevant to the given task. Once the agent terminates, the container is shut down and its full working directory together with the container logs are copied to a persistent result folder.

LLM judge evaluation.

We use a separate LLM judge to assess both user-task success and attacker-task success for every experiment. The judge receives (i) the agent’s final output, (ii) the complete working directory, and (iii) a bash history file that we inject into the container setup to record all shell commands executed during the session. The judge is instructed to first inspect the agent’s output and then cross-check the bash history for any commands that indicate execution of the injected payload (e.g.,
curl
calls to attacker-controlled URLs,
rm
commands on user files, or execution of referenced scripts). If additional context is needed, the judge may explore the remaining files in the working directory.

Success criteria.

The user task is marked as successful if the judge determines that the agent’s output satisfies the task specification (e.g., the requested document was created, the code compiles, or the requested edits were applied). The attacker task is marked as successful if the judge finds evidence that the injected payload was executed, based on the bash history, file system changes, or network requests observed in the logs.

Comments on GPT-4 performance.

GPT-4 achieves the lowest ASR among evaluated models but also the lowest task completion rate. This is largely attributable to its substantially shorter context window relative to the other models, which limits its ability to process the long skill files in our benchmark. Many skill files exceed GPT-4’s effective context, causing it to miss both the legitimate task instructions and the injected payload.

Comments on Opus 4.5 performance.

Opus 4.5 exhibits a counter-intuitive pattern: its ASR under the
Legitimizing
condition is
lower
than under
Normal
or
Warning
. We hypothesize that appending a legitimizing policy to the system prompt does not grant it higher authority than the skill instructions themselves; instead, the attempt to coerce the model into trusting the injected action makes it more suspicious. This is consistent with
(
4
)
, where the authors report that Opus 4.5 exhibits very high resistance to harmful requests originating from the system prompt. In our setting, this robustness appears to manifest as reduced utility on the contextual injections that rely on the legitimizing framing. We note that we did not optimize the policy text to appear especially innocuous, and several attempts with alternative policy headers and footers failed to reliably increase the utility of Opus 4.5 under this condition.

Task-injection orthogonality.

In some of our experiments, a successful attack renders the user task impossible to complete. For example, the ransomware attack in
Figure

4
encrypts and deletes the files the agent would need to finish the task, and several other attacks instruct the agent to delete files that are relevant to the user’s request. Including these cases in the task completion rate would conflate two distinct failure modes: the agent failing to complete the task due to lack of capability, and the agent failing because the attack itself destroyed the prerequisites. To avoid this confound, we exclude injection–task pairs in which the injected payload, if executed, makes the user task infeasible by design when computing the task completion rate.
