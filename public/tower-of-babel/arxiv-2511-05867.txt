MCP-RiskCue: Can LLM Infer Risk Information From MCP Server System Logs?
Jiayi Fu, Qiyao Sun

Abstract
Large Language Models (LLMs) demonstrate strong capabilities in solving complex tasks when integrated with external tools. The Model Context Protocol (MCP) has become a standard interface for enabling such tool-based interactions. However, these interactions introduce substantial security concerns, particularly when the MCP server is compromised or untrustworthy. While prior benchmarks primarily focus on prompt injection attacks or analyze the vulnerabilities of LLM–MCP interaction trajectories, limited attention has been given to the underlying system logs associated with malicious MCP servers. To address this gap, we present the first synthetic benchmark for evaluating LLMs’ ability to identify security risks from system logs. We define nine categories of MCP server risks and generate 1,800 synthetic system logs using ten state-of-the-art LLMs. These logs are embedded in the return values of 243 curated MCP servers, yielding a dataset of 2,421 chat histories for training and 471 queries for evaluation. Our pilot experiments reveal that smaller models often fail to detect risky system logs, leading to high false negatives. While models trained with supervised fine-tuning (SFT) tend to over-flag benign logs, resulting in elevated false positives, Reinforcement Learning from Verifiable Reward (RLVR) offers a better precision–recall balance. In particular, after training with Group Relative Policy Optimization (GRPO), Llama3.1-8B-Instruct achieves 83% accuracy—surpassing the best-performing large remote model by 9 percentage points. Fine-grained, per-category analysis further underscores the effectiveness of reinforcement learning in enhancing LLM safety within the MCP framework. Code and data are available at https://github.com/PorUna-byte/MCP-RiskCue .

Introduction

The ability to use external tools is widely regarded as a critical milestone in the progression of LLMs toward Artificial General Intelligence (AGI). To support flexible interactions between LLMs and third-party tools, Anthropic
[
4
]
proposed the MCP, a standardized interface that enables LLM agents to access external tools via MCP servers. While MCP simplifies integration by providing a unified abstraction layer, it also introduces significant security risks
[
16
]
, such as unauthorized access to sensitive user data
[
37
]
.
Existing research primarily focuses on prompt injection attacks or analyzes the vulnerabilities associated with interaction trajectories between LLMs and MCP servers. However, little attention has been paid to the system logs of potentially malicious MCP servers. Assuming that such servers may leave detectable traces in their system logs, we introduce
MCP-RiskCue
—the first synthetic benchmark designed to evaluate LLMs’ ability to infer potential security risks from system-level logs in MCP-based environments.

We define nine classical risk categories that characterize potentially malicious MCP servers. Based on these categories, we manually construct 243 dummy MCP servers using the FastMCP
[
15
]
framework and deploy them on a local machine.
We do not implement real attacks on our local machine to obtain tractable system logs due to the high cost and potential harm. Many attacks are resource-intensive and may pose damage to the local machine.
Thus, to obtain high-quality system logs representative of each risk type, we employ ten state-of-the-art LLMs to generate 20 system logs per risk category, yielding a total of 1,800 logs.
A total of 2,892 user queries are generated using GPT-4o, ensuring that each query is fully answerable by the MCP servers. We randomly sample 2,421 queries and use the pipeline (Figure
1(b)
) to instantiate chat trajectories, with GPT-4o serving as the backend model.
Each trajectory begins with the user query and corresponding MCP server descriptions, which are provided to the LLM agent. The agent interacts with the MCP servers via tool calls and, after each interaction, receives both tool responses and system logs. Based on the content, the agent chooses one of three actions: (1) issue a warning message if the system log is identified as risky, (2) continue querying for additional information, or (3) synthesize a final response to the user.
The 2,421 instantiated chat histories are converted into the training set using the strategy illustrated in Figure
2
, while the remaining 471 queries are used as the evaluation set.
We then conduct extensive experiments on the constructed dataset. For local model evaluation, we select five representative open-source models spanning three categories: instruction-tuned, reasoning, and safety-aligned models. These include
Qwen3-4B-Instruct-2507
,
Llama-3.1-8B-Instruct
,
DeepSeek-R1-0528-Qwen3-8B
,
Qwen3Guard-Gen-4B
, and
Llama-Guard-3-8B
. For remote model evaluation, we include ten SOTA models, as detailed in Section
4
. Our evaluation is performed at two levels: (1) binary classification of system logs as risky or benign, and (2) fine-grained classification of risk type given a risky system log.

In the level-1 evaluation, we observe that all vanilla local models fail to reliably identify risky system logs. These models consistently classify most logs as benign, resulting in high false negatives and overall accuracy around 50%, nearly random guessing. To enhance their performance, we apply supervised fine-tuning (SFT) using the training set. However, the accuracy improvements are marginal, primarily due to a notable increase in false positives. We hypothesize that this is a consequence of the imitative nature of SFT. Specifically, for each risky log in the system log pool, there exists a closely resembling benign log (i.e., a hard negative), and SFT tends to learn superficial artifacts rather than capturing the underlying distinctions. To address this limitation, we further apply the RLVR technique to fine-tune the SFT models. This approach yields substantial accuracy gains by achieving a better balance between false positives and false negatives, highlighting the importance of reinforcement learning in enhancing LLM reasoning and safety. Remote models also face challenges, exhibiting either high false positive or false negatives. Among them,
Doubao-1.5
,
GPT-5
, and
Kimi-k2
achieve the highest overall accuracy. Notably, the best-performing local model,
Llama3.1-8B-Instruct
, achieves an accuracy of 83% after applying GRPO, outperforming the best-performing remote model,
Doubao-1.5
, by 9 percentage points.

In the level-2 evaluation, vanilla local models exhibit the highest false negatives across most risk categories. While SFT significantly reduces false negatives, it introduces elevated false positives, particularly for risk types ① (Sensitive Data Exfiltration) and ③ (Malicious Code Execution). In contrast, GRPO retains the low false negatives achieved by SFT while substantially reducing false positives, resulting in more accurate and well-calibrated decision boundaries across risk types. Remote models display concentrated false negatives for risk types ①, ② (Covert Channel Attack), and ③, indicating that these categories remain particularly challenging for LLMs. Conversely, false positives often peak for risk type ⑨ (Log Explosion Attacks), suggesting the presence of ambiguous or misleading patterns. Risk types ⑥ (Cache or Local State Pollution) and ⑧ (Denial-of-Service), however, appear less problematic, with most models achieving low false negative and false positives in these categories.

Our key contributions are threefolds:

•

We introduce
MCP-RiskCue
, the first benchmark designed to evaluate the ability of LLMs to infer security risk types from system logs. The detailed guideline for constructing the benchmark is also provided.

•

We conduct comprehensive experiments on both local small-scale models and remote large-scale models. Our results show that SFT alone offers limited improvement for local models, likely due to their constrained reasoning capabilities. In contrast, the RLVR technique enables small models to outperform much larger models in accurately identifying risk types from system logs.

•

We release our code and dataset to support future research on safety issues in MCP scenarios.

3
Benchmark

We introduce the
MCP-RiskCue
benchmark to evaluate the ability of large language models to identify risk types of MCP servers based on system logs. This section provides a detailed overview of the benchmark construction process. The following subsections describe the risk taxonomy, the creation of dummy MCP servers, the design of system logs, the curation of user queries, the generation of chat histories, the transformation of these histories into the training set, the construction of the test set, and the evaluation metrics.

3.1
Risk Taxonomy

We group nine risk types into four high level categories to align with classic security goals (confidentiality, integrity, availability) and how attacks actually manifest in MCP systems.
Information Leakage and Covert Channel Attacks
(①,②) cover direct and indirect ways to exfiltrate sensitive data.
Code Execution and Privilege Escalation Attacks
(③,④) capture integrity violations where untrusted code runs or capabilities are illegitimately amplified.
Persistent Threat and Implantation Attacks
(⑤,⑥,⑦) focus on attacks that modify backends, caches, or states to create long-term, hard-to-detect footholds, including delayed triggers.
Performance and Resource Consumption Attacks
(⑧,⑨) target availability and observability by exhausting resources or inflating logs. The nine fine-grained risk types are defined as below.

① Sensitive Data Exfiltration

Unauthorized extraction of confidential information.

② Covert Channel Attack

Leakage via unintended channels (e.g., timing, contention).

③ Malicious Code Execution

Injection or execution of harmful scripts/commands.

④ Privilege Escalation

Obtaining access beyond intended permissions.

⑤ Persistence via Backdoor Implantation

Installing hidden mechanisms to retain access.

⑥ Cache or Local State Pollution

Corrupting caches or local/model state to bias behavior.

⑦ Delayed or Time-Triggered Attacks

Actions that activate later or under conditions.

⑧ Denial-of-Service

Exhausting compute/storage/network to degrade availability.

⑨ Log Explosion Attacks

Flooding logs to exhaust storage/costs and hide activity.

3.3
System Logs Pool

The system log pool is the core component of our benchmark for evaluating the safety of LLMs. Ideally, realistic system logs would be collected from malicious MCP servers corresponding to the nine risk types defined above. However, implementing such malicious servers is non-trivial and may pose risks to our working machines. Therefore, we instead leverage LLMs to construct a diverse set of system logs that cover all nine risk types.

Specifically, we leverage ten widely used language models: Claude-3.7, Doubao-1.5, Gemini-2.5, GLM-4.5, Grok-4, GPT-5, GPT-4o, DeepSeek-R1, Kimi-K2, and OpenAI-O3
[

10

1,800

To prevent surface cues from trivially revealing the risk type, we prompt the models to produce system logs that require multi-step reasoning to uncover the underlying risks. In addition, we inject irrelevant details as decoys to increase task difficulty. The benign hard negatives are carefully constructed to closely resemble risky cases while remaining non-harmful. The full system prompt used for system log generation is provided in Appendix
6.3
, and illustrative examples of system logs for each risk type are included in Appendix
6.5

Note that the system log is independent of the dummy MCP server. During each MCP server call, a system log is randomly sampled from the system log pool and returned to the user along with the tool result. This means that the MCP servers themselves are benign, and the system logs are not tied to any specific server. Instead, each log is a synthetic instance used to simulate potential MCP server risks.

Queries

3.5
Chat Histories

The overall pipeline for chat history generation is illustrated in Figure
1(b)
. An LLM agent interacts with locally deployed dummy MCP servers. For each dialogue, the user query and relevant server descriptions are provided as context. At each assistant turn, the agent chooses one of three actions: (1) invoke a tool provided by the MCP server to retrieve additional information; (2) generate a final response that answers the user query and terminates the dialogue; or (3) issue a warning message indicating a potential risk and terminate the dialogue.
The agent is prompted to follow a simple decision policy: if the system log received at the current turn indicates a potential risk, it selects action (3); else if additional information is needed to respond, it selects action (1); otherwise, it proceeds with action (2).
We use GPT-4o as the backbone model to instantiate dialogues for each randomly selected
2,421
query following the pipeline in Figure
1(b)
, the system prompt used for chat-history generation is provided in Appendix
6.3
.

3.6
Dataset

Training split

The chat histories are post-processed to construct training examples. Since the dialogues are instantiated using GPT-4o, which may not always correctly identify the risk type of a given system log, we categorize the resulting chat histories into four possible scenarios:

1.

False positive:
The system log is benign, but the LLM incorrectly issues a warning message. In this case, we truncate the chat history at the turn preceding the warning message and use the truncated prefix as input. A separate LLM is then prompted to synthesize a normal response, which serves as the label.

2.

False negative:
The system log is risky, but the LLM either fails to issue a warning or produces an incorrect risk type. Here, we truncate the dialogue at the first turn containing a risky system log and use the truncated prefix as input. The label is manually curated as
Unsafe MCP Server: {{"ServerName":"<name>", "ToolName":"<tool>", "Reason":"<risk type>"}}
.

3.

True positive:
The system log is risky and the LLM correctly issues a warning. We use the final assistant turn as the label and the preceding dialogue as input.

4.

True negative:
The system log is benign and the LLM responds appropriately. Similar to the true positive case, we use the last assistant turn as the label and the remaining dialogue as input.

Test split and Metrics

The remaining
471
queries are reserved as the test split. To evaluate a model—whether local or remote—we use it as the backbone to instantiate chat histories for each query in the test set. Once these chat histories are generated, we assess them using a set of two-level evaluation metrics.

The
level-1
metric evaluates whether an LLM can accurately distinguish risky system logs from safe ones. This constitutes a binary classification task (
Risk
vs.
Safe
), for which we report true positives, false positives, false negatives, true negatives, accuracy, precision, and recall.
The
level-2
metric measures the model’s ability to correctly identify the specific type of risk. For each risk type, we report false positives (instances incorrectly classified as the target risk type but actually belonging to another risk type or the safe class) and false negatives (instances belonging to the target risk type but misclassified as another type or as safe). This enables fine-grained error analysis across risk categories.

Supervised Fine-tuning (SFT)

For SFT, we concatenate the input with its corresponding label, where the label is formatted as an assistant turn. The assistant output either issues a warning that specifies the risk type or provides a standard reply addressing the user’s query. During training, we apply a loss mask to exclude non-assistant turns, ensuring that the model learns to generate appropriate responses and perform tool-calling behavior within a single supervised phase.

5
Conclusion

In this paper, we introduce MCP-RiskCue, the first benchmark designed to evaluate the ability of large language models (LLMs) to infer security risks from system logs associated with malicious MCP servers. Our experimental results reveal that vanilla small-scale models tend to overlook risky system logs, resulting in high false negatives. While supervised fine-tuning (SFT) mitigates this issue to some extent, it often overflags benign logs, leading to a surge in false positives. In contrast, the RLVR technique effectively balances false negatives and false positives, thereby improving overall accuracy. A fine-grained analysis across risk types further underscores the importance of reinforcement learning in equipping LLMs with the reasoning capabilities necessary to accurately identify specific risk categories.
