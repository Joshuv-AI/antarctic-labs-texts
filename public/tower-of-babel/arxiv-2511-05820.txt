WAR-Re: Web API Recommendation with Semantic Reasoning
Zishuo Xu, Dezhong Yao, Yao Wan

Abstract
With the development of cloud computing, the number of Web APIs has increased dramatically, further intensifying the demand for efficient Web API recommendation. Despite the demonstrated success of previous Web API recommendation solutions, two critical challenges persist: 1) a fixed top-N recommendation that cannot accommodate the varying API cardinality requirements of different mashups, and 2) these methods output only ranked API lists without accompanying reasons, depriving users of understanding the recommendation. To address these challenges, we propose WAR-Re, an LLM-based model for Web API recommendation with semantic reasoning for justification. WAR-Re leverages special start and stop tokens to handle the first challenge and uses two-stage training: supervised fine-tuning and reinforcement learning via Group Relative Policy Optimization (GRPO) to enhance the model’s ability in both tasks. Comprehensive experimental evaluations on the ProgrammableWeb dataset demonstrate that WAR-Re achieves a gain of up to 21.59% over the state-of-the-art baseline model in recommendation accuracy, while consistently producing high-quality semantic reasons for recommendations.

Introduction

With the development of emerging technologies, notably cloud computing, the number of Web APIs has increased dramatically
7
. For example, ProgrammableWeb reported in 2022 that its registry comprised over 24000 distinct APIs, highlighting a more than tenfold increase over the preceding decade. Web APIs enable users to leverage the functionality of other applications or services and can be easily invoked by multiple types of devices in a distributed environment. These characteristics have given rise to a new technique known as mashup, which allows developers to integrate existing Web API resources to meet complex requirements without starting from scratch
22
. However, the challenge of identifying APIs that best satisfy a mashup’s requirements grows with the increasing size of Web APIs. Developers—particularly those without deep expertise in APIs—face a combinatorial explosion when evaluating candidate APIs. Consequently, automated Web API recommendation systems have become indispensable tools, guiding developers toward high-quality, compatible APIs and reducing integration effort
21
;
20
.

Numerous approaches have been proposed for Web API recommendation, ranging from content-based and collaborative filtering (CF) techniques to various hybrid strategies. Despite the existing methods’ advancements, there are still two challenges:
1) The fixed top-N API recommendation fails to adapt to mashup complexity, resulting in either superfluous or insufficient recommendations. Existing approaches typically compute a matching score for each candidate API and then select the top
-
N APIs via simple ranking. This uniform cardinality strategy ignores that simple mashups may need only one or two APIs while complex ones require many more, thereby introducing irrelevant services in simple compositions and omitting essential ones in complex cases.
2) The lack of clear reasons for recommended APIs impairs users’ understanding and trust of the recommendations. Current recommendation systems generally present users with a ranked list of APIs but offer no insight into the underlying rationale for each suggestion. Without interpretable explanations—such as which functional requirements or semantic features of the mashup description triggered a particular API’s inclusion—users may find the results opaque or untrustworthy, which could hinder their mashup creation.

Related Work

2.1
Web API Recommendation

Web API recommendation solutions can be divided into three types: content-based, collaborative filtering (CF), and hybrid methods. Content-based Web API recommendation techniques suggest relevant APIs by leveraging salient features extracted from mashup and API descriptions
2
. Shi et al.
15
apply an attention mechanism on LSTM to prioritize critical description segments. ServiceBERT
18

1

12

Collaborative filtering is designed to recommend Web APIs by leveraging users’ past interactions and preferences. Chen et al.
3
propose a hybrid CF approach that combines user-based and item-based strategies, incorporating QoS metrics to assess API suitability. Yao et al.
25
develop a probabilistic matrix factorization model that accounts for explicit similarity measures and latent API correlations to optimize mashup co-invocation predictions. Wang et al.
17
integrate knowledge graph embeddings with CF, and model semantic relationships between APIs and mashups.

Hybrid frameworks integrate multiple information sources to mitigate limitations of individual methods. Xia et al.
24
propose a category-aware clustering of services combined with CF to predict category-specific rankings. Qi et al.
9
construct a correlation graph to generate tailored API suggestions that meet both functional requirements and compatibility constraints. Wang et al.
21
develop FSFM, fusing requirement semantic vectors with representations of structural intersection.

Problem Definition

3.1
Definition of Web API Recommendation with Semantic Reasoning

This study enhances Web API recommendation by integrating semantic reasoning, which provides justificatory reasons for each recommended API. The task is formalized as follows: Let
T^{m_{i}}
represent the requirement description for a mashup
m_{i}
, as specified by the user. Let

A=\{a_{1},\ldots,a_{j},\ldots,a_{S}\}

denote a repository comprising
S
Web APIs. Each API
a_{j}=\langle D^{a_{j}},C^{a_{j}},X^{a_{j}}\rangle\in A
is defined by its functional description
D^{a_{j}}
, category
C^{a_{j}}
, and associated meta-elements
X^{a_{j}}
. Given
T^{m_{i}}
and
A
, our goal is twofold. First, we must identify a subset

S^{m_{i}}=\{a_{1},\ldots,a_{l},\ldots,a_{s}\}\subseteq A

of size
s
that best satisfy the user’s needs. Then, to enhance transparency and usability, each recommended API
a_{l}
is provided with an explanatory reason
r_{a_{l}}^{m_{i}}
to justify its inclusion, yielding a set of reasons
R^{m_{i}}=\{r_{a_{1}}^{m_{i}},\ldots,r_{a_{l}}^{m_{i}},\ldots,r_{a_{s}}^{m_{i}}\}
. Finally, using APIs from
S^{m_{i}}
, the user creates their mashup
m_{i}=\langle D^{m_{i}},C^{m_{i}},A^{m_{i}},X^{m_{i}}\rangle
where
D^{m_{i}}
is a textual description to introduce its functions,

C^{m_{i}}
is a set of categories to indicate its functions,

A^{m_{i}}
is a bundle of APIs to participate in the mashup,

X^{m_{i}}
is a set of meta-elements to prepare for composition. In the ideal scenario, the recommendations exactly match the chosen APIs:
A^{m_{i}}=S^{m_{i}}
.

4
Methodology

4.1
WAR-Re Architecture

Figure
2
depicts the overall architecture of WAR-Re. First, we augment the original corpus of historical mashup API calls by employing LLMs such as DeepSeek-R1 to generate explanatory reasons for why each target API is invoked, given both the mashup’s requirement description and the respective API’s function description. Next, WAR-Re, which is built upon a TinyLlama backbone, is trained in two stages: (1) Supervised fine-tuning. We perform standard language modeling with a cross-entropy loss to train the model to predict the next token in a sequence of mashup descriptions, recommended APIs and rationale texts. After supervised fine-tuning, WAR-Re acquires foundational capabilities for API recommendation and semantic reasoning.
(2) GRPO Reinforcement Learning with Low-Rank Adaptation (LoRA)
5
. We then fine-tune the model via GRPO, incorporating LoRA to restrict trainable parameters to a lightweight subset, thereby reducing computational cost. After reinforcement learning, WAR-Re further enhances the performance, especially in alignment between recommendation and reasoning by ensuring more recommended APIs are accompanied by justificatory reasons.

4.3
First Stage Training: Supervised Fine-tuning for Foundational Capabilities

Building on the annotated dataset, we conduct supervised fine-tuning to equip WAR-Re with foundational capabilities for API recommendation and semantic reasoning.
Since most API names are initially out of the tokenizer’s vocabulary, we explicitly add each API as a single indivisible token (e.g.,
<API_sendgrid>
) to prevent the tokenizer from decomposing an API name into multiple tokens and enable the model to recognize whether an API is present in or absent from the repository.
Inspired by T2I-R1
6
which uses
<img_start>
for image token generation, we introduce task-specific delimiters to structure the model’s output:
<API_start>
and
<API_stop>
frame the API recommendation sequence, while
<REASON_start>
and
<REASON_stop>
enclose the explanatory reasoning. This design enables the model to clearly distinguish between the two subtasks and learn precise generation boundaries. During training, the input sequence is constructed according to the template in Table
2
. The template includes three key parts: the mashup’s requirement description; a recommended API list enclosed by
<API_start>
and
<API_stop>
; explanatory reasons for each API, wrapped by
<REASON_start>
and
<REASON_stop>
. The mashup descriptions and recommended APIs are derived from historical records, and the explanatory reasons are annotated by LLMs. The model learns patterns in mashup descriptions to improve recommendations for similar mashups.

Let
H
denote the total length of the target token sequence and
w_{h}
the
h
-th token. The model parameterized by
\Phi
produces a predictive distribution
P_{\Phi}(w_{h}\mid w_{1},\dots,w_{h-1})
at each step. We adopt the standard cross-entropy loss over the entire sequence:

\displaystyle\mathcal{L}_{\Phi}=-\frac{1}{H}\sum\limits_{h=1}^{H}\log P_{\Phi}(w_{h}\mid w_{1},\ldots,w_{h-1})

(1)

Here, the term
\log P_{\Phi}(w_{h}\mid w_{1},\ldots,w_{h-1})
measures the log-likelihood of the true token
w_{h}
under the model’s predictive distribution. Negating and averaging these log-likelihoods across all positions
h
in the sequence encourages the model to prioritize correct tokens at each step. This formulation ensures the model learns foundational capabilities of generating syntactically valid sequences that respect the structure imposed by special tokens (e.g., transitioning from
<API_start>
to API tokens to
<API_stop>
), selecting APIs relevant to the mashup description, and producing coherent reasons that align with the recommended APIs.

4.4
Second Stage Training: GRPO with LoRA for Performance Enhancement

Overall Introduction

After the first stage training, the model gains foundational recommendation and reasoning capabilities. However, supervised fine-tuning is limited by reliance on static training data and lacks mechanisms to explore new API combinations beyond historical patterns. To further enhance performance, we adopt GRPO as its exploration mechanism and group-based comparative feedback encourages the model to explicitly learn which outputs better satisfy evaluation metrics. For each input question
q
omitting recommended APIs and reasons as given in Table
2
, GRPO samples a group of outputs
\{o_{1},o_{2},\dots,o_{G}\}
from the old policy
\pi_{\theta_{\mathrm{old}}}
and then optimizes the policy model by maximizing the following objective:

\mathcal{J}_{\mathrm{GRPO}}(\theta)=\mathbb{E}_{\begin{subarray}{c}q\sim P(Q),\\
\{o_{i}\}\sim\pi_{\theta_{\mathrm{old}}}\end{subarray}}\Bigl[\frac{1}{G}\sum_{i=1}^{G}\frac{1}{|o_{i}|}\sum_{t=1}^{|o_{i}|}\\
\min\Bigl\{\frac{\pi_{\theta}(o_{i,t}\mid q,o_{i,<t})}{\pi_{\theta_{\mathrm{old}}}(o_{i,t}\mid q,o_{i,<t})}\,\hat{A}_{i,t},\,\mathrm{clip}\bigl(\frac{\pi_{\theta}}{\pi_{\theta_{\mathrm{old}}}},1-\varepsilon,1+\varepsilon\bigr)\,\hat{A}_{i,t}\Bigr\}\\
-\,\beta\,D_{\mathrm{KL}}\bigl[\pi_{\theta}\|\pi_{\mathrm{ref}}\bigr]\Bigr].

(2)

Here
\varepsilon
and
\beta
are hyper-parameters, and
\hat{A}_{i,t}
is the advantage computed using a group of rewards
\{r_{1},r_{2},\dots,r_{G}\}
corresponding to the outputs within each group:

\displaystyle\hat{A}_{i,t}=\frac{r_{i}-\text{mean}\bigl(\{r_{1},r_{2},\cdots,r_{G}\}\bigr)}{\text{std}\bigl(\{r_{1},r_{2},\cdots,r_{G}\}\bigr)}.

(3)

GRPO incorporates regularization by adding the KL divergence between the learned policy and the reference policy directly into the loss, thereby sidestepping any added complexity in computing
\hat{A}_{i,t}
. In our implementation, the reference policy
\pi_{\mathrm{ref}}
is set to the old policy
\pi_{\theta_{\mathrm{old}}}
, ensuring alignment with the policy update framework.

To reduce computational cost, we adopt LoRA in our GRPO training. For a given weight matrix
\mathbf{W}_{0}\in\mathbb{R}^{d\times k}
, LoRA employs a low-rank decomposition to modify the weights, expressed as
\mathbf{W}_{0}+\Delta\mathbf{W}=\mathbf{W}_{0}+\mathbf{B}\mathbf{A}
, where
\mathbf{B}\in\mathbb{R}^{d\times r}
and
\mathbf{A}\in\mathbb{R}^{r\times k}
, with the rank
r\ll\min(d,k)
. During the training process,
\mathbf{W}_{0}
remains fixed and does not receive gradient updates, while the matrices
\mathbf{A}
and
\mathbf{B}
are trainable. Thus, in our GRPO stage we only optimize the LoRA parameters
\{\mathbf{A},\mathbf{B}\}
.

Design of the Reward Function

Our overall reward consists of two components: (i) Recommendation quality and (ii) Reasoning quality.

For the recommendation reward, we employ standard information retrieval metrics to assess API recommendation performance. As
s
denotes the number of recommended APIs output by the model, we use “@
s
” to indicate that these metrics are computed over all APIs recommended by the model. Precision@
s
refers to the ratio of the number of real hits in the recommended APIs to the number of recommended APIs. Recall@
s
is defined as the ratio of the number of real hits in the recommended APIs to the number of all real APIs. Furthermore, the F1 score, as the harmonic mean of Precision and Recall, balances these two metrics. Since Precision@
s
and Recall@
s
do not take into account the order in the results, we use additional evaluation metrics: Mean Average Precision (MAP) and Normalized Discounted Cumulative Gain (NDCG). NDCG is calculated from DCG by normalizing IDCG which is the ideal DCG. Average Precision (AP) calculates Precision at each position, and averages these values over all matching positions. MAP is obtained by averaging AP across all mashups. In practice, the batch size is set to 1 during the second-stage training. As a result, the reward function at this stage directly uses AP@
s
computed for each individual mashup. The recommendation reward is given as:

\begin{split}\text{recommendation reward}=0.4*\text{F1}+0.1*\text{Precision}+0.1*\text{Recall}+0.2*\text{NDCG}+0.2*\text{AP}.\end{split}

(4)

Since F1 encapsulates both Precision and Recall, we assign it a greater weight; however, we retain small weights for individual metrics to reward high performance in specific aspects.

For the reasoning reward, we introduce Reasoning Precision (RP) and Reasoning Recall (RR) to evaluate the quality of reasoning. RP quantifies the proportion of all provided reasons that correspond to APIs actually recommended by the model.

\displaystyle\text{RP}=\frac{|\text{{APIs}}_{\text{{recommend}}}\cap\text{APIs}_{\text{reason }}|}{|\text{APIs}_{\text{reason}}|}.

(5)

RR quantifies the proportion of all APIs recommended by the model that are accompanied by a valid reason.

\displaystyle\text{RR}=\frac{|\text{{APIs}}_{\text{{recommend}}}\cap\text{APIs}_{\text{reason}}|}{|\text{APIs}_{\text{recommend}}|}.

(6)

RP and RR are equally weighted, so the reasoning reward is formulated as:

\begin{split}\text{reasoning reward}=0.5*\text{RP}+0.5*\text{RR}.\end{split}

(7)

The overall reward is the sum of the recommendation reward and reasoning reward, as both components carry equal significance in our model design.

6
Conclusion

In this study, we propose WAR-Re, a novel LLM-based model that enhances Web API recommendation with semantic reasoning and supports variable API cardinality for diverse mashup complexities. We first use DeepSeek-R1 to generate explanations for historical mashup–API calls in the dataset and attach them as annotations. Then WAR-Re is trained via two stages: supervised fine-tuning followed by GRPO reinforcement learning with LoRA. Experimental results demonstrate WAR-Re’s superior performance in recommendation accuracy over state-of-the-art models and high quality in semantic reasoning as validated by quantitative metrics and LLM evaluations. Ablation studies confirm the effectiveness of GRPO training, the special start and stop tokens and the mutual benefits of integrating reasoning with recommendation tasks. Future work will focus on increasing the scale of the underlying language model to further broaden WAR-Re’s applicability in real world scenarios.
