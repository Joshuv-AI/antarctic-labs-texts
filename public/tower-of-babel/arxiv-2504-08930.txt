An Adaptive Vector Index Partitioning Scheme for Low-Latency RAG Pipeline Conference: 29th International Conference on Architectural Support for Programming Languages and Operating Systems; March 2026; Boston, MA, USA CCS: Computer systems organization Heterogeneous (hybrid) systems
Junkyum Kim, Divya Mahajan

Abstract
. Retrieval-Augmented Generation (RAG) systems enhance response quality by integrating Large Language Models (LLMs) with vector databases, enabling external knowledge retrieval to support language model reasoning. While RAG enables efficient question answering with smaller LLMs, existing optimizations for vector search and LLM serving have largely been developed in isolation. As a result, their integration often leads to suboptimal end-to-end performance. LLM execution has traditionally been on GPUs, while vector search is often offloaded to CPUs or dedicated accelerators ( bib:anna ) in RAG pipelines to reserve GPU resources—both memory and compute—for LLMs. Although independent efforts have optimized vector search on GPUs ( bib:faiss ) , naively moving vector indices to GPU memory introduces resource contention, particularly in memory allocation. This contention reduces space available for the LLM’s key-value (KV) cache, degrading LLM generation performance and lowering overall system throughput. This paper introduces VectorLiteRAG , an optimized vector index partitioning mechanism designed for RAG systems that enhances the responsiveness of the system by jointly optimizing vector search and LLM serving across CPU and GPU system. A key challenge is to determine which indices and how much of the vector index should reside on the GPU and adjusting LLM batch sizes to balance the pipeline for lower Time-To-First-Token (TTFT) and meeting user-defined Service-Level Objectives (SLOs). To address this, we leverage the insight that cluster access in vector databases exhibits access skew, where a subset of clusters are queried significantly more frequently than others. VectorLiteRAG exploits this property through an optimized memory distribution strategy, dynamically allocating the minimum number of vector indices corresponding to frequently accessed clusters onto the GPU HBM to ensure a balanced pipeline with the LLM for high responsiveness. This adaptive partitioning scheme is guided by a statistical model that informs memory allocation and workload distribution. Our evaluation demonstrates that VectorLiteRAG improves vector search responsiveness by 2 × \times , significantly reduces end-to-end TTFT in RAG systems by intelligently balancing memory resources between vector search and LLM execution.



1.
Introduction

Retrieval-Augmented Generation (RAG) has gained significant attention in natural language processing since its introduction
(
bib:rag
;
bib:realm
)
, particularly for domain-specific question answering and information retrieval tasks.
RAG’s key advantage lies in its ability to combine non-parametric (knowledge stored in databases) and parametric memory (Large Language Models).
Parametric memory, represented by the weight parameters of LLMs, is massive and resource intensive to train or fine-tune. To mitigate this, RAG pipelines first perform similarity search using approximate nearest neighbor (ANN) algorithms to retrieve the most relevant documents from a knowledge corpus.
The retrieved information is then used by the LLM to generate reliable and up-to-date responses.

Efforts to optimize RAG pipelines can be broadly categorized into two main approaches. One line of work focuses on optimizing the LLM generator, refining its algorithms and scheduling strategies for RAG applications
(
bib:ragcache
;
bib:blockattention
;
bib:speculaterag
;
bib:ragserve
)
. These techniques improve responsiveness and throughput by reusing KV caches, modifying attention mechanisms, and efficiently scheduling generation requests.
The other line of work optimizes the ANN algorithm
(
bib:fastscan
;
bib:scann_soar
;
bib:scann_avq
)
.
However, the vector search stage is often overlooked, as its execution time is generally considered negligible compared to the overall response latency. This assumption holds primarily because many prior studies evaluate RAG systems with relatively small vector databases, often containing only a few million documents
(
bib:qa_dataset
;
bib:ir_dataset
)
.

Impact of large vector databases in RAGs.
With larger vector databases, vector search latency can become a bottleneck, particularly when higher recall is required – i.e., when the system must retrieve a greater proportion of all relevant results to ensure comprehensive and accurate retrieval. Higher recall often necessitates searching a larger set of candidate vectors, expanding the search radius, or lowering approximation thresholds, all of which increase vector search overhead. As a result, while high-recall queries improve response quality by reducing missing relevant information, they also impose greater latency due to the increased search complexity.
Vector search algorithms process millions of vectors, computing distances between the query and database vectors before ranking the most relevant results. This challenge is further exacerbated by modern embedding models, which generate increasingly high-dimensional representations, often spanning several thousand dimensions
(
bib:stella
;
bib:openai_embed
)
. While quantization and compression techniques help mitigate computational costs, they often introduce accuracy loss, limiting their effectiveness in high-precision semantic search
(
bib:highprecision
)
.
As shown in Figure
1
(b), for a fixed vector database containing 128 million vectors of 2048 dimensions, vector search can contribute up to 85.8% of the total Time-to-First-Token (TTFT). This results in a more than 6× increase compared to a standalone LLM, even as the LLM scales with GPU capability and capacity.

Challenges in optimizing vector search across CPUs and GPUs.

Modern CPUs are equipped with vector processing units, and state-of-the-art approximate nearest neighbor search algorithms, such as those based on inverted file indexing (IVF) and product quantization (PQ), exploit these architectures
(
bib:fastscan
)
. Combined with multi-threaded parallel search, these optimizations significantly improve vector search speed
(
bib:faiss
;
bib:scann
)
. However, due to the limited size of vector registers, CPU-based vector processing becomes inadequate for longer embedding vectors and large databases.
With higher parallelism offered by GPUs, vector search can benefit from the GPU’s high-bandwidth HBM and vector processing capabilities. Existing vector search libraries efficiently implement fast vector search algorithms on GPUs
(
bib:faiss_gpu
;
bib:carga
)
. However, using GPUs for vector search in RAGs can be detrimental to overall performance if not carefully managed, as GPU compute and memory resources are scarce and primarily allocated to LLM generation. Even when a quantized vector index fits within the combined memory of multiple GPUs, achieving high recall often requires computing exact distances in the final search stage. This necessitates storing the entire vector database in HBM, making GPU-based solutions infeasible for large vector databases.

Serialized pipeline overhead in RAG systems.

The serialized pipeline of RAG systems, where vector retrieval and LLM inference occur sequentially, introduces latency overhead compared to standalone LLMs that can generate responses immediately. Since the LLM must wait for retrieval to complete before token generation begins, the overall responsiveness of the system decreases, making real-time interactions slower.
This serialized execution complicates seamless integration with highly optimized LLM serving frameworks like vLLM
(
bib:vllm
;
bib:SGlang
;
bib:TensorRT
)
, which are designed for continuous inference with efficient batching and KV cache management.
These frameworks expect a steady stream of token generation requests, but RAG’s dependency on retrieval introduces stalls and irregular workload patterns, disrupting batching efficiency and GPU memory utilization.

As a result, achieving high throughput and low latency in RAG systems requires rethinking how vector search can feed the LLMs continuously.
This can be done through optimized GPU resource sharing, as vector index can benefit from the parallel execution on GPUs, thus reducing the delay in feeding the LLMs with retrieval information.

Balancing throughput and latency in RAG.

To maximize hardware utilization and throughput, queries are typically batched for vector search. Batching significantly improves throughput by enabling more efficient comparison and ranking while avoiding redundant recalculations of shared distance terms. However, it also increases latency due to additional queuing delays and longer processing times. Thus, it is crucial to strike a balance between throughput and latency, especially when meeting SLO.

Optimizing RAG through adaptive vector index partitioning across GPU and CPU.

For the reasons outlined above, optimizing RAG systems requires a holistic approach that considers the impact of GPU optimized vector search on LLM generation, to ensure a balanced pipeline.
In this work, we present
VectorLiteRAG
, a system that optimizes the vector search engine by intelligently sharing GPU resources with the LLM generation and dynamically dispatching tasks to enhance the effectiveness of continuous batching in LLM serving.
To maintain GPU generation throughput, maximizing available memory for LLMs KV cache is essential.
VectorLiteRAG
, thus, jointly considers this trade-off between memory usage between vector index and LLM on the GPU, thus ensuring high workload performance to achieve a faster response.
An adaptive vector index partitioning in
VectorLiteRAG
is based on the insight that popularity patterns exist within vector index clusters. Our analysis of coarse quantizer assignments in vector search reveals exploitable access patterns in indexes.
While search operations in certain clusters take significantly longer, frequently accessed clusters can be prioritized for GPU allocation, enabling parallelized searches that are effectively hidden by CPU search time.
To meet target SLO objectives,
VectorLiteRAG
estimates the optimal vector index partitioning point based on decreasing cluster popularity—ensuring minimal GPU memory overhead for LLMs.
This estimation is based on a simple yet effective statistical model that captures the key characteristics vector index.
This statistical model of the CPU search time, enables
VectorLiteRAG
to determine the amount of vector index that should reside on the GPU, to ensure the RAG pipeline is balanced.
In modeling CPU search time,
VectorLiteRAG
determines the appropriate portion of the vector index to offload onto the GPU, maintaining a balanced RAG pipeline.

Once partitioning is established,
VectorLiteRAG
employs a novel vector search mechanism that effectively utilizes both CPU and GPU. However, introducing hybrid search execution across different platforms introduces variability in query retrieval times.
To address this challenge,
VectorLiteRAG
dynamically and continuously allocates batched requests to the LLM engine as soon as their retrieval is complete. This approach ensures efficient resource utilization, optimizes search latency, and guarantees that vector search results are readily available for response generation— improving the overall performance of the RAG pipeline.
Our contributions are summarized as follows:

•

Joint Optimization of Vector Search and LLM Serving through efficient resource sharing:

VectorLiteRAG
dynamically balances GPU resources between vector search and LLM inference to minimize search overhead without degrading LLM performance. It ensures efficient resource sharing to reduce retrieval latency while maintaining high throughput.

•

Adaptive vector index partitioning based on access-pattern of indexes in vector database:
The system intelligently partitions the vector index across GPU and CPU based on access patterns, prioritizing frequently queried clusters for GPU execution. This approach reduces search latency while preserving high recall.

•

Novel statistical model for resource allocation:

VectorLiteRAG
employs a lightweight statistical model to determine the optimal GPU memory allocation for vector search balancing memory use while considering both latency objectives and throughput metrics.

•

Enabling batched inference and integration with optimized LLM serving frameworks:
By aligning retrieval with frameworks like vLLM,
VectorLiteRAG
avoids inefficiencies from serialized execution and improves batching effectiveness. This results in reduced stalls, faster token generation (TTFT), and improved overall RAG performance.

VectorLiteRag
’s profiler successfully predicts the performance of the partitioned index using profiling results, ensuring that only the necessary clusters are loaded onto the GPU. On the largest dataset,
VectorLiteRag
achieves a 3.1× performance improvement, demonstrating its efficiency in optimizing retrieval latency and resource utilization.

Background and Related Work

2.1.
Retrieval Augmented Generation Pipeline

Retrieval-Augmented Generation (RAG) pipeline combine information retrieval with LLM inference to enable efficient, context-aware response generation
(
bib:rag
;
bib:ragsurvey1
;
bib:ragsurvey2
)
. In RAG systems user queries are transformed into an embedding vector by embedding models such as sentence transformers
(
bib:sentence-transformer
)
. These embeddings capture the semantics of the input, enabling semantic similarity search by comparing query vectors to the embedding vectors obtained from the knowledge base, which are stored in a vector database.
Since exhaustive pairwise search is computationally prohibitive at scale, large-scale vector retrieval relies on approximate nearest neighbor (ANN) search to efficiently identify the most relevant information. The retrieved vectors are then mapped to corresponding documents, which are then provided as additional context to the LLM alongside the original query. This approach enhances the model’s ability to generate accurate, well-grounded responses beyond its static training data.

2.2.
Vector Search and IVF-PQ

In this work, we build on Inverted File System with Product Quantization (IVF-PQ).
IVF-PQ is an efficient algorithm for Approximate Nearest Neighbor Search that balances memory efficiency and search speed through coarse clustering and quantization
(
bib:ivf
)
.
IVF-PQ index subdivide the database into a clusters using k-means clustering, with each cluster represented by a centroid. During index training, data vectors are assigned to their nearest centroids that represent clusters, forming an inverted file structure. Figure
2
illustrates query process in IVF-PQ index. At query time, the query vector is compared against all cluster centroids to identify a small subset of relevant clusters, significantly reducing the search space and improving retrieval efficiency. This stage is called quantization or coarse quantization as it maps the input vector to discrete set of centroid vectors, hence the first layer of index is called coarse quantizer.

The number of clusters selected by the quantizer,
n_{probe}
is tunable main performance parameter of IVF-PQ index. Larger
n_{probe}
leads to longer search time as it requires comparing distances of more vectors, but improves accuracies. Additionally, for larger databases IVF-PQ is trained with higher count of clusters to avoid having clusters that are too larger for fine grained search in the second stage. Thus as the database sizes grow, even higher
n_{probe}
is required to achieve the same level of accuracy.

In the next stage of search process, Product Quantization (PQ) accelerates the distance computations. PQ splits each vector into smaller subspaces and then quantizes them using pre-trained codebooks, and stores them as compact codes. To compare a query vector against the quantized vectors, a lookup table (LUT) that stores partial distances between the query’s subspaces and the PQ centroids is precomputed. Then the full distances is aggregated by scanning through the LUTs. This scanning process is performed cluster by cluster, determining the nearest neighbors. This two-step process - coarse quantization followed by LUT-based PQ refinement - ensures scalability and high performance in large-scale ANN tasks.

GPU based approximate nearest neighbor search.

Prior work on accelerating Approximate Nearest Neighbor (ANN) Search has extensively explored hardware and system-level optimizations to meet the demands of large-scale, high-dimensional data retrieval. GPU-based solutions, such as NVIDIA’s cuANN library and optimizations for frameworks like Faiss, leverage parallelism to accelerate vector similarity computations, enabling low-latency queries over billions of vectors

bib:faiss_gpu

bib:faiss

Numbers of prior works have presented hardware solution designed to accelerate ANNS workloads. Many of these solutions shares the idea to move computation near to the vector data. Employing emerging memory device like CXL is explored to accelerate large scale vector data based on graph base index

bib:cxl-anns

While these approaches achieve significant performance improvements and reduce overall response times, they rely on additional dedicated hardware solely for vector search operations.

3.
Motivation

3.1.
Vector Search Latency Breakdown

Figure 3.
(Left) Latency breakdown of vector search. (Right) LLM throughput comparison when the entire GPU memory is allocated to LLM generation versus when the full vector index is offloaded to the GPU.

The response time in a Retrieval-Augmented Generation (RAG) pipeline is heavily influenced by the retriever’s efficiency, as its latency constitutes a significant portion of the total query processing time.
When the vector database is large and the dimensionality of embedding vectors spans hundreds to thousands, the retriever’s latency becomes a major factor in determining the time to first token, as illustrated in Figure
1
(b). To mitigate this bottleneck, we aim to reduce vector retrieval latency by offloading part of the search process to the GPU.

A deeper analysis of vector search, shown in Figure
3
(left), reveals that the majority of the search time is spent on constructing and scanning the distance lookup table (LUT). Since LUT construction involves computing dot product between query sub-vectors and codebook data, it can be efficiently executed using matrix-vector or matrix-matrix operations that are highly optimized for GPUs. As a result, LUT construction benefits significantly when offloaded to the GPU. Additionally, LUT scanning also sees considerable performance improvements when executed on the GPU, as its large shared memory and high-bandwidth memory (HBM) enable faster table lookups.

Offloading both LUT construction and scanning to the GPU is natural, as splitting them across CPU and GPU would introduce substantial data transfer overhead between the two, negating potential performance gains. In contrast, the coarse quantizer, typically implemented using graph-based indices like HNSW, offers limited parallelization opportunities due to the inherently sequential nature of graph traversal
(
bib:hnsw
)
.
Among the various components of vector search, offloading LUT-related operations to the GPU is expected to yield the highest performance gains, significantly reducing overall retrieval latency in the RAG pipeline.

3.2.
Impact of Naive GPU Index Loading

Although vector search can benefit from GPU execution, naively offloading the entire index to the GPU can negatively impact LLM time-to-first-token (TTFT) by reducing the available memory for the LLM’s KV cache.
Vector search is inherently memory-intensive due to the substantial data movement and storage requirements during retrieval. The large memory footprint of precomputed tables and LUTs, combined with frequent lookups, makes the operation both memory-capacity and I/O-bound. In addition to the sheer volume of vector data, additional temporary memory is required to store lookup table data during execution.
Figure
3
(right) illustrates how LLM throughput decreases when the entire vector index is offloaded to the GPU. The system in this example consists of eight L40S GPUs, each with 48GB of memory, while the loaded database, Stella 2048, occupies 17GB of GPU memory, including vector data, PQ codebooks, and temporary LUT storage. This substantial memory allocation reduces the space available for the LLM’s KV cache, significantly degrading LLM throughput.

3.3.
Uneven Cluster Accesses in IVF-PQ

The distribution of query access patterns in IVF-PQ indexes reveals the presence of “hot clusters,” which are accessed disproportionately more frequently than others.
As shown on the left of Figure
4
, the cumulative distribution function (CDF) of cluster access frequencies for the top-5 documents in queries from the Microsoft’s ORCAS dataset
(
bib:naturalquestion
)
and wiki-all dataset
(
bib:wikiall
)
reveals a sharp concentration of query activity in a small fraction of the clusters. Specifically, 10% of the clusters account for 40% of search operations in wiki-all dataset. For ORCAS queries, around 80% quantization results comes from less than 10% of clusters. This skewed access pattern contrasts with a uniform distribution, indicating that only a small subset of clusters contributes significantly to query results while the majority remain underutilized or sparsely accessed. This uneven workload distribution highlights an inefficiency in the retrieval process, as a large amount of computational effort is expended maintaining and searching infrequently accessed clusters.

The Figure
4
right illustrates the normalized latency of single query search from Wiki-all
(
bib:wikiall
)
dataset, further emphasizes the impact of this phenomenon on execution time. By filtering or skipping retrieval operations for the top 10%-20% of the hottest clusters, substantial latency reductions can be achieved, as these clusters contribute disproportionately to the computational cost. Despite their small portion of the total cluster set, the hottest clusters dominate execution time due to repeated access and computational overhead associated with them. This shows the importance of optimizing retrieval mechanisms to prioritize frequently accessed clusters and minimize unnecessary operations on less active ones. Furthermore, the rightmost bar in the figure represents GPU search time without filtering. Although GPU search involves communication overhead between CPU and GPU, the latency of a full single query search is still lower than that of the filtered CPU search. This demonstrates that, as claimed earlier, GPU search can run concurrently with the CPU fast scan, achieving complete overlap and further reducing the latency.

The access skew between hot and cold clusters presents an opportunity for significant performance improvements in RAG pipelines through better vector index placement.

4.
Design

VectorLiteRAG
is an optimized Retrieval-Augmented Generation (RAG) system designed to minimize query processing serialization by efficiently utilizing GPU memory for both vector indexing and LLM execution.
While both vector search and LLM inference benefit from GPU acceleration, they compete for memory and compute resources, necessitating careful workload distribution to maintain a balanced RAG pipeline.

VectorLiteRAG
introduces a novel vector indexing framework that adaptively partitions the vector index across CPU and GPU while ensuring efficient utilization of GPU High-Bandwidth Memory (HBM) for both the index and LLM execution. By leveraging the GPU’s parallelism for vector search, the framework reduces search latency, enabling higher-throughput batched processing within the RAG pipeline. This design improves system efficiency while meeting user-defined SLO requirements.

VectorLiteRAG
is based on the insight that certain clusters in the vector database are accessed significantly more frequently than others, making them ideal candidates for adaptive index distribution across memory.

VectorLiteRag
performs two key tasks. First, during initialization, it determines the
minimum
GPU memory allocation for the vector index based on user-defined SLO requirements, selectively caching the portion of the index associated with frequently accessed hot clusters on the GPU. The classification of clusters as hot or cold is guided by profiling a few hundred batched requests and is re-calibrated if access patterns shift. To determine the optimal index partitioning,
VectorLiteRag
employs a lightweight yet accurate model to estimate batch processing time and throughput for different hit rates—that is, the proportion of cluster processing that can be offloaded to the GPU versus the CPU.
Second, during steady-state operation, the framework employs a hybrid index search algorithm that leverages adaptive index partitioning to maximize the GPU’s parallel compute capabilities and HBM, accelerating searches for hot clusters. Its compute resource manager dynamically allocates GPU resources across vector search, embedding transformations, and LLM generation, optimizing throughput while minimizing contention. This enables
VectorLiteRAG
to dispatch queries to the LLM as soon as their top-k results are retrieved, eliminating the need to wait for all queries in a batch to complete.

With this adaptive partitioning scheme,
VectorLiteRag
enhances the responsiveness of the RAG pipeline while maximizing resource efficiency.
These integrated optimizations are illustrated in Figure
5
, where the patterned blocks represent the novel components of the
VectorLiteRag
framework, which optimizes the pipeline based on its partitioning strategy.

4.1.
Adaptive Vector Index Partitioning

This section explains the initialization of
VectorLiteRag
to classify clusters into frequently accessed ”hot“ clusters (on GPU HBM) and the remainder ”cold“ clusters (in CPU memory).
Due to the access-skew, profiling is only required to be performed for a very small number of requests (100 batched requests) to classify the clusters
(
fae
;
hotline
)
.
By profiling a few of the initial query patterns, the system can identify the most frequently accessed clusters and adaptively offloads a portion of the index corresponding to those clusters onto the GPU, leveraging its high-bandwidth memory (HBM) and parallel processing capabilities for faster index searching.
While storing a larger portion of the index on the GPU improves vector search latency, loading the entire index onto the GPU can negatively impact LLM efficiency, especially as the vector database scales.
To balance this trade-off,
VectorLiteRag
employs a profiling-based partitioning strategy that dynamically determines the optimal split between GPU and CPU for vector database. This adaptive memory placement is guided by historical access patterns, latency statistics, and SLO requirements, ensuring efficient resource allocation to improve the responsiveness of the system.

Modeling CPU index search time.

We need to determine the CPU search time when the index is partitioned across CPU and GPU.
Since GPU search time is hidden behind CPU search time for cold clusters, modeling GPU latency is unnecessary.
This search time estimation model is based on the insight that when the entire database resides on the CPU, lookup table (LUT) operations dominate search time. Both LUT operations and coarse quantization exhibit an almost linear increase in execution time as batch size grows (Figure
6
).
The execution time for coarse quantization is primarily driven by graph traversal and distance computations. As more queries are processed, the number of traversals and computations increases. However, because entry nodes and their neighboring nodes are frequently revisited, graph-based coarse quantization benefits from cache locality, leading to a sublinear growth trend.
In contrast, the execution time of LUT operations is directly proportional to the size and number of LUTs, both of which scale with batch size, resulting in a linear growth pattern. To model execution time, each operation can be effectively approximated using a linear equation, with slopes
a_{cq}
and
a_{lut}
and intercepts
T_{c_{0}}
and
T_{l_{0}}
.

(1)

T^{cpu}_{search}=T_{cq}+T_{lut}=(a_{cq}B+T_{c0})+(a_{lut}B+T_{l0})

When the index is partitioned across the CPU and GPU, CPU search time is estimated based on the number of clusters accessed from the cold pool. The proportion of clusters retrieved from the GPU per request is referred to as the hit rate, which directly impacts the CPU search latency—higher hit rates reduce CPU search time, while lower hit rates increase it.
For a given hit rate
\eta
, the CPU search time
T^{cpu}_{search}
for a query in the partitioned index must be estimated. Since LUT processing scales with the number of clusters searched on the CPU, search time is proportional to the number of CPU-resident clusters. If a query has a GPU hit rate of
\eta
, its CPU search time reduces to:

(2)

T^{cpu}_{search}=T_{cq}+(1-\eta)T_{lut}

Estimating CPU search time.

In inverted file indexes, each query selects
n_{probe}
clusters for nearest neighbor search. By identifying frequently accessed clusters and loading them onto the GPU, a significant portion of search operations can be offloaded to GPU memory, improving query efficiency. However, not all
n_{probe}
clusters are guaranteed to reside on the GPU. As more clusters are accessed on the CPU, search time increases, impacting both individual query latency and batch processing time.
To model batch CPU search time in a partitioned index, we estimate the minimum GPU index hit rate within a batch. While accesses to less frequently used clusters appear nearly random, they can be approximated using a Beta-binomial distribution.
The Beta-binomial distribution models a process where an event succeeds with an average probability
\eta_{0}
, but unlike a simple binomial distribution, the success probability varies according to a Beta distribution.
Based on this insight,
VectorLiteRag
defines the probability of a query hitting
k
clusters on the GPU. The probability that the query with the fewest GPU hits in a batch has
k
hits is given by:

(3)

P\left(k\right)=B\cdot BetaBin(k)[1-F(x>k)]^{B-1}

where
F(x)
is the cumulative-Beta-binomial distribution. The expected minimum hit rate is obtained by summing over this distribution:

(4)

\footnotesize E\left[\eta_{min}\right]=\frac{1}{n_{probe}}\sum_{k=0}^{n_{probe}}B\cdot x\cdot BetaBin(x)[1-F(x)]^{B-1}

Using this expected hit rate, the CPU search time for a partitioned vector index can be estimated as:

(5)

T^{cpu}_{search}=T_{cq}+(1-E\left[\eta_{min}\right])T_{lut}

This search time estimation allows us to compute the throughput of the partitioned index as:

(6)

\mu_{cpu}=\frac{B}{T^{cpu}_{search}}

The intersection of this throughput with the user’s SLO constraints determines the minimum hit rate—and consequently, the smallest portion of the vector index that must reside on the GPU.

Figure 7.
QPS vs. batch size curve used to determine the optimal hit rate.

Profile-guided hit rate estimation based on throughput estimation and SLO requirements.

By solving two constraints, we determine the minimum required hit rate, which in turn defines the necessary partitioning percentage of the index.

(1) Throughput Constraint: The vector search throughput from Equation 6 must be at least equal to the GPU’s LLM generation throughput to ensure that search does not become a bottleneck in the pipeline:

(7)

\mu_{cpu}\geq LLM_{t}

The LLM throughput depends on both the GPU and the ML model. Since
VectorLiteRag
does not optimize LLM execution, this value is treated as a fixed constant for each model and GPU type.

(2) Latency Constraint: The time to generate the first token must satisfy the user-defined SLO requirements. The feasible hit rates are those that meet both constraints. We use the CPU vector search SLO as a proxy for the overall end-to-end system performance SLO, as it needs to ensure that moving the indexes to the GPU does not violate the LLM SLO.

Figure
7
illustrates the throughput curve based on precomputed hit rates and batch sizes. The shaded region highlights the hit rates that satisfy both constraints. The expected throughput at different mean hit rates is shown as blue curve, while the GPU’s maximum LLM serving rate is represented by a horizontal QPS line. To fully utilize the GPU for LLM inference, the search engine must operate above this threshold. This threshold shifts depending on the LLM model and GPU configuration.
Among the feasible configurations after applying constrain 1 of the LLM throughput threshold,
VectorLiteRag
selects the lowest hit rate that still meets performance requirements. This approach ensures a memory-efficient GPU index while maintaining high search performance. The selection process involves scanning the hit rate range and choosing the optimal mean hit rate
\eta_{0}
for partitioning.
This second constraint, is represented as following:

(8)

SLO^{cpu}_{search}\geq QueuingDelay+T^{cpu}_{search}(B)

In the steady state, to achieve optimal performance, the batch queuing time and the search time should be approximately equal, modifying the above equation to:

(9)

SLO^{cpu}_{search}\geq 2\times T^{cpu}_{search}(B)

Using Equation 6, we express CPU search time in terms of throughput:

(10)

\mu_{cpu}=\frac{B}{T^{cpu}_{search}}\geq\frac{2B}{SLO^{cpu}_{search}}

By solving the constraints in Equations 7 and 9, we determine the smallest required hit rate. In Figure

, this value is 0.7.

Converting hit rate to cluster classification and index partitioning.

Once the hit rate is determined, we use interpolated data from the access patterns of past queries (such as the data shown in Figure
4
) to model the relationship between hit rate and cluster loading. By analyzing the CDF of these access patterns, we can invert the relationship to estimate the portion of clusters that should be loaded onto the GPU in order to achieve the desired hit rate. This approach leverages historical query access patterns to predict the optimal cluster distribution that balances memory usage and search performance.

When the indexes are loaded onto the GPUs, the clusters (which are groups of data) are distributed across the GPUs in a round-robin manner. This means that the data is spread evenly across the devices, one cluster at a time, to make sure that no single GPU becomes overloaded with too much data.
Larger clusters are typically accessed more frequently and use more memory. By distributing the clusters evenly across GPUs, this strategy helps to ensure that each GPU has a similar amount of memory used for storing the LLM’s KV cache. It also makes sure that the work (i.e., handling the queries) distributed fairly across all the GPUs.
This balanced distribution prevents any one GPU from being overburdened with too much data or too many queries, slowing down the system. As a result, the overall system works more efficiently, both in terms of memory usage and query processing.

Re-calibrating the hot and cold clusters.

As the access skew of clusters changes over time, the partitioning of the vector index based on evolving hot and cold clusters must be dynamically adjusted. This dynamic partitioning affects the slope of the CDF in Figure
4
, as the distribution of hot and cold clusters can shift. The hit rate remains unchanged, as it is determined by the CPU search time and the percentage of hits on the GPU, rather than by which clusters are hot or cold.
Additionally, while the memory assignment, SLO requirements, and LLM throughput remain unchanged, the vector index corresponding to the newly identified hot clusters must be swapped with the older hot clusters on the GPU.

4.2.
Concurrent Search of Partitioned Index

While partitioning vector data based on access patterns, or ”hotness“, significantly improves system utilization by allocating more frequently accessed clusters to the GPU, it introduces a new challenge. Specifically, due to the variability in retrieval times between the CPU and GPU, different queries may might be ready for LLM at different times.
This variability in retrieval times can lead to imbalances in overall system, where some queries finish retrieval earlier and remain idle while waiting for slower queries to complete. To address this challenge, we propose novel components – namely, a partitioning-aware quantizer and a streamlined result dispatcher—that work together to mitigate this variability.
Since both the CPU and GPU are utilized for vector search and operate concurrently, the search workload is split across devices and later merged. Each index shard independently searches for the top-
k
nearest neighbors within its assigned cluster pool. Once the last shard, including the CPU index, completes its search, the results from all devices are merged and re-ranked to obtain the final top-
k
nearest neighbors.

Partitioning-aware Quantizer

Existing vector search libraries typically rely on a static search configuration, using a fixed number of probes (
n_{\text{probe}}
) for all queries. In these systems, the scanning of distance lookup tables (LUTs) and vector data follows a strided approach with fixed widths and lengths. However, in
VectorLiteRag
, the number of clusters searched per device varies depending on the query, resulting in irregularly shaped data structures. To address this, it is crucial to efficiently track the coarse quantization results of each query in order to access the relevant data and minimize redundant computations during the distance scanning process.
To manage and track clusters effectively during the search process, we introduce a partitioning-aware coarse quantizer. The quantizer relies on a centroid ID mapping table, maintained by the index manager, to identify whether a cluster is a hit or miss. It tracks the effective number of probes to calculate the memory addresses for the LUTs and vector data.
During coarse quantization, clusters are assigned based on their hit or miss status. For each hit, the number of clusters searched within the CPU index is decremented. For each miss, the coarse quantizer assigns a centroid ID of -1, effectively marking the cluster as unassigned in the GPU index. This mechanism prevents unnecessary distance computations for query-cluster pairs that do not match.
Given the highly parallelized nature of the GPU, the search kernel is launched with a 2D rectangular grid of thread blocks. To optimize resource allocation, the kernel is initially launched with a reduced grid size, where the width is adjusted to minimize the number of allocated thread blocks and reduce overhead. Additionally, because missed clusters are assigned a value of -1, the GPU can skip computations for those clusters, further alleviating computational pressure.

Streamlined Result Dispatcher

In traditional Retrieval-Augmented Generation (RAG) pipelines, vector search engines often wait for all queries in a batch to complete before proceeding to the next stage. This introduces unnecessary latency, particularly when some queries finish their retrieval process early but remain idle, waiting for slower queries to complete. To address this,
VectorLiteRAG
introduces a streamlined result dispatcher that dynamically merges and dispatches results to the LLM as soon as the top-
k
nearest neighbors are retrieved from the vector database.
In
VectorLiteRag
, popular clusters are rapidly processed on the GPU, which reduces the number of scanning loops required on the CPU. However, certain tail-case queries that access a large number of CPU-resident clusters may still experience extended search times. To mitigate the impact of such queries on overall batch performance, the dispatcher monitors each query’s scanning status in real time.
Upon completion of the GPU search, the dispatcher merges the GPU search results into the intermediate CPU search results for each query. It also tracks the number of clusters scanned for each query. If a query has completed scanning all the relevant clusters, and the GPU results are already merged, the dispatcher immediately forwards the results for document retrieval and LLM generation, rather than waiting for all queries in the batch to finish.
The dispatcher operates as a bridge between the vector search engine and the LLM engines, which are executed in separate sub-processes running on dedicated cores. It continuously invokes a callback function that triggers document retrieval from the knowledge base and subsequent LLM generation. This architecture ensures that queries are processed as soon as sufficient results are available, effectively utilizing the continuous batching capabilities of the LLM.

Through the integration of an adaptive cluster-level partitioning scheme, dynamic query tracking, and resource-aware management,
VectorLiteRAG
enhances system performance by leveraging the GPU’s computational power to accelerate vector search. The proposed approach improves scalability and resource efficiency by optimizing GPU memory usage and balancing computational load across vector index and LLM execution.

6.
Conclusion

In this paper, we propose
VectorLiteRAG
, a system that optimizes RAG pipeline by strategically partitioning vector search between the CPU and GPU while ensuring efficient LLM execution. Unlike traditional approaches that statically allocate resources,
VectorLiteRAG
dynamically balances GPU memory between the vector index and LLM KV cache, maximizing search acceleration without compromising generation throughput.
By leveraging an adaptive partitioning scheme,
VectorLiteRAG
efficiently places frequently accessed clusters on the GPU, reducing retrieval latency and enhancing overall pipeline responsiveness. It effectively determines the optimal partitioning point that satisfies the given SLO requirements, achieving an average TTFT reduction of 2×. Additionally, the partitioning-aware quantizer and streamlined result dispatcher mitigate retrieval variability between CPU and GPU searches, enabling continuous batching for LLM serving.
