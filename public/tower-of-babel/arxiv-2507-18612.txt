Approximate SMT Counting Beyond Discrete Domains
Arijit Shaw, Kuldeep S. Meel

Abstract
Satisfiability Modulo Theory (SMT) solvers have advanced automated reasoning, solving complex formulas across discrete and continuous domains. Recent progress in propositional model counting motivates extending SMT capabilities toward model counting, especially for hybrid SMT formulas. Existing approaches, like bit-blasting, are limited to discrete variables, highlighting the challenge of counting solutions projected onto the discrete domain in hybrid formulas. We introduce 𝗉𝖺𝖼𝗍 \textstyle\mathsf{pact} , an SMT model counter for hybrid formulas that uses hashing-based approximate model counting to estimate solutions with theoretical guarantees. 𝗉𝖺𝖼𝗍 \textstyle\mathsf{pact} makes a logarithmic number of SMT solver calls relative to the projection variables, leveraging optimized hash functions. 𝗉𝖺𝖼𝗍 \textstyle\mathsf{pact} achieves significant performance improvements over baselines on a large suite of benchmarks. In particular, out of 14,202 instances, 𝗉𝖺𝖼𝗍 \textstyle\mathsf{pact} successfully finished on 603 instances, while 𝖡𝖺𝗌𝖾𝗅𝗂𝗇𝖾 \textstyle\mathsf{Baseline} could only finish on 13 instances.

I-A

Applications

We now discuss four motivating applications for counting over hybrid SMT formulas.

Robustness Analysis of Automotive Cyber-Physical Systems.

Evaluating robustness is crucial in automotive cyber-physical systems (CPS), especially with the rise of autonomous vehicles. Koley et al.
[
28
]
encoded the problem using SMT to identify potential CPS attack vectors, incorporating both discrete and continuous variables to represent cybernetic and physical aspects, respectively. This framework extends to a quantitative approach, where the problem becomes an SMT counting query. Robustness is assessed by counting potential attack points, with the projection set defined by the system’s input parameters.

Reachability Analysis of Critical Software.
Consider a control-flow graph (CFG) of critical software, where we are interested in knowing how many different paths exist in that CFG, such that some violating conditions are reached. We can encode this problem as a counting problem on the SMT formula with discrete and continuous variables, and the projection set would contain Boolean variables indicating whether a node of CFG is reachable. The projected model count will give the number of satisfying paths in CFG.

Quantitative Software Verification.

To ensure software reliability, identifying bugs is not always sufficient; a quantitative approach is vital for understanding their impact. A program with an assertion is converted into an SMT formula through a Single Static Assignment (SSA), revealing inputs that lead to assertion failures by counting these specific inputs. Teuber and Weigl
[
4
]
reduced the quantitative verification to projected counting over hybrid SMT formulas, wherein the underlying theory is QF_BVFP.

Quantification of Information Flow.

In the domain of software reliability, the quantification of information flow represents a critical challenge, particularly in measuring information leakage within industrial software applications. Phan and Malacaria
[
29
]
showed that the problem of quantification of information flow in the case of standard programs can be reduced to the task of counting over hybrid SMT formulas defined over QF_BVFP.

II
Preliminaries

Satisfiability Modulo Theory (SMT)

[
8
]
combines Boolean satisfiability (SAT) with theories such as integer and real arithmetic, bit-vectors, arrays, enabling efficient and automated analysis of logical formulas involving various data types.
SMT solvers
solves the satisfiability of an SMT formula.

Hybrid SMT Formulas.
Some SMT theories are discrete (such as bitvectors and integers), while others are continuous (such as reals and floating points).
We define a
hybrid SMT formula
as an SMT formula that combines two or more theories, where there is at least one discrete theory and one continuous theory. For example, a formula in QF_BVLRA is a hybrid formula because it contains both real variables (continuous) and bitvector variables (discrete).

Projection Set and Projected Solutions.

Let
\textstyle F
represent an SMT formula, where
\textstyle\mathsf{Vars}(F)
signifies the set of all variables of
\textstyle F
. A

\textstyle S
is a subset of
\textstyle\mathsf{Vars}(F)
. Given an assignment
\textstyle\tau
to
\textstyle\mathsf{Vars}(F)
,
\textstyle T_{\downarrow S}
denotes the projection of
\textstyle\tau
on
\textstyle S

\textstyle\mathsf{Sol}(F)
denotes the set of all solutions to the formula
\textstyle F
.
\textstyle\mathsf{Sol}(F)_{\downarrow{S}}
represents the set of all solutions of
\textstyle F
projected on
\textstyle S
. In the context of this paper,
\textstyle S
is a set of discrete variables and therefore,
\textstyle\mathsf{Sol}(F)_{\downarrow{S}}
is a finite set.

Model Counting.

Given a formula
\textstyle F
and a projection set
\textstyle S
, the problem of model counting is to compute
\textstyle|\mathsf{Sol}(F)_{\downarrow{S}}|
.
An
approximate model counter
takes in a formula
\textstyle F
, projection set
\textstyle S
, tolerance parameter
\textstyle\varepsilon
, and confidence parameter
\textstyle\delta
, and returns
\textstyle c
such that
\textstyle\Pr\left[\frac{|\mathsf{Sol}(F)_{\downarrow{S}}|}{1+\varepsilon}\leq c\leq(1+\varepsilon)|\mathsf{Sol}(F)_{\downarrow{S}}|\right]\geq 1-\delta
.

Hash functions.

A
hash function

\textstyle h:U\to[m]
maps elements from a universe
\textstyle U
to a range
\textstyle[m]=\{0,1,\dots,m-1\}
. A
pairwise independent hash function
is a hash function chosen from a
family

\textstyle\mathcal{H}
of functions
\textstyle h:U\to[m]
such that, for any two distinct elements
\textstyle x_{1},x_{2}\in U
and for any
\textstyle i_{1},i_{2}\in[m]

\textstyle\Pr[h(x_{1})=i_{1}\land h(x_{2})=i_{2}]=\nicefrac{{1}}{{m^{2}}}.

A
vector hash function

\textstyle h:U^{d}\to[m]
extends this concept by mapping
\textstyle d
-dimensional vectors of
\textstyle w
-bit integers to the range
\textstyle[m]
.
In this paper, the term
hash function
refers to
hash-based constraint
, represented as
\textstyle h(\mathbf{x})=\alpha
. The solutions of the formula
\textstyle F\land(h(\mathbf{x})=\alpha)
form a subset of the solutions to
\textstyle F
, restricted to those where the hash function maps to
\textstyle\alpha
.

III-A

Hash functions.

The choice of hash function is one of the most important parts in a hashing-based model counter like
\textstyle\mathsf{pact}
.
In
\textstyle\mathsf{pact}
, we experiment with three different pairwise independent vector hash functions, which have been used in different literature.

•

Multiply mod prime
(
\textstyle\mathcal{H}_{\textit{prime}}
)
[
46
]
: For a prime number
\textstyle p
, and independent random values
\textstyle\mathbf{a}=a_{0},\ldots,a_{d-1},b\in[p]
, the hash function from
\textstyle[p]^{d}
to
\textstyle[p]
is given by:

h_{\mathbf{a},b}(\mathbf{x})\equiv\left(\sum_{i\in[d]}a_{i}x_{i}+b\right)\bmod p=\alpha

•

Multiply-shift (
\textstyle\mathcal{H}_{\textit{shift}}
)

[
47
]
: For independent random values
\textstyle\mathbf{a}=a_{0},\ldots,a_{d-1},b\in[2^{\overline{w}}]
, where
\textstyle\overline{w}\geq w+\ell-1
the hash function from
\textstyle[2^{w}]^{d}
to
\textstyle[2^{\ell}]
is given by:

h_{\mathbf{a},b}(\mathbf{x})\equiv\left(\sum_{i\in[d]}a_{i}x_{i}+b\right)[\overline{w}-\ell,\overline{w})=\alpha

•

Bitwise XOR (
\textstyle\mathcal{H}_{\textit{xor}}
)

[
48
]
: This is a particular case of the multiply mod prime scheme when
\textstyle p=2
.

h_{\mathbf{a}}(\mathbf{x})\equiv\bigoplus_{\{i|a_{i}=1\}}x_{i}=\alpha

Given the type of hash function to generate, the procedure
\textstyle\mathsf{GenerateHash}
generates the constraints of the form
\textstyle h_{\mathbf{a},b}=\alpha
, where
\textstyle\alpha
is a randomly chosen element from the domain of the hash function.
When this hash function-based constraint
\textstyle H
is added to the input formula
\textstyle F
,
\textstyle F\land H
satisfies only those solutions of
\textstyle H
for which the hashed value by
\textstyle H_{\mathbf{a},b}
is
\textstyle\alpha
.
therefore, the number of solutions of
\textstyle F\land H
is approximately
\textstyle p^{th}
fraction of number of solution of
\textstyle F
.

\textstyle\mathcal{H}_{\textit{prime}}
and
\textstyle\mathcal{H}_{\textit{shift}}
are word-level hash functions that allow us to choose a number of partitions we want to divide our solution space into. When
\textstyle\mathsf{pact}
uses these hash functions, along with the projection set
\textstyle S
, and the
\textstyle\mathsf{family}
,
\textstyle\mathsf{GenerateHash}
takes a parameter
\textstyle\ell
, and generates a hash function with domain size
\textstyle p
, such that
\textstyle 2^{\ell}\leq p<2^{\ell+1}
. Specifically, in
\textstyle\mathcal{H}_{\textit{shift}}
,
\textstyle p=2^{\ell}
, in
\textstyle\mathcal{H}_{\textit{prime}}
,
\textstyle p
is the smallest prime
\textstyle>2^{\ell}
.
In case of
\textstyle\mathcal{H}_{\textit{xor}}
,
\textstyle\ell=1,p=2
.
As
\textstyle S
is evident from the context, and
\textstyle\mathbf{a},b
are randomly generated, we use the notation
\textstyle h
instead of
\textstyle h(S)
to denote the hash functions.

While each of the hashing constraints partitions the solution space into
\textstyle p
slices, we often want to partition it into more.
To partition the solution space into
\textstyle p^{c}
cells, we use the Cartesian product of
\textstyle c
hash functions:
\textstyle\mathcal{H}\times\mathcal{H}\times\dots\times\mathcal{H}
. We use the notation
\textstyle H_{[i]}
to denote the Cartesian product of the first
\textstyle i+1
hash functions, i.e.,
\textstyle H_{[i]}=h_{0}\times h_{1}\times\dots\times h_{i}
.

In
\textstyle\mathsf{GenerateHash}
subroutine of
\textstyle\mathsf{pact}

slice
them into bitvectors of smaller width so that the value of (sliced) bitvector lies within the domain of the hash function.
Instead of defining hash functions on the variables from
\textstyle S
, we define hash functions on
slices
of the variables, defined as follows:
For a bitvector
\textstyle\mathbf{x}
of width
\textstyle w
, we define
\textstyle\lceil w/\ell\rceil
slices of width
\textstyle\ell
:

\textstyle x(\lceil w/\ell\rceil-1),\dots,x(1),x(0)
, where
\textstyle x(i)=x\left[{(i+1)\ell}-1:{i\ell}\right]
.

III-B

Enumerating in a cell.

Another crucial step in
\textstyle\mathsf{pact}
is to determine when the size of a cell is less than the threshold.
\textstyle\mathsf{pact}
uses the
\textstyle\mathsf{SaturatingCounter}
subroutine to enumerate solutions of the formula
\textstyle F\land H_{[i]}
to determine the size. An SMT solver is employed to find a solution
\textstyle\mathsf{res}
for the given formula
\textstyle F
. The projection of this solution,
\textstyle\mathsf{res}_{\downarrow S}
, is then
blocked
by adding a constraint
\textstyle\neg(\mathsf{res}_{\downarrow S})
. Subsequently, the solver is asked to find another solution. This process is repeated in a loop until the solver finds
\textstyle\mathsf{thresh}
many solutions or reports UNSAT.

III-E

Impact of Hash Function Families

Our empirical evaluation indicates
\textstyle\mathsf{SaturatingCounter}
is computationally the most expensive subroutine during execution of
\textstyle\mathsf{pact}
. Recall that
\textstyle\mathsf{SaturatingCounter}
is invoked over the formula instance
\textstyle F\land H_{[i]}
; naturally, the choice of the hash function
\textstyle\mathsf{family}
impacts the practical difficulty of the instance
\textstyle F\land H_{[i]}
. Below, we highlight the tradeoffs offered by different hash function families along many dimensions.

•

Bit-level vs. Bitvector Operations:
The hash function
\textstyle\mathcal{H}_{\textit{xor}}
operates at the bit level, whereas
\textstyle\mathcal{H}_{\textit{shift}}
and
\textstyle\mathcal{H}_{\textit{prime}}
function on bitvectors, making the latter two more amenable to SMT reasoning. This fundamental difference in operation also enables
\textstyle\mathcal{H}_{\textit{prime}}
and
\textstyle\mathcal{H}_{\textit{shift}}
to vary the hash function’s domain sizes, a flexibility not available with
\textstyle\mathcal{H}_{\textit{xor}}
.

•

Number of hash functions:
As each hash function cannot partition the solution space by more than two partitions,
\textstyle\mathcal{H}_{\textit{xor}}
requires more number of constraints for counting an instance compared to
\textstyle\mathcal{H}_{\textit{shift}}
and
\textstyle\mathcal{H}_{\textit{prime}}
. A number of constraints generally make the problem harder for the solver to solve efficiently.

•

Complexity of required operations:
Multiplication and modulus operations impose significant computational overhead on SMT solvers, making
\textstyle\mathcal{H}_{\textit{prime}}
and
\textstyle\mathcal{H}_{\textit{shift}}
more complicated than
\textstyle\mathcal{H}_{\textit{xor}}
. Moreover, when
\textstyle\mathsf{pact}
uses
\textstyle\mathcal{H}_{\textit{xor}}
, it leverages the native XOR reasoning capability of
\textstyle\mathsf{CryptoMiniSat}
SAT solver inside
\textstyle\mathsf{pact}
, further increasing the counter’s performance.

•

Requirement of bitwidth:
To represent the value of
\textstyle\sum a_{i}x_{i}
, a bitvector of width
\textstyle 2w
is required in
\textstyle\mathcal{H}_{\textit{shift}}
, whereas a bitwidth of
\textstyle 2w+d
is needed in
\textstyle\mathcal{H}_{\textit{prime}}
, as the hash value in
\textstyle\mathcal{H}_{\textit{shift}}
is calculated modulo
\textstyle 2^{2w}
, while in
\textstyle\mathcal{H}_{\textit{prime}}
is computed modulo a prime. Since SMT solver performance degrades quickly with increasing bitwidth,
\textstyle\mathcal{H}_{\textit{shift}}
is a more favorable choice in this context. In an alternative implementation of
\textstyle\mathcal{H}_{\textit{prime}}
, each term
\textstyle a_{i}x_{i}
could be represented modulo a prime, but this would require an additional
\textstyle d
modulo operations, increasing complexity.

IV
Experimental Evaluation

We implemented the proposed algorithm on top of state-of-the-art SMT solver
cvc5
. We used the following experimental setup in the evaluation:

Baseline.
As mentioned in Section
I
, the existing tools for SMT counting are unable to handle
\textstyle\mathsf{Count{\mathcal{T}}_{\downarrow{\mathcal{P}}}}
problems. The situation is similar to the early days of propositional model counting, wherein enumeration-based counters were employed as a baseline. In the same vein, we developed an enumeration-based counter, referred to as
\textstyle\mathsf{Baseline}
, that uses the state-of-the-art SMT solver,
cvc5
, the same solver employed by
\textstyle\mathsf{pact}
.
\textstyle\mathsf{Baseline}
operates by asking for a solution from the SMT solver and then appending a blocking clause that includes assignments to the projection variable. Subsequently, it asks the solver for another solution, continuing this process until the solver indicates UNSAT.

Benchmarks.

Our benchmark suite comprises 14,202 instances from the SMT-Lib 2023 release. To minimize bias, we adopted a benchmark selection methodology inspired by early works on propositional model counting. We initially selected all instances supported by six theories. Subsequently, we filtered out instances where the number of solutions was very small (less than 500 models) or where even satisfiability was computationally challenging, as determined by
cvc5
’s inability to find a satisfying assignment within 5 seconds.

Environment.
We conducted all our experiments on a high-performance computer cluster, with each node consisting of Intel Xeon Gold 6148 CPUs. We allocated one CPU core and an 8GB memory limit to each solver instance pair. To adhere to the standard timeout used in model counting competitions, we set the timeout for all experiments to 3600 seconds. We use values of
\textstyle\varepsilon=0.8
and
\textstyle\delta=0.2
, in line with prior work in the model counting community.

We conduct extensive experiments to understand the following:

RQ1.

How does the runtime performance of
\textstyle\mathsf{pact}
compare to that of
\textstyle\mathsf{Baseline}
, and how does the performance vary with different hash function families?

RQ2.

How accurate is the count computed by
\textstyle\mathsf{pact}
in comparison to the exact count?

From our benchmark set, only 13 instances were solved by

\textstyle\mathsf{Baseline}

\textstyle\mathsf{pact}

\textstyle\varepsilon
. Analysis of all 64 cases found that for
\textstyle\mathsf{pact}_{\textit{xor}}
, the maximum
\textstyle e
to be
\textstyle 0.26
and the average to be
\textstyle 0.03
, signifying
\textstyle\mathsf{pact}
substantially outperforms its theoretical bounds, which is 0.8. In

V
Conclusion and Future Work

In this work, we introduced
\textstyle\mathsf{pact}
, a projected model counter designed for hybrid SMT formulas. Motivated by the diverse applications of model counting and the role of hashing, we explored the impact of various hash functions, examining both bit-level and bitvector-level approaches. Our empirical evaluation demonstrates that
\textstyle\mathsf{pact}
achieves strong performance on a broad application benchmark set. A dedicated XOR reasoning engine significantly enhanced
\textstyle\mathsf{pact}
’s performance, suggesting that further development of specialized reasoning engines for bit vector-level hash functions could be a promising research direction. Additionally,
\textstyle\mathsf{pact}
’s theoretical framework supports the SMT theory of integers (with specified bounds) as projection variables; this feature is not yet implemented and remains an avenue for future work.
