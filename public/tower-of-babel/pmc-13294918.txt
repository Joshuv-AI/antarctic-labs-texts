MOrbVis: Browser-Based Molecular Orbital Visualization with WebGPU-Accelerated On-the-Fly Evaluation
Authors: Yasuaki Ito, Satoki Tsuji, Koji Nakano, Akihiko Kasagi
Published: 2026

ABSTRACT
MOrbVis is an open-source web application that visualizes molecular orbitals directly in the browser without precomputed Gaussian Cube files. Reading only a Molden file, it evaluates Gaussian-type basis functions (s through g shells) on a three-dimensional grid through WebGPU compute shaders. Benchmarks on five devicesfrom a smartphone to a desktop with an NVIDIA RTX 5090show that single-orbital evaluation on grids exceeding 106 points finishes within 100 ms, up to 3 orders of magnitude faster than the single-threaded CPU path. The tool requires no installation and is available at https://yasuaki-ito.github.io/morbvis/.

Introduction

Molecular orbitals (MOs) provide a direct window into the electronic structure of molecules: bonding patterns, lone pairs, and frontier orbital interactionsparticularly the highest occupied MO (HOMO) and lowest unoccupied MO (LUMO)underpin much of chemical reasoning in quantum chemistry (QC). , Visualization of these orbitals is therefore a routine yet important step in electronic structure calculations. Historically, the standard practice has followed a two-stage pipeline. First, an electronic structure programGaussian, PySCF, GAMESS, ORCA, GANSU, or otherssolves the Schrödinger equation and stores MO coefficients in the chosen basis set. Second, the same or a companion program evaluates the MO on a three-dimensional grid and writes the result as a Gaussian Cube file, which a separate visualization application (GaussView, VMD, Avogadro, Molden, IboView) reads to extract and render isosurfaces.

This Cube-file-centric workflow became the norm for a clear historical reason: when desktop applications were the only visualization option, shipping precomputed volumetric data was the most practical way to decouple the QC engine from the viewer. However, the approach carries costs that have become increasingly apparent as electronic structure studies are performed across diverse computing environments:Data bloat. A single Cube file at 1003 resolution occupies ∼13 MB in the standard ASCII format. The grid spacing and spatial extent are locked at export time. Adjusting these parameters requires returning to the QC program and regenerating the Cube data, breaking the interactive exploration loop.Installation barrier. Desktop viewers require OS-specific installation, graphics driver configuration, and sometimes commercial licenses.

Why has this workflow persisted? The key bottleneck is computational. Evaluating the linear combination of atomic orbitals (LCAO) expansion ψ i (r) = ∑μ C μi χμ(r) at N = 106–107 grid points requires O(NM) floating-point operations, where M is the number of basis functions. On a single CPU thread, this takes secondstoo slow for interactive use and far too slow for a web application, where any perceptible lag degrades the user experience. Until recently, web browsers simply lacked the computational machinery to perform this evaluation at interactive rates.

Two technological developments have now removed this barrier. First, the WebGPU standard (supported in Chrome/Edge 113+, Firefox 141+, Safari 18+) exposes general-purpose compute shaders to JavaScript, unlike WebGL, which was limited to graphics rendering. Second, modern GPU hardwareeven integrated GPUs in commodity laptopsprovides thousands of parallel execution units that can evaluate independent grid points simultaneously, reducing the wall-clock time from seconds to milliseconds.

In this paper, we present MOrbVis (Molecular Orbital Visualization tool), an open-source tool that evaluates MOs directly from basis set coefficients in the browser, removing the dependence on precomputed volumetric data. MOrbVis reads a compact Molden file, computes the orbital values on a 3D grid via a WebGPU compute shader, extracts isosurfaces, and renders the resultall on the client side, with no Cube files, no server, and no installation. This work makes the following contributions:A new MO visualization workflow in which a single Molden file (∼100s KB) replaces per-orbital Cube files (∼13 MB each), and grid resolution, spatial extent, and isovalue are adjustable interactively rather than fixed at export time.GPU-accelerated basis function evaluation in the browser via a WebGPU compute shader written in WGSL (WebGPU Shading Language) that handles s, p, d, f, and g shells in both Cartesian and spherical harmonic representations, achieving speedups of up to 3 orders of magnitude over the CPU fallback and enabling sub-60 ms evaluation at 4 × 106 grid points.A zero-installation application with high-quality rendering (SSAO, bloom, six material presets), multiformat export (PNG, WebM, Cube, STL), and 48 built-in sample molecules for immediate use.

Methods

From Cube Files to On-the-Fly Evaluation

In the conventional pipeline, the QC program evaluates the molecular orbital ψ i (r) on a user-specified grid and writes one Cube file per orbital; a desktop viewer then reads the file, runs the marching cubes algorithm, and renders the isosurface. Changing the resolution or selecting additional orbitals requires rerunning the export step.

In the MOrbVis workflow, the QC program exports only the basis set definitions and MO coefficients in Molden format. The browser application parses this file, and when the user selects an orbital, the WebGPU compute shader evaluates the LCAO expansion on the fly at the currently selected resolution. Isosurface extraction and rendering follow immediately. Because the Molden file contains all orbital coefficients, every orbital is accessible without additional file I/O; the user switches orbitals with a single click or keyboard shortcut. Thus, the central methodological contribution is shifting the evaluation step from the QC program to the visualization client, enabled by GPU parallelism.

Molecular Orbital Evaluation

In the LCAO framework, molecular orbital ψ i (r) is expressed as a linear combination of basis functions: 1 ψi(r)=∑μ=1MCμiχμ(r) where C μi are the MO coefficients and M is the number of basis functions. Each basis function is a contracted Gaussian-type orbital (CGTO): 2 χμ(r)=∑k=1KμckN(αk,l,m,n)xAlyAmzAnexp(−αkrA2) where c k and α k are the contraction coefficients and exponents, r A = r – A is the displacement from the atomic center, l + m + n = L defines the angular momentum, and N(α k , l, m, n) is the normalization constant: 3 N(α,l,m,n)=(2απ)3/4(4α)(l+m+n)/2(2l−1)!!(2m−1)!!(2n−1)!!

The key observation enabling GPU parallelism is that the evaluation at each grid point r j is completely independent of every other point. For a grid of N points, the N evaluations of eq can be dispatched to N GPU threads with no synchronization or communication, making the problem embarrassingly parallel.

MOrbVis supports s (one component), p (three), d (six Cartesian or five spherical), f (10 Cartesian or seven spherical), and g (15 Cartesian or nine spherical) shells. For spherical harmonic representations, real solid harmonic transformations are applied: 4 d0=z2−12(x2+y2),d±1=3{x,y}z,d+2=32(x2−y2),d−2=3xy with analogous expressions for the seven spherical f and nine spherical g functions.

The total electron density is computed as 5 ρ(r)=∑ioccni|ψi(r)|2 where n i is the occupation number of orbital i.

Adaptive Grid Generation

A three-dimensional Cartesian grid is automatically constructed from the molecular bounding box with a configurable margin (default: 3.0 Å). The grid spacing is determined by the user-specified resolution parameter (number of points along the longest molecular axis, default: 100), and dimensions along the shorter axes are proportionally reduced. This adaptive scheme avoids wasting computation on empty space for noncubic molecules; for example, the planar benzene molecule at grid 160 produces ∼3.1 million points rather than 1603 ≈ 4.1 million.

Isosurface Extraction

Isosurfaces are extracted using the marching cubes algorithm with the Paul Bourke convention. Surface normals are derived from the scalar field gradient via central finite differences rather than from the triangulated geometry, yielding smooth shading: 6 n(r)=−sign(σ)∇ψ(r)|∇ψ(r)| where σ is the isovalue. Two separate meshes are generated for the positive (ψ > σ) and negative (ψ < −σ) lobes, rendered in distinct colors to represent orbital phase.

Implementation

Architecture Overview

MOrbVis is implemented in TypeScript using React for the user interface, Three.js (via React Three Fiber for 3D rendering, and WebGPU for GPU computation. The architecture (Figure ) is designed around the principle that the visualization client performs the computation, in contrast to conventional tools where the QC program bears this responsibility.

Software architecture of MOrbVis. For Molden input (left path), the parser extracts atomic coordinates, basis set shells, and MO coefficients; the grid generator and GPU/CPU evaluator then compute the scalar field on the fly. For Cube input (right path), the parser reads the precomputed scalar field directly. Both paths merge at the marching cubes step, which extracts isosurfaces for rendering via React Three Fiber with optional postprocessing.

This client-side computation model is important because it eliminates the need for a server: the application is a static Web site that can be hosted on any web server (including GitHub Pages) with no backend infrastructure. All computation is performed locally in the browser; user-loaded Molden files are never transmitted to any external server, and no data beyond the initial page request leaves the client. Because the source code is publicly available under the BSD-3-Clause license, users can independently verify this behavior. For environments that require complete network isolation, MOrbVis is also distributed as a standalone desktop application for Windows built with Tauri (WebView2), providing identical functionality in a fully offline setting.

WebGPU Compute Shader

The MO evaluation is implemented as a WebGPU compute shader in WGSL. The shader is dispatched with a workgroup size of 256. Each thread computes one grid point: it recovers 3D indices from a flat thread index, converts coordinates from Å to Bohr, evaluates all contracted basis functions with proper normalization (eq ), accumulates the LCAO sum (eq ), and writes the result. All shell types and both Cartesian/spherical representations are handled within the shader by branching on the shell type.

After dispatch, results are copied to a staging buffer and read back asynchronously via the WebGPU mapAsync API. The current WebGPU standard mandates single-precision (FP32) arithmetic in compute shaders; double-precision (FP64) is not available. For isosurface visualization, where the relevant quantity is the sign and approximate magnitude of ψ­(r) relative to a user-chosen isovalue (typically |σ| ∼ 0.02–0.05), FP32 provides more than sufficient precision. The GPU results are promoted to 64-bit floating point on the CPU for the downstream marching cubes step to maintain compatibility with the JavaScript number type.

CPU Fallback

When WebGPU is unavailable, MOrbVis falls back to CPU evaluation using Web Workers, which perform mathematically identical operations in a triple-nested loop. Progress callbacks after each z-slice provide a real-time progress bar. A dedicated density worker computes ρ­(r) by iterating over occupied orbitals.

Both paths employ a generation counter to handle race conditions: if a new evaluation is requested before the current one completes (e.g., rapid orbital switching via keyboard shortcuts), stale results are silently discarded. A three-level cache (MO scalar fields by orbital index, electron density by grid resolution, rendered mesh) prevents redundant computation when revisiting previously viewed orbitals.

Molden File Parser

The Molden format stores atomic coordinates, contracted shell definitions, and MO coefficients in a human-readable text file. MOrbVis parses the [Atoms], [GTO], and [MO] sections, automatically detecting atomic units (AU) and spherical harmonics ([5d], [7f], [9g]the highest angular momentum the Molden format itself defines). We adopted the Molden format as the primary input because it remains the common format for orbital data among quantum chemistry programs: it is produced by Gaussian, PySCF, GAMESS, ORCA, GANSU, Molpro, NWChem, Q-Chem, and Turbomole, among others, so a single parser is compatible with a wide range of computational workflows.

Gaussian Cube files are also supported as input, enabling users with existing Cube data to use the rendering and export features of MOrbVis. Plain XYZ files are accepted as well, for geometry-only display when no electronic structure data is available.

Rendering and Post-Processing

Isosurface meshes are rendered via React Three Fiber with six material presets (Table ), covering use cases from schematic illustration (Toon) to photorealistic presentation (Glass, Glossy). A high-quality (HQ) mode adds screen-space ambient occlusion (SSAO) for depth-cueing shadows between atoms, bloom effects for highlight emphasis, and studio-preset environment mapping for natural reflections. These effects are useful for producing publication-quality figures directly in the browser without postprocessing in external graphics software.

Export Capabilities

MOrbVis exports PNG images (1–4× DPI, optional transparent background), WebM video recordings of rotating views, Gaussian Cube files (enabling round-tripping to desktop tools), binary STL meshes for 3D printing of orbital shapes, and batch ZIP archives that render multiple selected orbitals with a consistent camera angle and rendering style, ensuring uniform figure quality across an entire orbital set.

Gap 1: Desktop tools that evaluate MOs cannot run in the browser. GaussView, Avogadro, Molden, IboView, Pegamoid, VIAMD, and VMD can all evaluate MOs from basis coefficients, but they require desktop installation. VMD supports CUDA-based GPU acceleration for MO evaluation; however, it is limited to NVIDIA GPUs and requires a native application. VIAMD, the companion visualization platform for VeloxChem, is the closest desktop counterpart to MOrbVis in feature coverage but is distributed as a native application requiring installation. GaussView requires a commercial license.

Gap 2: Browser-based tools cannot evaluate MOs. 3Dmol.js and Mol* demonstrate that molecular visualization is feasible in the browser, but they are designed for structural biology (PDB files, cryo-EM maps) and lack the ability to evaluate quantum chemical basis functions. They can display precomputed cube data, but the user must generate it externally.

MOrbVis bridges both gaps: it combines browser-based, zero-installation access with on-the-fly MO evaluation accelerated by WebGPU, which runs on GPUs from any vendor (NVIDIA, AMD, Intel, Apple) without requiring a native application or CUDA installation.

MOrbVis also provides features uncommon in MO-focused viewers: cross-sectional contour visualization, six physically based rendering presets, SSAO/bloom postprocessing, and STL export for 3D printing. The 48 built-in sample molecules, computed with GANSU at the Hartree–Fock/STO-3G level, enable immediate use without any input data.

Performance Evaluation

Because MOrbVis runs in a web browser, it will be used on hardware ranging from smartphones and thin-client laptops to high-end workstations. Whether the GPU acceleration provided by WebGPU is sufficient for interactive use across this entire range is a key practical question. We therefore benchmarked five systems spanning from an iPhone to a desktop with a current-generation discrete GPU (Table ), and evaluated performance along two axes: (1) basis set scaling, where the same molecule (benzene) is computed with increasingly large basis sets, and (2) molecular size scaling, where progressively larger molecules are computed with the same basis set. Electron Density Computation

Electron density evaluation in the current implementation (eq ) is performed by evaluating each occupied orbital on the grid and accumulating n i |ψ i (r)|2. Orbitals with zero occupancy are skipped, so N occ rather than the total number of MOs enters the cost. Even so, this is substantially more expensive than single-MO evaluation because N occ evaluations of the LCAO sum are required at every grid point. An alternative formulation expresses the density in terms of the one-particle density matrix P μν = ∑ i n i C μi C νi : 7 ρ(r)=∑μνPμνχμ(r)χν(r) where P μν is precomputed once on the CPU. The per-grid evaluation then becomes a single contraction over basis-function pairs and the cost is independent of N occ. The density-matrix formulation is therefore the more efficient route for systems with many occupied orbitals; we did not adopt it in the initial release because the orbital-by-orbital path reuses the same WGSL kernel as single-MO evaluation, but it is a natural direction for future optimization. We also exploit the fact that ρ­(r) ≥ 0 everywhere by skipping the negative-isosurface marching-cubes pass in density mode, halving the surface-extraction cost relative to MO visualization. Discussion

The benchmarks reveal three key findings.

First, GPU evaluation enables interactive MO visualization on all five hardware tiersfrom a smartphone to a desktop workstation with a discrete GPU. At grid 100, all systems deliver sub-25 ms GPU evaluation for any tested basis set. At grid 200, the slowest system (iPhone, cc-pVTZ) completes in 94 ms, and the other systems stay below 83 ms. Combined with marching cubes extraction (∼10–30 ms) and Three.js rendering (∼5–15 ms), the complete pipeline from orbital selection to rendered frame completes in 30–100 ms depending on the device, corresponding to 10–30 frames per second. In practice, users can switch orbitals, adjust isovalues, and rotate the 3D view without perceivable delay.

Second, the GPU advantage grows with computational complexity. The scenarios where CPU computation becomes impracticallarge basis sets, high grid resolution, electron densityare the ones where WebGPU provides the greatest speedup. On the RTX 2080 Ti, the speedup reaches 1,287× for single-MO evaluation (benzene, cc-pVTZ, grid 200). The Surface with an integrated Intel GPU achieves 407× for the same configuration, and even the iPhone reaches 170×.

Third, on the CPU fallback path, single-MO evaluation at grid 100 takes 0.5–4.7 s depending on the basis setnoticeable but usable. However, density evaluation on the CPU takes 13–110 s at grid 100, making it impractical without GPU acceleration. A progress bar provides feedback during CPU computations, and the three-level caching system makes revisiting a previously viewed orbital instantaneous regardless of the backend.

File Size Comparison: Molden File vs Gaussian Cube Files for All Molecular Orbitals at 1003 Grid Resolution

The Molden file is more than 3 orders of magnitude smaller than the full set of Cube files. This difference is fundamental: the Molden file stores M × N MO coefficients (a matrix), whereas each Cube file stores n x × n y × n z grid values (a volume). The two storage costs scale differently with system size, so a crossover is in principle possible. For a closed-shell system N MO ∼ M, so the Molden footprint grows as S Molden ∼ M 2, whereas the Cube footprint for all MOs grows as S Cube ∼ N MO G ∼ M G where G = n x n y n z is the (fixed) grid size. Equating the two yields the crossover M★ ∼ G: at the standard G = 1003 = 106 grid resolution used in Table , the formats become comparable only at M ≈ 106 basis functions, far beyond any system to which MO visualization is meaningfully applied (it would require tens of thousands of atoms in a triple-ζ basis). Even at a coarse grid of G = 503 = 1.25 × 105, the crossover is pushed only to M ≈ 105, still well outside typical use. For the more realistic scenario in which the user visualizes only a handful of orbitals of interestone HOMO, one LUMO, possibly a few frontier orbitalsthe per-orbital Cube footprint is just G, independent of M, while Molden remains M 2. The crossover then shifts to M★∼G , i.e., around M ∼ 103 basis functions at G = 106 (∼100 atoms with 6-31G*), which is plausible but still uncommon for orbital visualization. In practice the Molden-based workflow remains far smaller across the entire range of systems addressed by MOrbVis. Postponing the crossover further is straightforward: if needed, the Molden file can be losslessly gzipped (typically a factor of 3–5 reduction on the ASCII coefficients), exported in binary form, or, for very large systems, restricted to the orbital window of interesteach of these moves the crossover further toward larger M without sacrificing the on-the-fly evaluation capability of the client.

This compact data footprint has direct practical implications: Molden files can be emailed, stored in version control, or transferred over slow network connectionsscenarios where gigabytes of Cube data would be prohibitive.

Use Cases

Research: Quick Inspection

Researchers running QC calculations on a cluster can download a Molden file (∼100s KB) to their laptop and immediately inspect all orbitals in the browser, rather than transferring hundreds of megabytes of cube files or installing visualization software on the cluster. The cross-sectional view and energy diagram provide complementary analysis tools for rapid assessment.

Publication Figures

The HQ rendering mode produces figures suitable for journal submission directly in the browser. SSAO provides depth-cueing shadows, bloom highlights orbital lobes, and the Glass/Glossy presets create photorealistic effectsall exportable as high-DPI transparent PNGs.

Cloud and Remote Environments

In cloud-based QC workflows (e.g., Google Colab, JupyterHub on HPC), Molden files can be generated server-side and visualized client-side without downloading large volumetric data sets. Since MOrbVis is a static web application, it can also be self-hosted behind a firewall for proprietary data.

Education

The 48 built-in sample molecules and zero-installation requirement make MOrbVis deployable in classroom settings. Students can explore orbital shapes, energy level diagrams, and the HOMO–LUMO gap directly in a web browser.

Browser and Hardware Compatibility

WebGPU is supported in Chrome/Edge 113+, Firefox 141+, and Safari 18+, abstracting over Direct3D 12 (Windows), Metal (macOS), and Vulkan (Linux). Because WebGPU targets the hardware abstraction layer rather than a specific GPU API, acceleration is available even on integrated GPUs (Intel UHD, Apple M-series) commonly found in laptops and Chromebooks. On iOS, Safari supports WebGPU via Metal, enabling MO visualization on iPhones and iPads. When WebGPU is not available, the automatic CPU fallback ensures that MOrbVis remains fully functionalalbeit without GPU speedupon any browser supporting Web Workers.

Future development will address these limitations and explore natural transition orbitals (NTOs) for excited-state visualization, volume rendering as an alternative to isosurfaces, and tighter integration with server-side QC programs. Visualization of complex-valued orbitals from spin–orbit-coupled and two-component relativistic calculations, and of h-or-higher shells, would also be valuable; both depend on the adoption of a widely supported file format that carries the necessary data.

Conclusions

We have presented MOrbVis, a tool that evaluates molecular orbitals on the fly from Molden coefficient files directly in the browser, replacing the two-stage cube-file-based desktop workflow with a single-step pipeline.

Three results support this. First, the data footprint is reduced by more than 3 orders of magnitude: a ∼260 KB Molden file replaces ∼1.2 GB of Cube data for all 96 orbitals of benzene (6-31G*) at 1003 resolution. Second, WebGPU compute shaders achieve speedups of up to 1,287× for single-MO evaluation on a desktop GPU (RTX 2080 Ti) and 100–407× on a laptop with an integrated GPU (Intel Iris Xe), delivering sub-60 ms MO evaluation even for large basis sets (cc-pVTZ, 264 basis functions) at 4.1 million grid points. Third, because the evaluation is performed on demand, grid resolution and isovalue become interactive parameters that the user adjusts in real time, rather than quantities fixed at export time.

MOrbVis combines this workflow with publication-quality rendering (SSAO, bloom, six material presets), multiformat export, and 48 built-in sample molecules, all in a zero-installation web application. The automatic CPU fallback ensures accessibility when WebGPU is unavailable.
