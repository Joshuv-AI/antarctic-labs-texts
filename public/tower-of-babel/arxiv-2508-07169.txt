From Noise to Knowledge: Interactive Summaries for Developer Alerts
Burak Yetiştiren, Hong Jin Kang, Miryung Kim

Abstract
Programmers using bug-finding tools often review their reported warnings one by one. Based on the insight that identifying recurring themes and relationships can enhance the cognitive process of sensemaking , we propose CLARITY , which supports interpreting tool-generated warnings through interactive inquiry. CLARITY derives summary rules for custom grouping of related warnings with active feedback. As users mark warnings as interesting or uninteresting, CLARITY ’s rule inference algorithm surfaces common symptoms, highlighting structural similarities in containment, subtyping, invoked methods, accessed fields, and expressions. We demonstrate CLARITY on Infer and SpotBugs warnings across two mature Java projects. In a within-subject user study with 14 participants, users articulated root causes for similar uninteresting warnings faster and with more confidence using CLARITY . We observed significant individual variation in desired grouping, reinforcing the need for customizable sensemaking. Simulation shows that with rule-level feedback, only 11.8 interactions are needed on average to align all inferred rules with a simulated user’s labels (vs. 17.8 without). Our evaluation suggests that CLARITY ’s active learning-based summarization enhances interactive warning sensemaking.

To evaluate

, we conducted a user study and a simulation experiment. First, we carried out a within-subject user study with 14 participants. The participants inspected null pointer dereference warnings reported by Infer and Spotbugs on two large mature projects. They had to quickly review tool-generated warnings and articulate commonalities between uninteresting warnings.
We built a baseline for inspecting warnings one-by-one, similar to conventional tree-based organization bundled with Infer
[
19

A total of 55 different rules were formulated by 14 participants, with an average of 3.9 rules.
When using
CLARITY

CLARITY

CLARITY

As a second evaluation method, we conducted simulation experiments to quantify the benefit of rule-based feedback and summarization. When a user provides rule-level feedback as opposed to instance-level feedback,
CLARITY
’s resulting rules become aligned faster with interactive feedback. On average, for the warnings found in Alibaba Nacos, within 12 iterations, the rule alignment becomes over 80%, and within 18 iterations, rule alignment becomes 100%.

1.

To improve sensemaking of tool-generated warnings, we design an interactive approach that incorporates human feedback and highlights common characteristics among related warnings. Its automated rule-inference groups similar warnings using code locations, type hierarchy, the API signature of methods, the use of similar expressions, etc.

2.

In a within-subject user study, participants using
CLARITY

3.

Our simulation shows that resulting summary rules become aligned faster with rule-level feedback, as opposed to instance-level feedback.

II-A

Lack of sensemaking support in existing tools

Suppose that Alice is given the task of inspecting warnings generated by a static analyzer, Infer. Upon running it, Alice is overwhelmed by a large number of tool-generated warnings. Suppose that Alice browses
Null Pointer Dereference
warnings, the most common kind of warnings. After inspecting several of them, Alice is frustrated and cannot easily make sense of which warnings should be acted upon. Figure
3(a)
shows an example of null pointer dereference reported by Infer.

Difficulty of sensemaking when inspecting warnings one-by-one

Reviewing each warning one-by-one, Alice determines if each warning
is worthwhile to address or should be ignored.
After inspecting a few, Alice notices that several uninteresting warnings share similar characteristics, for example, being located in the same package or invoking similar API calls.
This process remains burdensome and frustrating, as Alice cannot easily check and articulate the underlying characteristics of similar recurring warnings.

Difficulty of sensemaking when using pre-determined filters

Alice may decide to determine a set of filter rules for suppressing tool-generated warnings. She observes that many warnings from the package
com.alibaba.nacos.persistence
are uninteresting for the same reason (e.g., a field set with the value fetched from a database is not
null
). Suppose that she manually writes a script to filter warnings in package
com.alibaba.nacos.persistence
.
Afterwards, she observes that several warnings related to a field set through serialization tend to be uninteresting; she hypothesizes that these warnings tend to be located in package
com.alibaba.nacos.config.server
. Another hypothesis she has is that such warnings should be refined by subtyping relations since they are located in classes implementing database-related interfaces. Then she has to revise an existing script or write another script. She realizes that it is difficult to pre-define a set of filter rules, because the sensemaking process requires interactive navigation, search, and summarization of similar warnings.

II-B

CLARITY
’s interactive sense-making

Using
CLARITY
, after Alice labels a few uninteresting warnings, it automatically proposes summary rules for grouping similar unwanted warnings. These summary rules are predicated over containment relation, type hierarchy of the implicated warning, the API signature of methods where warnings are reported, and the use of similar expressions. For example, a rule may match all warnings in package

com.alibaba.nacos.config.server
. Below, we discuss two kinds of sensemaking process in more details.

Example sensemaking with a containment relation.

Alice can then view and provide feedback on multiple warnings simultaneously at the rule level.
For example, the code snippets implicated by the warnings could follow the same API usage patterns
[
20
]
(e.g., calling the API functions from
DatabaseOperate
) or interact with the same third-party package dependency
[
21
]
(e.g., using functions from
Apache Commons Collections
).

CLARITY
derives a different set of rules after accounting for new labeling feedback. For example, it returns a newly proposed rule based on subtyping (e.g.,
classes that implement interface PaginationHelper
), which maps to the functionality of querying databases. She inspects and labels several related warnings matched by this rule.
After this feedback, the warning distribution for the rule is updated, allowing Alice to confirm that the rule does not match any interesting warnings (i.e., the number of matched interesting warnings stays at 0).
Now confident that this rule entails only uninteresting warnings, she clicks button
“Label matching warnings as: Uninteresting”
, expediting her inspection.

Example sensemaking with salient code expressions.

Moving on to the remaining warnings, Alice labels a few more and
CLARITY
proposes a new refined rule, grouping warnings with package
com.alibaba.nacos.client
.
As the warnings in this group (including Figure
3(c)
) share similarities, she is able to discern a common function call
getProperty()
is a marker for uninteresting warnings.
She thus highlights expression
getProperty
on the code snippet view on the right side to provide a hint to
CLARITY
that the expression
getProperty
should be when reformulating a rule. Given this highlighting hint,
CLARITY
refines the rule to surface all warnings within package
com.alibaba.nacos.client
and calling API
getProperty

getProperty
.

III
Approach: Sensemaking with Interactive Review and Learning

Fig. 4
:
CLARITY
’s workflow: A user can provide two modes of interactive feedback: (1) instance-level feedback for each warning, (2) marking all warnings as interesting or uninteresting per rule, and (3) clicking and highlighting code expressions in a code snippet view to guide rule inference. Based on feedback,
CLARITY
updates its candidate rules and displays a distribution of matched and unmatched warning instances for each summary rule.

CLARITY
eases the process of sensemaking tool-generated warnings by proposing summary rules that group related warnings. Rules are iteratively refined as the user provides feedback on individual warnings or a group of warnings matched by the rule, selects among suggested common characteristics, and/or highlights salient code expressions, as shown in Figure

III-A

Active learning-enabled rule formulation

We formulate the task of deriving summary rules as an
Active Learning
problem as follows:

Input:

CLARITY
uses the following inputs:

1.

Labels of each inspected warning.
A warning,
w
, is labeled either as uninteresting (

w\in E^{-}
) or interesting (
w\in E^{+}
).

2.

Background knowledge. A knowledge base with predicates on containment relationships and salient code expressions.

Output:

CLARITY
returns a set of summary rules,
R
.
Each rule,
r\in R
, is a conjunction of predicates.
The goal is for each rule to group related uninteresting warnings.
A warning matches a rule if every predicate in the rule is associated with it.

Active Learning.

CLARITY
has several requirements:

1.

To minimize the time users spend analyzing individual warnings one by one,
CLARITY
should provide help early in the inspection process.
Thus, even when the total number of warnings labeled “Uninteresting”,
|E^{-}|
, and “Interesting Warning”,
|E^{+}|
, is much lower than the total number of warnings,
|W|
,
CLARITY
should be able to derive rules.

2.

Rules derived from limited data is unlikely to accurately match the user’s intent.
Thus, their refinement is necessary to formulate meaningful rules.
We favor starting with a general set of rules, which maximizes the number of matching, uninspected warnings.

3.

Following Occam’s Razor
[
22
]
.

CLARITY
should propose as few rules as required.

As shown in Algorithm
1

CLARITY
utilizes inductive logic programming
[
23

to derive a set of summary rules.

CLARITY
maintains a background knowledge that is initialized by extracting facts of the implicated code’s scope (package, class name), type hierarchy (subtyping/interfaces implemented) and other API signatures (return type, fields used) (line 1).
The user provides feedback by marking each warning instance as interesting or uninteresting or by selecting salient code expression for the warning. If a user provides instance-level feedback, the set of uninteresting warnings and interesting warnings are updated (lines 5–12).
If a user highlights code expression as a hint in a code snippet window, the knowledge base is then updated by extracting new facts related to the code expression (lines 13–16).
Note that we do not initialize the background knowledge with all possible code expressions, given the large space of possible rules, if every code expression is considered. Instead,
CLARITY
relies on the user to provide hints by highlighting salient code expressions.

To derive a set of rules,

CLARITY
encodes the knowledge base as a logic program.
The rules should group uninteresting warnings together to minimize the number of warnings inspected by the user.
In our problem domain, a hypothesis is an assignment of predicates to rules such that the rule should not match the interesting examples,
E^{+}
, while matching as many uninteresting examples,
E^{-}
(line 17).
Ties between possible hypotheses are broken by the number of matched warnings, following the objective of maximizing the rules’ generality.
We use an off-the-shelf logic program solver
[
24
]
to search for candidate hypotheses. Finally, the found hypothesis is presented to the user as the proposed set of rules (line 18).

III-C

Rule design

Containment relationships.

CLARITY
infers rules as a composite of predicates with the following structural relations.

1.

Package: The package where the warning was reported (expressed as a predicate
package(X)
)

2.

Classname: The name of the class where the warning was reported (
classname(X)
)

3.

Return type: The return type of the method where the warning was reported (i.e.,
rettype(X
))

4.

Fields used: The fields of the class used in the method (i.e.,
fields(X
))

5.

Subtyping: The parent classes and interfaces of the class (i.e.,
subtype(X
))

Salient code expressions.

A user can select expressions to provide hints with code features associated with warnings—specific method calls
[
18
]
or API usage conventions
[
20
]
. For the code expression highlighted by a user,
CLARITY
extracts the methods called (e.g.,
getProperty
), the types of the variables (e.g.,
String
), the values of literals (
os.name
), control-flow elements, such as
if-then
statements, as well as conditionals such as a null-check.
CLARITY
encodes each code expression as a predicate, adding them to the background knowledge for rule inference.

Protocol.

We conducted a 1-hour user study with each participant, involving both

Participants completed both case studies, with each task set for 10 minutes but with the option to finish early. RQ1. Variation in user-formulated rules

Number and variance of derived rules.
In total, 55 different rules were derived and used by the participants.
Each participant formulated an average of 3.9 rules, and created at least one unique rule.
This highlights that during sensemaking, users develop

VI
Discussion

Inferring configurable and personalized rules.

A high degree of variations exist among the rules formulated by the participants with the help of
CLARITY
.
This high level of subjectivity in how users wish to group related warnings is aligned with the motivation behind
CLARITY
—filtering tool-generated warnings with a ‘one-size-fits-all’ rule is not ideal, since users have their own ways of sensemaking and grouping warnings. In other words, this observation justifies
CLARITY
’s active learning approach where a user is allowed to provide labeling feedback and guide rule inference with custom hints, e.g., code highlighting and a check mark
\checkmark
over candidate predicates.

In the post-study survey, participants indicated a preference for highlighting code expressions over pre-defined predicates (i.e., package and class names, subtyping, used fields, called methods, and return type, etc). Several participants commented that they would prefer even more customization, including the ability to define rules from scratch. Therefore, future work can enhance customizability even further by enabling direct editing capability for custom rules with dual modality of logic rules and natural language descriptions.

Efficiency of inspection.

While
CLARITY
increased confidence, the participants took longer to examine tool-generated warnings.
On average, participants using the baseline inspected over 20% more warnings.
Having to review the rules carefully slowed down the participants, which may indicate the care taken to reason about the commonalities among related warnings. P6 mentions “
efficiency gained
[using
CLARITY
]
was offset by the time I spent trying to get the inference engine to generate the rules I wanted
”.

Ease of use.

There is an initial learning curve for using
CLARITY
compared to the examination of individual warnings.
Nevertheless, tools perceived to be difficult to use can still provide utility and value
[
45
]
.
Participants were better at articulating common symptoms of similar warnings using
CLARITY
.

Threats to validity.

One threat to validity is related to the choice of bug types (i.e., analysis kind) used in our study. We focused on null pointer de-references and resource leaks since these kinds of analysis are widely supported by commercial static analyzers.
Grouping based on containment, type hierarchy, code similarity, and API methods and fields used in
CLARITY
should generalize to grouping other kinds of tool-generated warnings on code snippets.

While our study included only 14 participants, studies that use a within-subject study with a crossover design require fewer participants
[
26
]
, as the crossover minimizes variability
[
46
]
. Moreover, our participants had a wide range of programming experiences, and included both graduate students and professional developers.

VIII
Conclusion

CLARITY
is the first to systematically support personalized, sensemaking of tool-generated warnings by harnessing user feedback with active learning.
Our key insight is that automatically refined summary rules can enable users to contrast common characteristics among related warnings and that user’s specific hints should be incorporated to re-infer summary rules.
These rules group related warnings using predicates capturing containment, subtyping, method call, field usage relationships and the use of similar code expressions highlighted by users, allowing users to formulate custom abstraction about which warnings should be (or should not be) acted upon.

CLARITY
is an active learning approach where users can provide feedback by labeling individual warnings, by marking each rule, and by highlighting code hints used to re-infer rules.

We evaluate
CLARITY
with two different evaluation methods. First, our user study reveals that participants developed individualized, custom rules for grouping related warnings, confirming our insight that one-size-fits-all policy may not work during the cognitive, sensemaking process and that users desire configurability.
CLARITY
helps users discern commonalities and differences among different groups of uninteresting warnings. When using
CLARITY
, users reported lower levels of frustration, higher levels of confidence, and could articulate more details about underlying similarities regarding uninteresting warnings. Second, our simulation study found that, by enabling users to provide feedback at the level of rules,
CLARITY
’s resulting rules become aligned faster with labeling feedback.
