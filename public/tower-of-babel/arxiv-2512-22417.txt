A Bounded Game Semantics Checker for Precise Smart Contract Analysis
Vasileios Koutavas, Yu-Yang Lin, Nikos Tzevelekos

Abstract
. We present a new approach to finding smart contract vulnerabilities that is precise (no false positives up to our EVM-Yul interpreter), bounded-complete, and, when instrumented with domain knowledge, scales to real-world contracts. Our method is based on game semantics, modelling computation as an interaction between a contract and its environment, reducing reasoning about unknown or malicious external contracts to trace enumeration. We implement this in a tool we refer to as YulToolkit, a bounded game-semantics checker for Yul, the intermediate language of Solidity. By exploring only feasible interactions, YulToolkit avoids over-approximation, and by relying on the theory of game semantics it achieves bounded completeness. To make exploration tractable, YulToolkit supports instrumentation written in Solidity and propagated to Yul, comparable in effort to creating a test harness. Unlike tests, however, our technique explores all admissible traces within the chosen parameters and bounds. We evaluate YulToolkit on three real-world incidents: The DAO, PredyPool, and Lendf.Me, as well as benchmark contracts. In all cases, YulToolkit detects the known vulnerabilities (producing a violation-triggering trace), and after applying fixes, reports no further violations within bounds. These results show that bounded game semantics exploration is an effective and precise addition to the smart contract analysis toolbox, particularly for vulnerabilities such as reentrancy that are hard to detect precisely in real code.

Introduction

Programmable blockchains extend distributed blockchain ledgers with
smart contracts
: programs invoked by transactions that can read and write on-chain state.
They underpin decentralised applications, notably in decentralised finance (DeFi).
On Ethereum, one of the earliest and largest programmable blockchains, smart contracts are typically written in high-level languages such as Solidity, and compiled to Ethereum Virtual Machine (EVM) bytecode.

Because most properties of interest are intractable,

Static analysis and abstract interpretation largely follow the first approach,

State-of-the-art tools often combine approaches to balance trade-offs (e.g.

These tools are valuable for large-scale scans of deployed contracts.
For developers and auditors, however,
interpreting false positives in complex DeFi codebases is costly;
sampling and heuristics can miss intricate, cross-contract exploits;
and scalability of precise methods to production contracts remains a challenge.

Modelling the blockchain’s open environment, where any contract can call any other through its Application Binary Interface (ABI), is an additional source of intractability. Tools often rely again on over- or under-approximations, or on enforcing code patterns (e.g. checks-effects-interactions
(
41

In this work we propose a new approach to finding smart contract vulnerabilities that has no false positives, is bounded-complete, and with instrumentation scales to real-world contracts.
Our goal is not to replace existing tools, but rather to broaden the toolbox available to contract creators and auditors.
Our approach has the following four key features.

Environment-Complete.

Our approach is based on the theory of
Game Semantics

(
1
;
23
;
30
)
.
It models computation as an interaction between a program, called the
Proponent
, and its environment, called the
Opponent
; and
enumerates all admissible calls and returns between them.
In this way, quantification over unknown external contracts,
including malicious ones, becomes quantification over game-semantics
traces
: sequences of
call
and
return

moves
.
Game Semantics is complete: if there is no vulnerable trace in the semantics then no exploitable vulnerability exists in the code.

Executable and Bounded-Complete.

Although most smart contracts have infinite game semantics,
inspired by Bounded Model Checking (BMC)
(
7
;
10
)
, we have implemented
YulToolkit
, a
bounded exploration
tool over EVM game semantics
and an interpreter of the operational semantics of Yul
(
25
)
, the intermediate language of the Solidity compiler.
Bounds target EVM-specific resources, including transaction gas (the cost of running a transaction on the blockchain), number of calls per function and tool execution time.
YulToolkit
is
bounded-complete
: if no vulnerable trace is reported then no attack exists within bounds.

Precise (no false positives).

By exploring only feasible Proponent–Opponent interactions, our method avoids over-approximation and is
precise
: if
YulToolkit
reports a vulnerable trace, then there exists a concrete attack contract that exploits it.

Scales to real code.

YulToolkit
supports the recent EVM execution-layer (all instructions from the Shanghai hard fork up to Cancun)
and runs real-world contracts emitted as Yul by a recent Solidity compiler (
solc
0.8.30, excluding transient storage).

3.
Methodology

Figure 1.
Overview of the
YulToolkit
processing pipeline.

In this section we describe our method to analyse Solidity smart contracts via their Yul intermediate representation (IR) and detect undesirable behaviour, expressed as automatic or manual assertions.
Given a Solidity project and a designated top-level contract (e.g. the main contract or a deployer that instantiates all dependencies),
our analysis, implemented in our tool
YulToolkit
, either returns a game semantics trace witnessing an assertion violation or exhausts the search bounds.

Remark 1.

We assume a Solidity compiler capable of producing Yul IR that follows standard naming and layout conventions (as of v0.8.30). Although
YulToolkit
can process any valid Yul term, our pipeline depends on the compiler’s default object structure — in particular, globally unique identifiers of the form “
<
ContractName
>
_
<
counter
>
_deployed
” for deployed contracts — to reliably match each deployed
contract
with its respective compiled Yul object. We describe the specific versions of the EVM and Solidity
supported
in
YulToolkit
in
Section

4.2
.

Figure

1
summarises the
YulToolkit
pipeline.
Inputs are Solidity sources targeting a 0.8-series compiler.
Users may optionally instrument the sources with assertions (calls to special hook functions in the Solidity code) and harnesses (e.g. a deployer that constructs the system under test).
These sources are then compiled with the Solidity compiler obtaining their Yul IR and the Application Binary Interface (ABI) of all contracts in a JSON file.

The solidity compiler emits Yul IR with nested contracts. The compiled top-level contract (e.g. the deployer) contains a single top-level Yul object that nests the Yul objects for all dependencies.
After preprocessing, this entire object is
given to the core
YulToolkit
engine.
Preprocessing involves:

(1)

Library linking:
inserting deployment and linking code for all required libraries.

(2)

Opcode injection:
replaces all calls to
YulToolkit
hooks with corresponding custom opcodes.

(3)

Legacy mode:
disables compiler-inserted overflow checks to preserve the semantics of older contracts (optional, used to analyse older contracts in our case studies).

For the JSON file,
we automatically extract the ABI contained in it. At this stage, users may optionally prune the ABI to retain only functions relevant to the analysis, reducing the analysis state space.

The final Yul and ABI files are passed to the core
YulToolkit
engine with optional Command Line Interface (CLI) parameters (

4.
Modelling an EVM-Flavoured Yul

Yul is an intermediate representation (IR) language between Solidity and EVM bytecode.
It is parameterised by a
dialect
that defines available data types, primitive operations, and other constructs.
Core Yul, independent of the dialect, provides a small set of structured control-flow constructs, avoiding low-level stack manipulation and jumps.
Next we describe the EVM dialect of Yul used by
YulToolkit
, which builds on the operational semantics and interpreter of Yul presented in
(
25
)
.

4.1.
Yul Objects

Solidity smart contracts and libraries are the primary structural units mapped by the
Yul specification
(
42
)

4.2.
The EVM Dialect

Our EVM dialect is a substantially complete, custom implementation of the EVM layer, originally based on the Ethereum Shanghai upgrade and updated to reflect subsequent minor specification changes.
It is paired with a Game Semantics for EVM-flavoured Yul. Transient Storage (EIP-1153
(
2
)
, introduced in the Cancun upgrade
(
40
)
) is not implemented.
As Yul is stable across Solidity versions, our system supports contracts compiled with Solidity 0.8.x up to at least 0.8.30, excluding those using transient storage.

Our implementation ports the Python execution specification
(
16
)
to OCaml 4.10, preserving line-by-line fidelity where possible.
To enable automated analysis, we extend the model with Yul-specific instructions and replace certain low-level mechanisms with abstractions.
The result faithfully simulates the EVM but is structured for automated analysis via Game Semantics.
Key modifications are outlined below.

YulToolkit
supports the full range of opcode categories defined in the specifications
(
16
)
: Arithmetic, Bitwise, Block, Comparison, Control-flow, Message Environment, Keccak, Memory, Stack, Storage and System.
It also supports Yul-specific opcodes for objects (see previous section),
immutable data
and
linking
.
Opcodes irrelevant to Yul (e.g. certain stack operations) or with no semantic effect (e.g.
memoryguard
or logging) are implemented as no-ops.

Gas
costs (the EVM execution cost model) are computed precisely in
YulToolkit
using
uint256
arithmetic for supported opcodes.
However, because Yul replaces explicit stack and jump instructions with structured control flow, gas computations are under-approximations of actual execution cost.

Memory
(the EVM’s transient state) is a byte-indexable map from
uint256
indices to
byte
values, while

Storage
(the persistent state in the blockchain) is a map from
uint256
to
uint256
.

Keccak256
is EVM’s cryptographic hashing function. In
YulToolkit
it is modelled as a bijective map from
byte
sequences to
uint256
words.
We assume no collisions:
each hash is generated by a deterministic, pseudo-random process with memoisation to produce stable results and avoid collisions.
Our keccak implementation works with Yul objects (which are not bytecode in
YulToolkit
), and is significantly faster than concrete implementations.

Solidity libraries are compiled into Yul objects and deployed at separate addresses.
These are invoked via the EVM opcode
delegatecall
, which executes library code in the context of the caller’s memory.
Since library addresses are unknown at compile time, the Solidity compiler emits
linkersymbol
(
"library_id"
)
as placeholders.
In the
YulToolkit
toolchain, we automatically resolve all such symbols, locate the corresponding Yul objects, and inject deployment code for required libraries into the constructor of the top-level object.
At analysis time, each
linkersymbol
instruction evaluates to the correct address of the linked library.

YulToolkit
also defines a set of custom opcodes (written in uppercase) used exclusively for analysis,
inserted post-compilation in the place of hooks written by the user in the program. The main custom opcodes include:

IMPERSONATECALL
, a variant of the
call
opcode with an additional address argument specifying the
msg
.
sender
of the call message;

ASSERT
, which halts the analysis and reports the Game Semantics trace;

REVEAL_UINT
and
REVEAL_ADDR
, which add values to the Opponent’s known-value sets (
Section

5.1
);

EXT_FUND
, directly increasing the balance of an address;

PRINT
,
PRINT_signed
,
PRINT_hex
, etc. which output values to the terminal.

Game Semantics

The previous section detailed the Yul and EVM components; we now describe the Games Semantics component and its integration with the rest.

As shown in

The parser constructs an abstract syntax tree (AST) for the top-level Yul object and records all available functions (with their hashes) per object in the ABI.
These are used to construct a

, represented as a triple
(

,

,

o

The

each frame is either a

containing only an EVM configuration.
The
addresses

o

track the sets of values known to Opponent, used as arguments to Proponent.

5.1.
Opponent Domains (Known-Value Sets)

As described above,
o
-
domains
are sets of values known to the Opponent.
Currently, there are two dynamic base domains:
uint
/
bytes32
and
address
;
and three fixed base domains:
bool
,
string
and
bytes
.
All base domains may be seeded with parameters, but dynamic domains may additionally grow as the Opponent learns new values from the Proponent.
From these, we derive further domains:
uintN
for an
N
{}\leq 256
divisible by 8,
and
bytesN
for
1<{}
N
{}<32
, with values drawn from their respective base domains.
We also support two hard-coded domains:
unit
[2]
and
bytes32
[2]
, which currently always return the pair
[1,1]
— sufficient for all experiments.
In future work, we plan to develop these knowledge sets into a more rigorous theory.

5.2.
Game Semantics Moves

The initial configuration contains a single Proponent frame for the top-level Yul object, the addresses allocated to Opponent, and the initial knowledge sets (cf.
Table

1
).
Once constructed, the Game Semantics module begins evaluation by enumerating all possible moves at each point in a trace, described next.

\bullet

deploy
is a move that occurs once per game and marks the beginning of the Opponent’s exploration of all possible traces in the game.
It is triggered at the end of the constructor of the top-level contract.
The move returns to an empty stack, adds the newly created address to the Proponent’s addresses,
and creates an Opponent configuration to begin trace enumeration.

\bullet

o-call
is an Opponent move targeting a Proponent address.
Such moves occur whenever the active stack frame is an Opponent frame.
They are not triggered by concrete code; instead, the Opponent branches exhaustively over all known function hashes (from the exploration ABI, cf.
Table

1
) for each Proponent address in
addresses
,
issuing calls from every Opponent address in
addresses
.
For each call, arguments are chosen combinatorially from
o
-
domains
according to the function’s ABI signature.
Opponent calls are bounded by the number of times a function may be called in a trace, the maximum stack depth, and available gas.

\bullet

po-call
occurs when the active Proponent frame calls a function at an Opponent address, at which point execution of Proponent code becomes stuck.
This pushes a new Opponent frame onto the stack, containing the child EVM.
From there, the Opponent enumerates all possible
o-call
moves (as above) and a return move (discussed below).
Arguments passed to Opponent in these calls are added in the appropriate knowledge sets in
o
-
domains
.
These moves are bounded by gas.

\bullet

pp-call
,
create
, and
create2
are Proponent-to-Proponent moves which
occur when control is passed from one Proponent contract to another.
They arise when the active Proponent frame is stuck on
a message opcode, i.e.
call
,
staticcall
,
delegatecall
, the variant
IMPERSONATECALL
,
create
, or
create2
.
They push a new child Proponent frame onto the stack as the active frame, containing the target object code and the child EVM.
These moves are also bounded only by gas.

\bullet

o-ret
,
po-ret
,
pp-ret
are return moves that occur when the active (child) frame passes control back to its parent frame.
This is done by popping the child frame and
incorporating
its EVM into its parent’s EVM.
Incorporation depends on how the parent became stuck: if stuck on a call, the child’s output data is copied into the parent’s return data and the value
1
is returned to the parent’s code.
If stuck on a create, the parent’s return data is cleared and the new contract address is returned to the parent, and recorded in the Proponent addresses in
addresses
.
In both cases, the parent frame is restored as active and unstuck

For Proponent frames, return moves are triggered by
halting opcodes

stop
and
return
.
Traces terminate on
revert
;

invalid
is not implemented (we have not observed contracts using it); and

selfdestruct
is omitted as it is being phased out of the EVM since version 0.8.18
(
15
;
6
)
.

\bullet

Internal moves
are Yul-semantics reductions.
If the active frame is a Proponent frame which is not stuck, its Yul object is passed to the Yul semantics module for evaluation.
This module performs as many reductions as possible, invoking the EVM dialect module to evaluate opcodes.
If a control-passing opcode is encountered, the EVM and Yul configurations — and with them the current frame — become stuck and control returns to the Game Semantics module.
In addition to the opcodes above, the following also render the current frame stuck, returning to the Game Semantics:

ASSERT
, which signals a property violation in the current trace; and

REVEAL_UINT
and
REVEAL_ADDR
, which are used in rare cases of instrumentation to manually add values to the Opponent’s knowledge.
Internal moves are bounded by gas.

\bullet

o-wait
is a top-level move that occurs only when a single Opponent frame is on the stack.
It signals the end of the current transaction and advances time by a fixed amount.
The stack remains unchanged, permitting further
o-wait
and
o-call
moves.
This move is bounded by the maximum time allowed in a trace (cf.
Table

1
).

Remark 1.

All the
o-
moves are enabled whenever the Games Semantics encounters an active Opponent frame, with
o-wait
and
o-ret
enabled when there is one and more than one stack frame, respectively.

YulToolkit
systematically enumerates all such non-deterministic options, thereby exploring every possible contract environment, including malicious ones.
This non-determinism can cause an exponential blowup in the number of traces. We mitigate this in several ways, allowing our tool to scale to real-world contracts, as shown in our experiments.
In particular:

\bullet
Functions that do not modify state (marked
view
or
pure
in the ABI) are excluded by default, with a bound of zero calls.
For example, in the DAO, 27 out of 48 functions were pure, leaving only 21 state-changing functions to consider for exploration.

\bullet
Users may restrict Opponent calls to a subset of functions in the contract’s ABI.
Empirically, most real attacks rely on only a few functions, justifying this approach.
The exploration ABI can be chosen via domain knowledge, or systematically by testing all subsets of functions up to some small size
N
, or a combination of both.

\bullet
Knowledge sets restrict arguments to values relevant in context.
This is particularly useful when one function outputs a
uint256
identifier that must be supplied to later calls to trigger an exploit.
This mechanism enabled discovery of both the DAO and PredyPool attacks, where random arguments would not have sufficed.

\bullet
Users control
wait
moves by specifying granularity and maximum duration, or disabling them entirely.
Parameters are usually apparent from code inspection, again encoding domain knowledge.

\bullet
Finally, users may define big-step moves for the Opponent.
For example, in the analysis of PredyPool, we exposed a function that, given two ERC-20 token addresses, issues the correct sequence of calls to create a Uniswap v3 liquidity pair.
This enabled the Opponent to perform the complex interactions required in this example.
Such instrumentation is natural for domain experts, as similar constructs already appear in tests.

Related Work and Conclusions

A large number of tools aim to detect vulnerabilities and verify smart contract safety, with
surveys cataloguing extensive literature
(
45
)
.

Symbolic execution
(e.g.
(
29
;
11
)
)
and
model checking
(e.g.
(
20
;
43
)
)
are precise, largely automatic techniques that aim to exhaustively explore feasible program
paths and discharge path constraints with SMT solving. However they face challenges
in covering the full state space even in relatively small programs, particularly in the presence of reentrancy.
As discussed in
Section

6.1
, unlike
YulToolkit
, Mythril
(
11
)
and Manticore
(
29
)
fail to detect all vulnerabilities in the Gigahorse reentrancy benchmarks.

Static analysis
(e.g.
(
8
)
) and
abstract interpretation
(e.g.
(
21
)
) are also automatic techniques that scale well by over-approximating program behaviour,
but inevitably produce false positives. In complex DeFi systems, these spurious alarms can be costly to audit.
By contrast, in our DAO (
Section

6.2
) and PredyPool (
Section

6.3
) case studies,
YulToolkit
reported no issues after fixes.
On Gigahorse reentrancy benchmarks, it matched or outperformed Symvalic
(
37
)
, a state-of-the-art static analysis tool.

Dynamic analysis
and
fuzzing
(e.g.
(
24
)
) combine scalability with precision when guided by instrumented harnesses.
However, they rely on randomness or heuristics such as coverage, which can miss errors.

YulToolkit
instead exhaustively enumerates all execution paths within bounds, including all possible environment behaviours.
State-of-the-art tools often combine approaches to balance trade-offs (e.g.
(
37
;
28
)
).
Lastly, most tools over- or under-approximate the behaviour of external contracts.
A notable exception is SmartPulse
(
43
)
, which encodes an attacker model with moves reminiscent of game semantics, though it does not scale to large real-world systems such as those we analysed.

We introduced
YulToolkit
, the first bounded game semantics checker for Ethereum smart contracts.
It systematically explores all Proponent-Opponent interactions within user-defined bounds, ensuring precision (no false positives) while scaling to real code through instrumentation.
In experiments on three real-world exploits (the DAO, Lendf.Me, and PredyPool) and on 23 Gigahorse reentrancy benchmarks,

YulToolkit
reproduced the known attacks and reported no violations after fixes.
While we focused on reentrancy as a particularly challenging and prevalent class of vulnerabilities, illustrating game semantics checking.
However the approach supports arbitrary assertion checking, generalising to any safety property
(
27
)
including access-control safety
(
4
;
26
)
.
In future work, we will perform a broader evaluation across vulnerability classes and focus on the detection of previously unknown flaws.
