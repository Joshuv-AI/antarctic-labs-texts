What a diff makes: automating code migration with large language models
Katherine A. Rosenfeld, Cliff C. Kerr, Jessica Lundin

Abstract
Modern software programs are built on stacks that are often undergoing changes that introduce updates and improvements, but may also break any project that depends upon them. In this paper we explore the use of Large Language Models (LLMs) for code migration, specifically the problem of maintaining compatibility with a dependency as it undergoes major and minor semantic version changes. We demonstrate, using metrics such as test coverage and change comparisons, that contexts containing diffs can significantly improve performance against out of the box LLMs and, in some cases, perform better than using code. We provide a dataset to assist in further development of this problem area, as well as an open-source Python package, AIM igrate , that can be used to assist with migrating code bases. In a real-world migration of T yphoidsim between S tarsim versions, AIM igrate correctly identified 65% of required changes in a single run, increasing to 80% with multiple runs, with 47% of changes generated perfectly.

Introduction

Large Language Models (LLMs) have demonstrated impressive capability in various coding problems, including generation, refactoring, and translation
Roziere et al. 2022
;
TehraniJamsaz et al. 2024
. In this paper we focus on a specific subtask under code translation: migrating code to maintain compatibility with major semantic version changes to a dependency. This task is common to projects involving software maintenance, application deployment, and research program management. Furthermore, it is a problem that affects teams ranging from individuals to collaborations.

One of the challenges associated with this problem is that it requires changes that both maintain functionality and ensure compatibility with the existing (and sometimes rapidly changing) ecosystem of the project and its dependencies. This differentiates the task from many other coding problems where the problem is generally structured by the language and basic functionality. Relatedly, there have been significant results from tool calling to code generation and repair
Patil et al. 2023
;
Tang et al. 2024
;
Wang et al. 2024
;
Zheng et al. 2024
. Simultaneously, there have been a growing number of solutions (many available only at cost) with impressive performance across tasks related to software engineering
Yang et al. 2024
.

However, these solutions generally do not serve smaller projects where migration is an important part of maintaining communities and impact. For example, the task is not captured in current benchmarks
Chen et al. 2021
;
Jimenez et al. 2024
;
Shah et al. 2024
. On the other hand, there are established methods to help with the migration process, including the identification and classification of refactoring patterns
Tsantalis et al. 2018
;
Tsantalis et al. 2022
, along with the automated updates based on these identified patterns
Pawlak et al. 2016
. However, these tools are often paired with specific libraries and languages, rather than being general purpose solutions to the migration problem itself.

In this work, we explore pairing
diff
utilities and LLMs to approach this problem using a zero-shot approach that leverages the large context window of state-of-the-art models (e.g., 128k tokens for gpt-4o). A
diff
utility uses algorithms that find the longest common subsequence (LCS) and creates a script for transforming one sequence into another (e.g., the LCS of “dolphin” and “penguin” is “pin”). Diffs have been used for a variety of interesting applications from modeling the evolution of topics in software projects
Thomas et al. 2011
to training LLMs to use APIs
Zan et al. 2024
; however, we are not aware of diffs being used directly for code translation or generation.

2
Motivation

State-of-the-art LLMs demonstrate impressive performance out of the box on a wide range of challenging benchmarks. In practice, however, using LLMs often requires data compression through some form or combination of filtering (e.g., RAG), structuring (e.g., graphs), or tuning (e.g., fine-tuning, test-time-training). One reason we consider diffs is that they present a concise way to capture changes in code. Figure
1
shows the size of three Python libraries over their commit history measured using the o200k_base encoding. We compare the total size of the repository (filtering for
.py
files and excluding
docs
and
tests
directories) against the sequential diff commits. Notably, the size of the diff is almost always less than the size of the repository and often significantly so. Furthermore, changes to the code base are co-located by design in the diff output. So while the size of the diff will likely increase with the number of commits, it is clear that there are some cases where the diff provide some form of compression as well as concentration.

The general concept of differencing has been utilized in multiple LLM applications including pre-training
Zhang et al. 2022
, training for API invocation
Zan et al. 2024
, differential testing
Rao et al. 2024
, and code review/commit message generation
Fan et al. 2024
. In particular,
Fan et al. 2024
reported that pairing in context learning with diff formatted code changes resulted in better performance for comment generation than using code. However, we are not aware of quantitative, general assessments of LLM comprehension of diff outputs. In order to motivate our usage of diffs for the task at hand (code migration) we explore this issue to see a) if LLMs can comprehend diff outputs for coding tasks and b) how the quality of the comprehension compares to using pure code.

The HumanEval dataset, released by OpenAI in 2021, was designed to test code generators using docstrings. The benchmark, consists of 165 function headers and docstrings, solutions, and tests
Chen et al. 2021
. Using 100 of the provided solutions, we use Claude 3.5 Sonnet to generate two solutions: one solution is prompted for correctness and the other for a mistake. The prompt strategy is meant to produce meaningful changes in the style and implementation of the code. Using the harness provided by OpenAI, we filtered the results to ensure that code would produce the correct pass/fail status leaving 174/200 verified test questions.

For our “diff comprehension test”, each test question is composed a subset of three files:

•

FileA.py: A concatenation of 5 randomly chosen functions from the HumanEval dataset solutions (function header + function body with no docstring)

•

FileB.py: A concatenation of the same functions using the new solutions where we uniformly choose between 0 and 5 of the functions to be incorrect

•

FileC.py: the diff between FileA.py and FileB.py.

We assess the LLM’s output count of the number of functions that have errors over two trials where the first trial includes FileA.py and FileB.py and the second trial includes FileA.py and FileC.py. Diff comprehension can be assessed by comparing performance against random answer and the answer using pure code. Figure
2
plots the results for several of the OpenAI models. To account for uncertainty in the LLM output, we compute a weighted average of the token probabilities,

\sum_{t=0}^{5}tp(t)
.

3
Method

The migration workflow (see figure
3
) requires specification of 1) the legacy library version, 2) target library version, and 3) the pre-update project files. In practice, since the repositories and resulting diff files can exceed the context window size of current models, the workflow also requires filtering for for which library artifact (e.g., files) to use in the migration process. While this step could be automated using e.g.
ast
, we use file patterns to either include or exclude files. This specification is used to construct a single diff containing all the changes to the filtered files between the legacy and target versions of the library
2
2

2

We use the git CLI default diff implementation
Myers 1986
. The diff is combined with each pre-update project file, separately, and the LLM output is the post-update project file. The collection of these post-update files can then be assessed for quality and accuracy. Further details about prompt construction are provided in Appendix
D
.

Key aspects of this approach include:

•

There is no dependency on the library or project code, thus avoiding any potential conflicts.

•

While the examples presented in this paper are exclusively for Python, the approach is not limited to any specific programming language.

•

It does not require generating specialized scripts for the dependency (cf. migration approaches based on, for example, G
rit
QL) and the same workflow can be applied to multiple libraries for a fixed project.

•

The workflow sketch (figure
3
) does not include checks of the generated code; any code produced by the LLM should be inspected for both safety and quality.

Figure 3:
Diagram showing how AIM
igrate
uses diffs to automate code migration. The diagram does not capture how the pre-update project files are filtered for migration nor does it capture the quality and safety checks applied to the resulting code. The migration loop can be run multiple times to increase overall quality of the results (section
5.3
) Figure made with app.diagrams.net/.

We provide an implementation of this diff-based workflow (along with other approaches discussed in section
4
) as a publicly available Python library, AIM
igrate
. The tool supports OpenAI, Anthropic, Gemini, and local models (using ollama). See Appendix
F
for an example.

4.1
Data

We present three case studies that highlight strengths and challenges of the methodology. Each case study contains files compatible with the legacy and target library. The post-update files are a reference created by the project maintainers. We then apply the diff-based workflow using AIM
igrate
, along with two other migration strategies, to the initial migration problem and compare our results to the reference post-update files by using a testing framework approach as well as via direct line-by-line comparisons.

These case studies were selected for their diversity (ranging from software/application development to disease modeling). The include recent updates featuring changes to syntax, structure, and features. The code supplied with this analysis provides instructions for adding additional case studies. Furthermore, we provide a dataset of working, minimal changes that capture the migration task. This data is utilized to assess the diff-based approach.

Each of the case studies is based on an existing, open-source

4.2
Evaluation

AIM
igrate
should be paired with thorough review and assessment; in practice it provides a useful starting point to identify potential changes necessary for the migration. However, we assess the out of the box performance of the workflow on the three case studies described in detail below. We report two methods of assessment: performance on a suite of tests and line-by-line classification performance. Each case study comes with a suite of tests that assess functionality of the post-update project. We use
pytest
to automate running the tests and tracking the number that pass. The second assessment is a line-by-line classification where we first identify all significant changes to the pre-update project from our reference version (generated by a human / associated with the project). We estimate recall and precision by looking for a matching line change between the AIM
igrate
version and the reference version. These metrics assess correctness line-by-line and complement the test based approach. We conduct an additional analysis looking at code correctness in section
5.3
.

For each case study, we run three migration strategies:

•

Black box
: We include only the name, common alias (e.g., np for numpy) and versions of the legacy and target library in the prompt.

•

With code
: We include the filtered code files from the target library in the prompt.

•

With diff
: We include the diff for the filtered code files in the prompt.

We tried AIM
igrate
with the datasets using a suite of open and private LLMs including from OpenAI (gpt-4o, gpt-4o-mini, o1, o1-mini), Google (gemini-flash-1.5, gemini-2.0-flash-exp), llama (llama3-8b), and Anthropic (claude-sonnet-3.5). Of these, we observed that only a subset of the OpenAI models (gpt-4o, gpt-4o-mini, and o1) were appropriate for this particular analysis (see appendix
C.1
for specific model release information). The Gemini models had a tendency to devolve from producing Python code to incomprehensible diffs format; o1-mini would fail on single file requests; our requests exceeded Anthropic’s rate limits; and llama3’s memory requirements exceeded the memory of our devices. While additional engineering on the pipeline would likely reduce these model failures, we include these differences as useful notes and will focus on the three most robust models (gpt-4o, gpt-4o-mini, and o1) for our analysis.

Our evaluation pipeline involves running code generated by the LLM. Follow basic safety procedures such as using an isolated container and secure environment when running the scripts associated with this analysis
Lacasse 2018
.

5.3
Code correctness

We used AIM
igrate
in a real-world example to migrate T
yphoidsim
from S
tarsim
v1.0.3 to v2.2.0. The main change was the introduction of time units, which necessitated many often subtle changes to the code (see figure
7
for an example), such as replacing a unitless scalar parameter value with a unit-aware object instance. Many class methods were also renamed, and some methods also had changed signatures (i.e., the new methods required different input arguments). In short, these changes were far more extensive and more complex than what could be easily accomplished through either find-and-replace or manual inspection.

We used two metrics to assess the performance of AIM
igrate
in migrating T
yphoidsim
from S
tarsim
v1.0.3 to v2.2.0: accuracy of finding the
location
(i.e. line number) of each required change, and accuracy of producing the
correct
change. In both cases, we are treating the (AI-assisted) human-migrated code as the reference. (Note: even though there are three
semantic
changes shown in the example shown in figure
7
, for the purposes of quantification, this would be counted as two changes with locations 21 and 24, since consecutive lines are treated as a single change by the diff algorithm.)

Although there were many cases where AIM
igrate
produced an “almost” correct solution (such as subtle changes to whitespace or comments), here we are counting a code change as “correct” if and only if it is identical to the human-migrated change.

To perform the reference migration (AI-assisted human), AIM
igrate
was run on T
yphoidsim
four times, generating four copies of the T
yphoidsim
source files. These were then manually merged with each other by a T
yphoidsim
project maintainer, keeping only valid changes in each merge. The merged version was then manually edited until the code was fully compatible with S
tarsim
v2.2.0.

Performance of AIM
igrate
is shown in figure
8
. Of the 220 required changes between the original T
yphoidsim
code and the reference migration, a single run of AIM
igrate
correctly identified 144 (65%) of these changes. The second run identified slightly fewer correct changes (140), but, since the changes identified were only partially overlapping, when combined with the first run, significantly increased the number of changes identified to 176 (80%). Further runs resulted in few additional changes identified.

Of the 220 required changes, the first AIM
igrate
run correctly generated 104 (47%) of them, which increased to 124 (56%), 130 (59%), and 131 (59%) correct changes when combined with the three subsequent runs. Thus, even for a complex migration involving a large number of changes to code logic and syntax, AIM
igrate
was able to make nearly half of these changes perfectly from a single run.

6
Conclusion

Diffs provide a way to compress and localize code changes and have the potential to increase the performance of LLM-based tools. Indeed, this has already been reported for some tasks
Fan et al. 2024
. With our diff comprehension test we provide additional evidence that some LLMs can use diffs to solve a problem with similar performance to how it would with the entire code (see section
2
). Building upon this result, we explore the potential application of diffs to help automate code migration: taking a project and updating it to use a new version of a dependency.

We present a Python library, AIM
igrate
, that can help automate code migration using this diff-based approach, referencing library files, or using an LLM out of the box. Using AIM
igrate
we explore three case studies drawn from three different domains: disease transmission modeling, particle tracking for ocean circulation models, and building LLM based applications. Furthermore, the structures and challenges associated with the case studies are also quite different. This diversity contained in these examples allow us to highlight where this diff-based approach may exceed, or at least have parity with, the code based approach. In addition we present a real-world example where the AI assists the human and demonstrate that the diff based approach can make nearly half of the required changes perfectly from a single run (see section
5.3
). Future work includes assessing different algorithms for constructing the diff (e.g., Myers vs patience) as there have been measurable effects in previous diff applications
Nugroho et al. 2020
and improving the filtering and artifact creation for the diff.

There are several important limitations to this method. First, the selection of files to include from the library is user-specified rather than automated or rule-based. In practice the user should have knowledge of both the project and the library and so already has some prior. Second, the diffs can easily become large, exceeding the context window length of most LLMs and potentially reducing the quality of the output
Li et al. 2024
;
Levy et al. 2024
. See appendix
C.3
and
C.4
for cost and timing reports. Such a large context window (
\geq 128k
tokens) may be prohibitive to deploy locally.

We hope that AIM
igrate
can make a difference for migration or exploration using diff-based approaches.

What is the parcels python package?

The ‘parcels’ Python package is a tool designed for simulating the transport and dispersion of particles in oceanic and other fluid environments. It is particularly useful in the fields of oceanography, environmental science, and computational fluid dynamics. The package provides a framework for defining particle properties, movement equations, and the interactions of particles with their surrounding environment based on various flow models.

Key features of the Parcels package include:

1. **Particle Tracking**: Simulates the movement of particles based on flow fields, which can be derived from various sources, including observational data or numerical models.

2. **Flexible Framework**: Users can customize the behavior of particles, including their initial conditions, advection schemes, and interactions with environmental factors.

3. **Integration Methods**: Supports multiple numerical integration methods for the advection of particles, allowing users to choose the most appropriate method for their specific application.

4. **Compatibility**: Works with various data formats and can be integrated with other oceanographic tools and libraries in Python, such as NumPy and xarray.

5. **Visualization**: Provides utilities for visualizing the trajectories of particles and analyzing the results of simulations.

Parcels is beneficial for researchers and practitioners looking to model and understand the dynamics of particles in various fluid systems, including ocean currents, estuarine mixing, and pollutant dispersion.

To get started with Parcels, users typically need to install it via pip and then refer to the documentation for details on how to set up and run simulations. The package is actively maintained and has a growing community of users contributing to its development and application in various scientific studies.

LangChain is especially useful for developers looking to create applications that require dynamic interaction, context management, and the ability to handle complex queries using natural language processing.
