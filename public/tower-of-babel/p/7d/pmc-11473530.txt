Identifying shader sub-patterns for GPU performance tuning and architecture design
Authors: Lin Zhao, Chai Kiat Yeo, Arijit Khan, Robby Luo, Ling Peng Jin
Published: 2024

ABSTRACT
AbstractGPUs are increasingly playing vital roles in the modern technology industry. Improving the GPU performance involves optimizing its architectural design and fine-tuning its software code. However, to achieve this, engineers must investigate codes from as many GPU-related applications as possible to identify code portions that need fine-tuning. Moreover, this effort requires engineers to have good domain knowledge, and their work is made more arduous because the source codes of applications are normally confidential. To this end, we introduce ShaderAnalyzer, a solution leveraging graph mining and machine learning to analyze GPU-executed low-level machine codes and identify their fine-tuning opportunities. Our approach includes representing machine code with graph structure and subsequently identifying frequently occurring substructures within the codes. Optimizing the execution of these substructures can enhance the overall performance of the GPU. In addition, our model leverages these frequent patterns to further facilitate engineers’ tasks by selecting representative patterns to predict and investigate low-efficiency ones. We conduct comprehensive experiments to evaluate the performance of our solution, and the results have been validated by our industry partners. ShaderAnalyzer is an end-to-end framework that helps engineers identify code segments with the highest potential for performance gains after fine-tuning and offers valuable insights for hardware architects in future products design.Subject terms: Computer science, Information technology, Electrical and electronic engineering

Introduction

GPUs have evolved from specialized visual processors to multi-functional units supporting applications ranging from video games to high-performance computing and deep learning. Continuously enhancing the GPU’s hardware architecture and optimizing device performance post-design is critical for manufacturers. However, identifying design improvements and conducting performance tuning are challenging and labor-intensive tasks. In the conventional engineering process, shader-oriented design and tuning are essential to improve GPU performance, as shaders are the code that is machine-level and hardware-related. Shaders, including Geometry Shader (GS), Pixel Shader (PS), Compute Shader (CS), etc., perform diversified functions such as primitive and pixel rendering and parallel and intensive computational tasks. Conventional performance tuning involves executing shaders on GPUs and analyzing output metrics to adjust hardware parameters.

Problem definition

Typically, the industry adopts two methods for tuning GPUs. The first method involves iteratively sweeping through different GPU configuration parameters during program execution on a GPU to determine the optimal setting for each application. The critical parameters to test are determined by domain experience. The second approach selects key frames based on pre-defined rules, executes these frames on the GPU, and analyzes its performance. With these results, engineers then conduct a step-by-step analysis to locate bottleneck portions in shader codes, investigate the root causes, and determine optimal settings as well as hardware architecture improvements.

However, several challenges are observed while applying the conventional methods. (1) Engineers face substantial constraints when accessing the application source code. The high-level source codes of games and applications are encrypted by their developers, and they are inaccessible to GPU engineers. Instead, only a limited number of low-level shader codes generated by the runtime compiler are available. This fundamentally restricts tuning activities and identifying optimal tuning strategies. (2) Every game renders a significant number of frames, with each frame requiring thousands of draws (each draw presenting an algorithm or a function carried out by the programs referred to as shaders). Their huge number makes it infeasible to tune GPUs based on every piece of them. Table 1 shows an example of 4 games with the maximum and average number of instructions for one frame. Within a draw, there can be 20,000 lines of instructions, and it is difficult for engineers to investigate them one by one. (3) The requirement for extensive customization across diverse applications brings another layer of complexity. This leads to suboptimal performance as a single methodology fails to meet the diverse needs of different applications. (4) The time and efforts incurred are prohibitive to enable software driver optimization as well as hardware architectures to adapt to the continual emergence of thousands of new games or applications.

Related work

Device tuning

Existing works are mainly from a hardware perspective. There is little analysis from a software (shader) perspective to find opportunities for efficient fine-tuning. Several toolkits by manufacturers such as AMD Radeon Developer Tool Suite1, Intel VTune2 and NVIDIA GPU toolkits3, as well as third-party tools like HPCToolKit4 and Greenspector5 facilitate GPU performance profiling by analyzing graphics, event timing, pipeline stalls, compute usage, barriers, bottlenecks, and other performance-related works. Additionally, research projects6–8 contribute advanced methods and models for efficient GPU application code optimization and profiling. Furthermore, many studies have been conducted to characterize GPU simulation programs9,10. One major direction is to select the representative portions of a GPU application based on statistics obtained from running it on a simulator.

The aforementioned tools for visualization and identification of code segments which need to be improved in the software development phase, as the GPU is no longer a black box. Besides, these tools identify performance issues based on a single application. The proposed method is intended for GPU designers and engineers who want to maximize the performance of the new generation of products for various use cases, including the cutting-edge ones. Our proposed method, ShaderAnalyzer speeds up the entire GPU fine-tuning process by reducing the number of shader codes to be investigated, utilizing graph mining and machine learning techniques. It can also locate application weaknesses that might help boost hardware performance as a whole.

Graph in code analysis

Graph-based techniques play a crucial role in code analysis for, e.g., debugging, malware detection, and code comparison11–13. Xia et al.11 applied graph embeddings to extract code semantics and built a model for cross-platform binary code similarity search. Mi et al.12 proposed a graph-based code representation method that parses source codes into an abstract syntax tree (AST) and trains the graph neural network (GNN) model to achieve its classification goal. Ning et al.14 created graphs based on the function calls in software codes and obtained structure semantics using graph auto-encoder. Abdelaziz et al.13 built a knowledge graph of codes for applications like program search, code understanding, automation, and bug detection.

Compared with these tools, in which high-level languages are translated into a graph, our proposed ShaderAnalyzer, focuses on machine-level code analysis, where nodes refer to resource groups and edges indicate the execution sequence.

Our contributions

To address the aforementioned challenges, we develop a novel system called ShaderAnalyzer that integrates graph mining with machine learning techniques to guide GPU performance tuning and future hardware design from a shader code perspective. Our key ideas are as follows. (1) We convert the low-level shader codes of GPU-based applications (e.g., video games) into shader graphs and construct the shader graph dataset. (2) Next, we mine frequent sub-graphs from the dataset to identify critical portions of shader codes for performance tuning. While adopting state-of-the-art frequent subgraph mining algorithms to this problem, two issues arise. Some of the generated subgraphs are very small as well as incomplete, which are thus not meaningful in practice. To address these issues, we propose two algorithms: MAX-gSpan and shader graph partition and mapping, to obtain maximal and meaningful subgraphs. (3) Finally, we design downstream tasks aiming to further reduce the number of frequent sub-shaders that require tuning. These tasks identify representative and low-performance frequent sub-shaders, enabling engineers to prioritize and focus on them during device tuning. As a result, ShaderAnalyzer improves the coverage of the performance tuning to more applications (e.g., games) within the given time limit and the tuning becomes more focused and efficient. The integration of methodologies and their practical implementation signifies a notable advancement in this domain, establishing a new benchmark for shader code analysis and optimization.

With the help of ShaderAnalyzer, the performance tuning can be boosted in several impactful ways:

(1) ShaderAnalyzer identifies common sub-patterns across all applications that represent the algorithmic structures in these applications. By optimizing these frequent but low-performance algorithmic structures, engineers can significantly boost the overall GPU performance. Such patterns also provide valuable insights for hardware architects in designing next-generation products. For example, a specialized hardware architecture can be allocated to handle the most frequent patterns so that the product can process these patterns with maximum efficiency. (2) This tool highlights representative frames, applications, and sub-patterns which reduce the redundancy of tuning tasks across similar applications and shaders. This approach not only decreases the time and effort required for tuning, but also expands the coverage to include applications with diverse features, making the tuning process more comprehensive. (3) Given a new application dataset, ShaderAnalyzer can quickly identify similar program structures from existing libraries to facilitate the optimization process using reference configuration. It also predicts under-performing subpatterns to help GPU designers quickly pinpoint weaknesses and enable them to create targeted solutions from both software optimization and hardware architecture perspectives.

This paper is an extension of our initial work15 to showcase the comprehensive performance of our proposed ShaderAnalyzer, as well as to improve upon the identified weaknesses of the initial work. Case studies have been added to demonstrate the benefits and performance of the ShaderAnalyzer. Moreover, an end-to-end framework is proposed to facilitate ease of use by product engineers. A shortcoming of our initial work is that some of the mined subpatterns are too short for any meaningful code semantics and patterns to be identified. We have since rendered the mined subpatterns more meaningful through a post-processing method. In addition, the previous work converts shader codes to graph format using only key instructions from the code in order to simplify the graph structure as well as focus only on critical instructions identified by domain experts. As a result, some potentially important instructions that the experts have not studied before are missed. In this work, we introduce the full instruction graph structure and discuss the characteristics of this graph dataset. We also perform a study on the scalability of the frequent subgraph mining algorithm to gain insights into the running time when the proposed framework is used for more shader code datasets and instructions. Furthermore, we showcase how the results from our proposed ShaderAnalyzer are being used in practical applications, which can significantly facilitate the engineers to enhance the performance of the current GPU products, as well as help with the design of the next generation of products. The codes and sample datasets have been uploaded to GitHub16.

Proposed method

We demonstrate our system ShaderAnalyzer using video game datasets in this study. In fact, it can be extended to other applications as long as these applications are designed to execute on GPUs, their codes will be transformed to machine-level languages, which ShaderAnalyzer can accept as input.

System architecture

Figure 1 shows the architecture of the proposed framework in detail. First, video games are translated into disassembled shader codes by executing this game on GPUs using a graphics debugger, such as RenderDoc17. With the shader code, their corresponding shader graphs are formed by converting the shader instructions into nodes and their connections as edges. The frequent subgraphs are then mined from the shader graph dataset. For our purpose, only the maximal subgraphs are returned. Therefore, an algorithm called MAX-gSapn is developed to achieve this goal.

Architecture of the proposed framework.

Four downstream tasks are conducted to reduce the number of frequent subgraphs to be selected for performance tuning based on the graph community detection algorithm and machine learning techniques. As a result, a small subset of shader sub-graphs that appear more frequently are selected for the performance-tuning activity. As mining outputs are typically one portion of the graph that is not semantically meaningful to engineers, the shader graph partition and mapping strategy is developed to cut the entire shader graph into small portions that represent meaningful code blocks behind the scenes. Next, the mined frequent subgraphs are mapped to the shader code blocks and semantically meaningful frequent sub-shader code blocks are extracted as the final output for engineers to fine-tune.

Shader graph formulation

The graph dataset formulation comprises two steps. First, a few open-source tools like AMD Radeon GPU Profiler1 and RenderDoc17 convert video games into disassembled shader code. Second, these disassembled machine-level codes are transformed into graphs. Two types of graph formats are introduced and their differences are compared. Moreover, the consideration of applying different formats under different scenarios is discussed.

Figure 2a presents a disassembled shader sample comprising 10 instructions. Two graph formulation methods are introduced based on this code: the full-instruction and critical-instruction graphs. The former treats each instruction as a node, providing comprehensive details on node labels (Fig. 2b) and edge relationships (Fig. 2c). The latter concentrates on critical, time-intensive instructions (Critical and time-intensive instructions can be recognized by keywords such as VMEM, IMAGE_LOAD, etc. based on domain experience.) as node (Fig. 2e) to expedite analysis. The relatively fast-processed commands are aggregated into edge distance (Fig. 2f). Figure 2d and g demonstrate the corresponding graphs formulated from node and edge list.

A critical-instruction graph node label refers to that institution’s GPU functional blocks. For example, in Fig. 2e, SMEM_INSTR includes scalar memory related instructions such as SMEM_RD (appeared in Fig. 2b). The group named OTHERS includes all the instructions that are time-intensive, but does not belong to any major function groups (scalar memory, vector memory, etc.). In this paper, we demonstrate all results using the critical instructions graph dataset, which is aligned with industrial practices. It should be noted that the example employs chain structures. More complex patterns also exist in the graph dataset. A branch is formed due to the instruction BRANCH & LABEL and a cycle is created when there are S_SUBVECTOR_LOOP_BEGIN and S_SUBVECTOR_LOOP_END. These two machine codes indicate the beginning and the end of a loop function.

Mehodology

Maximal frequent subgraph mining

Frequent subgraphs are mined from each of the 68 scenes spanning 31 different games. For each scene, all shader code graphs derived from their representative frames are considered. To extract frequent subgraphs, the Graph-based Substructure Pattern Mining (gSpan)18 algorithm is employed, with the minimum support value set to 25% of the total number of graphs in each representative frame. Based on the parameter sweeping result, the pattern size becomes smaller and the number of results gets fewer with increasing support value. However, using lower support values leads to non-stop program execution for more than 1 day for the dataset and a large number of frequent subgraphs. Therefore, a minimum support threshold of 25% is selected. Additionally, our focus is on frequent subgraphs containing at least 5 nodes, thus we eliminate smaller, but frequently occurring subgraphs that offer fewer advantages for hardware optimization.

The time complexity of gSpan18 is O(kFS+rF), where k represents the maximum number of subgraph isomorphism between a frequent subgraph and a graph in a scene dataset, F is the maximum number of frequent subgraphs, S is the maximum number of graphs in a scene dataset, and r denotes the maximum number of duplicate DFS codes of a frequent subgraph originating from other minimum DFS codes. Figure 3 reveals that the gSpan runtime increases at a steeper rate with larger graphs compared to an increased number of graphs. With an average (maximum) of 1080 (6664) nodes and an average (maximum) of 1258 (8364) edges as well as about 8000 graphs, the running time of gSpan is modest at around 10 minutes.

gSpan running time vs. graph size and # graphs.

One observation from the subgraph results is that some subgraphs are subsets of others due to the algorithm’s mining procedure. These smaller graphs are redundant and consume memory space. To address this issue, Algorithms 1 and 2 show the implementation of MAX-gSpan which are developed on top of gSpan to retain only the maximal frequent subgraphs. A demonstration of MAX-gSpan workflow is given in Fig. 4. Subgraphs meeting all criteria are saved as a list with their support values. After discovering all subgraphs, a pair-wise comparison using subgraph isomorphism is performed to identify and eliminate non-maximal subgraphs.

Semantically meaningful code block generation

Further analysis reveals that the mined frequent sub-structures are often partial and do not represent complete, semantically meaningful code blocks. For example, in Fig. 5, a completed if branch is more meaningful. However, the mined subgraph is short of one vertex. This poses challenges for engineers in investigating these partial patterns as they lack the full context of the algorithm.

A comparison of shader subgraph of expected code block and the actual mined frequent subgraph.

A novel post-processing method, illustrated in Fig. 6, addresses this issue. Initially, each piece of shader code is segmented into discrete code blocks (step 1). In this study, code blocks refer to three types: loops, branches, and sequential computations. The first two types are identified as cycles in the graph, while the third type is a chain structure. To segment shader graphs, the directed shader graphs are converted to undirected graphs for identifying cycles (e.g., partition 2 in Fig. 6) and chain structures (e.g., partition 1 in Fig. 6). In this way, shader graphs are partitioned into sets of code blocks. Subsequently, the mined subgraph locates its position within its parent graph through subgraph isomorphism19 (step 2). Once all matches are found in the parent graph, a collection of code segments from the parent graph that covers all identified node indices is selected to form a complete code block as the output (step 3). This approach ensures that the frequently appearing instructions are coherently and fully represented as complete code blocks. Thus, it is easier for engineers to identify important code blocks. We show a graphic example and its corresponding text example of the partial subgraphs (in red) with their completed code blocks (in black) in Fig. 7.

Empirical study

The completed block of mined frequent subgraphs helps engineers with efficient GPU tuning and provides insights for design improvements. Engineers can focus on optimizing frequent patterns to enhance process efficiency. Additionally, they serve as datasets for future empirical studies. In this section, four empirical studies using the mined patterns are conducted.

Graph dataset validation

In this study, we would like to address the research question: are graph structures good enough to represent shader code?

To address this question, TF-IDF Vectorizer20 is employed to represent pure text contents as vectors. Term Frequency (TF) counts word occurrence within a shader and increases the importance of terms that appear frequently in a document, while Inverse Document Frequency (IDF) assesses word rarity across all shaders. Cosine similarity (ranging from 0 to 1) is then calculated between shader code pairs, and the average similarity between two successive frames is presented by comparing all distinct shader codes of a specific type (e.g., vertex shaders).

Next, the Weisfeiler-Lehman Graph Kernel (WL kernel)21 is applied to access graph structure similarity of shader codes. The WL kernel transforms the graphs into a series of graphs (kernel features) whose node attributes include structural and label information. It provides a comprehensive and efficient method for similarity comparison between shader graphs. The average WL kernel similarity value is computed across all pairs (one from the first frame and another from the second frame) from all distinct shader code graphs (taking into account a specific type of shader, such as compute shader (CS)) in these two frames. Furthermore, the pairwise graph similarity values are normalized between 0 and 1, by dividing them with ΠiK(Gi,Gi), where K(Gi,Gi) is the WL kernel-based self-similarity of graph Gi to itself, and we consider all Gi’s from these two frames.

Figure 8 displays the text content-based and graph structure similarity values for consecutive frames from 3DMark Fire Strike (3DMark FS) and Grand Theft Auto 5 (GTA5). All shader types in 3DMark FS and GTA5 have been analyzed but due to space constraints, only the VS (Vertex Shader) for 3DMark FS and the CS (Compute Shader) for GTA5 are illustrated. In 3DMark FS, small variations are observed across the 2800 frames, with more significant changes during scene transitions. In GTA5, CS shaders show clear changes at scene borders, with some scenes exhibiting consistent shader code structures.

3DMarkFS and GTA5: Content similarity (TF-IDF) vs graph similarity (WL kernel).

The WL kernel-based similarity graphs show the same basic tendencies as those based on TF-IDF text content similarity. This indicates that the graph representation consistently reflects the shader code contents. Besides, it also shows that graphic rendering algorithms are similar within scenes but vary across different scenes. Leveraging the WL kernel similarity result, the most representative frames can be selected with the highest similarity values, indicating that they capture predominant algorithmic patterns. It helps GPU designers by reducing repeated work during tuning and potentially reducing executions of repeated algorithms through efficient caching, thus speeding up data retrieval and rendering.

Clustering of games/scenes

With the identified frames from games, the second research question we investigate is the following: Is it possible to group games based on their subgraph characteristics to find representative games for performance tuning? By doing so, one can enhance the efficiency of tuning by avoiding redundant efforts on application datasets that have comparable characteristics. In practice, engineers consider each scene as a distinct dataset. Therefore, in this experiment, representative scenes are identified.

Method

All the maximal frequent subgraphs are used as features of each scene to cluster them. There are 64 data points (one for every scene), each with a dimensionality of 825 (representing all maximal frequent subgraphs). For a specific scene Si and dimension dj, the value Si[dj]∈(0,1) is computed as the maximum pairwise WL kernel similarity between each frequent subgraph of Si and the maximal frequent subgraph corresponding to dj. As a result, each data point has 825 features.

Next, K-means22, Gaussian Mixture23, and Birch24 algorithms are applied to unsupervisedly cluster these data points. Prior to clustering, Principal Component Analysis (PCA) is employed to decrease the number of features in order to mitigate the issue of high dimensionality. The optimal number of clusters is determined based on the Elbow method25. Figure 9a reports the within-cluster variance that monotonically decreases with larger cluster numbers K. The Elbow method selects K where the within-cluster variance no longer decreases sharply (e.g., 4 for K-means in this case). When new datasets are introduced for analysis, the distance between each dataset and the existing clusters is computed to determine the appropriate group for each dataset.

Scene clustering results.

Experimental result

Observations indicate that both K-means and Gaussian Mixture algorithms yield clustering results with a 93.75% overlap. Additionally, the BIRCH algorithm demonstrates a 95.31% overlap with the K-means clustering. Scenes with different grouping outcomes are located near the boundary of two groups based on the three clustering approaches. The K-means clustering result is depicted in Fig. 9b.

Every group is assigned a distinct color. The cross symbol represents the centroid of that particular group. Scenes within the same group have analogous frequent subgraph topologies, indicating that the algorithmic patterns utilized in these scenes are similarly comparable. Thus, choosing the scene that is closest to the centroid of each group for performance analysis and tuning will be a highly effective and efficient approach. The grouping results are presented in Table 3. Further investigations aiming at identifying the key factors behind such grouping are done. First, it is observed that different scenes from the same game (e.g., f1173_TS_GT1, f207_TS_GT2) have similar frequent subgraphs; therefore, they are grouped into the same clusters. However, there are a few negative cases too, for instance, f444_3DM11P_GT4 and f251_3DM11P_GT1 (same game of 3DM11P but different scene) get assigned to two different groups. Second, the game engines used for developing the games may affect the high-level coding, as a result, the shader codes can be affected. For example, it can be found that game GF, XYS, FN, and ST adopt the Unreal Engine26. Games GF, XYS, and two frames from FN are assigned to group 4; however, ST belongs to group 3. In summary, there are many factors that can make a difference in the shader codes’ structures. No single dominating factor is always maintained in the clustering results. This highlights the importance of designing a systematic method for clustering scenes and games, such as ShaderAnalyzer, based on frequent subgraphs’ similarity.

Clustering of subgraphs

Building upon the previous task that selected representative frames and scenes, we now aim to further refine frequent subgraphs awaiting tuning by addressing the third research question: Can all the mined frequent subgraphs be clustered into groups based on their graph characteristics? Leveraging the clustering result, each group will be tuned using specific methods, with settings saved for future adoption. When a new application dataset comes in, its subgraphs are clustered accordingly and pre-determined settings are applied to tune the GPU for this application. This process eliminates redundant work on similar patterns. If the mined frequent subgraphs are new compared to existing groups, successful tuning based on them expands the tuning coverage.

Method

We form a new integrated graph with its vertices as each mined frequent subgraphs. Graph similarities are calculated using the WL graph kernel21 among all mined frequent subgraphs. A graph similarity threshold is determined from extensive parameter-sweeping experiments. The value is decided considering a balance between the number of communities and pattern variations within each community. For each pair of nodes, when the similarity value satisfies the predefined criteria for sufficient similarity, an edge is established to connect the two frequent subgraphs, which are now modeled as vertices. Subsequently, a graph community detection algorithm is employed to partition the newly constructed graph into distinct groups. A community is defined as a subset of vertices (i.e., originally a set of mined frequent subgraphs) that are densely interconnected with each other and loosely connected to the vertices outside the community.

Several state-of-the-art community detection algorithms are evaluated, including Multilevel27, Greedy28, and Walktrap29. Our findings indicate that Multilevel performs well on a large-scale dataset and produces reasonable community detection results. Therefore, the Multilevel algorithm is selected for the following experiment.

Experimental results

There are 1943 frequent subgraphs obtained from 21 games. With the similarity threshold set at 85%, we found 48 communities, with the top two groups containing 44.4% of all subgraphs. To evaluate the clustering result, Fig. 10 compares within-community similarity and between-cluster similarity values. The second barplot describes the maximum pair-wise graph similarity between clusters. It demonstrates the most similar subgraphs across different communities. This comparison shows a clear separation between within-community similarity and between-community similarity for most subgraphs, validating the efficacy of the clustering method in grouping subgraphs based on their graph structures and node labels. When new datasets are available, with the mined subgraphs, we compute the graph similarity between new subgraphs and the rest of the existing subgraphs in each community, the mined subgraphs can be put into the subgraphs community if the similarity value is higher than the minimum value of the within-community similarity. Since each group already has an optimal set of configurations based on past results, the tuning activity for the new subgraph can refer to it. In the worst case that some subgraphs do not belong to any existing communities, the whole analysis process should be re-executed to identify groups for these subgraphs.

The clustering results were also sent to domain experts for manual review and assessment. Through this inspection, they confirmed that graphs within the same cluster exhibit similar patterns that correspond to commonly adopted game engine algorithms, whereas the subgraphs in different clusters exhibit distinct patterns. This technique has been integrated into their daily workflow. We obtained two valuable pieces of feedback. First, adopting this technique has significantly enhanced their efficiency, reducing analysis time by over 2/3 and allowing more resources for exploring new algorithms during tuning. Furthermore, the dominant clusters, which reveal typical game algorithms, have been reported to chip designers for potential architectural improvements in the next-generation product.

Further discussion on industrial impact

If a piece of code is implemented using a loop and it is identified as a frequently appearing code segment, it can be realized in hardware using Application Specific Integrated Circuit (ASIC) technology. ASIC integrates circuit elements with different functionalities into a single chip. As opposed to the general purpose of microprocessors, they are designed for certain types of tasks.

In GPUs with Single Instruction Multiple Data (SIMD) computing, a thread is the smallest work element. The term “wave” refers to a collection of threads executing instructions simultaneously on a GPU. In traditional design, for memory read or write instructions, all threads within a wave must access memory using identical surface descriptors, which include parameters such as data format, memory type, dimension, and access mode. When threads access new surface descriptors, the compiler converts this need into a loop of code segments. In fact, this piece of frequently appearing code only targets specific applications utilizing various resource types. With ASIC technology, the GPU hardware architecture can be enhanced by preparing a resource cache for the most frequently used surface descriptor (frequent sub-patterns) and then modifying the instruction to transmit surface descriptor ID instead of the actual descriptor. Thus, when the instruction is executed, rather than sending a single surface descriptor per instruction to access memory, each thread of a wave can send one surface ID to the resource cache to retrieve surface descriptors. Utilizing an ASIC in this manner requires only one instruction, as opposed to a loop of instructions, thereby enhancing GPU performance.

Prediction of subgraph efficiency

In addition to eliminating redundant work, if frequently used subsets of shader codes can be enhanced for more efficient GPU processing, overall GPU performance will be improved. Even for domain experts, identifying inefficient portions from shaders is challenging when examining the entire code due to its extensive size and complex structure. Therefore, in this experiment, the research question to be investigated is: can we identify low-efficiency frequent sub-shaders from the mined sub-shader dataset to guide engineers on efficient fine-tuning?

Method

The subpatterns dataset is derived from representative frames of 68 scenes. As previously stated, the support threshold value for gSpan is set to 25% of the total number of graphs in each sample frame of a scene. Only the frequent subgraphs with at least 5 nodes are considered. The obtained subgraphs are used for the following experiment. Our industry collaborators annotated the dataset with label 1 for subpatterns that typically exhibit low efficiency in GPU execution and label 0 for subpatterns that exhibit high efficiency. The reasoning behind annotation is based on what was found in the mined subgraphs, mostly the latency and functional block characteristics of the GPU following domain experience.

The subpattern dataset incorporates a total of 43 GPU function blocks within the instruction set. The training dataset is represented by the number of appearances each functional block makes. This results in 43-dimensional data points for each frequent subgraph, where each dimension corresponds to the count of occurrences of the GPU function blocks involved.

The resulting dataset is unbalanced, with 11.98% of subpatterns labeled as low-efficiency (Label 1) and 88.02% as high-efficiency (Label 0). To obtain a balanced dataset for supervised learning, an equal number of samples from the high-efficiency subpattern dataset are randomly selected. Next, the dataset is split into 80% for training the model and 20% for validating the model prediction result. Due to the small dataset size, several fundamental machine learning models are evaluated, including XGBoost, Random Forest (RF), Logistic Regression (LR), and K-Nearest Neighbour (KNN). Ultimately, the Random Forest classifier with 4-fold cross-validation is chosen to forecast the efficiency of the frequent shader subgraphs, as it demonstrated superior performance in both accuracy and execution time.

Experimental results

An average validation accuracy of 0.94, AUC-PRC 0.97, and AUC-ROC 0.975 were obtained. A higher AUC-ROC score indicates a higher true positive rate and a lower false positive rate for each threshold, meaning a good distinction between high and low-performance classes. The AUC-PRC score implies 97% correct identification of low-performance shader by the classifier.

Utilizing the trained Random Forest model, the frequent subpatterns of a new game are classified into low-efficiency and high-efficiency groups while testing the model. To further validate the result, our industry collaborators have checked and confirmed that the majority of identified low-efficiency shader codes are reasonable based on their domain knowledge. Beyond identifying potential areas of improvement, utilizing our supervised frequent subgraphs classification model to mine sub-shaders from a new game allows for forecasting how well the new game will perform. If the room for improvement is minimal, engineers can shift focus to other games or applications to expand the coverage of GPU tuning.

Conclusions

ShaderAnalyzer presents a novel approach to examine the applications executed on GPUs. It converts large volumes of shader commands to graphs, and incorporates graph analysis tools to help users gain a deeper understanding of the code and identify frequently occurring sub-patterns.

A representative frame can be selected from a scene. Based on the frequent sub-patterns mined from applications, ShaderAnalyzer clusters all games and all sub-patterns into groups according to their graph similarities. Consequently, when frequent sub-patterns from a new game are extracted, whether it belongs to any game groups can be decided through a trained K-means model. Whether its sub-patterns belong to any pre-existing sub-pattern groups can be determined by computing the minimum pair-wise graph similarity. If the group is found, the previously summarized configurations for that group serve as a valuable reference for GPU tuning specific to the new patterns. This strategy significantly reduces the time and effort required for pinpointing the relevant sections for investigation and refining the hardware, minimizing reliance on trial-and-error methods. ShaderAnalyzer predicts low-performance sub-patterns in new game datasets. Beyond just reducing the optimization time, the identified patterns also provide valuable insights to hardware architects regarding commonly used instructions and potential design improvements for next-generation chips.

Utilizing gSpan frequent subgraph mining algorithm encounters limitations in generating maximal frequent subgraphs and semantically complete code outputs. To address these, an enhancement to gSpan and a post-processing phase that segments graphs into blocks and pairs them with the mined sub-patterns are proposed.

The current implementation of ShaderAnalyzer has limitations in handling different aspects of information from the original shader codes and relies on experts’ decisions for certain analyses. Future enhancement will incorporate additional shader code elements, such as input data and binding resources by improving graph representation. Furthermore, integrating deep learning models into the framework is also under consideration.
