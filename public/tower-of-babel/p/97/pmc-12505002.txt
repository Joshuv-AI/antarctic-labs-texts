Experimental dataset of video and radar detection for cooperative perception in urban environment
Authors: Andreia Figueiredo, João Amaral, Marcos Mendes, Rodrigo Rosmaninho, Duarte Dias, Pedro Rito, Miguel Luís, Duarte Raposo, Susana Sargento
Published: 2025

ABSTRACT
Cooperative perception is an emerging concept in intelligent transportation systems that enhances situational awareness by allowing vehicles and infrastructure nodes to share sensor information. By extending the sensing range beyond the line of sight of a single agent, cooperative perception enables safer and more informed decision-making in complex traffic situations. To support research in this area, especially from the perspective of infrastructure-based sensing, high-quality datasets are essential. This article presents a dataset that combines radar and camera-based object detection data in standardized Collective Perception Messages (CPMs), collected in a real vehicular environment. The dataset includes object-level information such as unique tracking identifiers, spatial position, speed, heading, and classification. In addition to the raw sensor detections, it provides message-level CPMs generated in real time by the infrastructure node, following the European Telecommunications Standards Institute (ETSI) Collective Perception Service (CPS) specification and applying its object inclusion rules. All data is timestamped and spatially referenced, enabling the reconstruction of object trajectories and behavior over time. The dataset is suitable for developing and evaluating cooperative perception algorithms, as well as applications like trajectory prediction, object classification refinement, and multi-sensor fusion benchmarking. Its accessibility aims to support the research community in advancing perception and prediction models for autonomous driving and intelligent transportation systems.

Value of the Data

•Importance: This dataset provides a unique perspective on cooperative perception from the infrastructure side, combining radar and camera-based sensing to track and classify road users in real-world urban traffic conditions. The dataset captures 72 hours of continuous data, weekend and week days, ensuring that natural variations in traffic density, object types, and environmental conditions are well represented. The data includes both sensor-level detections and standardized Collective Perception Messages (CPMs), making it directly applicable for end-to-end research in cooperative awareness and connected vehicle technologies.•Target audience: This dataset is relevant for researchers in the fields of cooperative perception, intelligent transportation systems, and autonomous driving. It is particularly valuable for those focused on Collective Perception Service (CPS), Vulnerable Road User (VRU) safety analysis, sensor fusion, object tracking, edge computing, and real-time message generation for vehicular networks. Additionally, researchers developing or validating infrastructure-assisted driving or decision-making frameworks will benefit from the standardized and geo-referenced sensor outputs.•Future use: This dataset offers extensive support for various applications, particularly in the domain of cooperative perception algorithms, trajectory forecasting models, and cross-sensor object association techniques. It serves as a valuable resource for benchmarking radar-camera fusion strategies and simulating infrastructure-generated perception messages, such as CPMs. Researchers can leverage this dataset to explore multiple research directions, including developing and testing object inclusion and selection strategies, establishing effective radar-camera fusion pipelines, and refining association algorithms. Additionally, it can aid in trajectory prediction models that utilize infrastructure-based sensing, risk assessment, and collision detection for VRUs. Furthermore, the dataset is beneficial for evaluating the message generation frequency under varying traffic conditions and integrating smart infrastructure into urban digital twin platforms or smart city data systems. For researchers without access to physical deployments, this dataset enables the simulation and testing of cooperative perception architectures, assessing robustness of perception-sharing methods, and comparing algorithmic performance through realistic, time-synchronized multi-sensor data streams.

Background

Cooperative perception enables intelligent transportation systems to improve safety and decision-making by sharing information across vehicles and infrastructure. Many recent datasets, such as DAIR-V2X [1], TUMTraffic [2], and V2XSet [3], primarily emphasize perception or classification tasks in controlled or scenario-specific settings. Others, like INTERACTION [4], focus on trajectory modeling but are limited in temporal coverage and lack standardized message formats. More recently, V2AIX [5] introduced a valuable dataset containing European Telecommunications Standards Institute (ETSI)-standard Vehicle to Everything (V2X) messages such as Cooperative Awareness Messages (CAMs), Decentralized Environmental Notification Messages (DENMs), MAP Extended Messages (MAPEMs), and Signal Phase And Timing Extended Messages (SPATEMs). While highly relevant, this dataset does not provide CPMs and does not offer long-duration continuous data. The motivation for compiling the present dataset is to address these limitations by offering a complete pipeline—from real-world object detection using infrastructure-based radar and camera sensors to the generation of ETSI-compliant CPMs. Data was collected continuously over 72 hours using a smart lamppost equipped with a Smartmicro radar and a Reolink IP camera, both connected to a local edge computing unit. The system performs real-time object detection, tracking, and classification, and outputs both sensor-level detections and the corresponding CPMs.

By including detailed object information alongside cooperative perception messages, this dataset supports research in sensor fusion, object uncertainty, CPM construction, and infrastructure-assisted V2X communication. It is designed to facilitate reproducible experimentation and algorithm validation in realistic urban scenarios.

Data Description

The dataset comprises three files types generated over a 72-hour data collection period by an edge node situated in a real urban environment. These files include information obtained from both radar and video-based object detection, as well as CPMs created from the collected sensor data.

Due to the volume of data, each sensor’s output has been organized hierarchically and divided into hourly files. For each data source type (radar, camera, CPMs) a top-level folder is provided. Within each folder, files are named according to the date and hour of capture, using the format YYYY-MM-DD for the date (e.g., 2025–04–12) and a zero-padded 24-hour format for the hour (e.g., 08, 13).

The complete file path and naming pattern is as follows:•camera/camera_{day}_{hour}h.csv•radar/radar_{day}_{hour}h.csv•cpm/cpm_{day}_{hour}h.jsonl

The radar and camera datasets feature object-level entries, with each row representing a single object detected at a specific timestamp. In contrast, the CPM dataset contains message-level entries, where each entry corresponds to a single CPM generated by the edge node at a particular time. This entry may include multiple objects detected simultaneously. Experimental Design, Materials and Methods

The dataset was collected using the infrastructure provided by the Aveiro Tech City Living Lab (ATCLL) [6], a large-scale urban testbed developed in the city of Aveiro, Portugal. The ATCLL infrastructure consists of 44 edge nodes deployed throughout the city, connected via a high-speed fibre network with 10 GbE links and centrally managed by a software-defined networking (SDN) switch located at the Instituto de Telecomunicações in Aveiro. Edge nodes are deployed in two physical formats: Smart Lamp Posts, installed near roads, and Wall Boxes, mounted on building facade. Each node is equipped with communication interfaces (5 G, 4 G, ITS-G5, WiFi, LoRaWAN), edge computing platforms (e.g., NVIDIA Jetson Nano/Xavier, Raspberry Pi 4), and a variety of environmental and traffic sensors, including radar, lidar, video cameras, and weather sensors.

For the dataset described in this article, a Smart Lamp Post located near a crosswalk on a four-lane road—a high-traffic entry/exit point in Aveiro—was used (Fig. 4). This node is equipped with a Smartmicro radar unit and a Reolink video camera, both connected to a local computation unit, NVIDIA Jetson Xavier, via Ethernet (Fig. 5). Data collection was carried out continuously for 72 hours, encompassing two weekend days and one weekday to reflect different traffic densities and patterns.Fig. 4Edge node location seen from two angles.Fig 4Fig. 5System architecture.Fig 5

System architecture.

The edge node runs a set of modular services responsible for sensor data acquisition, object detection and tracking, and CPM generation. These services operate concurrently and communicate through a local Message Queuing Telemetry Transport (MQTT) broker, which enables efficient and decoupled data exchange between components. Sensor-level outputs from both the radar and camera processing pipelines are published to the MQTT broker and stored in a local database for later use and analysis. To ensure consistent and synchronized timestamps across all modalities, the Jetson used as the edge computing device was configured with Network Time Protocol (NTP). All timestamps are generated on the same system and reflect the exact moment of data processing.

Fig. 5 illustrates the high-level architecture and complete data processing workflow. The Radar Processing service decodes the radar packets, extracts object-level information, and infers additional attributes such as geographic coordinates and classification. The Camera Processing service acquires video frames, performs object detection and classification, and projects the results into global geographic coordinates. Both services independently publish their results in real time in the MQTT broker. A local datasabe consumes those topics and stores the information for future use. The CPS service also subscribes to these outputs, applies the object inclusion rules defined by the ETSI CPS standard, and constructs CPMs. Each generated message is passed to the Vanetza-NAP [7] encoder and transmitted to the vehicular network. In parallel, a structured JSON representation of each CPM is saved locally. This architecture defines the complete data generation protocol used in the dataset. All components, from sensor acquisition to CPM construction and logging, operate in a real-time and synchronized environment.

Radar data collection

The radar data was collected using a Smartmicro UMRR-11 Type 44 radar, a 24,GHz multi-object tracking sensor designed for multi-lane traffic monitoring.1 This device can track up to 64 objects simultaneously and includes an integrated tracking algorithm that outputs object-level information such as position, velocity, heading, and length.

As detailed in [8], the radar is equipped with a built-in tracking service that transmits detection data via Ethernet to a local computation unit. As shown in Fig. 5, a custom processing service, referred to as Radar Processing, decodes the received packets at the edge. The extracted information is then sent to the MQTT broker, where it becomes available for other services to utilize. One of these services is a local database that consumes the information and stores it for later use.

The parameters provided directly by the radar form the basis for further processing. Each detection record sent by the radar includes the x and y position (in local radar coordinates), absolute speed, heading angle (relative to the radar’s reference), estimated object length, and a temporary object ID. Since the radar reports object positions in a local coordinate system, defined relative to the sensor’s orientation, this data must be transformed into geographic coordinates (latitude and longitude) to ensure compatibility with other geo-referenced sensor data and downstream applications. Additionally, the radar does not provide acceleration directly; instead, it is estimated in the processing pipeline by comparing the current and previous speed values for each tracked object. When no previous measurement is available, the acceleration field is marked as missing. Object classification is also inferred during processing. Based on the object’s length and speed, each detection is assigned to one of four classes: motorcycle, car, truck, or VRU, the latter comprising pedestrians and bicycles. This additional information enriches the raw radar data, enabling its use in cooperative perception and traffic analysis tasks.

Camera data collection

The camera data was collected using a Reolink IP camera (model RLC-823). The process of acquiring and processing the camera data builds on the architecture developed and evaluated in [9]. The image processing pipeline runs on the edge node co-located with the radar and is responsible for acquiring video frames, detecting objects, and calculating their global positions.

The Camera Processing service (Fig. 5) first acquires frames using GStreamer and compensates for lens distortion using a pre-computed calibration matrix. Object detection is then performed using the YOLO algorithm. Although the system was originally based on YOLOv8, as presented in [9], it has since then been updated to use YOLOv112. This allows for the identification of each object’s class, bounding box, and tracking ID. Finally, the service transforms the detected pixel coordinates into global geographic coordinates using a geo-referencing matrix obtained during the calibration phase. This step enables spatial alignment with data from other sensors, such as the radar. Once the object data, including classification, bounding box, and position, is extracted, it is then published to an MQTT broker. This broker serves as a message distribution hub, facilitating efficient communication and data exchange between multiple services. One of these services involves a local database that stores this information for later use.

CPM generation

The generation of CPMs follows the ETSI CPS specification [10]. The implementation used in this work is based on the framework and methodologies presented in [11,12], which enable real-time CPS-compatible message generation and processing.

The CPS collects the processed outputs from both the radar and camera pipelines running at the edge node. It applies the object inclusion rules defined by the CPS specification to determine when an object should be included in a message. An object is added to the CPM if it appears for the first time, moves more than 4 meters since it was last included, changes its velocity by more than 0.5 m/s, changes its heading by more than 4°, or if more than one second has passed since its last transmission. In addition to object data, information about the sensor is transmitted at least once per second as required by the CPS. If no objects meet the inclusion criteria within a given second, a CPM is still generated containing only the sensor information and indicating that zero objects are present. Each CPM is structured according to the ETSI message format and encoded using Vanetza-NAP [7]. For each constructed message, a JSON presentation of the message is saved in a local file.

Limitations

Object positions obtained from the radar are provided in local coordinates before being transformed into geographic coordinates using a calibration-based method. In contrast, camera-based object positions are geo-referenced directly through a pre-computed transformation matrix applied to the detected image-space coordinates, as described in [9]. Despite careful execution of these transformations, minor inaccuracies in localization may still arise, which should be taken into account for applications that require high-precision positioning. Additionally, some object attributes, such as acceleration, may be missing during initial detections. While default placeholders are consistently applied, this could impact models that depend on complete feature vectors.
