Creating an Interactive Web Interface for Networks Stored in Knowledge Graph Databases
Authors: John Erol Evangelista, Andrew D Lutsky, Anna I Byrd, Daniel J B Clarke, Abinanda Prabhakaran, Sherry L Jenkins, Avi Ma'ayan
Published: 2025

ABSTRACT
AbstractKnowledge graphs (KG) are an emerging approach to organize biomedical research data by abstracting knowledge into networks that connect genes, diseases, pathogens, drugs, metabolites, cell types, pathways, patients, researchers, and other related concepts. While there are many KG databases, most do not offer a free and customizable web‐based user interface (UI) to query and interact with KG. We developed an open‐source UI to create interactive websites from data stored in KG databases. So far, the KG‐UI has been applied to eight bioinformatics projects: ReproTox‐KG, Enrichr‐KG, Harmonizome‐KG, Data Distillery KG‐UI, Biomarker‐KG, Common Fund Data Ecosystem Gene Set Enrichment (CFDE‐GSE), ChEA‐KG, and lncRNAlyzr. To demonstrate how to install and customize the KG‐UI, we created a demo KG that displays a network of relationships between NIH‐funded principal investigators (PIs) from a single institution in a specific year. This PI network was constructed by querying PubMed using grant information collected by the Blue Ridge Institute for Medical Research (BRIMR). After publications were collected from PubMed, PI name disambiguation and metadata formatting was performed to create the PI demo KG. Instructions for ingesting this network of PIs into a KG database, setting up the web app, and customizing the app are provided in a step‐by‐step user guide. The KG‐UI source code is available from: https://github.com/MaayanLab/Knowledge‐Graph‐UI/ and the demo KG is available from: https://github.com/MaayanLab/PINetworkDemo. © 2025 The Author(s). INTRODUCTION

The volume and diversity of biomedical knowledge is expanding rapidly. Such data are sourced from omics profiling of cells and tissues, including genomics, epigenomics, transcriptomics, proteomics, and metabolomics, as well as data from electronic health records (Cremin et al., 2022; Ristevski & Chen, 2018). It is estimated that only a small fraction of such data is reused to advance our collective knowledge because of the computational challenges involved in harmonizing data from different modalities (Wang & Alexander, 2020). One growing strategy to harmonize datasets for reuse and knowledge discovery is to abstract the data into networks that represent the relationships between entities. Abstracting biomedical data into networks is not a new idea and has been demonstrated to be useful for facilitating data integration that leads to useful insights (Barabási & Oltvai, 2004; Gosak et al., 2017; Ma'ayan, 2009; Pavlopoulos et al., 2011; Zitnik et al., 2024). In biomedical research, nodes commonly represent entities such as genes, proteins, drugs, metabolites, pathways, cells, tissues, patients, and diseases. Edges commonly represent the relationships between two nodes. For example, the knowledge graph assertion that “INS” (node), “participates in” (edge), and “Insulin signaling pathway” (node) conveys the knowledge that the insulin gene is involved in the insulin signaling pathway. Knowledge graph (KG) databases have emerged as a useful way to store, query, and serve networks in biomedical research and other fields (Callahan et al., 2020). KG databases store network information in their native structure, facilitating fast and efficient searches and supporting many node and edge types (Garg et al., 2024; Nelson et al., 2022; Rotmensch et al., 2017; Santos et al., 2022).

Many KG databases have emerged in recent years (Table 1), offering different features and different ways in which data are stored and queried. One of the most widely used KG databases is Neo4j (https://neo4j.com/), which implements the Cypher query language and has an interface to visualize query results as ball‐and‐stick diagrams. However, its network visualization feature is currently embedded with the Neo4j desktop interface, which requires writing queries in Cypher and this provides limited customizability of the network visualization features. There are several alternatives to visualize and interact with KG databases including Neo4j (Table 3). For example, Neo4j Bloom and yWorks Data Explorer for Neo4j offer the ability to interact with Neo4j in the Neo4j Browser. However, most of these platforms require a paid subscription and provide limited ability to build customizable web‐based interfaces. There are open‐source network visualization software libraries that could be used to construct web‐based interfaces to interact with KG databases (Table 2), but building such applications requires significant skill and effort.

To address this gap and further promote the use of KG databases, we have developed an open‐source user interface (UI) that enables users to visualize and interact with KGs and enables developers to create customized web‐server applications that interface with KG databases. The KG‐UI was developed in a React framework that interacts with a free‐tier instance of a Neo4j database. The database runs on the server side in a Docker container. The KG‐UI allows users to visualize subnetworks using simple dropdown menus and search fields to perform queries. The KG‐UI website can be customized via a single JSON schema file that lets developers edit their website name and logo, customize the search and filtering options, and add pre‐built features to tailor the website for specific use cases by adding or removing components from the user interface. So far, the KG‐UI has been used to create eight web‐server applications (Table 4) that display a variety of biological networks. These include ReproTox‐KG (Evangelista, Clarke et al., 2023), Enrichr‐KG (Evangelista, Xie et al., 2023), Harmonizome‐KG (Diamant et al., 2024), Data Distillery KG‐UI, Biomarker‐KG, Common Fund Data Ecosystem Gene Set Enrichment (CFDE‐GSE) (Evangelista, Clarke et al., 2025), ChEA‐KG (Byrd et al., 2025), and lncRNAlyzr (Evangelista, Ali‐Nasser et al., 2025). Here, we provide detailed instructions on how to prepare networks for ingestion into Neo4j, as well as deploy and customize the KG‐UI web‐server application via a customizable workflow (Fig. 1). In Basic Protocol 1, we demonstrate how to construct a network that connects NIH‐funded principal investigators (PIs) utilizing data from PubMed and other resources. This PI network offers an intuitive example of constructing a KG. Next, Basic Protocol 2 describes how to validate the network by testing its structural integrity and by computing descriptive statistics about the types of nodes and the connectivity distribution. Basic Protocol 3 demonstrates the use of the Neo4j database container to ingest the formatted KG. Basic Protocol 4 describes how to interact with the KG using the Neo4j remote interface. Basic Protocol 5 describes how to adapt the KG‐UI to the ingested KG to produce a web‐server application. Finally, Basic Protocol 6 demonstrates how to interact with the KG‐UI. Together these protocols should provide developers of biomedical KGs the needed information to deploy a UI for their KG, fostering the sharing of curated biomedical knowledge.

CREATING THE PRINCIPAL INVESTIGATOR NETWORK

The following protocol describes in detail the process of constructing a KG of PIs connected via shared publications, grants, and MeSH terms. To limit the size of such a KG, the starting point is NIH grants data compiled by the Blue Ridge Institute for Medical Research (BRIMR, https://brimr.org). BRIMR collects grant information annually from the NIH RePORTER database and compiles it in an intuitive and integrated manner. From BRIMR, we collect all award identifiers that belong to a single organization and then query the PubMed database with these identifiers utilizing the Biopython Entrez wrapper library (Cock et al., 2009). The single organization is by default our institution (Icahn School of Medicine at Mount Sinai), but this can be modified easily. We then utilize the information from the returned publication from each query to construct the set of nodes (PIs, publications, grants, and MeSH terms) and a set of edges that connect them.

Edge files require three fields: source, relation, and target, where sources and targets are nodes identified by their IDs and the relation is the edge description (i.e., “Coauthors” or “Publications”). Edge files should be titled <edge type>.<relation>.<edge type>.edges.csv. Below we format the PI network for ingestion. VALIDATING THE PRINCIPAL INVESTIGATOR NETWORK

After the KG has been created, it is important to test whether the connections that emerged make logical sense and are valid based on their biological meaning. Different errors can emerge at different levels, for example, a node that represents a tissue may become connected with a cell type that is not present in the tissue, or genes not expressed in the tissue, or the cell type may become connected to these entities. Such logical mistakes should be caught before ingestion. In some cases, however, such apparent logical “errors” could be novel predictions that can be used for forming useful hypotheses. Comparing query results to existing knowledge and comparing results with external tools are suggested to ensure that the ingested KG is semantically coherent. Specifically, it is recommended to perform descriptive statistics of the networks, such as node and edge type counts, connectivity distribution histograms, and other common network analysis properties.

Below we describe the process of setting up and running the notebook network_validation_example.ipynb along with its output. After each step, run the code block(s) referenced in that step by clicking the “run” button. Steps 1‐10 should be completed immediately after constructing the network and before ingestion. The remaining steps should be completed after ingestion.

INGESTING THE KG ASSERTIONS INTO Neo4j

KG assertions can be stored in a Neo4j KG database to facilitate querying the data and exploring the relationships between nodes and links by running queries. Two ingestion scripts are provided in PINetworkDemo/src. The script import_csv.py is the default script used to ingest the network. If a network has redundant attributes (e.g., repeated IDs), then import_csv_with_merge.py should be used. This will merge the metadata associated with the repeated IDs into one node. Both scripts take as input the path to a directory that contains the formatted network assertions. To be compatible with the ingestion scripts, the assertion files must be formatted and named according to the specifications provided in Sinai2024.ipynb. The ingested data can then be used to serve the KG‐UI. The loaded data can also be viewed inside the Neo4j remote browser (available at https://localhost:7474/browser) and queried using the Cypher language.

Data security consideration: Users should be aware that KG‐UI may expose read‐only Neo4j databases that are not available directly from the internet. Any user with access to the KG‐UI frontend may effectively be able access the contents in the backend database. For protected data, KG‐UI should be deployed on an internal protected network.

BUILDING AND CUSTOMIZING THE KG‐UI

While the Neo4j remote interface provides data visualization, it lacks a public web‐based open‐source UI where users can easily query data without the need to know how to write queries in Cypher. Additionally, many applications require a customizable UI for serving their specific applications. To address this, we developed a UI that interfaces with KG databases such as Neo4j. This UI can be customized with installable components, including (1) standard single‐term and two‐term search that allows users to query by label and other metadata and (2) visualization of subnetworks returned from enrichment analysis. The UI also includes themes to customize the look and feel of the web interface. These themes modify the overall color palette of the site and control other aesthetic elements. Additional custom components and themes can be added to extend the site. The KG‐UI is built using React, Next.js, Cytoscape.js, and Material UI.

Here, we demonstrate the various customization options of the UI using the demo co‐authorship network as an example. Steps 1‐10 describe the process of creating schema.json and the various customization options. Steps 11‐18 describe how to run and deploy the UI. To demonstrate the variety of customization options, we include examples from several existing implementations of the UI. Schema

The UI is built using a JSON document, schema.json. This file includes five fields: nodes, edges, header, footer, and user interface theme. Each field defines part of the UI. While schema.json can be edited manually, we also provide the notebook setting_up_ui.ipynb, which automatically adapts the file to describe the loaded Neo4j database to the UI.

Add and configure page components

The KG‐UI comes with components that facilitate queries of the Neo4j database. These include a single‐term search that returns a node's immediate neighbors, term‐to‐node‐type search that returns the shortest path between the search query node and a type of node (e.g., author “Robert O Wright” to Publications nodes), two‐term search that returns the shortest path between two terms, and an enrichment analysis component that performs integrated enrichment analysis. New components can easily be added to cater to specific use cases. We describe several components below using examples from existing implementations of the KG‐UI.

KnowledgeGraph and SimpleKnowledgeGraph differ on whether users can filter by other metadata fields. Add Enrichment component. The enrichment component performs enrichment analysis using an external API, defined in the .env file as NEXT_PUBLIC_ENRICHR_URL. Using this component, you can input a gene set and select multiple libraries. It then returns a subnetwork connecting genes to enriched terms, providing an integrated view from multiple libraries (Fig. 9A,B). This component is structured similarly to the KnowledgeGraph component, with the following differences:

The component field is changed to Enrichment.

Within props, the placeholder field customizes the placeholder in the input text area.

The example field provides the input gene set and libraries selected when trying an example.

The libraries field defines (1) the libraries for enrichment analysis, (2) the name of the node in the Neo4j database, and optionally (3) a regex pattern that is used when the gene set library has directionality (e.g., up or down gene set) reflected in the edges.

The sortLibraries field sorts the libraries alphabetically, if needed.

The default_options field contains the preset options when visiting this component.

The enrichment component also supports free text summary of the network (Fig. 9C), which can be done by adding the templates field in the edge's schema. COMMENTARY

Background Information

Several implementations of the KG‐UI are publicly accessible (Table 4; Fig. 5). Among these, Reprotox‐KG, Enrichr‐KG, Harmonizome, and lncRNAlyzr are an integral component of a publication (Diamant et al., 2024; Evangelista, Ali‐Nasser et al., 2025; Evangelista, Clarke et al., 2023; Evangelista, Xie et al., 2023). Reprotox‐KG, CFDE‐GSE, Data Distillery KG, and Biomarker‐KG were developed for projects related to the CFDE program (Evangelista, Clarke et al., 2025; Fig. 5). Together, these implementations cover a range of applications and demonstrate the adaptability of the KG‐UI to specific use cases. Additional background is provided below for the four published KG‐UI implementations.

Reprotox‐KG (Evangelista, Clarke et al., 2023) integrates data about drugs, genes, and adverse events from multiple sources to predict drugs that may induce birth defects and to explain mechanisms of action of drugs and genes known to lead to formation of birth defects. The included data are from co‐mentions of drugs and birth defects in publications, and drug‐ and gene‐induced changes in gene expression from the NIH LINCS program (Evangelista, Ali‐Nasser et al., 2025; Keenan et al., 2018), birth defect terms from ontologies, known drug targets, and phenotype‐gene associations from GWAS studies.

Enrichr‐KG (Evangelista, Xie et al., 2023) is a data analysis visualization layer that utilizes the Enrichr gene set search engine API to visualize enrichment analysis results as interactive node‐and‐stick diagrams. The KG is built using a subset of 24 Enrichr gene set libraries. The result is a network of enrichment terms and their associated genes across multiple libraries.

The Harmonizome database (Diamant et al., 2024; Rouillard et al., 2016) integrates multi‐omics data from 140 publicly available datasets by processing these datasets into several abstract representation data structures. It provides several tools for integrative data analysis of these datasets, gene and protein landing pages that serve knowledge from all the sources, and the ability to download the processed data in multiple formats. Harmonizome 3.0 (Diamant et al., 2024) has a knowledge graph feature that enables users to view datasets as interactive ball‐and‐stick diagrams utilizing the KG‐UI.

lncRNAlyzr (Evangelista, Ali‐Nasser et al., 2025) is a long noncoding RNA (lncRNA) enrichment analysis tool developed for conducting gene set enrichment analysis for sets of lncRNAs. lncRNAlyzr contains 33 libraries computed from gene‐gene co‐expression correlations between lncRNAs and coding gene sets. The co‐expression correlations are computed from thousands of uniformly aligned bulk RNA‐seq samples (Lachmann et al., 2018) extracted from the Gene Expression Omnibus (GEO).

Critical Parameters

File location

Several of the provided notebooks and scripts in Basic Protocol 1 pre‐define the input file location, which is the construction/Network directory. These files must be organized in the same way for the scripts to run properly.

Network assertion files

While an example network is provided in Basic Protocol 1, other types of networks can be ingested into Neo4j for use with the KG‐UI. In this case, the formatting match what is required by the ingestion scripts. The names of the assertion files must follow the naming convention described in Basic Protocol 3. Each node and edge file must contain only one node type or one edge type. Additionally, the fields in each assertion file must include, at a minimum, an “id” and “label” for nodes, and a “source”, “target”, and “relation” for edges.

schema.json

The schema used to build the UI takes many parameters that are described in Basic Protocol 6. The node and edge fields are the most important parameters needed to visualize the network. The name of each node and edge type, and the fields associated with each in schema.json, must match the names and fields used in the assertion files.

Standards and protocols for building KG databases

The KG‐UI requires unique IDs for nodes when ingesting a network into Neo4j. This enables the indexing of nodes for faster performance. One way of improving your data and ensuring it is FAIR (Wilkinson et al., 2016) is to comply with community standards and protocols. KG‐Hub is an initiative that seeks to address these issues by defining standards for building knowledge graphs with reusability in mind (Caufield et al., 2023).

Ontologies provide information about relationships between entities based on object shared physical characteristics. BioPortal is a valuable resource for hosting community developed ontologies across many knowledge domains (Vendetti et al., 2025). Additionally, the BioPortal site has a recommender that suggests ontologies that closely matches a term set queried by a user (Martínez‐Romero et al., 2017). Understanding the Results

Reproducibility and accuracy of the PI network demo

This demo network is intended to serve as an example and therefore may contain unintended mistakes, inaccuracies, and missing information. When developing co‐authorship networks, several caveats should be considered, for example, author name disambiguation and misattributed author affiliations. This demo network was not manually pruned to ensure that all links and nodes are accurate. The example network was created to demonstrate the utility and workflow of the protocol and KG‐UI resource for academic use.

Using the KG

Once the website is up and running, the KG can be used to investigate relationships between its entities. Depending on the needs of the application, various aspects of the network visualization can be altered, as described in Basic Protocol 6.
