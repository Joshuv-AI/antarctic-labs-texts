Semantic architectures for domain-specific programming AI agents: lessons from a JavaScript semantic assistant
Authors: Muhammad Ishaq, Muhammad Sarmad, Muhammad Asim, Korhan Cengiz, Nikola Ivković
Published: 2026

ABSTRACT
AbstractThis work proposes a semantic ontology-based dataset leveraging fine tuning large language model to facilitate JavaScript debugging and domain-specific code generation. Ontology is used to train the model with a dataset that has an exact or logical relationship between JavaScript syntax elements. The system gains deep subject knowledge with the help of a formal linked database, producing a high-quality QandA dataset from it, and employing parameter-efficient fine-tuning of a base LLM (LLaMA-3B). The fine-tuned model is assessed through a strict framework for domain competency. Code correctness, logical consistency, adaptability, and error detection efficiency metrics were used for evaluation. Experimental results show that the ontology-augmented model performs much better across all measures than baseline generic LLaMA model. Baseline here refers to a model refined on non-ontology data, and retrieval-based techniques. Logical verification and comparisons of fine-tuning techniques (BitFit, LoRA, and standard tuning) is provided. For performance contextualization, an additional benchmark against a cutting-edge code model (CodeLlama) is provided. The enhanced outcomes show that using ontologies to incorporate structured semantic knowledge can result in significant improvements in domain-specific code comprehension, providing a repeatable route for creating specialized programming AI systems. For reproducibility, the implementation and resources (ontology, SPARQL queries, code) are made publicly accessible.Keywords: Large language models (LLMs), Semantic ontologies, JavaScript coding assistant, Domain competence evaluationSubject terms: Engineering, Mathematics and computing

Introduction

Large language models (LLMs) may now perform exceptionally well on a variety of tasks thanks to recent developments in artificial intelligence (AI) and natural language processing (NLP). However, there are drawbacks when general LLMs are used to specialized fields like software engineering: outputs may be syntactically sound but semantically incorrect or out of step with best practices. Computer programming requires precision and contextual knowledge of the respective programming languages. Human programmers are unaware of the code they use. And they miss implementation circumstances. In professional coding contexts, pure LLM-based assistants are less reliable due to hallucinations, domain biases, and a lack of deep domain understanding.

In this work, these gaps were addressed by integrating explicit semantic knowledge into a programming assistant. Our goal is not to claim broad artificial general intelligence (AGI), but rather to create a domain-aware JavaScript coding assistant. Concretely, the aim to embed an understanding of JavaScript’s semantics and best practices into the model so that it can generate correct code, detect and fix errors, and adapt to novel tasks. This is achieved by developing a formal JavaScript ontology and using it to guide the LLM’s training and reasoning.

JavaScript Ontology Design: The build ontology of JavaScript comprehensively covers the concepts (syntax elements, control structures, object behaviors, error types, etc.), encoding explicit rules and relationships. The ontology contains 100–150 classes, 50–60 object properties, and 30 data properties, with several hundred axioms. The class hierarchy is normally three levels deep, e.g. AsyncFunction → Function → Executable. This structure is a fairly sophisticated event-driven design that relies on lexical closures and asynchronous functions. This gives rise to two ontological questions that are often discussed in the context of modern language design:

Should scope rules inside of nested functions be enforced?

Will every async function definitely return a Promise object?

These are the kinds of questions that show how ontology applies to real-world programming scenarios. The ontology was primarily built using tools such as Protégé. Normally you need recommendations from an LLM to add new relationships. All of this is double-checked by a reasoner to ensure it is consistent. The ontology is converted into natural language Q\andA pairs for fine-tuning for data generation. Such facts as subclass relations, property domains and ranges are systematically transformed into question templates. This is done by running SPARQL queries over OWL ontology. For example, a Variable class might answer the question “What is a variable in JavaScript?” with a simple text explanation that would be based on its definition. A true/false question is a constraint like "An AsyncFunction must return a Promise. The template can switch between “What is X?” and “Explain the concept of X” to make it sound more natural. There is at least one QandA generated for each class or property to ensure full coverage. In the end, the final dataset includes about 1,500 QandA pairs.This corpus is stored in JSON for consistency.

Fine-Tuning and Model Setup: We fine-tune a LLaMA-3B-Instruct model on the ontology-derived dataset using parameter-efficient tuning. In the primary experiments, BitFit is used (updating only bias terms, about 0.1% of ~ 3B parameters) for efficiency. For comparison, LoRA (low-rank adapters with rank 4) and standard full fine-tuning on the same data were applied. Train/validation/test split of 80/10/10 is used for the QandA data1. Hyperparameters include a learning rate of 1e−5, batch size 16, and 3–5 training epochs, chosen to balance convergence and overfitting. For reproducibility, the details are provided in "Methodology" section for the exact optimization settings and freezing schedule. In addition to the ontology-derived QAs, a generic fine-tuning baseline is considered: the same LLM is fine-tuned on a large set of JavaScript QandA examples (code snippets and explanations) unrelated to the ontology. Finally, the preparation of a retrieval-based baseline involves RAG (retrieval-augmented generation) using the ontology corpus. In the RAG setup, the index ontology have a QAs with a vector store and at inference retrieve top-k passages as context for the base LLM, without additional fine-tuning2.

Reasoning Verification Layer: After the model generates an answer or code, an optional step of reasoning is applied. The OWL reasoner (Pellet) is implemented to check the output against ontology constraints. For example, if the model omits a return statement from an AsyncFunction, the reasoner will flag a rule of violation. In practice, the model output is parsed (using automated scripts) into a semantic form, run through the reasoner, and if violations are found, the model is prompted to revise the answer. This reasoning as a layer is only used during inference mechanism. This is pre-training phase. The reasoner‑intervention is roughly 30% for all execution paths, and it is frequently resolving issues like faulty error handling and scope leakage. A comparative performance study is carried out for a better quantification of its contribution. Here an ablation study with reasoner and without reasoner.

To better assess the benchmarked, the chatbot is tested across a diverse suite of JavaScript challenges. Multiple evaluation metrics were used to capture both functional correctness and efficiency. The elements of the domain competency framework are:

Code Correctness: Percentage of created programs that pass all unit tests. Also, hand-written test suites (Jest) with a benchmark of around 100 coding activities (algorithms, API usage etc.) were used.

Logical Consistency: ratio of outputs that follow best practices and JavaScript semantics. This is measured via automated ontology checks (e.g., no illegal scope access) and manual review by two expert developers (average Cohen’s κ > 0.85).

Error Detection Efficiency: Debugging task F1-score. The model is asked to find and correct about fifty flawed code snippets. The ground-truth error labels are used to calculate precision and recall.

Adaptability: The degree to which new tasks outside of the training distribution are successfully completed. The percentage measurement of tasks that the model correctly completes on its first attempt using about thirty scenario-based challenges (new APIs, developing frameworks) were conducted.

The ontology-augmented model is compared with each of the previously mentioned baselines. We present 95% confidence intervals for all measurements, which are averaged across three random seeds. To determine whether improvements are significant,The statistical tests (paired t-tests) were conducted.

Findings and Interpretation: On every metric, our ontology-augmented model performs better than all baselines. For instance, the code precision rate increases to 92% ± 2% with BitFit fine-tuning, as opposed to 70% ± 3% for the raw LLaMA baseline, 80% ± 2% for the general fine-tuned model, 75% ± 3% for the RAG-only model, and approximately 78% for CodeLlama-7B. In comparison to 65% (raw) and less than 75% for other alternatives, the logical consistency is 87% ± 3%. Adaptability is 82% vs. 55%, and error detection F1 is 0.88 (baseline 0.60). Every pairwise improvement is statistically significant (p < 0.01). While full fine-tuning gives marginal benefits, LoRA fine-tuning uses slightly more parameters to obtain almost equivalent outcomes (e.g., 90% precision). Correctness and consistency are decreased by about 4 points when the reasoning stage in inference is disabled. These results show that domain competency is greatly improved by explicit ontology knowledge and reasoning. In qualitative terms, the model generates cleaner code (often with helpful comments) and catches subtle bugs that the baseline misses.

Reproducibility: All implementation details are documented. For complete transparency, the ontology (OWL file), SPARQL query scripts, fine-tuning code, and assessment suite will be made publicly available on GitHub and archived (e.g., Zenodo). Ten hours and about 2,000 QandA examples were used during training on a single 8-GPU computer. Only bias terms (~ 3 million parameters) were updated by the BitFit variation; LoRA adapters contributed ~ 8 million parameters (rank 4). The final optimized model weights are made available under an open license1.

This research in conclusion shows that ontology-driven fine-tuning produces a Java Script-specific coding aid. Considerable improvement in raw correctness, semantic robustness, and flexibility with respect to abstract intelligence scores. These ontology-driven programming bots improve similar knowledgeable assistants for more relevant programming languages with specialized tasks. Our approach is broadly applicable: by swapping in different ontologies, one could build similarly knowledgeable assistants for other programming languages or specialized tasks. The overstatements of AGI are removed, with clarified ontology details, introduced ablations and baselines, and added missing implementation specifics.

Related work

The integration of symbolic knowledge representations (ontologies/knowledge graphs) and large language models (LLMs) has become an active research area in computing and information science as it tackles two complementary problems: the fluent but sometimes unreliable knowledge generation of LLMs and the difficulties of symbolic knowledge structures in flexible natural-language reasoning. Researchers demonstrated different techniques for such a hybridization and retrieval-augmented generation (RAG). RAG that looks up structured knowledge at runtime. Pipelines that turn knowledge graphs into retrieval indexes3. The latest trend to inject structured knowledge to model weights is parameter-efficient fine-tuning. These strands have quickly converged in 2023–2025, creating new systems and evaluations in forums for computer science and information sciences that are of direct interest to ontology-driven domain specialists such as programming assistants.

One important branch of work involves improving LLMs at inference time by retrieving facts from structured repositories (vector stores, document corpora, or knowledge graphs). Early RAG systems were based on plain-text retrieval, but recent research suggests that embedding knowledge graph structure into retrieval improves factuality and enables multi-hop reasoning4. For example, Graph-RAG variants rely on the node/edge structure to select more relevant contexts for generation, improving grounded answers in specialized domains. These Graph-RAG and KG-RAG approaches demonstrate how relational structure can contribute to hallucination reduction and bias model outputs towards verifiable facts. Such systems are of particular interest to information systems researchers because they directly combine knowledge-engineering artifacts with production-grade generative models.

Closely related are “ontology-aware” RAG approaches, which explicitly embed ontological constraints into the retrieval and answer verification stages. Recent work on cybersecurity and education demonstrates that ontologies can serve as sources to retrieve supporting facts, and can also be used to validate or filter model outputs for safety and domain compliance, for example by rejecting answers that contradict ontology rules. These approaches demonstrate two useful trends for computational research: (1) ontologies help to improve precision when used as structured retrieval targets and (2) symbolic validators (reasoners) can be used post-hoc to improve the reliability of generated content. This line of inquiry casts ontologies as both retrieval targets and correctness constraints, a model that is directly applicable to programming domains that require strict syntactic/semantic guarantees.

A complementary strand focuses on efficient fine-tuning and adaptation of large models so that structured knowledge becomes, at least partially, internalized by the model weights5. Parameter-efficient fine-tuning (PEFT) methods, such as BitFit and LoRA, have become standard tools in applied computing research because of their competitive performance while drastically reducing training cost and storage needs. BitFit (bias parameters only) and LoRA (low-rank adapters) are popular for domain specialization, and were suggested repeatedly in recent system-level studies as practical ways to fine-tune LLMs to domain tasks without retraining the whole networks. Such PEFT techniques are particularly appealing to information science teams that face domain specificity and resource constraints.

In addition to retrieval or fine-tuning, researchers have studied how to jointly reason over ontologies and LLM outputs. Hybrid pipelines combine description-logic reasoners or graph reasoning modules to infer implicit facts or to check logical consistency, where these pipelines coupled with LLMs have shown gains in multi-hop reasoning and rule-compliance on specialized QA and domain extraction tasks. Interleaving symbolic reasoning and generation has shown promising results in recent ACL/NAACL/ISWC workshops and papers, showing that hybrid symbolic-neural systems can provide higher trustworthiness in critical domains.

In the active trends is the use of LLMs themselves to accelerate ontology engineering. Work in 2024–2025 shows that LLMs can assist in drafting OWL ontologies, suggest class/property candidates, and assist in mapping natural-language competency questions to formal axioms.This lowers the barrier of ontology construction and maintenance and is relevant for computing researchers who want up-to-date knowledge artifacts but cannot afford full manual ontology engineering workflows. However, studies emphasize the need for human validation and for coupling LLM outputs with formal verification tools to avoid injection of subtle inconsistencies into ontologies6.

Taken together, the recent computing and information-science literature suggests a practical taxonomy of methods to combine ontologies and LLMs: (a) Retrieve-then-generate (RAG/KG-RAG) where ontologies/graphs are retrieval targets; (b) Hybrid reasoning pipelines that run symbolic validation or inference alongside generation; and (c) PEFT-based specialization where models are fine-tuned with ontology-derived corpora so that domain rules are reflected in model behavior. The strongest systems in 2023–2025 use combinations of these patterns, for instance, PEFT to internalize common rules, and RAG + reasoners to handle long-tail or evolving knowledge7.

Gaps and opportunity. Despite these advances, three important gaps remain in the computing literature relevant to domain-specific programming assistants. First, many KG/RAG efforts focus on retrieval fidelity and single-turn QA rather than on program generation correctness and maintainability (e.g., unit-test pass rates, code complexity). Second, although PEFT methods have been widely studied in NLP tasks, their joint effect with symbolic ontologies (ontology-derived corpora + PEFT) on code quality and debugging ability is still underexplored. Third, tools for ontology generation reduce engineering burden, but also raise validation challenges, especially for dynamic languages like JavaScript with evolving idioms. These gaps point to an opportunity for a hybrid pipeline that (1) constructs a curated JavaScript ontology, (2) transforms the ontology into high-quality QA/code examples for PEFT fine-tuning (BitFit/LoRA style), and (3) utilizes ontology-based reasoning during inference to verify correctness, which together align with recent computing community priorities for trustworthy, verifiable AI systems.

Our approach distinguishes itself by uniting several of these threads into a cohesive architecture for a programming AI agent. Unlike prior works that often remain in simulation or focus on static knowledge tasks, The validation of our approach on dynamic coding exercises (with unit tests, debugging scenarios, etc.), demonstrating concrete improvements is carried out in an applied setting. Moreover, the concept of domain-specific IQ as a performance framework is introduced as a way to measure and drive the development of specialized AGI agents. By quantifying metrics like code correctness, logical consistency, error resolution ability, and adaptability, This work provides a structured lens to evaluate progress towards human-like intelligence in narrow domains.

Building on the computing- and information-science trends summarized above, our work implements the hybrid pattern that the literature recommends but rarely executes end-to-end for coding assistants: (1) a formal JavaScript ontology is created, (2) generate a large, ontology-derived QA/code corpus and use parameter-efficient fine-tuning to imbue the LLM with domain knowledge, and (3) use an ontology reasoner during evaluation/inference to enforce correctness constraints. This directly addresses identified shortcomings for enhancing code correctness, logical coherence, error detection, and adaptability. Thus, our work is firmly situated in recent CS/InfoSci work on trustworthy, knowledge-grounded generative systems.

Hybrid AI systems, which integrate symbolic knowledge (ontologies, knowledge graphs) and LLMs, have recently (2023–2025) gained momentum. Current approaches can be classified into two broad categories: augmentation with retrieval and integration with the model. Retrieval-augmented generation (RAG) methods retrieve relevant facts from a knowledge base at inference time2. Graph-RAG variants improve on this by exploiting knowledge graph structures for multi-hop reasoning3. By contrast, ontology-guided pipelines enhance consistency by validating or filtering LLM outputs with symbolic reasoners8. Our research corresponds with these tendencies, concentrating on the programming domain: the refinement of the model utilizing ontology-derived data (integrating knowledge into weights) and employing the ontology for validation.

Parameter-efficient fine-tuning methods like BitFit9 and LoRA10 have proven effective for domain specialization without retraining entire networks. Prior studies (e.g11.,) show such methods can adapt LLMs to new fields cheaply. However, few works integrate a formal ontology into this process. Some recent efforts use LLMs to help build ontologies, our concept invert this by using the ontology to shape the LLM.

In the software engineering context, most prior systems rely on large code models (e.g., Codex, CodeLlama12) or heuristics. To our knowledge, no prior work has evaluated an ontology-driven fine-tuning for code generation. Methodology

The proposed methodical strategy is to merge semantic ontologies with a transformer-based language model, aiming to elevate the model’s JavaScript programming capabilities. The development process was structured into multiple stages, each building on the previous: (1) constructing the JavaScript ontology, (2) generating a training dataset from the ontology, (3) implementing reasoning mechanisms and fine-tuning the model, and (4) evaluating performance against defined IQ-oriented criteria.overall workflow is shown in the Fig. 2.

Ontology development

The JavaScript ontology should include almost all language constructs, principles, and laws. Ontologies were created using the open Web Ontology Language (OWL) format with XML like Resource Description Framework (RDF). There are some well-known editing tools such as Protégé and programmatic handling via OWL API/RDFLib. The JS ontology covers essential programming constructs such as syntax elements (keywords, operators, control structures), function and object behaviors (scoping rules, closures, prototype inheritance), common error types (such as undefined variables and type mismatches), and suggested best practices. The ultimate goal is to structure JS programming data in linked format for logical utilization in training the AI algorithm. Linked or ontology is necessary for logical analysis.

Pisu et al.30 utilize a SciBERT model for ontology generation or research terminologies. This approach is the base model in our JS ontology development. In a similar way, the proposed transformer model automatically retrieve and build links between concepts through code and documentation scanning. Abolhasani and Pan22 OntoKGen process is to automate several aspects of ontology development. The ontology’s structure was visualized and verified using tools such as Protégé's OntoGraf, which ensured that classes (such as Loop, Function, and Event), attributes (such as hasParameter, throwsException), and constraints (cardinalities, types) accurately represented JavaScript semantics. The resulting ontology is a comprehensive knowledge graph of JavaScript, forming the backbone of our training data and reasoning engine. We constructed a JavaScript ontology in OWL/RDF capturing the core semantics of the language. It contains classes like Variable, Function, Promise, Closure, Loop, AsyncFunction, Event etc. There are about 130 classes in all. About 300 axioms (class hierarchies, domain/range restrictions, property cardinalities) are composed of about 55 object properties (hasParameter, returns, throwsException etc.) and 30 data properties (hasName, hasReturnType etc.). Average depth of class hierarchy was 3–4 levels (e.g. ForLoop → Loop → ControlStructure).

Examples: Asynchronous patterns are defined explicitly: AsyncFunction is a subclass of Function, and there is an axiom in this ontology that every AsyncFunction returns a Promise. Loop Control structures such as ForLoop, WhileLoop are Loop. The error types (UndefinedVariableError, TypeMismatchError) are associated with the time they can occur. In addition, the encoded scoping rules are included in the ontology. For example, a Closure usually has an implicit enclosesVariable relation indicating the lexical scope.

Relevant competency questions were “Does every AsyncFunction return a Promise?” This is merely to steer ontology content. The usual answer is Yes, it is encoded as a universal constraint. "Is there any possibility that a Function and its inner Closure to have the same variable name?" (This is a question for individual cases of Scope.)

What is the use of a ForLoop counter variable? Modeled with a type-constrained hasCounterVariable attribute.

"Get the types of errors associated with built-in operations?" (ThrowsException was used to relate classes and operations to errors. These queries make sure to include important components.

The ontology is developed in Protégé from key language references. The relevant API of the GPT-4 is used for enhance coverage. In this ontology additional relations between classes (e.g. between specific array methods and exceptions) are proposed. Any AI-suggested additions will be reviewed by a JavaScript expert. The Pellet reasoner imposes the consistency check. Classification is regularly performed to catch unsatisfied classes or any unintended inference. It usually corrects modelling errors on the fly.

The ontology formalizes explicit rules (scoping, type hierarchies), and common pitfalls. The ontology thus acts as a structured knowledge base for the model. For example, modeling scoping rules helped the assistant avoid undefined-variable bugs and increase logical consistency.Similarly, the addition of error patterns into the ontology increased the error detection capabilities of the model, as later observed in the evaluation (the model learned from the ontology that specific code patterns are erroneous).

Generating dataset from the ontology

The ontological knowledge is transformed into a large set of natural language question–answer (QA) pairs to train the language model effectively. Each QA pair is designed to express a specific fact or rule from the ontology, and hence to teach the model about JavaScript in a contextualized manner. For instance, if there is an ontology class Variable, the generated question would be “What is a Variable in JavaScript?” and the answer would be based on the description of that class (e.g., “It is a storage entity which holds data, and has a name and a data type”). We take inspiration from the idea of knowledge-based data augmentation proposed by Agarwal et al.31 who showed that synthetic corpora constructed from knowledge graphs improve the factual grounding of LLMs.

The written SPARQL queries systematically extract information from the OWL/RDF ontology. These queries pulled out class hierarchies, property domains and ranges, and constraint definitions. One query, for example, produced information such as "A ForLoop is a type of Loop, which is a ControlStructure" by retrieving all subclass relations. "The hasParameter property connects a Function to a Variable" is one example of an object property that links classes, according to another query. Every recovered fact was methodically converted into a simple QandA format. To ensure uniformity, standard template phrasing is used to maintain these pairs clear and consistent. For example, concept X brief explanation could be addressed in answer to the question "What is the meaning does X in JavaScript?" Similarly, OWL restrictions of cardinality or return types can be specified as descriptive or yes/no type questions. For example whether syncFunction return a Promise? The Correct answer: Will be "Yes, every AsyncFunction returns a Promise by definition".

During this dataset construction, several challenges were encountered:

SPARQL syntax and query issues

At first the SPARQL queries may fail due to code bugs or non-alignment with the ontology structure. It results in missing or incorrect data. The continuous refinement of queries and cross-validation results against the ontology’s expected retrieved contents. The goal of refinement is to ensure that all relevant triples were collected.

Natural language formulation

Triple subject, object and predicate and its conversion to usual question and answer pair for a more facilitated and refined dataset. There are usually modest modifications to questions to overcome templating and improve correctness. The statement "What is X?" is switched with "Explain the concept of X. This allowed the model for more improved or broad learning. It will also reduce overfitting a single pattern.

Coverage and diversity

The ontology includes classes, individuals, data, and object properties. So full coverage of the structure and characteristics is important. Each triple connection is converted into at least one QandA pair. Programming language code or pseudocode samples help to understand ground abstract concepts in practical reality.

Data quality and consistency

Some ontology entries lack technical definitions and may limit the model’s performance with repeated use. Careful examination and modification of such entries for clarity and supplemented with external resources like JS definitions. The finished dataset was saved in a structured JSON format. The whole JSON structure has items that include a question and an answer. The model can learn real work relationships among the terms. This JSON format was validated to handle special characters and nested content correctly.

The developed ontology consists of thousands of QA pairings using ontology-driven QandA creation. The terminology or corpus is domain specific. It means that all terms are only focused on JavaScript knowledge and problem-solving ability. It consists on formal semantics, making it a unique fine-tuning resource when compared to other general corpus.

Reasoning and model fine-tuning implementation

A unique and different feature of the proposed architecture is the utilization of a reasoning layer that uses ontology linked nodes as a reasoning engine alongside the LLM. The descriptor logic reasoners like Pellet and HermiT are optimal or prime choices. This is particularly used to ensure logical consistency and allow an improved inference over the ontology. These reasoners can extract implicit facts such as a variable’s with type restrictions. It can be used to validate the bot’s code suggestions against ontology rules. For example the generation of an asynchronous function that returns a Promise. This hybrid approach is inspired by Qureshi and Faber25 et.al the OWL2QL meta-reasoning and Liu et al.26 Ontology-Guided Reverse Thinking (ORT) methods. Both techniques prove that the combined symbolic reasoning along with LLMs improves formal rule adherence and multi-hop reasoning precision.

Our proposed system can query ontology in the training stage for inference. In one case the alteration of generated code can utilize the reasoner to find out the variation and constraints. How to call a method on an undefined variable or using an outdated API that is not a part of the ontology. If this happens then it is a discovered violation during training. The output is considered as a negative example with respect to other learning models.

Model fine-tuning

The fine-tunning of the pretrained LLaMA-3B Instruct model (a 3-billion-parameter variation) is exactly in accordance with our curated dataset and methodologies based on recent research. The following tactics were used to improve the model’s performance while keeping efficiency in mind.

Pre-training augmentation

Agarwal et al. (2021) also proposed the pre-training augmentation. Synthetic QA as proposed in our contribution expanded the model’s knowledge by incorporating pairings from the ontology prior to fine-tuning code tasks. This guaranteed that the model had a solid foundation in JavaScript principles, similar to giving it an organized mini-education in the field.

Contrastive learning

The secondary training objective is introduced where the model learns to distinguish between correct and incorrect outputs. In particular, it generates an answer pair for some questions: a correct answer (ontology-based) and a subtly incorrect answer (plausible-sounding but incorrect). The model was trained to rank the correct answer higher than the others. This trains the bot to avoid common mistakes and hallucinations by reinforcing what not to do, as advocated by prior research on improving LLM factual accuracy.

Multi-task learning

The training formulated involves multiple task types: code generation, explanation, debugging etc. instead of simple QandA. For example, some training prompts asked the model to generate a code snippet from a description (testing code generation), some presented a piece of code with an error and asked for a fix (testing debugging), and some were conceptual questions from the ontology (testing explanatory capability). As a result, the model learned to balance these skills. For the multi-task fine-tuning, we used the BitFit approach that updates only the bias terms for efficiency and regularization. This sparse fine-tuning was necessary due to resource constraints, as it dramatically reduced the number of parameters that were updated while still allowing for performance improvements.

Incremental freezing

The frozen transformer layers and the only fine-tuned final layers added adapters for domain-specific terms in early epochs32. The training continued, and as the model became more stable with the new information, it slowly unfroze more layers. The stepwise unfreezing bypasses catastrophic forgetting of the model’s core linguistic abilities while integrating new information.

Fine-tuning was performed with the HuggingFace Transformers library. QA dataset is converted into code samples in a single format (conversational prompt-response model). As an example, a training instance may look like:

Accuracy

Accuracy is defined as the degree to which a value that has been determined in advance corresponds to a measurement that has been carried out experimentally. The phrase “accurate” is used to refer to anything that is either extremely close to its actual value or to a standard that is generally recognized by the majority of people. For example, a computer has the ability to carry out accurate mathematical calculations that are suitable for the information that has been provided, but which do not match the exact value. These calculations are appropriate for the information that has been provided.

Precision and recall

The effectiveness of an information retrieval system (e.g., one that returns code for a given query) is usually measured using two metrics used in tandem: precision and recall.

We define precision as the number of relevant items (e.g., correctly generated or retrieved code snippets) divided by the number of items retrieved or generated by the system. In other words, precision answers the question: “Of all the results returned by the system, how many were actually useful?”.

Recall, also called “sensitivity”, is the proportion of relevant items successfully retrieved or generated out of all items that were truly relevant in the whole set. Recall answers the question: “Out of all the correct answers that were there, how many did the system actually manage to return?

Discussion

Integrating semantic ontology with a large language model that is capable of more smart programming has been proved more efficient through experiments. The bot trained through link databases shows improved performance over other baseline models. These improvements are in code precision, logical reasoning, debugging, adaptability, and domain-specific intelligent quotient. These results indicate more improved implications and considerations.

First, its high ratio of code correctness (92%) clearly shows that the bot can deliver solutions for a wide variety of programming tasks. Developer work is now easy, and they can avoid manual fixing and extensive testing. Their level of dependability is really encouraging in cases of AI-generated code. Finally, the high consistency of nearly 87% with coherence of logic means that the programming bot aligns with enhanced semantics and industry requirements. The goal is to produce good code that is more problem oriented. LLM is used in our effort to write code that is both syntactically and semantically correct. The improved error detection with (F1 0.88) also indicates it is strong in debugging. So, it can be used for maintenance and revision of code. Adaptability of the developed bot exceeds almost the threshold of 82% on novel tasks. The bot demonstrates continuous learning capability. The bot can successfully handle new emerging challenges and maintain its best performance. Such capabilities improve overall bot intelligence.

There are some potential hurdles in the translation of the developed ontology into a JSON QA dataset. Consistent struggle overcomes all potential issues. The encountered issues include inaccurate SPARQL queries35. There are some inconsistencies in the queries between the ontology and real-world usage that had to be ironed out. Proper and careful attention required with manual intervention to ensure top-notch training data. Development of ontologies and then the construction of required dataset requires domain expertise and iterative refinement. This is an extensive effort in the creation of linked datasets or structured knowledge graphs. It may extend the benefits of model performance.

The tokenization issue is the main technical challenge faced during JSON dataset formatting for training. It require adjustment to encoding and padding. The model also encounters occasional gradient explosion during adaptation to new data. It is the mitigation of gradient clipping and lowering the learning rate. Structured or properly linked datasets stress the current fine-tunning pipelines. Future research motivation is to explore improved neural networks training techniques for highly structured knowledge graph like datasets.

Comparative analysis of the refined model with the base LLaMA 3B further raises the value and the importance of our enhancements. The lack of specialized reasoning in the base model overshadows its strength as a general language model. From results and comparative studies, it is now clear that ontology datasets, fine tuning with reasoning, is effective in strategy. There are a series of activities or changes in this technique and its impact is upto the mark. Only fine tuning is not enough. Using ontology-based datasets without needful fine tuning gives poor results. So combine modifications to model and datasets give positive results. The ontology-based structured dataset is ingrained in the model through training. The model knows the exact logical relationship among ontology components or classes and even properties.

The proposed methodology is also scalable. This semantic enabled generative kind of intelligent bot can be used in any application domain through formal or semi-formal ontologies. There are healthcare and biomedical rich expert SNOMED CT and CRAFT ontologies. These linked databases can be used in specialized AI agents. Respective decision support systems in any respective domain can be improved through semantic or IQ-enabled bots. It helps us with diagnosis and response assistance because domain knowledge combines with the linguistic fluency of LLMs. Utilization of selective agri ontologies improve the performance of relevant AI agent Ishaq et al.36.

There are some potential limitations and hurdles in the development of ontologies. It is time-consuming and requires maintenance. In the development of JavaScript ontology processes, it is complex to capture all emerging patterns in the JavaScript. The JavaScript ontology can be extended to include the types of TypeScript. There is potential computational overhead using reasoning engines. The existing Pellet cannot be utilized for large ontologies. Ontology updating and creation through automated AI enabled systems is another feature research area. More efficient graph technologies can be utilized for automated ontology development.

Another consideration is how this approach intersects with the broader goal of AGI. The bot demonstrated a partial intelligence: a specialized agent with human-like competency in a narrow field. This seems a viable path forward ,one can imagine a collection of such agents, each an expert in a domain, collectively forming a more general intelligence. It somewhat mirrors how human society accumulates intelligence: individual experts in various fields whose knowledge can be combined. Our work advances human-like intelligence in machines by embedding explicit semantic rules into the black-box world of neural networks, making their behavior more interpretable and controllable. A fascinating observation is that our bot, in many ways, reasoned during problem-solving, which is not typical for end-to-end neural models. This hints that ontologies and symbolic knowledge might be one key to unlocking reasoning in AI, a necessary ingredient for true intelligence as argued by many cognitive scientists.

In summary, the discussion reinforces that the proposed semantic architecture is not only effective for the task at hand but also provides a blueprint for scaling AI to be more knowledgeable, reliable, and intelligent. The positive results are a step toward bridging the gap between narrow AI performance and the adaptable, reasoned problem-solving characteristic of human intelligence. At the same time, careful consideration of the effort and complexity introduced by semantic integration is mandatory. It is necessary to continue the refinement of these methods to make them more automated and efficient.

Conclusion and future work

In this work, the successfully developed and evaluated specialized JavaScript programming bot combines a semantic ontology with the LLaMA 3B-Instruct LLM, achieving notable strides toward partial intelligence capabilities in the programming domain. The bot demonstrated exceptional performance in generating accurate JavaScript code, maintaining logical consistency, identifying and fixing errors, and adapting to new challenges ,meeting or surpassing the target benchmarks. It is initially set to 92% code correctness vs. 90% goal, 0.88 F1 in error detection vs. 0.85 goal, etc. These improvements address several limitations of plain LLMs, such as hallucinations and shallow understanding, by integrating structured domain knowledge directly into the model’s training process.

Our methodology encompassed the end-to-end pipeline of ontology development, dataset generation, model fine-tuning, and thorough evaluation. Throughout this process, a number of challenges were tackled: from technical issues like SPARQL query syntax errors and JSON formatting nuances to engineering hurdles like model tokenization quirks, limited computational resources, and risks of overfitting. Each obstacle was met with targeted solutions, refining queries, adjusting tokenization, employing techniques like gradient clipping and careful scheduling of learning rates, ensuring the robustness of our experimental pipeline. Overcoming these challenges not only validated our approach but also yielded valuable insights into best practices for knowledge-infused AI development. For example, one insight is that maintaining a balanced training regimen (mixing strict knowledge QA with creative coding tasks) is crucial to preserve the model’s versatility while injecting knowledge.

Comparative analysis with the baseline LLaMA model underscored the transformative impact of our semantic enhancements. The fine-tuned bot consistently and significantly outperformed the base model across all measures, highlighting how ontology-driven reasoning and domain-specific fine-tuning elevate the model’s capabilities. This serves as a proof-of-concept that large language models, when guided by explicit knowledge frameworks, can be steered closer to human-like intelligence in specialized tasks. It is in essence, present a scalable framework to build domain-specific intelligent agents: one that can be adapted to other fields by following a similar recipe (domain ontology + curated dataset + fine-tuning + reasoning integration).

The bot’s reliability and skillset position it as a practical tool for real-world JavaScript development. For instance, it could be integrated into an IDE to provide on-demand code generation and debugging suggestions, potentially increasing developer productivity and reducing errors. Perhaps more intriguingly, the generalizability of our approach means that similar bots could be developed in fields like data science (an AI data analyst), finance (an AI financial advisor using financial ontologies), or biomedicine (an AI researcher using medical ontologies). Such specialized systems offer a path forward in the quest for human-like AI: rather than aiming for a monolithic intelligence, cultivating a forest of expert agents that collectively cover broad intelligence.

This study contributes to the broader AI community by demonstrating a concrete step toward bridging symbolic and neural AI. By showing that an ontology (a symbolic artifact) can significantly improve an LLM’s performance and reasoning, this concept reinforced that hybrid systems might be key in achieving true general intelligence. The success here suggests that neither pure deep learning nor pure symbolic AI is sufficient alone; it’s their combination that unleashes new potential.

Looking ahead, there are several avenues for future work:

Expanding ontology scope

One immediate next step is to extend the ontology to cover more aspects of programming or even multiple programming languages. A cross-domain ontology that links concepts across languages (JavaScript, Python, etc.) could lead to a more versatile coding assistant and test the limits of the bot’s transfer learning abilities.

Improving computational efficiency

While our fine-tuning process was relatively lightweight (thanks to BitFit and similar methods), scaling to larger models or more complex ontologies could be challenging. Future research might explore model compression, quantization, or more efficient fine-tuning techniques like LoRA (Low-Rank Adaptation) to keep deployment feasible. The goal would be to allow even resource-constrained users to benefit from such specialized bots.

Automating ontology generation

Creating and maintaining the ontology by hand is a bottleneck. Techniques to automatically generate or update ontologies from documentation or code repositories (perhaps using an AI itself to read and structure knowledge) would be hugely beneficial. Our work could be combined with systems like OntoKGen or other ontology learning algorithms to bootstrap new domains.

Real-world deployment and feedback

Deploying the bot in actual development environments would provide insights into its performance under unpredictable conditions and with human users in the loop. By collecting feedback and usage data (which errors are commonly caught, what suggestions are accepted, etc.), identification of gaps in the ontology or model iteratively improve the system. This would also test the bot’s integration into tools like VS Code or web-based editors.

Cross-domain applications

The goal is to access the performance of the bot in domains beyond programming, as mentioned. Early ideas include an AI assistant for agriculture using an ontology of crops and farming practices (aligning with the mission of the Sarhad Journal of Agriculture), or an AI in education that uses an ontology of pedagogical strategies to personalize learning. These would challenge the approach in new ways and potentially benefit those sectors with smart, knowledgeable AI tools.

Advanced learning and overcoming overfitting

To continually improve the bot’s adaptability, advanced techniques like meta-learning or continuous learning could be introduced. For example, allowing the bot to learn from new examples on the fly (perhaps through user corrections) without forgetting its core knowledge. Ensuring it doesn’t overfit to the ontology (so that it can still think outside the box when needed) might involve introducing adversarial training where the model is sometimes pushed to consider alternatives outside the ontology’s prescriptions.

Optimizing reasoners

Scaling to bigger ontologies also requires an optimized reasoning component. Future versions might use a mix of heavy and light reasoning ,e.g., a quick, approximate reasoning for real-time checks and a deeper reasoning for validation passes. Research into neural-symbolic reasoners that can partially learn the ontology constraints could also offer speed benefits.

In conclusion, our research shows that semantic architectures hold great promise for advancing AI towards greater intelligence and utility. By injecting structured human knowledge into LLMs, it can create agents that not only generate content but do so with understanding and purpose. The develop JavaScript programming bot is a tangible example of this, achieving a level of domain expertise and reasoning that would have been difficult with LLM technology alone. This work thus marks a significant step toward the broader vision of machines that can think and reason more like humans, within and eventually across domains. It is inferred that continuing to blend symbolic knowledge with learning-based models is a fruitful path toward true intelligence, and this study inspires further exploration in that direction.
