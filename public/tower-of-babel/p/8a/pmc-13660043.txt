Background

The advent of affordable whole-genome assembly has facilitated the creation of haplotype-resolved pangenomes, broadly defined as a collection of genomes, to mitigate reference bias [1] that the single reference genome poses in genome analyses. Consequently, this technological advancement is driving the development of precise methodologies tailored to handle the intricate sequence and variation profiles found within extensive sets of related genomes [2]. These methodologies frequently leverage graphical representations of pangenomes to bolster algorithms for tasks such as sequence alignment and visualization, and more accurate downstream analyses such as functional genomics and association studies [3]. By harnessing the additional insights afforded by pangenomes, these approaches demonstrate enhanced efficacy across a spectrum of bioinformatics endeavors, including read alignment, variant calling, and genotyping [4]. For highly mutating genomes (e.g., viral and bacterial genomes), the pangenome graphs have been playing a pivotal role in capturing genetic diversity for further analyses (e.g., antibacterial resistance, virulence [5]) [6, 7]. In recent years, the human pangenome projects also gained momentum with the release of the first draft of the human pangenome reference represented as a sequence graph [8]. While the potential of pangenome graphs to supplant linear reference genomes remains uncertain, their capacity to seamlessly reconcile multiple sequences and coordinate systems ensures their utility regardless of prevailing pangenomic models in the future.

Using graphs to represent data visually enables the exploration of important insights and the recognition of key advantageous patterns for users. Visualization facilitates this analysis by emphasizing the patterns, connections, and trends, thereby enhancing the comprehension [9].

Several tools have been developed to analyze pangenomes via graphs using interactive or static visualizations. ODGI [10] can create 1D and 2D static images while primarily focusing on editing pangenome graphs rather than visual analysis. Bandage [11, 12] provides interactive operations, including navigation and node labeling, and supports BLAST searches on the graph. GfaViz [13], on the other hand, enables querying by segment ID as well as navigation, but it is limited to Linux or macOS operating systems. MoMI–G [14] can display read alignments and structural variations in genome graphs, but it does not support genomes longer than the human genome. SequenceTubeMaps [15] demonstrates vg-generated [16] graphs as tube maps; thus, the long jumps between the vertices on the graphs are difficult to conceptualize visually. VRPG [17] is a web-based interactive framework for visualizing and annotating pangenome graphs using a reference-based coordinate system with features like highlighting directed assembly paths and listing copy number variations of genomic segments. PanGraphViewer [18] is available as both a desktop application and a web-based one, offering coordinate-based subgraph visualizations rather than whole-genome visualizations. Assembly Graph Browser (AGB) [19] addresses Bandage’s limitations in navigating large and complex graphs, but lacks the level of detail available on the nodes.

In summary, existing tools fall short in several critical areas: they lack specialized layout algorithms, effective sequence-highlighting mechanisms, and mature interactive capabilities. Moreover, they do not provide scalable methods for managing or querying large pangenome graphs, including the ability to selectively focus on specific genomic segments through server-side database access. Finally, most existing solutions either involve cumbersome installation procedures or offer web-based deployments with significantly constrained functionality.

To fill this void, we have developed certain custom layout and query algorithms for pangenome graphs. Then, we designed and implemented a free, open-source, web-based tool named PG2 (PanGenoGrapher) dedicated to interactive visual analysis of sequence graphs. PG2 supports both variation graphs and de Bruijn graphs in the commonly adopted GFA format [20].

Methods

We refer the reader to [21] for the basics of graph theory.

Graph model

In pangenome graphs, each sequence segment is represented by a single node. Meanwhile, edges connect segments, as defined in the popular GFA format, via links, jumps, or containments, where the overlaps are specified with a CIGAR string [22]. This graph model is not only assumed by our algorithms but can also be utilized within the viewer and the backend graph database, seamlessly integrated with a pangenome graph visualization component. Upon loading a large GFA file into a software tool, the associated pangenome graph data could be imported into the database for subsequent use. Users can then explore their regions of interest within the viewer, facilitated by a comprehensive range of graph-based querying options.

Querying pangenome graph databases

Given a graph database that stores pangenomes modeled as described above, a variety of graph-traversal-based queries can be used to initiate and extend downstream analyses. These queries that PG2 provides can be broadly grouped into the following categories:

SQL-like attribute queries retrieve segments or links that satisfy specified constraints. Example: identify all segments whose sequences are shorter than 100 bases and terminate with “AT”.

Queries in the first category can be implemented directly in any standard graph database. For the latter two categories, we adapted a set of specialized graph-traversal queries, as outlined below.

Customized layout

Automated arrangement plays a pivotal role in ensuring a clear presentation of relational data, as a subpar layout can result in user perplexity [9]. There are many different strategies for automatic graph layout. One such popular approach is the force-directed layout approach [25], where the nodes with initial random placement continuously move according to a system of forces based on physical metaphors related to systems of springs or molecular mechanics. fCoSE [26] is an example of such a layout algorithm where certain placement constraints may be enforced on specified nodes.

To emphasize the ordering of segments in pangenome graphs, we designed a customized layout algorithm based on fCoSE, where the main goal is that end segments (zero in- or out-degree ones) are constrained to the left or right side of the drawing, respectively, maintaining a left-to-right directional flow. We determine how much to the left or right an end node should be constrained by calculating the distances of such nodes to the opposite side end nodes and introducing dummy nodes accordingly.

PG2 architecture

The tool PG2, which implements the above custom methods along with other generic ones used in graph-based analysis, was designed to have a web-based front end with advanced visualization capabilities and a backend that maintains the pangenome graphs in a graph database. This enables a relatively lightweight client-side, where only the current focus window (i.e., subgraph) is presented to the user through advanced graph-based querying to the database and simple SQL-like queries. Figure 3 shows the high-level architecture of PG2.

High-level architecture of PG2

To build a front-end visualization component for PG2, we chose to use a graph visualization development toolkit named Visuall [27], which is based on the popular graph rendering library Cytoscape.js [28]. PG2 inherits many state-of-the-art visual analysis components from Visuall, including facilities for inspection of graph objects, the highlight of paths and walks, context menus to display up or downstream of a particular node, automatic graph layout, advanced querying options to the database to narrow the focus and complexity management operations to reduce the complexity of the graph current in view.

Starting with an empty canvas and querying the database to obtain an initial, partial subsequence of interest, being able to gradually expand this partial subsequence in the desired direction is very important since displaying the entire pangenome graph upfront usually results in “hairball” layouts. Additional operations for complexity management help the user change their focus to a part of the graph in the canvas as well.

Query and rendering performance

We evaluated the interactive use of PG2 with a browser-side benchmark suite implemented in our sample web application. This benchmark complements the database import benchmark: import time describes preprocessing throughput, whereas the web benchmark describes the cost of retrieving and rendering the query results that are presented to a user during exploration. The benchmark suite executes a set of representative query workloads against an already imported Neo4j database and records one row per run.

The workloads cover three interaction classes.

First, baseline Cypher workloads measure direct database access through summary, high-degree segment, edge-sample, and local-neighborhood queries.

Third, custom search workloads exercise segment-name search, sequence-substring search, and sequence-chain search. The workloads that return graph data are passed through the same Cytoscape.js loading and layout path used by the interface; the summary and high-degree table queries measure query retrieval only.

Third, custom search workloads exercise segment-name search, sequence-substring search, and sequence-chain search. The workloads that return graph data are passed through the same Cytoscape.js loading and layout path used by the interface; the summary and high-degree table queries measure query retrieval only.

Rendering is evaluated on bounded query results rather than by attempting to draw the full pangenome graph at once. This reflects the intended use of PG2: the database stores the complete graph, while the web interface supports interactive inspection of query-selected subgraphs. The benchmark, therefore, varies the size or reach of subgraph-producing workloads through edge limits, neighborhood radii, procedure page sizes, and custom-search parameters. For the default configuration, edge-sample result limits are 150, 500, 1000, and 2500 edges, and neighborhood radii are 2, 4, and 6.

The benchmark uses one warm-up run and five measured runs per case by default. Warm-up rows are excluded from reported statistics. For seed-dependent workloads, PG2 accepts explicit segment names or automatically chooses high-degree segment nodes.

The graph-of-interest and common-stream workloads can optionally draw seeds from a local procedure seed pool around candidate anchors; this avoids relying only on independently selected high-degree nodes. For each run, PG2 records browser-observed query time, optional table-to-graph conversion time, Cytoscape.js graph-loading time, layout scheduling time, layout execution time, total elapsed time, result cardinalities, serialized response size, and browser heap usage when the browser exposes this metric.

Intended usage and workflow

Loading and inspecting graphs

PG2 can display the contents of pangenome graphs in a graphic-rich format (Fig. 5), specified via a GFA file. Even though entire pangenome graphs may be displayed simultaneously with anticipated performance degradation, PG2 was designed to display and inspect parts of the file content (segments of interest) through queries. These parts may later be expanded or reduced through complexity management operations interactively. The user may hover or select a graph object to inspect its properties (e.g., sequence of a segment node). Combined sequences may be displayed through tooltips of edges using a color-coding that eases comprehension of overlaps. PG2 also supports walk and path lines as described in GFA files.

Starting your analysis

The user may initiate their analysis with either an SQL-like query or a custom query that identifies segments by name or sequence. For example, in the sample “Human HLA-A Pangenome” graph (HLA-A subgraph extracted using the scripts provided by [29] from the HPRC graphs [30]), one can retrieve nodes whose segments are shorter than 100 bases and terminate with the substring “AT,” as illustrated in Fig. 7. The results are automatically laid out to enhance visual clarity.

An example SQL-like query to find the nodes whose segments include fewer than 100 bases and end with “AT”

Expanding or reducing segments of interest

Users may access up/downstream of a segment through context menus or visual cues. Figure 8 shows a 3-level neighborhood of the segments of interest from Fig. 7. If a user is overwhelmed with current contents, they may hide manually selected parts of the current graph or up/downstream of a specific segment.

Accessing your graph of interest

Once the analysis has been seeded using one of the previously described approaches, it can be enriched by adding connecting edges or by incorporating a specified neighborhood around the queried segments. For instance, performing a graph-of-interest query on the three segments from Fig. 7 links these segments with minimal paths as shown in Fig. 9.

In addition, the user may supply a sequence chain (e.g., seed chain) and enumerate all maximal paths that align with this sequence as described earlier (see Fig. 10 for an example).

BLAST support

PG2 facilitates BLAST searches both in standalone mode and through its web service. With the former, users can perform sequence similarity searches by creating a local database and manually entering sequences or extracting them from selected segments in the displayed pangenome graph. The results may be shown as a table or visual highlights can be added to sources on the graph. Conversely, the BLAST Web service provides a means to access these BLAST functionalities remotely, eliminating the need for software installation and maintenance. It allows users to submit sequences, set search parameters, and receive results, which are manageable through the interface that tracks the query’s status and retrieves results when ready.

Once a BLAST search is performed, each segment node that yields a match is annotated with a badge indicating the degree of similarity, represented by a value in the range ([0,1]) (see Fig. 5 for an example).

Limitations and future work

PG2 currently lacks support for parsing structural variations (SVs) and handling gene-specific information. In addition, the software does not currently support sequence-to-graph mapping.

We aim to integrate support for GAM/GAF file inputs in future iterations. This integration is intended to extend the current simple polymorphism marking feature to accommodate structural variations. Furthermore, if genes are represented as paths within those GAM/GAF files, we hope to enable gene annotation and highlighting capabilities.

In addition, we plan to explore adding full sequence-to-graph mapping capabilities. Since PG2 can already identify simple chains of sequence matches, leveraging this foundation to develop a more robust mapping feature is a key objective on our development roadmap.
