A unified framework for efficient test case generation and prioritization driven by multiple coverage criteria
Authors: Xinyue Xu, Xiangxian Chen, Zhonghao Guo
Published: 2026

ABSTRACT
Software testing is fundamental to system reliability and remains resource-intensive. Traditional frameworks often treat test case generation and prioritization as disconnected phases, neglecting the rich coverage metadata produced during generation and necessitating costly pre-execution. To bridge this gap, we present an integrated framework that enables profiling-free prioritization by reusing generation-time coverage metadata, with the objective of enabling earlier accumulation of multi-criteria structural coverage during test execution, and empirically facilitating earlier fault exposure. The proposed framework features Multiple Coverage Test Case Generation (MCTCG), an enhanced symbolic execution tool engineered to generate test suites satisfying six diverse coverage criteria while simultaneously capturing granular coverage data. Leveraging this intrinsic data, \documentclass[12pt]{minimal} \usepackage{amsmath} \usepackage{wasysym} \usepackage{amsfonts} \usepackage{amssymb} \usepackage{amsbsy} \usepackage{mathrsfs} \usepackage{upgreek} \setlength{\oddsidemargin}{-69pt} \begin{document}$$TCP_{all-first}$$\end{document} performs greedy multi criteria coverage prioritization by maximizing marginal structural coverage in the execution prefix, without requiring re-execution. Experimental results on CodeNet and RERS benchmarks demonstrate that MCTCG achieves superior coverage and bug detection rates compared to baseline tools. Furthermore, \documentclass[12pt]{minimal} \usepackage{amsmath} \usepackage{wasysym} \usepackage{amsfonts} \usepackage{amssymb} \usepackage{amsbsy} \usepackage{mathrsfs} \usepackage{upgreek} \setlength{\oddsidemargin}{-69pt} \begin{document}$$TCP_{all-first}$$\end{document} significantly outperforms state-of-the-art prioritization methods, improving the Average Percentage of Faults Detected (APFD) by 4.11% and reducing the first-fail metric by 8.7%. This work effectively enhances testing efficiency by seamlessly unifying the generation and prioritization processes, making it particularly valuable for standard-compliant white-box testing.

Introduction

Software defects impose a substantial economic burden on the engineering industry. Industry estimates suggest that poor software quality cost the U.S. economy approximately $2.41 trillion in 2022 (CISQ)1. Given that manual testing is labor-intensive and has historically accounted for up to 50% of development costs2, Automated Test Case Generation (ATCG) has emerged as a vital solution. Techniques like symbolic execution effectively utilize constraint solvers to explore program paths. However, as software complexity grows, testing efficiency depends not only on generating inputs but critically on the diversity of coverage criteria and the execution order of the generated test cases3,4.

In the pursuit of high structural coverage for white-box testing, various automated paradigms have been employed5,6. While approaches like fuzz testing7 excel at finding crashes and model-based testing8 verifies system logic, symbolic execution has emerged as the preferred technique for standard-compliant testing due to its unique ability to systematically explore program paths and precisely target specific code elements. Prominent tools like KLEE9, Driller10, and SymQEMU11 define the state-of-the-art; however, they generally suffer from a significant limitation: they are primarily designed to satisfy single coverage metrics rather than multiple coverage criteria. Research confirms that higher structural coverage is often associated with stronger fault-detection effectiveness, and that diverse criteria (e.g., MC/DC vs. Branch) complement each other in revealing distinct defect types12. Existing tools fail to leverage this complementarity, underscoring the need for an enhanced generation approach that effectively satisfies multiple rigorous standards simultaneously.

To further accelerate fault detection and improve software quality, Test Case Prioritization (TCP) is widely adopted to expose faults earlier during test execution13. While techniques exist based on bug prediction or execution cost, coverage-based TCP remains the dominant approach used to prioritize cases based on elements like statements or branches14–16. Although recent advancements have introduced strategies like code combination coverage or diversity-aware prioritization to further enhance bug-finding capabilities, a fundamental inefficiency persists: these frameworks predominantly treat generation and prioritization as disconnected phases17,25. Conventional algorithms rely on coverage information obtained from test case execution results, creating an “execution bottleneck” where test cases must be executed solely to gather data for prioritization. This disconnection neglects the rich internal states available during generation, leading to significant resource redundancy and ultimately delaying the actual fault discovery process.

Consequently, there is a compelling need for a unified mechanism that can extract prioritization data during the generation phase, thereby eliminating the overhead of post-generation execution while still supporting prioritization for earlier fault exposure. Directly addressing this need, this study presents an integrated framework combines test case generation and prioritization. The proposed solution is built upon MCTCG, an enhanced symbolic execution tool designed to generate test suites satisfying six diverse coverage criteria (including MC/DC). Coupled with this tool is \documentclass[12pt]{minimal} \usepackage{amsmath} \usepackage{wasysym} \usepackage{amsfonts} \usepackage{amssymb} \usepackage{amsbsy} \usepackage{mathrsfs} \usepackage{upgreek} \setlength{\oddsidemargin}{-69pt} \begin{document}$$TCP_{all-first}$$\end{document}, which leverages fine-grained generated coverage metadata to perform greedy multi criteria pre-execution ordering by maximizing marginal coverage gains in the execution prefix. By seamlessly linking prioritization with generation-time states, this unified mechanism achieves profiling-free efficiency, breaking the circular dependency of pre-execution. Benchmarks on CodeNet and RERS confirm that this approach yields superior coverage and outperforms state-of-the-art methods, improving APFD by 4.11% and reducing the first-fail metric by 8.7%.

Related work

Automated test case generation algorithms reduce the cost of manually crafting test cases, while test case prioritization optimizes the testing process to detect bugs earlier. Overall, automated test case generation and test case prioritization are crucial techniques in software testing, complementing each other to provide robust support for ensuring software system quality. Therefore, we introduce some related work on these two areas.

Related work of test case generation

Automated test case generation algorithms can be broadly categorized into four types: symbolic execution, fuzz testing, model-based testing, and search-based testing testing.

Symbolic execution

Traditional symbolic execution is a static analysis technique19 that uses symbols instead of concrete values as input variables, simulating code execution to gather relevant information. To address the path explosion problem in traditional symbolic execution, concolic execution, which combines symbolic execution with concrete execution, was introduced by Patrice Godefroid20 and Koushik Sen21. A well-known tool in this area is KLEE, introduced by Cristian Cadar in 2008. KLEE demonstrated significantly higher coverage compared to manually written test cases in experiments conducted on 89 independent programs from the GNU COREUTILS suite in Unix systems. In addition to KLEE, Driller and SymQEMU are also widely used symbolic execution tools. There has been significant research aimed at optimizing symbolic execution for better coverage. For instance, Cai et al.22 proposed BDGSE, which aims to improve MC/DC coverage by using static analysis to compute branch dependencies, guiding symbolic execution to selectively explore paths and simplify test cases. Tang et al.23 developed TaintSE, which combines symbolic execution with dynamic taint analysis, improving path coverage by 24–35%. Li et al.24 integrated heuristic search algorithms with symbolic execution, proposing a local search algorithm based on adaptive simulated annealing and symbolic path constraints to generate high-coverage test cases for multiple criteria within a limited time budget. These studies inspired the development of MCTCG.

Fuzz testing

Fuzz testing involves generating syntactically or semantically incorrect test cases and repeatedly running the program to discover potential vulnerabilities. This method was first proposed by Miller et al.17 in 1990. To improve code coverage, some studies have utilized coverage information to guide test case generation strategies. Many modern fuzz testing tools, such as AFT26 and Vuzzer27, have adopted this approach, demonstrating its effectiveness. While fuzz testing is a powerful method, especially suited for uncovering input validation and boundary condition issues, it can produce many invalid test cases, necessitating proper filtering and optimization.

Model-based testing

Model-based testing generates test cases by modeling system requirements. Testers must accurately define the behavior of the program system and its response to environmental changes to generate relevant test cases. This concept dates back to a method proposed by Chow28 in 1978, which used finite state machines to model the system under test and generate test cases accordingly. In 2008, Microsoft Research introduced Spec Explorer29, a tool integrated into Visual Studio that provided a visual environment for model-based testing. In 2014, Amalfitano et al. proposed MobiGUITAR30, which automated GUI-driven testing for Android applications. MobiGUITAR builds an extensible state machine model and combines it with coverage criteria to automatically generate test cases.

Search-based testing

Search-based testing can automatically generate test cases for software systems to optimize specific objectives, such as maximizing code coverage, detecting faults, or satisfying particular test requirements. Xue-Wei et al.6 combined an optimized particle swarm algorithm with mutation relations for test case generation. Chengying Mao31 used a modified ant colony algorithm to generate structural test cases, comparing its performance with particle swarm, simulated annealing, and genetic algorithms. Ahmed et al.32 employed a genetic algorithm aimed at multi-path coverage. Andreas Windisch et al.33 compared the effectiveness of particle swarm and genetic algorithms using branch coverage probability and iteration algebra as metrics. Many studies have used search-based algorithms for generating test cases aimed at multiple coverage criteria. Miguel Rojas, et al.34 extended the EvoSuite unit testing tool by integrating a multi-coverage fitness function within a meta-heuristic search algorithm to support combinatorial coverage for multiple testing standards. Zhichao Zhou, et al.35 also employed heuristic search algorithms to optimize test case generation for multiple coverage criteria. They proposed using intelligent selection instead of simple combinations of coverage standards, allowing generated test cases to satisfy primary criteria while addressing other standards. Building on Rojas’ work, Gregory Gay36 explored the impact of combinatorial coverage standards on bug detection efficiency and identified which combinations are most beneficial for detecting bugs. While search-based techniques are effective for optimizing multiple coverage goals, we choose symbolic execution here because it is more suitable for systematic structural coverage targeting and direct collection of generation-time coverage metadata in our framework37.

Related work of test case prioritization

Test Case Prioritization (TCP) was first introduced by Rothermel et al.38. In this research, Test case prioritization technique does not discard test cases, but runs the most important test cases first, which is better than test case selection as it does not reduce the bug detection rate of the tests. TCP methods can be classified into four main types based on their prioritization criteria: coverage-based TCP, bug prediction-based TCP, cost-based TCP, and multi-objective TCP.

Coverage-based TCP

This widely used technique prioritizes test cases to quickly improve coverage of specific program elements (e.g., statements, branches).39, with the ultimate goal of improving bug detection efficiency.39, Coverage-based TCP requires knowledge of the source code structure and test case coverage, making it suitable for white-box testing. Since 2001, coverage-based TCP has been a focus of research, with studies like Rothermel et al.’s showing that better coverage leads to better bug detection.39. Recent work includes Rubing Huang et al.’s algorithm, which considers statement, branch, and method coverage to determine test case priority.41, and Muhammad Nazir et al.’s research, which achieved an 85% bug coverage rate while minimizing execution time41.

Bug prediction-based TCP

This approach has gained traction recently43. It prioritizes test cases based on the location of past bugs or predictions from bug models. This method focuses on areas likely to have bugs to improve detection rates. However, it relies on historical bug data or high accuracy from bug prediction models. For example, Kim and Baik (2010) introduced Fault Aware Test Case Prioritization (FATCP) using historical fault information44. In 2022, Mostafa Mahdieh et al.44 proposed a method combining test case diversification and error tendency estimation using bug prediction models and clustering to enhance test case diversity. Bug prediction-based TCP is often combined with coverage-based TCP.

Cost-based TCP

This method aims to minimize the total cost of executing test cases needed to find a certain number of bugs44. Costs may include computational resources, execution time, and labor hours.

Multi-objective TCP

This approach considers multiple factors of interest, such as coverage, bugs, cost, and risk, to prioritize test cases. By integrating these elements, multi-objective TCP provides a more balanced and comprehensive prioritization. Samad et al.46 (2021) proposed a multi-objective TCP method that accounts for cost, fault detection, and test coverage, showing improved performance compared to similar methods.

Methodology

To implement the unified approach capable of profiling-free prioritization, we construct a streamlined architecture bridging source code analysis and test suite generation. The process begins with MCTCG accepting C source code as input, where it applies static instrumentation to support six diverse coverage criteria (including MC/DC). During the subsequent symbolic execution phase, unlike traditional tools that discard intermediate states, our framework captures granular coverage metadata in real-time. This architecture effectively bridges the gap between generation and prioritization, ensuring the production of a high-efficiency test suite without incurring post-generation execution overhead.

MCTCG represents a specialized evolution in symbolic execution tool design, engineered to transcend the single-metric limitations of standard tools. While leveraging the robust LLVM infrastructure of KLEE as a foundational substrate, MCTCG introduces a novel instrumentation and expression extraction layer. Unlike the original implementation which is confined to statement and path coverage, MCTCG actively injects monitoring probes to capture complex logic predicates. Algorithm 1: MCTCG generates test suites that meet multiple class coverage criteria

The symbolic execution tool KLEE is a popular test case generation tool. However, the original KLEE has a major limitation: it supports only a few coverage criteria. This study improves KLEE to create MCTCG, which can generate test case sets for six coverage criteria: statement coverage, path coverage, decision coverage, condition coverage, condition/decision coverage, and modified condition/decision coverage. Algorithm 1 describes MCTCG, and its workflow is shown in Fig. 1 as the following four modules: Static Analysis, Program preprocessing, test case generation and test suite generation for multiple coverage criteria.

As shown in the top four modules of Fig. 1, Algorithm 1 starts from the source code. It performs static analysis to extract condition expressions for branches and loops through variable analysis and expression extraction. Additionally, the compiler translates the source code into an IR intermediate file, assigning a unique ID to each block. Subsequently, it automatically generates instrumentation code, assertion code, and driver functions. KLEE’s symbolic execution feature is then used to generate a complete set of test cases. Finally, a greedy algorithm selects a subset of test cases from this complete set based on the required coverage criteria.

Static analysis module

This module includes variable analysis, expression analysis, and condition combination calculation. Variable analysis determines the types and names of input variables in the tested functions. Expression analysis extracts conditions for each branch and parses them into atomic conditions and logical operators. Condition combination calculation uses these expressions to generate a set of paths that meet specific coverage requirements (with broadly defined path here). Branch conditions in variable and expression analysis are obtained using regular expression matching and string processing. The parsing method converts branch conditions into expression trees, where leaf nodes are atomic conditions and non-leaf nodes are logical operators. By knowing the values of leaf nodes, the values of the entire expression can be inferred. Additionally, each atomic condition’s position in the source code is recorded to facilitate coverage information collection for the test cases.

Test case generation module

KLEE generates test cases through symbolic execution. During this process, it maintains a symbolic state table, a map where keys are variables and values are symbolic expressions. At each path’s exit, symbolic execution produces a symbolic path constraint, representing the conditions that the input variables must satisfy to follow that path. These constraints are then input into a solver to determine the values for the input variables, resulting in test cases that cover the path. To generate test cases meeting various coverage requirements, different approaches are used:Statement and path coverage: The original KLEE supports automatic generation of test cases for statement and path coverage. For these, we use KLEE’s built-in methods and only need to generate driver functions for the source code to complete test case generation and testing.Condition combination coverage: KLEE does not directly support generating test cases for condition combination coverage, which requires all pairwise combinations of Boolean values for atomic conditions in each branch to be covered at least once. This study analyzes expressions to identify all branch and atomic conditions in the source code. Pairwise combinations are then calculated to determine the required path sets. By using insertion and assertion functions to match paths in these sets, and analyzing the instrumented code with KLEE’s symbolic execution, we generate test cases that meet condition combination coverage.Branch, condition, C/DC, and MC/DC coverage: While Instrumentation method can generate test cases for these coverage types, condition combination coverage inherently includes cases that satisfy branch, condition, C/DC, and MC/DC coverage but may contain redundant cases. To avoid generating duplicates, we use a greedy algorithm to select test cases from the condition combination coverage set that fulfill branch, condition, C/DC, and MC/DC coverage requirements. The relationships between these coverage requirements are illustrated in Fig. 2, where an arrow indicates that test cases satisfying the source coverage type are a subset of those satisfying the target coverage type.Fig. 2Inclusion relationships among coverage criteria.

Test suite generation for multiple coverage criteria

We use a greedy algorithm to generate a test case subset that meets specific coverage requirements. The input to the algorithm is the complete set of test cases T and the set of elements S that need to be covered. The output is the subset T2, which is a subset of T. The goal of the algorithm is to eliminate redundant test cases. It does this by iteratively removing test cases from T2 until removing any additional test case would mean that T2 no longer covers all the elements in S.

Obtain coverage information

This module begins by generating the control flow graph (CFG) of the program under test and uses a depth-first search algorithm to obtain the program’s path set (narrow defined paths). Then, it compiles the source code into LLVM IR and assigns a unique identifier to each block as its name. This identifier allows atomic expressions identified by the static analysis module to be matched with the corresponding blocks, facilitating the translation of atomic expression coverage into block coverage. This is essential for calculating coverage information under six different coverage criteria. After obtaining all blocks from the IR, the module traverses each block, recording the covered lines, branches, conditions and path. Conclusion

This study addressed the inefficiency caused by the disconnection between test case generation and prioritization in automated testing. We proposed an integrated framework that combines MCTCG with the \documentclass[12pt]{minimal} \usepackage{amsmath} \usepackage{wasysym} \usepackage{amsfonts} \usepackage{amssymb} \usepackage{amsbsy} \usepackage{mathrsfs} \usepackage{upgreek} \setlength{\oddsidemargin}{-69pt} \begin{document}$$TCP_{all-first}$$\end{document} algorithm. MCTCG is an enhanced symbolic execution tool capable of satisfying six diverse coverage criteria (including the rigorous MC/DC), By utilizing granular coverage metadata captured directly during the generation process, our approach enables dynamic prioritization without the need for pre-execution, effectively achieving profiling-free efficiency. Experimental results on CodeNet and RERS benchmarks demonstrate that the proposed method significantly outperforms state-of-the-art techniques, improving the Average Percentage of Faults Detected (APFD) by 4.11% and reducing the First-fail metric by 8.7%. Future work will prioritize enhancing scalability for safety-critical domains and developing adaptive strategies to improve prioritization precision.
