Design of a low-power RISC-V based intelligent endoscopy detection processor: EndoRISC-V
Authors: Amritha Anand, Saraswathy B, Sasipriya P, Anita Angeline A
Published: 2026

ABSTRACT
AbstractCapsule endoscopy provides a non-invasive method for examining the gastrointestinal tract, but it generates more than 50,000 images which need several hours of manual examination. Real-time image processing in wearable receiver units could reduce the errors, but demand high computational throughput with low power and latency constraints. Standard CPUs are built for general-purpose workloads and fail to handle the mathematical computations and data throughput of image processing operations. This paper presents EndoRISC-V, a two-level reconfigurable RISC-V Harvard architecture consuming 124 mW total power at 100 MHz operation. This processor features: (i) Switchable execution units during runtime allowing selection between standard ALU instructions and image operations that include four extended instructions (MAXPOOL, Histogram Equalization, Sobel-X, and Sobel-Y), providing 4.29× throughput improvement over baseline RISC-V with 6.75× speedup for down-sampling operations; (ii) Pipelined architecture with variable pipeline depth between 3 and 5 stages, achieving 16.3% cycle reduction for image-intensive workloads in low-power mode. The design was built using Verilog HDL while the synthesis and implementation was performed on Xilinx Artix-7 FPGA. The design consumes 2,971 LUTs and 1,858 flip-flops at 100 MHz with 6.898 ns positive timing slack. Real-time processing capabilities were validated on the Kvasir Gastrointestinal dataset through edge-based polyp detection, which processed 8×8 regions with a 3.45 μs execution time at 60.4 frames per second using 640×480 resolution, exceeding the clinical requirement of 2–4 frames per second by a 15.1× margin. The system uses 124 mW of power to achieve 0.428 nJ energy efficiency per classification. The custom image processing unit requires 115 LUTs, representing 3.9% of total design space, to deliver 3.77× better performance than standard RISC-V.Keywords: RISC-V processor, Reconfigurable architecture, Domain-specific instruction set extension, Capsule endoscopy, Medical image processing, Hardware acceleration, Adaptive pipeline, Edge computingSubject terms: Engineering, Mathematics and computing

Introduction

Capsule endoscopy allows physicians to examine the digestive system without surgery by using a pill-sized camera (30×11 mm) to record 2 to 4 images every second for 8 hours, transmitting 50,000 to 60,000 raw images to a wearable receiver belt that must be manually reviewed. The process faces a major challenge because 60–80% of images display normal mucus membranes, resulting in high healthcare costs. The strict limitations of medical devices require the development of dedicated processing systems which must achieve an optimal balance between system performance, power usage, and device programming capabilities. This work proposes real-time image processing in the receiver belt, reducing review time to minutes by classifying images immediately upon receiving. The proposed work consumes only 124 mW while operating at 60.4 Frames Per Second (FPS), ensuring immediate classification during the procedure.

Standard RISC-V processors are capable of only 3–4 million operations per second (MOPS) on image processing kernels. For example, image processing on general-purpose CPUs is done in a serial manner; consequently, a single Sobel edge detection operation requires 27 RISC-V instructions and 30 cycles to execute. The result is a requirement for clock frequencies in the gigahertz range and power consumption in the multi-watt range.

Polyp detection in gastrointestinal imaging requires a specific processing pipeline: (a) Histogram equalization—the capsule’s LED creates uneven illumination as distance varies during transit; intestinal folds create shadows which make polyps impossible to see without contrast enhancement; (b) Edge detection—polyps appear as raised circular or elliptical lesions on the intestinal wall; the Sobel gradient detection method establishes boundary lines which the system uses for automatic identification; (c) Spatial down-sampling—wireless transmission uses high power consumption; the system extends battery life for complete examination by reducing normal tissue bandwidth while keeping full resolution for flagged regions.

The main RISC-V Instruction Set Architecture (ISA) can be augmented with custom image processing instructions that directly invoke dedicated hardware components. This approach allows faster and more efficient execution of image operations. By including extended instructions as hardware accelerators, this approach removes data overhead and simplifies the model, serving as a middle ground between general-purpose CPU architectures and full ASIC implementations.

Furthermore, the pipeline depth provides an option to vary so as to improve power optimisation and hence provides two functioning modes: (i) Balanced power mode: 5-stage implementation design provides complete forwarding paths and advanced hazard management capabilities which enable operation at higher frequencies; (ii) Low power mode: 3-stage pipeline bypasses the memory (MEM) stage pipeline registers, merging EX and ID stages which results in decreased cycle count and therefore decreased time for workloads that process large image datasets. This combination of execution-level ISA extensions and pipeline-level reconfiguration creates a new design point: image processing that is programmable yet efficient for edge systems with limited resources.

This study addresses the feasibility of achieving real-time image processing on ultra-constrained medical devices with metrics including clinical performance constraints, Power and Area constraints, and Programmability Requirements. The existing solutions fail to satisfy at least one of these metrics.

This paper presents a two-level reconfigurable RISC-V architecture that addresses the identified challenges through synchronised reconfiguration at the execution level and the pipeline level.

Level 1: Execution-Level Reconfigurability: Custom instructions invoke dedicated hardware components directly, reducing the number of cycles drastically. Four custom ISA extensions (MAXPOOL, Histogram Equalization, Sobel Detection X-axis, Sobel Detection Y-axis) are introduced and configured in the execution stage through an Image Execution Unit (IMG_EU). These instructions achieve 5.0–5.4× cycle reduction on image processing kernels, executing the same functions that take 2–27 cycles in only 1–5 cycles, while occupying only 115 LUTs (3.9% of total processor area).

Level 2: Pipeline-Level Reconfigurability: The processor supports runtime switching between 3-stage and 5-stage pipelines, introducing a low power mode and enabling power optimisation.

Further, the operating modes incorporated are:(i) Low Power Mode: 3-stage mode (IF-EX/ID-WB), Optimized for image-intensive workloads with minimal power consumption, achieving execution of a image- intensive stress sequence in just 41 cycles as compared to 5-stage which takes 49 cycles.(ii) Balanced Power Mode: Balanced Power Mode: 5-stage mode (IF-ID-EX-MEM-WB), providing full pipeline forwarding paths and capable of higher maximum clock frequency through reduced critical path length per stage.

Related works

The necessity of edge vision processing has motivated researchers to investigate various architectural methods, ranging from adding custom instructions to entirely restructuring processor pipelines. This section indicates the position of this multi-level reconfigurable architecture in the scenario of RISC-V-based image processing and the reconfigurability achieved through combined execution-level and pipeline-level for better results,while compared to optimizing either one separately.

Custom instructions for image processing

Processors augmented with custom instructions provide a pragmatic, middle-ground alternative to slow general-purpose CPUs and inflexible hardware accelerators. Rezunov et al.1 developed an automated tool called CIDRE that identifies which code takes the longest to run and suggests new custom instructions to speed up those parts. The performance against standard embedded benchmarks showed 2.47×faster execution at the expense of only 24% more chip area. However, the technique assumes a static pipeline. Liu et al.7 designed a custom instruction for gamma correction that replaced a series of normal instructions with a single one, reducing computation time by 58% and code size by 77%. Kumar et al.9 worked on memory operations that reduce the performance of neural networks; the custom load/store instruction halved the number of cycles and power consumption while taking only 4% additional area. A recent survey10 thoroughly reviewed all methods of RISC-V architecture enhancements, pointing out the gaps between current architectural features and the needs of Artificial Intelligence (AI) and edge computing applications.

Vector extensions and parallel processing

Vector instructions lead to simultaneous processing of several data elements at once. This is a perfect fit for image processing because the same operation is performed on thousands of pixels. Li et al.2 applied RISC-V vector extensions to computer vision tasks using an 8-lane vector processor, reporting up to 24× reduction in instruction counts and 2.98× speedup. However, disadvantages include increased chip area due to vector register files, higher complexity of the programming model, and the inefficiency of histogram-like operations due to irregular memory access. The multi-core approach of8 opted for parallel processing via on-chip interconnection of several RISC-V processors. The Sobel convolution becomes one instruction rather than dozens, resulting in a 19.3× reduction in instructions with only 3.9% area overhead.

Pipeline design choices

Speed and power consumption are greatly influenced by how pipeline stages are structured. The conventional 3-stage pipeline11 could not be adapted and always worked at 50 MHz. The 5-stage processor13 incorporated low power but still fixed the pipeline structure at the outset.

Unorthodox pipeline patterns have been investigated in recent studies. The architecture in14 arranged different pipeline stages for multiple functional units in a sequential rather than parallel arrangement, showing lower power and fewer resources than parallel Very Long Instruction Word (VLIW). The flexible pipeline concept15 allows designers to choose the number of pipeline stages at design time depending on application requirements targeting FPGAs or ASICs.

The novelty of this contribution is the flexibility to adjust at run time. The processor changes from a 3-stage to a 5-stage configuration during operation depending on workload requirements. Picture-heavy sequences take 41 cycles in 3-stage mode and 49 cycles in 5-stage mode. The 8-cycle (16.3%) improvement results from reconfiguring the pipeline, not merely deactivating some stages.

Runtime reconfiguration and system implementations

The advanced pipeline organizations have been aimed at certain applications. PipeCIM12 crafted a nested three-level pipeline for CNN acceleration, achieving 133.8 TOPS/W and 128.56× VGG-16 speedup via computing-in-memory techniques with custom RISC-V instructions. Luo and Wu3made an image acquisition system for industrial inspection with 26% storage efficiency and 27% speed improvement through multi-buffer DMA on FPGA. Dörflinger et al.5 evaluated major open-source RISC-V processors (Rocket, BOOM, CVA6, SHAKTI) under the same benchmarks. Baglietto et al.4 gave a historical perspective from 1996 on RISC processors handling image workloads. Charaf et al.19 enabled dynamic partial reconfiguration for FPGA-based RISC-V SoCs using RV-CAP that showed runtime hardware adaptability at the fabric level but without coordinated instruction level optimization.

This study executes reconfiguration at both the execution and pipeline levels, where the selection of pipeline structure relies on the instruction mix and vice versa, thus proving that joint optimization is better than independent tuning.

Research gaps and contributions

Looking across the literature, this research reveals several gaps. Past work has either modified instruction functionality1,7,9,16,17 or pipeline organization11,13–15,18, but not both simultaneously where the decision at one level influences the other. Moreover, most approaches target either fine-grained pixel-level operations2,8 or coarse-grained accelerator blocks12,16,17. This work is situated in the middle ground with kernel-level operations, reducing instruction count by 19.3× with only 3.9% area overhead. Furthermore, specialized processors usually set their configuration at synthesis time1,6,7,9,11,13, whereas runtime reconfigurability enabling workload-adaptive optimization has not been fully explored.

RISC-V baseline architecture

The baseline processor is a standard 5-stage pipelined RISC-V architecture which follows the RV32I instruction set specification. The system performs as the primary evaluation platform measuring performance improvements from multi-level reconfigurable systems. The design implements Harvard architecture because it separates instruction memory and data memory into distinct physical storage locations, enabling dual memory access during both instruction fetching and data processing activities without introducing structural hazards.

Instruction fetch stage

The Instruction Fetch stage fetches the instruction from the instruction memory using the Program Counter (PC). The PC value increases by 4 when an instruction is fetched and when branching instructions direct it to destination addresses. A dedicated instruction memory port is required to prevent collision of memory access operations. Harvard Architecture solves the collision by enabling separate spaces for data and instruction access. The IF/ID pipeline register stores the retrieved instruction for the next processing stage.

Instruction decode stage

The Instruction Decode stage is responsible for interpreting the instructions by separating them into instruction fields. The register file is accessed through two read ports to obtain the source operands.Three key components operate in this stage to ensure the instructions are decoded correctly: Control Unit, which produces the control signal; Immediate Generator that extracts the immediate values; and the Register File unit that supplies the source operands.

Execute stage

The Execute stage calculates the result using the Arithmetic Logic Unit (ALU).The branch conditions are continuously assessed through the branch unit. The data from ID/EX pipeline register is utilized to provide results that are sent to the EX/MEM register.

Memory Access (MEM)

The Memory Access stage establishes a connection between the processor and the data memory to handle load and store commands. Load instructions read data from memory using the calculated address and Store instructions write register data to memory. Separate read and write ports are present to support both operations.

Write Back (WB)

The Write-Back stage updates the Register File with the result of the instruction. The value written may have been the result of an ALU operation or could be from the data memory. The final result is stored in the destination address, hence the execution and storage of an instruction is completed with this stage.

Hazard detection and resolution mechanisms

Pipeline Hazards occur when instruction execution cannot proceed as planned in the next clock cycle because of dependencies in data and resource conflicts. The baseline architecture installs hazard units to detect such hazards by stalling the pipeline, forwarding the data and flushing instructions.

Hazard detection unit

The hazard detection unit monitors pipeline state to identify conditions requiring intervention. The unit detects three primary hazard scenarios.

Load-Use Hazards: When a load instruction in the execute stage targets the register that is required by the next instruction that is still in the decode stage it creates a Load-Use hazard. When such sequences are identified the pipeline is stalled by inserting NOP (No Operation) instruction into the Execute stage while the path through IF and ID is blocked temporarily.

Branch Hazards: When the outcome of a conditional branch instruction still remains unknown till the execute stage the processor hangs as it cannot determine whether to fetch to the next instruction or jump to the target address creating Control/Branch hazards. The hazard unit invalidates incorrectly fetched instructions. This results in a two-cycle control flow penalty for every taken branch.

Data Dependencies: When the previous instruction is still executing and the result is required for the subsequent operation, Read-After-Write (RAW) dependencies are created. The source register address in the decode stage is compared with destination registers in execute, memory, and write-back stages.

Data forwarding unit

The data forwarding unit allows direct routing of computed results from later pipeline stages to earlier stages to prevent pipeline stalls when dependencies can be resolved without waiting for write-back completion.

Proposed architecture

Architecture overview

The proposed RISC-V processor architecture is enhanced with three major improvements to increase the image processing capabilities of the processor. The first enhancement consists of custom image processing instruction set extensions. The second enhancement introduces an Image Processing Execution Unit (IPEU) which can switch between standard ALU and IPEU operation during runtime. The third enhancement allows users to adjust power–performance through pipeline reconfiguration operating between 3-stage and 5-stage modes. Figure 2 illustrates the complete reconfigurable architecture showing the integration of these components.

Complete reconfigurable architecture with IPEU and variable pipeline

The design addresses the core problem of making embedded vision systems both fast and energy-efficient. Because image processing tasks usually involve parallel data, predictable memory patterns, and can handle slightly lower pipeline throughput. The proposed architecture aims to design a custom hardware accelerator called the IPEU (Image Processing Execution Unit).

Custom image processing instruction set extensions

The instruction set extension introduces four domain-specific operations targeting essential image processing functions using the custom-0 opcode space (0001011) that the RISC-V specification permits for user-defined extensions. The instructions use R-type encoding format to specify operations through funct3 and funct7 fields.

Instruction Encoding Format: The custom instructions follow the R-type RISC-V encoding format. Each instruction is encoded in 32 bits as shown in Table 4.

Max Pooling: The MAXPOOL operation enables spatial down-sampling by selecting the maximum pixel value from a 2×2 pixel block. The operation calculates results from four input pixels stored in register rs1.

Sobel Edge Detection: The SOBEL_X and SOBEL_Y operations achieve edge detection through gradient-based methods using 3×3 Sobel kernels for discrete convolution. The 3×3 pixel window uses row-major order to calculate the gradient.

Histogram Equalization: The HIST_EQ operation uses intensity remapping according to cumulative distribution function (CDF) mapping to enhance contrast. The current implementation assumes lookup table values are pre-fetched into registers by software, requiring 1 cycle for table lookup plus 3 cycles for pixel remapping. A fully autonomous implementation would require on-chip LUT storage (256×8 bits = 256 bytes) or iterative CDF computation (∼50 cycles latency).

These custom instructions are executed through a dedicated Image Processing Execution Unit (IPEU). The IPEU uses a multi-cycle finite state machine that executes different sequences depending on each operation to handle 32-bit data containing 8-bit pixel values. The system automatically chooses between ALU and IPEU through opcode decoding when the custom-0 opcode (0001011) is detected.

Hazard management for multi-cycle IPEU operations

The multi-cycle IPEU operations create additional hazardous situations beyond those present in the initial pipeline operations. The IPEU prevents reading stale values until its write-back operation completes. To prevent overlapping of multi-cycle operations, the hazard unit stalls new image instructions when any IPEU operation is active. This serializes image operations, trading throughput for implementation simplicity.

Variable pipeline architecture

The architecture offers variable pipeline depths that can switch between 3 stage and 5 stage depending on the power_mode. The 3 stage configuration bypasses pipeline registers and merges state logic. Figure 3 compares the two pipeline configurations.

Pipeline configuration comparison

The 3-stage mode merges the Instruction Decode stage and the Execute stage into a combined EX/ID stage. The Register File access and ALU operations occur in the same cycle in this case. The IF/ID register remains to break combinational paths between fetch and decode stages. The MEM/WB register is bypassed such that the Write-Back stage directly receives signals through multiplexers from the Memory stage.

The 5-stage mode is a balanced power mode that results in higher maximum operating frequency while the energy usage is decreased in the 3-stage mode. The 3-stage mode further achieves 16.3% cycle reduction for operations that require excessive hazard management as it bypasses the MEM/WB register completely.

Complete system integration

The complete architecture offers three enhancements from the baseline architecture: The instruction set extension with image processing instructions, execution unit specialization and pipeline depth reconfiguration. The proper working of custom image instructions in both 3-stage and 5-stage modes provides a good advantage over RV32I instructions.

Design and implementation

The proposed architecture is implemented in Verilog HDL on the Xilinx Artix-7 XC7A200T FPGA. The implementation of the IPEU datapath and the Execute stage multiplexing logic is explained in the following sections. The design obtains timing closure at 100 MHz with a timing slack of 6.989 ns timing slack, offering room for timing closure at higher frequencies.

Image processing execution unit architecture

The Image Processing Execution Unit implements multi-cycle execution that is controlled by a Finite State Machine (FSM). Figure 4 illustrates the IPEU datapath showing pixel extraction and arithmetic computation units and result generation logic. The unit processes three 32-bit inputs (operand_a, operand_b, operand_c) to extract eight 8-bit pixel values and execute the specified operation. It finally produces a 32 bit output.

Image processing execution unit datapath

The main architectural elements show the following characteristics:

Pixel Extraction: The system uses extracts 8-bit pixel values from packed 32-bit operands through bit slicing. For example, 9 pixels are extracted and stored in an internal pixel register array (pixel[0:8]) for Sobel operations.

Multi-Cycle Arithmetic: The Sobel gradient computation uses staged accumulation to process multiply-accumulate operations through three registers (grad_pos, grad_neg, gradient). The system implements ×2 multiplications through left-shift operations, removing the need for dedicated multiplier hardware.

Saturation Logic: The last cycle tests for overflow conditions when gradient magnitude exceeds 255 and saturates the output to 0xFF. The absolute value computation processes signed gradient values by identifying the sign bit and applying two’s complement negation when necessary.

Runtime switching between ALU and IPEU

The execute stage uses instruction opcodes to determine whether the standard ALU or IPEU should be used. The control unit decodes the opcode field and send a signal to the use_img_eu control signal when a custom image instruction is detected (opcode = 0001011). Figure 5 illustrates the multiplexing mechanism in the execute stage datapath.

Execute stage multiplexing architecture

Operand routing at the execute stage input and the result selection at the EX/MEM register uses multiplexing. Standard instructions use forwarding multiplexers to direct their operands to the ALU. The IPEU does not process them until the start signal activates its operation even after receiving the operands.

Standard instructions incur no processing overhead because the IPEU stays inactive and does not generate dynamic energy consumption. The extra multiplexing introduces minimal delay through a single 2:1 multiplexer in the result path.

Custom instruction hardware mapping

The hardware implementation of the custom instructions is detailed in this section. Each instruction is mapped to a dedicated path on the Xilinx Artix-7 FPGA. The Sobel operations (Sobel-X and Sobel-y) use 3x3 convolution kernals with coefficients 0, 1 and 2 share a unified datapath. Both Sobel-X and Sobel-Y are identical in hardware. Instead of using DSP blocks or MACs, the × 2 coefficient is handled by a 1-bit left shift to maximize efficiency. To calculate the gradient, two 11-bit adder trees are used. The resulting negative and positive gradients are fed into a 12 bit subtractor and an absolute value unit. This logic is mapped to 9 CARRY4 primitives and 78 LUTs. The MAXPOOL instruction uses comparators to compare two 8-bit comparisons on the first cycle and one final comparison on the second cycle to determine the result. The operation uses 3 CARRY4 primitives and 33 LUTs. The current version of Histogram Equalization uses a lookup table to extract the data from the memory, so it only uses 6 LUTs and 18 Flipflops. Clinical validation: gastrointestinal imaging

Dataset and methodology

Validation is performed using the Kvasir gastrointestinal image dataset from Vestre Viken Health Trust, Norway. Eight images - 4 polyp, 4 normal, were selected from the representative dataset and was preprocessed to grayscale. The hardware output showed complete accuracy when matched with MATLAB reference, verifying every single pixel.

The validation flow includes a MATLAB preprocessing script that generates a input hex file (input.hex) that is provided to a testbench of the RTL design loaded in ModelSim. The testbench produces an output hex file (output.hex) which is then fed to a MATLAB verification script that reconstructs the image and displays the processed image for clinical comparison. The hardware blocks for SOBEL_X, SOBEL_Y, MAXPOOL, and HIST_EQ shown in Figure 6 are physically implemented within the img_exec_unit module on the Artix-7 FPGA. Limitations and future work

The present system shows notable improvements but it also presents some operational limitations. The custom instruction set provides functionality for specific image-processing tasks through its extended ISA. The current system needs additional hardware components to achieve advanced kernel processing capabilities. The histogram Equalization technique needs a LookUp Table (LUT) to be stored because this Pre-fetching method avoids delays due to external memory access. The static power consumption of the Artix-7 platform establishes the primary power consumption pattern, making it difficult to determine the dynamic power efficiency advantages from custom instruction operations.

The future research will focus on expanding the instruction set architecture through additional image-processing instructions including convolution, Gaussian filtering, and edge-preserving filters. System performance will reach higher efficiency levels through DSP block implementations that can handle multiply and accumulate operations. The transition to an ASIC design process will provide better assessment of power consumption and space efficiency by removing FPGA static power consumption. The combination of on-chip memory buffers will enable better scalability for real-time high-resolution image processing.

Conclusion

The study demonstrates a multi-level reconfigurable RISC-V system which supports custom image-processing instructions and shows capacity for both fixed and adaptive pipeline depths. The design achieves a performance increase of 5.4× while reducing instructions by 16.7× through branch penalty elimination and substantial code size reduction.

The Kvasir gastrointestinal dataset demonstrated perfect clinical validation results, achieving 100% accuracy in eight distinct test cases. The entire system executes edge-based polyp detection at 3.45 μs per 8×8 region (345 cycles), allowing real-time capsule endoscopy operation processing 640×480 frames at 60.4 FPS. The system operates at 124 mW power consumption while achieving 0.428 nJ energy efficiency per classification.

The Xilinx Artix-7 XC7A200T FPGA implementation shows 2.21% LUT utilisation, achieves successful timing closure without any violations, and maintains stable performance at 0.124 W total on-chip power. The research results show that embedded image-processing workloads gain performance and reliability improvements through the combination of domain-specific ISA extensions and pipeline-level reconfiguration without any negative impact on hardware efficiency.
