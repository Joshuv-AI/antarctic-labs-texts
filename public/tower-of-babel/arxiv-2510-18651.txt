CPSLint: A Domain-Specific Language Providing Data Validation and Sanitisation for Industrial Cyber-Physical Systems Conference: The 41st ACM/SIGAPP Symposium On Applied Computing; March 23–27, 2026; Thessaloniki, Greece
Uraz Odyurt, Ömer Sayilir, Mariëlle Stoelinga, Vadim Zaytsev

Abstract
. Raw datasets are often too large and unstructured to work with directly, and require a data preparation process. The domain of industrial Cyber-Physical Systems (CPS) is no exception, as raw data typically consists of large amounts of time-series data logging the system’s status in regular time intervals. Such data has to be sanity checked and preprocessed to be consumable by data-centric workflows. We introduce CPSLint , a Domain-Specific Language designed to provide data preparation for industrial CPS. We build up on the fact that many raw data collections in the CPS domain require similar actions to render them suitable for Machine-Learning (ML) solutions , e.g., Fault Detection and Identification (FDI) workflows, yet still vary enough to hope for one universally applicable solution. CPSLint ’s main features include type checking and enforcing constraints through validation and remediation for data columns, such as imputing missing data from surrounding rows. More advanced features cover inference of extra CPS-specific data structures, both column-wise and row-wise. For instance, as row-wise structures, descriptive execution phases are an effective method of data compartmentalisation are extracted and prepared for ML-assisted FDI workflows. We demonstrate CPSLint ’s features through a proof of concept implementation.

1.
Introduction

Sensor data collected from industrial Cyber-Physical Systems (CPS) is seldom well formatted or error-free. Additionally, such data collections are not consumable by data-centric solutions and workflows without going through preprocessing steps. Data preparation is needed to both ensure robust and reliable operation of solutions, and to enable functionalities dependent on context-specific preprocessing. As such, prior to the consumption of machine data by different analytic workflows, validation, sanitisation, remediation (where applicable), and structuring is necessary. This is particularly apparent and problematic for anomaly detection and identification, which is a cornerstone of Fault Detection and Isolation (FDI) in industrial contexts, as corroborated in multiple surveys
Arts et al. 2025
;
Kim et al. 2021
;
Tamssaouet et al. 2023
.

A common way to execute data preparation is to cover it as part of the data-centric workflow, programming validation, structuring and so forth, into the algorithms as preceding steps to the workflow itself. This is common practice, and one example is applying sanity checks, e.g., validation of input file format consistency. While functionally effective, the approach is inefficient. Even considering proper software development practices, much ad hoc and per use-case programming will be required. At the same time, this approach will require the permanent involvement of software engineers alongside domain experts.

We improve the robustness of a family of Machine Learning (ML)-assisted solutions by ensuring correctness of input data and by performing the fundamental data preparation task, i.e., compartmentalising the data into segments called
execution phases
. Examples of incorrect data are various, but we can mention instances of corruption, e.g., textual characters in numeric fields, unexpected line separators, missing data fields, or even rows, and so forth. We propose and showcase
CPSLint
, a specialised Domain-Specific Language (DSL) for this task, making it a reusable tool, accessible directly to domain experts.

Targeted solutions

CPSLint
is specifically applicable to a category of solutions involving time-series data processing alongside ML model usage, e.g., fault detection solutions. These solutions involve data compartmentalisation using
execution phases
and are primarily intended for processing of machine traces collected during the operation of industrial CPS. Examples include semiconductor photolithography machines, production printing machines, die bonder machines, and similar equipment. A few of the common characteristics apparent in such systems are: presence of highly complex, multi-node compute and control elements; a narrowly defined domain of operational tasks, i.e., highly purpose-built; highly repetitive and predominantly sequential machine cycles; constrained yet non-deterministic behaviour; and a continuous focus on achieving high-yield production output. 2.
Background

Below, a few background concepts fundamental to the topic of this paper are elaborated.

2.1.
Domain-Specific Languages

DSLs are programming languages with a higher level of abstraction than General-purpose Programming Languages (GPLs)
Mernik et al. 2005
. DSLs are often employed to perform specific tasks, for instance database management languages like SQL, and to enable domain experts to undertake programming tasks using terms and concepts familiar to them, e.g., MATLAB for scientific computing). The output of DSLs does not always need to be executable; for example, the DOT language of GraphViz can be used to draw graphs, YAML can be used to orchestrate Docker containers using Docker Compose, and
L
a
T
e
X
can be used to write documents. Regardless of the domain or output, DSLs provide a way to perform a task with significantly less effort and expertise than would be required using a GPL. In this paper, we make a DSL from similarities found across the domain of data validation and sanitisation, combined with the information from the cyber-physical domain.

2.2.
Execution phases

Execution phases are segments of monitoring data, reflecting the behaviour of the system under scrutiny per individual task during an execution. Phases are applicable to time-series monitoring data collected from industrial CPS. As industrial CPS operate primarily on sequential and repetitive machine cycles, the concept of phases is an effective method of data compartmentalisation. As such, data related to each task or sub-task can be analysed individually and in isolation. Phases covering tasks and respective sub-tasks form a hierarchical relation. A visual representation of different phases assigned to tasks and sub-tasks during a generic execution timeline is given in
Figure

Section

. Considering the repetitive nature of industrial CPS, compartmentalised phase data are most suitable for collecting ML dataset instances.

2.3.
Required preprocessing

In the context of the described category of use-cases involving industrial CPS, the concept of execution phases is particularly effective. Preprocessing for compartmentalised data, based on execution phases, results in rather descriptive datasets for traditional ML training
Odyurt et al. 2022
. The considered phases for this experiment, i.e., image processing cycle high-level task, image load subtask, and neural image detection subtask, are visualised in
Figure

2
. As such, the preprocessing shall cover parsing of machine traces as a preparatory step, followed by trace cutting steps, resulting in data compartments representing individual phases.

The correct operation of ML-assisted solutions intended for industrial CPS, or any type of system for that matter, relies on the correctness of data. An ad hoc approach is to implement as many sanity checks and corrective actions in the face of corrupt or malformed data. We aim to follow a formal methodology and ensure robustness of these preprocessing steps using a DSL, i.e.,
CPSLint
.

2.4.
Data corruption types

Data corruptions are a common occurrence when collecting monitoring data from industrial machines. We describe well-known categories below and at the same time, we explain how each corruption type is being emulated for our experiments and demonstration.

To systematically evaluate the capabilities of
CPSLint
, we designed a set of corruption strategies, mimicking common errors observed in monitoring data. These corruptions are applied to the original raw data in localised, non-overlapping blocks of rows (10 rows). The corruptions affect a predefined fraction of the total data, in this case 0.5%. The motivation behind corrupting contiguous segments is to ensure that the effects are realistic, challenging and resembling real transmission errors, sensor failures, or logging issues. During high-frequency logging, trace logs usually portray a delay effect before going back to normal. The following corruption types are supported.

Data type mismatch

Numeric fields are injected with invalid characters, e.g., letters or special symbols, rendering them non-parsable. In some cases, the Universal Asynchronous Receiver/Transmitter (UART) identifier field is also corrupted, simulating noisy channel logs.

Data type mismatch with targeted UART

Similar to the previous corruption, but biased towards affecting rows associated with a specified UART identifier. This enables testing of selective corruption of device-specific data.

Out-of-bounds values

Numeric fields are replaced with extreme constants, e.g.,
“99 999.999”
, that are far outside expected measurement ranges. Depending on configuration, this may affect all numeric columns or a random subset within each block.

Out-of-order rows with reliable timestamps

Rows in a block are randomly permuted, but their original timestamps are preserved. This simulates reordering of messages while maintaining temporal information.

Out-of-order rows with unreliable timestamps

Rows are shuffled, and new monotonically increasing timestamps are generated for the block. This simulates cases where both order and timing metadata are compromised during collection.

Missing fields

A randomly chosen numeric column is blanked out across all rows in a block, representing systematic loss of a sensor channel.

Missing rows

Entire blocks of rows are deleted, optionally biased toward containing a specified UART identifier. This models partial loss of data segments, such as dropped packets or truncated logs.

Misplaced end-of-line markers

Rows within a block are concatenated with their successors, simulating the effect of missing or corrupted line delimiters. This results in malformed records and broken row alignment, resembling common parsing errors in raw log files.

3.
Implementation

Our implementation which currently is tuned as a demonstrator for an example use-case is elaborated below. We start with describing the use-case.

3.1.
Use-case

The concept of execution phases and the use of a phase-based solution can be demonstrated with an experimental platform.

3.1.1.
Experimental platform

The reference monitoring data is collected from a computing device based on the ODROID-XU4, incorporating the ARM big.LITTLE architecture. The considered workload is an image processing application running on a Linux OS with minimal footprint. Images can be read either from the attached camera, or the available storage device. The monitoring device is an external power data logger with a separate Power Supply Unit to enforce isolation and ensure correctness of readings
Odyurt et al. 2021
.

3.1.2.
Reference data

To collect the chosen reference monitoring data, the experimental platform has been extensively benchmarked
Odyurt et al. 2021
. Monitoring data is collected while running different workloads, i.e., the image processing application, running with different inputs, and a variety of operational conditions, resulting in 24 data collection scenarios. These scenarios are defined by combining the following parameters:

•

3 physical execution conditions,
Normal
,
NoFan
,
UnderVolt

•

2 sets of workload inputs

•

2 selected core types from the available hardware, Little Core and Big Core

•

2 repetition counts, single round of input processing and 10 rounds of input processing

This reference data covers electrical metrics (potential, current, power) in the form of time-series, augmented by core clock readings and multiple platform temperature sensor readings. Collection frequencies vary, in particular, electric potential and current are collected with the sampling rates of 1 kHz and 4 kHz, respectively. Lastly, messages sent over UART are included, acting as signalling data to follow individual tasks and sub-tasks.

3.1.3.
Raw data description

The data collected directly from the logger has the following header:

•

Timestamp (S)

•

Arc Main Current (A)

•

Arc Main Voltage (V)

•

Arc Main Energy (J)

•

Arc UART (TXT)

The column titles are self-explanatory. UART cells are not populated in every row. Useful UART messages are limited to start of processing, start and end of execution phases, core clock readings and board temperature readings, collected with the low frequency of per processed input instance.

3.2.
Implemented features

Currently the
CPSLint
implementation supports a core set of features, providing the following capabilities:

•

Inspect a dataset and provide a baseline
CPSLint
script

•

Filter unwanted substrings globally or per column

•

Enforce data types on columns

•

Enforce a valid range of values for numeric columns

•

Impute missing data with various configurable strategies

•

Compartmentalise larger datasets based on flags in the data

With these core features,
CPSLint
can be used to prepare datasets for ML workflows. The current functionality of the language mostly focuses on the facilitation of remedies for corrupted data. For example, missing sensor data can be imputed using an appropriate technique, e.g., taking the mean of all available values, or performing interpolation. Remediation strategies are fairly configurable, e.g., the type of interpolation to be used.

5.
Discussion: Advantages of a DSL

A natural question to be raised is the motivation behind the use of a DSL
Mernik et al. 2005
;
Tomassetti & Zaytsev 2020
vs natively programming the functionality as part of the targeted solution we mentioned in the
Section

1
. In this context, DSL use has a number of advantages.

Separation of concerns

We mentioned in
Section

2.3
that preprocessing of machine data will involve cutting the data according to use-case phases. Every use-case has a different set of phases, while the targeted solutions consuming phase data stay the same, e.g., FDI workflows. As such, it is advantageous to draw a boundary and delegate handling of dynamic aspects of machine data to a descriptive tool, which is easier to reconfigure. Aside from the phase definitions per use-case, expected corruptions have a dynamic nature as well, e.g., different expectations per machine type or model.

Declarative expressiveness

Expressiveness of a DSL, i.e., being closer to domain language, is the enabler for the aforementioned ease of reconfigurability. It will allow involvement of domain experts, who may not be programmers, in applying the DSL.

Standardisation and consistency

Following the same line of reasoning, the contained and consistent set of rules enforced by a DSL is a better alternative to various styles of programming using a general purpose language. This is especially the case in larger organisations, where tasks are delegated to different engineers.

Alternative approaches

Closely related to standardisation and consistency, usage of general purpose and vastly capable programming languages by different programmers will lead to ad hoc solutions. Whereas, using a specialised DSL with a much smaller domain of vocabulary, ensures that the generated Python (or any other) code uses embedded methodical techniques for functionality supported by the DSL, e.g., filtering unwanted substrings. The methodical vs ad hoc argument is valid for both sanitisation and remediation techniques.

On demand code generation

Another less obvious advantage of our approach, which leads to code generated in a general purpose language, is the
on demand
nature of this code generation. While
CPSLint
can be extended to a point that it would support large catalogues of sanitisation and remediation techniques, different use-cases will only require a relevant subset. In this fashion, the generated code, in this case Python, will only cover the required functionality. This is much more efficient than having a maximalist package or library that can serve any and every use-case, making the DSL-driven approach much more streamlined.

6.
Related work

From the notable tooling at the time of this writing, we recognise the following examples, each providing various sets of features.

GNU datamash

GNU Project 2025
is a command-line tool that performs basic numeric, textual, and statistical operations on textual data. While it is not a fully-fledged DSL, it is suitable for handling basic manipulation and analysis on the input.

Lisp Query Notation

Hoff 2024
is an embedded DSL in Common Lisp that can operate on CSV data as well as structured formats such as JSON. It allows users to query and manipulate textual data both as a DSL and as a command-line tool. Being embedded in Common Lisp enables users to extend its functionality and makes it possible to fall back on Lisp when the DSL is limiting for certain operations.

DescribeML

Giner-Miguelez et al. 2023
is a DSL designed to precisely describe machine learning datasets in terms of their structure, provenance, and social concerns, with the aim of providing a method for dataset documentation based on their characteristics, thereby helping data scientists select the appropriate dataset for a given project. DescribeML is implemented using Langium and has been published as a Visual Studio Code extension.

RADAR

Heine et al. 2020
is a DSL built for data quality monitoring. RADAR’s capabilities include simple checks like making sure there are no null values, data integrity checks and statistical checks like conformance of the data to a certain distribution. This DSL is made up of 3 types of definitions; sources (referring to the input data), checks (which act like functions that accept parameters), and actions (which apply the checks on data from a source and define what should be reported for the resulting values).

Lavoisier

de la Vega et al. 2020
is a DSL that helps with creation of datasets that conform to the format accepted by data mining algorithms. It is meant to reduce script size compared to accomplishing the same result using other ways to prepare date such as SQL and Pandas.

Papin

Sal et al. 2024
is a spin-off DSL of Lavoisier that specialises further and makes it compatible with fishbone diagrams, a notation used by industrial engineers to model cause and effect. For the Papin pipeline the authors introduce an new fishbone diagram called data-oriented fishbone diagrams which combines domain data (defined using Lavoisier expressions) with standard fishbone diagrams. These diagrams then are used as input for the Papin specification.

Jet

Ackermann et al. 2012
is an embedded DSL in written in Scala which is meant to be used for batch processing of large datasets. This DSL can generate code for both Apache Spark and Apache Hadoop, both of which are systems for processing big data. The compiler, relational, and domain-specific optimisations of the implementation provide substantial performance gains compared to the naive handwritten processing code.

DSL4DPiFS

Vogel-Heuser et al. 2025
is a graphical DSL to help with deploying data pipelines in industrial metal forming systems, built with interdisciplinary collaboration in mind. These data-pipelines used to enable process optimisation, quality management, and predictive maintenance of these systems.

7.
Conclusion and future work

We have introduced
CPSLint
as a DSL specialised for preparation of machine data prior to data-centric workflows, e.g., anomaly detection and identification. We demonstrated
CPSLint
’s capabilities with examples, especially the ability to compartmentalise machine data in accordance with system execution phases. The output of
CPSLint
, which is Python code, can be conveniently orchestrated alongside targeted data-centric solutions.

We have also covered many advantages of using a DSL for this type of activity in
Section

5
, such as expressiveness, consistency throughout different implementations, enabling accessibility to experts without programming knowledge.

Future work: Industrial case study

In
Figure

1
, we showcased the high-level sequence of tasks, i.e., machine cycle, for an ITEC die bonder machine. As the essence of machine data collected from industrial CPS sensors is the same, we shall apply
CPSLint
to real ITEC machine data as part of our immediate future work. This will require possible further enhancement of
CPSLint
to consider additional corruptions common to these machines, if any, and to compartmentalise machine data according to ITEC-specific execution phases, which will be achieved by providing
CPSLint
to domain experts.
