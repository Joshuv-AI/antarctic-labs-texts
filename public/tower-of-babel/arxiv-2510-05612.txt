Redefining Cost Estimation in Database Systems: The Role of Execution Plan Features and Machine Learning Conference: ; ; CCS: Information systems Data management systems CCS: Computing methodologies Machine learning approaches
Utsav Pathak, Amit Mankodi

Abstract
. Accurate query runtime prediction is a critical component of effective query optimization in modern database systems. Traditional cost models, such as those used in PostgreSQL, rely on static heuristics that often fail to reflect actual query performance under complex and evolving workloads. This remains an active area of research ( Zhu et al. 2024 ; Li et al. 2024 ) ], with recent work exploring machine learning techniques to replace or augment traditional cost estimators ( Li et al. 2022 ; Siddiqui et al. 2020 ) . In this paper, we present a machine learning-based framework for predicting SQL query runtimes using execution plan features extracted from PostgreSQL ( PostgreSQL Global Development Group 2025c ) . Our approach integrates scalar and structural features from execution plans and semantic representations of SQL queries to train predictive models. We construct an automated pipeline for data collection and feature extraction using parameterized TPC-H queries ( Poess and Floyd 2000 ) , enabling systematic evaluation of multiple modeling techniques. Unlike prior efforts that focus either on cardinality estimation or on synthetic cost metrics, we model the actual runtimes using fine-grained plan statistics and query embeddings derived from execution traces, to improve the model accuracy ( Lan et al. 2021 ) . We compare baseline regressors, a refined XGBoost model, and a sequential LSTM-based model to assess their effectiveness in runtime prediction. Our dataset includes over 1000 queries generated from TPC-H query templates executed in PostgreSQL with EXPLAIN ANALYZE. Experimental results show that the XGBoost model significantly outperforms others, achieving a mean squared error of 0.3002 and prediction accuracy within ±10% of the true runtime in over 65% of cases. The findings highlight the potential of tree-based learning combined with execution plan features for improving cost estimation in query optimizers. Our work contributes a reproducible, extensible framework and provides insights into model selection for integrating learned predictions into real-world database systems.



1.
Introduction

Modern data-driven applications—from business analytics and finance to e-commerce and cloud computing—depend heavily on efficient database systems to ensure responsiveness and scalability
(
Silberschatz et al. 2019
)
. At the core of this efficiency lies the database query optimizer, which is responsible for generating execution plans that minimize query runtime
(
Stonebraker and Rowe 1986
)
. A key component of this optimization is the cost model, which estimates the execution time and resource usage of alternative plans. However, traditional cost models, such as those used in PostgreSQL
(
PostgreSQL Global Development Group 2025b
)
, are heuristic-driven and often inaccurate, especially when applied to complex queries, skewed data distributions, or evolving workloads
(
Lan et al. 2021
)
.

These inaccuracies lead to suboptimal plan choices, resulting in increased latency, poor resource utilization, and missed service-level objectives. To address these limitations, recent research has proposed machine learning (ML)-based techniques that learn from past query executions and predict query performance more accurately than static estimators
(
Hastie et al. 2009
;
Siddiqui et al. 2020
)
. While cardinality estimation has seen significant progress using ML
(
Malik et al. 2007
;
Zhang et al. 2023
)
, relatively fewer works focus on direct query runtime prediction. Some models estimate runtime based on simplified or synthetic cost functions
(
Li et al. 2022
)
, while others rely solely on cardinality as a proxy. These approaches often ignore structural details of the execution plan or fail to incorporate real execution statistics—issues we revisit in Section
8
.

In this paper, we present a data-driven approach for predicting SQL query runtimes in PostgreSQL using machine learning models trained on execution plan features
(
PostgreSQL Global Development Group 2025c
)
. In contrast to prior work that often targets cardinality estimation or uses handcrafted operator features
(
Gu et al. 2023
)
, our framework directly models total query runtime using real execution traces from PostgreSQL’s
EXPLAIN ANALYZE

(
PostgreSQL Global Development Group 2025a
)
. We integrate scalar features (e.g., rows, cost, and execution time), structural plan properties (e.g., node depth, operator hierarchy), and semantic representations of SQL queries (e.g., TF-IDF embeddings
(
Jones 1972
)
) to enhance model expressiveness.

Our contributions are as follows:

•

We develop an automated system that collects a dataset of over 1000 TPC-H queries and their corresponding execution plans and actual runtimes from PostgreSQL using
EXPLAIN ANALYZE

(
Poess and Floyd 2000
;
Transaction Processing Performance Council 2024
)
, covering variations across all 22 TPC-H query templates
(
Transaction Processing Performance Council 2021
)
.

•

We extract and engineer a diverse set of plan-level features, including more than 20 scalar metrics (e.g., estimated/actual rows, total cost, execution time), 6 structural indicators (e.g., depth, parent-child links), and TF-IDF-based semantic vectors representing the SQL query text
(
Jones 1972
)
.

•

We evaluate three modeling approaches: (a) baseline regressors (linear
(
Draper and Smith 1998
)
, SVR
(
Smola and Schölkopf 2004
)
, random forest
(
Breiman 2001
)
), (b) a refined XGBoost model
(
Chen and Guestrin 2016
)
using structural and semantic plan features, and (c) a replicated sequential LSTM model
(
Hochreiter and Schmidhuber 1997
)
inspired by RAAL that treats plan nodes as temporal sequences.

•

We conduct a detailed performance analysis of each model and find that the XGBoost model
(
Chen and Guestrin 2016
)
outperforms others, achieving an MSE of 0.3002 and ±10% prediction accuracy in over 65% of cases. The LSTM model
(
Hochreiter and Schmidhuber 1997
)
underperforms due to limited data and architectural constraints.

2.
Background and Motivation

Accurate query cost estimation is fundamental to database performance optimization
(
Silberschatz et al. 2019
)
. Traditional cost models, such as those in PostgreSQL
(
PostgreSQL Global Development Group 2025b
;
Stonebraker and Rowe 1986
)
, use fixed heuristics and precomputed statistics to estimate the cost of query plans. These methods, while computationally lightweight, often yield inaccurate estimates—particularly in the presence of complex joins, skewed or correlated data, and modern, evolving workloads
(
Lan et al. 2021
)
. PostgreSQL’s cost-based optimizer, for instance, assumes uniform data distributions and independence among attributes, which rarely hold in practice
(
PostgreSQL Global Development Group 2025a
)
. This can mislead the query planner into choosing suboptimal plans, resulting in longer runtimes, inefficient resource usage, and SLA violations in latency-sensitive applications. Although recent research has explored ML-based alternatives
(
Hastie et al. 2009
;
Siddiqui et al. 2020
)
, many focus primarily on cardinality estimation
(
Malik et al. 2007
;
Zhang et al. 2023
)
or optimizer feedback
(
Gu et al. 2023
)
, with fewer studies directly targeting query runtime prediction using real execution plan features
(
Li et al. 2022
)
.

In this work, we pose the problem of learned query runtime prediction in PostgreSQL as a supervised learning task over real execution traces
(
PostgreSQL Global Development Group 2025c
)
, with the goal of producing accurate, generalizable, and interpretable models. Our motivation is grounded in the following research questions:

•

RQ1: Can real execution traces from PostgreSQL be effectively leveraged to learn predictive models for total query runtime?

PostgreSQL’s
EXPLAIN ANALYZE
output provides rich operator-level information, including actual runtimes, estimated and actual rows, and plan hierarchies
(
PostgreSQL Global Development Group 2025c
;
Lubaczewski 2025
)
. We hypothesize that these statistics can serve as reliable supervision signals for runtime learning.

•

RQ2: How do different categories of features—scalar, structural, and semantic—contribute to the accuracy of learned cost models?

Execution plans form hierarchical trees of operators. Capturing scalar metrics alone may miss critical structural or contextual patterns
(
Dalibo 2025
)
. We explore whether incorporating these multi-level features improves prediction quality.

•

RQ3: Which types of ML models are most effective for learned runtime prediction in low-data regimes?

While deep models such as LSTMs
(
Hochreiter and Schmidhuber 1997
)
offer expressive power, they often require substantial training data. We examine how well simpler models like tree-based regressors
(
Breiman 2001
;
Chen and Guestrin 2016
)
perform relative to deep models under practical dataset sizes.

•

RQ4: Can semantic understanding the queries improve the accurancy of the prediction model?

By introducing semantic understanding features from query text
(
Jones 1972
;
Reimers and Gurevych 2019
)
in addition to execution plan features, we evaluate the performance of the prediction model.

These questions form the foundation for our system design and evaluation, motivating the architecture we present in the next section.

3.
Our Methodology

Figure 1
.
Overview of Our Methodology

This section describes the architecture of our end-to-end framework for learning query runtime prediction models using PostgreSQL
(
PostgreSQL Global Development Group 2025b
)
and the TPC-H benchmark
(
Poess and Floyd 2000
)
. The system automates the entire pipeline—from query generation and execution to feature extraction and model training—enabling systematic experimentation and evaluation. It is organized into five key stages: query generation, query execution and feature extraction, data preprocessing, and model training. Figure
1
shows the overview of our methodology.

3.1.
Query Generation

We construct our workload using the TPC-H benchmark, which consists of 22 analytical query templates designed for decision support
(
Transaction Processing Performance Council 2021
;
Transaction Processing Performance Council 2024
)
. To generate a diverse set of queries, we systematically vary template parameters such as date ranges, region filters, and numeric thresholds. This produces a broad spectrum of queries that differ semantically while preserving structural patterns, resulting in over 1000 unique SQL queries executed against a PostgreSQL instance
(
PostgreSQL Global Development Group 2025b
)
.

3.2.
Query Execution and Feature Extraction

Each query is executed with
EXPLAIN ANALYZE
enabled to capture real execution plans
(
PostgreSQL Global Development Group 2025c
;
PostgreSQL Global Development Group 2025a
)
. We automate this process via a shell script (
run_all.sh
) that logs each query and its corresponding plan output in JSON format. From these plans, we extract structured features across three main categories:

•

Scalar Features:
Estimated and actual row counts, total cost, startup cost, and execution time
(
Lubaczewski 2025
)
.

•

Structural Features:
Properties such as plan node type, depth in the tree, and parent-child relationships
(
Dalibo 2025
)
.

•

Semantic Features:
Dense query representations generated using the
all-MiniLM-L6-v2
transformer model
(
Reimers and Gurevych 2019
)
, capturing contextual semantics of the SQL text and enhancing the model’s ability to differentiate between similar plan structures arising from semantically different queries.

Each plan is decomposed into its constituent nodes, and the resulting feature vectors are compiled into a structured CSV file, where each row corresponds to a plan node associated with its parent query
(
Wikipedia contributors 2025
)
.

3.3.
Data Preprocessing

Before model training, we encode categorical fields (e.g., node type) using label encoding or one-hot encoding
(
Pedregosa et al. 2011
)
. Derived features such as cardinality ratios (actual vs. estimated rows) and normalized costs are also computed to improve predictive signal
(
Malik et al. 2007
)
. Missing values are handled using filtering or imputation strategies. Semantic features are generated using TF-IDF over the corpus of SQL queries
(
Jones 1972
)
, enabling integration into hybrid learning models.

3.4.
Modeling Pipeline

The final stage involves training machine learning models on the processed dataset
(
Hastie et al. 2009
)
. We implement several model families:

•

Baseline Regressors:
Including linear regression
(
Draper and Smith 1998
)
, support vector regression (SVR)
(
Smola and Schölkopf 2004
)
, and random forest regressors
(
Breiman 2001
)
.

•

XGBoost Model:
A refined gradient-boosted tree ensemble that incorporates both structural and semantic features
(
Chen and Guestrin 2016
)
.

•

Sequential LSTM Model:
A simplified implementation of RAAL, treating the plan as a sequence of node vectors to learn temporal dependencies
(
Hochreiter and Schmidhuber 1997
)
.

Each model is trained to predict the total query runtime given node- and query-level features. The modular design of our system allows controlled experimentation with alternative features and architectures, supporting reproducibility and extensibility for future research.

4.1.

Scalar features capture node-level numeric information as reported by PostgreSQL’s
EXPLAIN ANALYZE

(

;

•

Ratios of actual to estimated rows (cardinality error)

Structural Features

To capture hierarchical execution flow, we extract structural features from the plan tree
(
Dalibo 2025
)
:

•

Node Depth:
Position of the node in the tree hierarchy.

•

Parent-Child Relationships:
Useful for modeling the execution order and plan shape.

•

Subtree Cardinality:
Number of descendant nodes, indicating computational depth.

•

Node Type:
Encoded operator labels (e.g., Seq Scan, Hash Join, Nested Loop).

These features encode the execution strategy and flow, enabling tree-based models to reason about operator placement and execution dependencies
(
Breiman 2001
;
Chen and Guestrin 2016
)
.

Beyond plan structure, we capture query-level semantics to embed the high-level intent of the SQL query

•

Query text Embeddings:
Each query is encoded using dense semantic embeddings derived from the
all-MiniLM-L6-v2
transformer model
(
Reimers and Gurevych 2019
)
. These representations capture the contextual meaning of the entire SQL query rather than relying on traditional token frequency statistics.

•

Plan-Level Aggregations:
Aggregated representations across plan nodes are used in hybrid models to capture global structure.

4.4.
Feature Encoding and Normalization

Categorical variables (e.g., node type, join strategy) are encoded using one-hot or label encoding depending on model requirements
(
Pedregosa et al. 2011
)
. Numeric features are normalized via z-score standardization or min-max scaling. Sparse or missing values are handled through imputation or filtering based on threshold-based rules. These steps ensure feature consistency and gradient stability during training
(
Hastie et al. 2009
)
.

By combining scalar execution signals, hierarchical structural properties, and SQL-level semantics, our feature engineering approach provides a robust and expressive representation of query plans, which drives the performance of the models discussed in subsequent sections.

5.
Modeling Approaches

In this section, we present the machine learning models used for query runtime prediction
(
Hastie et al. 2009
)
. Our objective is to learn a mapping from engineered plan features to accurate predictions of total query execution time. We explore a range of models—starting from classical regressors to advanced architectures—that leverage both structural and semantic information.

5.1.
Training and Evaluation

All models are trained using the same dataset comprising over 1000 TPC-H query instances
(
Poess and Floyd 2000
;
Transaction Processing Performance Council 2024
)
, with an 80-20 train-test split. We evaluate performance using three metrics:

•

Mean Squared Error (MSE):
Captures the average squared difference between predicted and actual runtimes:

\text{MSE}=\frac{1}{n}\sum_{i=1}^{n}(y_{i}-\hat{y}_{i})^{2}

where
y_{i}
is the true runtime and
\hat{y}_{i}
is the predicted runtime. MSE penalizes larger errors more heavily
(
Draper and Smith 1998
)
.

•

R-squared (R²):
Measures the proportion of variance in the actual runtimes explained by the model:

R^{2}=1-\frac{\sum_{i=1}^{n}(y_{i}-\hat{y}_{i})^{2}}{\sum_{i=1}^{n}(y_{i}-\bar{y})^{2}}

where
\bar{y}
is the mean of actual runtimes. Higher R² indicates better model fit
(
Draper and Smith 1998
)
.

•

Accuracy within ±10%:
The percentage of predictions where the relative error is within ±10

\text{Accuracy}_{10\%}=\frac{1}{n}\sum_{i=1}^{n}\mathbb{I}\left[\frac{|y_{i}-\hat{y}_{i}|}{y_{i}}\leq 0.1\right]\times 100

This metric offers an interpretable benchmark of model precision in a real-world scenario.

These metrics provide a balanced view of model quality—covering both statistical performance (MSE, R²) and practical prediction fidelity (±10% accuracy). Hyperparameters are tuned using grid search or validation splits
(
Pedregosa et al. 2011
)
.

5.2.
Baseline Models

We begin with a set of standard regression models that serve as baselines:

•

Linear Regression:
A simple model assuming a linear relationship between input features and runtime. It provides interpretability but often underperforms on non-linear data
(
Draper and Smith 1998
)
.

•

Support Vector Regression (SVR):
Utilizes a radial basis function kernel to capture non-linear relationships. While effective, SVR can be computationally expensive for large feature sets
(
Smola and Schölkopf 2004
)
.

•

Random Forest Regression:
An ensemble of decision trees trained on feature subsets. It is robust to overfitting and captures feature interactions, though it may struggle with capturing plan-wide dependencies
(
Breiman 2001
)
.

These models provide a useful reference point to evaluate the benefits of more expressive learning architectures.

5.3.
XGBoost with Plan Features and Query Text Embeddings

We implement a refined model using XGBoost, a tree-based gradient boosting algorithm well-suited for tabular regression problems
(
Chen and Guestrin 2016
)
. Our XGBoost model integrates three categories of input features:

•

Scalar Plan Features:
Including both estimated (e.g., cost, rows) and actual metrics (e.g., execution time, loops)
(
PostgreSQL Global Development Group 2025c
)
.

•

Structural Features:
Such as node depth, parent-child relationships, and node types
(
Dalibo 2025
)
.

•

Query Text Embeddings:
Sentence-level vector representations derived from SQL text using the
all-MiniLM-L6-v2
transformer model
(
Reimers and Gurevych 2019
)
. These embeddings capture the semantic and syntactic nuances of the query beyond surface-level token patterns
(
Jones 1972
)
.

XGBoost’s ability to handle heterogeneous inputs and model complex interactions makes it ideal for capturing both local and global signals from execution plans.

5.4.
LSTM-Based Sequential Model

To explore deep learning for plan modeling, we replicate a simplified version of the Resource-Aware Attentional LSTM (RAAL)
(
Li et al. 2022
;
Hochreiter and Schmidhuber 1997
)
. In our version, each execution plan is flattened into a sequence of node feature vectors, which are passed through a stacked LSTM followed by dense layers to regress total runtime.

Due to limited dataset size and the absence of resource usage tracking (as required by RAAL), we omit the attention mechanism and resource-aware components. Nevertheless, the model serves as a benchmark for evaluating the viability of sequence models in capturing temporal and hierarchical plan patterns
(
Hochreiter and Schmidhuber 1997
)
.

6.7.
Summary

These results validate the effectiveness of hybrid tree-based models for query runtime prediction in PostgreSQL
(
PostgreSQL Global Development Group 2025b
)
