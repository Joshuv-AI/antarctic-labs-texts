SciML Agents: Write the Solver, Not the Solution
Saarth Gaonkar, Xiang Zheng, Haocheng Xi, Rishabh Tiwari, Kurt Keutzer, Dmitriy Morozov, Michael W. Mahoney, Amir Gholami

Abstract
A large body of recent work in scientific machine learning (SciML) aims to tackle scientific tasks directly by predicting target values with neural networks (e.g., physics-informed neural networks, neural ODEs, neural operators, etc.), but attaining high accuracy and robustness has been challenging. We explore an alternative view: use large language models (LLMs) to write code that leverages decades of numerical algorithms. This shifts the burden from learning a solution function to making domain-aware numerical choices. We ask whether LLMs can act as SciML agents that, given a natural-language ODE description, generate runnable code that is scientifically appropriate —selecting suitable solvers (stiff vs. non-stiff), setting tolerances, and enforcing stability checks. There is currently no benchmark to measure this kind of capability for scientific computing tasks. As such, we first introduce two new datasets: a diagnostic dataset of adversarial “misleading” problems; and a large-scale benchmark of 1,000 diverse ODE tasks. The diagnostic set contains problems whose superficial appearance suggests stiffness, and that require algebraic simplification to demonstrate non-stiffness; and the large-scale benchmark spans stiff and non-stiff ODE regimes. We evaluate open- and closed-source LLM models along two axes: (i) unguided versus guided prompting with domain-specific knowledge; and (ii) off-the-shelf versus fine-tuned variants. Our evaluation measures both executability and numerical validity against reference solutions. We find that with sufficient context and guided prompts, newer instruction-following models achieve high accuracy on both criteria. In many cases, recent open-source systems (e.g., the Qwen3 family) perform strongly without fine-tuning, while older or smaller models still benefit from fine-tuning. Overall, our preliminary results indicate that careful prompting and fine-tuning can yield a specialized LLM agent capable of reliably solving simple ODE problems. We have open-sourced the code and benchmark at https://github.com/SqueezeAILab/sciml-agent .

By contrast, decades of numerical analysis offer robust algorithms for scientific computing problems.
This raises a natural question: instead of predicting target values directly, why not use AI models to write code that leverages established numerical solvers?

This direction builds on the rapid progress of large language models (LLMs) in reasoning and code generation. General-purpose coding agents (e.g., IDE-integrated assistants) have excelled at code correctness, but not necessarily at domain-appropriate numerical choices. We therefore ask: given a natural-language description of a physical system, e.g., governed by an Ordinary Differential Equation (ODE)
10.5555/153158
, can an LLM generate code that not only compiles correctly and runs, but is also
scientifically appropriate
? If so, LLMs can serve as a bridge from problem descriptions to mature numerical solvers, yielding accurate solutions via principled computation.

While general-purpose coding assistants are becoming commonplace, scientific coding demands much more than syntactic correctness.
It requires domain-aware, numerically appropriate design choices.
Examples include selecting the right solver for a stiff versus non-stiff problem, setting sensible error tolerances, and ensuring the stability of the solution.
An incorrect choice can yield a scientifically invalid result, even if the code executes without error.

Prior work on general-purpose coding agents have largely focused on algorithmic correctness and passing unit tests.
However, scientific computing tasks have nuanced requirements of numerical suitability and appropriate algorithmic choices that depend on the problem structure.
As such, a significant gap exists in the evaluation of LLMs for scientific code generation.
In particular, there is currently no standard benchmark designed to systematically measure the scientific validity of LLM-generated code for solving ODEs.
This leaves it unclear how robustly these models can reason about the underlying mathematical properties of a problem to select an optimal solution strategy.

In this work, we address this gap through the following contributions.

•

Robustness Evaluation of Symbolic Reasoning.

We design adversarial,
misleading
ODEs whose superficial form suggests stiffness, but which algebraically simplifies to a non-stiff ODE. The task probes whether models perform genuine symbolic reduction rather than pattern matching, and whether they choose explicit methods when appropriate. We find that while older models struggle more with these examples, newer models demonstrate strong “reasoning” capabilities. In addition, we observe that providing the model with a guided prompt can significantly boost performance. See Section
3.2.1
for details.

•

ODE-1000 Benchmark.

To evaluate scientific code generation capability of these models, we create the ODE-1000 benchmark, comprising 1,000 diverse ODE problems. We evaluate the performance by (i) checking if the generated code compiles correctly, and (ii) computing the resulting error of the final numerical solution against the ground truth. See Section
3.2.2
for details.

•

Prompting vs. Fine-Tuning.

Using the ODE-1000 dataset,
we conduct a detailed empirical analysis across a wide range of open- and closed-source LLMs.
In particular, we evaluate the code generation quality by considering several scenarios: (i) zero-shot/bare minimum prompt, (ii) guided prompt, and (iii) fine-tuned models.
We find that with careful guidance, LLMs can act as practical and reliable SciML agents for a wide range of simple ODE tasks.
Newer, larger models are particularly adept at this, often achieving high accuracy with prompting alone, while smaller models still benefit significantly from fine-tuning.
See Section
5
for details.

These preliminary results establish initial evidence that careful prompting and targeted fine-tuning can yield practical
SciML coding agents
for simple ODE problems, and that they can provide a foundation for evaluating scientific code generation beyond syntactic correctness.

3
Problem Setup

In this section, we first describe the problem formulation and then the two benchmark datasets that are used to evaluate the scientific code generation capability of the LLMs.

3.1
Task Definition

We focus mainly on the following task: given a natural-language description of a physical or mathematical system governed by an ODE, how can we make an LLM generate a complete and executable Python program that can numerically solve the ODE?

A successful LLM output should (of course) return executable code, correct parameters, and a relatively low numerical error.
However, the code should also be “scientifically appropriate,” e.g., meaning that the LLM should demonstrate an understanding of the underlying mathematical properties of the ODE to make informed design decisions.
Here are examples of key factors to consider.

•

Solver Selection.
An appropriate numerical solver must be chosen (e.g., an explicit Runge-Kutta method for non-stiff problems versus an implicit method like BDF for stiff problems).

•

Code Execution.
Executable and correct Python code must be generated to solve the ODE problem, setting sensible parameters, such as time intervals and step sizes.

•

Numerical Validity.
The final solution produced by the code must achieve a low numerical error, when compared against a high-fidelity ground-truth or analytical solution.

3.2
Benchmark datasets

A significant challenge we faced in evaluating LLMs for scientific tasks is the lack of benchmarks that explicitly account for the numerical and mathematical nuances required in scientific computation.
Existing code generation datasets primarily emphasize algorithmic correctness and passing unit tests, but they do not capture the scientific validity/accuracy of the final solution. This is particularly problematic because for scientific computing problems there are many syntactically valid arguments and solvers that could be used, but only relatively few will lead to accurate solutions.

To address this gap, we first introduce a benchmark suite composed of two novel datasets.
First, we present a specialized Diagnostic Dataset that contains problems that are intentionally “misleading” to probe the LLM’s ability for deeper mathematical reasoning, rather than solely relying on superficial pattern matching.
Second, we present a large-scale dataset of 1,000 diverse ODE problems derived from natural-language descriptions, designed to test the end-to-end task of generating complete and numerically accurate solver code.

3.2.1
Symbolic-Equivalence Diagnostic Dataset

In numerical ODE integration,
explicit
solvers advance the state directly from the current value.
They are simple and efficient, but they can become unstable on stiff systems.
In contrast,
implicit
solvers require solving for the unknown future state.
They are typically more stable (though costlier), making them preferable for stiff or constrained dynamics.
In practice, scientific computing experts first assess whether a problem is stiff, which then strongly influences their solver choice.

Here, we test whether current LLMs can correctly classify ODEs as stiff or non-stiff, an essential step for choosing the
right
algorithm when generating code, and whether they rely on superficial cues (e.g., large coefficients) or perform nontrivial symbolic reasoning.

Dataset Construction.

The Diagnostic Dataset comprises three subsets that appear
stiff
before simplification, but that reduce to non-stiff forms: a trigonometric subset, an inverse function subset, and an algebraic subset, described as follows.

1.

Trigonometric subset
uses trigonometric identities, such as
\sin(t+\pi/2)+\cos t=0
, to simplify the equation.

2.

Inverse-function subset
uses inverse operators collapse, such as
\arcsin(\sin t)=t
on
[-\pi/2,\pi/2]
, to simplify the equation.

3.

Algebraic subset
uses expansions/factorizations, such as
(x+1)^{3}-6(x^{2}+1)-(x-1)^{3}=0
, that remove large coefficients after simplification.

In each case, the coefficients appear large, but they can be simplified through mathematical identities.
Consequently, the correct choice is always an explicit method.
We report accuracy as the proportion of instances for which the model selects an explicit solver. This setup probes basic symbolic reduction capability, rather than more simple pattern matching, by the LLM.

3.2.2
ODE-1000 Dataset

Overview.

The ODE-1000 dataset is a curated dataset consisting of 1,000 ODE problems paired with executable Python solutions.
The dataset is designed to evaluate the ability of LLMs to derive a correct ODE and problem setup from a natural-language description, and to produce syntactically valid, numerically stable solver code with an appropriate method choice (e.g., implicit vs. explicit solver).
Below, we describe the generation pipeline, example structure, and coverage.

Generation.

We synthesize candidate problems with GPT 4.1 (prompt templates in Appendix
A
) by letting the model (1) derive the ODE from a realistic scenario, where the description is
natural language

The prompt is designed to enforce
diversity
across: stiff vs. non-stiff dynamics, orders, time intervals, magnitudes and signs of coefficients, and solver coverage.
The target distribution is visualized in Figure

4
SciML Agent Setup: Models, Prompting, and Fine-Tuning

To evaluate the capabilities of LLMs as scientific computing agents for solving ODEs, we consider a diverse range of open/closed-source models, two distinct prompting strategies to analyze the impact of guidance, and a fine-tuning recipe to enhance the performance of small models.

4.1
Models

Our evaluation includes a wide array of both
open- and closed-source LLM families
, to ensure broad coverage of the current LLM landscape.
Open-source models we tested include the Llama series (Llama2, Llama3, Llama3.1) and the Qwen series (Qwen1, Qwen1.5, Qwen2, Qwen2.5, Qwen3). For a closed-source model, we tested OpenAI’s GPT-4.1.

We investigated a wide range of
model sizes
, from small models like Qwen3-0.6B to large-scale models such as Llama3.1-405B, to analyze the correlation between parameter count and scientific reasoning ability.
We also consider model
vintage
, distinguishing between “older” models (released in 2023–2024) and “newer” instruction-following models (from 2025).
This allows us to track the evolution of reasoning and instruction-following capabilities over successive generations.

4.2
Prompting Methods

While pretrained language models possess strong symbolic capabilities, we observe that these abilities often remain underutilized in zero-shot settings, at least without a proper prompting structure.
To explore this, we assess model performance under two different prompting methodologies to understand the effect of contextual guidance.

•

Unguided Prompt.
This prompt provides only minimal instructions. For the diagnostic tasks, it simply asks the model to classify an ODE and choose a solver. This regime is designed to test the model’s out-of-the-box reasoning ability.

•

Guided Prompt.
In contrast, this prompt is engineered to provide substantial guidance. It explicitly instructs the model to perform step-by-step reasoning, simplify expressions algebraically, and analyze coefficient behavior before arriving at a solution. The prompt enriches the model’s decision-making process by embedding domain-specific heuristics.

Details on these two prompts can be found in Appendix
C
.

4.3
Fine-Tuning

While newer, larger models often perform well with guided prompting, fine-tuning can be essential for improving the reliability of smaller models. We employ a supervised fine-tuning (SFT) approach to create specialized ODE-solving agents.

•

Training Data.
The training data is derived from our
ODE-1000 benchmark
. We use 900 examples for training and reserve the remaining 100 for testing. For the Qwen models, the fine-tuning data included the intermediate reasoning traces to better leverage their native reasoning capabilities, whereas for the Llama models, only the final Python code was used.

•

Settings.
We performed
full parameter fine-tuning
rather than a parameter-efficient method like LoRA. Models were trained for 3 epochs across 8 GPUs.

5.2
ODE Dataset Evaluation

5.2.1
Evaluation Criteria

We test model performance on the ODE-1000 dataset using three main metrics.

•

Code execution rate.
We measure the proportion of times the code successfully compiles and runs end-to-end in a sandbox.

•

Accuracy.
Among the examples in which the code runs successfully, the accuracy is defined as the fraction of instances in which the relative error
L_{2}
with respect to the ground truth (SymPy closed-form solution) is less than 0.01.

•

Mean relative
L_{2}
error.
We also calculate the mean relative error of the code outputted by the model with respect to the ground truth, where we clamp to 1 to alleviate the effect of extreme outliers.

6
Conclusion and Future Work

We asked whether LLMs can serve as
SciML agents
that translate natural-language ODE descriptions into runnable,
scientifically appropriate
code. To study this, we introduced two benchmarks: a Symbolic-Equivalence diagnostic suite that probes algebraic simplification and solver choice, and
ODE-1000
, a large-scale collection of diverse problems. Our evaluation, measuring both
executability
and
numerical validity
against reference solutions, shows that careful guidance substantially improves performance: newer instruction-following models often achieve high accuracy with domain-aware prompting, while smaller or older models benefit markedly from fine-tuning. Together, these results indicate a practical path to specialized LLM agents that leverage mature numerical solvers rather than predicting solutions directly, and they establish a foundation for assessing scientific code generation beyond syntactic correctness.

Limitations and future work.

Our study targets simple ODE settings; extending to richer regimes is an immediate next step. We plan to broaden the benchmarks to include systems with event handling and time-varying stiffness, multi-dimensional and higher-order dynamics, chaotic and stiff regimes with sharper diagnostics, boundary-value and parameter-estimation tasks, and ultimately PDEs. Methodologically, we aim to strengthen agent tooling (e.g., symbolic simplification and stability checks), incorporate property-based tests and invariants, and examine cross-library generalization. These directions will help stress-test scientific appropriateness, reliability, and robustness at scale.

Appendix F
Failure Cases from Pattern Matching

In this section, we present reasoning traces showing how GPT-4.1 falls into pattern matching when determining the stiffness of ODEs across the trigonometric, inverse function, and algebraic subsets. We also include some successful cases in which large language models perform the correct mathematical reasoning and arrive at the correct result.

F.1
Trigonometric Subset

1. Failed Case

•

ODE example
: dy/dt = (50000*(cos(2*t) - 2*cos(t)**2 + 1))*y + sin(2*t),

•

Traces of Failed Reasoning
: This ODE has the derivative term dy/dt involving a large coefficient (50000) multiplied by y and trigonometric functions of t. Such a large coefficient creates rapid changes in y with respect to t and leads to the presence of both fast and slow dynamics. This multiscale behavior is characteristic of stiff ODEs, where explicit methods would require extremely small timesteps for stability, making them inefficient. Therefore, an implicit solver is more appropriate.

2. Successful Case

•

ODE example
: dy/dt = (20000*(sin(t)**2 + cos(t)**2) - 20000)*y + cos(t),

•

Traces of Successful Reasoning
: The ODE simplifies
(sin(t)^{2}+cos(t)^{2}=1)
, so dy/dt = (20000*1 - 20000)*y + cos(t) = cos(t). This reduces to dy/dt = cos(t), a very simple, non-stiff ODE with no dependence on the large coefficient (since it cancels out). There are no rapidly decaying or strongly coupled components in the equation; the solution is smooth and varies on the scale of cos(t), not 20000. Therefore, stiffness is not an issue.

F.2
Inverse Function Subset

1. Failed Case

•

ODE example
: dy/dt = (4e7 * (sin(arcsin(t/2)) - t/2))*y + exp(t),

•

Domain
: t
\in
[0, 1],

•

Traces of Failed Reasoning
: The ODE’s coefficient of y contains a large constant factor (4e7) that multiplies a function of t, which can lead to very rapid changes in the solution (potentially large negative or positive eigenvalues in the Jacobian). This is characteristic of stiff ODEs, as explicit methods may require prohibitively small step sizes for stability over even a short interval. Thus, an implicit solver is appropriate.

2. Successful Case

•

ODE example
: dy/dt = (1e7 * log(exp(t + 1)) - 1e7 * (t + 1))*y + cos(t),

•

Domain
: t
\in
[0, 1],

•

Traces of Successful Reasoning
: The log(exp(t + 1)) term equals t + 1, so 1e7 * log(exp(t + 1)) - 1e7 * (t + 1) cancels to 0. The Jacobian with respect to y is 0, so there are no stiff eigenvalues and the system is not stiff. Only the cos(t) term remains, thus an explicit solver is appropriate.

F.3
Algebraic Subset

1. Failed Case

•

ODE example
: dy/dt = ((t-5)**4 - t**4 + 20*t**3 - 150*t**2 + 500*t - 625)*y + sqrt(t+3),

•

Traces of Failed Reasoning
: To determine stiffness, let’s analyze the ODE
dy/dt=((t-5)^{4}-t^{4}+20*t^{3}-150*t^{2}+500*t-625)*y+sqrt(t+3)
. The right side shows linear dependence on y with a time-varying coefficient
P(t)=(t-5)^{4}-t^{4}+20t^{3}-150t^{2}+500t-625
. We should check for stiffness by looking for rapidly changing or large negative real parts in the eigenvalue (which, for linear scalar ODEs, is just P(t)). Evaluating P(t) at the endpoints: P(0) = 625, P(5) = (-625) + (2500) - (3750) + (2500) - (750) - (625) = large negative value. So, P(t) varies from positive to large negative within a short interval, potentially becoming very large in magnitude. Such large coefficients can make the ODE stiff, as the solution can rapidly decay or grow depending on sign and magnitude, and explicit solvers may need exceedingly small timesteps for stability.

2. Successful Case

•

ODE example
: dy/dt = ((t+5)**3 - t**3 - 15*t**2 - 75*t - 125)*y + sqrt(t+2),

•

Traces of Successful Reasoning
: To assess stiffness, examine the ODE’s right-hand side:
dy/dt=((t+5)^{3}-t^{3}-15t^{2}-75t-125)*y+sqrt(t+2)
. The coefficient of y simplifies as follows:
(t+5)^{3}-t^{3}-15t^{2}-75t-125=(t^{3}+15t^{2}+75t+125)-t^{3}-15t^{2}-75t-125=0
. Therefore, dy/dt = sqrt(t+2). This is a simple function of t, and there is no y dependency beyond the initial value; thus, the ODE is not stiff. Its explicit integration is straightforward and does not require an implicit solver.
