SceneGenAgent: Precise Industrial Scene Generation with Coding Agent
Xiao Xia, Dan Zhang, Zibo Liao, Zhenyu Hou, Tianrui Sun, Jing Li, Fu Ling, Yuxiao Dong

Abstract
The modeling of industrial scenes is essential for simulations in industrial manufacturing. While large language models (LLMs) have shown significant progress in generating general 3D scenes from textual descriptions, generating industrial scenes with LLMs poses a unique challenge due to their demand for precise measurements and positioning, requiring complex planning over spatial arrangement. To address this challenge, we introduce SceneGenAgent , an LLM-based agent for generating industrial scenes through C# code. SceneGenAgent ensures precise layout planning through a structured and calculable format, layout verification, and iterative refinement to meet the quantitative requirements of industrial scenarios. Experiment results demonstrate that LLMs powered by SceneGenAgent exceed their original performance, reaching up to 81.0% success rate in real-world industrial scene generation tasks and effectively meeting most scene generation requirements. To further enhance accessibility, we construct SceneInstruct , a dataset designed for fine-tuning open-source LLMs to integrate into SceneGenAgent . Experiments show that fine-tuning open-source LLMs on SceneInstruct yields significant performance improvements, with Llama3.1-70B approaching the capabilities of GPT-4o. Our code and data are available at https://github.com/THUDM/SceneGenAgent .

Modeling of Industrial Scenes.

A scene can be represented as a collection of 3D models, denoted as objects
\mathcal{O}
, drawn from an object library.
Each object
o_{i}\in\mathcal{O}
in the scene is characterized by its coordinates
c_{i}
and direction
d_{i}
.
The coordinates specify the object’s location on a two-dimensional plane, where the positive x-axis represents the front and the positive y-axis represents the left.
The direction defines the object’s angle rotated counterclockwise from the positive direction of the x-axis.
The placement of an object,
p_{i}=(o_{i},c_{i},d_{i})
, encapsulates its spatial properties.
The Euclidean distance between two objects must be at least 1 meter to avoid collision.
The set of all objects’ placements
\mathcal{P}=\{p_{i}=(o_{i},c_{i},d_{i})|o_{i}\in\mathcal{O}\}
provides a modeling of the scene.
Given an industrial scene’s description, we aim to identify the objects and their placements to reconstruct the scene.

Code Representation of Industrial Scenes.

We use C# code to leverage Tecnomatix APIs and model industrial scenes.
The code aims to place objects from
\mathcal{O}
according to the predefined placement
\mathcal{P}
.
We restrict the code’s functionality to loading object models and placing objects to streamline API integration.
The first selects and loads the model files of objects according to
\mathcal{O}
, and the second sets coordinates and directions for objects with specifications outlined in
\mathcal{P}
.
The code is run in the Process Simulate software
2
2

2

https://plm.sw.siemens.com/en-US/tecnomatix/products/process-simulate-software/
to render the scene.

Method

This section comprises two parts:
SceneGenAgent
and
SceneInstruct
.
Regarding the first part, we design an agent,
SceneGenAgent
, as shown in Figure
2
, which leverages LLMs to translate the description into scene-modeling code.
In the second part, we synthesize a new dataset
SceneInstruct
to fine-tune open-source LLMs to achieve performance comparable to API-based models.

3.1
SceneGenAgent

We introduce the workflow of an industrial scene-generating agent, which consists of two phases:
Layout Analysis (Agent)
aiming to extract and analyze the scene’s layout and
Code Generation
for generating code using Tecnomatix APIs.

3.1.1
Layout Analysis (Agent)

SceneGenAgent
performs layout analysis to recover the objects
\mathcal{O}
and placements
\mathcal{P}
.
Layout analysis consists of three stages: object retrieval, layout extraction, and placement assignment.

Object retrieval.

SceneGenAgent
identifies the objects in the scene and retrieves the corresponding items from the object library.
The agent executes all the following operations in a single LLM call using the description as input.

First, the agent generates a list of objects that should appear in the scene based on the description.
This list includes ambiguously mentioned objects like “a random object”.
The agent then maps the objects to their counterparts within the library by incorporating the objects from the library and objects found in the description into the LLM’s input context and tasking the LLM to verify the presence of each object in the description within the library.
If an object is not found in the library, the agent attempts to replace it with a similar object from the library that conforms to the description.
In cases where no suitable substitute is available, the agent removes the object.
Consequently, the agent retrieves the object collection
\mathcal{O}=\{o_{i}\}
from the library.
Finally, the agent rewrites the description to reflect the retrieved objects’ layout, replacing the original objects’ names with those of the retrieved ones and retaining solely layout information.
The output of this rewriting is the layout’s concise depiction, denoted as the new description
s
.

Layout extraction.

SceneGenAgent
extracts all layout information from
s
.
We categorize the existing layout information in
s
into two types:

•

Position
, which refers to the positional state of an object, noted as
{\textnormal{p}}=(o_{i},l,d)
, where
o_{i}
denotes the object,
l
the location, and
d
the direction.
Either
l
or
d
must be specified with specific values or general statements.

•

Relation
, which concerns the interactions between two objects, including aspects like distance and relative direction.
This is expressed as
{\textnormal{r}}=(o_{i},o_{j},r)
, where
o_{i}
and
o_{j}
denotes the two objects and
r
their relationship.

r
is a text describing relationships such as adjacency, parallel, surrounding, etc.
Relations involving multiple objects are represented as a series of relations between object pairs, which, accompanied by the description
s
, can be comprehended by the agent.

The existing layout information in
s
can be formalized into two sets
{\mathbb{P}}=\{{\textnormal{p}}\}
and
{\mathbb{R}}=\{{\textnormal{r}}\}
, representing the set of positions and relations respectively.
The agent extracts all layout information with an LLM call, incorporating
s
and
\mathcal{O}
into the input and listing positions and relations in the output.

Placement assignment.

SceneGenAgent
assigns the final placement of every object
\mathcal{P}
based on
{\mathbb{P}}
and
{\mathbb{R}}
and improve
\mathcal{P}
through verification.
Beyond adhering to the description, the assignment must also satisfy supplementary constraints, i.e. the specifications concerning
collisions, to ensure the coherence of the scene.
The agent undertakes the following steps in one LLM call:

1.

Infer placement from
{\mathbb{P}}
: For each position
{\textnormal{p}}=(o_{i},l,d)
, if
c_{i}
or
d_{i}
of
o_{i}
is included in or can be deduced from
l
or
d
, assign
c_{i}
or
d_{i}
to
o_{i}
.

2.

Infer coordinate differences from
{\mathbb{R}}
: Relations
{\textnormal{r}}=(o_{i},o_{j},r)\in{\mathbb{R}}
are viewed as differences in coordinates between two objects.
For instance, the distance between two objects is expressed as the magnitude of their coordinate difference vector.
Rewrite all relations into coordinate differences, forming the set
\Delta=\{(o_{i},o_{j},\delta)|\delta\text{ is rewritten from }r,(o_{i},o_{j},r)\in{\mathbb{R}}\}
, where
\delta
represents vector difference between the coordinates of
o_{i}
and
o_{j}
.

3.

Compute coordinates and directions
: For each coordinate difference
(o_{i},o_{j},\delta)\in\Delta
, if the coordinates of one object are known, compute the other’s coordinates based on
\delta
. For each relation
{\textnormal{r}}=(o_{i},o_{j},r)\in{\mathbb{R}}
, if
r
states that
o_{i}
is oriented towards the
o_{j}
and the coordinates of both objects are known, calculate the direction of
o_{i}
, and vice versa.

4.

Allocate placement to the rest of objects
: Allocate placement to objects whose coordinates or directions have not yet been determined without collision, adhering to the description.

All objects are placed after these steps, forming the initial placement
\mathcal{P}
.

Verification.
The initial placement may contain flaws since the LLM may make common-sense errors or miscalculate values.
Recent studies
(
Shinn et al. 2023
;
Madaan et al. 2024
)
have shown the ability of LLMs to critique their own decisions.
Hence,
SceneGenAgent
iteratively checks
\mathcal{P}
for the following potential errors:
(1) whether the placement violates constraints described in
s
, and
(2) whether any objects collide, measured by the distances between adjacent objects.
If errors are identified, the agent utilizes
{\mathbb{P}}
,
{\mathbb{R}}
,
\mathcal{P}
, and the detected errors as inputs and attempts to fix the errors to generate a new
\mathcal{P}
until no errors are found.

3.1.2
Code Generation

This phase involves writing C# code with Tecnomatix APIs to visualize the layout and model the scene.
We design a code template containing basic code such as initialization and leave the parts responsible for model loading and object placement incomplete for the agent to fill.
Following prior works
(
Zhou et al. 2023
)
that integrate code documentation into the model’s input, we provide
coding guidance
alongside the template to aid the agent in using APIs.
The guidance includes usage guidelines and example code snippets corresponding to APIs.
The agent employs an LLM to
generate code
, integrating
\mathcal{P}
, code template, and coding guidance into the input.

The LLM may produce errors in the generated code, including omitting code or fabricating methods or variables unsupported by Tecnomatix.
The agent conducts a rule-based evaluation by scanning keywords associated with the APIs to assess whether the LLM has correctly implemented the API calls.
The detected invalid code is used as feedback to prompt the LLM to revise the code accordingly.
Once the code passes the check, we run it to
render the industrial scene
.

3.2
SceneInstruct

This section details our efforts in training open-source LLMs to integrate into
SceneGenAgent
.
Inspired by previous research
(
Zeng et al. 2023a
;
Chen et al. 2023
)
fine-tuning LLMs on agent trajectories to enhance their agent abilities, we gather the agent’s trajectory data to build
SceneInstruct
, constructing a collection of industrial scene descriptions and feeding them into the agent with API-based models as its backbone.
Then, we use
SceneInstruct
to fine-tune open-source LLMs.

3.2.1
SceneInstruct
Construction

Instruction Construction.

We construct a description dataset that serves as the agent’s instruction to obtain its behavior trajectory.
We manually write 20 scene descriptions as the initial description pool, encompassing fundamental variations of industrial scenes.
Then, we adopt the Evol-Instruct method
(
Xu et al. 2024
)
to rewrite descriptions iteratively with an LLM, generating diverse variants.
We design 6 rewriting methods based on possible variations of descriptions.
In each iteration, a random description from the current pool and a rewriting method are sampled.
The description is rewritten by Llama3.1-70B
(
Dubey et al. 2024
)
into a new description.
Appendix
A.2
details the rewriting strategies and sampling.

Each new description undergoes verification and deduplication.
Verification detects errors including common-sense mistakes like collision or contradictions between different parts of the description.
An object’s placement might be specified multiple times but its placements derived in these different ways may not match.
The LLM first attempts to compute placements, distances, and relative positions as much as possible based on the description, then examines common-sense errors and conflicts in calculated results.
Deduplication evaluates the similarity between new and existing descriptions with the MinHash
(
Broder 2000
)
algorithm.
The LLM retries rewriting if verification or deduplication fails, and then we add it to the description pool for sampling in later iterations.
The final dataset includes 3002 descriptions, from which we use 95%(2852) for training and the rest for validation.

Trajectory Collection.

After constructing the instructions, we collect the trajectories of
SceneGenAgent
with GPT-4
(
Achiam et al. 2023
)
as the backbone, comprising the inputs and outputs of GPT-4 within the workflow.
We refer to Llama3.1-70B, given its capabilities for instruction following, multi-turn dialogue, and writing C# code, to select which parts of the agent need data collection.
We observe that while it can handle most operations, the performance in assigning placement can be improved.
Therefore, we gather data from this stage, where the LLM should complete three tasks: assign, verify, and reassign placement.
For each description, Llama3.1-70B first completes the agent’s tasks up to extracting layout, then GPT-4 assigns placement and we collect its inputs and outputs.

Data containing inaccuracies is crucial to train the model to be sensitive to errors during placement verification.
Nevertheless, the positions assigned by GPT-4 tend to be classified as correct.
Thus, we add extra data by changing the LLM that assigns placement to the weaker Llama3.1-8B to obtain more data with errors.
We add this data to the existing dataset, forming
SceneInstruct
.

4.3
Ablation Study

We conduct detailed ablation studies to demonstrate the effectiveness of our approach, in addressing key challenges in industrial scene generation, including the precise placement of objects and the limited availability of training data.

4.3.1
Necessity of agent design

We implement a sophisticated agent workflow to detect objects within the scene, assign spatial placements, and verify and adjust them.
To confirm the necessity of this agent design, we test two settings:
(1) obtaining objects and layout in a single LLM call, that is, not adopting the agent methodology,
and (2) omitting verification after assigning placement, simplifying the agent.
In the first case, the LLM should directly identify the objects and layout from the description.
We also add all requirements to the input, including object library and specifications concerning object distance and orientation, to guarantee that the LLM can access the same knowledge as the agent.
The prompt for this call is in Appendix
A.4.2
.
In the second case, we skip verifying placement and directly proceed to code generation.
We evaluate the performance under both settings and compare it with the original
SceneGenAgent
.

We evaluate GPT-4o and both base and fine-tuned versions of Llama3.1-70B.

4.3.2
Influence of data scaling

Due to the limited availability of high-quality, domain-specific data in industrial applications, we investigate the impact of the quantity of training data on performance to explore how much data is needed for scene generation capability
(
Zhang et al. 2024a
;
Zhang et al. 2024b
)
.
We conduct experiments using varying proportions of the original training data and assess the agent’s performance across different data scales.
We retrain LLMs of various sizes on different subsets of
SceneInstruct
with 10%, 20%, 50%, and 90% ratios, and compare the performance to that obtained with the full dataset.

The results are in Figure

.
Smaller models exhibit more significant and stable performance improvements as the data ratio increases.
In contrast, larger models show slower progress, with Llama3.1-70B’s

Related Work

Generating scenes from textual descriptions has broad applicability across various fields such as indoor environments
(
Chang et al. 2017
;
Song et al. 2023
)
, road traffic
(
Kar et al. 2019
;
Tan et al. 2021
)
, and city planning
(
Lipp et al. 2011
;
Qin et al. 2024
)
.
Studies using LLMs to generate 3D scenes introduce various techniques to control scene components.
LayoutGPT
(
Feng et al. 2024
)
, 3D-GPT
(
Sun et al. 2023
)
, and SceneX
(
Zhou et al. 2024a
)
directly generate configurations of the scene, assuming that the LLMs are reliable for accurate arrangement.
Other studies adjust the scene’s spatial layout to better adhere to the text.
LLMR
(
De La Torre et al. 2024
)
relies on validation to refine the LLM’s layout planning.
Some methods treat the layout information in the description as constraints.
SceneCraft
(
Hu et al. 2024
)
models the constraints with learnable scoring functions and optimizes these scores.
Holodeck
(
Yang et al. 2024b
)
employs Depth-First-Search on a relational constraint graph to find a placement that satisfies the constraints.
GALA3D
(
Zhou et al. 2024b
)
expresses the constraints with 3D Gaussian splatting representations to refine the layout.

SceneGenAgent
differentiates from them by regarding layout information as computable and refinable data structures, enabling precise placement through calculation and reasoning.

6
Conclusion

This paper introduces
SceneGenAgent
, an LLM-based agent that automates the precise generation of industrial scenes, translating textual descriptions into C# code using Tecnomatix API.
We propose a layout analysis pipeline within
SceneGenAgent
that ensures accurate spatial positioning and compliance with complex numerical constraints in industrial layouts.

SceneGenAgent
uses a structured, calculable format to represent spatial specifications and infer overall layout planning through computation, iterative verification, and refinement.
Furthermore, we fine-tune open-source LLMs with our constructed dataset
SceneInstruct
to improve their performance in
SceneGenAgent
, approaching the capabilities of API-based models.
We believe that
SceneGenAgent
can significantly enhance the efficiency and accuracy of industrial manufacturing and provide insights for further advancements in the scene generation field.

Limitations

Broader applications.
Our experiments predominantly focus on object assets and textual descriptions within industrial contexts.
However, our proposed method for precise layout generation is not limited to such environments and holds potential for broader application in general scene generation tasks.
Specifically, this method can enhance the quantitative accuracy of generated results across various domains.
We plan to expand this work to more generalized scene generation by incorporating standardized benchmarks and robust evaluation methodologies in the future.

Evaluation methods.
Moreover, due to lacking automated tool suites for industrial software, our evaluation relies on manual evaluation, which is labor-intensive and inherently susceptible to subjective bias.
Future work could explore developing automated evaluation methods to assess the generated scene’s compliance with quantitative constraints, particularly in industrial software applications.

A.1
Necessity of guidance in code generation

During the code generation phase, we provide the LLM with coding guidance related to Tecnomatix APIs.
We assess whether the models require targeted guidance to utilize the APIs.
We experiment by removing the API-specific instructions for object placement and instead instruct the LLMs to write Tecnomatix-based code to set the coordinates and directions of objects, drawing on their inherent knowledge regarding the Tecnomatix framework.
This allows us to evaluate the models’ performance without explicit coding guidance.
We present this prompt for code generation in Appendix
A.4.2
.

We conduct these tests on GPT-4o and Llama3.1-70B without fine-tuning.

All generated code fails to compile without API guidance, yielding 0 in
\text{pass}@1
for both models.

Rather than invoking the correct methods, the models often resort to fabricated methods not supported by Tecnomatix.
This finding reveals that LLMs struggle to produce functional code without framework-specific instruction and validates our approach, emphasizing the necessity of API guidance for generating code.

A.2
Instruction Construction Details in SceneInstruct

During constructing descriptions as instructions in
SceneInstruct
, we devise the following rewriting methods:

•

Object addition/replacement
: Introduce new objects or substitute one or more objects in the description with 2 to 4 objects randomly picked from the object library.

•

Location specification
: Specify the locations of the objects in the description with reasonable coordinate values. We advise the LLM to choose coordinate values greater than -5000 and less than 5000. The distance between objects should be greater than 1 meter.

•

Relation specification
: Specify the relations between two objects mentioned in the description. The relation may include distance, direction, or orientation. We advise the LLM that the distance between objects should be greater than 1 meter and less than 5 meters.

•

Quantity modification
: Adjust the quantity of an object to a value between 3 and 10 if it is not assigned placement or relations.

•

Fuzzy expressions
: Replace precise numerical relations between two objects with more ambiguous or qualitative expressions.
This is to get more data where the agent must set values actively, encouraging the agent to infer values independently.

•

Rephrasing
: Restate the description using alternative wording while retaining its meaning.

A rewriting method is selected following a multinomial distribution in each rewriting iteration.
The sampling probability of each method is
(\frac{5}{24},\frac{6}{24},\frac{6}{24},\frac{1}{24},\frac{5}{24},\frac{1}{24})
, encouraging modifications of objects and layout in the description.
Descriptions are sampled from the description pool with equal probability.
