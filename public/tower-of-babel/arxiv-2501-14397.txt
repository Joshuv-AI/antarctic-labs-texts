Streamlining Plug-and-Charge Authorization for Electric Vehicles with OAuth2 and OIDC
Jonas Primbs, Dustin Kern, Michael Menth, Christoph Krauß

Abstract
The PnC ( PnC ) process defined by ISO 15118 standardizes automated EV ( EV ) charging by enabling automatic installation of credentials and use for authentication between EV and CP ( CP ). However, the current credential installation process is non-uniform, relies on a complex PKI ( PKI ), lacks support for fine-grained authorization parameters, and is not very user-friendly. In this paper, we propose a streamlined approach to the initial charging authorization process by leveraging the OAuth Device Authorization Grant and Rich Authorization Requests. The proposed solution reduces technical complexity, simplifies credential installation, introduces flexible authorization constraints (e.g., time- and cost-based), and facilitates payment through OIDC ( OIDC ). We present a proof-of-concept implementation along with performance evaluations and conduct a symbolic protocol verification using the Tamarin prover. Furthermore, our approach solves the issue of OAuth’s cross-device authorization, making it suitable as a formally proven blueprint in contexts beyond EV charging.

Introduction

The charging of
EV
at public
CP
is currently realized with different systems for user authorization, e.g., RFID cards or charging apps.
To make this process more user-friendly, various protocols have been defined in recent years.
One of the most important developments is the definition of
PnC
based on the ISO 15118 standard
[
1
]
.
With
PnC
, an
EV
can use locally installed credentials, i.e., a certificate and corresponding key pair, to authenticate itself at a
CP
without requiring user interaction.
This
PnC
authentication then serves as the basis for charge authorization and billing.

The
PnC
process, however, requires a complex
PKI
where several backend actors operate individual (sub-)
CA
.
The custom ISO 15118
PKI
and corresponding credential installation processes impose a high level of complexity, which is reflected in the critique of relevant stakeholders
[
2
]
and which means that complexity-reducing measures are important
[
3
]
.
Moreover, relevant parts of the installation process are out-of-scope for ISO 15118.
This resulted in standardization bodies trying to fill the gaps
[
4
]
and in a non-uniform
PnC
installation process which varies based on the combination of
EV
model and
EMSP
(
EMSP
).
Usability for end users should also be simplified when installing contract credentials.

In this paper, we address these issues by proposing a novel method based on OAuth 2 that streamlines the credential installation process for
EV
charging.
Compared to the patchwork of proprietary solutions that are utilized for the current credential management method, OAuth 2 represents a widely accepted and standardized solution.
The proposed approach reduces the complexity of the required infrastructure by reducing the number of required sub-
CA
in the
PKI
.
It simplifies the installation process for drivers with a uniform app-guided process which is independent of
EV
model and
EMSP
and utilizes OAuth’s
RAR
(
RAR
) to increase security by enabling more fine-grained authorizations like limiting the
EV
’s charging periods/costs.
The proposed method can be extended by an
OIDC
-based login with payment providers, as known from the express checkout feature in online stores.
This extension enables drivers to become a customer of the
EMSP
without creating a new account.
The main contributions of the paper can be summarized as follows.

(i)

We analyze the current
EV
charging processes, obtaining a relevant adversary model, as well as security and feasibility requirements with respect to an OAuth-based solution.

(ii)

We design a detailed concept for the application of OAuth methods to
EV
charging under consideration of the respective adversary and requirements.

(iii)

We implement the proposed solution as a proof-of-concept, evaluate it with regard to feasibility, and publish the corresponding source code.

(iv)

We verify the security of the proposed solution using a tool-based formal security verification with the Tamarin prover
[
5
]
and publish the corresponding Tamarin models.

2.2
OAuth 2.0

The OAuth 2 authorization framework is standardized in RFC 6749
[
6
]
.
It is based on the
HTTP
(
HTTP
)
[
7
]
and the
JSON
(
JSON
)
[
8
]
.
The framework enables users to grant their clients, which may be web or native applications, scoped access to
PR
(
PR
) on a
RS
(
RS
).

PR
may be user data or restricted actions; the user is therefore designated as the
RO
(
RO
).

Non-OAuth approaches often use a ’naive’ approach for authentication and authorization, where the user stores the credentials in the client, thereby allowing the client direct access to all
PR
at the
RS
.
In contrast, the OAuth 2 protocol requires the user (
RO
) to log in to an
AS
(
AS
) and subsequently grant the client permission to access a pre-defined set of
PR
, referred to as the scope.
Subsequently, the
AS
issues an
AT
(
AT
) to the client, which enables the client to access the
PR
within the granted scope on the
RS
.
OAuth thus enhances security by limiting client access to the user-granted scope within the user’s account without disclosing credentials to the client.

Device Authorization.

RFC 8628
[
9
]
extends OAuth 2 by a cross-device authorization flow in which the
RO
authorizes a so-called device client, e.g., a streaming service on a smart TV, from a trusted device, e.g., a smartphone.
The flow’s major advantage is that the
RO
does not need to enter any credentials on the client device.
This improves usability because active sessions on the
RO
’s device (the smartphone) can be re-used.
It also improves security because the device client only obtains a scoped access token instead of a full-fledged session identifier.
Figure
3
illustrates the typical cross-device authorization flow.

Figure 3:
OAuth 2 cross-device authorization flow.

First, the device client sends a device authorization request to the
AS
, containing its client ID which was pre-registered by a developer, and the requested scope (1).
The
AS
then registers this request (2), responds with a verification URI, and issues a complex non-guessable device code, and a non-guessable but easily transcribable user code of typically 8 alphanumeric characters (3).
The device client then displays (4) the verification URI typically in form of a QR code and the device code to the
RO
(5).
Then, it starts polling a device access token request from the
AS
periodically (6).

The
RO
then browses the verification URI on a trusted device and enters the displayed user code (7).
Subsequently, the
AS
authenticates the
RO
(8) who then reviews the requested scope to determine whether to grant authorization to the device client (9).
When granted, the
AS
activates the corresponding device code (10).
At the next time, when the device client polls a device access token request with this device code and the corresponding client ID (11), the
AS
generates an access token (12) and issues it in the device access token response (13).
This token contains the authorized scope with a short-term validity period and is signed with
AS
’s private key
K^{-}_{AS}
.

RAR
(
RAR
).

In OAuth 2, scopes are finite, meaning they can, e.g., grant payment authorization in general, but they cannot grant specific transaction limits.
This is because an infinite number of pre-registered scopes would be required to accommodate any given transaction amount.
RFC 9396
[

In the authorization step (9), the

Such authorization details may include, e.g., a transaction limit of $100 per month.

3.1

As the connectivity of modern vehicles increases, so does their potential attack surface

]
.
One relatively new area of vehicle connectivity is that between an

In this e-mobility system, there are several actors and communication protocols, which lead to various potential security threats
[

.
The possible consequences of attacks in the e-mobility sector range from financial damage over privacy violations to safety risks and even power grid stability issues
[

,
14

.

Several papers propose security architectures for the

For example,
[

]
propose the integration of

into ISO 15118 to protect the private billing-relevant data of

and ensure the integrity of an

The authors of
[
19
]
focus on providing end-to-end security of charging data via middleware-based publish/subscribe communication,
[
20
]
looks at long-term non-repudiation, and
[
21
]
offers post-quantum security for
EV
charging.
Various decentralized approaches exist:
[
22
,
23
,
24
]
propose different blockchain-based approaches to

charging and

[
25
,
26
,
27
]
consider

-based methods.
Furthermore, several papers offer privacy enhancements in the
EV
charging context. For instance,
[
28
]
proposes a pseudonym based fast authentication scheme for contactless charging,
[
29
]
designs a homomorphic encryption-based scheme for energy supplier matching, and the solutions presented in
[
30
,
31
,
32
]
all look at the use of

In comparison to related work, this paper provides scientific novelty by proposing an OAuth-based approach to
EV

3.2
OAuth 2

OAuth was combined with EV charging several times.
Henry Gadacz proposed the Online Internet Account Authentication approach
[
33
]
where the driver authorizes payment via Google Pay with OAuth.
Therefore, the driver scans a QR code on the
CP
which initializes an OAuth flow to authorize the
CP
to debit money from the driver’s bank account for the charging process.
This requires the
CP
to implement this payment method, and the driver must trust the
CP
and QR code to not being manipulated.
The driver must repeat this authorization process for every charging process.
In our approach, the driver authorizes the
EV
for
PnC
to debit money from the driver’s bank account once and to pay for any future charging process.
Timpner et al. proposed a smartphone-based registration and key deployment for vehicle-to-cloud communications
[
34
]
to persist a payment authorization for
EV
charging processes.
In their proposal, the driver generates a key pair on a smartphone and requests a signed certificate from a
CA
to deploy this key pair with the issued certificate to the
EV
.
The EV can then authenticate with this certificate to prove authorization to pay for charging with the driver’s bank account.
The approach is not directly compatible with the
PnC
infrastructure, but some basic concepts may also be applied.
However, generating the key pair on a third-party device and then transferring it to the
EV
is a bad design
[
17
,
18
]
.
In our approach, we fix this and implement modern OAuth extensions like the Device Authorization Grant (RFC 8628
[
9
]
) and Rich Authorization Requests (RFC 9396
[
10
]
) to improve the security further.
The Client-Initiated Backchannel Authentication (CIBA) Flow
[
35
]
extends OpenID Connect by the capability of cross-device authentication and is typically used for online banking applications.
Applied to the
EV
charging authorization use case, this would require the user to already have established a side channel from his smartphone to the
EMSP
to receive push notifications.
It will also result in the user logging in with a cross-device flow on the
EV
and authorizing the requested scopes there.
A compromised
EV
could therefore grant itself any preferred scope, which makes the user losing control.
We solve this issue by using OAuth’s cross-device authorization flow (RFC 8628
[
9
]
) instead.
Kasselman et al. proposed a security best current practice draft at IETF
[
36
]
on cross-device flows with OAuth.
However, they only explain common attack vectors with cross-device flows without explicitly suggesting solutions for them.
Instead, they recommend implementers to do formal proof verification of developed concepts before implementing them.
We address this by providing a specific solution by the example of
EV
charging authorization with a formal proof analysis.
The concept may be applied to other applications where the authorized device has displaying capability and a Bluetooth, NFC, or UWB interface, e.g., when authorizing a streaming service on a smart TV.

4
System-/Adversary Model and Requirements

We assume an e-mobility system model with
EV
,
CP
,
CPO
, and
EMSP
as described in
Section

2.1
.
Based on this system model and considering relevant threat analyses from related work (cf.
Section

3.1
), we derive an adversary model to cover realistic threats to the system in the following sub-section.
Afterwards, we define appropriate security and feasibility requirements, which should enable a solution to address the threats considered while achieving a satisfactory level of usability.

4.1
Adversary Model

In this paper, we consider the following kinds of adversaries:

Local Adversary.

We consider a local adversary with physical access to devices, specifically, to
EV
and
CP
which are commonly left unattended in public areas for long periods of time. The adversary can physically tamper with the respective devices and extract or modify any local data unless it is tamper protected.

Network Adversary.

We consider a network hacker according to the commonly used Dolev-Yao model
[
37
]
. That is, an adversary with full control over network traffic who can arbitrarily send, drop, or modify any network data. However, the adversary cannot break cryptographic primitives unless they have access to the respective private keys.

Adversary with Access to Leaked Backend Data.

We consider an adversary with access to leaked backend data, i.e., the users’ payment credentials. Since in the current e-mobility system, the billing-relevant contract credentials of all users are generated by the respective
EMSP
, this is a serious problem. This opens up the unnecessary threat of a large-scale data leak at an
EMSP
, which would give the adversary access to the billing-relevant data of a large number of users.

4.2
Requirements

We define the requirements for security (
RS
) and feasibility (
RF
) as follows:

RS_{1}

Secure credential installation.
Mutual authentication of data sent between
CPS
and
EV
for credential installation must be guaranteed.

RS_{2}

Fine-grained authorization.
The solution must support authorization constraints, e.g., to define expiration times or charge amount limits for an
EV
’s authorization.

RS_{3}

Secure key storage.
Private keys must be generated locally in a secure environment (e.g., an
HSM
in the
EV
) and must never leave it.

RS_{4}

Crypto-agility.
The system must provide a mechanism to update or replace outdated or broken cryptographic algorithms securely.

RS_{5}

Secure charge authorization.
The authenticity of charge authorization requests sent from
EV
to
CP
must be guaranteed.

RS_{6}

Charge data authenticity.
The authenticity of charge data received as attested by the
EV
must be guaranteed towards the
EMSP
.

RF_{1}

Minor overhead.
The system should keep additional communication and computational overhead within the constraints of existing standards.

RF_{2}

Simple integration.

The system should not alter the message flow of existing protocols and only introduce minor changes to message content.

RF_{3}

Improved usability.

The usability of the proposed system should be improved by utilizing widely used standardized solutions.

This section describes the general concept of the proposed protocol which adds new components to the

(i)

OAuth was chosen for its huge popularity in modern identity and access solutions which causes compatibility with existing backend services and a well-known user experience.

7.2
Formal Security Verification

We analyze the security of the proposed protocol in the symbolic model, also called the Dolev-Yao model
[
37
]
. Hereby, the adversary has full control over the network. Additionally, cryptographic primitives are assumed to be perfectly secure, i.e., cannot be broken without knowing the respective private key.
Specifically, the formal security analysis focuses on the authentication properties of the OAuth-based credential installation protocol (

⁢
R

S
1

). Other security requirements are discussed in
Section

7.3
.

The symbolic security verification is performed with the Tamarin prover
[
5
]
.
Tamarin is a state-of-the-art tool for automated security protocol analysis.
With Tamarin, a protocol is modeled via a set of rules, defining the communication and data processing steps.
Additionally, security properties are modeled via lemmas that must hold for all possible execution traces of the model.
Afterwards, Tamarin starts in a state where the lemma was violated and performs an exhaustive backwards search.
If a valid execution trace is found that violates the lemma, this trace serves as a counterexample, i.e., a possible attack. Otherwise, the security property is shown to hold.

For the verification of strong authentication properties, we adopt the commonly used notion of injective agreement:

Definition 1
(Injective agreement)

A protocol guarantees
injective agreement
to an honest initiator
A
with an honest responder
B
on a set of data items
\vec{ds}
if, whenever
A
, acting as initiator, completes a run with the protocol,
apparently with responder
B
, then
B
has previously been running the protocol, apparently with
A
, and
B
was acting as a responder in this run.
Moreover, each run of
A
corresponds to a unique run of
B
and both agents agree on the values of the variables in
\vec{ds}
.
[
53
]

For our Tamarin model, we assume that initial exchange of
OOB
(
OOB
) data (via QR code) for Bluetooth pairing is secure (i.e., modeled via a secure channel). Additionally,
any of the user’s interactions with their user agent are assumed to be secure.
Furthermore, any long-term secrets (e.g., private keys of passwords) of actors involved in a specific protocol run are assumed to be secure.
Hence, to keep the needed assumptions as weak as possible, any actors that are not directly involved in a specific protocol run can be compromised.
For example, the security of a protocol run with
EMSP

A
should not be compromised by a key leak at
EMSP

B
.
The establishment of a shared symmetric key during Bluetooth pairing is modeled as per the most recent Bluetooth core specification
[
54
]
.
The establishment of symmetric keys during the
TLS
handshakes are modeled as key encapsulations based on the
EMSP
public key for simplicity.
This includes the
TLS
handshakes between user agent and
EMSP
as well as
EV
and
EMSP
; both with unilateral authentication by the
EMSP
.
Any other communication and data processing steps of the proposed protocol are modeled as described in
Section

5
.
Our full Tamarin model definition can be found online (cf.
Footnote

1
on
Footnote

1
).

As mentioned, we mainly focus on the verification of strong authentication properties for the installation of contract credentials based on the notion of injective agreement.
This notion can be transferred to our use case in the form of a Tamarin lemma as shown by the example
in
Section

0.A.3
.

Besides the injective agreement lemmas to prove secure authentication, the model also includes verifications of intermediate steps and weaker security properties based on Lowe’s hierarchy of authentication properties
[
53
]
.
The model further includes several correctness lemmas, i.e., lemmas that verify that the correct/expected execution of the model is possible to avoid false security proofs by an erroneous model.
Additionally, we include several performance optimizations for the automated proofs to terminate within an acceptable timeframe, such as reuse lemmas (which can provide partial proofs for reuse in later lemmas) and an oracle (which guides the automated proof execution, affecting runtime but not correctness).

The automated symbolic analysis with Tamarin and the model shows that the proposed protocol satisfies the security properties, as no counterexamples are found.
Specifically, the analysis shows that injective agreement over the contract credentials holds between
EV
and
EMSP
during credential installation. Injective agreement is shown to hold in both directions, i.e., installation request and response.
Results of the automated symbolic analysis and details on how to recreate the evaluations results with the Tamarin prover can be found online (cf.
Footnote

1
on
Footnote

1
).
In short, on a standard laptop, the verification of all lemmas with automatic sources generation finished in roughly 228 minutes and consisted of a total of
131,305
proof steps.

8
Conclusion

To enhance the usability of
EV
, the
PnC
feature of ISO 15118 plays a critical role. However, a key criticism of PnC lies in its complex and poorly defined
PKI
and credential installation/management processes.
In this paper, we present a method to address these challenges by proposing a solution for
EV
credential installation based on the widely adopted OAuth 2.0 standard. This approach improves usability by introducing an app-guided installation process, which operates seamlessly across various combinations of
EMSP
and
EV
, leveraging familiar user interaction patterns. Additionally, the solution enables users to easily become customers of different
EMSP
by simplifying the contract credential installation process, which operates seamlessly across various combinations of by utilizing
OIDC
-based payment providers, facilitating an express checkout process similar to that found in online retail environments.
Security is further enhanced through fine-grained authorizations enabled by OAuth’s
RAR
(
RAR
). Through a proof-of-concept implementation, we demonstrate that the proposed solution meets essential performance and usability requirements. Moreover, security properties were formally verified using the Tamarin prover, ensuring that the solution satisfies critical security criteria. This verification underscores the robustness of the OAuth cross-device authorization flow, which has been applied to the secure installation of billing-relevant contract credentials for
EV
.
Lastly, the implementation’s source code and the Tamarin models used for verification are made available online, ensuring the reproducibility of the presented results and providing a foundation for future applications in similar contexts.

Extension: Single Sign-On with Payment Providers

This section provides technical details on the
OIDC
extension, whose usability benefits are discussed in Section
5.5
.

Modern Single Sign-On (SSO) systems are commonly implemented using the
OIDC
(
OIDC
) standard
[
55
]
, which is built upon OAuth 2.0 (RFC 6749
[
6
]
). A simplified overview of how
OIDC
can be integrated into step 2 of the authorization process (as outlined in Section
5.5
) is shown in Figure
16
.

Figure 16:
Simplified
OIDC
(
OIDC
) authorization flow.

In this scenario, instead of manually entering login credentials for an
EMSP
account, the driver opts to authenticate via a third-party
IdP
.
This initiates an Authorization Request to the selected
IdP
’s
AS
(1), redirecting the driver (i.e., the
RO
) to the
IdP
’s
AS
through their web browser. The driver then authenticates using their existing
IdP
credentials (2) and authorizes the
EMSP
’s
AS
to access specific profile information—such as name and address—using the scope
openid profile address
. If the
IdP
is also a payment provider, the Authorization Request may include an additional scope to request continuous payment authorization. Upon granting the requested scope (3), the
IdP
’s
AS
issues an access token to the
EMSP
’s
AS
(4), allowing the
EMSP
to execute payments. Simultaneously, the
IdP
’s
AS
provides an ID token (4) containing the driver’s profile information. Both tokens are signed by the
IdP
’s
AS
.

Such payment
IdP
are typically private online payment providers which are often used in online shops, e.g., Apple (Pay), Google (Pay), or PayPal.
However, the OpenID Foundation proposed the use of a bank’s
AS
as
IdP
for OAuth-based payment authorizations in its Open Banking whitepaper
[
56
]
.
For this, the OpenID Foundation has developed the
FAPI
(
FAPI
) security profile
[
57
]
which was formally analyzed by Fett et al.
[
58
]
.

FAPI
is already adopted by large ecosystems like OpenBanking UK
[
59
]
.
Additionally, payment providers like MasterCard
[
60
]
and PayPal
[
61
]
have integrated OAuth 2.0 into their systems.

Certain
EMSP
may already offer Single Sign-On capabilities and online payment authorization capabilities within the ISO 15118-based
PnC
framework, as these technologies are complementary. However, the proposed OAuth-based extension to the ISO 15118
PnC
authorization process significantly enhances user convenience, enabling rapid switching between
EMSP
. This flexibility allows drivers to take advantage of discounts at
CP
offered by specific
EMSP
, while simultaneously lowering the barriers for
EMSP
to attract new customers by simplifying contract initiation.

Listing 1:
Tamarin Lemma for Injective Agreement Between the
EMSP
and the
EV
for Credential Installation

Intuitively, the lemma can be described as:
Whenever an
EMSP
accepts a public key from an
EV
(line 3–4) it follows that the same
EV
has previously sent an installation request with the same public key to the same
EMSP
(lines 5–8). Moreover, each accepted public key by the
EMSP
corresponds to a unique request (lines 9–12).
These security properties may only be violated if the long term secrets of one of the parties, involved in the specific protocol run, were leaked (line 14).
Injective agreement in the reverse direction is modeled analogously over the contract certificate generated by the
EMSP
and accepted by the
EV
.
