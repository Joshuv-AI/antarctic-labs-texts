A Generic and Efficient Python Runtime Verification System and its Large-scale Evaluation
Zhuohang Shen, Mohammed Yaseen, Denini Silva, Kevin Guan, Junho Lee, Marcelo d’Amorim, Owolabi Legunsen

Abstract
Runtime verification (RV) now scales for testing thousands of open-source Java projects, helping find hundreds of bugs. The popular Python ecosystem could use such benefits. But, today’s Python RV systems are limited to a domain or specification logic, or slow. We propose PyMOP, a generic, extensible, and efficient RV system for Python. PyMOP supports five logics, implements five existing monitoring algorithms, ships with 73 API specs of Python and widely-used libraries, supports three instrumentation strategies, and users can easily add more of these. On 290,133 unit tests in 1,463 GitHub projects, we find mainly that (i) the default monitoring algorithm for Java is often not the fastest for Python; (ii) PyMOP is up to 1 ​ t ​ r ​ u ​ e ​ 168.32 1true168.32 x faster than two recent dynamic analysis systems; and (iii) 44 of 121 bugs that PyMOP helped find so far were fixed by developers. PyMOP’s generality and efficiency position it well as an excellent platform for the next advances on RV for Python.

3.1
Background on parametric trace slicing

A
trace
is a sequence of events
[
136
]
. A

parametric event
is one whose abstract parameters are bound to
concrete data like heap objects at runtime. A
parametric trace

consists of parametric events. Conceptually, a spec encodes a

property
that maps traces to categories (e.g.,

\mathtt{violating}
,
\mathtt{not-violating}
, or
\mathtt{dont-know}
).
Specs in this paper encode
parametric properties
that map
parametric traces to categories.
Say, at program end, the TOCTOU related trace is
\tau={{\mathtt{os.access(f_{2})}}}\leadsto{{\mathtt{open(f_{1})}}}\leadsto{{\mathtt{os.access(f_{2})}}}\leadsto{{\mathtt{os.access(f_{1})}}}
.
Here, events
\mathtt{os.access}
and
\mathtt{open}
are parametric—the
parameter
f
is bound to different objects
f_{1}
and
f_{2}
at
runtime. So,
\tau
is a parametric trace. Non-parametric RV might
wrongly map
\tau
to

\mathtt{violating}
:
\mathtt{open}
comes after

\mathtt{os.access}

\tau

Existing RV algorithms treat parameters in different ways.

not
in the trace). These features make
\mathbb{B}\langle X\rangle
more
time- and space-efficient than
\mathbb{A}\langle X\rangle
. Algorithm
2
shows
\mathbb{B}\langle X\rangle
;
it takes instrumented code
P
and monitor template
M
. A main difference with
\mathbb{A}\langle X\rangle
is that, in
\mathbb{B}\langle X\rangle
,
traces are sliced and monitored “on the fly” as each parametric
event is signaled from
P
(line
8
).
\mathbb{B}\langle X\rangle

tracks the state of the
monitor instance
(obtained from
M
) for

\theta^{\prime}
in
\Delta
, and transitions that instance based on
\sigma

by
e
(line
10
). Next,
\mathbb{B}\langle X\rangle
categorizes the
current state of the monitor instance for
\theta^{\prime}
according to

\gamma
and stores it in

\Gamma
(line
11
). A
\mathtt{Handler}
is
triggered if
\theta^{\prime}
slice violates a spec.

3. Algorithm
\mathbb{C}\langle X\rangle
.

\mathbb{B}\langle X\rangle
’s search for compatible parameters and combination with
\theta

(line
9
in Algorithm
2
) can be
expensive for long traces. To optimize,
\mathbb{C}\langle X\rangle
uses an auxiliary data
structure,
\mathcal{U}
, with
\Delta
and
\Gamma
.
\mathcal{U}
maps each parameter instance
\theta
to the
set of parameter instances in
\Delta
that are strictly more
informative than
\theta
.
So, for each
e\langle{\theta}\rangle
,
\mathbb{C}\langle X\rangle
can more quickly find
compatible parameters by looking up
\theta
in
\mathcal{U}
, instead
of repeatedly searching through all elements of (often very large)

\Theta
like
\mathbb{B}\langle X\rangle
does. Also, unlike
\mathbb{B}\langle X\rangle
,
\mathbb{C}\langle X\rangle
does
not

explicitly store
\Theta
, but implicitly captures it as
\Delta
’s
domain. Doing so reduces the time to update
\Delta
after each

e\langle{\theta}\rangle
, and saves memory. But, in projects where
traces are mostly short,
\mathbb{C}\langle X\rangle
’s extra machinery can add extra costs.

4. Algorithm
\mathbb{C}^{+}\langle X\rangle
.
For specs with multiple parameter types, violations often cannot
occur until a “creation event” has occurred.
\mathbb{C}^{+}\langle X\rangle
leverages this observation: monitors
are only instantiated upon creation events. If many non-creation
events occur before the creation event or if a creation event never
occurs,
\mathbb{C}^{+}\langle X\rangle
can be faster and use less memory than
\mathbb{C}\langle X\rangle
. In a
sense,
\mathbb{C}\langle X\rangle
is a special case of
\mathbb{C}^{+}\langle X\rangle
where all events are creation
events
[
21
]
. So,
\mathbb{C}\langle X\rangle
can be as efficient at

\mathbb{C}^{+}\langle X\rangle
for specs that do not designate a creation event.

5. Algorithm
\mathbb{D}\langle X\rangle
.
This algorithm uses information about the spec to avoid creating
unneeded monitors. The information that
\mathbb{D}\langle X\rangle
uses is
called
enable sets
and it is computed via static analysis of
each spec at compile time. Intuitively, the enable sets of a spec maps each non-parametric event
e
to the set of parameters that must
have been bound by the current slice
\tau
for
\tau.e
or its future
extensions to reach a category of interest. PyMOP implements the
algorithms in
[
29
]
for computing enable-sets for
regular and context-free specs.
\mathbb{B}\langle X\rangle
,
\mathbb{C}\langle X\rangle
, and
\mathbb{C}^{+}\langle X\rangle
do not take
such information into account, so they can create monitors for slices
that do make semantic sense, or those that cannot reach a violating
state.
\mathbb{D}\langle X\rangle
is the most complex among MOP-style parametric monitoring
algorithms and it can be more efficient than others for monitoring
multi-object specs. But, enable sets can be an unnecessary overhead
for single-object specs.

3.3
Monitor Garbage-Collection Algorithm

Monitor garbage collection
(MGC)
[
93
]
makes RV more efficient
by proactively eliminating monitors that can no longer reach a verdict
category. The MGC algorithm uses
coenable set
to determine when
to remove monitors; it is set of events that should still be possible
(depending on alive parameters) to reach a category. PyMOP implements
coenable sets: each event received by a monitor triggers an MGC check
of that monitor’s coenable set. If parameter instances associated with
events in the coenable set have been garbage collected, then PyMOP concludes that the monitor can be safely garbage collected.

3.4
Implementation

We implement PyMOP as a plugin for
\mathtt{pytest}
; users can invoke it like
so:

pytest -p pythonmop
. We briefly discuss salient parts of
PyMOP’s implementation.

Monitor Synthesizer
1
.
PyMOP invokes JavaMOP’s mature and well-tested monitor-synthesis
plugins for ERE, FSM, past- and future-time LTL specs. Doing so sped
up our PyMOP development. We also provide a new CFG monitor-synthesis
plugin as a proof of concept on how to add other logic plugins.
All monitor-synthesis plugins produce monitor templates (circles in
Figure
4
) from which runtime monitors are
instantiated. For ERE, FSM, and LTL, that template defines an FSM. For
CFG, that template defines a parser
derivative
[
113
]
.

Instrumenter
2
.
PyMOP supports three instrumentation strategies: (i) Python-level
Monkey Patching only
[
88
]
, (ii) Python-level Monkey
Patching plus C-level Monkey Patching via the curses function
in
\mathtt{forbiddenfruit}

[
35
]
, and
(iii) Python-level Monkey Patching plus AST
transformation
[
127
]
. Using these strategies, PyMOP
rewrites the CUT, libraries, and the Python
runtime to signal events “before” or “after” spec-related events
at runtime. PyMOP also has an API for adding more strategies in the
future. Our appendix discusses in great detail the tradeoffs in
capability and cost among the currently supported strategies.

Monitoring Algorithms
3
.
MOP monitoring algorithms can be implemented as (i) libraries (easier
for humans to work with but slower) or (ii) spec-compiler generated
code (harder for humans to work with but faster).
Different from prior work
[
21
,
116
,
94
,
109
]
, we implement

\mathbb{A}\langle X\rangle
,
\mathbb{B}\langle X\rangle
,
\mathbb{C}\langle X\rangle
,
\mathbb{C}^{+}\langle X\rangle
, and
\mathbb{D}\langle X\rangle
as libraries in PyMOP to help
others understand and extend them. PyMOP offers command-line options
for choosing among these algorithms (
e.g.
,
pytest -p
pythonmop --algo=C+
for
\mathbb{C}^{+}\langle X\rangle
). Future work can further
optimize PyMOP by implementing these algorithms via code generation.

Specs
.
PyMOP ships with 73 specs (§
4.1
) that use all
its logic plugins. Users can add more specs by writing them in
PyMOP’s logic syntax, or via a JSON-like syntax (
e.g.
,
Figure
1
) that PyMOP translates to its logic
syntax.

4.2
RQ1: The overheads of PyMOP’s monitoring algorithms

1. How robust are the algorithms?

An algorithm is considered
successful
for a given project if it
completes with the same outcome (success or failure) as the baseline
(i.e., without RV). An execution fails either because it exceeds the
time limit (4 hours) or exhausts system memory (15GB), often caused by
the creation of a large number of monitors. When monitoring
all 73 specs simultaneously, each algorithm exhibits
different levels of robustness.
\mathbb{D}\langle X\rangle
was the only algorithm
successful in all 1,463 projects.
\mathbb{C}^{+}\langle X\rangle
was successful in
1,462 projects,
\mathbb{C}\langle X\rangle
was
successful in 1,461 projects,
and
\mathbb{B}\langle X\rangle
was successful on 1,437
projects.

2. Is there a statistical difference in the runtime
overhead of PyMOP’s online monitoring algorithms?

Overhead

is the ratio between the execution time of an RV algorithm and the
time to run tests without RV.
\mathbb{D}\langle X\rangle
has mean and max overheads of

12.33
x and
848.76x,
respectively.
\mathbb{C}^{+}\langle X\rangle
’s mean and max overheads were

16.70
x and
879.71x, respectively.

\mathbb{C}\langle X\rangle
’s mean and max overheads were

17.15
x and
879.01x,
respectively. Lastly,
\mathbb{B}\langle X\rangle
has mean and max overhead of

33.96
x and
5,500.27x, respectively.

We conduct Friedman and pairwise Wilcoxon signed-rank test with
Bonferroni correction for multiple
comparisons
[
37
]
. We use these non-parametric
tests due to the lack of normal distributions in the algorithms’
times. For fairness, we only use 628 projects for these statistical
tests: starting from
1,437 projects
that all four algorithms succeed on, we discard 798 where tests
without RV take less than 2s (to reduce the influence of noise from
short executions), and discard 11 whose times vary
non-deterministically (to improve measurement reliability). Our
conclusions remain the same when we use all
1,437 projects.

The Friedman test shows statistically significant differences in four
algorithms’ times
but it does not reveal which pairs differ. So, we perform pairwise
Wilcoxon signed-rank tests with Bonferroni correction
[
37
,
86
]
:
(i) differences between
\mathbb{C}\langle X\rangle
and
\mathbb{C}^{+}\langle X\rangle
are not statistically
significant; (ii) all other pairs have high significant differences
(
p<0.001
). To see the magnitude of differences, we calculate
effect sizes using the rank-biserial correlation
coefficient
[
97
]
: (i) the effect size for
\mathbb{C}\langle X\rangle
vs.
\mathbb{C}^{+}\langle X\rangle
is
negligible; and (ii)
\mathbb{D}\langle X\rangle
outperforms the other algorithms in our
experiments, having the largest effect against
\mathbb{B}\langle X\rangle
.

translate to DynaPyt and DyLin; others cannot be translated due to
usage of idioms that are incompatible with DyLin, or usage of
multiple parameters and formal logic. We have contributed these 19
specs to DyLin
[
56

circular references because the checkers use 3rd-party libraries (4 checkers),
and we cannot implement them consistently between PyMOP and DyLin (1 checker).

CUT

Discussion

Is PyMOP the only needed Python RV system?

No! We develop PyMOP because (i) despite recent success of work that
used JavaMOP for simultaneous monitoring of scores of specs during
testing in many projects, we cannot find a similar system for Python;
(ii) the lack of such Python RV systems is a big gap in today’s
AI-driven and data-intensive computing landscape; and (iii) we
developed other MOP-based RV systems
[

. But,
there are

PyMOP’s offline RV support
.
PyMOP enables offline RV, but our main evaluation focuses on online
algorithms for use in testing. We conduct a small experiment to get a
sense of PyMOP’s offline RV capability. To do so, we compare the time
of PyMOP’s offline
\mathbb{A}\langle X\rangle
algorithm (§
3.2
) with those
of online algorithms implemented in PyMOP (
\mathbb{B}\langle X\rangle
,
\mathbb{C}\langle X\rangle
,
\mathbb{C}^{+}\langle X\rangle
, and

\mathbb{D}\langle X\rangle
), using 73 specs and 68 projects from the last
decile in §
4.2
, where the online algorithms show the
largest overhead and noticeable differences among them. The results
show that the average relative overhead of
\mathbb{A}\langle X\rangle

is 95.19x, while the
average relative overhead of
\mathbb{B}\langle X\rangle

is 23.58x,
\mathbb{C}\langle X\rangle

is 12.92x,
\mathbb{C}^{+}\langle X\rangle

is 13.01x, and
\mathbb{D}\langle X\rangle

is 11.11x. So, online
algorithms are more efficient than PyMOP’s offline algorithm.

Impact of monitor garbage collection (MGC)
.
We compare
\mathbb{D}\langle X\rangle
’s times with and without MGC
(§
3.3
),
using
1true363
projects. 645
of these projects are faster with MGC, the
other 718
are slower. With a 0.5 seconds tolerance for time equality, MGC has no
impact on
1true290

projects. Among the
other 73
projects, only 34
are faster with MGC. As expected, projects in which many monitors for
multi-object specs are instantiated at runtime tend to see more
speedups from MGC. So, as more of these kinds of specs are added
to PyMOP in the future, MGC will be important for reducing its
overhead.

Why not static analysis?

§
2
discusses how static analysis may not detect
violations that require inter-procedural analysis or multi-type
reasoning. Also, some violations had traces with some events in a
program and some events in a 3rd-party library; static analysis may
not scale well for these. But, static analysis and RV are orthogonal
and complementary
[
30
,
23
,
54
,
123
,
22
,
163
,
84
]
. In fact, DyLin authors show that Python static
and dynamic analysis are complementary
[
58
]
.

Limitations and future work
.
We only evaluate PyMOP during testing. Future work should investigate
the suitability of PyMOP for monitoring deployed Python
programs. PyMOP currently does not yet have monitor-synthesis plugins
for many spec logics,
e.g.
,
[

. We plan to continue adding
more plugins. PyMOP is efficient, but there is room to optimize it,
given the high overheads in some projects. Two potential directions:
(i) optimized code generation of monitoring algorithms (as done
in JavaMOP) could provide speedups; and (ii) evolution-aware
techniques for Python could speed up RV by focusing on code affected
by changes during CI
[
102
,
101
,
169
,
75

76
]
. We do
not yet study the ease of writing PyMOP specs in Python or its
JSON-like frontend. Future work can conduct user studies like we did
for Java RV specs
[
156
]
.

Threats to validity
.
To mitigate the threat due to the kinds of specs, we follow prior RV work’s approach to writing specs in different logics, APIs, domains,
and frameworks (Python or libraries). There may be bugs in our specs,
so we peer review all our specs and write at least two tests
per spec—one violating and another not. These tests
are part of PyMOP. Another set of projects could show different
results. To mitigate this threat, we use a large corpus to
evaluate PyMOP, with 1,463 GitHub open-source projects (instead of benchmarks
similar to DaCapo
[
20
]
). We lack
domain expertise on the evaluated projects, so we open pull requests
and issues to check our findings about bugs with developers.

7
Conclusion

PyMOP is the first MOP-based RV system for Python. It
is
generic
, supporting five monitoring algorithms, three
instrumentation strategies, and five spec logics
(with 73 specs written), with features to add more of
these. PyMOP is also
efficient
as our large-scale evaluation
with
1,463 projects shows. PyMOP has helped us find 44
confirmed bugs during testing of open-source projects. We outline an agenda of future
research and development that PyMOP can enable.
