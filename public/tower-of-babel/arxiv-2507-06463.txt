Evaluating Efficiency and Novelty of LLM-Generated Code for Graph Analysis This work was supported in part by NSF grants CCF-2109988 and OAC-2402560, and CCF-2453324.
Atieh Barati Nia, Mohammad Dindoost, David A. Bader

Abstract
Large Language Models (LLMs) are increasingly used to automate software development, yet most prior evaluations focus on functional correctness or high‑level languages such as Python. We present the first systematic study of LLMs’ ability to generate efficient C implementations of graph‑analysis routines—code that must satisfy the stringent runtime and memory constraints. Eight state‑of‑the‑art models (OpenAI ChatGPT o3 and o4‑mini‑high, Anthropic Claude 4 Sonnet and Sonnet Extended, Google Gemini 2.5 Flash and Pro, xAI Grok 3‑Think, and DeepSeek DeepThink R1) are benchmarked by two distinct approaches. The first approach checks the ability of LLMs in generating an algorithm outperforming other present algorithms in the benchmark. The second approach evaluates the ability of LLMs to generate graph algorithms for integration into the benchmark. Results show that Claude Sonnet 4 Extended achieves the best result in the case of ready-to-use code generation and efficiency, outperforming human‑written baselines in triangle counting. The study confirms that contemporary LLMs excel at optimizing and integrating established algorithms but not inventing novel techniques. We provide prompts, the first approach’s generated code, and measurement scripts to foster reproducible research.



I
Introduction

The rapid advancement of Artificial Intelligence (AI), particularly large language models (LLMs), has significantly impacted both everyday life and also scientific workflows, accelerating research and development across disciplines. LLMs have shown significant promise in enhancing learning, automating tasks, and boosting productivity in a variety of domains. A recent survey by Chang

While Python dominates recent research, computer scientists still depend on lower‑level languages like C to attain peak performance. Assessing the efficiency of LLM‑generated C code is therefore vital for judging these models’ ability to produce optimized implementations. Yet, to the best of our knowledge, no study has systematically examined the performance of LLM‑generated code in C—a language central to high‑performance and scientific computing.

Moreover, prompting an LLM to generate an algorithm without explicit contextual constraints may raise issues of construct validity, because we cannot know whether the model is simply repeating code it saw during training. To address this concern, we adopt a more rigorous evaluation strategy, the first to our knowledge that places the models inside an existing codebase, by supplying concrete source files and asking the LLMs to produce algorithms that integrate with them. This targeted setup sharply reduces the chance of pre‑training contamination and yields a clearer measure of each model’s genuine coding ability.

This paper offers the first systematic evaluation of cutting‑edge LLMs at producing efficient C implementations for graph algorithms. We evaluated the generated code along four axes: compilability, functional correctness, execution time, and memory footprint. We anticipate that our findings will not only guide LLM developers in enhancing their models but also assist those computer scientists, who implement application codes or graph analytics, in selecting the most suitable LLMs for their real-time applications.

I-A

Related work

Recent research has increasingly focused on the efficiency of code generated by large language models (LLMs), moving beyond the traditional emphasis on correctness. Huang
et al.
[
11
]
introduced EffiBench, a benchmark that evaluates the runtime and algorithmic complexity of Python code, revealing that syntactically correct code is not always efficient. Similarly, Qiu
et al.
[
12
]
proposed a rigorous benchmark to jointly assess both the correctness and efficiency of LLM-generated Python code. Licorish
et al.
[
13
]
compared human- and LLM-generated code across correctness, efficiency, and maintainability, concluding that current models still fall short of human performance. Du
et al.
[
14
]
presented Mercury, a broad efficiency benchmark for LLMs across multiple programming tasks, while Niu
et al.
[
15
]
and Liu
et al.
[
16
]
examined key challenges and proposed frameworks for measuring efficiency in generated Python code.

While these studies yield valuable insight for a popular high‑level language, C remains the workhorse of high‑performance computing (HPC) and systems programming. Virtually all supercomputing kernels, MPI/OpenMP libraries, operating‑system components, and performance‑critical embedded routines are still written in C (or C‑centric dialects such as CUDA and OpenCL). Unlike Python—whose interpreter and dynamic typing add layers of abstraction—C exposes explicit memory management and low‑level control over hardware, so a small inefficiency can translate into orders‑of‑magnitude slowdowns at HPC scale. Evaluating LLM output in C therefore probes a harder and more consequential problem: can these models generate code that meets the stringent runtime and memory budgets demanded by real‑time analytics, exascale simulations, and kernel‑level software?

Other relevant efforts have focused on improving code quality or efficiency. Siddiq
et al.
[
17
]
introduced FRANC, a framework designed to enhance the correctness and readability of LLM-generated Java and Python code. Yetistiren
et al.
[
18
]
empirically evaluated tools like GitHub Copilot, Amazon CodeWhisperer, and ChatGPT, focusing on quality dimensions such as correctness and maintainability, but primarily using earlier LLMs. In contrast, our study evaluates the efficiency of code produced by state-of-the-art models.

Ye
et al.
[
19
]
proposed LLM4EFFI, a framework that guides LLMs to produce more efficient and correct Python code using prompt engineering and iterative feedback. Likewise, Waghjale
et al.
[
20
]
introduced ECCO, a post-processing framework that optimizes generated code for efficiency. Unlike these works, our study evaluates the inherent efficiency of code generated by modern LLMs in C, without manual intervention or optimization, to reflect their true capabilities in producing performant code.

II
Study Settings

In this section, we describe the data and source code of the program, the models we use for evaluation and comparison, and how we conduct the experiment to investigate the LLM efficiency.

II-A

Data

Bader
[
21
]
introduced a comprehensive framework in C to evaluate the efficiency of triangle counting algorithms introduced by humans. Within this framework, he implemented various algorithms in compressed sparse row (CSR) format, measured their execution times, and established a benchmark for comparison. This benchmark is a good input file to LLMs to incorporate in it to reduce the risk of using pre-trained data.

II-B

Models

Since we want to examine the efficiency performance of LLMs in helping programmers, we selected the seven models of widely recognized LLMs that are publicly accessible and gained attraction because of their performance in code-generating problems.

OpenAI ChatGPT o3 and ChatGPT o4-mini-high:
OpenAI’s models are among of the most well-known LLMs, mostly known as ChatGPT, having played a pivotal role in ushering in the modern era of generative AI. So, we included the evaluation of the latest available versions related to code implementation which were released on April 16, 2025. OpenAI o3 which uses advanced reasoning by spending more time thinking before responding, and OpenAI o4-mini-high which said to be great at coding and visual reasoning are selected to be the representative of OpenAI company.

Claude 4 Sonnet and Claude 4 Sonnet Extended:
Anthropic’s Claude models are renowned for their advanced reasoning, language comprehension, and efficient code generation. The most recent model, Claude 4 Sonnet which was released on May 22, 2025, includes an extended variant with enhanced capabilities, both of which we incorporate in our analysis.

Google Gemini 2.5 Flash and Gemini 2.5 Pro:
Google’s strong track record in AI innovation makes its latest Gemini models essential to our benchmark. We therefore include Gemini 2.5 Flash, first released in public preview on April 17 2025, alongside Gemini 2.5 Pro, whose public‑preview build launched on May 6 2025 and is specifically promoted for advanced reasoning, mathematical skill, and code‑generation prowess, ensuring our evaluation is truly comprehensive.

xAI Grok 3 - Think:
we include xAI’s Grok 3, released on February 17 2025, and evaluate it in its dedicated “Think” mode, which is optimized for deeper reasoning, to gauge how the latest entrant performs under our efficiency benchmark.

DeepSeek DeepThink (R1):
Upon its launch on January 20 2025, DeepSeek R1 (marketed as DeepThink) drew wide attention for matching the performance of costly proprietary LLMs while remaining free and requiring far fewer training resources. Because of this exceptional efficiency and cost‑effectiveness, we include DeepSeek DeepThink (R1) in our evaluation to measure its capabilities against the established models in our benchmark.

II-C

Methodology

A critical challenge in evaluating LLMs is the risk that their outputs may reproduce memorized training data rather than demonstrate genuine reasoning. To address this, we employ a novel evaluation strategy: rather than relying on textual prompts alone, we provide each LLM with the C source files from Bader’s benchmark
[
22
]
and instruct them to generate a functional triangle counting algorithm that integrates into the existing framework. This approach allows us to assess the models’ true algorithmic reasoning capabilities, minimizing the influence of memorized solutions.

Our study comprises two approaches: Optimization approach and Algorithm-Synthesis approach. The Optimization approach supplies each LLM with the full collection of C source files for existing sequential triangle‑counting implementations and challenges it to generate the most efficient routine. By exposing the models to every known approach, we probe whether they can synthesize genuinely novel strategies that outperform human‑written code. The complete prompt template appears in Figure
1
.

Prompt:
The attached code implements triangle counting in a graph given in CSR format. Write a C routine tc_fast() with the API below that is the fastest sequential triangle counting code you can generate.

UINT_t tc_fast(const GRAPH_TYPE *graph)

Attached Files:
(bfs.c, graph.c, main.c, queue.c, tc.c)

Fig. 1:
The First Prompt Structure Template.

The Algorithm‑Synthesis approach evaluates how well each model can generate efficient implementations of Triangle Counting, Diameter Finding, Vertex Connectivity, Edge Connectivity, and Clique Number when no prior code for these algorithms is provided. In this approach the provided C source contains the project’s core graph infrastructure; the algorithm implementations are deliberately absent. Each model must therefore write a new routine that integrates seamlessly with this codebase. The prompt template for this approach is shown in Figure
2
.

After collecting the generated functions for both approachs, we incorporated them into the benchmark and executed all tests to compare performance. The benchmark reports the average runtime over 10 executions for each implementation, providing statistical validity and smoothing out measurement noise to ensure robust and reliable performance measurements.

The attached code implements a graph in CSR format. Write a C routine fast() with the API below that is the fastest sequential implementation for finding the {ALGORITHM} of a graph that can be integrated into the attached files:

UINT_t fast(const GRAPH_TYPE *graph)

Attached Files:
(bfs.c, graph.c, main.c, queue.c)

III
Experimental Results

The experiments were conducted on Wulver, an HPC cluster at NJIT
[
23

III-A

Optimization Approach

The evaluation demonstrated that while all examined models successfully generated code that integrated seamlessly into the benchmark framework without requiring modifications, DeepSeek R1, Gemini 2.5 Flash, and Grok 3- Think produced implementations that failed to correctly count number of triangles. Consequently, due to these incorrect outputs, the algorithmic details for these three models were excluded from further analysis.

Most models leveraged efficient approaches already present in the benchmark, combining optimized techniques such as degree-based vertex sorting (using the benchmark’s built-in function), hash-based intersection, the Forward Triangle Counting algorithm
[
24
,
25
]
, and BFS traversal
[
26
]
. These strategies, while not groundbreaking, were effectively synthesized into workable solutions.

Although both Gemini 2.5 Pro and Claude Sonnet 4 Extended employed similar core methods, using the Forward Counting Algorithm combined with sorting and hashing, Claude Sonnet 4 Extended achieved faster performance. This improvement indicates a more effective utilization of memory management and cache locality by the Claude model. Other models achieve their fastest runtimes by leveraging higher peak memory.

ChatGPT o4-mini-high implemented the Forward Triangle Counting Algorithm for its solution. However, its implementation did not incorporate advanced optimizations such as hashing or sorting of nodes to accelerate neighbor intersection computations which led to suboptimal time performance, particularly in graphs with high-degree vertices where efficient lookup mechanisms could reduce redundant comparisons. As a result, its implementation placed third among the LLMs implementations, trailing behind human-written code.

ChatGPT o3 incorporated two human-written helper functions—one for graphs with more than 16,384 edges and another for smaller instances. However, its choice of which function to apply was not optimal compared to other LLMs or the hand-written baseline, leading to a slower runtime despite achieving the lowest peak memory usage compared to other LLMs.

Claude Sonnet 4 also adopted the Forward Triangle Counting Algorithm and incorporated hashing to optimize neighbor intersection operations, a strategy that theoretically should improve performance for common neighbors. However, its implementation exhibited significantly worse time performance compared to other models which shows its poor performance in implementing efficient code.

This suggests that, while large language models excel at optimizing and refining code, their current capabilities remain focused on improving known methods rather than developing fundamentally new algorithmic advances.

III-B

Algorithm-Synthesis Appraoch

In this approach, we assess each model’s capability to produce efficient implementations of established graph algorithms without access to any pre-existing code. Performance is evaluated according to two principal criteria: Ready-To-Use (RTU) Capability and Efficiency Trade-Offs.

III-B
1
Ready-To-Use (RTU) Capability

A model is deemed RTU for a given algorithm if it generates code that meets all of the following requirements:

•

Compilability:
The submitted code must compile successfully without any manual modifications.

•

Correctness:
The code must pass our complete suite of predefined test cases.

•

Timeliness:
The implementation must execute within an acceptable runtime threshold, ensuring practical usability.

IV
Conclusion

In conclusion, this empirical study systematically evaluated the efficiency of C code generated by leading LLMs, yielding valuable insights into their performance: all models successfully integrated their code into our benchmark environment during Optimization approach, but significant efficiency differences emerged, with Claude 4 Sonnet Extended and Gemini 2.5 Pro exhibiting the most impressive runtime and memory profiles, underscoring that LLMs currently excel at synthesizing and optimizing established methods rather than creating entirely new algorithms. In Algorithm-Synthesis approach, again, Claude Sonnet 4 Extended achieved the highest Ready‐To‐Use (RTU) rate and generated the most efficient implementations of well‐known graph algorithms in C, making it the leading model for efficient graph‐algorithm code generation at present. Despite these strengths, LLMs still have ample room to advance, particularly in developing fundamentally novel computational strategies, and future research should investigate their capacity to produce parallel algorithms, leverage GPU architectures, and address security and correctness concerns, thereby extending their impact in high‐performance computing and beyond.

V
Future Work

While this study has assessed LLMs’ ability to generate efficient sequential graph algorithms for CPU execution, several avenues warrant further exploration. First, extending the evaluation to parallel graph algorithms, especially those targeting GPU architectures, could reveal how effectively LLMs optimize for load balancing, synchronization, and memory‑access patterns in massively parallel settings. Second, beyond empirical runtime measurements, future work should include rigorous theoretical analyses of the upper‑bound time complexity and memory consumption of LLM‑generated code, offering formal guarantees on performance and resource usage. Third, assessing the security implications of automatically generated code remains critical, particularly for safety‑sensitive graph algorithms where correctness and robustness are paramount. Finally, broadening the benchmark to encompass a wider range of graph problems and hardware architectures would yield a more comprehensive picture of LLMs’ strengths and limitations in graph‑algorithm implementation.
