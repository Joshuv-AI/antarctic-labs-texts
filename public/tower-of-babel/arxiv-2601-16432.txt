iPDB - Optimizing SQL Queries with ML and LLM Predicates
Udesh Kumarasinghe, Tyler Liu, Chunwei Liu, Walid G. Aref

Abstract
. Structured Query Language (SQL) has remained the standard query language for databases. SQL is highly optimized for processing structured data laid out in relations. Meanwhile, in the present application development landscape, it is highly desirable to utilize the power of learned models to perform complex tasks. Large language models (LLMs) have been shown to understand and extract information from unstructured textual data. However, SQL as a query language and accompanying relational database systems are either incompatible or inefficient for workloads that require leveraging learned models. This results in complex engineering and multiple data migration operations that move data between the data sources and the model inference platform. In this paper, we present iPDB, a relational system that supports in-database machine learning (ML) and large language model (LLM) inferencing using extended SQL syntax. In iPDB, LLMs and ML calls can function as semantic projects, as predicates to perform semantic selects and semantic joins, or for semantic grouping in group-by clauses. iPDB has a novel relational predict operator and semantic query optimizations that enable users to write and efficiently execute semantic SQL queries, outperforming the state-of-the-art.



Keywords:

In-database LLMs, Optimization, Semantic Operators

Recent advances in AI have opened the way for breakthroughs in applications, e.g., question answering
(

(

Although SQL is optimized for querying tables with structured attributes, e.g., numeric values and strings, it is inefficient on workloads that require semantic reasoning and extracting semantic information from unstructured data, which is highly relevant in today’s application development landscape.

The success of deep learning and large language models (LLMs) has led to the application of learned models to perform complex tasks. For instance, LLMs have become highly desirable for extracting semantic information. Several studies have proposed systems that extract and filter information from documents

These added functions enable context-aware predictions and semantic operations, such as semantic selects, semantic projects, and semantic joins, surpassing the capabilities of traditional relational operations and predicates. It is evident that this functionality facilitates practical use cases. Incorporating learned model inference into SQL queries provides a generalized syntax for running inference on data stored in the database, enabling a wide array of tasks, e.g., classification, sentiment analysis, summarization, and text generation. Furthermore, having model inference capabilities within SQL enables users to leverage traditional SQL functionality and expressiveness to create more complex semantic queries that cannot be accomplished by simply feeding rows of unprocessed data into models. Additionally, by identifying patterns in semantic queries and performing logical and physical optimizations, it is possible to efficiently execute large-scale inference tasks. These optimizations are vital as LLM workloads are expensive in both runtime and monetary terms
(
15
)
.

Although supporting semantic queries in a relational database system is important, realizing an efficient system is non-trivial. We observe the following challenges in implementing this system.

•

Inference in learned models is expensive and has a higher latency than traditional database operations. Thus, inferencing will be the bottleneck operation in semantic queries, necessitating prioritizing it when optimizing semantic queries.

•

Schema alignment must be ensured to fit text-native LLMs into relational databases that are schema-driven (i.e., typed columns and constraints). The inference operator must ensure that LLM output can be parsed into consistent column types (i.e., VARCHAR, INT, DOUBLE).

•

Learned models may produce missing values, values with type mismatches, or hallucinate outputs. The system must minimize the possibility of errors and handle adversities.

•

Inferencing is prone to runtime errors as a result of external factors e.g., memory overflow, GPU latency, and network errors. The system must handle these errors gracefully.

To overcome these challenges, we realize iPDB, a data system with extended SQL and an execution engine that supports semantic queries. iPDB treats learned models as first-class citizens, where users can define, manage, and infer within the clauses of SQL, i.e.,
SELECT
,
FROM
,
WHERE
,
GROUP BY
, and
ORDER BY
. We utilize DuckDB
(
18
)
, a columnar-based relational engine, to reuse its
parser, relational query primitives, storage, and base query engine. However, to execute semantic queries in iPDB, we introduce several new components and extend DuckDB’s parser, planner, optimizer, and execution engine. The parser is extended with model manipulation language and predict/LLM predicates
to support semantic queries. The model management capabilities are realized by introducing a new system catalog to store and retrieve model metadata. The inference of learned models is achieved through a new physical predict
operator that manages input tuple processing and model probing, and extracts output attributes for schema compliance. Furthermore, new optimizations
are introduced within the predict operator and the plan optimizer to minimize the latency of model inference.

The following are the key contributions of the iPDB system:

•

Extended SQL Syntax for model inference, a new PREDICT and an LLM clause that appear among traditional SQL clauses to enable scalar inference, table inference and table generation, LLMs as predicates in the where clause, in semantic grouping, and in order-by clauses. These operators integrate model inference into Relational Algebra to take tables as input, perform model probing, and produce schema-compliant output tables.

•

New optimizations for LLM calls, e.g., prompt deduplication, multi-row prompt marshaling, semantic-predicate ordering, and semantic vs. traditional operator ordering.

•

A unified system that extends the relational parser, planner, optimizer, and execution engine to integrate model inference and metadata management, enabling the execution of relational and semantic query processing within a single declarative SQL framework.

•

Experimental results demonstrate that iPDB with the optimizations achieves up to 1000x improvement in performance over state-of-the-art systems by reducing the number of tokens and model calls while improving accuracy.

iPDB treats learned models as first-class citizens while recognizing their unique characteristics and providing new optimization strategies to optimize their performance.

Background

OLAP
: Unlike Online Transaction Processing (OLTP) systems that prioritize rapid updates and inserts, Online Analytical Processing (OLAP) systems focus on maximizing query throughput and minimizing latency for analytical workloads
(
23
)
. Key design choices include columnar storage layouts that enable high compression and facilitate selective access to relevant columns, and vectorized execution models that process data in batches to exploit modern CPU architectures
(
1
)
.
Modern analytical systems, e.g., DuckDB
(
18
)
, combine SQL expressiveness with efficient in-memory, parallel processing capabilities, and optimization techniques, e.g., predicate pushdown, join reordering, and materialized views further enhance performance. Consequently, analytical databases are powerful systems for analytics and data-driven applications. However, traditional relational operators are not designed with native support for model inference, often requiring data export to external ML systems. This introduces inefficiency and data governance issues.

LLMs
: Deep learning has redefined machine learning by enabling models to learn multi-level feature representations directly from data
(
12
)
. Subsequent advances have introduced transformer architectures
(
24
)
that have become the foundation for large-scale natural language processing. Large Language Models (LLMs) utilize self-attention mechanisms to model long-range dependencies in text, enabling remarkable generalization through pretraining on extensive corpora.
These models enable tasks including text classification, summarization, and semantic reasoning. However, the billions of parameters these model utilize makes them computationally expensive during inference. Despite computational expensiveness, LLMs are being increasingly applied to tasks involving structured and semi-structured data because of their capabilities.

In-database Inference
: In-database inference bridges the gap between databases and ML by enabling model inference directly within the database engine. This eliminates the need for data export and external processing pipelines, allowing predictions to be computed near the data source
(
14
)
. By leveraging existing database optimizations, e.g., vectorized execution, parallelization, and caching, this integration reduces latency and improves throughput for large-scale inference workloads. Several systems have explored this integration, e.g., MADlib
(
7
)
supports the training and inference of ML models within the database. Also, emerging in-database inference systems
(
19
;
11
;
10
)
extend this concept towards inferencing deep learning models. Recent work investigates semantic operators, query components that call external LLMs as part of query evaluation, e.g.,
(
17
)
. These developments suggest a promising direction where databases evolve into intelligent systems capable of combining relational computation with semantic understanding.

3.3.
Relational Algebra for Semantic Operators

We introduce an extended relational algebra operator for model inference, allowing it to coexist with traditional relational operators. Let
f
be a learned model that takes
x_{1},\cdots,x_{n}
input attributes and produces
y_{1},\cdots,y_{m}
output attributes:
f(x_{1},\cdots,x_{n})=({y_{1},\cdots,y_{m}}).
We define the relational algebra inference operator that takes a user-defined learned model
f
and the input attributes
x_{1},\cdots,x_{n}
of an input relation
T
.
f
produces the predicted attributes
y_{1},\cdots,y_{n}
by probing the learned model with the input attributes. The inference operator
\delta
is as follows:
\delta_{y_{1},...,y_{m}}(f,T_{x_{1},...,x_{n}})
. Regardless of the model type, task, or the location in the query, it can be transformed into an equivalent
\delta
operator in Relational Algebra.
\delta
is a minimal Relational Algebra operator for inference in a query.

For semantic queries that infer
LLM
s, Operator
\delta
can be further extended to semantic relational algebra operators, enabling logical transformations and equivalencies. For
LLM
, the input is a well-formatted prompt embedded with input data values. Hence, we first define the prompt
P=~\langle instruction,In,Out\rangle
, where
instruction
is a textual instruction, e.g., a natural language condition, transformation, or generation request,
In
are the input attributes defined in the prompt, and
Out
are the output attributes defined in the prompt. Using the prompt, we can define the structured input for the corresponding LLMs. Consider a tuple
t
of Relation
T
and a language model instance
f
.
LLM(P,t)=f(instruction\oplus_{a\in In}t_{a})
, where
\oplus
is a string concatenation operation of input attributes,
a\in In
. Note that
schema(LLM(P,t))=Out
.

Semantic Project:

Projects a given set of input attributes to a new set of output attributes based on a user-defined prompt. The cardinality of the input and output relation stays the same. The new semantically projected attributes,
Out
, are defined by the prompt
P
along with the input attributes,
In
, that are
a subset of the input attributes of Relation
T
. Notice that the schema of the semantic projection is equal to the output column in the prompt,
schema(\pi_{p}^{s}~(T))=Out
.

\pi_{P}^{s}~(T)=\left\{LLM(P,t[In])~|~t\in T\right\}.

For example, consider a projection to extract genre and main character from each movie:
\pi^{s}_{P}~(Movie)
, where

\begin{gathered}P=\text{"Given movie \lx@text@lbrace\lx@text@lbrace plot\lx@text@rbrace\lx@text@rbrace, extract
\lx@text@lbrace genre\lx@text@rbrace and \lx@text@lbrace main\_character\lx@text@rbrace."}\\
instruction=\text{'extract'}\\
In=\left\{\text{plot}\right\},Out=\left\{\text{genre, main\_character}\right\}\\
\end{gathered}

Semantic Select:

Filters the tuples in the input relation based on the condition and a user-defined prompt. The cardinality of the input and output relation will differ based on the selectivity of the condition that the LLM determines whether each tuple is satisfied. The select condition, the input attributes
In
, are defined in the prompt
P
. The schema of the output of the semantic select remains the same as that of the input relation.

\sigma^{s}_{P}~(T)=\left\{t\in T~|~LLM(P,t[In])=\text{True}\right\}.

For example, consider selecting negative movie reviews:
\sigma^{s}_{P}~(Review)
, where

\begin{gathered}P=\text{"Given movie \lx@text@lbrace\lx@text@lbrace review\lx@text@rbrace\lx@text@rbrace s, get the negative reviews."}\\
instruction=\text{'get negative movie reviews'}\\
In=\left\{review\}\right\},Out=\left\{\text{True, False}\right\}\\
\end{gathered}

Semantic Relation:

Generates a new relation from a learned model (e.g., LLM). The attributes of the relation are defined by the user in the prompt that must contain explicitly listed output columns and an implicit select predicate, as the LLM can be considered a source with an infinite domain and cardinality. The cardinality of the relation will depend on the implicit predicate applied to the model’s learned information. The attributes of the relation
Out
are defined by Prompt
P
,
schema(\rho_{p}^{s})=Out
. In this case, no input relation is given to the operator:
\rho^{s}_{P}=\left\{t\in LLM(P)\right\}.

For example, consider collecting all the rating categories in US movies maturity rating system:
MaturityRating=\rho^{s}_{P}
, where

\begin{gathered}P=\text{"Get all the maturity rating \lx@text@lbrace category\lx@text@rbrace s and \lx@text@lbrace description\lx@text@rbrace s."}\\
instruction=\text{' Get all the maturity ratings'}\\
Out=\left\{category,description\right\}\\
\end{gathered}

Semantic Join:

Joins two tables based on a condition in the user’s prompt. The prompt contains join attributes from both tables. The semantic join predicate is defined by the prompt along with the join attributes
In_{R}
and
In_{S}
. The output schema is the union of output columns from both input tables,
schema(R\bowtie_{P}^{s}S)=schema(R)\cup schema(S)
.

R\bowtie_{P}^{s}S=\left\{(t_{R},t_{s})~|~LLM(P,t_{R}[In_{R}],t_{S}[In_{S}])=\text{True}\right\}.

For example, join movies and maturity rating by comparing the plot with rating description:
Movie\bowtie_{P}^{s}Review
, where

\begin{gathered}P=\text{"Is the movie \lx@text@lbrace plot\lx@text@rbrace described by the rating \lx@text@lbrace description\lx@text@rbrace s."}\\
instruction=\text{'Is the plot described by the rating description'}\\
In=\left\{plot,description\}\right\},Out=\left\{\text{True, False}\right\}\\
\end{gathered}

A key design choice in implementing iPDB is the choice of a base relational engine to extend with a native predict operator and its accompanying components. Using a compatible base engine enables us to focus on functionality and optimization of the predict operator rather than writing a relational engine from scratch. We choose DuckDB as the foundation for iPDB due to its analytical focus, lightweight design, and modern execution architecture. DuckDB

is a columnar, in-process analytical database optimized for OLAP workloads. It is designed for high-performance analytical query processing, offering a vectorized execution engine that operates on columnar data. This execution model aligns well with iPDB’s inference workloads, where batch-wise (chunked) data processing and prompt marshaling can significantly reduce latency.

The model catalog enables users to declaratively reference models at query time without having to configure the execution of inference models imperatively. The catalog also helps ensure consistency and validation by verifying model availability, compatibility, and schema alignment at query time. This design provides the same convenience and reusability for models as first-class citizens, similar to traditional relational objects, e.g., tables and views. The model catalog is persisted by DuckDB’s storage primitives.

4.2.
Semantic Query Parsing

In iPDB, DuckDB’s SQL parser is extended with new
PREDICT
, and
LLM
clauses. The parsed inference clauses are stored in a unified
PGPredictExpr
node that holds key information to initialize a PREDICT operator, namely,
model_name
,
source
,
prompt
, and
agg
.
model_name
is a qualified model that already exists in the model catalog.
source
is a table reference if the input table is parsed (i.e., as an input relation for the
PREDICT
clause or table inference
LLM
clause).
prompt
stores the prompt string if the
LLM
clause is parsed. Boolean Flag
agg
indicates if the
LLM
clause is a semantic aggregate. The user may provide an optional
alias
for table inference using an
AS
clause. During parsing, placeholders within prompts are resolved into explicit input (e.g.,
{{column}}
) and output (e.g.,
{column TYPE}
) attributes, enabling semantic operators to integrate seamlessly with typed relational columns. For models bound to a table or predefined feature, the input and output attributes are resolved from the model catalog. Upon parsing the query into an abstract syntax tree, the binding phase validates model reference against the catalog. Then, metadata, e.g., base API URL, secret keys, and model-specific options are probed from the model catalog. The input columns are checked against the bound columns by the descendant operators, and the output columns and types are informed to the ancestors to ensure compatibility with subsequent query operators. This ensures model’s properties are known to the optimizer in the next stage of query processing.

4.3.
Semantic Query Planning

Once the query is parsed and bound, semantic queries are transformed into logical plans that explicitly incorporate inference operators alongside traditional relational operators. The inference operators are realized by
LogicalPredict
that extends DuckDB’s logical operator. It maintains the
PredictInfo
structure to store the state required for inference: the model’s type, name, path, API URL, secret, and execution options. Moreover, metadata for inference, e.g., names and types of input/output columns, are kept.

Once the logical plan is materialized, the mature optimizer of the base engine is used to optimize traditional operations, such as selections, projections, aggregations, and joins. However, without understanding that inference is expensive, the traditional operator will attempt to reorder inference operators, believing they are zero-cost. iPDB has guardrails to inform the optimizer that the operation is expensive and prevent redundant operator pushdown optimizations. Additionally, iPDB will pull up inference operators if the logical transformation of the result is equal and the new location has higher selectivity. The logical optimization of queries with inference operators is discussed in more detail in Section
6
.

4.4.
Semantic Query Execution

Execution of semantic queries in iPDB is by the physical operator
predict
.
Predict
is initialized based on the location of the inference clause. For table inference,
predict
is a generic operator that takes an input data chunk, processes the model, and populates the output data chunk. Scalar inference is realized by a
predict
expression executor that produces a single vector instead of a data chunk, enabling it to integrate seamlessly with DuckDB’s expression executor. A table generation initializes a
predict
scan that produces an output data chunk as a source.
At runtime, in a generic
predict
, the model is either loaded into memory for the local models or API clients are initialized for the remote models. Next, during execution, the input tuples are collected into a data chunk that is a vectorized, column-ordered set of tuples.
Predict
integrates with the base vectorized execution engine to enable batching multiple tuples and row marshalling when possible (As in the optimization in Section
6.2
). For on-prompt queries, the prompt template and the passed input tuples are transformed into structured prompts that are sent to the target model. Model responses are parsed and are validated against the expected schem. The predicted values are written to output data chunks that are passed to downstream operators. Error handling mechanisms are in place to gracefully recover from malformed outputs, timeouts, or external service failures by retrying requests. We discuss the physical
predict
operator in-depth in the next section.

5.
Implementation of the
Predict
Operator

We enable the execution of semantic SQL queries in iPDB by implementing the Operator
predict
. Regardless of the inference type,
predict
has three stages: the
configuration
stage, the
loading
stage, and the
execution
stage.
The
configuration
phase probes system defaults, session options, model-specific options, and configures
predict’s
model execution. Next, the
loading
phase either loads a locally stored model and its decoder sampling chain or initializes the API clients for remote models.
In the
execution
stage, the inference operator adheres to the push-based vectorized execution framework of DuckDB.
Predict
is executed once the operators in the sub-trees have aggregated a sufficient data chunk, producing an output chunk that contains the processed dataset.
Predict
is supplied with a consolidated data chunk from the input relations that consists of a set of rows organized as column vectors. It probes only the columns designated as inputs for the LLMs. For each row, it extracts the relevant input values and appends them to the prompt as key-value pairs.
Additionally,
Predict
pre-processes the prompt to ensure the generated output is optimal and structured. Once the prompt is thoroughly populated, it is fed into the LLM that generates the desired results. Finally,
Predict
extracts the structured output values from the LLM-generated results and populates them into the output data chunk in their respective predicted columns.

5.1.
Implicit Prompt Rewriting

iPDB rewrites the LLM prompt from within
predict
to embed the tuple’s data into the prompt. The extracted prompt, with user-provided placeholders at query time, is reformatted to remove the placeholders, and embed tuple data as key-value pairs. If multi-row prompt marshaling is used, the input key-value pairs are embedded as an array.
Further refinements to the prompt are introduced transparently to the user, e.g., stating the types of the generated outputs and the number of tuples to process. If an LLM produces unparsable or ambiguous outputs, the operator applies fallback strategies, e.g., re-prompts with stricter formatting instructions.

5.2.
Structured Output Generation

One challenge in incorporating LLMs into the relational model is obtaining consistent, schema-compliant output. iPDB augments user prompts with structural constraints, e.g., requiring outputs in JSON format, to ensure that predictions can be parsed reliably. Upon loading the physical predict operator, it first takes the prompt and output columns to determine an output format structure.

Grammar Forced Generation for Local Models:

We use context-free grammar to guide and constrain sampling of local LLM models. LLMs’ decoders use sampling parameters, e.g.,
temperature
,
top_p
, to pick the next token from the top
k
tokens. iPDB uses grammar-based sampling rules to constrain the top-k tokens. The grammar is constructed using Backus-Naur Form to produce key typed value outputs. At execution, push-down automation samples the next tokens by filtering candidates that match one of the grammar rules.

Guided Generation for Remote Models:
Unlike local LLM models, iPDB cannot extend the generation algorithm. However, some models support a structured output format parameter in their inference parameter. If this is the case, the operator passes the output column names and types as a JSON schema. Otherwise, the operator falls back to guiding the LLM to produce structured outputs by instructing the model from system instructions to produce a parsable JSON object or array. It is instructed not to include any extra text, explanations, language specifiers, produce <key>: <typed value> pairs, and must be parsable by a standard parser.

Supported Data Types:

To adhere to the concept of atomic attributes in relational databases, the inference should produce attributes with atomic values. It is trivial for tabular models (e.g., DNN models) that output a predefined set of typed columns. However, text-native models, e.g., LLMs produce text output regardless of the underlying type of the attributes they produce. Although it is feasible to treat any value returned by the LLM as text, this limits the potential operation applicable to that extracted attribute (e.g., a range predicate on an age value represented in a string). Thus, iPDB allows users to extract typed values from the language models. This behavior is achieved by instructing the model to produce parable values for each type and post-processing the generated text to extract values in the corresponding type. Table

6.
Optimizing Semantic SQL Queries

A vital reason for the widespread adoption of relational databases is the declarative nature of SQL. It is the database system’s responsibility to generate an optimal execution plan for the given query. iPDB aims to optimize semantic SQL queries to achieve minimal latency and cost within defined accuracy guarantees.

6.1.
Prompt Deduplication

Duplicate values in a relational table are common. It is possible for duplicate values to exist in a stored database table or to be created in an intermediate relation during an operation, e.g., a join on a many-to-many table. However, naively asking the LLM the same prompt and inputs is redundant. Thus, iPDB utilizes a deduplication mechanism with a key-value cache in Operator
predict
.
Predict
maintains a concurrent hash table of input values and the LLM’s parsed output throughout the lifetime of
predict
. Before calling the LLM,
predict
checks and retrieves if an existing cache value is hit for the given input values. Hence, this results in fewer LLM calls and fewer tokens given to the LLM, reducing the cost.

6.2.
Multi-row Prompt Marshaling

LLM inferencing over a table makes an LLM call for every tuple. This is slow and inefficient. If a set of tuples is prompted to the LLM as a batch, it reduces the overall number of LLM calls. iPDB takes advantage of DuckDB’s vectorization to marshal the user-configurable number of tuple values that fit within the LLM’s context. The LLM is instructed to produce an array of predictions for each tuple. Multi-row prompt marshaling in iPDB is enabled alongside prompt deduplication. If an input value of a tuple is already in the cache, the tuple is not included in the batch, but the cached LLM output is returned along with the other tuples in that batch.

6.3.
Parallelization of LLM Calls

iPDB runs LLM calls in parallel across multiple threads. Users can specify the number of available threads system-wide or per model. This configuration enables users to parallelize calls without exceeding the rate limits set by proprietary LLM vendors. However, during batched parallel execution, the entire batch may fail if a single item in the batch fails. In this case, iPDB falls back to parallel execution of each tuple in the corresponding batch only for that failed batch. Along with multi-row prompt marshaling and parallel LLM calls, iPDB reduces the latency for a given workload by a significant factor compared to serial per-tuple execution of an LLM.

6.4.
Semantic Predicate Ordering

In relational query optimization, the order in which predicates are applied is important. Having a highly selective predicate before expensive operations, e.g., sort or join, produces a more efficient query execution plan. Thus, traditional optimizers assume predicates as zero-latency operations and push them to the closest query sub-tree that contains the relation set of the predicate operation. This optimization is invalid for semantic predicates due to their high execution costs.
Thus, naively pushing LLM predicates down results in redundant LLM calls that may be removed by other traditional filters. Thus, iPDB pulls
predict
operators that contain a predicate on the predicted columns up the query tree. This results in fewer LLM calls that in turn reduces latency and cost.

6.5.
Semantic Select vs. Join Ordering

A key distinction of semantic select is that it is selective yet expensive, unlike traditional filters that are virtually cost-free. Naively pushing semantic selects under joins can result in redundant LLM calls, as inference may be performed on tuples that are later discarded by the join condition. Whether the tuples get eliminated or not depends on which side of the join the semantic select is located (e.g., primary vs. foreign key side). iPDB optimizes both the semantic select and the joins by reordering semantic selects relative to joins in a cost-aware manner, ensuring that expensive inference is only applied when necessary. This optimization is done by pulling or pushing the semantic selects across a join. Which either reduces redundant calls while preserving query semantics or reduces the join size. Section
7.9
analyzes the impact of ordering semantic selects vs. relational joins.

6.6.
Semantic Predicate Merging

When a query contains multiple semantic operators, iPDB may merge them into one prompt to minimize redundant inference. However, not all semantic operators can be merged, and doing so may not improve efficiency, e.g., consider two LLM calls on the same attribute, where instead of invoking one LLM call for sentiment analysis and another for topic extraction, iPDB combines both tasks into a single inference request that outputs multiple predicted attributes. This optimization not only reduces the number of model calls but also leverages LLMs’ contextual awareness to jointly perform related tasks more effectively. However, merging two highly selective semantic selects may negatively impact performance as the merged calls will perform redundant tasks that would be eliminated by the other predicate.

Impact of Semantic Select vs Join Ordering

Impact of Semantic Select vs Join ordering.

In a one-to-many relationship, when the Semantic Select is on the foreign-key side, applying the Semantic Select before the join minimizes latency. Observe that the size of the resulting join is the cardinality of the foreign key relation. Since the LLM call is on the foreign-key side, the number of LLM calls is unaffected whether the join or the select is executed first. However, executing the select first reduces the join cost, resulting in an overall execution time of 49.804s versus 51.130s. Thus, the optimal strategy is to perform the select first.

If the select is on the primary-key side, as in Figure
7
, then the semantic operator may be applied to duplicate entries on that side, since the resulting join has the cardinality of the foreign-key relation. The naive strategy would be to push select under the join to eliminate duplicate inference. However, the join condition in a one-to-many join may eliminate tuples on the primary-key side. Thus, using iPDB’s deduplication, the optimal strategy is to pull up the select and infer only the unique values of the primary key side.

In a many-to-many join, tuples under the semantic select can appear multiple times in the output of the join. A tuple may also not appear in the output relation. Thus, pushing select under the join can result in making redundant LLM calls. Thus, the best strategy is to pull up the select over the join. Deduplication eliminates the need to recompute outputs of multiple instances of the same input.

7.10.
Semantic Operator Ordering: Best Practices

Performance of semantic operators depends on the input and task. Hence, the ordering of semantic operators can change the latency and monetary cost. A specific ordering may result in redundant LLM calls, inflating latency and expenses. While the optimization of semantic operator ordering is out of the scope of this work; we present our observations and guidelines when querying iPDB.

In a workload that selects movies based on predicted language and genre, the language prediction from the title consistently uses fewer tokens and runs faster than the genre prediction using the plot attribute. Because the titles are shorter relative to lengthy plot descriptions. Upon changing the selectivity of the first semantic operator and comparing both orderings. Results show that when the first operator is reasonably accurate and highly selective, placing it first reduces the total number of tuples and tokens seen by the second operator, thereby decreasing overall runtime.

However, we observed that the genre classifier is inaccurate, reducing the number of tuples that pass through when applied first. When the plot
\rightarrow
title ordering is applied, fewer tuples are sent to the second operator, yielding lower total runtime despite a higher per-tuple token cost. This highlights that individual operator accuracy, not just selectivity, affects the cost of different orderings. Hence, we recommend ordering the operators first by input size, then by selectivity, and finally by quality.

Related Work

Several recent studies aim to address the execution of ML and semantic queries in databases.

Document Precessing Systems:

Palimpzest
(
15
)
implements a physical optimization scheme for semantic operators for document processing. The user defines the imperative set of semantic operators to analyze a document, which will be mapped to a logical plan. The key contribution in the work is the physical optimizer that selects the best model for each semantic operator for a given optimization policy. DocETL
(
21
)
offers a configuration interface where users can plan for the semantic operations. These systems have shown promising results in document processing, but they are not ideal for structured data in the relational model. They do not provide a declarative SQL-like interface, and queries must be defined imperatively. Both systems only allow semantic operations, lacking the ability to utilize traditional operations.

Systems with ML/AI UDFs:

Several research and production-ready systems have introduced Python-based user-defined functions. This enables users to conveniently write model inference logic in Python and use the UDF interface to bind it with the database. However, in a generic UDF implementation, the database treats the inference function as a black box that limits its optimization capabilities. Additionally, the user has to implement and optimize how the model is inferred in the UDFs. Several recent works have proposed UDFs optimized for ML and LLM inference. EvaDB
(
9
)
offers LLM inference in SQL with UDFs and an adaptive optimization technique to route conjunctive predicates. However, the optimization is limited to such predicates. Flock
(
4
)
implements an LLM extension for DuckDB with scalar and aggregate LLM inference. However, it is incapable of performing semantic joins, semantic relations, or table inference. Also, both lack the ability to extract typed information from generated outputs, which is vital in relational settings.

Systems with ML Operators:
Few studies propose to integrate model inference at a granular level in the database as native ML operators. Recent work
(
19
)
implements a model inference operator in the Umbra database engine that is capable of loading and executing pre-trained models. It aims to minimize data movement and copy. However, it is limited to tabular deep learning models. Similarly, other work
(
11
)
implements a deep learning operator that has common primitive layers (fully connected layer, RNN, LSTM) and a model weight storage technique. It has a novel technique for in-database inference. However, its set of compatible models is limited.
(
10
)
extends towards inferencing deep learning models.

ML-to-SQL Systems:

Other works focus on implementing model inference in standard SQL primitives. The Duck’s Brain
(
20
)
propose neural network training and inference using recursive CTEs in DuckDB. ML-TO-SQL
(
11
)
converts common model layers to standard SQL. MADlib
(
7
)
trains and inferences classical ML models within the database with SQL. These efforts strive to achieve in-database inference with minimal changes to the underlying database engine. However, this approach limits the generalizability to different models, which is crucial in this highly dynamic model development space.
In contrast, iPDB combines the strengths of relational databases with flexible LLM inference. It allows scalar, table, and aggregate functions in SQL queries to directly use LLM-based information extraction, filtering, and aggregation on both structured and unstructured data. iPDB supports typed data extraction, semantic joins, and compatibility of both local and remote models, resulting in a generalized, declarative, and extensible solution that bridges traditional query execution with semantic operations.

9.
Conclusion

We introduced iPDB, an extension of SQL with inline LLM inference, enabling semantic queries directly within relational databases. By unifying relational operations with LLM based semantic operators, iPDB enables semantic querying without external pipelines. We demonstrate a series of use case queries on how this integration offers a practical, declarative approach for combining traditional SQL with semantic data processing. The optimization introduce for logical planing and the execution of semantic operators shown 1000x performance improvement over the state-of-the-art in terms of latency, while maintaining correctness.
