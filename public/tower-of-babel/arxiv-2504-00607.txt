Contextualized Autonomous Drone Navigation using LLMs Deployed in Edge-Cloud Computing
Hongqian Chen, Yun Tang, Antonios Tsourdos, Weisi Guo

Abstract
Autonomous navigation is usually trained offline in diverse scenarios and fine-tuned online subject to real-world experiences. However, the real world is dynamic and changeable, and many environmental encounters/effects are not accounted for in real-time due to difficulties in describing them within offline training data or hard to describe even in online scenarios. However, we know that the human operator can describe these dynamic environmental encounters through natural language, adding semantic context. The research is to deploy Large Language Models (LLMs) to perform real-time contextual code adjustment to autonomous navigation. The challenge not evaluated in literature is what LLMs are appropriate and where should these computationally heavy algorithms sit in the computation-communication edge-cloud computing architectures. In this paper, we evaluate how different LLMs can adjust both the navigation map parameters dynamically (e.g., contour map shaping) and also derive navigation task instruction sets. We then evaluate which LLMs are most suitable and where they should sit in future edge-cloud of 6G telecommunication architectures.

I-A

Review of LLM-informed Navigation

The attention-based transformer architecture in LLMs utilizes a self-attention mechanism to process input data. Unlike previous models such as RNNs and LSTMs, which process data sequentially, transformers handle input data in parallel. This parallel processing not only enhances model efficiency but also strengthens the model’s ability to understand the context within language. During the training of an LLM, the model typically undergoes two main phases: pre-training and fine-tuning:

•

In the pre-training phase, the model is trained on a large amount of text using unsupervised learning techniques to gain a general understanding of language and context.

•

In the fine-tuning phase, the model is adjusted on a smaller, task-specific dataset to perform well on specific tasks such as answering questions or classification.

LLMs as such have the strong ability to semantically contextualize a wide range of algorithms. For example, in

I-B

Gap and Novelty

The research is to deploy Large Language Models (LLMs) to perform real-time contextual code adjustment to autonomous navigation. LLMs translate user natural language into formal code generation, modifications, or parameterizations in real time. What is not sufficient acknowledged are two important areas: (1) how can LLMs generate instruction sets for autonomous navigation that requires several sub-tasks, and (2) which LLMs are most suitable for mobile agents and where they should sit in future edge-fog-cloud continuum of 6G telecommunication architectures. We aim to show how we can create realistic urban drone navigation scenarios via a simulation platform and:

•

Using LLMs to contextualize path planning - digesting situational contexts and new obstacle data.

•

Using Small language models to generate sequence of sub-tasks and tactical control commands for a planned path;

•

Evaluate the suitability of different LLMs (GPT, LLama, Moonshot, Qwen) in terms of computation and latency and where they should sit architecturally to enable the above functionalities;

Combined, they offer a new level of LLM-navigation architecture for real-time navigation situations for future urban mobility.

II-A

LLM-informed Navigation: Path Planning Level

For the LLM to adjust navigation algorithms (Fig.
1
A-C), it is first necessary to inform the LLM of the format of the original map, allowing the LLM to understand and analyze the meaning of the JSON-formatted map. Subsequently, the changes in the map must be conveyed to the LLM in human language, and the LLM is required to comprehend the updated information about the map. It should then alter the map according to the construction method of the original map, outputting the new map in the JSON format of the original map. Finally, the map outputted by the LLM needs to be passed to path planning algorithms, such as the A* algorithm, to generate a new path.

II-A
1
Map Information Parsing

In this process, the LLM’s input is map information in JSON format, and the output is its understanding of the map information. The understanding of the map information here is merely to verify whether the LLM has truly comprehended the JSON-formatted map and does not serve as subsequent input. However, it should be noted that the LLM has the capability to remember context. This part of the input is also saved in the LLM’s memory, which means that in subsequent steps, the LLM can also know in what form the original map was constructed without additional input.

Parsing this map involves creating a 20x20 grid in a data structure see Fig.
2
A, such as a two-dimensional array. Each cell of the grid would be initialized to represent open space. The obstacles would then be used to mark certain cells as obstacles, which should be avoided when calculating a path from the start to the end.
For a navigation algorithm, the grid would be scanned to identify the starting point and end-point. Then, the algorithm would consider the map’s dimensions and the positions of the obstacles to determine a viable path while adhering to the no-fly zones. The specific logic for avoiding obstacles would depend on the algorithm used.

II-A
2
LLM-adjusted Potential Fields

At this stage, the LLM needs to dynamically adjust the map based on the description in human language and output it in the original JSON map format, as shown in the Fig.
2
B. Note that this stage must be conducted continuously with the previous process involving the LLM; otherwise, without the format information of the map in the LLM’s memory, it cannot output the correct map format:

•

Example Input: ”Next I will give you some new descriptions, and you need to regenerate the map based on the description. At (13, 15), I was suddenly notified that there was a large flock of birds, covering an area of about 3 grids. I need to avoid this area. Please generate a new map and output your map in the original json format.”

•

Output: “To incorporate the new description into the existing map and regenerate it while adhering to the original JSON format, you would add an entry for the bird flock to the (obstacle list). The area covered by the birds is approximately 3 grids, so you might define a rectangular area to represent this on the map.

This JSON structure maintains the original format and includes the new obstacle, allowing any navigation algorithm that uses this map to navigate around the bird flock as well.

II-B

LLM-informed Navigation: Sub-Task Instruction Level

For the LLM to create instruction sets of sub-task sequences (Fig.
1
D), this is traditionally executed by a human operator following rules and regulations that include for example pre-flight check lists,…etc.

Here, we use Moonshot LLM to create instruction sets, subject to mission requirements:

1.

Pre-Flight Check: Before takeoff, perform a pre-flight check to ensure the drone and its systems are operational.

2.

Takeoff: Initiate the takeoff sequence, lifting the drone off the ground to a safe altitude for the initial hover.

3.

Hover: Once airborne, hover at the starting point (0, 0) to stabilize and confirm the drone’s readiness to proceed.

4.

Navigate to First Waypoint: Begin the flight by flying forward to the first waypoint, maintaining a steady altitude and watching for any obstacles.

5.

Sequential Waypoints: For each subsequent waypoint in the path [(0, 1), (0, 2), …, (19, 19)], I would fly forward to next coordinate, perform turn on approach, and adjust altitude if needed.

6.

Avoid Obstacles: Continuously scan for obstacles and be prepared to adjust the flight path to avoid them while keeping the drone on course.

7.

**Hover Before Turns**: Before making a significant directional change, I might choose to hover momentarily to assess the surroundings and ensure a clear path.

8.

Final Approach: As the drone approaches the final waypoint (19, 19), I would slow down and prepare for landing.

9.

Land: Execute a safe landing sequence, bringing the drone down gently to the ground at the endpoint.

10.

Post-Flight: After landing, perform a post-flight check to ensure the drone is intact and ready for future flights.

III-A

Evaluation Criteria

Evaluation of LLMs generally centers around their outputs; in this case it is to see if the code generated or modified is correct or not compared to human coder. There are a number of evaluation criteria for error categories, each with different error sources
[
13
,
14
,
15
]
.

Through the aforementioned system setup and methodology, we check the output of the LLMs and the evaluation criteria include the following items:

1.

Can the map be correctly understood?

2.

Can the map be correctly modified for the lunch break scenario? Errors include two types: failure to correctly modify the map and incorrect map format output.

3.

Can the map be correctly modified for the emerging scenarios (e.g., bird flock)? Errors include two types: failure to correctly modify the map and incorrect map format output.

4.

Can the path planned by the algorithm be correctly understood and translated into flight instructions in human language? Errors include misunderstanding of the path and incorrect output in human language.

5.

Can the path be correctly understood and transformed into drone control commands? Errors include incorrect understanding of the path and incorrect drone action commands.

III-C

Next Steps: Future 6G Architecture for Native LLM-Navigation

As shown in Fig.
3
, the future enabling computing-communication architecture will sit inside an Open Radio Access Network (ORAN) as part of 6G telecommunication vision. Here, native AI including LLMs will be embedded in the telecommunication GPUs, to serve both the telecommunication and its application end-user services. In this case, the LLMs will act as both real-time tactical command via (xApps) and near real-time path planning (rApps). These Apps are programmable into ORAN and act as a near operation computation capability.

We saw from Table
I
that some smaller LLMs are suitable for edge implementation, sitting at the edge Distributed Unit (DU) and Radio Unit (RU) architecture level, offering low latency command and control for autonomous platforms. Other larger LLMs are suitable for slow but accurate path planning, taking into account wide range of contextual requirements and obstacle data - sitting in the cloud Central Unit (CU).

IV
Conclusions and Future Work

In this work, we analyzed the entire drone navigation process and found that traditional algorithms often fail to utilize information in human language to adjust maps in a timely manner when faced with dynamically changing environments; moreover, the output of the algorithms is based on mathematical model maps, which is not conducive to guiding drone pilots. Therefore, we introduced large language models (LLMs) as a bridge between the mathematical model world and the real human world. This approach can quickly and dynamically adjust maps based on instructions in human language, and on the other hand, they can quickly generate drone navigation instructions in human language based on the results of path planning algorithms. Furthermore, they can even directly generate flight control instructions for drone navigation.

We conducted various experiments with multiple LLMs and different maps, and the results prove that our work is reliable. Our work not only has good practical significance but also proposes a general framework for LLM-assisted drone navigation tasks, thus allowing for further research within our framework. We also compared LLM performances and suggest architecturally how to deploy them for future 6G native AI architectures.

Our future work will look to enhancing the LLM performance and will need to use Retrieval Augmented Generation (RAG) and inductive logic to achieve better inductive reasoning
[
16
]
.
