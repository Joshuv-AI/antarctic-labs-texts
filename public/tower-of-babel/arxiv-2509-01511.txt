Type-Based Incorrectness Reasoning
Zhe Zhou, Benjamin Delaware, Suresh Jagannathan

Abstract
. A coverage type generalizes refinement types found in many functional languages with support for must -style underapproximate reasoning. Property-based testing frameworks are one particularly useful domain where such capabilities are useful as they allow us to verify the completeness , as well as safety, of test generators. There is a surprising connection between the kind of underapproximate reasoning coverage types offer and the style of reasoning enabled by recently proposed Incorrectness Logic frameworks. In our presentation, we propose to explore this connection more deeply, identifying mechanisms that more systematically integrate incorrectness reasoning within an expressive refinement type system and the opportunities that such integration offers to functional programmers, program verifiers, and program analyzers and related tools.



1.
Introduction

In recent work, we proposed
coverage refinement types
(
Zhou et al. 2023a
;
Zhou et al. 2023b
)
as a mechanism to automatically verify the

completeness
of test input generators used in property-based
testing (PBT)
frameworks
(
Lampropoulos et al. 2019
;
Claessen and Hughes 2000
)
. An
input generator is complete with respect to some property if it is
capable of producing
all
elements that satisfy that
property. Analogous to how Incorrectness Logic (IL)
(
O’Hearn 2019
)
precisely
captures the conditions that can trigger a program fault, our coverage
type system uses “
must
-style” underapproximate reasoning
principles to characterize the possible outputs of a program. In our
system, properties are encoded as type qualifiers in the vein of
refinement type systems
(
Jhala and Vazou 2021
)
. When a program type checks
against a coverage type, however, it is guaranteed to be able to
produce
all
values satisfying the qualifier of that type, in
contrast to standard refinement type systems in which a refinement
constrains the set of values an expression
may
produce.

.

Verifying completeness properties in the context of PBT is quite
different from the typical use case of IL, which has been primarily
studied in the context of bug finding
(
O’Hearn 2019
;
Raad et al. 2020
;
Le et al. 2022
)
. It is
interesting to ask if coverage types are sufficiently expressive to
also verify program incorrectness, similar to other IL
proposals. Our proposed talk will explore this question, showing how
coverage types can be used to reason about the incorrectness of OCaml
programs, using a small set of straightforward extensions to the
original source language and type system of
Zhou et al. 2023a
.

Coverage types can be seen as a type-based interpretation of
Incorrectness Logic. As shown in

A standard refinement type

application of the built-in random number generator

Intuition

This example illustrates how can perform
incorrectness reasoning with coverage types. After modifying the
original program by adding a random initialization procedure
consistent with an underapproximate precondition at the beginning of
the code fragment, we can then ask if it can cover all values
consistent with the underapproximate postcondtion. For example, the
program under test in this example takes the results of generators
(e.g.,
{\tt int\_range\ 11\ 11}
), and can be treated as a
generator that covers the value
42
.

Following this intuition, we new describe a more systematic approach
to typed-based incorrectness reasoning in an expressive functional
language like OCaml, focusing in particular on the assumptions and
assertions from imperative language that don’t exist in a pure
functional language.

Assumptions

We have informally seen how a coverage type
system can verify the incorrectness of a given program, provided the
programmer has inserted appropriate in generators (e.g.,

{\tt int\_range}\ 11\ 11
) to mark the space of inputs consistent
with a desired precondition. To improve usability and readability,
however, we can instead introduce dedicated syntax to express our
assumption on the existence of such a generator. We do so via the
term
{\tt assume}\ {\color[rgb]{0,0.2773,0.6719}\mbox{\rm{[}}}{}{\nu{:}{b}\,|\,{\phi}}{\color[rgb]{0,0.2773,0.6719}\mbox{\rm{]}}}{}\equiv{\tt f\ ()}

assumes the existence of some function
{\tt f}
that has been
type-checked against the function type

{\tt unit}{\,\shortrightarrow\,}{\color[rgb]{0,0.2773,0.6719}\mbox{\rm{[}}}{}{\nu{:}{b}\,|\,{\phi}}{\color[rgb]{0,0.2773,0.6719}\mbox{\rm{]}}}{}

input generator that covers all values in qualifier
\phi

Discussion and Future Work

These examples establish a number of tantalizing links between
coverage types and IL. There are several interesting future directions
we hope to explore to flesh out these connections further; we list
just one of them below, and plan to discuss these links in more detail
at our presentation, should this proposal be accepted.
