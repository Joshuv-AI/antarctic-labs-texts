Runtime-Augmented LLMs for Crash Detection and Diagnosis in ML Notebooks CCS: Software and its engineering Software testing and debugging
Yiran Wang, José Antonio Hernández López, Ulf Nilsson, Dániel Varró

Abstract
. Jupyter notebooks have become popular for machine learning (ML) development, enabling interactive and iterative experimentation. However, ML notebooks are prone to bugs, among which crashes are the most disruptive. Despite their practical importance, crash detection and diagnosis in ML notebooks remain largely unexplored. We present CRANE-LLM, a runtime-augmented approach that provides large language models (LLMs) with structured runtime information extracted from the notebook kernel state to detect and diagnose crashes before executing a target cell. Given a sequence of successfully executed cells and a target cell, CRANE-LLM incorporates static code context together with extracted runtime information, such as object types, tensor shapes, and data attributes, into LLM prompts to predict whether the target cell will crash (detection) and to explain the underlying cause (diagnosis). We evaluate CRANE-LLM on JunoBench, a benchmark of 222 ML notebooks comprising 111 pairs of crashing and corresponding non-crashing notebooks, spanning multiple popular ML libraries and crash root causes. Across three state-of-the-art LLMs (i.e., Gemini, Qwen, and GPT-5), incorporating runtime information consistently improves their crash detection and diagnosis performance by 7–10 percentage points in accuracy and 8–11 percentage points in F1-score. The improvements are more pronounced when diagnosis is required, indicating that runtime context is especially valuable for reasoning about the causes of crashes than merely identifying their presence. Moreover, while augmenting LLMs with runtime information consistently improves detection and diagnosis of crashes in ML notebooks, the extent of these improvements varies across ML libraries, crash causes, and the LLM in use, and depends on the integration of complementary categories of runtime information, such as structural execution context, object types, and value-level data attributes, rather than relying on any single source of runtime information.

Runtime information in ML notebooks

Unlike traditional Python scripts that execute linearly from start to finish, notebooks allow nonlinear and selective executions. The kernel maintains a persistent execution state across cells
(
32
;
46
)
, meaning that objects created in one cell remain accessible to subsequent cells.

This kernel state represents a complete snapshot of the program’s execution at a given time and can be accessed while the session is active.
However, directly inspecting kernel variables often yields impractical results. As shown in
Figure 1
(middle), some objects (e.g., dataframes) display all their values when printed, whereas others (e.g.,
Keras
iterators) reveal only minimal type information.
While functions like
\lst@ifdisplaystyle
vars
()
expose internal attributes, they may produce excessive low-level values. These make it challenging to obtain a meaningful and appropriately detailed summary of the kernel state for downstream analysis.
To address this,
runtime information extraction
is necessary to selectively summarize object properties into structured, concise, and interpretable representations that preserve essential runtime semantics.

This extracted runtime information enables the prediction of potential crashes in a target cell before executing it, particularly for data-dependent errors that cannot be inferred from source code alone.
For example, in
Figure 1
(right), the number of classes in
\lst@ifdisplaystyle
train_images
, cannot be determined from the source code, while the model output layer defines five neurons. Determining whether the last code cell will crash therefore requires extracting the generator’s data attributes from the kernel state.

Kernel state corruption in notebooks

In interactive notebooks, executing a crashing cell corrupts the kernel by leaving variables, objects, or external resources in a partially updated or inconsistent state.
When a crashing cell is executed, statements successfully executed before the crashing line may already have mutated global variables, overwritten data structures, or modified model parameters, while statements after the crashing line are skipped.

For example, in
Figure 2
, the notebook first loads the data and constructs a neural network using
PyTorch
. Inspecting the model parameters after executing the first two cells shows their initial state (left side of the figure). When the crashing cell is executed, the training statements run without error, but the cell fails during validation due to incompatible input dimensions. Although the cell crashes, the
\lst@ifdisplaystyle
optimizer
.
step
()
call has already updated the model parameters, which are stored as mutable objects in the kernel. After executing the crashing cell, if the model parameters are inspected again (as shown on the right side of the figure), one can see that they have changed. This leaves the kernel in an inconsistent state: the model now reflects a partially completed training step that should not have been committed. If the developer fixes the bug and re-executes the cell, the optimizer updates the model parameters again. Because the first iteration partially executed before the crash, the parameters now reflect a partial update followed by a repeated update, which can silently corrupt the model and produce incorrect or unpredictable behavior.

Because Jupyter provides no built-in mechanism to snapshot, roll back, or reliably serialize the full kernel state, such corruption is irreversible. As a result, restoring correctness requires restarting the kernel and re-executing all prior cells, including potentially expensive preprocessing steps. This behavior makes crashes particularly costly in notebook-based ML workflows and motivates techniques for early crash detection before cell execution to prevent kernel state corruption.

3.1.
Runtime information extraction

First, we extract runtime information from the current Jupyter notebook kernel state (i.e., the program state generated by executed code cells).
Because the full kernel state can include all objects and their nested data structures, it is often prohibitively large to feed into an LLM. Providing the entire context would not only increase token usage and computational or economic cost, but also introduce noise that could distract the model from identifying information relevant to the task.

To mitigate this, we first filter the kernel state to retain only information deemed relevant to the target cell. Specifically, we parse the target cell’s abstract syntax tree (AST) to identify referenced variables, function calls, and attributes, and then collect the corresponding runtime data from the kernel.
Furthermore, as shown in
Figure 1
, directly inspecting runtime variables can either reveal excessively detailed raw values or expose almost nothing. We summarize the relevant objects into structured abstractions that preserve concise yet representative attributes.

Our choice of target object types for runtime summarization is motivated by
a prior study on ML notebook crashes
(
49
)
. The study shows that data-related bugs, such as tensor shape mismatches and dataset misalignments, are among the most frequent, and identifies
TensorFlow/Keras
),
PyTorch
, and
Scikit-learn
as the three most challenging ML libraries for notebook developers.
Guided by these findings, we extract runtime information for commonly used ML data structures, including tensors (
PyTorch
,
TensorFlow/Keras
), arrays (
NumPy
), and dataframes (
Pandas
).
Furthermore, we summarize ML-specific objects that encapsulate runtime state directly affecting execution outcomes in the three challenging libraries, such as image data iterators and datasets in
TensorFlow/Keras
, iterable datasets and data loaders in
PyTorch
, and label encoders and models in
Scikit-learn
.

3.2.
Crash detection and diagnosis

After extracting runtime information, we construct a prompt that combines three key elements: (1) the ordered sequence of previously executed cells, (2) the target cell under analysis, and (3) runtime information relevant to the target cell. This prompt is used to query an LLM to reason and detect whether the target cell will crash.

Designing the prompt for CRANE-LLM is guided by two design considerations. First, providing the LLM with
successfully executed cells in execution order
allows it to analyze the source code and reason about dependencies that may influence the target cell
(
3
)
. This reflects the incremental execution model of notebooks and provides the necessary code context to understand data flow and variable dependencies. Second, the prompt includes
relevant runtime information
, such as object types and data attributes, to expose execution states that are typically unavailable from source code alone. This information is particularly important for ML notebook crashes that depend on concrete runtime properties, such as tensor shape mismatches or violations of data constraints.

The prompt explicitly instructs the LLM to
reason step by step
to encourage chain-of-thought reasoning when producing its prediction. Prior work has shown that such reasoning can improve performance in complex reasoning tasks
(
53
)
. In the context of ML crash detection and diagnosis, step-by-step reasoning supports analysis of crashes that emerge from interactions across data transformations, model training steps, and the model’s own expectations. For example, a shape mismatch occurs when an input tensor with a specific shape reaches a layer expecting a different size, or when the number of classes produced by a data generator does not match a model’s output layer. Encouraging step-by-step reasoning helps the LLM reconstruct these dependencies and identify plausible root causes of crashes.

For LLMs that support structured output through APIs (e.g., Gemini), we enforce a predefined JSON schema in the API call. For other LLMs, the prompt instructs the LLM to return its response in the same JSON format. The output schema consists of a concise diagnostic explanation (i.e.,
reasoning
) followed by a binary crash
detection
verdict (
true
only when the model is confident that the target cell will crash, and
false
otherwise). This standardized output format ensures consistency across models, facilitates evaluation, and improves the interpretability of predictions. The prompt structure with an enforced JSON output schema is illustrated in

3.3.
CRANE-LLM configurations

CRANE-LLM supports multiple configurations that control the actual information provided to the LLM, including different types of runtime information, as well as explicit grounding using API information (e.g., function signatures and documentation text). These configurations enable a systematic analysis of how different sources of information affect LLM performance in crash detection and diagnosis for ML notebooks, while the default configuration uses the full set of supported runtime information and without including API information grounding.

Runtime information

Runtime information captures different aspects of ML execution. To support systematic analysis while maintaining interpretability, we organize the extracted runtime information into a few, high-level categories, each reflecting a distinct type of execution trace. This categorization enables to configure the use of runtime information in CRANE-LLM. For example, it supports ablation studies or targeted analysis of the contribution of specific source of runtime information.

Specifically, we group runtime information into the following three categories:

•

Structural information (S).
This category characterizes the
size, shape, or count
of datasets and runtime objects, such as tensor shapes, dataset dimensions, and sample counts. These features capture whether objects are structurally compatible with the expectations of downstream operations or APIs.

•

Representation and type semantics (R).
This category captures how data and models are represented at runtime, including
object types, data types and dtypes, and schema-level properties
. These features describe the kinds of objects manipulated during execution and their internal representations.

•

Value semantics (V).
This category captures properties of
concrete data values
and their task-level semantics, such as value ranges, presence of
\lst@ifdisplaystyle
NaNs
, number of classes, and example values. It also includes object-state information (e.g., whether a model has been fitted), which reflects runtime readiness and execution context. Together, these features characterize where observed data and object states are semantically consistent with the intended operations.

In the remainder of the paper, we use
-S
,
-R
, and
-V
to denote configurations where the corresponding category of runtime information is excluded from the
full runtime information setting
.
Each category corresponds to a distinct class of runtime failure modes commonly observed in ML notebooks
(
49
)
, in the sense that failures can arise from violations at different semantic levels. Structural failures occur when object shapes do not align with API expectations, representation-level failures arise when objects have incompatible types or internal representations despite being structurally valid, and value-level failures occur when concrete values or object states are semantically invalid even when both structure and representation are correct. This separation balances expressiveness with interpretability, allowing CRANE-LLM to isolate and study the impact of different runtime information sources while keeping the number of configurable conditions manageable.

API documentation grounding

LLMs are known to suffer from hallucination
(
62
)
, particularly in the context of code understanding tasks
(
63
;
31
)
. While static code and runtime information provide important execution context, they may not be sufficient for LLMs to reliably infer precise API semantics, especially when the LLM’s prior knowledge is incomplete or outdated, potentially due to the rapid evolution of ML APIs and the fixed knowledge cutoff of pretrained models
(
19
)
. Providing API documentation to LLMs therefore may offer an additional source of semantic grounding that could potentially improve crash detection and diagnosis performance of CRANE-LLM.

However, API documentation is frequently verbose and heterogeneous in structure
(
26
)
. Naively incorporating raw documentation can substantially increase the input token budget and distract the LLM from the core program context. To mitigate this, we do not incorporate raw documentation text. Instead, we extract structured API documentation for relevant API calls appearing in the target cell. Specifically, we identify callable APIs (e.g., methods or functions) invoked on runtime objects referenced in the target cell, and retrieve their documentation directly from the notebook kernel. The extracted documentation is distilled into a concise, structured representation, including callable signatures (parameter names, required versus optional arguments, default values, keyword-only constraints, return types, and type annotations when available), public attributes of the associated objects, and semantically critical documentation sections such as
Notes
,
Important
, and
Warnings
.

Because incorporating API documentation introduces additional input tokens and may inject auxiliary information that does
not
necessarily improve prediction performance, API documentation grounding is provided as an optional configuration in CRANE-LLM and is not enabled by default. This design enables controlled analysis of how incorporating API documentation grounding, and the resulting increase in input context, affects LLM behavior.

4.1.
Research questions (RQs)

To assess the performance of CRANE-LLM, our experiments aim to address the following research questions:

•

RQ1: To what extent does runtime information improve LLM-based crash detection and diagnosis in ML notebooks overall?

Motivation:
Many crashes in ML notebooks arise from mismatches between code assumptions and concrete runtime states, such as tensor shapes or data dimensionality. However, it is unclear whether providing explicit runtime information yields substantial benefits beyond what LLMs can already approximate from static code alone, or whether the added complexity of extracting runtime context is justified. By systematically quantifying the impact of runtime information on crash detection and diagnosis performance, we assess when and to what extent runtime-aware LLMs offer practical advantages.

•

RQ2: How does the impact of runtime information on LLM-based crash detection and diagnosis vary across different ML libraries and root causes?

Motivation:
ML notebook crashes arise from diverse root causes, such as data confusion errors and API misuse, and span multiple ML libraries with distinct abstractions and execution models. These differences suggest that runtime information may not benefit all crashes equally. Therefore, we investigate how the impact of runtime information varies across ML libraries and root causes, shedding light on which crash patterns benefit most from runtime context and whether runtime-aware approaches should be specialized or generalized.

•

RQ3: How do different types of information affect the crash detection performance of CRANE-LLM for ML notebooks?

Motivation:
Runtime information captures complementary aspects of execution, such as data structure, types, and concrete values. While such information has the potential to improve LLM-based crash detection, it is unclear which categories of runtime information are most critical for accurately identifying crashing code. Quantifying their individual contributions can guide the design of more effective and efficient runtime-aware debugging methods.
In addition, grounding LLMs with API documentation could in principle provide authoritative, library-specific knowledge that might aid crash detection. To systematically study these effects, we conduct (1) an ablation study that isolates the contribution of different runtime information categories, and (2) a controlled analysis that evaluates the impact of API documentation grounding. We focus on crash detection in these studies, as it is a prerequisite for meaningful diagnosis and enables objective comparison without confounding factors introduced by subjective diagnostic assessment.

4.2.
Dataset

To evaluate CRANE-LLM, we use JunoBench
(
48

To the best of our knowledge, at the time being, JunoBench is the only publicly available benchmark specifically designed to study crashes in ML notebooks.

We adopt JunoBench for the following reasons:
(1) JunoBench is built from Kaggle notebooks in native

(2) It systematically balances crashes across major ML and DL libraries, including 15 cases each from
TensorFlow/Keras
,
PyTorch
,
Scikit-learn
,
NumPy
and
Pandas
; 16 cases collectively from

4.4.
Evaluation

We evaluate the performance of crash detection and diagnosis of CRANE-LLM under two settings: (1)
crash detection
alone, and (2)
end-to-end crash detection and diagnosis
together.

Following prior work on bug detection and localization
(
57
;
28
;
27
)
, we evaluate our approach using standard performance metrics including precision, recall, F1-score, and accuracy.
Let TP, FP, TN, and FN denote true positives, false positives, true negatives, and false negatives, respectively. These metrics are defined as follows:

\text{prec}=\frac{\text{TP}}{\text{TP}+\text{FP}}\quad\text{recall}=\frac{\text{TP}}{\text{TP}+\text{FN}}\quad F_{1}=\frac{2\cdot\text{prec}\cdot\text{recall}}{\text{prec}+\text{recall}}

\text{Accuracy}=\frac{\text{TP}+\text{TN}}{\text{TP}+\text{TN}+\text{FP}+\text{FN}}

4.4.1.
Crash detection evaluation.

Each crash prediction output by LLMs is formatted as a JSON object containing: (i) a boolean field
detection
(i.e.,
true
or
false
) indicating whether a crash is detected, and (ii) a free-text field
reasoning
describing the diagnosis.

Crash detection performance is evaluated automatically by comparing only the predicted
detection
field against the ground truth crash label provided by JunoBench (see
Section 4.2
). This fully automated procedure enables exact, scalable, and reproducible evaluation of crash detection across all predictions. Diagnosis prediction (i.e.,
reasoning
field) does not affect detection metrics.
Specifically, each detection prediction is classified into the following two outcomes:

•

Correct:
The crash detection prediction is correct.

•

Wrong:
The crash detection prediction is incorrect.

For metric calculation under crash detection evaluation:

•

TP: a crash is predicted and the ground truth indicates a crash.

•

FP: a crash is predicted but the ground truth indicates no crash.

•

TN: no crash is predicted and the ground truth indicates no crash.

•

FN: no crash is predicted but the ground truth indicates a crash.

4.4.2.
End-to-end (crash detection and diagnosis) evaluation.

End-to-end evaluation assesses whether the crash prediction output both (1) correctly detects a crash and (2) provides a correct diagnosis when a crash is correctly detected.
Each output is classified into one of the following outcomes:

•

Correct:
The crash detection prediction is correct and, when detection is
true
, the predicted diagnosis is fully aligned with the ground truth diagnosis label provided in JunoBench.

•

Partially correct:
The crash detection prediction is correct, and the diagnosis is partially correct but contains incorrect elements.

•

Reasoning wrong:
The crash detection prediction is correct, but the diagnosis is entirely inaccurate or unrelated.

•

Wrong:
The crash detection prediction is incorrect, regardless of the diagnosis.

We treat both
partially correct
and
reasoning wrong
outcomes as
wrong
in metric calculation, since incorrect or irrelevant diagnosis could mislead developers during debugging. However, separately tracking them provides additional insight into the reasoning tendencies of the LLMs. Therefore, for metric computation, we reduce these outcomes to a binary decision reflecting practical usefulness:

•

TP: a crash is correctly detected and
correctly diagnosed
.

•

FP: a crash is detected but the ground truth indicates no crash.

•

TN: no crash is detected and the ground truth indicates no crash.

•

FN: a real crash exists but it is not detected or
incorrectly diagnosed
.

End-to-end evaluation proceeds in two stages. First, crash detection evaluation is determined automatically as described in
Section 4.4.1
. Second, for the subset of cases where both the detection prediction and ground truth indicate a crash, crash diagnosis prediction evaluation is required, which is evaluated by human annotators (introduced in the following
Section 4.4.3
).

4.4.3.
Human evaluation of crash diagnosis.

Crash diagnosis evaluation assesses the quality of the explanatory reasoning generated by the LLMs and therefore requires human semantic judgment. Diagnosis is evaluated for the correctly detected crash cases. Each prediction is classified into one of three categories:
correct
,
partially correct
, or
reasoning wrong
, according to its consistency with the ground-truth diagnosis labels provided in JunoBench (see
Section 4.2
).

We employ two human evaluators
1
1

1

Both evaluators are authors of this paper.
in the evaluation of crash diagnoses.
First, all applicable predictions are evaluated by one human evaluator. To assess evaluation consistency, a second human evaluator independently evaluates a statistically representative subset of size
n
drawn from the full set of
N
diagnoses requiring evaluation. The target sample size
n
is estimated using standard statistical sampling with a 95% confidence level and a 5% margin of error:

(1)

n=\frac{N\cdot Z^{2}\cdot p\cdot(1-p)}{E^{2}\cdot(N-1)+Z^{2}\cdot p\cdot(1-p)},

where
Z=1.96
,
p=0.5
,
E=0.05
,
N
is is the total number of applicable diagnoses (i.e., population). We adopt
p=0.5
to assume maximum variability, yielding a conservative estimate of the required sample size. Finally, inter-annotator agreement is measured using Cohen’s
\kappa
and reported to quantify evaluation reliability.

RQ3.2: Grounding LLM-based crash detection with API documentation

We evaluated an augmented variant of CRANE-LLM that incorporates API documentation as external grounding. This variant was compared with the standard CRANE-LLM setting to isolate the marginal effect of API documentation information on crash detection performance.

pp
in accuracy. Gemini and GPT-5 exhibit smaller but still consistent declines, with F1-score decreasing by 1.3
pp
and 0.9
pp
respectively, and accuracy decreasing by 0.9
pp
for both models.

These results indicate that supplying additional API documentation does not improve crash detection accuracy for any evaluated LLM and instead introduces information that appears to interfere with effective reasoning.
One plausible explanation is that the structured runtime information already provides sufficiently strong and concrete traces for detecting crashes.
Another possibility is that modern LLMs have already been trained on API documentation for widely used libraries, making the additional documentation largely redundant at inference time.
Despite extracting and structuring only semantically important API documentation, this information may still be too generic or independent from the concrete runtime state of a specific notebook execution to be used effectively by LLMs for crash detection. Consequently, it may provide limited additional help while increasing contextual complexity, leading to degraded performance. This effect is more pronounced for smaller or less robust models, such as Qwen, suggesting that model capacity and prompt-compliance robustness influence sensitivity to contextual noise.

Table 5
quantifies the additional token cost incurred by incorporating structured API documentation into the LLM input. On average, API documentation grounding introduces 855 additional tokens per notebook instance, corresponding to a 73.6% increase over the default CRANE-LLM input. The median increase is 569 tokens (35.9%), indicating that even in typical cases, API documentation constitutes a substantial expansion of the input context.
The token cost exhibits a heavy-tailed distribution. At the 75th percentile, API documentation adds 1,198 tokens, nearly doubling the input size (93.8% increase), while at the 90th percentile, it introduces 2,386 additional tokens, corresponding to a 198.1% increase. These results show that API documentation grounding can significantly inflate the input size for a non-trivial fraction of notebooks, substantially increasing inference cost and pushing inputs closer to model context limits.

From a practical perspective, this variability implies that API documentation grounding introduces unpredictable and potentially high inference costs for crash detection in ML notebooks, especially when multiple libraries or large documentation are involved. Even when structured and selectively extracted, documentation can remain verbose and heterogeneous to be used by LLMs effectively, limiting its suitability as a default input component.

Altogether, the performance and token cost results evaluate the hypothesized trade-off between richer semantic grounding and token efficiency, showing that API documentation grounding substantially increases input size without increasing crash detection performance.
Rather than diminishing the value of the experiment, these results provide empirical evidence against the intuitive assumption that additional semantic grounding necessarily improves LLM-based crash detection. In the evaluated setting, where runtime information is already available, API documentation introduces substantial token overhead without improving performance, justifying the design choice of CRANE-LLM to exclude documentation by default and to treat it as an optional, task-dependent configuration.

6.4.
CRANE-LLM achieves early crash detection by saving execution time from kernel state corruption

While CRANE-LLM introduces additional overhead for crash detection and diagnosis (e.g., an average of 1.6s per query when using GPT-5), this cost must be weighed against the extra execution time it can help avoid. In interactive notebook environments, crashes often corrupt the kernel state, requiring developers to rerun
all

To quantify this effect, we measured the cumulative execution time of all cells preceding the crashing cell across the 111 buggy notebooks in JunoBench, and compared this cost against the query latency of a representative LLM (i.e., GPT-5). While this comparison is not intended to precisely measure end-to-end developer productivity, it provides a conservative, observable estimate for execution time overhead. Across the benchmark, this analysis yields a net execution time saving of 1,103s (approximately 18 minutes), indicating that the cost of querying CRANE-LLM is typically outweighed by the execution time required to rerun prior notebook cells.

A further source of time savings arises from preventing the execution of the crashing cell itself.

Furthermore, our approach can be integrated as an interactive tool that runs as the developer edits code cells. This enables proactive crash prediction before cell execution, avoiding unnecessary model training and thereby saving considerable time during development.

7.
Threats to validity

7.1.
Construct validity

A potential threat to construct validity is that our baseline for
without runtime information
uses the ordered executed code cells, which inherently encode some runtime context, such as execution order. As a result, the measured improvements from runtime information may be slightly conservative, though this setup reflects a meaningful reproducible code context. Another potential threat arises from how crash detection and diagnosis performance is measured. To mitigate this, we adopt metrics such as precision, recall, F1-score, and accuracy, that are widely used in prior studies
(
57
;
28
;
27
)
on fault detection and localization.

7.2.
Internal validity

Our approach relies on LLMs, which introduces several threats to internal validity. First, LLMs are inherently non-deterministic and may produce different outputs across runs for identical inputs. Such variability can affect the stability of crash prediction results. To mitigate this threat, we perform five independent runs for each experimental setting and report aggregated results. For LLMs that support temperature control (i.e., Qwen and Gemini), we fix a low temperature (0.01) to reduce output randomness and improve reproducibility.
Second, the effectiveness of CRANE-LLM may depend on the specific LLM employed, due to differences in model architectures, training data, and alignment objectives. To reduce this threat, we evaluate CRANE-LLM using three different LLMs and observe consistent performance trends across models, suggesting that our findings are not tied to a particular LLM instance.

Moreover, human evaluation is involved in assessing the correctness of CRANE-LLM’s diagnosis outputs, which introduces potential subjectivity. To mitigate this threat, we employ two independent evaluators with experience in debugging ML notebooks. Inter-rater agreement is quantified using Cohen’s kappa (
\kappa=0.89
), indicating a high level of agreement and suggesting that the evaluation criteria are consistently applied. Nevertheless, as with all human judgment, the results may still be influenced by individual interpretation and should be considered with this limitation in mind.

7.3.
External validity

Our experiments were conducted on JunoBench, which consists of ML notebook crashes related to widely used libraries such as
TensorFlow/Keras
,
PyTorch
,
Scikit-learn
,
NumPy
, and
Pandas
. While these libraries are representative of mainstream supervised and data-driven ML workflows, our evaluation does not explicitly cover notebooks implementing other ML paradigms, such as unsupervised learning, reinforcement learning, active learning, or domain-specific learning frameworks.
In addition, although JunoBench includes a diverse set of crashes across multiple ML libraries and notebook-specific issues, it may not fully capture the types of failures encountered in industrial ML systems. Consequently, the generalizability of our approach to less common ML paradigms, specialized libraries, and industrial settings remains a threat to external validity and should be explored in future work.

Moreover, the opaque and evolving nature of LLM training data and model updates introduces another threat to external validity. Results obtained using current LLM versions may not fully generalize to future model releases. Nevertheless, our emphasis on relative performance comparisons and cross-LLM evaluation helps mitigate this concern.

Unlike general-purpose programs, ML/DL programs frequently fail due to mismatches between data properties, tensor shapes, and model expectations, which are often difficult to infer from source code alone.

8.3.
Summary and our contribution

Prior work on ML bug detection largely relies on static rules, predefined verification conditions, or supervised learning over fixed fault categories.
Static and rule-based approaches require manually crafted rules and detect known bug patterns but lack execution awareness, limiting their ability to identify crashes that depend on runtime data attributes.
Dynamic approaches capture runtime behavior but typically detect faults during or after execution and are not designed for early crash detection.
Learning-based approaches depend on labeled datasets and predefined bug categories, restricting their adaptability and diagnostic flexibility.
LLM-based methods show promise for reasoning about ML code without handcrafted rules, but have been applied primarily in a static setting or as interactive assistants.

To the best of our knowledge, no prior work systematically extracts and structures different categories of runtime information from the notebook kernel state and integrates them into LLM prompts for crash detection and diagnosis
before
executing the target cell in ML notebooks.
CRANE-LLM addresses this gap by combining LLM-based reasoning with runtime information (e.g., object types, tensor shapes, and data attributes) extracted from the current notebook kernel state to predict crashes before executing a target cell, and to provide natural-language explanations that reconstruct the causal chain leading to the failure, without relying on handcrafted rules or task-specific training.

9.
Conclusions

We present CRANE-LLM, a runtime-augmented LLM-based approach for crash detection and diagnosis in ML notebooks.
CRANE-LLM integrates runtime information extracted and structured from the notebook kernel state, such as object types, tensor shapes, and data attributes, together with static code context into LLM prompts, enabling the LLM to identify crashing cells and provide explanatory diagnoses before executing a target cell.
Our evaluation on the JunoBench dataset demonstrates that incorporating runtime information consistently improves crash detection and diagnosis performance across multiple state-of-the-art LLMs.
The improvements are more pronounced when diagnosis is required, indicating that runtime context is particularly valuable for reasoning about underlying crash causes than merely detecting the presence of a crash.
We also observe that the impact of runtime information varies across ML libraries, root causes, and LLMs, suggesting that the execution context contributes differently depending on the nature of the crash and the LLM’s reasoning characteristics.

Our ablation study reveals that different categories of runtime information play complementary roles.
Structural, type-level, and value-based runtime information each contribute to performance, with different LLMs exhibiting varying sensitivities to these categories.
These findings suggest that effective runtime-aware crash detection benefits from a combined representation of execution context rather than reliance on a single type of runtime information.
We also investigated whether grounding LLMs with API documentation provides additional benefits.
Our results indicate that, when runtime information is already incorporated, additional API documentation does not yield measurable performance gains and introduces substantial token cost.

While our study provides encouraging results, it comes with certain limitations that point to opportunities for future research.
Our current design uses a fixed runtime representation to establish a systematic baseline for integrating structured runtime information. We do not explore adaptive or LLM-specific selection of runtime information included, which represents a promising direction for future work.
Moreover, our evaluation is conducted on a single benchmark and a fixed set of runtime context, and we do not claim coverage of all possible ML crashes or ML libraries.
These limitations highlight that incorporating runtime context into LLM reasoning requires careful design choices regarding what information to extract and how to present it.

Overall, our work shows that structured integration of runtime execution state is a practical and effective strategy for enhancing LLM performance in crash detection and diagnosis in ML notebooks.
Our results provide a foundation for execution-informed LLM systems and motivate future research on adaptive runtime feature selection, richer representations of runtime context, and broader empirical evaluations across diverse datasets and ML libraries.
