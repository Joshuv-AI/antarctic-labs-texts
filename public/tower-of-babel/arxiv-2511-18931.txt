Abstract
. Modern large language models integrate web search to provide real-time answers, yet it remains unclear whether they are efficiently calibrated to use search when it is actually needed. We introduce a benchmark evaluating both the necessity and effectiveness of web access across commercial models with no access to internal states or parameters. The dataset includes a static split of 783 temporally anchored questions answerable from pre-cutoff knowledge, aimed at testing whether models invoke search based on low internal confidence, and a dynamic split of 288 post-cutoff queries designed to test whether models recognise when search is required and retrieve updated information. Web access substantially improves static accuracy for GPT-5-mini and Claude Haiku 4.5, though confidence calibration worsens. On dynamic queries, both models frequently invoke search yet remain below 70 percent accuracy due to weak query formulation. Costs per accuracy-improving call remain low, but returns diminish once initial retrieval fails. Selective invocation helps, but models become overconfident and inconsistent after search. Overall, built-in web search meaningfully improves factual accuracy and can be invoked selectively, yet models remain overconfident, skip retrieval when it is essential, and falter once initial search queries underperform. Taken together, internal web search works better as a good low-latency verification layer than a reliable analytical tool, with clear room for improvement. Recent work has explored the capabilities of browsing agents and tool-augmented LLMs, examining which sources they prefer and how reachable those sources are. Yet no exploratory study or benchmark exists to directly test a core research question:
"Do LLMs actually know when they should invoke a search tool for current facts rather than defaulting to parametric knowledge, and can they retrieve what they need with minimal expensive web calls?"
. While similar questions can be studied more directly in open-source models where internal states and parameter-level traces are available, closed-source systems require external measurement and behavioural analysis to infer invocation strategy. We therefore focus on widely deployed commercial models from OpenAI and Anthropic, both because they are commonly used in real-world applications and because their web search capabilities warrant empirical evaluation before being deployed reliably. Our approach offers an exploratory, externally-grounded assessment using targeted data rather than internal instrumentation.

Frontier models from OpenAI and Anthropic now ship with built-in search capabilities called
web search tools
, and both note that models "use internal reasoning capabilities to determine whether the web search tool would help provide a more accurate response"
23
;
3
. In practice, we expect this internal reasoning to depend on two signals: low internal confidence in a factual claim
31
and the recognition that a query refers to information beyond the model’s training cut-off
7
. There is no standardised evaluation focused on closed-source settings that measures how reliably or precisely LLMs use internal web search tools to boost accuracy or other performance metrics. This leaves a central capability essentially untested.

To address this gap, we introduce a benchmark to provide an exploratory analysis of evaluating the quality and the necessity of web search for LLMs when answering simple factual questions. The benchmark is divided into a static and a dynamic part. The static part enables a clean comparison of models with and without web search, and tests how their factual confidence influences the decision to use web search. It contains questions about fixed facts from before each model’s knowledge cut-off, allowing a controlled assessment of accuracy gains, cost-accuracy trade-off and confidence calibration
25
. The dynamic part provides a stand-alone evaluation of web search capability and precision, using time-sensitive questions framed with terms such as “currently” and “present” to test how these cues shape a model’s decision to call the tool
8
. Here we evaluate whether models execute searches efficiently and how much accuracy they gain for the cost incurred.

Overall, the paper offers a focused and systematic way to extrinsically measure how effectively modern LLMs use in-built web search capabilities without accessing internal parameters or configuration. The main contributions of our work can be summarised as follows:

•

We introduce a benchmark that can explore how well calibrated frontier LLMs are in their use of web search, without relying on internal configuration details

•

We analyse LLMs’ web search capabilities through a comparative evaluation of the benefits and cost with and without web search, as well as a stand-alone assessment of calibration in search-enabled settings

•

We offer deployment-oriented guidance on best uses for inbuilt web search and selective invocation strategies, mapping model behaviour and cost–accuracy dynamics to concrete application scenarios

2.
Related Work

While past work has assessed agent competence (browsing, navigation, tool use) or safety, our contribution lies in evaluating the decision-making mechanism behind search invocation and its efficiency in closed-source yet widely used models from an external perspective.

2.1.
Web-Augmented LLMs

Recent methods have embedded web access into LLMs to mitigate reliance on stale parametric knowledge, enabling retrieval-augmented, browser-like capabilities with AI integration, such as RaDA
17
and DeepResearcher
36
. Similarly, several benchmarks have been proposed to test web agents across diverse tasks and settings. BrowserGym
9
provides a standardized gym-like ecosystem to evaluate agents, Search Arena
21
analyses multi-turn user interactions, and DailyQA
8
measures performance on fast-changing factual data. Frontier models, including OpenAI’s GPT series and Anthropic’s Claude models, now feature integrated web search tools; however, their decision-making processes and effectiveness in invoking search have not yet been formally evaluated.

2.2.
Browsing and Tool-Use Benchmarks

There is a growing set of benchmarks to evaluate LLMs and agents on web-interaction tasks, focused on depth and reach of web search capabilities. Mind2Web
10
and its follow-up
11
analyse performance over real-world tasks on live websites, while WebWalkerQA
29
tests LLMs on structured web navigation. BrowseComp
28
and its multilingual variants
37
evaluate persistent multi-step internet search. These benchmarks demonstrate the demands of web search and browsing, but they generally assume the model will attempt to browse; they do not examine whether or why the model chooses to initiate search. Other works propose evaluating LLM tool usage itself, even if not focused on web search. Agent-SafetyBench
35
and AgentHarm
1
systematically evaluate misuse modes, jailbreaking, and compliance in multi-step agent workflows. T-Eval
6
breaks down tool usage into sub-tasks, ACEBench
4
categorises scenarios to score LLMs’ use of tools, and StableToolBench
12
traces tool learning and application. Collectively, these works provide different methods to gain insight into agent capabilities and tool use for various objectives.

3.
Methodology

To capture both the calibration and the precision of LLMs in using web search, we structure our evaluation from two different viewpoints, visualised in Figure
1
and explained ahead. In our analysis, we define a call or web search invocation as an outbound web search request issued by the model through the inbuilt tool in the provider API.

3.1.
Static Split

3.1.1.
Dataset

This part is curated to isolate how a model’s internal confidence in its factual knowledge shapes the decision to invoke web search. It contains precise, fully specified factual questions with a single verifiable answer. To build our dataset, we manually filter the TempRAGEval
34
dataset to retain only questions with at least one temporal reference and complete details of facts before the knowledge-cutoff (May 2024 for GPT-5-mini
22
and Feb 2025 for Claude 4.5 Haiku
2
), ensuring that each query has a definite factual answer. The construction procedure is as follows.

(1)

Base corpus:
We start from the TempRAGEval test set (a temporally-perturbed QA benchmark that repurposes TimeQA
5
and SituatedQA
33
) with a total of 1.24k rows.

(2)

Temporal and factual filtering:
We retain only examples that (a) contain at least one explicit temporal reference or anchor (for example, explicit years, relative phrases such as "in 2010", or constructions that indicate the fact was true at a prior date), and (b) refer to facts whose temporal context (key time in the original dataset) is before the model knowledge-cutoff. To avoid ambiguity when comparing models with different cut-offs, the static split is restricted to facts verifiable on or before the earliest knowledge-cutoff (before May 2024 for GPT-5-mini) among both evaluated models.

(3)

Manual sanity checking and de-duplication:
We manually inspect retained examples to remove duplicates, ambiguous wording, and questions that may require long-form reasoning or multi-step inference beyond a single factual lookup. We also manually verify that the factual answer can be reliably retrieved through standard web search for every question, confirming that the correct result appears in the top one or two Google results using the query. Finally, we manually include all semantic variations as reference answers wherever applicable, covering alternate phrasings or writing styles and accounting for very minor lexical or syntactic differences.

Through this process, we obtain and release the final static split containing 783 verified factual queries. More details of the dataset and sample rows are provided in Section
C
in the Appendix.

3.1.2.
Evaluation and Metrics

To study the role of factual confidence, each question from the static split is given to the same model twice: once with web search disabled and once with search enabled, with a maximum of two search calls allowed. In both cases, the model is also asked to verbalise a confidence score between 0 and 1 for its answer, following the prompts in Figures
7
and
8
in the Appendix. For the search-enabled setting, we provide only the query itself, without any cue or pressure to use the tool, as seen in the prompt. Model outputs are evaluated by exact matching against a set of semantic variations of the expected answer. This setup serves both as a comparative evaluation across settings and as an ablation study that analyses the effectiveness of web search on fully specified factual queries. The aim is straightforward: the model should rely on its internal factual confidence and use web search to verify or find responses to queries where it believes it has lower confidence or does not know the answer. This comparative setup allows us to measure:

(1)

Accuracy and confidence gains upon providing the option of web search tool

(2)

Alignment between search call decisions and the model’s stated factual confidence

(3)

Trade-off between improved accuracy and additional costs of using web search

3.2.
Dynamic Split

3.2.1.
Dataset

This split evaluates whether models recognise and act on time-sensitive information to search the web for up-to-date answers. This part is built from a subset of questions manually adapted from the static split by removing explicit temporal references and converting them into genuinely time-sensitive queries containing terms explicitly indicating current information is needed. We also ensure that each question has undergone a factual change after the model’s knowledge cut-off so that parametric knowledge alone cannot yield the correct answer. For example, a static question such as “Who was the CEO of Company X in 2021” becomes “Who is the current CEO of Company X”, where the CEO of X has changed post the knowledge cut-off. Since these queries concern well documented developments such as national leadership changes or major corporate appointments, we expect the model to identify the need for web search and recover the correct answer within two calls. The construction procedure is detailed as follows.

(1)

Source pool:
We begin with the finalised static split of 783 examples. From these, we select candidates where (a) the answer involves a role, office, leadership position, or other attribute likely to change over time, and (b) the question structure is amenable to removing explicit temporal anchors while preserving semantic clarity.

(2)

Temporally neutral rewriting:
For each candidate, we remove explicit temporal references and rewrite the question to express a present-tense information need with lexical cues such as "currently", "as of now" and so on.

(3)

Post-cutoff factual change verification and web discoverability check:
We retain questions where the ground-truth answer has changed after the latest model knowledge-cutoff date (Feb 2025 for Claude 4.5 Haiku) by manually verifying with high-quality sources such as Wikipedia revision histories and reputable news coverage. For each remaining question we also ensure that the correct, updated answer is discoverable via standard web search. Specifically, we require that major news reporting or authoritative sources confirming the post-cutoff ground truth appear within the top 1–2 Google search results under a simple formulation of the query. All semantic variations, if any, are incorporated as reference answers.

Following this process we obtain a final dynamic split of 288 queries. All answers were verified to be correct as of 13 November 2025, and all experimentation was conducted between 13 and 14 November 2025 to avoid temporal drift in factual labels. The questions are designed so that correct answers cannot be produced from parametric knowledge alone, and web search is both necessary and sufficient for success under normal model assumptions. Additional details and examples are provided in Section
C
in the Appendix.

3.2.2.
Evaluation and Metrics

Each query in the dynamic split is presented to the model with at most two permitted web search call invocations. As in the static evaluation, we provide only the question itself and do not hint at or encourage tool use, following the prompt in Figure
9
in the Appendix. Also, we evaluate with an exact match to any of the semantic variations of the expected answer. This setting allows us to assess how effectively time-sensitive cues prompt the model to initiate a search and whether it can obtain the correct information efficiently. We then analyse:

(1)

Answer accuracy with web search

(2)

Rate and efficiency of web search invocation

(3)

Cost effectiveness of invoking web search for current time-sensitive information

3.3.
Experimental Setup

We evaluate two frontier models equipped with web search tool capabilities through their respective provider APIs for both splits. We experiment with OpenAI’s GPT-5-mini and Anthropic’s Claude Haiku 4.5, since the queries are straightforward and factual, and do not require complex reasoning or creative answering. We set temperature to 0 to ensure deterministic outputs and cap web search invocation at two calls per query. This upper bound reflects the manual verification conducted to ensure that questions in both static and dynamic splits can be answered through information available within the top 1 or 2 Google search results. All remaining parameters follow provider defaults. Full technical details and configuration settings are listed in Section

Analysis and Result Discussion

4.1.
How effective is web search in improving LLM accuracy?

To analyse how web search affects factual accuracy, we report results for both splits in Table
1
. Both models show clear accuracy gains when search is enabled. On the static split,
GPT-5-mini achieves a 62 percent relative improvement
, while
Claude Haiku 4.5 improves by about 80 percent
. These gains suggest that access to external information helps answer fully specified factual queries. Accuracy on the dynamic split remains lower overall, which is expected since these questions require retrieving new information that was not present during training. Although the dynamic split focuses on widely reported recent events, both models remain constrained by web search precision and search efficiency, with
neither surpassing 70 percent accuracy
. We align with previous findings that web search is beneficial but far from perfect, and closing the gap might require improvements in search query formulation and source selection.

We also plot accuracy for both dataset splits grouped by the number of web search calls in Figure
3
, when web search functionality is provided to the models. On the static split, accuracy for both models remains nearly unchanged when a single web search is issued but drops when two calls are triggered, suggesting that models struggle to improve results once the first search fails to surface useful information. On the dynamic split, accuracy is zero with no web calls as expected, peaks with a single web call, then declines when models issue multiple queries, with a modest drop for GPT and a far steeper fall for Claude, indicating that excessive searching often reflects unresolved uncertainty and poor query formulation rather than improved evidence gathering.

4.4.
Can LLMs’ confidence scores be used as gated thresholds for web search?

We analyse confidence scores of the model on the static split by binning model-reported confidence scores and examining how the proportion of beneficial and harmful outcomes varies across these bins, revealing whether lower confidence in the initial run without web search aligns with more web search usage when the function is provided. Results for both GPT-5-mini and Claude Haiku 4.5 shown in Figure
5
show a higher proportion of beneficial outcomes in low-confidence intervals, indicating that models tend to invoke web search effectively when uncertain, correcting initially incorrect answers. At higher-confidence intervals, the majority of outcomes remain correct with web search use, suggesting that models accurately recognize when their parametric knowledge is sufficient, but still use web search for verification.

Outcomes where the answer remains incorrect are more frequent at low-confidence bins, reflecting where search was called rightly to correct errors, but proved ineffective. Harmful outcomes where models change answers to incorrect upon using web search are relatively rare overall but tend to increase slightly in higher-confidence intervals, implying occasional over-reliance on web search even when parametric knowledge was accurate. Overall, patterns indicate that LLM confidence is reasonably well calibrated to call web search, implying that internal confidence must be a major factor in guiding efficient and effective use of web search use.

We further study how self-reported confidence relates to web search usage by simulating confidence-gated search invocation on the static dataset. After generating an answer and verbal confidence score without web search, we sweep a threshold and allow web search only when confidence falls below that threshold. For each threshold we compute both accuracy and the proportion of queries that trigger search, as shown in Figure
6
. This setup evaluates whether low confidence corresponds to cases where web search contributes meaningful improvements and whether selective invocation can outperform static policies such as always searching or never searching. As an upper-bound reference, we compare against an oracle that issues a search request only when doing so leads to a correct answer; this provides a theoretical ceiling that highlights how far confidence gating falls short of optimal selective routing.

Results show that confidence-gated invocation consistently outperforms random gating and improves substantially over using parametric knowledge alone. Accuracy peaks well before always calling, indicating that selective invocation is both effective and efficient, and that correlation in web search decisions and internal factual confidence is strong as well as useful. The oracle curve, which represents the best possible strategy that only retrieves when web search would correct an error, highlights that confidence is only partially aligned with true information need, suggesting room for improved uncertainty estimation or more sophisticated internal web search invocation strategies.

4.5.
Do LLMs correctly trigger web search when absolutely essential?

To evaluate how reliably models call web search when external information is necessary, we analyse the performance across the dynamic split consisting of queries explicitly asking for current knowledge. Table

Results show that both GPT and Claude encouragingly trigger web search for the majority of queries, with invocation rates of 87.5% and 91%, respectively. The few cases where web search was not invoked despite outdated parametric knowledge highlight missed opportunities, even when explicit cues signalled the need for current information. Total extra cost is computed as the number of web calls multiplied by the per-call price ($10 per 1k calls for both models). We report only the additional cost from web search invocation and do not account for token-level differences, since the queries are short and responses are expected to be very concise. Our abstraction models cost as dominated by outbound requests rather than language model inference, which is reasonable here because queries are brief and responses are strongly constrained to short spans within the prompts. We therefore report only incremental web-call cost as the extra cost associated with web search.

For the static split,
Strict Improvement

Two observations stand out. First, extra costs web search costs are modest in absolute terms, with average per-query cost below one cent for Claude and just above one cent for GPT across both splits, despite roughly one search call per query on average. Second, strict cost-per-improvement values vary more sharply: in the static case, Claude achieves lower cost per corrected answer than GPT, consistent with a more selective query issuance strategy as seen in previous sections, while GPT tends to incur redundant calls that preserve correctness rather than fix errors. On the dynamic split, strict improvement costs fall, suggesting that web search is more cost-aligned with information need when questions explicitly demand up-to-date facts. In all cases, Claude shows much better cost-efficiency than GPT on our exploratory benchmark.

Taken together, these patterns indicate that web search is cheap to invoke but not uniformly effective, and that cost-efficiency depends on individual use cases depending on how important it is to get a verified correct answer.

5.
Practical Implications and Guide

Our results translate into several actionable guidelines and recommendations for deploying LLMs in web-related contexts. While we outline model choices and web search strategies that work well in our evaluation, ultimately, we recommend that deployment decisions should be driven by the application, risk tolerance, and cost constraints rather than one-size-fits-all conclusions.

5.1.
Cost–accuracy trade-offs for LLM web search

We show that closed-source web-augmented LLMs substantially improve factual accuracy with modest marginal cost, but the gains are uneven and sensitive to when and how retrieval is triggered. In settings with stable, fully specified factual queries such as domain-specific lookups, structured comparisons, and technical reference tasks, a single targeted retrieval step offers a strong accuracy-to-cost trade-off. Hence, we suggest enabling web search with a maximum of one call as a lightweight verification layer if higher accuracy is required. In contrast, queries tied to rapidly evolving information see diminishing returns combined with high costs when multiple searches are invoked, indicating that repeated retrieval often reflects unresolved uncertainty and poor query formulation rather than improved evidence gathering. We recommend that deployments that expose models to live data streams on the web should instead use external tools or scaffolding to feed information into LLMs, rather than relying on inbuilt search capabilities.

5.2.
Inbuilt web search vs external retrieval

Our findings also clarify how model-initiated search compares to externally scaffolded retrieval pipelines such as RAG frameworks, curated web agents, or application-level query planners. Native invocation offers tighter coupling between uncertainty and retrieval decisions, and is suitable for lightweight consumer-facing applications such as chat interfaces, browser extensions, or mobile assistants where simplicity and latency matter more than full control. Externally orchestrated RAG pipelines, on the other hand, are preferable when retrieval must be auditable
15
, versioned, domain-restricted, or grounded in structured corpora rather than open web results. For instance, a biomedical assistant querying clinical guidelines benefits from deterministic retrieval and source control, whereas a travel assistant answering simple queries like “What time does the Louvre close today?” benefits from native web search that dynamically routes to fresh public sources. In short, internal web search is opportunistic and quick, while scaffolded retrieval may be better governed, verifiable, and domain-aware; the right choice depends on whether the task demands agility or rigorous provenance.

5.3.
Selective invocation strategies

Selective web search invocation also emerges as a practical middle ground for most common applications. Since confidence gating outperforms both always-retrieve and no-retrieve baselines, confidence can serve as a lightweight mechanism for routing queries when retrieval cost or latency matters, such as in interactive assistants or on-device models that defer to remote search services. However, calibration degrades when web search is enabled, so verbalised confidence scores posy using web search may not give the best idea about search quality. Production systems that rely on model confidence for deferrals, safety, or human verification should integrate additional signals including retrieval redundancy, citation quality, and cross-source consistency if using integrated web search tools.

5.4.
Model-specific behaviours

The two models evaluated in our research, Claude Haiku 4.5 and GPT-5-mini, also exhibit notably different web search behaviours. Claude tends to issue fewer calls and achieves lower cost per corrected answer, making it better suited for workloads where retrieval must be selective, predictable in latency, and cost-efficient, such as customer-facing assistants or mobile-constrained deployments. GPT is more likely to retrieve for verification even when its parametric answer is sufficient, which is wasteful in constrained settings but can be beneficial in safety-critical domains where redundant evidence checks are desirable, for example financial reporting, medical reference assistants, or legal document grounding.

6.
Conclusion

Overall, our paper provides a principled and externally measurable framework for evaluating how well closed-source LLMs decide when to use inbuilt web search and whether they answer correctly upon use. By pairing static and dynamic factual splits with confidence-based selective routing and outcome transition analysis, we offer a benchmark that isolates internal uncertainty, search decisions, and downstream factual reliability without requiring access to model internals or tool-use configuration. Our evaluation surfaces both performance gains and systematic calibration failures that arise when retrieval becomes available, showing that access to external evidence increases correctness but inflates confidence even when retrieval does not help.

More broadly, our work evaluates the intersection of parametric knowledge, model-estimated uncertainty, and external search in web-enabled LLMs and analyses how cohesively the LLMs can make use of them together. We argue that future progress will come not only from stronger models or more data, but from improving the mechanisms that govern when web search is triggered internally by providers such as OpenAI and Anthropic, how queries are internally formulated, and how evidence affects confidence in answers. We release our entire code and dataset and hope that they offer a step toward providing a transparent way to measure alignment between information need and web search behaviour in frontier models.

7.
Limitations and Future Work

While our benchmark offers a clear step toward evaluating web search in models, we also acknowledge certain limitations that suggest avenues for extension.

•

Model Scope:
Our evaluation focuses on two closed-source models to study native, tool-integrated web search in focus. The same methodology can be applied to other commercial systems and extended to open-source models with access to internal tool parameters, enabling joint analysis of internal scoring mechanisms and observable decision behaviour.

•

Source Quality Analysis:
We do not evaluate source quality, correctness of retrieved evidence, or alignment between citations and final answers, since we focus on fixed factual information. Future work can incorporate gold-standard evidence labels, source provenance, and failure mode analysis (for example, repetitive sources, low-quality domains, or misaligned top hits).

•

Search Diversity:
We cap retrieval at two calls and do not evaluate multi-hop, compositional, or adversarial queries that require deeper reasoning over retrieved content. Extending the benchmark to tasks that require query reformulation, summarisation across sources, or constraints under limited API budgets would broaden the scope of analysis.

Appendix A
Model details and configuration

We evaluate two closed-source frontier models, GPT-5-mini and Claude Haiku 4.5, both accessed through provider APIs with native web search capabilities enabled. All experiments were conducted with temperature set to 0 to maximise determinism, while all other decoding and model parameters were left at default provider settings unless otherwise noted.

•

GPT-5-mini:
We use the model version gpt-5-mini-2025-08-07, accessed via the official OpenAI Python SDK using the Responses API. Web search was enabled by registering the built-in search tool with automatic invocation, with a maximum of two external calls permitted per query. This setup allows the model to decide autonomously whether web search is useful. We do not restrict any domains or set other web search tool parameters. All requests specify only the browsing tool as tools=["type": "web_search"]| and pass a single textual input per query. The temperature is set to
0
and other parameters are kept at default values.

•

Claude Haiku 4.5:
We access Anthropic’s claude-haiku-4-5-20251001 through the v2 API. Similar to the GPT configuration, we allow the model to determine whether to trigger retrieval internally, and cap the number of web search calls to two per query. The tool is configured using:

{"type": "web_search_20250305", "name": "web_search", "max_uses": 2}

We do not restrict any domains or set other web search tool parameters. Temperature is set to
0
and other decoding parameters remain at default values to reflect realistic deployment scenarios.

Appendix C
Dataset Statistics and Samples

The static split consists of 783 fully specified factual queries that can be answered using pre-cutoff knowledge. Each question contains at least one explicit temporal reference and is verified to have a unique answer retrievable from authoritative web sources. The dynamic split contains 288 time-sensitive reformulations derived from the static dataset. Each question has undergone a factual change after the largest model knowledge-cutoff and cannot be answered correctly from parametric knowledge alone. Every updated answer is verified to be discoverable through standard web search, ensuring that retrieval is both necessary and sufficient for correct response.
