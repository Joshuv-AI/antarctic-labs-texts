PEAR: Planner-Executor Agent Robustness Benchmark
Shen Dong, Mingxuan Zhang, Pengfei He, Li Ma, Bhavani Thuraisingham, Hui Liu, Yue Xing

Abstract
Large Language Model (LLM)–based Multi-Agent Systems (MAS) have emerged as a powerful paradigm for tackling complex, multi-step tasks across diverse domains. However, despite their impressive capabilities, MAS remain susceptible to adversarial manipulation. Existing studies typically examine isolated attack surfaces or specific scenarios, leaving a lack of holistic understanding of MAS vulnerabilities. To bridge this gap, we introduce PEAR , a benchmark for systematically evaluating both the utility and vulnerability of planner–executor MAS. While compatible with various MAS architectures, our benchmark focuses on the planner–executor structure—a practical and widely adopted design. Through extensive experiments, we find that (1) a weak planner degrades overall clean task performance more severely than a weak executor; (2) while a memory module is essential for the planner, having a memory module for the executor does not impact the clean task performance; (3) there exists a trade-off between task performance and robustness; and (4) attacks targeting the planner are particularly effective at misleading the system. These findings offer actionable insights for enhancing the robustness of MAS and lay the groundwork for principled defenses in multi-agent settings. All codes and data are available on Github .

Despite the impressive effectiveness, agent systems can be vulnerable to potential adversaries. Attackers can circumvent an agent’s logic and alter its roles to elicit harmful behavior

Although considerable research has been done to uncover and mitigate vulnerabilities in individual LLMs

The limited scope makes it hard to generalize findings across the diverse range of agent-based applications. As a result, we still lack a holistic understanding of the potential vulnerabilities that multi-agent systems may face under adversarial conditions.

To address the gap identified above, we propose building a
comprehensive benchmark for evaluating the security of LLM-based multi
-
agent systems
. Although MAS structures vary widely
He et al. 2025a
, including some tailored to specific tasks, we focus on the generalist planner–executor architecture, which has emerged as a practical and representative MAS structure, such as Plan-and-Act
Erdogan et al. 2025

Typically, planners decompose the whole task into several smaller, actionable sub-tasks and assign them to appropriate executors, and then executors carry out the steps using their possessed tools and data sources. This basic structure has become the solid basis for many complex, realistic agents, including WebPilot

In this paper, we present a benchmark to evaluate the generalist planner–executor MAS.
Our benchmark enables systematic assessment of both their functional utility and their potential vulnerabilities under attacks.

Details of
PEAR

In this section, we introduce details of
PEAR
, including the planner-executor structure, the (clean) user task, the implementations of attack tasks and injection attacks. As in Figure
1
, there are several components in
PEAR
: the planner-executor MAS with some configurations in the system (Section
3.1
), user tasks for evaluating the MAS utility (Section
3.2
), and attack tasks and different injection attacks (Section
3.3
).

3.1
Planner-Executor Agent Setup

As shown in the center of Figure
1
, the system consists of a few critical components.

Planner Agent
. The planner interprets the user’s request and decomposes it into concise, actionable sub
-
tasks. It then assigns the sub
-
tasks to the executor for execution. The planner produces a step
-
by
-
step strategy and provides clear instructions to guide the executor. For example, in a travel MAS, the planner first extracts requirements (e.g., dates, destination, party size, budget), then proposes sub
-
tasks such as searching flights and hotels, comparing options, and handing off bookings.
We use the same prompt template across all task scenarios, and a full example is in Appendix
A
.

Executor Agent
. The executor carries out the planner’s sub-tasks by invoking tools, which are callable functions for specific operations, and by interacting with the environment. In
PEAR
, we use synthesized tools (i.e., not third-party MCP servers) to keep the evaluation controllable.
Detailed tool examples can be found in Appendix
A
.

Environment
. The environment is the shared setting in which multiple agents interact, communicate, and collaborate to achieve individual or collective goals
(
Guo et al. 2024b
)
.
In the planner–executor system, the planner observes the environment state and produces feasible sub-tasks; the executor then carries them out to achieve the goal.
Then, the planner can re-observes the updated state and replans as needed, yielding a continual perceive–plan–act loop toward the user’s goal.

Memory Module.

The memory component enhances planner–executor performance by providing agent trajectories from earlier steps within the same task, ensuring continuity across reasoning and execution cycles.
In
PEAR
, the memory module is configured in four modes, specifying which agent retains memory and whether the memory is shared between them:
(1)
Separate Memory
: both agents are equipped with memory but maintain independent histories;
(2)
Shared Memory
: both agents access and update the same memory space, enabling cross-agent information sharing;
(3)
No Memory
: neither agent has access to any previous trajectories; and
(4)
Planner-Only Memory
: only the planner retains past trajectories, while the executor relies solely on the planner’s current instructions.

3.2
User Tasks

We follow AgentDojo
(
Debenedetti et al. 2024
)
and adopt its user task design, where each task is formulated as a natural language instruction (user query) that defines the desired goal for the agent to achieve within an interactive environment. Each task is associated with a set of environment-specific tools that the agent may call to read or modify the environment state, such as scheduling calendar events, sending Slack messages, or managing workspace files. To ensure objective evaluation, every task is also paired with a utility function that determines whether the final output and updated environment satisfy the task requirements.

3.3
Attacks

In
PEAR
, there are two types of adversarial scenarios: (1) base
attack tasks
, which are pure adversarial tasks without any contexts from the user tasks (e.g., send the sensitive information of a person to a specific email address); and (2)
injection attacks
, which are a combination of the user tasks and attacks injected to the MAS to achieve the malicious goals in (1). For each pair of user task and attack task, the injection can happen in different stages and places, e.g., prompt injection before sending the prompt from the planner to the executor, injection into the planner’s system prompt, etc.

Threat model

We consider three attack surfaces that capture different levels of adversarial access to the multi-agent system (MAS).

- User prompt (attack task)
. The adversary interacts with the MAS through queries, without access to internal messages or system configurations.

- Planner–executor communication flow (injection attack into messages)
. The adversary gains access to the communication between the planner and the executor, and can inject attacks into the messages exchanged between them.

- Agent system prompt (injection attack into system prompt)
. The adversary has access to and can alter the system prompt of either agent in the MAS.
In this way, the adversary can induce persistent behavioral deviations that compromise safety constraints and decision policies.

Goals of Attack Tasks

In
PEAR
, we include three representative malicious goals.

- Harmful Actions
.
In agent systems, malicious inputs can trigger direct harmful actions because agents can invoke external tools, run code, or interact with high-privilege systems.
In the benchmark, the harmful actions include initiating recurring payments to the attacker’s account (banking), maliciously changing travel plans (travel), and deleting users’ events without permission (workspace), etc.
To determine whether the attack succeeds or not, we measure whether the targeted harmful action is performed by the system.

- Privacy Leakage
.
Agent systems are also prone to privacy breaches due to inter-agent communication channels. A malicious or compromised agent can solicit sensitive information from other agents, infer hidden context from conversation history, or manipulate others into revealing confidential data
Lee and Tiwari 2024
.
In the benchmark, the privacy leakage includes gathering information from sensitive Slack channels (Slack), exfiltrating users’ personally identifiable information (banking), leaking users’ traveling reservations (travel) and etc.
To exactly evaluate whether the attack succeeds or not, we check whether the specific pieces of private information are contained in the output/action.

- Resource Exhaustion
.
MAS can be forced into excessive consumption of computational or communication resources, impacting both cost and availability. Attackers may inflate token usage by generating excessively long or repetitive inter-agent messages
Zhou et al. 2025
, trigger high-latency operations by misusing tools, or flood the system with redundant tasks.
In the benchmark, we propose attack tasks including creating an overwhelming number of calendar entries (travel), initiating a massive number of small transactions (banking), inducing infinite loops by inserting triggers in the generated output and etc.
To evaluate the performance of such an attack, we monitor the change in the computation efficiency of the tasks.

For the attack tasks, we use Gemini-2.5-pro to generate the draft version and manually revise the prompt and evaluation function. Examples of different attack tasks can be found in Appendix
C
.

Injection attacks

As shown in Figure
1
, we inject the base attack tasks into the MAS when running user tasks to stress-test its robustness.
In detail, following the threat model, we implement two prompt-injection types of attacks.
The first type targets the
planner–executor communication flow
through injections at three stages: planner start, executor start, and executor end, appending injection prompts to messages exchanged between the two agents at different phases of execution.

(I1)
At planner start, the injection is appended to the planner’s initial input;

(I2)
at executor start, the injection is appended to the planner
\rightarrow
executor message, i.e. the concrete instructions or subtasks delivered to the executor;

(I3)
at executor end, the injection is appended to the executor
\rightarrow
planner message—this message contains the executor’s outputs, tool responses, and execution trace.
The second attack type targets
agent system prompts
, where the attacker modifies the system prompt supplied to either the planner or the executor. The evaluation metric follows the ones in the attack tasks.

Besides, to ensure injected content is semantically coherent with the target channel, we manually design connector prompts that explicitly link each attack task prompt to the communication flow message or to the agent’s system prompt. One connector is created for each combination of injection type (communication-flow and system-prompt), attack target (harmful actions and privacy leakage) and model family (GPT and Gemini).
Examples can be found in Appendix
D
.

4
Experiments

4.1
Evaluation Metrics

In the following, we summarize the evaluation metrics used in this work.

Utility
. We evaluate the utility of the MAS using task-specific utility functions, which assess whether the final output and the environment state meet the intended task objectives.

Attack Success Rate (ASR)
. As mentioned in Section
3.3
, we consider different attacks with different malicious goals. To examine the performance of the attack, for each attack in each task scenario, we specify the expected outcome when the attack succeeds and wrap this into a verifier, which is a security check function. For instance, we claim the success of a harmful behavior if the targeted harmful consequence is achieved; a privacy attack is successful if the desired sensitive information is leaked; an exhaustion attack is successful if a timeout happens or the max-retry exceeds. Detailed examples can be found in Appendix
C
.

4.2
Experiment Setup

To evaluate the planner–executor system, we use the three components of data in Section
3.2
and
3.3
to perform three complementary evaluations:

(1) User tasks
measure task performance (utility) and are used to explore how well the system completes intended user goals.

(2) Attack tasks
are used to explore the system’s robustness against externally supplied adversarial queries on different attacking goals.

(3) Injection attack
experiments probe internal surfaces of the planner–executor structure.

User Tasks
.
We evaluate the utility of planner-executor on the four scenarios (banking, slack, travel, and workspace) containing 14, 17, 20, and 33 user tasks, respectively. We compute the utility percentage across the four scenarios as the utility score of a single run. Each experiment is repeated five times to obtain the mean and the standard error.

Detailed numerical results are reported in Table

in Appendix

.

Attack Tasks
.
We evaluate our framework on the same four scenarios, each containing a specific set of attack tasks designed for the corresponding scenario. Specifically, every scenario includes 10 harmful-action tasks, 10 privacy-leakage tasks, and 10 exhaustion tasks (120 tasks in total for four scenarios). For each adversarial goal, we calculate the ASR and repeat the experiment for five times.

Injection Attack Tasks
.
We evaluate the vulnerability of the system by performing prompt-injection attacks during the execution of user tasks. In each case, attack-task queries are appended to the target content according to the specified injection type.
We focus on two attack goals, harmful actions and privacy leakage, and employ corresponding attack tasks for each. Exhaustion tasks are excluded because their evaluation depends on retry and time-limit policies, while injection inherently increases both, leading to inaccurate measurement of attack success.
We test the injection settings as specified in Section
3.3
: planner-executor communication flow injection at the planner start, executor start, and executor end, as well as agent system prompt injection on the planner and on the executor. Each configuration is evaluated across all four scenarios with 140, 170, 200, and 330 combined user–attack tasks, respectively. For each injection type, we repeat the experiment for three times.

Core LLM in the MAS
.
We select LLMs of different scales from four model families (GPT, Gemini, Claude, and Deepseek) to serve as the core LLM for the planner and executor agents. In the utility evaluation, we test 7, 7, 5, and 4 planner-executor pairs from the GPT, Gemini, Claude, and Deepseek families to investigate how agents with varying LLM capabilities influence overall utility. For the attack and injection attack evaluations, we focus on 3 representative planner-executor configurations from each of the GPT and Gemini families.

Memory Settings

In the experiments on utility, attack tasks, and injection attack tasks, we use the
Separate Memory
, i.e., both agents are equipped with memory but maintain independent histories. For the evaluation of planner–executor memory, we test all the four memory settings.

4.3
Utility

We evaluate the utility of the planner-executor system and present results in Figure
2
, where the X-axis denotes planner-executor pairs and the Y-axis denotes the utility.

An overall observation is that, across most configurations, we observe that the planner–executor structure consistently achieves utility levels above or around 65%. This finding highlights two important aspects. First, it validates the overall capability of the planner–executor architecture to effectively coordinate task-solving through tool usage. Second, it demonstrates the reliability of our
PEAR
, where tasks are sufficiently challenging to expose differences across LLMs while still solvable under a wide range of LLMs.

For more detailed comparisons, Figure
2
and detailed experimental results in Appendix
E
suggest that
planner quality exerts a stronger influence on performance than the executor
. While weak executors can cause considerable performance declines (e.g., Gemini-2.5-pro/Gemini-2.0-flash around 50%), the impact of weak planners is far more severe, leading to substantial drops in overall utility. For example, employing Gemini-2.0-flash as the planner leads to a utility of only about 30% with Gemini-2.0-flash or Gemini-2.5-flash as executors, and GPT-5-nano as the planner yields below 60% when combined with GPT-5-nano or GPT-5-mini executors. This indicates that a weak planner constrains the entire system, and its negative effect cannot be offset even by stronger executors. In contrast, when the planner is strong, the executor choices result in relatively smaller differences.

4.4
Memory

We evaluate the planner–executor system under the different memory settings described in Section
3.1
.
To better highlight the impact of memory, we increase the number of planner–executor iterations compared to the utility experiments, allowing agents to accumulate richer historical trajectories (which also explains why results under the same separate-memory setting differ from those in Table
2
).
Experimental results highlight the crucial role of planner memory: across GPT, Gemini, and Deepseek families, utility improves by roughly 10–30% when the planner gains memory access. Separate and shared memory configurations perform comparably to the planner-only setting, suggesting that the primary advantage lies in enabling the planner to recall past trajectories.

Injection Attacks

The injection experiments show that injection attacks on planner–executor systems are broadly effective and that their impact depends strongly on the injection surface and phase.

. Table

reports the results of communication
-
flow injection attacks. Across settings, absolute ASR values are high—mostly above 60% and, for Gemini under harmful attacks, exceeding 77%, indicating that corrupting inter
-
agent communication introduces substantial vulnerabilities in MAS. Notably, planner
-
targeted injections are consistently more effective than executor
-
targeted ones: planner
-
start attacks reach 82.03% (GPT, harmful), 88.62% (Gemini, harmful), 72.73% (GPT, privacy), and 78.52% (Gemini, privacy), whereas executor-start/end attacks remain consistently lower across all settings, showing a reduction of 3–20%. The likely reason is that compromising the planner distorts global reasoning and sub
-
task decomposition, propagating errors through subsequent executions. By contrast, compromising the executor typically corrupts only sub
-
tasks without global planning, yielding comparatively less damage to overall system performance.

Agent system prompt attacks
. Table
5
shows that injecting adversarial content directly into an agent’s
system prompt
yields consistently high ASR—above 60% across settings and above 80% in several cases (e.g., harmful attacks on Gemini exceed 85%). This indicates that safeguarding
role prompts
is essential and that model
-
level alignment alone may not protect against system
-
prompt injection. Consistent with communication
-
flow attacks, corrupting the planner’s prompt causes more severe end
-
to
-
end failures than corrupting the executor’s prompt, as planner errors propagate through sub
-
task decomposition and subsequent execution.

Overall, these results show that both inter
-
agent messages and internal role prompts are critical attack surfaces in MAS, and that planner
-
side corruption is particularly damaging. Effective defense therefore requires agent
-
level safeguards, such as trust
-
aware planning and message vetting, in addition to model
-
level alignment.

Conclusion

This work introduces the first comprehensive benchmark for evaluating the security of planner–executor LLM-based multi-agent systems. By jointly assessing utility and vulnerability, our study reveals that while these systems can achieve strong task performance, they remain consistently susceptible to adversarial manipulation. In particular, we find that higher-utility configurations often exhibit greater attack success rates, and that attacks targeting the planner stage are especially harmful due to their downstream influence on execution. These findings highlight an emergent vulnerability in multi-agents, underscoring the need for future research on agent-level safeguards, and systematic defenses under adversarial settings.

Limitations

While
PEAR
provides a unified and reproducible framework for assessing the robustness of planner–executor multi-agent systems, its current scope is still limited by its focus on a controlled and representative set of task environments and attack goals, which prioritizes reproducibility over full environmental diversity. This design enables systematic comparison but may not fully capture the variability of open-ended real-world interactions.
