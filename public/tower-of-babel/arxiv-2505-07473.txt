Web-Bench: A LLM Code Benchmark Based on Web Standards and Frameworks
Kai Xu, YiWei Mao, XinYi Guan, ZiLong Feng

Abstract
The application of large language models (LLMs) in the field of coding is evolving rapidly: from code assistants, to autonomous coding agents, and then to generating complete projects through natural language. Early LLM code benchmarks primarily focused on code generation accuracy, but these benchmarks have gradually become saturated. Benchmark saturation weakens their guiding role for LLMs. For example, HumanEval Pass@1 has reached 99.4% and MBPP 94.2%. Among various attempts to address benchmark saturation, approaches based on software engineering have stood out, but the saturation of existing software engineering benchmarks is rapidly increasing. To address this, we propose a new benchmark, Web-Bench 1 1 1 https://github.com/bytedance/web-bench 2 2 2 https://huggingface.co/datasets/bytedance-research/Web-Bench , which contains 50 projects, each consisting of 20 tasks with sequential dependencies. The tasks implement project features in sequence, simulating real-world human development workflows. When designing Web-Bench, we aim to cover the foundational elements of Web development: Web Standards and Web Frameworks. Given the scale and complexity of these projects, which were designed by engineers with 5 to 10 years of experience, each presents a significant challenge. On average, a single project takes 4 to 8 hours for a senior engineer to complete. On our given benchmark agent (Web-Agent), SOTA (Claude 3.7 Sonnet) achieves only 25.1% Pass@1, significantly lower (better) than SWE-Bench’s Verified (65.4%) and Full (33.8%) scores. Finally, we discuss that in any development field, Standards and Frameworks represent foundational knowledge and efficiency tools, respectively, and LLMs require optimization tailored to them.

2.2 Standard and Framework

2.2.1 Standard

Web Standards are the basic knowledge of Web development, especially those that are frequently used, offer extensive functionality, and enable more complex features. We have selected the core standards that Web applications rely on, covering HTML, CSS and JavaScript.

Partial core standards:

•

ECMAScript: the JavaScript language standard that ensures the interoperability of web pages across different web browsers.

•

TypeScript: A strongly typed programming language that builds on JavaScript. TypeScript code converts to JavaScript, which runs anywhere JavaScript runs. Most modern web applications are now built with TypeScript.

•

CSS Selector: Patterns that match against elements in a tree and are one of the core technologies used to select nodes in a document.

•

Flexbox: A layout model that arranges items in one dimension. The children of a flex container can be laid out in any direction, and can "flex" their sizes, either growing to fill unused space or shrinking to avoid overflowing the parent. It is widely used in most web applications.

•

Grid: A two-dimensional grid-based layout system. The children of a grid container can be positioned into arbitrary slots in a predefined flexible or fixed-size layout grid. It is more powerful than flexbox and also widely used in web applications.

•

DOM (Document Object Model): defines a platform neutral model for events and node trees. It is the main technology used to manipulate web page elements.

•

SVG (Scalable Vector Graphics): An XML-based language for describing two-dimensional graphics. SVG drawings can be interactive and dynamic. Animations can be defined and triggered declaratively.

•

Canvas: Used for drawing graphics via JavaScript and the HTML <canvas> element. It can be used for animation, game graphics, data visualization, photo manipulation, and real-time video processing.

•

WebGL (Web Graphic Language): An immediate mode 3D rendering API designed for the web. It is derived from OpenGL® ES 3.0, and provides similar rendering functionality, but in an HTML context.

2.2.2 Framework

In the early stages of Web development, there were not many development frameworks, and various Web applications could be developed using native technologies. However, with the rise of Web 2.0, both the technical complexity and application scale of Web applications have increased dramatically, and the development efficiency based solely on native Web technology has been challenged. Development frameworks have brought greater abstraction capabilities, improved development efficiency, and enhanced collaboration to Web development, covering its main aspects:

•

UI Framework: Usually provides a component-based development model and supporting development tools to improve the efficiency of single-unit development and collaboration, such as React, Vue, Angular, Threejs, etc.

•

State Management: UI state management is one of the core tasks in Web application development. Excellent frameworks will simplify the state model and improve development and maintenance efficiency, such as Redux, Zustand, Jotai, Mobx, etc.

•

CSS Framework: Improves CSS maintainability and development efficiency by enhancing basic capabilities such as variables, modules, functions, or providing CSS utilities. Examples include SASS, LESS, Stylus, Tailwind, etc.

•

Build: Web applications eventually run in browsers, and during the development phase, JS code and various resources (CSS, images, icons etc.) are usually split into many modules (or files), which require modular packaging using build tools, as well as optimization such as merging and compression. At the same time, build tools are also required to unify the development experience — handling JS syntax conversion, CSS preprocessing, and integration of various tools (including linting, formatting, testing frameworks, etc.) — such as Webpack, Vite, Parcel, etc.

•

Fullstack Framework: Fullstack usually refers to the ability of developers to handle both front-end (such as UI) and back-end (such as data and logic processing) development. In this context, it refers to frameworks that support both front-end and back-end development, such as Next.js, Nuxt, Express.js, etc.

•

Database Framework Data management is a relatively independent and core part of back-end logic. Data can be managed directly via SQL using tools like SQLite, or through object-relational mapping frameworks such as Prisma and Sequelize.

3.4 Metrics

\textbf{pass@1}=\left(\frac{\textbf{pass\_tasks@1}}{\textbf{tasks}}\right)\times 100\%

(1)

•

Percentage of tasks passing all E2E tests on the first attempt.

•

pass_tasks@1: number of tasks passed on first attempt before any failure.

•

tasks: total number of tasks in ’tasks.jsonl’.

\textbf{pass@2}=\left(\frac{\textbf{pass\_tasks@2}}{\textbf{tasks}}\right)\times 100\%

(2)

•

Percentage of tasks passing all E2E tests on the second attempt. pass@2 (retry with error context) is closer to the behavior of human engineers.

•

pass_tasks@2: total number of passed tasks including retries.

Example:

•

tasks: 20

•

pass_tasks@1: 5, the first failed evaluation happened at task-6

•

pass_tasks@2: 15, total passed tasks is 15 (task-16’s second attempt failed)

•

pass@1:
5/20\times 100\%=25\%

•

pass@2:
15/20\times 100\%=75\%

5. Related Work

Early LLM code benchmarks focused on the accuracy of single-function code generation. We review several widely cited benchmarks:

•

HumanEval
[
6
]
: 164 handwritten Python coding questions are used to evaluate functional correctness. Each question contains a function signature, docstring, and function body, and has an average of 7.7 test cases.

•

MBPP
[
8
]
: About 1,000 entry-level crowd-sourced Python coding questions covering coding basics and standard library functions, with each question having an average of 3 test cases.

•

APPS
[
29
]
: 10,000 Python coding questions—5,000 for training and 5,000 for testing—sourced from multiple coding competition websites, covering simple problems, technical interview questions, and algorithm competition-level challenges. Each question has an average of 13 test cases.

From Table
3
, we can see that HumanEval is saturated, and MBPP is close to saturation. APPS performs slightly better due to its larger dataset size, but it is also approaching saturation. To address code benchmark saturation, many new ideas have emerged.

5.1 Increase programming languages

Most of the problems in early code benchmarks used Python as the programming language. In addition to Python, mainstream languages in real-world development include C++, JavaScript, Java, Go, etc., making it natural to consider expanding language coverage.

•

MultiPL-E
[
10
]
translates HumanEval and MBPP to 18 other programming languages.

•

HumanEval-X
[
11
]
extends the HumanEval benchmark to Python, C++, Java, JavaScript, and Go via human translations

•

HumanEvalPack
[
12
]
extends the HumanEval benchmark to cover three coding tasks—code repair, code interpretation, and code generation—and six languages (Python, JavaScript, Java, Go, C++, Rust) via human translations. As shown in Table
3
, the SOTA in 2024 has reached 78%.

5.2 Increase test coverage

This stems from a simple idea: improving test coverage and increasing the presence of edge cases is expected to reduce the pass rate.

•

CodeContests
[
13
]
is a competitive coding dataset for machine learning. It automatically generates additional test cases (mutations), such as bit flipping of input strings or integer addition and subtraction. It uses multiple correct solutions to verify the new tests and ensure consistent output, and filters out problems with insufficient or overly simple test cases.

•

EvalPlus
[
14
]
detects the robustness of generated code by strengthening the scope and number of HumanEval and MBPP tests. For the same LLM, Pass@1 can generally be reduced by 5–10%. However, as shown in Table
3
, the latest SOTA has reached 89%, gradually approaching saturation.

5.3 Increasing dataset complexity

The problems in the early code benchmarks contain many basic algorithms, which are no longer challenging for LLMs; increasing the complexity of a single problem is also an idea.

•

DS-1000
[
15
]
is a code generation benchmark containing 1,000 data science problems, covering seven Python libraries such as NumPy and Pandas. The problems come from Stackoverflow and have been lightly edited.

•

CoderEval
[
16
]
contains 230 Python and 230 Java code generation problems carefully selected from popular open source projects. It supports code generation problems with six different levels of context dependency. It supports problems with six levels of context dependency, and performance is significantly better when generating independent functions compared to non-independent ones.

•

BigCodeBench
[
17
]
combines tools from 139 libraries across 7 domains to support 1,140 fine-grained tasks. It integrates multiple existing benchmarks and enables the implementation of functions such as data analysis and web development by calling multiple tools.

•

MLE-bench
[
18
]
is a benchmark for measuring the performance of AI agents in machine learning engineering tasks. 75 ML engineering competitions were selected from Kaggle to evaluate real-world skills such as model training, dataset preparation, and running experiments for machine learning workflows. As shown in Table
3
, the current SOTA is only 16.9%. As the coding capabilities of LLMs continue to improve, such professionally oriented benchmarks are expected to become more prevalent.

5.4 Improving software engineering reproducibility

Some benchmarks simulate the software engineering process from different perspectives:

•

CodeXGLUE
[
19
]
includes 14 datasets for 10 diverse programming language tasks including code-code, text-code, code-text and text-text scenarios. Provides three baseline models to support these tasks, including a BERT-style pre-trained model for understanding tasks, a GPT-style pre-trained model for code completion and generation, and an encoder-decoder framework that supports sequence-to-sequence generation.

•

RepoBench
[
20
]
is a new benchmark containing three subtasks (RepoBench-R retrieval, RepoBench-C completion, RepoBench-P pipeline), supporting Python and Java, and covering the evaluation of automatic code completion systems at the code repository level.

•

DevBench
[
21
]
is based on the waterfall model. It explores the performance of the evaluated model across five stages: software design, environment configuration, implementation, acceptance testing, and unit testing.

•

SWE-bench
[
22
]
focuses on solving real and complex software engineering problems. 2,294 tasks come from 12 popular Python libraries on GitHub. The filtering rules are as follows: approximately 90,000 Pull Requests were collected, each associated with a code base. A GitHub issue was resolved, the test files in the repository were modified, at least one test case was included, and the test status changed from failed to passed. SWE-bench offers substantial scale and real-world software engineering complexity. In the past two years, it has gradually become a highly cited code benchmark. As shown in Table
3
, after two years, the SOTA—especially on the Full set—remains far from saturation.

6. Discussion

6.1 Why Software Engineering?

Based on the discussion in Chapter 5 and the SOTA data presented in Table
3
:

Increasing the types of programming languages cannot solve the benchmark saturation problem. This is intuitive. Real-world programming languages have their own characteristics and strengths, but are similar in expressiveness. In fact, LLM pass rates across different language versions of the same benchmark do not vary significantly
[
12
]
.

Increasing test coverage seems to have some effect, but EvalPlus
[
14
]
also approached saturation within two years of its publication. Although CodeContests
[
13
]
performs better, its unsaturated SOTA is likely due to the high difficulty of its competition-level question set. Similarly, in real-world scenarios, project complexity arises from factors such as lines of code, code logic complexity, and the structure of the module/component dependency tree. Even 100% test coverage cannot change the complexity of the project itself.

Increasing the complexity of the dataset—whether by increasing the complexity of individual problems
[
16
,
18
]
or by expanding the scale of the benchmark
[
17
]
—appears effective based on SOTA results. However, the upper limit of this approach often consists of uncommon and complex algorithmic problems, which gradually deviate from real-world coding. This may lead LLM coding to evolve in a less practical direction.

Simulating the software engineering process has been theoretically demonstrated as feasible by CodeXGLUE, RepoBench, and DevBench. These benchmarks have also been preliminarily validated on earlier LLMs, paving the way for larger-scale software engineering benchmarks such as SWE-bench and Web-Bench. Benchmarks in the software engineering direction are grounded in real-world coding behaviors.

Web-Bench is a new software engineering benchmark and fills the gap: Sequential task evaluation for fullstack web development based on Web standards and frameworks.

6.2 LLMs require optimization tailored to Standards and Frameworks

Referring to the previous section, we note that software engineering provides a promising solution to benchmark saturation. Furthermore, if the problems contained in the benchmark (or in the projects presented in this work) accurately reflect real-world code, they can help guide LLMs to evolve in a practical direction. A fundamental question arises: what is the basis of real-world coding? Although this article primarily discusses web application development, the development process in any field
[
30
]
is fundamentally built upon standards (also referred to as protocols, specifications, or recommendations) and frameworks (which may include libraries or third-party packages). Standards and Frameworks represent the basic knowledge and efficiency tools in a coding field, respectively. From this perspective, they are universally applicable. So we have an intuition: LLM needs optimization tailored to Standards and Frameworks.

We are also conducting further in-depth research in this direction, which may serve as a potential breakthrough in the next stage:

1.

Standards-aware Training:

•

Inject W3C/WHATWG documentation into pretraining data.

•

Finetune with AST based syntax constraint checks.

2.

Framework-specific Adaptation:

•

Add framework rule checkers to decoding loops.

•

Develop plugin architectures for framework updates (avoiding retraining).

7. Limitation

Web 2.0 has brought about the rapid development of the Web development ecosystem. Dating back to 2005, nearly two decades have passed. Although the current version of Web-Bench covers the core Standards and Frameworks, many others remain uncovered due to workload constraints. In the future, we will strive to cover more standards and frameworks by innovating project design and development tools.

This paper mainly studies the accuracy of code generation for LLMs. We have also received feedback from users on multiple occasions expressing interest in evaluating the aesthetics and code quality of the generated pages. Since the evaluation of aesthetics and code quality can largely reuse the existing benchmark infrastructure, Web-Bench already includes a built-in screenshot function. In the future, it can be easily extended to support additional metrics.

- Local-Agent: Local-Agent has the basic capability to interact with LLM. It can specify the corresponding model in the ’apps/eval/src/model.json’. Local-Agent is actually the Web-Agent introduced by this paper

- HTTP-Agent: Through HTTP-Agent, it calls the configured agentEndPoint to send a request to the custom Agent.
