A novel NFR-based conceptual quality framework for modern API industry
Authors: Aumir Shabbir, Aziz Deraman, Mohamad Nor Bin Hassan, Kamal Uddin Sarker, Shahid Kamal
Published: 2026

ABSTRACT
The modern software ecosystems employ application programming interface (API) to allow interoperability and integration across various platforms. Non-functional requirements (NFRs) as quality attributes are as vital as functional requirements (FRs) in assuring software quality and user satisfaction. API quality management is a challenge to software industry owing to poor NFRs handling during API development, resulting in cost increase, project failure and dissatisfied customers. The existing standards failed in producing a comprehensive quality framework for APIs. OpenAPI Specification (OAS) focuses on functional aspects, whereas ISO/IEC 25010:2023 emphases on traditional software quality. Hence, this study proposes a novel non-functional requirement quality framework for APIs (NFRQF-API). In compliance with ISO/IEC 25010, the framework includes key NFRs and their influencing factors to facilitate the development of high-quality APIs. Explanatory sequential mixed-methods design was applied in this study, involving a survey tool. Data were collected using a questionnaire comprising eight Likert-scale items and two open-ended items. Descriptive statistics and reliability testing were applied for quantitative data analysis, while thematic analysis was applied to evaluate the qualitative data, which supports in achieving a comprehensive expert-based justification for the conceptual feasibility and applicability of framework. Based on the experts’ survey, analyses results demonstrated the potential effectiveness of the proposed framework in managing the Core, Critical, and Contextual NFRs in the entire API development lifecycle. This study bridges the gap between existing quality models and API quality assurance challenges. The structured expert-refined framework facilitates the enhancement of API quality management and offers KPI-based conceptual quality standards for the industry to design high-quality APIs by effectively handling critical NFR issues.

Introduction

Application programming interface (API) is prevalent in the current era of software engineering. In a digital environment, APIs support web apps, mobile platforms, and enterprise solutions1. In modern software ecosystems, APIs facilitate modularity, integration, efficiency and collaboration2–4. Through the use of high-quality APIs, resiliency, maintainability, observability as well as security can be attained, resulting in trust and adoption potential among organizations and developers. Nonetheless, despite their vital role and extensive usage, API often fail owing to overlooked Non-Functional requirements like maintainability5,6, resiliency7,8 and observability9, while failure of API can result in interrupted digital services. In APIs, observability and resiliency are among the key NFRs as they facilitate the handling of intricate issues related to quality8,9. As APIs behave differently from conventional software applications; therefore, dedicated API quality management is essential in modern distributed environments10. For instance, the observability attributes involve the monitoring of logs and continuous system during real-time operations9,11, while the resiliency attributes involve the handling of failures that occur during API operation, without causing disruption12. Notably, auto recovery from application failure is a recent feature that makes the system considerably more resilient13, while decreasing the downtime7,8.

OpenAPI Specification 3.1 and ISO/IEC 25010, which are among the existing standards for software systems, have drawbacks. For instance, OpenAPI 3.1 only focuses on operations and schemas, not on NFRs and KPI (Key Performance Indicators) metrics14, resulting in gaps for NFRs in API. On the other hand, ISO/IEC 25010, which has a broad scope, provides an outline for a high-level product quality model and characteristics15. Somehow, it often neglects the specific NFRs that are integral to APIs16. APIs, although important, are still ineffectively managed in terms of quality. In fact, the existing quality models mostly focus on the handling of functional aspects. On the other hand, various aspects of NFRs, including performance, security, scalability, observability, and resiliency, are often inadequately addressed or even neglected altogether17. Clearly, the factors of NFRs have not been adequately considered during API development16, while a comprehensive quality framework to support high-quality API development is yet to exist5,18,19.

Accordingly, this study addresses a critical gap in existing software quality standards, where the effective management of API-specific NFRs is not explicitly defined. Although ISO/IEC 25010 provides a comprehensive foundation for the quality of traditional software, while it does not adequately address the unique characteristics and operational requirements of modern APIs. Hence the current study offers an expert-refined Non-Functional Requirement Quality Framework for APIs (NFRQF-API) aligned with ISO/IEC 25010:2023, which provides a structured and systematic approach for managing API quality and its influencing factors throughout the API development lifecycle. Consequently, to both academic research and modern API domains, this study contributes to the following:

Research background

Challenges in API development and management

APIs are an integral element in modern software ecosystems and the internet of things (IoT), where the main function of APIs is to connect applications, systems, and platforms. In API development and documentation, security, performance, and reliability are among the NFRs to be taken into account20, considering that APIs operate the external access to back-end systems21. It is thus crucial to systematically addressed these NFRs to achieve dependable, secure and high-performing APIs22. Furthermore, clear and inclusive API documentation would result in increased API adoption and smooth integration23.

Role of NFRs in API quality

NFRs, which are as important as functional requirements (FRs), specify the quality attributes that are vital for software applications to assure software quality and user satisfaction20. The attributes that are considered vital to software applications include reliability, security, maintainability, performance, functional suitability, scalability, and usability24. Failure in fulfilling NFRs can result in undesirable consequences such as increased costs, customer dissatisfaction, and even project failure25,26. Eliciting, documenting and integrating NFRs are no easy tasks. Somehow, owing to the positive impact of NFRs on the conceptual models and on the project outcomes, they should be treated as main requirements27. Significant impact of NFRs on project cost, duration, and business success has been empirically proven, especially when NFRs were perceived as important as FRs25,26.

Observability and Resiliency have emerged as major NFRs, with observability being highly influential in assuring APIs’ dependability and performance28,29. Observability is primarily associated with the critical post-deployment operations, especially the logging and continuous monitoring of real-time APIs30–32. In this regard, efficient and robust API is one that has inclusive logging and real-time monitoring32–34. Meanwhile, the attribute of resiliency allows fault tolerance, automatic smooth recovery and smooth degradation in APIs35. Specifically, fault tolerance assures that the services ensue amidst system failure8,36. Resiliency also allows the system to automatically recover to its normal operations7,37. Clearly, in modern software systems, the incorporation of NFRs (e.g., performance, security, maintainability, observability, and resiliency) will assure robust, dependable and quality APIs. Somehow, it is challenging for organizations to effectively manage NFRs38.

Limitations in current standards and models

ISO/IEC 25010:2023 is a commonly used standard in software product quality evaluation. It outlines nine quality characteristics, namely, Functional Suitability, Performance Efficiency, Compatibility, Interaction Capability, Reliability, Security, Maintainability, Flexibility, and Safety. Notably, this standard merely provides a general framework to manage the quality of conventional software systems and services15,39, and there are no predefined metrics and API-specific guidance16. Correspondingly, OpenAPI Specification is commonly used in describing the structure, endpoints, and data models of REST APIs. The aim of this standard is to support users in their understanding of and interaction with API operations40,41. Additionally, OAS, which was developed mainly to document functional aspects, doesn’t have the built-in support to manage NFRs (e.g., performance and reliability) or security issues14,21,42.

Numerous models and approaches for managing NFRs in APIs have been proposed, for instance, continuous integration (CI) environments43 and automated tools44. Both these approaches address the aspects of security, performance, and reliability. On the other hand, other aspects, which are also crucial, such as maintainability, usability, and scalability, have been ignored. Meanwhile, a few other available domain-specific frameworks are focusing only the precise domains like machine learning systems or product lines, and this limits their general pertinence to broader contexts of API45,46. In their study, Sherif, Helmy, and Galal-Edeen47 proposed the MANoR framework to manage NFRs in Agile Software Development. However, the framework was mainly focusing on Scrum and offered no specific guidance for API. Correspondingly, the studies of Viviani48 and Kumar49 highlighted the usefulness of NFRs during software development, owing to the frequent disregard over the aspects of usability, security, privacy, and reliability. However, the authors did not offer a structured quality framework for APIs. Similarly, Pargaonkar50, Koci51, and Lamothe52 presented some insights on NFR management in their studies. However, their insights did not comply with quality standards like ISO/IEC 25010. Agile, Scrum, Spiral, and DevOps are among the different development methods available today, but their main focus are on the functional aspects, resulting in the neglect on the vital aspect of NFRs during API designing53. Markedly, the quality of an application is majorly determined by NFRs. Consequently, maintaining high software quality within their development environment is essential and requires constant attention54.

Table 1 mentioned above summarizes prior studies specifically focus on API quality management. Since the behaviour of API is different from traditional software, few additional non-API focused studies are intentionally included and discussed in the literature review to highlight gaps regarding the limited addressing of API-specific NFRs. While APIs are integral components of software applications, however, studies on traditional software applications do not explicitly address API-specific quality aspects. Similarly, a detailed review of seventeen articles presented in Table 1 revealed that the six articles focused on traditional software applications rather than the APIs. Likewise, twelve articles are not aligned with any of the existing quality standards, such as ISO/IEC 25010 whereas, seven articles have shown limited or no validation in their studies. Additionally, six articles recommended that an NFR based quality framework is required explicitly for managing the NFR-based challenges in APIs. Besides, benchmarking in this study is conducted qualitatively to compare conceptual aspects, such as NFR coverage, API coverage, alignment with existing quality standards (ISO/IEC25010) as well as identified limitations with existing studies and frameworks. However, quantitative performance benchmarking against the frameworks and approaches mentioned in the literature would require empirical deployment, which is beyond the scope of this conceptual study.

Methodology

Research design

This study adopted an Explanatory Sequential Mixed-Methods Design, as shown in Fig. 1 below, following the guidelines of Creswell and Plano Clark (2017)64, who recommended collecting quantitative data first, followed by qualitative data, to evaluate the NFRQF-API. The approach combined the quantitative analysis of software industry expert ratings on the framework and the qualitative insights of the experts on the framework into its practical applicability. This enhanced the understanding of the potential effectiveness and relevance of the framework in the industry of API development.

A structure of research methodology.

Survey design and validation

This study employed a survey questionnaire as the data collection instrument. The questionnaire included demographic questions to evaluate the experts’ relevancy, in addition to ten questions to determine the clarity and the practical applicability of the proposed framework (eight Likert-scale questions and two open-ended questions). In order to assure accuracy, clarity, and appropriateness, the first draft of the questionnaire was sent to six experts who were selected based on eligibility criteria (see Appendix A: Expert Selection and Survey Validation Criteria) belonging to the academic research and software industry domains, where both the face validity and content validity65,66 of the questionnaire were evaluated. Furthermore, we also verified their expertise using publicly available profiles, such as institutional webpages, publication histories, and professional records. The face validity and content validity of the questionnaire were ascertained, as detailed below:

Face validity

The six experts (as mentioned below in Table 3) evaluated the face validity65 of the questionnaire. In particular, the experts evaluated the clarity, layout, overlap, and consistency of the items in the questionnaire. Based on their feedback, one overlapping item was removed, the term “Developer” was changed to “API Developer,” the country options were changed to continent options, and all demographic items were standardized to have five answer options.

Data collection

As previously indicated, data were collected from software industry experts through a structured questionnaire, where these experts were recruited from various professional platforms, such as LinkedIn, institutional webpages, and publication records, and invited to participate in the survey via LinkedIn professional groups or direct email invitations. The informed consent was obtained from the experts before their participation, the consent statement was included at the beginning of the online survey. The questionnaire comprising eight Likert-scale items and two open-ended items where the items on Likert scale comprises of 5 levels of agreement as follows: 5 to denote Strongly Agree, 4 to denote Agree, 3 to denote Neutral, 2 to denote Disagree, and 1 to denote Strongly Disagree. For the two open-ended items, they were for ascertaining the efficacy of the framework in the industry, as perceived by the experts. The experts comprised API developers, Quality Assurance Experts, and Software Architects. They were chosen due to their capability in evaluating the potential effectiveness of the proposed framework (NFRQF-API). The aim of the questionnaire was to assess the key aspects, such as the clarity and flow of the structure of the framework, NFR coverage, and also the practical pertinence of the framework to the API industry. As API quality engineering is a one of the highly specialized domains therefore, overall, 63 responses were collected. However, based on the strict guidelines (see Appendix A) recommended by Palinkas et al.67, 49 of the collected responses were considered usable. The samples were excluded based on the limited industrial experience of participants with less than 3 years, who have no practical knowledge of development, as well as a lack of knowledge about NFRs and quality standards. Where on the other hand, this sample size exceeds the typical threshold of existing API experts validation studies, where the samples remain under 303,38. Thus, the achieved sample size is sufficiently rich for the validation of framework.

Data analysis

IBM SPSS Statistics (Version 21.0) was employed for data analysis68. The software is available at https://www.ibm.com/products/spss-statistics. Cronbach’s alpha based on the guidelines of Malapane and Ndlovu69, Tavakol and Dennick70 was applied in determining the internal consistency of the eight Likert-scale items, to validate the proposed framework. Cronbach’s alpha of quantitative data from 49 valid responses was computed and the resulting Cronbach’s alpha coefficient for the scale was α = 0.831, denoting good internal consistency69,70. Notably, the eight Likert-scale items were treated as a single scale, because these items jointly measure the perceptions of the respondents on the clarity, usability, comprehensiveness, and practical applicability of the proposed framework. Furthermore, the option “alpha if item deleted” in SPSS affirmed that no individual item decreased the overall reliability. The reliability evaluation did not include open-ended questions.

Subsequently, the descriptive statistics using IBM SPSS Statistics were run on the responses of the eight Likert-scale items to compute the mean and standard deviation values. The guidelines from Boone and Boone71 and George & Mallery72 were followed. On the other hand, thematic analysis was performed on the responses of the respondents on the two open-ended questions. This was to obtain clarity and deeper understanding from the feedback in case of further refinement in framework. The analysis involved six phases proposed by Nowell et al.73 and Braun and Clarke74. The phases were: Familiarization with the data (Phase 1), Generating initial codes (Phase 2), Searching for themes (Phase 3), Reviewing the themes (Phase 4), Defining and naming the themes (Phase 5), and Producing the report (Phase 6).

Qualitative results

Qualitative data from the responses on open-ended questions were analyzed through thematic analysis. The analysis involved six phases (see Fig. 2) based on Braun and Clarke74 and Nowell et al.73. The approach was appropriate for this study as it supported a systematic and rigorous identification of patterns in expert responses. The aspects that were identified were clarity, usability, and practical relevance of the NFRQF-API framework proposed in this study. Hence, the frequent aspects were highlighted by the experts regarding the frameworks’ clarity as well as need for clearer KPI integration, such as “Label the levels to clearly specify the flow direction”, “Appropriate labeling of arrow directions can enhance readability,” and “Reconsider the arrow directions and overall framework flow”. In addition, experts emphasized the importance of conceptual KPI-related guidance, such as “the framework may seem more practical in future deployments if KPI measurement tools are included”, “commonly used measurement tools would significantly improve practical applicability”, and “KPIs should be clearly defined at the Quality Assurance level.” One expert further suggested that metrics such as “API uptime could be monitored using commonly available monitoring platforms, mentioned as illustrative examples (e.g., Datadog or similar tools)”.

Thematic analysis process

Based on the qualitative findings, the six phases of thematic analysis process are presented below:

Phase 1: familiarization with the data

Initially, the responses from all the respondents (the experts) were repeatedly read. This was to gain a thorough understanding of their insight. From the reading, several key points were identified. The identified key points were: “improve the clarity of data flow labels,” “enhance diagram readability,” “provide the relevant arrow labelling,” “use of measurement tools for KPIs” and “Add KPI testing tools.”

Phase 2: generating initial codes

Subsequently, the researcher systematically coded all the responses, where the significant aspects of the data were highlighted. The codes were assigned as follows: “framework flow,” “diagram readability,” “arrow labelling,” “KPI measurement tools,” and “KPI testing tools.”

Phase 3: searching for themes

Following this, connected codes were placed together into broader categories, while codes on labelling and readability were placed together into a candidate theme labelled “Visual clarity and flow.” The “KPI testing tools” code was combined into the candidate theme called “KPI measurement tools.”

Phase 4: reviewing the themes

In order to assure internal consistency, the defined themes were prudently reviewed. Codes that were overlapping were merged together, while codes with insignificant contribution but were contributing to broader themes, were added into its respective theme. In this context, the “framework flow” code was placed under “Visual clarity and flow”.

Phase 5: defining and naming the themes

Thereafter, the two last themes were clearly defined, where the themes were given simple and profound names, to generate clear understanding. “Visual clarity and flow,” which was the first theme, displays the suggestions made by the experts in improving the readability of the framework diagram. Among the suggestions were to include labels and clarify the directions of the arrows to further enhance the coherency of framework. “KPIs measurement tools” as the second theme, shows the suggestions of the experts to link KPIs to relevant practical monitoring and testing tools. Through such names and definitions, it could be assured that each theme focuses on a certain aspect of the experts’ feedback.

Phase 6: producing the report

In this phase, which is the ending phase, the themes were finalized by providing with comprehensive descriptions. This was to show how the feedback from experts guided the researcher in refining the proposed framework. The “Visual clarity and flow” theme was labelled. Also, clear direction was provided to facilitate the understanding of the diagram. For the “KPIs measurement tools” theme, the KPI sample tools were added into the QA layer, as per the suggestion of the experts.

Strategic level

For this level, input is obtained from the NFRs, where the NFRs are classed into the following categories: Core (MY, RS)78–80, Critical (FS, PE, CY, RL, SE, OY)78,79,81 and Contextual (IC, FY, SA)79,82,83. These classifications were recommended by the experts and also in studies like Shabbir in 202510. Not only that, NFR classification becomes the base for planning and implementation to assure early and judicious preparation for the Core and Critical NFRs during APIs development. Quality standards are clearly outlined in accordance with KPI evaluations. Meanwhile, roles are assigned within the team for the management and review of quality-related activities. Next, the developed guidance and quality standards at this level are incorporated into the operational level during API design. Consistent feedback from the Quality Assurance Level and industry experts (internal QA validation and external industry feedback) improves the quality standards of the strategic level.

Operational level

This level aligns with the lifecycle of API development that includes the phases of Planning, Developing, Testing, Deploying, and Retiring. During operational level, the guidance and quality standards developed at the strategic level are implemented, with the primary purpose of systematically addressing NFRs, the inducing factors and their KPIs all through the development phases of API. This would assure the development of APIs of high quality aligned with the framework.

Quality assurance level

The purpose of this level is to assure that NFRs as well as their inducing factors are addressed appropriately all through the lifecycle of API development. Quality assurance also provides verification on the appropriate implementation of KPIs at the Operational Level. Furthermore, through its immediate feedback, quality assurance facilitates corrective actions. Additionally, to assure that the newly-developed framework-aligned APIs fully meet the expected quality standards to support output validation. As part of long-term quality planning, QA findings are reported to the strategic level in quality performance reviews and feedback.

Discussion and implications

Results demonstrated strong accord among the study respondents (the experts in the industry) on the overall structure and practical significance of the NFRQF-API framework. ISO/IEC 25010, as one of the available standards, presents quality guidelines for general software quality. Somehow, it does not provide API-specific guidance, and it also ineffectual in dealing with emergent API related attributes such as observability and resiliency. Meanwhile, the OpenAPI Specification (OAS), which is an API quality standard, merely focuses on functional aspects and interoperability, but it does not offer inclusive NFR management support, where NFRQF-API proposed in this study addresses these issues directly. Specifically, it classifies NFRs into Core, Critical, and Contextual categories, with measurable KPIs and continuous feedback loops embedded to it. This study employed an explanatory sequential mixed-methods design. It facilitated this study in showing how quantitative validation and afterwards qualitative analysis, can strongly prove the adaptability of the proposed framework across various contexts of API development. However, one of the 5-point Likert scale based-items related to the implication of KPI metrics in frameworks’ practicality achieved a positive mean score of 4.10 but showed “Moderate consensus”. Later the thematic analysis of the open-ended question revealed the full agreement of experts on the clarity and relevance of the NFRQF-API with the suggestion of inclusion of KPI measurement tools which were incorporated in the expert-refined version of the framework. Hence the item with “Moderate consensus” accompanying by open-ended suggestions successfully addressed in the expert-refined version of NFRQF-API. Overall, results of quantitative analysis affirmed the general aptness of the framework, while results of qualitative analysis facilitated the study in identifying the ways to improve the framework, specifically, by improving the visual clarity and by outlining the KPI measurement tools. The proposed framework was refined after modifications and its effectiveness for potential industry adoption was improved.

In theoretical implication, the proposed framework in this study expands the ISO/IEC 25010 with the inclusion of two emergent NFRs into the API domain. It also addresses the limitations in the existing standards, like in OAS that only addresses the API-specific FRs, where OAS was selected as a reference specification because it is widely adopted as a standardized model for API description. The NFRQF-API framework is intentionally designed as a technology-agnostic and architecture-independent. Subsequently, to maintain the technology-agnostic nature of the framework, the referenced KPI tools are provided as illustrative examples and are not mandatory for the framework, however, they are intended to be adapted to specific organizational and technological contexts. From a practical perspective, the expert-refined framework classes eleven NFRs into three categories, namely Core, Critical, and Contextual categories. Such classification supports a more comprehensive approach to define and implement the conceptual quality guidelines at the Strategic, Operational, and Quality Assurance levels and assures the framework to address diverse API architectures (such as, centralized versus distributed, monolithic versus microservice-based), API technologies (like, REST, GraphQL, gRPC, WebSocket), as well as various API types (private, public, composite). In addition, while Service Level Objectives (SLOs) and Service Level Agreements (SLAs) are typically defined at the operational stage, the proposed framework supports their early alignment by structuring NFR identification and KPI integration during the design phase. This supports clearer and more consistent SLO and SLA definition after real-time deployment of the framework. Consequently, the framework provides a solid bridge between scholarly research and industry practice.

Threats to validity and limitations

Even though the NFRQF-API has been refined based on the experts’ feedback, however, this study has several limitations. Notably, the proposed framework could not be fully deployed for real-world testing. Still, this study provides an opportunity for testing the conceptually validated framework in real-world API projects and assessing the adaptableness of the framework across various contexts of software engineering. Accordingly, future research may focus on empirically defining and validating SLO and SLA targets through real-world deployment of the framework. Similarly, the KPI definitions and measurement approaches presented in this study are illustrative and provide the conceptual guidance for operationalizing NFRs within the proposed framework. Additionally, the study faces potential threats to validity as the validation methodology relies on experts-based perception rather than empirical experimentation. Furthermore, the survey may not capture all aspects of API quality due to the limited extent of divergent responses, so the findings may have limited generalizability beyond the selected experts. These limitations are acknowledged, and future studies are encouraged to empirically validate the framework by employing more discriminative items after implementing it in real-world API environments.

Conclusion

This study presents an expert-refined Non-Functional Requirement Quality Framework for APIs (NFRQF-API) to significantly manage API development practices. The framework aims to address the most critical NFRs and their influencing factors systematically. Likewise, it provides clear quality standards, defined KPIs, and constant feedback mechanisms through three levels namely Strategic level, Operational level, and Quality Assurance level. Additionally, the internal QA validation and external industry feedback are the two mechanisms that strengthen the foundation of NFRQF-API by providing the consistent refinement of its quality standards. The Explanatory Sequential Mixed-Methods Design was the approach employed in this study, involving the evaluation of quantitative data from eight Likert-scale items to ascertain the clarity, structure, feasibility and applicability of the framework. Whereas, the evaluation of qualitative data from two open-ended questions was used to determine the adequateness of the classified NFRs and their inducing factors in addressing API quality challenges. The experts also offered some suggestions to improve the clarity, usability, and applicability of the framework. Quantitative and qualitative analysis results reflect positive experts’ perceptions of the framework’s clarity and structural soundness within the API domain. Additionally, the feedback by the experts allowed the researcher to refine the framework, especially through the inclusion of measurable KPI indicators in addition to the improvement in visual flow of the framework. Besides, the launching of expert-refined NFRQF-API framework in this study, bridged the gap in the extant literature. In particular, the framework combines a robust theoretical base with practical guidance, which offers validated conceptual quality guidelines to facilitate the software industry in the management of NFR-related issues as well as support the researchers in their scholarly works on APIs. Hence, this comprehensive study and the industry feedback have resulted in NFRQF-API framework with the ability to effectively guide both researchers and industry experts in improving API quality management practices.
