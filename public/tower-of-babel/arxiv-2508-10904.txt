A2HCoder: An LLM-Driven Coding Agent for Hierarchical Algorithm-to-HDL Translation
Jie Lei, Ruofan Jia, J. Andrew Zhang, Hao Zhang

Abstract
In wireless communication systems, stringent requirements such as ultra-low latency and power consumption have significantly increased the demand for efficient algorithm-to-hardware deployment. However, a persistent and substantial gap remains between algorithm design and hardware implementation. Bridging this gap traditionally requires extensive domain expertise and time-consuming manual development, due to fundamental mismatches between high-level programming languages like MATLAB and hardware description languages (HDLs) such as Verilog—in terms of memory access patterns, data processing manners, and datatype representations. To address this challenge, we propose A2HCoder: a Hierarchical Algorithm-to-HDL Coding Agent, powered by large language models (LLMs), designed to enable agile and reliable algorithm-to-hardware translation. A2HCoder introduces a hierarchical framework that enhances both robustness and interpretability while suppressing common hallucination issues in LLM-generated code. In the horizontal dimension, A2HCoder decomposes complex algorithms into modular functional blocks, simplifying code generation and improving consistency. In the vertical dimension, instead of relying on end-to-end generation, A2HCoder performs step-by-step, fine-grained translation, leveraging external toolchains such as MATLAB and Vitis HLS for debugging and circuit-level synthesis. This structured process significantly mitigates hallucinations and ensures hardware-level correctness. We validate A2HCoder through a real-world deployment case in the 5G wireless communication domain, demonstrating its practicality, reliability, and deployment efficiency.

Introduction

The rapid evolution of wireless communication systems has led to increasingly stringent requirements on real-time signal processing performance. In emerging applications such as massive MIMO, millimeter-wave communications, and software-defined radios, the ability to deploy high-throughput, low-latency signal processing algorithms on hardware platforms has become paramount. Among these platforms, Field Programmable Gate Arrays (FPGAs) offer a compelling combination of flexibility, parallelism, and power efficiency, making them an attractive choice for implementing real-time digital signal processing (DSP) pipelines.
Despite these advantages, deploying algorithms onto FPGA platforms remains a highly challenging task. The process involves not only functional translation but also architectural transformation to meet stringent timing, resource, and power constraints. Developers are required to address a broad set of design challenges—including data path optimization, memory hierarchy, and pipelining—all of which demand substantial expertise in both algorithm development and hardware design. This complexity often results in long development cycles, limited portability, and difficulty in rapid prototyping and iteration.

automated C-to-High-Level Synthesis (HLS) conversion for CPU-FPGA acceleration. However, existing approaches face notable limitations. First, generating hardware description languages (HDLs) such as Verilog directly from natural language involves an immense abstraction leap, often resulting in poor code readability and substantial debugging overhead. Second, methods relying on fine-tuned LLMs not only demand considerable computational resources and expert effort, but also yield models that, despite specialization, still underperform compared to state-of-the-art large-scale models such as GPT-4

To address the long-standing gap between algorithm development and hardware implementation, we propose a novel direction: leveraging LLMs to bridge the well-established MATLAB algorithm design environment with mature hardware synthesis flows. Specifically, we focus on automating the transformation of MATLAB-based communication algorithms into hardware-compatible implementations, with an intermediate stage targeting HLS to ensure both interpretability and synthesis reliability.
Our framework, A2HCoder, operates under a hierarchical transformation strategy that incorporates both horizontal algorithm decomposition and vertical refinement flow. Horizontally, A2HCoder disassembles complex communication algorithms into modular, loosely coupled components, simplifying the translation process and improving robustness. Vertically, it performs step-by-step refinement from MATLAB source code to synthesizable C code, ultimately targeting HDL synthesis via existing HLS toolchains. This staged transformation avoids the brittleness of direct HDL generation and the unpredictability of end-to-end LLM outputs.
A central challenge lies in reconciling the frame-based global memory paradigm of MATLAB with the stream-based, dataflow-oriented execution preferred in hardware. To this end, A2HCoder includes a dedicated code adaptation layer that restructures data access patterns and control flow into hardware-friendly forms. Furthermore, at each stage of the pipeline, agent-style feedback loops allow the LLM to iteratively revise its outputs based on synthesis feedback and task constraints, significantly reducing hallucinations and improving functional correctness.
By combining LLM-assisted reasoning with a structured and interpretable transformation pipeline, A2HCoder provides a scalable, train-free solution for agile algorithm-to-hardware deployment. We demonstrate its effectiveness through a real-world 5G communication system use case, highlighting its ability to generate synthesizable, efficient designs from high-level MATLAB algorithms.
Our main contributions are summarized as follows:

•

We propose A2HCoder, a hierarchical LLM-powered coding agent that automates the transformation of MATLAB-based communication algorithms into synthesizable hardware implementations. The framework bridges the semantic and structural gap between high-level algorithm design and hardware synthesis through a structured, multi-stage transformation pipeline.

•

We address the core challenge of mismatched execution models between algorithm and hardware by introducing a code restructuring module that adapts memory access patterns and computation styles to align with hardware’s stream-based semantics.

•

We demonstrate the effectiveness of A2HCoder through a case study involving a complete algorithm-to-FPGA deployment for a 5G baseband processing task, showcasing the framework’s scalability, reliability, and real-world applicability.

A2HCoder

To address the complexity of translating high-level MATLAB algorithms into efficient hardware implementations, we propose a hierarchical transformation framework that decomposes the end-to-end workflow into modular, verifiable stages. This layered design enforces clear semantic boundaries between subprocesses, facilitating fault isolation, iterative refinement, and overall system robustness.

As shown in Figure
1
, A2HCoder first performs submodule decomposition, which enables modular design, facilitates parallel development, and improves verification efficiency. Each submodule is then processed independently through a three-stage submodule processing pipeline: code adaption, code translation, and refinement. Finally, the processed submodules are assembled through system integration to form the complete system. Additionally, a support infrastructure coordinates with external tools to assist in code validation, synthesis, and other necessary operations throughout the pipeline.

Submodule Processing Pipeline

Workflow of Code Adaption.

3.1.1
Code Adaption within the MATLAB Domain

The first stage in bridging algorithm design and hardware deployment operates entirely within the MATLAB domain, where the focus is on adapting high-level, CPU-oriented code to meet the constraints of FPGA architectures. MATLAB algorithms are typically developed under a frame-based, global memory model with sequential control flow—characteristics well-suited to CPUs but misaligned with FPGA requirements such as stream-based data movement, predictable memory access, and pipelined execution. To resolve this mismatch, the adaptation process transforms both the memory access and execution models of the original code.

Global memory randomly accesses, such as
M[a,b]
, are restructured into sequential patterns like
M[i++]
that align with the limited and predictable access patterns of bounded on-chip storage such as circular buffers or shift registers. Similarly, batch-based operations are rewritten into sample-wise streaming pipelines, enabling compatibility with FPGA dataflow architectures. This transformation is not based on fixed rules; instead, it is guided by structured prompts fed into a LLM. These prompts encode domain-specific execution semantics—such as pipelinability, locality, and control boundedness—steering the LLM to generate hardware-friendly code without altering the algorithm’s functional intent.
The input to this stage is the original MATLAB code and its testbench (ori.m, ori-tb.m), and the output is an optimized version (opt.m) accompanied by an updated testbench for functional verification (Figure
2
). The transformation is validated through a two-step process: a functionality check and a rule compliance check, both conducted by an LLM-based agent. This ensures the adapted code maintains algorithmic correctness while conforming to FPGA-oriented coding standards. Successful verification completes the first stage and produces a semantically aligned intermediate representation ready for efficient translation into HLS C++, forming a robust bridge between software-centric algorithm design and hardware synthesis.

Figure 3:
Workflow of Code Translation.

3.1.2
Code Translation From MATLAB to HLS C++

The second stage transforms the optimized MATLAB code produced in the first stage into synthesizable HLS C++ code (module.cpp). This stage focuses on translating the algorithm for hardware-oriented execution by restructuring both the function’s input/output interface and its internal operations. Specifically, sample-based processing modules originally written in MATLAB are converted into stream-oriented structures that align with FPGA dataflow paradigms. Matrix-centric operations are rewritten using C-style constructs, and the resulting architecture is parameterized to support flexible hardware customization (Figure
3
).
To enhance performance and parallelism, instruction-level optimizations—such as pipelining, loop unrolling, and array partitioning—are applied. The generated HLS C++ code serves as the design-under-test (DUT) in the Xilinx Vitis toolchain, where it undergoes a comprehensive flow that includes C simulation, synthesis, and co-simulation, thereby completing the second stage of the transformation process.

Throughout testing and simulation, we leverage the mature capabilities of the Vitis HLS toolchain to ensure the translation process remains interpretable and debuggable. The toolchain generates detailed simulation log files that provide critical insights into functional and performance issues. These logs are fed back into the LLM-guided workflow, enabling automated or assisted debugging and refinement of the generated code, thus forming a closed-loop system that enhances both reliability and development efficiency.

3.1.3
Optimization and Refinement

Figure 4:
Workflow of Refinement.

The final stage of the submodule processing pipeline focuses on optimizing the validated HLS C++ code to reduce both resource utilization and computation latency. Building on the correctness established in the previous stages, this step ensures the generated hardware design is not only functional but also efficient (Figure
4
).
To address latency optimization, we introduce a buffer management mechanism. This component—guided by a combination of automated agents and LLM—identifies and eliminates unnecessary memory initialization overheads that often originate from variable declarations in the original MATLAB code. By streamlining buffer usage, execution latency is significantly reduced without altering the functional behavior.
For resource optimization, we employ design space exploration (DSE) techniques. Specifically, DSE analyzes different candidate implementations and explores the impact of varying data bit-widths to achieve an optimal balance between performance and hardware cost. This fine-grained tuning of data representation allows the refined module to meet area and timing constraints more effectively.
The outcome of this refinement stage is a highly optimized version of the submodule (e.g., module_ref.cpp), ready for integration into the final system design.

3.2
System-Level Integration and Deployment

After submodule-level processing, the focus shifts to system-level integration, where individually refined modules are composed into a unified, executable hardware design. This phase adopts a stream-based dataflow architecture, enabling multiple functional units to operate concurrently. The resulting design enhances throughput and resource utilization, making it well-suited for complex, high-performance FPGA deployments.

To orchestrate the overall system, A2HCoder automatically generates a top-level design file (top.cpp) that coordinates data movement and control signaling across all submodules. This top module ensures accurate producer-consumer communication by duplicating streaming channels where necessary to preserve one-to-one dataflow semantics. Interconnections are carefully constructed to maintain data dependencies while maximizing concurrency. Standard streaming protocols, such as AXI-Stream, are employed to enable low-latency communication with minimal buffering overhead (Figure
5
).
The integrated system is then processed using the Vitis HLS toolchain, which includes C-level simulation, synthesis, and co-simulation. These steps verify functional correctness, evaluate performance characteristics, and ensure that the design meets timing and resource constraints on the target FPGA. In addition, Vitis HLS provides detailed simulation logs, which offer insight into inter-module behavior, communication bottlenecks, and potential performance optimizations.
To further enhance system performance, DSE is applied after integration. This process systematically tunes parameters—particularly those related to parallelism levels—to strike a balance between throughput, area, and resource efficiency. By exploring various configuration options, DSE helps identify the most effective trade-offs for the target application.

Through this integration process, A2HCoder assembles reusable, optimized building blocks into a scalable and high-performance hardware system, completing the transformation from abstract algorithm design to a fully synthesized and deployable FPGA implementation.

3.3
Experience Repository for Continual Learning

To enhance adaptability and convergence efficiency across diverse code transformation tasks, we design a Prompt Library that functions as a persistent knowledge base for storing and reusing high-value transformation experiences. Unlike traditional static prompt engineering, this component introduces a lightweight yet effective mechanism for continual learning within our framework—enabling the system to recall, adapt, and generalize from prior successful cases.

The Prompt Library ingests and organizes information collected throughout the transformation process, including: (1) the task type (e.g., FFT pipeline, channel equalization), (2) the structured prompt used by the LLM agent, (3) the corresponding generated code, and (4) relevant validation logs and outcomes. This information is automatically extracted and stored when a transformation loop successfully produces functionally correct and constraint-compliant results.

During future iterations, the library enables two key reuse strategies:

•

Prompt Retrieval: When the system encounters a new task similar to a previously solved one, the agent retrieves the most relevant prompt(s) based on task metadata or semantic similarity. These prompts serve as strong priors, reducing the number of iterations required for convergence.

•

Contextual Prompt Construction: In more complex scenarios, the agent may embed code snippets or partial transformation trajectories from past cases directly into the new prompt. This provides the LLM with richer context and improves reasoning consistency across similar structural patterns.

By integrating prompt reuse and context injection, the Prompt Library empowers the system to accumulate procedural knowledge over time, effectively bootstrapping from earlier successes. This continual refinement process improves both efficiency and robustness, particularly when scaling to new domains or algorithm classes. The design is lightweight and model-agnostic, further enhancing the framework’s long-term adaptability and performance.

4
Experiments

To validate the practicality and robustness of the proposed A2HCoder framework, we apply it to a real-world 5G signal processing task: the hardware implementation of a 5G New Radio (NR) Synchronization Signal Block (SSB) detection system, referred to as detectSSB. The project follows the 3GPP 5G NR specifications and targets FPGA deployment using MATLAB, Vitis HLS, and RFNoC. It is implemented on a NI USRP X310 platform and could achieve a high-performance streaming architecture with 1 sample/cycle throughput and post-route clock frequencies up to 292 MHz. In a practical deployment, the system throughput was deliberately limited to one sample per eight clock cycles to reduce the number of DSP units required for PSS cross-correlation, taking into account the low sampling rate of the 5G NR SSB at 7.68 Msps.

The detection pipeline consists of five core submodules, each handling a specific stage of the SSB detection algorithm:

•

pssCorrelator
: Detects PSS sequences via complex correlation using FIR filter structures.

•

calcThreshold
: Computes dynamic, energy-based detection thresholds to adapt to varying signal conditions.

•

peakFinder
: Identifies local peaks in correlation results using a sliding window approach.

•

collectLocations
: Aggregates and filters valid peak locations across PSS sequences.

•

extractSSBsig
: Extracts full 4-symbol SSB segments and formats output with metadata and RFNoC framing.

A top-level module,
detectSSB
, integrates these submodules into a complete system that operates under RFNoC constraints and supports runtime configuration via AXI register interfaces. This system represents a complex, multi-stage, and performance-critical application, making it a suitable benchmark for assessing A2HCoder’s capability in modular decomposition, stepwise transformation, and hardware-oriented code generation.
Each functional submodule is individually passed through A2HCoder’s hierarchical pipeline—code adaptation, translation, integration—and verified through simulation and hardware synthesis. The streaming and AXI4-Stream compatibility of the final outputs enables deployment within an RFSoC-based USRP system, demonstrating the framework’s effectiveness in agile, reliable, and standards-compliant algorithm-to-hardware deployment.

Case Study 1: calcThreshold

The first case study focuses on
calcThreshold
, a dynamic energy thresholding module that processes streaming complex input samples and outputs a signal energy threshold used in SSB detection.
The baseline generates functionally correct C++ code using a LLM, but the structure closely mirrors MATLAB’s imperative computation model. In particular, the shift-register based delay line for implementing a moving average filter is unrolled into deeply pipelined hardware, leading to excessive resource utilization and routing congestion. As a result, although the synthesized design produces outputs, it fails to complete implementation due to critical timing violations and excessive LUT and FF usage. In contrast, the Code Adaptation stage replaces this memory-intensive structure with a circular buffer and a running sum accumulator, significantly reducing memory bandwidth and hardware arithmetic complexity. This transformation reduces LUT usage from 36,500 to 685 and enables successful implementation at 277 MHz post-route, with equivalent latency preserved.
Finally, Refinement introduces optimized fixed-point widths identified by DSE, reducing arithmetic precision without violating functional constraints. Additionally, LLM-guided latency refinement eliminates the 256-cycle buffer initialization loop through conditional logic, treating uninitialized values as zero during early iterations. This results in a 6,013-cycle latency (vs. 6,301 previously), while further shrinking the resource footprint to 173 LUTs, 274 FFs, and only 3 DSP blocks. The final design operates at 322 MHz post-route, achieving full functionality with the highest timing closure and minimal hardware cost. Table

Case Study 2: extractSSBsig

The second case study focuses on
extractSSBsig
, a module responsible for extracting the 4-symbol SSB segments from a received 5G NR frame based on detected peak locations. This operation involves segmenting a windowed region from a buffered stream and outputting selected SSB candidates. As with the previous case, we evaluate three configurations: Direct LLM Translation, Code Adaptation, and Refinement.

In the baseline configuration, the implementation replicates the original MATLAB logic with minimal restructuring. The entire input is pre-buffered, and a fixed loop performs indexed access to extract the SSB segments. While functionally correct, this monolithic design performs poorly in terms of hardware efficiency, requiring 4,468 LUTs and 7,071 FFs, along with 24 BRAMs. The extraction latency is also extremely high at 24,890 cycles, due to inefficient control logic and unnecessary buffering of the full signal.
In the Adaptation version, we refactor the architecture into a streaming pipeline with an FSM-based controller. A circular buffer stores incoming samples, and SSB extraction is gated based on data readiness and peak arrival. This adaptation reduces latency by nearly 50%, from 24,890 to 12,441 cycles, and trims logic usage to 275 LUTs and 353 FFs. The design also eliminates most BRAMs (from 24 to 4) through more targeted memory buffering.
The Refinement version further enhances the FSM controller with conditional logic that removes unnecessary buffer initialization and guards against invalid memory access. In particular, uninitialized memory locations are handled via safe zero-substitution, and peak processing skips expired or overlapping segments to avoid pipeline stalls. These changes reduce latency to 6,730 cycles—a 73% reduction from the baseline—and bring LUT usage down to just 155. Clock frequency improves to 269 MHz post-route, making it suitable for high-throughput deployments. Table

Conclusion

In this work, we introduced A2HCoder, a hierarchical, LLM-driven coding agent designed to bridge the longstanding gap between high-level algorithm design and hardware implementation. By leveraging the reasoning capabilities of LLMs in a structured, multi-stage pipeline, A2HCoder transforms MATLAB-based communication algorithms into synthesizable HDL code in a reliable, interpretable, and efficient manner.
Our hierarchical approach—combining horizontal algorithm decomposition with vertical step-by-step refinement—effectively addresses the semantic mismatch between software-oriented design paradigms and hardware constraints. By incorporating prompt-guided code restructuring and agent-style feedback loops, A2HCoder significantly mitigates hallucination issues common in LLM-generated code and ensures correctness throughout the transformation process.

Through a real-world case study of a 5G New Radio SSB detection system, we demonstrated A2HCoder’s capability to generate high-performance, resource-efficient, and deployable FPGA implementations. The results highlight the critical contribution of each stage in the framework and confirm its practicality for agile hardware deployment, enabling both modular synthesis and seamless system-level integration.
Looking ahead, we plan to extend A2HCoder to support a broader range of input languages and hardware platforms, and to incorporate multimodal capabilities for deeper contextual understanding. We believe that A2HCoder represents a meaningful step toward intelligent, automated hardware design, and offers a compelling direction for deploying LLMs in engineering-centric domains.
