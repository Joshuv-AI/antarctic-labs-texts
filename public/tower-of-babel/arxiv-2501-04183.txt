Transparent Transformations for Timing Side-Channel Analysis
Santiago Arranz-Olmos, Gilles Barthe, Lionel Blatter, Sören van der Wall, Zhiyuan Zhang

Abstract
. Side-channel analysis frameworks often lift programs into an intermediate representation (IR) before analyzing them. These IRs are subject to transformations, which we call ex ante ( xa ) transformations, that improve the efficiency and accuracy of the analysis, thereby directly impacting the validity of analysis results. This paper explores the impact of xa transformations in the setting of timing-based side-channel analysis frameworks, focusing on the constant-time policy that many cryptographic libraries adopt. We identify two properties of xa transformations that directly impact the soundness and precision of side-channel analysis. The first property, preservation , requires that the transformation does not introduce leakage and is required to avoid false positives, i.e., for precision. The second one, reflection , requires that the transformation does not remove leakage and is required to avoid false negatives, i.e., for soundness. The combination of preservation and reflection, which we call transparency , is essential for sound and precise transformations. While preservation has been studied in the context of secure compilation, there is little work on reflection. This paper initiates the formal study of reflection and transparency. We formalize their definitions, propose a general method for proving that a transformation is transparent, and apply our method to different standard transformations. Subsequently, we present a transparent core decompiler that combines seven common xa transformations and prove that it is sound and precise. Additionally, we review the transparency of five existing tools and unveil violations in popular side-channel analysis frameworks and decompilers. Finally, we extend our approach to the setting of speculative side-channels. We redefine transparency of transformations with respect to Spectre attacks, and reevaluate the xa transformations for transparency with respect to Spectre.



1.
Introduction

Timing attacks
(
Koc96
;
bernstein2005cache
)
are a prominent class
of side-channel attacks that infer information about program secrets
from observing and analyzing program execution time under different
inputs. These attacks often target cryptographic libraries, and can
allow malicious parties to recover cryptographic keys in real-time.
To counter this threat, cryptographic libraries developers adopt the
so-called constant-time (CT) policy, which mandates that programs do not
branch on secrets and do not perform secret depend memory accesses.
Following this policy ensures that common timing attacks can not
infer secret values.

The constant-time policy is conceptually simple. Nevertheless, it is
notoriously hard, even for expert programmers, to write CT
code that satisfies typical efficiency constraints for cryptographic
implementations. Over the last decade, numerous side-channel analysis
tools
(
BarbosaBBBCLP21
;
DBLP:conf/sp/JancarFBSSBFA22
;
GeimerVRDBM23
)

have emerged to assist developers in writing constant-time code. These
tools have helped detecting many CT violations in widely deployed
libraries. A further benefit of these tools is that they are grounded in
solid theoretical foundations, including static and dynamic analysis,
type systems, or program verification.

Problem Statement.

Generally, side-channel analysis frameworks do not operate on programs
directly, but rather on programs representations. They rely on

ex ante
transformations to turn programs into their
representation and (potentially) simplify them.
This leads to a gap between the real program and the
analyzed program with the potential for incorrect analysis results:

xa
transformations can introduce or remove CT violations, which can
result in false positives and false negatives.
False positives impact the precision of the analysis, while false
negatives break its soundness.

Ex ante
transformations are widespread: they can be applied at
source, intermediate representation, assembly, and binary levels, and
they are method agnostic, i.e., they apply both to
static
(
DanielBR20
)
and logical
analyses
(
DBLP:conf/uss/AlmeidaBBDE16
)
.
Furthermore, such transformations are frequently necessary for analyses
that expect a specific representation of their input.
Unfortunately,
xa
transformations are rarely documented, and
their security impact is poorly understood.

This paper aims to develop a better understanding of the security gap
introduced by
xa
transformations.
We address the following research questions:

Q1

What are the key properties of
xa

transformations that guarantee sound and precise analysis results?

Q2

How can we enforce these properties in
xa

transformations?

Q3

Do
xa
transformations in practical tools
satisfy these properties or are they susceptible to incorrect analysis
results?

Contributions.

Our work contributes to answer the questions as follows.
For
Q1
, we identify two properties of
xa

The first property,

, ensures that
xa

This is a necessary condition for precise analysis results.
The second property,

xa

This property is essential for sound analysis results.
The combination of preservation and reflection, which we call

Motivated by recent work

2.
Background

In this section, we provide a brief overview of micro-architectural
side-channel attacks, the constant-time policy, and tools for detection of CT violations.

Micro-Architectural Side-Channel Attacks.

Side-channel attacks manipulate and monitor
micro-architectural resources, shared between the attacker and the victim, to
leak secret information.
In the past two decades,
various micro-architectural resources have been shown to be exploitable.
Two major types of attacks are cache-based and branch-based attacks.
Cache based attacks such as
Prime+Probe

(
DBLP:conf/ctrsa/OsvikST06
)
and

Flush+Reload

(
DBLP:conf/uss/YaromF14
)
reliably monitor the cache
activity of a victim program.
Whenever the address to a memory access is dependend on secret data,
this leaks information of the secret to the attacker.
Similarly, in branch based attacks,
attackers infer branch outcomes of a victim program
by monitoring execution time
(
DBLP:conf/micro/EvtyushkinPA16
)
,
hardware performance counters
(
DBLP:conf/asplos/EvtyushkinRAP18
)
,
or the instruction prefetcher
(
ZhangTOCGY23
)
.
In this case, secret-dependend branching conditions leak to the attacker.
Other resources have also been exploited to leak secrets, such as execution
ports
(
DBLP:conf/ccs/BhattacharyyaSN19
;
DBLP:conf/sp/AldayaBHGT19
)
and
load/store
buffers
(
DBLP:conf/ctrsa/MoghimiES18
;
DBLP:journals/tches/SieckZBCEY24
)
.

Constant-Time and Vulnerability Detection.

The constant-time policy protects cryptographic libraries against side-channel attacks.
This policy assumes that an attacker can
observe the control flow and memory accesses of a program during
execution, and requires that the observations leak no
secret information.
There exist over fifty analysis tools for the constant-time
policy
(
BarbosaBBBCLP21
;
DBLP:conf/sp/JancarFBSSBFA22
;
GeimerVRDBM23
;
FourneBJSSBFA24
)
.
Dynamic analysis and logical/static analysis are two main methods.
Dynamic analysis
(
DBLP:conf/acsac/WichelmannMES18
;
DBLP:conf/ccs/WichelmannSP022
)

executes a binary to find vulnerabilities.
In contrast, logical/static analysis
(
DBLP:conf/uss/AlmeidaBBDE16
)
does not execute the binary.
Instead, it uses logical reduction, abstract interpretation, or
symbolic execution to achieve formal guarantees on the execution of the program.
Namely, the analysis guarantees to find all violations (sometimes
only up to some bound) or proves their absence.
However, static analysis tends to operate on the source code or an
ad hoc representation of the program.
They suffer from not being able to find vulnerabilities introduced
by compilers, since the apply only to source programs.
According to the table of analyzers summarized by
(
GeimerVRDBM23
)
,
only four out of nineteen logical/static analyzers work on binary programs.
To utilize the other tools, one needs to apply
xa
transformations
to turn the binary into source code or their ad hoc representation.

We consider that a programming language is a set
