Analyzing Variations in Dependency Distributions Due to Code Smell Interactions
1 st Zushuai Zhang, 2 nd Elliott Wen, 3 rd Ewan Tempero

Abstract
The existence of dependencies between modules, such as classes, can mean that changing a module triggers ripple effects that make maintenance complex and costly, so the advice is to minimize dependencies between modules. It is therefore important to understand the circumstances that can lead to increased dependencies. Recent studies suggest that code smells, which are characteristics of code that indicate potential design issues, may interact in ways that increase dependencies between modules. In this study, we aim to confirm previous observations and investigate whether and how the distribution of static dependencies changes in the presence of code smell interactions. We conducted a dependency analysis on 116 open-source Java systems to quantify the interactions, comparing interactions among code smells and interactions between code smells and non-code smells . Our results suggest that while interactions between code smell pairs are associated with increases in certain dependencies and decreases in others, overall, they are associated with an increase in total dependencies. For example, the median number of dependencies between Feature Envy methods and Data Classes is seven times as many as when the methods are non-Feature Envy methods, increasing from 1 to 7. This implies that developers should prioritize addressing code smells that interact with each other, rather than code smells that exist only in isolation.



I
Introduction

Maintainability is a critical aspect of software. One of the challenges in maintaining software is managing dependencies between modules, such as classes. Dependencies can propagate changes across the system, leading to ripple effects that make maintenance activities complex and costly
[
1
]
. As a best practice, software engineering recommends minimizing dependencies to improve modularity. However, our understanding of what factors affect the presence of dependencies is incomplete.

One such factor that has gained attention is the presence of code smells, which are characteristics of the source code that suggest possible design flaws
[
2
]
. Code smells have traditionally been studied in isolation, but research suggests they may interact in ways that increase dependencies
[
3
,
4
]
. However, to the best of our knowledge, no previous study has formally defined the term “interaction” or quantitatively compared interactions among code smells and between code smells and non-code smells to investigate the influence of code smell interactions on dependency growth.

The primary objective of this study is to validate previous observations and theories while providing new insights into how code smell interactions influence the distribution of dependencies. To achieve this, we define interaction as a set of static dependencies between artifacts and analyze 116 open-source Java systems, focusing on five commonly studied code smells: Brain Class (BC), God Class (GC), Brain Method (BM), Feature Envy (FE) and Data Class (DC). By comparing the number of dependencies when code smells interact with other code smells versus when they interact with non-code smells, we provide empirical evidence to either support or challenge existing theories and observations on code smell interactions, as well as explore new insights.

Our results indicate that interactions between pairs of code smells are associated with increases in certain dependencies and decreases in others. However, overall, they are associated with a significant increase in the total number of dependencies, with at least a small effect size. Although this may not be surprising, to our knowledge, this is the first quantitative evidence that confirms what has been believed. The implication is that, during refactoring, it may be more effective to prioritize code smells that interact with each other, rather than those that exist in isolation, as the former tend to involve stronger dependencies.

These findings carry several important consequences for software engineering research and practice:

•

Dependency analysis tools can identify problematic dependencies by focusing on code smell interactions, aiding developers in better managing code quality and prioritizing refactoring resources.

•

Researchers conducting dependency-related studies need to account for the presence of code smells and their interactions, as these factors may significantly influence the representativeness of study results.

III
Study Design

III-A

Research Questions

This study aims to answer the following two research questions (RQs):

RQ1

How frequently do code smells interact?

RQ2

How do dependency distributions differ due to code smell interactions?

Our main focus is RQ2. However, we first need to understand how frequently code smells interact. If interactions are rare, then investigating their consequences becomes less meaningful. Hence, we begin with RQ1.

III-B

Dependency

To answer our RQs, we need to define what we mean by “interaction,” and to do that, we need to define what we mean by “artifact” and “dependency.” We consider artifacts as one of three types: Class (which includes both regular classes and interfaces), Callable (both Method and Constructor), and Field. Field and Callable are more fine-grained than Class, as a Class can contain both. We adopt the dependency definition discussed in Section
II-C
, but attribute it to the most fine-grained artifact possible to better capture interactions. For example, if a class contains a field of the type of another class, we attribute the dependency from the field to the other class, rather than between the classes themselves. Table

When this happens, we treat them as distinct dependency types. Each dependency is directional, flowing from the source artifact to the target artifact.

III-D

Roles

Fig. 2:
Roles for Methods and Fields

Roles are assigned to artifacts involved in dependencies from the interaction set. In addition to general roles such as Class, Method, Field, or Constructor, we assign additional meaningful roles to methods and fields based on their purpose to gain deeper insights. For example, accessor methods are primarily used to get or set fields, whereas non-accessor methods, referred to as functional methods (FMs), typically perform more complex operations. A constant field stores data that remains the same, while an instance field holds data specific to a particular object created from the class.

As shown in Figure
2
, blue rectangles represent roles assigned to methods, while red rectangles represent roles assigned to fields. Field roles are determined based on their modifiers, whereas method roles are assigned based on whether they function as accessors. An artifact can have multiple roles; for example, a constant field can have the roles Field, Static Field, and Constant.

III-E

Detection of Code Smells and Non-Code Smells

We employed the metric-based approach
[
6
]
to detect code smells, as described in Section
II-A
. A non-code smell (nonCS) refers to an artifact of the same type that does not exhibit the specific smell. For example, a non-God Class (nonGC) is defined as a class that is not a GC, although it may exhibit other smells, such as DC. If all GC are detected in a system, the remaining classes will be considered nonGC.

III-F

Methodology

To answer RQ1, for each code smell pair CS1 and CS2, we determine the percentage of distinct CS1 artifacts that interact with at least one CS2 artifact (i.e., with a non-empty interaction set), relative to the total number of CS1 occurrences. We then apply the same approach from the perspective of CS2.

For RQ2, to determine whether dependency distributions vary due to code smell interactions, we compare situations where a code smell interacts with another code smell (code smell interaction present) and where a code smell interacts with a non-code smell (code smell interaction absent). Specifically, given a code smell pair CS1 and CS2, we define the following three interaction cases:

•

CS1-CS2 (CS1 interacts with CS2)

•

CS1-nonCS2 (CS1 interacts with nonCS2)

•

nonCS1-CS2 (nonCS1 interacts with CS2)

We conduct the following two comparisons to determine whether there is a significant difference in the number of dependencies, as measured by the size of the interaction set for each interaction case:

•

(CS1-CS2) vs. (CS1-nonCS2)

•

(CS1-CS2) vs. (nonCS1-CS2)

To test RQ2, we test the hypothesis:

•

H_{0}
: The number of dependencies is
not
significantly different when a code smell interacts with another code smell compared to when it interacts with a non-code smell.

•

H_{1}
: The number of dependencies is significantly different when a code smell interacts with another code smell compared to when it interacts with a non-code smell.

To ensure a comprehensive analysis, these hypotheses are tested against the following conditions:
Relative Location
,
Type of Dependency
,
Flow Direction
, and
Roles
. Relative Location refers to whether the two artifacts involved in the interaction are in the same or different classes. Type of Dependency is as shown in Table
I
. Flow direction refers to whether it is forward or backward. Role refers to the roles of the two artifacts.

This study is limited to five code smells, interactions between smells of different types (corresponding to 10 smell pairs), and the roles specified in Figure
2
.

III-G

Systems Selection

We focus on open-source Java projects on GitHub. The rationale for assessing only Java projects is to ensure consistency with previous research for comparable results. To prioritize the most popular and widely accepted projects, we sorted all available projects in descending order based on the number of stars. Then, we applied the following inclusion and exclusion criteria (IC and EC):

IC1
. More than 100 forks (indicating active use and acceptance by the community).

IC2
. Recent Activity: The last commit must be later than January 1, 2024 (ensuring active development and maintenance).

IC3
. Java Percentage: Over 80% of the source code must be written in Java (due to tool limitations).

EC1
. Educational projects that do not represent real-world software development practices.

EC2
. Projects that are no longer maintained

We selected the first 150 projects that matched the IC. Then, we manually analyzed each project to apply the EC, ultimately selecting 116 projects. Table

provides a statistical summary of the 116 Java projects analyzed, covering key software metrics such as the number of classes (NOC), number of methods (NOM), lines of code (LOC, excluding blank lines and comments), and the occurrence of five code smells. The dataset varies greatly in size: the standard deviation (SD) of LOC is almost twice the mean. The largest project (Hadoop) contains over 2.7 million lines of code, whereas the smallest (RxAndroid) has just over 1,300. Similarly, the number of code smells varies from zero to high occurrences. Given the diversity in project scale and code smells, we believe this sample is representative of real-world Java software and provides sufficient data for analyzing code smell interactions.

For each system, we detected code smells and non-code smells, along with all types of dependencies. Then, for each pair of interacting artifacts that matched an interaction case of a code smell pair, we collected the interaction set and relative location information. We exclude artifact pairs that do not interact (i.e., those with an empty interaction set) because our research focuses on understanding interaction. Including non-interacting pairs would not contribute to this understanding and could dilute the results. For example, for the code smell pair BC and GC, consider one of its interaction cases (BC-nonGC). For every pair of interacting artifacts, with one being BC and the other nonGC, we collect their interaction set and determine whether they belong to the same class or different classes.

Afterward, for each dependency from the interaction set, we recorded its dependency type and flow direction, then assigned roles to its source and target artifacts. An example would be a call (Callable to Callable) dependency from an FM in a BC to a getter method in a GC, with a forward flow direction. The pairing of the source and target artifacts’ roles (in this case, the pairing is (FM, getter)) is used as a condition in data analysis.

After collecting this information for each system, we combined the data from all 116 systems to create an aggregated dataset. By assessing the interaction set from the aggregated dataset, we calculated the frequency of interactions for each code smell pair to support RQ1. To answer RQ2, we conducted two types of analysis: General Analysis and Specific Analysis. Both analyses assess whether, when comparing different interaction cases for a given code smell pair, there is a significant difference in the number of dependencies that satisfy a specific selection of conditions. In General Analysis, we consider only relative location as a condition and focus on the total number of dependencies (i.e., the size of the interaction set). In Specific Analysis, we introduce three additional conditions to further refine the dependency category under consideration: dependency type, flow direction, and roles. For this analysis, we consider the size of the interaction set after filtering out dependencies that do not satisfy the selected conditions. A comparison of the two analyses is shown in Table
III
.

The General Analysis provides an overview of how interactions influence the total number of dependencies. In contrast, the Specific Analysis takes a more context-aware approach, offering a finer-grained understanding of which specific dependency categories are influenced by code smell interactions and which contribute more to variations in the total number of dependencies. We applied both analyses to each individual system as well as to the aggregated dataset to determine whether the results remain consistent across different systems.

The Mann-Whitney U test
[
59
]
was selected as the primary statistical test. This test was chosen because our data does not follow a normal distribution, and the two interaction cases being compared are independent with unequal sample sizes (e.g., there are more pairs of artifacts that interact between code smells and non-code smells than among code smells, due to the larger number of non-code smells compared to code smells).

Since this test only determines whether a difference exists but does not measure its magnitude, we computed Cliff’s Delta, a non-parametric effect size measure that quantifies the strength of the observed difference. Cliff’s Delta can be positive or negative. A positive value indicates that code smell interactions are associated with a higher number of dependencies compared to interactions between code smells and non-code smells, while a negative value suggests the opposite. To interpret Cliff’s Delta, we adopted widely accepted thresholds
[
60
]
:
negligible (
|d|<0.147
), small (
0.147\leq|d|<0.33
), medium (
0.33\leq|d|<0.474
),
and large (
|d|\geq 0.474
).

Implementation

CodeQL

The ”Not Sig.” category represents systems that are not statistically significant. Categories “No Int. (No Smell)” and “No Int. (Missed)” account for systems that lack the specific interactions required for statistical testing. “No Int. (No Smell)” includes systems where at least one of the code smells in the pair is absent, making interaction impossible. For example, consider the row BC-GC: a system falls into this category if it lacks either BC or GC. “No Int. (Missed)” includes systems where both code smells (e.g., BC and GC) are present but do not interact. Since our approach only analyzes interacting artifacts, systems without interactions do not affect or dilute the results.

The percentage in the top right of each bar chart represents the
significance rate
, which is calculated as the number of significant projects (sum of categories 1 to 8) divided by the number of projects where interaction exists (sum of categories 1 to 9). The significance rates for the pairs BC-DC and GC-DC under the same-class condition are marked as “NULL” because no interactions exist in any system.

Approximately 25% of the comparisons have a significance rate greater than 50%. The comparison with the highest significance rate is (BM-DC) vs. (nonBM-DC) under the Same Class condition (83.33%), followed by (FE-DC) vs. (nonFE-DC) under the Different Class condition (81.71%). The lowest significance rate occurs for (BC-GC) vs. (BC-nonGC) under the Same Class condition (2.56%).

The number of projects with missing interactions is more dominant under the Same Class condition compared to the Different Class condition, especially for the pairs: BC-DC, GC-DC, BM-DC, and FE-DC. This is because DC refers to simple classes, while BC, GC, BM, and FE represent complex artifacts, making it unlikely for them to appear in the same class. The number of projects that exhibit no interaction due to the absence of a code smell is the same across all four comparisons for every code smell pair.

V
Discussion

V-A

Frequency of Code Smell Interactions (RQ1)

From Table
IV
, the high interaction percentage between BC and BM (99.7%), and the much lower percentage from BM to BC (56.7%), is not surprising. This is because a class must have at least one BM to be detected as BC. Any intra-class dependency involving the BM will be considered an interaction. However, the reverse is not necessarily true because BM can appear in a nonBC class. Separately, the low interaction percentage between BM and FE (7.0%) is due to the fact that both are method-level smells. The only way they can interact is through method calls. However, BM and FE both require data but do not provide it. Since calling each other does not satisfy their data requirements, they are unlikely to interact. Another observation is the high interaction percentage between BC and GC (79.8%), possibly because they are both complex classes that depend on each other’s methods.

Examining the column for DC reveals that the interaction percentage from any other smell to DC is relatively high (with the lowest being 19.8%). This can be explained by the fact that DC provides data, while other code smells either require data (BM, GC, and FE) or contain methods that require data (BC), making interaction likely. In contrast, when looking at the row for DC, the interaction percentages are lower than those in the column. This is because DC has the highest occurrence across 116 systems. Although many other smells obtain data from DC, the number of other smells is significantly lower than the number of DC occurrences. As a result, the interaction percentage between DC and any other smell is diluted by the large number of DC instances.

RQ1 Summary:
Overall, our results indicate that most code smell pairs frequently interact with each other, with over 50% of the pairs exhibiting an interaction rate above 40%, likely due to dependencies on data and methods. This highlights the importance of assessing the consequences of code smell interactions, as addressed in RQ2.

V-E

Threats to Validity

As with any similar study, there is a threat to external validity due to the systems we studied. Our conclusions may still apply to languages similar to Java, such as C++ and C#. It would be extremely interesting if the language were significant. The expensive nature of our analysis limited the sample size. A post-hoc analysis revealed that the selected projects vary in size, number of code smells, and domains. Based on this, we concluded that our sample is sufficiently representative of Java projects. While there is no reason to expect a larger sample would change the conclusions, we do note that some individual projects did not follow the trend we observed.

A threat to construct validity is the choice of tool used to detect code smells. To mitigate this threat, we avoided using existing tools due to unclear documentation regarding code smell definitions and detection methods, potential inconsistencies with prior literature, and a lack of availability or discontinued maintenance. Instead, we implemented our own tool for code smell detection. We ensured that our implementation aligns with the widely used metric-based approach proposed by Lanza and Marinescu
[
6
]
, adhering to their code smell and metric definitions, thresholds, and detection rules.

A threat to internal validity is detection error. To minimize false positives, we selected the stricter bound when the threshold was specified as a range. While false negatives may still occur, their impact on the results is limited because the detected smells are typically real and severe, meaning the identified trends remain valid.

Another threat to internal validity in our study arises from our decision on how to count dependency frequency. Specifically, we recorded each type of dependency only once between two artifacts, regardless of how many times it occurred. For example, if method A has a call dependency on method B and invokes it three times, we record this dependency only once. While this approach may result in some loss of information regarding the intensity of certain dependencies, it helps reduce noise from repeated dependencies that may not necessarily indicate a more meaningful distribution, such as repeated calls to print or log methods.

VI
Conclusions

The objective of this study is to investigate the frequency of code smell interactions and how dependency distribution varies due to these interactions. This is achieved by examining five code smells across 116 open-source Java projects. Empirical evidence suggests that most pairs of code smells frequently interact, particularly Brain Class and God Class, highlighting the importance of examining the consequences of such interactions. Additionally, the findings show that while code smell interactions are associated with increases in certain dependencies and decreases in others, they are overall linked to a significant increase in the total number of dependencies, with at least a small effect size. Although this result may not be surprising, to the best of our knowledge, this is the first study to provide such empirical evidence. These findings imply that practitioners should prioritize addressing interacting code smells rather than those that exist in isolation, as the former tend to exhibit more severe dependencies.

Future work will investigate a broader range of code smells, interactions between code smells of the same type, and additional types of roles. Additionally, studies could examine contextual variables, such as the project domain and programming language, to assess their influence on code smell interactions.
