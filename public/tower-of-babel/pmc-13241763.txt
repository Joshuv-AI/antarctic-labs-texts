Mexican sign language 3D static alphabet dataset
Authors: Homero V. Rios-Figueroa, Candy O. Sosa-Jiménez
Published: 2026

ABSTRACT
Sign language (SL) is mostly used by hearing-impaired people to communicate. Each country has its own SL. Usually, SL is structured in terms of its alphabet, words, and grammar. In Mexico, there are few investigations on Mexican Sign Language (MSL) automatic recognition, and published datasets are rare. To contribute to this research, we obtained a dataset of 21 static letters from the MSL alphabet. For each letter, 15 individuals performed the task once, and the data were collected using a 3D surface sensor to obtain the coordinates of the 3D points. All individuals used their right hand to perform the signs. The dataset contains 315 text files with 3D coordinates of the letters.

This dataset corresponds to training with 12 examples per class and testing with three examples per class. MSL research and datasets.

Background

The most recent 2020 Mexican census reported that the general population of the country was 126,014,024. Of these, 5,104,644 people had some difficulty in hearing and 2,234,303 people had difficulties in talking or communicating. This indicates that at least 7,338,967 people may use MSL as a primary language for communication in addition to those who want to communicate with this community.

Communication is highly important in society. Hearing-impaired people have problems communicating because most of them only use sign language. Only a very small percentage of the general population understands and can communicate with MSL. There are only 40 certified interpreters of the MSL. Therefore, automatic translator systems between MSL and Mexican Spanish could help overcome this bottleneck of communication.

There are very few investigations on the automatic recognition of MSL [[5], [6], [7], [8], [9]], and public datasets are even smaller [1,2]. Most existing research focuses on using color or grayscale images, but only a limited number of studies have used 3D data from depth sensors. The main motivation for compiling this dataset is to foster research on the automatic recognition of MSL static alphabets using 3D data to serve as one of the reference datasets.

Data Description

The MSL alphabet is composed of 21 static letters and six to nine dynamic letters, depending on the reference. The 21 static letters are A, B, C, D, E, F, G, H, I, L, M, N, O, P, R, S, T, U, V, W, Y. most authors agree on at least six dynamic letters: J, K, Ñ, Q, X, and Z [[12], [13], [14]]. Calvo-Hernández added two additional dynamic letters, LL, RR [13]. López-García et al. add another one: CH [14].

This data article focuses only on the MSL static alphabet. The main folder where the dataset is stored is the 3D Mexican Sign Language Static Alphabet, Normalized about the origin and in scale. It contains 21 subfolders named in the upper case: A, B, C, D, E, F, G, H, I, L, M, N, O, P, R, S, T, U, V, W, and Y, corresponding to right-hand static letters in the MSL Alphabet (Fig. 1).Fig. 1Subfolder structure of the 3D MSL Static Alphabet, normalized about the origin and in scale, dataset.Fig 1 dummy alt text

Subfolder structure of the 3D MSL Static Alphabet, normalized about the origin and in scale, dataset.

Each subfolder contained 15 files (.txt) with the name of the letter in the lower case, followed by numbers between 1 and 15. For example, for letter A, the files are a1.txt, a2.txt…, and a15.txt (Fig. 2). The naming convention was consistent and invariant throughout the dataset. A folder named with upper case, for instance, “A” is used for the class shape (Fig. 1), and the 15 specific instances are named with lower case (Fig. 2).Fig. 2For each letter in the 3D MSL Static Alphabet, normalized about the origin and in scale, dataset, there are 15 text files. Each text file contains as many lines as the letter has 3D points for its spatial representation. Each line was composed of three floating-point numbers that provided the coordinates (X, Y, Z) of a 3D point (Fig. 3). For example, file a1.txt, its corresponding class label is letter “A,” it has 1618 point (Fig 3). The data in this file can be read in a matrix of 1618 rows and three columns corresponding to the (X, Y, Z) coordinates. A simplified matrix representation showing the first two rows and last two rows is presented in Table 2. A user loading any of the files in the dataset into a matrix obtains a similar representation. The MS Kinect V.1 sensor coordinate system for depth image acquisition was placed at the center of the depth camera. The coordinate system followed a right-handed convention. The X-axis points to the left (from the perspective of the sensor), the Y-axis points upward, and the Z-axis points forward in the direction facing the camera. The coordinates (X, Y, Z) are in meters. From the 3D data in the text file, it is possible to recover geometrical and graphical representations. For example, the data in the a12.txt file is shown as a 3D plot in Fig. 4.Fig. 43D plot representation of the data in file a12.txt. It is composed of 4,299 3D points.Fig 4 dummy alt text

3D plot representation of the data in file a12.txt. It is composed of 4,299 3D points.

Because there are 21 subfolders, and each has 15 files, the total number of files in the dataset is 315. The point clouds were normalized in translation and centered around the origin of the Cartesian coordinates (0,0,0). They were also normalized in scale to fit inside a sphere of radius one. These transformations did not change shape. Owing to scale normalization, the displayed dimensions were unitless. The horizontal axis represents the X-axis. The vertical axis represents the Y-axis. The Z-axis shows the depth.

In the dataset, each sample (file) is composed of a set of 3D points whose cardinality is variable owing to the acquisition conditions of the depth sensors.

This variability is expected in data captured by RGB-D cameras and depends on physical and geometrical factors.

One factor is the type of sign performed. Some signs require more compact manual configurations, such as closed fist. When fewer surfaces are visible, this corresponds to fewer 3D points acquired by the sensor. In other configurations that include arm extension or separation of the hands, these increase the area detected and the density of the depth cloud.

The second factor is arm posture and hand pose with respect to the sensor. When the hand is not facing perpendicular but is in an oblique position, partially occluded, or with finger occlusions, this generates missing points in the depth acquisition.

In addition, the precision of the sensor decreased with distance. Natural variations of the participant when performing the sign can generate a lack of points in occluded regions, and the number of points is reduced through background segmentation (regions outside the sign of interest) and forearm segmentation to isolate the hand geometry. This variation in the number of points for each point cloud should be considered in the development of feature extraction, classification methods, and inter-subject generalization. One possible strategy is to use a form of normalization that is not affected by the number of points present in each point cloud. For example, if the point cloud is considered as a histogram of frequencies over spherical coordinate sectors, then dividing the frequency in each sector by the number of total points in the cloud results in a discrete probability distribution that adds up to one, independent of the number of points in the cloud.

Another factor is anthropometric differences between the participants. The dataset includes individuals with very different physical characteristics. For example, variations in body size, arm length, and hand size. These differences modify the volume occupied and the surface visible to the sensor, and therefore the number of 3D points that receive each hand and arm.

All 315 point clouds (files) that compose the dataset are complete, free of missing values, and validated by opening and displaying each one.

The described format is easy to read because it is stored in text format, and each point is represented in a row by three float point numbers, which are the (X, Y, Z) coordinates of the point. Each file contains all the points that form a handsign shape, as performed by an individual.

All the points in a file can be loaded into a matrix with as many rows as points and three columns for the (X, Y, Z) coordinates. The point cloud can be analyzed for common tasks such as feature extraction, that is, determining tangent planes or normal vectors at each point for 3D shape analysis.

In addition, this representation is very convenient for computing features, such as moment invariants. There are moment invariants of different transformations, such as 3D translation, scaling, rotation, and affine operations. These invariants allow for the characterization of 3D shapes for similarity and classification [15]. For example, a recommended normalization for users of point clouds is to compute the 3D centroid and then update each 3D point as a vector by subtracting the centroid. This generates a new point cloud, whose new centroid is located at the origin coordinates. In addition, following this procedure, invariance to 3D translation was obtained, which is useful as a first step in shape analysis. Several additional recommended normalizations for the shape analysis of 3D point clouds can be found in Flusser et al [15,16]. The dataset presented in this data article can be used as a benchmark to compare the classification accuracy of sign language datasets for finger spelling. There are American Sign Language (ASL) datasets for finger spelling with 20 classes and an Argentinian dataset for fingerspelling with 16 classes [4], but there is no publicly available 3D depth dataset for MSL finger spelling with 21 classes, as the dataset presented in this data article.

In future work, two datasets will be possible. The one for the static 3D MSL alphabet includes more people and more samples per individual per sign. That would be V.3. for the dataset described in this study. The second possibility is to acquire a dataset for the full 3D MSL alphabet, which includes static and dynamic signs. In this case, V.1 for this type of dataset.

Experimental Design, Materials and Methods

Participants

Fifteen volunteers participated in data acquisition. Their ages varied between six and 34 years, with seven females and eight males. They performed each sign after rehearsing it once because they were not native MSL users. Each participant performed 21 MSL signs. All participants used their right hand only during the sign action.

The exclusion of native signers at the time of the data acquisition was because additional coordination is needed to contact a deaf organization, and an interpreter would be needed to communicate with the native signer to perform the signs. This additional effort could be considered in future versions of the dataset.

The design choice of only one sample per participant per class reduced the time required by participants during data acquisition. However, this decision has implications because the intra-subject variability cannot be quantified for each sign class. In addition, data limitations affect the training of robust machine learning models. This limitation in the dataset can be reduced through data augmentation by applying different mathematical transformations, such as rotations, scaling, symmetry, and deformations.

The participation of a minor (six-year-old) was provided with informed consent from the mother, who acted as a legal tutor. Parental consent was obtained prior to data collection and participation was conducted under supervision. The minor participated voluntarily and was always in the presence of the mother. The collected data were anonymized and used only for academic purposes.

Preprocessing

The MS Kinect V.1 3D sensor acquires the depth shape of all people. For all participants, a manually set depth threshold was used to segment the performing arm from the rest of the body.

The depth threshold used for segmenting the arm from the rest of the body and scene was defined empirically and through a preliminary test in the capture environment. During this phase, several threshold values were tested to identify a depth threshold that could consistently isolate the hand and forearm of the participant without including background information or losing relevant information from the sign.

From these tests, a depth threshold of 0.8 meters from the sensor was established and maintained without modification for all the participants and all sessions during the data acquisition. A fixed depth threshold was defined to guarantee the uniformity of the procedure and to avoid introducing methodological variance between samples.

The selection criteria considered the average distance of the participants from the sensor during the sign performance, necessity to exclude the background in a stable manner, and complete preservation of the hand geometry in different sign configurations.

Regarding the sensitivity of the data acquisition to the selected threshold, it was observed that small variations in this range did not significantly alter the segmented region. This approach allowed for a homogeneous segmentation procedure in the dataset while maintaining similar acquisition conditions for all samples.

To segment the hand from the forearm, a semi-automatic segmentation procedure was implemented following Tao et al. [17]. This algorithm applies palm region approximation, forearm region segmentation, and forearm region removal to isolate the hand.

In our case, because we assume, as in Tao et al. [17], that the hand-arm point cloud is the closest object to the camera, the palm region approximation is computed by determining the 3D centroid from the 3D point cloud. The palm region is segmented into a circular region in the XY plane. Tao et al. did not provide details for the computation of the radius. In our case, we considered the radius to be the distance between the centroid and the farthest point in the X direction with the same Y value as the centroid. Then, the polar histogram was computed as in Tao et al. [17]. The points outside the palm region were clustered. The region with the most points was the forearm, which was removed. For some point clouds, one iteration of the procedure was sufficient. Other point clouds with larger forearm regions require a second iteration. In our case, most point clouds required only one iteration. Only a few cases required two iterations. Whole forearm segmentation is semi-automatic, as the user must see the results of the segmentation to determine whether one iteration is sufficient or another is necessary.

In addition to the preprocessing described above no other post segmentation filtering was applied.

The 3D data points included in the dataset correspond to the results of spatial segmentation. No other post segmentation filtering was applied, such as smoothing, outlier removal, or downsampling.

The decision not to include any type of filtering was to preserve the hand shape geometry in the point clouds, as acquired with the sensor. The noise inherent in the MS Kinect V.1 sensor may affect the distinctions between some class shapes. For instance, class “M” and “N” are very similar and can be differentiated only with fine hand shape distinctions. Class “M” has three extended fingers and class “N” has two extended fingers in almost the same hand configuration (Fig. 6). Other example that requires fine hand shape distinctions to differentiate class shapes, is class “S” and “T.” Both have a close fist, but in the case of class “T,” the thumb goes in the middle of the fist, and the extreme of the thumb appears between the index and middle finger (Fig. 7). We decided to retain the data captured by the sensor and not introduce noise filtering because it could also remove small shape distinctions, as in the cases mentioned in this paragraph.Fig. 63D plot of representative shapes of MSL static alphabet classes G, H, I, L, M and N. Normalization in coordinates and scale

After the segmentation of the hand shape, to provide invariance to the translation of the 3D coordinate system and scale of the corresponding point cloud, while keeping the hand shape and original 3D rotation (pose), we applied the following normalization to each point cloud.

Normalization of coordinates. The normalization consists of computing the centroid of the point cloud (Xc,Yc,Zc)= 1N∑i=1N(Xi,Yi,Zi), where N is the number of points in the point cloud, and (Xi,Yi,Zi) is the ith point in the point cloud, and the new coordinates are computed as (Xi0,Yi0,Zi0)=(Xi,Yi,Zi)−(Xc,Yc,Zc) . The resulting point cloud was centered at the origin (0,0,0).

Normalization in scale. To obtain the invariance to scale for each point cloud, the farthest point from the centroid was searched, and the maximum Euclidean distance, Distmax was computed. The new coordinates (Xis,Yis,Zis)of the point cloud, which is centered at the origin and inside a sphere of radious one, are computed as (Xis,Yis,Zis)=(Xi0,Yi0,Zi0)/Distmax.

The resulting point clouds preserve the original shape and pose, and are invariant to translation and scaling, although the original scale is lost. The new coordinates were unitless.

Additional recommended processing steps

Further normalization is in 3D rotation. Flusser et al. [15,16] provided a useful reference for options.

Once the point clouds are normalized in translation, scale and 3D rotation, one possible route following traditional AI is to develop a method to extract features using "hand crafted" features.

The dataset can then be randomly partitioned and used with the developed method to train and test the cross-validation portions of the dataset. The predicted classes on the test set can be compared with the actual classes to compute a confusion matrix and obtain the classification metrics.

Another possible route using modern AI is to perform data augmentation on the dataset to generate more samples, then design and apply an end-to-end neural network to train directly on the dataset and finally test its performance on the test set.

Limitations

The 3D data were collected indoors under artificial light to reduce variations in luminance.

For each of the 21 MSL static letters, each of the 15 individuals had only one capture per sign. Thus, 315 files were generated. Our dataset is not applicable to studies that require the analysis of intra-individual differences in the sign shape and performance.

Owing to the lack of six dynamic alphabet letter signs, only the 21 static alphabet letters of the MSL were included in this data article and in the dataset.

The use of the MS Kinect V.1 sensor for data acquisition, which in some laboratories has been substituted by more recent sensors with higher resolution and frame rate. This sensor suffers from obsolescence because it is not produced or supported by a manufacturer.

Non-native sign-language users performed the MSL letter signs. Although we took all the care to instruct the participants with visual aids and books on how to correctly perform each sign, since non-native signers may not perform the signs as well as native signers, this may affect the generalizability of real-world sign language recognition.

The dataset only includes right hand gestures.
