Abstract
. 5G promises enhanced performance—not only in bandwidth and capacity, but also latency and security. Its ultra-reliable low-latency configuration targets round-trip times below 1 ms, while optional security controls extend protection across all interfaces, making 5G attractive for mission-critical applications. A key enabler of low latency is the disaggregation of network components, including the RAN, allowing user-plane functions to be deployed nearer to end users. However, this split introduces additional interfaces, whose protection increases latency overhead. In this paper, guided by discussions with a network operator and a 5G manufacturer, we evaluate the latency overhead of enabling optional 5G security controls across internal RAN interfaces and the 5G user plane. To this end, we deploy the first testbed implementing a disaggregated RAN with standardized optional security mechanisms. Our results show that disaggregated RAN deployments retain a latency advantage over monolithic designs, even with security enabled. However, achieving sub-1 ms round-trip times remains challenging, as cryptographic overhead alone can already exceed this target.

1.
Introduction

The fifth generation of mobile networks (5G) introduces a major architectural transition, shifting from hardware-centric, monolithic deployments to software-defined, cloud-native designs
(
3GPP 2023
)
.
This evolution enables 3GPP, for the first time, to extend its focus beyond traditional consumer connectivity and to address industrial and mission-critical sectors that demand ultra-low latency
(
Michaelides et al. 2025a
)
.

In such sectors, the modular and cloud-native architecture of 5G—enabled by the disaggregation of the 5G Core and Radio Access Network into individual network functions—allows latency-critical User Plane components (e.g., the Control Unit-User Plane and User Plane Function) to be deployed closer to end devices, thereby reducing latency
(
Michaelides et al. 2025a
;
Samsung 2019
;
Sajid et al. 2025
)
and enabling 5G to target Round-Trip Times (RTT) as low as
1\text{\,}\mathrm{ms}

(
Gong et al. 2025
)
.

Beyond low latency and high reliability, these critical sectors also demand strong security measures as their importance in societal, economic, and public safety-critical functions makes them a frequent target for powerful attacks
(
Stellios et al. 2018
;
Henze et al. 2013
)
.
Consequently, as 5G is being deployed in these environments—expanding the attack surface through new interfaces and components—strong security controls must be implemented to mitigate resulting threats.

Fortunately, 5G introduces a comprehensive suite of security controls across its architecture, covering nearly every component and interface. Although each component is required to support these mechanisms, the activation of most remains optional, granting network operators flexibility
(
Michaelides et al. 2025a
;
Michaelides et al. 2025b
;
Heijligenberg et al. 2023
;
Zeidler et al. 2024
)
.
As enabling these controls inevitably introduces cryptographic operations that add latency, it remains open whether 5G can still achieve its promised sub-
1\text{\,}\mathrm{ms}
RTT targets while maintaining robust security.

The importance of this issue is highlighted by the extensive prior work examining security controls within the 5G Core, N3, and Uu interfaces
(
Zeidler et al. 2024
;
Michaelides et al. 2025b
;
Heijligenberg et al. 2023
)
.
While these studies provide insights into individual controls, they focus on isolated interfaces without considering the broader implications of Radio Access Network disaggregation, which is critical for low-latency communication
(
Samsung 2019
;
Michaelides et al. 2025a
)
.
Thus, there is a need to evaluate security controls across the entire 5G architecture and their overall impact on system performance.

In this paper, we present the first comprehensive evaluation of optional security controls across the 5G User Plane, with a focus on disaggregated Radio Access Network deployments, crucial for achieving ultra-low latency
(
Michaelides et al. 2025a
;
Samsung 2019
)
.
Our work is guided by discussions with a Mobile Network Operator and a 5G vendor, providing practical insights into the benefits of disaggregated Radio Access Network deployments and the use of optional security controls in real networks, ensuring that our findings have direct practical relevance.
More specifically, our key contributions are:

(1)

Practical insights from an Mobile Network Operator and a 5G vendor on security and performance in disaggregated Radio Access Network deployments, offering guidance for secure low-latency deployments (§
3
).

(2)

The first
open-source
5G testbed supporting all optional internal RAN security controls (§
4
); available at
(
5GI 2025
)
.

(3)

Evaluation of the impact of security on latency across RAN interfaces for both control and user planes (§
5
), identifying IPsec as the most latency-efficient option, with configurations adding less than
60\text{\,}\mathrm{\SIUnitSymbolMicro s}
of overhead.

(4)

End-to-end User Plane latency analysis from User Equipment to User Plane Function in monolithic and disaggregated setups (§

), showing that security alone already pushes RTTs beyond
1\text{\,}\mathrm{ms}
.

2.
5G Networks and Security Controls

From a high-level view, 5G follows the same basic structure as earlier mobile networks, consisting of the User Equipment, the 5G Core, and the Radio Access Network (cf. Fig.
1
).
It also maintains a split between the Control Plane, which handles signaling such as session management and mobility, and the User Plane (UP), which handles user-data forwarding
(
Michaelides et al. 2025b
)
.
This section outlines the 5G architecture (§
2.1
), the main interfaces and their associated security controls (§
2.2
), and the optional security mechanisms examined in related work (§
2.3
).

2.1.
Architectural Components

The User Equipment is the end device that accesses network services provided by the 5G Core using authentication credentials
(
3GPP 2024a
)
.
The 5G Core consists of interconnected Network Functions responsible for control and user-plane operations: Control Plane functions such as the Authentication and Mobility Function and Session Mangement Function manage authentication, mobility, and session control, while the User Plane Function on the User Plane handles routing of user data
(
3GPP 2024a
)
.
The Radio Access Network mediates between the User Equipment and the 5G Core by providing the wireless connectivity, and can be deployed either monolithically or disaggregated
(
3GPP 2024d
)
.

In monolithic Radio Access Network deployments, the Baseband Unit implements the full protocol stack except radio transmission, handled by the Radio Unit.
In a disaggregated deployment, the Baseband Unit is split into Control Unit and Distributed Unit
(
3GPP 2024d
)
.
The Distributed Unit handles real-time lower-layer functions, including scheduling, signal processing, modulation, coding, and beamforming, while the Control Unit manages higher-layer functions such as resource control, security, intra-Radio Access Network mobility, and Distributed Unit management.
The Control Unit is split into Control Unit-Control Plane and Control Unit-User Plane (CU-UP), reflecting control- and user-plane separation, allowing independent scaling, optimization, and placement of each plane.
Placing User Plane functions and the Distributed Unit on the edge cloud (
blue
in Fig.
1
) near the User Equipment is crucial for low-latency communication (cf. §
3
), while keeping Control Plane centralized (
red
in Fig.
1
) enables better control.

2.2.
5G Interfaces and Security

Following the control–user plane separation, we examine the 5G interfaces and their associated security controls.

Control Plane:

Control Plane data is exchanged between network nodes to maintain and support 5G operations.
This includes signaling between the User Equipment and Authentication and Mobility Function over the N1 interface for authentication and mobility management, as well as signaling over the Uu interface between the User Equipment and the Radio Access Network for requesting and allocating radio resources.
These messages are mandatorily integrity-protected using the NIA algorithms based on SNOW, AES, or ZUC
(
Heijligenberg et al. 2023
;
3GPP 2024c
)
, and may optionally be encrypted using the corresponding NEA schemes.
Within the Radio Access Network, control signaling occurs over the F1-C and E1 interfaces.
These interfaces support operations such as intra-Radio Access Network handovers, the exchange of Control Plane data to and from the User Equipments, radio resource management, radio resource control forwarding, and User Plane control commands.
Control signaling between the Radio Access Network and the 5G Core takes place over the N2 interface, which carries handover messages, mobility management information, and session-related control data between the Control Unit-Control Plane and the Authentication and Mobility Function.
All three interfaces are optionally protected using IPsec or DTLS
(
3GPP 2024c
, §9.8.2, §9.8.3, §9.2)
.
Within the 5G Core, Control Plane data is exchanged between Network Functions for tasks such as session management and retrieving authentication credentials.
Data over the Service Based Interfaces can be optionally secured with TLS or IPsec
(
3GPP 2024c
, §13.1.0)
, and with IPsec over the N4 interface
(
3GPP 2024c
, §9.9)
.
While most security controls are optional
"because they can be replaced with physical security"

(
Michaelides et al. 2025b
)
, disaggregated Radio Access Network deployments—where physical security is infeasible—often rely on these controls (cf. §
3
).
Given that Control Plane security is critical for the network operation, we evaluate how security controls within the Radio Access Network affect crucial Control Plane operations of the 5G system (§
5
).

User Plane:

The User Plane is responsible for carrying the user data from the User Equipment to the User Plane Function.
Between the User Equipment and the Radio Access Network (Control Unit-User Plane), this data is optionally secured using the NIA/NEA schemes
(
3GPP 2024c
, §5.2)
.
While these controls also cover data over the F1-U interface between the Control Unit-User Plane and Distributed Unit, security on this interface is crucial, as F1-U not only transports User Plane data but also carries control traffic used by the Distributed Unit to regulate downlink data and prevent buffer overflows
(
3GPP 2024e
, §5.3)
.
IPsec is defined as an optional security control for this interface. The same applies to the N3 interface, which carries User Plane data between the Control Unit-User Plane and the User Plane Function
(
3GPP 2024c
, §9.3)
.
Security over User Plane interfaces adds latency and may affect 5G’s low-latency capabilities.
In this paper, we first assess the impact of F1-U security in isolation (§
5
), as it is the only User Plane interface not studied in prior work (cf. §
2.3
), before evaluating all User Plane security controls collectively (§
6
).

The special case of the Fronthaul (FH) Interface:

The FH carries Control Plane and User Plane data and allows the Distributed Unit to manage Radio Units (e.g., synchronization).
Defined by the Common Public Radio Interface consortium rather than 3GPP, proprietary CPRI links up to LTE transmitted analog signals, with security only feasible at the hardware level.
In 5G, enhanced CPRI gradually replaces CPRI with a packet-based interface that enables partial distribution of Distributed Unit functions to the Radio Unit; however, implementing security controls (e.g., MACsec) is only recommended, not mandated, by the specification.
As the FH lacks standardized security controls and has diverse vendor-specific implementations, we exclude it from our evaluation, though we reference related work.

2.3.
Related Work

The studies summarized in Tab.
1
highlight the current state of research on optional security controls in 5G systems and motivate our work.
Heijligenberg et al.
(
Heijligenberg et al. 2023
)
were the first to examine the impact of optional security controls, evaluating NIA schemes on the User Plane in terms of bandwidth and latency and showing a noticeable yet comparable impact across all schemes.
Zeidler et al.
(
Zeidler et al. 2024
)
analyzed TLS as the primary security mechanism over the Service Based Interfaces, reporting minimal performance degradation in an operational 5G system but significant delays during initial security establishment.
Similarly, in prior work
(
Michaelides et al. 2025b
)
, we investigated IPsec within the 5G Core and across the N3 interface, demonstrating that IPsec can outperform TLS due to its ability to pre-establish security associations, while introducing only minimal latency on N3.
Lastly, Dik et al.
(
Dik and Berger [n. d.]
)
examined MACsec (although not standardized) on the FH, showing a negligible impact on latency.
Overall, these studies reveal the absence of an architecture-wide evaluation of the User Plane and a lack of consideration for disaggregated Radio Access Network deployments—vital for achieving low latencies—thereby underscoring the gap filled by our contributions.

3.
Insights on Disaggregated RANs

To guide our research on disaggregated Radio Access Network architectures and optional security controls in real-world 5G deployments, we consulted a major 5G equipment manufacturer and a European Mobile Network Operator (who requested to not be named).
These discussions highlight the practical benefits of such deployments (§
3.1
) and the use of optional security controls (§
3.2
), underscoring the relevance of this work.

3.1.
Practical Benefits of Disaggregated RANs

During our discussions with the Mobile Network Operator, we learned that most current Radio Access Networks deployments are monolithic due to legacy infrastructure.
However, they emphasized that new Radio Access Network deployments are disaggregated and virtualized to improve cost efficiency, availability, and scalability.
As they explained, it is more convenient to dynamically deploy instances of the Distributed Unit or Control Unit rather than the entire stack, significantly reducing costs.
These deployments also allow the Mobile Network Operator to quickly identify and isolate faulty instances and redeploy replacements, minimizing downtime—a top operational priority
(
Michaelides et al. 2025b
)
.
Finally, the Mobile Network Operator, which is currently in the process of deploying a low-latency network slice, pointed out that internal measurements indicate that without physically reducing the distance between User Plane components and end-users, achieving low-latencies is infeasible.

3.2.
Security in Real-World 5G Networks

The equipment manufacturer we contacted is also responsible for configuring networks according to the requirements of clients, which include both MNOs and private companies.
The manufacturer reported an increasing demand for disaggregated and virtualized Radio Access Networks, which aligns with findings from Dell’Oro (and Nokia)
(
Nokia 2024
)
, projecting that by 2028, 20% of Radio Access Networks will be disaggregated and virtualized.
When asked about security, the manufacturer noted that optional security controls are typically not used in traditional 5G deployments due to bandwidth considerations and potential performance bottlenecks especially on the User Plane, which bears more traffic.
In contrast, optional security mechanisms are almost always employed in disaggregated Radio Access Network deployments, as these components are often geographically distributed across cloud infrastructure where physical security is not feasible (cf. §
2.2
).

Our discussions highlight the benefits of disaggregated Radio Access Network deployments, their role in low latency, and the use of optional security controls in real-world 5G networks, demonstrating the relevance and real-world applicability of evaluating security-induced latency on 5G RAN interfaces and User Plane communication.

4.
Deploying a Disaggregated-RAN 5G Testbed

To lay the foundation for such evaluations, we first identify optional security controls applied to the RAN interfaces (§
4.1
), before deploying them by extending an existing state-of-the-art testbed (§
4.2
).

4.1.
Identified Optional Security Controls

To identify optional security controls, we examine the relevant 3GPP specifications and determine the mandatory-to-support configurations, as these ensure a degree of compatibility between devices from different manufacturers.
For IPsec, we leverage the same controls as those we discovered in our previous work on evaluating tunneling protocols over the N3 and the SBIs
(
Michaelides et al. 2025b
)
.
These comprise six different algorithm combinations, which can be used with either certificates or pre-shared keys.
For DTLS, we extract three configurations from
(
3GPP 2024b
, §6.2)
.
All three configurations employ the same Authenticated Encryption with Associated Data algorithm for encryption and integrity protection (AES-GCM with 128-bit keys) but differ in their key exchange and authentication mechanisms.
Interestingly, while standard TLS configurations mandate support for version 1.3, DTLS only requires version 1.2.

During our experiments, the Radio Access Network components establish their security (i.e., authentication and key exchange) once, during the discovery phase at deployment.
Thus, our measurements focus on the overhead of encryption and integrity protection, evaluating six IPsec ESP configurations and one DTLS configuration (cf. Fig.
2
).
This mirrors real-world 5G systems, where the network runs continuously and security associations are thus rarely re-established.

Figure 2.
Securing internal-RAN interfaces using IPsec adds only minimal latency overhead regardless of the configuration, making it suitable to support low-latencies.

4.2.
Testbed and Experimental Setup

To deploy and study the identified security protocols, we extend our previously presented open-source testbed
(
Michaelides et al. 2025b
)
, which implements IPsec over the N3 interface using UERANSIM and Open5GS.
As UERANSIM lacks Radio Access Network disaggregation support and a full 5G protocol stack, we replace it with Open Air Interface (OAI)
(
group 2025
)
, a widely adopted in academia and industry.
This upgrade not only supports a fully disaggregated Radio Access Network, but also allows seamless integration with software-defined radios, enabling both simulated and over-the-air deployments.
Each network function—including the 5G Core, disaggregated Radio Access Network functions, and the User Equipment—runs as an independent Docker container, interconnected via dedicated subnetworks that emulate 3GPP interfaces.
The F1-C, F1-U, and E1 links are represented as separate Docker bridges, allowing their precise monitoring.

For consistency with the original setup, we deploy IPsec over the F1-C, F1-U, and E1 interfaces using strongSwan, establishing IKEv2/ESP tunnels automatically at container startup.
DTLS is implemented over the F1-C and E1 interfaces using the lightweight socat utility, which provides bidirectional DTLS tunnels between RAN components.
Our setup also allows dynamic switching between security configurations and authentication methods via environment variables, making it easily adaptable.
The complete testbed runs on a physical host with Ubuntu 22.04.5 LTS on an AMD Ryzen 7 Pro 6850U (8 cores, 16 threads) with an integrated Rembrandt GPU, 32 GB DDR5 RAM, and Linux kernel 6.8.0-60-generic.
The CPU supports AES-NI for AES acceleration, which we leverage to reflect realistic performance in modern 5G deployments.

5.
Impact of Security on Internal-RAN Interfaces

To assess the impact of security on Radio Access Network interfaces, we use our testbed to perform reproducible Control Plane and User Plane tests, with and without security to quantify the overhead.
We first outline the methodology we follow for each plane (§
5.1
) before presenting our results (§
5.2
).

5.1.
Methodology

We use different methodologies for the two planes as we can directly generate traffic on the User Plane, whereas we cannot do so on the Control Plane.

User Plane:
To assess the latency impact on the User Plane over the F1-U interface, we generate user data.
We employ the
ping
tool, which uses ICMP messages to measure the RTT between two hosts, following the methodology of related work
(
Heijligenberg et al. 2023
;
Michaelides et al. 2025b
)
.
From within the User Equipment container, we ping the User Plane Function container, ensuring that the traffic remains confined within the same physical host to minimize external factors that may affect latency.
We employ 1024-byte payloads to amplify the effect of cryptographic operations and repeat the experiment 20,000 times for statistical confidence.

Control Plane:
In contrast to the User Plane, we cannot directly generate traffic on the Control Plane interface, as it is triggered by control procedures such as authentication and handovers.
Therefore, we use
UE registration
, one of the most common Control Plane operations
(
Zeidler et al. 2024
)
, to trigger Control Plane activity.
To this end, we deploy a User Equipment that automatically sends a registration request.
While we do not monitor the registration data itself, we capture the Control Plane sub-procedures triggered during authentication to establish connectivity between the User Equipment and the User Plane Function.
Over the F1-C, we monitor the User Equipment Context Setup procedure, which establishes the User Equipment context and provides the Distributed Unit with the information needed to manage the User Equipment.
We measure the time from the User Equipment Context Setup request sent by the Control Unit-Control Plane until the corresponding response, which indicates that the Distributed Unit is ready to handle the User Equipment.
For the E1 interface, we monitor the E1 Bearer Context Setup procedure, responsible for allocating resources and establishing GTP tunnels between the User Equipment and the User Plane Function over Control Unit-User Plane.
We measure the time between the Bearer Context Setup request from the Control Unit-Control Plane to the Control Unit-User Plane and the corresponding response, confirming the successful establishment of GTP-U tunnels for the F1-U and N3 interfaces.
To ensure statistical confidence, we repeat the experiment 1,000 times.

5.2.
Results

Our results (cf. Fig.
2
) are shown as 99% confidence intervals of the average latency across all repetitions, providing statistical confidence in the true mean.
Across all interfaces, the fastest IPsec configuration adds only minimal overhead on the order of tenths of microseconds, whereas DTLS consistently incurs higher latency.

User Plane:

Over the F1-U interface, where only IPsec is specified, all IPsec configurations combined add on average
\sim
120\text{\,}\mathrm{\SIUnitSymbolMicro s}
RTT (
\sim
60\text{\,}\mathrm{\SIUnitSymbolMicro s}
one-way), with minimal variation across cipher suites.
Differences between cipher suites are indistinguishable, due to overlapping confidence intervals.
These results closely align with related work on the User Plane (over N3), where the same IPsec algorithms were shown to add on average
55\text{\,}\mathrm{\SIUnitSymbolMicro s}
, also with overlapping confidence intervals
(
Michaelides et al. 2025b
)
.
This indicates that IPsec is a strong candidate for secure, low-latency User Plane data transmission across the 5G architecture, as the added latency is well below the
1\text{\,}\mathrm{ms}
threshold.

Control Plane:

On the Control Plane, specifically the F1-C interface, all IPsec configurations add on average
\sim
120\text{\,}\mathrm{\SIUnitSymbolMicro s}
to UE context setup, compared to
\sim
430\text{\,}\mathrm{\SIUnitSymbolMicro s}
for DTLS.
The fastest IPsec configuration (AES256-HMAC) adds only
\sim
40\text{\,}\mathrm{\SIUnitSymbolMicro s}
, making it nearly indistinguishable from unprotected traffic.
Over the E1 interface, IPsec configurations introduce on average
\sim
80\text{\,}\mathrm{\SIUnitSymbolMicro s}
of overhead, whereas DTLS adds
\sim
300\text{\,}\mathrm{\SIUnitSymbolMicro s}
.
However, IPsec with AES128-GCM performs best, adding only
\sim
10\text{\,}\mathrm{\SIUnitSymbolMicro s}
.
From a practical perspective, both protocols can be used for procedures that are not latency-critical—such as UE authentication—without noticeable impact.
For latency-critical operations, such as intra-Radio Access Network handovers, IPsec remains the preferred option due to its consistently lower overhead.

6.
User Plane-Wide Evaluation

Having deployed and evaluated security within the Radio Access Network, we now assess its overall impact on latency when enabled across the entire 5G User Plane, from the User Equipment to the User Plane Function.
We first describe our methodology (§
6.1
), present results with 99% confidence intervals (§
6.2
), and report tests conducted in a realistic 5G deployment (§
6.3
).

6.1.
Methodology

To evaluate the impact across the 5G User Plane, we follow a similar approach as for the F1-U measurements. We perform 20,000 ping measurements between the User Equipment and the User Plane Function using 1024-byte packets.
We assess latency overhead by comparing RTTs of a baseline without security to a deployment with security enabled on all User Plane links.
We consider both a monolithic Radio Access Network, securing Uu and N3, and a disaggregated Radio Access Network, additionally securing F1-U.

To secure the interfaces, we have two options: either enable only integrity protection or enable both integrity and encryption. Encryption must always be integrity-protected for some interfaces (e.g., N3
(
Michaelides et al. 2025b
)
) and, by itself, provides no protection against tampering attacks
(
Rupprecht et al. 2019
)
.
However, we observed that enabling only integrity protection provides no measurable advantage over enabling both.
Therefore, we choose to enable both encryption and integrity protection on all interfaces for enhanced security.
Over N3 and F1-U, we use IPsec with AES-GCM128, which provides both integrity and encryption, with performance comparable to schemes that only provide integrity protection.
The same applies to the Uu interface in which we measure no difference when enabling NIA and NEA simultaneously compared to using only NIA.
There, we utilize NIA&NEA option 2 based on AES, as it has been shown to outperform the other two schemes in runtime and throughput
(
Heijligenberg et al. 2023
)
.

6.2.
Results

By examining the 99% confidence intervals in Fig.
3
, we observe that disaggregated Radio Access Network deployments achieve better baseline performance than monolithic ones (
11\text{\,}\mathrm{ms}
vs.
12\text{\,}\mathrm{ms}
), due to the independent handling of User Plane data—even without being physically closer to the end device.
This confirms that disaggregated architectures are inherently well-suited for low-latency communication.
Even with security enabled, disaggregated Radio Access Network maintains its performance advantage despite the additional interfaces to protect.
Cryptographic overhead exceeds
1\text{\,}\mathrm{ms}
in both cases—approximately
1\text{\,}\mathrm{ms}
for the monolithic setup and
1.3\text{\,}\mathrm{ms}
for the disaggregated deployment.
Given minimal CPU load and comparable memory usage, we attribute the measured overhead primarily to cryptographic operations.
While disaggregated Radio Access Network remains faster overall, the high cost of cryptographic operations shows that achieving sub-
1\text{\,}\mathrm{ms}
latency is extremely challenging for both Radio Access Network deployments, highlighting the combined effect of multiple optional security controls as a key limiting factor for ultra-low-latency applications.

6.3.
Validation in a Realistic 5G Deployment

To ensure reproducibility in an isolated setup, our main results are obtained using a simulated radio and User Equipment, where both disaggregated and monolithic Radio Access Network deployments are equally close to the User Equipment, minimizing the benefits of disaggregation.
To validate these results in realistic 5G deployments, we repeat experiments using a User Equipment with a MediaTek Dimensity 700 baseband, a sysmocom ISIM-SJA5 SIM card, and a USRP B210, considering two scenarios differing in User Plane placement.
In the disaggregated deployment, the User Plane Function and Control Unit-User Plane are colocated with the Distributed Unit on one host, placing User Plane functions closer to the User Equipment, while the Control Plane resides on a separate host connected via a network switch.
In the centralized deployment, the Distributed Unit remains local, while the User Plane components are colocated with the Control Plane on a second host, introducing “distance” from the User Equipment, resembling a monolithic setup.
The disaggregated scenario achieves
2.5\text{\,}\mathrm{ms}
and
2.1\text{\,}\mathrm{ms}
lower latency without and with security enabled, respectively, highlighting the benefits of disaggregation for low-latency communication and validating the trends observed in our main experiments.

7.
IPsec Configuration Benchmarking

While we focus on the latency of security controls, throughput is of equal concern to Mobile Network Operators, especially on the User Plane (cf. §
3.2
).
Related work has studied NIA schemes, showing linear scaling with input size and identifying NIA2 as most efficient in throughput and runtime

8.
Discussion

Finally, we discuss the broader implications of our results, including their transferability to real-world 5G systems, the underlying the root cause of high latencies, and potential avenues for improvement.

Transferability of Results:

Even in our small-scale 5G network, latency already exceeds
1\text{\,}\mathrm{ms}
, and overheads are likely to be higher in larger, real-world deployments with increased load.
Our measurements show overheads in the order of tenths of microseconds—extremely fast—so further gains from more powerful machines would be minimal.
Additional security controls, such as those over the FH or other non-parallelizable schemes (e.g., NIA1/NEA1 or AES-CBC_HMAC), would further increase latency.
Lastly, in our experiments, we ping the User Plane Function, but in real 5G networks, where communication might occur between two User Equipments, cryptographic actions would double, effectively also doubling the overhead.
As such, our conclusion that achieving sub-1 ms RTTs is challenging is broadly transferable to real-world 5G deployments.

NIA/NEA as the Limiting Factor:

Although IPsec achieves very low latencies using fast, parallelizable schemes such as AES-GCM, the overall end-to-end latency remains high.
We attribute this high latency to the 5G NIA/NEA algorithms, which must be executed sequentially in a MAC-then-encrypt fashion
(
Heijligenberg et al. 2023
)
, inherently introducing additional latency.
While NEA2 is based on AES-CTR, which is parallelizable, NIA2 relies on CMAC mode, which is sequential, introducing data dependencies, further increasing latency.

Reducing Latency:

Latency can be reduced by minimizing cryptographic operations on User Plane data. Approaches include security-aware traffic separation (e.g., avoiding re-encryption of User Plane data over F1-U) or true end-to-end security between User Equipment and User Plane Function. Lastly, using Authenticated Encryption with Associated Data algorithms (e.g., AES-GCM or ChaCha20
-
Poly1305) in NIA/NEA schemes can further lower latency.

9.
Conclusion

With this work, we underscore the importance of RAN disaggregation to meet low latencies in ultra-low-latency scenarios such as industrial networks.
Guided by discussion with a real-world Mobile Network Operator and a Radio Access Network manufacturer, using a disaggregated Radio Access Network 5G setup, we show that the security impact on its interfaces can be kept to a minimum with IPsec, and—despite additional interfaces—it still outperforms its monolithic counterpart in an end-to-end User Plane evaluation.
However, our results also reveal that achieving sub-millisecond RTTs remains difficult, as the cumulative cryptographic overhead already exceeds this threshold, even in a small-scale network.
