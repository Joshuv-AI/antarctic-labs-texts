RTLSquad: Multi-Agent Based Interpretable RTL Design
1 st Wang Bowei, 2 nd Qi Xiong, 3 rd Zeqing Xiang, 4 th Lei Wang, 5 th Renzhi Chen

Abstract
Optimizing Register-Transfer Level (RTL) code is crucial for improving hardware PPA performance. Large Language Models (LLMs) offer new approaches for automatic RTL code generation and optimization. However, existing methods often lack decision interpretability (sufficient, understandable justification for decisions), making it difficult for hardware engineers to trust the generated results, thus preventing these methods from being integrated into the design process. To address this, we propose RTLSquad, a novel LLM-Based Multi-Agent system for interpretable RTL code generation. RTLSquad divides the design process into exploration, implementation, and verification & evaluation stages managed by specialized agent squads, generating optimized RTL code through inter-agent collaboration, and providing decision interpretability through the communication process. Experiments show that RTLSquad excels in generating functionally correct RTL code and optimizing PPA performance, while also having the capability to provide decision paths, demonstrating the practical value of our system.

Register-transfer level (RTL) design fundamentally impacts the power, performance, and area (PPA) of hardware, highlighting the importance of optimizing RTL code. Recent research has introduced large language model (LLM) techniques for automated RTL code generation, either by fine-tuning to produce high-quality RTL code

Multi-stage RTL code generation process requires decision-making ability (what design to select, how to implement the design, etc.). Existing work leverages traditional heuristic algorithms to guide LLMs in making decisions, such as Monte Carlo Tree Search algorithm
[
yaoRTLRewriterMethodologiesLarge2024
,
delorenzoMakeEveryMove2024
,
LLMCodeGen
]
. These methods can provide
result interpretability
by providing generated code after each decision, but they are limited in providing
decision interpretability

[

]
, the ability to clearly explain the rationale behind each decision. This limitation arises from the inherent randomness and opaque nature of heuristic methods. The lack of decision interpretability leads to: 1) Hardware engineers may struggle to trust the generated results, therefore unlikely to integrate these methods into current design process
[
mohammadkhani2023systematicliteraturereviewexplainable
]
; 2) Engineers being unable to discern the quality of results during the generation process, thus lacking sufficient reason to accept the final result over others; 3) Engineers also being unable to learn from the decision-making process, therefore possible to adopt an erroneous design found to be faulty in the past again.

The LLM-based multi-agent (LLM-MA) system is an innovative method for providing decision interpretability. LLM-MA system consists of multiple LLM agents with different role settings, solve tasks by simulating human collaboration
[
chanChatEvalBetterLLMbased2023
,
li2024improvingmultiagentdebatesparse
,
smit2024goingmadlookmultiagent
]
. This setup demonstrates greater problem-solving capabilities compared to a single LLM instance
[
qian2024chatdevcommunicativeagentssoftware
,
liangEncouragingDivergentThinking2023
]
. A key feature of the system is that agents communicate and negotiate decisions using natural language, making the decision-making process inherently transparent and comprehensible to users, thereby offers significant advantages in providing decision interpretability.

To fully leverage the advantages of the LLM-MA system in decision interpretability for hardware design, we propose
RTLSquad
, a novel LLM-MA system dedicated to RTL code generation and optimization. RTLSquad operates through a multi-stage process, as shown in Figure
1
:
exploration stage
, exploring various design options to optimize PPA;
implementation stage
, generating correct RTL code according to specifications and requirements;
verification & evaluation stage
, analyzing EDA tool reports and identifying trends in data changes. Each stage is driven by a squad composed of multiple specialized LLM agents, where the communication process within the squad can be regarded as an interpretation of each design decision step, thereby providing decision interpretability for hardware engineers. Through iterative optimization, RTLSquad can progressively explore and implement various designs based on tool feedback, ultimately producing RTL code that is both correct and well-optimized.

Experimental results across various designs demonstrate that RTLSquad’s iterative optimization enhances backbone model’s ability to generate correct RTL code, with Pass@1 performance improving by 7.2% and matching or exceeding the PPA of the reference design in most cases (73.3%). The decision paths are formatted into well-structured documents as outputs, providing comprehensive explanations for each decision in each stage, effectively addressing the disadvantages caused by insufficient decision interpretability. Our contributions are summarized as follows:

•

We propose RTLSquad, an RTL code generation and optimization framework dedicated to providing reliable and understandable hardware design.

•

We have developed various interaction mechanisms to enable multiple agents to effectively collaborate on generating RTL code.

•

We are the first to be able to generate RTL code while providing decision paths, thereby possessing greater practical practical value.

III-A

Overview

Figure
1
illustrates the workflow of RTLSquad. Consistent with the standard RTL design process, RTLSquad accepts design specifications, testbench files, and optional initial code as inputs, and outputs optimized code and comprehensive decision path documentation. Depending on whether the functional verification is passed, the iterative process of RTLSquad is divided into the
verification-fix loop (inner loop)
and the
exploration-implementation loop (outer loop)
. If the current version of the RTL code fails the functional verification, it enters the inner loop, switching between the verification and implementation stages to obtain error reports and correct errors in the code; if verification is successful, RTLSquad enters the outer loop, switching between the exploration, implementation, and verification stages to explore and implement new design methods.

III-B

Implementation Stage

Fig. 2:
The implementation stage of RTLSquad.

As shown in Figure
2
, the implementation stage is used to implement the exploration plan (see Section
III-D
) or to fix errors discovered during the verification stage. The implementation squad
\mathcal{S}_{Impl}
consists of a
programmer
and a
reviewer
. A checklist is maintained during the operation, with each item representing a task to be implemented or fixed. The programmer first summarizes the incomplete tasks in the checklist and the reviewer’s feedback, then plans the code generation steps, and finally generates a new version of the code. The reviewer is responsible for reviewing the code, providing feedback on potential errors to the programmer, and overseeing whether the code completes the tasks in the checklist. The implementation stage will only conclude and proceed to the verification stage when the reviewer marks all tasks as completed. The multi-round feedback and correction process based on review provides better RTL code generation capabilities (see Section
).

III-C

Verification & Evaluation Stage

Fig. 3:
The Verification & Evaluation stage of RTLSquad.

As shown in Figure
3
, the verification & evaluation stage is used to perform functional simulation and logic synthesis on the RTL code provided by the implementation stage, observe and analyze the reports, and evaluate the design. The squad
\mathcal{S}_{Veri}
in the verification stage consists of an
observer
and an
analyst
. The observer is responsible for extracting important information such as compilation errors, verification failures, and abnormal performance indicators from the reports and conveying it to the analyst. The analyst analyzes the statistical characteristics of the indicators based on the current and past analysis records of the current code.

The analyst will give a rating score
r^{(k)}\in[1,5]
on the exploration plan, representing the effectiveness of the plan in optimizing PPA performance, with a higher score indicating greater effectiveness. The rating results will be used to adjust the exploration points
p^{(k+1)}
for the next round, guiding the agent to dynamically adjust the decision-making direction based on past performance, calculated as:

\displaystyle\hat{p}^{(k)}=\left(\alpha-\beta r\right)\cdot p^{(k)}

(1)

\displaystyle p^{(k+1)}=\eta\hat{p}^{(k)}+(1-\eta)p^{(k)}

(2)

where
\alpha,\beta
are the mapping factors from scores to scaling coefficients, typically set as
\alpha=2.375,\beta=0.375
,
\eta
is the smoothing factor, typically set as
\eta=0.4
. The above calculation results in an inverse relationship between the scores and the number of exploration points for the next round, thereby encouraging progressive optimization or break away from the current design.

The analyst will determine if the current code has reached its optimal state. If further improvements are possible, they will transition to the exploration stage to attempt other designs. If the performance metrics of the code show a flat or declining trend, new exploration actions may not bring performance improvements. The analyst will choose to terminate the iteration, selecting the version with the overall best performance from all historical code versions as the output. Subsequently, the user can decide whether to accept this version of the RTL code or continue optimizing.

III-D

Exploration Stage

Fig. 4:
The exploration stage of RTLSquad.

As shown in Figure
4
, the exploration stage is used to explore different designs, forming a set of code design decisions that can optimize current code in terms of PPA. The exploration stage includes a squad
\mathcal{S}_{expl}
composed of
experts in optimizing power, performance, and area
, where three agents will engage in a debate. The agents communicate through a shared message pool
[
chanChatEvalBetterLLMbased2023
]
. The three agents take turns speaking, and the order of speaking in each round will be randomly arranged to ensure fairness.

During the debate, an exploration plan consisting of exploration actions (code design decisions to implement in the implementation stage) is maintained. First, agents will
communicate
with each other, discussing current exploration plan. Then, agents will propose
commits
, including adding new actions or modifying/deleting existing actions. Finally, agents will
review
the commits, judging their acceptability based on their own stance. Commits that receive a majority vote will be applied to the exploration plan. When all agents have not proposed new commits and the exploration plan is acceptable (see below), the exploration stage will end, transitioning to the implementation stage.

Exploration actions are restricted to exploration (
expl
) and optimization (
opt
), representing radical or incremental modifications to the existing design. The number and type of actions are limited by the exploration points
p^{(k)}
, where
expl
actions consume 2 points and
opt
actions consume 1 point. Exploration points can heuristically guide the agent to dynamically adjust the aggressiveness of exploration (proposing more exploration or optimization actions) based on past performance, while not imposing excessive constraints to ensure flexibility. The available points for each round are provided by the verification stage (detailed in Section
III-C
).
