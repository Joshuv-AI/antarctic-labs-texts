APEX–SWE
Abhi Kottamasu, Akul Datta, Aakash Barthwal, Ajay Arun, Chirag Mahapatra, Adarsh Hiremath, Brendan Foody, Bertie Vidgen

Abstract
We introduce the AI Productivity Index for Software Engineering (APEX–SWE), a benchmark for assessing whether frontier AI models can execute economically valuable software engineering work. Unlike existing evaluations that focus on narrow, well-defined tasks, APEX–SWE assesses two novel task types that reflect real-world software engineering: (1) Integration tasks ( n = 100 n=100 ), which require constructing end-to-end systems across heterogeneous cloud primitives, business applications, and infrastructure-as-code services, and (2) Observability tasks ( n = 100 n=100 ), which require debugging production failures using telemetry signals such as logs and dashboards, as well as unstructured context. We evaluated eight frontier models for the APEX–SWE leaderboard. Gemini 3 Pro (Thinking=High) performs best, with a Pass@1 score of 25 % 25\% . Our analysis shows that strong performance is primarily driven by epistemic reasoning, defined as the ability to distinguish between assumptions and verified facts, combined with agency to resolve uncertainty prior to acting. We open-source the APEX–SWE evaluation harness and a dev set ( n = 50 n=50 ).

AI coding models and assistants have been widely adopted for professional software engineering. Recent industry reports indicate that over
90\%

APEX–SWE Integration
(
n=100
) evaluates a model’s ability to orchestrate end-to-end workflows across heterogeneous services. Models are required to write application code, configure infrastructure, and deploy functioning services. Tasks reflect realistic greenfield engineering workflows, including implementing idempotent payment pipelines, configuring serverless event-driven architectures, and synchronizing data between CRM and ticketing systems. The test stack includes cloud primitives (AWS LocalStack: S3, Lambda, DynamoDB, Kinesis) and production-grade business applications (EspoCRM, Medusa, Zammad, Plane).

APEX–SWE Observability
(
n=100
) evaluates a model’s ability to diagnose and remediate real-world production failures. Unlike conventional bug-fix benchmarks, models are not provided with failing unit tests. Instead, they must interrogate production logs (via Grafana/Loki), correlate evidence from developer chat discussions, and trace root causes through the codebase before implementing a fix that resolves the issue without introducing regressions. Each task includes a real GitHub issue from widely adopted programming languages, including Go, TypeScript, Python, Rust, and Java.

Dataset Overview

The production process for Integration and Observability tasks, as well as our grading process, is shown in Figure
3
.

2.1
Integration Tasks Data

Task Environment

All Integration tasks include Plane, as well as six other services: LocalStack (
56\%
), which emulates AWS primitives such as S3, Lambda, DynamoDB, and Kinesis. Business applications include EspoCRM (
35\%
), MailHog (
33\%
) for SMTP testing, Mattermost (
32\%
), Medusa (
31\%
) for e-commerce, and Zammad (
26\%
). Tasks also include an in-memory PostgreSQL database.

Task Sourcing

Tasks were created by software engineers with 3+ years of experience. Each case underwent a three-stage validation process. First, a check to verify that task prompts align with the source documents provided to the model. Second, test validation to ensure that the test suite faithfully evaluates the request without being susceptible to reward hacking. Third, create a gold standard output, checking that the human-authored solution passes all tests with a 100% score.

Authentication & Security

Tasks have authentication schemes to test models’ ability to handle real-world credential management, including Basic Auth for EspoCRM and Zammad, JWT tokens for Medusa, IAM policies and STS credentials for LocalStack, API keys for various webhooks, and PostgreSQL connection strings. Models must read credentials from environment variables rather than hardcoding values, enforcing production-grade security practices.

2.2
Observability Tasks Data

Task Environment

Each task deploys a containerized environment orchestrating five services: a client workspace, Loki and Promtail for log aggregation, Grafana for visualization, and Plane/Mattermost for ticket and chat context. Engineers scripted synthetic logs (500–1,000 lines of normal operation mixed with 10–20 lines of bug symptoms) and chat history to replicate a production failure. The model is provided with a summary of the user issue, an
interface.md
file describing relevant repository functions, and specifications for available Model Context Protocol (MCP)
1
tools. Chat data is pulled from public developer discussions about the repo, including GitHub Discussions and Gitter, and GitHub issue data are taken directly from the repo. Observability tasks additionally include several key files:
docker-compose.yaml
and
Dockerfile
for service orchestration and defining containers, a
task.yaml
containing task metadata, a data/ directory with seed data for all services, a rubric specifying evaluation criteria, and two patches:
test.patch
and
golden.patch
, which contain test fixtures applied at evaluation time and the reference solution for validation respectively.

Task Sourcing

Tasks are derived from real-world GitHub Issue–PR pairs, sourced from repositories with at least 350 stars. We filtered for complexity, selecting only patches with at least 100 lines of code impacting at least three files. Tasks were also evaluated for test coverage and brittleness, defined as whether tests are implementation-agnostic. Software engineers with 3+ years of experience converted open-source tasks into benchmark tasks, creating prompts that mimic a user report. They also dockerized the repository and generated logs that were validated as relevant to the flagged issue requiring debugging.

Programming Language

Observability tasks are distributed across five languages: Go (30%), Python (25%), TypeScript (25%), Java (10%), and C++ (10%).

3
Experimental Setup

3.1
Model selection

We evaluated eight frontier models against APEX–SWE: Claude Opus 4.5 (High), Claude Sonnet 4.5 (High), DeepSeek V3 03-24, Gemini 3 Pro (High), GPT–5.1 Codex (High), Grok 4, Kimi K2 Instruct, and Qwen3 Coder 480B. Thinking settings are set to High where available. In the Appendix, Table
9
describes the model configurations.

Models interact with the environment through a persistent, multi-step loop. The model receives a system prompt containing task instructions and tool definitions. It iterates until it outputs a
<task_complete>
tag or reaches the wall-clock timeout of one hour. Models have access to three categories of tools: Terminal (Bash execution via
/bin/bash
in a persistent tmux session), File Operations (with read/write access to the workspace), and MCP Servers (i.e., direct API access to all running services, such as Loki, Plane, Medusa, via Model Context Protocol).

3.2
Leaderboard Evaluation

For the APEX–SWE leaderboard, we assess models’ outputs using Pass@1, defined as the percentage of tasks where the model’s first attempt passes all correctness tests. For Integration tasks, correctness is verified via a
pytest
suite that interacts directly with service APIs. Tests validate executability, side effects (e.g., verifying that an email arrived in MailHog), and negative cases. For Observability tasks, correctness follows a
Fail_to_Pass
/
Pass_to_Pass
methodology inspired by SWE-bench
(
11
)
. The harness applies the model’s patch and executes framework-specific tests (
pytest
,
go test
,
jest
). A task passes only if all pre-identified failing tests transition to passing while existing passes remain as passes. We also report Pass@3 in this paper, assessing whether the model can achieve at least one correct outcome if given three attempts.

3.3
Rubric Grading

Beyond Pass@1, APEX–SWE uses rubrics to assess engineering quality. Rubric criteria are not part of the Leaderboard and are shared only as part of our secondary analyses to better understand models’ strengths and weaknesses. They are graded by Gemini 3 Pro as an LM judge (Temperature 0.1, Thinking=High). The judge evaluates the final patch and execution logs against the human-authored rubric criteria. If a model times out, it receives a 0 for Correctness but is still graded against the criteria based on work completed.

Functional Criteria

Implementation-agnostic behavior requirements (e.g., “Script must not leave zombie processes”).

Robustness Criteria

Error handling, edge case coverage, and fail-secure behavior.

Style Criteria (Observability only)

Documentation, organization, and adherence to language-specific conventions.

4.1
Success Analysis for Integration

We qualitatively reviewed the Integration tasks that were successfully executed. We find that success is not determined by raw coding capability; instead, it is driven by epistemic discipline — an agent’s ability to distinguish between assumptions and facts, and its willingness to verify the former before acting. High-performing models often exhibit a three-phase workflow: systematic exploration, explicit specification extraction, and closed-loop verification.

Problem Space Exploration

Successful agents prioritize building context over taking immediate action, investing early episodes in defining their strategy. Rather than immediately coding, they inspect data structures and query tools. In one task, Claude Opus 4.5 explicitly identified that it needed to retrieve full issue details via MCP before implementing, and executed shell commands to verify input schemas rather than inferring them. This deliberate pause ensures the agent solves for the actual environment state rather than a hallucinated version.

Task Specification

Once the environment is modeled, successful agents parse unstructured descriptions into lists of hard constraints. They treat resource names and paths as explicit specifications. In one instance, an agent produced a numbered list of requirements (e.g., “Create bucket daily-snapshots-bucket… Key format daily/YYYY-MM-DD/users.csv”) before generating code.

Verification & Self-Diagnosis

A key feature of successful agents is that they do not accept code generation on its own as evidence of task completion. These agents explicitly verify specifications by mapping outputs back to requirements. For instance, in one task, Claude Opus 4.5 ran
aws --endpoint-url=http://localstack:4566 s3 ls s3://daily-snapshots-bucket/ --recursive
to empirically confirm file existence, then walked through a self-generated checklist to verify that uploads succeeded and cron entries were valid. This self-verification step prevents false positive completion.

4.2
Failure Analysis for Integration

We qualitatively reviewed the Integration tasks where the agent did not execute the task. We find that failures stem from three primary causes: incorrect understanding, specification hallucination, and open loop execution. The lowest-performing models (Grok 4, Qwen3 Coder) frequently exhibit these patterns.

Bad Environment Understanding

Lower performing agents often hallucinate environment state when context retrieval fails. In one task, Grok 4 failed to find project context via MCP and assumed that no workspace existed. Instead of exploring the local filesystem, it spent 10 episodes mocking up an external API architecture, completely ignoring the provided input file. The result was a competent solution to a completely hallucinated problem.

Specification Hallucination

Lower-performing models incorrectly treat strict constraints as variables to be optimized for semantics. In one task, Qwen3 Coder altered a required bucket name (users-csv-bucket) to a more “logical” variant (terraform-csv-bucket), while Kimi K2 Instruct paraphrased a required ticket title, creating “Test Ticket - AI Assistant” instead of the exact string “Creating Test Ticket”. These are understanding failures, where the model prioritized generating appropriate variable names rather than strictly following naming conventions.

Open Loop Execution

The clearest differentiator between success and failure is self-verification. Lower-performing models work in an open loop, assuming that code generation is equivalent to task completion. In one task, Grok 4 set script permissions (
chmod +x
) then immediately signaled completion. Trajectory analysis showed that the script was never executed, and the agent did not create the S3 bucket it was supposed to. In this case, the failure was not due to a lack of knowledge but a process failure: the absence of the testing loop required to turn generated code into working software.

Performance by Integration Service

We analyze model performance by the service used for each task, as shown in Table
2
. Models perform significantly better on tasks using well-documented standards like LocalStack (AWS), scoring
28.1\%
on average, compared with just
17.4\%

In contrast, services like Medusa and EspoCRM require reasoning over deep, nested service-specific hierarchies (e.g., understanding that a Product requires Variants, which require Prices per region). >25\%

<10\%

4.4
Number of Episodes to Complete Integration Tasks

Models typically use fewer episodes on successful tasks compared with unsuccessful tasks (
24.0
vs
32.7
), as shown in Table
3

35\%

20.2

30\%

3.1\times

30+

Grok 4 has the lowest episode count (
9.48
) but also the lowest performance (
14\%

In one task requiring S3 bucket cleanup, Grok 4 wrongly assumed database context and attempted to open PostgreSQL connections, completely ignoring the S3 requirements. This shows that speed without comprehension is counter-productive; a minimum floor of context gathering is required for success. The ideal agent is neither the most exhaustive explorer (GPT–5.1 Codex) nor the fastest actor (Grok 4), but one that optimizes the ratio of information gain to action (Gemini 3 Pro).

5.1
Success Analysis for Observability tasks

Success analysis on APEX–SWE Observability tasks shows similar findings as the Integration tasks, with strong performance also driven by epistemic discipline. However, in this context, such discipline changes from verifying specifications to understanding the state of the system before attempting to repair it.

Iterative Debugging

High-performing models (Claude Opus 4.5, Gemini 3 Pro) treat log analysis as an iterative debugging loop rather than a retrieval task. They actively manage their context window by progressively filtering noise. In one task, Claude Opus 4.5 ran a broad query, observed the high volume of logs, and then refined the query with
| "ERROR|flush"
, reducing the output from 6,000+ characters to 1,669 characters.

System Exploration

Successful agents explore the environment reading an average of 10+ files before attempting a fix. In one task, Claude Opus 4.5 read 11 files to trace the full execution path, ultimately patching three separate components (logger, scanner, and tests) to correctly wire a new handler.

5.2
Failure Analysis for Observability tasks

Bad Context Handling

The most common failure mode for lower-performing models like DeepSeek V3 03-24 is to query logs in one shot without filtering. In the same task where Claude Opus 4.5 succeeded, DeepSeek V3 03-24 issued a single, unfiltered query that returned 16,515 characters, immediately triggering a truncated warning. It then ignored the truncation warning, did not refine the query, and patched the files based on incomplete data. Not viewing the relevant error log leading to a hallucinated fix.

Execution Failure

While some models fail because they cannot fully understand the problem, others fail because they just cannot implement the solution. Grok 4, despite successfully using log filters in
49\%
of attempts, exhibited a
22.7\%
code generation error rate - mostly basic indentation and syntax errors. Even when the agent correctly diagnoses the issue, it fails to translate that understanding into valid code. This instability suggests that for lower-tier models, the bottleneck is often basic code hygiene rather than high-level planning.

Performance by Language

We segmented model performance across five languages to isolate how build environments and type systems impact agents’ ability to solve Observability tasks. As shown in Table
6
, models perform best on Python (
33.0\%
) and Go (

), perform worse on C++ (

8.0\%
), and fail on all Java (
0.0\%

Python and TypeScript

Python has the most permissive runtime, allowing agents to execute imperfect code and utilize error feedback for iterative self-correction. On the other hand, models perform poorly on TypeScript performance, even though they are generally proficient in TypeScript, because they fail to adhere to rigid production software constraints like
strictNullChecks
. These compilation barriers prevent execution entirely, blinding the agent to logic errors and inhibiting the epistemic feedback loop required for repairing mistakes.

C++ and Go

In compiled languages like C++ and Go, failures stem from infrastructure rather than syntax. Agents frequently generate code that violates external build configurations - such as ignoring Go vendoring rules or breaking CMake targets - demonstrating an inability to perceive the underlying dependency graphs that govern compilation in complex environments.

Java

Java’s
0\%
pass rate is an outlier, driven by the framework rather than the models’ lack of ability. All Java tasks utilized Spring WebFlux, a reactive programming framework. Models consistently attempted to solve these tasks using imperative, synchronous patterns (e.g., blocking calls), failing to use the non-linear control flow that Spring WebFlux requires. This suggests that while models can write Java, they struggle to reason about specific architectural paradigms.

7
Conclusion

The APEX–SWE benchmark demonstrates that state–of–the–art performance in AI software engineering is no longer determined by raw coding capability alone, but by epistemic discipline - the agent’s ability to distinguish between assumptions and facts, and its willingness to verify the former before acting.

In the context of Integration tasks, epistemic discipline appears as architectural precision. The highest-performing models (Gemini 3 Pro, Claude Sonnet 4.5) extract explicit specifications for tasks, anchor implementations on non-negotiable constraints, and perform closed-loop verification. In the context of Observability tasks, epistemic discipline manifests itself in diagnostic agency. Models like Claude Opus 4.5 treat log analysis as an iterative search problem, filtering noise and mapping system dependencies before attempting repairs.

APEX–SWE shows that the skills required to architect systems are distinct from those required to debug them. For both Integration and Observability, there is substantial room for models to improve, with the best system (Gemini 3 Pro) scoring
25\%
at Pass@1, closely followed by Sonnet 4.5 and Opus 4.5. Ultimately, our findings suggest that the future progress of AI Software Engineering will depend less on training models to write better code, and more on teaching agents to emulate the rigorous engineering process: extracting strict specifications, iteratively debugging their own mental models, and refusing to declare success until empirical reality aligns with their intended design.

Related Work

Unit-Level Code Generation

Benchmarks such as HumanEval
5
and MBPP
3
evaluate standalone function generation, but they are now largely saturated, with frontier models exceeding 90
\%
Pass@1. Extensions include HumanEval Pro
19
for self-invoking tasks, MultiPL-E
4
for multilingual coverage, and LiveCodeBench
10
for contamination-resistant evaluation. Still, unit-level tasks differ fundamentally from real engineering work, which requires navigating existing codebases and debugging complex system interactions.

Repository-Level Code Generation

SWE-bench measures model performance on real GitHub issues that require multi-file patches. However, Wang et al.
14
found that 7.8
\%
of “passing" patches failed developers’ actual test suites, and Yu et al.
18
showed that enhanced testing can significantly shift model rankings. SWE-bench Verified (OpenAI, 2025) adds human verification, while SWE-bench Pro
6
targets similar structured but harder tasks. Nonetheless, these benchmarks remain limited to single-repository bug fixing and exclude observability, infrastructure, and cross-service integration.

Tool Orchestration and Function Calling

ComplexFuncBench
20
evaluates multi-step function calling across booking-domain APIs. MSC-Bench
7
provides a large-scale evaluation of tool orchestration within MCP ecosystems, covering 491 servers and a five-level curriculum ranging from simple retrieval to cross-server planning. BFCL v2
13
and ToolHop
17
offer additional perspectives. These benchmarks excel at measuring tool selection and coordination, but they stop short of evaluating infrastructure implementation. Tasks focus on calling APIs correctly rather than building production systems that persist data, deploy serverless functions, or implement full end-to-end business logic.

Domain-Specific Integration

CRMArena
9
evaluates CRM workflows, where agents achieve below 65
\%
success rates. ELT-Bench
12
measures data pipeline construction, with the best agent correctly generating only 3.9
\%
of data models. OSWorld
15
examines multimodal agents performing open-ended computer tasks across operating systems, and TheAgentCompany
16
simulates a software company environment with about 30
\%
autonomous task completion. These benchmarks focus on domain-specific expertise rather than the heterogeneous, cross-platform integration that characterizes real-world production engineering.
