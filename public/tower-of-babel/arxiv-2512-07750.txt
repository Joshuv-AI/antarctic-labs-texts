A Performance Analyzer for a Public Cloud’s ML-Augmented VM Allocator Conference: ; 2025
Roozbeh Bostandoost † \dagger , Pooria Namyar * , Siva Kesava Reddy Kakarla * , Ryan Beckett * , Santiago Segarra § , Eli Cortez ¶ , Ankur Mallick ¶ , Kevin Hsieh * , Rodrigo Fonseca * , Mohammad Hajiesmaili † \dagger , Behnaz Arzani * † \dagger University of Massachusetts Amherst , * Microsoft Research , § Rice University , ¶ Microsoft

Abstract
. Many operational cloud systems use one or more machine learning models that help them achieve better efficiency and performance. But operators do not have tools to help them understand how each model and the interaction between them affect the end-to-end system performance. Sanjesh is such a tool. Sanjesh supports a diverse set of performance-related queries which we answer through a bi-level optimization. We invent novel mechanisms to solve this optimization more quickly. These techniques allow us to solve an optimization which prior work failed to solve even after 24 24 hours. As a proof of concept, we apply Sanjesh to an example production system that uses multiple ML models to optimize virtual machine (VM) placement. These models impact how many servers the operators uses to host VMs and the frequency with which it has to live-migrate them because the servers run out of resources. Sanjesh finds scenarios where these models cause 4 × \penalty\ 4\times worse performance than what simulation-based approaches detect.



1.
Introduction

Cloud operators often rely on machine learning (ML) models to improve availability and efficiency
(
18
;
8
;
48
;
10
)
.
But operators often deploy these models in systems that contain other ML models and algorithms (which often approximate slower, optimal solutions). The predictions of these ML models and the algorithms that use these predictions can interact in complex ways.
This complexity makes it difficult to understand how each model affects overall system performance.
If we do not analyze and mitigate their impact, these interactions can lead to significant performance issues over time.

We develop
Sanjesh
to help operators address this challenge.

Sanjesh
helps operators comprehensively analyze systems that rely on predictions from one or more ML models and enables them to identify and prevent scenarios that could degrade performance.

The virtual machine (VM) allocator
(
18
)
of a public cloud is an example of such a system. The allocator’s goal is to pack incoming 1st-party VM requests onto physical servers to minimize cost and maintain performance. It constructs features that describe a VM request and employs a pipeline of ML models that predict a VM’s resource needs
(
18
)
(e.g., CPU and memory usage) and its operational lifetime
(
8
)
. The system feeds these predictions into a variant of the best-fit bin-packing heuristic that places the VMs onto servers. The VM allocator relies on these predictions to improve efficiency (most users request more resources than they need).

Errors in these ML model’s predictions pose a risk to the system: in benign cases, they lead to inefficient server usage, but in severe cases, they cause resource contention that forces operators to perform disruptive live migrations to re-balance the load
(
50
;
35
)
. These disruptions can cost the provider millions of dollars
(
12
;
55
;
46
)
.

It is important for operators to understand these risks
before
they deploy these models and answer questions such as:

•

When and under what conditions can performance problems happen?

•

Which models do they need to improve to avoid performance problems in production and by how much?

•

How do typical behaviors of an ML model and problems like data drift impact the end-to-end performance of their systems and how often should they re-train those models to avoid these risks?

Operators can use the answers to find what improvements can help reduce the operational risk of the overall system and to find ways to mitigate that risk where it happens.

To answer these questions, we need a system that can reason about each ML model and its errors, its interaction with the other ML models within the system, and the system itself (and the algorithms within it)
simultaneously
.
This is hard as the set of possible states and outcomes we have to reason through can be huge. For example, in the VM allocator, it is a function of the Cartesian product of all possible predictions (and mispredictions) of the ML models
for each
VM, the available capacity in each server, and the behavior of the bin-packing algorithm given those inputs.

This is why most existing solutions fall short (we highlight what each work does not support in

It is hard to bridge this gap because it is harder to verify the system performance compared to when we verify system correctness
(
43

probabilistic

(

. ML explainability and debugging solutions often focus on the behavior of individual models in isolation (e.g., they find the features that most influence a single model’s predictions
(

Sanjesh
considers the entire state-space. It finds

Sanjesh
enables operators to answer key operational queries (see
Table 2
) about how sensitive the system is to changes in the input feature distribution, the relative influence of each model on the system performance, how much they can improve end-to-end performance if they improve one or more of the ML models they deploy, and (for some subset of ML models) which combination of features are the most problematic for the system.

As a performance verifier,
Sanjesh
tackles a known hard problem
(
5
;
25
)
. One of the most challenging queries it answers is whether a hypothetical model with higher accuracy could improve the end-to-end system performance. To answer this,
Sanjesh
must capture both the range of possible behaviors of such a model and how it would interact with the rest of the system.

We solve the problem in two phases: we find the set of predictions of the models the system uses that cause the worst end-to-end performance and then map those predictions to the features that produced it. We describe this approach through a case study of a VM allocator of a large cloud.

For the first phase, we model the task as a bi-level optimization problem—which solves a Stackelberg game—and adapt techniques from prior work
(
43
)
to solve it.
Unlike previous approaches,
Sanjesh
can handle problems with
probabilistic
inputs.
Our approach is based on bounded model checking and the small-scope hypothesis
(
17
)
: we assume the behaviors that cause performance degradation in long VM arrival sequences can also occur in shorter sequences.
To help operators validate this assumption, we introduce a time-partitioning technique that breaks long VM arrival sequences into smaller segments. By solving the bi-level optimization problem on each segment in sequence,
Sanjesh
can efficiently analyze much longer workloads while preserving accuracy. This approach enables
Sanjesh
to handle VM sequences that are
10-20\times
larger than those supported by prior work
(
43
)
.

In the second phase, we find the specific set of input features that produce the problematic predictions from phase one. This itself is a hard problem because some features may be shared between different ML models. We use an SMT solver
(
19
)
and a novel method based on counterexample-guided abstraction refinement (CEGAR) to map these predictions back to their input features. The feature set
Sanjesh
produces helps operators find regions of the input space that can cause poor performance and to mitigate that risk (for example, they can choose to ignore the ML model’s predictions when they encounter inputs from those regions).

To build
Sanjesh
we combine techniques from optimization, probability, and formal methods. We evaluated it on production data from a large public cloud. We found
46\%
of the problematic feature combinations
Sanjesh
uncovers are present in the production traces.
Sanjesh
also found problematic scenarios that were much more severe (up to 4
\times
) than what operators can find with trace-driven simulations.

•

We use
Sanjesh

2.
The Motivator: The VM allocator of a cloud

We built
Sanjesh
to analyze the VM allocator of a large production cloud.
This allocator uses two ML models—similar to those in
(
18
;
8
)
—to guide VM placement decisions:

•

CPU utilization model
– predicts whether a VM will use more than 65% of its requested CPU.

•

Lifetime model
– predicts whether the VM will remain active for a long time or not.

The deployed models are light gradient boosting machines (LGBMs)
(
33
)
and are binary classifiers.
The allocator uses the outputs of these models as inputs to a variant of the best-fit bin-packing algorithm
(
8
)
to place VMs onto servers.
The CPU model provides the bin-packing algorithm with an estimate of how much CPU the VM is likely to need, while the lifetime model specifies which server pool the algorithm can use for placement.
The bin-packing algorithm uses servers from different server pools for VMs with different lifetimes.

The operators of this cloud wanted to have a mechanism to
validate
the impact of each of these models on end-to-end performance. They also wanted to understand if a similar “memory-model” that predicts the memory utilization of the VM could help further improve the system. They designed a prototype of such a model (not yet deployed): a multiclass LGBM that predicts what percentage (quantized) of the memory which a VM requests it will actually use.

The end-to-end performance metrics the operators wanted to measure were: (1) how many servers the system uses to allocate VMs; (2) how many VMs will they have to live-migrate (especially in the worst-case). Live migrations happen when the allocator assigns fewer resources to a VM than it actually uses due to the ML models’ underpredictions. This causes the host server to become overutilized, which means that the total number of CPU cores or memory (in GB) assigned to VMs exceeds the server’s physical capacity.

Simulations do not find such cases because the performance of the bin packing heuristic the VM allocator uses depends not just on the predictions of a single model for a single VM but that of both models (or all three models when the memory model is used)
and
on these predictions across VMs that arrive over time. Algorithms such as best fit are sensitive to the order in which requests arrive — there are many possible orderings which are all equally likely to happen in practice.

The scenarios we found are not theoretical outliers. The traces contained VMs with features and ground truth labels that match these scenarios:
46\%
of the VM arrival sequences we find have a matching sequence in the production trace (with a slight perturbation in the VM arrival times)! This means there are scenarios that are likely to happen in practice (that have not yet happened) and can degrade the performance of the VM allocator. It is important for operators to find such instances and apply mechanisms to mitigate them: many incidents in production systems happen because of such
hidden
vulnerabilities that eventually happen
(
43
;
7
;
28
)
.

We also found the three ML models impact the system in different ways (
Figure 1
).
We engineered the three models to have similar accuracy (
\sim 70\%
) and evaluate a system where we used the predictions of one of the models and the ground truth for the others. Although the three models have the same accuracy, the CPU model impacts the end-to-end performance (whether the operator will have to live-migrate the VM or not)
6\times
more than the memory model. The reason for this higher impact is (1) a single VM can consume an entire server’s CPU but not its memory; and (2) it is less granular than the memory model which means its mis-predictions are more likely to cause the allocator to place the VM on a server with insufficient capacity. The lifetime model has no impact on live-migrations (when we have accurate information about how much resources a VM needs, we can ensure we place them on servers with enough capacity eliminating any live-migrations).

These are the types of insights that allow operators to prioritize which models to improve and how.
Sanjesh
provides a mechanism for them to analyze the system and the ML models it uses end-to-end and to validate the system is safe to use in production and to find ways to improve it.

3.
Sanjesh

Our goal is to find the features (and the ML model’s predictions) that cause the worst-case performance in the system compared to one which has access to the ground-truth labels. We also want to enable operators to constrain the search space to those features and predictions (and mis-predictions) that are likely to happen in practice.

Our solution is based on an idea that was first introduced by recent work in heuristic analysis
(
43
)
: we can view the problem as a leader-follower game. In this game, the leader produces inputs that cause the system to underperform compared to the optimal. The followers take this input and produce the outcomes the optimal algorithm and the existing system would produce.

In our context, the optimal system is one that has access to the ground truth information. The existing system consists of the variant of the best-fit heuristic that the VM allocator uses
(
8
)
and, the
predictions
from the CPU, memory, and lifetime models. The game translates to a bi-level optimization:

Once we solve this bi-level optimization and find the values

The analyzer then formulates the problem and passes it to the bi-level optimization solver. Our bi-level optimization solver extends the solver in the open source MetaOpt

The bi-level optimization solver produces the predictions and ground truth labels that cause the end-to-end system to underperform.
Sanjesh

The VM Allocator applies to a sequence of VM arrivals. Like prior work in performance verification we rely on the assumptions of bounded model checking: we assume the behaviors that cause performance problems in large sequences also appear in shorter ones (we see this in our results in

4.
Technical challenges

Prior work such as MetaOpt
(
43
)
also solve bi-level optimization problems. But the nature of ML-augmented systems and the queries we want to support introduce challenges which make them hard to apply directly to our problem:

Probabilistic inputs and constraints.
The inputs to our systems (and, more crucially, the constraints we impose on these inputs) are inherently probabilistic. If we use
F({\textbf{f}})
to represent the mapping of the input features
f
to their ground-truth labels, then this
F
is a probabilistic function: the same features may map to different ground-truth labels (this a common occurrence where we have confounders that can perturb the outcome but are not in the feature-set).
For the same reason, the error distribution of the ML models (which is one of the constraints we impose on
\textbf{I}^{\prime}
) is also probabilistic in nature. MetaOpt takes a frequentist approach to probabilistic inputs which has a significant impact on its ability to solve the bi-level problem at scale. MetaOpt does not natively support probabilistic constraints.

The inter-dependencies LGBMs introduce.
The structure of the LGBMs the VM allocator uses introduce another challenge. These models are ensembles of decision trees where the LGBM groups the trees based on their ground truth labels. For a given input, each tree produces a score. To make a prediction, the LGBM passes these scores through a softmax function to get a probability for each class. The model predicts the class with the highest probability. This coupling makes it hard to separately analyze each tree — a method many verification solutions use to analyze random forests
(
57
;
20
)
. We develop a CEGAR-based approach to handle this.

How to ensure the inputs are consistent.
The models the system uses share input features and are not
100\%
accurate.
This implies: (1) the inputs
I
and
\textbf{I}^{\prime}
are dependent, and we need to enforce these dependencies in our bi-level formulation; (2) we need to jointly analyze these ML models when we want to find the feature vectors that produce
I
and
\textbf{I}^{\prime}
. To solve (1) we develop novel techniques to impose the joint distribution of
I
and
\textbf{I}^{\prime}
in the bi-level optimization. To solve (2), we develop a novel CEGAR-based approach in which we model an abstracted version of the LGBM trees (
Section

6.2
).

It is hard to formulate the queries in
Table 2
.

Sanjesh
supports a wide range of queries. It is hard to model these queries in MetaOpt — the tool was not designed to handle the scenarios these queries target. We need mechanisms that allow us to formulate these queries into the constraints or the objective of the bi-level optimization. For example, to encode query
, we have to encode
F(\textbf{f})
which is hard to describe as a closed-form function. To encode
we need to describe the behavior of a model that does not yet exist. We develop mechanisms to mathematically model these queries and also make it easier for users to define new ones.

How to solve the bi-level optimization.
MetaOpt can solve bi-level optimizations, but it cannot do so in a reasonable time-frame
(
15
)
(it did not give a solution to the problem we modeled even after 24 hours). This is why (even though we can model LGBMs as part of the bi-level optimization

F
) we partition the problem in two ways: (1) we first find the predictions that cause the VM allocator to underperform and then find the features that produce those predictions; and (2) we devise a time-partitioning solution to further scale the first part of the problem. This decomposition also provides a secondary benefit: it allows us to generalize
Sanjesh
and apply it to systems that use non-LGBM models more easily (the first stage applies directly).

(
M_{1}
) The “typical” worst-case impact of the ML models.
We need to analyze “typical” scenarios and find the worst case impact among those scenarios. Typical scenarios are those that fit the patterns we observe in production trace (we can find these patterns from the input data that the user provides).

Typical scenarios capture: (1) the
joint
error distributions of the ML models, (2) how often each ground-truth label appears, (3) how often different VM types are requested, and (4) how frequently users submit VM requests within a given time window (e.g., a day).
To ensure we capture only the worst-case system performance under such typical scenarios, we add constraints that: (a) match the joint error distribution across all ML models; (b) preserve the observed mix of ground-truth labels and VM request types; and (c) match the observed frequency of VM submissions within the target time window.

For example, a CPU model may be
70\%
accurate (the predicted label and the ground truth are the same) and underpredict (predicts
0
when the true label is
1
) in
15\%
of scenarios.

We can enforce these characteristics if we constrain the number of VMs or predictions that satisfy each of these properties. But because these constraints are inherently
probabilistic
(they describe the probability with which a VM or a prediction satisfies a particular property), we need to ensure that we analyze a long enough sequence for the constraints to hold with statistical significance. But the length of the sequence we analyze directly impacts our ability to scale.

We develop two techniques to help with this problem: first, we add a mechanism in the constraint encoder to pick the smallest sufficient sequence size that ensures statistical significance; and we develop a time partitioning solution which we will describe later in section
Section

6.1
.

(
M_{2}
) Probabilistic constraints over a finite sequence
.
Sanjesh
like most performance verifiers
(
43
;
25
;
5
)
relies on the principles of bounded model checking: we assume that we can observe the patterns that cause a system to underperform on small instances.
Sanjesh
analyzes a sequence of
N
VMs.

We need to pick
N
such that the distributions we enforce (those from
M_{1}
) are statistically significant: we must ensure a finite sequence reflects the properties we want to enforce with high probability (e.g., 99.99%).

To see why, imagine tossing a biased coin where the chance of heads is
p
. If you toss it infinitely many times, the fraction of heads will converge to
p
. But if you only toss it
N
times, the number of heads you observe will vary due to randomness, it might be more or less than
p\cdot N
. The question we face is: how many heads should we expect in those N tosses to confidently say that this sample behaves like the original biased coin?

We estimate the range of values that are highly likely (with probability
\geq 99\%
) in a sequence of size
N
. We describe these values in terms of an interval that contains
p
(
i.e.,

[p-e,p+e^{\prime}]
) and use standard statistical tools
(
13
)
to find the bounds of that interval (see
Appendix

B
for the details).

For example, if the CPU model’s accuracy is
70\%
, then in a sequence of 10 VMs it will have an accuracy between
60-80\%
with high probability (
Figure 3
).

(
M_{3}
) Ground truth mapping
. Many queries in
Sanjesh
compare the current system to an ideal system that has access to ground truth. But we do not have a closed-form function
\mathcal{F}(\textbf{f})
that maps feature vectors to their true labels.

We do have access to the production data: feature vectors paired with their ground truth labels, which gives us a partial view of
\mathcal{F}(\textbf{f})
. The first phase of our solution only operates on the predictions and labels and we can use the distribution of labels in the production data to specify the range of ground-truth labels we can observe and their frequency. This also makes it easy to model queries where the operator wants to understand the impact of the change in the underlying data on the system’s behavior: we can relax the constraints that enforce the label distribution and capture such scenarios.

In the second stage, we need
\mathcal{F}(\textbf{f})
— we need to find the features where the model makes the predictions we found in the prior step and where the ground-truth matches the ground truth we found. We cannot model
\mathcal{F}(\textbf{f})
as a discrete map (it does not scale) but we can approximate this map with an overfit model (we call this overfit model a reference model).

Overfit models memorize the training data and because of that they generalize poorly. This makes overfit models brittle and a poor candidate when we want to predict the outcome for new instances but they serve as a great approximation for an existing hash-map. To build an overfit model we train a model that is nearly 100% accurate on the production data and treat it like any other ML model in the system.

(
M_{4}
) Data drift
. Data drift is a change in the mapping from features to labels — as a change in
\mathcal{F}(\textbf{f})
in time: we can think of
\mathcal{F}(\textbf{f}
) as a function in time (
\mathcal{F}(\textbf{f},t)
, where
t
is time).

To analyze the model performance under
\mathcal{F}(\textbf{f},t_{future})
, we change
p\%
of the ground truth labels in the data and use this new dataset as our ground-truth. We can relax the constraints that enforce this behavior to account for the uncertainty in the amount of drift we think is possible.

The optimization technique that enables this relaxation is a standard technique based on slack variables
(
11
)
. Slack variables are positive variables which we add to a constraint to allow it to “relax”:
Ax\geq b
becomes
Ax+s\geq b
which allows
Ax
to sometimes become smaller than
b
. We can bound
s
to control how much we relax the constraint. We use this technique in
Sanjesh
to relax any constraints where we want to allow the model to deviate from constraints we enforce (e.g., we can use it in
M_{4}
so that we find, in a controlled way, scenarios where the ground truth distributions deviate from the data we have seen so far).

We show an example of how we model data drift in
Figure 3
: we reduce the frequency with which the ground truth label is
0
by
10-20\%
(the original frequency was
60\%
).

(
M_{5}
) The behavior of a hypothetical model (query
)
. To support this query, we
bound
the set of possible behaviors the model can have relative to the existing models and the ground truth labels. In this way, we restrict the model to have a specific accuracy and we describe how its predictions relate to the predictions of the existing model. This approach also allows us to explore different ways we can improve the model (e.g., reduce false positives/negatives) that impact the end-to-end performance of the system. These bounds specify constraints on how often the predictions from this hypothetical model match those of the existing one, and how often they deviate and by how much.

For example we may have a CPU model that is
70\%
accurate and has
15\%
false positive/negative rate. We want to consider a hypothetical model that improves the accuracy to
80\%
. We want this hypothetical model to reduce the false positive/negative rate to
10\%
, and to match the predictions of the existing model
90\%
of the time (notice how this leaves
10\%
of the predictions for the analyzer to play with — we can add constraints to control these too if we have a guess as to how the improved model handles them).

The bounds we described above enforce the marginal distributions of predictions from the hypothetical model as functions of the marginal distributions of the existing model (a marginal distribution only captures the probability distribution in one dimension whereas the joint probability distribution describes the full probability space — the joint probability distribution also dictates the marginal). For these marginals to hold, a consistent joint distribution must explain them. Each joint outcome contributes to one part of the marginals, but we enforce constraints so that all joint outcomes together satisfy all marginals. We detail this process in
Appendix

G
.

6.
How to scale

With these mechanisms in place, we must ensure the analysis completes within a practical time frame. Operators use
Sanjesh

offline
during the design phase (before deploying ML models) and periodically to check system health after retraining (typically once per week), so the runtime should not exceed one day. We designed our approach to finish in
\leq 15
hours, with hyper-parameters that let operators trade off optimality for runtime (
Section

7
).

Sanjesh
runs in two stages: (1) it first finds predictions that cause the VM allocator to underperform; and then (2) finds the feature vectors that produce those predictions. To scale the first phase we partition the VM sequence into smaller groups based on their arrival time and analyze these groups one at a time (each problem is smaller). To scale the second step we develop a novel CEGAR-based method.

6.1.
The first phase: time-based partitioning

Sanjesh
is based on the concept of bounded model checking
(
17
)
which assumes the same problematic instances that occur in long sequences are also observable in shorter ones. For example, MetaOpt used sequences of only five items (it takes a few hours for it to analyze a sequence of 10-20 VMs) to prove new bounds for a bin-packing heuristic. But, as we saw in
Section

5
, the probabilistic constraints we model in
Sanjesh
require we analyze longer sequences (
N\sim 100-200
).

We develop an approximate time-partitioning technique that allows us to run the analysis in the same time-frame for sequences that are
10-20\times
larger.

We split the
N
VMs we want to analyze into
k
partitions based on their arrival time. We solve the bi-level optimization for each partition separately. When we find a solution for each partition, we update the starting state for each server before we find the solution for the next partition. With this solution we control the trade-off between speed and accuracy: small partitions run faster but have a higher approximation error.

To manage this trade-off, we can take advantage of the warm-start feature that most optimization solvers such as Gurobi
(
47
)
provide and iteratively increase the size of the partitions we use: we first solve the problem with small partitions and use the solution we find in this step as a warm start to the same problem but with larger partitions — the warm-start allows the solver to find a solution more quickly.

The same “typical worst-case” challenge we saw earlier in mechanism
M_{1}
(
Table 3
) appears here in a different form: we need to apply the constraints we defined for the entire
N
-VM sequence locally within each partition which introduces a dependency between them.

Suppose we want to enforce constraints on the VM type distribution (which describes the amount of CPU and memory available on a VM) to match realistic VM-request distributions. When we want to analyze a sequence of
N
-VMs, these constraints enforce how many of these VMs can be of each type. But then how do we translate this constraint to constraints on VMs we place in each partition? Here, we take a frequentist approach: we use the mechanism we developed in
M_{2}
, and find a lower and upper bound (
l_{i}
and
u_{i}
) on the number of VMs we can have in each partition of each type for the overall constraint to hold. We then enforce this lower and upper bound in each partition.

6.2.
The second phase: CEGAR-based approach

Once we find the predictions we search for the feature vectors that led to them. We could scan the training data but this often fails: shared features across models make it hard to find examples consistent with all models’ training data.

We could directly model the light gradient-boosting machines (LGBMs) of VM allocator (CPU model, lifetime model, and optionally memory model) as part of our bi-level optimization and find the feature vectors that produce these predictions (
Appendix

F
). This works well for smaller models but struggles with larger ones. Symbolic execution
(
34
)
faces similar scalability issues.

We develop a solution based on SMT solvers and scale it with a novel CEGAR
(
16
)
-based approach. We encode an abstracted version of each LGBM as a set of decision paths and feed them into an SMT solver like Z3
(
19
)
. The solver checks whether there exists a feature vector that can lead each model to produce a specific prediction. We only refine the abstracted model of the LGBM if we need to (this is what allows us to scale the solution to large instances).

The approach uses how LGBM works for classification: each model uses
n
trees per class, sums their outputs, and selects the class with the highest sum
1
1

1

LGBMs apply a softmax over scores but the outcomes are the same.
.

Consider a multi-class LGBM with three (
f_{1}
,
f_{2}
,
f_{3}
) features and one tree per class (
Fig.

5
). We want to find a feature set that causes the model to predict
Class
2
2
2

2

In the multi-model case, the goal is to find a single feature set that leads each model to a specific class.
.

We first prune each tree to a fixed depth and abstract deeper nodes. We replace the leaf values with pessimistic approximates: the minimum for
Class
1 and 3, and the maximum for
Class
2. This biases the model towards
Class
2 and ensures if
Class
2 is unreachable in this abstraction, it is unreachable in the full model as well.

An SMT solver then checks if any input yields
Class
2. If not, we conclude no such input exists. If we find an example, we evaluate it on the full trees. If the outcome matches, we are done. If not, the example reveals that the abstraction was coarse. We use the example to refine the abstraction: we expand one or more of the trees to a deeper level, where we prioritize the nodes that are most relevant to the counterexample. We repeat this until we find a valid input.

This approach is especially powerful when models share features, such as when the same VM input feeds into LGBMs predicting CPU, memory, and lifetime. We can ask whether a single input yields specific outcomes across all models. Our approach explores this joint constraint space and uses shared features to iteratively find a solution or prove none exist.

This abstraction helps quickly eliminate infeasible scenarios: if no input satisfies the constraints, we prove there is no viable path to the desired predictions. See
Appendix

C
where we compare this approach to traditional solutions.

7.
Evaluation

Sanjesh
is the first system that can analyze how multiple ML models jointly affect the end-to-end performance of a system. As a proof of concept, we analyze the VM allocator of a production cloud
3
3

3

We did not find public data available for ML-based caching solutions
(
10
)
though our implementation natively supports such systems as well
. We show:
(1) how
Sanjesh
evaluates the performance of the allocator across realistic workloads and answers operator-driven queries and
(2) how
Sanjesh
outperforms simulation-based approaches.

7.1.
Methodology

We use MetaOpt
(
43
)
to solve the bi-level optimization in
Equation 1
. We use Z3
(
19
)
as our SMT solver and Gurobi
(
47
)
for our optimization solver. We analyze a sequence of
200
VM arrivals. We divided time into 10-minute epochs, and analyze the system state at each epoch over a full day (144 epochs). We repeat each experiment until we achieve a p-value that indicates our results were statistically significant with
\alpha=0.1
.

Datasets
We use data (from 3 week days in July 2024) and the CPU/lifetime models from a VM allocator of a large public cloud. We also experiment with a prototype memory model the operators were developing. We train the models with data from the first day and use the rest to compute the distributions we enforce for each query.

Metric.
We use a metric we call the “Risk of Migration” to measure allocator’s
performance
: number of servers that become over-utilized in each epoch on average. We normalize the results to
Sanjesh
’s median. We also provide limited evaluations based on the total number of servers utilized.

Benchmarks.
To our knowledge, no prior work can perform an end-to-end analysis of multi-model ML-based systems and answer all queries in
Table 2
. Operators and researchers typically rely on simulation-based approaches or analyze each model in isolation. We use simulators as our benchmark.

We give simulators the same runtime budget as
Sanjesh
and compare the worst-case scenarios each produces. In our benchmarks we: (1) randomly sample 200 VMs (same as
Sanjesh
) from the production trace, run the system, and report the allocator performance across all samples within the time limit; (2) use the full production trace, place VMs by their arrival order, then perturb the sequence until the time budget expires, and report the average of the allocator performance we observed (
\texttt{Trace}_{\texttt{avg}}
).

We also compare
Sanjesh
to SHAP
(
38
)
(which ranks features by how much they influence the model’s prediction) and find that both point to the same dominant features (
Figure 10
).

7.2.
Sanjesh
outperforms simulations

A simulation-based approach, which is based on a real production traces, struggles to uncover the worst-case impact of the models on the system due to the large search space.
As
Fig.

6

Sanjesh
can find a scenario that can induce

The VM allocator can use 16 more servers per epoch compared to one that has access to the ground truth labels on average. Simulations cannot uncover this worst-case scenario but instead find scenarios where the allocator only uses 2 (
0.03

To evaluate the impact of time partitioning technique, we ran the first phase of
Sanjesh
without this technique on 200 VMs. After 24 hours, it still failed to produce any adversarial predictions — partitioning is essential at this scale.

8.
Discussion

To our knowledge,
Sanjesh
is the first system that can analyze the impact of the predictions from
multiple
ML models on the end-to-end system performance.
Through a case study of a large public cloud’s VM allocator (similar to
(
18
)
), we showed the range of queries
Sanjesh
can answer. In addition to the scenario we analyzed:

Sanjesh
applies to non-LGBM models.

We split the problem into finding the worst-case predictions and then finding the features that produce them.
Because of this splitting technique,
Sanjesh
can analyze any model as long as we can define a mechanism to map its predictions to features that produce them. For example,
(
44
)
shows how to do this for DNNs. Other models such as linear or logistic regression are also easy to capture as feasibility constraints which we can analyze through SMT solvers like Z3
(
19
)
.

Sanjesh
is general.
We can analyze any system that we can model as a bi-level optimization (
Equation 1
). Our implementation of
Sanjesh
can support other systems such as ML-based caching
(
10
)
and traffic engineering
(
48
)
. The main requirement to model a ML-based system in
Sanjesh
is to capture the algorithms within the system either as a feasibility or a convex optimization.
MetaOpt introduced topology-based partitioning. This technique, along with the time partitioning techniques we introduced in this paper, allows
Sanjesh
to scalably analyze a broad range of systems.

How to use outcomes
Sanjesh
produces in practice.
Operators can use the mechanisms in
Table 3
to enable new queries. They can use the answers to guide how they design their ML-based systems and where they focus their efforts: in our analysis of the VM allocator we found the CPU model and its improvement has the most impact on performance.

9.
Related work

We distinguish our work from four related areas.

Empirical analysis.
Operators can empirically analyze end-to-end systems by studying their pipelines and observed failures
(
60
;
45
;
54
)
. Pandora
(
45
)
combines human expertise with automated analysis of past failures. It examines multiple ML components together and provides quantitative insights into failures. However, because it depends on past observations, it cannot uncover critical failure scenarios that have not yet appeared. In contrast,
Sanjesh
systematically explores worst-case scenarios to identify risks before they manifest.

ML safety verifiers.
Tools such as
(
51
;
58
;
23
;
32
;
31
;
37
;
56
)
verify whether a
single
ML model satisfies the safety properties. For example, whiRL
(
22
)
uses formal methods to verify reinforcement learning policies. These approaches do not capture how prediction errors affect system-level performance.

Distributed system analyzers.
Much work analyzes the different aspects of the performance of distributed systems
(
24
;
52
;
29
;
26
;
1
)
. Heuristic analyzers
(
43
;
44
;
5
;
42
)
also provide a vehicle to formally analyze the performance of such systems. But none analyze multi-model ML-based systems.

Tree-based model analyzers
. There are works that analyze a
single
tree-based model and understand how sensitive that model is to perturbations of the features
(
15
;
30
;
57
;
14
;
59
;
61
;
21
)
. This problem is NP-complete for general tree ensembles
(
30
)
.
Sanjesh
considers multi-model ML-based systems and analyzes the impact of these models (and finds features that cause it) on system performance. To do so, we not only have to reason about the ML models but also about their interaction with the system and its downstream components.

10.
Conclusion

Sanjesh
is the first comprehensive analysis tool for multi-model ML-based systems that allows operators to
formally
characterize the impact of the ML models they deploy on the performance of a production VM allocator.
Sanjesh
models the allocator’s underlying algorithms in MetaOpt and jointly analyzes the interactions of its CPU, memory, and lifetime models predictions with the bin-packing heuristic. Our results show that
Sanjesh
outperforms simulations and uncovers worst-case scenarios for the VM allocator with up to
4\times
higher impact on system performance compared to trace-based simulations.

Appendix C
Mapping predictions to feature inputs with CEGAR-based approach

To map MetaOpt’s predicted labels to actual feature vectors, we encode the VM allocator’s ML models, specifically, the binary LGBMs for CPU and lifetime prediction, into the Z3 SMT solver
(
19
)
. Each decision tree in these models is modeled such that Z3 follows the path based on threshold conditions at each node and branches left or right depending on whether the input feature is below or above the threshold, and reaches a leaf node that determines the output of the tree. Since the CPU and lifetime models share features, Z3 must find a single global feature vector such that each model, given only its relevant subset of features, produces the required prediction. This shared-feature constraint makes solving the SMT query challenging.

To address this, we combine Z3 with a CEGAR-based approach, which uses abstracted versions of the LGBMs to simplify the search.
We evaluated performance by configuring our CEGAR-based approach in Z3 to search for feature vectors that produce all possible combinations of output labels from the two binary models (i.e., four combinations: (False, False), (True, False), (False, True), and (True, True)) across different VM sizes (VM request in quantized CPU core count and memory in GB) and VM arrival hours within a day. The solver runs with 20 parallel threads on a PowerEdge R630 server (
10\times
3.3 GHz CPUs, 256 GB RAM).

Figure 11
shows that our CEGAR-based approach quickly finds most combinations — completing all but one in 5 minutes, and all in 1 hour. In contrast, Z3 without CEGAR (which models the full tree structure) finds only 57% of combinations in the same 5-minute window. This speedup matters because when no feature vector exists for a model-output combination in
Sanjesh
’s first phase, we must re-run that phase with the invalid combination removed. Detecting such cases early avoids wasted exploration. The abstraction also lets us quickly rule out impossible outputs.

Our CEGAR-based approach also scales better as allocators grow more complex. Operators may add new models, deepen existing ones, or introduce additional shared features. Each of these increases the solver complexity. Abstraction and refinement provide a way to keep the search tractable, offering speedups in practice and robustness as allocators evolve. Z3 alone may eventually find all combinations, but our CEGAR-based approach enables faster verification, ensures timely pruning of infeasible outputs.

Appendix E
The overall risk surface for a VM sequence

We showed how one can compute a risk surface for the model when we analyze systems where a single prediction of each model determines the system’s end-to-end performance. But in systems like the VM allocator we analyze a sequence of predictions and need to merge these risk surfaces (which show the risk surface for each VM in the sequence) to find the overall risk surface.

Our goal is to find the area in the “adversarial feature space” (
i.e.,
what we find as the risk surface for each VM in the sequence) which is most common across all VMs in the sequence. Our approach is simple, we score each region of the feature space based on the number individual risk-surfaces it appears in. This means the more VMs that share that region of the feature space in their adversarial feature space the higher the score of that region in our analysis. We then return the areas in the feature space with the highest score as the overall risk surface of the sequence.

The entropy for the values of a given feature in it’s risk surface (compared to its full range) determine whether that feature plays a critical role in the performance of the system or not. For example, in our analysis of the VM allocator we see that multiple features have a risk surface with maximum possible entropy (
i.e.,
the value of the feature in its risk surface spans the entire range of values that feature can take): these features do not pose a critical threat to the system.

One can imagine different variants of this approach: we can have a cut-off for the minimum number of risk surfaces a sub-region needs to belong to before it qualifies in the sequence adversarial space or we can have a strict requirement where we only consider a sub-region as part of the risk surface if it appears in every VM’s adversarial feature space. Our goal here is to show the potential of
Sanjesh
to facilitate such analysis and the study of which of these metrics is the right one to use is beyond the scope of this work.

Appendix H
Details of VM placement algorithm

The VM allocator uses the Dynamic Preferred Best-fit Rule (DPBFR) algorithm from
(
8
)
as its VM placement algorithm. This algorithm extends the conventional best-fit algorithm and dynamically adjusts the allocation preferences based on the VM’s lifetime prediction. We extend the best-fit implementation in MetaOpt to model it.

DPBFR enhances the best-fit algorithm by: (1) using the lifetime model predictions and (2) quantizing the best-fit scores.

The best-fit score is based on how much space would be left on a server if the VM were placed there. It considers all resource types, like Memory and CPU. For example, if a server has 8 CPUs and 32 GB of memory, and a VM needs 2 CPUs and 8 GB of memory, then the remaining capacity would be 6 CPUs and 24 GB. The best-fit score captures how well this leftover space compares to the total server size. Lower scores indicate a tighter fit, which is generally preferred.

DPBFR discretizes the score into either 3 or 5 buckets depending on whether the lifetime model predicts the VM to be short-lived or long-lived respectively. The quantized best-fit score allows DPBFR to be more robust against small fluctuations in score values and simplifies the server selection process. It ensures that the solution is stable and efficient.

With this description, it is easy to see how we extend DPBFR and apply it to the bin-packing heuristic in MetaOpt. We use binary variables to apply the quantization. We approximate the random (uniform) bin selection of DPBFR we enforce round-robin bin selection from the set of candidate servers: this mimics DPBFR’s performance in the average case. To model the worst-case operators, we can remove this constraint, which then allows MetaOpt to select the worst-case selection of servers.

We formulate DPBFR as a feasibility problem in MetaOpt, defined by a set of constraints without an explicit objective. The notation used is summarized in
Table 6
.
