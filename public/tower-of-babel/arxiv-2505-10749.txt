Code-Driven Planning in Grid Worlds with Large Language Models
Ashwath Vaithinathan Aravindan, Zhisheng Tang, Mayank Kejriwal

Abstract
We propose an iterative programmatic planning (IPP) framework for solving grid-based tasks by synthesizing interpretable agent policies expressed in code using large language models (LLMs). Instead of relying on traditional search or reinforcement learning, our approach uses code generation as policy synthesis, where the LLM outputs executable programs that map environment states to action sequences. Our proposed architecture incorporates several prompting strategies, including direct code generation, pseudocode-conditioned refinement, and curriculum-based prompting, but also includes an iterative refinement mechanism that updates code based on task performance feedback. We evaluate our approach using six leading LLMs and two challenging grid-based benchmarks (GRASP and MiniGrid). Our IPP framework demonstrates improvements over direct code generation ranging from 10% to as much as 10x across five of the six models and establishes a new state-of-the-art result for GRASP. IPP is found to significantly outperform direct elicitation of a solution from GPT-o3-mini (by 63% on MiniGrid to 116% on GRASP), demonstrating the viability of the overall approach. Computational costs of all code generation approaches are similar. While code generation has a higher initial prompting cost compared to direct solution elicitation ($0.08 per task vs. $0.002 per instance for GPT-o3-mini), the code can be reused for any number of instances, making the amortized cost significantly lower (by 400x on GPT-o3-mini across the complete GRASP benchmark).

Approach

We consider planning problems that can be represented as discrete, grid-based environments. We assume that each environment is fully observable and composed of cells, and each cell is associated with attributes such as obstacles, items, and goal-relevant entities. Agents must navigate these grids and execute a task e.g., item collection or goal-reaching—by performing valid action sequences that satisfy task-specific constraints. These environments are common in domains like embodied AI, robotics, and reinforcement learning
[
11
,
21
,
52
]
.

Formally, each planning problem is represented as a tuple
\mathcal{P}=(\mathcal{S},\mathcal{A},T,s_{0},\mathcal{G})
, where
\mathcal{S}
is the state space; each
s\in\mathcal{S}
denotes a configuration of the grid environment, including the agent’s position and attributes (e.g., energy, inventory), as well as locations of objects and obstacles.
\mathcal{A}
is the finite set of discrete actions (e.g., move, pick up, unlock, drop) that the agent is allowed.
T:\mathcal{S}\times\mathcal{A}\rightarrow\mathcal{S}
is the pre-defined transition function. We assume the transition function is deterministic and fully defined, so the effects of each action in a given state are predictable and known.
s_{0}\in\mathcal{S}
is the initial state. We assume that this is fully observable, meaning the agent has access to the complete initial state of the environment. Finally,
\mathcal{G}\subseteq\mathcal{S}
is the set of goal states.

A valid plan is then defined as a sequence of actions
\pi=[a_{0},a_{1},\dots,a_{T}]
such that the resulting state after executing
\pi
from
s_{0}
falls within the goal region:
T(T(\dots T(s_{0},a_{0}),a_{1}),\dots,a_{T})\in\mathcal{G}
. The agent’s task is to generate a sequence of actions
\pi=[a_{0},a_{1},\dots,a_{T}]
that transforms the initial state
s_{0}\in\mathcal{S}
into a goal state
s_{T}\in\mathcal{G}
under the transition function
T
. This requires reasoning about the structure of the environment, anticipating the effects of actions via
T(s,a)
, and selecting actions from
\mathcal{A}
that satisfy task-specific constraints while getting closer toward the objective.

To solve such planning problems, we propose an Iterative Programmatic Planning (IPP) framework that uses LLMs to synthesize interpretable and executable programs that serve as action policies. In this framework, the LLM generates programs that map environment observations to sequences of allowable actions, effectively functioning as planning agents. We first decompose the problem into three key components: (
1) direct program synthesis
, where the LLM is prompted to generate complete, executable programs in a general-purpose interpretable language (e.g., Python) from natural language task descriptions;
(2) pseudocode-conditioned refinement
, where the model is seeded with a high-level algorithmic sketch (e.g., greedy search) and tasked with completing or adapting it to the task environment; and
(3) curriculum-based prompting
, where the model is guided through a sequence of incrementally complex subproblems to facilitate generalization to harder tasks.

We combine these components into a unified prompting-based approach suitable for zero-shot and few-shot planning through code generation. However, to further
optimize
the program generated by the model, we also incorporate an iterative refinement process whereby the LLM first generates an initial candidate program, which is then executed and evaluated on a set of task instances. Based on some performance metric (such as reward and completion rate), the model is prompted to revise the code. Iteration continues until performance converges or improves no further. Through refinement, we show that the LLM learns to correct logical errors, incorporate missing constraints, and restructure control flow.

2.1
Code-driven Planning with Iterative Refinement

Rather than relying on traditional search algorithms or reinforcement learning to solve
\mathcal{P}
, code-as-plan frameworks use an LLM to generate an interpretable program
f
that, when executed against a specific environment instance, produces a sequence of actions
\pi=[a_{0},a_{1},\dots,a_{T}]
transitioning the agent from the initial state
s_{0}
to a goal state
s_{T}\in\mathcal{G}
. This program acts as a reusable and interpretable policy that maps environment observations to action sequences.

This approach contrasts with classical reinforcement learning methods, which typically learn a policy
\pi:\mathcal{S}\rightarrow\mathcal{A}
through repeated interaction with the environment and optimization of cumulative rewards, a process that is time-consuming and computationally intensive. At the other extreme, an LLM could be prompted to directly produce a plan given a grid-based planning problem. Experimentally, this approach is found to yield significantly low-quality solutions, even for leading LLMs (Section
4
; see also Figure
1
). Code-driven planning offers a compromise by forcing the LLM to provide an explicit policy, using only a few prompts, encoded as an interpretable program. An auxiliary advantage of such a policy is that its logic is observable and interpretable.

Direct Generation

Our baseline approach,
direct generation
, prompts the LLM to directly synthesize a complete and executable program
f
given only a natural language task description and environment specifications. This approach assumes that the model can generate code that considers both a high-level strategy and low-level execution details in a single pass. While fast and straightforward, this approach may overlook edge cases or misapply rules. Nonetheless, it establishes a strong starting point for comparing more advanced techniques

Pseudocode Extension

To address some of the flaws of direct generation, we introduce a pseudocode-based prompting strategy. Here, the LLM is provided with a high-level baseline method (e.g., greedy or rule-based logic in pseudocode) and tasked with extending and refining it into an executable program
f
. This approach narrows the LLM’s search space, allowing the model to use
symbolic priors
while preserving flexibility. A disadvantage of this approach is that it requires the pseudocode prior to be provided in the first place. For complex grids, providing such a prior may be cumbersome or even infeasible.

Step-by-Step

The
step-by-step
approach introduces a curriculum-style procedure, in which the model is prompted to solve increasingly complex versions of the task, gradually building up to the full problem. Beginning with simplified environments (e.g., no obstacles, no step cost), the model produces initial code
f^{(0)}
that works under minimal assumptions. At each subsequent stage
i
, the model is given an updated problem with more complexity, such as limited energy, obstacles, or carry constraints, and is required to revise and extend the previous program
f^{(i-1)}
into a new program
f^{(i)}
that can solve the current problem. This formulation mimics human incremental reasoning and in theory, should help the LLM produce a strategy that it might fail to produce through (for example) one-pass direct generation.

Iterative Refinement

To improve the correctness and generality of the generated program
f
, we propose an
Iterative Refinement (IR)
strategy, whereby an LLM iteratively improves its generated code through alternating steps of evaluation and feedback-driven refinement (Algorithm
2.1
). Starting from an initial candidate program
f^{(0)}
(obtained via direct generation), we evaluate its performance on a training set of planning problems
\mathcal{P}
and measure its performance via a pre-defined task-specific metric
J^{(i)}
for each instance.

The aggregate performance
J_{\text{curr}}=\texttt{Aggregate}({J^{(i)}})
is then compared to the previous iteration’s performance
J_{\text{prev}}
. If no improvement is observed, we assume convergence and terminate the loop. Otherwise, we identify the
k
worst-performing instances (i.e., those with the lowest
J^{(i)}
values) as
\mathcal{D}_{\text{fail}}
, and prompt the LLM to refine the current program
f^{(t)}
based on this feedback. The revised program
f^{(t+1)}
is expected to address the identified issues while preserving correct behavior elsewhere.

From an optimization perspective, IR can be viewed as a discrete, non-gradient-based search procedure over the space of executable programs. Each refinement step attempts to improve a program
f^{(t)}
by minimizing an implicit loss function, which is captured via task-specific evaluation metrics, over a finite dataset of grid instances. The feedback-driven update acts as a heuristic gradient, guiding the LLM to generate a new program
f^{(t+1)}
that corrects previous failures while maintaining performance on successful instances. While analytically not an optimizer, IR approximates iterative function minimization in a symbolic space, guided by performance signals rather than gradients.

3
Experimental setup

We evaluate our proposed framework on two benchmarks: the GRASP dataset
[
48
]
and three tasks from MiniGrid
[
11
]
. They are chosen for their structured 2D grid environments, which can be easily converted into LLM prompts (Appendix
A.3
).

Evaluation Benchmarks

The GRASP benchmark is a spatial planning task that requires an agent to collect energy under different constraints. Each environment instance varies by movement type, carry limit, per-step energy cost, energy distribution, obstacles, and starting position, yielding 16,000 unique instances. Performance is measured by average energy collected within 20 steps, implicitly penalizing inefficient movement and suboptimal planning. In parallel, we evaluate the LLMs on three tasks from the MiniGrid benchmark:
Unlock, Door-Key
, and
Unlock-Pickup
. MiniGrid is a lightweight grid-based benchmark for spatial reasoning, navigation, and object interaction. The selected three tasks increase in complexity. For each task, we generate 1,000 instances and measure two metrics: the average reward and the average completion rate.

Prompting Strategies and Baselines

We evaluate the IPP framework using four prompting strategies:
Direct Generation, Pseudocode Extension, Step-by-Step,
and
Iterative Refinement
. We also compare it to four non-code-based planning and prompting baselines. Using the Chain-of-Thought (CoT) methods
[
59
]
, the model is prompted to reason through intermediate steps in natural language before outputting the full action plan. We also introduce a 2-Step CoT variant that splits the planning into two stages: the model first generates a partial action plan up to a defined midpoint, then completes it based on the updated environment. This approach reduces planning burden by dividing the task, enabling more focused and accurate reasoning at each stage.
Finally, we evaluate two simple programmatic baselines:
Random
and
Greedy
. The
Random
agent selects valid actions uniformly at random, serving as a lower bound. The
Greedy
agent follows a hand-coded, myopic policy based on immediate utility, offering a fast but potentially short-sighted comparison.

LLMs Evaluated

We evaluate our IPP framework using six LLMs, including both general-purpose LLMs and code-specialized ones. Specifically, we use the following: GPT-4o
[
34
]
, GPT-o1
[
35
]
, GPT-o3-mini
[
36
]
, Claude 3.7 Sonnet
[
5
]
, Gemini 2.5 Pro
[
16
]
, and DeepSeek-R1
[
2
]
. All models are accessed through the OpenRouter API

]
. Code for reproducing all experiments is available

Discussion and Limitations

Our experiments show that LLMs, when guided by a structured iterative process, can generate interpretable and reusable code-based planning policies, even on problems they find initially challenging. The proposed iterative programmatic planning (IPP) framework consistently improves task performance on both GRASP and MiniGrid benchmarks. Even models with a weak initial program benefit significantly from refinement, highlighting the value of execution-based feedback.

Our results demonstrate that both the structure of prompts and the choice of LLMs are critical to planning performance. While direct code generation works in simple scenarios, structured prompting strategies such as pseudocode extension and curriculum-based step-by-step prompting significantly improve outcomes on more complex tasks. For IR, improvements emerge within the first one or two refinement steps, indicating that the process is both effective and computationally efficient. However, LLMs’ response to IR varies. GPT-o1, Claude-3.7, and Gemini-2.5-Pro consistently benefit from our approach, whereas DeepSeek-R1 and GPT-4o sometimes show degraded performance.

A major advantage of IPP is the interpretability of its code-driven policies. Unlike black-box planners or reinforcement learning agents, the generated programs are human-readable and editable, allowing experts to inspect, debug, or adapt plans (see Appendix
A.2
for examples). This transparency is especially valuable in safety-critical domains like robotics. IPP is also more efficient than traditional prompting methods. While chain-of-thought requires inference for each instance, IPP produces a single reusable program, reducing API costs and latency. Rather than competing with reinforcement learning, our aim is to provide a lower-cost, interpretable alternative that can solve similar planning tasks without intensive environment interaction, making it suitable for real-time or resource-constrained applications.

One potential limitation of our framework is that it depends heavily on the language model’s own ability to understand the environment and task rules. While the grid-based setup is fairly simple, models can still make mistakes in tracking the agent’s state, recognizing environment-specific entities, or following task constraints. These mistakes can happen in more complex tasks or when new situations arise that the model hasn’t seen before. Although iterative refinement helps fix some of these problems, there is still no guarantee that the final code will work correctly in all cases. We note, however, that this also applies to RL-based policies.

Another limitation is the cost and time involved in generating and refining the code. The refinement process requires running the model multiple times, each time testing the program on a large number of task instances and asking the model to improve it based on performance. This can take time and compute, especially for harder tasks or when the initial code is far from correct. Also, the way the model uses performance feedback is not very precise. It only sees whether the program did better or worse overall, without knowing exactly what part of the code caused the problem. This can make the refinement less efficient and harder to apply to tasks where small mistakes matter a lot.

Related work

LLMs for Code Generation and Planning
LLMs have demonstrated significant capability in code generation and other code-related tasks, such as bug fixing and program testing
[
7
,
13
,
42
,
56
,
24
,
26
]
. This makes LLMs attractive for planning tasks, where structured reasoning, abstraction, and correct execution are critical. Recent frameworks use LLMs to generate and refine plans by combining high-level reasoning with feedback from control or execution.
[
3
,
32
,
54
]
. It has been shown that LLMs can translate natural language instructions into planning formalisms like PDDL
[
38
,
45
]
, or synthesize generalized planners that solve novel tasks via chain-of-thought reasoning and iterative debugging
[
43
]
. In embodied AI, LLM has been used to generate code that serves as executable policies for robot control
[
28
,
30
]
. This progress suggests the feasibility of using LLMs to produce interpretable and adaptive policies for real-world tasks.

However, much of the prior work has focused on generating action plans for specific instances, often assuming strong task priors. These methods typically emphasize plan generation over policy synthesis, and often lack mechanisms for generalization across varied problem settings. In contrast, our approach treats code as a reusable policy that can adapt to multiple instances within a task. We move beyond static plan generation and instead use LLMs to produce and improve executable programs based on observed performance.

Iterative Code Generation
Recent work on iterative code generation LLMs has shown significant progress in code quality and reliability through repeated cycles of feedback and correction
[
23
,
8
]
. More specifically, the SELF-REFINE framework showed that LLMs can iteratively improve their outputs by generating feedback and refining their own code, achieving up to 13% improvement
[
31
]
. Building on this idea, later approaches automate refinement using external signals such as execution feedback from test suites
[
17
]
, compiler diagnostics
[
6
]
, and preference-guided comparisons of successful versus failed generations
[
50
]
. Additionally, some research explores multi-agent and interactive refinement, where LLMs act as solvers, verifiers, or critics. This includes self-play for code and test generation
[
29
,
1
]
, critique-driven updates
[
62
]
, and counterexample-guided refinement in inductive synthesis
[
58
]
.

While prior work applies iterative methods to typical coding tasks like function completion or bug fixing, our approach extends this paradigm to planning. Instead of refining code for correctness, we use task-level metrics like energy or reward from failures to iteratively guide program generation. Our method improves entire policy programs that can handle a range of environments, not just small code pieces. Unlike traditional tools that use test cases, our framework treats code as a control policy and refines it based on real task performance.

import collections
import math

# --- Helper Functions ---

def is_valid(coord, grid_height, grid_width, grid):
"""Checks if a coordinate is within bounds and not an obstacle."""
r, c = coord
return 0 <= r < grid_height and 0 <= c < grid_width and grid[r][c] != "O"

def get_neighbors(coord, grid_height, grid_width, grid, move_directions):
"""Gets valid neighboring coordinates based on move directions."""
r, c = coord
potential_moves = []
# 4 directions
potential_moves.extend(
[
((r - 1, c), "UP"),
((r + 1, c), "DOWN"),
((r, c - 1), "LEFT"),
((r, c + 1), "RIGHT"),
]
)
# 8 directions (add diagonals)
if move_directions == 8:
potential_moves.extend(
[
((r - 1, c - 1), "UPLEFT"),
((r - 1, c + 1), "UPRIGHT"),
((r + 1, c - 1), "DOWNLEFT"),
((r + 1, c + 1), "DOWNRIGHT"),
]
)

valid_neighbors = []
for neighbor_coord, move_name in potential_moves:
if is_valid(neighbor_coord, grid_height, grid_width, grid):
valid_neighbors.append((neighbor_coord, move_name))
return valid_neighbors

def update_position(pos, move):
"""Calculates the new position based on a move action."""
r, c = pos
if move == "UP":
return (r - 1, c)
if move == "DOWN":
return (r + 1, c)
if move == "LEFT":
return (r, c - 1)
if move == "RIGHT":
return (r, c + 1)
if move == "UPLEFT":
return (r - 1, c - 1)
if move == "UPRIGHT":
return (r - 1, c + 1)
if move == "DOWNLEFT":
return (r + 1, c - 1)
if move == "DOWNRIGHT":
return (r + 1, c + 1)
return pos # Should not happen if move is valid

def find_path_bfs(from_coord, to_coord, grid, move_directions, move_cost):
"""
Finds the shortest path using Breadth-First Search (BFS).
Returns (list_of_moves, total_cost) or (None, float(’inf’)).
"""
grid_height = len(grid)
grid_width = len(grid[0])
queue = collections.deque(
[(from_coord, [])]
) # (coordinate, path_list_of_moves)
visited = {from_coord}

while queue:
current_coord, path = queue.popleft()

if current_coord == to_coord:
return path, len(path) * move_cost

for neighbor_coord, move_name in get_neighbors(
current_coord, grid_height, grid_width, grid, move_directions
):
if neighbor_coord not in visited:
visited.add(neighbor_coord)
new_path = path + [move_name]
queue.append((neighbor_coord, new_path))

return None, float("inf") # No path found

def solve_energy_game(
grid, start_pos, max_actions, capacity, move_cost=1, move_directions=4
):
"""
Solves the energy collection game.

Args:
grid (2-D list): The game grid represented as a 2D list of strings.
max_actions (int): Maximum number of actions allowed.
capacity (int): Maximum energy tokens the agent can carry.
move_cost (int): Cost per move action (default 1).
move_directions (int): 4 or 8 directional movement (default 4).

Returns:
list: A list of action strings performed by the agent.
Returns an empty list if the input grid is invalid.
"""
# --- Grid Parsing and Initialization ---

grid_height = len(grid)
grid_width = len(grid[0]) if grid else 0

start_pos = None
initial_energy_coords = set()
for r in range(grid_height):
for c in range(grid_width):
if grid[r][c] == "A":
start_pos = (r, c)
grid[r][c] = " " # Agent location is not a permanent fixture
elif grid[r][c] == "E":
initial_energy_coords.add((r, c))

if start_pos is None:
print("Error: Agent ’A’ not found in the grid.")
return []

current_pos = start_pos
remaining_actions = max_actions
current_holding = 0
# Score only counts energy at the start location (initially or dropped)
score = 1 if (start_pos in initial_energy_coords) else 0
action_list = []
# Use a copy of coordinates to track remaining energy
energy_coords = initial_energy_coords.copy()
if start_pos in energy_coords:
energy_coords.remove(
start_pos
) # Don’t try to collect from start location initially

print(
f"Starting Game: Max Actions={max_actions}, Capacity={capacity}, Start={start_pos}"
)
print(f"Initial Energy Count: {len(initial_energy_coords)}")
# --- Main Loop ---
while remaining_actions > 0:
best_trip_plan = None
max_trip_value = -1 # Using -1 to ensure any valid trip is better

# --- Evaluate Potential Trips ---
potential_targets = list(
energy_coords
) # Convert set to list for iteration

for e_coord in potential_targets:
# Check capacity *before* calculating paths
if current_holding >= capacity:
continue

# 1. Calculate cost from current position to energy E
path_to_e, cost_to_e = find_path_bfs(
current_pos, e_coord, grid, move_directions, move_cost
)

if path_to_e is not None:
# 2. Calculate cost from energy E back to start position
path_to_start, cost_to_start = find_path_bfs(
e_coord, start_pos, grid, move_directions, move_cost
)

if path_to_start is not None:
actions_take = 1 # Cost of TAKE action
actions_drop = 1 # Cost of DROP action
num_e_collected = 1 # Evaluating single E trips here
total_trip_actions = (
cost_to_e + actions_take + cost_to_start + actions_drop
)

# 3. Check Feasibility (Actions)
if total_trip_actions <= remaining_actions:
# Simple value: E’s collected per action. Higher is better.
# Add small epsilon to avoid division by zero if
# total_actions is 0 (shouldn’t happen here)
trip_value = num_e_collected / (
total_trip_actions + 1e-9
)

# 4. Select Best Feasible Trip
if trip_value > max_trip_value:
max_trip_value = trip_value
best_trip_plan = {
"target_e": e_coord,
"path_to_target": path_to_e,
"cost_to_target": cost_to_e,
"path_to_start": path_to_start,
"cost_to_start": cost_to_start,
"total_actions": total_trip_actions,
"collect_count": num_e_collected,
}
print(
f" Found potential trip to {e_coord}: "\
"Cost={total_trip_actions}, Value={trip_value:.2f}"
)

# --- Execute Best Trip or Finish ---
if best_trip_plan:
print(
f"Executing trip to {best_trip_plan[’target_e’]} "\
"(Cost: {best_trip_plan[’total_actions’]},"\
"Current Actions: {remaining_actions})"
)
target_coord = best_trip_plan["target_e"]

# Move to Target E
for move in best_trip_plan["path_to_target"]:
if remaining_actions < move_cost:
break # Cannot afford next move
action_list.append(move)
current_pos = update_position(current_pos, move)
remaining_actions -= move_cost
if (
remaining_actions < move_cost and current_pos != target_coord
): # Check if ran out before reaching target
print(" Ran out of actions before reaching target.")
break # Exit main loop if cannot complete action sequence

# TAKE Action (Check actions first)
if (
remaining_actions >= 1
and current_pos == target_coord
and target_coord in energy_coords
):
action_list.append("TAKE")
remaining_actions -= 1
current_holding += 1
energy_coords.remove(
target_coord
) # Remove E from available targets
print(
f" TAKE at {target_coord}. Holding: {current_holding}. "\
"Actions left: {remaining_actions}"
)

# Move back to Start
for move in best_trip_plan["path_to_start"]:
if remaining_actions < move_cost:
break # Cannot afford next move
action_list.append(move)
current_pos = update_position(current_pos, move)
remaining_actions -= move_cost
if (
remaining_actions < move_cost and current_pos != start_pos
): # Check if ran out before reaching start
print(" Ran out of actions before returning to start.")
break # Exit main loop

# DROP Action (Check actions and position first)
if (
remaining_actions >= 1
and current_pos == start_pos
and current_holding > 0
):
action_list.append("DROP")
remaining_actions -= 1
score += current_holding # SCORE UPDATED HERE
print(
f" DROP at {start_pos}. Score: {score}. "\
"Actions left: {remaining_actions}"
)
current_holding = 0
else:
# Could happen if ran out of actions exactly when arriving
# at start, or wasn’t at start
if current_pos != start_pos:
print(
f" Warning: Arrived somewhere else ({current_pos}) "\
"instead of start after return path."
)
if current_holding > 0:
print(
f" Warning: Failed to DROP {current_holding} energy."
)
# Continue loop if actions remain, but energy wasn’t dropped.
# Or break if no actions left
if remaining_actions <= 0:
break

else:
# Failed TAKE (no actions, or not at target, or E already gone somehow)
if remaining_actions < 1:
print(f" Cannot TAKE at {target_coord}, no actions left.")
elif current_pos != target_coord:
print(
f" Cannot TAKE, not at target {target_coord} (at {current_pos})."
)
elif target_coord not in energy_coords:
print(
f" Cannot TAKE at {target_coord}, E is already gone."
)
break # Critical failure in trip execution

else:
# No feasible trips found with remaining actions
print("No more feasible trips found.")
break # Exit main loop

# --- Final Return if Holding Energy ---
if (
current_holding > 0
and remaining_actions > 0
and current_pos != start_pos
):
print(
f"Attempting final return to base with {current_holding} energy "\
"(Actions left: {remaining_actions})"
)
path_home, cost_home = find_path_bfs(
current_pos, start_pos, grid, move_directions, move_cost
)

if (
path_home is not None and (cost_home + 1) <= remaining_actions
): # +1 for DROP
print(f" Executing final return path (Cost: {cost_home + 1})")
# Execute return path
for move in path_home:
if remaining_actions < move_cost:
break
action_list.append(move)
current_pos = update_position(current_pos, move)
remaining_actions -= move_cost

# Final Drop (Check position and actions again)
if remaining_actions >= 1 and current_pos == start_pos:
action_list.append("DROP")
remaining_actions -= 1
score += current_holding
print(
f" Final DROP successful. Final Score: {score}. "\
"Actions left: {remaining_actions}"
)
current_holding = 0
else:
print(
f" Final return failed (Actions left: {remaining_actions}, "\
"Position: {current_pos}). Energy lost."
)
pass
else:
print(
f" Cannot execute final return (Not enough actions or no path)."
)
pass

elif (
current_holding > 0
and current_pos == start_pos
and remaining_actions >= 1
):
# If ended loop at start but still holding, perform final drop if possible
print(
f"Performing final DROP at start (Actions left: {remaining_actions})"
)
action_list.append("DROP")
remaining_actions -= 1
score += current_holding
print(
f" Final DROP successful. Final Score: {score}. "\
"Actions left: {remaining_actions}"
)
current_holding = 0

print(f"--- Game Over ---")
print(f"Final Position: {current_pos}")
print(f"Final Actions Remaining: {remaining_actions}")
print(f"Final Energy Held: {current_holding}")
print(f"Final Score (Energy at {start_pos}): {score}")
return action_list

The above shows the result of direct generation by the Gemini-2.5-pro. The code is a simple greedy search that takes round trips around the grid, collecting exactly 1 energy token each time. It selects the energy token for each round trip greedily by picking the one that is closest. But this code confuses movement costs with the total number of actions allowed, which results in reasonable performance when the movement cost is 0, but a negative score when the movement cost is positive, causing the average performance to be negative.

def navigate_to(grid, current_pos, current_direction, target_pos):
"""
Find the shortest path from current_pos to adjacent cell of target_pos.

Returns:
Dict containing actions, final position and direction
"""
# Implementation of A* pathfinding
from heapq import heappush, heappop

def heuristic(pos1, pos2):
# Manhattan distance
return abs(pos1[0] - pos2[0]) + abs(pos1[1] - pos2[1])

# Find positions adjacent to target
adjacent_positions = []
for d in ["UP", "RIGHT", "DOWN", "LEFT"]:
adj_pos = get_adjacent_position(target_pos, d)
if is_valid_position(grid, adj_pos) and grid[adj_pos[0]][
adj_pos[1]
] not in ["WALL", "DOOR", "BOX", "KEY"]:
adjacent_positions.append(adj_pos)

if not adjacent_positions:
return {
"actions": [],
"final_pos": current_pos,
"final_direction": current_direction,
}

# Start A* search
open_set = []
heappush(open_set, (0, current_pos, current_direction, []))
closed_set = set()

while open_set:
_, pos, direction, path = heappop(open_set)

if pos in closed_set:
continue

closed_set.add(pos)

# If we’ve reached an adjacent position to target, return the path
if pos in adjacent_positions:
return {
"actions": path,
"final_pos": pos,
"final_direction": direction,
}

# Try all four directions
for d in ["UP", "RIGHT", "DOWN", "LEFT"]:
orient_results = orient_to_direction(direction, d)
new_direction = orient_results["final_direction"]
new_pos = get_position_after_move(pos, new_direction)

if (
is_valid_position(grid, new_pos)
and new_pos not in closed_set
and grid[new_pos[0]][new_pos[1]]
not in ["WALL", "DOOR", "BOX", "KEY"]
):

new_path = path.copy()
new_path.extend(orient_results["actions"])
new_path.append("MOVE")

priority = len(new_path) + heuristic(new_pos, target_pos)
heappush(open_set, (priority, new_pos, new_direction, new_path))

# If no path is found, return empty
return {
"actions": [],
"final_pos": current_pos,
"final_direction": current_direction,
}

grid, current_pos, current_direction, target_pos, door_unlocked=False

"""
Find a path to a position adjacent to target_pos.
Returns:
Dict containing actions, final position and direction

if is_adjacent(current_pos, target_pos):
return {
"actions": [],
"final_pos": current_pos,
"final_direction": current_direction,
}

# Use BFS to find the shortest path
from collections import deque

queue = deque(
[(current_pos, current_direction, [])]
) # (pos, direction, actions)
visited = {(current_pos, current_direction)}

while queue:
pos, direction, actions_so_far = queue.popleft()

# Check if we’re adjacent to target
if is_adjacent(pos, target_pos):
return {
"actions": actions_so_far,
"final_pos": pos,
"final_direction": direction,
}

# Try all possible movements from current position
for turn_action, new_dir in [
([], direction),
(["RIGHT"], turn_right(direction)),
(["LEFT"], turn_left(direction)),
(["RIGHT", "RIGHT"], turn_right(turn_right(direction))),
]:
# Apply turn

new_actions.extend(turn_action)

new_pos = get_position_after_move(pos, new_dir)

# Check if the move is valid

grid[new_pos[0]][new_pos[1]] == ""
or (door_unlocked and grid[new_pos[0]][new_pos[1]] == "DOOR")
)

move_actions = new_actions.copy()
move_actions.append("MOVE")

visited.add((new_pos, new_dir))
queue.append((new_pos, new_dir, move_actions))

# If no path is found, return empty

"actions": [],
"final_pos": current_pos,
"final_direction": current_direction,
}

IF directions_num == 4:
directions = ["LEFT", "RIGHT", "UP", "DOWN"]
ELSE:
directions = ["LEFT", "RIGHT", "UP", "DOWN", "UPLEFT", \

actions_taken = [] # List to keep track of actions taken for backtracking
all_action = [] # List to store the full sequence of actions

# Move the agent in a random direction 6 times and collect energy
FOR i FROM 1 TO 6:
direction = RANDOM_CHOICE(directions)
MOVE_AGENT(agent, direction)
actions_taken.APPEND(direction)
all_action.APPEND(direction)
TAKE_ENERGY(agent)
all_action.APPEND(’take’)

# Backtrack by reversing the path taken
FOR direction IN REVERSE(actions_taken):
opposite_direction = GET_OPPOSITE_DIRECTION(direction)
MOVE_AGENT(agent, opposite_direction)
all_action.APPEND(opposite_direction)

# Drop all collected energy
DROP_ALL_ENERGY(agent)
all_action.APPEND(’drop’)

RETURN all_action

FUNCTION GREEDY_SOLVE(grid, start_position, is_diagonals_allowed, max_actions):
actions = []
current_position = start_position
actions_remaining = max_actions
while actions_remaining > 0:
# Perform Breadth First Search (BFS) to find the nearest energy token
nearest_energy_position, path = find_nearest_energy_bfs(
grid, current_position, is_diagonals_allowed
)
if nearest_energy_position is None:
# No more energy tokens available in the grid
break
path_length = len(path)
# Find the number of steps required to return to the start
# by backtracking in the same path to reach here
steps_needed_to_return = len(
[action for action in actions if action not in [’TAKE’, ’DROP’]]
)
# If there is not enough steps to go to the nearest energy token
# and come back to the start, return to start and end the trip
# The +2 is for the TAKE and DROP to be performed
if 2*path_length + steps_needed_to_return + 2 > actions_remaining:
# Actions to backtrack the same path taken to reach here
return_actions = return_to_start(actions)
actions.extend(return_actions)
actions.append(’DROP’)
return actions
# The remaining steps allow going to the nearest energy token before
# going back to start
for direction in path:
if actions_remaining <= 0:
break
move_agent(direction)
actions.append(direction)
actions_remaining -= 1
actions.append(’TAKE’)
actions_remaining -= 1
return actions

Guidelines:

•

The answer NA means that there is no societal impact of the work performed.

•

If the authors answer NA or No, they should explain why their work has no societal impact or why the paper does not address societal impact.

•

Examples of negative societal impacts include potential malicious or unintended uses (e.g., disinformation, generating fake profiles, surveillance), fairness considerations (e.g., deployment of technologies that could make decisions that unfairly impact specific groups), privacy considerations, and security considerations.

•

The conference expects that many papers will be foundational research and not tied to particular applications, let alone deployments. However, if there is a direct path to any negative applications, the authors should point it out. For example, it is legitimate to point out that an improvement in the quality of generative models could be used to generate deepfakes for disinformation. On the other hand, it is not needed to point out that a generic algorithm for optimizing neural networks could enable people to train models that generate Deepfakes faster.

•

The authors should consider possible harms that could arise when the technology is being used as intended and functioning correctly, harms that could arise when the technology is being used as intended but gives incorrect results, and harms following from (intentional or unintentional) misuse of the technology.

•

If there are negative societal impacts, the authors could also discuss possible mitigation strategies (e.g., gated release of models, providing defenses in addition to attacks, mechanisms for monitoring misuse, mechanisms to monitor how a system learns from feedback over time, improving the efficiency and accessibility of ML).
