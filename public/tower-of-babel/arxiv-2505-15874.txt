Text-to-Pipeline: Bridging Natural Language and Data Preparation Pipelines


Abstract
Data preparation (DP) transforms raw data into a form suitable for downstream applications, typically by composing operations into executable pipelines. Building such pipelines is time-consuming and requires sophisticated programming skills. If we can build the pipelines with natural language (NL), the technical barrier of DP will be significantly reduced. However, constructing DP pipelines from NL instructions remains underexplored. To fill the gap, we introduce Text-to-Pipeline , a new task that translates NL data preparation instructions into DP pipelines. Furthermore, we develop a benchmark named PARROT to support systematic evaluation. To simulate realistic DP scenarios, we mined transformation patterns from production pipelines and instantiated them on 23,009 real-world tables collected from six public sources. The resulting benchmark comprises ~18,000 pipelines covering 16 core DP operators. We evaluated cutting-edge large language models on PARROT and observed that they only solved 72.86% of the cases, revealing notable limitations in instruction understanding and multi-step reasoning. To address this, we propose Pipeline-Agent , a stronger baseline that iteratively predicts and executes operations with intermediate table feedback, achieving the best performance of 76.17%. Despite this improvement, there remains substantial room for progress on Text-to-Pipeline . Our data, codes, and evaluation tools are available at https://anonymous.4open.science/r/Text-to-Pipeline .

Constructing such a benchmark poses several challenges: First, pipelines must be valid and faithfully aligned with NL instructions. Second, NL should capture diverse and realistic intent. Third, operator sequences must be grounded in real table semantics. To address these challenges, we design a five-stage synthesis framework. We then generate intent-aligned NL instructions using LLMs and refine them to reflect natural, human-like expression. Each DSL program is compiled into executable backend code, enabling automated evaluation. Finally, we perform multi-phase validation involving six PhD-level human experts to ensure consistency between instructions and programs and verify correctness through execution results.

3
Benchmark Construction

3.1
Task Definition

We define
Text-to-Pipeline
as the task of synthesizing executable, multi-step data preparation pipelines from natural language instructions over input tables. The data pipelines are symbolic programs defined over a domain-specific language (DSL), which can be compiled into different backend codes.

Problem Setup.

Let
\mathcal{X}
denote the space of input tables,
\mathcal{Y}
the space of output tables,
\mathcal{L}
the space of natural language instructions, and
\mathcal{P}
the space of DSL. Each instance is associated with a reference output table
y\in\mathcal{Y}
, which reflects the expected transformation result given an instruction and input.
Given an instruction
\ell\in\mathcal{L}
and an input table
x\in\mathcal{X}
, the objective is to learn a mapping
f:\mathcal{L}\times\mathcal{X}\rightarrow\mathcal{P}
that yields a symbolic program
p=f(\ell,x)
, which can be compiled and executed to produce an output
\hat{y}
:

\hat{y}=\texttt{Exec}(c,x)\quad\text{where }c=\texttt{Compile}(p).

(1)

Here,
\texttt{Compile}(p)
the compiled executable code,
Exec
denotes the execution engine (e.g., Pandas or SQL), and
\hat{y}
is expected to equivalent to the reference output
y
, either semantically or structurally.
In summary, each instance of this
Text-to-Pipeline
can be represented as a five-tuple
(x,\ell,p,c,y)
.

Pipeline Structure.

Each program
p\in\mathcal{P}
is represented as a left-to-right chain of
k
symbolic operators:
p=o_{1}\circ o_{2}\circ\dots\circ o_{k}
, where each operator
o_{i}\in\mathcal{O}
is drawn from a core set covering common DP actions:

\mathcal{O}=\{\texttt{groupby},\texttt{sort},\texttt{join},\texttt{fillna},\texttt{filter},\dots\}.

(2)

Each operator
o_{i}
is parameterized by structured arguments (e.g., column names, aggregation functions). For a complete list of the 16 supported operators, refer to Sec.
4
.
Despite its modular design, synthesizing such pipelines remains highly non-trivial. The space of valid operator sequences grows combinatorially with length, and each step is constrained by schema compatibility, parameter validity, and cross-step dependencies. Moreover, subtle interactions among operators (e.g., column renaming before aggregation) can significantly affect program correctness and execution outcomes.

Why DSL over Direct Code.

Compared to generating Pandas code directly, DSL offers three key advantages:
(1)
Stable structure
: DSL uses a fixed set of operations with clear parameter formats, avoiding the syntactic variance of Pandas (e.g., multiple ways to filter or group data). This improves model learnability and consistency.
(2)
Backend flexibility
: DSL can be compiled to Pandas, SQL, or Spark, making it adaptable to different runtime environments. In contrast, Pandas ties the output to Python execution.
(3)
Better planning and verification
: DSL supports step-wise reasoning, schema validation, and error tracing. It enables fine-grained evaluation (e.g., operator accuracy) and is easier to synthesize at scale. Experiments further confirm this choice, showing consistent performance advantages over direct Pandas and SQL generation (see Sec.
4
).

Evaluation Metrics.

We employ three primary metrics to provide a multifaceted view of model performance, evaluating both execution correctness and program structure fidelity.

•

Execution Accuracy (EA)
: Given an input table
x
and a generated program
\hat{p}
, we execute
\hat{p}
to obtain
\hat{y}=\texttt{Exec}(\hat{p},x)
. EA measures the proportion of samples where
\hat{y}\overset{\star}{=}y
, i.e., the predicted output
\hat{y}
matches the ground truth
y
up to canonical equivalence (e.g., row/column permutations, floating-point tolerance):

\text{EA}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{I}(\hat{y}_{i}\overset{\star}{=}y_{i}),

where
N
is the number of test samples, and
\mathbb{I}(\cdot)
is the indicator function.

•

Program Validity (PV)
: The proportion of generated programs
\hat{p}
that are syntactically valid and executable without runtime errors, regardless of output correctness:

\text{PV}=\frac{1}{N}\sum_{i=1}^{N}\mathbb{I}(\texttt{Valid}(\hat{p}_{i})),

where
\texttt{Valid}(\hat{p}_{i})
returns true if
\hat{p}_{i}
compiles and executes successfully.

•

Operator Accuracy (OA)
: The proportion of correctly generated operators in the sequence, regardless of the order of operations. For each generated program
\hat{p}=[\hat{o}_{1},\dots,\hat{o}_{k}]
and ground truth program
p=[o_{1},\dots,o_{k}]
, OA is computed as:

\text{OA}=\frac{1}{N}\sum_{i=1}^{N}\frac{|\hat{p}_{i}\cap p_{i}|}{|p_{i}|},

where
|\hat{p}_{i}\cap p_{i}|
denotes the number of correctly generated operators at each position.

Stage 2: Operator Chain Construction.

To capture realistic transformation behaviors, we collect 1,200 data pipeline scripts from open-source data science repositories (e.g., Kaggle notebooks, GitHub ETL pipelines), extracting transition patterns to construct an empirical transition matrix
\mathbf{P}\in\mathbb{R}^{|\mathcal{O}|\times|\mathcal{O}|}
that models co-occurrence probabilities in practical pipelines (see App.
A.5
for details). We define a DSL with 16 core operators, categorized into
Data Cleaning
,
Data Integration
,
Structural Reconstruction
, and
Assisted Operations
(see Tab.
8
). Operator chains are sampled via a Markov process
robert1999monte
, where the initial operator is drawn uniformly and subsequent steps are selected according to
\mathbf{P}
, conditioned on schema and history. Schema validity is enforced (e.g., joins require shared keys), and the chain length
k
is sampled from a truncated geometric distribution over
[1,8]
. To control task complexity, we adopt a three-level difficulty scheme based on program length (see App.
C.6
for definitions and examples). This construction strategy ensures that the resulting pipelines are diverse, executable, and reflective of real-world DP scenarios across varying levels of reasoning difficulty. A summary of the sampling process is provided in Algo.
1
.

Stage 3: Instruction Generation.

Given input-output preview (10 rows) and operator chains, we generate semantically aligned natural language instructions in two steps. First, we prompt an LLM (e.g., GPT-4o) to generate schema-aware pipeline descriptions grounded in
\{x,y,p\}
. Then, we apply style-controlled refinement to convert the structured draft into fluent, user-centric instructions. We provide 10 in-context demonstrations to anchor operator-language mappings and ensure semantic preservation. The details of the demonstration can be referred to App.
A.4
. This matrix guides the construction of realistic operator chains and reflects common transformation motifs such as
select
–
filter
–
groupby
(see Fig.
3
, right).

Stage 4: Rule-Based Code Compilation.

Each DSL
\{o_{i}\}
is deterministically compiled into executable Pandas code via a rule engine. The compiler fills parameter templates and maintains a running schema state across steps to guarantee correct argument resolution and type-safe execution. Specifically, after applying each operator, the schema is updated via an operator-specific rule
\delta(o_{t},\mathcal{S}_{t})\rightarrow\mathcal{S}_{t+1}
, where
\mathcal{S}_{t}
represents the current column names and types. This schema propagation mechanism supports early validation of column dependencies (e.g., ensuring join keys exist, or that aggregations are applied to numeric fields) and helps prevent execution failures. It also enables compatibility checks for multi-table operations (e.g., schema alignment for joins and unions). Our code templates are modular and extendable to SQL or Spark with minimal effort. Full specifications of schema propagation are provided in App.
A.6
.

Stage 5: Multi-phase Validation.

To ensure quality and reliability, we perform both automatic and human-in-the-loop validation. First, we execute the compiled code
c
on the input table
x
and compare the result
\hat{y}
against the reference output
y
to verify execution correctness (
\hat{y}\overset{\star}{=}y
). Second, we assess instruction fidelity by checking semantic alignment between the natural language instruction and the underlying operator chain
\{O_{i}\}_{i=1}^{k}
. This is done via a two-stage strategy: (1) LLM-based consistency scoring using zero-shot classification prompts, and (2) manual review.
For the latter, we recruited six graduate-level experts (MSc/PhD students in data science and NLP) to review a stratified sample of 3,000 instances, scoring each on instruction accuracy, operator coverage, and semantic clarity. The inter-annotator agreement reached 91.4% (Cohen’s
\kappa
= 0.82), confirming label reliability. Only samples that pass both phases are retained. The resulting high-quality data serves as the development and test set. Additionally, to assist human experts in reviewing the data, we further designed a data visualization platform (see App.
D
). All implementation details can be found in App.
A
.

5.1
Experimental Setup

We conduct a comprehensive evaluation of various models on the
PARROT

Text-to-Pipeline

LLM Baselines.

To establish a comprehensive performance baseline on
PARROT
, we evaluate a diverse set of LLMs, encompassing both zero-shot inference capabilities of proprietary models and the performance of fine-tuned open-source models. These models represent the current state-of-the-art in code generation and natural language understanding:
(1)
Zero-shot LLMs:
We utilize several leading API-based models, including GPT-4o
openai2023gpt
, GPT-4o-mini
openai2023gpt
, Gemini-2.5-Pro
reid2024gemini
, and DeepSeek-V3
liu2024deepseek
. These models are prompted with the task instruction and table schema without any task-specific fine-tuning.
(2)
Fine-tuned LLMs:
We fine-tune a series of strong open-source code generation models: Qwen2.5-Coder-1.5B
hui2024qwen2
, Qwen2.5-Coder-3B
hui2024qwen2
, and Qwen2.5-Coder-7B
hui2024qwen2
. These models are trained on the
PARROT

PARROT
benchmark, to adapt them specifically to the
Text-to-Pipeline

Structured Generation Approaches.

We evaluate three distinct target output formalisms for generating executable data pipelines to understand their efficacy in representing and synthesizing complex transformations:
(1)
Text-to-Code (Pandas)
: Direct generation of executable Pandas code.
(2)
Text-to-SQL
: Generation of SQL statements, assessing the adaptability of SQL-centric approaches to broader data preparation tasks not typically addressed by SQL.
(3)
Text-to-Pipeline
: Our primary approach, where models generate operation sequences in our DSL, subsequently compiled to Pandas. The DSL is architected for modular planning, type safety through enforcement, and schema-aware validation, aiming for a more robust generation pathway.

Planning and Agent-based Approaches.

To assess the capabilities of more sophisticated reasoning strategies for multi-step pipelines, we evaluate several planning and agent-based paradigms:
(1)
Tool Calling API (One-shot)
qin2024tool
: LLMs are instructed to generate the full multi-step execution plan or program for a
PARROT
task in a single pass, simulating a direct tool-use scenario.
(2)
Plan-and-Solve
wang2023plan
: This approach first generates a high-level operation plan (e.g., a sequence of operations), then synthesizes the executable program based on that plan.
(3)
Chain-of-Tables
wang2024chain
: This strategy involves evolving and manipulating intermediate tabular states throughout the reasoning chain to guide the transformation process for tasks from
PARROT
.
(4)
Pipeline-Agent
: Our proposed ReAct-style
yao2023react
agent that iteratively predicts an operation, executes it on the current table, and reflects on the result. By leveraging intermediate states, it enables context-aware planning and handles schema evolution in long-horizon
PARROT
tasks.

Implementation Details.

For zero-shot LLM evaluations, we utilized consistent prompt templates. Each prompt included:
(1) a clear definition of the
Text-to-Pipeline
task.
(2) the input table (column names and data types).
(3) 10 sample rows from the input table to provide context on data values, and
(4) the natural language instruction. We used a temperature of 0.7 for deterministic or near-deterministic outputs for evaluation purposes.
For fine-tuned models, we performed supervised fine-tuning on the
PARROT

(3)

Case Study.

We examine a failure case, shown in App.
E.8
, where the model is instructed to perform a series of operations: extract relevant columns (
select
), filter rows by value (
filter
), aggregate results (
groupby
), and finally rename a column (

“Extract the ‘Transaction ID’, ‘Buyer Name’, and ‘Amount Paid’ columns from table_1. Filter the rows where ‘Amount Paid’ is greater than 1000. Then, group the data by ‘Buyer Name’ and calculate the total sum of ‘Amount Paid’ for each buyer. Finally, rename ‘Amount Paid’ to ‘Total Payment’.”

The ground truth program includes all four operations in the specified order. However, the model-generated pipeline omits the initial
select
step and begins directly with
filter
, followed by
groupby
and
rename
. This mistake illustrates multiple compounding challenges:
(1)
Compositional Reasoning.
The model fails to recognize the structural dependency between early-stage column pruning and subsequent transformations. The omission of
select
results in a program that potentially operates on extraneous or irrelevant fields, which may lead to execution failures or incorrect aggregation.
(2)
Instruction Grounding.
While the model correctly identifies the need to apply
filter
,
groupby
, and
rename
, it misinterprets the scope of the task—particularly the requirement to operate only over a subset of columns. This suggests a shallow parsing of the intent rather than a grounded mapping to executable semantics.
(3)
Schema Evolution Awareness.
Downstream operations assume a schema transformed by previous steps. By skipping
select
, the model introduces a mismatch between the assumed and actual schema, particularly impacting the correctness of the
groupby
and
rename
steps, which depend on
Amount Paid
being cleanly isolated and unambiguous.

Conclusion

We propose
Text-to-Pipeline
, a novel task that maps NL instructions to executable data preparation pipelines, and introduce
PARROT
, a large-scale benchmark built from real-world tables and production-inspired transformation patterns. Empirical results show that current LLMs struggle with compositionality and schema evolution, motivating the need for more robust reasoning. To this end, we present
Pipeline-Agent
, an execution-aware baseline that iteratively plans and reflects over intermediate states. Beyond these contributions, our work advocates a paradigm shift in data preparation, from manual processing to intelligent, agent-driven systems. By grounding pipeline synthesis in NL and execution feedback, we pave the way toward autonomous DP agents capable of planning, adaptation, and self-correction, moving closer to fully automated data management.

Appendix A
Details of Automatic Pipeline Data Synthesis Framework

In this section, we provide additional details of our automatic pipeline data synthesis framework, including implementation details, dataset collection, DSL-to-code compilation, operator transition modeling, and schema propagation.

A.1
Implementation Details

Natural language instructions are generated, refined, and verified using
GPT-4o-mini
via OpenAI’s API (
gpt-4o-mini-2024-07-18
), with a temperature of 0.7 to ensure deterministic outputs. The prompt typically includes the task description, table schema, and sampled rows (up to 10) to provide contextual grounding. Additionally, we adopt a few-shot prompting format with three curated demonstrations at the hard level to control the generation style during instruction refinement. All prompts used for data synthesis are listed in App.
E.9
. The process of data synthesis is conducted on a compute cluster equipped with 64-core AMD EPYC CPUs. Synthesis of the full dataset takes approximately 16 hours with three threads. We implement automated validation to filter out ill-formed programs. Each synthesized DSL program is compiled and executed on its corresponding table; results are compared against the reference output to verify execution success and type compatibility. Invalid programs are resampled up to three times.
The full codebase, datasets, and evaluation tools are available at
https://anonymous.4open.science/r/Text-to-Pipeline
. This setup ensures scalable, high-quality synthesis of instruction-program pairs grounded in realistic data preparation scenarios.

A.2
Data Collection

Our benchmark data is sourced from six widely used public datasets. These sources offer a broad range of real-world tables across different domains, enabling realistic scenarios for our model. Below, we provide a brief introduction to each source.

Spider

[
46
]
is a dataset developed by researchers at Yale University. It is a large-scale benchmark annotated by humans, designed to advance the development of semantic parsing and natural language interfaces for databases.. It comprises 10,181 natural language questions and 5,693 unique complex SQL queries across 200 databases spanning 138 diverse domains. Each database contains multiple tables, requiring models to understand intricate relationships and perform multi-step reasoning. A distinctive feature of Spider is its emphasis on cross-domain generalization: the training and testing sets contain different databases and SQL queries, compelling models to adapt to new schemas and query patterns.

Bird

[
25
]
is a large-scale benchmark. It is specifically constructed to evaluate the capabilities of large language models in real-world database interface scenarios. The dataset includes over 12,751 natural language questions paired with SQL queries across 95 large databases, reflecting realistic business intelligence (BI) tasks. These databases are derived from actual industry schemas, featuring varied table structures, real-world naming conventions, and complex join conditions. Bird emphasizes practical cross-domain reasoning, requiring models to handle diverse and noisy schema representations, ambiguous question formulations, and the need for context-aware SQL generation. Unlike synthetic or simplified benchmarks, Bird aims to mirror the challenges faced in enterprise environments, making it a critical resource for assessing the robustness and generalizability of Text-to-SQL systems.

Auto-Pipeline

[
44
]
is a dataset developed by researchers at the University of Chicago and Microsoft Research. It is a benchmark designed to advance the automation of complex data preparation workflows by leveraging reinforcement learning and search techniques. The dataset encompasses 716 real-world data pipelines, systematically curated from GitHub repositories and commercial vendors. These pipelines encompass a variety of operations, including string transformations and table manipulations such as joins, group-bys, and pivots. A distinctive feature of Auto-Pipeline is its adoption of the "by-target" paradigm, wherein users specify the desired output schema instead of providing step-by-step examples. This approach necessitates models to infer the sequence of transformations required to achieve the target schema, often relying on implicit table constraints like functional dependencies and keys to constrain the search space.

Auto-Tables

[
27
]
is a benchmark dataset designed to evaluate systems that automatically synthesize multi-step transformations to convert non-relational tables into standard relational formats without requiring input-output examples. The dataset comprises 244 real-world test cases collected from user spreadsheets and online forums, reflecting common challenges in data preparation tasks. These cases necessitate complex restructuring operations—such as unpivoting, transposing, and filling missing values—that are often difficult for users to program manually.

TableBench

[
42
]
is a comprehensive benchmark designed to evaluate Table Question Answering (TableQA) systems, emphasizing complex reasoning over tabular data. It encompasses 886 question-answer pairs across 18 subcategories within four major domains: Fact Checking, Numerical Reasoning, Data Analysis, and Visualization. This dataset was meticulously curated to bridge the gap between academic benchmarks and real-world applications, reflecting the intricate reasoning required in practical scenarios.

LakeBench

[
8
]
is a large-scale benchmark designed to evaluate methods for discovering joinable and unionable tables within data lakes. It includes over 16 million real tables—approximately 1,600 times larger than existing datasets—and spans more than 1 TB in storage size. The benchmark features over 10,000 queries with ground truth annotations, covering binary classification, regression, and multi-label classification tasks. These queries were meticulously labeled over 7,500 human hours, encompassing diverse categories such as government data from CKAN, Socrata, and the European Central Bank. LakeBench serves as a comprehensive resource for evaluating the effectiveness, efficiency, and scalability of table discovery methods in data lakes.

A.3
DSL-to-Code Compilation

We implement a compiler to translate DSL programs into executable code. The process maps each operator to backend-specific templates, ensuring correct parameter binding, schema handling, and code generation. Below, we outline the workflow and backend support.

Compilation workflow.

Given a DSL program
p=[o_{1},o_{2},\dots,o_{k}]
, the compiler performs the following:

1.

Parameter binding:
For each operator
o_{i}
, extract its parameters and map them to template slots;

2.

Schema-aware quoting:
Apply column name escaping (e.g.,
_quote(col)
) to handle special characters;

3.

Code merging:
Concatenate code lines using a left-to-right chaining convention (e.g., method chaining in Pandas);

4.

Execution trace annotation:
Optionally insert line comments to denote DSL operator source (useful for debugging).

Backend support.

While Pandas is the primary backend in this paper, the compiler is modular and supports alternate targets such as SQL or Spark by switching template registries. Each backend maintains an operator-to-template mapping, enabling flexible deployment without changing the symbolic layer.

Example.

Given the DSL sequence:

[

}

{

"ascending": false
}

]

⬇

.

(

)[

]

.

()

.

()

.

(

=
’sales’
,

This translation preserves the semantics of the symbolic pipeline while ensuring correctness and interpretability.

A.5
Operator Transition Matrix

To guide the construction of realistic and semantically coherent operator chains, we build an operator transition matrix
\mathbf{P}\in\mathbb{R}^{|\mathcal{O}|\times|\mathcal{O}|}
, as introduced in Sec.
3.2
. This matrix models the empirical likelihood of transitioning from one operator
o_{i}
to another
o_{j}
, capturing common patterns observed in real-world data pipelines. Below, we introduce the details of the construction of the operator transition matrix.

•

Source corpus.
We collect 1,200 data transformation scripts from open-source data science repositories (e.g., Kaggle notebooks, GitHub ETL pipelines)
[
27
,
44
,
43
]
, focusing on Pandas and SQL-based workflows.

•

Operator normalization.
Scripts are parsed into abstract syntax trees (ASTs), from which high-level transformation calls are extracted and mapped to our DSL operator set via rule-based normalization (e.g.,
drop_duplicates

\rightarrow

dedup
).

•

Transition statistics.
For each script, we record observed consecutive operator pairs
(o_{i}\rightarrow o_{j})
and compute transition frequencies. These are normalized to conditional probabilities using:

P(o_{j}\mid o_{i})=\frac{\text{Count}(o_{i}\rightarrow o_{j})+\alpha}{\sum_{k}\text{Count}(o_{i}\rightarrow o_{k})+\alpha|\mathcal{O}|}

where
\alpha=0.5
is the Laplace smoothing coefficient to mitigate sparsity in low-frequency transitions.

•

Semantic constraints.
To prevent invalid or semantically implausible operator chains, we impose heuristic transition filters based on operator categories and schema dependencies. For instance, transitions like
groupby

\rightarrow

dropna
are pruned unless
dropna
targets non-aggregated columns, while
sort
is allowed to follow most aggregation or integration steps.

•

Sampling integration.
During Markov-based operator chain synthesis, we use
\mathbf{P}
as a dynamic prior, further modulated by table-specific features (e.g., presence of missing values, column types) and previously sampled operator context to promote coherent and executable transformation workflows.

This transition matrix supports structurally diverse yet realistic program generation, ensuring sampled pipelines reflect common data preparation practices while preserving semantic feasibility.

A.6
Schema Propagation Mechanism

To ensure semantic correctness and column dependency integrity throughout the execution of a transformation program, we implement a schema propagation mechanism that tracks and updates the table schema after each operator in the DSL sequence.

•

Schema representation.

At each step
t
in a pipeline
p=[o_{1},o_{2},\dots,o_{k}]
, the schema is represented as a structured object:

\mathcal{S}_{t}=\{(c_{i},\tau_{i})\}_{i=1}^{n}

where
c_{i}
is the column name and
\tau_{i}
is its data type (e.g.,
int
,
str
,
float
,
datetime
).

•

Operator effect rules.

Each DSL operator is associated with a transformation rule
\delta:\mathcal{S}_{t}\rightarrow\mathcal{S}_{t+1}
that specifies how it modifies the schema. For example:

–

groupby
introduces new aggregation columns and may drop non-grouped fields.

–

join
merges two schemas, with name disambiguation (e.g., suffixes
_x
,
_y
) if overlapping columns exist.

–

rename
updates column names while preserving types.

–

dropna
does not modify schema but may remove rows.

–

pivot
restructures column names based on index and column values.

•

Propagation strategy.

During operator chain construction or execution, we maintain a running schema
\mathcal{S}_{t}
:

\mathcal{S}_{t+1}=\delta(o_{t},\mathcal{S}_{t})

This enables type-checking, operator compatibility filtering, and parameter validation at each stage.

•

Error prevention.

Before executing each operator
o_{t}
, we validate whether its required arguments (e.g., column names, aggregation targets) are present and well-typed in
\mathcal{S}_{t}
. If the check fails, the pipeline is rejected or resampled.

•

Multi-table support.

For multi-source operations (e.g.,
join
,
union
), we track a set of schemas
\{\mathcal{S}_{t}^{(1)},\mathcal{S}_{t}^{(2)},\dots\}
and apply compatibility checks across tables (e.g., matching join keys, union column alignment).

This schema propagation mechanism ensures that each transformation step operates on a valid, context-aware schema, supporting both program correctness and dynamic code generation across execution backends (e.g., Pandas, SQL).

Appendix B
Broader Discussion

Limitation

The main limitations of our PARROT benchmark lie in instruction generation and schema coverage.
(1)
Instruction Generalization
: Our natural language instructions are constructed through LLM-based synthesis with controlled diversity and refinement, resulting in high lexical and structural coverage (as shown in Sec.
4
). While this design captures a wide range of realistic user intents, there may still exist extremely informal, ambiguous, or domain-specific expressions in the wild that fall outside our constructed distribution. Addressing such tail cases typically requires direct user-authored inputs or context-rich interactions, which are beyond the scope of current benchmark automation.
(2)
Schema and Language Bias
: Our benchmark is built on 23,000+ real-world tables from public sources, which include diverse domains and formats. However, some domains (e.g., English-speaking) are overrepresented, and tables with non-English headers or code-mixed schemas, though present, remain a minority. As a result, models trained on
PARROT
may exhibit lower robustness when encountering underrepresented languages. Nevertheless, these limitations have minimal impact on the benchmark’s primary goal: enabling standardized, large-scale evaluation of executable data preparation pipelines from natural language instructions under realistic table semantics.

Social Impact

PARROT
is developed with the goal of advancing natural language interfaces for data preparation, ultimately reducing the technical barriers faced by non-programmers. By grounding transformation logic in symbolic pipelines and ensuring execution validity, our benchmark promotes transparency and debuggability in LLM-driven systems. In addition, we exclusively use publicly available datasets and exclude any sensitive or personal data during construction. Instructions are synthetically generated and manually validated to avoid offensive content, misinformation, or privacy risks. We believe the probability of our benchmark posing adverse effects related to safety, fairness, or misuse is negligible. Instead, it offers a valuable testbed for future research into controllable, interpretable, and inclusive automation of data workflows.

Appendix E
Details of Experiments

E.1
Zero-shot LLMs

To maintain evaluation consistency across models, we employed a unified prompt format, the details of which are provided in
E.10
. This schema-aware, instruction-driven, and output-targeted approach was consistently applied unless otherwise specified.

Inference Environment

To ensure consistency and reproducibility across all experiments, we set the temperature of the LLM to 0.7 and limit the maximum output length to 4000 tokens. For models that do not support the
temperature
parameter (e.g.,
o3-mini
and
o4-mini
), this setting is omitted.

E.2
Fine-Tuning of LLMs

To better align large language models (LLMs) with data preparation tasks, we conducted supervised fine-tuning on a set of recent instruction-tuned LLMs, including
Qwen2.5-Coder-1.5B-Instruct
,
Qwen2.5-Coder-3B-Instruct
, and
Qwen2.5-Coder-7B-Instruct
. The goal is to improve the model’s ability to interpret natural language instructions and generate accurate transformation plans.

Training Environment

Training is conducted on a server equipped with four NVIDIA RTX 4090 GPUs. We utilize
torchrun
with 4 GPUs per run. The models are trained using mixed-precision (bf16), with a batch size of 2 for the 1.5B model and 1 for the 3B and 7B models. Training runs for 3 epochs, with a maximum sequence length of 4096. We employ Parameter-Efficient Fine-Tuning (PEFT) to reduce computational cost. DeepSpeed is used to manage memory and optimize performance.

E.3
Text-to-Pandas

The Text-to-Pandas module is designed to convert natural language instructions into executable pandas transformation code. It leverages carefully engineered prompts to guide large language models in interpreting user intents and generating accurate, efficient pandas scripts.

This approach centers on prompt engineering—designing clear, context-aware prompts that help the model accurately understand user intent and generate precise Pandas code. The module detects the data operation type (e.g., filtering, grouping, pivoting) and converts natural language instructions into corresponding Python code based on the data schema, lowering the barrier for complex data transformations.

Detailed prompt templates are provided to facilitate reproducibility and further development (see Sec.
E.11
).

E.4
Text-to-SQL

To evaluate models in the Text-to-SQL setting, we simulate a realistic database-backed environment. All data used in our transformation tasks is stored in a relational database (SQLite), ensuring that the models operate over structured data with executable queries.

Database Construction.

We construct a normalized relational database that mirrors the tabular inputs used in the benchmark. Each table in the database is defined with an explicit schema including column names and data types. Where applicable, foreign key relationships are established to support multi-table joins. This setup ensures that the generated SQL can be directly executed for validation.

Prompt Template.

To support accurate and consistent code generation in the Text-to-Pandas module, we design structured prompt templates (see Sec.
E.12
) that pair natural language instructions with table schemas.

E.5
Agent-Based Methods

We evaluate three major classes of agent-based methods—Tool Calling Agent, Plan-and-Solving Agent, and Chain-of-Tables Agent—as described in Sec.
5.1
. To reduce redundancy, we omit high-level descriptions here and instead provide implementation and execution details for reproducibility.

Tool and Environment Setup.

Each data preparation operation is implemented as a callable tool (see
E.6
). Agents interact with these tools using LangChain’s
tool calling
. All agents are executed within a Python environment with access to the full table context (i.e., input, schema, partial states).

Tool Calling API.

This agent directly maps natural language instructions to tool calls via LLM reasoning. We use LangChain’s native tool calling support with GPT-4o, GPT-4o-mini, and DeepSeek-V3. The input to the agent includes the partial table preview, instructions, and tool schema documentation. Tool descriptions are standardized to ensure consistency across models.

Plan-and-Solve.

This agent follows a two-phase paradigm: it first prompts the LLM to generate a high-level transformation plan as a sequence of operations (e.g., filter → groupby → sort), and then executes each operation step-by-step via tool invocation.

Chain-of-Tables.

The Chain-of-Tables Agent operates by tracking and updating intermediate tabular states, enabling stepwise manipulation of evolving data frames. It is especially suited for multi-hop tabular tasks. We reuse the plan-execute-react loop similar to
[
40
]
, but adapt it to work with our DSL-based transformation layer rather than raw SQL.

E.6
Pipeline-Agent

We propose
Pipeline-Agent
, a unified framework for data preparation that integrates iterative reasoning and tool-based execution in a closed-loop interaction cycle. This design enables the agent to make step-by-step decisions, invoke appropriate tools, and leverage execution feedback to guide subsequent actions, thereby ensuring accurate and consistent transformation outcomes.

Specifically, we first adopt the ReAct framework
[
45
]
, enabling the agent to reason about intermediate table states and determine the next operation to apply. This reasoning is interleaved with execution, allowing the agent to refine its plan based on observed table changes.

We then define a set of modular tools, each corresponding to a specific data preparation operation such as
filter
,
groupby
,
sort
, or
pivot
. These tools share a standard interface (e.g.,
transform(df)
) and accept structured input arguments, making them readily callable by LLM-based agents.

Finally, Pipeline-Agent dynamically invokes these tools along its reasoning trajectory, forming a toolchain that adapts to the evolving table state. This tight coupling of reasoning and execution enables the agent to maintain a coherent transformation process, even in complex multi-step scenarios.

Comparison with Baseline Agents.

Unlike the Tool Calling API, which executes a one-shot instruction without considering intermediate states, or the Plan-and-Solve approach, which separates planning from execution, our Pipeline-Agent tightly integrates both aspects in a single loop. Compared to Chain-of-Tables, which focuses on static table reasoning, Pipeline-Agent emphasizes dynamic state tracking and adaptive tool chaining, making it more suitable for iterative table transformation tasks.

Tool Definitions and Interaction.

Each tool in the Pipeline-Agent is a self-contained module that encapsulates a particular transformation logic. Tools expose a unified interface for execution and are compatible with structured reasoning inputs from LLMs. During the agent’s reasoning process, these tools are dynamically selected and applied, enabling seamless integration into the closed-loop pipeline. The toolset spans essential operations such as filtering, grouping, sorting, pivoting, and more, supporting a wide range of data preparation needs.

E.7
Error Analysis

As shown in Fig.
14
,
type errors
consistently account for the largest proportion across all models, ranging from 41.2% (GPT-4o-mini) to 54.5% (DeepSeek-R1). These errors typically stem from applying transformations to columns with incompatible data types, such as aggregating over non-numeric fields or sorting categorical columns without conversion. Models with weaker schema-tracking capabilities (e.g., DeepSeek-R1/V3) exhibit higher type error rates.

Semantic errors
constitute the second largest category, with models like GPT-4o and Gemini-2.5-Pro showing around 27% semantic failures. These reflect incorrect or missing operations, broken logic chains, or hallucinated steps that deviate from the task intent. The relatively lower semantic error rates of DeepSeek models may indicate a conservative generation style, albeit at the cost of lower execution accuracy.

Column/index errors
are more prominent in GPT-o3/4-mini and Gemini-2.5-Pro, often resulting from misaligned references due to schema evolution (e.g., renaming or selection). This suggests limitations in maintaining coherent schema state across steps.

Attribute errors
(e.g., wrong aggregation function or sorting order) appear in 3%–7% of cases across models, indicating shallow mapping between instruction semantics and operator parameters.

Notably,
GPT-4o
demonstrates a more balanced error profile, with relatively lower type error rates and a higher proportion of semantic errors—implying its stronger capacity in basic type resolution but remaining challenges in compositional reasoning. In contrast,
DeepSeek-R1
shows a high concentration of type errors, suggesting brittle type inference.

Overall, these results highlight the
diverse failure modes
of different LLMs in
Text-to-Pipeline
, and emphasize the importance of schema tracking, operator grounding, and long-range reasoning in achieving robust program synthesis.

E.8
Case Study

This example presents a representative failure case encountered during zero-shot prompting with GPT-4o. The user instruction specifies a four-step transformation: (1) select three relevant columns, (2) filter rows based on a numeric threshold, (3) aggregate the results grouped by buyer, and (4) rename the resulting column for presentation. However, the predicted pipeline skips the initial
select
operation and begins directly with filtering.

While this omission may appear minor, it triggers a chain of downstream errors. First, the filter and groupby steps are applied over the full original schema, causing the inclusion of irrelevant fields such as
Product
. Second, due to the missing projection, records not intended for analysis, such as rows with values below the threshold or involving different aggregation semantics, are mistakenly retained in the final output. The resulting prediction not only introduces extra columns but also contains logically inconsistent rows (e.g., the buyer “Bob” appears with an amount below 1000, contradicting the filtering intent).

This case exemplifies several challenges specific to
Text-to-Pipeline
:

•

Instruction grounding
: The model fails to fully map the natural language intent to a faithful operator sequence, omitting the projection implied by “extract the columns.”

•

Schema evolution tracking
: Without the initial pruning, subsequent operations operate on a misaligned schema, which affects aggregation and renaming logic.

•

Multi-step reasoning
: The model struggles to anticipate how early-stage operations affect downstream validity, leading to cascading inconsistencies.

Such errors highlight the brittle nature of zero-shot pipelines when schema dependencies are not explicitly modeled. They also underscore the importance of symbolic alignment and intermediate validation, motivating the design of agent-based methods such as Pipeline-Agent that incorporate execution-aware reasoning and schema propagation during generation.
