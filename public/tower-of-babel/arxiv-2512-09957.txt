CloudFix: Automated Policy Repair for Cloud Access Control Policies Using Large Language Models
Bethel Hall, Owen Ungaro, William Eiers

Abstract
Access control policies are vital for securing modern cloud computing, where organizations must manage access to sensitive data across thousands of users in distributed system settings. Cloud administrators typically write and update policies manually, which can be an error-prone and time-consuming process and can potentially lead to security vulnerabilities. Existing approaches based on symbolic analysis have demonstrated success in automated debugging and repairing access control policies; however, their generalizability is limited in the context of cloud-based access control. Conversely, Large Language Models (LLMs) have been utilized for automated program repair; however, their applicability to repairing cloud access control policies remains unexplored. In this work, we introduce CloudFix, the first automated policy repair framework for cloud access control that combines formal methods with LLMs. Given an access control policy and a specification of allowed and denied access requests, CloudFix employs Formal Methods-based Fault Localization to identify faulty statements in the policy and leverages LLMs to generate potential repairs, which are then verified using SMT solvers. To evaluate CloudFix, we curated a dataset of 282 real-world AWS access control policies extracted from forum posts and augmented them with synthetically generated request sets based on real scenarios. Our experimental results show that CloudFix improves repair accuracy over a Baseline implementation across varying request sizes. Our work is the first to leverage LLMs for policy repair, showcasing the effectiveness of LLMs for access control and enabling efficient and automated repair of cloud access control policies. We make our tool Cloudfix and AWS dataset publicly available.



I
Introduction

Cloud compute systems allow administrators to write policies that specify access control rules, which specify how access to private data is governed. Policies are typically written in a convenient language, such as the Amazon Web Services (AWS) Identity and Access Management (IAM) policy language, allowing administrators to write their own policies. However, this is a tedious, complex, and often error-prone process. Moreover, policies must be modified on a regular basis due to the ever changing nature of cloud computing. Creating and maintaining policies is a challenging endeavor and often requires significant technical skills and domain expertise in ensuring access control is correctly implemented. This can potentially lead to smaller organizations or those without the proper resources to forgo best security practices in ensuring access privilege is kept to a minimum, and instead provide broad access in order to ensure their cloud computing services work as intended.

Cloud computing services often provide tools to assist administrators in writing and maintaining policies or monitoring access to resources (e.g., AWs IAM Access Analyzer, AWS IAM Policy Simulator, AWS Cloudtrail service). However, when policies do not function as they are intended, or must be modified to incorporate access to new services or resources, these tools are inadequate when administrators lack the technical expertise to use them. This is additionally compounded by the lack of automated approaches for creating or repairing policies, as existing techniques either do not extend to cloud access control policies or are restricted in the ways they repair policies

In this work, we take the first step towards leveraging Large Language Models for access control policy repair. Given a faulty or misconfigured access control policy and access control requests which must be allowed or denied by the policy, our approach repairs the policy so that it correctly classifies the given set of requests. We implement our approach in a tool called CloudFix and showcase its effectiveness in repairing AWS IAM access control policies. Additionally, we curate the first policy repair dataset for cloud access control policies and make it publicly available for future research endeavors. Specifically, we make the following key contributions:

•

We automate the access control policy repair process using an LLM-driven Fault-localization-guided approach.

•

We present the first integration of LLMs with SMT-based formal verification for repairing access control policies;

•

We experimentally show that our fault-localization techniques enable LLMs to repair faulty policies.

•

We release the public dataset for cloud policy repair and make the source code for CloudFix available on GitHub.

II
Overview and Background

In this work we focus primarily on access control policies written in AWS IAM policy language. However, the techniques we present in this work are not specific to the AWS IAM policy language and can be applied to any policy language.

II-A

Amazon Web Service Policies

An AWS IAM policy
P
is a declarative policy consisting of a list of statements describing how access is governed. Policies field access control requests which are either allowed or denied by the policy. An access control request is a tuple
(\delta,a,r,e)
where
\delta
is a specific principal performing the access,
a
is the action to be performed,
r
is the resource being accessed, and
e
is the set of environment variables within the request (e.g., IP address, current time, etc). A policy statement
S
is a 5-tuple (
Effect, Principal, Action, Resource, Condition
) where:

•

Effect
is either Allow or Deny

•

Principal
consists of a list of users or entities

•

Action
is a list of actions

•

Resource
is a list of resources

•

Condition
is an optional list of conditions further specifying how access is constrained

Initially, all requests are implicitly denied. An access control request is granted access if and only there is at least one statement within the policy which explicitly allows access and no statement in the policy explicitly revokes or denies access. The AWS policy language allows special characters to be used which represent broad access: the ’*’ wildcard character can be used to represent any string, while the ’?’ character can be used to represent any character. Additionally AWS allows identity-based policies which omit the Principal field.

Manual Policy Repair Process. Stage 1 shows an administrator authoring a policy while a user generates access requests. In Stage 2, a cloud evaluation engine validates these requests, correctly allowing one (s3:GetObject) but implicitly denying another (ec2:RunInstances) because no statement permits it. In Stage 3, the administrator manually interprets this feedback, adding a new Allow statement to the policy to fix the issue, and resubmits it for validation.

II-B

A Motivating Example

In real-world cloud computing, debugging and repairing access control policies are done collaboratively but largely manually. Administrators write policies in the AWS IAM consoles and attach them to users/roles, or use the IAM Policy Simulator, which still requires manual work. This prompts iterative manual debugging until the desired permissions are allowed and denied. A common yet risky solution for this is to craft overly broad permissions (e.g., action: s3: *) to temporarily prevent requests from being unintentionally denied and attempt to narrow the scope iteratively.

Figure
1
demonstrates how an AWS engineer identifies errors in the policy and attempts to repair it. The process has three states: in Stage 1, the Cloud Security Admin writes an access control policy that gives access to the principal to read any
s3
category and object across the account.
In the first request, the user is asking to read the object
newfile.txt
stored in the
s3

s3:GetObject

ec2

us-west-2

ec2:RunInstances
action on the resource
arn:aws:ec2:us-west-2:backend/logs
. These requests are stored in CloudTrail as access history logs and are accessible to the Admin. Next, the Admin examines the requests through the Cloud Engine to locate the failure points in the policy, as shown in Stage 2. The Cloud Engine validates and returns that the first request is correctly allowed, as the policy has an explicit statement that allows it, and the second request is implicitly denied since there is no statement allowing the request. In Stage 3, the Admin adds an explicit statement in the policy that allows the required request, which was initially denied by the policy. The Admin then uses the Cloud Engine to validate the repaired policy and deploys it.

This manual repair and validation process is tedious, time-consuming, and error-prone. Each time a user’s request is denied or overly allowed, the administrator must inspect the IAM policy line by line, trace the evaluation logic through the Cloud Engine, and cross-check the results against CloudTrail logs to understand why the policy denied or allowed the access request. Manually inspecting the policy to repair it requires redeploying and retesting the policy to confirm that intended requests are still allowed and denied. Moreover, this iterative process heavily relies on human reasoning and repeated trial and error; it becomes increasingly impractical as the number of users, policies, and requests grows.

III
CloudFix

In this section we introduce our policy repair framework CloudFix. The framework consists of four steps: (A) Goal Validation, (B) Fault Localization, (C) Prompt Generation, and (D) Repair Synthesizer. Figure
2
demonstrates the overall stages of the method. CloudFix operates over an input access control policy and request specification. The
Goal Validator
first evaluates the policy against the request specification: if all requests are correctly classified, the policy is considered correct and the framework returns the policy. Otherwise, the process proceeds iteratively. In each iteration, the faulty policy and the requests are fed into the
Fault Localizer
component that analyzes the failed requests and the current policy to identify statements that are responsible for misclassifications. These faulty statements, together with the policy and requests, are provided to the
Prompt Generator
, which produces an input prompt for the
Repair Synthesizer
. The
Repair Synthesizer
queries an LLM to generate a candidate policy as a potential repair. This candidate policy is validated against the requests by the
Goal Validator
. If the candidate policy correctly classifies all requests, then the policy has been completely repaired, and the algorithm terminates. Otherwise, the candidate policy becomes the new input to the next iteration of the loop. This process continues until a fully repaired policy is produced, or the iteration threshold is reached. Algorithm
1
presents the complete CloudFix algorithm.

III-B

Fault Localizer

Once the
Goal Validator
determines that a policy
\mathit{P}
is faulty (i.e., it misclassifies requests), then
\mathit{P}
is passed to the Fault Localizer to identify statements within it that misclassify the requests.
We define a request misclassification as allowing a request that is supposed to be denied and/or denying a request that is supposed to be allowed by the policy. We define three types of faults within the policy that are responsible for misclassifications:
case 1) faulty statements that explicitly allow requests which should be denied as per the request specification, case 2) statements that explicitly deny requests that should be allowed per the request specification, and case 3) requests which are implicitly denied yet should be allowed.
The process is shown in Algorithm
3
. Each misclassified request is analyzed with respect to the policy to determine the type of fault that incorrectly classifies it.

Given a policy
\mathit{P}
and a request set
\mathit{R}
, lines 4 - 17 in Algorithm
3
illustrate how we identify faulty statements within
\mathit{P}
. The
\mathrm{SMTSolver}
function determines the satisfiability of policy constraints against specific requests using the Z3 solver
[
4
]
for satisfiability checking and the Quacky tool for policy and request encoding.
For each misclassified request, to check if it falls into
case 1
,
\mathrm{SMTSolver}(r,s)
iteratively checks each allow statement
\mathit{s\in S^{+}}
to see if it allows request
\mathit{r}
by creating a minimal policy containing only that statement. Lines 7 and 8 show that if
\mathrm{SMTSolver}(r,s)
returns
\mathit{SAT}

\mathrm{SMTSolver}(r,P^{\star}\cup\{s\}))

\mathit{s}

\mathit{r}

is responsible for the incorrect denial of
\mathit{r}

Once the

In this work, we consider two types of prompts: Base and Fault Localization-Guided.

Base Prompt

This is the simplest prompt we employ to simulate a real-world scenario where an engineer has access only to a policy and requests. It consists of the policy that needs to be repaired in accordance with the must-allow and must-deny list specifications.

III-D

Repair Synthesizer (LLM)

We leverage an LLM to generate candidate repairs directly from misclassified requests and fault localization findings. The
Repair Synthesizer LLM
produces a candidate policy, which is then passed to the
Goal Validator
for verification. If the
Goal Validator
determines that the policy correctly classified the request specification, the policy will be returned as a successful repair. However, due to the complexity of the requests and the policies themselves, some faulty policies are difficult to fully repair in a single iteration. The repair cycle continues until the
Goal Validator
determines that the candidate policy correctly classifies the given must-allow and must-deny request specifications, or the predefined iteration threshold is reached. The candidate policy which achieved the highest classification accuracy is returned as a partially repaired policy.

IV
Dataset Collection and Request Generation

CloudFix works to repair cloud access control policies that are written in cloud access control languages. However there is currently no public dataset specifically curated for
policy repair
, which makes research in this area difficult. This is because policies model access control within organizations and if these policies were made public they would could create security vulnerabilities. To address this gap, we curate real-world AWS IAM policies from the
AWS re:Post
forum and make them available to the research community. An important component of policy repair is the availability of representative request sets, but obtaining such a dataset is non-trivial because AWS IAM request logs are also kept private. To overcome these gaps, we algorithmically generate synthetic requests directly from the structure of the policy by varying the proportions of must-allow and must-deny requests. Below, we discuss the details of dataset collection and request generation.

IV-A

Policy Collection

The policy collection process involves three steps: first scraping policies from public sources, then detecting and categorizing valid JSON policies, and finally normalizing and repairing formatting inconsistencies. To collect a sufficiently large dataset of IAM policies, we sourced user posts from
AWS re:Post
. In this community forum, AWS users share questions and answers regarding AWS services and
products. We specifically targeted posts containing IAM policies that either failed to function as
intended or required correction.
In total we scraped over 9,968 IAM-related posts. We then performed policy detection and categorization. Each post body was
scanned for JSON objects resembling IAM policies. Detection required identifying bracketed
structures containing keys such as Effect, Action, or Statement.
All collected policies were then tested for syntactic correctness using Quacky
[
8
]
, a quantitative policy analyzer.
Quacky revealed that many of the policies exhibited structural errors or formatting inconsistencies. To correct these issues, we implemented a naive syntactic repair tool to ensure we had a corpus of policies which adhered to standard IAM policy conventions.
In total, we collected 282 faulty policies (syntactically correct but needing to be repaired) and 45 repaired policies (policies that were community-accepted as repairing the original broken policy).

IV-B

Request Generation

Algorithm

shows our approach to automatically generating synthetic requests to evaluate our policy repair framework. We begin by extracting each element of the policy and then generate requests, making them 60% allowed and 40% denied. We include all elements of the policy (i.e., effect, action, resource, condition, and principal). To create a realistic repair, we add misclassified requests by selecting a subset of the truly allowed and/or denied requests and modifying either of the values in the policy keys to invert the expected effect(i.e., allow or deny). The SampleAllowed
(\mathcal{E},\lfloor 0.6n\rfloor)
function creates approximately 60% requests expected to be allowed, while

(\mathcal{E},n-|\mathcal{R}^{+}|)

From lines 24 - 31,

V
Experimental Design

The goal of our evalution is to answer the following research questions:

RQ1: Can CloudFix repair cloud access control policies?

RQ2: How effective is Fault Localization for policy repair?

RQ3: How does accuracy vary across LLMs with FL-guided Repair?

RQ4: How well do the repairs generated by CloudFix generalize to requests not seen during the repair process?

RQ5: Can CloudFix repair policies with requests generated from natural language descriptions of faulty policies?

V-A

Experiment Setup

All experiments were run using a Rocky Linux 9.3 computer cluster (Blue Onyx). Each job was allocated a single NVIDIA L40S GPU with 46 GB of memory, two Intel(R) Xeon(R) Platinum 8562Y+ CPU cores, and 251 GB of system RAM. All experiments were executed with a 64 GB memory limit and a single GPU per task.

V-B

Models

We evaluate our approach using four open-source instruction-tuned models of comparable size. Specifically, we used
CodeLLaMA-7B-Instruct
, a model trained for code synthesis and reasoning;
Granite-3.3-8B-Instruct
, an IBM model optimized for instruction following in software engineering tasks;
DeepSeek-Coder-7B-Instruct
, a model finetuned for code completion and reasoning, designed for software repair and program synthesis, and

Llama3.2-3B-Instruct
, an instruction-tuned text-only model that supports a maximum of 128K context window. We maintain similar prompts and model hyperparameters for all models used. All models were executed through Hugging Face’s transformers pipeline
[
25
]
.

V-C

Repair Approaches

We employ two repair approaches in our experiments. The first is a Baseline repair approach which uses a basic prompt to instruct the LLM to repair the policy. The Baseline receives the complete faulty policy, the requests that must be allowed and denied, and a generic repair instruction, where the model needs to identify faulty statements within the policy and repair them. The second is the Fault Localization guided approach, which is the crux of our framework and described in detail in Section
III
. We maintain the same user and system prompts for both approaches to ensure that the quality of the prompts does not confound the results.

Another important factor that influences repair accuracy is the size of the request. We use Algorithm
4
to generate
10
,
20
,
30
, and
50
request sizes. To increase the complexity of the requests, we ensure that each request targets a unique resource–resource-action-condition-principal pair. Furthermore, our dataset exhibits a higher proportion of must-allow requests compared to must-deny requests, as shown in Table
I
. This distribution reflects realistic cloud usage patterns where most access requests are operations that must be allowed by access control policies.

V-D

Evaluation Metric

Accuracy.
We evaluate our approach using accuracy, which is defined as the percentage of request specifications that are correctly classified by the policy.
\text{Accuracy}=\frac{R_{c}}{R_{\text{total}}}\times 100\%
,
where
R_{c}
is the number of correctly classified requests and
R_{\text{total}}
is the total number of requests. We define three accuracy categorys:
100% (complete repair)
,
80-99% (moderate repair)
, and
<80% (failed repair)
.

Iteration,
I
.
We evaluate the total number of iterations the repair takes to reach a
complete
,
moderate
, or
failed repair
. In our experiments,
I
is set to 5.

Time.
We measure the total repair duration, including the time that an LLM takes to generate a repair and the time the SMT solver takes to validate the repair across all iterations until either 100% is achieved or the max
I
is reached.

RQ1: Can CloudFix repair cloud access control policies?

Our first research question aims at testing whether our framework can automatically repair faulty policies such that all requests in the given specification are correctly classified.

Setup.
To answer this question, we evaluate our framework on our dataset of 282 AWS IAM policies. For each policy, we generate must-allow and must-deny requests of
10

20

Results.
Table

We see a performance degradation for 50 request sizes in both Baseline and Fault Localization, where the Baseline repairs 0 policies completely, while Fault Localization generates 7 completely repaired policies. The results demonstrate that FL consistently outperforms the Baseline as the request size increases, and gracefully degrades as Baseline performance dramatically decreases for higher request sizes.

We further performed a statistical significance analysis on the obtained results using a two-tailed

RQ4: How well do the repairs generated by CloudFix generalize to requests not seen during the repair process?

The goal of this experiment is to test whether our repair framework can identify and generalize to semantically similar access patterns rather than overfitting to specific requests. A motivating example for this experiment involves multiple requests targeting similar resources,

(s3:getObject,arn:aws:s3:::category/
data-1
)

(s3:getObject,arn:aws:s3:::category/
data-2
)

(s3:getObject,arn:aws:s3:::category/
data-3
)

which could be grouped together to allows access to

(s3:getObject,arn:aws:s3:::category/
data-*
)

Enumerating similar requests this way has undesired effect. It challenges the LLM’s ability to generalize. As a result, simpler models might try to patch the policy by adding a specific rule for each file. While this works to correctly classify the provided requests, it fails for semantically related other requests and requires the models to reason more.
Therefore, we test whether LLMs can repair policies in a way that generalizes to semantically similar access requests.

Setup.
To answer RQ4, we evaluate the generalizability of CloudFix. To enumerate the requests, we first pick one misclassified request from the request sets of each policy and enumerate its resource into 10 new variants, similar to those conforming to the pattern shown above. This generated a total of 20 requests. Next, for each policy, we generated the repair using both the Baseline and FL-guided approaches on these 20 requests. To evaluate the repair on unseen requests, we then synthesized 15 variant requests from the same requests and evaluated whether the repaired policies correctly classified these unseen but semantically similar requests.

Results.
Figure
6
presents the repair and generalization accuracy for both approaches. The left panel shows that FL-guided repair achieves 82.8% (172 complete repairs) accuracy compared to the Baseline’s 79.9% (147 complete repairs), showing a 2.9% improvement over the initial 20.9% accuracy of the faulty policies. We can see from the right panel of the figure that the Baseline achieves 79.9% accuracy on unseen request variants, and FL achieves 84.9%. Interestingly, the Baseline generalization accuracy matches its repair accuracy (79.9%). This suggests that when the Baseline generates complete repairs, it produces repairs that generalize well to semantically similar requests. The FL approach shows a stronger generalization, achieving 84.9% on variants compared to its 82.8% repair accuracy.

RQ5: Can CloudFix repair policies with requests generated from natural language descriptions of faulty policies

Finally, we test whether CloudFix can completely repair policies using requests generated by LLMs.

Setup.
To answer RQ5, we select 10 faulty policies from our dataset. As mentioned in Section IV, our AWS IAM dataset contains 45 policies that have

faulty policy
: the original, incorrect policy posted by a user experiencing access control issues,
ground truth policy
: the corrected policy provided by an AWS Cloud Engineer in the forum, and
user intent
: the natural language description of the request specifications or problem as described by the user. We first use GPT-5, accessed via it’s web interface, to synthesize requests. We follow the following procedure: for each policy, we prompted the model with the
user intent
,
faulty policy
, and
ground truth policy
and instruct it to generate 5 up to 10 valid requests. The criteria to generate a valid request were that they must be misclassified by the faulty policy, correctly classified by the ground truth, and encapsulate the user’s intent. We then used Algorithm
2
to validate that the requests were misclassified by the faulty policy and correctly classified by the ground truth policy. To validate if the requests align with the user’s expressed intent, we manually verified to ensure correctness. Next, we used
CodeLlama-7B-Instruct
to repair the 10 faulty policies with a maximum of 5 iterations and a target accuracy of 100%.

Results.
Figure
7
shows that the Baseline approach achieves 85.2% repair accuracy, while FL achieves 86.4%, both showing improvements over the 46.7% initial accuracy. This demonstrates that our framework can be used to generate policy repairs using requests generated by LLMs from natural langauge descriptions of the users intents.

VI
Discussion and Threat to Validity

In this study, our main contribution is to leverage LLMs for policy repair and showing that Fault Localization-guided prompt enables LLMs to repair with improved accuracy and time, particularly for moderately complex request sizes (RQ1, RQ2). Our results show that the choice of LLMs plays a key part in performance, as demonstrated in RQ3, with CodeLlama-7B-Instruct achieving the highest complete repair. Results obtained in RQ4 show that LLMs can be used to repair policies that generalize to unseen, semantically similar requests. We further showed that LLMs can be used to synthesize access requests, which can be used to repair faulty access control policies (RQ5).
We noticed the baseline repair took significantly more time for all repairs than FL, as shown in Table
IV
. This was often because the Baseline was attempting to enumerate the requests in an attempt to repair the policy, which often resulted in generating a failed policy (<80%). Our study did not use a timeout because we planned to focus on fairly evaluating the repair capability of our framework. Finally, our study relied on access control policies we curated from
AWS re:Post
, and algorithmically generated requests based on the structure of these policies; however, these policies may not fully capture the nuanced access control policies in real-world. The generalizability of our findings is constrained by the size of requests. We observed a degradation of repair accuracy and an increment of the overall repair time as the number of requests went up to 50, where FL generated only 7 complete repairs. Future work should consider techniques to maintain better accuracy for higher request sizes.

Beyond repair accuracy of our framework, the practicality of CloudFix hinges on its computational efficiency. Our analysis in Table
IV
shows that the FL-guided approach is significantly time-efficient than the baseline counterpart. However, more than 99% of the repair time was LLM inference time; therefore, future work should investigate the trade-off between accuracy and efficiency in model selection.

VIII
Conclusion

In this work, we introduced CloudFix, the first automated framework to integrate LLMs with Formal Methods for access control policy repair. Manually repairing policies is error-prone and time-consuming. We address this problem by developing a framework to automatically create policy repairs with LLMs and by enhancing their reasoning capabilities with targeted repairs, enabled by Fault Localization.
Our evaluation on a curated dataset of 282 real-world AWS policies showed that LLMs enhanced with Fault Localization can be used to repair cloud access control policies with significantly improved accuracy than the baseline approach.
