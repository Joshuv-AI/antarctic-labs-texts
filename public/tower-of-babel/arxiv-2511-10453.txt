Reasoning About Intent for Ambiguous Requests
Irina Saparina, Mirella Lapata, mlap@inf.ed.ac.uk

Abstract
Large language models often respond to ambiguous requests by implicitly committing to one interpretation. Intent misunderstandings can frustrate users and create safety risks. To address this, we propose generating multiple interpretation-answer pairs in a single structured response to ambiguous requests. Our models are trained with reinforcement learning and customized reward functions using multiple valid answers as supervision. 1 1 1 https://github.com/saparina/intentRL Experiments on conversational question answering and semantic parsing demonstrate that our method achieves higher coverage of valid answers than baseline approaches. Human evaluation confirms that predicted interpretations are highly aligned with their answers. Our approach promotes transparency with explicit interpretations, achieves efficiency by requiring only one generation step, and supports downstream applications through its structured output format.

Introduction

Ambiguity poses a fundamental challenge for large language models
(LLMs). Users routinely omit details either for the sake of brevity or
unintentionally
(
48
;
22
)
,
creating requests with multiple plausible interpretations (see the
examples in Table
1
, top row). LLMs often
respond with a single answer, implicitly committing to one
interpretation without acknowledging alternatives.
Beyond frustrating users who had a different meaning in mind, this
behavior poses safety risks as defaulting to a single interpretation
can lead to irreversible actions
(
20
)
. LLMs can
strategically exploit ambiguities, e.g., by deliberately
misinterpreting scalar quantifiers or bracketing in logical statements
to advance their own goals over user intentions

4
. Ambiguity also presents a challenge for
reasoning models, which can expend thousands of tokens on incorrect
interpretations, simultaneously wasting computational resources and
reinforcing the original error.

Prior work has explored different strategies for handling ambiguous
inputs, each with distinct trade-offs

(
35
)
.
Clarification questions explicitly engage users to resolve ambiguity,
but require additional interaction rounds and depend on users
providing clarifying responses. We illustrate this approach in
Table
1
for conversational question
answering and text-to-SQL parsing. An alternative is to give a
longer answer that includes multiple interpretations within a single
response
(
32
)
. Model outputs in this case
tend to be verbose, lacking explicit interpretations (see the examples
in Table
1
). As a result, the answers are
difficult to parse for downstream applications and potentially
overwhelming for users. Moreover, for certain ambiguity types (e.g.,
attachment ambiguity), interpretations may be mutually contradictory. In
domains like SQL generation, there may be no natural way to express a
unified response (e.g., for interpretations requiring different table
structures).

In this work, we propose a structured alternative, namely generating
multiple plausible answers, each paired with an explicit
interpretation (Table
1
, bottom). This
format requires a single generation step while producing outputs
that are easy to parse and use for downstream applications, e.g., in
agentic systems where branching across interpretations can be
beneficial.
Moreover, it generalizes beyond textual answers to any output type,
including code generation and API calls, while allowing users to
quickly identify their intended answer.
Recognizing that ambiguity relates to the broader problem of pluralistic
alignment (i.e., generating responses that reflect diverse
perspectives and interpretations;
30
), our approach
promotes
overton pluralism
by predicting multiple
interpretations within one answer. Methods embracing

distributional pluralism
rely on parallel samples and often
struggle to produce substantially different outputs

(
46
)
. Instead, we generate
interpretations sequentially within one response (where subsequent
interpretations are conditioned on previous ones), without changes to sampling parameters
or confidence
calibration.

Teaching models to handle ambiguity is challenging due to the lack of
suitable supervision. While ambiguity is pervasive in natural language,
humans can effortlessly communicate without explicitly clarifying
their intent. The most readily available supervision signal comes from
annotator disagreement, which manifests as multiple answers for a
single instance. Other forms of annotation, such as clarifications or explicit interpretations, are expensive and difficult to
obtain at scale. Building on the success of reinforcement learning
under sparse supervision
(
29
)
, we frame ambiguity
resolution as reasoning about
what
to answer rather than

how
: we encourage the model to reason about user intent, entertaining different interpretations of the input before committing
to an answer.
We train a reasoning model through reinforcement
learning with specialized reward functions that only require answer
annotations as supervision. For ambiguous inputs, we optimize for

recall
to maximize the coverage of interpretations. For
unambiguous inputs, we optimize for
precision
to avoid
generating spurious alternatives. This dual objective teaches the
model to enumerate interpretations when necessary
and
to
recognize when a question has a single intent.

We evaluate our approach on both verifiable and non-verifiable tasks, including text-to-SQL generation and conversational question answering. Experimental results show that our model effectively handles unambiguous and ambiguous cases, generalizing to out-of-distribution data while generating diverse, plausible answers with high coverage and meaningful interpretations. By teaching models to reason about user intent before answering, we move toward more robust, user-aligned LLMs that embrace rather than obscure ambiguity.

Related Work

Ambiguity in Question Answering

Ambiguity has gained significant attention in question answering as there is growing awareness that many questions can have multiple valid answers (see
35
for a comprehensive overview).
AmbiQA
(
18
)

was one of the first large-scale benchmarks to explicitly annotate multiple answers for individual questions, expanding on NaturalQuestions
(
13
)
. The open-domain QA setting has prompted numerous retrieval-augmented generation techniques (e.g.,
17
).

ASQA
(
32
)
extends AmbiQA by requiring long-form answers that cover multiple interpretations in a single response. While this format is intuitive, it poses challenges for evaluation and practical use due to the lack of explicit structure in the answers.
1
first infer multiple interpretations and then generate long-form answers through prompting.
We make interpretations explicit by generating structured interpretation–answer pairs.

9
explore clarification questions as a disambiguation strategy in conversational QA,
and more recently
3
introduced a preference optimization method that generates clarification questions for ambiguous instances and direct answers for unambiguous ones.
In contrast, our approach handles both cases in a single turn.

Ambiguity in Semantic Parsing

Ambiguity also presents challenges for semantic parsing tasks
(
25
;
15
;
19
;
33
)
. The realization that standard datasests often provide a single interpretation when multiple queries are plausible
(
23
;
8
)
, has motivated the development of benchmarks that include multiple SQL queries per input
(
2
;
27
)
or interactive scenarios with clarification questions
(
7
;
12
)
. Various approaches have been proposed to handle ambiguous queries including via counterfactual examples
41
, specialized decoding strategies
(
2
)
, two-stage methods that first generate interpretations and then answers
28
, and interactive generation of clarification questions
6
. Unlike multi-stage approaches, our method generates all plausible interpretations and corresponding SQL queries in one response.

Diversity in Model Outputs

LLMs have been recently shown to exhibit narrow behaviors and strong biases in tasks where many valid responses are possible
(
27
;
42
;
46
;
38
)
. Fine-tuning has been proposed as way of shifting LLM output from peaked to diffuse distributions
47
as well as post-training

31
.
45
found that explicitly enumerating possible answers with their probabilities via prompting improves diversity. Our structured interpretation–answer pairs can be viewed as a form of such enumeration, but with explicit interpretations rather than probability estimates.

3
Reasoning about User Intent

Our approach trains a reasoning model to explicitly consider user
intent before generating answers, producing outputs that enumerate
plausible interpretations of ambiguous inputs along with their
corresponding answers (see Table
1
bottom).

3.1
Problem Formulation

A question is ambiguous if it admits multiple distinct
interpretations that lead to different answers. Given some input
consisting of optional context
c
(e.g., a passage in
conversational QA or a database schema in text-to-SQL generation;
see Table
1
) and a question
q
, the
model must produce a set of interpretation-answer pairs
\{(i_{1},a_{1}),\dots(i_{m},a_{m})\}
. Each interpretation
i_{k}
explicitly
disambiguates the question by specifying what is being asked, while
a_{k}
is the corresponding answer for
interpretation
i_{k}
. For example, “The question refers to the
husband’s name” in Table
1
is one possible
interpretation of the ambiguous question “What is his name?” which
corresponds to the answer “Mike Comrie”.

We expect a maximum of five interpretation-answer pairs, which we find
represents the majority of ambiguity cases in existing datasets. In
theory, questions could have more interpretations, but at
that scale other approaches such as clarification
questions may be more appropriate than exhaustive enumeration.
In practice, the questions are often grounded in specific contexts, which naturally constrain the space of plausible interpretations.
In unambiguous cases, we expect a single interpretation-answer pair,
with the interpretation being identical to the original question or a
paraphrase that makes the intent even more explicit.

3.2
Model Training

Our model is trained on examples annotated with gold answers

\mathcal{A}=\{\hat{a_{1}},\dots\hat{a_{n}}\}
, where
n=1
for
unambiguous and
n>1
for ambiguous questions. These annotations are
easier to obtain compared to interpretations or clarification
questions; for example, they emerge naturally when multiple annotators
disagree on the answers they provide.

We instruct the model to first analyze the input for potential
ambiguities and then generate structured output consisting of
interpretation-answer pairs. We design a task-agnostic prompt template
that can be easily adapted to other tasks by modifying only the
context format and task-specific instructions (e.g., answer style
constraints). The prompt is given in Appendix
A
.
We generate interpretation-answer pairs sequentially.
Thanks to the autoregressive nature of language models, each subsequent
interpretation is conditioned on previously generated
interpretations and answers. This encourages diversity across
interpretations as well as semantic alignment between interpretations
and their corresponding answers.

We train our model using DAPO (Decoupled Clip and Dynamic Sampling
Policy Optimization
44
), a reinforcement learning
algorithm based on GRPO (Group Relative Policy Optimization;

29
). DAPO
extends GRPO with decoupled clipping parameters that enhance exploration and
dynamic sampling that filters out prompts with uniform outcomes to
maintain effective gradients (see Appendix
B
for
the formulas).

We design
reward functions
to optimize different objectives
for ambiguous versus unambiguous inputs. We extract the set of predicted answers
\mathcal{P}
from the model’s
output and compare it against the gold answer set
\mathcal{A}
, where
all answers are distinct by construction. For each predicted
answer
p\in\mathcal{P}
and gold answer
\hat{a}\in\mathcal{A}
we
compute a
similarity
score
sim(p,\hat{a})
where the
specific type of similarity function is task dependent.

For tasks like text-to-SQL whose output can be objectively verified,

sim(p,\hat{a})=1
if execution results are the same, and
sim(p,\hat{a})=0
otherwise. For tasks like question answering whose outputs are harder to verify,
we use soft similarity metrics. In experiments, we adopt F1 score
based on word overlap, however, any other word similarity function
could be used. Let
S_{ij}=sim(p_{i},\hat{a}_{j})
denote a matching
matrix, and
\mathcal{M}
the set of one-to-one matches between
predicted and gold answers. We compute optimal assignments between

\mathcal{P}
and
\mathcal{A}
using the Hungarian algorithm:

M^{*}=\text{argmax}_{M\in\mathcal{M}}\sum_{(i,j)\in M}S_{ij},

which is
efficient given that both sets are small (recall that we five interpretations maximum). For verifiable tasks with binary similarity (e.g., text-to-SQL),
M^{*}
reduces to exact matching.

For ambiguous questions (
|\mathcal{A}|>1
), our reward function is

recall
:

R_{\text{recall}}=\dfrac{1}{|\mathcal{A}|}\sum_{(p_{i},\hat{a}_{j})\in M^{*}}sim(p_{i},\hat{a_{j}})

which measures how many distinct valid interpretations are covered by
the model, rewarding more complete responses.

For unambiguous questions (
|\mathcal{A}|=1
), our primary objective
is
precision
:

R_{\text{precision}}=\dfrac{1}{|\mathcal{P}|}\sum_{(p_{i},\hat{a}_{j})\in M^{*}}sim(p_{i},\hat{a_{j}})

which penalizes the model for generating spurious interpretations.

Experimental Setup

4.1
Datasets and Evaluation Metrics

The only requirement for training our model is a dataset with multiple valid
answers per input. We focus on two such datasets that represent different evaluation
scenarios: Abg-CoQA
(
9
)
, a conversational question
answering dataset (non-verifiable outputs) and Ambrosia

(
27
)
, a text-to-SQL parsing benchmark (verifiable
outputs). Both datasets include contextual information (stories for
Abg-CoQA, database schemas for Ambrosia), making the ambiguity
resolution more challenging and realistic: models must validate their
interpretations against the provided context.
See examples in Table
1
and dataset statistics in
Table
2
. Descriptions of ambiguities are provided in Appendix
C
.

Abg-CoQA

(
9
)
is a conversational question answering dataset. The input consists of a passage, one or two
previous conversation turns, and a question that can be ambiguous,
leading to different answers. The dataset provides clarification
questions
but does not include explicit interpretations. Abg-CoQA
covers different types of ambiguity, the majority being coreference.

9
measure similarity between predicted and gold
answers using word overlap (macro-averaged F1). To account for
different wordings within the same interpretation, each prediction is
compared against three gold answers, and the maximum score is taken;
these scores are then averaged across gold answers.
This metric favors coverage over precision because
Abg-CoQA treats disambiguation and answer generation as separate
tasks.
For a more comprehensive evaluation, we also use an LLM-based judge to
assess both recall and precision. Unlike rule-based metrics (exact
match, word-overlap F1), LLM judges recognize semantic equivalence
despite wording differences (for example, in
Table
1
“Luca” vs. “His name was Luca”
would score only 40% F1, despite having identical meaning). This is
crucial for evaluating zero-shot and RL-trained models, which often
generate answers in different styles than gold annotations. We adapt
the prompt from
34
who found 98% agreement
between human judgments and LLM-based metrics.

We use Qwen3 4B Instruct

In preliminary experiments, we compared our judge with the larger

reformulations as incorrect. Using LLM-as-a-judge, we measure recall
(the proportion of gold answers covered by the predictions), precision
(the proportion of predictions that match a gold answer), and full
coverage (the percentage of instances where recall equals 1, meaning
that all gold answers are recovered). For unambiguous questions, there

and we report recall in these cases. These metrics allow us to
evaluate both the coverage of valid interpretations and spurious
over-generation.

Ambrosia

(
27

is a text-to-SQL dataset where
some user questions are ambiguous and can lead to different SQL
queries and execution results. The dataset showcases multiple
ambiguities including scope and attachment ambiguities and comes with
gold interpretations for ambiguous questions, which can also serve as
unambiguous examples. For this dataset, we compare query execution results and report recall, precision, and full coverage.
We use the data split from

28

4.2
Training Details

We train Qwen3 4B Instruct
(
43
)
as our
base model which offers a good balance between performance and
efficiency; it is small enough for fast training and inference while
maintaining competitive performance. We do not use reasoning models
(e.g., Qwen3 4B Thinking) as their lengthy reasoning traces (often
thousands of tokens) would increase cost and latency without
benefiting our task. Our preliminary experiments showed that thinking
models do not outperform instruction-tuned models on
ambiguity resolution.

Data Balancing

Datasets with ambiguous inputs are often
imbalanced, with many more unambiguous examples than ambiguous ones
(see Table
2
). However, ambiguous examples
are more challenging and require stronger learning signals,
especially with methods based on GRPO that have difficulty-level bias

(
16
)
. We therefore rebalance the training
data to maintain an ambiguous-to-unambiguous ratio of 3:1, by
oversampling ambiguous examples.
Ambiguous examples teach the model when to generate multiple
interpretations, while unambiguous ones serve as regularization,
preventing it from over-generating interpretations and
maintaining high precision on straightforward inputs. During
training, we sample 4 examples per batch, which combined with
the 3:1 ratio, allocates more compute to harder ambiguous cases while
still maintaining sufficient signal from unambiguous examples.

Reward Functions

For Abg-CoQA, we compute rewards using word-overlap F1 as
the similarity metric. While less reliable than LLM-as-a-judge for
final evaluation, we found F1 provides effective training signal
during reinforcement learning and is much faster to compute. For
Ambrosia, we use execution match (comparing predicted and gold SQL
query results) which provides an objective, verifiable reward signal.
We train using DAPO
(
44
)
for 5 epochs with a learning
rate of 5e-7 and linear learning rate scheduling with 3% warmup. We
generate 16 completions per prompt during training. Additional
hyperparameters are in Appendix
D
.

4.3
Comparison Methods

We compare against several baselines that vary in
their use of reasoning, output format, and supervision. Implementation details are in Appendix
E
.

Answer-only Methods

generate answers without explicit
interpretations. We use
zero-shot
prompting of
base models to evaluate their baseline capability
for handling ambiguity. We also
fine-tune
models on training
data using supervised learning (SFT) to predict answers directly.

Interpretation-Answer Pair Methods

generate explicit
interpretations paired with corresponding answers. We prompt models
with the same instructions as our method to reason about user intent
and generate interpretation-answer pairs (see prompt in Appendix
A
)
but without any training.
Zero-shot
chain-of thought
evaluates whether the task can be solved through
prompting alone. We further
fine-tune
models to predict
interpretation-answer pairs with supervised learning. We
evaluate this baseline only on Ambrosia, as it provides gold
interpretations unlike Abg-CoQA.

We evaluate zero-shot baselines across two model scales: Qwen3
4B and 235B Mixture-of-Expert (MoE; 22B active parameters), with standard instruction-tuned (Instruct) and
reasoning (Thinking) variants. For fine-tuning, we use Qwen 4B Instruct to match our model’s scale.

State-of-the-Art Methods

are also compared against
our approach.
ACT

(

preference optimization algorithm that trains models to ask

\beta

(
39
)
as the policy model and
Gemini Ultra 1.0
(
36
)
) for

DisambigParse

(
28
)
is a
two-stage approach for handling ambiguity in semantic parsing. It

(
37
)

(

5.1
Conversational Question Answering

Main Results

Table
3
summarizes our results on
Abg-CoQA. As mentioned earlier we report word overlap F1 and
LLM-as-a-Judge metrics.

Across model sizes, we observe that larger models consistently
outperform smaller ones, which suggests that our approach would
benefit from stronger backbone models. The 0-shot baselines reveal an
interesting pattern: models achieve higher recall than precision,
suggesting they suspect ambiguity more often and attempt to provide
multiple responses, but do so inefficiently. For instance, the 235B
Thinking model achieves 68.9% recall but only 62.6% precision on
ambiguous questions (answers-only), indicating it generates multiple
answers, some of which are spurious.

Supervised fine-tuning (SFT) reveals a critical limitation: despite
our efforts to rebalance the training data and make unambiguous
examples less frequent than ambiguous ones, the model overfits to
unambiguous cases. This results in high precision (70.3% for
ambiguous, 70.6% for unambiguous) at the cost of recall (48.1%) and
full coverage (20.3%) for ambiguous questions. The
model learns to commit to one answer rather than enumerate multiple
options. Teaching the model to generate high-quality
interpretations with SFT is non-trivial as it requires annotation of
interpretations, which do not exist for Abg-CoQA.

Our RL-based model (IntentRL) achieves the best
results for ambiguous questions: 72.9% word-overlap F1, 78.1%
recall, and 61.0% full coverage. For unambiguous questions, we
achieve 84.4% word-overlap F1 and 90.9% recall, demonstrating that
the model successfully recognizes when questions have a
single intent. Lower precision (53.5% for ambiguous,
40.7% for unambiguous) reflects a bias toward generating additional
interpretations as the model sometimes treats unambiguous questions as
ambiguous and produces alternatives. We achieve the best
precision on ambiguous questions among all interpretation-answer
approaches (53.5% vs. 42.7–49.7% for CoT), showing that our method
improves precision even though we do not explicitly optimize for it in
the reward function, and the base models initially exhibit even lower
precision than recall. High recall implies that when the
model generates multiple interpretations, the correct ones are often included. In safety-critical applications, over-generating
plausible interpretations is preferable to silently committing to a
one, potentially incorrect interpretation.
Table
11(a)
(Appendix
H
) reports ablation results on Abg-CoQA, showing that training with RL to predict only answers can also achieve high coverage (but lacks explicit interpretations), while data balancing is necessary to prevent overfitting to unambiguous examples.

Human Evaluation Setup

We sampled 30 ambiguous examples from each dataset (80 interpretation-answer pairs in Abg-CoQA and 92 in Ambrosia). We focused on ambiguous cases as appropriate interpretations are more critical when multiple plausible answers exist. For each pair, three annotators judged whether the interpretation is compatible with its answer (i.e., whether it supports or explains it). Annotators were given the full context, the ambiguous question, and instructions to evaluate alignment even in cases where the answer was incorrect; an interpretable wrong answer is better than an unexplained one since it allows users to quickly identify and reject wrong answers. Error Analysis

To better understand model failures, we further analyze the 30 examples sampled for evaluating interpretation alignment (Section

). On Abg-CoQA, we identify three types of error. First, the model ignores important context from previous dialogue turns. Second, it sometimes produces valid, well-specified interpretations but then gives factually incorrect answers, such as referencing a different person than the one implied in the interpretation. Third, it predicts generic interpretations like “The question is ambiguous.” In some cases, this is paired with a specific answer, without clarifying which interpretation the answer corresponds to. In other cases, it is paired with the answer “Unknown” which appears in some training examples, but the model has learned to produce it more often than necessary.

We also observe on Ambrosia that interpretations can be vague, sometimes paraphrasing the question without resolving the ambiguity. Moreover, the model occasionally produces correct interpretations but predicts queries that do not follow them (e.g., adding ID fields not mentioned in the question)

generates non-executable queries, even noting the error in SQL comments (e.g., “this column does not exist”).

8
Conclusion

We handle ambiguous requests by generating interpretations paired with corresponding answers
and train models to reason about user intent via reinforcement learning with specialized rewards. Experiments on conversational question answering and text-to-SQL parsing show our method achieves higher full coverage of valid answers. The generated interpretations align with their answers over 90% of the time, despite lacking explicit supervision during training. Our approach offers more efficient reasoning than thinking models with better coverage. Explicit interpretations help users quickly clarify their intent or reject incorrect interpretations, improving both user experience and safety.

In the future, we plan to use interpretations to identify and correct errors in real-time, without requiring a full re-generation of responses. Controlled decoding could further improve efficiency and accuracy, e.g., ensuring that interpretations are mutually exclusive. Finally, adapting to individual user preferences would make interpretations more personalized and relevant to each user.

Appendix B
DAPO Algorithm

DAPO
(
44
)
extends GRPO with several key modifications designed for long-form reasoning tasks. It removes the KL penalty term (as divergence from the initial model is acceptable during reasoning training) and introduces the following changes:

Decoupled Clipping

DAPO uses asymmetric clipping parameters
\epsilon_{\text{low}}
and
\epsilon_{\text{high}}
to enhance exploration while maintaining stability.

Token-Level Loss

Instead of sample-level averaging, DAPO weights tokens equally across all responses, giving longer sequences more influence proportional to their length.

Dynamic Sampling

DAPO filters out prompts where all sampled responses are either correct or incorrect (accuracy equal to 1 or 0), ensuring effective gradients throughout training.

The DAPO objective is:

\begin{split}J_{\text{DAPO}}(\theta)&=\mathbb{E}_{(q,a)\sim D,\{o_{i}\}_{i=1}^{G}\sim\pi_{\theta_{\text{old}}}(\cdot|q)}\\
&\Bigg[\frac{1}{\sum_{i=1}^{G}|o_{i}|}\sum_{i=1}^{G}\sum_{t=1}^{|o_{i}|}\min\big(r_{i,t}(\theta)\hat{A}_{i,t},\\
&\quad\text{clip}(r_{i,t}(\theta),1\!-\!\epsilon_{\text{low}},1\!+\!\epsilon_{\text{high}})\hat{A}_{i,t}\big)\Bigg]\end{split}

s.t.

0<|\{o_{i}\mid\text{is\_equivalent}(a,o_{i})\}|<G
,

and where

\begin{split}r_{i,t}(\theta)=\frac{\pi_{\theta}(o_{i,t}|q,o_{i,<t})}{\pi_{\theta_{\text{old}}}(o_{i,t}|q,o_{i,<t})},\\
~\hat{A}_{i,t}=\frac{R_{i}-\text{mean}(\{R_{i}\}_{i=1}^{G})}{\text{std}(\{R_{i}\}_{i=1}^{G})}\end{split}

Appendix C
Types of Ambiguity

Each dataset we use has its own ambiguity taxonomy. Below, we briefly describe the types of ambiguity as defined by the dataset authors. For more details, we refer readers to the original papers.

Abg-CoQA

9
defines four ambiguity types:

Coreference resolution
occurs when pronouns or referring expressions can map to multiple entities in the context. An example is provided in Table
1
.

Time-dependency
occurs when temporal context is underspecified, allowing questions to refer to different time periods. For example, in a story describing an accident, the question “What was everyone doing?” can refer to actions either before or after the accident.

Answer types
are ambiguous with respect to the intended level of granularity. For example, when asked “What pupils’ were reading?”, the answer could be either novels a specific book (e.g., “The Call of the Wild”).

Event ambiguity
occurs when a story contains multiple parallel events or storylines, and questions underspecify which event they are referring to. For example, when a story mentions both a police investigation and CNN’s reporting on the same incident, a question about whether the suspect was identified by name could refer to either storyline (the police identify but CNN does not).

Ambrosia

(
27
)
defines three ambiguity types:

Scope ambiguity
occurs when it is unclear which elements a quantifier (e.g., “every”, “each”) refers to. For example, the question “What activities does each gym offer?” has a collective interpretation (a common class for all gyms in the database) and distributive one (each gym is considered separately, a list of all classes and gyms).

Attachment ambiguity
occurs when it is unclear where a modifier attaches in a sentence. For example, “Show screenwriters and editors on a work-for-hire” can mean either both roles are on work-for-hire contracts (high attachment to the verb) or only editors are (low attachment to “editors”).

Vagueness
occurs when context creates uncertainty about which database entities are being referenced. For example, in Table
1
“required experience” could potentially refer to minimum years, preferred years, or both.

AmbiQT

(
2
)
defines four ambiguity types:

Column ambiguity
occurs when multiple columns satisfy the same semantic description.
For example, the question “List the ids of all students” is ambiguous when a database contains both columns named
admission_number
and
roll_number
.

Table ambiguity
occurs when multiple tables represent similar entities. For example, “How many singers do we have?” could query either an
artist
or
performer
table.

Join ambiguity
occurs when it is unclear whether information should be retrieved from a single table or from joining multiple tables. For example, asking for a person’s name and address is ambiguous when
address
is in the same table as
name
and
postal_address
is in a separate
person_details
table.

Precomputed aggregates
arise when databases store pre-aggregated values alongside raw data. For example, “Find the average weight for each pet type” could either compute the aggregate from data or select from pre-computed
avg_weight
.
