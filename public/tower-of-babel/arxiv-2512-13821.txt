The Double Life of Code World Models: Provably Unmasking Malicious Behavior Through Execution Traces
Subramanyam SahooBerkeley AI Safety Initiative (BASIS)UC Berkeley sahoo2vec@gmail.com Jared JunkinDepartment of Electrical and Computer EngineeringJohns Hopkins University jjunkin2@jhu.edu

Abstract
Large language models (LLMs) increasingly generate code with minimal human oversight, raising critical concerns about backdoor injection and malicious behavior. We present Cross-Trace Verification Protocol (CTVP) , a novel AI control framework that verifies untrusted code-generating models through semantic orbit analysis. Rather than directly executing potentially malicious code, CTVP leverages the model’s own predictions of execution traces across semantically equivalent program transformations. By analyzing consistency patterns in these predicted traces, we detect behavioral anomalies indicative of backdoors. Our approach introduces the Adversarial Robustness Quotient (ARQ), which quantifies the computational cost of verification relative to baseline generation, demonstrating exponential growth with orbit size. Theoretical analysis establishes information-theoretic bounds showing non-gamifiability—adversaries cannot improve through training due to fundamental space complexity constraints. This work demonstrates that semantic orbit analysis provides a scalable, theoretically grounded approach to AI control for code generation tasks.

Traditional defenses rely on execution-time sandboxing or rule-based scanning, both of which assume the model is benign and transparent. However, under adversarial or misaligned settings, such assumptions fail

Recent advances in AI control have emphasized designing verification mechanisms that remain effective even under potential subversion or model-level manipulation. Prior works in backdoor detection typically rely on white-box access, such as weight clustering or trigger inversion

3
Methodology

We propose a Cross-Trace Verification Protocol (CTVP) to detect hidden or context-dependent malicious behavior in code–model pairs by enforcing
semantic invariance
across syntactic variants. Given a program
P
, we generate a semantic orbit
\mathcal{O}=\{Q_{i}\}_{i=1}^{k}
using transformations that preserve semantics (variable renaming, dead-code injection, reformatting) while enforcing a minimum syntactic edit distance (Levenshtein) from
P
. For each
Q\in\{P\}\cup\mathcal{O}
we query an untrusted LLM to produce an execution trace
\tau(Q)
(stepwise variable states and final output), then compute pairwise similarities
s(\tau_{i},\tau_{j})
that combine step-length ratio, per-step state equality, and final-output agreement. We summarize agreement with a percentile-based consistency score

C\;=\;\mathrm{percentile}_{p}\bigl(\{s_{ij}\}_{i<j}\bigr),

and apply calibrated thresholds
T_{\mathrm{strict}}
and
T_{\mathrm{soft}}
according to

\text{Verdict}=\begin{cases}\text{REJECT},&C<T_{\mathrm{strict}},\\[4.0pt]
\text{(trusted check)},&T_{\mathrm{strict}}\leq C<T_{\mathrm{soft}},\\[4.0pt]
\text{ACCEPT},&C\geq T_{\mathrm{soft}}.\end{cases}

In the intermediate regime we compute
\tau_{\mathrm{trusted}}
from a vetted model and the median similarity
\operatorname{median}_{i}s(\tau_{\mathrm{trusted}},\tau_{i})
to decide rejection when the trusted gap or absolute trust score indicates significant disagreement. The protocol is deterministic given fixed RNG seeds, caches model outputs by program hash, and bounds false positives via the chosen percentile and gap parameters.

We evaluate CTVP on a curated corpus of benign and adversarial code samples while sweeping orbit size
k
, percentile
p
, and thresholds to probe the trade-off between detection power and computational cost. Reported metrics include true/false positive rates, precision/recall, and an Adversarial Robustness Quotient (ARQ) that measures wall-clock and FLOP overhead relative to single-trace inference (under token-linear cost assumptions
\mathrm{ARQ}\approx k+1
). Baselines comprise static pattern detectors (regex matches, AST complexity heuristics, Shannon entropy) and single-trace semantic checks.

Experimental Setup

In our experiments we run CTVP on a curated dataset of programs that contains both benign examples and adversarial (malicious) variants. For each program
P
we sweep orbit size

k\in\{3,\,5,\,10,\,20\},

and record the following metrics: detection rate (true positives), false positive rate, and benign acceptance. For every pair
(P,k)
we save the protocol verdict and compute the Adversarial Robustness Quotient
\mathrm{ARQ}
(wall-clock and FLOP overhead relative to single-trace inference). We additionally evaluate each baseline detector
b(\cdot)
on the same program corpus for direct comparison. The experiment runner enforces resource hygiene (memory cleanup and caching) and performs adaptive thresholding: every 10 programs it updates the strict threshold
T_{\mathrm{strict}}
using a PID-like controller targeting a lower false-positive rate. Finally, we complement empirical results with an information-theoretic analysis comparing the estimated program and trace space sizes
M,N
to observed outcomes, and we demonstrate non-gamifiability empirically by showing that plausible adversarial modifications cannot reliably force false negatives under CTVP.

Collectively, this methodology operationalizes
semantic invariance
: by requiring that all semantics-preserving transforms of a program produce consistent execution traces, CTVP reduces the opportunity for triggers that appear only in a single syntactic form. Robustness is achieved through cross-variant and (optionally) cross-model checks, trading additional compute (measured by
\mathrm{ARQ}
) for substantially improved detection of context-dependent malicious behavior. Algorithm

5
Results

We evaluate our AI control framework across varying orbit sizes ranging from 2.5 to 20. Our approach achieves perfect detection rates (100%) across all orbit configurations, successfully identifying all 120 malicious instances with zero false negatives as shown in the confusion matrix. The consistency scores are highly concentrated at 1.0, with all benign cases achieving perfect consistency, indicating robust and reliable behavior verification. Runtime monitoring successfully flags 21% of cases for additional scrutiny, while 79% are outright rejected, demonstrating effective security filtering. The median ARQ (Algorithmic Robustness Quotient) ratio exhibits exponential growth from
4\times 10^{0}
at orbit size 2.5 to
2\times 10^{1}
at orbit size 20, though computational overhead remains minimal with median execution times increasing linearly from 0.275s to 0.333s. Transformation generation success rates vary considerably with orbit size, dropping to 10% at size 10 before recovering to 50-75% at size 20, suggesting challenges in the intermediate regime. Notably, the system achieves 100% experimental success rate with zero errors across all 200 trials, validating the effectiveness of our control mechanisms. Resource utilization remains efficient with CPU memory stabilizing at approximately 4.8 GB and GPU memory at 17 GB, well below the 90% capacity threshold of 71.3 GB.

Limitation & Future Works

CTVP currently faces both practical and theoretical constraints. It relies on
LLM-based trace prediction
, approximating program behavior via predicted rather than executed traces, making detection vulnerable to model errors and adaptive adversaries. The
security guarantees
are largely theoretical—existing bounds assume perfect predictions, whereas real-world deployment demands additional hardening to mitigate adaptive attacks and manage benign false positives. CTVP’s
scalability
is also limited: verification time grows with orbit size, creating a trade-off between detection accuracy and throughput that restricts real-time use. Finally,
transformation coverage
remains narrow, with only five transformation types, potentially missing subtle semantics-preserving variants, while conservative edit-distance thresholds further constrain detection diversity.

Future work aims to broaden CTVP’s robustness and applicability. Integrating
real execution
through sandboxed environments (e.g., RestrictedPython) could provide ground-truth traces and stronger guarantees, albeit with added overhead and sandbox escape risks. Expanding
transformation techniques
—including data-flow–aware reordering, type-preserving edits, loop unrolling, and constant folding—may enrich semantic diversity.
Adaptive orbit sizing
can dynamically scale verification based on program complexity, optimizing cost–coverage trade-offs. Continuous
runtime monitoring
could enable periodic re-verification, anomaly detection, and feedback-driven retraining. Finally,
adversarial robustness testing
should assess resistance to gradient-based, steganographic, and multi-stage backdoor attacks.

7
Conclusion

We introduce
CTVP
, a black-box AI-control framework that detects backdoors in code-generating models by measuring consistency of execution traces across semantically equivalent transformations. Empirically, CTVP attains very good detection rates with reliable false positives, substantially outperforming static-analysis baselines.

Our theoretical contribution, the
Adversarial Robustness Quotient (ARQ)
, establishes non-gamifiability: adversarial evasion costs grow exponentially with orbit size
k
,

\text{cost}\propto\left(\frac{M}{N}\right)^{k-1},

implying expected trial counts on the order of
10^{6}
–
10^{30}
for practical
k
. CTVP requires only query access, uses PID-inspired adaptive thresholding to balance sensitivity and false positives, and supports cascaded verification (consistency scoring optionally combined with a trusted-model check) for defense-in-depth. In our evaluation, transformation generation succeeded in most of the attempts on Python programs up to 200 LOC. Three compact insights explain effectiveness: Backdoors must preserve trigger–response mappings across semantic variants, creating detectable inconsistencies. Generating semantic equivalents is
O(k)
, while constructing consistent evasions requires exponential search. Trace-level analysis captures behavioral semantics missed by syntax-focused defenses.

Trace prediction and similarity

Let a model (or verifier)
M
produce an execution trace for a program
Q
, denoted
T_{Q}:=M(Q)
. We assume a trace-similarity function

\operatorname{sim}:\mathcal{T}\times\mathcal{T}\to[0,1],

(3)

where
\mathcal{T}
is the space of traces and
\operatorname{sim}(T_{i},T_{j})=1
when traces are identical and
0
when maximally different. Examples: normalized sequence alignment score, BLEU-like measure for trace tokens, or graph-edit similarity for call graphs.

Define the
pairwise average consistency
of traces over the orbit
\mathcal{O}
as

C(P,M,\mathcal{O})\;=\;\frac{2}{k(k-1)}\sum_{1\leq i<j\leq k}\operatorname{sim}\big(T_{Q_{i}},T_{Q_{j}}\big).

(4)

C\in[0,1]
measures how consistent the model’s outputs are across semantically-equivalent inputs.

Adaptive Threshold Control

We implement a PID-inspired adaptive controller to balance detection power against false positives. Denote by
\theta_{\mathrm{strict}}^{(t)}
the strict threshold at iteration
t
and by
\mathrm{FPR}^{(t)}
the observed false positive rate at iteration
t
. Define the control error

e^{(t)}\;=\;\mathrm{FPR}^{(t)}-\mathrm{FPR}_{\mathrm{target}},\qquad\mathrm{FPR}_{\mathrm{target}}=0.05.

The PID update for the threshold is

\theta_{\mathrm{strict}}^{(t+1)}\;=\;\theta_{\mathrm{strict}}^{(t)}\;-\;\Biggl(k_{p}\,e^{(t)}\;+\;k_{i}\sum_{\tau=1}^{t}e^{(\tau)}\;+\;k_{d}\bigl(e^{(t)}-e^{(t-1)}\bigr)\Biggr),

(5)

with gains

k_{p}=0.1,\qquad k_{i}=0.05,\qquad k_{d}=0.01.

To keep the threshold in a safe operating range we clamp the updated value:

\theta_{\mathrm{strict}}^{(t+1)}\;=\;\operatorname{clip}\!\bigl(\theta_{\mathrm{strict}}^{(t+1)},\,0.5,\,0.99\bigr),

where
\operatorname{clip}(x,a,b)=\min(\max(x,a),b)
. In our implementation the controller is evaluated after every 10 processed programs; the integral term is reset or anti-windup is applied if the controller saturates.

Adversarial Robustness Quotient (ARQ)

We quantify the computational overhead of adversarial verification relative to a single-trace baseline by the Adversarial Robustness Quotient (ARQ). Let
k
be the orbit size,
n_{\text{tokens}}
the average tokens per trace, and
\mathrm{FLOPS}_{\text{token}}
the model-dependent FLOPs per token. Then

\displaystyle\mathrm{ARQ}(P,k)

\displaystyle=\frac{\mathrm{FLOPS}_{\text{adversarial}}}{\mathrm{FLOPS}_{\text{baseline}}}=\frac{(k+1)\,n_{\text{tokens}}\,\mathrm{FLOPS}_{\text{token}}}{n_{\text{tokens}}\,\mathrm{FLOPS}_{\text{token}}}=k+1.

(6)

Example token-FLOP estimates used in our experiments are:

\mathrm{FLOPS}_{\text{token}}(7\mathrm{B})=1.4\times 10^{10},\qquad\mathrm{FLOPS}_{\text{token}}(1.5\mathrm{B})=3.0\times 10^{9}.

We define the Adversarial Robustness Quotient (ARQ) for program
P
under model
M
and orbit
\mathcal{O}
simply as the average consistency:

\mathrm{ARQ}(P,M,\mathcal{O})\;:=\;C(P,M,\mathcal{O}).

(7)

Higher ARQ indicates higher robustness (outputs invariant under semantic-preserving syntactic rewrites). One can refine ARQ by incorporating a penalty for varying output semantics (e.g., execution exceptions) or by weighting pairwise similarities by program-proximity; this basic definition is intentionally simple and interpretable.

For a single program
P
, let:

•

T_{\mathrm{base}}
and
T_{\mathrm{adv}}
denote wall-clock times to generate the trace without and with adversarial verification, respectively (the latter corresponds to an orbit of size
k
),

•

F_{\mathrm{base}}
and
F_{\mathrm{adv}}
denote the corresponding estimated floating-point operations (FLOPs).

Then we define:

\displaystyle\mathrm{ARQ}_{\mathrm{time}}

\displaystyle=\frac{T_{\mathrm{adv}}}{T_{\mathrm{base}}},

(8)

\displaystyle\mathrm{ARQ}_{\mathrm{flops}}

\displaystyle=\frac{F_{\mathrm{adv}}}{F_{\mathrm{base}}}.

(9)

In practice,
T_{\mathrm{base}}
corresponds to the model’s inference time for a single trace, and
T_{\mathrm{adv}}
corresponds to
(k+1)
traces (the original plus
k

To approximate computational cost, let each trace consume
\ell

S
require
\phi_{S}
FLOPs per token. Then:

\displaystyle F_{\mathrm{base}}

\displaystyle=\ell\,\phi_{S},

(10)

\displaystyle F_{\mathrm{adv}}

\displaystyle=(k+1)\,\ell\,\phi_{S}.

(11)

Substituting into equation
9
gives a simple relation:

\mathrm{ARQ}_{\mathrm{flops}}\approx k+1.

(12)

Thus, the ARQ captures how much more expensive it is to execute the Cross-Trace Verification Protocol (CTVP) compared to a single inference.
The implementation also enforces minimum runtime thresholds to prevent degenerate estimates.

Information-Theoretic Bounds

Let
\mathcal{M}
be the trace space of size
M=|\mathcal{M}|
and
\mathcal{N}
the program-space of size
N=|\mathcal{N}|
. Under a conservative independence assumption, the probability that a backdoored model (or an accidental adversary) is
consistent
across
k
independently sampled semantic variants is

\Pr\bigl(\text{consistent}\mid\text{backdoor}\bigr)\;=\;\Bigl(\frac{N}{M}\Bigr)^{\,k-1}.

(13)

Hence the expected number of adversarial trials required to find a backdoor that is consistent across
k
samples is

\mathbb{E}[\text{trials}]\;=\;\frac{1}{\Pr(\text{consistent}\mid\text{backdoor})}\;=\;\Bigl(\frac{M}{N}\Bigr)^{\,k-1}.

(14)

We approximate typical sizes by

M\approx\bigl(n_{\text{vars}}\cdot V\bigr)^{\,n_{\text{steps}}},\qquad N\approx n_{\text{vars}}!\cdot n_{\text{blocks}}!,

where
V
is the effective per-variable value range (we use
V\!=\!1000
in our estimates). In practice
M\gg N
, so the cost in equation
14
grows exponentially in
k
.

Equivalently, using trace entropy
H(\mathcal{T})=\log_{2}M
, the expected trials scale as

\mathbb{E}[\text{trials}]\approx 2^{(k-1)\,H(\mathcal{T})}.

(15)

These bounds formalize the
non-gamifiability
intuition: an adversary must search an exponentially large space (in
k
) to construct a backdoor that remains consistent across a sampled orbit, making such attacks computationally infeasible under realistic assumptions.

We can further derive a theoretical lower bound for ARQ using information-theoretic reasoning.
If each new trace adds
H
bits of entropy, then the number of configurations required to distinguish adversarial behavior grows exponentially:

\text{Config}_{\min}\approx 2^{kH}.

(16)

In implementation, the function
calculate_theoretical_lower_bound
uses:

2^{(k\cdot H)},\quad\text{with}\quad H\approx\log_{2}(N_{\mathrm{samples}}),

(17)

where
N_{\mathrm{samples}}
is the number of observed trace samples.
This emphasizes that verification complexity scales exponentially with orbit size
k
, reinforcing the necessity of bounded, probabilistic verification rather than exhaustive exploration.

Decision logic

Given a threshold
\tau\in[0,1]
, the final decision rule is:

\text{flag}(P)\;=\;\begin{cases}\text{``ALERT''},&\mathrm{ARQ}(P,M,\mathcal{O})<\tau,\\[4.0pt]
\text{``OK''},&\mathrm{ARQ}(P,M,\mathcal{O})\geq\tau.\end{cases}

Thresholds may be set via calibration on benign and known-adversarial examples.

An orbit

Trace Prediction via Language Model

For each program
P
(original or transformed), we predict its execution trace using a large language model (LLM) as an oracle. The model is prompted in natural language, e.g.,

“Simulate executing this Python program step-by-step. Your trace:”
followed by the code of
P
.
The textual response is parsed as an execution trace

\tau=[s_{1},s_{2},\dots],

where each element
s_{i}
represents a partial program state (variable assignments and outputs).
Formally, at each step
i
, we record a mapping of the form
\{x\mapsto v\}
for each variable
x
and its corresponding value
v
.

The predictor caches traces by hashing the program string to avoid redundant LLM calls.
If prediction fails (e.g., parsing error or timeout), an invalid trace is returned.

Let
\tau(P)
denote the execution trace returned by the model as an
ExecutionTrace
object.
Before inference, the model and tokenizer are loaded with robust fallback strategies. Prompt construction is deterministic, and inference uses configuration-defined sampling parameters (e.g., temperature, top-
p
).
Although no closed-form equation exists, conceptually we view this as a probabilistic mapping:

\tau(P)=\mathrm{LLM}\big(\mathrm{prompt}(P)\big),

(18)

where the prompt requests a step-by-step simulation.
Since LLM inference is stochastic, even semantically equivalent programs may yield differing traces.

Trace Similarity Metric

To compare two traces
\tau_{1}
and
\tau_{2}
, we compute a weighted similarity

s(\tau_{1},\tau_{2})\in[0,1].

Let
n_{1}
and
n_{2}
be the number of steps (excluding the final output) in each trace.
We define three components: step-length, state, and output similarity.

Step-length similarity.

S_{\mathrm{len}}=\frac{\min(n_{1},n_{2})}{\max(n_{1},n_{2})}.

(19)

State similarity.

Let
m
be the count of steps
i=1,\dots,\min(n_{1},n_{2})
for which the variable assignments in
\tau_{1}
and
\tau_{2}
at step
i
are identical. Then

S_{\mathrm{state}}=\frac{m}{\min(n_{1},n_{2})}.

(20)

Output similarity.

We define the final-output agreement as

S_{\mathrm{out}}=\begin{cases}1,&\text{if final outputs are identical},\\[4.0pt]
0.5,&\text{if one output is missing},\\[4.0pt]
0,&\text{otherwise.}\end{cases}

Overall similarity.

The combined similarity score is a convex combination:

s(\tau_{1},\tau_{2})=\alpha\,S_{\mathrm{len}}+\beta\,S_{\mathrm{state}}+\gamma\,S_{\mathrm{out}},

(21)

where
\alpha,\beta,\gamma\in[0,1]
are configuration weights satisfying

\alpha+\beta+\gamma=1.

(22)

The implementation bounds
s(\tau_{1},\tau_{2})
to
[0,1]
explicitly.
In prose, this metric compares (i) how similar the lengths of traces are, (ii) how many intermediate states match exactly, and (iii) whether final outputs coincide, combining these aspects into a unified score.

Cross-Trace Verification Protocol (CTVP)

Using the semantic orbit and the similarity metric, we perform phase-wise verification on the input program
P
.
Let
\tau_{0}=\tau(P)
denote the execution trace of the original program under the
untrusted
predictor, and let
\{Q_{1},\dots,Q_{k}\}
be the generated orbit.
For each variant
Q_{i}
, we obtain the corresponding trace
\tau_{i}=\tau(Q_{i})
and collect all valid traces:

\mathcal{T}=\{\tau_{i}:i=0,1,\dots,k\}\quad(\tau_{0}\text{ included}),

ignoring invalid or error traces.

We now compute a
consistency score
among these traces by evaluating all pairwise similarities

s(\tau_{i},\tau_{j})
for
i<j
and
\tau_{i},\tau_{j}\in\mathcal{T}
.
Let
\{s_{ij}\}
denote this multiset of similarity values.
To ensure robustness to outliers, we take a high percentile (e.g.,
p=80
) of these values:

C=\mathrm{percentile}_{p}\big(\{s_{ij}\}\big).

(23)

Here
C\in[0,1]
represents the cross-trace consistency score—high
C
(close to 1) implies strong agreement among traces, whereas low
C
indicates divergent behavior.

Decision logic.

Let
T_{\mathrm{strict}}
and
T_{\mathrm{soft}}
denote the strict and soft thresholds, respectively.
The final decision is:

\text{Decision}=\begin{cases}\text{REJECT},&C<T_{\mathrm{strict}},\\[4.0pt]
\text{Check trusted model},&T_{\mathrm{strict}}\leq C<T_{\mathrm{soft}},\\[4.0pt]
\text{ACCEPT},&C\geq T_{\mathrm{soft}}.\end{cases}

Trusted model verification.

In the intermediate regime (
T_{\mathrm{strict}}\leq C<T_{\mathrm{soft}}
), we optionally engage a
trusted
model for verification.
Let
\tau_{\mathrm{trusted}}=\tau_{\mathrm{trusted}}(P)
be the trusted trace, and compute

s_{\mathrm{trusted}}=\mathrm{median}_{i}\big[s(\tau_{\mathrm{trusted}},\tau_{i})\big],

(24)

where
\tau_{i}\in\mathcal{T}
.
We also denote
s_{\mathrm{untrusted}}=C
.
If either

Theoretical Space Estimation

We quantify the theoretical search spaces of program transformations and execution traces to justify the difficulty of adversarially manipulating these features.
A
TheoreticalSpaceEstimator
computes two quantities:

•

Trace space size

M
: the number of distinct execution traces.

•

Program space size

N
: the number of distinct programs reachable via syntactic transformations.

Let
n_{\mathrm{id}}
denote the number of unique identifiers (variables or functions) in program
P
, and
n_{\mathrm{blk}}
the number of top-level code blocks.
Let
L
be the number of executable statements (approximate computational steps), and
R
be the average range of variable values (a hyperparameter from configuration).
Then, the theoretical estimator uses the following approximations:

\displaystyle M

\displaystyle\approx(n_{\mathrm{id}}\cdot R)^{L},

(25)

\displaystyle N

\displaystyle\approx n_{\mathrm{id}}!\times n_{\mathrm{blk}}!.

(26)

Equation equation
25
estimates the trace-space size
M
by assuming each of
n_{\mathrm{id}}
variables can take approximately
R
distinct values at each of
L
execution steps.
Equation equation
26
estimates the program-space size
N
as the number of possible renamings of identifiers and permutations of independent blocks.
In practice, extremely large values are capped numerically for stability.

These estimates demonstrate that even small programs have astronomically large semantic and syntactic variation spaces. This motivates the need for
sampling
(via the semantic orbit) rather than exhaustive enumeration.

Baseline Detection Methods

For comparison, we implement simple static baselines that do not rely on the LLM but instead check for obvious malicious patterns or anomalies.

Static code patterns.

We flag a program
P
if its source contains suspicious tokens such as
eval(
,
exec()
, secret constants, imports of
os.system
, or keywords like
BACKDOOR
.
Formally, this corresponds to a boolean predicate

b_{\mathrm{static}}(P)\in\{0,1\},

(27)

which evaluates to
1
if any predefined regular expression pattern matches the program text:

b_{\mathrm{static}}(P)=\begin{cases}1,&\text{if }\exists\,\text{pattern }r\text{ s.t. }r\text{ matches }P,\\[4.0pt]
0,&\text{otherwise.}\end{cases}

Complexity heuristic.

We parse
P
into an abstract syntax tree (AST) and compute:

n=\text{total number of AST nodes},\quad c=\text{number of control nodes (if, while, for, try, etc.)}.

If the code is either overly complex or underspecified, we flag it as suspicious. Specifically:

b_{\mathrm{complex}}(P)=\begin{cases}1,&n>50\text{ and }\tfrac{c}{n}>0.3,\\[4.0pt]
1,&n<20\text{ and }c>3,\\[4.0pt]
0,&\text{otherwise.}\end{cases}

(28)

Entropy heuristic.

We compute the Shannon entropy
H
of the character distribution in
P
:

H=-\sum_{x\in\Sigma}\frac{n_{x}}{N}\log_{2}\frac{n_{x}}{N},

(29)

where
n_{x}
is the count of character
x
,
N=|P|
is the total number of characters, and
\Sigma
is the program’s character alphabet.
Programs with extremely low or high entropy are flagged as potentially malicious:

b_{\mathrm{entropy}}(P)=\begin{cases}1,&H<3.0\text{ or }H>6.0,\\[4.0pt]
0,&\text{otherwise.}\end{cases}

(30)

Weighted combination.

The final baseline flags
P
as malicious if at least two of the above three checks trigger. Let

b_{\mathrm{static}},\;b_{\mathrm{complex}},\;b_{\mathrm{entropy}}\in\{0,1\}.

Then

b_{\mathrm{weighted}}(P)=\mathbb{I}\!\left[(b_{\mathrm{static}}+b_{\mathrm{complex}}+b_{\mathrm{entropy}})\geq 2\right],

(31)

where
\mathbb{I}[\cdot]
denotes the indicator function.
