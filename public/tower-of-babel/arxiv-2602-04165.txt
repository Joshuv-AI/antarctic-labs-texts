I Can’t Believe It’s Not a Valid Exploit
Derin Gezgin, Amartya Das, Shinhae Kim, Zhengdong Huang, Nevena Stojkovic, Claire Wang

Abstract
Recently Large Language Models (LLMs) have been used in security vulnerability detection tasks including generating proof-of-concept (PoC) exploits. A PoC exploit is a program used to demonstrate how a vulnerability can be exploited. Several approaches suggest that supporting LLMs with additional guidance can improve PoC generation outcomes, motivating further evaluation of their effectiveness. In this work, we develop PoC-Gym , a framework for PoC generation for Java security vulnerabilities via LLMs and systematic validation of generated exploits. Using PoC-Gym , we evaluate whether the guidance from static analysis tools improves the PoC generation success rate and manually inspect the resulting PoCs. Our results from running PoC-Gym with Claude Sonnet 4, GPT-5 Medium, and gpt-oss-20b show that using static analysis for guidance and criteria lead to 21% higher success rates than the prior baseline, FaultLine . However, manual inspection of both successful and failed PoCs reveals that 71.5% of the PoCs are invalid. These results show that the reported success of LLM-based PoC generation can be significantly misleading, which is hard to detect with current validation mechanisms.



1
Introduction

The number of reported security vulnerabilities has increased each year since 2016, with over 40,000 Common Vulnerabilities and Exposures (CVEs) reported in 2024 and more than 35,000 reported in the first three quarters of 2025
(
cve.org 2025
)
.
To identify these vulnerabilities, static application security testing (SAST) tools such as CodeQL
(
Avgustinov et al. 2016
)
, Semgrep
(
Semgrep, Inc. 2025
)
, and Snyk
(
Snyk.io
)
commonly rely on taint tracking, which models how untrusted data can flow from sources (e.g., user input) to sinks (e.g., database queries or system calls).
If not sanitized, these source-to-sink dataflow traces can indicate potentially vulnerable execution paths.
Traditional static taint analysis tools often depend on manually curated specifications for third-party APIs and use over-approximations of program behavior, which can result in incomplete coverage and imprecise results
(
Li et al. 2025
;
Kang et al. 2022a
)
.
Large language models have increasingly been applied to vulnerability detection and repair, with growing evidence that they can support program analysis via code understanding and synthesis
(
Zhou et al. 2025
)
.

A PoC demonstrates exploitability of a detected trace by triggering unintended or dangerous behavior when executed, providing evidence that a reported vulnerability can be triggered
(
Dang et al. 2025
)
.
PoCs are crucial for multiple stages of the vulnerability lifecycle, enabling reproducibility during vulnerability disclosure, aiding developers in patch development, and serving as regression tests.
Despite their importance, only a small fraction of publicly disclosed vulnerabilities are accompanied by an available PoC exploit
(
Householder et al. 2020
)
.
A detailed discussion of prior work on automated PoC generation and LLM-assisted vulnerability exploitation is provided in Appendix
A
.

We present
PoC-Gym
, a system for generating Java PoC exploits using LLMs and SAST tool dataflow traces.
We evaluate
PoC-Gym
on 20 real-world vulnerabilities across various LLMs.
Our results show how seemingly successful PoC exploits are often invalid due to various LLM failures.
Our novel approach helps mitigate the amount of false positive PoCs, but fails to guide the LLM to generate more valid PoCs.

2.1
Problem Statement

PoC-Gym
aims to generate proof-of-concept exploits for real-world Java projects.
A successful proof-of-concept is an executable program that executes a public entry point of a vulnerable program, triggers the vulnerable behavior, and produces an observable success signal.

Each problem instance corresponds to a single vulnerability is defined as

I=\big(P^{\text{vul}},\,P^{\text{fix}},\,\mathsf{desc},\,\mathsf{meta},\,\mathcal{T}\big),

(1)

where
P^{\text{vul}}
and
P^{\text{fix}}
are the vulnerable and patched versions of a Java project,
\mathsf{desc}
consists of the CVE and CWE descriptions of the project,
\mathsf{meta}
is the project meta-information, and
\mathcal{T}
is a static source–sink trace.

A PoC is a single Java program
\pi
executed in
P^{\text{vul}}
by an evaluation pipeline, which produces

\textsc{Run}(I,\pi)\rightarrow(c,s,\tau),

(2)

where
c
is the exit code,
s
is program output, and
\tau
is the dynamic execution trace.
A PoC is considered
valid
if it exits successfully, prints
[VULN]
, and reaches the sink of
\tau
:

\textsc{Valid}(I,\pi)=\mathbbm{1}\big[c=0\land\texttt{[VULN]}\in s\land\textsc{SinkHit}(\tau)\big].

(3)

2.2
Framework Overview

PoC-Gym
generates proof-of-concept exploits by iteratively producing candidates with an LLM and validating them through program execution.
As shown in Figure
1
, the pipeline consists of structured prompt construction, PoC generation by an LLM agent, and execution-based validation with feedback.
This section provides a high-level overview of these components; full technical details of
PoC-Gym
are detailed in Appendix
B
.

Prompt Construction.
For each vulnerability instance,
PoC-Gym
constructs a prompt that combines vulnerability context, static analysis guidance, and execution constraints.
The prompt includes CVE and CWE descriptions that specify the vulnerability and expected success conditions including an LLM-generated CVE-specific guidance, a static source–sink trace selected by an LLM among traces that are generated via CWE-specific CodeQL queries, and repository metadata.

PoC Generation and Validation.

Given the constructed prompt, an LLM agent generates a single Java PoC candidate, which is compiled and executed in the vulnerable version of the project.
Each candidate is validated using three conditions: successful program execution, printing
[VULN]
following vulnerability demonstration, and executing the given vulnerable sink.
Sink execution is determined via an AspectJ-based instrumentation.
If a candidate fails validation, a short failure summary is appended to the prompt and returned to the agent for the next attempt with the output of the current PoC.
The loop terminates upon success or when a fixed iteration budget is exhausted.

3
Experiments

PoC-Gym
is evaluated on 20 vulnerabilities from CWE-Bench-Java which provides real-world Java CVEs with vulnerable/patched commit information, and vulnerable code locations.
For details about the set of CVEs selected, see Appendix
C
.

Experiment Details.

We evaluate the effectiveness of the trace guidance by conducting experiments under two settings: with static source–sink traces and without trace information.
For experiments without trace information, we remove the sink reachability criterion from the validation loop, as no trace information is available.
For experiments with the trace information, we run the pipeline on the top-5 static trace candidates chosen by the LLM.
Both experimental settings are evaluated using Claude Code with Sonnet 4, Codex with GPT-5 Medium reasoning and Codex with
gpt-oss-20b
. CVE prompt generation and trace selection is done asynchronously via Claude Code with Sonnet 4.
GPT-OSS experiments used an Intel Xeon Gold 6338 (2.00 GHz) CPU with ten NVIDIA H100 PCIe GPUs and 1 TB of RAM, while all other experiments used an Intel Xeon Gold 6248 (2.50 GHz) CPU with four NVIDIA GeForce RTX 2080 Ti GPUs and 750 GB of RAM.

Post-Hoc Analysis.

Following the success cases in
PoC-Gym
, we perform a post-hoc evaluation to further validate each exploit.
For each PoC, we compare its dynamic execution trace that is captured via AspectJ against the ground-truth source–sink trace provided by CWE-Bench-Java, and assess whether the PoC’s execution reaches the real vulnerability sink.

Evaluation Metrics.

We evaluate
PoC-Gym
in three main metrics that capture exploit effectiveness and trace utilization:
the number of generated PoCs that successfully trigger the target vulnerability (
\#\text{Triggered}
) according to the existing validation mechanism,
the number of generated PoCs that pass the Post-Hoc analysis (
# Post-Hoc Valid
),
and the average trace coverage of the successful PoCs, defined as the fraction of trace steps executed by a generated PoC (
\text{Avg Coverage}\%
).

Manual Inspection.
We manually inspect successful PoCs to assess whether the CVE prompt, selected traces, and the generated PoC are consistent with the ground truth vulnerability, as each stage involves LLM usage.
PoCs that fail to exploit the vulnerability despite returning the success marker are flagged as invalid.

3.2
Discussion

Post-hoc analysis reveals that
44\%
of the successful exploits were invalid as they do not exploit the actual vulnerable location.
Following our manual inspection of the PoCs,
71.5\%
of the successful exploits were invalid.
The manual inspection results for the multi-trace runs are shown in Figure
2

These failures show that LLM errors propagate across the system, exploit the existing validation criteria, and show recurring false-positive patterns.
A detailed qualitative breakdown of these failure modes, including PoC excerpts and vulnerability-specific case studies, is provided in Appendix
E
.

LLM Errors Can Propagate.

Each PoC prompt contains an LLM-generated CVE description and LLM-selected traces.
25% of the CVE descriptions were unrelated to the actual CVE. Out of the unrelated descriptions, 60% led to failed PoCs.
Of the invalid traces (60%), 33.3% led to failed PoCs.
There were also attempts where the CVE description was related but the trace wasn’t.

Use External Instrumentation to Assist Validity.
Comparing AspectJ generated execution logs that provide low-level code-coverage against ground-truth source–sink information reveals failure cases that lighter validation methods cannot detect.
Approaches such as
FaultLine
rely on print statements or output-based checks, which may succeed even when the vulnerability is not triggered.

LLM Error Categories.

Our failure analysis led to deriving LLM error categories.

Bad validation
for PoCs that declare success using incomplete or incorrect checks, ignoring exceptions, or failing the verify the vulnerable codepath was executed.

Hardcoding the vulnerability
occurs when the PoC directly produces an exploit outcome without traversing the vulnerable execution path.

Non-malicious behavior
for cases where the PoC achieves the intended behavior through legitimate API usage rather than exploitation.

Simulating the library
when PoC re-implement or approximate vulnerable behavior instead of invoking the actual project code.

4
Conclusion

We evaluated
PoC-Gym
, a hybrid SAST+LLM framework for generating Java proof-of-concept exploits, on 20 real-world CVEs and found that false-positive success cases hide incorrect exploitation.
While agents frequently satisfy the pipeline’s success criteria, post-hoc validation against ground-truth vulnerability locations reveals that many “successful” PoCs never execute the true vulnerable path, over-estimating the reported effectiveness.
Static trace guidance helps reduce these false successes but does not eliminate them.
Compared to prior systems such as
FaultLine
,
PoC-Gym
performs better by incorporating dynamic instrumentation; however even our improved pipeline still results in a large fraction of PoCs that look successful under automated checks yet do not correspond to real exploitation.

These results show a fundamental limitation of current LLM-based exploit generation pipelines: success is often defined by indirect or surface-level signals rather than empirical validation methods.
When validation relies on program output, side effects, or agent self-reports, LLMs frequently produce PoCs that appear plausible yet fail to engage the underlying vulnerability.
This gap between the ideal and actual exploitation examples suggests that improvements in prompting, trace selection, or LLM-agents alone are insufficient without stronger execution-level guarantees.

Appendix A
Related Work

Attempts to automate proof-of-concept (PoC) exploit generation predate the widespread adoption of large language models.
Early approaches relied on program analysis and test generation techniques, including test mimicry and algorithmic synthesis of inputs based on expert-written examples
(
Kang et al. 2022b
)
.
More recent work explores large language models for automated vulnerability exploitation and penetration testing via prompt engineering over vulnerability descriptions or source code
(
Zhang et al. 2023
;
Deng et al. 2024
)
.
To improve contextual grounding, subsequent systems introduce retrieval-augmented generation (RAG) to supply additional vulnerability metadata and program context
(
Lotfi et al. 2025
;
Xu et al. 2024
)
.
Several approaches further integrate static program analysis with LLM-based reasoning to improve reachability assessment, guidance, and validation.
For instance,
VulEUT
uses call-path analysis to determine vulnerability reachability prior to test-case generation in Java projects
(
Gao et al. 2025
)
.

PoCGen
combines static taint analysis with LLM reasoning by extracting source-to-sink traces using CodeQL and conditioning the model on these traces to generate and validate PoC exploits for npm packages
(
Simsek et al. 2025
)
.

FaultLine
similarly targets proof-of-vulnerability tests for Java security vulnerabilities, but infers data-flow paths and branch conditions with LLM-driven reasoning rather than language-specific static analysis, refining candidates in a feedback-driven loop
(
Nitin et al. 2025
)
.
Other hybrid systems, such as SAST-Genius, use LLMs to assist static analysis by reducing false positives and supporting vulnerability triage
(
Agrawal & Ahi 2025
)
.

Appendix B
Implementation Details of the
PoC-Gym
Framework

The
PoC-Gym
framework consists of three main components: prompt construction (§
B.1
), PoC generation (§
B.2
), and PoC validation (§
B.3
).

The prompt construction component consists of multiple LLM-assisted sub-pipelines to generate CVE-specific guidance and static source–sink trace selection.
The PoC generation component generates a PoC using the constructed prompt and the PoC Validation component validates each candidate through compilation, execution and dynamic instrumentation.

B.1
Prompt Construction

PoC-Gym
constructs a structured prompt that combines vulnerability-specific context (§
B.1.1
), static analysis guidance (§
B.1.2
), and specific instructions to guide the PoC generation (§
B.1.3
).

B.1.1
Vulnerability Information

For each vulnerability, we collect the Common Vulnerabilities and Exposures (CVE) description
(
NIST 2026
)
and the Common Weakness Enumeration (CWE) description
(
MITRE 2026
)
.
The CVE description summarizes the specific vulnerability and its impacted project, while the CWE description describes the vulnerability class.
An LLM that has access to the source code of the vulnerable project and CVE & CWE descriptions of the vulnerability is prompted to return the specific CVE-specific goal and validation metrics to confirm the success of the generated PoC.

B.3
PoC Validation

After the agent returns a PoC candidate, the candidate is compiled and executed in the vulnerable version of the project with AspectJ instrumentation.
During execution,
PoC-Gym
ensures that a successful PoC corresponds to observable vulnerable behavior by following the validation process defined in Equation
3
.

Program Exists Successfully.

The PoC must compile and exit successfully with code zero. This filters out PoC candidates that fail due to syntax errors, unavailable dependencies, or runtime crashes.

Success Signal in the Output.

The PoC must include an explicit marker,
[VULN]
, in its output.
To prevent false positives that blindly print this marker, the prompt requires this marker to be printed only after a programmatic check that confirms the intended exploitation effect.

Sink Reachability.

PoC-Gym
verifies that the execution of the PoC candidate dynamically reaches the sink of the selected static trace.
AspectJ-based instrumentation is used to determine whether the sink location is covered during execution, ensuring that the PoC triggers the vulnerable sink.
An example of the AspectJ output is given in Listing
10
.
If the PoC fails to hit the expected sink, feedback to address that failure will be added to the next round of prompting.
Listing

which includes explicit information about if the source and the sink is hit and the trace coverage percentage.

Appendix E
Discussion Details

In this section, we provide a detailed qualitative analysis of failure modes observed in
PoC-Gym
to support the results discussed in Section
3.2
.
We analyze representative PoCs that were marked as successful by the automated validation mechanism of
PoC-Gym
but do not exploit the intended vulnerability, and trace these failures to specific stages of the LLM-driven pipeline.
We examine how errors introduced during CVE prompt construction, static trace selection, and exploit generation propagate downstream and result in failure patterns.

E.1
Error Propagation

Errors introduced in early stages of the pipeline can propagate downstream and directly affect the validity of the generated PoC.
When the CVE description or the selected static trace is unrelated to the ground-truth vulnerability, the LLM is guided toward an incorrect exploitation strategy.
We refer to this class of failures as
unrelated errors
, as the generated PoC is consistent with the provided context but disconnected from the actual vulnerability.

E.1.1
Description Based Error

In description-based errors, the CVE context provided to the LLM is too generic or not enough specific to the actual vulnerability.
As a result, the model lacks the information needed to reason about the real exploitation path and produces a PoC that only superficially triggers the vulnerability.
In the example below (CVE-2018-1002200), the prompt in Listing
13
describes a general class of path traversal vulnerabilities but does not explain the specific vulnerability in the target project.
As a result, the generated PoC in Listing
14
does not interact with the vulnerable extraction logic and instead simulates the expected behavior, leading to a false positive.

E.2
External Validation

As shown in Appendix
E.3
, LLM-generated PoCs frequently declare success despite failing to exercise the true vulnerable code path, or they achieve the stated goal through mechanisms that do not constitute real exploitation.
Lightweight validation based on print statements or output markers is insufficient, as these signals are easily satisfied by hardcoded behavior, simulation, or benign execution paths.
To address this gap, we perform post-hoc validation using AspectJ-based dynamic instrumentation, comparing executed traces against ground-truth vulnerability sinks for each CVE.
This instrumentation exposes which methods and paths are actually executed during PoC execution, enabling us to distinguish genuine exploitation from superficial success signals and reducing reliance on validation mechanisms that can be trivially manipulated.

E.3
Error Categories

In addition to errors caused by unrelated descriptions or traces, or validation, we observe several failure cases that arise during PoC generation itself.
These errors occur even when the CVE and trace information is correct and show systematic behaviors of the LLM when creating an exploit and validating success.
We categorize these failures based on how the generated PoC deviates from the ground-truth exploitation mechanism.

E.3.1
Hardcoded

In hardcoded failures, the LLM inserts the expected exploit outcome directly into the PoC rather than triggering the vulnerability through the target project’s source code.
In the example shown below for CVE-2021-30181 in Listing
17
, the PoC introduces a custom
ScriptEngineFactory
implementation that returns fixed metadata and performs the execution in a locally defined module.
This implementation is unrelated to the vulnerable code path in Apache Dubbo and does not interact with the framework’s actual scripting or routing mechanisms.
As a result, the PoC satisfies the surface-level execution and output requirements but bypasses the real vulnerability entirely, producing a false positive.
