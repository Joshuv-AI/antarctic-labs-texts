WARBERT: A Hierarchical BERT-based Model for Web API Recommendation
Zishuo Xu, Yuhong Gu, Dezhong Yao

Abstract
With the emergence of Web 2.0 and microservices architecture, the number of Web APIs has increased dramatically, further intensifying the demand for efficient Web API recommendation. Existing solutions typically fall into two categories: recommendation-type methods, which treat each API as a label for classification, and match-type methods, which focus on matching mashups through API retrieval. However, three critical challenges persist: 1) the semantic ambiguities in comparing API and mashup descriptions, 2) the lack of detailed comparisons between the individual API and the mashup in recommendation-type methods, and 3) time inefficiencies for API retrieval in match-type methods. To address these challenges, we propose WARBERT, a hierarchical BERT-based model for Web API recommendation. WARBERT leverages dual-component feature fusion and attention comparison to extract precise semantic representations of API and mashup descriptions. WARBERT consists of two main components: WARBERT(R) for Recommendation and WARBERT(M) for Matching. Specifically, WARBERT(R) serves as an initial filter, narrowing down the candidate APIs, while WARBERT(M) refines the matching process by calculating the similarity between candidate APIs and mashup. The final likelihood of a mashup being matched with an API is determined by combining the predictions from WARBERT(R) and WARBERT(M). Additionally, WARBERT(R) incorporates an auxiliary task of mashup category judgment, which enhances its effectiveness in candidate selection. Experimental results on the ProgrammableWeb dataset demonstrate that WARBERT outperforms most existing solutions and achieves improvements of up to 11.7% compared to the model MTFM (Multi-Task Fusion Model), delivering significant enhancements in accuracy and efficiency.

II
Related Work

API recommendation is a well-established problem that has been extensively explored over the years and continues to attract interest. Based on their approaches, we categorize the related work into four types: content-based methods, collaborative filtering (CF) methods, factorization machine (FM) methods, and hybrid methods.

II-A

Content based Methods

Content-based Web API recommendations are derived by analyzing the key features in the descriptions of mashups and APIs
[
14
]

We categorize content-based methods into two groups: recommendation-type methods and match-type methods.

Recommendation-type methods treat each Web API as a label for classifier training. In contrast, match-type methods evaluate each API individually against a mashup to identify matches, which generally demands greater computational effort. The former approach yields a comprehensive matching result for a mashup against the entire API repository. However, when the API repository changes, such as the number of available APIs, the recommendation method often retrains its model. This is because it establishes a mapping between mashups and APIs, commonly using the number of APIs in its task layer to generate predictions. Conversely, after adequate initial training, the match-type method usually continues to perform effectively without additional training, even as the API repository evolves. This adaptability stems from its focus on the inherent characteristics of both mashups and APIs, allowing it to adjust more smoothly to API landscape updates.

III-B

The Workflow of Web API Recommendation

In the actual scenario, the Web API recommendation process is divided into three steps. First, a recommendation model is designed. Second, the model is trained using data from the historical mashup API calls, with the mashup description
D^{m_{i}}
substituting for the requirement description
T^{m_{i}}
. Afterward, the developer submits the requirement description for a new mashup, the model will output a set of recommended APIs
S^{m_{i}}
from the API repository
A
that the developer can invoke.

In order to save the computational cost due to the large number of APIs, we add a step, called filtering. It will reduce the computational cost by removing APIs that are impossible to be called by the mashup. A complete end-to-end API recommendation framework consists of a filter and a matcher. The objective of the filter is to quickly fetch a set of candidate APIs
G^{m_{i}}=\{{a_{1}^{{}^{\prime}}},\ldots,{a_{j}^{{}^{\prime}}},\ldots,{a_{H}^{{}^{\prime}}}\}
from
A
. Top-
H
candidate APIs with high relevance scores for a mashup are selected using the permutation function
\sigma
. The goal of the matcher is to determine exactly whether each candidate API is likely to be called. It generates the recommended APIs
S^{m_{i}}
after ranking and selection. In our implementation, WARBERT(R) serves as the filter and WARBERT(M) serves as the matcher.

IV
Methodology

In this section, we first outline the overall architecture of WARBERT and describe the implementation of WARBERT for both components, then analyze its training process.

IV-A

WARBERT Architecture

Figure
3
shows the overall architecture of WARBERT. WARBERT consists of two main components, named WARBERT(R) and WARBERT(M).

WARBERT(R) treats API recommendation as a multi-label classification problem. Each possible API is a label. WARBERT(M) treats API recommendation as a retrieval process, assuming that both the descriptions of the mashup and the descriptions of the candidate APIs are expressed in the same semantic space. The semantic feature vectors generated from the mashup descriptions or the API descriptions are input into a classifier. The classifier determines the probability of the mashup calling the API.

BERT computes word embeddings from all words of the sentence, it captures semantic and generate contextual embeddings. With dual-component feature fusion, WARBERT(R) grasps more semantic features. With attention comparison, WARBERT(M) gives greater attention to discriminative words in API descriptions considering the mashup description.
For the hierarchical architecture, WARBERT(R) functions as a filter to generate potential API candidates based on its predictions, while WARBERT(M) matches these candidates with the mashup. The final matching result is a weighted average of the API relevance score vector predicted by WARBERT(R) and the mashup API similarity score vector predicted by WARBERT(M). Ultimately, we rank and choose the top-
N
APIs with the highest match scores and present them to the developer as a set of recommended APIs.

IV-B

Implementation of WARBERT(R)

IV-B
1
Computing Contextual Embedding

The mashup descriptions and API descriptions may contain noisy information. In this module, we can perform some pre-processing operations to reserve important information, such as abbreviation replacement and lemmatization
[
35
]
. The word sequence is then obtained through tokenization.

Given a description (API description or mashup description, in WARBERT(R) only mashup description is used), the word sequence of the mashup
m_{i}
description is denoted as
D^{m_{i}}=[d_{1}^{m_{i}},...,d_{n_{t}}^{m_{i}}]
, while the word sequence of the API
a_{j}
description is denoted as
D^{a_{j}}=[d_{1}^{a_{j}},...,d_{n_{t}}^{a_{j}}]
, where
n_{t}
is the number of words. The objective is to derive a representation for each word.

Traditional word embedding models are trained using a large corpus like Wiki. For each word, the model learns a global word embedding. However, the same word in different descriptions may have different contextual information. A single word embedding cannot distinguish between two meanings, making the semantics less accurate. This means that we need to generate different embeddings for the same word under different contexts.

Pre-trained language model BERT has demonstrated exceptional performance across various NLP tasks
[
37
]
. It leverages deep neural networks with multiple Transformer layers
[
38
]
. Transformer models excel at capturing long-range dependencies in input sequences and directly relate words with arbitrary spacing
[
39
]
. Under the Scaled Dot-Product Attention mechanism, the contextual information about words is obtained.
BERT further encodes word position information as vectors to incorporate word order. This position-aware word embedding enables the network to capture word spacing semantics.

Based on the above characteristics, WARBERT uses BERT to generate contextual embedding
\widehat{V}
of dimension
F
.
For the word sequence of the mashup
m_{i}
description, we use a special format for input to the model:

\displaystyle\widehat{V_{r}}=BERT([CLS],D^{m_{i}},[SEP]),

(2)

where [SEP] is a special segmentation token and [CLS] is the classification token.
Through BERT, the model learns to obtain the focus in the whole sequence.

IV-B
2
Classifier Utilizing Dual-Component Feature Fusion

Once the contextual embedding
\widehat{V_{r}}
is obtained, we derive the semantic feature embeddings for the mashup by leveraging the pooler-output of the contextual embedding and applying Mean-Pooling to the contextual embedding. These two feature embeddings are then individually passed through two fully connected layers
FC_{p}
and
FC_{m}
.

\displaystyle U_{p}=W_{p}\cdot Pooler(\widehat{V_{r}})+b_{p},

(3)

\displaystyle U_{m}=W_{m}\cdot MeanPooling(\widehat{V_{r}})+b_{m},

(4)

where
W\in\mathbb{R}^{L\times F}
and
b\in\mathbb{R}^{L}
are learnable parameters, with
L
representing the number of APIs.

A fusion layer
FC_{f}
is then employed to generate the API relevance score vector
v_{r}
after concatenating
U_{p}
with
U_{m}
. The vector
v_{r}
is determined following the application of a sigmoid activation function.

\displaystyle v_{r}=sigmoid(W_{f}\cdot[U_{p};U_{m}]+b_{f}),

(5)

where
W_{f}\in\mathbb{R}^{L\times 2L}
and
b_{f}\in\mathbb{R}^{L}
are learnable parameters.
Furthermore, by substituting the number of APIs with the number of API categories in the fully connected layers
FC_{p}
,
FC_{m}
, and
FC_{f}
, WARBERT(R) can also judge the category of the API that the mashup may utilize.

IV-C

Implementation of WARBERT(M)

IV-C
1
Attention Comparison

In WARBERT(M), the same mashup description is matched against different API descriptions with different weights for the words. For example, when Yelp is matched with the Social API like Twitter, the word ”reviews” in the API function will be given higher weight.

The Transformer structure already uses the expressive attention mechanism. On this basis,
for the word sequence of the input API
a_{j}^{{}^{\prime}}
description and mashup
m_{i}
description, we use a special format:

\displaystyle\widehat{V_{m}}=BERT([CLS],D^{m_{i}},[SEP],\allowbreak D^{a_{j}^{{}^{\prime}}},[SEP]).

(6)

In this configuration, the self-attention mechanism is applied not only within each individual word sequence but also across the compared word sequences. By utilizing a multi-layer Transformer, the model learns to identify focal points within both sequences.
In the API task layer
FC_{t}

m_{i}
and
a_{j}^{{}^{\prime}}

\displaystyle r^{m_{i}}_{j^{{}^{\prime}}}=sigmoid(W_{t}\cdot Pooler(\widehat{V_{m}})+b_{t}).

(7)

By applying this methodology on each candidate API in
G^{m_{i}}=\{{a_{1}^{{}^{\prime}}},\ldots,{a_{j}^{{}^{\prime}}},\ldots,{a_{H}^{{}^{\prime}}}\}

\displaystyle v_{m}=[r^{m_{i}}_{1^{{}^{\prime}}},\ldots,r^{m_{i}}_{j^{{}^{\prime}}},\ldots r^{m_{i}}_{H^{{}^{\prime}}}].

(8)

IV-D

Hierarchical Architecture with WARBERT(R) and WARBERT(M)

We utilize fine-tuned WARBERT(R) to generate
H

\displaystyle v=\lambda*v_{m}+(1-\lambda)*v_{r},

WARBERT uses the binary cross entropy function to compute the classification loss in both tasks. During training WARBERT converges to a state where it fits the dataset well via backpropagation.

Experiments And Analysis

To evaluate the effectiveness of WARBERT, we need to answer the following research questions:

RQ1: How effective is WARBERT in recommending accurate Web APIs when compared with the baseline models?

RQ2: How effective is WARBERT(R) in the auxiliary task mashup category judgment compared to the model MTFM and MTFM++?

V-B

Baseline Models

There is no universal benchmark for the API recommendation problem. Therefore, we use some representative methods as benchmarks. These include the previous solution FC-LSTM, SPR, RWR, MTFM and its variant MTFM++. We summarize these methods in the following.

•

FC-LSTM
: FC-LSTM uses an additional attention mechanism based on the LSTM model. The attention mechanism is used to mine the function features in mashups and APIs. In addition, FC-LSTM also uses LDA models for text enhancement. To ensure fairness, we disable this strategy
[
22
]
.

•

SPR
: The Service Profile Reconstruction Model (SPR) uses topic modeling to analyze the connection between mashup descriptions and APIs. It offers API recommendations based on the topic structure of the descriptions
[
18
]
.

•

RWR
: The Random Walk with Restart (RWR) model encodes mashup-specific contexts in a knowledge graph and ranks Web APIs by relevance using a schema that models mashup requirements with category entities. The RWR algorithm prioritizes these entities to estimate API relevance
[
17
]
.

•

MTFM
: MTFM
2
2

2

The source code is at
https://github.com/whale-ynu/MTFM
is the model based on CNN. It uses a multi-layer CNN network to extract the features of the mashup and the API. It concatenates the mashup feature with all the API features to get the advantage of collaborative filtering. Furthermore, it combines multi-task learning, and uses mashup category judgment as an auxiliary task
[
35
]
.

•

MTFM++
: MTFM++ is an extension of MTFM. It additionally uses the category attributes of the API and constructs quality features using Quality of Services (QoS) related attributes. Due to the additional use of attribute data, MTFM++ requires more demanding data formats.

•

WARBERT
: The WARBERT framework encompasses three implementations, namely WARBERT itself, along with its component WARBERT(R) and WARBERT(M). All implementations are evaluated on their performance in the Web API recommendation task. Furthermore WARBERT(R) shows the model’s multi-task learning ability in the task of mashup category judgment.

To obtain embedding from text data, we follow the MTFM setting. Except for the implementation of WARBERT and RWR, all other models use the GloVe-6B pre-trained word embedding model. This model generates a 300-dimensional word embedding for each word. For WARBERT especially WARBERT(M), in order to mitigate extended consumption times and memory constraints, we use BERT-Tiny to fine-tune the entire model. BERT-Tiny consists of two layers of Transformer. In BERT-Tiny, each word is finally represented as a 128-dimensional embedding.

V-D

Evaluation Metrics

As our experiment is to judge whether the mashup and API match, we pay more attention to the quality of the correct recommended APIs. We use Precision and Recall as the common evaluation metric. Usually, users pay more attention to APIs with high match scores in the recommendation list. To follow other methods, we also use Top-
N
results to evaluate the model. We use
N
as 1, 5 and 10.

Precision@N refers to the ratio of the number of real hits in the
recommended APIs to the number of recommended APIs.

\displaystyle Precision@N=\frac{|\text{{APIs}}_{\text{{real}}}\cap\text{APIs}_{\text{top-N }}|}{|\text{APIs}_{\text{top-N}}|}.

(10)

Recall@N refers to the ratio of the number of real hits in the
recommended APIs to the number of all real APIs.

\displaystyle Recall@N=\frac{|\text{APIs}_{\text{real}}\cap\text{APIs}_{\text{top-N}}|}{|\text{APIs}_{\text{real}}|}.

(11)

Higher values for these metrics indicate greater accuracy and enhanced performance of the model.
Also, since Precision@N and Recall@N do not take into account the order in the results. We used additional evaluation metrics: MAP@N and NDCG@N. The Mean Average Precision (MAP) and Normalized Discounted Cumulative Gain (NDCG) are commonly used evaluation metrics in information retrieval tasks, and they consider the order in the results. NDCG is calculated from DCG by normalizing IDCG. IDCG is the ideal DCG. DCG takes into account the ranking order, so that the top ranked items gain more and the bottom ranked items are discounted.

\displaystyle DCG@N=\sum_{i=1}^{N}\frac{rel_{i}}{log_{2}(i+1)},

(12)

\displaystyle IDCG@N=\sum_{i=1}^{|realAPIs|}\frac{1}{log_{2}(i+1)},

(13)

\displaystyle NDCG@N=\frac{DCG@N}{IDCG@N},

(14)

where
rel_{i}=1/0
represents whether the
i
-th API is truly relevant to the current mashup or not. AP calculates Precision at each position, and averages over all matching positions.

\displaystyle AP@N=\frac{\sum_{i=1}^{N}rel_{i}*Precision@i}{\sum_{i=1}^{N}rel_{i}}.

(15)

MAP is obtained by averaging the Average Precision (AP) across all mashups
M
:

\displaystyle MAP@N=\frac{1}{|M|}\sum_{m\in M}AP_{m}@N.

(16)

Main Results

V-E
1
RQ1: Performance of WARBERT on Web API recommendation and comparison with baseline models

WARBERT achieves better performance than the other models in all metrics. Table
II
shows the results of the performance on the task of Web API recommendation. Since the average number of API calls for a mashup is 2, the upper limits of API recommendation Precision for Top-5 and Top-10 are 40% and 20% on average. WARBERT outperforms MTFM in all metrics. For Precision and Recall, WARBERT improves by up to 11.5% and 11.7%. For NDCG and MAP, WARBERT averages 9.6% and 10.8% improvements over MTFM.

FC-LSTM gives higher weight to the function information in the description to improve the effect. However, FC-LSTM considers the function information of the API to be composed of words that are semantically similar to the tag. So FC-LSTM needs additional tag information. Due to data heterogeneity, the tag information in the dataset may not be accurate. In WARBERT, the descriptions of the mashup and the API are compared directly. In the comparison process, WARBERT learns the key words, which leads to a performance improvement.

SPR outperforms FC-LSTM. Its hidden topic layer addresses the limitations of the bag-of-words model. It enables semantic connections between requirements and APIs even when documents are sparse. RWR surpasses SPR probably due to its more descriptive tag composition, which better captures developer requirements. However it also raises the operational complexity for users who must accurately and comprehensively articulate their needs.

For MTFM, it combines the advantages of collaborative filtering and multi-task learning. This makes its results better than RWR. However, also due to the requirement of multi-task learning, MTFM needs to contain labeled data in the dataset. This makes it more difficult for developers to operate. MTFM++ further imposes additional requirements on the data. The API is required with the corresponding QoS information to obtain the quality vector. Finally, in MTFM FIC (Feature Interaction Component), the mashup embedding and all API embeddings are concatenated together into a single embedding.

Compared to other baseline models, WARBERT has significant improvements in all evaluation metrics. WARBERT employs a lightweight variant of BERT for fine-tuning, implying that scaling the language model’s capacity could enhance its performance. Moreover, WARBERT does not require additional information to run, which makes it more general for use in actual scenarios. This also demonstrates the potential of WARBERT for further improvement by enriching information sources.

RQ3: Effectiveness of the Hierarchical Architecture of WARBERT

WARBERT demonstrates significant performance improvements over its individual components. Specifically, for Precision and Recall, WARBERT shows enhancements of up to 10.1% and 9.7% respectively compared to WARBERT(M). Additionally, for NDCG and MAP, WARBERT achieves average improvements of 7.5% and 7.4% over WARBERT(M). When compared to WARBERT(R), WARBERT’s Precision and Recall see improvements of up to 3.3% and 3.3%, with average enhancements for NDCG and MAP at 2.9% and 3.1%.

These results illustrate that the integrated workflow of WARBERT enhances the performance of each standalone model. WARBERT(R) plays a crucial role by filtering APIs that are less likely to be utilized, thereby saving time and safeguarding WARBERT(M) from inaccurate matches. Meanwhile, WARBERT(M) contributes by refining the matching process, ensuring that mashups are paired with the most relevant APIs.

V-F

Ablation Study

To answer RQ4-RQ6, we design the ablation models and conduct the ablation study.

V-F
1
RQ4: Effectiveness of Dual-component Feature Fusion

In WARBERT, the performance is significantly reduced when the dual-component feature fusion is replaced with utilizing a single feature. Specifically, by removing the feature vector from the pooler-output of the contextual embedding, we obtain WARBERT(RNP), and by removing the feature vector from the Mean-Pooling of the contextual embedding, we obtain WARBERT(RNM). Moreover, by substituting WARBERT(R) in the original WARBERT with WARBERT(RNP) or WARBERT(RNM), we obtain WARBERT(NP) and WARBERT(NM) respectively.

In the task of API recommendation, a comparison between WARBERT(R) and WARBERT(RNP) reveals a performance decrease ranging from 7.2% to 9.0% across all evaluation metrics. In contrast, when comparing WARBERT(R) with WARBERT(RNM), a more substantial performance decline is observed, ranging from 38.0% to 44.5%. Additionally, the comparison between WARBERT(NP) and WARBERT shows a reduction in performance of 4.6% to 6.5%, while comparing WARBERT(NM) with WARBERT results in a more significant decrease of 10.1% to 17.1%.

Similarly, in the task of mashup category judgment, WARBERT(RNP) experiences a reduction of 2.6% to 4.1%, while WARBERT(RNM) sees a more significant drop of 28.6% to 49.8%.

These results indicate that the dual-component feature fusion enhances model performance by providing more comprehensive semantics. Furthermore, they suggest that the feature vector from the Mean-pooling of the contextual embedding is more critical to the model’s performance than the feature vector from the pooler-output of the contextual embedding.

V-F
2
RQ5: Effectiveness of Attention Comparison

In WARBERT the performance is greatly reduced when the attention comparison is replaced with a simplified encoding concatenation approach.
We use BERT-Tiny to encode mashup descriptions and API descriptions separately. We then concatenate their pooler-output and feed them into the API task layer to get the similarity score vector. The variant is denoted as WARBERT(MNA), and by substituting WARBERT(M) in the original WARBERT, we derive WARBERT(NA).

Relative to WARBERT(M), WARBERT(MNA) exhibits a performance reduction ranging from 20.7% to 48.5%, whereas WARBERT(NA) shows a decrease of between 1.1% and 4.3% compared to WARBERT.

These results demonstrate that the attention comparison mechanism enhances the encoding process by prioritizing key terms within API functions when jointly embedded with mashup descriptions. Furthermore, this approach reduces semantic discrepancies between user-oriented mashup descriptions and developer-provided API documentation. By aligning these textual representations, the pooler-output more effectively captures nuanced semantic relationships and functional correlations between the two descriptions.

V-G

Summary

WARBERT achieves the best performance in all metrics. WARBERT shows its superiority over the baseline models and also demonstrates the effect of the hierarchical architecture by showing improvements over its component WARBERT(R) and WARBERT(M). We verify the effectiveness of the components of the WARBERT by ablation study and it shows the effect of the dual-component feature fusion and attention comparison strategy. We further investigate the impact of the candidate number

\lambda

VI
Conclusions

The WARBERT framework, with its architecture of WARBERT(R) as an efficient filter and WARBERT(M) for precise matching, has demonstrated exceptional effectiveness in the Web API recommendation task. It consistently outperforms existing methods by achieving superior metrics such as Precision, Recall, NDCG, and MAP, with enhancements exceeding 9. 6% to 11. 7% compared to MTFM. The proposed attention comparison mechanism and dual-component feature fusion enable a more profound understanding of API and mashup descriptions, which contribute to the framework’s outstanding performance. Experimental results highlight the framework’s advantage when combining both components, as opposed to using them individually. The ablation study illustrates the importance of the dual-component feature fusion and attention comparison and insights into the impact of the weighting factor
\lambda
and the candidate number
H
. Looking ahead, WARBERT holds substantial potential for future enhancements, including enriching information sources beyond mashup and API descriptions, and expanding the capacity of the underlying language model.
