SBOM generation based on code-level external component trees
Authors: Xianglong Kong, Hangyi Zhuo, Xinyuan Miao, Wei Huang, Jiayu Du
Published: 2025

ABSTRACT
AbstractA huge body of research and engineering efforts have been dedicated to extract and utilize software bill of materials (SBOM) due to the requirement of supply chain security. Existing approaches primarily rely on property files from dependency management tools, e.g., pom.xml from Maven, to generate SBOMs. However, the effectiveness of SBOM is directly affected by the bloated dependency and missing dependency problems during dependency management. In this work, we propose a source code-based approach to SBOM generation that only focuses on identifying the actually used external components. To support this, we introduce a novel structure called the external component tree (ECT), which organizes code-level dependency declarations at scale. We design three filters to eliminate programming language native, project-specific, and unused external components, and further applies subtree trimming algorithms to extract representative components from complex dependency hierarchies. Our approach is evaluated on 30 open-source projects in Java, Python, and Scala languages, comparing with CycloneDX-Generator, OpenRewrite, Build-Info-Go, and Microsoft SBOM-Tool. The results show that all SBOMs generated by our approach are correct, successfully addressing the bloated dependencies in the experiments. Furthermore, our method achieves a recall rate of 99.8%, the highest among all evaluated tools, indicating minimal component omission of actual software dependencies.Subject terms: Engineering, Electrical and electronic engineering

Introduction

Software Bill of Materials (SBOM) is a formal record that contains the details and supply chain relationships of various components used in the construction of software. It is emphasized in Executive Order that is issued by Biden on May 12, 2021. The components are commonly involved in terms of third-party libraries, which are called as external components to be differentiated from programming language native and project-specific components1. SBOM can enable effective detection and defense of software supply chain attacks2, for example, the SolarWind attack3 and the Log4j vulnerability4. It is traditionally marked as the prepositive step of Software Composition Analysis (SCA)5, and receives more and more attention in recent years due to the requirements of traceable and secure supply chain6,7. According to the Linux foundation report8, 90% of the surveyed organizations have started or are planning to generate SBOM for their products.

Existing SBOMs are mainly extracted from properties or building logs of dependency management tools, e.g., pom.xml of Maven9. These tools are designed to integrate various external components into a list, and they are intrinsically close to SBOM generation. SBOM is expected to remain readable for both human and machine10. The existing SBOM benefits from the well-structure properties of dependency management tools11. All popular SBOM tools require the property file to conduct SBOM generation6, and Microsoft SBOM-Tool claims that it can support 11 types of dependency management tools based on the component detection module1 e.g. Maven, NPM, and Pip.

However, the properties of dependency management tools are not always accurate12. There are some existing problems in dependency management, such as bloated dependency13 and missing dependency14. Bloated dependency refers to the declared external component that is actually not necessary to build or run it. Missing dependency means that the project involves an undeclared external component during compiling and building. The bloated and missing dependency can affect the effectiveness of existing SBOM generation methods and further reduce the security of SBOM related applications.

To address these problems, we apply program analysis methods to extract dependency declaration from source code, along with three challenges. First, the declarations of programming language native, project-specific, and third-party libraries are mixed in source code15. We need to identify the actually used external components among them. Second, an external component can be declared in many variations because programming specification requires developers to import the target API or class in the declaration. There may be thousands of variations for a specific external component in a large project16. It is hard to keep the massive source code-level SBOM readable for humans. Third, we need to investigate a feature fusion method for the information from source code and dependency management tools. The publishing information (e.g., version, publisher)17 should be extracted by matching the code-level external component with dependency properties.

In this work, we generate SBOM from source code in three steps. At first, to extract the actually used external components, we design three filters to remove programming language native, project-specific, and declared-but-unused components, respectively. Then, we propose a novel data structure, i.e., an external component tree, to manage the massive variations of components. We also define the node weight on the basis of the frequency of declaration. Finally, we propose trimming algorithms to generate human-readable descriptions of external components from the trees and match the publishing information from dependency management repository. In this way, we can generate direct dependency in the SBOM, i.e., the external components directly appear in source code or dependency properties. The transitive dependency in SBOM can be recursively generated by applying the three steps to the source code of the components in direct dependency.

We conducted experiments on 30 widely used open source projects to evaluate the effectiveness of SBOM. Our approach is compared with four popular SBOM tools, i.e., CycloneDX-Generator18, OpenRewrite19, Build-info-Go20, and Microsoft SBOM-Tool21. The experimental results show that our approach produces complete and correct SBOMs, effectively mitigating dependency bloat. It also achieves 99.8% recall, outperforming all compared tools by capturing nearly all actual software components with minimal omission. Benefiting from public-available source code of external components in direct dependency, our approach has the ability to exhaust the transitive dependency with some performance loss.

Motivating example

Existing SBOM generators extract external component dependencies based on properties or building log of dependency management tools like Maven. So the quality of dependency management will directly affect the precision of the SBOM. Once the content of the properties deviates, it will lead to inaccurate external component information. The bloated dependency would make the SBOM contain redundant components, and the missing dependency results in an incomplete SBOM22. We selected two projects from GitHub, i.e., Checkstyle2 and Async-http-client3 as motivating examples. Both projects are high-quality and well-maintained open-source software13. Checkstyle is a tool for checking Java source code for adherence to a code standard or set of validation rules and has 7.9k stars. Async-http-client is a Java library that allows Java applications to easily execute HTTP requests and asynchronously process HTTP responses. The library has 6.2k stars.

We present examples of existing dependency management problems in Fig. 1. In the figure, BD refers to bloated dependency, and MD refers to missing dependency. The number within the text represents the line number in related pom.xml. The red dotted arrow indicates the transitive dependency for the studied projects. There are one BD instance and one MD instance for each project in the examples.

Examples of existing problems in dependency management.

For the Checkstyle project, we can find that the external component org.checkerframework : checker-qual is not actually used in the project but is declared in pom.xml, while org.hamcrest : hamcrest-core is used in the project but not declared in pom.xml. The component org.hamcrest : hamcrest-core is a dependency of the direct component JUnit. The JUnit directly exists in the SBOM, and org.hamcrest : hamcrest-core works as a transitive dependency that is missing in the SBOM. In addition, Checkstyle has a version constraint inconsistency of the dependency. The component org.xmlresolver : xmlresolver has two different versions in the SBOM.

For the Async-http-client project, we can find that the component ch.qos.logback : logback-classic is bloated dependency and component com.fasterxml.jackson : core is missing dependency. The com.fasterxml.jackson : core is firstly involved by com.fasterxml.jackson : databind, and then further involved by com.squareup.retrofit2 : converter-jackson. Both of com.fasterxml.jackson : core and com.fasterxml.jackson : databind are missed in the SBOM. The two-steps transitive dependency is hard to extract based on the dependency management properties.

Both of Checkstyle and Async-http-client projects have problems in dependency management, resulting in inaccurate SBOM obtained by the existing SBOM generators, e.g., CycloneDX-Generator and OpenRewrite. We have reported these problems to the online community, and the latest version has been fixed. To address the above dependency management problems during SBOM generation, we need to analyze the source code to extract more accurate information. We also find that the code-level external component is commonly represented as a sequence joined by slices and dot-like separator, or has hierarchical structure of the inner entities, e.g., org.junit.jupiter. The well-organized structure inspires us to investigate a method to manage the massive code-level declarations.

Approach

Our SBOM generation approach mainly contains three steps, i.e., extraction of external dependency based on three filters, construction of external component tree, and generation of human-readable SBOM. Figure 2 shows the overall framework. First, we parse the source code of the project to generate an abstract syntax tree and traverse it to extract all import declaration statements. The external components in the import declaration statements are identified based on three filters. Second, we traverse the dependency information of the external component, build an external component tree, and calculate the weight for each actually used external dependency. The weight represents the frequency of the declaration, it is attached with the last slice of the declaration, i.e., the leaf node of the dependency. Third, we trim the external component tree based on node weights. Then we extract an external components manifest using the trimmed external component tree. The necessary information such as supplier and version string is matched through the repository maintained by the dependency management tools. SBOM generation is intrinsically related to programming language specifics10. For different languages, we need to apply different program analysis tools to conduct abstract syntax tree (AST), and implement variants of our filter strategies. To simplify the illustration, we take Java projects as examples because Java is one of the top 3 widely-used languages and its ecosystem of third-party dependencies can enable the existing SBOM tools in a good manner23. We apply Eclipse JDT24 to generate AST for Java projects. For other programming languages, we can also use existing tools to obtain AST information. For example, we can apply the AST module25 to generate AST for Python projects, and we apply scala-parser-combinators26 to generate AST for Scala projects.

The overall framework of the proposed approach.

Extraction of external dependency based on three filters

By overriding the visit method of import declaration node within AST, we use a depth-first traversal algorithm to obtain all the candidate external components in the project. Then we design three filters to remove programming language native, project-specific, and declared-but-unused components.

The 1st filter for programming language native components. For a specific programming language, we crawl from the official documentation to extract basic packages. For example, we collect 224 basic packages from JavaDoc4 Then we scan the collected import declarations to remove the strings that belong to these basic packages. Basic libraries are commonly used to implement low-level operations, such as printing and iostream, which are not specific to business functionality. These components in Java commonly begin with java or javax.

The 2nd filter for project-specific components. An import declaration statement is divided into smaller elements using the “.” separator, with each element referred to as a slice. The import declarations commonly refer to classes or interfaces within a component, and the class/interface name generally corresponds to a file rather than a directory. Therefore, the last slice obtained by splitting the import statement is typically the class or interface name, which should be removed before traversal. When the last slice in the statement is a wildcard, e.g. “*”, it should also be removed. When we have removed the last slice, the other slice can correspond to the folder name in the project directory, i.e., the import string is actually a relative path. So we can traverse the project folders to check if one import declaration statement is matched with any path under the root of this project. If it is matched, this import declaration statement can be recognized as an import from project itself and needs to be removed.

The 3rd filter for declared-but-unused components. Unused import means the component is imported but not actually used in the project. Typically, the last slice obtained by splitting the import declaration is the class/interface name. And one import statement can be considered as an unused import if a class/interface name only appears in the import statement in projects. JDT package provides the SimpleName class, which is a type of AST nodes. In official document, it is described as an identifier other than a keyword, boolean literal (true, false) or null literal (null). So the class/interface name will be recorded in the SimpleName node in AST as a identifier. We visit all SimpleName nodes except the subtree of the import declaration node, and compare them with the class/interface names recorded in the previous step. In this way, the unused external dependency can be removed. When the the last slice is a wildcard, that is not suggested in high-quality project, we cannot detect it in SimpleName nodes, we roughly mark this declaration as an actually used dependency in this work.

By detecting and filtering the three types of components described above, we can obtain a list of external component declarations that contains only those actually used. However, some exceptional cases still need to be handled through subsequent steps, mainly of the following two types.

External components that do not need to be directly referenced in the project code. Some external components are used without appearing in import statements. These may be redundant dependencies or components usable without explicit imports. We identify such cases by comparing the detected components with entries in the project’s dependency configuration files. These configuration files are commonly stored in yml/yaml, conf/cfg, ini, properties, xml, toml, json and related files. According to the existing systematic study of configuration files27,28, we group the components may appear in configuration files into seven categories: database drivers (e.g., org.postgresql.Driver), connection pools (e.g., HikariCP sections), logging implementations (e.g., Log4j2 appender/encoder classes), framework integration tools (e.g., Flyway/Liquibase), testing tools (e.g., pytest plugins), type-checking plugins (e.g., the plugins field in mypy.ini), and hook tools (e.g., pre-commit hooks). For each category, we predefined search keywords–such as driver-class-name, deps, and plugins–to identify candidate components, and then cross-checked them against actual code samples to validate the external components. Our approach to extracting external components from configuration files is applicable only to the high-quality open-source projects analyzed in this study. In real-world scenarios, many custom configuration files exist, and we are currently unable to achieve complete matching for them.

External components imported via the Reflection mechanism. Reflection mechanism allows runtime class loading without import statements, most notably through Class.forName(). This method loads and initializes a class at runtime if it is present in the classpath and its fully qualified name is correct, after which instances and methods can be accessed via newInstance(), getMethod(), and invoke(). To detect such components, we traverse all MethodInvocation nodes in the AST, checking for Class.forName() calls by resolving their method bindings. If matched, we extract the parameter string (the fully qualified class name) as a candidate component.

We detect all Class.forName() calls and extract their parameter strings as potential external component names. This is implemented by passing an ASTNode instance to the CompilationUnit.accept() method and overriding the visit() method for MethodInvocation nodes to traverse all method calls in the compilation unit. Each node is checked via resolveMethodBinding() to confirm it references Class.forName(). If confirmed, its arguments() are parsed to obtain the fully qualified class name. Since classes loaded with Class.forName() are always instantiated at runtime, they bypass unused-component filtering but are still checked against the native and project-specific components.

After applying these strategies, the declarations list which only contains the set of truly used external components. We then parse configuration files to identify components usable without explicit imports. The two sets are merged to produce the final external dependency list, which serves as input for constructing the external component tree.

Construction of external component tree

Based on the list of external components, we propose a novel data structure, i.e., external component tree (XCT) in this work. The external component tree can be represented as . Name represents the set of slices and is the set of nodes of external component tree. And Dep represents the set of relationships between slices and is the set of edges of the external component tree.

For Java projects, the fully qualified name of an external component usually has a “.” symbol as a separator, such as com.alibaba.fastjson, which is called as a package name. Oracle has the following restrictions29 on the naming rules of package names. Package names are written in lowercase to avoid conflict with the names of classes or interfaces. Companies use their reversed Internet domain name to begin their package names. For example, com.example.mypackage represents a package mypackage is created by a developer at example.com. According to these restrictions, it is guaranteed that each slice obtained is a meaningful string. For slices obtained from the same package name, the slices located in the back are subordinate to the slices located in the front (e.g., in the case of com.alibaba.fastjson, fastjson is subordinate to alibaba).

Construction of external component tree

Algorithm 1 presents the details of external component tree construction. We accept a set of external components as the input and traverse the set to construct a tree. We split the component name string into slices, and use slices to construct a node of the tree. It should be noted that different components have different first slices, so we create a virtual node ROOT as the root node of this external component tree. If the current slice is the last segment of a component name, the node is recognized as a leaf node to represent the component, and the weight field of the leaf node is filled in at the same time. The weight is defined as the number of times the component is represented by the source code. After this, a preliminary external component tree is constructed. Figure 3 shows an example external component tree of the project handlebars. We collect 609 code-level import declarations for handlebars, and split the declarations into slices with “.” separator. The declarations with the same prefix (e.g., company and groups) can be merged into a subtree. For example, an import declaration like “import org.antlr.v4.runtime.ANTLRErrorListener” will be treated as “import org.antlr.v4.runtime” according the second filter during the extraction of external dependency, because ANTLRErrorListener is a class with the runtime lib. And, this dependency can be marked as org(0).antlr(0).v4(0).runtime(1) in the external component tree. The declaration “import org.antlr.v4.runtime.dfa.DFA” is marked as org(0).antlr(0).v4(0).runtime(0).dfa(1) beacuse dfa is a sub-package within runtime lib and DFA is a class within dfa. In this way, the 609 code-level import declarations can be merged into the external component tree in Fig. 3.

Generation of Human-readable SBOM

For the external component tree, the path from the root node to a leaf node is the fully qualified name of the component (or package/class within the component). The leaf nodes represent the import targets of the dependency declarations. We design a recursive trimming algorithm to generate a human-readable SBOM. Algorithm 2 shows the details of this process.

XCT trimming

At first, we accept the ROOT node of the external component tree as curNode, then we traverse the XCT by visiting the child node of curNode. If we encounter a node whose weight is greater than 1, then this slice is directly used in the projects, and we end the external component with it. We also set a threshold value for the traversing process, the threshold value determines the length of the dependency name. The threshold value can make our trimming algorithm fit to different forms of external component of different programming languages. In the Java example, it is set to 5. According to the results obtained by the existing SBOM generation tools, the length of the fully qualified name of an external component is generally not less than 3 and not greater than 5 slices, which means that the depth of one path in the external component tree should be between 3 and 5. In addition, according to the naming restrictions of the Java package, the first two slices of a fully qualified name refer to the reversed Internet domain name of package supplier. The third and fourth slices refer to the region or the project name in order to resolve the name collisions that occur within a single supplier. The fifth slice represents the package or class/interface in the project. This is also the reason we set the threshold value of readable depths to 5. Once the depth of the node is greater than 5, this fully qualified name most likely points to a class or a interface under a project. When we finish traversing the external component tree, a set of paths in this external component tree can be obtained.

When we obtain a list of representative external components for each subtree, we further obtain the related publishing information, i.e., publisher, version, licenses and description from Maven online repository to construct SBOM. This information can be obtained from the machine-readable list of the external components mentioned above. With a moderately abstract component name and the necessary additional information, a human-readable SBOM can be constructed.

Tool implementation

We implement a tool according to the above methods, and propose a logical view30 in Fig. 4, which presents the class diagram of our tool The main functional components are implemented in SBOMTool.java file, such as the three filters and the extraction of external component trees. The SbomComparator.java file contains the experiment related methods, and the AstanalyzeApplication.java is the entry of the tool. The generation of SBOM is based on an integrated AST parser, that is also used in our previous work31,32.

Class diagram of the tool implementation.

The SBOMTool.java file parses project source code to extract external component dependencies based on the AST parser, and handles building and pruning the external component tree. The tree is built primarily by traversing the AST and filtering to identify the external components that are actually used. Through trimming, the external component tree can output a list of external components that includes only direct dependencies. Then it retrieves release metadata from the online repositories of dependency management tools and recursively resolves transitive dependencies to produce a complete SBOM. The source code of the implemented tool is available in our online repository, https://github.com/xlkong/SBOMdata/tree/main/SBOMGenerator.

Benchmarks

To measure the precision, we first build a benchmark based on all of the generated SBOM. We aggregate the outputs from our approach and four studied SBOM generators, treating the overlapping (consensus) dependencies as correct. Given the quality of these tools, co-occurring dependencies are highly reliable. Though our approach has not been proven in public, the integration cannot lower the accuracy of the other four widely used tools, because we only collect the completely consensus components from the results33. For the dependency that is only identified by parts of the studied SBOM generators, we further check it one by one based on project properties and code-level usage information, which is similar to an existing work34. The standards impose varying requirements on the contents of an SBOM35. In our work, we primarily focus on the dependency data itself to address issues of bloated and missing dependencies, while intentionally disregarding the associated publishing metadata during evaluation.

Bloated dependency. If one dependency appears in the SBOM generated by tools but not in the benchmarks, we mark it as bloated dependency. Bloated dependency is generally caused by inaccurate maintenance, e.g., developers may not remove deprecated dependency in a released version, or may not update properties in a timely manner.

Missing dependency. If one dependency appears in benchmarks but does not appear in the generated SBOM, we mark it as missing dependency. Missing dependency is commonly caused by two reasons. One of the reasons is that transitive dependency is directly used in the project. In this case, the project can still run, but it is bad for dependency management. If an update to a direct dependency causes the version of this transitive dependency to change, it may cause the project to fail to run normally. Another reason is that the project imports a local component and has not recorded it in properties.

To examine bloated and missing dependencies across the studied techniques, we run scripts to match the first three segments of collected component affiliations, for example, matching the groupId within the component tags of SBOM-Tool results with the group field in our results. According to the matching results of the five generators, we further compare detailed component names for one-to-one matching results. One-to-many matches are manually reviewed to identify overlapping dependencies.

A component is marked as a potential bloated dependency if it appears in property files such as pom.xml. Conversely, it is marked as a potential missing dependency if it is absent from these files. Our approach collects import declarations, usage locations, and components referenced in configurations during SBOM generation. For potential bloated dependencies, we verify actual usage by checking whether they are present in the code or build processes. We also attempt to remove them from property files and rebuild the project to confirm whether they are indeed bloated. For potential missing dependencies, we locate relevant code snippets or configuration files to verify their presence. A component is classified as a missing dependency if it is used in the project but omitted from the property files.

Since our manual inspection starts from inconsistent components identified by existing tools, we avoid large-scale source code analysis. For instance, in the largest project (neo4j), which contains 686k lines of valid code, we only need to examine 132 inconsistent components. Our component usage analysis is static: a dependency is considered actually used if it is found in the project. Dynamic checks for path accessibility were not performed due to limited experimental resources. We evaluate precision based on the prevalence of bloated and missing dependencies: fewer such issues indicate higher accuracy. Our benchmarks and the generated SBOMs are shared on a online repository, https://github.com/xlkong/SBOMdata.

First, our approach performs best among the studied SBOM generators in terms of precision. We have designed three filters to remove declared-but-unused code-level dependency, so we do not have bloated dependency in the generated SBOM. The number of missing dependency is also much less than that of other techniques, since we directly obtain the external components from source code and complete the list with the hidden components in configuration files. There are still some exceptions in our results. We look into related projects to find reasons. In javaparser, our approach has missed org.junit.vintage. This dependency is a thin layer on top of JUnit 4 to allow running vintage tests with the JUnit Platform launcher infrastructure. In neo4j, our approach has missed org.graalvm. The dependency org.graalvm is an ecosystem for compiling and running applications written in multiple languages. In kafka-python, our approach has missed flake8. This dependency is a Python code checker tool and can be invoked on the command line. These dependencies can not be scanned in any source code, dependency properties, and configuration files, so our approach cannot identify them as actually used dependency. These kinds of external components are commonly embedded in the execution environment.

Second, the precision of CycloneDX-Generator and Microsoft SBOM-Tool is similar. Both contain 18 missing dependencies and more than 140 bloated dependencies. The difference comes from several projects, for example, commons-configuration. For this project, Microsoft SBOM-Tool has one more bloated dependency than CycloneDX-Generator. The bloated dependency of SBOM-Tool in this project is commons-configuration, that is, SBOM-Tool adds the project itself to the SBOM as a dependency of this project. Project jenkins and project para-core are in the same situation. SBOM-Tool contains io.jenkins.plugins:caffeine-api as bloated dependency in project jenkins and contains para-core as bloated dependency in project para-core. And these dependencies are not in SBOMs generated by CycloneDX-Generator. So we believe that the difference between SBOM-Tool and CycloneDX-Generator is that CycloneDX-Generator can remove project-specific dependencies but SBOM-Tool will contain them in its SBOM. Both of the two tools generate SBOM strictly according to the dependency properties, so these two generators have relatively few missing dependencies in their SBOMs.

Third, OpenRewrite and Build-Info-Go can generate less bloated dependency than CycloneDX-Generator and Microsoft SBOM-Tool, and they have missed a large number of external components in their SBOMs. OpenRewrite and Build-Info-Go try to remove dependency in the test scope of the dependency properties. There are controversies about the test dependency in SBOM. To the best of our knowledge, certain attacks have been identified that infiltrate systems via components or configurations36 introduced during software testing. We suggest keeping test dependency in SBOM. The test removal methods in OpenRewrite and Build-Info-Go are not accurate, since they have removed much more dependencies that are used during building and compiling.

Finding 1All SBOMs generated by our approach are accurate, effectively addressing bloated dependencies observed in the experiments. Our method achieves a recall of 99.8%—the highest among all evaluated tools—indicating minimal omission of true software dependencies. OpenRewrite and Build-Info-Go generate less bloated dependencies than CycloneDX-Generator and Microsoft SBOM-Tool, and produce the most missing dependencies due to their test dependency removal strategy.

RQ2: Precision of transitive dependency in SBOM

The existing SBOM generators extract the transitive dependency by analyzing the properties, e.g., pom.xml of the external components. The extraction is limited by the dependency managements. Once a component in the supply chain manages dependency in other manner, e.g, use Gradle in the components that all use Maven, the extraction of transitive dependency would be interrupted. In this case, the existing SBOM generators only provide one-step transitive dependency in SBOM.

Unlike existing SBOM generators, we extract the SBOM mainly based on source code. The different settings of dependency managements cannot affect our work. Since the current external components are almost open source software, we can obtain the source code through online repositories. Our approach has the ability to exhaust the transitive dependency.

Due to the different levels of transitive dependency, we evaluate the precision of transitive dependency in a case study. For the example project alluxio, our approach can not only extract the one-step transitive dependency as the existing work, but also generate a two-steps transitive dependency, i.e., org.objectweb:asm:3.3.1. Threats to validity

Threats to internal validity. The main threat to internal validity lies in the potential fault during the construction of the benchmark. We follow our previous work33 to extract the overlapping components as the correct results. The benchmark has some limitations. The overlapping results may be wrong if the five studied techniques generate common model failures. This is a temporary solution for the trade-off of experimental resources and data integrity. To mitigate this threat, we validate suspicious external components in use by cross-referencing dependency property declarations with code-level import statements. The confirmation of the one-to-many group matching, and the existence check of potential bloated and missing dependencies contains manual work. To minimize human involvement, our manual work begins from the limited inconsistent components rather than the large-scale source code. The authors have carefully checked the results, and we have shared the benchmark online. We will continue to collect output results from more techniques to improve the validity of the dataset.

The extraction of external dependencies using the three-filter strategy may also brings in internal threats. This extraction process, which underpins the SBOM generation, involves AST construction and heuristic-based filtering. To mitigate this threat, the first two authors manually reviewed the generated results during the experiments. Our method relies on source code analysis, meaning it is only applicable when the source code for both the project and its external components is available. Our component extraction method is limited to the high-quality open-source projects. The pre-defined formats of configuration files are based on existing studies and our development experience. Currently, it cannot achieve complete matching for custom configuration files prevalent in real-world scenarios. The external component tree is designed for the well-structured dependencies, which may not be compatible with all programming languages.

Threats to external validity. We obtain the source code of four existing SBOM generators from GitHub, which may introduce potential threats to external validity. In our experiments, we use the default configuration settings, so the effectiveness of the selected techniques may differ from results in other evaluations. To mitigate this threat, we plan to extend our comparative analysis by optimizing the configurations for these tools. Our current experiments include 30 projects written in Java, Python, and Scala, which may not fully represent the generalization capability of the techniques. To address this limitation, we will conduct a more comprehensive analysis on projects in additional languages, such as C and C++, in future work.

Related work

In this section, we review related work on the design, generation, usage, and evaluation of SBOMs.

Design of SBOMs

As a formal document representing the external component dependencies of a project, the construction of SBOM must adhere to existing industry standards. The US National Telecommunications and Information Administration (NTIA) has identified three widely used SBOM specifications: Software Package Data Exchange (SPDX), CycloneDX, and Software Identification (SWID) Tags35. The SPDX specification37 was developed by the SPDX Workgroup under the Linux Foundation. An SPDX document includes fields such as package name, version, license, URL for vulnerability disclosure, and relationships between software packages. CycloneDX, proposed by OWASP (https://github.com/CycloneDX/), provides standardized formats in XML, JSON, and Protocol Buffers, along with a wide range of officially supported and community-contributed build tools. SWID tags are defined by the ISO/IEC 19770-2:2015 standard (https://csrc.nist.gov/projects/Software-Identification-SWID), and defines a lifecycle in which a SWID tag is added to the endpoint as part of the software installation process and removed during uninstallation. The standards require different factors in SBOM. Our results mainly focus on the dependency itself to address bloated and missing dependency problem, regardless of the attached publishing information during evaluation.

Generation of SBOMs

Most of the current work obtains the external dependencies of the project by parsing dependency properties or using package manager plugins. Xiao et al.1 gathered the distributed code (JAR files) linked to the SBOMs and designed JBomAudit to automatically detect dependency inconsistencies between SBOMs and the code. Their results confirm widespread non-compliance in official SBOMs for open-source Java projects. Ivan et al.38 use the dependency:tree and dependency:resolve instructions provided by Maven to build the dependency tree of each POM and resolve conflicts and duplications, thereby solving the problem of over-expansion of vulnerability dependency reports in open source software. Kula et al.39 studied the update frequency of external component dependencies of 4659 projects based on the Maven dependency properties in GitHub. Bodin et al.40 implemented a code-based Node.js application vulnerability detection tool that uses parsing of the package.json file and modules directory to extract third-party dependencies and bill of materials for Node.js project. Prana et al.41 proposed an analysis method that combines static and dynamic analysis of call graphs to check the reachability of vulnerable dependencies. Pereira et al.42 obtained SBOMs based on binary-level information, and prevented disastrous supply-chain attacks based on zero-shot Learning. In addition, the industry has also produced some tools for building SBOM. CycloneDX-Generator18 is a polyglot tool and a library for generating SBOM for most applications and container images with a single command. For Java projects, it detects and scans package manager such as Maven or Gradle to obtain dependencies. Rewrite-maven-plugin19 executes rewrite:cyclonedx to generate a CycloneDx SBOM outlining all the project’s dependencies, including transitive dependencies by parsing pom file. Build-Info-Go20 is a Go library, which allows generating build-info for a source code project. It includes all the details about the build broken down into segments that include version history, artifacts, project modules, dependencies, and everything that was required to create the build. Microsoft SBOM-Tool21 is a highly scalable and enterprise ready tool to create SPDX 2.2 compatible SBOMs for any variety of artifacts. The tool uses the component-detection libraries to detect components and the ClearlyDefined API to populate license information for these components.

Use of SBOMs

SBOMs are mainly used in vulnerability management during software composition analysis. Lemay and Katiyar43 assess their supply chain’s vulnerability to XZ-type infiltration by incorporating maintenance-related metadata from GitHub and npm repositories to SBOM data. They defined key features contributing to this risk and developed a metric to identify high-risk cases. Additionally, the study highlighted instances where developers made tradeoffs between productivity and technical debt, including cybersecurity risks. Pashchenko et al.44 carried out a qualitative study based on semi-structured interviews with 25 developers, exploring their practices in selecting, updating, and managing dependencies, as well as their strategies for mitigating vulnerable components. Benedetti et al.45 conduct security analysis of vulnerability detection tools that use SBOMs as input, and introduce PIP-sbom, that enhances component identification and dependency resolution. They analyze the impact of SBOM generation by feeding SBOM outputs into vulnerability identification software, identifying the root causes of these tools’ inefficiencies. Kloeg et al.46 investigate the roles of various business stakeholder groups in SBOM production and consumption, aiming to understand who drives or inhibits SBOM adoption and why. The analysis finds that System Integrators and Software Vendors show the highest potential for SBOM adoption, while B2B customers and Individual Developers demonstrate the least motivation. The findings suggest that overall SBOM adoption remains limited and would require substantial external incentives to gain broader traction.

Evaluation of SBOMs

Stalnaker et al.47 proposed a comprehensive study of SBOM to discuss the related challenges and solutions. Their results show that SBOM specifications are complex, and the currents SBOMs are inaccurate and incomplete to some contents. Xia et al.6 conducted an empirical study to interview and survey SBOM practitioners. They applied a mixed qualitative and quantitative method for gathering data from 17 interviewees and 65 survey respondents. They also found that SBOM practitioners generally believe that the quality of SBOM needs to be improved. Nusrat et al.7 outlined the top five benefits and challenges of adopting SBOMs, identified by reviewing 200 Internet articles. Balliu et al.10 deep-dived into 6 tools and the generated SBOMs for complex open-source Java projects. Mirakhorli et al.48 conducted an extensive empirical analysis to assess the current landscape of open-source and proprietary tools related to SBOM. Rabbi et al.49 compared four SBOM tools for JavaScript projects, and obtained significant performance variations. These tool survey work commonly mentioned that most of SBOM tools have a high false positive rate, and many practitioners commented that the industry lacks the tools to accurately and automatically generate SBOM data at scale for a product’s supply chain. Nocera et al.50 mined projects from GitHub to evaluate the adoption of SBOMs.

Most of existing surveys confirm that SBOM generation is necessary for software industry, and the current SBOM tools are insufficient. One important reason is that they rely on dependency properties and package manager to generate SBOM. In this work, we obtain dependencies based on static code analysis to improve the construction method and precision of the SBOM.

Conclusion

This paper presents a novel source code-based approach for generating accurate SBOM, aiming to overcome persistent issues such as bloated and missing dependencies in traditional metadata-based methods. By introducing the external component tree, we offer a scalable structure to manage fine-grained code-level dependency declarations. Through the use of three filters that target language-native modules, project-specific components, and unused dependencies, we can identify the actually used components. Furthermore, our trimming algorithms extract representative components from complex dependency hierarchies to construct precise SBOM. We evaluated our method across 30 open-source projects written in Java, Python, and Scala, comparing it against four state-of-the-art SBOM tools, i.e., CycloneDX-Generator, OpenRewrite, Build-Info-Go, and Microsoft SBOM Tool. The results demonstrate that our approach generates fully correct SBOMs, effectively mitigating the problem of bloated dependencies. Moreover, it achieves a 99.8% recall rate, outperforming all compared tools by capturing nearly all actual software components with minimal omission. Our system also supports recursive resolution of both direct and transitive dependencies by leveraging publicly accessible online repositories, albeit with some performance overhead. However, our approach requires access to the project’s source code, and extracting dependency information may affect performance. In the future, we plan to improve the efficiency of our method and extend its applicability to a broader set of programming languages and larger project scales. This work lays the foundation for more effective, source-based SBOM generation that aligns with the security needs of modern software supply chains.
