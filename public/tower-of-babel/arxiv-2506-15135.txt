Abstract

Programmers of distributed systems need to reason about concurrency to avoid races. However, reasoning about concurrency is difficult, and unexpected races show up as bugs.

Data race detection in shared memory systems is well-studied (dynamic data race detection
[
12
]
, behavioral types
[
14
]
, dynamic race detection
[
29
]
).

Similar to how a data race consists of reads and writes not related by happens-before at a shared memory location, a communication race consists of receives and sends not related by happens-before on a shared channel.
Communication races are problematic: a receiver expects a specific message from a specific sender, but with a communication race, the receiver can receive a message meant for another receiver, or not receive anything at all.

In this work, we describe a verification framework that can prove the absence of communication races for distributed programs that use a subset of the Go programming language, where synchronization is mainly achieved via message passing.
We statically reason about how a distributed program executes, using a happens-before order, extended to buffered and unbuffered channels.

Introduction

Distributed software is important in the digital world, with their footprint firmly anchored in many areas, from intelligent appliances to large-scale cloud systems. Java and C used to be preferred languages for writing such software, but languages such as Go have become more popular, due to its more lightweight and supposedly safer concurrency.

Despite its careful design which relies heavily on message passing to achieve synchronization, empirical studies
[
38
]
Liu2021AutomaticallyDA8668036 show that Go programs may still exhibit concurrency related bugs.
To ensure the safe and correct construction of Go programs, we propose a rigorous method to specify them, and demonstrate how to verify them using specifications.

In this work, we describe a formal verification framework that can prove that some sends or receives happen before other sends or receives.
We statically verify that a distributed program satisfies a protocol, by reasoning about a happens-before order, extended to buffered and unbuffered channels.
The happens-before order subsumes all possible sequential executions, therefore we can statically reason about all possible sequential executions.

Approaches to verify distributed programs can be categorised as follows:

1.

Dynamic approaches need to execute the distributed program, and therefore need to wait for messages to travel across the network.
Messages can take a long time to travel, or even longer if the messages are not delivered and must be resent.
Dynamic approaches includes runtime testing of distributed programs, which can only ever cover a small subset of all possible inputs and all possible interleavings.

2.

Model checking represents a distributed program as a state transition system.
To verify a property, all states are explored.
This does not scale with the number of interleavings of a distributed program.
To mitigate this scalability issue, advances in model checking include the following:

(a)

Having less information in the model, by abstracting more information from the distributed program.
Practical advances also increased the efficiency of model checking, allowing larger systems to be verified.

(b)

The properties to be verified are weakened.
This includes model checking only up to a bounded number of states, thus allowing infinite-state systems to be verified.
These kinds of bounded model checking can verify less properties than usual.

Although these advances have made model checking more attractive, the scalability issue is still prominent.

3.

Deductive verification verifies a distributed program without executing it.
Therefore, unlike dynamic approaches, deductive verification does not need to wait for messages to travel across the network.

Deductive verification can universally quantify over all possible interleavings, and use a domain-specific theorem prover to deduce satisfiability of the universally quantified logical formula.
Note that unlike model checking, deductive verification does not explore all possible interleavings, they merely reason about all possible interleavings.
Therefore, deductive verification does not have the same kind of scalability issues that model checking has.

Due to these differences of deductive verification with other approaches, we decided to verify Go programs deductively.

Our main contribution.

This work includes an extension of
Costea, 2017
to deductively verify that implementations that use a subset of the Go programming language satisfy communication protocols.
The verification specifically reasons about Go’s memory model.
In extending
Costea, 2017
’s work, we simplify their verification process by reducing the amount of formal machinery needed for verification.
For example, unlike
Costea, 2017
, we do not need to formalize the dual of guards, referred to by
Costea, 2017
as “assumptions”.
Representing communication protocols as partial orders helped us come up with this simplified verification process.

4
Overview

Go is a programming language that concurrently executes lightweight threads, called goroutines, with shared memory.
A goroutine is a sequentially executing program that expresses an order on lines of code
[
35
]
.

We consider Go programs that execute on distributed systems.
According to
van Steen and Tanenbaum, 2017
:

a distributed system is a concurrently executing collection of autonomous computing elements. Each computing element is called a node. Since nodes are autonomous, we cannot always assume that there is a global clock that synchronizes the actions of all nodes. The nodes:

1.

are geographically dispersed, so that sending and receiving takes a long time, and may be arbitrarily delayed.

2.

can join and leave the system, and the connection network between nodes continuously changes topology and performance.

The goal of this work is to describe a verification framework that can verify that an implementation satisfies a specification.
Users of our framework should follow the following software development methodology:
A specification designer writes a specification that the programmer’s Go implementation is supposed to satisfy.
A programmer writes a distributed Go implementation.
If our framework then verifies that the implementation does not satisfy the specification, then both the programmer and the specification designer should rewrite their implementation and specification.
On the other hand, if our framework then verifies that the implementation satisfies the specification, then users of our framework can be confident that the implementation always has properties that the specification guarantees, no matter what kind of interleaving execution the implementation can have.

4.3
Details of Verification

In this work, we restrict how a Go program can be verified as race-free: Go programs must use Go’s synchronization primitives to be verified as race-free.
Although Go’s sync package
[
37
]
defines many kinds of synchronization primitives, we require race-free Go programs to order their transmissions by synchronizing goroutines on an unbuffered channel.
We call such a synchronizing transmission on an unbuffered channel a “rendezvous” between the send and the receive of the transmission.
This restriction of synchronization to rendezvous simplifies verification, because the rendezvous is specified by the happens-before order over unbuffered channels, and our verification framework already models the happens-before order over unbuffered channels.

Although the given global protocol offers a global view of the communication, we opt for a modular verification where each channel endpoint in each party may be independently verified.
This means that verification can be parallelized.
To this purpose, the global protocol is projected onto parties, and then projected again onto channel endpoints.
Our framework then deductively verifies by using Hoare triples to consume the heads of each endpoint’s protocol.
The verification succeeds, because the implementation has rendezvous on channels
d
and
e
.
Each rendezvous forces all events before the rendezvous to happen-before all events after the rendezvous, even if these events occur in different parties.
Therefore, the parties in the implementation must communicate in a race-free way.

Channels in the Go Programming Language

Go channels are FIFO: if there is an
i^{th}
send and
i^{th}
receive on the channel, then the
i^{th}
receive on the channel receives data from the
i^{th}
send on the channel. If there is no
i^{th}
send on the channel, the
i^{th}
receive blocks until there is an
i^{th}
send on the channel.

A channel variable can be in shared memory, and accessed by concurrently executing goroutines.
We emphasize that despite the FIFO property of channels, a program may still send messages to unexpectedly different receiving parties.

Go channels are typed, and all messages on a channel must type check against the channel type. This may lead to runtime type errors if the channel type is something like a sum type, discussion of which is deferred to section
13.5
.
For brevity, in the rest of this work, unless necessary, we do not mention channel types, message types, and message values.
We still mention them in Go programs, because they are used by the Go compiler.
We also mention message values when we use the extended per-endpoint protocol syntax
1
.

A channel buffer stores the messages provided by sends on the channel, that have not yet been received.
Channel buffers have a nonnegative size and a nonnegative capacity.
The size of a channel is the number of messages currently stored on the buffer.
The capacity of a channel is the number of messages that can be stored on the buffer, before the buffer is full.
A channel with nonnegative capacity
k
is denoted by
{{c}^{k}}

An “unbuffered channel” is a channel with zero capacity, denoted by
{{c}^{0}}
.
A “buffered channel” is a channel with positive capacity, denoted by

If we do not care about the capacity of channel, we denote the channel by

sequence diagrams, each as observed by one of the goroutines.
Despite this, only one sequence diagram is enough.
This is because sends and receives of one goroutine cannot be observed to execute differently by another goroutine.
Therefore, it is enough to consider only the execution where each goroutine sees itself executing according to its program order, and all other goroutines also see that this goroutine executes according to the same order.
In other words, it is enough to show only one order of events (the program order) on each lifeline in a sequence diagram.

An execution may be shown as a sequence diagram with many goroutines.
Each goroutine has a lifeline.
Events of each goroutine happen on the lifeline, and happen in program order.
All events happen at a specific time on the global clock, along a specific horizontal line in the sequence diagram.
This explains why the executions of Go programs are sequentially consistent if the Go programs have only sends and receives.

According to
Fava et al., 2018
, for a memory model
inspired
by Go, executions of Go programs are sequentially consistent under data-race freedom (up to when an execution has a data race).
We believe this claim of sequential consistency also holds for the memory model of Go, for executions up to when the execution has a communication race.

\prec_{HB}

We define our
\prec_{HB}

Program order as mentioned in section

\prec_{HB}
.
Events not ordered by
\prec_{HB}
may either happen in either order, or may happen at the same time.

However, in our work, we do not take inspiration from Lamport’s other ideas. This simplifies our approach.
For example, although Lamport’s happens-before order is related to Lamport’s thread-local clocks, we do not define any local clocks.
Therefore, our approach is simplified because we do not have to synchronize any clocks.
In other words, we assume all events happen relative to the same global clock.
Although this assumption appears to contradict the characteristic of distributed systems that nodes are autonomous, this is assumption is sound in our work, because we focus only on verifying FIFO race-freedom.
To verify, we only need to prove that sends on one endpoint of a shared channel are ordered by
\prec_{HB}
, and that receives on the other endpoint of the same shared channel are ordered by
\prec_{HB}
.
It is reasonable to assume that events occuring on an endpoint happen relative to the same global clock.

Our

order differs from Lamport’s happens-before order
[

]
.

Lamport’s events happen instantaneously, whereas we use the terminology

[

happen over a duration.
2
2

Lamport’s happens-before order is a strict partial order over a set of events (irreflexive and transitive, therefore also asymmetric), whereas our happens-before order is also a strict partial order, but over a set containing both their starts and their completions. We must distinguish between the start of an event and its completion so that we can describe the events of a rendezvous with a
\prec_{HB}

Therefore, an unbuffered channel can be modelled by the two rules.
To apply rule (

A transmission on an unbuffered channel executes as in the rendezvous execution

The rendezvous execution

This assumes no propogation delay, because if the propogation delay is significant enough, then the completion of the send can happen-before the receive.
Significant propogation delay conflicts with the definition that the actual transmission happens instantaneously at some point during the overlapped durations.

Otherwise, we call this a “race-free global protocol”.
Unlike buggy executions with races, we do not consider a global protocol with races to be buggy, because the global protocol is the ultimate source of truth.
Therefore, we assume that the global protocol designer intended for the global protocol to have races.

8
Sequential Executions

A sequential execution is a special kind of execution.

A sequential execution that refines a global protocol is a linear order, ordered only by the
\prec_{HB}
relation, on both the starts and the completions of events, for all events.
The linear order of a sequential execution that refines a global protocol is a linearization with the same underlying set of events as the set of events in the global protocol.
The linearization contains the global protocol’s
\prec_{HB}
order, and maybe also contains some
\prec_{HB}^{{{c}^{\ast}}}
elements between sends and receives not in the global protocol, where each added
\prec_{HB}^{{{c}^{\ast}}}
can have different
{{c}^{\ast}}
.
In a sequential execution, all events must be atomic, so that there is no event between the start and the completion of an event.
Each added
E^{S}\prec_{HB}^{{{c}^{\ast}}}E^{R}
for some
{{c}^{\ast}}
means the receive
E^{R}
actually receives data from send
E^{S}
on channel
{{c}^{\ast}}
, and the completion of
E^{S}
happens-before the start of
E^{R}
.
Each added
E\prec_{HB}E^{{}^{\prime}}
means the sequential execution executes in such a way that the completion of
E
happens-before the start of
E^{{}^{\prime}}
.

Note that the linear order of a sequential execution does not include elements from the
\prec_{CB}
order of the global protocol: intuitively, a sequential execution does not care about how sends are specified to communicate with receives, it only cares about which receives actually receives data from certain sends (as given by
\prec_{HB}
).

We are motivated to define sequential executions, because in most cases, sequential executions are easier to discuss about than concurrent executions.
Sequential execution events are atomic, so that we can define sequential execution events to be instantaneous without duration.
Therefore, when discussing sequential executions, we do not need to mention the start or completion of a sequential execution event.
We only need to mention the sequential execution event as a whole.
As another consequence, sequence diagrams of sequential executions become more concise.
For the rest of this work, the only executions we will consider are sequential executions with atomic events, except for when we must consider concurrent executions, or except for when we are citing another work.

A sequential execution simulates a concurrent execution.
We are allowed to represent a concurrent execution with a sequential execution, because this is similar to how true concurrency semantics and interleaved concurrency semantics are indistinguishable for process calculi.
Interleaved concurrency semantics simulates true concurrency semantics by arriving at the same conclusion in two reductions instead of one reduction. Process calculi do not distinguish the proof of a conclusion by the number of reductions.

A true concurrency rule that reduces process

Similarly, the sequential semantics for any two events that concurrently access a shared channel (send and send, send and receive, receive and send, receive and receive) is a linearization of this concurrent access, with the condition that no other events happen in-between these two events.
Intuitively, this means the two linearized concurrent events are regarded by all other events to happen at nearly the same time.
This simulates that the two linearized concurrent events happen at the same time.

However, there is one case where a sequential execution does not simulate a concurrent execution.
If

We have described in section

We now define guards.
A guard

\Psi

In other words, a guard is an abstraction over how proposition

A verification proves a guard

An implementation satisfies a global protocol only if the implementation communicates according to the global protocol, and if the verification proves all the guards in the global protocol.

10.1
Projections

In this section, we show how to obtain local views of a given global protocol.
We do so by defining two projection functions to obtain “per-party protocols”, and “per-endpoint protocols”.
In a party, all channels actually refer to the channel endpoint that the party communicates on.
The resulting projected protocols guide the verification of an implementation.
We focus on applying our framework to verify that a Go program is FIFO race-free.

A given implementation is verified as follows.
A given global protocol is projected onto each party of the global protocol, to get per-party protocols.
Then, each party of the implementation is verified against the corresponding per-party protocol.
Each party of the implementation satisfies its corresponding per-party protocol only if its verification succeeds.
An implementation satisfies the global protocol only if all parties of the implementation satisfies their corresponding per-party protocol.

11
Conclusion

Our main contribution is the extension of
Costea, 2017
to deductively verify that implementations that use a subset of the Go programming language satisfy communication protocols, and we specifically reason about Go’s memory model.

We achieved this by doing the following:

1.

Represent Go programs as CFGs, thereby determining the program order of goroutines. Then, we combine the program orders with the send-receive order to obtain the
\prec_{HB}
order, which is different from Lamport’s happens-before order in that we can use the
\prec_{HB}
to represent a rendezvous.

2.

Recognize that a distributed Go program with only sends and receives is sequentially consistent up to races. This allows us to represent a global protocol or an execution with a sequence diagram.

3.

Define sequential executions, which are easier to discuss about than concurrent executions, because sequential execution events are atomic. Therefore, when discussing sequential executions, we do not need to mention the start or completion of a sequential execution event. This simplifies our thought process when considering which executions a global protocol has, and this also simplifies and increases the help in visual understanding that sequence diagrams give us.

4.

Define guards as proof obligations of whether an element exists in the
\prec_{HB}
order. This allows our verification framework to determine whether an implementation orders two events.

5.

Use guards to define race-free global protocols. If our verification determines that an implementation satisfies a race-free global protocol, then users of our verification framework can be certain that the implementation is race-free.

In doing so, we also simplify the verification process of
Costea, 2017
by reducing the amount of formal machinery needed for verification.

Related Work

12.1
Other Verification Approaches

We compare our approach to verification of Go programs, to other works with other approaches to similar problems.

1.

Dynamic approaches need to execute the distributed program, whereas our static approach does not need to execute the distributed program.
Despite the difference in approaches, our using of a happens-before order is similar to dynamic approaches that construct a happens-before order on-the-fly
[
34
]
.
Still, the dynamically constructed happens-before order depends on how the program executes.
The large number of possible interleavings of a distributed programs makes it unlikely that a single execution exhibits a behavior representative of many other executions, therefore the dynamically constructed happens-before order could be imprecise.

2.

Model checking approaches verify that a state representation of a program meets a specification.
According to
Gerrand, 2010
, the design of Go was influenced by Communicating Sequential Processes (CSP)
[
21
]
, therefore it is natural to represent Go programs with CSP.
Indeed,
Prasertsang and Pradubsuwun, 2016
proposes translating Go programs to a machine-readable version of CSP, on which tools like The CSP Refinement Checker
[
17
]
can be used.
Although we do not use a model checking approach, this representation with a process algebra suggests that Go programs are highly structured, and that we can use formal verification techniques on Go programs.
CSP is similar to another process algebra, the
\pi
-calculus.

Caires and Pfenning, 2010
has shown that the
\pi
-calculus and session types are related.
Therefore, it is not surprising that there have been many works on verifying Go programs with session types
[
6
]
DY2013lange2018verificationgabet2020static.
There is also a work that model-checks up to a bound
Lange et al., 2017
.

3.

Deductive verification approaches verify a distributed program without executing it.
Our approach is also similar to the deductive verification approach of
Oortwijn and Huisman, 2019
, in that we also use concurrent separation logic (CSL)
[
4
]
as the underlying logic.
CSL is used to reason about local concurrency, which is relevant to distributed programs. According to
Castro et al., 2019
, “distributed programming in practice often involves local concurrency: goroutines and channels are effective for dealing locally with the inherent asynchrony of distributed interactions.”.
Program states of concurrent programs can be deductively verified with CSL
[
39
]
or Concurrent Kleene Algebra (CKA)
[
20
]
.
However, verification techniques for local concurrency are not enough to verify distributed systems, and these verification techniques need to be extended.
Program states of distributed programs can be deductively verified with an extension to CSL
[
11
]
, or an extension to CKA
[
23
]
.
Our approach deductively verifies distributed Go programs by extending CSL with the Hoare triples (
Endpoint Send
), (
Endpoint Receive
), (
Data Send
), and (
Data Receive
).
This is similar to how
Ding and Sato, 2020
extends CSL with send and receive operations.

12.2
Global Protocol Syntax

Our global protocol syntax is similar to the abstract syntax tree (AST) global types syntax of
Honda et al., 2008
.

Honda et al., 2008
notice a limitation of expressiveness.
They identify that a safe process cannot be represented with abstract syntax tree (AST) global types
[
22
, Section 6.1]
.
The safe process they identified is the parallel composition of parties
P\equiv s!.t?
and
Q\equiv t!.s?
(each party sends before receiving).
Although we have a similar global protocol syntax, we do not have the limitation of expressiveness, because their ordering on events (definition 3.3 (prefix ordering)) differs from ours: in the global protocol
{A}\xrightarrow[{{c}^{\ast}}]{1}{B}\ssep{A}\xrightarrow[{{d}^{\ast}}]{2}{C}
, they order the two sending actions of
A
, whereas we do not order the two sending actions of
A
because they occur on different channels.

The safe process can be expressed as a global protocol in our syntax as
{P}\xrightarrow[s]{1}{Q}\asep{Q}\xrightarrow[t]{2}{P}
.
One limitation of our syntax is: the global protocol
{P}\xrightarrow[s]{1}{Q}\asep{Q}\xrightarrow[t]{2}{P}
also expresses implementations that deadlock.
Using the syntax of
Honda et al., 2008
, one such deadlocked implementation is the parallel composition of parties
P\equiv t?.s!
and
Q\equiv s?.t!
(each party receives before sending).
This limitation of our syntax can be mitigated by detecting implementations that deadlock with wait-for graphs
[
8
, Section 5.3]
, such that only safe implementations remain.

12.3
Considering All Sequential Executions

A recent work by
Fava and Steffen, 2020
detects data races for programs that use channel communications to coordinate accesses to shared memory. The authors considered extending the definition of happens-before with the FIFO order of channels, but the authors decided against this extension, because race detection is performed locally by each goroutine, so that a receiver can learn about events that the sender does not know about. Our work does not have this limitation, because we perform a global static race detection, instead of local race detection.

Additionally, there is an example in
Fava and Steffen, 2020
of how not extending the definition of happens-before with the FIFO order of channels results in a false positive (a data race is detected but there are actually no data races).
Their race detector detects a positive, because the write event and the read event are not related by happens-before.
This positive is false, because the FIFO order of the channel guarantees that the write event happens-before the read event.
If the definition of happens-before is extended with the FIFO order of channels, there are two possible sequential executions of concurrent receives (we use their notation for channels, therefore we do not indicate the channel capacity):

\displaystyle p_{1}\text{'s}\mathrel{\mathtt{rv}}\ {c}\quad\prec_{HB}\quad p_{2}\text{'s}\mathrel{\mathtt{rv}}\ {c}

(22a)

\displaystyle p_{2}\text{'s}\mathrel{\mathtt{rv}}\ {c}\quad\prec_{HB}\quad p_{1}\text{'s}\mathrel{\mathtt{rv}}\ {c}

(22b)

The false positive disappears if the receives linearize as in sequential execution (
22a
).

However, this example does not consider the other sequential execution (
22b
). This sequential execution is drawn as a sequence diagram
19
.
The example has the program
if r = 1 then load z
, so that the read event
load z
does not even exist if the sequential execution is (
22b
). There is one write event, but no read event for the write event to race with. In this sequential execution, a data race cannot occur, therefore there is no need to consider this sequential execution.

In general, for other programs, we cannot ignore such sequential executions.
If we modify the program in the example by replacing
if r = 1 then load z
with
load z
, then the read event exists, and the write event happens concurrently with the read event, therefore a data race occurs if the sequential execution is (
22b
).
Even if we extend the definition of happens-before with the FIFO order of channels, a data race could still occur. This means we need something other than FIFO order to avoid data races. Particularly, we need a global protocol with guards that tells us which one of the two sequential executions we should force the execution to go along. This is the inspiration for our main result: the root problem of the data race is an execution where a communication race occurs, and our solution is a global protocol with guards that gets rid of all executions that contain a communication race.

Our solution offers some improvements for this modified example.
Firstly, our solution considers all possible sequential executions, because we represent a global protocol with a partial order, and a partial order subsumes all linearizations of it.
Secondly, our solution relates the two concurrent receives by happens-before, so that we avoid the data race caused by the communication race.

13.3
Channels between Distributed Nodes

We understand that a send and a receive on a Go channel is not the same as a send and a receive between distributed nodes in a distributed Go program.
An unbuffered channel cannot communicate with other distributed nodes, whereas distributed sends and receives would for example be on Transmission Control Protocol sockets.
Nevertheless, the connections between distributed nodes can be modelled by buffered channels, which our framework analyzes.
Therefore, our work lays the foundation for future work, where messages on these distributed channels can be verified to satisfy certain properties.

13.4
Other Synchronization Primitives

Our approach of modelling only channels is similar to
Liu et al., 2021
, where although they mainly model channels, their framework can be extended to other synchronization primitives.
This is because other synchronization primitives, e.g. mutexes and condition variables, can be implemented with channels, and thereby are covered under their model.
It remains to show that our framework can also be extended to mutexes and condition variables.

Liu et al., 2021
does not say whether other synchronization primitives, e.g. WaitGroups, can also be modelled with channels.
On the other hand, we can use CSL to model other synchronization primitives with their own set of specifications.
For example, we claim Go’s WaitGroup is abstractly identical Java’s CountDownLatch, which
Chin et al., 2019
specifies with CSL.

The semantic conditions (

A lemma is unsound if the lemma can be used to prove that a global protocol with races is race-free.

We want to know whether

We are interested because if a lemma is sound, then we can apply it on a partial order, resulting in a partial order with more elements.
A partial order with more elements has fewer sequential executions.
Intuitively, our verification can rule out more run-time sequential executions, and take less time to analyze.

14.2.1
Transitive Closure

\prec_{HB}
is transitive. Yet, we avoid taking the transitive closure, because this can lead to confusion about which send a receive receives data from.
