AutoPatch: Automated Generation of Hotpatches for Real-Time Embedded Devices
Mohsen Salehi, Karthik Pattabiraman

Abstract
. Real-time embedded devices like medical or industrial devices are increasingly targeted by cyber-attacks. Prompt patching is crucial to mitigate the serious consequences of such attacks on these devices. Hotpatching is an approach to apply a patch to mission-critical embedded devices without rebooting them. However, existing hotpatching approaches require developers to manually write the hotpatch for target systems, which is time-consuming and error-prone. To address these issues, we propose AutoPatch 1 1 1 This paper has been accepted to the ACM CCS 2024 Conference and will appear in the conference proceedings. , a new hotpatching technique that automatically generates functionally equivalent hotpatches via static analysis of the official patches. AutoPatch introduces a new software triggering approach that supports diverse embedded devices, and preserves the functionality of the official patch. In contrast to prior work, AutoPatch does not rely on hardware support for triggering patches, or on executing patches in specialized virtual machines. We implemented AutoPatch using the LLVM compiler, and evaluated its efficiency, effectiveness and generality using 62 real CVEs on four embedded devices with different specifications and architectures running popular RTOSes. We found that AutoPatch can fix more than 90% of CVEs, and resolve the vulnerability successfully. The results revealed an average total delay of less than 12.7 μ ​ s \mu s for fixing the vulnerabilities, representing a performance improvement of 50% over RapidPatch, a state-of-the-art approach. Further, our memory overhead, on average, was slightly lower than theirs (23%). Finally, AutoPatch was able to generate hotpatches for all four devices without any modifications.

1.
Introduction

Embedded devices are used in every aspect of our lives,
from medical devices and power grids to everyday consumer products.
Due to the use of these devices in different places, especially in critical infrastructures,
they have attracted the attention of attackers (e.g., RIPPLE20
(
rip, 2024
)
).
Successful cyber-attacks on embedded devices can have serious, even life-threatening consequences. Therefore, manufacturers need to prioritize device security by promptly providing patches for vulnerabilities and ensuring regular device updates.

Studies have found it takes about three months to more than a year for a device to be patched after a vulnerability is discovered
(
He et al., 2022
)
. This is because manufacturers face two main challenges for patching vulnerabilities.
First, current updating approaches require rebooting or halting devices
to fix the vulnerability (
main challenge 1
), which
cannot be used in mission-critical places like medical devices.
For example, turning off critical health devices
(e.g., ventilators, pacemakers) may lead to serious consequences such as the death of the patient.
Second, device manufacturers need to manually write patches for each of their embedded devices,
which is a time-consuming and error-prone process (
main challenge 2
).

To address the first challenge, prior work has proposed hotpatching techniques
(
Chen et al., 2018
;
Chen et al., 2017
)

where the manufacturer can install the desired patch without stopping the device or tasks.
However, these approaches require runtime code modification,
which is not feasible for embedded devices since their code is stored on flash-based ROM.
To alleviate this issue,
HERA
(
Niesler et al., 2021
)
uses a hardware feature available in the Cortex-M3 and M4 generations of ARM processors
called FPB
(
FPB, 2024
)
(Flash Patch and Breakpoint Unit) to trigger the patch. However, newer generations of ARM (e.g., Cortex-M7)
(
NOF, 2024
)
and other microcontroller units (e.g., RISC-V)
do not have this hardware feature, and hence cannot use this approach.
Furthermore, even if the hardware feature is available,
developers still need to expend manual effort
to compare the patched and unpatched versions of the program and extract the differences
to generate the hotpatches.

To address the first limitation (i.e., relies on FPB),
RapidPatch
(
He et al., 2022
)
modifies applications to
add a branch instruction (trampoline
2
2

2

A single instruction, such as a branch or jump instruction, that is added to the application
to redirect its original control flow.
) at the beginning of each function
that will execute the desired patch after deployment.
Furthermore, they use the eBPF
(
eBP, 2024
)
(Extended Berkeley Packet Filter) virtual machine (VM), to execute
patches written in a specialized language.
However, their approach has two limitations.
First, using a VM incurs performance and memory overheads, which is often challenging for embedded devices, especially real-time embedded devices.
Second, the real-time operating system (RTOS) developer has to manually rewrite the patch in the eBPF language after writing the patch in C.
This is both time and effort-intensive, especially for larger patches resulting from CVEs.

To address the above challenges, we propose AutoPatch
3
3

3

AutoPatch was also presented as a 3-page poster at ACM CCS 2022
(
Salehi and Pattabiraman, 2022
)
.
, an approach for device maintainers to
automatically generate
hotpatches for their embedded devices
, and apply the generated patches
without halting or rebooting
these devices.
AutoPatch has two main goals:
1) Eliminate the need for using either a VM or hardware support,
and 2) Generating hotpatches requiring neither manual effort, nor the use of specialized languages by developers.

AutoPatch addresses the above goals through two innovations.
First, it proposes an instrumentation technique based on static analysis
to redirect the control flow and trigger the hotpatch to fix vulnerabilities.
However, the vulnerable function may have complex code patterns (e.g., dynamic loops), which makes them difficult to analyze statically by AutoPatch.
Existing methods
(
He et al., 2022
;
Xu et al., 2020
)
use either simplification or estimation techniques
to abstract the effect of the official patch and generate a hotpatch. However, the resulting hotpatch may not reflect the functionality of the original patch.
This is important for safety-critical embedded devices.
To address this issue, we insert trampolines into
all locations
that are difficult to be analyzed statically by AutoPatch. Thus, AutoPatch does not need to analyze the code at those locations to generate hotpatches.

Second, trampolines are in specific locations, while the official patch may be written anywhere in the vulnerable function.
This is because developers need not have any knowledge of where the trampolines are inserted, as per our goals.
Therefore, AutoPatch should generate the hotpatch so it can be executed by one of the
fixed instrumented trampolines,
and can also have the same effect as the official patch.
To do so, AutoPatch automatically analyzes the official patch using a backward static approach,
and generates a hotpatch that is functionally equivalent to the original patch, but can be executed
by one of the instrumented trampolines (goal 2).
Furthermore, AutoPatch operates on the official patch language (i.e., C or C++) to analyze and generate hotpatches,
eliminating the need for a VM or programming in an alternate language (goal 1).

Similar to previous work HERA and RapidPatch
(
He et al., 2022
;
Niesler et al., 2021
)
, we
support two commonly used types of security patches: (1)
filter
patches that check for malicious inputs, and
(2)
code replace
patches that replace vulnerable code with secure patched code.
These two types of patches are commonly used because they can address a large portion of existing vulnerabilities.
Therefore, in this paper we also consider these types of patches. This excludes any patch that requires changes in the global application’s state or data structures from our technique’s scope (similar to the other techniques).

To the best of our knowledge, AutoPatch is the first hotpatching framework that automatically generates hotpatches without needing either a specialized VM or manual effort.

Our contributions are:

•

Propose a new software triggering method for patches by using static analysis techniques
for inserting instrumentation into specific locations in the firmware.

•

Propose an automated static analysis method for analyzing the official patch
and generating functionally equivalent patches by using backward static analysis.

•

Design AutoPatch, a new hotpatching framework to integrate the software-based triggering with the
analysis technique. AutoPatch uses the former’s output before installing the firmware on the device. Then, it analyzes the vulnerable function and the official patch to produce
the functionally equivalent hotpatch.
AutoPatch is implemented using the LLVM compiler
(
llv, 2024a
)
, and hence supports different devices.

•

Evaluate AutoPatch on four different RTOSes - 62 real-world CVEs on diverse
security vulnerabilities and four different devices in terms of efficiency, effectiveness, and generality.

The results demonstrate that (1) the hotpatches generated by AutoPatch effectively address security vulnerabilities in the CVEs. (2) The average runtime overhead incurred by the entire AutoPatch execution is negligible (less than 12.7
\mu s
), resulting in a 50% average speedup over RapidPatch
(
He et al., 2022
)
.
This indicates that AutoPatch is better than RapidPatch in terms of overhead, despite requiring no manual effort.
Further, AutoPatch reduces the memory overhead by 23% compared to RapidPatch.
(3) The instrumented code by AutoPatch incurs a maximum performance overhead of
3.5\%
for real applications, when run on the embedded device.
(4) AutoPatch works with different embedded devices
without necessitating any changes to its implementation, which demonstrates its generality.

Background

2.1.
Terminology

A
RTOS developer
is an individual or a team responsible
for designing and implementing an operating system (e.g., Apache NuttX RTOS
(
Nut, 2024
)
and Zephyr OS
(
zep, 2024a
)
)
that provides real-time capabilities.
The RTOS developer is also responsible for releasing official patches to fix security vulnerabilities in the RTOS.

A
device maintainer
is an individual or a team that have multiple types of device products.
These people are responsible for receiving the generated patch (hotpatch) if their device uses a vulnerable
version of RTOS, and compiling it using the appropriate compiler and installing it on the target device.

2.2.
Real-Time Embedded Devices

Embedded devices are used in many application areas ranging from industrial control systems to smart homes and medical devices.
One class of embedded devices are real-time devices that have a specific deadline for their operation.
To manage real-time embedded devices and make sure that tasks do not miss deadlines,
these devices use special operating systems called real-time operating system (RTOS).
Examples of RTOS include FreeRTOS
(
Fre, 2024
)
, NuttX
(
Nut, 2024
)
,
VxWorks
(
VxW, 2024
)
, and Zephyr OS
(
zep, 2024a
;
zep, 2024b
)
.
These systems are often used in embedded systems and control applications
where it is important to have fast and predictable response times.
For example, an RTOS is used in medical devices to ensure
that patient vital signs are monitored and reported in a timely fashion.

2.4.
Hotpatching Techniques

Current hotpatching approaches use one of three main methods:
(1) A/B updating method, (2) instrumenting binary function at runtime, and (3) relocation linked binary libraries.

A/B method:
Patching approaches that use this type of method
(
Mugarza et al., 2020
;
Abs, 2024a
)

have two instances of the system at the same time, such as A and B,
one of which is running (A) and the other (B) is used for updates.
When the B update is completed, the old system A is transferred to the new system B.
This method requires storing the information of both instances simultaneously.
However, since embedded systems are memory-constrained, these methods are challenging to apply.
Furthermore, to transfer from system A to B, there is a need to reboot the device,
which is against the purpose of hotpatching.
For example, the authors use A/B method based on over-the-air (OTA) update for Espressif ESP32 MCU
(
Abs, 2024a
)
,
and Android devices
(
Abs, 2024b
)
.

Furthermore, many low power embedded devices such as medical devices cannot have multiple devices
due to power/form constraints.
For instance, one cannot install two pacemakers in a single patient’s body.
Further, even if a safety critical system has redundant devices executing in lock-step for reliability,
rebooting one device will affect the functionality of the entire system (as both devices need to agree on an operation for it to proceed).

Instrumenting function:
These methods
(
Rommel et al., 2020
)
modify and instrument the instructions of running program.
Due to the hardware characteristics of embedded devices
4
4

4

Flash-based ROMs are used in embedded devices to execute code.
,
the proposed approaches cannot change the code during the program’s execution for adding the trampoline,
and it requires clearing the entire flash sector.
As a result, the device must be halted or rebooted, which is against the purpose of hotpatching approaches.
Since this type of technique needs to modify the program at runtime to add the patch, they are not applicable for embedded devices.

Relocating linked binaries:
These approaches
(
Holmbacka et al., 2013
)
use a feature
called dynamic linking. This shared code piece is accessed by the operating system through a data structure that contains symbolic links, which are resolved during execution.
This feature is used for libraries that want to be shared between multiple applications.
For hotpatching the system, these approaches add patches by modifying these symbolic links at runtime.
However, dynamic linking is typically not supported in real-time embedded devices
as it incurs significant performance overhead, and adds uncertainty to the execution time
(
Niesler et al., 2021
;
He et al., 2022
)
.

3.
Motivation

In this section, we describe the main requirements of hotpatching
for real-time embedded devices (
3.1
).
Then, we examine current approaches in terms of how they address these requirements (
3.2
),
and finally how AutoPatch addresses them (
3.3
).

3.1.
Requirements

Like any other system, embedded software also has vulnerabilities,
which can be exploited by attackers to compromise safety (e.g., vulnerabilities in medical devices
(
Rushanan et al., 2014
)
).
We have identified five requirements that patching approaches for addressing vulnerabilities
in embedded devices should meet.
Existing approaches fail to meet these requirements,
leading to extended periods—ranging from three months to over a year—to address vulnerabilities
in embedded devices
(
He et al., 2022
)
.
We describe these requirements below.

R1:

Memory Constraints
: Embedded devices are designed with cost reduction as a primary consideration,
which leads to constraints in different parts such as memory.
Therefore, updating approaches should use the least possible amount of memory to fix the vulnerability.

R2:

No Rebooting
: Many real-time embedded devices are used in safety-critical applications like medical devices,
and hence there should be no interruption or delay in the execution of main tasks.
Therefore, the proposed approaches should fix vulnerabilities without interrupting or rebooting
the device.

R3:

No Special Hardware
: Embedded devices are designed for low power and low cost, and hence the approach should not rely on special-purpose hardware.
For example, there is a hardware feature called FPB
(
FPB, 2024
)

in the Cortex-M3/M4 series of ARM processors, but
later generations of ARM processors do not have it
(
NOF, 2024
)
(e.g., Cortex-M7)
and other microcontroller architectures.
Therefore, the proposed approaches should be general and applicable to most devices
without the need for special hardware.

R4:

Functionality Preservation (Soundness)

The generated patch must be functionally equal to the official patch
and must be able to have a similar effect on the vulnerable function to fix the security vulnerability.
This is because embedded devices are often used in safety-critical contexts,
and the generated patch applied to them must be functionally equivalent to the original patch.
Therefore, patching approaches should not use optimization or estimation approaches that are unsound
(e.g., loop summarization algorithms
(
Xie et al., 2017
)
).

R5:

Patch Generation
:
Existing approaches often assume that developers will write patches at functions’ entrance
(
He et al., 2022
)
.
However, in practice, the patch may be written anywhere in vulnerable functions
(e.g., the middle of the function in CVE-2020-10021, see Section
2.3
),
and hence developers must manually translate the patch to the beginning of the function (for example).
However, this process is time-consuming and error-prone, and requires significant effort from developers.

3.3.
Our Solution

We introduce AutoPatch, a hotpatching approach that proposes four solutions (i.e, S1-4) to
satisfy each of the requirements (R1-R5).

S1:

Addressing R1.
Due to memory constraints in embedded devices, AutoPatch stores only the generated hotpatches in the device’s memory.
In other words, the memory overhead depends on the official patch, and AutoPatch does not need to store entire patched function or any additional information.

S2:

Addressing R2 and R3.

We propose a software-only technique to address the issue of rebooting or halting the device
to fix vulnerabilities (see Section
4.2
).
This technique involves inserting trampolines in various required locations,
allowing for the triggering of generated hotpatches to fix vulnerabilities while the device is still running (R2).
Furthermore, using this technique, AutoPatch does not need special-purpose hardware for triggering the patches (R3).

S3:

Addressing R4.

Another benefit of our software triggering approach is that AutoPatch can generate a functionally equivalent hotpatch
based on the official patch to fix the vulnerabilities.
Therefore, since AutoPatch inserts trampolines in all instrumentation locations (e.g., after nested loops),
it does not need to use estimation or summarization approaches
(
Xie et al., 2017
)

to generate the hotpatches.

S4:

Addressing R5.

We proposed the first automatic hotpatching approach for real-time embedded devices.
To achieve this goal, AutoPatch analyzes the official patch using static analysis,
and automatically generates a hotpatch that can be executed by one of the trampolines.

3.4.
Assumptions and Adversary Model

Assumptions.

We make four assumptions as follows.
First, RTOS developers have already written the official patch for the security vulnerability,
and after the hotpatch is generated by AutoPatch,
the device maintainers have secure access to the patches.
We assume that AutoPatch has access to the source code of official patches as developers are the ones who use AutoPatch. However,
because AutoPatch operates on LLVM IR, it can also work if RTOS developers release patches in LLVM IR. Second, as in the previous techniques
(
Niesler et al., 2021
;
He et al., 2022
)
,
we assume that hotpatches are transferred in a signed and encrypted form, and so we do not consider malicious modifications of the patch itself.
Third, we assume attackers cannot modify the patch after it has been transferred to device maintainers.
Finally, similar to previous work
(
He et al., 2022
;
Niesler et al., 2021
)
, we assume that the
official patches written by the developers are correct (see Section
8
).

Adversary Model.

We assume attackers perform remote attacks on the device and do not have physical or root access to it.
However, attackers can exploit memory-safety related bugs (e.g., buffer overflows)
in the device to overwrite parts of the memory, and launch a
run-time attack.
As embedded devices’ firmware is usually tailored by the device manufacturers
and lacks support for user applications from external sources,
it is not possible for attackers to introduce harmful activities, such as executing third-party code,
through user applications.
Prior work
(
He et al., 2022
;
Niesler et al., 2021
)
has made similar assumptions.

the first automatic hotpatching approach for real-time embedded devices
by addressing the issues discussed in Section
3
.
We begin with an overview of AutoPatch and its key innovations (Section
4.1
),
before moving on to describe the different phases of the system in detail (Section
4.3
and Section

4.1.
Overview of AutoPatch

Our approach aims to derive and execute functionally equivalent hotpatches without relying on hardware or summarization approaches,
which we have discussed in Section
3
(see S2 and S3).
To achieve these goals, we propose two innovations. The first innovation is a novel software triggering method that involves
identifying appropriate locations for instrumentation
, and inserting trampolines
in those locations. We use this method in the instrumentation phase.

The second key innovation of our approach is the use of
backward static analysis

to automatically generate functionally equivalent hotpatches based on the official patches to address security vulnerabilities,
as well as the integration of the hotpatching process with the RTOS to ensure
that it does not interrupt the execution of other tasks (see S4 in Section
3.3
).
This is done in the analysis phase,
which includes an
analysis component (AC)
to generate corresponding patches for the RTOS.
After the hotpatch is generated using AutoPatch, it is released for device maintainers, to install on their devices if they use the vulnerable version.
Then device maintainers compile the hotpatch using a suitable compiler for their platforms, and install it on the device (see S1 in Section
3.3
).
There is no additional effort needed from maintainers to install the patch.

After the installation, when the vulnerable function is executed,
the desired patch is triggered, and the vulnerability is fixed without disrupting
the normal operation of the device or requiring rebooting. We discuss the process in more detail in the following sections (Sections
4.3
and
4.4
).
Note that, for the sake of simplicity, the examples are shown using the C language, while AutoPatch is based on LLVM IR.
Further, to explain our examples, we treat each line of code (i.e., program statement)
in the C programming language as an instruction. In reality, these would be multiple LLVM instructions.

4.2.
Locations of Instrumentation

Unlike previous hotpatching approaches
(
Xu et al., 2020
;
He et al., 2022
)
,
AutoPatch does not use summarization or estimation approaches for generating patches (see Section
3.1
).
The goal of AutoPatch is to statically create a functionally equivalent hotpatch based on the official patch, and to trigger the hotpatch in the vulnerable function.
RapidPatch, a prior hotpatching approach
(
He et al., 2022
)
, only adds one trampoline at the beginning of each function, as it assumes that developers manually abstract the effect of the official patch at functions entrances.
Unfortunately, it is not always possible for AutoPatch to statically analyze complex code structures and abstract their effects on the patch. Therefore, we insert trampolines inside/after code structures that are too complex to statically analyze. Trampolines will in turn, trigger the hotpatch that will be created at these locations by AC.

A straw man solution would be adding a trampoline before each instruction to avoid
the challenges mentioned, but this solution would incur significant overhead, and is hence not suitable for real-time embedded devices.

Our main observation is that it suffices to insert trampolines in a few strategic locations
. However, the locations for instrumenting trampolines depend on where the patch is inserted.
In several cases, the trampoline needed to be inserted at the function entrance to redirect execution flow before the vulnerability could be exploited.
In other cases, the trampoline needed to be inserted at a specific point within the function,
such as after function calls.
Overall, to achieve our goal of generating a functionally equivalent hotpatch without relying on estimation techniques,
we identified four
instrumentation locations
where trampolines should be inserted.
Also, we validated these locations with actual CVEs, and the results confirmed that these instrumentation locations are sufficient
to execute hotpatches to fix real-world vulnerabilities (Section
6.1
).
These four locations are as follows.

Function Entrance:

The first location for inserting trampolines is at the beginning of every function.
This location is crucial for ensuring that any vulnerabilities found
at the beginning of the function are patched before the function is executed.
For example, as shown in Listing
1
, a patch was written at the entrance of the vulnerable function to fix a vulnerability in the function.

After Function Calls:

Function calls are one of the locations chosen for instrumentation, as
it is often difficult to statically determine the effect of the callee function on patch variables, as doing so would require complex inter-procedural analysis. Therefore, AutoPatch inserts a trampoline after function calls.

Inside and After Complex Loops:

Complex loops are loops that either have conditions (number of executions) that cannot be calculated statically
or consist of several nested loops.
Otherwise, the loop is considered a simple loop.

For instance, when a loop’s condition involves a pointer whose value cannot be determined statically, it falls into the category of complex loops.
These loops are challenging for static analysis to accurately ascertain the precise number of loop iterations and the resulting output values.
Therefore, AutoPatch inserts trampolines inside and after these loops to generate a functionally preserving hotpatch based on the official patch.

4.3.

The instrumentation phase inserts trampolines in the instrumentation locations of the firmware functions.
To perform this phase automatically,

4.4.
Analysis Phase

The AutoPatch process’s next phase is the analysis phase,
used when a security vulnerability is discovered in the firmware. The goal of this phase is to automatically generate hotpatches based on official patches.
In the instrumentation phase, IC inserted trampolines in instrumentation locations
within functions, while the official patch may have been written anywhere within the function.

To address this issue, the AutoPatch analysis phase is designed to:
(1) find the best trampoline (Section
4.4.1
)
for triggering the patch,
and (2) analyze the official patch and automatically generate a
hotpatch that can be executed by the selected trampoline and have the same effect as the official patch (i.e., functionally equivalent hotpatch),
using backward static analysis. To achieve these goals, the analysis phase consists of three main steps:
patch generation, patch compilation, and patch installation.
The following provides a detailed explanation of each step in the analysis phase of AutoPatch.

Patch Compilation

After completing the analysis, the instructions obtained from the previous step

to receive information from trampolines.
In other words, when the trampoline is triggered and the hotpatch needs to be executed,
the values of the vulnerable function should be passed to the hotpatch
through the hotpatch function’s argument.
This is released as the hotpatch to fix the vulnerability.

If device maintainers are using the vulnerable version of the firmware on their devices,
they would download the hotpatch and compile it using a
cross compiler

into an executable file compatible with the target board, allowing them to install it on the board.

4.4.3.
Patch Installation and Execution

The last step of the hotpatching process is installing the hotpatch on the board by device maintainers.
Similar to previous work
(
He et al., 2022
;
Niesler et al., 2021
)
,
we assume that device maintainers use an encrypted channel to transmit the
executable file (hotpatch) alongside
the patch configuration file including address of the best trampoline for this hotpatch to the board.
Then, the hotpatch is added to the list of active hotpatches using the
lr
(link register) index,
which represents the address of the trampoline responsible for executing this hotpatch.
When the trampoline is executed, it enters the dispatcher section and saves the current values of the vulnerable function.
If a patch is available, it retrieves the patch using the index from the list of active patches and executes it.
The stored values are passed through the data frame argument of the hotpatch function. As each trampoline can have multiple active hotpatches,
device maintainers can disable them if they are not needed through a secure connection (Section
3.4
).

Similar to RapidPatch, after executing the hotpatch and based on its result,
the dispatcher decides to change the program execution flow by changing the return address (
lr
)
based on one of the three operations: PASS (i.e., resume normal execution of the function),
REDIRECT (i.e., redirect the program flow to a specific section of the vulnerable function) or
DROP (i.e., bypass the vulnerable function entirely).
Note that selecting one of these two operations (i.e., REDIRECT and DROP) depends on the official patch.
For instance, if a malicious input is detected, the RTOS developer may opt to return to the caller function,
similar to using DROP in the hotpatch.
Therefore, executing DROP or REDIRECT has no impact on the program’s functionality.

5.2.
Analysis Phase

The analysis component takes the patched function and patch information as input.
Once the function is compiled to LLVM IR using Clang, AutoPatch begins static analysis
to find the best trampoline based on the characteristics mentioned in Section
4.4
.
Then, AC checks whether the best trampoline to the patch is the previous or next instruction of the patch instructions.
If so, it indicates that there are no intermediate instructions that could modify the variables involved in the patch.
In this case, the official patch and the hotpatch are considered identical, and the patch can be executed using the identified trampoline (i.e., best trampoline).

Otherwise, if the best trampoline is not adjacent to patch instructions,
AutoPatch conducts a static analysis of the official patch.
It parses the patch and stores all its variables in a data structure.
Next, it identifies the basic blocks between the patch and the selected trampoline
and performs a backward static analysis starting from the official patch until reaching the trampoline
to determine instructions affecting patch variables.
Thereafter, AC stores instructions in a new LLVM IR format function,
whose input is a data frame structure and whose return value is based on one of the three operations
PASS, REDIRECT or DROP.
Finally, AC saves the function in a
ll
file as a hotpatch,
which can then be compiled into a file that can be executed on the desired board by using cross compiler.

To implement the AutoPatch runtime, which includes the trampoline, dispatching, and execution of hotpatches,
we leveraged the RapidPatch implementation.
In contrast to RapidPatch (execution part), which stores the eBPF patch code and performs
a context switch to the eBPF VM for execution, AutoPatch stores the hotpatch as an executable file.
Then, when the dispatcher locates it using
lr
, the corresponding hotpatch function is called with
the vulnerable function variables passed as arguments.
Therefore, AutoPatch reduces the performance overhead of hotpatch execution over RapidPatch (see Section
6.2.5
and Section
6.2.8
).

The results show that AutoPatch effectively mitigates potentially harmful operations that can lead to compromises.

these techniques cannot generate hotpatches for patches (e.g., CVE-2017-14202 in Zephyr OS) that modify the structures definitions or macros.

6.2.1.
Instrumentation Component (IC) Overhead

AutoPatch’s instrumentation phase is executed offline before firmware installation,
and is measured on the desktop computer.
We performed IC on the functions of RTOSes, and calculated the average time required to instrument each function.
Our results showed that an average of 0.15

is needed to identify the instrumentation locations
in the function and insert the trampoline in those locations.
As an example, we applied IC to the "packet_length_decode" function (Figure

associated with CVE-2020-10062. Our LLVM pass successfully identified three instrumentation locations within the function and added trampolines
at those locations, all within a mere 0.1

The next step in the hotpatch generation process involves running AC on the official patch
and creating the hotpatch via static analysis.
This phase, like the previous one, is performed offline, and does not impose any overhead on the embedded device.
We calculated the average time for generating a hotpatch for the 12 CVEs, as reported in Table

Our results show that the average time is 0.6

6.2.3.
Trampoline Overhead

The software triggering method utilized in AutoPatch involves a fixed set of instructions
for triggering the hotpatch, and storing and retrieving function information.
Therefore, we can evaluate the overheads of this method independent of the specific patch. To measure the standalone loading delay,
we executed the software triggering method 20 times on the nRF52840 board
and calculated the average CPU cycles taken. We found that the triggering approach takes 65 cycles,
which is approximately 1.01
\mu s
for each execution on the board.

Furthermore, we evaluated the overhead of the instrumented version of different applications provided by Zephyr OS. We observed a latency increase ranging from 0.05% to 3.7% across different scenarios (average of 10 runs each).
RapidPatch incurred 0.05% to 0.6% latency overhead in the same scenarios.
Thus, AutoPatch incurred a higher performance overhead than RapidPatch on the real applications due to the additional instrumentation added by it. This is because RapidPatch only inserts a single trampoline in each function, unlike AutoPatch, which inserts multiple trampolines.

Furthermore, instrumenting Zephyr OS and FreeRTOS in the instrumentation phase using AutoPatch
incurred memory overheads of 11% and 8%, respectively.
On the other hand, RapidPatch incurred 7% and 3.8% overheads for Zephyr OS and FreeRTOS, respectively.

6.2.4.
Hotpatch Dispatching Overhead

When a trampoline is triggered in a vulnerable function, AutoPatch should select the appropriate patch
for that function from among the active patches - this is the hotpatch dispatching overhead.
Similar to RapidPatch, due to the memory limitation in embedded devices, we stored a maximum of 64 patches
and evaluated the associated overhead.
We evaluated this overhead by calculating the average time for different numbers of active patches
(ranging from 1 to 64).
Our results indicate that the overhead was 2.1
\mu s
for 1 patch and 4.4
\mu s
for 64 patches, respectively.
This is because AutoPatch uses binary search for finding the patch (similar to RapidPatch), and hence it takes
O(logn)
time.

Related Work

Traditional and Android Systems Update.

Segal et al.
(
Segal and Frieder, 1993
;
Frieder and Segal, 1991
)
,
introduced a PODUS system
(the procedure oriented dynamic updating system) for updating C applications.
Other work has focused on server applications
in this field
(
Altekar et al., 2005
;
Chen et al., 2007
;
Payer and Gross, 2013
;
Giuffrida et al., 2016
)
.
Some of these approaches change the compiler
(
Altekar et al., 2005
;
Chen et al., 2007
)
,
while other approaches change the programming language
(
Smith et al., 2012
)
.
The main challenge of hotpatching for these systems is that after making changes and rebooting the device,
the system state must also be maintained.

Hayden et al.
(
Hayden et al., 2012
)
proposed Kitsune that leverages update points
where the states of the program are easily accessible, and these points are specified by the programmer.
Guiffrida et al.
(
Giuffrida et al., 2013
)
used fault-tolerant state transfer method for solving this challenge,
while Makris et al.
(
Makris and Bazzi, 2009
)
leveraged an algorithm called stack reconstruction.
However, the unique characteristics of real-time systems, such as timeliness, resource limitations,
and the necessity for predictability, limit the applicability of these techniques.

Ksplice
(
Arnold and Kaashoek, 2009
)
proposed a generic hotpatching technique for Linux systems that operates at the object code level.
Ksplice identifies the differences between the vulnerable kernel and the patched kernel,
locates the modified functions, and adds the entire function along with the patch to the device at runtime.
However, since Ksplice stores the complete patched function beside the vulnerable function,
it requires a large amount of memory.
In contrast, AutoPatch does not need to store the entire patched function and it only stores
the generated hotpatch. This makes it better suited for memory-constrained devices such as real-time embedded devices.
Also, Ksplice needs to modify the code at execution time to apply the patch, which is not suitable for embedded devices due to the hardware characteristics, as discussed in Section
2.4
.

The authors in
(
Chen et al., 2018
;
Chen et al., 2017
)
proposed two hotpatching techniques for Android
devices by writing hotpatches in new languages (i.e., GuardSpec and Lua).
However, rewriting a patch in a new language can be a time-consuming and error-prone process.
Furthermore, KARMA
(
Chen et al., 2017
)
requires code rewriting to insert trampolines,
which needs to reboot the embedded devices (Section
2.4
)
while Instaguard
(
Chen et al., 2018
)
relies on hardware techniques to trigger the patch,
which are not commonly supported in embedded devices.

Zhang et al.
(
Zhang et al., 2017
)
proposed Embroidery, a patching system designed
to fix vulnerabilities on outdated Android devices by using binary code.
However, Embroidery requires rewriting the kernel and modifying the kernel memory region,
which results in device reboots and violates one of our main requirements (Section
3.1
).

Finally, Bowknots
(
Talebi et al., 2021
)
attempts to maintain system functionality and nullify the side effects of currently executing
system calls when a kernel bug is triggered, and no official patch is available.
This method assumes that the official patch has not yet been released,
focusing on the window between the discovery of the vulnerability and the release of the patch.
Therefore, our work is orthogonal to this line of work.

Embedded Devices Update.

In recent years, the patching and updating of embedded devices firmware has become
important
(
Park et al., 2010
;
Arakadakis et al., 2021
;
Felser et al., 2007
;
Dong et al., 2013
)
.
Most previous approaches used the over-the-air (OTA) method to update the system and
fix bugs and vulnerabilities in the program
(
Bauwens et al., 2020
;
Arakadakis et al., 2021
)
.
There are challenges in the OTA method, such as secure updating and reduction of transmitted data,
which researchers
(
Ammar and Crispo, 2020
;
Panta et al., 2009
;
Bauwens et al., 2020
)
have addressed.
These OTA methods require reprogramming, and since embedded devices run code on the flash-based ROM,
they require that the entire flash sector be erased.
Thus, the system must reboot, which halts the running task, making them unsuitable for mission-critical applications, which is our focus.

ChkUp
(
Wu et al., 2024
)
proposed a technique to detect vulnerabilities in the firmware update process by using cross-language inter-process
control flow analysis and program slicing.
While there have been hotpatching approaches that do not require a reboot for embedded devices
(
Niesler et al., 2021
;
Wahler et al., 2009
;
He et al., 2022
;
Wahler and Oriol, 2014
)
, each of the approaches has problems that make them unsuitable for our purposes (see Section
3.2
for details).

8.
Discussion

Although AutoPatch has addressed hotpatching challenges, it still has three main limitations.
First, while the evaluation in Section
6.2.3
demonstrated
that the software triggering approach does not impose significant overhead on the device and application,
it is possible to further minimize this overhead by reducing the number of trampoline locations.
Previous work
(
He et al., 2022
)
has shown that the majority of vulnerabilities are associated
with network payload processing functions, and therefore the instrumentation
can be done only for packet ingress functions.
Additionally, given that embedded devices are designed for specific purposes,
they consistently use certain OS functions and libraries throughout their operational lifespan.
Consequently, instrumenting only those specific functions can effectively decrease
the overhead imposed on the device. These changes will not require modifications in the IC and AC.

Second, similar to prior work, we made the assumption that the official patches released by RTOS developers
for resolving vulnerabilities are free of bugs.
However, there are many formal verification
(
Jacobs et al., 2011
)
techniques that can be used to verify the patches.

Third, similar to RapidPatch
(
He et al., 2022
)
and HERA
(
Niesler et al., 2021
)
, AutoPatch does not support official patches
that require changes to either data structures or macro definitions (Section
1
). However, we found that only 2 out of 62 CVEs had official patches that made such changes.

9.
Conclusion

We propose AutoPatch
7
7

7

We have made our code and data publicly available at
https://github.com/DependableSystemsLab/AutoPatch
.
, the first automatic hotpatching framework for real-time embedded devices.
AutoPatch addresses challenges existing in current hotpatching techniques by combining static instrumentation
and analysis techniques to
automatically
generate functionality-preserving hotpatches based on official patches.
AutoPatch is implemented using the LLVM compiler and is hence portable to different platforms.
We evaluated AutoPatch using real CVEs on four different embedded boards with various architectures
running different RTOSes. Our evaluation found that AutoPatch
successfully generated the hotpatches while preserving their functionality for over 90% of CVEs.
Further, AutoPatch had negligible runtime overhead and minimal memory consumption,
and incurred lower performance and memory overheads than a prior state-of-the-art hotpatching approach, despite needing no manual effort. Finally, AutoPatch generated hotpatches can be executed on different boards, without any changes, thus demonstrating its generality.
