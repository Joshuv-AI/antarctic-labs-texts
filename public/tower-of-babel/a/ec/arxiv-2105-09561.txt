Generating Significant Examples for Conceptual Schema Validation Asymetrix Report 94-3
H.A. Proper

Abstract
This report bases itself on the idea of using concrete examples to verify conceptual schemas, and in particular cardinality constraints. When novice ORM modellers model domains, the selection of proper cardinality constraints for relationship types is quite often prone to errors. In this report we propose a mechanism for the generation of significant examples for selected subschemas. The generated examples are significant in the sense that they illustrate the possible combinations of instances that are allowed with respect to the cardinality constraints on the involved relationship types. In this report we firstly provide a brief informal discussion of the basic idea. Then we present a syntactic mechanism to select the subschema for which example instances are to be generated. This is followed by the actual example generation algorithm itself. We will also present, as a spin-off , an algorithm that allows us to detect possible flaws in the conceptual schema by calculating the number of instances that can be used to populate the types in the schema.



Published as:

H.A. (Erik) Proper. Generating Significant Examples for Conceptual Schema Validation. Technical report, Asymetrix Research Laboratory, University of Queensland, Brisbane, Queensland, Australia, 1994.

Introduction

A key aspect in the conceptual design procedure (
[
Hal95
]
)
is the use of examples to derive the initial design of conceptual schemas.
A further use of the examples is the validation of parts of the final
conceptual schema.
Example populations of relationship types can be used to validate the correctness of
the information structure, and even more importantly, for the validation of
constraints.
In this report we propose a mechanism to generate significant example
populations for subsets of conceptual schemas.
This idea has been described informally in
[
Har94
]
.
In general, generating a significant example population is hardly possible.
Therefore, we limit ourselves to cardinality constraints and significance
of the examples with respect to single relationship types only.

The sample populations are used to visualise for the users what the effects
are of adding or removing cardinality constraints on relationship types, and
to a lesser extent that of changing the information structure itself.
An informal discussion of this idea can be found in

[
Har94
]
.
This proposed mechanism will initially be used in DBCreate and is expected to
migrate to InfoModeler in a later stage; after the idea has been tested by
the user community.

The aim of DBCreate is to enable (semi!) laymen to design their own database.
The example generation tool fits quite well into that idea.
Note that it is only obvious that these semi laymen are still presumed to have
some basic knowledge of conceptual (and preferably ORM) modelling.
No matter how user friendly a CAD/CAM system may become, an architect desiging
a house is still required to have a basic working knowledge of the design of
houses.

As stated before, in general it is nearly impossible to construct sample
populations that are truely significant with respect to all constraints
(
[
BHW91
]
).
In this report we therefore define a significant population of a relationship
type to be a population that shows all allowed combinations of instances with
respect to the cardinality constraints defined on that relationship type.
Setting a less limited goal can easily lead to a combinatoric explosion.
The restrictions we made, however, are not an unreasonable limitation in the
context of our aims.
The most commonly used (and thus mis-used) constraints are the cardinality
constraints (totality and uniqueness).
For the other constraint types there is of course still the possibility
of verbalising them in a semi-natural language format.

Creating a Forrest

This section discusses the syntax of a forrest for the example grid and also
provides a brief formalisation of the ORM concepts needed.
Although the example generation tool will initially be used in the context of
DBCreate (value types, entity types and binary relationship types), we already
allow for ORM schemas as used by InfoModeler.
We start out from a formalisation of ORM based on the one used in
(
[
HP95
]
).
However, since only a limited part of the formalisation is needed, we do not
cover the formalisation in full detail.

2.1
ORM Basis

A conceptual schema is presumed to consist of a set of types
{\cal T\!P}
.
Within this set of types two subsets can be distinguished:
the relationship types
{\cal R\!L}
,
and the object types
{\cal O\!B}
.
Furthermore, let
{\cal R\!O}
be the set of roles in the conceptual schema.
The fabric of the conceptual schema is then captured by two functions and two
predicates.
The set of roles associated to a relationship type are provided by the
partition:
\mathop{\mbox{\normalsize$\mbox{\tenasf Roles}$}}\nolimits:\mbox{${\cal R\!L}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$})
.
Using this partition, we can define the function
\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits
which returns for each
role the relationship type in which it is involved:

\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits(r)=f\iff r\in\mathop{\mbox{\normalsize$\mbox{\tenasf Roles}$}}\nolimits(f)
.
Every role has an object type at its base called the player of the role.
This player is formally provided by the function:

\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits:\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mbox{${\cal T\!P}$}
.
Subtyping of object types is captured by the predicates

\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits\subseteq\mbox{${\cal O\!B}$}\times\mbox{${\cal O\!B}$}
.
Using
\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits
we can define the notion of type relatedness:
x\sim y
for
object types
x
and
y
.
This notion captures the intuition that two object types may share instances.
This relation is defined by the following four derivation rules:

1.

x\in\mbox{${\cal T\!P}$}~\vdash~x\sim x

2.

x\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits y~\vdash~x\sim y

3.

x\sim y~\vdash~y\sim x

4.

x\sim y\sim z~\vdash~x\sim z

Note that when using ORM with the advanced concepts
(
[
HP95
]
) such as polymorphism, sequence types,
set types, etc., the definition of
\sim
needs to be refined.

Instances of all non-value types must be identified in terms of instances of
other object types.
This identification is usually provided by a so called
reference schema
.
If
{\cal V\hskip-1.99997ptL}
denotes the set of value types, then the (direct!)
identification relationship between types is presumed to be captured by the
function:

\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits:(\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\mbox{\normalsize\boldmath$-$}$}}\nolimits\mbox{${\cal V\hskip-1.99997ptL}$})\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\cup$}}\nolimits\mbox{${\cal R\!O}$}^{+}\mathop{\mbox{\normalsize$\cup$}}\nolimits(\mbox{${\cal R\!O}$}\times\mbox{${\cal R\!O}$})^{+}

Each non-value type is either identified by a type (a super type), or
a sequence of roles (a relationship type), or a sequenc of role pairs
(compositely identified object types).
Note that in this report we do not concern ourselves with well-formedness
rules on reference schemas.
A function that is derived from
\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits
and which is needed in the
remainder is
\mathop{\mbox{\normalsize$\mbox{\tenasf IdfObjs}$}}\nolimits:\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mbox{${\cal O\!B}$}^{+}
.
This function returns the sequence of object types needed to directly identify
a given object type.
Its definition is provided as:

\mathop{\mbox{\normalsize$\mbox{\tenasf IdfObjs}$}}\nolimits(x)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}[y]&\mbox{\normalsize if~}\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits(x)=[y]\\[2.84544pt]
[y_{1},\ldots,y_{l}]&\mbox{\normalsize if~}\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits(x)=[\left\langle p_{1},y_{1}\right\rangle,\ldots,\left\langle p_{l},y_{l}\right\rangle]\\[2.84544pt]
[y_{1},\ldots,y_{l}]&\mbox{\normalsize if~}\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits(x)=[\left\langle p_{1},q_{1},y_{1}\right\rangle,\ldots,\left\langle p_{l},q_{l},y_{l}\right\rangle]\end{array}\right.

Note that we presume the existance of an implicit coercion function
between sequences and sets.
So, for example, if
S
is a set of sequences we allow ourselves to
write
\mathop{\mbox{\normalsize$\cup$}}\nolimits S
for the set of all elements occurring in the sequences
in
S
.

A lot of the decissions made by the example generation algorithm are based
on the maximum size of the populations of the object types.
Later on, an algorithm to calculate these sizes is presented.
However, the maximum sizes of the populations of the value types should be
given by the modeller.
For instance, a value type representing the gender of persons will usually
contain at most two instances.
To accommodate this, we presume the existance of the function

\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits:\mbox{${\cal V\hskip-1.99997ptL}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~
.
One obvious requirement for this function is:

x,y\in\mbox{${\cal V\hskip-1.99997ptL}$}\land x\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits y\Rightarrow\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits(x)\leq\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits(y)
.

Finally, in this report an important role is played by the uniqueness and
tolality constraints.
For that purpose, we presume the predicates
\mathop{\mbox{\normalsize$\mbox{\tenasf Unique}$}}\nolimits\subseteq\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$})

and
\mathop{\mbox{\normalsize$\mbox{\tenasf Total}$}}\nolimits\subseteq\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$})
to provide all uniqueness and totality
constraints.

In this report we thus only use the following components of an ORM schema:

\left\langle\mbox{${\cal T\!P}$},\mbox{${\cal R\!L}$},\mbox{${\cal V\hskip-1.99997ptL}$},\mbox{${\cal O\!B}$},\mbox{${\cal R\!O}$},\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf Roles}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf RefSch}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf Unique}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf Total}$}}\nolimits\right\rangle

When implementing the algorithms and ideas presented in this article, these
components are the
interface
between the example generator tool and
the meta model from the fact base.

2.2
Forrests

A tree of an example grid is built from a set of nodes.
Let in the remainder
ℕ
be a set of all such nodes.
Formally, a tree can now be defined by two functions:
\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits
and
\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits
.
As one object type can be represented by more than one node, the object type
represented by a node is provided by the function:

\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mbox{${\cal O\!B}$}
.
The edges of the tree are provided by the function

\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{\tenmsy L}\times\mbox{\tenmsy N})
.
This function provides for each node the set of outgoing edges.
Using the
\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits
function the following “inverse” function can be derived,
which returns for each node the set of incomming edges:

\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{\tenmsy L}\times\mbox{\tenmsy N})

\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits(n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{\normalsize$\left\{\begin{array}[]{c}\left\langle l,m\right\rangle\>\left|\>\begin{array}[]{c}\left\langle l,n\right\rangle\in\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(m)\end{array}\right.\end{array}\right\}$}

The edges of the tree are labelled with link information.
The set of links
𝕃
is defined by:

\mbox{\tenmsy L}~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\cup$}}\nolimits\mbox{${\cal R\!P}$}
, where

\mbox{${\cal R\!P}$}~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{\normalsize$\left\{\begin{array}[]{c}{p}^{\leftarrow}\>\left|\>\begin{array}[]{c}p\in\mbox{${\cal R\!O}$}\end{array}\right.\end{array}\right\}$}
is the set of
reversed

roles.
The reversed roles can be used to connect a node representing a relationship
type to a node representing one of the participating object types.
Each link has a starting point and an ending point.
To access these points (object types) uniformly, we introduce the
following two generic functions:

\mathop{\mbox{\normalsize$\mbox{\tenasf Start}$}}\nolimits,\mathop{\mbox{\normalsize$\mbox{\tenasf End}$}}\nolimits:\mbox{\tenmsy L}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mbox{${\cal T\!P}$}

\mathop{\mbox{\normalsize$\mbox{\tenasf Start}$}}\nolimits(x)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits(x)&\mbox{\normalsize if~}x\in\mbox{${\cal R\!O}$}\\[2.84544pt]
\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits(x)&\mbox{\normalsize otherwise}\end{array}\right.

\mathop{\mbox{\normalsize$\mbox{\tenasf End}$}}\nolimits(x)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits(x)&\mbox{\normalsize if~}x\in\mbox{${\cal R\!O}$}\\[2.84544pt]
\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits(x)&\mbox{\normalsize otherwise}\end{array}\right.

Note: from now on we presume
\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits
and
\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits
to be generalised to
elements from
{\cal R\!P}
in the obvious way.

In order for
\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits
and
\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits
to span a tree, they must adhere to certain
properties.
Each edge in the tree must be a connection between the source and destination
of the edge via the role.
This is expressed by the following axiom:

[T1]

For each
l\in\mbox{\tenmsy L}
:

\left\langle l,m\right\rangle\in\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\Rightarrow\mathop{\mbox{\normalsize$\mbox{\tenasf Start}$}}\nolimits(l)\sim\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n)\land\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(m)=\mathop{\mbox{\normalsize$\mbox{\tenasf End}$}}\nolimits(l)

The function
\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits
must indeed define a tree, so the graph spanned by

\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits
has to be a connected, acyclic graph with a unique root.

[T2]

\left|\mbox{\Large$\pi$}_{2}(\mathop{\mbox{\normalsize$\cup$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\tenasf ran}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits))\right|=\left|\mathop{\mbox{\normalsize$\mbox{\tenasf ran}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits)\right|

[T3]

\exists!_{\scriptstyle x\in\mathop{\mbox{\scriptsize$\mbox{\sixasf dom}$}}\nolimits(\mathop{\mbox{\scriptsize$\mbox{\sixasf EOut}$}}\nolimits)}\left[x\not\in\mbox{\Large$\pi$}_{2}(\mathop{\mbox{\normalsize$\cup$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\tenasf ran}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits))\right]

Note: if a directed graph has a unique root then it is automatically
connected.
All used nodes must have an object type associated:

[T4]

\mathop{\mbox{\normalsize$\mbox{\tenasf dom}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits)\mathop{\mbox{\normalsize$\cup$}}\nolimits\mbox{\Large$\pi$}_{2}(\mathop{\mbox{\normalsize$\cup$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\tenasf ran}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits))\subseteq\mathop{\mbox{\normalsize$\mbox{\tenasf dom}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits)

Furthermore, a link can be used only once for an outgoing edge of a
node.
This is formally enforced by:

[T5]

\left\langle l,n_{1}\right\rangle\in\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(m)\land\left\langle l,n_{2}\right\rangle\in\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(m)\Rightarrow n_{1}=n_{2}

One of the items that can be shown when displaying nodes on screen is the
fact that a given node can be extended with more edges.
In

1
, the right-button behind the
Customer
indicated
that more relationship types are available for this object type.
A node can be extended with an extra edge iff a link exists that can form a
proper edge, and is not already used by on another edge of this node.
This property can be expressed formally as:

\mbox{\tenasf CanExtend}(n)\iff\mbox{\normalsize$\left\{\begin{array}[]{c}l\in\mbox{${\cal R\!O}$}\>\left|\>\begin{array}[]{c}\mathop{\mbox{\normalsize$\mbox{\tenasf Start}$}}\nolimits(l)\sim\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n)\land l\not\in\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\end{array}\right.\end{array}\right\}$}\not=\mathchar 1343\relax

The set in the righthand side of the above definition can actually be used to
fill the listbox displayed in

6
.

The order in which the nodes themselves are displayed on the screen is
recorded by the function
\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~
.
As this function must provide a total order of the nodes, we should have:

\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits(x_{1})=\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits(x_{2})\Rightarrow x_{1}=x_{2}

One additional option of a system using an example generator is to have the
system re-order the tree based on the conceptual relevance of the object
types represented by the nodes.
If
\mathop{\mbox{\normalsize$\mbox{\tenasf CWeight}$}}\nolimits:\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~
is a function returning the conceptual weight
of types, then the system is able to order the nodes such that:

\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits(n_{1})<\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits(n_{2})\Rightarrow\mathop{\mbox{\normalsize$\mbox{\tenasf CWeight}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n_{1}))\leq\mathop{\mbox{\normalsize$\mbox{\tenasf CWeight}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n_{2}))

Note: more than one order may exist for the same
\mathop{\mbox{\normalsize$\mbox{\tenasf CWeight}$}}\nolimits
values since
differing object types may have the same conceptual weight.
Not all nodes need to be displayed on the screen.
Some nodes can be left implicit.
For instance, a node representing a non-objectified binary relationship
does not have to be shown on the screen.
The set of implicit nodes in a tree is identified by:

\mbox{\tenmsy I}~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{\normalsize$\left\{\begin{array}[]{c}n\in\mbox{\tenmsy N}\>\left|\>\begin{array}[]{c}\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits(n)\mathop{\mbox{\normalsize$\cap$}}\nolimits\mbox{${\cal R\!P}$}=\mathchar 1343\relax\land\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\mathop{\mbox{\normalsize$\cap$}}\nolimits\mbox{${\cal R\!O}$}=\mathchar 1343\relax\land\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits(n)\neq\mathchar 1343\relax\land\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\neq\mathchar 1343\relax\end{array}\right.\end{array}\right\}$}

From this definition immediately follows that two neighbouring nodes cannot
both be implicit.
This leads to the following lemma:

Lemma 2.1

(
no implicit neighbours
)

n\in\mbox{\tenmsy N}\land m\in\mbox{\Large$\pi$}_{2}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\Rightarrow\mbox{\normalsize$\{n,m\}$}\not\subseteq\mbox{\tenmsy I}

Proof:

Let
n\in\mbox{\tenmsy N}\land m\in\mbox{\Large$\pi$}_{2}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)

such that
\mbox{\normalsize$\{n,m\}$}\subseteq\mbox{\tenmsy I}
.

Since
m\in\mbox{\Large$\pi$}_{2}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)
it immediately follows from the
definition of
\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits
that:

\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EIn}$}}\nolimits(m)=\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)

As we presumed that

Negotiating the Size of the Example Space

As the title of this section suggests, in this section we concern ourselves
with a negotiation mechanism to determine the number of examples that are
to be used in the example grid.
Such a negotation phase is needed because some object types may have a limited
set of instances.
In particular value types such as
Gender
which will generally have two
or three instances only.

The first question we need to answer is the maximum number of instances that
a given type may have.
Due to relationships between types and the constraint patterns associated to
the relationships; limiting the number of instances of a value type may propagate
through the conceptual schema.
As an example consider the schema shown in

10
.
Object type
B
has a maximum number of instances of 2.
As each instance of object type
A
must play relationship
f
with
a unique instance of
B
, there can be only two instances of
A
.
As a result, there can be only two instances of relationship
f
, so
if
f
would be objectified this could lead to another propagation of
a size limitation.
In the context of larger schemas, these propagations may cause “ripple”
effects through the entire schema.
Note that if
A
is connected to
B
through a series of other
relationship types, then it could even be the case that the maximum size
of
B
needs to be reduced further!

schema.
Since the pattern generation algorithm only uses a limited class of patterns,
this kind of plausibility check may be a bit “oversensitive”.

x\in\mbox{\normalsize$\left\{\begin{array}[]{c}\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits(p)\>\left|\>\begin{array}[]{c}p\in\mathop{\mbox{\normalsize$\mbox{\tenasf Roles}$}}\nolimits(r)\end{array}\right.\end{array}\right\}$}\mathop{\mbox{\normalsize$\cup$}}\nolimits\mbox{\normalsize$\{r\}$}

DO

{\it Size}(x):=\mathop{\mbox{\normalsize$\mbox{\tenasf min}$}}\nolimits({\it Size}(x),{\it Used}(x))
;

END FOR
;

END FOR
;

# Propagate maximums in subtype hierarchy

FOR EACH
x,y\in\mbox{${\cal O\!B}$}

DO

IF
x\mathop{\mbox{\normalsize$\mbox{\tenasf SpecOf}$}}\nolimits y

THEN

{\it Size}(x):=\mathop{\mbox{\normalsize$\mbox{\tenasf min}$}}\nolimits({\it Size}(y),{\it Size}(x))
;

END IF
;

END FOR
;

RETURN
Size
;

END
.

The idea is now to constantly call the above resize algorithm until the
eventual maximum sizes have been stabalised.
We do this by means of the following fixed-point calculation:

\mathop{\mbox{\normalsize$\mbox{\tenasf CalcSizes}$}}\nolimits:\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits(\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\!\!^{\infty}$}}\nolimits)

\mathop{\mbox{\normalsize$\mbox{\tenasf CalcSizes}$}}\nolimits()~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~

VAR

Size
:

\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\!\!^{\infty}$}}\nolimits
;

NewSize
:

\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\!\!^{\infty}$}}\nolimits
;

BEGIN

{\it NewSize}:=\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits
;

# Do fixed point calculation

REPEAT

{\it Size}:={\it NewSize}
;

{\it NewSize}:=\mathop{\mbox{\normalsize$\mbox{\tenasf ReSize}$}}\nolimits({\it Size})
;

UNTIL
{\it NewSize}={\it Size}
;

END
.

Note that this algorithm terminates since the number of type classes is
finite and when resizing the maximum sizes we always choose the minimum
value.
In this last algorithm,
\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits
is the initial setting of the maximum
sizes.
This initial setting completely depends on the number of instances
(or generatable) for the value types in the conceptual schema.
In

2.1
we introduced the function
\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits:\mbox{${\cal V\hskip-1.99997ptL}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~

as the function that provides these sizes.
From this we can derive the initial maximum size for any object type as
follows:

\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits:\mbox{${\cal T\!P}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\!\!^{\infty}$}}\nolimits

\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits(x)&\mbox{\normalsize if~}\exists_{\scriptstyle x}\left[\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits\!\!\downarrow\!\!x$}}\nolimits\right]\\[2.84544pt]
\infty&\mbox{\normalsize otherwise}\end{array}\right.

We are now in a position to interpret the results from
\mathop{\mbox{\normalsize$\mbox{\tenasf CalcSizes}$}}\nolimits
.
Let
\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(x)
be the size of type
x
resulting after
\mathop{\mbox{\normalsize$\mbox{\tenasf CalcSizes}$}}\nolimits
.
If
\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(x)=0
for some type
x
, then it is highly likely that there is
a problem with the constraint patterns.
In such a case, each relationship type with a player
y
such that

\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(y)=0
and a player
z
such that
\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(z)>0
should be examined.

Furthermore, if there is a type
x
such that
\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(x)<\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x)
, there
is a limited likelyhood that there is a problem with the constraint patterns.
In this case, each relationship with a player
y
such that

\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(y)<\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(y)
and a player
z
such that
\mathop{\mbox{\normalsize$\mbox{\tenasf Size}$}}\nolimits(z)=\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(z)
,
should be examined.

3.3
The Example Space

When generating examples for an example grid, we do this for each
“umbrella” in the tree, i.e. a node and its direct descendants.
The umbrella associated to a node
n
is defined formally by:

\mathop{\mbox{\normalsize$\mbox{\tenasf Umbrella}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{\tenmsy N})

\mathop{\mbox{\normalsize$\mbox{\tenasf Umbrella}$}}\nolimits(n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{\Large$\pi$}_{2}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\mathop{\mbox{\normalsize$\cup$}}\nolimits\mathop{\mbox{\normalsize$\bigcup$}}\nolimits\limits_{\scriptstyle y\in\mbox{\footnotesize$\pi$}_{2}\mathop{\mbox{\scriptsize$\mbox{\sixasf EOut}$}}\nolimits(n)\mathop{\mbox{\scriptsize$\cap$}}\nolimits\mbox{\sevenmsy I}}\mathop{\mbox{\normalsize$\mbox{\tenasf Umbrella}$}}\nolimits(y)

From

Lemma 2.1
follows that an umbrella can be at most three
nodes deep: the root, one layer of explicit or implicit nodes, and the
layer containing the off-spring of the implicit nodes of layer 2.
An example of two umbrellas is shown in

11
.
These two umbrellas correspond to two tables of the example grid shown
in

1
.
When generating the examples for an entire tree, we only have to consider
all umbrellas of the nodes which are not implicit, since the implicit nodes
are already contained in these umbrellas.

Figure 11:
Two example umbrellas

The set of relationships involved in an umbrella can now simply be derived
as follows:

\mathop{\mbox{\normalsize$\mbox{\tenasf RelSet}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!L}$})

\mathop{\mbox{\normalsize$\mbox{\tenasf RelSet}$}}\nolimits(n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mbox{\normalsize$\left\{\begin{array}[]{c}\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits(l)\>\left|\>\begin{array}[]{c}l\in\mbox{\Large$\pi$}_{1}\mathop{\mbox{\normalsize$\mbox{\tenasf EOut}$}}\nolimits(n)\end{array}\right.\end{array}\right\}$}

where
\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits
is presumed to be generalised to elements of
{\cal R\!P}
.
Note that we only need to look at the set of outgoing edges from root of
the umbrella as the outgoing edges from the nodes of the second layer
are all implicit nodes, which allows us to apply

Lemma 2.2
.

A crucial first step in the generation of the examples is the negotiation
of the number of instances in the root of each umbrella.
In this negotiation we disregard the context of each umbrella, so we can
not simply use the results of the
\mathop{\mbox{\normalsize$\mbox{\tenasf CalcSizes}$}}\nolimits
function.
The reason to ignore the context lies in the fact that when validating the
constraint pattern of one relationship type, one does not want to have a
negative influence on the number of examples by a (possible) problem in
another part of the schema.
In the definition, again an initial maximum size of type populations
is needed.
From this we can derive the maximum size for any object type using the
following recursive function:

\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits:\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~

\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}\mathop{\mbox{\normalsize$\mbox{\tenasf DomSize}$}}\nolimits(x)&\mbox{\normalsize if~$x\in\mbox{${\cal V\hskip-1.99997ptL}$}$}\\[2.84544pt]
\Pi_{\scriptstyle y\in\mathop{\mbox{\scriptsize$\mbox{\sixasf IdfObjs}$}}\nolimits(x)}\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(y)&\mbox{\normalsize otherwise}\end{array}\right.

Using this function the actual ‘negotiation’ function can be defined,
determining the proper size of the root of an umbrella:

\mathop{\mbox{\normalsize$\mbox{\tenasf NodeSize}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~

\mathop{\mbox{\normalsize$\mbox{\tenasf NodeSize}$}}\nolimits(n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\mathop{\mbox{\normalsize$\mbox{\tenasf min}$}}\nolimits({\it MaxUserSizePref},\mathop{\mbox{\normalsize$\mbox{\tenasf min}$}}\nolimits_{\scriptstyle r\in\mathop{\mbox{\scriptsize$\mbox{\sixasf RelSet}$}}\nolimits(n)}{\it Usage}(r,n))

where
{\it Usage}
is defined as:

{\it Usage}:\mbox{${\cal R\!L}$}\times\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~

{\it Usage}(r,n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}{\it Used}(\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n))&\mbox{\normalsize if~}\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(n)\not=\infty\\[2.84544pt]
\infty&\mbox{\normalsize otherwise}\end{array}\right.

such that:

\left\langle{\it Used},{\it Pattern}\right\rangle=\mathop{\mbox{\normalsize$\mbox{\tenasf GenPattern}$}}\nolimits(r,\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits)

and
MaxUserSizePref
is a user defined constant providing the preferred
maximum size of root nodes.
Note: we presume
\mathop{\mbox{\normalsize$\mbox{\tenasf max}$}}\nolimits_{\scriptstyle x\in X}f(x)
returns
0
if
X=\mathchar 1343\relax
.

4
Filling an Example Grid

In this section we do the final step and actually populate the example
grids.
Thus far the only result from the
\mathop{\mbox{\normalsize$\mbox{\tenasf GenPattern}$}}\nolimits
algorithm we used was the
usage of instances.
In this section, the patterns generated by
\mathop{\mbox{\normalsize$\mbox{\tenasf GenPattern}$}}\nolimits
are finally utilised
to generate the real examples.

4.1
Filling Object Types

When generating instances for the edges of an umbrella, we need to generate
instances for the nodes (object types) first.
Let
\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits:\mbox{${\cal O\!B}$}\times\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\Omega
be a given function that
generates instances for object types.
This function need the natural number to generate unique (and yet
deterministic) instances.

When applied for a value type
x
, the result of
\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits(x,n)
is one of the
instances of the domain for values of
x
.
Suppose that the user has given 8/7/94, 8/8/94, 8/9/94 as examples for the

Date
value, then
\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits(\mbox{\tenasf Date},2)
would result in 8/8/94.
When the
\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits(x,n)
is used for a non-value type, a surrogate instance
is generated.
For instance,
\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits(\mbox{\tenasf LineInfo},1)
could result in
LineInfo1
.
The set
\mathop{\mbox{\normalsize$\Omega$}}\nolimits
is used in this report as a general domain for simple
instances from value types and composed instances from compositely identified
types.
Using this primitive function, the following more refined generation function
can be defined, which also takes the required details of identifications
(
\mathop{\mbox{\normalsize$\mbox{\tenasf IdfNodes}$}}\nolimits
) into account:

\mathop{\mbox{\normalsize$\mbox{\tenasf GetInst}$}}\nolimits:\mbox{${\cal O\!B}$}\times\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits

\mathop{\mbox{\normalsize$\mbox{\tenasf GetInst}$}}\nolimits(x,n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}{\it nil}&\mbox{\normalsize if~}n=0\\[2.84544pt]
\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf IdfNodes}$}}\nolimits(x),n-1)&\mbox{\normalsize if~}\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$\mbox{\tenasf IdfNodes}$}}\nolimits\!\!\downarrow\!\!x$}}\\[2.84544pt]
[\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits(x,n)]&\mbox{\normalsize otherwise}\end{array}\right.

Note that the
n=0
case is a special case.
Generating a nil value for
n=0
allows us to treat patterns resulting from
optional roles uniform to the other patterns.
The
\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits
function is used to construct the actual instance in the
case of an object type with an identification provided by
\mathop{\mbox{\normalsize$\mbox{\tenasf IdfNodes}$}}\nolimits
.

\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits:\mbox{${\cal O\!B}$}^{+}\times\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits

\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits([x_{1},\ldots,x_{n}],m)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~\left\{\begin{array}[]{ll}[\mathop{\mbox{\normalsize$\mbox{\tenasf GetInst}$}}\nolimits(x_{1},\gamma(m)+1)]&\mbox{\normalsize if~}n=1\\[5.69046pt]
[\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits([x_{1}],\gamma(m)\mathop{\mbox{\normalsize$\mbox{\tenasf DIV}$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x_{1}))]\mathop{\mbox{\normalsize$+\!\!+$}}&\\[2.84544pt]
\mbox{\normalsize~~~}[\mathop{\mbox{\normalsize$\mbox{\tenasf Compose}$}}\nolimits([x_{2},\ldots,x_{n}],\gamma(m)\mathop{\mbox{\normalsize$\mbox{\tenasf MOD}$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x_{1}))]&\mbox{\normalsize otherwise}\end{array}\right.

where:

\gamma(m)=\left\{\begin{array}[]{ll}x/2&\mbox{\normalsize if~}\mbox{\tenasf IsEven(x)}\\[2.84544pt]
\Pi_{\scriptstyle 1\leq i\leq n}\mathop{\mbox{\normalsize$\mbox{\tenasf MaxSize}$}}\nolimits(x_{i})-(m+1)/2&\mbox{\normalsize otherwise}\end{array}\right.

Note that the use of the
\gamma
function causes a “natural” spread in the
use of the examples.

4.2
Filling an Example Grid

For filling an umbrella with instances all that remains to be done is to call

\mathop{\mbox{\normalsize$\mbox{\tenasf GenPattern}$}}\nolimits
for each relationship type contained in the umbrella with the
negotiated nodesizes given in
\mathop{\mbox{\normalsize$\mbox{\tenasf NodeSize}$}}\nolimits
,
generate the concrete instances using
\mathop{\mbox{\normalsize$\mbox{\tenasf GetInst}$}}\nolimits
, and finally order the
result.
All this is done by the
\mathop{\mbox{\normalsize$\mbox{\tenasf GenPop}$}}\nolimits
algorithm.
The algorithm takes the root node of the current umbrella as its input
parameter and results in a population of the relationship types contained in
the umbrella, together with an
ordered
population of the object types
playing a role in these relationship types.
The results can than be used (together with the earlier discussed
\mathop{\mbox{\normalsize$\mbox{\tenasf Order}$}}\nolimits

for the nodes) to present the examples in an ordered way.
The algorithm is defined as:

\mathop{\mbox{\normalsize$\mbox{\tenasf GenPop}$}}\nolimits:\mbox{\tenmsy N}\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits(\mbox{${\cal R\!L}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits))\times(\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits^{+})

\mathop{\mbox{\normalsize$\mbox{\tenasf GenPop}$}}\nolimits(n)~\mathop{\mbox{\normalsize$\mathchar 13356\relax$}}\nolimits~

VAR

\begin{array}[]{ll}{\it RPop}:&\mbox{${\cal R\!L}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits)\\[2.84544pt]
{\it OPop}:&\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits^{+}\\[2.84544pt]
{\it Rel}:&\mbox{${\cal R\!L}$}\\[2.84544pt]
{\it Tuple}:&\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\\[2.84544pt]
{\it NewTuple}:&\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\\[2.84544pt]
{\it Role}:&\mbox{${\cal R\!O}$}\end{array}

BEGIN

FOR EACH
{\it Rel}\in\mathop{\mbox{\normalsize$\mbox{\tenasf RelSet}$}}\nolimits(n)

DO

\left\langle{\it Used},{\it Pattern}\right\rangle:=\mathop{\mbox{\normalsize$\mbox{\tenasf GenerateInst}$}}\nolimits({\it Rel},\mathop{\mbox{\normalsize$\mbox{\tenasf NodeSize}$}}\nolimits)
;

FOR EACH
{\it Tuple}\in{\it Pattern}

DO

# We presume that
\mathop{\mbox{\normalsize$\rm I\hskip-2.10007ptN\hskip-7.5ptI\hskip 0.70007pt$}}\nolimits~\subseteq\mathop{\mbox{\normalsize$\Omega$}}\nolimits

NewTuple
:=
Tuple

FOR EACH
{\it Role}\in\mathop{\mbox{\normalsize$\mbox{\tenasf Roles}$}}\nolimits(\mbox{\normalsize\normalsize\it Rel})

DO

{\it NewTuple}({\it Role}):=\mathop{\mbox{\normalsize$\mbox{\tenasf GetInst}$}}\nolimits(\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits({\it Role}),{\it Tuple}({\it Role}))
;

{\it OPop}(\mathop{\mbox{\normalsize$\mbox{\tenasf Player}$}}\nolimits({\it Role}))\mathop{\mbox{\normalsize$\mathop{\mbox{\normalsize$+\!\!+$}}\nolimits\!\!:=~$}}\nolimits[{\it NewTuple}({\it Role}))]
;

END FOR
;

{\it RPop}({\it Rel})\mathop{\mbox{\normalsize$+\!\!:=$}}\nolimits\mbox{\normalsize$\{{\it NewTuple}\}$}
;

END FOR
;

END FOR
;

{\it OPop}:=\mathop{\mbox{\normalsize$\mbox{\tenasf ReOrder}$}}\nolimits({\it RPop},{\it OPop},\mathop{\mbox{\normalsize$\mbox{\tenasf Obj}$}}\nolimits(n))
;

\mbox{\tenasf RETURN~}\left\langle{\it RPop},{\it OPop}\right\rangle
;

END
.

The
\mathop{\mbox{\normalsize$\mbox{\tenasf ReOrder}$}}\nolimits:(\mbox{${\cal R\!L}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\mbox{\Large$\wp$}$}}\nolimits(\mbox{${\cal R\!O}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits))\times(\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits^{+})\times\mbox{${\cal T\!P}$}~~\mathop{\mbox{\normalsize$\rightarrow$}}\nolimits~~(\mbox{${\cal O\!B}$}\mathop{\mbox{\normalsize$\mathchar 13338\relax$}}\nolimits\mathop{\mbox{\normalsize$\Omega$}}\nolimits^{+})

function is used to order the instances in the result.
The order is based on the number of tuples in the relationship examples that
use the instances.
We do not provide an ordering algorithm for this function and leave that to
the choice of the programmers.
However, the following ordering condition must be met.
If
P=\mathop{\mbox{\normalsize$\mbox{\tenasf ReOrder}$}}\nolimits({\it RPop},{\it OPop},x)
, then:

\forall_{\scriptstyle i,j\in\mathop{\mbox{\scriptsize$\mbox{\sixasf dom}$}}\nolimits(P)}\left[~i<j\Rightarrow\left|\mathop{\mbox{\normalsize$\mbox{\tenasf Tuples}$}}\nolimits({\it RPop},P[i],x)\right|\geq\left|\mathop{\mbox{\normalsize$\mbox{\tenasf Tuples}$}}\nolimits({\it RPop},P[j],x)\right|~\right]

where
\mathop{\mbox{\normalsize$\mbox{\tenasf Tuples}$}}\nolimits({\it RPop},v,x)=\mbox{\normalsize$\left\{\begin{array}[]{c}t\>\left|\>\begin{array}[]{c}\exists_{\scriptstyle p:\mathop{\mbox{\scriptsize$\mbox{\sixasf Player}$}}\nolimits(p)=x}\left[t\in{\it RPop}(\mathop{\mbox{\normalsize$\mbox{\tenasf Rel}$}}\nolimits(p))\land t(p)=v\right]\end{array}\right.\end{array}\right\}$}
.

5
Conclusions

In this report we have presented an algorithm to generate examples for a
selection of relationship types, such that the examples are significant
(to a certain degree).
These examples can be used to fill example grids, allowing users to validate
cardinality constraints by looking at example patterns.

As a spin-off, we also discussed the option of calculating the maximum sizes
of all types in a conceptual schema.
This would allow us to detect possible problems with cardinality constraints.

The next step is to integrate these ideas into DBCreate and in a later stage
InfoModeler itself.
The definitions in this report are already suited for the ORM schemas as they
can be specified in InfoModeler.
They are not yet suited for the extended ORM concepts as introduced in

[
HP95
]
.
However, the modification of the here presented algorithms to cover these
extensions is not expected to be hard.
