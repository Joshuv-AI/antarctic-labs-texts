Abstract
. Authorization currently introduces partial centralization in otherwise distributed network architectures, such as ICN approaches. Analyzing existing work in (partially) distributed authentication and authorization, and rearranging proven methods, this paper introduces a generalized, capability based and fully distributed authorization scheme. It argues that such a scheme can fit neatly into ICN architectures in order to enhance the trust model and mitigate against certain classes of denial-of-service attacks. Keywords: authorization, distributed systems security, ICN



1.
Introduction

At the advent of the Internet, Baran distinguished
(
Baran 1964
)
between
centralized, decentralized and distributed networks. The distinguishing
characteristic lies in how many other network nodes each node maintains
connections to. In distributed networks, each node maintains multiple connections –
with the effect that a single node failure can easily be routed around (see
figure
1
).

Figure 1.
Centralized, Decentralized and Distributed Networks (Baran)

Baran was concerned with catastrophic failure; however, distributed networks
have qualities that makes them attractive for uses where node failure is part
of nominal operations, such as peer-to-peer or information-centric network
architectures.

Traditional authorization schemes in networks rely on a centralized component,
an
authorization server
, to reply to authorization requests. This reduces distribution,
and moves the overall network architecture closer to a decentralized one.
While there is no architectural requirement to partially centralize all network
requests in this manner, authorization is a sufficiently common and critical
operation that its centralization affects a significant percentage of
requests.

This paper explores the use of cryptographic
capabilities
as a means to remove the
single point of failure that is the
authorization server
.

The key to achieving this is to distinguish between several authorization
phases rather than treating authorization as an atomic operation. Cryptographic
signatures permit transferring state from a prior stage to a latter stage in a
verifiable and tamper-proof manner.

2.
Related Work

This paper combines developments from
object capabilities
,

cryptographic certificates
and
authorization protocols
.
Most related work falls into one of those three categories. Other informative
sources revolve around
distributed identifiers
.

2.1.
Object Capabilities

Object capabilities
(
Dennis and
Van Horn 1966
)
are first described in a 1966 paper as a
combination of a pointer to an object, and actions that may be carried out on
that object. A key property of capabilities is that they are serializable, that
is, one process can provide them to another as part of a request for some
computation. The paper imagines a
supervisor
in a multi-user machine
to arbitrate access to objects based on the capabilities a process holds.

While the paper refers to
principals
as the users or
groups on whose behalf computations are performed, they are not part of the
serialized capability. Instead, the system state provides answers: if a process requests some computation
presenting a capability, it is inferred that the user who owns the process is
the principal.

Many object capability based systems are designed and explored in the meantime,
but tend to remain restricted to single domains. In 1989, Gong recognizes
that they do not translate well to distributed systems, as network user
identifiers do not necessarily map to the same local user identifier on each of
the participating nodes.

ICAP addresses this
omission
(
Gong 1989
)
, by adding the network user identifier to the transmitted
capability. It should be noted,
however, that the
access control server
is not completely removed and
remains a single point of failure in the ICAP design.

2.2.
Cryptographic Certificates

The more popular sibling of authorization is authentication; after all, one
needs to establish an identity of sorts before deciding whether to grant them
access to some object.

Two technologies in widespread use merit mention as related work: first, X.509
certificates
(
Recommendation
X.509 2000
)
(used in e.g. Transport Layer Security) are probably
the most popular technology that aids in identification.

The certificates contain structured metadata about an entity that, one hopes,
can be used to establish a real-world identity. An additional piece of metadata
is a cryptographic fingerprint of the public part of an asymmetric key pair.
All of this is signed using the key of some chosen authority, establishing a

security assertion
: if one can trust the authority, then one can also
trust that the identified public key belongs to the identified real-world
entity.

This shifts the issue of establishing a root in a trust chain to the distribution
of authorities, or
root certificates
. In principle, applications can
choose their own root certificates. But in practice, at least as far as the world
wide web is concerned, the most commonly used root certificates are distributed as
part of operating system updates.

Where the use of X.509 certificates provides a binary answer to a trust
question, Pretty Good Privacy (PGP) provides slightly more variations
(
Finney et al. 2007
)
.
In much the same way as X.509, PGP associates some identifying metadata with a
public key. Unlike X.509, however, PGP does not rely on well-known roots of
trust.

Instead, PGP opts to let the recipient of a certificate decide
whether or not to trust the signer – and by how much. For the latter purpose,
PGP adds a piece of metadata, a numeric
trust level
, which users can choose
to assign their own, locally applicable meaning to.

In this manner, PGP crosses over into the realm of authorization: by assigning
a trust level of X to a key, and then deciding to grant some privilege to all
keys with that trust level, a user effectively authorizes the affected keys.

Trust levels, however, have only locally assigned meaning. While a user may
receive a recommendation to trust a key at a certain level, both the decision
to do so, as well as the interpretation as to what that means in practice,
remains entirely under their own control. It is therefore not possible to
grant a privilege, and generate a token encoding this
authorization grant
in a way that
becomes an authoritative statement.

2.3.
Authorization Protocols

In lieu of listing the abundance of different authorization protocols in use, this paper
instead focuses only on OAuth 2.0
(
Hardt 2012
)
as a particularly meaningful
stand-in for the class of centralized authorization protocols due to its prevalence in web
applications. Authorization flows in OAuth all require an
authorization server
. This is in part due
to the fact that the server is also intended to authenticate clients.

OAuth generates authorization tokens that encode a
authorization grant
; these may be
transmitted similar to
capabilities
as part of an access request. The specific format
of token is undefined in the base specification, however. Additional
specifications
(
Jones and Hardt 2012
)
define how such bearer tokens may be transmitted.

It is worth noting that here the specifications introduce a requirement for TLS
transport encryption, in order to mitigate against various attacks involving
the leakage of tokens. The
conclusion must then be that the specification does not expect the token to
contain any protections such as
capabilities
in ICAP above that make copying them free
of risk.

One token format that can be used is JSON Web Token (JWT)
(
Jones
et al. 2015
)
. JWT
are self-contained, and contain digital signatures, making them comparable in
the abstract to X.509 certificates (section
2.2
).

2.4.
Distributed Identifiers

This document focuses on authorization, which must follow authentication.
Either involves a degree of identification of the authenticated and authorized
subject. The W3C Distributed Identifier (DID)
(
Sporny et al. 2022
)
specification is of
some interest here, as it describes a system whereby some amount of
authentication can be achieved without requiring a server component.

This is done by a similar method as X.509 certificates, in that the DID
document may contain public key material. Unlike X.509, however, DID documents
can specify to a limited degree what purpose such public keys serve.

The
relationship between public key and additional material is also inverted: where
X.509 uses the public key as the implied identifier and associates further
material with it, DIDs are themselves identifiers. They may refer to public
keys, however, establishing a similar link.

It is necessary to stress that for this reason, DID documents are not self-verifiable.
Rather, the specification requires a verifiable storage medium.

2.5.
Seals and Notaries

From a historical perspective, authorization has had two major forms dating
back millennia.

People recognized that rulers can not be omnipresent, so resorted to
delegation. In order to transfer to the ruler’s authority to their delegates,
systems often put into places provided delegates with difficult to reproduce
seals of authority. We still rely on this mechanism in the form of e.g. police
badges or similar means of establishing sanctioned delegation of authority.

In a more generalized form, we refer to this as mechanism as "power of
attorney", a concept which can be brought into the digital realm via
cryptographic signatures
(
Sudarsan
et al. 2023
)
.

The underlying mechanism to this is notarization, in which an established
authority signs statements that then delegate trust, establishing the rules by
which cryptographic certificates function.

2.6.
Evaluation

While far from a complete listing of related work, the above selection serves
to highlight the common characteristics of related technologies that together
define the context in which distributed authorization must operate.

(1)

Several technologies attempt to encode
authorization grants
into
transmittable tokens (OCAP, ICAP, OAuth, JWT).

(2)

Cryptographic identification can be solved by associating some
identifier with identifying metadata, and signing the combination with a
trusted key (X.509, PGP, JWT).

(3)

Authentication and authorization tend to be provided by an
authorization server

or local service (OCAP, ICAP, OAuth).

(4)

Nonetheless, some limited support for embedding
authorization grants
into
cryptographically verifiable assertions relating to identifiers (PGP, JWT,
DID).

As distributed authorization requires that the use of an
authorization server
as a
centralizing single point of failure is eliminated, the focus of this work is to
establish a generalized, flexible means of authorization using an approach
comparable to, but expanded from PGP, JWT and DID. The result is a fully self-verifiable
capability for use in distributed systems.

3.
System Design

When comparing the related work, it becomes apparent that it is difficult to
address authorization without first discussing authentication (section

3.1
); to make matters
worse, authentication itself can refer to subtly different things. This paper
therefore first summarizes authentication as understood in the context of the
proposed
capability
scheme (section
3.1
).

Section
3.2
examines different phases of authorization in order to both
better localize how related work centralizes the authorization problem, but
also to provide the conceptual clarity required to design a distributed
authorization scheme.

Sections
3.4
and
3.5
address ways
to mitigate potentially compromised keys referenced in
capabilities
.

Finally, section
3.6
lists necessary components of a

capability
in order to address all of the preceding considerations.

3.1.
(Distributed) Authentication

Authentication is essentially an atomic operation yielding a binary
response to the question: "Is this
subject
who they claim they are?"

However, the
subject
can be either of a real-world
person
or entity
1
1

1

We can use ”
person
” similar to the legal sense of either a natural
person (human) or a legal person, or some other meaningful group of natural
persons.
, or it can refer to a digital
agent
acting on behalf of a
person
.

This difference requires two distinct authentication processes.

3.1.1.
Authentication of a
person

Authentication a
person
establishes their identity by comparing the

person
’s observable characteristics to previously established records;
thus, if e.g. their fingerprints match those on Alice’s record, they are
identified as Alice.

3.1.2.
Authentication of an
agent

agent
identification revolves around verifying that the
agent
is in
possession of some secret, such as via
credential-based authentication
or
cryptographic authentication
.

In either case, a suitable challenge/response protocol establishes whether
the
agent
can prove such possession.

3.1.3.
Full Trust Chain

In order to establish that an
agent
acts on behalf of a
person
, some means
of combining the two approaches above is required. In the digital realm,
observing physical
person
characteristic is possible by some biometric
scanning process. But in distributed systems, the
person
is rarely in
physical proximity of the authenticating device, requiring that authentication
becomes distributed in some way.

The method of choice, such as in TLS’s use of X.509 certificates, is to
accept that there is a delay between
person
and
agent
authentication.

person
authentication occurs beforehand, and endows an
agent

identifier

with verifiable metadata that sufficiently proves the
person
’s identity
for the use case. For this reason, we refer to this as
endowment
2
2

2

In practice, automated certificate
signing via protocols such as ACME
(
Barnes et al. 2019
)
skip the identification of
real-world relationships, and instead focus only on whether related services
are under the requester’s control. This may be deemed sufficient in some use
cases.
.

A trusted authority performs use-case relevant
person
authentication. It
produces a set of identifying metadata, and adds the
agent

identifier
. It then
notarizes the combination by adding it’s cryptographic signature, producing
a cryptographic certificate.

At the point of its own authentication, the
agent
an then presents the
certificate along with answering the cryptographic challenge. For the trust
chain to be established, all that is required is that the
agent

identifier
in
the certificate is the same as used for the challenge/response protocol (or
one can be verifiably mapped to the other).

Conceptually, this introduces a
time-delayed transmission channel
: between the creation of a certificate,
and the communication of it to an endpoint that needs to authenticate the

agent
, sufficient time passes that authentication cannot be viewed as an
atomic unit any longer.

This concept of a
time-delayed transmission channel
can similarly be applied to the problem of
authorization, as described in section
3.2
.

3.2.
Distributed Authorization

Figure 2.
Architecture for capability-based distributed authorization

In the proposed scheme, we divide the authorization process into two distinct
phases similar to the preceding analysis of distributed authentication: a
pre-authorization phase grants some privilege, and serializes it into a
capability
.
The
capability
propagates to the second phase via a
time-delayed transmission channel
. In the second
verification phase, the
capability
contents are verified in a manner comparable to
that performed in authentication (section
3.1
).

Figure
2
illustrates the phases below, the components
involved and
communication flows between them.

3.2.1.
Phase I: Pre-Authorization

The pre-authorization phase is initiated by an
authorization query
. A
grantor
with
authority to grant privileges looks up
authorization tuples
in an
authorization tuple store
.

Having found an appropriate
authorization grant
, the
grantor
adds required metadata,
serializes the results and adds a signature, creating a
capability
.

The
capability
enters the conceptual
time-delayed transmission channel
.

3.2.2.
Phase II: Verification

The verification phase starts with an
access request
to a
service
. The request should come from
the
grantee
of a
capability
and should include the
capability
in its payload.

Strictly
speaking, the
time-delayed transmission channel
can have delivered the
capability
independently to the

service
before the request was made. However, as the purpose of capabilities
is to embed all relevant information to authorize a request, it makes sense to
treat the
capability
as part of the request payload. The essential part is that the
request and
capability
are both present at the
service
at this point.

It is at this point assumed that the
agent
is authenticated to represent the

grantee
, otherwise the request must fail.

The
service
then forwards the
capability
to a
verifier
. The distinction between

service
and
verifier
here is made purely in the functional domain; this
does not imply that they exist on separate network nodes. In fact, separating
them into distinct nodes might re-introduce a single point of failure for the
service.

The key point is that the
service
does not need to be aware of trust
chains, or be capable of cryptographic operations. It treats the
verifier
as
a function yielding a binary response: is the
grantee
authorized to access a
given object?

Once the
verifier
provides its response, the
service
can evaluate whether
it knows the
object
and supports the requested
privilege
. If that is the case,
it can grant effective access by responding to the request.

3.3.
Authorization Tuples

Given the above scheme, it is necessary to define the
authorization tuple
that the

grantor
looks up and signs.

The work previously done on
capabilities
is informative here (section

2.1
): whereas OCAP defines merely a
privilege
and an
object
,
ICAP expands this to include a
grantee
as well in order to mitigate against
impersonators.

Given that the
agent
needs to authenticate as acting on behalf of the

grantee
, the ideal choice for the
grantee
field is either a public key that
the
agent
can use to authenticate, or a fingerprint or other identifier that
the
service
can easily map to such a public key.

Note, however, that a resolution step may introduce new system requirements that are most easily
addressed by centralized services, so care should be taken to avoid this
pitfall.

The
object
can be any application defined identifier. However, if the

object
identifier namespace includes the
grantee
identifier namespace, this
opens possibilities for issuing
capabilities
on other
persons
in the system, which
can be used in more complex privilege management scenarios.

Similarly, the
privilege
can be any application defined value. Existing privilege
schemes such as read/write permissions for file-like objects can be trivially
mapped into this
capability
scheme. However, more complex
privileges
might include
specifying how to delegate certain
privileges
to a different
person
, and
establish a power of attorney scheme.

More discussion on delegation and
persons
as
objects
are outside the
scope of this paper.

Note also that these three fields can be
mapped neatly onto Resource Description Framework (RDF) N-Triples
(
Cyganiak
et al. 2014
)
,
which opens the possibility of treating each field as a pointer to richer
documents. Again, however, additional resolution steps may re-centralize a
system making such a choice.

3.4.
Validity Period

One concern with issuing storable and transmittable
capabilities
for authorization is
that a capability can be issued at a time when trust was established, but used
at a later date when trust was already lost.

Much the same issue exists in digital certificates for authentication, however,
so applying the same solution is valid:
capabilities
should include a pair of
timestamps defining the period of their validity.

Some use cases may require that validity periods are not used, however. This is
in particular the case when devices cannot have synchronized their local clock
yet, such as in e.g. Internet-of-Things (IoT) provisioning.

3.5.
Revocation

Issuing
capabilities
is a relatively cheap process. For this reason, validity periods
can usually be kept quite short.

However, it is always possible for trust to be lost within the validity period.
If there is then a way for the
grantor
to contact a
service
about impending
danger, that possibility should be explored.

Luckily, the data required for authoritatively granting privileges and for
authoritatively revoking them is essentially the same. It is recommended that

capabilities
come in two flavors: grants and revocations, indicated by some flag in
their content.

In doing so, revocations similarly do not require the use of a third service
that can become a single point of failure. However, revocations must occur in
real-time, introducing such a service is unavoidable.

Adding revocations also introduces an ordering issue. Assume a grant C1 is
issued for a period of [S1, E1], then a revocation C2 is issued for [S2, E2].
Finally, a third
capability
C3 is issued, granting the privilege again for [S3, E3].

For simplicity’s sake, assume S1 < S2 < S3, and E1 > E2 > E3; that is, the
periods are neatly nested into each other rather than overlapping.

For a given time point T, where T > S3 and T < E3, it is only possible to
determine whether the privilege is granted if the three
capabilities
are consulted in
issue order. If the consultation order were C1, C3 and C2, then C3’s grant
would merely confirm C1’s grant for time point, while C2’s revocation would
yield the false final result.

Introducing revocations therefore introduces the need for some way to determine
the issue order of

capabilities
– X.509 for this purpose contains a
CertificateSerialNumber

that issuers must strictly increment. A
capability
based distributed authorization
scheme should do the same.

3.6.
Capability Components

With the overall system design and additional considerations outlined in the
previous sections, it is now possible to provide a complete list of components
for
capabilities
that enable distributed authorization schemes.

Grantor Identifier:

Due to the fact that cryptographic
signatures are used, it is necessary to know which grantor issued a
capability
,
so that the signature can be verified using the appropriate key. The
identifier here can be a full public key, or a fingerprint, or some other
identifier that can be resolved to a public key
(section
3.2
).

Flavour:

The
capability
can come in a grant flavor or a
revocation flavor (section
3.5
).

Validity Period:

A period of validity should be provided
using two timestamps (section
3.4
).

Serial Number:

In order to avoid ambiguity,
capabilities
require a
serial number (section
3.5
).

Authorization Tuple:

A
capability
must contain at least one such
tuple. It is
possible, however, for a
capability
to contain multiple
authorization tuples
as an
optimization (section
3.3
).

Signature:

Finally, a signature by the
grantor
over the
preceding fields is required.

4.
Evaluation

This paper presents a generalized concept for distributed authorization
using cryptographically signed
capabilities
as a transport mechanism over a
time-delayed transmission channel
.

Information-centric networks such as Named Data Networking (NDN) issue requests
in the form of Interest packets. Routers in NDN store Interests that have not
yet been satisfied in a Pending Interest Table (PIT), and forward them to other
nodes.

Interests are intended for (short-term) storage, as are
capabilities
. This raises the
possibility of embedding
capabilities
in an Interest, such that data serving nodes
can reason about whether satisfying an Interest is desirable. In NDN, for
example, this could be done as part of the

ApplicationParameters
field
(
ndn [n. d.]
)
.

The NDN trust model revolves around encryption of Data packets, such that only
parties legitimately issuing Interests should be able to make use of the
embedded payload.

While this is approach secures payload, it is not efficient. An attacker could
easily generate otherwise legitimate Interests and receive Data packets, and then discard
them. This may be used to flood caches in intermediary routers, forcing the
network to re-fetch previously stored data requested by fully legitimate
parties (cache flooding attack).

Introducing a new component to the NDN trust model is well out of scope for
this section or paper. That being said, the components and properties of the
proposed
capabilities
are sufficient for NDN routers to determine whether an Interest
should be satisfied, if

(1)

the
grantee
can be mapped to the
KeyLocator
element of an
Interest,

(2)

the
privilege
is chosen appropriately, and

(3)

the
object
can be mapped to the
Name
element of the
Interest.

5.
Conclusion

capabilities
for distributed authorization fit well into existing information-centric
network designs, and can serve as a component in enhancing the network’s trust
model in order to mitigate against cache flooding attacks.

By decoupling cryptographic authorization into two distinct phases,
capabilities

become storable without losing authority,
and thus easily embeddable in Interest packets.

Further research is required, however, to present a full enhancement to the
trust model. In particular, routers need to become aware of whether
grantors

are authoritative for a requested
Name
without requesting and storing the
associated Data packet.
