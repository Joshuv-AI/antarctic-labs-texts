Bryt: Data Rich Analytics Based Computer Architecture for A New Paradigm of Chip Design
Ian McDougall, Shayne Wadle, Harish Batchu, Michael Davies, Karthikeyan Sankaralingam karu@cs.wisc.edu University of Wisconsin-Madison

Abstract
. Motivated by the end of Moore’s Law and Dennard Scaling which necessitate architectural efficiency as the means for improved capability for the next decade or two, this paper introduces a new data-rich paradigm of chip design for the semi-conductor industry. The goal is to enable monitoring chip hardware behavior in the field, at real-time speeds with no slowdowns, with minimal power overheads and obtain insights on chip behavior and workloads. We posit that, such extensive amounts of data would allow better and more capable architectures addressing three problems: obfuscated hardware, obfuscated software, and inability of A/B testing for hardware ideas. This paper implements the first version of the paradigm with a system architecture and the concept of an anal Y tics P rocessing U nit (YPU). We perform 4 case studies, and implement an RTL level prototype. Across the case studies we show a YPU with area overhead < 1 % <1\% at 7nm, and overall power consumption of < 25 ​ m ​ W <25mW is able to create previously inconceivable analysis: per-instruction cycles stacks of arbitrary programs, evaluating instruction prefetchers in the wild before deployment, fine-grained cycle-by-cycle utilization of hardware modules, and histograms of tensor-value distributions of DL models.

System Overview

Figure 2.
Cloud is purple, chip/DAT is green, blue is existing processes, orange is our contribution/new circuitry

We provide a full overview of Bryt’s software and hardware components first as shown in
Figure 2
, before providing the details in the following sections. To provide some context, we outline two example analytics program. First, for simplicity one that can be done in other ways as well. Consider the outputs of a Tensorcore every cycle. One analytics program is to build histograms (say 1024 equal-sized bins) of distributions of values as they are produced. The DAT would be Tensorcore, the signals are it’s output values, and the YPU would run instructions every cycle to determine the bins those values should go to. The histogram could be sent to the host’s memory every 1 million cycles. Second, considering A/B testing - an analytics program could be instruction prefetch logic, with a DAT being a CPU’s front-end block, with one signal - the
current PC
being fetched. The analytic’s output is the effective miss-rate and accuracy.

Hardware
.
The Analytics Processing Unit (YPU) is a collection of smaller hardware blocks, called YPU tiles (Figure
2
(a)). Each tile is a modified in-order RISC-V core that includes specialized instructions beneficial in analysis, and soft logic for those finite-state-machine-heavy analytics programs. These tiles are responsible for monitoring individual hardware components of the underlying chip, which we dub Data Analysis Targets (DATs). Examples of possible DATs include individual sub-modules within a core, L2 controller, GPU SM sub-modules, a CPU core etc. The tiles will be flattened into the hierarchy of the DAT for P&R purposes (Figure
2
(b)). The tiles are also connected to the underlying chip’s OCN, which is used to transfer analytics output information out of the chip. Analytics programs output small packets at long intervals so the generated traffic does not impact the applications performance.

Runtime View
.
The runtime analysis of a program is cascaded in Figure
2
(c) with time flowing downward. It shows solely the in host processes after initial setup; in other words, downloading the analytics code is not shown. The YPU driver exposes an API to configure and load the analytics code. The application can specify what regions to analyze. Once configuration is complete, the application begins execution. On each data input to the YPU, it determines if the data is within the region to analyze. If so, the analysis program executes on said data. While analysis is on-going, any further incoming data is dropped. Therefore, analytics programmers must be cognizant of the specifications from the hardware ABI. Once analysis execution completes, the YPU awaits the next data. In most analysis software, outputs occur at intervals through a logical FIFO (Figure
2
(e)). Once the user application ends, the YPU output can be post processed and, finally, exported onto disk or into the cloud.

System Architecture
.
The system architecture (Figure
2
(d)) comprises of three components: the cloud layer, an interface which exposes the YPU via an API, and the YPU itself. On the user’s end, the YPU appears as a single PCIe device, which can be programmed via a simple API. Users can download programs for the YPU “device” from an app store-like environment. This “app-store” component can either be implemented by a third-party which will host analytics programs from various actors, or it can be implemented as a first-party storefront hosting only a particular company’s analytics programs. The same is true for the cloud infrastructure needed to transmit analytics information back to those parties. The analytics programs themselves can be written by chip designers, researchers, software engineers, etc. The analytics program is then submitted to the app-store and verified, where it can be downloaded by a user with the required hardware components.

Security and Code Integrity
.

Figure
2
(e) shows an abstraction that can serve as the framework for understanding YPU’s privacy/security implications. By design, YPU cannot inject any signals into the hardware DAT. Binaries and meta-data enter a YPU tile, and analytic data is generated by it. The binaries and meta-data inputts, introduces primarily security concerns. For this work, we assume a code-signing mechanism (common in Android/iOS app store for e.g.
(
androidsigning
;
iossigning
)
) for security - which is based on highly secure public/private key technology. By associating a YPU physically to its hardware block, and using security certificates to control what code runs on a YPU, we can avoid malicious analytics.

Privacy
. Fundamentally, any technique which enables richer program analysis introduces a mechanism to leak microarchitecture design information - PICS
(
10.1145/3579371.3589058
)
enables excellent analysis of the bottlenecks of a core; by doing so, it could reveal some of the decisions that were made in producing said core. Desikan et al
(
10.1145/375212.379271
)
used performance counters to determine the Alpha21264 details decades ago.

The key privacy question is, what the analytics can infer that is not intended and thus be learned by end users or other entities like hyperscalar, foundry, etc.
For example, a end-user inferring microarchitecture details meant to be undisclosed by DAT designer. We propose a policy based approach. In the
closed
policy, a DAT designer doesn’t allow any 3rd party development. In the
restrictive
policy, a DAT designer requires source-code analysis prior to code-signing. In the
permissive
policy, a DAT designer has no restrictions, and only needs developers to have authenticated credentials. During code signing these policies are enforced, and DAT designers may use the information they know about their design and the semantics of the signals of their DAT to make this determination.
Sophisticated techniques like program verification, local differential privacy
(
rappor
;
shuffle-dp
;
cormode2018privacy
;
ldp-tianhao
;
51929
)
and secure mulitparty computation
(
cryptoeprint:2020/300
)
can provide formal and automated guarantees and are future work.
A further subtle (arguably exotic) issue is of using analytics on
DAT_{x}
to learn more information about an unrelated DAT or about the chip it is part of. It belongs in the same realm of side-channel attacks or industrial reverse engineering/espionage (through debug monitors etc.), and we acknowledge they are possible, with Bryt increasing the attack surface compared to performance counters etc.
Finally, we provide strong user privacy guarantees with a heavily restrictive system-level API that only allows analytics data to be streamed out, without any other access to host state (IP address, MAC address etc.).

4.
Software Architecture

This section describes the software implementation of Bryt with a deep dive on analytics programs. These programs, called “analytic binaries”, include code that will be run on the YPU. Bryt also exposes a host API for configuring what analytic binary to run and trigger logic. The term “user program” refers to application that runs on the chip (CPU or GPU) - like web-browser, Photoshop, DL inference etc.

4.1.
Programmer’s Model

The YPU is like any other programmable RISCV core with a unique interface: 32 named values are available as input to the analytic binary. API calls can configure what region(s) of the user program is analyzed. The analytics program analyzes one set of inputs per execution. A small on-YPU memory is available for programs to use. Once analysis finishes, if new input data is available, the program is ran again or the YPU enters an idle state waiting for data. At the end of the user program some post processing can be done to finalize information for offloading.

Data & Transfer Semantics
.
A DAT’s signal interface to these 32 named values would be exposed to users through a formal documentation like an ABI Spec specifying semantics of signals and data arrival rate. Analytics developers must ensure that DAT signal production rate matches analytics processing speed in the YPU tiles, or use sampling, or be cognizant that some data will be dropped if there is a mismatch. Like microarchitecture-specific performance counters, this ABI is microarchitecture specific.

Analytic binaries are able to transmit data via host-memory mapped to the YPU’s address space. For example, on a PCIe device, a host-memory FIFO can be mapped to the device. The YPU can then issue simple memory instructions to the device’s memory hierarchy that are then transparently routed to a region in host memory. Using this, we can create a store for analytics results.

4.2.
Software API and Execution Management

To configure what analytic binary is to be executed as well as execution triggers, Bryt exposes a minimal host-side API which are facilitated via memory-mapped I/O to the YPU. To configure a binary for execution,
YPU_CONFIG_IMAGE(image)
specifies that a YPU should load a given analytic binary
image
. To configure the analysis begin and end points,

YPU_CONFIG_START(addr)
and
YPU_CONFIG_STOP(addr)

sets the YPU to begin and end processing, respectively, when the program to be analyzed reaches
addr
. To enable fine-grained analysis we expose
YPU_PAUSE()
and
YPU_RESUME()
to temporarily pause and resume analytics execution. Finally, the command
YPU_FINALIZE()
instructs the YPU to execute any clean-up code necessary for the analytics program.

This API is exposed similar to CUPTI for CUDA
(
nvtx
)
or Linux’s perf /
perf_event
API
(
linux-perf
)
where a harness process can configure and trigger YPU execution transparent to an application binary; or alternatively, a user binary can be instrumented itself to configure the YPU and make use of
PAUSE
/
RESUME
to allow for more fine-grained processing.

5.
Hardware Architecture

We first describe the YPU’s architecture, then the details of a tile. We use the term host to refer to the chip whose DAT blocks the YPU tiles are connected to.

5.1.
YPU Architecture

Figure 3.
YPU hardware architecture.

YPU is a logically and physically tiled architecture, comprising of YPU tiles as shown in Figure
3
(a). These tiles observe hardware signals from DATs and run analytics binaries on those signals. The tiles use the host chip’s OCN, which enables them to transmit analytics outputs to (which are infrequent) and configuration from the host. The YPU is visible as a PCIe device and uses PCIe to interface with the host as shown in Figure
3
a.
If the host chip lacks an OCN, some form of network which connects the tiles to the PCIe interface will need to be added by the chip developers.
DAT-tile connections are short because the YPU tile is flattened into the DAT during P&R. Therefore, wiring overheads are negligible. Depending on the signals in a DAT and what the DAT itself is - there could be wiring issues, which can be addressed with standard buffering techniques used for performance counters. Consider a square DAT that is 2
mm^{2}
. At a simple level, signals might need to traverse
2.8mm
(half the perimeter of the DAT) to reach the YPU logic. To avoid timing issues for a high frequency design, one flip-flop might be necessary. Since this “far away” signal is buffered by one cycle, it implies all signals of this
DAT\rightarrow YPU
must be buffered. DAT designers can use P&R feedback to judiciously select signals to avoid/minimize this.

There is no type of cross-chip wires. Analytics configuration and output transfers occur over the host’s OCN and PCIe; both transmit small packets at long intervals meaning the traffic is negligible. We acknowledge, that even this meagre PCIe analytics traffic can introduce QoS and interference leading to non-linear slowdowns. Optimizations to this traffic management are beyond the scope of this paper.

Configuration of the YPU occurs through an API call:
YPU_CONFIG_IMAGE(image)
. This bundles the analytics binary (and trigger logic meta-data - details in the tile description below) and sends it to the appropriate tile based on a given a hardware device ID.

5.2.
YPU Tile

Figure 4.
YPU Tile Microarchitecture showing datapath, control-path changes and soft-logic design

Hardware organization
.
The YPU tile architecture comprises of five components:
a programmable core, soft-logic, a scratchpad SRAM, 32 input registers (IORegs), and 3 trigger registers: Trigger Start (TS), Trigger End (TE), and ADDR. The Trigger logic looks at the ADDR signal from the DAT along with TS and TE (programmed using API calls) to control when the tile becomes active. This is shown in Figure
3
c. The soft-logic interfaces with the RISCV core through 8 32-bit special registers (SLRegs) that are memory-mapped starting at address 0x5000. The soft-logic is abstracted through specialized instructions that perform large amounts of work. For most programs, the soft-logic can be thought of as being converted into clusters of logic that are explicitly activated by a bit-mask register under control of the RISCV core. If the soft-logic block is used, the RTL design would be included as part of the analytics program which the user downloads, and could be transmitted to the tile in the same way as the analytics binary and trigger logic information is. To concretize the architecture, we select some sizes for these components: the core is 32-bit RISCV core (RV32I instruction set) using a data-SRAM and an instruction-SRAM extended with specialized instructions (see above); the soft-logic is essentially an embedded FPGA with CLBs and very small BRAMs; the scratchpad is a 32KB SRAM. The choice of specialized instructions was driven by their ubiquity of usage.

RISCV core (Figure
4
(a))
. We implemented the processor core to have access to a small instruction and data-memory without caches. Programs are sized to be small, and their data structures are expected to be small. For security reasons the tiles operate in their own address space (8 KB) and cannot write to DAT or host memory. In cases where output logs need to be written, they use PCIe stores to a host address space FIFO allocated by the program’s host code. The core is implemented with a 5 stage pipeline - we are able to run this at 2 GHz at 7nm. The modifications to a standard core are shown in blue in Figure
4
(a).

The histogram unit is shown in Figure
4
(b) - it can classify 4 inputs every cycle into 128 buckets, by first “quantizing” or hashing the inputs to create a bucket number. The four bucket numbers are fed through a collector network that then feeds into 128 18-bit accumulators (ACCs) which maintain the values of the buckets. We built a parameterized histogram unit, and 128 buckets was a good sweet spot for utility, area, and power. This unit also serves as a 4-wide SIMD adder, by avoiding any hashing in the first step and treating the inputs as the inputs to the ACCs. We added the loop-counter mode to allow processing every cycle without bubbles for single-instruction and analytics code with small-loop programs. Our hash instruction’s implementation uses XOR based hashing of nearby bits for each bit of the output word
(
1432664
)
.

Soft Logic (Figure
4
(c)(d))
.
The soft-logic configuration is based on empirical work and it is arguably a bit over-fitted.
We size to have it to have 590 CLBs, eight very small BRAMs (64 entries deep and 64-bits wide), and AIO tiles (470). We mapped an open-source
(
fp32-repo
)
FP32 add (3-stage), mul (4-stage), divider unit (bit-wise), which reached 49% utilization.
The AIO tile design is our modification to the baseline IO tile, in which we removed staging flip-flops, which are already in our IORegs. The basic soft-logic design is based on Fabulous
(
10.1145/3431920.3439302
)
and their tool-chain which is silicon-proven.

Execution Model
.
A YPU tile has a 4-bit STATUS register, putting it in 6 states: PAUSED (P), ACTIVE-PAUSED (AP), ACTIVE-RUNNING (AR), FINALIZE (F), ERROR (E), UNDEFINED (U). It’s program structure includes 3 predefined program regions:
init, main
, and
end
. Borrowing from the simplicity of micro-controllers,
init
is hardcoded to instruction memory address 0x0. The entire instruction memory is 8KB which amounts to 2048 instructions long. On power-on, PC is set to 0 and starts executing the code in
init
. By convention,
finish
is hard-coded to be 16 instructions from the bottom of the instruction memory 0x7F0. When the tile is set to the finalize state, it executes code in the
finish
function and transitions to the PAUSED state.

The execution model of code on a tile is data-driven, i.e. when new inputs arrive the
_main
function is called if the tile is in ACTIVE-PAUSED state. If it is running code triggered by previous output it will be in ACTIVE-RUNNING state - data received when in this state is dropped. Whenever we show a datapath of X bits for the IO registers, there is an implied additional valid bit associated, which is used by the tile’s hardware to determine whether new input has arrived. The analytics developer must reason about dropped data’s impact, if DAT data arrival exceeds the tile’s processing rate.

Analytics
. The analytics code has two phases: every cycle we update a Performance Signature Vector (PSV) which is essentially a bit-mask that indicates which event has occurred for a particular dynamic instance of a PC. This follows a sequential if-else-if sequence across all supported hardware events, where if an event occurs in the core pipeline a load-modify-store sequence sets a specific bit of the appropriate PSV to a ’1’. If an instruction is flushed, we store its associated PC value in the tile’s memory, so that we can reference it after it commits. Every 400,000 cycles (TEA paper’s design value) we update PICS which correspond to combining the delays of every dynamic instance of a PC into a single entry. The analytics code scans through the active list of PSVs to determine to which PSV we can attribute cycles and sends to the FIFO a payload comprising of PSV (PC + signature).

Performance analysis
.
215 bits of data are used every cycle in this case study. Because events are rare, in the common case (representing more than 75% of the cycles - our results and traces we obtained from TEA authors confirm this), no event is triggered when the ROB is sampled (as it isn’t stalled/drained). In the 25% eventful cycles, typically a single long latency event occurs. Some times 2 or more events occur when the ROB is sampled (very rarely 3 events, and almost never more than that). Outside of the cycles where the ROB is sampled, there are typically 1-3 events in the processor pipeline which need to be processed, triggering 3-9 instructions of code. The analytics output data volume is low – a few bytes of PSV data every 400,000 cycles.

. Our second case study is a novel type of hardware design flow - feature testing in the field. We show that the recently proposed entangled prefetcher

SOTA-Capability
. This use case fundamentally requires cycle-level processing of values beyond distribution / aggregation requiring all five attributes to support something like A/B testing of prefetching. The LBA paradigm
(

DAT & Interface
. The DAT is the CPU front end block, and we need essentially one data signal - fetch PC being issued by the processor core (depending on the decoupled front-end design, the signal could be different). The analysis is performed over the entire program as no signal is connected to ADDR.

Analytics Code
. Implementing the prefetcher using RISCV code is too slow resulting in many dropped data (a state-machine traversal is heavily branchy code). Instead we implement it on the soft-logic and are able to run at one address per cycle with nearly full eFPGA utilization. The RTL design of the prefetch emulator is shown in Figure
8
. Since we cannot inject anything into hardware, our entangling design assumes that all L1 misses are L2 hits to determine entangling pairs (we measure the error this introduces). The execution of memory requests is still correct under this assumption - it does not change the contents of L1.

Performance analysis
. The performance analysis here is quite simple - the design accumulates coverage, misses, and accuracy counters in hardware and emits them periodically (every
2^{31}
cycles to the host) to avoid overflow. Thus the traffic to host is quite minimal.

Simulation methodology and results
.
In our Champsim testbed we ran 135 CVP2 traces and compared YPU based prefetch to the original entangled prefetch implementation from authors. Our results are nearly identical to the results from the original paper, as the only difference is the always-hit-in-L2 assumption, discussed below. To measure error we compare our statistics to the reference simulation’s statistics.

Bryt can study microprocessor policies in the field on real workloads to infer behavior prior to implementing in new versions of Silicon: a form of in-field A/B testing thus far impossible for microprocessors.

Use case definition and utility
. Both GPU hardware and software designers could benefit from a cycle-level view of hardware activity of in-field use as GPU architecture evolves in complexity

Recent studies have leveraged this available utilization for 15% improvements
(

gpu-utilization-combo

SOTA-Capability
. To achieve this case study, we need the state of different signals in different points in time, on which we perform analytics (i.e. create a distribution). The hardware profiler body of work (
Table 1
) is the closest approach for this case study. In particular, profiling co-processors
(

would be the most amenable to this case study but is not able to accurately capture fine-grained utilization particularly when phases of utilization are non-uniform.

DAT & Interface
. This is a GPU case study, with the DAT for the YPU being an SM scoreboard block. The data signals are 3 one-bit signals indicating whether, the SIMT core is active, TC is active, L1 cache subsystem is in a state where it is servicing one or more outstanding requests (MSHRs non-empty status). While GPU hardware is proprietary the performance counters from NCU count aggregates for these signals indicating they are readily available and not disrputive from a design standpoint.
Optionally retiring PC is connected to the ADDR register with YPU’s software API used to restrict regions of interest. To isolate to a region within a kernel, PC start and end range be provided. Or can be run without trigger to capture this activity for entire kernel.

Analytics code
.
The analytics code is a single histogram instruction (optimized with a loop directive) that runs for 256 cycles getting new data every cycle. The output is 3 bytes every 256 cycles, denoting how many active cycles of that unit, which can also be batched across windows.

Performance analysis
. Every 256 cycles, we we emit three 1-byte values; thus output data analytics bandwidth is
3 * 108(#SMs) / 256 bytes per cycle = 1.7 GB/second at 1.4 GHz. This frequency of this host traffic can be further reduced by batching in the tile’s data-store. By using longer windows the traffic can be further reduced.

7.4.
Value Histograms

Use case definition and utility
. This use case is targeted at arithmetic,
showing that by looking at the distribution of values in the wild in real applications, informed data-driven decisions on arithmetic can be made for both design-time and adaptive run-time decisions. In particular, we determine histograms of
values
of tensors in deep learning applications to understand inter- and intra-application differences.

SOTA-Capability
. Since performance counters track events, not values, they wouldn’t be able to implement this case-study. Software-based value profilers (that support GPUs) would be able to implement this use-case, but would suffer integer-factor slowdowns, consequently voiding pervasiveness and in-the-wild gathering of data (see
Table 1
).

Recent work has shown arithmetic can play a large role in energy efficiency
(
darvish2020pushing
)
. With Bryt, foundries, IP-block developers, chip designers, and users can develop targeted solutions. We study studies this in the context of GPUs (although the exact same interface and analytics code can be used on a CPU). We demonstrate empirically two results: first we can obtain histograms of distributions. Second, we show that distributions have substantial differences between operators and across operators between applications, showing that data richness is necessary. The description of the design is brief due to space.

DAT & Interface
. The DAT is the L1 dCache block. The data signal is 256-bits corresponding to cache-line writes into the L1 cache (exact width not public), of which 64-bits are used with the remaining dropped to conserve power and area.

Design, Performance, Results, Error Analysis
.
The analytics is a single instruction hash. Our hardware histogram unit has a 18-bit adder, hashing 4 elements every cycle, thus running for 65536 cycles without overflows. Thus, our analytics data stream bandwidth is
128*3~bytes*108~SM*1.4GHz/65536=0.9GB/sec
. For results, we produce a histogram per tensor for the values within around 5000 activation tensors from inference Resnet (batch=16), BERT (tokens=128) and LLama2 (tokens=64). By considering each tensor’s histogram as a 128-D vector, we can get inter-tensor cosine similarity. By averaging tensors across an application, we can also get inter-application similarity. Both of these are shown in Figure
6
(d). These show tensors have dis-similarity between applications in their value distributions, showing application-driven arithmetic optimizations could help. For high efficiency, we sample only 1/4th of the data, whose error metric can be defined as average relative error of every tensor across every bucket per application between sampled and non-sampled.

Takeaway 4.

Using Bryt, value histograms are possible without application modification by all entities in the semi-conductor stack. Furthermore, our analysis shows that values distributions are highly varied across applications and within, thus showing data richness is necessary and valuable.

8.
Conclusion

This paper introduces a new paradigm of computing called Data Rich Analytics based design that allows future chips to introspectively run analytics on the data they generate. The vision of this paradigm is to transform computer architecture into a heavily data driven field, allowing data analytics on real workloads running in the wild at real-time speeds. This paradigm allows a more efficient design cycle and could serve as a replacement to the now ended Moore’s Law + Dennard Scaling cycle. We showed an implementation with Bryt’s architecture that only adds
3\%
of area and
<25
milliwatts of power per YPU tile evaluated with four diverse case studies of the paradigm. Bryt, and future implementations, could transform the way chips are designed.
