PathFinder: Returning Paths in Graph Queries Volume: 0
B.F.Benjamín Faríaslabel=e1]bffarias@uc.cl, W.M.Wim Martenslabel=e2]wim.martens@uni-bayreuth.de, C.R.Carlos Rojaslabel=e3]cirojas6@uc.cl, D.V.Domagoj Vrgočlabel=ed]vrdomagoj@uc.cl

Abstract
Path queries are a central feature of all modern graph query languages and standards, such as SPARQL, Cypher, SQL/PGQ, and GQL. While SPARQL returns endpoints of path queries, it is possible in Cypher, SQL/PGQ, and GQL to return entire paths . In this paper, we present the first framework for returning paths that match regular path queries under all twenty seven modes supported by the SQL/PGQ and GQL standards. At the core of our approach is the product graph construction combined with a way to compactly represent a potentially exponential number of results that can match a path query. We describe the approach on a conceptual level and provide runtime guarantees for evaluating path queries. We also show how it can be incorporated into the SPARQL query language, thus extending RDF engines with the ability to return witnesses to property path queries (under the GQL semantics). To show the feasibility of our methods in practice, we develop a reference implementation on top of an existing open-source graph processing engine MillenniumDB, and perform a detailed analysis of path querying over several synthetic and real-world datasets. Most notably, we test our implementation over Wikidata using property path queries posted by users, extending them with the ability to return paths. We obtain order-of-magnitude speedups over modern graph database engines and remarkably stable performance, even for theoretically intractable queries.

Graph databases

All these languages have

G

n1

endpoints

[
52

[
16

A natural task would be to explore the influence network of, say,
Joe
, i.e., finding the people that
Joe
follows, then people they follow, and so on, transitively traversing
follows

, signaling that we wish to start at
Joe

follows

e1
and
e2
, there is an infinite number of paths that start with
Joe
and return to
Joe
. To avoid having to return an infinite number of paths (which can happen if the graph is cyclic), GQL and SQL/PGQ let the user specify restrictions on the type of paths to be returned through so-called
path modes

We give a few examples of path modes and provide comprehensive details later. Two common path modes are
SIMPLE
, which requires the paths to not repeat any node (apart from the first and last one), and
TRAIL
, which requires to not repeat any edge. For instance, there is precisely one path satisfying
TRAIL
that leaves
Joe
and comes back in the graph of Figure

and then back via
e1

Another common way to restrict paths is by selecting only the shortest paths. In GQL and SQL/PGQ,
ANY SHORTEST
will return a single shortest path for each different pair of endpoints in the answer, whereas
ALL SHORTEST
will return all such shortest paths. Consider the RPQ
(\textsf{Joe},\texttt{follows}^{+}\cdot\texttt{works},?x)

Joe

While Cypher, GQL, and SQL/PGQ all recognize the need to return paths that match regular path queries, the support for these features in modern graph databases is still lacking. As already stated, in SPARQL engines, RPQ matching is fully supported, but paths cannot be returned. In property graph engines that implement (fragments of) GQL or SQL/PGQ, only a handful of path modes is supported, and no property graph engine to date supports all regular path queries like SPARQL engines do. We see that SPARQL engines support all RPQs, but cannot return paths. On the other hand, while several property graph engines can return some (but not all) types of paths, they only offer a limited support for regular expressions. In addition, both SPARQL engines and property graph engines have significant issues handling path queries

. We believe that this is the case because of scalability, that is,
the number of paths that match an RPQ can be exponential in the size of the graph

.
In this paper, we tackle these problems and show that:

1.

Regular path queries can be evaluated efficiently while at the same time returning paths under the path modes prescribed by GQL.

2.

Adding these implementations on top of an existing property graph engine can be done with ease.

3.

One can extend these algorithms to the RDF/SPARQL context and extend existing SPARQL engines with the ability to return paths.

Our contribution.
To achieve the three points above, in this paper we introduce
PathFinder
, a unified framework for returning paths in graph query answers. Concrete contributions of our work can be summarized as follows:

•

We describe implementable algorithms for evaluating RPQs and returning paths under each GQL path mode. We do this by showing how to modify classical graph search to run on the product graph
[
44
,
43
]
and at the same time produce a path multiset representation
[
43
]
, a compact representation of all paths that need to be returned. We show how the compact representation can be constructed lazily, such that paths can be returned as soon as they are detected, allowing for seamless incorporation into a database pipeline.

•

We provide full implementation of
PathFinder
which is the first property graph engine to support returning paths using
all 27 modes
prescribed in the GQL and SQL/PGQ standards, while at the same time permitting
all RPQs
.

•

We extend the SPARQL syntax with the ability to return paths and implement this extension on top of an existing RDF engine, showing that our approach is a feasible extension for existing triplestores.

•

We perform a detailed experimental evaluation of our solution, using both synthetic and real-world data and queries. Most notably, we test our approach over Wikidata
[
62
]
using real world queries
[
38
]
and show remarkably scalable performance, even for theoretically intractable queries.

Our work shows that it is possible to extend SPARQL with path returning features and to keep query evaluation performant. Importantly for a clean design, however, is that the semantics of path returning queries is consistent with standard constructions in automata theory
[
37
]
. We discuss this in more depth in Section
8
.

2
Graph Databases and Path Queries

In this section we define graph databases and path queries as supported by the GQL and SQL/PGQ standard.

Graph databases.

Let
Nodes
be a set of node identifiers and
Edges
be a set of edge identifiers, with
Nodes
and
Edges
being disjoint. Additionally, let
Lab
be a set of labels. Following
[
2
,
16
,
26
,
43
]
, we define graph databases as follows.

Definition 1
.

A
graph database

G
is a tuple
(V,E,\rho,\lambda)
, where

•

V\subseteq\textsf{Nodes}
is a finite set of nodes,

•

E\subseteq\textsf{Edges}
is a finite set of edges,

•

\rho:E\rightarrow(V\times V)
is a total function, and

•

\lambda:E\rightarrow\mathsf{Lab}
is a total function assigning a label to each edge.

Intuitively,
\rho(e)=(v_{1},v_{2})
means that
e
is a directed edge going from
v_{1}
to
v_{2}
.
Here we use a simplified version of property graphs which omits node and edge properties (with their associated values). This is done since the type of queries we consider only use nodes, edges, and edge labels. However, all of our results transfer verbatim to the full version of property graphs. We also remark that our results apply directly to RDF graphs
[
46
]
and edge-labeled graphs
[
44
,
6
]
, which do not use explicit edge identifiers.

Paths.
A sequence

p=v_{0}e_{1}v_{1}e_{2}v_{2}\cdots e_{n}v_{n}
is called a
path
in a graph database
G=(V,E,\rho,\lambda)
, if
n\geq 0
,
e_{i}\in E
, and
\rho(e_{i})=(v_{i-1},v_{i})
for
i=1,\ldots,n
. If
p
is a path in
G
, we write
\mathsf{lab}(p)
for the sequence of labels
\mathsf{lab}(p)=\lambda(e_{1})\cdots\lambda(e_{n})
occurring on the edges of
p
. We write
\mathsf{src}(p)
for the starting node
v_{0}
of
p
, and
\mathsf{tgt}(p)
for the end node
v_{n}
of
p
. The length of a path
p
, denoted

\mathsf{len}(p)
, is defined as the number
n
of edges it uses. We say that a path
p
is

•

a
walk
, for every
p
(as per GQL and SQL/PGQ terminology);

•

a
trail
, if
p
does not repeat an edge (that is,
e_{i}\neq e_{j}
for every
i\neq j
);

•

acyclic
, if
p
does not repeat a node (that is,
v_{i}\neq v_{j}
for every
i\neq j
); and

•

simple
, if
p
does not repeat a node, except that possibly
\mathsf{src}(p)=\mathsf{tgt}(p)
.

Furthermore, given a set of paths
P
over a graph database
G
, we say that
p\in P
is a
shortest path in
P
, if
\mathsf{len}(p)\leq\mathsf{len}(p^{\prime})
for each
p^{\prime}\in P
. We use
\mathsf{Paths}(G)
to denote the (possibly infinite) set of all paths in a graph database
G
.

Path queries in GQL and SQL/PGQ.

Following the GQL
[
33
]
and SQL/PGQ
[
32
]
standards, we define
path queries
as expressions of the form

\textsf{selector}?\ \textsf{restrictor}\ (\texttt{x},\texttt{regex},\texttt{y})

where
selector
?
means that
selector
is optional and
regex
is a regular expression. In this paper, regular expressions are inductively defined as follows. Each element of
\mathsf{Lab}
is a regular expression,
\varepsilon
is a regular expression, and if
r
,
r_{1}
, and
r_{2}
are regular expressions, then so are their disjunction
(r_{1}+r_{2})
, their concatenation
(r_{1}\cdot r_{2})
, and the Kleene closure
r^{*}
. By standard convention, we omit brackets and (usually) omit the sign
\cdot
to simplify notation. We use
r?
to abbreviate
(r+\varepsilon)
and
r^{+}
to abbreviate
(r\cdot r^{*})
. The
language

\mathcal{L}(\texttt{regex})
of the regular expression
regex
is inductively defined as
\mathcal{L}(\varepsilon)=\{\varepsilon\}
and
\mathcal{L}(a)=\{a\}
for every
a\in\mathsf{Lab}
. Furthermore,
\mathcal{L}(r_{1}+r_{2})=\mathcal{L}(r_{1})\cup\mathcal{L}(r_{2})
,
\mathcal{L}(r_{1}\cdot r_{2})=\mathcal{L}(r_{1})\cdot\mathcal{L}(r_{2})
, and
\mathcal{L}(r^{*})=\cup_{k=0}^{\infty}\mathcal{L}(r)^{k}
. Here, for a set of words
S
, we denote by
S^{k}
the
k
-fold concatenation of
S
. The
size
of a regular expression, which we write as
|\texttt{regex}|
, is the number of occurrences of symbols of
\mathsf{Lab}
it contains.

Furthermore,
x
and
y
are variables (denoted as
?x,?y,\ldots
) or nodes in the graph (denoted
v,v^{\prime},n,n^{\prime},\ldots
). We denote variables with question marks to distinguish them from nodes in
G
.

Selectors
and
restrictors
are used to specify which paths are to be returned. Their grammar is:

\displaystyle\textsf{selector}:

\displaystyle\ \textsf{ANY}\ |\ \textsf{ANY SHORTEST}\ |\ \textsf{ALL SHORTEST}\ |\ \textsf{ANY}\ k\ |\ \textsf{SHORTEST}\ k\ |\ \textsf{SHORTEST}\ k\ \textsf{GROUPS}

\displaystyle\textsf{restrictor}:

\displaystyle\ \textsf{WALK}\ |\ \textsf{TRAIL}\ |\ \textsf{SIMPLE}\ |\ \textsf{ACYCLIC}

Here,
k
is a natural number at least 1.

A
path mode
is either just a restrictor or a selector-restrictor combination. We have 28 path modes: 6 selectors times 4 restrictors, plus the 4 restrictors without selector. However,
WALK
needs to be preceded by a selector
[
16
]
to avoid the need to return infinitely many paths in the presence of cycles, which gives 27 modes. We will often refer to the
(\texttt{x},\texttt{regex},\texttt{y})
portion of our queries as
regular path queries
or
RPQs

[
6
]
.

Next, we formally define the semantics of path queries.
Let
G
be a graph database and
q
be a path query of the form

\textsf{restrictor}\ (?x,\texttt{regex},?y)\;.

For now, we omit the optional
selector
part and assume that
x
and
y
are distinct variables
?x
and
?y
respectively.
We use
\mathsf{Paths}(G,\textsf{restrictor})
to denote the set of all paths in
G
that are valid according to
restrictor
. For example,
\mathsf{Paths}(G,\textsf{TRAIL})
is the set of all trails in
G
. We then define the semantics of
q
over
G
, denoted
\llbracket q\rrbracket_{G}
, where
q=\textsf{restrictor}\ (?x,\texttt{regex},?y)
, as follows:

\displaystyle\llbracket\textsf{restrictor}\ (?x,\texttt{regex},?y)\rrbracket_{G}=\{(v,v^{\prime},p)\mid

\displaystyle\ p\in\mathsf{Paths}(G,\textsf{restrictor}),

\displaystyle\ \mathsf{src}(p)=v,\mathsf{tgt}(p)=v^{\prime},

\displaystyle\ \mathsf{lab}(p)\in\mathcal{L}(\texttt{regex})\ \}\ .

Intuitively, for a query “
\textsf{TRAIL}\ (?x,\allowbreak\texttt{regex},?y)
”, the semantics returns all tuples
(v,v^{\prime},p)
such that
p
is a trail in our graph that connects
v
to
v^{\prime}
and
\mathsf{lab}(p)\in\mathcal{L}(\texttt{regex})
. Notice that in the case of the
WALK
restrictor, the answer set can be infinite when there are cycles in our graph.

The semantics of selectors is defined on a case-by-case basis. Using
q
to denote the selector-free query

q=\textsf{restrictor}\ (?x,\texttt{regex},?y)\;,

we now have:

•

\llbracket\textsf{ANY}\ q\rrbracket_{G}
returns, for each pair of nodes
(v,v^{\prime})

such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
, for some
p
, a
single tuple

(v,v^{\prime},p_{out})\in\llbracket q\rrbracket_{G}
.

•

\llbracket\textsf{ANY SHORTEST}\ q\rrbracket_{G}
returns, for each pair
(v,v^{\prime})

such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
, for some
p
, a
single tuple

(v,v^{\prime},p_{out})\in\llbracket q\rrbracket_{G}
such that
p_{out}
is
SHORTEST
among all paths
p^{\prime}
with
(v,v^{\prime},p^{\prime})\in\llbracket q\rrbracket_{G}
.

•

\llbracket\textsf{ALL SHORTEST}\ q\rrbracket_{G}
returns, for each pair
(v,v^{\prime})

such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
for some
p
,
all tuples

(v,v^{\prime},p_{out})\in\llbracket q\rrbracket_{G}
such that
p_{out}
is
SHORTEST
among all paths
p^{\prime}
with
(v,v^{\prime},p^{\prime})\in\llbracket q\rrbracket_{G}
.

•

\llbracket\textsf{ANY}\ k\ q\rrbracket_{G}
returns, for each pair
(v,v^{\prime})
such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
, for some
p
, any
k
tuples

(v,v^{\prime},p_{out})
such that
p_{out}
is a path connecting
v
and
v^{\prime}
. If there are less than
k
paths, all are returned.

•

\llbracket\textsf{SHORTEST}\ k\ q\rrbracket_{G}
returns, for each pair
(v,v^{\prime})
such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
, for some
p
, any
k
tuples

(v,v^{\prime},p_{out})
such that
p_{out}
is among
k
shortest paths connecting
v
and
v^{\prime}
. If there are less than
k
paths, all are returned.

•

\llbracket\textsf{SHORTEST}\ k\ \textsf{GROUPS}\ q\rrbracket_{G}
returns, for each pair
(v,v^{\prime})
such that
(v,v^{\prime},p)\in\llbracket q\rrbracket_{G}
, for some path
p
,
all tuples

(v,v^{\prime},p_{out})
such that
p_{out}
is a path of length
less than

i_{k}
, where
i_{1}<i_{2}<\ldots i_{k}
are
k

smallest lengths of paths between

v
and
v^{\prime}
. Each set of paths of length
i_{\ell}
is called a group. If there are less than
k
groups, all such paths are returned.

Notice that the
SHORTEST
modes only select shortest paths
grouped by endpoints
. That is, the selected paths do not need to be the shortest in the entire output, they only need to be the shortest matching paths from
v
to
v^{\prime}
. Furthermore, the semantics of
ANY
,
ANY SHORTEST
,
ANY
k
and
SHORTEST
k
is non-deterministic when there are multiple (shortest) paths connecting a pair of nodes and satisfying the restrictor specified by the query. We also remind that GQL and SQL/PGQ prohibit the
WALK
restrictor to be present without any selector attached to it, in order to ensure a finite result set.

Finally, if
x
is a node
n
in
G
, then the semantics is defined exactly as above, but only keep the answers
(v,v^{\prime},p)
where
v=n
. (Analogously if
y
is a node in
G
.) As such, one can also use queries of the form

\textsf{ALL TRAILS}\ (n,\texttt{a}^{+},?y)
or
\textsf{ALL TRAILS}\ (n,\texttt{a}^{+},n^{\prime})
, where
n
and
n^{\prime}
are nodes in the graph.

Example 1
.

To illustrate different path modes, we return to the graph
G
of Figure
1
and consider the RPQ

(\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x).

While
(\textsf{Joe},\textsf{ENS Paris})
is the only pair of nodes connected by a path matching this regular expression, depending on different configuration of selectors and restrictors, the set of matching paths can differ significantly. For instance:

•

\llbracket\textsf{ANY WALK}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

can contain
the triple
(\textsf{Joe},\textsf{ENS Paris},p)
, where
p
is the
path traced by the edges
\textsf{e2}\rightarrow\textsf{e1}\rightarrow\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}
, which loops back to
Joe
;

•

\llbracket\textsf{ANY SHORTEST WALK}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

can contain
the triple
(\textsf{Joe},\textsf{ENS Paris},p)
, where
p
is the
path traced by the edges
\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}
;

•

\llbracket\textsf{ALL SHORTEST WALKS}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

contains

Joe
and
ENS Paris
together with the three shortest paths linking them; namely:

1.

\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}

2.

\textsf{e3}\rightarrow\textsf{e6}\rightarrow\textsf{e10}
; and

3.

\textsf{e4}\rightarrow\textsf{e7}\rightarrow\textsf{e10}

•

\llbracket\textsf{SHORTEST $5$ WALKS}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

can contain

Joe
and
ENS Paris
together with the following five paths:

1.

\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}

2.

\textsf{e3}\rightarrow\textsf{e6}\rightarrow\textsf{e10}

3.

\textsf{e4}\rightarrow\textsf{e7}\rightarrow\textsf{e10}

4.

\textsf{e2}\rightarrow\textsf{e1}\rightarrow\textsf{e3}\rightarrow\textsf{e6}\rightarrow\textsf{e10}
; and

5.

\textsf{e2}\rightarrow\textsf{e1}\rightarrow\textsf{e4}\rightarrow\textsf{e7}\rightarrow\textsf{e10}
.

Notice here that the last two paths are not shortest in the absolute sense, but are amongst the shortest five paths linking the two nodes. Replacing
WALKS
with
SIMPLE
wold remove the final result since there are only three simple path slinking these nodes.

•

\llbracket\textsf{ANY $4$ TRAIL}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

can contain

Joe
and
ENS Paris
together with the following four paths:

1.

\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}

2.

\textsf{e3}\rightarrow\textsf{e6}\rightarrow\textsf{e10}

3.

\textsf{e4}\rightarrow\textsf{e7}\rightarrow\textsf{e10}

4.

\textsf{e2}\rightarrow\textsf{e1}\rightarrow\textsf{e3}\rightarrow\textsf{e6}\rightarrow\textsf{e10}
; and

Replacing
TRAIL
with
SIMPLE
would remove the fourth path.

•

\llbracket\textsf{SHORTEST $2$ GROUPS WALKS}\ (\textsf{Joe},\texttt{follows}^{*}\cdot\texttt{works},?x)\rrbracket_{G}

contains

Joe
and
ENS Paris
together with the following two groups of paths:

1.

Paths of length three:
\textsf{e3}\rightarrow\textsf{e5}\rightarrow\textsf{e11}
,

Remark.
While we define the semantics of the query as the
set
of all answers, the GQL specification requires path modes which can return multiple paths for a single pair
(v,v^{\prime})
of start and end nodes to return results in a grouped fashion. For instance, when answering a query of the form
ALL SHORTEST
q
, if there are multiple paths linking some
(v,v^{\prime})
pair, these should be returned one after the other before moving to another pair of nodes. All of the algorithms we present in the paper enumerate the results in such a fashion.

Output-linear delay.
Returning paths can result in a large number of outputs. Therefore, to measure the efficiency of our algorithms, we will use the paradigm of
enumeration algorithms

[
7
,
54
,
24
,
43
]
. Such algorithms work in two phases: a
pre-processing phase
, which constructs a data structure allowing us to output the solutions; and the
enumeration phase
, which enumerates these solutions
without repetitions
. The efficiency of an enumeration algorithm is measured by the complexity of the pre-processing phase, and the delay between any two outputs produced during the enumeration phase. We will say that an enumeration algorithm works with
output-linear delay
, when the delay is linear in the size of each output element. This means that the time needed to output a single path is linear in the number of nodes in the path, after which we immediately start to output the next path. Notice that this is optimal in a sense that to return a path to the user, we have to at least write down each element of the path.

Regular expressions and automata.
We assume basic familiarity with regular expressions and finite state automata
[
50
]
.
We use
\mathcal{A}=(Q,\Sigma,\delta,q_{0},F)
to denote a non-deterministic finite automaton (NFA). Here
Q
is a set of states,
\Sigma
a finite alphabet of edge labels,
\delta
the transition relation over
Q\times\Sigma\times Q
,
q_{0}
the initial state, and
F
the set of final states, respectively. An NFA is deterministic (or a DFA for short), if
\delta
is a function. A
regex
can be converted into an equivalent NFA of size linear in
|\texttt{regex}|
(see
[
50
]
). There are several standard ways of converting an expression to an automaton, for instance using Thompson’s, or Glushkov’s construction
[
50
]
. In this paper, we assume that the automaton has a single initial state and that no
\varepsilon
-transitions are present. An NFA is called
unambiguous
if it has at most one accepting run for every word. Every DFA is unambiguous, but the converse is not necessarily true.

3
Backbone of
PathFinder
and the WALK Semantics

In this section we describe the main idea behind
PathFinder
and show how it can be used to
evaluate RPQs under the
WALK
semantics. That is, we show how to treat queries of the form

\textsf{selector WALK}\ (v,\texttt{regex},?x)\;.

Recall that the
selector
is obligatory in GQL, since the set of all walks can be infinite. For simplicity of exposition, we assume for now that the starting point of the RPQ is fixed (i.e., we start from a node
v
) and discuss the other cases for endpoints later.
Our approach relies heavily on the product graph construction
[
31
,
44
]
. We present here how the product graph is built in its entirety, but in practice it is important to construct the product
lazily
, i.e., only construct the part of it that is needed to evaluate the query.

Product graph.
Given a graph database
G=(V,E,\rho,\lambda)
and an expression of the form
q=(v,\texttt{regex},\texttt{?x})
,
the
product graph
is constructed by first converting the regular expression
regex
into an equivalent non-deterministic finite automaton
(Q,\Sigma,\delta,q_{0},F)
. The automaton consists of a set of states
Q
, a finite alphabet of edge labels
\Sigma
, the transition relation
\delta\subseteq Q\times\Sigma\times Q
, the initial state
q_{0}
, and the set of final states
F
. The construction of the automaton (without
\varepsilon
-transitions) can be done in time linear in the size of
regex

[
50
]
. The product graph
G_{\times}
is then defined as the graph database
G_{\times}=(V_{\times},E_{\times},\rho_{\times},\lambda_{\times})
, where

•

V_{\times}=V\times Q
;

•

E_{\times}=\{(e,(q_{1},a,q_{2}))\in E\times\delta\mid\lambda(e)=a\}
;

•

\rho_{\times}(e,d)=((x,q_{1}),(y,q_{2}))
if:

–

d=(q_{1},a,q_{2})

–

\lambda(e)=a

–

\rho(e)=(x,y)
; and

•

\lambda_{\times}((e,d))=\lambda(e)
.

Each node of the form
(u,q)
in
G_{\times}
corresponds to the node
u
in
G
and, furthermore, each path
P
of the form
(v,q_{0}),(v_{1},q_{1}),\dots,(v_{n},q_{n})
in
G_{\times}
corresponds to a path
p=v,v_{1},\dots,v_{n}
in
G
that (a) has the same length as
P
and (b) brings the automaton from state
q_{0}
to
q_{n}
.
As such, when
q_{n}\in F
, then this path in
G
matches
regex
. In other words, all nodes
v^{\prime}
that can be reached from
v
by a path that matches
regex
can be found by using standard graph search algorithms (e.g., BFS/DFS) on
G_{\times}
starting in the node
(v,q_{0})
.

While this approach allows finding pairs
(v,v^{\prime})
in answers to an RPQ, we show next how it can be used to also find paths.
Our approach is rooted in this fairly standard construction in automata theory, but on the other hand, it has nice advantages: (a) the product graph can indeed be explored lazily
for all 27 path modes
, (b) paths can be always returned
on-the-fly
, allowing pipelined execution, and (c) the approach is highly efficient (Section
6
). We point out in which cases subtleties such as
unambiguity of the automaton
need to be taken into account to achieve a correct algorithm.

3.1

We first treat the
WALK
restrictor combined with selectors

and

\displaystyle q=\textsf{ANY (SHORTEST)? WALK}\ (v,\texttt{regex},?x)

The idea is that, given a graph database

The basic object we manipulate is a

•

•

•

TRAIL, SIMPLE, and ACYCLIC

We now devise algorithms for finding trails, simple paths, or acyclic paths. It is well established in the research literature that even checking whether there is a single path between two nodes that conforms to a regular expression and is a simple path or a trail is NP-complete
[
6
,
14
,
42
,
8
]
, so we do not know any efficient algorithms.
On the other hand, regular expressions for which this problem is indeed NP-hard are rare in practice
[
9
,
39
,
40
]
and, moreover, regular expressions for which these problems are tractable can be evaluated by cleverly enumerating paths in the product graph
[
39
,
41
]
.
Our algorithms will follow this intuition and prune the search space whenever possible. In the worst case all such algorithms will be exponential but we will show that, on real-world graphs, the number of paths will be manageable, and the pruning technique will ensure that all dead-ends are discarded. We begin by showing how to find
all
trails and simple/acyclic paths.

Implementation Details

PathFinder
is implemented as the path processing engine of
MillenniumDB
, a recent open-source graph database engine
[
64
]
.
MillenniumDB
provides the infrastructure necessary to process generic queries such as RPQs, and takes care of parsing, generation of execution plans, and data storage, while
PathFinder
executes path queries as described in the paper.

MillenniumDB
supports both the property graph data model coupled with an expressive fragment of Cypher
[
25
]
and RDF with a fully compliant implementation of SPARQL 1.1 query. The system also provides updates and a light transactional management mechanism in terms of multi-version concurrency control with a single writer thread. While the Cypher-like fragment we implement provides support for returning paths as described in this paper, we also extend the SPARQL syntax to allow path retrieval.

Syntax for returning paths in property graphs.
We extend
MillenniumDB
’s Cypher-like syntax with a special new construct that allows returning paths in RPQ query answers by adding patterns of the following form into the
MATCH
clause:

(<src>)=[<PathMode> <PathVariable> <RegularPathQuery>]=>(<tgt>)

Here
src
and
tgt
are either graph nodes or variables,
PathMode
is any path mode supported in GQL,
PathVariable
is the variable used to bind and return the path, and
RegularPathQuery
is any RPQ pattern constructed from edge labels. It is currently not permitted to reuse path variables. Notice that we use a different edge arrow for this class of queries, namely
=[]=>
, instead of the usual
-[]->
used in Cypher and GQL.

To illustrate this syntax, the query below would return all shortest paths starting at node
Joe
in Figure
1
which conform to the
:follows+/:works
RPQ:

MATCH (?src {name:"Joe"})=[ALL SHORTEST ?p :follows+/:works*]=>(?tgt)
RETURN ?tgt.name, ?p

Note that here we assume that nodes in Figure
1
have an attribute
name
which identifies their value as commonly used in property graphs.

Extending SPARQL with path returning capabilities.
To support returning paths in SPARQL, we introduce a new triple pattern with the following abstract definition:

<src> <PathMode> (<PropertyPath> AS <PathVariable>) <tgt>

Similarly as in the case of property graphs,
src
and
tgt
are either nodes (i.e. IRIs or literals) or variables,
PathMode
is a GQL path mode,
PathVariable
is the variable used to bind and return the path, and
PropertyPath
is a property path pattern. Our implementation currently supports property path patterns which do not use negated property sets and we do not yes implement the
TRAIL
path modes, as it is not clear whether a triple in RDF represents an edge, or whether a more subtle definition should be made as in the case of property graphs. Path variables are used only to return paths. Such triple patterns can the be added to SPARQL
WHERE
clause. An example query that extracts the names of people connected to
Joe
in an RDF dataset similar to the one in Figure
1
would be:

SELECT ?name ?p
WHERE {
ex:Joe ANY SHORTEST (:follows+/:works AS ?p) ?tgt .
?tgt :hasName ?name .
}

Data access.

By default,
MillenniumDB
stores graph data on disk using B+trees, and loads the necessary pages into a main memory buffer during query execution. B+trees we use are clustered on initial loading of data and their leaves store the required relations using node/edge IDs. All literal values (strings, numbers, etc.) are also represented via numeric IDs and converted to their original representation as needed. All B+trees in
MillenniumDB
are accessed using the standard linear iterator interface used in relational databases
[
48
]
. Depending on the data model used, a different set of relations is stored as we explain next.

Property graphs.

To represent property graphs,
MillenniumDB
indexes several relations, however, our algorithms only use the following two:

Edges(NodeFrom, Label, NodeTo, EdgeId)

Nodes(NodeId)

The first relation allows us to find Neighbors of a certain node reachable by an edge with a specific label, as used, for instance, in Algorithm
1
(line 14). The second table keeps track of nodes that are materialized in the database. In essence, the table
Nodes
is only used when checking whether the start node of an RPQ actually exists in the database (see e.g. Algorithm
1
, line 9). Additionally, we remark that all of the proposed algorithms can be easily extended with the ability to traverse edges backwards, as required, for instance, by C2RPQs
[
12
]
and SPARQL property paths
[
29
]
. To support this, we also index the inverse
Edges
relation
\textsc{Edges${}^{-}$(NodeTo, Label, NodeFrom, EdgeId)}.
We can then easily extend all of the described algorithms to allow RPQs with backward edges, and use the
EDGES
-
table whenever looking for a neighbour accessed via a backward edge.

RDF data.

When storing RDF data we use four different permutations of the
Triples(s,p,o)
relation. Most importantly for us being the
SPO
and
OPS
permutations which mimic the
EDGES
and
EDGES
-
relations from property graphs.

Pipelined execution.
In
PathFinder
all the algorithms are implemented in a pipelined fashion using linear iterators. In particular, this means that the solution is returned to the user as soon as it is encountered. This requires, for instance, that the main while loop of Algorithm
1
be halted as soon as a new solution is detected in line 19, and similarly for Algorithm
5
. In the case of Algorithm
2
the situation is a bit more complex, as solutions can be detected while scanning the neighbors (lines 14–24), instead of upon popping an element from the queue (lines 11-13). All of these issues can be resolved by noting that linear iterators for neighbors of a node can be paused, and their execution resumed. For completeness, we include an expanded pseudo-code of our algorithms written in a pipelined fashion, in our online appendix
[
20
]
. The main benefit of the pipelined execution is that paths can be encountered on demand, and the entire solution set need not be constructed in advance.

Query variables.
Throughout the paper we assumed that the RPQ part of our query takes the form
(v,\texttt{regex},?x),

where
v
is a node identifier, and
?x
is a variable. Namely, we were searching for all nodes reachable from a fixed point
v
. It is straightforward to extend our algorithms to patterns of the form
(v,\texttt{regex},v^{\prime})
, where both endpoints of the path are known. That is, we can run any of the algorithms as described in the paper, and check whether
v^{\prime}
is a query answer. The case when both ends are variables; namely,
(?x,\texttt{regex},?y)
, is not so easy to handle, and the techniques we developed only allow supporting it by testing all possible start nodes. Some immediate optimizations are possible here; for instance, by only considering start nodes of edges labeled by transitions that leave the initial state of the automaton for
regex
. We leave the study of this problem for future work.

How we ran the experiments.
The experiments were run on a commodity server with an Intel®Xeon®Silver 4110 CPU, and 128GB of

6.6
Conclusions

Based on our experiments, we believe that one can conclude that
PathFinder
offers a sound strategy for dealing with path queries. It is highly performant on all the query loads we considered, and runs faster than any other system in every scenario we tested. This is particularly true for the
WALK
semantics, which runs very fast and with few timeouts, even on huge datasets such as Wikidata. When it comes to
TRAILS
one has to be careful whether the BFS or DFS strategy is selected, with the former being a good candidate for highly connected graphs with few hops, and the latter being able to better handle a huge number of paths. Finally, we remark that
PathFinder
was tested only as a disk-based system that loads data into a main memory buffer as required by the queries. Our code
[
21
]
also includes an in-memory version of
PathFinder
, which uses the Compressed Sparse Row representation of graphs
[
11
]
in order to store the data in memory, and which runs about twice as fast as the results we presented (results not included for brevity).

Related Work

Most work in the area focuses on finding nodes connected by an RPQ-conforming path and not on returning the paths
[
67
,
27
,
23
,
8
,
42
,
39
,
13
]
. Notable extensions include
[
28
]
where paths are returned, but not according to an RPQ pattern, and
[
53
]
, which uses a BFS-style exploration to find the first
k
paths, meaning some non-shortest paths will be returned. Similar approach for top-
k
results is presented in
[
1
]
, but not preferring shortest paths. Closest to our work is
[
43
]
, where a compact representation of RPQ-conforming paths (called a PMR) is presented for
some
GQL path modes. Compared to
[
43
]
, we support
all
GQL path modes and present implementable algorithms, whereas
[
43
]
mostly focuses on theoretical guarantees. Interestingly, one can show that the
Visited
structure of our algorithms in fact encodes the PMR of
[
43
]
for any GQL path mode. We also need to stress that finding top
k
walks and trails is a well studied problem when the requirement that a path matches an RPQ is dropped
[
68
,
17
]
.
Additional important approaches that share similarity with our algorithmic toolbox are
[
23
]
, where a graph crawl based on the product graph construction is also exploited, and
[
47
]
, where an expressive framework for proposing witnesses to an RPQ answer (or the lack thereof) is explored. Finally, we mention that
[
15
]
studied an equivalent of Algorithm
2
which removes the restriction of unambiguity on the automaton used to find all shortest walks between a fixed pair of nodes.

8
Conclusions

We present
PathFinder
, a unifying framework for returning paths in RPQ query answers. We believe
PathFinder
to be the first system that allows returning paths under
every
mode prescribed by the GQL and SQL/PGQ query standards
[
16
]
, and that our experimental evaluation shows the approach to be highly competitive on realistic workloads. While our work was developed in the context of property graphs, it is straightforward to implement it on top of an existing SPARQL engine (see
[
21
]
for an example of this).
We showed that returning paths that match RPQs can be practically viable, which opens the question to which extent we want to explore similar functionality for SPARQL
[
29
]
. While our initial results do show that supporting path retrieval in SPARQL is feasible, it remains to be worked out how this functionality mixes with the property path syntax and semantics (which differs significantly from RPQs) and how such an extension could be worked into the new version of the SPARQL standard. In the future we also plan to look at more expressive GQL path queries which take into consideration the data residing in nodes and edges and try to develop a toolbox of algorithms to handle these cases.
