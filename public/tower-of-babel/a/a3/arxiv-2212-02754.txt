Automatically Transform Rust Source to Petri Nets for Checking Deadlocks
Kaiwen Zhang, Guanjun Liu

Abstract
This paper presents a method of automatically converting source codes (Rust programs) into Petri nets, focusing on the detection of deadlocks caused by the double locks and lock conflicts in the parallel Rust programs. We construct the transformation rules and develop a tool. Our method can omit those Rust codes without relations to locks when scanning the input codes, and thus tool can handle a large-scale code. We do a number of experiments to show the advantages of our method compared with the state-of-the-art ones.

Rust is a programming language for system software

. System languages like C or C++ focus on achieving native performance and providing programmers a full control over resource management. Rust inherits most of the features of C, while rigorous checks at the compile time can eliminate some of the security problems of C. Over the past few years, Rust has become increasingly popular, especially when building low-level softwares such as operating systems

Rust checks these safety rules at the compile time, enhancing the runtime performance compared to unsafe languages such as C. However, they still can not fully guarantee the safty of memory and thread. For example, the ownership of a lock variable can be borrowed or transferred via a pointer, and multiple aliases can read the value of the same address. Despite of Rust’s claims of fearless concurrency, there are still some potential deadlocks in multi-threaded codes due to code writing problems.

The purpose of this paper is to propose rules for transforming Rust program sources into Petri nets for detecting deadlocks caused by the lock mechanism in the Rust language. We consider various cases that lead to deadlocks, such as double locking of data and read-write conflicts. Preliminaries

2.1
Petri Net

A net is a three-tuple
N=(P,T,F)
, where
P=\{p_{1},...,p_{n}\}
is a finite set of places,
T=\{t_{1},...,t_{m}\}
is a finite set of transitions,
F\subseteq(P\times T)\cup(T\times P)
is a set of arcs, and
P\cap T=\emptyset
. The inverse net of a net
N=(P,T,F)
is defined as
N^{-1}=(P,T,F^{-1})
, i.e., the direction of each arc of
N
is changed
[
22
]
. A net can be viewed as a directed bipartite diagram where transitions are graphically represented by rectangles and places by circles. A marking of
N=(P,T,F)
is a mapping
M:P\rightarrow\mathbb{N}
, where
M(p)
is the number of tokens in place
p
and
\mathbb{N}
is the set of all nonnegative integers. Place
p
is marked at
M
if
M(p)>0
. In this paper, a marking is also called a state.

2.2
Slicing the program using Rustc

This paper choose the front of Rust compile to design the parser module, and the Rust compiler uses a different query system which is organized as a sequence of code passes executed sequentially. The aim this is done in such a way at the compiling stage is to carry out an incremental compilation when a user makes changes to their program and recompiles it
[
23
]
. In a Rust output, as shown in Figure
1
, we obtain the program’s control flow graph (CFG), which contains the paths that may be traversed during program execution.

Figure 1:
Slicing the program using
Rustc

Different from some traditional multi-threaded programming languages such as C/C++, the locking mechanism in Rust is designed to protect data accesses rather than code fragments.
Mutex structures are declared using pointers for a safe access between multiple threads, and the lock function returns a reference to a shared variable and locks it. the Rust compiler verifies whether all accesses to a shared variable are made while holding a lock, in order to guarantee mutual exclusion. The lock is automatically released when the lifetime of the returned variable holding the reference ends. Note that the Rust compiler implicitly calls
unlock()
when the lifetime ends.
Meanwhile, the following case happens almost invisibly in the code: running destructors and cleanup in the case of a panic. i.e. locks held by threads may not be released after panic.

2.3
Building a dedicated perspective

Our method and tool is based on CFG of Rust, and it only handles the CFG of functions related to lock sentences and then constructs Petri net for them. This paper considers function calls (sysall semantics) and thread constructs (sync semantics).

The function call graph uses all single-state function instances as the call list. To use function generation semantics in a multi-threading model, it is necessary to construct the fork-join model relationship between the main thread function and the child thread function. For each lock structure, the parser module extracts the relevant elements from CFG and stores them into a separate data files. The file is then transferred to a builder module.

3.1
User Interface

We provide a straightforward user interface such that users can use the tool together with other tools in the Rust ecosystem with minimal effort. Our user interface is a customized subcommand of Cargo that is the official package manager of Rust. It reads a Rust crate as its input, together with user-provided options that configure the behaviors of the transform procedure (e.g., the type of the lock). Cargo is called to automatically lock for dependencies of the input crate and to collect all the needed source files. Then, according to the lock type provided by the user, The tool initializes the converter instance with the appropriate configuration and then uses the dependency information to filter the source file, i.e. we only call the converter for the source files in the lock-related crate. This can significantly reduce the analysis time as well as the net scale.

After borrow checking and optimizations on MIR, all codes unrolled and all Rust-specific static analysis and optimizations are done. MIR optimizations greatly reduce the code and features like constant propagation and dead code elimination will help to reduce the effects of state explosion. 4.1
The Whole Program

Our transformation process starts with a set of CFGs extracted from the target Rust program. It traverses a CFG to obtain user option’s information, including lock type, thread functions, basic block and flow information. Every CFG is a directed graph. To obtain a Petri net, we first create a place for Basic Block (BB) of the CFG. For each arc connecting two block in the graph, we create a transition and two arcs in the Petri net: one is from the place corresponding to the source block to the transition, and one from the place corresponding to the target block to the transition. In general, a BB-terminate-BB chain in a CFG is transformed into a place-arc-transition-arc-place chain in the corresponding Petri net model

]
.

4.2
Control and Loop Structure

MIR takes Rust source code and simplifies it, optimizing common Rust syntax such as for-loops, matching expressions, and even method calls. These constructs are translated into an alternative format. Branch judgment logic (
if-else

Also, due to Rust lifecycle constraints, every locking operation generated in a loop is implicitly invoked at the end of the loop in order to unlock it. Hence locking in a loop can be considered as a single locking operation. The Petri net model with loop structure is shown in Figure

4.3
Function and SysCall

The Cargo command line can create bin and lib format programs. This paper utilizes bin. The conversion process starts from the Main function. Similar to program modeling in section 4.1, each function uses a pair of start and end positions. The Main function can call other functions, which can in turn call other functions, and so on. When a program is executed, the called functions are organized on a call. When a new function is entered, a new stack frame is pushed onto the stack, including function parameters, local variables, and so on. When leaving the function, it is removed from a stack, freeing the memory occupied by the frame. In MIR, the invocation and return of a function is done in a basic block terminator, and can occur arbitrarily frequently, as shown in Figure
5
. In the mapping with the Petri net model, we assign the CallSite a placeholder, and the substitution nesting is done after the CFG transformation of function is done. Considering that some behaviors in the Petri-Net function model are not helpful, we require that irrelevant functions only leave the calling position to save the calling relationship between functions.

Figure 7:
The Petri Net Model of Thread

In our implementation, we traverse the base block of the function structure to detect function calls. Every time, we encounter a function call terminator, bind the called function (the entry and exit place had beensetted for all functions at initialization) and return to the next position of the calling function when we are done. However, this approach has some drawbacks. 1. if the same function is called multiple times in the program, it will possibly produce wrong returns in a formal analysisi tool. For example, in the Figure
5
the blue token and the green token may trigger a
return1
variation, producing a wrong path. 2. low-level Petri-Nets cannot model recursion. In this paper, we focus on deadlock detection, considering that locks are generally not used in recursive functions in real programs. Therefore, our approach does not consider recursion. As shown in Figure
6
, this paper models the copy for functions with multiple calls in order to reduce the generation of false positives. In addition, the lock-independent functions will be skipped in the conversion process, so that the size of the constructed Petri Net will not be too large.

4.4
Multi-Thread

Splitting the computation in a program into multiple threads can improve performance because multiple tasks can be performed at the same time, but it also increases complexity. Because threads run concurrently, the order of execution of codes in different threads cannot be guaranteed in advance. To create a new thread, the thread::spawn function is called and a closure containing the code you want to run on the new thread is passed. The return type of thread::spawn is JoinHandle, that is an owned value. When the join method is called on it, it blocks the current thread until the thread represented by the handle ends. The thread execution model is shown in Figure
7

The execution of threads are modeled as tokens flowing through the Petri net. To properly model the lock acquisition/release functions, we split a basic block containing multiple lock functions into a group of blocks such that each block has at most one lock function associated with it. Therefore, after the model transformation, each locking operation is represented by a single transformation in the Petri net.

4.5
Model and Optimization

According to the Rust documentation, Rust uses the RAII (Resource Acquisition Is Initialization) mechanism for the lock management. Mutex allows only one thread to access some certain data at any time. In order to access the data mutually by multiple threads, a thread first needs to indicate that it wants to access the data by acquiring the lock on the mutex. The lock functions
Mutex::lock()
,
RwLock::read()
and
RwLock::write()
will return an object lock-guard which records who has exclusive access to the data. Rust complier can only access the protected data through lock-guard. When the lifetime of a lock-guard ends, the lock is automatically unlocked during the lock-guard release.

While a thread uses mutex, the entire thread is locked. When modeling a lock resource, Petri net only considers whether the resource is owned but does not consider the internal operation of the resource. Although the internal principles of mutex locks and spin locks are different, but the corresponding Petri nets have the same semantics. The representation of the Petri net corresponding to the
lock()
and
unlock()
functions is shown in Figure
8
.

Due to the exclusive nature of locks, the
reads()
and
writes()
of RwLock are behave similar to
Mutex.lock()
. Therefore they follow a double lock pattern. Almost RwLock implements write a lock variable with a higher priority. Figure
9
illustrates deadlock caused by this case, where N represents the number of concurrently acquired read locks. Read operations consume one token each time, and write operations consume all tokens. The read lock is acquired from Thread-A, which locks the write lock in Thread-B. But the second read lock waits for the write lock because the write lock has a higher priority than the read lock. Consequently Thread-A is stuck on the second read lock and Thread-B is stuck on the write lock, resulting in a deadlock.
If we want to avoid deadlock, we must ensure that there is no lock before any two lock applications in the same task, and the write lock is released as soon as possible. According to this situation, the read-write lock can also be modeled as Figure

5.2
The generated Petri net

Implementing a basic graph structure to represent our Petri-Net is not very difficult. But in order to be compatible with an existing model checker, we have to use some interface or a standard that defines a commonly known structure. Fortunately, there exists an XML-based standard for Petri Net called Petri Net Markup Language(PNML)
[
26
,
27
]
. They can list nodes (places and transitions) and arcs of a graph. Additionally, the Petri-Net representations encode information for token count and arc weight. In a generated model, the white hollow rectangle represents immediate transition and the naming rule is that the thread and lock resources are function calls. For example,
callstie
means that a function call occurs here, and
thread::spawn()
means that a new thread is opened here. After exporting a Petri net model, the PIPE tool is used to detect whether the main function is terminated or not, i.e. the termination state can be reached.

5.3
Compare to Other Static Analysis Tools

Qin et al.
[
12
]
proposed two static analysis algorithms in the
lockbud

Transforming Rust source code to a Petri net for checking deadlocks and combining with the pointer analysis technique of static analysis, out tool can correlate the operations of different functions on the same lock object. This guarantees the correctness of concurrency semantics. Also a Petri net models the called function separately, embedding it into the transition of
callsite
, and waiting for the calling function to return before continuing execution. When anther method calls the same function, we copy the calling function model and embed it into the corresponding position, and it can be modeled as the same function call in subsequent advanced net work.

Our tool constructs Petri net by re-traversing the CFG, constructing a subnet model for duplicate function copies, and comprehensively detecting the deadlock problem caused by double-lock.

Conclusion

In this paper, we propose a method to automatically convert Rust programs into Petri nets for deadlock analysis. This technique, called static analysis, is similar to performing model checking.
We use Rust compile as a front end to execute programmatic queries. We utilize CFG of a Rust program to generate a Petri net. Experiments are based on Cargo, and there is no need to rewrite commands. To reduce the size of the generated Petri nets, we consider different perspectives on program deadlocks. Depending on the information of
locked
,
unlocked
,
spawn
and
join
represented in a CFG to transfer. Our transformation process relies on our designed rules, associated with locking mechanisms. These rules have been implemented in tool prototypes. Future work will transfer source codes to advanced Petri nets in order to accommodate more error detection, such as signal, variable handling and array bounds checking.
