Efficient Secure Aggregation for Privacy-Preserving Federated Machine Learning
Rouzbeh Behnia, Sherman S. M. Chow, Arman Riasi, Balaji Padmanabhan, Reza Ebrahimi, Thang Hoang

Abstract
Secure aggregation protocols ensure the privacy of users’ data in federated learning by preventing the disclosure of local gradients. Many existing protocols impose significant communication and computational burdens on participants and may not efficiently handle the large update vectors typical of machine learning models. Correspondingly, we present e-SeaFL , an efficient verifiable secure aggregation protocol taking only one communication round during the aggregation phase. e-SeaFL allows the aggregation server to generate proof of honest aggregation to participants via authenticated homomorphic vector commitments. Our core idea is the use of assisting nodes to help the aggregation server, under similar trust assumptions existing works place upon the participating users. Our experiments show that the user enjoys an order of magnitude efficiency improvement over the state-of-the-art (IEEE S&P 2023) for large gradient vectors with thousands of parameters. Our open-source implementation is available at https://github.com/vt-asaplab/e-SeaFL .

Integrity

A malicious server can easily inject the final model with malicious updates.

The non-colluding assumption is needed since colluding users can falsely claim their data as legitimate.

III-A

Detailed Construction

Our approach extends the assumption made in most existing protocols, which rely on a subset of honest users, to a set of assisting nodes.
For privacy guarantee, only one assisting needs to be honest.
As discussed later (Section
IV-B
), the computation and communication overhead for assisting nodes are on par with common users in some of the most efficient existing protocols.
Thus, we can assume a dynamic and rotating set of users (similar to
[
22
]
) to serve as assisting nodes in each iteration (see Section
III-A2
).

In Algorithm
1
,
each user generates a
(\mathsf{sk}^{\mathtt{P}_{i}}_{\Sigma},\mathsf{pk}^{\mathtt{P}_{i}}_{\Sigma})
pair for the key exchange protocol to compute a common secret
{\mathtt{x}}_{\mathtt{P}_{i}}^{\mathtt{A}_{j}}
with assisting nodes
\mathtt{A}_{j}
.
In the malicious setting,
users and assisting nodes set up key pairs for signatures.

\mathtt{APVC}
is also initialized,
and a system secret
\rho

In the first round of Algorithm
2
,
updates are masked for aggregation.
Each user computes a masking vector
\vec{a}_{t}^{\mathtt{P}_{i}}

(using common secrets
{\mathtt{x}}_{\mathtt{P}_{i}}^{\mathtt{A}_{j}}
for
j=\{1,\dots,k\}
) to mask their local gradient vector
{\vec{w}_{t}^{\mathtt{P}_{i}}}
.
For model integrity, each user uses
\mathtt{APVC}.\mathtt{Comm}(\cdot)
to derive a commitment
\mathtt{cm}^{\mathtt{P}_{i}}
on their local gradient and sends it to aggregation server
\mathtt{S}
.
The masked gradient
\vec{y}_{t}^{\mathtt{P}_{i}}
and
the iteration number

\mathtt{S}
and the

In the malicious setting, all outgoing messages are signed

The second round is for aggregate updates.

\mathcal{L}_{j,t}

III-A
1
Extra Mechanisms around User Dropout

To ensure consistency, a dispute phase can be introduced.
If a user is missing from the list of a certain assisting node, the missing user participation message (and signature) can be delivered to the assisting node to update their list.
Alternatively, We could assume a star network topology, where users send everything through the aggregation server, which then distributes them to the assisting nodes.

III-A
2
Dynamic Selection of Assisting nodes

e-SeaFL
can be instantiated with as few as two assisting nodes (
i.e.
,
k=2
)
while maintaining privacy as long as at least one node is honest.
Other protocols relying on external assistance to unmask the gradients require a much higher participation rate from these nodes
(
e.g.
, Flamingo
[
11
]
expects
{\geq}64
decryptors per iteration).

e-SeaFL
presented in Algorithms
1
and
2
assumes a static set of assisting nodes.
However, by incorporating randomness from a trusted source (
e.g.
,
[
37
]
), the protocol can initialize with
y\gg k
assisting nodes during the setup phase and then randomly sample
k
of them for each iteration.
Assisting nodes need not be high-performance devices.
For instance, during our aggregation phase with
200
users, assisting nodes require only
{\sim}1.5
GB of memory, even when handling large models with
16,000
weights.

III-A
3
Resiliency Against Assisting Nodes Dropout

The failure of an assisting node can impede model convergence, resulting in wasted training iterations.
We suggest two approaches to enhance resiliency.
First, by dynamically selecting a small set of assisting nodes in each iteration and employing a simple secret-sharing method, other assisting nodes can reconstruct the dropped node’s secret and assist the server in unmasking the model.
This would only incur an overhead in terms of
k
, which is usually a small number and does not introduce any overhead on the users.
However, it might expose the secret of the dropped assisting node, disqualifying it from future selection.

Alternatively, we can use key-homomorphic PRF

[
26
]
.
This method permits the computation of the dropped node’s unmasking term
\mathbf{a}_{t}^{\mathtt{A}_{j}}
using only secret shares, thereby preserving the confidentiality of the assisting node’s secret key.

V
Conclusion and Future Work

Federated learning often involves highly distributed devices operating under limited bandwidth or power constraints.
Therefore, user dropouts are common, potentially disrupting the convergence of the final model or impacting its generalizability.
Existing secure aggregation protocols often require multiple communication rounds to successfully unmask the final model, with the dropout rate in each round increasing the communication overhead for all participants.

We propose
e-SeaFL
, an efficient secure aggregation protocol leveraging assisting nodes.

e-SeaFL
takes only one round in the aggregation phase.
With this simple workflow,
the usual computation overhead dependent on the dropout rate can be minimized.
Also, the dropout rate could be lower since the online aggregation only takes one round.

e-SeaFL
also provides proof of aggregation to the participating users.

One future work is to explore other privacy-preserving techniques, such as differential privacy (DP) and
k
-anonymity, to protect the intermediate and final model.

e-SeaFL
design allows for the adoption of both instance-level
[
38
]
and client-level
[
42
]
DP methods to protect against inference attacks.
Moreover, leveraging real-world data will allow for a deeper investigation into these methods’ computational and communication efficiency.

Our work did not consider protection against malicious users compromising the integrity of the final model.
Some existing approaches could be employed alongside our approach to fully protect the model’s integrity
However, such methods would require examining user (private) data, necessitating verifiable computation techniques for processing encrypted data.
Doing so

[
43
]
often involves resource-intensive cryptographic methods,
e.g.
,

[
44
]
.
Additionally, the absence of a “ground truth” becomes a significant challenge if malicious users have fabricated the data.
An alternative approach with different system assumptions, such as utilizing semi-trusted certifiers to inspect user private data, could offer an interesting direction for future research.

Appendix A
Cryptographic Building Blocks

A key exchange protocol allows two parties to agree securely on a symmetric key over a public channel.

Definition 5

(Key Exchange)
.

A key exchange protocol is a tuple of algorithms
\Sigma:({\mathtt{Kg}},{\mathtt{Ka}})
defined as follows.

•

(\mathsf{pk}_{\Sigma},\mathsf{sk}_{\Sigma})\leftarrow{\mathtt{Kg}}(1^{\kappa})
:
Takes as input a security parameter
\kappa
and outputs a key pair
(\mathsf{pk}_{\Sigma},\mathsf{sk}_{\Sigma})
.

•

{\mathtt{x}}^{\mathtt{U}_{2}}_{\mathtt{U}_{1}}\leftarrow{\mathtt{Ka}}(\mathsf{pk}_{\Sigma}^{\mathtt{U}_{1}},\mathsf{sk}_{\Sigma}^{\mathtt{U}_{2}})
: Takes as input the public key of any user
\mathsf{pk}_{\Sigma}^{\mathtt{U}_{1}}
and the private key of user
\mathtt{U}_{2}
,
\mathsf{sk}_{\Sigma}^{\mathtt{U}_{2}}
, and outputs a shared secret key
{\mathtt{x}}^{\mathtt{U}_{2}}_{\mathtt{U}_{1}}
.

The security of such protocols requires
any probabilistic polynomial time (PPT) adversary who is given two honestly generated public keys
\mathsf{pk}_{\Sigma}^{\mathtt{P}_{1}}
and
