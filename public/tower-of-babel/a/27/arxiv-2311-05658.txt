Three non-cubical applications of extension types
Tesla Zhang

Abstract
. The development of cubical type theory inspired the idea of “extension types” which has been found to have applications in other type theories that are unrelated to homotopy type theory or cubical type theory. This article describes these applications, including on records, metaprogramming, controlling unfolding, and some more exotic ones.

1.
Applications of extension types

Before getting into extension types, we first introduce some desirable features
in dependent type theories. Some can be implemented without extension types,
but extension types have their own benefit that their metatheory is fairly well understood.

1.1.
Controlling unfolding

There are times we don’t want to unfold definitions arbitrarily when programming in dependent type theory.
Imagine the following scenarios, which are also discussed in
[
6
]

(“cluttered proof states and unreadable error messages”):

•

We are to prove
f(u)=f(v)
where
f
expands to a gigantic term,
what we really need to know is that we need to show
u=v
, but the type checker is free to
just unfold
f
since
\beta
-reduction is an equality,
which would make it uneasy to see what is really going on.
Function definitions exist for reasons!

•

We wrote a library, and it’s used by a downstream codebase, and we want to change the library.
In a non-dependently typed language, we can guarantee backward compatibility by not changing the interface,
say, the types. But in our case, this is no longer true,
because definitions are part of the interfaces,
and if the downstream relies on certain functions to unfold in certain ways, then we can’t change that.
But how do we know?

That is why controlling unfolding is important. What gets proposed is that we now make explicit
in each definition that, during the type checking of this defining,
what other definitions we intend to unfold, and by default we don’t unfold anything.
There are certain things we wish to guarantee:

•

Unfolding is
transitive
. If function
f
unfolds
g
while
g
unfolds
h
,
then in
f
, we also unfold
h
.

•

Normalization
and
canonicity
. Since we’re touching judgmental equality now,
normalization in this case becomes a bit more complicated.
Sometimes we have a definition that is not unfolded, but it’s only because we do not want it to,
while traditional normalization needs us to unfold everything.
There are things we need to change here — either how we define normalization or how we think about definitions.

1.3.
Opaque encoding for metaprogramming

It is a long term debate that whether we should
encode
the complicated types with simpler types,
or have primitive notions of complicated types.
For example, we may define natural numbers in System F as the following type:

{\color[rgb]{0,0.3828,0.4766}\mathrm{Nat}}:=\forall X.X\to(X\to X)\to X

This makes the notion of inductive definitions in the type theory disappear completely.
Another example could be encoding inductive records using an inductive type with a single constructor,
as done in Lean 3
[
7
]
and Lean 4
3
3

3

https://lean-lang.org/lean4/doc/struct.html
,
or with a
\Sigma
type.
For instance, the definition
Precat
above could be encoded this way:

{\color[rgb]{0,0.3828,0.4766}\mathrm{Precat}}:=\sum_{{\color[rgb]{0,0.3828,0.4766}\mathrm{Ob}}:{\color[rgb]{0,0.3828,0.4766}\mathrm{Type}}}\sum_{{\color[rgb]{0,0.3828,0.4766}\mathrm{Hom}}:{\color[rgb]{0,0.3828,0.4766}\mathrm{Ob}}\to{\color[rgb]{0,0.3828,0.4766}\mathrm{Ob}}\to{\color[rgb]{0,0.3828,0.4766}\mathrm{Type}}}\cdots

Encoding has many advantages:

•

They make the theory
simple and expressive
: we can talk about these complicated things in a
minimalistic type theory with just
\Pi
,
\Sigma
types and universes,

•

They make
automated theorem proving
easier, because the solvers will have fewer constructions to understand,

•

They make
metaprogramming
much more pleasant, because we can now write programs that manipulate these encodings,
which is based on a much simpler syntax. A minimalistic type theory is way easier to do
induction (or unrestricted recursion) due to their tree-like nature
4
4

4

We refrain from saying they’re
inductive

or
algebraic
because syntax might involve in recursions in negative positions, which is not allowed in inductive types.
,
while the primitive inductive types have a way more complicated inherent structure.

They also have disadvantages:

•

Error messages
will be unreadable. There are times we want to talk about theorems on natural numbers,
lists, or trees, but somehow due to the encoding they can become theorems about long functions,
and it is easier to get lost,

•

Interactive theorem proving
becomes painful. What constructor should I apply?
How should I think about this data structure?
It is the type that should give this kind of information, but now it’s gone,

•

Without the encoding, type checking is more
efficient
. Comparing two long function types is less efficient than just
comparing two names.

It would be so nice if we can work with primitive inductive types or records most of the time,
and whenever we need to talk about metatheory, do metaprogramming, or invoke a solver,
we replace with encoding.
If at the end of the day everything is encoded, compiling the language would also be easier.

But how do we control this? This sounds a bit like controlling unfolding,
but instead of definitions, we talk about unfolding types themselves.
Looks like they can be solved by the same mechanism!

Suppose we are working on a type theory based on Martin-Löf’s dependent type theory

2.1.
Context restrictions with propositions

We add a new “universe of
strict
propositions”
F
to our type theory,
which we think of as a type, and instances as certain
propositions
.
They are called so because we wish to talk about the
truthness
of these instances.

This is not to be confused with the “propositions-as(-some)-types” propositions.
For instance, if there were to have logical connectives in
F
,
they will be unrelated to the formation rules in the type theory.
We will not have implication in
F
just because we have function type.

Remark 2.1

(ST
λ
C)
.

From a syntax perspective of type theory,
the treatment of
F
compared to the universe of propositions as in Curry–Howard correspondence,
is similar to how Russell’s simple theory of types
[
9
]
is related to simply typed
λ
-calculus:
The instances of
F
do not correspond to types, nor do they correspond to

as in universe á la Tarski
[
10
]
. Instead, they are just terms, and the logical deduction on these terms
follows its own system, and is nothing to do with things like function types in the type theory.

This is also mentioned in
[
6
, Remark 2]
in a different context.
∎

Remark 2.2
.

Actually,

is no longer true if we are to think about semantics
or type theories with multiple layers, because these propositions can be thought of as types
from another

.
But we will avoid those discussions to keep the focus
on the syntax and implementation aspects of type theories.
∎

We will keep working with the universe of propositions abstractly when
defining the syntax, and then talk about the intuition and examples.
If readers have trouble understanding the syntax, they are encouraged to jump between the latter
sections and contents below to avoid brain stack overflow.

With

, we introduce the notion of

, which gives rise to judgments of this form,

Γ⊢φ:{\color[rgb]{0,0.3828,0.4766}F}
and

The idea is that we add

Then, it is part of the

When substituting over this judgment, we not only need to provide an instantiation for

but also a proof for

.
Naturally, we assume

Observation 2.3
.

The structure of the propositions in

because they affect typing.
It is very easy to break decidability of type checking

∎

Demonstration 2.4
.

Suppose we can talk about judgmental equality in
{\color[rgb]{0,0.3828,0.4766}F}

then we essentially get equality reflection,
because we can now say things like

And this judgment should hold. Essentially we have a way to

This is both an example of how to think about context restrictions in action
and how to abuse them to break decidability.
∎

Remark 2.5

(Semantics)
.

Continuing the discussion in
remark

: from a semantic point of view,
judgments with propositions in the context can be thought of as really passing their proofs.
But this all happens in the meta-level,
and the proofs need to be done automatically in the type checker.

Extension types and their typing rules

Context restriction is the tool we need to define extension types.

The rules (in the order of formation, introduction, elimination, computation)

Define the uniqueness rule.

\frac{\Gamma\vdash A~\text{type}\quad\Gamma\vdash φ:{\color[rgb]{0,0.3828,0.4766}F}\quad Γ,φ⊢u:A}{\Gamma\vdash\Set{A}{\overline{φ▷u}}~\text{type}}\frac{\Gamma\vdash v:A\quad\overline{Γ,φ⊢u≡v:A}}{\Gamma\vdash\textsf{inS}(v):\Set{A}{\overline{φ▷u}}}\frac{\Gamma\vdash v:\Set{A}{\overline{φ▷u}}}{\Gamma\vdash\textsf{outS}(v):A\\

\overline{Γ,φ⊢\textsf{outS}(v)≡u:A}}\frac{\Gamma\vdash v:A}{\Gamma\vdash\textsf{outS}(\textsf{inS}(v))≡v:A}

Figure 2.1.
Rules of extension types

Let’s read the rules one by one.

•

The

3.
Extension types in action

3.1.
Controlling unfolding and metaprogramming

For controlling unfolding, we for every definition
f
create a corresponding proposition

φ_{f}:{\color[rgb]{0,0.3828,0.4766}F}
, meaning that “we want to unfold
f
”.
Then, this is what happens when we call functions:

•

Now, whenever we say in the context “we want to unfold
f
”,
we add
φ_{f}
to the context and restrict the context by it.

•

Every definition
f
gets renamed to
\delta_{f}
,
and references to it gets wrapped into an extension type:

f:\Set{A}{φ_{f}▷\delta_{f}}

So, it only unfolds to its actual definition when we say so.

•

When we call a function, say, write
f
in the source code,
the type checker translate that into
\textsf{outS}(f)
.
This term has the same type as in the source code,
and the only difference is in judgmental equality.

For every definition
f
, it declares which other definitions it unfolds (say,

),
and this is used to restrict the context when type checking
f
,
and in the logic of
F
, we add a rule
φ_{f}\implies φ_{g}
.
This makes unfolding automatically transitive due to the transitive nature of logical implication.

.

[

]

and in their HoTT 2023 abstract
5
5

5

it’s called

.
∎

Then we get the following guarantee:

•

Unfolding is totally controlled by the context restriction, which is controlled by the user.

•

Unfolding is transitive and only transitive —

Modifications of judgmental equality is achieved with extension types,

Definitional projection with projective extension types

Another approach is to use a new extension type designed specifically for records
and their projections.
For record

,

\frac{\Gamma\vdash R~\text{is {\color[rgb]{0,0.1992,0.7031}record}}\quad\Gamma\vdash\overline{f~\text{is a field of type}~T~\text{of}~R}\quad Γ⊢\overline{u:T}}{\Gamma\vdash\Set{R}{\overline{f▷u}}~\text{type}}\frac{\Gamma\vdash\overline{r.f≡u:T}}{\Gamma\vdash\textsf{inS}(r):\Set{R}{\overline{f▷u}}}\frac{\Gamma\vdash r:\Set{R}{\overline{f▷u}}}{\Gamma\vdash\textsf{outS}(r):R\\

\Gamma\vdash\overline{r.f≡u:T}}\frac{\Gamma\vdash r:R}{\textsf{outS}(\textsf{inS}(r))≡r:R}

Compared to the rules of extension types, the only differences are:

•

we let

•

We additionally allow projections on the extension type,
and they compute to the expected value.

Note that in the rules presented above, we also treated the iterative nature of record fields informally.
In fact, for every specified field, we need to have that known type available in the type checking of the
rest of the clauses. This is because records are dependent, and some clauses will only make sense when
other clauses are specified.

The
=
and
0
in this expression are not the usual equality and zero,
instead they are just keywords.
We may use the following type to encode the path type
a=_{A}b
:

(i:\mathbb{I})\to\Set{A}{(i=0)▷a,(i=1)▷b}

Elements of this type will behave exactly the same as paths in cubical type theory,
where applied by
0
it returns the left endpoint
a
, and applied by
1
it returns the right endpoint
b
.
Introduction of this type behaves exactly the same as the introduction of paths, no surprise.

Note that this is exactly what is called an extension type in cubical type theory,
where the free variables in the propositions
φ
are all bound in the extension type.
In the PL applications, all propositions are constants,
so we don’t need to have a place for all those binders.
The unbounded version of this in cubical type theory is called a
cubical subtype
.

If we think of the

The formation rule for extension types in cubical looks like the following:

\frac{Φ,\overline{i:\mathbb{I}}⊢φ:{\color[rgb]{0,0.3828,0.4766}F}\quad Φ,\overline{i:\mathbb{I}};Γ,φ⊢A~\text{type}\quad Φ,\overline{i:\mathbb{I}};Γ,φ⊢u:A}{Φ,Γ⊢[\overline{i:\mathbb{I}}]\Set{A}{\overline{φ▷u}}~\text{type}}

The context is
dyadic
, that is to say,
split into “interval context”
Φ
and the usual “type theory context”
Γ
,
and all the terms in the formation are bound in the interval variables in the list
\overline{i:\mathbb{I}}
.

In simplicial type theory where extension types are first introduced,
the definition is much more general and fine-grained.
It starts with a general notion of
type theory with shapes
where
there is the type of
cubes
, e.g. an interval type
\mathbb{I}
and its products,
and the type of
shapes
described as propositions on cubes.
So, saying
\overline{i:\mathbb{I}}⊢φ:{\color[rgb]{0,0.3828,0.4766}F}
is similar to saying “
\Set{\overline{i}}{φ}
is a shape”,
and
φ
by itself is referred to as a
tope
.

Demonstration 3.7
.

In the context
i,j:\mathbb{I}
, the truth proposition is the full square,
the proposition
(i=0)
is an edge of the square,
and proposition
(i≤j)
is a triangle in the square.
∎

Based on this idea, we first rewrite the cubical version of extension type using
the notation in simplicial type theory

2

\frac{Φ,\overline{i:\mathbb{I}}⊢φ~\text{shape}\quad Φ,\overline{i:\mathbb{I}};Γ,φ⊢A~\text{type}\quad Φ,\overline{i:\mathbb{I}};Γ,φ⊢u:A}{Φ,Γ⊢\Braket{\prod\nolimits_{\overline{i:\mathbb{I}}}A|{}^{φ}_{u}}~\text{type}}

Then, we allow
A
and

to be in difference shapes.
This gives us the very original definition of extension types:

\frac{Φ,\overline{i:\mathbb{I}}⊢φ~\text{shape}\quad Φ,\overline{i:\mathbb{I}}⊢θ~\text{shape}\quad Φ,\overline{i:\mathbb{I}},φ⊢θ\quad Φ,\overline{i:\mathbb{I}};Γ,θ⊢A~\text{type}\quad Φ,\overline{i:\mathbb{I}};Γ,φ⊢u:A}{Φ,Γ⊢\Braket{\prod\nolimits_{\overline{i:\mathbb{I}}~\mid~θ}A|{}^{φ}_{u}}~\text{type}}
