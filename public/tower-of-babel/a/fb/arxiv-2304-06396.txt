Kind Inference for the FreeST Programming Language
Bernardo Almeida, Andreia Mordido, Vasco T. Vasconcelos

Abstract
We present a kind inference algorithm for the FreeST programming language. The input to the algorithm is FreeST source code with (possibly part of) kind annotations replaced by kind variables. The algorithm infers concrete kinds for all kind variables. We ran the algorithm on the FreeST test suite by first replacing kind annotation on all type variables by fresh kind variables, and concluded that the algorithm correctly infers all kinds. Non surprisingly, we found out that programmers do not choose the most general kind in 20% of the cases.

valid patterns of interactions. For example a file should be opened and
eventually closed, after which no read or write operations should ever be

Quill
[

functional types. Contrarily to

kind mechanisms to distinguish between linear and functional types, instead it
uses type predicates (or, qualified types) to reason about linearity.
Furthermore, Quill does not support subkinding. Quill also has a type inference
algorithm which was proven sound and complete.
Affe
[
14
]
is an ML-like language with support to linear, affine
and unrestricted types. Like Quill, Affe uses kinds and constrained types to
distinguish between linear and affine types. Affe supports subkinding and it is
equipped with full principal type inference.
Like Affe, Alms
[
18
]
is an ML-like language but is based on

, the higher-order polymorphic

with subtyping. Alms supports affine and unrestricted types. It features a rich
kind system with dependent kinds, unions, and intersections. Moreover, Alms supports ML
modules, allows to expose unrestricted types as affine which gives
flexibility to library programmers and it is equipped with local type
inference.
\text{F}^{\,\circ}

[
9
]
is an extension of System F that
uses kinds to distinguish between linear and unrestricted types. Similarly to
Affe and Alms, it supports subkinding. Similarly to
FreeST
, but unlike Affe,

\text{F}^{\,\circ}
does not support quantification over kinds.
The work closest to
FreeST
in terms of context-free session types is

\text{FuSe}^{\{\}}

[
12
]
. Padovani proposed an alternative
formulation of context-free session types in which code and types are aligned
via extra annotations, something we decided to avoid in
FreeST
.
Linear Haskell
[
5
]
is a proposal to bring linear types to
Haskell. In Linear Haskell functions

and

describe how the arguments of the function are used. The latter form, inspired
by linear logic
[
6
]
, uses the argument

,
annotated arrows
{\color[rgb]{0,0.5,1}{{T}\mathrel{{{\color[rgb]{0,0.88,0}{\textbf{{*}}}}}\!\!\rightarrow}{U}}}
or
{\color[rgb]{0,0.5,1}{{T}\mathrel{{{\color[rgb]{0,0.88,0}{\textbf{{1}}}}}\!\!\rightarrow}{U}}}
describe how the function is
used (unbounded usage or exactly once).

FreeST
kinding system differentiates session from functional types. It also
classifies types according to their usage, linear or unrestricted. Other systems
consider these notions separately (or only one of them). The ideas behind our
inference algorithm are similar to Quill and Affe, but the details are quite
different since we do not use type qualifiers to reason about linearity.

3
Kind Inference

Our approach to kind inference follows the established two-step process, wherein
the first gathers constraints and the second resolves the constraints.
The constraint generation step produces constraints in two forms:

{\color[rgb]{0,0.88,0}{\kappa}}<:{\color[rgb]{0,0.88,0}{\kappa}}
and

{\color[rgb]{0,0.88,0}{\varphi}}=\bigsqcup_{\ell\in L}\mathtt{mult}({\color[rgb]{0,0.88,0}{\kappa_{\ell}}})
.
The first form represents subkinding constraints, while the second represents equalities between multiplicity variables and the least upper bound
of a given set of multiplicities. To enhance readability, we use shorthand
notation
{\color[rgb]{0,0.88,0}{\varphi}}=\mathtt{mult}({\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}}})
for

{\color[rgb]{0,0.88,0}{\varphi}}=\bigsqcup\mathtt{mult}({\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}}})
and use
\bigsqcup
in infix format
for binary sets.

Constraint Generation from Types

Kind and multiplicity constraints are captured by judgement

{\Delta_{\text{in}}}\vdash{{\color[rgb]{0,0.5,1}{T}}_{\text{in}}\colon{{\color[rgb]{0,0.88,0}{\kappa}}_{\text{out}}}}\;{\Rightarrow}\;{\mathcal{C}_{\text{out}}}
.
The judgement states that type
{\color[rgb]{0,0.5,1}{T}}
has kind
{\color[rgb]{0,0.88,0}{\kappa}}
under kinding context

\Delta
(a map from type variables to kinds), producing constraint set
\mathcal{C}
.
To clarify the distinction between input and output, we use the subscript

in
for parameters and
out
for results.

We explain a core subset of the constraint generation rules, those in

fig.

2
(the complete set is in

fig.

4

Rule CG-Var reads the kind for type variable
{\color[rgb]{0,0.5,1}{a}}
(recursive or
polymorphic) from the kinding context, generating no additional restrictions.
Rule CG-Rec governs recursive types which can either be session or
functional. The kind of the recursion variable is copied to the kinding context when
analysing type
{\color[rgb]{0,0.5,1}{T}}
. A constraint
{\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}^{\prime}}}<:{\color[rgb]{0,0.88,0}{\kappa}}
is
generated to ensure that the kind
{\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}^{\prime}}}

We now describe an algorithm to solve constraint sets.

1.

Initialise all kind variables
{\color[rgb]{0,0.88,0}{\chi}}
to the maximum of the kind
lattice,
1
t
. Likewise initialize all multiplicity variables
{\color[rgb]{0,0.88,0}{\varphi}}

to the maximum of multiplicities,
1

\sigma

2.

Iterate over each constraint in the set:

(a)

If the constraint is of the form
{\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\chi}}}}<:{\color[rgb]{0,0.88,0}{\kappa}}

update the entry for
{\color[rgb]{0,0.88,0}{\chi}}
in
\sigma
with the greatest lower bound of

{\color[rgb]{0,0.88,0}{\kappa}}
and
\sigma({\color[rgb]{0,0.88,0}{\chi}})
.
For example, if
\sigma=[{\color[rgb]{0,0.88,0}{\chi}}\mapsto{\color[rgb]{0,0.88,0}{\textbf{{1}}}}{\color[rgb]{0,0.88,0}{\textbf{{t}}}}]
and we are analysing

(b)

If the constraint is of the form

{\color[rgb]{0,0.88,0}{\kappa}}

(c)

If the constraint is of the form
{\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}_{1}}}<:{\color[rgb]{0,0.88,0}{{\color[rgb]{0,0.88,0}{\kappa}}_{2}}}

(d)

If the constraint is a multiplicity constraint

least upper bound of the multiplicities. If any

\sigma

If the thus obtained kind is more restrictive than that for

in
\sigma

Repeat the process in step 2 until there are no further updates to be made.

4.

If all constraints have been satisfied, then return the solution

Otherwise, the constraint set is unsatisfiable.

The algorithm iteratively updates the values of the kind and multiplicity
variables until no further updates can be made, that is, until a fixed point is
reached. Since the kind lattice is finite, any sequence of updates must
eventually converge to a fixed point. For the same reason, each constraint can
only be updated a finite number of times. Therefore, the algorithm terminates
after a finite number of iterations.

The running time of the constraint generation algorithm is linear on the size
of the input expression; that of the constraint satisfaction algorithm is
quadratic. In the worst case scenario the number of constraints is equal to the
size of the expression.
Each constraint can only update
\sigma
twice (when a more restrictive solution
is found). The worst case happens when a different constraint performs an update
in each iteration, forcing the algorithm to analyse all the constraints in each
iteration.
A sensible optimization removes the constraints from the constraint set also in
items 2(a) and 2(b), after concluding that they cannot update
\sigma
to a more
restrictive solution. Since the update can only be performed a constant number of
times, the algorithm becomes linear on the size of the input expression.

Future Work

There are several avenues for future work. The most immediate is to prove the
correctness of the algorithm with respect to the typing system.
Then, equipped with kind inference, we may think of introducing a third base
kind, that for session types that must be eventually closed (that reach type
). In this case we would require the kind of the argument to function
to be of the newly introduced kind.
We further plan to study the possibility of quantifying over kinds or
