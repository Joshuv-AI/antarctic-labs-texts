Lightweight Frequency-Based Tiering for CXL Memory Systems
Kevin Song, Jiacheng Yang, Sihang Liu, Gennady Pekhimenko

Abstract
Modern workloads are demanding increasingly larger memory capacity. Compute Express Link (CXL)-based memory tiering has emerged as a promising solution for addressing this trend by utilizing traditional DRAM alongside slow-tier CXL-memory devices in the same system. Unfortunately, most prior tiering systems are recency-based, which cannot accurately identify hot and cold pages, since a recently accessed page is not necessarily a hot page. On the other hand, more accurate frequency-based systems suffer from high memory and runtime overhead as a result of tracking large memories. In this paper, we propose FreqTier, a fast and accurate frequency-based tiering system for CXL memory. We observe that memory tiering systems can tolerate a small amount of tracking inaccuracy without compromising the overall application performance. Based on this observation, FreqTier probablistically tracks the access frequency of each page, enabling accurate identification of hot and cold pages while maintaining minimal memory overhead. Finally, FreqTier intelligently adjusts the intensity of tiering operations based on the application’s memory access behavior, thereby significantly reducing the amount of migration traffic and application interference. We evaluate FreqTier on two emulated CXL memory devices with different bandwidths. On the high bandwidth CXL device, FreqTier can outperform state-of-the-art tiering systems while using 4 × \times less local DRAM memory for in-memory caching workloads. On GAP graph analytics and XGBoost workloads with 1:32 local DRAM to CXL-memory ratio, FreqTier outperforms prior works by 1.04 − - 2.04 × \times (1.39 × \times on average). Even on the low bandwidth CXL device, FreqTier outperforms AutoNUMA by 1.14 × \times on average.

II
Background and Motivation

II-A

CXL-Enabled Memory Tiering Systems

CXL is an open industry standard interconnect running on top of the PCIe physical layer
[
59
,
43
,
58
,
48
]
. The key goal of CXL is to better support heterogeneous computing and memory capabilities in future data center architectures. Any device attached through the CXL interface will share a unified and cache-coherent memory space with the host processor and other CXL devices.
Since its introduction in 2019, the CXL ecosystem has been under rapid development. With support from major vendors across the data center stack, CXL is widely believed to make a significant impact in future data center architectures.

A CXL-enabled memory tiering system utilizes both regular local DRAM and CXL-attached memory technologies in the same system. Local DRAM offers better latency and bandwidth but has greater cost-per-GB, while CXL memory provides higher capacity and lower cost-per-GB but suffers from lower performance. The key goal of a tiered memory system is to combine the benefits of both local DRAM and CXL-memory while minimizing the amount of performance degradation due to occasional accesses to CXL-memory. To achieve this, memory tiering systems must accurately identify hot and cold data and place them into the local DRAM and CXL-memory, respectively.

II-B

Skewness in Large Memory Workloads

Large memory workloads often exhibit skewed memory access distribution, where the small set of addresses accounts for the majority of memory accesses.
For instance, Twitter and Meta both report that the popularity of in-memory caching workloads largely follows Zipfian distribution with a high degree of skewness
[
70
,
7
]
– a maximum alpha value of 2.5. For reference, a Zipfian distribution with alpha = 0.9 indicates the top 10% most popular items make up approximately 80% of all accesses.
TPP
[
40
]
reports that certain Meta web serving and advertisement workloads only use 20-40% of the total allocated memory within a two-minute interval, while the rest of the memory remains cold
[
40
]
.
For graph analytics workloads, Moura et. al
[
44
]
observe that for the betweenness centrality kernel in the GAP benchmark suite, the top two hottest objects consume nearly 40% of all accesses.

Skewed access distributions make memory tiering especially promising. Since the hottest data typically only constitute a small portion of the total application footprint, an effective tiering system should achieve near-optimal performance when its fast-tier memory capacity is large enough to fit the application’s hot pages. However, as the fast-tier memory capacity reduces, the margin for tiering inaccuracies is also reduced.
For example, when the local DRAM to CXL-memory capacity ratio drops from 1:8 to 1:32, TPP experiences up to 9.6
\%
drop in throughput on a CacheLib
[
7
]
workload.
Thus,
the ability to accurately identify hot and cold pages
is crucial for high-performance tiering systems.

II-C

State-of-the-art and Limitations

While skewness makes tiering promising in theory, designing a practical and performant tiering system is challenging.

II-C

Prior Recency-based Tiering Systems

Recency-based tiering uses data access recency to approximate data hotness. In general, such systems make data migration decisions based on data access information from a relatively short window of time, usually in the order of seconds. AutoNUMA
[
24
]
and TPP
[
40

are two state-of-the-art recency-based tiering systems

AutoNUMA is the tiering system used by the Linux kernel.
To sample memory accesses, AutoNUMA periodically scans the application address space and unmaps 256MB of pages (the scan window). The next access to an unmapped page will trigger a minor page fault, at which time AutoNUMA calculates the time elapsed since the page was unmapped (hint fault latency). If the hint fault latency is less than a hot threshold, this page is considered hot and promoted
[
23
]
.
TPP
[
40
]
uses the same hint fault mechanism to sample memory accesses. Different from AutoNUMA, TPP promotes a faulted page only if it is in the active LRU list.

The advantage of recency-based systems is that they can be lightweight. However, their classification accuracy suffers.
AutoNUMA can suffer from inaccurate tiering for two reasons.
(1) Missed frequency information:
As illustrated in the first timeline of Figure

(2) Page misclassification:
In the second and third timelines, a cold page can be mistakenly classified as a hot page and promoted if just one access falls within the hot window, while a hot page may not get promoted because none of its recent accesses happen to fall within the hot window

Similarly, TPP’s LRU-based promotion mechanism treats all pages within the active LRU list equally, even though they can have varying degrees of hotness.

When given 16GB of local DRAM and 512GB of CXL-memory, AutoNUMA, and TPP suffer from low hit ratios of 71% and 70% respectively. In Section

This lower hit ratio not only limits the effective use of local memory but also leads to interference with the application.

Prior Frequency-based Tiering Systems

In comparison to recency-based tiering, frequency-based tiering can achieve a higher local DRAM hit ratio when targeting skewed workloads.
Frequency-based tiering measures data hotness based on access information from a relatively longer window of time in the order of minutes to hours. State-of-the-art frequency-based tiering systems such as HeMem
[

adopt data structures such as a hash table to track page access frequencies.

While prior frequency-based systems do not suffer from low classification accuracy, their memory overhead is high. In Section

\%

III
FreqTier Key Ideas

In this section, we first summarize the challenges of designing an effective CXL tiering system and then describe how we tackle them.

Challenge 1
. Inaccurate data placement between DRAM and CXL memory can significantly degrade application performance. This is because CXL-memory has considerably longer access latency and lower bandwidth compared to local DRAM, as studied by prior works
[
40
,
33
,
60
]
. Thus, the first challenge is how a memory tiering system can accurately identify hot pages and place them in local memory to minimize the number of accesses to CXL-memory.

Solution
.
For better classification accuracy, we adopt frequency-based tiering at page granularity. FreqTier employs high-performance Processor Event-Based Sampling (PEBS) counters to efficiently collect local DRAM and CXL-memory access samples. FreqTier records separate frequency counts for each 4KB page, the smallest granularity supported by Linux memory migration interfaces. Based on the access frequency of each page, FreqTier determines the appropriate hot threshold based on the current access hotness distribution and performs promotion and demotion accordingly. Our approach effectively reduces the amount of page migration traffic by 4.2
\times
on average over prior works, as shown in Figure
2
.

Challenge 2
. The tiering system can induce significant memory and runtime overhead, especially for frequency-based tiering.
In modern large memory systems with TBs of memory, storing
the hotness of all pages for a long period of time can require a significant amount of memory.
Thus, tiering systems must minimize their memory overhead, otherwise, the cost saving of memory tiering systems is diminished.
To reduce the memory overhead, prior works rely on techniques such as tracking at the huge page granularity. However, such approaches sacrifice classification accuracy.
In addition, page migrations between local DRAM and CXL-memory consume memory and compute resources due to page copying and updating the OS page table entries
[
60
]
. If not managed carefully, this overhead can interfere with applications and diminish their performance.

Solution
. FreqTier exploits an observation that tiering systems can tolerate tracking inaccuracy.
Ultimately, the goal of the tiering system is to differentiate between hot and cold pages. Whether a page is extremely hot or moderately hot does not change the fact that this page will be promoted to local DRAM.
Thus, if the overall access frequency distribution of the application can be accurately captured, the access frequency of a page can often be reliably approximated.
Using this insight, FreqTier
tracks page access frequencies probabilistically
to significantly reduce the memory overhead.
To mitigate interference with the application, FreqTier adopts an adaptive method that adjusts the tiering intensity based on the application’s memory behavior.

IV-A

Workflow Overview

Figure

\bf\raisebox{-0.8pt} {\small1}⃝
FreqTier dynamically links the FreqTier shared library into the target application binary using

transparent

\bf\raisebox{-0.8pt} {\small2}⃝

\bf\raisebox{-0.8pt} {\small3}⃝

\bf\raisebox{-0.8pt} {\small4}⃝

Finally, FreqTier utilizes Linux kernel system call to promote hot pages to local DRAM and demote cold pages to CXL-memory.

IV-B

Probabilistic Frequency Tracking

Data structures such as a hash table are precise, ensuring that page access frequencies are stored exactly as initially recorded.
However, absolute accuracy is not always required in the context of memory tiering.
For instance, even if a page is inaccurately recorded as having an access count of one when in fact it has never been accessed, this page will likely still be classified as a cold page and no migration decisions will be affected by this particular inaccuracy. We differentiate between this tracking inaccuracy and the inaccuracies inherent in recency-based tiering systems. For frequency tracking, a small amount of inaccuracy does not substantially alter the overall frequency distribution among all memory pages. As a result, it has a negligible impact on tiering decisions, as we demonstrate in Section
VII-E1
. On the other hand, recency-based tiering is fundamentally incapable of capturing the access frequency distribution.

Based on the above observation, we propose to use the counting bloom filter (CBF)
[
18
]
, a probabilistic data structure, to track access frequencies of each page.
The CBF builds upon the bloom filter, where each element in the array is a counter value instead of a single bit.
Intuitively, CBF introduces a controllable level of tracking inaccuracy to achieve better memory efficiency.
To store the access frequencies of TBs of pages, one obvious data structure is the hash table, where the hash key is the page address and the value is the access count.
Unlike hash tables, CBF does not store the hash keys to significantly reduce its memory consumption.
The CBF purposely allows hash collisions to occur and controls the likelihood of collisions with the array size, where a larger CBF provides higher accuracy. We perform a detailed study on how different CBF sizes affect performance in Section
VII-E
and demonstrate that a moderately sized CBF can achieve high tracking accuracy. A detailed description of CBF is presented in Section
V-A
.

Dynamic tiering intensity.

Constantly collecting memory access samples with high sampling frequency enables FreqTier to make more accurate tiering decisions, but also incurs high runtime overhead. We observe that once the majority of hot pages are identified, further page migrations cease to improve application performance.

V-B
1
Demotion Algorithm

Once enough pages are demoted to reach
DEMOTE_WMARK
, FreqTier checkpoints the last scanned address and resumes from this address the next time demotion is triggered. This allows FreqTier to save its demotion scanning progress, as illustrated in Figure
7
. Once the demotion scan reaches the last address in the process address space, it returns to the first address and continues scanning.
To further reduce the demotion overhead, FreqTier queries
/proc/PID/pagemaps
in a batch of contiguous pages. Once enough cold pages are identified and collected, one
numa_move_pages()
call demotes all cold pages.
With the above optimizations, on CacheLib workloads with 16GB of local DRAM, FreqTier demotes roughly 160k pages every time demotion is triggered, a process that takes less than 3 seconds.

V-B
2
Dynamic tiering intensity

By default, FreqTier offers three levels of sampling frequencies by default: 100kHz, 10kHz, and 1kHz.
At initialization, FreqTier samples accesses at 100kHz. While pages are being migrated, FreqTier records the instantaneous local DRAM hit ratio every minute.
If the hot ratios stay largely the same (i.e., vary within 0.5% in our implementation), the hit ratio is deemed stable.

If the local DRAM hit ratio is deemed stable, FreqTier reduces the sampling frequency by one level. If the hit ratio becomes unstable, FreqTier increases the sampling frequency by one level. This allows FreqTier to continue sampling at a high rate if the hit ratio is only stable temporarily.

If the hit ratio is stable and the current sampling frequency is already at the lowest level, FreqTier enters low overhead monitoring mode.
In monitoring mode, FreqTier utilizes perf-stat
[
51
]
to continue tracking the local DRAM hit ratio. Compared to access sampling, perf-stat only counts the number of local DRAM and CXL-memory accesses, thus incurring negligible overhead. Within monitoring mode, if the local DRAM hit ratio becomes unstable, FreqTier considers the access distribution to have changed, returns to the promotion state, and restarts sampling with the highest sampling frequency.

In addition to a stable hit ratio, FreqTier enters monitoring mode if any of the two following conditions are true:

(1) Promotion plateau:

In addition to local DRAM hit ratio, since applications such as GAP workloads have naturally unstable local DRAM hit ratios, FreqTier also monitors the number of pages promoted for each one-minute window. If no pages are promoted in the past window, we refer to this as a promotion plateau. When promotion occurs at such slow rates, the small amount of tiering improvement does not justify the tiering overhead and FreqTier enters monitoring mode.

(2) Empty demotion scan:

As more cold pages are demoted, eventually no more cold pages remain in local DRAM. At this point, further page migrations are likely not beneficial, as local DRAM is already full of hot pages.
If FreqTier reaches the end of the address space, it restarts the demotion scan from the top of the process address space to demote any newly allocated cold pages, as illustrated in Figure
7
. If no more cold pages are found, FreqTier enters monitoring mode.

V-C

FreqTier Optimizations

In this section, we describe three optimizations to FreqTier: (a) dynamic hot threshold, (b) blocked CBF, and (c) CBF increment coalescing.

Dynamic Hot Threshold.

The hot threshold determines the minimum number of accesses a page should possess to be considered hot. FreqTier dynamically adjusts the hot threshold to maximize the tiering quality. To utilize local DRAM most efficiently, the hot threshold should be set such that the total size of hot pages is roughly equal to the size of local DRAM.
If the number of hot pages (based on the current hot threshold) is larger than the local DRAM capacity, FreqTier increases the hot threshold to only keep the hottest data. Similarly, if the hot pages cannot fill the entire local DRAM, FreqTier decreases the hot threshold.
By default, the initial hot threshold is 5, which we observe to work well experimentally.

Blocked Counting Bloom Filter.

In the traditional CBF described in Section
V-A
, since the counter array can be larger than the L3 cache, each access to the CBF can require up to three cache line accesses and worst case three DRAM accesses. Block CBF is a variation that bounds the max number of cache lines and/or DRAM accesses to one. With Blocked CBF, all counters of the same page belong to the same 64-byte block, the size of one cache line. We follow the implementation of Caffeine
[
35
]
to use portions of one hash function to first select a 64-byte block. The rest of the hash functions select which three counters within this block to use. We observe negligible counting accuracy loss when switching to blocked CBF.

Counting Bloom Filter Increment Coalescing.

Since the memory access distribution is often skewed, accesses to the bloom filter are often focused on a few hot pages. Thus, repeating increment_frequency() calls to the same page can be coalesced to a single increase_frequency(page_address, amount) call, which increases the frequency of page_address by amount. While collecting access samples, FreqTier tracks the number of samples collected for each page address using a hash table. After a batch of samples is collected, we invoke increase_frequency instead of increment_frequency for each unique page address in the hash table. We observe 4
\times
fewer CBF accesses with this optimization.

VII-D

Adapting to Changing Access Distribution

Access distribution may change over time.
For example, Meta reports that its CacheLib workloads experience a high degree of churn
[
7
]
, i.e., the change in key popularity.
The tiering system must keep the recorded frequencies fresh in order to effectively identify and promote new hot data.

To evaluate how effectively FreqTier can detect and adapt to changes in memory access distribution, we modify the CacheLib benchmark framework to change the item access distribution.
In this experiment, we use the popularity and size distribution from the original CDN workload provided by Meta.
First, all items are inserted into the cache. During the first phase, we redirect all generated accesses to the first half of items. From 430 seconds onward, we redirect all accesses to the second half of items.
This represents a worst-case distribution change, where all data accessed during the first phase become cold in the second phase.

Figure
11
shows how well FreqTier and the fastest baseline AutoNUMA adjust to the changing distribution under the 1:32 configuration.
After the distribution changes, FreqTier’s low overhead monitoring mechanism detects this change in distribution within 30 seconds and increases the hardware counter sample frequency.
From 500 to 1100 seconds, FreqTier identifies the new set of hot pages while demoting cold pages out of the local DRAM.
FreqTier experiences slightly higher P50 latency than AutoNUMA from 500 to 900 seconds largely due to the overhead associated with counter sampling. That being said, after the temporary slowdown, FreqTier continues to outperform AutoNUMA.
We conclude that FreqTier can effectively detect and adjust to changing access distributions.

Number of bits per frequency counter:

In the CBF, the number of bits allocated for each counter determines the maximum frequency count any page can have. For example, if 4 bits are allocated for each counter, then all pages with a frequency count
\geq
15 are treated equally. To determine the appropriate max frequency count, we characterize the access frequency distribution of the target workloads. Figure
14
shows the cumulative distributions of pages in the CBF. For each workload, one frequency distribution is recorded for every 100k samples. The distribution with the highest number of pages having frequency
=
15 is selected.

We observe that the amount of pages with frequency
\geq
15 is less than 2
\%
among our workloads. Since the ratio between local DRAM and CXL-memory is usually much larger than 2%, additional frequency counter bits is unnecessary – pages with access count
\geq
15 can be safely be classified as hot and placed in the local DRAM.
Thus, FreqTier allocates 4 bits for each frequency counter by default.
Similar to other parameters, the number of bits can also be scaled if needed.

VIII
Discussions

Non-skewed Applications

FreqTier and frequency-based tiering systems in general are intended for applications with skewed memory access distributions. Extensive studies in the literature have shown that this is true for a significant portion of modern large memory workloads
[
7
,
6
,
70
]
.
Applications that do not exhibit this property will see little performance benefits from FreqTier.

CXL Memory Pooling

This work emulates CXL 1.1 due to the lack of commercial CXL devices on the market.
Newer generations of CXL standards, namely CXL 2.0 and 3.0, extend CXL’s tiering capability to memory pooling across multi-host systems. This work focuses on single-machine memory expansion, which we view as orthogonal to multi-host tiering.
Fundamentally, FreqTier aims to address the problem of identifying hot/cold data, which is also applicable to multi-host tiering. We leave such extensions to future works.

Userspace vs. Kernel Tiering

We implement FreqTier in the userspace due to its flexibility.
This advantage is recognized by both prior memory tiering systems
[
54
,
57
]
and software systems such as userspace networking systems
[
36
,
13
]
and file systems
[
4
]
.
Kernel-based memory tiering has its advantages, such as avoiding context-switch overheads and allowing for the management of multiple applications.
However, the ideas behind FreqTier are not limited to userspace and can be implemented in the kernel.

FreqTier is built based on the key observation that memory tiering can tolerate a small amount of tracking inaccuracy. In addition to locally-attached CXL memory managed by FreqTier, the target server can further expand its memory capacity through disaggregated tiering systems.

X
Conclusion

We propose FreqTier, an application-transparent fine-grained frequency-based tiering system. FreqTier achieves both high classification accuracy and low overhead by adopting novel probabilistic access frequency tracking and flexible migration policy. On in-memory caching workloads, FreqTier outperforms prior works while using 4× less local DRAM memory. while requiring less than 100MB of memory overhead. On graph analytic and gradient boosting workloads, FreqTier outperforms prior works by 1.39
\times
on average under 1:32 local DRAM to CXL-memory ratio. FreqTier’s performance gains generalize to a CXL device with lower bandwidth, outperforming AutoNUMA by an average of 1.14
\times
.
