What’s in a Package? Getting Visibility Into Package Security-Sensitive Resource Access
Imranur Rahman, ∗† Ranindya Paramitha, ∗† Henrik Plate, ‡ Dominik Wermke, ∗ Laurie Williams, ∗

Abstract
. The Log4Shell vulnerability occurred because the JNDI (Java Naming and Directory Interface) lookup feature was used, even though it was not needed for log4j’s core functionality. This case illustrates why developers may want visibility into the sensitive capabilities available through a dependency. The presence of a call alone does not establish that the call is unnecessary or risky. Security-sensitive APIs provide access to security-sensitive resources, such as filesystem, network, or process-related resources. If developers know which types of sensitive resources a dependency can access, they can control their dependencies at a finer grain, and they can consider an alternative dependency when a dependency makes unnecessary or suspicious security-sensitive API calls. However, prior work has not provided a documented, repeatable procedure for deriving an ecosystem-specific security-sensitive API list, so developers lack systematic visibility into the sensitive capabilities of their dependencies. The goal of this study is to aid developers in understanding sensitive resources accessible to their dependencies by identifying security-sensitive APIs in packages through an empirical study of Java packages. In this study, we present a novel and repeatable methodology to construct a security-sensitive API list for an ecosystem, and we apply it to Java. We then compare the security-sensitive API calls of functionally similar Java packages. The number of security-sensitive API calls (call level) ranges from 0 to 368 in one capability and from 0 to 429 in total among packages with similar functionality. These packages also differ in capability breadth , the number of the 15 capabilities that a package reaches. For example, capability breadth ranges from 0 to 10 in the “Dependency Injection” category and from 0 to 13 in the “Web Frameworks” category. A higher number of security-sensitive API calls does not by itself mean a higher security risk; the calls show which sensitive resources a dependency can reach. In a survey of 110 developers (response rate 1.4%), 44.6% of the respondents said that they would consider security-sensitive API information when they select a dependency. Based on our findings, we recommend adding security-sensitive API information to dependency management tools (e.g., npm cli, OpenSSF Scorecard), so that developers can better control their projects.

The Log4Shell (CVE-2021-44228) vulnerability impacted most networked organization at the time of its disclosure
(
1
)
.
The vulnerable versions of log4j included a JNDI (Java Naming and Directory Interface) lookup feature that allowed the remote loading of an object from an attacker-controlled website.
This JNDI lookup was added to log4j as a feature request in 2013
(
2
)
.
Most developers were unaware that log4j included a JNDI lookup feature that was enabled by default.
One mitigation for the Log4Shell vulnerability was to disable the feature by default
(
3
)
.
This mitigation approach indicates that the JNDI lookup feature was not core log4j functionality and could be avoided if developers who had log4j as a dependency in their projects were aware that such a feature existed and was enabled by default.

The JNDI lookup can be categorized as a security-sensitive API, an API for accessing network resources.
Security-sensitive APIs provide access to security-sensitive resources, such as filesystem, network, or process-related resources
(
4
)
.
Developers would benefit from knowing which sensitive resources their dependencies can access during dependency selection.
By understanding the sensitive resources accessible to a dependency, developers can apply fine-grained permissions for each dependency to manage the software’s attack surface
(
5
)
.
However, developers cannot manually review their projects’ dependencies line by line due to limited time and the high number of dependencies present typically in a project (e.g., the mean dependency count for a Python project is 44
(
6
)
).

Prior work found that when selecting among alternative third
-
party packages, developers consider a range of criteria beyond basic functionality, including security, performance, documentation quality, and maintainability
(
7
)
.
Having a systematic method to quantify security-sensitive API calls made by a dependency, developers can make informed dependency selection for their expected functionality.
As shown in Table
1
(a preview of our analysis result), a developer choosing a “dependency injection” package may notice that
dagger
calls no sensitive API, whereas
spring-context
calls 53 different security-sensitive APIs and reaches 10 of the 15 capabilities, although they provide similar functionality.
Our intent is not to claim that every security-sensitive API call is dangerous or that a higher number of calls means a higher security risk.
The calls show which sensitive resources a dependency can reach, and developers can compare this information with the functionality that they expect from the dependency.

However, to get this information, a tool first needs a list of the security-sensitive APIs of the ecosystem.
The current state of the art
(
8
)
relies on expert selection to identify security-sensitive APIs within an ecosystem, and others cannot repeat this selection.
We lack a repeatable methodology for identifying security-sensitive APIs in an ecosystem, so no tool gives developers security-sensitive API information, and developers cannot use it to evaluate packages when they select a dependency.

The goal of this study is to aid developers in understanding sensitive resources accessible to their dependencies by identifying security-sensitive APIs in packages through an empirical study of Java packages.

We conducted a mixed-method empirical study on the Java ecosystem to answer the following four research questions to reach our goal:

RQ1:

2.
Terminology

In this section, we formally define a security-sensitive API, a call graph (with and without dependencies), the levels of granularity at which we report security-sensitive API calls, and the Quasi Golden Standard (QGS), which are used throughout the study.

Definition 0 (
Security-Sensitive API
).

We define a security-sensitive API as an API that can be used to access security-sensitive resources: the filesystem, network, or system processes.

java.io.File.createTempFile()
,
java.net.Socket.connect()
,
javax.script.ScriptEngine.eval()
, and
java.lang.Runtime.load()
are examples of security-sensitive APIs.

We adopted the categorization by Ferreira et al.
(
11
)
:
Filesystem
,
Network
, and
Process
as sensitive resource types.

Filesystem
::

related to interacting with the local filesystem, including opening, reading, modifying, creating, and writing from/ to files.
It also includes the APIs for setting, removing, and updating file permissions.

Network
::

interact with network resources, including HTTP servlet/client, URL connection, socket, and naming directory services, which are required for communicating with remote servers.

Process
::

expose operating-system process and subprocess-handling routines, including program loading and script execution.

Definition 0 (
Intra-Package and Inter-Package Call Graph
).

An intra-package call graph is created by analyzing the code of a single package and represents the
<caller, callee>
relationships between methods of types defined in the package.

An inter-package call graph is created by stitching (using type hierarchy) the intra-package call graphs of a given package and its dependencies, meaning that callee types specified in the intra-package call graphs are resolved to all possible implementation types.
As a result, an inter-package call graph represents all
<caller, callee>
relationships between methods in a package and its dependencies that can be connected to a given package.

For example,
log4j-core
’s method
ConfigurationSource.fromUri()
calls the static method
FileUtils.fileFromUri()
and instantiates
java.io.FileInputStream
, which is represented by corresponding call graph edges in the intra- and inter-package call graphs of
log4j-core
.

Definition 0 (
Levels of Granularity
).

We report the security-sensitive API calls of a package at four levels of granularity, from coarse to fine: the resource level, the capability level, the API level, and the call level (Table
2
).

Definition 0 (
Quasi Gold Standard (QGS)
).

A Quasi Gold Standard (QGS) is a list of security-sensitive APIs in an ecosystem from known venues and journals for a given time frame.

To evaluate the coverage of our security-sensitive API list, we adopted (with some modifications) Quasi Gold Standard (QGS), which is a commonly used approach in evaluating the completeness of a systematic literature review as suggested by Zhang et al.
(
12
,
13
)
, Tran et al.
(
14
)
, and Kitchenham and Brereton
(
15
)
.
According to Zhang et al.
(
13
)
, a QGS is a list of work from known venues and journals for a given time frame.
Zhang et al. evaluate a search string by how much of the QGS it retrieves.
We use the QGS in the same way, to measure coverage only.
This approach allows us to evaluate our search string and, if necessary, refine it until we achieve adequate coverage.
In our study, instead of a set of papers, the QGS contains security-sensitive APIs from the studied ecosystem, extracted from known articles within a given time frame, to evaluate our identification process.

Research Methodology: Package Selection

In this section, we present the methodology for selecting the core packages and their corresponding package categories for our empirical analysis.
Developers often have multiple functionally similar packages to choose from when building their project.
Our goal in this research is to show developers the security-sensitive API calls made by the functionally similar packages.
So we need more than one functionally similar packages grouped together to understand the similarities and differences in security-sensitive API usage.
Our package selection process consists of five steps, as shown in Figure
1
.

1. Select Popular Maven Package Categories.:

MvnRepository
(
16

provides a list of widely used open-source package categories, each representing functionally similar packages.
Examples of package categories are HTTP Clients, JSON Libraries, and Logging Frameworks.
We select the top 25 most-used package categories from MvnRepository to reflect what developers use in practice.
To determine the main functionality of each package category, we review the descriptions of the top 15 packages in each category (
15\times 25=375
total packages) and how to use these packages as dependencies from GitHub.

2. Package Category Inclusion.:

We then apply the following
inclusion criteria
on the Maven package categories: we only use package categories with packages that

(1):

are used at runtime
that excludes anything related to building, testing, or mocking. We excluded test or build-time dependencies, which are not present in production, and included only runtime dependencies, since our goal is to assess vulnerability risks via sensitive API usage.

(2):

provide alternative functionality for a given task.
We wanted to compare similar-functioning packages with their respective sensitive API usage. If there is only one package that provides a unique functionality, we cannot compare it with any other package by design. For example, the category “Java Specifications” does not meet this criterion because its task range is too broad.

(3):

are used in “typical” server-side Java Web applications

With this criterion, we retain the functionalities needed in Java web backends (e.g., frameworks, parsers, database clients) and exclude unrelated areas (e.g., mobile, IoT), thereby keeping our analysis focused and relevant.

4.
RQ
1
: How Can Security-sensitive APIs Be Identified In An Ecosystem?

In this section, we answer
RQ
1
.
First, in Section
4.1
, we present the methodology on how to construct the security-sensitive API list and security-sensitive API list evaluation.
Then, in Section
4.2
, we present the implementation of the method to construct the security-sensitive API list in Java as a case study and the evaluation result for the Java security-sensitive API list.

4.1.
Security-Sensitive API List Construction Process For An Ecosystem

In this section, we first present the CVE and CWE collection and mapping in Section
4.1.1
, then the three-pronged approach to the security-sensitive API list construction process in Section
4.1.2
, and finally the methods to evaluate the constructed security-sensitive API list in Section
4.1.3
.

4.1.1.
CVE and CWE Collection and Mapping

We conduct a
CVE-to-CWE-to-OWASP Top 10 Mapping
to support the identification of security-sensitive API entries from CWE examples.
For a given set of packages and their dependencies, CVEs are retrieved from the NVD and, where available, verified against their associated vulnerable functions by a domain expert or automated tooling.
The unique CWEs surfacing from these CVEs are then mapped to the OWASP Top 10
(
18
)
.
When a CWE has no direct mapping, its parent CWE is checked for a mapping and used accordingly; if no mapping exists at any level, the entry is classified as “Others.”
The input of this step is a set of selected packages of an ecosystem (in our case, the 1210 unique packages in Outcome (c) from Figure
1
).
The output of this step is the CVEs for these selected packages mapped to CWEs.

4.1.2.
Security-Sensitive API List Construction Process

We define a three-pronged approach to construct a security-sensitive API list for an ecosystem, as illustrated in Figure
3
:

1. Ecosystem’s API Documentation.:

The Ecosystem API documentation provides a comprehensive list of APIs available to users without requiring additional dependencies. We argue that the ecosystem API documentation should be the main source to construct security-sensitive API list for an ecosystem. Additional inclusion criteria in this step are APIs that interact with system resources, e.g., the filesystem, network, or processes. This inclusion criterion ensures that the API list only contains APIs that access security-sensitive resources.
Inter-rater agreement should be achieved at this step, and manual validation is required after the initial list is created.
The input for this step is the API documentation for the ecosystem, and the output is a list of security-sensitive APIs for that ecosystem.

2. CVE Fixes.:

CVE fixes contain the added, removed, or modified code to address the vulnerability. We argue that if a certain ecosystem API is added, removed, or modified in the CVE fix, the API must be security-sensitive.
The input to this step is the fixes for the CVEs from Section
4.1.1
, and the output is the APIs added, removed, or modified in the CVE fixes.
We include such APIs in our security-sensitive API list.

3. CWE Examples.:

The MITRE CWE
(
19
)
definitions provide code snippets as “Demonstrative Examples” for most CWEs in various languages.
CWE examples can complement the above two steps when no vulnerability exists in a given API, but the API can still be used to exploit a vulnerability.
The input of this step is the mapped CWEs from Section
4.1.1
, and the output is a list of security-sensitive API.

After these three steps, an expert rule-based selection is conducted with multiple individuals to manually validate the constructed security-sensitive API list.
In this step, experts categorize the APIs into resource types and capability types for the ecosystem.
Categorization is done using card-sorting techniques (open, closed, or hybrid).
Card sorting is a qualitative technique to classify text into themes
(
20
)
and is commonly used in research to create informative categories
(
21
,
22
)
.
Ecosystem-specific or language-specific inclusion-exclusion criteria are applied in this step if necessary (e.g., excluding packages written in Kotlin or Scala when creating security-sensitive API list for Java, although these three are JVM-based languages).
Disagreements between raters are resolved by the negotiated agreement technique
(
17
)
.
The final outcome is a list of security-sensitive APIs for an ecosystem with a categorization.

4.1.3.
Security-sensitive API List Evaluation

To evaluate the quality of the process to identify our security-sensitive API list, we performed two approaches: (1) developed a Quasi-Gold Standard and measured how much of it our list covers (sensitivity);
and (2) measured the prevalence of the APIs in our list in real-world vulnerable functions.

Methodology to Create Quasi Gold Standard (QGS) for evaluating security-sensitive API list construction process

To develop the QGS for our security-sensitive API list to evaluate on, we adapted the QGS construction from Tran et al.
(
14
)
.
An illustration of our QGS creation is depicted in Figure
2
.
The steps are the following:

1. Perform Literature Search on Databases.:

We performed a literature search on ACM Digital Library
(
23
)
with the following search strings.

Search String #1:

[["security" AND "sensitive api*"] OR "security api*"] AND [java]

Search String #2:

[["capability model" OR "capability analysis" OR "capability inference"] AND [api] AND [java]]

We then merged the results from both search strings and removed duplicate entries.
We also used the IEEE Xplore Digital Library and Scopus.

Result:
Search string #1 returned 207 papers and search string #2 returned 91 papers. After merging and removing duplicate entries, we have a list of 291 papers.

2. Inclusion Exclusion Criteria (Publication Filtering).:

We limit the result to publication type
article
and
inproceedings
only, as
proceedings
usually only contains a table of contents and a list of
inproceedings
. We also limit the results to work from the last four years (2022-2025) to maintain recency and make sure of the relevance of the APIs.

Result:
After filtering by publication type and year, we are left with 52 papers.

3. Additional Filtering (Gathering the API List).:

We manually reviewed the published works to see whether they define a list of “security-sensitive API” in Java (different papers may use a different name for the list). For the works that have a defined API list, we went to their paper/artifact and collected the list until we had a list of lists.

Result:
Among the 52 papers, only 14 papers have a defined sensitive Java API list. The 14 API lists contain, on average, 317 APIs (std dev: 948), ranging from 2 to 3,585 APIs (median: 13). The total number of unique APIs across all lists is 3,866.

4. Additional Filtering (API List Filter based on Occurrence).:

For each API in the lists, we counted its occurrences across the lists; i.e., if an API occurs in 5 lists (5 papers defined it as sensitive), we assigned it an occurrence count of 5. We included only APIs that appear in more than 3 papers (i.e., more than 3 papers agreed that this API is sensitive). This filter is also used to limit the number of APIs in our QGS to no more than 100.

Result:
From the unique API list, only 16 APIs are considered sensitive in more than 3 papers.

5. Additional Filtering (API List Filter based on Relevance and Type).:

We manually went through each of the 16 APIs’ descriptions, and we only kept the APIs that (1) are included in our resource types (Section
2
: filesystem, network, and process); and (2) are not abstract methods.

Evaluation Metrics for Our Security-sensitive API List With Respect To QGS.

We use this QGS to evaluate the coverage of our security-sensitive API list.

1

(
13

2

(1)

\text{Sensitivity}=\frac{\text{The number of APIs in the API list that are also in the QGS}}{\text{Total APIs in the QGS}}\times 100\%

(2)

\text{Overlap ratio}=\frac{\text{The number of APIs in the API list that are also in the QGS}}{\text{Total APIs in the API list}}\times 100\%

The overlap ratio measures only how much of our list the QGS accounts for.
The QGS is small and non-exhaustive by design, so most APIs in our list cannot appear in it, and the overlap ratio does not bound the false positives of our list.
We therefore use the QGS to support a coverage claim only.
We do not quantify the precision of our list: a sound estimate needs a reference list of Java security-sensitive APIs that is independent of ours and complete enough to serve as ground truth, and no such list exists.

4.2.2.
Security-sensitive API List Construction

We apply the methodology present in Section
4.1.2
to construct the security-sensitive API list for Java using a three-pronged approach.
For categorizing the security-sensitive API list, we adopt the categorization by Ferreira et al.
(
11
)
:
Filesystem
,
Network
, and
Process
.

Filesystem
::

related to interacting with the filesystem, including opening, reading, modifying, creating, and writing from/ to files.
It also includes the APIs for file permissions.

Network
::

interact with network resources, including HTTP servlet/client, URL connection, socket, and naming directory services.

Process
::

manage encoding/ encryption, program loading, and script execution.

To construct a security-sensitive API list in Java, we use a three-pronged approach, as illustrated in Figure
3
:

1. Ecosystem’s API documentation (JDK).:

One author went through all the API documentation (Java 11 JDK) and selected a preliminary sensitive API list using two rules: either (1) the API accesses sensitive resources based on the defined resource types: file system, network, and process, or (2) the API can perform the operation that a weakness in a fixed list of CWEs exploits, i.e., CWE-22 (Path Traversal), CWE-78 (OS Command Injection), CWE-94 (Code Injection, which can lead to remote code execution). An API meets rule (2) when its Javadoc describes this operation, for example, an API that opens a file at a given path for CWE-22. This preliminary list contains 127 security-sensitive APIs. Two other authors manually validated this list.
The input for this step is the JDK Javadoc, and the output is a list of 127 Java security-sensitive APIs.

2. CVE fixes.:

One author analyzed the 255 CVE fixes associated with our 45 core packages (from Endor Labs) using VFCFinder
(
24
)
to identify APIs associated with system or information compromise if the vulnerability were exploited.
For APIs affected by the vulnerability fixes, we check whether the API call is added, removed, or modified in the fix.
This process resulted in 76 security-sensitive APIs, of which 66 are new (not on the preliminary list).
The input to this step is the CVE fixes from Section
4.2.1
, and the output is the 76 APIs that were added, removed, or modified in those fixes.
We analyze the CWEs associated with these CVEs in the next section.

3. CWE examples.:

One author reviewed the MITRE CWE
(
19
)
for each of the 71 unique CWEs identified in the 255 CVEs to find common exploitation examples in Java.
If no example was found in MITRE CWE, we used two LLM-based tools to propose examples: Gemini integrated with Google search, with the query “What is the example of CWE-XXX in Java?”, and ChatGPT (GPT 4.0), with the prompt “Give me an example of CWE-XXX in JAVA.”.
The tools only proposed candidate APIs through generated examples: we kept only the APIs that both tools returned, and we checked every candidate manually against the JDK documentation for hallucinations before it entered the list, so the tools could not add an API that does not exist.
This step applied to 12 of the 71 CWEs and contributed 26 APIs.
To measure the stability of this step, we repeated the prompts five times for each of the 12 CWEs with both tools: both tools returned all 26 APIs in every run, and the raw outputs contained no API that does not exist in the JDK.
In this way, we compile a list of APIs present in the CWE examples. From this process, we got 42 security-sensitive APIs of which 26 are new (not in the list of other 2 steps).
The input of this step is the mapped CWEs from Section

In this section, we present our methodology for constructing the call graphs on our selected packages and for the empirical analysis.

We opted to use the specific call graph generated by Endor Labs Call Graph Tool because it can accumulate the reachable APIs of dependencies.
However, this can also be done using other open-source Java call graph generation tools.
The Endor Labs tool is proprietary.
So that others can recompute RQ2 and RQ3 without it, our replication package contains the security-sensitive API call-graph edges and the security-sensitive API call tables for each package version.
The tool generated both intra-pkg call graphs and stitched them together to form inter-pkg call graphs.
To generate the inter-pkg call graph for a package, the tool examines all call sites in the package and connects them to potential callees in packages in its dependency graph.
The call graph construction process includes building a type hierarchy for all types across all packages in the dependency graph, which is important for resolving dynamically dispatched calls.
In addition, the call graph construction process allows, e.g., to stitch an interface call across all implementations of this interface, regardless of which package in the dependency graph contains them.
Using this call graph generation tool, we generated a call graph for each package version (intra-pkg call graph) of our set of 30,772 package versions.
The tool uses Class Hierarchy Analysis (CHA)
(
35
)
: at a virtual call site, it adds an edge to every matching method implementation in the package’s dependency graph.
Section
5.2
describes how we validated these call graphs with a second, open-source call graph generator.

After receiving the call graphs in JSON format, we traversed them using a pre-order breadth-first search (BFS) to determine whether any of our security-sensitive APIs were called in the package version.
Our pre-order breadth-first-traversal is similar to Mir et al.
(
36
)

Reachability analysis

(

After this

5.2.
Call Graph Validation

A static call graph can be wrong in two directions.
The call graph
over-approximates
when it contains an edge that no execution of the program takes.
The call graph
under-approximates
when it misses an edge that an execution can take.
For our counts, an over-approximation can add a security-sensitive API that a package does not call, and an under-approximation can hide a security-sensitive API that a package calls.
Our call graphs can contain both kinds of error.
CHA over-approximates at virtual call sites: CHA connects a virtual call to every matching implementation, also to implementations that the program never creates.
A static call graph under-approximates the calls through reflection: a package can reach a security-sensitive API only as the
target
of a reflective call (e.g.,
Method.invoke()
on a method name read from a configuration file), and a static call graph has no edge for such a call.
In addition, our call graphs come from a proprietary tool, so the counts can depend on how this one tool works.
We therefore validated the call graphs with a second, open-source call graph generator, OPAL
(
38
)
, to answer two questions:
(1) how much does CHA over-approximate the security-sensitive API calls, and
(2) do the results depend on the call graph generator?

Configurations.

The second is Rapid Type Analysis (RTA)

RTA therefore keeps a subset of the CHA edges, and it is more precise than CHA.
RTA is still a static over-approximation, so the CHA edges that RTA removes are a lower bound on the over-approximation of CHA, not its full size.
Both configurations used the same inputs: the package JAR, the resolved runtime dependency JARs, and the same JDK (OpenJDK 21).
Both used the library setting of Reif et al.
(
40
)

In the inter-package scope, the analyzed JARs include the dependency JARs.
Both also ran the same analyses that find the entry points and the instantiated types in library code, so the two configurations differ only in how they resolve virtual calls.
OPAL did not analyze the JDK implementation.
OPAL records a call from a package to a JDK method, but OPAL does not follow the calls inside the JDK, and OPAL does not resolve a call on a JDK interface (e.g.,
ScriptEngine.eval()
) to an implementation.

For example, if 10 packages each call
File.delete()
, this API gives 10 pairs.
The security-sensitive API counts that RQ2 and RQ3 report come from the call graphs of the Endor Labs tool.

Comparison 1: over-approximation (OPAL CHA vs. OPAL RTA).

The tool and the inputs are the same, so every difference comes from the algorithm.
For each scope and each capability, we report the share of the CHA package–API pairs that RTA keeps, with a 95% bootstrap confidence interval that resamples packages.

Comparison 2: tool agreement (Endor Labs tool vs. OPAL CHA).

We compared the two tools in the intra-package scope only, where both tools analyze the same code.
We did not compare the inter-package scope, because the two tools define it differently: the inter-package call graph of the Endor Labs tool contains only the dependency code that the package’s own code can reach, while OPAL treats every public method of the dependencies as an entry point.
We report three statistics:

•

Spearman’s
\rho
of the numbers of unique security-sensitive APIs per package. The coefficient shows whether the two tools rank the packages in the same order (
\rho=1
: the same order).

•

Cohen’s
\kappa
for the presence of each capability in each package (
34\times 15
decisions). The coefficient shows whether the tools agree on which capabilities a package reaches, corrected for agreement by chance (
\kappa=1
: full agreement).

•

The median
Jaccard index
of the API sets. For one package, the Jaccard index is the number of security-sensitive APIs that both tools report, divided by the number of security-sensitive APIs that at least one tool reports (
1
: the same set).

To explain the differences between the tools, we separate two kinds of edges to a security-sensitive API.
A
direct edge
goes to the method that the call instruction in the bytecode names.
A
virtual edge
goes to a different method, which the call graph generator selects when it resolves a virtual call on a supertype to a method of a subtype.
We gave every package–API pair that only one tool reports one of three labels (the short names are the column names of Table
11
):

•

OPAL over-approx.
(over-approximation by OPAL CHA): only OPAL reports the API, and all its edges to the API are virtual edges. For example, the package calls
OutputStream.write()
, and OPAL resolves this call to
FileOutputStream.write()
, although the stream may not be a file.

•

Endor under-approx.
(under-approximation by the Endor Labs tool): only OPAL reports the API, and at least one OPAL edge to the API is not a virtual edge. The call is a direct call, or a call on the package’s own subclass that inherits the JDK method (e.g., a class loader of the package that calls the inherited
ClassLoader.defineClass()
).

•

OPAL under-approx.
(under-approximation by OPAL): only the Endor Labs tool reports the API, and the package’s bytecode contains a call instruction to the API.

To assign these labels, we inspected the bytecode of each package with
javap
.
For each pair, we checked whether the bytecode contains a call instruction to the API, and whether the instruction names the API itself or a method of a supertype.
The labels classify the differences between the outputs of the two tools.
The labels do not show that a call executes at runtime.

Effect on the findings.

Finally, we recomputed the RQ2 and RQ3 findings at the API level under each call graph: the capability with the most package–API pairs, the packages with no security-sensitive API, and, for each package category, the ranking of packages and the packages with the most and the fewest security-sensitive APIs.

We then qualitatively compare functionally similar packages (Table

For this analysis, we consider only the security-sensitive API calls from the inter-package CG of the latest version of the packages.
One author reviewed the source code, documentation, design patterns, dependency usage, implementation choices, usage examples, and overall API usage of each of the 34 packages in the seven categories (Section

The full analysis is present in the supplementary material.
Our observation of qualitative analysis on the individual packages in each category can be summarized into four patterns:

1. Same Functionality, Different Implementation.:

The expected functionality of a package is fixed (eg, HTTP spec
(
53
)
).
But
dagger

2. Different Features.:

At a high level, all web framework packages are supposed to provide the functionality of building web applications.
However, each web framework has a slightly different feature set, making it unique.
Similarly, JSON library
fastjson2
provides additional features than the
gson
and
jackson-core
.
Having additional features is reflected in the differences in security-sensitive API usage.

3. Modularity And Reuse.:

HTTP client packages have a low usage of
network
APIs.
The implementations are very modular.
For example, rather than having three
network
calls for GET, POST, and PUT,
httpclient5
uses one
java.lang.Socket.connect()
method in
ProxyClient.java
and reuse the
ProxyClient
class to implement other methods.

4. Using A Similar Package As Dependency.:

Even with another HTTP client package
okhttp
as a dependency,
retrofit
uses fewer security-sensitive API calls than
okhttp
.

Retrofit
is a high-level REST abstraction built on top of
okhttp
.
In this setting,
okhttp
provides low-level HTTP functionality, whereas
retrofit
provides
additional features
, e.g., URL manipulation.
A similar pattern can be found in web frameworks as well:

spring-webflow
and
spring-webmvc
both use
spring-web
for different use cases from the high-level.

Comparison Across Package Categories.

This comparison covers the latest versions of the 34 packages in the seven categories of alternatives (the counts in the heatmaps); the comparison excludes the JDBC Driver category.

Process/reflection
is the most used capability, both by the number of calls (3,044, call level) and by the number of packages that call it (28 of 34), and every package category calls it.

Process/dependency
is the least used capability: none of the 34 packages calls it.
With the JDBC Driver packages included (39 packages), the result is the same:
process/reflection
is the most used (3,494 calls, 33 packages), and

is the least used (6 calls), called only by four of the five JDBC drivers.

Finding #3:
Packages have varying security-sensitive API calls (call level: from 0 to 368 in one capability and from 0 to 429 in total), although they provide similar functionality. Capability breadth (capability level) also varies, for example from 0 to 10 in “Dependency Injection”. These ranges are the same with and without the exploratory JDBC Driver category.
The differences in security-sensitive API calls in a package category stem from diverse implementations, additional features, modularity, and abstraction levels.

Effect on the Findings

The validation supports the findings of RQ2 and RQ3 as statements about which security-sensitive APIs and capabilities the analyzed call graphs report and how functionally similar packages compare. The validation does not establish runtime reachability for every reported API.

•

The over-approximation that RTA removes is small.
RTA, a more precise algorithm, removes 3.1% of the package–API pairs intra-package and 2.6% inter-package, and it does not change any comparison between packages. RTA is also an over-approximation, so these figures are a lower bound on the over-approximation of CHA. The over-approximation that RTA finds is therefore too small to change any finding of RQ2 or RQ3. The validation cannot measure the over-approximation that RTA does not find.

•

Effect of dependencies (Finding #2).
Under every call graph, dependencies increase the number of security-sensitive APIs. On the 34 packages, at the API level, the number of package–API pairs increases from intra-package to inter-package by a factor of 1.8 under the Endor Labs tool (583 to 1,065) and 2.6 under OPAL CHA (671 to 1,725) and OPAL RTA (650 to 1,681). The OPAL factor is greater partly because OPAL treats every public method of the dependencies as an entry point (Section
5.2
).

Under every call graph, packages in the same category differ substantially, and the packages without any security-sensitive API are the same. RQ
1
: To what extent would prior knowledge of security-sensitive API information influence developers’ dependency selection decisions?

Our survey aims to understand how security-sensitive API information would influence developers’ dependency selection.
We received valid responses from 110 developers (response rate: 1.4%).
Because of the low response rate and possible self-selection (Section
12

If you had known this security-sensitive API information before choosing the dependency, how would it affect your decision?

We found that 44.6% of respondents said they would consider this information in a dependency selection process: 20% said they would keep using the chosen dependency but factor security-sensitive API information into future decisions, 19.1% said they would select the dependency with the lowest security-sensitive API call count, and 5.5% said they would select based on calls to a specific capability. Implications

We discuss the implications of our study’s results in this section.
Note that, the goal of our study is to show the importance of visibility into dependencies through security sensitive API calls.

For Practitioners

Our respondents appear to be generally aware of risks with security-sensitive APIs and risks with vulnerabilities in dependencies.
However, greater awareness of security-sensitive APIs and their potential implications will help developers in their dependency selection process.
As evidenced by the survey, our study can complement
{ZTD}_{JAVA}

(
5
)
.

Our results can give developers visibility into potentially sensitive resource use by a dependency (RQ
1
and RQ
1
). If they use a dependency whose capabilities are unnecessary for its role, they could use a permission system such as
{ZTD}_{JAVA}
to restrict access.

In our survey, 44.6% of respondents said they would consider security-sensitive API calls when selecting packages (
RQ
1
); the survey measured stated interest, not observed selection outcomes.
Incorporating this data alongside traditional selection criteria (e.g., functionality, popularity, ease of use) can help developers see which sensitive resources a dependency can reach during the dependency selection process.
Our results show that packages in the same functional category can differ by up to 429 call-graph edges to listed APIs (call level) and by up to 13 of the 15 capabilities (capability level) (
RQ
1
). These comparisons give developers information to consider alongside functionality and other selection criteria; the comparisons do not establish that a package with fewer calls or capabilities is safer.
If developers opt for a dependency that makes excessive calls to any resource or capability due to the specific use case, they should be aware of the potential vulnerability classes associated with the security-sensitive API (our API-to-CWE mapping).
Knowing the potential risk might help developers mitigate it more quickly if such a vulnerability arises.
Overall,
we advocate developers to use security-sensitive APIs for dependency selection
.

For Tool Builders

Our motivation for the lack of tools providing security-sensitive API information is reflected in the developer’s response.
To bridge the gap, we contribute an open-source tool that takes a package call graph as input and generates comparative visualizations of security-sensitive API calls for those packages.
Regardless of how the call graph is generated (e.g., with or without dependencies), our tool can compare the security-sensitive API calls across the provided packages.
Our tool can be integrated in four ways: (a) as a standalone tool, (b) as a plugin in IDEs, (c) as a plugin in package management tools (e.g., Maven, Gradle), and (d) as a part of a dependency management/checking tool (e.g., OpenSSF Scorecard
(
54
)
).
Several developers stated that the way (c) and (d) would be more useful (
RQ
1
), as stated by
\langle P9\rangle

“I would not run a tool to decide this manually—too much effort—but if it was auto-provided in the PR say—then it’s a small nice to have.”

We recommend integrating the tool into package management tools (e.g., npm cli, OpenSSF Scorecard) so developers can quickly compare and identify the most secure option.

For Researchers

To ensure that dependencies remain secure throughout the development lifecycle, security-sensitive API analysis should be integrated into CI/CD pipelines.
Regular security audits can help track and mitigate any introduction of risky dependencies or changes in security-sensitive API usage over time, especially with transitive dependencies.

Our tool can be used to automatically audit the delta in used security-sensitive APIs between two versions of the same dependency, which can be helpful in an already-deployed system.

We envision future research that further explores this type of longitudinal analysis of packages’ security-sensitive API calls to chart the evolution of the attack surface over time.
In addition, future research should also explore whether such a delta can be used to identify malicious package updates.

Threats To Validity

In this section, we present the threats to validity to our study.

Generalizability and Coverage

We use CVEs and CWEs from the 45 packages in our chosen Maven repositories as a reference for our analysis to determine a list of security-sensitive APIs.
We acknowledge that this list of security-sensitive APIs may not reflect the whole population of (possibly) security-sensitive APIs.
However, during our analysis, we found that (1) not all CVE patches and CWEs have related security-sensitive APIs, and (2) the more CVEs and CWEs we analyzed, the more our list gets saturated with repeating security-sensitive API.
Our list of 227 security-sensitive APIs provides an overview of these API calls in the studied Java packages and can inform developers’ consideration of open-source dependencies.
In addition, we did not consider CVE severity (e.g., CVSS score) in our analysis, but CVE severity may affect developers’ decisions on selecting a dependency.

API List Construction Method.

We opt not to consider only the APIs used by the vulnerable functions (from our chosen packages) sensitive.
Considering all APIs called from vulnerable functions as sensitive would be an overapproximation.
Thus, we constructed our security-sensitive API list through expert selection (based on manual inspection of JavaDoc, CVE patches, and CWE examples).
To address potential threats to construct validity, the security-sensitive API list was developed collaboratively with domain experts, ensuring that only APIs with recognized security impacts were included.
The CWE-example step used LLM-based tools, whose output can change between runs and can contain APIs that do not exist.
We reduced this threat in two ways: we kept only the APIs that both Gemini and ChatGPT returned, and we checked every candidate manually against the JDK documentation.
In addition, we checked the 201 JDK APIs of the final list against the JDK 11 class files; this check found seven misspelled names in the list in Appendix
B
, which we corrected, and all 201 names now exist in JDK 11 (the other 26 APIs belong to the Servlet and WebSocket APIs of Java EE and Jakarta EE).
We also repeated the prompts five times for each of the 12 CWEs to which this step applied: both tools returned all 26 APIs of this step in every run, and the raw outputs contained no API that does not exist in the JDK.

Dependence on Endor Labs

Two inputs of our study come from our industry partner, Endor Labs: the call graphs (Section
5.2
) and the manual verification of the vulnerable functions of the 255 CVEs (Section
4.2.1
).
Both steps are proprietary, so we release their outputs: the replication package contains the security-sensitive API call-graph edges, the security-sensitive API call tables for each package version, and the verified vulnerable functions of the 255 CVEs.
The call graph validation in Section
8
uses only open-source tools, and the replication package contains its OPAL configurations, scripts, and outputs, so others can run it from bytecode to results without Endor Labs tools.

Call Graph Construction and Analysis

Our call graphs come from a third-party tool from Endor Labs
(
57
)
, which uses Class Hierarchy Analysis (CHA). At a virtual call site in Java bytecode, CHA creates an edge from the calling method to every matching method implementation in any Java archive of the package’s dependency graph.
Like most program analyses used in practice, the analysis is neither sound nor complete
(
58
,
59
)
, and it can both over-approximate and under-approximate runtime reachability.
First, CHA
over-approximates
: it can include edges that no execution takes.
Our validation (Section
8
) compared OPAL CHA with OPAL RTA: at the API level, RTA retained 96.9% (intra-package) and 97.4% (inter-package) of the package–API pairs found by CHA. This comparison estimates the effect of changing algorithms on our analyzed packages; the comparison does not measure net error against runtime behavior.
Second, the analysis
under-approximates
: it may miss security-sensitive APIs that a package reaches only as the target of a reflective call, a dynamic proxy, or a class loaded at run time. This does not affect the calls
to
the reflection APIs that we count, which are direct calls in the bytecode. Because the analysis can also add unreachable edges, the net direction of error in the overall counts is unknown; the reported results describe APIs found by our static analysis and may omit dynamically reached APIs.
Our analysis also does not check how a package uses a security-sensitive API, for example with which arguments or in which execution context, so a call does not by itself mean a security risk; a finer analysis, such as a data-flow analysis of the arguments, could separate benign calls from risky ones, and we leave it to future work.
We did not measure the number of omitted reflective targets. Measuring them would require dynamic analysis with client applications, which are not available for the library versions in our dataset. Prior work on application code found a median recall of 0.88 for static call graphs
(
60
)
; that result should not be taken as an estimate for our packages.
The validation has three further limits.
The validation covers the latest versions of the 34 RQ3 packages, not a random sample of the 30,772 versions of RQ2.
We compared the Endor Labs tool and OPAL only in the intra-package scope, because the two tools define the inter-package scope differently; in this scope, they agree on which security-sensitive APIs each package calls (Spearman’s
\rho=0.99
), and we labeled every remaining difference.
Finally, OPAL 5.0.0 reported that some Java 21 class files exceed the class-file versions it supports; we used the same JDK and the same OPAL version for both algorithms.
In addition, some package versions in our dataset lacked source code, leading the call graph generator to produce no output.

Survey Limitation

The generalization of our findings beyond the pool of participants should be made with caution since this is a common limitation of works of this kind
(
61
)
.
The developers who participated in the survey might not have represented the entire developer population.
The response rate was 1.4% (110 of 7,785 contacted developers), so the survey results describe our respondents only.
Developers participating in an API study might be more knowledgeable/aware of APIs than the average (self-selection bias
(
62
,
63
)
).
Our study may be affected by social desirability bias
(
64
)
, similar to other studies
(
65
,
51
,
66
)
.
Participants’ reported reactions might differ from what they would have done in real life.
Inspired by previous studies and survey best practices, we sought to minimize social desirability bias through iterative pre-testing and softening language.
The survey result may also be affected by how we explain the problem (survey clarity) and present the alternatives (visualization clarity).
To ensure our survey and visualization are clear, we conducted a pilot and modified our survey accordingly.

Conclusion

In this paper, we present a repeatable methodology to construct a security-sensitive API list for an ecosystem, and we use the Java list to give visibility into the sensitive resources that a dependency can reach.
Our static analysis shows that functionally similar packages differ in the security-sensitive APIs and the capabilities that their call graphs reach.
This visibility can help developers compare alternatives, review the calls of a dependency, or restrict them with a permission system.
Our study does not show that this visibility reduces the attack surface of software or changes real-world dependency choices: the call graphs measure static reachability, and the survey measured the stated intentions of 110 respondents in a hypothetical scenario.
We envision that tool builders will integrate security-sensitive API information into dependency management tools, and future work can measure whether developers who use this information select different dependencies.
