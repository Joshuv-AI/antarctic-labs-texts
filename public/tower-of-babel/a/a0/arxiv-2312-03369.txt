Analysis of Linux-PRNG (Pseudo Random Number Generator)
UGP Report

Abstract




Abstract

The Linux pseudorandom number generator (PRNG) is a PRNG with entropy inputs and is widely used in many security-related applications and protocols. This PRNG is written as an open-source code which is subject to regular changes. It has been analysed in the works of Gutterman
et al.

[
GPR06
]
,
Lacharme et al.

[
LRSV12
]
and
[
KASN15
]
, while in the meantime, several changes have been applied to the code, to counter the attacks presented since then. Our work describes the Linux PRNG of kernel versions 5.3 and upwards. We discuss the PRNG architecture briefly and in detail about the entropy mixing function.

Our goal is to study the entropy mixing function and analyse it over two properties, namely, injectivity and length of the longest chain. For this purpose, we will be using SAT solving and model counting over targetted formulas involving multiple states of the Linux entropy store.

1
Introduction

Many security protocols base their security on the impossibility of an attacker being able to guess the random data, such as session keys for cryptosystems or nonces for cryptographic protocols. However, the amount of required random data can differ significantly with the application. Therefore, random data generation should take into account the fact that the user can request either high-quality random data or a great amount of pseudorandom data. Even a recent article
[
Edg19
]
demanding a fix in Linux’s
getrandom()
function to provide an alternative to get a great amount of pseudorandom data without getting blocked for entropy.

A pseudorandom number generator with entropy inputs produces bits non-deterministically as the internal state is frequently refreshed with unpredictable data from one or several external entropy sources. It is typically made of (1) several physical sources of randomness called entropy sources, (2) a harvesting mechanism to accumulate the entropy from these sources into the internal state, and (3) a post-processing procedure. The latter frequently uses a
cryptographically secure PRNG
(CSPRNG) to generate outputs and to update the internal state.

PRNG Model

In Unix-like operating systems, a pseudo-random number generator with input was implemented for the first time for Linux
1.3.30
in
1994
. The entropy source comes from device drivers and other sources such as latencies between user-triggered events (keystroke, disk I/O, mouse clicks, …). It is gathered into an internal state called the
entropy pool
. The internal state keeps an estimate of the number of bits of entropy in the internal state and (pseudo-)random bits are created from the special files
/dev/random
and
/dev/urandom
. Barak and Halevi
[
BH05
]
discussed the generator
/dev/random
briefly, but its conformity with their robustness security definition is not formally analysed.

The first security analysis of these generators was given in
2006
by Gutterman, Pinkas and Reinman
[
GPR06
]
. It was completed in
2012
by Lacharme, Röck, Strubel and Videau
[
LRSV12
]
. Gutterman
et al.

[
GPR06
]
presented an attack based on kernel version
2.6.10
for which a fix was published in the following versions. Lacharme
et al.

[
LRSV12
]
gives a detailed description of the operations of the generators and provides a result on the entropy preservation property of the
mixing function
used to refresh the internal state.

In the next few sections, we will discuss the
Architecture
of the Linux PRNG briefly and in detail the
mixing function
applied over the
entropy pool
to refresh the internal state of the random number generator. The works of Lacharme
et al.

[
LRSV12
]
suggested that the
mixing function
has the property of entropy preservation, and analysing the same property is one of our goals.

The motivations behind this analysis are:

•

Gain insights into the working of the Linux PRNG

•

Gain a deeper undestanding of the entropy estimation and accumulation processes.

•

Verify the entropy preservation properties as claimed in
[
LRSV12

.

Previous works on the analysis of Linux PRNG claim that the
mixing function
which is used to refresh the internal state preserves the entropy received from various entropy sources, our primary goal with this analysis is to verify this using the techniques of SAT solving and model counting.

Our goals regarding this analysis are:

•

Comment the property of injectivity of the entropy mixing function.

•

Estimate the length of the longest chain, i.e. the size of input bytes which when supplied with an initial state of
entropy pool

2
Architecture

The Linux PRNG has been a part of the Linux kernel since
1994
. Ts’o wrote the original version, and Mackall
[
MT09
]
later modified it. The generator, apart from the entropy input hooks inserted into drivers, represents about
2500
lines of C code in a single source file,
drivers/char/random.c
.

2.1
General Structure

Unlike other PRNGs, the internal state of the Linux PRNG is divided into three entropy pools, the
input pool
, the
blocking pool
and the
non-blocking pool
. The blocking and the non-blocking pools together form the
output pools
. The size of the input pool is
128

32
-bit words (
4096
bits) and the size of each output pool is
32

32
-bit words (
1024
bits). The generator is designed to perform the collection of entropy inputs as efficiently as possible; therefore, it uses a linear mixing function instead of a more usual hash function. The general structure of a Linux PRNG is shown in
Figure

2
.

Figure 2:
PRNG Model
[
LRSV12
]

The PRNG relies on external entropy sources. The various system events like keyboard and mouse movements, disk events, and hardware interrupt inside the kernel act as the entropy source for Linux PRNG and inputs are collected from them. The collected inputs are accumulated inside the input pool. An entropy counter is associated with each pool, decremented when entropy is extracted from the pools and incremented when entropy is added to the pools. Entropy transfers take place from the input pool to the output pools only when some entropy needs to be extracted from Linux PRNG. Hence, the entropy counters of the output pools remain close to zero except for the transition state. It makes the entropy counter of the input pool as the most significant one as the available entropy in Linux PRNG is reflected by the entropy counter value of the input pool
[
LRSV12
]
.

Linux PRNG provides two character interfaces
/dev/random
and
/dev/urandom
to read the random output. The
/dev/random
reads from the blocking pool and
/dev/urandom
read from the non-blocking pool.
/dev/random
provides cryptographically stronger bytes, blocks if sufficient entropy is not present in the pools and resumes when enough new entropy samples have been mixed into the input pool. Thus, it limits the number of generated bits according to the estimation of the entropy available in the PRNG.
/dev/urandom
always provides the desired amount of bytes and does not block; it is meant for the fast generation of large amounts of random data. In addition to these two character interfaces, Linux PRNG also provides
get_random_bytes()
which is a kernel interface. It allows the other kernel components to read from the non-blocking pool.

Entropy accumulation in Linux PRNG is a process of three major steps, namely, collecting entropy from various entropy sources, mixing the collected entropy into the input pool using a
mixing function
and estimating the total entropy associated with each input which is mixed into the input pool. Broadly, the structure of Linux PRNG consists of four major components which are described in the following subsections.
Section

2.2
describes the various entropy sources briefly used by the Linux PRNG for accumulating entropy.
Section

3
describes the mixing function used for mixing the inputs collected from different entropy sources into the input pool. The same mixing function is also used when entropy is transferred from the input pool to the output pools when the entropy content of the output pools is less than that of the requested entropy bytes from Linux PRNG.
Section

2.3
describes briefly the entropy estimation process used by Linux PRNG to estimate the entropy associated with each input which is mixed into the input pool.
Section

2.4
briefly describes the output generation process in Linux PRNG, which is used whenever entropy is extracted from the output pools or a transfer of entropy occurs between the input pool and the output pools.

2.2
Entropy Sources

Entropy inputs are injected into the generator for initialization, and through the updating mechanism, provides the backbone of the security of the PRNG. The Linux PRNG is intended to be used independently of any specific hardware. Therefore, it cannot rely on nondeterministic physical phenomena generally used in the random generation, which require additional hardware.

The Linux PRNG processes events from different entropy sources, namely, user inputs (keyboard and mouse movements), disk events, and hardware interrupts. Each input generated from these entropy sources are mixed into the input pool and consists of three values, as shown in
Figure

3
, also known as
sample
.

Figure 3:
An Entropy Input

In the above
sample
,

•

num
: It is a
32
-bit value representing the specific event type.

•

jiffies
: It represents the jiffy count value of the system at which the events mixed into the input pool of the Linux PRNG. ‘Jiffy’ is the time between two ticks of the system timer interrupt, and the jiffy count value of a system represents the total number of ticks of system timer interrupt from the boot time.

•

cycles
: It is a
32
-bit value representing the CPU cycle count value.

The functions
add_input_randomness
,
add_disk_randomness
and
add_interrupt_randomness
of
/drivers/char/random.c
file of Linux kernel manage the collection of inputs from different entropy sources of the Linux PRNG. All these inputs are accumulated into the input pool of Linux PRNG through a mixing function.

2.3
Entropy Estimation

The entropy estimation is one of the crucial steps for generation of data via
/dev/random
. An accurate estimation of whether the corresponding pool contains enough entropy to generate unpredictable output data is essential.

The entropy counter associated with each pool keeps an estimate of the entropy content of that pool. Entropy estimation of a Linux PRNG is based on the timing of the events generated from different entropy sources, which mixed into the input pool. Although, both
cycles
and
jiffies
represents the timing of the event,
jiffies
being the one having more coarser granularity is used for estimating the entropy of Linux PRNG. The difference of
jiffies
associated with each input event is used for entropy estimation.

2.4
Output Generation

There are three output interfaces provided by the Linux PRNG for extracting entropy from the blocking and non-blocking pools.
/dev/random
and
/dev/urandom
are the character interfaces for the users and
get_random_bytes()
is the kernel interface for extracting entropy.
/dev/random
extracts entropy from blocking pool and may block if enough entropy is not present, providing very high-quality random bits.
/dev/urandom
can provide as many bits as requested, extracting from the non-blocking pool. The function
get_random_bytes
is available only within the kernel and extracts entropy from the non-blocking pool.

The output generation function can be divided into two phases, namely, feedback phase and extraction phase. It uses
SHA-1
hash function in two-steps.

1.

All bytes of the pool are hashed to produce
5
-word hash and
20
bytes are mixed back into the pool using mixing function. Mixing back of generated hash in the pool prevents the backtracing attacks. This step forms the feedback phase of output generation function.

2.

16
words from the mixed pool content are again hashed along with the 5 output words from the previous step. The 20-byte output from this second hash is folded in half to get a
10
byte output.

The entropy counter of the output pool is finally decremented by the number of bytes generated from the Linux PRNG.

3
Mixing Function

The structure of the mixing function of Linux PRNG is shown in
Figure

4
. This function mixes one byte of the input at a time by first extending that one byte to a
32
-bit word, followed by a rotation of the extended
32
-bit word by a changing factor, and finally mixing it in the pool by using a linear shift register. It is designed so that no entropy gets lost while diffusing into the pools.

Figure 4:
The mixing function
[
LRSV12
]

The Mixing function is defined by the function
mix_pool_bytes
in

/drivers/char/random.c
file of Linux kernel. The function
mix_pool_bytes
takes three arguments.

1.

struct entropy_store *r
: Entropy store is a structure which contains various entities such as
poolinfo
containing the definition for both input and output pools,
pool
containing the name of the pool being used for mixing the entropy input,
entropy count
representing the entropy count of the respective pool. The input pool is declared as an array containing
128
words and the output pools which includes both blocking and non-blocking pools are declared arrays of
32
words each. The variables
add_ptr
and
input_rotate
are defined as data of type unsigned int (C data type).

2.

const void *in
: Pointer to the input collected from various entropy sources which is mixed into the entropy pools. When inputs are mixed into the input pool from the function
add_timer_randomness
,
in
becomes a pointer to the structure
sample
as shown in
Figure

3
.

3.

int nbytes
: This represents the total number of bytes to be mixed into the pool. The total number of bytes added to the input pool is either
12
bytes or
16
bytes depending on the architecture of the system used.

The mixing function updates the input entropy store after mixing the input bytes received from various entropy sources.

Apart from these function arguments, there are also different variables declared inside the mixing function.
unsigned long integers tap1, tap2, tap3, tap4
and
tap5
are declared inside the function, their values are
104,76,51,25
and
1
respectively for the input pool and
26,19,14,7
and
1
respectively for the output pools. A variable
wordmask
is also defined inside the function
mix_pool_bytes
whose value is
127
for the input pool and
31
for the output pools.

3.1
The Process

The input bytes also known as samples are mixed into the input pool using mixing function, one byte at a time. For a
n
byte sample, the whole process of mixing is repeated
n
times. The one-byte value of the sample is first type casted to
__u32
(expanded to
32
bits) form of C language and is then rotated with a function called
rol32
, defined in
linux/bitops.h
of Linux kernel. The
rol32
function takes two arguments, a
word
to be rotated (
32
bit) and a factor
shift
by which that word is rotated.

\text{w}=(\text{word}\gg\text{shift})\ |\ \text{word}\ll(32-\text{shift})

The initial value of
shift
is
0
. The variable
i
declared inside the mixing function is equal to the output of a function
ACCESS_ONCE(x)
, where
x
is equal to a variable
add_ptr
defined in the structure
entropy store
, this function is defined as a macro in
linux/compiler.h
of Linux kernel. In each iteration, a
byte
of the entropy input is mixed into the entropy pool via following steps:

1.

The
byte
representing one byte value of the input sample is expanded to
32
bits, rotated using the
rol32
function and the variable
w
is assigned its value.

2.

The variable
i
, which was assigned the value
add_ptr
from the entropy store is updated with
(i - 1) & wordmask
.

3.

The word
w
is then
XOR
ed at each of the tap locations defined for the corresponding pool in the following way:

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[i];

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[(i+\text{tap1})\ \&\ \text{wordmask}];

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[(i+\text{tap2})\ \&\ \text{wordmask}];

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[(i+\text{tap3})\ \&\ \text{wordmask}];

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[(i+\text{tap4})\ \&\ \text{wordmask}];

\displaystyle w

\displaystyle=w\oplus r\rightarrow\text{pool}[(i+\text{tap5})\ \&\ \text{wordmask}];

The word
w
is then finally mixed back into the entropy pool at the
i^{t}h
location using the following:

r\rightarrow\text{pool}[i]=(w\gg 3)\oplus\text{twist\_table}[w\ \&\ 7];

Twist table is defined in
drivers/char/random.c
as an array containing
8

32
-bit hexa-decimal values. These values are the monomials in the field
(F_{2})/(Q)

[
Koo02
]
.
Q(x)
is defined in
[
Koo02
]
as equal to
x^{32}+x^{26}+x^{23}+x^{22}+x^{16}+x^{12}+x^{11}+x^{10}+x^{8}+x^{7}+x^{5}+x^{4}+x^{2}+x+1
, is a CRC32 polynomial used for Ethernet protocol.

4.

Finally, the
input_rotate
value, i.e.
shift
is increased by a value of
7
if the value of
i
is non-zero, else it is incremented by 14.

When all the bytes of an entropy input are mixed into the entropy pool, the value of
input_rotate
and
i
is then again accessed using the function
ACCESS_ONCE
and is assigned to the respective variables.

4
Design and Evaluation

Our main goal, as discussed in
Section

1
to analyse the Linux’s
mixing function
and comment on the properties of injectivity and length of the longest chain. With the help of this analysis, we can verify whether the entropy once supplied to the
mixing function
is preserved or not.

For our analysis, we will use the techniques of SAT solving and model counting in order to ensure that the function preserves entropy. We have imitated the parts of code in
/drivers/char/random.c
concerning the
mixing function
and the
entropy store
in
scala
as part of our tool
Entropy-Mixer
. In the next subsection, we are going to discuss in detail the implementation design of
Entropy-Mixer
.

4.1
Design

Our tool
Entropy-Mixer
, takes an initial entropy store and an array of entropy bytes as input and applies the mixing function on the store, mixing one byte at a time and updates the initial entropy store to the final state of the entropy store after the mixing is complete. During this entire process, the variables involved are
bit-vector expressions
. Hence, the final store generated is also a bit-vector expression represented as an expression of input entropy store and entropy bytes combined with logical bit operations.

The model structure of our tool is as follows:

1.

Expr Class
: Denotes a boolean expression containing boolean variables and boolean operators (each defined as a case class), an expression can be one of the following.

•

A constant boolean value, i.e.
true
or
false
.

•

A boolean variable (value unknown), denoted by a name (string).

•

Complement of an expression, i.e.
Not(expr)
.

•

Boolean operator applied over a list of expressions, such as
and
,
or
and others.

2.

BitVector Class
: Denotes a bit-vector of arbitrary but constant length defined as an array of boolean expressions (using the
Expr
class).

3.

Entropy Store
: Denotes the
entropy pool
as discussed in
Section

3
, the entropy pool can be of size
128

32
-bit words in which case it is an input pool, or it can be of size
32

32
-bit words becoming one of the output pools. Each word is denoted as an instance of the
BitVector
class.

The mixing function involves a good amount of bit operations to be performed on the data, in order to incorporate those in our model, we have designed
BitVectorOperations
object to address our needs of bit operations. The operations defined are as follows:

1.

bitOr, bitAnd, bitXor
and
bitXnor
: These operations take
2
bit-vectors of same size (e.g.
32
bit) and generate a bit-vector after applying bitwise
or, and, xor
and
xnor
respectively on the
2
bit-vectors.

2.

bitLeftShift
and
bitRightShift
: These operations take a bit-vector and an integer value, applies the bitwise
left shift
and
right shift
respectively to generate the output bit-vector.

3.

expandBitVector
: It takes as input a bit-vector and an integer value (greater than size of bit-vector), expands the bit-vector to the provided size.

4.

threeMux
: It takes an array of bit-vectors and a bitvector
select
value, and it imitates the functionality of a
3
pin multiplexer.

Using the above classes and operations, we imitate the code of
mix_pool_bytes
function of Linux kernel in order to gain the final
entropy store
in the form of
bit-vector expressions
to be used further by SAT solvers.

4.2
Evaluation

We have discussed in detail the design of our tool and model setup, in this subsection, we will look at the functions we tried to analyse using SAT solvers to judge the property of
injectivity
for the mixing function.

We used
Cadical

[
Bie19
]
for SAT Solving and
Maxcount

[
FRS17
]

The formulas that we analysed are as follows:

1.

Formula-1
:

(i_{1}\neq i_{2})\ \&\ (f(x,i_{1})=f(x,i_{2}))

(1)

This formula checks the condition of
2
different sets of entropy input bytes (with the same size) being used as input for the mixing function (denoted by

2.

Formula-2
:

((x_{1}\neq x_{2})\ |\ (i_{1}\neq i_{2}))\ \&\ (f(x_{1},i_{1})=f(x_{2},i_{2}))

(2)

This formula checks the condition of the final state of entropy stores being same after the mixing even though the initial state of entropy stores was different or the entropy bytes used for mixing were distinct (of same size but different value).

For testing above formulas, we used the output pool as the entropy store, the size of the output pool is
32

32
-bit words, the input entropy bytes will be an array of size
8
bit-vectors.

After running SAT Solvers on the above formulas:

1.

Formula-1
:
UNSAT
upto size
88
of input entropy bytes, i.e. variables
i_{1}
and
i_{2}
.

2.

Formula-2
:
SAT
upto size
288
of input entropy bytes.
