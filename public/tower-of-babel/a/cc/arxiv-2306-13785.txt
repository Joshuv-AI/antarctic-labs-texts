Parallel-batched Interpolation Search Tree
Vitaly Aksenov, Ilya Kokorin, Alena Martsenyuk

Abstract
A sorted set (or map) is one of the most used data types in computer science. In addition to standard set operations, like Insert , Remove , and Contains , it can provide set-set operations such as Union , Intersection , and Difference . Each of these set-set operations is equivalent to some batched operation: the data structure should be able to execute Insert , Remove , and Contains on a batch of keys. It is obvious that we want these “large” operations to be parallelized. These sets are usually implemented with the trees of logarithmic height, such as 2-3 trees, treaps, AVL trees, red-black trees, etc. Until now, little attention was devoted to data structures that work asymptotically better under several restrictions on the stored data. In this work, we parallelize Interpolation Search Tree which is expected to serve requests from a smooth distribution in doubly-logarithmic time. Our data structure of size n n performs a batch of m m operations in O ⁡ ( m ​ log ⁡ log ​ n ) O(m\log\log n) work and poly-log span.

Definition 1

We want a sorted set to implement the following batched operations:

We can employ parallel programming techniques (e.g.,

Definition 2

A batched data structure

2.3
Time complexity model

In our work, we assume the standard
work-span
complexity model
[
1
]
for
fork-join
computations. We model each computation as a

v\rightarrow a_{1}\rightarrow a_{2}\rightarrow\ldots\rightarrow a_{n}\rightarrow u
from operation

nor path

exists, operations

can be executed in any order, even in parallel (see Fig
1

(i.e., the node with zero incoming edges) and exactly one

(i.e., the node with zero outcoming edges). The only
source node
corresponds to the start of the execution, while the only
sink node
corresponds to the end of the execution.
Some nodes have two
outcoming edges
— such operations spawn two parallel tasks and are called
fork operations
.
Some nodes have two
incoming edges
— such operations wait for two corresponding parallel tasks to complete and are called
join operations
.

:

, representing a parallel execution

For example, in Fig.

Considering the execution graph of the algorithm, our target complexities are:

•

3.5
Time and space complexity

Mehlhorn and Tsakalidis
[
15
]
give a definition of a
smooth probability distribution
. For example, uniform distribution
U(a;b)
is smooth for every
-\infty<a<b<+\infty
.

Definition 6

An insertion is
\mu
-random
if the key to be inserted is drawn from probability density
\mu
.

A removal is
random
if every key present in the set is equally likely to be removed.

Mehlhorn and Tsakalidis
[
15
]
state that if probability distribution
\mu
is smooth:

•

IST with
n
keys takes
O(n)
space;

•

The expected amortized insertion and removal cost is
O(\log\log n)
;

•

The amortized insertion and removal cost is
O(\log n)
;

•

The expected search time on IST, generated by
\mu
-random insertions and random removals, is
O(\log\log n)
;

•

the worst-case search time is
O(\log^{2}n)
;

These estimations are based on the fact, that the expected cost of the interpolation search on a sorted array, generated by
\mu
-random insertions and random removals given that
\mu
is smooth, is
O(1)
, and the ideally balanced IST storing
n
keys has depth
O(\log\log n)
.

Therefore, IST can execute operations in
o(\log n)
time under reasonable assumptions. As our goal, we want to design a parallel-batched version of the IST that processes operations asymptotically faster than known sorted set implementations (e.g., red-black trees).

7
Parallel tree rebuilding

7.1
Rebuilding principle

Following the removal algorithm from Section
6
, we face the following problem: logically removed keys still reside in the IST wasting memory space (Fig.
14
), since we do not have any mechanism for physically deleting removed keys. We can even end up in a situation when all the keys in the IST are logically removed, but the IST still occupies a great amount of memory without being able to reclaim any of the occupied space.

Figure 14
:
IST, that is logically empty, still occupies some space for removed keys

We can employ
subtree rebuilding
approach to reclaim space, occupied by logically removed keys. Moreover, as stated in Section
3.4
, we employ the very same approach to keep the IST balanced (and thus keep the operation execution time bounded).

Our rebuilding algorithm is conceptually similar to the algorithm proposed e.g., in
[
15
,
7
,
19
]
: For each node of the IST we maintain
Mod_Cnt
— the number of modifications (successful insertions and removals) applied to that node subtree. Moreover, each node stores
Init_Subtree_Size
— the number of keys in that node subtree when the node was created.

Suppose we are executing an update batch operation
Op
(i.e., either
InsertBatched
or
RemoveBatched
) in node
v
and
Op
increases
v.Mod_Cnt
by
k
(i.e., it either inserts
k
new keys to
v
subtree or removes
k
existing keys from
v
subtree).

If
v.Mod_Cnt + k
\leq
C
\cdot
v.Init_Subtree_Size
(where
C
is a predefined integer constant, e.g.,
2
) we increment
v.Mod_Cnt
by
k
and continue the execution of
Op
in an ordinary way (as described in Sections
5
and
6
); Otherwise, we rebuild the whole subtree of
v
. The subtree rebuilding works in the following way:

1.

We
flatten
the subtree into an array: we collect all non-removed keys from the subtree to array
subtree_keys
in ascending order. This operation is described in more detail in Section
7.2
;

2.

We apply the operation, that triggered the rebuilding, to the
subtree_keys
array:

(a)

If
InsertBatched(v, keys[], left, right)
operation triggered the rebuilding, we merge (see Section
2.4
)
keys[left..right)
into
subtree_keys
:
subtree_keys
\leftarrow
Merge(subtree_keys, keys[left..right))
;

(b)

If
RemoveBatched(v, keys[], left, right)
operation triggered the rebuilding, we filter out
keys[left..right)
from the
subtree_keys
via the
Difference
operation (see Section
2.4
):
subtree_keys
\leftarrow
Difference( subtree_keys, keys[left..right))
;

3.

Finally, we build an ideal IST
v’
, containing all entries from
subtree_keys
. This operation is described in more detail in Section
7.3
. Note, that
v’
will contain all the keys we were inserting into
v
(if we are inserting new keys) or will not contain the keys were removing from
v
(if we are removing the existing keys).

7.2

First of all, we need to know how many keys are located in each node subtree. We store this number in a

•

•

•

•

•

7.3

Suppose we have a sorted array of keys and we want to build an
ideally balanced IST
(see Section
3.4
) from these keys. We implement this procedure recursively via
build_IST_subarray(keys[], left, right)
procedure — it builds an ideal IST containing keys from the
keys[left..right)
subarray and returns the root of the newly-built subtree. Thus, to build a new subtree from array
keys
we just use
new_root := build_IST_subarray(keys[], 0, |keys|)
to obtain the root of the IST built from the whole

array.

If the size of the subarray (i.e.,
right - left
) is less than some constant
H
, we return a leaf node containing all the keys from
keys[left..right)
in its
Rep
array.

Otherwise (i.e., if
right - left
is big enough), we have to build a non-leaf node. Let us denote
m := right - left; k :=
\lfloor\sqrt{m}\rfloor-1
. As follows from Definition
5
,
Rep
array should have size
\Theta(\sqrt{m})
and its elements must be equally spaced keys of the initial array. Thus, we copy
k
-th key into
Rep[0]
,
(2\cdot k)
-th key into
Rep[1]
,
(3\cdot k)
-th key into
Rep[2]
and so on — in general, we copy
(i+1)\cdot k
-th key into
Rep[i]
.
Note, our subarray
keys[left..right)
begins at position
left
of the initial array
keys
. Thus, we copy key
keys[left + (i + 1)
\cdot
k]
into

. All the copying can be done in parallel since there are no data dependencies. This way we obtain

\Theta(\sqrt{m})
filled with equally-spaced keys of the initial subarray (Fig.
16
).

Now we should build the children of the newly-created node (Fig.
16
):

•

Rep[0] = keys[left + k]
. Thus, all keys less than
keys[left + k]
will be stored in
C[0]
subtree (see Section
3
for details). Since
keys
array is sorted,

must be built from
keys[left..left + k)
, thus
C[0] = build_IST_subarray(keys[], left, left + k)
;

•

for

,

\cdot

and
Rep[i] = keys[left + (i + 1)
\cdot
k]
. Thus, all keys
x
such that

should be stored in
C[i]
subtree. Since
keys
array is sorted,
C[i]
must be built from the subarray

\cdot

\cdot

, thus

\cdot

\cdot

;

•

k^{2}
]
(note, that

= left +
{\left(\lfloor\sqrt{\texttt{right}-\texttt{left}}\rfloor-1\right)}^{2}<\texttt{right}
).
Thus, all keys greater than

]
are stored in

subtree. Since

must be built from
keys[left +
k^{2}
..right)
, thus

.

We can build all children in parallel, since there is no data dependencies between them.

Use
ID := Rank(bounds, node.Rep)
. After that
ID[i] = j
iff
Rep[j]\leq\texttt{bounds[i]}<Rep[j+1]

8
Theoretical results

In this section, we present the theoretical bounds for our data structure. These bounds are quite trivial, so, we just explain the intuition behind them.

Theorem 8.1

The flatten operation of an IST with
n
keys has
O(n)
work and
O(\log^{3}n)
span. The building procedure of an ideal IST from an array of size
n
has
O(n)
work and
O(\log n\cdot\log\log n)
span. Thus, the rebuilding of IST with
n
keys costs
O(n)
work and
O(\log^{3}n)
span.

Proof
(Sketch)

While the work bounds are trivial, we are more interested in span bounds.
From
[
15
]
we know that in the worst case, the height of IST with
n
keys does not exceed
O(\log^{2}n)
.
Thus, the flatten operation just goes recursively into
O(\log^{2}n)
levels and spends
O(\log n)
span at each level. This gives
O(\log^{3}n)
span in total. The construction of an ideal IST has
O(\log\log n)
recursive levels while each level can be executed in
O(\log n)
time, i.e., copy the elements into
Rep
array. This gives us the result.

This brings us closer to our main complexity theorem.

Theorem 8.2

The work of a batched operation on our parallel-batched IST has the same complexity as if we apply all
m
operations from this batch sequentially to the original IST of size
n
(from
[
15
]
, the expected execution time is
O(m\log\log n)
). The total span of a batched operation is
O(\log^{4}n)
.

Proof
(Sketch)

The work bound is trivial — the only difference with the original IST is that we can rebuild the subtree in advance before applying some of the operations.
Now, we get to the span bounds. From
[
15
]
, we know that the height of IST with
n
keys does not exceed
O(\log^{2}n)
. On each level, we spend: 1) at most
O(\log^{2}n)
span for merge and rank operations; or 2) we rebuild a subtree at that level and stop. The first part gives us
O(\log^{4}n)
span, while rebuilding takes just
O(\log^{3}n)
span. This leads us to the result of the total
O(\log^{4}n)
span.

10
Conclusion

In this work, we presented the first parallel-batched version of the interpolation search tree that has an optimal work in comparison to the sequential implementation and has a polylogarithmic span. We implemented it and got very promising results. We believe that this work will encourage others to look into parallel-batched data structures based on something more complex than binary search trees.
