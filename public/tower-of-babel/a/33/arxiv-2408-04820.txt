Abstract
. We propose using natural language outlines as a novel modality and interaction surface for providing AI assistance to developers throughout the software development process. An NL outline for a code function comprises multiple statements written in concise prose, which partition the code and summarize its main ideas in the style of literate programming. Crucially, we find that modern LLMs can generate accurate and high-quality NL outlines in practice. Moreover, NL outlines enable a bidirectional sync between code and NL, where a developer can change either code or NL and have the LLM automatically update the other. We discuss many use cases for NL outlines: they can accelerate understanding and navigation of code and diffs, simplify code maintenance, augment code search, steer code generation, and more. We then propose and compare multiple LLM prompting techniques for generating outlines and ask professional developers to judge outline quality. Finally, we present two case studies applying NL outlines toward code review and malware detection.

1.
Introduction

Outlining a complex document is a standard way to improve its organization and accessibility. A
table of contents
presents organizational notes separately from the document’s content, but these notes may also be interleaved with the content as chapter or section headings. Modern examples of outlines include the “Contents” sidebar on Wikipedia pages listing the section headings, and for programming, the “Outline view” in VS Code and the “Symbols pane” on GitHub list the classes and functions in a code file.
These outlines also assist navigation by jumping to the corresponding part of the file when clicked.
Advances in large language models (LLMs) such as Gemini
(
Gemini Team, 2023
;
Gemini Team, 2024
)
and
GPT-4

(
OpenAI, 2023
)
raise new opportunities to automatically generate outlines of software artifacts in reimagined ways.
After all, large software projects are incredibly complex, with one study finding that developers spend 70% of their time on program comprehension
(
Minelli et al., 2015
)
.

Summarization is another way to accelerate understanding of a document. Scientific papers have an
abstract
, and business documents may have an
executive summary
, to help readers quickly understand the key points without reading the entire text.
Even if one does read the entire text, reading the summary beforehand may still improve understanding
(
LeCourt et al., 2024
;
Addison, 2022
)
. Recent works apply machine learning and LLMs toward automatic text summarization
(
Jin et al., 2024
)
and code summarization
(
Zhang et al., 2022
;
Zhu and Pan, 2019
;
Hu et al., 2022
;
Ahmed and Devanbu, 2022
;
Ahmad et al., 2020
;
Ahmed et al., 2024
;
Dvivedi et al., 2024
)
, with many summary styles for different purposes and audiences
(
Geng et al., 2024
;
Sun et al., 2024
;
Mu et al., 2023
;
Chen et al., 2021
)
. For example, upon straightforwardly asking Gemini or ChatGPT to summarize a piece of code, one usually receives long paragraphs explaining each aspect of the code in detail, often totaling more text than the code itself. Such explanations are useful for learning but are not optimized for helping an experienced developer work more quickly. Instead, we desire a concise summary that efficiently conveys the key ideas, with clear alignment between the summary and the code.

Another common way to improve the clarity of code is to incorporate natural language (NL). Writing docstrings, comments, helpful error messages, and descriptive identifier names are well-known aspects of good coding style
(
PYT, 2024
)
. In computational notebooks or other forms of
literate programming

(
Knuth, 1984
)
, code and explanatory NL are interleaved in a file that is both executable and self-documenting. NL is generally easier for humans to read than code, so well-written NL can help developers understand the associated code more quickly.

Using these themes of outlining, summarization, and literate programming, we propose using LLMs to generate a new form of code explanation:
natural language outlines
(NL outlines). An NL outline consists of natural language statements that partition the code into logical sections, while summarizing each section of code with concise wording. The outline may be shown interleaved with the code or displayed separately, depending on the application. NL outlines are a particularly appealing modality for AI developer assistance due to their broad applicability: in addition to helping developers understand and navigate code,
Fig.

1
illustrates our vision of how NL outlines can be used throughout the software development, e.g., for code generation and maintenance, code search, and code review.

NL outlines are not just one tool or feature. Instead, NL outlines are a conceptual foundation and framework enabling many possible features across all of the different software development surfaces that we use today.
This highlights a key conceptual difference to previous work.
Existing AI auto-commenting techniques focus on reproducing current developer behavior by
training on large code bases. In contrast, our work
does
not
aim to reproduce existing
comments, but to encourage the use of a
new style of code summarization
, the NL outline.
At a technical level, we cannot
simply rely on the LLM’s inherent commenting abilities—we need to provide the model with guidance about what makes a good NL outline, which we do via carefully designed few-shot prompting (
Section

4
).
Thus, this paper aims to demonstrate that NL outlines are
broadly useful
across the software development stack and that
LLMs are already capable enough
to support these new ideas in practice.

2.
Natural Language Outlines

A
natural language outline
(NL outline) for a function or snippet of code consists of one or more statements written in concise prose, which are aligned with the code and partition it into semantically-coherent sections, such that each outline statement summarizes the section of code it aligns to.

As an example,
Fig.

2(a)
shows a Python function from an author’s prior project. Even though the code is self-contained and only uses common libraries, it still takes a considerable amount of time for a developer to parse the code and decipher the steps taken to achieve its goals. A docstring might help somewhat, but docstrings usually discuss the function’s contract instead of its implementation strategy which may be more pertinent when editing the code.

To gain a high-level understanding of the implementation, one may instead read the NL outline in
Fig.

2(b)
which mirrors the code’s ideas and structure, while being more concise (using about half as many characters) and easier to read (English versus code). The compact nature of the outline would also reduce scrolling when browsing through the file. If one wishes to see more details or reference the code “source of truth,” the outline may also be displayed as comments or annotations interleaved with the code in the style of
literate programming

(
Knuth, 1984
)
, as shown in
Fig.

2(c)
. In this format, the outline provides visual structure and allows the reader to seamlessly switch between reading NL or code syntax as needed. Some developers already write these kinds of comments manually,
even despite the risks that they might become stale and are time-consuming to maintain (but
Section

3
offers solutions for both),
adding to the familiarity of NL outlines as a concept.

But with recent advancements in large language models (LLMs), there is little need for developers to write NL outlines manually, as modern LLMs can generate high-quality NL outlines even for proprietary code outside their training data (
Section

5
). Thus, we propose that NL outlines can be used as a means to provide AI
assistance
to developers, with many use cases illustrated in
Fig.

1
and further discussed in
Section

3
. NL outlines are designed to
improve developer efficiency
for code authors, maintainers, and users.

NL outlines serve a very different purpose than existing automatic code summarization techniques (see
Section

8
).
Compared to generating a
docstring
which describes a function’s contract for API users
(
Goodger and van Rossum, 2001
)
,
an NL outline instead summarizes a function’s implementation for developers maintaining or extending it.
Even though NL outlines can be displayed alongside the code like
inline comments
(
Fig.

2(c)
), they differ in content and design. Typical inline comments contain sparse notes about design rationales, subtle pitfalls, and remaining tasks
(
Pascarella and Bacchelli, 2017
;
Reuveni and Bourrillion, 2017
)
, but
Scalabrino et al. (2017)
found that such comments are not correlated with perceived or actual understanding of code. In contrast, NL outlines focus on boosting high-level understanding of the code, are overwhelmingly rated as “Very helpful” or “Extremely helpful” (
Figs.

5
and
7
), and are designed to provide a complete overview even when shown without code (
Fig.

2(b)
, e.g., in a code search UI).

App.

B
has further discussion including a taxonomy of different forms of code explanation.

NL outlines are
not
intended to do any of the following: document all details about the code (providing too much information would reduce efficiency), educate developers about concepts or APIs (developers can look up tutorials or documentation elsewhere as needed), provide complex reasoning (some comments are too important or complex to relegate to AI, including documentation of tricky implementation or design details), or replace code entirely (code remains the source of truth considering the ambiguity of NL).

3.
Use Cases for NL Outlines

The broad applicability of NL outlines is a key factor in their appeal as a surface for human-AI interaction. Here we provide an overview of many potential use cases as illustrated in
Fig.

1
. A full evaluation of each use case is beyond the scope of this paper—instead,
Section

Section

Code understanding and navigation.

Fig.

3

Outlines can also be shown in the main editor interleaved with the code, assisting with rapid code understanding and offering intuitive code folding
(
Fowkes et al., 2017
)
. The user experience can be enhanced through customization of outline styling, and IDE shortcuts can show or hide outlines, generate new outlines, convert between outlines and comments, and jump to adjacent outline statements. NL outlines can be similarly displayed in other developer tools for code browsing, searching, and so on.

Code maintenance.
Once the user is accustomed to using NL outlines interleaved with code as in
Fig.

3
, we can apply NL outlines beyond static (unchanging) code and toward code maintenance.

For example, the IDE can detect when the user is editing a function. When there is a lull in typing, the IDE may automatically update the outline to reflect the current code. (This can be done by providing an LLM with the old code, old outline, and current code, and prompting the LLM to predict an updated outline.)
Some users may prefer that outlines are updated automatically with minimal friction, while others might explicitly request an outline update through a keyboard shortcut and review a diff of the predicted changes. Either way, this use case resolves a common issue of comments becoming stale as the code evolves
(
Panthaplackel et al., 2020
;
Wen et al., 2019
)
, lifting the burden of tedious updates (and constantly checking if any comments need updating) from the user and delegating it to the LLM. Hence, NL outlines can serve as
automatic living documentation
of the code.

We can also perform updates in the reverse direction. If NL outlines are themselves editable by the user, then the user may specify the high-level idea of a code change simply by editing the outline, letting the LLM predict the corresponding code changes.
This concept is quite flexible: edit an outline statement to convey a minor logic change in that portion of the code, add new outline statements to guide a multi-line suggestion of new code, reorder outline statements (potentially outside the function’s boundaries) for a refactoring that handles dataflow dependencies better than mere copy/paste, and delete outline statements for a code cleanup that also removes resulting dead code elsewhere.
This would allow developers to
program primarily through natural language
, as if developing high-level pseudocode that is automatically synced to real code (but we still encourage careful review of the LLM’s code).

We can actually generalize the two previous ideas (where the user makes a
complete
edit to the code
or
outline, and the LLM only updates the other to match). Instead, we can let the user
start any change(s)
(to the code or outline) and have the LLM
finish the change(s)
(modifying the code and outline as needed). Many code changes start with one key idea and then require propagating changes to code and documentation elsewhere. With this feature, the user only needs to specify the main idea of each desired change, and the LLM can perform the more tedious work of implementing and propagating the change. This may increase developer efficiency by allowing them to think at a higher level of abstraction and delegating the lesser details (with careful review). The user can edit the outline for broad ideas or edit the code to specify more exact changes, seamlessly switching between code and NL as needed, as in the literate programming paradigm but with a novel bidirectional connection between NL and code powered by modern LLMs.

We built this into a prototype
Finish Changes
feature in an IDE by providing the old code, old outline, current code, and current outline to an LLM which then predicts the new code and new outline.
Fig.

4
shows screenshots with real predictions from Gemini 1.5 Flash.
In
Fig.

4(a)
, editing a variable assignment causes updates to its description in the outline and its type throughout the code. In
Fig.

4(b)
, replacing one word in the outline causes a multi-line implementation change and a docstring update.
Chain-of-thought (CoT) prompting
(
Wei et al., 2022
)
is quite effective here, where the LLM lists the user’s changes, reasons about further edits to finish those changes, and lastly predicts the new code with new outline interleaved.

Code generation.
The standard approach to function generation is to take a specification (e.g., the function signature and docstring) and predict the entire body, but it can be difficult to understand incorrect or unexpected predictions. The user might even discover that the prediction is so wrong that they delete it and start over, having wasted their time completely.

Instead, as previously mentioned, users can write new outline statements to steer code generation using a
Finish Changes
feature. But when writing an entire new function, we can further assist users by having the LLM
propose
an NL outline (displayed without code) for the user to approve before proceeding—an easier task than writing an outline from scratch or reviewing predicted code directly
(
Liu et al., 2023
)
. The LLM may also predict multiple outlines with different approaches or interpretations for the user to brainstorm with.
The user may edit an outline to correct mistakes instead of debugging the code later. By having the LLM generate code aligned with a user-approved outline, we increase the likelihood that the code satisfies the user, and it is also easier for the user to interpret the code because they already expect the outlined approach.

Code review.
During code review, a key part of software development
(
Bacchelli and Bird, 2013
;
Sadowski et al., 2018
)
, NL outlines can help reviewers understand code written by others. For example, if NL outlines are automatically updated to reflect code changes, then the outline changes form an NL summary of the code changes. Reviewers may then inspect a diff of the old versus new outlines in addition to the code diff.

Code search.
Code search systems in practice mainly use structured forms of search
(
GOO, [n. d.]
;
Sadowski et al., 2015
)
, but users sometimes do not know the needed keyword or regex. NL outlines may enable or enhance more intuitive text-based search:
after generating and indexing NL outlines, a search query containing NL and/or regexes could be matched to outlines and/or code. Users could then search for
concepts
, e.g., to find usage examples or where a particular action occurs in an application. NL outlines can also provide helpful context around search results, whether for NL queries, traditional regex queries, or even symbol references and function call sites.

4.
Outline Generation

We can generate NL outlines by few-shot prompting an LLM, but different prompting techniques have different benefits.

Interleaved Generation.
The most straightforward way to generate NL outlines is to provide an LLM with the code to be outlined, prompting it to repeat the code with outline comments added but without any other code changes. This is more effective with prompt instructions describing the purpose of NL outlines and their desirable qualities, and with few-shot examples demonstrating the task and what good NL outlines look like. We call this approach
Interleaved Generation
because the model predicts an outline interleaved with the code. However, a notable downside of this approach is the possibility that the model changes the code against our wishes. If the model’s prediction significantly deviates from the original code, the outline might not describe the original code anymore. Minor deviations (e.g., changes to blank lines and existing comments are common) can be ignored if the model gets back on track, but in extreme cases the outline must be discarded.

This issue can be remedied with the
Constrained Generation
approach, using constrained decoding
(
Koo et al., 2024
;
Willard and Louf, 2023
)
to alter token probabilities in a way that prevents changing the code. Specifically, we construct a regex-like constraint that repeats the code exactly, except with optional comment lines between code lines.
App.

D
discusses additional heuristics and implementation difficulties.

Line Number Infilling.
A drawback shared by Interleaved Generation and Constrained Generation is that they spend output tokens repeating the code, leading to unnecessary cost and latency.
We design a solution called
Line Number Infilling
: we prepend each line of the original code with its line number, and we prompt the model to output a sequence of outline statements, each containing the line number where the outline statement should be added, and the text of the statement itself. For example, the original code “
def sq(x):\n return x**2
” is given to the model as “
1|def sq(x):\n2| return x**2
”, and the model may respond with “
2|Squares the input.
” (using multiple lines for multiple outline statements). This prediction task is similar to fill-in-the-middle (FiM) in language modeling
(
Donahue et al., 2020
;
Bavarian et al., 2022
;
Tay et al., 2023
)
, where the LLM must predict text (like outline statements) to insert at specially-marked locations (like the line numbers), although in our case the LLM must also choose which locations to insert at. Since this response format does not involve code tokens at all, we resolve the prior problems of changing the original code or spending tokens to repeat the code. The prompt is also shorter because the few-shot examples do not repeat the code either. In practice, we observe that Line Number Infilling provides a
4\times
to
5\times
speedup over Interleaved Generation. However, Line Number Infilling has a downside that the prediction format is less natural for LLMs, i.e., “code with comments” is more similar to the training data than “line numbers and summaries.” Hence, this approach can cause weaker LLMs to generate outlines with formatting mistakes, misplaced statements, or generally worse quality.

has suggestions for further research to improve outline generation, e.g., retrieval-augmented generation
(

;
Gao et al., 2023
;
Nashid et al., 2023
;

)
, few-shot selection
(
Gao et al., 2021
;

)
, and finetuning
(

6.1.
Android Security

We consider the problem of assessing the security and privacy of Android applications (or apps). These assessments are performed routinely by online app stores such as Google Play and Samsung Galaxy Store, where apps submitted by developers across the world are analyzed for compliance with
policies
6
6

6

Google Play’s policies are at
https://play.google/developer-content-policy/

Apps that are deceptive, malicious, or intended to abuse or misuse any network, device, or personal data are strictly prohibited.

Determining whether an app is deceptive or malicious involves understanding the code and relating its functionality to the app’s description, UI, and user expectations.
There are millions of apps in stores and tens of thousands of new apps added per month, so security assessments must be efficient.

To detect malicious apps, reverse engineers (REs) use static and dynamic program analyses to flag code as potentially problematic and then confirm violations through manual review. The initial challenge is in the volume of code: many apps have millions of lines of code, thousands of classes, and complex event-driven execution paths. Furthermore, an app’s source code is usually not available, so REs inspect
decompiled code
which is difficult to understand for several reasons. Decompiled app code is unnatural due to the compilation process performing optimizations (e.g., inlining code and changing code structure) and removing code artifacts (e.g., comments, docstrings, types, variable names, and names of inlined API constants). App code may be further transformed by minification to reduce app size
(
PRO, [n. d.]

and obfuscation to protect intellectual property
(
DEX, [n. d.]
)

Applying NL outlines.
We collected a dataset of 80 decompiled functions from real Android apps. Half were manually curated “suspicious” functions that REs had previously flagged as using malware techniques, and we focused on including a variety of techniques and avoiding similar code. All dataset functions have between 24 and 99 lines of code, and we tried to make the two halves of the dataset have similar distributions in code length and style (minified or obfuscated) as much as reasonably possible to reduce bias.

6.2.
Code Review

This application is motivated by a common pain-point in code review: the
difficulty in reviewing large or complex change lists (CLs). With increasing CL complexity, it becomes increasingly difficult to maintain a complete mental model of all of the changes and how they interact. This software development anti-pattern is so substantial that code reviewers may even send large CLs back to the authors to be split into smaller CLs that are individually more manageable. Reviewers actually spend much less time per line reviewing large CLs, raising potential concerns about fatigue and review quality. Although tools have been developed to assist in moving code changes between CLs, actually splitting a CL is time-consuming, and in some cases it might not be possible if the changes are particularly entangled. So, the burden often falls on the reviewer to mentally disentangle messy CLs during code review.

We address this with a prototype feature called
Virtual CL Split
, which is a layer in an existing code review interface that allows a reviewer to view individual code changes grouped into logical topics. Each topic is described with a natural language phrase that helps the reviewer interpret the changes. The topics form a partition of the original CL, but this splitting is done
virtually
, i.e., the CL itself is unchanged and there is no requirement that any individual topic can become a standalone CL. Upon selecting a topic in the UI, all changes in that topic have their code diffs expanded and other changes are collapsed (or shown with muted diff highlighting when the reviewer wants to see more file context), so that the reviewer can focus on the selected topic to simplify their mental stack. Virtual Split ensures that every code change appears in some topic, so that the reviewer is “done” after examining all topics.

App.

I
shows screenshots of the Virtual Split feature on an example CL.

For example, consider a CL where the author first performed a refactoring causing multiple small changes. This enabled the author to implement a complex new function and add unit tests for it. Finally, the author invoked a code formatting tool causing whitespace changes.
In this CL, a Virtual CL Split may suggest 3 topics: first the new function with its tests, then the refactoring, and lastly the whitespace changes. The first topic enables the reviewer to inspect the new function and its tests
together
(without unnecessary searching or scrolling even though they come from different files), and the topic description summarizes the new functionality. This is the most important part of the CL, so it is shown first to improve review quality
(
Bagirov et al., 2023
)
. Afterward, the second topic helps the reviewer inspect the refactoring without distraction from whitespace changes, which are in the last and least important topic.

To generate a Virtual Split, we first provide the CL description and all file diffs (in unified format) to an LLM to generate a list of topics with few-shot prompting. Then, for each file in parallel, we provide the CL description, the diff with line numbers prepended, and the list of topics. With few-shot prompting, the LLM generates an NL outline of the diff using the Line Number Infilling technique, except that the NL outline partitions and describes code changes (instead of code functionality), and for each diff section, the model also predicts which topic it belongs to. The resulting diff section boundaries and topic assignments thus form the Virtual Split. We highlight that this is an example of how NL outlines can serve as a foundation for features with very different objectives and UX.

Evaluation.
In a preliminary market fit study, we worked with four software engineers from the same team to evaluate how often CLs are
complex enough
to benefit from virtual splitting, and how often the predicted splits were
useful
. We randomly selected 73 CLs submitted in their team over the prior weeks with more than 10 lines changed. Many of these were too simple for virtual splitting to be helpful, including CLs that were still very short, CLs which cannot reasonably be split further, and CLs with mostly deletions, generated files, or rollbacks. Overall,
24
(
33\%
) of the CLs were deemed
complex enough
for a virtual split to be helpful. At the scale of a large software company, this is a huge opportunity to help reviewers facing complex CLs.
We generated virtual splits, and among the
24

14

58\%

useful

We also observed the pattern that, if the CL is complex enough and the split was rated as
high-quality
(i.e., changes were correctly assigned to topics), then the split was almost always considered
useful
, indicating that the concept is well-designed.

After the preliminary study, we improved split quality via prompting improvements, e.g., summarizing each diff as chain-of-thought reasoning
before generating topics,
better utilizing Gemini’s long context,
providing “hints” of line numbers where blocks of changes start, and adjusting few-shot examples and instructions. In a small experiment on 10 CLs, these changes noticeably improved split quality for 7 CLs and only decreased quality for 1.
We also used a newer LLM and made other UX and infrastructure improvements, and launched the feature to a beta group of about 7000 users
on live code review traffic.
Examples of positive user feedback include:

“Is this a new feature? It seems to parse the CL description, breaks it down into small individual tasks/features and then only shows the relevant diffs. This is amazing :mind-blown:”

“Because the CL was split into 3 tasks, it was easier for me to understand the change step by step.”

“It makes it a lot easier to review related changes across multiple files. Without this feature, I have to go back and forth between files a lot more especially for large CLs.”

“I saw a CL getting split up into topics in Critique. Simply beautiful… It’s already saved me time in code reviews :)”

Negative feedback mainly expressed that the CL was already simple enough to be easily understood without a split, so we are working to better detect these cases preemptively.

7.
Discussion

We discuss practical considerations that arise when integrating NL outlines at scale, ways to improve outline generation, using outlines within LLM pipelines, and limitations.

Verifying outlines.
When paired with feedback mechanisms, NL outlines can become a resource shared across developers. For example, thumbs up/down feedback can be collected, and with sufficient thumbs down, an outline may be hidden or regenerated. Enough thumbs up can cause an outline to become “verified” and displayed in a special way (e.g., with a checkmark) signaling that this outline has approval from other humans. Trusted developers such as code authors, code reviewers, and project leads may be given outsized power to influence outlines, e.g., unilaterally marking an outline as verified. Trusted developers may also be allowed to edit outlines to correct mistakes (with the edits shown to everyone else), increasing the quality of outlines and users’ confidence in them.

However, verifying NL outlines takes time and effort, which must be considered alongside the quality and confidence benefits of having verified outlines. We emphasize a philosophy of making things easier for developers in the long run. NL outlines as a concept may be more or less helpful for different teams, depending on what they do (e.g., writing new code versus maintaining existing code, or building standalone projects versus frameworks with users), the technology and concepts used (e.g., custom APIs that confuse the LLM), and simply personal preference of team members. A team may reasonably decide that reviewing NL outlines should be completely optional. Ultimately, developers should not be given more work that they think is not worthwhile. We also emphasize that the code is the source of truth: it is what the computer runs, and NL is inherently ambiguous. Further research is needed to measure the perceived and actual benefits of NL outlines used at scale in the various ways proposed, which should then guide decisions around tooling, UX design, and team culture.

Comments or metadata?
When building NL outlines into prototype IDE features, we encountered a major implementation decision: should outlines be stored in the source code as comments with a special syntax, or as non-code metadata that is stored and manipulated separately from code? We discuss these options from the perspective of a large software company.

Storing outlines as non-code metadata has drawbacks mainly in the difficulty of implementation: the metadata files or databases must be managed, each developer tool would need to load or edit the metadata in addition to source code and have a custom UI layer to support displaying or editing outlines, and implementation differences may reduce portability and compatibility.

Alternatively, if NL outlines are to be inserted into code as comments, then they should use a special syntax to distinguish them from other comments, so that readers can treat AI-generated comments with appropriate caution. We propose the
star comment
syntax as in
Fig.

2(c)
. This is simply a regular line comment but with an asterisk after the comment syntax, e.g.,

#*

or

//*

for most common programming languages.
12
12

12

A star comment

//*

should not be confused with a multi-line comment

/* … */

. Syntax highlighting can help differentiate the two.
The asterisk is chosen to mimic the stars commonly found in AI-related icons such as for Gemini and GPT-4, while being ASCII and standard on keyboards (hence compatible with code).
Verified
outlines may be shown with syntax like

#*!

indicating that the comment is more trustworthy. Programmers and developer tools should follow two basic rules about star comments: (1) Star comments are usually AI-generated and should be trusted cautiously, and (2) It is expected that star comments may be changed, added, or removed by AI tools.

Adding NL outlines into code as star comments leads to a relatively simple integration of NL outlines into developer tooling. There is no need to update programming language parsers because star comments are already comments, and similarly no need for metadata outside the source code file. By default, IDEs and other developer tools would display star comments in the same way as regular comments except distinguished by the asterisk, but it would also be simple to adjust their syntax highlighting. Star comments are maximally portable because the syntax is not specific to any developer tool or implementation. Users can add, remove, or edit star comments in the same way as editing other code. Users can also convert between normal comments and star comments by adding or deleting the star to allow or prevent AI updates to that comment. IDEs may offer keyboard shortcuts to perform some of these actions. However, star comments have important downsides in churn, flexibility, and distraction, discussed in more detail in

Improving outlines.
In this work, we generate NL outlines of a function
f
only from
f
’s code and few-shot examples, but providing more context through retrieval-augmented generation (RAG)
(
Lewis et al., 2020
;
Gao et al., 2023
;
Nashid et al., 2023
)
may improve the predicted outline’s quality. For example, one may provide the LLM with the file containing
f
, unit tests for
f
, functions that call or are called by
f
, and even design documents describing the need for
f
. Similarly, few-shot selection
(
Gao et al., 2021
;
An et al., 2023
)
can choose few-shot examples that are the most similar to
f
, e.g., considering the programming language, kind of function (unit tests, instance methods, etc.), and so on.

Finetuning is another technique to improve outline generation quality, using data collected through various means. One can mine outline-like comments from existing code, but many such comments are low-quality or incomplete (i.e., only part of the function is outlined), and we found it difficult to detect such cases at scale. Another approach is to sample outlines and keep those that score well on LLM-based evaluation metrics
(
Kahng et al., 2024
;
Allamanis et al., 2024
)
, but this approach is limited by the model’s ability to generate a good outline in the first place. A promising direction could be to use real feedback gathered from NL outlines integrated into developer tooling, such as thumbs up or down, accepted or rejected outline predictions, and user edits to outlines. These would enable the outline-generation system to learn and improve from human feedback (RLHF)
(
Christiano et al., 2017
;
Bai et al., 2022
;
Kaufmann et al., 2023
)
.

Helping LLMs.

Sections

5
and
6.1
show that NL outlines are very helpful to humans—can they also help LLMs? Indeed, NL outlines as an intermediate step can potentially improve LLM performance on downstream code-related tasks. For example, the case study in
Section

6.2
generates outlines to summarize code changes in individual files, so that a subsequent prompt can reason about a multi-file change without being overwhelmed. Similarly,
App.

K

Limitations.
In
Section

5
we used 6 survey participants, and in
Section

6.2
we used 4 participants from one team, so those findings may be specific to those participants. As described in
Section

5
, the 30 dataset functions were not sampled uniformly. In practice, many functions are boilerplate, very short or simple, or otherwise less interesting, making it less likely that a developer would read an NL outline for that function anyway. Instead, we focused on dataset
variety
and choosing
interesting
functions (and only in Python which is our expertise). Our choice of functions can introduce bias.

9.
Conclusion

Natural language outlines
are a new form of code explanation that summarize the main ideas for rapid understanding. Our experiments show that LLMs can generate accurate and helpful NL outlines in practice. We describe the huge potential to use NL outlines to assist software developers in numerous ways, and we call for further research to advance these transformational ideas.

Taxonomy of Code Explanation

NL outlines are a novel way of explaining code
with different benefits and drawbacks
compared to other types of code explanation like docstrings and tutorials.
To clarify the distinctions, we can classify types of code explanations by:

(1)

Topic:
It may primarily explain the
interface
of some code, its
implementation
, the
design
decisions it required, details of
APIs and concepts
involved, etc.

(2)

Audience:
The target readers could be
novice
programmers,
experienced
developers,
maintainers
of the code,
users
of an API,
project managers
, etc.

(3)

Location:
Explanations can occur
within code
like names and inline comments, in a separate
document
like a design document or bug report, within
developer tools
like IDEs or code search interfaces, in
Web sites
like Javadocs,
ephemerally
in conversation with an LLM chatbot, etc.

(4)

Length:
Effective explanations can be as short as a
single symbol
like a well chosen method name, or much longer like a
sentence
,
paragraph
, or even a
book
.

NL outlines occupy a particular space within this taxonomy. In terms of topic, NL outlines focus on the implementation strategy: the high-level steps taken to achieve the function’s goal. The audience comprises experienced developers who wish to write, maintain, or build upon the code. NL outlines would primarily be shown within code and in developer tools. Finally, an outline is a list of sentence-length statements which in total are much shorter than the code they describe.

This helps distinguish NL outlines from other forms of code explanation. For example, docstrings focus on the contract of a function and its usage instead of the implementation
(
Goodger and van Rossum, 2001
)
, and are more often read by API users than code maintainers. Pseudocode is more literal than NL outlines (e.g., explicitly providing every variable update instead of abstracting out the broad concepts) and usually appears in textbooks
(
Cormen et al., 2009
)
and rarely in professional software projects. LLM explanations also vary widely depending on the user’s prompt
(
Nam et al., 2024
)
, but they are often ephemeral and long explanations going into great detail to help novices and developers unfamiliar with the concepts involved, unlike the concise format of NL outlines which persist in the code or developer tooling. Design documents are a longer form of code explanation, aiming to describe a software architecture including constraints on the design and alternatives that were considered
(
Ernst, N.A. and Robillard, M.P., 2023
)
, ultimately presenting a different set of information for a different audience (e.g., project managers) compared to NL outlines.

At first glance, NL outlines may seem similar to inline code comments, especially because NL outlines may be
displayed
like comments.
Interestingly,
Scalabrino et al. (2017)
measured how code understandability correlates to various metrics including the presence of comments, but ultimately obtained a negative result: the number of comments was not correlated with perceived or actual understanding. We take this as evidence that the style of comments typically written by developers is not optimized for code understanding—developers usually write sporadic comments about pitfalls, developer intent, and reminders for future work
(
Pascarella and Bacchelli, 2017
;
Reuveni and Bourrillion, 2017
)
, without summarizing the functionality more completely. In contrast, our NL outlines focus on the high-level ideas in the function’s implementation, are written in a way that still makes sense when presented without code, and are designed to boost code understanding (e.g., overwhelmingly rated as “Very helpful” or “Extremely helpful” in
Figs.

5
and
7
).

Section

3
describes using NL outlines for code maintenance, in particular suggesting a
Finish Changes
feature which allows the LLM to finish any changes the user has made to the code or outline.
Fig.

4
illustrates two example usages of the
Finish Changes
feature, each involving one conceptual edit. But actually, Gemini 1.5 Flash is powerful enough to handle multiple changes at once:
Fig.

8
shows a successful implementation of three simultaneous changes.

In our experience, the
Finish Changes
feature with Gemini 1.5 Flash can suggest surprisingly good edits, but it is not always perfect. The likelihood of slight mistakes tends to increase with more changes requested simultaneously, or if one change requires propagating many different kinds of edits to different locations. We observed that the most common mistake is an incomplete propagation of changes that lacks some necessary downstream edit. But, this also means that most of the suggested changes are on the right track.

Gemini 1.5 Flash occasionally suggests an “improvement” that is not strictly needed to finish the user’s changes, such as adding more detail to a docstring which was not made stale in the first place. The actual suggestions are usually very reasonable, but this behavior may be distracting to users.

We chose to explore the
Finish Changes
feature with Gemini 1.5 Flash due to its low latency—we receive predicted diffs in about 5 seconds, allowing developers to iterate on
code quickly
.

Appendix D
Constrained Generation

Recall from
Section

4
that Interleaved Generation has the drawback of potentially changing the code against our wishes, resulting in predicted outlines that no longer apply to the original code. Our Constrained Generation approach resolves this issue by using constrained decoding
(
Koo et al., 2024
;
Willard and Louf, 2023
)
: we construct a regex-like constraint that forces the model to repeat the code exactly, except with optional comment lines between code lines. If the original code parses, we can also require an outline statement before the first line of the function body (after the function signature and docstring) and prevent outline statements from being added above a blank line or in the middle of a multi-line statement or comment block. These extra heuristics help ensure that outline statements are placed appropriately. We found that constraints with these heuristics are broad enough to permit all “ground-truth” outlines that we hand-wrote for prompting and experimentation, while being precise enough to avoid almost all formatting mistakes from Interleaved Generation. However, the downside of Constrained Generation is in the implementation and portability: only certain LLMs work with certain constrained decoding APIs, and some constrained decoding engines only support constraints up to a maximum size which limits the length of functions we can outline (but a workaround to these constraint size limitations is to use a sequence of constrained decodings, each continuing where the previous one left off).

Appendix F
Errors when Parsing Outline Predictions

Sections

5
and
1
mention errors detected while parsing an LLM’s outline predictions. Here we provide more details about the specific errors and their frequency.

Here is a list of all errors we checked for when parsing an outline prediction using the Interleaved Generation technique, including the severity (major or minor), the frequency in the experiment (number of LLM predictions where the error occurred, out of 150 predictions considering the 5 models and 30 functions), a description of the error’s meaning, and what we do when encountering the error:

•

Extra blank line (minor, 19 predictions)
: When performing a top-down line-by-line comparison of the predicted code with outline versus the original code (i.e., searching for added comments which form the interleaved outline), we encounter a blank line in the prediction where the corresponding line in the original code is not blank (lines containing only whitespace are also considered blank). We simply skip the blank line in the prediction, as if it did not exist.

•

Missing blank line (minor, 7)
: When performing the same line-by-line comparison as described above, we encounter a blank line in the original code where the corresponding line in the prediction is not blank. We similarly skip this line in the original code, as if the prediction did contain a matching blank line.

•

Consecutive comment (major, 0)
: We encounter multiple consecutive comment lines present in the prediction but not in the original code. We concatenate the text of the comments into one outline statement, just in case the model decided to split a long comment onto multiple lines, but the long comment length likely indicates poor quality.

•

Missing comment (minor, 20)
: We encounter a comment line in the original code where the prediction does not have a corresponding match. We simply skip this line in the original code, as if the prediction did contain a matching comment.

•

Changed trailing comment (minor, 1)
: We encounter corresponding lines in the prediction and original code that do not match, and neither is a blank line or comment line, and they
do
match if we ignore trailing comments. We simply move on, as if the prediction’s trailing comment did match the original code’s trailing comment (if any).

•

Changed code (major, 10)
: We encounter corresponding lines in the prediction and original code that do not match, and none of the prior cases apply. We stop processing the prediction and return any outline statements already parsed, because any further outline statements are for predicted code that has deviated significantly from the original code.

•

Extra prediction lines (minor, 0)
: We matched all lines in the original code to corresponding lines in the prediction, but the prediction still has unmatched lines remaining. We ignore those lines, as if the prediction stopped in accordance with the original code.

•

Missing prediction lines (major, 0)
: We matched all lines in the prediction to corresponding lines in the original code, but the original code still has unmatched lines remaining. The predicted outline is likely incomplete since the prediction stopped early, but there is not much we can do about it (without another LLM query).

•

Empty outline (major, 2)
: After the parsing process, the outline contains zero outline statements. This is clearly a poor prediction, but there is not much we can do about it.

Although the Constrained Generation technique is not used in our experiments (
Section

5
), its predictions are formatted like those for Interleaved Generation. Hence, we use the same procedure to parse the LLM predictions and detect errors (although some are no longer possible due to the constraints).

Here is an analogous list of errors we checked for when using the Line Number Infilling technique:

•

Malformed line (major, 1 prediction)
: The prediction line does not follow the expected format of line number, separator, and outline statement. We skip this line.

•

Line number out of bounds (major, 0)
: The line number is smaller than 1 or greater than the number of lines in the original code. We skip this line.

•

Not sorted (minor, 0)
: The prediction lines were not sorted by line number in ascending order. We sort the lines.

•

Duplicate line number (major, 0)
: The prediction contained multiple lines with the same line number. We keep the first instance and ignore the latter duplicates.

•

Commented empty line (minor, 6)
: A line number actually points to a blank line in the original code. Since it is unnatural to add a comment above a blank line (the blank line should go above the comment, which is then directly above its section of code), we increase the line number such that the outline statement is placed above the next non-empty line.

•

Empty outline (major, 0)
: After the parsing process, the outline contains zero outline statements. This is clearly a poor prediction, but there is not much we can do about it.

Appendix G
Quality Survey Questions

Section

5
and
Fig.

5
refer to a survey we used to gather human opinions about NL outline quality. In total, we obtained
300
outline predictions:
30
functions in the dataset
\times

5
LLMs
\times

2
generation techniques. For each function, we asked the contributor of that function to inspect the function’s
10
predicted outlines, which were presented in shuffled order without any labeling of which LLM or technique produced that outline. For each outline, the function contributor answered five survey questions with multiple-choice answers, listed below. Survey participants were also given a document containing clarifications to the questions, also listed below.

(1)

How good is the outline
overall
, relative to an optimal outline for this function?

\rightarrow
Excellent / Good / Acceptable / Bad / Terrible

•

This question measures the room for improvement in the LLM predictions.

•

Don’t judge the broad concept of NL Outlines, or that outlines may be fundamentally less useful for certain kinds of functions. Instead, judge the outline sample relative to the best outline you can think of for that function. How close is this outline to being the
best it can be
for that function?

•

The factors in the other questions (helpfulness, correctness, detail, style/fluency) may factor into your judgment for this question. How much to consider each factor is up to you, so that you can judge the outline holistically.

•

As a point of reference, a completely empty outline should be considered “Bad”. Note that a “Terrible” outline can be worse than this, if it ends up being a big waste of time (e.g., a lot of words that are obviously nonsense, or a convincing but incorrect outline that leads to future bugs).

(2)

How
helpful
would this outline be in practice?

\rightarrow
Very helpful / Somewhat helpful / Not helpful

•

This question measures the practical utility of the outline, relative to the baseline of not having outlines at all.

•

How helpful would this outline be to developers in general, including the code author and other developers who may have varying amounts of familiarity with the code?

•

Consider the purpose of NL Outlines and multiple potential use-cases, as described above.

•

You may consider that some functions (e.g., very simple functions) might naturally benefit less from outlines.

•

Assume that readers of the outline understand that it is AI-generated and may be incorrect, and they act reasonably with that understanding. The amount of trust they have in the outline may depend on how convincing the outline seems, within reason.

(3)

Is the outline factually
correct
?

\rightarrow
Completely correct / Mostly correct / Incorrect

•

Does the outline say factually correct things?

•

Use your expertise of the function and its context within the broader project.

•

It is not necessary to be 100% perfect here. Think about how you would summarize the function to a colleague to help them gain an initial high-level understanding. You don’t want to confuse your colleague with misinformation, but if some detail would take a paragraph to fully hash out, you’d likely do your best to give a “good enough” explanation instead, striking a balance between exhaustive correctness and efficient explanation.

•

Omitting important information is primarily a “Needs more detail” issue (for the question below), but it may also affect this correctness question if the missing information leaves the reader with a factual misunderstanding (like “lying by omission”).

(4)

Does the outline have the right
amount of detail
?

\rightarrow
Right amount of detail / Needs more detail / Too much detail

•

Does the outline help you (the author
or other developers
) understand the code
more quickly
? Omitting important details, or including too many details, can both slow down understanding.

•

Use your expertise of the function and how it plays a role in the larger project, to determine which details are important enough to say. What should another developer know if they wanted to find a bug or implement a new feature, in this function or a related one?

•

It is possible for an outline to simultaneously include unnecessary details, while also missing important details. In this case, choose “Needs more detail” or “Too much detail” depending on which is the bigger problem for this outline.

(5)

How is the outline’s
style and fluency
? Consider formatting, grammar, tone, clarity, etc.

\rightarrow
Excellent / Good / Bad

•

Is the language clear or ambiguous? Is the outline easy to misunderstand?

•

Are you distracted by awkward phrasing or grammatical errors?

•

Are the outline statements placed correctly? If a statement is slightly misplaced, that doesn’t necessarily impact the factual correctness or amount of detail, but should be considered here.

•

Some predictions may seem unnaturally cut off. Indeed this may happen if the model’s prediction becomes malformed somehow. That kind of issue should be reflected here, and in the other questions as appropriate.

Appendix J
Drawbacks to Star Comments

Star comments, proposed in
Section

7
, have important downsides in churn, flexibility, and distraction.

Churn:
Source code is expensive to store and edit considering the costs of version-controlled storage forever, the human cost of code review, and extra strain on continuous testing infrastructure.
13
13

13

Adding comments can unfortunately cause tests to fail. Detecting and fixing these issues across a large codebase is a real cost.
Putting all iterations of NL outlines (which change alongside the code or through LLM upgrades or experimentation) into source code is thus surprisingly expensive. Alternatively, storing NL outlines as non-code metadata in a central database or in extra files adjacent to the source code (but without version control, mandatory code review, or continuous testing) would significantly reduce churn.

Flexibility:
Star comments reduce the flexibility to update outlines without causing more churn. Even if the code is not changed, it may still be desirable to update or deprecate outlines due to prompting improvements, LLM upgrades, or human-provided feedback, and to perform A/B experiments providing users with different outlines. These would be straightforward with outlines stored as non-code metadata, but with star comments, updates are expensive due to churn and A/B experiments are impossible.

Distraction:
Star comments in the code are by default visible, like any other code. This may be distracting to users who suddenly see outlines in developer tooling that does not yet support enough outline-related features to make them worthwhile. Developers need the ability to hide outlines at times, so this functionality must be built into various tooling at the outset. Alternatively, outlines as metadata would be hidden by default and can be gradually shown to users depending on their enthusiasm (e.g., beta testers) and the tooling readiness.

In our view, star comments may be used to explore using NL outlines in practice with a limited scope of users and files (e.g., a small team or small company), but outlines should be stored separately from code in the long term at large companies.

Appendix K
Generalizing Outlines to Files and Projects

This paper focuses on NL outlines for individual functions because code flow within a function is naturally structured: code flows from top down, excluding control flow jumps. This implies that adjacent code lines are likely to be semantically related, forming clusters of related lines. Hence, an NL outline is designed to
partition
the lines into those logical clusters.

This is no longer true at the level of a class or file, where code flow is less predictable without enforcement of an organized ordering of functions or classes within a file.
If
functions were well-organized, then it would be straightforward to partition them into semantic groups with outline statements, but it is less clear what should be done if the functions are not organized. Should the LLM suggest a reordering? That could help keep files more organized but could also confuse developers unaware of the reordering. Alternatively, we may create a file outline that is not aligned with the code (and thus cannot be shown interleaved with the code), e.g., an unordered mapping of functions to semantic groups. The list of symbols in a file (provided in an IDE sidebar) typically allows the user to sort the symbols by code position or alphabetically, and this idea may suggest a new semantically-grouped ordering where each group is summarized with an outline statement.

Outlining a project may mean generation of a README file that summarizes the main ideas, lists important directories and files and their purpose, and provides examples of usage or application flow. It may also include generated diagrams illustrating the user journeys, data flows, class hierarchies, and so on. The outline may incorporate human-written sections and could be automatically updated as the code evolves.

We imagine that outlining a file or project likely begins with generating NL outlines for functions first, and then using those for further LLM prompting, reasoning, abstraction, and summarization in a hierarchical manner, and combined with static or dynamic analyses where applicable. In this sense, NL outlines can be building blocks in complex LLM pipelines.
