LookAhead: Preventing DeFi Attacks via Unveiling Adversarial Contracts Conference: ; October 14–18, 2024; Salt Lake City, USA
Shoupeng Ren, Tianyu Tu, Jian Liu, Di Wu, Kui Ren

Abstract
. DeFi incidents stemming from various smart contract vulnerabilities have culminated in financial damages exceeding 3 billion USD. The attacks causing such incidents commonly commence with the deployment of adversarial contracts, subsequently leveraging these contracts to execute adversarial transactions that exploit vulnerabilities in victim contracts. Existing defense mechanisms leverage heuristic or machine learning algorithms to detect adversarial transactions, but they face significant challenges in detecting private adversarial transactions. Namely, attackers can send adversarial transactions directly to miners, evading visibility within the blockchain network and effectively bypassing the detection. In this paper, we propose a new direction for detecting DeFi attacks, i.e., detecting adversarial contracts instead of adversarial transactions, allowing us to proactively identify potential attack intentions, even if they employ private adversarial transactions. Specifically, we observe that most adversarial contracts follow a similar pattern, e.g., anonymous fund source, closed-source, frequent token-related function calls. Based on this observation, we build a machine learning classifier that can effectively distinguish adversarial contracts from benign ones. We build a dataset consists of features extracted from 269 adversarial contracts and 13,000 benign contracts. Based on this dataset, we evaluate different classifiers, the results of which show that our method for identifying DeFi adversarial contracts performs exceptionally well. For example, the F1-Score for LightGBM-based classifier is 0.9541, with a remarkably low false positive rate of only 0.15%.

2.
Background

In this section, we outline the required background to better understand our work.

2.1.
Ethereum

Blockchain is a distributed ledger built on a peer-to-peer (P2P) network, maintained through specific consensus mechanisms to ensure the consistency of the ledger. Ethereum
Wood 2014
is one of the most renowned blockchain platforms. It introduces Ethereum Virtual Machine (EVM) to support smart contracts and has spawned a series of EVM-compatible chains.

Account.
Accounts are entities that can hold Ether and send transactions. Ethereum has two types of accounts: External Owned Accounts (EOAs) and Contract Accounts (CAs). EOAs are controlled by users’ private keys, while CAs contain corresponding code and storage. Both types of accounts have their address, balance, and nonce. The address of an EOA is derived from the hash of the public key, whereas the address of a CA is usually related to its creator.

Transcation.
Ethereum is often regarded as a transaction-driven state machine, where transactions are initiated by EOA, signed, and ultimately update the Ethereum network’s state. After a transaction is sent, it’s first placed in the
mempool
, a transparent and publicly accessible pool filled with pending transactions, waiting for the block producer to select and finalize them.
Transactions are typically used for transferring Ether, invoking contracts, or creating contracts. In the case of contract deployment, the
to
field of the transaction is 0. During the execution of a normal transaction, interacted contracts may trigger additional message calls, commonly known as internal transactions.

Smart Contract.
From a high-level perspective, smart contracts can be viewed as instantiated objects stored on the blockchain and executed within the EVM. Due to the nature of blockchain, once deployed, the code within a smart contract cannot be changed. Smart contracts are typically written in high-level programming languages such as Solidity
Dannen 2017
. The source code is compiled to bytecode, which can be executed within the EVM. The EVM is a stack-based virtual machine that supports a set of Turing-complete instructions. Bytecode mainly consists of two parts, creation code and runtime code. Creation code is used for initialization (not deployed on the blockchain) and is executed only once. Runtime code is the primary code segment executed when the contract receives a message call.

2.2.
DeFi

DeFi is a financial ecosystem that operates on a blockchain network. It is built upon smart contracts and aims to provide traditional financial services in a more open and transparent manner. DeFi has also introduced some unique financial concepts, such as tokens, decentralized exchange, and flashloan.

The tokens.
There are numerous cryptocurrencies created by smart contracts on Ethereum, known as tokens. These tokens serve as the cornerstone of the DeFi ecosystem, facilitating the diversified development of applications and services within DeFi. Tokens come in two main types: fungible tokens and non-fungible tokens (NFT), which widely follow the ERC-20
17 17
and ERC-721
19 19
standards respectively. A token contract typically must implement a set of functions and events specified in these standards. Furthermore, Ether, which is used to reward contribution in the consensus, is also referred to as the native token.

Decentralized Exchange (DEX).
Similar to traditional markets, the cryptocurrency market depends on exchanges. But unlike centralized exchanges (CEX), DEX doesn’t require users to deposit digital assets into the exchange. Instead, it conducts asset transactions directly on the blockchain through smart contracts, ensuring transparency, security, and decentralization. The most prevalent DEXs
Adams et al. 2021
;
Martinelli & Mushegian 2019
utilize the Automated Market Maker (AMM) model, which relies on mathematical formulas to dynamically adjust the prices of digital assets, diverging from the traditional order book approach used in CEXs. In this model, the core contracts known as liquidity pools are funded by entities called liquidity providers, allowing users to continuously exchange assets.

Flashloan.
Flashloan is a unique form of cryptocurrency lending that leverages the atomic nature of the transaction, where a transaction is either fully executed or not executed at all, allowing users to borrow and repay cryptocurrency in one transaction. To utilize the flashloan, specific callback functions must be implemented in the borrowing smart contracts. Many DeFi protocols
2 2
;
Adams et al. 2021
;
14 14
currently provide flashloan function, offering everyone the opportunity to temporarily possess a large number of tokens with only a small fee. However, flashloan also facilitates numerous attacks
Cao et al. 2021
;
Qin et al. 2021
;
Wang et al. 2020
.

2.3.
Miner Extractable Value

Traditionally, miner determine the order of transactions in a block based on transaction fees. Since the mempool is publicly accessible, users have the ability to influence the placement of their transactions by adjusting the transaction fees, allowing for front-running
Eskandari et al. 2020
;
Torres & Camino 2021
or back-running. The value derived from manipulating the order of transactions within a block, beyond the standard block rewards and transaction fees, is referred to as Miner Extractable Value (MEV)
Daian et al. 2020
. It has been proven to have a significant impact on the security of blockchain networks
Qin et al. 2022
.

Front-running.
Front-running is a fundamental means used to extract MEV, typically employed in arbitrage, liquidation, and sandwich attack. Front-runners usually deploy a contract on the blockchain, akin to a virtual machine, capable of interpreting the input data of transactions. When the front-running bot detects a victim transaction that meets specific conditions, it constructs input data to execute the specific logic for profit. On the other hand, front-running has also been considered as a means in the intrusion prevention systems
Qin et al. 2023
;
Zhang et al. 2023
, attempting to frontrun adversarial transactions to prevent the attacks from occurring.

Private Service.
In response to MEV, researchers have proposed various countermeasures
Yang et al. 2022
. The MEV-auction solution introduced by Flashbots
22 22
gained popularity
Weintraub et al. 2022
. Users could utilize their service
Lyu et al. 2022
to send private transactions directly to miners, evading exposure in the mempool. However, private service providers like Flashbots on Ethereum and 48 club
1 1
on BSC, are also utilized by attackers to send private adversarial transactions, aiming bypass various detection effectively.

To utilize supervised machine learning algorithms for binary classification of smart contracts, distinguishing whether they are adversarial or not, we first collect both adversarial contracts used in DeFi incidents and benign contracts unrelated to attacks.

3.1.
Adversarial Contract

Data Sources.
To comprehensively collect adversarial contracts, we gathered information on DeFi incidents from various publicly available sources, such as repositories on GitHub that document historic DeFi attacks
13 13
;
25 25
, attack alerts posted by security companies
6 6
;
10 10
;
SlowMist 2018
. Subsequently, we undertake a meticulous manual review of these incidents to identify the adversarial contracts utilized by attackers. Additionally, We also conduct a thorough scrutiny of the transaction history of EOAs involved in these incidents, including the contract creators, callers, and associated transfer accounts, in order to identify any potentially overlooked attack incidents.

It should be noted that, because some attackers did not use private transactions to conceal their attacks, certain attacks have been executed by front-running bots. In response, we examined transactions that failed within the same block and subsequent blocks as the adversarial transaction, along with contract deployment in blocks preceding the attack block, aiming to trace back to the the initial adversarial contract deployed by the original attacker.

Scope and Exclusions.
Due to the contracts deployed by front-running bots do not contain actual vulnerability exploitation logic and therefore are not within the scope of our detection efforts. Furthermore, we observed that while attack incidents occurred on various blockchains, Ethereum and BSC accounted for the vast majority of the data we collected. To streamline further work, we focused on attack incidents from Ethereum and BSC.
Additionally, we only considered contracts containing the core attacking logic. Other contracts, such as those used solely for concealing profits to avoid detection or fake token contract to facilitate attacks, were not included in our analysis.

Ultimately, we obtained a total of 269 contracts related to DeFi attacks on Ethereum and BSC from April 2020 to December 2023, with 109 on Ethereum and 160 on BSC, resulting in a cumulative loss estimated to exceed 1 billion USD.

Private transactions analysis.
Transactions with labels of MEV Transactions or Flashbots in Etherscan indicate that they bypassed the Ethereum mempool and were sent directly to the block producer. By obtaining the labels of transactions related to DeFi incidents through Etherscan, we have the capability to scrutinize the utilization of private transactions in these attacks. As shown in table
1
, our analysis revealed that in the DeFi incidents on Ethereum, about 50% of the attacks involved the use of private transactions. Notably, within this specific subset, nearly all of the attacks employed private services when initiating adversarial transactions. Moreover, as depicted in Figure
2
, the percentage of adversarial transactions sent using privacy services displayed a remarkable upward trend, surging from 33% in the first half of 2022 to a notable 63% in the latter half of 2023.

3.2.
Benign Contract

To ensure that the benign contract samples are comprehensive and cover a wide range of contract types, we initially utilized Google’s BigQuery Ethereum service to query all transaction records from June 2022 to June 2023, and filtered transactions with the
to
field value of 0, resulting in a total of 417,300 contracts. These contracts do not represent all contracts created during this period. In other transactions, new contracts can also be created through internal transactions. However, based on our analysis of DeFi incidents, almost all attackers utilized standard transactions initiated by EOA to deploy adversarial contracts. Therefore, we exclusively focus on these contracts.

Furthermore, we conducted interaction count statistics for these contracts using the API provided by Etherscan
21 21
. The interaction encompass both normal transactions and internal transactions. Due to API constraints, we could retrieve a maximum of 10,000 transactions for each transaction type. The results are depicted in Figure
3
. In the entirety of contracts within the specified year, the majority exhibited low interaction counts, with over a quarter of contracts having only a single transaction, which typically corresponds to the contract deployment itself, without any subsequent interactions.

To constitute our benign contract samples, we selected the top 13,000 contracts with the highest interaction counts. The minimum number of interactions among them is close to 1,000. We believe that contracts with a high number of interactions are less likely to be associated with attacks, and they exhibit a certain degree of representativeness.

This category encompasses features related to the contract creator. The nonce indicates the number of transactions sent from the contract creator before the deployment of the contract. 4.1.2.
Transaction Data

This category pertains to information concerning the transaction that created the contract. In cases where the contract’s constructor is
payable
, the creator possesses the ability to directly transfer native tokens, such as ETH on Ethereum, to the contract address during the contract’s creation. The specific amount transferred is denoted by the value field within the transaction.

In the context of the contract deployment, the input data field of a transaction represents the bytecode of the contract. The gas consumption for a transaction is contingent upon the specific content of the bytecode. Consequently, the length of the input data and the corresponding gas consumption could serve as indicators of the complexity of the contract. As depicted in Figure
5
, within our contract samples, it is observed that in the case of adversarial contracts, the deployment transactions typically involve less input data, with gas consumption concentrated in the range of 1.0e6 to 1.5e6 wei. Conversely, benign contracts exhibit slightly more input data, accompanied by a more widespread gas consumption, exceeding 2.0e6 in general.

We do not select gas price as a feature because it fluctuates dynamically with network congestion. What may be considered a high gas price at one time may not be so at another. Additionally, attackers usually do not need to increase the gas price to prevent contract deployment from being frontrun.

Function Call

This category provides insights into the specific calls of each function in the contract, including the number of external and internal calls, the total number of calls, the ratio of external calls, and the number of delegatecall. We have also taken into consideration external calls related to ERC-20 tokens, including their count and proportion. The specific functions are outlined in Table

Furthermore, we introduce two novel features to assess function interactions with tokens: MaxTokenCall and AvgTokenCall. To better understand their significance, it’s essential to first consider the concept of the function execution flow. The flow encompasses the complete process a function undergoes during its operation. Specifically, when a public function is executed, it often involves invoking other implemented functions. MaxTokenCall is designed to capture the peak level of token-related interactions within a single public function execution flow, which helps identify functions with exceptionally high token interactions. On the other hand, AvgTokenCall indicates the average number of token-related calls per public function execution flow, providing a measure of the average token interaction level.

4.2.
Feature Extraction

4.2.1.
Transaction Data Retrieval

In the first step of feature extraction, we utilize an RPC (Remote Procedure Call) provider to send direct requests to nodes within the blockchain. This allows us to obtain the raw data of transactions corresponding to the contract deployment, thereby acquiring essential features such as nonce, value, input data length, and gas consumption. Additionally, the transaction sender, input data and created contract address can also be obtained, which will be utilized in subsequent phases of feature extraction.

4.2.2.
Explorer Data Retrieval

Subsequently, we leverage the APIs provided by blockchain explorers, namely Etherscan and Bscscan, to easily retrieve information about the contract’s verification status.

However, considering that our label dataset may not be complete enough, when no corresponding label is found and the address has a substantial transaction history, it can be inferred that this address is used for unknown purpose, and the Unknown label is returned. Specifically, as present in line 15-17, when the transaction volume is greater than the threshold of 10,000, we consider it to be an unknown address. The setting of the threshold is based on the fact that the maximum transaction volume obtained through a single API request is 10,000. Therefore, if it is greater than or equal to 10,000, it indicates that the historical transaction volume of the address may be much higher than 10,000.

Specifically, We categorize fund source addresses into four types:

1)

Safe:
Denotes fund sources with relatively secure origins, such as KYC-required centralized exchanges, which are less likely to be used by attackers.

2)

Anonymous:
Signifies fund sources with anonymous origins, including mixers and some KYC-free exchanges, which are more susceptible to be used for malicious purposes.

3)

Bridge:
Indicates funds originating from cross-chain transfers. We cannot definitively determine if their source is anonymous or not, so they are considered potentially usable for attacks.

4)

Unknown:
Addresses lacking specific labels but possessing a substantial historical transaction volume. We cannot categorize them accurately.

Specifically, we first decompile the runtime code (deployed on the chain) of the contract to obtain the comprehensive pseudocode. Then, we employ regular expressions to extract information about implemented functions, and delve deeper into parsing the function calls within each identified function. Ultimately, the abstract representation of each function is meticulously documented, exemplified by Listing
1
. Regarding public functions, Dedaub’s decompilation process strives to automatically resolve function signatures. As a result, it may either reconstruct the function names or retain the original function selectors, which are unique identifiers derived from the hash of function signatures, used by the EVM to identify and invoke functions. Conversely, for private functions, due to their invocation using
jump
instructions, they are represented by the destination location where the function resides.

Following this processing, we can acquire various fundamental features in both Implemented Function and Function Call categories, such as PublicFuncNumber, PrivateFuncNumber, ExternalCallNumber, InternalCallNumber, and DelegateCallNumber. Additionally, we can also determine whether the contract can self-destruct.

To glean insights into token-related calls within each function and the implementation of flashloan callbacks, we need to attempt matching each function within the contract with the functions listed in Table
4
. It’s worth noting that the function resolved results by decompilation may not always be exhaustive. Therefore, we use both function names and selectors to detect token-related calls and flashloan callbacks. To further extract the MaxTokenCall and AvgTokenCall features, we analyze the execution flow of each public function, which means iteratively traversing the calls within the function, and then counting token-related calls corresponding to the involved private functions and flashloan callbacks.

Furthermore, to ascertain whether the contract is a token contract, we inspect the implemented functions to check if it fully implements all functions of a specific token ERC standard. Specifically, we implement detection for ERC-20
17 17
, ERC-721
19 19
, and ERC-1155
15 15
token contract standards. It’s noteworthy that other token ERC standards, such as ERC-777
20 20
and ERC-4626
18 18
, are backward-compatible with ERC-20. For identifying proxy contracts, despite various proxy patterns, most proxy contracts, following ERC-1967
16 16
, typically saves the logic contract’s address in a specific storage slot. Therefore, if a contract involves a delegatecall and the contract bytecode contains the slot value, we consider it a proxy contract, by which the majority of proxy cases are covered.

4.3.
Classifier Building

Once all the required features have been collected, we proceed to train a supervised learning classifier using the previously gathered datasets of benign and adversarial contracts.

Due to the limited quantity of adversarial samples, to mitigate the issue of class imbalance that can bias model predictions, we employed an oversampling technique known as ADASYN (Adaptive Synthetic Sampling). This approach synthesizes additional adversarial samples to bring the number of attack samples in the training set closer to that of benign samples.

For the fund source feature, which consists of categorical data with low cardinality, we applied one-hot encoding. Additionally, to facilitate better comparability among features of varying dimensions in numerical terms and to improve the accuracy of the classifier, we standardized the data using Z-score normalization. This process centers each feature’s values around 0 with a standard deviation of 1.

Finally, when selecting an appropriate supervised machine learning algorithm to construct the classifier, we explore various models. These models include classical approaches such as Logistic Regression and Decision Trees. We also try ensemble learning approaches, such as Random Forest based on bagging and the LightGBM based on boosting. In addition, we considered the use of a classic neural network architecture, the Multilayer Perceptron (MLP), as one of the candidate models.

5.1.
Metrics and Methodology

In addition to commonly used binary classification performance metrics such as accuracy, precision, recall, F1-Score, we also calculate the False Positive Rate (FPR) metric, which holds particular significance in our scenario. A high FPR implies that the classifier is more likely to incorrectly identify benign contracts as adversarial, potentially leading to significant manual audit costs.

A distinguishing aspect of our research compared to traditional supervised machine learning problems is the explicit chronological relationship between contract deployment. Different contracts deployed over time may exhibit varying characteristics and vulnerabilities, meaning that adversarial contracts may evolve as well. Additionally, our objective is to train a classifier based on existing DeFi incident data to detect potential future attacks. Consequently, traditional cross-validation techniques, which assume each data is independent, may not be suitable for our evaluation.

In response, we adopt a chronological approach to select adversarial contracts for training and testing. We use the earliest 80% of the contracts for training and reserve the latest 20% for testing. Specifically, the 53 most recent adversarial contracts, deployed between August 18, 2023, and December 21, 2023, are allocated for testing, while the remaining 216 earlier contracts are used for training.

5.4.
Failure Analysis

In this section, we analyze the failure instances of the LightGBM-based classifier, where the classifier made incorrect identifications during testing. Specifically, there is one false negative and four false positives. Table
8
presents these failure contracts along with a subset of their important features.

5.4.1.
False Negative

The adversarial contract with address
0x0f41f9
stands out as the sole false negative instance, erroneously classified as benign by the classifier. While it exhibits some characteristics typically associated with adversarial contracts, such as an Anonymous fund source, lack of verification, a single public function, and relatively low input data and gas consumption, it notably lacks the implementation of the flashloan callback and does not involve token-related calls. These deviations from the typical adversarial contract might have contributed to the misclassification by the classifier.

This incident occurred on September 29, 2023, resulting in approximately 4,000 USD in losses. Upon analyzing the victim contract and the adversarial transaction, it becomes apparent that the vulnerability exploited in this attack was an access control flaw that led to arbitrary external call. In the adversarial contract, the attack was completed with only three external calls. (1) It first invoked the
update
function within the victim contract. This function could modify critical variables but lack proper access control, enabling anyone to call it. (2) Next, the adversarial contract exploited the
functionCallWithValue
function of the victim contract, transferring its native tokens to adversarial contract specified in the previously called
update
function. (3) Finally, the acquired tokens were transferred to the attacker. This attack was relatively simple, with losses directly in native tokens and no involvement of token-related calls, suggesting that our detection method may have limitations when confronted with adversarial contracts that employ straightforward attack flow.

5.4.2.
False Positive

The four false positive instances share certain characteristics resembling typical adversarial contracts, such as non-Safe fund source labels, unverified status, the usage of token-related calls, and the ability to self-destruct. These particular features might have led the classifier to identify them as adversarial contracts.

Arbitrage.
The contract
0xdac3d4
was found to be involved in arbitrage activities through an analysis of its transaction history. Arbitrage involves profiting from price differences in tokens across different platforms. Specifically, this contract was used for the NFT arbitrage. Taking its first transaction after deployment, transaction
0x25637d
, as an example, the contract initially purchased an NFT on the Blur
7 7
for 0.3 Ether and immediately sold it on the Sudoswap
30 30
for approximately 0.314 Ether, thereby profiting from the price difference. The entire process was executed within a single transaction using the contract and leveraged the private service of flashbots to mitigate the risk of failure.

SniperBots.
The contract
0x1d2cbc
has already self-destructed. Upon analyzing its transaction history, it was observed that nearly all of its transactions involved purchasing ERC-20 tokens with Ether. Furthermore, the purchase transaction and the transaction for creating the liquidity pool corresponding to the target token both occurred within the same block. Consequently, this contract was actually used by sniper bots
Cernera et al. 2023
. These bots engage in buying tokens on liquidity pools as soon as they are listed, allowing them to "snipe" new tokens at their initial price before anyone else, with the intention of selling them at a profit once their value increases. The contract
0x70d2f0
was also utilized by similar sniper bots.

Phishing.
The contract
0xfd594e
has relatively simple code. An analysis of its transaction history reveals a consistent pattern in all transactions, which is phishing activity in fact. Specifically, it was employed for zero-value transfer phishing. In this phishing method, scammers begin by generating fake addresses with characters matching the first and last few characters of the victim’s recent interaction address. Subsequently, they employ the
transferFrom
function to perform zero-value transfer to the victim’s address. This action results in the appearance of the fake address in the victim’s transaction history, misleading users with the intent of causing them to inadvertently send tokens to this fraudulent address, thereby stealing the victim’s tokens.

These false positives suggest that contracts used for arbitrage, as well as those employed in sniper bots, phishing, and other suspicious activities aimed at financial gain, bear certain similarities to adversarial contracts involved in DeFi attacks. These may represent the primary contract types responsible for the false positives in our detection methodology.

6.
Limitations and Future Work

In this section, we discuss the limitation as well as the possible future work.

Detection Scope.
Our current method has certain limitations in the scope of detection.
In terms of feature selection, we rely on existing attack patterns, with a specific focus on DeFi attacks involving financial losses, tailored to prevalent attack scenarios. Consequently, we may miss attacks that do not result in financial losses and certain adversarial contracts with novel attack vectors. Furthermore, in the cat-and-mouse game of DeFi attack and defense, we have observed that some DeFi attackers, similar to front-running bots, encapsulate function calls related to attacks within the input data of adversarial transactions. As the attacking logic employing this approach is not included in the contract, it also poses difficulties for detection.

Performance.
As analyzed in section §
5.4
, our classifier struggles to correctly categorize adversarial contracts with overly simplistic attacking logic, as well as contracts designed for suspicious activities aimed at financial gain, which significantly impacts the accuracy of our detection system. Additionally, the current feature extraction process relies on RPC providers and blockchain explorer APIs. While these components can be replaced by running our custom nodes, as of writing, there is a lack of robust open-source decompilation tools. Solely relying on Dedaub’s online decompilation service results in slow response times, making real-time detection impractical.

In the future, we will continue to refine our contract dataset, which involves not only supplementing the adversarial contracts but also gathering a more diverse range of benign contracts from a broader time span.
Additionally, we plan to delve deeper into the nuanced differences between contracts utilized in suspicious activities such as arbitrage, sniper bots, phishing, and contracts implicated in DeFi attacks, helping us extract more representative features to reduce false positives while maintaining efficient detection capability for adversarial contracts. We are also contemplating a more granular classification of adversarial contracts based on specific attacking logic they employ, enabling us to identify the vulnerabilities that the attackers intent to exploit in the victim contract.
Furthermore, we recognize the potential benefits of developing our own decompilation module. This would not only improve the real-time performance of feature extraction but also allow for more comprehensive features from bytecode.

8.
Conclusion

In this paper, we propose a new direction for detecting DeFi attacks, i.e., detecting adversarial contracts instead of adversarial transactions.
We build the first dataset for adversarial contracts. Based on this dataset, we found that
the proportion of adversarial transactions sent using privacy services has exhibited a significant upward trend, thereby evading traditional adversarial transaction detection methods.
Through the analysis of DeFi attack patterns, we extract six categories of features across multiple dimensions, such as attributes of the contract creator, functions implemented in the contract, and types of contracts. Utilizing these features,
we build a machine learning classifier
that can effectively distinguish adversarial contracts from benign ones.
The evaluation show that our method performs exceptionally well. The F1-Score for LightGBM-based classifier is 0.9541, with a remarkably low false positive rate of only 0.15%. By analyzing cases where the classifier made incorrect identifications, we point out contracts that could be confused with adversarial contracts used in DeFi attacks.
