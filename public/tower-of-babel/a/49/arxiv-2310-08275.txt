Puzhuo Liu, Chengnian Sun, Yaowen Zheng, Xuan Feng, Chuan Qin, Yuncheng Wang, Zhenyang Xu, Zhi Li, Peng Di, Yu Jiang, Limin Sun

Abstract
. This paper proposes LATTE , the first static binary taint analysis that is powered by a large language model (LLM). LATTE is superior to the state of the art ( e.g. , Emtaint, Arbiter, Karonte) in three aspects. First, LATTE is fully automated while prior static binary taint analyzers need rely on human expertise to manually customize taint propagation rules and vulnerability inspection rules. Second, LATTE is significantly effective in vulnerability detection, demonstrated by our comprehensive evaluations. For example, LATTE has found 37 new bugs in real-world firmware, which the baselines failed to find. Moreover, 10 of them have been assigned CVE numbers. Lastly, LATTE incurs remarkably low engineering cost, making it a cost-efficient and scalable solution for security researchers and practitioners. We strongly believe that LATTE opens up a new direction to harness the recent advance in LLMs to improve vulnerability analysis for binary programs.

Static Binary Taint Analysis.

Among these analysis and testing techniques

,

for brevity in this paper)
stands out as an effective approach for vulnerability inspection.
It can directly analyze binaries with several advantages, including

The standard taint analysis workflow comprises three steps.

1

Identifying Taint Sources
:
Taint sources are typically functions that receive external data.
This external data can be manipulated by attackers.
For example, the function
recv
reads data through a socket,

getenv
retrieves information from an environment variable,
and
fgets
loads data from a file.

2

Propagating Taint Labels
:
Initially, the external data received through taint sources
are labeled tainted.
Then the analysis traces the flow of the tainted data through the program;
it propagates the taint labels along data dependencies, such as
assignments, computations, and function calls,
to discover how the tainted data spreads throughout the program.
Meanwhile, if a memory region with a taint label is overwritten with untainted data
or the region is sanitized with certain checks,
then the taint label is removed from that memory region.

3

Identifying and Inspecting Sinks
:
Sinks are potential points in the program where tainted data might
be misused or lead to security vulnerabilities.
They are usually sensitive operations including
manipulating strings (
e.g.
,
strcpy
,
strcat
),
executing commands (
e.g.
,
system
,
execl
),
and formatted outputting (
e.g.
,
printf
,
fprintf
).

Limitations of Taint Analysis.

Taint analysis remains a partially automated process,
demanding considerable human effort for its execution.
The effectiveness of this analysis heavily relies on
the accuracy and quality of rules
governing taint source, taint label propagation and sink inspection.
In particular, using taint analysis for vulnerability detection
not only involves the effective propagation of taints,
but also requires setting up as complete taint checking rules as possible to reduce
false positives and false negatives.
Regrettably, designing these rules necessitates
meticulous manual crafting,
resulting in a non-trivial and error-prone task.
Previous techniques
[
73
;
12
;
87
;
44
;
30
;
11
]

have relied on human expertise to manually define these rules,
thereby introducing the risk of false positives or false negatives
in the analysis results due to potential rule errors and absences
[
44
;
10
]
.
For instance, determining taint sources involves identifying functions that receive external data,
and establishing the initial taint labels requires the specification of these functions.
Additionally, the sanitization checks that transform tainted data
into safe data in propagation rules
are diverse and specific to function semantics.
Furthermore, the inspection rules also vary based on the types of
vulnerabilities and sinks involved (further details in
section

3
).

The limitation of taint analysis primarily arises from the requirement of

To overcome this limitation, we firmly believe that large language models (LLMs)

LLMs have advantages in code-related tasks
by providing

While LLMs have their advantages, it is essential to note that they are not a silver bullet.
Therefore, in this paper,
we embark on the first study for vulnerability discovery
that explores the synergistic combination of

This will improve the automation and accuracy of taint-style vulnerability inspections.

Challenge of Using LLMs.

There are unexplored challenges
in applying LLMs for vulnerability inspection in binaries.

1
Prompt engineering:
Prompts play a crucial role in instructing LLMs to generate responses, and their design significantly influences the performance of LLMs.
In the context of vulnerability analysis,
well-constructed prompts must include
the code snippets to be analyzed
and a clear description of the analysis tasks.
However, current LLMs have their limitations:
providing all the code snippets related to potential
vulnerabilities at once or directly instructing vulnerability
analysis often leads to unsatisfactory results.
Therefore, it is preferable to
break down the relevant code snippets and vulnerability analysis tasks,
and prompt LLMs to perform step-by-step analysis.
Furthermore, the prompt engineering process should be
designed to be general, without requiring human intervention
whenever the program or vulnerability analysis task changes.

2
Encoding of code context:
To conduct accurate vulnerability analysis,
having adequate code context, including function call stacks, data dependencies,
and control flow, is crucial to determine
whether a piece of code is vulnerable.
However, most LLMs currently accept only a limited amount of context,
striking a balance between computational costs and response quality.
For example, the state-of-the-art LLM GPT-4.0 supports contexts
consisting of just 32,000 tokens (approximately 24,000 words) for both prompts and responses
[
63
]
.
Consequently, when dealing with real binaries,
encoding the code context to meet this size constraint of LLMs becomes necessary.
Analyzing the entire binary directly is often impractical, as the decompiled code
itself usually surpasses this size limitation.

LATTE
.

We propose
LATTE
(
L
LM-Powered Bin
a
ry
T
ain
t
Analyz
e
r),
the first technique to inspect vulnerabilities in released binaries
by combining the power of LLMs and the concept of taint analysis.
It conquers the practical limitations of taint analysis
by harnessing the ability of LLMs in code understanding to automate and streamline the manual components of taint analysis,
and addresses the challenges of using LLMs with dedicated static analysis and prompt engineering.
The key idea of
LATTE
is to construct prompt sequences driven by code slicing.
Concretely,

(1)

Initially,
we preprocess the binary
to recover the code structure,
by performing analysis such as disassembly and decompilation.

(2)

Based on the preprocessing results,
we use LLMs to identify sinks and then
determine potentially vulnerable destinations,
i.e.
,
call sites of security sensitive functions (sinks).
These vulnerable destinations will need to be inspected.

(3)

With the identified vulnerable destinations,
we
perform
backward
intraprocedural and interprocedural data dependency slicing
to establish function call chains starting from the vulnerable destinations.

(4)

We consider function call chains involving external input data as
dangerous flows
.
To this end, we first use LLMs to identify sources that pass externally controllable data into the program
and then identify such call chains that include sources.

(5)

Based on the dangerous flows,
we use functions as units and
combine them with program analysis tasks, such as flow analysis,
alias analysis and taint analysis, to form prompt sequences.
These prompt sequences are generated to converse with LLMs,
completing the vulnerability inspection.

LATTE
significantly outperforms

CWE is a community-developed list of software weakness types

CWE is a tree-like relationship between weaknesses at different levels of abstraction, which can be divided into

,

As shown in

1

The

(B) is used to present more specific types of weaknesses.
The
variant
(V) is described at a low level of details, usually restricted to a specific language or technology.

To ensure that vulnerability types do not overlap,
we classify taint-style vulnerability types
according to the following principles.

1
Vulnerability types are mapped to the CWE’s basic level,
which is used to present specific types of weaknesses.
If basic level does not exist, then the variant level is used.

2
Classification is based on the cause the vulnerability is triggered,
regardless of the reason for the introduction of tainted data.
Otherwise a vulnerability would have multiple labels.
For example, if a command injection vulnerability (CWE-78)
is caused by unchecked input data, it will be classified as CWE-78,
not CWE-76 (Improper Neutralization of Equivalent Special Elements).

3
Classification is based on the first reason the vulnerability is triggered.
For instance, if there is an integer overflow vulnerability (CWE-190)
in the operation of input data,
and the subsequent use of the operation result leads
to a buffer overflow (CWE-680: Integer Overflow to Buffer Overflow),
we still classify it as CWE-190.

3.1.
Problem 1. Determining Taint Sources and Initial Taint Labels

Manually identifying taint sources, which receive external input
in a binary, is a laborious process,
because not only standard C/C++ functions
(such as

,

,

)
but also third-party functions (
e.g.

can receive external data.
More importantly, determining the initial taint labels
for the return values and parameters
of the taint sources
requires deep understanding of the semantics of the taint sources.
For example,
only with the semantics of

can we determine
the
third
parameter

(
line

to be tainted, as

stores the external input retrieved by

the first and second parameters should not be labeled as tainted.
Note that it is even more challenging to determine initial taint labels for
third-party functions than standard C/C++ functions because the former
usually do not have documentation whereas the latter are at least documented
in the C/C++ language standard.
Mislabeling often leads to the incorrect propagation
of taint information throughout the program under analysis.

3.4.
Advantages of LLMs in Vulnerability Inspection

The aforementioned specific implementation of the taint analysis
often requires manual efforts combined together with human expertise of vulnerability analysis
to establish taint rules.
Comprehensive taint rules can reduce the workload of post-processing analysis results,
but also increase the complexity of the rules and the cost of analysis.
For example,
if the length of the tainted string with the null-terminator
meets the requirements of the destination buffer of

the tainted string will not cause a buffer overflow vulnerability.
Traditional taint analysis tracks the flow of taint labels from sources to sinks,
so post-processing to verify alerts is critical, such as bounds checking and value analysis.

4.
Overview of
LATTE

We propose
LATTE
, a novel approach that leverages the code understanding capabilities of
LLMs to assist in taint analysis for identifying potential vulnerabilities in binaries.
This approach raises the key research question:

How can we practically and effectively prepare prompts to guide
LLMs in performing vulnerability inspection?

Effective prompts must provide LLMs with sufficient code context
and clear analysis instructions. However, achieving this requires overcoming two main challenges.

Challenge 1: Large Code Size and Complexity
vs.
Limited Token Context of LLMs.

The size and complexity of binary code make it impractical to
directly feed an entire binary program to LLMs for analysis.
LLMs have limits on the number of tokens and the amount
of context they can process.
When these limits are exceeded,
LLMs may lose track of previously analyzed information,
affecting subsequent code analysis. Even without these input limitations,
effectively inspecting vulnerabilities across the entire codebase
of a real-world software project remains a daunting challenge.

Solution to Challenge 1.

Incorporating the principles of taint analysis,
we extract dangerous flows for LLMs to analyze.
By slicing the program, we reduce the analysis complexity for LLMs.
This method employs taint analysis principles to conduct
dependency analysis on dangerous data
related to the program’s external input.
However, unlike traditional taint analysis,
we do not perform sanitization and vulnerability inspections;
instead, we focus solely on extracting dangerous flows.

A dangerous flow is defined as a slice of functions
involved in data dependencies between the external data input function
and potential destinations that could lead to vulnerabilities

(see

section

5.1
and

section

5.2
).
Through this process, multiple dangerous flows can be extracted from the program,
forming a superset of potential vulnerabilities.
This approach partitions the analysis space for LLMs,
reducing the overhead of complex taint analysis algorithms
and minimizing the risk of false negatives.
The extracted dangerous flows provide
LLMs with relevant and contextually concise input,
enhancing the accuracy and efficiency of vulnerability analysis.

Challenge 2: Obscurity of Vulnerability Discovery
vs.
Generality of Instructions for LLMs.

Vulnerability discovery inherently involves exploring the unknown.
Instructing LLMs to perform
similarity analysis based on known vulnerabilities
limits the ability of LLMs to detect unknown vulnerabilities.
Additionally, it is impractical to provide
examples of all possible vulnerability patterns
in the prompt and use
few-shot learning for analysis
[
16
]
.
The instructions for vulnerability checking
described in the prompt should remain general,
requiring no additional effort when the code or vulnerability types change.

Solution to Challenge 2.

Inspired by the idea of manual code auditing
that usually splits a vulnerability analysis task into multiple smaller sub-tasks,
we instruct LLMs to analyze the dangerous flow step by step in a similar manner.
When manually auditing code,
we often use functions as units to gradually understand the entire program.
In addition, manual audits often determine whether vulnerabilities exist
in a general way by understanding the definition of functions and the processing flow of data,
rather than finding similarities through specific vulnerability examples.
Therefore, taking the functions in the dangerous flow as units,
we construct a comprehensive prompt sequence corresponding to the dangerous flow,
which specifies the data source to carry out data flow tracing and vulnerability inspection (see
section

5.3
).
This prompt sequence allows LLMs to complete the vulnerability analysis of
the dangerous flow in the form of a conversation.
Consequently, LLMs can explore and discover vulnerabilities more effectively,
even in scenarios with
different binaries or vulnerability types.

4.1.
Workflow of
LATTE

LATTE
utilizes the idea of
code slicing
and

task splitting

to build prompts to instruct LLMs for vulnerability inspection.
The overall workflow of
LATTE
is depicted in
fig.

6
,
primarily comprising three modules.
Firstly, we

the input binary
using disassembly and decompilation techniques.
This module provides
the recovered code structures for further analysis.
In the second module, we

extracting relevant code snippets involving

For each dangerous flow,

Then, the third module uses the generated prompt sequence to engage in a

the dangerous flow analysis for discovering vulnerabilities.

The code slicing and prompt construction module serve as the core of
LATTE
.
We further explain the three phases of this module.

Phase 1: Function Call Chain Extraction.

In this phase, we begin by identifying vulnerable destinations
(
i.e.
, call sites of sinks)
within the binary.
To achieve this,
we utilize the LLM to analyze each external function to identify sinks and their related parameters,
which may potentially trigger vulnerabilities.
We consider the calls to these sinks as the vulnerable destinations.
Next,
we conduct backward data dependency analysis,
encompassing both intraprocedural and interprocedural aspects,
starting from each vulnerable destination.
This analysis helps us reconstruct the function call chains leading to these vulnerable destinations
(details in
section

5.1
).
Function call chains are defined as below.

Definition 4.1 (Call Chain).

A call chain
CC
is a sequence of functions
[f_{1},f_{2},\cdots,f_{n}]
, where

f_{n}
contains a vulnerable destination
VD
and
\forall i\in[1,n):f_{i}\mbox{ calls }f_{i+1}
.

Phase 2: Dangerous Flow Generation.

The second phase focuses on identifying external input sources and matching them to the previously generated function call chains to generate dangerous flows.
To achieve this, we once again rely on the LLM to identify sources from external functions and determine their calls.
Then, we match the caller of the sources within the function call chains.
If the caller exists in a chain, we consider the chain as a candidate dangerous flow
whose starting point is the caller.
By applying a sequence-sensitive filtering process,
we eliminate repeated flows among candidate dangerous flows,
resulting in a set of distinct dangerous flows
(details in
section

5.2
).

Definition 4.2 (Dangerous Flow).

A dangerous flow
DF
is a call chain
\textnormal{{CC}}=[f_{1},f_{2},\cdots,f_{n}]
,
where
f_{1}
contains at least one call to a taint source,

f_{i}

(1<i\leq n)
may contain calls to taint sources,

f_{n}
contains a
VD
,
and the external data obtained
from any of the taint sources called on the chain
can possibly flow to the
VD
.

Phase 3: Prompt Sequence Construction.

The third phase involves constructing prompt sequences
by combining the identified dangerous flows with specific analysis tasks.
For each dangerous flow,
we create the corresponding prompt sequence using functions as units.
To be applicable to various binaries,
we design three prompt templates to complete the construction of prompts.
The first prompt template is used to initiate a conversation,
which combines with the first function in the flow to clarify the source of analysis,
and instructs the LLM to perform data aliasing, data dependency and taint analysis.
We then use a second template
combined with
each function in the dangerous flow to
recursively construct prompts
for data flow analysis until reach the end of the dangerous flow.
The last prompt instructs the LLM to initiate the final vulnerability analysis
(details in
section

5.3
).

5.3.
Prompt Sequence Construction

In the prompt sequence construction phase,
our objective is to create prompt sequences (
PSs
)
that instructs the LLM to perform vulnerability
inspection based on identified

DFs
.
To ensure that the
PS
effectively instructs the LLM and remains valid and effective for different, diverse programs,
we propose prompt templates (
PTs
)
that are applicable to all
DFs
and can be instantiated to fit each
DF
.
We follow a rigorous iteration and optimization process
that ranged from initial prompt design to testing and feedback analysis.
The final PTs include the following key elements for effective analysis:

•

Clearly state the analysis tasks.
Precise instructions for vulnerability analysis are essential to prevent irrelevant content.

•

Enrich the context of tasks.
Additional instructions related to vulnerability analysis,
such as alias analysis and focusing on tainted data flows, enhance accuracy.

•

Persona assignment.
Assigning appropriate roles improves the professionalism of LLMs in responding to descriptions.

•

Splitting of analysis tasks or data.
For large data to be analyzed,
splitting or preprocessing the data helps improve accuracy.

•

The specified output format.
The determined output format facilitates analysis for downstream tasks.

According to these elements,
we design three templates shown in the

fig.

10
.
The PTs are inspired by the general approach of manual code auditing.
Specifically, data dependency analysis starts from the function containing the external data source
and progresses through the function call chain until the last function in the
DF
.
If a
DF
contains only one function, then
the
PS
for it includes a start prompt and an end prompt.
For a
DF
consisting of more than one function, the middle template is used recursively to complete the PS construction.
This structured approach ensures that LATTE performs vulnerability analysis effectively and consistently across different scenarios.
The detailed explanation of
PTs
design is as follows.

Start Template (
fig.

10(a)
).

Initializes the analysis by specifying the task and context clearly.
The start prompt assigns the persona of the LLM and explains the analysis background and tasks.
Specifically, we instruct the LLM to conduct the following conversion
in the role of program analyst.
Then, we clarify the taint source of program analysis.
For example, for the
\textnormal{{DF}}=[\texttt{fun2},\texttt{fun1}]
shown in
fig.

8
,
the pair (
<function>
,
<parameter>
)
in
fig.

10(a)
is replaced with (
fgets
,
first
).
At the same time,
the body of first function
fun2

is appended at the end of the prompt for analysis.
In the description of the analysis task,
we mainly focus on the propagation of tainted data,
so we emphasize the analysis of data dependencies.
To conduct more accurate analysis,
we also emphasize the focus on data aliases and tainted data operations.

Middle Template (
fig.

10(b)
).

Recursively used to handle intermediate steps in the
DF
,
enriching the context and focusing on relevant data flows.
Specifically,
the middle prompt are reused to describe functions in a
DF
other than the first function.
Thanks to the short-term memory capability of the LLM itself,
we can complete data dependency analysis between functions.
Therefore, the middle prompt needs to indicate
that the taint analysis is continued
based on the analysis results of the previous function.
Similarly, we put the function body to be analyzed at the end of the prompt.
For example,
for the
\textnormal{{DF}}=[\texttt{fun2},\texttt{fun1}]
shown in
fig.

8
,
the body of function
fun1
is appended at the end of the prompt for analysis.
Moreover, if there is a
source
in the current function,
we fill in the source name and the corresponding parameter
at
<function>
and
<parameter>

as in the start template.
Otherwise, taint propagation analysis is performed
based on the analysis results
of the previous function
and the prompt
does not include the content in parentheses (
i.e.
,
“(Note the new taint source … as the taint label.” in
fig.

10(b)
).

End Template (
fig.

10(c)
).

Concludes the analysis, ensuring that all necessary information is captured and formatted correctly.
Specifically
the end template is used after all functions in have been analyzed.
The main task of the end template is to perform vulnerability inspection
based on the analysis results of all
DF
functions.
At the same time, to facilitate vulnerability identification and analysis,
we also let the end template classify vulnerabilities based on CWE.
It is worth mentioning that this not only provides a more detailed vulnerability analysis description,
but also provides patching suggestions based on the code context.

6.1.
Evaluation Setup

Implementation.

The implementation of
LATTE
is based on the reverse engineering framework Ghidra
[
61
;
75
]

and the large language model GPT-4.0
[
62
]
.
Below, we outline the overall implementation process.
The first step involves loading the target binary into Ghidra,
where the custom Ghidra plugin is utilized to automate extraction tasks.
Through the plugin,
LATTE retrieves critical information from the binary,
such as decompiled code, the call graph,
control flow graph (CFG), import table,
and additional metadata necessary for in-depth analysis.
Once the binary data is collected,
LATTE conducts detailed program analysis to extract DFs
that are relevant to vulnerability triggering.
Using predefined prompt templates,
LATTE constructs PSs that correspond to each DF.
Each PS is specifically designed to interact with GPT-4.0,
setting up a session in which the LLM conducts a vulnerability assessment of the associated DF.
As GPT-4.0 processes each PS,
it evaluates the corresponding DF for potential vulnerability issues.
Once the analysis across all DFs within a binary is completed,
LATTE saves the results generated by GPT-4.0.
These results, stored as individual files,
are organized for further verification and validation,
supporting a comprehensive review of any identified vulnerabilities.

Benchmarks.

To thoroughly and fairly evaluate the capabilities of
LATTE
,
we used the Juliet Test Suite
[
22
]

and Karonte data set
[
73
]
.
We first selected the benchmarks included in the standard data set Juliet Test Suite (v1.3)
according to
table

1
to evaluate RQ1-RQ4
(Juliet has no benchmarks for CWE-120 and we used the Karonte dataset for CWE-120).
To ensure that our evaluation mirrors real-world scenarios, we removed debug information and symbol tables from the compiled benchmark programs.
Furthermore, since
LATTE
aims to detect vulnerabilities caused by external inputs,
test subjects with internal data as a source have been removed.
The number of test subjects used for evaluation
is listed in
table

2
.
Second, we performed RQ5 evaluation
on real firmware data set provided by Karonte
to illustrate
LATTE
’s ability to find vulnerabilities in the real world.
Since the source code of firmware in Karonte
are not publicly accessible,
and thus not in the training sets of LLMs.
The evaluation on Karonte helps to investigate whether

LATTE
suffers from the data leakage problem
[
91
]
.

Baselines.

We selected Emtaint
[
12
]
and Arbiter
[
87
]

for comparison on the Juliet Test Suite.
These techniques represent the state of the art as shown
in

table

.
For the Karonte dataset,

We did not include CodeQL

Metrics.

In the evaluation based on the Juliet Test Suite,
we measured the effectiveness of
LATTE
using six indicators:
true positive (TP), false negative (FN), true negative (TN),
false positive (FP),
accuracy (
\frac{\textit{TP }+\textit{TN }}{\textit{TP }+\textit{TN }+\textit{FP }+\textit{FN }}

and F1 score (
\frac{2*\textit{precision}*\textit{recall}}{\textit{precision}+\textit{recall}}

where
\textit{precision}=\frac{\textit{TP }}{\textit{TP }+\textit{FP }}

\textit{recall}=\frac{\textit{TP }}{\textit{TP }+\textit{FN }}

For the evaluation on the real-world firmware dataset provided by Karonte,
since there are no labels,
we mainly measured the TP and FP in the analysis alerts.

7.
Discussion

7.1.
Limitations on Vulnerability Types

LATTE
faces challenges in handling certain types of vulnerabilities,
such as logic vulnerabilitie
[
56
]
,
race condition vulnerabilities
[
57
]
,
and vulnerabilities involving complex mathematical calculations
[
68
;
55
]
.
These vulnerabilities often involve intricate code snippets
with complex nesting and jumping,
making them difficult for the LLM to effectively analyze.
Therefore, the under/over-tainting problem is prone to occur.
Moreover, these vulnerabilities
are also difficult to detect
by using taint analysis alone.
Complex vulnerabilities
require the extraction of more
context information
such as resource locks,
interrupt vector tables,
shared memory addresses,
etc.
to assist in analysis.
Collecting more valuable context information and
providing it to LLMs for vulnerability analysis
is a direction worthy of further research.

7.2.
Limitations on Binary Analysis

LATTE
implements binary analysis based on Ghidra
[
61
]
,
including reverse engineering, function structure recovery, and calling relationship analysis.
Ghidra provides relatively complete analysis algorithms and APIs for developers to use.

However, binary analysis itself is inherently complex and poses several challenges
[
51
]
.
Many issues remain partially or entirely unsolved.
For example, Ghidra’s analysis can struggle to determine when two pointers refer to the same memory location,
leading to potential inaccuracies in data flow tracking and alias analysis.
Additionally, Ghidra sometimes has difficulty resolving virtual calls,
which can obscure the true calling relationships in the binary.
This limitation is especially problematic in C++ programs with extensive use of polymorphism,
where the inability to accurately resolve virtual calls
can hinder the understanding of control flow and data dependencies.
LLM excels at identifying patterns in code and data flow, and it would be
worth exploring further in the future to assist in identifying common indirect control flow patterns.

Moreover, when the compiler inlines a function,
the original boundary between the caller function
and the callee function is eliminated,
making it difficult to reconstruct the original function structure
and understand the precise calling relationship.
Fortunately,
if a callee is inlined,
the caller becomes larger by incorporating the implementation of the callee.
Therefore, it does not affect the analysis
of the code with LLMs.
Moreover,
function inlining affects
the identification of statically-linked source and sink functions.
But in most cases,
the source and sink are provided by the system library
[
87
;
30
]
.
In order to ensure the size and compatibility of the program,
the system library is usually
dynamically linked,

e.g.
, glibc
[
87
;
73
]
.

7.3.
Importance of Metrics for Evaluating Vulnerability Analysis

Precision and recall are two key metrics
for real program vulnerability analysis.
Analytical methods often require
a balance between false positives (FPs)
and false negatives (FNs)
[
87
]
.
Precise analysis algorithms can reduce false positives,
but may overlook diverse potential vulnerabilities,
thus increasing false negatives.
Conversely, over-approximation analysis algorithms may identify
more potential vulnerabilities, but also increase the number of false positives.
Therefore, security engineers need to choose the appropriate method
based on specific analysis contexts and objectives.
Furthermore, identifying unique bugs is crucial for
both precision and recall metrics.
Duplicate true positives (TPs)
not only add no value to security analysis
but also increase the overhead involved
in validating vulnerabilities
[
73
;
12
]
.

The following guidelines provide tool selection recommendations
based on analysis costs, business scenarios, and security requirement standards
[
49
;
60
;
35
]
.
The recall score is particularly important
when resources such as time and labor are sufficient.
Additionally, using high-recall tools to find as many vulnerabilities
as possible is especially useful in the early stages or when reviewing new code.
On the other hand, when dealing with a large number of subjects
and limited resources,
security engineers should prioritize
high-precision tools
to ensure that reported vulnerabilities are genuine,
thus minimizing the time spent on false positives.
For systems requiring stringent security measures,
use a combination of tools to balance precision and recall,
ensuring comprehensive
coverage and accurate identification of vulnerabilities.

According to the evaluation results in
section

6.2.1
,

LATTE
outperforms other tools in both of precision and recall.
Meanwhile,
LATTE
found more unique bugs in the evaluation of real firmwares
in
section

6.6
,
and covered the bug results of Arbiter and Karonte.
Based on the above guidelines, engineers should give priority to LATTE.
However, the cost of LLM tokens for using
LATTE
is unavoidable.
Therefore, if engineers have sufficient token resources,

LATTE
is recommended to be used over traditional methods.

7.4.
Impact of Binary Protection on
LATTE

LATTE
performs binary analysis based on the intermediate representation P-Code
of Ghidra,
enabling binary analysis across different architectures
such as X86, X64, ARM, and MIPS.
Consistent with other binary vulnerability analysis techniques
[
73
;
12
;
10
;
87
]
,

LATTE
cannot directly analyze binaries that have been obfuscated or encrypted.
Additional steps are needed to ensure the binary can be processed by Ghidra.
There is ongoing research focused on deobfuscation and decryption,
which can aid subsequent vulnerability analysis
[
47
;
88
;
85
;
24
]
.

Moreover,
the performance of
LATTE
was evaluated on binaries lacking debugging information,
symbol tables, and comments.
Maliciously tampered semantics can interfere with
LATTE
’s analysis.
For example, renaming a function containing a vulnerability to “no_vulnerability” might increase
the likelihood of misjudgment.
However, by instructing LLMs to ignore such semantic information, the impact can be significantly reduced.
Offensive and defensive techniques in binary analysis remain an ongoing challenge,
and our findings contribute to understanding the capabilities and limitations of LLMs in this context.

7.5.
Identification of Sources and Sinks

The specification of sources and sinks is necessary to initiate
LATTE
analysis.
If the analyst already has the identified sources and sinks,
the source and sink identification stage can be skipped and
DF extraction and PS construction
can be performed directly by setting the sources and sinks.
If not,
the analyst can use
LATTE
to help identify sources and sinks.
We evaluated source and sink identification based on the
Juliet test suite in
section

6.3
.
The identification results of sources and sinks can be reused
if another binary uses the same dynamic library.
We conducted vulnerability inspections
using these identification results in realwolrd firmwares in

section

6.6
.

In the real world, identifying sources and sinks is a complex problem.
First, real programs require more queries
due to the presence of various linked libraries.
For example, the glibc requires about 3000-4000 queries,
and the OpenGL requires several hundred queries.
Therefore, even with
LATTE
to assist
in identifying sources and sinks for caching,
it requires a certain amount of time overhead.
Second, as described in
section

7.2
,
although most binary prorams use dynamic linking,
static linking and inlining make it more difficult to identify sources and sinks.

LATTE
needs to be combined with program analysis techniques such as
code summarization and dynamic analysis to further determine the source and sink.
Third,
some custom functions in real-world binaries
may also be used as tainted sources and sinks
[
45
]
,
which further complicates the identification of sources and sinks.
LLMs can recognize well-known functions like

recv
and
printf
,
its performance is limited when encountering previously unseen functions.
Meanwhile, the hallucination of LLMs seriously
affects the identification of sources and sinks.
Continuously refining and optimizing prompts or models based on
expert feedback, code information,
and specification data is critical
to meeting the challenges of various libraries and custom functions.

7.6.
Applicability to Source Code

While
LATTE
is designed for vulnerability analysis of binary code,
its underlying concept is adaptable for source code analysis as well.
If source code analysis is required,
three components of the
LATTE
workflow (outlined in
fig.

6
)
would need adjustment.
First, source code analysis bypasses the need for disassembly or decompilation,
allowing for direct code analysis to identify dangerous flows.
Second, the algorithm for extracting dangerous flows
must be modified to work with source code.
For example, in decompiled code,
the analysis relies on registers and memory addresses,
whereas, in source code, it focuses on variable analysis.
Furthermore, binary code typically integrates
all calling relationships and dependencies into a single file,
while source code requires parsing dependencies across multiple files.
Third, the prompt templates need to be optimized.
The start template in binary analysis states that the code
is "generated by decompilation,"
which provides helpful context.
When analyzing source code,
removing this statement or
indicating that the code is source code
can help LLMs analyze the source code more directly,
benefiting from explicit variable names and comments.
Providing additional descriptive information further
aids LLMs in analyzing the code effectively.

To demonstrate the feasibility of the concept of
LATTE
for source code,
we utilized SVF
[
80
]

to extract dangerous flows from the source code of the Juliet test cases
(
section

6
)
and removed the “generated by decompilation” statement
from the start prompt.
As shown in
table

7
,
the accuracy of detecting
vulnerabilities in source code for CWE-78, CWE-134, CWE-190,
and CWE-606 improved by 1.64%, 2.91%, 17.9%, and 5.07% respectively,
compared to stripped binary analysis.
The p-values for these comparisons,
calculated using the Mann-Whitney U Test,
were all less than
0.1
,
indicating statistical significance.
This improvement results from the semantic clarity in source code,
with function names, variable names,
and type definitions providing critical
context that aids LLMs
in understanding and analyzing
vulnerabilities.

However, when combined with LLMs,
there may be more effective approaches than LATTE for source code analysis.
For instance, integrating LLMs with advanced program analysis
tools such as CodeQL
[
33
;
83
;
89
]

could provide a more comprehensive understanding of
code structure and semantics.
Additionally, pointer analysis and other techniques
could be applied directly to source code, rather than decompiled code,
to further enhance the accuracy and effectiveness of vulnerability detection.

8.
Related Work

Taint Analysis.

Taint analysis is a software security analysis method
that aims to identify and analyze potential security vulnerabilities in programs.
It is widely used for analysis in source code, web applications and Android programs.
VulSlicer
[
74
]
and FICS
[
3
]

performed data flow analysis on the source and sink pairs in the source code.
Merlin
[
46
]
, Julian Thomé et al.
[
84
]

and JOZA
[
59
]

summarized artificial experience into rules and used heuristic methods
to discover taint-style vulnerability in web applications.
DroidSafe
[
29
]
, SCANDAL
[
38
]
and AndroidLeaks
[
25
]

identified some API calls or callback functions as taint sources
in Android programs to perform taint analysis.
The main difference between taint analysis of binary programs and the above
program types is the loss of information such as program semantics and code structure.
Therefore, when implementing a binary taint analysis engine, more expert experience
and more manual work are required.
Specific binary taint analysis techniques are introduced in the next paragraph.

Binary Vulnerbility Analysis.

For vulnerability analysis of binary,
there are both dynamic and static techniques.
Dynamic techniques monitor unexpected behaviors of test targets as they execute test cases,
such as fuzzing
[
21
;
43
;
76
;
8
;
100
]
,
concolic execution
[
79
;
67
;
98
;
15
]
, emulation analysis
[
39
;
34
;
14
;
52
;
20
]
.
The results of dynamic analysis are reliable,
but the test code coverage is low and the
test execution depends on the specific operating environment.
Binary execution environments vary depending on the operating system,
architecture, and even peripherals.
As a result, the application and performance of dynamic analysis is often limited.
Static analysis techniques are suitable for binary analysis
due to their high code test coverage and not limited to the execution environment.
BootStomp
[
72
]
, Saluki
[
30
]
, Dtaint
[
11
]
, Karonte
[
73
]
, SATC
[
10
]
,
Arbiter
[
87
]
and Emtaint
[
12
]
techniques
primarily leverage taint analysis
combined with program analysis, symbol execution, and machine learning
to analyze binary vulnerabilities.
However, these methods commonly rely on human experience to define propagation and inspection rules.

LATTE
, on the other hand, is the first to propose a taint analysis technique
combined with LLMs for binary vulnerability inspection,
offering a novel approach that avoids the need for manual rule definition.

LLM-assisted Code Analysis.

The LLM is a class of deep learning models
that have significantly impacted natural language processing.
In recent years, with the excellent code understanding ability of LLMs,
they have been widely applied in code-related tasks,
such as code generation
[
64
;
2
;
23
;
97
]
,
patch generation
[
92
;
93
;
78
;
69
]
,
and code summarization
[
4
]
.
For code vulnerability analysis,
it is often necessary to combine various program analysis techniques
on the basis of LLMs’ code understanding to conduct effective vulnerability auditing.
For instance, FuzzGPT
[
18
]
and TitanFuzz
[
17
]
utilize the LLM to analyze existing code snippets and generate test cases to assist in API fuzzing.
CODAMOSA
[
41
]
uses the LLM to analyze code coverage information and modify test cases to improve test coverage.
Moreover,
LLMDFA
[
wangllmdfa
]
, inspired by summary-based data flow analysis, introduced the dadaflow analysis framework supported
by LLM and explored the idea of LLM-assisted source code analysis.
LLMSAN
[
wangsanitizing
]
further used the ideas of few-shot chain-of-thought and program properties
to reduce the impact of LLM hallucination on the reliability of data flow analysis.
Unlike these LLM-assisted analysis techniques,

LATTE
utilizes the LLM to assist static analysis and works on binaries that provide less code information than source code.

Security Slicing.

Obtaining code snippets from a program for vulnerability analysis is a popular security analysis method. To reduce the time overhead of verifying warnings and improve inspection accuracy, the results of code slicing are often combined with other analysis and testing techniques for further verification.
FuzzSlice
[
58
]
and Helium
[
36
]

used static analysis technology
to construct compilable harnesses from source code slices,
which are then subjected to vulnerability verification through fuzzing.
SFuzz
[
9
]
implemented fuzzing on independent code snippets
extracted from real-time operating systems binaries.
These techniques must ensure that the code snippets
not only contain the entire input processing flow
but also that the slicing result is compilable and executable.
To address the constraints on the execution conditions of code snippets,
Engler et al.
[
71
]

proposed under-constrained symbolic execution,
allowing symbolic execution of any function
without initializing any of its data structures or setting up any environment.
However, this technique still faces challenges with loops, pointers
and library function calls, affecting analysis accuracy.
Our approach,
LATTE
, leverages the idea of taint analysis to slice the program
and then utilizes LLMs for vulnerability analysis.
By using LLMs, our approach reduces the dependency on the execution environment,
alleviating the need for comprehensive environment setup and initialization.
LLMs provide a deeper semantic understanding of the code, improving the identification and analysis of vulnerabilities within the sliced snippets.
Combining taint analysis with LLMs allows for a more focused and relevant slicing,
ensuring that the critical parts of the code related
to potential vulnerabilities are included in the analysis.

9.
Conclusion

This paper proposes
LATTE
, the first LLM-powered static binary taint analysis.
Traditional taint analyzers rely on human expertise to manually define patterns and rules,
and this manual nature severely limits the effectiveness and performance of
the taint analysis technique.

LATTE
performs dangerous flow slicing by slicing vulnerable destinations back to external input sources.

LATTE
then combines code snippets to construct prompt sequences, leveraging LLMs’
context-aware assistance and human-like understanding capabilities for code vulnerability inspection.
Based on the substantial evaluations,

LATTE
outperforms the state of the art across all taint-style vulnerability types,
such as buffer overflow and command injection.

LATTE
sheds light on the combination of program analysis and LLMs for vulnerability analysis.
