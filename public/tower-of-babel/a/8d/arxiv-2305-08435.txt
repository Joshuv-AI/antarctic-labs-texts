Kugelblitz: Streamlining Reconfigurable Packet Processing Pipeline Design and Evaluation
Artem Ageev, Antoine Kaufmann

Abstract
Reconfigurable packet processing pipelines have emerged as a common building block for offloading fast and efficient packet processing to programmable switches and SmartNICs. However, designing or extending such architectures is complex, laborious, and resource intensive, due to the large design space coupled with the need for building architecture-specific compilers and RTL implementations before any evaluation is feasible. In this paper, we present Kugelblitz, a framework for rapidly designing, implementing and evaluating reconfigurable packet processing pipeline architectures. Kugelblitz comprises domain specific abstractions for separately representing pipeline architectures and protocol processing programs, a compiler for automatically mapping programs to specific architectures, and a hardware generator outputting complete RTL implementations for specific pipeline architectures. Kugelblitz enables meaningful full-system evaluation including chip area and timing from VLSI synthesis of the generated RTL, and end-to-end system benchmarks running real application workloads in full system simulation. In our evaluation, we demonstrate that Kugelblitz generates realistic and efficient RTL implementations, scales to large pipelines, enables fast design exploration, and provides meaningful application offload performance results.

Introduction

Modern network devices, especially switches and network interface controllers
(NICs) increasingly provide some programmability in their packet processing.
Programmable processing increases flexibility and allows devices to cover
a broader range of use-cases and avoids the need for operators to deploy new
hardware if protocols change over time.
Realizing this programmability in hardware gives rise to a host of challenges.
In data centers especially, modern NICs process packets at bandwidths up to
200 Gbps, while switches need to provide aggregate bandwidths of up to
12 Tbps.
End-to-end communication latencies can be below 10
\mu
s leaving individual
devices with processing budgets below 1
\mu
s.
Finally, modern NIC and, especially switch chips, already require large chip
area even without programmability overhead.

Reconfigurable packet processing pipelines (RPPPs) have emerged as one of the
key hardware building blocks for meeting these requirements in
NICs

switches

The capability of these building blocks ranges from minimal pre-processing such
as extracting packet fields or basic packet

plane processing in switches

Reconfigurable pipelines are spatial architectures comprising multiple pipeline
stages that contain ALUs, memories, and routing elements that packets pass
through sequentially (typically) executing the same processing steps for every
packet.
Operators or vendors program these pipelines by configuring parameters such as
the opcode for each ALU, what addresses or keys to use for memory and CAM
accesses, and how to route inputs and outputs between these elements.

The specific design parameters vary widely between specific architectures, such
as number of stages, number of ALUs per stage, operations supported,
configuration and availability of memories, interconnects topology and
configurability for routing inputs to and outputs between elements.
These parameters affect a packet processing pipeline’s processing capability,
i.e. what protocol processing it is capable of performing, as well as the
chip area and achievable timing and system performance.
As a result, these trade-offs are subject of both innovation in commercially
available products

]
and in

Unfortunately, research on new reconfigurable pipeline architectures is
typically challenging to implement and evaluate because of multiple compounding
factors.
First off, the design space for these architectures is very large due to the
many design parameters, with only few reference points for existing designs.
Choosing concrete design parameters is further complicated as many parameters
not only affect performance, but indirectly also determine what protocol
processing can be executed on the architecture.
However, to determine if a concrete protocol processing program can be realized,
a compiler for the specific architecture first has to be developed.
In addition to processing capability, different architectures will result in
different hardware cost and performance.
Evaluating both requires a complete RTL implementation of the architecture,
which can then be passed through VLSI synthesis to obtain chip area
and timing analysis.
Finally, while clock frequency is a useful performance evaluation metric, the
main metric of interest is typically performance of the complete system
including the pipeline.
Beyond a full RTL implementation, obtaining this ordinarily requires a complete
chip implementation and measurements in a physical testbed cluster.
Due to the prohibitive time and resource requirements, most academic work stops
short, instead opting for a piecemeal evaluation, e.g. implementing and
synthesizing RTL for small design
components
[

]
, rarely opting for complete RTL
prototypes combining VLSI synthesis and timing analysis with FPGA emulation for
functional system tests

.

In this paper we aim to tackle this challenge with Kugelblitz, a framework for
streamlining design exploration, implementation, and evaluation for
reconfigurable packet processing pipelines.
First, we introduce an abstract representation for specifying complete
reconfigurable pipeline architectures.
We then separately represent packet processing programs in an
architecture-agnostic representation.
Based on these two abstractions we design a compiler to automatically map
programs to specific pipeline architectures or determine that a program cannot
be realized on the specified architecture.
This provides early and rapid feedback on what architectures can run which
programs.
Next, we design and implement a hardware implementation generator that
automatically generates complete and synthesizable RTL implementations from
pipeline architecture specifications.
Besides synthesizing for chip area and timing, we also implement a harness for
cycle accurate simulation of the RTL as part of an end-to-end full system
simulation using the SimBricks modular simulation framework
[
li:simbricks
]
.
Finally, Kugelblitz can also convert protocol processing programs to fixed pipeline
architectures implementing this processing to serve as baselines for evaluation.
In combination, Kugelblitz enables fast design space exploration for pipeline
architectures guided by protocol processing programs that fit, chip area,
and end-to-end performance of application workloads.

Reconfigurable Packet Processing Pipelines

We first discuss background on reconfigurable pipelines followed by the
challenges in designing and evaluating them.

2.1
Uses

As programmable network hardware is increasingly replacing fixed function
hardware, RPPPs have become a common building block in many modern switches and
NICs.

In programmable switches
[
bosshart:rmt
,
product:cavium:xpliant
,
product:intel:tofino
]
, the complete switching logic, including packet
filtering, forwarding decisions, en- and de-capsulation, and even
telemetry
[
int
]
, are handled by RPPPs configured accordingly.
In such switches, a regular server-class CPU is responsible for the control path
including programming the pipeline and as well as initializing and maintaining
pipeline state (such as forwarding tables, ACLs, etc.).
This control-path separation removes significant complexity from the data path
for handling the (relatively) infrequent updates to programming and state, at
the cost of slower out-of-band operation.

For NICs the role varies more widely, from simple pre-processing steps for
otherwise fixed-function NICs, over coordinating other units on the NIC, all the
way to implementing most of the packet handling.
Intel’s recent E810
[
intel:e810
]
100 Gbps+ data center NIC series use
their
FlexiPipe
programmable pipeline for flexible packet switching,
classification, ACLs in between the network port and the rest of the
conventional NIC logic.
Pensando’s DSC
[
matus:pensando
]
(now AMD) and the PANIC
[
lin:panic
]

SmartNIC architectures use RPPPs to flexibly coordinate packet processing on
among multiple different processing units on the NIC.
Finally, FlexNIC
[
kaufmann:flexnic
]
proposes to implement most NIC
functionality including DMA logic through RPPPs with little to no fixed
processing.

2.2
Architecture and Design Space

Figure 1:
Reconfigurable packet processing pipeline example.

Figure 1
shows an example RPPP with the typical elements:
(de)parser, interconnects, registers, ALUs, and memories.

Packets enter the pipeline through a
parser
that extracts relevant packet
fields from the whole packet for processing in the rest of the pipeline.
The rest of the pipeline only operates on these extracted fields and cannot
access to the rest of the packet.
These can be as simple as taking a prefix of the first N packet bytes, or more
capable TCAM-driven programmable parsers
[
gibb:pktparser
,
bosshart:rmt
]
.
At the end of the pipeline a
de-parser
re-combines updated packet fields
and modification instructions with the original packet.

Inside the pipeline, intermediate results are passed through
registers

into subsequent stages.
Given the spatial pipeline architecture, only values explicitly assigned to
registers are available in the next stage.
In each stage, configurable
interconnects
route values from the input
registers to the inputs of units in the stage, and from unit outputs to the
output registers.
Specific interconnect topologies vary widely between designs,
RMT
[
bosshart:rmt
]
for example, uses full crossbars for input routing, but
hardwires each ALU output to a specific register.

The actual computation in RPPPs occurs in the
ALUs
where each ALU only
executes one operation for each packet.
For each ALU, the programmed runtime configuration chooses the operation to
execute.
The number of ALUs and the operations they support vary between implementations.
Due to timing and space constraints ALUs typically support common bit operations
as well as addition and subtraction, but typically not multiplication or
division.

Finally, different types of
memories
serve one of two tasks:
1) communicating state to and from the control plane, and
2) maintaining state across packets.
Lookup tables, implemented as hash tables in SRAM or for ternary lookups in
TCAM, are the most common types for the former.
While regular RAM blocks, that the pipeline reads and writes, are common for the
latter.
Timing is often a key constraint, especially for memories that are accessed
in a read-modify-write pattern (e.g. counters for statistics), as packets
needing access to the same memory elements can arrive directly back-to-back.
As a result, memory is typically local to a specific pipeline stage where it has
to be both read and written, significantly limiting complexity of stateful
operations
[
sivaraman:packet_transactions
]
.
Specifics of the types, numbers, and sizes of memories available again vary
widely.

2.3
Design and Evaluation Challenges

Building new reconfigurable programmable packet processing pipeline
architectures and systems is a complex endeavor.

C1: Large and unexplored design-space

The first question is how to choose concrete design parameters from the vast
design space.
How many pipeline stages?
How many registers and ALUs per pipeline stage, and how to interconnect them?
What operations should the ALUs support, and what bit-width?
What configuration of memories, including types and sizes?
Should the pipeline be homogenous and regular with the same parameters for each
stage, or heterogeneous with different parameters in different stages?
Accurately and optimally answering these questions at design time is nearly
impossible.
The design space is huge and there are only few existing reference points with
concrete and varying answers for each question.
To make matters worse, many of the existing architectures are proprietary with
some unknown parameters, and often little information about chip area and timing
that they achieve.
As a result, designs inevitably involve educated guesses and iterative
exploration.

C2: Trade-off between cost, performance, capacity

Choosing design parameters thus requires navigating a three-way trade-off
between performance, cost, and feasible processing.
Unlike with conventional processor architectures where most design parameters
just affect performance and cost, the specific design parameters of an RPPP directly limit what protocol processing it can support.
While additional protocol processing operations on a processor just increase
execution time by a few cycles, for a reconfigurable pipeline processing will
either fit or not fit.
Predicting what processing is feasible ahead of time is challenging,
e.g. even if sufficient ALUs and registers are available in total, a program
might not fit because of routing constraints.

C3: Reconfigurable architectures need compilers

To map a packet processing program onto a specific pipeline architecture, a
compiler for the specific architecture is required.
Even for small programs manually writing pipeline configurations is typically
not feasible for all but the smallest pipeline architectures.
So in addition to choosing architecture parameters, designers also have to
implement a compiler before being able to determine what protocol processing
programs a specific architecture can support.
A compiler is also required for actually testing a pipeline implementation.

C4: Measuring chip cost and end-to-end performance

The final challenge, is a meaningful evaluation of a pipeline architecture.
Besides the capability of running the necessary protocol processing, possibly
with hard to quantify additional capacity for flexibility to meet future
needs, there are additional key metrics.
The high level metrics of interest are overall system cost and performance.
For both the first step is a complete RTL implementation of the architecture.
VLSI synthesis tools such as Synopsys, Cadence, or OpenROAD then provide a
hardware implementation, along with reports on chip area and timing analysis.
Area reports provide a reasonable proxy for hardware cost.
Timing analysis confirms the achievable clock frequency for the chip, which
factors into system performance.

However, predicting overall system performance from chip clock frequency in
network systems can be challenging.
Especially when evaluating cost and benefit of offload designs, where the
RPPP only implements part of the overall system processing many other factors
affect system performance, such as processing latency and variations in timing.
Reliable full system measurements require running all system components in
combination in a testbed.
However, there are significant additional time- and cost-intensive steps before
a complete hardware prototype is ready for evaluation.
These last steps in particular are out of reach of most researchers in academia,
and even for industrial research only getting results very late in the process
is a challenge.
This particularly makes reliably putting system cost in context with performance
improvements achieved compared to baseline systems nearly impossible.

3
Kugelblitz Approach

To address these challenges, we propose Kugelblitz, an framework for end-to-end design
exploration for RPPPs.

3.1
Design Goals

Specifically, Kugelblitz has the following design goals:

•

Flexibility
: enable exploration of a broad range of pipeline
architectures with different design parameters and degrees of programmability,
including fixed function pipelines as comparison points.

•

Low programmer effort
: minimize implementation effort required
for comparing different pipeline architectures and combinations with protocol
processing programs.

•

Realistic
: obtain representative implementations in terms of
cost, system performance, and processing capacity that can meaningfully guide
design exploration.

•

Scalability
: support the necessary scale for pipeline
architectures with thousands of ALUs and tens of stages, and protocol programs
to match.

•

Quantitative comparison
: enable meaningful evaluation of cost as
well as full system performance for different designs, without fabricating and
deploying hardware.
