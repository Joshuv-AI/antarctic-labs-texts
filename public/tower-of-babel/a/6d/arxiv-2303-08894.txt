A Formalization of Operads in Coq
Zachary Flores, Angelo Taranto, Eric Bond, Yakir Forman

Abstract
What provides the highest level of assurance for correctness of execution within a programming language? One answer, and our solution in particular, to this problem is to provide a formalization for, if it exists, the denotational semantics of a programming language. Achieving such a formalization provides a gold standard for ensuring a programming language is correct-by-construction. In our effort on the DARPA V-SPELLS program, we worked to provide a foundation for the denotational semantics of a meta-language using a mathematical object known as an operad. This object has compositional properties which are vital to building languages from smaller pieces. In this paper, we discuss our formalization of an operad in the proof assistant Coq. Moreover, our definition within Coq is capable of providing proofs that objects specified within Coq are operads. This work within Coq provides a formal mathematical basis for our meta-language development within V-SPELLS. Our work also provides, to our knowledge, the first known formalization of operads within a proof assistant that has significant automation, as well as a model that can be replicated without knowledge of Homotopy Type Theory.

The DARPA V-SPELLS (Verified Security and Performance Enhancement of Large Legacy Software) program aims to create developer-accessible capability for piece-by-piece enhancement of software components for large legacy codebases with new verified code that is
safely composable
with the rest of the system.

In our approach with the Johns Hopkins Applied Physics Laboratory to solving the problems posed by V-SPELLS, our tool in development, called LUMOS, begins by applying methods from static analysis, natural language processing, and dynamic analysis to the legacy source code in order to generate high-level abstractions of these DSLs (Domain Specific Languages) that we call domain-specific semantic models (DSSMs) from the DSLs that comprise the source code. These DSSMs will be generated in a language we refer to as the
meta-DSL
, and in order to provide the patches to the legacy code requested in V-SPELLS, these DSSMs will have to be composed in very specific ways. In order to ensure correctness of composition, as is required in V-SPELLS, we are providing verification via an algebraic framework using several ideas from category theory in which the key structure to our modeling is called an
operad
. Operads have begun to play an increasingly important role within applied mathematics (see
[
LBPF
,
FBSD
,
BF
,
BO
,
GLMN
]
), and we find they provide an excellent mathematical model for our verification needs on V-SPELLS.

To be more precise about our modeling, when a DSSM is written in the meta-DSL, we will use an operad to represent the DSSM in the meta-DSL, and composition of DSSMs within the meta-DSL will be modeled via a “gluing” operation. Mathematically, we are providing denotational semantics for a key portion of the language of the meta-DSL. To ensure the highest level of correctness on composition between DSSMs in the meta-DSL, we aim provide a formalization of the denotational semantics of the meta-DSL. In particular, we need to provide a formalization for the foundation for the denotational semantics of the meta-DSL: operads. We provide this formalization within the proof assistant Coq, and this is the focus of our paper.

In this way, the type $T$ is a set together with an injective mapping to ${\color{teal}\textbf{Type}}$, which is exactly the data of a subset of ${\color{teal}\textbf{Type}}$. Our approach to implementing this definition in Coq involves the following:
\par\begin{enumerate}\enumerate@item@a type $\mathcal{B}$ in Coq with nullary constructors, we call the {base types}, and whose terms we refer to as {type sigils};
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@the constructors that define the type $T$, which include:
\begin{itemize}\itemize@item@a constructor with signature $\textbf{Ty}:\mathcal{B}\rightarrow T$ which encodes the base types into $T$;
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\itemize@item@other constructors that may model products, such as $\textbf{p}:T\rightarrow T\rightarrow T$, or $\textbf{fn}:T\rightarrow T\rightarrow T$, which can model functions;
\end{itemize}\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@an assignment for $\mathcal{B}$ within ${\color{teal}\textbf{Type}}$, and a recursively-defined interpretation function $\textbf{El}:T\rightarrow{\color{teal}\textbf{Type}}$ that assigns a value within ${\color{teal}\textbf{Type}}$ to each $t:T$.
\end{enumerate}\par We give an example of what this would look like explicitly.
\par\begin{example}We define our collection of base types $\mathcal{B}$ in Coq with the nullary constructors $N,U$, and $B$. Within Coq, we create a function $\textbf{I}$ that interprets these type sigils: $N$ is assigned to $\mathbb{N}$, the type of natural numbers; $U$ to $\mathbb{U}$, the unit type; $B$ to $\mathbb{B}$, which is bool.
\par If we want to model products and functions within in $T$, then we can define $T$ with constructors:
\par\begin{enumerate}\enumerate@item@$\textbf{Ty}:\mathcal{B}\rightarrow T$;
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@$\textbf{p}:T\rightarrow T\rightarrow T$;
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@$\textbf{fn}:T\rightarrow T\rightarrow T$.
\end{enumerate}\par Now $\textbf{El}$ will provide the embedding into Coq via the following recursion:
\par\begin{enumerate}\enumerate@item@$\textbf{El}\,(\textbf{Ty}\,t)\Rightarrow\textbf{I}\,t$
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@$\textbf{El}\,(\textbf{p}\,t\,t^{\prime})\Rightarrow\textbf{El}\,t\times\textbf{El}\,t^{\prime}$
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@$\textbf{El}\,(\textbf{fn}\,t\,t^{\prime})\Rightarrow\textbf{El}\,t\rightarrow\textbf{El}\,t^{\prime}$
\end{enumerate}\par For an explicit example of a code in $T$, we have $\textbf{p}\,(\textbf{Ty}\,N)(\textbf{Ty}\,N):T$, and via the embedding $\textbf{El}$, this is a model for $\mathbb{N}\times\mathbb{N}$ in Coq.
\par\par\end{example}\par\par\@@numbered@section{section}{toc}{A Proof Using Our Model}
\par Our goal in this section is to discuss the formal proof that the equivalent of Example \ref{exsets} in Coq, which we denote by $\textbf{Type}$ and define in Example \ref{extype1}, is an operad according to our model.
\par To formally demonstrate that $\textbf{Type}$ is an operad, we first need a definition of the function in the only field of the record {Operad} (see Note \ref{opdefcoq}). Next, in the record {OperadLaws}, we need to define, for $c:{\color{teal}\textbf{Type}}$, the $c$-colored units (1 of Definition \ref{defoperad1}), provide proofs that $\textbf{Type}{d\choose\underline{c}}$ is invariant (up to injection) under reordering of $\underline{c}$ (2 of Definition \ref{defoperad1}), define the multi-composition functions (3 of Definition \ref{defoperad1}), and show all axioms in Definition \ref{defoperad2} hold according. Wrapping these assignments and proofs together provides a term of type {Operad} and {OperadLaws}, which gives our desired formal proof.
\par In Example \ref{extype1}, we give the definition of the required function in {Operad} for $\textbf{Type}$: given $\underline{c}=c_{0},\ldots,c_{n-1}:\textbf{list}\,{\color{teal}\textbf{Type}}$ and $d:{\color{teal}\textbf{Type}}$, we write:
\par$$\textbf{Type}{d\choose\underline{c}}:=c_{0}\rightarrow\cdots\ \rightarrow c_{n-1}\rightarrow d,$$\par which is the type of $n$-ary functions with codomain defined by $\underline{c}$ and return type $d$. Our instantiation of {OperadLaws} for $\textbf{Type}$ will use this definition throughout.
\par The right-hand side of $\textbf{Type}{d\choose\underline{c}}$ is defined via a recursive function, which we denote as {arr} (short for {arrow}), with type signature $\,\textbf{list}\,{\color{teal}\textbf{Type}}\rightarrow{\color{teal}\textbf{Type}}\rightarrow{\color{teal}\textbf{Type}}$. In particular, we define $\textbf{arr}\,\emptyset\,d=d$ (where $\emptyset$ is the empty list).
\par\par\@@numbered@section{subsection}{toc}{Implementing the Data for Type in Coq}
\par Next we discuss in a series of notes, the implementation of Definition \ref{defoperad1} for {Type} in Coq, as well as the tools that were developed for use in this implementation.
\par\begin{note}If $\underline{c}$ has single entry $c:{\color{teal}\textbf{Type}}$, then $\textbf{Type}{c\choose\underline{c}}=c\rightarrow c$, which is the type of all functions with domain and range given by $c$. Then $\mathbbm{1}_{c}:=\text{id}_{c}$, the identity function on $c$.
\end{note}\par\begin{note}Our motivation is to provide the equivalent of Example \ref{exsets} within Coq, and the analogous isomorphism for the operad $\textbf{Sets}_{T}$ is,
\par$$\text{Hom}(c_{0}\times\cdots\times c_{n-1},d)\cong\text{Hom}(c_{\sigma(0)}\times\cdots\times c_{\sigma(n-1)},d),$$\par given $\underline{c}=c_{0},\ldots,c_{n-1}$ and a permutation $\sigma$ on $n$ letters. The isomorphism in the context of Coq asks us to construct a bijection between the two sets above. Following Definition \ref{operadnote1} and comments in Remark \ref{operadnote1remark}, we can translate this into Coq for $\textbf{Type}$ as: for all $d:{\color{teal}\textbf{Type}}$, $\underline{c},\underline{c}^{\prime}:\textbf{list}\,{\color{teal}\textbf{Type}}$ with the length $\underline{c}$ at least $1$, and $\textbf{Permutation}\,\underline{c}\,\underline{c}^{\prime}$, there is a bijection between $\textbf{Type}{d\choose\underline{c}},\textbf{Type}{d\choose\underline{c}^{\prime}}:{\color{teal}\textbf{Type}}$.
\par We can prove this in Coq using induction on the length of $\underline{c}$, along with some preceding lemmas about the behavior of function composition and isomorphism in this setting.
\end{note}\par\begin{note}Lastly, we need to write (3) of Definition \ref{operadnote1} for $\textbf{Type}$ in Coq. Writing $\textbf{Type}{d\choose\underline{c}}$ in the curried form, as opposed to using a verbatim translation of $\textbf{Sets}_{T}{d\choose\underline{c}}$ from Example \ref{exsets}, provides the needed flexibility, via partial application, to implement the multi-composition function $\circ_{i}$ for $\textbf{Type}$ in Coq with respect to (3) of Definition \ref{defoperad1}. The most important piece of our definition in Coq is that we define a recursive function $\textbf{compose}$ with type signature
\par$$\textbf{arr}\,\underline{c}^{\prime}\,(t\rightarrow t^{\prime})\rightarrow\textbf{arr}\,\underline{b}\,t\rightarrow\textbf{arr}\,\underline{c}^{\prime}\,(\textbf{arr}\,\underline{b}\,t^{\prime});$$\par where $t,t^{\prime}:{\color{teal}\textbf{Type}}$, and $\underline{c}^{\prime},\underline{b}:\textbf{list}\,{\color{teal}\textbf{Type}}$. If $\underline{c}=c_{0},\ldots,c_{i-1},c_{i},c_{i+1},\ldots,c_{n-1}$, we let $\underline{c}^{\prime}=c_{0},\ldots,c_{i-1}$, $t=c_{i}$, and $t^{\prime}=c_{i}\rightarrow c_{i+1}\rightarrow\cdots\rightarrow c_{n-1}\rightarrow d$, and this gives us, provided the correct type inference is written in, the required multi-composition operator $\circ_{i}$ for $\textbf{Type}$.
\end{note}\par\par\@@numbered@section{subsection}{toc}{Implementing the Axioms for Type in Coq}
\par Definition \ref{defoperad1} provides the base to build the axioms of an operad, which are given in Definition \ref{defoperad2}, and we discuss our implementation in Coq of this here. There are several axioms listed in Definition \ref{defoperad2}, and as in Note \ref{operadnote2}, we keep our discussion focused on the horizontal associativity axiom (1 of Definition \ref{defoperad2}), as the proof that $\textbf{Type}$ satisfies all other axioms in Definition \ref{defoperad2} follows from a similar procedure in Coq.
\par Our first hurdle comes from noticing that our definition for $\circ_{i}$ in Note \ref{circi in Coq} is what we want mathematically, but that Coq does not automatically recognize the equality of types:
\par$$\underline{c}^{\prime}\,(\textbf{arr}\,\underline{b}\,t^{\prime})=\textbf{arr}(\underline{c}\bullet_{i}\underline{b})\,d,$$\par where $\underline{c}=c_{0},\ldots,c_{i-1},c_{i},c_{i+1},\ldots,c_{n-1}$, $\underline{c}^{\prime}=c_{0},\ldots,c_{i-1}$, $t=c_{i}$, $t^{\prime}=c_{i}\rightarrow c_{i+1}\rightarrow\cdots\rightarrow c_{n-1}\rightarrow d$, so that (see 3 of Definition \ref{defoperad1}) $\underline{c}\bullet_{i}b=c_{0},\ldots,c_{i-1},\underline{b},c_{i+1},\ldots,c_{n-1}$. Since we require for $f:\textbf{Type}{d\choose\underline{c}},g:\textbf{Type}{c_{i}\choose\underline{b}}$ that $f\circ_{i}g:\textbf{Type}{d\choose\underline{c}\bullet_{i}\underline{b}}$, this presents an issue whose solution is, as in Note \ref{operadnote2}, a type casting function.
\par The remainder of our formalization of $\textbf{Type}$ within Coq is a tour de force of type casting, and we discuss the tools we use in this proof below. First, we give the formal definition we use for a type cast within Coq.
\par\begin{definition}Given $A,B:{\color{teal}\textbf{Type}}$, and an equation, $A=B$, a {type cast} $\mathcal{C}_{A=B}$ is a function such that for $a:A$, $\mathcal{C}_{A=B}\,a:B$.
\end{definition}\par\par In order to manipulate the type casts that occur throughout our proof that $\textbf{Type}$ satisfies the axioms in Definition \ref{defoperad2}, we prove a handful of general facts about type casts in Coq, which we discuss below.
\par\begin{note}\begin{enumerate}\enumerate@item@The composition two type casts is a type cast: given equations of types $A=B$ and $B=C$, we have $\mathcal{C}_{B=C}\circ\mathcal{C}_{A=B}=\mathcal{C}_{A=C}$.
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@A type cast using an equation of types $A=A$ (i.e., a type cast between two types Coq recognizes as identical) is equal to the identity: $\mathcal{C}_{A=A}\,a=a$ for $a:A$.
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@Two type casts between the same two types (i.e., both using equations of type $A=B$) are equal: for all $a:A$, $\mathcal{C}_{A=B}\,a=\mathcal{C}^{\prime}_{A=B}\,a$.
\par\vskip 4.0pt\vskip 4.0pt plus 2.0pt minus 1.0pt\enumerate@item@Type casting a function and then applying it to an argument is the same as applying the original function to an argument that had been type cast: if $f:B\rightarrow C$ and $a:A$, then $(\mathcal{C}_{A\rightarrow B=B\rightarrow C}\,f)\,a=f\,(\mathcal{C}_{A=B}\,a)$
\end{enumerate}\end{note}\par These facts smooth the process of showing $\textbf{Type}$ satisfies the operad axioms of Definition \ref{defoperad2}, as this involves manipulations of several type casts. For example, 2 and 3 of Note \ref{tcnote} ensure that it is not necessary to keep track of how these manipulations impact the \emph{equations} on which the type casts rely, since we need only that the \emph{types} involved match in order to show equality.
\par Now we discuss how to utilize the facts we demonstrated in Note \ref{tcnote}, by discussing their use in our proof the horizontal associativity axiom (1 of Definition \ref{defoperad2}) is satisfied in $\textbf{Type}$. Our first step is to prove the following key lemma of equality involving the {compose} function:
\par\par\par\begin{equation}\textbf{compose}\,(\,\mathcal{C}\,(\,\textbf{compose}\,(\,\mathcal{C}\,\alpha\,)\,\beta\,)\,)\,\gamma=\\
\mathcal{C}\,(\,\textbf{compose}\,(\,\mathcal{C}\,(\,\textbf{compose}\,(\,\mathcal{C}\,\alpha\,)\,\gamma\,)\,)\,\beta\,).\end{equation}\par Here, $\alpha,\beta,\gamma$ are terms of the appropriate types in the operad $\textbf{Type}$, and the type casting equations have been suppressed from the notation. We can show the equality in Equation \ref{eq:compHaa} by induction on the appropriate lists and several uses of 4 of Note \ref{tcnote}. Notice that Equation \ref{eq:compHaa} is essentially the horizontal associativity axiom in $\textbf{Type}$, and this is the case: to prove the horizontal associativity axiom, we manipulate type casts using our work in Note \ref{tcnote} until they match the equality in Equation \ref{eq:compHaa}.
\par Demonstrating the remainder of the axioms in Definition \ref{defoperad2} for $\textbf{Type}$ within Coq follows a similar pattern: show the pattern for the given axiom holds for {compose}, and then manipulate the type casts appropriately using Note \ref{tcnote} to arrive at the desired axiom.
\par\par\par\@@numbered@section{section}{toc}{Related Work }
In \cite[cite]{[\@@bibref{}{HH}{}{}]}, the authors present a formalization of a simpler type of an operad using Cubical Agda, which is an extension of Agda with Cubical Type Theory. Cubical Type Theory is an alternative to Homotopy type theory that is more directly amenable to constructive interpretations, so fully understanding the implementation of operads in \cite[cite]{[\@@bibref{}{HH}{}{}]} requires a working knowledge of a variant of Homotopy type theory, as well as how to use its implementation in Agda.
\par Moreover, Agda does not have significant automation, so showing, for example, our proof in Section \ref{forproofop} would require {significantly} more work. However, we do not think that our work would be impossible to translate into Agda, just require much more boilerplate code (e.g. handwriting structural induction tactics).
\par We also want to compare what was formalized in our work to that of \cite[cite]{[\@@bibref{}{HH}{}{}]}. What they use in \cite[cite]{[\@@bibref{}{HH}{}{}]} to refer to an operad is an operad with a collection of types $T$ for which $|T|=1$. In particular, $\mathcal{O}{d\choose\underline{c}}$ can be parametrized by the natural numbers, so we can write $\mathcal{P}(n):=\mathcal{O}{d\choose\underline{c}}$, if $|\underline{c}|=n$, where $\underline{c}=c_{0},\ldots,c_{n-1}$, with $c_{i}=d$. Moreover, there is a unique identity ($1\in\mathcal{P}(1)$), the functions $\circ_{i}$ have type $\mathcal{P}(n)\rightarrow\mathcal{P}(m)\rightarrow\mathcal{P}(n+m-1)$, and there is a significant simplification of the associativity axioms in Definition \ref{defoperad2}. We also note \cite[cite]{[\@@bibref{}{HH}{}{}]} they define their singly-colored operads to have the {equivariance axiom} given in \cite[cite]{[\@@bibref{}{MR3837179}{}{}]}.
