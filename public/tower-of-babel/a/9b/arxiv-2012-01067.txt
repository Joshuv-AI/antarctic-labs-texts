Abstract
. Liveness properties, such as termination, of even the simplest shared-memory concurrent programs under sequential consistency typically require some fairness assumptions about the scheduler. Under weak memory models, we observe that the standard notions of thread fairness are insufficient, and an additional fairness property, which we call memory fairness , is needed. In this paper, we propose a uniform definition for memory fairness that can be integrated into any declarative memory model enforcing acyclicity of the union of the program order and the reads-from relation. For the well-known models, SC, x86-TSO, RA, and StrongCOH, that have equivalent operational and declarative presentations, we show that our declarative memory fairness condition is equivalent to an intuitive model-specific operational notion of memory fairness, which requires the memory system to fairly execute its internal propagation steps. Our fairness condition preserves the correctness of local transformations and the compilation scheme from RC11 to x86-TSO, and also enables the first formal proofs of termination of mutual exclusion lock implementations under declarative weak memory models.

1.
Introduction

Suppose we want to prove termination of a concurrent program under a
full-featured weak memory model, such as RC11
(
Lahav
et al. 2017
)
.
Sadly, this is not currently possible because RC11 does not support reasoning about liveness.
Extending its formal definition to enable reasoning about liveness properties
is very important because, as shown by
Oberhauser
et al. 2021a
,
multiple existing mutual exclusion lock implementations hang if too few fences are used.
This is also the case for the published version of the HMCS algorithm
(
Chabbi
et al. 2015
)
:
it contains such a termination bug, a simplified version of which we describe in
Section

5.3
.

Termination of concurrent programs typically relies on some fairness assumptions about
concurrency as illustrated by the following program, whose variables are initialized with
0
.

(SpinLoop)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}x:=1\end{array}&\begin{array}[]{@{}l@{}}\textbf{{repeat}}\;\{\;a:=x\;\}\;\textbf{{until}}\;(a\neq 0)\end{array}\end{array}

Under
sequential consistency
(SC), the program can diverge if,
e.g.,
thread 2 is always scheduled and thread 1 never gets a chance to run.
This run is considered unfair because although thread 1 is always available to be scheduled, it is never selected.
A standard assumption is
thread fairness

(which is typically simply called fairness in the literature
(
Lamport 1977
;
Park 1979
;
Lehmann
et al. 1981
;
Francez 1986
)
),
namely that every (unblocked) non-terminated thread is eventually scheduled.
With a fair scheduler,
SpinLoop
is guaranteed to terminate.

Under weak memory consistency,
thread fairness alone does not suffice to ensure termination of
SpinLoop

because merely executing the
x:=1
write does not mean that
its effect is propagated to the other threads.
Take, for example, the operational TSO model
(
Owens
et al. 2009
)
,
where writes are appended to a thread-local buffer
and are later asynchronously applied to the shared memory.
With such a model,
it is possible that the
x:=1
write is forever stuck in the first thread’s buffer
and so thread 2 never gets a chance to read
x=1
.
To rule out such behaviors, we introduce another property,
memory fairness
(MF),
that ensures that threads do not indefinitely observe the same stale memory state.

Operational models can easily be extended to support MF by requiring fairness of the
internal transitions of the model,
which correspond to the propagation of writes to the different threads.
For the standard interleaving semantics of SC
(
Lamport 1979
)
,
MF holds vacuously (because the model does not have any internal transitions).
For the usual TSO operational model
(
Owens
et al. 2009
)
, MF requires that every buffered write eventually propagates to the main memory.
For the operational characterization of
release-acquire
(RA)
following
Kang
et al. 2017
, more adaptations are necessary:
(1) we constrain the timestamp ordering
so that no write can overtake infinitely many other writes;
and (2) add a transition that forcefully updates the views of threads
so that all executed writes eventually become globally visible.
The same criteria are required for MF in the model of
strong coherence
(StrongCOH),
which is essentially a restriction of the promise-free fragment of
Kang
et al. 2017
’s model (as well as of RC11)
to relaxed accesses.

In contrast, it is quite challenging to support MF in declarative (a.k.a. axiomatic) models,
which have become the norm for hardware architectures
(x86-TSO
(
Owens
et al. 2009
)
, Power
(
Alglave
et al. 2014
)
, Arm
(
Pulte et al. 2017
)
) and
programming languages (e.g., RC11
(
Lahav
et al. 2017
)
, OCaml
(
Dolan et al. 2018
)
,
JavaAtomics
(
Bender and
Palsberg 2019
)
, Javascript
(
Watt et al. 2020
)
,
WebAssembly
(
Watt
et al. 2019
)
) alike.
In these models, there are no explicit write propagation transitions so that MF could require them to eventually take place.
Further, the memory accesses of different threads are not even totally ordered,
so even the concept of an event eventually happening is not immediate.
We observe, however, neither internal transitions nor a total order are necessary for defining fairness;
what is important is that every event is preceded by only a finite number of other events,
and this can be defined on the execution graphs used by declarative models.

Specifically, for declarative models satisfying
({\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}})
-acyclicity
(
i.e.,
acyclicity of the union of the program order and the reads-from relation),
such as RC11, SC, TSO, RA, and StrongCOH,
we show that MF can be defined in a uniform fashion
as prefix-finiteness of the extended coherence order.
The latter is a relation used in declarative models to order accesses to the same location
for guaranteeing SC-per-location
(
Alglave
et al. 2014
)
.
Requiring this relation to be prefix-finite
means that in a fair execution no write can be preceded by an infinite number
of other events in this order (
e.g.,
reads that have not yet observed the write).

We justify the uniform declarative definition of memory fairness in three ways.
First,
we show that our declarative MF condition is equivalent to operational MF
for models that have equivalent declarative and operational presentations
(
i.e.,
SC, TSO, RA, and StrongCOH).
This requires extending the existing equivalence results between operational
and declarative models to
infinite
executions, and involves more
advanced constructions that make use of memory fairness.
Second, we show that including our MF condition in the RC11 declarative language model,
which currently lacks any fairness guarantees,
incurs no performance overhead: the correctness of local program
transformations and the compilation scheme to TSO are unaffected.
Third, we show that memory fairness allows lifting robustness theorems about
finite executions to infinite ones.

We finally demonstrate that our declarative MF condition enables verification
of liveness properties of concurrent programs under RC11
by verifying termination and/or fairness of multiple lock implementations
(see
Section

5
),
including the MCS lock once the fence missing in the presentation of
Chabbi
et al. 2015

is added.
Key to those proofs is a reduction theorem we show for the termination of
spinloops.
Under certain conditions about the program, which hold for multiple standard implementations, a spinloop terminates
under a fair model if and only if it exits whenever an iteration reads
only the latest writes in the coherence order. For example, the loop in

SpinLoop
terminates because reading the latest write (
x:=1
)
exits the loop.

What is a Fair Operational Semantics?

In this section, we define our operational framework and its fairness constraints.
We initially demonstrate our terminology for sequential consistency (SC).
In
Sections

2.1
,
2.2
and
2.3
, we instantiate our framework
to the total store order (TSO), release/acquire (RA), and strong coherence (StrongCOH) models,
and discuss memory fairness in each of these models.

Labeled Transition Systems.

Our formal development is based on
labeled transition systems
(LTSs),
which we use to represent both programs and operational memory models.
We assume that the transition labels of these systems are split between

(externally) observable transition labels
and
silent transition labels
.
Using transition labels we define a

trace
to be a (finite or infinite) sequence of transition labels (of any kind);
whereas an
observable trace
is a
(finite or infinite) sequence of observable transition labels.
Then, LTSs capture sets of traces and observable traces
in the standard way, which is formulated below.

Formally, we define an LTS
{A}
to be a tuple

{\langle{Q,\Sigma,\Theta,\mathit{init},\xrightarrow{}}\rangle}
, where
Q
is a set of
states
,

\Sigma
is a set of
observable transition labels
,

\Theta
is a set of
silent transition labels
,

\mathit{init}\in Q
is the
initial state
,
and
{\xrightarrow{}}\subseteq Q\times(\Sigma\uplus\Theta)\times Q
is a set of
transitions
.
We denote by
{A}.{\mathtt{Q}}
,
{A}.{\mathbf{\Sigma}}
,
{A}.{\mathbf{\Theta}}
,
{A}.{\mathtt{init}}
, and
\xrightarrow{}_{{A}}
the components of an LTS
{A}
.

We denote by
{\mathtt{src}}(t)
,
{\mathtt{tlab}}(t)
, and
{\mathtt{tgt}}(t)
the three components of a transition
t\in\,\xrightarrow{}
.
For
\sigma\in\Sigma\uplus\Theta
,
we write
\mathrel{\raisebox{-0.8pt}{$\xrightarrow{\sigma}$}}
for the relation
\{{{\langle{{\mathtt{src}}(t),{\mathtt{tgt}}(t)}\rangle}\;|\;t\in{}\xrightarrow{},{\mathtt{tlab}}(t)=\sigma}\}
.
We use
\xrightarrow{}
for the relation
\bigcup_{\sigma\in\Sigma\uplus\Theta}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{\sigma}$}}
.
We say that a transition label
\sigma\in\Sigma\uplus\Theta
is
enabled
in some state
q\in Q

if
q\mathrel{\raisebox{-0.8pt}{$\xrightarrow{\sigma}$}}q^{\prime}
for some
q^{\prime}\in Q
.

A
run
of
{A}
is a (finite or infinite) sequence
\mu
of transitions in
\xrightarrow{}_{{A}}
such that

{\mathtt{src}}(\mu(0))={A}.{\mathtt{init}}
and
{\mathtt{tgt}}(\mu(k-1))={\mathtt{src}}(\mu(k))
for every
k\geq 1
in
\textit{dom}{({\mu})}
.
A run
\mu
of
{A}

induces
the trace
\rho
if
\rho(k)={\mathtt{tlab}}(\mu(k))
for every
k\in\textit{dom}{({\mu})}
.
Also,
\mu
induces the
observable
trace
\rho^{\prime}
if
\rho^{\prime}
is the restriction
to
\Sigma
of some trace
\rho
that is induced by
\mu
.

An (observable) trace
\rho
is called an (observable) trace of
{A}
if it is induced by some run of
{A}
.
We write
\mathsf{OTr}({{A}})
for the set of all observable traces of
{A}

and
\mathsf{OTr^{fin}}({{A}})
for the set of all finite observable traces of
{A}
.

Domains and Event Labels.

To define programs and their semantics, we fix sets

\mathsf{Loc}
,
\mathsf{Tid}
, and
\mathsf{Val}
of
(shared) locations
,
thread identifiers
, and

(respectively).
We assume that
\mathsf{Val}
contains a distinguished value

, which serves as the initial value for all locations.
In addition, we assume that
\mathsf{Tid}
is finite, given by
\mathsf{Tid}=\{{1,2{,}\ldots{,}N}\}

.
(Our main result below requires

.)
We use

to range over
\mathsf{Loc}
;

to range over
\mathsf{Tid}
;
and

to range over
\mathsf{Val}
.
Programs interact with the memory using

, defined as follows.

Definition 2.1.

An

is one of the following:

•

Read event label:
{{\mathtt{R}}}({{x}},{v_{\mathtt{R}}})
where
{x}\in\mathsf{Loc}
and
v_{\mathtt{R}}\in\mathsf{Val}
.

•

Write event label:
{{\mathtt{W}}}({{x}},{v_{\mathtt{W}}})
where
{x}\in\mathsf{Loc}
and
v_{\mathtt{W}}\in\mathsf{Val}
.

•

Read-modify-write label:
{{\mathtt{RMW}}}({{x}},{v_{\mathtt{R}}},{v_{\mathtt{W}}})
where
{x}\in\mathsf{Loc}
and

.

The functions
{\mathtt{typ}}
,
{\mathtt{loc}}
,
{\mathtt{val_{r}}}
, and
{\mathtt{val_{w}}}

return (when applicable) the type (
{\mathtt{R}}/{\mathtt{W}}/{\mathtt{RMW}}
), location (
{x}
),

), and written value (

) of a given event label

.
We denote by

the set of all event labels.

Remark 1.

For conciseness, we have not included

in the set of event labels.
In TSO
(
Owens
et al. 2009
)
and RA
(

et al. 2016
)
,

to an otherwise-unused distinguished location

Remark 2.

Rich programming languages like C/C++
(
Batty
et al. 2011
)

and Java
(
Bender and
Palsberg 2019
)

This requires us to extend our event labels with additional modifiers.
However, simple event labels as defined above suffice for the purpose of this paper.

Sequential Programs.

To keep the presentation abstract, we do not fix a particular programming language,
but rather represent sequential (thread-local) programs as LTSs
with
\mathsf{ELab}
, the set of all event labels, serving as the set of observable transition labels.
For simplicity, we assume that sequential programs do not have silent transitions.

In our code snippets throughout the paper, we implicitly assume such a standard interpretation.

We refer to observable traces of sequential programs (

Concurrent Programs.

A
concurrent program
, which we also simply call a
program
,
is a top-level parallel composition of sequential programs,
defined as a
finite
mapping assigning a sequential program to each thread
{\tau}\in\mathsf{Tid}
.
A concurrent program
{P}
induces an LTS
with
\mathsf{Tid}\times\mathsf{ELab}
serving as the set of observable transition labels
(and no silent transition labels).
This LTS follows the interleaving semantics of
{P}
:
its states are tuples in
\prod_{{\tau}\in\mathsf{Tid}}{P}({\tau}).{\mathtt{Q}}
;
the initial state is
\lambda{\tau}.\;{P}({\tau}).{\mathtt{init}}
;
and the transitions are given by:

\frac{\overline{p}({\tau})\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{l}}$}}_{{P}({\tau})}p\quad}{\overline{p}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{l}}$}}_{P}\overline{p}[{\tau}\mapsto p]}

In the sequel, we identify concurrent programs with their induced LTSs.

We refer to observable traces of concurrent programs (
i.e.,
sequences over
\mathsf{Tid}\times\mathsf{ELab}
)
as
concurrent traces
.
We denote the two components of a pair
\sigma\in\mathsf{Tid}\times\mathsf{ELab}

by
{\mathtt{tid}}(\sigma)
and
{\mathtt{elab}}(\sigma)
respectively.

Behaviors.

We define a
behavior
to be a function
\beta
assigning a sequential trace to every thread,
since the events executed by each thread capture precisely what it has observed
about the memory system.

Notation 2.3.

The restriction of a concurrent trace
\rho
to thread
{\tau}\in\mathsf{Tid}
,
denoted by
\rho|_{{\tau}}
, is the sequence obtained from
\rho

by keeping only the transition labels of the form
{\tau}:\_
.

Definition 2.4.

The
behavior induced by a concurrent trace

\rho
, denoted by
\beta(\rho)
,
is given by

\beta(\rho)\triangleq\lambda{\tau}\in\mathsf{Tid}.\;\lambda k\in\textit{dom}{({\rho|_{{\tau}}})}.\;{\mathtt{elab}}(\rho|_{{\tau}}(k)).

This notation is extended to sets of concurrent traces in the obvious way
(
\beta(S)\triangleq\{{\beta(\rho)\;|\;\rho\in S}\}
).

Notation 2.5.

For an LTS
{A}
with
{A}.{\mathbf{\Sigma}}=\mathsf{Tid}\times\mathsf{ELab}
,
we denote by
\mathsf{B}({{A}})
the set of behaviors induced by observable traces of
{A}

(
i.e.,

\mathsf{B}({{A}})\triangleq\beta(\mathsf{OTr}({{A}}))
)
and by
\mathsf{B^{fin}}({{A}})
the set of behaviors induced by finite observable traces of
{A}

(
i.e.,

\mathsf{B^{fin}}({{A}})\triangleq\beta(\mathsf{OTr^{fin}}({{A}}))
).

Since operations of different threads commute in the program semantics,
the following property easily follows from our definitions.

Proposition 2.6.

For every program
{P}
,
if
\beta(\rho_{1})=\beta(\rho_{2})
, then

\rho_{1}\in\mathsf{OTr}({{P}})

\rho_{2}\in\mathsf{OTr}({{P}})
.

Thread Fairness.

Not all program behaviors are fair.

Example 2.7.

Consider the following program:

(
Rloop
)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}{x}\;{:=}\;1\end{array}&\begin{array}[]{@{}l@{}}L\colon a\;{:=}\;{x}\\
\phantom{L\colon}\textbf{{if}}\;a=0\;\textbf{{goto}}\;L\end{array}\end{array}

assigning
{{\mathtt{W}}}({{x}},{1})
to the first thread
and
{{\mathtt{R}}}({{x}},{1})
to the second,

and the infinite sequence

This behavior occurs if an unfair scheduler only schedules the second thread to run even though the first thread is always
available to execute.

2

On this level, without considering a particular memory system (as defined below),

Memory Systems.

To give operational semantics to programs,
we synchronize them with
memory systems
,
which, like programs, are LTSs with
\mathsf{Tid}\times\mathsf{ELab}
serving as the set of observable transition labels.
In addition, memory systems have silent transition labels, which vary from one system to another.
Intuitively, the set of silent transition labels
{\mathcal{M}}.{\mathbf{\Theta}}
of a memory system
{\mathcal{M}}

consists of internal actions that the program cannot observe
(
e.g.,
cache-related operations).

The most well-known memory system is that of
sequential consistency

(
Lamport 1979
)
,
denoted here by
{\mathcal{M}}_{\mathsf{SC}}
,
in which writes by each thread are made immediately visible to all other threads.

{\mathcal{M}}_{\mathsf{SC}}
tracks the most recent value written to each location.
Its initial state maps each location to zero.
That is,
{\mathcal{M}}_{\mathsf{SC}}.{\mathtt{Q}}\triangleq\mathsf{Loc}\to\mathsf{Val}
and
{\mathcal{M}}_{\mathsf{SC}}.{\mathtt{init}}\triangleq\lambda{x}.\;0
.
The system
{\mathcal{M}}_{\mathsf{SC}}
has no silent transitions (
{\mathcal{M}}_{\mathsf{SC}}.{\mathbf{\Theta}}=\emptyset
)
and its transition relation
\xrightarrow{}_{{\mathcal{M}}_{\mathsf{SC}}}
is defined as follows:

\frac{{M}^{\prime}={M}[{x}\mapsto v]}{{{M}}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{W}}}({{x}},{v})}$}}_{{\mathcal{M}}_{\mathsf{SC}}}{{M}^{\prime}}}\frac{{M}({x})=v}{{{M}}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{R}}}({{x}},{v})}$}}_{{\mathcal{M}}_{\mathsf{SC}}}{{M}}}\frac{{{M}}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{R}}}({{x}},{v_{\mathtt{R}}})}$}}_{{\mathcal{M}}_{\mathsf{SC}}}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{W}}}({{x}},{v_{\mathtt{W}}})}$}}_{{\mathcal{M}}_{\mathsf{SC}}}{{M}^{\prime}}}{{{M}}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{RMW}}}({{x}},{v_{\mathtt{R}}},{v_{\mathtt{W}}})}$}}_{{\mathcal{M}}_{\mathsf{SC}}}{{M}^{\prime}}}

Writing
v
to
{x}
simply updates the value of
{x}
stored in
{M}
.
(
{M}[{x}\mapsto v]
is the function that maps
{x}
to
v

and all other locations
{y}
to
{M}({y})
.)
Reading
v
from
{x}
succeeds iff the value stored for
{x}
in memory is
v
.
The atomic read-modify-write
{{\mathtt{RMW}}}({{x}},{v_{\mathtt{R}}},{v_{\mathtt{W}}})

reads location
{x}
yielding value
v_{\mathtt{R}}
and immediately writes
v_{\mathtt{W}}
to it.
Note that
{\mathcal{M}}_{\mathsf{SC}}
is oblivious to the thread that takes the action
(
\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{l}}$}}_{{\mathcal{M}}_{\mathsf{SC}}}=\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\pi}:{l}}$}}_{{\mathcal{M}}_{\mathsf{SC}}}
).
The other memory systems below do not have this property.

Linking Programs and Memory Systems.

By linking programs and memory systems, we
can talk about the behavior of a program
{P}
under a memory system
{\mathcal{M}}
.
We say that a certain behavior
\beta
is a
behavior of a program

under a memory system

if
\beta
is both a behavior of
{P}
and a behavior of
{\mathcal{M}}

(
i.e.,

\beta\in\mathsf{B}({{P}})\cap\mathsf{B}({{\mathcal{M}}})
).
Similarly,
\beta
is called a
thread-fair behavior of
{P}
under
{\mathcal{M}}

if
\beta\in\mathsf{B^{tf}}({{P}})\cap\mathsf{B}({{\mathcal{M}}})
.

Let
{P}
be a program,
{\mathcal{M}}
be a memory system,
and
\beta
be a behavior.

•

\beta
is a behavior of
{P}
under
{\mathcal{M}}
iff

\beta=\beta(\rho)
for some
\rho\in\mathsf{OTr}({{P}})\cap\mathsf{OTr}({{\mathcal{M}}})
.

•

\beta
is a thread-fair behavior of
{P}
under

iff

\beta=\beta(\rho)
for some

.

Example 2.11.

Thread-fair behaviors of the program
Rloop
under
{\mathcal{M}}_{\mathsf{SC}}
must be finite.
Indeed, in observable traces of
{\mathcal{M}}_{\mathsf{SC}}
, after the first thread performs
{{\mathtt{W}}}({{x}},{1})
,
the second thread will perform
{{\mathtt{R}}}({{x}},{1})
and terminate its execution.
The behavior
\beta_{\text{inf}}
that assigns the empty sequence to the first thread
and the infinite sequence consisting of
{{\mathtt{R}}}({{x}},{0})
event labels to the second thread
cannot be obtained from a thread-fair run of

.

Memory Fairness.

As we have already discussed, thread-fairness alone is often insufficient
to reason about termination under weak memory models.
For this reason, we introduce
memory fairness
(MF),
which ensures that a thread cannot be lagging behind indefinitely
because the memory system did not propagate certain updates to it.
We formalize this intuition by having MF require that the memory silent transitions
(responsible for such propagation steps) are scheduled infinitely often.

Definition 2.12.

Let
{\mathcal{M}}
be a memory system.

•

A silent transition label
\theta\in{\mathcal{M}}.{\mathbf{\Theta}}
is
continuously enabled at index
k
in an infinite run
\mu
of
{\mathcal{M}}

if it is enabled in
{\mathtt{src}}(\mu(j))
for every index
j\geq k
.
The label
\theta
is
continuously enabled
in
\mu
if it is continuously enabled in
\mu
at some index
k
.

•

A run
\mu
of
{\mathcal{M}}
is
memory-fair
if
\mu
is finite or
for every silent memory transition label
\theta\in{\mathcal{M}}.{\mathbf{\Theta}}
and index
k

such that
\theta
is continuously enabled in
\mu
at
k
,
there exists
j\geq k
such that
{\mathtt{tlab}}(\mu(j))=\theta
.

•

A
memory-fair observable trace of
{\mathcal{M}}
is any concurrent trace induced
by a memory-fair run of
{\mathcal{M}}
.

•

A
memory-fair behavior of
{\mathcal{M}}
is any behavior induced
by a memory-fair observable trace of
{\mathcal{M}}
.
We denote by
\mathsf{B^{mf}}({{\mathcal{M}}})
the set of all memory-fair behaviors of
{\mathcal{M}}
.

Linking this definition with programs,
we say that a certain behavior
\beta
is a
memory-fair behavior of a program
{P}
under a memory system
{\mathcal{M}}

if
\beta\in\mathsf{B}({{P}})\cap\mathsf{B^{mf}}({{\mathcal{M}}})
.
Similarly,
\beta
is called a
thread&memory-fair behavior of
{P}
under
{\mathcal{M}}

if
\beta\in\mathsf{B^{tf}}({{P}})\cap\mathsf{B^{mf}}({{\mathcal{M}}})
.

Proposition 2.13.

Let
{P}
be a program,
{\mathcal{M}}
be a memory system,
and
\beta
be a behavior.

•

\beta
is a memory-fair behavior of
{P}
under
{\mathcal{M}}
iff

\beta=\beta(\rho)
for some observable trace
\rho
of
{P}

that is also a memory-fair observable trace of
{\mathcal{M}}
.

•

\beta
is a thread&memory-fair behavior of

under
{\mathcal{M}}
iff

\beta=\beta(\rho)
for some thread-fair observable trace
\rho
of
{P}

that is also a memory-fair observable trace of
{\mathcal{M}}
.

Since
{\mathcal{M}}_{\mathsf{SC}}.{\mathbf{\Theta}}=\emptyset
,
every behavior of a program
{P}
under
{{\mathcal{M}}_{\mathsf{SC}}}
is (vacuously) memory-fair.

Example 2.14.

Consider the following program (assuming that
{x}
is initialized to
0
):

(WWRloop)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}L_{1}\colon{x}\;{:=}\;1\\
\phantom{L_{1}\colon}{x}\;{:=}\;0\\
\phantom{L_{1}\colon}\textbf{{goto}}\;L_{1}\end{array}&\begin{array}[]{@{}l@{}}L_{2}\colon a\;{:=}\;{x}\\
\phantom{L_{2}\colon}\textbf{{if}}\;a=0\;\textbf{{goto}}\;L_{2}\\
\end{array}\end{array}

The infinite behavior that assigns the infinite sequences

{{\mathtt{W}}}({{x}},{1}),{{\mathtt{W}}}({{x}},{0}),{{\mathtt{W}}}({{x}},{1}),{{\mathtt{W}}}({{x}},{0}),\ldots
,
and
{{\mathtt{R}}}({{x}},{0}),{{\mathtt{R}}}({{x}},{0}),\ldots

to the first and second threads (respectively)
is a thread&memory-fair behavior of this program under
{{\mathcal{M}}_{\mathsf{SC}}}
:
in a corresponding run both threads
are executed infinitely often.
In particular, note that our definitions require that transitions that are
continuously
enabled
are eventually taken, and while the transition
{{\mathtt{R}}}({{x}},{1})
is infinitely often enabled for the second thread,
it is not continuously enabled.

Next, we demonstrate three weaker memory systems with non-empty sets of silent transitions
that have non-memory-fair traces.
In these systems, whether a program terminates or deadlocks may crucially depend on memory fairness.

2.1.
The Total Store Order Memory System

We instantiate memory fairness to the “Total Store Order” (TSO) model
(
Sewell et al. 2010
;
Owens
et al. 2009
)

of the x86 architecture.
This memory system, denoted by
{\mathcal{M}}_{\mathsf{TSO}}
, is defined by:

(1)

{\mathcal{M}}_{\mathsf{TSO}}.{\mathtt{Q}}\triangleq(\mathsf{Loc}\to\mathsf{Val})\times(\mathsf{Tid}\to(\mathsf{Loc}\times\mathsf{Val})^{*})

(Each state consists of a memory and a per-thread store buffer.)

(2)

{\mathcal{M}}_{\mathsf{TSO}}.{\mathbf{\Theta}}\triangleq\{{{\mathtt{prop}}({\tau})\;|\;{\tau}\in\mathsf{Tid}}\}

(Silent transitions consist of a propagation label for every thread.)

(3)

{\mathcal{M}}_{\mathsf{TSO}}.{\mathtt{init}}\triangleq{\langle{{M}_{0},{B}_{0}}\rangle}
, where

{M}_{0}\triangleq\lambda{x}.\;0
and
{B}_{0}\triangleq\lambda{\tau}.\;\epsilon

(Initially, all buffers are empty.)

(4)

\xrightarrow{}_{{\mathcal{M}}_{\mathsf{TSO}}}
is given in
Fig.

1
.

In addition to the global memory

include a mapping

to every thread.
Writes are first written to the local buffer and later non-deterministically propagate to memory (in the order in which they were issued).
Reads read the most recent value of the relevant location in the thread’s buffer and refer to the memory if such value

RMWs can only execute when the thread’s buffer is empty and write their result

Example 2.15 (Store Buffering).

The following annotated behavior is

under
{\mathcal{M}}_{\mathsf{TSO}}
(but not under
{\mathcal{M}}_{\mathsf{SC}}

(SB)

Then, when the second thread runs, it reads the initial value (

from the memory.

Example 2.16.

Revisiting the

program from
Section

2
,
unlike under

under

include
the (infinite) behavior assigning the

to the first thread
and the infinite sequence
{{\mathtt{R}}}({{x}},{0}),{{\mathtt{R}}}({{x}},{0}),\ldots
to the second.
Indeed, the entry

may indefinitely remain in the first thread’s buffer,
so that

is never executed from the point of view of the second thread.

Indeed, in runs inducing this infinite behavior, the silent memory transition

is necessarily continuously enabled.
Memory fairness requires that
{\mathtt{prop}}(1)
will be eventually executed,
and from that point on

prohibits the second thread from executing
{{\mathtt{R}}}({{x}},{0})
.

We note that the notion of memory fairness is sensitive to the choice of
silent memory transitions.
For example, consider an alternative memory system, denoted by
{\mathcal{M}}_{\mathsf{TSO}}^{\prime}
,
with less informative silent transition labels that do not record the thread identifier of the propagated write.
(Formally
{\mathcal{M}}_{\mathsf{TSO}}^{\prime}
is defined just like
{\mathcal{M}}_{\mathsf{TSO}}
except for

,

Then,

induces the same set of behaviors as
{\mathcal{M}}_{\mathsf{TSO}}

but not the same set of

behaviors.
In particular, we can extend the
Rloop
program with an additional thread that constantly writes
to some unrelated location

,
and obtain a memory fair run of
{\mathcal{M}}_{\mathsf{TSO}}^{\prime}

by infinitely often propagating a write to
{y}
,
but never propagating the
{{\mathtt{W}}}({{x}},{1})
entry.

2.2.
The Release/Acquire Memory System

We instantiate our operational framework with a memory system for Release/Acquire (RA),
enriched with silent memory transitions for capturing fair behaviors.
Here we follow an operational formulation of RA from
Kaiser et al. 2017
,
based on the Promising Semantics of
Kang
et al. 2017
.

The memory of the RA system records a (finite) set of
messages
,
each of which corresponds to some write that was previously executed.
Messages (of the same location) are ordered using
timestamps
,
and carry a
view
—a mapping from locations to timestamps.
In turn, the states of this memory system also keep track of the current view of each thread,
and use these views to confine the set of messages that threads may read and write.
In particular, if a thread has observed (either by reading or by writing itself)
a message whose view
\mathit{V}
has
\mathit{V}({x})=t
,
then it can only read messages of
{x}
whose timestamp is greater than or equal to
t
.

To formally define this system, we let
\mathsf{Time}\triangleq{\mathbb{N}}
(using natural numbers as timestamps),

\mathsf{View}\triangleq\mathsf{Loc}\to\mathsf{Time}
(the set of views),
and
\mathsf{Msg}\triangleq\mathsf{Loc}\times\mathsf{Val}\times\mathsf{Time}\times\mathsf{View}
(the set of messages).
We denote a message
m
as a tuple of the form
{\langle{{x}:v@t,\mathit{V}}\rangle}
,
where
{x}\in\mathsf{Loc}
,
v\in\mathsf{Val}
,
t\in\mathsf{Time}
, and
\mathit{V}\in\mathsf{View}
.
We write
{\mathtt{loc}}(m)
,
{\mathtt{val}}(m)
,
{\mathtt{ts}}(m)
, and
{\mathtt{view}}(m)

to refer to the components of a message
m
.
The usual order
<
on natural numbers is lifted pointwise to a partial order on views;

\sqcup
denotes the pointwise maximum on views;
and
\mathit{V}_{0}
is the minimum view
(
\mathit{V}_{0}\triangleq\lambda{x}.\;0
).

With these definitions and notations, the RA memory system, denoted here by
{\mathcal{M}}_{\mathsf{RA}}
, is defined as follows
(additional silent memory transitions are discussed below):

(1)

{\mathcal{M}}_{\mathsf{RA}}.{\mathtt{Q}}\triangleq\mathcal{P}({\mathsf{Msg}})\times(\mathsf{Tid}\to\mathsf{View})
.

(2)

{\mathcal{M}}_{\mathsf{RA}}.{\mathtt{init}}\triangleq{\langle{{M}_{0},\lambda{\tau}.\;\mathit{V}_{0}}\rangle}
, where
the initial memory is
{M}_{0}\triangleq\{{{\langle{{x}:0@0,\mathit{V}_{0}}\rangle}\;|\;{x}\in\mathsf{Loc}}\}
.

(3)

\xrightarrow{}_{{\mathcal{M}}_{\mathsf{RA}}}
is given in
Fig.

2
.

\frac{\nexists m\in{M}.\;{\mathtt{loc}}(m)={x}\land{\mathtt{ts}}(m)=t\quad\quad\mathit{T}({\tau})({x})<t\quad\quad\mathit{T}^{\prime}=\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})[{x}\mapsto t]]\quad\quad{M}^{\prime}={M}\cup\{{{\langle{{x}:v@t,\mathit{T}^{\prime}({\tau})}\rangle}}\}}{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{W}}}({{x}},{v})}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M}^{\prime},\mathit{T}^{\prime}}\rangle}}\frac{{\langle{{x}:v@t,\mathit{V}}\rangle}\in{M}\quad\quad\mathit{T}({\tau})({x})\leq t\quad\quad\mathit{T}^{\prime}=\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})\sqcup\mathit{V}]}{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{R}}}({{x}},{v})}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M},\mathit{T}^{\prime}}\rangle}}\frac{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{R}}}({{x}},{v_{\mathtt{R}}})}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M},\mathit{T}^{\prime}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{W}}}({{x}},{v_{\mathtt{W}}})}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M}^{\prime},\mathit{T}^{\prime\prime}}\rangle}\quad\mathit{T}^{\prime\prime}({\tau})({x})=\mathit{T}^{\prime}({\tau})({x})+1}{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{RMW}}}({{x}},{v_{\mathtt{R}}},{v_{\mathtt{W}}})}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M}^{\prime},\mathit{T}^{\prime\prime}}\rangle}}

Figure 2

Transitions of
{\mathcal{M}}_{\mathsf{RA}}

The states of
{\mathcal{M}}_{\mathsf{RA}}
consist of a set
{M}
of all messages added to the memory so far
and a mapping
\mathit{T}
assigning a view to each thread.
Write steps of thread
{\tau}
writing to location
{x}
pick a timestamp
t
that is fresh
(
\nexists m\in{M}.\;{\mathtt{loc}}(m)={x}\land{\mathtt{ts}}(m)=t
)
and greater than the latest timestamp that
{\tau}
has observed for
{x}

(
\mathit{T}({\tau})({x})<t
);
update the thread’s view to include this timestamp
(
\mathit{T}^{\prime}=\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})[{x}\mapsto t]]
);
and add a corresponding message to the memory carrying the (updated) thread view
(
{M}^{\prime}={M}\cup\{{{\langle{{x}:v@t,\mathit{T}^{\prime}({\tau})}\rangle}}\}
).
Read steps of thread
{\tau}
reading from location
{x}
pick a message from the current memory
(
{\langle{{x}:v@t,\mathit{V}}\rangle}\in{M}
) whose timestamp
is greater than or equal to the latest timestamp that
{\tau}
has observed for
{x}

(
\mathit{T}({\tau})({x})\leq t
);
and incorporate the message’s view in the thread view
(
\mathit{T}^{\prime}=\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})\sqcup\mathit{V}]
).
RMW steps are defined as atomic sequencing of a read step followed by a write step,
with the restriction that the new message’s (fresh) timestamp is the successor of the timestamp of the read message
(
\mathit{T}^{\prime\prime}({\tau})({x})=\mathit{T}^{\prime}({\tau})({x})+1
).
The latter condition is needed to ensure the atomicity of RMWs: no other write can intervene
between the read part and the write part of the RMW (
i.e.,
no message can be placed between
the read and the written messages in the timestamp order).

Example 2.17 (Message passing).

The following annotated behavior is
disallowed
under
{\mathcal{M}}_{\mathsf{RA}}
:

(MP)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}{x}\;{:=}\;1\\
{y}\;{:=}\;1\end{array}&\begin{array}[]{@{}l@{}}a\;{:=}\;{y}\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 1}}\\
b\;{:=}\;{x}\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 0}}\end{array}\end{array}

Indeed, the second thread can read
1
for
{y}
,
only after the first thread added two messages

m_{x}={\langle{{x}:1@t_{x},[{x}\mapsto t_{x}]}\rangle}

and

m_{y}={\langle{{y}:1@t_{y},[{x}\mapsto t_{x},{y}\mapsto t_{y}]}\rangle}
to the memory
with
t_{x},t_{y}>0
.
When reading
m_{y}
, the second thread increases its view of
{x}
to be
t_{x}
.
Since
t_{x}>0
, it is then unable to read the initial message of
{x}
,
and must read
m_{x}
.

Example 2.18.

By forcing RMWs to use the successor of the read message as the timestamp of the written message,

{\mathcal{M}}_{\mathsf{RA}}
forbids different RMWs to read the same message.
To see this, consider the following example (where
FADD
denotes an atomic fetch-and-add instruction
that returns its read value):

(2RMW)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}a\;{:=}\;\textbf{{FADD}}({{x}},{1})\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 0}}\end{array}&\begin{array}[]{@{}l@{}}b\;{:=}\;\textbf{{FADD}}({{x}},{1})\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 0}}\end{array}\end{array}

W.l.o.g., if the first runs first, it reads from the initialization message
{\langle{{x}:0@0,\mathit{V}_{0}}\rangle}

(it is the only message of
{x}
in
{M}_{0}
),
and it is forced to add a message
with timestamp
1
.
When the second thread runs, it may
not
read from the initialization message: that would again require adding a message of
{x}
with timestamp
1
, but that timestamp is no longer available.
Thus, it may only read from the message that was added by the first thread.

Example 2.19.

Fences (modeled as RMWs to an otherwise unused distinguished location
f
)
can be used to recover sequential consistency when needed.
The following outcome is forbidden by
\mathsf{RA}
.

(SB+RMWs)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}{x}\;{:=}\;1\\
\textbf{{FADD}}({f},{0})\\
a\;{:=}\;{y}\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 0}}\end{array}&\begin{array}[]{@{}l@{}}{y}\;{:=}\;1\\
\textbf{{FADD}}({f},{0})\\
b\;{:=}\;{x}\color[rgb]{0,0.5,0.5}{~~\texttt{/\!\!/}\textit{reads 0}}\end{array}\end{array}

Due to the RMWs in both threads,
{\mathcal{M}}_{\mathsf{RA}}
forbids the annotated program behavior.
Indeed, suppose, w.l.o.g., that the first thread executes its
\textbf{{FADD}}({f},{0})
first,
it will read from the initialization message to
f
and will add to memory
a message of the form
{\langle{f:0@1,\mathit{V}}\rangle}
with
\mathit{V}({x})>0
.
When the second thread executes its
\textbf{{FADD}}({f},{0})
,
it will necessarily read that message and incorporate the view
\mathit{V}
in its thread view,
so that its view of
{x}
will be increased.
Then, when it reads
{x}
it may not pick the initial message.

The RA memory system defined so far (with no silent transitions) allows non-fair executions.
In particular, it allows messages added by some thread to never propagate to other threads,
so that other threads may forever read a message with a lower timestamp, and thus, allows,
e.g.,
a thread-fair
infinite
behavior for the
Rloop
program from
Section

2
.

To address this problem, we include silent memory transitions in
{\mathcal{M}}_{\mathsf{RA}}
,
labeled with tuples of the form
{\mathtt{prop}}({\tau},m)
, where
{\tau}\in\mathsf{Tid}
and
m\in\mathsf{Msg}

(
i.e.,

{\mathcal{M}}_{\mathsf{RA}}.{\mathbf{\Theta}}\triangleq\{{{\mathtt{prop}}({\tau},m)\mid{\tau}\in\mathsf{Tid},m\in\mathsf{Msg}}\}
).
Then, we include in
{\mathcal{M}}_{\mathsf{RA}}
the following silent memory step:

\frac{m\in{M}\quad\mathit{T}({\tau})({\mathtt{loc}}(m))<{\mathtt{ts}}(m)}{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\mathtt{prop}}({\tau},m)}$}}_{{\mathcal{M}}_{\mathsf{RA}}}{\langle{{M},\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})[{\mathtt{loc}}(m)\mapsto{\mathtt{ts}}(m)]]}\rangle}}\quad\textsc{RA-propagate}

For a given thread
{\tau}
and message
m
that has not been yet observed by thread
{\tau}

(
\mathit{T}({\tau})({\mathtt{loc}}(m))<{\mathtt{ts}}(m)
),
this step increases
{\tau}
’s view to include
m
’s timestamp.
Intuitively speaking, it ensures that every thread
{\tau}
eventually advances
its view so that it cannot keep reading an old message indefinitely.

Example 2.20.

While thread-fair behaviors of
Rloop
under
{{\mathcal{M}}_{\mathsf{RA}}}
include
an infinite behavior (in which the second thread indefinitely read the initialization message),
memory fairness forbids this behavior.
Indeed, in runs inducing this infinite behavior, a silent label

{\mathtt{prop}}(2,{\langle{{x}:1@t,[{x}\mapsto t]}\rangle})
(where
t
is a timestamp of a message added by instruction
{x}\;{:=}\;1
of
Rloop
)
is necessarily continuously enabled.
Memory fairness ensures that the corresponding transition is eventually executed,
and from that point on,
{\mathcal{M}}_{\mathsf{RA}}
prohibits the second thread from executing
{{\mathtt{R}}}({{x}},{0})
.

We emphasize again that
memory fairness is sensitive to the choice of silent memory transitions.
For instance, the system obtained from
{\mathcal{M}}_{\mathsf{RA}}
by discarding the message
m
from the labels of silent memory steps
induces the same set of behaviors as
{\mathcal{M}}_{\mathsf{RA}}
,
but not the same set of

behaviors.
In the next sections, we present the declarative approach for defining the semantics of memory systems,
which uniformly captures memory fairness, and does not require the technical ingenuity needed for ensuring fairness in
operational memory systems.

2.3.
The Strong-Coherence Memory System

We consider a memory system for Strong-Coherence (StrongCOH),
i.e.,
the relaxed fragment of RC11.
Similar to RA, we follow an operational formulation of StrongCOH following the relaxed and
promise-free fragment of the Promising Semantics of
Kang
et al. 2017
.
Since this operational formulation is very close to RA’s one discussed above,
we describe only the difference between them.

The states of
{\mathcal{M}}_{\mathsf{StrongCOH}}
are the same as of
{\mathcal{M}}_{\mathsf{RA}}
, and transitions are similar,
where the only difference is in the read transition (note the crossed out “
\sqcup\mathit{V}

\frac{{\langle{{x}:v@t,\mathit{V}}\rangle}\in{M}\quad\mathit{T}({\tau})({x})\leq t\quad\mathit{T}^{\prime}=\mathit{T}[{\tau}\mapsto\mathit{T}({\tau})[{x}\mapsto t]\cancel{\sqcup\mathit{V}}]}{{\langle{{M},\mathit{T}}\rangle}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{{\mathtt{R}}}({{x}},{v})}$}}_{{\mathcal{M}}_{\mathsf{StrongCOH}}}{\langle{{M},\mathit{T}^{\prime}}\rangle}}

That is, when a thread reads from a message, it does not update its view by the message’s view
but just by its timestamp.
3
3

3

In this model one may change messages to not store views at all
since they are never used. We keep the message views only in order to be
as close as possible to RA.

This change makes the semantics weaker:
StrongCOH allows weak behavior of

and
SB+RMWs
from
Examples

and
2.19
.

We include the same silent memory transitions in

as we do for

which is enough to guarantee termination of memory-fair executions of

for the same reason
as for RA.

3.
Preliminaries on Declarative Semantics

In this section, we review the declarative (a.k.a. axiomatic) framework
for assigning semantics to concurrent programs
and present the well-known declarative models for the four operational models presented above.
Later, we will extend the framework and the existing correspondence results with fairness guarantees
that account for infinite behaviors.

Relations

Given a binary relation (in particular, a function)
R
,
\textit{dom}{({R})}
and
\textit{codom}{({R})}
denote its domain and codomain.
We write
R^{?}
,
R^{+}
, and
R^{*}
respectively to denote its reflexive, transitive, and reflexive-transitive closures.
The inverse relation is denoted by
R^{-1}
.
We denote by
R_{1}\mathbin{;}R_{2}
the (left) composition of two relations
R_{1},R_{2}
,
and assume that
\mathbin{;}
binds tighter than
\cup
and
\setminus
.
We denote by
[A]
the identity relation on a set
A
.
In particular,
[A]\mathbin{;}R\mathbin{;}[B]=R\cap(A\times B)
.
For
n\geq 0
and a relation
R
on a set
A
,
R^{n}
is recursively defined by
R^{0}\triangleq[A]

and
R^{n+1}\triangleq R\mathbin{;}R^{n}
.
We write
R^{\leq n}
for the union
\bigcup_{1\leq i\leq n}R^{n}
.

Events

Events represent individual memory accesses in a run of a program.
They consist of a thread identifier, an event label, and a serial number used to
uniquely identify events and order the events inside each thread.

Definition 3.1.

An
event

e
is a tuple
{\langle{k,{\tau}:{l}}\rangle}
where

k\in{\mathbb{N}}\cup\{{\bot}\}
is a serial number inside each thread (
\bot
for initialization events),

{\tau}\in\mathsf{Tid}\uplus\{{\bot}\}
is a thread identifier
(
\bot
for initialization events),
and
{l}\in\mathsf{ELab}
is an event label (as defined in
Definition

2.1
).
The functions
{\mathtt{sn}}
,
{\mathtt{tid}}
, and
{\mathtt{elab}}

return the serial number, thread identifier, and the event label of an event.
The functions
{\mathtt{typ}}
,
{\mathtt{loc}}
,
{\mathtt{val_{r}}}
, and
{\mathtt{val_{w}}}
are lifted to events in an obvious way.
We denote by
\mathsf{Event}
the set of all events, and
use
{\mathtt{R}},{\mathtt{W}}
, and
{\mathtt{RMW}}
to denote the following subsets:

\displaystyle{\mathtt{R}}

\displaystyle\triangleq\{{e\in\mathsf{Event}\;|\;{\mathtt{typ}}(e)={\mathtt{R}}\lor{\mathtt{typ}}(e)={\mathtt{RMW}}}\}

\displaystyle{\mathtt{W}}

\displaystyle\triangleq\{{e\in\mathsf{Event}\;|\;{\mathtt{typ}}(e)={\mathtt{W}}\lor{\mathtt{typ}}(e)={\mathtt{RMW}}}\}

\displaystyle{\mathtt{RMW}}

\displaystyle\triangleq\{{e\in\mathsf{Event}\;|\;{\mathtt{typ}}(e)={\mathtt{RMW}}}\}

We use subscripts and superscripts to restrict sets of events to certain location
and thread
(
e.g.,

{\mathtt{W}}_{x}=\{{w\in{\mathtt{W}}\;|\;{\mathtt{loc}}(w)={x}}\}

and
E^{\tau}=\{{e\in E\;|\;{\mathtt{tid}}(e)={\tau}}\}
).
The set of
initialization events

is given by
\mathsf{Init}\triangleq\{{{\langle{\bot,\bot:{{\mathtt{W}}}({{x}},{0})}\rangle}\;|\;{x}\in\mathsf{Loc}}\}
.

Notation 3.2.

Given a relation
R
on events, we denote by
R|_{{\mathtt{loc}}}
the restriction of
R
to events of
the same location:

R|_{{\mathtt{loc}}}=\{{{\langle{e_{1},e_{2}}\rangle}\in R\;|\;\exists{x}\in\mathsf{Loc}.\;{\mathtt{loc}}(e_{1})={\mathtt{loc}}(e_{2})={x}}\}

Our representation of events induces a
sequenced-before
partial order on events given by:

e_{1}<e_{2}\;\mathrel{\stackrel{{\scriptstyle\mathsf{\triangle}}}{{\Leftrightarrow}}}\;\begin{array}[]{@{}l@{}}(e_{1}\in\mathsf{Init}\land e_{2}\not\in\mathsf{Init})\lor{}({\mathtt{tid}}(e_{1})={\mathtt{tid}}(e_{2})\land{\mathtt{sn}}(e_{1})<{\mathtt{sn}}(e_{2}))\end{array}

Initialization events precede all non-initialization events,
while events of the same thread are ordered according to their serial numbers.

Behaviors (
i.e.,
mappings from threads to sequential traces)
are associated with sets of events in an obvious way:

Definition 3.3.

The set of events
extracted from a behavior

\beta
,
denoted by
\mathsf{Event}(\beta)
, is given by

\mathsf{Event}(\beta)\triangleq\mathsf{Init}\cup\{{{\langle{k,{\tau}:\beta({\tau})(k)}\rangle}\;|\;{\tau}\in\mathsf{Tid},k\in\textit{dom}{({\beta({\tau})})}}\}
.

It is easy to see that for every behavior
\beta
,

\mathsf{Event}(\beta)
satisfies certain “well-formedness” properties:

Definition 3.4.

A set
E\subseteq\mathsf{Event}
is
well-formed
if the following hold:

•

\mathsf{Init}\subseteq E
.

•

{\mathtt{tid}}(e)\neq\bot
and
{\mathtt{sn}}(e)\neq\bot
for every
e\in E\setminus\mathsf{Init}
.

•

If
{\mathtt{tid}}(e_{1})={\mathtt{tid}}(e_{2})
and
{\mathtt{sn}}(e_{1})={\mathtt{sn}}(e_{2})
, then
e_{1}=e_{2}
for all
e_{1},e_{2}\notin\mathsf{Init}
.

•

For every
e\in E\setminus\mathsf{Init}
and
0\leq k<{\mathtt{sn}}(e)
, there exists
{l}\in\mathsf{ELab}

such that
{\langle{k,{\mathtt{tid}}(e):{l}}\rangle}\in E
.

Execution Graphs

An execution graph consists of a set of events, a
reads-from
mapping that determines the write event from which
each read reads its value, and a
modification order
which totally orders the writes to each location.

Definition 3.5.

An
execution graph

G
is a tuple
{\langle{E,{\color[rgb]{0,0.6,0}\mathit{rf}},{\color[rgb]{1,0.5,0}\mathit{mo}}}\rangle}
where:

(1)

E
is a well-formed (possibly, infinite) set of events.

(2)

{\color[rgb]{0,0.6,0}\mathit{rf}}
, called
reads-from
, is a relation on
E
satisfying:

•

If
{\langle{w,r}\rangle}\in{\color[rgb]{0,0.6,0}\mathit{rf}}
then
w\in{\mathtt{W}}
,
r\in{\mathtt{R}}
,
{\mathtt{loc}}(w)={\mathtt{loc}}(r)
, and
{\mathtt{val_{w}}}(w)={\mathtt{val_{r}}}(r)
.

•

w_{1}=w_{2}
whenever
{\langle{w_{1},r}\rangle},{\langle{w_{2},r}\rangle}\in{\color[rgb]{0,0.6,0}\mathit{rf}}
(that is,
{\color[rgb]{0,0.6,0}\mathit{rf}}^{-1}
is functional).

•

E\cap{\mathtt{R}}\subseteq\textit{codom}{({{\color[rgb]{0,0.6,0}\mathit{rf}}})}
(every read should read from some write).

(3)

{\color[rgb]{1,0.5,0}\mathit{mo}}
, called
modification order
, is a disjoint union of relations
\{{{\color[rgb]{1,0.5,0}\mathit{mo}}_{x}}\}_{{x}\in\mathsf{Loc}}
,
such that each
{\color[rgb]{1,0.5,0}\mathit{mo}}_{x}
is a strict total order on
E\cap{\mathtt{W}}_{x}
.

We denote the components of
G
by
G.{\mathtt{E}}
,
G.{\color[rgb]{0,0.6,0}\mathtt{rf}}
, and
G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
,
and write
G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
(called
program order
) for the restriction of sequenced-before to
G.{\mathtt{E}}

(
i.e.,

G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\triangleq[G.{\mathtt{E}}];<;[G.{\mathtt{E}}]
).
For a set
E^{\prime}\subseteq\mathsf{Event}
, we write
G.E^{\prime}
for
G.{\mathtt{E}}\cap E^{\prime}
(
e.g.,

G.{\mathtt{W}}=G.{\mathtt{E}}\cap{\mathtt{W}}
).
The set of all execution graphs is denoted by
\mathsf{EGraph}
.

A
declarative memory system
is simply a set
\mathcal{G}
of execution graphs
(often formulated using a conjunction of several constraints).
We refer to execution graphs in a declarative memory system
\mathcal{G}

as
\mathcal{G}
-consistent
execution graphs.

We can now define the behaviors allowed by a given declarative memory system.

Definition 3.6.

A behavior
\beta
is
allowed by a declarative memory system

\mathcal{G}

if
\mathsf{Event}(\beta)=G.{\mathtt{E}}
for some execution graph
G\in\mathcal{G}
.
We denote by
\mathsf{B}({\mathcal{G}})
(
\mathsf{B^{fin}}({\mathcal{G}})
) the set of all (finite) behaviors that are allowed by
\mathcal{G}
.

The linking with programs is defined as follows.

Definition 3.7.

Let
{P}
be a program,
\mathcal{G}
be a declarative memory system,
and
\beta
be a behavior.

•

\beta
is a

behavior of
{P}
under
\mathcal{G}
if
\beta\in\mathsf{B}({{P}})\cap\mathsf{B}({\mathcal{G}})
.

•

\beta
is a

thread-fair behavior of
{P}
under
\mathcal{G}
if
\beta\in\mathsf{B^{tf}}({{P}})\cap\mathsf{B}({\mathcal{G}})
.

A Declarative Memory System for SC

To provide a declarative formulation of

we use the standard “from-read” relation (a.k.a. “reads-before”).
In this relation a read

Definition 3.8.

The

3.2.
A Declarative Memory System for TSO

Following
Alglave
et al. 2014

is easily obtained from the one of

in

(

\displaystyle G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\mathtt{e}

-happens-before

\displaystyle G.{\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{TSO}}

\displaystyle\triangleq(G.{\color[rgb]{1,0,1}\mathtt{ppo}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\mathtt{e}\cup G.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}})^{+}

4.
Making Declarative Semantics Fair

In this section, we introduce memory fairness
into declarative models in a model-agnostic fashion.

To define fairness of execution graphs, we require that the partial ordering of events
in the graph is, like the ordering of natural numbers,
prefix-finite
.
From an operational point of view,
an event preceded by an infinite number of events is never executed.

Definition 4.1.

A relation
R
on a set
A
is
prefix-finite

if
\{{a\;|\;{\langle{a,b}\rangle}\in R}\}
is finite for every
b\in A
.

Concretely, we require the modification order and the from-read relation
to be prefix-finite.
4
4

4

Note that the
program order
and the

Theorem 4.5.

As a corollary, it easily follows from our definitions that the set

{P}

{\mathcal{M}}_{X}
coincides with the set of (thread&) memory-fair behaviors of a program
{P}

.

The full proof of
Theorem

4.5
is included in appendix (
(
Lahav et al. 2021a
)
)
and its Coq mechanization in
(
Lahav et al. 2021b
)
.
Here, we outline the proof
starting with the easier direction.

4.1.
\mathsf{B^{mf}}({{\mathcal{M}}_{X}})\subseteq\mathsf{B}({\mathcal{G}_{X}^{\texttt{fair}}})

Given a memory-fair behavior
\beta
of
{\mathcal{M}}_{X}
,
we let
\rho
be a memory-fair observable trace of
{\mathcal{M}}_{X}

such that
\beta(\rho)=\beta
.
Then, using
\rho
, we construct a fair execution graph
G\in\mathcal{G}_{X}
.
Its events are determined by
\beta
(
G.{\mathtt{E}}=\mathsf{Event}(\beta)
),
and its relations are defined differently for every system:

SC

The
{\color[rgb]{0,0.6,0}\mathtt{rf}}
and
{\color[rgb]{1,0.5,0}\mathtt{mo}}
relations are determined by the trace order:
for each read
{\color[rgb]{0,0.6,0}\mathtt{rf}}
assigns the latest write of the same location,
while
{\color[rgb]{1,0.5,0}\mathtt{mo}}
corresponds to the trace order restricted to writes to the same location.
It follows that
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
is included in the trace order,
and since the trace order is prefix-finite,
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
are prefix-finite as well.

TSO

We define
{\color[rgb]{1,0.5,0}\mathtt{mo}}
to be the order in which writes to the same location are propagated (unbuffered) to memory.
For each read,
{\color[rgb]{0,0.6,0}\mathtt{rf}}
maps it either to the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal write to the same location
that was propagated before it in
\rho
(if the read reads from memory)
or to the
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
-maximal one by the same thread (if it reads from the buffer).
Since every write is eventually propagated to memory,
and once propagated no thread can read from an
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-prior write,
it follows that both
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
are prefix-finite.

RA and StrongCOH

The
{\color[rgb]{1,0.5,0}\mathtt{mo}}
component of
G
follows
the order induced by timestamps of messages in the operational run.
Prefix-finiteness of
{\color[rgb]{1,0.5,0}\mathtt{mo}}
follows from the facts that
a location and a timestamp uniquely identify the corresponding message
(and the write event in
G
respectively)
and that timestamps are natural numbers—that is,
each write event
w
representing a message with a timestamp
t

has at most
t

{\color[rgb]{1,0.5,0}\mathtt{mo}}
-prior writes.

The
{\color[rgb]{0,0.6,0}\mathtt{rf}}
component of
G
connects
an event related to a read/RMW transition of
\rho
with
a write event representing the message read by the transition.

Prefix-finiteness of
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
follows from the fact that in the fair operational run
every message is eventually propagated to every thread.
That is, for any given write event
w
to a location
{x}
in
G
representing a message with a timestamp
t
,
there cannot be infinitely many reads from
{x}
in
G
reading from
write events that correspond to messages with timestamps smaller than
t
.

4.2.
\mathsf{B}({\mathcal{G}_{X}^{\texttt{fair}}})\subseteq\mathsf{B^{mf}}({{\mathcal{M}}_{X}})

The converse direction is more challenging.
Given a fair
\mathcal{G}_{X}
-consistent execution graph
G
,
we have to find a memory-fair observable trace
\rho
of
{\mathcal{M}}_{X}

such that
\mathsf{Event}(\beta(\rho))=G.{\mathtt{E}}
.

Put differently, we need a total order over
G.{\mathtt{E}}\setminus\mathsf{Init}
that extends
G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
,
so that some memory-fair run of
{\mathcal{M}}_{X}
executes according to this order.
Existing proofs of correspondence between declarative and operational definitions
of SC, RA, and StrongCOH pick an arbitrary total order extending
G.{\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{SC}}
(for SC) and
G.{\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{RA}}
(for RA and StrongCOH).
(Assuming the axiom of choice, any partial order
R
on a set
A
can be
extended to a total order on
A
.)
It is then not difficult to show that executing the program following that order yields the labels appearing in the execution graph.
For infinite graphs, however, an arbitrary extension of
G.{\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{SC}}
(or
G.{\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{RA}}
respectively)
does not necessarily correspond to a (memory-fair) run of the program.
For this, we need an
enumeration
of
G.{\mathtt{E}}\setminus\mathsf{Init}
, as defined next.

Definition 4.6.

An
enumeration
of a set
A
is a (finite or infinite) injective (
i.e.,
without repetitions) sequence
\nu

covering all the elements in
A
(
i.e.,

A=\{{\nu(i)\;|\;i\in\textit{dom}{({\nu})}}\}
).
An enumeration
\nu
of
A

respects
a partial order
R
on
A

if
i<j
whenever
{\langle{\nu(i),\nu(j)}\rangle}\in R
.

Prefix-finiteness of a partial order ensures that a suitable enumeration exists
(our proof employs classical, non-constructive, reasoning):

Proposition 4.7.

Let
R
be a prefix-finite partial order on a countable set
A
.
Then, there exists an enumeration of
A
that respects
R
.

However, we do not yet have that the “happens-before” relation of each model is prefix-finite;
we only know that
G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
are prefix-finite.
Next, we show that prefix-finiteness of
G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}

suffices for prefix-finiteness of the other relations,
as long as the program in question has a bounded number of threads.
(Recall that we assume that the set
\mathsf{Tid}
is finite.)

First, note that every relation on a finite set is prefix-finite,
and prefix-finiteness is preserved by (finite) composition.

Lemma 4.8.

Let
R
and
R^{\prime}
be prefix-finite relations and
n\in{\mathbb{N}}
.
Then
R\cup R^{\prime}
,
R\mathbin{;}R^{\prime}
and
R^{\leq n}
are also prefix-finite.

For transitive closures, we need an auxiliary property.

Definition 4.9.

A relation
R
on a set
A
is
n
-total
if for every
n+1
distinct
elements
a_{1}{,}\ldots{,}a_{n+1}\in A
, we have
{\langle{a_{i},a_{j}}\rangle}\in R
for some
1\leq i,j\leq n+1
.

For an execution graph
G
with
n
threads,

G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
is
n
-total
(as a relation on
G.{\mathtt{E}}\setminus\mathsf{Init}
).
By the pigeonhole principle, any set of
n+1
events in
G.{\mathtt{E}}\setminus\mathsf{Init}
contain two elements
belonging to the same thread, and those two events are ordered by
G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
.

Now, if a relation
R
is
n
-total and acyclic, its transitive closure
R^{+}
has
bounded length, which entails that
R^{+}
is prefix-finite provided
R
is
prefix-finite.

Lemma 4.10.

Let
R
be an acyclic,
n
-total, prefix-finite relation.
Then,
R^{+}
is prefix-finite.

As a corollary, we obtain that the prefix-finiteness of the “happens-before”
relation in fair execution graphs.

Corollary 4.11.

For
X\in\{{\mathsf{SC},\mathsf{TSO},\mathsf{RA},\mathsf{StrongCOH}}\}
, let
G
be a fair
\mathcal{G}_{X}
-consistent execution graph.
Then
[G.{\mathtt{E}}\setminus\mathsf{Init}]\mathbin{;}G.{\color[rgb]{0,0,1}\mathtt{hb}}_{X}

5

We define

From
Proposition

4.7
, there is an enumeration
\nu

{\color[rgb]{0,0,1}\mathtt{hb}}_{X}

We use
\nu
to construct a program trace
\rho

SC

The trace
\rho
follows
\nu
exactly.
Since
{\mathcal{M}}_{\mathsf{SC}}
has no silent memory transitions,
\rho
is trivially memory fair.

TSO

The trace
\rho
is incrementally constructed by following the order of events
in
\nu
and appending an appropriate sequence of transitions.
If the next event in
\nu
is a read,
we append to
\rho
all unexecuted
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
-prior writes and then the read.
If the next event in
\nu
is a write, we append the write to the trace
if it has not already been included in the trace.
In addition, when the next event is a write, we append its propagation action to memory.
By construction, every write in
\rho
is eventually propagated to memory.

RA and StrongCOH

The trace
\rho
is the enumeration
\nu
interleaved with silent
\mathsf{RA}
/
\mathsf{StrongCOH}
transition labels.
Namely, for each write
w
and thread
{\tau}
, we compute an index
i
in the enumeration
such that it is
safe
to propagate
w
to
{\tau}
at that index:
for each event in
{\tau}
with index greater than
i
, there is no
\mathtt{X}
-following (where
\mathtt{X}={\color[rgb]{0,0,1}\mathtt{hb}}_{\mathsf{RA}}
for
\mathsf{RA}
and
\mathtt{X}={\color[rgb]{0,0.6,0}\mathtt{rf}}^{?}\mathbin{;}{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}^{?}
for
\mathsf{StrongCOH}
)
(i) write that
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-precedes
w

and (ii) read that reads from a write
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-preceding
w
.
Since
G
is fair, such an index is defined for all (non-initialization) writes.
Then, after the event with an index corresponding to some write has been enumerated, we execute a propagation transition for the write.
In that way, every write is eventually propagated to every thread, so the resulting trace is memory fair.

4.3.
Making RC11 Fair

Having established evidence for the adequacy of the declarative fairness condition,
we may apply this condition in other (and richer) declarative models.
In particular, we propose to adopt this condition into the C/C++ memory model.
Next, we discuss this proposal in the context of the RC11 model
(
Lahav
et al. 2017
)
,
a repaired version of the C/C++11 specification
(
Batty et al. 2012
)

that fixes certain issues involving sequentially consistent accesses
and works around the “thin-air” problem by completely forbidding
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
cycles.
A full definition of RC11 is obtained by carefully
combining the key concepts of
\mathsf{SC}
,
\mathsf{RA}
, and
\mathsf{StrongCOH}
.
It requires us to include in the declarative framework
access modes (a.k.a. “memory orderings”—the consistency level required from every memory access),
and several types of fences.
For simplicity, we elide these definitions and keep the discussion more abstract.
Indeed, there is nothing special about RC11 in this context—the declarative fairness
condition could be added to any model requiring
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
acyclicity.

Generally speaking, when proposing a strengthening of a programming language memory model,
one has to make sure that the mapping schemes to multicore architectures are not broken,
and that source-to-source compiler transformations are still validated.
In our case, the mapping of RC11 to x86-TSO trivially remains sound.
Indeed, as we saw in
Theorem

4.5
, the natural operational characterization of liveness in TSO
corresponds to the declarative condition requiring that the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
relations
are prefix-finite. Since the same condition is applied both in the source level (RC11)
and in the target level (x86-TSO), and mappings of source graphs to target ones
keep
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
intact, we maintain the soundness of the known mappings.
6
6

6

See

http://www.cl.cam.ac.uk/~pes20/cpp/cpp0xmappings.html
[accessed July-2021].

We note that for establishing the soundness of the mappings to other architectures, one first needs a formal fairness
condition of the architecture. While this may be more difficult in architectures
weaker than x86-TSO (see
Section

6
), it is likely that no hardware
will allow that a write is placed after infinitely many other writes in the coherence order
(non-prefix-finite
{\color[rgb]{1,0.5,0}\mathtt{mo}}
), or that infinitely many reads do not observe a later
write (non-prefix-finite
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
).

Considering compiler transformations, one has to show that
every behavior of the target program explained by a consistent graph
G_{\text{tgt}}

is also obtained by a consistent graph
G_{\text{src}}
of the source program.
It is not hard to see that the constructions of
Vafeiadis et al. 2015
and
Lahav
et al. 2017

work as-is for the RC11 model strengthened with fairness.
First, the constructions of
G_{\text{src}}
for
reordering transformations
,
which reorder two memory accesses under certain conditions,
keep the same
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
relations of
G_{\text{tgt}}
;
so their prefix-finiteness trivially follows.

Second, we consider
elimination transformations

that eliminate a redundant memory access.
In this case,

G_{\text{src}}
is obtained from
G_{\text{tgt}}
by adding one additional event

e_{\text{new}}
that corresponds to the eliminated instruction.
For read elimination (read-after-read or read-after-write),

e_{\text{new}}
is a read event, and the construction of
ensures that
G_{\text{src}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}=G_{\text{tgt}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}
.
In turn,
G_{\text{tgt}}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}\subseteq G_{\text{src}}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
, but since only one event
is added to
G_{\text{src}}
, prefix-finiteness of
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
is again trivially preserved.

Finally, we consider write-after-write elimination.
Let
w_{0}
denote the immediate
G_{\text{src}}.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}
-successor of
e_{\text{new}}
.
Then, to construct
G_{\text{src}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}
, one places
e_{\text{new}}
as the
immediate predecessor of
w_{0}
.
Then, consistency of
G_{\text{src}}
follows the argument of
(
Lahav
et al. 2017
)
,
and it remains to show that fairness of
G_{\text{src}}
follows from the fairness of
G_{\text{tgt}}
.
The latter is easy: write events in
G_{\text{src}}
other than
e_{\text{new}}

all have at most one more incoming
G_{\text{src}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}
edge (from
e_{\text{new}}
),
and the same set of incoming
G_{\text{src}}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
edges.
In turn, For
e_{\text{new}}
itself, we have:

\{{e\in G_{\text{src}}.{\mathtt{E}}\;|\;{\langle{e,e_{\text{new}}}\rangle}\in G_{\text{src}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G_{\text{src}}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}}\}\subseteq\{{e\in G_{\text{tgt}}.{\mathtt{E}}\;|\;{\langle{e,w_{0}}\rangle}\in G_{\text{tgt}}.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G_{\text{tgt}}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}}\}.

In the next section, we demonstrate that adding fairness to RC11 as proposed above
provides the necessary underpinnings allowing one to formally reason about termination under RC11.

4.4.
From Finite to Infinite Robustness

Common advice given to programmers of multi-threaded software
is to follow a programming discipline that hides the effects of that weak memory model,

e.g.,
to use exclusively sequentially consistent accesses.
Programs that follow such a discipline are
robust
,
meaning that they have only sequentially consistent behaviors on the underlying weak memory model.
While there is a rich literature on programming disciplines that imply robustness
and verification techniques for robustness
(
Bouajjani
et al. 2013
;
Bouajjani
et al. 2011
;
Derevenetc and
Meyer 2014
;
Bouajjani et al. 2018
;
Margalit and
Lahav 2021
;
Lahav and
Margalit 2019
;
Oberhauser 2018
)
, most work only considers
finite
behaviors, i.e., they leave open whether programs following the discipline have only sequentially consistent
infinite
behaviors.
This means that any correctness properties that only concern infinite behaviors, such as starvation-freedom, might be lost on the weak memory model despite its (finite) robustness.
In this section, we show that this cannot happen as long as the weak memory model satisfies our declarative memory fairness condition and its consistency predicate is
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix closed.
This is the case for all models studied in this paper.
Thus our unified definition of memory fairness lifts all existing robustness results for these models from the literature to infinite behaviors.

First, we observe that the consistency predicates based on acyclicity (
\mathsf{SC}
-consisterncy, in particular)
enjoy a “compactness property”—if they hold for all finite prefixes of a graph, then they also hold for the full graph.
Below, by
finite
execution graph, we mean a graph
G
with
G.{\mathtt{E}}\setminus\mathsf{Init}
being finite
(the set
\mathsf{Init}
of initialization events may be infinite if
\mathsf{Loc}
is infinite).

Definition 4.12.

An execution graph
G^{\prime}
is a
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix
of an execution graph
G

if we have
\textit{dom}{({(G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}})\mathbin{;}[G^{\prime}.{\mathtt{E}}]})}\subseteq G^{\prime}.{\mathtt{E}}
,

G^{\prime}.{\color[rgb]{0,0.6,0}\mathtt{rf}}=[G^{\prime}.{\mathtt{E}}]\mathbin{;}G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\mathbin{;}[G^{\prime}.{\mathtt{E}}]
,
and
G^{\prime}.{\color[rgb]{1,0.5,0}\mathtt{mo}}=[G^{\prime}.{\mathtt{E}}]\mathbin{;}G.{\color[rgb]{1,0.5,0}\mathtt{mo}}\mathbin{;}[G^{\prime}.{\mathtt{E}}]
.

Proposition 4.13 (
\mathcal{G}_{\mathsf{SC}}
compactness).

Let
G
be an execution graph with prefix-finite
([G.{\mathtt{E}}\setminus\mathsf{Init}]\mathbin{;}G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}})^{+}
.
If every finite
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix of
G
is
\mathcal{G}_{\mathsf{SC}}
-consistent, then so is
G
.

Proof.

Suppose that
G
is
\mathcal{G}_{\mathsf{SC}}
-inconsistent,
and let
a_{1}{,}\ldots{,}a_{n}\in G.{\mathtt{E}}
such that

{\langle{a_{i},a_{i+1}}\rangle}\in G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\cup G.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
for every
1\leq i\leq n-1
,
and
{\langle{a_{n},a_{1}}\rangle}\in G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\cup G.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
.
Let
E^{\prime}=\mathsf{Init}\cup\textit{dom}{({(G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}})^{*}\mathbin{;}[\{{a_{1}{,}\ldots{,}a_{n}}\}]})}
,
and let
G^{\prime}={\langle{E^{\prime},[E^{\prime}]\mathbin{;}G.{\color[rgb]{0,0.6,0}\mathtt{rf}}\mathbin{;}[E^{\prime}],[E^{\prime}]\mathbin{;}G.{\color[rgb]{1,0.5,0}\mathtt{mo}}\mathbin{;}[E^{\prime}]}\rangle}
.
Since
([G.{\mathtt{E}}\setminus\mathsf{Init}]\mathbin{;}G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}})^{+}
is prefix-finite,

G^{\prime}
is a finite
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix of
G
.
However, we have

{\langle{a_{i},a_{i+1}}\rangle}\in G^{\prime}.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G^{\prime}.{\color[rgb]{0,0.6,0}\mathtt{rf}}\cup G^{\prime}.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G^{\prime}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
for every
1\leq i\leq n-1
,
and
{\langle{a_{n},a_{1}}\rangle}\in G^{\prime}.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G^{\prime}.{\color[rgb]{0,0.6,0}\mathtt{rf}}\cup G^{\prime}.{\color[rgb]{1,0.5,0}\mathtt{mo}}\cup G^{\prime}.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
,
so
G^{\prime}
is
\mathcal{G}_{\mathsf{SC}}
-inconsistent.
∎

Definition 4.14 (Robustness).

Let
{P}
be a program and
\mathcal{G}
be a declarative memory system.

•

{P}
is
finitely execution-graph robust
against
\mathcal{G}

if for every finite behavior
\beta\in\mathsf{B}({{P}})
and
G\in\mathcal{G}
with
\mathsf{Event}(\beta)=G.{\mathtt{E}}
,
we have
G\in\mathcal{G}_{\mathsf{SC}}
.

•

{P}
is
strongly execution-graph robust
against
\mathcal{G}

if for every (finite or infinite) behavior
\beta\in\mathsf{B}({{P}})
and
G\in\mathcal{G}
with
\mathsf{Event}(\beta)=G.{\mathtt{E}}
,
we have
G\in\mathcal{G}_{\mathsf{SC}}
.

Theorem 4.15.

Let
\mathcal{G}
be a declarative memory system such that:

•

\mathcal{G}
-consistency is
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix closed (
i.e.,
if
G\in\mathcal{G}
then
G^{\prime}\in\mathcal{G}
for every
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix
G^{\prime}
of
G
).

•

G\in\mathcal{G}
implies that
([G.{\mathtt{E}}\setminus\mathsf{Init}]\mathbin{;}G.{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup G.{\color[rgb]{0,0.6,0}\mathtt{rf}})^{+}
is prefix-finite.

Then, if a program
{P}
is finitely execution-graph robust against
\mathcal{G}
,
then it is also strongly execution-graph robust against
\mathcal{G}
.

Proof.

Suppose that
{P}
is finitely execution-graph robust against
\mathcal{G}
.
Let
G\in\mathcal{G}
such that
G.{\mathtt{E}}=\mathsf{Event}(\beta)
for some behavior
\beta\in\mathsf{B}({{P}})
.
From finite execution-graph robustness, it follows that every finite
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
-prefix of
G
is
\mathcal{G}_{\mathsf{SC}}
-consistent.
By
Proposition

4.13
,
G
is
\mathcal{G}_{\mathsf{SC}}
-consistent as well.
∎

We note that the declarative
\mathsf{TSO}
,
\mathsf{RA}
,
\mathsf{StrongCOH}
, and
\mathsf{RC11}
models satisfy the premises
of
Theorem

4.15
.
The Coq mechanization includes the formal proof of the statement below.

Corollary 4.16.

Suppose that a program
{P}
is finitely execution-graph robust against
\mathcal{G}_{X}
for
X\in\{{\mathsf{TSO},\mathsf{RA},\mathsf{StrongCOH},\mathsf{RC11}}\}
.
Then, the set of (thread&) memory-fair behaviors of
{P}
under
{\mathcal{M}}_{X}

coincides with the set of (thread&) memory-fair behaviors of
{P}
under
{\mathcal{M}}_{\mathsf{SC}}
.

Proof.

One direction is obvious since
{\mathcal{M}}_{\mathsf{SC}}
is stronger than
{\mathcal{M}}_{X}
.
For the converse, let
\beta
be a memory-fair behavior of
{P}
under
{\mathcal{M}}_{X}
.
Then, by
Theorem

4.5
, we have that

\beta
be a memory-fair behavior of
{P}
under
\mathcal{G}_{X}^{\texttt{fair}}
.
By definition, we have that
\beta\in\mathsf{B}({{P}})\cap\mathsf{B}({\mathcal{G}_{X}^{\texttt{fair}}})
.
Let
G\in\mathcal{G}_{X}
such that
\mathsf{Event}(\beta)=G.{\mathtt{E}}
.
Then, since
G\in\mathcal{G}_{X}
, by
Theorem

4.15
, we have that
G\in\mathcal{G}_{\mathsf{SC}}
.
Since the declarative fairness condition is the same in all four models, we have

G\in\mathcal{G}_{\mathsf{SC}}^{\texttt{fair}}
.
Hence, we have
\beta\in\mathsf{B}({{P}})\cap\mathsf{B}({\mathcal{G}_{\mathsf{SC}}^{\texttt{fair}}})
,
and so by
Theorem

4.5
, it follows that

\beta
be a memory-fair behavior of
{P}
under
{\mathcal{M}}_{\mathsf{SC}}
.
Finally, to deal with thread fairness, one has to use
\mathsf{B^{tf}}({{P}})
instead of
\mathsf{B}({{P}})
in this argument.
∎

As a simple application example, the
SpinLock-Client
program in
Section

5.1
below is
(finitely) execution-graph robust because the program employs only a single location (the location
l
for the lock implementation).
Then,
Corollary

4.16
entails that this program may diverge under the weak memory models studied in this paper
iff it diverges under
\mathsf{SC}
, and that the same also holds when assuming thread fairness.

5.
Proving Deadlock Freedom for Locks

In this section, we prove the termination and/or fairness of spinlock, ticket lock, and MCS lock clients.
The key to doing so is
Theorem

5.3
below,
which reduces proving termination of spinloops under fair weak memory models
to reasoning about a single specific iteration of the loop.

For simplicity, we henceforth assume that the sequential programs composing the concurrent programs are
deterministic, as defined below. (The thread interleaving itself still makes the
concurrent program semantics non-deterministic.)

Definition 5.1.

A program
{P}
is
deterministic
if

\overline{p}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{l}_{1}}$}}_{P}\overline{p}_{1}

and
\overline{p}\mathrel{\raisebox{-0.8pt}{$\xrightarrow{{\tau}:{l}_{2}}$}}_{P}\overline{p}_{2}

imply that
{\mathtt{typ}}({l}_{1})={\mathtt{typ}}({l}_{2})
and
{\mathtt{loc}}({l}_{1})={\mathtt{loc}}({l}_{2})
,
and, moreover, if
{l}_{1}={l}_{2}
, then
\overline{p}_{1}=\overline{p}_{2}
also holds.

For a behavior
\beta
of a deterministic program
{P}

and
{\tau}\in\mathsf{Tid}
,
we denote by
\mu_{\tau}(\beta)
the unique run of
{P}({\tau})

that induces the sequential trace
\beta({\tau})
.

Definition 5.2.

A
spinloop iteration
of thread
{\tau}
in a behavior
\beta

is a range of event serial numbers
[n,n^{\prime}]
such that
the sequence of corresponding program steps:

(1)

performs only reads:

{\mathtt{typ}}({\mathtt{tlab}}(\mu_{\tau}(\beta)(i)))={\mathtt{R}}
for
n\leq i\leq n^{\prime}
; and

(2)

returns the program to the starting state of the loop:

{\mathtt{src}}(\mu_{\tau}(\beta)(n))={\mathtt{tgt}}(\mu_{\tau}(\beta)(n^{\prime}))
.

An
infinite spinloop
of thread
{\tau}
in a behavior
\beta
is an infinite sequence
s
of consecutive spinloop iterations of thread
{\tau}
(
i.e.,

s(i)=[n_{i},n_{i}^{\prime}]\implies\exists n_{i+1}^{\prime}.\,s(i+1)=[n_{i}^{\prime},n_{i+1}^{\prime}]
).

If infinite spinloops are the only source of unbounded behavior in programs
(
i.e.,
their individual iterations are of bounded length
and there are boundedly many writes to each memory location),
then because of fairness, an infinite spinloop has to eventually read from the

{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal writes.

Theorem 5.3.

Let
\beta
be a behavior of a deterministic program
and
G
be a fair execution graph with
G.{\mathtt{E}}=\mathsf{Event}(\beta)

and
G.{\mathtt{sc}}_{{\mathtt{loc}}}
(see
Section

3.2
) irreflexive.
For every infinite spinloop
s
of a thread
{\tau}
in
\beta

whose iterations have bounded length
and read only from locations that are written to by finitely many writes in
G
,
there is a loop iteration
s(i)
whose reads all read from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal writes.

This theorem provides a sufficient condition for establishing termination of
spinloops. In the supplementary material, we also establish the other direction:
whenever a deterministic program has a behavior where all non-terminated
threads end with a loop iteration reading from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal writes,
then it has an infinite memory-fair behavior.

5.1.
Spinlock

Consider the following spinlock implementation:

\begin{array}[t]{@{}l@{}}\textbf{{int}}\;l\;{:=}\;0\\
\textbf{{void}}\;lock()\;\{\;\begin{array}[t]{@{}l@{}}\textbf{{int}}\;r\\
\textbf{{repeat}}\;\{\;\begin{array}[t]{@{}l@{}}\textbf{{repeat}}\;\{\;r\;{:=}\;l\;\}\;\textbf{{until}}\;(r=0)\;\}\end{array}\\
\quad\textbf{{until}}\,(\textbf{{CAS}}(l,0,1))\;\}\end{array}\\
\textbf{{void}}\;unlock()\;\{\;l\;{:=}\;0\;\}\end{array}

Theorem 5.4.

All thread-fair behaviors of the following client program
under
\mathcal{G}^{\texttt{fair}}_{\{{\mathsf{SC},\mathsf{TSO},\mathsf{RA},\mathsf{StrongCOH}}\}}
are finite:

(SpinLock-Client)

\begin{array}[]{@{}l@{~~}||@{~~}l@{~~}||@{~~}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}lock()\\
unlock()\end{array}&\begin{array}[]{@{}l@{}}lock()\\
unlock()\end{array}&\begin{array}[]{@{}l@{}}\dots\end{array}&\begin{array}[]{@{}l@{}}lock()\\
unlock()\end{array}\end{array}

Proof.

Assume for the sake of contradiction that the program has an infinite
thread-fair behavior
\beta
, which is induced by a fair execution graph
G
.
By inspection, since
G
is infinite,
\beta
must contain an infinite spinloop.
The number of write events to the location
l
in
G
is finite since each thread makes at most two writes to
l
.
Fix the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal one among them and denote it
w
.
Due to thread fairness of
\beta
,
the value written by
w
has to be
0
.
(Otherwise, it could have been only the value
1
produced by the
CAS
instruction,
which is followed by a store writing
0
, and
the write event produced by the store would have been
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-following for
w

by
\{{\mathsf{SC},\mathsf{TSO},\mathsf{RA},\mathsf{StrongCOH}}\}
-consistency of
G
.)
By
Theorem

5.3
,
there is a spinloop iteration that reads from
w
,
which is a contradiction, since reading
0
from location
l
exits the loop.
∎

5.2.
Ticket Lock

Consider the following ticket lock implementation:

\begin{array}[t]{@{}l@{}}\textbf{{int}}\;serving:=0,\;ticket\;{:=}\;0\\
\textbf{{void}}\;lock()\;\{\;\begin{array}[t]{@{}l@{}}\textbf{{int}}\;s:=0,\;r\;{:=}\;\textbf{{FADD}}(ticket,1)\\
\textbf{{repeat}}\;\{\;s\;{:=}\;serving\;\}\;\textbf{{until}}\;(s=r)\;\}\end{array}\\
\textbf{{void}}\;unlock()\;\{\;serving\;{:=}\;serving+1\;\}\end{array}

Theorem 5.5.

In every thread-fair behavior
of the following program under
\mathcal{G}^{\texttt{fair}}_{\{{\mathsf{SC},\mathsf{TSO},\mathsf{RA},\mathsf{StrongCOH}}\}}
,

r_{1}{,}\ldots{,}r_{N}
all grow unboundedly:

\begin{array}[]{@{}l@{~~}||@{~~}l@{~~}||@{~~}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}L_{1}:lock()\\
r_{1}:=r_{1}+1\\
unlock()\\
\textbf{{goto}}\;L_{1}\end{array}&\begin{array}[]{@{}l@{}}L_{2}:lock()\\
r_{2}:=r_{2}+1\\
unlock()\\
\textbf{{goto}}\;L_{2}\end{array}&\begin{array}[]{@{}l@{}}\dots\end{array}&\begin{array}[]{@{}l@{}}L_{N}:lock()\\
r_{N}:=r_{N}+1\\
unlock()\\
\textbf{{goto}}\;L_{N}\end{array}\end{array}

Proof.

For any thread-fair behavior
\beta
of this program
and a fair execution graph
G
inducing
\beta
,
it can be shown that each call to
lock
reads a unique value from
\mathit{ticket}
,
and that whenever a certain
lock
call reads ticket value
v
(and the spinloop exits),
the corresponding
unlock
writes to
\mathit{serving}
value
v+1
.
Moreover, the values written to
\mathit{ticket}
and to
\mathit{serving}
are strictly increasing along
G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
.
(These are standard safety properties, so we elide details of their proofs.)

By means of contradiction, now
assume that there is a fair execution graph
G
inducing
\beta

where
r_{i}
for some
1\leq i\leq N
is incremented only a finite number of times.

Due to thread-fairness of
\beta
, the only way this can happen is if thread
i
has an infinite spinloop.
There may well be multiple threads with infinite spinloops,
so among those threads let us consider the thread
{\tau}
that reads the smallest value for
\mathit{ticket}
, say
k
,
just before going into the infinite spinloop.
So, for all
0\leq j<k
, some
lock
has incremented
\mathit{ticket}
to value
j
and subsequently
\mathit{serving}
to value
j+1
.
In particular, the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal among those sets
\mathit{serving}
to value
k
.
Note that there cannot be any writes to
\mathit{serving}
with larger values
because they all require
\mathit{serving}
to first be set to
k+1
(which does not happen since
{\tau}
is stuck in a spinloop).

Because of thread-fairness and
Theorem

5.3
,
the infinite spinloop must have an iteration that reads from the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal write to
\mathit{serving}
,

i.e.,
reading value
k
.
This is a contradiction, because reading
k
exits the loop.
∎

5.3.
MCS lock

As a third example, we study the MCS lock
(
Mellor-Crummey and
Scott 1991
)
,
which is the basis of the
qspinlock
currently used in the Linux kernel
and the highly scalable NUMA-aware HMCS lock
(
Chabbi
et al. 2015
)
.
For the latter,
Oberhauser et al. 2021b
observe that “the fences necessary
for the HMCS lock on systems with processors that use weak ordering” presented
in the original HMCS paper
(
Chabbi
et al. 2015
, p. 218)
result in non-terminating behaviors
under RC11, which do in fact occur in practice when running the HMCS lock on a
Kunpeng 920 Arm server.
Non-termination is due to a missing release fence (or store-release) in the MCS lock used in that algorithm.
For simplicity, we therefore limit our discussion to the MCS lock, whose code follows.

\begin{array}[]{@{}l@{~~}m{2em}@{~~}l@{}}\begin{array}[]{@{}l@{}}\textbf{{QNode}}\;\textit{Lock}\;{:=}\;\textbf{{null}}\\[5.0pt]
\textbf{{void}}\;lock(\textbf{{QNode}}\;n)\;\{\\
\quad\begin{array}[t]{@{}l@{}}n.\textit{locked}\;{:=}\;1\\
n.\textit{next}\;{:=}\;\textbf{{null}}\\
{\color[rgb]{0,0.5,0.5}//\;\textit{$\textbf{{fence}}^{\textbf{{rel}}}$ missing in HMCS paper}}\\
\textbf{{QNode}}\;\textit{pred}\;{:=}\;\textbf{{SWAP}}^{\textbf{{acqrel}}}(\textit{Lock},n)\\
\textbf{{if}}\;\textit{pred}\not=\textbf{{null}}\\
\begin{array}[t]{@{}l@{}l}\textbf{{then}}&\begin{array}[t]{l}\textit{pred}.\textit{next}\;{:=}\;n\\
\textbf{{while}}\;n.\textit{locked}=1\;\{\;\;\}\\
\textbf{{fence}}^{\textbf{{acq}}}\end{array}\\
\end{array}\end{array}\\
\}\\
\end{array}&&\begin{array}[]{@{}l@{}}\textbf{{void}}\;unlock(\textbf{{QNode}}\;n)\;\{\\
\quad\begin{array}[t]{@{}l@{}}\textbf{{fence}}^{\textbf{{rel}}}\\
\textbf{{QNode}}\;\textit{succ}\;{:=}\;n.\textit{next}\\
\textbf{{fence}}^{\textbf{{acq}}}\quad{\color[rgb]{0,0.5,0.5}//\;\textit{can be elided on ARM}}\\
\textbf{{if}}\;\textit{succ}=\textbf{{null}}\\
\begin{array}[t]{@{}l@{}l}\textbf{{then}}&\begin{array}[t]{l}\textbf{{if}}\;\textbf{{CAS}}^{\textbf{{acqrel}}}(\textit{Lock},n,\textbf{{null}})\\
\begin{array}[t]{@{}l@{}l}\textbf{{then}}&\begin{array}[t]{l}\textbf{{return}}\end{array}\\
\textbf{{else}}&\begin{array}[t]{l}\textbf{{repeat}}\;\{\;\begin{array}[t]{@{}l@{}}\textit{succ}\;{:=}\;n.\textit{next}\;\}\end{array}\\
\quad\textbf{{until}}\,\textit{succ}\not=\textbf{{null}}\end{array}\\
\end{array}\end{array}\\
\end{array}\\
\textit{succ}.\textit{locked}\;{:=}\;0\end{array}\\
\}\\
\end{array}\end{array}

The MCS lock uses a FIFO queue to ensure fairness.
Therefore, the
lock
and
unlock
functions take a
QNode
argument to identify the calling thread.
A thread
T
can enter the critical section (after calling the
lock
function) either if the queue is empty
or after its predecessor in the queue lowers the
locked
bit in
T
’s
QNode
.
To release the lock, a thread
T
lowers the
locked
bit of the next thread in the queue,
or if no such thread exists, empties the queue.

Consider now the following client program, in which two threads enter the critical section once.

(MCS-Client)

\begin{array}[]{@{}l@{~~}||@{~~}l@{}}\begin{array}[]{@{}l@{}}a\;{:=}\;\textbf{{new QNode}}()\\
\textit{lock}(\textit{Lock},a)\\
\textit{unlock}(\textit{Lock},a)\end{array}&\begin{array}[]{@{}l@{}}b\;{:=}\;\textbf{{new QNode}}()\\
\textit{lock}(\textit{Lock},b)\\
\textit{unlock}(\textit{Lock},b)\end{array}\end{array}

Suppose we want to show that this program terminates
and, in particular, that the
while
loops in
\mathit{lock}
terminate if ever reached.
Due to symmetry, we only consider the loop for
n=a
.
By
Theorem

5.3
, it suffices to consider the iteration in which the loop reads from the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal store.
We can now construct all candidate
{\color[rgb]{1,0.5,0}\mathtt{mo}}
s and attempt to show for each one that
either the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal store allows the loop to terminate or any graph with that
{\color[rgb]{1,0.5,0}\mathtt{mo}}
is not RC11-consistent.

It is easy to show that in every execution of this program in which that loop is reached,
there are exactly two non-initial stores to
a.\textit{locked}
,
generated by the calls
\mathit{lock}(\textit{Lock},a)
and
\mathit{unlock}(\textit{Lock},b)
, respectively.
For brevity’s sake, we call these stores
A
and
B
respectively.
Since
B
writes
a.\textit{locked}=0
, reading from it allows the loop to terminate.
Consequently, the loop may only diverge in execution graphs in which
A
is
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal.
Such a graph is shown below.
{{\mathtt{W}}}({a.\textit{locked}},{1})

A

{{\mathtt{W}}}({a.\textit{next}},{\textbf{{null}}})

{{\mathtt{RMW}}}({\textit{Lock}},{b},{a})

{{\mathtt{W}}}({b.\textit{next}},{a})

{{\mathtt{R}}}({a.\textit{locked}},{1})

…
{{\mathtt{W}}}({b.\textit{locked}},{1})
{{\mathtt{W}}}({b.\textit{next}},{\textbf{{null}}})

{{\mathtt{RMW}}}({\textit{Lock}},{\textbf{{null}}},{b})

ABC
\textbf{{F}}^{\textbf{{rel}}}
{{\mathtt{R}}}({b.\textit{next}},{a})

ABC
\textbf{{F}}^{\textbf{{acq}}}
{{\mathtt{W}}}({a.\textit{locked}},{0})

B

{\color[rgb]{1,0.5,0}\mathtt{mo}}
{\color[rgb]{0,0.6,0}\mathtt{rf}}
{\color[rgb]{1,0.5,0}\mathtt{mo}}
{\color[rgb]{0,0.6,0}\mathtt{rf}}
{\color[rgb]{0,0.6,0}\mathtt{rf}}

The graph is in fact RC11-consistent, and therefore the client program does not always terminate.
Once, however, we add back the commented-out
\textbf{{fence}}^{\textbf{{rel}}}
in the
lock
function, then
the highlighted
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\mathbin{;}{\color[rgb]{0,0.6,0}\mathtt{rf}}\mathbin{;}{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\mathbin{;}{\color[rgb]{1,0.5,0}\mathtt{mo}}

cycle in the execution graph above is forbidden.
Similarly, the release fence also rules out all other graphs in which
A
is the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal store,
and we can thus prove the following theorem.
(Our Coq proof generalizes this theorem to an arbitrary finite number of threads.)

Theorem 5.6.

If the
\textbf{{fence}}^{\textbf{{rel}}}
in the MCS lock is uncommented,
MCS-Client
’s thread-fair behaviors
under
G^{\texttt{fair}}_{\{{\mathsf{SC},\mathsf{TSO},\mathsf{RA},\mathsf{RC11}}\}}
are all finite.

6.
Related Work and Discussion

We have investigated fairness in
({\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}})
-acyclic weak memory models,
both operationally and declaratively, established four equivalence results,
and showed how the declarative formulations can be used for reasoning about program termination.

Several papers,
e.g.,

(
Cerone
et al. 2015
;
Bouajjani
et al. 2014
;
Gotsman and
Burckhardt 2017
)
, have studied
declarative formulations of transactional consistency with prefix-finiteness
constraints to ensure that a transaction is never preceded by an infinite set
of other transactions.
In particular,

Gotsman and
Burckhardt 2017
established a connection
between declarative presentations that include fairness constraints
and operational presentations for models in their “Global Operation
Sequencing” framework. The TSO model can be expressed in this framework.
Their declarative specifications require prefix-finiteness of the global visibility order,
while we derive this property from prefix finiteness of more local relations (
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
).
Thus, our formulation is easily applicable for model checking based on partial order reduction
in the style of
Kokologiannakis et al. 2017
;
Kokologiannakis et al. 2019
.
To the best of our knowledge, this is the first work to make a connection
between liveness in declarative models formulated in the widely used framework of
Alglave
et al. 2014

and in operational models.

Termination of the MCS lock was previously studied by
(
Oberhauser
et al. 2021a
)
;
however, due to the lack of a formal definition of fairness,
Oberhauser
et al. 2021a

assumed a highly technical consequence of fairness in their proofs.
Our unified definition of fairness and
Theorem

5.3

bridge the gap left in their arguments and allow us to obtain the first
complete formal termination proof for the MCS lock.

We note that our approach for establishing termination of spinloops is not only
useful for manually proving deadlock-freedom and related progress properties as
shown in
Section

5
, but can also be used to automatically establish
termination of programs whose only potentially unbounded behavior is due to
spinloops. One can use
Theorem

5.3
to reason about
the termination of such programs by examining only a finite number of finite
execution graphs. This approach has actually been implemented in the

GenMC
model checker
(
Kokologiannakis
and Vafeiadis 2021
)
, and thus termination of
the example programs in the paper (for a bounded number of threads) can
also be shown automatically.

We outline two directions for future work,
which concern extending our results to more complex models.

Fairness under non-
({\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}})
-acyclic models

Some low-level hardware memory models, such as Arm
(
Flur et al. 2016
)
and
POWER
(
Alglave
et al. 2014
)
, and hardware-inspired memory models,
such as LKMM
(
Alglave et al. 2018
)
and IMM
(
Podkopaev
et al. 2019
)
,
record syntactic dependencies between instructions
so as to allow certain executions with cycles in
{\color[rgb]{0.3,0.3,0.3}\mathtt{po}}\cup{\color[rgb]{0,0.6,0}\mathtt{rf}}
.
In these models, prefix-finiteness of
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
alone does not suffice
for prefix-finiteness of the appropriate “happens-before” relation.
For instance, under Arm (version 8)
(
Flur et al. 2016
)
,
assuming prefix-finiteness of
{\color[rgb]{1,0.5,0}\mathtt{mo}}
and
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
does not forbid
the out-of-thin-air read of the value
5
in the following example
(with an unbounded address domain):

Weak RMWs

Besides ordinary (‘‘strong’’) CAS instructions,
C11 supports ‘‘weak’’ CASes,
7
7

7

See
https://en.cppreference.com/w/cpp/atomic/atomic/compare_exchange
[accessed November-2020].

which may fail spuriously,

i.e.,
even when they read the expected value,
since on some architectures—namely, POWER and Arm—weak CASes are
more efficient than strong ones.
A strong CAS can be implemented by repeatedly performing a weak CAS
in a loop as long as it fails spuriously.
Termination of such loops depends upon the weak CASes not always failing spuriously, which constitutes an additional fairness requirement.
Since this requirement is orthogonal to the notion of memory fairness introduced in this paper,
we leave it for future work.

\mathsf{B^{mf}}({{\mathcal{M}}_{\mathsf{SC}}})\subseteq\mathsf{B}({\mathcal{G}_{\mathsf{SC}}^{\texttt{fair}}})

\overline{\rho}^{\cdot}:\mathbb{N}\rightharpoonup\mathsf{Tid}\times{\mathbb{N}}\times\mathsf{ELab}

\overline{\rho}^{k}\triangleq\begin{cases}{\langle{n,{\tau}:{l}}\rangle}&\text{where }k\in\textit{dom}{({\rho})},\;\rho(k)={\tau}:{l},\;{l}\in\mathsf{ELab},\\
&\quad\text{and }n\triangleq|\{{i\leq k\;|\;\exists{l}^{\prime}\in\mathsf{ELab}.\;\rho(i)={\tau}:{l}^{\prime}}\}|\\

–

–

{\color[rgb]{0.75,0,0.25}\mathtt{fr}}\subseteq{<_{\rho}}

G

\beta(G)=\beta

Appendix C
Termination Checking

Just like termination, non-termination can be proven by considering only the iteration of a spinloop which reads only from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores.
If in a finite graph some threads are blocked by spinloop iterations which read from only
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores, and all other threads have terminated, then the graph can be extended to a fair infinite graph with infinite spinloops.

Definition C.1.

A thread
{\tau}
is terminated in execution graph
G
if in the (unique) behavior
\beta
with
G.{\mathtt{E}}=\mathsf{Event}(\beta)
,
\mu_{\tau}(\beta)
is terminating.

An execution graph
G
is a non-termination witness if there is a thread which is not terminated in
G
and all threads
{\tau}
which are not terminated in
G
have finite runs
\mu_{\tau}(\beta)
where
\beta
is the (unique) behavior with
G.{\mathtt{E}}=\mathsf{Event}(\beta)
, and these runs end in a spinloop iteration reading from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores, i.e., for all
{\tau}
there is a spinloop iteration
[n_{\tau},{n_{\tau}}^{\prime}]
of
{\tau}
in
\beta
where
{n_{\tau}}^{\prime}
is the length of
\mu_{\tau}(\beta)
and

[\{{e\in G.{\mathtt{E}}^{\tau}\;|\;n_{\tau}\leq{\mathtt{sn}}(e)\leq{n_{\tau}}^{\prime}}\}];G.{\color[rgb]{0.75,0,0.25}\mathtt{fr}}=\emptyset

Every non-termination witness proves the existence of a fair graph with infinite spinloops.

Theorem C.2.

Let
G
be a non-termination witness with
G.{\mathtt{E}}=\mathsf{Event}(\beta)
where
\beta
is a behavior of a deterministic program.
Then there is a fair execution graph
G^{\prime}
with
G^{\prime}.{\mathtt{E}}=\mathsf{Event}(\beta^{\prime})
where
\beta^{\prime}
is a behavior of the program and every thread which is not terminated in
G
has an infinite spinloop in
\beta^{\prime}
.

Proof.

We first define
\beta^{\prime}
. For each
{\tau}
we defined
\beta^{\prime}({\tau})
by case analysis on whether
{\tau}
is terminated in
G
.
If
{\tau}
is terminated, then
\beta^{\prime}({\tau})=\beta({\tau})
. Otherwise, since
G
is a non-termination witness, the run
\mu_{\tau}(\beta)
of
{\tau}
is finite. Let
K_{\tau}
be the length of this run. For steps
k<K_{\tau}
inside this run, the behavior is unchanged

k<K_{\tau}\ \implies\ \beta^{\prime}({\tau},k)=\beta({\tau},k)

For later steps, we repeat the last spinloop iteration infinitely often. Let
[n_{\tau},{n_{\tau}}^{\prime}]
be the final spinloop iteration of
{\tau}
in
\beta
which reads from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores, and
L_{\tau}={n_{\tau}}^{\prime}-n_{\tau}+1
the length of that iteration (i.e., the number of transitions in the iteration). Then the infinite repetition of this spinloop iteration is defined by

k\geq K_{\tau}\ \implies\ \beta^{\prime}({\tau},k)=\beta({\tau},K_{\tau}-L_{\tau}+(k-K_{\tau})\mod L_{\tau})

Due to determinism, each of these spinloop iterations in the program reads exactly the same values from the same locations and hence traverses exactly the same states. This shows that
\beta^{\prime}
is a behavior of the program.

We proceed to define
G^{\prime}
. The set of events is defined by
G^{\prime}.{\mathtt{E}}=\mathsf{Event}(\beta^{\prime})
. Modification order is unchanged (
G^{\prime}.{\color[rgb]{1,0.5,0}\mathtt{mo}}=G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
). For the reads-from relation we let each of the new events read from the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal store that the final spinloop iteration read from.
We first define a mapping
l({\tau},k)
which maps each serial number
k
of an event in
G^{\prime}
to the serial number of the corresponding event in
G

l({\tau},k)=\begin{cases}k&{\tau}\ \text{is terminated}\ \lor\ k<K_{\tau}\\
K_{\tau}-L_{\tau}+(k-K_{\tau})\mod L_{\tau}&\text{o.w.}\end{cases}

With this definition, we have
\beta^{\prime}({\tau},k)=\beta({\tau},l({\tau},k))
.
We lift this mapping to events in the obvious way:

l(e)={\langle{l({\mathtt{tid}}(e),{\mathtt{sn}}(e)),{\mathtt{tid}}(e):{\mathtt{elab}}(e)}\rangle}

Observe that we have
l(e)\in G.{\mathtt{E}}
for all
e\in G^{\prime}.{\mathtt{E}}
.
Furthermore
G.{\mathtt{E}}\subseteq G^{\prime}.{\mathtt{E}}
; hence
l
is a relation on
G^{\prime}.{\mathtt{E}}
.
It relates new events to the corresponding old event.
Its inverse
l^{-1}
relates old events to the corresponding new events.
This allows defining the reads-from relation of
G^{\prime}
as

G^{\prime}.{\color[rgb]{0,0.6,0}\mathtt{rf}}\ =\ G.{\color[rgb]{0,0.6,0}\mathtt{rf}};l^{-1}

Since
G^{\prime}.{\color[rgb]{1,0.5,0}\mathtt{mo}}
is
G.{\color[rgb]{1,0.5,0}\mathtt{mo}}
, it remains prefix-finite.
Furthermore, the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores in
G^{\prime}
are exactly the
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores in
G
.
Since all the new reads added read from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores, they have no
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}
-successors.
Thus
{\color[rgb]{0.75,0,0.25}\mathtt{fr}}

Therefore
G^{\prime}
is fair, and the claim follows.
∎

Using
Theorems

C.5
and
5.3
, we can use model checking to automatically decide the termination of spinloops for any client which does not generate infinite modification orders. The model checker must simply generate all finite executions of a program in which spinloops are executed for at most one iteration.
This enumerates all non-termination witnesses (modulo staying in spinloops longer than necessary). If any non-termination witness exists, then by
Theorem

C.5
there is an infinite, fair extension of the graph in which the spinloop never terminates.
If there is no non-termination witness, then all spinloops must terminate after reading from
{\color[rgb]{1,0.5,0}\mathtt{mo}}
-maximal stores. Thus by
Theorem

5.3
, all spinloops terminate.

In
(
Oberhauser
et al. 2021a
)
we have implemented this scheme as an extension of GenMC
(
Kokologiannakis et al. 2019
)
, a model checker which can be parametrized with declarative memory systems satisfying certain conditions (MM1–MM4 in
(
Kokologiannakis et al. 2019
)
).
We applied the extended model checker to several locks. Among others, the MCS lock, waiter-count based locks, and the Linux qspinlock can get stuck in a spinloop when using incorrect barrier combinations.
Many of these barrier combinations ensure safety of the locks.
Since non-termination problems under weak consistency can not be detected by existing model checkers, and these barrier combinations are otherwise correct, existing model checkers may give verification engineers an unwarranted level of confidence for programs that have spinloops.
