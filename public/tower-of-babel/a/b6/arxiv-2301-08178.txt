Work-Efficient Query Evaluation with PRAMs
Jens Keppeler, Thomas Schwentick, Christopher Spinrath

Abstract
. The article studies query evaluation in parallel constant time in the CRCW PRAM model. While it is well-known that all relational algebra queries can be evaluated in constant time on an appropriate CRCW PRAM model, this article is interested in the efficiency of evaluation algorithms, that is, in the number of processors or, asymptotically equivalent, in the work. Naive evaluation in the parallel setting results in huge (polynomial) bounds on the work of such algorithms and in presentations of the result sets that can be extremely scattered in memory. The article discusses some obstacles for constant-time PRAM query evaluation. It presents algorithms for relational operators and explores three settings, in which efficient sequential query evaluation algorithms exist: acyclic queries, semijoin algebra queries, and join queries — the latter in the worst-case optimal framework. Under mild assumptions — that data values are numbers of polynomial size in the size of the database or that the relations of the database are suitably sorted — constant-time algorithms are presented that are weakly work-efficient in the sense that work 𝒪 ⁡ ( T 1 + ε ) \mathcal{O}(T^{1+\varepsilon}) can be achieved, for every ε > 0 \varepsilon>0 , compared to the time T T of an optimal sequential algorithm. Important tools are the algorithms for approximate prefix sums and compaction from Goldberg and Zwick (1995).

1.
Introduction

Parallel query evaluation has been an active research area during the
last 10+ years. Parallel evaluation algorithms have been thoroughly
investigated, mostly using the Massively Parallel Communication (MPC) model

[
BKS17
]
. For surveys we refer to

[
KSS18
,
HY20
]
.

Although the MPC model is arguably very well-suited
to study parallel query evaluation, it is not the
only model to investigate parallel query evaluation. Indeed, there is also the
Parallel Random Access Machine (PRAM) model, a more
“theoretical” model which allows for a more
fine-grained analysis of parallel algorithms, particularly in
non-distributed settings. It was shown by Immerman

[
Imm89
,
Imm99
]
that PRAMs with polynomially many processors can evaluate first-order formulas
and thus relational algebra queries in time
\operatorname{\mathcal{O}}(1)
.

In the study of PRAM algorithms it is considered very important that
algorithms perform well, compared with optimal sequential algorithms. The
overall number of computation steps in a PRAM-computation is
called its
work
. An important goal is
to design parallel algorithms that are
work-optimal
in the
sense that their work asymptotically matches the running time of the
best sequential algorithms.

Obviously, for
\operatorname{\mathcal{O}}(1)
-time PRAM
algorithms the work and the number of processors differ at most by a
constant factor. Thus, the result by Immerman shows that relational
algebra queries can be evaluated in parallel constant time with polynomial work.
Surprisingly, to the best of our knowledge, work-efficiency of
\operatorname{\mathcal{O}}(1)
-time PRAM
algorithms for query evaluation has not been investigated in the
literature. This article is meant to lay some groundwork in this direction.

The proof
of the afore-mentioned result that each relational algebra query
can be evaluated in constant-time by a PRAM with polynomial work is
scattered over several articles. It consists basically of three steps, translating from queries
to first-order logic formulas
[
Cod72
]
, to bounded-depth
circuits
[
BIS90
]
, and then to PRAMs
[
Imm89
]
. A complete
account can be found in a monograph by Immerman
[
Imm99
]
. It was
not meant as a “practical translation” of queries and does not yield
one. However, it is not hard to see directly that the operators of the
relational algebra can, in principle, be evaluated in constant time on
a PRAM. It is slightly less obvious, though, how the output of such an
operation is represented, and how it can be fed into the next operator.

{exa}

Let us consider an example to illustrate some issues of constant-time
query evaluation on a PRAM. Let

q
be the following conjunctive query, written in a rule-based
fashion, for readability.

q(x,y,z)\leftarrow E(x,x_{1}),E(x_{1},x_{2}),E(y,y_{1}),E(y_{1},y_{2}),E(z,z_{1}),E(z_{1},z_{2}),R(x_{2},y_{2},z_{2})

A (very) naive evaluation algorithm can assign one processor to each
combination of six
E
-tuples and one
R
-tuple, resulting in work

\operatorname{\mathcal{O}}(|E|^{6}|R|)
. Since the query is obviously acyclic, it can
be evaluated more efficiently in the spirit of Yannakakis’
algorithm
[
Yan81
]
. After its
semijoin phase, the join underlying the
first two atoms
E(x,x_{1}),E(x_{1},x_{2})
can be computed as a sub-query
q_{1}(x,x_{2})\leftarrow E(x,x_{1}),E(x_{1},x_{2})
. This can be evaluated by
|E|^{2}
many
processors, each getting a pair of tuples
E(a_{1},a_{2}),E(b_{1},b_{2})

and producing output tuple
(a_{1},b_{2})
in case
a_{2}=b_{1}
. The output
can be written into a two-dimensional table, indexed in both
dimensions by the tuples of
E
. In the next round, the output
tuples can be joined with tuples from
R
to compute
q_{2}(x,y_{2},z_{2})\leftarrow E(x,x_{1}),E(x_{1},x_{2}),R(x_{2},y_{2},z_{2})
. However, since it is
not clear in advance, which entries of the two-dimensional table
carry
q_{1}
-tuples, the required work is about
|E|^{2}\cdot|R|
. Output tuples of
q_{2}
can again be written into a two-dimensional
table, this time indexed by one tuple from
E
(for
x
) and one tuple from

R
(for
y_{2}
and
z_{2}
). Proceeding in a similar fashion,

q
can be evaluated with work
\operatorname{\mathcal{O}}(|E|^{3}|R|)
. Other evaluation orders
are possible but result in similar work bounds.
In terms of the input size of the database, this amounts to

\operatorname{\mathcal{O}}(\textnormal{{IN}}^{4})
, whereas Yannakakis’ algorithm yields

\operatorname{\mathcal{O}}(\textnormal{{IN}}\cdot\textnormal{{OUT}})
in the sequential setting, where
IN
denotes
the number of tuples in the given relations and
OUT
the size of the query result, respectively.

Let us take a look at the representation of the output of this
algorithm. The result tuples reside in a three-dimensional table, where each dimension is indexed
by tuples from
E
. They are thus scattered over a space of size

|E|^{3}
, no matter the size of the result. Furthermore, the same
output tuple might occur several times due to several valuations. To
produce a table, in which each output tuple occurs exactly once, a
deduplication step is needed, which could yield additional work in the order of

|E|^{6}
.

The example illustrates two challenges posed by the
\operatorname{\mathcal{O}}(1)
-time PRAM
setting, which will be discussed in more detail in
Section 2
.

\blacktriangleright

It is, in general, not
possible to represent the result of a query in a compact form, say,
as an array, contiguously filled with result tuples. In the above
analysis, this obstacle
yields upper bounds in terms of the size of the input database,
but not in the size of the query result.

\blacktriangleright

It might be necessary to deduplicate output (or intermediate)
relations, but, unfortunately, this cannot be done by sorting a
relation, since (compact) sorting in constant time is not possible on PRAMs, either.

We will use compactification techniques for
PRAMs from Goldberg and Zwick
[
GZ95
]
to deal with the first
challenge. The second challenge is addressed by a suitable
representation of the relations. Besides a general setting without any
assumptions, we consider a setting, where data items are mapped to
a linear-sized
1
1

1

As will be discussed at the end of
Section 7
an
initial segment of polynomial size yields the same results, in
most cases.
initial segment of the natural numbers by a dictionary, and a
setting where a linear order for the data values is available.

Although every query of the relational algebra can be evaluated by a

\operatorname{\mathcal{O}}(1)
-time parallel algorithm with polynomial work, the polynomials can be arbitrarily
bad.
In fact, that a graph has a
k
-clique can be expressed by a
conjunctive query (cf.
Section 6.2
) with
k
variables and it follows from Rossman’s

\omega(n^{k/4})
lower bound for the size of bounded-depth circuit
families for
k
-Clique
[
Ros08
]
that any
\operatorname{\mathcal{O}}(1)
-time parallel algorithm that evaluates this query
needs work
\omega(n^{k/4})
. Furthermore, it is conjectured
that the
k
-clique problem cannot be solved in time significantly less than
\operatorname{\mathcal{O}}(n^{k})
by any sequential combinatorial algorithm
[
ABW15
,
ABBK17
]
and therefore it cannot be solved by a constant-time parallel algorithm with work less than
\operatorname{\mathcal{O}}(n^{k})
, either.
2
2

2

For arbitrary algorithms this conjectured bound is
\operatorname{\mathcal{O}}(n^{\smash{\frac{k\omega}{3}}})
, where
\omega
is the fast matrix multiplication exponent.

Hence, it cannot be expected that conjunctive queries can be evaluated in constant time and small work, in general. Therefore, we consider restricted query classes like acyclic conjunctive queries or the semijoin algebra, where much better bounds for sequential algorithms are possible.
We show that, for each
\varepsilon>0
, there are Yannakakis-based algorithms for
acyclic join queries and free-connex acyclic join queries in the dictionary setting with upper work bounds of
\operatorname{\mathcal{O}}((\textnormal{{IN}}\cdot\textnormal{{OUT}})^{1+\varepsilon})
and
\operatorname{\mathcal{O}}((\textnormal{{IN}}+\textnormal{{OUT}})^{1+\varepsilon})
, respectively. Two other results are work-optimal algorithms
for queries of the
semijoin algebra, and algorithms for join queries that are almost
worst-case optimal and almost
work-optimal.

We emphasise that the stated results do not claim a fixed algorithm
that has an upper work bound
W
such that, for every

\varepsilon>0
, it holds
W\in\operatorname{\mathcal{O}}((\textnormal{{IN}}\cdot\textnormal{{OUT}})^{1+\varepsilon})
. It rather means that there is
a uniform algorithm that has
\varepsilon
as a parameter and has the stated
work bound, for each fixed
\varepsilon>0
. The linear factor hidden
in the
\operatorname{\mathcal{O}}
-notation thus depends on
\varepsilon
. This holds analogously
for our other upper bounds of this form.

Furthermore, we consider the semijoin algebra, conjunctive queries with their generalised hypertree width as a
parameter, and worst-case optimal join
evaluation.

Related work.

The initial motivation for our research was to study parallel constant-time algorithms that maintain query results in a dynamic setting, where the database can change over time. This is related to the
dynamic complexity
framework of Patnaik and Immerman

[
PI97
]
and similarly Dong and Su
[
DS95
]
. In this framework, it is studied, which queries can be maintained by dynamic programs
that are allowed to perform a constant time parallel PRAM computation
after each change in the database. In fact, the dynamic programs are
ususually expressed by first-order formulas, but, as stated above, the

\operatorname{\mathcal{O}}(1)
-time PRAM point of view is equivalent. Research on
dynamic complexity has mostly concentrated on queries that cannot be expressed in the
relational algebra (e.g., involving transitive closure as for the
reachability query). It has mainly considered expressibility
questions, i.e., which queries can be maintained in constant time, at
all. Recently, the investigation of such dynamic programs from the work-efficiency point of
view has been initiated
[
SST+21
]
. In this line of research, the plan was to study
the work-aware dynamic complexity of database queries. However, it then
turned out that, due to a lack of existing results, it makes sense to first study how work-efficient queries can be evaluated by constant time PRAM algorithms in the purely static setting.

As mentioned above, to the best of our knowledge, work-efficiency of
\operatorname{\mathcal{O}}(1)
-time parallel algorithms has not been investigated in the literature.
However, parallel query evaluation has, of course, been studied for various other models.
In a recent article, Wang and Yi studied query evaluation by circuits

[
WY22
]
.
Although this is in principle closely related, the article ignores polylogarithmic depth factors and therefore does not study
\operatorname{\mathcal{O}}(1)
-time.

Denninghoff and Vianu
[
DV91
]
proposed
database method schemas
as model for studying parallel query evaluation.
While these schemas are defined for
object-oriented databases
they can also be applied to relational databases.
However, although
[
DV91
]
considers constant-time parallel evaluation, they do not study the work of
\operatorname{\mathcal{O}}(1)
-time parallel algorithms.
Notably, they prove that PRAMs and database method schemas can simulate each other within a logarithmic time factor under some (reasonable) assumptions
[
DV91
, Section 5]
.

Finally, query evaluation has been studied extensively in the Massively Parallel Communication (MPC) model, originally introduced by Beame et al.
[
BKS17
]
.
Particularly noteworthy in the context of our research is that worst-case optimal algorithms
[
KBS16
]
and Yannakakis’ algorithm
[
HY19
]
have been studied within the MPC model.
However, the research focussed – as the name of the model suggests – on the communication between servers, or more precisely the number of required communication rounds and the
load
– that is, the maximal amount of data a server receives during a round.
For the actual computation in between the communication phases, the MPC model has no notion of computation steps; which is why, for studying work bounds, we opted for the PRAM model instead.

2.
A Primer on Constant-Time CRCW PRAM Algorithms

In this section, we define PRAMs and review some results about
\operatorname{\mathcal{O}}(1)
-time parallel
algorithms on CRCW PRAMs from the literature. More precisely, we recall some negative
results, in particular for sorting and some positive results,
involving quite powerful constant-time algorithms for approximative
prefix sums and linear compaction, and padded sorting.
We also give a
\operatorname{\mathcal{O}}(1)
-time algorithm for padded
sorting of sequences of numbers of polynomial size that will be useful
for our purposes.

2.1.
Parallel Random Access Machines (PRAMs)

A
parallel random access machine (PRAM)
consists of a number of
processors that work in parallel and use a shared memory.
The processors are consecutively numbered from
1
to some number

p_{\textnormal{max}}
that depends on the size of the input.
Each processor can access its
processor number
and freely use it in computations.
For instance, a common application is to use it as an array index.
The memory consists of finitely many, consecutively numbered memory cells.
The number of a memory cell is called its
address
.
The input for a PRAM consists of a sequence of
n
but strings of
length
\operatorname{\mathcal{O}}(\log n)
, residing in some designated input memory cells.
We presume that the
word size
, that is, the number of bits that
can be stored in a memory cell, is bounded by
\operatorname{\mathcal{O}}(\log n)
.

A processor can access any memory cell in

\operatorname{\mathcal{O}}(1)
time, given its address.
Furthermore, we assume that the usual arithmetic and bitwise
operations can be performed in
\operatorname{\mathcal{O}}(1)
time by any processor.

The
work
of a
PRAM computation is the sum of the number of all computation steps of
all processors made during the computation.
We define the space required by a PRAM computation as the maximal
address of any memory cell accessed during the
computation.
3
3

3

For simplicity, we do not count the space that
a processor might need for its working register. For some of our
algorithms, the space of a
computation under this definition might be significantly smaller than the number of
processors. However, we never state bounds of that kind, since we do
not consider them useful. Thus, our space bounds for an algorithm are always at least
as large as the work bounds.

We mostly use
the
Concurrent-Read Concurrent-Write model (CRCW PRAM)
,
i.e., processors are allowed to read and write concurrently from and to
the same memory location. More precisely, we mainly assume the

Arbitrary
CRCW PRAM model: if multiple processors concurrently write
to the same memory location, one of them,
“arbitrarily”
,
succeeds. This is our standard model and we often refer to it simply by
CRCW PRAM
.

For some algorithms the weaker
Common
model suffices,
where all processors need to write the same value into the same
location. On the other hand, the lower bounds below even hold for the
stronger
Priority
model, where always the processor with the
smallest processor number succeeds in writing into a memory
cell.

It is well known that the
weakest of the three models, the Common CRCW PRAM, can simulate one step of the strongest model, the Priority CRCW PRAM, in
constant time

[
CDHR88
, Theorem 3.2]
. The simulation in
[
CDHR88
]
only requires an extra
\operatorname{\mathcal{O}}(\log n)
work factor, but might require an extra
\operatorname{\mathcal{O}}(n)
-factor of space. The technique of
[
CDHR88
, Theorem 3.2]
can be easily adapted to yield an extra
\operatorname{\mathcal{O}}(n^{\epsilon})
work factor, but also only an extra
\operatorname{\mathcal{O}}(n^{\epsilon})
-factor of space, for any
\epsilon>0
.

For some algorithms even the Exclusive-Read

Exclusive-Write model (EREW PRAM)
model, where concurrent access is
forbidden or the
CREW PRAM
model, where concurrent writing is
forbidden, are sufficient. Both models are strictly weaker than the
CRCW model with respect to constant time algorithms, since they are,
e.g., not able to compute the OR of
n
bits in constant time

[
CDR86
, Theorem 7]
.

We refer to
[
JáJ92
]
for more details on PRAMs and to
[
vEB90
, Section 2.2.3]
for a discussion of alternative space measures.

2.2.
Lower and Upper Bounds for Constant-Time CRCW PRAM Algorithms

Next, we are going to review some known results about PRAM algorithms
for some basic algorithmic tasks from the literature. These tasks deal
with arrays, a very natural data structure for PRAMs. Before we
describe the results, we first fix some notation for arrays.

An array
\mathbf{A}
is a sequence of consecutive memory cells.
The
size

\left\lvert\mathbf{A}\right\rvert
of

By
\mathbf{A}[i]
for

we refer to the
i
-th cell of
\mathbf{A}
, and to the
(current) content of that cell.
We call

the
index
of cell
\mathbf{A}[i]
.
Furthermore, we assume that the size of an array is always available to all processors (for instance, it might be stored in a
“hidden”
cell with index
0
).
Given an index
i

\mathbf{A}[i]
in
\operatorname{\mathcal{O}}(1)
time with
\operatorname{\mathcal{O}}(1)
work.

We will also use arrays whose cells correspond to
c

c>0
.
In terms of some programming languages this corresponds to an array of structs (or records).
Since a single processor can read and write

constant time, we often blur this distinction.
For instance, we might write
\mathbf{A}[i]

-th block of

c

particular, this will allow us to refer to the
i
-th tuple of a
relation that is stored in that array in a concise way.

1

2.2.1.
Approximate Compaction

1
rules out any constant-time algorithms that compact a
non-compact array (for the stated models). Therefore, the best we can
hope for is approximate compaction, i.e., compaction that guarantees
some maximum size of the result array in terms of the number of
non-empty entries. In the following,
\lambda(n)
will be an

accuracy function
.

We say that an array is
of size
n
is
\lambda
-compact
, for a function

\lambda
, if it has at least
\frac{n}{1+\lambda(n)}

non-empty-cells. That is,
n
is at most
(1+\lambda(n))m
, where
m

is the number of non-empty cells. An
algorithm achieves
\lambda
-approximate
compaction
, if it compacts arrays into
\lambda
-compact
arrays. We call it
order-preserving

array elements does not change.

We can always assume that
\lambda(n)\geq\frac{1}{n+1}
holds, since otherwise (perfect) compaction would be required.
Later on in this article

will be a constant or of

(\log n)^{-a}
, for some
a

We will see that approximate compaction can be done quite well, but the
following result implies a trade-off between time and number of

{propC}

[
[

Any algorithm that achieves

-approximate compaction, for

\lambda

\mu(n)n

\Omega(\log{\frac{\log{n}}{\log{(\mu(n)\lambda(n)+2)}}})

Any algorithm that achieves
\lambda

\lambda>0

\Omega(n^{1+\varepsilon})

Therefore

\frac{\log{n}}{\log{(\mu(n)\lambda+2)}}\leq 2^{t/c}
and
\log{n}\leq 2^{t/c}\log{(\mu(n)\lambda+2)}

Finally, we get
(\mu(n)\lambda+2)^{2^{t/c}}\geq n

\mu(n)\lambda+2\geq n^{1/c^{\prime}}

2.2.2.
Processor Allocation

A crucial task for PRAM algorithms is to assign processors properly to
tasks. Sometimes this is straightforward, e.g., if each element of
some array needs to be processed by a separate processor. However,
sometimes the assignment of processors to tasks is not clear, a
priori. This will, in particular, be the case for the evaluation of
the Join operator. Processor allocation can be formalised as follows.

A
task description

d=(m,\bar{x})
consists of a number

m
specifying how many processors are required for the task, and a
constant number of additional numbers
\bar{x}=(x_{1},\ldots,x_{k})

serving as
“input”
for the task, e.g.
\bar{x}
may
contain links to input arrays or which algorithm is used to solve the
task.A
task schedule
for a sequence
d_{1},\ldots,d_{n}
of task descriptions is an array
\mathbf{C}
of size at least
\sum_{i=1}^{n}m_{i}
such that, for every
i\in\{1,\ldots,n\}

m_{i}
consecutive cells
\mathbf{C}[j_{i}],\ldots,\mathbf{C}[j_{i}+m_{i}-1]
with content
d_{i}
and each of these cells is augmented by a link to
\mathbf{C}[j_{i}]
, i.e. the cell with the smallest index in the sequence.
The tasks specified by
d_{1},\ldots,d_{n}
can then be solved in parallel using
\left\lvert\mathbf{C}\right\rvert
processors: Processor
j
can lookup the task it helps to solve in cell
\mathbf{C}[j]
, and using the link it can also determine its relative processor number for the task.
If a cell
\mathbf{C}[j]
is empty, processor
j
does nothing.

The processor allocation problem is closely related to the prefix sums and interval allocation problems.
We believe the following lemma is folklore.
The relationship of these problems and an analogous result for randomised PRAMs and
\operatorname{\mathcal{O}}(\log^{*}n)

3.
Databases and their Representations for PRAM Algorithms

In this section, we first recall some concepts
from database theory.
Then we discuss three settings that differ by how a
PRAM can access the relations of databases.

Finally, we explain how relations can be represented with the help of arrays.
While the concrete representation will depend on the setting, arrays
will provide a unified interface allowing us to represent
intermediate results and to evaluate queries in a compositional manner.

Notation for databases and queries.

A
database schema
\Sigma

is a finite set of relation symbols,
where each symbol
R
is equipped with a finite set
\textnormal{{attr}}(R)
of attributes.
A tuple
t=(a_{1},\ldots,a_{|\mathcal{X}|})
over a finite list
\mathcal{X}=(A_{1},\ldots,A_{k})
of attributes has, for each
i
, a value

a_{i}
for attribute
A_{i}
.
Unless we are interested in the
lexicographic order of a relation, induced by
\mathcal{X}
, we can view
\mathcal{X}
as
a set.
An
R
-relation is a finite set of tuples over
\textnormal{{attr}}(R)
.
The
arity

\texttt{ar}(R)
of
R
is
|\textnormal{{attr}}(R)|
.
For
\mathcal{Y}\subseteq\mathcal{X}
, we write
t[\mathcal{Y}]
for the restriction of
t
to
\mathcal{Y}
. For
\mathcal{Y}\subseteq\textnormal{{attr}}(R)
,
R[\mathcal{Y}]=\{t[\mathcal{Y}]\mid t\in R\}
.
A database
D
over
\Sigma
consists of an
R
-relation
D(R)
, for each
R\in\Sigma
.
We usually write
R
instead of
D(R)
if
D
is understood from the context.
That is, we do not distinguish between relations and relation symbols.
The size
|R|
of a relation
R
is the number of tuples in
R
.
By
|D|
we denote the number of tuple entries in database
D
.
For details on (the operators of) the relational algebra,
we refer to
[
ABL+21
]
. Throughout this article,
D
always
denotes the underlying database.
We always assume a fixed schema and therefore, in particular, a fixed maximal arity
of
tuples.

Settings.

We next describe the three settings that we study in this article,
distinguished by how PRAMs can interact with (input) databases.

In the most
general setting
, we do not specify how databases are
actually stored. We only assume that the tuples in a relation
R
are numbered from
1
to
\left\lvert R\right\rvert
and the following elemental operations can be carried out in constant time by a single processor.

\blacktriangleright

\operatorname{\textnormal{{Equal}}}(R_{1},i_{1},j_{1};R_{2},i_{2},j_{2})
tests whether
the
j_{1}
-th attribute of the
i_{1}
-th tuple of
R_{1}
has the same
value as the
j_{2}
-th attribute of the
i_{2}
-th tuple of
R_{2}
;

\blacktriangleright

\operatorname{\textnormal{{EqualConst}}}(R,i,j,x)
tests whether
the
j
-th attribute of the
i
-th tuple of
R
has value
x
;

\blacktriangleright

\operatorname{\textnormal{{Output}}}(R,i_{1},j_{2};i_{2},j_{2})
outputs the value of the
j_{1}
-th
attribute of the
i_{1}
-th tuple of
R
as
j_{2}
-th attribute of the

i_{2}
-th output tuple;

\blacktriangleright

\operatorname{\textnormal{{NumTuples}}}(R)
returns the number of tuples in relation
R
.

We note that the operations
\operatorname{\textnormal{{EqualConst}}}(R,i,j,x)
are only required for selections with constants, e.g.
\sigma_{A=a}(R)
for a domain value
a
.
For queries without constants, they can be omitted.

The second setting is the
ordered setting
.
Here we assume that there is a linear order on the data values
occurring in the database
D
, and that the following additional
elemental operation is available to access this order.

\blacktriangleright

\operatorname{\textnormal{{LessThan}}}(R_{1},i_{1},j_{1};R_{2},i_{2},j_{2})
tests whether
the
j_{1}
-th attribute of the
i_{1}
-th tuple of
R_{1}
is less or equal than the
value of the
j_{2}
-th attribute of the
i_{2}
-th tuple of
R_{2}
.

The third setting is a specialisation of the ordered setting, in which
we assume that data items are small numbers. More precisely, in the
dictionary setting
we assume that the database
D

has
small data values
, that is, that its data
values are natural numbers from
\{1,\ldots,c_{\texttt{val}}\left\lvert D\right\rvert\}
, for some fixed
constant
c_{\texttt{val}}
.
It is in the spirit of dictionary-based
compressed databases, see, e.g.,
[
CGK01
]
. In a nutshell, such a
database has a dictionary that maps data values to natural numbers and
uses these numbers instead of the original data values throughout
query processing. Such dictionaries are often defined attribute-wise,
but for the purpose of this article we assume for simplicity that
there is only one mapping for all values of the database.

To summarise, the general setting makes no assumptions on the data,
the ordered setting assumes that the data is ordered, and the
dictionary setting further assumes that it consists of small
numbers.

We will see later how the general and the ordered setting can be
translated into the dictionary setting with
reasonable effort and we will mostly study actual query processing for
the dictionary setting.

We note, that the queries we consider do not refer to any
order of data values. Therefore, a possible order has no semantical
use, but it is only used to get better query evaluation algorithms.

It should be noted that the settings considered here are very
analogous to the various alphabet settings in string algorithms for
non-fixed alphabets. For
general alphabets
, algorithms can only
test whether two positions carry the same symbol, for
general ordered
alphabets
, they can be compared with respect to some linear
order. Other algorithms assume
integer alphabets
or

polymomial integer alphabets
, where the symbols are numbers or
numbers of polynomial size in the length of the string, respectively
(see, e.g.,
[
Bre92
,
AB96
]
).

Next, we will explain how data values, tuples, and relations can be represented by a PRAM in memory.
This is in particular intended for storing (intermediate) results and having an interface for (database) operations.

Representing data items.

As indicated before, in this article, databases are represented by
arrays. We first explain how data items are represented such that
each item only requires one memory cell.

In the dictionary setting a data value can be directly stored in a memory cell.
Consequently, for each relation, a tuple can be stored in a constant
number of cells.

However, in the general and the ordered setting we do not make any
assumptions on the size or nature of a single data item. Therefore we
do not assume that a data item can itself be stored in a memory cell
of the PRAM.
Instead, we use token of the form
(R,i,j)
to represent data values, where
R
is a relation symbol,
i\in\{1,\ldots,\left\lvert R\right\rvert\}
and
j\in\{1,\ldots,\left\lvert\textnormal{{attr}}(R)\right\rvert\}
.
More precisely,
(R,i,j)
represents the value of the
j
-th attribute of the
i
-th tuple in relation
R
.
We emphasise that different token
(R_{1},i_{1},j_{1})
and
(R_{2},i_{2},j_{2})
can represent the same data value.
Note that a single processor can test in constant time whether two such token represent the same data value using the operation
\operatorname{\textnormal{{Equal}}}(R_{1},i_{1},j_{1};R_{2},i_{2},j_{2})
.
In the ordered setting the data values represented can be compared using
\operatorname{\textnormal{{LessThan}}}(R_{1},i_{1},j_{1};R_{2},i_{2},j_{2})
.

This encoding extends to tuples in the natural fashion.
Furthermore, such token can be stored in memory cells of a PRAM.
We will refer to this encoding as
token representation
of a data value or tuple.

{exa}

Consider the ternary relation
R
given by

R=\big\{(\texttt{"Hello"},6000,\texttt{blob}_{1}),(\texttt{"World"},3.14,\texttt{blob}_{2}),(\texttt{"Hello"},3.14,\texttt{blob}_{3})\big\}.

The tuples of
R
can be represented by the token sequences

((R,1,1),(R,1,2),(R,1,3)),((R,2,1),(R,2,2),(R,2,3)),\textnormal{ and }((R,3,1),(R,3,2),(R,3,3)).

However, the third tuple could as well be represented by
((R,1,1),(R,2,2),(R,3,3))
.

Of course, even tuples not in
R
can be represented by
token sequences.
For instance,
((R,3,1),(R,2,1))
represents the tuple
(\texttt{"Hello"},\texttt{"World"})
.

Representing databases by arrays.

As indicated before, we represent relations by one-dimensional arrays,
whose cells contain tuples or their token representations and might
be augmented by additional data.

There are
various possibilities how to deal with ordered relations. One might
store a relation
R
in an array and, if available, one or more
ordered lists of position numbers (with respect to some attribute
lists) in additional index arrays.

However, in this article, we rather represent a relation by one array,
which might be ordered with respect to some attribute
list. We made this choice to simplify notation and because, in most
results, only one order of a relation is relevant. The choice does not
affect the complexity results. In the framework with index arrays,
algorithms just need to keep relation arrays and index arrays in sync
(by pointers in both directions) and if a relation array is compacted,
its index arrays are compacted, as well.

Due to the impossibility of (perfect) compaction and sorting in
constant time, as discussed in
Section 2
, our algorithms will often yield
result arrays, in which not all cells represent result
tuples.

Therefore, a cell can be
inhabited
, if it represents a

“useful”
tuple, or
uninhabited
, otherwise, indicated by
some flag.
In all three settings, we refer to the tuple represented by an
inhabited cell
\mathbf{A}[i]
by
\mathbf{A}[i].t
, even if this
representation is via token as in the general and the ordered
setting. In the same spirit we say that a tuple occurs in a cell or a
cell contains a tuple when the cell actually contains a token
representation for the tuple. Please note that the terms “inhabited”
and “uninhabited”
are used on the level of tuples, whereas the terms “non-empty” and
“empty” are used on the level of arrays. In particular, an inhabited
cell (not carrying a
useful
tuple) can be non-empty.

We note that, in all three settings, all elemental operations can be performed by a single processor
in constant time (and space).
Since the arities of the relations at hand are always fixed, this also
extends to tuples.

As mentioned before, there might be additional data stored in a cell, e.g., further Boolean flags and links to
other cells of (possibly) other arrays.
However, the number of items is always bounded by a constant,
therefore we still view the representation of a tuple together with
this additional data as a
cell
, since all of it
can be read or written in time
\operatorname{\mathcal{O}}(1)
.

We say that an array
represents
a
relation
R
, if for each tuple
t
of
R
, there is some inhabited cell
that contains
t
and no inhabited cells represent other tuples not in
R
.
This definition allows that a tuple occurs more than once.
An array represents
R

concisely
, if each tuple occurs in
exactly one inhabited cell. In this case, we call the array
concise
.

To indicate that an array represents a
relation
R
we usually denote it as
\mathbf{R}
,
\mathbf{R}^{\prime}
, etc.

We call an array representing a relation
compact
if it has no
uninhabited cells. We similarly adapt the
notion of
\lambda
-compact arrays to arrays representing
relations.

We often consider the
induced tuple sequence

t_{1},\ldots,t_{\left\lvert\mathbf{A}\right\rvert}
of an array
\mathbf{A}
.
Here,
t_{i}=\mathbf{A}[i].t
is a
proper
tuple, if

\mathbf{A}[i]
is inhabited, or otherwise
t_{i}
is the
empty
tuple

\bot
.

{exa}

The tuple sequence
[(1,5),\bot,(3,4),(8,3),(1,5),\bot,\bot,(7,3)]
from an array

\mathbf{A}
of size eight has five proper tuples and three empty tuples.
It represents the relation
R=\{(1,5),(3,4),(8,3),(7,3)\}
, but
not
concisely.
The sequence
[(1,5),(3,4),(7,3),\bot,(8,3)]
represents

R
concisely and ordered with respect to the
canonical attribute order.
It is not compact but
\frac{1}{4}
-compact.

We assume throughout this article that, if a database is represented by
arrays, all these arrays are concise.

In the ordered and dictionary setting an array
\mathbf{R}
that represents a relation
R
is

\mathcal{X}
-ordered
, for some ordered list
\mathcal{X}
of attributes of
R
’s
schema, if
i<j
implies
\mathbf{A}[i].t[\mathcal{X}]\leq\mathbf{A}[j].t[\mathcal{X}]
, for all indices
i,j
.
We note that this definition allows that tuples that agree on all attributes of
X
occur
in any order. We call
\mathbf{A}

fully ordered
, if it is

\mathcal{X}
-ordered, for some
\mathcal{X}
that contains all
attributes of
R
’s
schema. In this case, the relative order is uniquely determined for all tuples.
We emphasize that, in neither setting, it is guaranteed that ordered arrays for the database relations are given a priori; we discuss this in more detail in
Section 7.2
.

4.
Algorithms for Basic Array Operations

In this section, we present algorithms for some basic operations on database arrays which we will use as building blocks to implement database operations and the transformations between PRAM settings.

To illustrate some aspects of parallel query processing in the PRAM model we first consider an example. Afterwards, we introduce some basic operations in
Section 4.1
. In
Section 4.2
, we give algorithms for padded sorting and compaction, based on the algorithms in
Section 2
.
In
Section 4.3
we study work-efficient search and deduplication algorithms in the dictionary setting and in
Section 4.4
we consider space-efficient search and deduplication algorithms for sorted arrays.

{exa}

We sketch how to evaluate the projection
\pi_{B}(R)
given the array
\mathbf{R}=[(1,5),(3,4),(7,3),\bot,(8,3)]
representing
R
from
Section 3
.

First, the array
\mathbf{R}^{\prime}=[5,4,3,\bot,3]
is computed and each tuple

\mathbf{R}[i]
is augmented by a link to
\mathbf{R}^{\prime}[i]
and vice versa.
For instance,
t_{3}=(7,3)
is augmented by a link to the third cell of
\mathbf{R}^{\prime}
containing
t_{3}^{\prime}=3
and
t_{5}=(8,3)
by a link to the fifth cell containing
t_{5}^{\prime}=3
(and vice versa).
We say that the tuples are mutually linked.

To achieve this, the tuples from
\mathbf{R}
are loaded to processors
1,\ldots,5
, each processor applies the necessary changes to its tuple (or the token representation thereof), and then writes the new tuple to the new array
\mathbf{R}^{\prime}
.
We note that it is not known in advance which cells of
\mathbf{A}
are inhabited and therefore, we need to assign one processor for each cell.
Each processor only applies a constant number of steps, so the overall work is in
\operatorname{\mathcal{O}}(\left\lvert\mathbf{R}\right\rvert)
.

Towards a concise representation of
\pi_{B}(R)
, a second operation eliminates duplicates.
To this end, it creates a copy
\mathbf{R}^{\prime\prime}
of
\mathbf{R}^{\prime}
and checks in parallel, with one processor per pair
(i,j)
of indices with
i<j
, whether
\mathbf{R}^{\prime\prime}[i].t=\mathbf{R}^{\prime\prime}[j].t
holds.
If
\mathbf{R}^{\prime\prime}[i].t=\mathbf{R}^{\prime\prime}[j].t
holds, then cell
\mathbf{R}^{\prime\prime}[j]
is flagged as uninhabited.
Lastly, the algorithm creates links from every cell in
\mathbf{R}^{\prime}
to the unique inhabited cell in
\mathbf{R}^{\prime\prime}
holding the same tuple.
To this end, each processor for a pair
(i,j)
with
\mathbf{R}^{\prime}[i].t=\mathbf{R}^{\prime\prime}[j].t
, for which
\mathbf{R}^{\prime\prime}[i]
is still inhabited, augments the cell
\mathbf{R}^{\prime}[j]
with a link to
\mathbf{R}^{\prime\prime}[i]
. Furthermore, a link from
\mathbf{R}^{\prime\prime}[i]
to
\mathbf{R}[i]
is added.
Note that multiple processors might attempt to augment a cell
\mathbf{R}^{\prime\prime}[i]
with a link to
\mathbf{R}[i]
; but this is fine, even in the Common CRCW model.
Overall, we get two-step-links from
\mathbf{R}
to
\mathbf{R}^{\prime\prime}
and immediate links from
\mathbf{R}^{\prime\prime}
to
“representatives”
in
\mathbf{R}
.

The second operation has a work bound of
\operatorname{\mathcal{O}}(\left\lvert\mathbf{R}\right\rvert^{2})
because it suffices to assign one processor for each pair
(i,j)
of indices and each processor only applies a constant number of steps.

Observe that the algorithms we sketched above can be realised even in the most general setting, since all steps can be implemented with
\operatorname{\textnormal{{Equal}}}
and by manipulating token representations.
∎
As in this example, algorithms for query evaluation will use basic operations. In fact, besides deduplication, also compaction, (padded) sorting and search will be used.

We will see below that the work bound for deduplication can be considerably improved in the dictionary setting or if the array is ordered, thereby also improving the bound for
the ordered setting.

4.1.
Basic Operations

We now describe the basic array operations which we will use as building
blocks for query evaluation algorithms
for PRAMs.

Just as in
Section 4
, the operations
are usually applied to arrays representing relations, and produce an array as output. Furthermore, in all participating arrays, tuples might be augmented by additional data, in particular, by links to other tuples. In fact, each time a tuple of an output
array results from some tuple of an input array links are added.

We emphasise that the input (and output) arrays of the following operations do
not
necessarily have to represent relations concisely, some operations are even only meaningful if they do not.

\blacktriangleright

\operatorname{\textnormal{{Compact}}}_{\lambda}(\mathbf{A})
copies the
proper tuples in
\mathbf{A}
into distinct cells of an array

\mathbf{B}
of size at most
(1+\lambda)k
,
where
k
is the number of proper tuples in
\mathbf{A}
and
\lambda>0
a constant.
Mutual links are added between each inhabited cell
\mathbf{A}[i]
and the cell of
\mathbf{B}
the contents of
\mathbf{A}[i]
got copied to.
Additionally, the operation preserves the relative order of tuples.

\blacktriangleright

\operatorname{\textnormal{{Sort}}}_{\lambda}(\mathbf{A},\mathcal{X})
returns an
\mathcal{X}
-ordered array
\mathbf{B}
of size
(1+\lambda)\left\lvert\mathbf{A}\right\rvert
which contains all proper tuples of
\mathbf{A}
.
Here
\mathcal{X}
is an ordered list of attributes from the relation represented by
\mathbf{A}
.
Mutual links are added between each inhabited cell of
\mathbf{A}
and the corresponding cell of
\mathbf{B}
.

\blacktriangleright

\operatorname{\textnormal{{SearchTuples}}}(\mathbf{A},\mathbf{B})
links every inhabited cell

\mathbf{A}[i]
to an inhabited cell
\mathbf{B}[j]
,
such that
\mathbf{B}[j].t=\mathbf{A}[i].t
holds, if such a cell
exists. We sometimes write
\operatorname{\textnormal{{SearchTuple}}}(t,\mathbf{B})
in the special case that only one tuple
t
is searched for.

\blacktriangleright

\operatorname{\textnormal{{Deduplicate}}}(\mathbf{A})
chooses one representative tuple from
each set of identical tuples, deactivates the other tuples and adds a link from each deactivated other tuple to the representative tuple for the set.

In the remainder of this section, we give
\operatorname{\mathcal{O}}(1)
-time parallel algorithms for these operations.

\blacktriangleright

For
\operatorname{\textnormal{{Compact}}}_{\lambda}
we give an algorithm that even works in the most general setting and relies on
Section 2.2.1
.

\blacktriangleright

For
\operatorname{\textnormal{{Sort}}}_{\lambda}
we give an algorithm for the dictionary setting.

\blacktriangleright

For the other three operations, we give work-efficient algorithms in the dictionary setting and space-efficient algorithms that assumes that (at least) one array is ordered in an appropriate way.

4.2.
Algorithms for Compaction and Padded Sorting

In this subsection, we present algorithms for compaction and sorting.
They are both easily inherited from their counterparts in
Section 2
.

The following result for
\operatorname{\textnormal{{Compact}}}_{\lambda}
basically follows from
Section 2.2.1
.

{lemC}

[
[
GZ95
, implied by Theorem 4.2]
]
For every constant
\lambda>0
and
\varepsilon>0
, there is a
\operatorname{\mathcal{O}}(1)
-time parallel algorithm for
\operatorname{\textnormal{{Compact}}}_{\lambda}
that, given an array
\mathbf{A}
, requires
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert^{1+\varepsilon})

We note that the result holds even for the most general setting.

follows from

by observing that for any constant

.
The mutual links can be established as follows: Instead of compacting
\mathbf{A}
directly, the algorithm allocates an array
\mathbf{A}^{\prime}
of the same size as

and sets
\mathbf{A}^{\prime}[i]=i
if

and

.

The following result for
\operatorname{\textnormal{{Sort}}}_{\lambda}
is easily obtained from

Lemma 7
.

For all constants
\lambda>0
and
k
, there is a
\operatorname{\mathcal{O}}(1)
-time parallel algorithm for
\operatorname{\textnormal{{Sort}}}_{\lambda}
that, given an array
\mathbf{A}
and a list

of

attributes, requires
\operatorname{\mathcal{O}}((\left\lvert\mathbf{A}\right\rvert+\left\lvert D\right\rvert)^{1+\varepsilon})
work and space on a Common CRCW PRAM in the dictionary setting.

Proof 4.1
.

Let
t_{1},\ldots,t_{n}
with
n=\left\lvert\mathbf{A}\right\rvert
be the tuple sequence given by
\mathbf{A}
.
We assume that
\mathcal{X}=(A_{1},\ldots,A_{k})
contains all attributes occurring in
\mathbf{A}
.
Otherwise,
\mathcal{X}
can be extended arbitrarily.
In the following we denote by
\leq_{\mathcal{X}}
the lexicographic order induced by
\mathcal{X}
on the tuples occurring in
\mathbf{A}
.

For each proper tuple
t_{i}
, the algorithm computes its characteristic number

c_{i}=\sum_{j=1}^{k}t_{i}[A_{j}]m^{k-j}

where
m=c_{\texttt{val}}\left\lvert D\right\rvert+1
.
Observe that, since the database has small values,

is larger than any value in
\mathbf{A}
.
Thus, we have
t_{i}\leq_{\mathcal{X}}t_{j}
if and only if
c_{i}\leq c_{j}
for all

.
Furthermore, a processor can derive
t_{i}
from

in constant time.

Thanks to

an array of size
(1+\lambda)\max\{\left\lvert\mathbf{A}\right\rvert,\left\lvert D\right\rvert\}
representing a sequence

, can be computed in constant time with
\operatorname{\mathcal{O}}((\left\lvert\mathbf{A}\right\rvert+\left\lvert D\right\rvert)^{1+\varepsilon})
work and space, such that

implies
c_{i_{j}}\leq c_{i_{\ell}}
. The result array
\mathbf{B}
can then be obtained by storing each tuple

\mathbf{B}[i_{j}]
.
If necessary,

The computation of mutual links is straightforward.

4.3.
Work-Efficient Algorithms for Search and Deduplication

In the dictionary setting, both search and deduplication can be implemented in a work-efficient fashion based on hashing. The dictionary setting in itself can be seen as a form of hashing, more precisely, as mapping (arbitrary) data values injectively to small natural numbers
\operatorname{\mathcal{O}}(\left\lvert D\right\rvert)
. Implicitly, these mappings induce mappings of tuples of arity
k
to numbers of size
\operatorname{\mathcal{O}}(\left\lvert D\right\rvert^{k})
. However, this does not suffice
to obtain work-efficient algorithms for search and deduplication operations. Instead, we lift the basic hashing mappings to the level of tuples in a way that yields natural numbers of size
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert)
for tuples from a given array
\mathbf{A}
. More formally,
we call a mapping that maps each inhabited cell of an array
\mathbf{A}
to a number from

\{1,\ldots,\left\lvert\mathbf{A}\right\rvert\}
, such that
\mathbf{A}[i]
and
\mathbf{A}[j]
get the same number if and only if
\mathbf{A}[i].t=\mathbf{A}[j].t
holds, an

array hash table
.
Array hash tables can be efficiently computed, as the following lemma states.

Lemma 8
.

For every
\varepsilon>0
, there is a
\operatorname{\mathcal{O}}(1)
-time parallel algorithm that, in the dictionary setting, computes an array hash table for a given array
\mathbf{A}
, and requires
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert)
work and
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert\cdot\left\lvert D\right\rvert^{\varepsilon})
space on an Arbitrary CRCW PRAM.

We note that the array hash table computed by the algorithm underlying
8
is not uniquely determined by
\mathbf{A}
, but can depend on the
“arbitrary”
resolution of concurrent write operations.

Proof 4.2

(Proof sketch)
.

We describe the construction for
\varepsilon=1
.

Let
A_{1},\ldots,A_{\ell}
be the attributes of the relation
R
represented by
\mathbf{A}
in an arbitrary but fixed order and define
\mathcal{X}_{j}=(A_{1},\ldots,A_{j})
for all
j\in\{1,\ldots,\ell\}
.
The algorithm inductively computes hash values for tuples in
R[\mathcal{X}_{j}]
for increasing
j
from
1
to
\ell
. It uses
\left\lvert\mathbf{A}\right\rvert
processors.

The idea is to assign, to each tuple
t\in R[\mathcal{X}_{j}]
, a number in the range
\{1,\ldots,\left\lvert\mathbf{A}\right\rvert\}
as hash value and to augment each cell of
\mathbf{A}
containing a proper tuple
t^{\prime}
with
t^{\prime}[\mathcal{X}]=t
by this hash value.
The challenge is that the same (projected) tuple
t\in R[\mathcal{X}_{j}]
might occur in multiple cells of
\mathbf{A}
.

Recall that, in the dictionary setting, each value in the active domain is a number of size at most
c_{\texttt{val}}\left\lvert D\right\rvert
.

For the base case
j=1
the algorithm allocates an auxiliary array
\mathbf{B}
of size
c_{\texttt{val}}\left\lvert D\right\rvert
. For each
i\leq\left\lvert\mathbf{A}\right\rvert
, let
t_{i}=\mathbf{A}[i].t
.
Each processor
i
with a proper tuple writes its processor number
i
into cell
t_{i}[A_{1}]
of
\mathbf{B}
and then augments
t_{i}
by the value actually written at position
t_{i}[A_{1}]
.
Note that, for each value
a
, all processors
i
with
t_{i}[A_{1}]=a
will assign the same value to their tuple
t_{i}
, since precisely one processor among the processors with
t_{i}[A_{1}]=a
succeeds in writing its number to cell
t_{i}[A_{1}]
on an Arbitrary CRCW PRAM.
This needs
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert)
work and
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert+\left\lvert D\right\rvert)
space.

For
j>1
the algorithm proceeds similarly but also takes, for a tuple
t
, the previous hash value
h_{j-1}(t[\mathcal{X}_{j-1}])
for
t[\mathcal{X}_{j-1}]
into account, in addition to
t[A_{j}]
.
It allocates an auxiliary array
\mathbf{B}
of size
\left\lvert\mathbf{A}\right\rvert\cdot c_{\texttt{val}}\left\lvert D\right\rvert
which is interpreted as two-dimensional array and each processor writes its number
i
into cell
(h_{j-1}(t_{i}[\mathcal{X}_{j-1}]),t_{i}[\mathcal{X}_{j}])
of
\mathbf{B}
, if
t_{i}
is a proper tuple.
The number written into this cell is then the hash value for
t_{i}[\mathcal{X}_{j}]
, as in the base case.

Writing and reading back the processor numbers requires
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert)
work and
\mathbf{B}
requires
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert\cdot\left\lvert D\right\rvert)
space.
The same bounds hold for the recursive invocations of
\operatorname{\textnormal{{ComputeHashvalues}}}
.
Since the recursion depth is
\ell
, the procedure requires
\operatorname{\mathcal{O}}(\ell\cdot\left\lvert\mathbf{A}\right\rvert)=\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert)
work and, because the space for
\mathbf{B}
can be reused,
\operatorname{\mathcal{O}}(\left\lvert\mathbf{A}\right\rvert\cdot\left\lvert D\right\rvert)
space in total.
This concludes the proof for the case
\varepsilon=1
and, of course, the same construction works for
\varepsilon>1
.

For
\varepsilon<1
, each attribute can be replaced by a list of
\lceil\frac{1}{\varepsilon}\rceil
attributes with values of size
\operatorname{\mathcal{O}}(\left\lvert D\right\rvert^{\varepsilon})
. The factor
\left\lvert D\right\rvert
in the space bound above can thus be replaced by
\left\lvert D\right\rvert^{\varepsilon}
, as in the statement of the lemma. The asymptotic overall work is not affected by this adaptation, since it only adds a factor of
\lceil\frac{1}{\varepsilon}\rceil
.

Lemma 9
.

For every
\varepsilon>0
, there is a
\operatorname{\mathcal{O}}(1)
-time parallel algorithm for
\operatorname{\textnormal{{SearchTuples}}}
that, given arrays

and space

(Proof sketch)
.

First an array hash table for (the concatenation of)

and

Even though the algorithms of

In sequential database processing, indexes implemented by search trees make it possible to efficiently test whether a given tuple is in a given relation and to find the largest “smaller” tuple, if it is not. In a concise ordered array, this is possible in constant time with work

6.2.
Acyclic and other Conjunctive Queries

There are various fragments of the class of conjunctive queries, defined by restrictions on the structure of a query, that allow efficient query evaluation. For instance, there are the acyclic join queries and, more generally, acyclic queries, which can be evaluated efficiently by the well-known Yannakakis algorithm
[

]

In this subsection, we study how queries of some of these fragments can be evaluated work-efficiently in parallel constant time. We first study acyclic queries and their variants and then generalise the results to queries of bounded generalised hypertree width. Before that we recall the definition of conjunctive queries and fix our notation.

Conjunctive queries are conjunctions of relation atoms. We write a

7.
Query Evaluation in Other Settings

In this section we discuss query evaluation in other settings than the
dictionary setting.

We first consider the general setting, where data
can only be compared with respect to equality. In this setting it
turns out that the naive algorithms for the evaluation of database
operations are already work-optimal: for
\operatorname{\textnormal{{Select}}}_{A=a}
the work is
linear and for the other operators quadratic. We also show that with
quadratic work in its size, a database can be translated into the
dictionary setting in constant parallel time. Therefore, all results
of
Section 6
apply to the general setting with an extra additive term

\operatorname{\mathcal{O}}(\left\lvert D\right\rvert^{2})
(or
\operatorname{\mathcal{O}}(\textnormal{{IN}}^{2})
— cf.
Table 3
, left column).

Then we consider the setting, where data can be compared with respect
to a linear order. Without any further assumption, the linear order
does not give us better algorithms while the lower bounds of the general
setting cease to exist. However, with a somewhat stronger assumption
it is possible to translate a given database into the dictionary setting
in constant parallel time with work

\operatorname{\mathcal{O}}(\left\lvert D\right\rvert^{1+\varepsilon})
and in this way most bounds of

Section 6
for query evaluation apply (cf.
Table 3
, middle column). We refer to this setting
as the
attribute-wise
ordered
(or
a-ordered
) setting.

Conclusion

This article is meant as a first study on work-efficient

-time parallel algorithms for

evaluation algorithm. Of course, it would be nice if this impression
could be substantiated by lower bound results, but that seems to be challenging.

Some of the results presented in this article can be slightly improved. Indeed, Daniel Albert has shown in his Master’s thesis that predecessor and successor links can be computed with work and space

There remain many questions for future work. Is it possible to improve some of the work bounds of the form

k

\sum_{k=0}^{m}\binom{m}{k}\left(\frac{1}{m^{b}}\right)^{k}=1+m\cdot\frac{1}{m^{b}}+\sum_{k=2}^{m}\binom{m}{k}\left(\frac{1}{m^{b}}\right)^{k}=1+m\cdot\frac{1}{m^{b}}+\sum_{k=1}^{m-1}\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k+1}.

To establish the inequality it thus suffices to show that
r=\sum_{k=1}^{m-1}\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k+1}
is less or equal than
m\cdot\frac{1}{m^{b}}
.
Indeed, then it follows that

(1+\frac{1}{m^{b}})^{m}=1+m\cdot\frac{1}{m^{b}}+\sum_{k=1}^{m-1}\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k+1}\leq 1+2\cdot m\cdot\frac{1}{m^{b}}=1+2(\log n)\cdot\lambda^{\prime}(n)

holds.

For establishing
r\leq m\cdot\frac{1}{m^{b}}
, we observe that it suffices to show that
\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k}\leq 1
holds, for every
k\in\{1,\ldots,m-1\}
.
Expanding the binomial coefficient yields

\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k}=\frac{m!}{(k+1)!\cdot(m-k-1)!}\cdot\left(\frac{1}{m^{b}}\right)^{k}\\
=\frac{m\cdot(m-1)\cdot\ldots\cdot(m-k)}{(k+1)!}\left(\frac{1}{m^{b}}\right)^{k}=\frac{m\cdot(m-1)\cdot\ldots\cdot(m-k)}{(k+1)!\cdot m^{bk}}.

Finally, note that there are
k+1
factors in the numerator, each of which is less or equal than
m
, and
m
occurs at least
bk\geq 2k\geq k+1
times in the denominator, since
k\geq 1
and
b>1
by assumption.
Since also
(k+1)!\geq 1
, we can conclude that
\binom{m}{k+1}\left(\frac{1}{m^{b}}\right)^{k}\leq 1
holds.

The last step to prove
Section 2.2.1
is to show that the work and space bounds can be improved to
\operatorname{\mathcal{O}}(n^{1+\varepsilon})
.

Proof A.2

(Proof of
Section 2.2.1
)
.

Due to
Appendix A
there is a
\operatorname{\mathcal{O}}(1)
-time parallel algorithm that computes prefix sums with polynomial work and space.
Let
n=\left\lvert\mathbf{A}\right\rvert
and
c
be a constant such that this algorithm requires work and space
\operatorname{\mathcal{O}}(n^{c})
.
Furthermore, let
\varepsilon>0
be arbitrary but fixed, and define
\delta=\frac{\varepsilon}{c}
.

Let
\lambda^{\prime}(n)
be an accuracy function of the form
\lambda^{\prime}(n)=(\log n)^{-b}
such that
(1+\lambda^{\prime}(n))^{2}\leq(1+\lambda(n))
holds for all
n>2
.
Note that this can be done by choosing a large enough
b
which only depends on
a
.

The algorithm operates as follows in three steps.
It first divides the given array
\mathbf{A}
into
m=n^{1-\delta}
subarrays
\mathbf{A}_{1},\ldots,\mathbf{A}_{m}
of size at most
n^{\delta}
.
Then, for each subarray
\mathbf{A}_{k}
in parallel, arrays
\mathbf{B}_{k}
containing consistent
\lambda^{\prime}
-approximate prefix sums for
\mathbf{A}_{k}
are computed using the algorithm guaranteed by
Appendix A
.
This step requires work and space
\operatorname{\mathcal{O}}(n^{1+\varepsilon})
because

\left(n^{\delta}\right)^{c}\cdot n^{1-\delta}=n^{\frac{\varepsilon}{c}c}\cdot n^{1-\frac{\varepsilon}{c}}=n^{1+\varepsilon-\frac{\varepsilon}{c}}\leq n^{1+\varepsilon}.

In the second step, the algorithm initialises an array
\mathbf{C}
of size
n^{1-\delta}
by setting
\mathbf{C}[1]=0
and, for every index
k>1
,
\mathbf{C}[k]
to the largest prefix sum computed for
\mathbf{A}_{k-1}
, i.e.
\mathbf{B}_{k-1}[n^{\delta}]
.
It then recursively computes an array
\mathbf{D}
containing consistent
\lambda^{\prime}
-approximate prefix sums for
\mathbf{C}
.

Finally, in the third step, the prefix sums for the
\mathbf{A}_{k}
and
\mathbf{C}
are combined to prefix sums for
\mathbf{A}
.
For an index
i\in\{1,\ldots,n\}
let
k_{i}\in\{1,\ldots,m\}
and
i^{\prime}\in\{1,\ldots,n^{\delta}\}
be such that
n^{\delta}\cdot(k_{i}-1)+i^{\prime}=i
.
That is, the
i
-th cell of
\mathbf{A}
is the
i^{\prime}
-th cell of subarray
\mathbf{A}_{k_{i}}
.
Let
\mathbf{B}
be the array of length
n
with
\mathbf{B}[i]=\mathbf{B}_{k_{i}}[i]+\mathbf{D}[k_{i}]
.
The algorithm returns the array
\mathbf{B}
.

The last step can easily be performed with linear work and space.
The recursive call in the second step thus requires
\operatorname{\mathcal{O}}(n^{1+\varepsilon})
as well.
Note that the recursion depth is at most
\log_{n^{\delta}}n\in\operatorname{\mathcal{O}}(\frac{1}{\delta})
.
Therefore, the algorithm runs in constant time and requires work and space
\operatorname{\mathcal{O}}(n^{1+\varepsilon})
as claimed.

In the following we prove that the algorithm is correct.
That is, we prove that
\mathbf{B}
contains consistent
\lambda
-approximate prefix sums for
\mathbf{A}
.

Let
i\in\{1,\ldots,n\}
and let
i^{\prime}
and
k_{i}
be as before.
We first show that
\mathbf{B}
contains (not necessarily consistent) approximate prefix sums for
\mathbf{A}
.
Indeed, we have

\displaystyle\sum_{j=1}^{i}\mathbf{A}[j]

\displaystyle=\sum_{\ell=1}^{k_{i}-1}\sum_{j=1}^{n^{\delta}}\mathbf{A}_{\ell}[j]+\sum_{j=1}^{i^{\prime}}\mathbf{A}_{k_{i}}[j]

\displaystyle\leq\sum_{\ell=1}^{k_{i}-1}\mathbf{B}_{\ell}[n^{\delta}]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle=\sum_{\ell=1}^{k_{i}-1}\mathbf{C}[\ell+1]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle=\sum_{\ell=1}^{k_{i}}\mathbf{C}[\ell]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle\leq\mathbf{D}[k_{i}]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle=\mathbf{B}[i]

where the first inequality holds because the
\mathbf{B}_{\ell}
contain prefix sums for the
\mathbf{A}_{\ell}
, the second and third equalities hold by definition of
\mathbf{C}
(in particular,
\mathbf{C}[1]=0
), and the last inequality holds because
\mathbf{D}
contains approximate prefix sums for
\mathbf{C}
.

Conversely, we have

\displaystyle\mathbf{B}[i]

\displaystyle=\mathbf{D}[k_{i}]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle\leq(1+\lambda^{\prime}(n))\sum_{\ell=1}^{k_{i}}\mathbf{C}[\ell]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle=(1+\lambda^{\prime}(n))\sum_{\ell=1}^{k_{i}-1}\mathbf{B}_{\ell}[n^{\delta}]+\mathbf{B}_{k_{i}}[i^{\prime}]

\displaystyle\leq(1+\lambda^{\prime}(n))\sum_{\ell=1}^{k_{i}-1}(1+\lambda^{\prime}(n))\sum_{j=1}^{n^{\delta}}\mathbf{A}_{\ell}[j]+(1+\lambda^{\prime}(n))\sum_{j=1}^{i^{\prime}}\mathbf{A}_{k_{i}}[j]

\displaystyle\leq(1+\lambda^{\prime}(n))^{2}\Big[\sum_{\ell=1}^{k_{i}-1}\sum_{j=1}^{n^{\delta}}\mathbf{A}_{\ell}[j]+\sum_{j=1}^{i^{\prime}}\mathbf{A}_{k_{i}}[j]\Big]

\displaystyle=(1+\lambda^{\prime}(n))^{2}\sum_{j=1}^{i}\mathbf{A}[j]

\displaystyle\leq(1+\lambda(n))\sum_{j=1}^{i}\mathbf{A}[j]

where the first inequality holds because
\mathbf{D}
contains
\lambda^{\prime}
-approximate prefix sums for
\mathbf{C}
, the second equality holds by definition of
\mathbf{C}
, and the second inequality holds because the
\mathbf{B}_{\ell}
contain
\lambda^{\prime}
-approximate prefix sums for the
\mathbf{A}_{\ell}
.
The final inequality holds by choice of
\lambda^{\prime}
.

It remains to show consistency for
i\geq 2
.
That is, we have to assert that
\mathbf{B}[i]-\mathbf{B}[i-1]\geq\mathbf{A}[i]
holds.
We make a case distinction.
If
i
and
i-1
both map to the same subarray, i.e. if
k_{i}=k_{i-1}
holds, then

\mathbf{B}[i]-\mathbf{B}[i-1]=(\mathbf{B}_{k_{i}}[i^{\prime}]+\mathbf{D}[k_{i}])-(\mathbf{B}_{k_{i}}[i^{\prime}-1]+\mathbf{D}[k_{i}])=\mathbf{B}_{k_{i}}[i^{\prime}]-\mathbf{B}_{k_{i}}[i^{\prime}-1]\geq\mathbf{A}_{k_{i}}[i^{\prime}]=\mathbf{A}[i]

where the inequality holds because
\mathbf{B}_{k_{i}}
contains consistent approximate prefix sums for
\mathbf{A}_{k_{i}}
.

Otherwise, we can conclude that
i
is mapped to the first cell of
\mathbf{A}_{k_{i}}
and
i-1
is mapped to the last cell of
\mathbf{A}_{k_{i}-1}
.
Thus, we have

\displaystyle\mathbf{B}[i]-\mathbf{B}[i-1]

\displaystyle=(\mathbf{B}_{k_{i}}[1]+\mathbf{D}[k_{i}])-(\mathbf{B}_{k_{i}-1}[n^{\delta}]+\mathbf{D}[k_{i}-1])

\displaystyle=\mathbf{D}[k_{i}]-\mathbf{D}[k_{i}-1]-\mathbf{B}_{k_{i}-1}[n^{\delta}]+\mathbf{B}_{k_{i}}[1]

\displaystyle\geq\mathbf{C}[k_{i}]-\mathbf{B}_{k_{i}-1}[n^{\delta}]+\mathbf{B}_{k_{i}}[1]

\displaystyle=\mathbf{B}_{k_{i}}[1]

\displaystyle\geq\mathbf{A}_{k_{i}}[1]=\mathbf{A}[i]

where the first inequality holds because
\mathbf{D}
contains consistent approximate prefix sums for
\mathbf{C}
, the last equality holds because we have
\mathbf{C}[k_{i}]=\mathbf{B}_{k_{i}-1}[n^{\delta}]
by definition, and the last inequality holds because
\mathbf{B}_{k_{i}}
contains approximate prefix sums for
\mathbf{A}_{k-1}
.
