A modern framework for jet tagger development Journal:
Annika Stein 1

Abstract
This paper presents a new tool to perform various steps in jet tagger development in an efficient and comprehensive way. A common data structure is used for training, as well as for performance evaluation in data. The introduction of this new framework reduces the amount of data to be stored while accomplishing the same tasks, and shortens waiting times between algorithm development and data-to-simulation results becoming available from months to days, taking typical CMS experiment CMS pipelines as a reference. Proper utilization of high-throughput systems enables first data-to-simulation studies with a recent neural network architecture, Particle Transformer, adapted to jet flavour tagging. Unlike official implementations of the collaboration, the new framework allows investigating different variants, like different training paradigms, and their impact on data/simulation agreement, without producing any new large files on disk, and within the same run of the analysis framework. Besides being more time- and storage-efficient and thus enabling the first results of that kind to be available just few hours after finishing neural network training, the framework is currently the only realization capable of studying how adversarial techniques affect data/simulation agreement for tagger algorithm outputs as well as inputs.

Introduction

As the amount of data to be processed and reduced to meaningful quantities increases, especially now during the Run 3 data-taking period of the Large Hadron Collider (LHC)
LHC
;
LHCDesignReport
;
LHCMachine
at higher energies and with more pile-up, efficient processing tools become increasingly important. Not only the amount of individual samples to be processed, but also the depth in information carried along with each event, or each physics object, forces researchers to adopt new approaches in storage, I/O-handling, feature extraction and data analysis techniques.

Several workflows executed in typical reconstruction or identification algorithm development stages and performance evaluation scenarios as well as physics analysis involve production of samples with specialized data tiers and data formats
mini
;
nano
;
nanotools
;
bta
;
dnt
. The worst-case being that each step along the chain requires its own individual set of inputs, its own format, being incompatible with the frameworks of different layers. Such framework design has the disadvantage that the same information is stored in (slightly) different, yet incompatible formats, blocking available disk space. Also, every realization of the same underlying data needs to be processed, thus requiring computing resources, i.e. computing time in core-hours as well as the “actual time” that passes, to run over the parent data set.

Duplication of data sets in various data formats for each purpose can be avoided, if the frameworks used for the full chain from feature engineering, neural network training, neural network evaluation, and final extraction of data-to-simulation agreement along with scale factors all use the same data structure.

The focus for this paper will be the introduction of a new framework that solves this particular problem in the context of jet tagging developments. Here, jet tagging refers to the task of identifying the flavour of the elementary particle initiating a jet at a hadron collider. Jets are to be understood as the physics objects clustered from a set of collimated particles that underwent hadronization. The key steps that can be unified are identified in the respective following sections, and a practical example where this framework exploits high-throughput computing centers to yield the first data/simulation comparisons of the particular model in question, is given afterwards.

Overview of a commonly used jet tagging development and evaluation workflow, experiment-specific

2.1
Training stage

To facilitate this explanation, assume a new algorithm shall be developed in the context of one of the LHC experiments, for example CMS. Low-level information relevant for the use case presented in this paper exists at the MiniAOD-level, stored with object collections as ROOT
root

np

This explains the existence of ntuples, which are yet again only a very specific variant of the data targeted at this particular algorithm training (again in ROOT format), but flattened to the level of jets. The framework accompanying the DeepJet
deepjet
tagger, which is used for a plethora of CMS analyses (non-exhaustive list:

;

), and publicly available

•

storing resulting data in a format (.djcdc) only readable by the very framework that produced them.

At this point, the underlying information already exists in three variants, parent (MiniAOD), derived ntuples, derived custom data structure. It should be noted that the last item is tagger-input specific, adding another feature would not be possible on-the-fly, instead, the whole chain would need to be repeated. The whole framework is embedded into container images via apptainer, and while writing this manuscript, the supported Python version in the available images excludes using most recent major version updates of PyTorch

2.2
Integration into official reconstruction pipeline

Once training is performed, performance studies are carried out to decide which model should make it into production. At this stage, the workflow only considers simulation, the simulated (statistically independent) sample for cross-validation. Typical studies include derivation of ROC curves, AUC scores, differential efficiencies and mistagging rates. Based on this, highly-performing models are picked, converted into production-ready format (in case of CMS, via ONNX
onnx
), and with each new architecture and / or additional input features, the experiment-specific code (mainly written in C++) needs to be updated for this new reconstruction algorithm. After all this is done, re-processing can happen to evaluate the newly introduced algorithm. Investigating the most recent modifications in the publicly available code base, this can very well take weeks or months and is strongly tied to existing schedules and deadlines induced by LHC or detector operations. If all steps are done up to the level of the last element in the chain, e.g. MiniAOD / NanoAOD, sample production can start. Admittedly, this is just a very superficial summary, but should suffice to get an idea of timescales.

2.3
Studying tagger performance with data

Assuming samples are produced (days or weeks after previous step), a pipeline to investigate data/simulation agreement and eventually derive scale factors (SF) applies selections enriching different jet flavours in pre-defined control regions
CMScalib
. Histograms are filled and statements on the level of agreement are made, taking uncertainties into account. All of this is usually developed independently for various derivation methods, and a plethora of frameworks exists roughly proportional to the number of working groups or phase spaces studied, some requiring particular branches not accessible in centrally produced samples. More information is added into custom ntuples, tools for “post-processed” samples are developed
bta
;
nanotools
;
CMScalib
. While the detailed review of all such tools is beyond the scope of the present paper, it is sufficient to note that a large number of (sub-)frameworks exist, achieving similar goals with (sometimes only slightly) different data-processing methods. At the time of writing, the author is not aware of evaluation tools that read in the exact same data structure used also for training of the algorithms in question and instead require intermediate steps, including those detailed in Sec.
2.2
to be finished. For maximum comparability with the new framework, all interaction with parallel developments for other physics objects potentially affecting the data/MC setup or which corrections need to be applied may be disregarded / idle. Only the jet tagging evaluations tools themselves are to be compared.

The benchmark chosen to demonstrate where the new framework adds or replaces functionality is targeted at a phase space enriching light-flavoured jets, with particular focus on Drell-Yan events with additional jets
CMScalib
. Adding to the challenge, the existing framework to be enhanced by the new one depends on PyROOT
pyroot
imported as part of experiment-specific software, and its building-blocks are event loops with physics object loops nested therein. Parts of the existing implementation are written in Python 2.

3
One framework to synchronize various development steps

The framework comprises two aspects, the data structure, as well as the usage by machine learning and data analysis tools. First, the data structure shall be described.

As previously mentioned, a suitable starting point is MiniAOD which is read by a set of plugins summarized under the term PFNano
pfnano
. The resulting ROOT files are readable by a variety of subsequent tools, including uproot
up
, which can then be interfaced with other libraries ensuring interoperability (e.g. awkward-arrays
ak
, pandas-dataframes
pd
). The term already alludes to two important components: being an extension of
Nano
AOD containing more details on Particle Flow (
PF
)
Particle-flow
candidates and secondary vertices. Thus, with customized functions either calculating features from first principles or accessing features already available as branches in MiniAOD, it is possible to enrich the content of commonly used NanoAOD files with missing features to perform tagger training and evaluation.

Compared to the approaches described in Sec.
2
, this constitutes a format suitable not only for tagger training (perhaps with a format only readable by the specific toolbox), but also for a variety of tasks typically conducted during physics analyses, when performing algorithm validation, or studying data/simulation agreement. The result in terms of efficiency: files that would anyway need to be produced for commissioning or scale factor derivation can be used for training as well. This has multiple consequences: an entire production stage is eliminated, no more duplication of input features in multiple data tiers, saving time and storage. The author has implemented the necessary variables in said plugins, along with new variables that have not been part of existing algorithms, rendering the previously used ntuple-producer redundant.

Considering that indeed, PFNano is already used for evaluation purposes enabled by more recent branch additions

The modules described in Listing

use uproot, awkward, numpy, scipy, scikit-learn, PyTorch, components in brackets are enhancements or alternatives not strictly necessary to replicate the design described in Sec.

. They are designed to run in an interoperable way, just requiring a conda-environment (

All drivers to interact with NVIDIA GPUs available on a variety of clusters can be added into the conda environment, compatibility with the “module” system when enabling CUDA as well as cudnn has been verified. A quick overview on how the different steps are implemented shall be given.
preparations
performs all tasks that need to be finished before any training can be started. To facilitate this chain of operations, for most python-modules an accompanying shell-script is provided that can be executed by computing clusters, utilizing SLURM (
https://slurm.schedmd.com/
) or HTCondor (
https://htcondor.org/
). With the help of aforementioned packages, selections on the samples are placed to remove entries with kinematic properties outside the considered tracker acceptance, based on the number of generator-level particles of a certain kind, jets are labeled with an additional column, input distributions are scanned for outliers, for defaulted or unphysical values and such values replaced with configurable placeholders. A two-dimensional, configurable binning is implemented (equal-width or customized to ensure all bins contain samples) to derive, for each flavour considered, a suitable weighting factor. The target is again configurable, by default, the average across flavours is used, flat distributions or reference distributions for a given flavour are implemented as alternatives. The weights can be configured to either correct only imbalance on two kinematic quantities (
p_{\mathrm{T}},\eta
), only the class imbalance, or both (default). Similar to Ref.
AT
, sample splitting into training, validation and test sets is conducted, and standardization of distributions, with the training set acting as reference, is applied. With results of previous steps in the chain, defaulted values are not considered when deriving the scaling parameters. In the
training
modules, the model is first defined independently outside all other wrapper tools and can thus be imported also elsewhere in later steps. A custom dataloader is provided that ensures quick tensor shuffling and replaces a loop with fast, vectorized operations, loss functions are stored as classes and as simple python functions covering multiple use cases, a custom reweighter class that takes previously created weights into account is added. The core of all resampling or loss-reweighting techniques for the given use case is looking up flavour, transverse momentum and pseudorapidity in an efficient way and then drawing from a distribution, or performing this task once and only using individual sample weights. The latter has been found to be more efficient, which is why this lookup is performed in advance. Its results yield a new column that is appended to the inputs, ensuring tight connection during shuffling. All of these components are accessed by the wrapper module, which carries the training and validation loops, loads the data and stores, after each full iteration through all available samples, the model parameters with additional metadata like loss and accuracy. Several standard metrics are available in
evaluation
, inputs and their correlations can be visualized (properties of each input variable like units, and several helpers to better display relevant intervals assist here), loss curves (training / validation) are available, output scores of the algorithm in question as well as discriminants, ROC curves and AUC complete this set. Finally, the
attacks
module covers what has been introduced to investigate tagger robustness
AT
;
deepjetAT
and will come into play in a later section.

For each PFNano file to be processed for further analysis, a job is submitted via customized HTCondor submission shell-scripts. They are configurable by keywords triggering which models, after which epoch, and with which setup or hyper-parameters, shall be evaluated besides the common algorithms already provided officially. Currently, the framework is designed to perform the analysis with up to three different networks at once, as this has been found to be a reasonable trade-off considering queueing times at typical computing clusters and available resources. As mentioned previously, when interfacing with existing experiment-specific code, an HTCondor job must be able to work both with the established conda-environment, as well as with the PyROOT infrastructure. Therefore, the conda-environment is compressed and can be un-packed and (de-)activated at different stages during execution of the shell-script. The
inference
modules ensure that during every job, the parameters (like model architecture) are known to all executables (bookkeeping). As with the training part, also here the PFNano files are converted into PyTorch tensors for evaluating the networks (see
training/model
), this is done batch-wise, where the batches are customizable to maximize resource usage while taking available memory into account. Default settings are made available to profit from opportunistic resource allocation. It should be noted that predicting is again a vectorized task after flattening from event– to jet–level involving only the outer loop over batches, numpy-arrays are used as output data structure. If one decides to interface this step with
analysis
frameworks making use of event–loops, the flat numpy-arrays are missing the relevant mapping between jet and event. Thus, reshaping with the awkward-package is done to mediate this conflict. After each iteration through an event, the framework notices all jets that have been selected, as well as the jets that did not pass the selection, ensuring the indexing is not affected. Finally, resulting arrays as histogrammed after the selections have been applied. Any input, any output of the different architectures studies, is added, and with the existence of the
attacks
module, all those comparisons can be done not only with the original samples, but also with distorted inputs. This opens a whole new way to study features, their correlations, and how (adversarial) attacks can be understood in the context of data/MC agreement for inputs and outputs.

The author decided against coffea
cof
(probably the most obvious choice at first glance), for the following reasons experienced when using in conjunction with machine learning frameworks:

•

neural network evaluation with some of the largest models present in high-energy physics is memory intensitive,

•

an out-of-memory event happening within parsl- or dask-induced coffea-processors will kill the entire job, not only the single chunk affected, thus loosing all progress and having to start again,

•

logs not particularly helpful for deciphering individual events or objects responsible for unexpected behavior,

•

memory becomes even more of a limiting factor when utilizing coffea for storing arrays instead of map-reducing to histograms,

•

as a follow-up, storing arrays and with that, understanding or investigating correlations between features would not be possible by default or only with massive resource utilization conflicting with user’s computing quota and priority at computing sites.

How the proposed framework can be utilized to quickly get results for new machine learning algorithms will be discussed in the next section.

4
Applying the framework to investigate novel architectures: first data/MC studies

The so called Particle Transformer
ParT
architecture shall be investigated not only with simulated samples, but also in data, in this case recorded by CMS in 2017. Given that Ref.
AT
still raises the question whether adversarial methods improving robustness also translate to better data-to-simulation agreement, two training routines are compared. One the one hand, a nominal training against inputs as available in the data sets is done, on the other hand, a second training imposes adversarial attacks (via FGSM
szegedy2014intriguing
;
goodfellow2015explaining
) on the inputs during training. It has been trained with Run 2 samples using anti-
k_{\mathrm{T}}
jets with
R=0.4
, where the CHS algorithm handles pile-up mitigation
Cacciari_2008
;
Salam_2010
;
Cacciari:2011ma
, inputs mostly follow those previously used for the DeepJet algorithm. Targets and output nodes are b, bb, leptonic b, c, uds, g, same as for DeepJet as well. Training is carried out with methods described in above sections and best validation loss is used to define the epoch and checkpoint considered for following studies. It has been validated with three discriminants (likelihood ratios similar to Ref.
AT
), BvsL, CvsB, CvsL, that the two taggers approach similar performance in terms of ROC curves and AUC scores. For performance evaluation, the methods, considered physics processes and conditions detailed in Ref.
CMScalib
apply. To also include the comparison between nominal training as typically conducted (see for example Ref.
deepjet
;
CMS-BTV-16-002
) and the adversarial training studied in Refs.
AT
;
deepjetAT
, all evaluations are attached for those two methods. This is enabled by the customized analysis that evaluates multiple variants of a network in the same HTCondor job, such that for a given phase space like the one considered here, only one job submission is necessary. Each variant of a tagger is added as an additional branch filled from columns obtained from awkward-arrays and PyTorch tensors. This approach has been compared with the official routine, to save here about five hours, just considering the actual run time, independent of waiting times in the HTCondor queue at the computing cluster. Not to mention the usual workflow oftentimes only starts with month-long delays for the reasons outlined in Sec.
2
. Additionally, one can be sure definitions are synchronized between training and validation, given the same scheme and variable definition applies in both stages, by construction. Once added to the data structure, new branches become available to training and evaluation automatically, which explains how it is possible to investigate performance in data within only one day after the model has been trained.

On the actual results presented in Fig.
1
, the key message of previous results still holds: considering the phase space chosen for this proof-of-concept, adversarial training improves agreement between data and simulation by a large margin. To make this point, statistical uncertainties have been taken into account. Given that in official workflows, no tagger inference is re-run on systematically shifted or scaled quantities (i.e. systematic variations, being theory- or experiment-induced), their inclusion would affect the events selected for nominal or adversarial training in the same way, independent of the algorithm. One may perform this in another step, and while the resulting distributions could be affected by new weights for individual variations, the data/MC ratios in Fig.
1
allow a first cautious interpretation. With uncertainty bands covering the disagreement for nominal training, one could cover the majority of the ratios for adversarial training (in fact all but few bins at very low CvsL scores with few entries only, where statistical effects play a role), while the opposite is not true.

5
Conclusion

The proposed framework has been shown to require only one type of data structure to perform the relevant steps in jet tagger development. Thus, it is conceivable that it can act as the successor of a multitude of individual frameworks, each requiring their own data structure. With the switch from the identified existing data structures to a common one, need for synchronization across frameworks becomes unnecessary. By design, differences are eliminated as the underlying structure is same. Person power attempting to document differences across frameworks and having to reinvent the wheel can be freed up to actually perform the evaluation steps, develop more powerful architectures, and investigate them in a broader context. Existing data sets using this proposed common framework can be reused for multiple purposes, thus saving effectively the costly additional storage requested otherwise. For the first time, the choice which model shall be included for the official reconstruction pipeline, is not limited to performance on simulated samples, but can be facilitated with knowledge on data-to-simulation agreement. Before, decisions were made on only one aspect, now, the presented framework allows statements on algorithm performance from every angle. Previously, such studies have been possible only after a decision had been made. The author hopes that this proof-of-principle, full jet tagging framework can serve as a starting point such that keeping up with fast-paced developments in machine learning becomes easier while still ensuring usability of new algorithms for analysers.

As an example where this new framework shines light into the unknown data-to-simulation properties of a transformer network performing jet flavour tagging in two different variants, three discriminants in a specific control region have been shown. This is the first data/MC study for the network in question. Besides that, these results are another hint that adversarial training improves data-to-simulation agreement, even for an architecture as complex as the transformer. With existing frameworks, the process of finding suitable model architectures becomes intransparent, as only the last iteration that has been chosen finally would be evaluated. The crucial studies that happen to come to conclusions on model choice are otherwise not available, while they yield insights on the way different machine learning techniques deal with the underlying physics. With the presented framework, the author hopes that such investigations become more instructive, that more people start considering data/MC agreement early on in their algorithm development without just focusing on getting another permille improvement in simulation-performance.
