CASU : C ompromise A voidance via S ecure U pdate for Low-end Embedded Systems
Ivan De Oliveira Nunes, Sashidhar Jakkamsetti, Youngil Kim, Gene Tsudik

Abstract
Guaranteeing runtime integrity of embedded system software is an open problem. Trade-offs between security and other priorities (e.g., cost or performance) are inherent, and resolving them is both challenging and important. The proliferation of runtime attacks that introduce malicious code (e.g., by injection) into embedded devices has prompted a range of mitigation techniques. One popular approach is Remote Attestation ( ℛ ​ 𝖠 \sf{\mathcal{R}A} ), whereby a trusted entity (verifier) checks the current software state of an untrusted remote device (prover). RA yields a timely authenticated snapshot of prover state that verifier uses to decide whether an attack occurred. Current RA schemes require verifier to explicitly initiate ℛ ​ 𝖠 \sf{\mathcal{R}A} , based on some unclear criteria. Thus, in case of prover’s compromise, verifier only learns about it late, upon the next ℛ ​ 𝖠 \sf{\mathcal{R}A} instance. While sufficient for compromise detection, some applications would benefit from a more proactive, prevention-based approach. To this end, we construct CASU : Compromise Avoidance via Secure Updates. CASU is an inexpensive hardware/software co-design enforcing: (i) runtime software immutability, thus precluding any illegal software modification, and (ii) authenticated updates as the sole means of modifying software. In CASU, a successful ℛ ​ 𝖠 \sf{\mathcal{R}A} instance serves as a proof of successful update, and continuous subsequent software integrity is implicit, due to the runtime immutability guarantee. This obviates the need for ℛ ​ 𝖠 \sf{\mathcal{R}A} in between software updates and leads to unobtrusive integrity assurance with guarantees akin to those of prior ℛ ​ 𝖠 \sf{\mathcal{R}A} techniques, with better overall performance.



I
Introduction

Over the past two decades, Internet-of-Things (IoT) devices and Cyber-Physical Systems (CPS) have become very popular.
They are deployed in many everyday settings, including both private (e.g., homes, offices, and factories) and public (e.g., cultural, entertainment, and transportation) spaces.
They are also widely used in farming, industrial, and vehicular automation.
These devices often collect sensitive information and perform safety-critical tasks.
Also, in many cases, they are both interconnected and connected to the global Internet.
They are usually implemented atop low-end microcontroller units (MCUs) that have very stringent cost, size, and energy constraints, and unlike their higher-end counterparts, have no (or few) security features.
It is thus not at all surprising that these embedded devices (sensors, actuators, and hybrids) have become attractive attack targets.

In particular, code injection attacks
[
1
,
2
,
3
,
4
]
represent a real and prominent threat to low-end devices.
Embedded systems software is mostly written in C, C++, or Assembly – languages that are very prone to errors.
Code injection attacks exploit these errors to cause buffer overflows and inject malicious code into the existing software or somewhere else in the device memory.

Some previous results considered such attacks in low-end devices and proposed security techniques such as Remote Attestation (
\sf{\mathcal{R}A}
)
[
5
,
6
,
7
,
8
,
9
,
10
]
, as well as proofs of remote software updates and memory erasure
[
11
,
12
,
13
]
.

\sf{\mathcal{R}A}
aims to detect compromise by authenticated measurement of the device’s current software state.
However, it has considerable runtime costs since it requires computing a cryptographic function (usually, a Message Authentication Code (MAC)) over the entire software.
A recent result,
RATA

[
14
]
, minimized the cost of
\sf{\mathcal{R}A}
by measuring a constant-size memory region that reflects the time of last software modification (legal or otherwise).

RATA
achieved that by introducing a hardware security monitor that securely logs each modification time to that region.

Regardless of their specifics,
\sf{\mathcal{R}A}
techniques only
detect
code modifications
after the fact
.
They cannot prevent them from taking place.
Hence, there could be a sizeable window of time between the initial compromise and the next
\sf{\mathcal{R}A}
instance when the compromise would be detected.

To this end, the goal of this paper is to take a more proactive, prevention-based approach to avoid potential compromise.
It constructs
CASU
:
C
ompromise
A
voidance via
S
ecure
U
pdate, which consists of two main components.
First is a simple hardware security monitor that is formally verified.
It performs two functions: (1) blocks all modifications to the specific program memory region where the software resides, and (2) prevents anything stored outside that region from executing.
It runs independently from (in parallel with) the MCU core, without modifying the latter.
This thwarts all code injection attacks.
However, it is unrealistic to prohibit all modifications to program memory, since genuine software updates need to be installed during the device’s lifetime.
Otherwise, the software could be housed in ROM or the entire device would function as an ASIC (Application Specific Integrated Circuit).
Therefore,
CASU
second component is a secure remote software update scheme.

The key benefit of
CASU
is maintaining constant software integrity without repeated
\sf{\mathcal{R}A}
measurements while allowing genuine secure software updates.
Specifically, it guarantees that, between any two successive secure updates, device software is immutable.
However, the device liveness can be ascertained at any time by repeating the latest update, which essentially represents
\sf{\mathcal{R}A}
.

The intended contributions of
CASU
are:

1.

A tiny formally verified hardware monitor that guarantees benign (authorized) software immutability and prevents the execution of any unauthorized code.

2.

A scheme to enable secure software updates when authorized by a trusted 3rd party.

3.

An open-source
CASU
prototype built atop a commodity low-end MCU to demonstrate its low cost and practicality.

II
Preliminaries

II-A

Targeted Devices

This paper focuses on CPS/IoT sensors and actuators (or hybrids thereof) with low computing power.
These are some of the smallest and weakest devices based on ultra-low-power single-core MCUs with only a few KBytes of memory.
Two prominent examples are Atmel AVR ATmega
[
15
]
and TI MSP430
[
16
]
, with
8
- and
16
-bit CPUs respectively, typically running at
1
-
16
MHz clock frequencies, with
\approx 64
KBytes of addressable memory.
Figure
1
shows a typical architecture of such an MCU.
It includes a CPU core, a Direct Memory Access (DMA) controller, and an interrupt control logic connected to the memory via a bus.
DMA is a hardware controller that can read/write to memory in parallel with the core.
Main memory contains several regions: Interrupt Vector Table (IVT), program memory (PMEM), read-only memory (ROM), data memory (DMEM or RAM), and peripheral memory.
IVT stores pointers to the Interrupt Service Routines (ISRs), where the execution jumps when an interrupt occurs; it also contains the Reset Vector pointer from where the core starts to execute, after a reboot.
Application software is installed in PMEM and it uses DMEM for its stack and heap.
ROM contains the bootloader and/or any immutable software hard-coded at manufacturing time.

MCUs usually run software atop “bare metal” and execute instructions in place, i.e., directly from PMEM.
They have neither memory management units (MMUs) to support virtualization, nor memory protection units (MPUs) for isolating memory regions.
Therefore, privilege levels and isolation regimes used in higher-end devices and generic trusted execution environments (e.g., ARM TrustZone
[
17
]
or Intel SGX
[
18
]
) are not viable.

NOTE:
Our initial implementation of
CASU
uses MSP430 MCU, a common platform for low-end embedded devices.
One important factor in this choice is the public availability of an open-source MSP430 MCU design – OpenMSP430
[
19
]
.
Nonetheless,
CASU
is readily applicable to other low-end MCUs of the same class.

II-B

Remote Attestation & VRASED

\sf{\mathcal{R}A}
, mentioned above, allows a trusted entity (verifier =
\sf{\mathcal{V}rf}
) to remotely measure current memory contents (e.g., software) of an untrusted embedded device (prover =
\sf{\mathcal{P}rv}
).

\sf{\mathcal{R}A}
is usually realized as a simple challenge-response protocol:

1.

\sf{\mathcal{V}rf}
sends an
\sf{\mathcal{R}A}
request with a challenge (
\sf{\mathcal{C}hal}
) to
\sf{\mathcal{P}rv}
.

2.

\sf{\mathcal{P}rv}
receives the request and computes an authenticate integrity check over its software memory region and
\sf{\mathcal{C}hal}
. The memory region can be either pre-defined or explicitly specified in the
\sf{\mathcal{R}A}
request.

3.

\sf{\mathcal{P}rv}
returns the result to
\sf{\mathcal{V}rf}
.

4.

\sf{\mathcal{V}rf}
verifies the result and decides if
\sf{\mathcal{P}rv}
is in a valid state.

Although several
\sf{\mathcal{R}A}
techniques for low-end devices have been proposed, only very few offer any concrete (provable) security guarantees.
The latter include SIMPLE
[
8
]
,
VRASED

[
7
]
, and a variant of SANCUS
[
6
]
.
While SIMPLE, as its name suggests, is simple, it is a purely software-based
\sf{\mathcal{R}A}
technique (meaning that no hardware modifications are needed) that only protects against remote attacks and does not support DMA.
Whereas, SANCUS is a purely hardware-based
\sf{\mathcal{R}A}
technique which, though very fast, incurs a significant hardware cost over the baseline MCU.

VRASED

[
7
]
is a formally verified hybrid (hardware/software)
\sf{\mathcal{R}A}
design comprising verified hardware and software sub-modules.
The software sub-module, which is immutable (stored in ROM), implements the authenticated integrity function computed over some “Attested Region” (AR) of
\sf{\mathcal{P}rv}
memory (usually in PMEM).
Meanwhile, its hardware component assures that its software counterpart executes securely and that no function of the
\sf{\mathcal{R}A}
secret key (
\mathcal{K}
) is ever leaked.
The authenticated integrity function is realized with a formally verified HMAC implementation from the HACL* cryptographic library
[
20
]
used to compute:

H=HMAC(KDF(\mathcal{K},{\sf{\mathcal{C}hal}}),AR)

(1)

where
KDF(\mathcal{K},{\sf{\mathcal{C}hal}})
is a one-time key derived from the received
\sf{\mathcal{C}hal}
and
\mathcal{K}
using a key derivation function.

NOTE:

CASU
uses
VRASED
to verify the update request before it installs the new software on the device.
Specifically,
CASU
invokes
VRASED
to compute equation
1
on the new software and checks whether
H
matches an authentication token sent in the update request.
Consequently,
CASU
update verification inherits the security properties of
VRASED
.

II-C

TOCTOU
Attacks &
TOCTOU
-Security

All
\sf{\mathcal{R}A}
techniques share a common limitation: they yield no information about the state of
\sf{\mathcal{P}rv}
software during the time
between
two consecutive
\sf{\mathcal{R}A}
instances.
Consequently, it is impossible to detect the past presence of transient malware that: (1) infected
\sf{\mathcal{P}rv}
, (2) remained active for a while, and (3) at some later time erased itself and restored
\sf{\mathcal{P}rv}
software to its “good” state.
This holds as long as (1)-(3) occur between two successive
\sf{\mathcal{R}A}
instances.
This attack type is referred to as
Time-Of-Check Time-Of-Use
(
TOCTOU
).

One recent technique,
RATA

[
14
]
, mitigates
TOCTOU
attacks with a minimal additional hardware component that securely logs the time of the last PMEM modification to a protected memory region called Latest Modification Time (LMT) that can not be modified by any software.
LMT is then covered by the
\sf{\mathcal{R}A}
function.
Therefore, an
\sf{\mathcal{R}A}
response captures both the current software state of
\sf{\mathcal{P}rv}
and the time of change to that state.
Furthermore,
RATA
minimizes the computational cost of
\sf{\mathcal{R}A}
for
\sf{\mathcal{P}rv}
, since, instead of attesting its entire software, it suffices for
\sf{\mathcal{P}rv}
to attest just the LMT.
This way, instead of computing a MAC over the entire PMEM,
\sf{\mathcal{P}rv}
computes it over a fixed-size (32-byte)
LMT
region.

NOTE:
In this paper, unlike
RATA
,
CASU
actively
prevents
any modification to PMEM at runtime, unless it is a securely and causally authorized (by the trusted
\sf{\mathcal{V}rf}
) software update.

III-A

Basics

Similar to the typical
\sf{\mathcal{R}A}
setting,
CASU
involves a low-end MCU (
\sf{\mathcal{P}rv}
) and verifier (
\sf{\mathcal{V}rf}

The latter is a trusted higher-end device, e.g, a laptop, a smartphone, a smart home gateway, or a device manufacturer’s back-end server.

\sf{\mathcal{V}rf}

We assume a single
\sf{\mathcal{V}rf}

.
Also,
\sf{\mathcal{P}rv}
and
\sf{\mathcal{V}rf}
are assumed to share a master secret key (
\mathcal{K}
) installed on
\sf{\mathcal{P}rv}
at manufacturing time.
Our discussion focuses on the symmetric key setting, which is more practical for low-end MCUs.
Nonetheless, the use of public-key cryptography is possible with some cosmetic changes to
CASU
, provided that
\sf{\mathcal{P}rv}
has sufficient computing capabilities

III-B

Secure Update Overview

At the time of its initial deployment,
\sf{\mathcal{V}rf}
is assumed to know the software state (
\sf{\mathcal{S}_{old}}
) of
\sf{\mathcal{P}rv}
.
When
\sf{\mathcal{V}rf}
later wishes to update this software, it issues an update request, denoted by
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
, to
\sf{\mathcal{P}rv}
.
This request carries the new software
\sf{\mathcal{S}_{new}}
and a fresh authentication token
\mathsf{ATok}
, based on
\sf{\mathcal{S}_{new}}
.

When
\sf{\mathcal{P}rv}
receives an
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
,
\sf{\mathcal{S}_{old}}
invokes
CASU
, which handles the update process in two steps: (1)
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
verifies that
\mathsf{ATok}
is a fresh and timely token that corresponds to
\sf{\mathcal{S}_{new}}
, and (2) if the first step succeeds,
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
replaces
\sf{\mathcal{S}_{old}}
with
\sf{\mathcal{S}_{new}}
and generates an authenticated acknowledgment (
\mathsf{AAck}
).
At this point,
CASU
terminates and control is given to
\sf{\mathcal{S}_{new}}
which must send
\mathsf{AAck}
to
\sf{\mathcal{V}rf}
.

Upon receiving
\mathsf{AAck}
,
\sf{\mathcal{V}rf}
executes the
\mathsf{\bf Verify}^{{\sf{\mathcal{V}rf}}}
procedure to check whether the
\mathsf{AAck}
is a valid confirmation for the outstanding
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
.
If no
\mathsf{AAck}
is received, or if
\mathsf{AAck}
verification fails,
\sf{\mathcal{V}rf}
assumes a failed update.
Figure
2
illustrates the interaction between
\sf{\mathcal{V}rf}
and
\sf{\mathcal{P}rv}
.
Protocol details are described in Section

below.

III-C

Adversary Model

We consider an adversary,
\sf{\mathcal{A}dv}
, that controls the entire memory state of
\sf{\mathcal{P}rv}
, including PMEM (flash) and DMEM (RAM).
It can attempt to write, read or execute any memory location. It can also attempt to remotely launch code injection attacks to modify
\sf{\mathcal{P}rv}
software.
It may also divert the execution control-flow to ignore update requests, as well as attempt to extract any
\sf{\mathcal{P}rv}
secrets or forge update confirmations.

Furthermore,
\sf{\mathcal{A}dv}
can configure DMA controllers on
\sf{\mathcal{P}rv}
to read/write to any part of the memory while bypassing the CPU.
It can induce interrupts in an attempt to pause the update procedure, modify any part of the old or new software versions, or cause inconsistencies or race conditions.
It might also eavesdrop on, and interfere, with network traffic between
\sf{\mathcal{V}rf}
and
\sf{\mathcal{P}rv}
, in a typical Dolev-Yao manner
[
21
]
.

As common in most related work, physical attacks requiring adversarial presence are considered out of scope.
This includes both non-invasive and invasive physical attacks.
The former describes attacks whereby
\sf{\mathcal{A}dv}
physically reprograms
\sf{\mathcal{P}rv}
software using direct/wired interfaces, such as USB/UART, SPI, or I2C.
The latter refers to inducing hardware faults, modifying code in ROM, extracting secrets via physical side-channels, and tampering with hardware.
Protection against non-invasive attacks can be obtained via well-known features, such as a secure boot.
Whereas, protection against invasive attacks can be obtained via standard tamper-resistant techniques
[
22
]
.

IV
CASU
Design

One of
CASU
main features is the prevention of all unauthorized software modifications to
\sf{\mathcal{P}rv}
software.
As mentioned earlier, the former can be trivially achieved by making all
\sf{\mathcal{P}rv}
software read-only, or by making
\sf{\mathcal{P}rv}
an ASIC.
However, this precludes all benign (authorized) updates.
Therefore, it is essential to have a secure update mechanism.
The term “authorized” refers to software installed on
\sf{\mathcal{P}rv}
physically at manufacture or deployment time, as well as each subsequent version installed via update request by
\sf{\mathcal{V}rf}
.

From
\sf{\mathcal{V}rf}
perspective,
CASU
guarantees that, once installed, authorized software on
\sf{\mathcal{P}rv}
remains unchanged until the
next
\sf{\mathcal{V}rf}
-initiated successful secure update. This is achieved via three features:

1.

Authorized Software Immutability:
Except via a secure update (implemented within
CASU
trusted code),
authorized software cannot be modified.

2.

Unauthorized Software Execution Prevention:
Only the memory containing the (immutable) authorized software is executable.

3.

Secure Update:

\sf{\mathcal{V}rf}
is the only entity that can authenticate to
\sf{\mathcal{P}rv}
to install new software. After an update, the previous version of the installed software is no longer authorized.

The first two features are realized by a hardware module,
CASU
-HW
, that runs in parallel with the CPU.
It monitors a few CPU hardware signals and triggers an MCU reset if any violation is detected.
The third feature is realized by a trusted code base (TCB),
CASU
-SW
, that extends
VRASED
to authenticate incoming update requests containing new software to be installed (
\sf{\mathcal{S}_{new}}
) and an authorization token (
\mathsf{ATok}
) that must be issued by
\sf{\mathcal{V}rf}
using the key
\mathcal{K}
pre-shared with
CASU
module within
\sf{\mathcal{P}rv}
.
If
\mathsf{ATok}
matches
\sf{\mathcal{S}_{new}}
, then
CASU
-SW
installs
\sf{\mathcal{S}_{new}}
on
\sf{\mathcal{P}rv}
and produces an authenticated
\mathsf{AAck}
, attesting to
\sf{\mathcal{V}rf}
that a successful update occurred on
\sf{\mathcal{P}rv}
.

IV-B

CASU
Secure Update

Recall (from Section
III-B
) that
CASU
Secure Update implements: (
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
,
\mathsf{\bf Verify}^{{\sf{\mathcal{V}rf}}}
) on
\sf{\mathcal{V}rf}
and (
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
,
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
) on
\sf{\mathcal{P}rv}

At a high level, there are two ways of implementing it on
\sf{\mathcal{P}rv}

1.

Download
\sf{\mathcal{S}_{new}}
to DMEM (RAM), i.e., the stack or heap of the current software (
\sf{\mathcal{S}_{old}}
), and invoke
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}

If it succeeds,
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
overwrites
ER

\sf{\mathcal{S}_{new}}
and updates
EP

\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}

Secure update requires for any software
\sf{\mathcal{S}_{new}}
to be installed on
\sf{\mathcal{P}rv}
to adhere to the following format

{\sf{\mathcal{S}_{new}}}:=(L_{{\sf{\mathcal{S}_{new}}}}||V_{{\sf{\mathcal{S}_{new}}}}||N_{{\sf{\mathcal{S}_{new}}}}||BIN_{{\sf{\mathcal{S}_{new}}}}||IVT_{{\sf{\mathcal{S}_{new}}}})

L_{{\sf{\mathcal{S}_{new}}}}
,
V_{{\sf{\mathcal{S}_{new}}}}
,
N_{{\sf{\mathcal{S}_{new}}}}
is the
\sf{\mathcal{S}_{new}}

header

consisting of its size, version number, and a random nonce, respectively.

BIN_{{\sf{\mathcal{S}_{new}}}}
is the
\sf{\mathcal{S}_{new}}
binary in byte-code that mandatorily includes a
\mathsf{\bf download}
and
\mathsf{\bf acknowledge}
subroutine
that accepts future update requests and replies acknowledgment message back to
\sf{\mathcal{V}rf}
.

IVT_{{\sf{\mathcal{S}_{new}}}}
is the IVT of
\sf{\mathcal{S}_{new}}
that needs to be overwritten to
IVTR
region so that MCU knows where to jump into the new software when an interrupt is triggered.
Another requirement is that
V_{{\sf{\mathcal{S}_{new}}}}
should always be greater than the version number of the current (or old) software on
\sf{\mathcal{P}rv}
.
This avoids replay attacks that attempt to trick
\sf{\mathcal{P}rv}
into installing an old software version that contains vulnerabilities.
In case
\sf{\mathcal{V}rf}
wishes to revert to an older version (e.g., due to later-discovered bugs in
\sf{\mathcal{S}_{new}}
), it must issue a brand new update
request with the older-version software, though with a
new version
number.

\sf{\mathcal{V}rf}
, by invoking
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
, computes
\mathsf{ATok}
using equation
4
and sends
({\sf{\mathcal{S}_{new}}},{\mathsf{ATok}})
to
\sf{\mathcal{P}rv}
.

IV-B
2
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}

When
\sf{\mathcal{P}rv}
receives
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
with
\sf{\mathcal{S}_{new}}
and
\mathsf{ATok}
, the current
\mathsf{\bf download}
subroutine on
\sf{\mathcal{S}_{old}}
in
ER
accepts and downloads
\sf{\mathcal{S}_{new}}
to
an available PMEM slot. It then writes the pointers to
\sf{\mathcal{S}_{new}}
to
bEP
, buffer Executable Pointer, in PMEM, and writes
\mathsf{ATok}
to
ATR
.
This
\mathsf{\bf download}
subroutine should not be a part of
CASU
-SW
, as exposing network interfaces directly to trusted parts of the device is hazardous and may result in the exploitation of unknown vulnerabilities in it, leading to key leakage.
Hence, even though
ER
is untrusted, it should be the one receiving the request, because even if it fails to receive or chooses to not call
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
, then
\mathsf{AAck}
is not generated/sent, which is a clear indication to
\sf{\mathcal{V}rf}
that the update was unsuccessful.

To securely verify that
\sf{\mathcal{S}_{new}}
is a valid software to be installed on
\sf{\mathcal{P}rv}
,
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
first checks whether the
V_{{\sf{\mathcal{S}_{new}}}}
is greater than the one of
ER
, i.e.,
V_{ER}
.
If the
V_{{\sf{\mathcal{S}_{new}}}}
is valid, it invokes
VRASED
as a subroutine to compute
\sigma
according to equation
5
.
If
\sigma
matches with
\mathsf{ATok}
received from
\sf{\mathcal{V}rf}
, then it outputs
\top
(accept symbol) and further invokes
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
to apply the update.
Otherwise, it outputs
\perp
(reject symbol) and returns to old software at
ER
without computing any response to be sent back to
\sf{\mathcal{V}rf}
.

Note that
CASU
-SW
execution is guarded by
CASU
-HW
(which inherits
VRASED
hardware properties), i.e., any interrupts or DMA, or any attempts to access the key or any confidential data that
CASU
-SW
generates, will be considered as a
violation
and an MCU reset will be triggered immediately.
Also note that if such an abrupt reset occurs, MCU will return to the old software, and eventually
\sf{\mathcal{V}rf}
has to send a new update request.
In this new request,
\sf{\mathcal{V}rf}
can use the same version number (but with a different nonce for maintaining freshness) because the previous update was not applied, and thus, the version number of the current software is still old.

IV-B
3
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}

Once
\sf{\mathcal{S}_{new}}
is authenticated,
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
is invoked.
This is the critical step of Secure Update.
It is responsible for updating the
EP
with
bEP
,
IVTR
with
IVT_{{\sf{\mathcal{S}_{new}}}}
and computing authenticated acknowledgment
\mathsf{AAck}
that is to be replied to
\sf{\mathcal{V}rf}
.
As mentioned in Section
IV-B2
, if a reset occurs during any of these sub-steps, they have to be repeated from the beginning.
This is because, if
EP
is updated and
IVTR
is not, vulnerabilities in old ISRs pointed to by the old
IVT
can be exploited by malware.
Furthermore, if
EP
and
IVTR
are updated, yet the computation of
\mathsf{AAck}
failed,
\sf{\mathcal{V}rf}
assumes that the update failed and repeats the update request with the same version number (since
EP
is updated to the new software), and
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
will fail again.
Therefore, all three sub-steps must take place atomically.
To this end,
CASU
-SW
uses a
Status
flag
SF
in PMEM, which it sets and unsets, before and after the completion of
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
sub-steps, respectively.

To handle cases when a reset is triggered during
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
, the Reset Vector in
IVTR
is programmed to start executing from
CASU
-SW
.
This technique is analogous to having a bootloader. At boot time,
CASU
-SW
uses
Status
to determine whether a reset occurred prior to the completion of
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
.
If so,
CASU
-SW
re-invokes
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
from the beginning.

Finally,
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
computes
\mathsf{AAck}
according to equation
6
and writes it to
ATR
.
After generating
\mathsf{AAck}
,
CASU
-SW
jumps to new
ER
. Now, it is the responsibility of the
\mathsf{\bf acknowledge}
subroutine in
\sf{\mathcal{S}_{new}}
to reply to
\sf{\mathcal{V}rf}
with
\mathsf{AAck}
.

Acknowledgment Receipt:
There are two unlikely cases where
\sf{\mathcal{V}rf}
may not receive
\mathsf{AAck}
, after being generated by
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
.
Firstly,
\mathsf{AAck}
sent by
\sf{\mathcal{P}rv}
being lost or corrupted in transit.
In this case, upon a time-out,
\sf{\mathcal{V}rf}
re-sends
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
.
Since
\mathsf{\bf Install}^{{\sf{\mathcal{P}rv}}}
stores
\mathsf{AAck}
in a dedicated region of DMEM (
ATR
),
\mathsf{\bf download}
in
ER
checks whether the update request has the same version number as itself and directly replies
\mathsf{AAck}
to
\sf{\mathcal{V}rf}
, instead of invoking
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
again.
Secondly, a reset occurring after a successful update and before
\mathsf{AAck}
is sent to
\sf{\mathcal{V}rf}
.
In that case,
\mathsf{AAck}
is lost and, upon a timeout,
\sf{\mathcal{V}rf}
needs to send a new
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
with a new version number.
The drawback of this approach is that the same update is re-applied, wasting MCU clock cycles.
However, the latter case is very rare, and even if it occurs,
CASU
-SW
only takes less than a second to re-install
\sf{\mathcal{S}_{new}}
(see Section
VI-B
).

\sf{\mathcal{V}rf}
can distinguish between these cases by first re-sending the same
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
.
If there is still no response, then
\mathsf{AAck}
is most likely lost due to a reset and
\sf{\mathcal{V}rf}
must send a new
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
with a new version number.

There are other ways to mitigate the aforementioned
\mathsf{AAck}
issues.
Rather than storing
\mathsf{AAck}
in DMEM, it could be placed into a reserved memory in PMEM to ensure its persistence even if a reset occurs.
Now,
\mathsf{\bf download}
can always reply with
\mathsf{AAck}
whenever it sees a duplicate request, thus eliminating the cost of re-update.
However, this approach requires an additional write to flash, which may be undesirable.
Alternatively, we can use a
\sf{\mathcal{V}rf}
-supplied timestamp instead of a nonce in
\sf{\mathcal{S}_{new}}
and modify
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
to accept duplicate requests with a more recent timestamp.
This approach does not require any reserved memory (not even in DMEM).
However, it incurs runtime overhead every time
\sf{\mathcal{V}rf}
issues a duplicate request.
Each aforementioned alternative has its own benefits and drawbacks.
We leave it up to
\sf{\mathcal{V}rf}
to decide which is most suitable.

Note that none of the above can result in a DoS attack due to multiple requests,
because all
\mathsf{\bf Update}^{{\sf{\mathcal{V}rf}}}
-s originate from a legit
\sf{\mathcal{V}rf}
and are verified by
\mathsf{\bf Auth}^{{\sf{\mathcal{P}rv}}}
.
Moreover,
\mathsf{\bf download}
can check the
\sf{\mathcal{S}_{new}}
header to check if the request was already seen,
discard the rest of the packets, and simply reply stored
\mathsf{AAck}
to
\sf{\mathcal{V}rf}
.

If either

There are two states in the FSM:

is
1

0

(1)
modifications to
ER
,
EP
,
SF
, or
IVTR
,
and
(2)
execution attempts outside
ER
and
TCR
. In either case, the FSM transitions to
RESET
.

We implement the FSM using Verilog HDL and automatically translate it into Symbolic Model Verifier (SMV) language using

[

]
tool. Finally, we use the NuSMV Model Checker
[
24

V-B

CASU
-SW Secure Update Routine

CASU
-SW
implements subroutines
casu_entry
,
casu_authenticate
,
casu_install
, and
casu_exit
.

casu_entry
is the only legal entry point to
CASU
-SW
; it is invoked at boot and during an update.
Boot invocation is obtained by setting the IVT reset vector to
casu_entry
.

casu_entry
takes a boolean argument to test whether it was invoked at boot or by
ER
for an update.
In the former case, it checks
Status
to determine whether to invoke
casu_install
in order to resume the
unfinished update from the last reset. Otherwise, it calls
casu_exit
, which clears the MCU registers and
jumps to the binary in
ER
.
In the latter case, it invokes
casu_authenticate
.

casu_authenticate
checks for the validity of the version number of
\sf{\mathcal{S}_{new}}
at
bEP
and invokes
VRASED
software to compute HMAC. If the measurement matches
\mathsf{ATok}
,
casu_install
is invoked;
otherwise, it jumps to
casu_exit
. Finally,
casu_install
updates
EP
, copies the new IVT to
IVTR
, and
computes and stores
\mathsf{AAck}
at
ATR
. It also sets/unsets
Status
to indicate the status of installation to

casu_entry
subroutine, in case of a reset.

CASU
-SW
is implemented in C with a tiny TCB of
\approx 140
lines of code.
It uses
VRASED
software, which is implemented using a formally verified cryptographic library, HACL*
[
20
]
.

In total, it consumes 41 bytes of additional storage.

VIII
Conclusions

In this paper, we designed
CASU
, a prevention-based root-of-trust architecture for low-end MCUs.

CASU
differs from prior work by disallowing illegal software modifications rather than detecting them.

CASU
also prevents execution of any unauthorized software and supports secure software updates.

CASU
is prototyped on OpenMSP430 and its hardware component is
formally verified.
Experiments show that
CASU
incurs quite low overhead and is thus suitable for resource-constrained low-end IoT devices.
Its entire implementation is publicly available at
[
25
]
.
