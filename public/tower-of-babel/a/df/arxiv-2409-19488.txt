A House United Within Itself: SLO-Awareness for On-Premises Containerized ML Inference Clusters via Faro
Beomyeol Jeon, Chen Wang, Diana Arroyo, Alaa Youssef, Indranil Gupta

Abstract
. This paper tackles the challenge of running multiple ML inference jobs (models) under time-varying workloads, on a constrained on-premises production cluster. Our system Faro takes in latency Service Level Objectives (SLOs) for each job, auto-distills them into utility functions, “sloppifies” these utility functions to make them amenable to mathematical optimization, automatically predicts workload via probabilistic prediction, and dynamically makes implicit cross-job resource allocations, in order to satisfy cluster-wide objectives, e.g., total utility, fairness, and other hybrid variants. A major challenge Faro tackles is that using precise utilities and high-fidelity predictors, can be too slow (and in a sense too precise!) for the fast adaptation we require. Faro’s solution is to “sloppify” (relax) its multiple design components to achieve fast adaptation without overly degrading solution quality. Faro is implemented in a stack consisting of Ray Serve running atop a Kubernetes cluster. Trace-driven cluster deployments show that Faro achieves 2.3 × 2.3\times – 23 × 23\times lower SLO violations compared to state-of-the-art systems.

Challenges in Faro:

Faro’s goal is autoscaling in a fixed-size cluster where a fixed set of jobs (pre-trained models) is running, and each job is receiving a stream of queries. Query rates vary significantly over time. Each job has an SLO that is a latency target (tail latency or average latency). Further, the cluster administrator may wish to specify a cluster-level objective that targets either maximizing all jobs’ SLOs, a heavy hitter job’s SLO, or SLO fairness across jobs, etc.

Faro has to tackle the following challenges: (i) specifying the
cluster-level objective
to maximize (which we call the
utility function
), (ii)
right-sized
workload prediction for each job as a function of its current query rate,
and (iii) making
anticipatory
autoscaling decisions that are both
non-myopic and fast
.
Faro tackles the first challenge above by distilling each job’s SLO target and current SLO performance into automatically calculating a per-job
max utility
value and
current utility value
—concepts of utility have been used elsewhere
(
Kalim et al., 2018
;
Zhang et al., 2017
;
Wang et al., 2013
;
Elhabbash et al., 2019
;
Wilkes, 2009
;
AuYoung et al., 2006
;
Bhardwaj et al., 2023
;
Ferguson et al., 2012
)
.
Using these, Faro specifies a
cluster-wide utility
function that the autoscaler aims to maximize. Faro provides a family of utility functions for the cluster administrator to choose from—for either maximizing cluster utility, or fairness across jobs, or minimizing penalty from dropped requests, or combinations thereof.
This cluster utility formulation can then be input to optimization solvers.

For the second challenge of workload prediction, existing techniques often focus on predicting future workload in a rather
precise
way—this is unable to capture fluctuations in workloads, and thus often underestimates resource needs to meet the SLO. Faro instead uses
probabilistic prediction
.
This “sloppy” prediction provides a “window” (range) of resource needs.
This window (distribution) is fed as input to our autoscaler, which can make anticipatory up/down-scaling decisions.
Our choice of sloppy prediction is also motivated by other works that have shown that so-called “accurate” predictions of systems performance are not so accurate after all
(
Fu et al., 2021
)
.

For the third challenge of making autoscaling decisions in fast and non-myopic ways—first, we observe that solving a cluster-wide utility optimization function can be time-consuming (and thus at odds with the need to adapt quickly). For instance, a statistical package like
scipy.optimize

(
Virtanen et al., 2020
)
takes 15-20 seconds to solve an objective function (and still outputs a solution quite far from optimal!).
Adaptation needs to be faster, within seconds because of stringent latency SLOs.
While other areas have used sloppification
(
Kumar et al., 2016
;
Freedman et al., 2004
)
, Faro is the first to apply it to ML inference, by creating an
approximate
but quickly-solvable objective function.

OS-level approaches based on jobs’ priorities and preempting resources, are not viable solutions. Priority preemption is a match with only some of the above listed cluster administrator goals, e.g., it can satisfy heavy hitters’ SLOs but neither SLO fairness nor maximizing all jobs’ SLOs.

Contributions:

Faro’s contributions are that it:
(1) Distills user-specified SLOs into utility functions;
(2) Forecasts workload fluctuation by probabilistic prediction;
(3) Makes fast and close-to-optimal resource allocation decisions for ML jobs by carefully relaxing cluster utility functions;
(4) Is integrated with Ray Serve framework atop Kubernetes;
(5) Is evaluated both on a real deployment (cluster) and a deployment-matched simulator, using Twitter & Azure production traces;
(6) Reduces both SLO violations by
2.3\times
–
23\times

and lost cluster utility by
1.7\times
–
13.1\times
,
vs. state-of-the-art.

While Faro adapts techniques from elsewhere (e.g., utility, latency estimation, time-series prediction, etc.) our two major contributions are (1) combining these techniques (Sec.

and
4

3.1.
Per-job Utility Functions

The developer of each job merely needs to specify a service level objective (SLO) for the job, containing two pieces: (i) a
latency target
, defined as the time between a query being received by the system until an inference output is generated; and (ii) a
percentile

k
, e.g., 99
th
percentile, 90
th
percentile, median (50
th
percentile), etc. Denote the SLO of the
i
th
job as
s^{i}
. If the
k
th
percentile latency currently experienced by the job is
l^{i}
(Table
4
), then Faro automatically distills the job’s SLO into a
utility
function:

U_{original}(l^{i},s^{i})=\begin{cases}1&l^{i}\leq s^{i}\\
0&l^{i}>s^{i}\end{cases}

This is a step function. When the latency target is met, the job’s utility
U_{original}
is 1, otherwise it is 0.

While utility functions have been used to capture SLOs
(
Kalim et al., 2018
;
Bhardwaj et al., 2023
;
Wilkes, 2009
)
,
a major drawback of
U_{original}
is that
it has a
plateau
—
plateaus
(
Russell and Norvig, 2009
)
are flat regions in the search space where nearby local search points return the same value, which makes it hard for optimization solvers to find global extrema.
Optimization formulations involving plateau functions require computationally-heavy optimization operations (e.g., evolutionary algorithm
(
Storn and Price, 1997
)
) and yet produce suboptimal results
(
Friedrich et al., 2010
;
Pascanu et al., 2014
;
Dauphin et al., 2014
)
.
This makes
U_{original}
impractical to use.

Hence we also write
relaxed
variants of the original utility that is non-plateau (except the global maxima), as follows:

(1)

U(l^{i},s^{i})=\min((\frac{s^{i}}{l^{i}})^{\alpha},1)\vskip-1.42271pt

Faro automatically derives this relaxed utility equation from the SLO (latency, percentile).
Figure
4(a)
shows that as
\alpha
increases (to
\infty
), this relaxed utility
U
approaches
original utility
U_{original}
.
Overall, utility values are good proxies for SLOs.
Figure
4(b)
plots, for a trace-driven job,
SLO satisfaction rates
defined as
fractions of requests satisfied within latency SLO
. The plot confirms that utility values are
lower bounds
on the SLO satisfaction rates. Faro can thus use these pessimistic (utility) estimates for resource allocation decisions.

Faro does not
require
jobs to be amenable to a weakened form of SLO (utility)—instead, utility is Faro’s way of solving the SLO problem.
We use both SLO satisfaction rates and utilities as our main experimental metrics.

3.2.
Cluster Objective Functions

In a constrained cluster running multiple jobs (each job is a model receiving inference queries), cluster administrators may have different goals of cluster-wide objectives, including (but not limited to): SLO fairness, total SLO satisfaction, penalizing jobs dropping requests, etc.
Faro provides a family of
cluster objective functions
to choose from.

While Faro can handle arbitrary cluster objectives, for concreteness we present below five concrete cluster objectives for utility maximization, fairness, and drop request penalty.

1. Faro-Sum:
Maximize cluster-wide satisfaction of SLOs, i.e., the sum of job utilities, Formally, the goal is to:

\maximize{}\sum_{i}\pi^{i}U^{i}

Coefficients
\pi^{i}
s can reflect job
i
’s priority (1 by default).

2. Faro-Fair:
Maximize fairness, i.e., minimize the difference between maximum and minimum utility across all jobs:

\minimize{(\max_{i}U^{i}-\min_{i}U^{i})}

3. Faro-FairSum:
Hybrid of Faro-Sum and Faro-Fair:

\displaystyle\maximize{\left[\sum_{i}\pi^{i}U^{i}-\gamma\ (\max_{i}U^{i}-\min_{i}U^{i})\right]}

Parameter
\gamma
determines the relative weight of fairness. We recommend setting it to job count, normalizing both terms.

4. Faro-PenaltySum:

When a cluster with limited resources is overloaded under incoming requests, some requests may need to be explicitly dropped in order to:
(i) satisfy the SLO for remaining queries, and (ii) avoid OOM (Out of Memory) errors. Dropping queries should naturally incur a penalty. To calculate this penalty Faro uses a
penalty multiplier
, structured similar to credit functions commonly used by cloud providers today for dropped requests
(
Services, 2024
;
IBM, 2024b
)
—Table
5
shows the penalty function,
penalty(availability=1-d^{i}(\text{drop rate}))
, we use, borrowed from AWS.
Faro uses this to calculate the
Effective Utility (EU)
of the job:

(2)

EU^{i}=\phi(d^{i})\times U^{i}(\text{non-dropped requests})

where
\phi(d^{i})=1-penalty(1-d^{i})
.
This allows us to define Faro-PenaltySum’s cluster objective:

\maximize{\sum_{i}\pi^{i}EU^{i}}

5. Faro-PenaltyFairSum:
This combines Faro-FairSum and Eq.
2
to capture both fairness and penalty:

\maximize{\left[\sum_{i}\pi^{i}EU^{i}-\gamma\ (\max_{i}EU^{i}-\min_{i}EU^{i})\right]}

3.3.
Latency Estimation

Our relaxed cluster optimization (discussed soon) uses Faro’s two techniques for latency estimation:

I. Upper-Bound Estimator:
This is a pessimistic estimate.
If
\kappa
requests arrive simultaneously, with
N
replicas and per-request processing time of
c
, the completion time is
\frac{c\times\kappa}{N}
.

II. Queuing Theory:

It is known that ML inference workloads show Poisson arrival patterns
(
Gupta et al., 2020
;
Reddi et al., 2020
)
and request processing times show low variation
(
Gujarati et al., 2017
)
. Thus the pessimistic approach may be too conservative. Our second approach is to leverage the
M/D/c queuing model

(
Franx, 2001
;
Shortle et al., 2018
)
, which assumes Poisson arrivals and constant processing time.
The estimate of the
k
th
percentile latency is:

\begin{cases}latency_{M/D/c}(k,p,\lambda,N)&\rho=\frac{p\times\lambda}{N}<1\\
\infty&otherwise\end{cases}

In practice, we observed that the M/D/c model estimates fewer replicas than the upper-bound model.
Suppose
p
= 150 ms,
\lambda
= 40 req / s, and
s
= 600 ms (See Table
4
for notations).
The upper-bound model estimates 10 replicas, but the M/D/c model estimates 8 replicas with 99.99
th
percentile latency.
This can avoid overprovisioning of resources to meet latency SLOs, an asset when cluster resources are limited.

To expedite the M/D/c queue latency estimation, we adopt common engineering approximations
(
Tijms, 2006
)
by treating M/D/c queue waiting time
\approx

\frac{1}{2}
M/M/c queue
(
Shortle et al., 2018
)
waiting time.

Given the latency estimation from Sec.
3.3

3.2
into precise forms. Then we discuss why and how to relax them.

Precise Optimization:
For each of the five cluster objectives listed in Sec.
3.2
—Faro-Sum, Faro-Fair, Faro-FairSum, Faro-PenaltySum, Faro-PenaltyFairSum—we have precise optimization formulations.
For concreteness and due to brevity reasons, we present one of the five. For Faro-PenaltySum, Faro calculates utility
using the step per-job utility function (
U_{original}
from Sec.
3.1
) and via 99
th
percentile M/D/c queue model from Sec.
3.3
. This gives the following precise cluster optimization problem specification:

(3)

\displaystyle\argmax_{x^{i},d^{i}}

\displaystyle{\sum_{i}\pi^{i}EU_{original}^{i}(\lambda^{i},x^{i},s^{i},p^{i})}

\displaystyle=

\displaystyle\sum_{i}\pi^{i}{\phi(d^{i})}U_{original}^{i}(\lambda^{i}(1-d^{i}),x^{i},s^{i},p^{i})

(min. # replicas, drop rate)

s.t.

\displaystyle x_{i}\geq 1,0\leq d_{i}\leq 1

(vCPU limit)

\displaystyle\sum_{i}Res_{cpu}(x_{i})\leq ResMax_{cpu}

(memory limit)

\displaystyle\sum_{i}Res_{mem}(x_{i})\leq ResMax_{mem}

Faro-Fair, Faro-Sum, Faro-FairSum, and Faro-PenaltyFairSum,
each has similar precise formulations.

Difficulties of Solving the Precise Optimization:
Solving this formulation precisely
and
quickly is hard.

Relaxing the Optimization Function:
To derive fast and good quality solutions,
we relax precise optimization (e.g., Eq.
3
) by converting the plateau functions (for per-job utility function, M/D/c queue latency estimation, and penalty multiplier) into non-plateau functions. Figure
5
shows that our relaxed variant is fast and produces good-quality solutions.

Figure
6
depicts a concrete example of the two stages of Faro’s relaxation of utility for a given job.
The left plot, derived directly from the SLO, is relaxed in the middle plot using the inverse utility function (Sec.
3.1
).
However, this still has a plateau—if a job receives requests more than its processing capability (
\rho=\frac{p\times\lambda}{N}>1
), its queue size keeps growing (unstable queue). In such a case, we estimate latency as
\infty
(Sec.
3.3
) but this does not differentiate
how fast
the queue size grows. This creates a plateau in the middle plot.

Hence we next relax the M/D/c queue latency estimation to produce the right plot in Figure
6
.
Concretely, Faro estimates latency with an unstable queue as penalized latency under a stable queue.
We thus define the
penalty proportional to the queue size growth rate (
\propto\lambda
), as the following:

\begin{cases}latency_{M/D/c}(k,p,\lambda,N)&\rho\leq\rho_{max}\\
\frac{\lambda}{\lambda^{\rho_{max}}}\times latency_{M/D/c}(k,p,\lambda^{\rho_{max}},N)&otherwise\end{cases}

Here,
\rho_{max}
(
=p\lambda^{\rho_{max}}/N<1
) is a knob determining how close original and relaxed estimations are. Values of
\rho_{max}
near 1.0
accurately model actual queue behavior, but may create a plateau.
Faro sets
\rho_{max}=0.95
so as to remove the plateau but still stay close to estimated latency.

Finally, we note that relaxing the penalty multiplier (Table
5
in Sec.
3.2
) into a piece-wise linear function also creates a plateau-free optimization function.

Putting together all these relaxations, all three optimizers find (nearly-)optimal solutions (orange dots of Figure
5
).
The local optimizers (COBYLA and SLSQP) solve the problem within a sub-second, but the evolutionary algorithm (DE) takes longer (20 seconds) as it explores a larger state space after the relaxation.
Hence Faro uses COBYLA by default.

Hierarchical Optimization:

With more jobs, the optimization variables rise too. To scale the solving, we use a

hierarchical optimization
. Faro creates
G
groups, assigning each job to a random group. Group
g_{i}
’s aggregated job arrival rate and processing time are then:
\lambda_{g_{i}}=\sum_{j\in g_{i}}\lambda^{j}
,
p_{g_{i}}=\sum_{i\in{g_{i}}}p^{j}/|g_{i}|
.
We plug this into Eq.
3
as
Res_{cpu}(g_{j})=\sum_{i\in g_{j}}Res_{cpu}(x_{i})
,
Res_{mem}(g_{j})=\sum_{i\in g_{j}}Res_{mem}(x_{i})
,
\sum_{i}Res_{cpu}(g_{i})\leq ResMax_{cpu}
and
\sum_{i}Res_{mem}(g_{i})\leq ResMax_{mem}

(Table
4
has notations).

Figure
7(a)
shows just a few groups speed up the base Faro solution (
G=1
) by 64
\times
, improving utility by
2\%
at
>
50 jobs. At
<
50 jobs, aggregated
\lambda_{g_{i}}
and
p_{g_{i}}
degrades utility. For simplicity of design we use
G=10
as default in the rest of the paper.

3.5.
Probabilistic Time-series Prediction

We describe how Faro predicts a job’s future workload.

3.5.1.
Time Series Prediction Model: N-Hits

Prior works for proactive autoscaling in ML inference employed prediction algorithms like linear regression
(
Gujarati et al., 2017
)
, Prophet
(
Bhattacharjee et al., 2019
)
, neural network based prediction (e.g., LSTM
(
Zhang et al., 2019
)
, DeepAR
(
Gunasekaran et al., 2022
)
).
We implemented LSTM and DeepAR, but
they had lower prediction quality (RMSE: 123.95 and 122.38) vs. Faro’s approach (RMSE: 116.24) (the same setup as Sec.
6
). They also incurred 2–3
\times
higher inference latency over Faro’s predictor.

At its base Faro uses a N-HiTS
(
Challu et al., 2023
)
-based prediction model to predict future arrival rates for proactive autoscaling. N-HiTS is a state-of-the-art neural network based time series prediction model that incorporates hierarchical interpolation and multi-rate data sampling to reduce computational complexity and to address prediction volatility.

3.5.2.
Probabilistic Prediction

The base time-series prediction approach is

too precise
, and thus unable to capture workload fluctuation.
For instance, it is common to train a time-series prediction model using mean absolute error (MAE) or root-mean-square error (RMSE) as a loss function
(
Gunasekaran et al., 2022
;
Challu et al., 2023
)
.
However, the trained model with MAE or RMSE does not capture the fluctuation in a dynamic input workload.

Figure
8(a)
shows a portion of a 1-day arrival trace from Azure Function trace
(
Shahrad et al., 2020
)
.
We trained the N-HiTS model to predict arrival rates over next (say) 40 time units, by using arrival rates over the past (say) 60 time units (RMSE loss function).
Figure
8(b)
shows prediction results.
The blue line shows the damped (weighted) average, however it is unable to capture any of the natural fluctuation in the workload.

Capturing fluctuation is critical for SLO satisfaction. To minimize SLO violations, the autoscaling decision should ideally handle the
maximum expected
arrival rate over the prediction window.
As Figure
8(b)
shows,
the ground-truth maximum arrival rate over the prediction window is over 2
\times
higher than predicted arrival rate.

Prior works address this underestimation problem by threshold based overprovisioning
(
Gujarati et al., 2017
)
or reactive upscaling
(
Gunasekaran et al., 2022
;
Zhang et al., 2019
)
when SLO violations are observed.
The former approach is susceptible to misconfiguration.
In the latter, SLO violations still occur due to non-negligible upscaling overhead.

Faro addresses this challenge by leveraging probabilistic time-series prediction
(
Gneiting and Katzfuss, 2014
)
.
Instead of predicting
single-valued future arrival rates
, a probabilistic prediction technique predicts the
probability distributions
of future arrival rates, i.e., parameters of the distribution for future arrivals.
Concretely Faro incorporates the Gaussian distribution model into N-HiTS. Figure
8(c)
shows Faro’s prediction results—we generate 100 prediction samples and plot the range between the min-max samples, 20
th
-80
th
percentiles, and 30
th
-70
th
percentiles.
The generated sample ranges cover the ground truth fluctuation, and Faro captures the workload fluctuation.

4.
Faro Autoscaler Design

Using the building blocks just described, we now detail how Faro’s multi-tenant autoscaler makes decisions in a centralized manner.
These decisions
implicitly
give more (or less) resources to individual jobs, and thus implicitly move resources (vCPUs and memory) from one job to another (since the cluster is capped in size).
Faro periodically collects metrics and periodically invokes the Faro autoscaler (we discuss frequencies later).
Whenever Faro’s autoscaler is invoked, it executes in three stages: (1)
Per-job Autoscaling Formulation
, (2)

Multi-tenant Autoscaling
, and (3)
Multi-Job Shrinking
.

4.1.
Stage 1: Per-job Autoscaling Formulation

We specify the per-job optimization problem which relates its replicas to SLO satisfaction.
Concretely, Faro fetches metrics for each job: average per-request replica processing time (
p
) and past arrival rates. Over the next
w
time units, future loads
(
\Lambda_{pred}
=
\{\lambda^{1}_{pred},\dots,\lambda^{w}_{pred}\}
) are predicted via the probabilistic time-series prediction of Sec.
3.5
.
For given future loads, processing time, and SLO target (
s
),
Faro derives a per-job objective function with respect to the number of replicas (
x
). It uses the latency estimation (
L
) of Sec.
3.3
and the per-job utility function (
U
) of Sec.
3.1
. This per-job objective is:

\maximize_{x}\frac{1}{w}\sum_{k}^{w}U(L(\lambda_{pred}^{k},p,x),s).

A cold-start penalty for new replica creation is typically 10s of seconds to a few minutes (up to 70 s in our runs).
Faro incorporates this cold-start penalty into the optimization by planning for replica startup after the cold start.

4.2.
Stage 2: Multi-tenant Autoscaling

Merely solving the per-job SLO optimization problem from Sec.
4.1
may exceed the total cluster resources.
Hence, Faro formulates the multi-tenant autoscaling problem using the approach from Sec.
3.4
.
Faro specifies this by using the cluster objective function in Sec.
3.2
which contains the per-job autoscaling functions from Sec.
4.1
.

Faro solves the multi-tenant autoscaling objective function by using the nonlinear programming solver called COBYLA
(
Powell, 1994
)
, using the total cluster resources
(vCPU and memory)
as a constraint (used resources
\leq
total cluster resources).
This solving is usually fast, e.g., less than 1 second.
The solution is post-processed by converting it into integers for replica counts, staying within the cluster size.

4.3.
Stage 3: Shrinking

While Faro’s multi-tenant autoscaler scales jobs to optimize the cluster objective within the total cluster resources,
more resources can be allocated to a job than it needs to meet its SLO for future load.
This especially happens when resources are sufficient for all jobs to satisfy their SLOs.

We subsequently shrink job replica counts
(thus improving resource utilization)
by
post-processing
the previous stage output.
Faro iteratively shrinks (reduces) a replica count for (only) a job with (predicted) utility 1, until the cluster utility changes—thereupon, iterative shrinking is stopped for that job, and the next job is tried.
(Note this criterion uses cluster utility instead of “any job’s utility” since Faro’s goal is achieving cluster objective as specified by the cluster administrator.)
The result of Stage 3 is
right-sized
allocation of resources for the collection of jobs, just sufficient to meet their respective SLOs.
Naturally, Stage 3 is inapplicable if no jobs are meeting their SLOs (i.e., all jobs have utility
<1
).
Stage 3’s decisions are executed automatically by Faro.

4.4.
Selecting an Autoscaling Frequency: Faro’s Hybrid Autoscaler

Too frequent autoscaling makes some resources unusable during the autoscaling operations (e.g., reallocating resources from one job to another job).
If the autoscaling interval is too large, multiple concerns arise: (i) prediction quality degradation, (ii) suboptimal autoscaling decisions due to dynamic workload changes, and (iii) failure to handle unpredictable workload changes (e.g., spike).

To address this dilemma, Faro contains a
hybrid autoscaler
that uses an intelligent combination of a
long-term predictive
autoscaler and a
short-term reactive
autoscaler.
Faro performs long-term predictive autoscaling (every 5 min) by using the multi-tenant autoscaler.
Faro triggers its short-term reactive autoscaling more frequently (10 s)
in order to react to unpredictable workload changes.
In this short-term autoscaler, Faro scales up jobs in an
additive
manner and only if SLO violations are observed.
Since the long-term autoscaler determines the current number of replicas, Faro does not use its short-term autoscaler for downscale operations.

In Ray terminology, a
Ray cluster
refers to a subcluster (a subset of nodes in the cluster).
Atop Kubernetes, a subcluster consists of its controller server (head pod) and multiple worker servers (worker pods).
Ray Serve deploys ML inference jobs on a subcluster (Ray cluster) by running Ray Serve Replicas that perform inference tasks on worker pods, and running a Router that accepts and routes incoming requests to Ray Serve Replicas, on the head pod.

We allocate a subcluster to a single ML inference job. This isolates each job’s congestion at its Ray Router, and prevents resource fragmentation as we configure (subcluster-specific) worker pod resource allocation size appropriate to a single Ray Serve Replica.
We modify Ray Router to:
(i) collect metrics (arrival rates, average per-request replica processing time, and average per-request latency), all continually;
(ii) export these metrics on API request;
(iii) explicitly drop requests as instructed by Faro autoscaler; and
(iv) tail drop
(
Comer, 2000
)
requests when the queue length at a Router (for a job) reaches a specified threshold (50; values in range
[20,100]
behaved similarly), sending the client an HTTP 503 response.

Faro autoscaler (Sec.
4
) runs as a separate Kubernetes pod and periodically scales all Ray Serve jobs.
Our scaling period of 5 mins is chosen to be larger than autoscaling (cold-start) overhead (1 min) but frequent enough to capture workload changes.
The prediction window is 7 mins, so it overlaps with the next autoscaling cycle and covers cold start overhead.
Faro changes the number of Ray Serve replicas by using Ray Serve Python API, and drops requests by sending control requests to Routers based on autoscaling decisions.

We implement Faro’s autoscaler in Python and its time-series predictor (Sec.
3.5
) using Darts
(
Herzen et al., 2022
)
v0.22. We train it with a 15-min arrival rate history to predict the next 7-min window.
For optimization solver (Sec.
3.4
),
Faro uses COBYLA
(
Powell, 1994
)
in
scipy.optimize

(
Virtanen et al., 2020
)
with the initial variable change of 2. We accelerate the objective function calculation via Numba
(
Lam et al., 2015
)
.

This shows that merely generalizing single-job autoscaling policies to a multi-tenant cluster is insufficient and impractical. Faro’s techniques are needed.

Counterintuitively FairShare is unfair. Since the required resources to satisfy an SLO vary over time, static fair allocation is ineffective.

AIAD is better at fairness as its cautious autoscaling does not over-allocate, and thus it retains resources for needy jobs.

Although Mark/Cocktail/Barista has higher cluster utility than AIAD and Oneshot, it is unfair especially in a slightly oversubscribed cluster (Figure

\times

some jobs to stay at a low SLO satisfaction over the entire run.

Faro’s fairness variants have “tighter” boxplots, indicating smaller utility differences among jobs, and thus better fairness. Not surprisingly, Faro variants that explicitly include fairness (e.g., all Faro-*Fair* variants) exhibit better fairness than other variants (Faro-Sum and Faro-PenaltySum).

7.
Discussion and Limitations

Beyond On-Premises Clusters:
Limited clusters also arise beyond on-premises clusters. A common example is deployment on a public cloud wherein developers prefer a VM instance type but have a budget limit ($ per hour) they can spend. Another example is an edge deployment that has user
quotas
. Faro is also applicable in these scenarios.

CPU/GPU mixes and Heterogeneity:
Due to low prices and high availability of CPU resources, enterprises still prefer to run inference workloads on homogeneous CPUs. Admitting heterogeneous mixes of accelerators (GPUs) with CPUs is an open problem, with Faro representing a first step.

Orthogonal Techniques (Batching, Memory):
Faro is orthogonal to, and thus combinable with: Ray’s and Kubernetes’ fault-tolerance mechanisms, intelligent request batching
(
Ali et al., 2020
;
Crankshaw et al., 2017
)
, hyperparameter tuning
(
Akiba et al., 2019
;
Liaw et al., 2018
)
, and different types of ML parallelism (pipeline, model) for large models
(
Rasley et al., 2020
)
.

Heterogeneity:
Homogeneous clusters are common due to ease of manageability, and Faro focuses on them; heterogeneity is an open challenge. Faro is applicable to ML pipelines that make chained calls to multiple ML jobs, if the application SLO can be split into sub-SLOs for each called model, e.g., proportionally: for a chain with two model calls, if one model takes 2
\times
other, if the SLO is split as 66%-33%.

Decentralized Approaches:
Decentralizing Faro is not essential but could be an interesting future direction
(
Ousterhout et al., 2013
;
Wang et al., 2021
)
.

Admission Control:
While ML job arrivals/departures are rare, it remains an open question whether admission control decisions can be designed to guarantee SLO satisfaction, perhaps with some workload assumptions.

Beyond ML Inference:
While we have focused on ML inference clusters, it is possible that Faro’s techniques could be extended to other domains, e.g., microservices and batch processing jobs. Our use of ML inference-specific techniques, e.g., M/D/c queueing (Sec.
3.3
), will need to be adapted, e.g., via M/M/c or G/G/c queuing, and utility functions for batch processing, e.g., ML training workloads
(
Bhardwaj et al., 2023
;
Ferguson et al., 2012
;
Wilkes, 2009
;
Zheng et al., 2023
)
.

8.
Related Work

ML inference autoscaling either makes per-job independent scaling decisions, or assumes infinite (cloud) resources.
Swayam
(
Gujarati et al., 2017
)
proactively autoscales to minimize resource utilization under SLOs, relying on latency estimation.
However, Swayam cannot work with constrained clusters or multi-tenant setups. Swayam’s customized decentralized architecture prevented us from reusing it for the Ray Serve | Kubernetes stack.
Mark
(
Zhang et al., 2019
)
and Barista
(
Bhattacharjee et al., 2019
)
use SLO-aware autoscaling heuristics to minimize cost on various cloud resources, e.g., VM instance types, serverless, etc.
Greedy heuristics iteratively pick a cloud resource type with the lowest cost-per-request, until job SLOs are met.
Cost-per-request is based on max throughputs of each instance type. Faro solves a different problem in constrained clusters.
Because of their orthogonality, an open direction is to combine Faro with Mark/Barista’s heterogeneity awareness to realize a constrained cluster version of Faro in public clouds.
Cocktail
(
Gunasekaran et al., 2022
)
is an ensemble model-serving system to meet request accuracy and latency requirements. Cocktail
only
scales up jobs (proactively).
Yet an upscaled job never relinquishes its resources, even if the workload drops, making it non-adaptable under changing workloads.
INFaaS
(
Romero et al., 2021
)
auto-selects cost-efficient configurations (e.g., ML model, hardware) based on user needs. It reactively autoscales
additively
by monitoring job throughput, hence our AIAD baseline captures it.

Data center scheduling work
(
Boutin et al., 2014
;
Grandl et al., 2014
;
Delimitrou and Kozyrakis, 2014
;
Delimitrou and Kozyrakis, 2013
)
focuses on placement but does not deal with autoscaling to meet (human-facing) latency SLOs.
Some recent works
(
Ferguson et al., 2012
;
Jyothi et al., 2016
;
Bhardwaj et al., 2023
;
Rzadca et al., 2020
)
tackle SLO-aware autoscaling in fixed clusters
(
Ferguson et al., 2012
;
Jyothi et al., 2016
;
Bhardwaj et al., 2023
;
Rzadca et al., 2020
)
.
Of these, Autopilot and Jockey
(
Ferguson et al., 2012
)
only autoscale individual jobs, like Mark
(
Zhang et al., 2019
)
and K8s HPA
(
Team, 2024a
)
, which we have compared against
(
Zhang et al., 2019
;
Bhattacharjee et al., 2019
;
Gunasekaran et al., 2022
)
.
Morpheus
(
Jyothi et al., 2016
)
supports only periodic data-analytic jobs. Cilantro
(
Bhardwaj et al., 2023
)
maximizes global objectives but converges too slowly (Figure
2
).
ML training scheduling work
(
Narayanan et al., 2020
;
Xiao et al., 2018
;
Chaudhary et al., 2020a
;
Qiao et al., 2021
;
Zheng et al., 2023
;
Mahajan et al., 2020
;
Chaudhary et al., 2020b
)
support neither horizontal autoscaling
(
Narayanan et al., 2020
;
Xiao et al., 2018
;
Chaudhary et al., 2020a
;
Mahajan et al., 2020
)
, nor stringent latency SLOs (ms) for inference
(
Qiao et al., 2021
;
Zheng et al., 2023
;
Chaudhary et al., 2020b
)
.

9.
Summary

We presented Faro, an SLO-aware autoscaling system for ML inference services in a constrained containerized cluster. Faro adopts a “sloppified but fast” approach, e.g., w.r.t. objectives, workload prediction, etc.
Deployment and simulation results show that against state-of-the-art systems which focus on single jobs only, Faro: (1) lowers SLO violations by
2.3\times
–
23\times
when the resources are sufficient,
and (2) lowers SLO violations by

1.1\times
–
1.5\times
,
in constrained clusters.

https://dprg.cs.uiuc.edu/traces/go.php?id=40
