Protecting Locks Against Unbalanced Unlock()
Vivek Shahare, Milind Chabbi, Nikhil Hegde

Abstract
. The lock is a building-block synchronization primitive that enables mutually exclusive access to shared data in shared-memory parallel programs. Mutual exclusion is typically achieved by guarding the code that accesses the shared data with a pair of lock() and unlock() operations. Concurrency bugs arise when this ordering of operations is violated. In this paper, we study a particular pattern of misuse where an unlock() is issued without first issuing a lock() , which can happen in code with complex control flow. This misuse is surprisingly common in several important open-source repositories we study. We systematically study what happens due to this misuse in several popular locking algorithms. We study how misuse can be detected and how the locking protocols can be fixed to avoid the unwanted consequences of misuse. Most locks require simple changes to detect and prevent this misuse. We evaluate the performance traits of modified implementations, which show mild performance penalties in most scalable locks.

•

can it violate mutual exclusion? if so, how many threads may enter the

Show that unbalanced-unlock is a surprisingly common lock misuse scenario in many critical systems.

•

Systematically study the behavior of popular locking algorithms in the event of an unbalanced-unlock.

•

Provide remedies to popular locks to make them resilient to the unbalanced-unlock situation.

•

Empirically demonstrate that making popular scalable locks resilient to unbalanced-unlock need not significantly compromise their performance while retaining the original design goals.

2.2.
The role of the locking algorithms

What happens to the system/application in the event of an unbalanced-unlock depends on numerous considerations such as:

(1)

whether or not the lock results in violating the mutual exclusion?

(2)

if a data race ensues due to mutex violation, whether the programming model/language offers any semantic guarantees or does it lead to the so-called “catch-fire” semantics (e.g., C++
(
Boehm and Adve 2008
)
)?

(3)

whether or not one or more threads get into starvation?

(4)

whether or not the lock internals be corrupted in a way that subsequent lock usage is hampered?

Answering some of these questions are application context and programming model related and hence outside the realm of the locking algorithm. However, the locking algorithm has a crucial role to play in mutex violation or starvation.

What a locking algorithm does in an unbalanced-unlock is not a simple answer because lock algorithms come in myriad shapes and forms.
Some allow FIFO property, some do not;
some enable read-only feature, some do not;
some use hardware-provided atomics and others are software-only locks; some are tailored for the memory hierarchy while others are not; some allow recursive acquisitions others do not; some need to carry a context from acquire to release while other do not; to a few varieties.

Some locks such as the Array-based queuing locks
(
Anderson 1990
)
cause mutex violation but do not cause starvation; locks such as Graunke-Thakkar lock
(
Graunke and Thakkar 1990
)
cause only starvation but not mutex violation; locks such as the MCS lock
(
Mellor-Crummey and Scott 1991a
)
can cause both and additionally may cause illegal memory access.
A clear understanding of the lock’s behavior in the event of a misuse helps us a) assess the potential worst-case scenario and b) modify the lock internals such that it can self-detect that an invocation of
release()
is an instance of unbalanced-unlock and avert potential problems.

2.3.
Generic solution and its insufficiency

Any lock implementation can be enhanced in a generic manner to detect unbalanced-unlock by maintaining an additional PID field in the lock.
Such PID would be set to the lock acquiring thread’s id on lock acquisition; the
release()
would check the stored PID against its own PID; in case of a mismatch flag an error and return.

Naively introducing a PID field, however, may not be advisable under all circumstances for the following reasons:

(1)

The PID field increases the memory footprint of the lock, which has significant consequences when millions of lock instances are created and used concurrently
3
3

3

The
fluidanimite
application in PARSEC3.0
(
Bienia 2011
)
benchmark has 1.7 million lock instances.
.

(2)

Several systems, such as the Linux Kernel, require the lock to be compact, sometimes only a single machine word
(
Wang et al. 2016
;
Dice and Kogan 2019
)
.

(3)

A PID may be unavailable in some task-based systems (e.g., Golang
(
Taylor 2017
)
and CilkPlus
(
Project 2016
)
) since tasks may migrate across OS threads.

Our attempt here is to avoid using a PID as much as possible, and we fall back to the PID solution only when unavoidable.

The details of misuse scenarios, their side effects, and handling the side effects are the subject of the next three Sections.

3.
Unbalanced Unlock in Popular Locking Algorithms

In this section, we study popular locking algorithms and what happens on an instance of unbalanced-unlock.
We also propose detectability and remediation as code deltas to the pseudo-code of the original locks.
We refer the reader to
(
Mellor-Crummey and Scott 1991a
;
Dice et al. 2012
;
Chabbi et al. 2015
;
Magnusson et al. 1994
;
Craig 1993
)
for the basic knowledge of test-and-set, ticket, array-based queueing, MCS, CLH, and hierarchical locks.
We refer to the misbehaving thread as
T_{m}
.
We adapt the pseudo-code from
(
Mellor-Crummey and Scott 1991a
)
by Mellor-Crummey and Scott for our discussions but use the C++11 syntax in our discussion.
We use the C++11
atomics
for all shared variables and assume sequential consistency as the memory model.
We modify the signature of all
release()
functions to return
false
in the event of unbalanced-unlock and
true
otherwise.

Our work is centered around making minimal modifications to the locking protocols to detect and remedy unbalanced-unlock.
There are other ways in which the lock can be misused—for example, passing a null or arbitrary lock pointer to
acquire()
or
release()
APIs.
Furthermore, locks such as MCS, CLH, and Array-based queuing locks, need thread-local “context” pointer that is carried from the
acquire()
API to the
release()
API.

Any time a pointer is passed to an API, there is the potential to cause illegal memory access.
We cannot possibly fix this issue in an unsafe language such as C.
For languages such as C, our algorithmic modifications only detect and fix the misuse if the context pointer is a legal memory owned by the thread.
An arbitrary pointer is not possible in memory-safe languages such as Java—a null-pointer check suffices.
Our solution to avoid arbitrary pointers in C++ is to pass objects by lvalue references
(
Reference 2022
)
instead of pointers; C++ references can only point to valid objects unless someone takes the additional burden to circumvent this.
All our code examples follow this strategy.
In what follows, we, typically, do not discuss the consequences of passing a null or a rogue lock/context pointer to the
release()
API as part of unbalanced-unlock.

Test and Set (TAS) lock

The TAS lock (Figure

There is a shared boolean variable

The

The

The details discussed herein apply to the family of TAS locks, which include Test-and-test-and-set (TATAS) and TATAS with exponential back-off (BO)

Different situations arise in the unbalanced-unlock of a TAS lock.
If the lock is not held by another thread, when the misbehaving thread,

The misuse does not introduce any starvation—neither the misbehaving thread nor other threads spin forever; note, however, that, by design, the TAS lock does not ensure starvation freedom to any waiting thread.

Detection and solution:

We can detect an attempt to perform an unbalanced-unlock by storing the PID into

In the modified form, the

During

Our solution does not introduce a new field in the lock to store the PID; it re-purposes the same lock word with the PID.

3.2.
Ticket lock

The ticket lock (Figure
3
) is a FIFO lock.
It employs two global variables—
nowServing
and

. Each thread wanting to enter the

to gets its position in the queue and waits until

equals its position. The exiting thread increments

Mutex violation:

If the misbehaving thread

increments

when one thread (

) is already in the

, it admits the successor thread (

) into the

The situation beyond this is quite complex.
Without the loss of generality, assume that
t_{1}
finishes its

before
t_{2}
calls its

.
This admits the next waiting thread (
t_{3}
) into the
CS
, along with the already present
t_{2}
and the situation of two threads in the
CS
can propagate.
Alternatively,
t_{1}
and
t_{2}
may racily update
nowServing
from a value of, say

, making the lock recover for the remaining threads.
A single instance of unbalanced-unlock will allow at most two threads to be simultaneously into the
CS
.

N
instances of unbalanced-unlocks will allow at most
N+1
threads to be simultaneously into the
CS
.

Starvation
:
Starvation ensues if
nowServing
does not increase monotonically.
For example: let
nextTicket=nowServing=x
.
Now let,
T_{m}
load
nowServing
;
let an arbitrary number

pairs finish making
nextTicket=nowServing=x+n
.
Now let,
T_{m}
store
nowServing=x+1
.
After this, all new lock requests will starve since

will never reach

In almost all cases, a misbehaving thread in a ticket lock causes starvation for all other threads, violation of mutual exclusion, or both. The only time when there is no detrimental effect is when the lock holder and

both racily update
nowServing
to the same value and no other thread notices the updated

in the intervening window.

Interestingly, the misbehaving thread itself does not experience starvation, unless it attempts to

later.

Detection and solution:

By introducing a

3
, we remedy the lock.
The

is set after lock acquisition; the

3.3.1.
Anderson’s lock:

Anderson’s array-based lock
(

)
(Figure

In a nutshell, there is an array

A thread desiring to acquire the lock obtains a slot (indexed by

The lock-releasing thread unblocks the next waiting thread in the array.

It is the per-thread context that is carried from

An unbalanced-unlock can pass an uninitialized value of

The modulus operation in

However, it can release a waiting thread into the

There will not be any starvation of any thread—the modulus operation acts as a safety guard.

Detection and solution:
We wrap the

3.3.2.
Graunke-Thakkar lock (GT-Lock):

GT-Lock
(
Graunke and Thakkar 1990
)
(Figure
5
) is also a FIFO lock and organizes the threads in a queue. However, unlike ABQL, the waiting threads are on disjoint memory locations (similar to the CLH lock
(

;

)

The global
lock
structure has two fields—an array of booleans
slots
and a
tail

The

is organized such that each element falls in a processor-private memory module and is on an even-numbered address—the lowest-order bit (LSB) zero (the code uses

The
acquire()
for a thread with id PID publishes its slot address and its value (encoded via bitwise ORing
&slots[pid]|slots[pid]
) at the
tail
via the
SWAP

In return, it obtains its predecessor’s location (
pred
) and the value (
locked
) to wait on.
The thread then spins until the value at address
pred
is

. Correspondingly, the
release()
protocol toggles the value at
slots[pid]
to pass the lock to a waiting successor via an atomic
xor
.

To bootstrap the process,

is initialized to point to the address of an arbitrary element of the slot (say
&slots[0]

\neg
slots[0]
).

In the case of an unbalanced-unlock, the GT-lock does not violate the mutual exclusion but can cause starvation for all other threads.

No mutex violation:
Mutex violation is not possible because of the following argument. The slot
slots[
T_{m}
]
that the
T_{m}
toggles, is either in the queue or not in the queue; if it is not in the queue, the bit toggling has no impact on any thread.
If it is in the queue, it is either at the head of the queue or not at the head of the queue.
If it is at the head of the queue, then no thread is in the
CS
, toggling in the

due to unbalanced-unlock will only release a legit successor (say
T_{s}
) into the
CS
.
Finally,
slots[
T_{m}
]
may not be at the head of the queue if-and-only-if

enqueued it, which can happen only via an

operation, which contradicts the fact that the

is an unbalanced-unlock.

Starvation:
The
T_{m}
can cause starvation in the following way: consider
T_{m}
performing a round of successful

and during this time a successor
T_{s}
starts spinning on
slots[
T_{m}
]
.
Before
T_{s}
observes the change of the bit,
T_{m}
may perform another

, causing an instance of unbalanced-unlock reverting the bit back to the original value. Thus

will miss the update and may wait indefinitely. Due to the FIFO property, no thread will enter the

.

Detection and solution:

We introduce another boolean array
holder
of size
MAX_PROCS
and initialize all elements to
false
.
We change the

protocol to set

to
true
after lock acquisition.
The releaser checks if
holder[pid]
is
true
and detects unbalanced-unlock if is
false
.
A successful
release()
protocol resets this bit to
false
.
We note that one can repurpose the

holder

3.4.
MCS lock

The MCS lock (Figure
6
) is a FIFO lock.
It forms a singly linked list of waiting threads, each spinning on its own flag (
locked
field) in a
qnode
structure. Each thread enqueues itself into the queue by
SWAP

qnode
with the tail pointer
L
. This operation allows it to know its predecessor. An additional step of updating the predecessor’s
next
pointer is involved before starting to spin locally.
The release protocol involves one of the following: a) following the
I.next
and setting the successor’s
locked
to
false
, or b)
CAS
ing tail pointer to
NULL
if there is no successor.

For the MCS lock, in the event of an unbalanced-unlock, the following situations can happen:

(1)

if
I.next
is null, the misbehaving thread will loop forever waiting for a successor to enqueue.

(2)

if
I.next
is an arbitrary pointer, it can corrupt the memory leading to unpredictable behavior.

(3)

if
I.next
points to another legal
qnode
that is already enqueued, it will release such thread into

violating the mutual exclusion. This situation arises when passing a previously used
qnode
to the
release()
operation during unbalanced-unlock. In this case, a previously set
I.next
may be pointing to a
qnode
that is also enqueued again.

Note that the C++ lvalue reference avoids
I
from taking a rogue or a null value.

The MCS lock does not cause starvation for threads other than
T_{m}
. The argument for no starvation for other threads is the following: there are two loops one in
acquire()
and another in
release()
.
A misbehaving thread can only set the
locked
field to
false
, releasing any waiting thread in
acquire()
.
The loop in
release()
is on the
next
field, which is untouched by a misbehaving thread.

Detection and solution:

Our solution to the MCS lock is to always set the
locked
to
true
after the lock acquisition. In the
release()
, we reset
locked
to
false
. With this scheme, we can detect a misplaced

because

.

3.8.
Hierarchical locks

A series of multi-level locks were introduced to address remote memory accesses in Non-Uniform Memory Access (NUMA) systems. Here we discuss them informally.

3.8.1.
HMCS lock
(
Chabbi et al. 2015
)

The HMCS lock employs a tree of MCS locks mimicking the system’s memory hierarchy.
A thread enters the
CS
when it “logically” owns all locks from a leaf to the root of the tree.
Lock acquisition for each thread begins by competing for the local MCS lock at a designated leaf of the tree.
If the thread is at the head of the MCS queue at a level, it proceeds to compete for the lock at the parent level.
A thread that acquires the lock at the root of the tree immediately enters the
CS
.
Any thread that fails to immediately acquire a lock in the tree waits and receives that lock (and implicitly all ancestral locks) from its predecessor.
The release protocol also starts at a leaf of the tree.
A waiting successor, if any, at the deepest node on a thread’s path to the root implicitly inherits all locks held by its predecessor. As a result, when a successor is granted a lock, it immediately enters the
CS
without explicitly contending for other locks along its path to the root.

In the event of an unbalanced-unlock, the HMCS lock suffers from the same set of issues as discussed previously in Section
3.4
for the MCS lock.
Furthermore, since a lock releaser may proceed to release its ancestral MCS locks, it can introduce the same issue at every level in the tree.
Fortunately, the detection and remedy are also simple.
Since the release protocol starts at the leaf of the HMCS tree, we only need to adjust the MCS lock used at the leaf of the tree to use our renewed protocol discussed in the remedy for the MCS lock in Section
3.4
. To be specific, the
acquire()
protocol sets
I.locked
to
true
after the lock acquisition, and the
release()
protocol checks to make sure
I.locked
is
true
; otherwise, it infers an instance of unbalanced-unlock returning immediately.
At the end of a successful
release()
protocol,
I.locked
is reset to
false
.

The AHMCS lock
(
Chabbi and Mellor-Crummey 2016
)
is a refinement atop the HMCS lock allowing threads to start their
acquire()
and the corresponding
release()
at any level in the tree to dynamically adjust to contention. Our suggested remedy for HMCS applies to AHMCS as well since each thread brings its own
qnode
allowing us to inspect whether the
locked
flag is set.

3.8.2.
HCLH lock
(
Luchangco et al. 2006
)

The HCLH lock has two queues, a local queue (per NUMA domain) and a global queue. The thread at the head of the local queue waits to accumulate more requests within the local queue and then splices the local queue into the global queue via a
SWAP
operation.

A key deviation in HCLH over CLH is that predecessor
qnode
over which a thread subsequently gains ownership, is returned as part of the
acquire()
API instead of the
release()
API (as was done in the CLH lock).
As a result of this change, the
release()
protocol in HCLH is minimal—just setting
I->succ_must_wait=false
.

In the event of an unbalanced-unlock in the HCLH lock, the
qnode

I
used in
release()
is not enqueued. Hence, changing
succ_must_wait
on an un-enqueued node has no effect on the lock; consequently, there will be neither violation of the mutual exclusion nor starvation of any thread. Thus HCLH is relatively immune to unbalanced-unlock. We assume that the caller of unbalanced-unlock does not use any old
qnode
on which previously it had ownership, which could put it back in the same situation as the CLH lock.

3.8.3.
HBO lock
(
Radovic and Hagersten 2003
)

The Hierarchical Backoff Lock (HBO) builds on the TAS lock discussed previously.
In the HBO lock, the thread
CAS
es an ID representing its NUMA domain into the lock word
L
(instead of the
LOCKED
boolean).
Other threads can observe the NUMA domain ID of the lock holder when they attempt to acquire the lock.
With this knowledge, the threads from the same NUMA domain as the lock holder back off for a shorter period, whereas the threads from a remote NUMA domain back off for a longer period.

Our solution to detect and remedy unbalanced-unlock TAS lock can be retrofit for the HBO lock in the following way.
We need to
CAS
both the PID of the lock owner as well as the NUMA domain ID of the lock owner into
L
, so that the
release()
protocol can detect an unbalanced-unlock and the
acquire()
protocol can detect how much to back off.
The two fields can be easily encoded (via bit shifting and bitwise-ORing) into a single 64-bit lock word—a 32-bit PID and (say) an 8-bit NUMA domain ID.

3.8.4.
Cohort locks

Dice et al.
(
Dice et al. 2012
)
invented cohort locks, which allows combining two locks (may be of different type) into a two-level hierarchy. The properties required to form a cohort lock out of two lock types
G
and
S
are: a)
G
should allow the acquiring thread to differ from the releasing thread and b)
S
should have the cohort detection property:
a thread releasing the lock can detect other threads are concurrently attempting to acquire the same lock. A cohort lock is formed by making
G
a global lock and by assigning each NUMA cluster
c
with a distinct local lock
S_{c}
.

Dice et.al., discuss combining a local backoff lock (BO) with a global backoff lock to form a C-BO-BO lock. Combining two ticket locks (TKT) forms a C-TKT-TKT lock. Combining two MCS locks forms a C-MCS-MCS. Combining a global ticket lock with a local MCS lock forms C-TKT-MCS lock. The acquisition and release sequences always begin at the local lock and proceed to the global lock iff there is no cohort at the local level, similar to HMCS.

In the event of an unbalanced-unlock, all these locks suffer from the issues that we already discussed for the corresponding locks used at the local level. As such, the detection and remedy are also obvious—reuse the techniques to detect and remedy the local lock. For example, by storing the PID of the thread in the local BO lock (ref: Section
3.1
), we can fix a C-BO-BO lock; by storing the PID of the local lock into a field of a ticket lock (ref: Section
3.1
), we can fix the C-TKT-TKT lock. C-MCS-MCS is a degenerate case of HMCS lock with 2 levels, and the solution trivially applies (ref: Section
3.8.1
). By employing the remedy discussed in Section
3.4
for the MCS lock, C-TKT-MCS lock can be fixed.

4.
Reader-Writer (RW) Locks

A reader-writer lock allows the lock to be acquired in read-only mode in addition to the standard read-write mode. The read-only mode admits concurrent reader into
CS

We assume four APIs in the context of RW locks:
RLock()
paired with
RUnlock()
used by readers and
WLock()
paired with
WUnlock()

Invoking
RUnlock()
or
WUnlock()
without first invoking its corresponding locking API leads to an unbalanced-unlock situation. Mismatches such as pairing

WUnlock()
and
WLock()
-
RUnlock()
also cause unbalanced-unlocks.

Numerous RW-locking algorithms exist
(
Mellor-Crummey and Scott 1991b
;
Dice and Shavit 2010
;
Hsieh and Weihl 1991
;
Lev et al. 2009
;
Shirako et al. 2012
;
Calciu et al. 2013
)
, covering them all is impractical. We focus on the recent NUMA-aware RW lock by Calciu et al
(
Calciu et al. 2013
)
.
The NUMA-aware lock has several variants. We focus on the neutral-preference RW-lock (C-RW-NP), but the findings directly carry over to the other variants.

6.
Evaluation

We now present the evaluation of ten applications, each with six lock algorithms. We start with the evaluation methodology, which includes a brief discussion on the applications and the evaluation framework. This is followed by a comparative study for each application using the original and modified lock implementations.

System configuration.

We use a dual-socket system with a 24-core 2-way SMT Intel Xeon Gold 6240C@2.60GHz processor for a total of 48 hardware threads.
The CPU has 64 KB shared data and instruction caches, 1 MB unified L2, and 36 MB L3 unified caches. The system has 384GB DDR4 memory running Rocky Linux 9.

many lock algorithms from the literature. We modify the

We start with a configuration where there is no contention for the lock (i.e., running only one thread) and go up to maximum contention for the lock (i.e., running threads utilizing all the physical cores on the machine).
Every configuration of a test is run 5 times and best run of original lock implementation is compared with the best run of the modified lock implementation.

On lock design and performance

There exists a rich and diverse body of work focusing on the design of efficient locks targeted at various hardware architectures. While a majority of these
(
Chabbi et al. 2015
;
Chabbi et al. 2017
;
Dice et al. 2012
;
Mellor-Crummey and Scott 1991a
;
Auslander et al. 2002

Lozi et al. 2016
;
Craig 1993
;
Magnusson et al. 1994
;

;

)
rely on atomic instructions that all modern systems support, there are works that do not rely on such hardware support
(
Peterson 1981
;
Lamport 1987
;
Yang and Anderson 1995
;
Dijkstra 1968
)
. In all these works, the design addresses the performance of lock considering factors such as contention, lock usage pattern—some threads reading mutable data and while others write—
(
Lev et al. 2009
;
Calciu et al. 2013
;
Mellor-Crummey and Scott 1991b
)
, fairness criteria
(
Anderson 1990
;
Graunke and Thakkar 1990
;
Reed and Kanodia 1979
;
Mellor-Crummey and Scott 1991a
)
, energy efficiency
(
Falsafi et al. 2016
)
, whether running on single core or multicore
(
Project 2022
)
, and NUMA hierarchy
(
Chabbi et al. 2015
;
Chabbi et al. 2017
;
Dice et al. 2012
;
Calciu et al. 2013
;
Luchangco et al. 2006
)
. In comparison, we consider
unintentional
misuse and the resilience of locks against misuse rather than the performance of locks.

Guerraoui et al.
(
Guerraoui et al. 2019
)
do a thorough empirical evaluation of existing lock algorithms with a broad range of applications on a variety of architectures. Also, they provide a simple and effective way to evaluate new lock algorithms
(
Guiroux 2018
)
. While they suggest guidelines for software developers to overcome performance bottlenecks when using locks, they do not consider the misuse scenarios. We use their framework
(
Guiroux 2018
)
to evaluate our modified lock implementations.

On concurrency bugs and support system

The unbalanced-unlock scenario is a specific case of a concurrency bug. Race, deadlock detection, atomicity violation, and techniques to uncover concurrency bugs dynamically and statically is the focus in some of the important works
(
Lu et al. 2008
;
Choi et al. 2002
;
Engler and Ashcraft 2003
;
Prvulovic and Torrellas 2003
;
Savage et al. 1997
;
Yu et al. 2005
;
Boyapati et al. 2002
;
Lucia et al. 2011
;
Liu et al. 2021
;
Jin et al. 2012
;
Jula et al. 2008
;
Li et al. 2019
;
Sen 2008
)
.
Part of the work presented in this paper focuses on the prevention of a specific concurrency bug, unbalanced-unlock, through better engineering of lock designs. From a software engineering perspective, by making the unbalanced-unlock usage side effect free, our proposed fixes improve the software reliability in mission-critical systems and do not compromise the entire system due to one misbehaving thread.
More elaborate feedback to the programmer via returning error codes or raising panics is also a possible design choice: e.g.,
pthread_mutex
lock implements a separate lock type
PTHREAD_MUTEX_ERRORCHECK
, which allows an error code to be returned when a thread calls
unlock()
without holding the lock. Golang introduces API support to panic when an unlocked
sync.Mutex
is unlocked. The C++ thread sanitizer built into the LLVM toolchain also takes the same approach as that of Golang. However, the panic is enabled only in debug mode. In comparison to these approaches,
our proposed fixes modify the lock protocol and hence, do not affect the application code.

8.
Conclusions

In this paper, we presented an approach to making popular locking algorithms resilient to accidental misuse.
We considered a specific misuse scenario, unbalanced-unlock, where a misbehaving thread calls
unlock()
without holding the lock.
We presented data to show that unbalanced-unlock is a surprisingly common problem in large popular open-source repositories.
A systematic analysis of popular locks in the presence of unbalanced-unlock showed that the misuse could violate mutual exclusion, lead to starvation, corrupt the internal state of the lock and/or thread, and sometimes be side-effect free. We then presented remedies to avoid the side effects, and applied these remedies to a representative set of lock implementations. We evaluated the modified lock implementations for a set of lock-sensitive applications and showed that the modified lock implementations do not significantly affect the performance.
