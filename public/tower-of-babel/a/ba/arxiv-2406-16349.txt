AnnotatedTables: A Large Tabular Dataset with Language Model Annotations
Yaojie Hu, Ilias Fountalis, Jin Tian, Nikolaos Vasiloglou

Abstract
Tabular data is ubiquitous in real-world applications and abundant on the web, yet its annotation has traditionally required human labor, posing a significant scalability bottleneck for tabular machine learning. In this paper, we introduce methods that leverage Large Language Models (LLMs) to understand and annotate tabular data. Our methodology can successfully annotate a large amount of tabular data and can be flexibly steered to generate various types of annotations based on specific research objectives, as we demonstrate with SQL annotation and input-target column annotation as examples. As a result, we release AnnotatedTables, a collection of 32,119 databases with LLM-generated annotations. The dataset includes 405,616 valid SQL programs, making it the largest SQL dataset with associated tabular data that supports query execution. To further demonstrate the value of our methodology and dataset, we perform two follow-up research studies. 1) We investigate whether LLMs can translate SQL programs to Rel programs, a database language previously unknown to LLMs, while obtaining the same execution results. Using our Incremental Prompt Engineering methods based on execution feedback, we show that LLMs can produce adequate translations with few-shot learning. 2) We evaluate the performance of TabPFN, a recent neural tabular classifier trained on Bayesian priors, on 2,720 tables with input-target columns identified and annotated by LLMs. On average, TabPFN performs on par with the baseline AutoML method, though the relative performance can vary significantly from one data table to another, making both models viable for practical applications depending on the situation. Our findings underscore the potential of LLMs in automating the annotation of large volumes of diverse tabular data.

Introduction

Tabular data is one of the most common data types with pervasive real-world applications such as finance, healthcare management, and marketing analytics
(
Shwartz-Ziv & Armon, 2022
;
Borisov et al., 2022
;
Chui et al., 2018
)
. The tabular format can organize structured data as relational databases.
Machine learning models are able to understand and generate SQL queries against the relational databases
(
Zhong et al., 2017
;
Yan et al., 2020
)
, and large language models (LLMs) have emerged as a prominent method in this field
(
Liu et al., 2023a
;
Li et al., 2023a
)
. Recent studies show that LLMs can achieve state-of-the-art SQL generation with carefully engineered prompts
(
Gao et al., 2023
)
, owing thanks to the massive amount of open-source SQL code in their training set
(
Li et al., 2023b
)
.
Although valuable for training LLMs, SQL code alone is not enough for other tabular machine learning problems. For example, to evaluate the text-to-SQL ability where the model generates SQL code based on a description, both tabular data and SQL code would be required to calculate the execution accuracy
(
Zhong et al., 2017
;
Xu et al., 2017
;
Chang & Fosler-Lussier, 2023
)
.
While either SQL code or tabular data can be abundant, obtaining both at the same time can be far more difficult. Not limited to SQL code, annotations for tabular datasets can be generally difficult to collect, which we call
tabular dataset annotation problem
in this paper. We use executable SQL code as a lens to explore this tabular dataset annotation problem in detail and propose our machine learning solutions.

WikiSQL
(
Zhong et al., 2017
)
and Spider
(
Yu et al., 2018b
)
are two popular datasets with both SQL code and tabular data suitable for execution. However, their sizes are limited, mainly because their annotation methodologies do not scale up to make full use of either the tabular data or the SQL code on the web.
WikiSQL gathers its tabular data from Wikipedia pages, which is a limited source and does not reflect the complications of real-world tabular data. Also, its SQL programs are annotated manually by a crowd-sourcing service called Amazon Mechanical Turk.
Every crowd-sourced SQL program in WikiSQL only queries one table at a time, without table-join operations.
Spider, on the other hand, does include relatively more complex queries on multiple tables in a database, but it also relies on human annotations from 11 college students to collectively write the SQL programs. Human annotation is common in all tabular datasets with executable SQL code prior to our work (Table
1
), an expensive methodology to reproduce and expand upon
(
Hsueh et al., 2009
)
.
However, recent work shows that LLMs are able to synthesize SQL code robustly given instructions
(
Liu et al., 2023a
)
, which motivates us to explore the potential to use LLMs to synthesize the SQL code for the abundant, unannotated tabular data.
Our work focuses on SQL code, but SQL code is not the only type of annotation that tabular machine learning systems may need. Can LLMs create other types of annotations and generally replace expensive human annotations for tabular datasets?
Inspired by the multi-tasking
(
Srivastava et al., 2022
)
and emergent abilities
(
Wei et al., 2022
;
Schaeffer et al., 2024
)
of LLMs, we see both value and potential in tackling the tabular dataset annotation problem.

In this paper, we introduce AnnotatedTables, a large scale tabular dataset with large language model annotations.
To overcome the bottleneck of labor-intensive human annotations, we use LLMs to understand tabular data and generate synthetic annotations.
Our dataset construction starts with diverse cross-domain tabular data
encountered in real-world data science practices, while maintaining general applicability to other tabular data sources.
With careful prompt design, we instruct LLMs to synthesize SQL code with zero-shot learning, which, despite its large scale, proves to be a quick and cost-effective method to create a rich dataset without expensive human labor.
To ensure the quality of LLM-generated SQL code, we verify them with execution on the tabular data, and we report the validity of generated SQL queries for analysis.
To date, AnnotatedTables is the largest collection of SQL code that can be executed on the associated tabular data (Table
1
).
SQL programs are not the only annotations LLMs can produce. Some columns in a table may serve as model input to predict others, and such input-target columns are usually identified by people manually.
The LLM annotation methodology can be extended to annotate input-target columns for our tables, making them suitable for tabular classification.
Our work shows that LLMs can simplify and automate the process of tabular dataset construction.

To validate the soundness and value of our dataset, we conduct two follow-up studies. 1) We study LLM’s ability to learn a new programming language in-context. 2) We scale up the evaluation of a recent tabular classification model and test its performance on diverse real-world data. Both studies demonstrate how LLM annotation can flexibly adapt our dataset to target specific research problems. Our code and data will be released publicly.

The contributions of our paper are summarized as follows.

•

We introduce in-context learning methods of LLMs to understand and annotate a large amount of real-world tabular data, addressing the scaling bottleneck of traditional human annotation.

•

We use a LLM to annotate public data tables and construct a cross-domain dataset named AnnotatedTables, currently the largest SQL dataset with tabular data that supports query execution.

•

We extensively assess the quality of the LLM-generated annotations throughout the study. We demonstrate the research value of AnnotatedTables dataset through two follow-up studies.

•

We introduce Incremental Prompt Engineering to teach LLMs to translate SQL programs to Rel programs with adequate accuracy, where Rel is a new language not previously learned by LLMs.

•

We use the input-target columns annotated by LLMs to study TabPFN’s performance on a wide variety of tabular classification problems.
We find that TabPFN performs overall on par with the baseline method, with each model potentially performing better depending on the tables.

Database management systems and deep learning

For cardinality estimation, neural networks can predict the number of rows returned by an intermediate operation for query optimization

;

;

;

,
and end-to-end neural query optimizers can be built
(
Fischer et al., 2019
;
Gupta et al., 2020
;
Marcus et al., 2019
;
Marcus et al., 2021
)
.
Other deep learning for database problems
include query answering
(
Hilprecht et al., 2019
)
,
anomaly detection
(

)
,
ontology matching
(
Bento et al., 2020
)
,
relational data modeling
(
Fan et al., 2020
;
Liu, 2022
)
, and database indexing
(
Kraska et al., 2018
)
.
All these problems could potentially benefit from a large-scale multi-domain dataset like AnnotatedTables. LLM annotation can also be applied to these problems to acquire a large amount of tabular training data. Moreover, our dataset supports query execution, which is required for text-to-SQL and cardinality estimation to collect ground truth.

SQL datasets with tabular data.

SQL annotation is a focus of our paper. AnnotatedTables is the largest SQL dataset with associated tabular data that supports query execution.
Currently, the most commonly used SQL datasets with tabular data are listed in Table
1
, surveyed in
(
Deng et al., 2022
;
Qin et al., 2022
;
Li et al., 2023a
)
. All of them are annotated by humans, and our work is the first tabular dataset annotated by LLMs. Our LLM methods can cheaply generate a large amount of annotations that match the volume of tabular data available on the web.
Existing SQL datasets with tabular data often include English descriptions for text-to-SQL evaluation. While we collect these descriptions, we do not assess or ensure their quality. Unlike SQL programs, which can be validated through execution
(
Yu et al., 2019
)
, English descriptions cannot be executed.

Large Language Models for data annotation.

LLMs have been used for data annotation on text domains
(
Mao et al., 2024
)
and can outperform human annoators
(
Gilardi et al., 2023
)
. LLMs can detect implicit hate speech and provide natural language explanations as annotations

LLMs are also used for natural language generation evaluation, showing a high alignment with human evaluation
(

)
.
Texts can be directly understood and annotated by LLMs, while tabular data requires additional annotation methods, which we introduce.

3
AnnotatedTables

3.1
Dataset Construction

Collection of public data tables

The construction of AnnotatedTables starts by collecting public tabular data.
Our goal is to tap into the large quantity of un-annotated tabular data that exist on the web, with a preference for curated tables encountered in real-world data science applications.
Kaggle, a data science platform, meets our requirements
(
Risdal & Bozsolik, 2022
;
Quaranta et al., 2021
;
Wang et al., 2021
)
.
Kaggle hosts data tables that are crowd sourced by a community of data enthusiasts and professionals. Users can share and analyze datasets on a wide variety of real-world topics, including football players, U.S airline flights, renewable energy output, weather forecasting, and e-commerce product reviews.
Users may rate, improve, and analyze the datasets on Kaggle, contributing to the curation of useable and reliable data.
Although individual Kaggle datasets have been studied in prior works
(
Bojer & Meldgaard, 2021
;
Taieb & Hyndman, 2014
;
Yang et al., 2018
;
Tolkachev et al., 2020
;
Yang & Ding, 2020
)
, our research aggregates and examines the data tables en masse, uncovering an previously overlooked goldmine of diverse and high-quality data tables.

We use Kaggle’s public API to search for datasets
with sizes ranging from 10 megabytes to 1 gigabyte for faster data collection and processing.
We also require every dataset’s “usability rating” to be higher than 0.1. The “usability rating” is a quality score given by Kaggle users and helps us filter out low-quality datasets and datasets with no usages.
We collect 70,000 Kaggle datasets before stopping for further processing.
Our LLM annotation methodology is flexible and automated. The rest of our methods can be applied to other data sources and is not limited to Kaggle datasets alone.

Describing databases to LLMs with schema and example rows

In order for LLMs to understand and annotate tabular data, we need to design a textual description for each database as a part of the prompt.
Using entire tables in the prompt could exceed the maximum input length of LLMs, and we use a much shorter description instead that contains a basic schema and example rows.

Figure 1
:
An illustration of the SQL code annotation process with a large language model.

Table schema is a summary description of its structure, commonly used to define the table during its creation
(
Uschold, 2015
)
.
For our annotation purposes, we use a basic schema that includes the table name, the table’s column names, and the data type of each column (Figure
1
).
We find tabular data stored as CSV files in the Kaggle datasets and automate schema extraction.
As CSV files do not include table names in their content, we opt to use the file names as table names.
Column names are included in the CSV files as the header row.
Upon inspection, we find that the column names and file names are typically well-labeled and descriptive enough for LLMs to infer the information in the table.
Lastly, we use an existing data analysis software (pandas) to load the tables and infer the column data types.
Our schema extraction method is practical and effective.

A Kaggle dataset may contain multiple tables and therefore multiple table schemas. The set of table schemas describe the database structure: how many tables there are, what the columns and types are, and whether a column appears in multiple tables that could potentially be a
JOIN
key.

Example rows contain content from the table, and they are necessary for LLMs to write many common SQL queries, such as
WHERE
statements that filter the table based on a condition. For a concrete example, in
SELECT * FROM CUSTOMERS WHERE COUNTRY=‘MEXICO’
, the table name
CUSTOMERS
and column name
COUNTRY
can be found in the database schemas, while
‘MEXICO’
is a value that can only be found in a table row. Providing row examples in addition to the schema is necessary for LLMs to synthesize
WHERE
statements in SQL.
For the example row, we use the
first row of each table, converted to text through JSON formatting.
Our schema and example row descriptions are generic and allow almost all tabular data to be annotated by LLMs.

SQL annotations with zero-shot synthesis by LLMs

Through zero-shot learning, we instruct LLMs to synthesize SQL code that queries the data tables we collected as one type of annotation. Currently, OpenAI’s ChatGPT
(
Ouyang et al., 2022
)
is one of the best performing LLMs on various benchmarks
(
Hendrycks et al., 2021
;
Zellers et al., 2019
;
Sakaguchi et al., 2021
)
.
For our paper, we use ChatGPT with GPT-3.5 backbone as our annotation LLM, referred to as “the LLM” from now on.

To perform zero-shot SQL annotation for each database, we create a prompt that contains the instruction, the database schema, and the example row of every table, illustrated in Figure
1
.
The instruction asks the LLM to write SQL queries from “typical users who access this database”. In addition, the instruction asks for queries “with relatively high complexity”, which steers the synthesis results to more complicated SQL code and makes the dataset more challenging. Lastly, the instruction asks the language model to create more
JOIN
queries when multiple tables are present, as
JOIN
queries are especially valuable data points when studying problems including cardinality estimation and query optimization
(
Yang et al., 2020
;
Marcus et al., 2021
)
.
For every Kaggle dataset with tabular data, we prompt the LLM to generate 15
SQL program annotations with natural language annotations.

Execution-based validation

Some of the LLM-generated SQL programs could be incorrect, and it is important to examine and ensure the quality of the LLM annotations.
As AnnotatedTables has tabular data available for execution, we verify the validity of the SQL programs by executing them
(
Yu et al., 2019
)
. If a SQL program can be executed and returns non-empty results, then we classify it as a valid SQL annotation. Executable queries with empty results are marked. In our follow-up study of SQL-to-Rel translation, a pair of SQL and Rel queries with empty results cannot be compared by execution accuracy, and SQL queries with empty results will not be used.
We do not validate the English descriptions. All intermediate data artifacts are released as a part of AnnotatedTables.

3.2
Features, Statistics, and Examples of AnnotatedTables

Human-like annotation

We find that the LLM can write SQL programs with human-like intent and usage. Examples of the LLM-annotated SQL programs are provided in Table
2
. Instructed by our prompt to play the role of a typical user of a database, the LLM writes meaningful queries to look for useful data analytics.

Correctness and complexity

Given a high percentage (82.25%) of valid SQL programs, the annotation quality is good. The LLM can write complex programs with a variety of SQL components (Table
3
).
The percentages of valid queries in all SQL component categories except
JOIN
exceed 50%.
49.47% of
JOIN
queries are valid, possibly reflecting a higher level of data understanding and programming skills required to combine multiple tables.

For limitations, we note that some simple SQL statements appear often, in the form of
SELECT * FROM table
, reflected by a high percentage (48.4% among valid SQL programs) of
FROM
statements without other SQL components. Although valid, they may not be as valuable as the more complicated SQL programs for downstream learning and analysis. In the prompt, we steer the LLM to generate SQL programs “with relative high complexity” and see success to some extent (Appendix
B
). However, the dual objectives to generate complex queries and correct queries may inherently conflict with each other, and LLMs could be inclined to generate simple ones to prioritize correctness over complexity.

Invalid SQL annotations

As shown in Table
2
, some LLM-annotated SQL programs may be invalid for different reasons. At times, the LLM hallucinates non-existing table names such as “
table_name
” (Example 3) or leaves a place holder text “
condition
” instead of the exact selection condition (Example 3). In some CSV files, the column names may be numerical, which are invalid column names in a SQL statement, and the LLM is unable to annotate (Example 4). Lastly, as execution result needs to be non-empty so that execution accuracy can be computed for downstream tasks, some syntactically correct SQL programs that return empty results are labeled (Example 5).

4
AnnotatedTables for In-Context Translation from SQL to Rel

We use AnnotatedTables to study large language models’ ability to learn to code in Rel, a new database language
(
RelationalAI, 2021
)
.
For new programming languages, there is not much open-source code
available to train machine learning models with gradient-descent methods,
and, with few training examples, few-shot in-context learning (ICL) becomes a natural candidate instead

(
Min et al., 2022
)
.
ICL has been studied, but ICL of a new programming language is a novel research problem. New programming languages are rare, and the lens of this study is unique and timely.

All SQL programs in AnnotatedTables are executable, which is necessary in order to evaluate the correctness of the translations with execution accuracy.
AnnotatedTables contains many SQL programs and data tables, which can measure the general performance of our SQL-to-Rel translation method.
SQL programs in AnnotatedTables emulate the usage and intent of typical database users, and, by translating these queries, we indirectly synthesize a large dataset of non-trivial Rel programs that is valuable for downstream analysis and machine learning of the new programming language.

Machine learning of a new programming language may seem challenging with limited training data, but as our results show, our translation accuracy increases steadily as more in-context examples are included, and with 45 translation pairs in the prompt, the translation accuracy can reach around 40%.

4.1
Task Formulation of SQL-to-Rel Translation

Given a SQL program
S
that can be executed on table
T
, the task is to build a model
\mathcal{M}
that
learns to translate
S
into a Rel program
R
, such that
S
and
R
return the same query results when executed on table
T
. In our case, the model
\mathcal{M}
is a LLM parameterized by an instruction prompt that contains few-shot examples. Execution accuracy is the percentage of queries
S,R
that return the same non-empty results.
Execution accuracy is a common metric for SQL generation
(
Zhong et al., 2017
;
Xu et al., 2017
;
Chang & Fosler-Lussier, 2023
)
.
Program equivalence is generally undecidable
(
Rice, 1953
;
Strichman, 2018
)
, and it is not possible to directly compare SQL and Rel programs.

4.2
Extending AnnotatedTables with Few-shot SQL-to-Rel Translation Pairs

While LLMs have already learned to program in SQL from comprehensive pre-training
(
Brown et al., 2020
;
OpenAI, 2023
)
, they do not know how to write programs in Rel. To enable ICL, one idea is to use the Rel language specification and documentation as the prompt. However, language models such as ChatGPT have limited context span up to 16,000 tokens (around 12,000 English words)
(
Tay et al., 2020
;
Beltagy et al., 2020
)
, and it is currently infeasible for the prompt to contain the complete Rel specification and documentation (estimated 500,000 words). Instead, we use SQL-to-Rel translation examples to teach the LLM to code in Rel, which is simple and effective. Rel is a declarative language similar to Datalog and Prolog. LLMs may transfer their background knowledge in related languages to learn Rel. ICL through translation examples cannot comprehensively cover all the edge cases of the Rel language, but, as our results show, around 40% of our SQL code can be successfully translated.

Incremental Prompt Engineering of translation examples

To develop SQL-to-Rel translation examples to teach LLMs to code in Rel, we introduce a technique called
Incremental Prompt Engineering
(IPE).
For step
i=1,2,...,k
, we start with some manually annotated SQL-to-Rel translation examples
E_{i}
and instruct the language model to translate some unseen SQL programs
S_{i}
to Rel programs
R_{i}
.
We then calculate the execution accuracy by comparing the query results of
S_{i}
and
R_{i}
at every step
i
.
The execution accuracy is used as a feedback, and for the SQL code in
S_{i}
that the LLM fails to translate, we manually annotate the ones that represent
common failure patterns to add to
E_{i}
as the few-shot examples
E_{i+1}
at the next step.
In practice, we start with 5 translation examples and add multiple manual annotations at a time until the execution accuracy converges with around 45 translation examples (Figure
2
).
All examples used in the prompt are in Appendix
A
.

The LLM can learn a new programming language adequately from dozens of examples

Table
4
shows examples of SQL programs and their Rel translations produced by the LLM. As seen in the examples, the two languages differ greatly, and it is not an easy task to translate them, even for experienced programmers. For example, SQL aggregators such as
MAX
have their counterpart
max
function in Rel, but the syntax differs greatly (Example 1). Nevertheless, the LLM is able to perform adequate translations by learning a new programming language from just 45 examples in-context. Aggregators including
MAX
,
MIN
, and
COUNT
have higher-than-average translation accuracy. This is an impressive result for a challenging problem. Notably, no manual examples illustrate how to translate
MIN
queries, and LLM has inferred its usage from
MAX
examples.

Execution accuracy measures the translation correctness, where every SQL and Rel pair are executed on the same database and compare their results. Table
5
shows that the overall execution accuracy is 40.8%, showing that the LLM can generate adequate translations from SQL to Rel.
Machine learning of new programming languages is challenging and valuable. Since the best text-to-SQL models have 60%-80% accuracy
(
Liu et al., 2023a
;
Li et al., 2023a
)
, 40% SQL-to-Rel is a promising first step, which could be
sufficient for applications such as coding suggestions and automatic test generation.

Translation errors and limitations

53.6% of the Rel translations have errors before returning results, while 5.6% of the Rel translations finish execution but have different results (Table
5
). This suggests that most of the failed translations have syntactical problems and cannot be executed.
Examples of inaccurate translations are in Table
4
. LLMs may use SQL language constructs such as “
groupby
”, “
orderby
”, and “
desc
” directly in Rel programs (Example 4, 6), causing syntactically incorrect programs.
In Example 5, the first underscore “_” caused a syntax error.
In Example 7, the SQL method “
LENGTH
” is not demonstrated in-context, and the LLM used “length” as a variable name instead, causing a change in semantics and different execution results.
Examples 8 and 9 show different execution results, but the translations are correct by our inspection. Rel is a language based on the Sixth-Normal-Form (6NF)
(
Date et al., 2004
;
Knowles, 2012
)
, which represents all data as sets of tuples with only one value column, without null values or empty rows. Rel’s data representation is not the same as SQL’s data representation, and we make conservative conversions when comparing the results to prioritize precision over recall by allowing some false negatives in execution accuracy. Therefore, some correct Rel translations may have different results due to the conversion, though such cases are rare, as the percentage of Rel errors is 10x higher than different results. Discounting this limitation, the SQL-to-Rel translation accuracy may be even higher than that reported in Table
5
.

Performance convergence of Incremental Prompt Engineering

To study the effectiveness of IPE, we vary the number of few-shot examples incrementally added and measure the translation accuracy on a randomly selected subset of 2,000 SQL programs. We plot the execution accuracy versus the number of translation examples in Figure
2
.

Figure 2
:
With Incremental Prompt Engineering, translation accuracy gradually improves and converges as more examples are added.

Conceptually, Incremental Prompt Engineering adds demonstrations for the failed translations in the previous step and integrates execution feedback into prompt engineering. It is an effective way to improve translation accuracy, as we see a clear increase in the percentage of correctly translated Rel programs as more examples are added. When the number of few-shot examples increases above 30, we see a diminishing return on the accuracy improvements. At 45 examples, the accuracy converges around 40%. Due to the convergence, more examples may not improve the accuracy beyond 40%, and additional prompt engineering or LLM techniques may be required.

5
AnnotatedTables for an Extended Evaluation of TabPFN

In this section, we use AnnotatedTables to comprehensively evaluate TabPFN’s tabular classification performance on diverse, real-world data tables.
TabPFN
(
Hollmann et al., 2023
)
is a Prior-Data Fitted Network (PFN), a new type of neural networks trained on synthetic data drawn from a Bayesian prior.
Once trained, it takes the entire test set as the input and produces all predictions in a single forward pass.
TabPFN represents a novel approach to tabular classification, a domain dominated by traditional methods and largely uncontested by deep learning methods
(
Shwartz-Ziv & Armon, 2022
)
.
Inspired by its state-of-the-art results on a small curated benchmark
(
Hollmann et al., 2023
)
,
we wonder if TabPFN will perform robustly against the complications of real-world tabular data.

TabPFN evaluation and ours

TabPFN was evaluated on the OpenML-CC18 benchmark suite
(
Bischl et al., 2017
)
. The benchmark has 30 datasets in total, and 18 of them have only numerical features with no missing values, the same as the Bayesian prior that TabPFN is trained on. The authors choose five standard ML methods and two state-of-the-art AutoML methods as baselines to compare with TabPFN. The ML methods include K-nearest-neighbors (KNN), logistic regression, and three gradient boosting methods – XGBoost
(
Chen & Guestrin, 2016
)
, CatBoost
(
Prokhorenkova et al., 2018
)
, LightGBM
(
Ke et al., 2017
)
. The AutoML baseline methods are AutoGluon
(
Erickson et al., 2020
;
Shi et al., 2021
)
and AutoSkLearn

(
Feurer et al., 2022
)
. On the 18 numerical datsets, TabPFN outperformed all baselines, and AutoGluon was the best performing baseline (see Table 1 of
(
Hollmann et al., 2023
)
), which we will use as the baseline in our study.
In this section, we follow TabPFN authors’ experimental settings and use AnnotatedTables to vastly scale up the evaluation, with a focus on assessing its real-world performance.
We evaluate TabPFN on 2,720 tabular classification problems, a 90x increase
over OpenML-CC18.
Moreover, in comparison to the OpenML-CC18 benchmark, AnnotatedTables contains diverse tabular data gathered from a public platform, which would be a more comprehensive evaluation of TabPFN’s robustness in real world problems.

5.1
Task Formulation of Tabular Classification

For tabular classification, a table
T
has rows
\{R_{1},R_{2},...\}
. A row
R_{i}
has one or more column values
\mathbf{x}_{i}
and a categorical column value
y_{i}
.
A tabular classification model
f
aims to use
\mathbf{x}_{i}
to predict
y_{i}
.

Our experimental settings follow the TabPFN authors’ settings.
We train AutoGluon with a time budget of one minute and five minutes per table, and we split the training and test set once per table.
To reduce the total training time as we have many more tables than OpenML-CC18, we do not repeat training on every table with a five-fold training-test set split.
We use AutoGluon as our baseline, because it is the best performing baseline model in the original evaluation
(
Hollmann et al., 2023
)
.
Our work does not alter the TabPFN model architecture, and we use the authors’ publicly released pre-trained checkpoint. For more model details, we refer readers to the paper
(
Hollmann et al., 2023
)
.

5.2
Extending AnnotatedTables with LLM-Annotated Input-Target Columns

The Kaggle data tables collected in AnnotatedTables could be used for tabular classification task, if LLMs can identify the potential input and target columns.
We give the schema description from Sec
3.1
to the LLM to identify potential input and target columns in the tables.
TabPFN requires that the input columns are numeric and the target column is categorical for classification. LLM annotation is flexible, and we instruct the LLM to find columns that satisfy this data type requirement (for complete prompt, see Appendix
A
).
We use the input-target columns annotated to train TabPFN and AutoGluon, and if the models cannot be trained, the annotations are discarded (Appendix
E
).

TabPFN performs robustly on diverse tabular data

We fit TabPFN and AutoGluon on 2,720 tabular classification problems in AnnotatedTables,
and we compute the AUROC (one-versus-one) and cross entropy for every one of them, shown in Table
6
.
WilCoxon signed-rank test shows that all the paired differences between TabPFN and AutoGluon for both AUROC and cross entropy and for both 1 minute and 5 minutes are non-zero with statistical significance (p-values and discussions in Appendix
D
).
AnnotatedTables allows us to conduct a large number of experiments to draw statistically significant conclusions,
but the paired differences are small and may not be informative for model selection,
an issue known generally as “statistical significance versus practical significance”
(
Kirk, 1996
;
Peeters, 2016
;
McShane & Gelman, 2022
)
.
Overall, TabPFN performs on par with the AutoGluon baseline.

The classification problems in AnnotatedTables are diverse and have lots of inherent variations, which is reflected by the standard deviation of both models’ performance. Between the two, TabPFN has a lower standard deviation for both AUROC and cross entropy, showing a more consistent performance.

The inherent diversity of AnnotatedTables can be seen from the dot plots in Figure
3
, where we plot the AUROC of both models versus each other. Given a relatively high spread of AUROC and overall on-par performance, it is not possible to pre-determine which model will perform better, and either model could be better on a specific table.
Practitioners may fit both models and select the better performing one in practice. Given that AutoGluon is a widely used AutoML framework, we believe that the newly introduced TabPFN is a welcome addition that would raise the state-of-the-art performance on many real-world tabular classification problems, especially as it takes only a fraction of the time budget per table
(2 seconds) compared to AutoGluon (1 or 5 minutes in our experiments).

LLM annotation quality

Running TabPFN and AutoGluon on LLM-generated annotation proves that LLMs can successfully identify potential input and target columns in a table and annotate them, given only a prompt that describes each table’s name, column names and data types. As seen in Figure
3
, most of the tabular classification problems annotated by LLMs have an AUROC over 0.5 for both TabPFN and AutoGluon. This means, for most tables, the target columns identified by LLMs do have non-trivial relationships with the input columns and can be predicted to some extent, and the LLM successfully found the suitable tables for the tabular classification task.

6
Conclusions and Discussions

Prior to this work, human labor had been necessary to acquire tabular dataset annotations.
Large language models can bring a radical change to how machine learning datasets are constructed, and AnnotatedTables is the first to pioneer tabular dataset annotation with LLMs. LLMs can be steered to generate annotations based on detailed instructions, and tabular machine learning researchers could easily acquire tailored annotations that fit their research directions.
With the human annotation bottleneck opened, our methodology could enable more studies with reduced costs and automation.

We use the public service from OpenAI to access ChatGPT with the GPT-3.5 large language model. To support our claim that LLM annotations are cheap and accessible, we provide an estimate of our annotation cost.

1.

Generating SQL programs costs less than 400 U.S. dollars.

2.

Generating Rel translations for SQL programs costs less than 2000 U.S. dollars. The prompt for SQL-to-Rel translation is very long, as seen in Appendix
A
.

3.

Generating input-output column annotations for the data tables costs less than 100 U.S. dollars.

The time spent on annotation depends on the account limitations. OpenAI API calls can be made asynchronously to parallize the annotation process. All annotation processes combined can be completed within 2 days.

Appendix D
Wilcoxon Signed-Rank Test for TabPFN and AutoGluon Tabular Classification Performance Difference

Wilcoxon signed-rank test
(
Wilcoxon, 1945
)
is a non-parametric statistical test for paired data. We use the test to determine if there is a statistically significant performance difference between TabPFN and AutoGluon on the tabular classification problems from AnnotatedTables. For every tabular classification problem among the 2,720 problems, for every specific time budget (either 1 min or 5 mins), the performance metrics (either AUROC or cross entropy) of TabPFN and AutoGluon form a paired data. The tests show that the median difference between the pairs is nonzero with statistical significance for all settings. The p-value of Wilcoxon signed-rank test is shown in Table
7
. The paired bar plots are in Figure
4
.

Judging by the results of the Wilcoxon signed-rank test, TabPFN performs better than AutoGluon with 1 minute time budget, and AutoGluon with 5 minutes time budget performs better than TabPFN. However, the difference of medians is small, and the standard deviation of performances are high.
Based solely on the general results of Wilcoxon signed-rank test, we cannot predict if one model will outperform the other for a particular tabular classification problem. The issue of “statistical significance verus practical significance”
(
Kirk, 1996
)
is reflected here: even if a result is statistically significant, it may not be practically significant if the effect size is very small.

Appendix F
Tabular Dataset Annotation and Semantic Annotation of Tabular Data

Our paper studies the “tabular dataset annotation problem”, that is the problem of dataset annotation limited to the tabular data domain. Based on the common concept of dataset annotation, tabular dataset annotation is the process of labeling tabular data for machine learning. Currently, tabular dataset annotation is done through expert annotators or crowd-sourced human workers.

The “tabular dataset annotation problem” should not be confused with “semantic annotation of tabular data”, which is also called “tabular data annotation” in some context
(
PapersWithCode, 2024
)
. “Semantic annotation of tabular data” aims to match tabular data with knowledge graph entities.
