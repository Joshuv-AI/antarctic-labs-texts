Concurrency Testing in the Linux Kernel via eBPF
Jiacheng Xu, Dylan Wolff, Han Xing Yi, Jialin Li, Abhik Roychoudhury

Abstract
. Concurrency is vital for our critical software to meet modern performance requirements, yet concurrency bugs are notoriously difficult to detect and reproduce. Controlled Concurrency Testing (CCT) can make bugs easier to expose by enabling control over thread interleavings and systematically exploring the interleaving space through scheduling algorithms. However, existing CCT solutions for kernel code are heavyweight, leading to significant performance, maintainability and extensibility issues. In this work, we introduce LACE , a lightweight CCT framework for kernel code empowered by eBPF. Without hypervisor modification, LACE features a custom scheduler tailored for CCT algorithms to serialize non-determistic thread execution into a controlled ordering. LACE also provides a mechanism to safely inject scheduling points into the kernel for fine-grained control. Furthermore, LACE employs a two-phase mutation strategy to integrate the scheduler with a concurrency fuzzer, allowing for automated exploration of both the input and schedule space. In our evaluation, LACE achieves 38% more branches, 57% overhead reduction and 11.4 × \times speed-up in bug exposure compared to the state-of-the-art kernel concurrency fuzzers. Our qualitative analysis also demonstrates the extensibility and maintainability of LACE . Furthermore, LACE discovers eight previously unknown bugs in the Linux kernel, with six confirmed by developers.



1.
Introduction

In 21st-century computing, the end of Moore’s Law has led to a shift towards increasingly parallel and distributed software systems
(
conc:1
;
conc:2
;
conc:3
)
.
However, while concurrency has allowed Linux developers to write a scalable and performant kernel that is the core of the most widely used operating system in the world, the complexity of concurrency mechanisms in the Linux kernel contributes to a large number of concurrency bugs
(
conc:vuln
)
.
These concurrency bugs can lead to severe consequences due to the fundamental role of kernels in the software stack.
One prominent example is the Dirty COW vulnerability
(
cve-2016-5195
)
, where a race condition exploited a flaw
in the kernel’s memory management.
This allowed an attacker to gain write access to sensitive memory mappings, facilitating local privilege escalation and potentially affecting millions of computing devices.
Thus, finding concurrency bugs is essential in ensuring a safe and reliable kernel.

Concurrency bugs are often more challenging to discover
compared to their sequential counterparts
(
conc:opensource
)
.
This difficulty stems from the non-deterministic behaviour of concurrent operations, where certain bugs are only triggered with two important ingredients:
execution of the buggy code path and observation of a particular thread interleaving.
Finding these bugs thus involves exploring the thread interleaving space which can be exponential in the number of instructions in a sequentially consistent execution.

Traditionally, kernel developers often rely on stress-testing
(
stress:2
;
stress:CHESS
;
stress:java
;
stress:java2
)
to uncover concurrency bugs.
While subjecting the system to intensive workloads can sometimes increase the probability of bug triggering, it is labor-intensive to handwritten test suites.
Recent coverage-guided kernel fuzzers
(
actor
;
Syzkaller
;
kernelgpt
;
mock
)
primarily focus on navigating the input search space to reveal hard-to-find bugs in uncommon execution paths.
Complementing this direction, concurrency-oriented fuzzing techniques
(
Razzer
;
Conzzer
;
Snowboard
;
SegFuzz
)
have been proposed to control thread scheduling and explore different interleavings, leveraging both static and dynamic analysis in combination with custom heuristics.
However, these existing approaches still face the following challenges and limitations:

C0: Full, fine-grained scheduling control.

Many concurrency fuzzers either provide only weak control over thread scheduling by injecting delays
(
Krace
)
or limited control via a small number of coarse-grained scheduling points
(
Razzer
;
Conzzer
)
.
With only weak or limited, coarse-grained control, some concurrency bugs will be rendered unreachable during testing.
While trading completeness for performance is sometimes reasonable, these works fundamentally cannot enforce a higher degree of control.

C1: High runtime overhead.

Traditional concurrency fuzzers with full control typically operate at the hypervisor level
(
SegFuzz
;
Snowboard
)
.
These hypervisor-specific techniques are extremely heavyweight and exhibit poor scalability.
For example, Snowboard
(
Snowboard
)
introduces a substantial performance overhead, slowing execution by more than
10\times
. Additionally, the limitations of the hypervisor’s functionality restrict SegFuzz’s support
(
SegFuzz
)
for parallel fuzzing processes, resulting in a significant reduction in overall throughput (c.f. Section
6.2
).

C2: Lack of forward compatibility.

OS kernels have been under continuous development, with frequent updates and ongoing evolution. In addition to custom hypervisors, existing fuzzers usually require extensive customization tailored to specific kernel versions
(
SegFuzz
;
Krace
;
Razzer
)
. For instance, Krace
(
Krace
)
involves invasive kernel features, introducing a patch of over 10k lines of code across 105 files. This level of modification increases the cost and effort required to port the fuzzer to newer versions, and may also reduce its effectiveness. As a result, the practical usability and maintainability of such approaches are often compromised.

C3: Restricted extensibility.

Scheduling algorithms in existing concurrency fuzzers are often bespoke and tightly integrated with critical components of the underlying implementation.
Extending or duplicating them in a new codebase is typically extremely challenging and demands deep domain expertise.
As a result, traditional fuzzers that rely on default scheduling behavior are often still used to attempt to find concurrency bugs in practice.

Background and Related Work

2.1.
Kernel Fuzzing

Fuzzing
(
miller1990empirical
)
can be broadly defined as automatically feeding randomized inputs to target software and observing its behavior for bugs.
It has become the de facto standard technique for dynamically uncovering software vulnerabilities
(
aflplusplus
;
aflgo
;
stateafl
;
miner
;
park2020fuzzing
;
mopt
)
.
A prominent example is Syzkaller
(
Syzkaller
)
, a state-of-the-art kernel fuzzer that has been integrated as part of the upstream Linux kernel development pipeline.
Traditional fuzzers usually can be categorized into sequential-oriented
(
statefuzz
;
syz:2
;
actor
;
syz:6
;
syzvegas
;
healer
)
and concurrency-oriented
(
Razzer
;
Krace
;
Conzzer
;
Snowboard
;
SegFuzz
)
.
Sequential-oriented fuzzers explore kernel states by prioritizing test inputs that cover new branches.
For instance, Syzkaller generates system call (syscall) programs as inputs for the Linux kernel, primarily meant for sequential execution; it has identified over 5,000 bugs in the upstream Linux kernel but only roughly
10\%
are concurrency-related issues.
These fuzzing approaches have no control over the thread interleavings, relying entirely on the default OS scheduler; this greatly restricts their ability to explore the scheduling space to discover deeper concurrency bugs.

To fill this gap, several concurrency-oriented fuzzers have been proposed to handle exploration of concurrency space.
Krace
(
Krace
)
introduces an alias coverage that is implemented to guide fuzzing towards new interleavings.
However, Krace adopts a lightweight, but weak form of scheduling control by injecting random delays at memory access points.
Delay injection alone, however, is likely to miss many uncommon thread interleavings during fuzzing
(
Conzzer
)
.
Moreover, Krace requires substantial modifications of the Linux kernel, making it difficult to maintain as the kernel evolves over time (
C2
).

Razzer
(
Razzer
)
modifies the hypervisor to include hypercalls that, when called by a kernel thread, would install hardware breakpoints on the vCPU for scheduling.
These hardware breakpoints are installed at memory reads and writes, which are pre-determined by a heuristic-driven static analysis.
To trigger a race, Razzer does a single step on the specified vCPU before resuming execution on all vCPUs.
However, Razzer can still only enforce control at a small number of hardware breakpoints (typically 4 on current generation Intel processors), limiting its ability to explore schedules involving more than four events (
C0
).

SegFuzz
(
SegFuzz
)
, which builds on top of the Razzer architecture, improves on Razzer’s limitation by replacing hardware breakpoints at runtime, enforcing a fully controlled schedule sent by the fuzzer process via hypercalls.
Nevertheless, we observe that SegFuzz, constrained by its reliance on the hypervisor and virtualized hardware: it is limited to a single fuzzing process per virtual machine and thus does not scale well to larger fuzzing campaigns (
C1
).

SKI
(
SKI
)
and Snowboard
(
Snowboard
)
use a similar method of sending hypercalls to suspend and resume the execution of vCPUs according to a schedule.
However, instead of hardware breakpoints, they make use of the ability to set a thread’s CPU affinity to pin each thread to its own vCPU.
While this avoids the limited parallelism of SegFuzz, it introduces high latency for fine-grained context switches, as it does not leverage hardware features to achieve fast preemption (
C0
).

Also, due to the high degree of code coupling, these works typically employ a single CCT algorithm, thereby limiting their potential for efficiency improvements (
C3
).

2.2.
Controlled Concurrency Testing

A strongly related research to concurrency fuzzing is Controlled Concurrency Testing (CCT).
These works focus on exploring the space of interleavings of a
fixed input
, rather than simultaneously searching the space of inputs and interleavings as in concurrency fuzzing.
Many systematic
(
musuvathi2008finding
;
contextbound2005
)
and randomized
(
wolff2024greybox
;
sen2007effective
)
CCT scheduling algorithms have been developed which can effectively navigate the interleaving space.
In practice, randomized algorithms tend to outperform their systematic counterparts at scale
(
thomson2016concurrency
)
, and some of these randomized algorithms even provide probabilistic guarantees for finding certain classes of bugs
(
PCT
;
yuan2018partial
;
zhao2025surw
)
.
These algorithms have seen deployments in large-scale, industrial settings at companies like Amazon
(
bornholt2021using
)
and Microsoft
(
coyote
)
for testing user-space programs.
However, with the notable exception of SKI
(
SKI
)
, which implements only the PCT
(
PCT
)
algorithm, CCT scheduling algorithms remain largely unevaluated by past concurrency research
(
Krace
;
Conzzer
;
SegFuzz
)
.
As such an explicit goal of this work is to make these algorithms available in an extensible framework for kernel code (
C3
).

Finally, happens-before and other dynamic analysis tools such as TSAN can detect a subset of concurrency bugs (e.g. data races) efficiently
(
serebryany2009threadsanitizer
;
FastTrack
;
smaragdakis2012sound
)
.
However, development of such an analysis for the kernel –KTSAN– was halted due to the inherent complexity of modeling kernel concurrency primitives and high performance overhead
(
ktsan_2024
)
.

2.3.
eBPF Technology

The Extended Berkeley Packet Filter (eBPF) is a revolutionary technology with origins in the Linux kernel that can run powerful in-kernel virtual machine (VM)
(
mohamed2023under
;
dejaeghere2023comparing
)
. It offers a new way of kernel programming: developers can write programs that can be loaded at runtime and run in a safe, sandboxed environment within the Linux kernel, without directly modifying the kernel or loading a kernel module. Originally designed for packet filtering, eBPF has evolved into a general-purpose mechanism for observability
(
levin2020viperprobe
;
kawasaki2023failure
)
, security enforcement
(
bertrone2018acc
;
wang2023pet
)
, and performance improvement
(
zhou2024dint
;
zhong2022xrp
)
in a runtime switchable manner. By allowing user-space applications to inject custom logic into the kernel at runtime, eBPF provides a flexible and low-overhead means to monitor and manipulate kernel behavior.

One notable application of eBPF is the
sched_ext
feature
(
daniel2024sched
)
, which is designed to enhance application performance at scale. It has been officially merged into the mainline Linux kernel as of version 6.12. Traditionally, process scheduling in Linux has been limited to a fixed set of in-kernel policies, such as the Completely Fair Scheduler (CFS). This design restricts experimentation and specialization for emerging domains, including real-time systems, high-performance computing, and artificial intelligence workloads.
sched_ext
addresses this limitation by decoupling scheduling policy from the kernel and exposing user-defined scheduling logic through public interfaces
(
yasukata2024developing
)
. This provides a flexible infrastructure for developers to prototype and evaluate alternative scheduling strategies. While
sched_ext
is originally developed for writing domain-specific schedulers for performance optimization, we innovatively repurpose this feature to support kernel fuzzing for CCT.

3.
Motivation

Many concurrency bugs are triggered only by very particular orderings of (sequentially consistent) instructions executed in different threads or processes.
During normal execution, the interleaving is determined by the OS scheduler.
For the Linux kernel, the default scheduler typically attempts to allocate CPU time to the processes as evenly as possible
(
CFS
)
.
However, as its primary goals are fairness and performance (rather than schedule exploration), the OS scheduler may only trigger a concurrency bug with very low probability, possibly only under particular workloads or on specific hardware.
Thus, the ability to manipulate scheduling behaviour precisely can be a powerful strategy to find and reproduce concurrency bugs.

Motivating Example

To show the need for a CCT tool for the Linux kernel, we examine a concurrency bug that we found in the
fs/jfs
module that results in a null pointer dereference.
It is closely related to a recent bug which had been reported as fixed
(
d6c1b3
)
.
The previous issue was a use-after-free (UAF) due to missing synchronization in the
jfs_ioc_trim
function that allowed it to interleave execution with
dbUnmount
.
We show both functions in
Figure 1
with the partial fix highlighted in blue and the additional lines needed for a complete fix in yellow.
The UAF was triggered when
dbUnmount
freed
bmap
in one thread while
jfs_ioc_trim
still had a reference to it in another thread.
It was resolved by adding a read-write semaphore such that the free cannot interleave between obtaining the pointer and dereferencing it in
jfs_ioc_trim
.

Unfortunately, the accepted patch was still susceptible to a null pointer dereference, which was not caught by kernel developers but was found by
LACE
.
In particular,
JFS_SBI(ipbmap->i_sb)->bmap
is set to null in
dbFreeBits
after it is freed.
Thus, while the UAF bug can no longer occur, if the critical section in
dbUnmount
executes first, the resulting pointer will be null instead of the old address.
As the pointer is dereferenced in
jfs_ioc_trim
, this leads to a null pointer dereference under some interleavings.

We observed that this bug cannot be reproduced by the default OS scheduler in 10,000 executions of a syscall sequence under which the bug was observed;
with
LACE
, we are always able to reproduce the issue in less than ten executions.
This partial fix also demonstrates the need for more robust testing for concurrency issues, such as that provided by
LACE
.

Design of
LACE

Figure 2.

Figure 2

LACE
.

LACE
performs a two-phase fuzzing.
The first phase is sequential fuzzing, which aims to explore the input space with traditional generation and mutation strategies, maximizing code coverage.
The second phase, concurrency fuzzing, explores thread interleaving space with the
sched_ext
-based CCT scheduler.
To enable fine-grained thread control in this second phase,
LACE
can optionally inject additional safe preemption points into the kernel code (\raisebox{-0.9pt}{1}⃝) at compile time.
The scheduler can be loaded once at test-time in a few seconds (\raisebox{-0.9pt}{2}⃝) without needing to reboot or recompile the kernel.
During the concurrency fuzzing phase, to enhance concurrent exploration, we develop a concurrency mutation strategy (\raisebox{-0.9pt}{3}⃝) to generate multi-threaded syscall programs.
As
LACE
’s core, we propose a lightweight and effective scheduler to control the concurrent behavior of the test case
under the
sched_ext
scheduling policy (\raisebox{-0.9pt}{4}⃝).
As such, during execution of a multi-threaded test input (\raisebox{-0.9pt}{5}⃝),
LACE
replaces the native OS scheduling algorithm for a chosen subset of threads.
When a scheduling point (e.g. an I/O block) is reached,
LACE
enforces a schedule decision and selects the next thread to run from the set of runnable candidates according to a CCT scheduling algorithm.

LACE
repeats this scheduling process until all concurrent threads are finished.
In doing so,
LACE
can effectively serialize (\raisebox{-0.9pt}{6}⃝) non-determistic multi-threaded executions in a controlled order according to any CCT algorithm, thereby increasing the likelihood of triggering bugs that manifest due to rare interleavings.
During the execution of sequential or controlled concurrefnt test cases,
LACE
monitors whether the kernel under test crashes or terminates with any errors, in addition to collecting code coverage feedback (\raisebox{-0.9pt}{7}⃝) to drive exploration of the input space.

Through steps \raisebox{-0.9pt}{1}⃝ - \raisebox{-0.9pt}{7}⃝, there are four main components to our approach, shown in blue in
Figure 2
:
the
LACE
scheduler itself, the CCT scheduling algorithms implemented in
LACE
, the
LACE
instrumentation, and the
LACE
fuzzing loop.
In the following section, we explain in detail each of these components to our approach.

4.1.

Scheduler for Concurrency Fuzzing

Figure 3.
Thread lifecycle within the
sched_ext
infrastructure. Grey ovals represent the states that a thread can be in, and blue ovals represent actions that a thread can undergo.

The goal of our
LACE
scheduler is to carefully control the interleaving of kernel thread executions to expose elusive data race conditions in the kernel.
Although prior work has shown that such fine-grained control is possible using heavy-weight solutions, doing so without modified hypervisors and/or special hardware support was an unsolved technical challenge.
Here, we detail our solution to achieving controlled kernel interleaving using only lightweight, native eBPF kernel extensions.

We summarize the thread lifecycle model of the
sched_ext
scheduling class illustrated in
Figure 3
.
Each thread is initially created in the init_task state and and then is placed in a queue (enqueued) until it can be dispatched to a CPU for execution.
Upon being dispatched, a thread is allocated a time budget.
The thread reaches a stopping state when consuming its time slice or after voluntarily yielding the CPU from the program side for e.g. a blocking operation.

We implement the
LACE
scheduler in an eBPF program which is loaded during test runtime.
The scheduler uses the interface exposed by
sched_ext
to control kernel thread scheduling.
According to (
C0
) we
serialize
the execution of concurrent kernel threads under test to
fully control
their event ordering (e.g. accesses to shared data).
To do so, the scheduler strictly permits one running thread under test at a time.
After dispatching a task, the scheduler waits for the task to either become quiescent or be enqueued again before dispatching another task, even if idle cores and runnable tasks are available.
By default, per
Figure 3
this means that the scheduler will be invoked
only
when the lone running thread either yields control because of a blocking operation or it has exhausted its time slice.

LACE
repeats this procedure until all involved threads have exited.

To enable running parallel test instances in the same VM, the scheduler partitions threads spawned under different instances into different scheduling subsets.
Scheduling decisions among the subsets are completely decoupled, though threads from different subsets may time-share the same VM cores.
Our design thus logically
isolates
thread scheduling across testing instances to ensure correctness (equivalent to running each instance alone), while physically sharing the same VM for higher testing efficiency.

Enabling CCT in
sched_ext

While the
sched_ext
infrastructure provides a priority queue interface for dispatching tasks, this interface prohibits any updates to thread attributes after it has been added.
Unfortunately, using this rigid interface would preclude making dynamic scheduling decisions — once a task has been put into a dispatch queue, its priority (weight) is fixed and cannot be adjusted.
However, many concurrency testing scheduling algorithms such as PCT
(
PCT
)
and POS
(
yuan2018partial
)
require weights to be updated at runtime based on the dynamic state of the tasks in the program (e.g., after a certain number of events have occurred).
This dynamism is crucial to allow the scheduling algorithm to adjust to events in the program as they occur – for example, when the current thread is identified as racing with an event on another paused thread, we might want to increase the weight of the paused thread to allow it to run first
(
yuan2018partial
)
.
Therefore, the existing dispatch queue is not sufficient to address
C1
.

In
LACE
, we abandon the default priority queues in
sched_ext
, and instead define and manage our own queue structure via eBPF maps.
In this queue, we store a unique data structure for each task that encapsulates its dynamic priority (weight), enqueued status, subset identifier, and other related meta-data.
Dynamic priorities are algorithm-specific;
as we illustrate later, each algorithm can define its own priority strategy based on event attribute and runtime information.

4.2.
Scheduling Algorithms for Concurrency Testing

So far, we have described the mechanism by which
LACE
serializes the execution of the syscall program under test using the
sched_ext
infrastructure.
Proper concurrency testing also requires effective scheduling policies to explore large event interleaving space.
As introduced earlier, a scheduling algorithm in
LACE
implements a specific policy by defining a weight assignment function that is invoked at each scheduling point.
We have implemented four such randomized scheduling algorithms in the initial implementation of
LACE
: Random Walk, PCT
(
PCT
)
, Random Priority, POS
(
yuan2018partial
)
.
Our infrastructure is also extensible to support other more sophisticated scheduling strategies.

Random Walk

Random Walk (RW) is our most naive scheduling algorithm.
At each scheduling point, we select the next task to run from the pool of enqueued tasks uniformly at random.
Effectively, the algorithm assigns the same weight to all runnable tasks.
Notably, random walk provides probabilistic fairness — threads are unlikely to be delayed for an extended period of time.
It also results in many preemptive context switches, as each scheduling decision has a
\frac{N-1}{N}
probability of switching tasks if there are
N
enqueued tasks available to run.

Random Priority

For the Random Priority (RP) algorithm, at each scheduling point, we assign the most recently executed thread a random weight.
The algorithm then picks the runnable thread with the highest weight to execute next.
This approach differs from RW in that the weights of most of the threads persist across scheduling points.
As a result, Random Priority is prone to starvation, in that a thread with low weight will likely not be selected by the algorithm, and thus stick with its low priority for subsequent scheduling decisions.
RP also results in fewer context switches than RW.

Partial Order Sampling

In Partial Order Sampling (POS), each thread has a random weight and the weight of the thread most recently executed is reset at each scheduling point, similar to RP.
However, POS also reassigns the weight of any thread that has an event that
interferes
with the most recent event of the previously scheduled task
(
yuan2018partial
)
.
Here, interference can broadly be defined as accessing the same heap object, with at least one access being destructive (e.g., a
load
and
store
instruction accessing the same address).
This small change allows POS to choose different orderings of the interfering events with equal probability (as both will have their weights reset).
In particular, this makes POS the only
semantically aware
concurrency testing algorithm implemented in
LACE
: the algorithm requires source code information to compute interference.
As POS is a modification of RP, it can also suffer from starvation.

PCT
Probabilistic Concurrency Testing (PCT)
(
PCT
)
is a well-known algorithm developed for concurrency testing that provides a lower bound on the probability of detecting
low depth
concurrency bugs – parameterized by
d
.
It is an extremely
unfair
algorithm: It only enforces
d-1
context switches in an entire execution of thousands, or even millions of events, where
d
is often recommended to be set as low as 3
(
thomson2016concurrency
)
.
In PCT,
d
intervals are sampled uniformly from possible locations in the program execution.
Threads are assigned static weights at the beginning of execution.
At each of the
d
intervals, the thread with the highest weight is de-prioritized, giving the second highest weighted thread primacy.
To compute the interval sizes, PCT requires an estimate of the total number of events in a given execution, usually approximated by counting the events of a “trial run”.

4.3.
Scheduling Point Injection

When
LACE
dispatches a task to run, that task will continue to run until it hits a blocking operation or its allotted time-slice expires, at which point the scheduler will be invoked.
However, voluntarily scheduling only on blocking operations may not be fine-grained enough to trigger many concurrency issues (
C0
).
In principle, any operation that allows threads to synchronize or otherwise communicate with each other could lead to buggy behavior if reordered.
These communication points include locking operations on mutexes, spin locks, and accesses to memory shared across multiple tasks.
Ideally, a scheduler can switch tasks between each such operation to guarantee completeness: i.e. that each feasible reordering of an execution is also schedulable.
To attain fine-grained control, additional voluntary preemptions can be injected into a kernel under test before synchronizing operations using the
LACE
instrumentation.

Identifying Preemption

We delegate the majority of the responsibility of identifying important and safe scheduling points to runtime.
We take this approach because efficiently identifying all possible sources of inter-thread communication (including shared pointers) without large numbers of false negatives and/or false positives is extremely difficult for a C codebase the size of the Linux kernel.
In this setting, falsely excluding a source of inter-thread communication can render large portions of the potential scheduling space unreachable (i.e. reducing the completeness of
LACE
–
C0
).
As such, we use only lightweight, sound heuristics to identify scheduling points.
Similarly, determining
a priori
whether preemption is safe in a given context is extremely difficult.
Specifically, we focus on memory safety–related instructions (such as
load
and
store
) that may potentially race with other threads, as well as 37 other synchronization primitive functions we manually identified in the kernel source code.
These synchronizations include acquiring and releasing spin locks, semaphores, RCU locks and other concurrency primitives available to kernel developers.
To avoid excessive overhead from instrumenting nearly all loads and stores in the large Linux kernel codebase,
LACE
takes a sampling rate as an input parameter.
By default, we invoke the scheduler at with 10% probability at each scheduling point during fuzzing.
As with missed synchronization primitives, this reduces
LACE
’s theoretical completeness, but significantly lowers performance overhead and does not affect its soundness.
Crucially, unlike other weak and limited control concurrency fuzzers, different sampling rates and distributions are fully tuneable within the
LACE
framework.

Preemption Safety

When injecting additional scheduling points in arbitrary kernel code, it is important that we do not violate any assumptions made by kernel developers about where context-switches might occur.
Failure to do so can lead to false positives that are caused by context switching when it is not safe to do so.
For example, a kernel process which holds a lock could be preempted by another higher priority task or interrupt, which then tries to acquire the same lock, resulting in a deadlock on some systems.
Unfortunately, precisely whether or not it is safe to context switch at a given point is not encoded into the kernel source code, nor recorded in comments or documentation.
In order to aid Linux kernel development, however, developers have created some safety assertions.
For the
LACE
instrumentation, we extract these checks from the widely used synchronization helper functions (e.g.,
might_sleep
) and ensure that they are all passing before invoking the scheduler.
We note that passing these checks does not guarantee that it is safe to invoke the scheduler.
However, failing them will almost ensure that it is not safe.
Without using these checks, kernel panics can happen frequently when injecting scheduling points using instrumentation.

4.4.
Fuzzing Loop

Finding kernel concurrency bugs requires exploring both the kernel execution paths via the test input space and thread interleaving via the scheduling space.
To this end,
LACE
employs a two-phase fuzzing strategy, sequential fuzzing followed by concurrency fuzzing, seamlessly integrating the effective CCT scheduler into the fuzzing process.

Sequential Fuzzing
The primary goal of sequential fuzzing is to explore a broader range of execution paths in the kernel.
In this phase,
LACE
delegates to Syzkallers’ existing input-fuzzing strategy, which we summarize below.
For input fuzzing,
LACE
uses syscall specifications, which formally describe the set of system calls of the target kernel, including the structure and semantics of the parameters.
During test case generation,
LACE
iteratively selects syscalls,
appends them to the end of the current sequence, and instantiates the parameters.
Then, the resulting sequences are executed successively in their original order by the kernel under test.
If a sequence triggers previously unexplored code branches, it is considered promising and will be preserved in the corpus for further mutation.
To enhance coverage,
LACE
employs traditional mutation strategies, such as inserting additional syscalls, removing existing syscalls, and modifying the values of the parameters of the syscalls.
During test case mutation,
LACE
picks up a seed from the corpus and performs one of these mutation strategies in an attempt to uncover new execution paths.
While these strategies are effective in navigating sequential input space, they only trigger concurrency bugs as a rare secondary effect by placing stress on the kernel under test.

6.4.
Qualitative Examination of
LACE

To answer
RQ4
, we look at several aspects of its implementation.
While quantifying forward compatibility
(C2)
is difficult in general, one important driver of incompatibilities in other tools is the changes they make to the kernel source code itself.
Such changes can result in merge-conflicts when ported to newer kernels or break unexpectedly when internal kernel functionality changes.
Krace
(
Krace
)
requires over 10k lines of code changes.
SegFuzz
(
SegFuzz
)
applies over 5k lines of code changes to the guest kernel, with additional patches that must be applied to the host kernel as well.

In contrast,
LACE
leverages an LLVM pass for changes to the kernel code, only adding one additional helper function to the kernel source itself with less than 25 lines of code, fewer even than Razzer (40 lines changed) which exercises only weak scheduling control.
As a result,
LACE
will never produce merge conflicts.
That being said, lines of code are not the only metric of forward compatibility.
SKI
(
SKI
)
does not modify kernel code, but only is compatible with 32 bit kernels.
Snowboard
(
Snowboard
)
also does not modify the kernel under test, but unfortunately did not work on recent kernel versions in our experiments due to a possible implementation bug, indicating some forward compatibility issues as well.
It is difficult to anticipate if
LACE
will face similar issues, but qualitatively, we were able to use
LACE
on multiple versions of the kernel during our development and evaluation of the tool with no modifications at all.

(C3)

sl_sync

This bug is a concurrent use-after-free in
sl_sync
.
It is caused by a kernel thread improperly freeing a Serial Line IP Device (
slip_dev
) without first acquiring an
rtnl_lock
.
The use occurs when attempting to clean up existing open SLIP channels.
Notably, this bug is so difficult to reproduce, it was previously marked as invalid by kernel developers.
We show the average number of trials to reproduce this bug in Figure

.
Here we can see that
LACE
can reproduce this bug in an order of magnitude fewer schedules than the default OS scheduler.

8.
Limitations

Input Fuzzing and Concurrent Feedback

The primary focus of
LACE
is to enable lightweight, maintainable, extensible and fully controlled scheduling of kernel code.
While we enable
LACE
to search the input space for concurrent executions, the approach was kept minimal so as not to preclude future extensions of
LACE
(
C3
).
Other works have developed customized concurrency aware feedback
(
Krace
)
or input mutations
(
Snowboard
)
which can more effectively find concurrent syscall programs to be scheduled.
We hope such modifications can be added to the
LACE
framework in future work.

Completeness

The approach taken by
LACE
is theoretically complete in that it is able to instantiate an execution that is semantically equivalent to any sequentially consistent schedule that is feasible for the OS-scheduler.
However, the
LACE
instrumentation may miss some synchronization operations in the kernel due to e.g. inline assembly code and our safety checks may spuriously mark locations as unsafe for preemption.
As a result, it is likely that some schedules that are feasible for the OS scheduler are not feasible for
LACE
.

Semantic Extensibility

We have enabled
LACE
to provide some semantic information to the scheduling algorithms (e.g. memory address accessed), however, if a new scheduling algorithm requires
different
semantic information, this would require changes to
LACE
itself beyond simply implementing the standalone algorithm in eBPF code.
However, anticipating exactly what information might be needed from future CCT scheduling algorithms is difficult to anticipate, thus we still believe we have addressed
C3
as far as it is possible to do so.

9.
Perspectives

The operating system kernels today underpin all of our software infrastructure.
Thus ensuring that these kernels are reliable is of the utmost importance.

LACE
is a new tool that is both practical and effective for discovering and reproducing concurrency bugs in kernel code.
We hope that our lightweight design for extensibility and forward compatibility will allow developers and researchers to leverage it to increase the robustness of operating system kernels.
In particular, we hope to unify a fragmented research ecosystem, lowering the barrier to entry for new experimentation with different concurrency testing algorithms in real-world, large-scale concurrent code in the Linux kernel.
