AXE: An Agentic eXploit Engine for Confirming Zero-Day Vulnerability Reports
Amirali Sajadi, Tu Nguyen, Kostadin Damevski, Preetha Chatterjee

Abstract
Vulnerability detection tools are widely adopted in software projects, yet they often overwhelm maintainers with false positives and non-actionable reports. Automated exploitation systems can help validate these reports; however, existing approaches typically operate in isolation from detection pipelines, failing to leverage readily available metadata such as vulnerability type and source-code location. In this paper, we investigate how reported security vulnerabilities can be assessed in a realistic grey-box exploitation setting that leverages minimal vulnerability metadata, specifically a CWE classification and a vulnerable code location. We introduce Agentic eXploit Engine (AXE) , a multi-agent framework for Web application exploitation that maps lightweight detection metadata to concrete exploits through decoupled planning, code exploration, and dynamic execution feedback. Evaluated on the CVE-Bench dataset, AXE achieves a 30% exploitation success rate, a 3× improvement over state-of-the-art black-box baselines. Even in a single-agent configuration, grey-box metadata yields a 1.75× performance gain. Systematic error analysis shows that most failed attempts arise from specific reasoning gaps, including misinterpreted vulnerability semantics and unmet execution preconditions. For successful exploits, AXE produces actionable, reproducible proof-of-concept artifacts, demonstrating its utility in streamlining Web vulnerability triage and remediation. We further evaluate AXE’s generalizability through a case study on a recent real-world vulnerability not included in CVE-Bench.

Introduction

Modern open source software projects receive many more vulnerability reports than maintainers can realistically validate. Reports come from automated detection tools such as static application security testing (SAST) systems, which are known to produce high false positive rates

[

Addressing this vulnerability report backlog requires mechanisms that go beyond automated detection and assist with the
validation
of vulnerability reports. In practice, maintainers must decide whether a reported issue poses a genuine security threat under realistic workflows. Many reports, however, provide limited technical detail, ignore preconditions, or fail to include reproduction steps
[
32
,
38
]
. As a result, maintainers are left to manually reason about program logic and plausible attack paths to evaluate potential vulnerabilities. While such reasoning is feasible with sufficient context, time, and expertise, it does not scale to the volume of vulnerability reports encountered in practice.

To bridge this gap, we investigate how reported security issues can be assessed in a grey-box setting, mirroring the minimal information typically available during triage (e.g., in SAST reports).
Rather than relying on complete disclosures, exploit scripts, or prior knowledge of exploitation paths, the available information is limited to a weakness category (CWE classification), a location in the codebase, and access to the affected source code. The goal of this assessment is to automatically identify which reported issues are immediately exploitable in practice, allowing maintainers to distinguish urgent issues from benign or purely theoretical reports.

We present AXE, a multi-agent framework for automated exploitability assessment of Web application vulnerabilities. AXE treats the process as an iterative search over application endpoints, guided by feedback from both source code inspection and interactions with a running target via HTTP requests and responses. To support this process, AXE separates planning, source inspection, and execution into distinct roles. This separation allows hypotheses about exploitability to be proposed, tested, and refined over multiple attempts. When AXE performs a successful exploit, this process produces a concrete Proof-of-Concept (PoC). Exploit success is confirmed using automated evaluation tests that are specific to the attack type (e.g., SQL injection or privilege escalation).

Contributions.

This paper makes the following contributions:

•

We present AXE, a multi-agent framework that automatically explores and tests exploitation possibilities in Web applications. AXE leverages a feedback loop between static source analysis and dynamic execution to determine exploitability and produce concrete PoC evidence.

•

We extend the CVE-Bench benchmark
[
55
]
by augmenting its targets with collected source code and exploit-relevant metadata, thereby creating a standardized evaluation harness for grey-box assessment.

•

We conduct a systematic evaluation study that measures exploitation effectiveness of AXE, characterizes common failure patterns in our grey-box agentic exploitation (e.g., misinterpreted vulnerability semantics), and analyzes the clarity and reproducibility of the generated PoC artifacts.

•

We showcase AXE’s generalizability beyond CVE-Bench through a detailed case study on a recent real-world CVE that lacked any public exploit or proof-of-concept.

In our evaluation on CVE-Bench, a benchmark of real-world Web application vulnerabilities, AXE outperforms black-box methods by 3x, successfully exploiting 30% of the evaluated vulnerabilities. For successful cases, we find that AXE’s PoC outputs are highly useful for validation: 11 of 12 included an explicit verification oracle and instructions that reproduce the evaluator-defined success condition. Beyond these successes, our analysis reveals systematic reasoning bottlenecks in grey-box agentic exploitation, including difficulty connecting abstract vulnerability descriptions to concrete program behaviors. We characterize these failures to inform future improvements to agentic exploitation systems.

2.1
Overview

Figure
1
shows AXE’s workflow for validating vulnerability reports through an iterative loop of planning, source code exploration, and sandboxed execution.

AXE takes as input minimal detection metadata: 1) a CWE identifier, 2) a source code location given as a file path and line range, and 3) source code of the target Web application. From the provided location, AXE automatically extracts the corresponding code snippet to begin the vulnerability investigation with initial context. To further inform the process, AXE performs lightweight endpoint discovery against the target service using
dirb

[
8
]
to obtain and cache an initial list of reachable endpoints. All agents operate within a single attacker container that contains the application source code. The attacker Docker container is separately instantiated for each vulnerability and is isolated from the container running the vulnerable service. All interactions are limited to network communications.

AXE is composed of four specialized components that coordinate to transform raw metadata into verified exploits. The
Strategist
acts as the central reasoning engine, maintaining the global exploitation state and iteratively refining attack hypotheses based on observed feedback. It delegates information gathering to the
Explorer
, which performs on-demand source code analysis to extract critical facts about program logic and security controls. Execution is handled by the
Exploiter
, which translates high-level plans into concrete network interactions and manages the low-level details of multi-step attack chains. Finally, the
PoC Gen Module
synthesizes successful execution traces into a structured, Proof-of-Concept (PoC) report, providing the reproducible evidence necessary for efficient vulnerability triage and remediation.

After initialization, AXE enters an iterative exploitation loop. Each iteration produces an exploitation approach, optionally retrieves additional source context, executes a candidate exploit against the target service through the container network, and records the full command and response history. The outcome of each iteration is checked by an external evaluator, which runs automatically generated validation tests corresponding to different attack types. These tests check for post-conditions that indicate successful exploitation, such as unauthorized data access, database modifications, or evidence of a low-privilege user being elevated to an admin role. The next iteration is conditioned on this feedback, enabling AXE to revise its approach based on observed evidence rather than repeating the same unsuccessful actions. When exploitation is verified, AXE outputs a reproducible PoC and a developer-facing report (
PoC.md
) generated from the successful execution traces, while unsuccessful runs yield summaries that capture what was tried and what evidence was observed.

We adopt an agentic design rather than one-shot prompting because exploitation is inherently interactive and multi-step in practice
[
37
,
16
]
. Initial exploitation attempts often fail due to missing preconditions, incomplete request structure, or overlooked dynamic values. These deficiencies are typically revealed only through targeted probing and execution feedback. By using iterative planning with tool use, AXE supports hypothesis-driven exploration, discovery, and refinement based on concrete evidence. This process is consistent with established penetration testing workflows
[
37
,
16
]
, and leverages recent advances in agentic architectures designed to enhance reasoning for long and complex tasks
[
30
,
53
]
.

More specifically, AXE uses a multi-agent architecture to improve performance on multi-step exploitation workflows. Although single-agent designs can engage with complex tasks, they commonly struggle with longer workflows that entail many steps and are prone to repeating ineffective actions under partial feedback
[
15
,
53
,
30
,
50
,
13
,
44
]
. Decomposing the task into specialized roles improves robustness by separating global reasoning from source context retrieval and execution. It enables structured feedback that helps the system correct course across iterations. We adopt a hierarchical architecture with lateral cooperation
[
53
]
to keep control and decision making centralized while still allowing on-demand context retrieval and command execution. Further, we summarize raw tool and command outputs before they are fed back into planning to reduce noise and token usage.

Next, we describe each component of AXE in more detail to illustrate how information and decisions flow.

2.2
Strategist

The Strategist coordinates the exploitation process, maintains, and develops an exploitation approach across iterations. Its role is to reason about vulnerability reachability and required preconditions, form hypotheses about viable exploitation paths, and iteratively refine these hypotheses based on evidence gathered during exploration and execution. Strategist maintains a working context that captures key observations, failed assumptions, and progress toward a viable exploit.

In each iteration, the Strategist assesses whether the available information is sufficient to synthesize an executable exploitation plan. When critical details are missing, it first requests additional source-level code context to inform its subsequent planning decisions. Once the necessary information has been gathered, the Strategist synthesizes a concrete exploitation plan and delegates it to the Exploiter for execution. If an attempt is unsuccessful, the Strategist analyzes the outcome and updates its assumptions to guide the next iterations. This feedback-driven refinement helps AXE avoid repeating ineffective actions and supports progress on multi-step exploitation workflows where early attempts are often inadequate.

2.3
Explorer

Explorer provides on-demand source context retrieval to support Strategist in its plan formulation. It has access to the source tree and performs actions such as listing directories, reading or searching files, and checking path existence. In response to Strategist queries, the Explorer locates relevant code regions and extracts concrete facts needed for planning, such as control flow conditions, how user-controlled inputs propagate into security-sensitive operations, and where validation or authorization checks may be missing or insufficient.

The Explorer summarizes its findings into concise, task-relevant statements and includes short code excerpts whenever necessary to contextualize its responses. These summaries reduce noise and token usage and build a compact Q&A-style working context about the target and vulnerability that can be reused across iterations, as illustrated in Figure
2
.

Figure 2
:

2.4
Exploiter

The Exploiter is responsible for carrying out exploitation attempts against the target service from the attacker container. It executes the Strategist’s high-level plan while handling the execution level details required to realize it in practice. This includes issuing concrete HTTP requests, extracting dynamic values such as cookies or identifiers, adapting request structure based on server responses, and sequencing multi-step commands when necessary. The Exploiter can invoke cli tools and programs (e.g.,
dirb, sqlmap, grep
), run shell commands, and create artifacts such as scripts and payload files to support these workflows.

During each attempt, the Exploiter records the full command and response history, producing an execution trace that captures both successful and unsuccessful interactions. When an attempt does not succeed, the Exploiter generates a concise outcome summary and failure analysis that highlights salient observations and execution level issues. These summaries are returned to the Strategist to inform subsequent planning decisions and help the system avoid repeating unproductive actions.

2.5
PoC Gen Module

Upon a verified successful exploitation attempt, the LLM-based
PoC Gen
module generates a developer-facing report as a markdown file (
PoC.md
). The content of this file is derived from the successful execution trace and the exploitation plan, and is intended to support vulnerability validation and triage.

The report records the affected components, relevant code locations, a concrete trigger that reproduces the vulnerability, and the verification oracle used to demonstrate exploit impact. It also includes step-by-step reproduction instructions and potential remediation steps when applicable. The included fields are chosen to prioritize reproducibility and usefulness for practitioners based on prior analyses of proof-of-concept reports
[
5
,
48
]
. Figure
4(b)
shows an example PoC artifact produced by AXE.

3
Threat Model

We model AXE as a white hat attacker performing vulnerability validation under realistic conditions. We assume a competent adversary who may operate in a grey-box setting with access to the application source code, as is common for open source software. In addition to source access, the attacker may have minimal vulnerability hints, such as a suspected vulnerability type and a code location identified by a detection tool or manual inspection. These hints may be incomplete or inaccurate. AXE uses this information in the same way a real attacker or security analyst would by reasoning about program logic, probing reachable attack surfaces, and attempting exploitation through the application’s exposed interfaces. To ensure safety, all exploitation attempts are conducted in isolated containerized environments and do not involve live or production systems. We do not consider closed-source software, vulnerabilities that require physical access or side channels, or attacks that rely on social engineering. When AXE produces a concrete and confirmed PoC, this constitutes sufficient evidence that the vulnerability is exploitable in practice, while failure to produce a proof of concept does not imply that the vulnerability is non-exploitable.

4
Experimental Setup

4.1
Dataset

We evaluate AXE on the CVE-Bench dataset
[
55
]
, a benchmark of 40 real-world, critical-severity web application vulnerabilities extracted from the National Vulnerability Database (NVD)
[
34
]
and disclosed between May 1, 2024, and June 14, 2024. We choose CVE-Bench because it provides real-world, reproducible, and critical-severity Web CVEs. Additionally, CVE-Bench provides containerized instances of vulnerable applications alongside automated exploit success checks for a set of attack types. Exploitation success is verified via test cases that check for the creation or modification of server-side files, unauthorized file or database reads, and persistent changes to database content, enabling automated confirmation of exploit impact.

For each vulnerability, we instantiate the target service using the official CVE-Bench Docker setup and retrieve the exact vulnerable version of the application source code corresponding to the deployed container. This source code is automatically copied into the attacker container where AXE operates, and access to it is provided to the Explorer agent.

We manually map each CVE to its specific file and line number by cross-referencing patch diffs, security advisories, and available exploit documentation. When a vulnerability involves multiple contributing code locations, we select a single location corresponding to the critical function that enables exploitation. In practice, this location can correspond to any suspected vulnerable line(s) in the program, identified by a static analysis tool, vulnerability scanner, or other detection method. AXE is not given any additional information about the vulnerability, exploit logic, or advisory context; rather, it is responsible for identifying relevant code paths and operational details starting from this vulnerability location.

4.2
Baselines

To comprehensively evaluate our framework’s performance and validate our contributions, we conduct comparisons against three categories of baselines. Because existing automated exploitation tools are primarily designed for black-box environments, we develop custom grey-box baselines to isolate the specific impact of our multi-agent architecture and metadata-driven approach while maintaining a consistent information boundary.

1) SOTA black-box tools:
We compare our approach against existing automated exploitation tools (T-Agent
[
56
]
and AutoGPT
[
40
]
) operating in their native black-box mode without access to any vulnerability metadata or source code. This establishes our framework’s performance relative to current capabilities in automated black-box exploitation.

2) Single-agent grey-box baseline:
We implement a single-agent baseline that receives the same grey-box inputs as AXE (e.g., vulnerability information and source access), but collapses AXE’s specialized roles into a single-agent that is solely responsible for interpreting vulnerability context, selecting exploration and exploitation actions, and iteratively refining its approach across attempts. We allocate the agent a fixed interaction budget per CVE; for baselines, we map this budget to loop-equivalent attempts for metric computation. In addition, the agent maintains a persistent, long-term software knowledge base. Whenever the agent discovers new facts about the target system (e.g., endpoints, configuration constraints, authentication requirements, relevant code locations, or error signatures), it records them in a structured memory store and reuses them in subsequent iterations to avoid relearning the same information. The design follows prior work that augments an agent with a persistent database of system knowledge
[
17
]
.

3) Our framework without vulnerability metadata (AXE-BlackBox):
We run our multi-agent framework in black-box mode, removing access to vulnerability metadata (e.g., CWE classification), source code, and the Explorer agent. Comparing this against our full framework demonstrates how vulnerability metadata enhances our framework’s exploitation capabilities and validates our approach of integrating static analysis findings into the exploitation process.

4.3
Metrics

We evaluate AXE using three metrics established in prior work
[
10
]
.
Success Rate (SR)
captures overall effectiveness by measuring whether exploitation succeeds within a fixed attempt budget. To complement this, we report two efficiency-oriented metrics (
Average Task Completion Attempts, Success Efficiency
) that account for iterative progress under bounded interaction budgets. Together, these metrics capture not only whether exploitation succeeds, but also how quickly a valid exploit is reached when success occurs.

1) Success Rate (SR).

Success Rate measures the proportion of vulnerabilities for which a given system successfully produces a verified exploit within the allowed attempt budget.

\mathrm{SR}=\frac{\text{Exploited CVEs}}{\text{Total CVEs}}

2) Average Task Completion Attempts (AvgTCA):
Average Task Completion Attempts measures the average number of attempts required to successfully exploit a vulnerability. In our framework, one task completion attempt corresponds to a full strategy–execution loop, consisting of a planning step by the Strategist followed by an exploitation attempt by the Exploiter. For baselines without an explicit loop structure, we normalize attempts by converting interaction steps into loop-equivalent attempts based on the execution budget of a single AXE loop. Lower AvgTCA values indicate that the framework converges to a valid exploit more efficiently.

\mathrm{AvgTCA}=\frac{1}{\text{Exploited CVEs}}\sum\mathrm{TCA}

3) Success Efficiency (SE):
Success Efficiency combines and measures both effectiveness and efficiency by enforcing a penalty on successful exploitations that require many failed attempts. It rewards systems that achieve successful exploitation in fewer attempts while maintaining a high success rate. MaxA denotes the maximum number of allowed attempts per CVE, set to 5 for AXE, corresponding to 5 execution loops.

\mathrm{SE}=\frac{\mathrm{SR}}{\mathrm{AvgTCA}\left(\frac{\mathrm{AvgTCA}-1}{\mathrm{MaxA}-1}\right)}

These metrics provide a more informative evaluation than success rate alone, distinguishing between systems that occasionally succeed after many failed attempts and those that efficiently confirm exploitability within a small number of iterations.

4.4
Implementation

All experiments use GPT-4o with default decoding settings and temperature, whose training cutoff
[
36
]
postdates the disclosure window of the dataset, starting on May 1, 2024, to mitigate the possibility of data contamination. Evaluations were conducted on a single commodity laptop (Apple M2, 16 GB RAM). Since we do not report runtime or throughput metrics, hardware characteristics do not affect the reported results. Prompts, execution traces, and full implementation details are provided in the replication package
[
39
]
.

These tools become especially effective in the grey-box setting, where combining tool outputs with source-guided context from the vulnerable code location reduces probing and increases the likelihood of converging on a working exploit.

RQ1 Summary.

AXE demonstrates that combining minimal grey-box vulnerability metadata with a role-specialized, multi-agent framework improves exploitation success over both black-box systems and single-agent grey-box baselines. Providing only a vulnerability category and source-code location increases Success@5 from 10% to 30%, while decomposing exploitation into smaller subtasks further improves success from 17.5% to 30% under identical grey-box inputs.

5.2
RQ2: Failure Patterns in Grey-box, Agentic Exploitation

We investigate and characterize the dominant failure patterns encountered in AXE’s grey-box, agentic exploitation approach. While agentic failure analyses often focus on general benchmarks and issue resolution, vulnerability exploitation can introduce distinct challenges, such as reasoning about implicit preconditions, constructing vulnerability-specific payloads,
and bridging high-level vulnerability metadata such as CWE labels to concrete program-specific attack surfaces and exploitation paths. We therefore study failures in AXE to understand how these challenges manifest in agentic exploitation.
For each unsuccessful run, two authors manually inspect the execution trace and first attribute the failure to the AXE component where the run first goes off the rails, based on the role-specific responsibilities of the Strategist, Explorer, and Exploiter. We then analyze the trace segment produced by that failure-inducing component and perform iterative open coding to derive a taxonomy of technical failure causes, assigning one or more failure-cause labels per run. Disagreements are resolved through multiple discussions until a consensus (100% agreement between the annotators) is reached. Annotation guidelines and per-run labels are documented in our replication package
[
39
]
.

Our failure analysis considers 25 out of the 28 unexploited runs. Three CVEs are excluded from the taxonomy counts because they do not meaningfully fit our grey-box exploitation setting: CVE-2024-5452 involves a vulnerability rooted in a dependency whose source code is unavailable for inspection; CVE-2024-37999 is closed-source; and CVE-2024-25641 lacks a practical command-line exploitation path in our evaluation environment. AXE’s execution on CVE-2023-51483 begins with an initial exploitation attempt derived solely from the vulnerable code snippet and surrounding file context. In the first loop, the Strategist observes that the registration logic can influence account roles via a

7
Discussion

Backlog-driven triage.

In practice, vulnerability reports accumulate faster than they can be manually assessed, leaving developers and security teams with large, noisy backlogs. Reports from static analysis tools, bug bounty programs, and coordinated disclosure efforts frequently lack sufficient detail to determine practical exploitability. Prior empirical studies of offensive security practices observe a shift away from purely black-box testing toward grey-box approaches that improve efficiency and coverage
[
16
]
. Incorporating a grey-box agentic exploitation framework such as AXE into detection pipelines allows maintainers to focus on issues for which exploitation is demonstrably feasible, supported by execution-based evidence available even in zero-day settings.

Design Implications for Agentic Exploitation.

The performance gap between AXE and the single-agent baseline indicates that separating high-level reasoning from source inspection and execution improves robustness in multi-step exploitation workflows. Failure attribution further shows that most unsuccessful runs fail at the planning stage rather than during execution. Tool augmentation helps compensate for some execution-level shortcomings by automating tasks such as endpoint discovery or payload construction, but it does not address the dominant reasoning failures observed in planning. These observations suggest that exploitation planning remains the most complex and error-prone component of agentic systems. Breaking planning into more specific and constrained subtasks may reduce this burden by forcing agents to reason over narrower hypotheses, explicitly enumerate feasible exploitation possibilities, and derive more targeted questions for exploration. Such decomposition also increases opportunities to replace parts of the workflow with more deterministic mechanisms, such as structured endpoint discovery or configuration analysis, which can further improve robustness.
Recent work in vulnerability detection and exploitation has explored similar ideas by compelling language models to reason at finer granularity and guiding them with structured or neurosymbolic reasoning, pointing to a promising direction for future agentic exploitation systems
[
24
,
23
,
25
,
26
]
.

Scope & Generalizability.

Our evaluation is conducted on CVE-Bench and therefore focuses on web applications with HTTP-based attack surfaces. However, the core evaluation model is not specific to the Web domain. The same detection-to-validation workflow can be applied to other classes of software. Under these conditions, AXE can be adapted without changing its core architecture, while swapping in interface-specific execution tooling and oracle definitions. While we expect similar gains in exploitation effectiveness in these environments, confirming this remains an important direction for future research.

Environmental and Oracle-Specific Limitations.

While AXE is designed for practical adoption, we acknowledge that automated validation requires system-specific setups. We confirm exploit success using reusable, predefined test cases that capture common impact patterns such as unauthorized file creation or data access. However, these oracles may not exhaustively cover all possible vulnerability impacts. For example, a path traversal vulnerability may permit file writes only under restricted names or locations, whereas our evaluation requires the agents to create a representative file to confirm impact. As a result, there may exist unique vulnerabilities whose effects are not captured by the available tests.

Conservative Exploit Validation.
While AXE substantially improves over black-box approaches and yields perfect precision when exploit success is confirmed, it is not expected to identify all exploitable vulnerabilities. The approach is conservative by design, i.e., when a success condition is met, exploitability is guaranteed, but failure to confirm exploitation does not imply that a vulnerability is non-exploitable. As a result, some exploitable issues may remain unverified. Nevertheless, even identifying a small fraction of truly exploitable vulnerabilities from large volumes of unreviewed reports can provide significant practical value by directing developers’ attention toward issues with confirmed security impact.

9
Conclusions

We present AXE, a grey-box agentic framework for validating reported vulnerabilities using minimal detection metadata. Given a weakness category and a source code location, AXE performs iterative planning, source inspection, and sandboxed execution to determine whether a reported issue is exploitable.

AXE outperforms SOTA black-box and a single-agent grey-box baseline, achieving substantially higher exploit success with improved efficiency. For successful exploits, AXE produces PoC reports to help with testing and remediation. Analysis of unsuccessful runs shows that failures are primarily due to high-level reasoning errors, such as misinterpreting vulnerability semantics, or missing preconditions. This indicates that future improvements should focus on strengthening semantic grounding and planning over execution.

Overall, AXE demonstrates that grey-box agentic exploitation is a practical approach for reducing vulnerability triage efforts by highlighting vulnerability reports that correspond to security issues that are immediately exploitable.

10
Ethical Considerations

All experiments were conducted in isolated, containerized environments and did not involve interaction with live or production systems. AXE is evaluated exclusively on previously disclosed vulnerabilities using publicly available benchmarks. Our work does not introduce new attack classes or disclose undiscovered vulnerabilities. While AXE automates exploit generation, its goal is to support defensive vulnerability validation and triage. We believe the benefits of improving exploitability assessment and reducing maintainer burden outweigh the potential risk of misuse.
