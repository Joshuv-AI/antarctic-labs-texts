Validated Code Translation for Projects with External Libraries
Hanliang Zhang, Arindam Sharma, Cristina David, Meng Wang, Brandon Paulsen, Daniel Kroening, Wenjia Ye, Taro Sekiyama

Abstract
Large Language Models (LLMs) have shown promise for program translation, particularly for migrating systems code to memory-safe languages such as Rust. However, existing approaches struggle when source programs depend on external libraries: LLMs frequently hallucinate non-existent target APIs and fail to generate call-enabling imports; moreover, validating semantic equivalence is challenging when the code manipulates opaque, library-defined types. We present a translation and validation framework for translating Go projects with external dependencies to Rust . Our approach combines (i) a retrieval mechanism that maps Go library APIs to Rust APIs, and (ii) a cross-language validation pipeline that establishes language interoperability in the presence of opaque library types by synthesising adapters exclusively from public library APIs, prior to validating I/O equivalence. We evaluate our system on six real-world Go repositories with non-trivial external dependencies. Our approach significantly increases both the compilation and equivalence success rate (up to 100% in the most dependency-heavy case; approx. 2x on average) by enabling validated translation that manipulate opaque, library-defined types.

3
High-Level Approach

At a high level, our pipeline performs
modular, function-level translation
:
each type definition and function is translated in isolation by an LLM, guided by a compact

dependency summary
capturing the in-scope types and the signatures of
direct callees. This design is in the spirit of prior modular LLM-based translation approaches such as

Oxidizer

[
62
]
.

3.1
Stage 1: Cross-Language Library Mapping (Challenge 1)

As discussed in Section
2
, LLMs often fail to resolve

which

Rust
crate and API best matches a given
Go
call. Even
for standard-library usage, the correct counterpart may live in a third-party
Rust crate rather than in
std
, and multiple candidate crates may
provide overlapping functionality.

To mitigate this, we augment each translation prompt with explicit
library-resolution context
.
Specifically, for every Go function we (i) extract the set of Go library APIs it invokes, and
(ii) retrieve a small set of semantically relevant
candidate Rust APIs
. These candidates are obtained via a retrieval-augmented pipeline briefly described below (and in more detail in Section
4
):

Crate matching.

First, we map each Go package
pkg
to a corresponding Rust crate
crate
. We assume an
injective
mapping: each Go package maps to a single Rust crate, and all APIs from
pkg
are resolved within
crate
. This keeps retrieval focused and prompt budgets manageable. While this can be relaxed to allow multiple crates per package, we found injectivity to be a useful practical approximation.

We obtain candidate crates by combining (i) LLM-proposed matches based on package-level
documentation summaries and (ii) keyword-based search over
crates.io
, followed by
documentation-based reranking, with mappings pre-computed before the main translation loop. For the running example in
Figure
1
, this yields
sha2
for
crypto/sha512
and

ed25519_dalek
for
crypto/ed25519
.

Per-crate knowledge base.

For each matched target crate
crate
, we precompute a crate-specific knowledge base

\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small crate}}
containing its public APIs.
For each library API used in the source function, we then query
\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small crate}}

using a textual description that combines the Go API name and its documentation. For example,
for
sha512.New
we construct:

\text{Query}_{\text{{\color[rgb]{0.3047,0.7695,0.918}\small sha512.New}}}=\text{{\color[rgb]{0.3047,0.7695,0.918}\small sha512.New}:}

“
New returns a new hash.Hash computing the SHA-512 checksum.
”,
and retrieve candidates from
\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small sha2}}
. In our system,

Sha512::new
is ranked highest.

Rust import resolution.

Given that, as explained in Section
2
, import resolution is non-trivial in Rust,
we extend our crate-specific knowledge base
\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small crate}}
to
capture not only
what
APIs exist, but also
how
they can be imported and used.
Concretely, each entry in
\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small crate}}
stores a publicly usable API together with
its documentation and one or more
valid, public import paths
.
In our running example, the top match for
sha512.New
is
Sha512::new
, returned
with the call-enabling imports
sha2::{Sha512, Digest}
, enabling the Rust translation
in Figure
1
. Likewise, the Go call
pk.Seed()
(Go line 6) is
resolved to
SigningKey::to_bytes()
(Rust line 6) via

\mathcal{K}_{\textbf{\color[rgb]{0.9766,0.4063,0.082}\small ed25519\_dalek}}
, using the correct root-level import path

ed25519_dalek::SigningKey
.

3.3
Cross-Language Validation with Opaque Library Types (Challenge 2)

To enable end-to-end validation, we adopt a
two-stage
pipeline.
First, we establish
cross-language interoperability
between the source and target languages
by synthesising adapters that allow values to cross the Go–Rust boundary.
Second, once cross-language execution becomes possible, we validate

I/O equivalence
between each Go function and its Rust translation
via differential testing.

Cross-language interoperability via a schema-backed carrier representation.

Our key idea is to bridge Go and Rust via a
shared, language-neutral
intermediate data
format (IDF) specified as a single
Protobuf
schema
T_{\mathrm{Proto}}

[
22
]
. We
synthesise this schema with an LLM from the source Go type definition: for example, given

RSAIdentity
(Figure
3
), the model generates the IDF schema in
Figure
7
.

From
T_{\mathrm{Proto}}
, the
Protobuf
compiler generates
language-specific carrier types

T_{\mathrm{Proto}}^{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
and
T_{\mathrm{Proto}}^{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
, together with
(de)serialization code that maps these carriers to and from the shared wire format. Concretely,

T_{\mathrm{Proto}}^{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
is a Go struct type (e.g.,
ProtoRSAIdentity
in
Figure
7
), while
T_{\mathrm{Proto}}^{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
is the corresponding Rust
type generated from the same schema. These carrier types are isomorphic by construction
and provide a common representation on which we can build cross-language adapters.

This reduces cross-language interoperability to synthesising two pairs of conversions around the
shared carrier representation. On the source side, we require adapters that map between the Go
types used by the original program and the Go carrier type
T_{\mathrm{Proto}}^{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
; on the
target side, we analogously require adapters between the Rust carrier type

T_{\mathrm{Proto}}^{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
and the Rust types used by the translation. In both cases, the
carrier acts as the common “meeting point” through which values can be transported across the
Go–Rust boundary via
Protobuf
serialisation.

Crucially, these conversions cannot be implemented via field-level access. Realistic code frequently
wraps library-defined objects whose internal representations are opaque or constrained by
invariants enforced by the library. For example,
RSAIdentity

(Figure
3
) and its translation
RsaIdentity

(Figure
3
) encapsulate cryptographic key types such as

ssh.PublicKey
and
russh::keys::PublicKey
, which can only be constructed and
observed through restricted public APIs rather than by directly inspecting or populating fields.

Synthesising adapters using public APIs.

Given the carrier types generated from
T_{\mathrm{Proto}}
, we synthesise the required
high-level adapters by querying our previously constructed library knowledge bases for relevant
public
APIs and constraining the LLM to assemble conversions exclusively from these APIs. This is essential for
opaque library types, where direct structural conversion is impossible and correct construction must
go through library-provided routines. For example, the Go-to-carrier adapter
(Figure
8
) serialises keys using
x509.MarshalPKCS1PrivateKey
and the
interface method
ssh.PublicKey.Marshal
. On the Rust side, the carrier-to-Rust adapter
(Figure
9
) reconstructs keys via crate-specific decoding routines (e.g.,
PKCS#1 decoding and public-key parsing).

Handling complex types.

In practice, values passed across the boundary can be arbitrarily structured, combining multiple
components—including nested user-defined wrappers and opaque library-defined objects. For
instance,
RSAKeyPair
and its Rust translation
RsaKeyPair

(Figures
11
and
11
) embed both wrapper-level fields and
library types. To scale to such cases, we generate carrier schemas and adapters modularly, reusing
previously validated conversions for each component. For example, in
Figure
(line 4), the carrier-to-Rust adapter for

RsaKeyPair
reuses the carrier-level conversion for
RsaIdentity
from
Figure
9
.

Schema and carriers validation.

Since both the carrier schema (Figure
7
) and the adapters
(Figures
8
and
9
) are LLM-synthesised, we validate them
via
round-trip
checks before using them for I/O equivalence testing. Concretely, on the Go
side we require the forward/backward adapters
f_{\mathrm{Go}\rightarrow\mathrm{Proto}}
and

f_{\mathrm{Proto}\rightarrow\mathrm{Go}}
(between the original
Go
types and
T_{\mathrm{Proto}}
) to satisfy
f_{\mathrm{Proto}\rightarrow\mathrm{Go}}(f_{\mathrm{Go}\rightarrow\mathrm{Proto}}(v))=v
on representative
values
v
(e.g., obtained from unit-test executions), providing evidence that the carrier preserves
enough information to reconstruct the original Go value. Once Go
\leftrightarrow
Proto roundtripping succeeds, we validate full cross-language interoperability by composing the one-sided adapters into end-to-end transformations between the source and target types:
f_{\mathrm{Rust}\rightarrow\mathrm{Go}}(f_{\mathrm{Go}\rightarrow\mathrm{Rust}}(v))=v
. Passing these checks is a necessary precondition for transporting inputs and outputs across the language boundary, after which we can meaningfully test end-to-end I/O equivalence.

On round-trip checks failure, we regenerate adapters while keeping the translation fixed. If retries exceed a predefined budget, we regenerate the translation and revalidate.

Differential I/O validation.

Once type interoperability is established for a function’s input and output types, we reuse the
validated adapters to execute the Go source and Rust translation on the same unit-test inputs (mapped through the
carrier representation), and compare their observable outputs. This enables
repository-level differential testing even when translated code manipulates
library-defined types that would otherwise be inexpressible across the language
boundary.

If I/O validation fails, we freeze the translated types, function signatures, and
adapters, and regenerate only the function body—up to a fixed budget—until the
validation succeeds or the budget is exhausted.

As shown in

We make use of the structural representation of the

to build
ApiIndex
for a Rust crate. For this purpose, we systematically enumerate its publicly usable API surface
together with
call-enabling

trait-scoped method callability. Our algorithm therefore traverses the public module tree, resolves

types, traits, and methods. For trait methods, we initially record placeholder trait references and
later rewrite them to concrete import paths in a final revision pass. We show that all generated

4.2
Constructing the Knowledge Base

From the per-crate inventory
ApiIndex
, we build a knowledge base
\mathcal{K}
for retrieving
relevant
API candidates from natural-language queries. Concretely,
\mathcal{K}
ranks entries by relevance to a query
Q
(e.g., derived from Go documentation and signatures) and returns top matches with their call-enabling import paths.

Two-stage retrieval and reranking.

Directly applying an LLM reranker over the full
ApiIndex
is infeasible for
real-world crates, which may expose thousands of APIs. Instead, we adopt a
standard two-stage information retrieval pipeline: an efficient first-stage
retriever followed by a more accurate reranker.

Given a query
Q
, we first apply a dense bi-encoder retriever in the style of
Dense Passage Retrieval (DPR)
[
30
]
to score API entries by
semantic similarity between
Q
and their documentation, and select a small
candidate set (top-
k
, with
k=35
in our implementation beyond which we observed diminishing returns in recall). We then rerank these candidates using a stronger cross-encoder model in the style of
BERT-based reranking
[
38
]
. Finally, we apply an LLM-based
list-wise reranker to obtain the final ordering
[
45
]
.

5
Validating the Translation

In this section, we develop a validation framework for checking equivalence of function translations in the presence of library dependencies.
As discussed in Section
2
, validating Go-to-Rust translations remains challenging even when the generated code compiles, because the two languages have incompatible value representations and pervasive library-defined types. To support end-to-end validation, we employ a
two-stage
pipeline: we first establish
cross-language interoperability

by synthesising adapters that safely serialize values across the Go–Rust boundary, and then leverage these validated adapters to check
I/O equivalence
between each Go function and its Rust translation via differential testing on unit-test derived inputs.

5.1
Cross-Language Interoperability

Our goal is to enable cross-language execution for validation: given a Go value of a type

T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
, we must construct a
corresponding Rust value of the translated type
T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
, and conversely recover a
Go value back. We model this as synthesising a pair of
cross-language adapters

\mathcal{A}_{T}:T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}\qquad\mathcal{A}^{-}_{T}:T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}\rightarrow T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}},

where
\mathcal{A}_{T}
lifts Go unit-test inputs/outputs into Rust for downstream differential
testing, and
\mathcal{A}^{-}_{T}
supports round-trip validation. In particular, the composition

\mathcal{A}^{-}_{T}\circ\mathcal{A}_{T}
should preserve observable Go values, providing evidence
that (i) the translated Rust type does not discard semantically relevant information and
(ii) the adapters are behaviour-preserving on realistic inputs.

Directly generating
\mathcal{A}_{T}
and
\mathcal{A}^{-}_{T}
is difficult because Go and Rust values
have incompatible representations, and library-defined types are often opaque (private fields)
and only manipulable via public APIs. To address this, we
introduce a shared
intermediate representation
based on
Protobuf
,
T_{\mathrm{Proto}}
, which
serves as a language-neutral carrier for values crossing the Go–Rust boundary.

Protobuf
schema generation.

We next describe how the carrier schema
T_{\mathrm{Proto}}
is synthesised from
a composite source Go type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}

A key distinction is between
language- or library-defined
composite types and

user-defined
ones. With respect to the former, given a composite type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
, for each one of its fields the LLM selects an appropriate
Protobuf
encoding. Primitive Go types (e.g.,
int32
,
string
,
bool
) are mapped directly to their corresponding
Protobuf
scalar types. In contrast, complex or opaque fields—particularly library-defined types with private internal representations—are conservatively represented as byte arrays. This byte-array fallback ensures that values remain transmissible across the language boundary even when their internal structure is inaccessible or lacks a natural
Protobuf
analogue.

For user-defined composite types with nested user-defined dependencies, we
generate schemas compositionally in dependency order.
The LLM
incrementally constructs
schemas for types that reference previously processed ones.
When generating a schema for a type
T
that refers to another user-defined
type
T^{\prime}
, we instruct the LLM to reuse the existing
Protobuf
definition of

T^{\prime}
, ensuring consistency across schemas and avoiding redundant
declarations.

This structural exposure of user-defined composites is crucial for later stages: it enables the synthesis of glue code that composes field-level conversions and systematically reuses
existing library APIs when mapping between
Go
,
Rust
, and the carrier
representation.
By contrast, library-defined types—whose internal structure is often opaque to
clients—are treated conservatively and handled via API-based adapters rather
than field-level access.

High-level glue code generation.

From the
Protobuf
schema, the
Protobuf
compiler generates
language-specific carrier types

T_{\mathrm{Proto}}^{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
and
T_{\mathrm{Proto}}^{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
, together with low-level serialization and deserialization routines that encode values into (and decode values from) the shared wire format.
These compiler-generated types and routines provide a lightweight interoperability layer, avoiding explicit FFI manipulation.
At a conceptual level, the schema
T_{\mathrm{Proto}}
defines a language-neutral carrier that is realised concretely in both
Go
and
Rust
.
We therefore treat
T_{\mathrm{Proto}}
as a type that
exists in both
languages
, and reduce the interoperability problem to synthesising

high-level glue code
that connects
T_{\mathrm{Proto}}
to the source
type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
and the translated type
T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
.

With
T_{\mathrm{Proto}}
fixed, cross-language interoperability reduces to generating
language-local
glue code converting between each
T_{\mathrm{Lang}}
and
T_{\mathrm{Proto}}
:

\mathcal{A}_{T_{\mathrm{Lang}}}:T_{\mathrm{Lang}}\rightarrow T_{\mathrm{Proto}}\qquad\mathcal{A}^{-}_{T_{\mathrm{Lang}}}:T_{\mathrm{Proto}}\rightarrow T_{\mathrm{Lang}},

where
\mathrm{Lang}\in\{\textsc{Go},\ \textsc{Rust}\}
. These adapters bridge rich, language-specific data structures and the shared
Protobuf
encoding.

By construction,
T_{\mathrm{Proto}}
is lightweight, containing only
Protobuf
-native
primitives like scalars, enumerations, byte arrays, and shallow aggregates.
In contrast,
T_{\mathrm{Lang}}
types may be deeply nested, include user-defined structures, and depend on library types accessible only through public APIs.

We synthesise the glue functions using an LLM, prompted with the definitions of

T_{\mathrm{Lang}}
and
T_{\mathrm{Proto}}
. For composite types, we instruct the model to generate glue
code compositionally, reusing existing conversions whenever possible and relying on retrieved
library guidance when necessary:

1.

Reuse of existing adapters.
If
T_{\mathrm{Proto}}
(or
T_{\mathrm{Lang}}
) depends on a
nested type
U
, we reuse previously generated adapters for
U
to avoid duplicating conversion
logic and to maintain consistency across the repository.

2.

Knowledge-guided library conversions.
If
T_{\mathrm{Lang}}
contains a type from library
lib
, we augment the prompt with APIs retrieved from the corresponding
knowledge base
\mathcal{K}_{\textit{lib}}(\text{Query}_{T_{\mathrm{Lang}}\leftrightarrow T_{\mathrm{Proto}}})
.
The query
\text{Query}_{T_{\mathrm{Lang}}\leftrightarrow T_{\mathrm{Proto}}}
includes the definitions of

T_{\mathrm{Lang}}
and
T_{\mathrm{Proto}}
to steer the model towards call-enabled constructors,
accessors, and (de)serialization routines.

Despite this guidance, LLM-generated glue code remains fallible: the model may select
inappropriate APIs, introduce type mismatches, or produce code that compiles but violates semantics at runtime. We therefore validate adapters via round-trip checking before downstream equivalence testing, as described next.

Round-tripping validation.

Since the carrier schema
T_{\mathrm{Proto}}
, the translated Rust type
T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
, and the
glue functions
\mathcal{A}_{T_{\mathrm{Lang}}}
and
\mathcal{A}^{-}_{T_{\mathrm{Lang}}}
are all synthesised by an
LLM, we explicitly validate that they preserve information before using them for downstream
equivalence checking. Taking the source type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
as ground truth, we perform
validation in two phases: we first validate Go
\leftrightarrow
Proto conversions, and only then
validate full Go
\leftrightarrow
Rust interoperability.

Go
-side roundtripping.

In the first phase, we validate that Go-side glue code roundtrips values through the carrier representation without loss:

Definition 1
(
Go
-side round-trip property)

Given a
Go
type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
and transformations

\mathcal{A}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}:T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow T_{\mathrm{Proto}}
and

\mathcal{A}^{-}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}:T_{\mathrm{Proto}}\rightarrow T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
,
the following property holds:

\forall v.\quad\mathcal{A}^{-}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}\!\bigl(\mathcal{A}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}(v)\bigr)=v.

Satisfying Definition
1
implies that the forward embedding

\mathcal{A}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}
is injective on the tested values, providing evidence that the
generated schema
T_{\mathrm{Proto}}
captures all semantically relevant information present in

T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
(i.e., no loss or unintended normalisation is introduced by the carrier).

Establishing this universally quantified property is infeasible in general,
so we approximate it using concrete values
\overline{v}
extracted from existing unit tests. A failure indicates
either (i) an inadequate carrier schema or (ii) incorrect Go-side glue code, and triggers regeneration
of
both

T_{\mathrm{Proto}}
and the Go
\leftrightarrow
Proto adapters.

Full roundtripping.

Once Go
\leftrightarrow
Proto roundtripping succeeds, we validate full cross-language
interoperability by composing the one-sided adapters into end-to-end transformations between the
source and target types:

\mathcal{A}_{T}=\mathcal{A}^{-}_{T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}}\circ\mathcal{A}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}\qquad\text{and}\qquad\mathcal{A}^{-}_{T}=\mathcal{A}^{-}_{T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}}\circ\mathcal{A}_{T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}}.

We then validate the corresponding round-trip property:

Definition 2
(Full round-trip property)

Given a
Go
type
T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
and transformations

\mathcal{A}_{T}:T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
and

\mathcal{A}^{-}_{T}:T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}\rightarrow T_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}
, the following property holds:

\forall v.\quad\mathcal{A}^{-}_{T}\!\bigl(\mathcal{A}_{T}(v)\bigr)=v.

As before, we approximate Definition
2
by testing it on a finite set of values. Since the first phase has already established
the correctness of Go
\leftrightarrow
Proto conversions, failures in this phase can be attributed to
the Rust-side artefacts (the translated type
T_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}
or the Rust
\leftrightarrow
Proto glue).
Accordingly, when the full round-trip check fails, we regenerate only the Rust-side adapters,
avoiding unnecessary recomputation of
T_{\mathrm{Proto}}
and the validated Go-side glue code.

5.2
Validation of I/O Equivalence

With interoperability established (Section
5.1
), we validate
observable behaviour
via differential testing. Given a Go function
f
and its LLM-generated Rust translation
g
:

f:I_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow O_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\qquad g:I_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}\rightarrow O_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}.

For simplicity, we assume single input and output types throughout this section.
Since inputs and outputs may involve
opaque library-defined types, we validate I/O equivalence by comparing executions via the adapters from
Section
5.1
, which transport values across the Go–Rust boundary:

Definition 3
(I/O Equivalence)

Given a
Go
function
f
and the
Rust
translation
g
, as well as
the transformations generated in the previous step,

\mathcal{A}_{I}:I_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow I_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}\qquad\mathcal{A}_{O}:O_{{\color[rgb]{0.3047,0.7695,0.918}\textsc{Go}}}\rightarrow O_{{\color[rgb]{0.9766,0.4063,0.082}\textsc{Rust}}}

then
f
and
g
are I/O equivalent if
\forall v.\mathcal{A}_{O}\bigl(f(v)\bigr)=g\bigl(\mathcal{A}_{I}(v)\bigr)
.

I/O equivalence on observed inputs.

We assume the source repository includes unit tests, whose executions yield concrete I/O examples

\overline{(i,o)}
for
f
. We treat these examples as a behavioural specification and validate I/O
equivalence by checking that
g
matches
f
on the observed inputs. Concretely, letting

\overline{i}
denote the set of Go inputs extracted from unit-test runs, we report I/O equivalence
for
(f,g)
when Definition
3
holds for every
v\in\overline{i}
(for
\overline{i}
the inputs in
\overline{(i,o)}
).

Interpreting the guarantee.

Our checks do not establish full semantic equivalence between
f
and
g
; rather, they provide evidence that translation preserves behaviour on observed inputs. To interpret this at the Go-level, we apply the inverse adapter
\mathcal{A}^{-}_{O}
to the Rust output, yielding:

Lemma 1
(Go-level behavioural agreement on observed inputs)

Assume the full round-trip property (Definition
2
) holds for the output type
O
on all values in

\{f(v)\mid v\in\overline{i}\}
, and assume I/O equivalence holds for all
v\in\overline{i}
.
Then for every
v\in\overline{i}
,

f(v)\;=\;\mathcal{A}^{-}_{O}\!\left(g\left(\mathcal{A}_{I}(v)\right)\right),

i.e., on the observed inputs,
f
produces the same outputs as the function

\mathcal{A}^{-}_{O}\circ g\circ\mathcal{A}_{I}
.

Proof

Fix any
v\in\overline{i}
. By I/O equivalence (Definition
3
) we have

\mathcal{A}_{O}\bigl(f(v)\bigr)\;=\;g\bigl(\mathcal{A}_{I}(v)\bigr)
.
By the full round-trip property for outputs (Definition
2
),
\mathcal{A}_{O}
and

\mathcal{A}^{-}_{O}
are defined on
f(v)
and satisfy

\mathcal{A}^{-}_{O}(\mathcal{A}_{O}(f(v)))=f(v)
. Applying
\mathcal{A}^{-}_{O}
to both sides of the
above equation yields
f(v)\;=\;\mathcal{A}^{-}_{O}\!\left(g\left(\mathcal{A}_{I}(v)\right)\right)
.
Since
v
was arbitrary, the claim holds for all
v\in\overline{i}
.

Proposition
1
implies the Rust implementation can replace the Go function on observed inputs, even when they involve opaque library types.

8
Conclusions

We proposed a library-aware, RAG-guided framework for Go to Rust
translation. It maps external Go APIs to Rust using a curated knowledge
base of public, crate-root-reachable items, then validates results in two
steps: cross-language round trips followed by differential I/O. On projects
with external dependencies, this improved both compilation and equivalence
success rate (approximate 2x on average) by enabling translation for
functions with external dependencies.

Appendix 0.A
An
ApiIndex
Construction Algorithm for
Rust

We first formalize the notions of valid import path and re-exports.

Paths.

A path
\mathit{{p}}
is a fully-qualified name used to reference an API item within a
crate. Intuitively, a path begins at the crate root module and traverses zero
or more nested submodules before terminating at an item
\mathit{{i}}
.
However, not every syntactically well-formed path is a
valid import path
.
In Rust, each module has an associated visibility, and items contained within a
private module are not accessible to external clients. Consequently, a path is
invalid whenever it passes through a module that is not visible from the crate
root under Rust’s privacy rules.

Definition 4
(Valid import path)

Let
m_{0}
be the root module of a crate. A syntactic path

p=m_{0}::m_{1}::\cdots::m_{k}::i

is a
valid import path
if every intermediate module on the path is
publicly visible, i.e.

\mathsf{Valid}(p){:=}\forall j\in\{1,\ldots,k\}.\ \mathsf{Public}(m_{j}).

Re-exports.

Rust additionally allows developers to expose items through alternative paths
using re-exports. A re-export statement
pub use

p
introduces an
alias for the item referenced by
p
, making that item accessible from the
re-exporting module under a new path. Re-exports are widely used to define clean
public APIs that hide internal module hierarchies, and to surface selected items
from transitive dependencies as part of a crate’s public interface.

Definition 5
(Re-export resolution)

Let
m
be a module and let
p
be a path. If
p
resolves to an item
i
,
written
p\Downarrow i
, then a re-export declaration

\texttt{\color[rgb]{0.9766,0.4063,0.082}\small pub use}\ p
in
m
induces an alias path
m::i^{\prime}
such that

(p\Downarrow i)\;\Rightarrow\;(m::i^{\prime}\leadsto i).

Constructing
ApiIndex
.

For example, in
Figure 1
the API
SigningKey

is defined in the internal module
ed25519_dalek::signing
. Since

signing
is private, the defining path is not a valid import path for
crate users. The crate therefore re-exports
SigningKey
at the root,
making
ed25519_dalek::SigningKey
a valid import path. Re-exports are
also commonly used to propagate APIs from dependencies. For instance,

Sha512::new
is available through the trait
sha2::Digest
,
which is defined in the transitive dependency
digest
.

To construct the
ApiIndex
for a crate, we must also analyse its transitive dependencies, as
pub use
re-exports can expose dependency-defined APIs as part of the crate’s public interface. As shown in
Algorithm 1
, we compute
ApiIndex
s for dependencies in post-order, ensuring they are available before processing the current crate. These precomputed maps are passed into the extraction of the target crate’s
ApiIndex
, which is returned as the final result.

The procedure for computing a per-crate
ApiIndex
is detailed in
Algorithm 2
. The main entry point,
ComputeItemsMap
, first invokes
traverseModule
to construct an initial
ApiIndex
that may contain placeholder import paths for method APIs. It then performs a revision pass to resolve these placeholders into concrete import paths, yielding a fully resolved
ApiIndex
.

Sub-routine for traversing a crate

The recursive subroutine
traverseModule
enumerates all publicly
reachable modules and items within a crate. It maintains the current module path
prefix
\Pi
, representing the sequence of enclosing modules from the crate
root to the current module, and uses this prefix to construct import paths for
each discovered API.

For an external re-export of the form

\texttt{\color[rgb]{0.9766,0.4063,0.082}\small pub use}\ n::\ldots::i
where
n\neq m
and
m
denotes the
current crate, the root
n
refers to a crate in the transitive dependency
set. In this case, we retrieve the API entry for
i
from the precomputed

CratesMap
and record it under the re-exported path
\Pi^{\prime}::i
,
reflecting its publicly exposed location in the current crate.

For an internal re-export of the form
\texttt{\color[rgb]{0.9766,0.4063,0.082}\small pub use}\ m::\ldots::i
, where the referenced path originates from
the current crate root, we treat
i
as locally defined within the current
module. This allows internal re-exports to be processed uniformly with
module-local public items during traversal.

Finally, for each public item in the current module—together with the items
introduced via internal re-exports—we either extract its associated
documentation (for types and traits) or, if the item is itself a submodule,
recursively invoke
traverseModule
to continue the traversal.

Sub-routine for extracting API

We extract traits, types, and methods as outlined in
Algorithm 3
. For method APIs, although the input path
\Pi
identifies the type with which these methods are associated, it cannot be used directly to compute their correct import paths. This limitation arises from Rust’s trait system: the use of a trait method is only permitted when the defining trait
\mathbb{T}
is in scope, which requires importing
\mathbb{T}
itself. Consequently, the appropriate import path for a method API can only be determined after all traits within the library have been identified and their import paths established. To accommodate this dependency, we initially record method APIs with a placeholder import path corresponding to the defining trait
\mathbb{T}
, to be resolved in a later stage.

Final stage of revision

After constructing an initial
ApiIndex
that may contain placeholder import paths for method APIs, the main procedure
ComputeItemsMap
performs a final revision pass. During this pass, each placeholder trait reference is replaced with the concrete import path computed for the corresponding trait, yielding a fully resolved
ApiIndex
for the target library.

Soundness of Path Generation.

Our
ApiIndex
construction enumerates candidate import paths by traversing the
public module tree and collecting all paths to reachable items, additionally
including paths introduced via
pub use
re-exports.

Lemma 2
(Validity of generated import paths)

Every path
p
produced by our
ApiIndex
construction satisfies

\mathsf{Valid}(p)
.

Proof
(sketch)

A path is produced in one of two ways.
(1)
Direct paths:
These are obtained by traversing the module hierarchy
starting from the crate root and following only publicly visible submodules.
Thus, every prefix module on such a path is public by construction, so

\mathsf{Valid}(p)
holds.
(2)
Re-exported paths:
A re-export path is introduced only by a

pub use
declaration occurring in some publicly reachable module.
Since the re-export is itself public, the resulting alias path is externally
visible from the root, hence
\mathsf{Valid}(p)
holds.
