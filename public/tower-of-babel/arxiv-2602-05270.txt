PatchGuru : Patch Oracle Inference from Natural Language Artifacts with Large Language Models CCS: Software and its engineering Software defect analysis
Thanh Le-Cong, Bach Le, Toby Murray, Michael Pradel, Cristian Cadar

Abstract
. As software systems evolve, code changes may inadvertently introduce unintended behavioral changes. Validating patches against their intended behaviors remains challenging due to the lack of adequate and executable specifications: regression tests are often incomplete, while natural language (NL) descriptions of patch intent are informal and non-executable. This paper presents PatchGuru , the first automated technique that infers executable patch specifications from real-world pull requests (PRs). Given a PR, PatchGuru leverages large language models (LLMs) to distill developer intent from its NL artifacts and synthesizes an under-approximate yet practical form of patch specifications called patch oracles , which capture key behavioral patch properties as runtime assertions within comparison programs that merge pre- and post-patch versions. The benefits of patch oracles are threefold: (1) they concentrate on behaviors affected by the patch, making their inference more tractable and their validation more efficient; (2) they are expressed as runtime assertions, enabling automated validation; and (3) they are written within comparison programs combining both pre- and post-patch versions, thus allowing cross-version properties to be specified. By comparing the behavior of pre- and post-patch versions of modified functions against these inferred oracles, PatchGuru iteratively refines the oracles, identifies inconsistencies when violations arise, filters them via a self-review mechanism, and eventually creates bug reports to developers. We evaluate PatchGuru on 400 recent PRs from four widely used open-source Python projects. The evaluation shows that PatchGuru reports 39 warnings with a precision of 0.62, yielding 24 confirmed true positives, including 12 previously unknown bugs. Following our reports, developers confirmed all unknown bugs and actively addressed them, submitting pull requests for 11 out of the 12. Compared to the state-of-the-art patch validation technique Testora, PatchGuru detects 17 more bugs (24 vs. 7) while increasing precision from 0.32 to 0.62. PatchGuru has a reasonable average cost of around 8.9 minutes and USD 0.07 per PR. We envision PatchGuru as a complement to existing code review and regression testing practices, providing both explicit documentation and automated validation of patch intent.



1.
Introduction

Software systems continuously evolve to meet the changing needs of users and businesses.
This evolution is primarily realized through patches that aim to fix bugs, improve performance, and introduce new functionality.
Ironically, patches, which are intended to improve the software, can inadvertently introduce bugs and even vulnerabilities, leading to catastrophic consequences.
For example, a seemingly minor update in CrowdStrike caused a severe regression that disrupted the functionality of approximately 8.5 million devices
(
36
)
, and a small patch in OpenSSL caused havoc by introducing the HeartBleed security vulnerability
(
15
)
.
Therefore, it is crucial to validate the correctness of patches against their intended behavior prior to their integration into the codebase.

Patch validation is facing a long-standing challenge: the lack of a precise and executable specification that captures the intended behavior of a patch.
A standard option for partly specifying the intent of a patch is through regression tests, which are designed to ensure that previously correct behavior remains unaffected.
However, maintaining high-quality regression tests is a labor-intensive and expertise-demanding task, and regression tests are often incomplete in practice
(
39
)
.
Moreover, as regression tests are not targeting the specific changes introduced by individual patches, they often do not check whether intended behavioral changes are actually realized by the patches.
This “specification gap” allows buggy patches that satisfy existing regression testing, yet introduce unintended behaviors or preserve behavior that the developer actually intends to change.

An alternative to formally specifying the intended behaviors of patches is natural language (NL) documentation written by developers, e.g., commit messages and descriptions of pull requests (PRs).
Unfortunately, these NL artifacts are informal, ambiguous, and non-executable, leaving them unsuitable for automated validation of patch correctness.
Consequently, manual code review
(
2
;
27
)
is commonly employed to assess whether a patch aligns with its documented intent.
Code review, however, is both time-consuming and error-prone, and its effectiveness depends heavily on reviewers’ expertise, workload, and contextual understanding.
These limitations can result in overlooked inconsistencies and the eventual integration of incorrect patches
(
20
)
.

To bridge this gap, Cadar et al. recently proposed the idea of
patch specifications

(
7
)
.
Unlike traditional specifications that describe the overall behavior of a piece of code, a patch specification defines the behavioral delta between the pre-patch (
\mathcal{F}_{pre}
) and post-patch (
\mathcal{F}_{post}
) versions of a program.
For instance, a patch specification could state that for all inputs
x
,
\mathcal{F}_{post}(x)
must return the same value as
\mathcal{F}_{pre}(x)
except when
x
is a negative number, in which case
\mathcal{F}_{pre}(x)
raises an exception, whereas
\mathcal{F}_{post}(x)
returns
-x
.
Patch specifications thus provide a principled and expressive foundation for automated patch validation.
However, their practical adoption is currently limited by the substantial manual effort required to write them
(
7
;
35
)
.

This paper presents
PatchGuru
, the first automated technique for inferring a form of patch specifications from real-world patches.
In particular,
PatchGuru
infers what we call
patch oracles
, an under-approximate yet practical form of patch specifications that capture key behavioral properties of patches.
We design patch oracles as runtime assertions checked in a
comparison program

(
13
)
, which is a synthetic program that contains the pre- and post-patch versions of a modified function as independent functions, allowing for direct comparison of their behavior.
The benefits of this design are threefold.
First, patch oracles mainly focus on behaviors affected by the patch, making their inference more tractable and their validation more efficient compared to whole-program specifications, e.g., using regression tests or formal specifications.
Second, their representation as assertions enables direct execution within comparison programs, providing automated patch validation through dynamic analysis.
Third, the use of comparison programs allows
PatchGuru
to specify cross-version properties between pre- and post-patch behaviors, which are essential for characterizing patch intent, yet difficult to express using traditional specification approaches.

To infer these patch oracles, our key idea is to utilize NL artifacts associated with patches, such as commit messages, descriptions, and code review comments, which typically contain rich information about the developers’ intent behind a change.
In particular,
PatchGuru
leverages the capabilities of Large Language Models (LLMs) to understand and synthesize code from NL artifacts, and employs dynamic analysis techniques to iteratively refine and validate the inferred oracles.
Specifically, given a PR,
PatchGuru
distills relevant NL artifacts and leverages LLMs to synthesize an executable patch oracle.
The inferred patch oracle is executed and iteratively refined to improve its adequacy by generalizing assertions and exploring edge cases.
When assertion failures arise,
PatchGuru
adopts an LLM-based self-reviewing mechanism to analyze the failures, identify potential inconsistencies between the code changes and the inferred specification, and generate a report for developers.

Our evaluation applies
PatchGuru
to 400 real-world PRs from four popular and complex open-source projects, showing that it finds bugs that have remained undetected during code review and regression testing.
In total,
PatchGuru
identifies 24 bugs, i.e., true inconsistencies between code changes and their intended behaviors, including 17 code bugs and 7 documentation bugs.
Among these, 12 are previously unknown bugs that still exist in the latest project releases.
Following our reports, developers confirmed all these previously unknown bugs and actively addressed them.
They submitted pull requests for fixing 11 of the 12 bugs; among these, 7 have already been merged, and 4 are waiting for final approval.
Compared to Testora
(
34
)
, a state-of-the-art technique for patch validation,
PatchGuru
detects 17 more bugs (24 vs. 7) while reducing false positives from 68% to 38%.
Additionally,
PatchGuru
-inferred patch oracles kill significantly more (+21%) mutants than existing regression tests.
By combining both, the mutation score increases by 41%, demonstrating that
PatchGuru
-inferred oracles effectively complement existing regression tests.
Finally, we show that the costs of using
PatchGuru
are acceptable for real-world deployment, with an average inference time of 8.9 minutes and an average LLM cost of $US 0.07 per PR.

In summary, this paper makes the following contributions:

•

Idea.
We are the first to present the idea of inferring patch oracles from NL artifacts associated with patches, providing a novel way of bridging the specification gap in patch validation.

•

Technique.
We design and implement
PatchGuru
, an automated technique that synthesizes patch oracles as comparison programs with runtime assertions, iteratively refines them through dynamic analysis, and detects inconsistencies between code changes and their intended behaviors.

•

Evaluation.
We conduct a comprehensive evaluation of
PatchGuru
on 400 real-world PRs from popular open-source Python projects, demonstrating its effectiveness in inferring adequate patch oracles and identifying real bugs, along with its practical efficiency.

•

Artifacts.
We release
PatchGuru
as open-source, along with the dataset of PRs, inferred oracles, and detected inconsistencies to facilitate future research
(
1
)
.

2.
Problem Formulation

Before presenting our approach, we formally define the problem that
PatchGuru
aims to solve.

Input:

PatchGuru
takes a PR, which typically has two main components:
(1) the code patch
\mathcal{C}
, representing the changes to the codebase, and
(2) the NL artifacts
\mathcal{D}
, including the PR description, commit messages, and related discussions that provide the high-level rationale for the change.

Output:
The goal of
PatchGuru
is two-fold:
(i) to derive an executable patch oracle
\mathcal{O}
from the NL artifacts
\mathcal{D}
of the PR under analysis, and
(ii) to verify whether the code patch
\mathcal{C}
is consistent with the inferred oracle
\mathcal{O}
.
The final output of
PatchGuru
is a tuple
(\mathcal{O},\mathcal{R})
, where
\mathcal{O}
is the inferred patch oracle and
\mathcal{R}
is a validation report indicating whether the code patch
\mathcal{C}
adheres to the inferred oracle
\mathcal{O}
.
In the case of inconsistencies,
PatchGuru
will raise a warning and provide
\mathcal{O}
as reproducible evidence of the inconsistencies along with
\mathcal{R}
as natural language explanations that describe the inconsistencies and explain why they arise.

Our problem formulation differs from existing techniques to reason about code changes.
Compared to traditional regression testing, which reasons about correctness in general, we specifically target the behavioral changes introduced by a PR.
Moreover, the inferred patch oracles can detect cases where the patch fails to change behavior as intended, whereas regression tests are designed to ensure that existing behavior remains unchanged.
Compared to ChangeGuard
(
13
)
, which introduced the idea of comparison programs, we go beyond determining whether a code change introduces any behavioral differences, but instead reason about the consistency of the intent expressed in the NL artifacts and the code change.
Finally, compared to the recent Testora technique
(
34
)
, our formulation not only checks for PRs that introduce unintended behavioral changes, but also validates that the intended changes are correctly implemented.
Our evaluation (§
4
, RQ2) shows that this capability allows
PatchGuru
to detect bugs missed by Testora.

We envision that
PatchGuru
would augment current development practices.
When
PatchGuru
flags inconsistencies between the inferred patch oracle and the actual implementation, this can help developers in two ways:
(1) if the inconsistencies arise from code bugs, developers can proactively fix these issues, ensuring that bugs are remediated prior to being merged into the main codebase;
(2) if the inconsistencies stem from ambiguous or incomplete NL descriptions,
PatchGuru
prompts developers to clarify their intent, which can improve the quality of the project documentation.
A key benefit of
PatchGuru
is that it provides actionable feedback at the moment of peak developer receptivity, when the context of the change is still in the developer’s mind.
This feedback minimizes the “context-switching” penalty typically associated with late-stage bug discovery, enabling developers to address problems before subsequent changes are introduced, thereby avoiding complex bug fixing efforts that may result from compounded code changes
(
14
)
.

Approach

’s workflow, which consists of three main phases coordinated by an orchestrator.
Given a PR (§

),
PatchGuru
first employs an LLM-based inference module (§
3.2
) to derive an initial patch oracle from the PR’s NL artifacts.
The inferred oracle includes runtime assertions that encode the intended behavior described in the PR, together with test inputs that trigger these behaviors.
If the behavior of the code patch is consistent with the inferred oracle,
PatchGuru
enters an iterative oracle enhancement phase (§
3.3
) to improve the completeness of the inferred oracle.
During this phase,
PatchGuru
generalizes initial assertions to cover broader input domains, and synthesizes additional test inputs to explore edge cases.
At any point, if inconsistencies are detected,
PatchGuru
triggers a self-review phase (§
3.4
), which applies an LLM-as-a-judge mechanism to distinguish true inconsistencies from false positives.
Throughout the workflow, the orchestrator (§
3.5
) executes inferred oracles, monitors runtime behavior, repairs incorrect oracles, and orchestrates transitions between phases.

3.1.
Target Pull Requests

To keep the scope of our approach focused and manageable,
PatchGuru
targets PRs that meet specific criteria.
First, we exclude PRs that modify only documentation, such as files in documentation directories, code comments, or README files.
To this end, we perform an AST-based comparison between the pre- and post-patch versions of the codebase to identify executable code changes and filter out modifications to documentation files.
Then, we select only PRs with at least one change made to executable code.
Second, we focus on PRs that modify a single function within the codebase.
This restriction simplifies the oracle inference and validation process, as it allows us to concentrate on the behavioral changes introduced by a single function modification.
We acknowledge that this restriction as a limitation of
PatchGuru
and will further discuss our decision in §
5
.

3.2.
Oracle Inference

The goal of the oracle inference phase is to formalize the developer’s intent, as expressed in the NL artifacts of a PR, into an executable patch oracle.
The resulting oracle consists of runtime assertions paired with test inputs that collectively characterize the intended behavior of the modified function.
We designed these assertions to capture the behavioral relationship between the pre-patch and post-patch versions of the function including three types of properties:
(1)
preserved behavior
assertions that specify identical behavior between the pre- and post-patch versions for certain inputs;
(2)
changed behavior
assertions that specify modified behaviors for specific inputs; and
(3)
new behavior
assertions that describe entirely new functionalities added by the patch.
For example, Figure
2
show a PR aiming to fix an issue where the
fields.Url
function does not accept file URLs without hostnames.
Consequently,
PatchGuru
infers a patch oracle that asserts the following properties:
(1) for valid URLs, both pre- and post-patch versions should not yield any errors and return them as-is (line 9);
(2) for invalid URLs, both versions should raise
ValidationError
(line 15); and
(3) for file URLs without hostnames, the pre-patch version should raise a
ValidationError
, while the post-patch version should accept them as valid URL (lines 21 and 27).

To this end, in this phase,
PatchGuru
performs three steps: (1) collecting relevant NL artifacts, (2) extracting code context of the modified function from the pre-patch version, and (3) synthesizing assertions and test inputs from the collected information.

3.2.1.
Gathering Natural Language Artifacts

PatchGuru
operates under the presumption that developer intent is primarily conveyed through NL artifacts. Accordingly, it collects all PR-associated textual information, including the PR title, description, and contributor comments.
In addition, we also retrieve issues linked within the PR.
For instance, in our illustrative example, the original PR description does not specify that
field.url
should accept file URLs without hostnames; this intent was instead documented in the referenced issue #2249.
As external references may contain irrelevant or misleading information,
PatchGuru
applies an LLM-based distillation step that summarizes and extracts only the information most relevant to the PR.

3.2.2.
Extracting Context of Modified Functions

Although NL artifacts form the primary input for oracle inference, adequate code context is essential for understanding pre-patch behavior and for generating type-compatible test inputs.

PatchGuru
therefore extracts three categories of code context: (1) the complete pre-patch implementation of the modified function, (2) its internal and external dependencies, and (3) the enclosing class implementation, if the function is a method. To extract the modified function,
PatchGuru
identifies the modified file and the range of deleted lines in the patch, locates the enclosing function definition, and retrieves its full pre-patch implementation.
Internal dependencies are identified by parsing the modified file into an abstract syntax tree (AST) and extracting top-level function and class definitions.
External dependencies are obtained by analyzing import statements and retrieving the corresponding modules.
Since oracles are executed in isolation, we convert access paths to absolute references to ensure correct linkage.
If the modified function is part of a class,
PatchGuru
also extracts the complete class definition to provide additional context and ensure the correct initialization of instance variables.

3.2.3.
Patch Oracle Synthesis

Using the collected NL artifacts and code context,
PatchGuru
invokes an LLM to synthesize an initial patch oracle based on a structured prompt template (see details in our replication package
(
1
)
). The prompt consists of four components:

(1)

Role Definition
is a system prompt that frames the LLM as an expert software developer tasked with inferring patch oracles from NL artifacts and code context.

(2)

Guidelines
contain detailed instructions that outline the steps the LLM should follow to perform the oracle inference task.
These guidelines were initially generated via a meta prompt
(
6
)
and subsequently refined manually to ensure clarity and logical completeness.
These guidelines instruct the LLM to follow a reasoning process similar to least-to-most prompting
(
38
)
, breaking down the inference task into manageable sub-problems to enhance the quality and reliability of the generated oracles.
Key steps in the guidelines include
(1) comprehending the developer’s intent from NL artifacts,
(2) analyzing the pre-patch function to understand its behavior,
(3) identifying behavioral changes introduced by the code patch and invariants that should hold before and after the patch,
(4) synthesizing runtime assertions, and
(5) generating test inputs that effectively exercise the modified function and validate the assertions.

(3)

Contextual Information
comprises specific information for the current PR under analysis, including the collected NL artifacts and the extracted code context of the modified function.
This input provides the LLM with the necessary background to perform accurate oracle inference.

(4)

Output Formatting
consists of explicit constraints that dictate the structure and content of the LLM’s response.
We require the LLM to produce a structured output that includes clearly defined sections for reasoning traces, testing hypotheses, and the final patch oracle in the form of a comparison program (§
3.5.1
).
The comparison program is also required to contain specialized placeholders for the concrete implementation of pre- and post-patch functions, which are necessary for subsequent processing of the orchestrator (§
3.5
) to facilitate oracle execution and validation.
For example, in Figure
2
, the placeholders
pre_validation
and
post_validation
are used to denote the pre- and post-patch implementations of the modified function, respectively.

To ensure correct parsing and execution of the generated patch oracle,
PatchGuru
applies a lightweight validation step to check that the generated oracle adheres to the expected format.
If validation fails, we re-invoke the LLM with the error feedback until a valid oracle is produced.

3.3.
Oracle Enhancement

The oracle enhancement phase iteratively refines the initial patch oracle to improve its bug detection capabilities.
For instance, in our illustrative example (Figure
2
),
PatchGuru
initially infers assertions that account only for lowercase file URLs, i.e., those beginning with “file://” (line 21).
During the enhancement process,
PatchGuru
generalizes these assertions to include uppercase file URLs, e.g., those beginning with “FILE://” (line 27), thereby improving the oracle’s adequacy.
This generalization enables the detection of a previously unknown bug introduced by the PR, as the post-patch code fails to handle uppercase file URLs correctly.

To this end, this phase reuses the prompt template from §
3.2.3
, with modifications tailored to bug discovery. Specifically, the role definition is specialized to emphasize proactive bug discovery with the goal of uncovering inconsistencies between pre- and post-patch code.
Meanwhile, the guidelines encourage (1) generalization of existing assertions to broader input domains, (2) systematic exploration of edge cases and boundary conditions, and (3) diversification of test inputs.
The contextual information is augmented with the current version of the patch oracle, while output formatting remains unchanged to preserve executability.

PatchGuru
repeatedly invokes the LLM to refine the oracle until either an assertion failure is observed or a pre-defined iteration limit is reached.
In the later case,
PatchGuru
concludes that code patch behaviors are consistent and returns the patch oracle as the final output.

3.4.
Self-Review

The self-review phase aims to eliminate false positives, i.e., spurious assertion failures that do not correspond to true inconsistencies. To this end, this phase again reuses the prompt template from §
3.2.3
, with adaptations specific to the review tasks.
Specifically, the LLM is cast as a code reviewer and instructed to analyze failing assertions by cross-referencing NL artifacts, code changes, and observed runtime behavior.
The contextual information is augmented with execution logs and error reports produced by the orchestrator.
For each failing assertion, the LLM produces a verdict, i.e., true positive or false positive, along with a justification grounded in the available evidence.
In case of a false positive,
PatchGuru
prompts the LLM to propose concrete enhancements to the oracle.
In case of a true positive,
PatchGuru
raises a warning to notify developers of the detected inconsistency and generates a validation report that summarizes the findings.
For the example in Figure
2
, the LLM identifies that the assertion failure arises from the post-patch code’s case-sensitive handling of file URLs, which contradicts the developer’s intent.
Thus, the LLM concludes that this failure represents a true inconsistency (i.e., a bug) and provides a detailed explanation as illustrated in the “Self-Review” section of Figure
2
.
This process repeats until a true inconsistency is confirmed or all false positives are resolved, with a fixed upper bound on review iterations to ensure termination.

3.5.
Core Algorithm

The orchestrator coordinates the overall
PatchGuru
workflow by managing interactions among LLM modules and executing inferred oracles.
Given an oracle inferred or refined by the LLM, the orchestrator
(i) constructs and executes a comparison program with the inferred oracles and
(ii) selects subsequent actions based on the execution outcome, including oracle enhancement, self-review, or error repair, following Algorithm
1
.

3.5.1.
Constructing and Executing Comparison Programs

As mentioned in §
3.2.3
, patch oracles contains placeholders for the pre- and post-patch implementations.
The orchestrator replaces these placeholders by extracting the relevant code functions from the pre- and post-patch versions of the modified file, based on the ranges of deleted and added lines.
To avoid naming conflicts, the orchestrator renames the pre- and post-patch functions by appending the prefixes
pre_
and
post_
.
Additionally, the orchestrator also integrates all necessary dependencies extracted in §
3.2.2
into the comparison program to ensure correct linkage during execution.
By following this procedure, the orchestrator converts inferred patch oracles into executable comparison programs to validate pre- and post-patch behavior.
While our extraction may miss some dependencies due to the complexity of real-world codebases,
PatchGuru
handles them in the subsequent error repair phase (§
3.5.3
).

Once an executable comparison program is constructed, the orchestrator proceeds to execute it while monitoring runtime behavior.
To this end,
PatchGuru
builds a Docker container that encapsulates the necessary runtime environment, including language interpreters, libraries, and dependencies required for executing the comparison program.
This containerized approach ensures consistency and isolation during execution, mitigating potential conflicts with the host environment. During execution, the orchestrator captures detailed execution logs, including standard output, error messages, and stack traces.
It also monitors the evaluation of assertions defined in the patch oracle, recording any violations or exceptions that occur.
After execution, the orchestrator compiles a comprehensive report summarizing the execution results, including the status of each assertion (passed or failed), any runtime errors encountered, and relevant execution logs.
This report is then relayed back to the respective LLM modules for oracle enhancement, self-review, or error repair.

3.5.2.
Selecting Next Actions

After executing the comparison program, the orchestrator evaluates the results to determine the next action, considering several scenarios:

•

No Errors or Violations:
If all assertions pass without runtime errors, the orchestrator considers the pre- and post-patch behaviors consistent under the current oracle.

PatchGuru
then invokes the oracle enhancement phase (§
3.3
, Algorithm
1
, line 7) to further refine the oracle.
If this phase reaches its iteration limit without detecting inconsistencies,
PatchGuru
terminates and reports consistency between the patch and developer intent.

•

Assertion Violations:
If any assertions fail during execution, the orchestrator triggers the self-review phase (§
3.4
; Algorithm
1
, line 10).
The self-review process determines whether the violations represent true inconsistencies or false positives that require oracle enhancement.
Note that
PatchGuru
does not only generate assertions on the post-patch function, but also on the pre-patch function to capture its intended behavior, thus assertion violations can also be raised on pre-patch function.
However, we assume that the pre-patch function is correct as our goal is to detect bugs introduced by the patch relative to the pre-patch version, thus any assertion violations on the pre-patch function are treated as
reasoning errors
made by the LLM during oracle inference or enhancement, and will be handled in the error repair phase (§
3.5.3
, Algorithm
1
, line 16). This design enables
PatchGuru
to avoid misinterpreting the behavior of pre-patch function, thereby providing more accurate patch oracles.

•

Unexpected Errors:
If any other errors occur during execution, the orchestrator categorizes these as execution errors and invokes the error repair module (§
3.5.3
, Algorithm
1
, line 16) to address them. Specifically, we consider two main categories of execution errors: (1)
Syntax Errors
, these errors are caused by invalid code constructs in the generated comparison program, such as incorrect indentation, missing colons, or unmatched parentheses; (2)
Runtime Errors
, these errors occur during the execution of the comparison program, including but not limited to NameError due to undefined variables or functions, ImportError resulting from missing dependencies, and TypeError arising from incompatible operations between different data types.

3.5.3.
Error Repair

When execution errors are detected by the orchestrator,
PatchGuru
invokes an LLM-based error repair module to diagnose and resolve these issues.
As discussed above,
PatchGuru
focuses on three main categories of errors:
(i) Reasoning Errors, which lead to assertion violations on the pre-patch function,
(ii) Syntax Errors during compilation, and
(iii) Runtime Errors during execution.
To address these errors, we employ a structured prompt template similar to previous LLM invocations, customized for the error repair tasks.
Specifically, the role definition frames the LLM as an expert software debugger, while the guidelines provide step-by-step instructions for diagnosing and fixing the identified errors. The contextual information includes the generated comparison program, execution logs, and error reports from the orchestrator.
The output formatting specifies the expected structure of the LLM’s response, which includes a corrected version of the comparison program along with explanations of the changes made.

3.6.
Implementation Details

While
PatchGuru
is conceptually language-agnostic, we evaluate it by implementing a prototype for the Python ecosystem.
We selected Python due to its popularity and the availability of mature, large-scale open-source repositories.
Moreover, LLMs have demonstrated strong capabilities in understanding and generating Python code, making it a suitable target for our approach.
We employ GPT-5-mini
(
31
)
as the underlying LLM as our preliminary experiments showed that it offers a reasonable trade-off between effectiveness and computational cost.
The prototype is implemented in Python 3, consisting of approximately 4,300 executable lines of code.
To facilitate static analysis and code transformation, we leverage the built-in
ast
module and the
libCST
library.
Interaction with the LLM is managed via the
openai
Python library. For data collection, we use the
PyGitHub
and
GitPython
libraries to collect and manipulate artifacts from GitHub.
To ensure reproducible and isolated execution, all target repositories are analyzed within
Docker
containers, orchestrated via the
docker
Python SDK.

All experiments are conducted on a server equipped with an AMD EPYC 9474F 32-Core processor at 3.6 GHz with 128GB of RAM, running Ubuntu 22.04 LTS.
To maintain computational efficiency, we enforce a 1h timeout per test execution, which includes the time for compiling and running the comparison program within the Docker container.
We configure GPT-5-mini with a temperature of 0.7 following the default setting of ChatGPT.
We use the model’s full context window of 400,000 tokens per LLM query for input prompts to maximize the available context.
We also limit output generation at 16,384 tokens per LLM query to prevent excessive computational cost.
Empirically, most generated oracles are well below these upper bounds, suggesting that the impact of these parameters on effectiveness is minimal.

Baselines

To evaluate the effectiveness of our approach, we compare
PatchGuru

Testora (RQ
1

To evaluate the effectiveness of
PatchGuru
in detecting real-world bugs, we compare it against Testora
(
34

, a state-of-the-art patch validation technique that also checks Python code patches against NL artifacts in PRs.
Testora generates tests and executing them independently on pre- and post-patch program versions to obtain their outputs for comparison.
When differences arise between the outputs, Testora uses an LLM to determine whether observed behavioral differences are intended w.r.t. the NL artifacts; if not, it raises a warning.
For a fair comparison, we sought the help of Testora’s author to run it on our dataset of PRs using their recommended settings and GPT5-mini (i.e., the same model used by
PatchGuru
) as the underlying LLM.
The reason for comparing against Testora in RQ

Developer-written regression tests (RQ

Developers commonly rely on regression tests to ensure that software evolution does not break existing functionality.
Thus, to assess the quality of patch oracles generated by

For RQ

For RQ

4.2.
RQ
1
: Effectiveness at Finding Real-World Bugs

In this research question, we evaluate the practical usefulness of
PatchGuru
by assessing its effectiveness in detecting real-world bugs in code patches.
Specifically, we apply
PatchGuru
to the 400 PRs and manually analyze the raised warnings to identify true inconsistencies between code patches and developer intent.
A true positive is defined as a warning that correctly identifies an inconsistency between the behavior of a code patch and the developers’ intents as expressed in NL artifacts, whereas any other warnings are false positives.
Next, we calculate the precision of
PatchGuru
in detecting real-world bugs, defined as the ratio of true positives to the total number of warnings issued.
Finally, we compare the performance of
PatchGuru
against Testora.

During manual inspection, we observe that some true positives correspond to patches that exhibit desirable behavior despite being inconsistent with the stated developer intent.
For instance, a patch may inadvertently fix an unrelated bug that is not mentioned in the PR description.
Therefore, we further classify true positives into two categories:
(i)
documentation bugs
, where the documentation inaccurately describes the unintended yet correct behavior introduced by the patch, and
(ii)
code bugs
, where the patch introduces unintended and undesirable behavior that deviates from the developers’ intent.
For all code bugs, we check whether the problem still exists in the latest version of the project, and if so, report the bug to the developers.
While we believe that documentation bugs would be useful to report as long as a PR is still open, we do not report them in our evaluation as all PRs in our dataset have already been merged, and the developers are unlikely to revisit them.

True Positives

Table

summarizes the 24 bugs detected by
PatchGuru
in the four studied projects.
Among these, 17 are code bugs and 7 are documentation bugs.
Notably, of the 17 code bugs, 12 were still present in the latest version of these projects at the time of evaluation, while the remaining 5 had been fixed independently by developers.
We reported 12 previously unknown bugs to the respective project maintainers; as of this writing, maintainers confirmed all these bugs and actively addressed them.
They submitted pull requests for 11 of the 12 bugs; among these, 7 have already been merged, and 4 are waiting for final approval.

It is worth noting that all PRs analyzed by
PatchGuru
had already been merged into the main codebase, i.e., these issues were not detected by standard patch validation processes, including both regression testing and manual code review.
For example, in PR #2800 of the Marshmallow project (illustrated in Figure
2
), the buggy code changes were still merged despite passing all regression tests and being approved in code reviews.
In contrast,
PatchGuru
-generated patch oracles precisely captured the intended behavior described in the PR including the handling of both uppercase and lower case file urls, allowing it to identify the inconsistency introduced by the patch.

By analyzing these true positives, we found three types of bugs that can be effectively identified by
PatchGuru
.
First,
PatchGuru
detects bugs caused by incomplete patches that do not fully realize the intended behavior described in NL artifacts.
For example, in Pandas PR #61966, the patch aimed to fix an issue in the representation of string categories, which were previously unquoted.

PatchGuru
correctly inferred a patch oracle,
pre_out == post_out[1:-1]
, capturing the intended behavior by relating the pre-patch output (
pre_out
) to the post-patch output (
post_out
) with quotes removed.
Then,
PatchGuru
also generated diverse inputs to test this behavior, discovering that while the patch correctly handled the
str
type, it failed to address the
string
type, leading to an incomplete fix.
This issue was later confirmed and fixed by Pandas’s maintainers.
This example also illustrates the benefit of
PatchGuru
’s patch oracles over traditional specifications, which enable reasoning about cross-version properties between pre- and post-patch behavior rather than focusing solely on post-patch behavior.

Second,
PatchGuru
can identify patches that inadvertently introduce regressions while fixing other issues or implementing new features.
For example, in Keras PR #20765, a patch addressing a bug in the
TimeDistributed
layer for partial batch sizes introduced a regression that silently accepted masks with mismatched timesteps.
In this case,
PatchGuru
not only generated patch oracles capturing the intended behavioral changes, but also inferred an invariant between the pre- and post-patch versions:
they should both raise errors when masks have mismatched timesteps.
Executing these oracles revealed that the post-patch version failed to raise an error.

Finally,
PatchGuru
can identify documentation bugs in which NL artifacts inaccurately describe patch behavior.
For instance, in Pandas PR #61162, the documentation claimed that the patch enabled
Series[bool]
indexing without specifying to what types of series it applies.
However, the patch was intended to apply only to integer-indexed series and intentionally excluded non-integer indexes.

PatchGuru
-generated patch oracles captured this behavior for both integer- and non-integer indexes.
Executing these oracles revealed that the post-patch version raises exceptions for non-integer indexes, exposing a discrepancy between the documented intent and the actual behavior.
Although documentation bugs do not directly affect correctness, they can confuse developers.
By identifying these discrepancies,
PatchGuru
helps improve documentation quality in rapidly evolving codebases.

Comparison with Testora

To further evaluate the effectiveness of
PatchGuru
, we compare its performance against Testora
(
34
)
, a state-of-the-art patch validation technique.
As shown in Table
1
, Testora issued a total of 22 warnings across the four projects, of which only 7 were confirmed as true positives, resulting in a precision of 0.32.
By comparison,
PatchGuru
not only detected a substantially higher number of true bugs (24 vs. 7), but also had a higher precision (0.62 vs. 0.32).
This performance improvement arise from two factors.
First,
PatchGuru
generates explicit patch oracles that not only prevent unintended behavioral changes but check for intended behaviors as described in NL artifacts.
In contrast, Testora relies exclusively on differential testing between pre- and post-patch versions, which can miss bugs that do not manifest as behavioral differences in generated tests.
In our example (Figure
2
), both versions exhibit the same incorrect behavior for uppercase file URL schemes, causing Testora to miss the bug, whereas
PatchGuru
’s explicit oracles capture the intended behavior and detect the issue.
Second,
PatchGuru
generates and refines patch oracles using execution feedback and self-review to better align with developer intent, enhancing the accuracy of the inferred oracles.
By comparison, Testora depends on LLM-based interpretation of behavioral differences, which is more susceptible to hallucination, especially when NL artifacts are ambiguous or incomplete.
This advantage is particularly evident by higher precision of
PatchGuru
over Testora (0.62 vs. 0.32).

False Positives

To understand the current limitations of
PatchGuru
, we manually analyze all 15 false positives identified during our evaluation.
This analysis reveals two primary root causes.
First, in 8 cases,
PatchGuru
generates unrealistic inputs in the synthesized patch oracles that do not reflect actual usage scenarios, thereby producing false warnings.
This issue is caused by limitations in
PatchGuru
’s current comparison program synthesis and input generation strategies.
Specifically,
PatchGuru
occasionally synthesizes unrealistic mock data types to enable the execution of comparison programs, or generates inputs that violate path constraints along the calling stack from top-level APIs to the modified functions.
Second, in three cases,
PatchGuru
generates incorrect assertions, which misinterpret the developer intent.
Notably, two cases arise because
PatchGuru
disagrees with developer intent as expressed in NL artifacts despite correctly inferring it.
For example, in PR #60867,
PatchGuru
infers that the intended behavior is to return
frozenset
objects with curly braces even for empty sets, but assumes that an empty
frozenset
should be represented as
frozenset()
, resulting in false warnings.
In two additional cases,
PatchGuru
fails to capture execution-environment-specific behavior (e.g., platform-dependent behavior), leading to incorrect oracles.
For the remaining two cases, we are unable to definitively determine whether they are true positives due to insufficient context and therefore conservatively classify them as false positives.

This research question conducts an ablation study to assess the contribution of individual components of
PatchGuru
to its overall performance. Specifically, we evaluate two modules: (i) the oracle enhancement module (§
3.3
) and (ii) the self-review module (§
3.4
).
We create two ablation variants of
PatchGuru
by removing each component in turn and evaluating them on the same set of 400 PRs.
The results are reported in Table
4
.

4.5.1.
PatchGuru
without Oracle Enhancement

In this variant, we disable the oracle enhancement module and directly use the initial patch oracles generated by the LLM without further refinement.
As shown in Table
4
, removing this module reduces oracle adequacy, as evidenced by a decrease in mutation score from 0.70 to 0.64.
Consequently,
PatchGuru
’s effectiveness in detecting real-world bugs is negatively affected: the number of warnings drops from 39 to 18, and true positives decrease from 24 to 12.
Although precision slightly increases from 0.62 to 0.69, the bug detection is considerably affected.
These results demonstrate that the enhancement module is essential for improving oracle quality by generalizing patch oracles and generating comprehensive test inputs.

4.5.2.
PatchGuru
without Oracle Self-Review

In this variant, we disable the self-review module, i.e., directly report detected inconsistencies between patch behavior and inferred oracles.
This results in an excessive number of warnings (195 out of 400 analyzed PRs), rendering exhaustive manual inspection impractical.
We therefore estimate the results as follows:
(1) we partition the warnings into two groups based on the self-review outcomes in the full
PatchGuru
;
(2) for warnings classified as “bug” by the self-review module, we reuse the inspection results from RQ
1
;
(3) for warnings filtered out by the self-review module, we randomly sample five warnings per project and manually inspect them to determine true and false positives;
(4) finally, we extrapolate from the sampled inspections to estimate the total numbers of true and false positives for the entire set.

5.
Threats to Validity

Our evaluation is subject to several threats to validity.
First, our benchmarks may not be representative of all software projects.
To mitigate this threat, we selected popular Python projects from diverse domains.
Moreover,
PatchGuru
currently focuses on Python projects, which may limit the generalizability of our findings to other programming languages.
Although
PatchGuru
’s core approaches are language-agnostic, applying it to other languages may pose additional engineering challenges.
Second,
PatchGuru
currently focuses on patches that modify a single function, which simplifies the construction of comparison programs.
The extension of
PatchGuru
to handle multi-function patches is non-trivial, as it requires sophisticated program analysis techniques to accurately model the interactions between modified functions and their dependencies.
Future work could explore techniques such as inter-procedural analysis and modular reasoning to extend
PatchGuru
’s capabilities to multi-function patches.
Next, the manual analysis of detected inconsistencies is subject to human error.
To address this, we employed multiple reviewers to cross-validate the findings and ensure consistency in the analysis.
We also disclosed all identified bugs to the respective project maintainers for confirmation.
Finally, the effectiveness of
PatchGuru
depends on LLM capabilities; due to limited funding, we evaluated only
GPT5-mini
.
Future work could assess performance across diverse LLMs and configurations.

Related Work

Reasoning about Code Changes

As software evolves, understanding and reasoning about code changes is crucial for maintaining software quality.
The most relevant line of work to
PatchGuru
is on patch specification
(
7
;
35
)
.
Cadar et al. propose the vision of patch specification using product programs to specify the indented behaviors of patches
(
7
)
.
Sharma et al. present P
3
, a technique that automatically synthesizes product programs to support reasoning about code changes
(
35
)
.
However, both works require manually provided patch specifications to validate the correctness of code changes.
Our approach addresses this limitation by automatically inferring patch oracles, an under-approximated yet practical form of patch specifications, from NL artifacts, enabling automated validation of code changes without minimal human intervention.

PatchGuru
is also closely related to recent work on reasoning about code changes using learning-guided execution, e.g., ChangeGuard
(
13
)
and LLMs, e.g., Testora
(
34
)
.
However, as discussed in §
2
, our formulation yields additional benefits over these works, e.g., the ability to detect incorrect patches that wrongly implement the intended behavior described in NL artifacts, leading to more effective validation as shown in §
4
.

PatchGuru
is also related to just-in-time bug prediction techniques
(
16
;
37
;
28
;
29
;
33
)
, which estimate the likelihood that a commit introduces defects using models trained on historical data.
However, recent studies
(
28
;
37
)
report their limited practical effectiveness due to severe class imbalance between buggy and clean commits
(
28
)
and noise in bug-inducing commit labels derived from SZZ-based heuristics
(
11
)
.

More broadly, automated testing techniques have been used to target code patches
(
26
;
22
;
5
;
21
;
25
)
.
For example, Shadow
(
22
)
executes pre- and post-patch versions within a single symbolic execution instance to generate inputs that exercise divergent branches, while ChaCo
(
39
)
identifies uncovered lines in the post-patch version and uses LLMs to generate tests that improve coverage.
While these techniques effectively generate tests that exercise code changes, they do not address the oracle problem, which is essential for determining correctness.
In principle, they are complementary to
PatchGuru
and could be combined with it to generate tests that are then validated against inferred patch oracles.

Test Oracle Problem

Software testing relies on test oracles to determine the correctness of program outputs, yet such oracles are often incomplete or absent, leading to the well-known oracle problem
(
3
)
.
Prior work addresses this challenge by inferring oracles from API documentation, including metamorphic relations
(
4
)
and exception oracles
(
12
)
, or by generating assertions for test prefixes using deep learning models and LLMs
(
8
;
17
)
.
Other approaches infer program specifications that serve as oracles through dynamic invariant inference
(
30
;
10
;
24
)
or LLM-based techniques
(
23
;
9
)
.
Despite their effectiveness, these techniques primarily validate overall program behavior rather than behavior introduced or modified by code changes.
This formulation is ill-suited to large, rapidly evolving systems: validating the entire program behavior requires comprehensive coverage, which is often infeasible in real-world systems, and inferred oracles must be continually updated, incurring high maintenance costs.
In contrast,
PatchGuru
infers patch oracles that target only the behavior affected by a change, enabling more efficient validation.
This formulation also allows
PatchGuru
to exploit NL artifacts, e.g., commit messages and code review comments, that describe developer intent and are readily available in modern workflows.

7.
Conclusion

Software patches are essential for system evolution but remain a major source of bugs and vulnerabilities due to lack of executable specifications capturing developer intent.
In this paper, we introduced
PatchGuru
, an automated technique that infers executable patch oracles from natural language artifacts using LLMs and dynamic analysis.
Our evaluation on 400 real-world PRs shows that
PatchGuru
identifies 24 real inconsistencies, including 12 previously unknown code bugs.
The approach imposes reasonable costs of 8.9 minutes and $0.07 per PR, suitable for real-world deployment.
We envision
PatchGuru
as a complement to existing development practices by providing executable behavioral documentation and enabling early detection of unexpected behaviors missed by traditional approaches.
