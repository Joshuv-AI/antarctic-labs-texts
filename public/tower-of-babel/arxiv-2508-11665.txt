StackPilot: Autonomous Function Agents for Scalable and Environment-Free Code Execution
Xinkui Zhao, Yifan Zhang, Zhengyi Zhou, Yueshen Xu

Abstract
Recent advances in large language models (LLMs) have substantially enhanced automated code generation across a wide range of programming languages. Nonetheless, verifying the correctness and executability of LLM-generated code remains a significant challenge, as traditional methods rely on language-specific compilers and environment-dependent runtimes. To overcome these limitations, we introduce StackPilot, an LLM-native, multi-agent framework designed for language-agnostic code verification and execution, which operates independently of conventional toolchains. StackPilot offers three principal innovations: (1) a Function-as-Agents paradigm, in which each function is modeled as an autonomous agent capable of fine-grained reasoning and collaborative verification; (2) an LLM-as-Executor strategy, which enables scalable verification via stack-based scheduling; and (3) a novel snapshot mechanism that preserves complete execution contexts, facilitating deterministic and lossless context switching during verification. Empirical evaluations demonstrate that StackPilot achieves framework reliability rates between 89% and 97%, substantially outperforming baseline approaches. These results indicate that StackPilot can reliably verify and execute a significantly larger proportion of LLM-generated code across diverse programming tasks compared to existing methods.

LLMs for Code Generation.

Recent years have witnessed rapid progress in large language models (LLMs)
(
Achiam et al. 2023
;
Touvron et al. 2023
;
Liu et al. 2024a

, driven by advances in neural architectures and the availability of massive text datasets. These models, originally developed for natural language understanding and generation, have demonstrated remarkable generalization abilities across a wide range of tasks.

With the inclusion of large-scale code corpora in their training data, LLMs have also shown strong performance in code-related domains
(

;

These tools can assist developers with code completion, code synthesis from natural language descriptions, automatic bug fixing, and code translation between languages.

LLM-based coding assistants have been adopted across various domains, including web development, data science, education, and competitive programming. Their ability to handle diverse programming languages and understand both code and natural language makes them increasingly valuable in both industry and academia.

Traditional Code Verification Pipelines.

Despite the remarkable progress in code generation, ensuring the correctness and reliability of automatically generated code remains a core challenge. Traditional software engineering relies on well-established verification pipelines, typically including syntax checking

Human developers are responsible for interpreting error messages, diagnosing root causes, and applying fixes—creating a significant bottleneck as code generation becomes increasingly automated and large-scale.

Moreover, the effectiveness of these pipelines is tightly coupled to specific programming languages, language versions, and technology stacks. Dedicated compilers, analyzers, and testing frameworks are rarely portable across languages or even between major versions
(
Ray et al. 2014

These limitations highlight the pressing need for more flexible, scalable, and automated approaches to code verification, particularly as LLM-driven code generation expands across diverse technical landscapes.

Formalizing Programs as Function Graphs.

To more systematically analyze and verify code—particularly in the context of large-scale, automatically generated programs—it is instructive to revisit the fundamental structure of software from first principles. Rather than viewing a program merely as a sequence of instructions or lines of code, we adopt a more abstract perspective that emphasizes modularity and compositionality.

At its core, a program can be regarded as a collection of functions or procedures, each encapsulating a distinct computational task and a well-defined interface. Formally, we model a program as a set of functions:

\mathcal{F}=\{f_{1},f_{2},\ldots,f_{n}\},

where each
f_{i}
represents an individual function or procedure.

The invocation relationships among these functions can then be captured by a set of directed edges

G=(\mathcal{F},E),

Each function

\mathbf{x}_{i}

\mathbf{y}_{i}
, local state
s_{i}
, and its own execution logic
\mathcal{B}_{i}
.
Formally, we model each function as a tuple:

f_{i}=(\mathbf{x}_{i},\mathbf{y}_{i},s_{i},\mathcal{B}_{i}),

(3)

where
\mathbf{x}_{i}

Motivation

Although large language models (LLMs) have transformed the landscape of code generation, current code verification pipelines exhibit several key limitations:

•

Tight Coupling to Toolchains:
Existing verification workflows rely heavily on external runtimes, compilers, and language-specific tooling, making it difficult to support cross-language or cross-version code verification.

•

Complex Environment Setup:
Setting up and maintaining verification environments is resource-intensive, particularly when handling diverse programming languages, fast-evolving libraries, and complex dependency stacks.

•

Limited Detection of Semantic Errors:
Traditional static analysis and unit testing can catch many surface-level issues, but often fail to identify deeper semantic errors—such as implicit dependencies and inter-function logic bugs.

Recent advances in LLMs introduce new possibilities for code understanding and simulation. Modern LLMs can reason about code across multiple languages, simulate execution, and even predict program outcomes—all without requiring a concrete runtime or traditional execution environment. However, existing verification pipelines are not designed to harness these capabilities in a principled, scalable, and language-agnostic manner.

This motivates a new research question:

Can we design a code verification framework that fully leverages the universal reasoning abilities of LLMs, eliminating dependence on external toolchains and environments?

Methodology

System Overview

To address these challenges, we revisit the theoretical underpinnings of program structure and verification. A program can be abstracted as a set of interacting functions, whose invocation relationships form a directed call graph. Notably, this modular, compositional structure strongly parallels the agent paradigm in multi-agent systems (MAS): both functions and agents encapsulate local state and computation, expose explicit interfaces, and collaborate within an orchestrated system. The execution of such programs is traditionally governed by a stack-based control flow, enabling disciplined invocation, local state management, and orderly returns from nested calls.

StackPilot builds on these insights and introduces two central innovations.
First
, we model each function as an autonomous agent, enabling fine-grained, modular reasoning and collaborative verification (
Function-as-Agent paradigm
).
Second
, we leverage LLMs as universal, language-agnostic executors and environment simulators (
LLM-as-Executor
), removing dependence on traditional runtimes or compilers.

Formally, given a program represented by the set of functions
\mathcal{F}
(Eq.
1
) and its call graph
G=(\mathcal{F},E)
(Eq.
2
), we define a corresponding set of agents:

\mathcal{A}=\{a_{i}\mid a_{i}=\text{Agent}(f_{i}),\ f_{i}\in\mathcal{F}\},

(4)

where each agent
a_{i}
encapsulates the reasoning and simulation logic for function
f_{i}
.

During verification, a stack-based scheduler
\mathcal{S}
orchestrates agent execution according to the call graph
G
, maintaining a global variable heap
\mathcal{H}
to track program state, and invoking the LLM executor
\mathcal{L}
to simulate code behavior within each agent.

The overall verification process can be abstracted as:

\mathcal{V}(P)=\mathcal{S}(\mathcal{A},G,\mathcal{L},\mathcal{H}),

(5)

where
\mathcal{S}
coordinates agent interactions, LLM-powered execution, and variable state management to collaboratively analyze and verify program

Functions-as-Agents Abstraction

Isolation of Agent

Building on the formalization of each function
f_{i}
as a tuple
(\mathbf{x}_{i},\mathbf{y}_{i},s_{i},\mathcal{B}_{i})
(Eq.
3
), the Functions-as-Agents abstraction models each agent
a_{i}
as an autonomous entity corresponding to function
f_{i}
, represented as

a_{i}=(\mathbf{x}_{i},\mathbf{y}_{i},s_{i},\mathcal{B}_{i})

(6)

where
\mathbf{x}_{i}
and
\mathbf{y}_{i}
are the agent’s inputs and outputs,
s_{i}
is its private state, and
\mathcal{B}_{i}
denotes its internal computation.

Each agent comprises four modules: (1)
Local State
(
s_{i}
), storing private variables; (2)
Input
(
\mathbf{x}_{i}
), handling received parameters or messages; (3)
Decision Logic
(
\mathcal{B}_{i}

(
\mathbf{y}_{i}

Crucially, only explicit interfaces—inputs (
\mathbf{x}_{i}

\mathbf{y}_{i}

Collaboration of Agents

Collaboration between agents is strictly governed by explicit interaction interfaces. For any pair of agents
a_{i}
and
a_{j}
(each defined as
a_{k}=(\mathbf{x}_{k},\mathbf{y}_{k},s_{k},\mathcal{B}_{k})
per Eq.
6
), all communication occurs via designated input and output channels.

Formally, an interaction from
a_{i}
to
a_{j}
can be represented as a mapping:

M_{i\rightarrow j}:\mathbf{y}_{i}\rightarrow\mathbf{x}_{j}

(7)

where
a_{i}
’s output
\mathbf{y}_{i}
becomes part (or all) of
a_{j}
’s input
\mathbf{x}_{j}
, possibly via a structured message or parameter passing.

The set of all such interactions across the agent set
\mathcal{A}
forms the collaboration graph:

C=(\mathcal{A},\mathcal{E})

(8)

where each edge
(a_{i},a_{j})\in\mathcal{E}
indicates that
a_{i}
can send information (via
M_{i\rightarrow j}
) to
a_{j}
through explicit interfaces.

By restricting all inter-agent collaboration to these well-defined mappings
M_{i\rightarrow j}
, the system guarantees that:

•

All dependencies and information flows are transparent and auditable.

•

Modularity is preserved, as no agent exposes its internal state (
s_{i}
) or decision logic (
\mathcal{B}_{i}
) to others.

•

Agents can coordinate, share results, and collectively achieve program-level objectives.

StackPilot Execution

This section describes the StackPilot execution process, integrating the formal agent-based program model with stack-based scheduling to achieve modular, collaborative program verification. At its core, StackPilot transforms program execution into a multi-agent workflow: each function instance is instantiated as an autonomous agent (per Eq.
6
), and their interactions are coordinated by a centralized call stack mechanism that mirrors real-world program execution.

Function Agents as Execution Units

In StackPilot, each function agent
a_{i}=(\mathbf{x}_{i},\mathbf{y}_{i},s_{i},\mathcal{B}_{i})
represents an autonomous execution unit encapsulating the context and logic of a specific function invocation. Upon program analysis, StackPilot identifies all functions
\mathcal{F}
and their call relationships
G
(Eq.
1
, Eq.
2
), instantiating an agent for each invocation. Multiple concurrent agents may correspond to different invocations of the same function, each with an isolated stack frame—including local variables (
s_{i}
), execution pointer, and execution logs—while sharing global resources via a centralized pool.

Execution within each agent proceeds step-wise at the code line or block level. To enable precise traceability, StackPilot enforces code annotation and uniquely labels each line, supporting robust inter-agent coordination and LLM-based simulation. The agent interprets code lines according to its decision logic
\mathcal{B}_{i}
, maintains state
s_{i}
, and manages inputs/outputs
(\mathbf{x}_{i},\mathbf{y}_{i})
. For leaf agents, initialization includes memory allocation, pointer setup, and code context embedding, after which the agent executes sequentially.

Variable management in StackPilot is handled through a unified dictionary structure, which clearly distinguishes between each agent’s local variables and shared global state.

Algorithm 1

Stack-based Scheduling with Agent Snapshots

Stack as Coordinator

StackPilot extends the classical call stack mechanism to a multi-agent context, using a stack-based scheduler
\mathcal{S}
(see Eq.
5
) to orchestrate agent interactions. Following Algorithm
1
, StackPilot enforces Last-In-First-Out (LIFO) scheduling: when a function call is encountered, the scheduler instantiates a new agent for the callee, pushes it onto the agent stack, and suspends the caller agent, preserving its execution context and local state.

Agent Snapshot Abstraction

To enable fine-grained execution control and robust context management, we introduce the concept of
Agent Snapshots
. Each snapshot encapsulates the full execution context of a function agent at a specific point in time. Concretely, each agent snapshot consists of the following four components: Local State, Execution Pointer, Execution Logs,and Interface State (
\mathbf{x}_{i},\mathbf{y}_{i}
). To uniquely identify snapshots, particularly in the presence of recursive or iterative function calls, each snapshot is distinguished by a combination of the function name and its appearance index.

Snapshot Capture and Storage

A key event that triggers snapshot capture is a function call, which requires suspending the current agent and invoking a callee. When a function agent encounters a call instruction, StackPilot executes a
stop-the-world
operation: the scheduler immediately halts the running agent and captures its complete state as a snapshot. Specifically, the agent’s local memory, execution pointer, logs, and interface data are frozen and packaged into a snapshot object. This snapshot is then pushed onto the top of the agent stack, preserving the full context.

Figure 2:
Case study
. StackPilot visualization of agent snapshots and variable states during execution of line 28 in an union-find algorithm.

Snapshot Pop and Resume

After a snapshot is pushed onto the stack, the scheduler instantiates and activates a new agent for the called function, which then executes in isolation. When the callee agent completes, the top snapshot is popped from the stack. The scheduler parses the snapshot, restores the saved state, and resumes the suspended agent at the exact position where it was previously halted. The return value from the callee is delivered to the restored agent as input, enabling seamless continuation of execution.

Agent Termination and Snapshot Destruction

Once an agent completes its execution and returns a value, its corresponding snapshot is destroyed and removed from the stack. This marks the end of the agent’s lifecycle. The scheduler then proceeds to restore the caller agent’s snapshot (if any), ensuring that control flow and execution state are consistently maintained throughout the verification process.

Conclusion

In this work, we propose
StackPilot
, an LLM-native, plug-and-play framework for reliable code verification and execution. Built upon the principles of Function-as-Agents, LLM-as-Executor, and stack-based scheduling with agent snapshots, StackPilot enables seamless and unified management of function-level code without the need for traditional toolchains or environment configuration. Extensive experiments demonstrate that StackPilot consistently achieves state-of-the-art reliability in code verification, significantly outperforming existing baselines. Our results highlight StackPilot’s robustness, generalizability, and potential to serve as a foundation for trustworthy code evaluation in a wide range of programming scenarios.

Limitations

Despite its strong performance, StackPilot has several limitations. It depends on large language models, which may lack accuracy in numerical computation and complex algorithmic reasoning. StackPilot also does not fully support code requiring external capabilities such as graphics, hardware, or system-level operations, limiting its domain applicability. Additionally, its serial agent scheduling restricts scalability and efficiency for large or modular codebases. Addressing these challenges is an important direction for future work.
