Abstract
. Existing unstructured data analytics systems rely on experts to write code and manage complex analysis workflows, making them both expensive and time-consuming. To address these challenges, we introduce AgenticData , an innovative agentic data analytics system that allows users to simply pose natural language (NL) questions while autonomously analyzing data sources across multiple domains, including both unstructured and structured data. First, AgenticData employs a feedback-driven planning technique that automatically converts an NL query into a semantic plan composed of relational and semantic operators. We propose a multi-agent collaboration strategy by utilizing a data profiling agent for discovering relevant data, a semantic cross-validation agent for iterative optimization based on feedback, and a smart memory agent for maintaining short-term context and long-term knowledge. Second, we propose a semantic optimization model to refine and execute semantic plans effectively. Our system, AgenticData , has been tested using three benchmarks. Experimental results showed that AgenticData achieved superior accuracy on both easy and difficult tasks, significantly outperforming state-of-the-art methods.



1.
Introduction

While large language models (LLMs) have made significant strides in understanding and generating for unstructured data, substantial gaps remain in their ability to perform
data analysis on unstructured and structured data
. Harnessing the capabilities of LLMs, such as understanding, reasoning, planning, and generation, holds great promise for transforming data analytics systems that handle both structured and unstructured data.

To enhance analytics on unstructured data (or text columns within structured data), semantic operators are utilized to boost system capabilities
(
AOP
;
Lotus
;
palimpzestCIDR
;
TAG
)
. For example, we can use the
semantic filter
to identify movies with positive sentiments, and employ the
semantic group
to classify movies based on the emotions they evoke, like "uplifting," "melancholic," "thought-provoking," etc.

While there have been some efforts to support semantic data analytics on unstructured data, these approaches face several limitations. First, certain methods propose coding-based solutions that require humans to write code using semantic operators for analyzing both unstructured and structured data
(
Luna
;
UQE
;
palimpzestCIDR
;
Lotus
)
. However, relying on humans to manage declarative pipelines is costly, highlighting the need for natural language (NL) interfaces to facilitate data analysis across both unstructured and structured datasets. Second, some methods extend SQL to include semantic operators
(
UQE
)
, allowing for semantic analysis of structured data. Unfortunately, these methods cannot handle unstructured data due to the challenges in obtaining schemas. It’s worth mentioning that while there are NL2SQL works
(
liu2025surveytexttosqlerallms
;
10.14778/3685800.3685905
)
, they are limited to SQL-based databases and lack the capability for cross-data-source analysis. Third, some methods utilize NL queries to perform semantic analysis on unstructured data
(
ZenDB
;
DocETL
)
. However, they require extracting structured data from the unstructured content before analysis, making them unsuitable for scenarios where a structured schema cannot be derived.

To overcome these limitations, we explore semantic data analytics for both unstructured and structured data using NL queries. Recent advancements in AI agents
(
shen2025mindmachinerisemanus
;
xagent2023
;
huang-chang-2023-towards
;
smolagents
)
have enabled these agents to write code, search for relevant information online, and handle complex tasks. However, general AI agents are not tailored for collaborative multi-agent systems in data analysis tasks, which leads to lower quality results in these scenarios. The challenges in developing an agentic data analytics system include:

Challenge 1:
How can we efficiently discover task-specific datasets from vast data repositories in production environments? For example, bank production systems contain thousands of datasets, but many lack detailed metadata and schema documentation, making it difficult to pinpoint relevant datasets for analytical tasks.

Challenge 2:
How can we develop logically correct and valid semantic plans for an NL query? Given ten primitive relational and semantic operators, the number of possible plans expands to trillions of variations, turning the task of finding one correct solution into a search for a needle in a haystack.

Challenge 3:
How can we optimize and execute a semantic plan to minimize LLM costs while maintaining high accuracy?

To tackle these challenges, we introduce
AgenticData
, a feedback-based multi-agent data analytics system.
AgenticData
begins with the development of a collaborative multi-agent planning framework that converts an NL query into a semantic plan composed of a data profiling agent, a data planning agent, and a data manipulation agent. The data profiling agent is designed to thoroughly comprehend the data analysis task description, select and analyze pertinent datasets, extract catalogs from unstructured datasets, and proactively learn domain knowledge from the datasets. The planning agent formulates an initial sketch of the semantic plan. Given the propensity for LLMs to produce errors, especially in complex plans, we design semantic and grammar validation techniques as well as smart memory management, providing essential feedback for plan correction. The data manipulation agent enhances the semantic plan by incorporating data access tools, such as calling functions or generating codes. Furthermore, we propose effective optimization strategies to reduce LLM costs without compromising plan accuracy. In summary, we make the following contributions.

(1) We propose
AgenticData
, a feedback-based agentic data system featuring multi-agent collaboration, which facilitates data analysis on multi-source heterogeneous datasets with humans writing NL queries. To the best of our knowledge, this is the first agentic data analytics system designed for heterogeneous data. (See Section
2
)

(2) We introduce a groundbreaking planning framework that translates NL queries into semantic plans, utilizing
semantic data discovery
,
semantic cross-validation
, and
smart memory management
techniques. These techniques ensure accurate plan generation and automatic plan correction.
(See Section
3
)

(3) We propose an optimization method at both the operator and plan levels to minimize LLM costs without compromising plan accuracy. (See Section
4
)

(4) We evaluated our system on three benchmarks, and the results showed that
AgenticData
achieved the highest accuracy and the least cost comparing to SOTA baselines. (See Section

2.
System Overview

2.1.
Problem Formulation

In this paper, we present
AgenticData
, a data agent system designed for analyzing multi-source heterogeneous data. Users employ NL to specify their requirements for extracting insights from underlying datasets, and
AgenticData
delivers high-quality results that accurately capture the intended data insights. The system should demonstrate three key characteristics: (1) High Accuracy: The results must be highly accurate with minimal hallucination, (2) Low Cost: The expenses of using LLMs should be minimized, and (3) Low Latency: The overall response time should be low.

To fulfill these requirements,
AgenticData
supports a comprehensive set of relational operators (e.g., Scan, Filter, Project, Join, Aggregate, Union, Merge, Sort, Limit, etc.) as well as semantic operators (e.g., Extract, Sentiment Analysis, Semantic Filter, Semantic Group, Semantic Join, etc.). The semantic operators are specifically designed for analyzing unstructured data or textual columns
(
unify
;
palimpzestCIDR
)
. Additionally,
AgenticData
can leverage LLMs to generate code for supporting non-predefined operators.
AgenticData
is designed to translate an NL query into a tree-structured semantic plan that incorporates various operators, optimizing and executing the semantic plan to minimize costs without compromising accuracy.

2.2.
System Architecture

Figure 1
.
Architecture of Our
AgenticData
System.

To achieve fully autonomous data analysis capabilities, the system is driven by multiple collaborative data agents. These agents are responsible for generating a high-quality semantic logical plan, optimizing it into an effective semantic physical plan, and executing the plan efficiently. The planner includes a data profiling agent to discover relevant data, a data planning agent to generate a high-quality plan, and a data manipulation agent to utilize tools for handling data. It also features a memory component to store both short-term information (e.g., context) and long-term information (e.g., knowledge). Additionally,
AgenticData
comprises three components: a plan validator, a plan optimizer, and a plan executor, each dedicated to optimizing and executing the logical plan.

Planner.
Unlike existing NL2Data systems that generate a logical plan in a single step using sufficient prompts
(
10.14778/3685800.3685905
;
AOP
)
,
AgenticData
employs multiple specialized agents for planning, with each agent serving as an expert in specific sub-tasks. This approach improves performance by allowing each expert agent to concentrate on solving a particular aspect of the problem. We divide the challenge of plan generation into three key areas: data discovery, task planning, and plan generation, and design three agents (a data profiling agent, a data planning agent, and a data manipulation agent) to tackle these specific challenges.
The data profiling agent provides tools for extracting metadata from both structured and unstructured data, using LLM with RAG techniques to enrich metadata and build a semantic catalog within vector databases. The data planning agent chooses relevant datasets based on the semantic requirements of the task and domain knowledge, plans the solution step-by-step, and creates a high-level plan. Lastly, the data manipulation agent outlines detailed attributes of the plan, such as generating SQL for the database Scan operator, specifying tool names and parameters for the file Scan operator, and selecting keys (e.g., columns) and functions (e.g., Max/Avg/Count) for the Aggregate operator.

AgenticData
incorporates a smart memory mechanism to manage short-term context and long-term knowledge. It automatically extracts valuable insights from short-term contexts to build long-term knowledge, such as frequently used patterns. It uses vector databases to store memory information, dynamically removing outdated short-term contexts and adding new ones as needed.

Validator.
Relying solely on LLMs to comprehend lengthy contexts can result in flawed plans with unexpected grammatical and logical errors due to the attention mechanism missing key information. To identify these errors before executing the plan, we propose a
Validator
module that checks both the grammar and semantic accuracy of the plan generated by the
Planner
.
AgenticData
uses a JSON decoder and a validator operator to ensure the generated plan is executable and properly structured. Additionally, it employs a discriminative LLM to assess the plan’s completeness, ensuring it can effectively address the data analysis task. If any issues are detected, the
Validator
records detailed error messages in memory, which are then used to inform and guide subsequent plan generation.

Optimizer.
LLM costs dominate the overall expenses associated with semantic operators, and a cost-effective physical plan is crucial for maintaining a low-cost data analysis system. In
AgenticData
, we design an optimizer module that enhances both latency and cost efficiency. Initially, the optimizer applies optimization rules to reduce query latency and lower LLM costs. It then selects suitable LLM models for semantic operators to maximize quality within a specified budget. We introduce an innovative plan-level quality model for tree-structured plans and use the model to minimize the cost. The design of the
Optimizer
is detailed in Section
4
.

Executor.
To execute the physical plan generated by the optimizer, we propose a bottom-up cascade executor engine that employs well-defined strategies for executing different operators. (1) Semantic Operators: We offer two physical implementations. The first invokes LLM services for each row using prompts supplied by agents. The second uses a vector index to search for similar content in the vector database. Operator optimization will be discussed in Section
4
.
(2) Relational Operators: We utilize underlying engines such as RDBMS, Spark, and Pandas DataFrame through the Model-Context Protocol (MCP), which provides a solution for integrating data access tools and managing variations across data engines. The MCP server is self-describing, enabling users to easily extend supported data sources by adding new services.
The executor participates in the multi-agent feedback loop, where exceptions are logged into memory and trigger a new iteration.

Semantic Data Organization and Indexing.
We organize the varied data into a hierarchy based on their semantics. To do this, we randomly select a sample of the data and use LLMs to create a semantic hierarchy. We then train a smaller LLM to categorize the data within this hierarchy. Furthermore, we divide the data into segments, compute embeddings for each segment, and build a vector index to speed up semantic filtering.

Memory Manager.
As a multi-agent system,
AgenticData
relies on memory to collect and provide feedback for learning by analogy and correcting errors. Since all the errors encountered during the semantic planning process are managed in memory, it is challenging to prevent an overload of error messages from overwhelming the LLM’s features. Therefore, unlike the traditional ReAct agent framework that incorporates all error messages into agents,
AgenticData
uses a smart memory management approach to improve effectiveness by eliminating redundant information, summarizing commonalities from logs, and scheduling memory to different agents based on categories. We address three challenges in smart memory design. (1) What should be stored in memory? We store plan context (e.g., plan hints) and error messages (e.g., parser errors, execution errors) in short-term memory, and summarize the frequent information in the short-term memory and move them into long-term memory. (2) How should information be transferred between short-term and long-term memory? Initially, error messages are collected in the short-term memory, and all expired messages are stored in the temporary memory. Next, we invoke the LLM to analyze the semantics of error messages in the temporary memory and determine whether to transfer them to long-term memory. If an error message can offer common value for error-prone scenarios, we summarize the commonalities and add them to the long-term memory. The long-term memory is stored in the vector database, which is a relation table with attributes [‘task’, ‘task-embedding’, ‘memory’]. For instance, as shown in Figure
2
, if the syntax error “(== [])” occurs only once, it would be discarded. However, if similar syntax errors such as “(’H’ in )” recur, then the knowledge tuple “Ensure the columns referred in the expression exist in the datasets.” should be inserted into the long-term memory. (3) How can memory information be fed into different agents? To prevent each agent from receiving messages unrelated to its role, we propose a two-phase memory selection techniques to send memory to those agents that are semantically correlated. Initially, we convert the task into embeddings, and inquiry knowledge of similar tasks from the long-term memory. Then, we categorize memory messages of both selected long-term memory and short-term memory into three types: data errors, semantic errors, and grammar errors, and they are sent to the data profiling agent, data planning agent, and data manipulation agent, respectively. To classify the errors, we construct an error type dictionary, and find the category of an error by searching the dictionary. For those who cannot match with any error in the dictionary, we resort to LLM to classify it.

3.
Semantic Task Planning

Semantic planning is the central process of
AgenticData
for achieving accurate plans. Figure
2
illustrates the overall workflow.

Data Profiling.
To discover data for specific tasks,
AgenticData
surveys all data servers and profiles the data contents. Initially, users set up the system by configuring access URLs, tokens for the LLM service and embedding service, and integrating a domain-specific data directory or database into the list of data servers. Subsequently,
AgenticData
activates all data servers and invokes the
data_profile
method on each server to retrieve dataset descriptions. For instance,
AgenticData
launches three servers for text/json/csv data files and one server for accessing the database. During profiling, each dataset is evaluated. If the data is recognized as unstructured – such as domain knowledge manuals or dataset design documentation – it will be segmented, with each segment containing complete information useful for the data agents’ understanding of the data and analytical tasks. These unstructured segments are then converted into embedding vectors and stored in a vector database
(
gaussdbvector
)
for semantic searches. Moreover, if a segment contains tabular details (e.g., enumerated column values),
AgenticData
extracts this information into a new structured file placed in the same directory alongside other structured datasets. On the other hand, if the dataset is identified as structured with a clear schema, it undergoes an in-depth review by the data profiling agent with four key stages. (i) The schema and sample data of the dataset are extracted. If the dataset lacks structure, the schema is analyzed by an LLM. (ii) To fully understand the dataset’s contents, schema description and domain knowledge are retrieved from the vector database. (iii) A concise summary of the entire dataset is generated by the LLM and added to its data profile. Figure
2
shows an example, composed of JSON-formatted strings that list profiles of all datasets.

Query Planning.
It includes five steps to accurately generate a logical plan for an NL query. First,
AgenticData
examines the data profiles and assigned tasks, identifies pertinent datasets, and learns access methods using MCP server tools. Second,
AgenticData
seeks related knowledge within vector databases to understand how to calculate the cost. Third,
AgenticData
breaks down the task and provides guidance for planning the logical pathway. Fourth,
AgenticData
reviews the definitions of predefined operators, devises a high-level logical plan incorporating these operators according to the solving logic. Fifth, the high-level logical plan, along with data profiles and operator descriptions, is fed into the data manipulation agent, which develops the comprehensive plan by adhering to each attribute’s instructions. Importantly, any irrelevant datasets and operators are excluded in the final phase to prevent the LLM from overlooking crucial information.

Plan Validation.
Since LLM-based agents using a single-step approach can experience hallucination issues, particularly in extensive contexts, it is crucial to use multiple agents for cross-validation to improve the accuracy of logical plan generation. Figure
2
provides examples of outputs from plan validation agents for cases labeled as
Validated
and
Not Validated
. When agents detect errors, they specify the necessary corrections for subsequent amendments. To ensure effective error identification in the logical plan, two types of validators are used: one checks if the plan fully addresses the task, and the other verifies the logic of the plan against guidelines in the manuals by searching the vector database. For each type, multiple parallel validations (e.g., 3) are conducted, and
AgenticData
only accepts a logical plan if the majority of validations approve it. If the plan is rejected, the mismatching details and error correction suggestions are stored in memory.

Semantic Catalog Construction.
The procedures outlined above leverage unstructured knowledge to improve precision. We use a hierarchical segmentation method for handling unstructured profile files because a single-layer approach will not satisfy the diverse RAG requirements. For instance, schema profiling needs precise and clear attribute details with minimal extraneous information, while planning for a specific task often requires multiple relevant paragraphs containing comprehensive domain knowledge. To achieve this, we first employ a cost-effective LLM (e.g., a 7B model) to divide the text into snippets. Next, we use an embedding model to convert these snippets into vectors, storing them alongside the original snippets in a vector database. Finally, we construct ANN indexes for dense and sparse vectors to accelerate semantic searching.

4.
Semantic Query Optimization

Current semantic query processing systems
(
palimpzestCIDR
;
Lotus
)
use rules and sampling methods to minimize costs. However, they do not support to optimize cost for complex queries with multiple data sources (e.g., joins and tree-structured plans). To address this, we propose a three-step semantic query optimization method to reduce the cost. Initially, equivalent cost optimization rules are applied to the logical plan without degrading quality (e.g., pushing down the relational operators before semantic operators). Then, we refine join orders and reduce estimated selectivity using a Dynamic Programming algorithm. Finally, we employ a cascading optimization approach to reduce LLM costs by initially using embeddings, followed by smaller LLMs for filtering, and finally employing larger LLMs to verify results for each semantic operator.

Step 1: Cost-aware rule-based optimization.

The cost of a semantic physical plan mainly stems from LLM service charges, the typical size of input/output tokens, and the frequency of LLM invocations. In
AgenticData
, we calculate the expected input size for each semantic query plan by considering the average text length derived from the data and the prompt length in the semantic operator. Likewise, we determine the expected output size based on the anticipated output of the semantic operator. The frequency of LLM invocations, influenced by the number of rows, is estimated using a novel semantic plan cardinality estimation method. We begin by using the semantic catalog to identify relevant data and then apply an importance sampling method to estimate cardinality – assigning higher weights to data with greater importance. Finally, the overall cost of a semantic plan is evaluated as
\sum{Cardinality\times(|InputToken|*Fee_{in}+|OutputToken|*Fee_{out})}
.

To optimize costs, we propose three rules for the cost optimization of semantic queries aimed at deferring the execution of semantic operators as long as possible.

RULE 1.
Move the semantic operators after the relational filters. For example, considering a subplan “SemanticExtract(col1)
\rightarrow
SemanticFilter(col1)
\rightarrow
Filter(col2)”,
AgenticData
converts it as “Filter(col2)
\rightarrow
SemanticExtract(col1)
\rightarrow
SemanticFilter(col1)”.

RULE 2.
Move semantic operators that are not used by other operators to the root. Considering a subplan “SemanticExtract(col1, col2)
\rightarrow
SemanticFilter(col1) ”, we convert it as “SemanticExtract(col1)
\rightarrow
SemanticFilter(col1)
\rightarrow
SemanticExtract(col2)”.

RULE 3.
Move the semantic extractions of keys right before the filters or joins using the keys. For example, considering a subplan “SemanticExtract(col1, col2) as (key1, key2)
\rightarrow
SemanticFilter(key1)
\rightarrow
Join(key2, key3)”, and
AgenticData
converts it as “SemanticExtract(col1) as key1
\rightarrow
SemanticFilter(key1)
\rightarrow
SemanticExtract(col2) as key2
\rightarrow
Join(key2, key3)”.

Step 2: Join Order Selection.

Similar to traditional optimizers, reordering join operations to reduce the size of intermediate results is beneficial for cost optimization. Since this is an NP-hard problem,
AgenticData
employs a dynamic-programming-based method. To estimate the selectivity of joins, we first assess the selectivity of semantic filter operations with multi-column predicates through progressive sampling, and then calculate the selectivity of join operations by multiplying the selectivity of each joined branch
(
gaussml
)
.

Step 3: Quality-aware LLM cost optimization.
We have three strategies for implementing a semantic operator: using a larger LLM, a smaller LLM, or an embedding-based approach. The first option offers the highest accuracy but incurs the greatest cost, while the last option provides the lowest accuracy but is more cost-effective. Thus, it is crucial to choose an appropriate method that minimizes cost while maintaining high accuracy. This problem can be modeled as a Multiple Knapsack Problem. Suppose we have
x
LLMs and
y
semantic operators. The goal of quality-bounded LLM selection is to minimize the plan cost by assigning one of the LLM models to each LLM operator while maintaining a total quality constraint. We adopt a greedy-based approach to solve this problem. Initially, we assign the most expensive LLMs to the semantic operators. Then, we iteratively select semantic operators to downgrade their LLM for lower cost. In each iteration, we choose an operator that offers the least quality degradation and the most cost reduction when its LLM is downgraded. The selection process ends when the quality degrades by less than a constant value, such as 0.05.

6.
Conclusions

In this paper, we have proposed an agentic data analytics system,
AgenticData
, which autonomously translates a natural language query into a semantic query plan composed of semantic and relational operators. We have developed a multi-agent framework to generate high-quality semantic plans and introduced effective LLM cascade optimization techniques to reduce costs. Experimental results on widely used benchmarks demonstrate that
AgenticData
significantly outperformed state-of-the-art baselines.
