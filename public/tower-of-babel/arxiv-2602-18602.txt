Package Managers à la Carte Journal: PACMPL - Volume: - -
Ryan Gibb, Patrick Ferris, David Allsopp, Thomas Gazagnaire, Anil Madhavapeddy

Abstract
. Package managers are legion. Every programming language and operating system has its own solution, each with subtly different semantics for dependency resolution. This fragmentation prevents multilingual projects from expressing precise dependencies across language ecosystems; it leaves external system and hardware dependencies implicit and unversioned; it obscures security vulnerabilities that lie in the full dependency graph. We present the Package Calculus , a formalism for dependency resolution that unifies the core semantics of diverse package managers. Through a series of formal reductions, we show how this core is expressive enough to model the diversity that real-world package managers employ in their dependency expression languages. By using the Package Calculus as the intermediate representation of dependencies, we enable translation between distinct package managers and resolution across ecosystems.



A Formal Model of Dependency Resolution

1.
Introduction

Package managers are numerous and diverse, yet all fundamentally solve the same problem, while remaining ad hoc and non-interoperable.
Consider a machine learning research project on Debian Linux, using a combination of C, Rust, and OCaml code for a static binary, with dynamic Python bindings that use GPU drivers, which in turn depend on a particular kernel driver.
Four separate package managers are required to deploy this program: opam (OCaml), Cargo (Rust), pip (Python), and APT (Debian).
If the program is to be portable beyond Debian, even more are required: APK for Alpine, DNF for Red Hat-based Linux.
Dependencies between these ecosystems are managed ad hoc: they are typically unversioned, duplicated across ecosystems, and consequently invisible to security tooling.
Yet all these package managers share a common core: they all take dependencies written in a domain-specific language (DSL)
(
8
)
and ultimately resolve them to output a filesystem subtree.
In this paper, we offer not only a framework to understand and reason about package managers in their commonality and diversity, but also a
lingua franca
for translating between package managers’ dependency languages to enable cross-ecosystem resolution.

We make these contributions:

•

A survey of over thirty package managers across operating system and programming language ecosystems, identifying a shared core of dependency relations, dependency resolution, and deployment; and axes along which they diverge: conflicts, concurrent versions, peer dependencies, features, package formulae, variable formulae, and virtual packages (§
2
).

•

The
Package Calculus
, a minimal formal system which captures dependency resolution in three conditions – root inclusion, dependency closure, and version uniqueness.
We show how the NP-completeness of dependency resolution can be avoided, but is ultimately inherent in capturing the complexity of real-world package managers (§
3
).

•

A model for each axis of variation in dependency expression as an extension to the core calculus, with a sound and complete reduction from each extension back to the core (§
4
).

•

A reduction of the cross-ecosystem translation problem from
n^{2}
to
2n
translators, using the calculus as an intermediate representation for dependency expression, enabling dependency resolution across ecosystem boundaries.
We show when the reductions compose and when they do not (§
5
).

Package management to date has not unified the semantics of different systems; existing interoperability efforts have focused on sharing solving mechanisms between ecosystems with the same semantics (§
6
).
Instead of seeing package managers as monolithic and unrelated, we tease apart the commonality and diversity to show how we can unify the semantics of dependency expression (§
7
).

2.
Defining Package Managers

Package managers evolved from simple tools for automating software installation and underwent a Cambrian explosion in the mid-2000s as it became standard for every new operating system and programming language to define its own solution (Appendix
A
).
They use inconsistent terminology and exhibit a variety of subtly different semantics to solve their domain-specific problems, but share a common core.
We identify the common characteristics of package management (§
2.1
) and define the axes in which diversity emerges (§
2.2
).

2.1.
Commonality

2.1.1.
Dependency

Package managers express
dependency
relations from a
depender
package to a
dependee
package, meaning the depender requires the dependee.
Dependees, sometimes called libraries, can be source code, a shared object, or data files.
If a package is not a dependee, it might be an ‘application’ intended for use by an end-user.
Packages are identified by a
name
and
version
, and a depender can normally express a set of compatible versions of a dependee.

2.1.2.
Resolution

We use dependency
resolution
to refer to the problem of computing, given a package, the set of package names and versions that must be provided to satisfy its dependencies transitively.
A
resolver
performs dependency resolution.
A
resolution
is the set of packages selected by
resolving
dependencies.

2.1.3.
Deployment

Given a
resolution
, package managers will typically provide the packages through
deployment
.
This is typically a filesystem subtree, though for embedded systems such as BusyBox or Yocto Linux, it may be a firmware image.
Source-based language package managers for interpreted languages such as JavaScript might simply place source code into a local directory, as npm does.
System package managers that handle binary packages might unpack archives into the file system hierarchy.
Other package managers might build the software according to instructions in the package metadata, as happens with Cargo, opam, or Cabal (Haskell).
Haiku OS deploys packages by mounting them in a union filesystem, allowing for layering and sharing of multiple packages.
Nix places built packages at a path containing a cryptographic hash of their store derivation in the ‘Nix store’.
Some ecosystems are primarily binary-based, while others are source-based.
In practice, many lie on a spectrum: Gentoo’s binary package hosting allows users to substitute pre-built binaries for source builds, and Nix treats binary deployment as a transparent optimisation of source-based deployment via binary cache substitution.
If a package manager is source-based, it might employ sandboxing to ensure reproducibility and isolation while building packages, as opam and Nix do.

2.2.
Diversity

Table
compares a selection of package managers according to our classification.

2.2.1.
Ecosystems

The first section of Table
describes the particular use case for which a package manager exists.
As noted, package managers generally fall into two categories: language package managers and system package managers.
The intended use for language package managers is in distributing libraries and tools to developers in a specific programming language, and system package managers in administering a full operating system.
The lines between these often blur; system package managers do distribute language libraries, and language package managers can facilitate setting up a development environment with system dependencies.
System package managers tend to lag behind the latest versions of libraries as they maintain a coordinated, coherent package set within the ecosystem, while language package managers prioritise freshness with less coordination.

2.2.2.
Repositories

Almost all package managers group packages together in a centralised repository, allowing for discoverability of packages and curation of version constraints.
For example, Debian maintains a coherent set of versions of packages, and opam uses reverse dependency checks on new releases of dependees to validate dependency version constraints.
Some package managers keep one main repository where changes are made continuously; a ‘rolling release’.
Others periodically release a version of their repository, representing a ‘versioned release’ of their operating system distribution.
Security and other updates may be backported to previous releases of their repository for some time, creating ‘minor’ releases which should be safe for every user to deploy without risking software incompatibilities.
Multiple repositories can also often be combined, for example, with non-free packages, or unofficial user-contributed packages.
Go is a notable exception: packages are identified by URL with no requirement for a central package repository, though Go does maintain a central proxy for availability of modules.

2.2.3.
Toolchain Integration

Some package managers, especially language package managers, have some degree of integration with other parts of the toolchain: build systems and compilers.
opam includes build scripts in package metadata which can invoke a build system or compiler, but is language-agnostic.
This is similar to how a build system’s rules will include invocations of a compiler, such as a makefile target invoking
gcc
.
Other ecosystems have tighter integration; Cargo is the Rust ecosystem’s package manager
and
build system.
The Go tool is a package manager, build system, and compiler.
This enables functionality that might not be otherwise possible without a well-defined API between these parts of the toolchain.
For example, Cargo’s concurrent version support is enabled by using knowledge of package management to provide unique symbols using package versions.
The Unison language has eliminated dependency resolution by content-addressing all definitions: each function is identified by a hash of its syntax tree, so dependencies are pinned to exact hashes rather than version constraints.

Some system package managers also manage configuration files: APT’s
dpkg
tracks configuration files and prompts users to merge, overwrite, or keep local modifications when a package upgrade changes a shipped default.
NixOS
(
22
)
takes this further by treating the entire operating system configuration as a fixed point of composable modules, subsuming system configuration into the package manager.

2.2.4.
Packaging Language

Package managers express dependencies (§
2.1.1
) in a variety of packaging DSLs, normally as static data structures – e.g. TOML,
.deb
control files, or
.opam
files.
Sometimes the DSLs are expressions embedded in Turing-complete languages
(
27
)
– e.g. Homebrew’s (macOS) Ruby, Spack’s (HPC) Python, or Portage’s (Gentoo Linux) ebuild scripts – that can be compiled to a static structure, as the Nix DSL compiles to store derivation
.drv
ATerm files.
These DSLs can support functionality such as variable assignment, boolean algebra, or parameterised dependency relations.
The DSLs store other metadata, such as build scripts, and are often provided by a centralised repository (§
2.2.2
).

The relationship between specification and tooling varies across ecosystems.
Some have a formal specification consumed by disparate tools: Python’s dependency metadata has evolved through
setup.py
,
setup.cfg
, and
pyproject.toml
, with multiple incompatible lockfile formats.
Others have a single reference implementation whose format other tools consume, such as opam’s
.opam
files used by the OCaml build system Dune, or Ruby’s Gemfiles shared between Bundler and Gel.

2.2.5.
Version Constraints

Dependency resolution relies on the version constraints of a dependency (§
2.1.1
).
For example, a package depending on
1\leq\texttt{a}\leq 3
might depend on a set containing
a
with versions
1
,
2
, and
3
.
Some package managers, such as Nix, can only express a dependency on a single version of a package name.
Go’s minimum version selection specifies only a minimum version bound for each dependency, and has a linear-time dependency resolution algorithm (§
3.3
).
In this column we characterise the expressivity of the package manager’s version constraints.

2.2.6.
Conflicts

Package managers can support packages expressing
conflicts
– a dependency on the
absence
of a package.
This can be used for forks of a project which are not co-installable.
Conflicts can be version-scoped, for example to allow conflicting only with versions below 2.0 of a package.
Portage distinguishes
weak blocks
(
!pkg
) from
strong blocks
(
!!pkg
): weak blocks are non-binding preferences to the solver, analogous to Debian’s
Recommends
(§
2.2.13
), while strong blocks enforce hard mutual exclusion.

2.2.7.
Concurrent Versions

Many package managers allow only one version of a package name in a resolution due to deployment constraints such as requiring unique symbols when linking objects, or storing packages at a unique path in the filesystem.
The OCaml compiler toolchain does not support multiple versions of a package, but opam can manage multiple independent installations called switches, each of which can contain different versions of the same package.
System package managers often put a package at a particular path in the filesystem, so multiple versions of the same package would collide.

Other package managers allow
concurrent versions
of the same package to exist in a resolution.
Cargo uses name mangling to support linking multiple versions of a single library into the same binary, where typically only one version can be linked due to duplicate symbols.
Cargo restricts this to packages with different major versions under the semantic versioning scheme: co-linking minor versions would create duplicate, incompatible types in the binary, while different major versions are expected to have distinct APIs
(
12
;
39
)
.
Concurrent versions are therefore isolated – the types of one major version cannot interoperate with another.
Nix
(
21
)
diverges from the Linux Filesystem Hierarchy Standard to place packages at paths containing unique cryptographic hashes, allowing the installation of multiple versions of a package on the same system.
npm allows duplication of dependee packages by storing them in a subdirectory of their depender.

2.2.8.
Peer Dependencies

Package managers which support concurrent versions can also support
peer dependencies
.
In npm, for example, a plugin such as a React component library declares a peer dependency on
react
: it does not bundle its own copy, but instead requires that its parent also depends on
react
with a compatible version.
More generally, given a dependency from a parent (depender) to a child (dependee), a peer dependency is a relation from the child to a peer package, expressing that the parent must also depend on the peer.
The peer version selected must satisfy both the peer dependency version constraints and the parent’s version constraints on the peer.

npm supports peer dependencies, but their behaviour has changed multiple times.
The
--legacy-peer-deps
behaviour is that a peer dependee is only included when the parent also depends on it.
The contemporary behaviour is that peer dependees that are not marked as optional are included regardless of the parent’s dependencies.

2.2.9.
Features

Cargo supports
features
of packages that are used to enable optional functionality that may require additional dependencies.
Dependency relations are parameterised by a set of features, and features can also alter the dependencies of a package.
The resolver unifies features, so a package will be provided with the union of all features requested by its dependers.

In the Python world, dependency specifiers define ‘extras’ which can similarly add dependencies.
Portage’s
USE flags
serve the same role: a dependency can request USE flags with
dev-libs/foo[bar]
, and USE flags can trigger additional dependencies via
bar? ( dev-libs/baz )
.
Like Spack’s
variants
, USE flags additionally allow a package to depend on the
absence
of a flag –
dev-libs/foo[-bar]
in Portage,
depends_on(’foo’, when=’˜bar’)
in Spack – combining features with conflicts (§
2.2.6
).
Cargo features are only additive: a depender can require a feature but not block its presence.

Ecosystems without native feature support sometimes encode features manually in version strings.
For example, opam’s
ocaml-option-*
packages encode compiler options such as
ocaml-option-flambda
and
ocaml-option-afl
as distinct packages, and the
ocaml-options-only-*
packages (e.g.
ocaml-options-only-flambda-fp
) create a distinct package for each exclusive combination.
This is structurally similar to the feature reduction we will define in Definition
4.4.4
, but without feature unification.
Since each combination is a separate version, version uniqueness (§
3.1
) forces a single choice, and the number of versions grows combinatorially with the number of options.

2.2.10.
Package Formula

Some package managers support
package formulae
– boolean expressions over package dependencies.
For example, opam allows a package to declare that it requires either
lwt
or
async
as a concurrency monad (
"lwt" | "async"
), or that it requires both (
"lwt" & "async"
).
APT supports disjunction via the
|
operator in
Depends
fields, for example
Depends: libssl-dev | libgnutls-dev
to accept either TLS implementation.

2.2.11.
Virtual Packages

Closely related to package formulae are
virtual packages
.
APT supports virtual packages which allow multiple packages to provide the same functionality.
Packages can express dependencies on virtual packages that other packages ‘provide’
(
19
)
.
For example, both
openssh-server
and
dropbear-bin
provide the virtual package
ssh-server
.

2.2.12.
Variable Formula

An extension of the package formula (§
2.2.10
) is the
variable formula
.
Some package managers support global and local variables in package formulae (§
4.5
).
For example, in opam, the global variable
os-distribution
makes a formula conditional on the operating system the package manager is deploying the package on.
In APT, dependencies can similarly be parameterised by computer architecture.
The opam package-local
with-test
denotes dependencies that are only required when tests have been enabled for the package.
Python’s dependency groups serve a similar role, having groups such as
docs
or
test
in
pyproject.toml
labelling sets of dependencies that are conditional on the development task.
Variables can also be used to distinguish build-time from run-time dependencies.
Instead of an explicit boolean formula, these can also be implicit labels on dependencies, making them conditional on the platform or architecture.

2.2.13.
Optional Dependencies

Package managers can support
optional dependencies
, which affect the build plan rather than the resolution.
An optional dependency from a depender to a dependee means the depender will use the dependee if and only if it appears in the resolution; the resolver does not attempt to include or exclude it.
In opam, optional dependencies determine build ordering and trigger rebuilds: if the optional dependee is installed, the depender is built after it and may need rebuilding when it changes.
Like features (§
2.2.9
), optional dependencies can enable additional functionality of a package, but are less expressive in that one cannot disable an optional dependency if the optional dependee is in the resolution – their effect is resolution-wide rather than scoped to individual dependencies.

This definition of optional dependencies is distinct from npm’s
optionalDependencies
, which have the same behaviour as Debian’s
Recommends
.
These are a way to request the resolver to include them in the resolution, but not to return an error if this is not possible.
As we are concerned only with satisfiability of resolutions, we do not model this; an extension with solver preferences could capture such best-effort behaviour.

3.
Package Managers, Abstractly

We define a minimal formal system for dependency resolution in package management systems (§
3.1

3.2

3.3
).

(b)

Definition 3.1.2

(Dependency)

We define dependencies

We denote an element of

(a)

\forall\,(n,v),(n,v^{\prime})\in S.\,v=v^{\prime}

(Version Ordering)

3.3.
Resolution Complexity

Real-world package managers navigate the NP-completeness of
DependencyResolution
(Theorem
3.1.4
) in different ways, forming a spectrum from restricted-but-tractable resolution to full NP-completeness.
At the most restricted end, Go’s minimum version selection (MVS)
(
17
)
achieves deterministic, linear-time resolution.
MVS relies on strict adherence to semantic versioning
(
39
)
: minor and patch versions must be backwards-compatible, and only major version changes can break APIs.
Under this assumption, dependencies specify only a minimum version bound, since any version above the minimum within the same major version is guaranteed to be compatible.
Different major versions are treated as different package names
(
16
)
, allowing multiple major versions to coexist in the same resolution.
Rather than selecting the latest available version, MVS selects the
minimum
version satisfying all bounds – the maximum of all minimum bounds.
Since what constitutes a breaking change is ambiguous in practice, selecting the minimum reduces exposure to unintended breakage.
Upgrades are an explicit developer action that rewrites the minimum bounds.

Cargo also allows multiple versions of a package name to exist in a resolution, but it falls short of linear-time resolution as its dependency formulae allow upper bounds within a major version, because sometimes minor version bumps include breaking changes.
Its dependency formulae can also span semver-incompatible
(
39
)
version sets (e.g.
">=1, <3"
,
">=0.1, <0.5"
), whereas you can only depend on
one
major version of a Go module.

At the other end, in ecosystems like OCaml, any API change is potentially breaking due to features such as module inclusion, where a package’s API is implicitly dependent on the APIs of its dependees.
There is no meaningful distinction between major and minor versions, making semantic versioning inapplicable and MVS unviable.
Under MVS, opam devolves into singular dependencies (§
4.9
), as packages are unable to express compatibility with multiple major versions.
For this reason, opam specifies no upper bounds by default, relying on extensive reverse dependency checking of new package releases to verify type-level API compatibility.

Nix sidesteps the spectrum entirely by treating every name-version pair as a distinct package and requiring the exact version of a dependee to be specified.
Derivations are parameterised by their dependencies in the Nix DSL, so version selection is performed manually by the packager rather than by a constraint solver.
In the Nixpkgs package repository, typically only one version of a package is included at a time, and breakages are often due to incompatibilities introduced by updates.

We can formalise the approaches underlying this spectrum as two independent ways to reduce the complexity of resolution:

(1)

Restrict version constraints to lower bounds.

With a total ordering
\leq_{v}
of versions (Definition
3.2.1
), we redefine a dependency relation to only have a minimum bound, with a dependency as
p\Delta_{\min}(n,v)
where
p\in P
,
n\in N
,
v\in V
, and
v
is the minimum bound.
We replace the dependency closure condition (Definition
3.1.3.b
) with,

\forall\,p\in S.\,p\Delta_{\min}(n,v_{1})\implies\exists\,v_{2}\in V.\,(n,v_{2})\in S\land v_{1}\leq_{v}v_{2}

An incompatibility between a depender and a dependee satisfying this relationship is considered ill-specification; the depender and dependee authors must collaborate to fix it.
Without upper bounds, any version above the maximum of all minimum bounds is valid, so a greedy algorithm suffices – selecting the minimum satisfying version for stability, as MVS does, or the latest for freshness.
This reduces the problem to a graph traversal and version sorting in
O(|\Delta_{\min}|+|R|)
time.

(2)

Remove version uniqueness.

Remove resolution condition
3.1.3.c
, allowing multiple versions of a package.
Each dependency can be resolved independently, allowing a greedy algorithm to select any compatible version for each dependency.
This reduces the problem to graph traversal in
O(|\Delta|)
time.

Go’s MVS combines both approaches – the version uniqueness constraint is removed for different major versions (approach
2
), and within a major version, version constraints are restricted to a lower bound (approach
1
).
Cargo also removes the version uniqueness constraint for different major versions, but the practical need for upper bounds within a major version reintroduces NP-completeness.
opam exploits neither, accepting NP-complete resolution in exchange for expressiveness, at the cost of extensive compatibility testing.
Nix adopts approach
2
as well as a restriction stronger than approach
1
: singular dependencies (§
4.9
), where each dependency specifies exactly one version, delegating version selection from the constraint solver to a Turing-complete packaging language.

Where a package manager sits on this spectrum determines the sophistication of its resolver: greedy algorithms suffice at the restricted end, while package managers accepting full NP-completeness employ SAT solvers (Appendix
C
) or conflict-driven clause learning (CDCL) for performance and error reporting.
Similarly, lock files – snapshots of a resolution – are unnecessary under MVS, where the resolution is determined by the minimum bounds alone, but are essential in ecosystems where selecting the latest version makes the resolution non-deterministic over time.

4.
Package Managers, Completely

We illustrate how a variety of properties of real-world package managers (§
2
) can be modelled by a minimally expressive core calculus (§
3.1
) by extending the calculus and reducing these extensions back to the core.
We show this for conflicts (§
4.1
), concurrent versions (§
4.2
), peer dependencies (§
4.3
), features (§
4.4
), package formulae (§
4.5
), variable formulae (§
4.6
), and virtual packages (§
4.7
).
We also consider optional dependencies (§
4.8
), which do not extend the calculus, and singular dependencies (§
4.9
), which are less expressive than the core.

We subscript definitions from the core calculus with a symbol representing the extension in order to differentiate them from the reduction of the extension to the core.
For example, in §

\Gamma

\Delta_{\Gamma}
as

and

Unless we explicitly redefine a subscript of a core calculus definition – as we do with version formula dependency
\Delta_{\Phi}
in Definition

Definition 4.2.1

(Granularity Function)

We define

\Delta_{C}

(Feature Dependency)
.

p\Delta_{f}(n,vs,fs)

as a relation where an element

(n,vs,fs)
as in
\Delta_{f}
.

(Feature Resolution)
.

4.8.
Optional Dependencies

A valid resolution (Definition
3.1.3
) determines
which
packages to install, but not the
order
in which to install them.
Package managers like opam, as part of their deployment (§
2.1.3
), must linearise the resolution into a sequence of build actions such that all the dependees of a package are built before the depender itself.
This requires a topological sort of the dependency graph induced by the resolution – which is only possible when that graph is acyclic.

In practice, dependency graphs can contain cycles.
In Debian, for example,
libgcc-s1
depends on
libc6
(it requires the C library at run time), while
libc6
depends on
libgcc-s1
(it requires the GCC runtime support library).
Both packages are valid in a resolution, but no linear installation order can satisfy both ordering constraints simultaneously.
APT handles this by breaking cycles at an arbitrary point and relying on
dpkg
’s ability to partially unpack packages before their dependees are fully configured
(
19
)
.
In opam, packages can be marked with the
post
variable, which indicates that the dependee is not required at build time, allowing the cycle to be broken explicitly.
Other package managers avoid the problem entirely: npm lays out files in nested directories and relies on Node.js’s module loader to handle cycles between modules.

We formalise this installation ordering as the
build graph
.

Definition 4.8.1

(Build Graph)
.

Given dependencies
\Delta
(Definition
3.1.2
) and a resolution
S
(Definition
3.1.3
) the build graph is a directed graph with vertices
S
and edges:

\displaystyle E=\{(p,(n,v))\mid

\displaystyle p\in S,\ p\Delta(n,vs),\ (n,v)\in S\}

We show that optional dependencies (§
2.2.13
) are purely a build graph consideration: they affect the installation ordering but not the resolution.

Definition 4.8.2

(Optional Dependency)
.

We define optional dependencies as a relation
O\subseteq P\times(N\times\mathcal{P}(V))
.
We denote an element of
O
as
pO(n,vs)
where package
p
will use package
n
with version
v\in vs
if it is in the resolution.

When creating a build graph (Definition
4.8.1
) from the resolution, optional dependees are required before their depender.

E=\{(p,(n,v))\mid p\in S,\ p\Delta(n,vs),\ (n,v)\in S\}\cup\{(p,(n,v))\mid p\in S,\ pO(n,vs),\ (n,v)\in S\}

Example 4.8.3.

Consider,

(A,1)\Delta(B,\{1\})\qquad(A,1)\Delta(D,\{1\})\qquad(B,1)\Delta(C,\{1\})\qquad(B,1)O(D,\{1\})

For
Q=\{(B,\{1\})\}
, the resolution is
S=\{r,(B,1),(C,1)\}
, and the build graph is

.
For

4.9.

5.
Package Managers à la Carte

We return to the motivating example of §
1
, using four package managers for a single project.
Dependencies between these ecosystems are unversioned; the binary will fail if APT has not been used to install the required C libraries and drivers from the Debian repository at compatible versions.
Build sandboxing prevents one package manager from invoking another, so opam cannot call Cargo during a sandboxed build.
This leads to ad hoc solutions, such as opam invoking a system package manager to install dependencies via its depext mechanism
(
35
)
.
Another workaround is vendoring dependees across ecosystems – copying the source code into a project’s version control system – so that versions are fixed and dependencies are available inside sandboxed build environments.
Similarly, containerisation technologies, like Docker, are used to sidestep the problem by bundling all dependencies together.
To avoid vendoring or bundling in containers, packages can be duplicated between ecosystem-specific package formats, such as Rust projects packaged in opam.
But these workarounds carry serious costs: vendored and duplicated packages require ongoing maintenance when new versions are released; and the dependencies they introduce are hidden from package managers, rendering security vulnerability tracking incomplete.

Mechanically translating packages between
n
ecosystems directly requires
n^{2}
translators, each of which must understand both the source and target dependency languages.
We observe that the reductions of §
4
are proofs that the extensions are expressible in the core calculus, but they also serve as compilation passes that lower extended instances to core instances, and can be reversed to lift reduced core instances to extended instances.
The Package Calculus serves as an intermediate representation for dependency expression: each ecosystem need only define a translation to and from the core, reducing the translation problem from
n^{2}
to
2n
translators.

5.1.
Transpiling Packaging Languages

Each ecosystem natively supports a subset of the extensions defined in §
4
(Table
).
A translation from ecosystem
A
to ecosystem
B
follows the pipeline:

L_{A}\xrightarrow{\;\textup{parse}\;}\Delta_{A}\xrightarrow{\;\textup{lower}\;}\Delta\xrightarrow{\;\textup{lift}\;}\Delta_{B}\xrightarrow{\;\textup{emit}\;}L_{B}

where
L_{A}
and
L_{B}
denote the source and target DSLs, and
\Delta_{A}
and
\Delta_{B}
denote the source and target dependencies, respectively.

Lowering (frontend).

The source DSL is parsed into an instance of the extended calculus determined by
E_{A}
, and a

reduces this to a core calculus instance
(\Delta,r)
.
When an ecosystem supports multiple extensions, the lowering composes their reductions, subject to the ordering and type-interaction constraints discussed in §
5.2
.
Soundness and completeness ensure valid resolutions are preserved:
\mathcal{S}(\Delta,r)\cong\mathcal{S}_{E}(\Delta_{E},r_{E})
.

Lifting (backend).

A

reconstructs an extended instance from the core.
Each reduction encodes extended constructs as synthetic packages with structured names
\langle\cdot\rangle\in N
; the backend decodes these names to recover the original constructs.
Where the target ecosystem does not support an extension, the core encoding is emitted directly.
Lifting is desirable because a solver that understands the target’s native extensions can exploit their structure – for example, propagating conflicts directly rather than through synthetic packages.

Each translation therefore need only handle the extensions its ecosystem supports: for instance, Cargo dependencies can be lowered to the core and solved by an opam-based resolver that knows nothing about features, yet the feature selections can be extracted from the core resolution (Theorems
4.4.5
and
4.4.6
).
By the same token, as-yet-undiscovered dependency expression semantics admitting a sound and complete reduction to the core can be incorporated into a translation.

5.2.2.
Limits of Composition

The composition above succeeds because the feature reduction is version-preserving: it does not introduce new versions, so version granularity passes through unchanged.
Not all reductions compose so cleanly.

Invariant Violation.

The conflict reduction (Definition
4.1.3
) and the negation encoding of the package formula reduction (Definition
4.5.4
) both introduce synthetic packages with two versions that encode mutual exclusion via version uniqueness.
The Concurrent Package Calculus relaxes version uniqueness to version granularity, allowing both versions to coexist and breaking the encoding.

A correct composition requires reducing concurrent versions
first
– restoring version uniqueness – then applying the conflict or formula reduction.
However, the concurrent reduction renames packages via
\langle n,g(v)\rangle
, so the conflict and formula reductions must be made aware of the concurrent versions reduction.
Alternatively the concurrent versions reduction could be made conflict-aware, so that the granularity function for the synthetic packages always returns
\epsilon
and they conflict in Definition
4.2.2.c
.

Interacting Extensions.

Even when invariants are preserved, extensions whose dependency types interact require reductions that are aware of each other’s constructs.
For example, Portage combines features (§
4.4
) with package formulae (§
4.5
), and a formula atom can carry feature annotations:
|| ( foo[bar] baz )
.
A correct composition requires the formula atom
(n,vs)
(Definition
4.5.1.a
) to support features (e.g.
(n,vs,fs)
), and the feature additional dependency target
(n,vs,fs)
(Definition
4.4.3.c
) to support formulae (e.g.
\psi
).

Ecosystem Variation.

The semantics of individual extensions can also differ subtly between ecosystems.
For example, npm supports two different behaviours for peer dependencies depending on the resolver version (§
4.3
), and opam’s filtered dependencies combine package formulae with variable conditionals in a single construct, which we represent by composing the package formula (§
4.5
) and variable formula (§
4.6
) extensions – though a dedicated first-class extension could model this more directly.
The extensions and reductions presented here are not intended as a fixed catalogue, but as a framework: extensions and reductions can be defined to capture ecosystem-specific semantics, equipped with reductions to the core calculus, and composed with existing extensions following the principles above.
By using a minimal core calculus we describe the semantics of dependency expression precisely and prevent mistakenly translating functionality from one ecosystem to functionality in another ecosystem with the same name but subtly different semantics.

6.
Related Work

Dependency Resolution.

The idea of using a formalism to aid with package versioning dates back to the Optimal Package Install/Uninstall Manager (Opium)
(
48
)
in 2007, which adapted Debian’s apt-get to use a SAT solver for dependency resolution.
Opium’s formalism is close to our Conflict Package Calculus; it encodes Debian’s dependencies and conflicts in a SAT problem, expanding version formulae to sets.
We describe how a dependency resolution algorithm can prioritise fresher resolutions (Definition
3.2.2
); Opium goes further by optimising an objective function over resolutions via pseudo-boolean and ILP solvers, which it uses to define the install and uninstall problems.

Later work on the Common Upgradeability Description Format (CUDF)
(
46
)
generalised the solver interface into a file format that could be consumed by specialised package resolvers.
One such early resolver used answer-set programming
(
24
)
, which also found use in high-performance computing software infrastructure for solving dependencies with support for a rich set of user-specified resolver preferences
(
23
)
.
CUDF provides a fixed vocabulary of dependency constructs – depends, conflicts, and provides – with integer versions, rich optimisation criteria, and support for upgrade semantics (modelling the currently installed state).
Despite the goal to be the
common
format, the fixed-vocabulary nature of CUDF means it has not seen adoption beyond the Debian and opam ecosystems, and package managers with varying semantics have only proliferated since: Cargo’s features and concurrent versions, npm’s peer dependencies, and pip’s extras; none fit CUDF’s fixed vocabulary.

Abate et al.
(
1
)
observed in 2020 that while SAT-based dependency solving did find traction among some package manager implementations, reusable components for version solving had not seen wider adoption.
In recent years, some of the larger package ecosystems such as npm are under severe scaling pressure, and it is becoming increasingly important to revisit the question of how to reuse knowledge across ecosystems.
For example, PacSolve’s MaxSMT based resolver is a drop-in replacement for npm that reduced vulnerabilities in resolved packages and picked fresher and fewer dependees
(
38
)
.
Approximate solving has also been useful for package selection under bounded latency situations
(
28
)
.
However, these systems are all tied to a single ecosystem: PacSolve targets npm, Spack’s ASP solver targets HPC, and opam’s CUDF bridge targets OCaml – none can resolve dependencies that cross ecosystem boundaries.
PubGrub
(
49
)
is a CDCL-based dependency resolution algorithm created for Pub (Dart’s package manager) that has since been adopted by Bundler (Ruby), Poetry (Python), and Swift Package Manager, among others.
The pubgrub-rs Rust implementation
(
40
)
contains an encoding of concurrent versions and features very similar to our reductions in §
4.2
and §
4.4
.

Open-source Ecosystems.

There is an enormous and increasing amount of open-source software being published, and the problem of managing dependencies will only grow more acute.
Software Heritage is building a universal archive of this source code
(
3
)
, and the Package Calculus offers the chance to build a higher-level and cross-ecosystem semantic representation of these interdependencies.

Maintainers of some of the key distributions such as Debian (which form the basis for many other downstream products) are having to scale their automation in order to manage the ever-growing package set
(
7
)
and vulnerabilities
(
31
)
.
The Package Calculus approach of bringing common semantic meaning across language ecosystems should help reuse tooling that is currently language-specific to support the distribution maintainers such as those in Debian or Red Hat-based Linux.
Being able to reason about large-scale dependencies is also important for alleviating the reproducibility crisis in scientific computing
(
29
)
, and the Package Calculus could (with sufficient tooling) support the longer-term availability of published scientific results.

Build Systems.

Package management is closely tied to build systems, which are also surprisingly poorly specified
(
33
)
.
Build systems and package management systems are sometimes unified in newer toolchains (Table
), but doing so makes it difficult to compose projects that span ecosystems (e.g. consider the difficulty of depending on a Rust library from OCaml code with just two package managers involved).
Therefore, the Package Calculus approach of specifying a formalism that can be implemented as a translation library across package ecosystems maintains the separation from the underlying build systems.
In the long term, creating a composable formal theory of build systems and package managers
(
4
)
would let us combine cross-ecosystem codebases to conduct correctness testing across the vast amount of source code published
(
32
)
.
It would also allow the use of fuzzing techniques on the Package Calculus to spot incorrect packaging specifications, a technique already successfully applied to build systems
(
30
)
.

Software Supply Chain Security.

The increasing complexity of cross-ecosystem dependency chains puts pressure on the security of software supply chains, both on the choice of dependees selected for a software project
(
6
;
5
;
50
)
but also in vulnerabilities in the many package managers available
(
11
;
10
)
.
Software Bill of Materials (SBOMs) manifests are being rapidly adopted
(
13
)
to specify the full set of versioned dependees that go into a given application.
However, the same problem of uneven quality across ecosystems applies here, with the JavaScript ecosystem being particularly unpredictable
(
41
)
.
The Package Calculus could be used to generate SBOMs systematically, to reduce transitive trust dependencies across language and OS ecosystems
(
43
)
, drop resource usage by debloating unnecessary packages
(
37
)
, and reduce the latency of applying security updates in third-party dependees
(
42
;
44
)
.

7.
Conclusion

We have presented the Package Calculus, a minimal formal system for dependency resolution that captures the common core of over thirty package managers, and modelled their diversity as extensions with reductions back to the core.
The reductions serve a dual purpose: they prove the extensions are expressible in the core, but also act as compilation passes that lower ecosystem-specific dependency languages into a common intermediate representation, reducing cross-ecosystem translation from
n^{2}
to
2n
translators.
Some reductions compose cleanly – we proved this for features with concurrent versions – while others require ordering constraints or mutual awareness (§
5.2.2
).
Returning to §
1
, this provides the formal foundation for dependencies from OCaml, Python, Rust, and system packages to be lowered, resolved together, and lifted back – rather than relying on four separate uncoordinated tools.
The formalism does not model deployment or build semantics, which remain ecosystem-specific; practical tooling to parse ecosystem DSLs into the calculus and emit solutions back is a natural next step.

Appendix A
A Short History of Package Managers

The original Unix and pre-Unix operating systems had no concept of automated package management; the operating system was distributed with libraries and utilities, and third-party software had to be built and installed manually.
System V Release 4.0 in 1988 included the ‘packaging tool’
pkgadd
and related commands to automate the process of installing packages onto the system from a source such as a tape, CD-ROM, or networked filesystem, as well as updating and removing them
(
45
)
.
It verified that dependees were installed, but did not automatically select and install compatible versions.
Other commercial Unix vendors created similar systems in the following years, as well as early Linux (1991) distributions with Slackware’s
pkgtool
(1993), Debian’s
dpkg
(1994), and Red Hat’s
rpm
(1995).
FreeBSD’s Ports (1994) introduced automatic dependee installation, relying on regular expressions on package names to ensure application binary interface (ABI) compatibility.

Early programming-language package managers emerged in the form of archive networks for distributing software over the Internet with the Comprehensive
T
e
X
Archive Network (CTAN) in 1992
(
25
)
, the Comprehensive Perl Archive Network (CPAN) in 1995
(
14
)
, and the Comprehensive R Archive Network (CRAN) in 1997
(
26
)
.
These early repositories provided centralised distribution and discoverability of packages.
The Perl module
CPAN.pm
and CRAN’s
install.packages()
allowed for the automatic installation of dependees, but always selected the latest indexed version of each, performing no version solving.
CTAN had no native automated installer; package management was later provided by TeX Live’s
tlmgr
(2008), which likewise installed only the latest versions, though TeX Live mitigated incoherence by distributing packages as a curated annual snapshot rather than a continuously updated live index.

Debian’s Advanced Packaging Tool (APT) (1998), building atop the existing
dpkg
, resolved compatible versions of dependencies based on version constraints and automatically installed them.
Red Hat’s Yellowdog Updater Modified (YUM) (2002) brought similar capabilities to RPM-based distributions building on
rpm
, later superseded by Dandified YUM (DNF) (2012).
Dependency resolution in these systems was shown to be NP-complete by Di Cosmo in 2005
(
20
)
.
Slackware is a notable exception to the norm in package management dependency resolution; official mechanisms do not provide any support for dependency tracking, instead relying on the user to manually install dependees of a package.

By the mid-2000s, automatic dependency resolution with version constraints became standard practice.
Package managers began to be built as monolithic systems expected of any new operating system or programming language.
This evolutionary pattern extends beyond operating systems and programming languages: plugin ecosystems for web browsers, text editors, and applications have similarly progressed through centralised archives, automatic installation, and dependency resolution.
As these package managers have developed, the semantics of their dependencies have diverged, each introducing functionality to address their ecosystem’s specific needs.
