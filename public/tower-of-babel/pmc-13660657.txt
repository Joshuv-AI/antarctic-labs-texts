Protocol for detecting germline copy number variants from whole-exome sequencing using agent-assisted Snakemake workflows
Authors: Xiang Chen
Published: 2026

ABSTRACT
SummaryGermline copy number variants (gCNVs) are vital for diagnosing rare monogenic disorders. Here, we present a containerized, agent-assisted Snakemake protocol for detecting, annotating, and visualizing gCNVs from short-read whole-exome sequencing data. We describe steps for constructing baseline models, executing CNV calling, annotating variant pathogenicity using public datasets, and rendering interactive visual reports. This automated workflow simplifies routine management and ensures cross-platform reproducibility through a unified interface.

Before you begin

High-throughput Whole Exome Sequencing (WES) has become widely adopted for the diagnosis and screening of rare genetic disorders, substantially improving molecular diagnostic yield in clinical practice. However, accurate detection of germline CNVs (gCNVs) from short-read WES data remains technically challenging. Several intrinsic limitations affect WES-based CNV analysis: 1) incomplete breakpoint resolution because many CNV breakpoints occur outside captured exonic regions; 2) uneven target capture efficiency caused by GC-rich or repetitive regions; 3) limited sensitivity for small CNVs because of sparse probe spacing; and 4) batch effects introduced by sequencing platform differences, library preparation methods, and experimental variability. These limitations affect essentially all WES-based CNV detection methods, including the Genome Analysis Toolkit (GATK) gCNV framework1 used in this protocol.

The GATK gCNV caller is currently one of the most widely used approaches for CNV detection from exome sequencing data. By leveraging Bayesian modeling and cohort-based normalization, GATK gCNV improves specificity and robustness compared with earlier depth-based methods. Nevertheless, practical implementation often requires complex software configuration, coordinated execution of multiple preprocessing steps, and careful management of model training and inference. To address these practical challenges, we developed a fully reproducible Snakemake-based workflow for WES CNV detection. Compared with traditional shell-script pipelines, the workflow provides improved modularity, reproducibility, scalability, and execution transparency through automatic dependency management, checkpoint tracking, parallel execution, and containerized deployment.

All workflow files, scripts, configuration files, and example datasets are available in the GitHub repository (https://github.com/model-lab/Identify_gCNV_with_WES). The workflow is implemented in Snakemake, which automates task scheduling, dependency management, execution tracking, and reproducible pipeline execution. All command-line examples provided in this protocol have been validated using the included demonstration dataset in a standard Linux environment. Unless otherwise specified, commands should be executed within the supplied Conda environment or the recommended Docker container. Throughout this protocol, input files, output directories, configuration files, and naming conventions are standardized. Users generally need only modify project-specific file paths and sample identifiers while preserving the overall directory structure and file formats. This modular Snakemake implementation simplifies workflow customization and enables scalable, reproducible CNV analysis compared with conventional shell script–based pipelines.

Innovation

Beyond the standard GATK-gCNV analytical workflow, this protocol introduces an integrated framework designed to optimize usability, automation, and reproducibility. Key advancements include a reproducible Snakemake workflow that ensures automated dependency tracking, checkpoint management, and scalable parallel execution. Software environments are standardized via Docker and Conda to guarantee version control across platforms. To streamline execution, the protocol incorporates agent-assisted automation utilities that automate routine workflow planning, project validation, command generation, quality control aggregation, and standardized result packaging. These utilities reduce manual configuration and user errors while preserving Snakemake’s underlying execution engine. Furthermore, the framework provides flexible execution modes, supporting both cohort-specific model training and rapid direct inference using pre-trained models. Finally, it seamlessly connects raw calling to comprehensive downstream analyses, including CNV annotation, quality assessment, and publication-ready report generation. Validated on publicly available 1000 Genomes Project (1kGP) WES data, the workflow accepts FASTQ or BAM/CRAM inputs for end-to-end processing.

To maximize computational reproducibility, this workflow employs a software management strategy based on Conda and Docker. For cross-platform support, Windows users should run Docker Desktop with Windows Subsystem for Linux 2 (WSL2), while macOS users can execute it via Docker, given sufficient computational resources.

As part of the workflow, the visualize_knotAnnotSV rule automatically invokes the wrapper script scripts/visualize_knotannotsv.py to generate interactive HTML reports from the annotated CNV table. These reports facilitate rapid inspection of CNV-associated genes, genomic coordinates, overlapping pathogenic regions, and annotation information integrated from external databases. All generated reports are organized under outputs/figures/knot/, enabling convenient cohort-level review and manual interpretation of CNV results.

CRITICAL: Visualization is performed after joint segmentation and annotation to ensure that recurrent or shared CNV events are represented consistently across all samples in the cohort. This improves the interpretation of cohort-wide CNV patterns and facilitates downstream clinical review. The generated HTML reports provide interactive filtering, searchable annotation tables, database hyperlinks, color-coded pathogenicity indicators, and customizable annotation columns (Figure 1). The reports can be opened directly in modern web browsers, whereas the accompanying XLSM files can be viewed using standard spreadsheet software. The modular design of the workflow also enables users to incorporate additional annotation-aware visualization frameworks by extending the corresponding Snakemake rules.

The annotated CNV table represents the principal output of the protocol and should be used as the starting point for downstream biological interpretation. Candidate pathogenic CNVs can be prioritized according to gene content, predicted functional consequences, ACMG evidence, population frequency, and disease relevance with visualization of the annotated CNV table. Read-depth visualizations and IGV inspection provide complementary evidence supporting the computational CNV calls and are particularly useful for evaluating exon-level deletions or duplications before downstream validation.

In addition to the biological outputs, successful execution of the agent-assisted workflow utilities is reflected by the automatic generation of workflow management artifacts, including validated workflow plan files, execution logs, standardized directory structures, and quality-control summaries. Successful execution of the workflow can be assessed using several practical quality-control criteria. First, the Snakemake workflow should complete without failed rules or interrupted tasks, and all expected output directories should be generated successfully. Second, the final annotation files, quality-control reports, and visualization outputs should be produced without software errors. Third, sequencing coverage should be sufficient for reliable CNV detection, and quality-control reports should not indicate abnormal target coverage or excessive missing intervals. Finally, representative CNVs should exhibit read-depth patterns consistent with the predicted copy-number state in the generated visualization files. When orthogonal validation data, such as Whole Genome Sequencing (WGS), are available, representative CNVs are expected to show concordant copy-number status, providing additional support for the detected events.

Quantification and statistical analysis

To improve CNV detection accuracy, we suggest filtering out false positives by analyzing CNV frequencies within the studied cohort. Frequently identified CNVs in certain regions are often attributable to sequencing bias, whereas rare CNV regions are more likely to represent true positives. We propose that CNV frequencies within a large cohort should follow a normal distribution. Typically, CNVs with frequencies significantly exceeding the 95% confidence interval of the cohort’s overall distribution are considered less reliable. Additionally, CNV annotation combined with existing databases that link CNV frequency and pathogenicity can further refine the filtering process.

Limitations

While this protocol provides an automated, reproducible workflow for gCNVs discovery from WES data, several inherent limitations remain. Primarily, WES is less optimal for clinical CNV detection compared to WES because CNV breakpoints often lie in non-coding intronic or intergenic regions outside the targeted exons, while typical short read lengths further hamper exact breakpoint identification. Consequently, CNV calling relies heavily on target capture depth, making performance highly susceptible to sequencing biases, low-mappability zones, high GC-content regions, and batch effects introduced by DNA capture technologies and sequencing procedures. Benchmark studies on real-world WES data consistently report low sensitivity and recall across existing computational tools, leading to a noticeable rate of false positives. In practice, high-frequency CNVs in 5′UTR-CDS, CDS-3′UTR, or UTR regions frequently arise from systematic sequencing bias and require frequency-based filtering, while improper CNV merging may split contiguous non-overlapping regions and necessitate manual or plot-based inspection. Indeed, our validation on 1000 Genomes Project data revealed that several CNVs initially deemed true positives were confirmed as false positives when evaluated against whole-genome sequencing ground truth (see the supplemental materials for false-positive cases). Additionally, cohort-based baseline model training requires a minimum number of high-quality control samples under identical capture kits to establish stable read-depth expectations, constraining single-sample processing without pre-trained cohort references. To mitigate these challenges, users should validate CNV reliability across larger cohort datasets to reduce false positives and consider developing downstream machine learning models to further refine candidate variant prioritization.

Troubleshooting

Problem 1

Select the appropriate genome version before executing this protocol. This pertains to the data preprocessing outlined in the ‘before you begin’ section, as well as the Baseline CNV Model Training steps.

Potential solution

The genome version chosen during the WES data preprocessing mapping step dictates the genome version for all subsequent reference files in this protocol. While the protocol is flexible regarding genome versions, maintaining consistency throughout the entire procedure is crucial. Different genome versions have a negligible effect on CNV detection rates; however, for accurate CNV annotation using databases, we advise using the widely accepted human genome versions GRCh37 and GRCh38.

Problem 2

In the “Prepare the software environment” step, differences in software dependencies and installation requirements among GATK releases may lead to installation failures or compatibility issues. During CNV model training, changes to the gcnvkernel Python module across GATK versions may also affect training parameters and model performance. In addition, some GATK releases do not support sample names shorter than four characters, which can cause model training to fail.

Potential solution

GATK is actively maintained, and newer releases frequently resolve installation, compatibility, and functionality issues present in earlier versions. If installation or model training problems occur, we recommend using the latest stable GATK release rather than the default version specified in key resources table, provided that compatibility with the remaining workflow components is maintained. Users should also ensure that sample names contain at least four characters before initiating model training.

Problem 3

Strategies for genetic screening of individual CNV results involve methods to exclude false positives and enhance screening efficiency.

Potential solution

CNV detection accuracy is strongly influenced by the characteristics of the input WES data, including the sequencing institution, sequencing platform, and target capture technology. To minimize technical bias, we recommend using control samples generated with the same sequencing platform, sequencing center, and capture kit for both baseline model training and CNV detection. If matched control data are unavailable, increasing the size and diversity of the training cohort can improve model robustness across different sequencing conditions. In addition, aggregating individual CNV calls into a cohort-level callset and annotating variants with population and clinical databases enables frequency- and annotation-based filtering, thereby reducing false positives and improving the prioritization of candidate CNVs.

Problem 4

Reduced sensitivity for detecting exon-level or smaller CNVs.

Potential solution

Detection of small CNVs depends on the resolution of the baseline model and interval design. To improve sensitivity for exon-level CNVs, we recommend training the model using intervals optimized for smaller events. During the CNV model training stage, reducing the --padding parameter can increase breakpoint resolution and improve the detection of small CNVs. However, smaller padding values may also increase sensitivity to technical noise, so parameter optimization should be performed according to the sequencing data quality and target capture design.

Problem 5

CNV model training is computationally intensive and requires a long execution time.

Potential solution

To improve computational efficiency, we recommend training baseline models separately for each chromosome, allowing multiple training jobs to run in parallel. The resulting chromosome-specific models can then be applied independently and integrated during the CNV detection stage. This strategy substantially reduces overall runtime while maintaining detection performance.

Problem 6

The Snakemake workflow fails to execute because of missing rule dependencies, incorrect file paths, or incomplete workflow plan files.

Potential solution

Ensure that the workflow is executed from the Identify_gCNV_with_WES/directory and that all file paths specified in workflow/config.yaml and the workflow plan (∗.plan.yaml) are correct and accessible. Before running the workflow, perform a Snakemake dry run:snakemake --snakefile workflow/Snakefile --configfile plans/EXAMPLE.plan.yaml -n

snakemake --snakefile workflow/Snakefile --configfile plans/EXAMPLE.plan.yaml -n

This command validates the workflow graph, rule dependencies, input/output files, and expected execution plan without running any jobs, allowing users to identify configuration errors before actual execution.
