Paweł Liskowski, Benjamin Han, Paritosh Aggarwal, Bowei Chen, Boxin Jiang, Nitish Jindal, Zihan Li, Aaron Lin, Kyle Schmaus, Jay Tayade, Weicheng Zhao, Anupam Datta, Nathan Wiegand, Dimitris Tsirogiannis

Abstract
. Integrating AI’s semantic capabilities directly into SQL is a key goal, as it would enable users to write declarative queries that seamlessly blend relational operations with semantic reasoning. This would allow for effortless querying of both structured and unstructured data. However, achieving production-scale efficiency for semantic operations presents significant hurdles. Semantic operations inherently cost more than traditional SQL operations and possess different latency and throughput characteristics, making their application at large scales prohibitively expensive. Moreover, current query execution engines are not designed to optimize semantic operations, often leading to suboptimal query plans. This optimization challenge is compounded because the cost and selectivity of semantic operations are typically unknown at the time of compilation. Snowflake’s Cortex AISQL is a query execution engine that addresses these challenges through three novel techniques informed by production deployment data from Snowflake customers. First, AI-aware query optimization treats AI inference cost as a first-class optimization objective, reasoning about large language model (LLM) cost directly during query planning to achieve 2–8 × \times speedups. Second, adaptive model cascades reduce inference costs by routing most rows through a fast proxy model while escalating uncertain cases to a powerful oracle model, achieving 2–6 × \times speedups while maintaining 90–95% of oracle model quality. Third, semantic join query rewriting lowers the quadratic time complexity of join operations to linear through reformulation as multi-label classification tasks, achieving 15–70 × \times speedups with often improved prediction quality. AISQL is deployed in production at Snowflake, where it powers diverse customer workloads across analytics, search, and content understanding.



1.
Introduction

The growth of large language models (LLMs)
(
3
;
26
;
31
;
33
)
has transformed how organizations interact with data. Modern enterprises now store vast volumes of unstructured content – documents, images, audio, and text – alongside traditional structured data in relational tables. While contemporary data warehouses excel at processing structured data with SQL, they lack native support for semantic reasoning over unstructured information. As a result, users who need to filter documents by topic relevance, join tables based on semantic similarity, or summarize customer feedback must export data to external systems, write custom scripts, or build complex pipelines that orchestrate LLM APIs outside the database. The result is significant friction: data must be moved across systems, increasing latency and cost; manual orchestration becomes error-prone; and the database loses the ability to optimize the workload end-to-end.

We present Snowflake’s Cortex AISQL, a SQL engine that enables users to
talk
to their data, both structured and unstructured, through native AI operators integrated directly into SQL. AISQL extends SQL with primitive operators that bring LLM capabilities to the relational model:
AI_COMPLETE
for text generation,
AI_FILTER
for semantic filtering,
AI_JOIN
for semantic joins,
AI_CLASSIFY
for categorization, and
AI_AGG
and
AI_SUMMARIZE_AGG
for semantic aggregations and text summarizations, respectively. These operators naturally compose with traditional SQL constructs, allowing users to write declarative queries that blend relational operations with semantic reasoning. For example, a product manager analyzing customer feedback can filter support transcripts for conversations where customers expressed frustration (
AI_FILTER
), semantically join them with a product catalog to identify which specific products were discussed (
AI_JOIN
), classify the severity of each issue (
AI_CLASSIFY
), and generate executive summaries grouped by product category (
AI_SUMMARIZE_AGG
) – all within a single declarative SQL query that combines structured sales data with unstructured conversational text.

AISQL builds on an emerging body of work in semantic query processing. Systems such as LOTUS
(
27
)
introduced semantic operators for processing pandas-like dataframes, Palimpzest
(
21
)
provided a declarative framework for LLM-powered data transformations, while ThalamusDB
(
13
)
explored multimodal query processing with natural language predicates. Commercial systems have also adopted this direction: Google BigQuery
(
8
)
provides AI functions such as
AI.CLASSIFY
for semantic operations, while Azure SQL exposes row-level LLM invocations within SQL queries. However, making semantic operators efficient at production scale in a distributed database remains a fundamental challenge. Such operators are orders of magnitude more expensive than traditional SQL operations. For example, a single
AI_FILTER
predicate applied to a million-row table could invoke an LLM thousands of times, leading to prohibitive execution costs and latency. Traditional query optimization heuristics, such as minimizing join costs or pushing filters below joins, can produce extremely inefficient plans when AI operators are involved. Furthermore, semantic operators behave as black boxes to the query optimizer. Unlike conventional predicates, their cost and selectivity cannot be inferred from historical statistics or column distributions. Estimating how many rows will pass an AI-based filter, or how expensive that evaluation will be, is nearly impossible at compile time. Yet, these placement and cost estimates can alter overall query performance by orders of magnitude.

The AISQL query execution engine addresses these challenges through a combination of novel optimization techniques and runtime adaptations, showcasing that semantic operations can be effectively integrated into database engines, thus enabling use cases that analyze both structured and unstructured data. Production deployment data from Snowflake customers directly shaped our design choices. We observed that LLM inference costs far exceed traditional query processing expenses, with AI operations accounting for the dominant share of execution budgets. Multi-table queries are also prevalent, representing nearly 40% of all AISQL workloads and consuming well over half of aggregate computation time (see Section
4
for details). These observations guide the design of our optimization strategies that are applied at both the query and individual operator level:

(1)

AI-aware query optimization.
The AISQL optimizer treats AI inference cost as a first-class optimization objective. Rather than optimizing solely for traditional metrics like join cardinality, the optimizer considers the monetary and computational cost of LLM invocations when determining operator placement and predicate evaluation order. For instance, the optimizer may pull expensive multi-modal
AI_FILTER
predicates above joins or reorder multiple AI predicates based on their relative cost, even when traditional selectivity-based heuristics would suggest otherwise. These optimizations enhance the performance of the AISQL query, with the degree of improvement depending on factors such as the selectivities of various query operators (e.g., predicates, joins). Across synthetic datasets and queries modeled after actual Snowflake customer workloads, we have measured 2
\times
–8
\times
more performant execution plans. During execution, runtime statistics about predicate cost and selectivity enable dynamic reordering to adapt to actual data distributions. By reasoning about LLM cost directly during query planning, AISQL now makes even complex multi-modal workloads efficient and scalable.

(2)

Adaptive model cascades.
To reduce inference costs and maintain query prediction accuracy, AISQL implements model cascades for
AI_FILTER
operations. A fast and inexpensive proxy model processes most rows, while a powerful oracle model handles only uncertain cases. The system learns confidence thresholds online through importance sampling and adaptive threshold estimation, partitioning rows into accept, reject, and uncertainty regions. Our algorithm is tailored for a distributed execution environment and achieves 2–6
\times
speedups across various benchmarks while maintaining 90–95% of oracle model quality. On the NQ dataset, the cascade achieves 5.85
\times
speedup and preserves the near-identical F1 score; see Section
6.2
for details.

(3)

Query rewriting for semantic joins.
Naive semantic joins using
AI_FILTER
typically require a quadratic number of inference calls making them impractical for large datasets. The AISQL engine rewrites certain join patterns into multi-label classification problems using
AI_CLASSIFY
, reducing complexity from quadratic to linear. Our implementation not only achieves 15–70
\times
speedups across a number of datasets but often improves prediction quality by enabling better comparative reasoning. On the CNN dataset, the rewrite achieves 69.52
\times
speedup, reducing execution time from 4.4 hours to 3.8 minutes; see Section
6.3
for details.

AISQL is deployed in production at Snowflake, where it powers diverse customer workloads across analytics, search, and content understanding. It is fully integrated into the SQL engine and is optimized for efficiency and high prediction quality, as demonstrated by our extensive experimental analysis.

The commoditization of AI, driven by the rapid growth and adoption of LLMs, has introduced new workloads and reshaped existing data-management tasks. AI agents today need to operate on data traditionally stored and managed in a warehouse. At the same time, users want to run analytical workloads and extract insights from unstructured data (e.g., documents, images, audio, and video). Section
4
analyzes AI workloads at Snowflake.

To support these workloads, we introduced the
Cortex Platform
into the Snowflake architecture (Figure
1
). The Cortex Platform is a multi-tenant service that executes both interactive (e.g., via REST) and batch AI workloads (e.g., via SQL). Its primary components are (a)
Inference Engines
, (b) the
Scheduler
, and (c) the
API Service
.

The Inference Engines provide the core capabilities of the Cortex Platform. Each engine is a specialized service that runs trained models (e.g., LLMs) to generate predictions or insights from data. An engine manages both the underlying hardware (e.g., GPUs) and the inference stack (e.g., vLLM). The Cortex Platform automatically scales engines up or down to match fluctuations in inference demand.

The Scheduler is the component responsible for orchestrating requests and assigning them to the most appropriate Inference Engine. For instance, an inference request for a specific LLM (e.g., Llama 3.1 70B) is routed to an engine that already hosts that model and is ready to serve it.

The API Service acts as the front-end for the Cortex Platform. It receives inference requests from either the Cloud Services layer or the Query Processing layer, applies API-specific business logic, and forwards the request to the Scheduler.

The Cortex Platform supports a broad set of models from partners including OpenAI, Anthropic, and Meta, enabling users to build and evaluate AI applications easily. For each inference request, the Cortex Platform determines whether to execute it using one of its Inference Engines or forward it to a partner endpoint. For instance, requests for GPT models are routed to OpenAI’s endpoints.

Unlike row-level operators, aggregation presents a unique challenge: tables and columns often contain more text than can fit in a single model’s context window. To address this, we employ a hierarchical aggregation strategy that processes data in batches and recursively combines intermediate results.

Our approach relies on three distinct phases:

(1)

Extract
key information from a subset of the text rows into intermediate states

(2)

Recursively
combine
intermediate states, discarding extraneous information while synthesizing similar data

(3)

Summarize
the combined state in a style and tone appropriate for the user’s context

As can be seen in the pseudo-code of Algorithm
1
, the aggregate function iterates over rows, accumulating text rows in a row buffer
R
. Once the row buffer has exceed the
BATCH_SIZE
token limit,
\texttt{LLM.Extract}(R)
generates intermediate states containing the most important information for summarization, which are all inserted into an intermediate state buffer
S
.

Once the state buffer has exceeded
BATCH_SIZE
,
\texttt{LLM.Combine}(S)
synthesizes as many intermediate states as possible (based on the context window limit) into combined intermediate states. This process repeats until
S
is sufficiently small.

Finally, after all rows are processed,
LLM.Extract
and
LLM.Combine
are executed until
R.empty()
and
len(S)==1

\texttt{LLM.Summarize}(S[0])

5.1.
Optimizing AI Operators

One of the key challenges in optimizing AISQL queries is that AI operators are typically treated as black boxes by the optimizer. For example, without historical data from previous invocations on the same data, it is not possible to estimate the selectivity and hardware cost of an
AI_FILTER
predicate. At the same time, the per-row monetary and runtime costs of AI operators are typically orders of magnitude higher than those of other typical SQL operators and functions. Consequently, the suboptimal placement of an AI operator in the execution plan can have devastating effects on both cost and execution time. This problem is not new in database systems. Optimizing user-defined functions (UDFs) in database engines shares many similarities with the problem of optimizing AI operators, and many of the techniques published 20 years ago remain relevant
(
9
;
11
;
4
)
.

The AISQL query in this example has three predicates with different cost and performance characteristics. The first is a predicate on a "date" column, which is relatively "cheap" to evaluate and for which most database engines can do a reasonably good job at estimating its selectivity. The second predicate is an
AI_FILTER
on a VARCHAR column, which is more expensive as it invokes an LLM for each row and its selectivity is unknown at compile time. The execution cost can be estimated based on the average number of tokens in the column values. The third predicate is also an
AI_FILTER
, but it is applied to images and invokes a multimodal model. Multimodal models are typically larger and more expensive than models operating only on text input.

Suppose the cost of each predicate is ignored. In that case, the optimizer may generate
Plan A
that is shown in Figure
7
, in which all predicates are "pushed" below the join, with the underlying assumption that join is an expensive operator and hence the number of rows sent to this operator should be minimized. In addition, the most selective predicate (

in this example) is applied first on the rows scanned from the "papers" table.
Plan A

This example highlights two of the optimizations that the Snowflake execution engine is applying to improve the performance of AISQL queries (see Section
6
for an experimental evaluation), namely: a) predicate reordering, b) optimizing query plans for AI inference cost. Predicate reordering has both a compiler and an execution component. During compilation, the predicate evaluation order is determined based on the relative cost of each predicate, i.e., the most expensive predicates are evaluated last. During execution, runtime statistics are collected on the cost and selectivity of predicates. These statistics are used to determine at runtime whether a different predicate evaluation order is more effective. For instance, if an AISQL query evaluates two
AI_FILTER
predicates on text columns from the same input, we can determine at runtime which one is more selective and change the evaluation order so that the more selective
AI_FILTER
predicate is applied first.

As we discussed in Section
4
, AISQL queries typically spend a significant fraction of execution time in AI operators. Consequently, optimizing AISQL queries requires us to rethink the optimization criteria used in the compiler. We initially considered how
AI_FILTER
predicates are placed in the execution plan with respect to joins and aggregations, as this problem showed up in numerous customer workloads. Although the selectivity of an
AI_FILTER
is unknown at compile time, we identified that simply optimizing the total number of AI inference calls produces good results in many cases. However, as AISQL queries become more complex and compiler estimations less reliable, these kinds of optimizations become less effective in practice. To that end, we are considering dynamic optimization techniques and caching runtime statistics that can help the compiler make more informed decisions in subsequent AISQL queries. Additionally, we are exploring methods to generalize the compiler’s optimization of AI functions and operator placement in complex execution plans.

5.2.
Adaptive Model Cascades

AI operators such as
AI_FILTER
must often process millions of rows in production database workloads. However, invoking an LLM on every row introduces prohibitive costs and latency. To address this challenge, the AISQL engine implements
model cascades
: a lightweight
proxy model
processes most rows, while a powerful
oracle model
handles only difficult cases where the proxy exhibits uncertainty. The proxy model’s predictions are accepted when confidence is high, but uncertain cases are escalated to the oracle for more reliable decisions.

Implementing model cascades in a production database system presents unique challenges. First, the system must learn an effective routing strategy online from streaming data without prior knowledge of the query’s data distribution. Second, the algorithm must operate in a highly concurrent environment, where multiple workers process different portions of the data in parallel. Third, it must honor user-specified cost budgets while maintaining high-quality results. Finally, the routing decisions must adapt dynamically as data characteristics change across batches.

Snowflake’s AISQL engine addresses these challenges through an
adaptive threshold learning
algorithm that reframes cascade routing as a statistical estimation problem. The algorithm uses a sample of oracle evaluations to learn confidence thresholds that partition rows into three regions: an accept region where the proxy is confident and predicts positive, a reject region where proxy confidence is low and predicts negative, and an uncertainty region that might require invoking the oracle and making conservative decisions.

The algorithm operates in four phases over batches of rows:

Phase 1: Proxy Inference.
Execute the proxy model on all rows in the current batch to obtain predictions and confidence scores. For an
AI_FILTER
predicate, each row
i
receives a score
s_{i}\in[0,1]
representing the proxy’s confidence that the predicate is satisfied.

Phase 2: Sampling.
Allocate a fraction of the oracle budget to sample rows for ground-truth labels. Rather than sampling uniformly, the algorithm uses
importance sampling
to oversample rows with intermediate confidence scores. These are the rows where the proxy is most uncertain and where oracle feedback provides maximum information for threshold estimation.

Phase 3: Threshold Learning.
Using the sampled oracle labels, compute two thresholds
\tau_{\text{low}}
and
\tau_{\text{high}}
that define the uncertainty region:

(1)

Rows with
s_{i}<\tau_{\text{low}}
are predicted negative (proxy is confident it’s false)

(2)

Rows with
s_{i}>\tau_{\text{high}}
are predicted positive (proxy is confident it’s true)

(3)

Rows with
\tau_{\text{low}}\leq s_{i}\leq\tau_{\text{high}}
remain in the uncertainty region

These thresholds are computed using concentration inequalities that provide probabilistic guarantees with limited samples
(
15
)
. The algorithm accounts for sampling bias through importance weighting, ensuring threshold estimates are unbiased despite non-uniform sampling.

Phase 4: Adaptive Refinement.
The algorithm refines thresholds iteratively across batches. For each new batch: (1) identify rows falling in the current uncertainty region, (2) allocate remaining oracle budget to sample additional rows from this region, (3) update threshold estimates using the new sample, and (4) repeat until the oracle budget is exhausted or the uncertainty region is empty. Iterative refinement allows the thresholds to adapt to evolving data distributions.

Once thresholds are learned, the engine makes final routing decisions. Rows outside the uncertainty region are classified directly using learned thresholds and proxy predictions. Rows remaining in the uncertainty region are routed to the oracle if budget permits; otherwise, the proxy prediction is used as a fallback.

The iterative batch-based implementation in the AISQL engine naturally accommodates concurrent database execution. Multiple workers process different data partitions in parallel, each collecting oracle samples within their assigned batches. These samples may be periodically aggregated to update shared threshold estimates, allowing the algorithm to learn from the entire data stream while workers proceed independently.

The oracle analyzes the user-specified natural language prompt, schema metadata (e.g., column and table names), statistics (e.g., number of distinct values), as well as sample values from each input source. Using all that information, the oracle determines during compilation if a semantic join should be converted into a classification task and which input dataset contains the labels for the classification. Subsequently, the transformation is performed as a regular rewrite operation by the compiler. The rewritten query is equivalent to the original user query but adds additional operations to: a) reduce the number of input labels to each

5.4.
AI Aggregation

Earlier, we described an incremental fold strategy for combining intermediate states within a Reduce operation for both

introduces significant overhead for small datasets that fit within the model context window. Therefore, a simple "short-circuit" alternative provides opportunities for throughput improvements by identifying these scenarios and skipping unnecessary incremental fold steps. This simple algorithm change measured an 86.1% latency reduction in

Related Work

The intersection of databases and AI has evolved along two directions: AI4DB, which utilizes ML to enhance database systems themselves, and DB4AI, which integrates native AI capabilities into databases to simplify analytics and model inference. AISQL builds upon both paradigms by integrating LLMs directly into the SQL execution layer.

The AI4DB line of research applies ML algorithms to internal database components such as query optimization, indexing, and configuration tuning. Early systems like LEO
(

(

It developed a formal model for estimating predicate costs and selectivities, enabling the optimizer to reorder and combine such predicates effectively to minimize overall query execution time.

AISQL unifies the goals of both research directions. From AI4DB, it borrows the principle of learning to optimize workloads by applying cost modeling, feedback, and adaptive execution to manage expensive semantic operators. From DB4AI, it inherits the vision of integrating LLM-powered inference directly into the SQL engine. Unlike systems that provide best-effort performance or focus solely on row-wise operations, AISQL co-optimizes query execution and LLM inference within a unified relational framework. AISQL represents a step toward production-ready AI-native database systems that reason, learn, and optimize within the same execution environment.

8.
Conclusions

The proliferation of unstructured data alongside traditional structured datasets has created a fundamental gap in modern data warehouses: users need to perform semantic reasoning over hybrid data but are forced to export data to external systems, orchestrate complex pipelines, and sacrifice the optimization benefits of integrated query processing. This paper presents Snowflake AISQL, a production SQL engine that bridges this gap by integrating LLM capabilities directly into SQL through semantic operators.

AISQL introduces six semantic operators that compose naturally with relational SQL primitives. These operators enable users to express complex analytical tasks that blend structured queries with semantic reasoning in a single declarative statement, and eliminate the need for external data movement and manual pipeline orchestration.

The core technical challenge we address is making semantic operators efficient at a production scale. LLM-based semantic operators are orders of magnitude more expensive than traditional SQL operations; their cost and selectivity are opaque to the query optimizer, and conventional optimization heuristics can produce plans that are catastrophically inefficient. Our solution comprises three techniques driven by analysis of real customer workloads. AI-aware query optimization treats LLM inference cost as a first-class objective, resulting in efficient operator placement and predicate evaluation order. Adaptive model cascades reduce costs through intelligent routing between lightweight proxy models and powerful oracle models. Query rewriting for semantic joins transforms quadratic-complexity joins into a linear multi-label classification task and, as a result, delivers speedups with improved prediction quality.

Our production deployment at Snowflake validates these design choices. Analysis of customer workloads reveals that AI operators consume the majority of execution costs, and nearly half of queries involve multi-table operations. These observations directly motivate our focus on join optimization and cost-aware planning. Extensive experimental evaluation across diverse benchmarks demonstrates that AISQL successfully delivers both efficiency and quality at the production scale.

AISQL represents a step toward unified data processing architectures where semantic reasoning over unstructured content is a first-class database capability rather than an external add-on. By integrating LLM capabilities into the SQL engine, with a focus on cost optimization, we enable organizations to unlock insights from their data assets through familiar declarative interfaces, while maintaining the performance, scalability, and reliability expected from modern data warehouses.
