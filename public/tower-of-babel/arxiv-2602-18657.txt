DSLean: A Framework for Type-Correct Interoperability Between Lean 4 and External DSLs
Tate Rowney, Riyaz Ahuja, Jeremy Avigad, Sean Welleck

Abstract
Domain-specific languages (DSLs) mediate interactions between interactive proof assistants and external automation, but translating between the prover’s internal representation and such DSLs is a tedious engineering chore. To simplify this task, we present DSLean , a framework for bidirectional translation between expressions in the Lean proof assistant and external syntax. DSLean requires only a specification of an external language and its Lean equivalents, abstracting away meta-level implementation details. We demonstrate DSLean’s capabilities by implementing three new automation tactics, providing access to external solvers for interval arithmetic, ordinary differential equations, and ring ideal membership.

Introduction

Verifying claims in an interactive theorem prover can often be assisted by the use of external automation, either by reconstructing proofs within the proof assistant or using them as a trusted oracle. Communication between the ITP and the external solver is often mediated by a domain-specific language (DSL) interpretable by both. Examples within the Lean ecosystem include
[
21
,
16
,
18
,
3
,
12
]
.

Implementing such translations is generally challenging. There is little general infrastructure for exporting information from Lean, so translation often requires the use of bespoke intermediate structures. In the other direction, transforming raw serialized data from an external tool into Lean expressions requires meta-level code to parse the data into a concrete syntax tree, elaborate it into an abstract syntax tree, and modify or recombine it to form a Lean expression. This results in application-specific code that is difficult to maintain and understand, and often requires expertise with Lean metaprogramming.

Contributions.
We present DSLean, a framework for bidirectional translation between Lean 4 and arbitrary domain-specific languages. DSLean is implemented fully in Lean, and uses Lean’s native parser and metavariable unification algorithm to allow for robust transformations of type-correct Lean expressions to well-formed syntax and vice versa. Despite its internal complexity, DSLean provides an intuitive user interface that abstracts away implementation details such as parsing and elaboration, automatically determining how best to handle settings such as parser precedences, typeclass synthesis, polymorphism, and postponed elaboration.

We also showcase several applications of DSLean, in the form of Lean automation tactics:

•

The
gappa
tactic uses DSLean to interface with the Gappa
[
6
]
interval arithmetic solver, automatically proving nontrivial bounds on real numbers by translating Gappa’s proof certificates, written in Rocq
[
26
]
syntax, into Lean.

•

The
desolve
tactic connects to the SageMath
[
27
]
computer algebra package to obtain general solutions to ordinary differential equations.

•

The
lean_m2
tactic communicates with the Macaulay2 package
[
8
]
, providing witnesses to problems involving ring ideal membership and Gröbner bases.

Due to DSLean’s capabilities, each example above has a short and interpretable implementation, using approximately 300 lines of code or fewer. We believe DSLean’s general nature makes it applicable to many forms of proof automation beyond what is presented here.

4
DSLean

We now provide an overview of DSLean’s design and implementation. DSLean is implemented in Lean and uses Lean’s metaprogramming APIs to perform translation from Lean expressions to external syntax (Section
4.2
), and from external syntax back to Lean (Section
4.3
). Translation into external syntax proceeds by partially matching a target expression with one corresponding to a pattern, recursively repeating this process until the entire target is matched. Translation into Lean begins by parsing raw data into an intermediate datastructure (Section
4.3.1
), then elaborates it into an expression by recursively combining the expressions corresponding to each detected pattern using Lean’s metavariable unification algorithm (Section
4.3.2
). These processes are described in detail below.

4.1
Design Principles

DSLean is designed to achieve three goals.
First, rather than require the user to specify type- and structure-related constraints in the DSL, we instead utilize Lean’s semantics to impose such structure. By requiring and verifying type-correctness at each step of any pattern-matching or reconstruction performed, the types of Lean objects induce typing constraints on corresponding external syntax, allowing for more nuanced structural properties than a simple inductively-defined specification. Lean allows users to define and use objects with a wide variety of useful signatures should available objects be insufficient to induce the desired structure.

Second, we strive for round-trip consistency; that is, translating an expression out of and back into Lean, or vice versa, should result in the same object modulo definitional equality. As DSLean utilizes Lean’s parser and other unsafe or unverifiable code, we provide no formal guarantee of this property. However, apart from initial parsing or final serialization, all processing is performed by substituting definitionally equal expressions, improving the level of assurance that this property holds.

Finally, we attempt to make DSLean as simple and intuitive as possible for the user, requiring only the minimum amount of non-optional configuration and allowing them to disregard metaprogramming-related trivialities. Methods of inferring reasonable values for unspecified parameters are described below.

4.2
Translation: Lean to External

Translation from Lean objects to external syntax does not use Lean’s default pretty-printing system: rather, we opt to recursively check definitional equality between a Lean expression and each equivalence to ensure one-to-one correspondence with external patterns.

Each user-specified
equivalence
, written via the syntax
...<==>...
, contains an external pattern on the left in the form of a sequence of strings, and a Lean pattern on the right in the form of an expression. Apart from some simple equivalences, both sides contain matching free variables corresponding to
nonterminals
, placeholders left in the pattern to be filled by other equivalences. In context of the original
external
declaration, the Lean portion of each equivalence undergoes partial elaboration into Lean’s internal representation of expressions, the
Expr
type. We do this so that free variables intended to indicate nonterminals do not overlap with free variables declared while translating external syntax, as well as to determine whether a translation may only be performed in a single direction if it has more nonterminals on one side (this step is also required for translation away from Lean; see section
4.3
). We allow unassigned
metavariables
, syntactic placeholders for as-yet undetermined sub-expressions, to remain in this intermediate expression, and additionally create metavariables corresponding to nonterminals in the pattern.

When translating an input expression
\Gamma\vdash e
to external syntax, DSLean attempts to find an equivalence that matches
e
by iterating through each partially elaborated Lean pattern
e^{\prime}
with metavariables
\{\Gamma_{e,i}\vdash?m_{e^{\prime},i}\}_{i<n}
, abstracting them, and re-creating them in
\Gamma
’s context as new metavariables
\{\Gamma\cup\Gamma_{e,i}\vdash?m^{\prime}_{e^{\prime},i}\}_{i<n}
. After substituting these into
e^{\prime}
via
e^{\prime}[?m^{\prime}_{e,0}/?m_{e,0}]...[?m^{\prime}_{e,n-1}/?m_{e,n-1}]
, it checks this expression’s definitional equality to
e
, assigning the metavariables accordingly if successful.
It then repeats this process on each metavariable corresponding to a nonterminal until no nonterminals remain; then from the last recursive call upwards it fills in the string representation of this expression according to the patterns specified by each equivalence. The aforementioned definitional equality checks at every stage ensure that translation back into Lean by the same equivalences will remain definitionally equal to the original (modulo the correctness of Lean’s parser; see Section
4.3.1
).

Additionally, due to elaboration in separate contexts, metavariables in
e^{\prime}
are not functions of any bound variables that may occur in
e
, which is required by Lean’s unification system for said metavariables’ value or type to be dependent on outside binders. To remedy this, should an outside metavariable
?m_{e^{\prime},i}
potentially be unified with an expression occurring with bound variables
(b_{1},...b_{n})
in scope, we perform the substitution
e^{\prime}[(\lambda x_{1}.\cdots\lambda x_{n}.?m_{e^{\prime},i})b_{1}\cdots b_{n}/?m_{e^{\prime},i}]
to ensure such dependence can occur. We assert that this remains faithful to the original expression, as unused bound variables disappear from this sub-expression after
\beta
-reduction, which is applied following unification.

To prevent superfluous matching on an expression without real progress being made, patterns that leave the current expression unchanged modulo a single reduction are given lower priority. For example, a pattern
e^{\prime}:=(\lambda x.?m_{0})?m_{1}
is definitionally equal to any target expression
e
, with
?m_{0}\leftarrow x,?m_{1}\leftarrow e
; this assignment doesn’t make substantial progress as
\beta
-reducing
e^{\prime}
yields
e
again, leaving us back where we started. To avoid this issue, such patterns are not utilized unless no other options are available: when this is the case (which may occur when the input expression is not fully translatable by the specified equivalences), an upper limit is imposed on the number of recursive calls to prevent stack overflow.

4.3
Translation: External to Lean

Translation from external syntax to Lean proceeds in two steps: parsing (
4.3.1
) and elaboration (
4.3.2
).

4.3.1
Parsing

External syntax is parsed using Lean’s native parser
[
17
]
, a Pratt parser
[
20
]
with additional dynamic information in the style of Swierstra and Duponcheel’s combinator parsers
[
23
]
. It is designed with extensibility in mind, and thus is suitable for processing a wide variety of reasonably-designed external grammars.

The external syntax portion of each user-specified equivalence is transformed into a single
production rule
; string literals and free variables in the specification correspond to terminal and nonterminal symbols respectively. A single syntax category is used for each DSL, as we count on the elaboration stage described below to prevent ill-typed statements. For binary operations and production rules with more than one nonterminal in a row, the first symbol is given higher precedence to avoid potential interference with highly generic rules such as function application. This causes operations to be left-associative by default: we believe this is a reasonable assumption to make, as many of Lean’s standard mathematical operations are left-associative. Users may modify the associativity of a production rule with the
+rightAssociative
flag, or manually modify the precedence with the
precedence := ...
option.

Lean’s parser implements optimized parsing of numerals via a separate parser category: we retain this behavior for performance and convenience, as we believe requiring the inductive specification of the definition of base-10 numerals in every DSL imposes an unnecessary burden on the user. We also use Lean’s identifier parser at maximum precedence to parse bound variables.

While powerful, Lean’s parser contains certain assumptions about the structure of grammars it parses, causing it to refuse certain production rules. These include rules containing certain reserved terminal symbols such as lone numerals or quotation marks, as well as identifiers that begin with certain characters such as punctuation. It is possible that some or all of these limitations are caused by certain APIs used to expose them and not due to limitations of its theoretical foundations. Future work could address this by modifying or augmenting the parser for greater generalizability.

4.3.2
Elaboration

DSLean does not utilize Lean’s default term elaborator directly, instead creating a custom elaboration stage built on top of it. Each equivalence’s Lean pattern is partially elaborated in separate contexts,
before being merged together at runtime in the structure specified by parsed syntax.

After parsing external syntax, we begin with the ambient context
\Gamma
and a fresh metavariable
\Gamma\vdash?m_{0}
; then following the Concrete Syntax Tree given by the parser, we identify the relevant target expression
e
with metavariables
\{\Gamma_{e,i}\vdash?m_{e,i}\}_{i<n}
, which has been partially elaborated as described in
4.2
.
We abstract and re-create these metavariables in
\Gamma
as new metavariables
\{\Gamma\cup\Gamma_{e,i}\vdash?m^{\prime}_{e,i}\}_{i<n}
. We obtain an updated expression
e^{\prime}:=e[?m^{\prime}_{e,0}/?m_{e,0}]...[?m^{\prime}_{e,n-1}/?m_{e,n-1}]
by substituting in the new metavariables, and assign
?m_{0}\leftarrow e^{\prime}
while checking definitional equality: should this succeed, the expression remains type-correct. This process is repeated for each unassigned metavariable in
e^{\prime}
corresponding to a nonterminal, until no nonterminals remain.

During elaboration, binders in expressions are temporarily transformed into free variables while their bodies are elaborated, after which all occurrences of this free variable are turned back into a bound variable. This causes the contexts of some metavariables, which are instantiated before this process, to become out of date; to remedy this, we manually modify the contexts of any
\Gamma\vdash?m^{\prime}_{e,i}
occurring within the binder
x
to include
\Gamma\cup\{x\}\vdash?m^{\prime}_{e,i}
. Although this could potentially cause another instance of
?m^{\prime}_{e,i}
outside this binder to be assigned to a free variable which is not in scope, we assert this transformation is safe, as such a situation is equivalent to attempting to translate an occurrence of a bound variable with no corresponding binder; both these situations will be flagged by the type-checker at the end as ill-typed syntax.

Since Lean’s parser processes numerals as a separate category in an optimized fashion (see section
4.3.1
), elaboration of numerals is also handled separately without user specification. By default, numerals are elaborated into natural numbers (Lean’s
Nat
type) with coercion applied wherever possible; this behavior may be changed by specifying the
numberCast
option.

Finally, the syntactic structure of expressions such as automation tactics depends heavily on their expected type, causing their elaboration to be postponed until their type is known. We treat such expressions specially, disallowing nonterminals and elaborating them within the new context at translation time instead.

6
Conclusion

We present DSLean, an extensible and user-friendly framework for bridging between Lean 4 and arbitrary external DSLs. We additionally introduce three Lean automation tactics made using DSLean, which take advantage of communication with external solvers to address a range of nontrivial mathematics problems.

While automation via external solvers motivates the use of such a system in and of itself, there are undoubtedly other applications of communication between ITPs and external languages. For example, future research could expand on this work by utilizing similar methods to translate syntax of unverified programming languages into a form amenable to verification, or to increase the clarity of formal proofs via translation into natural language.
