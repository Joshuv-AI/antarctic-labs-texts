When Are Reactive Notebooks Not Reactive?
Megan Zheng, Will Crichton, Akshay Narayan, Deepti Raghavan, Nikos Vasilakis

Abstract
. Computational notebooks are convenient for programmers, but can easily become confusing and inconsistent due to the ability to incrementally edit a program that is running. Recent reactive notebook systems, such as IPyflow , Marimo and Observable , strive to keep notebook state in sync with the current cell code by re-executing a minimal set of cells upon modification. However, each system defines reactivity a different way. Additionally, within any definition, we find simple notebook modifications that can break each system. Overall, these inconsistencies make it difficult for users to construct a mental model of their reactive notebook’s implementation. This paper proposes Rex , a fine-grained test suite to discuss and assess reactivity capabilities within reactive notebook systems. We evaluate Rex on three existing reactive notebook systems and classify their failures with the aims of (i) helping programmers understand when reactivity fails and (ii) helping notebook implementations improve.

Similarly, another set of traditional data analysis tools provides the same features: spreadsheet applications. Contrastingly, although a spreadsheets’ key feature also includes reactivity, their reactivity is ironclad: a user can update a cell and always be confident in the effect their update will have on the rest of their spreadsheet.

Therefore, the impetus for this work is a gap between the reactivity claims made by these systems and the systems’ behavior in practice.

2.
Defining Reactivity

A computational notebook consists of a sequence of cells. Each cell can contain a combination of variable definitions, re-definitions, mutations, and read/write interactions with external state such as the file system or an external API service.
Each cell is associated with visible and invisible state.
The visible state, also called a cell’s output, consists of state that is printed to the user during the notebook execution, typically via prints to the notebook’s
stdout
;
invisible state consists of all internal and external program state, e.g. relevant file system state, at the point in time when a cell executed.

Historically, computational notebook implementations did not require or establish relationships between cells. Rather, users could execute cells
interactively
in an arbitrary order, or with repetitions
(
Chattopadhyay et al. 2020
)
.
While this remains a popular way of using computational notebooks today, in this paper we focus specifically on
reactive
computational notebooks.

At first, the behavior these reactive notebook systems should implement seems intuitive — after editing a cell, the cell output and any side-effects on notebook state should be equivalent to an execution in which the user had restarted the runtime environment and run the notebook from top-to-bottom, with respect to the spatial ordering of notebook cells.
But it is important to more precisely define what proper reactivity means, as careful inspection reveals two key questions:
(i) should reactivity encompass effects on the system, like file writes?
(ii) what does reactivity mean if a notebook does not have a particular linear order?
We resolve these ambiguities with background and definitions useful for understanding reactive notebook systems.

Execution order
.
Some reactive systems like
IPyflow
are designed to handle programs with cross-cell effects, such as creating an object in one cell and mutating it in another, as in
Figure

1
.
For these systems, there is a strongly recommended valid execution order: linearly from top-to-bottom.
A given cell
C
depends on any spatially preceding cell
C^{\prime}
which either defines or mutates data used in
C
.

For systems restricted to no cross-cell effects, such as
Observable
and
Marimo
, cell ordering is purely presentational and the execution order should not affect the efficacy of the system.
Any topological sort of the cells based on their dependency structure is a valid execution order.
Therefore a given cell
C
depends on any cell
C^{\prime}
anywhere in the notebook which defines data used in
C
. For the scope of this paper, we primarily focus our evaluation on linear, top-to-bottom execution order.

Consistency
.
Suppose that a user starts a notebook in an initial runtime environment
E
, and that they execute and/or modify some of its cells.
We define that notebook’s state
S
as being
consistent
with its source code if
S
is identical to a
S^{\prime}
which could be reached through a valid execution order starting in a fresh state under
E
.
For example, the bottom-right notebook in
Figure

1
is an inconsistent state because a linear execution of the notebook could not produce that state.

The external environment aspect of this consistency definition is more restrictive than how any existing reactive system approaches consistency.
These systems only focus on consistency with effects legible to the language (defining variables, appending to a list, etc.), but we argue that true consistency should extend to the environment, including e.g. the file system and sources of nondeterminism like random number generators.

Undefined behavior
.
Notions of execution order and consistency are only well-defined for notebooks that are in-scope for a given reactive system. If a system does not permit cross-cell effects, then we say that a program which contains such effects exhibits
undefined behavior
. For example,
Figure

1
contains undefined behavior for
Marimo
and
Observable
, but not
IPyflow
.

Notebook modifications
.
A modification to a notebook can add, modify, or delete a cell, or swap the position of two cells.
Modifications can change assignments or re-assignment of variables, change which specific state is being mutated, how state is being mutated, or any combination of these.

Reactivity
.
Given a modified notebook, we define a
reaction
as actions to make the notebook’s state consistent with the new source.
These actions normally consist of re-executing a subset of the notebook’s cells. A reaction is
sound
if it produces a consistent state, and a reaction is
precise
if no redundant work is performed to ensure consistency. For example, in
Figure

1
, a simple “restart and run all” approach would be sound but not precise, because re-executing the cell
z = 123
is unnecessary.

If a modification would introduce undefined behavior, we consider an error that prevents the notebook from executing as a sound reaction. This definition is analogous to type safety, how a type system is considered sound if it prevents a program from encountering undefined behavior.

3.
A Benchmark for Reactive Notebooks

To evaluate the soundness and precision of reactive notebook systems, we developed
Rex
, a notebooks micro-benchmark.
Rex
contains 87 Python programs defined in Jupyter
ipynb
files.
Each benchmark consists of a notebook, a modification, and the expected set of cells that satisfy sound and precise reaction.

3.1.
Benchmark Notebooks

The goal of
Rex
is to systematically explore a wide variety of code patterns to stress-test potential edge cases.
We developed its component notebooks manually to represent a wide variety of notebook computations
2
2

2

While developing notebooks manually means our benchmark does not represent real-world use, our goal in this paper is rather to understand notebooks’ behavior across a variety of computational patterns.
.
Specifically, we focused on three dimensions:

(1)

Direct assignment
: A modification on the definition of a variable. The modification can be on the RHS or LHS of the assignment operation.

(2)

Reassignment
: A modification which reassigns or redefines a variable defined previously in another cell.

(3)

Mutation
: A modification which performs any in-place mutations of existing values or external resources such as file systems.

We delineate
direct assignment
and
reassignment
since no references to a variable can occur prior to executing the cell defining the variable. Thus, direct assignment modifications do not require re-execution of the variable’s upstream dependent cells, while reassignments may.
Although collection objects can be updated via reassignment of any member’s value (e.g.,
x[0] = ...
), such operations mutate the original object in place. Since members are not independent of their container structure, we conservatively label modifications of in-place updates, including those written as reassignments, as mutations.

However, if the RHS of the direct assignment references another variable, upstream dependent cells of the RHS variable
may
require re-execution, specifically when the RHS variable’s downstream dependent cells exhibit mutations, increasing the complexity of the modification.
This demonstrates that at times, the modification code
alone
, e.g. the modification described by cell 2 in figure
1
, may be insufficient to describe the modification’s complexity; any variable and state the modification will affect must also be considered, e.g. list
a
in the collection defined by
x
in cell 1 of figure
1
. We resolve this by striking a balance between how easy the modification is to detect prior to execution and the complexity of reactions systems may need to perform. Therefore, we classify modifications based on this complexity hierarchy,
(1) reassignment, (2) mutations, and (3) direct assignment
.
For example, if upstream or downstream dependent cells of the modification induces reassignment, we classify the modification as
reassignment
. Similarly, if any downstream dependent cell of any variable(s) affected by the modification contains mutation, we classify the modification as
mutation
.

External Effects
.  Users not only write programs that solely interact with state created and maintained by the notebook runtime, but also programs that modify external resources such as file systems or databases. This imposes design trade-offs for reactive system designers to consider when determining their system’s scope.
For instance, if a reactive system designer wished to include file systems in the reactive system’s scope, their system may need to track file system changes and, in cases of non-idempotent file system modifications, “undo” prior file system modifications for the newest modification to overwrite any stale states.

Precision
.  Reactive systems should also be efficient and not incur significant overhead such that there is a degradation to user experience. A viable system must not only identify all cells required to re-execute for soundness, but should also discover the precise and minimal set such if any cell in the cells to re-execute were excluded, reactivity would no longer be satisfied. Therefore, we designed notebook benchmarks to contain cells unrelated to the target modification to evaluate when systems unnecessarily execute additional cells.

Rerun-All

Rerun-All

Rerun-All

Run Subsequent Cells
embeds a naive assumption about how users construct programs: that cells defining variables will be placed, created, and ran prior to cells that use those variables. Hence,
Run Subsequent Cells
is also language agnostic as it only depends on the spatial ordering of the notebook’s cells. Further, it is a simple optimization over
Rerun-All
since it does not re-execute
all
cells upon modifications.

3.3.
Benchmark Implementation

We manually translated benchmarks to JavaScript,
Observable
’s supporting language, resulting in 52 benchmarks which preserved semantic equivalency.
The remaining 35 benchmarks were hard to translate because they used incompatible Python libraries or because
Observable
’s purely in-browser framework restricts access to file systems.
16/52 translatable benchmarks were incomparable because
Observable
’s out-of-order execution
(
Observable Team 2021
)
does not match our definition of reactivity.

We used
Marimo
’s
converter
tool
(
Marimo Team 2025
)
to transform notebooks from Jupyter into
Marimo
-compatible format.
We executed notebooks manually with
Observable
and
Marimo
, and automatically with
Rerun-All
,
Run Subsequent Cells
, and
IPyflow
using an automatic benchmark execution tool we built.
We used
Rerun-All
,
Run Subsequent Cells
, and
IPyflow
v0.0.201 (9fff16a) with Jupyter Lab v4.4.4,
Observable
as of July 2025 (reactivity runtime v6.0.0), and
Marimo
v0.14.10.

We begin each benchmark by initiating two fresh kernels to isolate notebook runtime state: one for executing the
original notebook
and another for executing the
modified notebook
. First, we execute all cells in the
original notebook
sequentially. Next, we edit-in the single user modification, determined from the difference of the
modified notebook
vs. the
original notebook
, to the target cell in the
original notebook
. Then, we execute the cell containing the modification and trigger the system’s reactivity functionalities. Finally, we execute all cells sequentially in the
modified notebook
, which produces the expected top-to-bottom execution result. We compare cell outputs and count the number of cells that were part of the reaction.

As Table
1
shows, some systems declare certain program features as in-scope for reactivity and others further provide linting to prohibit execution when given out-of-scope features by raising an error. To fairly assess a system’s efficacy with respect to each system’s explicitly supported features, we consider
out-of-scope but caught
as sound and behaviorally correct. In other words, when a system identifies and prohibits (errors on) any execution of out-of-scope features declared in documentations, we consider the reaction as sound.

4.
Results

Using
Rex
, we evaluated all reactive systems across selected notebook systems. Except for
Rerun-All
, which serves as a feasibility baseline for top-to-bottom execution, no system achieved sound reactivity across all tests consistently. However, inspecting by category reveals more uniform behavior in each system’s handling of both in-scope and out-of-scope tests. Thus, this synthetic suite helps identify fault lines between reactive notebook systems.

4.1.
Modification Complexity

We see that all reactive systems achieved consistent reactivity for the direct assignment benchmark. However, reassignment begins to introduce inconsistent behavior, with
IPyflow
failing one case. With mutations, systems either fail to detect unsupported modifications or react inconsistently. Thus, the data supports our expectation that more complex modifications are harder to handle.

Direct assignment
.

Direct assignment
modifications are in-scope and explicitly supported by all evaluated systems: all systems correctly identified and re-executed at least the expected set of cells for these benchmarks, rendering consistently sound reactivity to these modifications (figure
3
). This consistency suggests direct assignment modifications represent a baseline capability for systems with respect to soundness.

Reassignment
.

Reassignment
modifications introduce greater complexity as expected. While reassignment is explicitly outside the supported scope of
Marimo
and
Observable
(table
1
), both systems are able to statically detect and catch the presence of such out-of-scope modifications and prevent users executing notebooks containing these features
(
Marimo Contributors 2024
;
Larkworthy 2023
)
. This behavior is consistent with their declared limitations and demonstrates that rejecting unhandled executions can be a viable fallback when precise dependency tracking is not available.
Run Subsequent Cells
does not provide any handling of upstream dependencies of a cell, and thus only matches 3/14 of cases.

IPyflow
, which supports reassignment, correctly handles all but one test case:
aliasing_val_swap
, as shown in figure
2
.
In this benchmark, a one-line tuple swap (
a, b = b, a
) updates both variables simultaneously. The expected behavior is to execute the cells that define
a
and
b
(cells 1 and 2) as well as their dependents (cells 3 and 4) as part of the reaction. However,
IPyflow
fails to include cell 1 as an upstream dependent cell of cell 2, resulting in stale values:
b
is then assigned the original value of
a
, 5, instead of the correct value, 9.
Swap operations like this are particularly challenging. They introduce mutual dependencies between variables and require the system to reason not only about data-flow but about the versioning of each variable. While
IPyflow
does associate variables with version metadata
(
Unknown 2022
)
, the simultaneous update pattern of tuple unpacking appears to violate assumptions in its analyzer implementation.

Mutation
.

Mutation

4.2.
File System

Other than
Rerun-All
, which we designed to delete any files the running notebook created between modifications, all other reactive systems are not designed to be aware of notebooks interacting with external resources. Understandably, this resulted in
IPyflow
and
Marimo
only matching in 1/8 of all file system benchmarks as these cases are not declared to be in-scope. Although
Run Subsequent Cells
presented matching for 50% of all file system mutation benchmark, write operations in those notebooks are idempotent, so
Run Subsequent Cells
did not have to “undo” any stale state and could directly overwrite the files’ previous values. Conclusively, no system other than
Rerun-All
reacted soundly to any non-idempotent file system mutations in our current test cases.

4.3.
Precision

Rerunning a cell can potentially be very expensive
(
Chattopadhyay et al. 2020
)
. While previous sections discuss soundness of reactivity systems, we now discuss
precision
, i.e. can systems efficiently identify the minimum set of cells while preserving soundness?

To also normalize across the wide range of typical notebook sizes, we answer “by what
factor
does system X execute more cells than required?” using the ratio
\frac{|C_{sys}|}{|C_{E}|}
, where
C_{sys}
is the sequence of cells re-executed by the system, and
C_{E}
is a minimal sequence of cells to re-execute.
We denote the ratio as the
re-run ratio
. Intuitively, an
inefficient
reactive system implementation executes more cells than required, and thus has a high re-run ratio.

Overall, we find that systems which explicitly limit the supported language complexity can make assumptions that remove cells as candidates to react more aggressively, without losing comprehensiveness within their supported scope (Figure
5
). Specifically,
Marimo
and
Observable
both have an average rerun ratio of exactly 1 for direct assignment tests, while
IPyflow
has an average of 1.44.
Having to only consider direct assignment eliminates many of the edge cases related to dependency graph changes and tracking lineage, since a change in a variable’s value always occurs at its definition site.
The limited scope allows
Observable
and
Marimo
to track dependencies with only static analysis techniques
(
Agrawal 2024
;
MacWright 2018
)
.

However, Macke et. al. report that static techniques actually fail to produce more precise reaction computation when systems are given scope beyond direct assignment. Thus, to optimize the ratio of cells rerun,
IPyflow
combines static analysis approaches with a dynamic analyzer, primarily to resolve cascading dependencies during runtime
(
Shankar et al. 2022
)
.
While the combined approach may allow
IPyflow
to react with a tighter ratio (~1.18 vs
Rerun-All
’s average, ~1.59, for mutation modifications) there is a clear tradeoff between efficiency and implementation difficulty, given the inconsistency we observe with
IPyflow
’s reactivity.

5.
Discussion

So, when are reactive notebooks not reactive?
Marimo
and
Observable
clearly are not reactive for programs out of scope, suggesting the need for better analysis tools which can detect undefined behavior and alert users.

IPyflow
fails to react to a handful of edge cases, although there are few clear patterns to the failures. All the systems we tested failed to react to changes to the external environment, as expected.

Our results demonstrate the need for reactive notebook systems to more clearly communicate their capabilities and limitations to their users, through both documentation and tooling.
These systems do not need to be perfect, but users at least need a reasonable model of when they can expect a given system to function correctly. We hope that benchmarks like
Rex
will provide one avenue for system designers to identify system limitations.

Future work might consider developing complementary benchmarks, such as sampling real-world notebooks to complement
Rex
’s synthetic data.
Additionally, we hope that
Rex
will spawn avenues of research that address the gaps classified in existing systems.
For example, we imagine that reactivity systems can draw on system tracing, sandboxing, and checkpointing techniques to monitor interactions with external system state and correctly react to modifications involving external state.
Side-effect control of arbitrary components in combination with just-in-time multi-grained dependency reconstruction can help track and respond to changes at levels appropriate for the granularity of changes performed by their users.
Orthogonally, ways to annotate library interfaces can help reactivity systems understand how external library functions read and mutate program state.
Finally, research on state tracking in language-agnostic intermediate representations by leveraging, for example, web assembly, can help create reactivity systems capable of working in any programming language.

Beyond Reactivity
.
Reactivity is not the only solution for improving state management and user experience with computational notebooks. An alternative solution is taking snapshots of the current notebook state for users to rollback or maintain more organized exploration process through version control
(
Weinman et al. 2021
;
Li et al. 2023
;
Li et al. 2025
;
Sato and Nakamaru 2024
;
Manne et al. 2022
;
Kery and Myers 2018
)
. Similarly, users may choose to traverse multiple isolated exploration path by forking
(
Fang et al. 2025
)
. Lineage tracking in notebooks further assist users in associating related cells and quickly identify cells needed to produce certain outputs
(
Macke et al. 2021
;
Head et al. 2019
)
, increasing reproducibility of notebooks. Additionally, various annotations tools allow users to easily record exploration process, improving reproducibility in notebooks
(
Rule et al. 2018a
)
. Regardless,
Rex
can be adapted for continued development of these solutions or future works.

6.
Conclusion

Computational notebooks are interesting because they provide a execution model that allows users to modify programs as they run them. This makes notebooks a natural fit for writing exploratory programs. However, it is common for notebook state to become messy and unreproducible. Reactive notebooks are a popular solution for handling state management on-behalf of the users. Different from other reactive applications such as spreadsheets, reactive notebooks flip the feature set: they support arbitrary programs and thus provide users more flexibility, but as we have seen, offer inconsistent and unpredictable reactivity implementations instead.
The success of spreadsheet applications shows that users benefit from reactivity when it provides consistent results.
We thus call for research on bringing this ironclad reactivity to computational notebooks, which will unlock an entire class of exploratory programming held back by inconsistent implementations today.
