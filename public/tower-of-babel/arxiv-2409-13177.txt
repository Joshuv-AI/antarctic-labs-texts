An Adaptive End-to-End IoT Security Framework Using Explainable AI and LLMs
Sudipto Baral, Sajal Saha, Anwar Haque

Abstract
The exponential growth of the Internet of Things (IoT) has significantly increased the complexity and volume of cybersecurity threats, necessitating the development of advanced, scalable, and interpretable security frameworks. This paper presents an innovative, comprehensive framework for real-time IoT attack detection and response that leverages Machine Learning (ML), Explainable AI (XAI), and Large Language Models (LLM). By integrating XAI techniques such as SHAP (SHapley Additive exPlanations) and LIME (Local Interpretable Model-agnostic Explanations) with a model-independent architecture, we ensure our framework’s adaptability across various ML algorithms. Additionally, the incorporation of LLMs enhances the interpretability and accessibility of detection decisions, providing system administrators with actionable, human-understandable explanations of detected threats. Our end-to-end framework not only facilitates a seamless transition from model development to deployment but also represents a real-world application capability that is often lacking in existing research. Based on our experiments with the CIC-IOT-2023 dataset [ 1 ] , Gemini and OPENAI LLMS demonstrate unique strengths in attack mitigation: Gemini offers precise, focused strategies, while OPENAI provides extensive, in-depth security measures. Incorporating SHAP and LIME algorithms within XAI provides comprehensive insights into attack detection, emphasizing opportunities for model improvement through detailed feature analysis, fine-tuning, and the adaptation of misclassifications to enhance accuracy.

III-A

Model Deployment Module

Our proposed framework features a flexible and adaptable architecture designed to seamlessly integrate and deploy various ML models. Deployment process is summarized in Algorithm (
1
). This architecture is model-agnostic, meaning it can work with any custom-built detection model provided through an Application Programming Interface (API). This approach guarantees that the framework can easily accommodate different detection models for analysis without requiring significant changes to the framework itself. The model deployment process unfolds in two distinct stages as below:

1.

Data Transformation and Processing:
Initially, model weights are uploaded using the API, followed by the submission of the JSON schema corresponding to the dataset utilized for model training. Based on the provided JSON schema, a transformer is instantiated. This transformer facilitates the conversion of raw internet traffic data into a format intelligible to the ML model in use.

2.

Integration of Message Queue Service:
Handling raw traffic streams within the architecture involves the integration of a message queue service, a robust distributed system serving as the foundation for managing data flows. Incoming internet traffic is aggregated into the message queue upon entering the network. Subsequently, the IDS system functions as a consumer of this queue, extracting data for detection purposes, with the transformer operating intermediary in this process.

III-B

Model Interpretation Module

This module is a key component of our proposed framework, designed to enhance transparency and build trust by clarifying machine learning predictions. Utilizing SHAP and LIME algorithms, it explains the rationale behind predictions, providing network administrators with actionable insights for informed decision-making. Our framework provided a dual-layered interpretation as below:

1.

Global and Feature-level Explanations with SHAP:
Firstly, we utilized SHAP, leveraging its game-theoretic approach to explain the output of any machine learning model by quantifying the contributions of each feature using Shapley values.

2.

Local Insights with LIME:
Complementing SHAP, we used LIME to provide a local understanding of predictions, focusing on local fidelity to accurately reflect the classifier’s behavior “around” the instance being predicted.

In addition to the explanation, this module also provides a mechanism to identify the top five influential features by analyzing the SHAP and LIME values. XAI algorithms, such as SHAP and LIME return a numerical value representing the influence of individual features on the prediction made by a machine learning model. A positive value for a feature indicates that its presence or increase contributes positively to the model’s prediction, while negative values suggest a negative impact. To determine the top 5 influential features, we selected those with the highest absolute values. Initially, we generated two sets of features, each comprising the top five influential features recommended by SHAP and LIME, respectively. Typically, some features appear in both sets. Hence, as depicted in Equation

III-C

Attack Explanation and Mitigation Module

Our framework enhances the comprehensibility of detected network attacks by translating complex machine learning outputs into easily understandable narratives and possible mitigation techniques. This process, powered by LLM, is structured into three main sub-modules as below:

1.

Prompt Generation:
Our prompt generator accommodates four input values: Influential Features, Predicted Attack, Experience Level, and Descriptiveness. Influential Features and Predicted Attacks are internally processed by the prompt generator, while users can manipulate descriptiveness and experience level through the dashboard interface. Consequently, a prompt is dynamically generated based on the received values.

2.

LLM Integration:
A seamless integration with the LLM backend is pivotal for transforming these prompts into detailed explanations. We establish a secure and efficient communication pathway with the LLM provider through a configuration file. These configurations, which include essential parameters such as the API URL and authentication keys, are integrated into the framework via environment variables.

3.

Response Reception and Dissemination:
After providing prompts to the connected LLM provider, the generated response is obtained through HTTP communication. This response is then relayed to the system administrator via the Analysis Dashboard, which receives real-time updates through WebSocket communication. Such explanations empower administrators to swiftly grasp the nature of detected threats, facilitating informed decision-making for subsequent actions.

III-D

Attack Response Module

Our framework integrates a comprehensive attack response module designed to streamline the detection, analysis, and response to network security incidents. This module integrates three critical functionalities: logging, monitoring, and alerting, providing a robust system for network security management.

1.

Logging with Grafana:
We employ Grafana, a leading open-source platform for analytics and monitoring, to handle our logging needs. Grafana enables the detailed logging of network activities, including packet values and timestamps, facilitating in-depth analysis of network traffic and potential security breaches.

2.

Alerting with AWS SNS:
For alerting, our system integrates with Amazon Simple Notification Service (AWS SNS), a flexible, fully managed messaging service. This integration allows for the efficient dissemination of alerts and notifications in response to detected threats.

3.

Real-Time Monitoring and Control:
The core of our incident response module is directly linked to our framework’s API via WebSocket, ensuring real-time monitoring and centralized control over the IDS. This setup enables immediate notification and visualization of detected attacks through our user-friendly dashboard, enhancing situational awareness and facilitating rapid response actions.

To construct our experimental dataset, we integrated nine instances of attack data with benign traffic data. We ensured a minimum of 20,000 data points in each category.

IV-B

Model Interpretability Analysis using SHAP and LIME

To assess the performance of the interpretation module of our proposed framework, we trained a random forest classifier using the CIC-IOT-2023
[
1
]
attack dataset. The resulting model demonstrated strong performance, achieving approximately 99.97% accuracy during testing. For further analysis of the model performance using XAI and LLM, we uploaded our trained model into the framework through the model deployment module.

According to Table
I
, both SHAP and LIME highlight network traffic characteristics such as “Header_Length,” “DNS,” and various flag numbers (e.g., “syn_flag_number,” “fin_flag_number”) as crucial for classifying network attacks. This highlights a foundational principle in network security: the anomalies in network traffic patterns are indicative of malicious activities. For example, unusually long headers or a high rate of specific flag usage can signal an ongoing attack. The variation in feature importance between SHAP and LIME methods reflects their underlying mechanisms—global versus local interpretability. This discrepancy is particularly helpful, as it suggests that while some features consistently influence the model’s predictions across different instances (SHAP), others may only be significant in specific contexts (LIME). This duality emphasizes the complexity of network attacks and the need for adaptive, context-aware models in IDS.

Analyzing misclassified entries, we notice that certain features appear uniquely in either SHAP or LIME lists, which may point to why the model struggles with certain predictions. For example, “Drate” and “HTTP” are identified by SHAP for test observation with index 6, but LIME emphasizes “psh_flag_number” and “fin_flag_number,” suggesting a possible misalignment in how the model weights protocol-specific features versus flag behaviors in its decision-making process. This observation implies that for misclassified instances, the model might be relying on features that, while generally important, fail to capture the nuanced differences required to distinguish between similar attack types, such as differentiating between DoS and DDoS attacks or identifying specific attack strategies like Mirai-greeth_flood.

In cases where SHAP and LIME agree on the importance of certain features (e.g., “Header_Length,” “DNS”), yet misclassification occurs, it may indicate that these features, despite their overall importance, are insufficient by themselves to accurately classify all instances. This suggests the need for either additional features or a re-evaluation of how these features are processed and weighted by the model. The analysis of misclassifications through the lens of SHAP and LIME can guide model refinement. For example, extending the model with additional context-specific features or adjusting the weighting of features based on insights from both SHAP and LIME could address the misalignments leading to misclassifications. Additionally, the comparative analysis highlights the importance of incorporating both global and local interpretability perspectives for a more holistic understanding of model behavior. This dual perspective can reveal discrepancies in feature importance that, if addressed, could significantly improve model accuracy, especially in complex scenarios where subtle distinctions between classes are crucial.

IV-C

Model Interpretability Analysis using Gemini and OPENAI

Both LLMs explained critical features associated with the DoS-TCP_Flood attack, such as ‘Header_Length’, ‘DNS’, ‘syn_flag_number’, ‘Rate’, and TCP-specific flags (‘ece_flag_number’, ‘psh_flag_number’). These features are indicative of abnormal network behaviors and patterns, such as oversized packet headers or an excessive number of SYN flags, which are typical markers of DoS attacks. Each model proposed mitigation strategies aligned with standard cybersecurity practices, including rate-limiting SYN packets, filtering spoofed packets, implementing SYN cookies, and utilizing traffic shaping techniques. These strategies reflect a deep understanding of network security mechanisms and the specific nature of DoS attacks.

In a comparative analysis of responses from Gemini and OPENAI to a cybersecurity prompt, each LLM showcased distinctive strengths in addressing the detection and mitigation of a DoS-TCP_Flood attack. According to Table 2, Gemini’s response was notably concise, offering a clear overview of the key features indicative of the attack, as identified by SHAP and LIME methodologies. It highlighted the necessity for targeted countermeasures such as filtering spoofed packets and implementing rate limiting, directly aligning mitigation strategies with the attack’s specific characteristics. In contrast, OPENAI provided a more detailed exposition, both in terms of feature explanation and the range of suggested mitigation strategies. The approach advocated by OPENAI emphasized a comprehensive, multi-layered security framework, incorporating a variety of defenses from firewall configurations to intrusion prevention systems and sophisticated traffic analysis tools. This contrast between the two models highlights a pivotal distinction in their application: while Gemini focuses on succinct, direct responses tailored to the immediate features of an attack, OPENAI opts for a broader, more detailed perspective, advocating an extensive suite of security measures to combat potential threats.

V
Conclusion

This paper presented a novel end-to-end framework for IoT security that integrates Explainable AI (XAI) and Large Language Models (LLMs) for enhanced attack detection and response. By integrating XAI techniques like SHAP and LIME with an intelligent LLM Agent, the framework ensures the interpretability of ML model predictions. Empirical tests using the CIC-IOT-2023 dataset validated the effectiveness of our proposed framework in detecting and mitigating threats, proving its adaptability and potential in safeguarding IoT network. Future research will focus on expanding the framework’s detection capabilities and exploring emerging XAI methods for deeper insights, aiming to strengthen IoT security against evolving threats.
