Operationalizing Large Language Models with Design-Aware Contexts for Code Comment Generation Conference: International Conference on Software Engineering; April 12–18, 2026; Rio de Janeiro, Brazil
Aritra Mitra, Srijoni Majumdar, Anamitra Mukhopadhyay, Partha Pratim Das, Paul D Clough, Partha Pratim Chakrabarti

Abstract
. Comments are very useful to the flow of code development. With the increasing commonality of code, novice coders have been creating a significant amount of codebases. Due to lack of commenting standards, their comments are often useless, and increase the time taken to further maintain codes. This study intends to find the usefulness of large language models (LLMs) in these cases to generate potentially better comments. This study focuses on the feasibility of design documents as a context for the LLMs to generate more useful comments, as design documents are often used by maintainers to understand code when comments do not suffice.



1.
Introduction

Large Language Models (LLMs) have proved to be very useful in the world of natural language processing. These models are primarily tested for predict-the-next token, however, they can perform tasks like code summarization, test generation, code generation etc. after some fine-tuning
(
Chen et al., 2021
)
. In this study, we focus on the task of comment generation. Code comments are the first layer of support for understanding code, offering file- and method-level context, whereas inline comments capture design choices. Discrepancies between comments and code can show bugs and aid developers. Hence, developers should write succinct, accurate, and updated comments to guide future maintainers and users. But, comments are often neglected while writing codes
(
Fluri et al., 2007
;
Shmerlin et al., 2015
)
. A good comment reduces maintenance cost while not bloating the codebase
(
Sridhara et al., 2010
;
Aggarwal et al., 2002
;
Tenny, 1988
)
, while a bad comment provides little to no help, increasing the bloat. This is especially important when the majority of the time spent by developers is to understand a codebase
(
Xia et al., 2018
;
Chatterjee et al., 2023
)
.

This task has previously been performed with the code as context, with some additional information. However, we use the design documents as project-specific context. Design documents are used commonly to reference a codebase, as they explain the design choices, intended functionality, and any other common information, provide information on the architecture of the codebase, requirements of the system, contain links to any relevant sources, etc. Hence, for a maintainer, design documents provide useful information while working on the codebase. It is also important for the maintainer to keep these documents accurate, so it does not become erroneous for other maintainers, as well as the end-users. To tie everything together, we focus on the following research questions:

RQ1::

Can design documents improve the quality of comments generated by LLMs?

RQ2::

Can Abstract Syntax Trees (ASTs) be used as structural cues to generate better comments?

We use the paradigm of Retrieval-Augmented Generation (RAG)
(
Lewis et al., 2021
)
to generate comments from the code, with the design document as a source for the retrieval. RAG models have been shown to provide substantial benefit over vanilla LLMs for knowledge-intensive tasks
(
Gao et al., 2024
;
Lewis et al., 2021
)
. We have performed automated testing of the comments generated in this fashion using metrics such as ROUGE
(
Lin, 2004
)
, BLEU
(
Papineni et al., 2002
)
, CodeBERTScore
(
Cui et al., 2022
)
and GPTScore
(
Fu et al., 2023
)
, as well as conducting a study with novice coders, providing them with bug-fixing and codebase enhancement tasks. We have also classified the generated comments by the kind of information they provide.

We evaluated four generation setups: (i) Few-shot prompting with 30 examples, with at least 10 positive and 10 negative examples, (ii) Few-shot prompting with condensed abstract syntax trees (ASTs) as added context, (iii) Few-shot prompting with RAG on design document, (iv) Combining ASTs and RAG on design document. In the cases with the design document, we have found an increased number of navigational comments: linking to other parts of the code, algorithmic comments: explaining the workings of the code, and exception-based comments: showing edge-cases of the code. This can be seen from the examples in Table
1
, as LLM-generated comments with design documents fare better than the comments without them. We have seen a 35% decrease in bug-fixing time for LLM generated comments with the design document provided. The results for the codebase enhancement task are very similar, except that the decrease in time reduces to 28%. This can be explained due to the time taken to write the code not being affected, and the decrease coming from the time taken in understanding. To the best of our knowledge, this is the first systematic study of comment generation in C using an LLM architecture, with the following three major contributions:

•

A pipeline with the source code, ASTs, design documents, and RAG to support scalable and informative LLM-based comment generation for C and C++.

•

An assessment framework for C and C++ comments based on their usefulness, combining LLM-based metrics and human judgment.

•

Using design documents as context cues to gather project-specific information, and abstract syntax trees to gather system-specific information.

Related Work

We have seen that, even though there are shortcomings in code understanding capabilities of LLMs
(

;

)
, they are a useful tool to developers, and provide genuine aid in writing good code

. In previous works, LLMs were used to evaluate

and generate

have used API documentation for this purpose, but with RNN-based models instead of LLMs. However, these works were on generating code summary, which is generally much shorter than explanatory comments. We have also used the AST of the code for which we generate comments. But ASTs are generated while compilation, and preprocessor macros can change it depending on the system specifications. 4.2.
Prompt Engineering

We have used several techniques to remove any bias introduced by prompting. (i) For
exemplar bias
, we use a uniform distribution of good and bad comments in our prompts, so that the LLM can separate the good comments from the bad ones, and create a good comment. (ii) For
positional bias
, we have seen that changing the order of the examples showed a CodeBERTScore similarity of
\geq 0.95
in the generated comments for 71% of the cases. (iii) For
format bias

(
Xu et al., 2024
)
, we have seen that changing the wording also showed a CodeBERTScore similarity of
\geq 0.95
in the generated comments for 70% of the cases. (iv) For
knowledge bias

(
Xu et al., 2024
)
, we find that decreasing the context length only works for shorter codes, else the context limit is reached. However, the generated comments have a CodeBERTScore similarity of
\geq 0.95
in 78% of the cases.

4.3.
Human Survey Details

A total of 22 undergraduate Computer Science students were chosen for the experiments. While they had solid theoretical knowledge, they had limited practical experience with codebases or libraries, making them novice maintainers by industry standards. Each participant received 22 code samples: one without comments, one with original comments, and 20 with comments generated by LLMs (one for each LLM and context). Moreover, 22 versions of each code were created, so every participant viewed only one version of each file. The methodology was as follows: (i) Generate comments based on LLM for each file using the appropriate context. (ii.a) For bug-fixing, introduce a runtime bug that the compiler does not detect without changing major parts of the code. (ii.b) For enhancements in the codebase, remove a utility function but keep the related comment, or add a comment if none existed. (iii) Ask participants to fix the file. (iv) Record the time taken to complete for quantitative analysis. Note that comments were generated before inserting bugs, which created intentional inconsistencies between code and comments helping to find bugs. All experiments were conducted on Intel x86-64 systems running Ubuntu 22.04 LTS to maintain consistency. Participants did not have access to LLMs but could use the internet.

6.
Discussion

We have seen that, with the documents already available in the repositories, as per Table
3
, we are able to generate comments with a lightweight RAG-based implementation, that can facilitate better bug-fixing and enhancements in the codebases. Through this effective comment generation, we can move in a new direction, wherein, we can develop a holistic view of the complete database through the comment, effectively reverse engineering the design. We can also state that (
RQ1
) design documents can be used as project-specific context to generate better explanatory comments, helping novice coders, and (
RQ2
) ASTs overwhelm LLMs with too much information, causing worse comments.

Threats to validity.
There are several important points to note regarding comment generation using LLMs, which we discuss here.

Completeness.
When a larger piece of code is input to an LLM, it often omits parts of the code in its output. Moreover, this issue happens differently for different LLMs.
GPT-4o
,
OpenAI o4-mini
,
OpenAI o3
remove macros while keeping the core code intact, while
DeepSeek-R1
removes function bodies and replaces with
{...}
.
DeepSeek-R1
and
Codestral 25.01
also omit whole functions, and generate no comments. To quantify this issue, we define
Completeness Ratio
as the ratio of the sizes of the generated file and the original file, removing all comments and whitespaces.

.

Context Size.
The context lengths of the LLM models are often smaller than a large file, so the comments for that file must be generated through several passes. This creates consistency issues: even though the coding guidelines mention the commenting style, comments of a previous function are important to the comments further down. This nuance is lost if the information of the previous function is not accessible while generating further comments.

7.
Conclusion

We propose the use of design documents as a project-specific context for explanatory comment generation, using retrieval-augmented generation. We have shown that the comments thus generated provide significant help to developers in their most frequent tasks. We have also seen the effects and caveats of different LLMs, with

Future Plans

Here, we focused on generating comments for novice developers using LLMs, using RAG with the design document as additional context. In future, we can extend this study by changing the target demographic of the comment generations. We can also integrate this pipeline with existing integrated development environments (IDEs), allowing us to use IDE-specific information as well. Also, in future we can reduce the computational cost by using smaller but equally capable models for our task, possibly fine-tuned for this purpose.
