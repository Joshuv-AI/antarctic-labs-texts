SpIDER : Spatially Informed Dense Embedding Retrieval for Software Issue Localization
Shravan Chaudhari, Rahul Thomas Jacob, Mononito Goswami, Jiajun Cao, Shihab Rashid, Christian Bock

Abstract
Retrieving code units (e.g., files, classes, functions) that are semantically relevant to a given user query, bug report, or feature request from large codebases is a fundamental challenge for LLM-based coding agents. Agentic approaches typically employ sparse retrieval methods like BM25 or dense embedding strategies to identify relevant units. While embedding-based approaches can outperform BM25 by large margins, they often lack exploration of the codebase and underutilize its underlying graph structure. To address this, we propose SpIDER ( Sp atially I nformed D ense E mbedding R etrieval), an enhanced dense retrieval approach that incorporates LLM-based reasoning over auxiliary context obtained through graph-based exploration of the codebase. Empirical results show that SpIDER consistently improves dense retrieval performance across several programming languages.

Recent work has demonstrated the potential of agents powered by Large Language Models (LLMs) to perform automated bug repair and implement basic features within large-scale software repositories
(
16
;
5
;
15
)
. A critical prerequisite for effective code generation is the precise identification of relevant contextual information, specifically code units such as functions, classes, or files. This code localization task represents a foundational yet notably difficult challenge, particularly when operating at the fine-grained level of function retrieval
(
9
;
11
;
17
;
1
)
. Poor code retrieval directly compromises the quality of generated code, leading to incorrect or incomplete fixes, the introduction of new bugs, and substantial increases in both the computational cost and duration of the repair process. Effective code localization is thus essential for realizing the promise of autonomous software engineering agents.

Current approaches to code localization fall into two primary categories. Some recent methods exploit graph representations of code repositories alongside the reasoning capabilities of LLMs
(
10
;
1
;
8
)
. These approaches primarily employ sparse retrieval strategies such as
BM25

(
13
)
to identify relevant graph nodes or subgraphs for agent exploration. Other methods train bi-modal encoders that semantically align dense embeddings of code units with issue descriptions
(
3
;
12
)
. These dense retrieval methods rank code units, such as functions, classes, or files, based on their embedding similarity (typically cosine similarity) to the issue description.

However, existing approaches face three critical limitations. First, conventional contrastive learning-based retrieval methods overlook the structural context of code modules within a repository when ranking them. We observe that in software issue localization, buggy code modules are often spatially proximate within the codebase (e.g., within the same file or in neighboring functions), and top-ranked entities retrieved via dense semantic similarity frequently reside near the actual buggy modules. Consequently, relying exclusively on semantic similarity to select the top-
K
functions may overlook relevant candidates that are spatially close to highly-ranked modules but exhibit marginally lower embedding similarity scores. Second, existing methods have been primarily evaluated on Python benchmarks
(
1
;
3
)
, particularly
SWEBench-Lite
,
SWEBench-Verified
, and
LocBench

(
9
;
2
;
1
)
– leaving their performance on other programming languages largely underexplored.
Third, function-level retrieval, which represents the most challenging granularity compared to class-level and file-level retrieval
(
11
;
12
;
1
)
, remains largely understudied.

To address these limitations, we introduce
SpIDER
, a novel and simple graph-aware dense retrieval strategy for function-level code localization.
SpIDER
incorporates spatial locality as a complementary signal to semantic similarity, enabling the joint exploitation of both code content and repository structure within a fixed retrieval budget. Our primary focus is on retrieval methods that can augment downstream tasks, including ranking code modules, precise localization, and automated patch generation for resolving GitHub-style issues. Moreover, to facilitate comprehensive evaluation across multiple programming languages, we also introduce
SpIDER-Bench
for code localization, encompassing Python, Java, JavaScript, and TypeScript repositories from
SWEBench-Verified
,
SWE-PolyBench
, and
Multi-SWEBench
.

Our primary contributions are as follows:

•

We propose
SpIDER
, a novel ane simple graph-aware dense retrieval strategy that incorporates both semantic content and code structure to determine the most relevant code functions for a given issue description under a fixed retrieval budget.

•

We introduce
SpIDER-Bench
, a heterogeneous graph-structured dataset for multi-language code localization. It consists of software issues from existing GitHub repositories in
SWEBench-Verified
,
SWE-PolyBench
, and
Multi-SWEBench

•

We provide comprehensive empirical validation of
SpIDER

BM25
across all four languages in
SpIDER-Bench

Code Graph Construction

Given a code repository, the goal is to construct a graph that can be utilized by a downstream user (e.g., LLM agent) to understand the code structure in unison with the code content to estimate the likelihood of a module to solve a given issue based on logical reasoning and understanding of the codebase. There are various unique designs of code graphs that can be constructed from a code repository based on the definition and construction of the nodes and edges.
For example, in
10
each node of the graph corresponds to a line of code which can of type either definition or reference.
The edges between nodes capture the relation between them which can of type ‘
invokes
’ or ‘
contains
’.
On the other hand, in
1
, each node corresponds to a code module (function, class, file or directory) which are connected via edges of types ‘
contains
’, ‘
invokes
’, ‘
imports
’ and ‘
inherits
’.

8
defines two types of graphs, directory-level graph (called module call graph) and file-level graph (called function call graph).
Directory-level graph captures the directory structure where each node is a file which in turn can be expanded into function call graph, each node being a function.
The files are connected using ‘
imports
’ edge whereas functions are connected using ‘
invokes
’ or ‘
inherits
’ edges.

Problem Definition and Notations

Given a retrieval budget
K
, issue description
Q
, and a codebase represented as a graph
\mathcal{G}=(\mathcal{V},\mathcal{E})
with
n
nodes, the task is to retrieve the top-
K
functions that are most likely to require edits in order to resolve the issue described by
Q
. Here,
\mathcal{V}=\{v_{i}\}_{i=1}^{n}
is the set of nodes and
\mathcal{E}\subseteq\mathcal{V}\times\mathcal{V}
is the set of edges.
Each node
v_{i}\in\mathcal{V}
represents a code entity such as a function, class, file, or directory, and entities of interest (in this case function nodes) contain the corresponding source code content.
Each edge
e(v_{i},v_{j})\in\mathcal{E}
denotes a relation between code entities, and can be one of the four edge types, ‘contains‘, ‘imports‘, ‘invokes‘ and ‘inherits‘.

Let
\mathcal{V}^{*}=\{v^{*}_{i}\}^{m}_{i=1}\subseteq\mathcal{V}
denote the ground-truth set of
m
relevant function nodes for issue
Q
. Let
\mathcal{V}_{K}=\{\hat{v}_{i}\}^{K}_{i=1}\subseteq\mathcal{V}
denote the top-
K
function nodes retrieved by a model. The objective is to maximize Recall@
K
and Accuracy@
K
(denoted as Acc@
K
), defined as follows:

\text{Recall@}K=\frac{|\mathcal{V}^{*}\cap\mathcal{V}_{K}|}{|\mathcal{V}^{*}|}

\text{Acc@}K=\mathbb{I}[\mathcal{V}^{*}\subseteq\mathcal{V}_{K}]

Intuitively, Recall@
K
measures the proportion of ground truth nodes that appear in the retrieved top-
K
list. In contrast, Acc@
K
is a stricter metric: it is 1 for an instance only if all of its ground truth nodes are included in the top-
K
results. At the dataset level, mean Acc@
K
reflects the proportion of instances that achieve perfect recall (i.e., Recall@
K
= 1).

Building Code Graphs

To represent a codebase as a graph, we follow
1
, and define each node as a module that can be either function, class, file or directory, connected by edges of type ‘imports’, ‘invokes’, ‘contains’ and ‘inherits’.
We use python AST module
1
1

1

https://docs.python.org/3/library/ast.html
for constructing graphs for Python programming language, whereas for Java, JavaScript and TypeScript, we use tree-sitter
2
2

2

https://github.com/tree-sitter
implementation to construct similar code graphs. The graph construction starts by navigating the repository.
For a directory encounter, it is added as a directory node to the graph. Similarly, if a file is encountered, it is added to the graph if it contains a class or a function, otherwise, it is ignored.
Then we analyze the valid files (ending in ‘.py’ for python, ‘.java’ for Java, ‘.js’ for JavaScript and ‘.ts’ for TypeScript) further to handle various types of code lines in the file parsed by the tree-sitter or AST python module.

The core challenge in constructing graphs for Java, JavaScript and TypeScript lies in the many ways functions and classes can be defined and organized.
For instance, a class might be declared in one file with no method implementations, while its methods are defined elsewhere, either in a different part of the same file or even in a completely separate file.
This separation complicates the process of building a complete and accurate program graph.
We explicitly handle diverse scenarios of such declaration/definitions using Tree-sitter.

section

Figure

1
provides a high-level overview of our proposed framework.
Given an issue description (bug report, feature requests, etc.) and codebase,
SpIDER
retrieves top
K
most relevant functions that should be modified to solve the issue.
This method can be easily extended to class level as well as file level retrieval by using subset of code chunks if the entire class or file level code cannot fit into the LLM context (refer to
section

A.2
for more details).
For this reason, we use the terms ‘function retrieval’ and ‘node retrieval’ interchangeably.

SpIDER
’s design reflects our key observation: for instances with multiple edits, it is often the case that the edits are spatially close to each other in a code graph due to the dependencies on other functions/classes/files.
Therefore, modifying a function can have cascading effects, requiring modifications to all other functions that call it, as well as to its containing class/file.
Similarly, while semantically retrieved nodes offer diverse coverage of the potential candidate functions across the codebase, they may not be fully leveraging the "near miss" scenarios, where the true solution may spatially close to the top
K
ranked functions.

SpIDER
tries to improve the coverage by balancing the neighborhood exploration and semantic retrieval to retrieve the most likely set of
K
functions.

Semantic Retrieval.

The first step is to retrieve the top
K
functions based on the semantic similarity of their dense embeddings to the issue description.
We can obtain dense embeddings from encoders like
CodeSAGE

18
or an embedding model from
SweRank

12
.
Once function embeddings are generated in the code graph, we rank functions by cosine similarity to the issue description embedding.
Next, we retrieve top
K
functions from the semantically ranked list of functions. We call the set of node indices of the top
K
functions ranked in the descending order of their similarity scores with the issue descriptions as
\mathcal{I}_{K}
.
We also store a set of node indices of top
N
ranked functions
\mathcal{I}_{N}
where
N>K
. This is our primary set of retrieved functions which we aim to further improve using neighborhood exploration.

Neighborhood Exploration.

Since we have a retrieval limit of
K
, it is not affordable to store the entire neighborhood of all the nodes in
\mathcal{I}_{K}
.
To strictly limit the neighbors we explore and add to the final retrieval list of the same size
K
, we restrict the neighborhood exploration to the first
C
nodes in
\mathcal{I}_{K}
within a
d
-hop distance from the center nodes.
While we primarily focus on exploring neighbors via the ‘
contains
’ edge type to capture the structural organization of the codebase,
SpIDER
can be extended to incorporate other edge types like ‘
imports
’, ‘
invokes
’, ‘
inherits
’, etc. for further performance enhancements.
Two functions within the same class would be 2 hops away from each other. Similarly, two functions within two separate classes in two separate files will be 4 hops away. We do not explore neighbors beyond
d
hop distance. Increasing the depth improves coverage at the cost of increased neighbors context per center. Hence,
d
and
C
are hyperparameters that a user can adjust based on the downstream budget, thereby offering more flexibility and tuning capabilities in terms of retrieval performance.

For evaluation, we set
C=5
and
N=500
based on optimal performance observed for Python in the
SWE-PolyBench
dataset (see
table

4
and
table

12
).
These values are kept fixed across all languages and datasets to avoid hyperparameter overfitting. Additionally, we set
d=4
to ensure that token consumption per LLM invocation remains below
10\,000
.
While higher values of
K
generally improve retrieval performance (see
table

13
,
fig.

2
), we evaluate for
K=20
in our main results (Tables
3
and
2
) to ensure fairness to the
SweRank
baseline, which selects
K=20
as optimal for its downstream LLM-based reranker that improves localization at higher ranks.

Neighbor filtering

We perform 2-stage filtering of the neighbors.
In the first stage, we ignore all neighbors whose indices are not present in
\mathcal{I}_{N}
.

N
is another hyperparameter to be configured based on available LLM context budget.
The second filtration step leverages the logical reasoning capabilities of LLM to determine the most relevant neighbors for a particular center.
The LLM is instructed to only return the neighbors which it considers relevant to solving the issue.
This restricts the LLM from resulting in superfluous set of neighbors of the centers.
We then add the newly LLM-selected neighbors
\mathcal{I}_{\text{LLM}}
(including the centers in
\mathcal{I}_{C}
) to the list
\mathcal{I}_{K}
. We define the non-center nodes in
\mathcal{I}_{K}
as
\mathcal{I}_{\text{rest}}:=\mathcal{I}_{K}\setminus\mathcal{I}_{C}
.
Since
\mathcal{I}_{\text{LLM}}
consist of additional neighbor nodes which may or may not be present in
\mathcal{I}_{K}
, we include the nodes in
\mathcal{I}_{\text{LLM}}
at the cost of dropping bottom ranked nodes in the set
\mathcal{I}_{\text{rest}}
. The number of bottom ranked nodes dropped from
\mathcal{I}_{\text{rest}}
are equal to the new neighbor nodes present in
\mathcal{I}_{\text{LLM}}
keeping the number of retrieved nodes constant (i.e.,
K
).
In other words, our final set of indices
\mathcal{I}_{\text{final}}:=\mathcal{I}_{\text{LLM}}\cup\mathcal{I}_{\text{retain}}
where
\mathcal{I}_{\text{retain}}
is top-
(K-|\mathcal{I}_{\text{LLM}}|)
ranked nodes from
\mathcal{I}_{\text{rest}}
.

6
Experiments

Our goal is to answer the following three research hypotheses from our experiments:

H1
Can the graph structure of a codebase be leveraged to improve retrieval recall and accuracy for instances involving multiple function edits that are spatially close within the code graph?

H2
Among the top-
K
nodes retrieved using dense embedding retrieval, do the highest-ranked nodes serve as accurate approximations of the actual ground truth locations in the code graph? If so, is it possible to reach the true nodes through local exploration of the code graph, potentially trading off some lower-ranked retrieved nodes in favor of better spatial coverage?

H3
How do existing retrieval methods, along with our proposed approach, perform across programming languages beyond Python?

To this end, we focus our study towards scenarios having more than 1 edit per instance as shown in table
1
for 4 programming languages, namely Python, Java, JavaScript and TypeScript, highlighting the robustness of the baselines and our approach.

.

Our results reveal that our
SpIDER
strategy consistently enhances retrieval performance, particularly in Recall@K and Acc@K, across all programming languages and datasets. The best-performing embedding model across datasets is
SweRankEmbed-Small
, and applying
SpIDER
further increases Recall@20 and Acc@20 by at least

The MRR@
K
metric benefits from

primarily when the first relevant ground-truth item within the top-

results is a neighbor of a center node. In cases where the first relevant item is a non-center node, particularly in TypeScript as shown in Tab.

—
SpIDER
may rank neighbors of center nodes ahead, slightly reducing MRR@
K
. Since
SpIDER
is not explicitly designed to optimize the precise ranking order within the top-
K
results, improvements in MRR@
K
over baseline DER methods are modest but still observable.

On the Number of Top
C
Centers

In this section, we provide ablation studies on varying the number of top
C
centers on
SWE-PolyBench
for retrieval performance. Increasing
C
results in more neighborhood explorations and addition of relevant neighbors in the list of top-
K
retrieved modules at the cost of dropping bottom semantically ranked modules. Furthermore, each neighborhood exploration around a center requires 1 LLM call for filtering neighbors. Hence, increasing
C
results in increased number of LLM calls. In
table

4
, we ablate on
C
and observe the corresponding performance changes. We see that the performance saturates at
C=5
for
N=500,d=4
at
K=20
. Hence, we stick with
C=5
for all our experiments. A downstream user can aim to choose a
C
that fits in their LLM invocation limits per instance.

On
K

The choice of
K
for retrieval depends on the budget of the downstream application. Retrieval performance is expected to improve as
K
increases. We further validate this claim in figures
2
and
5
where we see a monotonic improvement in performance as
K
incremented. The downstream user can choose a
K
that is allowed by their budget while aiming for best retrieval performance.

On depth
d

In this section, we vary the maximum depth
d
for breadth-first search (BFS) exploration while selecting neighbors and observe the corresponding impact on the performance. Greater depth would result in more number of neighbors per center that need to be filtered using the two-stage neighborhood filtering. In
table

5
, we ablate on
d
keeping
N=100,C=3
and
K=20
. We see that there is notable improvement in the Recall@20 and Acc@20 performance with increasing depth
d
, however, increasing
d
also increases the token consumption to LLM while filtering the neighbors. The downstream user can choose
d
based on their token budget per LLM invocation.

On the Primary Neighborhood Filtering Threshold
N

In
table

12
, ablate on
N
to see it’s impact on the retrieval performance. Higher
N
results in more neighbors passing the primary filteration and hence, more neighbors for the LLMs to sift from. We see that the performance saturates around
N=300
for
C=3,K=20,d=4
. Hence, the choice of
N
offers the same flexibility as
d
to the downstream user. The user can choose
N
based on the token limit per LLM call.

7
Conclusion

We introduced
SpIDER
, an neurosymbolic code retrieval framework built on dense embedding models and spatial information from graph representations of a codebase.
Through rigorous empirical analysis, we demonstrated the efficacy and efficiency of our method over existing retrieval methods in the the challenging setting of function-level retrieval.

SpIDER
’s exploration depth can be efficiently controlled by adjusting the subgraph size during retrieval, maintaining robust performance even with compact subgraph configurations for token-constrained applications.
While, in this work, we pioneer retrieval evaluation for non-python programming languages such as Java, JavaScript and TypeScript,
SpIDER
can be readily adapted to other programming languages as it builds on the
Tree-sitter
library.
