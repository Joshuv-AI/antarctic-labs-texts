SilverTorch: A Unified Model-based System to Democratize Large-Scale Recommendation on GPUs

Abstract
. Serving deep learning based recommendation models (DLRM) at scale is challenging. Existing systems rely on CPU-based ANN indexing and filtering services, suffering from non-negligible costs and forgoing joint optimization opportunities. Such inefficiency makes them difficult to support more complex model architectures, such as learned similarities and multi-task retrieval. In this paper, we propose SilverTorch, a model-based system for serving recommendation models on GPUs. SilverTorch unifies model serving by replacing standalone indexing and filtering services with layers of served models. We propose a Bloom index algorithm on GPUs for feature filtering and a tensor-native fused Int8 ANN kernel on GPUs for nearest neighbor search. We further co-design the ANN search index and filtering index to reduce GPU memory utilization and eliminate unnecessary computation. Benefit from SilverTorch’s serving paradigm, we introduce a OverArch scoring layer and a Value Model to aggregate results across multi-tasks. These advancements improve the accuracy for retrieval and enable future studies for serving more complex models. For ranking, SilverTorch’s design accelerates item embedding calculation by caching the pre-calculated embeddings inside the serving model. Our evaluation on the industry-scale datasets show that SilverTorch achieves up to 5.6 × 5.6\times lower latency and 23.7 × 23.7\times higher throughput compared to the state-of-the-art approaches. We also demonstrate that SilverTorch’s solution is 13.35 × 13.35\times more cost-efficient than CPU-based solution while improving accuracy via serving more complex models. SilverTorch serves over hundreds of models online across major products and recommends contents for billions of daily active users.



1.
Introduction

In the past decade, recommendation systems have become a fundamental way for individuals to discover information. Behind the scenes, embedding-based Deep learning recommendation models (DLRM) play a critical role in learning the relationship between users and items
(
Mudigere et al. 2022
;
Covington et al. 2016
)
.
Recommendation systems face unique challenge during inference, as trained models cannot be served directly. At inference time, the inputs are user features only, returning a list of items. Industrial scales contain 10 - 100 million items, which is computationally infeasible to rank all during serving. Consequently, a multi-stage design is widely adopted, comprising a retrieval stage and multiple ranking stages. Each stage defines its model, and later stage models typically rely on richer features and utilize more complex architectures.
This design works like a funnel. First, the retrieval model narrows the item candidate pool to thousands of items by formulating the task as a Approximate Nearest Neighbor (ANN) search problem in vector space, identifying relevant items based on vector similarities. This is commonly implemented using libraries like Faiss
(
Douze et al. 2024
;
Johnson et al. 2019
)
, RAFT
(
Rapidsai 2022
)
or a dedicated vector database system like Milvus
(
Wang et al. 2021
)
. Meanwhile, the retrieval stage incorporates feature filtering to match users’ feature attributes in multiple dimensions, removing irrelevant items. These filters are mostly implemented using inverted-index mechanism. The retrieved items are then passed to ranking models. The ranking stage can be further divided into an early-stage ranking(ESR) model, which trims the set to hundreds, and a late-stage ranking(LSR) model, which selects the final tens of items. Ranking models can be served directly since the number of items to be ranked is small.

While existing works attempt to fill this gap, they introduce additional services including ANN search, feature filtering, and caching.
These systems are originally designed for general-purposed applications, requiring customized optimizations when conducting to recommendation. Specifically, for recommendation, modern retrieval models expect the ANN service to return tens of thousand items for further scoring. This is not effectively supported by existing libraries. Similarly, inverted-index based filtering approach has proven to be efficient for text-based search. However, in recommendation, the cardinality of the feature attributes for each item is orders of magnitude smaller. Furthermore, service-based recommendation systems must handle the version consistency because different parts of the serving model are split across services to generate a logical snapshot during inference. Such system divergence and the versioning challenge add unexpected delays and complexities.
In this work, we propose SilverTorch, a unified model-based system built on PyTorch. Rather than building standalone services, a SilverTorch model defines the ANN index and feature filtering as parts of serving model itself. SilverTorch also pre-fetches item embeddings and features into serving model to accelerate early-stage ranking(ESR) models, eliminating additional requests for calling caching service. By leveraging such a in-model design, SilverTorch not only provides unified recommendation stack on top of PyTorch that naturally avoids handling versioning across services, but also simplifies the client-side logic. Instead of handling multiple requests to different services during serving, client sends a single request to the runtime that serves SilverTorch models.

Another major challenge in serving large-scale recommendation models is compute scalability. As candidate pool grows, retrieval models must build larger-size index for efficient ANN search and feature filtering. Meanwhile, recommendation models are becoming deeper and more complex. Recent retrieval approaches adopt more complex learned structures to replace the dot-product to represent similarities
(
Zhai et al. 2023
)
. There is also trend to incorporate richer historical user-item interaction data as input features
(
Zhai et al. 2024
)
, further increasing computational demand. Unfortunately, existing solutions cannot satisfy these needs. First, existing recommendation systems adopt CPU-based ANN indexing and feature filtering
(
Jayaram Subramanya et al. 2019
;
Pinterest 2023
;
Covington et al. 2016
;
Huang et al. 2020
)
. To the best of our knowledge, no existing work studying feature filtering on GPUs. For ANN search, there are libraries implement ANN algorithms on GPUs
(
Johnson et al. 2019
;
Wang et al. 2021
)
. However, they only supports topk and probes less than 2048
(
github
)
and topk less than 1024
(

)
. This limits the evolution of retrieval models. For example, advanced retrieval models require to search hundreds of thousands of items from ANN and re-rank them in the following interaction layers.
The CPU-based ANN search and filtering can scale out by adding more CPU servers to partition the larger index, but it quickly becomes expensive and inefficient to server complex models for online recommendation.
CPU-based index building mechanisms such as HNSW
(
Malkov and Yashunin 2018
)
also delay the model deployment because they rely on updating parallelism-unfriendly data structures like graphs and trees
(

Intermediate results between services must be serialized and transformed to appropriate formats. Such unnecessary data transformation and network cost increase serving latency.
SilverTorch leverages PyTorch to fully utilize GPUs, introducing model-based ANN search and bloom index filtering designed for recommendation systems. Both the ANN search and the feature filtering processes during inference are unified as tensor computation, consistent with other model serving operators. Such unified design enable us to further optimize the ANN search and feature filtering by co-designing them to further reduce GPU memory allocation during inference and eliminate unnecessary computation.

Benefit from SilverTorch’s in-model design, we extend existing retrieval models by introducing a OverArch scoring layer to further learn user-item interactions. The initial returned items from ANN search and filtering are re-ranked by the OverArch layer and return retrieval items. Furthermore, we enable multi-task retrieval together with a in-model aggregation layer (referred to as Value Model) to compute the overall score across multi-task objectives. For ESR models, SilverTorch model contains pre-calculated item embeddings that are loaded into GPU memory during serving to reduce network overhead and calculation cost. For a multi-stage recommendation system, SilverTorch’s serving paradigm enables more functionalities into retrieval models and ESR models, aligning the objectives of retrieval and ranking more consistently throughout the recommendation funnel(known as funnel consistency). Background and Motivation

2.1.
Multi-stage Recommendation Flow

Figure 1.
Motivation Examples: Figure 1(a) shows the service-based recommendation serving. Figure 1(b) shows the versioning challenge of service-based retrieval.

Features for recommendation models are categorized into dense (numerical) and sparse (categorical). User and item features contain both types, with contextual features (e.g., timestamp) bundled with user features. Retrieval models use representative user and item features but exclude cross features. ESR models add interaction layers after concatenating user and item embeddings. LSR models use comprehensive features, including cross features, and adopt more complex architectures. The embedding in our paper refers to the vector representation generated from either the user-side layers(User Tower) or the item-side layers(Item Tower).
Typical flow of service-based recommendation systems include training, post-processing and online severing. In offline part, post-processing generates item embeddings from trained retrieval model and building inverted index for feature filtering such as location, language and interest. The item embeddings are used to build ANN search index. In online part, as shown in Figure
1
(a), a request first triggers retrieval stage. User features are loaded from the feature store to compute user embedding from the User Tower, which is used as the query for ANN Search. Meanwhile, recommendation request is also sent to the filtering service. Finally, results are merged and sent to ESR.
User embedding and item embedding for ESR are computed through forward pass of the model. The LSR stage takes ESR output and return final items. This flow is widely adopted across industrial and academic studies. However, it has two major drawbacks.

2.2.
Limits of Service-based Recommendation

Lack of Co-Design
. As shown in Figure

Adopting a unified design approach facilitates co-design across recommendation services, making it friendly to further disaggregate serving components based on serving characteristics(e.g. compute bound, memory bound) rather than pre-defined boundaries.

3.
SilverTorch Overview

Figure 2.
Overall workflow of SilverTorch model publish and serving and Pseudocode of SilverTorch model definition.

We propose SilverTorch, a model-based approach to unify recommendation systems. Instead of building standalone services, SilverTorch defines model layers to replace the functionalities of dependent services for serving. A SilverTorch model consists all serving components inside the model itself. The inference flow is no difference than a forward function execution of tensor operators. Figure
2
illustrates the overall workflow of SilverTorch and its prototype.

After model training, the post-processing before serving is defined as SilverTorch publish. We initially load trained retrieval and ESR models, which we refer to as root models. The embedding evaluator utilizes both the item features from the candidate pool and the root model to calculate the item embeddings.
The item embeddings layer are added into root models. We leverage GPUs calculating the embeddings to speedup the publish.
The item embeddings of the retrieval model are also processed by the ANN index builder. It quantizes the embeddings to Int8 precision and adopts KMeans++-based
(
Arthur and Vassilvitskii 2006
)
clustering to the embedding vectors. This process also runs on GPUs to accelerate the publish. For feature filtering, SilverTorch introduces a novel signature-based GPU index(referred as Bloom Index) instead of using inverted index. This high-speed index is inspired by the bloom filter and BitFunnel
(
Goodwin et al. 2017
)
, transforming online index matching to bit operators. Both the ANN index and bloom index are represented as a group of tensors that added into root model. These tensors serve as parameters of the model that take query tensor from a recommendation request as input, conduct kernel operators on GPUs and output tensor results.
Meanwhile, User Tower, OverArch layers, and Value Model are quantized to BFloat16 and constructed as model parameters by corresponding builders. The model composer assembles all these components into a SilverTorch model. Finally, the model optimizer compiles the eager-mode SilverTorch model into a graph representation and applies graph-level optimizations, lowering and scripting.
The output of publish is a SilverTorch model snapshot representing as a model definition with different layers of model parameter tensors that can be served in pure C++ runtime(referred to as predictor).

During online serving, the predictor runtime is simplified as a forward function executing of a SilverTorch model. The retrieval process is triggered first. The SilverTorch retrieval model extracts different types of user features and the filtering query from recommendation request, executes a sequence of kernel operators on GPUs. First, the user layer computes the user embedding. Subsequently, the Bloom index layer further filters out irrelevant items and generate a mask tensor. The user embedding and the mask tensor are then fed into the ANN layer to search approximately tens to hundreds of thousands of items. OverArch layers fetches corresponding item embeddings from embedding cache of retrieval model, and re-rank these items by calculating scores and aggregate using the value model across multi-tasks. Final retrieval result contains thousand-scaled ids and triggers the ESR. The ESR request contains both user features and the retrieval results. The user embedding of ESR is calculated, the item embeddings are looked up from embedding cache, followed by following operators. The ESR model typically returns hundred-scaled items.

4.
SilverTorch Model Design

The idea of SilverTorch is to define the recommendation serving components as model, which provides a unified interface and enables the co-design between components. This section first introduces key abstractions in SilverTorch, and discuss in-model design containing the bloom index based feature filtering and a fused Int8 ANN search. Finally, we discuss a co-designed ANN search and feature filtering algorithm. Overall, SilverTorch follows two design principles.

Index as Model
. In recommendation systems, both ANN search and feature filtering are required to efficiently serve online requests within a service level agreement(e.g., 80ms P99 latency). A typical recommendation query can be defined as follows:

ANN_Index(user_emb) AND
(feature1=value1 OR feature1=value2 OR ...) AND
(feature2=value1 OR feature2=value2 OR ...) AND..

A concrete example is below:

ANN_Index(user_emb) AND item_country = "US"
AND (item_lang = "EN" OR item_lang = "ES")

The user embedding (user_emb) is computed from User Tower, while item attributes such as item_country and item_lang are pre-defined. Query parameters include user-specific features (user_emb, user_country, user_lang1, user_lang2).
To support the ANN search sub-query, SilverTorch provides a tensor-native Int8 ANN kernel leveraging the IVF(inverted file indexing) algorithm. It first probes and expands the ANN operator into a subquery that matches a subset of items with high overlap with the exact K nearest neighbors. Then it calculates the topk items within each cluster and aggregates to the global topk result.
For feature filtering, we propose bloom index, which transforms the feature filtering process into bit-wise tensor operations on GPUs. Benefit from the unified stack, we co-design the feature filtering with ANN search by proposing a ANN search and filtering co-designed kernel.
The whole processes are executed inside a single runtime(referred to as predictor) since both the ANN search and feature filtering are consistent with running other layers of the model inference. This design eliminates the communication to standalone indexing services and fully utilizes the GPU resources for serving recommendation queries.

Embedding and Feature Cache
. For Early-Stage-Ranking models, item embeddings serve as item representations and are combined with user embedding as inputs to OverArch. A typical ESR model calculates thousand-scale items online. To reduce computational cost online, SilverTorch pre-computes item embeddings during publish and populates results into GPU memory as embedding cache. Frequent embedding look-ups benefit from High Bandwidth Memory(HBM) that allows extracting a batch of item embeddings. The in-model embedding look-up removing the dependency of caching services and reduces network cost. For advanced retrieval models, we introduce OverArch which takes item ids from ANN and bloom index as input to re-rank items. The embedding cache can be also used here.

4.1.
Bloom Index

A recommendation query contains feature filtering parts to match relevant item features to user’s attributes. The filtering subquery is represented as nested logical expression with values. A common mechanism is to build inverted index, which maps each terms to a list called posting list. Similarly, in recommendation, we can build such index to map each feature value to a items list.
Unfortunately, inverted index is not well suited to GPUs.
First, in contrast to text terms in web search that follows a Zipf’s distribution with many shorts postings, recommendation features are typically broad and dense. The lack of sparsity removes the efficiency gains that inverted indexes provide in the Needle-in-the-Haystack search scenarios. Second, the list-based structure of inverted indexes is inherently sequential and poorly aligned with modern accelerators. These limitations motivate us to design a more efficient index structure of feature filtering.

SilverTorch adopts the design by placing the indexing components inside serving model. We revisit the feature filtering problem with following observations. First, we know the general structure of filtering query when we build the SilverTorch model so that we can leverage this knowledge to arrange data in specific structures. Second, in recommendation systems, each item only contains limited feature values comparing to the high feature cardinality in text retrieval.
We found forward index could evaluate against the query independently. The fact that the forward index search is stateless implies that all items can be evaluated in parallel, making it a good fit for GPUs. During filtering, different thread processes a partition of items and matches local results. This approach could largely improve efficiency in high-recall search scenario compared to the multi-way merge of inverted index search. In SilverTorch, we define the operators in PyTorch, therefore, the tensor layout of forward index can be represented as following tensors: feature_ids tensor for feature identifiers, feature_values tensor for grouped feature values by (item, feature_ids), and feature_offsets tensor to index feature_values, defining value boundaries for each feature. The feature_values for a given (item, feature_id) pair are sorted. However, although forward index allows parallel computation across items, they are sub-optimal for GPUs. Offset lookups for each (item, feature) pair create irregular and non-contiguous memory access patterns, limiting throughput when multiple filter conditions must be matched. And since the GPU memory is expensive and largely impact the throughput, forward index requires a large memory footprint because it stores the actual feature values using int64. To overcome these limitations, we propose a bloom-filter based GPU indexing structure, named the Bloom Index. It addresses the warp divergence of forward index, ensures contiguous memory access through bitwise operations and significantly reduces memory consumption by providing a signature bits for each item.

Figure 3.
Bloom Index Design for Feature Filtering

The feature filtering problem can be formulated as follows, given a list of items V, where each item is represented as a list of features:

(1)

V=\{V_{i}=[f_{1},f_{2},...f_{t}]\}

Given a query Q, which can also be represented as a list of features:

(2)

Q=[f_{1},f_{2},...f_{t}]

The goal is to find a list of items that meet following criteria:

(3)

R=\{V_{i}\in V\mid Q\cap V_{i}=Q\}

Bloom filter is a hash-based structure used to check whether an element exists in a set. In bloom index design, we construct a M-bit bloom filter for each item, denoted as VB_i. For each feature, we apply K hash functions to compute hash_i(feature) % N and set the corresponding bits in bloom filter to 1. Similarly, we generate a M-bit bloom filter for the filtering query, denoted as QB, and apply previous k hash functions to mark corresponding bits to 1. By applying this to (3), we obtain:

(4)

R=\{V_{i}\in V\mid V_{i}=VB_{i}\wedge(QB\&VB_{i}=VB)\}

To implement (4), each GPU thread first iterates through the bits of QB and then iterates each item in its partition to compute the matches. Figure
3
(a) illustrates this process using a real example. While transforming filtering into bit manipulation of matrix, it has two drawbacks. First, each GPU thread processes one item at a time. Second, items corresponding to 0 bits in QB are also evaluated. We optimize it by examining only bits set to 1 in QB. If all the corresponding bits in VB_i are also 1, the item is a match. By rotating the matrix, we isolate the rows containing 1 bits in the query and skip the rest. Such transpose allowing multiple items to be matched simultaneously while eliminating the bit masks necessary to perform Boolean computation.
We only calculate rows containing the 1 bit from QB by performing a bit-wise AND operation between all the matched rows. Any 0 bits indicate a non-match, while 1 bits indicate a match. Figure
3
(b) shows the process how our bloom index works. QB is a 8-bit bloom filter, and V2 and V6 are matched items.
We use a single instruction to execute a 64-bit AND operation (PTX: and.b64), meaning each thread processes 64 items using a single instruction. Comparing to forward index, which matches item-by-item iterative inside a partition and requires a Boolean to store the result for each item, bloom index process 64 items at one time and could store the results of 64 items using just one int64. For a case of 40 million items, the data can be splitted into 625,000 partitions. Each thread processes
\frac{625,000}{\text{\#Threads}}
partitions of items.
Bloom index relies on bloom filter, which may introduce false positives due to hash collision. By tuning the bloom filter size M and the number of hash functions K based on the number of features N could keep the rate very low. Additionally, bloom index is primarily used in retrieval stage so rare false positive items can always be evicted by future ranking stages.

4.2.
Fused Int8 ANN Search

ANN search is critical for retrieval in recommendation. Existing solutions rely on standalone services. For example, we can build a service leveraging the open-source Faiss library, or deploy a vector search service such as Milvus. However, both of them are general-purposed and can not satisfy the requirements of large-scale recommendation systems. For example, although both Faiss and Milvus supports executing ANN search on GPUs, a hard limitation is that both limit the topk and number of probes. In real recommendation model design, ANN search is only part of the retrieval process, and it requires returning hundreds of thousands of items from ANN search for further scoring. Therefore, most of existing recommendation systems in production still adopt CPU-based ANN search during retrieval due to its scalability and maturity. As discussed, CPU-based retrieval hinders serving more complex model architectures such as multi-task retrieval and OverArch scoring layers.

To overcome above limitations, we propose a tensor-native ANN search kernel in SilverTorch, leveraging tensor as ANN index container. The tensor-native design can be directly incorporated into any ML model serving stack and is by nature parallel-friendly on GPUs. We adopt the clustering-based IVF algorithm that can be transformed into two matrix multiplication(MM) operations internally. First, calculate the dot product between query embedding and all centroid embeddings. Second, construct the item embeddings from previous selected clusters and identify the topk similar items based on their proximity to the query embedding.
Unfortunately, the bottleneck of this algorithm lies in the index selection step that generates a temporary embedding indices tensor to get embeddings for compute the topk. Additionally, the performance of index selection operator itself is slow. To address these issues, we introduce a fused index-matmul operator after probing, it streams item embeddings directly from the embedding table and computes dot-product with batched queries on-the-fly, avoiding the construction of a large intermediate tensor. By assigning each warp to process a contiguous tile of items, this operator fully exploits GPU parallelism and achieves coalesced memory access.

In recommendation systems, we found that even if we could get precise nearest neighbor search results, overall accuracy for retrieval may not be perfect. The reason is the dot-product over simplifies the retrieval model. Additionally, since the ANN index stores complete embedding tensors together with cluster-related tensors in memory, it becomes the bottleneck when candidate pool size as well as the model size increase. Base on these observations, we propose a INT8 quantized fused ANN search algorithm. By representing each embedding with 8-bit integer and leveraging GPU instructions such as dp4a(an instruction that capable of computing four multiplications and additions in a single instruction), we achieve much higher throughput and lower memory footprint by half. The quantization process occurs during SilverTorch model publish, involving computing the global min and max values among all the embedding values. Then the max and min values are scaled to fit within the range [-128, 127], representing the range that can be represented by each integer. Each embedding is then assigned an integer representation based on the range it falls into, using
the corresponding integer within [-128, 127]. We found that our INT8 quantized fused ANN search has limited quality loss but can improve the serving performance a lot. The performance headroom can fund serving more complex model to further scoring using neural network blocks. Our algorithm could effectively support searching arbitrary topk and number of probes. In practice, it could achieve searching with 64 probes of top 2048 items without any accuracy loss. Note that for index building during publish, we implement KMeans++
(
Arthur and Vassilvitskii 2006
)
to mitigate the problem of local minimal.

4.3.
ANN Search and Filtering Co-design

In service-based model serving systems, data are transferred between ANN search, feature filtering and remaining model inference components. There are services that provide a interface to support both ANN search and feature filtering(e.g., Elasticsearch or MongoDB), but data are stored with different formats for filtering and ANN search. In contrast, SilverTorch unifies the serving operators within PyTorch stack. All operators are running in the same runtime environment and different types of indexes are stored as tensors in GPU memory. This provides us the opportunities to jointly optimize the operators. In our Int8 ANN search operator, we support passing a bit mask output from bloom index. While PyTorch native supports Boolean as mask(8 bits per item), we use a bit mask with one bit for each item. It can both conserves memory and enhances performance by reducing the amount of data that need to be loaded from GPU’s global memory. Taking the bit mask, before executing the final step of calculating topk results, the ANN search operator applies the bloom bitmask to filter out unmatched items and then apply topk calculation. Such flexibility and co-design benefit from SilverTorch’s model-based index design.
In real use cases, a feature filtering query can be very complex that containing multiple logical expression of different matches. To support this, we parse the query and pre-compute each feature’s bloom result. We store each operator(e.g, And, OR, NOT) followed by the bloom result in an operation array. During serving, we go through this operation array sequentially, leveraging a stack to push temporary computation results and pop for logical computation between bloom results. A single batch queries could contain hundreds of sub-queries for feature filtering in total, thus having hundreds of bloom search computation. Additionally, the throughput of SilverTorch models was bounded by GPU memory. To solve these challenges, we propose feature filtering and ANN search by proposing a partial ANN search algorithm with bloom results, named as ANN and filtering co-designed index.
The co-designed index leverages the fact that only items within selected clusters need to apply the feature filtering. By calculating bloom results for the items in selected clusters only, we can return equivalent results while significantly reducing both computation and memory utilization for each request. For a case of 81 million items with 9000 clusters, each cluster has 9000 items on average. Bloom index is applied to only 2.3 million items(2.8% of the full items with 256 probes, achieving
30\times
saving of feature filtering compute and reduce
30\times
of scratch memory during serving.

5.
Extensibility

By leveraging the in-model design, SilverTorch supports serving more advanced recommendation models. This section explores two major extensions built on top of canonical retrieval models. We also discuss how SilverTorch further scales out to multi-GPUs.

5.1.
OverArch Scoring

In the two tower model design, user-item similarities are scored using the dot product. Unfortunately, it has no trainable parameters so that it over-simplifies the interactions. Without SilverTorch’s GPU-based approach, it is difficult to meet the latency requirement by adding these interaction layers. SilverTorch largely reduces inference cost so that retrieval can be extended to be more complex beyond nearest neighbor search. On top of ANN search and feature filtering query defined in
4
, a SilverTorch model comes with additional scoring layers(named as OverArch layers). The retrieval first execute the query and filter out K0 items(in the scale of O(10,000) to O(100,000)) from original candidate pool. Dot-product is still applied for efficient distance calculation inside the co-designed index. Second, a scoring layers that adopts neural network modules to rank these K0 user-item pairs and return as the final retrieval result. By incorporating the OverArch layer, user-item interactions are better learned by model weights. We found that by introducing the OverArch layers during inference gives us a better recall than improving the ANN search accuracy.

A OverArch layer can be defined as a Multi-layer Perception (MLP), or a multiple stacked self-attention layers to capture the correlation in order to understand user’s interest, with the capability of looking at items in an entire session. Recent study proposes more structured interaction layer using Mixture of logits (MoL)
(
Zhai et al. 2023
)

(
Ding and Zhai 2025
)
, which defines similarity between user and item as adaptive composition of elementary functions. Similar with ESR, the inputs for OverArch layers include the item embeddings and user embedding features and other cross-features. Benefit from SilverTorch’s caching design, item embeddings and cross-features can be directly extracted from GPU memory which are constructed during publish and loaded in predictor. SilverTorch supports arbitrary OverArch architectures that could improve model quality of retrieval through the full fidelity of training and serving consistency.

5.2.
Multi-Task Retrieval with Value Model

To learn multiple aspects of users, recommendation need to be capable of predicting multiple objectives. For example, in the context recommendation of social media, a user has different behaviors towards a single content, such as like, share, comment. Compared with tacking each task separately, multi-task learning aims to learn multi-tasks within a single model, while exploiting commonalities and differences across tasks. This way, it achieves better prediction accuracy due to knowledge sharing.
An straightforward approach to implement multi-task retrieval is to apply different user embeddings and item embeddings to represent each task and trains them together. However, based on the assumption that item features are learned to be the semantics representation of them so that they do not change across tasks. An empirical multi-tasks retrieval model defines that in user tower, different tasks share a lookup table and it applies different dense layers for each task to generate different user embeddings for different tasks. While the item embeddings are shared across tasks. At serving time, ANN search is built to handle multi-task user embedding queries and returns different item ids for different tasks. In CPU-based solutions, we need to replicate number of tasks copies of ANN indexes to multiple servers to avoid latency increase. Therefore, the cost increases linearly with number of tasks. In contrast, due to the parallelism nature of GPU, SilverTorch supports batching multiple requests from different tasks within one copy of index without latency regression. We found that SilverTorch’s GPU approach is more cost-efficient than CPU-based indexing services because it can batching not only different tasks but also different requests together for processing in parallel. After returning item lists for different tasks from ANN search and filtering, a merge operation is applied before the OverArch. Model designers are able to define customized merge operator such as an intersection of items or an union of items across tasks. The OverArch layer then predicts the scores for each task. To final aggregate scores across tasks, we adopt a aggregation function(named as Value Model) that supports user-define formulates to calculate the final scores for each item across tasks. The value model is defined as a JSON-like format that supports control flows of business logic. SilverTorch implements the in-model value model kernel can parse the input configuration format and then calculates the formulas on GPUs. Instead of only applying such business logic at later ranking stages, applying it earlier in retrieval stage make later stages(ESR, LSR) rank more accurate items. This functionality in retrieval stage proposes better interpretability and better consistency across the recommendation funnel.

5.3.
Scale Out

To deal with even larger candidate pool and models, SilverTorch could scale out to multiple GPUs. The ANN index and the bloom index are sharded across GPU cards, with each GPU processes a partition of items from candidate pool. The parameters of OverArch layer and Value Model are replicated on each GPUs during publish. During online serving, each GPU independently computes its local topk results based on local co-designed ANN search and filtering indexes. After that, the item embeddings are gathered into one of GPU ranks to calculate the final results through the OverArch layers and the Value Model. Since each GPU owns the OverArch layer and the Value Model, different batches of requests can be randomly routed to different GPUs in parallel. This avoids one of the GPU cards becoming bottleneck of the serving flow.

Since GPUs are expensive, the major factor to decide how many GPUs needed for serving is the memory. The memory size depends on multiple factors including the candidate pool size, the ANN index and the bloom index size and the size of the OverArch model weights. As the candidate pool size increases, the bloom index sizes grow as well as the ANN index size. ANN index size also relies on the quantization precision and the embedding dimensions of each model. SilverTorch’s quantized Int8 ANN index and the bloom index designs already saves a large amount of GPU memory. Finally, the complexity of OverArch layers determines the number of items a GPU could serve because consuming more GPU memory can hit the resource boundary of GPU. In our real deployment, there are cases that a single GPU could serve around 100 million items, as well as multiple GPUs serving billions items. For the user embedding table, we scale out to CPU parameter servers for distributed inference.

7.
Discussion and Future Work

SilverTorch is originally designed for large-scale recommendation with more than tens to hundreds of million items. However, SilverTorch provides benefits of unified development and serving. Instead of maintaining different services on multiple CPU servers, users can use single GPU server to support thousand QPS. If the traffic is smaller, the headroom can be considered for potential business grow. For extreme smaller scale case, users can switch to the CPU kernel with a configuration change.

8.
Conclusion

We present SilverTorch, a unified model-based system for serving large-scale recommendation on GPUs. SilverTorch democratizes recommendation model development using PyTorch, simplifying client-side logic and eliminating dependencies on standalone services. SilverTorch proposes a fused Int8 ANN index and introduces a bloom index feature filtering as model layers. We further propose a co-designing bloom index and ANN search algorithm. SilverTorch extends existing retrieval model by introducing OverArch and in-model value model, enhancing recall while keeps latency low. SilverTorch employs embedding cache to avoid calculating item embedding for ranking. Our experiments demonstrate SilverTorch can serve million items and scale to multiple GPUs. Compared to state-of-the-art systems, SilverTorch achieves
5.6\times
lower latency,
23.7\times
throughput improvement and is
13.35\times
more cost-efficient. We believe that SilverTorch represents an important step toward GPU-based serving for future recommendation models.
