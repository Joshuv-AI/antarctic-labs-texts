A Trace-based Approach for Code Safety Analysis
Hui Xu

Abstract
. Rust is a memory-safe programming language that disallows undefined behavior. Its safety guarantees have been extensively examined by the community through empirical studies, which has led to its remarkable success. However, unsafe code remains a critical concern in Rust. By reviewing Rust’s safety design and analyzing real-world Rust projects, this paper establishes a systematic framework for understanding unsafe code and undefined behavior, and summarizes the soundness criteria for Rust code. It further derives actionable guidance for achieving sound encapsulation.



1.
Introduction

This paper is based on Rust, a system programming language that emphasizes memory safety. Starting from the safety promise of Rust,
i.e.,
safe code cannot cause undefined behavior
(
safetypromise
)
, we first establish a main theorem about the relationship between unsafe code and undefined behavior.
Informally, undefined behavior originates exclusively from unsafe code and is solely determined by the safety constraints of that unsafe code.

The theorem is derived from an observation about unsafe code in Rust: all unsafe APIs must declare safety constraints that need to be satisfied to prevent undefined behavior. These constraints serve as sufficient conditions and are applicable to all usage scenarios.
The theorem enables a
trace-based approach
to safety encapsulation. This approach is analogous to taint analysis, where unsafe code within a function can be viewed as the taint source and the function exits as the sinks. Under this perspective, all propagations of undefined behavior risks introduced by unsafe code must not cross encapsulation boundaries.
By treating the safety constraint of a safe function as empty, we can derive a corollary that specifies how to achieve safety encapsulation for both safe and unsafe functions.
Informally, a function must ensure the safety constraints of its unsafe callees are satisfied if the safety constraint of itself can be satisfied.

We further extend the application of the theorem to structs, which consist of data fields and methods.
For a struct, the sinks (or safe boundaries) correspond to the exits of all its methods. Moreover, the methods of a struct are interrelated because they operate on the same instance and shared data. On one hand, dynamic methods (those with a
&self
or
&mut self
parameter) can only be executed after a constructor.
On the other hand, methods with a
&mut self
parameter may affect the safety encapsulation of other methods. Therefore, we derive the following rule for ensuring the encapsulation of a sound struct.
Informally, a struct must ensure that all its constructors and static methods satisfy the sound function encapsulation criterion; moreover, for each dynamic method with unsafe callees, the struct must guarantee that the safety constraints of those callees are satisfied by any combination of a constructor and the method, and that these constraints are not invalidated by other methods.

The remainder of this paper is organized as follows. We first introduce the notations used, followed by the formal definition and proof of the main theorem. We then discuss how to achieve sound encapsulation for both safe and unsafe functions, before extending the analysis to structs and modules. Finally, we present an actionable approach for applying the theory to audit the soundness of Rust crates.

3.
Main Theorem

In this section, we establish the main theorem, which characterizes the relationship between undefined behavior and unsafe code in Rust.

Theorem 1 (Main Theorem).

Let
P
be a well-typed Rust program. Then, undefined behavior can occur in
P
only if
P
contains unsafe code and
P
violates its associated safety constraints. Formally,

P\leadsto UB\quad\Rightarrow\quad(P\ni UC)\wedge(P\nvdash SC_{UC}),

where
UC
denotes a piece of unsafe code (typically an unsafe function call) contained in
P
, and
SC_{UC}
denotes the safety constraints of the unsafe code.

This theorem asserts that undefined behavior (UB) originates exclusively from unsafe code and is entirely determined by the safety constraints of the corresponding unsafe code.

To prove this theorem, we rely on the soundness criteria for both safe and unsafe code.
For simplicity, we assume that unsafe code consists solely of calls to unsafe functions.
This assumption does not restrict generality, as the same reasoning applies to other forms of unsafe operations, such as raw pointer dereferences or accesses to static mutable variables, which likewise possess well-defined safety constraints.

3.1.
Soundness Criterion of Safe Code

Rust’s safety promise is originally stated as follows
(
safetypromise
)
:

“For Rust, this (soundness) means well-typed programs cannot cause Undefined Behavior. This promise only extends to safe code however; for unsafe code, it is up to the programmer to uphold this contract.”

Assuming the compiler is sound, only well-typed code can pass type checking. Consequently, the safety promise can be formally expressed as follows:

Definition 0 (Safety Promise of Rust).

Safe code cannot cause undefined behavior, and only unsafe code may exhibit undefined behavior. Formally,

\forall P,\;P\notni UC\;\Rightarrow\;P\not\leadsto UB.

Building upon the safety promise, we formalize the soundness criterion for safe Rust code as follows.

Definition 0 (Soundness criterion of Safe Functions).

A safe function
f_{s}
is
sound
if and only if

\forall P,\;(\mathrm{Callee}(P)\ni f_{s}\;\wedge\;P\notni UC)\;\Rightarrow\;P\not\leadsto UB,

which can be simplified as

\forall P_{f_{s}},\;P_{f_{s}}\not\leadsto UB,

where
P_{f_{s}}
denotes a program that calls
f_{s}
and contains no unsafe code,
including any that may be introduced by other APIs with internal unsafe implementations.

3.2.
Soundness Criterion of Unsafe Code

Based on best practices observed in real-world Rust projects, particularly in the standard library, we find that unsafe functions are typically accompanied by well-documented safety requirements or constraints. These constraints exhibit two essential properties:

•

Pervasiveness:
Every unsafe function is associated with a set of safety constraints that must be satisfied to prevent undefined behavior. These constraints serve as sufficient conditions for safety.

•

Uniformity:
The safety constraints associated with a given function are consistent across all of its call sites.

Building upon these observations, we make the following formal assumption about unsafe functions and their safety constraints.

Assumption 1 (Properties of Safety Constraints).

\forall f_{u},\;\exists SC_{f_{u}}\;\mathrm{s.t.}\;\forall P_{f_{u}},\;P_{f_{u}}\vdash SC_{f_{u}}\;\Rightarrow\;P_{f_{u}}\not\leadsto UB,

where
SC_{f_{u}}
denotes the safety constraints of an unsafe function
f_{u}
, and
P_{f_{u}}
is a program that uses
f_{u}
and contains no other unsafe code, including any that may be introduced by other APIs with internal unsafe implementations.

Based on Assumption
1
, we can derive the following soundness criterion for unsafe functions:

Definition 0 (Soundness Criterion of Unsafe Functions).

An unsafe function
f_{u}
is sound if and only if

\forall P_{f_{u}},\;P_{f_{u}}\vdash SC_{f_{u}}\;\Rightarrow\;P_{f_{u}}\not\leadsto UB

With this criterion, we can now prove the correctness of Theorem
1
. Specifically, Definition
2
implies that
P\ni UC
is a necessary condition for undefined behavior, while Definition
4
implies that
P_{f_{u}}\nvdash SC_{f_{u}}
is also a necessary condition.

4.
Sound Function Encapsulation

From Theorem
1
, we can derive corollaries for achieving sound encapsulation of both safe and unsafe functions.

Corollary 1 (Safe Function Encapsulation).

A safe function
f_{s}
is sound if either it contains no unsafe code, or the safety constraints of all unsafe callees are satisfied. Formally,

\forall f^{\prime}_{u}\in\mathrm{UnsafeCallee}(f_{s}),\;f_{s}\vdash SC_{f^{\prime}_{u}}\;\Rightarrow\;\forall P_{f_{s}},\;P_{f_{s}}\not\leadsto UB,

where
\mathrm{UnsafeCallee}(f_{s})
denotes the set of unsafe functions called by
f_{s}
,
and
SC_{f_{u}}
denotes the safety constraints of
f_{u}
.

Corollary 2 (Unsafe Function Encapsulation).

An unsafe function
f_{u}
is sound if the safety constraints of all its unsafe callees are satisfied. Formally,

\forall f^{\prime}_{u}\in\mathrm{UnsafeCallee}(f_{u}),\;(F_{u}\cup SC_{f_{u}})\vdash SC_{f^{\prime}_{u}}\;\Rightarrow\;\forall P_{f_{u}}\vdash SC_{f_{u}},\;P_{f_{u}}\not\leadsto UB.

We can unify Corollary
1
and Corollary
2
by treating a safe function as having an empty constraint set. In this way, we obtain the following general corollary for function encapsulation.

Corollary 3 (Function Encapsulation).

A function
f
(safe or unsafe) is sound if the safety constraints of all its unsafe callees are satisfied. Formally,

\forall f_{u}\in\mathrm{UnsafeCallee}(f),\;(f\cup SC_{f})\vdash SC_{f_{u}}\;\Rightarrow\;\forall P_{f}\vdash SC_{f},\;P_{f}\not\leadsto UB

5.
Struct Soundness

This section extends the previous results to structs.

5.1.
Soundness Criteria of Structs

A struct may contain multiple fields and methods. The methods of a struct are interrelated: on one hand, dynamic methods (those with a
&self
or
&mut self
parameter) can only be executed after a constructor; on the other hand, methods with a
&mut self
parameter may affect the safety encapsulation of other methods.
Based on these observations, we derive the following criterion for the soundness of a struct.

Definition 0 (Soundness Criteria of Structs).

Let a struct be

\mathcal{S}=\{\mathcal{C},\mathcal{F},\mathcal{M},\textit{d}\},

where
\mathcal{C}
is the set of constructors (including literal constructors),
\mathcal{F}
is the set of static methods,
and
\mathcal{M}
is the set of dynamic methods (including trait methods and direct field access),
d
is the destructor. Then
\mathcal{S}
is
sound
if and only if:

(1)

\forall f\in\mathcal{C}\cup\mathcal{F},\;P_{f}\vdash SC_{f}\;\Rightarrow\;P_{f}\not\leadsto UB

(2)

\forall c\in\mathcal{C},\;m\in\mathcal{M\cup\textit{d}},\;P_{c,m}\vdash(SC_{c}\cup SC_{m})\;\Rightarrow\;P_{c,m}\not\leadsto UB

Note that constructors are treated similarly to other static methods because they do not require a
&self
or
&mut self
argument. The main difference is that a constructor’s execution is generally followed by a destructor. We do not need to consider the destructor separately because it is automatically added by the compiler and is safe. Although developers can implement the
Drop
trait with unsafe code, such unsafe code should be properly encapsulated within the
drop()
function, which is safe and has no safety constraint. We treat the destructor similarly to other dynamic methods because it also requires the
&mut self
argument.

5.2.
Sound Struct Encapsulation

We discuss the encapsulation of struct methods by distinguishing between static and dynamic methods. For static methods, we can directly apply the sound function encapsulation method specified in Corollary
3
.

Corollary 2 (Sound Static Method Encapsulation).

A static method
f\in\mathcal{C}\cup\mathcal{F}
is sound if the safety constraints of all its unsafe callees are satisfied. Formally,

\forall f_{u}\in\mathrm{UnsafeCallee}(f),\;(f\cup SC_{f})\vdash SC_{f_{u}}\;\Rightarrow\;\forall P_{f}\vdash SC_{f},\;P_{f}\not\leadsto UB

Corollary 3 (Sound Method Encapsulation).

A dynamic method
m\in\mathcal{M}\cup d
is sound only if, for any instance crated by constructor
c\in\mathcal{C}
, the safety constraints of
m
’s unsafe callees are satisfied. Formally,

\forall c\in\mathcal{C},\;\forall f_{u}\in\mathrm{UnsafeCallee}(m),\;(c\cup m\cup SC_{c}\cup SC_{m})\vdash SC_{f_{u}}\;\Leftarrow\;\forall P_{c,m}\vdash(SC_{c}\cup SC_{m}),\;P_{c,m}\not\leadsto UB,

where
P_{c,m}
denotes the program obtained by executing the constructor
c
followed by the method
m
,
and contains no other unsafe code;

SC_{c}
denotes the safety constraints of the constructor,

SC_{m}
denotes those of the method
m
,
and
SC_{f_{u}}
denotes the safety constraints of each unsafe callee
f_{u}
.

The above are necessary conditions for the soundness of the enclosing struct. To define a sufficient condition for sound struct encapsulation, we consider the influence of other methods that may mutate the state of the struct instance.

A method
m\in\mathcal{M}
is
disruptive
if it may break the safety invariants required by other methods. The set of broken invariants caused by
m
is denoted
BS_{m}
. If
m
is unsafe,
BS_{m}
should also account for the safety constraints of
m
,
i.e.,

BS_{m}=BS^{\prime}_{m}\setminus SC_{m},

where
BS^{\prime}_{m}
is the safety invariants being invalidated by
m
through modifying the instance fields.

A struct may contain several disruptive methods

\mathscr{M}=\{m_{1},\dots,m_{n}\}
, the total set of broken invariants is

BS_{\mathscr{M}}=\bigcup_{i=1}^{n}BS_{m_{i}}.

Based on the analysis above, we can derive a corollary for achieving sound struct encapsulation.

Corollary 4 (Sound Struct Encapsulation).

A struct is sound if

(1)

\forall f\in\mathcal{C}\cup\mathcal{F},\;\forall f_{u}\in\mathrm{UnsafeCallee}(f),\;(f\cup SC_{f})\vdash SC_{f_{u}}\;\Rightarrow\;\forall P_{f}\vdash SC_{f},\;P_{f}\not\leadsto UB

(2)

\displaystyle\forall c\in\mathcal{C}\wedge m\in\mathcal{M},\;\forall f_{u}\in\mathrm{UnsafeCallee}(m),\;(c\ \cup\ m\ \cup\ SC_{c}\ \cup\ SC_{m}\ \setminus\ BS_{\mathscr{M}})\vdash SC_{f_{u}}

\displaystyle\Rightarrow\;\forall P_{c,m}\vdash(SC_{c}\cup SC_{m}),\;P_{c,m}\not\leadsto UB

The second part of Corollary
4
states that, for all dynamic methods
m\in\mathcal{M}
, no matter which constructor
c\in\mathcal{C}
is used to create the instance, the safety constraints of
m
’s unsafe callees must be satisfied even after removing the broken invariants caused by all disruptive methods.

We can show that Corollary
4
provides a sufficient condition for struct soundness.
According to Definition
1
, a sound struct must satisfy two criteria.
The first criterion requires that all static methods be sound, which is ensured by the first part of Corollary
4
.
The second criterion is also fulfilled, as it directly follows from the second part of Corollary
4
.

5.3.
Considerations of Traits

This work treats traits as a set of methods. When a struct implements a trait, the trait’s methods are added to the struct, so the previous results still hold. In addition, some traits are unsafe and have their own safety constraints for implementation. We consider the soundness of such implementations to be a separate issue, independent of struct soundness.

6.
Module and Crate Soundness

This section further extends the previous results to modules and crates.

6.1.
Soundness Criteria of Modules

Module soundness can be classified into two levels based on visibility:
strong
and
weak
.
Strong soundness requires that all structs and functions within the module are sound.
Weak soundness requires that only the public APIs of the module are sound.

Definition 0 (Strong Module Soundness Criteria).

A module
\mathbb{M}
is strongly sound if and only if all its functions
\mathcal{F}
and structs
\mathcal{S}
, no matter public or private, are sound.

(1)

\forall f\in\mathcal{F},\;P_{f}\vdash SC_{f}\;\Rightarrow\;P_{f}\not\leadsto UB

(2)

\forall s\in\mathcal{S},\;P_{s}\vdash SC_{s}\;\Rightarrow\;P_{s}\not\leadsto UB,

where
P_{s}
is a program using the struct
s
and contains no other unsafe code except the struct’s own unsafe methods, whose safety constraints
SC_{s}
are satisfied by
P_{s}
.

Note that we do not need to consider interleavings among functions and structs,
even though they may share some static mutable variables.
These static variables are distinct from method fields:
accessing method fields is safe, whereas accessing static mutable variables is unsafe.
The safety constraints for accessing such static mutable variables are assumed to have been enforced by the corresponding functions and structs, so that these functions and structs are themselves sound. Therefore, as long as each individual function and struct of a module is sound, the entire module is considered sound.

Definition 0 (Weak Module Soundness Criteria).

A module
\mathbb{M}
is weakly (or publicly) sound if and only if all its public functions
\mathcal{F}_{p}
and public structures
\mathcal{S}_{p}
are sound. Formally,

(1)

\forall f\in\mathcal{F}_{p},\;P_{f}\vdash SC_{f}\;\Rightarrow\;P_{f}\not\leadsto UB

(2)

\forall s\in\mathcal{S}_{p},\;P_{s}\vdash SC_{s}\;\Rightarrow\;P_{s}\not\leadsto UB

6.2.
Sound Module Encapsulation

Since the soundness criteria of modules decouple the requirements for functions and structs separately, we can directly refer to Corollary
3
and Corollary
4
to achieve sound module encapsulation.

6.3.
Crate Soundness

In Rust, software is organized into crates, each of which may consist of multiple modules.
A crate is considered sound if all of its modules satisfy the soundness criteria, as there are no shared states across modules.

7.
Application

Building upon the soundness encapsulation corollaries for functions and structs, we can design a systematic approach to audit the soundness of Rust modules or crates.
This approach is based on the
unsafety propagation graph
(UPG), which tracks all function calls with unsafe callees, as well as each struct containing methods that invoke unsafe code.

Definition 0 (Unsafety Propagation Graph (UPG)).

A UPG
\mathcal{G(F,E,S(C,M,\textit{d}))}
is a directed graph that tracks the propagation of unsafe code through function calls and instance flows in a Rust module or crate, where:

•

\mathcal{F}
is the set of nodes representing functions and static methods.

•

\mathcal{E}
is a set of edges capturing all function calls involving unsafe callees.

•

\mathcal{S(C,M,\textit{d})}
is the set of struct with constructors
\mathcal{C}
, dynamic methods
\mathcal{M}
, and a destructor
d
. For each struct, at least one of these methods should contain unsafe callees.

Given a Rust crate, its unsafety propagation graph captures all essential encapsulation requirements necessary to ensure both function-level and structure-level soundness. In practice, such a graph can become very large, so it can be segmented into smaller subgraphs to facilitate auditing. Specifically, we identify three types of subgraphs:

•

Unsafe Node:
For every unsafe function or method, developers should explicitly specify its safety constraints. This specification is essential for soundness encapsulation and subsequent verification.

•

Function Call with Unsafe Callee:
This type includes both functions and static methods as callers. Each such call should satisfy Corollary
3
or the first part of Corollary
4
.

•

Struct:
Each struct may contain multiple methods that invoke unsafe callees. For each of these methods, we construct a subgraph encompassing all constructors and disruptive methods of the struct for auditing. All such subgraphs must satisfy the second part of Corollary
4
.

8.
Conclusion

This work introduces a trace-based approach for analyzing unsafe code and verifying soundness. The approach is grounded in a main theorem, which states that undefined behavior originates exclusively from unsafe code and is solely determined by the safety constraints of that code.
We have proved the correctness of the main theorem under assumptions regarding the properties of safety constraints.
Building on this theorem, we have derived soundness criteria for both functions and structs, along with guidance for achieving sound encapsulation.
