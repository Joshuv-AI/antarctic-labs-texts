Visualizing Privacy-Relevant Data Flows in Android Applications
1 st Mugdha Khedkar, 2 nd Michael Schlichtig, 3 rd Santhosh Mohan, 4 th Eric Bodden

Abstract
Android applications collecting data from users must protect it according to the current legal frameworks. Such data protection has become even more important since in 2018 the European Union rolled out the General Data Protection Regulation (GDPR). Since app developers are not legal experts, they find it difficult to integrate privacy-aware practices into source code development. Despite these legal obligations, developers have limited tool support to reason about data protection throughout their app development process. This paper explores the use of static program slicing and software visualization to analyze privacy-relevant data flows in Android apps. We introduce SliceViz , a web tool that analyzes an Android app by slicing all privacy-relevant data sources detected in the source code on the back-end. It then helps developers by visualizing these privacy-relevant program slices. We conducted a user study with 12 participants demonstrating that SliceViz effectively aids developers in identifying privacy-relevant properties in Android apps. Our findings indicate that program slicing can be employed to identify and reason about privacy-relevant data flows in Android applications. With further usability improvements, developers can be better equipped to handle privacy-sensitive information.



I
Introduction

Any software that reaches the European market has to adhere to the General Data Protection Regulation (GDPR)
[
1
]
, known as the
toughest privacy and security law in the world

[
2
]
.
Moreover, with the EU’s Cyber Resilience Act (CRA)
[
3
]
on the horizon, software developers will soon face the challenge of writing code that complies with stricter security and privacy standards.
These regulations extend to mobile applications that gather data from users in the EU.

The GDPR defines personal data as
any information relating to an identified or identifiable natural person, a data subject
, and imposes obligations on the access, storage and processing of such data. Under the GDPR, data protection violations can result in severe financial penalties
[
4
]
.
If these violations cause vulnerabilities and data leaks, additional fines may be levied under the CRA.
Companies thus must identify and secure security-critical data-processing code, and prioritize testing efforts accordingly.
The main challenge is identifying this sensitive code early in the development lifecycle.

The growing demand for privacy by design
[
5
]
, both by end users and by the GDPR, necessitates that app developers use state-of-the-art technical measures to protect their users’ privacy.
The legal description of the GDPR is very complex and lengthy and hence it can be difficult for app developers to understand.
Since they lack legal expertise, app developers may be left wondering which technical measures need to be taken for which categories of user input data.
In Android, merely including data-hungry third-party libraries may result in inadvertent data sharing
[
6
]
, highlighting the importance of careful consideration in app development.

Advocating for transparency, Article §13
[
7
]
of the GDPR mandates that the collection and processing of personal data be disclosed to the user through documents such as privacy policies. Therefore, all Android apps must provide a privacy policy which explains how apps collect, share, and process user data. However, these privacy policies are often long and vague, and may not always be authored by the app developers. Several studies
[
8
,
9
,
10
,
11
,
12
]
have consistently shown significant discrepancies between privacy policies and the actual source code, undermining their accuracy and misleading users.

To address these inaccuracies, Google recently launched the data safety section
[
13
]
, which shifts the responsibility of privacy-relevant reporting to app developers.
This necessitates the completion of a form, outlining how apps collect, share, and secure user data.
App developers also need to share if the app uses data protection measures such as encryption or on-demand data deletion.
Before being able to create a store listing for an Android app, developers must complete this form.
This manual process often results in inaccuracies in reporting
[
14
,
15
]
, providing users with a false sense of privacy.
To bridge the gap between reported and actual handling of privacy-relevant data, app developers need technical support.

To address this, this paper presents an approach that uses static analysis to evaluate privacy-relevant data in Android applications.
Static analysis checks the source code thoroughly before execution, covering all possible execution paths, offering the potential to eventually provide legally useful guarantees.
Since its introduction in the 1980s
[
16
,
17
]
, the static analysis technique of program slicing has been used to assist developers in tasks such as debugging, testing, finding bugs, and understanding the code.
Slicing systematically identifies and highlights all the statements that could be affected by a specific program location
[
18
]
.
This paper explores the use of static program slicing to identify parts of the source code affected by sources of privacy-relevant data.
Our hypothesis is that the resulting program slices can help developers understand how privacy-relevant data flows through the source code and determine which privacy-relevant methods are reachable along the way.
This, for instance, will allow developers to choose secure measures to protect privacy-relevant data.

The idea of tracking data flow from predefined sources is similar to taint analysis.
Yet, an important difference to taint analysis is that for analyzing privacy-relevant data one needs to explore
all
paths originating at the sources of personal data, and needs to understand the processing activities along those paths.
Without a predefined list of sinks, the analysis requires thorough examination of
all
code handling personal data
[
19
]
.

To achieve this, we introduce
SliceViz
, a web tool that analyzes an Android app by slicing all privacy-relevant data sources detected in the source code.
It then helps developers by visualizing these privacy-relevant program slices in both Jimple (a Java intermediate representation
[
20
]
), and Java.

Additionally, we conduct a user study with 12 participants to evaluate how effectively SliceViz assists developers in understanding data protection in Android apps.

The user study reveals that SliceViz effectively aids identifying and observing privacy-relevant properties in Android apps.
Additionally, developers feel better supported by the Java program slices than Jimple, as they are more concise and align with the source code.
We make all artifacts available at
https://zenodo.org/records/15059372
.

To summarize, this work makes the following contributions:

•

We present SliceViz, a web tool that statically slices an Android app at the back-end, and assists developers by visualizing the privacy-relevant program slices.

•

With a user study on 12 participants, we show that SliceViz aids developers in identifying and observing privacy-relevant properties in Android apps.

II
Problem Statement

We next use a motivating example to define and explain our problem statement.

II-A

Motivating Example

Alice, a Java programmer unfamiliar with legal privacy frameworks, needs to create a Google Play Store
[
21
]
listing for her company’s app. To accomplish this task, she must complete the data safety form on Play Console
[
22
]
.
This step is mandatory for creating the store listing.

Yet, Alice has no prior knowledge regarding privacy or GDPR requirements. She thus consults Play Console Help
[
23
]
to understand how to complete the form, and learns that she needs to also report data collected by the app but sent directly to analytics engines.
Despite knowing that the app uses Google Analytics
[
24
]
, she struggles to identify which specific analytics APIs collect which data from the app code.
The app’s privacy policy is outdated, offering little to no guidance.

Google rejects her form request, and insists on getting more explanations about data collection and sharing.
Alice then consults colleagues, but they struggle to understand the complicated terminology used in Google’s guide
[
25
]
.
After days of manual effort, Alice finally completes the data safety form and uploads the app on the Play Store.
Yet, she still has no way to make sure that the data she entered is actually correct, that it corresponds fully to the app’s implementation.

Alice’s uncertainty worries Bob, the newly appointed Data Protection Officer (DPO)
[
26
]
, who knows about the severe fines imposed by the GDPR and CRA.
Bob initiates a data protection impact assessment (DPIA)
[
27
]
to comply with Article §35
[
28
]
of the GDPR.
This process would require Alice and Bob to use the sample DPIA template
[
29
]
and address questions regarding data collection, processing, storage, sharing, deletion, and pseudonymization.
With no tool support to answer such specific questions, they are forced to manually sift through extensive lines of code to find answers.

Despite Alice’s expertise as a programmer, the codebase might be too large for her to manually locate the necessary information. She may need to randomly sample the source code and check it manually.
However, Bob might doubt whether the sampled code sections include all sections needed to comprehensively answer the DPIA questions.
This could result in lengthy discussions with the legal team, during which Alice would need to explain complex technical concepts to non-technical stakeholders.
Consequently, completing the DPIA could require weeks of manual effort, particularly for start-ups that have not yet hired a DPO.

As part of a separate study, we conducted interviews with DPOs and privacy experts, which confirmed that these challenges are widespread.
One DPO highlighted the disconnect between legal and technical teams:
“Ideally, developers and legal teams should collaborate and conduct a DPIA before starting processing activities.
But as my professional experience is concerned, that is the biggest void in the market.
There is no communication between developers and lawyers—they are in two completely different worlds.
Privacy by design requires developers to consider legal principles, but this rarely happens.”

A privacy researcher further emphasized the gap:

“According to GDPR, DPOs should maintain the record of processing activities
[
30
]
, filled out after talking to developers.
The legal team drafting the DPIA needs input from developers, but developers cannot provide legal answers.
There has to be some common ground, which doesn’t exist.”

II-B

Research Problem

This example identifies critical challenges in streamlining the process of app development and privacy compliance:

1. App developers need to spend considerable time to understand how collected data must be protected according to the legal frameworks.

Article §5
[
31
]
of the GDPR highlights the importance of data minimization, which means collecting only the personal data necessary for specific purposes.
Once personal data is collected, the GDPR requires app developers to implement technical and organizational measures to protect it.
These measures include effectively disguising personal data using a
pseudonymization
function. Pseudonymization aims to protect personal data by replacing parts of it with unique, non-identifying
pseudonyms
.
It starts with a single input (personal data) and results in a pair of outputs (pseudonym, additional information) that together can reconstruct personal data
[
32
]
.
Hence, pseudonyms cannot be mapped back to personal data of the data subject without the use of this additional information. Even though pseudonymized data still qualifies as personal data, pseudonymization techniques mitigate data protection risks.
By pseudonymizing personal data, organizations may continue to use the data for their purposes while reducing the risk of severe consequences in case of a privacy breach
[
33
]
.

Iwaya et al.
[
34
]
conducted an interview-based study with 30 practitioners from 29 companies of nine countries and backgrounds to understand software practitioners’ perspectives and mindset regarding privacy.
One significant finding was the increasing awareness among software practitioners regarding privacy issues, although they remain mostly unaware of existing standards related to privacy engineering
[
35
]
.
Franke et al.
[
36
]
surveyed 56 open-source developers to understand their experiences of GDPR.
Their observations highlight the need for tools that support data privacy regulation implementation and compliance in open-source software.

Nonetheless, app developers aiming to comply with the GDPR need to answer pivotal questions: Which personal data is collected by the app? Does this data need to be collected? Which data is derived from the collected personal data? Are technical measures taken to ensure data protection? Are these measures present in all code execution paths?
Conducting such a comprehensive assessment could pose an additional burden for developers, particularly those whose primary expertise does not lie within the domain of security and privacy.

While the GDPR developer’s guide
[
37
]
outlines best practices for data protection, ensuring the practical implementation of these best practices predominantly remains a manual effort
[
34
]
.
This raises the concern: Will developers be required to manually oversee data protection requirements while developing and managing large code bases?

Goal 1:
Guide app developers in
automatically identifying personal data sources and assessing protection requirements
.

2. App developers lack tool support to accurately report privacy-relevant information.

Article §13
[
7
]
of the GDPR mandates that personal data collection and processing be disclosed through documents such as privacy policies.
However, these policies may not be written by the app developers and hence may not align with the source code
[
8
,
9
,
10
,
11
,
12
]
.
In early 2022, Google Play launched the data safety section
[
13
]
, which requires
app developers
to share how apps collect, share, and secure users’ data.

However, a study by Mozilla
[
38
]
has revealed discrepancies between the information reported in data safety sections and privacy policies of Android apps.
Khandelwal et al.
[
14
]
monitor the evolution of the data safety section and highlight underreporting, overreporting and inconsistencies in data practices.
Their study highlights the challenges encountered by developers in completing the data safety section, particularly in understanding the data collected from third-party libraries, amidst the frequent changes in Google’s data safety policies.

A recent experiment by Khedkar et al.
[
15
]
has revealed discrepancies between the data collection reported in data safety sections and the source code of the app.
Thus, it appears that neither documentation provides a precise summary of the data collected and processed by an Android app.
Disclosing privacy-relevant information through such documents may require significant manual effort from app developers such as Alice, resulting in inaccurate documentation.

Goal 2:
Support app developers in
identifying and visualizing high-risk sections of the source code
to facilitate the generation of privacy-relevant reporting documents.

II-C

Research Question

To achieve the two goals discussed above, we aim to answer the research question:
How effectively does the combination of static program slicing and source code visualization help developers understand data protection in Android apps?

Alice had to randomly sample the source code, since it was too large to be examined manually.
Access to smaller, more manageable privacy-relevant program slices could now potentially enhance her understanding of the source code.
We will investigate how visualizing these slices can facilitate collaboration between Alice and Bob for simplifying DPIAs.

III
Related Work

We next discuss existing research on this topic.

Program slicing
. Jicer
[
39
]
is the only available static slicer for Android apps, which uses Soot
[
20
]
’s DotGraph API
[
40
]
to generate static graphs in SVG format.
However, these graphs do not scale well and lack interactivity.
Xu et al.’s survey
[
41
]
provides a broad overview of slicing techniques and challenges.
In 2007, Sridharan et al.
[
18
]
proposed thin slicing, which excludes control dependencies and focuses only on
producer statements
, which compute and copy the value returned by the slicing criterion.
Their approach was based on WALA
[
42
]
. To the best of our knowledge, our approach is the first to use static program slicing to bridge the gap between technical and legal aspects of Android data protection.

Assessment of data protection requirements
. PTPDroid
[
12
]
uses the taint analysis tool FlowDroid
[
43
]
to study the reachability of third party libraries and compares it with the privacy policy section of
data sharing with third parties
.
Similarly, ATPChecker
[
44
]
uses FlowDroid to automatically identify whether the usage of in-app third-party libraries complies with privacy-relevant regulations. PTPDroid and ATPChecker focus on data sharing and lack examination of data processing.
In contrast, our approach aims to conduct a more holistic privacy analysis by highlighting where personal data is disguised and processed.
Tang and Østvold
[
45
]
describe an automatic software analysis technique that presents the results as a graph of privacy flows and operations.
Their analysis aims to assist app developers and DPOs in evaluating privacy compliance and simplifying DPIAs.
While our approach has similar objectives, we intend to use static program slicing and further conduct a risk-based assessment of collected data.

Data safety section
. Researchers have studied Android’s privacy labels since Google Play
[
13
]
introduced the data safety section.
A Mozilla study
[
38
]
graded popular apps based on discrepancies between data safety sections and privacy policies.
Khandelwal et al.
[
14
]
noted underreporting, overreporting, and inconsistencies in data practices, analyzing developer interactions using snapshot data without source code analysis.
In contrast, we aim to analyze source code to help developers report information accurately.

In 2022, Google introduced Checks
[
46
]
, a paid service that assists app developers in completing the data safety section.
However, its cost could hinder many app developers from using its services.
An open source alternative to this is Matcha
[
47
]
, a JetBrain’s plugin aiding developers in creating accurate Google play data safety labels.
Matcha analyzes the source code and suggests labels to the developers, who can then annotate the source code.
Unlike Matcha, our approach does not need developers to annotate their source code and extends beyond data safety sections to help developers identify privacy-relevant data in the source code.

A recent experiment conducted by Khedkar et al.
[
15
]
has revealed discrepancies between the data collection reported in data safety sections and the source code of the app.
Their approach introduces a prototype to statically detect and label the privacy-relevant data collected by the source code, user interface screens, and permissions.
Their findings highlight the need for improved tool support to aid Android developers in comprehensively understanding privacy implications in their source code—a gap that we aim to address with SliceViz.

IV-B

Slicing Engine

Slicing Engine (
Ⓑ
in Figure
1
) is the back-end of SliceViz, responsible for performing static analysis on APKs and generating dependence graphs.
It requires two elements, namely an
identifier dataset
(
B.1
) to match system API calls with privacy labels, and a collection of
privacy-relevant libraries
package names to identify privacy-relevant methods (
B.2
).
The Slicing Engine employs both
B.1
and
B.2
to identify privacy-relevant sources, and then slices the Android app from these privacy-relevant sources. It is implemented as Java code and seeks to answer two primary questions that developers might have:

1.

Which data collected by the app should be considered and reported as high-risk?

2.

How does this data flow through the source code, and does it flow into data processing methods (eg. analytics, advertisement, authorization methods)?

B.1

Identifier Dataset.
To answer the first question, the Slicing Engine uses a manually annotated
identifier dataset
introduced by Khedkar et al.
[
15
]
, which labels data sources based on a risk-based definition of privacy-relevant data.
Personal data that can identify an individual or a device without the use of any additional information is categorized as
risk 1
, while data requiring additional information for identification is classified as
risk 2
.
The dataset categories align with Google’s data safety section to simplify form completion.

B.2

Privacy-Relevant Libraries.
The Slicing Engine statically matches the system API calls against a list of packages of privacy-relevant third-party libraries and APIs.
Note that the Slicing Engine is designed as a proactive privacy by design
[
5
]
measure, integrating into the app developer’s workflow to analyze privacy-relevant third party libraries and API calls early in the development process.
It operates before name mangling or obfuscation
[
51
,
52
]
, which are typically applied later when packaging the app for deployment.

We consulted the AppBrain statistics
[
53
]
and related literature
[
54
,
55
,
56
]
to select the most commonly used libraries for pseudonymization, analytics, advertisements, authentication, network, input/output, email, image processing, data serialization and location. According to GDPR, robust pseudonymization involves creating pseudonymns that cannot be easily re-identified and reproduced by third parties
[
32
]
. Hashing, considered a weak technique for pseudonymization, can be reversed with a limited dictionary
[
57
]
. Grading pseudonymization functions based on these criteria can help app developers identify areas requiring additional data protection measures.

After the slicing process is complete, the Slicing Engine generates text files with privacy-relevant program slices and transfers them to Visualizer for further analysis.

Instead of high-effort random sampling, Alice (cf. Section
II
) can now use SliceViz to generate program slices originating from all privacy-relevant data sources, and visualize and explain these slices to Bob.
As a result, Alice and Bob can complete the DPIA with reduced manual labor.

Early experiments – SliceViz.

The first implementation of SliceViz composed only of a simple UI, the Slicing Engine (
Ⓑ
) and the Jimple view.
For an initial assessment of the viability of our approach we conducted two pilot studies (involving 10 and 6 participants, respectively) to evaluate the usability of SliceViz.
While participants found the visualized program slices to be more efficient than manual code inspection, those unfamiliar with Jimple struggled to interpret the graphs generated by SliceViz.
Additionally, visualizations with more than 50 nodes became challenging to interpret, due to increased cognitive load, as proven by Yoghourdjian et al.
[
60
]
.
Since Jimple breaks down each Java statement into multiple statements, the Jimple view resulted in larger slices.

To address this, we implemented an experimental
Java view
that relies on the back-end to simplify and transform the data.
The Slicing Engine’s transformers omit Jimple-specific nodes, reducing the size and complexity of the application dependence graph (ADG) while preserving essential privacy-relevant information.
Developers can now choose which view,
Jimple
or
Java
, they use (cf. Figure
4
).
Moreover, the UI provides three key
customization options
(cf. Figure
4
) to manage graph complexity and reduce visual overload:

1.

Toggle inclusion of control dependencies in the graph.

2.

Set a maximum analysis time limit for generating slices.

3.

Specify a maximum number of nodes allowed in a graph.

V-B

Slicing Engine

Slicing Engine (
Ⓑ
) is the back-end of SliceViz, responsible for performing static analysis on APKs and generating dependence graphs.

The Slicing Engine is a command-line tool implemented in Java.
It is built on top of Jicer
[
39
]
, a static program slicer that works with Jimple, an intermediate representation of Java code.
Jicer is tailored to address Android-specific challenges, such as the absence of a main method, extensive use of callbacks and inter-component communication
[
39
]
.
The Slicing Engine uses Jicer’s functionality to statically construct an application dependence graph (ADG) from the APK, preserving control and data dependencies in the source code
[
61
]
.
It introduces its own algorithm to match method signatures from the ADG with the
identifier dataset
(
B.1
), labeling privacy-relevant data sources in the code.
Once labeled, the Slicing Engine uses Jicer’s slicing component to perform forward slicing on the ADG, starting from the identified privacy-relevant data sources.
This process yields forward slices representing the code components reachable from all labeled privacy-relevant data sources.
Finally, the Slicing Engine adds its own functionality to automatically label pseudonymization methods and other privacy-relevant methods within the sliced ADG using a privacy-relevant libraries dataset (
B.2
).
It stores the sliced ADGs as text files, facilitating further analysis.

When the
Java view
is enabled through the user interface (cf. Figure
4
), SliceViz triggers the Slicing Engine to execute custom transformations on the sliced ADGs.
These transformations remove intermediate Jimple-specific nodes, reduce graph size and complexity, and convert Jimple nodes into more readable, Java-like representations to improve comprehension for developers.
The transformed graphs present semantically correct Java-like statements (cf. Figure
6
) instead of raw Jimple statements (cf. Figure
5
), enabling developers to work effectively without needing prior Jimple knowledge.

Currently, the Slicing Engine transforms key Jimple statements into Java-like representations, including
invoke
,
assignment
,
if
,
return
,
binary expressions
,
invoke expressions
, and
array variables
.
These statements are commonly involved in data flows and their processing, and they tend to be more complex to interpret in Jimple compared to Java.
Moreover, recent research
[
62
]
reveals that
function calls
,
expression statements
,
if
and
decl statements
implement privacy behaviors in Android apps.
We are actively working on expanding the mapping between Jimple and Java to improve the
Java view
.

Early experiments – Slicing Engine.
At the initial assessment of SliceViz, we also tested the Slicing Engine on 36 applications: 5 apps from DroidBench
[
63
]
, 25 apps from TaintBench
[
48
]
, and 6 real-world Android apps available on Google Play Store.
While DroidBench contains hand-crafted, small micro benchmark apps, the TaintBench suite consists of real-world malware apps, which are similar with respect to size and features to apps downloadable from Google Play Store.
We observed that program slices were getting too large for manual evaluation.
We investigated adapting further changes in the program slicing and compared the sizes of slices generated by default and the slices generated when excluding control dependencies while building the ADG.

We observed that excluding control dependencies significantly reduced slice sizes.
We thus added a
customization option
in the user interface (cf. Figure
4
), that allows toggling inclusion of control dependencies in the graph.

V-C

Correctness Check

To ensure the correctness of SliceViz’s results, we first conducted sanity checks by manually verifying its output.
The experiments were performed on an Ubuntu 20.04.2 machine with an Intel(R) Core i7-10850H processor (6 cores).

We tested SliceViz on 32 applications from TaintBench
[
48
]
, verifying the presence of detected risk sources against the ground truth.
We chose all (32) apps from the TaintBench suite that had code size less than 60,000 lines. The sanity check revealed that all the sources detected by SliceViz matched with the sources present in the TaintBench ground truth.
On average, SliceViz processed each app in 41.96 seconds.

VI-B

Results

In this section, we present the results of the user study conducted with 12 participants, who we refer to as P01–P12.

We summarize the results below:

Participant Experience.
At the beginning of the study, participants self-reported familiarity with Android app development (median 1/5), Java (median 3/5), Jimple (median 2/5), static analysis tools (median 2/5), graph visualization (median 3/5), data privacy (median 3/5), and GDPR (median 3/5) (cf. Table

Participants have a median of approximately 1.5 years of experience in Java development.

RQ1. To what extent does SliceViz help developers understand data protection in Android apps?

Participants first worked with a DroidBench app, which had one privacy-relevant program slice with 10 nodes.
Despite limited knowledge of GDPR, 10 participants successfully identified the privacy risks in the app and accurately determined which data required GDPR protection.
Apart from P04 who over-reported the risky sources, all the other participants were able to analyze the slices, interpret the graphs, and understand the data flow, correctly identifying privacy-relevant properties.

The TaintBench app given for Task 2 had seven program slices, with a maximum size of 20 nodes.
Of the 11 participants, 10 accurately identified all the privacy-relevant information in the given app.
P03 correctly identified 50% of the privacy-relevant details, but failed to report risk 4 slices, likely due to customizing SliceViz to only report risk 1 data sources.
Interestingly, P04 (who struggled to understand privacy risks and data flow in the first task) could successfully identify and report the privacy-relevant details in this app.

The first two tasks included questions about the dashboard.

VII
Limitations and Threats to Validity

We next discuss the limitations of our approach.

Slicing Engine.
The
identifier dataset
may miss out on some libraries.
However, Khedkar et al.
[
15
]
ensure a comprehensive evaluation by including the most used third-party libraries from different categories.
The degree of identifiability relies on human subjectivity and it may vary with different domains and compliance regimes.
Since our approach focuses on GDPR, we can use the
identifier dataset
directly.
The Slicing Engine matches the method signatures in the ADG with the labeled methods present in the
identifier dataset
.
Since we use keyword matching to detect the presence of data sources including those from some third-party libraries, the analysis cannot handle code obfuscation in cases where the obfuscation also renames calls to these third-party APIs.
However, as mentioned in Section
V
, the Slicing Engine is designed to operate as a proactive privacy measure before name mangling or obfuscation measures are applied.
The Java view can be improved by expanding the mapping between Jimple and Java, comprehensively covering the app source code.

Usability Assessment.
To investigate possible usability implications of SliceViz, we conducted two pilot studies and one user study.
Since it is challenging to recruit developers for a user study and students are considered reasonable proxies for software developers
[
67
,
68
,
69
]
, our user study used students as participants.
We conducted the user study in a controlled environment (12 participants, 1 hour study duration) rather than in a development setting.
In practice, users would have more time to investigate more advanced apps.
It would, however, be interesting to conduct a larger quantitative evaluation in real-life conditions.

VIII
Conclusion

In this paper, we have explored how static program slicing can be used to identify parts of the source code affected by sources of privacy-relevant data.

To achieve this, we have introduced
SliceViz
, a web tool that analyzes an Android app by slicing all privacy-relevant data sources detected in the source code.
It then helps developers by visualizing these privacy-relevant program slices.

With a user study conducted on 12 participants, we have shown that SliceViz effectively assists developers with prior development experience in identifying and observing privacy-relevant properties in Android apps.

Our findings suggest that program slicing can be employed to reason about privacy-relevant data flows in Android applications.
With further usability improvements, developers can be better equipped to handle privacy-sensitive information.
