Adaptable TeaStore
Simon Bliudze, Giuseppe De Palma, Saverio Giallorenzo, Ivan Lanese, Gianluigi Zavattaro, Brice Arléon Zemtsop Ndadji

Abstract




1
Introduction

In modern Cloud software architectures, the ability to configure and adapt
services is essential to face the diverse set of known and unknown events that
can occur in a distributed system. In this context, the challenge to design a
system that can adapt and remain operational under different conditions is
critical.

Modern, state-of-the-art Cloud architectures mainly follow the
microservices
[
1
]
or the serverless
[
2
]
styles.
In the literature, TeaStore
[
3
]
is a well-known microservice
reference architecture that provides a comprehensive architecture with
components whose different performance characteristics and degrees of freedom
regarding deployment and configuration offer a valuable benchmarking framework
for modelling and resource management techniques. However, TeaStore’s original
setup does not directly support the level of configurability to capture the
diverse events and operational scenarios that can arise in real-world
deployments.

To address this limitation, we propose a variant of TeaStore that introduces the
concept of mandatory and optional services, along with the potential integration
of third-party providers of critical services. In this variant, core services
such as the WebUI, Image Provider, and Persistence are deemed mandatory,
ensuring the basic functionality of the application, while optional services,
including the Recommender and Auth, allow the architecture to provide its full
range of features.

We present the architectural design and the range of possible configurations for
the adaptable TeaStore variant.

2
TeaStore

The TeaStore is a well-known reference architecture microservices systems
literature. It involves 5 different services: WebUI, Auth, Persistence, Image
Provider, and Recommender.

Figure 1:
TeaStore Architecture. Adapted from Teastore paper

In
Figure

1
, we show an overview of the TeaStore architecture. The
WebUI service is the entry point for the user, and it is the main service that
interacts with all other services. The Persistence service is the layer on top
of the database. It is used by the WebUI to retrieve and store data and by the
Auth service to retrieve user data, which is then passed to the WebUI. On
startup, the Persistence service populates the database with data. The Image
provider and Recommender both connect to a provided interface at the Persistence
service. However, this is only necessary on startup (dashed lines). The Image
provider must generate an image for each product, whereas the Recommender needs
the current order history as training data. Once running, only the
Authentication and the WebUI access, modify, and create data using the
Persistence.

WebUI

The WebUI service manages the user interface and contacts all the other services
to retrieve and display data. It compiles and serves Java Server Pages (JSPs)
with the categories, products, recommendations, and images. It performs
preliminary validation on user inputs before sending them to the Persistence
service.

Image Provider

The Image Provider handles the serving and resizing of images in various sizes
for the WebUI. It uses a cache to optimize performance, resizing and caching
images if necessary. The system employs a least-frequently-used caching strategy
to reduce resource demand, and response time depends on whether an image is
already cached or needs resizing.

Authentication

This service verifies user login and session data, using BCrypt for login
verification and SHA-512 hashes for session validation. Session data includes
shopping cart content, login status, and order history. The performance depends
on the volume of session data. The service remains stateless since all session
data is passed to the client.

Recommender

The Recommender service provides product recommendations based on items other
customers bought, on the products in a user’s current shopping cart, and on the
product the user is viewing at the time. It maintains coherence between
different instances by sharing training data (additional Recommender instances
query existing instances for their training data-set). Several recommendation
algorithms can be used, including two ‘Slope One’ variants and an order-based
nearest-neighbourhood method, with different algorithms optimising for either
memory or CPU performance. There is a fallback algorithm based on overall item
popularity.

Persistence

The Persistence service manages access and caching for the store’s relational
database, which stores data on products, categories, purchases, and users. There
is an internal cache to improve scalability and reduce the load on the database.
The cache is kept coherent across multiple Persistence service instances. All
data inside the database itself is generated at the first start of the initial
persistence instance.

3
Adaptable Teastore

The original TeaStore architecture is static, lacking scenarios where the
structure of the system needs to change due to failures and variations of
environmental conditions or user requirements. To enhance the case study in this
direction, we extend it with optional services and external dependencies that
the user deploying system, henceforth called the
company
, has no control
over. We describe this adaptable version of the TeaStore below, depicting its
components in
Figure

2
. The main changes to the original
architecture include:

1.

Outsourceable Services:
The Image Provider, Persistence, and
Authentication (Auth) services can be considered as offered either by an
external provider, simulating a realistic scenario with services such as
Database-as-a-Service (DaaS) platforms (e.g., Firebase, Supabase), or as a
separate set of services that might be shared among multiple applications
within the same company.

2.

External Services:
By external services we mean
functionalities that are not available in the architecture. For instance, we
could introduce Single Sign-On (SSO) authentication logins as an external
dependency for the Auth service. This reflects a common scenario in many
applications that integrate third-party login options (e.g. Google,
Facebook).

3.

Local Cache Services:
With the application separated in local
services and provider’ services, the system can be run without external
dependencies by making use of 2 new local services: a local Image Provider
with placeholder images and a local Persistence service with static data.
These services can switch into a local cache mode when the external services
are available.

4.

Mandatory and Optional Services:
The WebUI, Image Provider,
and Persistence services are considered
mandatory
for the system to
operate. For the latter two, either the local version or the external
provider can be used. The Recommender service can be disabled, which removes
the feature from the system. The Auth service is needed for user
authentication to enable user-specific features, but if not available the
application can still be used with anonymous users to browse products.

5.

Service Flavors:
Services can have different
flavors

or versions, offering varying levels of functionality. For instance:

•

The Image Provider service can be configured as a lightweight
version that does not provide image resizing, or a full version with
resizing capabilities.

•

The Recommender service can be disabled, run in a low-power mode
(with just the fallback algorithm), or be fully enabled.

3.1
Configuration Levels

Discussion of the different configurations. Discussion on low-power and
full-mode configurations flavours. Analysis of configurations with external
service providers.

3 configuration levels:

•

Barebone configuration: only mandatory services are running to offer
minimum functionality for anonymous users (WebUI, Local Static Images, Local
Static DB)

•

Barebone configuration + Recommender service (in low-power mode)

•

Persistence, Auth, Image Provider possibly deployed in another region
(these services could be used in other applications from the same company
besides TeaStore). As an alternative, these services can be rented from an
external provider (e.g. Supabase). In this configuration the database
(persistence), a storage service for images with resizing capabilities and the
Auth service are available. The Local Cache Img and Local Cache DB are used in
place of Local Static DB and Local Static Images. The recommender can be used in
Full mode.

If other provider is down and the Auth system is not available, the recommender
cannot be used in Full mode because of missing user data.

Up to discussion: can the other provider be adaptable (we can ask to change
flavours) or it can change flavours indipendently and we have to adapt to it? Or
there are no flavours in other provider and we adapt based on metrics (how much
time it takes to resize images, costs, latency etc).

4
Scenarios

We now move to present a set of scenarios designed to evaluate a system’s
ability to adapt across various operational challenges. Each scenario tests
specific capabilities of the models, techniques, and tools under consideration: from handling
infrastructure failures to responding to security threats and managing resource
constraints. The scenarios cover different basic aspects. They can be combined to test the capability for the adaptation to sophisticated multi-cause events.

4.1
Database Unavailable

The system is deployed in a barebone configuration with only local services. The
queries to the local database start to timeout and the WebUI becomes
unresponsive. The WebUI adapts to avoid querying the database and show a
maintenance message while the system restarts the database service. Once the
database is back online the WebUI resumes normal operation.

4.2
Cyberattack on External Services

The system is deployed in the full configuration with an external provider for
the Image Provider, Auth, and Database services. The external provider detects
an attack (e.g. a privilege escalation) and has to take down and restart the
three services. In response to the unavailability of external (instances of
outsourced) services due to a security threat, the system enables the Local
Static Images and the Local Static DB services. The WebUI adapts by disabling
the authentication functionality, such as new logins and registrations, and
starts using the local services. At some point, the newly deployed external
services are back online and the system returns to the full configuration, as
before the attack.

4.3
Cloud Provider Outage

The system is deployed in the full configuration. The external provider services
go offline due to an outage (e.g. power supply failure). The WebUI requests to these services start
to timeout. The system adapts by first switching the configuration to barebone,
to be able to provide the essential functionalities, while the outsourced
services are being redeployed in a different provider. After the redeployed
services are online, the system switches back to the full configuration.

As an example, the system is up and running with an external Image Provider.
WebUI can access the external Image Provider to fetch images via the
Local Cache IMG provider. A user accesses a product page and the WebUI
tries to fetch the image from the local cache service. The local cache service
does not have the image, therefore it tries to fetch the image from the external Image Provider. The Local Cache IMG Provider does not receive a response from the Image Provider and the request times out. The system adapts the configuration by switching the Local Cache Service to the Local Static Images service. Meanwhile, the system deploys the external services to a different provider and switches back to the full configuration when they are online.

4.4
Sudden Traffic Increase

4.4.1
Benign Traffic Increase

Incoming traffic towards the WebUI increases significantly due to a genuine
increase in users. Since the traffic increase is benign, the system must adapt
by scaling out the services to handle the increased load or taking other measures to the same purpose (e.g. switch to low-power versions of the services).

As an example, on a system with the Recommender service in full mode, the
Recommender service is under heavy load due to the sudden increase in user
requests. The service quality degrades, and the response time increases
significantly (defined by a user-specified QoS threshold). The system adapts the
configuration by switching the Recommender service to low-power mode, which
uses the fallback algorithm to provide recommendations based on item popularity.

4.4.2
Malicious Traffic Increase

Incoming traffic towards the WebUI increases significantly due to a DDoS attack.
The adaptations include deploying circuit breakers between services to prevent
cascading failures, switch Auth service to a more restrictive mode with additional
verification, the Recommender switching to low-power mode, and Local Cache
services activating to reduce external service dependencies.

4.4.3
Conditional Handling of Traffic Increase

Incoming traffic towards WebUI increases significantly. However, no explicit
information is available about the reason for that: the increase can be either
due to a genuine increase in the number of users or to a DDoS attack. The
system must evaluate the situation and adapt accordingly. Notice that the
decision and the adaptation need not be a mutually exclusive choice between the
benign and malicious scenarios above, it can be a combination of the two.

4.5
DevOps Requirements Change

The system should be able to adapt to reconfiguration requests from DevOps. For
instance, DevOps can decide to scale out a service or switch between different
versions, thus increasing/decreasing the amount of resources available to it or
modifying the features of the architecture (e.g. removing or adding new
services). This could involve adding a payment method to the WebUI, supporting
external SSO login options or forcing a particular recommender algorithm. Notice
that the reconfiguration request might be incomplete, providing information only
about the required changes but not necessarily about all their dependencies.
The system should adapt by moving to a valid configuration, ideally without
downtime.

For example, the administrator of the system requires switching between local
and external providers (e.g. moving from local database to cloud provider) with
little to no downtime by supporting the smooth transition with local caching as
a transition layer.
