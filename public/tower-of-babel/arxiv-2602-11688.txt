GORGO: Maximizing KV-Cache Reuse While Minimizing Network Latency in Cross-Region LLM Load Balancing
Alessio Ricci Toniolo, Abinaya Dinesh, Rome Thorstenson

Abstract
Distributing LLM inference across geographical regions can improve Time-to-First-Token (TTFT) by regionalizing service deployments. While existing multi-region load balancers save prefill computation by prioritizing Key--Value (KV) Cache hit rate, they ignore cluster networking latency, a critical factor in routing decisions. We introduce GORGO, a method for minimizing TTFT by optimizing a total serving cost as a function of available compute, network latency, and prefix caching. Using extensive profiling on custom infrastructure, we analyze component-level latency bottlenecks and benchmark GORGO against three baselines: (1) naive least-load routing, which ignores prefix-cache overlap; (2) prefix-similarity routing, which selectively pushes requests to the replica with the highest cached-prefix overlap; and (3) a centralized HTTP proxy that runs the GORGO policy while tracking requests across all nodes. We demonstrate that GORGO reduces P99 TTFT through network-aware routing and improves average TTFT by preventing pathological cross-region forwarding. Additionally, we find that GORGO-proxy overcomes synchronization overhead in previous methods and is 2.5x faster on median TTFT, demonstrating the success of a centralized router. 1 1 1 Code is available at https://github.com/atoniolo76/gotoni/tree/benchmark-load-balancing . 1
Introduction

Large language model (LLM) inference is increasingly deployed on geo-distributed
GPU clusters, driven by the need to serve geographically distributed users while
maintaining low latency and high availability. Recent multi-region systems have
shown that routing across regions can also improve utilization by aggregating
diurnally shifting demand
(
23
)
. In this setting, however, requests
have unpredictable output lengths and can take anywhere from milliseconds to
minutes to complete, making load difficult to anticipate and coordinate. The
dominant user-facing metric for interactive applications is often
Time-to-First-Token (TTFT); a single misrouted request that incurs unnecessary
wide-area latency or queuing can dominate tail performance

(
6
;
21
)
, even if the system-level throughput
remains high.

LLM inference can be decomposed into two computational phases:
prefill

and
decode
. Prefill processes the input prompt and constructs
KV cache state, while decode generates output tokens autoregressively

(
26
;
10
)
. Prefix caching can reduce TTFT by reusing cached KV state from
recurring system prompts, prior conversation turns, or other shared context

(
29
;
19
)
.

In a distributed deployment, each region hosts replicas with their own local KV
caches. Routing requests toward a replica (or region) with higher prefix overlap
can therefore reduce prefill work, but several factors complicate this decision:
a target may be busy, unavailable, or queued, and cross-region forwarding incurs
wide-area latency
(
23
;
22
)
. Load balancing policies must
therefore model the tradeoff between KV-cache reuse, network, and queueing costs.

A central challenge is:
when is it better to forward a request to a
distant region with lower cache overlap versus serve it locally with higher
cache hit rates?
Existing approaches often prioritize cache overlap while
treating network latency as a secondary or negligible concern. We demonstrate that network latency and KV cache similarity must be jointly optimized.

Our contribution:
we introduce
GORGO
, a per-region load balancer
that routes requests locally when possible, but selectively forwards to peer
regions using a joint optimization over (i) prefix-cache locality, (ii) measured
inter-region latency, and (iii) instantaneous admission/queue state.
This is enabled by low-latency, low-bandwidth observability that continuously
propagates peer network metrics to every deployed load balancer. We benchmark
GORGO against three baselines: (1) naive least-load routing, (2) prefix-similarity
routing that ignores network costs, and (3) a centralized HTTP proxy that tracks
prefix-cache state and network latency to route requests.

The remainder of the paper is organized as follows. We first review existing
multi-region and cache-aware routing strategies and motivate the network–cache
tradeoff that GORGO targets. We then describe GORGO’s architecture and cost
function before presenting an empirical evaluation.

2
Background and Motivation

2.1
Serving Primitives: Continuous Batching and KV Caching

Modern LLM serving stacks are built around two structural facts: (i) inference is
stateful due to the Key–Value (KV) cache, and (ii) throughput depends on how
well the system can admit new requests into a running batch. Orca introduced

iteration-level scheduling
(often referred to as continuous batching), in
which requests are admitted and retired at each decoding iteration to improve
GPU utilization and reduce padding waste
(
26
)
. vLLM complements this by
making KV-cache memory management explicit: PagedAttention stores KV blocks
non-contiguously to reduce fragmentation and improve serving throughput

(
10
)
.

KV caching also enables
prefix reuse
: when multiple requests share an
identical prefix (e.g., system prompts or shared conversation context), the
serving system can reuse cached KV state to skip redundant prefill computation.
SGLang’s RadixAttention operationalizes this mechanism using a radix-trie
representation that supports automatic KV reuse across structured generation
calls
(
29
)
.

2.2
Prefix-Aware Routing and Its Coordination Costs

Because the benefit of prefix reuse depends on where prior KV state resides,
request placement becomes a routing problem. Preble demonstrates that
prefix-aware scheduling can increase cache utilization by routing requests with
shared prefixes to replicas likely to contain the corresponding KV cache state

(
19
)
. DLPM further explores distributed prompt management and
scheduling, emphasizing that prefix-aware policies must balance locality with
system-level objectives such as fairness and coordination overhead

(
5
)
.

A central tension is that accurate prefix-aware routing typically requires
tracking (or approximating) per-replica cache state. Centralized coordinators can
maintain a global view, but their control-plane costs and tail latency penalties
grow with cluster scale and KV-cache size
(
5
)
.

2.3
Geo-Distributed Inference and Cross-Region Routing

Multi-region deployments are motivated by availability, latency to globally
distributed users, and cost efficiency when demand shifts across regions over
the day. SkyServe represents this broader trend toward multi-region serving
frameworks that manage placement and operation across regions and clouds

(
12
)
. Building on this setting, SkyWalker argues that cross-region
traffic handling can exploit diurnal demand skew to provision closer to global
peak, while mitigating the performance penalty of misrouting through a
geo-distributed load-balancer architecture with KV-cache-aware routing and
selective pushing
(
23
)
.

A key systems constraint in geo-distributed routing is wide-area latency.
Empirical characterizations of inter-region network behavior report typical
intercontinental round-trip times on the order of tens to hundreds of
milliseconds
(
22
)
. These costs interact directly with TTFT when a
request is forwarded across regions.

In production, multi-cluster and cross-region gateways (e.g., GKE multi-cluster
Gateways and AWS Bedrock cross-region inference) provide global routing and
failover mechanisms. However, these interfaces largely treat inference as an
opaque service endpoint, rather than incorporating LLM-specific signals such as
KV-cache locality or continuous-batch admission capacity

(
7
;
2
)
. In contrast, commercial systems such as
Modal support prefix caching within a single region, but do not optimize routing
across geographical deployments or account for cross-region latency
(
15
)
. In practice, regionalized deployments can also be constrained by market
conditions (e.g., not all GPU types are available in all regions across all
providers); systems such as SkyPilot address this by aggregating capacity across
clouds
(
25
)
.

2.4
Routing Objectives and the Network–Cache Tradeoff

Taken together, prior work establishes that KV-cache locality is a first-order
determinant of serving efficiency
(
23
;
29
;
19
;
10
)
, while geo-routing
introduces non-trivial network costs
(
22
)
. Classical load
balancing mechanisms such as consistent hashing provide stable request-to-backend
mappings with minimal disruption under membership changes
(
9
)

(and related distributed lookup protocols such as Chord
(
20
)
), and
thus are frequently used as lightweight affinity mechanisms.

Nevertheless, affinity signals alone are insufficient for TTFT-sensitive
workloads in geo-distributed clusters: maximizing prefix overlap can increase
TTFT if the routing decision induces a large cross-region latency penalty or
queues behind a saturated continuous batch.

For example, a request arriving at a West Coast load balancer finds the local region in a low-utilization state, providing a baseline for optimal performance. However, as regional traffic bursts, the balancer must choose between:

•

US-West (High Load):
3 ms network latency, 5% cache hit, 6,500 running tokens (
\sim
300 ms delay)
\rightarrow{}\sim
303 ms TTFT, 305.59 ms total.

•

Germany (Direct):
281 ms network latency, 0% cache hit, 0 running tokens
\rightarrow{}\sim
281 ms TTFT, 295.75 ms total.

•

Israel (Queued):
183 ms network latency, 15% cache hit, 4,200 queued tokens (
\sim
195.75 ms delay)
\rightarrow{}\sim
378 ms TTFT, 378.75 ms total.

Existing policies either pick (1) by default or always pick (3) for maximum cache utilization. This motivates GORGO’s central
question: how should a load balancer jointly account for (i) expected prefill
savings from prefix reuse, (ii) measured network latency, and (iii) instantaneous
queueing/admission state when selecting a serving region to minimize TTFT,
particularly at the tail?

3
Routing and the GORGO Policy

3.1
Initial Geo-proximal Routing

Requests are initially sent to the proxy’s chat-completion endpoint for geo-proximal routing. We pre-hash messages from the WildChat dataset and utilize a Lookup Table of hashes to global coordinates. The haversine distance is calculated from the WildChat user’s coordinates to every node’s coordinates. Using the minimum calculated distance, a new request is constructed and sent to the respective load balancer endpoint.

3.2
Design objective and signal requirements

GORGO targets the network–cache tradeoff by selecting a serving region that
minimizes
estimated
TTFT, jointly accounting for prefix reuse, network
latency, and instantaneous load.

Concretely, a GORGO load balancer relies on three signals:

1.

Cache locality:
estimated prefill time between incoming requests and prefix overlap in each region.

2.

Network latency:
measured round-trip latency (RTT) between load balancers.

3.

Admission/queue state:
whether local regions can admit a new request promptly under continuous batching.

3.3
System architecture and routing workflow

GORGO uses a distributed, per-region load balancer architecture. Each region
runs a
loadbalancer.go
instance that serves as client ingress, mirrors
local serving state, and periodically exchanges summarized state with peer load
balancers.

Local control state.

Each load balancer maintains a lightweight prefix index that mirrors the serving
SGLang’s prefix structure, which represents cached prefixes using a radix trie

(
29
)
. The load balancer also mirrors local admission state (e.g.,
running vs.
waiting requests) and maintains per-token timing statistics exported by the
runtime.

Peer summaries.

Load balancers maintain a peer table with recent RTT measurements and refreshed
summaries of peer availability and prefix-locality estimates.

Per-request decision.

For each region, the load balancer estimates TTFT as
(a) forwarding latency, plus (b) residual prefill time after accounting for
prefix reuse, plus (c) queueing/admission delay. Requests are forwarded only when the local region cannot immediately admit them into a running batch, and the request can optionally stay in the local region depending on the queue-size estimate.

3.4
Per-request objective: cost model

GORGO implements this decision using an additive cost model because components occur sequentially:

\displaystyle\mathrm{Cost}(\text{region})

\displaystyle=\mathrm{NetworkLatency}(\text{peer})

\displaystyle\quad+t_{\text{p}}\cdot\mathrm{PrefillCost}(\text{peer + local})

\displaystyle\quad+\hat{q}_{s}\cdot\mathrm{QueueWaitTime}(\text{local}).

Here,
\mathrm{NetworkLatency}(\text{peer})
is the measured RTT to the
peer load balancer;
\mathrm{PrefillCost}(\text{peer + local})
estimates the portion of
prefill work not covered by prefix reuse using the measured per-token prefill
rate; and
\mathrm{QueueWaitTime}(\text{peer})
estimates admission delay from
mirrored requests in the queue and current running batch. The weights
t_{\text{p}}
and
\hat{q}_{s}
are tunable at runtime.

Translating prefix overlap into time.

Given an estimated cached-prefix length
L_{\text{hit}}
and total prefill length

L_{\text{p}}
, we convert overlap into time using the runtime’s per-token
prefill time
t_{\text{p}}
:

\displaystyle\mathrm{SavedTime}

\displaystyle=L_{\text{hit}}\cdot t_{\text{p}},

\displaystyle\mathrm{ResidualPrefillTime}

\displaystyle=(L_{\text{p}}-L_{\text{hit}})\cdot t_{\text{p}}.

3.5
Implementation

Telemetry and request tracing

The load balancer records per-request metadata needed to measure bottlenecks and to
reconstruct routing paths:

•

request creation timestamp and unique request identifier

•

the sequence of load balancers traversed, with per-hop timestamps

•

time from creation to admission by an
executing region

Each load balancer also reports aggregate metrics (total requests handled,
uptime/downtime intervals, and instantaneous queue depth).

Handler path.

Upon receiving a request,
Handler()
first pre-calculates the token count
from the request body. If
localHasCapacity()
returns true (based on
polled SGLang metrics: running requests below threshold and GPU cache below limit),
the request is processed locally via reverse proxy.

When local capacity is exhausted and the hop count is below
MaxHops
,

selectPeer()
consults the configured strategy. All queued request lengths
are multiplied by
t_{p}
.

Prefix index.

The prefix trie structure stores mappings from prompt prefixes to peer nodes that
have previously served matching requests. During peer selection, the trie is
traversed to find the longest matching prefix, enabling KV-cache-aware routing
without storing actual KV pairs.

Serving-runtime integration (SGLang) and queue mirroring.

The serving runtime exposes a status endpoint that provides (i) current queue
state, (ii) available KV-cache capacity, and (iii) per-token computation time.
SGLang provides the radix-trie mechanism enabling prefix reuse
(
29
)
,
and continuous batching motivates explicit admission/queue mirroring
(
26
)
.

Central observability service.

For experiments and debugging, we also run a lightweight SGLang polling service that
periodically pulls metrics from all load balancers to provide a consolidated view
of state (including RTT measurements and
NumWaitingRequests
).

Our goal is to assess whether incorporating
measured wide-area latency
,

prefix-cache locality
, and
admission/queue state
into a single

4.3
Workload

Our work leverages GuideLLM, WildChat, and a geoproximal integration between the two to benchmark GORGO. This encompasses a synthetic mixed request distribution across regions with variable prompt lengths, including shared system prompts to induce non-trivial prefix overlap. In WildChat, requests follow multi-turn dialogue patterns similar to prior public traces
(
27
;
28
)
. In GuideLLM, we are able to vary workloads between four major types: concurrent, poisson, throughput, and sweep-based.

1.

Concurrent
workloads enable us to compute the maximal sustainable throughput of each load-balancing policy, as it maintains a fixed number of parallel requests in flight and consistently replaces completed requests.

2.

Poisson
workloads model human-like behavior by sending requests at a Poisson-distributed rate, mimicking bursty traffic patterns. Testing at a variable rate enables us to measure improvements at tail latencies (P99).

3.

Throughput
based request-firing enables us to zoom in on load balancing behavior when there are greater requests/second than what is available in the server running, available, and waiting queues.

4.

Sweep-based
workloads progressively increase request rate until latency degrades or errors appear.

Finally, we integrate WildChat with GuideLLM to benchmark our load balancing policies against simple geo-proximal routing. Since GuideLLM only supports targeting a single endpoint, we leverage the location metadata included in each WildChat conversation. First, we preprocess WildChat to create a lookup table mapping hash(prompt) → (lat, lon) and export prompts as a JSONL dataset. Then, we run a local geo-routing tunnel that GuideLLM targets. When the proxy receives a request, it hashes the prompt, looks up the user’s location, and forwards the request to the geographically nearest cluster node.

4.4
Baselines

We compare against four routing policies that represent common design points:

1.

Least-load routing
naively routes each request to the instance with the highest availability.

2.

Prefix-similarity routing (
Prefixtrie
)
routes to maximize cached-prefix overlap, without accounting for inter-cluster network latency and gpu availability.

3.

GORGO
accounts for local estimated TTFT (based on queue sizes), point to point latency, KV cache overlap to other peers, and GPU availability §
3
.

4.

GORGO-proxy
acts as a middleware node by serving a http-proxy that runs the GORGO policy with centralized information about incoming requests and instance-based metrics.

5
Discussion

Interpreting the routing objective.

The motivating premise of GORGO is that minimizing TTFT in geo-distributed
serving is fundamentally a
multi-signal
decision problem. Prefix reuse
reduces prefill work, but the value of that reuse depends on the latency of the
forwarding path and the likelihood of prompt admission under continuous
batching (§
3
). Framing routing as the minimization of an estimated
TTFT—rather than as “maximize cache overlap” or “minimize load” in
isolation—makes the network–cache tradeoff explicit and highlights why
policies optimized for throughput can be misaligned with TTFT-sensitive
workloads.

Why an additive cost model is a useful abstraction.

GORGO’s cost model aggregates three terms that are already present in the
serving pipeline: forwarding latency, residual prefill time after accounting for
prefix reuse, and admission delay (§
3
). This decomposition
clarifies which signals the load balancer must track (per-token compute rates,
measured RTT, and admission/queue state) and provides a common interface for
integrating cache-aware routing with geo-routing. Importantly, the model is not
intended to perfectly predict per-request latency; rather, it operationalizes a
consistent set of tradeoffs that can be evaluated and tuned within a deployment.

Centralized proxies versus coordination overhead.

Prior work in cross-regional inference has exclusively used distributed load balancers, assuming high overhead costs to synchronize a centralized load balancer
(
23
)
.
However, with GORGO-proxy, we show that a middleware proxy can achieve high throughput and an over 2x lower TTFT in highly distributed workloads, improving on the decentralized approach, GORGO. We find that by retaining the full-picture of every node’s KV-Cache and end-to-end latencies from proxy to node, the singular load balancer has a significant information advantage over individual load balancers. This is a direction for future work.

Design implications: avoiding pathological forwarding.

The explicit inclusion of network latency and admission state helps guard against
pathological decisions in which a request is forwarded to chase cache overlap but
incurs a larger latency penalty or queues behind an effectively saturated batch.
From a systems perspective, this emphasizes that prefix locality is best treated
as a
means
to reduce prefill cost, not as an end-to-end objective. It also
suggests that cache-aware policies require a notion of “how much compute is
actually saved” (via per-token rates) to be meaningfully compared against wide-area network
costs and queueing risk.

Scope of applicability.

GORGO targets deployments where (i) requests are TTFT-sensitive, (ii) regions are
connected by non-trivial wide-area latency, and (iii) the serving stack exposes
admission state and stable per-token timing signals. Within this scope, GORGO’s
architecture remains lightweight: it relies on summarized peer state and does
not require centralized coordination or transfer of KV-cache contents.

Connection to prior systems.

Taken together, the discussion above motivates why GORGO should be interpreted as
a bridge between cache-aware routing mechanisms and geo-distributed gateways: it
adopts LLM-specific locality signals while making wide-area latency a first-class
term in the routing decision. We next situate this design relative to prior
systems in serving, prefix-aware placement, and geo-routing.

Related Work

Geo-distributed serving and inter-cloud orchestration.

A growing line of systems work studies how to provision and route services across
regions and clouds to improve availability and cost efficiency.
SkyServe and SkyWalker exemplify this trend for LLM inference, emphasizing
geo-distributed deployments and the operational benefits of shifting capacity to
follow diurnal demand
(
12
;
23
)
.
In parallel, general “sky computing” efforts such as SkyPilot focus on
inter-cloud resource selection and job placement, abstracting away heterogeneity
across providers while optimizing for performance/cost trade-offs
(
25
)
.
GORGO is complementary to these frameworks: rather than deciding
where to run

(or which cloud to use), our focus is the
online request-routing decision

once multiple regions are already deployed, and specifically on minimizing TTFT
under LLM-specific statefulness.

LLM serving, KV caching, and prefix-aware routing.

Recent serving systems make the Key–Value (KV) cache a first-class concern and
exploit prefix reuse to reduce redundant prefill computation.
Single-region systems such as SGLang and vLLM operationalize prefix caching via
explicit data structures and memory management, enabling reuse when many
requests share common prompt prefixes
(
29
;
10
)
.
Preble extends this idea toward distributed settings by coordinating placement to
increase prefix reuse and throughput
(
19
)
, and subsequent work explores
more structured schedulers and fairness guarantees on top of prefix locality
(e.g., DLPM)
(
5
)
.
These approaches motivate our use of prefix overlap as a routing signal, but they
primarily target throughput and/or rely on centralized coordination.
GORGO instead targets geo-distributed TTFT: we treat prefix locality as one input
into a cost model that is explicitly co-optimized with wide-area latency and
admission delay, and we do so in a per-region, distributed control plane.

Centralized vs.
lightweight coordination for stateful routing.

A central scheduler can maintain a detailed global view of cache state and queue
conditions, enabling high-quality placement decisions
(
19
;
5
)
.
However, as deployments span regions, the control-plane RTT and the risk of a
single failure domain become first-order concerns.
GORGO occupies a different point in the design space: each region makes routing
decisions locally using periodically exchanged summaries, aiming to preserve the
benefits of cache-aware placement while avoiding tight, latency-sensitive
coordination across regions.

Production multi-region gateways.

Commercial offerings expose cross-region inference and global endpoints—for
instance, AWS Bedrock supports cross-region inference and GKE multi-cluster
gateways provide a unified ingress across Kubernetes clusters

(
2
;
7
)
.
These systems provide robust failover and coarse traffic shifting, but largely
treat inference as an opaque backend.
In contrast, GORGO leverages LLM-specific signals (prefix locality and
continuous-batching admission state) and makes network latency an explicit term
in the routing objective, enabling decisions that directly target TTFT rather
than only availability or aggregate load.

Managing prefill–decode imbalance and disaggregation.

As prompts become longer and more “prompt-heavy,” several systems address the
prefill–decode imbalance using techniques such as chunked prefill and
prefill/decode disaggregation across GPUs
(
1
;
30
)
.
Other work explores alternative reuse mechanisms (e.g., non-prefix sharing or
kernel-level optimizations) that are largely orthogonal to routing

(
11
;
24
)
.
These advances reduce the compute component of TTFT, but do not by themselves
resolve geo-routing trade-offs when cache locality and network latency conflict.
GORGO is complementary: it assumes an underlying serving stack that may already
use chunked prefill or disaggregation, and focuses on selecting the region where
that stack should execute to minimize end-to-end TTFT.

Classic load balancing and scheduler designs.

Prior work on latency-sensitive datacenter scheduling often studies microsecond-
scale tasks and emphasizes work stealing and fine-grained core reallocation

(
13
;
17
)
. These approaches inform our baselines and
motivate treating admission and queueing explicitly, but their assumptions and
coordination timescales differ from GPU-backed LLM inference
(
26
)
.

7
Limitations

Trade-off between latency and throughput.

While GORGO excels in TTFT, the policy suffers with throughput (see Figures
2
and
3
). In order to leverage selective pushing at scale and prevent queue overloading, we impose rate limits and queuing limits on individual instances. This may lead to GORGO overselecting for a TTFT-optimal route at the expense of underutilized compute. However, this problem is remediated by GORGO-proxy, which achieves both the lowest TTFT and greatest throughput by leveraging GORGO’s logical policy along with logs from inference backends for efficient hardware usage.

Methodological limitations.

Our routing decisions depend on the accuracy and freshness of four signals:
measured RTT, estimated prefix overlap, mirrored admission/queue state, and
per-token compute rates. In particular, prefix-overlap estimates are derived
from a lightweight prefix index rather than from the serving runtime’s exact KV
state, and per-token rates may shift with batch composition, prompt lengths, and
system noise. These approximations can lead to misestimation of the true TTFT
benefit of forwarding or cache reuse.

Experimental limitations.

The current evaluation is constrained to a small number of regions and a limited
set of deployment configurations. However, three regions do capture the dominant intercontinental latency regimes while keeping experiments reproducible. We use WildChat as
the primary data source driving our request mix, and treat it as representative
of real-world usage. For posterity, we updated the GORGO policy to incorporate prompt-length characteristics from both the queue and currently running requests.

8
Future Work

Several directions follow naturally from these limitations.

On-device kernel for policy computation.

We find that the individual processes of tokenization and radix-trie traversal introduce non-zero latencies for GORGO.
Prefixtrie
, which neglects the calculation of the prefill time for a request, is computationally less-intensive due to fewer radix-trie searches and the lack of tokenization sidecar process. Future work could develop a native CUDA kernel for GPUs to perform the tokenization lookup and prefix trie search processes in parallel, dramatically speeding up the cost of calculation for efficient neural-network approaches

(
8
)
.

Learning or adapting the cost weights.

The weights
t_{p}
and
\hat{q}_{s}
are deployment parameters.
Automatically tuning
\hat{q}_{s}
using online feedback from observed TTFT and inter-token latency values could reduce
manual calibration effort and improve robustness to changing network conditions and workload mixes. In general we deliberately focus on an interpretable, systems-driven policy to ensure predictability under changing network conditions, but learning-based routing is an avenue for future work.

Heterogeneous regions and policy constraints.

The current cost model assumes that per-token timing statistics are comparable
within an experiment. Extending the model to heterogeneous accelerator fleets
(e.g., different GPU types or memory capacities) would require normalizing
compute-rate estimates and integrating capacity constraints. A related direction
is to incorporate policy constraints (e.g., data residency) into the feasible set
of routing targets.

Proactive prefix placement and cache warming.

GORGO is reactive: it routes based on current prefix locality and measured state.
Proactively replicating or warming high-value prefixes in anticipation of demand
shifts could reduce the need for cross-region forwarding while preserving cache
reuse.

Robustness to GPU Failures and Slow Ranks

During development and evaluation of the GORGO policy, we found that GPU health was a major issue in high-throughput benchmark testing. In order to test our selective pushing GORGO-proxy, we ran maximum-throughput requests that would accumulate on the load balancer’s queue. This reached Linux’s file descriptor limit and required a system reboot, thus delaying our benchmarking process from completing. Modal, which operates a warm pool of over 20,000 GPUs, leverages a reliability dashboard for observing health metrics such as memory utilization and power usage
(
4
)
. We experimented with centralizing logging through running Grafana Alloy services and Prometheus visualization through polling SGLang’s ‘/metrics’ endpoint. Similarly, for training clusters with 100,000 GPUs, Meta developed a custom communication backend which pushes RDMA WQE events to a tracing database for identifying ‘Start’ to ‘Stop’ time discrepancies
(
18
)
. We developed our own tracing process with event-based pushing and circular buffering for profiling in Perfetto. Future work may improve the reliability of GPU clusters by adaptively responding to inference engine failures or sudden performance drops based on these methods.

9
Conclusion

Distributed LLM inference across geographical regions requires careful
coordination between network topology and cache management. Existing approaches
often optimize cache reuse and network latency independently, leading to either
poor cache utilization (when routing ignores prefix locality) or degraded TTFT from cross-region forwarding (when routing ignores wide-area latency and
queueing).

GORGO introduces a joint optimization framework that treats routing as a
multi-objective problem, balancing network latency, KV cache similarity, and
queue depths. By modeling routing cost as a function of all three factors, GORGO
provides a principled approach to request placement that adapts to current
network conditions and system load. While a heuristic policy and not a provably optimal scheduler, GORGO-proxy offers distinct advantages compared to existing solutions.

The key insight is that
network latency and cache similarity should not be
optimized independently
. A high cache hit rate in a distant region may result
in worse TTFT than a lower cache hit rate locally. GORGO’s cost function captures
this trade-off explicitly, enabling intelligent routing decisions that minimize
user-perceived latency.

As LLM deployments continue to scale globally, intelligent load balancing will
become increasingly critical. GORGO provides a practical foundation for building
responsive, efficient, and globally distributed LLM serving systems.

Impact Statement

This paper studies geo-distributed routing for LLM inference, with the goal of
reducing Time-to-First-Token (TTFT) and avoiding pathological cross-region
forwarding. If deployed, such routing can improve responsiveness for globally
distributed users and increase serving efficiency by better trading off network
latency and KV-cache reuse. Improved efficiency may also reduce the energy and
hardware required per request by avoiding redundant prefill computation.

From a systems perspective, cache-aware routing and telemetry introduce privacy and security considerations. While GORGO does not require moving KV-cache contents between regions, any practical deployment must ensure that routing
metadata and measurements do not leak sensitive user information (e.g., through
logs or timing side channels), and must respect policy constraints such as data
residency. Mitigations include minimizing and anonymizing logged data, avoiding
retention of raw prompts, enforcing strict access controls, and constraining the
set of eligible regions according to regulatory and organizational policies.
