Space-Time Tradeoffs for Spatial Conjunctive Queries
Aryan Esmailpour, Xiao Hu, Stavros Sintos

Abstract
. Given a conjunctive query and a database instance, we aim to develop an index that can efficiently answer spatial queries on the results of a conjunctive query. We are interested in some commonly used spatial queries, such as range emptiness, range count, and nearest neighbor queries. These queries have essential applications in data analytics, such as filtering relational data based on attribute ranges and temporal graph analysis for counting graph structures like stars, paths, and cliques. Furthermore, this line of research can accelerate relational algorithms that incorporate spatial queries in their workflow, such as relational clustering. Known approaches either have to spend O ~ ​ ( N ) \tilde{O}(N) query time or use space as large as the number of query results, which are inefficient or unrealistic to employ in practice. Hence, we aim to construct an index that answers spatial conjunctive queries in both time- and space-efficient ways. In this paper, we establish lower bounds on the tradeoff between answering time and space usage. For k k -star (resp. k k -path) queries, we show that any index for range emptiness, range counting or nearest neighbor queries with T T answering time requires Ω ⁡ ( N + N k T k ) \Omega\left(N+\frac{N^{k}}{T^{k}}\right) (resp. Ω ⁡ ( N + N 2 T 2 / ( k − 1 ) ) \Omega\left(N+\frac{N^{2}}{T^{2/(k-1)}}\right) ) space. Then, we construct optimal indexes for answering range emptiness and range counting problems over k k -star and k k -path queries. Extending this result, we build an index for hierarchical queries. By resorting to the generalized hypertree decomposition, we can extend our index to arbitrary conjunctive queries for supporting spatial conjunctive queries. Finally, we show how our new indexes can be used to improve the running time of known algorithms in the relational setting.



1.
Introduction

In the digital age, tera-bytes of data are generated every second.
A large amount of raw data would be useless if we could not analyze them to extract valuable knowledge. One standard way to extract knowledge is by asking data queries on the input data.
A data analyst might ask several queries to an index built on the entire or a subset of the input data set. In relational databases, data is gathered and stored across various tables, where each row corresponds to a tuple and each column to an attribute. Two tuples stored in different tables can be joined if their shared attributes are equal. This setting is quite common in practical database management systems (DBMS) since more than 70% of DBMS are relational and more than 65% of the data sets in learning tasks are relational data
(
kaggle
;
link1
)
.

Spatial conjunctive queries
(SCQ) are spatial queries defined on the results of a
conjunctive query
(CQ) over relational data. The most common spatial queries include range emptiness, range counting, and nearest neighbor queries. Due to the importance and ubiquitousness of relational data and spatial queries, SCQs have significant applications in several domains, such as geographic information systems, social networks, and temporal graph analysis.

Example 1.1.

A crypto exchange startup has a table
\mathsf{SellOffer}(\mathsf{sellerID},\mathsf{CSS},\mathsf{currency})
for all selling offers, containing the seller’s id, seller’s credit score, and the currency the seller wants to sell (bitcoin, Ethereum, etc.).
It also contains
a table for all buyers
\mathsf{Buyer}(\mathsf{buyerID},\mathsf{CSB},\mathsf{currency})
that contains the buyer’s id, buyer’s credit score, and the currency the buyer will use to pay.
Notice that each seller can make multiple offers, and each buyer might be interested in multiple offers.
The startup wants to support a Nearest Neighbor classifier on the pairs
(\mathsf{CSS},\mathsf{CSB})
, where the credit score of a buyer is paired with the credit score of a seller if the buyer and the seller are interested in the same currency.
The startup aims to construct an index for nearest neighbor queries such that, given a query point
(x,y)
,
the goal is to find the nearest neighbor in
\pi_{\mathsf{CSS},\mathsf{CSB}}(\mathsf{SellOffer}\Join\mathsf{Buyer})
),
where
\pi
is the projection operation, and
\Join
is the join operation.

Example 1.2.

Let
G(V,E)
be a graph representing a social network with
|V|
users and
N=|E|
edges representing the friendships between the users. Every user
u
is associated with a social score, indicating their performance on social media
(
linkHookle
)
.
A team of researchers aims to count the number of
3
-star user-patterns where the center node has high score and the rest of nodes have low score (nodes
u,v,w,z
form a
3
-star with center
u
, if
v,w,z
are all connected to
u
) to understand how the social network influences user interactions.
More formally, let
R(\mathsf{userA},\mathsf{userB})
be a relation that has a tuple for each edge
(u,v)\in E
. Furthermore, let
S(\mathsf{userA},\mathsf{score})
be a relation that has a tuple for each node of the graph along with their social score.
The researchers aim to construct an index such that given a query rectangle
[x_{l},x_{r}]\times[y_{l},y_{r}]\times[z_{l},z_{r}]\times[w_{l},w_{r}]
(a rectangle contains one interval for every attribute) the goal is to count the number of tuples in

R(A_{1},B)\Join R(A_{2},B)\Join R(A_{3},B)\Join\sigma_{x_{l}\leq C_{1}\leq x_{r}}(S(A_{1},C_{1}))\Join\sigma_{y_{l}\leq C_{2}\leq y_{r}}(S(A_{2},C_{2}))\Join\sigma_{z_{l}\leq C_{3}\leq z_{r}}(S(A_{3},C_{3}))\Join\sigma_{w_{l}\leq C_{4}\leq w_{r}}(S_{4}(B,C_{4}))
,
where
\sigma
is the selection operation.

Interestingly, in addition to all their real applications, SCQs play a key role in optimization problems over relational data.
For example, Agarwal et al.
(
agarwal2025computing
)
, designed efficient algorithms to find a diverse set on the results of a join (or conjunctive) query in relational data. In their algorithms, they repeatedly use an oracle to count the number of results of a conjunctive query that lie in a query rectangle and an oracle to compute nearest neighbor queries on the results of a conjunctive query.
Furthermore, Esmailpour and Sintos
(
esmailpour2025improved
)
designed efficient algorithms for
k
-means and
k
-median clustering on the results of a join query in relational data, using similar spatial oracles.
In both papers, the authors constructed indexes with
O(N)
query time to model the required spatial oracles.

There are two main ways to handle SCQs. For range emptiness or range counting queries, given a query hyper-rectangle, one approach
(
agarwal2025computing
;
esmailpour2025improved
)
is to filter out tuples from the input databases that do not satisfy the linear constraints and then run a standard join algorithm on the remaining tuples. While the space used is only
O(N)
, the query time of this approach is
\Omega(N)
(such as Yannakakis algorithm
(
yannakakis1981algorithms
)
) to count the number of join results of an acyclic query).
Similarly, for nearest neighbor queries, the indexes constructed in
(
deep2022ranked
;
deep2021ranked
;
tziavelis2020optimal
)
can be used as described in
(
agarwal2025computing
)
to compute the nearest neighbor of a query point
q
in
O(N)
time for join (or conjunctive) queries using
O(N)
space.
The other approach is first to materialize all join results and then construct a geometric index (for example, a range tree
(
de1997computational
)
for range counting or quadtree
(
finkel1974quad
)
for approximate nearest neighbor queries) on the join results. While the query time on these indexes is only
\tilde{O}(1)
(we use
\tilde{O}
notation to hide
{\textsf{polylog}}(n)
factors) the space usage is high, which heavily depends on the number of join results. For example, the space needed to materialize all results in Example
1.1
is
\Omega(N^{2})
, and the space needed in Example
1.2
is
\Omega(N^{3})
. Overall, no known index exists for SCQs that use less space than materializing all CQ results having sublinear query time with respect to the size of the input database.

1.1.
Conjunctive Queries

Let
{\mathbf{R}}
be a database schema that contains
m
relations
R_{1},R_{2},\cdots,R_{m}
. Let
{\mathbf{A}}
be the set of all attributes in
{\mathbf{R}}
. Each relation
R_{i}
is defined on a subset of attributes
{\mathbf{A}}_{i}\subseteq{\mathbf{A}}
. We use
A,B,C,A_{1},A_{2},A_{3},\cdots
etc. to denote the attributes in
{\mathbf{A}}
and
a,b,c,\cdots
etc. to denote their values. Let
{\texttt{dom}}(A)=\mathbb{R}
be the domain of attribute
A\in{\mathbf{A}}
. The domain of a set of attributes
X\subseteq{\mathbf{A}}
is defined as
{\texttt{dom}}(X)=\mathbb{R}^{|X|}
.
Given the database schema
{\mathbf{R}}
, let
\mathbf{I}
be a given database of
{\mathbf{R}}
, and let the corresponding relations of
R_{1},\cdots,R_{m}
be
R_{1}^{\mathbf{I}},\cdots
,
R_{m}^{\mathbf{I}}
, where
R_{i}^{\mathbf{I}}
is a collection of tuples defined on
{\texttt{dom}}({\mathbf{A}}_{i})
. The
input size
of database
\mathbf{I}
is denoted as
N=\sum_{i\in[m]}|R^{\mathbf{I}}_{i}|
.
For a database
\mathbf{I}
, the
active domain

{\texttt{adom}}^{\mathbf{I}}(A)
of an attribute
A\in{\mathbf{A}}
is defined as the set of values from
{\texttt{dom}}(A)
that appear in at least one tuple of
\mathbf{I}
.
We drop the superscripts when
\mathbf{I}
is clear from the context.
If an attribute
A\in{\mathbf{A}}
belongs to more than one relation, it is called
join attribute
. We consider the class of
conjunctive queries
:

\mathcal{Q}(\mathbf{y}):-R_{1}(\mathbf{A}_{1}),R_{2}(\mathbf{A}_{2}),\cdots,R_{m}(\mathbf{A}_{m}),

where
\mathbf{y}\subseteq{\mathbf{A}}
is the set of
output attributes
(a.k.a.
free attributes
) and
\mathbf{A}-\mathbf{y}
is the set of
non-output attributes
(a.k.a.
existential attributes
). A CQ is
full
if
\mathbf{A}=\mathbf{y}
(a full CQ is also called a
join query
), indicating the natural join among the given relations; otherwise, it is
non-full
. In this work, we focus on
data complexity
: the query size
m
and
|{\mathbf{A}}|
are constants, and the complexity of our algorithms is measured by the input size of the database,
N
.
We can always represent a CQ
\mathcal{Q}
as a hypergraph
G_{\mathcal{Q}}=(\mathcal{V},\mathcal{E})
, where every attribute
A\in{\mathbf{A}}
is a vertex in
\mathcal{V}
, and every relation
R_{j}\in{\mathbf{R}}
is a hyper-edge containing all vertices corresponding to attributes
{\mathbf{A}}_{j}
.
For an attribute
A\in{\mathbf{A}}
, let
E_{A}=\{R\in{\mathbf{R}}\mid A\in{\mathbf{A}}\}
.

Extending the notations above, we also use
{\mathsf{head}}(\mathcal{Q})
to denote the output attributes of
\mathcal{Q}
.
For a subset of attributes
X\subseteq{\mathbf{A}}
and a set of tuples
Y
, let
\pi_{X}(Y)
be the set containing the projection of the tuples in
Y
onto the attributes
X
. Notice that two tuples in
Y
might have the same projection on
X
; however,
\pi_{X}(Y)
is defined as a set, so the projected tuple is stored once. We also define the multi-set
\bar{\pi}_{X}(Y)
so that if for two different tuples
t_{1},t_{2}\in Y
it holds that
\pi_{X}(t_{1})=\pi_{X}(t_{2})
, then the tuple
\pi_{X}(t_{1})
exists more than once in
\bar{\pi}_{X}(Y)
.
When a CQ
\mathcal{Q}
is evaluated on database
\mathbf{I}
, its query result denoted as
\mathcal{Q}(\mathbf{I})
is the projection of the natural join result of
R_{1}(\mathbf{A}_{1})\Join R_{2}(\mathbf{A}_{2})\Join\cdots\Join R_{m}(\mathbf{A}_{m})
onto
{\mathsf{head}}(\mathcal{Q})
. We study our problem under
bag semantics
, so the result of a conjunctive query might contain duplicates.
More formally, the result of
\mathcal{Q}
over database
\mathbf{I}
under bag semantics, is defined as
\mathcal{Q}(\mathbf{I})=\bar{\pi}_{{\mathsf{head}}(\mathcal{Q})}(\Join_{i\in[m]}R_{i}({\mathbf{A}}_{i}))
.

We notice that bag semantics is the default option in SQL. This choice aligns with the needs of practical database management, where queries often involve aggregations (e.g., COUNT, SUM), and duplicate-preserving behavior is crucial for correct computations. Unlike set semantics, which eliminates duplicates by default, bag semantics enables more efficient query evaluation and aligns with real-world data retrieval scenarios, such as financial transactions, sensor data collection, and reporting tasks. Furthermore, preserving duplicates allows for better optimization strategies in query execution plans, as many relational database engines leverage multi-set operations to improve performance.

We introduce several important classes of CQs that will be commonly used throughout the paper. The
k
-star query is defined as
\mathcal{Q}_{\mathsf{star}}^{k}(\mathcal{A}_{1},\ldots,\mathcal{A}_{k}):-R_{1}(\mathcal{A}_{1},\mathcal{B}),R_{2}(\mathcal{A}_{2},\mathcal{B}),\ldots,R_{k}(\mathcal{A}_{k},\mathcal{B}),

where
\mathcal{A}_{i},\mathcal{B}\subseteq{\mathbf{A}}
,
\mathcal{A}_{i}\cap\mathcal{A}_{j}=\emptyset
, for
i,j\in[k]
with
i\neq j
, and
\mathcal{A}_{i}\cap\mathcal{B}=\emptyset
, for
i\in[k]
. The
k
-path query is defined as
\mathcal{Q}_{\mathsf{path}}^{k}(\mathcal{A}_{1},\mathcal{A}_{2}):-R_{1}(\mathcal{A}_{1},\mathcal{B}_{1}),R_{2}(\mathcal{B}_{1},\mathcal{B}_{2}),\ldots,R_{k}(\mathcal{B}_{k-1},\mathcal{A}_{2}),

where
\mathcal{A}_{1},\mathcal{A}_{2},\mathcal{B}_{j}\subseteq{\mathbf{A}}
, for
j\in[k-1]
,
\mathcal{A}_{1}\cap\mathcal{A}_{2}=\emptyset
, and
\mathcal{B}_{i}\cap\mathcal{B}_{j}=\emptyset
, for
i,j\in[k-1]
with
i\neq j
.
We note that for these queries, none of their join attributes belong to the head of
\mathcal{Q}_{\mathsf{star}}^{k}
or
\mathcal{Q}_{\mathsf{path}}^{k}
query. When some join attributes are in the head of
\mathcal{Q}_{\mathsf{star}}^{k}
(resp.
\mathcal{Q}_{\mathsf{path}}^{k}
) we call them the generalized
k
-star query (resp. generalized
k
-path query).
A further generalization of star queries is the class of hierarchical queries
(
dalvi2007efficient
)
: A CQ
\mathcal{Q}
over the set of relations
{\mathbf{R}}
and set of attributes
{\mathbf{A}}
is
hierarchical
, if for any pair of attributes
A,B\in{\mathbf{A}}
, either
E_{A}\subseteq E_{B}
or
E_{B}\subseteq E_{A}
or
E_{A}\cap E_{B}=\emptyset
.

1.2.
Problem definition

For a CQ
\mathcal{Q}
, a hyper-rectangle
\mathcal{R}
in
\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}
, is defined as
\mathcal{R}=\delta_{1}\times\ldots\times\delta_{|{\mathsf{head}}(\mathcal{Q})|}
, where
\delta_{j}=[\delta_{j}^{-},\delta_{j}^{+}]
is an interval denoting the query range predicate on the
j
-th head attribute. We start by defining the
RCQ
problem.

Definition 1.3 (Rectangle Counting Query Problem).

For a CQ
\mathcal{Q}
and a database
\mathbf{I}
, the goal is to construct an index, such that given any hyper-rectangle
\mathcal{R}=\delta_{1}\times\ldots\times\delta_{|{\mathsf{head}}(\mathcal{Q})|}
, it returns the number of
query results from
\mathcal{Q}(\mathbf{I})
falling into
\mathcal{R}
, i.e.,
|\mathcal{Q}(\mathbf{I})\cap\mathcal{R}|=|\sigma_{\delta_{j}^{-}\leq A_{j}\leq\delta_{j}^{+},A_{j}\in{\mathsf{head}}(\mathcal{Q})}(\mathcal{Q}(\mathbf{I}))|
.

Figure 1
.
For query rectangle
\mathcal{R}=[4,7]\times[7,8]
,
RCQ
returns
3
because
\bar{\pi}_{A_{1},A_{2}}(\sigma_{4\leq A_{1}\leq 7}(R_{1})\Join\sigma_{7\leq A_{2}\leq 8}(R_{2}))=\{(4,7),(5,7),(7,8)\}
. Given the query point
q=(7,2)
and
\varepsilon=1
, the
ANNQ
(might) return the query result
p=(9,2)
because
\phi(q,p)=2\leq(1+1)\cdot 1
, since the nearest neighbor of
q
is the tuple
(8,2)
, within distance
1
.

See an example in Figure
1
. We use

{\texttt{RCQ}}(\mathcal{Q},\mathbf{I},\mathcal{R})
to denote the answer to rectangle query
\mathcal{R}
over
\mathcal{Q}(\mathbf{I})
. The range emptiness query can be modeled as an instance of the
RCQ
problem, by checking whether
{\texttt{RCQ}}(\mathcal{Q},\mathbf{I},\mathcal{R})>0
.

Let
\phi:\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}\times\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}\to\mathbb{R}
be a distance function. In this work, we focus on the Euclidean distance
\phi(p,q)=\sqrt{\sum_{A\in{\mathsf{head}}(\mathcal{Q})}\left(\pi_{A}(p)-\pi_{A}(q)\right)^{2}},
for two tuples
p,q\in\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}
.
For any tuple
q\in\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}
, let
\displaystyle{\textsf{dist}(q,\mathcal{Q}(\mathbf{I}))=\min_{p\in\mathcal{Q}(\mathbf{I})}(p,q)}
denote the distance between
q
and the closest result in
\mathcal{Q}(\mathbf{I})
.
Let
\texttt{NN}(\mathcal{Q},\mathbf{I},q)
denote the closest tuple in
\mathcal{Q}(\mathbf{I})
from
q
, i.e.,

\phi(q,\texttt{NN}(\mathcal{Q},\mathbf{I},q))=\phi(q,\mathcal{Q}(\mathbf{I}))
.
Lower bounds on nearest neighbor queries
(
liu2004strong
;
chazelle1996simplex
;
afshani2012improved
)
rule out the possibility of a near-linear size index with
\tilde{O}(1)
query time even if all tuples belong in one relation.
Hence, we introduce the approximated version of the nearest neighbor query, called the
ANNQ
problem.

Definition 1.4 (
\varepsilon
-Nearest Neighbor Query Problem).

For a CQ
\mathcal{Q}
and a database
\mathbf{I}
, the goal is to build an index, such that given an arbitrary point
q\in\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q})|}
and a constant parameter
\varepsilon\in(0,1]
, it returns a tuple from
\mathcal{Q}(\mathbf{I})
that is at most
(1+\varepsilon)\cdot\phi(q,\mathcal{Q}(\mathbf{I}))
far from
q
.

We use

\texttt{ANNQ}(\mathcal{Q},\mathbf{I},q)
to denote an answer to point query
q
over
\mathcal{Q}(\mathbf{I})
, i.e.,

\phi(q,\texttt{ANNQ}(\mathcal{Q},\mathbf{I},q))\leq(1+\varepsilon)\phi(q,\mathcal{Q}(\mathbf{I}))
.

1.3.
Our Results

In this paper, we propose efficient indexes for spatial conjunctive queries, achieving a better tradeoff between space usage and query time. Our main contributions are summarized below (see Table
1
).

•

We show conditional lower bounds for
RCQ
and
ANNQ
problems on
k
-star and
k
-path queries, using the
k
-set-disjointness conjecture
and the
k
-path-reachability conjecture
, respectively. In particular, we show that any index for the
RCQ
problem (or
ANNQ
problem) with query time
T
must use at least
\Omega(N+N^{k}/T^{k})
space for
k
-star queries,
(in fact, this lower bound can be extended to any
hierarchical CQ
),
and
\Omega(N+N^{2}/T^{2/(k-1)})
space for
k
-path queries.
(Section
3
)

•

We design near-optimal indexes for the
RCQ
problem on
k
-star and
k
-path queries. In particular, we propose an index for the
RCQ
problem over
k
-star queries with
T
query time using
\tilde{O}(N+N^{k}/T^{k})
space, where
T>0
is any user-defined parameter. Furthermore, we propose an index for the
RCQ
problem over
k
-path queries with
T
query time using
\tilde{O}(N+N^{2}/T^{2/(k-1)})
space.

(Section
4
)

•

We design indexes for
RCQ
and
ANNQ
problems on general CQs. We first show an index for
RCQ
and
ANNQ
problems on generalized
k
-star queries with
T
query time and
\tilde{O}(N+N^{k}/T^{k-1})
space. We extend it to any hierarchical query
\mathcal{Q}
with
T
query time and
\displaystyle{\tilde{O}\left(\min_{\ell\in\{0,\ldots,\mathcal{L}-1\}}\frac{N^{m}}{T^{(m-1)/(\ell+1)}}+N^{m_{\ell+1}}\right)}
space, where
\mathcal{L}
is the depth of the attribute tree of
\mathcal{Q}
, and
m_{\ell+1}
is the maximum number of leaf nodes in the subtree rooted at a node of level
\ell+1
in the attribute tree of
\mathcal{Q}
. We then extend this result to arbitrary CQs using hypertree decomposition techniques.
(Section
5
)

•

While we mostly focus on the tradeoffs between space usage and query time, for all indexes above we also analyze their preprocessing time. Based on the preprocessing and query time, we show how our new indexes can be used to improve the running time of known relational algorithms for clustering problems over the results of conjunctive queries
(
esmailpour2025improved
)
(relational clustering).
In certain cases, our indexes yield a
\sqrt{N}
-factor improvement in the runtime of state-of-the-art relational clustering algorithms.

(Section
6
)
.

•

Our new indexes are not only of theoretical interest but also practical and easy to implement. We evaluate their performance by implementing them and comparing their query time and space usage against known baseline indexes on real-world and synthetic datasets.
While known baselines have either super-linear query time or high space consumption, our indexes provide the best space-time tradeoffs.
(Appendix
E
)

Even though the space complexity of our index for a hierarchical or general CQ seems high or complicated, we show its strength using a simple example. Consider a full CQ
R_{1}(A,B,D)\Join R_{2}(A,B,E)\Join R_{3}(A,C,F)\Join R_{4}(A,C,G)
.
As we discussed above, there are two known indexes for spatial CQs, (for both
RCQ
and
ANNQ
). An index of size
O(N)
can be used so that each query takes
\tilde{O}(N)
time. Alternatively, an index of size
\tilde{O}(N^{4})
can be used so that each query takes
\tilde{O}(1)
time. Using our result for hierarchical queries, we can construct an index of
\tilde{O}(N^{2})
space so that each query takes
\tilde{O}(\sqrt{N})
time. In some sense, our new indexes balance the space-time tradeoff between the two known extremes.
Overall, we do not claim that our new indexes dominate both the space and the query time of the known indexes. Instead, our new indexes provide a better tradeoff between space and query time. More specifically, our indexes use less space than materializing all join results, and at the same time, they achieve sublinear query time. To the best of our knowledge, no such index was known before for SCQs.

Related Work

Recently,
space-tradeoff indexes have been studied for reporting, enumeration, or intersection queries on graphs
(
agarwal2014space
;
patrascu2014distance
;
cohen2010hardness
;
goldstein2017conditional
;
xirogiannopoulos2017extracting
;
agarwal2011approximate
)
and conjunctive queries in databases

(
deep2023general
;
zhao2023space
;
deep2018compressed
;
kara2020trade
;
kara2023conjunctive
)
.
However, none considered spatial queries (such as range counting or approximate nearest neighbor queries) or counting queries so
RCQ
and
ANNQ
problems cannot be solved using these methods.

Deng et al.
(
deng2023space
)
studied space-query tradeoffs for range subgraph counting and enumeration. Given a graph
G(V,E)
with
n
nodes and
m
edges, each node
v\in V
is associated with a value
x_{v}\in\mathbb{R}
.
For a general pattern
Q
of constant size (for example,
k
-star subgraph), they construct an index of
\tilde{O}(n^{2})
space such that given a query interval
\delta
, it returns the number of
Q
-type subgraphs in
G
in the range
\delta
. A
Q
-type subgraph
H
in
G
is in the range
\delta
if for every node
v\in H
it holds
x_{v}\in\delta
. They also improve this index for some special types of subgraphs such as
k
-cliques. While their index can handle range counting queries in temporal graphs, and their graph-based indexes can be extended to relational data (similar to our case), their indexes are heavily based on the fact that the query interval
\delta
is the same across all graph nodes. In our problem, we allow different ranges across different attributes. Their results do not hold in our setting.
Even worse, in Section
3
, we show lower bounds that prevent us from having quadratic space index with
\tilde{O}(1)
query time for every CQ.

Wang et al.
(
wang2023index
)
studied the
set intersection problem with post filtering. Given a collection of sets
S_{1},\ldots,S_{n}
, the goal is to construct an index such that given two set ids
a,b
the index answers
F(S_{a}\cap S_{b})
, where
F(\cdot)
is a filtering function, such as the skyline, the convex hull, and the
k
-nearest items in
S_{a}\cap S_{b}
to a query item
q
. They derive both lower bounds (using the set disjointness conjecture) and design indexes with low space and low query time for common filtering functions
F
. This work does not use ranges over the sets and does not consider relational data, so their methods cannot be directly used to solve our problems.

There is also a lot of work on
similarity join queries

(
agarwal2021dynamic
;
mamoulis2001multiway
;
wangoptimal
;
abo2022complexity
)
where geometric objects (such as points or rectangles) are stored as tuples in database tables. The goal is to report or count all the joined objects/tuples between two (or more) tables.
There are different definitions of the similarity join operator. For example, two objects (points) are joined if their distance exceeds a threshold
\tau
, or two objects (rectangles) are joined if they intersect.
These problems do not consider geometric queries on the attributes of the database, so their techniques cannot be used in our problems.

Definition 3.1 (

Any index answering

Proof.

The reductions from

Given an instance of the

We next show that the

First, assume that the

Near-Optimal Indexes

We now propose indexes for the
RCQ
problem on
\mathcal{Q}_{\mathsf{star}}^{k}
and
\mathcal{Q}_{\mathsf{path}}^{k}
.
In the end, we show some additional conjunctive queries where

can be solved near-optimally.

.

4.1.
Star Queries

Main idea

Each relation
R_{i}
is first sorted by attribute
A_{i}
and partitioned into fixed-size blocks, with each block’s attribute values encapsulated within a minimal bounding interval. A one-dimensional range tree is constructed for each attribute, where leaf nodes store blocks of tuples, and inner nodes store unions of child node blocks. For every combination of tree nodes across attributes, we precompute and store tuple counts corresponding to block intersections. Given a query range, we locate relevant blocks using range trees: Blocks fully contained in the range contribute directly to the count (their count has been precomputed). Partially intersected blocks are processed by iterating over their tuples, and for each such tuple
t
, count the query results using a secondary primitive index that filters tuples based on
\pi_{\mathcal{B}}(t)
.

Primitive index

Before describing the optimal index, we show the following primitive index to count the number of results from
\mathcal{Q}_{\mathsf{star}}^{k}\cap\mathcal{R}
whose joined tuples have a fixed projection
b

on the attributes
\mathcal{B}
.

Lemma 4.1.

Given
\mathcal{Q}_{\mathsf{star}}^{k}
and a database
\mathbf{I}
of size
N
, there exists an index
\mathcal{D}
of
\tilde{O}(N)
space, such that, given a query tuple
b\in\mathbb{R}^{|\mathcal{B}|}
and a hyper-rectangle
\mathcal{R}\in\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q}_{\mathsf{star}}^{k})|}
, the index
\mathcal{D}
has a procedure
\mathcal{D}.\mathsf{count}(b,\mathcal{R})
that returns the count
|\{t\in\mathcal{Q}_{\mathsf{star}}^{k}(\mathbf{I})\mid t\in\mathcal{R},\forall i\in[k],\exists t_{i}\in R_{i}:\pi_{\mathcal{A}_{i}}(t_{i})=\pi_{\mathcal{A}_{i}}(t),\pi_{\mathcal{B}}(t_{i})=b\}|
in
\tilde{O}(1)
time.

In other words, if
\mathcal{Q}_{\mathsf{star}}^{k}[b]
is the query obtained from
\mathcal{Q}_{\mathsf{star}}^{k}
by adding the condition
\mathcal{B}=b
to its body,
then
\mathcal{D}.\mathsf{count}(b,\mathcal{R})={\texttt{RCQ}}(\mathcal{Q}_{\mathsf{star}}^{k}[b],\mathbf{I},\mathcal{R})
.

We start with a simpler case of the problem, where
\mathcal{Q}_{\mathsf{star}}^{k}
contains exactly one attribute
A_{i}
in
\mathcal{A}_{i}
, for
i\in[k]
, and precisely one attribute
B\in\mathcal{B}
.
Lastly, we extend our index to the
k
-star query with any (constant) number of attributes.

Index construction

For each
i\in[k]
we first sort and order all the tuples in
R_{i}
based on their value of
A_{i}
in ascending order, and store the sorted tuples of
R_{i}
, in a list denoted by
S_{i}
. Let
s_{i,j}
denote the
j
’th tuple in
S_{i}
and let
\alpha
be any integer parameter such that
1\leq\alpha\leq N
. We divide each
S_{i}
, into
\frac{N}{\alpha}
blocks of size
\alpha
. Let
C_{i}
be the set of blocks in
S_{i}
and let
C_{i,j}
denote the
j
’th block of
S_{i}
, i.e., for each
i\in[k]
, tuples
s_{i,[1,\alpha]}
(the first
\alpha
tuples of
S_{i}
) belong to the block
C_{i,1}
, tuples
s_{i,[\alpha+1,2\alpha]}
belong to the block
C_{i,2}
, and so on.
Let
I_{i,j}
be the smallest interval that contains all values in
\pi_{A_{i}}(C_{i,j})
and let
I_{i}=\{I_{i,j}\mid j\in[N/\alpha]\}
be the set of all these smallest intervals.
For every
i\in[k]
, we build a binary search tree (
1
-dimensional range-tree)
\mathcal{T}_{i}
on the intervals
I_{i}
, i.e., the
j
-th leaf node of the tree corresponds to
I_{i,j}\in I_{i}
(we note that intervals in
I_{i}
do not intersect in their interiors). If
u
is the
j
-th leaf node of
\mathcal{T}_{i}
then it stores the block
C_{i}^{(u)}=C_{i,j}
. If
u
is an inner node of
\mathcal{T}_{i}
, then it stores a block that includes the union of all blocks in the leaf nodes of the subtree rooted at
u
. More specifically, if
u

has children
v,w
, then we set
C_{i}^{(u)}=C_{i}^{(v)}\cup C_{i}^{(w)}
.
Every node
u
is also associated with the corresponding interval
I_{i}^{(u)}
, which is the smallest interval that contains all values in
\pi_{A_{i}}(C_{i}^{(u)})
.
For every combination of nodes
u_{1}\in\mathcal{T}_{1},\ldots,u_{k}\in\mathcal{T}_{k}
, we compute and store
n_{u_{1},\ldots,u_{k}}=|\{t\in\mathcal{Q}_{\mathsf{star}}^{k}(\mathbf{I})\mid\forall i\in[k],\pi_{{\mathbf{A}}_{i}}(t)\in C_{i}^{(u_{i})}\}|
,
i.e., the number of query results whose projection on
{\mathbf{A}}_{i}=\{A_{i},B\}
is contained in the block
C_{i}^{(u_{i})}
for every
i\in[k]
.
Finally, we construct the index
\mathcal{D}
from Lemma
4.1
over the query
\mathcal{Q}_{\mathsf{star}}^{k}
and then database instance
\mathbf{I}
.

Lemma 4.2.

The space of the constructed index is
\tilde{O}(N+N^{k}/\alpha^{k})
and its preprocessing time is
\tilde{O}(N+N^{k+1}/\alpha^{k+1})
.

Query procedure

Given a query rectangle
\mathcal{R}\in\mathbb{R}^{k}
, let
\mathcal{R}_{i}=\pi_{A_{i}}(\mathcal{R})=[l_{i},r_{i}]
be
\mathcal{R}
’s interval on
A_{i}
.
We search on
\mathcal{T}_{i}
using the range
\mathcal{R}_{i}
. Let
\mathcal{I}_{i}\subseteq\mathcal{R}_{i}
be the largest interval that does not partially intersect any block in the leaf nodes of the tree. Notice that it might be the case that
\mathcal{I}_{i}=\emptyset
.
There are
\mu_{i}=\tilde{O}(1)
canonical nodes
U_{i}=\{u_{(i,1)},\ldots,u_{(i,\mu_{i})}\}
in
\mathcal{T}_{i}
such that

\{r\in R_{i}\mid\pi_{A_{i}}(r)\in\mathcal{I}_{i}\}=\bigcup_{h\in[\mu_{i}]}C_{i}^{(u_{(i,h)})}
.
Using precomputed values, we compute the following sum over all combinations
u_{(1,j_{1})}\in U_{1},\ldots,u_{(k,j_{k})}\in U_{k}
,
\ell_{1}=\sum_{u_{(1,j_{1})}\in U_{1},\ldots,u_{(k,j_{k})}\in U_{k}}n_{u_{(1,j_{1})},\ldots,u_{(k,j_{k})}}
.
By definition,
\ell_{1}
computes the number of tuples in
\mathcal{Q}(\mathbf{I})
whose projections in
A_{1},\ldots,A_{k}
lie in blocks completely inside
\mathcal{R}
.
It remains to handle the blocks partially intersected by
\mathcal{R}
. For every
i\in[k]
, there are at most
2
blocks in the leaf level that are partially intersected by
\mathcal{R}_{i}
. We visit the relations in order
R_{1},R_{2},\ldots,R_{k}
. We first fix the relation
R_{1}
. Assume that the blocks
C_{1,j_{1}}
and
C_{1,j^{\prime}_{1}}
are partially intersected by
\mathcal{R}_{1}
. For every tuple
t\in C_{1,j_{1}}\cup C_{i,j^{\prime}_{1}}
such that
\pi_{A_{1}}(t)\in\mathcal{R}_{1}
we set
b=\pi_{B}(t)
and the rectangle
\mathcal{R}_{t}=[\pi_{A_{1}}(t),\pi_{A_{1}}(t)]\times\mathcal{R}_{2}\times\mathcal{R}_{3}\times\ldots\times\mathcal{R}_{k}
. We run a query in the primitive index
\mathcal{D}
giving the tuple
b
and the rectangle
\mathcal{R}_{t}
as the input to the query. We set
x_{t}=\mathcal{D}.\mathsf{count}(b,\mathcal{R}_{t})
.
We compute,

\ell_{2}^{(1)}=\sum_{t\in C_{1,j_{1}}\cup C_{1,j^{\prime}_{1}},\pi_{A_{1}}(t)\in\mathcal{R}_{1}}x_{t}
.
For any other relation
R_{i}
with
i\in[2,k]
, we consider the partially intersected blocks, say,
C_{i,j_{i}}
and
C_{i,j^{\prime}_{i}}
. For every tuple
t\in C_{i,j_{i}}\cup C_{i,j^{\prime}_{i}}
such that
\pi_{A_{i}}(t)\in\mathcal{R}_{i}
, we set
b=\pi_{B}(t)
and the rectangle
\mathcal{R}_{t}=\mathcal{I}_{1}\times\mathcal{I}_{2}\times\ldots\times\mathcal{I}_{i-1}\times[\pi_{A_{i}}(t),\pi_{A_{i}}(t)]\times\mathcal{R}_{i+1}\times\mathcal{R}_{k}
.
We run a query in the primitive index
\mathcal{D}
, giving the tuple
b
and the rectangle
\mathcal{R}_{t}
as the input to the query. We set
x_{t}=\mathcal{D}.\mathsf{count}(b,\mathcal{R}_{t})
.
We compute,

\ell_{2}^{(i)}=\sum_{t\in C_{i,j_{i}}\cup C_{i,j^{\prime}_{i}},\pi_{A_{i}}(t)\in\mathcal{R}_{i}}x_{t}
.
In the end, we return
\ell_{1}+\sum_{i\in[k]}\ell_{2}^{(i)}
.

We show the correctness of our index in Appendix
B
.

Query time

The canonical nodes
U_{i}

are derived in
\tilde{O}(1)
time, by the query procedure of range trees. Since there are
\tilde{O}(1)
canonical nodes in every tree
\mathcal{T}_{i}
, all combinations of canonical nodes over the
k
different trees are
\tilde{O}(1)
, so the value
\ell_{1}
is computed in
\tilde{O}(1)
time. Next, every value
\ell_{2}^{(i)}
is computed by running
O(\alpha)
queries to the primitive index
\mathcal{D}
. Every query on
\mathcal{D}
takes
\tilde{O}(1)
time, so in total the query procedure takes
\tilde{O}(k\cdot\alpha)=\tilde{O}(\alpha)
time.

In Appendix
B
, we straightforwardly extend our index to handle star queries where
\mathcal{A}_{i}
,
\mathcal{B}
contain more than one attributes.
We conclude with the next theorem.

Theorem 4.3.

Given a star CQ
\mathcal{Q}_{\mathsf{star}}^{k}
on a database
\mathbf{I}
of size
N
, and a parameter
1\leq T\leq N
, there exists an index of
\tilde{O}(N+N^{k}/T^{k})
space that is constructed in
\tilde{O}(N+N^{k+1}/T^{k+1})
time, such that given a hyper-rectangle
\mathcal{R}\in\mathbb{R}^{|{\mathsf{head}}(\mathcal{Q}_{\mathsf{star}}^{k})|}
, it returns

in

query time.

4.2.
Path queries

Main idea

We construct an index for efficiently processing path queries by leveraging hierarchical data partitioning and precomputed aggregations, similarly to star queries. The index is built inductively: for
k=2
, the problem reduces to a star query, and for general
k
, we assume an index exists for
(k-1)
-path queries. The tuples in the first and last relations are sorted based on their respective attributes and divided into fixed-size blocks, encapsulated within minimal bounding intervals. One-dimensional range trees are built over these intervals, where leaf nodes store blocks, and inner nodes store unions of child node blocks. For every combination of tree nodes across attributes, we precompute and store tuple counts corresponding to block intersections.
Given a query range, we locate relevant blocks using the range trees: blocks fully contained in the range contribute directly to the count (their count has been precomputed).
Partially intersected blocks are resolved by iterating over their tuples, and for each such tuple
t
in
R_{1}
(resp.
R_{k}
), count the query results given that
t
is the tuple in
R_{1}
(resp
R_{k}
) by querying the
(k-1)
-path index.

We start with a simpler instance of the problem, where
\mathcal{Q}_{\mathsf{path}}^{k}
contains exactly one attribute
A_{1}\in\mathcal{A}_{1}
,
A_{2}\in\mathcal{A}_{2}
, and
B_{i}\in\mathcal{B}_{i}
for
i\in[k-1]
. Hence,
\mathcal{Q}_{\mathsf{path}}^{k}(A_{1},A_{2}):-R_{1}(A_{1},B_{1}),\ldots,R_{k}(B_{k},A_{2})
. In the end we extend our index to the general path query.

Index construction

We show an inductive construction of our new index. For
k=2
, the star query is equivalent to the
2
-path query so let
\mathcal{D}_{2}
be the index from Theorem
4.3
.
Without loss of generality, assume that the index for the
RCQ
problem on any
(k-1)
-path query is known and denoted by
\mathcal{D}_{k-1}
. We show the construction of an index
\mathcal{D}_{k}
for the
RCQ
-problem on
\mathcal{Q}_{\mathsf{path}}^{k}
.

We first sort and order all the tuples in
R_{1}
(resp.
R_{k}
) based on their values of
A_{1}
(resp.
A_{2}
) in ascending order, and store the sorted tuples of
R_{1}
(resp.
R_{k}
), in a list denoted by
S_{1}
(resp.
S_{k}
).
Let
\alpha
be any integer parameter between
1
and
N
. We divide
S_{1}
(resp.
S_{k}
), into
\frac{N}{\alpha}
blocks of size
\alpha
. Let
C_{1}
(resp.
C_{k}
) be the set of blocks in
S_{1}
(resp.
S_{k}
) and let
C_{1,j}
(resp.
C_{k,j}
) denote the
j
-th block of
S_{1}
(resp.
S_{k}
).
Let
I_{1,j}
(resp.
I_{2,j}
) be the smallest interval that contains all values in
\pi_{A_{1}}(C_{1,j})
(resp.
\pi_{A_{2}}(C_{k,j})
) and let
I_{1}
(resp.
I_{2}
) be the set of these intervals in
S_{1}
(resp.
S_{k}
).
We build a binary search tree (
1
-dimensional range-tree)
\mathcal{T}_{1}
(resp.
\mathcal{T}_{2}

5.1.
Generalized
k
-Star Queries

We describe an index for answering
RCQ
and

in time
T
using
\tilde{O}(N^{k}/T^{k-1})
space.

Main idea

Our index construction partitions values of attribute(s)
\mathcal{B}
into two categories:
heavy
and
light
, based on the number of tuples associated with each value.
We precompute and store all join results where the projection on
\mathcal{B}
belongs to the light set, constructing a range counting index
D^{L}
over these results. For each heavy value
b_{i}
, we construct separate range counting indexes
D^{H}_{i,j}
for each relation
R_{j}
. Given a query rectangle, we first use
D^{L}
to count results with light projections. Then, for each heavy value, we compute the number of tuples in each relation within the query range using

and aggregate these counts across relations. The final result is the sum of both counts.
Intuitively, light values generate only a small number of join results (so

has small size) and the heavy values are limited (making their traversal efficient).

Index construction

Let
\alpha
be any integer parameter between
1
and
N

\mathcal{B}

b_{i}

and

b_{i}

\mathcal{B}
attribute(s) i.e.,
Q_{L}=\{t\in\mathcal{Q}_{\mathsf{star}}^{k}(\mathbf{I})|\pi_{\mathcal{B}}(t)\in L\}=\bigcup\limits_{b_{i}\in L}(\Join_{j\in[k]}R_{j}^{b_{i}})
.
Then we construct a range counting index

(from Theorem
2.1
) over the points in
Q_{L}

We are given a query rectangle

5.2.
Hierarchical Queries

In this section, we study the
RCQ
and
ANNQ
problems on hierarchical queries.
Hierarchical queries can be thought of as a generalization of the star queries. To answer
RCQ
queries, we build the attribute tree that always exists for hierarchical queries.

Definition 5.4 (Attribute Tree).

The
attribute tree
of a hierarchical CQ
\mathcal{Q}
over the set of relations
{\mathbf{R}}
and the attributes
{\mathbf{A}}
, denoted by
\mathcal{T}(\mathcal{Q})
is a rooted tree such that each node corresponds to an attribute in
{\mathbf{A}}
;
x
is a descendant of
y
if
E_{x}\subseteq E_{y}
;
and each path from the root to a leaf node corresponds to a relation in
{\mathbf{R}}
.

If
\mathcal{T}(\mathcal{Q})
is not connected, it is easy to see that we can solve
RCQ
on each connected component and then multiply all the answers to get an answer for the whole query. Thus, we only focus on the case where
\mathcal{T}(\mathcal{Q})
is connected and propose the following index for solving
RCQ
on full hierarchical queries.

Main idea

Our index construction follows a similar strategy to the previous method, where values of a key attribute are categorized as
heavy
or
light
to optimize query performance. However, instead of partitioning the values based on attributes
\mathcal{B}
, we partition the the tuples of the root node
r
in the attribute tree as light and heavy.
We precompute all join results where the projection on
r
belongs to the light set, constructing a range counting index
D^{L}
over these results.
For a heavy value
r_{i}

instead of indexing each relation separately as in the previous approach, we group relations based on shared child attributes and construct range counting indexes
D^{H}_{i,c}
for each child attribute
c
. Given a query rectangle, we first retrieve results for light values using
D^{L}
. For each heavy value, we compute relevant tuple counts for each child attribute and aggregate them across all children.

Index construction

Let
r
be the root attribute in
\mathcal{T}(\mathcal{Q})
and let

be the children of the root that we call the

k
relations in
{\mathbf{R}}
. Let
\alpha
be any integer parameter between
1
and

whose projection on

is

{\texttt{adom}}(r)

H=\{r_{i}\in{\texttt{adom}}(r)|\frac{N}{\alpha}\leq|T_{i}|\}

r_{i}

be the set of light
r_{i}

We construct all the results having light value on the

By the definition of the light values, we know that for each

6.
Improved Relational Algorithms

We show how our new indexes are used to improve the running time of known algorithms in the relational setting.
There is a recent line of work solving combinatorial problems on the results of a CQ without explicitly computing
\mathcal{Q}(\mathbf{I})
; for example enumeration
(
deep2022ranked
;
deep2021ranked
;
tziavelis2020optimal
)
, quantiles
(
tziavelis2023efficient
)
,
direct access
(
carmeli2023tractable
)
, diversity
(
agarwal2025computing
;
arenas2024towards
;
merkl2025diversity
)
, top-
k

(
tziavelis2020optimal
)
, and clustering
(
agarwal2025computing
;
chen2022coresets
;
curtin2020rk
;
esmailpour2025improved
;
moseley2021relational
)
.
In the rest of this section for simplicity, we focus on acyclic queries
\mathcal{Q}

(
beeri1983desirability
;
fagin1983degrees
)
.

One of the main techniques in the papers above is to use oracles (indexes in our case) to get useful statistics over the results of a CQ. For example, in relational clustering
(
esmailpour2025improved
)
(
\mathcal{K}
-median and
\mathcal{K}
-means clustering problems) the authors used a (counting) oracle to compute
|\mathcal{R}\cap\mathcal{Q}(\mathbf{I})|
given a rectangle
\mathcal{R}
, or use a (sampling) oracle to get a sample from
\mathcal{R}\cap\mathcal{Q}(\mathbf{I})
uniformly at random. In all cases, they describe straightforward oracles/indexes with
O(N)
query time. The running time all the proposed algorithms in
(
esmailpour2025improved
)
can be written as
O(\tau\cdot\mathcal{T}+f(\mathcal{K}^{2}))
, where
\tau
is the number of queries to the oracles,
\mathcal{T}
is the query time of the oracle, and
f(\mathcal{K}^{2})
is the runtime of a clustering algorithm in the standard computational setting (i.e., input data stored in one table) over an input of size
\mathcal{K}^{2}
. More specifically, the authors describe a deterministic
O(\mathcal{K}^{2d+2}\cdot N+f(\mathcal{K}^{2}))
time algorithm performing
\tau=O(\mathcal{K}^{2d+2})
queries to a counting oracle and a randomized
O(\mathcal{K}^{2}\cdot N+f(\mathcal{K}^{2}))
time algorithm performing
\tau=O(\mathcal{K}^{2})
queries to a counting and sampling oracle, where
d=|{\mathsf{head}}(\mathcal{Q})|
.
For simplicity we skip the term
f(\mathcal{K}^{2})
from the running time because in most cases, using the fastest algorithms for clustering in the standard computational setting
(
har2003coresets
)
,
f(\mathcal{K}^{2})\ll\mathcal{K}^{2}\cdot N
.
Both algorithms return a
(2+\varepsilon)
-approximation solution for the relational
\mathcal{K}
-median problem and a
(4+\varepsilon)
-approximation solution for the relational
\mathcal{K}
-means problem, where
\varepsilon
is an arbitrary small constant. We note that these are the fastest known
(2+\varepsilon)
-approximation algorithms (resp.
(4+\varepsilon)
-approximation algorithms) for the relational
\mathcal{K}
-median (resp.
\mathcal{K}
-means) problem.
In the next paragraphs we represent the query and preprocessing time of our indexes over a database instance
\mathbf{I}
of size
N
as
T(N)
and
P(N)
, respectively.

We first consider the deterministic algorithm from
(
esmailpour2025improved
)
, where
\tau=O(\mathcal{K}^{2d+2})
counting oracle queries are executed to compute
|\mathcal{R}\cap\mathcal{Q}(\mathbf{I})|
, given a rectangle
\mathcal{R}
. Consider the query
\mathcal{Q}_{\mathsf{star}}^{k}
. We can use the index from the
RCQ
problem on
k
-star queries to compute
|\mathcal{R}\cap\mathcal{Q}(\mathbf{I})|
when is needed.
Using our result from Theorem
4.3
, the deterministic algorithm runs in
O(P(N)+\tau\cdot T(N))=O(N+\frac{N^{k+1}}{T^{k+1}}+\mathcal{K}^{2d+2}\cdot T)
.
Our new algorithm is faster than the running time proposed in
(
esmailpour2025improved
)
, if
N+\frac{N^{k+1}}{T^{k+1}}+\mathcal{K}^{2d+2}\cdot T\ll\mathcal{K}^{2d+2}\cdot N
. This is indeed the case for larger values of
\mathcal{K}
. For example, assume
\mathcal{K}=N^{1/(2d+2)}
. Then the deterministic algorithm from
(
esmailpour2025improved
)
runs in
O(N^{2})
time, while our implementation runs in
O(\frac{N^{k+1}}{T^{k+1}}+N\cdot T)
. By selecting
T=N^{k/(k+2)}
, the running time of our implementation is
O(N^{(2k+2)/(k+2)})
which is always asymptotically smaller than
O(N^{2})
. For example, for
k=2
(matrix query) our new algorithm runs in
O(N^{3/2})
which is faster than the algorithm in
(
esmailpour2025improved
)
, by a
N^{1/2}
factor.
We can make similar arguments for the
\mathcal{Q}_{\mathsf{path}}^{k}
query using our index in Theorem
4.5
, and general queries using our indexes from Section
5
.

Next, we consider the randomized algorithm from
(
esmailpour2025improved
)
. It requires a counting oracle and a sampling oracle. Interestingly, by making slight modifications, all our indexes from Section
5
can be extended to return uniform samples in
\mathcal{R}\cap\mathcal{Q}(\mathbf{I})
with the same guarantees as in the
RCQ
problem. We call it the Range Sampling Query (
RSQ
) problem. We show the details in Appendix
D
.
The randomized algorithm from
(
esmailpour2025improved
)
runs in
\tilde{O}(\mathcal{K}^{2}\cdot N)
time, performing
\tau=O(\mathcal{K}^{2})
queries to the counting and sampling oracles. Consider any generalized
k
-star query
\mathcal{Q}_{\mathsf{star}}^{k}
. Using our index from Theorem
5.2
, the randomized algorithm can be implemented in
O(N+\frac{N^{k}}{T^{k-1}}+\mathcal{K}^{2}\cdot T)
time. The new algorithm is faster than the proposed algorithm in
(
esmailpour2025improved
)
, if
N+\frac{N^{k}}{T^{k-1}}+\mathcal{K}^{2}\cdot T\ll\mathcal{K}^{2}\cdot N
. If
\mathcal{K}=N^{1/2}
then the randomized algorithm from
(
esmailpour2025improved
)
runs in
O(N^{2})
time, while our implementation runs in
O(\frac{N^{k}}{T^{k-1}}+N\cdot T)
. By selecting,
T=N^{(k-1)/k}
, the running time of our algorithm is
O(N^{(2k-1)/k})
which is asymptotically smaller than
O(N^{2})
for every
k>1
.
We can make similar arguments for hierarchical and general queries using the results from Theorems
5.5
,
5.6
.
We conclude with the next theorem.

Theorem 6.1.

Given an acyclic CQ
\mathcal{Q}
, a database instance
\mathbf{I}
of size
N
, a parameter
\mathcal{K}\in[1,N]
, and a constant parameter
\varepsilon\in(0,1)
, there exists a deterministic (resp. randomized)
(2+\varepsilon)
-approximation algorithm for the relational
\mathcal{K}
-median problem that runs in
O(\min\{\mathcal{K}^{2d+2}\cdot N,P(N)\!+\!\mathcal{K}^{2d+2}\!\cdot\!T(N)\}\!+\!f(\mathcal{K}^{2}))
time (resp.
O(\min\{\mathcal{K}^{2}\!\cdot\!N,P(N)\!+\!\mathcal{K}^{2}\cdot T(N)\}\!+\!f(\mathcal{K}^{2}))
time), where
d=|{\mathsf{head}}(\mathcal{Q})|
,
f(\mathcal{K}^{2})
is the time complexity of a
\mathcal{K}
-median clustering algorithm in the standard computational setting,
P(N)
is the preprocessing, and
T(N)
is the query time of the new proposed indexes for the
RCQ
and
RSQ
problems.
The algorithms can be extended to
(4+\varepsilon)
-approximation algorithms for the relational
\mathcal{K}
-means problem with the same time guarantees.

7.
Conclusion

In this paper, we design indexes with space-time tradeoffs for spatial conjunctive queries.
There are multiple interesting open problems derived from this work.
While we showed near-optimal index for the
RCQ
problem on
k
-star and
k
-path queries, it is interesting to study whether there exists a near-optimal index for the
ANNQ
problem on
k
-star and
k
-path queries. Furthermore, an interesting problem is to close the gap between the space-time lower and upper bound for
RCQ
and
ANNQ
on hierarchical and general CQs.

Our ideas can be extended to handle the

Instead of using the range tree indexes from Theorem

2.2
. More specifically, we construct the ANN index
D^{L}
on

on
\pi_{\mathcal{A}_{j}}(R_{j}^{b_{i}})

Given a query point

t^{(H)}_{i,j}=D^{H}_{i,j}(\pi_{\mathcal{A}_{j}}(q))
for every

t_{i}^{(H)}=(t_{i,1}^{(H)},t_{i,2}^{(H)},\ldots,t_{i,k}^{(H)},b_{i})

t^{(H)}=\argmin_{t_{i}^{(H)}}\phi(q,t_{i}^{(H)})

We return
t^{\prime}=\argmin_{t\in\{t^{(L)},t^{(H)}\}}\phi(q,t)
.

Lemma C.1.

It holds that
\phi(q,t^{\prime})\leq(1+\varepsilon)\phi(q,\mathcal{Q}_{\mathsf{star}}^{k}(\mathbf{I}))
.

Proof.

Let
t^{*}
be the nearest neighbor in
\mathcal{Q}_{\mathsf{star}}^{k}
from the point query
q
. If
\pi_{B}(t^{*})\in L
, by definition
\phi(q,t^{\prime})\leq\phi(q,t^{(L)})\leq(1+\varepsilon)\phi(q,t^{*})
. Then, we assume
\pi_{\mathcal{B}}(t^{*})=b_{i}\in H
. By definition of
D_{i,j}^{H}
, we have
\phi(\pi_{\mathcal{A}_{j}}(q),t_{i,j}^{(H)})\leq(1+\varepsilon)\phi(\pi_{\mathcal{A}_{j}}(q),\pi_{\mathcal{A}_{j}}(t^{*}))
.
Hence,

\displaystyle\phi(q,t^{(H)})\!\!\leq\!\!\phi(q,t_{i}^{(H)})\!=\!\!\sqrt{\sum_{j\in[k]}\!\!\!\phi^{2}\left(\pi_{\mathcal{A}_{j}}(q),t_{i,j}^{(H)}\right)}\!\!\leq\!\!\sqrt{\sum_{j\in[k]}\!\!(1+\varepsilon)^{2}\phi^{2}\left(\pi_{\mathcal{A}_{j}}(q),\pi_{A_{j}}(t^{*})\right)}\!=\!(1+\varepsilon)\phi(q,t^{*}).

\mathcal{Q}
over a database instance
\mathbf{I}
of size
N
the goal is to construct an index, such that given a query rectangle
\mathcal{R}\in\mathbb{R}^{|{\mathsf{head}}|}

\mathcal{R}\cap\mathcal{Q}(\mathbf{I})
is returned uniformly at random. We show that all indexes from Section
5
can be straightforwardly modified to to solve the
RSQ
problem.

First, we claim that we can focus on full CQs as in Lemma
5.1
. Indeed, if we have an index
D
for the
RSQ
problem on a full CQ
\mathcal{Q}^{\prime}
oer a set of attributes
{\mathbf{A}}
, then we can use the same index with the same guarantees for the
RSQ
problem on the CQ
\mathcal{Q}
with the same body attributes and relations as
\mathcal{Q}^{\prime}
, where
{\mathsf{head}}(\mathcal{Q})\subset{\mathbf{A}}

E.1.
Setup

All our experiments were implemented in C++ and performed on a Linux machine with a 3.5 GHz Intel Core i9 processor and 128 GB of memory. All the codes are public at
(
code

.

Queries and Algorithms

We evaluate all algorithms over the matrix query
\mathcal{Q}_{\textsf{matrix}}(A,C):-R_{1}(A,B),R_{2}(C,B)
, where
R_{1}
and
R_{2}
are relations from different datasets
I
, as described later. We use multiple randomly generated rectangles
\mathcal{R}=[l_{A},r_{A}]\times[l_{C}\times r_{C}]
and report the average query time and memory used for answering
{\texttt{RCQ}}(\mathcal{Q}_{\textsf{matrix}},I,\mathcal{R})
. The exact process of generating the rectangles is shown later in Section
E.2
.
We compare our indexes with the following three baselines:

•

(\textbf{RangeS})
This is a version of Yannakakis
(
yannakakis1981algorithms
)
algorithm specifically optimized for
\mathcal{Q}_{\textsf{matrix}}
. For each value
b\in{\texttt{adom}}(B)
, we store two sorted lists in the preprocessing time. One containing the list of
A
-values
\bar{\pi}_{A}(\sigma_{B=b}R_{1})
and one containing the
C
-values
\bar{\pi}_{C}(\sigma_{B=b}R_{2})
, denoted by
L^{b}_{1}
and
L^{b}_{2}
, respectively. When a query
\mathcal{R}=[l_{A},r_{A}]\times[l_{C}\times r_{C}]
comes, we go over each
b\in{\texttt{adom}}(B)
, and obtain two counters
\Delta^{b}_{1}=|\{a\in L^{b}_{1}:l_{A}\leq a\leq r_{A}\}|
and
\Delta^{b}_{2}=|\{c\in L^{b}_{2}:l_{C}\leq c\leq r_{C}\}|
the number of values satisfying the given ranges in
L^{b}_{1}
and
L^{b}_{2}
, respectively. Finally, we return
\sum_{b\in{\texttt{adom}}(B)}\Delta^{b}_{1}\cdot\Delta^{b}_{2}
. For each
b
, we run a binary search on
L^{b}_{1}
and
L^{b}_{2}
to obtain
\Delta^{b}_{1}
and
\Delta^{b}_{2}
, respectively.

•

(
RangeT
) We materialize all the results of the underlying CQ in a range tree index and then use the standard range tree query procedure to answer
RCQ
queries.

•

(
RangeG
) We materialize all the results of the underlying CQ in a table and then use the GIST spatial index from the PostGIS extension of PostgreSQL to answer
RCQ
queries.

We implemented our algorithm for
2
-star queries described in Section
4
, which almost matches the lower bounds and the more general algorithm described in Section
5
. These algorithms are denoted as
NewD
and
NewH
, respectively.
For the implementation of
NewD
, we added the following simple optimization. When a query comes up, we can quickly calculate the number of operations we need to make to answer the query. If this number is larger than the number of distinct values in the active domain of
B
, we use the algorithm
RangeS
instead. Using this trick, we can quickly answer the queries in datasets with a rather small number of different values for the attribute
B
. Moreover, as described before, a tradeoff between memory usage and query time for both algorithms
NewD
and
NewH
can be tuned as desired. We tuned the parameters for these algorithms in different ways, which will be elaborated later.

E.2.
Experimental Results

As mentioned before, the tradeoff between the query time and the memory usage of our algorithms
NewD
and
NewH
can be controlled by changing the parameter
T
as shown in Theorems
4.3
and
5.2
. This can be very useful in practical scenarios where the space is limited since none of the baseline algorithms allow this flexibility, and all of them will use a fixed amount of memory based on the database instance. For the first part of the experiments, we fixed the parameter
T
to be close to
\sqrt{N}
for both of our algorithms. By theorems
4.3
and
5.2
, this results in an asymptotic query time of
\tilde{O}(\sqrt{N})
for both the algorithms while using
O(N)
additional space for the
NewD
algorithm and
O(N^{3/2})
space for the
NewH
algorithm. Note that although
NewH
may use more memory than
NewD
, it can be used on a more generalized set of queries, as shown in Section
5
. For the
taxi
dataset, we omit the results for algorithms
RangeT
and
RangeG
, since they need to materialize all the results in
\mathcal{Q}_{\textsf{matrix}}(\mathbf{I})
. The huge size of
\mathcal{Q}_{\textsf{matrix}}(\mathbf{I})
, as shown in Table
2
, makes it impossible to store all the results on our machine. Hence, it becomes obvious that the baselines
RangeT
and
RangeG
are not practical even in databases with a couple of million tuples.

Memory and Query time

With these settings, the memory usage of algorithms over all the datasets is shown in Figure

\mathcal{R}

(and

(
l_{C}

\mathcal{R}=[l_{A},r_{A}]\times[l_{C},r_{C}]

. We observe that the memory usage of the two indexes
NewD
and
RangeS
is very close to each other and significantly less than all the other baselines. This is as expected since these two indexes are the only ones that use space linear to the input size in theory. On the datasets
synthetic
and

, we can see that the memory usage of

is large and is close to the
RangeT

taxi
and
flights

NewH
shows a much better performance compared to both
RangeT
and
RangeG
. This is because in the
flights
and
taxi
datasets, a small number of different values in the active domain of
B
, contribute to the most number of result tuples in
\mathcal{Q}_{\textsf{matrix}}(\mathbf{I})
. Intuitively, there are only a few crowded airports, and the other airports have significantly fewer flights passing them, or most taxi rides have a fare in a certain range, and there are very few rides that have a very low or very high fare. More precisely, in
flights

4\%
of different values in the active domain of

90\%
of the results in
\mathcal{Q}_{\textsf{matrix}}(\mathbf{I})
, and this percentage is
5\%
for the
taxi

synthetic

35\%
and

NewH
, since it can quickly separate them and take care of them at the query time.
In Figure
8
, we observe that the query time of
RangeT
, beats all the other indexes over all applicable datasets, yet this query performance is not for free since the memory consumption is huge. As we tuned the asymptotic query time complexity of
NewD
and

both equal to
\sqrt{N}
, their performance is close to each other and much better than the baselines except for
RangeT
. It can be seen that
NewD
performs significantly better than

, despite both having similar memory usage. As described above,

performs better on its preferable datasets
taxi
and

while
NewD
performs better on the other datasets. Although

is one of the most commonly used indexes for spatial range counting, we observe that it answers the queries slower than all the other baselines over all the datasets. We note that this index is not designed to answer range counting over Conjunctive Queries. The underlying
R

{\texttt{RCQ}}(\mathcal{Q}_{\textsf{matrix}},\mathbf{I},\mathcal{R})
queries where
\mathcal{R}
has small volume or when it contains a small number of tuples, but it performs significantly worse in average without any restriction on
\mathcal{R}

\mathcal{R}=[l_{A},r_{A}]\times[l_{C},r_{C}]
and ask the algorithms to compute
{\texttt{RCQ}}(\mathcal{Q}_{\textsf{matrix}},\mathbf{I},\mathcal{R})
. We repeat this process 100 times and report the average time in Figures

We can tune the query time of
NewD
and
NewH

RangeS
has a low memory consumption but suffers from a large query time. On the other extreme,
RangeT

Summary

The main strength of
NewH
and
NewD
is their ability to tune the query time based on the available memory. Indeed, when memory usage is out of concern, the best approach is to materialize all the results in
\mathcal{Q}_{\textsf{matrix}}(\mathbf{I})
in an index designed explicitly for range counting queries such as range trees. However, when there is a memory limit, the goal is to answer the counting queries as fast as possible. The experiments show that our indexes can achieve this goal by quickly answering
RCQ
queries while meeting the memory constraint. Neither of our two indexes dominates the other one, and the performance highly depends on the amount of available memory, the input dataset, and the selectivity of the queried ranges.
Moreover, we showed that when the available space is nearly equal to the size of the dataset, our index
NewD
achieves significantly faster query time compared to the baseline
RangeS
, while using almost the same amount of memory.
