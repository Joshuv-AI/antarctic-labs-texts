Understanding Software Engineering Agents Through the Lens of Traceability: An Empirical Study
Ira Ceka, Saurabh Pujar, Shyam Ramji, Luca Buratti, Gail Kaiser, Baishakhi Ray

Abstract
. With the advent of large language models (LLMs), software engineering agents (SWE agents) have emerged as a powerful paradigm for automating a range of software tasks—from code generation and repair to test case synthesis. These agents operate autonomously by interpreting user input and responding to environmental feedback. While various agent architectures have demonstrated strong empirical performance, the internal decision-making workflows that drive their behavior remain poorly understood. Deeper insight into these workflows hold promise for improving both agent reliability and efficiency. In this work, we present the first systematic study of SWE agent behavior through the lens of execution traces. Our contributions are as follows: (1) we propose the first taxonomy of decision-making pathways across five representative agents; (2) using this taxonomy, we identify three core components essential to agent success-bug localization, patch generation, and reproduction test generation-and study each in depth; (3) we study the impact of test generation on successful patch production; and analyze strategies that can lead to successful test generation; (4) we further conduct the first large-scale code clone analysis comparing agent-generated and developer-written patches and provide a qualitative study revealing structural and stylistic differences in patch content. Together, these findings offer novel insights into agent design and open avenues for building agents that are both more effective and more aligned with human development practices.



1.
Introduction

The emergence of large language models (LLMs) has ushered in a new paradigm in software engineering: software engineering agents (SWE agents). SWE agents are autonomous systems that leverage the reasoning and generative capabilities of LLMs to perform complex, multi-step software development tasks. To support such capabilities, SWE agents incorporate planning, self-reflection, and external tool use, including web search, file I/O, static analysis, and debugging—enabling them to decompose high-level objectives, assess their own intermediate outputs, and interact with the broader development ecosystem. As a result, recent research has demonstrated that SWE agents are capable of executing a wide range of software engineering tasks
(
Chen and Jiang 2025
)
, including code synthesis from natural language specifications
(
Wang et al. 2024
)
, fault localization
(
Li et al. 2024
)
, automated test generation
(
Ahmed et al. 2025
)
, and program repair
(
Zhang et al. 2024
;
Xia et al. 2024
)
.

Among these, automated program repair has emerged as a particularly promising application. Traditional repair systems typically rely on manually crafted templates
(
Liu et al. 2019
)
, predefined transformation rules, or search-guided enumeration of patches
(
Le Goues et al. 2019
)
. In contrast, SWE agents offer a more general and adaptive approach. They can ingest structured or unstructured bug reports, localize faults using lightweight static analysis or test-driven diagnosis, synthesize candidate patches, validate them through iterative compilation and test execution, and ultimately decide when and how to apply a fix.
This end-to-end workflow—spanning fault localization, patch synthesis, patch validation, and code integration—broadly mirrors the cognitive processes of a human developer, highlighting the potential of SWE agents to function as autonomous repair assistants.
As such, program repair serves as a compelling benchmark for evaluating the reasoning, generalization, and autonomy of LLM-based SWE agents.

A leading benchmark for evaluating automated program repair agents is SWE-bench
(
Jimenez et al. 2023
)
, which comprises 2,294 real-world tasks curated from 12 actively maintained Python GitHub repositories. Each task is anchored to a specific repository version and accompanied by a natural language issue description, requiring the generation of a candidate patch that resolves the issue. Evaluation is conducted via test execution, including fail-to-pass tests that confirm issue resolution and pass-to-pass tests that check for regression safety. To improve the robustness of the benchmark, OpenAI recently curated a high-quality subset known as SWE-bench Verified
(
OpenAI [n. d.]
)
, consisting of 500 tasks with well-defined and semantically meaningful test cases.

SWE-bench and its Verified variant have quickly become the de facto standard for assessing the capabilities of LLM-based repair systems. They are now widely used in both academic research and industrial settings to evaluate models’ code understanding, reasoning, and patch synthesis abilities. As a result, an increasing number of repair agents—developed across both academic and industrial settings—are being explicitly designed to target this benchmark, with growing emphasis on achieving steady improvements in the number of successfully repaired issues, as reflected in the evolving SWE-bench leader-board
(
swe 2025
)
.

While recent agents have achieved impressive leaderboard scores, such metrics reveal little about how agents reason, where they fail, or how their behavior compares to human developers. As agent development accelerates, there is a growing need for deeper analysis beyond pass/fail outcomes. This work addresses that gap by tracing agents’ full decision-making pipelines—from issue description to patch validation—and framing the investigation through the following research questions:

RQ1: How effective are agents at fixing real-world SWE issues?
We begin by evaluating overall success rates across multiple agents on SWE-bench tasks. We find that agents are generally better at fixing easy bugs—especially the kinds that developers can solve quickly. No single agent is best at everything; each one tends to do well on different types of problems, depending on how it is designed. We also see that when there are more test cases that clearly reproduce the issue, fixing becomes harder, as more tests help prevent overfitting
(
Smith et al. 2015
)
. Overall, these results suggest that stronger agents will need more flexible strategies and better reasoning to handle the harder bugs reliably.

This finding leads us to examine agent design more closely by building a taxonomy of their decision-making pipelines. Despite architectural differences, most agents rely on three core capabilities: bug localization, reproduction test generation, and patch synthesis. Within these, two main strategies emerge—iterative refinement, where steps build on prior outputs, and sampling-based selection, where multiple candidates are generated and the best one is chosen. A key insight is the importance of issue reproduction: without reproducing the failure, agents cannot reliably assess patch correctness. This motivates our second research question.

RQ2: How effective are agents at generating issue-reproducing test cases?
We analyze both behavioral traces and ablation experiments to isolate key contributors to successful test generation. We observe that diverse sampling alone is ineffective when issue descriptions are vague—even with multiple tries agents often repeat the same failed attempts. Adding targeted context, such as the likely buggy file or code region, may help guide the model to generate the test cases. This result suggests that reliable agents should combine natural language inputs with structured signals like bug localization for issue reproduction and repairs.

Having studied how agents may succeed, we next examine how their solutions compare to those written by humans:

RQ3: How do agent and developer patches differ?

Our comparative analysis reveals that agent patches often diverge significantly from their human-authored counterparts.
As issue difficulty increases, agent produced candidate patches differ more.

Manual analysis also reveals several interesting stylistic distinctions: agents tend to prefer localized, minimal edits, whereas human developers are more likely to restructure code or make broader, context-aware changes.

Together, these findings offer new insights into the capabilities and limitations of current SWE agents, and provide concrete guidance for building next-generation systems with greater reliability, transparency, and developer alignment.

The main contributions of this paper are as follows:

•

In-depth analysis.
We present the first systematic study of the behavior of LLM-based, software-engineering agents on the SWE-bench benchmark, tracing their entire decision-making pipelines from issue description to patch application.

•

Taxonomy.
We develop a taxonomy of agent workflows, identifying core behavioral modules (e.g., bug localization, reproduction test generation, patch synthesis) and characterizing dominant design strategies.

•

Insights.
We offer insights to help agent designers produce more reliable and effective patches.

•

Reproduction Package.
We provide a replication package
(
rep [n. d.]
)
that includes our framework and results.

Study Methodology

This section outlines how we have collected traces and patches produced by the agents (
Section

2.1
) followed by the taxonomy of agentic design (
Section

2.2
).

2.1.
Trace Collection

From the raw execution
traces
of an agent, we extract each agent’s full
trajectory
—defined as the ordered sequence of interactions or actions taken by the agent throughout the issue-solving process.
Each trace consists of discrete steps, such as issuing commands, navigating files, editing code, or validating outputs.
For every action in this sequence, we extract both the associated role label (e.g.,
user
,
assistant
,
system
) and a high-level summary of the LLM-generated response, which helps us to realize the agent trajectory, including the agent’s intended operation or rationale at that step.

To ensure correctness and interpretability, we cross-validate these extracted trajectory
by comparing them against the open-source implementations and workflow diagrams published in each agent’s respective documentation or paper. This validation step allows us to confirm that the trajectories reflect true agent behavior and that the summarized intents align with the agent’s underlying design.

In parallel, we extract the agent-generated
patch.diff
files from the traces and retrieve corresponding developer-written patches from the SWE-bench Verified Parquet dataset. We normalize both sets of patches by removing diff-specific symbols (e.g., “
+
”, “
--
”) and formatting artifacts, producing clean versions suitable for side-by-side comparison in downstream clone analysis and structural evaluation.

2.2.
Constructing a Taxonomy

To better characterize each agent’s unique capabilities and workflows, we construct a taxonomy of decision-making pathways based on their execution traces.
As shown in
Figure

1
, we synthesize the behavior of five representative SWE agents—AutoCodeRover, Agentless, SWE-Agent, OpenHands-CodeAct, and MASAI (see
Table

1
)—into a unified flow graph.
In this taxonomy,
nodes
represent discrete agent actions (e.g., code retrieval, patch synthesis, test invocation), and
edges
represent transitions between decisions or phases.

While all agents follow a shared high-level structure–comprising project understanding, context construction, patch generation, and test validation–they diverge in notable ways. OpenHands-CodeAct uniquely performs browser-based lookups. AutoCodeRover and Agentless restructure the codebase and employ keyword search, whereas SWE-Agent applies information retrieval for localization. MASAI and Agentless both rank patch candidates, though MASAI does so only after generating a test template, reflecting a more staged approach. Agents also differ in ways they generate or modify test cases—MASAI does so early, while SWE-Agent and OpenHands delay until after patch synthesis.

The taxonomy highlights two dominant strategies:
iterative refinement
, as in OpenHands, SWE-Agent, and AutoCodeRover, which generate and refine a single patch; and
parallel sampling
, as in MASAI and Agentless, which produce multiple candidates—only MASAI refines across them. Refinement occurs at multiple points, including file/class selection, context generation, and test generation.

Graph analysis identifies three core components across all agents: (1)
Localization
, the most connected node type and essential for context setup; (2)
Patch Generation
, a central and unavoidable phase; and (3)
Reproduction Testing
, necessary for validating correctness. These three components form the backbone of modern SWE-agent workflows and motivate us to study deeper, as presented in the following sections.

3.
Experimental Design

3.1.
Benchmark Selection

SWE-bench is a leading benchmark for evaluating automated program repair agents, comprising 2,294 real-world tasks from 12 actively maintained Python GitHub repositories. Each task specifies a repository version and includes a natural language issue description, requiring a candidate patch that passes both
fail-to-pass
(bug-fixing) and
pass-to-pass
(regression) tests.
Note that while evaluation is performed using these test cases, not all issues were originally reported with fail-to-pass tests; some tests were reconstructed or inferred during the benchmark’s construction.

To improve benchmark reliability, OpenAI released
SWE-bench Verified

(
OpenAI 2024
)
, a curated subset of 500 tasks selected through a human annotation campaign involving 93 experienced developers. Annotators removed 68.3% of tasks due to invalid test harnesses, vague descriptions, or environment dependencies. This subset serves as a high-quality gold standard for evaluating SWE agents.

Each task in SWE-bench Verified is further labeled with a difficulty level based on estimated human resolution time:

•

Easy
:
<
15 min fix

•

Moderate
: 15 min – 1 hr fix

•

Hard
: 1 – 4 hr fix

•

Very Hard
:
>
4 hr fix

We use this difficulty signal to analyze agent performance and patch patterns. All experiments are based on the publicly available at
https://github.com/swe-bench/experiments
repository.
Agent logs, trajectories, and patch-level diffs are retrieved from the public S3 bucket using the AWS CLI.

3.2.
Agent Selection

We use the term “agent” to refer to any LLM-based system designed to solve software engineering tasks—specifically, systems that generate code patches for natural language-described issues. Such agents augment the base LLM with tools and mechanisms for performing concrete actions such as navigating repositories, retrieving context, editing files, and running tests.

Broadly, we observe two kinds of agentic designs:

•

Workflow-based agents
structure the repair process into a fixed pipeline of subtasks (e.g., localization, patch generation, validation). These agents often rely on pre-defined task flows and explicit module boundaries, promoting modularity and reproducibility.

•

Open-process agents
delegate more autonomy to the LLM by exposing it to a flexible interface (e.g., CLI, browser, file system) through which it can issue commands, make decisions interactively, and adaptively control execution. These agents emphasize flexibility and emergent strategies.

We select five agents representing these paradigms based on the following criteria: (1) strong performance on the SWE-bench leaderboard
(
swe 2025
)
; (2) open-source codebases or fully documented system descriptions; and (3) support for systematic inspection of decision trajectories.

Research Questions

In the rest of the study we evaluate the effectiveness of program repair agents using the following RQs.

4.
Agent Effectiveness in Patch Generation (RQ1)

4.1.
Motivation

As a first step, we evaluate the overall issue-fixing capabilities of the studied agents to understand the current landscape of LLM-based automated program repair. This analysis helps surface both the strengths and limitations of these systems and highlights opportunities for advancing their design and effectiveness. We frame our investigation through the following three research questions:

•

RQ1.1 Performance across difficulty levels:
We examine how agent performance varies across issues of increasing complexity, using the difficulty tiers defined in SWE-bench Verified (see
Section

3.2
). This allows us to assess how well agents scale from simple, syntactic fixes to more semantically complex and time-consuming challenges.

•

RQ1.2 Divergence in agent capability:
We analyze whether the agents tend to solve overlapping subsets of issues or whether their success cases are largely disjoint. This helps us understand whether different agents exhibit unique problem-solving strategies, architectural biases, or tool use that contribute to complementary strengths—offering insight into potential gains from ensemble or hybrid approaches.

•

RQ1.3 Issue of overfitting and test case coverage:
We investigate the effect of fail-to-pass test case availability on patch success rates. Specifically, we ask whether agents overfit more easily when such test cases are limited in number and whether the presence of rigorous test specifications poses greater challenges. This helps evaluate the robustness of agentic capabilities and highlights the role of test coverage in enforcing semantic correctness.

When such test cases exist, agents face stricter constraints during patch validation, reducing the likelihood of overfitting or producing semantically incorrect yet plausible patches. The results show statistically significant differences with large effect sizes, indicating that the presence of more fail-to-pass test cases introduces a substantial challenge for current agent-based repair systems and potentially reduce overfitting.

RQ1 Findings:

Overall, we observe that agents are better at fixing easier problems that developers can also solve quickly. Different agents are good at different kinds of problems—no one agent is best at everything. Further, having more issue-reproducing test cases makes the patching task harder as it prevents overfitting.

4.3.
Implications

Our study reveals that current LLM-based repair agents are most effective on easier, developer-quick-fixable issues, but struggle significantly as task complexity increases. This indicates a gap in agents’ ability to generalize to harder software engineering challenges, highlighting the need for more advanced reasoning and planning capabilities. Second, the fact that no single agent consistently outperforms others suggests that different architectural choices yield specialized strengths. This points to the opportunity for designing ensemble or hybrid systems that combine complementary capabilities to achieve broader coverage. Finally, we show that agents perform worse when more fail-to-pass test cases are available—due to stricter validation constraints—which confirms that richer test specifications help prevent overfitting but make the task more demanding. Future benchmarks and agent designs should take these trade-offs into account to ensure both robustness and real-world effectiveness.

5.
Agent Effectiveness in Issue-Reproducing Test Generation (RQ2)

5.1.
Motivation

In RQ1, we observed that the presence of more issue-reproducing test cases (i.e., fail-to-pass tests) plays a critical role in preventing agents from overfitting (i.e., producing incorrect but plausible patches). These test cases provide a concrete failure signal that helps guide patch generation and enforce semantic correctness. However, in many real-world settings, such test cases are missing or limited, and agents must generate them as part of the repair process. This raises a natural next question:
How effective are agents at generating meaningful issue-reproducing test cases that improve patch reliability and reduce overfitting?
Understanding this capability is essential for evaluating the robustness of agent workflows and the role of test generation in successful automated program repair. To this end, we experiment with different agent design choices (See Taxonomy
Section

2.2
) to identify which ones lead to more effective reproduction test generation. In particular, we explore (RQ2.1) inference time scaling—sampling with different temperature and (RQ2.2) impact of bug localization on test generation.

5.2.
Approach

Problem Statement.

Given an original codebase
C_{o}
and a bug report
b
, the goal of test generation is to synthesize a test
T_{\text{gen}}
(e.g., a
.py
file) that reliably triggers the bug described in
b
when executed on
C_{o}
. Bug reports typically include natural language descriptions and may also contain auxiliary information such as stack traces or error messages.

In most agent workflows, the test generation phase relies solely on the bug report
b
and the buggy codebase
C_{o}
. The agent formulates a prompt
P(b)
that includes the issue description, task instructions (e.g., “Write a test to reproduce the bug”), and often an example test. This prompt is passed to the LLM to produce
T_{\text{gen}}
. Some agents, such as Agentless, generate multiple test samples in parallel (e.g., 40 at once).

The test generation process is considered
successful
if at least one generated test reliably reproduces the bug on
C_{o}
.
The successful tests are then reused in the patch validation phase: a generated patch is accepted if the same test, when run on the patched codebase, no longer triggers the bug.

Experimental Setup.
In this RQ, we use Agentless for all experiments, as it is the best-performing fixed-workflow agent; fixed-workflow enables easier reproduction of results when varying agentic components.

For each issue instance (e.g.,
django-11815
), the pipeline queries the SWE-bench Verified dataset to retrieve the original repository URL and base commit (
C_{o}
). A Docker image is built by cloning the repo at the base commit and setting up the required Conda environment. The image is then used to launch containers in which the generated test
T_{\text{gen}}
is executed.

The number of workers (i.e. number of concurrently active CPU cores) is capped to a value that guarantees runtime stability.
All experiments use Claude-3.5-Sonnet via Anthropic’s API, for which we implement safeguards to avoid long-polling and rate-limit errors: limiting output tokens, batching prompts within token budgets, and throttling requests with 60-second intervals between batches.

Sampling & Temperature.
We vary two factors: (1) the number of sampled test-case outputs
s\in\{15,\,40\}
, and (2) the temperature
t\in\{0.2,\,0.6,\,1.0\}
, where lower values of
t
encourage more deterministic generations and higher values promote diversity. For each
(s,t)
setting, we sample
s
tests
T_{\mathrm{gen}}=\{t_{1},\dots,t_{s}\}
and evaluate reproduction success as defined above.

Bug Localization.

Here we manually analyze 20 issues, a scale that permits a thorough manual analysis of every trajectory. We draw these issues using a stratified sampling approach across multiple projects to ensure cross-project coverage and diversity of difficulty (that is, we include issues that are labeled easy fixes (
<
15 min) as well as harder (1-4 hr) issues). For each issue, we generate
30
independent
T_{\text{gen}}
samples.
We evaluate two configurations: (1)
Default:
the unmodifed approach; (2)
with bug localization
utilizing our framework which enhances issue reproduction prompt with localization information extracted using embedding-based retrieval. Our success criterion is whether the issue is reproduced, as described earlier. Our reported metric is
k/30
where
k
is the count of successful samples.

5.4.
Implication

These findings suggest that simply generating more outputs or using higher diversity during inference is not enough when the issue description is unclear. Without specific guidance, agents tend to repeat the same failed attempts, wasting time and resources. However, providing additional context—such as pointing to the likely buggy file or class—can make a big difference. It helps the model focus on the right part of the code and increases the chances of producing a useful test earlier in the process. This means that for agents to be more reliable and efficient, they should not rely only on natural language descriptions. Instead, they should be designed to use extra signals like bug localization to better understand and solve the problem.

6.2.
Approach

We evaluate the similarities between developer and agent generated patches using two ways:

A. Patch Edit-Distance.
We compute the character-level Levenshtein distance
(
Wagner and Fischer 1974
)
between each successful agent-generated patch and its corresponding developer patch, grouping results by the difficulties of the issues: Easy, Medium, and Hard. Note that since none of the agents can solve very hard issues, we omit them in this RQ.

B. Code Clones.
We assess the similarity between agent-generated and developer-written patches using
code clone
analysis, based on the taxonomy of Bellon et al.
(
Bellon et al. 2007
)
. Clones are categorized as follows:
Type 1
—exact matches differing only in whitespace, layout, or comments;
Type 2
—syntactically identical code with variations in identifiers, literals, or types; and
Type 3
—structurally similar code with added, removed, or modified statements. As all studied patches pass at least one test case, they share a degree of semantic intent and can be treated as
Type 4
clones by default.

To classify clone types, we use Claude-3.5-Sonnet as an LLM-based judge, prompting it with a standardized template to evaluate each agent–developer patch pair. A manual audit of a random subset shows strong agreement with human judgment (Cohen’s
\kappa=0.82
), supporting the reliability of this approach. We apply this method across all 192 issues resolved by Agentless+Claude-3.5.

6.5.
Implication

RQ3 observation highlights a fundamental limitation in current agentic approaches to program repair. While agents perform well on simple, localized bugs—often producing patches that are syntactically similar to developer fixes—they struggle to match the broader, multi-step reasoning that developers use for more complex issues. The agent’s preference for single-site edits suggests a limited understanding of program structure and interdependencies, often avoiding the kinds of refactorings or cross-cutting changes that developers routinely make, such as modifying function signatures, updating multiple call sites, or restructuring control flow.

This gap has important implications: it suggests that despite passing test cases, agent-generated patches may be less maintainable, less generalizable, or misaligned with human coding conventions. To address this, future repair agents will need enhanced architectural awareness and planning capabilities—potentially through better code navigation tools, persistent memory, or multi-turn reasoning. Incorporating static analysis, symbolic reasoning, or learned patterns of developer behavior could also help agents move beyond reactive fixes and towards more semantically aligned, holistic solutions.

SWE Agents for Program Repair.

Automated AI-assisted tools are increasingly adopted in industry
(

;
Vaithilingam et al. 2022
;
Liang et al. 2024
;
Davila et al. 2024
;
Marginean et al. 2019
)
, but significant challenges remain
(

;
Vaithilingam et al. 2022
;
Barke et al. 2023
;
Weisz et al. 2025
;
Winter et al. 2022
)
. A key limitation is overreliance on test suites to validate fixes: even with good coverage, many fail to capture the specific defect, leaving patch correctness uncertain. Wang et al.
(
Wang et al. 2025
)
show that benchmark-approved AI patches often fail developer-written tests or cause unintended behavior.

Studies have also shown that developers may accept overfitting or misleading fixes
(
Eladawy et al. 2024
)
, skip inspection for large patches
(
Cambronero et al. 2019
)
, or need to refactor AI-generated code to maintain quality
(
Licorish et al. 2025
)
.
There are many previous studies on the correctness of automatically generated patches
(
Xiong et al. 2018
;
Yang et al. 2023
;
Xin and Reiss 2017
;
Qi et al. 2015
)
. Our work is complementary to all these works and focuses on agentic approaches.

Agent vs. Developer Code.

Prior work has evaluated LLM outputs and patch correctness
(
Rondon et al. 2025
)
, but key gaps remain. Licorish et al.
(
Licorish et al. 2025
)
assess GPT-4’s code quality but not repair patches. Chen et al.
(
Chen and Jiang 2024
)
localize edit sites but not logic similarity. Wang et al.
(
Wang et al. 2025
)
evaluate test-passing correctness, while we focus on identifying patch patterns through code clone detection and construct-level analysis. Our study asks:
what code structures do agents generate, and how do they differ from human-written fixes?

Issue Reproduction.

A prerequisite for solving the issues is reproducing them. Many agents generate test cases from issue descriptions to induce the failure, which should then pass once the fix is applied. Reliable reproduction is critical to validate fixes
(
Mündler et al. 2024
)
. Because LLM output quality varies, inference-time scaling is often used. Two strategies exist:
parallel scaling
(generate many outputs, select best), and
sequential scaling
(iteratively refine outputs). Prior work has studied scaling for general code generation
(
Li et al. 2025
)
, but not specifically in the context of test generation. Agent designs differ: Agentless uses parallel sampling
(
Xia et al. 2024
)
, while Otter
(
Ahmed et al. 2025
)
and SpecRover
(
Ruan et al. 2024
)
use sequential refinement. In both styles, reproduction tests are critical—they must fail before patching and pass afterward. Still, success remains low: Otter achieves just 29% reproduction on SWT-Bench-Lite
(
Ahmed et al. 2024
)
.

LIBRO
(

)
explores LLM prompting for generating reproduction tests from bug reports.
SWT-Bench
(

)
modifies the prompts of existing agents but does not explore the impact of adding localization information.

As opposed to focus solely on a test generation agent, we study in a patch repair framework which strategies may benefit test generation.
Further, we show impact of bug localization in this setting.

8.
Threats to Validity

We identify and address several potential threats to the validity of our findings:

LLM Choice (Claude 3.5 Sonnet).
Our study primarily uses Claude 3.5 Sonnet as the base LLM for generation and evaluation. While the behavior and reasoning patterns of this specific model may not generalize to other LLMs (e.g., GPT-4, Gemini), Claude 3.5 is one of the strongest open agents available at the time of writing and has been successfully used in related work as a reliable evaluator
(
Klemmer et al. 2024
;
Wang et al. 2025
)
. To mitigate concerns of LLM subjectivity in evaluation, we complement its judgments with two additional metrics: (i) Levenshtein edit distance to assess patch similarity, and (ii) Cohen’s
\kappa
to quantify inter-rater agreement between the model and human annotators. These provide triangulation to strengthen confidence in automated evaluations.

Human Annotation Bias.
Any manual analysis, including patch labeling or trajectory intent extraction, is subject to human interpretation and bias. To minimize individual bias, all ambiguous or borderline cases are collaboratively reviewed by a team of researchers. Labeling decisions are made through consensus, and inter-annotator discrepancies are explicitly discussed and resolved. This collaborative process ensures that labels are more consistent and reliable across evaluators.

Sampling Bias.
Our findings are based on a subset of issues from the SWE-bench Verified dataset. To ensure that our conclusions are not skewed by a biased sample, we adopt a stratified sampling strategy. We categorize issues into four difficulty levels—
easy
,
moderate
,
hard
, and
very-hard
—based on prior human resolution time and reproduction success rates. We then sample proportionally from each stratum to reflect the full distribution of problem difficulty. This approach ensures that our results generalize across a range of issue complexities.

Taxonomy Coverage.
While our taxonomy presents an exhaustive set of decision-making components observed across agents, we do not empirically evaluate all possible combinations of these components. The space of potential configurations is combinatorially large. To ensure tractability, we select representative and influential agent workflows that span the dominant actions in practice (e.g., test generation, bug localization) and strategies (e.g., inference time sampling). Although this choice introduces a coverage limitation, our focus on representative pathways still produce some meaningful insights.

9.
Conclusions

This work provides a foundational understanding of how current SWE agents approach program repair, offering insights to guide the design of more robust and reliable systems. We show that agents struggle with harder bugs unless they combine natural language input with structured signals like test generation and bug localization. In particular, reproduction testing remains a weak link—limited by over-reliance on test suites and brittle scaling strategies. Future agents must adopt more adaptive reasoning and hybrid inputs to validate and apply patches effectively.

Our contributions include a full tracing of agent decision-making pipelines, a taxonomy of core workflows (localization, test generation, patching), and a detailed empirical study revealing both statistical patterns and qualitative distinctions in agent behavior. These findings inform the next generation of agents—ones that reason more flexibly and mirror human-like workflows in solving complex software issues. We provide open-source artifacts and support replication and independent verification of our contributions
(
rep [n. d.]
)
.

10.
Future Work

A promising direction for future work is extending the taxonomy to cover a broader space of agent configurations. This includes agent-specific subgraphs that capture variations in execution pathways. Graph structure lends itself to further techniques drawn from graph theory, such as critical path analysis, identification of performance bottlenecks, and optimization of resource use (e.g. LLM call budget, inference latency). Combined with our insights on issue resolution, reproduction, and agent-introduced patterns, these analyses can inform design choices that target performance, interpretability, and efficiency in real-world deployment scenarios.
