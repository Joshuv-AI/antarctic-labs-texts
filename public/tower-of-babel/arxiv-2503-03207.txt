PolyVer : A Compositional Approach for Polyglot System Modeling and Verification
Pei-Wei Chen 1 , Shaokai Lin 1 , Adwait Godbole 1 , Ramneet Singh 2 , Elizabeth Polgreen 3 , Edward A. Lee 1 , Sanjit A. Seshia 1

Abstract
Many software systems are polyglot ; that is, they comprise programs implemented in a combination of programming languages. Program verifiers, however, tend to be customized for individual languages. Verification by compiling to a common encoding requires supporting full language syntax and semantics which is prohibitive for modern languages. We present PolyVer , an alternative compositional approach to polyglot verification that bootstraps off-the-shelf language-specific verifiers with abstraction and synthesis. PolyVer uses contracts written in an intermediate language to abstract individual procedures in the system. Our verification approach uses language-specific verifiers (e.g., for C or Rust) to validate these contracts and the UCLID5 model checker for compositionally verifying a temporal property on the overall system using the contracts. The intermediate language sidesteps the need for compiling implementation languages to a common encoding, a key obstacle with polyglot verification. Finally, PolyVer automates the generation of contracts using synthesis oracles such as large-language-models (LLMs). Overall PolyVer performs contract synthesis and verification in a counterexample-guided abstraction refinement and inductive synthesis (CEGIS-CEGAR) loop to verify the system-level property. We use PolyVer to verify programs in the Lingua Franca polyglot language. We are able to verify systems with C and Rust procedures, as well as C language fragments that were unsupported in previous work.

I
Introduction

Many modern software systems comprise code written in a combination of programming languages
[
1
]
. For example, the Robot Operation System 2 (ROS2)
[
2
,
3
]
allows users to specify processes that communicate with each other, called ROS nodes, where each node can be implemented in a different programming language. Other languages and frameworks provide similar cross-language functionality for various domains, like Lingua Franca
[
4
]
for real-time, distributed embedded systems, and Eclipse Cyclone DDS
[
5
]
and gRPC
[
6
]
for distributed systems and networking. We refer to these multi-language software systems as
polyglot
systems.

Polyglot systems allow developers to pick and choose the best programming language for specific system components. Unfortunately, this flexibility comes at a cost, with studies indicating that the increased complexity of polyglot systems can lead to an increase in bugs
[
1
]
. Recent work has addressed these issues through testing and other incomplete methods. For example, Yang et al.
[
7
]
develop a deep-learning-based method that helps localize bugs specifically due to the interaction between multiple languages in a single system. These tools and techniques can help developers build safer systems, but they cannot provide the guarantees needed in safety-critical settings and other vital settings in which polyglot systems appear.

In this paper, we study the problem of formally verifying polyglot systems. Just like developing polyglot systems introduces new challenges in the development cycle, verifying polyglot systems introduces new challenges in the verification process. Over the past few decades, there has been substantial work on program verifiers that operate directly on
individual programming languages. We refer to these tools as
language-specific verifiers
. For example, CBMC
[
8
]
and Frama-C
[
9
]
can be used to verify C code, Kani
[
10
]
and Verus
[
11
]
for Rust, ESC/Java
[
12
]
, Java PathFinder
[
13
]
, and JBMC for Java
[
14
]
, etc. However, very few approaches have been proposed for multi-language systems, so polyglot verification challenges remain largely unexplored.

The main existing approach for polyglot system verification translates all code to one common language and applies existing reasoning engines to that common representation. However, this approach is challenging due to the complexity of handling diverse syntax and semantics across languages, and arguably, it loses the benefits of having highly optimized language-specific verifiers. For instance, prior work, such as Lin et al.
[
15
]
, only handles very restricted C code within the Lingua Franca language, highlighting the difficulties of such monolithic approaches. Encoding a multi-language system in a single verification model may also result in scalability issues, as the generated verification problem can become prohibitively large. To our knowledge, no existing approach enables automated verification of multi-language software systems through
cooperative
use of language-specific verifiers.

We propose a compositional verification approach
to address this gap.
Our approach has two key components: (a) interface contracts written in an
intermediate contract language
that abstract individual components, and (b) a
synthesizer
that automatically generates and refines these contracts with the help of language-specific verifiers.
The intermediate contract language is much smaller than the languages of individual components, allowing us to sidestep full language translation.
Instead, we can use language-specific verifiers to check the contract validity by only translating the (much smaller) intermediate language fragment.
Further, our large language model (LLM)-based synthesizer and language-specific verifiers eliminate the burden of manually writing and refining contracts.
This enables scalable and automated verification of multi-language systems without requiring a full translation into a single verification framework.

In summary, the novel contributions of this paper are:

\bullet

Polyglot verification problem.
We formalize the polyglot verification problem and propose a compositional solution integrating multiple language-specific verifiers.

\bullet

Automated pre/post-condition contract synthesis.
We automate synthesis and refinement of pre/post-condition contracts using an intermediate language and combining counterexample-guided inductive synthesis (CEGIS) and abstraction refinement (CEGAR). Our approach uses synthesis oracles including syntax-guided synthesis (SyGuS) solvers and large language models (LLMs).

\bullet

Our tool.
We implemented
PolyVer
on top of UCLID5
[
16
,
17
]
, supporting C and Rust via CBMC
[
8
]
and Kani
[
10
]
.
Our implementation shows that an LLM-based synthesis oracle outperforms pure symbolic synthesis approaches.

\bullet

Case study and evaluation.
We developed a verifier for the Lingua Franca coordination language
[
4
]
and show that our approach is able to verify multi-language systems with reasonable synthesis time.
We also introduce a new set of polyglot verification benchmarks and realistic applications that are only solved by our approach.

Language-specific verification (LSV) tools

Verifying polyglot systems with LSVs requires
connecting these verifiers
, which is challenging due to these differences.

Compositional (contract-based) verification
uses interface specifications, also called

Once the validity of a contract w.r.t. the system component is checked using an LSV, it can be soundly used for system-level verification.
Crucially, given the contract, system-level check becomes
agnostic of techniques/backends employed by the LSV

PolyVer

In this sense, verification in

operates much like assume-guarantee/requires-ensures reasoning
[
21

22
]

Manually identifying valid, yet

E.g.,

(Fig.

((request->value < 3) || response->value)
&& (request == \old(request))

To address this,
PolyVer
performs automated contract synthesis
by using refinement-based neural (LLM-based) contract search in combination with symbolic verification of the contract.
Thus, with contract synthesis,
PolyVer
bootstraps existing LSVs to solve the multi-language verification problem, at the same time avoiding the challenges of encoding the entire system into a single language.

III
Problem Formulation

Polyglot systems are compositions of components where each component is a procedure in some language
{\mathcal{L}}
(e.g., C, Rust, Java).
Such a setup is widely seen in distributed systems where nodes execute code in a specific language and interact via mechanisms like remote procedure calls (RPCs).
We formalize such systems and define the verification problem.

We model polyglot systems as Extended State Machines (ESM)
[
23
]
.
Informally, ESMs capture inter-procedural control flow as transitions between
modes
, where each transition has an associated
update function
representing a sequence of procedure calls.
ESMs operate on a set of typed variables
V
shared across all procedures in the system.
We refer to the domain of (typed) variable
v\in V
as
D(v)
and denote the Cartesian product of the domains of all variables as
D(V)
.
D(V)
thus forms the set of assignments
d
to
V
.
A
predicate
is a function

D(V)\rightarrow\mathbb{B}
.

Definition 1

(Extended State Machine)
.

An
Extended State Machine (ESM)
is a tuple
(Q,V,I_{0},T)
where

1.

Q
is a set of modes,

2.

V
is a set of typed variables,

3.

I_{0}\subseteq Q\times D(V)
is a set of initial states,

4.

T\subseteq(Q\times Q)\times(G\times U)
is a set of mode-mode transitions, each associated with a guard in
G=D(V)\rightarrow\mathbb{B}
and an update relation in
U=2^{D(V)\times D(V)}
.

Executions.
The guard
g
is a predicate determining whether a transition can occur, and the update relation
u
defines how the transition affects
V
. At every step, the ESM in a state
(q,d)
takes a transition
((q,q^{\prime}),(g,u))
such that
g(d)
is true. The ESM then updates the state to
(q^{\prime},d^{\prime})
where
(d,d^{\prime})\in u
.
While the update relation (
u
) in each ESM transition is kept abstract, polyglot systems specialize them to be invocations of procedures (possibly from different languages).

Definition 2

(Language)
.

A
language

{\mathcal{L}}
is a set of terms and predicates constructed through syntactic rules over a set of variables
V
.
The language fixes the interpretation of each term
t\in{\mathcal{L}}
and predicate
p\in{\mathcal{L}}
denoted as
{\llbracket t\rrbracket}_{\mathcal{L}}:D(V)\rightarrow D(V)
and
{\llbracket p\rrbracket}_{\mathcal{L}}:D(V)\rightarrow\mathbb{B}
respectively.

We assume that the set
V
contains all the variables read or written by the procedures implemented in the various languages.
Further, the interface variables shared across languages must have matching types, and hence we use the same
D(V)
for different languages. This interface type-consistency is enforced in practical polyglot frameworks such as Lingua Franca
[
4
]
and ROS2
[
2
]
.
Unless otherwise noted, we implicitly use the same variable set
V
for the rest of the paper.

Next, we define procedures.

Definition 3

(Procedure)
.

A
procedure

f
is a pair
(C,{\mathcal{L}})
where
C\in{\mathcal{L}}
represents the procedure body. We call such a procedure an
{\mathcal{L}}
-procedure.
We refer to pre-state and post-state variables of a procedure as
V
and
V^{\prime}
, respectively.

We assume that procedures are total and always terminate

Polyglot models
, our model for polyglot systems, are ESMs where update relations are procedure invocation sequences.

Definition 4

(Polyglot Model)
.

A
polyglot model

{\mathcal{M}}
is a tuple
(Q,V,I_{0},T,F)
where
(Q,V,I_{0},T)
is an ESM and
F
is a set of procedures. Each transition
((q,q^{\prime}),(g,u))\in T
is s.t.
u=\{(d,d^{\prime})~|~d^{\prime}=f_{k}\circ\cdots\circ f_{1}(d)\}
for some
f_{i}\in F
, where
\circ
denotes procedure composition:
f_{1}\circ f_{2}(d)={\llbracket C_{1}\rrbracket}_{{\mathcal{L}}_{1}}({\llbracket C_{2}\rrbracket}_{{\mathcal{L}}_{2}}(d))
.

An example of a polyglot model is shown in Figure
1
,
where
Q=\{q_{i}\}_{i}
,
I_{0}=(q_{0},\_)
is the state after executing the procedures on the initial transition,
T
is depicted by the transitions, and
F=\{\texttt{Init},~\texttt{ProcessQuery},\cdots\}
.

Remark on semantics:

While procedures are deterministic in our formulation (terms have deterministic semantics), nondeterministic procedures can be introduced by changing term interpretations from functions to relations.
Further, side-effects are emulated by extending
V
with global variables.

Traces.
Each execution of the model produces an infinite
trace
that is the sequence of assignments (
d
) to variables in
V
seen in the execution.
A property
\phi
is a set of traces, typically in the form of a temporal logic formula.
Let the set of all traces that can be produced by a model
{\mathcal{M}}
be
\mathcal{T}({\mathcal{M}})
.
We write
{\mathcal{M}}\models\phi
if
\mathcal{T}({\mathcal{M}})\subseteq\phi
.
The polyglot verification problem aims to determine whether a polyglot model satisfies a property
\phi
.

Problem Statement 1

(Polyglot verification problem)
.

Given a polyglot model
{\mathcal{M}}=(Q,V,I_{0},T,F)
and a system property
\phi

determine whether
{\mathcal{M}}\models\phi
.
If
{\mathcal{M}}\not\models\phi
, provide a counterexample trace generated by
{\mathcal{M}}
that violates
\phi
.

Verification Challenge and Insight.

Crucially, while the procedure bodies (
C
) in
{\mathcal{M}}
are known,
capturing their interpretations (
{\llbracket C\rrbracket}_{\mathcal{L}}
) is difficult
.
Naive monolithic verification of
{\mathcal{M}}
would require encoding full semantics of
{\mathcal{L}}
(for all
{\mathcal{L}}
) to a common modeling language, e.g. SMT-LIB.
This is extremely tedious and would require a parser/compiler infrastructure for each language.
Our solution is to use contracts written in an
intermediate language

{\mathcal{L}^{*}}
– in this way we only need to support encodings for this (much smaller) language
{\mathcal{L}^{*}}
.

IV
Polyglot Verification through a Contract IL

We now introduce contract-based decomposition.
The key component is a pre-post condition contract that abstracts (over-approximates) the behavior of a procedure
f
.

Definition 5

(Contract)
.

A (
{\mathcal{L}}
-)
contract
for procedure
(C,{\mathcal{L}})
is a pair
(P,Q)
where
P,Q
are predicates in
{\mathcal{L}}
.

(P,Q)
is
valid
iff the Hoare-triple
\{P\}C\{Q\}
holds, i.e.,

\forall d,d^{\prime}\in D(V).({\llbracket P\rrbracket}_{\mathcal{L}}(d)\land d^{\prime}={\llbracket C\rrbracket}_{\mathcal{L}}(d))\implies{\llbracket Q\rrbracket}_{\mathcal{L}}(d^{\prime})

(1)

By convention, preconditions
P
can only refer to pre-state variables
V
, while postconditions
Q
can refer to both pre- and post-state variables
V
and
V^{\prime}
.
Equation (
1
) can be checked with a language-specific verifier for
{\mathcal{L}}
.
A valid contract can serve as a sound system-facing abstraction of the procedure, as we now discuss.

Contract composition
replaces procedures in a polyglot system
{\mathcal{M}}
with their contracts.

Formally, for each transition
u=f_{k}\circ\cdots\circ f_{1}
in
{\mathcal{M}}
,
we generate contracts
(P_{j},Q_{j})
for each
{\mathcal{L}}_{j}
-procedure
f_{j}
such that,

\forall d\in D(V).{\llbracket Q_{j}\rrbracket}_{{\mathcal{L}}_{j}}(d)\implies{\llbracket P_{j+1}\rrbracket}_{{\mathcal{L}}_{j+1}}(d)

(2)

Then, we define a new model
{\mathcal{M}}^{\prime}
where
u
is replaced with the contract-derived relation
u^{\prime}=\{(a,b)\mid{\llbracket P_{1}(a)\rrbracket}_{{\mathcal{L}}_{1}}\implies{\llbracket Q_{k}(b)\rrbracket}_{{\mathcal{L}}_{k}}\}
.
Since the replacement contract
u^{\prime}
overapproximates
u
, we have the following theorem.

Theorem 1
.

If
\mathcal{M^{\prime}}\models\phi
, then
{\mathcal{M}}\models\phi
.

How does a contract IL help verification?

A key challenge with contract-based polyglot verification is checking Equation (
2
), which involves predicates
in two different languages
.
We are unable to use a language-specific verifier to check this.
Our solution is to
write contracts in an intermediate language

{\mathcal{L}^{*}}
and bridge contracts using a
semantics-preserving compilation
.

Definition 6

(Intermediate Language)
.

An
intermediate language
(IL)
{\mathcal{L}^{*}}
is a language of pre/post-condition contracts,
whose semantics is defined by the SMT-based semantics of the language
{\mathcal{L}}
to which it is translated.

Concretely, we translate contract predicates from
{\mathcal{L}^{*}}
to each procedure language
{\mathcal{L}}
, e.g., C, Rust, through a semantics-preserving compilation
\mathsf{comp}_{\mathcal{L}}
:

Assumption 1

(
{\mathcal{L}^{*}}\rightarrow{\mathcal{L}}
Compilation)
.

\forall C\in{\mathcal{L}^{*}}.~{\llbracket\mathsf{comp}_{{\mathcal{L}}}(C)\rrbracket}_{\mathcal{L}}\equiv{\llbracket C\rrbracket}_{{\mathcal{L}^{*}}}

Assumption
1
allows us to compose and validate contracts in
{\mathcal{L}^{*}}
.
When contracts are in
{\mathcal{L}^{*}}
, contract composition check (Equation (
2
)) simplifies to:

\forall d\in D(V).{\llbracket Q_{j}\rrbracket}_{{\mathcal{L}^{*}}}(d)\implies{\llbracket P_{j+1}\rrbracket}_{{\mathcal{L}^{*}}}(d)

(3)

Equation (
3
) can be checked by a model checker when
{\mathcal{L}^{*}}
is translated into a modeling language like UCLID5.
Validity checking (Equation (
1
)) of an
{\mathcal{L}^{*}}
-contract
(P,Q)
simply reduces to that of an
{\mathcal{L}}
-contract
(\mathsf{comp}_{{\mathcal{L}}}(P),\mathsf{comp}_{{\mathcal{L}}}(Q))
.

Counterexample guided contract refinement.
While Theorem
1
provides a soundness result, the converse does not hold.
A counterexample trace found in
{\mathcal{M}}^{\prime}
may be a spurious counterexample that cannot be produced by
{\mathcal{M}}
.
Contracts must be strengthened to exclude this trace.
However, developing
valid contracts that are strong enough
to prove system-level properties is challenging, often involving iterative contract refinement.
To address this, we introduce the valid contract synthesis problem, which aims to generate a contract that avoids a set of spurious traces provided as
negative
examples.

Problem Statement 2

(Valid Contract Synthesis Problem)
.

Given an
{\mathcal{L}}
-procedure
f
and positive, negative example sets
X,\overline{X}\subseteq D(V)\times D(V)
, synthesize a valid contract in
{\mathcal{L}^{*}}
that includes the positive examples and excludes negative ones.

How does a contract IL help synthesis?

Contract synthesis illustrates the second benefit of the intermediate language
{\mathcal{L}^{*}}
.
Language-specific contracts would require synthesizers tailored to the syntax and semantics of each language.
A common IL allows us to maintain a single interface with synthesis oracles. For instance, in the case of Syntax Guided Synthesis (SyGuS)
[
24
]
we require a single grammar, or in the case of neural search (e.g., using LLMs), we require a single in-context example set.
Like verification, this greatly reduces the effort in developing synthesis oracles.

3
illustrates how
{\mathcal{L}^{*}}
mediates contract synthesis and verification.

An Abstraction Synthesis Approach for Polyglot Model Verification

We present an approach for contract synthesis (Problem
2
) which we use as a subroutine to solve Problem
1
.
We provide some background and then an overview in Section
V-B

V-A

Background: CEGIS and CEGAR

We synthesize contracts by combining Counterexample Guided Inductive Synthesis (CEGIS)
[
25
]
and Counterexample Guided Refinement Abstraction (CEGAR)
[
26
]
.

CEGIS uses an iterative interaction between a
learner
and a
teacher
to synthesize a solution (in our case contracts) satisfying a set of constraints (in our case, example traces).
The
learner
generates a candidate solution satisfying the constraints, while the
teacher
checks whether the solution satisfies the overall specification.
Synthesis succeeds if the solution is correct; else, the teacher provides a new counterexample.

CEGAR iteratively refines an abstraction (in our case contracts) in the context of a property. At each step, the abstraction is checked for correctness. If verification fails, the counterexample is analyzed to determine whether it is spurious (due to the abstraction being too coarse). If the counterexample is real, the system is buggy; else, the abstraction is refined.

The approach is parameterized by the set of synthesis oracles, verification oracles, and the intermediate contract language
{\mathcal{L}^{*}}

It operates by performing CEGIS (inner loop; line

CEGAR (outer loop) then uses these contracts to generate the induced

V-F

Correctness Guarantee

Our approach makes assumptions
1
,
2
, and
3
.
Given these assumptions, we guarantee

, meaning that if

terminates with

{\mathcal{M}}\not\models\phi

We intuit this result as follows.
For soundness, notice that contracts used in the induced model must overapproximate procedure behaviors because of the verification oracle assumption (Assumption

This means that when

reports

For completeness, when
\mathsf{mc}

This trace must also be producible by the procedures by the spuriousness check (§

Our Running Example as a Lingua Franca Program

VII-B

Methodology: Mapping LF Programs to Polyglot Models

LFVerifier
[
15
]
performs end-to-end LF verification by mapping the program onto a State Space Diagram (SSD) and compiling it along with the reaction body (C code) into a monolithic axiomatic model.

PolyVer
instead compiles the SSD into an operational polyglot model.

An SSD is a graph where each node (state)
s
contains the current logical time, a set
R
of reactions to be executed, and a set of pending events,
and each edge represents logical time advancement.
Figure
6
in the Appendix shows an example SSD generated from the LF program in Figure
5
.

LF timing semantics at each state
s
impose a directed-acyclic graph (DAG) over the set of reactions
R
, with edges encoding execution precedence.
A reaction may fire only when all of its predecessors have run to completion, so any topological sort of the DAG is a valid execution order.
Independent reactions whose predecessors have finished may execute in either order, hence introducing nondeterministic reaction interleaving.
Once all reactions in
R
are completed, the SSD state can advance to the next state.

We encode time progression and nondeterministic reaction interleaving in UCLID5 by encoding reaction DAGs and dynamically tracking their execution status.
This yields a nondeterministic polyglot model (Definition
4
) where each transition executes one reaction, as in the model in Figure
1
.
We integrate the
PolyVer
-based verifier into the LF compiler, which generates C, Rust, and UCLID5 code and performs verification.

IX
Related Work

Most approaches to verifying multi-language systems rely on manually translating some parts of the system until everything is in a common language.
For instance, Cook et al.
[
35
]
translate fragments of assembly code into C to verify the Xen hypervisor,
and Marin et al.
[
36
]
define a small imperative language within the Maude modeling language to manually encode LF reactions.
Where it is common to combine a fragment of one language with another, tools may automate translation of that fragment.
For example, prior work
[
15
]
on LF verification automatically translates a fragment of C into the verification language, and tools like CBMC
[
8
]
support small fragments of assembly code.
Another method is to black-box unanalyzable code and infer summaries from their observed input-output behavior
[
37
]
.
While similar to us, this relies on sufficient examples and lacks the guarantees that fully integrating language-specific verifiers provides.

We employ compositional verification based on Hoare logic
[
38
]
. This is commonly applied to verification problems that, whilst written in only one language, are too large to be tackled in a single verification query
[
39
]
.
Previous work, e.g.,
[
40
,
41
,
42
,
43
]
, automates this by learning pre/post-conditions using abstract interpretation and CEGAR
[
26
]
.

There are also property-guided approaches to inferring contracts, while we aim to discover a contract that is just good enough to prove a given property. Here, previous work uses syntactic patterns
[
44
]
, Constrained Horn Clause solvers
[
45
]
, and even CEGIS
[
25
,
46
]
. Recently, LLMs have been applied to learning specifications, including pre/post-conditions, for code
[
47
]
.
The work closest to ours uses CEGIS and LLMs to infer post-conditions, but neither of these approaches addresses the challenge of multi-language verification.

Our approach to compositional verification, relying on learning-based synthesis oracles, implements the paradigm of “verification by reduction to synthesis” and the use of learning-driven synthesis advocated by
[
48
]
.
Our contract learning approach is based on an integration of CEGIS and CEGAR. This integration can be considered a form of oracle-guided synthesis/learning
[
49
,
48
,
30
]
, where the verification oracle and model checker act as oracles guiding the synthesis search.
In hardware, prior work
[
50
]
uses synthesis to generate environment invariants for modular hardware verification. These invariants can be seen as pre-conditions in our context.

X
Conclusions

We formulated the polyglot verification problem and proposed
PolyVer
, a contract-based approach. This approach bootstraps off-the-shelf language-specific verifiers to verify polyglot systems, while side-stepping challenges involved in compiling the entire system to a single homogenous encoding.
We implemented our approach in a tool that automatically iterates between CEGAR and CEGIS loops to synthesize contracts using an LLM-based synthesizer.
We demonstrate a significant qualitative improvement by verifying full-fledged, multi-language systems that previous work could not handle.

There are several interesting directions for future work.
One is to apply the
PolyVer
approach to verifying other kinds of polyglot distributed software systems or robotics software systems.
We believe our approach is also applicable in cases where the software is not necessarily polyglot to begin with. For example, it would also be interesting to apply this approach to the problem of formally-verified translation of code from one language to another (e.g., from C to Rust), where the translation is performed in stages, and the intermediate state of the translated code involves a mix of languages.
