Layered Modal ML: Syntax and Full Abstraction
Haoxuan Yin, Andrzej S. Murawski, C.-H. Luke Ong

Abstract
. MetaML-style metaprogramming languages allow programmers to construct, manipulate and run code. In the presence of higher-order references for code, ensuring type safety is challenging, as free variables can escape their binders. In this paper, we present Layered Modal ML (LMML), the first metaprogramming language that supports storing and running open code under a strong type safety guarantee . The type system utilises contextual modal types to track and reason about free variables in code explicitly. A crucial concern in metaprogramming-based program optimisations is whether the optimised program preserves the meaning of the original program. Addressing this question requires a notion of program equivalence and techniques to reason about it. In this paper, we provide a semantic model that captures contextual equivalence for LMML, establishing the first full abstraction result for an imperative MetaML-style language . Our model is based on traces derived via operational game semantics, where the meaning of a program is modelled by its possible interactions with the environment. We also establish a novel closed instances of use theorem that accounts for both call-by-value and call-by-name closing substitutions.

1.2.
Closed instances of use with both call-by-name and call-by-value substitutions

After introducing LMML and proving its type safety,
we move on to discuss program equivalence in this language.
When performing metaprogramming-based program optimisations,
a critical concern is whether the optimisation is faithful.
In the above power example,
we expect that
power
and
power_staged
are equivalent.
To address this concern, we need to develop a theoretical foundation for the following question:

When are two LMML programs equivalent?

Encapsulating this problem denotationally is commonly known as the
full abstraction
problem
(
28
)
,
where one looks for a sound and complete model that captures
contextual equivalence
.
Two programs
M_{1}
and
M_{2}
are said to be contextually equivalent
if their observable behaviours such as termination are the same in all suitable contexts.

The behaviour of a program in an arbitrary context is difficult to analyze for two reasons.
First, the program might be erased or duplicated before it is executed.
Second, the context can bind free variables in the program.
To overcome these difficulties,
programming language researchers utilise
closed instances of use
(CIU)

(
10
;
37
)
approximations,
which say that equivalence under all suitable contexts
coincides with equivalence under all suitable evaluation contexts, heaps, and substitutions that close all free variables.

In LMML, there are two kinds of variables.
Local variables
x,y,z
are bound by
\lambda
-abstractions
and substituted in
\beta
-reductions.
Such variables are meant to represent values,
and are substituted in a call-by-value manner.
Global variables
u,v,w
are bound by
\mathbf{letbox}

and substituted in the reduction rule

(\mathbf{letbox}\ u\leftarrow\mathbf{box\ }M_{1}\ \mathbf{in}\ M_{2},h)\rightarrow(M_{2}[M_{1}/u],h)

Such variables are meant to represent unboxed code (
M_{1}
in the above rule),
and are substituted in a call-by-name manner.
Therefore, our definition of closed instances of use
needs to take into account both kinds of substitutions.
For local variables, we consider all closing substitutions that map them to values,
while for global variables, we consider all closing substitutions that map them to arbitrary terms.
In short,

local variables represent closed values, global variables represent open terms

Operational game semantics for imperative metaprogramming

Although CIU approximations suffice for small examples like above,
we need a more powerful tool to reason about contextual equivalences in general.

Operational game semantics

(
25

17

has been successfully used to construct fully abstract models for various programming languages.
It represents the behaviour of a program in a context
as a sequence of interactions between the program and the context.
An interaction is represented as an

and a sequence of actions is called a
trace

The semantics of a program is then given by a set of
all the traces that the program can generate
according to a set of transition rules.
This approach is valued for its intuitive, operational nature
and is particularly well-suited to higher-order imperative programming languages.
Its prominent feature is the use of names to represent in abstract terms the functions
that are being called and communicated between the program and the context when they interact.

For example, consider a simplified trace

\overline{f_{1}}\quad f_{1}(3)\quad\overline{f_{2}}\quad f_{2}(2)\quad\overline{8}

The program and the context alternate in taking actions as if it were a dialogue.

Global variables, ranging over

are a special type of variables that are used in contextual type theories to represent open terms.

LMML features two metaprogramming constructs.
The Box operator
\mathbf{box\ }M
converts a term

into a value

The Letbox operator

The word

Readers familiar with MetaML

3.
Closed Instances of Use

Closed Instances of Use approximation
(
37
)

is widely used in reasoning about program equivalence in higher-order call-by-value languages.
It says that two terms are contextually equivalent
if and only if they are equivalent under all suitable evaluation contexts,
heaps, and closing substitutions.

LMML has two kinds of variables.
Local variables are similar to normal variables in call-by-value languages,
so for every free variable declared as
x:T
in the local variable context,
the closing substitution shall substitute a closed value of type
T
for
x
.

Global variables, on the other hand, are declared as
u:\Gamma\vdash T
in the global variable context,
which says that
u
represents a term of type
T
under local variable context
\Gamma
.
Also, when a substitution for
u
is created by the (Letbox) rule,
what gets substituted is exactly a term of type
T
under local variable context
\Gamma
.
Therefore, for every such global variable
u
,
the closing substitution shall substitute a term of type
T
under local variable context
\Gamma
.

The distinction between local and global variables can now be summarised as:
“local variables represent closed values, global variables represent open terms.”
Note that the word “open” here means that the term might contain free variables,
but does not have to.

Definition 0 (Closed Instances of Use).

Given two terms
\Sigma;\Psi;\Gamma\vdash_{i}M_{1},M_{2}:T
,
we define
M_{1}\lesssim^{\mathrm{CIU}}M_{2}
to hold if,
for any global substitution
\Sigma^{\prime};\cdot\vdash\sigma:\Psi
,
local substitution
\Sigma^{\prime};\cdot;\cdot\vdash_{i}\delta:\Gamma
,
evaluation context
\Sigma^{\prime};\cdot;\cdot\vdash K:(\cdot;\cdot;i;T)\rightarrow(\cdot;\cdot;i^{\prime};T^{\prime})
,
and heap
\Sigma^{\prime};\cdot;\cdot\vdash h:\mathbf{heap}

such that
\Sigma^{\prime}\supseteq\Sigma
,
if
(K[M_{1}[\sigma][\delta]],h)\Downarrow
then
(K[M_{2}[\sigma][\delta]],h)\Downarrow
.

Note that although we write the global substitution as
\Sigma^{\prime};\cdot\vdash\sigma:\Psi
,
we are not saying that
\sigma(u)
must be a closed term.
By definition, this notation means
\Sigma^{\prime};\cdot;\Gamma\vdash\sigma(u):T

for all
u:\Gamma\vdash T
in
\Psi
.
In other words,
\sigma(u)
can contain free local variables as declared in
\Psi
,
but should not introduce any new free global variables.

The “elimination rule” for

4.
Trace Model

This section presents the trace model of LMML.
To this end, we shall introduce a labelled transition system
that will generate traces for a given term.
Intuitively, they can be viewed as an abstract record of interaction between the term and a context.
In particular, whenever functions or pieces of code are exchanged between the term and the context,
the values will be represented symbolically using names,
so that syntactically different but semantically equivalent values will not be distinguishable.
In a similar spirit, a location in the program heap will be visible to the context only if it has been revealed.

4.1.
Names

Names are a representation of closed higher-order values.
They expose the type of a value but encapsulate the underlying syntax.
We will rely on an infinite set of names

,
partitioned into
function names
(
\mathrm{FNames}
) and

(
\mathrm{BNames}
).
The two sets will be used to represent function and box (code) values respectively.
In line with Lemma
2
,
we assume that
\mathrm{FNames}
and
\mathrm{BNames}

are further partitioned by

\mathrm{FNames}=\biguplus_{(T_{1},T_{2},i)\in\mathrm{FTyp}}\mathrm{FNames}_{T_{1}\rightarrow T_{2},i}
where
\mathrm{FTyp}=\{(T_{1},T_{2},i)\mid\ \vdash_{i}T_{1}\rightarrow T_{2}:\mathbf{typ}\}
,
and
\mathrm{BNames}=\biguplus_{(\Gamma,T)\in\mathrm{BTyp}}\mathrm{BNames}_{\Box(\Gamma\vdash T),1}
where
\mathrm{BTyp}=\{(\Gamma,T)\mid\ \vdash_{1}\Box(\Gamma\vdash T):\mathbf{typ}\}
,
to reflect the possible types of values.
We assume that all the constituent sets are countably infinite.
We will use
f
,
b
and
n
to range over
\mathrm{FNames}
,
\mathrm{BNames}
and
\mathrm{Names}
respectively.
We have typing rule

n\in\mathrm{Names}_{T,i}

i^{\prime}\geq i

(Tm-Name)

\Sigma;\Psi;\Gamma\vdash_{i^{\prime}}n:T

A name
n
is considered as closed value in the operational semantics,
and subsumes any substitutions, i.e.,

n[\delta]=n[\sigma]=n
.

To handle box names operationally, we add one special reduction rule

(Letbox name)

(\mathbf{letbox}\ u\leftarrow b\ \mathbf{in}\ M,h)\rightarrow(M[\#b/u],h)

where the symbol
\#b
denotes the result of removing the outermost box of
b
.
Like
u
, all the occurrences of
\#b
should be associated with a local substitution
that closes all the free local variables in it.
Accordingly, we have typing rule

b\in\mathrm{Names}_{\Box(\Gamma^{\prime}\vdash T),1}

\Sigma;\Psi;\Gamma\vdash_{i}\delta:\Gamma^{\prime}

(Tm-Unbox)

\Sigma;\Psi;\Gamma\vdash_{i}\#b^{\delta}:T

Substitutions on
\#b^{\delta}
are defined as

(\#b^{\delta})[\delta^{\prime}]=\#b^{\delta[\delta^{\prime}]}

and
(\#b^{\delta})[\sigma]=\#b^{\delta[\sigma]}
.
The term
\#b^{\delta}
is a redex in the operational semantics.

For a unified treatment of values of box type,
we define
\#(\mathbf{box\ }M)=M
.
One can verify that the above statements also hold if we change all occurrences of
b
to
\mathbf{box\ }M
.

4.2.
Value abstraction

As already mentioned, function and box values will be abstracted by names in our traces,
while ground values and and locations will be represented literally.
To keep track of abstractions,
we need a notation that links values to the set of their possible abstractions.
When the abstraction is a name,
we will also need to record the correspondence between the name and the underlying value.

Definition 0 (value abstraction).

Given a closed value
\Sigma;\cdot;\cdot\vdash_{i}V:T
,
we define its abstraction set
\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}V:T)

by cases from Lemma
2
.

•

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}():\mathbf{Unit})\overset{\triangle}{=}\{((),\emptyset)\}
.

•

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}\widehat{n}:\mathbf{Int})\overset{\triangle}{=}\{(\widehat{n},\emptyset)\}
.

•

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}\ell:\mathbf{ref\ }T)\overset{\triangle}{=}\{(\ell,\emptyset)\}
.

•

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}V:T_{1}\rightarrow T_{2})\overset{\triangle}{=}\{(f,f\mapsto V)\mid f\in\mathrm{FNames}_{T_{1}\rightarrow T_{2},i}\}
.

•

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{1}V:\Box(\Gamma\vdash T))\overset{\triangle}{=}\{(b,b\mapsto V)\mid f\in\mathrm{BNames}_{\Box(\Gamma\vdash T),1}\}
.

Throughout the paper, we use
A
to refer to any possible abstraction, i.e.
A
ranges over unit, numerals, locations and names.
We use
\nu(A)
to denote the set of names occurring in
A
,
and
\mu(A)
for the set of locations occurring in
A
.
Both
\nu(A)
and
\mu(A)
are either empty or singleton.

Having defined what it means to abstract values,
we now lift the process to local substitutions and heaps,
where we want to replace all the participating values with corresponding abstractions.
We use
\rho
and
\chi
to refer to abstract local substitutions and heaps respectively.

Given a local substitution
\Sigma;\cdot;\cdot\vdash_{i}\delta:\Gamma
,
we let

\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}\delta:\Gamma)\overset{\triangle}{=}\{(\rho,\bigcup_{x}\gamma_{x})\mid\mathrm{dom}(\rho)=\mathrm{dom}(\delta),(\rho(x),\gamma_{x})\in\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}\delta(x):\Gamma(x)),\cap_{x\in\mathrm{dom}(\rho)}\nu(\rho(x))=\emptyset\}
.
Given a heap
\Sigma;\cdot;\cdot\vdash h:\mathbf{heap}
,
let
\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash h:\mathbf{heap})\overset{\triangle}{=}\{(\chi,\bigcup_{\ell}\gamma_{\ell})\mid\mathrm{dom}(\chi)=\mathrm{dom}(h),(\chi(\ell),\gamma_{\ell})\in\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{i}h(\ell):\Sigma(\ell)),\cap_{\ell\in\mathrm{dom}(\chi)}\nu(\chi(\ell))=\emptyset\}
.
We define
\nu(\chi)=\biguplus_{\ell}\nu(\chi(\ell))
, i.e.
\nu(\chi)
contains all names in
\chi
.
We define
\mu(\rho)=\biguplus_{x}\mu(\rho(x))
, i.e.
\mu(\rho)
contains all locations in
\rho
.

4.3.
Actions

In our model, the meaning of a program will be interpreted as a set of traces.
A trace will be a sequence of actions alternating between the program
and the context. Traditionally in game semantics, the program is referred to as P (Player, Proponent)
and the context as O (Opponent).
We will stick to this terminology below for compatibility with earlier works in the area.
Intuitively, the actions should be viewed as abstractions of calls and returns made by the program or context.
Traditionally, the former are called questions and the latter are answers.
Note that actions will also feature abstract heaps
\Sigma;\cdot;\cdot\vdash\chi:\mathbf{heap}
,
which are an abstraction of the part
of the heap that was exposed during the interaction.

Our semantics will be based on the following kinds of actions.

•

Player Answer (PA)
(\overline{A},\Sigma,\chi)
.
Program replies to a previous question with the answer
\Sigma;\cdot;\cdot\vdash_{i}A:T
,
setting the values of shared locations to
\Sigma;\cdot;\cdot\vdash\chi:\mathbf{heap}
.

•

Player Question of Function (PQF)
(\overline{f}(A),\Sigma,\chi)
.
Program asks for the result of applying
f\in\mathrm{FNames}_{T_{1}\rightarrow T_{2},i}
to the abstract value
\Sigma;\cdot;\cdot\vdash_{i}A:T_{1}
,
setting the values of shared locations to
\Sigma;\cdot;\cdot\vdash\chi:\mathbf{heap}
.

•

Player Question of Box (PRB)
(\overline{\mathbf{run\ }b^{\delta}},\Sigma,\chi)
.
Program asks for the result of running (unboxing) the box name
b\in\mathrm{BNames}_{\Box(\Gamma\vdash T)}

under abstract local substitution
\Sigma;\cdot;\cdot\vdash_{i}\rho:\Gamma
,
setting the values of shared locations to
\Sigma;\cdot;\cdot\vdash\chi:\mathbf{heap}
.

•

Opponent Answer (OA)
(A,\Sigma,\chi)
, Opponent Question of Function (OQF)
(f(A),\Sigma,\chi)
,
and Opponent Question of Box (OQB)
(\mathbf{run\ }b^{\rho},\Sigma,\chi)
are similar,
except that they are initiated by the context.

An action is legitimate only if

\chi
is closed with respect to reachable locations and
disjoint names are used for abstraction:

\chi(\ell)=\ell^{\prime}
implies
\ell^{\prime}\in\mathrm{dom}(\chi)
and
\bigcap_{\ell\in\mathrm{dom}(\chi)}\nu(\chi(\ell))=\emptyset
.

4.4.
Configurations and transitions

Finally, we define the labelled transition system (LTS) that will generate traces from terms.
We start off by discussing the shape of its configurations.

A
passive configuration
describes a moment when the context (Opponent) is about to initiate a computation.
It is a tuple
(\Sigma,h,\gamma,\phi,\xi,\theta)
where

\Sigma;\cdot;\cdot\vdash h:\mathbf{heap}
is the heap,
\gamma
maps function and box names to the value that they represent,

\phi\subseteq\mathrm{Names}
collects all the names that have been introduced so far,

and
\theta\subseteq\mathrm{dom}(h)
is the set of locations currently shared by program and context.

Following an action by the context,
passive configurations will evolve into active ones,
which we define next.

Active configurations
have the form

(M,i,T,\Sigma,h,\gamma,\phi,\xi,\theta)

where
\Sigma;\cdot;\cdot\vdash_{i}M:T
is a term and other components are as defined above.
Active configurations correspond to computations by the program (Player).
An active configuration can evolve into another active configuration through silent moves,
or into a passive one after the program performs an action.

4.5.

To start defining the trace semantics,
we first need to define the initial configuration induced by an arbitrary term

To handle free global variables in

\mathbf{AVal}(\Sigma;\cdot\vdash\sigma:\Psi)\overset{\triangle}{=}\{(\eta,\bigcup_{u}\gamma_{u})\mid\mathrm{dom}(\eta)=\mathrm{dom}(\sigma),\allowbreak\eta(u)=\#(\eta^{\prime}(u)),(\eta^{\prime}(u),\gamma_{u})\in\mathbf{AVal}(\Sigma;\cdot;\cdot\vdash_{1}\mathbf{box\ }\sigma(u):\Box(\Gamma\vdash T))\text{ for all }u:(\Gamma\vdash T)\in\Psi,\cap_{u\in\mathrm{dom}(\eta)}\nu(\eta(u))=\emptyset\}

We use

Reminicent of Theorem
4

the initial configurations are parameterized by the term

an abstract global substitution
\eta

an abstract local substitution
\rho
,
and an abstract heap

Definition 0 (Initial configurations).

Given a term
\Sigma;\Psi;\Gamma\vdash_{i}M:T

Below we define the set of such traces
\mathrm{Tr}(\mathbf{C})

\mathbf{C}

Definition 0 (Derived traces).

Given two configurations
\mathbf{C}

\mathbf{C}^{\prime}

Given two terms

To show completeness, we prove a definability property stating that,
for any well-behaved sequence of actions,
we can find a configuration that generates this trace only.

We say that a name is

as the codomain of the substitution in a (QB) action,

We say that a (PA) (resp. (OA)) action

Related Work

Type systems for imperative MetaML

Purely functional MetaML as proposed by
35

was one of the first safe multi-stage programming languages with explicit annotations.
Since then, many type systems for imperative MetaML have been developed,
with a primary focus on designing a safe type system for higher-order references of code.
Notable examples include closed types
(
6
)
,
refined environment classifiers
(
21
;
16
)
,
Mint
(
39
)
,
and
\lambda^{\oslash}

(
19
;
20
)
.
These type systems view scope extrusion as undesirable,
and prevent a piece of open code such as
\langle{x}\rangle
(or, in our term,
\mathbf{box\ }x
)
from being stored in a reference cell at all.
Another line of work such as MetaOCaml
23
;
22

and MacoCaml
(
41
;
7
)

gives up static type safety
and relies on a dynamic scope extrusion detection when dereferencing a cell at runtime.
In the former approach, open code cannot be stored.
In the latter approach, open code can be stored but cannot be used.
However, as we have shown in this paper,
there are situations where the ability to store and use open code is useful.
And scope extrusion does not necessarily lead to type unsafety,
as long as the type system reasons about free variables in code values properly.

Contextual type theory

Contextual modal type theory
(
29
;
31
;
30
)

was originally developed for recursively analyzing open term via higher-order pattern matching.
In these systems, there is a hard division between
the meta language that analyzes and object language that is analyzed.
Therefore, these type systems do not support running code,
which is essentially promoting the object language into the meta language.
Mœbius
(
18
)

is the first so-called homogeneous contextual type theory
where there is no distinction between the meta language and the object language,
and it supports running code.
However, its operational semantics is not type safe
as there is no guarantee of progress, i.e. a well-typed program might get stuck.
Layered modal type theory
(
11
)

achieves type safety by restricting the depth of nested code,
and is most similar to our work.
There has been an extension of the layered approach to dependent types
12
,
but this is orthogonal to our concern.
All of the above systems are purely functional; in contrast, our contribution is the design of such a (layered modal type) system for higher-order references of arbitrary open code.
We drop the ability to pattern-match on code because this would make full abstraction trivial,
since any syntactically different code would be distinguishable by pattern matching.

Operational game semantics

Game semantics has been a powerful tool to obtain fully abstract models for a variety of programming languages.
Many such models are categorical constructions
(
1

14

32

In contrast, the more recent operational game semantics

The system LMML presented in this paper only has two layers.
Although this already covers most practical use cases of generative metaprogramming,
there are scenarios where more than two layers are needed.

13

This generalization requires more work

We believe that if we generalize our system to

we can retain the type safety proof by following

However, adapting the CIU and full abstraction proofs will require some more work.
In CIU, for example,

\displaystyle\begin{aligned} \vdash_{1}\mathbf{rec}\ f(n).\lambda xy.&\mathbf{if}\ n=0\ \mathbf{then}\ {y:=1}\\
&\mathbf{else}\ (f\ (n-1)\ x\ y;y:=!y*x)\end{aligned}

\displaystyle\colon\mathbf{Int}\rightarrow\mathbf{Int}\rightarrow\mathbf{ref\ }\mathbf{Int}\rightarrow\mathbf{Unit}

\displaystyle\begin{aligned} \vdash_{1}\mathbf{rec\ }f(n).\lambda xy.&\mathbf{if}\ n=0\ \mathbf{then}\ \mathbf{letbox}\ u\leftarrow y\ \mathbf{in}\ \mathbf{box\ }(u^{y/y}:=1)\\

\displaystyle\vdash_{1}\lambda n.\mathbf{letbox}\ u\leftarrow\mathit{power\_staged\_gen}\ n\ (\mathbf{box\ }x)\ (\mathbf{box\ }y)\ \mathbf{in}\ \lambda xy.u^{x/x,y/y}

Proof.

It suffices to prove that

\mathrm{Tr}(\mathit{power\_staged})\subsetneqq\mathrm{Tr}(\mathit{power})=

\mathrm{Tr}(\lambda nxy.\mathit{power\_staged}\ n\ x\ y)

by Theorem
7
.
We first prove
\mathrm{Tr}(\mathit{power})=\mathrm{Tr}(\lambda nxy.\mathit{power\_staged}\ n\ x\ y)
.
Consider the representative traces (again
\Sigma
is omitted for brevity)

\displaystyle\mathtt{t}_{1}\ =

\displaystyle(\overline{f_{1}},\cdot)\;(f_{1}(3),\cdot)\;(\overline{f_{2}},\cdot)\;(f_{2}(2),\cdot)\;(\overline{f_{3}},\cdot)

\displaystyle(f_{3}(\ell_{1}),\{\ell_{1}\mapsto 0\})\;(\overline{()},\{\ell_{1}\mapsto 8\})

and

\mathtt{t}_{2}\ =\ (\overline{f_{1}},\cdot)\;(f_{1}(-1),\cdot)\;(\overline{f_{2}},\cdot)

All traces that can be generated from
\mathit{power}
and
\lambda nxy.\mathit{power\_staged}\ n\ x\ y

can be represented as a tree.
The trace
\mathtt{t}_{1}
is a representative path in the tree,
and other traces can be obtained by branching at the three (OQ) actions.
Due to higher-order references, the opponent can also freely return to previous nodes
and pose questions on the function names with different arguments.
Any path, as long as it follows the transition rules, is valid up to the action
of the form

because no real computation is done until all three arguments are supplied.

Once
n
,
x
and
y
