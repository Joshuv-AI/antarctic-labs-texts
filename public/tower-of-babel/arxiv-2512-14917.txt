Abstract
. Code reasoning tasks are becoming prevalent in large language model (LLM) assessments. Existing benchmarks involve simple programs, failing to represent real-world complexities such as inter- or intra-procedural dependencies, core or third-party API calls, highly nested constructs, and non-primitive complex types. Evaluating LLMs under such a simplistic setting poses a significant threat to assumptions about their generalizability in practice. To enable a more realistic evaluation of code reasoning, this paper proposes RE2-Bench 1 1 1 RE2-Bench stands for Re alistic Re soning , a benchmark of 1 , 101 1,101 reasoning problems, including 195 195 drawn from mature real-world projects. RE2-Bench leverages static and dynamic program analysis to automatically serialize/deserialize compound, complex, and custom types galore in real-world code, going far beyond only primitive types used in prior techniques. A key feature of RE2-Bench is categorizing each reasoning problem as Easy or Hard via a principled majority-vote mechanism over nine interpretable code complexity metrics, resulting in two well-separated and semantically meaningful problem difficulty categories, suitable for precise calibration of LLM reasoning ability. A comprehensive evaluation of six general and reasoning LLMs on two widely-used code reasoning tasks—input and output prediction—using RE2-Bench shows a significant performance drop from Easy to Hard problems ( 51.50 % 51.50\% for input prediction and 42.15 % 42.15\% for output prediction), confirming inflated and unrealistic assumptions about the reasoning capabilities of LLMs. RE2-Bench integrates static analysis algorithms and visualization tools to analyze the impact of various programming constructs, call chain length, prompting/training strategies, overall program complexity, and individual complexity metrics on the reasoning abilities of LLMs. We also follow a systematic, complexity-informed approach for reasoning failure analysis, categorizing them into 18 18 groups. This categorization, along with case studies, can help the development of future LLMs for better code reasoning.

Empirical Evaluation

We use
RE2-Bench

Effectiveness.
To what extent do
RE2-Bench

Impacting Factors.
What factors make input and output predictions more challenging for LLMs? To what extent does encoding reasoning into the training strategy help LLMs in code reasoning?

Reasoning Failure Analysis.
What are the most common root causes of reasoning failures?

Ablation Study.
To what extent do different prompt engineering components contribute to the overall reasoning performance of LLMs?

3.2.1.
Evaluation Tasks

Existing research has explored various tasks to assess different aspects of LLM’s code reasoning, including specification reasoning, specification inference, dynamic semantic reasoning, structural reasoning, and code execution simulation, and prediction of input, output, coverage, variable values, or execution path (next statement or the entire execution trace). Among these tasks, we chose input and output prediction in our experiments due to three reasons: (1) prior research has shown that LLMs that perform well in these tasks may struggle in other reasoning tasks. Thereby, input and output prediction tasks can determine the
upper bound
for LLM’s code reasoning abilities. (2) Furthermore, these tasks directly test forward and backward end-to-end functional reasoning, supporting consistent and scalable evaluation concerning the complexities of real-world projects. (3) These tasks are the most prevalent ones in the evaluation of the most recent models. In our experiments, we will show that this upper bound drastically drops when LLMs are evaluated under complex real-world settings, motivating future research to evaluate them in other tasks and improve their code reasoning abilities.

3.4.
Evaluation Metrics

RE2-Bench
measures LLM reasoning abilities at two levels of granularity. At the highest level, the reasoning success,
RS_{i}
, is
0
or
1
, i.e., the LLM prediction is identical to the collected ground truth values. This metric, however, is very conservative and unfair. In the example of Figure
3

and
LLM_{y}

one
and
six
of the
seven
properties of the input

RS_{i}=0
for this program. However, the
LLM_{y}
is superior to
LLM_{x}
due to its ability to predict more properties.

This problem could have been negligible or non-existent for previous code reasoning benchmarks. However, since

To enable more insightful comparison between the reasoning abilities of the models, we introduce an additional metric to measure the partial reasoning correctness,
RS_{partial_{i}}
, as below:

(1)

RS_{partial_{i}}=\dfrac{\sum\limits_{j=1}^{m}\llbracket Pred_{j}=GT_{j}\rrbracket}{m}

where

is the total number of properties for each input or output variable to be predicted for problem
i
,
Pred_{j}
is the prediction of LLM for that property, and

is the ground-truth value for the property. Using this metric, the LLMs mentioned in the previous example (
LLM_{x}
and
LLM_{y}
) achieve
RS_{partial_{i}}=0.14

(\frac{1}{7})
and
RS_{partial_{i}}=0.86

(\frac{6}{7})
, respectively, providing a fairer comparison between models. Once all the
RS_{i}
or

values are calculated,

computes the average of them as collective metrics of

and
RS_{partial}
for a group of problems.

3.5.1.
False Negatives in Input Prediction

The possibility of false negatives in output prediction is narrow, since the outputs were either provided by the tests in the datasets, or we executed the tests to collect actual values during test execution. However, false negatives in input prediction are plausible: multiple inputs may result in the same output
(
Dijkstra and Dijkstra 1982
;
Dinges and Agha 2014
)
.

RE2-Bench
automates the detection of such cases for Avatar, ClassEval, CRUXEval, and HumanEval, and updates their reasoning success. To automate false negative detection in input prediction,
RE2-Bench
runs the standalone methods with the predicted inputs by LLMs and the ground truth input separately, and compares their execution results with assertions. For ClassEval, an additional step of initializing the class with the predicted and ground truth
self
arguments before executing methods is required. Once confirmed as a false negative,
RE2-Bench
updates the
RS
and
RS_{partial}
values to one.
All the reported numbers in the paper reflect the correction of false negatives to true positives.

4.
Related Work

RE2-Bench
is related to
studies on code reasoning tasks
(
Gu et al. 2024
;
Liu et al. 2024
;
Chen et al. 2024a
;
Beger and Dutta 2025
;
Kopel 2025
;
Le-Cong et al. 2025
;
Yang et al. 2025
;
Sun et al. 2025
;
Bouras et al. 2025
;
Gautam et al. 2025
)
. CRUXEval
(
Gu et al. 2024
)
and CodeMind
(
Liu et al. 2024
)
are pioneers in evaluating LLMs for different code reasoning tasks. CRUXEval reasoning tasks are input prediction (given the output) and output prediction (given the inputs). CodeMind proposed three tasks (independent execution reasoning, dependent execution reasoning, and specification reasoning) to evaluate LLMs’ inductive code reasoning abilities. REval
(
Chen et al. 2024a
)
took one step forward to include the runtime behavior in the reasoning process using four runtime prediction tasks: code coverage prediction, program state prediction, execution path prediction, and output prediction. CoCoNUT
(
Beger and Dutta 2025
)
challenges LLMs to generate a trace of line numbers executed by the program for a given set of inputs.
EquiBench
(
Wei et al. 2025
)
assesses LLMs’ understanding of code execution semantics by requiring them to judge whether two programs produce equivalent outputs for every possible input.
These techniques either leveraged LLMs to generate the reasoning problem or used programs from existing programming benchmarks. As we showed in this paper, the reasoning problems used in prior studies are far from representing the complexities of real-world programs, failing to challenge the reasoning abilities of LLMs properly (§
1
). Compared to these techniques,
RE2-Bench
extracts reasoning problems from real-world projects.

Two closely related works are EXE
(
Kopel 2025
)
and CodeSense
(
Roy et al. 2025
)
that evaluate LLM code reasoning on
open-source Python repositories. Similar to CRUXEval, EXE relies on LLMs to generate test inputs, limiting them to simple and primitive variable types.
CodeSence collects input-output pairs from actual execution trace logs, but rules out those with non-primitive data types.
To better preserve the complexity of real-world code inputs,
RE2-Bench
collects actual runtime inputs by executing project test cases. It goes beyond primitive and core compound types and can serialize any complex custom type into a readable JSON-like format. Furthermore,
RE2-Bench
follows a systematic approach to categorize the reasoning benchmarks into three difficulty levels.

5.
Threats to Validity

External Validity.

To mitigate the threat of generalizing results to other experimental settings (other models, benchmarks, and tasks), our selected models cover both open-source and API access models, as well as general and reasoning models.
Concerning new benchmarks,
RE2-Bench
pipeline is generic, i.e., it can convert any Python project with executable test suites into reasoning problems. The rigorous design of difficulty-level categorization of problems makes
RE2-Bench
adaptive to new problems and new LLM capabilities, as discussed in the paper.
As a proof of concept, this paper shows that the code reasoning abilities of LLMs in two widely used tasks of input and output prediction can be significantly challenged under real-world settings.
RE2-Bench
currently focuses on Python, as the majority of the programming datasets widely use it. Focusing on one language also enables systematic control over complexity metrics and avoids language-induced variance.

Internal Validity.

LLMs are inherently non-deterministic. One way to account for non-determinism is repeating the experiments
k
times, and reporting the
RS@k
results.
However, a similar computation is not possible for
RS_{partial}
due to the inherent dependency between attributes of complex objects. Given that in practice, users of LLMs do not repeatedly prompt LLMs and pick the correct solution, if it exists, this design decision does not pose a threat to the validity of the results.

Construct Validity.

To account for the imbalance between the problems in each difficulty category,
RE2-Bench
systematically sampled
Easy
reasoning problems, equal to the number of
Hard
problems.

6.
Conclusion

In this paper, we introduce
RE2-Bench
, a curated collection of existing programming benchmarks tailored for code reasoning, in which reasoning problems are categorized into two difficulty levels. We evaluate six widely used reasoning and general LLMs on input and output prediction tasks and observe a substantial performance drop from Easy to Hard programs, revealing that existing benchmarks may overstate LLMs’ reasoning capabilities. For future work, we plan to support more reasoning tasks and programming languages, and implement a more systematic approach for detecting false negatives in input prediction for SWE-bench reasoning problems.
