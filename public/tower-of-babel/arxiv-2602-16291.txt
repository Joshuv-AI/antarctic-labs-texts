Abstract
. Just as the λ \lambda -calculus uses three primitives (abstraction, application, variable) as the foundation of functional programming, inheritance-calculus uses three primitives (record, definition, inheritance) as the foundation of declarative programming. It trivially embeds the λ \lambda -calculus, although the entire semantics rests solely on set theory; as a consequence, all constructs including inheritance are inherently commutative, idempotent, and associative; the linearization problem of multiple inheritance does not arise. This induces a fully abstract semantics of the lazy λ \lambda -calculus with respect to Böhm tree equivalence ( 9 ) . Inheritance-calculus is distilled from MIXINv2, a practical implementation in which we observed further emergent phenomena: the same code acts as different function colors ( 64 ) ; ordinary arithmetic yields the relational semantics of logic programming ( 76 ) ; self-reference resolves to multiple targets; and programs are immune to the Expression Problem ( 78 ) . This makes inheritance-calculus strictly more expressive than the λ \lambda -calculus in both common sense and Felleisen’s sense ( 38 ) .

Contributions

•

We present inheritance-calculus, a minimal computational model for
declarative programming that contains three constructs (record,
definition, inheritance) and no functions or scalar types.

•

The mixin is a single abstraction that unifies class,

Inheritance

An inheritance is written as a reference
that navigates the scope hierarchy upward and then projects
properties downward. The upward navigation admits two equivalent
notations:

Named form:

\ell_{\mathrm{up}}.\mathbf{this}.\ell_{\mathrm{down},1}\ldots\ell_{\mathrm{down},k}

Outer.this.field

Each
\{\ldots\}

Indexed form:

\uparrow^{\!n}.\ell_{\mathrm{down},1}\ldots\ell_{\mathrm{down},k}

(
27
)

n=0

Both forms retrieve the target scope, that is, the fully inherited record

from it.
The named form desugars to the indexed form during parsing
(Section
3

A new scope level is created at each
\{\ldots\}
record literal.
The scope contains all properties of that mixin, including those

For example,
\{a\mapsto\{\},\;b\mapsto\{\}\}
is a single mixin whose scope
contains both

b

where

is a reference to a record containing

Inheritance sources do not create additional scope levels.

•

\mathrm{Foo}.\mathbf{this}
(equivalently,
\uparrow^{\!n}
where

\mathrm{Foo}
is

•

•

Properties

The properties of a path are its own properties together with

(1)

Intuitively,

Since a mixin can play the role of a method,

Intuitively,

Concretely,

\mathtt{bases}(p)=\left\{\;p_{\mathrm{target}}\;\left|\;\begin{aligned} &p_{\mathrm{override}}\in\mathtt{overrides}(p),\\

Reference resolution

Intuitively,
\mathtt{resolve}
turns a syntactic reference into the
set of paths it points to in the fully inherited tree.
It takes an inheritance-site path
p_{\mathrm{site}}
,
a definition-site path

and downward projections

Resolution proceeds in two phases:

starting from the enclosing scope

mapping the definition-site path to inheritance-site paths;
then the downward projections

(5)

\mathtt{resolve}(p_{\mathrm{site}},\;p_{\mathrm{def}},\;n,\;\ell_{\mathrm{down},*})=\\
\bigl\{\;p_{\mathrm{current}}\mathbin{\triangleright}\ell_{\mathrm{down},1}\mathbin{\triangleright}\cdots\mathbin{\triangleright}\ell_{\mathrm{down},k}\;\big|\;p_{\mathrm{current}}\in\mathtt{this}(\{p_{\mathrm{site}}\},\;\mathtt{init}(p_{\mathrm{def}}),\;n)\;\bigr\}

When multiple routes exist due to multi-path inheritance,
they may yield different target paths; all are collected.
We now define
\mathtt{this}
.

Qualified this resolution

\mathtt{this}
answers the question:
“in the fully inherited tree, where does

Each step finds, among the supers of every path in the

After

(6)

\mathtt{this}(S,\;p_{\mathrm{def}},\;n)=\begin{cases}S&\text{if }n=0\\[6.0pt]
\mathtt{this}\!\left(\left\{\;p_{\mathrm{site}}\;\left|\;\begin{aligned} &p_{\mathrm{current}}\in S,\\
&(p_{\mathrm{site}},\;p_{\mathrm{override}})\in\mathtt{supers}(p_{\mathrm{current}}),\\
&\text{s.t.}\;p_{\mathrm{override}}=p_{\mathrm{def}}\end{aligned}\right.\right\},\;\mathtt{init}(p_{\mathrm{def}}),\;n-1\right)&\text{if }n>0\end{cases}

At each step
\mathtt{init}
shortens

Since

is a nonnegative integer, the recursion terminates.

This completes the chain of definitions needed to compute
\mathtt{properties}(p)

3.2.
Recursive Evaluation

The six equations
(
1
)–(
6
) define set membership
recursively:

\ell\in\mathtt{properties}(p)
holds if and only if it can
be established by a finite chain of applications of
these equations.
Well-definedness follows from a termination argument:
if the recursive evaluation terminates, the reachable
dependency subgraph is finite and acyclic, and the equations
have a unique solution
(Appendix
C
).
When no finite derivation exists for a given query, the
recursive evaluation does not terminate, analogous to
divergence in the
\lambda
-calculus.

The equations
are
the interpreter: the observer
drives the computation by choosing which path to inspect,
and the equations unfold on demand.
The equations are pure and order-independent, so the
reflexive-transitive closure
\mathtt{bases}^{*}

in (
2
) may be explored breadth-first or
depth-first without affecting the result;
paths may be
interned
so that structural equality
reduces to pointer equality;
and the six equations form a memoizable
dynamic-programming recurrence keyed by paths.
No separate operational semantics is needed.

4.2.
Expressive Asymmetry

Two
\lambda
-terms that are Böhm-tree equivalent—and
therefore indistinguishable in the
\lambda
-calculus—can be
separated in inheritance-calculus by inheriting new observable
projections onto an existing definition via open extension.
By Felleisen’s expressiveness
criterion
(
38

, inheritance-calculus is
strictly more expressive than its sublanguage
\mathscr{L}_{0}

(isomorphic to the lazy
\lambda
-calculus under observational
equivalence):
the forward embedding is macro-expressible
(Theorem
A.2
), but
\mathscr{L}_{0}

cannot macro-express inheritance
(Theorem
A.3
).
The formal definitions, constructions, and proofs are given in
Appendix
A

the separating construction is itself a miniature instance of
the Expression Problem, adding a new observable projection to
an existing definition without modifying it.

The underlying mechanism is open extension: mixin
definitions compose via open recursion, so existing
definitions gain new observable properties without
modification. In the
\lambda
-calculus, a function’s result
is closed—there is no way to add new observable projections
to an already-computed value without modifying the function’s
definition.

Function color blindness:

Structured effects require no dedicated mechanism.
Business logic in MIXINv2 declares abstract property slots;

Minimal Turing-complete models

Schönfinkel

Each of these models achieves Turing completeness by

Semantic descriptions of the
\lambda
-calculus

The semantics of the
\lambda
-calculus can be defined in
several fundamentally different ways.

Operational semantics
takes
\beta

(\lambda x.\,M)\,N\to M[N/x]
as the primitive notion of

(
19
;
20
;
9
)

This requires capture-avoiding substitution, a mechanism whose
subtleties motivated de Bruijn

(
27
)
and explicit substitution

(
1
)
, and a choice of evaluation
strategy: call-by-name versus
call-by-value
(
65
)
or the lazy
strategy of Abramsky
(
6
)
.

Denotational semantics

(
72
;
73
)

interprets terms in a mathematical domain, but giving meaning
to
\beta
-reduction requires a reflexive domain

D\cong[D\to D]
, which has no set-theoretic solution by
Cantor’s theorem; Scott’s
D_{\infty}
resolves this by
constructing

as an inverse limit of continuous
lattices
(
74
)
.
The resulting semantics is adequate but not fully
abstract
(
66
;
61
)
:
it identifies terms that observational equivalence
distinguishes
(
65
)
.

Game semantics

(
3
;
46

62
)

achieves full abstraction for PCF and for the lazy

\lambda
-calculus
(
5
;
4
)

at the cost of considerably more intricate mathematical
machinery (arenas, strategies, innocence conditions).
In each of these approaches, the function space
[D\to D]

is the central obstacle: operational semantics needs it
implicitly (via substitution), denotational semantics
constructs it explicitly, and game semantics refines it via
strategies.
None of these approaches yields a semantics of the lazy

\lambda
-calculus that simultaneously lives in naive set
theory and is fully abstract: Scott’s
D_{\infty}
is adequate
but not fully abstract, and game semantics is fully abstract
but requires machinery (arenas, strategies, innocence
conditions) far beyond set theory.
In all three approaches the semantic objects are not directly
computable: Scott’s denotations are elements of an uncountable
continuous lattice, game-semantic strategies are infinite trees
over move sequences, and the function space
[D\to D]
has no
effective enumeration.
Each framework therefore requires a separate operational
semantics to define how computation proceeds; the denotational or
game-semantic model then serves as a mathematical proxy whose
adequacy with respect to the operational semantics must be proved
separately.
None of them eliminates the function space from the semantic
domain; none avoids capture-avoiding substitution; and none
dispenses with reduction rules or evaluation strategies.

Set-theoretic models of the
\lambda
-calculus

Several families of

In each family the denotation of a term is a set-theoretic

None of these denotations can be computed from the term alone;

All three families are semantic

None of them is a self-contained calculus with its own

Moreover, graph and filter models’ equational theories

Recursive equations and fixpoint semantics

Van Emden and Kowalski

showed that

three equivalent characterizations:
operational (SLD resolution), model-theoretic (least Herbrand
model), and fixed-point (least fixed point of the immediate
consequence operator

on the powerset of ground atoms).
The
T_{P}
operator is monotone on a complete lattice, but
the fixpoint definition and its execution are not isomorphic:
answering a single query requires a search strategy (SLD
resolution), and different strategies (depth-first,
breadth-first, tabling) yield different completeness properties.
The gap between the declarative fixpoint and the procedural
execution is non-trivial.
Aczel
(
7
)
gave a systematic treatment of
inductive definitions via monotone operators on powerset lattices,
providing the logical foundations that Datalog-style semantics
rests on.
Cousot and Cousot
(
23
)
independently
developed abstract interpretation, a framework for program
analysis that computes fixed points on abstract lattices connected
to concrete semantics by Galois connections.
Abstract interpretation
approximates
the behavior of
programs rather than defining it exactly;
the lattice-theoretic technique, however, is shared.
Leroy and Grall
(
57

addressed the
treatment of divergence in big-step operational semantics by
passing from inductive to

definitions;
when divergence already emerges as
non-termination of recursive evaluation, no separate coinductive
formulation is needed.
Each of these prior frameworks operates on its own domain
(Herbrand models, abstract domains, evaluation judgments);
none has been applied to a tree-structured domain of paths
to obtain a fully abstract semantics of the lazy

\lambda
-calculus without function spaces, substitution, or
reduction rules.

7.2.
Inheritance, Objects, and Records

Denotational semantics of inheritance

Cook
(
21
)
gave the first denotational
semantics of inheritance, modeling objects as recursive records and
inheritance as composition of
generators
, which are functions from self
to complete object, and
wrappers
, which are functions that modify
generators, solved by a fixed-point construction.
Cook’s key insight, that inheritance is a general mechanism
applicable to any form of recursive definition and not only
object-oriented methods, is one of the starting points of the
present work.
The model has four primitives—records, functions, generators, and
wrappers—and requires a fixed-point combinator; composition is
asymmetric, as a wrapper modifies a generator but not vice versa.
The fixed-point construction relies on Scott continuity in a
domain of functions; the resulting denotations are not directly
executable, so a separate operational semantics is needed to
define method dispatch and object construction at runtime.

Mixin-based inheritance

Bracha and Cook
(
13
)
formalized mixins as
abstract subclasses, that is, functions from a superclass parameter to a
subclass, unifying the inheritance mechanisms of Smalltalk, Beta,
and CLOS under a single model.
Because mixin application is function composition, it is

neither commutative nor idempotent
: applying the same
mixin twice may produce different results, and applying two
mixins in different orders may yield different linearizations.
The C3 linearization algorithm
(
11
)
was later
developed to impose a deterministic order;
whether linearization is inherent to inheritance or an artifact of
noncommutativity had not been established.
Mixin composition operates at the
method level
: applying a
mixin replaces or extends individual methods in a flat namespace.
There is no recursive merging of nested structure: composing two
mixins that define the same method name results in an override, not
deep merge.
Finally, mixins presuppose the
\lambda
-calculus as their
computational foundation: method bodies are functions, and mixin
application is function composition.
Mixins organize and compose functions but cannot replace
them; without the underlying
\lambda
-calculus, there is nothing
to compose. The mixin mechanism itself is not Turing complete.
Bracha–Cook mixins are therefore not deep-mergeable.

Traits

Schärli et al.
(
70
)
introduced traits as
composable units of behavior. Trait composition is symmetric and
commutative: the sum of two traits is order-independent, which is
a departure from mixin ordering.
However, when two traits provide methods with the
same name, a
conflict
arises and must be explicitly resolved
by the programmer through exclusion or aliasing.
Ducasse et al.
(
33
)
extended the model with a

flattening property
: the semantics of a class is independent
of whether its methods originate from traits or are defined directly.
Like mixins, trait composition is
flat
: it operates on
individual method names, not on nested structures, so same-name
definitions are conflicts rather than recursive merges.
And like mixins, traits presuppose the
\lambda
-calculus: trait
methods are functions, and the computational power resides in those
functions, not in the trait mechanism itself.
Traits are therefore not deep-mergeable mixins either.

Family polymorphism and virtual classes

Ernst
(
37
)
introduced family polymorphism, where
families of mutually dependent classes can be refined together in
subclasses. Ernst, Ostermann, and Cook
(
36
)

formalized this in the virtual class calculus, where classes are
class-valued attributes of objects, accessed via path expressions of
the form
this.out.C
.
The path
this.out
navigates to an enclosing scope.
A notable restriction is that each such path resolves to a

single
class in a
single
enclosing object.
When multiple inheritance routes lead to the same scope, a common
situation under inheritance, single-valued resolution must choose
one route and discard the others, losing information.
The framework provides no mechanism for set-valued resolution.

Object calculi

Abadi and Cardelli
(
2
)
developed a comprehensive
theory of objects, treating objects rather than classes as the
primitive notion. Their calculi include method update and
self-referential objects, but methods are fundamentally functions
that take self as a parameter, and object extension is asymmetric
since method override replaces the previous definition.
Boudol
(
12
)
studied the recursive record
semantics of objects in a call-by-value setting, showing that
self-referential records require an unsafe fixed-point operator.
The unsafe fixed-point operator produces denotations in a domain
where well-definedness depends on the evaluation strategy; the
semantics is therefore inseparable from the operational reduction
rules.
Whether self-reference can be handled without a fixed-point operator
in the object language, for instance through coalgebraic
observation rather than reduction, was not explored in these calculi.

Record calculi

Harper and Pierce
(
41
)
presented a record
calculus based on symmetric concatenation with a type system that
tracks the absence of fields.
When two records define the same label, concatenation
is undefined and raises a type error; the calculus leaves same-label
composition undefined.
Cardelli
(
17
)

studied extensible records with subtyping;
Rémy
(
69
)
gave a type system for records and
variants in ML.
These calculi operate on
flat
records with no nesting and
treat records as
data
, that is, initial algebras: a record is a
finite map from labels to values, fully determined at construction
time. Nested records, self-reference, and lazy observation, which are the
properties needed for records to serve as a computational
substrate, are outside their scope.

DOT calculus

Amin et al.
(
8
)
formalized path-dependent types in
the DOT calculus, the theoretical foundation of Scala’s type system.
DOT paths navigate through objects to reach nested type members,
providing a rich dependent type structure.
DOT includes the
\lambda
-calculus as a sub-language.
DOT stratifies its syntax into terms and types, with types further
divided into abstract type members bounded by
L..U
and concrete
definitions; each stratum requires its own subtyping rules.
Whether these three roles could be unified under a single construct
remains an open question in the DOT line of work.
DOT’s self variable in the object constructor
\nu(x:T)\,d

binds
x
to a single object; when multiple inheritance routes
lead to the same enclosing scope, the resulting intersection type
is unrealizable and Scala rejects it at compile time
(Appendix
B
).
When the path structure is simple enough that no multi-target

\mathtt{this}
resolution is needed, Scala programmers can approximate
deep merge manually: the cake pattern layers traits with

self:
annotations, and object
algebras
(
26
)
compose operations via
trait intersection, both requiring the programmer to write the
merge logic by hand for each level of nesting.

7.3.
Configuration Languages and Module Systems

Configuration languages

CUE
(
77
)
unifies types and values in a single lattice
where unification (
&
) is commutative, associative, and
idempotent.
CUE’s design was motivated by Google’s Borg Configuration
Language (GCL), which used graph unification.
CUE’s lattice includes scalar types with a conflict
semantics where unifying incompatible scalars yields
\bot
; whether
scalars are necessary for a configuration language, or whether
tree structure alone suffices, is an interesting design question.
Jsonnet
(
24
)
provides object inheritance via the

+
operator with mixin semantics: composition is

not
commutative since the right-hand side wins on scalar
conflicts, and deep merging requires explicit opt-in via the
+:

syntax) on a per-field basis, so deep merge is
available but not the default.
Dhall
(
40
)
takes a functional approach: it is a typed

\lambda
-calculus with records, where composition is a record merge
operator, not an inheritance mechanism.

Module systems and deep merge

The NixOS module system
(
31
;
63
)

composes modules by
recursively merging nested attribute sets
,
not by linearization or method-level override, which is the same deep-merge
semantics that distinguishes tree-level inheritance from method-level
composition in prior mixin and trait calculi.
When two modules define the same nested path, their subtrees are
merged rather than overridden.
The NixOS module system incorporates deep merge,
recursive self-reference, deferred evaluation of modules, and a
rich type-checking layer on top.
The same mechanism powers
NixOS system configuration, Home
Manager
(
43
)
, nix-darwin
(
49
)
,
flake-parts
(
44
)
, and dozens of other ecosystems,
collectively managing configurations of arbitrary complexity.
The one aspect that appears not to have been fully addressed is the
semantics of self-reference under multiple inheritance.
When two independent modules that inherit from the same
deferred module are composed, each import introduces its own
declaration of the shared options; the module system’s

mergeOptionDecls
rejects duplicate declarations
with a static error (Appendix
B
).
The module system cannot express that both routes contribute
equally to the same option, that is, the multi-path situation that
recursive merging naturally gives rise to, which motivated the
observational semantics of Section
3
.

7.4.
Our Companion Work

Modular software architectures

Plugin systems, component frameworks, and dependency injection frameworks
enable software extensibility through declarative inheritance. The
symmetric, associative nature of inheritance (Section
3
) explains why such
systems work: components can be inherited in any order without changing
behavior.
MIXINv2
(
85
)

is itself a dependency injection framework:
each scope declares its dependencies as named slots, and
composition resolves them by name across scope boundaries,
making the inheritance-calculus patterns explicit rather than ad hoc.

Union file systems

Union file systems (UnionFS, OverlayFS, AUFS) layer multiple directory
hierarchies to present a unified view. Their semantics resembles
inheritance-calculus in that later layers override earlier layers and files from all
layers remain accessible, but without a formal foundation these systems
resort to ad-hoc choices: asymmetric inheritance, noncommutative
conflict resolution for scalar files, and no late-binding or dynamic
dispatch across layers.
We implemented inheritance-calculus directly as a union file
system
(
84
)
,
obtaining late-binding semantics and dynamic dispatch for file lookups
with no additional mechanism beyond the three primitives.
In package managers, build systems, and OS distributions,
external toolchains transform configuration into file trees;
here, the file system serves as configuration to itself,
and the transformation is inheritance: a

file-system-as-compiler
in which the directory tree is
both the source program and the compilation target.

8.
Future Work

MIXINv2
(
85
)
is an executable implementation of inheritance-calculus
that already goes beyond the untyped calculus presented here:
it includes compile-time checking that all references resolve to
valid paths in the mixin tree, and a foreign-function interface (FFI)
that introduces scalar values from the host language.
The future work described below concerns the distance between this
implementation and a fully practical language, spanning both
theoretical foundations and library-level encodings.

8.1.
Type System

MIXINv2’s existing compile-time checks verify that every
reference path resolves to a property that exists in the inherited
result. Formalizing the soundness of these checks, that is, proving that
well-typed programs do not produce dangling references at
runtime, is one direction of future work.
Such a formalization would relate to the DOT
calculus
(
8
)
in a manner analogous to how
inheritance-calculus relates to the
\lambda
-calculus: a Typed
inheritance-calculus can be viewed as DOT without
\lambda
, retaining
path-dependent types while replacing functions with
mixin inheritance.
A formal type system would be amenable to mechanization in proof
assistants (Coq, Agda) for verifying type safety, progress, and
preservation properties.

Beyond soundness of the existing checks, additional type system
features would strengthen the language.
A key example is
totality checking
: verifying that an
inheritance provides implementations for all required slots, not
merely that references resolve.
In untyped inheritance-calculus, writing
\mathrm{magnitude}\mapsto\{\}

is purely documentary: it defines a structural slot but imposes no
constraint on what must fill it.
Totality checking would enforce such declarations statically,
rejecting inheritances that leave required slots unfilled.

8.2.
Embedding Datalog

Section
6.1
observed that ordinary
arithmetic on Church-encoded values produces the relational
semantics of logic programming as an emergent phenomenon:
trie union is a relation,
\mathtt{bases}
is cross-join,
\mathtt{supers}
is
union, and
\mathtt{properties}
is projection.
Formalizing this observation as an embedding of Datalog
into inheritance-calculus, analogous to the
\lambda
-calculus
embedding of Section
4
, is future
work.
Such an embedding would be structurally notable: the

\lambda
-calculus is inherently lazy, Datalog is inherently
eager, and inheritance-calculus is neither, suggesting that
the two models are projections of the same observational
fixed-point semantics.

8.3.
Standard Library

The remaining items concern the
standard library
: they require
no extensions to the calculus or type system, but involve nontrivial
encodings within the existing framework.

Inheritance-calculus is
open by default
: inheritance
can freely merge any two mixins, and a value may simultaneously
inhabit multiple constructors (e.g.,

\{\mathrm{Zero},\;\mathrm{Odd},\;\mathrm{half}\mapsto\mathrm{Zero}\}
).
This is not a defect; it is the natural trie semantics of the
calculus, and the basis for solving the expression problem
(Section
5
).
However, many operations (e.g., equality testing) assume that values
are
linear
, inhabiting exactly one constructor.
The observer pattern (Section
5
) does not enforce
this: applied to a multi-constructor value, all callbacks fire and
their results are inherited.

Schema validation
can be implemented at the library level
using existing primitives.
An observer can test whether a particular constructor is present,
returning a Boolean; a second Boolean dispatch then branches on the
result.
By chaining such tests, a factory can validate that a value matches
exactly one constructor and carries the required fields.
This does not restrict inheritance itself, which remains
unconstrained, but provides a way to detect invariant violations
before they propagate.

The same technique, an observer returning Boolean followed by Boolean
dispatch, yields
closed pattern matching
.
The observer pattern of Section
5
is inherently

open
: new constructor cases can be added through inheritance.
Closed matching, where exactly one branch is taken, can be encoded as
a
visitor chain
: a linked list of if-then-else nodes, each
testing one constructor and falling through on mismatch.
This is analogous to GHC.Generics’
\mathrm{(:+:)}
sum
representation
(
60
)
, where each link
corresponds to one summand.
An important consequence is that such chains do
not

commute, as they have a fixed order, and therefore cannot be extended
through open inheritance, which is the correct semantics for closed
dispatch.

9.
Conclusion

Immunity to nonextensibility guided the design of
inheritance-calculus.
The emergent phenomena exhibit an expressive asymmetry
between inheritance-calculus and the
\lambda
-calculus.
Inheritance is not a mechanism for organizing functions;
functions are syntactic sugar for inheritance.

Appendix C
Well-Definedness of the Semantic Functions

This appendix proves that the mutually recursive equations
(
1
)–(
6
) are well-defined:
for every query whose recursive evaluation terminates, the
result is uniquely determined.
The proof proceeds by contrapositive: both a cycle and an
infinite acyclic chain in the dependency graph force
divergence, so termination implies that the reachable
subgraph is finite and acyclic, which in turn implies
uniqueness.

Definition C.1 (Dependency graph).

Fix an AST with its primitive functions
\mathtt{defines}
and

\mathtt{inherits}
.
The
dependency graph

G
has as vertices all
semantic-function applications
(
\mathtt{properties}(p)
,
\mathtt{supers}(p)
,
\mathtt{overrides}(p)
,

\mathtt{bases}(p)
,
\mathtt{resolve}(\ldots)
,
\mathtt{this}(\ldots)
)
that arise from the AST.
There is a directed edge from vertex
u
to vertex
v

whenever computing
u
via
equations (
1
)–(
6
)
requires the value of
v
.

Lemma C.2 (Termination implies finite acyclic subgraph).

If the memoized recursive evaluation of a query
q

terminates, then the subgraph of
G
reachable from
q

is finite and acyclic.

Proof.

Contrapositive. A terminating computation visits finitely
many vertices, so the reachable subgraph is finite.
For acyclicity, suppose the reachable subgraph contains a
cycle
v_{0}\to v_{1}\to\cdots\to v_{k}=v_{0}
.
In a recursive evaluation, computing
v_{0}
eventually
requires the value of
v_{0}
before it has been determined.
Without a pre-assigned default value, this is infinite
recursion; hence the evaluation does not terminate.
∎

Lemma C.3 (Unique solution on acyclic graphs).

If the subgraph of
G
reachable from a query
q
is a
finite directed acyclic graph, then the six equations
determine a unique value for every vertex in this subgraph.

Proof.

By induction on the DAG in reverse topological order.
Leaves—vertices with no outgoing edges—have their
values determined directly by the AST primitives

\mathtt{defines}
and
\mathtt{inherits}
.
Each non-leaf vertex’s value is uniquely determined by its
children’s values via the corresponding equation.
∎

Theorem C.4 (Well-definedness).

The semantic functions

\mathtt{properties}
,
\mathtt{supers}
,
\mathtt{overrides}
,
\mathtt{bases}
,
\mathtt{resolve}
,

\mathtt{this}
are well-defined: for every query whose recursive
evaluation terminates, the result is the unique solution of
equations (
1
)–(
6
) on the
reachable dependency subgraph.

Proof.

By Lemma
C.2
, termination
implies that the reachable subgraph is a finite DAG.
By Lemma
C.3
, the equations have
a unique solution on this finite DAG.
Memoized recursive evaluation computes exactly this solution,
visiting each vertex at most once in reverse topological
order.
∎

Divergence

The recursive evaluation diverges in two cases:
(1) the dependency graph contains a cycle (circular
inheritance), causing infinite recursion; or
(2) the reachable subgraph is an infinite acyclic chain
(an infinite inheritance hierarchy whose paths grow without
bound).
This is the analogue of divergence in the
\lambda
-calculus.
No separate treatment of divergence is needed; it emerges
from the recursive evaluation itself.

Böhm Tree Correspondence: Proofs

(Theorem
4.2
) and Full Abstraction
(Theorem

) stated in
Section

D.1.
Böhm Trees

We briefly recall the definition of Böhm
trees
(
9
)
.
A
head reduction

M\to_{h}M^{\prime}
contracts
the outermost
\beta
-redex only: if
M
has the form

(\lambda x.\,e)\;v\;M_{1}\cdots M_{k}
, then

M\to_{h}e[v/x]\;M_{1}\cdots M_{k}
.
A term
M
is in
head normal form
(HNF) if it has no
head redex, i.e.,
M=\lambda x_{1}\ldots x_{m}.\;y\;M_{1}\cdots M_{k}
where
y
is a variable.

The
Böhm tree

\mathrm{BT}(M)
of a
\lambda
-term
M

is an infinite labeled tree defined by:

\mathrm{BT}(M)=\begin{cases}\bot&\text{if }M\text{ has no HNF}\\[6.0pt]
\lambda x_{1}\ldots x_{m}.\;y\bigl(\mathrm{BT}(M_{1}),\;\ldots,\;\mathrm{BT}(M_{k})\bigr)&\begin{aligned} &\text{if }M\to^{*}_{h}\\[-2.0pt]
&\lambda x_{1}\ldots x_{m}.\;y\;M_{1}\cdots M_{k}\end{aligned}\end{cases}

Böhm tree equivalence
\mathrm{BT}(M)=\mathrm{BT}(N)
is the
standard observational equivalence of the lazy

\lambda
-calculus
(
5
)
.

D.2.
Path Encoding

We define a correspondence between positions in the Böhm tree
and paths in the mixin tree.
When the translation
\mathcal{T}
is applied to an ANF

\lambda
-term, the resulting mixin tree has a specific shape:

•

An abstraction
\lambda x.\,M
translates to a record
with own properties
\{\mathrm{argument},\mathrm{result}\}

(the
abstraction shape
).

•

A
\mathbf{let}
-binding

\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M
translates
to a record with own properties
\{x,\mathrm{result}\}
,
where
x
holds the encapsulated application

\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\}
.

•

A tail call
V_{1}\;V_{2}
translates to a record with own
properties
\{\mathrm{tailCall},\mathrm{result}\}
, where

\mathrm{tailCall}
holds the encapsulated application and

\mathrm{result}
projects

\mathrm{tailCall}.\mathrm{result}
.

•

A variable
x
with de Bruijn index
n
translates to
an indexed reference
\uparrow^{\!n}.\mathrm{argument}
.

Each Böhm tree position is a sequence of navigation steps from
the root.
In the Böhm tree, the possible steps at a node

\lambda x_{1}\ldots x_{m}.\;y\;M_{1}\cdots M_{k}
are:
entering the body (peeling off one abstraction layer) and
entering the
i
-th argument
M_{i}
of the head variable.
In the mixin tree, these correspond to following the

\mathrm{result}
label (for entering the body) and the

\mathrm{argument}
label after
\mathtt{this}
resolution (for
entering an argument position).

Rather than comparing absolute paths across different mixin
trees (which would be sensitive to internal structure), we
observe only the
convergence
behavior accessible via
the
\mathrm{result}
projection.
Recall the definition of inheritance-convergence
(Definition
4.1
).
Each
\mathrm{result}
-following step corresponds to one head
reduction step in the
\lambda
-calculus: a tail call’s

\mathrm{result}
projects through the encapsulated
application, and a
\mathbf{let}
-binding’s
\mathrm{result}

enters the continuation.
The abstraction shape at the end signals that a weak head
normal form has been reached.

D.3.
Single-Path Lemma

The
\mathtt{this}
function (equation
6
) is designed for the
general case of multi-path mixin inheritance.
For translated
\lambda
-terms, we show it degenerates to
single-path resolution.

Lemma D.1 (Single Path).

For any closed ANF
\lambda
-term
M
, at every invocation of

\mathtt{this}(S,\;p_{\mathrm{def}},\;n)
during evaluation of

\mathcal{T}(M)
, the frontier set
S
contains exactly one
path.

Proof.

By induction on the structure of the ANF term.

Case
\mathcal{T}(\lambda x.\,M)=\{\mathrm{argument}\mapsto\{\},\;\mathrm{result}\mapsto\mathcal{T}(M)\}

This is a record literal with

\mathtt{defines}=\{\mathrm{argument},\mathrm{result}\}
and
no inheritance sources, so
\mathtt{inherits}=\varnothing
.
At the root path
p
, we have
\mathtt{overrides}(p)=\{p\}
(a single
path) since there are no inheritance sources to introduce
additional branches.
Inside
\mathcal{T}(M)
, any reference to
x
is

\uparrow^{\!n}.\mathrm{argument}
where
n
is the de Bruijn index
pointing to this scope level.
Since
\mathcal{T}(\lambda x.\,M)
introduces exactly one
scope level, there is exactly one
mixin at that level, hence
\mathtt{this}
finds exactly one matching
pair
(p_{\mathrm{site}},\;p_{\mathrm{override}})
in
\mathtt{supers}
.

Case

\mathcal{T}(\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M)=\{x\mapsto\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\},\;\mathrm{result}\mapsto\mathcal{T}(M)\}

The outer record has own properties
\{x,\mathrm{result}\}

and no inheritance sources at the outer level
(
\mathtt{inherits}=\varnothing
), so
\mathtt{overrides}(\text{root})=\{\text{root}\}
.
Inside the
x
subtree, the inheritance

\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\}
has exactly one inheritance source
(
\mathcal{T}(V_{1})
), creating exactly one
\mathtt{bases}
entry.
By induction on
V_{1}
, the single-path property holds inside

\mathcal{T}(V_{1})
.
Inside
\mathcal{T}(M)
, the induction hypothesis applies
directly.

Case
\mathcal{T}(V_{1}\;V_{2})=\{\mathrm{tailCall}\mapsto\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\},\;\mathrm{result}\mapsto\mathrm{tailCall}.\mathrm{result}\}

Identical to the
\mathbf{let}
-binding case: the outer record
has own properties
\{\mathrm{tailCall},\mathrm{result}\}

with no inheritance sources at the outer level, and the

\mathrm{tailCall}
subtree contains exactly one inheritance
source.

Case
\mathcal{T}(x)=\uparrow^{\!n}.\mathrm{argument}

This is a reference, not a record.
The
\mathtt{this}
function walks up
n
steps from the enclosing scope.
By the inductive hypothesis on the enclosing translations,
each step of
\mathtt{this}
encounters exactly one matching pair in

\mathtt{supers}
.

The key structural invariant is that the translation

\mathcal{T}
never produces two independent inheritance sources
at the same scope level that both define the same label.
In every case, application inheritances are
encapsulated

inside a named property (
x
or
\mathrm{tailCall}
), and each
such encapsulated inheritance has exactly one inheritance
source.
This prevents diamond inheritance and ensures single-path
resolution throughout.
∎

D.4.
Substitution Lemma

The core mechanism of the translation is that inheritance with

\mathrm{argument}\mapsto\mathcal{T}(V)
plays the role of
substitution. We make this precise.

Lemma D.2 (Substitution).

Let
M
be an ANF term in which
x
may occur free,
and let
V
be a closed value.
Define the
inherited tree

C=\{\mathcal{T}(\lambda x.\,M),\;\mathrm{argument}\mapsto\mathcal{T}(V)\}
.
Then for every path
p
under
C\mathbin{\triangleright}\mathrm{result}
and
every label
\ell
:

\ell\in\mathtt{properties}(p)\text{ in }C\mathbin{\triangleright}\mathrm{result}\quad\Longleftrightarrow\quad\ell\in\mathtt{properties}(p)\text{ in }\mathcal{T}(M[V/x])

where
M[V/x]
is the usual capture-avoiding substitution.

Proof.

By structural induction on
M
.

Base case:
M=x

Then
\mathcal{T}(x)=\uparrow^{\!n}.\mathrm{argument}
(where
n
is the de Bruijn index
of
x
), and

C\mathbin{\triangleright}\mathrm{result}
contains this reference.
In the inherited tree
C
,
\mathtt{resolve}
and
\mathtt{this}
resolve the reference by
navigating from the reference’s enclosing scope up
n
steps
to the binding
\lambda
, where the inheritance

\{\mathcal{T}(\lambda x.\,x),\;\mathrm{argument}\mapsto\mathcal{T}(V)\}
inherits into the

\mathrm{argument}
slot, providing
\mathcal{T}(V)
.
Since
C
is the
\mathrm{tailCall}
subtree of

\mathcal{T}\bigl((\lambda x.\,M)\;V\bigr)
, which is a
closed ANF term, Lemma
D.1
applies and

\mathtt{this}
finds exactly one path,
so
\mathtt{resolve}
returns
\mathcal{T}(V)
’s subtree.
Since
M[V/x]=V
, we have

\mathcal{T}(M[V/x])=\mathcal{T}(V)
, and the properties
coincide.

Base case:
M=y
where
y\neq x

Then
\uparrow^{\!m}.\mathrm{argument}
(where
m
is the de Bruijn
index of
y
,
m\neq n
) walks up to a different scope level,
so the inheritance with

\mathrm{argument}\mapsto\mathcal{T}(V)
at the
binding scope of
x
has no effect.
Since
M[V/x]=y
, the properties are identical.

Inductive case:
M=\lambda y.\,M^{\prime}

Then
\mathcal{T}(M)=\{\mathrm{argument}\mapsto\{\},\;\mathrm{result}\mapsto\mathcal{T}(M^{\prime})\}
.
The subtree at
C\mathbin{\triangleright}\mathrm{result}
is another
abstraction-shaped record.
References to
x
inside
\mathcal{T}(M^{\prime})
resolve through

\mathtt{this}
in exactly the same way (with one additional scope
level from the inner
\lambda
), and by induction on
M^{\prime}
, the
properties under

C\mathbin{\triangleright}\mathrm{result}\mathbin{\triangleright}\mathrm{result}

coincide with those of

\mathcal{T}(M^{\prime}[V/x])
.
Since

(\lambda y.\,M^{\prime})[V/x]=\lambda y.\,(M^{\prime}[V/x])

(assuming
y
is fresh), the result follows.

Inductive case:

M=\mathbf{let}\;z=V_{1}\;V_{2}

\mathbf{in}\;M^{\prime}

Then

\mathcal{T}(M)=\{z\mapsto\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\},\;\mathrm{result}\mapsto\mathcal{T}(M^{\prime})\}.

The substitution distributes:

M[V/x]=\mathbf{let}\;z=V_{1}[V/x]\;V_{2}[V/x]\;\mathbf{in}\;M^{\prime}[V/x]
.
By induction on
V_{1}
,
V_{2}
, and
M^{\prime}
, the properties under
each subtree (
z
and
\mathrm{result}
) coincide,
since references to
x
inside each subtree resolve to

\mathcal{T}(V)
via the same
\mathtt{this}
mechanism.

Inductive case:
M=V_{1}\;V_{2}
(tail call)

Analogous to the
\mathbf{let}
-binding case with

\mathrm{tailCall}
in place of
z
.
∎

D.5.
Convergence Preservation

The convergence criterion (Definition
4.1
)
follows the
\mathrm{result}
chain from the root.
Each step in this chain corresponds to one head reduction step
in the
\lambda
-calculus.
We make this precise.

Lemma D.3 (Result-step).

Let
(\lambda x.\,M)\;V
be a tail call (a
\beta
-redex).
Then for every path
p
and label
\ell
:

\ell\in\mathtt{properties}\!\bigl(\,\text{root}\mathbin{\triangleright}\mathrm{result}\mathbin{\triangleright}p\,\bigr)\text{ in }\mathcal{T}\bigl((\lambda x.\,M)\;V\bigr)\;\Longleftrightarrow\;\ell\in\mathtt{properties}\!\bigl(\,\text{root}\mathbin{\triangleright}p\,\bigr)\text{ in }\mathcal{T}(M[V/x])

That is, following one
\mathrm{result}
projection in the
tail call’s mixin tree yields the same properties as the
root of the reduct’s mixin tree.

Proof.

The translation gives:

\mathcal{T}\bigl((\lambda x.\,M)\;V\bigr)=\{\mathrm{tailCall}\mapsto\{\mathcal{T}(\lambda x.\,M),\;\mathrm{argument}\mapsto\mathcal{T}(V)\},\;\mathrm{result}\mapsto\mathrm{tailCall}.\mathrm{result}\}

The
\mathrm{result}
label at the root is defined as

\mathrm{tailCall}.\mathrm{result}
, so

\text{root}\mathbin{\triangleright}\mathrm{result}
resolves to the

\mathrm{result}
path inside the inheritance

\mathrm{tailCall}=\{\mathcal{T}(\lambda x.\,M),\;\mathrm{argument}\mapsto\mathcal{T}(V)\}
.
This inheritance is exactly the inherited tree
C
of
Lemma
D.2
, and

\mathrm{tailCall}\mathbin{\triangleright}\mathrm{result}
is

C\mathbin{\triangleright}\mathrm{result}
.
By Lemma
D.2
, the properties under

C\mathbin{\triangleright}\mathrm{result}
coincide with those of

\mathcal{T}(M[V/x])
.

Let-binding variant.

An analogous result holds for

\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M^{\prime}

where
V_{1}=\lambda y.\,M^{\prime\prime}
.
The translation gives:

\mathcal{T}\bigl(\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M^{\prime}\bigr)=\{x\mapsto\{\mathcal{T}(V_{1}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\},\;\mathrm{result}\mapsto\mathcal{T}(M^{\prime})\}

Since
\mathrm{result}\mapsto\mathcal{T}(M^{\prime})
is a property
definition, the subtree at

\text{root}\mathbin{\triangleright}\mathrm{result}
is
\mathcal{T}(M^{\prime})
.
Inside
\mathcal{T}(M^{\prime})
, each reference to
x
is

x.\mathrm{result}
, which resolves to the
\mathrm{result}

path inside the
x
subtree

\{\mathcal{T}(\lambda y.\,M^{\prime\prime}),\;\mathrm{argument}\mapsto\mathcal{T}(V_{2})\}
.
This is the inherited tree
C
of
Lemma
D.2
, so

x.\mathrm{result}
has the same properties as

\mathcal{T}(M^{\prime\prime}[V_{2}/y])
.
In the
\lambda
-calculus,

M=(\lambda x.\,M^{\prime})(V_{1}\;V_{2})
, and the head reduct is

N=M^{\prime}[(V_{1}\;V_{2})/x]
.
In
\mathcal{T}(N)
, each occurrence of
x
is replaced by

(V_{1}\;V_{2})
, whose result, by the tail-call variant above,
also yields
\mathcal{T}(M^{\prime\prime}[V_{2}/y])
.
Therefore the properties at

\text{root}\mathbin{\triangleright}\mathrm{result}\mathbin{\triangleright}p
in

\mathcal{T}(M)
coincide with those at

\text{root}\mathbin{\triangleright}p
in
\mathcal{T}(N)
for all
p
.
∎

Theorem D.4 (Convergence preservation).

If
M\to_{h}N
(head reduction), then

\mathcal{T}(M){\Downarrow}
if and only if

\mathcal{T}(N){\Downarrow}
.

Proof.

A head reduction step in ANF takes one of two forms:
a tail call
(\lambda x.\,M^{\prime})\;V\to_{h}M^{\prime}[V/x]
,
or a
\mathbf{let}
-binding

\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M^{\prime}\to_{h}M^{\prime}[(V_{1}\;V_{2})/x]

(since
\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M^{\prime}=(\lambda x.\,M^{\prime})(V_{1}\;V_{2})
in the
\lambda
-calculus).
In both cases, Lemma
D.3
(tail-call and
let-binding variants respectively) shows that
the properties at
\text{root}\mathbin{\triangleright}\mathrm{result}^{n}
in

\mathcal{T}(M)
coincide with the properties at

\text{root}\mathbin{\triangleright}\mathrm{result}^{n-1}
in

\mathcal{T}(N)
for all
n\geq 1
, where
N
is the
head reduct.
Hence the abstraction shape appears at depth
n
in the
pre-reduct if and only if it appears at depth
n-1
in
the post-reduct.
∎

D.6.
Adequacy

A closed ANF term at the top level is either an abstraction
(a value) or a computation (a
\mathbf{let}
-binding or tail
call).
An abstraction translates to a record whose root immediately
has the abstraction shape; a computation’s root has the form

\{x,\mathrm{result}\}
or

\{\mathrm{tailCall},\mathrm{result}\}
, and one must follow
the
\mathrm{result}
chain to find the eventual value.

Proof of Theorem
4.2
.

(
\Rightarrow
)
Suppose
M\to^{*}_{h}\lambda x.\,M^{\prime}
in
k
head reduction
steps.
We show
\mathcal{T}(M)
converges at depth
\leq k
by
induction on
k
.

Base case
(
k=0
):
M
is already an abstraction

\lambda x.\,M^{\prime}
.
Then
\mathcal{T}(M)=\{\mathrm{argument}\mapsto\{\},\;\mathrm{result}\mapsto\mathcal{T}(M^{\prime})\}
,
whose root has

\mathtt{defines}=\{\mathrm{argument},\mathrm{result}\}
.
These labels are directly in
\mathtt{defines}
of the root, so
the recursive evaluation returns them without further
recursion, and
\mathcal{T}(M)
converges at depth
n=0
.

Inductive step
(
k\geq 1
):
M
is not an abstraction,
so
M
is either a tail call or a
\mathbf{let}
-binding,
both of which are
\beta
-redexes.
Let
N
be the head reduct, so

M\to_{h}N\to^{k-1}_{h}\lambda x.\,M^{\prime}
.
By Lemma
D.3
(tail-call or
let-binding variant), the properties at

\text{root}\mathbin{\triangleright}\mathrm{result}\mathbin{\triangleright}p

in
\mathcal{T}(M)
coincide with those at

\text{root}\mathbin{\triangleright}p
in
\mathcal{T}(N)
.
By the induction hypothesis,
\mathcal{T}(N)

converges at depth
\leq k-1
, so
\mathcal{T}(M)

converges at depth
\leq k
.

(
\Leftarrow
)
Suppose
\mathcal{T}(M){\Downarrow}
at depth
n
.
We show
M
has a head normal form by induction on
n
.

Base case
(
n=0
): the root of
\mathcal{T}(M)
has
abstraction shape

\{\mathrm{argument},\mathrm{result}\}
.
Only the abstraction rule
\mathcal{T}(\lambda x.\,M^{\prime})

produces a root with own property
\mathrm{argument}
.
(For tail calls and
\mathbf{let}
-bindings, the root has

\mathtt{defines}=\{\mathrm{tailCall},\mathrm{result}\}

or
\{x,\mathrm{result}\}
, and
\mathrm{argument}
cannot
appear via
\mathtt{supers}
because

\mathtt{inherits}=\varnothing
at the root, giving

\mathtt{bases}(\text{root})=\varnothing
.)
Therefore
M
is an abstraction, hence already in head normal
form.

Inductive step
(
n\geq 1
): the abstraction shape
appears at depth
n
but not at depth
0
.
By the base case argument,
M
is not an abstraction, so
M

is either a tail call
V_{1}\;V_{2}
or a
\mathbf{let}
-binding

\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M^{\prime}
.
In both cases,
M
is a
\beta
-redex
(since
V_{1}=\lambda x.\,M^{\prime}
or

V_{1}=\lambda y.\,M^{\prime\prime}
respectively, the only closed
ANF value).
By Lemma
D.3
(tail-call or
let-binding variant respectively), the properties at depth

n-1
in
\mathcal{T}(N)
match those at depth
n

in
\mathcal{T}(M)
, where
N
is the head reduct.
So
\mathcal{T}(N)
converges at depth
n-1
.
By the induction hypothesis,
N
has a head normal
form, and since
M\to_{h}N
, so does
M
.
∎

D.7.
Full Abstraction

Adequacy relates a single term’s head normal form to its
inheritance-convergence.
Full abstraction lifts this to an equivalence between terms:
the translation
\mathcal{T}
preserves and reflects
observational equivalence.

Definition D.5 (
\lambda
-contextual equivalence under
\mathcal{T}
).

For closed
\lambda
-terms
M
and
N
, write

\mathcal{T}(M)\approx_{\lambda}\mathcal{T}(N)
if for every
closing
\lambda
-calculus context
C[\cdot]
:

\mathcal{T}(C[M]){\Downarrow}\;\Longleftrightarrow\;\mathcal{T}(C[N]){\Downarrow}

The subscript
\lambda
emphasizes that the quantification ranges
over
\lambda
-calculus contexts, not over all inheritance-calculus contexts.
This definition observes only convergence (a single bit), but
quantifying over all
\lambda
-contexts makes it a fine-grained
equivalence: different contexts can supply different arguments
and project different results, probing every aspect of the
term’s behavior within the
\lambda
-definable fragment.

Proof of Theorem
4.3
.

The translation
\mathcal{T}
is compositional: for every

\lambda
-calculus context
C[\cdot]
, the mixin tree

\mathcal{T}(C[M])
is determined by the mixin tree

\mathcal{T}(M)
and the translation of the context.
This means
\mathcal{T}
preserves the context structure
needed for the argument.

(
\Leftarrow
)
Suppose
\mathrm{BT}(M)=\mathrm{BT}(N)
.
Böhm tree equivalence is a congruence
(
9
)
,
so for every context
C[\cdot]
,

\mathrm{BT}(C[M])=\mathrm{BT}(C[N])
.
In particular,
C[M]
has a head normal form iff
C[N]
does.
By Theorem
4.2
,

\mathcal{T}(C[M]){\Downarrow}
iff

\mathcal{T}(C[N]){\Downarrow}
.
Hence
\mathcal{T}(M)\approx_{\lambda}\mathcal{T}(N)
.

(
\Rightarrow
)
Suppose
\mathrm{BT}(M)\neq\mathrm{BT}(N)
.
Böhm tree equivalence coincides with observational
equivalence for the lazy

\lambda
-calculus
(
5
)
:
there exists a context
C[\cdot]
such that
C[M]
converges
and
C[N]
diverges (or vice versa).
By Theorem
4.2
,

\mathcal{T}(C[M]){\Downarrow}
and

\mathcal{T}(C[N]){\Uparrow}
.
Hence
\mathcal{T}(M)\not\approx_{\lambda}\mathcal{T}(N)
.
∎

The proof rests on two pillars: Adequacy
(Theorem
4.2
), which is our contribution, and
the classical result that Böhm tree equivalence equals
observational equivalence for the lazy

\lambda
-calculus
(
5
)
.
The mixin tree semantics inherits full abstraction from the

\lambda
-calculus without needing to define or compare
absolute paths inside mixin trees.

Appendix E
Set-Theoretic Semantics of the ANF Lazy

\lambda
-Calculus

This appendix presents a semantics of the lazy

\lambda
-calculus in A-normal form (ANF) that lives entirely
in set theory.
The semantics is given by mutually recursive set-comprehension
equations whose well-definedness follows from the same
termination argument as in
Appendix
C
.
No function spaces, no substitution, no reduction rules,
no evaluation order, and no domain theory are needed.
The central idea is that function application is modeled as

tree grafting
: applying a function record to an argument
splices the function’s subtree into the call site, and variable
references navigate the resulting tree structure.

ANF is essential.
Traditional
\lambda
-calculus syntax allows anonymous
subexpressions such as
(f\;x)
in
(f\;x)\;y
that
have no label and cannot form paths.
ANF restores path-addressability by binding every
intermediate result to a name, so that every node in the
evaluation tree has a unique path address.

Syntax

Let
M
denote a computation and
V
a value.

\begin{array}[]{r@{\;::=\;}l}M&\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M\mid V_{1}\;V_{2}\mid V\\
V&x\mid\lambda x.\,M\end{array}

Every
\lambda
-term can be mechanically converted to ANF by
naming intermediate results; ANF is neither a restriction nor
an extension of the
\lambda
-calculus.
Variables use de Bruijn indices:
\uparrow^{\!n}
counts the number
of enclosing
scope levels
(record braces) between the
reference and its binder, following the same convention as
inheritance-calculus.
In particular, a
\lambda
-bound variable that crosses
k

intervening
\mathbf{let}
-binding scopes and
n
intervening

\lambda
-abstraction scopes is written
\uparrow^{\!n+k}
, not

\uparrow^{\!n}
.
Let-bound variables are referenced by their binding name
x
.

Evaluation tree

An evaluation tree has a single abstraction: every node can
serve as function, argument, binding, and result at the same time.
A
\mathtt{Path}
is a sequence of labels
(\ell_{1},\ldots,\ell_{k})

identifying a position in the mixin tree.
We write
p
for a path,
()
for the root,

p\mathbin{\triangleright}\ell
for extension,

\mathtt{init}(p)
for the parent path, and
\mathtt{last}(p)
for the final label.

AST

An ANF term is parsed into an AST that provides two
functions at each path
p
:

•

\mathtt{children}(p)
: the set of labels locally defined at
p
.

•

\mathtt{refs}(p)
: the set of reference pairs

(n,\;\ell_{*})
, where
n
is a de Bruijn index
and
\ell_{*}
is a list of downward projections.

Each ANF construct populates these as follows.

An abstraction
\lambda x.\,M
at path
p
:

\displaystyle\mathtt{children}(p)

\displaystyle=\{\mathrm{argument},\;\mathrm{result}\},

\displaystyle\mathtt{refs}(p)

\displaystyle=\varnothing.

The subtree at
p\mathbin{\triangleright}\mathrm{result}
is determined by
M
;
the subtree at
p\mathbin{\triangleright}\mathrm{argument}
is empty
(
\mathtt{children}=\varnothing
,
\mathtt{refs}=\varnothing
).

A let-binding
\mathbf{let}\;x=V_{1}\;V_{2}\;\mathbf{in}\;M

at path
p
:

\displaystyle\mathtt{children}(p)

\displaystyle=\{x,\;\mathrm{result}\},

\displaystyle\mathtt{refs}(p)

\displaystyle=\varnothing.

The subtree at
p\mathbin{\triangleright}\mathrm{result}
is determined by
M
.
The subtree at
p\mathbin{\triangleright}x
represents the application

V_{1}\;V_{2}
and is determined by the form of
V_{1}
:

•

If
V_{1}
is a variable (either
\uparrow^{\!m}
or a
let-bound name), then

\displaystyle\mathtt{children}(p\mathbin{\triangleright}x)

\displaystyle=\{\mathrm{argument}\},

\displaystyle\mathtt{refs}(p\mathbin{\triangleright}x)

\displaystyle=\{(n_{1},\;\ell_{*})\},

where the reference
(n_{1},\;\ell_{*})
encodes
the translation of
V_{1}
(see below).

•

If
V_{1}=\lambda y.\,M^{\prime}
, the
\lambda
-literal is
inlined:

\displaystyle\mathtt{children}(p\mathbin{\triangleright}x)

\displaystyle=\{\mathrm{argument},\;\mathrm{result}\},

\displaystyle\mathtt{refs}(p\mathbin{\triangleright}x)

\displaystyle=\varnothing,

and the subtree at
p\mathbin{\triangleright}x\mathbin{\triangleright}\mathrm{result}
is
determined by
M^{\prime}
.

In both cases the subtree at
p\mathbin{\triangleright}x\mathbin{\triangleright}\mathrm{argument}

is determined by
V_{2}
.

A tail call
V_{1}\;V_{2}
at path
p
:

\displaystyle\mathtt{children}(p)

\displaystyle=\{\mathrm{tailCall},\;\mathrm{result}\},

\displaystyle\mathtt{refs}(p)

\displaystyle=\varnothing.

The subtree at
p\mathbin{\triangleright}\mathrm{tailCall}
is analogous to
the application node
p\mathbin{\triangleright}x
above: if
V_{1}
is a variable,

\mathtt{children}=\{\mathrm{argument}\}
with

\mathtt{refs}=\{(n_{1},\;\ell_{*})\}
; if
V_{1}
is a
\lambda
-literal,

\mathtt{children}=\{\mathrm{argument},\;\mathrm{result}\}
with

\mathtt{refs}=\varnothing
and the
\lambda
-body inlined.
The subtree at
p\mathbin{\triangleright}\mathrm{result}
is a forwarding
reference:

\displaystyle\mathtt{children}(p\mathbin{\triangleright}\mathrm{result})

\displaystyle=\varnothing,

\displaystyle\mathtt{refs}(p\mathbin{\triangleright}\mathrm{result})

\displaystyle=\{(0,\;(\mathrm{tailCall},\;\mathrm{result}))\}.

Here
(0,\;(\mathrm{tailCall},\;\mathrm{result}))
navigates to
the enclosing scope (
p
itself, since
n=0
from

p\mathbin{\triangleright}\mathrm{result}
’s perspective), then projects

\mathrm{tailCall}.\mathrm{result}
.

A
\lambda
-bound variable
\uparrow^{\!n}
used as an inheritance
source at an application node
p
contributes

(n,\;(\mathrm{argument}))
to
\mathtt{refs}(p)
:
navigate up
n
scope levels, then project

\mathrm{argument}
.
The same applies when
\uparrow^{\!n}
occurs as a bare value in tail
position or as an argument value, contributing the reference to

\mathtt{refs}
at the corresponding path.

A let-bound variable
x
at path
p
is resolved lexically:
find the nearest ancestor
p^{\prime}
of
p
such that

x\in\mathtt{children}(p^{\prime})
, let
n=|p|-|p^{\prime}|-1
,
and contribute
(n,\;(x,\;\mathrm{result}))
to

\mathtt{refs}(p)
, projecting

x.\mathrm{result}
from the enclosing scope.

Note that since the de Bruijn index
n
counts
all

scope levels (not just
\lambda
-abstractions), it accounts
for intervening
\mathbf{let}
-binding and tail-call scopes.
For example, in
\lambda.\,\lambda.\,\mathbf{let}\;r=\uparrow^{\!2}\;\uparrow^{\!0}\;\mathbf{in}\;r
, the outer-
\lambda
variable
has de Bruijn index
2
(crossing the
\mathbf{let}
-scope and
the inner-
\lambda
scope), not
1
.

Both
\mathtt{children}
and
\mathtt{refs}
are pure data extracted from the AST;
they are not functions of runtime state.

Labels

The labels observable at a path are those locally
defined at any graft of any transitive callee:

(7)

\mathtt{labels}(p)=\bigl\{\;\ell\;\big|\;p_{\mathrm{step}}\in\mathtt{callee}^{*}(p),\;p_{\mathrm{graft}}\in\mathtt{grafts}(p_{\mathrm{step}}),\;\ell\in\mathtt{children}(p_{\mathrm{graft}})\;\bigr\}

Grafts

When a function is applied, its subtree is
grafted

at the call site.
A child label
\ell
of the callee also becomes a
child of the caller; the child at the callee’s

\ell
position and the child at the caller’s
\ell

position (if any) share the same identity.
The grafts of
p
collect all such identity-sharing
positions:

(8)

\mathtt{grafts}(p)=\begin{cases}\{p\}&\text{if }p=()\\[6.0pt]
\{p\}\;\cup\;\left\{\;p_{\mathrm{callee}}\mathbin{\triangleright}\mathtt{last}(p)\;\left|\;\begin{aligned} &p_{\mathrm{callee}}\in\mathtt{callee}^{*}(\mathtt{init}(p)),\\
&\text{s.t.}\;\mathtt{last}(p)\in\mathtt{children}(p_{\mathrm{callee}})\end{aligned}\right.\right\}&\text{if }p\neq()\end{cases}

Here
\mathtt{callee}^{*}
denotes the reflexive-transitive closure of

\mathtt{callee}
, defined next.

Callee

The callee of a path
p
is the set of paths that
p
is
grafted from.
Concretely,
\mathtt{callee}
resolves every reference in

p
’s grafts one step:

(9)

\mathtt{callee}(p)=\left\{\;p_{\mathrm{target}}\;\left|\;\begin{aligned} &p_{\mathrm{graft}}\in\mathtt{grafts}(p),\\
&(n,\;\ell_{*})\in\mathtt{refs}(p_{\mathrm{graft}}),\\
&p_{\mathrm{target}}=\mathtt{scope}(\mathtt{init}(p),\;\mathtt{init}(p_{\mathrm{graft}}),\;n)\mathbin{\triangleright}\ell_{1}\mathbin{\triangleright}\cdots\mathbin{\triangleright}\ell_{k}\end{aligned}\right.\right\}

where
\ell_{*}=(\ell_{1},\ldots,\ell_{k})
.
The
\mathtt{init}(p_{\mathrm{graft}})
passes the reference’s

enclosing scope
to
\mathtt{scope}
, matching the convention of

\mathtt{resolve}
(
5
), which calls

\mathtt{this}(\{p_{\mathrm{site}}\},\;\mathtt{init}(p_{\mathrm{def}}),\;n)
.

Scope resolution

\mathtt{scope}
navigates upward through the evaluation tree
to find the binding site of a de Bruijn reference.
Each ANF construct (
\lambda
-abstraction,
\mathbf{let}
-binding,
or tail call) introduces one scope level;
crossing a scope boundary means finding the call site
that grafted the current subtree.

\mathtt{scope}
takes three arguments: an evaluation-site path

p_{\mathrm{site}}
(where the grafted subtree lives),
a definition-site path
p_{\mathrm{def}}

(the position in the original AST),
and a de Bruijn index
n
.

(10)

\mathtt{scope}(p_{\mathrm{site}},\;p_{\mathrm{def}},\;n)=\begin{cases}p_{\mathrm{site}}&\text{if }n=0\\[6.0pt]
\mathtt{scope}\!\left(p_{\mathrm{caller}},\;\mathtt{init}(p_{\mathrm{def}}),\;n-1\right)&\text{if }n>0\end{cases}

where
p_{\mathrm{caller}}
is the unique path satisfying

(p_{\mathrm{caller}},\;p_{\mathrm{def}})\in\mathtt{callee}^{\mathrm{ctx}}(p_{\mathrm{site}})
,
and
\mathtt{callee}^{\mathrm{ctx}}
pairs each element of

\mathtt{callee}^{*}(p_{\mathrm{site}})
with its provenance:

(11)

\mathtt{callee}^{\mathrm{ctx}}(p)=\bigl\{\;(\mathtt{init}(p_{\mathrm{step}}),\;p_{\mathrm{graft}})\;\big|\;p_{\mathrm{step}}\in\mathtt{callee}^{*}(p),\;p_{\mathrm{graft}}\in\mathtt{grafts}(p_{\mathrm{step}})\;\bigr\}

At each step,
\mathtt{init}
shortens
p_{\mathrm{def}}
by one label
and
n
decreases by one.
Since
n
is a nonnegative integer, the recursion terminates.

This completes the chain of definitions needed to compute

\mathtt{labels}(p)
.

Observational fixpoint semantics

The definitions above constitute the complete semantics.
There are no reduction rules, no evaluation contexts, no
substitution.
Computation arises from querying progressively deeper paths
in a lazily constructed tree: the observer drives computation
by choosing which path to inspect, and the mutually recursive
definitions unfold on demand.

Formally, the mutually recursive
equations (
7
)–(
11
)
define set membership recursively:

\ell\in\mathtt{labels}(p)
holds if and only if it can be
established by a finite chain of applications of these
equations.
Well-definedness follows from the same termination argument
as for the mixin tree equations
(Appendix
C
): if the recursive
evaluation terminates, the reachable dependency subgraph is
finite and acyclic, and the equations have a unique solution.
When no finite derivation exists for a given query, the
recursive evaluation does not terminate, analogous to
divergence.

Convergence

An ANF term
M

converges
, written
M{\Downarrow}
,
if there exists
n\geq 0
such that

\{\mathrm{argument},\,\mathrm{result}\}\subseteq\mathtt{labels}(\underbrace{\mathrm{result}\mathbin{\triangleright}\cdots\mathbin{\triangleright}\mathrm{result}}_{n})

in the semantics defined by the equations above.
This corresponds exactly to the Böhm
tree
(
9
)
of the original term:

M
converges iff it has a head normal form
(Theorem
4.2
), and two terms are equivalent
under this semantics iff they have the same Böhm tree
(Theorem
4.3
).
The proofs, given in Appendix
D
,
apply verbatim: each equation above is the specialization
of the corresponding mixin tree equation
(Section
3
) to terms in the image of
the translation
\mathcal{T}

(Section
4
), where the
Single-Path Lemma (Lemma
D.1
) ensures
that the set-valued
\mathtt{this}
function
(equation
6
) degenerates to the single-valued

\mathtt{scope}
(equation
10
).
