Agent-Diff: Benchmarking LLM Agents on Enterprise API Tasks via Code Execution with State-Diff-Based Evaluation ISBN: 978-1-4503-XXXX-X/2018/06 CCS: Computing methodologies CCS: Computing methodologies Artificial intelligence CCS: Computing methodologies Modelling and simulation

Abstract
. We present Agent-Diff, a novel benchmarking framework for evaluating agentic Large Language Models (LLMs) on real-world tasks that execute code via external APIs. Agentic LLM performance varies due to differences in models, external tool access, prompt structures, and agentic frameworks. Benchmarks must make fundamental trade-offs between a sandboxed approach that controls for variation in software environments and more ecologically valid approaches employing real services. Agent-Diff attempts to capture the desirable features of both of these approaches by including access to the real API interfaces for software services while sandboxing the environment in which calls are made, processed, and evaluated. This approach relies on two key innovations. The first is a novel state-diff contract, which separates process from outcome - rather than fuzzy trace or parameter matching, we define task success as whether the expected change in environment state was achieved. The second is a novel sandbox that provides a standardized scripting layer that all models use to execute code against external APIs (Slack, Box, Linear, Google Calendar). Thus, we can evaluate different agentic LLMs against a standardized set of contracts using a unified sandbox while still evaluating their performance on real-world service interfaces. Using the Agent-Diff framework, we provide benchmarks for nine LLMs across 224 tasks utilizing enterprise software workflows. In addition, we evaluate the robustness of the framework with ablation experiments to assess the contribution of access to API documentation on benchmark performance. Code and data: https://github.com/agent-diff-bench/agent-diff .

containerized environments that can be instantiated identically across
runs – eliminating the temporal instability inherent in live-service
benchmarks. This approach helps maintain ecological validity while maintaining reproducibility and environmental control.

decouples processes and outcome measures. Rather than fuzzy trace or parameter matching,

3.
Agent-Diff

Agent-Diff evaluates code-execution agents on long-horizon enter-
prise API tasks and evaluates how state changed in the environment.
The framework requires: (i) black-box equivalence – closed-source APIs can be faithfully replicated from their
public contracts; (ii) state-centric modeling – all operations reduce to typed, state transitions that can be diffed; and (iii) deterministic isolation – each run starts from an identical snapshot.

3.1.
Agent-Diff Environments

Our central design hypothesis is that closed-source enterprise APIs
can be replicated with sufficient fidelity to produce representative
evaluation scores because the contract – not the implementation – defines correctness from
an agent’s perspective.

Consider an API as a function
f:(\mathcal{R},S)\rightarrow(S^{\prime},\mathcal{O})
mapping requests and state to new state and outputs. An agent observes only
\mathcal{R}
and
\mathcal{O}
; the internal path from
S
to
S^{\prime}
is opaque.

Two implementations
f
and
\hat{f}
are
behaviorally
equivalent
over
\mathcal{R}^{*}
if:

(1)

\forall\,r\in\mathcal{R}^{*},\,S:\;f(r,S)=\hat{f}(r,S)

Full equivalence over all possible requests is neither achievable
nor necessary. We target equivalence over the subset

\mathcal{R}^{*}\subset\mathcal{R}
exercised by the benchmark
tasks. Because the APIs in our benchmark are predominantly CRUD
interfaces over typed entities, internal side effects (notifications,
analytics, caching) are invisible to the agent and irrelevant for
evaluation – our replicas need only produce equivalent outputs for
equivalent inputs.

Crucially, all information required to construct
\hat{f}
is publicly
available: entity schemas (via OpenAPI or GraphQL introspection), operation
semantics, response formats (via official SDKs), and error
conditions
(
24
;
6
;
12
;
17
)
.
We validate replica fidelity through automated conformance testing against
production APIs and adversarial edge-case probing
(Appendix
8.10
).

State-Centric Modelling.

We model each service as a state machine where state
S
is a typed
relational database. Entity types (
User
,
Channel
,

Message
in Slack;
File
,
Folder
in Box, etc.)
map to tables with schemas derived from public API specifications.
All operations reduce to three transitions:

(2)

Insert

\displaystyle:S\rightarrow S\cup\{e\}

(3)

Update

\displaystyle:S\rightarrow(S\setminus\{e\})\cup\{e^{\prime}\}

(4)

Delete

\displaystyle:S\rightarrow S\setminus\{e\}

Rather than validating API call traces, we snapshot all tables before
and after agent execution and compute the state difference:

(5)

\displaystyle\Delta_{\text{add}}

\displaystyle=T_{\text{after}}\setminus T_{\text{before}}

(6)

\displaystyle\Delta_{\text{del}}

\displaystyle=T_{\text{before}}\setminus T_{\text{after}}

(7)

\displaystyle\Delta_{\text{mod}}

\displaystyle=\{(e,e^{\prime}):e.\text{pk}=e^{\prime}.\text{pk}\land e\neq e^{\prime}\}

The resulting
DiffResult
– containing all inserted, deleted,
and modified entities – is compared against the task’s expected state
changes.

Deterministic Isolation.

Each benchmark run instantiates a fresh, isolated environment. We
leverage PostgreSQL’s schema isolation: each environment operates within
its own schema namespace (e.g.,
state_{env_id}
), enabling
concurrent execution without cross-contamination. Environments are seeded
from deterministic templates, ensuring identical initial states
S_{0}

across runs. This architecture guarantees that for any task
\tau
and
agent
\mathcal{A}
:

(8)

\forall r_{1},r_{2}\in\text{Runs}(\tau,\mathcal{A}):S_{0}^{(r_{1})}=S_{0}^{(r_{2})}

enabling reproducible evaluation without the temporal instability of live
APIs. To support state diffing, we snapshot all entity tables immediately
before and after agent execution, creating immutable copies

T_{\text{before}}
and
T_{\text{after}}
within the same isolated
schema. Because each environment is fully independent, snapshots are
free from interference by concurrent runs, and the resulting diffs
reflect only the actions of the evaluated agent. Figure
1

illustrates the sandbox architecutre and end-to-end request flow.

3.2.
Agent-Diff Benchmark

Task taxonomy.

Each task
\tau
is characterized along five dimensions
(Table
3
), which arise at different stages of
the construction pipeline.

The primary axis is the
task horizon

n^{*}(\tau)
: the minimum
number of endpoint invocations required under an optimal policy,
directly controlled via the sampling procedure described below.

Two structural dimensions emerge from the sampled endpoint multiset:

•

Operation profile
: the set of API primitives
required – search, create, read, update, and/or delete (non-exclusive).

•

Entity scope

d_{\mathrm{scope}}
: single-entity
vs. multi-entity state changes.

Two pragmatic dimensions are shaped during generation and human curation:

•

Information availability

d_{\mathrm{info}}
: whether
required identifiers are provided explicitly in the prompt or must be
discovered via API queries. This is governed by the identifier policy
in the generation prompt.

•

Ambiguity

d_{\mathrm{amb}}
: the degree to which the
prompt underspecifies the exact target. Low-ambiguity tasks are
produced by the LLM; medium- and high-ambiguity variants are
introduced during human curation (e.g., removing explicit identifiers,
adding distractor entities).

These dimensions operationalize problem space beyond trace-level
tool calling: agents must search for missing identifiers, plan multi-step
workflows, and maintain state across dependent operations.

Tool-call budget.

We target a heavy-tailed distribution of task horizons by sampling intended
tool-call counts from a shifted truncated exponential over
\{1,\ldots,40\}

with rate
\lambda=0.3
:

(9)

\Pr[n=k]\propto e^{-\lambda(k-1)},\quad k\in\{1,\ldots,40\}.

This yields a target mean of
\mathbb{E}[n]\approx 4.3
, biased toward short
tasks with a controlled tail of long-horizon scenarios. After feasibility
filtering and manual curation, the realized distribution has mean
\bar{n}^{*}=5.3
with range 1–24,
reflecting a slight upward shift from the rejection of trivially simple proposals.

Endpoint sampling.

For each service
s
(Slack, Box, Linear, Google Calendar), let
\mathcal{E}_{s}
denote
the supported endpoints. Conditioned on
s
and the target horizon
n
, we sample an
intended endpoint multiset
(e_{1},\ldots,e_{n})
i.i.d. from

(10)

\Pr[e_{i}=e]=\frac{1}{|\mathcal{E}_{s}|},\ \ \ e\in\mathcal{E}_{s}.

Uniform sampling encourages coverage across the full API surface. The benchmark spans
108 unique endpoints (Box: 27, Slack: 25, Linear: 19, Calendar: 37), with each task
requiring a mean of 4.3 distinct endpoints (range 1–12).

Task generation pipeline.

For each sampled endpoint multiset, we use a mix of frontier LLMs
(Claude Opus 4 and Gemini 3 Pro) to generate:
(1) a natural-language user prompt whose completion induces state changes
consistent with
(e_{1},\ldots,e_{n})
, (2) a deterministic seed template
defining the initial sandbox state
S_{0}
, and (3) a set of declarative
assertions describing the expected state diff and forbidden side effects.
The endpoint multiset determines the structural dimensions of the task:
its operation profile and entity scope. The generation prompt additionally
controls information availability (
d_{\mathrm{info}}
) by instructing
the model whether to expose identifiers explicitly or require the agent
to discover them via API queries. In some cases, we supply a pre-authored
seed template and ask the model to generate only the prompt and assertions;
in others, the model constructs all three components jointly. The full
generation prompt is provided in Appendix
8.9
.

Human curation.

Each generated task is validated for executability in the sandbox –infeasible
samples are discarded or regenerated. Reviewers verify that required
identifiers are discoverable and that the necessary endpoints and permissions
exist under the stated prompt constraints. Reviewers then control the
ambiguity dimension (
d_{\mathrm{amb}}
) by selectively degrading prompts:
removing explicit identifiers, introducing typographical variations, or
adding distractor entities to the seed state. All tasks are annotated
along the five taxonomy dimensions post-hoc to verify broad coverage
(Table
3
).

Evaluation Methodology

State-diff evaluation.

Each task
\tau
executes in an isolated sandbox with initial state

S_{0}
and final state
S_{1}
. We compute a canonical state diff

\Delta S(\tau)=\mathrm{Diff}(S_{0},S_{1})
,
consisting of inserted, deleted, and updated entities across all
tables (Section
8.8
). Scoring depends
only on
\Delta S(\tau)
, not on the agent’s action trace.

Declarative verification logic.

To avoid brittle operation matching, we express task requirements as
a set of predicates evaluated on
\Delta S(\tau)
. Each assertion
specifies: (i) a
diff_type
(added/deleted/updated),
(ii) an
entity
(table), (iii) a conjunction of field-level
constraints in
where
(e.g., equality, substring), and
(iv) an
expected_count
. This forms a compact,
implementation-agnostic verification layer that can be authored
without writing imperative database queries.

Figure
2
shows the assertions for a
two-step Box task (“Delete the misfiled copy, then tag the correct
one”). The first assertion checks that the misfiled file was
removed (
deleted
); the second verifies that the tag was
applied (
updated
). Because this task has
|A(\tau)|=2

assertions, it contributes weight 2 to the aggregate score – a
task with 10 assertions would contribute weight 10, ensuring that
complex multi-step tasks are not underrepresented.

{"diff_type": "deleted",

Example assertion set for a two-step task.

diff_type
specifies which partition of the state diff to
query:
added
= entities present in
S_{1}
but not
S_{0}
;

deleted
= entities in
S_{0}
but not
S_{1}
;

updated
= entities whose primary key persists but one or
more field values changed. The
where
clause filters by
field-level predicates;
expected_count
sets the required
number of matching rows. This task contributes
m(\tau)=2
to the
denominator of the aggregate score.

Closed-world invariant.

Let
A(\tau)
denote the set of required assertions for task
\tau

and
F(\tau)
the set of fields explicitly marked as ignored. Each task’s
assertion set and ignore-list has been manually reviewed to exclude
non-deterministic third-order effects (e.g.,
updated_at

timestamps) while capturing all semantically
meaningful state changes. We enforce a
closed-world
invariant
: every entity change in
\Delta S(\tau)
must be
accounted for by some assertion in
A(\tau)
or involve only
fields in
F(\tau)
. Any unaccounted diff – an unexpected
insertion, deletion, or field mutation – is treated as a side
effect and the task score is set to zero. Formally,

(11)

\mathrm{clean}(\tau)=\mathbb{1}\big[\Delta S(\tau)\setminus\mathrm{cover}(A(\tau),F(\tau))=\emptyset\big],

where
\mathrm{cover}
denotes the set of diffs explained by
assertions or ignored fields. This prevents an agent from achieving
a high score by completing the requested actions while simultaneously
corrupting unrelated state.

Scoring metrics.

Let
\mathrm{sat}(a,\Delta S)\in\{0,1\}
indicate whether
assertion
a
holds on the state diff. We define three metrics:

Pass rate.
A binary indicator of full task completion with
no side effects:

(12)

\mathrm{Pass}(\tau)=\mathrm{clean}(\tau)\cdot\mathbb{1}\Big[\bigwedge_{a\in A(\tau)}\mathrm{sat}(a,\Delta S)=1\Big].

Score.
An assertion-weighted measure that gives
proportionally more credit to complex tasks. Each task contributes

s(\tau)=\mathrm{clean}(\tau)\cdot\sum_{a\in A(\tau)}\mathrm{sat}(a,\Delta S)
out of a maximum
m(\tau)=|A(\tau)|
.
The aggregate score across a task set
\mathcal{T}
is

(13)

\mathrm{Score}(\mathcal{T})=\frac{\sum_{\tau\in\mathcal{T}}s(\tau)}{\sum_{\tau\in\mathcal{T}}m(\tau)},

so a 10-assertion task that passes 8 assertions but triggers an
unexpected deletion contributes
(0,10)
, not
(8,10)
. This
weighting ensures that long-horizon tasks with many verification
points are not underrepresented relative to simple single-assertion
tasks.

5.1.
Experiment Setup

Prompting & Interaction.

We utilize the ReAct prompting framework
(
29
)
adapted for code execution. The system prompt
8.6
instructs the model to reason about the task and emit a code block (Bash) to interact with the environment.

Documentation conditions.

To disentangle reasoning ability from prior API knowledge, we
evaluate each model under three conditions.

No-docs
(
{\sim}400
tokens): the prompt contains only
the service name, base URL, and ReAct instructions; the agent
must discover endpoints by probing the API.

Relevant-docs
(
{\sim}3{,}200
–
10{,}000
tokens): the
target service’s API specification is injected into the prompt
(Table
10
).

All-docs
(
{\sim}22{,}300
tokens): specifications for
all four services, testing whether irrelevant documentation
degrades performance via context dilution.
No-docs serves as the primary baseline
(Table
4
); documentation effects are
measured relative to it (Table
5
).

Sandbox Execution Environment.

Model responses are parsed to extract Bash code blocks, which are executed in a stateless containerized environment. The sandbox is equipped with standard Linux utilities (
jq
,
curl
,
grep
,
sed
) and a stateless (test-to-test) local filesystem for intermediate file manipulation.
Crucially, all network traffic is intercepted and routed to our local service replicas (Slack, Linear, Box, Google Calendar). To the agent, these replicas are indistinguishable from real upstream APIs in terms of latency, headers, and error schemas.

Inference Parameters.

We evaluate the models listed in Table
11
(Appendix)
via the OpenRouter API using each provider’s default temperature.
Each model uses its full context window; episodes that exceed the
context or token limit are marked as failed. An episode terminates
when the agent emits a
<done>
token, the trace reaches

40 turns
, or wall-clock time exceeds
8 minutes
.

Evaluation Protocol.

Every test case instantiates a fresh sandbox with a deterministically
seeded database state. We perform
3 trials
per
(task, documentation-condition) combination across 3 conditions
(no-docs, relevant-docs, all-docs), yielding 9 runs per task per
model and 2,016 traces per model (224 tasks
\times
9). We log
full conversation traces, token usage, cost, and number of tool
invocations for efficiency analysis.

Bayesian bootstrap aggregation.

We quantify uncertainty via the Bayesian
bootstrap
(
22
)
with a uniform Dirichlet
prior, placing no
a priori
preference among tasks. For a
set of
n
tasks, we draw task weights

\mathbf{w}\sim\mathrm{Dirichlet}(\mathbf{1}_{n})
and compute the
assertion-weighted score

(14)

\hat{S}^{(b)}=\frac{\sum_{i}w_{i}^{(b)}\,s_{i}}{\sum_{i}w_{i}^{(b)}\,m_{i}},

where
s_{i}
is the mean raw score for task
i
(averaged over
trials) and
m_{i}=|A(\tau_{i})|
is the maximum possible score. We
repeat for
B=10{,}000
draws, reporting the posterior mean and
95% credible interval (CrI) from the empirical distribution of

\{\hat{S}^{(b)}\}_{b=1}^{B}
. The
\mathrm{Dirichlet}(\mathbf{1}_{n})

prior is the standard non-informative choice, treating all tasks as
equally likely before reweighting.

For the documentation ablation, we compare three conditions:

no_docs
(baseline),
relevant_docs
(target service
only), and
all_docs
(all four services). We use a paired
Bayesian bootstrap: the
same
Dirichlet
draw
\mathbf{w}^{(b)}
is applied to both conditions over their
shared task set, yielding a posterior over

\Delta^{(b)}=\hat{S}_{A}^{(b)}-\hat{S}_{B}^{(b)}
with correctly
correlated credible intervals on the treatment effect. We report

\Pr[\Delta>0]
as the posterior probability that documentation
improves performance. Cells with
\Pr[\Delta>0]>0.9
indicate
confident beneficial effects;
\Pr[\Delta>0]<0.1
indicates
confident harmful effects.

7.
Conclusion

We introduced Agent-Diff, a benchmark for code-executing LLM
agents on enterprise API tasks. Containerized replicas of
production APIs provide ecological fidelity with full
reproducibility, and a state-diff evaluation contract enables
reproducible, declarative assertions that verify expected state
changes while enforcing a closed-world invariant to detect
unintended side effects. Evaluating nine models across 224 tasks,
we find scores ranging from 38.0 to 88.1, with documentation
effects that are service- and model-specific: pass rates improve
significantly (
+7.0
pp,
P=1.00
) while assertion-weighted
scores do not (
+2.4
,
P=0.73
). A training-cutoff natural experiment validates our inclusion of recently introduced endpoints, which isolate inference-time learning from pre-training memorization.
Error and recovery analysis reveals that top-performing models
favor adaptive strategies (lookup, decomposition) over repetitive
ones (retry-same), indicating that planning quality differentiates
model tiers beyond API knowledge alone. Code and
infrastructure is released under MIT at

https://github.com/agent-diff-bench/agent-diff
.

8.2.
Bayesian Bootstrap Analysis of API Knowledge Errors

To rigorously assess whether documentation reduces API knowledge errors,
we employ a clustere Bayesian bootstrap
(
22
)
approach that accounts for
test-level dependencies and provides full posterior uncertainty quantification.

Error definition.

We define
API knowledge errors
as the sum of two error categories
extracted from our qualitative coding of agent trajectories:

•

Endpoint selection errors
: Calls to non-existent endpoints,
use of deprecated APIs, or selection of inappropriate endpoints for the task.

•

Parameter misuse
: Incorrect argument types, missing required
fields, malformed values, or violation of parameter constraints.

These categories capture failures attributable to incomplete or incorrect
knowledge of the API specification, as distinct from logical errors,
execution failures, or environmental issues.

Experimental design.

For each model, we compare runs under two conditions:
no_docs

(no API documentation provided) and
with_docs
(relevant API
documentation included in context). We compute the delta as

\Delta=\text{statistic}(\texttt{no\_docs})-\text{statistic}(\texttt{with\_docs})
,
such that positive values indicate documentation
reduces
errors.

Clustering by test.

Because the same test may appear under both documentation conditions,
observations are not independent. We cluster by
test_id
to
ensure that bootstrap resampling respects this paired structure.
Specifically, we restrict analysis to tests that appear in both conditions
(shared tests only), then apply Dirichlet-weighted resampling at the
cluster level rather than the observation level. This approach is
analogous to a paired bootstrap but accommodates for potentail unequal numbers of
runs per test.

Bootstrap procedure.

We use Bayesian bootstrap
(
22
)
with

Dirichlet
(1,1,\ldots,1)
reweighting

(
22
)
. For each of
n=100{,}000
draws:

(1)

Sample Dirichlet weights
\mathbf{w}\sim\text{Dir}(\mathbf{1})

for each group independently, with dimension equal to the number of
observations in that group.

(2)

Compute the weighted statistic for each group.

(3)

Record the delta (group A statistic minus group B statistic).

From the resulting posterior distribution of deltas, we extract:

•

Posterior mean
\bar{\Delta}

•

95% credible interval
[\Delta_{2.5},\Delta_{97.5}]

•

Posterior probability
P(\Delta>0)
and
P(\Delta<0)

We consider effects significant when
P(\Delta>0)>0.95
or

P(\Delta<0)>0.95
. All analyses use a fixed random seed (42)
for reproducibility.

Two complementary metrics.

We report two distinct statistics to guard against interpretive artifacts:

(1)

Ratio
(Figure
6
):
API knowledge errors as a proportion of total errors, computed as

\text{ratio}=\frac{\sum_{i}w_{i}\cdot\text{api\_errors}_{i}}{\sum_{i}w_{i}\cdot\text{total\_errors}_{i}}

This metric answers: What fraction of errors are API-knowledge-related?

(2)

Absolute rate
(Figure
7
):
API knowledge errors per test, computed as the weighted mean

\text{rate}=\sum_{i}w_{i}\cdot\text{api\_errors}_{i}

This metric answers: How many API knowledge errors occur per test?

The distinction matters because a reduction in the ratio could arise
from either (a) fewer API knowledge errors, or (b) more non-API errors
inflating the denominator. By reporting both metrics, we can distinguish
these scenarios:

•

If ratio decreases but absolute rate is unchanged: documentation
increases other error types, not a genuine improvement.

•

If absolute rate decreases but ratio is unchanged: documentation
reduces all error types proportionally.

•

If both decrease: documentation targets API knowledge gaps more than non-API knowledge gaps.

Reproducibility.

The bootstrap analysis uses a fixed random seed (42) for reproducibility.
Results, along with metadata including model lists and bootstrap parameters, are saved to JSON.

Recovery Strategies Analysis

We analyze recovery strategies – the behavioral patterns agents exhibit when encountering errors or obstacles during task execution. This analysis proceeds in two stages: first, we characterize the frequency with which different strategies are employed across models (usage rates); second, we evaluate whether employing each strategy is associated with better or worse task outcomes (scores).

Through qualitative coding of agent trajectories, we identified 13 distinct recovery strategies (plus an “other” category), descriptions of which are available in Appendix
9.2
. Each strategy is coded as binary (present/absent) per run, allowing a run to
exhibit multiple strategies.

8.4.
Per-Model Strategy Effectiveness

Usage rates alone do not establish whether a strategy helps or harms task
performance. A frequently-used strategy might be popular precisely because
it is ineffective (agents keep trying it) or because it is effective (agents
learn to rely on it). To disentangle usage from impact, we estimate the association between of each strateand on task scores using Bayesian bootstrap.

Estimand.

For each model
m
and strategy
s
, we estimate:

\Delta_{m,s}=\mathbb{E}[\text{Score}\mid s=1,m]-\mathbb{E}[\text{Score}\mid s=0,m]

where
s=1
indicates the strategy was used in a run and
s=0
indicates
it was not. A positive
\Delta
implies that runs employing the strategy
score higher on average; a negative
\Delta
implies they score lower.

Bayesian bootstrap methodology.

We employ the Bayesian bootstrap
(
22
)
to quantify uncertainty in our estimates via posterior resampling weights. For each bootstrap iteration
b\in\{1,\ldots,B\}
where
B=10{,}000
:

(1)

Draw Dirichlet weights
: Sample
\mathbf{w}^{(b)}\sim\text{Dirichlet}(\mathbf{1}_{n})
independently for each group, where
n

is the number of observations in that group. This is equivalent to
placing a uniform prior over the probability simplex.

(2)

Compute weighted statistics
: For each group (strategy-used
vs. strategy-not-used), compute the weighted mean score:

\bar{S}^{(b)}_{\text{used}}=\sum_{i:s_{i}=1}w_{i}^{(b)}\cdot\text{Score}_{i}

and similarly for
\bar{S}^{(b)}_{\text{not-used}}
.

(3)

Record delta
: Store
\Delta^{(b)}=\bar{S}^{(b)}_{\text{used}}-\bar{S}^{(b)}_{\text{not-used}}
.

From the
B
bootstrap samples, we extract:

•

Posterior mean:
\bar{\Delta}=\frac{1}{B}\sum_{b}\Delta^{(b)}

•

95% credible interval:
[\Delta_{2.5\%},\Delta_{97.5\%}]
(percentiles)

•

Posterior probability:
P(\Delta>0)=\frac{1}{B}\sum_{b}\mathbf{1}[\Delta^{(b)}>0]

Clustering by test.

A critical design decision is whether to account for the nested structure of
our data: multiple runs may share the same underlying test (task), inducing
correlation in the scores. We cluster by
test_id
to ensure that bootstrap
resampling respects this structure.

Specifically, rather than resampling individual runs, we resample at the
cluster (test) level. This approach:

•

Preserves the paired/matched structure when comparing conditions

•

Produces appropriately wider confidence intervals that reflect
true uncertainty

•

Avoids overstating precision due to pseudo-replication

Minimum usage threshold.

We exclude strategies with fewer than 5% usage in a given model to avoid
unstable estimates from extremely sparse cells. This threshold balances
statistical reliability against comprehensiveness.

Significance criteria.

We consider an effect confidently beneficial if
P(\Delta>0)\geq 0.95
,
suggestively beneficial if
0.90\leq P(\Delta>0)<0.95
, and
symmetrically for harmful effects using
P(\Delta<0)
. These thresholds
correspond to conventional 90% and 95% credible intervals excluding zero.

Reproducibility.

All bootstrap analyses use a fixed random seed (42) for reproducibility.
Results are persisted to JSON with full metadata including model lists,
strategy sets, thresholds, and bootstrap parameters.

These strategies likely succeed because they address fundamental sources
of API errors: incorrect parameter values and task complexity.

Universally harmful strategies.

appears in the bottom 1–2 positions for all models,
with strongly negative deltas (
\Delta=-10

This confirms intuition: repeating failed actions without modification

Model-dependent strategies.

shows heterogeneous effects: beneficial for

).

Causal interpretation caveats.

While we frame
\Delta
as an effect, the observational nature of our data
precludes strong causal claims. The association between strategy use and
outcomes may be confounded by:

•

Task difficulty
: Harder tasks may elicit both more
recovery attempts and lower scores.

•

Agent capability
: More capable agents may both employ
sophisticated strategies and achieve higher scores independently.

•

Error type
: Certain error types may trigger specific
strategies while also being intrinsically harder to recover from.

We mitigate these concerns through within-model comparisons (controlling
for capability) and test-level clustering (partially controlling for task
difficulty), but residual confounding remains possible. The effectiveness
estimates should be interpreted as associations conditional on model
and test, not as guaranteed performance improvements from strategy adoption.

8.5.
Median Split Analysis: Recovery Strategy Usage by Model Performance

To investigate whether high-performing and low-performing models differ systematically in their recovery strategy usage, we conducted a median split analysis comparing strategy adoption rates between performance tiers.

8.5.1.
Model Performance Ranking and Group Assignment

Models were ranked by their overall benchmark performance scores and divided into two groups at the median. This yielded the following assignment:

•

Top 4 Models (High Performers):
DeepSeek-V3, Devstral-Small, Qwen2.5-72B-Instruct, Kimi-K2-Instruct

•

Bottom Models (Low Performers):
Grok-3-Mini-Beta, Gemini-2.5-Flash-Preview, GPT-4.1-Mini, Claude-3.5-Haiku, Llama-4-Scout (excluded in sensitivity analysis)

The median split approach was chosen over arbitrary thresholds because it creates balanced comparison groups and is robust to the specific performance values observed. By comparing the top half against the bottom half, we maximize statistical power while maintaining interpretable group definitions.

8.5.2.
Llama Exclusion Rationale

We conducted two parallel analyses: one including all 9 models (Top 4 vs Bottom 5) and one excluding Llama-4-Scout (Top 4 vs Bottom 4). We conducted a test excluding Llama as a sensitivity analysis, since Llama would be classified as a statistical outlier using the Median Absolute Deviation (MAD) method. The modified Z-score for each model was computed as:

(15)

M_{i}=\frac{0.6745\times(x_{i}-\tilde{x})}{\text{MAD}}

where
\tilde{x}
is the median score (74.9) and MAD is the median absolute deviation (6.4). This procedure assumes that the model scores
\{x_{i}\}
are measured on a common scale and are comparable across models. We treat the median
\tilde{x}
as a robust estimate of the central tendency and
\mathrm{MAD}=\mathrm{median}(|x_{i}-\tilde{x}|)
as a robust estimate of dispersion, which is appropriate when a small number of scores may be extreme. The constant
0.6745
is included to put the statistic on an approximate standard normal “
z
-score” scale under a normal reference model: if
Z\sim\mathcal{N}(0,1)
, then
\mathrm{median}(|Z|)=0.6745
, implying
\sigma\approx\mathrm{MAD}/0.6745
for normal data. Using the standard threshold of
|M|>3.5
, Llama-4-Scout (
M=-3.89
) was identified as a statistical outlier.

Llama’s classification as a statistical outlier may indicate a meaningfully different recovery-strategy profile that both (1) places it at a comparative disadvantage under our evaluation setup and (2) exerts disproportionate influence on summary statistics and group-level comparisons.

The primary analysis includes Llama, with the exclusive analysis reported for transparency.

8.5.3.
Strategy Filtering

To ensure reliable estimates, we excluded recovery strategies with very low usage rates. Specifically, a strategy was included in the analysis only if it met a minimum 5% usage threshold in at least one of the two groups. This filtering serves three purposes:

(1)

Noise reduction:
Strategies used in only a handful of runs produce highly variable bootstrap estimates.

(2)

Actionable focus:
Very rare strategies are less relevant for understanding systematic behavioral differences.

(3)

Statistical validity:
Bootstrap resampling becomes unreliable when the base rate approaches zero.

Excluded strategies (typically
use_fallback
,
wait_and_retry
,
handle_ui_obstacle
) were documented but not analyzed.

8.5.4.
Bayesian Bootstrap Procedure

For each recovery strategy passing the usage threshold, we computed the difference in usage rates between the top and bottom groups using Bayesian bootstrap
(
22
)
with test-level clustering.

Statistic of Interest.

For each strategy
s
, we compute:

(16)

\Delta_{s}=\hat{p}_{s}^{\text{top}}-\hat{p}_{s}^{\text{bottom}}

where
\hat{p}_{s}^{\text{group}}
is the weighted proportion of runs in that group that employed strategy
s
. A positive
\Delta
indicates higher usage among top-performing models; a negative
\Delta
indicates higher usage among bottom-performing models.

Bootstrap Resampling.

We used a paired clustered Bayesian bootstrap designed for comparing two groups that share the same experimental units. The procedure operates as follows:

(1)

Cluster definition:
Runs were clustered by a composite key combining
test_id
and
include_api_docs
, treating each (test case
\times
documentation condition) pair as a separate experimental unit.

(2)

Paired weighting:
For each bootstrap draw, we generated a single set of Dirichlet
(1,1,\ldots,1)
weights over the shared clusters. Critically, the same cluster weight was applied to both the top-performing and bottom-performing model groups. This ensures that when comparing strategy usage rates, both groups are evaluated on identically-weighted tasks.

(3)

Within-group size correction:
Within each group, observations sharing a cluster divided that cluster’s weight equally. If cluster
c
received Dirichlet weight
w_{c}
and contained
n_{A}^{(c)}
observations in group A, each observation received weight
w_{c}/n_{A}^{(c)}
. This ensures each cluster contributes equally to the group statistic regardless of how many models completed that task.

(4)

Statistic computation:
For each draw, we computed the weighted usage rate in each group and took their difference:
\Delta=\hat{p}_{\text{top}}-\hat{p}_{\text{bottom}}
.

Formally, the procedure computes:

(17)

\Delta=\sum_{c}w_{c}\cdot\left(\bar{X}_{A}^{(c)}-\bar{X}_{B}^{(c)}\right)

where
w_{c}\sim\text{Dirichlet}(1,\ldots,1)
, and
\bar{X}_{A}^{(c)}
is the mean strategy usage within cluster
c
for group A.

This paired design controls for task-level confounds: if a particular test case is unusually difficult or easy, that effect cancels out when computing the within-cluster difference. The approach is analogous to a paired
t
-test but with Bayesian uncertainty quantification and proper handling of multiple observations per cluster.

We used 10,000 bootstrap draws with random seed 42 for reproducibility. Posterior summaries include the mean, 95% credible interval (2.5th–97.5th percentiles), and directional probabilities
P(\Delta>0)
and
P(\Delta<0)
.

Inference.

From the 10,000 bootstrap draws of
\Delta_{s}
, we computed:

•

Posterior mean:

\mathbb{E}[\Delta_{s}]

•

95% credible interval:

[\text{2.5th percentile},\text{97.5th percentile}]

•

Directional probabilities:

P(\Delta_{s}>0)
and
P(\Delta_{s}<0)

Results were classified according to the following scheme:

•

Significantly higher in top models:

P(\Delta>0)>0.95

•

Significantly lower in top models:

P(\Delta<0)>0.95

•

Not significant:
Neither probability exceeds 0.95

The 0.95 threshold was chosen as the Bayesian analogue to a two-sided
\alpha=0.10
frequentist test, providing a balance between sensitivity and specificity appropriate for exploratory analysis.

8.5.5.
Interpretation and Relationship to Effectiveness Analysis

The median split analysis addresses a fundamentally different question than the per-model effectiveness analysis presented in Appendix
8.4
. While effectiveness asks “does using strategy
s
improve scores within a model?”, the median split asks “do better-performing models use strategy
s
more frequently?”

These questions are complementary and can yield different answers:

•

A strategy might be effective but equally adopted: universally beneficial strategies that all models have learned to employ at similar rates.

•

A strategy might be more common in top models but not causally beneficial: the correlation may reflect model sophistication or training differences rather than the strategy itself driving performance.

•

A strategy might be both differentially adopted and effective: potential drivers of performance differences, where top models have learned behaviors that genuinely improve outcomes.

8.8.
Sandbox Architecture

8.8.1.
Request Interception and Routing

Agent code executes within a
Code Executor
that intercepts outbound HTTP requests and rewrites production URLs to sandbox endpoints. For example, a request to
https://slack.com/api/chat.postMessage
is transparently rewritten to:

{BASE_URL}/api/env/{env_id}/services/slack/chat.postMessage

This interception occurs at the HTTP client level, requiring no modification to agent code – agents believe they are communicating with production APIs.

An
Isolation Middleware
layer extracts the environment identifier from the request path and establishes a database session scoped to the corresponding schema. All downstream handlers operate on this isolated session, ensuring that concurrent environments cannot observe or mutate each other’s state.

8.8.2.
Database-Backed State

We represent service state as a PostgreSQL database, with one schema per environment instance. Entity types map directly to tables; for example, Slack’s state includes
users
,
channels
,
messages
,
reactions
, and
files
tables. Relationships (e.g., message
\rightarrow
channel) are enforced via foreign keys.

Schemas are derived from service specifications:

•

REST APIs
(Slack, Box, Slack): We parse OpenAPI schemas and SDK type definitions to generate SQLAlchemy ORM models. Nullable fields, enumerations, and nested objects are preserved.

•

GraphQL APIs
(Linear): We traverse the GraphQL schema, inferring relational structure from type definitions. Nested types are denormalized into separate tables with foreign key relationships.

8.8.3.
Environment Lifecycle

Each benchmark task executes in a fresh environment:

(1)

Schema Creation
: A new PostgreSQL schema
state_{env_id}
is created by cloning the structure from a service-specific template schema.

(2)

Data Seeding
: Initial state is populated via
INSERT ... SELECT
from the template, ensuring atomic, deterministic initialization.

(3)

Execution
: The agent interacts with replica APIs; all mutations modify tables within the isolated schema.

(4)

Snapshotting
: Before and after execution, we create snapshot tables (
{table}_snapshot_before
,

{table}_snapshot_after
) to preserve state for evaluation.

(5)

Cleanup
: Schemas are dropped after evaluation, reclaiming resources.

8.8.4.
Replica API Implementations

We implement API handlers that read from and write to the isolated database session:

REST Services (Slack, Box, Google Calendar).

Handlers are organized as a dispatch table mapping endpoints to functions. Each handler validates the request against the API specification, performs the corresponding database operations, and returns a response matching the documented schema. For example,
conversations.create
inserts a row into the
channels
table, adds the creator to

channel_members
, and returns the channel object.

GraphQL Services (Linear).

We use a schema-first approach with resolver functions bound to each field. The GraphQL schema is loaded from Linear’s public schema definition. Queries traverse the database via SQLAlchemy relationships; mutations perform validated writes and return updated objects.

Both implementations handle authentication tokens (injected via environment variables), pagination, rate limiting responses, and error conditions documented in the respective API specifications.

8.8.5.
State Diffing

Evaluation relies on computing the precise difference between pre- and post-execution states. Given snapshot tables
T_{\text{before}}
and
T_{\text{after}}
for each entity type (where
T
denotes a table snapshot of that entity’s state), we compute:

(18)

Inserts

\displaystyle=T_{\text{after}}\setminus T_{\text{before}}

(19)

Deletes

\displaystyle=T_{\text{before}}\setminus T_{\text{after}}

(20)

Updates

\displaystyle=\{(e,e^{\prime}):e.\text{pk}=e^{\prime}.\text{pk}\land e\neq e^{\prime}\}

where
e.\text{pk}
denotes the primary key. Set differences are computed via SQL
EXCEPT
queries; updates are detected by joining on primary keys and comparing column values. The resulting
DiffResult
structure contains all inserted, deleted, and modified entities, which is then compared against the task’s expected state changes.

8.9.
Task Generation Prompt

The generation pipeline proceeds in two stages. First, an
algorithmic sampler draws the task horizon

n\sim\text{TruncExp}(\lambda{=}0.3,\,1{..}40)
and samples

9.
Error and Recovery Strategy Methodology

This appendix documents the complete taxonomy used for qualitative coding of agent execution traces, the annotation procedure, and how fine-grained categories were merged for analysis.

9.1.
Error Annotation

9.1.1.
Fine-Grained Error Taxonomy

Each agent execution trace was evaluated for 32 fine-grained error types organized into four domains.

Tool Use Errors.

Errors related to how the agent interacts with tools and APIs.

endpoint_selection
:

Incorrect or irrelevant API endpoint choices for the intended operation.

parameter_misuse
:

Wrong parameter names, wrong data types, wrong structure (missing required keys, extra nesting), using a field not accepted by the tool, or mapping data to the wrong field when a more appropriate field exists.

format_errors
:

Unparseable or malformed tool output: invalid JSON, truncation, or mixing natural language into machine-readable payloads.

code_errors
:

Valid tool calls that fail during execution: Bash syntax errors, runtime exceptions (NameError, ImportError), logic bugs, or environment misconceptions.

Hallucination Errors.

Errors where the agent fabricates or asserts invented information as truth, distinct from reasoning errors (logic failures) and assumption errors (guessing without checking).

parameter_hallucination
:

Agent asserts invented parameter values (IDs, names, timestamps, URLs) as truth, when not grounded in the trace or user input.

outcome_hallucination
:

Agent falsely claims task completion or success despite evidence showing the task was not completed.

state_hallucination
:

Agent fabricates state that doesn’t exist (e.g., “the file was created” when it wasn’t). Distinct from
state_tracking_error
which involves forgetting existing state.

action_hallucination
:

Agent claims to have performed an action that doesn’t appear in the trace – fabricating that execution occurred.

capability_hallucination
:

Agent believes a tool/API can do something it cannot, or invents non-existent endpoints.

context_hallucination
:

Agent references information not present in trace, prompt, or API responses.

other_hallucination
:

A hallucination not covered by the categories above.

Reasoning Errors.

Errors involving logic failures, memory issues, or flawed inference – concerning how the agent thinks rather than fabricating information.

time_orientation_error
:

Confusing past vs. future events, incorrect date/time calculations, or timezone confusion.

state_tracking_error
:

Agent forgot previous actions, failed to update understanding after new information, or repeated already-completed actions (memory failure).

goal_misalignment_error
:

Solving a different problem than asked, missing implicit requirements, or understanding a requirement but deprioritizing it.

causal_reasoning_error
:

Misattributing why something failed, reversing cause and effect, or missing causal steps.

confirmation_bias
:

Ignoring contradictory error messages, persisting with failing approach despite clear feedback.

logical_fallacy
:

False dichotomy, circular reasoning, or non sequitur conclusions.

assumption_error
:

Agent guessed defaults or API behavior without checking first.

negation_error
:

Inverting boolean conditions, misunderstanding “not”/“except”/“exclude”.

scope_generalization_error
:

Over-generalizing from specific instructions or being too literal.

dependency_ordering_error
:

Performing actions in wrong sequence (about ordering, not missing steps).

incomplete_execution_error
:

Agent planned required subtasks but failed to attempt some entirely (about omission).

premature_termination_error
:

Agent stops and concludes task is complete before finishing, without recognizing remaining work.

quantitative_reasoning_error
:

Off-by-one errors, unit confusion, incorrect aggregation or sorting.

reference_resolution_error
:

Misunderstanding what “it”/“this” refers to, confusing similar entities.

instruction_fidelity_error
:

Modifying content that should be preserved verbatim or adding unrequested embellishments.

reasoning_action_mismatch
:

Agent’s explicit reasoning contradicts the action it executes.

infinite_loop_error
:

Agent stuck in pathological loop, repeating identical actions without progress.

other_reasoning_error
:

A reasoning error not covered above.

Other Categories.

model_refusal
:

Agent refuses to act, asks user for information it could retrieve, or delegates execution back to user.

other_error
:

An error that doesn’t fit any category above.

9.1.2.
Merged Error Categories

For interpretability, the 32 fine-grained error annotations were consolidated into 6 merged categories:

(1)

Endpoint Selection
– calling a non-existent or semantically wrong endpoint (direct mapping from
endpoint_selection
).

(2)

Parameter Errors
– incorrect values, missing required fields, type mismatches, or hallucinated parameters. Merged from:
parameter_misuse

\lor

parameter_hallucination
.

(3)

Execution Errors
– malformed JSON, syntax errors, or runtime exceptions in generated code. Merged from:
format_errors

\lor

code_errors
.

(4)

Hallucination
– fabricating API responses, system state, actions, or task outcomes (excluding parameter hallucination, captured above). Merged from:
outcome_hallucination

\lor

state_hallucination

\lor

action_hallucination

\lor

capability_hallucination

\lor

context_hallucination

\lor

other_hallucination
.

(5)

Reasoning Failures
– flawed planning, goal misalignment, confirmation bias, or incorrect state tracking. Merged from 16 reasoning error subtypes (excluding
incomplete_execution_error
and
premature_termination_error

(6)

Incomplete Execution
– runs where the agent stopped before completing all required sub-tasks or declared success prematurely. Merged from:
incomplete_execution_error

\lor

premature_termination_error
.

Categories are not mutually exclusive; a single run may exhibit multiple error types.

9.2.
Recovery Strategy Annotation

Recovery strategies are behavioral patterns agents exhibit when encountering errors or obstacles during task execution. We identified 14 distinct strategies plus a “no recovery” indicator:

retry_same
:

Retried the exact same action unchanged, hoping for a different result.

9.3.
Annotation Procedure

Each of the 4,032 traces was annotated by an LLM judge (Gemini-3-Flash) using a structured JSON schema. For each error and recovery category, the judge provides an explicit
present
/
absent
judgment with a concrete trace excerpt as evidence. The judge receives each trace alongside a reference trace – the highest-scoring run on the same task – to ground its assessments.

Normalization.

Prevalence aggregates are computed as the percentage of runs exhibiting each error or strategy, stratified by model. For comparative analyses (top vs. bottom performers), we apply paired clustered Bayesian bootstrap to control for task difficulty (see Appendix
).

System message.

Context preamble.

The human message includes the run under analysis, a reference run with score context, and the following evaluation instructions:

IMPORTANT EVALUATION CONTEXT:

The agents being evaluated were given these instructions in their

system prompt:

- "Use execute_bash to interact with [Service] API at [endpoint].

Complete the task using the tools provided."

- "Authentication is handled automatically via proxy. Leave a

Therefore, do NOT flag as errors:

- Agent not explicitly handling authentication (it’s automatic

via proxy)

- Agent using placeholder credentials or assuming auth works

- Agent proceeding directly to API calls without auth setup

Now analyze RUN_TO_ANALYZE (and use {other_run_type} only as a

reference for what a correct approach looks like). Evaluate the

following categories in order. For each category, provide the

required fields as specified.

Category 1: Tool Use Errors.

1) Tool Use Errors

Errors related to how the agent interacts with tools and APIs.

Evaluate each subtype explicitly:

endpoint_selection:

Determine whether the agent consistently selects correct endpoints.

- present: True if there are any incorrect or irrelevant endpoint

choices

- explanation: Brief summary of the issue (or why none were found)

- example: One concrete example from the trace (or ’N/A’)

parameter_misuse:

Determine whether the agent ever calls an API endpoint with

incorrectly formatted, incorrectly typed, or semantically

misplaced parameters. This includes:

- Wrong parameter names

- Wrong data types (string vs int vs list vs object)

- Wrong structure (scalar where object required, missing keys)

- Using a field not accepted by the tool

- Semantic field mapping errors: putting data in the wrong field

(e.g., location info in summary instead of location field)

Returns: present, explanation, example.

format_errors:

Determine whether the agent ever produces tool-related output

that is unparseable or malformed. Includes invalid JSON, incorrect

nesting, mixing natural language into machine-readable payloads,

truncation, or any syntax/format issue causing parse failure.

Returns: present, explanation, example.

code_errors:

Determine whether the agent produces valid tool calls but the

content fails during execution. Includes Bash syntax errors,

runtime exceptions (NameError, ImportError), logic bugs, or

environment misconceptions.

Returns: present, explanation, example.

Category 2: Model Refusal.

2) Model Refusal

Determine whether the agent refuses to perform the task, asks the

user for information it could retrieve itself, OR delegates

execution back to user. This includes:

- Explicitly refusing to perform the task

- Asking user for IDs, tokens, or file contents the agent could

find itself

- Passive delegation: gathering information but providing

recommendations instead of performing actions

Returns: present, explanation, example.

Category 3: Hallucination Errors.

3) Hallucination Errors

Hallucinations are when the agent FABRICATES or ASSERTS invented

information as truth. Distinct from reasoning errors (logic

failures) and assumption errors (guessing without checking).

For EACH type, explicitly evaluate whether it occurred. You MUST

provide a judgment (present: true/false) and example for EVERY

category:

- parameter_hallucination: Agent ASSERTS invented parameter values

(IDs, names, timestamps, URLs) as truth, not grounded in trace

or user input.

- outcome_hallucination: Agent falsely CLAIMS task completion

despite evidence showing the task was not completed.

- state_hallucination: Agent FABRICATES state that doesn’t exist.

Distinct from state_tracking_error (FORGETTING existing state).

- action_hallucination: Agent CLAIMS to have performed an action

that doesn’t appear in the trace.

- capability_hallucination: Agent believes a tool/API can do

something it cannot, or invents non-existent endpoints.

- context_hallucination: Agent references information not present

in trace, prompt, or API responses.

- other_hallucination: A hallucination not covered above.

Returns per category: present, example, explanation (only for

other_hallucination).

Category 4: Reasoning Errors.

4) Reasoning Errors

Reasoning errors involve logic failures, memory issues, or flawed

inference. About HOW the agent thinks, not fabricating information.

IMPORTANT DISTINCTIONS:

- state_tracking_error = agent FORGETS (memory failure)

- state_hallucination = agent INVENTS (fabrication)

- assumption_error = agent GUESSES without checking

- hallucination = agent ASSERTS invented facts as known truth

- dependency_ordering_error = wrong SEQUENCE

- incomplete_execution_error = OMITS steps entirely

- premature_termination_error = STOPS early thinking task is done

For EACH type, provide present: true/false and example:

- time_orientation_error: Confusing past vs future, incorrect

date/time calculations, timezone confusion.

- state_tracking_error: Agent FORGOT previous actions, failed to

update understanding, or repeated completed actions.

- goal_misalignment_error: Solving different problem than asked,

missing implicit requirements, deprioritizing explicit ones.

- causal_reasoning_error: Misattributing why something failed,

reversing cause and effect.

- confirmation_bias: Ignoring contradictory error messages,

persisting with failing approach despite clear feedback.

- logical_fallacy: False dichotomy, circular reasoning, non

sequitur conclusions.

- assumption_error: Agent GUESSED defaults or API behavior

WITHOUT CHECKING first.

- negation_error: Inverting boolean conditions, misunderstanding

"not"/"except"/"exclude".

- scope_generalization_error: Over-generalizing from specific

instructions, being too literal.

- dependency_ordering_error: Performing actions in wrong SEQUENCE.

- incomplete_execution_error: Planned subtasks but failed to

attempt some entirely (OMISSION).

- premature_termination_error: Stops and concludes task is

complete before finishing all required steps.

- quantitative_reasoning_error: Off-by-one errors, unit

confusion, incorrect aggregation or sorting.

- reference_resolution_error: Misunderstanding what "it"/"this"

refers to, confusing similar entities.

- instruction_fidelity_error: Modifying content that should be

preserved verbatim or adding unrequested embellishments.

- reasoning_action_mismatch: Agent’s reasoning contradicts the

action it actually executes.

- infinite_loop_error: Stuck in pathological loop, repeating

identical actions without progress.

- other_reasoning_error: Not covered above.

Category 5: Recovery Strategies.

5) Recovery Strategies

For EACH type, evaluate whether the agent attempted it. Provide

present: true/false and example for EVERY category:

- retry_same: Retried exact same action unchanged.

- retry_modified_params: Retried with adjusted parameters.

- switch_tool: Switched to different tool/endpoint for same goal.

- lookup_correct_value: Searched/queried to find correct value.

- backtrack: Returned to earlier step for missing information.

- parse_error_message: Extracted useful info from error output.

- handle_ui_obstacle: Handled popup, dialog, or login wall.

- change_strategy: Abandoned current approach entirely.

- break_into_steps: Decomposed complex action into smaller steps.

- verify_prerequisites: Checked conditions before retrying.

- skip_and_continue: Moved past blocking item to complete others.

- wait_and_retry: Added delay for rate limits or async ops.

- use_fallback: Used secondary/backup method.

- other_recovery_strategy: Not covered above.

- no_recovery_attempted: Gave up or stuck in loop without

recovery.

Category 6: Other Errors.

6) Other Errors

Determine if there are errors not covered by categories 1-4.

Returns: present, explanation (including proposed subcategory

Category 7: Qualitative Summary.

7) Qualitative Summary

Provide a high-level narrative analysis of this run.

Scoring dimensions (each 0--5):

- planning_score: Action sequencing, adaptation, efficiency.

3=Mixed (progress with avoidable detours)
