Zhenzhen Yang, Chenhui Cui, Tao Li, Rubing Huang, Nan Niu, Dave Towey, Shikai Guo

Abstract
. Appropriate test case generation is critical in software testing, significantly impacting the quality of the testing. Requirements-Based Test Generation (RBTG) derives test cases from software requirements, aiming to verify whether or not the system’s behaviors align with user needs and expectations. Requirements are often documented in Natural Language (NL), with use-case descriptions being a popular method for capturing functional behaviors and interaction flows in a structured and readable form. Recently, Large Language Models (LLMs) have shown strong potential for automating test generation directly from NL requirements (including use-case descriptions). However, current LLM-based approaches may not provide comprehensive, non-redundant coverage. They may also fail to capture complex conditional logic in requirements, resulting in incomplete test cases. To address these limitations, we propose a new end-to-end approach that automatically generates test cases from NL use-case descriptions, called Test Generation based on LLM-generated Control Flow Graphs (LLMCFG-TGen). LLMCFG-TGen comprises the following three main steps: (1) CFG Generation: An LLM transforms a use case into a structured, JSON-based Control Flow Graph (CFG) that encapsulates all potential branches; (2) Test-Path Extraction: The generated CFG is explored, and all complete execution paths are enumerated; and (3) Test Case Creation: Finally, the execution paths are then used to generate the test cases. To evaluate our proposed approach, we conducted a series of experiments using four multi-domain use-case datasets spanning diverse application areas. The experimental results demonstrate that LLMs can effectively construct well-structured CFGs from NL use cases. Compared with the two baseline methods, LLMCFG-TGen achieves full path coverage, improving completeness and ensuring clear and accurate test cases. Practitioner assessments confirm that LLMCFG-TGen produces logically consistent and comprehensive test cases, while substantially reducing manual effort. The findings suggest that coupling LLM-based semantic reasoning with structured modeling effectively bridges the gap between NL requirements and systematic test generation.

To address these limitations, we propose an automated approach for generating test cases from NL use-case descriptions,
Test Generation based on LLM-generated Control Flow Graphs
(LLMCFG-TGen).
LLMCFG-TGen is driven by two carefully designed prompts, and comprises three main steps:

(1)

CFG Generation:
An LLM transforms the use case into a structured, JSON-based
Control Flow Graph
(CFG) that is designed to encapsulate all branches.
The CFG is then validated by checking its nodes and edges:
It is rejected if any node is isolated, any non-root node has no incoming edge, or any edge references a non-existent node ID.
The LLM regenerates the CFG until it satisfies all checks and is accepted as structurally complete.
This step is guided by Prompt #1, which provides a concise instruction set and an explicit CFG-construction algorithm.

(2)

Test-Path Extraction:
The system then automatically checks the constructed CFG to enumerate all complete execution paths.
A
Depth-First Search
(DFS) algorithm identifies distinct node-level paths, and each node identifier in a path is replaced with its corresponding NL statement.

(3)

Test Case Creation:
The statement-level paths are converted into detailed test cases by the LLM.
Each test case is formatted according to predefined templates, and then presented to the user for review and confirmation.
This step is guided by Prompt #2, specifying both the instructions and the test
-
case structure.

Without restricting use-case expressiveness, or requiring manual intervention, LLMCFG-TGen supports single-click test generation through a web interface, producing comprehensive, non-redundant, and highly readable test cases.

To evaluate the performance of the proposed approach and its acceptance among practitioners, we performed a comprehensive study using
datasets from multiple domains, encompassing a total of 42 use cases.
We compared the LLM-generated CFGs against manually constructed ones, to assess their correctness and completeness.
The results show that LLMs can produce well-structured CFGs from NL use cases.
Compared with two baselines, LLMCFG-TGen achieves better completeness and lower redundancy.
The generated
CFGs enable full path coverage in the model, with the path-based procedure improving the clarity and accuracy of the resulting test cases.
Practitioner feedback further confirms that LLMCFG-TGen delivers high-quality tests, while substantially reducing the manual effort.

2.1.
Use-Case Description

Use cases can be used to document many elements of the software development process, including business workflows
(

)
.
They can facilitate requirements discussions, helping to define functional specifications, and to record system design decisions
(
11

38

(
15

A use-case description is a structured textual artifact that describes the system’s behavior in response to interactions initiated by external actors
(
60
)
.
It can capture possible sequences of events that lead to achieving a specific goal
(
11
)
.
Compared to full requirements specifications, use-case descriptions are shorter narratives that focus on a single function.
They differ from UML use-case diagrams, which graphically depict the relationships among actors and use cases (or among related use cases)
(
11
)
.
They have a strict syntax, but lack behavioral detail, making them suitable for early-stage communication
(
38
)
.
When used for testing, use-case descriptions provide much (though not all) of the information needed to develop a complete system test suite
(
9
)
.

Writing high-quality use cases can be challenging, because no precise rules exist for their composition, and a diverse range of templates and styles have been produced
(
13
)
.

29
used a paragraph-style format with fields such as name, actors, preconditions, postconditions, basic flow, and alternate flows.
Later work proposed constraints and authoring guidelines:
Cockburn’s template, for example, has been widely adopted, and is recognized as one of the most comprehensive formats
(
11
;
57
)
.
Our proposed approach is template-agnostic and can accommodate use cases written in diverse formats, without the need for structural standardization.

2.2.
Control Flow Graphs

Graphical models are widely used in requirements engineering to support communication among stakeholders, and to guide system design
(
18
)
.
A CFG is an abstract representation of all possible execution paths through a component or system
(
10
)
.
It is typically defined as a directed graph
G=(S,E)
, where
S
denotes the set of nodes and
E\subseteq S\times S
represents the set of directed edges
(
42
)
.
Nodes typically represent basic blocks, and edges denote control transfers between them.

In our context, the nodes correspond to the main, alternative, and exception steps within a use case, while the edges represent control transitions between steps (including sequencing, branching, and looping).
Edges may be annotated with guard conditions, reflecting the decision logic.
(It is assumed that the CFG has no unreachable nodes or edges.)
An execution path is any path from a unique root node to one or more exit nodes
(
39
)
:
They serve as the foundation for our path-based test case creation.

3.2.3.
CFG Verification

Although the LLM is explicitly instructed to avoid producing isolated nodes or edges, its inherent non-determinism
(
50
)
may, nevertheless, produce such things.
A post-generation validation step is therefore applied.

A CFG is considered invalid if any of the following conditions are true:

(1)

Isolated node
:
If any node listed in the node set does not appear in any edge.

(2)

Unreachable “secondary root”
:
If a non-root node lacks incoming edges, it is inaccessible from the designated root.

(3)

Orphaned reference
:
If a node ID specified in the
from
or
to
field of an edge does not exist in the node list.

All node identifiers are first retrieved from the CFG:
If the list is empty, the graph is deemed invalid.
The first node in the list is treated as the root, and all node IDs appearing in the
from
and
to
fields of the edges are recorded.
The node list is checked for each
from
and
to
element of each edge reference, with any mismatch indicating an orphaned reference.
Any nodes that are not in either edge field are flagged as isolated.
Each non-root node is checked for incoming edges, without which it is also marked as invalid.
If none of these situations are detected, the CFG is considered valid.

If the validation fails, then the LLM is re-prompted to regenerate the CFG until a valid structure is produced.
The validated CFG is then used in the subsequent test-path extraction.

3.3.
Step ❷: Test-Path Extraction

Given a verified CFG
G=(S,E)
, this step enumerates all feasible test paths, ensuring that every node and edge is covered at least once.
Figure
3
illustrates an example of the resulting test paths.
DFS with pruning is used to avoid infinite expansion due to cycles:
If a node is revisited within the current path, the traversal stops, and the path is recorded.
If an edge includes an associated condition, then the condition is preserved as a distinct step in the path, providing additional context for subsequent test case creation.

This step involves the following stages (Algorithm
2
):

(1)

Adjacency-list construction
:
This transforms the edge set
E
into an adjacency list
Adj
, where each entry stores the target node and any associated condition.

(2)

Path enumeration
:
Starting from the root node, DFS enumerates all distinct paths that terminate at leaf nodes or cycle entry points (previously visited nodes), recording conditions as separate steps.

(3)

Path translation
:
Node identifiers are replaced in each path with their corresponding NL statements.
Conditions are retained as independent steps, producing readable test scenarios.

3.4.
Step ❸: Test Case Creation

Figure 5.

The test-creation step involves passing each textual test path (from Step ❷) and the original use-case description to the LLM.
Figure
5
shows the prompt (Prompt #2), which defines the role, specifies the instructions, and includes a test-case example.
The LLM produces a complete test case for each test path.
Any LLM output not conforming to the expected format cannot be rendered correctly in the web interface:
In such cases, the LLM is prompted to regenerate the test case, enabling a fully automated workflow.

This per-path strategy ensures that the created test cases are internally coherent, directly traceable to a specific execution path in the CFG, and provide comprehensive coverage of the original use case.
This design enhances clarity, preserves contextual integrity, and ensures semantic completeness.

To answer the RQs, we conducted experiments using multiple use-case datasets.
Four datasets were collected from previous studies and public repositories:
The key details are summarized in Table
1

•

UC1:

UC1 has 12 use cases focusing on remote patient monitoring in the healthcare domain. It includes non-human “Device” actors, emphasizing device-patient-system interactions.
Its format lacks explicit “Title” or “Postconditions” fields, unlike UC3 and UC4.

•

UC2:

UC2 has 13 use cases that cover cross-domain scenarios (including e-commerce, logistics, and automotive).
Unlike the single-domain focus of UC1, UC3, and UC4, the UC2 format is flexible, with domain-specific elements (e.g., “Bounded Alternative Flow” for automotive use cases):
This helps test the adaptability of the proposed method.

•

UC3:

UC3 has five use cases, and is a manually-refined healthcare dataset centered on vital sign management.
It focuses on human-human interactions (in contrast to UC1’s device-centric design), and has the most standardized format (each use case includes “ID”, “Title”, and detailed “Error Handling” elements).

•

UC4:

UC4 has 12 use cases targeting the game domain, including gamer-oriented operations (e.g., adding new AI) and high-level abstract use cases.
The UC4 format integrates user roles into functional descriptions and includes unique “Comments” for cross-referencing (a feature not present in the other datasets).

These datasets span diverse domains and vary in specification detail, ensuring sufficient representativeness for evaluating the CFG generation, test-path extraction, and test-case creation.

4.3.
Baseline Approaches

Two baseline approaches were used in our evaluations:
(1) Direct test-case creation from use case using LLMs, denoted LLM (Direct); and
(2) AGORA
(
14
)
:

•

LLM (Direct):

Using LLMs to create test cases directly is a common approach
(
24
;
40
)
.
This involves providing the LLM with a prompt containing the requirements, and asking it to generate test cases that adhere to the specified format.
Our evaluation prompt had four main components:
A role definition;
instructions for creating the test cases;
an output example; and
the original use case.
The design of this prompt aligns with the LLMCFG-TGen Prompt #2 (Section
3.4
).
The prompt was provided to the LLM, and its test case generation capability was assessed.

•

AGORA:

AGORA uses LLMs in a two-step pipeline designed to create acceptance test cases automatically
(
14
)
.
In the first step, AGORA analyzes the use case to identify testable flows (such as main, alternative, and exception flows), producing a list of test cases.
In the second step, it generates detailed information for each test-case entry (including preconditions, participating actors, and step-by-step instructions with inputs and expected results).

LLM (Direct) is a straightforward, commonly-used approach:
It enables us to assess the core capability of LLMs in test case generation from minimal input.
In contrast, AGORA is a structured and systematic methodology that ensures comprehensive test coverage through a multi-step pipeline.
The combination of these two baselines enables a balanced and diverse assessment of other test-case creation techniques.

4.4.
Evaluation Procedure and Metrics

To answer the RQs, we assessed the quality and reliability of the CFGs and the test cases produced by LLMCFG-TGen.
The evaluation examined both the

effectiveness
and the practitioners’
satisfaction
.
The
effectiveness evaluation
quantitatively measured the correctness and completeness of the generated artifacts (CFGs and test cases) against a manually-established ground truth, comparing the results with those of the baseline methods.
The ground-truth CFGs were developed independently by three doctoral students specializing in computer technology and applications.
All three had prior industry experience (two had worked in software testing, and one in software development), and had a solid understanding of use-case modeling and control flow structures.
Their domain expertise ensured the quality and consistency of the reference CFGs.
Any discrepancies among their initial versions were resolved through collaborative discussion, resulting in a consolidated and reliable reference set for evaluation.
In contrast, the
satisfaction evaluation
relied on industry experts to review and judge the generated test cases.

4.4.1.
Effectiveness Evaluation

The effectiveness evaluation quantitatively assessed the structural accuracy of the LLM-generated CFGs, and the consistency of the generated test paths (compared with those derived from the ground-truth CFGs).
Four complementary metrics were employed:

Precision/Recall/F1-score

(
51
)
;

normalized Graph Edit Distance (nGED)

(
55
;
1
)
;

Discrepancy Rate
; and

Average Absolute Difference (Avg.
|\Delta|
)
.

•

Precision/Recall/F1-score for Nodes and Edges:

To evaluate the structural quality of the generated CFGs, the nodes and edges of each LLM-generated CFG were compared with a manually-constructed ground truth.
The cosine similarity measured the node similarity
(
35
)
between sentence embeddings generated by a pre-trained BERT-based model (
all-mpnet-base-v2

(
17
)
within the
SentenceTransformers
framework
(
54
)
).
The Hungarian algorithm
(
37
)
(implemented with the
linear_sum_assignment
function in the
SciPy
package
(
59
)
) established the optimal node correspondences.
Two nodes were considered equivalent when their cosine similarity exceeded a predefined threshold.
Based on pilot experiments and earlier studies
(
24
)
, a cosine similarity threshold of
0.75
was selected to balance the precision and recall.
When nodes were matched, their identifiers were synchronized, and their edge relationships in the graph were compared to assess the accuracy of connectivity.
The graphs were constructed using the
NetworkX
library
(
23
)
.
Suppose
TP
,
FP
, and
FN
denote the numbers of true positives (correctly matched nodes/edges), false positives (extra nodes/edges not in the ground truth), and false negatives (ground
-
truth nodes/edges missing in the generated outputs), respectively.
Precision, recall, and F1 can be calculated as:

(1)

\text{Precision}=\frac{TP}{TP+FP}

(2)

\text{Recall}=\frac{TP}{TP+FN}

(3)

\text{F1}=\frac{2\times\text{Precision}\times\text{Recall}}{\text{Precision}+\text{Recall}}

Higher precision indicated that a larger proportion of the generated items were correctly matched to the manually constructed CFG
—
meaning fewer false generations.
A higher recall meant that the generated nodes successfully matched more items in the manually constructed CFG
—
meaning fewer missing nodes.
(These interpretations apply to both the nodes and the edges.)
The F1
-
score offers a unified metric that balances precision and recall, reflecting overall matching quality.
Together, these metrics quantified the structural accuracy and completeness of the generated CFGs.

•

Normalized Graph Edit Distance (nGED):

The normalized Graph Edit Distance (nGED)
(
55
;
1
)

was also used to quantify the overall structural similarity.
The nGED measures the minimum number of edits needed to convert one graph into another.
Formally:

(4)

\text{nGED}(G_{1},G_{2})=1-\frac{\text{GED}(G_{1},G_{2})}{|V_{1}|+|E_{1}|+|V_{2}|+|E_{2}|}

(where
|V_{i}|
and
|E_{i}|
denote the numbers of nodes and edges, respectively, in graph
G_{i}
.)
An nGED value close to
1.0
indicates strong structural alignment, while values nearer to
0.0
represent significant topological differences.
(The graph constructions and comparisons were implemented in Python using the
NetworkX
library
(
23
)
.)

•

Discrepancy Rate:

The
Discrepancy Rate
measured the proportion of use cases in which the number of test paths generated from the LLM-derived CFGs differed from that obtained from the ground truth CFGs.

(5)

\text{Discrepancy Rate (\%)}=\frac{N_{\text{diff}}}{N_{\text{UCs}}}\times 100\%,

(where
N_{\text{diff}}
denotes the number of use cases with mismatched path counts, and
N_{\text{UCs}}
represents the total number of use cases.)
A lower discrepancy rate indicates greater consistency between generated and reference path enumerations, suggesting behavioral alignment in the underlying CFG structures.

•

Average Absolute Difference (Avg.
|\Delta|
):

We computed the
Average Absolute Difference (Avg.
|\Delta|
)
, across all use cases, to quantify the magnitude of deviation in the number of generated test paths:

(6)

\text{Avg.}\,|\Delta|=\frac{1}{N_{\text{UCs}}}\sum_{i=1}^{N_{\text{UCs}}}\left|\text{LLM}_{\text{path count},i}-\text{GroundTruth}_{\text{path count},i}\right|

(where
N_{\text{UCs}}
is the total number of use cases;

\text{LLM}_{\text{path count},i}
is the number of test paths generated from the LLM-based CFG for the
i
-th use case; and

\text{GroundTruth}_{\text{path count},i}
is the number of paths derived from the ground truth CFGs.)
A smaller
\text{Avg.}\,|\Delta|
value indicates that the generated test paths more closely reflect the behavioral complexity captured by the ground-truth CFGs.

These four metrics collectively captured both the structural and behavioral alignment between the generated and ground-truth CFGs, providing a comprehensive and objective assessment of generation effectiveness.

Satisfaction Evaluation

Answering RQ3 required an evaluation of the perceived quality of the LLMCFG-TGen test cases, compared to the baseline, as judged by industry practitioners.
The expert panel consisted of one quality assurance (QA) manager and three senior test engineers from a large international company specializing in consumer multimedia software for managing, editing, and sharing digital photos, videos, and music. Each expert had 13–20 years of professional experience in software testing.

The interface allows experts to compare MethodA and MethodB directly, while anonymizing method identities to ensure unbiased evaluation.

For every use case within the datasets, two sets of test cases were evaluated:
One generated by AGORA and the other by LLMCFG-TGen.
Both sets were created under identical experimental conditions, using the same GPT

case descriptions.
To ensure consistent and efficient assessment, we developed a web-based HTML interface that presented the original use case alongside two anonymized test case sets (MethodA

This enabled a direct comparison and rating across predefined dimensions, thus minimizing cognitive load and ensuring fairness (by maintaining a consistent level of contextual information).

).

The interview-based evaluation session lasted approximately two hours.
We first introduced the procedure and then provided a brief overview of the use cases.
Due to the limited expert availability, detailed feedback was only collected for 20 use cases (the first five from each dataset):
This covered 113 corresponding test cases generated by AGORA and LLMCFG-TGen.

Following the evaluation criteria established in previous studies
(
7
;
61
)
, the practitioners were asked to assess the two sets of test cases across four quality dimensions:

Relevance
,
Completeness
,
Correctness
, and
Clarity
.

•

Relevance:

This assesses whether or not the test case preserves the intent of the original requirement or use case.
A relevant test case should accurately reflect the intended behavior, avoiding ambiguity, misunderstanding, or hallucinated content.

•

Completeness:

This evaluates whether or not the test case fully covers all critical behaviors, conditions, and paths described in the source use case.
Possible situations include a complete omission of a test case, or some test suites may be incomplete (lacking essential elements such as titles, preconditions, steps, inputs, or outputs).

•

Correctness:

This refers to the logical and semantic validity of the test case.
A correct test case should follow a coherent structure, aligned with the domain logic and requirements’ constraints.
Redundant, illogical, or contradictory elements negatively impact the correctness.

•

Clarity:

The clarity refers to how readable and unambiguous the test case is:
Clear test cases present titles, preconditions, and steps concisely and unambiguously.
This then facilitates interpretation by human testers or use by other tools.

The test cases were evaluated across each of the four dimensions using a five-point Likert scale
(
41
)
, where 5 indicates Strongly Agree, 4 Agree, 3 Neutral, 2 Disagree, and 1 Strongly Disagree.
Each test case was evaluated by the four domain experts according to the criteria, with the scores then aggregated and analyzed.
These scores represented satisfaction, quantifying the practitioners’ subjective judgments.
Qualitative feedback was also collected from the experts, about their experiences with LLMCFG-TGen and their perceptions of the generated test cases.

5.5.
Threats to Validity

Some factors may impact the generalizability and robustness of our findings.
This section discusses possible validity threats and describes the measures taken to manage them.

Internal validity.

The results may be influenced by variability in the “LLM-as-judge” procedure.
Because LLMs can produce different outputs for the same prompt, due to stochastic decoding, we fixed the prompt and set the temperature to
0
to ensure deterministic behavior.
Furthermore, to minimize evaluator bias during the expert assessment, we concealed the origin of each test case:
The evaluators were not informed which method generated which case, either during the interviews or during the evaluation.

Construct validity.

Three complementary sets of metrics were used in the study:
(1) CFG-level metrics (node-level and edge-level precision, recall, F1, and nGED);
(2) test-case metrics (
Discrepancy Rate
and
Avg.
|\Delta|
); and
(3) practitioner metrics (Relevance, Completeness, Correctness, and Clarity).
Each set has limitations:
For example, although the
Discrepancy Rate
shows the number of differing use cases, it does not capture the magnitude of those differences.
To address this, we reported the results across all metric sets, providing a multi-perspective view that reduces the risk of misinterpretation from any single metric.

External validity.

We also acknowledge the limitations of our dataset selection.
Although the evaluation spans multiple domains and formats, the coverage was not exhaustive.
Certain domain-specific structures or linguistic patterns may be underrepresented, introducing potential selection bias, and limiting generalizability.
Future work should adopt a broader sampling strategy to include a wider range of styles and domain characteristics.

6.
Discussion

This section analyzes the strengths and limitations of LLMCFG-TGenin generating test cases from NL use-case descriptions across four multi-domain datasets, taking into account multiple evaluation metrics, including user satisfaction.

6.1.
Strengths

6.1.1.
Input Flexibility and Domain Independence

Unlike traditional methods
(
60
;
5
)
that depend on rigid use-case templates or domain-specific models, LLMCFG-TGen accepts diverse use-case formats, and does not require manual preprocessing.
The experimental results show that, across the four datasets spanning diverse domains and use-case formats, LLMCFG-TGen consistently produced high-quality test cases.

6.1.2.
Full Automation and Model Validation

In contrast to approaches that require manual construction of intermediate models, LLMCFG-TGen automatically generates CFGs, in JSON format, using an LLM.
Automated validation then ensures the completeness and correctness of the generated CFGs.
A web-based interface enables one-click generation of test cases from NL use cases, substantially reducing manual effort, and improving accessibility.

6.1.3.
High Coverage and Clarity of Generated Test Cases

The experimental results show that the LLMCFG-TGen test cases have comprehensive coverage, minimal redundancy, and high correctness and clarity.
Practitioner evaluations confirmed that LLMCFG-TGen creates test suites that are both relevant and easy to interpret, emphasizing its practical value for test case generation from requirements.

6.2.
Weaknesses

6.2.1.
Single-Use-Case Processing

The current implementation processes one use case at a time.
It does not yet support batch generation.
Future work will extend the approach to handle multiple related use cases by identifying relationships such as inclusion and extension before CFG construction.
By clustering related use cases into modules, the LLM could generate CFGs more efficiently, while preserving consistency across connected use cases.
Furthermore, to support large-scale use cases, the efficiency and scalability of path enumeration will need to be enhanced.

6.2.2.
Lack of Test Prioritization

The created test cases are not prioritized or ranked:
Although LLMCFG-TGen produces comprehensive coverage, it does not consider execution order.
Introducing prioritization
—
for example, executing main flows before exceptional paths
—
would improve testing efficiency, and better align with real-world testing practices.
Future work will explore extending CFGs with path-level priority to enable automated test-case ranking.

6.2.3.
Abstract Test Cases without Executable Scripts

The approach generates abstract test cases that can guide test engineers, but they do not include concrete input data or executable scripts.
Linking abstract test cases to source code or runtime environments could enable the generation of fully executable test cases, thereby reducing manual effort and supporting end-to-end automation.

7.
Conclusions and Future Work

This paper has proposed an end-to-end pipeline for generating test cases from NL use-case descriptions:
It is called
Test Generation based on LLM-generated Control Flow Graphs
(LLMCFG-TGen).
LLMCFG-TGen involves three steps:
(1) generating a CFG using an LLM;
(2) enumerating feasible execution paths; and
(3) creating test cases from the paths.
Experiments showed that LLMCFG-TGen produces CFGs that align closely with manually-constructed ones.
Compared with direct LLM-based generation or another existing pipeline, LLMCFG-TGen generated test suites with higher coverage, lower redundancy, greater correctness, and clearer wording.
LLMCFG-TGen has no specific use-case template requirements, does not need manual modeling, and is adaptable across different LLMs.
Practitioner evaluations further confirmed that the generated test cases were comparable to manually-created ones, in terms of both readability and structural coherence.

Our future work will include expanding support to a wider spectrum of datasets and diverse types of NL requirements, including user stories and unstructured requirement specifications.
This will require enhancing the robustness of CFG generation to better handle noisy, incomplete, or domain-specific inputs.
Furthermore, incorporating interactive or adaptive mechanisms, such as human-in-the-loop feedback
(
45
)
, may enable more comprehensive requirements analysis, integrating multimodal information (including text, images, and graphs).
Finally, establishing a unified LLM-driven framework that connects requirements analysis, model generation, and test creation, execution, and evaluation, is an interesting direction for self-adaptive and explainable test generation from requirements.
We look forward to engaging further with this goal.
