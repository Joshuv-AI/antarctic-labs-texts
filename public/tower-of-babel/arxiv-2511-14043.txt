AISAC: An Integrated multi-agent System for Transparent, Retrieval-Grounded Scientific Assistance
Chandrachur Bhattacharya, Sibendu Som

Abstract
AI Scientific Assistant Core (AISAC) is an integrated multi-agent system deployed at Argonne National Laboratory for scientific and engineering workflows. AISAC builds on established technologies—LangGraph for orchestration, FAISS for vector search, and SQLite for persistence—and integrates them into a unified system prototype focused on transparency, provenance tracking, and scientific adaptability. The system implements a Router–Planner–Coordinator workflow and an optional Evaluator role, using prompt-engineered agents coordinated via LangGraph’s StateGraph and supported by helper agents such as a Researcher . Each role is defined through custom system prompts that enforce structured JSON outputs. A hybrid memory approach (FAISS + SQLite) enables both semantic retrieval and structured conversation history. An incremental indexing strategy based on file hashing minimizes redundant re-embedding when scientific corpora evolve. A configuration-driven project bootstrap layer allows research teams to customize tools, prompts, and data sources without modifying core code. All agent decisions, tool invocations, and retrievals are logged and visualized through a custom Gradio interface, providing step-by-step transparency for each reasoning episode. The authors have applied AISAC to multiple research areas at Argonne, including specialized deployments for waste-to-products research and energy process safety, as well as general-purpose scientific assistance, demonstrating its cross-domain applicability. AISAC is not a new model architecture. Its contribution is a system-engineering blueprint for AI scientific assistance, consisting of: (1) a practical integration blueprint for transparent, retrieval-grounded multi-agent scientific assistance; and (2) a reusable, configuration-driven core that supports project-level specialization, provenance tracking, and persistent memory.

The
AI Scientific Assistant Core (AISAC)
adopts a layered, modular architecture that cleanly separates orchestration, memory, retrieval, and user interface functions.
Each layer — responsible respectively for reasoning control, data persistence, semantic grounding, and interaction — can evolve independently while preserving structured and inspectable execution.
This modularity aligns with contemporary design philosophies in transparent multi-agent systems

,

Unlike monolithic AI systems that require forking to support new domains, AISAC embeds extensibility into its substrate.
Each of the seven architectural layers (Orchestration, Memory, Retrieval, Tooling, Configuration, Transparency, and Extensibility) exposes well-defined extension points that projects can occupy without coordination or code conflict.
Projects are free to extend independently; the bootstrap mechanism ensures their customizations compose cleanly with the shared core.

1. Orchestration Layer.

Computation is represented as a directed state graph connecting three primary cognitive agents—
the
Router
,
Planner
, and
Coordinator
—supported by helper agents such as the

Researcher
and an optional
Evaluator
for quality assurance and feedback.
These agents implement intent routing, task decomposition, execution, and optional review; their roles are described in detail in Section
2.1
.
Every inter-agent transition and tool invocation is logged as a structured event within the
reasoning graph, enabling step-by-step reconstruction and auditability of the system’s reasoning
trace.
AISAC does not replace existing orchestration frameworks; rather, it uses them as compatible substrates on which science-specific capabilities—such as provenance logging, hybrid memory, and project bootstrapping—are layered.

2. Memory and Persistence Layer.

AISAC maintains a dual-memory subsystem integrating symbolic and semantic storage.
Conversational history and user interactions are stored relationally in an
SQLite
database, while contextual embeddings of dialogue and documents are managed within a
FAISS
vector index.
This hybrid design enables both exact recall and approximate semantic retrieval for long-horizon continuity; details of the memory and retrieval design are given in Section
3
.

3. Retrieval and Knowledge Integration.

AISAC’s retrieval-augmented generation (RAG) subsystem ingests, embeds, and indexes heterogeneous scientific artifacts—including papers, reports, scripts, and simulation logs.
The RAG system maintains a persistent manifest storing file metadata (SHA-256 hash, modification time, size, chunk count) for each indexed document. During updates, unchanged files are skipped, while modified or new files are re-embedded incrementally. Separate manifests for base and on-demand indices enable independent corpus evolution without redundant computation. This layer currently uses flat FAISS indices and grounds reasoning in verifiable sources, extending traditional RAG into a dynamic, evidence-aware memory. The incremental indexing strategy and on-demand data manifests are further discussed in Section
3
.

4. Tooling and Action Layer.

Scientific reasoning often requires computation and retrieval beyond text synthesis.
AISAC defines a structured tool interface schema, inspired by OpenAI’s function-calling protocol, to enable deterministic invocation of search engines, analytical routines, or domain APIs.
Each tool call produces structured logs capturing inputs, outputs, and execution metadata, creating a complete provenance record of every external action.
This reflective action space supports hybrid reasoning—combining symbolic, numerical, and textual processing—while remaining fully traceable for inspection.
Tools may be globally registered or extended dynamically through project-specific bootstraps (Section
5
), and the overall tooling design is detailed in Section
4
.

5. Configuration and Extensibility Layer.

System behavior—model selection, embedding backends, and runtime policies—is governed by declarative configuration objects.
This abstraction separates infrastructure-level parameters (e.g., context windows, model endpoints, embedding dimensions) from domain logic, enabling reproducibility and portability across environments.
The same configuration schema supports both hosted APIs and offline inference endpoints, offering flexibility for research scenarios where privacy, sensitivity, or connectivity constraints apply.

6. Graphical Transparency Interface.

AISAC includes a live graphical dashboard that visualizes the system’s reasoning process in real time.
Planner traces, retrieved evidence, and intermediate computations appear as hierarchical, navigable elements—mirroring structured introspection interfaces in recent orchestration frameworks
[
10
]
.
Each decision path, retrieval source, and tool invocation is inspectable, fulfilling the transparency and provenance requirements central to
AI for Science
.
This interface exposes the full reasoning trace, turning the assistant into an explainable, auditable collaborator.

7. Agent Prompt and Personality Registry.

Agent roles and communication styles are defined through parameterized prompt templates that encode task constraints, tone, and memory scope.
These templates can be rebranded programmatically for each project, ensuring consistent reasoning structure while allowing domain-specific language and formality (e.g., concise analytical responses for engineering workflows versus descriptive summaries for research documentation).
By decoupling reasoning logic from tone and domain framing, AISAC maintains reproducibility while supporting adaptive, field-specific deployments.

Together, these layers form a unified substrate for transparent scientific reasoning.
All reasoning, retrieval, and reflection steps are structured, logged, and explainable—providing not only reliable task execution but also verifiable provenance for reproducibility.
In AISAC, both tools and helper agents are exposed to the Planner as a unified capability namespace. Extending the system with new planner-callable behaviors typically requires only adding a configuration entry for a tool or agent—without modifying the Planner or Coordinator code.
Because all layers communicate through stable, schema-based message contracts, new capabilities—custom tools, data types, or reasoning graphs—can be integrated without altering the core, making
AISAC
a sustainable foundation for the next generation of AI-driven scientific assistants.

Beyond the Researcher, AISAC supports any helper agent registered in the agent registry. Planners list available helpers and invoke them via a generic helper interface. Each helper receives isolated context and can invoke tools within its own reasoning loop. 1.

Router (Intent Understanding & Context Retrieval)
—
Serves as the cognitive front-end and dispatcher.
The Router interprets user intent through semantic embeddings and historical context, classifying
whether a query is factual, analytical, or exploratory.
It retrieves relevant information from both relational (
SQLite

(
FAISS

context overload.
Depending on task complexity, the Router either dispatches the query directly to the Coordinator
for execution or to the Planner for decomposition.
All routing decisions, retrieved document identifiers, and similarity scores are serialized to
preserve complete provenance.

2.

Planner (Reasoning & Task Decomposition)
—
Acts as the system’s strategist, responsible for breaking complex scientific problems into
smaller, structured subtasks.
The Planner is intentionally
tool-less
, producing declarative reasoning plans that specify
which tools, datasets, or evidence types are required.
It delegates these subtasks to one or more Coordinators for execution and monitors intermediate
outputs to ensure logical alignment.
This separation of reasoning and execution maintains hierarchical context: the Planner preserves
the global reasoning state, while Coordinators operate within local task scopes.
In the AISAC interface, these nested reasoning levels are visualized as hierarchical panes,
allowing users to trace how high-level hypotheses translate into concrete computational actions.

3.

Coordinator (Execution & Synthesis)
—
Functions as AISAC’s
tooled workhorse
, executing the plans defined by the Planner or
simple user queries routed directly by the Router.
It invokes structured tools (e.g., scientific search, semantic retrieval, or code execution) to
perform analytical, computational, or retrieval tasks.
The Coordinator aggregates partial outputs, performs consistency checks across results, and
synthesizes findings into coherent, evidence-backed responses.
Each Coordinator maintains an independent reasoning trace and structured log of tool invocations,
ensuring every computational step is reproducible and verifiable.

4.

Researcher (Evidence-Centric Retrieval & Analysis)
—
Serves as AISAC’s dedicated evidence-gathering specialist and helper agent.
The Researcher consumes high-level goals from the Planner and performs deep, tool-using
retrieval over local RAG indices and external scientific sources (e.g., literature search tools,
structured databases).
It aggregates, filters, and annotates candidate evidence—papers, reports, simulation logs—into a
compact working set, along with provenance metadata such as file paths and retrieval scores.
This explicit separation of evidence collection from planning and execution makes it easy to audit

what
sources informed a given conclusion and to rerun analyses with updated corpora or
retrieval policies.

5.

Evaluator (Quality Assurance, Reflection & Adaptation)
—
An optional oversight agent that performs meta-level evaluation of the entire reasoning process.
The Evaluator reviews all serialized traces—including Router context selection, Planner
decomposition, and Coordinator outputs—to assess completeness and provide preliminary quality
checks on factuality and internal consistency. The Evaluator is implemented and can be enabled on a per user-exchange basis; longitudinal learning mechanisms represent planned future work. The Evaluator produces a JSON packet containing up to 10 critiques, each with a 0–1 severity score. It computes average severity and flags individual high-severity issues. These scores drive pass/fail decisions (avg ¿ threshold or single ¿ threshold), and when enabled, can trigger automatic re-routing without user intervention.

Each agent operates under version-controlled, schema-defined prompts (see
Section
5
), which specify objectives, input/output formats, and behavioral
constraints.
Because every routing decision, plan, tool call, and evaluation trace is serialized,

the high-level inference process is inspectable and auditable, and can be approximately reconstructed from its serialized trace, given similar model settings.

This explicit traceability distinguishes
AISAC
from opaque conversational systems,
positioning it as a transparent and verifiable collaborator in scientific discovery.

3. Memory and Retrieval Layer

The
AI Scientific Assistant Core (AISAC)
integrates relational persistence and dual-layer semantic retrieval to form a unified memory substrate—supporting both long-horizon conversational continuity and document-grounded scientific reasoning.
This design draws from hybrid symbolic–vector memory paradigms explored in cognitive and agent systems
[
12
,
13
]
, adapting them for the practical needs of reproducible, provenance-aware scientific workflows.

Relational Persistence (Symbolic Memory)

All cognitive events—including user prompts, agent plans, tool calls, and synthesized outputs—are stored in an
SQLite
database configured in write-ahead logging (WAL) mode for concurrent read/write operations.
Each record is indexed by session ID, timestamp, and message type, producing a fine-grained, queryable history of every reasoning episode.
This relational layer serves as AISAC’s
episodic memory
, providing deterministic traceability across sessions.
Every response can thus be linked to its originating query, retrieved evidence, and intermediate computation.
For scientific use, this symbolic persistence ensures version control, provenance tracking, and multi-experiment auditability—foundational for reproducible research pipelines.
In our implementation, each vector retrieval is associated with a symbolic reasoning trace in the relational store, enabling reconstruction of the entire cognitive chain.

Dual Semantic Retrieval (Vector Memory)

AISAC complements symbolic persistence with two FAISS-based vector stores, enabling both scientific grounding and conversational recall:

•

RAG Vector Index
— constructed from document embeddings of curated corpora (papers, reports, simulation logs), serving as the assistant’s long-term scientific memory;

•

Dialogue Vector Index
— a lightweight semantic index of past question–answer pairs, optimized for conversational continuity and contextual reuse.

In the current implementation, dialogue retrieval is used to populate semantically related “older pairs” that the Router can surface as context, while document-level grounding relies on explicit RAG tool calls (e.g., by the Coordinator or Researcher) into the RAG vector index.
This dual retrieval pathway allows AISAC to reuse prior conversations when helpful while still grounding new answers in curated scientific corpora.

Incremental RAG Subsystem

The retrieval-augmented generation subsystem forms the knowledge backbone of AISAC.
It incrementally scans and indexes project-defined repositories—PDFs, Word and Markdown documents, code scripts, and experiment logs—embedding each chunked segment for semantic retrieval.
Each file’s SHA-256 hash, size, and modification timestamp are stored in a manifest, allowing the indexer to skip unchanged files during updates.
This incremental approach supports continuous corpus evolution without redundant re-embedding, facilitating daily or scheduled refreshes for active research projects.

Conceptually, the RAG subsystem acts as AISAC’s
long-term scientific memory
: a curated, evidence-based substrate that grounds reasoning in validated, relatively stable sources such as peer-reviewed literature, technical reports, and simulation data.
By relying on persistent external knowledge rather than volatile parametric recall, AISAC reduces hallucination risk and maintains fidelity to verifiable sources
[
18
]
.

On-Demand Knowledge (Ad-Hoc Layer)

Complementing the persistent RAG index, AISAC maintains an
on-demand manifest
of transient or high-volume data—such as CSVs, spreadsheets, or simulation outputs—located in registered project directories.
These are cataloged but not embedded, avoiding unnecessary vector index inflation.
Instead, they are discoverable and analyzable through specialized tabular tools when explicitly referenced.
This design keeps the vector memory lightweight and semantically focused, while enabling flexible integration of ephemeral computational data when required by the reasoning chain.

From a systems perspective, RAG provides
stable, evidence-based grounding
, whereas on-demand data access provides
adaptive situational reasoning
.
Together, they enable AISAC to combine static scientific understanding with dynamic analytical insight—e.g., querying a static paper corpus while analyzing fresh simulation results during the same reasoning episode.

Scientific Implications

This hybrid memory architecture allows AISAC to operate simultaneously as a
knowledgeable scientist
and an
adaptive analyst
.
Its dual FAISS indices—one for persistent RAG grounding and one for dialogue continuity—ensure that both long-term context and short-term intent are preserved, while the relational store maintains a verifiable causal trace linking them.
This separation of stable and adaptive knowledge domains ensures
context-aware, reproducible, and auditable reasoning
, satisfying key requirements for next-generation AI systems in scientific research and engineering
[
15
]
.
Through this design, AISAC establishes a durable foundation for transparent, evidence-grounded scientific collaboration.

4. Tooling and Action Space

The
tooling layer
of the
AI Scientific Assistant Core (AISAC)
defines how agents interface with the external world—retrieving knowledge, executing analyses, and managing scientific evidence.
Rather than issuing unconstrained natural-language commands, every agent action is expressed through a
structured function call
validated against a standardized schema.
This schema-driven design, compatible with the function-calling paradigms of modern orchestration frameworks such as LangGraph and AutoGen
[
10
,
17
]
, ensures that every operation is type-safe, reproducible, and auditable.
By coupling structured execution with real-time introspection, AISAC turns conversational reasoning into an executable, transparent scientific workflow.

Structured Action Semantics

Each tool within AISAC is defined by a schema specifying its name, description, argument structure, and expected outputs.
Agents invoke these tools using structured JSON messages, which are automatically validated, logged, and serialized into the orchestration graph.
Every invocation produces a standardized response envelope—including execution status, results, and metadata (e.g., latency and source identifiers)—providing provenance for each computational act. AISAC does not rely on LangChain for orchestration; it uses only the tool-schema conventions for compatibility.

This approach is conceptually aligned with declarative program synthesis models such as DSPy
[
8
]
, where reasoning is compiled into interpretable, verifiable steps.
In scientific workflows, this schema-enforced execution guarantees
computational provenance
: each retrieval, analysis, or synthesis step is a discrete, replayable event rather than an opaque model output.
Consequently, the assistant’s reasoning chain becomes a form of executable documentation.

Traceability and Introspection

All tool interactions in AISAC emit trace events through an internal trace stream, capturing tool identity, input arguments, results, timing metrics, and associated agent state.
These are streamed in real time to the graphical user interface, where users can visualize ongoing reasoning, inspect intermediate computations, and replay prior executions.
This introspection model aligns with reflective-agent paradigms such as Reflexion
[
13
]
to support scientific accountability: each trace constitutes a verifiable step in the reasoning pipeline.
Researchers can thus obtain a full human- and machine-readable log of how each scientific result was derived. This design follows the conventions of LangChain and MCP-style interfaces, ensuring compatibility rather than introducing a competing standard.

Core Scientific Capability Suite

AISAC provides a concise but expressive baseline toolset that defines its
action vocabulary
—the essential operations through which an AI co-scientist engages with data, computation, and evidence:

1. Information Retrieval and Literature Search.

Schema-defined utilities allow agents to access both public and curated scientific sources.
General-purpose web search tools extend context beyond local knowledge, while specialized scientific endpoints (e.g.,
arxiv_search
,
pubmed_search
) retrieve structured metadata, abstracts, and citation records.
These ensure that reasoning remains grounded in citable, verifiable evidence rather than model recall.

2. Local Semantic Retrieval.

AISAC integrates natively with its retrieval-augmented memory subsystem (Section
3
).
Agents query local FAISS indices to retrieve project-specific materials—lab reports, CFD logs, or experimental notebooks—preserving data locality and confidentiality.
This hybrid local–global model enables evidence-based reasoning while maintaining full provenance and privacy for sensitive research data.

3. Computational and Analytical Tools.

The framework includes lightweight execution environments for running short analytical scripts, performing data transformations, or generating plots.
Each execution is schema-validated and logged with detailed provenance metadata.
Future versions will incorporate stronger sandboxing and resource limits for untrusted code.
These analytical capabilities allow AISAC not only to reason about results but also to
compute, verify, and visualize
them, bridging the gap between linguistic reasoning and scientific computation.

4. DataFrames and Stateful Execution.

AISAC maintains a DataFrame registry enabling tools to load tabular data from multiple sources (CSV, Excel with auto-detected header levels, Parquet, JSON) and marshal them into persistent code sessions. Each session has isolated import whitelisting and variable state, supporting multi-turn analytical workflows. DataFrames can be previewed, queried via pandas expressions, or exported to sessions for Python analysis.”

5. Summarization, Provenance, and Self-Reflection.

Beyond direct computation, AISAC provides meta-tools for summarization, citation generation, and provenance export.
Each reasoning session can be serialized into a structured record—akin to a computational notebook—capturing retrieval chains, code execution outputs, and reflection steps.
This enables direct conversion of an assistant’s reasoning trajectory into a version-controlled, auditable scientific artifact.

MCP Integration and Interoperability

AISAC’s tool schema follows MCP-style conventions for interoperability. Full MCP integration—including MCP server/client endpoints and cross-framework communication—remains planned future work.
Because each tool in AISAC exposes a structured interface (arguments, types, and return schema) equivalent to MCP-compliant contexts, the framework can both
consume
and
expose
these tools as MCP endpoints.
In practice, this allows AISAC agents to integrate seamlessly with third-party AI ecosystems or laboratory automation frameworks—sharing contextual state, memory, and results between local and hosted environments.
Thus, a computation or retrieval initiated by AISAC can be extended to any MCP-compatible agent or service, and vice versa, without loss of context or provenance.
This interoperability ensures that AISAC can function not only as a standalone assistant but also as a node in larger, multi-agent scientific workflows spanning models, APIs, and experimental systems.

Extensibility and Project Adaptation

AISAC’s tool space is
open by design
.
Projects can register domain-specific extensions—such as surrogate model evaluators, CFD post-processors, or chemical property databases—through lightweight local modules.
Each extension inherits the same validation, logging, and trace mechanisms as the built-in tools, guaranteeing consistent transparency across domains.
This modularity allows AISAC to adapt from combustion science to materials informatics, process optimization, or climate analytics without architectural modification.

Scientific Motivation and Impact

In scientific contexts, reproducibility and interpretability are non-negotiable.
AISAC’s structured action semantics enforce a standard of machine-readable provenance, turning every analytical or retrieval operation into an auditable event.
Each session thus produces a complete, inspectable record of reasoning activity, supporting scientific workflows that require traceable, evidence-based computation.
This design directly supports the DOE’s “AI for Science” initiative
[
15
]
and the broader FAIR data movement, ensuring that every computational insight is accompanied by its verifiable lineage.

Through its schema-enforced tooling and conceptual alignment with MCP-style interfaces,
AISAC
bridges the boundary between language and computation.
Every reasoning act—retrieval, calculation, or reflection—is executed as a reproducible, traceable operation, yielding both insight and its provenance.

5. Project-Specific Bootstrapping

A central architectural contribution of AISAC is its configuration-driven deployment model, which transforms the system from a fixed orchestration substrate into a
platform
for building, deploying, and maintaining multiple domain-specialized co-scientists.
The
project-specific bootstrapping layer
—a declarative mechanism enabling each research project or domain to extend, specialize, or constrain the shared framework without modification—ensures methodological consistency, version control, and reproducibility across projects.
This layer transforms AISAC from a monolithic framework into a
living ecosystem
of modular, interoperable scientific assistants.
The design follows modular AI principles
[
8
,
10
]
, ensuring reproducibility, version control, and sustainable co-evolution across diverse research programs.

Motivation and Design Philosophy

Scientific disciplines such as combustion, materials design, climate modeling, and process safety exhibit deeply heterogeneous data types, terminologies, and computational workflows.
Developing separate assistants for each field would lead to fragmentation and redundant maintenance, while enforcing a single rigid model would sacrifice domain fluency.
AISAC’s bootstrapping mechanism resolves this tension by decoupling the
core scientific reasoning substrate
—which must remain methodologically stable—from the
domain configuration layer
, which can evolve independently per project.

Each project defines a declarative specification describing its scope, expertise, and data roots.
This specification acts as a “cognitive overlay” atop the shared AISAC foundation: it dictates how the assistant reasons, which tools it may invoke, and which sources it treats as authoritative.
By externalizing domain customization, AISAC guarantees that
(i) improvements to the central engine propagate automatically to all assistants, and
(ii) each deployment remains independently versioned and auditable.
The result is a framework that is
domain-fluid but methodologically consistent
—the assistant adapts linguistically and contextually, while its reasoning, memory, and provenance systems remain consistent across scientific applications.

Bootstrap Mechanisms (Implemented)

AISAC operationalizes project customization through
three independent, toggleable extension layers
, each controlled by a boolean flag in the project manifest:

Tool Extension

Projects define domain-specific analytical capabilities—surrogate model evaluators, CFD post-processors, property calculators—through a project-level module that returns a list of schema-defined tools.
At bootstrap, these are merged into the global tool registry without modifying core code.
All custom tools inherit AISAC’s validation, tracing, and provenance logging, ensuring consistency across domains.

Example use cases:

•

Combustion research: Register heat-flux calculators, reaction-rate integrators

•

Materials science: Register phase-diagram lookups, crystal-structure validators

•

Process safety: Register hazard assessment utilities, risk-scoring models

Agent Specialization

Projects adapt Router, Planner, Coordinator, and Evaluator reasoning by providing optional prompt overlays.
These override the shared system prompts with domain-specific language, technical vocabulary, and reasoning depth.
For instance, a combustion assistant might add chemical kinetics terminology to the Coordinator, while a materials assistant adds phase-equilibria concepts to the Researcher.
Because prompts are applied as
runtime overlays
—not baked into source code—the same core orchestration serves multiple disciplines without recompilation or code branching.

Graph Augmentation

Projects can extend or reroute the orchestration graph by providing a custom graph builder function.
This enables addition of domain-specific reasoning nodes (e.g., a
Simulator
interfacing with HPC solvers, a
Domain Reviewer
performing hypothesis validation, an
Experiment Planner
designing laboratory workflows).
The custom builder receives the core graph as input and may add edges, nodes, or conditional branches while preserving compatibility with AISAC’s state contracts and tracing infrastructure.

Bootstrap Execution Pipeline

At runtime, a deterministic bootstrap sequence executes:

1.

Load project manifest and check extension toggles

2.

If enabled, load and merge tool extensions into global registry

3.

If enabled, load and overlay agent prompts onto core agents

4.

If enabled, load and apply graph transformations

5.

Initialize user memory and RAG indices

6.

Launch interface with merged configuration

This pipeline ensures that every customization is explicit, logged, and reproducible.
A project’s full runtime configuration can be reconstructed from its manifest and local extension modules, supporting version control, audit trails, and multi-environment consistency.

Project Manifest Structure

Each AISAC deployment is defined by a project manifest specifying:

Identity and Domain

•

Assistant display name (e.g., “Scientific Analyst for Materials Research”)

•

Assistant category (e.g., “Research Assistant,” “Engineering Tool”)

•

Specialized domain or focus area

Data Sources

•

Paths to persistent, embedded retrieval indices (with descriptions)

•

Paths to catalog-only on-demand data sources

Each path is indexed incrementally by file hash; unchanged files are skipped during refresh cycles, supporting continuous corpus evolution without redundant re-embedding.

Extension Toggles

•

Tool injection enabled/disabled (default:
disabled
)

•

Agent prompt specialization enabled/disabled (default:
disabled
)

•

Graph augmentation enabled/disabled (default:
disabled
)

All toggles default to
disabled
, ensuring that projects inherit the stable AISAC core until explicitly opting into customization.
This
safe-by-default
design minimizes configuration errors and ensures consistent baseline behavior across deployments.

Environmental Reproducibility

Because the manifest and local extension modules fully specify an assistant’s configuration, the same assistant can be instantiated identically across development, testing, and production environments.
Combined with AISAC’s serialized reasoning traces, this enables reproducible, auditable deployments where every reasoning episode is reconstructible from its configuration and event logs.

Runtime Integration and Deployment

At runtime, the bootstrapping layer dynamically composes each assistant’s environment by merging the stable core modules (orchestration, tools, memory, retrieval) with project-defined overlays.
Every imported module, tool, and data path is registered and logged in an initialization trace, ensuring that the assistant’s configuration is transparent and reproducible.

Configuration Validation

Before initializing reasoning, AISAC validates that all paths referenced in the manifest are accessible, all local extension modules are syntactically correct, and no name conflicts exist in the tool registry.
If validation fails, the bootstrap sequence halts with a descriptive error, preventing partial or corrupted deployments.
This strict validation ensures every running assistant reflects its declared configuration exactly.

Multi-Environment Consistency

Deployment modes range from interactive GUI sessions (localhost development) to headless execution on HPC or cloud systems, where assistants can monitor experiments, analyze results, or manage autonomous computational workflows.
The same project manifest can be deployed across all these environments without modification.
Platform-specific runtime details are handled transparently by the core, while domain logic and data sources remain invariant.
This portability is essential for scientific workflows where reasoning must transition seamlessly from exploratory to production phases.
In all cases, initialization follows a deterministic pipeline, guaranteeing consistent behavior across local, distributed, and hybrid environments.

Deployment Patterns

AISAC bootstrapping supports multiple institutional patterns:

Single-Domain Specialist

A research team in a specialized domain configures data sources pointing to their literature corpus, enables tool injection to register domain-specific analytical routines, and enables prompt specialization for domain terminology.
Their assistant is domain-fluent and computationally capable without leaving the AISAC framework.

Multi-Domain Portal

A single AISAC instance serves multiple departments by swapping manifests at launch time.
Each department sees its own specialized assistant (different name, expertise, tools, data sources) but all share backend infrastructure (memory, orchestration, interface).
This reduces maintenance burden and ensures cross-disciplinary consistency in how reasoning is traced and provenance is recorded.

Hybrid HPC + Local Reasoning

A research team uses graph augmentation to insert domain-specific reasoning nodes that interface with remote HPC job submission.
The planner decomposes tasks; coordinators retrieve literature and run local analyses; specialized nodes dispatch expensive computations to clusters.
All steps are logged and traced through a unified reasoning graph, providing end-to-end visibility into hybrid workflows.

Iterative Domain Expansion

A team starts with all extension toggles disabled, using stock AISAC.
As they identify domain-specific needs, they enable tool injection to register new analytical routines.
Later, they enable prompt specialization to adapt reasoning language.
Finally, they enable graph augmentation to introduce validation or planning nodes.
Each phase is purely additive; no existing functionality is sacrificed or reimplemented.

Scientific Impact and Rationale

Beyond its technical benefits, the bootstrapping mechanism provides a governance model for
sustainable, federated AI in science
.
By standardizing how assistants inherit, extend, and specialize, AISAC supports the creation of an interoperable ecosystem of co-scientists that share a common reasoning substrate while advancing domain-specific expertise.
Each assistant can contribute new tools, datasets, or reasoning modules back to the shared ecosystem without fragmenting it—promoting cumulative, transparent progress across research groups.
This architecture directly supports the DOE’s long-term vision for reusable, trustworthy AI systems that accelerate scientific discovery across mission areas
[
15
]
.

In summary, the project-specific bootstrapping layer transforms
AISAC
from a monolithic framework into a
living ecosystem
of modular, interoperable scientific assistants.
It operationalizes
extensibility without fragmentation
, allowing research groups to instantiate assistants that are domain-adaptive, methodologically consistent, and scientifically auditable—foundational traits for next-generation AI collaborators in scientific research.

6. Graphical User Interface

A defining feature of the
AI Scientific Assistant Core (AISAC)
is its integrated
Graphical User Interface (GUI)
, which exposes the assistant’s internal cognition in real time.
Far from a conventional chat front-end, the GUI functions as a
live reasoning dashboard
—making the system’s reasoning, retrieval, computation, synthesis, and optional evaluation observable, traceable, and reproducible from end to end.

Design Philosophy: Transparency as a System Property

The GUI operationalizes AISAC’s central design principle: transparency is not a presentation layer but a
systemic property
.
Every decision, retrieval, or computation is trace-linked to both its upstream context and downstream effect.
This embodies the architectural goals discussed in Sections
2
–
4
: structured actions, serialized state transitions, and trace-based reasoning reconstruction.
Users can fluidly navigate from a summarized explanation to the exact evidence, tool parameters, and intermediate outputs that produced it, achieving explainable cognition.

Event Stream and Data Flow

During operation, all components of AISAC publish structured trace events to an internal trace stream.
Each event includes:

1.

agent identity and phase (Router, Planner, Coordinator, Evaluator),

2.

timestamps and basic latency metrics,

3.

context retrieval details (e.g., RAG chunk identifiers and FAISS index names when available),

4.

tool invocation specifications (name, arguments, execution summaries), and

5.

compact reasoning excerpts for semantic comparison and debugging.

The GUI subscribes to this event stream, rendering an evolving visualization of the reasoning graph in real time while maintaining stable identifiers for replay, citation, and cross-session continuity.

Core Interface Components

The interface is organized into four synchronized views that together reveal the assistant’s reasoning lifecycle:

Planner Trace.

Displays the declarative task decomposition generated by the Planner.
Plans appear as hierarchical outlines of subtasks with explicit dependencies and ordering.
Because the Planner operates without direct tool execution, this panel represents the
intent structure
of reasoning—showing how the assistant frames complex scientific goals before taking any external action.

Coordinator Execution.

Presents the system’s
tooled work-horse
activity: the concrete execution of subtasks through structured tools such as
arxiv_search
,
rag_query
, or
run_python
.
Each call expands to reveal input arguments, result summaries (e.g., retrieved documents, computed values, or data transformations), and post-call validation notes.
Multiple Coordinators are grouped by subtask lineage, preserving the logical hierarchy and ensuring visual coherence even in multi-branch reasoning graphs.

Hierarchical Context Panes.

Show the nested working context assembled by the Router and Planner.
These panes include conversation history, retrieved passages, file manifests, and intermediate computations—each aligned to its reasoning node.
They enable users to trace how high-level questions propagate into specific evidence selections or dataset references without exceeding the global attention limit.

Evaluator Review (when enabled).

The Evaluator panel displays structured quality assessments including completeness checks, consistency analysis, and confidence scoring. Automated re-planning loops—where Evaluator feedback triggers immediate revision without user intervention—represent ongoing development work (Section
7
).

The GUI implements progressive disclosure through live-updating accordions: as tool calls execute, their headers retitle with query/result metadata, and outputs stream into per-step context buffers, enabling users to follow reasoning without page reloads or manual refreshes.

Traceability, Export, and Trace-Based Reconstruction

Every AISAC session can be exported as a machine-readable trace bundle containing:

•

a serialized reasoning graph (nodes, edges, timestamps);

•

complete tool invocation logs with hashed inputs/outputs;

•

context manifests referencing RAG chunk IDs and similarity ranks; and

•

configuration pins (model versions, embedding models, retrieval parameters).

The GUI and trace subsystem can export to JSON (for machine replay) and Markdown (for human-readable summaries).
Given the same configuration and available tools, the exported trace can be used to approximate the reasoning process and regenerate results to the extent permitted by model stochasticity—enabling independent inspection, lab-to-lab comparison, and peer validation of results.

Interaction Patterns and Usability

The GUI adheres to minimalist, research-oriented visualization principles to balance depth and clarity:

•

Progressive disclosure:
Nested accordions reveal details on demand, preventing visual overload while preserving trace fidelity.

•

Evidence previews:
Retrieved text and tabular results are rendered as side-by-side cards with source identifiers and similarity metadata.

•

Error surfacing:
Tool failures, validation mismatches, and Evaluator alerts are prioritized to the top of each pane with recommended remediations or re-run options.

These patterns turn reasoning traces into an intuitive, browsable research record rather than a debugging interface.

Role in Scientific Reproducibility

By coupling structured trace visualization with exportable configurations, the GUI transforms every interaction into a
citable scientific artifact
.
Researchers can append exported traces to electronic lab notebooks, simulation reports, or publications; collaborators can replay identical reasoning chains to verify or extend conclusions.
In doing so, the GUI becomes not merely an interface but a
transparency enforcer
—the operational embodiment of AISAC’s central commitments to provenance, accountability, and reproducible scientific reasoning.

7. Discussion and Future Work

The
AI Scientific Assistant Core (AISAC)
advances the vision of transparent, reproducible, and extensible
AI-for-Science
frameworks.
By uniting structured orchestration, hybrid persistence, and traceable reasoning, AISAC connects experimental multi-agent prototypes with production-grade scientific assistants capable of sustained collaboration.
Its layered architecture—spanning orchestration, memory, retrieval, and transparency—provides the foundation upon which domain-specialized co-scientists can be deployed across disciplines.

Scientific and Architectural Impact

AISAC demonstrates that autonomy and interpretability can coexist within a single architecture.
AISAC’s runtime centers on three primary agents (Router, Planner, Coordinator), supported by the Researcher and other extensible helper agents, with an optional Evaluator introduced as a separate feedback node. Together, these components enable complex, tool-mediated reasoning with explicit separation between intent routing, evidence collection, task design, and execution while preserving full auditability.
Every action—retrieval, computation, synthesis—is schema-validated and logged, helping machine reasoning meet the reproducibility standards expected of scientific inquiry.
This aligns directly with DOE’s “AI for Science” vision
[
15
,
16
]
, emphasizing explainable, evidence-grounded AI systems.

AISAC currently supports operational assistants at Argonne across three deployment categories: (i)
domain-specialized research assistants
for waste-to-products conversion (FM4R2P) and energy process safety (AI-EPS);
(ii) a
general-purpose scientific assistant
for literature analysis and daily research support; and (iii) a
meta-cognitive assistant
for AISAC system evaluation and code quality assessment. These deployments demonstrate AISAC’s versatility across specialized research, operational support, and reflexive system improvement.

These deployments validate AISAC’s adaptability to diverse, high-stakes research workflows.

Future Research Directions

The directions outlined below represent ongoing and planned work rather than fully implemented capabilities in the current AISAC core.

1. Reinforcement Learning for Orchestration.

The Planner and Coordinator are planned to be enhanced with reinforcement learning to optimize routing, tool selection, and context reuse based on Evaluator feedback.
This adaptive orchestration will enable AISAC to refine its reasoning strategies dynamically across tasks and sessions.

2. Multimodal and Visual Reasoning.

Scientific reasoning often requires analysis of figures, fields, or simulation plots.
Future versions will incorporate multimodal nodes integrating visual-language models and symbolic extractors, enabling interpretation of flowfields, phase maps, or microscopy data.

3. Distributed and HPC-Aware Execution.

AISAC will evolve toward distributed orchestration across hybrid HPC–cloud environments.
Computation-heavy subtasks (e.g., CFD post-processing or surrogate evaluation) will execute asynchronously on HPC backends while maintaining a synchronized reasoning graph for transparent oversight.

4. Domain Bootstraps.

Bootstraps—reference packages demonstrating how new scientific assistants can be instantiated from a shared AISAC core with minimal overhead.

5. Integration with External Standards.

AISAC’s schema-based tooling layer will deepen integration with the
Model Context Protocol (MCP)
to interoperate with other orchestration and model-serving ecosystems.
This will enable cross-framework collaboration and compliance with FAIR and open-science data principles.

6. Reflective and Longitudinal Learning.

The Evaluator will evolve from a per-session reviewer into a longitudinal meta-cognitive component, tracking recurring weaknesses (e.g., citation omissions or retrieval misalignment) and guiding continual improvement without retraining the underlying models.

Long-Term Vision

In the long term, AISAC aims to underpin a federated ecosystem of scientific co-scientists / interoperable assistants that share a common reasoning substrate while specializing in distinct domains.
Each instance will contribute structured knowledge, reasoning traces, and tools back to a shared repository, fostering cumulative, verifiable scientific progress.
By grounding autonomy in transparency and reasoning in evidence,
AISAC
positions AI not as an opaque generator, but as a
verifiable assistant supporting scientific workflows
.

8. Conclusion

We presented the
AI Scientific Assistant Core (AISAC)
—a modular, transparent, and extensible multi-agent framework for reproducible scientific reasoning.
AISAC combines structured orchestration, persistent hybrid memory, and retrieval-grounded reasoning to enable AI systems that are not only capable of analysis but also accountable for how those analyses are produced.
Its declarative, project-level bootstrap layer allows any research domain to instantiate its own assistant—complete with domain tools, data, and reasoning styles—without altering the shared, verifiable core.

AISAC’s primary contribution is not a new agent algorithm or orchestration primitive, but a systems-engineering approach to deploying them reproducibly across scientific domains.
The project-specific bootstrap layer operationalizes this: researchers define what they need (tools, reasoning styles, data sources) through a declarative manifest and optional extension modules.
The bootstrap pipeline merges these declarations into a runnable assistant—one that shares orchestration, memory, and tracing infrastructure with all other AISAC deployments while remaining contextually specialized.
This design enables both
methodological consistency
(all assistants reason transparently, use structured tools, and log provenance) and
disciplinary diversity
(each assistant employs domain terminology, specialized algorithms, and project-specific data).

Key Contributions:

•

Transparent multi-agent Orchestration:

A graph-based runtime centered on three primary agents (Router, Planner, Coordinator),
supported by the Researcher and other extensible helper LLM-driven agents, with an optional Evaluator
introduced as a separate feedback node. This design decomposes reasoning into interpretable,
inspectable steps with full provenance tracking and a clear split between evidence gathering
and computational synthesis.

•

Persistent Hybrid Memory:

Dual FAISS–SQLite architecture for combining symbolic conversation memory with semantic retrieval, supporting long-horizon and reproducible reasoning across sessions. Each conversational turn is stored with full provenance: role (user/assistant/planner/coordinator), structured metadata (scratchpad, action logs, planning patches), and indexed timestamps. This enables session reconstruction, turn-by-turn replay, and longitudinal analysis of reasoning patterns across multiple turns and sessions.

•

Incremental RAG Infrastructure:

An efficient, continuously updating retrieval subsystem for grounding reasoning in evolving scientific corpora and project datasets.

•

Structured Tooling and MCP Alignment:

Schema-defined tools that enable verifiable computation, data access, and literature retrieval—fully traceable today.
Tool schemas follow MCP conventions, enabling planned integration with external ecosystems.

•

Project-Level Bootstrapping:

A declarative configuration layer for domain-specific extensions, allowing laboratories to deploy custom assistants that share infrastructure but maintain methodological independence.

•

Graphical Transparency Interface:

A live, event-driven GUI that visualizes planner traces, tool actions, and reasoning graphs—turning AI cognition into an auditable scientific workflow.

•

Reflection and Self-Evaluation:

An optional Evaluator agent and planned longitudinal feedback loop for quality assurance, adaptive reasoning, and continuous model refinement.

Collectively, these elements establish
AISAC
as a reusable foundation for transparent, retrieval-grounded, and verifiable AI co-scientists.
By embedding reproducibility into every layer—reasoning, retrieval, computation, and reflection—AISAC aims to support AI as a dependable collaborator in the scientific process.
