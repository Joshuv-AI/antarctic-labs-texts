Automated Modernization of Machine Learning Engineering Notebooks for Reproducibility
Bihui Jin, Kaiyuan Wang, Pengyu Nie

Abstract
. Interactive computational notebooks (e.g., Jupyter notebooks) are widely used in machine learning engineering (MLE) to program and share end-to-end pipelines, from data preparation to model training and evaluation. However, environment erosion —the rapid evolution of hardware and software ecosystems for machine learning—has rendered many published MLE notebooks non-reproducible in contemporary environments, hindering code reuse and scientific progress. To quantify this gap, we study 12,720 notebooks mined from 79 popular Kaggle competitions: only 35.4% remain reproducible today. Crucially, we find that environment backporting, i.e., downgrading dependencies to match the submission time, does not improve reproducibility but rather introduces additional failure modes. To address environment erosion, we design and implement MLEModernizer , an LLM-driven agentic framework that treats the contemporary environment as a fixed constraint and modernizes notebook code to restore reproducibility. MLEModernizer iteratively executes notebooks, collects execution feedback, and applies targeted fixes in three types: error-repair, runtime-reduction, and score-calibration. Evaluated on 7,402 notebooks that are non-reproducible under the baseline environment, MLEModernizer makes 5,492 (74.2%) reproducible. MLEModernizer enables practitioners to validate, reuse, and maintain MLE artifacts as the hardware and software ecosystems continue to evolve.



1.
Introduction

Interactive computational notebooks, such as Jupyter notebooks
(
Kluyver et al. 2016
)
, are widely adopted in machine learning and data science
(
Wang et al. 2021
;
Yin et al. 2023
;
Ghahfarokhi et al. 2024
;
Pimentel et al. 2019
)
,
thanks to their combination of interactive code execution and rich visualizations
(
Rule et al. 2018
)
.
In machine learning engineering (MLE), Python Jupyter notebooks (referred to as
notebooks
from now on) serve as the primary code artifacts for documenting and sharing end-to-end machine learning pipelines, from data preparation to model training and evaluation
(
Wang et al. 2021
;
Pimentel et al. 2019
)
.
Many machine learning research prototypes are shared in this format
(
Pimentel et al. 2019
;
Ghahfarokhi et al. 2024
)
.

Reproducibility is a crucial property in MLE to ensure trusted scientific progress in academia, and to facilitate code reuse in industry.
Nonetheless, MLE notebooks increasingly suffer from the
environment erosion
problem: as hardware and software ecosystems rapidly evolve, re-executing older notebooks on a current environment often fails or yields different results, and reconstructing the exact historical environment is rarely feasible
(
Pimentel et al. 2019
;
Pineau et al. 2021
;
Gundersen and Kjensmo 2018
)
.
This motivates a practical question for both research and reuse: can we reproduce the reported scores of previously published notebooks on the latest hardware and software stack?

To assess this, we conduct a motivation study on 12,720 notebooks mined from 79 popular Kaggle competitions
(
Chan et al. 2024
)
.
We re-execute the notebooks using a recent Kaggle Docker container (aligned with how Kaggle executes submissions), allowing at most 10% score difference to account for evaluation mismatch and stochasticity.
Our study shows that only 35.4% of the notebooks are reproducible; the reproducibility gap persists despite a relatively standardized ecosystem
(
Pimentel et al. 2019
;
Pimentel et al. 2021
)
.

The standard industry response of environment backporting, i.e., downgrading dependencies to match the notebook’s submission time, does not close this gap.
Since Kaggle’s Docker images older than two years are no longer available, we implement a backporting algorithm that downgrades dependencies to the submission timestamp.
Surprisingly, only 35.1% notebooks are reproducible after backporting, fewer than at baseline’s 35.4%.
This result exposed a fundamental flaw in the prevailing paradigm: treating the environment as a variable to be reconstructed and the notebook code as an immutable artifact.
We therefore shift our focus to modernize the notebook code to restore reproducibility, treating the environment as a fixed constraint, so that notebooks are modernized to run and reproduce under the current environment rather than the historical one.
Repair in this setting cannot stop at “green” (no errors): an MLE notebook that runs but whose accuracy drops from 95% to 60% is not acceptable.
We therefore treat score-calibration—moving the reproduced score toward the reported Kaggle score within the replication band—as a first-class repair target alongside error repair and runtime reduction.

Recent advances in large language models (LLMs) have shown promising coding capabilities, especially for program repair
(
Bouzenia et al. 2025
;
Xie et al. 2025
)
and code evolution tasks such as adapting deprecated APIs
(
Wang et al. 2025a
;
Dilhara et al. 2023
)
.
In this work, we explore the use of LLMs to
modernize
MLE notebooks so that they can be reproducible in contemporary environments.
We design and implement
MLEModernizer
, an LLM-driven agentic framework that iteratively fixes a notebook towards reproducibility.
Each iteration begins with
MLEModernizer
executing the notebook and recording its score deviation (from the reported score), runtime, and any error messages during execution.
By analyzing the execution context,
MLEModernizer
prepares a targeted LLM prompt, in one of the three fix types: error-repair, score-calibration, or runtime-reduction.
Then,
MLEModernizer
uses LLM to generate a patch at the file level (i.e., the entire notebook), so that the LLM can identify the root cause of non-reproducibility and propose a comprehensive solution covering multiple code locations (thus reducing the number of fix iterations needed).

To evaluate
MLEModernizer
, we apply it on the 7,402 non-reproducible notebooks in our dataset, using GPT-5.2 as the LLM.

MLEModernizer
successfully modernizes 5,492 notebooks (74.2%) to be reproducible.
Notably,
MLEModernizer
is adaptive to cases where errors are unrelated to reproducibility: 1,284 notebooks (17.3%) become reproducible despite residual errors (Error Reproducible), a desirable property since those errors can be safe to ignore.

MLEModernizer
is also economically viable: it requires 5.70 fix iterations on average and costs 0.31 per notebook on average, making it practical for large-scale industrial use.
We also analyzed the types of errors that can be fixed by
MLEModernizer
, and performed an ablation study to understand whether cell-level error-repair can be more effective.

Our work has broad implications for the MLE community.
By enabling the automated modernization of MLE notebooks,
MLEModernizer
can facilitate the validation and reuse of MLE pipelines even as software and hardware stacks rapidly evolve.
Researchers can use
MLEModernizer
to reproduce the prototypes and results in prior work, which is a tedious process if done manually thus hindering knowledge transfer in ML research.
Engineers can use
MLEModernizer
to keep their MLE pipelines up-to-date and reproducible, improving user trust in their products.

The main contributions of this work include:

•

Motivation Study

We conducted a reproducibility study of MLE notebooks mined from popular Kaggle competitions, and showing that only a minority remain reproducible today.
We further demonstrated that environment backporting does not close the reproducibility gap.

•

Technique
.
We developed
MLEModernizer
, an LLM-driven agentic framework that modernizes MLE notebooks for reproducibility in contemporary environments via three targeted fix types: error-repair, runtime-reduction, and score-calibration.

•

Evaluation
.
We evaluated
MLEModernizer
and found that it successfully modernizes 5,492 (74.2%) of the non-reproducible notebooks in our dataset, with a low cost of 0.31USD per notebook, demonstrating practicality for large-scale use.

•

Dataset

We curated a dataset of real-world Kaggle MLE notebooks with execution traces and reproducibility labels, enabling future research on MLE notebooks.

2.1.
Reproducibility of MLE Notebooks

2.1.1.
Dataset Collection

To systematically study the reproducibility challenges in MLE notebooks, we constructed a large-scale dataset of real-world MLE notebooks from Kaggle. Our dataset collection process involves two main steps:
(1) identifying relevant submissions from Kaggle competitions, and
(2) extracting comprehensive metadata and code content for each submission version.

Competition Selection

We start from MLE-Bench
(
Chan et al. 2024
)
, a curated benchmark built from Kaggle competitions and designed for evaluating end-to-end ML workflows.
MLE-Bench provides a standardized offline grading setup, which makes it feasible to execute and grade notebooks at scale when Kaggle’s held-out test sets are not publicly available.
By anchoring our study on the competitions in MLE-Bench, we cover a broad range of high-quality MLE tasks including image classification, natural language processing, time series prediction, and tabular data analysis.

Notebook Mining

We leverage Kaggle’s official Python API
(
Kaggle 2025c
)
to identify all notebook submissions associated with the selected competitions, and we collect
all
available versions for each submission.
Because Kaggle’s API does not provide full notebook contents or version histories, we additionally scrape the Kaggle web interface using Selenium to retrieve (1) the code content converted into a standard Jupyter notebooks (
.ipynb
) format and (2) the notebook’s execution outcome on Kaggle, including success/failure, score, runtime, and (3) submission timestamp.
We skip versions marked as “Copied from notebook” (duplicates) and with empty code content. Through this process, we mined 171,075 notebooks from 79 Kaggle competitions (including 75 in MLE-Bench’s test set and 4 in MLE-Bench’s validation set).
This data collection was performed in April 2025, and the oldest notebook we collected dates back to August 2016.

.
Distribution of notebook runtime.

Filtering Criteria

We apply several filtering criteria to focus our study on notebooks where reproducibility can be meaningfully measured,
First, we retain only notebooks that have been successfully executed on Kaggle and have a non-zero score, as these represent notebooks that successfully produced valid predictions and can be evaluated against ground truth.
Second, we retain notebooks with runtime less than or equal to 600 seconds (decided by analyzing the distribution of runtime as shown in Figure
2
),
so that our study covers the majority of notebooks and remains tractable in terms of computational resources usage.
Third, we restrict our analysis to Python notebooks (excluding R notebooks) to maintain consistency in dependency management and execution.
Finally, we exclude notebooks that use external datasets beyond the competition’s provided data.
Such a filter eliminates external effects on reproducibility (e.g., datasets that may no longer be accessible or have changed over time) and allows us to focus on code modernization challenges.
A total of 12,720 notebooks are retained for our study after applying these filters.

2.1.2.
Execution Environment Setup

Kaggle notebooks are executed inside Docker containers
(
Kaggle 2025a
)
, and each execution produces a versioned snapshot that is tied to a particular container version.
To align with Kaggle’s environment model and minimize environment-induced discrepancies, we execute each notebook inside a GPU-enabled container based on Kaggle’s official Python image
2
2

2

https://github.com/Kaggle/docker-python
, with mounting the competition training and test sets provided by MLE-Bench.
The same execution environment is used for all experiments in this paper.

Environment and Hyper-Parameters

We conduct our experiments on a server with AMD EPYC 7343 CPU (16 Cores @ 1.5GHz), Nvidia RTX A6000 GPU (48G RAM), running Ubuntu 22.04 LTS.
To align with Kaggle’s technical specifications
(
Kaggle 2025b
)
, each run is provisioned with 4 CPU cores, 30 GB of memory, and one GPU.

Containerized Execution and Runtime Measurement

Notebooks are executed non-interactively via a notebook execution engine inside the container, with error-tolerant execution enabled so that exceptions do not immediately abort the run.
Allowing errors ensures we can capture partial progress, logs, and all error locations; some errors (e.g., arise during data visualization) may not affect the final execution outcome and may even be intentionally left unfixed.
We impose a wall-clock cutoff of 600 seconds per notebook, consistent with our data filtering criteria in §
2.1.1
.
The runtime measurement is applied on the notebook’s execution only, excluding the overhead of container initialization, filesystem mounting, and results grading.

Execution Outcome and Grading

Kaggle notebooks are desired to produce a competition “submission” file in CSV format.
The required schema (e.g., column names) is specified by each competition. We treat successful CSV generation as the primary execution artifact and evaluate generated submissions using a grader adapted from MLE-Bench.
Because Kaggle’s full evaluation benchmark is not publicly released for many competitions, the MLE-Bench grader approximates Kaggle evaluation by splitting the original Kaggle training set into training and held-out test sets.
For each notebook, we report three metrics:
(1) output status (whether the notebook has produced a valid CSV artifact),
(2) reproduced score, and
(3) runtime.
Together, these metrics capture whether the notebook runs end-to-end, whether it produces a meaningful and competitive prediction file.

Reproduction aims to replicate the historical performance that each notebook originally achieved.
Because MLE-Bench uses an offline grader (with train/test splits that may differ from Kaggle’s private leaderboard evaluation), reproduced scores may not exactly match the target scores reported on Kaggle even when the pipeline is correct.
We therefore adopt an interpretable criterion: a notebook is
reproducible
if its reproduced score deviation from the target score is within a threshold, and
non-reproducible
otherwise.
Concretely, a notebook is reproducible when the score deviation:

{{\mathtt{\delta s}}}=\frac{\lvert{{\mathtt{s_{r}}}}-{{\mathtt{s_{t}}}}\rvert}{\lvert{{\mathtt{s_{t}}}}\rvert}\leq{{\mathtt{\tau}}},

where
\mathtt{s_{r}}
is the reproduced score,
\mathtt{s_{t}}
is the target score, and
\mathtt{\tau}
is empirically set to 10% in our study.

2.2.
Environment Backporting

Backporting aims to reconstruct the historical software environment that originally executed each notebook on Kaggle.
Since Kaggle’s Docker images older than two years are no longer available for download, we approximate historical environments by downgrading dependencies to versions consistent with each notebook’s submission timestamp.

2.2.1.
Backporting Algorithm

We designed a rule-based procedure for selecting historical versions of Python and third-party libraries based on submission metadata and code characteristics.

Dependency Analysis

To identify the dependencies used by each notebook, we apply an AST-based dependency extraction tool (pigar
(
Damnever 2025
)
) to the notebook code and generate dependency lists with correct PyPI package names.
These dependency lists, together with the submission timestamp, form the inputs to our rule-based backporting procedure.

Inferring Python Version

First, we infer the Python major version (2 vs. 3) and specific release by cross-referencing the notebook’s submission timestamp with the release dates of all historical Python versions.
The code is also analyzed to detect syntax patterns characteristic of Python 2 (for example, bare
print
statements,
xrange
,
raw_input
) or Python 3 (for example,
print()
calls, f-strings,
async
/
await
).
Among the eligible versions released before the submission date, we choose the most recent Python release that predates the submission.
To avoid incompatibilities with operating-system level constraints on particular patch releases (e.g., Python 3.5.4), we use only the latest patch
y
in each 2/3.
x.y
family (for example, mapping 3.9.
z
to 3.9.25), relying on semantic versioning guarantees that patch releases rarely change public APIs.

Selecting Dependency Versions

Given a notebook and its inferred Python version, we select historical versions of all third-party dependencies used by that notebook.
For each imported package, we query the corresponding package index to retrieve the full release history, along with per-release metadata, required Python versions, and yanked-status flags.
We filter out yanked releases and, for each remaining version, record both the release time and the declared Python compatibility.
For a given notebook, we then choose the newest version before the submission timestamp; if no such version exists, we fall back first to the oldest version that is compatible with the inferred Python version and, as a last resort, to the oldest available version.
The resulting per-notebook dependency lists are written in a requirements-style format that constrains each package to be less than or equal to the selected version (e.g.,
package_name<=v_hist
).
Our rule-based selection strategy is designed to be robust, as it systematically respects submission dates, enforces Python-version compatibility,
and promotes the use of shared minimal versions.

Environment Materialization

We materialize the inferred environments based on the baseline Docker container (§
2.1.2
), using
\mathtt{virtualenv}
to install the inferred Python version and the selected dependency versions.
If the backported environment cannot be installed (e.g., due to dependency conflicts or unavailable historical wheels), we mark the notebook as Failed.

3.
MLEModernizer
Technique

Given that environment backporting fails to address the reproducibility gap, and motivated by the rapid evolution of execution environments in MLE, we focus on a solution to
modernize
notebook code with the environment fixed as a constraint.
We design
MLEModernizer
as an LLM-driven agentic framework that iteratively fixes a notebook towards reproducibility.
LLMs have shown promising capabilities for program repair and code migration, but different from prior work, the LLM fixes in
MLEModernizer
need to be performance-aware:
MLEModernizer
targets not only for successful execution, but also for reproducing the originally reported score.
Thus,
MLEModernizer
grounds LLM fixes with rich execution feedback (runtime, error tracebacks, and score deviation) and uses specific prompts (runtime-reduction, error-repair, score-calibration) to guide each LLM fix.
An overview of
MLEModernizer
’s workflow is shown in Figure
4
.

3.1.
Agentic Workflow

Figure 4
.
MLEModernizer
’s workflow.

MLEModernizer
takes as inputs a notebook and a target score
\mathtt{s_{t}}
to be reproduced.
Then,
MLEModernizer
adopts an agentic workflow that iteratively collects execution feedback and applies LLM-driven fixes.

At each iteration,
MLEModernizer
performs the following steps:

(1)

executes the notebook and collects execution feedback, namely the outputs, error tracebacks (if any error occurs), reproduced score
\mathtt{s_{r}}
, and runtime (detailed in §
3.2
);

(2)

analyzes the execution feedback to detect one of the three non-reproducibility issues:

•

if the execution times out, which can be caused by API misuse or not enabling GPU acceleration,
MLEModernizer
first needs to reduce the runtime;

•

if the score deviates and the notebook has errors,
MLEModernizer
attempts to fix the errors as they are likely to be the root causes of non-reproducibility;

•

if the score deviates and the notebook does not have errors, there is a hidden API behavior change and
MLEModernizer
needs to calibrate the score to the target score.

(3)

triggers a targeted LLM fix based on the detected issue (detailed in §
3.3
).

MLEModernizer
terminates when the notebook becomes reproducible (i.e., the score deviation is within the replication threshold
\mathtt{\tau}
= 10%).
We also set a maximum number of iterations
\mathtt{N}
= 16; if the notebook does not become reproducible within the cap, it is assigned a terminal outcome (e.g., Error Non-Reproducible, Error-Free Non-Reproducible, or Failed due to timeout/LLM failure).

3.2.
Execution Feedback Collection

Each notebook is executed inside the containerized environment as described in §
2.1.2
.
We also mount the MLE-Bench competition dataset into the container so notebooks can access inputs and emit the submission CSV to standardized paths.

The executor first checks if the notebook specifies alternative dependency versions (in the form of
\mathtt{!pipinstall}
commands), which will be installed prior to execution.
Then, the notebook is executed in an error-tolerant mode that continues past failing cells; the outputs and all error tracebacks are collected and saved to the notebook file.
If the ML pipeline runs successfully, a submission CSV should be produced.
The executor has a wall-clock time limit of 600 seconds.
The grader, which is adapted from MLE-Bench
(
Chan et al. 2024
)
, grades the submission CSV to obtain the reproduced score
\mathtt{s_{r}}
.

3.3.
LLM Fixing

The input to LLM is a structured prompt that includes a context-specific part and a shared part.
The context-specific part depends on the detected non-reproducibility issue, and instructs the LLM to follow certain requirements when performing the fix.
There are three types of fixes: Runtime-Reduction when the execution times out, Error-Repair when the notebook has errors, and Score-Calibration when the notebook does not have errors.

The shared part contains the following information:

•

Kaggle task description
: describing the competition’s task, evaluation metric, and dataset schema.

•

Execution environment
: describing the Python version and dependency libraries’ versions.

•

I/O contract
: specifying the paths for input data (
\mathtt{/kaggle/input/}
) and the expected submission CSV location (
\mathtt{/kaggle/working/}
).

•

Scores
: target
\mathtt{s_{t}}
, current
\mathtt{s_{r}}
, and the metric directionality (higher/lower is better).

•

Notebook
: the current notebook rendered in a cell-delimited format; when there are errors, the traceback is appended to the corresponding cell.

The LLM is also instructed to return a response in a fixed
plan
\rightarrow
patch
format:
(1) a short plan that enumerates the intended changes and their expected effect on the observed failure mode, followed by
(2) a single markdown code block containing the full updated notebook in the same cell-delimited representation.

MLEModernizer
parses this output deterministically and applies the patch to the notebook for the next iteration.
This protocol both enforces a concrete, executable patch and preserves sufficient structure for automated application and auditing.

Running Example

4.
Evaluation

Subjects

MLEModernizer
focuses on non-reproducible notebooks: these notebooks either fail to produce a valid submission artifact or produce a submission whose score falls outside the replication threshold (
10\%
).
We exclude reproducible notebooks because they already run and reproduce under the baseline environment and offer little headroom for improvement.
We also exclude notebooks that hard-fail due to timeouts or pathological resource usage, as such cases are dominated by system-level constraints rather than code-level modernization.

From the 7,874 non-reproducible notebooks identified in the baseline (§
2.1
), we further filter candidates based on prompt length.
For each notebook,
MLEModernizer
constructs prompts that include the source code (organized into cells) and, when applicable, error tracebacks from previous executions. To avoid exceeding the context window of the LLM and to prevent repeated failures due to overlong prompts, we empirically select a token cutoff based on the joint distribution of tokenized source and error text.
Specifically, we tokenize all notebooks and associated error messages using an OpenAI model-compatible tokenizer
(
Jain 2025
)
, compute the 95th percentile of the resulting token counts, and obtain a cutoff of 13,485 tokens.
Notebooks whose combined source and error text exceed this cutoff are excluded from the modernization pool.
The final subjects set consists of 7,402 notebooks (out of 7,874 non-reproducible notebooks); we remove 472 extremely large notebooks to keep LLM calls within context limits and avoid disproportionate allocation of compute budget.

We use the same software and hardware setup as the motivation study (§

).
We use OpenAI’s GPT-5.2 (the 2025-12-11 version) as the LLM in
MLEModernizer
.

4.5.
RQ5: Error Types

We analyze error types in each fix (including Error Reproducible notebooks) following the approach from prior work
(
Wang et al. 2025b
)
.
In Python,
NameError
is raised when a name is not defined (e.g.,
print(x)
with
x
undefined or a missing import);
AttributeError
when an object has no requested attribute (e.g.,
obj.foo
when
foo
does not exist);
ValueError
when an operation receives a valid type but invalid value (e.g.,
int(‘hello’)
);
KeyError
when a dictionary key is missing (e.g.,
d[‘key’]
);
TypeError
when an operation is applied to an inappropriate type (e.g.,
len(5)
).
Such errors often arise from API or dependency changes, incorrect variable scope, or data shape mismatches after modernization.

We find that
MLEModernizer
is highly effective at fixing
NameError
(undefined name or missing import; baseline 51,772, reduced to 405 after 16 fixes) and substantially reduces
KeyError
and
ValueError
;
AttributeError
(missing or invalid attribute on an object) is the most stubborn—it remains dominant among persistent errors in both Error Reproducible and Error Non-Reproducible notebooks after modernization.
Figure

shows how error counts by type evolve as #fix increases.
At baseline (#fix = 0), the top five types are
NameError
(51,772),
AttributeError
(19,923),
ValueError
(9,316),
KeyError
(2,773),
TypeError
(2,407), and Others (6,595).
Total errors drop sharply in the first few fixes (from
>
80K to
\sim

\sim

NameError
is largely eliminated by early fixes;
AttributeError
decreases in count but becomes the dominant
remaining
type at higher #fix, so
MLEModernizer
resolves
NameErrors
effectively but
AttributeErrors
are harder to fix.
We argue that missing-import or undefined-name issues are amenable to automated repair; attribute and API-usage issues often require deeper or multi-step fixes.

To this, we further investigate the root causes. We classify persistent errors in Error Reproducible and Error Non-Reproducible notebooks:
API misuse
(incorrect use of library or object API),
implementation error
(logic or type/data handling bugs),
data confusion
(wrong data shape or key),
NB specific
(notebook-specific issues such as variable scope or execution order),
environment setting
(paths, modules, I/O), and
library cause
(library-internal or third-party failures).
In Error Reproducible notebooks (5,901 crashes), overall root causes are dominated by API misuse (5,378, 91%), followed by implementation error (221), data confusion (126), NB specific (117), environment setting (31), and library cause (28).
For the top error type in Error Reproducible,
AttributeError
(5,381), the vast majority are attributed to API misuse (5,378); only three are implementation error.
In Error Non-Reproducible notebooks (2,147 crashes), overall root causes are API misuse (1,535, 71%), NB specific (422, 20%), implementation error (87), data confusion (41), environment setting (31), and library cause (31).
For
AttributeError
in Error Non-Reproducible (1,538), again almost all are API misuse (1,534); four are implementation error.
The persistent

in Error Non-Reproducible (405) are predominantly NB specific (404), i.e., notebook scope or execution-order issues that block reproducibility.

Summary
:

MLEModernizer
sharply reduces total errors (from
>

and
KeyError/ValueError
.

is the most stubborn type: it remains dominant among persistent errors,
and crash-report root-cause analysis shows that
AttributeError
is overwhelmingly
API misuse
(incorrect use of library or object API).

persists mainly in Error Non-Reproducible notebooks (19%) and is predominantly specific to notebook scope. Resolving
NameErrors
is often required to achieve reproducibility.

Discussions

5.1.
Ablation Study:
MLEModernizer
with Cell-Level Error-Repair

MLEModernizer
performs file-level error-repair, i.e., attempting to fix all errors in the notebook at once.
In this section, we perform an ablation study for an alternative strategy: cell-level error-repair, i.e., attempting to fix one error at a time.
Specifically, in the error-repair prompt, we only provide the notebook cells up to the first cell with error, plus the error’s traceback and the next cell, and instruct the LLM to focus on fixing the error.
Since this approach only diverges from the default
MLEModernizer
when errors persist, we perform the ablation study on the 6,583 Error Non-Reproducible notebooks in the baseline environment.

5.2.
Limitations

Offline Grading and Reproducibility Criteria

Since most Kaggle competitions do not publicly release their test sets, we use the offline-grading setup from MLE-Bench
(
Chan et al. 2024
)
to approximate the Kaggle evaluation.
This leads to a mismatch between the training/test sets.
To mitigate this, we operationalize reproducibility as the score deviation being within a threshold.
Future work can explore other sources of notebooks where the test set is publicly available to enable a more strict reproducibility criterion.

LLM Generalization

MLEModernizer
is designed to be compatible with any LLM with coding and reasoning capabilities.
We plan to expand the evaluation to other backend LLMs to understand the generalization of
MLEModernizer
’s agentic framework.

Flexible Error-Repair Approach

Some errors do not need to be fixed in order for notebooks to generate valid and reproducible predictions; this can be observed from our experimental results where around 1/4 of the reproducible notebooks are not error-free.
In future work, we plan to explore a more flexible error-repair approach that first classifies whether an error may impact the notebook’s functionality, and only focuses on the critical errors.

6.
Related Work

Reproducibility of ML research and notebooks

Pimentel et al. 2019
studied the reproducibility of Jupyter notebooks on GitHub; they extended this line of work and introduced Julynter
(
Pimentel et al. 2021
)
for identifying potential reproducibility issues in Jupyter notebooks.

Pineau et al. 2021
analyzed reproducibility in ML research papers through the NeurIPS reproducibility program, and
Gundersen and Kjensmo 2018
;
Henderson et al. 2018
studied reproducibility challenges in AI and deep RL.

Wang et al. 2025b
characterized notebook crash types by analyzing error outputs from notebooks mined from GitHub and Kaggle, without re-executing the notebooks.
In contrast, our study focused on large-scale re-execution in a containerized environment and evaluated not only execution success but also score deviation against the reported target.

Benchmarks and datasets for MLE notebooks

Yin et al. 2023
built ARCADE, a benchmark for natural-language-to-code generation in data science notebooks, and introduced PACH-INCO, a notebook-centric code LM that reasons over cells and execution context.

Ghahfarokhi et al. 2024
released DistilKaggle, a distilled dataset of Kaggle notebooks and code-quality signals, and
Chan et al. 2024
introduced MLE-Bench, an offline benchmark derived from Kaggle competitions for evaluating ML engineering agents.

Jin et al. 2025
studied learning to edit ML pipeline code in notebooks using LLMs and found low accuracy even after fine-tuning.
Our work leveraged MLE-Bench for large-scale, offline grading and studied how to modernize real-world Kaggle notebooks to restore reproducibility under contemporary environments.

Dilhara et al. 2023
mined and transplanted evolution patterns in Python ML systems, complementing our code-modernization perspective.

LLM-based program repair and code evolution

Bouzenia et al. 2025
presented RepairAgent, an autonomous LLM-based agent for program repair that invokes tools and validation.

Xie et al. 2025
proposed PReMM, an LLM-based repair technique for multi-method bugs, and
Zhang et al. 2024
;
Deligiannis et al. 2025
studied LLM-driven repair for Python and Rust, respectively.

Wang et al. 2025a
analyzed deprecated API usage in LLM-based code completion and proposed lightweight mitigation strategies.
Compared with prior program-repair work, our setting emphasized notebook-specific execution context (cells and state), a fixed modern environment, and
score-aware
repair: a patch was only acceptable if it restored end-to-end execution and brought the reproduced score within the replication band of the reported target score.

7.
Conclusions

We investigate the reproducibility challenges of MLE notebooks.
In a large-scale study of 12,720 Kaggle notebooks, only 35.4% are reproducible, and environment backporting hurts instead of helping.
We then develop
MLEModernizer
, an LLM-driven agentic framework that modernizes notebooks toward reproducibility.

MLEModernizer
iteratively executes notebooks and applies targeted fixes in three types: error-repair, runtime-reduction, and score-calibration.
Our evaluation shows that
MLEModernizer
successfully modernizes 74.2% of the notebooks that are non-reproducible at the baseline environment.
These results suggest that code modernization is a viable path to restoring reproducibility for legacy MLE notebooks, enabling more reliable validation and reuse of ML pipelines in a rapidly evolving hardware and software environment.
