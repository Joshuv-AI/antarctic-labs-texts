Abstract
. In the past few years LLMs have emerged as a tool that can aid programmers by taking natural language descriptions and generating code based on it. However, LLMs often generate incorrect code that users need to fix and the literature suggests users often struggle to detect these errors. In this work we seek to offer formal guarantees of correctness to LLM generated code; such guarantees could improve the experience of using AI Code Assistants and potentially enable natural language programming for users with little or no programming knowledge. To address this challenge we propose to incorporate a formal query language that can represent a user’s intent in a formally defined but natural language-like manner that a user can confirm matches their intent. Then, using such a query we propose to verify LLM generated code to ensure it matches the user’s intent. We implement these ideas in our system, Astrogator, for the Ansible programming language which includes such a formal query language, a calculus for representing the behavior of Ansible programs, and a symbolic interpreter which is used for the verification. On a benchmark suite of 21 code-generation tasks, our verifier is able to verify correct code in 83% of cases and identify incorrect code in 92%.



1.
Introduction

In recent years, Large Language Models (LLMs) have proven to be surprisingly successful at generating code from natural language prompts
(
Rozière et al. 2023
;
Guo et al. 2024
;
Lozhkov et al. 2024
)
.
The ability to program using natural language, often called
natural language programming
, has been a long sought after dream of the programming languages community
(
Sammet 1966
)
, though has also received some criticism
(
Dijkstra 1979
)
.
If natural language programming was achieved it would enable programming a computer without needing to learn a programming language and could therefore help democratize computer programming.
The ability to use LLMs for this purpose has led some to speculate that prompting LLMs to generate code will fully replace traditional programming, but as has been pointed out throughout the history of the search for natural language programming, programming in natural language has many challenges and using LLMs for this purpose has even more
(
Yellin 2023
)
.
For example, LLMs are known to suffer from hallucinations in code generation, including through generating code that uses non-existent APIs and libraries
(
Zhang et al. 2025b
)
and LLMs have also been shown to struggle with many practical programming tasks that rely on complex functions
(
Zhuo et al. 2025
;
Nguyen et al. 2025
)
and involve reasoning about large codebases
(
Jimenez et al. 2024
)
.

Using an LLM as a coding assistants seems to offer potential benefits to programmers
(
Ziegler et al. 2022
;
Liang et al. 2024
;
Barke et al. 2023
)
, including novice programmers
(
Kazemitabaar et al. 2023
)
.
However, such use is still a significant gap from true natural language programming, as the LLM only generates code fragments that often require modifications and potentially incorporation by the user
(
Sahoo et al. 2024
;
Vaithilingam et al. 2022
)
.
In the natural language programming setting described above, however, there is no user skilled in that language who can validate the generated code meaning that errors in generated code are unlikely to be caught.
Even in the AI Code Assistant setting the literature suggests that users often have a hard time checking LLM generated code
(
Liang et al. 2024
)
and that use of AI Coding Assistants can be associated with less secure code
(
Perry et al. 2023
)
, suggesting users struggle to check such aspects of generated code.
It is therefore essential to Natural Language Programming setting, and would greatly benefit the AI Code Assistant setting, to be able to provide a guarantee that the generated code is correct.

In our current work we are particularly interested in providing such guarantees for generating code in Domain-Specific Languages (DSLs).
The problem of correctness of LLM generated code is exacerbated in the context of DSLs because due to their often niche use the amount of available data on which models train is significantly lower than for general-purpose languages and due to the smaller user-bases there is a lack of tools for developers and research in DSL code generation
(
Gu et al. 2025
)
.
Additionally, we believe that the challenge of providing guarantees that generated code is correct may be easier in DSLs because we can use specialized domain knowledge not available in general-purpose programming languages (GPLs).
Many DSLs are also not Turing Complete, which can make techniques from program verification more tractable.
In this work, we focus on the Ansible programming language, which is used for IT automation; Ansible is an interesting example for us as it has a relatively large user-base and is important enough that it was acquired by Red Hat in 2015.
We provide additional background on Ansible in Section
2.1
.

Our broad, long-term goal – which may not be fully realizable as a formal proof – is to provide a high degree of confidence that LLM generated code for a given natural language description
has the user’s desired functionality
.
This goal is a step towards true natural language programming, in which we would like to offer complete formal guarantees of correctness, as well as in the AI Code Assistant setting, where this goal could significantly improve the correctness of LLM generated code and help avoid undetected errors.
Traditional approaches to offering formal guarantees of correctness, such as program synthesis and verification, are not immediately suitable to this setting because they rely on a formal specification of the problem, not a natural language description which, in general, may be ambiguous, vague, or incomplete.

In this paper, we aim to provide formal correctness guarantees that brings us close to this longer-term goal.
In particular, we propose the incorporation of a high-level and domain-specific
formal query language
which is designed to be close to the syntax of natural language but is precisely and formally defined.
Moreover, we aim to design this formal query language to be at a similar level of abstraction as we expect the user’s natural language description to be – using similar concepts and actions – so that a user can easily understand this formal query and ensure it reflects their intent.
We then propose to use this formal query to verify generated programs which enables us to ensure they match the user’s intent.
Even in the context of DSLs this formal verification is very difficult; we propose a particular solution for Ansible using symbolic interpretation of a novel calculus, but this approach is unlikely to work for all languages.

Our key contributions in this work are as follows:

(1)

Formalize our notion of natural language programming.

(2)

Propose the idea of an (artificially introduced) formal query language that captures the user’s intent in precise but high-level and user-accessible terms, that can be validated manually by the user.

(3)

Propose the use of this formal query to verify generated programs and identify ambiguity in the user’s description which they must resolve.

(4)

Present Astrogator, an implementation of such a formal query language and verifier for the Ansible programming language.

(5)

An evaluation of Astrogator for a benchmark suite of 21 LLM code-generation tasks for Ansible programs from natural language descriptions, showing that it is able to formally prove correctness of generated code in 83% of cases, and to precisely identify incorrect LLM generated code in 92% of cases.

In the rest of this paper, we present background on Ansible and Ansible code generation (Section
2
), formalize the program of natural language programming as we envision it (Section
3
), describe our approach to ensuring LLM generated code is correct (Section
4
), describe Astrogator (Section
5
), evaluate Astrogator and its ability to identify correct and incorrect code (Section
6
), discuss some limitations of our current implementation and the generalizability of our approach (Section
7
), discuss related work (Section
8
), and finally conclude (Section
9
).

2.2.
Ansible Code-Generation

While much of the research and development in LLM-based code generation has focused on well known general-purpose programming languages, Ansible has received some attention in the past few years including the development of Red Hat Ansible Lightspeed
(
Red Hat 2025a
)
, a suite of AI-based tools for working with Ansible.
Like other LLM-based code generation work, in Ansible code generation the goal is to take a natural language description and generate an Ansible code that performs the described tasks.
Prior work has made use of the
name
fields found in Ansible as a source of natural language descriptions, in order to construct large data sets for training and evaluation.
In this work we take a different approach as we have found that name fields, in practice, are often very terse notes, much more like comments, than full natural language descriptions necessary to properly describe the desired behavior.

In addition, in prior literature, there has been limited discussion of the correctness of the LLM-generated Ansible.
Works on training LLMs for this task
(
Pujar et al. 2023
;
Darnell et al. 2024
)
have focused their evaluations on comparisons against reference codes using metrics like BLEU
(
Papineni et al. 2002
)
, which compares the generated and reference codes for matching words or tokens which does not necessarily account for different ways to accomplish the same programming task, and CodeBERTScore
(
Zhou et al. 2023
)
, which attempts to address this problem by comparing the embeddings of the generated and reference code using an embedding trained to embed programs based on semantic similarity however CodeBERTScore is not trained on Ansible and the unique ways that Ansible programs may or may not be similar.
There has also been a study evaluating the use of LLM-generated suggestions from Ansible Lightspeed’s VS code plugin
(
Sahoo et al. 2024
)
.
While also an imperfect metric for code correctness, that work found that only 66% of code suggestions sent to users were initially accepted and of those only 60% were kept by the user unchanged, with another 21% requiring some modifications by the user.
This means that only 40% of the generated code was ultimately used, as generated, by the user.
While in the context of a coding assistant this may still be useful to users who can fix issues, this poses a serious serious challenge in the natural language programming setting.

While a detailed analytical study is beyond the scope of this work, from errors we observed in our Evaluation (Section
6
) we observe that there is a broad range of errors LLMs make in generating Ansible code.
One issue we observe in several cases are subtly incorrect package installations.
For example, consider installing the Python package numpy system-wide: on Red Hat Enterprise Linux (RHEL) this can be done via the Python package manager pip or the system package manager dnf with any of the package names numpy, python-numpy, or python3-numpy; on the other hand, on Debian it must be installed via the system package manager apt using the package name python3-numpy.
In LLM-generated code for this task, we have seen many programs that attempt to use pip on all systems, an incorrect package name on Debian, or to use apt on all systems including RHEL.
In all these cases the program fails to install the desired package.
This sort of error is quite subtle, for a user to catch such errors they need not only sufficient knowledge of Ansible to understand the generated code but also expertise in the package managers of these operating systems to know, for example, the correct package names or the fact that on Debian Python packages cannot be installed system-wide via pip.
Another example where determining whether a piece of code is correct came from a task of permanently setting an environment variable to a certain value.
The common way to do this is to add that variable and value to the
/etc/environment
file which has lines of the form
key=value
which are loaded as environment variables.
Ansible has a module specifically for adding and replacing lines in files that can be used for this task.
When replacing a line you specify expression to search for and then the a matching that regular expression will be replaced and if there is no match a new line will just be added.
This is the source of a subtle bug in some generated code; the correct regular expression is something like
^key=
because this will match any line that sets the value of the key we want to modify, however in some generated code the regular expression was instead
^key
which will also match any line with a variable which begins with
key
, such as
keys
and therefore this error can result in unintentionally replacing other environment variables.
As a final example, in a task to lock a particular user’s password, one LLM-generated solution was to directly modify the
/etc/shadow
file where Linux stores hashed passwords; technically the solution does work however it is almost certainly inadvisable since a mistake could have serious system implications and this LLM-generated code sets certain properties about when the password is required to be reset that were not part of the task.
While not a comprehensive or analytic study of the kinds of errors in LLM-generated Ansible playbooks, these observed errors give us guidance on the kinds of errors that need to detect to ensure the correctness of LLM-generated code.

3.
Problem Statement

As described earlier, a goal of our work is to develop a system which can take a natural language description and produce a program guaranteed to be correct, without requiring any knowledge of the programming language being generated from the user.
Although this assumption is not needed when programmers use LLMs as aid, modern AI agents are increasingly generating code to carry out actions for non-technical users who have little or no expertise in programming.
One way that such users can gain confidence in the correctness of the generated code is through the tools providing explanations on the steps taken.
To address this goal we need to first understand what it means for a program to be
correct
.
Informally, what we mean is that the program acts as the user intended it to, but we cannot provide any formal guarantee of this correctness if the user’s intention is only in their mind and expressed, likely imperfectly, in natural language.
As a concrete example if this Ansible, suppose a user provides the description “create a file at /some/path”.
This description is missing significant details like the contents, owner, group, mode, and so on.
In the user’s mind they likely know some of these details and others are likely implicit in the remote machine they want to program, such as what users exist that can own it.

To formalize this intuition, let us suppose that we are interested in generating a program in some language
\mathcal{T}
, Ansible in our case.
The user has some
intent
that they are hoping to generate a program in
\mathcal{T}
to satisfy; this intent is not necessarily a single program as there are generally many ways to achieve the same thing and there may be behaviors that are not necessary but a user finds acceptable.
For example, if a user wants to clone a git repository if git is already installed it is not necessary to install it again but it does not hurt either.
Therefore, we can describe the user’s intent as some set
\mathscr{U}\subset\mathcal{T}
; note importantly that we have
no way
of directly testing membership in this set, since it is only known by the user who does not know the language
\mathcal{T}
and so cannot actually verify that a particular program is in
\mathscr{U}
.
In fact
\mathscr{U}
need not be a decidable or even recursively enumerable language!
We can now formalize our informal notion of correctness: a program
p\in\mathcal{T}
is
correct
if and only if
p\in\mathscr{U}
.

The user then writes some natural language description
\mathscr{d}
to express their intent.
At this point, we do not have any way to computationally check whether a candidate program
p
is correct or not, and the only indication of the user’s intent is
\mathscr{d}
which does not have a formal meaning we can use.
To fix this, we need to introduce a bridge between the user’s intent, as expressed in
\mathscr{d}
, and some formal description that allows us to test correctness.
To do this, what we need is some formal specification.
For this, suppose that we have some formal specification language
\mathcal{S}
(in our setting this is the Ansible Formal Query Language discussed in Section
5.1
) and some semantics function
\left\llbracket\cdot\right\rrbracket:\mathcal{S}\to\mathcal{P}(\mathcal{T})
, which defines the set of programs that satisfy a particular specification.
We also assume that given a program
p\in\mathcal{T}
and specification
s\in\mathcal{S}
we can determine whether
p\in\left\llbracket s\right\rrbracket
or not.
Finally, suppose that we have an oracle that can be used to convert the natural language description
\mathscr{d}
into a formal specification
s
that best matches it.
Assuming the description
\mathscr{d}
is a good description of the user’s intent, we believe that with our formal specification
s
we should have that
\left\llbracket s\right\rrbracket\supseteq\mathscr{U}
.
These sets are not necessarily equal since some of the user’s intent may not be expressed in their description, as mentioned above.
Because of this, we expect that
s
may be an under-specification of the user’s intent and therefore there may be many programs that satisfy it.

Now, using any code generation, we can generate candidate programs
p
until we find one that satisfies the specification,
p\in\left\llbracket s\right\rrbracket
.
With this program, we are now close to a correct program but we need
p\in\mathscr{U}
, not just
p\in\left\llbracket s\right\rrbracket\supseteq\mathscr{U}
.
With the information at hand, the natural language description
\mathscr{d}
and the formal specification
s
, there is no way to check this especially since the difference between the user’s intent and the specification is likely not described by
\mathscr{d}
as otherwise it should be in
s
.
What we have is
s
which we have assumed is the correct formalization of a good description, and so we expect that
s
is close to the user’s intent and so if
p\not\in\mathscr{U}
this should be because of how
p
fills in under-specified details.
Therefore, what we need to do is identify how
p
differs from some kind of
unrefined
version of
s
which does not make any particular choices for the under-specified details.
To do this, suppose we are able to compute an operation
p\setminus s
which produces some high-level description of these choices.
Exactly what this operation and description looks like will vary depending on the target language
\mathcal{T}
, we discuss our approach for Ansible in Section
5.2.3
.
The result must be high-level so that it can be understood by the user and they can confirm whether or not the choices matches their intent.
By ensuring that the program
p\in\left\llbracket s\right\rrbracket
we reduce the space of possible issues that the user must consider, but ultimately the task of determining whether
p\in\mathscr{U}
is one that only the user can solve.
In the case of Ansible, these differences can include details like assuming that an additional program is installed, the program installing an additional program, a group or user needing to exist, or setting the owner of a particular file if it was not specified in
\mathscr{d}
.
With this theoretical basis of our approach, we now describe the design of such a system.

4.
Approach

With an understanding of the problem we are seeking to solve, we now turn to our proposed solution.
We propose two key components that are the focus of this work: the
Formal Query Language
which is our formal specification language
\mathcal{S}
which expresses the user’s intent in a formal manner and the
Verifier
which given a program
p
and formal query
s
determines whether
p
satisfies
s
(
p\in\left\llbracket s\right\rrbracket
).
We envision that, in the future, these ideas could be incorporated into a full end-to-end system, like shown in Figure
2
, that would guarantee the correctness of generated code as described in Section
3
.

From this figure we can identify a key design challenge for the Formal Query Language: it must be understandable to the user because they must check that it matches their intention because there is no other way to do so.
We discuss the design considerations of the formal query language, which is a significant challenge, in Section
4.1
.
While we believe converting the natural language description into the formal query (the “Formalize” in the diagram) can be achieved using LLMs an LLM generated query cannot be trusted because a mistake in it means we guaranteeing correctness with regards to an incorrect specification.
We do not address the problem of generating formal queries in this paper, but we believe it is suitable for LLMs, even though they are not trained on the formal query language, because in-context learning, where a few examples are provided to an LLM in the prompt, has shown efficacy at getting LLMs to generate code in a custom language or domain-specific language from few examples
(
Joel et al. 2024
)
and LLMs have been used in other settings to formalize natural language descriptions into postconditions
(
Endres et al. 2024
)
.
The generation of the formal query is also not too dissimilar to the explanations of their work that LLMs often give.

Once the user is satisfied with a formal query, we can use it and their natural language description to generate programs (the “Code Generator” in Figure
2
).
Note that even though the formal query is provided as input, the code generated by this step does not need to satisfy it.
In fact, in this work we do not use the formal query in code generation and we simply use some LLM as our code generator using the natural language description.
In future work we hope to explore whether providing the formal query could help avoid clarify the user’s intent.
We also intent to explore how to best use feedback, in the case that a generated program did not satisfy the specification, to improve the program perhaps using a mix of LLM code generation and program synthesis techniques.

Finally, a generated program is checked against the formal specification by the “Verifier”.
We discuss the role of the verifier in detail in Section
4.2
.
In Figure
2
we show that the user can be asked to check the choices a program made to address the under-specification of the query (
p\setminus s
) with the “Assumptions Check”.
In this work, we are able to produce the assumptions needed, in particular we can calculate
p\setminus s
, but in our evaluation we operate in a mode where so long as
p\in\left\llbracket s\right\rrbracket
we accept the program.

4.1.
Design Considerations for a Formal Query Language

As described earlier, to be able to provide any formal guarantee of correctness we need a formal specification of what the program should do.
We do not need this formal specification to be a complete specification of the program, indeed program synthesis is often done on incomplete specifications, but do need this specification to avoid the ambiguities that are present in the natural language description.
As a concrete example, consider the following description for a desired Ansible program: “copy a file from
/path/a
to
/path/b
.”
In the context of Ansible (unlike, say Bash or C), this could mean duplicating the file on the remote system, copying file
/path/a
from
the Ansible controller
to
/path/b

on the remote system
, or from the remote system to the controller!
Any of these interpretations is conceivably correct, i.e., the query is underspecified.
While we intended this example as the first interpretation,
we find that all six LLMs we prompted
only
generated code to copy a file from the controller to the remote system, potentially because this is the default mode implemented in the
copy
module.

This example raises a key design question:

(Q1)

How do we ensure the formal specification matches the user’s intent?

We have already stated that our approach is to use a high-level language and have the user check that it matches their intent, but we take a moment to explain why other kinds of specifications would not work.
A common form of specification from the synthesis literature are input-output examples, or more generally tests, as these are often simple for users to specify
(
Gulwani 2010
)
.
However, the formal guarantees of correctness in this setting is only that the program satisfies the provided tests, meaning that the correctness of the generated program is highly dependent on the test cases provided.
In the context of testing system configuration tasks, like in Ansible, identifying how to test something can be a challenge itself, for example it seem that running the command
import numpy
in Python would test if the numpy package is installed, but this command can succeed simply because a
numpy.py
file exists in the current directory.
Even ignoring the additional challenges of testing system configuration tasks, in general good test cases can be complicated and there it is not apparent how we would address (Q1).

This leaves us with specifications in a formal language, but what exactly should this look like?
Our answer to (Q1) is that the user must check the formal specification to ensure it matches their intent; there is no other solution because only they know their intent and the only other piece of information we have is the natural language description which has no formal semantics.
To be clear, this is not a design choice but rather a property of the problem we are attempting to solve: we need a specification that matches the user’s intent and so the user is the only one who can ensure that.
Since the user is not familiar with any programming language, the formal specification must be as close to natural language as possible so that they can simply read it.
This means that our formal specification must be high-level and appear natural language-like; we call such a language a
Formal Query Language
and a specification in this language a
Formal Query.

With that established, we identify a second key design question:

(Q2)

How do we ensure the user does not incorrectly believe a query matches their intent?

For example, as discussed previously, on Debian the package name for numpy is
python3-numpy
, but a user may not know this.
The solution is that the formal query language must preserve some high-level concepts, for example rather than using package names in the formal query language we use
package descriptions
such as “numpy” or “apache server” and use a trustworthy knowledge base which provides the correct package names (including handling OS-specific package names) and similar facts.
This need for high-level concepts and a knowledge base is part of why we believe our approach works best for Domain-Specific Languages; the domain
of the language provides the high-level concepts that are needed and provides the information needed to construct the knowledge base.
We discuss how to use these design principles to build a formal query language and accompanying knowledge base in Section
5.1
.

4.2.
Program Verifier

Along with the Formal Query Language, the Program Verifier is the other key component to our approach.
The exact details of the Verifier will vary depending on the target programming languages and the design of the formal query language, but the role of the Verifier is ultimately to take a generated program and a formal query and determine whether or not the program matches the
user’s intent
.
This is the big challenge for the verifier, because as discussed already we do not have a way to directly test this, but must instead use the formal query and ask questions of the user when necessary to determine if the program is actually correct.
As described earlier, we can use the formal query to detect certain errors (such as installing the wrong package name or using the wrong package manager) and to ensure the program matches the broad behavior described by the query.
The piece that is left, though, is to deal with the under-specified portions of the query.
Because the nature of the Verifier will vary significantly based on the target language and formal query language, how this under-specification is handled is the key piece we will discuss; a more detailed discussion of our verifier for Ansible is provided in Section
5.2
.

We described before an example of cloning a git repository; in our experiments we find that for this task LLM generated programs will sometimes simply invoke Ansible’s git module and at other times it will first install git on the remote system and then use the git module.
Both of these are reasonable programs, especially since the git module fails if git is not installed.
If the user’s intent is to run this program on a machine with git installed then would be happy to get the first version of this program and most-likely alright with the second, unless they do not want to or cannot grant sudo access to Ansible.
On the other hand, if the user’s target does not have git installed, they need the second version.
While an easy solution is to require the formal query to include a full description of what the user wants, so they would have to specify to install git, this violates design question (Q2) because it forces the query to address assumptions that generated programs may make.
This would require the user to realize that the generated code will rely on git being installed if they do not specify to install it.
Similarly, modules differ on whether they can create intermediate directories and this approach would sometimes require the user to know they must specify that intermediate directories need to be created.
This requirement would increase the chance the user accepts a query that does not match their intent.

Since formal queries are under-specifications, the verifier must provide space for generated code to perform additional actions not described, such as creating intermediate directories and installing programs, and handle the possibility that they rely on assumptions not implied by the query, such as requiring a program to already be installed.
To then ensure that a particular program satisfies the user’s intent we must check whether these additions match the user’s intent.
How we identify these assumptions and actions is again very specific to the target language and formal query language; our particular approach is described in Section
5.2.3
.

5.
Formal Query Language and Verification of LLM-Generated Code for Ansible

We now describe our implementation of this design, called Astrogator, for Ansible.
In Astrogator we have developed a formal query language and program verifier which together can be used (as shown in the Evaluation in Section
6

We describe the design of our Formal Query Language in Section
5.1

We then discuss the program verifier, which is built on a calculus we call the

Finally, we explain how formal language queries and Ansible programs are compiled into this calculus for verification (Sections

5.1.
Ansible Formal Query Language Design

As discussed in Section
4.1
, the natural language query from a user is translated into a formal query in the Formal Query Language in order to represent the precise meaning of the program to be generated, and which can be understood and accepted or rejected by the user.
We identified two key questions we must consider in designing our Formal Query Language.
Our answers to these are:

(A1)

The formal query language should be sufficiently high-level that a user can easily understand whether a query matches their intent or not.

(A2)

The differences between the natural language description and formal query should not rely on any specialized knowledge (such as package names or assumptions made by Ansible modules).

As discussed earlier, these properties ensure that the user can verify that the query is correct and that there is not room for error to be introduced in this process that goes undetected by the user.

5.2.
State Calculus and Interpreter

In order to verify correctness of LLM generated Ansible, we need a way to compare the behavior of the program and expected behavior defined by the query.
To achieve this, we have developed the
State Calculus
which provides a clean mechanism to describe the semantics of Ansible programs (Section
5.2.1
).
Given a program and query expressed in the State Calculus (see Sections
5.3
and
5.4
for details) we then make use of a symbolic interpreter to identify their behaviors (Section
5.2.2
).
Finally, using the results of the interpreter we compare the behaviors of the program and the formal query to determine whether the program satisfies the query (Section
5.2.3
).

5.2.1.
State Calculus

Programs in languages like Ansible and Bash are executed mostly for side-effects in the form of changes to system states; these programs may include some amount of computation but generally the computation is relatively simple and the core actions are these side-effects.
We can model such programs as executing on a system with some initial configuration (state) and having the ability to read information from the current state (such as whether a file exists) and make modifications to it, so that when the program ends we have arrived at some new state.
This observation gives rise to our
State Calculus
, which is a simple calculus designed to model programs that operate in this manner.

States

We take a generic approach in defining system states which is applicable to Ansible and similar languages and which we believe could be applicable to other domains as well.
We give a formal definition of states, denoted by
\sigma

Formally, states are a pair of functions, but we can think of it as a set of two kinds of values: attributes and elements.
In the state, attributes, described by
attribute labels
from some set
\mathcal{A}

\nu

For example, we might have an attribute os whose value describes the operating system we are running on or an attribute file_mode describing the file permissions of a certain file.
Elements are used to model the existence or non-existence of certain objects in the state, such as files or users.
An element is specified as an
element label
from
\mathcal{E}
and a value
\nu

\mathrm{file}\in\mathcal{E}

\mathrm{file}(\texttt{/etc/passwd})
would refer to the
/etc/passwd

Whereas attribute labels identify a piece of information, an element label describes a class of objects and when applied to a value a particular object.
In the state, elements map to either a
nested state

\sigma

\bullet

This nested state enables us to apply attributes onto an element, so the
\mathrm{file}(\texttt{/etc/passwd})

As an example, if we have

5.2.2.
Symbolic Interpreter

To understand the behavior of programs in the State Calculus, we develop a symbolic interpreter in which the state is treated as symbolic.
The result of the interpreter is a set of initial-final state pairs that reflect the behavior of the program under different initial states.
To do this, the interpreter tracks both an initial state and the cumulative modifications made to the state. We will often imprecisely refer to the cumulative modifications as the “current state.”
When operations read from the state we check whether the result of the read can be determined from the modifications or relies on the initial state.
For both the initial and cumulative states we use the abstract state definition shown in Figure
4(b)
; the difference from concrete states is that the attribute and element maps are partial functions.
This allows us to represent the generally infinite space of initial states compactly since we only need to represent the parts of the state that are relevant to the program.
We highlight a few details of this interpreter that relate to the state and symbolic values.
As discussed earlier, there are three constructs in the calculus that deal with the state:
get
,
add
, and
exists
.
Of those, the
add
construct for updating the state is the simplest since the addition to the state is simply recorded in the current state.
The other two constructs require a little more care, since we are dealing with partial states.

For
get
, which reads an attribute value, we attempt to find the attribute first in the current state but we may not find a value for one or two reasons: the attribute is not bound (since the state is partial) or some element the attribute is on is not bound.
In either of these cases, we then look up the attribute in the initial state, but we may not find it there either.
If in searching the initial state we simply found that the attribute was not bound, then we introduce a new symbolic value and add it to the initial state as the attribute’s value; this reflects the fact that attributes always have a value in concrete states, we just did not know the specific value.
However, if some element the attribute is on did not appear in the initial state but does appear in the current state then we add the attribute to the current state.
This situation reflects some object that has been created by the program but this attribute value was not set and is some unknown value.
As an example, suppose our initial state is
\textrm{file}(\texttt{/path})\mapsto[\bot]
(where
[\bot]
indicates a nested state where all attributes and elements are undefined) and the current state is
\textrm{file}(\texttt{/copy})\mapsto[\bot]
which indicates that the file
/path
already existed and we have created a file
/copy
.
If we access the attribute
\textrm{file}(\texttt{/path}).\textrm{owner}
we will look this up in the current state and since we do not find it we look in the initial state.
In the initial state we find the element but not the attribute and so we add it; the resulting initial state is
\textrm{file}(\texttt{/path})\mapsto[\textrm{owner}\mapsto?_{0}]
, where
?_{0}
is a symbolic value.
If we want to access the attribute
\textrm{file}(\texttt{/copy}).\textrm{owner}
we would update the current state, since the element
\textrm{file}(\texttt{/copy})
does not exist in the initial state, and we get
\textrm{file}(\texttt{/copy})\mapsto[\textrm{owner}\mapsto?_{1}]
.

For an
exists
we similarly check the current state first, and if we find the element bound to a nested state we take the
then
branch and if it is bound to
\bullet
we take the
else
branch.
If we do not find a binding of the element in the current state, we check the initial state and if it is bound we take the appropriate branch.
If the element is not bound in either then we will to take both branches (separately) with appropriately updated states to determine what will happen depending on whether or not the element exists.
For this, we modify the initial states by binding the element to an empty nested state for the
then
branch and to
\bullet
for the
else
branch.
We always add these to the initial state, unlike attributes, since the existence or non-existence of an element must have come from the initial state if it was not created or removed in the program and so recorded in the current state.
This difference from how attributes are handled reflects the fact that attributes represent values that always exist while elements represent objects that may or may not exist.

Because
get
and
exists
can introduce symbolic values, the rest of the interpreter must handle them as well.
In particular, the interpretation of pure functions, if-then-else statements, case statements, and for-each loops each require some attention.
For pure functions, the interpretation of a function may get “stuck” if it is applied to a symbolic value and so even fully evaluated values may contain not just symbolic values but also unevaluated functions.
The main impact of these unevaluated functions in values are that they are specially handled by if-then-else and case statements.
For if-then-else statements, if the condition is a boolean value, we of course just take the appropriate branch, the more interesting cases are when the condition is a symbolic value or contains unevaluated functions.
If the condition is symbolic, we will simply take both branches and in those branches we replace the symbolic value with the appropriate boolean value.
It is more complicated when the condition is an uninterpreted function; ultimately our approach is the same, the additional challenge comes from wanting to extract as much information from the condition as possible.
For example, if the condition is
\neg?_{i}
then in the
else
branch we could just record that
\neg?_{i}=\textrm{false}
but it is more useful to observe that
?_{i}=\textrm{true}
and we can then replace the symbolic value
?_{i}
with true.
Similarly, if the condition is
?_{i}==\text{``Debian''}
then in the
then
branch we can replace the symbolic value
?_{i}
with the string “Debian”.
To handle these, the interpreter includes a set of such simplifying rules that it attempts to apply.
The handling of case statements over symbolic values or uninterpreted functions is similar.
In both if-then-else and case statements when values with uninterpreted functions become constrained in this process, these constraints are recorded to ensure they are reused if encountered again later in the interpretation.

Handling for-each loops over symbolic values or uninterpreted functions is more challenging.
With a loop over a concrete value we simply execute the body of the loop for each element of the list, but for a symbolic or uninterpreted value we do not know the elements but we still want to execute the loop body and somehow record that any changes the loop causes were performed in a loop over these unknown elements.
To handle this, we create a new symbolic value to represent the elements of the list and mark this symbolic value so as to indicate that it represents all elements in the list.
While this approach is imprecise, loops in Ansible are simple enough that this representation does capture their behavior.

5.2.3.
Program Verifier

Finally, to verify that the behaviors of the program and query match we compare the results of interpreting them.
We call the component in our system which does this the
unifier
; we describe its basic operations first and then discuss the handling of under-specified queries.

Basic Operation

From the interpreter, we have a set of initial-file state pairs and we need to ensure that under the same initial state the program acts the same as the formal query.
To accomplish this, we take each element of the set of state pairs from the query and we seek at least one state pair for the program with an initial state consistent with the query’s and performs the same actions.
To identify such matching state pairs requires a unification-like approach since the results of the interpreter may involve symbolic values which have to be made concrete.
For example, for the query “if os is Debian then install git” the generated program may not check the OS and so in the interpreter results for it the OS may simply be a symbolic value and to unify it with the query, where the OS has value “Debian” we must replace the symbolic value.
While symbolic values appearing in the program’s interpretation can be instantiated in this manner, the same is not the case for the query because in that case a symbolic value indicates that the query works regardless of the concrete value and so we should expect the program to do the same, and so symbolic values in the query’s results can only be unified with symbolic values in the program’s results.

Given state pairs from the query and program, we check if they match starting with the initial states.
With the initial state there is no need for the program to include all the assumptions the query does, for instance if a query specifies an operating system but the program never checks it, and so in this step we ensure all assumptions in the program’s initial state have a matching assumption in the query’s where this matching may involve unification as discussed above.
If the program’s initial state matches we then check the final states, which is slightly more strict since the program must perform all actions the query does but otherwise this is the same as checking initial states.

Handling under-specified queries

As discussed in Section
4.2
it is often the case that a formal query is an under-specification and that a generated program will make additional assumptions or perform additional actions not specified; as part of the unifier we identify these so they can be reported to a user.
Because additional assumptions and actions are permitted this means that in matching the initial states of the program and query we do not have to ensure that all assumptions from program have a matching assumption from the query, instead we are just checking that any of their shared assumptions are consistent, in other words that they do not disagree on the existence of an element or the value of an attribute.
For the final state, we still must ensure the program performs all the same actions as the query but it may also perform others.
If the initial and final states match we are able to identify and collect all of the elements and attributes from the initial and final states of the program that did not appear in the query’s so they can be reported to the user.
While our system does identify the additional assumptions and actions as described, we do not make use of this functionality in our evaluation and simply accept any program which succeeds in unifying, regardless of the additional assumptions and action.

It is worth highlighting that this approach only works because the “final state” is actually the collection of changes the interpreted State Calculus program performed.
If instead we had the actual resulting state (which is these changes applied to the initial state) then it would be possible for a program to have a final state that matches the query by assuming certain properties are true in the initial state rather than actually making them true.
For example, instead of creating a file it could simply checked and assert that the file exists and this would appear to be equivalent except for the additional assumption in the initial state.
However, with our approach such a program will not verify since it did not perform a required action.

5.3.
Compiling Formal Queries to the State Calculus

Compiling a formal query into the State Calculus is relatively straightforward; the code for a sequence of sentences is composed from the code for each individual sentence and a sequence of atomic queries in a sentence is the composition of their code.
Conditional sentences are compiled into if-then-else statements after compiling the condition; boolean combinations of conditions are compiled to pure functions that perform these operations and the base conditions such as checking the OS or whether a file exists are compiled into specific code for this purpose.
For example, to check the operating system we read an attribute from the state that represents the OS and then check its value.

Compilation of atomic queries is based mostly on the verb though partially the description as well.
For example, creating a file and a directory generate different code, but creating a file always generates the same code regardless of the description of that file: we will add a file element for the appropriate path to the state and then set attributes on it as specified.
Similarly, installing a package is always the same: we add an element indicating the package’s presence and set some attributes on it such as the package manager it was installed using.
Other atomic queries are similarly straightforward.

5.4.
Compiling Ansible Programs to the State Calculus

To compile an Ansible program into the State Calculus we make use of a relatively simple compiler and definitions and type information for each Ansible module.
These definitions for modules need to be programs in the State Calculus as the Ansible modules are our stateful functions
\alpha
in the calculus.
To facilitate these definitions, we developed the
module definition language
which is well suited to specifying these descriptions.
We describe the Ansible compiler and module description language in turn.

5.4.1.
Ansible to State Calculus Compiler

The actual compilation of an Ansible program into the State Calculus is surprisingly simple.
We generate code for each task in each play in sequence and so the core of the procedure is just generating code for an individual task.
For this, the module itself simply becomes an invocation of the stateful function from
\alpha
for that module. The main challenge here is in constructing the input which relies heavily on type information since practically all values in YAML are treated as strings and we need to generate code that gives values their appropriate types.
The most interesting aspect of this is that in Ansible some arguments will have a limited set of (string) values they can take, for instance a package manager may have a
state
argument that is either “present” to install a package or “absent” to uninstall it; we represent these as enums so that impermissible values can be identified before even running the interpreter.
There are a handful of other features that tasks have, such as conditional execution, storing the return value to a variable, and iterating the task over some list.
Generating code for each of these is straight-forward.

One important aspect of this compilation is the identification of certain built-in Ansible variables, such as those that provide information on the OS.
We convert such variables into attribute accesses of the attributes we define in the state for this purpose.

5.4.2.
Module Description Language

As mentioned above, the definitions of modules and their types is essential to compiling and interpreting Ansible programs.
An immediate question is whether we could extract this information from an existing source, such as the documentation for a module or its implementation (in Python) but unfortunately neither is suitable.
With the documentation, while some information especially about types could be extracted automatically there are important details, like when two arguments are mutually exclusive, that are only described in natural language.
As for the implementations, the code is too low-level and complex to extract the core behavior we are looking for.
The module language, then, is designed to facilitate defining the behavior and types of modules and is higher-level than the State Calculus itself to make programming easier.
To do this, the language includes features for specifying module arguments as these can be quite complicated.
It is common for Ansible module to have many optional arguments, some with default values, and also to have sets of arguments where exactly one is required.
Many Ansible modules also have arguments that must take a value from some list of values; in Ansible these are simply represented as strings, but we represent them with user-defined enum types.
The module description language also allows the user to define new elements and attributes as needed for the modules they are specifying.

We have designed the module language, as much as possible, to make it easy to write specifications for modules, since a specification is needed for any module that we want to be able to model.
As part of this, it gives significant flexibility in determining the level of detail tracked in the state; for example, we model file-systems at a rather course level like shown in Figure
5
by just tracking the path name and system we are referring to, but this approach does not model hard-links, where two files share the same inode, correctly.
If we care about such details, either because users need to generate code that deals with them or because they can be exposed by programs that may be generated, the module language provides the flexibility to do this, perhaps by defining an inode attribute for files and having an inode element that maps an inode number to its contents.
In addition to this flexibility, which can make it easier to quickly write module descriptions, the language also makes it pretty easy to specify features of a module as you need them because you can add the extra variables and define their uses as needed.
It is worth noting that a less precise modeling may result in failing to verify a correct program or even accepting a wrong program.
For example, we represent users present on a system via a user element which is convenient for defining Ansible’s user module but means that an Ansible program which directly modifies the
/etc/passwd
file would not be verified since its interpretation will not update the appropriate user element, though using the user module is much better style and so perhaps rejecting the program is a good decision.

5.5.
Formal Query Language Knowledge Base

In our description of the compilation of formal queries into the State Calculus we glossed over some details, in particular how a description like
install numpy
or
create bashrc file for user="foo"
becomes a concrete program that knows the package name or file path needed.
For this we make use of a domain-specific knowledge base; in our context this knowledge base provides information like package names, paths of common files, and other similar details.
This knowledge base is essential to avoiding the issues we described earlier where relying on an LLM may lead to plausible sounding information that is in-fact incorrect and so the construction of the knowledge base is important to enable the query language to preserve high-level concepts while being able to compile them into the State Calculus where such concepts cannot be preserved since it is also the target of Ansible code.
Our compiler for formal queries is parameterized by the knowledge base, making it easy to modify or expand in the future.
The knowledge base’s interface enables looking up information about a number of high-level concepts and returns relevant information; for example given a package description and information on the operating systems being targeted, the knowledge base will return the package name (such as
python3-numpy
) if it knows it.
In our current implementation, we have curated the information by hand, including a number of common packages, files, and so on and this can be easily extended in the future.
The set of concepts a knowledge base needs to provide information for should come from the domain being targeted and is a choice in the language design.
Filling the knowledge base is then a task for domain experts who can provide common values; it may also be possible to leverage existing knowledge sources (such as publicly available lists of packages) to fill this knowledge base.

6.
Evaluation

To evaluate our approach, we study the ability of Astrogator to differentiate correct and incorrect LLM-generated code.
In this section we present a benchmark suite of natural language descriptions and formal queries for common Ansible tasks (Section
6.1
), describe our approach to determining the ground truth correctness of generated code (Section
6.2
), describe our setup for code-generation and describe the performance of the LLMs on the code-generation task (Section
6.3
), and finally discuss the success of the verifier at identifying correct and incorrect code (Section
6.4
).

6.1.
Benchmark Suite

To evaluate our system, we need both natural language descriptions and formal language queries that can be used in the verification process.
Prior work for Ansible code-generation has used the

Given the lack of a suitable existing benchmark suite, we have developed our own.

To develop the suite, we identified common tasks people ask how to solve using Ansible from top posts on StackOverflow and the Ansible Forum.
We have add to this set some tasks based on playbooks we found in Ansible Galaxy, a large repository of Ansible code, as well as some interesting variations on other tasks and tasks that highlight some of the difficulties we have mentioned already.

6.2.
Code Testing

The first step in our evaluation is to determine whether generated code is correct or not, since that information is necessary to evaluate whether Astrogator accurately recognizes both correct and incorrect programs.
To do this we use tests because, even though they can be imperfect, no other solution was feasible (e.g., manual inspection is infeasible for 1260 programs).
We have done our best to craft strong tests that address subtle aspects of our problems.
To test generated programs, we run them on a set of virtual machines along with setup and testing scripts which determine whether the program behaved as expected.
Because many of our problems are only expecting one particular behavior, many problems only have a single test, though in other cases multiple tests are needed to check behavior under different initial conditions, such as with problem 6 where the file should only be created if it does not already exist.

For our experimental setup, we use three VMs running Debian 12.11.0, Ubuntu 24.04.2, and Red Hat Enterprise Linux (RHEL) 9.6; for any problem that does not specify an operating system we test the program on each of these systems and for problems that specify certain operating systems we run it on those systems (for problem 15, we run it on all three systems since Ubuntu is a Debian-based system).
Between each program execution we reset the VMs from a snapshot of the systems to ensure that a program cannot impact the behavior of another.
A program is judged to be correct only if it passes all tests on all systems it was tested on.

6.3.
LLM Code Generation

To generate a diverse set of programs to test Astrogator, we have selected six LLMs and since the LLMs are nondeterministic we prompt each for ten programs for each problem to further increase the diversity of our program set, resulting in a total of 1,260 programs.

In problem 6, creating a file if it does not exist, the programs overwrote the file in all cases; to the verifier this is potentially valid program though since it just appears as an additional action performed by the program compared to the query.
Similarly in problem 12, rebooting the system if needed, the programs simply always reboot which to the verifier appears simply as an additional action performed by the program.
In both of these cases the formal queries involve a conditional and while it may seem implied that an action described in the then branch should not be performed in the else branch, because of the flexibility for additional actions we give we have not placed this restriction though it may be desirable so that a query like “if file

For problem 17, the two incorrect programs that are accepted work only if the “service” does not exist already.

This and similar issues are not rejected because the target files are ultimately created and if the alternate file sources have certain contents the program behaves as desired.
These assumptions about additional files again appear in the output of the verifier and so a user could easily indicate that they are not reasonable.

We observe that even though our verifier does accept incorrect programs in some cases, 79.8% of programs accepted by the verifier are in fact correct; which is significantly higher than the percentage of generated code which was correct.

7.
Discussion

We discuss two topics: limitations of our current system and the generality of the ideas presented.

7.1.
Limitations

As seen in our evaluation, some correct programs are rejected; some for readily addressable reasons and others requiring more substantial effort.
There are some unsupported features that could be easily addressed with some additional engineering, such as support for
block
constructs, which group a set of tasks, and handlers, which are a way to invoke a piece of code after a task.
The other significant feature not supported is shell commands which support is more difficult since it would require a specification of the behavior of shell programs; we discuss this possibility more in Section
7.2
.
The remainder of the correct programs that were rejected were due to the limitation that our knowledge base always produces a single response, even when multiple valid solutions exist.
Addressing this problem is more technical; a potential solution is to compile the query into the state calculus using symbolic values in place of values from the knowledge base and to add assertions that these values are acceptable according to the knowledge base.
The challenge with this is that currently all symbolic values are
universal
because they represent arbitrary values whereas these would need to be
existential
symbolic values that represent just some acceptable value.

The system also accepts some incorrect programs which are correct under certain assumptions, some of which are reasonable and others of which not such much.
This problem arises because, as described in Section
3
, ultimately these assumptions must be reviewed by the user.
Some of these assumptions that we view as unreasonable may be something that should be identified and rejected without the user’s intervention but how to identify such cases is not obvious.

Our formal query language is currently rather small since our knowledge base has been constructed by hand and is quite small.
For a full query language it needs to be much larger to encompass many more packages, files, etc. that a user may describe.
Additionally, our query language currently is focused on file, software package, and user management operations and to cover more of Ansible it needs support for concepts from other kinds of system configuration.

7.2.
Generality

While Astrogator is specific to Ansible many of the ideas presented in this work do not make assumptions about the language being verified though we do believe there are certain features that make a language more amenable.
First, we believe that domain specific languages (DSLs) are more suitable because the domain defines the concepts needed in the formal query language and provides the domain knowledge for the knowledge base.
There is so much breadth in a GPL like C or Python that a high-level query language would almost certainly end up either limiting what can be expressed or have low-level details in the queries.
In addition, we suspect that these techniques are more suitable to non-Turing Complete languages (which DSLs often are) since these languages are more amenable to automated verification.
In particular, our approach for handling symbolic values in the interpreter is sufficient for Ansible at least in part because loops in Ansible are generally quite simple and we are not sure the approach would work as well if this was not the case.

We believe that the State Calculus may also be useful in constructing verifiers for other languages.
The State Calculus is generic and designed to represent pretty arbitrary computation of a similar stateful nature to Ansible, such as many shell scripting languages and even fragments of C focusing on system-level task.
For such languages, we believe that the State Calculus, its interpreter, and our unifier could be reused, as is, to reduce the burden of building verifiers for these languages.
Of course, they would still need new formal query languages (though ideas could be borrowed from ours) and a compiler from the language to the Calculus.
We device our compiler between the simple Ansible compiler and the module definitions and we believe a similar approach is applicable to many other languages, for instance with Bash there are some core behaviors dealing with composing commands and then individual commands can be specified separately.
This compositionality helps reduce the burden of building the compiler and helps the system to grow incrementally.

8.
Related Work

Improving LLM Code Generation

There has been significant prior work on improving the performance of LLM-based code generation including through the curation of datasets
(
Li et al. 2023
;
Lozhkov et al. 2024
)
, fine-tuning models for code
(
Darnell et al. 2024
;
Li et al. 2024
)
, novel training techniques
(
Wu et al. 2025
;
Wei et al. 2024
;
Jha et al. 2025
;
Zhang et al. 2025a
)
, and decoding techniques to prevent syntax errors
(
Ugare et al. 2025
)
and type errors
(
Mündler et al. 2025
)
.
While these techniques can improve the likelihood that AI-generated code is correct, they do not offer strong formal guarantees as syntactic and type correctness are generally insufficient to ensure the program actually matches the user’s intent.
In the context of coding assistants user inspection is often expected to eliminate incorrect code, though this is not an ideal as LLM-generated bugs can often be subtle
(
Dou et al. 2024
)
.
Our work to offer formal guarantees can benefit applications of code generation models and can benefit from better code generation models.

Identifying Incorrect LLM Generated Code

Some prior work has used test cases, specified along with the natural language description, to check LLM generated code
(
Chen et al. 2021
)
.
This increases the likelihood that the generated code is correct and with a sufficient test suite can offer reasonably strong guarantees of correctness but this requires the user to craft good tests as insufficient tests can permit errors, such as those found in ground-truth solutions to the well known
HumanEval
benchmark suite
(
Liu et al. 2023b
)
.
Using LLMs to generate tests, rather than relying on the user, has also been explored
(
Chen et al. 2023
)
and shown potential to improve the likelihood of generating correct code, but this means the strength of the correctness guarantee is dependent on the tests generated by an LLM.

Verified LLM Generated Code

LLM code generation has been explored in the context of generating proofs proof assistants such as Rocq and Isabelle
(
First et al. 2023
)
.
In this setting, the generated proof is checked for correctness by the theorem prover to see if it proves the formal theorem statement provided by the user.
This approach is similar in that we verify the generated code.
To address the need for a formal theorem statement, the problem of auto-formalization has also been studied
(
Wu et al. 2022
)
, though the generated theorem statements are in a lower-level language than our formal query language making them more difficult for users to check.

Natural Language Summaries

Other works have also proposed the idea of showing the user a natural language like description to have them check, though prior work has explored providing a description of a generated program
(
Barnaby et al. 2024
;
Liu et al. 2023a
)
.
While this can help help a user determine if the generated code matches their intent we believe our approach of having the user verify a high-level specification is better since it helps avoid issues where a code summary may seem reasonable but contain subtle errors.

LLM Generation of Formal Specifications

While we have not explored it yet, we suggest using LLMs to generate formal queries; the idea of using LLMs to formalize the user’s intent have explored in other contexts such as generating post-conditions
(
Endres et al. 2024
)
and generating Isabelle theorem statements
(
Wu et al. 2022
)
.
These works show that LLMs can generate reasonable formalization which can then be used to check generated code or proofs.
However, we believe that the formalizations chosen by these prior works are not suited for the user to check correctness of as they are fragments of programming language.
Additionally the quality of a postcondition can significant impact how effectively it enforces correctness and so correctness guarantees rely on the use ensuring the postconditions are high-quality.

Program Synthesis

Finally, our work is an attempt to merge LLM-based code generation with some ideas and techniques from Program Synthesis.
In particular, in our vision for a complete code-generation system (Figure
2
) the loop between the Code Generator, Verifier, and Assumptions Check bears significant resemblance to the feedback loop found in Counterexample Guided Inductive Synthesis, and similar techniques.
Additionally, the user’s input in the Assumptions Check phase, where the user essentially checks whether aspects of the generated program not specified in the original query satisfy their intent, bears resemblance to interactive synthesis
(
Peleg et al. 2018
)
where the user may iteratively refine the specification until the generated programs matches their full intent.
There has also been some prior work that makes use of both LLM code generation and program synthesis, such as Photoscout
(
Barnaby et al. 2024
)
which uses an LLM to generate programs and then a semantic analysis identifies undefined components and replaces them with holes which are filled an enumerative synthesis approach.
This technique could be relevant to Ansible, as our formal queries could provide a basis to perform such synthesis.

9.
Conclusion

In this work we have proposed the use of
formal query languages
which formalize a user’s intent, expressed in natural language, to check LLM generated code for correctness.
We present design constraints for such a language to ensure that a user can check that a query matches their intent.
We present our implementation of this design, Astrogator, for the Ansible IT automation language and show that we can use our verifier to effectively identify correct and incorrect LLM generated code.
While the current verifier is imperfect, we analyze the errors and find that many of the programs rejected are due to current limitations that can be easily addressed and identify that the incorrect programs which were accepted are accepted because they rely on additional assumptions that require a user in the loop to decide whether they are reasonable or not based on their intent.
We believe this work can lay a design for building systems which from a natural language description are able to generate code that is guaranteed to match the user’s intent, which can advance the goal of natural language programming and improve correctness of LLM generated code in AI Code Assistants.
