Library Hallucinations in LLMs: Risk Analysis Grounded in Developer Queries
Lukas Twist, Jie M. Zhang, Mark Harman, Helen Yannakoudakis

Abstract
Large language models (LLMs) are increasingly used to generate code, yet they continue to hallucinate, often inventing non-existent libraries. Such library hallucinations are not just benign errors: they can mislead developers, break builds, and expose systems to supply chain threats such as slopsquatting. Despite increasing awareness of these risks, little is known about how real-world prompt variations affect hallucination rates. Therefore, we present the first systematic study of how user-level prompt variations impact library hallucinations in LLM-generated code. We evaluate six diverse LLMs across two hallucination types: library name hallucinations (invalid imports) and library member hallucinations (invalid calls from valid libraries). We investigate how realistic user language extracted from developer forums and how user errors of varying degrees (one- or multi-character misspellings and completely fake names/members) affect LLM hallucination rates. Our findings reveal systemic vulnerabilities: one-character misspellings in library names trigger hallucinations in up to 26% of tasks, fake library names are accepted in up to 99% of tasks, and time-related prompts lead to hallucinations in up to 84% of tasks. Prompt engineering shows promise for mitigating hallucinations, but remains inconsistent and LLM-dependent. Our results underscore the fragility of LLMs to natural prompt variation and highlight the urgent need for safeguards against library-related hallucinations and their potential exploitation.

Introduction

Large language models (LLMs) have rapidly become a cornerstone of modern software development, transforming natural language (NL) prompts into executable code with remarkable accuracy and speed
(
Jiang et al. 2024a
)
.
Their substantial traction in industry–evidenced by GitHub Copilot’s 90% merge rate in enterprise settings
(
Novet & Vanian 2025
)
and Microsoft’s usage rate of up to 30%
(
Gao & Research 2024
)
–means that LLM-generated code is increasingly deployed in real-world systems.
However, the reliability of this code remains a critical concern.
A particularly serious failure mode is code hallucinations–in which LLMs fabricate elements of the code they produce–with serious consequences in software engineering
(
Zhang et al. 2024
;
Lee et al. 2025
)
.
Unlike typical bugs, these hallucinations are generated confidently, may not trigger immediate errors, and can mislead developers into integrating non-existent or insecure components.

The problem is particularly acute for external libraries, which are central to modern software engineering and are routinely imported to accelerate development
(
Larios Vargas et al. 2020
)
.
Despite a clear ground truth of published documentation, LLMs still frequently exhibit library-related hallucinations when generating code
(
Spracklen et al. 2024
)
.
Such hallucinations bypass dependency validation and can mislead developers into integrating invalid, deprecated, or insecure packages, which pose significant risks in practice
(
Wang et al. 2025
;
Krishna et al. 2025
)
.
Furthermore, the recent emergence of “slopsquatting”–where a frequently hallucinated library is created by a malicious actor–poses another significant threat, one specific to library hallucinations
(
Park 2025
)
.

Existing studies on library hallucinations largely define the problem at a broad level, focussing on aggregate evaluations without offering a systematic understanding of what triggers them
(
Krishna et al. 2025
;
Spracklen et al. 2024
)
.
As a result, we lack a fine-grained understanding of how realistic user-language variations or common naming errors affect hallucination rates.
Mitigation efforts have been mainly based on retrieval-augmented generation (RAG), grounding responses in official documentation
(
Jain et al. 2024
)
or project-specific contexts
(
Wang et al. 2024b
)
.
Although effective, these approaches require considerable infrastructure that limits practicality for users who rely on off-the-shelf models and prompt engineering.
Moreover, RAG may still silently fail if users provide incorrect references that lack retrieval matches, causing LLMs to revert to default generation and produce confident hallucinations.

We go beyond previous aggregate evaluations by simulating real-world developer prompts, including user errors and natural language variation, and quantifying their effect on library-related hallucinations across
six
production-grade LLMs.
Understanding how LLMs respond to these language variations offers practical guidance for both LLM users to avoid triggering hallucinations and for LLM builders to realise vulnerabilities.
We focus on
two
classes of library-related hallucinations that can be reliably verified:
library name hallucinations
, where an LLM generates code that imports a non-existent library; and
library member hallucinations
, where the code references a non-existent function, class or object from a valid library.

We design
three
systematic experiments to quantify how prompt variations affect library hallucinations in LLM-generated code:

1)
We prompt LLMs using descriptions of libraries extracted from Software Recommendations StackExchange
1

Software Recommendations StackExchange:
https://softwarerecs.stackexchange.com/
to simulate authentic developer intent;

2)
We introduce controlled language variations simulating different degrees of user error, including one- and multi-character misspellings, or completely fake library names/members;

3)
We test whether prompt engineering techniques such as chain-of-thought or step-back prompting can mitigate hallucinations in these settings.

Our findings reveal key vulnerabilities in LLM code generation:

1)
LLMs largely ignore adjective-based library descriptions but are
highly susceptible to time-related prompts
– prompts asking for a library “from 2025” produce hallucinated libraries in up to 84% of tasks;

2)
LLMs are
not robust to user errors
in library names – requesting the use of a library with a one-character misspellings causes hallucinations in up to 26% of tasks, multi-character misspellings in up to 79% of tasks, and fake libraries are used in up to 99% of tasks. These results suggest that LLMs may inadvertently amplify typosquatting risks by treating small naming errors as valid packages;

3)
prompt-engineering strategies can reduce library hallucination rates in some scenarios, but improvements are not guaranteed, and well-studied reasoning prompts (such as chain-of-thought) often fail or even increase hallucination rates, highlighting the
need for further work in library hallucination mitigation
.

Our contributions are as follows:

1.

We present the first systematic empirical study on how prompt variations affect library name and member hallucination rates.

2.

We reveal concrete risks tied to user errors and time-related phrasing, showing how high model compliance can increase exposure to typosquatting and slopsquatting attacks.

3.

We uncover a novel connection between LLM behaviour and typosquatting: minor prompt errors can lead LLMs to confidently hallucinate, potentially exposing developers to supply chain threats. This complements prior work on slopsquatting by revealing a distinct, previously unexplored risk.

4.

We provide practical mitigation insights and release our code and a benchmark suite, including prompts, labels, and full outputs, to support future research on hallucination detection and prevention:
https://github.com/itsluketwist/realistic-library-hallucinations

2
Related Work

Background on Hallucinations
:
Hallucinations are a common failure mode in NL generation, referring to outputs that are nonsensical or unfaithful to the source content provided
(
Ji et al. 2023
)
.
For LLMs, the notion extends to confident but ungrounded predictions, where outputs appear fluent and coherent but conflict with external sources, or the intent or context of the prompt
(
Huang et al. 2023
;
Zhang et al. 2023
)
.

LLM Code Generation & Hallucinations
:
LLMs excel in code generation
(
Jiang et al. 2024a
)
, with increasingly impressive performance across a wide range of tasks
(
Chen et al. 2024
)
.
Hallucinations during code generation manifest themselves in programming-specific ways, including error-producing code, fabricated libraries, or misuse of functions.
Current work on code-based hallucinations consists mainly of defining the problem, with several works proposing overlapping but distinct taxonomies
(
Lee et al. 2025
;
Agarwal et al. 2024
;
Tian et al. 2024
;
Liu et al. 2024
)
.

Library-Based Code & Hallucinations
:
Generating code that relies on external libraries remains a persistent challenge for LLMs.
Accurate imports require up-to-date knowledge of library names, APIs, and import paths, many of which may be rare, private, or introduced after the model’s training cut-off
(
Zhuo et al. 2025
;
Cheng et al. 2024
)
.
Several works aim to address this by adopting two-stage approaches that first predict imports before generating code
(
Liu et al. 2023
;
Zan et al. 2022
)
;
incorporating library documentation via RAG
(
Patil et al. 2023
;
Peng et al. 2023
)
; or giving models knowledge of unseen APIs
(
Zan et al. 2023
;
Wang et al. 2024b
)
.
Despite these advances, hallucinations remain widespread, with models often fabricating non-existent libraries or invoking invalid members from real ones
(
Spracklen et al. 2024
;
Krishna et al. 2025
)
.
Current mitigation strategies rely heavily on RAG pipelines, which require significant infrastructure and cannot be deployed in prompt-only settings
(
Eghbali & Pradel 2024
;
Jain et al. 2024
;
Chen et al. 2025
)
.
This motivates our focus on how prompt variation alone affects hallucinations; and whether existing prompt strategies that do not require retrieval or fine-tuning show promise for mitigation.

Library Selection & Security
:
External libraries are an essential part of modern software development
(
Somerville 2016
)
.
Library selection is a key decision that can affect both the functionality and security of a project, and LLMs are increasingly used to recommend them
(
Latendresse et al. 2024
;
Wang et al. 2024a
)
.
A well-documented threat in this process is
“typosquatting”
, where malicious actors exploit minor misspellings of popular libraries
(
Taylor et al. 2020
;
Neupane et al. 2023
)
.
More recently,
“slopsquatting”
has been proposed to describe the registration of libraries that are commonly hallucinated by LLMs
(
Spracklen et al. 2024
;
Park 2025
)
.
Although typosquatting has been studied in traditional software ecosystems, its potential amplification through LLM usage has not. To our knowledge, no prior work has examined how prompt-level errors in library names lead LLMs to produce hallucinated or misleading library suggestions.
We address this gap with a targeted empirical analysis of LLM behaviour under potential user mistakes.

3
Experimental Design

3.1
LLM Selection

A wide range of LLMs are used in this study, to enable a broad understanding of how LLM architecture affects library-related hallucinations during code generation.
In particular, we want to experiment on a range of sizes (number of parameters), use cases (general, code-specific, or reasoning-enhanced), availabilities (open or closed source), and providers.
Therefore, we chose the following
six
LLMs for our study: GPT-4o-mini
(
OpenAI 2025a
)
, GPT-5-mini
(
OpenAI 2025b
)
, Ministral-8B
(
MistralAI 2025
)
, Qwen2.5-Coder
(
Hui et al. 2024
)
, LLama-3.3
(
Meta 2025
)
and DeepSeek-V3.1
(
DeepSeek 2025
)
.

LLM Usage
:
To reflect the typical usage of LLMs by developers, which often overlooks the role of LLM parameters
(
Donato et al. 2025
)
, each LLM is prompted using the default parameter configurations provided by its corresponding API.
Furthermore, we conduct each LLM interaction in a fresh API session, to avoid bias from prompt caching or leakage
(
Gu et al. 2025
)
;
and we do not use a system prompt to ensure that each LLM has its base functionality considered
(
Mu et al. 2025
)
.

Full details of each LLM and their configurations are given in Appendix
A
.

3.2
Dataset Selection

Our scope is restricted to
Python
due to its extensive library ecosystem, straightforward import extraction, and prevalence in modern software development
(
Feng et al. 2025
)
.
Therefore, we adopt BigCodeBench
(
Zhuo et al. 2024
)
as the seed dataset for our experiments.
BigCodeBench contains 1140
Python
coding tasks in
seven
domains (general, computation, visualisation, system, time, network and cryptography) – 71% of which use an external library in the ground-truth solution.
Its tasks are derived from ODEX
(
Wang et al. 2023
)
but rephrased with the NL-Augmenter framework
(
Dhole et al. 2023
)
, reducing the risk of data leakage and ensuring realistic yet unseen problem statements.
To avoid bias, we filter out tasks where the description directly mentions the ground-truth library and restrict to cases where external libraries have accessible documentation, yielding 356 tasks that use 30 distinct libraries.
We reserve 10% for preliminary experiments and run our main analysis on the remaining 90%, strengthening the robustness and generalisability of our final results.

Dataset Usage
:
We adopt a consistent template for all prompts to ensure comparability

(
Voronov et al. 2024
)
.
Our prompt template is inspired by BigCodeBench:
“Write a self-contained python function for the following task, using
{
library directive
}
.
{
task description
}
”
.
For each prompt, we generate
three
responses to mitigate sampling variability in LLM outputs
(
Sallou et al. 2024
)
.

Full preprocessing details and the final dataset are provided in our GitHub repository.

3.3
Experiment 1: Influence of Realistic User Language

Developers increasingly turn to LLMs for programming help, with notable declines in public Q&A activity following the rise of ChatGPT
(
Zhong & Wang 2024
;
Rio-Chanona et al. 2024
)
.
We investigate whether variations in user descriptions during these library-related queries affect hallucination rates.
To ground our experiments, we systematically analyse questions from Software Recommendations StackExchange (SRSE), which contains short, task-oriented requests for software and libraries, serving as a natural proxy for developer-inspired prompts.
This choice is supported by studies showing that developer–LLM interactions often mirror forum-style queries
(
Xiao et al. 2024
)
.

We filter to library-related questions only, then embed and cluster
n
-grams from their titles to identify recurring descriptors.
From this analysis, we obtain nine common variants:
open-source
,
alternative
,
free
,
best
,
simple
,
easy
,
fast
,
lightweight
and
modern
.
Each description is inserted into a fixed template (Section
3.2
), either asking the model to “use a library” with the property (for
library name hallucinations
) or to generate code with the property using a specified library (for
library member hallucinations
).
Furthermore, we found a common trend in the SRSE questions to request libraries from a given year, which aligns with studies showing that developers value recency in library selection
(
Cox et al. 2015
;
Tanzil et al. 2024
)
.
Therefore, we also include year-based descriptions, with prompts requesting libraries
“…from 2023/2024/2025 or later.”
.

Full details of the SRSE analysis, the clustering procedure, and the exact prompts used to generate the results, are provided in Appendix
B.2
.

3.4
Experiment 2: Influence of User Mistakes

Misspellings (otherwise known as typos) and name confusions in library references are common in real-world development
(
Hagiwara & Mita 2019
)
and have even been exploited in supply chain attacks such as typosquatting
(
Neupane et al. 2023
)
.
Minor errors are often treated as routine input noise and are generally expected to be tolerated by LLMs
(
Sperduti & Moreo 2025
)
; larger mistakes should be easy to reject due to knowledge conflicts, although they may instead trigger sycophancy, where the model simply agrees with the user
(
Perez et al. 2023
)
.
We therefore investigate whether different degrees of error cause LLMs to hallucinate library names or members when generating code, using the following error types:

one-character misspelling
(edit distance 1) – a simple slip, for example
numpi
over
numpy
;

multi-character misspelling
(edit distance 2–8) — a larger but still recognisable deviation from the original, for example
graphly
instead of
plotly
;

fake name/member
— a non-existent name/member, representing when a user has follow-up requests for a previous hallucination, for example
GaussianTools
as a data analysis library.

We generate misspellings and fake library names/members using a reasoning-enhanced LLM (OpenAI’s
o4-mini
), which produced the most plausible variants in preliminary testing.
Generated misspellings were checked to match the intended Levenshtein distances, and all names/members were verified to be non-existent using our hallucination-detection pipeline (Section
3.6
).
For each task, we use
two
instances of each type of error.
We insert each mistake into the fixed prompt template (Section
3.2
), for
library name hallucinations
we ask the LLM to use the specified library; for
library member hallucinations
we provide a valid library and specify a member to use.

Full details of the process for generating misspellings and false library names/members, and the exact prompts used to generate results, are provided in Appendix
B.3
.

3.5
Experiment 3: Prompt Engineering Mitigation Strategies

Finally, we analyse the impact of widely used prompt engineering strategies on library hallucinations.
Our goal is not to exhaustively optimise or design new prompting methods for hallucination mitigation, but rather to provide representative baselines that future work can build upon when developing more effective mitigation techniques.
Developers often omit code from their prompts
(
Xiao et al. 2024
)
, making few-shot and other in-context prompting approaches, which require multiple high-quality examples, impractical in typical development workflows.
Similarly, while RAG can improve accuracy, it is often unsuitable for most users due to its significant setup, latency, and infrastructure overheads
(
Zhao et al. 2024
)
.
We therefore evaluate low-effort prompt techniques that have been shown to be effective in software engineering tasks
(
Santana Jr et al. 2025
)
, and require only the addition of a brief instruction to an existing prompt.

We evaluate
four
prompt-engineering strategies, each designed to guide the LLM in different ways.
We choose to focus only on mitigating
library name hallucinations
, because they have the greatest potential to introduce security vulnerabilities; and we repeat only the previous experiments that exhibit the highest hallucination rates.
The strategies are detailed as follows, together with the exact text appended to the original prompts.

Chain-of-thought
— encourages the LLM to first generate internal reasoning steps, to improve logical consistency
(
Wei et al. 2022
)
.

“Let’s think step by step to solve the task.”

Step-back
— prompts the LLM to take a more abstract view of the task, fostering higher-level reasoning
(
Zheng et al. 2024
)
.

“Take a step back and think about the task before responding.”

Self-analysis
— instructs the model to review its initial solution and correct for any errors
(
Liu et al. 2025
)
.

“Double check your answer and fix any errors before responding.”

Explicit-check
— an obvious way to try to reduce hallucinations via the prompt, asking the LLM to specifically check existence.

“Make sure all libraries and members used are correct and exist.”

3.6
Result Analysis

Response Data Extraction
:
The LLMs used in the study typically format their responses as
Markdown
, or provide only the code itself.
In
Markdown
, code blocks are denoted by a triple backtick followed by the programming language name
(
Cone 2025
)
, therefore, we can use
regex
matching to extract code blocks and programming languages.
We then examine all
Python
code blocks to identify the imported library names and the used library members.
To do this, we construct the abstract syntax tree (AST) for each code block using
Python
’s
ast
module
(
PSF 2025
)
.
We traverse the AST, using
Import
and
ImportFrom
nodes determine which libraries have been imported, and using
Call
and
Attribute
nodes to determine the usage of library members.

Hallucination Detection
:
To detect
library name hallucinations
, we compare the imported library names against the list of libraries available on the Python Package Index (PyPI)
(
PyPI 2025
)
, following the methodology used in previous studies
(
Spracklen et al. 2024
;
Krishna et al. 2025
)
.
To address potential mismatches between import names and the registered PyPI name, we first apply package name normalisation
(
PyPA 2025
)
, and then manually review any unmatched libraries to ensure genuine hallucinations.
To detect
library member hallucinations
, we scrape the latest official documentation for each ground-truth library and check the extracted library members against it.
We use only the latest version of each library, as this is the default installed when no version is specified, and LLMs rarely include explicit version numbers when generating code
(
Raj & Costa 2024
)
.

Results

4.1
Results for Experiment 1: Influence of Realistic User Language

This experiment investigates how realistic variations in user descriptions of libraries and members influence the hallucination rates of LLMs.

Table
1
shows the results.

Library Name Hallucinations
:
We observe that adjective-based descriptions (for example, “fast” or “lightweight”) rarely trigger hallucinations: all LLMs showed a hallucination rate of
approx
0% in these cases.
Ministal and Qwen-2.5-Coder are the most sensitive, but still had hallucination rates below 0.5%.
Overall, this suggests that LLMs largely ignore these descriptions, defaulting to their preferred set of libraries.
This can be seen in the results, where LLMs simply rephrase why their preferred library fits the prompt instead of choosing a different library, and is consistent with previous work showing how LLMs have strong preferences for a small subset of libraries
(
Twist et al. 2025
)
.
Year-based descriptions tell a different story.
Asking for libraries “from” a specific year caused hallucinations to spike across all LLMs, with more recent years leading to higher hallucination rates.
In some cases this increase was dramatic, GPT-4o-mini hallucinated in 34% more responses when the year changed from 2023 to 2024, and GPT-5-mini had a 32% increase from 2024 to 2025.
LLama-3.3 was by far the best LLM at avoiding hallucinations for year-based prompts.
These results show that time-related signals are a strong trigger for hallucinations.
Although some of this can be explained by LLM knowledge cut-offs, the behaviour remains problematic: this style of request is realistic, yet users cannot reasonably be expected to always know the cut-off date of an LLM.

Library Member Hallucinations
:
All LLMs show consistent low levels of
library member hallucinations
, even for the base experiment without a description, showing greater sensitivity to using correct library members than correct library names.
Slight increases are observed across all LLMs for the “alternative”, “fast” and “modern” descriptions.
A recurring source of hallucinations is outdated knowledge – models suggesting deprecated functions without specifying a version
(
Wang et al. 2025
)
– which makes it even more surprising that the newest LLMs in the study (GPT-5-mini and DeepSeek-V3.1) showed consistently higher hallucination rates across all descriptions, sometimes hallucinating in up to 20% of tasks.
Notably, none of the responses with hallucinations included explicit version numbers, reinforcing that version awareness remains a major gap.

Experiment 1 Summary:

This experiment investigates the extent to which user mistakes–either a one- or multi-character misspelling, or a fake library name/member–affect the hallucination rates of LLMs for both library names and members.

Table

Library Name Hallucinations
:
LLMs had significant hallucinations when asked to use incorrect library names, and this effect worsened with more serious errors.

\approx

This sensitivity in code generation tasks is particularly surprising, as it is generally accepted that LLMs are robust to minor errors in NL prompts unless they are adversarial
(
Gan et al. 2024
;
Sun et al. 2020
)
.
Multi-character typos again reduced reliability, but fake library names proved to be the most used by a significant margin.
Three LLMs in this study (GPT-4o-mini, GPT-5-mini, and Ministral-8B) used the fake library in more than 90% of tasks, which means that they almost always complied with the user error rather than rejecting it or offering an alternative.
In contrast, Qwen-2.5-Coder was considerably more robust, using the fake library in only 21% of tasks.
This pattern, especially the eagerness of GPT models to comply, aligns with recent discussions of sycophancy in LLMs
(
Sharma et al. 2024
)
.
LLMs would rather use the library they are presented with than risk trying to correct the user, this is particularly worrying for obvious typos of popular libraries–such as
panfas
instead of
pandas
, and
nimpy
instead of
numpy
–both of which had multiple instances of confident usage by the LLMs.

Library Member Hallucinations
:
Member-based hallucinations were overall less severe.
LLMs use one-character misspellings of library members more willingly than library names, but there is no consistent trend where larger mistakes lead to significantly higher hallucination rates.
Fake library members led to far lower usage rates than for library names (34% average task usage rate for members vs. 68% for names).
This indicates that LLMs are more robust to incorrect library members than to incorrect libraries themselves.

Experiment 2 Summary:

LLMs showed strong susceptibility to user mistakes in library names: even a one-character misspelling led to hallucinations in up to 26% of tasks, and all LLMs consistently used fake library names, for up to 99% of tasks.

Library member hallucinations
were less common in general and showed a less clear scaling with the severity of the mistake.

Results for Experiment 3: Prompt Engineering Mitigation Strategies

This experiment investigates whether practical prompt engineering strategies can reduce
library name hallucinations
during code generation, focussing on the previous experiments with the highest hallucination rates.

Table

shows the results.

We find that prompt engineering can reduce
library name hallucinations
, but its impact is inconsistent.
Self-analysis and explicit-check are the most effective, reducing hallucinations in 29/36 and 30/36 instances, respectively, and often by double digits.
In contrast, open-ended strategies popularised for their ability to induce reasoning (chain-of-thought and step-back) were inconsistent and commonly increased hallucinations; they appear to reinforce incorrect reasoning, rather than encouraging the LLM to verify its facts.
The state-of-the-art LLMs responded best to mitigation strategies: GPT-5-mini and DeepSeek-V3.1 both have mean reductions in their hallucination rates of more than 5%.
However, Qwen-2.5-Coder, the only code-specific model tested, frequently regressed under these prompt strategies despite being one of the most robust in previous experiments.
This shows that whilst simple prompt edits can help to reduce hallucinations, general-purpose reasoning prompts cannot be relied upon, and they must all be validated per LLM before adoption.

5
Discussion

5.1
Inducing Hallucinations

We conducted further investigations after adjective-based prompts initially appeared low-risk.
Our analysis of the SRSE user forum showed a clear tendency for users to request “alternatives” to mainstream libraries, which is consistent with evidence that users explore novel options in practice
(
Mészáros & Wachs 2024
)
.
This desire for rarity can take many phrasings, with users wanting lesser known libraries
(
Ferrer 2025
)
, or even hidden gems
(
Chawla 2023
)
.
We prompted the LLMs with these descriptions and the results show a clear trend: the more a description implied rarity, the more often hallucinations occurred.
Asking for a “lesser known” library caused hallucinations in 1.92% of tasks (average across all LLMs), “not widely used” increased the rate to 3.01%, and adding “hidden gem” increased the rate to 5.35% - the highest among all adjective-based prompts.
This suggests that rarity-seeking language can encourage LLMs to hallucinate libraries; therefore, we recommend avoiding such language for practical coding scenarios.

Full details and results for this additional experiment are provided in Appendix
B.4
.

5.2
Harnessing Hallucinations

Although we treat library hallucinations as a failure mode during code generation, the same behaviour could be reframed as a source of creativity or ideation.
LLMs often invent not just plausible library names, but entirely new library concepts, complete with a description of their functionality – for example:
polarscatter
, “…provides a simple way to create polar scatter plots.”;
tzshift
, “…convert a time string from one timezone to another, considering daylight saving time.”; or
numpy-base64
, “…facilitates base64 encoding specifically for numpy arrays.”.
Although these are incorrect as-is, they hint at gaps in the coding ecosystem and could inspire genuinely useful new libraries, or extensions to existing libraries.
Recent work has started to explore similar ideas for NL, where hallucinations are not only seen as factual errors but also as creative output that has the potential to have some value
(
Sui et al. 2024
;
Jiang et al. 2024b
)
.
Code-based hallucinations, if syntactically valid and semantically meaningful, could hold similar promise.
If we look past the errors and treat these outputs explicitly as suggestions rather than executable code, there is a possibility that LLMs could hallucinate much more than just new library ideas: new architecture patterns, code formatting styles, and programming paradigms are just a few of the possibilities.

6
Threats to Validity

Internal validity
:
The threats to internal validity lie in our automatic data extraction, the realism of our prompt variations, and the construct validity.
To alleviate the first threat, we have both unit tested the responsible code and manually validated the library and member extraction process on 100 random samples from the experiments.
Prompt realism is supported by our systematic derivation of library descriptions from the SRSE user forum (Section
3.3
), and the common nature of errors in real-world code
(
Hagiwara & Mita 2019
)
.
To reduce threats to construct validity, we focus on a pragmatic, user-relevant subset of library hallucinations–those of
names and members
–that are simply defined and can be operationally detected using a clear ground truth (Section
3.6
).

External validity
:
The threats to external validity lie in dataset selection and LLM variability.
We mitigate dataset bias by excluding any tasks that reveal ground-truth libraries (Section
3.2
), any residual data leakage is likely to only cause
fewer
hallucinations, making our findings conservative if this were the case.
We reduce the threats presented by LLM variability–their nondeterministic nature and opaque updates
(
Sallou et al. 2024
)
–by repeating the experiments multiple times and specifying the exact version of each LLM to use.

7
Conclusion

We present the first systematic study of how developer-inspired prompt variations influence library name and member hallucinations in LLM-generated Python code.
While simple adjective-based descriptions are largely ignored, we find that prompts with year-based phrasing or minor user errors, such as typos or invented names, substantially increase hallucination rates.
Across models, LLMs often comply with invalid references rather than correcting them, revealing a critical gap in robustness.
Prompt-engineering techniques offer partial mitigation, but their effects are inconsistent and LLM-dependent.
Our findings highlight the need for reliable defences usable in prompt-only settings, and for threat models that reflect how hallucinations expose developers to real-world risks, including typosquatting and slopsquatting.
Future work should prioritize measurement frameworks that explicitly capture these risks to inform more effective safeguards.

To reduce hallucination risks in real-world use, we recommend enforcing mechanism-matched behaviours at the model interface, not just the user level.
First, cut-off-aware behaviour: when prompts include temporal pressure (e.g. “from 2025”), models should disclose their knowledge cut-off, refuse speculative imports, and suggest verified alternatives.
Second, anti-sycophancy behaviour: when a requested library or member closely resembles a known one (e.g., within small edit distance), the model should prefer clarification or substitution over uncritical compliance.
To make these behaviours auditable, we advocate for pre-decision steps: before generating code, the model explicitly verifies existence of all imports and members, and proceeds only if affirmed.
Future evaluations should report prompt-level hallucination, refusal, and calibration metrics to align measurements with the real-world triggers we uncover.

B.2
Experiment 1: Influence of Realistic User Language

In this experiment, we investigate how realistic variations in user descriptions of libraries and members influence the hallucination rates of LLMs.
Here, we detail the exact systematic analysis process (filtering and clustering details) and the prompts used to interact with the LLMs.

B.2.1
Systematic Analysis

We conduct a systematic analysis on all SRSE user questions, to determine common user descriptions of libraries.

Filtering
:
We first scrape all the SRSE questions and automatically filter them to retain only those related to the coding libraries.
Specifically, we kept questions that contain, or are tagged with, “library” or “framework”, and those tagged with a programming language, but not tagged with “books” or “ide”.
To validate this filter, we manually evaluated a random sample of 200 questions; the filter achieved precision = 0.95 and recall = 0.95, indicating that it is suitable for large-scale analysis.

Processing
:
After converting all questions to be lowercase, we extracted all
n
-grams (size 1–3) and remove any stopwords, using
CountVectorizer
from
scikit-learn

(
scikit learn 2025b
)
.
Any
n
-grams referring to highly specific technologies or concepts–such as “python”, “windows” or “online”–are removed, as could dominate clustering without being providing insights on the descriptive terms used.
We embed each remaining
n
-gram using the
all-MiniLM-L6-v2
sentence transformer model to obtain semantic vectors
(
Reimers & Gurevych 2019
)
.

Clustering
:
We cluster the embeddings with
AgglomerativeClustering
(using cosine distance and average linkage) from
scikit-learn

(
scikit learn 2025a
)
.
Clusters are ranked by the number of questions that contain one of their
n
-grams, retaining clusters that link to at least 20 questions.
After manually assessing relevance and labelling the clusters, we identified
nine
common user library-descriptions:
open-source
(
184
questions),
alternative
(
149
),
free
(
108
),
best
(
93
),
simple
(
77
),
easy
(
56
),
fast
(
56
),
lightweight
(
30
), and
modern
(
22
).
These cluster labels were used to construct realistic and representative prompt variants for our experiments.

Year-based Descriptions
:
Additionally, in our SRSE corpus, we found 23 library-related question titles that explicitly include a year.
Therefore, to model developers’ preference for recent releases, we also include year-based prompts that request libraries
“…from 20XX or later.”

B.2.2
Result Generation Prompts

For this experiment, we use different realistic user descriptions of libraries and members as the
{library directive}
, inserted into the prompt template defined in Appendix
B.1
.

We use the following directives when investigating
library name hallucinations

B.3
Experiment 2: Influence of User Mistakes

In this experiment, we investigate the extent to which user mistakes–either a one- or multi-character misspelling, or a fake library name/member–affect the hallucination rates of LLMs for both library names and members.
Here, we detail the exact mistake generation process and the prompts used to interact with the LLMs.

B.3.1
Mistake Generation

For this experiment, we need to generate the user mistakes (either one- or multi-character misspellings, or fake library names/members) to request the LLMs to use.
We use an LLM to do this.
In preliminary testing, we found that a reasoning enhanced LLM gave the most realistic errors, so we used OpenAI’s
o4-mini
.
We use a system prompt to ensure that correctly formatted lists are returned, and we generate incorrect library names and members on a per task basis.

For the
misspellings
, the LLM is provided with a library name or library member from the ground truth solution and examples of misspellings, and asked to generate typos with different levels of similarity.
The Levenshtein (edit) distance of each generated misspelling is then verified to ensure they are all within the specified ranges: edit distance of 1 for one-character misspellings; edit distance of 2–8 for multi-character misspellings.
For the
fake library names/members
, the LLM is instead given the task description and asked to generate realistic library names or library members that could plausibly match the intended functionality.
All generated mistakes are verified to be non-existent using our hallucination detection methods described in Section
3.6
.
