Abstract
. Tangled code changes—commits that conflate unrelated modifications such as bug fixes, refactorings, and enhancements—introduce significant noise into bug datasets and adversely affect the performance of bug prediction models. Addressing this issue at a fine-grained, method-level granularity remains underexplored. This is critical to address, as recent bug prediction models, driven by practitioner demand, are increasingly focusing on finer granularity rather than traditional class- or file-level predictions. This study investigates the utility of Large Language Models (LLMs) for detecting tangled code changes by leveraging both commit messages and method-level code diffs. We formulate the problem as a binary classification task and evaluate multiple prompting strategies, including zero-shot, few-shot, and chain-of-thought prompting, using state-of-the-art proprietary LLMs such as GPT-4o and Gemini-2.0-Flash. Our results demonstrate that combining commit messages with code diffs significantly enhances model performance, with the combined few-shot and chain-of-thought prompting achieving an F1-score of 0.88. Additionally, we explore embedding-based machine learning models trained on LLM-generated embeddings, where a multi-layer perceptron classifier achieves superior performance (F1-score: 0.906, MCC: 0.807). These findings are encouraging for the research community, as method-level bug prediction remains an open research problem, largely due to the lack of noise-free bug datasets. This research not only contributes a novel method-level perspective to the untangling problem but also highlights practical avenues for enhancing automated software quality assessment tools.

We utilize proprietary LLMs such as GPT and Gemini. In addition, we develop traditional machine learning models that operate on LLM-generated embeddings to explore lightweight, locally executable alternatives. Leveraging the capabilities of Large Language Models (LLMs) to detect tangled code changes, this study explores their effectiveness through the lens of three research questions.

RQ1:
Can zero-shot LLMs detect tangled code changes by using code diff and commit message?

We designed a classification-based approach that uses LLMs to detect tangled changes from method-level code diffs, both with and without the accompanying commit messages. Through experiments on our curated gold-standard dataset, we show that including the commit message significantly improves the model’s performance across multiple LLM variants, achieving the highest F1-score of 0.877 using gpt-4o.

RQ2:
How do different prompting techniques influence the effectiveness of detecting tangled code changes?

To answer this question, we investigate the impact of advanced prompting strategies, such as few-shot learning, chain-of-thought reasoning, and a hybrid combination, on tangled change detection. Our analysis demonstrates that LLMs can reason more accurately about change semantics when guided with structured prompts and exemplar-based context. Among these, chain-of-thought with few-shot prompting yields the highest performance of 0.883 F1-score with the ability to detect complex and ambiguous input.

RQ3:
How well can embedding-based machine learning models detect tangled code changes?

We utilized large language models (LLMs) to generate embeddings from commit messages and code diffs, which served as input for embedding-based classifiers. These models exhibit strong predictive capabilities, outperforming the results obtained in RQ1 and RQ2. Specifically, a Multi-layer Perceptron (MLP) classifier achieved the highest F1-score of 0.906, demonstrating the effectiveness of embedding-based representations for detecting tangled changes.

2.
Related Works

This section reviews prior research on tangled code changes, including their prevalence, impact, and methods for detection and untangling. It also examines related work on the application of large language models (LLMs) for analyzing and classifying text and source code. We also discuss how these studies have shaped the motivation and goals of our research.

2.1.
Tangled Changes

The issue of tangled changes, where commits combine unrelated or loosely related development activities, is well-documented in software engineering literature. Herzig and Zeller
(
Herzig and Zeller 2013
)
first used the term
Tangled Changes
and reported that up to 15% of bug-fixing commits across several open-source Java projects contained tangled change. Subsequent studies confirmed this prevalence. Tao and Kim
(
Tao and Kim 2015
)
found that tangled commits accounted for between 8% and 29% of revisions in open-source projects. Herbold et al.
(
Herbold et al. 2022
)
further validated the high occurrence and detrimental effects, showing that only 22% to 38% of the lines in a bug fix commit contribute to bug fixes. Kochhar et al.
(
Kochhar et al. 2014
)
analyzed 100 bug-fixing commits to find out the implication on tangling on bug localization. Their analysis showed that 28% of all files in bug fix commits do not have bugs.

The prevalence of tangled changes greatly affects the historical analysis of source code. By labeling all the modified methods in a bug-fixing commit as buggy methods, it harms the bug prediction models significantly
(
Herzig et al. 2016
;
Chowdhury et al. 2024
)
. Consequently, researchers focused on detecting and untangling commits.

Early techniques for untangling commits relied heavily on static analysis and heuristic rules. Herzig et al.
(
Herzig and Zeller 2013
)
introduced the concept of confidence voters that leverage file distance, change coupling, call graphs, and data dependencies to estimate whether two changes belong to the same task. Similarly, Tao and Kim
(
Tao and Kim 2015
)
used program slicing and pattern matching to cluster semantically related code edits, achieving 69% agreement with manual decompositions. Guo and Song
(
Guo and Song 2017
)
proposed CHGCUTTER, an interactive approach combining control and data dependencies to decompose composite changes while preserving syntactic correctness and enabling targeted regression testing. Muylaert and De Roover
(
Muylaert and De Roover 2018
)
applied program slicing on abstract syntax trees (ASTs) to isolate change sets based on their influence domains, offering finer granularity over line-based diffing.

Pârtachi et al. introduced Flexeme
(
Pâr

t

,

achi et al. 2020
)
with a
\delta
-NFG structure, which overlays name flows on program dependency graphs to better capture lexical cues. They used agglomerative clustering on the
\delta
-NFG to untangle commits using graph similarity. Heddle, the accompanying tool, demonstrated improved clustering accuracy (F1-score 0.81) and runtime efficiency over prior work.

Graph-based modeling has become a prominent paradigm due to its ability to represent complex code relationships. Shen et al.
(
Shen et al. 2021
)
proposed SmartCommit, which models diff hunks as nodes in a graph enriched with semantic links (hard, soft, refactoring, cosmetic) and employs partitioning to derive activity-oriented commit suggestions. Evaluation on industrial and open-source data showed a median decomposition accuracy of 71-84%. Chen et al.
(
Chen et al. 2022
)
and Xu et al.
(
Xu et al. 2025
)
extended this idea by integrating node attributes, such as token-level content and control/data flow, to perform attributed graph clustering and outperformed Flexeme by 7.8% and 8.2% accuracy, respectively. Xu et al. also introduced COMDET, a module to detect whether a commit is composite before applying the untangling process, addressing the risk of over-decomposition.

Fan et al.
(
Fan et al. 2024
)
proposed HD-GNN, a Heterogeneous Directed Graph Neural Network that addresses the inability of prior graph-based models to capture semantic dependencies without explicit code links. By leveraging hierarchical entity- and statement-level graphs, HD-GNN significantly improves untangling performance, achieving 25% and 19.2% gains for C# and Java, surpassing baselines like Flexeme and SmartCommit, with no loss in time efficiency.

Recent work increasingly leverages machine learning to learn to untangle patterns from data. UTANGO
(
Li et al. 2022
)
employs a graph convolutional network (GCN) to learn contextual embeddings of code changes, incorporating cloned code and surrounding context. It frames the task as supervised clustering, achieving 9.9% more accuracy than Flexeme. Dias et al.
(
Dias et al. 2015
)
and Liu et al.
(
Liu et al. 2018
)
proposed fine-grained tracking and clustering of code changes based on developer interactions and commit metadata. These methods emphasize high temporal and contextual resolution, using features such as change timing, file similarity, and developer behavior.

While prior approaches have yielded promising results at the file or statement level, the problem remains unaddressed at the method level, where many practical software maintenance and evolution decisions are made. Inspired by this, we investigate whether tangled code changes can be detected from method-level diff and the corresponding commit message.

2.2.
LLMs for Code Analysis & Classification

Large Language Models (LLMs) have demonstrated strong capabilities in both natural language understanding and source code analysis
(
Brown et al. 2020
;
Chen et al. 2021
)
. Their training on massive corpora of text and source code enables LLMs to generalize effectively to unseen inputs, often performing well in zero-shot settings
(
Kojima et al. [n. d.]
)
. This adaptability has prompted a surge of research on employing LLMs for text classification and code analysis tasks
(
Ahmad et al. 2021
;
Feng et al. 2020
)
. Building on these strengths, our study investigates the application of LLMs for detecting tangled code changes by jointly analyzing commit messages and code diffs.

Prompt design plays a critical role in optimizing LLM performance. Recent advancements in prompt engineering have introduced techniques such as zero-shot learning, few-shot learning, and chain-of-thought prompting
(
Wei et al. 2022
;
Brown et al. 2020
;
Wei et al. 2023
)
. Zero-shot learning requires only task instructions, making it the simplest method. Few-shot prompting augments the instruction with exemplar input-output pairs, effectively guiding the model’s response. Empirical studies have validated its improved performance across various tasks
(
Brown et al. 2020
)
. Chain-of-thought prompting further enhances reasoning by encouraging the model to decompose complex problems into sequential steps. This structured approach facilitates intermediate reasoning, which is particularly beneficial for nuanced classification problems
(
Wei et al. 2023
)
. Motivated by the empirical success of these techniques, we systematically evaluate their effectiveness in the context of tangled change detection.

LLMs are architected using Transformers, composed of encoder and decoder modules
(
Vaswani et al. 2017
)
. The encoder transforms input text into high-dimensional vector representations—embeddings—that preserve semantic relationships. These embeddings have been widely adopted for downstream classification tasks due to their capacity to encode nuanced contextual information
(
Petukhova et al. 2024
;
Keraghel et al. 2024
)
. In this work, we extend this utility to the domain of software engineering by generating embeddings from commit messages and code diffs. We then train machine learning models to classify these embeddings and assess their ability to distinguish between tangled and untangled changes. This constitutes the basis of our third research question.

In summary, this study is driven by three synergistic motivations: (1) the lack of fine-grained research on the implications of tangled changes at the method level, particularly in bug prediction tasks
(
Herzig et al. 2016
;
Chowdhury et al. 2024
)
; (2) the demonstrated capabilities of LLMs in analyzing textual and code artifacts through advanced prompting techniques; and (3) the semantic richness of LLM-generated embeddings as inputs for downstream classifiers. Together, these elements inform our investigation into LLM-based approaches for mitigating the adverse effects of tangled changes in software repository mining.
To the best of our knowledge, this is the first study to evaluate the effectiveness of LLMs in detecting tangled code changes within bug-fix commits, particularly at the method level.

3.1.
Data Collection

Detecting tangled code changes at the method level requires fine-grained historical data, specifically, method-level change histories with associated commit metadata. This level of granularity is essential for constructing a gold standard dataset that distinguishes between bug-related and non-bug-related changes, especially in tangled commits. To create such a dataset, it is essential to understand both what changed in a method and why it changed—information typically conveyed in commit messages. Equally important is knowing how many methods were modified in a given commit and tracing the complete history of each method, which allows us to determine whether a method was ever involved in a bug-fix. Without access to this full historical and semantic context, it becomes infeasible to reliably assess whether a method-level change was driven by bug fixing or whether the surrounding commit was tangled with unrelated modifications.

However, collecting such data at scale is challenging. Traditional version control tools like git log provide only file-level histories, and method-level tracking requires specialized tooling. Tools such as CodeShovel
(
Grund et al. 2021
)
and CodeTracker
(
Jodavi and Tsantalis 2022
)
have been developed to address this problem. These tools use structural analysis and similarity matching to trace a method across renames, moves, and edits over time. Among these, CodeShovel has been validated with industry developers and shown to perform robustly on large datasets
(
Chowdhury et al. 2024
)
, making it the tool of choice for our study. But this process is resource-intensive and time-consuming.

To overcome the high cost of method-level history extraction, we obtained a curated dataset from Chowdhury et al.
(
Chowdhury et al. 2024
)
, which includes the historical evolution of 774,051 Java methods across 49 popular open-source projects. Each method is linked to its full change history, represented as a sequence of diffs, and enriched with metadata including commit messages, timestamps, type of change, and authorship. Importantly, each method is annotated with the number of changed methods in the same commit and whether the commit is a bug fix commit. Whether the commit is a bug-fix commit or not is determined by analyzing the commit message using refined keyword-based heuristics. An example of method-level diffs for a bug-fix commit is presented in Figure
2
.

In summary, the dataset we utilized satisfies the critical requirements for method-level tangled change analysis: (1) high-fidelity change history per method, (2) commit-level bug fix annotations, and (3) indicators of tangledness based on the number and nature of modified methods per commit. These properties are indispensable for building accurate detection models and for evaluating their performance in real-world scenarios.

3.2.
Gold Set Creation

To enable the reliable evaluation of tangled change detection, a manually curated gold standard dataset was constructed. The gold set consists of 1,764 method-level change instances, labeled as either
Buggy
or
NotBuggy
, reflecting their actual relationship to bug-fixing activities. Figure
3
shows the dataset distribution.

Distribution of Gold dataset

Figure 3.
Distribution of Gold dataset
Distribution of Gold dataset

The construction of our gold standard dataset followed a stratified two-phase sampling procedure designed to ensure both label quality and representation of tangled change scenarios. In the first phase, we curated a balanced set of method-level changes that were clearly either buggy or not buggy, explicitly excluding any tangled commits. To mitigate potential biases introduced by method maturity, we excluded all methods with an age of less than two years, following the recommendation of Chowdhury et al.
(
Chowdhury 2025
)
. From the remaining method histories, we selected two distinct classes: (1) Buggy Methods, defined as methods that experienced at least one confirmed bug fix during their lifetime, with the corresponding bug-fix commit modifying only that single method, and (2) NotBuggy Methods, defined as methods that remained entirely untouched by any bug-fix commits throughout their version history. To maintain class balance, an equal number of samples were selected from both the Buggy and NotBuggy groups. Using the defined selection criteria, we identified 732 Buggy methods. Given the large pool of eligible NotBuggy methods, we randomly sampled 732 instances to match. As a result,
Phase 1
of our dataset construction yielded a total of 1,464 method-level examples.

While
Phase 1
ensured high-confidence labels, it did not reflect the complexity of real-world tangled change scenarios, where multiple unrelated modifications often co-occur in a single commit. To capture this nuance, we initiated a second phase focused on incorporating tangled examples. Here, we extracted additional method-level diffs from multi-method commits and conducted manual annotations to determine whether each method-level change was genuinely related to a bug fix (Buggy) or was incidental, such as refactorings or unrelated enhancements (NotBuggy). Each method was reviewed alongside its commit message to assess semantic alignment with bug-fixing intent, emphasizing structural corrections, error-handling logic, and domain-relevant repairs. To support consistency and reduce annotation error, we developed a dedicated user interface that enabled side-by-side inspection of code diffs and their corresponding commit metadata. In
Phase 2
, a total of 166 Tangled Buggy methods and 141 Tangled NotBuggy methods were collected through manual annotation.

The resulting dataset serves as a high-confidence benchmark for both training and evaluation of our detection approaches. Its composition—covering both untangled and tangled changes—enables robust measurement of precision, recall, and F1 under a range of prompting and modeling strategies.

3.3.
Prompt Preparation

The design of our prompt structure draws on recent advancements in prompt engineering that demonstrate the effectiveness of decomposing complex instructions into clearly scoped components
(
Brown et al. 2020
;
Wei et al. 2023
;
Zhou et al. 2023
)
. As prior work has shown, large language models (LLMs) are highly sensitive to prompt formulation, and performance can vary substantially based on how the task, instructions, and examples are framed
(
Liu et al. 2023
)
. To maximize reliability and adaptability across tasks, we designed a modular prompt template with three core components, shown in Figure
1
:

(1)

Instruction Section.
This component defines the LLM’s role and expectations. It is composed of four parts: (i) a role-based persona (e.g., “You are a Git commit review assistant”), which helps constrain the model’s responses by grounding its behavior and improves performance
(
Hu and Collier 2024
)
; (ii) a high-level task description; (iii) step-by-step behavioral guidance to structure the model’s reasoning
(
Wei et al. 2023
)
; and (iv) explicit output formatting requirements to reduce ambiguity and improve parseability.

(2)

Few-Shot Examples.
We provide two labeled examples illustrating correct classifications of method-level changes as either
Buggy
or
NotBuggy
. Few-shot prompting has been shown to significantly improve performance by enabling in-context learning, especially in code and software engineering tasks
(
Chen et al. 2021
)
. The examples (Figure
2
) are selected to highlight semantic differences between bug-fix-related and incidental changes within the same commit context, thereby helping the model to disambiguate tangled changes.

(3)

Query Input.
This includes the method-level code diff and its corresponding commit message.

Each research question required slight variations in prompt configuration—e.g., enabling or disabling few-shot examples, toggling chain-of-thought reasoning, or isolating input modalities (diff only vs. diff + message).

3.4.
Few-shot Examples

To provide the LLMs with examples of Buggy and NotBuggy diffs, two authors collaboratively selected a representative bug-fix commit containing one diff genuinely related to a bug fix and another unrelated change—a real instance of tangled code changes. These two fixed examples were consistently utilized to prime the LLMs in all experiments employing few-shot learning. These examples were selected to represent contrasting scenarios—one clearly indicative of a bug-fix and the other representing a refactor or performance-related change that does not qualify as a bug-fix, although both of the examples come from the same commit.

We intentionally limited the prompt to a single example per class (
Buggy
and
NotBuggy
), making it 2-shot prompting, to keep the input prompt within manageable token limits across different model families. Since method-level diffs can vary widely in length, the total prompt size is primarily driven by the input query itself, over which we have no control. Our only adjustable components are the instructions and the few-shot examples. As LLMs such as GPT-4 and Gemini-2.0 can have significant performance degradation when prompt length increases due to the inability to handle large context
(
Levy et al. 2024
;
Zhang et al. 2024
)
. Additionally, longer prompts incur higher computational and monetary costs, making token efficiency a practical concern. By limiting the number of in-context examples, we strike a balance between performance and resource usage. Future work could explore these trade-offs more systematically by varying the number of examples and measuring their impact on classification accuracy, especially in scenarios involving lengthy or complex code diffs.

The commit message from that particular commit that we used in the selected few-shot examples is: "
Fix bug in InetAddresses and performance problem in InternetDomainName (changed from regex to CharMatcher). This is intended as the last code update before release 06.
". For the negative example—not a bug-fix code change (NotBuggy)—we selected the code diff that merely replaced constant values with equivalent boolean literals, without altering the program’s logic or behavior. In contrast, the other code diff addressed a critical issue in the byte-to-hexadecimal conversion logic by correctly handling signed bytes using bit masking. This modification rectified a functional error and was therefore labeled as Buggy.

This strategy aligns with established practices in few-shot prompting
(
Brown et al. 2020
;
Min et al. 2022
)
, where concise and diverse instances are used to anchor the model’s reasoning prior to inference. In our setup, the examples provide contextual grounding by showcasing typical linguistic and structural patterns present in both buggy and non-buggy commits.

3.5.
Querying the LLMs

The three segments of the prompt are concatenated and formatted according to the input constraints of the respective LLM. The final prompt is submitted to the LLM, which generates an output classifying the change as either
Buggy
or
NotBuggy
. Outputs are reviewed and filtered automatically, if required, to ensure alignment with evaluation criteria.

3.7.
Evaluation Metrics

The goal of our experiments is to classify changes as either
Buggy
or
NotBuggy
. We evaluate model performance using standard classification metrics:

•

Precision:
Measures the proportion of correctly identified
Buggy
instances among all instances classified as
Buggy
.

•

Recall:
Measures the proportion of actual
Buggy
instances that were correctly identified.

•

F1-Score:
Harmonic mean of precision and recall, providing a balanced metric.

•

Accuracy:
Overall proportion of correctly classified instances.

•

Matthews Correlation Coefficient (MCC):
A robust metric accounting for true and false positives and negatives, especially useful in imbalanced datasets. It also shows whether the predictions are just random. MCC is 0 for random prediction and 1 for perfect prediction.

These metrics collectively provide a comprehensive evaluation of model effectiveness and robustness across both classes.

4.
Approach, Analysis & Results

In this section, we discuss the findings based on our three research questions. Research question-specific methodologies are also discussed here.

4.1.
RQ1: Can zero-shot LLMs detect tangled code changes by using code diff and commit
message?

We have both the commit message and the corresponding code diff available for analyzing the nature of code changes. While the diff captures the structural modifications to the source code, the commit message provides a natural language description of the developer’s intent. Large Language Models (LLMs) offer a powerful mechanism to detect semantic signals indicative of bug-fixing behavior across these modalities. By leveraging their ability to reason over structured and unstructured data (code + natural language)
(
Nam et al. 2024
;
Chew et al. 2023
)
, LLMs offer a promising alternative to traditional rule-based or static analysis techniques. Furthermore, using prompt-based inference avoids the need for task-specific fine-tuning, making the approach adaptable across repositories and languages. However, the effectiveness of LLMs is sensitive to input length, as inference cost increases with the number of tokens in the prompt. Given that both code diffs and commit messages can vary significantly in length, it becomes essential to evaluate whether both are necessary for effective detection or whether the code diff alone suffices. This research question seeks to empirically determine whether commit messages provide additive value beyond the code diff for detecting tangled (i.e., bug-related) changes.

We investigate two scenarios using large language models by designing tailored prompting strategies for binary classification of method-level diffs:

•

Diff-Only Detection
— The LLM is provided only with the code diff and instructed to assess whether the change represents a bug fix (
Buggy
) or not (
NotBuggy
). The prompt used for this experiment is: "
You are a Git commit review assistant. You excel at analyzing Java source code diffs. Given a Java source code diff, analyze it to determine if the changes are related to a bug fix. Examine the modifications carefully, looking for error-handling updates, logical corrections, exception-handling improvements, and other signs of bug-related changes. Output only a single word: ’Buggy’ if the changes indicate a bug fix, otherwise ’NotBuggy’.
"

•

Diff+Message Detection
— Both the code diff and the associated commit message are provided. The prompt instructs the model to assess semantic alignment between the message and code modifications to identify bug-fixing intent. The code change represents a bug fix (
Buggy
) or not (
NotBuggy
). The prompt used for this experiment is:
"
You are a Git commit review assistant. You excel at analyzing Java source code diffs and commit messages. Given a Java source code diff and its commit message, analyze both to determine if the changes align with the commit message and indicate a bug fix. Assess the relevance between the commit message and code modifications, identifying error-handling updates, logical corrections, exception-handling improvements, and other signs of bug-related changes. Output only a single word: ’Buggy’ if the changes indicate a bug fix, otherwise ’NotBuggy’.
"

4.2.
RQ2: How do different prompting techniques influence the effectiveness of detecting tangled code changes?

The effectiveness of LLMs highly depends on the input prompt, and the success of different prompting techniques is proven in various studies
(
Wei et al. 2022
;
Brown et al. 2020
;
Wei et al. 2023
)
. This research question investigates how different prompting techniques—namely
few-shot learning
,
chain-of-thought prompting
, and a hybrid approach combining both-impact the classification performance of LLMs.

We evaluated
gpt-4o
and
gemini-2.0-flash
under each prompting technique. The
gpt-4o-mini
model was excluded from this analysis for two reasons. First, as established in our RQ1 results,
gpt-4o
consistently outperforms
gpt-4o-mini
, making the latter redundant for further evaluation within the same model family. Second, the prompting techniques employed in this experiment involve substantial token usage—both in input and output—rendering the use of a cost-sensitive proprietary model like
gpt-4o-mini
impractical.

The experimental design involves binary classification of method-level code changes into
Buggy
or
NotBuggy
using commit diffs and messages. The performance was measured using standard evaluation metrics: Accuracy, Precision, Recall, F1-score, and Matthew’s Correlation Coefficient (MCC). We implemented the following prompting configurations:

•

Few-shot Prompting
— The prompt includes labeled examples of buggy and non-buggy changes to guide the model toward correct classification. The instruction prompt remains the same as RQ1.

•

Chain-of-thought Prompting
— The model is instructed to explain its reasoning before outputting the classification result. The last line of the instruction prompt is replaced with the following: "
Think step by step, explain your reasoning, and conclude with **Buggy** if the changes indicate a bug fix; otherwise, conclude with **NotBuggy**.
". No examples are provided with the prompt.

•

Chain-of-thought + Few-shot Prompting
— A combination of the above two techniques, providing both examples and a reasoning pathway.

4.3.
RQ3: How well can embedding-based machine learning models detect tangled code changes?

This research question explores the viability of embedding-based machine learning (ML) models for detecting tangled code changes. Unlike prompt-based approaches reliant on in-context reasoning of LLMs, this method leverages the embeddings—vector representations of the input data from the commit messages and code diffs—to train supervised classifiers. The key objective is to assess whether these embeddings, when used as features in ML models, can achieve competitive performance in detecting bug-related code changes. This experiment is motivated by the previous studies where embedding-based models performed well and, in some cases, outperformed prompt-based techniques
(
Petukhova et al. 2024
;
Keraghel et al. 2024
;
Kokkodis et al. 2025
)
.

The methodology employed for this research question diverges from that of the preceding research questions and the process illustrated in Figure

. Specifically, this experiment omits the complex prompt engineering component. Instead, only the core query, comprising the code diff and commit message, is retained and directly input to the LLM to generate fixed-length vector embeddings for downstream classification. 5.
Discussion

This study presents a comprehensive evaluation to detect tangled code changes using LLM at the method level, a granularity that is underexplored yet highly relevant to real-world software maintenance. The findings affirm that LLMs can detect tangled changes with substantial accuracy. Using both the commit message and the diff yields better results than diff-only detection using zero-shot detection with LLM. Notably, the
gpt-4o
model achieved an F1-score of 0.877 using both code diffs and commit messages (
RQ1
). The performance further improved to 0.883 under a hybrid prompting regime combining few-shot learning with chain-of-thought reasoning, surpassing the individual use of few-shot and chain-of-thought (
RQ2
). Furthermore, the embedding-based machine learning models evaluated in
RQ3
introduce a scalable alternative for environments where online LLM inference is impractical. The MLP classifier, using 768-dimensional embeddings derived from LLMs, achieved a peak F1-score of 0.906, surpassing the prompt-based approaches.

A critical insight from RQ1 and RQ2 is the additive value of commit messages. While code diffs encapsulate syntactic and structural changes, commit messages provide essential semantic cues reflecting developer intent. This combination enables LLMs to overcome superficial syntactic signals and engage in deeper semantic reasoning. The chain-of-thought examples demonstrated that structured reasoning allows models to correctly classify ambiguous cases, which zero-shot or few-shot alone often misclassify. On the other hand, the significant success of embedding-based models indicates that vectorized semantic representations of commits can encode sufficient contextual information to enable robust tangled change detection, even without elaborate prompt engineering.

The findings of this study highlight the growing potential of LLM-based methods to advance fine-grained software analysis tasks. By addressing the longstanding problem of tangled code changes through both prompt-driven inference and embedding-based classification, this work contributes novel empirical evidence supporting the viability of LLMs as both reasoning engines and feature extractors in software engineering.

Our findings offer impactful contributions to the ongoing evolution of software engineering research and practice, particularly in method-level bug prediction. By empirically demonstrating that LLM-based models, when guided by careful prompting or embedding-based learning, are capable of accurately identifying tangled code changes at the method-level, this work opens new avenues for removing noise from the method-level bug prediction dataset. Moreover, the methodology we propose is not limited to methods alone. Other granularities, such as class-level, file-level, or even line-level code elements, can benefit from similar LLM-instructed workflows. Thus, this method can remove noise created by tangled changes for all granularities, allowing the creation of high quality dataset for bug prediction.

There is an ongoing debate about the effectiveness of large language models (LLMs) in software engineering. Some studies highlight limitations such as hallucinations—plausible but incorrect outputs—occurring in both code-related and other tasks
(
Liu et al. 2024
;
Yao et al. 2024
;
Tie et al. 2024
;
Ji et al. 2023
;
Ye et al. 2023
)
, as well as concerns over data leakage and reproducibility
(
Sallou et al. 2024
)
. In contrast, other research demonstrates the potential of LLMs for tasks like code analysis and generation
(
Sghaier et al. 2025
;
Jaoua et al. 2025
;
Nascimento et al. 2024
)
. Contributing to this discussion, our study finds LLMs to be effective for the specific task of tangled change detection in software engineering research.

5.1.
Threats to Validity

Construct Validity
: The definition of “tangled change” and its manual annotation as “Buggy” or “NotBuggy” may introduce subjective bias. While clear criteria and a user interface were used to guide annotators, subjective judgment and semantic ambiguity in commit messages may have influenced labeling outcomes.

External Validity
: The study used a gold-standard dataset based on Java projects curated via CodeShovel. Generalization to other programming languages, project types, or commit styles may require adaptation of prompts and retraining.

Internal Validity
: The embedding-based approach used only Gemini’s proprietary embedding model. Evaluating embeddings from diverse LLMs could yield more generalizable insights.

Conclusion Validity
: All models were evaluated using standard metrics, including Accuracy, F1-score, and Matthews Correlation Coefficient (MCC), and we used both held-out test data and Leave-One-Out cross-validation to reduce evaluation bias. Nevertheless, unseen confounding variables or dataset-specific characteristics may still have influenced the observed performance trends.

6.
Conclusion

In this study, Large Language Models (LLMs) were employed to identify tangled code changes at the method level, with the aim of formulating a technique to produce high-quality bug datasets by reducing noise. By analyzing code diffs and commit messages, and experimenting with various prompting strategies and embedding-based classifiers, we demonstrated that LLMs can effectively distinguish bug-related changes from others.

Prompting strategies combining chain-of-thought reasoning with few-shot examples led to notable performance gains, while embedding-based classifiers, particularly Multi-layer Perceptrons, achieved the highest accuracy and F1-scores. These results suggest that LLMs can serve as both interpretable inference engines and feature generators for downstream learning tasks.

While our study demonstrates the utility of LLMs, the use of proprietary models (e.g., GPT-4o, Gemini) may limit accessibility. Future work should explore fine-tuning or prompting of open-source LLMs (e.g., Code LLaMA, StarCoder) for equitable deployment in industry and academia. Also, integrating these models into development tools (e.g., Git hooks, IDE plugins) to provide real-time feedback on committing unrelated code changes could be highly beneficial. Furthermore, studying the longitudinal impact of such feedback on software quality presents an interesting avenue for future research.
