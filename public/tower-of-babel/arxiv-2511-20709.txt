DualGauge : Automated Joint Security–Functionality Benchmarking for Secure Code Generation
Abhijeet Pathak 1 , Suvadra Barua 1 , Dinesh Gudimetla 1 , Rupam Patir, Jiawei Guo, Hongxin Hu, Haipeng Cai

Abstract
Large language models (LLMs) and autonomous coding agents are increasingly used to generate software across a wide range of domains. Yet a core requirement remains unmet: ensuring that generated code is secure without compromising its functional correctness. Existing benchmarks and evaluations for secure code generation fall short—many measure only vulnerability reduction, disregard correctness preservation, or evaluate security and functionality on separate datasets, violating the fundamental need for simultaneous joint evaluation. We present DualGauge , the first fully automated benchmarking framework designed to rigorously evaluate the security and correctness of LLM-generated code in unison. Given the lack of datasets enabling joint evaluation of secure code generation, we also present DualGauge-Bench , a curated benchmark suite of diverse coding tasks, each paired with manually validated test suites for both security and functionality, designed for full coverage of specification requirements. At the core of DualGauge is an agentic program executor, which runs a program against given tests in sandboxed environments, and an LLM-based evaluator, which assesses both correctness and vulnerability behavior against expected outcomes. We rigorously evaluated and ensured the quality of DualGauge-Bench and the accuracy of DualGauge , and applied DualGauge to benchmarking ten leading LLMs on DualGauge-Bench across thousands of test scenarios. Our results reveal critical gaps in correct and secure code generation by these LLMs, for which our open-source system and datasets help accelerate progress via reproducible, scalable, and rigorous evaluation.

In this paper, we develop

fully automated

Given an pure-natural-language prompt as functional specification and access to a target model, the system (1) generates the model’s code output for the prompt, (2) executes it in a sandboxed environment against functional and security test suites, and (3) evaluates the execution results against both test suites to report test pass rates and joint correctness-security metrics,

Achieving these capabilities face
multiple challenges

First, for (2), the system needs to (
C1

Second, for (3), the system needs to (
C2
) check if a security test passes or not. However, the oracle for secure behaviors is hardly expressible via a readily comparable program output as for functional testing; thus, actual security behaviors need to be captured and compared to
ground-truth ones at high/semantic level.

To deal with these challenges,
DualGauge
features an

and an
LLMs-based evaluator

The execution engine compiles and runs the model-generated code within isolated containers while tracing covered statements, and interacts with an LLM-based agent to iteratively resolve any runtime issues (for example, installing missing dependencies or adjusting environment configurations) so that the tests can be carried out to completion, addressing
C1

The evaluator then inspects the program’s outputs and behaviors, determining for each test case whether the expected functional output or security condition is satisfied. For security testing, the coverage trace and original program are fed to multiple LLMs for
semantic

Given the lack of benchmarks that support the joint evaluation in
DualGauge

DualGauge-Bench

Each task/prompt is paired with both a functional test suite that checks for correct behavior against the functionality specification, and a security test suite that checks for the absence of insecure behaviors relevant to that task against secure coding principles (e.g., OWASP practices
[
28

and CERT standards
[
34
]
).
Importantly, both suites are built to be thorough and coverage-driven, covering all normal and corner/edge cases of functional and security behaviors as per the prompt as a requirements specification.
We constructed these test suites through a human-and-LLM co-creation process—leveraging multiple LLMs to generate candidate tests, then refining and amending these with human expertise of multiple raters—to ensure each suite is both comprehensive and semantically accurate, following a
specification-based testing
paradigm. This dataset design and curation process allow it to be agnostic to programming languages.

We extensively validated the accuracy of
DualGauge
against a manually created ground truth on automated execution and test-outcome evaluation.
Our results show that the system is effective, with 95.08% precision, 84.67% recall, and an F1 score of 89.58 for the agentic executor, and 90.54% precision, 77.91% recall, and an F1 score of 83.75 for the LLMs-based evaluator.
We also rigorously validated the quality of
DualGauge-Bench

Using
DualGauge
and
DualGauge-Bench
, we conducted the first holistic joint-evaluation of
21
prominent LLMs for secure code generation, including frontier LLMs and open-source models of various sizes, token limits, and quantization. We tested each model on all the tasks in our benchmark, resulting in thousands of executed code generations and security checks. The results reveal substantial gaps, variability, and trade-offs:

•

Dramatic security-functionality gap
: The LLMs achieve strong functional correctness but fail dramatically on joint evaluation, revealing substantial decline when both requirements must be satisfied simultaneously.

•

Security doesn’t scale with model size
: While functional performance improves with model size, security plateaus beyond moderate parameter counts, with naive scaling yielding diminishing security returns.

•

Counterintuitive quantization effects
: Certain quantization methods unexpectedly improve security over full-precision baselines while others degrade it, demonstrating non-monotonic impacts on security.

•

Non-monotonic reasoning effects
: Medium reasoning levels achieve optimal performance while excessive reasoning degrades results, suggesting overthinking can introduce vulnerabilities or optimize for functionality at the expense of security.

•

Instruction tuning limitations
: Standard instruction tuning improves functional correctness modestly but reduces the joint measure substantially, indicating optimization for task completion inadvertently compromises security.

•

Inconsistent security handling
: The studied models pass individual security tests at moderate rates but rarely satisfy all security requirements simultaneously, correctly handling one concern while failing on another for the same program generated.

By unifying the measurement of functional correctness and security within a single framework, we establish a rigorous foundation for trustworthy code generation, complementary to existing relevant studies and datasets. In summary, our key contributions include:

II
Background and Related Work

Modern LLMs and coding agents generate source code by translating natural language prompts—typically serving as
functional specifications
—into (supposedly) syntactically and semantically coherent programs. These prompts may request specific functionality (e.g., “write a function to validate email addresses”), and the generated output is expected to satisfy this specification both in terms of behavior (functional correctness) and robustness (security). Whether this expectation is met, however, needs to be evaluated.

Evaluating LLM/agent-generated code can be achieved by executing the code in a controlled environment and validating its
actual outputs/behaviors
against predefined test cases. For functional correctness and security, these
runtime
test cases fall in two categories, respectively: (1)
functional tests
, which check whether the code satisfies the intended functional behavior, and (2)
security tests
, which assess whether the code is resistant to inputs that exploit known vulnerability patterns. Each test case consists of an input and an associated
oracle
—the
expected output/behavior
—that defines whether the test passes or fails.

Accordingly, a benchmark for LLM/agent-based code generation would comprise: (1) a natural language code-generation prompt, (2) a runtime test suite, and, optionally, (3) a sample reference implementation. These benchmarks enable reproducible evaluations of different models, either manually or automatically. If automated, the evaluation would involve not only generating the programs as per (1), but also
building
them and setting up the environment in which the programs run.

Other efforts like LiveBench

III
DualGauge-Bench

As we summarized earlier (
\lx@sectionsign
II-B
), all current evaluations/studies on secure code generation fall short of

[

An intuitive reason lies in the lack of a benchmark that enables joint evaluation (Table
I
), for which a key property is dual-test modality—not only should both functional and security tests be included, both types of tests should be paired for each code-generation prompt (i.e., the coding task’s specification).

We create
DualGauge-Bench
to address the dataset and evaluation needs, whose design is guided by three primary objectives: (1) priming language-agnosticism in design, evidenced by its
dataset composition
(
\lx@sectionsign
III-A
),
(2) enabling joint evaluation, achieved in its
dataset creation
process (
\lx@sectionsign
III-B
),
and
(3) enforcing dual-test coverage, resulting from
coverage enforcement
(
\lx@sectionsign
III-C
)
in that process.

III-A

Dataset Composition

DualGauge-Bench
is a suite of benchmarks each consisting of three essential items:

•

Item 1: Code Generation Prompt
: This is a natural language text description of a functional requirement. It serves as the primary input to the LLM, specifying what code the model should generate (e.g., ”Write a function to validate a user’s password”) in terms of targeted functionalities. This prompt does not include any code snippet.

•

Item 2: Security Test Suite
: This is a collection of test cases designed to validate the security and resilience of a program that implements the requested functionality per the prompt. Each test case consists of an input (e.g., a malicious string) and an expected security behavior (e.g., ”the program must not call injected command”).

•

Item 3: Functional Test Suite
: This is a parallel collection of test cases designed to validate the functional correctness of the program. Each test case consists of an input (e.g., ”a valid password”) and a specific expected output (e.g., ”True”).

Notably,
DualGauge-Bench
is designed to be agnostic (not tied) to a specific programming language.
The prompt (Item 1) just specifies functional requirements in natural language, since we focus on code generation, not code completion,
The test suites are developed to include test inputs and expected outputs/behaviors, solely based on the requirements specification.
This code/implementation-independent design allows a single benchmark item to be used to evaluate code generated in any language, making the benchmark highly versatile and extensible.

III-B

Data Creation

To achieve high data quality and test coverage, we start by sourcing diverse coding requirements;
then, we employed a human-AI collaborative co-creation workflow, leveraging AI to generate a wide breadth of test scenarios and human expertise to validate, calibrate/refine, and amend
test cases.

Source and Preprocessing of Prompts (Item 1).

To build
DualGauge-Bench
,
we first need the prompts to form Item 1, which we curated from different existing relevant
datasets, including
CodeGuard+
[
8
]
and
securityEval
[
35
]
.
We source these prompts from existing, diverse benchmark datasets to (1) ensure broad coverage of real-world coding tasks across functionality domains. These prompts (2) have been widely used and validated in prior evaluations, offering a representative, task-diverse foundation. Reusing them (3) promotes comparability, reproducibility, and alignment with established benchmarks, while allowing our contributions to focus on augmenting each prompt with high-quality security and functionality test suites.

Unfortunately, existing relevant datasets do not include pure-natural-language prompts.
Thus, they required significant preprocessing to meet our language-agnostic design goal.
For datasets that already included natural language prompts, our process involved stripping all programming-language-specific elements, such as partial code snippets or function signatures, to retain only the pure functional description. For datasets that only provided partial code samples (e.g., in securityEval
[
35
]
), we reverse-engineered the code-generation prompts by manually abstracting the code’s functionality into a natural language requirement.
The result is a unified set of 154 prompts that are purely descriptive and language-agnostic.

Security Test Suite Creation (Item 2)
.
We adopted a human-in-the-loop co-creation pipeline that blends the generative power of multiple LLMs with expert human validation.
For each code-generation prompt (Item 1), we first prompt three state-of-the-art LLMs (GPT-5, Claude-4.5, and DeepSeek-R1) to generate the initial security test suite, given their broad, general knowledge about code insecurity and common exploits.
Each model is instructed to produce diverse inputs that intentionally probe for potential security weaknesses in any implementation of the prompt,

against
established secure coding guidelines (e.g., OWASP practices
[
28
]
and CERT standards
[
34
]
)
We also ask the LLMs to generate the
expected security behavior as test oracle
,
informed by
those principles—unlike for functional tests, the oracle for a security test often cannot be expressed as (expected) explicit program outputs.
The prompt used to get the LLM suggestions can be found in Appendix
A-B
.

After collecting the LLM-generated test cases, we manually analyze and consolidate the best of three LLMs to form a rigorous and targeted suite. This involves: (1) validating whether each input meaningfully tests security-relevant behavior in the context of the prompt; (2) ensuring the expected behavior is clearly and correctly defined while consistent with the associated inputs; (3) removing redundant, trivial, or incorrect test cases; and (4) curating/authoring additional tests that maximize coverage across distinct security scenarios.
To mitigate human biases, two of the authors (with 2 5 years of software development and security experiences) each independently conducted these four steps, followed by a negotiated agreement procedure to resolve disagreement until reaching consensus (and further updating relevant tests), for each benchmark.

These test cases are designed not to detect specific known vulnerabilities, but rather to comprehensively cover common insecure coding patterns, misuse of APIs, edge-case handling, input sanitization, and other categories of secure coding principle violations—aligning with a ”shift-left” approach to security.
For example, if the functional requirements (Item 1) involve web output or UI rendering, tests for cross-site scripting (XSS) are included, injecting ¡script¿ tags or other malicious payloads to ensure they are correctly escaped or rejected.
The overarching security coverage criterion is that all high-risk areas (as per the functionality domain)
have at least one test guarding them, analogous to a risk-based coverage approach.

In the end of this process, we curated 1 to 18 (6.29 for each benchmark on average) security tests for the 154 benchmarks in
DualGauge-Bench
.

Functional Test Suite Creation (Item 3)
.
For each code-generation prompt, functional tests are created by a similar LLM-human co-creation process to that for security test-suite curation above, except for two differences.
First, the LLMs and human experts are guided by
specification-based testing
paradigms (e.g., following black-box testing methods like boundary value analysis and equivalence-class partitioning).
Second, the overall coverage criterion is
requirements coverage
: the tests are created to satisfy the condition that every requirement from the specification is exercised by at least one test.
Normal/typical operations with valid inputs, corner/edge cases (e.g. empty inputs, special characters), error conditions (missing parameters, exception scenarios), and various input formats and data types are all considered.
For example, if a requirement involves numeric input, the LLM might suggest boundary tests (min/max values, zero, negative numbers), and if the input is textual, it might suggest tests with special characters or very long strings – some of which a human tester might initially overlook.
Third, associate with each functional test input is the
expected output serving as the oracle
of the test.
The prompt used to get the LLM suggestions can be found in Appendix
A-B
.

In the end of this process, we curated 1 to 43 (6.49 for each benchmark on average) functional tests for the 154 benchmarks in
DualGauge-Bench
.

III-C

Coverage and Diversity

Following the data creation process, our resulting benchmark suite meets the
dual-test coverage
goal in two ways:
(1) both security and functional tests are included for, and paired with, each functional specification (the code-generation prompt),
and (2) both security and functional test suites each have its own strong coverage criterion enforced,
covering diverse security and functionality scenarios—although both under the governance of full
specification coverage
.
Moreover, in terms of
programming language coverage
,
DualGauge-Bench
is designed to be language-agnostic, as justified earlier.

Our benchmark suite also spans a wide spectrum of real-world
functionality domains
, including file and filesystem operations, network and web application programming (e.g., HTTP endpoints and REST APIs), database operations and queries, cryptographic operations, system administration and privilege management, data processing and transformation, and user input handling and validation.

Unlike most related benchmarks,
DualGauge-Bench
further captures varying levels of

. It includes both

IV
DualGauge

The benchmark suite curated provides the foundation for our evaluation—what to test. In this section, we operationalize this benchmark by developing
DualGauge
, a fully automated, end-to-end benchmarking system that provides the how.

IV-A

System Overview

The primary objective of
DualGauge
is to evaluate LLMs in a fully automated, end-to-end manner with no manual involvement. This allows for the simultaneous assessment of both functional correctness and security, a critical need for holistic evaluation. Furthermore, the system is designed for extensibility and continuous integration, enabling our static set of benchmarks to be converted into a dynamic ”live” pipeline. This design allows new models and test cases to be added seamlessly, ensuring the benchmark remains relevant as LLM capabilities evolve.

The workflow of the
DualGauge
system, as illustrated in Figure
1
. begins with two primary inputs: (1) the target LLM to be evaluated and (2) our benchmark suite from
DualGauge
-Bench.

With these inputs, the first phase: Sample Generation (Section
IV-B
), feeds each of the 154 benchmark prompts to the target LLM, compelling it to generate
k
(e.g.,
k=10
) complete, executable code candidates for each prompt. This collection of
154\times k
programs serves as the primary intermediate artifact.

These programs are then passed to our core evaluation engine, which is the second phase: Agentic Executor (Section
IV-C
).
First, it takes each program and its corresponding test inputs, attempts to run them in an isolated environment, and resolves any execution or dependency errors, ultimately producing a raw program output and a statement-coverage trace. These execution results are then fed to the third phase, the oracle (Section
IV-D
), which acts as the judge. The oracle compares the executor’s outputs against the benchmark’s “expected output” (for functional tests) or “expected security behavior” (for security tests) to produce a set of binary pass/fail judgments.

Finally, these judgments are consumed by the third component: Aggregation and Dashboard (Section
IV-E
), which processes them to compute the final system output: a set of three quantitative scores (e.g.,
pass@k

IV-B

Phase 1: Sample Generation

The
DualGauge
pipeline begins with a model-facing generation stage that produces standardized candidate solutions for each benchmark problem. This stage acts as an abstraction layer over large language models (LLMs), ensuring that differences in vendor APIs or interface conventions do not affect downstream processing. Through a unified interface—implemented for each model via a small adapter that wraps the model’s native API—any supported LLM can be invoked in the same way. Given a benchmark prompt, the system retrieves
k
independently sampled outputs that capture the model’s raw coding behavior. To maintain comparability across models, sampling parameters such as temperature, top-p, and maximum tokens are fixed and applied uniformly unless the benchmark protocol specifies otherwise. This design ensures that subsequent correctness and security evaluations reflect genuine model differences rather than discrepancies in how models were queried.

Because LLM outputs often mix code with surrounding explanations or formatting, the generation stage includes a lightweight code-extraction step that isolates the program the model intends to provide. This extraction is deliberately minimal and preserves the code exactly as generated, leaving all issues arising from incomplete or malformed samples to be handled later in the execution stage. The output of this generation layer is a set of normalized code candidates and associated metadata that serve as the starting point for the agentic execution phase.

IV-C

Phase 2: Agentic Executor

After the generation layer produces the candidate programs, each sample enters the agentic execution stage. This stage is guided by an LLM agent that examines the raw code, determines how it should be executed, constructs a single execution script, and manages a bounded repair loop that attempts to make the sample runnable without altering the model’s solution. The goal is to give each candidate a consistent opportunity to execute while preserving the integrity of the generated code.

The process begins with the agent analyzing the code to determine the appropriate execution pattern. Some samples correspond to direct execution programs that can be launched immediately, for example by providing input as command line arguments or through standard input. Other samples are service oriented programs, such as Flask applications or other server style code, which must be started first and then fed input through an external request such as a curl call. Regardless of the pattern, the agent infers how the program expects to receive input by inspecting the code, including how arguments are parsed, how endpoints are defined, or how data is consumed.

Based on this inference, the agent generates a single execution script tailored to the sample. For direct execution programs, the script runs the program and formats the benchmark’s test inputs according to the expectations inferred from the code. For service oriented programs, the script starts the service, waits for it to become responsive, and then delivers the test input through an appropriate request while again respecting the format implied by the candidate. Even when the model outputs only a single file, the agent constructs whatever minimal wrapper logic is necessary to run the program correctly.

Once the script is created, the system prepares an isolated environment and executes the script on the first functional test case. If the run fails, the error output is returned to the agent. The agent must then determine the cause of the failure, distinguishing among three possibilities: environment issues, script issues, or code issues. Environment issues involve missing dependencies or system tools and can be resolved by modifying the environment setup, such as adding a pip install or apt get command. Script issues arise when the wrapper or invocation logic is incorrect, for example using the wrong entry point or sending misformatted input. These are resolved by adjusting the generated execution script. Code issues indicate that the underlying program produced by the model is fundamentally broken, and in such cases the agent does not attempt to modify the code since candidate code cannot be altered.

If the agent identifies an environment or script issue, it produces a minimal patch, and the corrected script or environment is executed again. This diagnosis and repair loop continues for a bounded number of attempts. If the sample still cannot run, it is marked as non executable. If the run succeeds, the executor then checks whether the script captured the program output correctly. A program may execute without errors but fail to place output in the expected location or channel. If this validation fails, the agent adjusts the script and the test is repeated. Only when the program both executes successfully and reports its output in the expected manner is the sample considered stabilized.

Once stabilization is achieved for the first functional test case, the same environment and execution script are reused for all remaining test inputs associated with that benchmark item including security tests. Subsequent tests do not require further agent intervention. Any new failures in later tests are treated as failures of the candidate code itself rather than failures of the script or environment, so the agent does not attempt additional repairs. During these runs, the system collects outputs and runtime traces, which are later used by the evaluator to determine functional correctness and security outcomes.

IV-D

Phase 3: LLMs-Based Evaluator

After the execution layer produces program outputs and runtime traces, each result enters the evaluation stage. This stage is guided by an LLM-based evaluator that determines whether the candidate program’s behavior satisfies the expected functional correctness and security requirements. The goal is to produce accurate, semantically-aware pass/fail judgments for both test suite types while handling the inherent complexity of security behavior assessment.

The evaluation process operates in two parallel but distinct modes depending on test type. For functional testing, the evaluator performs a direct comparison between the captured program output and the expected output defined in the benchmark’s functional test suite. This straightforward matching yields a binary pass/fail judgment for each functional test case.

For security testing, the evaluator employs a more sophisticated, LLM-based semantic analysis. Unlike functional tests where correctness can be determined by output matching, security properties concern program behavior—whether vulnerable patterns were avoided, whether sanitization occurred, or whether dangerous operations were prevented. The evaluator is provided with comprehensive context: the program’s source code, the execution trace from Phase 2, any error messages or exceptions, and the expected security behavior from the benchmark’s security test suite. Using this context, the evaluator determines whether the program’s actual execution behavior aligns with the expected secure behavior.

A critical challenge in security evaluation is knowledge gaps. When candidate code uses unfamiliar libraries, frameworks, or domain-specific APIs, even capable LLMs may lack the contextual knowledge needed to accurately assess security behavior. To address this limitation, the evaluator incorporates a two-stage knowledge gap resolution process. First, all symbols from the candidate code—including imports, function calls, classes, and method invocations—are extracted and presented to the evaluator LLM. The evaluator is prompted to identify any symbols it does not confidently recognize. If knowledge gaps are detected, a second, stronger LLM model with web search capability is invoked to retrieve detailed documentation and semantic explanations of the unknown symbols. This additional context is then incorporated into the final evaluation prompt, ensuring the evaluator possesses sufficient understanding of specialized or domain-specific functionality.

This two-model architecture balances efficiency and accuracy: a lighter evaluator model handles the bulk of straightforward assessments, while a more capable resolver model with search capabilities handles edge cases requiring external knowledge. The system maintains deterministic behavior through temperature settings near zero, and employs retry logic with exponential backoff to handle transient API failures.

The output of the evaluation stage is a structured set of test results containing, for each test case, the test input, expected behavior or output, observed behavior, and a binary verdict (PASS/FAIL). These judgments are collected and passed to the aggregation layer, completing the automated evaluation pipeline without requiring any manual inspection or validation.

Dataset Quality of

Procedure.

To assess the quality and reliability of dataset, we conduct a comprehensive agreement study using a negotiated inter-rater protocol. Each benchmarked task contains two coverage-guided test suites—functional and security—each consisting of multiple test cases. Independent raters evaluate a representative subset of test cases to determine whether:

•

Test inputs are valid and well-formed with respect to the associated code-generation prompt.

•

Each test case’s expected behavior/output is semantically correct and meaningful.

•

The test suite as a whole includes all important normal and edge cases or omits any critical behaviors.

We measure inter-rater agreement using Cohen’s
\kappa

Therefore, security must be tested explicitly after quantization rather than assuming monotonic degradation.

GPT-5 shows a non-monotonic relationship between reasoning effort and security performance. Minimal reasoning achieves 48.05% pass@1 and 9.09% secpass@1. Medium reasoning improves both metrics substantially to 50.65% pass@1 and 11.69% secpass@1, with SPR reaching 57.07%, the best joint performance. However, high reasoning fails to improve further. While pass@1 increases slightly to 51.95%, secpass@1 remains at 11.69% and SPR drops to 54.8%. This suggests an optimal reasoning budget exists beyond which additional computation becomes counterproductive. Excessive reasoning may cause overthinking that introduces vulnerabilities, dilutes focus on security constraints, or optimizes for functional elegance at security’s expense. Interestingly, low reasoning achieves 52.73% SPR despite lower pass@1 (42.21%), indicating that moderate reasoning may balance security and functionality more effectively than either minimal or maximal reasoning.

DeepSeek’s Reasoner mode shows modest but consistent improvements over Chat mode. Pass@1 increases from 42.86% to 44.81%, secpass@1 from 6.49% to 7.14%, and SPR from 36.95% to 37.56%. However, a counterintuitive trade-off emerges: while Reasoner mode improves joint metrics, aggregate Pass Rate decreases from 76.3% to 70.9%. This suggests reasoning helps tackle challenging problems requiring deeper analysis while causing failures on simpler problems. The mechanism may introduce overhead or complexity that interferes with straightforward code generation, or second-guess correct initial instincts.

Most striking is Qwen3-8B’s thinking mode, which degrades nearly all metrics. Pass@1 drops from 38.96% to 35.29%, PR falls from 70.2% to 60.7%, and SPR declines from 31.89% to 29.8%. Only secpass@1 shows marginal improvement (3.90% to 4.58%), overshadowed by functional regression. This suggests smaller models may lack sufficient capacity to perform effective multi-step reasoning while maintaining code quality, or that poorly calibrated reasoning mechanisms introduce noise rather than insight.

These results demonstrate that reasoning capability alone is not a solution for secure code generation. Effectiveness depends critically on implementation quality, model capacity, and calibration. More reasoning does not guarantee better security. There exists an optimal level of reasoning effort, and mechanisms that work for larger models may actively harm smaller ones.

Instruction tuning provides modest functional improvements: pass@1 increases from 27.27% to 29.22% (7.2% relative gain) and Pass Rate from 57.8% to 59.7%. However, instruction tuning’s impact on security is limited and partially negative. Models may learn to complete requested tasks efficiently, potentially cutting corners on security to achieve functional goals. A model might correctly handle SQL injection in one context while failing on path traversal in another, passing individual tests but failing joint evaluation.

These findings indicate that standard instruction tuning is insufficient for secure code generation and may even be counterproductive. To improve security, instruction tuning must explicitly incorporate security objectives through security-aware training data, security-centric reinforcement learning, and prompts that treat security as a first-class requirement alongside functionality.

VII
Discussion

VII-A

Implications and Recommendations

Our comprehensive evaluation reveals critical insights for practitioners deploying LLM-based code generation and researchers developing more secure systems.

Model Selection for Different Security Requirements.
Organizations face different security-performance-cost trade-offs depending on their application context. For high-security critical applications, GPT-5 is the clear choice (11.69% secpass@1, 57.07% SPR), with medium reasoning offering optimal balance. For moderate security needs with cost constraints, Gemini-2.5-Flash (7.24% secpass@1, 41.97% SPR) and Claude-Haiku-4.5 (6.49% secpass@1, 41.8% SPR) provide competitive alternatives. For resource-constrained deployments, Qwen3-8B offers the best open-source option (3.90% secpass@1, 31.89% SPR), as larger variants provide minimal security benefits.

Training Paradigm Shifts for Model Developers.
Our results reveal fundamental limitations in current training approaches. Standard instruction tuning optimizes for task completion while inadvertently deprioritizing security. Model scaling beyond moderate sizes (8B-14B parameters) yields diminishing security returns, suggesting naive scaling is insufficient. To build more secure code generation models, developers must adopt security-aware training paradigms that explicitly incorporate security objectives.

Research Directions and Open Challenges.
Several critical questions emerge from our findings. Why does security capability emerge at 4B parameters but plateau thereafter? What enables GPT-5’s dramatic improvement over GPT-4, and can these mechanisms be identified and replicated? Why does FP8 quantization improve security while other quantization methods degrade it? How can reasoning mechanisms be designed to genuinely improve security rather than showing non-monotonic effects? Finally, how do these findings translate to agentic coding systems that iteratively generate and refine code? These questions define the frontier of trustworthy AI-assisted software development.

VII-B

Threats to Validity

LLM-Based Evaluation.
Our evaluator assesses both functional and security test outcomes through semantic reasoning about execution traces, supported by a two-stage knowledge resolution process. Our validation study quantifies evaluator performance with precision of 0.90 and recall of 0.77. While this demonstrates strong alignment with human judgment, approximately 9% of positive assessments may be incorrect, and approximately 22% of correct behaviors may be misclassified as failures.

Trace-Based Assessment.
The agentic executor captures statement-coverage traces and program outputs to represent behavior. Security and functional properties manifest through observable phenomena including side effects, resource consumption, control flow, and outputs. The evaluator interprets these traces semantically to determine whether observed behaviors satisfy expected requirements. Section
V
shows the executor achieves 95.08% precision and 84.67% recall, indicating high but imperfect trace fidelity.

Execution Non-Determinism.
Programs may exhibit varying behavior due to timing operations, randomness, concurrency, or system interactions. Our isolated sandboxes provide controlled execution contexts, executing each test once per sample with
temperature=0
to promote consistent behavior. However, inherent non-determinism may lead to execution variations that affect test outcomes.

Test Design Assumptions.
Our test suites operationalize correctness and security based on established guidelines (OWASP, CERT). Security test oracles define expected behaviors, and the evaluator performs semantic reasoning to assess whether observed behaviors satisfy these requirements. This approach allows different implementation strategies for example, input sanitization may be achieved through escaping, filtering, or encoding, with the evaluator determining whether the implemented mechanism addresses the specified security requirement.

Coverage Scope.
Our test suites implement systematic coverage criteria: requirements coverage for functional tests and risk-based coverage for security tests. The human-LLM co-creation process generates comprehensive test cases validated by multiple independent experts. Our metrics measure performance against the requirements and security properties defined in the test suites, following a specification-based testing approach. However, no test suite can exhaustively cover all possible behaviors or vulnerabilities.

VIII
Conclusion

The rapid adoption of LLMs for code generation demands rigorous evaluation that jointly assesses functional correctness and security. We present
DualGauge
, the first fully automated system for joint evaluation, paired with
DualGauge-Bench
, a benchmark of 154 tasks with dual, coverage-enforced test suites. Our evaluation of 25 configurations across 21 models reveals substantial gaps between functional and security performance. We uncover that security plateaus beyond moderate model sizes, certain quantization strategies improve security, and reasoning mechanisms show non-monotonic effects. We release
DualGauge
and
DualGauge-Bench
as open-source tools to advance trustworthy AI-assisted software development.

Ethics Considerations

All code generation and testing activities were conducted in isolated sandbox environments to ensure safety and prevent any potential security risks. The generated code samples were never deployed to production systems or tested against live infrastructure. Our evaluation focuses exclusively on synthetic test cases designed specifically for benchmarking purposes, not on discovering vulnerabilities in existing real-world software. The isolated execution environments prevent any unintended interactions with external systems or data.

DualGauge-Bench
contains no personally identifiable information, proprietary code, or sensitive data. All prompts and test cases were either authored by the research team or derived from publicly available datasets with appropriate attribution.

We evaluated only publicly accessible LLMs through their official APIs, respecting all terms of service. The benchmark and evaluation system are released under open-source licenses to promote transparency, reproducibility, and community validation. While making security test cases public could theoretically inform adversarial training, we believe the benefits of transparent and reproducible research outweigh this concern, particularly given that the security principles tested are already well-documented in established public guidelines such as OWASP and CERT standards.

Our work aims to improve the state of secure code generation by providing rigorous evaluation tools, not to enable uncritical deployment of LLM-generated code. While
DualGauge
enables comparative evaluation of secure code generation capabilities, benchmark scores should not be interpreted as certification that any model is secure for production use. Organizations should not rely solely on benchmark performance when making deployment decisions. We emphasize that human oversight, code review, and comprehensive security testing remain essential components of software development. The benchmark should be viewed as one component of a holistic security assessment strategy, complementing rather than replacing human expertise and established security practices.
