Taint-Based Code Slicing for LLMs-based Malicious NPM Package Detection CCS: Security and privacy Malware and its mitigation
Dang-Khoa Nguyen, Gia-Thang Ho, Quang-Minh Pham, Tuyet A. Dang-Thi, Minh-Khanh Vu, Thanh-Cong Nguyen, Phat T. Tran-Truong, Duc-Ly Vu

Abstract
. The increasing sophistication of malware attacks in the npm ecosystem, characterized by obfuscation and complex logic, necessitates advanced detection methods. Recently, researchers have turned their attention from traditional detection approaches to Large Language Models (LLMs) due to their strong capabilities in semantic code understanding. However, while LLMs offer superior semantic reasoning for code analysis, their practical application is constrained by limited context windows and high computational cost. This paper addresses this challenge by introducing a novel framework that leverages code slicing techniques for an LLM-based malicious package detection task. We propose a specialized taint-based slicing technique for npm packages, augmented by a heuristic backtracking mechanism to accurately capture malicious data flows across asynchronous, event-driven patterns (e.g., callbacks and Promises) that elude traditional analysis. An evaluation on a dataset of more than 5000 5000 malicious and benign npm packages demonstrates that our approach isolates security-relevant code, reducing input volume by over 99% while preserving critical behavioral semantics. Using the DeepSeek-Coder-6.7B model as the classification engine, our approach achieves a detection accuracy of 87.04 87.04 %, substantially outperforming a naive token-splitting baseline ( 75.41 75.41 %) and a traditional static-analysis-based approach. These results indicate that semantically optimized input representation via code slicing not only mitigates the LLM context-window bottleneck but also significantly enhances reasoning precision for security tasks, providing an efficient and effective defense against evolving malicious open-source packages.



1.
Introduction

Software supply chain attacks represent a critical and escalating threat to modern language-based ecosystems such as
npm
and PyPI. The Node Package Manager (
npm
) repository has become an increasingly attractive vector for malicious actors to distribute compromised packages
(
53
)
. Such attacks directly threaten millions of downstream consumers and pose significant challenges to the security posture of organizational software assets
(
9
;
38
)
. For example, the recent
Shai-Hulud
self-propagating
(
48
)
attack involved packages that spread across thousands of repositories, exfiltrating secrets and publishing new compromised payloads, thereby affecting numerous popular packages
(
12
)
.

To counter these threats, academic and industry researchers have developed various methodologies for detecting malicious open-source packages in repository ecosystems
(
34
)
. These include traditional signature-based or rule-based approaches, as well as machine learning and deep learning techniques. While signature- and rule-based methods offer fast detection and can be readily integrated into security pipelines
(
42
)
, they lack the adaptability to identify novel attack patterns. Attackers can easily bypass such defenses through code obfuscation
(
11
)
. Machine learning approaches
(
7
;
19
)
, which often rely on handcrafted features like API call sequences, provide greater flexibility. However, they remain labor-intensive to develop and are similarly vulnerable to evasion through obfuscation techniques that alter these engineered features
(
33
;
39
)
.

The emergence of Large Language Models (LLMs) has introduced transformative capabilities for security tasks, including malicious code analysis and detection
(
1
;
20
;
16
)
. Empirical evaluations demonstrate that LLM-based approaches can substantially outperform conventional detection methodologies
(
5
;
3
)
. Specifically, prior work shows that LLMs achieve strong precision and recall in detecting malicious
npm
packages, significantly surpassing traditional static analysis tools
(
52
)
. This success stems from the LLM’s capacity for semantic reasoning and context-aware pattern recognition across complex code structures
(
23
;
46
)
.

Despite their promise, LLM-based detection systems face substantial architectural constraints that limit practical deployment. The restricted context window of contemporary LLMs typically ranging from 4K to 16K tokens proves insufficient for the comprehensive analysis of large software packages
(
25
;
29
)
. Consequently, the model may lack visibility into the complete package context necessary for precise threat assessment when malicious logic is distributed across the codebase, leading to reduced detection accuracy
(
15
;
6
)
.

To mitigate this bottleneck, Wang et al.
(
44
)
proposed a taint-based code slicing methodology that isolates security-relevant code segments before LLM analysis. Their approach reduces context window overhead while preserving critical semantic information, demonstrating substantial improvements in detection precision and computational efficiency for PyPI packages. However, the generalizability of this methodology to other programming ecosystems remains an open question. The
npm
ecosystem presents fundamentally distinct analytical challenges: JavaScript’s asynchronous, event-driven execution model introduces significant complexity for control and data flow analysis
(
30
)
, and
npm
malware frequently employs aggressive code obfuscation and minification strategies to obscure malicious intent
(
34
)
.

To the best of our knowledge, no existing work provides a systematic treatment of code slicing specialized for the asynchronous execution patterns prevalent in
npm
packages. Foundational work by Madsen et al.
(
30
)
analyzes event-driven programs but does not propose a slicing-based methodology for malware detection. Thus, the intersection of (1) asynchronous program analysis and (2) semantic slicing for security-critical code reduction remains unexplored. This gap motivates our first research question:

•

RQ1
: How can contextual information within
npm
packages be effectively reduced while preserving semantic signals indicative of malicious behavior?

To answer RQ1, we extend taint-based slicing to the
npm
ecosystem by incorporating language-specific strategies for asynchronous execution. We then conduct a systematic evaluation to determine whether this code slicing preserves detection accuracy while reducing computational overhead.

Furthermore, to concretely assess the effectiveness of slicing as a preprocessing step for LLMs, we compare its performance against analyzing complete source code. This leads to our second research question:

•

RQ2
: How significantly does code slicing improve LLM-based malicious package detection performance compared to LLM analysis of complete package source code?

To answer this research question, we replicate the approach by Wang et al.
(
44
)
and compare it with our approach and the full package scanning approach. The comparison is made on a slice by slice basis based on standard evaluation metrics (e.g., precision, recall, and F1-Score).

Our core contribution lies in the design and implementation of a
Targeted-Taint Slicing
strategy for npm packages, which is inspired by the work by Wang et al.
(
44
)
. Their method generates
Sensitive Code Slices (SCS)
as input for the OCS-BERT model. While effective for vector embedding, we hypothesize that the broad dependency subgraphs they produce introduce excessive noise for generative LLM prompting, thereby reducing detection performance. In summary, we make the following contributions:

•

We introduce a
heuristic backtracking mechanism
that recovers tainted data flows across callback registrations, Promise chains, and event propagation, specifically designed for the asynchronous patterns of
npm
packages.

•

We demonstrate that high-signal, semantically-condensed slices enhance LLM detection accuracy compared to full-code baselines, achieving over 99% code volume reduction while maintaining or improving detection precision.

•

We provide empirical evidence of the accuracy-efficiency trade-off through an evaluation on real malicious and benign
npm
packages, showing that slicing-based input reduction enhances the detection performance of an LLM.

2.
Background and Related Work

2.1.
Syntactic Pattern Matching and Signature-Based Detection

Early malware detection systems operate fundamentally at the lexical and syntactic level, employing pattern matching against known malicious signatures. Representative techniques and tools include Microsoft’s OSS Detect Backdoor
(
31
;
32
)
, which performs registry and file system pattern scanning, and CodeQL-based systems
(
11
)
that employ rule-based syntax tree traversal.
These approaches exhibit linear computational complexity relative to codebase size, permitting scalable deployment across large package repositories. While the detection latency is minimal, and rule maintenance remains straightforward for known threat classes, traditional approaches face the following limitations:

•

Precision-Recall Trade-off:
Microsoft’s ODB exhibits 75.5% false positive rate coupled with 9.9% false negative rate
(
31
)
, necessitating extensive manual validation. These statistics contrast with the expectations of package maintainers, who typically require an extremely low false-positive rate
(
42
)
.

•

Syntactic Brittleness:
Rule-based detection systems such as
(
41
)
provide more flexibility in detecting malware variants. However, they fail systematically against code obfuscation (e.g., string encoding or control flow flattening), stylistic variation, and semantic preserving transformations
(
11
)
.

•

Signature Lag:
Novel attack patterns and polymorphic variants outpace rule development cycles, creating temporal vulnerability windows
(
9
)
. In this respect, malware researchers must regularly update their signature base to tackle different malware variants of the same family.

Other approaches propose combining different sources of package information for malicious package detection. For example, Duan et al.
(
9
)
introduced metadata augmented approaches (package version history, developer reputation). Vu et al.
(
40
)
called
LastPyMile
which identifies discrepancies between source and package of a PyPI package, and then scan those discrepancies for any sign of maliciousness. A later study by Scalco et al.
(
38
)
ported LastPyMile to npm packages.

2.1.1.
Behavioral Sequence Analysis Through API Monitoring

Dynamic analysis addresses syntactic limitations by instrumenting code execution and monitoring behavioral outputs. Two complementary approaches emerged: (1) API-call sequence capture in sandboxed environments, and (2) statistical and neural modeling of behavioral patterns.
Dynamic analysis captures semantic phenomena invisible to static syntactic inspection, including runtime polymorphism, reflection-based code execution, and environment dependent behavior. API call sequences provide a more abstract behavioral encoding than raw bytecode
(
50
)
. Pascanu et al.
(
36
)
employed Recurrent Neural Networks (RNNs) and Echo State Networks to model API call sequences, achieving sequence level abstraction. However, gradient vanishing/explosion and limited training data restricted accuracy improvements. Demirkiran et al.
(
7
)
proposed CNN-RNN hybrid ensembles capturing both local and sequential patterns. Kim et al.’s TextCNN
(
22
)
approach achieved comparable performance with reduced training complexity. Devlin et al.’s BERT
(
8
)
and specialized variants (CodeBERT
(
10
)
) introduced bidirectional context modeling. Subsequent work by Guo et al. extended this with data flow aware representations (GraphCodeBERT
(
14
)
) and unified cross modal encoding (UniXcoder
(
13
)
).

Huang et al.
(
50
)
documented that approximately 85% of API associations exhibit correlation coefficients between -0.25 and 0.25, indicating weak semantic cohesion. API sequences capture behavioral signatures but not behavioral intent. Malware increasingly employs anti analysis techniques process and registry scanning, timing-based sandbox detection, and conditional code paths dependent on the execution environment. Dynamic approaches are thus susceptible to evasion through environment adaptive execution
(
28
)
. Sandboxed execution imposes computational costs (resource consumption, isolation setup, execution latency) proportional to package complexity. This prohibits deployment in real-time registry-monitoring scenarios
(
19
)
.

2.2.
Semantic Representation Learning via Feature Engineering and Neural Methods

Contemporary approaches directly learn malware classifiers from data, employing engineered-feature sets or neural embeddings trained on behavioral or code characteristics. AMALFI
(
39
)
extracted package-level features (version churn, developer history, dependency anomalies) with SVM classification. Ohm et al.
(
33
)
employed Random Forests on hand-crafted code metrics and API usage patterns.

Feature selection is labor-intensive, domain-specific, and subject to expert disagreement, undermining reproducibility
(
33
)
. Hand-crafted features (e.g., code length, cyclomatic complexity, API frequency) remain invariant under obfuscating transformations that alter syntax while preserving semantics
(
11
)
. Malware families exhibit rapid evolution and ecosystem specific adaptations. Feature-based approaches require frequent retraining and exhibit poor cross-ecosystem generalization.

2.3.
Large Language Models for Semantic Code Analysis

Recent advances in Large Language Models (LLMs) introduce a qualitatively distinct analytical capability: semantic understanding of code as high-level program behavior rather than low-level syntax, statistics, or engineered-features.

Early foundation models demonstrated broad code comprehension. Codex
(
5
)
, trained on GitHub data, exhibited code generation capabilities surpassing human programmers on specific benchmarks. Brown et al.’s GPT-3
(
3
)
demonstrated few-shot transfer learning, enabling task specialization without explicit fine-tuning.

Code domain specialization refined these models through domain-specific pre-training:

•

Encoder-Only Models:
BERT
(
8
)
established the foundation for code-specific variants. CodeBERT
(
10
)
introduced bimodal pre-training on code documentation pairs. GraphCodeBERT
(
14
)
augmented BERT with Program Dependence Graph (PDG) structure, and UniXcoder
(
13
)
unified encoder decoder architectures with cross-modal contents (Abstract Syntax Trees, comments).

•

Encoder-Decoder Models:
CodeT5
(
45
)
introduced a unified encoder–decoder framework supporting both understanding and generation tasks.

Encoder-only models exhibit severe context-window limitations (512–1024 tokens), rendering them unsuitable for analyzing complete packages or performing multi-step reasoning
(
8
)
. These models are fundamentally designed for token-level tasks (classification, tagging) rather than document-level semantic assessment.
In contrast to encoder-only models, generative LLMs (GPT-3, GPT-4, DeepSeek Coder family) exhibit semantic reasoning capabilities that transcend statistical pattern matching:

•

Contextual Semantics:
Rather than predicting token sequences, generative models construct abstract program semantics and understanding data flows, control dependencies, and higher-order program intent
(
46
)
.

•

Obfuscation Resilience:
By operating on semantic representations rather than syntactic patterns, generative models maintain detection accuracy across code transformations that preserve intent
(
52
)
.

•

Cross-Language Transfer:
LLM representations span programming language boundaries, enabling transfer learning from Python to JavaScript to Java without explicit re-training
(
15
)
.

2.4.
Graph Representations of Program

Transforming source code from textual format into graph-based structures is a fundamental prerequisite for applying static analysis techniques. Graph representations facilitate the capture of program semantics, control flow, and data dependencies, which are often obscured in raw text
(
21
;
4
)
.

2.4.1.
Code Property Graph (CPG)

Code Property Graph (CPG), introduced by Yamaguchi et al.
(
49
)
, is a comprehensive super-graph that integrates three fundamental representations: Abstract Syntax Tree (AST), Control Flow Graph (CFG), and Data Dependence Graph (DDG). Formally, the CPG is a directed property multigraph where nodes and edges possess attributes representing syntactic elements (e.g., methods, variables, constants) and relationships (control flow, data flow, syntax).

Primary advantage of the CPG lies in its ability to enable unified queries across multiple representation levels, thereby facilitating the detection of vulnerabilities and malicious behaviors in source code. Tools such as Joern
(
49
)
leverage this structure to extract deep semantic features, supporting automated security analysis.

Data Dependence Graph (DDG)

Data Dependence Graph focuses on the relationships between variable definitions and their usages. A directed edge
e=(u,v)
exists if the statement at vertex
u
assigns a value to a variable
x
, and the statement at vertex
v
utilizes that value of
x
without any intervening re-assignment (reaching definition)
(
18
)
. The DDG is critical for identifying variables influenced by specific inputs and serves as the foundational structure for Code Slicing techniques.

Control Flow Graph (CFG)

Control Flow Graph depicts the execution order of statements within a program. Formally, a CFG is a directed graph
G_{CFG}=(V,E)
, where
V
represents basic blocks and
E
denotes the control flow transitions between them. CFG enables the identification of feasible execution paths, including branching and loops. However, as CFGs do not explicitly capture data dependencies, they are often combined with DDGs to form the Program Dependence Graph (PDG)
(
26
)
.

Abstract Syntax Tree (AST)

AST provides a hierarchical representation of the program’s syntactic structure. Each node in the AST corresponds to a syntactic construct, modeling the grammatical structure without including execution details. The AST serves as the skeletal basis upon which more complex representations, such as the CPG, are constructed.

2.5.
Taint-Based Analysis

Taint Analysis is a data flow analysis technique widely employed to detect security vulnerabilities and malicious behaviors
(
24
;
47
)
. The primary objective is to track the propagation of untrusted data from a specific entry point (Source) to a sensitive execution point (Sink). The analysis process comprises three distinct phases:

•

Source:
The entry point for untrusted data, such as user inputs, network payloads, or file reads.

•

Propagation:
The tracking of tainted data as it moves through assignments, computations, or function calls. This is typically modeled using DDGs or CPGs to map the data flow path
(
17
)
.

•

Sink:
Sensitive functions or locations where tainted data could cause information leakage or execution of malicious code if not properly sanitized.

Modern systems, such as
DepTaint

(
26
)
, integrate CPGs with taint analysis techniques to effectively identify dangerous behaviors, establishing a framework for extracting code slices suitable for training machine learning models.

Methodology

In this section, we present our proposed malware detection methodology, as illustrated in Figure
1
. The approach consists of three main stages:
Sensitive Code Extraction
,
Automated Security Scoring with LLMs
, and
Aggregation and Package-Level Evaluation
. Before detailing each component, we highlight key differences between our methodology and the OCS-BERT framework
(
44
)
, to our knowledge, the only prior work that applies code slicing to open-source malware detection across three main aspects:

•

Analysis Model:
While OCS-BERT utilizes code-slicing primarily to generate tokens for training BERT models, our approach leverages Large Language Models (LLMs) to directly analyze and interpret the semantics of code slices.

•

Target Ecosystem:
OCS-BERT was originally designed for Python packages (PyPI). Although Wang et al.
(
44
)
conducted exploratory experiments on npm to assess cross-language model transferability, they explicitly stated that their framework currently lacks the ability to slice code in other programming languages beyond Python.
Addressing this limitation, our framework is specifically tailored to the JavaScript ecosystem, providing native code-slicing support for npm packages.

•

Implementation Architecture:
Unlike prior methods that rely heavily on writing raw Joern queries, which can be difficult to manage and debug. Our system is built as a modular Scala framework.
This design choice allows for easier extensibility, better type-safety, and more efficient debugging of the analysis-pipeline.

3.1.
Sensitive Code Extraction

In the first step, we focus on isolating security-relevant code segments from npm packages using the following two distinct extraction strategies:

•

Static Code Slicing:
A control dependence based
backward slicing that performs reachability analysis over the
Control Flow Graph (CFG) embedded within the Code Property
Graph (CPG).

•

Taint-Based Slicing
: A semantic slicing approach
that integrates both CFG and Data Flow Graph (DFG) analyses
to selectively track sensitive APIs and their data flows.

We refine the methodology proposed by Wang et al.
(
44
)
by enforcing a stricter signal-to-noise filter. In particular, instead of preserving broad dependencies, our approach isolates only those data flows that explicitly originate from the high-risk feature groups defined in Table
2
, thereby discarding auxiliary logic to optimize the input for the model’s reasoning process.

Beyond categorization, we address a fundamental challenge in analyzing
JavaScript: standard static analysis often struggles to track taint
propagation across asynchronous constructs (e.g., callbacks, Promises)

(
30
)
. In our experiments,
we observed that the baseline Joern
(
49
)
analysis which serves as the underlying
engine for OCS-BERT
(
44
)
frequently fails to capture
these dependencies. This leads to instances of broken flows, where a sink
is detected without a traceable path to a source.

To mitigate this, we introduce a Heuristic Backtracking Mechanism.
When a high risk sink is identified but the data flow analysis yields no results
(i.e.,
flows.isEmpty
), our algorithm triggers a fallback procedure.
Instead of terminating, it traverses the Control Flow Graph (CFG) upstream to determine
if the sink is lexically enclosed within the callback scope of a known source.
This targeted recovery effectively reconnects implicit asynchronous
flows without incurring the high computational cost of full program dependence analysis.
To ensure scalability and prevent the generation of excessively large slices during
this fallback process, we enforce a strict timeout of 3 minutes.

•

Source
: Source group includes behaviors associated with the input side of information flow. These actions typically involve reading, collecting, or retrieving data that may later contribute to malicious activity.

•

Sink
: Sink group encompasses behaviors that directly execute or materialize malicious intent. Examples include executing system commands, performing obfuscation, or cleaning up the runtime environment.

•

Dual
: Dual group contains APIs whose behaviors can appear as either sources or sinks depending on context. These often involve operations that both read and write data, such as file operations or network communication.

The taint analysis engine incorporated custom extensions, including source sink classification for Node.js APIs and heuristics for recovering asynchronous broken flows.

In Static Code Slicing Algorithm
1
, we first query the Code Property Graph (CPG) to retrieve the node IDs for all sources in the Source Group (
SG
). Subsequently, for each sink in the Sink Group (
SKG
), we perform a backward slice. This process involves traversing the Control Flow Graph (CFG) in reverse, starting from the sink node. The traversal continues until all relevant source nodes are reached or no valid predecessor nodes remain. During this traversal, we collect all visited nodes to form a candidate slice. Finally, the algorithm returns the set of all valid collected slices.

In Taint-based Slicing Algorithm
2
, we employ a hybrid approach. First, we attempt a standard taint analysis using reachability flows between sources and sinks. If a valid data flow is detected, the slice is extracted directly from the flow path. However, if no direct flow is found (potentially due to broken flows in the static analysis), the algorithm falls back to a heuristic approach. It iterates through the sinks and traverses the Abstract Syntax Tree (AST) upwards via
FindEnclosingSource
to determine if a sink is structurally nested within a source call (e.g., a callback function). If such a nesting is found, a code snippet is constructed based on the line numbers of the source and sink.

3.3.
Aggregation and Package Evaluation

In the final step, the responses generated by the LLMs model are aggregated and evaluated to determine the maliciousness score of each input package. As a package can have multiple responses, corresponding to its individual code snippets, we choose the maximum
malware
score among all its responses is used as the key indicator for assessment. Then we apply a threshold to distinguish between malicious and benign package.
For every input configuration, the LLM processes the code snippet and outputs a JSON object containing a
malware
score
S\in[0,1]
. We apply a
threshold
\tau
to determine the final label:

\text{Label}=\begin{cases}\text{Malicious}&\text{if }S\geq\tau\\
\text{Benign}&\text{if }S<\tau\end{cases}

To empirically determine the optimal decision boundary
\tau
, we analyzed the Receiver Operating Characteristic (ROC) curves of our slicing strategies, as illustrated in Figure
4
.
This analysis highlights the trade-off between detection sensitivity (True Positive Rate) and false alarm frequency (False Positive Rate).
As demonstrated in the figure, Taint-based Slicing method consistently outperforms Static Slicing. Consequently, we selected
\tau=0.8
as the optimal threshold, as it corresponds to the "elbow" of the
Taint-based curve the point where performance is maximized before diminishing returns ensue. At this threshold, the system achieves a robust True Positive Rate (TPR) of 0.95 while maintaining a low False Positive Rate (FPR) of 0.18.
This strategy ensures that even a single high-risk snippet flags the entire package for further investigation, establishing a conservative yet effective approach for automated security evaluation.

In particular, a package is classified as malicious if the maximum
malware
score
\geq\tau
, and benign if the score
<\tau
. This aggregation strategy ensures that even a single highly risky snippet can flag the entire package for further investigation, providing a conservative and effective approach for automated security evaluation.

By wiring stdin, stdout, and stderr between the shell and the remote endpoint, the attacker is granted full interactive command execution on the victim machine. 4.3.
Experiment Setup

Our evaluation examines how different slicing techniques reduce contextual information while preserving malicious patterns (
RQ1
), as well as the impact of these slicing techniques when used as input to an LLM (

). To this end, we compare the following implementations:

•

Full Code (Baseline).

The complete JavaScript source code without slicing. Due to LLM context window limitations, files exceeding
500
tokens were segmented into non-overlapping chunks. Package-level classification is determined by the maximum risk score among all chunks.

•

Static Code Slicing.

A reachability-based slicing strategy that relies solely on the Control Flow Graph (CFG) to extract execution paths. This approach captures broad control dependencies (e.g., function calls and loops) reachable from entry points but does not explicitly track variable states or data propagation, serving as a structural baseline.

•

Taint-Based Slicing.

A comprehensive slicing strategy that integrates both the CFG and the Data Flow Graph (DFG) to track explicit information flow. This method preserves data continuity from defined sources to sensitive sinks (as described in Section
3
), ensuring that the LLM focuses on code regions where potentially malicious data is actively manipulated or executed.

Each configuration produces a distinct representation of a package, enabling a systematic comparison of how input granularity and semantic fidelity affect the LLM’s ability to detect malicious behavior. The evaluation followed the procedure outlined below:

(1)

(

Parse the JSON outputs and apply the classification threshold.

(5)

Aggregate evaluation metrics to assess the impact of slicing.

As a CodeQL-based static analysis tool, GENIE represents a fundamentally different analysis paradigm from both static slicing and taint-based slicing. GENIE relies on predefined CodeQL queries to identify suspicious patterns, vulnerability templates, or rule-based indicators across the codebase. While this approach is effective for detecting known vulnerability classes, its performance in malicious package detection is limited, as reflected in Table 9, where GENIE achieves only
48.68

35.32

The primary limitation of GENIE, relative to slicing techniques, lies in its pattern-centric analysis model. CodeQL queries operate over abstract syntax trees, control-flow graphs, and data-flow relations, but they are designed to flag discrete findings rather than to construct execution-coherent code representations. As a result, the output consumed by the LLM is often either overly coarse (entire files or large query matches) or fragmented across multiple independent findings. This lack of semantic continuity reduces the LLM’s ability to infer higher-level malicious intent, particularly in scenarios where the payload is obfuscated, conditionally activated, or distributed across multiple modules.

Static slicing improves upon GENIE by preserving control-flow and dependency structure without relying on predefined security rules. With
75.65
% accuracy and a

However, static slicing remains conservative: it includes all statements that are control- or data-dependent on a slicing criterion, regardless of whether those statements are security-relevant. Consequently, benign scaffolding code is frequently retained, which explains its moderate precision (

Taint-based slicing further advances beyond both GENIE and conventional static slicing by explicitly modeling attacker-controlled data propagation. Compared to GENIE, taint-based slicing improves accuracy by
38.36
percentage points and more than doubles the F1-score, underscoring how rule-based static analysis alone is insufficient for capturing malicious intent in modern supply-chain attacks. Unlike GENIE’s query-driven detection, taint-based slicing systematically filters execution paths to those influenced by untrusted inputs, producing slices that are both execution-coherent and security-focused.

Overall, these findings demonstrate that slicing is more than a preprocessing convenience; it is a structural intervention that substantively modifies the semantic quality of model inputs. By preserving or prioritizing security-relevant execution flow, slicing especially Taint-based Slicing aligns the input representation with meaningful behavioral signals while leveraging the DeepSeek model’s
16
k-token window more effectively. This results in materially improved detection performance and highlights the importance of semantic fidelity in preparing code representations for LLM-based security analysis.

Main Findings:
The taint-based slicing produces significantly more concentrated and behaviorally informative inputs. The marked improvements compared to static-code slicing reflect the model’s ability to leverage these focused slices to detect subtle patterns such as covert command execution. The taint-based slices reduce both false positives by excluding irrelevant benign code and false negatives by ensuring that the critical segments driving malicious behavior remain intact and within the model’s context window.

6.
Threats to Validity

Internal Validity: Scope and Resource Constraints

A primary threat to internal validity concerns the scope of our analysis. Malicious payloads frequently reside in
package.json
files (e.g., via installation scripts). However, we deliberately excluded samples containing only this file to strictly isolate and evaluate the effectiveness of the proposed slicing techniques on
JavaScript source code logic
, rather than metadata-based attack vectors.

Additionally, we encountered occasional out-of-memory (OOM) errors during inference on extremely large slices due to hardware constraints (
2\times
NVIDIA RTX 3080 GPUs). Although this may theoretically affect accuracy for a small number of outliers, the high overall recall (
96.23
%) observed in our results suggests that these edge cases do not materially undermine the validity of the proposed approach for the majority of the npm ecosystem.

External Validity: Ecological Realism

We acknowledge that our dataset exhibits a relatively balanced distribution (approximately
1.3
:1) between benign and malicious packages, which does not reflect the severe class imbalance (malware
<1\%
) observed in real-world npm repositories. This balance was an intentional design choice to establish a rigorous benchmark for technical evaluation. Assessing performance on a highly imbalanced dataset would disproportionately affect metrics such as precision and F1-score, making it difficult to isolate the specific contribution of the slicing techniques. A balanced dataset enables a statistically meaningful assessment of the model’s discriminative capability.

Construct Validity: Information Loss vs. Signal Retention

A potential threat to construct validity arises from the inherent information loss introduced by code slicing. One may argue that removing code segments could eliminate contextual cues necessary for effective LLM reasoning. However, our empirical analysis of Sensitive Feature Recall (SFR) mitigates this concern. The results show that taint-based slicing retains
73.7
% of malicious features while discarding over
90
% of benign code. Moreover, the substantial improvement in F1-score (
83.32
%) compared to the full-code baseline (
67.80
%) indicates that the sliced representation enhances, rather than degrades, semantic signal quality.

Generalizability: Model Selection

Our evaluation is currently limited to a single LLM family (DeepSeek-Coder). While reliance on one model may constrain immediate generalization, this model was chosen as a representative state-of-the-art open-source LLM specialized for code intelligence. We hypothesize that the core benefit of slicing—namely, increasing information density within a constrained context window—is largely model-agnostic. Consequently, the improvements observed in this study are likely to transfer to other large language models with comparable or stronger reasoning capabilities.

7.
Conclusion and Future Work

Recent malware attacks targeting open-source package repositories pose serious threats to software supply chain security. While prior detection approaches including those based on Large Language Models (LLMs) leverage rich semantic and contextual understanding, they remain constrained by limited context windows, leading to
contextual overloading
when analyzing large or complex packages.

This paper introduces a novel code slicing technique that reduces contextual input size while preserving security-relevant semantics for LLM-based analysis. Our experimental results demonstrate that the proposed approach outperforms traditional static slicing by nearly
10
% in F1-score, highlighting the effectiveness of semantics-aware input reduction for malicious package detection.

Although our findings show that code slicing, particularly taint-based slicing, substantially enhances LLM-based detection of malicious open-source packages, several promising avenues remain for future research.

•

First, we plan to explore fine-tuning LLMs for security-focused code understanding. In this study, the LLM operates in a prompt-based setting, which limits its ability to internalize domain-specific indicators of malicious behavior. Fine-tuning on carefully curated benign and malicious package datasets, combined with slicing-aware input representations, may further improve detection accuracy, reduce false positives, and enhance robustness against previously unseen attack patterns. Such specialization would enable the model to better distinguish complex benign logic from intentionally deceptive malicious implementations.

•

Second, future work will investigate integrating LLM-assisted deobfuscation techniques into the analysis pipeline. In practice, many supply chain attacks rely on obfuscation strategies, such as string encoding, control-flow flattening, dynamic imports, and indirect invocation, to evade static analysis and manual inspection. Leveraging LLMs to automatically deobfuscate or normalize such constructs prior to slicing could expose latent malicious semantics, enabling taint-based slicing to more precisely isolate attacker-controlled data and control flows.

•

Finally, we envision an end-to-end detection framework that jointly incorporates fine-tuned LLMs, deobfuscation-aware preprocessing, and semantic slicing. By co-optimizing these components, the system can adapt more effectively to evolving adversarial behaviors and obfuscation techniques prevalent in large-scale open-source ecosystems. Collectively, these directions aim to enhance the resilience and practical applicability of LLM-based security analysis, advancing toward deeper integration of program analysis and learned semantic reasoning.
