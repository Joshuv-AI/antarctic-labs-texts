Efficient Decrease-and-Conquer Linearizability Monitoring
Zheng Han Lee, Umang Mathur

Abstract
. Linearizability has become the de facto standard for specifying correctness of implementations of concurrent data structures. While formally verifying such implementations remains challenging, linearizability monitoring has emerged as a promising first step to rule out early problems in the development of custom implementations, and serves as a key component in approaches that stress test such implementations. In this work, we undertake an algorithmic investigation of the linearizability monitoring problem, which asks to check if an execution history obtained from a concurrent data structure implementation is linearizable. While this problem is largely understood to be intractable in general, a systematic understanding of when it becomes tractable has remained elusive. We revisit this problem and first present a unified ‘decrease-and-conquer’ algorithmic framework for designing linearizability monitoring. At its heart, this framework asks to identify special linearizability-preserving values in a given history — values whose presence yields an equi-linearizable sub-history (obtained by removing operations of such values), and whose absence indicates non-linearizability. More importantly, we prove that a polynomial time algorithm for the problem of identifying linearizability-preserving values, immediately yields a polynomial time algorithm for the linearizability monitoring problem, while conversely, intractability of this problem implies intractability of monitoring. We demonstrate the effectiveness of our decrease-and-conquer framework by instantiating it for several popular concurrent data types — registers, sets, stacks, queues and priority queues — deriving polynomial time algorithms for them, under the ( unambiguity ) restriction that each insertion to the underlying data structure adds a distinct value. We further optimize these algorithms to achieve log-linear running time through the use of efficient data structures for amortizing the cost of solving induced sub-problems. Our implementation and evaluation on publicly available implementations of concurrent data structures show that our approach scales to very large histories and significantly outperforms existing state-of-the-art tools.

1.
Introduction

Linearizability, originally proposed by Herlihy and Wing
(
Herlihy and Wing, 1990
)
,
serves as a systematic correctness criterion for implementations of
concurrent data structures, and has become the most popular choice of specifications.
Conceptually, it asks — given an implementation, are all its behaviors
equivalent to an ideal, but sequential implementation?
While full-fledged formal verification of concurrent data structure implementations
is desirable, as with other interesting properties about programs,
it is an undecidable property in its full generality
(
Bouajjani et al., 2013
)
,
and decidable classes of programs and sequential specifications remain
limited
(
Alur et al., 1996
;
Hamza, 2015
;
Bouajjani et al., 2015
;
Černý et al., 2010
)
.

In this work, we investigate the
linearizability monitoring
problem,
a pragmatic take on the correctness problem for data structure implementations.
Instead of ensuring that all behaviors are correct,
the linearizability monitoring problem has a more modest ask — given an execution history
obtained from the implementation of a concurrent data structure, is this history
equivalent to some execution obtained from a sequential implementation?
Linearizability monitoring forms a fundamental component of stress testing approaches
and efficient algorithms for solving this directly translate to efficiency in the testing process.
This is indeed the theme of this work — how efficiently
can a given history be monitored against linearizability?

As such, the complexity of checking linearizability of a history
crucially relies on the complexity of the sequential specification itself, but
can be solved in
NP
with access to an oracle that checks for membership in the sequential specification.
Gibbons and Korach
(
Gibbons and Korach, 1997
)
undertook a systematic
complexity-theoretic investigation of linearizability monitoring against
the register data structure — objects are registers and expose their
{\tt{\color[rgb]{0.122,0.435,0.698}write}}
and
{\tt{\color[rgb]{0.122,0.435,0.698}read}}

APIs. They showed that, in general, the monitoring
problem is
NP
-complete for registers, and further proposed restrictions on register histories
for which the linearizability monitoring problem can be solved in polynomial time.
Since then, some works have studied popular data structures like
stacks and queues
(
Bouajjani et al., 2015
;
Emmi et al., 2015
;
Gibbons et al., 2002
;
Gibbons et al., 1999
)

but a unified tractability result has remained a hard challenge.
Recently though, Emmi and Enea
(
Emmi and Enea, 2017
)

proposed a wide class of data structures — collection types — which includes registers, queues, sets and stacks,
and seemingly settled the tractability question for such data structures —
they show that under the well-studied
unambiguity
restriction
(
Bouajjani et al., 2017a
;
Emmi et al., 2015
;
Bouajjani et al., 2015
;
Gibbons and Korach, 1997
;
Emmi and Enea, 2017
)

(each value is inserted at most once in the data structure), monitoring can be solved
in polynomial time, by first reducing it, in polynomial time, to the satisfiability
problem of a predicate logic formula,
which can then be transformed, in polynomial time, to a Horn-SAT instance
using a technique they call
Hornification
.

We first re-investigate this result and
identify errors in it, owing to the translation to Horn-SAT,
and show that, as such, there may not be an easy fix; see Section
10.2
for more details.
As a result, the tractability problem for collection types continues to be open,
even for the unambiguity restriction.
As our main contribution in this work,
C1

we show that
for the class of data structures
\{\texttt{{\color[rgb]{0,0.525,0.043}set}},\texttt{{\color[rgb]{0,0.525,0.043}stack}},\texttt{{\color[rgb]{0,0.525,0.043}queue}},\texttt{{\color[rgb]{0,0.525,0.043}priority-queue}}\}
,
linearizability of unambiguous histories can,
in fact, be monitored in log-linear time!

To the best of our knowledge, our work proposes the most
efficient algorithms for this class of data structures.
Our work bears similarity with the work of
Gibbons et al
(
Gibbons et al., 2002
;
Gibbons et al., 1999
)

as well as concurrent work by Abdulla et al
(
Abdulla et al., 2025
)
,
but differs from them significantly, as we discuss in Section
10.1
.

Our algorithms are based on interesting insights.
Taking the
stack
data structure as an example, our algorithm, at a high level,
works in a greedy fashion.
At every step, it attempts to identify
a
value

v
that could potentially appear at the bottom of the underlying stack
in some equivalent sequential stack history (if one exists),
and removes all operations associated with this value
v
.
In doing so, it ensures the key invariant of
linearizability preservation
— if the
history was linearizable, then removing the operations associated with
v

results in a linearizable sub-history,
and, conversely, if the resulting sub-history is linearizable, then
the original one was too.
Interestingly, our algorithms for
set
,
queue
and
priority-queue
also work
within this same template — identify a linearizability-preserving value,
remove all operations of that value and recurse.
Drawing inspiration from these algorithms, as part of our
second main contribution,
C2

we propose
a generic value-centric decrease-and-conquer algorithm for linearizability monitoring,
and show that this algorithm is sound and complete for the class of container types
.
Container types are data structures whose sequential specifications are
downward-closed with respect to the removal of all operations of any single value.
While this decrease-and-conquer algorithmic template does not, in itself,
lend to tractable monitoring algorithms, it provides a clean principle
for the design of new monitoring algorithms.
We further substantiate its utility
by instantiating it to derive our polynomial time algorithms for
checking linearizability of unambiguous

set
,
stack
,
queue
and
priority-queue
histories,
as well as for unambiguous
register
histories
(
Gibbons and Korach, 1997
)
.
These algorithms form precursors to our final log-linear time algorithms,
which can be obtained by further optimizations and amortizations using
classic data structures.

For our third main contribution,

C3

we implemented our algorithms in our tool
LinP
(available publicly at
(
Lee and Mathur, 2025b
)
) and show that it
performs significantly faster than existing linearizability monitoring tools
and scales
to a million operations under a second, leveraging the efficiency of our algorithms.

2.
Preliminaries

In this section, we present background necessary for our presentation
including concurrent histories and operations,
as well as the linearizability monitoring problem.

2.1.
Histories and Operations

Operations.

The focus of this work is to design algorithms for checking
linearizability of concurrent histories.
A history essentially records concurrent operations on
data structures implementing abstract data types (ADTs).
We can model each
operation
as a tuple

o=\langle id,p,m,v,t_{{\sf inv}},t_{{\sf res}}\rangle
.
Here,
id
is a unique identifier for the operation
o
,

p\in\mathscr{P}
denotes the process executing
o
,

m\in\mathscr{M}
denotes the method of the underlying ADT,
the component
v
is either a value
v\in\mathscr{V}

denoting the argument of the operation
o

or is the dedicated symbol
\circledcirc\not\in\mathscr{V}
(in the case of methods like
m={\tt{\color[rgb]{0.122,0.435,0.698}empty}}
)
and
t_{{\sf inv}},t_{{\sf res}}\in\mathbb{Q}_{\geq 0}

denote the (rational) time corresponding to the invocation and
response of the operation
o
;
we require that
t_{{\sf inv}}<t_{{\sf res}}
.
We will use
{\sf p}(o)
,
{\sf m}(o)
,
{\sf v}(o)
,

{\sf inv}(o)
and
{\sf res}(o)

to denote respectively the process
p
, method
m
, argument
v
,
invocation time
t_{{\sf inv}}
and response time
t_{{\sf res}}
of operation
o
.
We will often drop the unique identifier
id
since it will be clear from context.
Further, we will often use a more focused shorthand

{m}(arg)

when only the method and argument attributes of the operation in question are important.
For example, in the context of a register object, the operation
{{\tt{\color[rgb]{0.122,0.435,0.698}read}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}42}})

denotes that the value
{\tt\small{\color[rgb]{0.698,0.111,0.111}42}}
has been read (or
loaded
).
Likewise, for the set object,
the operation
{{\tt{\color[rgb]{0.122,0.435,0.698}insert}}_{{\tt{\color[rgb]{0.122,0.435,0.698}ok}}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}1}})
denotes a
fresh
insertion
of the value
{\tt\small{\color[rgb]{0.698,0.111,0.111}1}}
in the set object in consideration when the set does
not already contain this value.
Linearizability is a
local
property
(
Herlihy and Wing, 1990
)
:
the monitoring problem for histories with multiple objects (i.e., ADT instances) is linear-time reducible
to the same problem for individual objects.
We, therefore, omit object identifiers in our formalism.
Finally, we reserve the special symbol
\circledcirc

to be used in an operation
o
which denote that the underlying data structure
is ‘empty’ when performing
o
.
For example, in the case of
queue
, an operation
o
with

{\sf v}(o)=\circledcirc
(and
{\sf m}(o)={\tt{\color[rgb]{0.122,0.435,0.698}empty}}
) denotes the case when
when a client of
issues an emptiness query, or alternatively,
issues a dequeue request which fails because the underlying queue is empty.

Histories.

A
concurrent history
(or simply history)
H
is a finite set of operations.
For instance, the following history of a queue object

H_{\sf queue}=\{o_{1}=\langle p_{1},{\tt{\color[rgb]{0.122,0.435,0.698}enq}},{\tt\small{\color[rgb]{0.698,0.111,0.111}3}},1,3\rangle,o_{2}=\langle p_{2},{\tt{\color[rgb]{0.122,0.435,0.698}deq}},{\tt\small{\color[rgb]{0.698,0.111,0.111}3}},2,4\rangle\},

comprises of two operations
o_{1}
and
o_{2}
performed respectively
by processes
p_{1}
and
p_{2}
.

o_{1}
enqueues value
{\tt\small{\color[rgb]{0.698,0.111,0.111}3}}
in the invocation/response interval
[1,3]
.

o_{2}
is a dequeue operation of value
{\tt\small{\color[rgb]{0.698,0.111,0.111}3}}
by process
p_{2}
in the interval
[2,4]
.
The size
|H|
of a history
H
denotes the number of operations in
H
.
We use
\mathscr{T}_{H}=\bigcup_{o\in H}\{{\sf inv}(o),{\sf res}(o)\}

to denote the set of invocation and response times in
H
,
and
\mathscr{V}_{H}=\{{\sf v}(o)\,|\,o\in H\}
of values of operations in
H
.
We also use
H|_{v}=\{o\in H\,|\,{\sf v}(o)=v\}
to denote the
subhistory of
H
containing exactly those operations whose value is
v
.
Likewise,
H|_{p}
(resp.
H|_{m}
) denotes the sub-history
of operations in
H
performed by process
p
(resp. whose method is
m
).
A history

is said to be

if all time intervals in it are non-overlapping,
i.e., for every pair
o_{1}\neq o_{2}\in H
, we have
either
{\sf res}(o_{1})<{\sf inv}(o_{2})
or

{\sf res}(o_{2})<{\sf inv}(o_{1})
.
Histories are assumed to be well-formed, i.,e, for each process
p\in\mathscr{P}
,
the sub-history
H|_{p}
is sequential.

2.2.
The Linearizability Monitoring Problem

Linearizations.

A
linearization
of history
H
is an injective mapping

\ell:H\to\mathbb{Q}_{\geq 0}
of operations in
H
to timestamps such
that for every
o\in H
,
{\sf inv}(o)<\ell(o)<{\sf res}(o)
.
In other words, a linearization is a total order of the operations
of a history that also respects their invocation and response times.
For the queue history
H_{\sf queue}
above,
two of the many possible linearizations include
\ell_{1}=\{o_{1}\mapsto 2.5,o_{2}\mapsto 3.5\}
and

\ell_{2}=\{o_{1}\mapsto 2.75,o_{2}\mapsto 2.5\}
.
Of course,
\ell_{2}
does not meet the
sequential specification
of a queue object;
see next.

Sequential Specifications.

The sequential specification of an abstract data type (ADT)
\mathcal{D}
, with methods
\mathscr{M}_{\mathcal{D}}
,
expresses all possible behaviors of an object of the ADT when the object is invoked by a sequential client.
Formally, an
abstract operation
is a pair
o=\langle m,v\rangle
, where

m\in\mathscr{M}_{\mathcal{D}},v\in\mathscr{V}

(alternatively denoted
o={m}(v)
).
An
abstract sequential history
is a finite sequence

\tau=o_{1}\cdot o_{2}\cdots o_{n}
of abstract operations.
The
sequential specification

\mathbb{T}_{\mathcal{D}}
of an abstract data type

\mathcal{D}
is a prefix-closed set of abstract sequential histories
and captures the intuitive operational meaning of the ADT.
As an example, the sequential specification
{\mathbb{T}}_{\texttt{{\color[rgb]{0,0.525,0.043}queue}}}
of the queue ADT
will include the sequence

\tau_{1}={{\tt{\color[rgb]{0.122,0.435,0.698}enq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}1}})\cdot{{\tt{\color[rgb]{0.122,0.435,0.698}enq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}2}})\cdot{{\tt{\color[rgb]{0.122,0.435,0.698}deq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}1}})\cdot{{\tt{\color[rgb]{0.122,0.435,0.698}deq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}2}})

but exclude the sequence

\tau_{2}={{\tt{\color[rgb]{0.122,0.435,0.698}enq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}1}})\cdot{{\tt{\color[rgb]{0.122,0.435,0.698}deq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}2}})\cdot{{\tt{\color[rgb]{0.122,0.435,0.698}enq}}}({\tt\small{\color[rgb]{0.698,0.111,0.111}2}})
.
We will present precise sequential specifications for the concrete
data types considered in the paper in subsequent sections.

Linearizability.

A linearization
\ell
of a history
H
naturally induces an abstract sequential
history, namely the sequence
\tau_{\ell}={\sf abs}(o_{1})\cdot{\sf abs}(o_{2})\cdots{\sf abs}(o_{n})

corresponding to the unique total order
on operations of
H
such that
\ell(o_{i})<\ell(o_{i+1})
for every
1\leq i<n
.
Here,
{\sf abs}(o)
denotes the abstract operation
\langle{\sf m}(o),{\sf v}(o)\rangle

corresponding to the operation
o
.
We say that linearization
\ell
of history
H
is a
legal linearization

with respect to an ADT specification
\mathbb{T}_{\mathcal{D}}

if the abstract sequential history
\tau_{\ell}
(as defined above)
satisfies
\tau_{\ell}\in\mathbb{T}_{\mathcal{D}}
.
If
\ell
is a legal linearization, then we also abuse notation
and write
\ell\in\mathbb{T}_{\mathcal{D}}
.

We now define the
linearizability monitoring
problem, also referred to as
the problem of
verifying linearizability
in
(
Gibbons and Korach, 1997
)
.

Definition 2.1 (Linearizable History).

Let
\mathbb{T}_{\mathcal{D}}
be a sequential specification
corresponding to some abstract data type
\mathcal{D}
.
A concurrent history
H
(derived from, say, an actual concurrent implementation of
\mathcal{D}
),
is said to be
linearizable
with respect to
\mathbb{T}_{\mathcal{D}}

if there is a linearization
\ell
of
H
such that
\ell\in\mathbb{T}_{\mathcal{D}}
.

Problem 1 (Monitoring Linearizability).

Let
\mathbb{T}_{\mathcal{D}}
be a sequential specification
corresponding to some abstract data type
\mathcal{D}
.
The linearizability monitoring problem against
\mathbb{T}_{\mathcal{D}}

asks if a given input concurrent history
H
is linearizable.

2.3.
LTSs for sequential specifications

While the sequential specifications for many ADTs are often
well understood, it will be helpful for the rigor of our presentation
to also formulate them precisely.
For many popular ADTs, including all of the ones we consider
in our work, a natural form of specification is through the use of
a
labeled transition system
(LTS)
where the states of the system essentially capture the internal state
of the ADT, labels on transitions represent valid actions,
and valid paths in the LTSs directly translate to abstract sequential histories.
Formally, for an ADT
\mathcal{D}
over methods
\mathscr{M}
and values
\mathscr{V}
, an LTS for its sequential specification,
has the form
{\sf LTS}_{\mathcal{D}}=(S_{\mathcal{D}},s_{0},\rightarrow)
, where
S_{\mathcal{D}}
is a set of states,
intuitively representing the set of internal states of a typical sequential implementation of
\mathcal{D}
;

s_{0}\in S
is the initial state.
The transition relation has the form
\rightarrow\subseteq S_{\mathcal{D}}\times\Lambda_{\mathcal{D}}\times S_{\mathcal{D}}
,
where transitions are labeled from the set
\Lambda_{\mathcal{D}}=\{m(v)\,|\,m\in\mathscr{M},v\in\mathscr{V}\}

of abstract operations of
\mathcal{D}
;
we will also write
(s\xrightarrow{m(v)}s^{\prime})
to denote a transition triple

(s,m(v),s^{\prime})\in\rightarrow
.
A run of such an LTS is a finite sequence

\rho=(q_{0}\xrightarrow{m_{0}(v_{0})}q^{\prime}_{0})\cdot(q_{1}\xrightarrow{m_{1}(v_{1})}q^{\prime}_{1})\cdots(q_{k}\xrightarrow{m_{k}(v_{k})}q^{\prime}_{k})
such that
q_{0}=s_{0}
,
for each
i<k
, we have
q^{\prime}_{i}=q_{i+1}
and for each
i\leq k
,

(q_{i}\xrightarrow{m_{i}(v_{i})}q^{\prime}_{i})\in\rightarrow
.
The labeling of a run
\rho
is the abstract sequential history
denoted by the sequence
\lambda(\rho)=m_{0}(v_{0})\cdot m_{1}(v_{1})\cdots m_{k}(v_{k})
of abstract
operations in
\rho
.
In this sense, the sequential specification of the ADT
\mathcal{D}
presented as
\mathsf{LTS}_{\mathcal{D}}

is precisely the set
\mathbb{T}_{\mathcal{D}}=\{\lambda(\rho)\,|\,\rho\text{ is a run of }\mathsf{LTS}_{\mathcal{D}}\}
.
Consider, for example the sequential specification for the
register
ADT
below, whose methods are
{\tt{\color[rgb]{0.122,0.435,0.698}read}}
and
{\tt{\color[rgb]{0.122,0.435,0.698}write}}
.

​​
Register data structure
:
\mathscr{M}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}=\{{\tt{\color[rgb]{0.122,0.435,0.698}read}},{\tt{\color[rgb]{0.122,0.435,0.698}write}}\}
,
S_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}=\mathscr{V}\uplus\{\bot\}
,
s_{0}=\bot

\displaystyle\begin{array}[]{ccccc}\frac{\begin{array}[]{c}s=s^{\prime}=v\in\mathscr{V}\end{array}}{\begin{array}[]{c}s\xrightarrow{{{\tt{\color[rgb]{0.122,0.435,0.698}read}}}(v)}s^{\prime}\end{array}}&&\frac{\begin{array}[]{c}s^{\prime}=v\end{array}}{\begin{array}[]{c}s\xrightarrow{{{\tt{\color[rgb]{0.122,0.435,0.698}write}}}(v)}s^{\prime}\end{array}}\end{array}

Each judgement rule indicates a transition of
\mathsf{LTS}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}
.
States are values (indicating the current value of the register).
A transition labeled with
{\tt{\color[rgb]{0.122,0.435,0.698}read}}(v)
is enabled only when
the state is not
\bot
and reflects
the value in the transition label,
and moreover, the state after this transition
stays the same.
Likewise a write operation changes the state to the value being written to.
Observe that a run in
\mathsf{LTS}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}
is essentially a sequence of read and write operations
where every read is preceded by atleast one write
and observes the value of the latest write before it.

2.4.
Complexity of Linearizability Monitoring and the Unambiguity Restriction

In general, solving the linearizability monitoring problem — given a history
H
,
is there a linear order of its operations
that will meet a given sequential specification
\mathbb{T}_{\mathcal{D}}
? — may require
a search over exponentially many permutations of the operations in
H
.
Indeed, this is likely the best one can do —
Gibbons and Korach
(
Gibbons and Korach, 1997
)
showed that
the linearizability monitoring problem is
NP
-hard
even for the simplest data type
register
s.

Nevertheless, for the
register
data type, Gibbons and Korach also identify a useful
restriction for which the problem becomes tractable —
the
reads-from
restriction.
Here, in addition to the register history
H
, the input is a reads-from
mapping
\mathsf{rf}_{H}
that disambiguates,
for each read operation, the write operation (of the same value) that it must read from,
and the ask is to determine if there is a linearization
that obeys this mapping, i.e., the latest write that precedes
a read operation
o_{r}
is precisely
o_{r}
is
\mathsf{rf}_{H}(o_{r})
.
Equivalently, the input is a history where each write operation has a unique value.
Gibbons and Korach show that, under this restriction,
the linearizability monitoring problem can be solved using an
O(n\log n)
time algorithm
(
Gibbons and Korach, 1997
)
.

This insight has been extended to the analogous but more general

unambiguity restriction
for histories of a larger
class of data structures, beyond registers
(
Bouajjani et al., 2017a
;
Emmi et al., 2015
;
Bouajjani et al., 2015
;
Gibbons and Korach, 1997
;
Emmi and Enea, 2017
)
,
and is also a key focus of this work.
While a more semantic definition of this restriction is possible,
we present the more intuitive and syntactic definition of this restriction here.
To be able to formally define such a restriction for each custom data type
\mathcal{D}
,
we need to first identify a subset of methods
{\mathscr{M}}^{\mathsf{Add}}_{\mathcal{D}}\subseteq\mathscr{M}_{\mathcal{D}}

that intuitively ‘add’ some value in the internal
state of the underlying data structure.
As an example, for the
stack
ADT, we have
{\mathscr{M}}^{\mathsf{Add}}_{\texttt{{\color[rgb]{0,0.525,0.043}stack}}}=\{{\tt{\color[rgb]{0.122,0.435,0.698}push}}\}

while for the
register
ADT, we have
{\mathscr{M}}^{\mathsf{Add}}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}=\{{\tt{\color[rgb]{0.122,0.435,0.698}write}}\}
.
Likewise, we need to identify a subset of methods
{\mathscr{M}}^{\mathsf{Remove}}_{\mathcal{D}}\subseteq\mathscr{M}_{\mathcal{D}}

that ‘remove’ a value.
Continuing our previous examples,
{\mathscr{M}}^{\mathsf{Remove}}_{\texttt{{\color[rgb]{0,0.525,0.043}stack}}}=\{{\tt{\color[rgb]{0.122,0.435,0.698}pop}}\}

while
{\mathscr{M}}^{\mathsf{Add}}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}=\varnothing
since no method in the
register
ADT explicitly
removes the value written to a register.
We further require that
{\mathscr{M}}^{\mathsf{Add}}_{\mathcal{D}}\cap{\mathscr{M}}^{\mathsf{Remove}}_{\mathcal{D}}=\varnothing
.

Unambiguous histories.

We can now formally define the unambiguity restriction on histories as follows.
A history of ADT
\mathcal{D}
is said to be an
unambiguous

history if for every value
v\in\mathscr{V}_{H}\setminus\{\circledcirc\}
, there is a unique operation that
‘add’s the value
v
, and also a unique (or none at all) operation
that ‘remove’s the value
v
, i.e.,

|\{o\in H\,|\,{\sf v}(o)=v,{\sf m}(o)\in{\mathscr{M}}^{\mathsf{Add}}_{\mathcal{D}}\}|=1

and

|\{o\in H\,|\,{\sf v}(o)=v,{\sf m}(o)\in{\mathscr{M}}^{\mathsf{Remove}}_{\mathcal{D}}\}|\leq 1
.
In other words, in an unambiguous history, the add and the remove operation
can be unambiguously identified for each value.
As an example, the
stack
history

The unambiguity restriction, as defined, is both realistic and straightforward to implement in practical settings.
In most implementations of concurrent data structures, each inserted value can be assigned a unique identifier.
This identifier may be derived from a combination of thread identifiers and local counters, or generated using an atomic fetch-and-add operation on a shared memory region.
Either approach ensures the unambiguity of concurrent histories generated.

3.
Linearizability Monitoring for Container Types

In this section, we formalize our decrease-and-conquer framework,
and
characterize a class of data types (i.e., sequential specifications)
for which this framework yields a sound and complete algorithm
for linearizability monitoring.
Recall that the we defined the ‘unambiguity’ restriction
(Section
2.4
) by generalizing the (register-specific) ‘reads-from’ restriction
to arbitrary data types.
In the same spirit, our framework can also be viewed as a generalization of the algorithm
for monitoring of register histories under the reads-from restriction.
At a very high level, the algorithm for unambiguous register
histories, due to Gibbons and Korach
(
Emmi and Enea, 2017
)
,

clusters
together operations of the same value;
the reads-from restriction ensures that each such
cluster contains a unique write operation
o_{w}
and exactly all the read
with the value
{\sf v}(o_{w})
of
o_{w}
.
Next, for each value
v\in\mathscr{V}(H)
in the history
H
,
the algorithm computes some summary metadata for the cluster of
v

(namely an interval
\mathsf{zone}_{v}=[t_{{\sf res}}^{v},t_{{\sf inv}}^{v}]

between the earliest response time
t_{{\sf res}}^{v}
and the
latest invocation time
t_{{\sf inv}}^{v}
in
H|_{v}
),
and finally checks the compatibility of the metadata for each
pair of clusters.

An overview of our decrease-and-conquer approach.

In this work though, we propose that this algorithm (for monitoring against
{\mathbb{T}}_{\texttt{{\color[rgb]{0,0.525,0.043}register}}}
)
can instead be formulated
in a
greedy
style —
(1) pick a specific value
v
(in the case of registers, picking any value suffices),
(2) check the compatibility of
v
by comparing its metadata with that of all other values,
(3) upon success, remove all operations of
v
(‘decrease’) from consideration and recurse (‘conquer’)
on the residual history, and
(4) upon failure, declare non-linearizability.
Our framework essentially generalizes this greedy algorithm.
A key ingredient here is the choice of the value to pick at each step;
a bad choice may result in an unsound or incomplete algorithm.
In Section
3.2
, we characterize this class of

linearizability-preserving
values,
which when picked ensure soundness and completeness.
We show that, this greedy decrease-and-conquer can seamlessly unify
linearizability monitoring algorithms for a large class of data types,
which we call ‘container’ data types, defined in Section
3.1
.
In Section
3.3
,
we outline how our decrease-and-conquer framework does not necessarily
reduce the complexity of linearizability monitoring but instead
cleanly delegates the burden of the algorithm on finding linearizability-preserving
values, which can be solved in isolation, often in polynomial time.

3.2.
Linearizability-Preserving Values

Recall the overall gist of our greedy approach — at each step,

accurately determines if

As a consequence, both the problems of linearizability monitoring of histories as well as the problem of determining if a value is linearizability preserving are
equi-tractable

both are solvable in polynomial time, or both are
NP
-hard.

Making histories well-matched.

Recall that, the unambiguity restriction asks that the input history
H

has, for each value
v\in\mathscr{V}_{H}
, exactly one operation whose method comes from
the pre-defined set
{\mathscr{M}}^{\mathsf{Add}}
and
also at most one operation with method from the
other pre-defined set
{\mathscr{M}}^{\mathsf{Remove}}

When for a value

matched
,
and say that

is

We say that an unambiguous history

is

if for every
v\in\mathscr{V}_{H}\setminus\{\circledcirc\}
,

is matched in

For each data structure

\mathcal{D}\in\{\texttt{{\color[rgb]{0,0.525,0.043}set}},\texttt{{\color[rgb]{0,0.525,0.043}stack}},\texttt{{\color[rgb]{0,0.525,0.043}queue}},\texttt{{\color[rgb]{0,0.525,0.043}priority-queue}}\}

we consider, there is a unique dedicated add
method

and also a unique dedicated
remove method
{\sf m}{}^{\mathsf{Remove}}_{\mathcal{D}}

(i.e.,
{\mathscr{M}}^{\mathsf{Add}}_{\mathcal{D}}=\{{\sf m}{}^{\mathsf{Add}}_{\mathcal{D}}\}

and
{\mathscr{M}}^{\mathsf{Remove}}_{\mathcal{D}}=\{{\sf m}{}^{\mathsf{Remove}}_{\mathcal{D}}\}
).
Fortunately, this means that unambiguous histories can be extended
using a simple linear time procedure so that the resulting histories are
well-matched.
For each unmatched value
v
in an unambiguous history
H
on
\mathcal{D}
,
we add an operation
o_{v}^{\mathsf{Remove}}
to

with
{\sf v}(o)=v
,

{\sf m}(o)={\sf m}{}^{\mathsf{Remove}}_{\mathcal{D}}
,

{\sf inv}(o)=t

{\sf res}(o)=t+1

where

We observe that, this such an extension takes
O(n)

(n =
|H|
), and for the data structures we study,
it results in a history that is linearizable iff
H
is.
For the remaining of this paper, we shall assume that our histories are well-matched.

Adjusting invocation and response times.

For each
\mathcal{D}\in\{\texttt{{\color[rgb]{0,0.525,0.043}set}},\texttt{{\color[rgb]{0,0.525,0.043}stack}},\texttt{{\color[rgb]{0,0.525,0.043}queue}},\texttt{{\color[rgb]{0,0.525,0.043}priority-queue}}\}{}

At a high level, our algorithm for monitoring

Intuitively, such a value

in some legal linearization, if one exists.
Consider, for example,

{\tt{\color[rgb]{0.122,0.435,0.698}pop}}({\tt\small{\color[rgb]{0.698,0.111,0.111}1}})

(2)

)
This indeed aligns with the intuition behind how we defined potentially bottom values:
if

cannot interfere with the operations of other values, and removing the operations of

Let

be a standardized unambiguous

6.2.

stack

In this section, we describe our
O(n\log n)
time algorithm
for linearizability monitoring of
stack
histories,
significantly improving upon the vanilla
O(n^{4})
time bound above,
or the algorithms in prior works
(
Gibbons et al., 2002
;
Abdulla et al., 2025
)
.
Our optimized algorithm maintains a global shared
state across multiple calls of the procedure

GetLinPreservingValue
(presented in Algorithm
5
)
that returns a potentially bottom value if one exists,
and uses simple data structures to amortize the overall time complexity.

Overview.

At a high-level, in addition to values, the algorithm also treats
individual operations, as well as
partitions
of the history,
as first class concepts.
A partition
I
of a history is simply a contiguous time interval
induced by two consecutive time points (either invocation or response times) in the history;
there are
2n
time points and thus
2n+1
partitions in a history of
n
operations.
Intuitively, each partition
I
is an equivalence class, in the sense that,
if the span interval
({\sf inv}(o),{\sf res}(o))
of an operation
o

intersects
I
, then in fact the entirety of
I
is in this span, i.e.,

I\subseteq({\sf inv}(o),{\sf res}(o))
.
This allows the design of an algorithm that can work with entire
partitions at once and is a key ingredient for efficiency.
The algorithm is iterative.
In each iteration, it determines
which operation
o
can be marked safe,
in that, it has already fulfilled the obligations of
Definition
6.1
.
To determine this, the algorithm attempts to find
a partition
I
that can witness the safety of
o
.
We observe that a safe operation remains safe in future iterations
(see Proposition
6.3
as the formal statement).
At any iteration, if all the operations of a value
v

are either marked safe in previous iterations, or in the most recent iteration,
then
v
is also guaranteed to be a potentially bottom value.
If no such value can be identified, then
\bot
can be regarded
as a linearizability-preserving value, i,e., the stack history is non-linearizable.
The algorithm makes use of segment tree and interval tree data structures in tandem,
to store partitions and operations, to efficiently query
plausible witness partitions together with the operations corresponding to them,
and to efficiently remove such operations.
In the following we formalize when an interval is safe for an operation,
noting some helpful observations that follow.

9.
Empirical Evaluation

The primary goal of our evaluation is to demonstrate the effectiveness of our log-linear
algorithms for unambiguous
set
(Section
5
),
stack
(Section
6
),

queue
(Section
7
) and
priority-queue
(Section
8
) data structures,
on histories derived from publicly available implementations of such data structures.
Towards this, we will evaluate
(
RQ1
) whether their improved asymptotic complexity
translates to better empirical performance compared to existing state-of-the-art tools, and
(
RQ2
) whether the algorithms maintain consistent log-linear scaling behavior
across increasingly large problem instances, establishing their suitability for
production-scale linearizability monitoring.

Implementation.

We have implemented all our algorithms in our tool
LinP

(
Lee and Mathur, 2025b
)
.

LinP
is primarily written in C++ to leverage its high performance and efficiency.
The input to
LinP
is a history specified as a sequence of invocation and response events,
where each event includes the details of the process that performs the event
as well as the method and the value of the corresponding operation.
We use the Scal framework
(
Haas et al., 2015
)
for obtaining implementations of concurrent data structures
as well as examples of client code that uses them.
Scal ships with suite of common implementations of data structures, including
queue
and
stack
.
Scal’s suite of implementations, however, does not include any implementation
for concurrent
set
and
priority-queue
, and for these data structures, we
implemented a custom lock-based implementation
(as a result, the histories they generate are guaranteed to be linearizable)
and a simple client based on Scal’s producer-consumer routine framework.

Compared tools and setup.

We benchmark
LinP
’s performance against other existing
state-of-the-art tools whose implementations are also publicly available:
Violin
(
Emmi et al., 2015
)
, Verilin
(
Jia et al., 2023
)
and the tool LiMo
due to more recent concurrent work
(
Abdulla et al., 2025
)
.
We remark that Violin and LiMo provides only implementations
of linearizability checkers for
stack
and
queue
data types.
Several implementations of concurrent

stack
and
queue
omit
{\tt{\color[rgb]{0.122,0.435,0.698}peek}}
operations,
and Violin and LiMo do not account for these operations.
We find that in absence of
{\tt{\color[rgb]{0.122,0.435,0.698}peek}}
operations,
further optimizations can significantly improve
LinP
’s performance,
and we include them in our evaluation against Violin and LiMo.
For the second part of our empirical evaluation where we gauge how far
LinP
scales,
we generated highly concurrent histories (20 consumers and 20 producers)
with up to 1,000,000 operations and
stress tested
LinP
’s performance against them.
We also compare its average performance (across 10 histories per data point)
with and without optimizations for excluding
{\tt{\color[rgb]{0.122,0.435,0.698}peek}}
operations.
Our results show that the constant factor improvement
is indeed worth considering for practical applications.
Our experiments are conducted on WSL Ubuntu 20.04 with 2.5GHz CPU and 8GB RAM.

Related Work and Discussion

Linearizability and its monitoring.

Gibbons and Korach
(
Gibbons and Korach, 1997
)

initiated the complexity-theoretic study of linearizability,
showing
NP
-hardness in general and tractability for unambiguous registers.
Given the intractability, a thorough complexity-theoretic understanding
of this problem has remained elusive for a broader class of
data structures, except for the work of
(
Emmi and Enea, 2017
)
,
which, as we show in Section
10.2
has incorrect results.
In
(
Gibbons and Korach, 1997
;
Gibbons et al., 2002
)
Gibbons et al studied
the linearizability monitoring problems for stacks, queues, priority queues
and other data structures in the setting when distinct values are inserted
in the data structure, and more recently
Abdulla et al
(
Abdulla et al., 2025
)
also study the problem for stacks, queues, sets
and multisets when the input histories are
data differentiated
, and also propose
efficient algorithms.
While there is overlap in some of our results and that
of
(
Abdulla et al., 2025
;
Gibbons et al., 1999
;
Gibbons et al., 2002
)
, our work improves these results
on several fronts, as we discuss in Section
10.1
.
Recent practical tools for monitoring take the stress testing
approach
(
Koval et al., 2023
;
Potapov et al., 2024
)
,
where for a given implementation of a concurrent data structure, one looks
for a large number of executions to see if any of them violate linearizability,
and for the sake of flexibility, implement generic algorithms that
enumerate exponentially many interleavings, either explicitly
(
Jia et al., 2023
;
Burckhardt et al., 2010
;
Wing and Gong, 1993
;
Lowe, 2017
;
Zhang, 2011
;
Horn and Kroening, 2015
)
or symbolically
(
Golovin et al., 2025
;
Emmi et al., 2015
)
,
and occasionally using small depth heuristics
(
Ozkan et al., 2019
)
.
Besides the classic notion of linearizability proposed by Herlihy and Wing
(
Herlihy and Wing, 1990
)
,
other notions such as strong linearizability
(
Golab et al., 2011
)
,
quantitative relaxations of specifications
(
Henzinger et al., 2013a
)
as well as
durable linearizability
(
Izraelevitz et al., 2016
)
have been proposed.

Automated and deductive verification for linearizability.

On the front of checking entire programs, decidability
results have been shown, including
for that against regular specifications
(
Alur et al., 1996
;
Hamza, 2015
)
for bounded
domain programs or restrictions on how the data structures are invoked
(
Černý et al., 2010
)
,
outside of which, undecidability persists
(
Bouajjani et al., 2013
)
.
Nevertheless, semi-decidable techniques have been extensively studied
(
Dongol and Derrick, 2015
)
.
Several deductive proof systems for verifying linearizability for data structure
algorithms and implementations
(
Jayanti et al., 2024
;
Jung et al., 2019
;
Henzinger et al., 2013b
)
,
but require significant manual annotation.

Monitoring other concurrency-centric properties.

With recent industrial adoption of model checking,
the core monitoring questions for concurrent programs and their algorithmic
and complexity-theoretic aspects have become popular.
The work on verifying sequential consistency by Gibbons and Korach
(
Gibbons and Korach, 1997
)
has now inspired
further work including sub-classes
(
Cantin et al., 2005
;
Abdulla et al., 2018
;
Agarwal et al., 2021
)
,
other memory models
(
Gontmakher et al., 2003
;
Chakraborty et al., 2024
;
Tunç et al., 2023a
;
Chini and Saivasan, 2020
)
,
database isolation levels
(
Biswas and Enea, 2019
;
Møldrup and Pavlogiannis, 2025
)
,
distributed systems consistency levels
(
Bouajjani et al., 2017b
;
Biswas and Enea, 2019
)

and runtime predictive
analysis
(
Mathur et al., 2020
;
Kulkarni et al., 2021
;
Mathur et al., 2021
;
Farzan and Mathur, 2024
;
Ang and Mathur, 2024
;
Shi et al., 2024
;
Shi et al., 2025
;
Ang et al., 2025
;
Mathur and Viswanathan, 2020
;
Kini et al., 2017
;
Mathur and Pavlogiannis, 2022
;
Pavlogiannis, 2019
;
Tunç et al., 2023b
)
.

10.1.
Detailed comparison with Gibbons et al
(
Gibbons et al., 1999
)
and Abdulla et al
(
Abdulla et al., 2025
)

Gibbons et al
(
Gibbons et al., 2002
)
, and more recently Abdulla et al
(
Abdulla et al., 2025
)

also study the linearizability monitoring problem for stacks (both), queues (both),
priority queues (
(
Gibbons et al., 2002
)
) and sets (
(
Abdulla et al., 2025
)
)
and propose similar tractability results under similar restrictions like unambiguity.
Apart from our generic decrease-and-coquer algorithmic framework,
there are significant differences between the our log linear algorithms and
their algorithms for the same data structures.
The first difference comes from the choice of operations.
Notably, in our work we consider histories
with peek/contains operations as well as ‘failed’ operations
(which we denote using
{\tt{\color[rgb]{0.122,0.435,0.698}empty}}
operations), which is in sharp contrast to both prior
works
(
Gibbons et al., 2002
;
Abdulla et al., 2025
)
.
In absence of peek operations, the unambiguity restriction boils down to
the more restricted version where each pair of method name and
value appears exactly once (‘data differentiated’
(
Abdulla et al., 2025
)
),
where there is a unique pair of ‘matching’ operations per value.
This simplicity allows for the design of algorithms that
take constantly many
O(n)
passes on the input.
We think that both sets of algorithms
(
Gibbons et al., 2002
;
Abdulla et al., 2025
)

cannot be easily extended to include such operations.
Our algorithm naturally, yet carefully, accounts for peek events,
in overall
O(n\log{n})
time.
Intuitively, disallowing peek/contains operations in is analogous
to disallowing multiple reads of the same value in a register history,
and thus unnatural; we also remark that Gibbons and Korach do account
for multiple reads of the same value in their very first work
(
Gibbons and Korach, 1997
)
.
Likewise, exteding the algortihmic insights of
(
Abdulla et al., 2025
;
Gibbons et al., 1999
)

to account for ‘failed’ operations also appears non-trivial.
The second significant improvement is due to the complexity of
monitoring for stacks.
The algorithm in
(
Abdulla et al., 2025
)
works in
O(n^{2})
time.
The algorithm in
(
Gibbons et al., 2002
)

works in
O(n^{3})
time and is fundamentally different from ours because
it addresses a more general problem (VSC problem) when the input history does not
necessarily induce an
interval order
. In this setting, when one also considers
peek operations, the monitoring problem becomes
NP
-hard
since there is a simple polynomial time many-one
reduction from the VSC problem of unambiguous registers
to VSC problem of unambiguous stacks.

10.2.
Collection types and OOS Linearizability
(
Emmi and Enea, 2017
)

In 2018, Emmi and Enea proposed a tractability result
for linearizability monitoring of unambiguous histories of a class
of data types called
collection types
, defined by a semantic characterization
(
Emmi and Enea, 2017
)
.
This tractability argument presented is two-folds:
First, it is shown that, for collection types, each instance of the linearizability
monitoring problem for unambiguous histories can be mapped in polynomial time
to an instance of another problem —- OOS linearizability (for a fixed quantifier rank).
The input to an OOS Linearizability problem is a first order logic formula
(‘Operation Order Specification’ or OOS for short), that encodes
the happens-before constraints of the given history, together with the
constraints of the sequential specification of the collection type in question,
and the linearizability problem boils down to checking if the formula
is satisfiable in a model, equipped with a total order that is consistent with
the happens-before constraint encoded in the formula.
Second, it is argued that
OOS linearizability can be solved in polynomial time for OOS’es of fixed quantifier ranks.
We revisit the second step and argue that OOS linearizability (even for quantifier rank of
\leq 3
)
is
NP
-hard (in contrast to
(
Emmi and Enea, 2017
)
),
and preset the full proof in Appendix
H
:

Theorem 10.1.

OOS Linearizability is
NP
-hard.

We also identify the error in the (incorrect) tractability
claim of the OOS linearizability problem, and identified

Hornification
as the source of unsoundness.
In essence, an OOS is
equisatisfiable with its (quantifier-free) ground instantiation (which
is only polynomially longer when the quantifier rank of the OOS is fixed)
that only contains happens-before constraints.
Hornification then asks to come transform this resulting quantifier-free formula
into a Horn formula, which is then argued to result into an equisatisfiable formula.
In contrast we argue that Hornification does not preserve satisfiability
and localize the issue in the proof of the equi-satisfaction claim
(see Appendix
H
).
In summary, tractability results for a generic class of
data structures (such as collection types) remains an open problem.
Our proposal of container types in Section
3.1

(which include priority queues, that are not collection types)
is a step towards obtaining a generic algorithm for linearizability monitoring, though
tractable algorithms continue to remain elusive.

11.
Conclusions and Future Work

In this work, we developed a unified decrease-and-conquer framework for the problem of linearizability monitoring, and instantiated it to obtain efficient algorithms for unambiguous
register
s,
set
s,
stack
s,
queue
s, and
priority-queue
s. Under the unambiguity restriction, we show that these fundamental data structures admit log-linear time monitors, thereby improving on the best-known complexity bounds and offering a significant performance advantage in practice. We further validated our algorithms through an implementation in
LinP
, demonstrating scalability to million-operation histories and outperforming existing state-of-the-art tools.

Beyond these contributions, our work opens several new avenues. A natural direction is to extend the decrease-and-conquer paradigm to richer concurrent objects, such as maps, dequeues, mutexes and counters. Another interesting direction is to relax the unambiguity restriction and explore whether variants of our framework can handle ambiguous or value-reuse histories without incurring exponential cost.

Appendix A
Common Lemmas

Lemma A.1 (Tightening Lemma).

Let
H
be a history and
t_{1}<t_{2}
be two rational numbers such that for all
o\in H
,
t_{1}<{\sf res}(o)
and
{\sf inv}(o)<t_{2}
. Given any linearization
\ell
, there exists another linearization
\ell^{\prime}
such that
\tau_{\ell}=\tau_{\ell^{\prime}}
and
t_{1}<\ell^{\prime}(o)<t_{2}
for all
o\in H
.

Proof.

Let
{\sf res}_{\min}=\min\{{\sf res}(o)\,|\,o\in H\}
be the minimum response time in
H
. Let
S=\{o_{1},o_{2},...,\allowbreak o_{k}\}
be the maximal subset of operations for which
\ell(o)\leq{\sf res}_{\min}
for
o\in S
, and
\ell(o_{1})<\ell(o_{2})<...<\ell(o_{k})
. By assumption,
t_{1}<{\sf res}_{\min}
. We construct an assignment of time
\ell^{\prime}
where
\ell^{\prime}(o)=\ell(o)
for
o\in H\setminus S
, and
\ell^{\prime}(o_{i})=\max\{t_{1}+\frac{i}{|S|+1}({\sf res}_{\min}-t_{1}),\ell(o_{i})\}
for
o\in S
. Notice that
{\sf inv}(o)<\ell(o)\leq\ell^{\prime}(o)<{\sf res}_{\min}\leq{\sf res}(o)
for all
o\in S
. Hence,
\ell
is indeed a linearization of
H
. Secondly,
\tau_{\ell}
and
\tau_{\ell^{\prime}}
remains the same (i.e.
\ell^{\prime}(o_{1})<\ell^{\prime}(o_{2})<...<\ell^{\prime}(o_{k})<{\sf res}_{\min}
). Lastly,
t_{1}<\ell^{\prime}(o)<{\sf res}_{\min}
for
o\in S
.

Symmetrically, we can construct a reassignment
\ell^{\prime\prime}
from
\ell^{\prime}
for operations in the set
\{o\in H\;|\;\ell^{\prime}(o)>\max\{{\sf inv}(o)\;|\;o\in H\}\}
such that
\ell^{\prime\prime}(o)<t_{2}
for
o\in S
. The conclusion follows.
∎

Lemma A.2 (Flushing Lemma).

Let
H
be a history and
t_{1}<t_{2}
be two rational numbers such that for all
o\in H
,
t_{1}<{\sf res}(o)
and
{\sf inv}(o)<t_{2}
. Given any linearization
\ell
, there exists linearizations
\ell^{\prime}
and
\ell^{\prime\prime}
such that:

(1)

\tau_{\ell}=\tau_{\ell^{\prime}}=\tau_{\ell^{\prime\prime}}
,

(2)

\ell^{\prime}(o)\leq\min\{t_{2},\ell(o)\}
for all
o\in H
, and

(3)

\max\{t_{1},\ell(o)\}\leq\ell^{\prime\prime}(o)
for all
o\in H
.

Proof.

By Lemma
A.1
, there exists legal linearization
\ell^{\prime\prime\prime}
such that
\tau_{\ell}=\tau_{\ell^{\prime\prime\prime}}
and
t_{1}<\ell^{\prime\prime\prime}(o)<t_{2}
for all
o\in H
. We then construct
\ell^{\prime}
where
\ell^{\prime}(o)=\min\{\ell^{\prime\prime\prime}(o),\ell(o)\}
for all
o\in H
. Clearly,
\ell^{\prime}(o)\leq\min\{t_{2},\ell(o)\}
. Secondly,
\ell^{\prime}
must be a linearization since
{\sf inv}(o)\leq\ell^{\prime\prime\prime}(o),\ell(o)\leq{\sf res}(o)
.

Let
o_{1},o_{2}\in H
be two operations such that
\ell(o_{1})<\ell(o_{2})
, and thus,
\ell^{\prime\prime\prime}(o_{1})<\ell^{\prime\prime\prime}(o_{2})
. Suppose
\ell^{\prime}(o_{1})\geq\ell^{\prime}(o_{2})
. By construction,
\ell^{\prime}(o_{1})
is one of
\ell(o_{1})
and
\ell^{\prime\prime\prime}(o_{1})
. Without loss of generality, assume
\ell^{\prime}(o_{1})=\ell(o_{1})
. Then it must be the case that
\ell^{\prime}(o_{2})\leq\ell^{\prime}(o_{1})=\ell(o_{1})<\ell(o_{2})
. Since
\ell^{\prime}(o_{2})<\ell(o_{2})
, we have
\ell^{\prime}(o_{2})=\ell^{\prime\prime\prime}(o_{2})
(again,
\ell^{\prime}(o_{2})
is one of
\ell(o_{2})
and
\ell^{\prime\prime\prime}(o_{2})
by construction). However, since
\ell^{\prime\prime\prime}(o_{1})<\ell^{\prime\prime\prime}(o_{2})
, we have that
\ell^{\prime\prime\prime}(o_{1})<\ell^{\prime}(o_{1})=\min\{\ell^{\prime\prime\prime}(o_{1}),\ell(o_{1})\}
, contradiction. Hence,
\ell^{\prime}
preserves the order of the abstract sequence (i.e.
\ell^{\prime}(o_{1})<\ell^{\prime}(o_{2})
for all
o_{1},o_{2}\in H
where
\ell(o_{1})<\ell(o_{2})
).

Symmetrically,
\ell^{\prime\prime}
can be constructed in the same way. The conclusion follows.
∎

Proposition B.1.

The class of collection types
(
Emmi and Enea, 2017
)
is included
in the class of container types (Definition
3.1
).

Proof.

Let
\mathbb{T}_{\mathcal{D}}
be a collection type, and
s\in\mathbb{T}_{\mathcal{D}}
be some operation sequence. If
s|_{\mathscr{V}\setminus\{v\}}=\varepsilon
, we are done as
\varepsilon\in\mathbb{T}_{\mathcal{D}}
. Now, let
s^{\prime}\cdot o=s|_{\mathscr{V}\setminus\{v\}}
for some
v\in\mathscr{V}
, operation sequence
s^{\prime}
and operation
o
.
Let
s^{\prime\prime}\cdot o
be a prefix of
s
. As specifications are prefix-closed,
s^{\prime\prime}\cdot o\in\mathbb{T}_{\mathcal{D}}
. Assume
{\sf drop}(s^{\prime\prime},\{v\})\cdot o\notin\mathbb{T}_{\mathcal{D}}
. By definition,
{\sf uses}(s^{\prime\prime}\cdot o,\{v\})
holds. Hence,
{\sf uses}^{\prime}(o,\{v\})
holds, where
{\sf uses}^{\prime}
is the local interpretation of
{\sf uses}
. Hence,
{\sf touches}(o,\{v\})
holds. By locality, since operations touch exactly the values appearing in its label,
v={\sf v}(o)
, contradicting the assumption that
s^{\prime}\cdot o=s|_{\mathscr{V}\setminus\{v\}}
.
Hence,
{\sf drop}(s^{\prime\prime},\{v\})\cdot o=s^{\prime}\cdot o\in\mathbb{T}_{\mathcal{D}}
. The conclusion follows.
∎

Lemma C.1.

Let
\mathcal{D}\in\{\texttt{{\color[rgb]{0,0.525,0.043}stack}},\texttt{{\color[rgb]{0,0.525,0.043}queue}},\texttt{{\color[rgb]{0,0.525,0.043}priority-queue}}\}
.

H
be a well-matched unambiguous and invocation-response-time-compliant history of

.

H
is linearizable iff
H\setminus H_{\circledcirc}
is linearizable,
and further, for each
o\in H_{\circledcirc}
,

V\subseteq\mathscr{V}_{H}\setminus\{\circledcirc\}
,
two subhistories
H_{o,1}=H|_{V}

and
H_{o,2}=H\setminus H_{\circledcirc}\setminus H_{o,1}
, and a time

t\in({\sf inv}(o),{\sf res}(o))
, that splits across
H_{o,1}
and
H_{o,2}
, i.e.,

(1)

for every
o^{\prime}\in H_{o,1}
,
{\sf inv}(o^{\prime})<t
, and

(2)

for all
o^{\prime}\in H_{o,2}

t<{\sf res}(o^{\prime})
.

Proof.

(
\Rightarrow

In 2018, Emmi and Enea
(

context of linearizability monitoring of unambiguous histories of a class
of data types called

This tractability argument proceeds by showing that,

NP
-hard.

At a high level, an OOS specification

The vocabulary of such formulae comes from

A model (or structure) of such an OOS formula

H.2.
Isolating the error in the proof: Hornification is unsound

Here, we investigate deeper and identify where exactly the proof of tractability
of OOS linearizability in
(
Emmi and Enea, 2017
)
breaks.
The crux of the argument in
(
Emmi and Enea, 2017
)
is two folds.
First, given an OOS formula
\varphi
and a history
H
, one can derive
a ground (i.e., quantifier-free) formula
in CNF
\psi_{H}=\varphi_{H}\land\varphi_{\textsf{total}}

containing only the relation symbol
\mathtt{before}
;
here
\varphi_{H}
is obtained by instantiating the quantifiers from

\varphi
using the model
\mathcal{A}_{H}
of the history
H
,
while the formula
\varphi_{\textsf{total}}
denotes that
\mathtt{before}
is a total
order and is obtained by instantiating the total order axioms using
\mathcal{A}_{H}
.
More importantly, it is shown that
H
is OOS linearizable for
\varphi

iff
\psi_{H}
is satisfiable (in the pure first order sense)
(
Emmi and Enea, 2017
, Lemma 5.5)
.
Following this, it is shown that the resulting ground CNF formula

\psi_{H}
can be translated
to an equisatisfiable ground Horn formula
\psi_{H}^{\textsf{Horn}}

using a
Hornification scheme

but we think this claim (see
(
Emmi and Enea, 2017
, Lemma 5.9)
) is incorrect — Hornification
does not preserve satisfiability as we show below.

Hornification does not preserve satisfiability.

Let us first recall the notion of Hornification scheme due to
(
Emmi and Enea, 2017
)
.
Recall that the first step of ground instantiation
of an OOS formula results into a ground CNF formula whose literals are of either the form

l=\mathtt{before}(o_{a},o_{b})
or
l=\neg\mathtt{before}(o_{a},o_{b})
,
where
o_{a}
and
o_{b}
represent constant symbols,
intuitively representing operations from the history in consideration.
Let us define
\sim
to be the smallest equivalence on such literals so that
for every
o,o^{\prime}
, we have
\mathtt{before}(o,o^{\prime})\sim\neg\mathtt{before}(o^{\prime},o)
.
This equivalence can then be lifted to equal-length clauses

C=(l_{1}\lor l_{2}\ldots l_{m})
and
C^{\prime}=(l^{\prime}_{1}\lor l_{2}\ldots l^{\prime}_{m})

as follows:

C\sim C^{\prime}
iff
\bigwedge l_{i}\sim l^{\prime}_{i}
.
The Hornification of a ground clause
C
is then the formula

C^{\mathsf{Horn}}=\bigwedge\limits_{C^{\prime}\sim C,\;C^{\prime}\text{ is a Horn clause}}C^{\prime}
,
and the Hornification of a ground formula
\psi=C_{1}\land C_{2}\ldots C_{k}
is
the formula
\psi^{\mathsf{Horn}}=C^{\mathsf{Horn}}_{1}\land C^{\mathsf{Horn}}_{2}\ldots C^{\mathsf{Horn}}_{k}
.

In essence, Hornification removes the non-Horn clauses
(which are imminent due to totality axioms) and replace them with all

\sim
-equivalent Horn clauses, resulting into a Horn formula.
However, such a translation does not preserve satisfiability.
Consider the formula
\psi=C_{1}\land C_{2}\land C_{3}\land C_{4}

over two constants
o_{1}
and
o_{2}
, where

\displaystyle\begin{array}[]{lcl}C_{1}=(\neg\mathtt{before}(o_{1},o_{2})\lor\mathtt{before}(o_{2},o_{1}))&&C_{2}=(\mathtt{before}(o_{1},o_{2})\lor\neg\mathtt{before}(o_{2},o_{1}))\\
C_{3}=(\neg\mathtt{before}(o_{1},o_{2})\lor\neg\mathtt{before}(o_{2},o_{1}))&&C_{4}=(\mathtt{before}(o_{1},o_{2})\lor\mathtt{before}(o_{2},o_{1}))\end{array}

Observe that the last two clauses
C_{3}
and
C_{4}
together encode totality.
The Hornification of
\psi
will contain exactly the clauses
C_{1},C_{2}
and
C_{3}
,
which are satisfiable simultaneously (by setting both
\mathtt{before}(o_{1},o_{2})
as well as
\mathtt{before}(o_{2},o_{1})
to false)!
This contradicts
(
Emmi and Enea, 2017
, Lemma 5.9)
.

We localized the error in the proof of
(
Emmi and Enea, 2017
, Lemma 5.9)
to the
‘

’ which claims that
for any resolution proof ‘

0

More precisely, the following statement
