SpecIBT: Formally Verified Protection Against Speculative Control-Flow Hijacking
Jonathan Baumann, Yonghyun Kim, Yan Farba, Cătălin Hri t , cu, Julay Leatherman-Brooks, [0.5em] MPI-SP, Bochum, Germany Ruhr University Bochum, Germany Portland State University, USA [0em]

Abstract
This paper introduces SpecIBT, a formally verified defense against Spectre BTB, RSB, and PHT that combines CET-style hardware-assisted control-flow integrity with compiler-inserted speculative load hardening (SLH). SpecIBT is based on the novel observation that in the presence of CET-style protection, we can precisely detect BTB misspeculation for indirect calls and set the SLH misspeculation flag. We formalize SpecIBT as a transformation in Rocq and provide a machine-checked proof that it achieves relative security: any transformed program running with speculation leaks no more than what the source program leaks without speculation. This strong security guarantee applies to arbitrary programs, even those not following the cryptographic constant-time programming discipline.

I
Introduction

The Spectre speculative side-channel attacks are a formidable threat for the
security of software systems
[
27
,
12
]
.
Without any defenses, attackers can easily construct “universal read gadgets”
that leak a sensitive program’s entire memory
[
27
,
33
]
.
Yet strong and efficient Spectre defenses are notoriously challenging to implement.
Even the Linux kernel, for which many developers have spent years to implement
effective Spectre defenses, still sometimes falls prey to Spectre attacks, including
universal read gadgets
[
43
,
42
]
, and the situation
seems worse when developers have fewer resources and rely
entirely on the defenses currently provided by the OSes and compilers.
These defenses often involve a complex combination of software in compilers and
OSes as well as hardware features and models, which are all very difficult to get right.
Often the attacks circumventing Spectre defenses exploit implementation
mistakes, bad security-efficiency tradeoffs, unclear attacker models, and
unclear and overly optimistic assumptions.

Two particularly powerful Spectre variants are Spectre BTB
[
27
]
, which exploits
indirect branch target speculation to jump to arbitrary addresses, and Spectre
RSB
[
28
,
32
]
, which exploits return address speculation.
These variants can be used to speculatively hijack control flow and then exploit
arbitrary gadgets in the code to leak secrets
[
9
]
.
Low-overhead mitigations against these variants can benefit from existing
control-flow integrity (CFI)
[
1
,
11
]

features in modern processors.
In particular, Intel CET
[
26
]
supports CFI protection both for forward
control-flow edges (e.g. indirect jumps) via Indirect Branch Tracking (IBT)
and also for backward edges (shadow stack for return addresses).
These hardware CFI features were originally introduced to defend against hijacking
control-flow using memory corruption
[
26
,
21
]
,
but were later also applied to mitigate
speculative control-flow hijacking
[
21
,
29
,
34
,
35
]
.
In response to such defenses
[
34
]
, Intel updated its CET
documentation
[
25
]
, confirming that the CET implementation in some of its current
processors (including products like Alder Lake-N and Arizona Beach) and the
intended long-term direction for CET is to also provide security under speculation.

Yet some of this previous work using CET
[
21
,
29
]

disregards that Spectre has a different attacker model than memory corruption.
In particular, even the most fine-grained forward-edge CFI defenses against
memory corruption
[
21
]
have to statically
overapproximate
the
set of possible targets of indirect calls and then dynamically check that each
call goes to a target in the corresponding set.
Directly applying this technique to defend against Spectre BTB preserves this
approximation aspect
[
21
,
29
]
, which allows clever
attackers to still circumvent these defenses in practice
[
43
]
.
Even Serberus
[
34
]
, which is designed to fully prevent Spectre BTB attacks, does
not avoid overapproximation, which in the end leads to complex
enforcement (e.g., procedure-private stacks, register cleaning)
and limitations (e.g., secrets can’t be passed by value).

In this work, we show that no approximation is needed when using CET to
defend against Spectre BTB.
We do this by introducing SpecIBT: a simple forward-edge CFI protection
specifically designed against the Spectre BTB attacker model.
With SpecIBT, the caller saves the function pointer
it is about to indirectly call in a
register and the callee checks that the value in this register is the correct one.
This check is useless in the absence of speculation, but it
precisely
detects
misspeculation, in which case we set a misspeculation flag register that
is used as a mask by Speculative Load Hardening (SLH).
Our current defense relies on Ultimate SLH
[
45
]

(very similar to strong SLH
[
38
]
),
which uses the misspeculation flag to mask not only the values loaded from
memory, but also any operands that could be leaked via timing (i.e., branch
conditions, addresses of memory accesses, etc.).

II
Background

II-A

Spectre PHT

Nearly all modern processors make use of a variety of hardware mechanisms
to improve performance (e.g., caches). These are part of the processor’s

microarchitecture
and are not
exposed in the
instruction set architecture
(ISA), so they should not affect the
results of computations. Still, their effects can be detected
across processes or even remotely by measuring execution time,
which can be used to leak secrets.

Speculative execution
is the result of a variety of techniques to avoid
stalling by executing code that is likely, but not guaranteed to be
needed by the program. While speculatively executed instructions do not affect
the
architectural
state, they still change the

microarchitectural
state. This enables the well-known

Spectre
attacks
[
27
]
,
which exploit speculative execution to leak
secrets into the microarchitectural state, from which they are
observed via traditional timing side-channels.

Spectre attacks are classified by the prediction mechanism
triggering speculation
[
12
]
.
The first and most well-known variant, Spectre PHT
[
27
]
,
targets the
pattern history table
, predicting the outcomes of
conditional branch instructions.

Relative Security

Several previous mitigations
[

5

34

have restricted their scope to

to ensure security against sequential

In this setting, it is possible to prove that the hardened program

Instead of requiring constant-time,

This is a relative notion of security
[

19

16

23
]
, as the hardened program is secure

[

]

Ultimate SLH satisfies relative security against Spectre PHT attacks
[

III
Key Ideas

III-A

Precisely Detecting BTB Misprediction

In this work, we show that when using CET to defend against Spectre BTB, no
approximation is necessary. Instead of using statically computed labels, we make
direct use of the indirectly called function pointer, which we store
in a designated register immediately before the call,
as illustrated in
2(c)
. All possible call
targets are also instrumented with a check comparing this designated register to
their actual location.
While this check is useless in the absence of speculation, it is able to detect
BTB mispredictions
precisely
, as a mismatch
between the intended target at the ISA level (the value stored in our
designated register) and the misspeculated target location predicted by the BTB.

As detection alone does not prevent Spectre attacks, we combine this approach
with Ultimate SLH (
§II-B
).
Our approach integrates nicely, as we can
directly update the same misspeculation flag, thus expanding the existing PHT
protection to also cover BTB misprediction.

III-B

Undefined Values

Correctly setting up the formal definitions and proving end-to-end relative
security for SpecIBT was nontrivial, most interestingly because of undefined behavior.
We built SpecIBT as an extension of Ultimate SLH, which has a realistic
implementation as one of the final passes of the LLVM compiler
[
45
]
,
since this reduces the likelihood that compilation passes break security.
Working in such a low-level intermediate language is also convenient for SpecIBT, since it
makes use of security features implemented in hardware (i.e., the CET IBT instructions).
Yet, this language still features an abstract notion of labelled basic blocks
and, like in prior compiler formalizations
[
31
,
44
]
,
we make the semantics feature
function pointer values
, which are distinct
from numerical values.
This allows us to still easily transform the code without changing the values of
the function pointers in the semantics of this intermediate language.

Since in mainstream compilers like LLVM all these values get compiled to just machine integers, the
distinction between function pointers and integers introduces undefined behavior in
the semantics, as the result of a comparison between a function pointer and a
numerical value cannot be determined before the program is compiled and laid out in memory.
In the presence of such undefined behavior, we can provide end-to-end security
guarantees only for safe inputs, which sequentially do not trigger undefined behavior.

However, restricting our guarantees to such safe inputs is not sufficient to be able
to prove relative security:
Due to the Ultimate SLH masking applied to the address of loads, during
misspeculated execution all loads will read from the same masked address, in
our case zero (
0
). This applies independently of whether the load would
sequentially load a function pointer or a numerical value. Thus, this masking
would lead to undefined operations during speculative execution for any
operations that depend on previously loaded values.

If we were to treat these undefined operations as undefined behavior, our
speculative semantics would not describe the behavior of our mitigation.
This would allow later compilation steps to refine it arbitrarily, potentially in
ways that leak secrets, which would break end-to-end relative security.
To prevent this, we ensure that our SpecIBT mitigation does not introduce
undefined behavior.
In other words, we prove that our mitigation preserves safety: Any safe input,
i.e., one that doesn’t trigger undefined behavior sequentially in the source,
is also safe during speculative execution of the SpecIBT-hardened program.
This then allows us to compose the relative security of SpecIBT with the
relative security of our subsequent step (
Figure 1
and

§VI

refines undefined behavior.

In order for safety preservation to hold for SpecIBT we need to make examples
like the one on the right-side of

the semantics of our intermediate language.
For this we introduce CompCert-style

[
31
]

to represent values that cannot be determined at the current level of
abstraction, but that are refined to arbitrary concrete values during later
compilation steps, like the one in
§VI
.
When an undefined value is created—e.g., when speculatively comparing an integer
introduced by our masking with a function pointer, like on like 3 on the
right-side of

Only if an undefined
value is used as the address of a load or store, or as the target of a call,
do we consider this to be undefined behavior.
However, undefined values which are the result of masking will not be used in
this way, as Ultimate SLH masks all loads, stores, and calls
during speculative execution, which replaces the undefined values with a constant.

Thus, SpecIBT does not introduce undefined behavior:

Lemma 1

(SpecIBT preserves safety)
.

For any input for which the source program does not encounter undefined behavior
with respect to the sequential semantics of our intermediate language, the result of hardening this
program using SpecIBT does not encounter undefined behavior with respect to the
speculative semantics of the language.

We used property-based testing in Rocq
[

to discover and
fix issues with safety preservation before trying to prove it. In
particular, testing produced counterexamples like the one in

The sequential semantics and its observations only allow us to
reason about leakage that occurs due to the intended control flow
and memory accesses of programs. Spectre attacks, however,
rely on observations produced during
transient
execution, when the
processor
speculatively
begins to execute the instructions along an
incorrect path before the instruction which determines the correct path has
fully resolved. Furthermore, speculative attackers are able to actively influence
these transient executions, by training the hardware prediction mechanisms to
predict an attacker-chosen path.

Our mitigation targets hardware IBT protection, which requires specific markers
(
ctarget
) to be inserted in all valid callable locations. In order to ensure
that our mitigation places these markers correctly, we need to model both an
attacker’s ability to misdirect execution to arbitrary locations even within
functions, as well as a hardware mechanism that halts execution if no

ctarget
marker is found.

Therefore, to model attacks in this setting, we use the speculative semantics with
CFI protection shown in
Figure 5
. This semantics is
a strict extension of the sequential semantics, which can be recovered by
removing the

An optional directive

overapproximates
the attacker’s ability to cause execution go down a specific
speculative path, either by forcing a conditional branch
with

(with an arbitrary program counter value, i.e. label and

semantics, but helps distinguish sequential and speculative execution in our

For every conditional branch, in both branches, the misspeculation flag

The proof proceeds by strong induction on the number of steps of the target run, with

To prove the inductive case, we introduce the notion of a

of target semantics:
a sequence of target steps corresponding to the protection mechanism that the SpecIBT inserts around each instruction.
The length of single cycles depends on the instruction:

\blacktriangleright

For most instructions, a cycle consists of a single step.

\blacktriangleright

For branch instructions with a true condition, a single cycle consists of three steps:
(1) the branch to the edge-split block, (2) update of the misspeculation bit in the edge-split block, and (3) jump to the actual target.
If the condition is false, a single cycle consists of two steps:
(1) the branch falls through, and (2) update of the misspeculation bit.

\blacktriangleright

For call instructions, a single cycle consists of four steps:
(1) update of the
\mathit{callee}

(3)
ctarget
instruction at the target, and (4) update of the misspeculation bit at the target.

The core lemma establishes backwards compiler correctness for single cycles:
when the source and target states satisfy the matching relation,
if the target executes exactly the number of steps corresponding to a single cycle,
then there exists a corresponding ideal semantics step, and the matching relation is restored between the resulting states.
The remaining execution is then handled by the induction hypothesis.

When the target execution does not take enough steps for a full cycle, (i.e., the target execution stops partially through a cycle),
we handle this case separately. We can still relate any produced observations
to the corresponding step in the ideal semantics, but without the full cycle,
we are unable to reestablish the relation between the resulting states.
However, this relation would only be required to apply the induction
hypothesis, which is not necessary since we are at the end of the target
execution.

Proof sketch.

The proof relies on a lock-step backwards simulation:
if the source state is safe and the source and target states are related,
then for every step in the target, the source can take a corresponding step

We apply this simulation inductively to obtain the result for multi-step
executions.

We divide the proof into two parts:

second, we prove safety preservation between ideal and speculative semantics.

For the first part, before misspeculation, ideal and sequential semantics behave identically.

For the second part, we use a strengthened version of

the ideal execution is safe, we obtain a step of the ideal semantics. By case

VII
Related Work

Spectre BTB defenses

We are not the first to propose defenses against Spectre BTB, with previous work
in this space including Serberus
[
34
]
,
Swivel
[
35
]
, and the work of
Fabian et al. 2025
.
Serberus
[
35
]
offers the most complete Spectre mitigation to
date, protecting not only against Spectre BTB, PHT, and RSB, but even against
the
data speculation
variants Spectre STL and PSF.
It achieves this with a combination of fence
insertion along a minimum cut, function-private stacks and register cleaning,
yielding a comprehensive yet efficient mitigation.
Their work includes security proofs on paper, while our work is mechanized in Rocq.
Their setting is more restrictive than the standard cryptographic
constant-time discipline, additionally requiring that all function arguments and
return values must be public (passing secrets is thus only possible by
reference). In contrast, our mitigation is much more permissive,
protecting arbitrary programs.
Finally, as mentioned in
§I
, by precisely detecting
misspeculation we also obtain simplicity benefits for SpecIBT.

Swivel
[
35
]
protects Wasm modules against Spectre PHT, BTB,
and RSB mounted from other modules running in the same process.
Their attack model is different from ours, as it aims to prevent malicious Wasm
modules both (1) from speculatively breaking out of the Wasm sandbox and
(2) from inducing speculative leakage in other modules.
Part (2) is similar to our attacker model, but weaker, since
they consider an attack mitigated if the attacker cannot train the prediction mechanism to take a
specific path, whereas our work assumes that the attacker has perfect control
over the prediction mechanisms, which prevents more sophisticated
attacks
[
42
]
.
Finally, while a small formal model of Swivel was sketched by

Cauligi et al. 2022b
, security proofs were left for future work.

Fabian et al. 2025
introduce a secure compilation framework that allows lifting
the security guarantees provided by Spectre countermeasures from weaker
speculative semantics to stronger ones.
This allows them to take software defenses against Spectre BTB (retpoline
variants
[
41
]
), prove them secure in a semantics that only includes
BTB, and obtain security against more variants (e.g., PHT), for programs that are
already secure against the extra variants (e.g., PHT).
They see this as a first step towards more easily composing Spectre mitigations.
They also lift PHT defenses like Ultimate SLH to obtain security against other
variants (e.g., RSB, STL, SLS), for programs that are already secure against the
extra variants (e.g., RSB, STL, SLS).
They show, however, that without modifications SLH-based defenses cannot be
lifted in the same way to obtain security against BTB, as indirect jumps can be
used to bypass SLH protection.
In this paper we show that Ultimate SLH can be modified to also defend against
BTB and for this we combine it with CET-style protection, a defense that is not
investigated by
Fabian et al. 2025
.

Spectre RSB defense

Arranz Olmos et al. 2025b
propose a mitigation for Spectre RSB and PHT for
the Jasmin language
[
2
]
and do a security proof for a
simplified version of it in Rocq. They compile returns to
tables of conditional jumps, then use
selective
SLH

[
39
]
to protect against Spectre PHT. Their work is
targeted only at cryptographic constant time code, and protection against
Spectre BTB is trivial, as their source language does not support indirect
jumps, and their transformation does not insert them.

Relative security and preservation of constant time by compilation

In this work we use the relative security definition for compilers introduced by

Baumann et al. 2025
.
This is inspired by
Dongol et al. 2024
, who defined relative security for a single program, but
varying inputs.
This is also inspired by related concepts used in prior work: speculative
non-interference
[
23
,
38
]
, relative
non-interference
[
39
,
14
]
, relative
constant-time
[
45
]
.

For compiling cryptographic code, a common security guarantee is

preservation of constant-time

[
4
,
6
]
,
i.e., proving that the target program is constant-time if
the source program is. This differs from relative security since it makes
certain assumptions about which inputs must be indistinguishable in the source
program, whereas relative security simply preserves indistinguishability.
However, it is worth noting that generalized versions, such as
\phi
-SCT

[
4
]
, can preserve arbitrary equivalence relations, and are thus
equivalent to relative security. One difference is that
Arranz Olmos et al. 2025a

require safety of
the source program, whereas our formalization allows for the program to be
unsafe on some inputs.

VIII
Conclusion and Future Work

In this paper we introduced SpecIBT, a formally verified defense that protects
arbitrary programs against Spectre attacks by combining CET-style
hardware-assisted control-flow integrity with compiler-inserted Ultimate SLH.
In the future, we would like to implement SpecIBT in LLVM by extending the
implementation of Ultimate SLH
[
45
]
.
To reduce overhead we will also investigate building SpecIBT on top of a
selective version of Ultimate SLH called FSLH
[
8
]
, which is,
however, itself yet to be implemented in LLVM.
It would also be interesting to investigate whether SpecIBT can also make use of
software defenses such as retpoline
[
41
]
and saferet
[
40
]
,
for old processors without Intel CET or Arm BTI, or for which these hardware
features are not implemented in a way that is secure under speculation.
Finally, it could be interesting to extend SpecIBT to indirect jumps that go
beyond calls through function pointers (e.g. switch tables).
