TEE is not a Healer: Rollback-Resistant Reliable Storage
Sadegh Keshavarzi, Gregory Chockler, Alexey Gotsman

Abstract
Recent advances in secure hardware technologies, such as Intel SGX or ARM TrustZone, offer an opportunity to substantially reduce the costs of Byzantine fault-tolerance by placing the program code and state within a secure enclave known as a Trusted Execution Environment (TEE) . However, the protection offered by a TEE only applies during program execution. Once power is switched off, the non-volatile portion of the program state becomes vulnerable to rollback attacks wherein it is undetectably reverted to an older version. In this paper, we consider a problem of implementing reliable read/write registers out of failure-prone replicas subject to state rollbacks. To this end, we introduce a new unified model that captures the multiple failure types that can affect a TEE-based system. We then establish tight bounds on the fault-tolerance of register constructions in this model for both the static case, where failure thresholds hold throughout the entire execution, and the dynamic case, where they only hold eventually. Our dynamic register emulation algorithm resolves a long-standing question of how to correctly rebuild replica state upon restart without relying on additional hardware assumptions such as trusted monotonic counters.

Introduction

Tolerating Byzantine failures plays a major role in designing modern reliable
distributed systems, and in particular blockchains. Unfortunately, tolerating
Byzantine failures is expensive in terms of both message complexity
[
14
]

and latency
[
2
,
41
]

as well as the number of replicas required
[
37
,
31
,
15
]
.
Recent advances in secure hardware
technologies, such as Intel SGX or ARM TrustZone, offer an opportunity to
substantially reduce these costs by placing the program’s code
and a portion of its state in a secure enclave known as a
Trusted Execution
Environments (TEE)
.
Additionally, applications can use integrity metadata stored inside the enclave to detect
any runtime alterations to state stored outside of its protection domain.
These mechanisms together can then be used to convert Byzantine failures
to simple crash or omission failures, which
are less expensive to tolerate
[
39
,
29
,
6
,
40
]
.

However, a TEE is a not a panacea, because
the protection it offers only applies during program
execution. Once power is switched off, the non-volatile portion of the
program state becomes vulnerable to tampering by an attacker.
To address this, hardware manufacturers provide a
sealing
mechanism
[
11
]

that allows programs to encrypt a portion of their state using a
device-specific key before storing it in non-volatile storage. When the
machine restarts, the TEE can check whether the sealed state
was indeed written by it in the past.
However, it cannot determine whether this state is the most recent version.
This limitation makes TEE-based systems vulnerable to
rollback
attacks where the sealed state
is undetectably replaced with an older
version
[
34
,
38
,
7
,
40
,
12
]
.

In this paper, we initiate a systematic study of theoretical foundations
for building reliable distributed systems in the presence of state rollbacks.
We start by introducing
crash-restart-rollback
(
\mathsf{CRR}
), a new unified
failure model that formalizes rollbacks alongside other types of failures that
can occur in a TEE-based system. In this model, the processes can use local
non-volatile storage to store their states and are assumed to behave correctly
while they are executing. A
\mathsf{CRR}
-faulty process can permanently crash, crash and
restart infinitely often, or crash and restart with the content of its
non-volatile storage being undetectably reverted to an older version. We assume
that upon restart, a process executes an

can take steps to ensure it continues operating from a correct state.

We then study the problem of implementing reliable read/write registers in an
asynchronous message-passing system in which the register’s state
is stored at a collection of

dedicated
\mathsf{CRR}

accessed
by arbitrarily many crash-prone

We give fine-grained characterization of failure resilience, time complexity,

of the thresholds

We also address the cases

For the model where the threshold

following: an implementation of a wait-free atomic multi-writer/multi-reader
(MWMR) register tolerating
k

.
For the lower bound, we prove that this number of processes is necessary even

[
19
]

safe
[

]

Our resilience bounds demonstrate that when

The number of replicas

On the other hand, the bounds are separated when

Our lower bound for non-volatile storage consumption establishes that in order to

2k+r+1

For the upper bound, we present
\mathcal{A}

Next, we analyze register implementability under a stronger failure model,

2
System Model

We consider an asynchronous message-passing system consisting of a collection of
failure-prone processes
\mathsf{\Pi}=\{p_{1},p_{2},\ldots\}
implementing a high-level
object abstraction. The set of processes is partitioned into a set
\mathsf{Rpl}=\{p_{1},\ldots,p_{n}\}
of
n

replicas
, and a set
\{p_{n+1},p_{n+2},\ldots\}
of a finite but unbounded number of
clients
.
Similarly to the classical faulty shared memory model of
[
23
,
3
]
,
the replicas are responsible for storing the object state, and
the clients interact with the replicas to handle the requests supported by
the implemented object type. We assume that the replicas
have access to non-volatile storage, which they can use
to store data persistently.

Formally, an object
implementation
is a composition of the client and
replica automata. An execution of an implementation is a sequence of states
interleaved with atomic send and receive actions starting from an initial
state. The action atomicity ensures that all non-volatile storage
modifications performed as a part of the received message handling
are
failure atomic

[
8
]
, i.e., their effects are either persisted
in their entirety or not at all.

Failure model.

Clients can experience permanent
crash
failures, but otherwise, do not
deviate from their prescribed protocols. A client is
correct
in an execution
if it never crashes, and is
faulty
, otherwise.
Our failure model for replicas, to which we refer as

crash-restart-rollback
(
\mathsf{CRR}
), formalizes the types of
failures that can occur in a TEE-based system (see §
1
).
Under
\mathsf{CRR}
, a replica can experience a
crash
that
interrupts its execution either permanently or temporarily.
A crashed replica can later
restart
, which causes
it to execute a specified
on restart
block and then
continue its execution from the state reached thereupon.
We refer to the restarted replicas that have
completed their
on restart
blocks as
active
.
Additionally, upon restart a replica may experience a
rollback
failure,
which causes the content of its non-volatile storage
to revert to a version older than it had before the latest crash.

For a time
t
, we say that a replica is
down
at
t
if
it has crashed at some time
t^{\prime}<t
and has not restarted between

t^{\prime}
and
t
; a replica is
up
at
t
if it is not down at
t
.
A replica is
eventually up
if there exists a time
t

such that the replica is up at all times
t^{\prime}\geq t
. A replica is
correct
if
it is eventually up and never rolls back; otherwise, it is
faulty
.
A correct replica is
perfect
if it never crashes, and
benign
,
otherwise. A faulty replica is
rollback-faulty
if it rolls back
at least once, and is
crash-faulty
, otherwise. Note that
a crash-faulty replica may either crash permanently or infinitely often, and
a rollback-faulty replica may experience all possible types of failures permitted
under
\mathsf{CRR}
.

Note that
\mathsf{CRR}
generalizes the classical crash-recovery failure
model
[
21
]
by extending its set of faulty behaviors with rollback
failures. It is also strictly weaker than the Byzantine failure model since
faulty replicas are required to follow their prescribed protocols. The
relationship of our model to other prior failure models is further discussed
in §
5
.

Channel reliability assumptions.

We assume that every pair of processes

p_{i}
and
p_{j}
are connected via point-to-point authenticated links such that
if both
p_{i}
and
p_{j}
never crash after some time
t
,
then every message sent by
p_{i}
to
p_{j}
after
t
is eventually delivered
by
p_{j}
. Note that this assumption is strictly weaker than the standard notion of a reliable channel.
Specifically, it does not require reliability for messages sent by a correct process
to another correct process before both processes are permanently up.

Fault-tolerant implementations.

We study reliable implementations of objects that can withstand

\mathsf{CRR}
failures of replicas and crash failures of clients.
We use standard safety and liveness notions to specify correctness conditions for
the implemented objects: atomicity
[
26
]

(linearizability
[
20
]
),
safeness
[
26
]
, wait freedom
[
18
]
,
and obstruction freedom
[
19
]
.

An object implementation is
k
-tolerant for a failure model

\mathcal{F}

[
23
]

if it is correct in every execution where at most
k
replicas experience failures
allowed by
\mathcal{F}
and any number of clients can crash.
An object implementation is
\diamond k
-tolerant for
\mathcal{F}

if it is
correct in every execution where the bound
k
on the number of faulty
replicas
holds from some unknown time
t\geq 0
onwards.
In particular, the following holds for every execution of a

\diamond k
-tolerant object implementation for
\mathsf{CRR}
: there exists a time
t^{\prime}\geq t
such
that before
t^{\prime}
, any number of replicas can crash and restart with or
without rollback, and after
t^{\prime}
, all correct replicas are permanently up.
We consider both

single-writer/single-reader (SWSR)
and
multi-writer/multi-reader (MWMR)
cases
for
our
bounds for read/write register implementations.

Tight Bounds for
k
-Tolerant Register Implementations for
\mathsf{CRR}

In this section, we give a full characterization of the costs of implementing a

k
-tolerant register in the presence of

\mathsf{CRR}
-faulty replicas in terms of its failure resilience, time complexity,
and non-volatile storage requirements.
For the resilience bounds, we establish necessary and sufficient conditions on
the number of
\mathsf{CRR}
-prone replicas
n
as a function of the thresholds

r\leq k
and
b\leq n
on the rollback-faulty and benign replicas, respectively. We
address the cases when both
r
and
b
are
known
(i.e., hold for all

We characterize non-volatile storage consumption as

storage. The latter is an important consideration in practical TEE-based systems:
Since non-volatile storage content is not protected

5
Related Work

Distributed state recovery was first considered
in
[
25
,
28
,
9
]

as the means of
eliminating dependency on stable storage in state machine replication
protocols. The proposed solutions however, did not use crash-consistent quorums for storing
their state, and were shown in
[
35
]
to suffer
from safety bugs.

The use of execution epoch versioning to enable consistent replica replacement
in the Paxos protocol
[
27
]
was first proposed in
[
24
]
. It was subsequently
generalized into the notion of crash-consistent quorums by Michael et al.
[
35
]
,
who also demonstrated how they can be used for implementing a recoverable MWMR atomic
register.
However, the safety of these versioning schemes critically depends on the replicas’ ability to track
their incarnations across restarts. In turn, supporting this capability in TEE-based
systems requires hardware-based persistent counters, which we do
not assume.
Although the technical report version of
[
36
]

suggests that such counters can be supported by means of a distributed mechanism, it does
not provide an implementation.

A refinement of the classical crash-recovery failure model
[
21
]

in which only a subset of processes is assumed to have access
to reliable stable storage was introduced in
[
4
]
. The same
model was also used in
[
16
]
to derive
tight bounds for a reliable register construction.
In contrast, in our
\mathsf{CRR}
model a recovering process
cannot trust its non-volatile storage to be up-to-date,
leading to different fault-tolerance bounds. Also, as we explain
in §
J
, the register construction of
[
16
]

does not use crash-consistent recovery, resulting in a
safety violation.

Dinis et al.
[
12
]
proposed a rollback-recovery
(RR) failure model to capture rollback attacks in TEE-based system. This
model however, is strictly weaker than
\mathsf{CRR}
as it disallows permanent process
crashes.
Furthermore, the recoverable atomic register implementation proposed
in
[
12
]
does not guarantee wait-freedom for read
operations,
and uses regular quorums instead of
crash-consistent ones. As a result, it is subject to a safety violation
similar to the one described in §
4
(see §
I
for a detailed
counterexample).

ROTE
[
34
]
proposed a rollback protection system, which uses
a rollback-resistant distributed counter
abstraction to detect rollbacks. The implementation of this abstraction relies
on a two-round protocol where a new value of the counter is first
written to a write quorum, and then read back from the
same
write
quorum to validate it was stored reliably.
Although this solution is safe, it does not ensure liveness as the same write
quorum cannot be guaranteed to be available two times in a row in the presence
of failures and asynchrony.
Engraft
[
40
]
uses a similar protocol to
implement a rollback-resistant key/value store, and is therefore
subject to the same liveness issue.

Persistent monotonic hardware counters have been demonstrated
in
[
38
]
to be a powerful mechanism to guard against rollback
attacks. In TEE-based systems, such as Intel SGX, they can be used in
conjunction with the sealing mechanism (§
1
) to validate state
freshness upon restart
[
11
]
.
However, these counters are implemented using flash memory, resulting in poor
write performance (on the order of 100s milliseconds) and quick wear-out
[
34
]
.
Furthermore, they are not universally supported by the TEE
manufacturers, and have been recently deprecated by
Intel SGX
[
22
]
.
