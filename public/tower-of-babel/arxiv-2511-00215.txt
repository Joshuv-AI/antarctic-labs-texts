Abstract
. Code-documentation inconsistencies are common and undesirable: they can lead to developer misunderstandings and software defects. This paper introduces DocPrism , a multi-language, code-documentation inconsistency detection tool. DocPrism uses a standard large language model (LLM) to analyze and explain inconsistencies. Plain use of LLMs for this task yield unacceptably high false positive rates: LLMs identify natural gaps between high-level documentation and detailed code implementations as inconsistencies. We introduce and apply the Local Categorization, External Filtering (LCEF) methodology to reduce false positives. LCEF relies on the LLM’s local completion skills rather than its long-term reasoning skills. In our ablation study, LCEF reduces DocPrism ’s inconsistency flag rate from 98% to 14%, and increases accuracy from 14% to 94%. On a broad evaluation across Python, TypeScript, C++, and Java, DocPrism maintains a low flag rate of 15%, and achieves a precision of 0.62 without performing any fine-tuning.



1.
Introduction

Code-documentation inconsistencies are the most frequently faced software documentation issue
(
Aghajani et al. 2020
)
.
These inconsistencies make it challenging for developers to accurately understand codebases, and can lead to defects during software evolution
(
Ibrahim et al. 2012
;
Huang et al. 2020
;
Silva et al. 2022
)
.
Code-documentation inconsistencies can occur during early stages of development when developers incorrectly document their intent, or incompletely or incorrectly implement their intent
(
Tan et al. 2012
)
.
Inconsistencies can also be introduced during software evolution, when developers modify code to fix bugs or add new features but fail to accurately update the associated documentation
(
Rabbi and Siddik 2020
)
.

Given the impact code-documentation inconsistencies can have on software quality
(
Rani 2021
;
Tan 2015
)
,
this work investigates a method for identifying inconsistencies between
function-level
documentation and code.
We posit that good function-level documentation should summarize what the function does, without the detail of
how
it does it. It is the purpose of the code, not the documentation, to describe precisely
how
the computation is accomplished.
Good documentation is always an abstraction of the source code it accompanies.

Identifying inconsistencies between functions and their documentation is challenging for two main reasons.
First, documentation and code have two different purposes: code exists to tell the computer what to do and is written in a
programming language
, while documentation exists only to help developers and is written in
natural language
.
This requires any approach for detecting inconsistencies to overcome differences between natural language and source code representations.
Second, good documentation is written at a higher level of abstraction than the code it documents.
Unfortunately, this challenge is pervasive in almost all functions as documentation usually elides implementation details.
We call this kind of code-documentation inconsistency an
under-promise
. We think under-promising is generally good practice rather than leading to actual inconsistencies.
In fact, a previous taxonomy of documentation issues does not consider these inconsistencies
(
Aghajani et al. 2019
)
.

Previous work in the space of inconsistency detection largely falls into two buckets. First are
pattern-based approaches
which rely on some specific natural language patterns or program analyses
(
Tan et al. 2012
;
Tan et al. 2007
;
Xu et al. 2025
;
Zhang et al. 2024
)
. These techniques are often restricted to specific programming languages, and only detect a specific type of inconsistencies. Second are
machine-learning based approaches

(
Huang et al. 2025
;
Xu et al. 2024
;
Tan et al. 2025
;
Panthaplackel et al. 2021
;
Rabbi and Siddik 2020
;
Cui et al. 2025
;
Igbomezie et al. 2024
;
Liu et al. 2018
;
Rong et al. 2025
)
. By treating code and documentation as text-like inputs to a model, these approaches have the potential to identify broader types inconsistencies. But apart from those which attempt automated rectification
(
Liu et al. 2021
;
Rong et al. 2025
;
Dau et al. 2024
)
, these approaches treat inconsistency detection as a binary classification problem. This makes their results hard for humans to reason about, as binary classification does not pinpoint any particular inconsistent code or documentation. Many works focus on “just-in-time”
(
Stulova et al. 2020
;
Liu et al. 2021
;
Xu et al. 2024
;
Tan et al. 2025
;
Huang et al. 2025
)
detection of inconsistencies at edit time, restricting their applicability to existing codebases. Finally, very few approaches can be run on multiple languages
(
Huang et al. 2025
;
Cui et al. 2025
)
, with Java as the most popular target language.

We present
DocPrism
, a lightweight, multi-language code-documentation inconsistency detector. To analyze documentation and code,
DocPrism
uses standard Large Language Models (LLMs) without any fine-tuning. Thus, it can detect inconsistencies beyond a specific set of patterns.
Rather than focusing on binary classification,
DocPrism
formats its output to be helpful for the developer: it highlights
fragments of the code and/or documentation that it considers inconsistent and explains the inconsistency.
DocPrism
does not require diff information, so it can perform post hoc inconsistency detection. Finally,
DocPrism
’s technique is not inherently tied to a particular programming language.

In order to be useful to developers
(
Nachtigall et al. 2019
)
,
DocPrism
must minimize its
flag rate
—the proportion of functions that are found to be inconsistent with their documentation—and have high-enough precision. Achieving this requires specific effort to avoid showing developers under-promises. To do this, we introduce the
Local Categorization External Filtering (LCEF)
methodology. Local Categorization turns under-promise identification into a local completion, rather than long-term reasoning, problem. In our ablation study, LCEF reduced flag rate from 98% to 14% and improved accuracy from 14% to 94%. We evaluate
DocPrism
on 1,615 benchmarks across 4 programming languages: across this diverse dataset it achieves a low average under-promise rate of 4%, a flag rate of 15%, and a precision of 0.62.

This paper makes two main contributions. First, our implementation and evaluation of

DocPrism
advances multi-language, multi-pattern code-documentation inconsistency detection.

DocPrism
’s flag rate is tractable for manual analysis, and its precision is
similar to that of classic code-doc inconsistency detection tools
(
Tan et al. 2007
;
Tan et al. 2012
)
. In our evaluation, we manually investigated results for each function to determine whether the inconsistency was correct. Our manual analysis uncovered the kinds of code-documentation inconsistencies present in practice and provides insight into our false positives.

Second, we introduce

Local-Categorization External-Filtering (LC-EF)
,
a novel approach for integrating LLMs into Software Engineering workflows.
We found LCEF vastly outperformed typical prompt-engineering strategies for filtering under-promises. In particular, in our ablation study, compared to “define in prompt and recall in output” (a.k.a
instructed
) categorization,
Local-Categorization (LC)
reduces under-promise rate from 50% to 0%. While we only explored it in the context of filtering out under-promises, we believe LC is simple enough to reasonably
port to other categorization tasks.

2.
Why (and Which) Inconsistencies Matter

The large scale of modern software systems is only possible through the pervasive use of abstraction.
Abstraction enables complex problems to be decomposed into more manageable components that teams and individuals can tackle.

One mechanism all programming languages support for enabling abstraction is function-level source code documentation.
Documentation allows a developer to understand
what
a method does without having to read its complex implementation—which encodes
how
the functionality is implemented.
This crucial abstraction mechanism is core to information hiding and allows developers to separate design decisions from implementation decisions.

Inconsistencies between what documentation says and what code does reduce trust in documentation. This means developers often rely on the source code alone, leading to the saying “code is king”
(
Singer 1998
)
.
In doing so, developers must violate information hiding principles, reading code to understand what it does instead of being able to
trust
the abstraction provided to them by documentation.

One pathway to improving trust in documentation is identifying inconsistencies so developers can fix them.
This requires tool support that can be applied in a straight-forward manner for a variety of programming languages.
To be useful for developers, such tool support must balance its flag rate (the proportion of methods flagged as inconsistent) with its precision (the proportion of flagged inconsistencies that are problematic).
Such a tool should also help developers identify both exactly what documentation and source code are inconsistent along with the nature of the inconsistency.

Core Challenge: Under-Promises.

Using LLMs to perform inconsistency detection is challenging because LLMs tend to answer questions in a way that aligns positively with user expectations
(
Ranaldi and Pucci 2025
)
.
In particular, LLMs are eager to flag under-promise inconsistencies, as they
are
differences between code and documentation.
But, many of these under-promises will not be actionable, because documentation is inherently concise and a gap between code and function-level documentation
should
exist.
Thus, we seek to filter out under-promises as much as possible and focus on more actionable types of inconsistencies:
over-promises
and
direct mismatches
.

3.1.
Prompts

Our prompts are lightweight by design, consisting of a system prompt followed by a user prompt that contains a pair of a function and its method-level documentation. That is, the LLM performs the inconsistency detection task in a zero-shot manner. The system prompt consists of two parts: a prefix that introduces the task and input format, and a JSON schema that specifies the output format.

3.1.1.
System Prompt - Prefix

The prefix of the system prompt defines the LLM’s role, specifies the task, and indicates the input format. Specifically, we instruct the LLM to act as a code review expert for the tested codebase, identifying inconsistencies between function-level code and its documentation. The tested codebase is followed by “library”, “framework”, or “project”, depending on its type. We then specify the expected input format: code is enclosed within
[CODE]

3.1.2.
System Prompt - JSON Schema

We break down the task of code-documentation inconsistency detection into five intermediate subtasks, following the chain-of-thought approach
(
Wei et al. 2022
)
. The first two subtasks require the LLM to generate summaries of (1) the input documentation and (2) the code. These preparatory tasks aim to prime the LLM’s understanding of code and documentation before identifying inconsistencies, mimicking how humans approach this task. The remaining three subtasks instruct the LLM to identify inconsistencies in each of the three categories from Section
2
: (3)
over-promise
, (4)
direct mismatch
, and (5)
under-promise
.

Instead of explicitly stating the five reasoning subtasks in the prompt, we encode them into a predefined JSON schema with eight keys. The rationale behind this approach is to treat the LLM as a completion model, without requiring it to “remember” subtasks it should accomplish. This offloads the subtasks to filling in the schema’s keys. Thus, the LLM is guided to perform the subtasks implicitly while generating output in the specified JSON format.

The first JSON key in the predefined JSON schema prompts the LLM to summarize the documentation.
(Subtask 2).
The second key instructs the LLM to summarize the code. We deliberately include the word

Local Categorization Subtasks.

The remaining three pairs of JSON keys apply the approach of
local categorization
, which
locally
and
implicitly
guides the LLM to identify
over-promises
,
direct mismatches
, and
under-promises
. Each pair has a check-in key (
CK
) and a follow-up key (
FK
). The check-in key is a well-crafted “Yes” or “No” question tailored to detecting inconsistencies in a certain category. If the LLM agrees with the question in the check-in key, the paired follow-up key prompts it to list inconsistencies in the corresponding category leveraging the chain-of-thought approach. Otherwise, the LLM either leaves the follow-up key unfilled or fills it in with an empty list or None.

In this manner, the task of identifying inconsistencies between code and documentation, and the category of these inconsistencies, is reduced to a
local completion
problem. The LLM is not required to “remember” the definitions of each inconsistency category, but only to complete each local part of the output format. As the LLM sequentially generates outputs for each pair of keys, it is implicitly guided to detect and list inconsistencies in each category, if any.

3.2.
Inconsistency Detection

For each pair of function and its documentation,
DocPrism
first generates the prompts, as described in Section
3.1
. To detect inconsistencies, it feeds these prompts to the open-source LLM LLaMA 3.1–70B
(
Dubey et al. 2024
)
. The output is in JSON format, following the schema specified in the system prompt. In rare cases where the output doesn’t match this format, we say
DocPrism
fails to identify inconsistencies and set the detection result to “consistent”. We set the temperature to 0 to encourage deterministic results from the LLM.

3.3.
External Filtering

DocPrism
’s External Filtering component takes in the JSON object output by the LLM. This component filters out inconsistencies in the third category,
under-promises
, by dropping content corresponding to the third JSON key pair described in Section
3.1.2
. Our HTML backend reports any remaining inconsistencies by highlighting the relevant code/doc, and rendering the LLM-generated explanations.

4.
Evaluation

Our experiments are designed to answer the following questions:

•

RQ1:
How does
DocPrism
perform on our Python dataset? What are common sources of true positives and false positives?

•

RQ2:
How does
DocPrism
perform on functions outside our core dataset, on multiple programming languages?

•

RQ3:
How do our design decisions, in particular Local Categorization and Exernal Filtering, affect
DocPrism
’s performance?

4.1.
Experimental Design Decisions

Experimental decisions all have costs and benefits. Following best-practice advice
(
Robillard et al. 2024
)
, we report the implications of our design decisions along with our experimental methodology rather than a separate threats to validity section.

The primary experimental design decision in this paper is the centrality of human labeling to determine whether code and documentation are inconsistent.
Alternatively, we could rely on a previously suggested heuristic approach that considers synthetic code-documentation pairs as inconsistent when documentation is updated
(
Panthaplackel et al. 2021
;
Huang et al. 2025
)
. The most popular
(
Panthaplackel et al. 2021
)
heuristic only identifies inconsistencies when documentation is edited—meaning all unfixed latent inconsistencies in a project are labeled consistent. We discuss some other issues with the heuristic in Section
5
.

The implication of our decision to manually label inconsistencies, beyond a considerable investment of human effort, is that we were able to closely examine hundreds of functions and their documentation, helping us to better understand the nature of inconsistencies in practice.
This also let us examine inconsistencies as they manifest in practice: we only examined functions and their
actual documentation
in real software systems.
A tradeoff of this decision is that our labeling process is
subject to human error.

The artifact for this paper includes all of the functions and documentation we examined, the
DocPrism
output for each function, illustrative examples of consistent and inconsistent output, and our manually-determined labels.

4.2.
Evaluation Datasets

We perform extensive
manual labeling in our evaluation.
We believe human labeling is crucial to understanding code-documentation inconsistencies: documentation is meant to be read by developers, who are the arbiters of whether the documentation is inconsistent.

To mitigate labeling error, labeling tasks involved multiple human coders who were authors from this paper.
The subsets of authors for each labeling task varied by the authors experience with the language being labeled.
To understand the reliability of the labeling process, we performed an inter-coder reliability analysis by comparing two coder’s results across 50 functions for one language; this yielded a Cohen’s Kappa value of 0.78, which is considered ‘substantial agreement’
(
McHugh 2012
)
.
This means human coding of inconsistencies can be performed with high consistency.

4.2.1.
Fully Labeled Construction Dataset

We construct a Python dataset of 124 fully labeled benchmarks, each consisting of a function and its method-level documentation. Specifically, 66 benchmarks come from the pandas library
(
The pandas development team 2025
)
, and 58 from the Requests library
(
The Requests development team 2025
)
. Both are popular open-source libraries with a high proportion of functions documented in the standardized format. Pandas functions are collected by exploring the ‘core’ directory of the pandas codebase, which contains the core implementation. Within this directory, we randomly select Python files from its top-level folders and extract functions with documentation in the docstring format. As for requests functions, we inspect files in the
/src/requests
directory and collect functions that have documentation in the docstring format.

Each benchmark is independently labeled by two authors proficient in Python.
These code-documentation pairs are labeled as either consistent or inconsistent; when inconsistent, the source of the inconsistency is noted.
Any differences in labels were discussed among both coders until agreement was reached for all 124 benchmarks.
The labeled Python dataset supports a full evaluation of
DocPrism
, including precision, recall, accuracy, and F1 score.

While creating
DocPrism
and the LCEF methodology, we examined performance on a subset of our Python dataset—52 benchmarks in total. We call this subset the
construction
dataset. The remaining 72 benchmarks were not used at tool-creation time.

4.2.2.
Extension Dataset

To gain insight into inconsistencies beyond Python and to learn how
DocPrism
generalizes to other languages we built a second dataset, the
extension
dataset,
across three other programming languages: TypeScript, C++, and Java.
This allowed us to examine the
DocPrism
’s flag rate and precision for languages beyond Python. This provides insight into cross-language performance and inconsistency differences in other languages.

Our metrics have two levels of granularity.

Function-Level Terminology

(1)

True Positive (TP):
The function is inconsistent with its documentation, and
DocPrism
correctly identifies at least one inconsistency.

(2)

False Positive (FP):
The function is consistent with its documentation, but
DocPrism
identifies them as inconsistent.

(3)

True Negative (TN):
The function is consistent with its documentation, and
DocPrism
identifies them as consistent.

(4)

False Negative (FN):
The function is inconsistent with its documentation, but
DocPrism
identifies them as consistent.

(5)

The percentage of functions flagged as inconsistent with its method-level documentation.

\small\text{Flag Rate}=\frac{\text{\# Functions Flagged as Inconsistent}}{\text{\# Total Tested Functions}}

4.5.2.
Classification of Correctly Identified Inconsistencies

We introduce seven categories of True Positives found by
DocPrism
in our datasets. On the Python dataset,
unimplemented feature
and
parameter type mismatch
are the most common.

Functionality Mismatch:
Features described in the documentation logically conflict with the actual implementation of the code. An example can be found in Figure
2
. While the documentation mentions returning the highest
OrderIndex + 1
, the code implements returning the highest
OrderIndex
.

Parameter Mismatch:

Parameters specified in the documentation do not align with those defined in the function signature. Either some documented parameters are not present in the function signature, or only a subset of the parameters defined in the function signature are documented.

Parameter Type Mismatch:

Parameters types specified in the documentation and the function signature do not match.

Identifier Mismatch:
Identifiers/variables referring to the same object do not match in the code and documentation.

Return Type Mismatch:
The function’s return type differs from what is specified in its documentation.

Unimplemented Feature:
A feature specified in the documentation is absent from the code.

Unused Parameter or Variable:

Unlike
parameter mismatch
, the parameters specified in the documentation do match with those defined in the function signature. However, some parameters are not used in the code body at all; or, some C++ codebases use
GGML_UNUSED(variable)
to avoid compiler warnings.

4.5.3.
Classification of Inconsistency-Level FPs

In this section, we introduce four main categories of False Positives, that is, reported inconsistencies that are not actually inconsistencies.

Lack of API knowledge:
The LLM is unsure about, or assumes missing, functionality in a callee API, even though the callee API actually implements the desired behavior.
The
info()
example from Figure
4
, explained in Section
4.5.1
, falls in this category.

Semantics Gap:
The LLM correctly understands the semantics of the documentation and code snippet, but fails to identify that the implementation in the code is an instance of the semantics in the documentation, or vice-versa. For example, the documentation of
n8n-43
mentions a feature of “expiring the current client” and the code implements it with
this.client = undefined;
. The LLM flags this function as inconsistent, saying that
“the documentation mentions expiring the current client, but the code only sets it to undefined”
. The LLM fails to identify that setting to
undefined
is sufficient to meet the definition of “expire”.

Effects of Chain-of-Thought (V1 vs. V2 / V3 vs. V4).

CoT JSON
guides the LLM use chain-of-thought reasoning while generating outputs.
V2 adds

to V1, and V4 adds

to V3. Adding

reduces under-promise rates in both cases: from 72% (V1) to 44% (V2), and from 48% (V3) to 28% (V4). We also see consistent improvements in inconsistency-level precision, going up from 0.07 (V1) to 0.14 (V2), and from 0.07 (V3) to 0.10 (V4).

V3 and V4
add
Instructed Categorization
and
Instructed Filter
to V1 and V2, respectively. This enhances the prompt with the three inconsistency categories and instructions to filter out

Effects of External Filter (V6 vs. V4).

Instead of instructing the LLM not to report
under-promises
through the prompt (V4), V6 prompts the LLM to label each detected inconsistency with its corresponding category (i.e.,
over-promise
,
direct mismatch
, or
under-promise
). It then filters out inconsistencies labeled with
under-promise
during the post-processing stage. V6 reduces the average flag rate from 92% to 62% on the extension dataset, and improves six out of seven evaluation metrics on the construction dataset. Specifically, it significantly reduces the flag rate from 98% (V4) to 48% (V6) and increases accuracy from 0.14 to 0.6 due to a substantial increase in true negatives. Note that there is no significant decrease in the under-promise rate. This is partly because V6 mislabels some
under-promises
as
over-promises
, so that some real
under-promises
can’t be filtered out. This issue is addressed by
DocPrism
.

Effects of Local Categorization (
DocPrism
vs. V7)

V7 adds documentation and function summaries to V6. Like V6 and V7,
DocPrism
employs an
external filter
to drop under-promises during the post-processing stage. However, unlike V6/V7,
DocPrism
adopts
local categorization
(LC), where the LLM is not required to “remember” the definitions of the inconsistency categories as in V6/V7. Instead it must answer the categorization questions for each check-in key in the predefined JSON schema.
DocPrism

significantly outperforms V7 on all evaluation metrics (and V6 on all metrics except recall). It reduces the flag rate from 39% to 14% and the under-promise rate from 50% to 0%, and increases function-level precision from 0.1 to 0.71, accuracy from 0.58 to 0.94, F1 score from 0.15 to 0.77, and inconsistency-level precision from 0.09 to 0.70. These results show the effectiveness of
local categorization
.

RQ3 Takeaway.

Local Categorization, External Filtering
(LCEF) is highly effective at reducing
DocPrism
’s under-promise and flag rates. Both LC and EF greatly decrease flag rates, but LC is key to decreasing under-promise rate and increasing precision.

5.
Related Work

Do Under-Promises Matter?
Aghajani et. al
(
Aghajani et al. 2019
)
identify two subcategories of code-documentation inconsistency: “Code must change to match doc” and “Behavior described in documentation but not implemented”. These match our direct mismatch and over-promise, supporting our decision to filter out under-promises. Uddin and Robillard
(
Uddin and Robillard 2015
)
find that
ambiguity
,
incompleteness
, and
incorrectness
issues in API documentation are the most severe. Incompleteness
is about missing information that
cannot be garnered directly from looking at the code
. This is distinct from our under-promises, which usually point out that the documentation misses details that
can be garnered directly from looking at the code
.

Pattern-Based Inconsistency Detection.
As documentation is a natural language artifact, handling it in a precise manner requires the strategic use of NLP methods to identify a few natural language patterns whose meaning can be precisely understood. icomment
(
Tan et al. 2007
)
looks for rule-containing documentation by checking for
imperative words (e.g.,
should
,
must
), and filters this down to lock-related and call-related rules with other keywords (e.g.,
lock
,
acquire
,
release
). It achieves a precision of 0.61 on a C/C++ dataset. tcomment
(
Tan et al. 2012
)
uses the structure of javadocs to infer how the code should behave based on whether specific parameters are null, and checks these inferred rules against dynamic behavior; it achieves a precision of 0.48 on its Java dataset.

Even with LLMs, tools that process code as a semantic object may still focus on particular patterns of inconsistencies. For instance,
MPChecker

(
Xu et al. 2025
)
focuses on
multi-parameter constraint
inconsistencies between API documentation and code. The approach relies on symbolic execution to extract code inconsistencies, making it hard to apply beyond the Python context it was developed in.
RustC4
(
Zhang et al. 2024
)
uses LLMs to extract a particular set of constraints from documentation, and compares these to constraints extracted by a static analysis pass over Rust ASTs. Both of these approaches achieve very high precision (>0.95), remain restricted to particular patterns of inconsistencies in particular programming languages.

Just-in-Time Approaches.

Inconsistency detection between code and documentation can be conducted in two different timings:
Just-In-Time
and
Post Hoc

(
Panthaplackel et al. 2021
)
. As
DocPrism
can function on code repositories in the wild, where inconsistencies may have been committed, our approach is
Post Hoc
.

Just-In-Time
refers to cases where the tool is run at code-update time, and admits an extra input to the system beyond the code and its documentation: the
diff
to these elements. As such,
DocPrism
is not directly comparable to exclusively
Just-In-Time
approaches
(
Stulova et al. 2020
;
Liu et al. 2021
;
Xu et al. 2024
;
Tan et al. 2025
;
Huang et al. 2025
)
: these all require some representation of the
diff
to work. Orthogonally, most of these
Just-In-Time
approaches are built and evaluated for Java
(
Stulova et al. 2020
;
Liu et al. 2021
;
Xu et al. 2024
;
Tan et al. 2025
)
, with one additionally evaluated on Python
(
Huang et al. 2025
)
.

Machine Learning-Based Inconsistency Detection.

While the pattern-based approaches mentioned earlier are restricted to specific types of inconsistencies, a number of works use machine learning to identify arbitrary code-doc inconsistencies.
Most prior works leveraging learning-based approaches
(
Huang et al. 2025
;
Xu et al. 2024
;
Tan et al. 2025
;
Panthaplackel et al. 2021
;
Rabbi and Siddik 2020
;
Cui et al. 2025
;
Igbomezie et al. 2024
;
Liu et al. 2018
;
Rong et al. 2025
)

treat inconsistency detection between code and comments as a binary classification problem. They train machine learning models
(
Rabbi and Siddik 2020
;
Panthaplackel et al. 2021
;
Tan et al. 2025
;
Huang et al. 2025
;
Igbomezie et al. 2024
;
Cui et al. 2025
;
Liu et al. 2018
)
or fine-tune pre-trained models
(
Rong et al. 2025
)
to achieve better performance across main evaluation metrics, such as precision, recall, and F1 score.

As aforementioned, manually labelling inconsistencies is hard. But training machine learning models requires plentiful labelled data. Some recent works
(
Xu et al. 2024
;
Rong et al. 2025
;
Cui et al. 2025
)
follow Panthaplackel et. al’s
(
Panthaplackel et al. 2021
)
procedure for constructing inconsistency data. The procedure two consecutive versions of (documentation, code) pair:
(D_{1},C_{1})
and
(D_{2},C_{2})
. Then, it labels the pair
(D_{1},C_{2})
as
inconsistent
if the code
and
documentation changed between versions (i.e.,
D_{1}\neq D_{2},C_{1}\neq C_{2}
), and labels the pair
(D_{1},C_{2})
as
consistent
if only the code changes (i.e.,
D_{1}=D_{2},C_{1}\neq C_{2}
). This falsely labels pairs as consistent when code changes in a semantically meaningful way but documentation fails to be updated.
Further, it has been pointed out that if documentation changes in a semantics-preserving manner,
(D_{1},C_{2})
will be falsely labeled as inconsistent
(
Xu et al. 2024
)
.
Also, the entire set of inconsistencies are doc-code pairs which never actually occur together in codebases (
(D_{1},C_{2})
does not occur in the codebase if
D_{1}\neq D_{2}
). This introduces potential distribution shift between these synthetic datasets and code “in-the-wild”.

We note that Panthaplackel et. al included a “clean” subset
(
Panthaplackel et al. 2021
)
, where these labels are validated by humans. Post Hoc peformance on the clean dataset was slightly lower than on the full dataset, with precision in the 0.54-0.61 range rather than the 0.56-0.63 range. This clean dataset has been reused in some subsequent work
(
Xu et al. 2024
)
, but not all
(
Cui et al. 2025
;
Rong et al. 2025
)
. Recent works included training methodologies to account for noise in the dataset labels
(
Xu et al. 2024
;
Rong et al. 2025
)
.

Automatically Fixing Inconsistencies
Our tool
DocPrism
not only performs binary classification but also attempts to explain inconsistencies.
Similarly, some works
(
Liu et al. 2021
;
Rong et al. 2025
)
aim to both classify and
automatically rectify
inconsistencies in the tested code or comments. Instead of automatically fixing inconsistencies,
DocPrism
aims to keep developers in the loop: it generates an HTML page for each benchmark, which provides the explanation and highlights inconsistent code and documentation snippets. This allows developers to be clearly informed and make corresponding judgments or fixes to the code or documentation. As current tooling is not accurate enough to fully automate rectification
(
Liu et al. 2021
;
Rong et al. 2025
)
, exploring ways to engage developers in rectification remains essential.

Prompting Methodologies.

Our local categorization approach, with its check-in and follow-up keys, is similar to the Chain of Thought (CoT)
(
Wei et al. 2022
)
approach, in that it breaks down a task into leading questions. The key distinction is that CoT is often used to improve the accuracy of the final LLM output; instead, we use the intermediate results in the check-in key directly, to filter out unwanted outputs.
Tam et. al find that constrained formats (i.e., JSON or XML) generally reduce performance on reasoning tasks
(
Tam et al. 2024
)
. However, they do find that for some classification tasks and LLMs, a JSON format greatly improves performance. They hypothesize that this format constraint helps with classification tasks because it constrains the number of possible answers; this is consistent with the improved performance from our local categorization prompt.

6.
Discussion

Overlap Between Different Inconsistency Types.
In our evaluation, we saw that some
DocPrism
sometimes outputs the same inconsistency into two categories. This happens most often with an inconsistency being listed as both an over-promise and direct mismatch, though sometimes an under-promise was also listed as direct mismatch (e.g., Figure
3
). This suggests that Local Categorization’s effectiveness depends on how well the Check-In Key question describes the target category. Upon analysis, our Check-In Key for direct mismatches,
“Does the code correctly implement what is mentioned in the documentation?”
, is semantically vague: “correctly implement” can also capture the notion of over-promise.

Generalization to Other LLMs.

Section
4
shows that
DocPrism
worked well using the LLaMa3.1-70B pre-trained model. To ensure the approach is not reliant on this one LLM, we also ran our approach with OpenAI’s GPT4.1 pre-trained model on our benchmark dataset. We see that LCEF remains effective at reducing the flag rate, with GPT-V4 flag rates of 87% dropping to 20% with GPT-DocPrism.
This suggests
DocPrism
is not over-fit to the LLaMa3.1-70B.
