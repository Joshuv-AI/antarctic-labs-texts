Bridging Language Gaps in Open-Source Documentation with Large-Language-Model Translation
1 st Elijah Kayode Adejumo, 2 nd Brittany Johnson, 3 rd Mariam Guizani

Abstract
While open source communities attract diverse contributors across the globe, only a few open-source software repositories provide essential documentation, such as ReadMe or CONTRIBUTING files, in languages other than English. Recently, large language models (LLMs) have demonstrated remarkable capabilities in a variety of software engineering tasks, even though they are not explicitly designed for such purposes. We have also seen advances in the use of LLMs for translations in other domains and contexts. Despite this progress, little is known regarding the capabilities of LLMs in translating open-source technical documentation, which is often a mixture of natural language, code, URLs, and markdown formatting. To better understand the need and potential for LLMs to support translation of technical documentation in open source, we evaluated community activity regarding translations along with English-to-German translations of 50 ReadMe files from OpenAI’s ChatGPT 4 and Anthropic’s Claude. We found scarce translation activity, most of which was found in larger repositories, community-driven and opportunistic in nature. A comparison of LLM performance as translators and evaluators of technical documentation suggests LLMs can provide accurate translations. However, an analysis of resulting translations found fidelity challenges: both models struggled to preserve structural components (e.g., hyperlinks) and exhibited formatting inconsistencies. These findings highlight both the promise and the challenges of LLM-assisted documentation internationalization. As a first step towards translation-aware continuous integration pipelines, we introduce TRIFID , an early-stage translation fidelity scoring framework that automatically checks how well translations preserve code, links, and formatting. Our efforts provide a foundation towards automated LLM-driven support for creating and maintaining open source documentation.

III
Methodology

Our initial focus was on identifying translation patterns across open-source software repositories and evaluating LLMs’ translation capabilities for technical documentation. To achieve this, we used the following methodology:

III-A

Data Set

To reveal translation activities across repositories, we analyzed repositories at three scales based on stars and forks, as these metrics typically represent community engagement and project adoption
[
26
,
27
]
.
They were classified into small-scale, medium-scale, and large-scale using the following criteria:

i

Small-Scale:
100 - 5,000 stars and forks

ii

Medium-Scale:
5,000 - 10,000 stars and forks

iii

Large-Scale:
Stars and forks greater than 10,000

Given the importance of the
ReadMe
file
[
28
]
, we considered it a strong foundation for understanding translation issues and contribution patterns. For each repository category (small-scale, medium-scale, and large-scale), we searched for and extracted pull requests and issues whose titles contained “translate README” using a keyword-based approach
[
29
]
. This allowed us to assess the current state of translation contributions and issues raised across different repository categories. We then analyzed the timestamps of these pull requests to understand contribution trends and identify when translation activity peaks, providing insights into the periods or seasons during which translation demand is most likely to surge.

To evaluate how effective and sustainable these translation contributions are, we examined whether the pull requests were actually adopted (merged) and, if merged, how well they kept up with their rapidly evolving English source. We compared the rate of change in the English and translated versions 180 days (six months) after each pull request was merged.

III-C

TriFid Preservation Scoring Framework

Most
ReadMe
files in open-source software contain a combination of written instructions, code snippets, and URLs linking to additional or relevant resources.
This information is typically formatted and structured using markdown
[
35
]

To assess how well Large Language Models (LLMs) preserve these key components, we introduce
TriFid
(TriFidelity) as an early stage evaluation framework.
TriFid
’s evaluation and automated scoring is defined as follows:

III-C
1
Code Block Evaluation and Score

This score evaluates consistency in code blocks and their content after translation.

Code Block Count Ratio:

Let
N_{\text{orig}}
and
N_{\text{trans}}
be the number of code blocks in original and translated versions, respectively. The count ratio is:

i.

Case 1:
If
N_{\text{orig}}=0
and
N_{\text{trans}}=0
, then
r_{\text{count}}=1.0

ii.

Case 2:
Otherwise,
r_{\text{count}}=\frac{\min(N_{\text{orig}},N_{\text{trans}})}{\max(N_{\text{orig}},N_{\text{trans}})}

The code block count score is:
CodeScore_{\text{count}}=50\times r_{\text{count}}

Code Content Preservation:

We verify that actual code content is preserved by normalizing code (ignoring translated comments and output lines starting with #, $, or *). Define the binary indicator:

1(\text{content preserved})=\begin{cases}1,&\text{if all normalized blocks in }\\
&\text{ original match translation}\\
0,&\text{otherwise}\end{cases}

The content preservation score is:
CodeScore_{\text{content}}=50\times 1(\text{content preserved})

Combined Code Score:

The overall code block score is:
Score_{\text{code}}=CodeScore_{\text{count}}+CodeScore_{\text{content}}

where
Score_{\text{code}}\in[0,100]
.

III-C
2
URL Evaluation and Score

This score evaluates URL preservation across original and translated texts, penalizing extra URLs in translation.

Definition:

i.

U_{\text{orig}}
= set of URLs in original text

ii.

U_{\text{trans}}
= set of URLs in translated text

iii.

n_{\text{preserved}}=|U_{\text{orig}}\cap U_{\text{trans}}|

iv.

n_{\text{missing}}=|U_{\text{orig}}\setminus U_{\text{trans}}|

v.

n_{\text{extra}}=|U_{\text{trans}}\setminus U_{\text{orig}}|

Total original URLs:
N_{\text{origURL}}=n_{\text{preserved}}+n_{\text{missing}}

Scoring Components:

i.

Preservation Component (70% weight):

S_{\text{preserve}}=70\times\frac{n_{\text{preserved}}}{N_{\text{origURL}}}

ii.

Extra URL Penalty (up to 30 points):

P_{\text{extra}}=\min\left(30,30\times\frac{n_{\text{extra}}}{N_{\text{origURL}}}\right)

Bonus for no extra URLs:
S_{\text{extra}}=30-P_{\text{extra}}

Final Score:

If
N_{\text{origURL}}>0
:

S_{\text{url}}=70\times\frac{n_{\text{preserved}}}{N_{\text{origURL}}}+\left(30-\min\left(30,30\times\frac{n_{\text{extra}}}{N_{\text{origURL}}}\right)\right)

If
N_{\text{origURL}}=0
:
S_{\text{url}}=100

Result is rounded to nearest integer within [0,100].

III-C
3
Markdown Formatting Evaluation and Score

This evaluation validates how well LLMs preserve Markdown syntax after translation
[
1
]
.

Define
M=7
categories: headers, bold, italic, lists, numbered lists, tables, and blockquotes.

For each category
i
:

i.

E_{\text{orig}}(i)
= count of elements in original text

ii.

E_{\text{trans}}(i)
= count of elements in translated text

For each category, the ratio is:

i.

If both counts are zero:
r_{i}=1.0

ii.

Otherwise:
r_{i}=\frac{\min(E_{\text{orig}}(i),E_{\text{trans}}(i))}{\max(E_{\text{orig}}(i),E_{\text{trans}}(i))}

The overall Markdown score is:

S_{\text{md}}=\left(\frac{1}{M}\sum_{i=1}^{M}r_{i}\right)\times 100

IV-B

LLM technologies for documentation translation

Our evaluation of translations produced by ChatGPT 4.0 and Claude 3.5 Sonnet found that both models can process inputs or queries written in markdown and generate corresponding translations in markdown format when explicitly prompted.
However, we observed notable differences in how accurately they preserve technical elements such as URLs, code snippets, and markdown formatting commonly found in technical documentation.

To quantify this, we applied our early stage
TriFid
preservation scoring framework, which assesses the fidelity of translations in terms of code, URLs, and markdown structure compared to the original content.
Based on the translation of 50
ReadMe
files, Claude achieved an average accuracy of 95.6% across URL, Code, and Markdown Preservation scores, while ChatGPT 4.0 attained an average accuracy of 89.18% for the same categories.
A closer inspection of markdown formatting revealed that 34% of translated
ReadMe
files exhibited inconsistencies in bold text, 32% lost italic emphasis, and 22% showed alterations in header structure. These discrepancies affect the integrity of the documentation’s information architecture, potentially hindering readability and navigability.

We also observed a moderate to strong negative correlation between
ReadMe
file sizes and the models’ ability to preserve code, URLs, and markdown elements. URL preservation showed the strongest negative correlation at
-0.699
, followed by markdown formatting at
-0.499
.
This indicates that as file sizes increased, the
TriFid
framework reported lower preservation scores across these dimensions.

V
Discussion & Future Work

We found that community engagement often plays a key role in supporting documentation translation within open source projects.
However, our findings indicate that this support primarily benefits larger, more established repositories.
Although periodic opportunities such as Hacktoberfest can trigger bursts of translation activity, smaller repositories often lack the visibility or contributor base needed for consistent translation efforts
[
40
]
.
Even in more mature projects that do receive occasional contributions, sustaining and updating translations remains a significant challenge.

LLMs present a promising, yet underexplored, alternative by offering on-demand translation capabilities that are independent of community size, event timing, or project popularity.

While LLM-generated translations may not yet be fully reliable on their own, our results suggest they can serve as a strong foundation for a more systematic, AI-assisted approach to multilingual documentation.
In cases where no translation currently exists, LLMs can produce initial drafts, easing the effort required to introduce diverse language support.
For projects that update their original (typically English) documentation, change-detection tools could prompt LLMs to generate updated translations automatically.
Moreover, as our findings indicate, providing LLMs with access to prior translations can enhance both quality and consistency, offering a path to improve translation updates over time.
In both scenarios, communities can use our
TriFid
framework to evaluate and guide translation efforts thereby enabling current and potential contributors to maintain translation quality more effectively.

V-A

Fine-tuning LLMs for Documentation Translation

Our early-stage
TriFid
evaluation uncovered structural issues that commonly affect LLM-generated translations of technical documentation particularly with preserving URLs, code snippets, and markdown formatting.
Unlike general-purpose translation tasks, technical documentation requires attention to structural fidelity, accurate technical terminology, and completeness.

As interest in LLMs grows, research increasingly supports the need for fine-tuning in domain-specific contexts
[
41
,
42
,
43
]
.
A promising direction for improving translation of technical documentation lies in adapting pre-trained LLMs such as ChatGPT and Claude specifically for this purpose.
This could involve designing loss functions that penalize structural deviations during training and incorporating verification mechanisms to ensure all sections from the source documentation are preserved in the output.

V-B

Optimizing
TriFid

While
TriFid
is still in an early stage without existing benchmarks for comparison, we plan to continuously optimize the framework going beyond
ReadMe
s to CONTRIBUTING guides and API reference pages. Since,
TriFid
provides crucial signals of preservation losses that are vital for fine-tuning LLMs for technical documentation tasks. The ability to easily refine and improve these core components makes LLM-driven translation more robust compared to traditional machine-translation approaches.

V-C

Human-In-Loop

Even a carefully tuned
TriFid
cannot capture every nuance that makes a translation usable for developers.
Adding a systematic human-in-the-loop layer on top of the automated checks. We will sample a small, stratified subset of PRs that pass (or narrowly fail)
TriFid
and send them to native speakers who are also professional technical writers or translators. These experts will (i) rate adequacy and fluency, (ii) flag subtler issues such as cultural tone, idiomatic terminology, or code comments that the metric currently overlooks, and (iii) annotate the minimal edits needed to reach publishable quality.
