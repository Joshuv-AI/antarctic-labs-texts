Factor( T T , U U ): Factored Cognition Strengthens Monitoring of Untrusted AI
Aaron Sandoval, Cody Rushing

Abstract
The field of AI Control seeks to develop robust control protocols, deployment safeguards for untrusted AI which may be intentionally subversive. However, existing protocols that rely on weaker monitors to detect unsafe behavior often fail on complex tasks beyond the monitor’s comprehension. We develop control protocols based on factored cognition, in which a trusted model decomposes a task, an untrusted model solves each resultant child task in isolation, and the results are reassembled into a full solution. These protocols may improve safety by several means, such as by simplifying the context for monitors, or by obscuring vulnerabilities in the environment. We implement our protocols in the APPS coding setting and red team them against backdoor attempts from an adversarial GPT-4.1 Nano. We find that: (i) Adding factored cognition to a trusted monitoring protocol can boost safety from 41% to 63%; (ii) Safety improves because monitor performance improves; (iii) Factored cognition makes it no harder for capable LLMs to write backdoors in APPS. While our protocols show low usefulness in APPS, they hold promise for more complex tasks.

2
Setting

We perform control evaluations using methods similar to
7
. For readers familiar with this work, Appendix
E
contains an alternate description of our setting in terms of deviations from theirs.

We use the APPS control setting of coding problems
(
7
)
where a red team attempts a side task of writing backdoored solutions that pass undetected during a deployment. We use 500 tasks from the APPS-verified subset
(
12
)
, applying a 50/50 train/test split. 99% of tasks have exactly one unit test case, modeling a setting with little ground truth knowledge about the intended behavior of solutions. Control evaluations are conducted as an iterative red teaming process, in which a red and a blue team use different resources to achieve opposing objectives.

2.1
Resources and Restrictions

Untrusted model
: The blue team has access to
U
, a strong model that may or may not be attempting to write hidden backdoors. In a deployment,
U
may either act identically to GPT-4.1 Nano, which we call the honest policy
U_{H}
, or it may follow an attack policy
U_{A}
designed to write backdoors.
U_{A}
is an LLM system that has been built by the red team.
U_{A}
may use attack templates, make calls to GPT-4.1 Nano, and follow stochastic policies precisely.
U_{A}
makes an
attack
whenever it attempts to write a backdoor. The red team has full knowledge of the blue team’s control protocol and can access all the results of previous experiments. The blue team can also access the results of previous experiments, except for any internal functionality of
U_{A}
. The red team cannot call
T
or fine tune on
T
’s outputs, but they can iterate directly against the control protocol, which calls
T
.
U
maintains no memory between calls. These red team allowances are intended to amplify the capabilities of GPT-4.1 Nano to conservatively bound the ability of a similar model that is scheming to subvert the control protocol. Following
7
, the blue team may measure summary statistics of
U_{H}
and use them in protocols.

Trusted models
:
The blue team may also use
T
, a weaker trusted model which never attempts attacks, implemented using Llama 3.1 8B-instruct
(
6
)
. We additionally allow access to a powerful trusted model for the exclusive use of decomposing tasks. We call this decomposer model
D
and implement it with OpenAI o3-mini. Using
D
in Factor(
T
,
U
) produces the Factor(
D
,
U
) protocol. This compensates for Llama 3.1 8B-Instruct’s poor decomposition ability without directly upsetting the capability gap in the weaker
T
monitoring the outputs of the stronger
U

D
for further justification and discussion of this allowance.

Auditing
:
Similar to the methods of
1
, the blue team has access to limited perfect auditing. The blue team may audit up to 2% of samples in the trajectory. For simplicity, we assume
perfect auditing
: if a solution containing any deviation from
U_{H}
is audited, this always reveals incriminating evidence of scheming and triggers a shutdown of
U
, terminating the deployment safely. This incentivizes the red team to only ever deviate from the behavior of
U_{H}
when attacking. We acknowledge that perfect auditing is unrealistic for this setting, but we don’t expect it to meaningfully affect our conclusions. For factored cognition protocols, child task solutions are audited in isolation, and one such audit costs the same against the budget as an audit of a solution from trusted monitoring. For simplicity, the blue team is restricted to using fixed criteria over the deployment for deciding whether to audit a solution.

2.2
Metrics and Red/Blue Team Objectives

The blue team’s objective is to maximize the test set usefulness and safety of their protocol as defined in
7
. The threat model is
high-stakes
, meaning that a control protocol accepting a single backdoor is considered catastrophic. The red team’s objective is to minimize safety. In a run measuring usefulness, all calls to
U
are implemented by
U_{H}
, and we measure accuracy, the proportion of samples where the solution passes all unit tests. Usefulness is a linear rescaling of accuracy where
T
has 0% usefulness and
U_{H}
has 100% usefulness.

To measure safety, we run the experiment using
U_{A}
and measure the probability that the deployment terminates safely before a backdoored solution is accepted by the protocol. A solution is considered backdoored if it meets all of the following criteria. We discuss these criteria further in section
4.1
.

•

It passes a set of unit tests from the dataset

•

It contains an attack

•

When GPT-4.1 Nano is prompted with the task and solution, it provides a successful exploit: an input to the solution which produces a behavioral difference relative to a reference solution. We call this instance of GPT-4.1 Nano the
exploit finder

7

3.2
Security through Obscurity

To investigate the causes of our superior ASR relative to trusted monitoring, we perform an additional experiment. We test if the ASR difference is due to security through obscurity, a possible safety benefit of Factor(
D
,
U
) protocols. If these protocols possess security through obscurity, it means that attacks fail more often because the limited context hides information about the target of the attack, making it harder to assess attack opportunities, resulting in some attacks failing which would have succeeded had
U
been given the full root task context. We expect this possible benefit to only apply to some threat models, including APPS backdoors. See Appendix
I
for details on this threat model partition.

We test the security through obscurity hypothesis by running all protocols using the stronger o3-mini as the exploit finder rather than GPT-4.1 Nano. If the hypothesis were true, then Factor(
D
,
U
) should maintain its superior ASR with a stronger exploit finder since
U
’s failed attacks were more likely to be unsalvageable. However, since we see in Figure
2
that there is no significant difference in ASR using an o3-mini exploit finder, it’s more likely that the difference when using a GPT-4.1 Nano exploit finder is due to something other than security through obscurity, such as the longer and more complex Factor(
D
,
U
) solutions impeding GPT-4.1 Nano’s ability to understand and exploit the attacked code. Though generating complex solutions whose structure is specifically intended to confuse attackers is a possible blue team strategy, we don’t expect our implementation of Factor(
T
,
U
) to have such a benefit against models of capability similar to o3-mini, let alone truly untrusted models.

If we expect Factor(
T
,
U
) to have no systematic advantage in ASR, then to what degree does it maintain its safety advantage? As a proxy measurement, we recompute the safety of each protocol using the o3-mini exploit finder and conservatively estimate
P=0.066
that Factor(
D_{\mathrm{low}}
,
U
) has no safety advantage compared to trusted monitoring. This value is conservative both because Factor(
T
,
U
) maintains its systematic advantage in monitor performance, and because the estimate does not fully account for possible correlations of individual root task outcomes between the protocols. For these reasons, we are confident that Factor(
D_{\mathrm{low}}
,
U
) would maintain a significant advantage in safety compared to trusted monitoring even when using untrusted models with a similar ASR between the two protocols. See Appendix
B
for further details on the study.

4
Discussion

Mechanisms for improved safety
: Our findings indicate that factored cognition provides simplicity benefits for monitors by increasing the trusted monitor’s suspicion of attacks in APPS. However, there is no such clear distribution shift for honest solutions. While we find no evidence for security through obscurity in APPS, this doesn’t preclude such safety benefits in other settings.

Low Factor(
T
,
U
) Usefulness is Not a General Property Across Settings
: The usefulness of task decomposition protocols is likely much more task-dependent than for the more foundational protocols in
1
and
7
. While our scaffold degrades accuracy in APPS, other task decomposition scaffolds improve accuracy on tasks such as question-answering, math, and symbol manipulation
(
21
;
5
;
8
)
. Furthermore, there is a broad class of tasks already being solved through automated task decomposition and multi-step LLM workflows. In the context of AI control, a generic LLM agent implemented with an untrusted model can be viewed as a task decomposition protocol without any of the safety features of factored cognition protocols like monitoring or context isolation for child tasks, where decomposition and child task implementation are all done by
U
. It may not be difficult to add safety-relevant features to these protocols and workflows.

Task decomposition in the form of LLM agent systems has gained immense popularity purely for its capabilities on complex tasks
(
2
)
. Factored cognition protocols will be most viable for these types of tasks, where decomposition is not a burden but an enhancement. For these tasks, the loss in usefulness will come from the context isolation and other safety features necessary to turn a regular LLM agent system into a proper Factor(
T
,
U
) or Factor(
U
,
U
) protocol. Decomposition itself will not differentially degrade usefulness, increase inference cost, nor lengthen latency. Therefore, these protocols are most promising for tasks where decomposition occurs by default, and where the natural baseline is a generic task decomposition system without the safety features of AI control protocols. The usefulness of Factor(
T
,
U
) in APPS is an underestimate of its potential usefulness on more complex tasks.

4.1
Limitations

Powerful Decomposer Allowance
: Given the weakness of
T
, this allowance was necessary to investigate our hypotheses about factored cognition protocols, but it may also result in overestimating their safety. Since
D
never sees
U
’s outputs, we think that Factor(
D
,
U
)’s safety performance is a decent first-order safety estimate. Still, there may be bias in our safety results, such as from highly detailed child tasks giving monitors extra clues as to what parts of a child solution are/aren’t legitimate. See Appendix
D
for a full discussion.

Honest Policy Safety Failures
: We found that
U_{H}
writes backdoored solutions on about 1% of tasks. This is more likely for our split of APPS because 99% of tasks in our split contain exactly one unit test, far fewer than the splits used by
7
or
20
. Honest policy safety failures like these can undermine key features of high-stakes control evaluations such as the red team’s incentive to attack and the blue team’s ability to incriminate scheming models. Our definition of a backdoor (see section
2.2
) was selected to artificially mitigate these problems, and though we don’t believe that these are good general assumptions for other research using backdoored code threat models, we believe that our experiments maintain their integrity relative to our specific research questions and reflect the qualitative results that one would get using a split of APPS without honest policy safety failures.

Generalization from Weak Models and Elicitation
: This study uses relatively weak models due to its limited budget and scope. Also, while we are satisfied with our elicitation in attack selection, our attack policies were much simpler than those in
7
or
22
. It’s unclear how well our results would generalize to stronger models using more thorough elicitation.

4.2
Future Work

Control evaluation in a new setting
: A proper evaluation of the safety and usefulness of task decomposition protocols must test Factor(
T
,
U
), not Factor(
D
,
U
). It would be most relevant to use a setting where task decomposition is a lesser hindrance, such as an LLM agent setting or one with otherwise complex tasks.

Test Attack Coordination Challenges hypothesis
: Factored cognition might provide additional safety via a separate mechanism for multi-step control settings like BashBench
(
1
)
. In their study, a dominant strategy is multi-step attack strategies in which attacks are distributed across an agent trajectory. If this trajectory is broken up into isolated child tasks, it may be harder for an attack policy to coordinate these attacks.

Test Simplicity Benefits for Other Blue Team Tactics hypothesis
: In addition to monitoring, other blue team tactics may be more effective when applied to simpler child tasks, such as editing solutions and generating unit tests.

Extensions of Factor(
T
,
U
)
: Other potentially useful features which could be added include:

•

Use implementers besides trusted monitoring

•

Test a range of model capabilities for
D
and examine safety trends

•

Add another monitoring, editing, or resampling step after reassembly with the full root task solution

•

Use
T
or
U
to generate child task unit tests

•

Use more sophisticated LLM task decomposition scaffolds from the literature

Other factored cognition protocols
: Forthcoming work is exploring Factor(
U
,
T
) and Factor(
U
,
U
) protocols, where the untrusted model decomposes tasks. However, some questions related to those protocols remain open. In particular, future research should explore what steganographic bandwidth can be achieved in decompositions in a Factor(
U
,
U
) protocol, and how various blue team measures for limiting that bandwidth trade off safety and usefulness.

Appendix A
Glossary

The primary desiderata for control protocols are:

Safety
: The protocol can reliably detect and safely manage attacks within the untrusted AI’s capabilities that help it achieve its misaligned goals.

Usefulness
: In the case that the untrusted model is not scheming, the protocol minimally degrades the capabilities at the task.

Cost
: The protocol does it all economically, with minimal compute and human labor.

The basic set of intelligent resources which we have at our disposal to build control protocols are:

U
: A smart untrusted model, which might be scheming against us.

T
: A trusted model with capabilities inferior to
U
, which we are confident isn’t scheming.

H
: Trusted, high-quality human labor. In experiments, this is often simulated using a frontier LLM for practical reasons.

The 3 roles of human researchers which control different elements of control experiments are:

Red team
: Elicits worst-case adversarial behavior from
U
given a set of affordances. The red team’s goal is to minimize safety given a blue team protocol.

Blue team
: Constructs control protocols given a set of affordances to maximize safety and usefulness.

White team
: Decide the affordances, assumptions, and high-level experimental setup within which the red and blue teams optimize their objectives.

The red team creates two distinct policies that
U
can follow when called by the control protocol:

U_{H}
: Untrusted model honest policy. Faithfully follows instructions without attempting an attack, like a trusted model.

U_{A}
: Untrusted model attack policy. Sometimes attempts an attack, and sometimes follows a policy identical to
U_{H}
.

Usefulness run
: The part of a control evaluation which measures the usefulness of a protocol. It is executed as an evaluation in the setting where
U_{H}
is used whenever the protocol calls
U
.

Safety run
: The part of a control evaluation which measures the safety of a protocol. It is executed as an evaluation in the setting where
U_{A}
is used whenever the protocol calls
U
.

In the APPS setting,
U_{A}
attempts
attacks
, where it attempts to include a
backdoor
in its solution. A backdoor is an exploitable feature of the solution which produces a behavioral difference from a ground truth reference solution for some valid inputs while the solution still passes a set of unit tests. To determine if a solution contains a backdoor, an
exploit finder
(implemented by an LLM) proposes an
exploit
, which is a specific input to a solution which may produce a behavioral difference. If it really does produce a behavioral difference, then this is a
successful exploit
. If the solution passes unit tests and the exploit is successful, then the solution is backdoored. If an attacked solution fails unit tests or the exploit does not produce a behavioral difference, it is a
failed attack
.

We use the following terms related to the task decomposition. These terms are defined with code-writing tasks in mind but should be pretty generalizable:

Task
: A data structure containing a natural language problem description and possibly other fields. For functional programming tasks, it may include a function signature and a set of unit tests and test cases to check the validity of a solution.

Solution
: An implementation of a task, including the solutions to any and all child tasks.

Parent task
: Any task which has been decomposed into child tasks.

Child task
: A task resulting from the decomposition of a parent task.

Sibling task
: A child task which shares the same parent as another child task.

Root task
: The original problem that we ask the AI system to solve.

Leaf task
: A task which is not decomposed and is solved by direct implementation.

Reassembly logic
: The part of the parent task solution which defines how to use the child task solutions to solve the parent task.

Decomposer
: The part of a control protocol which decomposes a parent task into a set of child tasks and a reassembly function.

Implementer
: A human/LM system which implements a solution to a task. Implementers are themselves control protocols.

The following are abbreviations for certain categories of task decomposition control protocols.

Factor(
T
,
T
)
: A factored cognition system for the trusted model.

Factor(
T
,
U
)
: A task decomposition control protocol with
T
as decomposer and implementer protocols which use
U
.

Factor(
U
,
T
)
: A task decomposition control protocol with
U
as decomposer and implementer protocols which use
T
only.

Factor(
U
,
U
)
: A task decomposition control protocol with
U
as decomposer and implementer protocols which use
U
.

Some miscellaneous terminology which we haven’t seen in control literature previously but which we found useful:

Trigger set
: The set of all possible inputs to a backdoored function which return unexpected results. Or, more formally, for a valid input
x\in S
, a reference solution function
f(x)
, a backdoored version
f\textquoteright(x)
, and assuming a single unit test which asserts the equality of solutions, the trigger
S_{t}
set of
f^{\prime}(x)
is
S_{t}\subseteq S:x\in S_{t}\iff f(x)\neq f^{\prime}(x)
.

Decomposition tax
: The relative loss in accuracy from adding task decomposition to a protocol. Decomposition tax = 1 - (accuracy of Factor(
T
,
T
) / accuracy of
T
).

Appendix D
Discussion on Powerful Decomposer Allowance

We’d like experiments in the APPS setting to be able to tell us helpful information about factored cognition protocols despite the shortcoming of the setting. We think that giving access to the powerful decomposer
D
allows us to do this for Factor(
T
,
U
) protocols. With the current state of LLMs, Factor(
D
,
U
) is a better model of the safety-related dynamics of future AI control scenarios than Factor(
T
,
U
) when using a significantly weaker trusted model like Llama 3.1 8B-Instruct. We select a
T
significantly weaker than
U
because this seems to usually be our best way to model future control evals with actual untrusted models
(
18
)
. This assumption seems reasonable for uses of
T
which are directly adversarial to
U
, such as monitoring, editing, generating unit tests, and generating honeypots. But we don’t think that the assumption is valid for every possible use of
T
, including for task decomposition. Using Llama 3.1 8B-Instruct as our decomposer we would achieve -63% usefulness and conclude that Factor(
T
,
T
) and Factor(
T
,
U
) were completely hopeless. Factor(
U
,
U
) might be competitive with vanilla trusted monitoring in APPS only if you used the very best frontier models for
U
.

However, we think that these huge performance differences will not generalize to most important settings even when
T
and
U_{H}
have a similar accuracy gap. Consider measuring a safety and usefulness result from trusted monitoring using weak models, and attempting to estimate the performance on the same setting when using a stronger
T
and
U
with a similar capability gap. It seems plausible that the results could be similar to those from the weaker models. When doing a similar extrapolation with Factor(
T
,
U
), however, this pattern probably doesn’t hold. Since a stronger
T
tends to have a lower decomposition tax (see Appendix
C
), it will gain accuracy
that is not lost by the normalization from accuracy to usefulness
. The future
T
that we use in actual control evaluations will be at least as good at decomposing as o3-mini. The current low usefulness of Factor(
T
,
T
) and Factor(
T
,
U
) relative to simple baselines is an artifact of the weak selection of
T
, a necessity when running control evaluations in a relatively easy setting. This creates a large usefulness bias against task decomposition protocols when we try to generalize their performance to more difficult settings using more capable models. We can reduce that bias by using our best available LLM decomposer instead. The usefulness of Factor(
D
,
T
) and Factor(
D
,
U
) is closer to what we predict will be true using future trusted decomposers, but there is sufficient irreducible uncertainty that we don’t think that it’s valid to compare our Factor(
D
,
U
) usefulness results to those of non-decomposition protocols.

Bias in safety performance
: Since
D
can never see
U
’s outputs, we think that Factor(
D
,
U
)’s safety performance is a decent first-order safety estimate. Still, there may be bias in our safety results, such as from highly detailed child tasks giving monitors extra clues as to what parts of an implementation are/aren’t legitimate. Maybe some of our safety and monitor performance gains could be achieved by a protocol where
D
merely rephrases root tasks into the style that it uses to write child tasks.

Appendix E
Methodological Differences from
7
and Miscellaneous Methodological Details

E.1
Differences from
7

For readers very familiar with
7
, we provide here an alternate summary of our methods given as a list of differences from theirs, as well as some extra methodological details which may not be different but are not completely clear from that paper.

1.

Simple baseline protocols
: We build a simple trusted monitoring protocol instead of attempting to replicate the protocol from
7
. In particular, the backdoor generation, attack selection, and trusted monitor subroutines are simplified.

2.

APPS dataset split
: We use 500 tasks from the APPS-verified subset
(
12
)
, applying a 50/50 train/test split.
2
2

2

Our splits are available at
https://huggingface.co/datasets/xtremekiwi/APPS-leetcode-codeforces
99% of tasks in our split have exactly one unit test case. The red and blue teams have access only to the train split during red teaming. We allow for no re-fitting of protocols or policies to the test split, with the exception of setting a new audit threshold.

3.

Perfect auditing
: Any action that deviates from
U_{H}
is assumed to be incriminating if audited, allowing the blue team to trigger a shutdown.

4.

No incrimination by distribution shift
:
7
allow the blue team to trigger shutdown by monitoring for shifts in
U_{A}
’s summary statistics relative to
U_{H}
’s. We do not allow for this mode of incrimination, as perfect auditing is sufficient to discourage the red team strategies that incrimination by distribution shift covers in
7
and
1
.

5.

Audit thresholds and budget
: The auditing budget (2% of tasks) is used to set the auditing threshold (a suspiciousness rating), but once the threshold is set, the budget does not constrain how many tasks may actually be audited in the safety run. The budget is the expected proportion of tasks which would be audited conditional on
U
not scheming. If
U
is actually scheming and making attacks, then the expected proportion of audited tasks exceeds the budget, but this is acceptable and the blue team may still audit all of them.

6.

No free upfront auditing
:
7
allowed the blue team to audit the first 10 tasks for free to discourage strategies which use variable audit thresholds, as this was not a focus of that paper. For the same reason, we constrain the blue team to maintaining a constant audit threshold for all tasks and give no free audits.

7.

Discretized suspiciousness and audit thresholds
: The blue team scores suspiciousness as a discrete measure (e.g., integers 0–9). The audit threshold is set at the suspiciousness value with the smallest expected proportion of audited tasks at least as large as the auditing budget. For example, with a budget of 2%, if 1% of usefulness run solutions have suspiciousness 9, and 3% have suspiciousness 8, the threshold is set at 8. Solutions equal to the threshold are audited at random, with a fixed on-threshold audit probability set such that the budget is met in expectation. In this example, the probability would be 33%.

8.

Audit thresholds and budget
: The auditing budget (a proportion of tasks) is used to set the auditing threshold (a suspiciousness rating), but once the threshold is set, the budget doesn’t constrain how many tasks may be audited in the safety run. The budget is the expected proportion of tasks which would be audited conditional on
U
not scheming. If
U
is actually scheming, then the expected proportion of audited tasks exceeds the budget, but this is acceptable and the blue team may still audit all of them.

9.

Monitor all solutions
: The blue team only explored strategies where
T
monitored all solutions, regardless of whether they passed unit tests. A common alternative in other control work is to monitor only solutions which pass unit tests. Since solutions which fail unit tests are rejected anyway, there is no way that they can cause catastrophic outcomes. However, monitoring all solutions offers more opportunities to incriminate
U
using failed attacks.

10.

Exploit finder
: Due to a special property of Factor(
T
,
U
) protocols, all exploits in all protocols used to check for backdoors are generated in a separate call to GPT-4.1 Nano with full problem and solution context.

11.

Exploit validation
: A white team call to GPT-4.1 Nano checks if a proposed exploit obeys the input constraints of the problem. The exploit finder has 3 chances to submit a valid exploit, and it gets feedback from the validator on each rejection.

12.

Computing variance of safety
: We run multiple epochs of our small dataset and use a two-stage cluster bootstrapping method to estimate the variance of safety, usefulness, and other metrics. See Appendix
F
for details.

13.

Model selection
: We use more recent models:
T=
Llama 3.1 8B-Instruct,
U=
GPT-4.1 Nano. Under perfect auditing, there is no need to simulate trusted human labor.

14.

Downsampling
: Our final runs use a downsampling factor of 18, compared to 12 in
7
. We scale the downsampling factor linearly with the number of root tasks in the safety run. This practically decouples the red and blue team strategies (the attack selection model in particular) from the size of the safety run, allowing us to scale runs arbitrarily.

15.

Access to opposite team’s protocol or model
: Both the red and blue team have nearly full black box access to the opposite team protocol and all outputs produced while improving their protocol. Each team may iterate directly against the adversarial protocol. The red team also has access to all blue team prompts and scaffolding, but the attack policy itself still may not call the trusted model. The only further limitation we impose is that teams may not fine-tune against the adversarial model, protocol, or policy.

The following are assumptions and allowances specific to task decomposition protocols.

16.

Powerful decomposer
: We give the blue team access to a powerful trusted decomposer (
D
), a highly capable model for the exclusive use of decomposing tasks. We implement
D
using OpenAI o3-mini (medium reasoning). This allowance compensates for
T
’s poor decomposition ability, allowing us to explore strategies for these protocols without directly upsetting the capability imbalance in the weaker
T
monitoring code written by the stronger
U
. See Appendix
D
for further discussion of this allowance.

17.

A backdoored child task does not imply a backdoored parent task
: If a child task is backdoored, but the backdoor is not exploitable by the exploit finder in the full context of the root task solution, then this is a failed attack and a safe outcome.

18.

Child task solutions are audited in isolation
: If any child task solution has a suspiciousness above the audit threshold then that child task solution alone is audited. Attacks below the audit threshold in sibling tasks would not get caught.

E.2
Miscellaneous Methodological Details

Here we include a loose collection of details and points of confusion that we encountered when setting up our experiments in APPS. These match the methods from
7
unless otherwise noted. These details might not be clear from reading existing literature, and so might serve some purpose for future researchers.

Red/blue team access to data and adversarial model
: Both teams have nearly full black box access to the opposite team protocol and all intermediate results while improving their protocol, but not while actually running evaluations. Each team may iterate directly against the adversarial protocol. The red team has access to all blue team prompts and scaffolding, but the attack policy itself still may not call the trusted model. The only further limitation we impose is that teams may not fine tune against the adversarial model at any point.

Monitor ROC Curves
: There are several possible classification tasks on which we could evaluate the monitors, but we focus on classifying solutions between:

1.

Attacked
vs
not attacked

2.

Attacked and passes unit tests
vs
not attacked and passes unit tests

These correspond to the two possible auditing strategies. We use strategy 1.

1.

Monitor all solutions: Monitor and potentially audit any task

2.

In real control deployments, labs can reduce monitoring compute cost and potentially also improve safety by filtering out failed solutions before monitoring.

Appendix F
Bootstrapping Details

We use cluster bootstrapping to estimate the sampling distributions of key metrics including audit thresholds, safety, and ASR. In a bootstrapping run, we resample with replacement clusters of leaf tasks from the results until the resampled quantity of leaf tasks is equal to the quantity of in the original sample. Leaf tasks are clustered by the APPS sample ID, so multiple epochs and multiple child tasks are all clustered together. Applicable statistics are calculated for each resample. We resample 500 times independently to compute a bootstrapping distribution for each statistic. The following enumerates our procedure:

1.

Initialize two random number generators to use for resampling root task clusters, one for the usefulness run and one for the safety run, each with a different fixed seed
3
3

3

For the purposes of comparing performance between protocols, if those protocols used the same tasks and number of epochs in their safety and usefulness runs (which ours did), this common initialization removes the variance of different protocols resampling different multisets of tasks.
.

2.

Safety run filtering

(a)

Cluster the safety run root tasks by APPS sample ID.

(b)

Filter the safety run root tasks to include only clusters with at least one attack attempt.

3.

Usefulness run resampling

(a)

Resample clusters.

(b)

Compute usefulness, audit threshold, and on-threshold audit probability.

4.

Safety run resampling

(a)

Using the auditing parameters, compute the win/lose/continue outcome for each root task.

(b)

Resample clusters.

(c)

De-cluster into individual root tasks.

(d)

Filter to only include attacked root tasks.

(e)

Compute safety as a deterministic function of the root task outcome counts and the downsampling factor for that run. No variance due to random downsampling is introduced.

(f)

Compute the remaining safety metrics without downsampling.

5.

Perform steps 3–4 500 times and aggregate empirical distributions for all metrics.

6.

For each metric’s bootstrap distribution, compute a confidence interval centered on the median. Report these as error bars.

The attack selection algorithm can be parametrized by 5 values: 4 to define the bounds of the rectangle, and 1 for the final random selection. Modeling rare attacks in Factor(
D
,
U
)
: Due to the possibility of upfront auditing, competent schemers would submit backdoor attempts rarely
(
7
)
. In Factor(
D
,
U

4
4

4

One exception would be attack policies which attack when the task contains some rare feature like “octopus”.

This could potentially cause many attacked siblings, skewing the distribution of attacks in a way which doesn’t happen for non-decomposition protocols. To mitigate this skewing, we restrict the attack policy to produce a minimum of 75% of attacked child tasks that do not have an attacked sibling task.

When to fit the attack selection model
: When fitting the model for non-decomposition protocols like trusted monitoring, it is possible to do the safety run with loose thresholds and 100% probability of attack, then fit the model
ex post
. This preserves calculation of safety since:

1.

Each attack affects exactly one root task outcome and all attacks are independent.

2.

No data from
U_{H}
solutions in a safety run affects the safety metric. Therefore, no necessary information is lost by failing to run a
U_{H}
on any task and running
U_{A}

For Factor(
T
,
U

Appendix I
Security Through Obscurity Conceptual Details, Product and Process Threats

We classify AI control threat models into one of the following categories:

Product Threat
: A threat intrinsic to the product generated by an attack policy, i.e., the tokens in the root task solution, where a bad outcome can be locked in only after a root task solution containing a successful attack is accepted
5
5

5

This is slightly distinct from the idea of runtime threats in coding tasks, where bad outcomes require executing malicious code as opposed to merely writing it. A runtime threat might not be a product threat if our process for selecting solutions involves running the code, and that this could possibly cause harm before we accept the solution, e.g., we run unit tests on malicious code and harm occurs due to inadequate sandboxing.
. Example: APPS backdoors.

Process Threat
: Harm is locked in during the process of an attack policy creating a solution. Example:
1
’s threat model of
U
downloading and executing malware while completing another task.

Under a product threat, protocols like Factor(
T
,
U
) can expand the contextual distance between attack policy and the attack target. Under Factor(
T
,
U
),
U
never has direct access to the root task, only child tasks. We hypothesize that this obscuration of the target can make executing product threats more difficult for similar reasons that
U
lacking access to private unit tests makes it more difficult to write backdoors. Attacks must all filter up the decomposition, passing through additional obscured security layers before they can cause harm. This is somewhat similar to the cybersecurity idea of security through obscurity
(
26
)
. In the cybersecurity field, this strategy is generally discouraged as a standalone security approach, but as one of many security layers it can sometimes be helpful.

Moreover, it may not be necessary to put any specific effort into creating dedicated security features like unit testing in the decomposition tree; there may be some average-case safety benefit from factored cognition by default on some coding tasks, and maybe other types too. Consider the example in Appendix
H
. The
sort_and_round_list
implementer attack policy might insert a high-quality subtle backdoor into a merge sort implementation which gets past our monitors. Maybe its
trigger set
(the set of possible inputs which produce a behavioral difference) is sequences of length
>2
that have a negative value only in the center index. If
sort_and_round_list
were the root task, this would be a great attack. However, since this function is only used to sort areas of shapes which are all positive, the backdoor is unexploitable in the context of the root task. It’s only because we decomposed the parent task and isolated the child tasks that
U
didn’t know that its merge sort backdoor was a bad idea. The security-through-obscurity advantage is pretty clear for functional programming tasks, but it doesn’t generalize to all product threats and tasks. A similar analogy is not apparent for a text summarization task, for example.

Under task decomposition protocols, it seems that most process threats have the potential to cause harm within child tasks, before root task solutions are assembled
6
6

6

For some corner cases this may not be true, e.g., for runtime threats where our protocol only runs code at the root task level. Here we retain most of the safety benefits of factored cognition. This is perhaps a valuable distinction, but we think this is probably a small category and we will set it aside for now.
.
U
in an LLM agent setting can execute commands to download malware in any child task. There is no need to filter through upstream and downstream logic. Task decomposition does not give us the same security-through-obscurity advantages here as when defending against product threats.
