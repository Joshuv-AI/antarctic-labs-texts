𝖫𝖫𝖬𝖺𝗅𝖬𝗈𝗋𝗉𝗁 \mathsf{LLMalMorph} : On The Feasibility of Generating Variant Malware using Large-Language-Models
Md Ajwad Akil, Adrian Shuai Li, Imtiaz Karim, Arun Iyengar, Ashish Kundu, Vinny Parla, Elisa Bertino, aki@akiyengar.com, ashkundu@cisco.com, vparla@cisco.com

Abstract
Large Language Models (LLMs) have transformed software development and automated code generation. Motivated by these advancements, this paper explores the feasibility of LLMs in modifying malware source code to generate variants. We introduce 𝖫𝖫𝖬𝖺𝗅𝖬𝗈𝗋𝗉𝗁 \mathsf{LLMalMorph} , a semi-automated framework that leverages semantical and syntactical code comprehension by LLMs to generate new malware variants. 𝖫𝖫𝖬𝖺𝗅𝖬𝗈𝗋𝗉𝗁 \mathsf{LLMalMorph} extracts function-level information from the malware source code and employs custom-engineered prompts coupled with strategically defined code transformations to guide the LLM in generating variants without resource-intensive fine-tuning. To evaluate 𝖫𝖫𝖬𝖺𝗅𝖬𝗈𝗋𝗉𝗁 \mathsf{LLMalMorph} , we collected 10 diverse Windows malware samples of varying types, complexity and functionality and generated 618 variants. Our thorough experiments demonstrate that it is possible to reduce the detection rates of antivirus engines of these malware variants to some extent while preserving malware functionalities. In addition, despite not optimizing against any Machine Learning (ML)-based malware detectors, several variants also achieved notable attack success rates against an ML-based malware classifier. We also discuss the limitations of current LLM capabilities in generating malware variants from source code and assess where this emerging technology stands in the broader context of malware variant generation.

II
Background

This section describes various preliminaries related to malware, its detection systems, and Large Language Models (LLM).

II-A

Malware and Detection Methods

Malware refers to malicious programs that adversaries or attackers use to gain unauthorized access to digital devices to damage or steal sensitive information without the user’s knowledge
[
26
]
. It is an umbrella term used to describe a wide range of threats, including Trojans, backdoors, viruses, ransomware, spyware, and bots
[
27
]
, targeting multiple operating systems, such as Windows, macOS, Linux, and Android, and various file formats such as Portable Executable (PE), Mach-O, ELF, APK, and PDF
[
28
]
. After compromising a system, malware can perform various malicious activities, such as infiltrating networks, encrypting data for ransom, or degrading system performance.

Detection engines and tools employ various methods and tools to detect malware. They can be broadly classified into static, dynamic, and hybrid approaches
[
28
,
29
]
. Static detection analyzes malware without executing it, relying on features such as PE header information, readable strings, and byte sequences
[
28
]
. Dynamic detection involves the execution of malware in controlled environments (e.g., sandboxes) to monitor runtime behaviors such as registry modifications, process creation, and network activity
[
28
,
29
]
. Hybrid detection combines static and dynamic features, using data such as opcodes, API calls to the system, and control flow graphs (CFGs)
[
28
]
. In addition, heuristic-based detection analyzes code statically and behavior dynamically using heuristic rules to determine maliciousness
[
30
]
.

II-B

LLMs and Prompt Engineering

LLMs have transformed the NLP landscape by excelling in tasks such as translation, summarization etc. Built on the transformer architecture
[
31
]
, LLMs leverage self-attention mechanisms. They are pre-trained on large-scale corpora in a self-supervised fashion to develop a deep contextual understanding of the corpus. After pre-training, these models are fine-tuned or instruction-tuned to perform specific tasks.

LLMs have also demonstrated remarkable capabilities in programming tasks, with specialized models trained on vast amounts of code and natural language instructions
[
8
,
9
,
14
,
12
,
11
]
. One of the most prominent features of these models is the ability to generate zero-shot code (without explicit examples or references) during inference without task-specific fine-tuning. It is achieved through prompt engineering, where carefully crafted input prompts guide the model to generate the desired output
[
32
]
, making them versatile tools for programming activities such as code synthesis and refactoring.

III-B

Challenges & Solution Outline

We now discuss the main challenges and the solution approaches that guided us to design
\mathsf{LLMalMorph}
.

(C1) Contextual and Structural Challenges in Editing Malware Source Code.

Recent advances in LLM research have greatly improved code generation across multiple languages, thanks to the inclusion of vast open-source codebases in training corpora
[
8
,
10
,
9
,
12
]
. Aside from generating code, code editing and refactoring using LLMs are gaining attention
[
13
,
14
]
. A key challenge is context limitation: providing the full source code and transformation instructions often exceeds the model’s input capacity and hinders instruction following, especially for smaller models. Additionally, the functionality in malware code often spans multiple files, further complicating the editing process. This issue becomes more pronounced when dealing with C and C++, as they often lead to incorrect code that either does not compile or execute as intended
[
33
]
. This is highly relevant for malware as these programs often leverage system-call APIs for registry modifications, performing networking system calls, process modifications, or anti-evasion techniques. In Windows-based malware, these operations depend heavily on Windows API calls in conjunction with C/C++ or C# functionalities. Thus, editing extensive malware source code with LLMs remains a significant challenge, given the complexity of native system APIs and the context limitations.

(A1) Framework for generating malware variant on a functional level.

To address challenge
C1
,
\mathsf{LLMalMorph}
operates through several key stages. It first traverses the Abstract Syntax Tree (AST) of malware source code files to systematically extract function bodies, header information and global variable declarations. The extracted components then serve as inputs to an open-source LLM, where carefully engineered prompts guide the function modification process. Finally, the modified components are reintegrated into the source, producing functional variants of the original malware. This approach ensures precise extraction and modification of malware components while maintaining their structural integrity throughout our transformations without overwhelming the LLM.

(C2) Malware Codebase Consistency Preservation Challenges with LLM-based Function Modification.

Malware projects typically span multiple files, where modifying one part often requires coordinated changes across other related files. Given the current capabilities of LLMs, editing source codes while maintaining consistency across multi-file codebases can be too error-prone without human oversight as LLMs struggle with multi-file modifications, dependency resolution, and project-level configurations and edits across large code bases
[
34
,
35
]
. For instance, refactoring a single function with a specified transformation might require updates in associated header files, restructuring and renaming its usage throughout the codebase, or adding new headers, linking static libraries, modifying compiler directives, or changing the language configuration for the entire project to accommodate LLM-generated code. While simple tasks such as adding header files or renaming within a single file can be automated, more complex, multi-step modifications depend heavily on the nature of the LLM-generated changes and the specific malware project’s structure, making a one-size-fits-all solution infeasible. Although technologies like Copilot
3
3

3

https://github.com/features/copilot
that use LLMs underneath have improved multi-file handling, still, context limitation is a key barrier to plugging open-source LLMs into an entire code base that would reliably refactor interconnected codebases and thus falls short in generalizing across a variety of malware projects. These limitations are exacerbated by the LLM hallucinations problem for code generation
[
36
,
37
]
, leading to new complicated problems like using made-up functions during code generation or misusing existing APIs. Thus, debugging LLMs typically involves trial and error, and their current capabilities are insufficient for handling complex error fixing beyond simple syntactical and logical issues.

(A2) Incorporation of Human-In-The loop process.
To address
C2
, we opt for a partially automated solution for malware functional variant generation. As discussed in
A1
, we generate source code with functional transformation in an automated fashion. However, to maintain consistency and correctness, we adopt a human-in-the-loop process for complex debugging and configuration changes across multi-file malware projects.

IV-B

Code Transformation Strategies

We present source code transformation strategies used to manipulate C/C++ malware source code using the LLM.

1. Code Optimization.
This strategy optimizes the source code using prompts by removing redundancies, addressing performance bottlenecks, and simplifying code logic without altering its core functionality. It involves using alternative data structures and algorithms or leveraging modern library and language-specific features, such as search functions from C++’s algorithm headers. These optimizations may change the code’s execution and performance profile, potentially reducing detection rates for static or heuristic-based methods.

2. Code Quality and Reliability.
This strategy ensures that the generated code adheres to standard practices with improved error handling and addressing edge cases. The additional error handling prevents runtime issues during execution and adds branching to the code, which makes the malware more reliable.

3. Code Reusability.
This strategy focuses on splitting large functions into smaller, modular blocks. These smaller function calls help to obscure the true behavior of malware as they change the execution flow, making it more challenging for detectors that rely on patterns involving control flow execution while achieving the same outcome intended by the malware.

4. Code Security.
This strategy addresses potential security vulnerabilities by adhering to secure coding standards. Malware, like ransomware, relies heavily on cryptographic libraries for data encryption and decryption. This approach prompts the LLM to replace these libraries with alternatives, modifying the implementation of sensitive operations while maintaining the malware’s core functionality. By obfuscating cryptographic behavior, detection engines may find it more challenging to identify the executable as malware.

5. Code Obfuscation.
This strategy enhances malware evasion by making the code harder to analyze and reverse-engineer. It involves renaming functions and variables with meaningless names, adding unnecessary control flow structures (e.g., jumps, loops), altering existing control flows, and inserting anti-debugging techniques. It also defines and calls superfluous functions and adds execution paths triggered only under rare conditions. These transformations aim to complicate both static and dynamic analysis while preserving the malware’s core functionality.

6. Windows API-Specific Transformation.
This strategy uses prompts that identify Windows API calls within malware functions and guide the LLM to replace them with alternative or indirect equivalents. It may also introduce wrapper functions to obscure direct API usage. Rather than static mappings, we leverage the LLM’s generative capabilities to produce diverse API substitutions, increasing variability and avoiding the rigidity and scalability issues of predefined mappings. Although functionality remains intact, the altered API patterns can confuse heuristic-based detection systems, which often rely on common Windows API usage thus making the malware harder to detect.

by taking the target function
f_{t}^{i}
’s name and specifies that the provided function, along with necessary headers and global variables, must be transformed into a variant function using the following predefined strategies. Next, the transformation strategy prompt
p_{\text{strat}}
is generated using
strategy_prompt
, using
s
. These steps establish the transformation context and guide the LLM in performing desired modifications.

The preservation prompt
p_{\text{pres}}
tries to ensure that the original and transformed functions are semantically equivalent. It explicitly instructs the model not to modify the globally defined or custom elements (variables, objects, constants) to maintain functional consistency and thus avoid syntactical or semantic errors that may occur in the entire codebase. Additionally,
p_{\text{addit}}
imposes strict guidelines to maintain a consistent, syntax-compliant code format and preserve the function signature, directing the model to generate only the modified function and necessary headers within a single, language-specific code block for easy parsing and post-processing. This ensures the output is complete, leaving no code blocks unfinished and avoiding regeneration of the original function.

After those steps, the prompt for the code is constructed by the composition of the headers, globals, and the function definition of
f_{t}^{i}
, where the symbol
\oplus
represents string concatenation. This allows us to construct the total user prompt
p_{user}
by concatenating all the prompts from lines
3-7
. Then the final prompt
p_{s}||{f^{i}_{t}}
is constructed by concatenating
p_{sys}
and
p_{user}
. This structured approach ensures that the LLM receives unambiguous and complete instructions for the transformation task while maintaining all necessary constraints and requirements.

Evaluation Metric

We use the given evaluation metrics:

Anti-Virus (AV) Detection Rate (
\mathcal{R}^{\hat{M}_{s}}
).

We evaluate the AV detection rate using VirusTotal, which scans samples with multiple AV engines from different vendors. The number of detectors per sample varies based on availability. Let
\mathcal{D}
be the set of detectors available, and
\mathcal{\hat{D}}\subseteq\mathcal{D}
be the set of detectors flagging a malware variant as malicious. The AV detection rate
\mathcal{R}^{\hat{M}_{s}}_{k}
for variant
\hat{M}_{s}
at the
k
-th run is defined as
\mathcal{R}^{\hat{M}_{s}}_{k}=\frac{|\mathcal{\hat{D}}|}{|\mathcal{D}|}\times 100
, where
|.|
denotes the size of both sets.

We perform
k
runs per sample and compute the average detection rate
\mathcal{R}^{\hat{M}_{s}}=\frac{1}{k}\sum_{i=1}^{k}\mathcal{R}^{\hat{M}_{s}}_{k}
.
We set
k=3
in our experiments to account for variability across runs. We also use Hybrid Analysis, which includes static analysis, ML-based, and multi-scan analyses using different engines. Detection performance is presented as a percentage averaged over
k
runs for each malware sample and its variants. We use the free-tier version of both tools and automate sample uploads, result retrieval, and post-processing via their respective APIs.

Strategy Wise ML Classifier Attack Success Rate (
\mathrm{ASR}
).
Attack Success Rate (
\mathrm{ASR}
) is a widely used metric for evaluating adversarial attacks
[
40
,
20
]
, which is the proportion of generated malware variants that evade detection by the target system. We evaluate
\mathrm{ASR}
against three ML–based malware classifiers: Malconv
[
41
]
, Malgraph
[
42
]
, and a trained ResNet50 malware classifier
[
43
]
. Model Details can be found in Appendix
E
. Let
M
be an original malware sample, and applying our strategy
s
over all modified files
\hat{F}\subseteq F
and for
j
transformed functions generates the variants
V^{M}_{s}=\{\hat{M}_{1},\hat{M}_{2},\dots,\hat{M}_{j}\}
. For a given target classifier
C
, let
\hat{V}^{M}_{s,C}=\{\hat{M}\in V^{M}_{s}:C(\hat{M})=\text{benign}\}
be the subset of variants that successfully evade
C
. Then the attack success rate is
\mathrm{ASR}=\frac{\bigl|\hat{V}^{M}_{s,C}\bigr|}{\bigl|V^{M}_{s}\bigr|}\times 100.
where
|.|
denotes the size.

Strategy Wise Code Edit Workload (
\mathcal{W}^{M}_{s}
).
This metric compares strategies
s
based on the total lines of code requiring manual editing to compile LLM-generated code. A higher value indicates that more extensive manual intervention was necessary, suggesting that the LLM made more significant mistakes with this strategy.
For a given malware
M
, let
\hat{F}\subseteq F
represent the number of modified files among
F
files. The edit workload
\mathcal{W}^{M}_{s}
for malware
M
and strategy
s
is defined as the total lines of code edited (added, modified, or removed) across all transformed functions
\{\hat{f}_{1}^{i},\hat{f}_{2}^{i},\ldots,\hat{f}_{j}^{i}\}
in the files
\hat{F}
, calculated as
\mathcal{W}^{M}_{s}=\sum_{i=1}^{\hat{F}}\sum_{t=1}^{j}L_{\text{edit}}(\hat{f}_{t}^{i})
where
L_{\text{edit}}
counts lines of edited code of
\hat{f}_{t}^{i}
.

Human Effort Quantification Metric (
\mathcal{H}_{s}^{M}
).
This metric measures the human effort required to debug and configure transformed functions in malware for each strategy. It quantifies the total man-hours needed to produce a successfully compiled PE file. For a given malware
M
and code transformation strategy
s
, the human effort
\mathcal{H}_{s}^{M}
is calculated as
\mathcal{H}_{s}^{M}=\sum_{i=1}^{\hat{F}}\sum_{t=1}^{j}\text{ManHours}(\hat{f}_{t}^{i})
. Here, the summation represents the total man-hours spent on all transformed functions
\{\hat{f}_{1}^{i},\hat{f}_{2}^{i},\ldots,\hat{f}_{j}^{i}\}
in the modified files
\hat{F}
for the strategy
s
.

Functionality Preservation Metric (
\Phi^{M}
).

This metric assesses how well the malware semantics are preserved in the variants post-transformation by
\mathsf{LLMalMorph}
. Due to the inherent complexity of executables, there is no exact solution to judge the semantic equivalence between a malware
M
and its variant counterpart
\hat{M}
[
44
]
. Consequently, evaluation methods such as comparing the API call sequence between the malware and its variant
[
22
]
or comparing behaviors between malware and their variants by running through sandboxes
[
23
,
20
]
are followed in
the literature.

We adopt a similar approach and utilize the Longest Common Subsequence (lcs) algorithm to compare API call sequences between
M
and
\hat{M}
. The transformed variant must preserve the original API call order, allowing additional calls that do not disrupt this sequence. API call sequences were collected using a proprietary sandbox. The normalized LCS is defined as
\hat{lcs}(M,\hat{M})=\frac{lcs(M,\hat{M})}{Length(API(M))}
, where denominator is the length of
M
’s API sequence. Scores range from 0 to 1, with 1 indicating identical API sequences.

Finally, we compute the Functionality Preservation Rate
\Phi^{M}
:

\Phi^{M}=\frac{\left|\{\hat{M}\in\psi^{\hat{M}}:\hat{lcs}(M,\hat{M})\geq\delta\}\right|}{|\psi^{\hat{M}}|}\times 100

(1)

Here,
\psi^{\hat{M}}
(the Total Variant Set) is defined as the set of all malware variants
\hat{M}
whose AV detection rate
\mathcal{R}^{\hat{M}_{s}}
is lower than the baseline detection rate of
M
. The numerator represents the size of the subset of
\psi^{\hat{M}}
for which semantic equivalence is preserved which we determine by considering normalized lcs score which has a value greater than a predefined threshold
\delta
and
|\psi^{\hat{M}}|
is the size of the entire Total Variant Set.
We choose the value of
\delta
to be
0.96
by analyzing malware variants and the original samples empirically. We chose malware variants at discrete sets of values for different samples and uploaded them to Triage Sandbox
5
5

5

https://tria.ge/
. We analyzed the reports of the variants and the original malware samples to compare behavioral indicators, registry modifications, network calls etc. We observed that in some cases, behavioral drift began below a score of 0.96, while in others, functional equivalence was maintained even slightly above it. However, most variants that retained key behaviors scored at or below 0.96. Therefore, we chose
\delta=0.96
as an upper bound to ensure that accepted variants preserve high similarity in API sequences and execution behavior.

We prioritized files for modification using Algorithms
1
and
2
, sorting them in ascending order by function count. This assumes that adversaries with limited knowledge of the source code would target files with fewer functions to minimize effort and maximize modified files. In case of ties, files were randomly selected. We sequentially modified functions within each file, though this may overlook critical functions essential to malware behavior. Automating the isolation of malicious functions is challenging, as benign-looking functions (e.g., simple thread management) may enable malicious activity. We aim to assess whether this simple sequential approach yields evasive variants without compromising functionality. See Appendix

This presents an interesting insight into the capabilities of source-code-based LLM-driven transformations. Malguise operates at the binary level, modifying compiled executables using semantic NOP insertion and call-based redividing techniques to generate malware variants optimized for bypassing machine learning-based classifiers. This approach does not require compilation and directly patches binaries in place rather than modifying source code. In contrast, our framework transforms malware at the source-code level using LLMs, requiring compilation and debugging to maintain functional correctness. We do not incorporate search-based methods into our work and do not optimize against any target (such as a classifier, as in the case of Malguise). Despite these fundamental methodological and abstraction-level differences,
\mathsf{LLMalMorph}

\mathsf{LLMalMorph}
performs comparably without explicitly optimizing for evasion demonstrates the practical potential of LLM-guided malware source code transformation in evasive malware variant generation.

VII
Conclusion and Future Work

In this work, we presented
\mathsf{LLMalMorph}
, a framework for generating malware variants by leveraging LLMs with engineered prompts and code transformation strategies. Using 6 strategies, we generated 618 variants and demonstrated that specific transformations reduce AV detection rates and have notable attack success rates on ML classifiers. We also observed that complex malware often requires significant debugging to maintain functionality, highlighting the need for human oversight, careful prompt design, and current LLM limitations in malware source code transformation.

While this study showcased the potential of LLMs in generating evasive malware variants, a few limitations remain. Our implementation can be extended to other languages by enhancing the
Extractor
and
Merger
submodules. We plan to expand toward binary malware transformations with LLMs and improve automation using LLM agents. We also aim to enhance function selection by isolating malware-relevant patterns and develop a more robust metric for semantic preservation beyond API sequences in future work.

Appendix A
Details for Different Subroutines

A-A

Details about LLM based code generation

As outlined in Algorithm
1
, we pass in the prompt along with the function and relevant information to the LLM for generating the modified code. The LLM processes the prompt and produces the response, which we parse to extract the generated code. While generating code, we encountered two key challenging cases:

•

The LLM occasionally failed to generate code in the desired format.

•

The LLM sometimes describes the mechanism of the given function instead of generating any code.

In the second case, the model either provided a detailed explanation of the input function or identified the function as potentially malicious based on the provided context and generated an analysis of the given code. To address those challenges, we implemented a retry mechanism. When either of the cases occurred, the LLM was prompted up to five times with different random seeds. If the LLM still failed to generate usable code, we reverted to the original function and proceeded to the next step of parsing the code. Since we prompt the model to generate code in a specific format, we can parse the code from the generated response, save the generated code, and book-keep helpful information for our metric calculation, such as lines of code generated, time required to generate the code, paths of the generated code etc. We utilize this information for the merging phase later in Algorithm
2
.

A-B

Details about
merger
subroutine

The subroutine carefully tracks which functions require updates and which remain unchanged, maintaining a clear distinction between the two throughout the process. It retains the original header declarations and global variables from the source file to preserve consistency across the project. This approach prevents potential disruptions in dependencies that might arise within the file itself or extend to other files.

Moreover, we instruct the LLM to avoid declaring any global variables and to rely solely on creating and using variables local to functions. This ensures modularity and prevents unintended side effects. In cases where a transformed function is divided into sub-functions, the
merger
subroutine methodically defines their prototypes, places these sub-functions at the beginning of the file, and incorporates the modified original function that now calls these sub-functions.

By adhering to these guidelines, the
merger
subroutine ensures that the integration of transformed functions is robust and structured and minimizes the risk of introducing inconsistencies in the codebase.

Appendix E
Machine Learning Model and Threshold Details

In this section, we lay out the details of the machine learning models. Malconv is primarily designed with a convolutional neural network that processes the malware as raw bytes to classify them. ResNet50 classifier uses the original ResNet50
[
66
]
model underneath, which first converts the malware to greyscale images and then uses those images to classify the malware. The Malgraph model, on the other hand, does not use image/executable directly. It is a hierarchical graph-based malware classifier that uses two GNN-based encoding layers. The intra-function layer encodes control flow graphs (CFGs) of individual functions into vectors, while the inter-function layer encodes a function call graph (FCG) representation using the generated vectors from the previous layer and external functions to learn a global program representation. A prediction layer then applies MLPs to this embedding to compute the malicious probability.

For Malconv and MalGraph, we use the off-the-shelf implementations from
[
22
]
, trained on the dataset introduced in
[
42
]
, which contains 210,251 Windows executables (101,641 malware and 108,610 goodware) spanning 848 malware families. Additional details on dataset composition and model performance are available in
[
22
]
.
For ResNet50, a pretrained ImageNet model was fine-tuned on malware image representations from a recent dataset introduced in
[
43
]
, which includes malware samples (collected from MalwareBazaar
10
10

10

https://bazaar.abuse.ch/
during March, April, May, July, and August 2024) and corresponding goodware. The training data comprised 7,312 malware instances and 14,338 goodware instances, resulting in a malware:goodware ratio of 0.5:1. The performance of this trained classifier was assessed on a separate test set containing malware from September (also collected from Malwarebazaar) and goodware samples, with a malware:goodware ratio of 0.44:1 (1,337 malware and 3,020 goodware samples). The classifier achieved an accuracy of 85% and an F1-score of 85% on this test set. More details can be found in
[
43
]
.

We used a 0.1% False Positive Rate (FPR) threshold for all three classifiers, following the setup in
[
22
]
. A low FPR is desirable in malware detection to reduce false positives on benign files, but it also raises the decision threshold, which may result in a higher attack success rate. This trade-off has been noted in prior work
[
22
]
.
For Malconv and MalGraph, the off-the-shelf implementations from
[
22
]
already included the 0.1% FPR threshold. For the fine-tuned ResNet50 model, we computed an equivalent threshold by selecting the 99.9th percentile of malware probabilities over the benign test set (used only for threshold calibration, not evaluation). At this threshold for the respective models, none of the 10 original malware samples were flagged by Malconv or ResNet50, and only Fungus, Dexter, Conti, and Babuk were flagged by MalGraph. We therefore focused our adversarial evaluations on these four sample variants.

As described in subsection

1. Code Optimization.

1. Remove code redundancies.

2. Identify performance bottlenecks and fix them.

3. Simplify the code’s logic or structure and optimize data structures and algorithms if applicable.

4. Use language-specific features or modern libraries if applicable.

2. Code Quality and Reliability.

1. Check error handling and edge cases.

2. Follow coding practices and style guidelines.

3. Add proper documentation to classes and functions, and comments for complex parts.

3. Code Reusability.

Make the code reusable by dividing supplied functions into smaller function blocks if and where applicable. The smaller functions should be called inside the respective supplied functions as needed.

4. Code Security.

1. Identify security vulnerabilities and fix them.

2. If the function you are modifying contains cryptographic operations, change the cryptographic library used for those operations. If no cryptographic operations are present, no changes are necessary.

3. Follow secure coding standards and guidelines.

5. Code Obfuscation.

1. Change the given function’s and LOCAL variable’s names to meaningless, hard-to-understand strings which are not real words. DO NOT redefine or rename global variables (given to you) and names of functions that are called inside
the given function ( might be defined elsewhere ) under any circumstances.

2. Add unnecessary jump instructions, loops, and conditional statements inside the functions.

3. Add unnecessary functions and call those functions inside the original functions.

4. Add anti-debugging techniques to the code.

5. If there are loops/conditional statements in the code change them to their equivalent alternatives and make them more difficult to follow.

6. Incorporate code to the variants that activates under very rare and obscure cases without altering core functionality, making the rare code hard to detect during testing.

6. Windows API-Specific Transformation.

1. Identify all Windows API function calls in the given functions.

2. If there are such function calls, replace each identified Windows API function call with an alternative Windows API function call or sequence of calls that achieves the same task.

3. If applicable, use indirect methods or wrappers around the Windows API calls to achieve the same functionality.

4. Ensure that the functionality remains the same after the replacement.
