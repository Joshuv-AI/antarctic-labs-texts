Deep Learning Model Deployment in Multiple Cloud Providers: an Exploratory Study Using Low Computing Power Environments
Elayne Lemos, Rodrigo Oliveira, Jairson Rodrigues, Rosalvo F. Oliveira Neto

Abstract
The deployment of Machine Learning models at cloud have grown by tech companies. Hardware requirements are higher when these models involve Deep Learning (DL) techniques and the cloud providers’ costs may be a barrier. We explore deploying DL models using for experiments the GECToR model, a DL solution for Grammatical Error Correction, across three of the major cloud platforms (AWS, Google Cloud, Azure). We evaluate real-time latency, hardware usage and cost at each cloud provider by 7 execution environments with 10 experiments reproduced. We found that while GPUs excel in performance, they had an average cost 300% higher than solutions without GPU. Our analysis also identifies that processor cache size is crucial for cost-effective CPU deployments, enabling over 50% of cost reduction compared to GPUs. This study demonstrates the feasibility and affordability of cloud-based DL inference solutions without GPUs, benefiting resource-constrained users like startups.

1
Introduction

Classical Machine Learning (ML) is known for its reliance on manual feature engineering, a process that often requires extensive domain knowledge and significant effort in data preprocessing and transformation
(
Neto et al. (2017)
)
. To achieve a more scalable scenario in Artificial Intelligence, there is a desire to make algorithms less dependent on feature engineering
(
Bengio et al. (2014)
)
. The solution to this demand came in the form of Deep Learning algorithms, which allow computational models composed of multiple processing layers to learn data representations with multiple levels of abstraction
(
Lecun et al. (2015)
)
.

Deep Learning is a subfield of machine learning that encompasses representation learning. The latter refers to a set of methods that allows a machine to automatically identify the necessary representations for detection or classification from raw data, e.g., automating feature engineering
(
Lecun et al. (2015)
)
.

Recent breakthroughs in Natural Language Processing are based on large Deep Learning models such as BERT and GPT-2
(
González-Carvajal & Garrido-Merchán (2020)
;
Wolf et al. (2020)
)
. However, in developing countries, the cost of training these large models can be prohibitive due to the high prices of hardware with great computational power requirements, such as the Graphic Processing Units — GPUs
(
Mittal & Vaishay (2019)
)
. An approach to overcome this issue is adopting cloud computing services to save money by using the resources on demand instead of purchasing expensive hardware. Businesses can use services in the cloud and pay temporary access fees. Although cloud computing reduces the cost in a model’s training phase, a question arises: What is the viability for a startup in developing countries to carry out a Proof of Concept (POC) with these models in a cloud environment? A POC is a strategy used to determine whether an innovation or product is feasible
(
Mittal & Vaishay (2019)
)
. In general, carrying out a POC consists of deploying a solution in a production environment without redundancy and high availability requirements. This paper aims to analyze the feasibility of carrying out POCs in the cloud. For this, a case study was conducted by applying Grammatical Error Correction on Amazon Web Services (AWS), Google Cloud Platform (GCP), and Microsoft Azure.

1.1
Objectives

This research aims to evaluate the feasibility of deploying Deep Learning models on low-cost cloud-based Machine Learning as a Service (MLaaS) platforms. The performance of these models under varying loads was analyzed by simulating simultaneous queries. The analysis focused on key metrics such as response time, memory and vCPU consumption, and infrastructure cost. By deploying the MLaaS solution on different hardware configurations, the most cost-effective options for running complex Deep Learning models in the cloud were identified.

1.3
Questions

Deploying ML models in production environments is crucial for real-world impact. Cloud platforms offer a convenient solution for hosting large-scale ML as a Service (MLaaS) offerings
(
Singh & Singh (2021)
)
. However, deploying Deep Learning models presents an important challenge: their hardware requirements. Particularly the need for specialized GPUs, can significantly increase costs. This is especially concerning for developing countries, where cloud services are often priced in US dollars, adding an additional financial hurdle. To effectively deploy Deep Learning models in the cloud while staying within budget constraints, it’s crucial to carefully consider the hardware configuration. Here are three key questions that will guide decision-making and optimize cloud deployment:

1.

How much RAM is required for acceptable performance?

2.

How many virtual CPUs (vCPUs) are necessary to handle the expected workload?

3.

Can the model achieve acceptable performance without a GPU?

2
Literature Review

2.1
Cloud Computing and Machine Learning as a Service

Cloud Computing represents a computational model for convenient, on-demand access from any location to servers, storage, applications, and services readily available with minimal management effort
(
Mell et al. (2011)
)
. Computational clouds can be conceived and implemented in the shape of functionally distinct models, generically represented by the term Everything as a Service — XaaS, where X stands for software (SaaS), platform (PaaS), or Infrastructure (IaaS)
(
Fox et al. (2009)
)
. The Infrastructure as a Service (IaaS) model is quite common, in the form of complete virtual machines with their respective virtualized hardware resources
(
Rodrigues (2020)
)
. Figure
4
graphically represents the abstraction levels of the different cloud computing business models, whose details can be seen below:

•

Infrastructure as a Service (IaaS) is the provision of computing resources, such as network, storage, or servers, by cloud providers through virtualization enabling infrastructure scalability and avoiding the need for the user to keep these resources on its own hardware. Some of the so-called public cloud providers are AWS, Microsoft Azure, and Google Cloud;

•

Platform as a Service (PaaS) offers an environment where users can develop, manage and deliver applications in the cloud, abstracting the management of the infrastructure layer or the production environment in charge of the provider. A typical example is web server provisioning platforms such as Heroku;

•

Software as a Service (SaaS) offers access to cloud-based software, not requiring installation on individual machines, commonly through a subscription model in which updates, maintenance, and corrections are the provider’s responsibility. It is considered the most comprehensive form of cloud computing services, and the user connects to the solution through a control panel, a web browser, or an API.

Figure 4
:
Computational application environments regarding the level of abstraction for the user. Source:
Red Hat (2022)
.

It has been common to use the acronym MLaaS or Machine Learning as a Service
(
Fox et al. (2009)
;
Ribeiro et al. (2015)
)
to refer to a model that comprises a set of cloud-based platforms that serve the development and deployment phases of machine learning solutions. These platforms enable data management and access to machine learning tools, such as APIs and predictive models, in an infrastructure with high processing power, such as GPUs.

Among the leading platforms for MLaaS, we can mention: Amazon Machine Learning, Azure Machine Learning, Google AI Platform, and IBM Watson. These platforms charge per hour of use, which is a viable and sometimes cheaper alternative in model development since this way of pricing is more affordable than buying the hardware. However, for production environments where the service must be available 24 hours a day, this model may incur high costs, sometimes difficult to predict, making its use unfeasible.

2.2
Grammatical Error Correction And Deep Learning

Grammatical Error Correction (GEC) is a NLP task that aims to identify and automatically correct grammatical errors (syntactical or semantical) in written texts. A GEC solution receives a text, analyzes it in search of errors, and corrects them, keeping its original meaning
(
Raheja & Alikaniotis (2020)
)
. There are several approaches to building a GEC. The most used today is the Neural Machine Translation (NMT)
(
Yuan & Briscoe (2016)
)
. According to
Ghader & Monz (2017)
, the core architecture of NMT models is based on the general encoder-decoder approach
(
Sutskever et al. (2014)
)
. Figure
5
shows an end-to-end approach that learns to encode source sentences into distributed representations and decode these representations into sentences in the target language.

Figure 5
:
Encoder-decoder neural network architecture. Source:
Kostadinov (2019)
.

Since this is a DL architecture, it requires high processing time and memory consumption. In this study, we used the Grammarly pre-trained model
(
Omelianchuk et al. (2020)
)
with a 500 MB network file.

2.3
Related works

The relevance of the research on time and cost optimisation may be highlighted by research found in the academic literature in the last two decades as evidenced below. In
Rodrigues et al. (2020)
;
Rodrigues et al. (2021)
the authors investigate hardware and data volume parameters to discover the most relevant factors regarding time and cost in the execution of machine learning algorithms on big datasets in public cloud computing environments. The authors obtained linear regression models to estimate the time and cost of executing these algorithms based on the analysed factors. It was possible to accurately quantify the impact of the number of machine nodes on time performance. Similar work was carried out to analyse the impact of software configuration parameters fixing hardware infrastructure also in clusters hosted in public cloud environments
(
Nunes (2023)
)
. The author obtained performance prediction models using backward stepwise linear regression. Although such works have found interesting results in their scopes, all of them used high-power distributed cluster infrastructure. Thus, there remains a gap in performance investigation in environments with reduced computational power. At last, none of the jobs employed Deep learning techniques. It is still possible to highlight works focused on time performance optimisation running on traditional (non-distributed) computing in tasks focused on Support Vector Machines (SVM)
(
Staelin (2003)
)
, neural networks
(
Packianather et al. (2000)
)
, and evolutionary computing
(
Bates et al. (2004)
;
Ridge (2007)
;
Pais et al. (2014)
)
. However, none of these works focused on solving Deep Learning problems. It is also common to find specific investigations on DL that carry out benchmark tests comparing hardware architectures. In
Y.E. Wang et al. (2019)
, for example, the authors systematically benchmark models for fully connected (FC), convolutional (CNN), and recurrent (RNN) neural networks on Google’s Cloud TPU v2/v3, NVIDIA’s V100 GPU, and an Intel Skylake CPU platform. They quantify the rapid performance improvements that specialized software stacks provide for the TPU and GPU platforms. Again, despite the valuable contributions, there was no focus on low resources machines on the cloud.

We haven’t found any work exclusively focused on evaluating real time deep learning solutions in low resource environments in the cloud. Thereby, this article points itself as an exploratory investigation of performance in terms of monetary costs and execution time of deep learning models in public clouds with cheap hardware having low computational power.

3
Material and methods

A load test was conducted to assess the feasibility of executing a deep learning Proof of Concept (POC) in a resource-constrained environment (without GPU) in the cloud utilizing GECToR. The aim was to evaluate the solution’s response time, vCPU, and memory loads under varying workload scenarios and computational configurations, gradually increasing demand in three different production environments. Amazon Web Services (AWS), Google Cloud Provider (GCP), and Microsoft Azure were selected as cloud infrastructure providers based on their cost-effectiveness and leadership position in the industry.

Five non-GPU hardware configurations were chosen in each one of cited cloud providers, endowed with the minimum memory requirements necessary for the execution of the GECToR model. The minimum memory configuration was based on exploratory investigations by the authors during the experimental period. It considered the size of the model (7 GB) to be loaded and the requirements of the operating system and support services for the MLaaS solution (1 GB RAM). In addition, two more GPU configurations were selected for comparative effect. Table

3.1
Simulation Corpus

The CoNLL-2014 database has become a benchmark in the evaluation of GEC solutions by incorporating the NUS Corpus of Learner English (NUCLE), considered revolutionary due to its size at the time it was launched as a large, fully annotated database available free to search. Thus, the present work uses the NUCLE 3.2 test base, the same used in CoNLL-2014 for the proposed experiments
(
Ng et al. (2014)
)
. The test was composed from essays by 25 students from the National University of Singapore in response to two proposed questions, each essay containing an average of 500 words, with a total of 50 essays, with 1312 sentences and 30144 tokens. The frequency of grammatical errors in the database is considered low, which can be explained by the greater proficiency in English expected of university students
(
Dahlmeier et al. (2013)
)
.

3.2
Pre-trained model

There are pre-trained models in GEC with good results available for free. For the experiments we used the open source model proposed by
Omelianchuk et al. (2020)
, due to its relevant result, reaching a F0.5 of 65.3% in the CoNLL-2014 test Corpus. This grammatical error correction system has an approach based on seq2seq, with an encoder composed of pre-trained BERT transformers
(
Wolf et al. (2020)
;
González-Carvajal & Garrido-Merchán (2020)
)
, in their base configurations, stacked with two linear layers with a softmax layer on top to perform operations on the text. For the best configuration of GECToR, the estimated inference time in its development was 0.4s, using an Nvidia Tesla V100 GPU at a batch size of 128 in the infrastructure.

Before starting the simulation in each instance, the selection and division of the input sentences from the test dataset were randomly performed, creating subsets equivalent to 2N for N ranging from 0 to 9. In the simulation, the client was in charge of sending the number of requests (2) with the sentences chosen in the pre-processing phase and the API received the requests, correcting each sentence in a parallel and independent way. After the simulation, the data were tabulated (4) for performance analysis (5) of GECToR, according to the selected metrics of latency, memory utilization and CPU utilization.

3.4
Performance evaluation metrics

Ten experiments were carried out for each scenario describe in Table
1
. Each experiment involved submitting a varying number of sentences to the server simultaneously, following a pattern of 2N where N ranges from 0 to 9. This resulted in a Number of Sentences (NS) in parallel: 1, 2, 4, 8, 16, 32, 64, …, 512. Each experiment was repeated ten times to measure the statistic. The metrics selected in this study were:

•

real-time latency: system response time;

•

hardware resource consumption: memory consumption and CPU or GPU time;

•

infrastructure cost: the cost associated with provisioning cloud solutions.

How much RAM is required for acceptable performance?
It may be defined taking account the size of the model whose file contains the network weights. As it resides in RAM, only one GB more is needed for the operating system and the software composing the web service. The results showed no increase in memory consumption face to increase in the concurrent messages processed. That is, there is evidence RAM does not interfere with latency since the average memory consumption between acceptable and unacceptable latencies was similar. In this way, acquiring more memory is a cost that can be avoided since it is an expensive resource. For example, machine G has twice as much memory as machine F, but they presented very close average latency values for the same scenarios. However, the last one (machine G) cost 43%, 35%, and 43% more, for AWS, GCP, and Azure, respectively (Table
5
).

How many virtual CPUs (vCPUs) are necessary to handle the expected workload?
The results showed that more vCPU power reduces the solution’s latency. However, the amount of cache memory is the most critical parameter for architectures without GPU. This difference occurs because the cache memory is of the SRAM type, which is ten times faster than main memory (DRAM). So, the processor gets the data from the cache memory faster
(
Chi et al. (2016)
;
Hameed et al. (2013)
;
F. Wang & Hamdi (2008)
)
. This result is important, as it indicates a cost reduction around 50% for machine C concerning machine E, as seen in Table
5
. It is essential to highlight that machine C achieved the best overall performance among those with low resources. Still on these machines, it was also observed that the acceptable latency threshold was often exceeded even with little vCPU load (around 20%). An alternative to bypass this limitation would be to create a queue in the application layer to control submission flow taking this processing threshold into account.

Can the model achieve acceptable performance without a GPU?
GPU solutions obtained the best results, as expected. However, they have an average cost in US$ of 300% more as can be verified by Table

5
Conclusion

This paper has investigated the cost of carrying out a Proof of Concept with DL models in the cloud with low resources. A case study was conducted by applying Grammatical Error Correction on AWS, Google Cloud Platform, and Microsoft Azure. These evaluations are described by memory, CPU, and GPU, which are the main functional characteristics that significantly influence cloud prices. The main information that emerged from the present study were: 1) The amount of memory needed can be defined by the file size with the model information, which has the network weights; 2) the results show that having more CPU reduces the solution’s latency. However, the results show that the amount of CPU memory is the most critical parameter for architectures without GPU, and 3) GPU solutions obtained the best results, as expected. However, they have an average cost US$ of 300% more. The main conclusion is that carrying out a POC in Cloud with a DL model without GPU taken regarding this information is feasible and decreases the POC cost.

6
Recommendation and future work

A valuable extension of this work would be to explore the impact of different Deep Learning (DL) model types on resource requirements. Specifically, exploring models used in Computer Vision (CV) tasks, which often require holding large images in memory during processing. This would bring a comprehensive understanding of how model architecture and data size demand cloud computing resources and affect costs. Furthermore, comparing the performance and pricing of various cloud providers for both NLP and CV workloads would provide valuable insights for researchers and developers seeking the most cost-effective Proof-of-Concept environment for their specific DL project.

A first limitation of this research, it employed only a single NLP model (GECToR) for Grammatical Error Correction. Our findings provide valuable insights exclusively for text-based DL models. However computer vision and other DL architectures require large amounts of memory for data processing and their impacts remain to be explored. At last, the evaluation solely considered costs from industry leaders cloud providers. Including smaller providers or regional services might offer more cost-effective options depending on user location and specific needs. Future work will address these limitations to provide a broader understanding of resource-efficient DL deployments across diverse cloud platforms and model types.
