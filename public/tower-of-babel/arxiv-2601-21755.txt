Migrating Esope to Fortran 2008 using model transformations
Younoussa Sow, Nicolas Anquetil, Léandre Brault, Stéphane Ducasse

Abstract
. Legacy programming languages such as FORTRAN 77 still play a vital role in many industrial applications. Maintaining and modernizing these languages is challenging, especially when migrating to newer standards such as Fortran 2008. This is exacerbated in the presence of legacy proprietary extensions on such legacy languages, because their semantics are often based on old context (limits of legacy language, domain logic,…). This paper presents an approach for automatically migrating FORTRAN 77 with a proprietary extension, named Esope, to Fortran 2008. We introduce a tool that converts Esope source code to Fortran 2008. While supporting readability of the generated code, we want to maintain the level of abstraction provided by Esope. Our method uses model-driven engineering techniques, with transformations to generate a target model from which we export easy-to-read Fortran 2008 source code. We discuss the advantages, limitations, and maintainability considerations of our approach and provide insights into its scalability and adaptability to evolving requirements.

2.2.
Model Transformation

Model transformation is a cornerstone of model-driven engineering (MDE) or model-driven development (MDD)
(
20
)
,
enabling the automation of tasks such as code generation, code refactoring, and code migration.
Model transformations are categorized into two primary paradigms
(
19
)
:

Model-to-Model
(M2M): These transformations operate between models at similar levels of abstraction.
They can adhere to the same metamodel (
e.g.,
migrating from Java 8 to Java 17) or adhere to different metamodels (
e.g.,
migrating from Fortran to Java);

Model-to-Text
(M2T): These generate textual artifacts (
e.g.,
source code, documentation) from models,
bridging abstract representations with concrete implementations.

There are three main
Model-to-Model
transformation approaches:

•

Rule-based approaches
: Tools such as ATL
(
18
)
and QVT
(
36
)
map models declaratively and offer high traceability.
However, scalability can be a challenge for complex models.
If it is easy to define a query finding a specific entity in a small model, it becomes harder to do it for a large one;

•

Operational approaches
: Imperative tools such as ATL, QVTo, and Xtend
(
17
)
provide fine-grained control,
which is ideal for handling complex mappings, but requires significant manual effort. One needs to define each operation to apply to each node of the AST;

•

Graph-based approaches
: Tools such as Henshin
(
3
)
use graph rewriting rules for intuitive and
visual transformation, but suffer from performance issues with large models.

For
Model-to-Text
transformation, there are two main approaches:

•

Template-based approaches
: Tools such as Acceleo
(
25
)
use predefined templates to generate text,
ensuring readability but limiting flexibility for complex structures;

•

Visitor-based approaches
: Tools such as Xtend
(
6
)
traverse model structures programmatically,
allowing fine-tuned output generation but increasing development overhead.

This paper innovates by hybridising
Model-to-Text
(visitor and string template) for a
Model-to-Model
transformation of Esope ASTs.

3.1.
A brief overview of Esope

FORTRAN 77 programmers are confronted with two primary challenges: (i) the language does not provide a record type construction (like a
struct

In order to address these issues, Esope
(
5

The goal was to create a programming language allowing (1) complex data structures, (2) automatic memory management, and (3) memory swap management.

This is how an entity called

A segment is a group of Fortran variables, called

The field definitions have the same syntax as regular variable definitions in Fortran.
An instance of a segment is referenced by a variable called a
pointer

Knowing the pointer is enough to access all the fields contained in the segment.

3.2.
Segment type

Each segment is instantiated inside some routine through a pointer, that supports passing segments as arguments to subprograms.
Note that in this paper, we call segment the structured type that contains fields as well as instances of this type that are pointed to by pointer variables.

Segments can contain other segments to create structures such as graphs.
Segments may also contain arrays.
In FORTRAN 77, the size of arrays must be known at compile time.
Esope introduced the ability to delay the sizing of arrays at run time with the concept of
dimensioning variable
and
dimensioning expression
.
This feature is only available to arrays inside segments.
Listing
1
, line 5 shows an example of this where the
dimensioning variable
is
ubbcnt
and the
dimensioning expression
is simply the variable, but could be more complex (eg.
ubbcnt*1.1
to give 10% extra space in the array).

The
dimensioning variable
must be assigned before the segment is allocated (see Section
3.3
).

Note that as an added complexity, Fortran does not impose to declare a variable (implicit typing), so line 2 of Listing
1
is optional.

Dimensioning arrays at run time offers the possibility to resize arrays and hence their segment at run time.
This is equivalent to the
realloc
function in C language.
In C,
realloc
takes an address as an argument and the new size.
It returns a (possibly new) address for the re-dimensioned structure.
Esope offers a similar feature, where the new size is given by a new value of the
dimensioning variable
.
But, differently to C, the pointer to the structure is guaranteed to remain the same.
Esope achieves this by managing a “double indirection”:
The “pointer” handled by the developer is actually an index in a large array of all the “descriptors” of existing segment instances.
When re-dimensioning a segment, the content of its descriptor, such as the memory address of its fields might change, but the index of its descriptor, known to the developer as a “pointer”, never changes.

Finally, for each segment, Esope automatically declares a default pointer with the same name as the segment, as if the
POINTEUR user.user
statement had been given after the segment definition.
Along with that, fields of a segment can be manipulated without the default pointer prefix.
For example, using the default pointer, the statement on line 11 of Listing
1
, could become
uname = name
where
uname
means the field
uname
in the segment pointed to by the default pointer
user
.

3.3.
Segment manipulation

The following Esope statements operate on pointer variables:

Declaring a pointer to a segment:

(
pointeur p.user
)

Declares a variable
p
pointing to an instance of
user
.

Allocating segment:

(
segini p
).
It allocates memory for an instance of a segment and put its address in
p
.

Freeing segment:

(
segsup p
)
It frees the memory pointed to by
p
.
The pointer variable is set to zero (
0
) which is the null pointer.

Resizing segment:

(
segadj p
)
The array fields, with
dimensioning variable
, of an existing instance of a segment (pointed by
p
)
are resized (enlarged or shrinked). The instance (value of the pointer) itself remains unchanged.
This statement preserves existing data in the instance.

Printing segment:

(
segprt p
) This is used to display the name, dimensions and value of each field of a segment.
Each field is printed on a separate line;

Swapping-out segment:

(
segdes p
) This indicates that the segment can be moved to “swap” in the event of a memory shortage.
It also marks the pointed segment as “inactive”;

Swapping-in segment:

(
segact p
) If the segment was swapped out, this indicates that it needs to be moved back into the main memory.
It also marks the segment as “active”;

Duplicating a segment:

(
segini newp=oldp
)
This is an alternate use of the
segini
statement where a new instance of the segment is allocated, its address put in the pointer
newp
, and the content of the existing instance (
oldp
) is copied to the new one.
The old instance is kept.
The state of
oldu
is not modified.
Both
newu
and
oldu
must be instance of the same segment.
This is informally referred to as a “segcop” by the developers.

Copying a segment:

(
segact newp=oldp
)
This is an alternate use of the
segact
statement, where an instance of a segment from the source (
oldp
) is copied to the destination (
newp
).
The target segment must already exist (ie. having been allocated) before this statement.
The statement also performs a
segact
on
newp
beforehand (in case the segment was swapped out).
This is informally referred to as a “segmov” by the developers.

3.4.
Migration motivation

Esope is a transpiler that converts Esope code into pure FORTRAN 77 code.
It manages its own heap memory as a huge FORTRAN 77 array
4
4

4

The heap memory array is a C array created once using
malloc
.
and converts the Esope commands as offsets in this memory zone.

A major issue with Esope is that the latest versions of the Fortran compilers are not compatible with these advanced memory management “tricks”.
The generated code compiles, but it can no longer be highly optimized by the compiler, which is a significant drawback for High Performance Computing applications.

This is seen as raising significant doubt on the ability of future compilers to just compile the code.
As such, it was decided to migrate Esope code to modern Fortran.

4.
From Esope to Fortran 2008

We just saw that our industrial partner wishes to migrate its Esope code base to modern Fortran.
We now justify the choice of Fortran 2008 as the target for the migration; then we discuss the various problems that this migration raises whether they originate in Esope itself, FORTRAN 77, or requirements that the company set.

4.1.
Fortran 2008

Fortran 2008 was chosen as the target for the migration for the following reasons:

•

Terekhov and Verhoef
(
33
)
warn about the danger of subtle differences between primitive data type representations in two different languages.
By using a more modern version of the same language (Fortran), we keep the same compiler and should therefore be immune to this kind of problems.

•

Esope programs actually contain a lot of FORTRAN 77 code, “peppered” with a few Esope commands.
Remaining in the same language allows us to not translate a large part of the original code and rely on the backward compatibility of the compiler to accept it.

•

The development team, comprised solely of physicists, has extensive experience with FORTRAN 77 and is familiar with its ecosystem, tools, and best practices.
By continuing to use Fortran, we minimize the impact on their working habits.

•

Object-oriented programming support exists in Fortran 2008: declaration of derived types and structures that seem a good match for the segments.
It may prove useful to handle collections of heterogeneous segment types.

•

Fortran 2008 offers dynamic memory management that the Esope programs need.

4.2.
Esope problems

We envisioned the following problems for the migration of Esope concepts to Fortran 2008:

(1)

All memory management commands (see Section
3.3
) must be re-implemented and their exact behavior preserved.
In Esope, these commands rely on a meta-description of the segment on which they are working.
We must find a way to have a similar behavior, but Fortran 2008 does not offer a meta-description of its user-defined types.

(2)

Some of these commands (
segact
and
segdes
) will be obsolete because it is no longer necessary to handle swapping explicitly.

(3)

As explained in Section
3.2
, memory reallocation is handled automatically by Esope with a “double indirection” mechanism to free the developers from address changes when a segment is resized.
We will need to re-implement this mechanism to avoid profound modifications of the code or disrupting developers’ habits.

(4)

FORTRAN 77 can declare a variable implicitly based on some naming conventions.
This is considered bad practice and the
implicit none
statement (not standard in FORTRAN 77) forces developers to declare all symbols’ type (variables and functions, see also point
(11)
) before they can be referenced.
However, Esope transpiler does not recognize this statement, and it was therefore ignored in all programs.
As a result, some variables were not explicitly declared in the Esope code.
Framatome wishes to enforce the
implicit none
convention in all migrated programs and the migration will need to declare all variables.

(5)

Esope pointers are implemented as Fortran integers and sometimes declared as such.
In Fortran 2008, the pointer type does exist and is different from the integer type.

(6)

Taking advantage of the equivalence between pointer and integer, Esope offers a feature that allows a “pointer” to be negative, providing additional functionalities depending on the context (
e.g.,
used to declare read-only segments).

(7)

Esope offers the possibility to access the fields of a segment in a simplified way for the default pointer of the segment (see Section
3.2
).
This feature does not exist in Fortran 2008 and we will need to create the appropriate explicit accesses.

4.3.
Fortran problems

Although the migration will target the Fortran language, there are special practices and differences between FORTRAN 77 and Fortran 2008 that must be considered:

(8)

There are preprocessor statements in the source code (
#define
,
#ifdef
, …) that Framatome wishes to eliminate
(
21
)
.
These statements seem to be mostly used to ensure portability of the code across various computer architectures.
This is no longer necessary, as computer architecture has now been standardised to intel x64.

(9)

The “outdated” constructs such as
COMMON
block or
GOTO
are well-known issues in Fortran migration
(
10
;
26
)
.

(10)

In FORTRAN 77, the interface of external functions (
i.e.,
defined in some other source file) is declared with the statement
external

which only specifies the name and the return type of the function and not the number and types of parameters.
The same statement in Fortran 2008 requires to completely specify the interface.

(11)

Furthermore, in FORTRAN 77 when using an external function (defined is some other source file), its return type must be declared independently of the
external
statement.
This can be explicit (
e.g.,

integer afunction
) or implicit (based on naming convention of the function) as described in point
(4)
.
In Fortran 2008 the declaration of external functions’ return type is no longer independent of the
external
statement, but one must be careful to not migrate the explicit return type definition as if it was a variable declaration (which has the same syntax in FORTRAN 77).

(12)

Fortran 2008 does not allow arrays of pointers
5
5

5

https://fortran-lang.discourse.group/t/arrays-of-pointers/4851
.
This is an issue because the source code contains many of these to implement collection of heterogeneous segments.

4.4.
Usage concerns

There are other concerns that are not related to programming language features, but have to do with actual usages and desirable practices for the future:

(13)

There are four include syntaxes in the existing code: preprocessor (
#include
), FORTRAN 77 (
include
), and Esope (
%inc
or
-inc
).
Framatome wishes to simplify this by using at most one syntax or possibly removing all includes
(
4
;
23
)
.

(14)

With the Fortran 2008 pointer, you can use either an assignment statement (
=
) or a pointer assignment statement (
=>
):

p => q
copies the address contained in pointer
q
into pointer
p
;
and

copies the values of the structured type pointed by

into the structured type pointed by
p
.
Framatome wishes to forbid the second behavior for segments.

(15)

In arrays within segments, dimensioning variables allow one to define at run time the size of the array (see Section
3.2
).
A perceived issue with Esope is that nothing differentiates these variables from “normal” Fortran ones.
We would like to offer the means to better differentiate these variables and control how they are manipulated.

(16)

To implement this “dimensioning expressions” behavior in Fortran 2008, there are two solutions: allocatable variables or pointer to arrays created dynamically.
Allocatable variables are typically recommended because Fortran can automatically resize an array if needed.
However, for consistency, Framatome does not wish to allow this behavior, which would compete with the dedicated
segadj
mechanism.

(17)

Esope provides a compact and natural way to create user-defined types through segments.
Fortran 2008 is a rather verbose language and Framatome wishes to keep a simple syntax to ensure readability of the segment definitions.

(18)

It is desirable that the generated code looks as familiar as possible to the developers.
Formatting, comments, or empty lines should be preserved as much as possible.

(19)

It is desirable to have a clear traceability of the migration that lets developers understand from where a given piece of code comes.
For example, if some code is added in a file as the result of performing an include statement, this should be clear in the migrated code (
e.g.,
by adding a comment).

(20)

After migration, some statements may become useless (see Section
4.2
).
However, and again for traceability reasons, it must be explicit in the resulting code that the instruction was removed and why it was removed.

(21)

Contrary to Fortran 2008, FORTRAN 77 was missing a declaration of whether parameters were input or output.
The information is sometimes made explicit in comments but not in a way that can be automatically processed.
Framatome wishes that this declaration be now explicit as allowed in Fortran 2008 (“parameter intent”).

(22)

The company has a wealth of archived segments where the relationship between segments (like graph of segments) depends on the double indirection (see Section
4.2
).
The migrated application will need to be able to reload these archived segments and therefore handle the double indirection in a manner compatible with Esope.

(23)

Obviously, Framatome wishes to keep similar performance in terms of execution time and memory usage.

5.
Strategies for Esope Migration

The migration of Esope to Fortran 2008 requires a methodical approach to ensure the
preservation of existing functionalities and behaviors.

The requirement listed in the previous section translate to the following high level tasks:

•

Find out how to implement the segments.

•

Implement the notion of dimensioning variables and dimensioning expressions in Fortran 2008.

•

Offer the possibility to resize array fields in segments.

•

Migrate the double indirection mechanism of Esope.

•

Migrate the Esope commands in Fortran 2008.

•

Migrate some additional Esope utilities (described in Section
3.1
): segment field access (“dotted notation”), or array field dimensions (“slash notation”).

•

Take care of the preprocessing statements.

•

Reintroduce explicit typing of variables in the migrated code (see Section
4.4
).

•

Explicitly declare the parameters’ intent (see Section
4.4
).

The following subsections discuss these points.
We do not discuss in this paper the problem of migrating “outdated” constructs (see point
(9)

By keeping Fortran as our target language, we may ignore them in a first solution.
Migrating these constructs has been studied elsewhere (

5.1.
Esope segment migration

We identified three possibilities for segment migration:

Derived Type::

It is a special form of data type that can encapsulate other built-in types as well as other derived types.
It could be considered equivalent to struct in C.

Parameterized Derived Type::

It is a derived type with parameters for its array attributes.
These parameters may specify the array size (as in Esope) or field type kind
e.g.,
integers flavours, on 1, 2, 4, or 8 bytes.

C interoperability::

Fortran 2008 has explicit C interoperability, enabling the transparent use of C functions (
e.g.,
malloc or free) as Fortran ones.

As described in Section
4.1
,
to minimize disruption to the developer’s working habits, we want to stick to the Fortran language.
Pletzer
et al.,

(
28
)
warn that interoperability between languages may raise some unexpected issues.
For this reason, we will not consider the C interoperability option.

Despite their apparent similarity to Esope segments, we will not use the Parameterized Derived Types because:

•

Parameterized derived types can be allocated at run time to a given size, but they cannot be resized;

•

Resizing can be done by creating a new Parameterized derived type, but this would involve copying the entire segment to a new location even when shrinking the segment.

By using derived types, we have to handle segment resizing manually, but this gives us finer control on the operation and how it is performed (see Section
5.5
).

5.2.
Dimensioning variables and expressions

In Esope dimensioning variables were plain Fortran variables (Section
3.1
, Listing
1
, line 2) declared next to the segment declaration to ease understanding.
It was often accompanied by a comment describing its use in the segment (see also Section
7
).

Framatome wishes to enforce better control on these variables (Section
4.4
, point
(15)
).
For this, we propose to declare the dimensioning variable inside the derived type as a private field.
This will force the developers to modify its value only through a subroutine that we will offer.

The dimensioning expressions that give the actual size of array fields in the segments are arithmetic expressions involving one or more dimensioning variable(s).
These expressions are needed to instantiate the segment (command
segini
) or to resize it (command
segadj
).
For convenience, we chose to implement each dimensioning expression as a private function in the derived type’s module.
It takes as parameters all the dimensioning variables of the segment and returns the expected value for the given array field it dimensions.

This implementation choice allows developers to easily find the dimensioning expressions and modify them when needed.
It would also allows one to put additional controls to ensure that the dimensioning variables or expressions fall within an acceptable range.
This is an additional security that did not exist in Esope but would need to be implemented by the developers on a per variable/expression basis.

5.3.

The allocatable solution is a recommended good practice as it delegates memory management to the compiler.

We therefore chose the deferred-shape solution even though it forces us to implement the proper memory (de-)allocation routines.

5.5.
Esope commands

Esope has a library of commands to manipulate segments (Section
3.3
).
For this, Esope could resort to its own meta-description of the segments.
To migrate these commands, we implement them as part of the derived type declaration, inside the module for this derived type.
For example we will have a

user_segini(...)
.
Since we specialize the command for each segment, we know their structure and can create these commands accordingly without requiring meta-description at compile time.

The aforementioned abstract derived type

Here are the details:

•

The two commands
segini

segadj
are not defined in the
segment

For example, the “user” derived type has one dimensioning variable

In our running example, line 10 in Listing

It is considered a bonus that the two commands will now require as explicit parameter the dimensioning variables of the segment (see Section

•

The two commands

They take only one parameter: the instance they manipulate.
They will be used with the statement:

•

The two commands “segcop”, and “segmov” are introduced.
They do not really exist in Esope but were informal names given by the developers to alternative forms of

and

(see Section

).
They are now declared as parts of the

They take two parameters: the target instance and source instance.
For example,

•

The two commands

5.7.
Preprocessor statements

File inclusion (
#include
) was used in Esope code, often to “import” the declaration of a segment (very much like a
.h
file inclusion in C), and sometimes to reuse the declaration and initialization of a group of variables, or even some statements such as a loop.

All the includes are removed from the migrated code.
Segment declarations are migrated in their own module as explained in Section
5.1
,
every other statement is copied from the included file to where the file was originally included.

Currently the comments in the included files are not copied.
One reason is that there are sometimes several pages of comments that would enlarge too much the including files.
Another difficulty is that it is difficult to assign automatically a comment to the entity it describes.
So, it is difficult to know if a comment would need to be copied in the module of a derived type or in the program unit that includes a file.

Since segments are now modules they need to be imported (
use
in Fortran 2008) in the program units that need them.
The
use
statements are computed afterwards, looking at everything that is required but not define by a program unit.

As a special traceability feature (Section
4.4
, point
(19)
) we generate a comment line to mark the beginning and end of all included code.

Others preprocessor statements such as
#define
,
#ifdef
will continue to be treated by the preprocessor (
cpp
).

5.8.
Implicit typing

Fortran allows one to use variables without declaring them.
In this case, the variable’s type is inferred from its name
8
8

8

Typically, variable names starting with the letters ‘i’ through ‘n’ denote integers, while other names denote reals.
.
An
implicit none
statement forbids to use the implicit typing.
It is largely present in Esope code, but very often replaced by
implicit logical (a-z)
just before calling the Esope transpiler,
which does not accept
implicit none
(see Section
4.2
).
However, not all code use such replacement statements.
As a consequence, some variables were implicitly typed by mistake.

Concurrently, there are also cases where
implicit none
was not used,
but a specific implicit declaration instead
9
9

9

For example
implicit integer (x)

that states that all variable names starting with ‘x’ are integer instead of the normal real.
.

In the migrated code, we remove all implicit statements and insert a mandatory
implicit none
in all files.
This may cause errors at compilation for the few variables that were inadvertently not declared explicitly.
We also ensure that all variables used in the code are explicitly declared by inferring their type using the standard Fortran naming rules.

5.9.
Parameter intent

In FORTRAN 77 parameters are passed by reference by default.
Fortran 2008 provides an
intent
declaration to specify:

•

in
: the parameter’s value in the caller is used in the called, but not modified;

•

out
: the parameter does not have an initial value provided by the caller, but is used to return a value;

•

inOut
: the parameter’s value from the caller is used in the called, and the (possibly modified) value is returned.

We could have declared all parameters as
inOut
in Fortran 2008.
But to improve code quality and reduce errors, we aim to determine the correct intent of all the parameters.
This is based on some simple rules:

•

If the parameter is first accessed before being assigned, then it must be at least
in
;

•

Conversely, if it is first assigned before being accessed, then it must be
out
;

•

If it is first access and then assigned, it is
inOut
(because it was passed by reference in FORTRAN 77);

•

Parameters passed along to other routines depend on the intent of these other routines to know whether they are an access or an assignment;

•

We created a catalog of predefined routines with their known parameter intents.

In the next section, we will discuss some details of the migration process and tool.

6.
Migration Implementation

In this section we explain how we implemented the Esope migration.
The solution implements the choices defined in the previous section.
It is based on Model Driven Engineering (MDE): the Esope source code is represented as a model (an AST); this model is transformed in a Fortran 2008 model; and finally, the resulting model is exported into Fortran 2008 code.
We also detail the migration process.
The result is applied on an example use case and we evaluate the result.

6.1.
Model Driven Migration

We chose to implement the migration based on metamodel transformation.
The solution is based on the Famix
(
1
;
2
)

and FAST
10
10

10

https://github.com/moosetechnology/FAST

metamodels
(
2
)
.

Famix is a dependency metamodel representing the “user defined entities” of a programming language (
e.g.,
classes, functions, parameters,…) and the dependencies between these entities (
e.g.,
invocations to functions, accesses to variables).
It does not contain enough detail to allow reproducing (or migrating) the source code.
The FAST (Famix AST) metamodel is a complete AST representation of the source code with expression, statements, identifiers,…

The Famix model is more concise: it allows one to model a large quantity of code (millions of lines of code if needed).
It also represents all dependencies across the entire application, for example between entities in different source files.

Containing all the details of the source code, FAST is a larger model.
It would not be possible to have the complete AST of the application in memory.
But this level of detail is required to be able to regenerate the code (in its old form or migrated to Fortran 2008).

Famix offers mechanisms to load and unload on the fly the FAST model of a given subprogram.
Nodes inside the AST (for example a call statement) are mapped to nodes inside Famix (a function invocation).

6.2.
Migration process

The migration process includes the following steps:

•

Step 1: Parse Esope source into a Famix model.

•

For all included files (that appear in some
#include
instruction):

–

Step 2: Import the content of the file into a FAST model.

–

Step 3: For any segment definition encountered, export the generated derived type into Fortran 2008.

–

Step 4: Any remaining statements are copied to the location of the
#include
in the host subprogram.

•

For each not included file, gather the subprograms it contains and for each of these:

–

Step 5: Import the FAST model for that subprogram.

–

Step 6: Migrate the Esope FAST model to a corresponding Fortran 2008 FAST model.

–

Step 7: Export the Fortran 2008 FAST model generated into a source file.

In our approach, we treat included files as program units.
However, we treat them separately from other program units because the segment definitions are migrated to their own module, and other instructions are copied where they are included in other program units. This is explained in step 3 and 4.

Parsing.

Parsing Esope code (steps 1, 2 and 5) is not trivial as there was no easily re-usable parser for it and the grammar was not formally defined.
We will not go, here, in the details of how this problem was solved.
In a nushell, we used a small island grammar parser that copied the Esope code into FORTRAN 77 code by putting in comments the Esope commands so that a standard FORTRAN 77 parser can parse the code.
From that modified code, we generate a Famix model including the comments.
We then go through this model again to generate Famix Esope entities from the statements in the comments.
This process is explained in more details in
(
32
)
.

Migration.

The migration itself (steps 3 and 6) is done through model transformation following the MDE approach.
Because we must go through the entire FORTRAN 77 AST to migrate it to a Fortran 2008 AST, we chose to use a visitor (instead of transformation rules for example).
We use out-of-place
(
19
)
transformation with two distinct models:
For a FORTRAN 77 subprogram, we visit its AST from the root (subprogram node) down to the leaves, and for each node, create a replacement in the Fortran 2008 AST model.
Pure FORTRAN 77 nodes are usually passed through as they are in the new model because Fortran 2008 is backward compatible.
We introduce a module node as root of the migrated program units to contain each subprogram.
Esope nodes are transformed into Fortran 2008 subtrees in the resulting AST.
Segment declarations are special in that they result in their own Fortran 2008 AST.

In Step 3, the result of migrating pure Fortran code (
ie.
not the segment declarations) of the included file is recorded in a dictionary of all included files.
These partial models are then inserted in-place whenever a
#include
for a given included file is encountered.
For readability, we also enclose these inserted nodes between two comment nodes.

Finally, exporting the migrated model to Fortran 2008 source code (steps 4 and 7) is straightforward, as the AST contains all the information needed.

6.3.
Generating large chunks of code

When we migrate a segment, we face code inflation due to the generation of all Esope commands for each derived type.

Constructing the AST for these commands would have been tedious and error-prone.
It would also make the migration tool difficult to maintain due to the sheer size of the code generating these large ASTs.

To simplify the migration process and make it easier to write and maintain the migration tool, we use plain strings and string templates with placeholders (
e.g.,

procedure ::

segini => {1}_segini
, where “{1}” is a placeholder).

One challenge is inserting child nodes into a typed AST, where the parent node expects children of a specific type.
For instance, an assignment statement node expects a variable as its left child and an expression as its right child.
Likewise, a subprogram definition node requires a specific structure comprising a name, parameters and body, each of which has its own expected type.
Inserting strings in this AST cannot be done anywhere.

We can use the string nodes to represent a single statement or a complete program unit.
To be able to do this, we use the traits of Pharo
11
11

11

https://pharo.org/
(similar to interfaces with default methods in Java) for these strings.
A string node (plain or template) can be both a statement or a subprogram thanks to traits.

These string nodes make it easier to generate a large amount of similar code.
But they also have some downsides:

•

Testing the compliance of string nodes with the Fortran 2008 meta-model is not possible.
They are in the model but outside the meta-model;

•

Correct formatting of the code is also more challenging. For example, indentation depends on the nesting level of the instructions, which may vary for various uses of the same string.

7.
Discussion

Although the migration is now working, there are still some points to be dealt with.
We discuss here future steps to take and limitations of our approach.

Comments:

Comments in reverse engineering are traditionally difficult to deal with because they are not part of the language’s grammar.
It can be difficult to automatically decide to what entity a comment pertains.
Therefore when migrating entities to different parts of the code, it is difficult to know where the comment should go.
We have the case with segment definition and the declaration of their dimensioning variables.
The first goes in a separate module while the second goes anywhere the segment is used.
For now we do not deal with this issue and all these comments go with the “segment module” (module defining the derived type for the segment).

Esope constructs:

We are not yet dealing with all Esope constructs (
e.g.,

segini p=q
or
segact p=q
) and the parser needs to be extended.

Esope code base relies heavily on outdated constructs:
GOTO
,
COMMON
, and
EQUIVALENCE
.
Eliminating them is a relevant and useful research topic
(
9
;
10
;
24
;
30
)
, but it is outside the scope of this project.
Because we are migrating to Fortran 2008, we do not need to worry right now about these outdated constructs.
We will rely on past results
(
10
;
26
)
to treat them.

Validation:

The use case has some limitations.
The real applications to migrate have been around since the early 1990s, and are the combined work of many developers.
By contrast, the Bookstore was created more recently by a single developer and may therefore reflect their best practices.

As is often the case, the real source code mixes, FORTRAN 77 conventions with newer ones (Fortran 90 statements).
We have yet to implement a parser that transparently accepts all these conventions and keeps the comments (see
(
32
)
for details).

Code inflation:

The migrated Fortran 2008 derived type includes the definitions of all the Esope commands for each derived type.
This results in a large code expansion (hundreds of lines of code for a segment) that makes reading them cumbersome and modifying them difficult.

The developers will have to maintain the code in the future and modify the segments’ definition.
As expressed in Section
4.4
the definition of the segments should be lightweight, easy to read, understand and modify.

We are considering using a companion DSL (Domain Specific Language) for this as well as a small tool to convert the DSL into Fortran 2008.
The DSL would express only the data structure of the segment just as is now the case with Esope.
The tool would then convert this data structure into the Fortran 2008 definition with the “boilerplate” code for the Esope commands (Section
5.5
).
In this vision, the developers would never look at the Fortran segments modules but only work with the application code and the DSL segment definition.

Two options are currently under study for the DSL:
(i) a simple textual description like TOML
12
12

12

https://toml.io/en/
;
(ii) keeping the old Esope format (for which we already have a parser) which is close to Fortran syntax.

8.
Conclusion

FORTRAN 77, a programming language in use since the
1980
s, remains essential for
many scientific applications where performance is critical.
Esope extends FORTRAN 77 offering additional features: structured type and dynamic memory allocation.
However, the evolution of compilers and development technologies has limited
certain essential optimisations, which could compromise the long-term sustainability
of these applications. This raises the fundamental question wether Esope applications will still be compilable in the future?

To address this challenge, we developed an approach that automatically migrates Esope applications to modern Fortran (Fortran 2008).
We presented all the difficulties and requirements of this migration and detailed how they were addressed.

Tests on an Esope example application demonstrated that this migration does not affect the validity of the code, with the same results between the Esope and Fortran 2008 versions. Furthermore, our evaluations of execution time and memory usage showed that the migrated application is faster and uses less memory than the Esope one.

This approach paves the way for ensuring the longevity of Esope legacy applications
while leveraging these applications by using Fortran 2008 with modern compilers.
Future work and research will be required to extend this process to more complex cases and
to keep pace with the evolution of compilers.
