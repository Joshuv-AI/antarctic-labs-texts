Omnibenchmark (alpha) for continuous and open benchmarking in bioinformatics
Izaskun Mallona, Almut Lütge, Ben Carrillo, Daniel Incicau, Reto Gerber, Anthony Sonrel, Charlotte Soneson, Mark D. Robinson

Abstract
Benchmarking in bioinformatics is a process of designing, running and disseminating rigorous performance evaluations of methods (software). Benchmarking systems facilitate the benchmarking process by providing an entrypoint to store, coordinate and execute concrete benchmarks. We describe an alpha version of a new benchmarking system, Omnibenchmark , to facilitate benchmark formalization and execution in solo and community efforts. Omnibenchmark provides a benchmark definition syntax (in a configuration YAML file), a dynamic workflow generation based on Snakemake , S3 -compatible storage handling, and reproducible software environments using EasyBuild , lmod , Apptainer or conda . Tutorials and installation instructions are available from https://omnibenchmark.org .



Aim

Computational biology tools are a staple in biological and medical research. Researchers use tools and software packages to make sense of their data and/or to refine these methods and develop new ones. In both cases, scientific benchmarking provides means to compare method performances, to pinpoint their strengths and weaknesses and to help choosing the best suited method for a given purpose and context.

Most frequently, benchmarks are carried out by small teams, vary in neutrality, and are often not updated after publication. Independent teams often publish overlapping benchmarks on the same topic; however, benchmark results tend to be hard to reuse due to a lack of practices such as: clear licensing, adoption of workflow frameworks, and software environment versioning
[
Cao et al., 2023
,
Sonrel et al., 2023
]
. Community benchmarking initiatives such as
openproblems.bio

[
Luecken et al., 2024
]
or
OpenEBench

[
Capella-Gutierrez et al., 2017
]
address these limitations by channeling contributors to structured and topic-driven benchmarking events.

To standardize and facilitate benchmarking, we are developing
Omnibenchmark
, a new continuous, distributed and open benchmarking system to self-deploy benchmarks by using a benchmark formalization language and its automated translation to reproducible workflows.

Design

Community benchmarking is an alternative to traditional benchmarking
[
Capella-Gutierrez et al., 2017
,
Seppey et al., 2020
,
Hanssen et al., 2023
,
Luecken et al., 2024
]
. Core themes include using workflow systems, building communities to run benchmarks during intensive challenges or hackathons, sharing data using standards and FAIR
[
Wilkinson et al., 2016
]
principles, using free and open source software, tracing contribution neutrality, and providing infrastructure entrypoints to facilitate computing in comparable and homogeneous systems, frequently using containerization techniques. The userbase of community benchmark is broad, and goes beyond methodologists:
OpenEBench

[
Capella-Gutierrez et al., 2017
]
categorizes users into developers (probably non-neutral method contributors), benchmarkers (more likely to be neutral contributors), end-users (anyone browsing results) and funders; each group with different aims, motivations, and preferred access gateways.

Omnibenchmark
aligns with other continuous benchmarking systems in aim, and shows some differences in design. Our system is meant to be run in a distributed manner, while also providing means for centralization. This has implications beyond infrastructure:
Omnibenchmark
can be used for solo benchmarking, e.g., a person interested in comparing their method performance against other tools and using public datasets. In this scenario, the researcher acts as developer, benchmarker, and end-user simultaneously. A solo benchmark can be run locally and outputs are kept locally and eventually pushed to a FAIR
[
Wilkinson et al., 2016
]
repository (e.g., Zenodo) on publication, without community building. In this scenario, transparency and reproducibility are built in; open access is optional. On the other hand,
Omnibenchmark
can be used for community benchmarking during a hackathon, challenge, or long-term benchmarking event. For that, operations are based on and resemble using
git
for version control: developers and benchmarkers have a local copy of the
Omnibenchmark
code, the benchmark specification and required code, data, and software stacks, and can contribute changes via commits and merge requests. Appropriate HPC infrastructure (e.g., virtual or physical Linux machines) and benchmark results (e.g.,
S3
-compatible buckets) are agreed upon by the benchmarking community members, so costs are controlled, benchmark runs are versioned and outputs are openly accessible to the community and, ideally, to the public.

Omnibenchmark
is a pip-installable Python package available on
omnibenchmark.org
. Its functionality can be divided into four layers:

1.

Formalization. Individual benchmark components (Figure
1
A), its architecture and metadata (including software environments) are formally described in a
YAML
configuration file (Figure
1
B).

2.

Software. The software backend is reproducibly built and activated following the benchmark
YAML
. Software is specified in separate configuration files, built using
EasyBuild

[
Hoste et al., 2012
]
and run either as
Apptainer
(
singularity
) images or local environmental modules (
lmod
); additionally,
conda --explicit
environments can be used.

3.

Workflow. The benchmarking
YAML
is parsed to dynamically generate a reproducible
Snakemake

[
Köster and Rahmann, 2012
]
workflow specification. The expressivity of the config
YAML
allows generating complex benchmarks beyond data-method-metric linear layouts, including gather-scatter
[
Köster and Rahmann, 2012
]
patterns (Figure
1
A) and adding dataset- or method-specific parameters. We use
Snakemake
(version
\geq 8
) capabilities to make use of the reproducible software environments, to populate remote storage, to collect (benchmark) resources metrics, and to track provenance.

4.

Storage for outcomes of the community benchmarking. Final and intermediate outputs are either stored locally (solo benchmarking or during development runs) or pushed to a versioned
S3
-compatible storage for sharing (Figure
1
C). Benchmark releases include code, software environments, results and metadata; every release is tagged following a semantic versioning system. Write access to
S3
buckets is restricted and controlled via access tokens, while reading and listing are open to everyone.

Ideally, benchmark specification files contain steps to generate interpretable performance metrics, e.g., F1 scores, adjusted Rand indexes, or similar. We suggest adding an extra benchmarking step collecting these metrics and forwarding them to bettr
[
Marini and Soneson, 2024
]
, a web application that provides customizable and dynamic plots and tabular representations of performance metrics, helping to aggregate them and evaluate performance in a flexible way suited to the final user needs.

Usage

To start a benchmark from scratch (Figure
1
), that can be just run locally, the user has to:

1.

Write a benchmark configuration
YAML
file, reflecting the benchmark layout, software environments, and other metadata. This configuration file will typically begin as a simplified version of the benchmark pipeline. This file can be validated for syntactic and semantic conformance from the command line (Figure
1
D).

2.

Populate a new
git
repository for each benchmark module (Figure
1
E). Each module is meant to be atomic, and should perform a single benchmarking task (e.g., prepare a dataset, compute a distance matrix, calculate F1 scores, hierarchically cluster a distance matrix using Ward’s method, etc.). Each module must provide a command line interface (e.g., via
argparse
) to define program input(s) and output(s). Input and output characteristics (file format, syntax) need to adhere to the benchmark
YAML
specification.

3.

Write one or more definitions for software execution backends. Backends will be made available for the benchmark execution (i.e., a conda explicit
env
files, easyconfigs, container images; see Table
1
). The benchmark definition
YAML
allows declaring multiple different execution environments.

Once
Omnibenchmark
is installed, running the benchmark will be possible by issuing a series of commands in order to: a) validate and visualize the
YAML
definition; b) build the software environments; c) optionally, attempt a dry run; and finally d) execute the workflow. To switch from a locally-stored benchmark to cloud storage, commands to configure the object storage and using it are provided.

To switch from
solo
to collaborative benchmarking, a benchmarker would still leverage the distributed paradigm. Similarly to
git
,
Omnibenchmark
is a distributed system by nature. Every user needs to obtain a local copy of
Omnibenchmark
and all the components associated with a given benchmark (e.g., the config file and the easyconfigs or container images). To share changes, users must agree on a common remote that will be used as reference (typically on a public
git
hosting service, such as GitLab, GitHub etc). Users can then add, commit and push changes to any of the declared git remotes (for the benchmark definition, or just changes to individual modules); other users can in turn approve, reject, and pull these changes. The governance of the benchmark declaration is decoupled from the governance of individual modules, which can be also developed as a collaborative effort.

Community building and benchmarking calls (for contributions) benefit from being publicly advertised. We recommend creating a ‘benchmarking billboard’
git
repo containing a thorough
README
that specifies the aim and scope of the benchmark, the benchmark
YAML
, the easyconfigs and
LICENSE
, and pushing it to a
git
remote where the community can access it and collaboratively modify its content. Contributors would clone or pull that repository and use it locally using their local
Omnibenchmark
installations. We recommend that changes to the benchmark specification file are then pushed (via merge requests) to this ‘benchmarking billboard’
git
remote, so that people in charge of running the benchmark in appropriate hardware (local, cloud or HPC) can pull the new specification, run the new benchmark version and populate the object storage with the benchmark version results.

Ensuring neutral benchmarks and constructive benchmarking communities, however, goes beyond the technical implementation. We suggest a ‘transparency builds trust’ approach
[
Mallona et al., 2024
]
and hence incorporating a code of conduct file to the ‘benchmarking venue’
git
repository. Similarly, the
README
should be explicit about benchmark philosophy, responsibilities and costs (e.g., who provides the storage and computing infrastructure), planned changes in benchmark layout, parameter handling strategies, and desired strategy for academic publication and authorship handling. Such documentation aligns well to pre-registration (e.g., as done in simulation studies
[
Siepe et al., 2023
]
); we encourage pre-registering benchmark plans in the early phase of a benchmark study.

One philosophical aspect of the
Omnibenchmark
design is that, because we want
Omnibenchmark
to track all relevant preprocessing and control the execution of methods run on data, we do not currently have a facility for users to upload results to the system.

We provide tutorials, how-to guides and a reference at
https://omnibenchmark.org
.

Limitations and future directions

Omnibenchmark v0.1.0.rc1
is released as an alpha version and is under active development. We welcome feedback on the implementation and, particularly, about its usability. New feature requests, backed by use cases that stretch the current specification, are greatly encouraged. We are currently working on improving the benchmark formalization with a dedicated ontology building on
PROV-O

[
Lebo et al., 2013
]
; embracing
CernVM-FS

[
Blomer et al., 2013
,
Blomer et al., 2017
]
to distribute software and
EESSI

[
Dröge et al., 2023
]
to automate both reproducible software installations and their distribution, implementing validations (e.g., input and output files formats and shapes, benchmark specifications, consistency across runs); increasing support for
arm64
architectures; providing hooks to snapshot full benchmarks and automate submission to public repositories (e.g., Zenodo); sending jobs to queuing systems; and deploying automated reports with metric post-processing strategies (multi-criteria decision making) and benchmark evolution fingerprinting (multidimensional unfolding).
