HLStrans: Dataset for LLM-Driven C-to-HLS Hardware Code Synthesis
Qingyun Zou, Nuo Chen, Yao Chen, Bingsheng He, WengFei Wong

Abstract
High-level synthesis (HLS) enables software developers to describe and implement hardware at a higher level of abstraction by using C/C++ instead of traditional hardware description languages to automatically generate FPGA-ready designs. However, generating HLS code significantly differs from standard C/C++: it disallows certain coding idioms, relies on specialized libraries, and critically requires fine-grained transformations and the insertion of optimization directives (pragmas) to achieve high performance. Large language models (LLMs) have shown promise in automating such transformations, yet existing open-source datasets lack sufficient complexity and optimization diversity. To address this gap, we introduce the HLStrans dataset, a comprehensive collection of 137 distinct real word programs, each annotated with a variety of C-to-HLS transformations that yield over 23K labeled design variants. These include a broad spectrum of pragmas and code-level optimizations. We benchmark state-of-the-art LLMs on this dataset to evaluate their ability to generate synthesizable, high-performance HLS code. As part of an ongoing effort, we plan to expand the HLStrans dataset in both scale and program variety, further empowering research at the intersection of AI and hardware synthesis.

Introduction

Specialized computing systems, also known as domain-specific architectures tailored to particular application domains, have seen dramatic growth as workloads like machine learning, signal processing, and data analytics outstrip the capabilities of general-purpose processors. By offloading compute-intensive kernels to accelerators such as Graphics Processing Units (GPUs), Field-Programmable Gate Arrays (FPGAs), or Application-Specific Integrated Circuits (ASICs), designers achieve orders-of-magnitude improvements in throughput, latency, and energy efficiency. To capitalize on this trend, begin by profiling your target workload to identify its most critical functions, then select the most appropriate hardware substrate and toolchain to implement those kernels with maximum parallelism and minimal overhead.

High-Level Synthesis (HLS) is a methodology that elevates hardware design to higher levels of abstraction by allowing engineers to describe functionality in software languages like C or C++, from which synthesizable hardware descriptions are automatically generated. The HLS tool analyzes the code, infers parallel execution paths, inserts pipeline registers, and maps data accesses to on-chip memories, producing Register-Transfer Level (RTL) descriptions in Hardware Description Languages (HDLs) such as Verilog or VHDL. Using HLS can accelerate the hardware design process and enable software engineers to engage in hardware development.

However, HLS departs radically from conventional software development by requiring developers to adopt a narrow, hardware-centric subset of C++ and acquire domain-specific expertise. Typical HLS workflows forbid features like dynamic memory allocation, unrestricted pointer arithmetic, recursion, and most of the standard library, instead demanding code that maps directly to efficient RTL
ye2024hida

sohrabizadeh2022autodse
. To achieve high-quality output, engineers must refactor their designs so that loops have compile-time bounds, arrays possess fixed sizes, and control logic forms strictly nested or single-producer/single-consumer structures
sudvarg2024hls

martin2009high

ye2022scalehls
. On top of this, HLS tools expose a suite of vendor-specific pragma directives for loop pipelining, unrolling, array partitioning, and dataflow streaming that developers weave into their code. Many also integrate specialized C++ libraries offering arbitrary-precision fixed-point types, hardware-friendly math routines, FIFO streams, and task-oriented dataflow constructs to bridge the gap between software abstractions and synthesizable hardware modules.

LLMs offer hope to aid designers in writing HLS code. Rather than just producing HLS code from natural language with LLMs, more recent works focus on converting existing C kernels into optimized HLS implementations
collini2024c2hlsc

xiong2024hlspilot

bhattacharyya2024llm

xu2024automated

prakriya2025lift
, leveraging structured inputs to yield high-performance designs rather than naive, resource-heavy translations. Despite these advances, integrating LLMs into HLS toolchains remains challenging and relatively unexplored, in large part because there is no comprehensive, open-source corpus of diverse, high-quality HLS kernels. This gap prevents practitioners and researchers from fully exploiting the code-generation and optimization capabilities of modern LLMs within their design workflows.

To address the scarcity of high-quality open-source HLS benchmarks, we introduce the HLStrans dataset, a comprehensive suite of 23K HLS kernels harvested from academic repositories. Each entry pairs a naive, functionally equivalent C implementation with multiple performance-tuned HLS variants. To assemble this corpus, we developed an automated augmentation pipeline that leverages Monte Carlo tree search (MCTS) guided by electronic design automation (EDA) tool feedback and design space exploration (DSE) tools, ensuring diverse yet compiler-friendly code transformations. Every kernel is annotated with cycle-accurate latency and detailed resource-utilization metrics obtained via synthesis, creating a rich training signal for both functional correctness and performance optimization. Building on this resource, we further fine-tune large language models using a novel reinforcement-style scheme of "performance tags" and "resource tags" (rated 1–10) that explicitly reward efficient hardware design choices.

In summary, we have the following contributions:

•

HLStrans Dataset: We introduce
HLStrans
, the
first
large-scale dataset of over 23K paired C and HLS programs for LLM-powered HLS code synthesis from software.

•

LLM-Driven HLS Data Augmentation: We propose the
first
effective augmentation framework that leverages LLMs, MCTS, EDA feedback, and DSE tools to generate high-quality synthetic HLS code.

•

Benchmark-Driven LLM Evaluation: Enabled by our benchmark suite, we evaluate various prompts and fine-tuning methods and demonstrate that while off-the-shelf code LLMs underperform on HLS tasks, retrieval augmentation and task-specific fine-tuning on HLStrans yield substantial improvements.

Related works

There is an increasing body of literature on applying LLMs to generate HLS design from original C code. C2HLS
collini2024c2hlsc
evaluates the basic task of translating naive C++ into synthesizable HLS C++.
bhattacharyya2024llm
demonstrates that LLMs can automate HLS pragmas and optimizations to produce synthesizable, high-performance RTL from C on image-processing benchmarks. LIFT
prakriya2025lift
introduces LLM–GNN hybrid methods that automatically optimize C/C++ designs to boost FPGA performance.
xu2024automated
presents an LLM-driven HLS program-repair framework that transforms C/C++ into synthesizable HLS-C. HLSPilot
xiong2024hlspilot
extends this approach with retrieval-augmented generation and chain-of-thought prompting to deliver optimized HLS implementations across nine applications. However, to date, no work has established a large-scale dataset for thoroughly evaluating an LLM’s HLS capabilities.

First, prior HLS datasets have primarily focused on resource estimation rather than on generating HLS code from C, and available program sources remain scarce. HLSsyn
bai2023towards
concentrates on encompassing a diverse range of optimization pragmas into only 42 kernels for training and evaluation of design quality prediction models. HLSDataset
wei2023hlsdataset
, including 34 data sources and 18K samples, targets power estimates, resource, and timing estimation. MLSBench
goswami2022mlsbench
is an open-source dataset created with the Xilinx Vivado HLS flow, covering 17 C/C++ and 13 SystemC benchmarks drawn from Polybench, CHStone, and MachSuite. It includes only HLS log files and reports. Spector
gautier2016spector
comprises a collection of OpenCL applications that the authors process with the Intel OpenCL SDK to produce 8,300 distinct hardware implementations for Intel FPGAs. Dai et al.
dai2018fast
have open-sourced a dataset of about 1,300 designs generated by using applications from suites such as CHStone, Machsuite, and Rosetta. Second, existing datasets inadequately capture comprehensive C-to-HLS transformations, focusing largely on pragma insertion. Third, they are not organized as paired C-and-HLS examples and omit the corresponding testbenches needed for LLM-based HLS code optimization, which are not ready for LLM.

4.1
Dataset Collection

Manually optimized codebases often suffer from inconsistent formatting and minimal documentation, making them ill-suited for LLM-driven code generation. Public kernels frequently rely on unexpanded macros and include extraneous utility functions that obscure core algorithms. Our goal is to prepare C-to-HLS designs for seamless LLM consumption by packaging each design with the following files:

•

Single original file
x
that is a slow original C/C++ codes.

•

Single optimized HLS file
y
that implements the kernel, including a top function and, if necessary, any sub-functions and specialized data types. The file must be synthesizable and not exceed the resources of the platform.

•

Self-contained C++ testbench
tb
includes all test cases and validation logic necessary to verify the kernel’s outputs against expected results. We manually write the testbenches and adjust the optimized HLS code to ensure it passes all tests.

Therefore, we construct pairs
(x,y,tb)

is synthesisable, the execution cycles from synthesis reports of

4.2
Dataset Augmentation

Given the performance, resource utilization, and compilation feedback provided by EDA toolchains, we employ Monte Carlo tree search (MCTS) and design space exploration (DSE) tools to efficiently explore the large and combinatorial action space as shown in Figure
3
.

First, MCTS performs structured exploration by balancing the exploitation of high-reward actions with the exploration of uncertain or less-visited regions of the search space. The optimization policy is generated by the retrieval augmentation generation (RAG) module. The search is guided to choose the suitable policy by both the verification pipeline and a reward model. The reward model incorporates detailed feedback from the HLS toolchain, including synthesis success or failure, compile warnings, and performance metrics such as resource usage, latency, and throughput. This heuristic-driven strategy enables the agent to iteratively refine transformation sequences and produce more high-quality, synthesizable HLS designs.

Second, HLS directive design space exploration using genetic algorithms
ferikoglou2023collectivehls
is adopted. It inserts pipeline, unroll, and partition pragmas to produce more effective data samples. Through iterative refinement, the framework converges toward optimized and synthesizable HLS code. After collecting these C-to-HLS code pairs, we use an LLM to produce a chain-of-thought narrative that analyzes the performance and resource bottlenecks, explains why the original code cannot be synthesized, and highlights the key optimizations applied in the HLS version. This explanatory reasoning is then integrated alongside the optimized HLS output.

4.2.1
Monte Carlo tree search (MCTS)

MCTS enables an agent to learn to navigate the vast space of possible code transformations while balancing multiple optimization objectives. The agent’s decisions are guided by comprehensive feedback from the HLS toolchain, including synthesis success, resource utilization, and performance metrics.Our MCTS has the following elements:

Environment E:
The environment is composed of the HLS toolchain, specifically Xilinx Vitis HLS, which compiles the code and provides critical feedback such as performance estimates.

Agent G:
We propose to use an LLM as the agent that leverages its pretrained knowledge of hardware design and in-context learning abilities.

Action A:
At each time step
t
, the agent selects an action
a_{t}
, which corresponds to a prompt or transformation applied to the current HLS code. We define two complementary action types: RAG
-
based actions retrieve optimization policies directly from our pre-built table and accompanying code examples shown in Figure
4
, leveraging retrieval
-
augmented generation to surface proven transformations rapidly and reliably. Reasoning
-
based actions with ReAct prompt
yao2023react
, in contrast, analyze compiler warnings such as pipeline
-
interval breaches or loop
-
unroll violations and apply targeted code reforms by interpreting warning semantics within the current code context.

State S:
The state
S_{t}
at time step
t
is defined as the current version of the HLS code after applying the previous actions.

Reward R:
Rule-based reward shaping has proven effective in guiding agent behavior in previous work
guo2025deepseek
. In our framework, the reward function
R(s_{t},a_{t})
is computed by applying rule-based scoring to verification results and feedback provided by the HLS tool. A penalty of
-2
is applied when the verification fails, and
-1
if synthesis fails or the design exceeds resource constraints. A neutral reward of
0
is given when the transformed design performs worse than the original, while a reward of
1
is granted when it performs better. If the design not only surpasses the original but also meets timing constraints, a higher reward of
2
is assigned.

In our cases, the MCTS begins at the initial state
S_{0}
(the root node), which is the naive HLS code. From a state
S_{t}
, the agent applies an optimization policy
\pi
, i.e., an action
a_{t}\in\mathcal{A}
, transitioning to the subsequent state
S_{t+1}
. MCTS consists of four key phases: selection, expansion, simulation, and backpropagation.

Selection
: We employ the upper confidence bounds for trees (UCT)
gelly2006exploration
algorithm to choose nodes.

\pi(s_{t})=\arg\max_{a_{t}\in\mathcal{A}}\left(\underbrace{R(s_{t},a_{t})}_{\text{reward}}+\beta\times\underbrace{\frac{\sqrt{1+N(s_{t})}}{1+N(s_{t},a_{t})}}_{\text{ $U$ Term}}\right).

Expansion:
From the current state
s_{t}
, generate one or more child nodes to explore untried actions, formalized as
a_{t+1}=\mathrm{llm}(s_{t})
.

Simulation:
Perform a rollout from the chosen child node by applying
a_{t+1}
, running HLS synthesis to estimate latency and resource utilization, and computing the reward
R(s_{t},a_{t+1})
.

Backpropagation:
Propagate the obtained reward back up the visited path, updating each node’s statistics (e.g., visit count and value estimate) to improve future selection.

4.2.2
Design Space Exploration

The tool implements an automated HLS design-space explorer that uses a genetic-algorithm optimizer to discover effective directive combinations, specifically loop pipelining, loop unrolling, and array partitioning, that maximize performance and resource utilization. By encoding each candidate solution as a set of directive parameters, evolving them through mutation and crossover, and evaluating them via HLS synthesis feedback, the tool generates high-quality configurations without manual tuning.

Overall, we leverage DeepSeek-R1 to generate high-quality synthetic code examples, the AMD Vitis HLS EDA tool, and DSE tools to validate, annotate, and collect performance/resource metrics within our framework, yielding an effective, end-to-end HLS code dataset. The detailed information on dataset generation is in Appendix
A.2
.

5
Experimental Evaluation of LLMs on Our Dataset

5.1
Prompting Methods

Zero-shot Prompting:
We craft concise, HLS-specific prompts that instruct the model to perform code optimization or transformation from its pretrained knowledge, without any additional fine-tuning or example demonstrations
liu2021makes

wei2021finetuned
.

Chain-of-Thought Prompting:
Building on the chain-of-thought approach of Wei et al.
wei2022chain
, our prompts first guide the model through a transformation reasoning phase before asking it to emit the refined code.

Retrieval-Based Prompting:

Recent studies
shrivastava2023repository

shypula2023learning
have shown that retrieval-based techniques can substantially boost code generation quality in large language models. In our approach, we first encode each program using CodeBERT
zhou2023codebertscore
to produce rich, semantically informed embeddings. We then index these vectors with FAISS
johnson2019billion
(Facebook AI Similarity Search) and perform a K-nearest-neighbors lookup to retrieve the top K most similar code snippets from our training corpus. Finally, we supply these retrieved examples alongside the original code as additional context to the LLM, guiding it to produce more accurate and effective edits. In our experiments, we set K to 1. The detailed prompt information is in Appendix
A.3
.

5.2
Experiment setting

Fine tuning setting.
Training was conducted using 2 NVIDIA H100 GPUs, each with 80 GB of memory. The computing environment was configured with CUDA 12.2 and cuDNN 9.1 to ensure optimal deep learning performance.

Optimization Conditioned Fine-tuning:
Programs that solve the same task can vary widely in how well they perform because of many different kinds of directives and code transformations. The optimized code has a jumble of small or large speedups, without any signal about which gains are most significant. To give the model clearer guidance, we borrow ideas from
shypula2023learning
and attach a “performance tag” and "resource tag" to each solution during training. Each tag reflects how close that program comes to the best attainable performance with resources minimized, using a discrete scale from 1 to 10, respectively. Concretely, for every benchmark problem, we rank its optimized solutions by latency and resource, labeling the top 10% in performance as a “10/10” performance tag and the lowest 10% in resource usage as a “10/10” resource tag. By examining these tags, the model learns which code patterns tend to yield the highest performance. At inference time, we prompt the model to generate the best-performing codes with the least resources. The detailed fine-tuning information is in Appendix
A.4
.

Models.
We evaluate closed-source models, GPT-4o and deepseek-R1. We also used pretrained checkpoints of open-source Qwen models
yang2024qwen2
: Qwen2.5-Coder-32B-Instruct, Qwen2.5-Coder-7B-Instruct, and Qwen2.5-Coder-3B-Instruct obtained via HuggingFace
wolf2020transformers
.

Metrics.
To evaluate the effects of HLS code generations, we use the following metrics:

•

Functional Accuracy (%Function Correct): The share of test programs that preserve the original functionality testbench.

•

Synthesis Accuracy (%Synthesis Correct): The share of programs that can be synthesized.

•

Reduce Latency (Acceleration): The ratio of original latency to new latency,
accel=o/n
, where
o
is the old latency and
n
is the new latency from reports of HLS synthesis respectively. We report the minimum, average, and maximum acceleration only for the functionally and syntactically correct cases.

•

Optimization Rate (%OPT): The percentage of test programs that reduce latency (Acceleration > 1) while remaining functionally correct.

FPGA Flow Setting:
We transform the given sequential C++ code of these benchmarks into optimized HLS kernel code. We adopt the Vitis HLS design flow, using the Xilinx Alveo U55C data center accelerator card. The target frequency is 200 MHz.

We selected 17 applications as test cases both unsynthesizable designs requiring repair and synthesizable designs in need of optimization and used the remaining 120 applications for training (90%) and validation (10%). Previous works
li2022competition
show that generating multiple program candidates per input and selecting the optimal one improves code synthesis performance. We generate
k
program variants for each input, then select the fastest one that successfully passes all test cases; we refer to this sampling-and-selection strategy as
Best@k
.

Conclusion

We introduce a novel dataset that transforms C kernels into richly annotated HLS implementations, empowering LLMs to learn hardware
-
aware optimizations such as loop pipelining, unrolling, and memory buffering. Our experiments demonstrate that retrieval and fine
-
tuning on this dataset significantly boosts both latency reduction and synthesis success rates, proving its effectiveness in accelerating and automating electronic design flows. By releasing both the dataset and training scripts, we aim to catalyze further exploration at the intersection of LLMs and hardware design.

7
Future work

We evaluate HLS designs based on synthesis reports, which yield resource and timing estimates rather than true hardware performance. In future work, we will measure and compare real execution time across different models on physical FPGA platforms.

Unlike large software-optimization datasets, publicly available HLS benchmarks remain scarce. To address this gap, we will explore more effective methods for generating HLS-specific datasets and continue to grow our collection of real-world examples. Our current dataset targets AMD FPGAs; we plan to extend this work by generating analogous datasets for Intel FPGAs and Catapult HLS.
