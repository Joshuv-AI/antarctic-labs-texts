ShIOEnv: An Environment for Synthesizing Bash Shell Inputs with Execution Artifacts
\name Jarrod Ragsdale \email jarrod.ragsdale@my.utsa.edu, \name Rajendra Boppana \email rajendra.boppana@utsa.edu

Abstract
We introduce ShIOEnv, a Gymnasium-compatible Bash environment for synthesizing execution-annotated shell input traces. Datasets containing such traces are useful for training models to perform execution-free shell simulation, which in turn is useful for deploying honeypots for cyber deception. Existing datasets, such as NL2CMD and other Bash command corpora, do not include complete execution artifacts (stdout, stderr, exit status, and changes to the system’s state) associated with a command’s execution. ShIOEnv synthesizes shell inputs, executes them in a controlled system context, and records stdout, stderr, exit status, and structured filesystem and environment patches. Unconstrained (random) generation of shell inputs (command and arguments) results in multiple instances of arguments that are mostly redundant or result in execution errors. We introduce grammar-constrained synthesis to generate syntactically valid arguments with high input irreducibility, which we estimate through self-ablative contrasts of execution artifacts. We prepare 1.6M samples using grammar-constrained and unconstrained synthesis and collect their execution artifacts for 86 Linux/Bash utilities. Using this dataset, we train small language models (CodeT5) and evaluate their accuracy in predicting the actual execution behavior of attacker-sourced Bash commands. These models outperform commonly used rule-based simulation (Cowrie) and prompted large language models by up to 14.2 pp in output edit similarity (O-ES). We enhance the NL2CMD dataset by constructing 500K samples executable in a grounded system context along with their complete execution artifacts. We empirically demonstrate that models trained on grammar-constrained samples outperform those trained on NL2CMD samples by 22.5 pp in O-ES. ShIOEnv, command grammars, and 2.1M samples used in our primary evaluations are released for use by other researchers.

Introduction

Execution-free shell simulation is the task of predicting the execution behavior of a shell input, consisting of a command and optional arguments, within a specified system context.
The target behavior includes execution artifacts, such as terminal output, exit status, and changes to system state that may affect subsequent inputs.
The system context comprises execution-relevant state that affects command behavior, including the filesystem, environment variables, permissions, and user identity.
Execution-free simulation may be useful in settings where direct shell input execution is unsafe, costly, or undesirable.
Examples include cyber-deception systems that emulate attacker-facing shell interactions and command-line agents that use terminal state or execution feedback when selecting subsequent actions
(
Sladić et al., 2024
;
Chakraborti et al., 2017
;
Yang et al., 2024
)
.

Preparing models for this task requires a diverse range of shell inputs paired with their execution behavior in a system context.
Existing public resources provide only partial support for this supervision regime.

Lin et al. (2018)
and
Fu et al. (2023)
provide datasets that primarily support natural-language-to-command translation; cybersecurity training logs provide observed command sequences and metadata; and recent security datasets synthesize command-like activity for detection tasks
Švábenskỳ et al. (2021)
;
Trizna (2022)
.
These datasets do not, by themselves, provide complete execution artifacts for commands executed under a shared, reproducible system context

To address these gaps, we introduce the shell input-output environment (ShIOEnv), a Gymnasium-compatible data-generation environment for collecting execution behaviors for given commands in grounded system contexts.
ShIOEnv casts shell input synthesis as a Markov decision process in which an agent incrementally constructs a shell input through argument-level actions.
When construction terminates, ShIOEnv executes the completed input and records the resulting execution behavior.

Shell inputs collapse into common execution behavior patterns in which invalid or redundant portions of the input can obscure the effect of individual arguments.
As a consequence, syntactic validity alone is insufficient as a data-quality criterion for execution-annotated samples.
We define behavioral irreducibility as a measurement of argument redundancy with respect to the final observed execution behavior.
We perform this measurement via contrasts of execution behaviors of argument-ablated inputs.
An input is considered irreducible if no such ablations produce the same execution artifacts.
However, constructing arguments in a command-agnostic manner, which we call unconstrained synthesis (UCS), yields low-irreducibility inputs in which execution behavior is dominated by invalid or redundant arguments.
We therefore introduce grammar-constrained synthesis (GCS), in which a command-specific grammar dictates a derivation for producing each argument.

This work treats shell-command corpus construction as a data-centric machine-learning problem, with the central question being how the data-generation process and irreducibility criteria affect the utility of execution-annotated shell inputs.
We generate 1.6M execution-annotated samples using grammar-constrained and unconstrained synthesis.
We also construct 500K execution-annotated samples from NL2CMD commands adapted to a specified system context.
Together, these data sources support controlled comparisons among synthesis methods (GCS and UCS) and adapted input-only command corpora from the literature (NL2CMD).
We evaluate the resulting datasets by training models for execution-free shell simulation and using model performance as a measure of dataset utility.
Models trained on GCS data outperform models trained on unconstrained inputs, adapted NL2CMD inputs, and external execution-free baselines such as Cowrie
(
Cowrie, 2014
)
.
Moreover, grammar-constrained samples demonstrate greater training efficiency, outperforming models trained on five times as many unconstrained samples.

To summarize, we make the following contributions:

•

We introduce ShIOEnv, a data-generation environment for constructing shell inputs and their execution artifacts for a given system context and for efficiently evaluating argument redundancy. Each sample links a shell input to its execution artifacts.

•

We introduce grammar-constrained synthesis as a data-generation intervention for shell-command corpora. Command-specific grammars, derived from the man pages, restrict argument generation to context-admissible regions of the input space, reducing degenerate execution behavior and improving the mapping of shell arguments to the resulting execution behaviors.

•

We curate and release 2.1M execution-annotated samples spanning 86 Linux commands, together with command grammars, execution artifacts, and dataset schema information required for reproducible use.

•

We evaluate the generated data by assessing its ability to train models to simulate the specified system’s execution behavior, empirically demonstrating improved performance over existing datasets and execution-free approaches.

Background

2.1
Preliminaries

ShIOEnv models shell input synthesis as a sequential decision process in which an agent incrementally constructs a shell input for execution in a controlled system context.
A shell input consists of a command string (e.g.,
find
,
ls
) followed by optional arguments (e.g.,
-l
,
--list
).
Our formulation consists of three complementary parts: Markov decision processes to form the basis of argument-level construction, context-free grammars to define a command-admissible argument space, and temporal abstraction to treat variable-length grammar derivations as single argument-level actions.

A Markov decision process is a tuple
M=\langle\mathcal{S},\mathcal{A},p,r\rangle
, where
\mathcal{S}
is a set of states,
\mathcal{A}
is a set of actions,
p(s^{\prime}\mid s,a)
is a transition function, and
r(s,a)
is a reward function
(
Puterman, 2014
)
.
In ShIOEnv, states represent partially constructed command-argument sequences, actions append completed arguments or terminate construction, and terminal transitions execute the completed input in the target system context.

A context-free grammar is a tuple
G=\langle N,\Sigma,\sigma,P\rangle
, where
N
is a set of nonterminals,
\Sigma
is a set of terminals,
\sigma\in N
is a start symbol, and
P
is a set of productions defining nonterminal expansions
n\rightarrow(N\cup\Sigma)^{*}
for all
n\in N

(
Hopcroft et al., 2001
)
.
A derivation expands nonterminals until only terminals remain.
The set of terminal sequences derivable from
\sigma
defines the language
L(G)
.
ShIOEnv uses the notation
G_{c,x}=\langle N_{c},\Sigma_{c,x},\sigma_{c},P_{c}\rangle
to denote the grammar used to construct inputs for the active command
c
in a system context
x
.

Because a complete shell argument may require a variable-length grammar derivation, ShIOEnv treats each derivation as a temporally abstracted action.
This is consistent with semi-Markov decision processes, where a high-level action may span multiple lower-level steps before returning control to the decision process
(
Sutton et al., 1999
)
.
Thus, ShIOEnv preserves argument-level decision epochs while using grammar expansion to construct admissible completed arguments.

2.2
Related Work

Shell Modeling

Execution-free shell simulation is relevant in settings where direct command execution is unsafe, such as cyber-deception systems, where attackers could escape containment and abuse the resources used for direct execution
(
Sladić et al., 2024
;
Otal and Canbaz, 2024
)
.
A more benign setting for execution-free simulation is found in command-line agents that must reason about terminal behavior before taking action
(
Agarwal et al., 2021
;
Yang et al., 2024
)
.
Prior work has used model-based methods to generate shell responses for interactive deception and terminal emulation
(
Sladić et al., 2024
;
Otal and Canbaz, 2024
;
Ragsdale and Boppana, 2024
)
.
These systems primarily target plausible or engaging shell interaction rather than supervised prediction of exact executor-specific artifacts, such as stdout, stderr, exit status, and persistent state changes.

The command token, subsequent arguments, and the system context all jointly affect execution behavior.
A training example for this setting should therefore associate an input with the context in which it is executed in addition to the resulting text generation (stdout and stderr) and exit code.
Datasets containing only one part of this association are insufficient, as they do not provide the requisite mapping for training.
This motivates the development of shell input corpora annotated with their execution artifacts, in which observable responses and structured state transitions serve as supervised targets.

Shell Datasets and Command Synthesis

Existing public shell datasets only partially support system-specific shell simulation.
The Linux Plan Corpus provides a limited input-to-behavior mapping, cybersecurity-training datasets record shell commands and execution metadata from participants, and NL2Bash and NL2CMD primarily support natural-language-to-command translation
(
Blaylock, 2010
;
Švábenskỳ et al., 2021
;
Lin et al., 2018
;
Fu et al., 2023
)
.
These resources are useful for studying command usage or command generation, but they are not designed to provide complete execution artifacts for commands executed under a shared, reproducible system context.

Command synthesis can be viewed as an instance of syntax-guided synthesis, where programs are generated from a grammar-constrained space to satisfy a given specification
(
Alur et al., 2013
)
.
In this formulation, the grammar restricts the syntactic space of admissible candidates and functions
(
Alur et al., 2013
)
.
Prior work has also used grammar-guided methods for program synthesis and scalable data generation
(
Parsert and Polgreen, 2024
)
.
In our setting, command-specific context-free grammars encode sequential production steps to produce an admissible argument.
We adopt this grammar-guided view, but use derivations to generate grammar-admissible shell arguments for execution and behavioral measurement rather than to synthesize programs against a logical specification.

The closest published work to the synthesis component of ShIOEnv is NL2CMD.
NL2CMD extracts utility syntax, flags, and argument categories from man pages to generate commands, covering 38 utilities from the original NL2Bash distribution
(
Fu et al., 2023
)
.
Bash commands are synthesized from these extracted elements to be executed and later paired with natural-language descriptions, yielding a dataset for natural-language-to-command translation.
Its execution step functions as a validation filter: placeholder arguments are instantiated, commands are executed in a virtual machine, and commands that fail to terminate with exit status zero are discarded.
The resulting corpus enables a scalable mechanism for generating shell inputs.
However, NL2CMD differs from ShIOEnv in objective and annotation scope.
ShIOEnv employs command grammars to constrain and direct the generation of arguments over a variable number of production steps, considering execution as a supervisory source rather than as a final preservation criterion.
Furthermore, each retained sample is accompanied by execution artifacts that are crucial for shell modeling but not required for natural-language-to-command translation.

Executable Environments

Executable command-line environments support agents that interact with terminal-like systems and condition subsequent actions on observed feedback.
InterCode formulates interactive coding as a reinforcement-learning environment with code actions and execution-feedback observations, including Bash-based tasks
(
Yang et al., 2024
)
.
UbuntuWorld uses the Bash terminal as a simulator for automated Ubuntu technical-support agents, while CLAI exposes the command line through a generic sense-act interface for AI agents
(
Chakraborti et al., 2017
;
Agarwal et al., 2020
)
.
These environments primarily target task completion, troubleshooting, or interactive agent evaluation.
They do not report systematic exploration of command argument spaces, construction of execution-annotated shell corpora, or measurement of argument-level behavioral necessity.
Because these environments and corpora are not designed around randomized or grammar-constrained argument synthesis, they do not directly address the argument-redundancy problem studied in this work.
Consequently, existing resources leave open the problem of constructing shell-input corpora that jointly support controlled argument-space exploration, system-specific execution annotation, and empirical measurement of whether individual arguments are behaviorally necessary.

3
ShIOEnv

We present ShIOEnv as a data-generation environment for constructing execution-annotated Bash shell inputs.
Given a target system context, ShIOEnv synthesizes shell inputs, executes completed inputs in that context, and records execution artifacts.
A system context specifies the filesystem, environment variables, user identity, permissions, and other execution-relevant state used by the executor.

ShIOEnv separates input construction from execution, allowing the environment to expose a controlled argument-level decision process while deferring system effects, execution artifacts, and contrastive ablations (to assess irreducibility) until a complete shell input has been formed.
During construction, the synthesizing agent incrementally builds a shell input by appending completed arguments to a command token.
When construction terminates, the completed input is executed and its irreducibility measured in the specified system context.

3.1
Environment Formulation

A shell input consists of a command token followed by an optional sequence of arguments whose execution behavior is evaluated in the specified system context.
For example, the default behavior of the disk listing command
df
is altered by arguments
-a
to show all candidates,
--output=source
to only show the source column, and
-B 512K
to print sizes as 512 kilobyte blocks.
Let
x\in\mathcal{X}
denote the instantiated system context.
Let
c\in C=\{\texttt{df},\texttt{ls},\dots\}
denote a command token and
a_{1},\dots,a_{n}
denote each following argument action.
Let
\mathcal{V}\subseteq\Sigma^{*}
denote the set of complete argument strings over vocabulary
\Sigma
.

Figure 1
:
Synthesis of shell input containing a
df
command and argument actions. Execution artifacts are collected upon completion.

Using the MDP tuple
\langle\mathcal{S},\mathcal{A},p,r\rangle

(
Puterman, 2014
)
, we define construction states as ordered command-argument sequences:

\mathcal{S}=\{(c,a_{1},\ldots,a_{n})\mid n\geq 0,\ c\in C,\ a_{i}\in\mathcal{V}\}.

The construction state represents a shell input built up to that point.
The system context
x
is not included in this state because it is specific to the environment used during a rollout.
The action set contains complete argument strings and a special stopping action:

\mathcal{A}=\mathcal{V}\cup\{a_{\mathrm{stop}}\}.

The transition function is deterministic for every construction state.
If
a\neq a_{\mathrm{stop}}
, the action appends
a
to the current command-argument sequence.
If
a=a_{\mathrm{stop}}
, the environment transitions to a terminal state and executes the completed input in the target system context, producing the execution behavior

E_{x}(s)=\bigl(\operatorname{stdout}_{x}(s),\operatorname{stderr}_{x}(s),\operatorname{exit}_{x}(s),\operatorname{patch}_{x}(s)\bigr),

denoting the execution artifact produced by executing
s
in context
x
.
The first three components capture observable terminal feedback exposed to the user.
These components characterize the command’s immediate response, though they do not capture persistent effects on the execution context.
The final component,
\operatorname{patch}_{x}(s)
, records state changes as a structured patch within the system context, capturing execution effects that would otherwise be hidden at the current step.
Context patches are retained because later inputs in an interactive shell session may depend on effects such as file creation, removal, permission changes, or changes to the working directory.
Observable records provide response-level supervision.
Context patches provide state-transition supervision for system-specific shell simulation.

The synthesis process is illustrated in
Figure

1
, where argument actions synthesized by the agent while interacting with the environment are appended to the construction state until
a_{\mathrm{stop}}
signals that the input is ready to be executed and artifacts are collected.
We calculate the reward using the irreducibility measurement discussed in
Section

3.2
.

3.2
Behavioral Irreducibility

Given the execution artifact
E_{x}(s)
defined above, behavioral irreducibility estimates the extent to which the artifact depends on the arguments in
s
.
Intuitively, an input is irreducible if the removal of any number of arguments results in a change in
E_{x}
.
Conversely, an input is reducible if one or more arguments can be removed without altering the observed execution artifacts.
For example, removing
-s
or
-r
from the shell input
uname -a -s -r
would have no effect on execution, as their behavior is dominated by
-a
.
We denote an input as fully irreducible when every proper retained-argument contrast changes the artifact.

Let
N=\{1,2,\ldots,n\}
denote the ordered set of argument indices for a completed input
s=(c,a_{1},\ldots,a_{n})
.
For any retained-index set
I\subseteq N
, let

s[I]=(c,a_{I_{1}},\ldots,a_{I_{|I|}})

denote an argument-ablated input formed by removing any arguments at indices not in
I
.
We contrast the
E_{x}
of the full input against the
E_{x}
of each ablated input.
Let
\Delta_{x}(s,s[I])\in\{0,1\}
be an indicator function returning
1
when
E_{x}(s)\neq E_{x}(s[I])
and
0
otherwise.
Two artifacts are treated as equivalent when their exit codes and context patches match and when the normalized edit similarity of stdout and stderr exceeds the noise threshold described in
Appendix

B
.

Not all contrasts are equally informative.
A less extensively ablated input is likely to correspond more closely with the candidate input than one with a greater number of arguments removed.
We therefore weight each execution contrast by the number of retained arguments measured by
\lvert s[I]\rvert
.
Let
\mathcal{O}_{n}=\{I\subseteq N\mid|I|<n\}
be the set of proper retained-index sets.
For inputs with at least one argument, the irreducibility score is given as

R_{x}^{\star}(s)=\frac{\sum_{I\in\mathcal{O}_{n}}\lvert s[I]\rvert\,\Delta_{x}\bigl(s,s[I]\bigr)}{\sum_{I\in\mathcal{O}_{n}}\lvert s[I]\rvert},\qquad\lvert\mathcal{O}_{n}\rvert\geq 1.

For inputs with no arguments, we set
R_{x}^{\star}(s)=1
, since no argument ablations are possible.
The weight
\lvert s[I]\rvert
upweights near-neighbor ablations and downweights heavily pruned comparisons.
The normalization term makes the score comparable across input lengths.
This definition captures higher-order argument interactions that would be missed by considering only single-argument removals.

Because exhaustive irreducibility requires evaluating all properly retained subsets of arguments, its computational cost increases exponentially with the number of arguments.
We therefore approximate
R_{x}^{\star}(s)
using a fixed-budget Monte Carlo estimator.
Let

B=\min(M,\lvert\mathcal{O}_{n}\rvert)

be the number of ablations evaluated, and let
\{I_{1},\ldots,I_{B}\}\subseteq\mathcal{O}_{n}
be retained-index sets drawn uniformly without replacement, using all retained-index sets when
B=\lvert\mathcal{O}_{n}\rvert
.
The estimator is given as

\widehat{R}_{M,x}(s)=\frac{\sum_{m=1}^{B}\lvert s[I]\rvert,\Delta_{x}\bigl(s,s[I_{m}]\bigr)}{\sum_{m=1}^{B}\lvert s[I]\rvert}.

In ShIOEnv,
\widehat{R}_{M,x}(s)
is returned as the terminal reward for completed inputs.
The evaluation uses this terminal reward as a data-quality measurement and filtering signal rather than optimizing a learned sampling policy against it.
When the system context is fixed and known, we omit the subscript
x
, written as
R^{\star}
or
\widehat{R}_{M}
.

3.3
Grammar-Constrained Synthesis

The unconstrained action space contains argument strings that are not valid for every command.
For example,
--output=source
is a valid argument
df
, but not for
find
,
grep
, or
uname
.
Consequently, unconstrained (random) synthesis can produce shell inputs that collapse into repeated usage errors.
We address this problem by constraining synthesis via command-specific CFGs.

For command
c
under system context
x
, let

G_{c,x}=\langle N_{c},\Sigma_{c,x},\sigma_{c},P_{c}\rangle

denote a context-free grammar for a command
c
with terminals in the system context
x
.
The terminal alphabet
\Sigma_{c,x}
includes context-dependent values drawn from
x
, such as filenames and environment variables.
The language of the grammar satisfies
L(G_{c,x})\subseteq\mathcal{S}
, wherein a shell input is grammar-admissible for command
c
in context
x
if it belongs to
L(G_{c,x})
.

Let
\sigma_{a}\subseteq(N_{c}\cup\Sigma_{c,x})
be the set of terminal and nonterminal tokens starting each independent argument.
We make this distinction in order to cleanly separate argument actions for ablations.

Figure 2
:
Expansion of
--output=source
argument by
df
grammar productions.

For a construction state
s=(c,a_{1},\ldots,a_{n})
, an internal derivation constructs an argument action consisting of terminals found from expansions rooted at any
\sigma_{a}
.
We provide
Figure

2
to illustrate this process where
\sigma_{a}=\{\textrm{df},\textrm{[df]},\textrm{[Target]}\}
.
Productions are followed to expand a long-option nonterminal from
[df]
into
--output=source
.
The resulting terminal string
--output=source
is emitted as one completed argument (
a_{2}
) action.
This process is performed in a single time step from the environment’s perspective to preserve temporal consistency.

Internal derivations are not exposed as ShIOEnv states and do not create intermediate rewards or executions.
The grammar expansion can be interpreted as a semi-MDP over production steps
(
Sutton et al., 1999
)
, while ShIOEnv retains decision epochs only at the argument level.
Grammar-constrained synthesis therefore operates without changing the argument-level construction semantics of the environment.

We compare grammar-constrained synthesis with unconstrained synthesis.
In unconstrained synthesis, inputs are produced in a command-agnostic manner (all command arguments considered).
In grammar-constrained synthesis, each emitted argument is generated by a derivation in
G_{c,x}
, so the action belongs to
L(G_{c,x})
and is admissible for command
c
in context
x
.
This comparison isolates the effect of command-specific grammar constraints on argument irreducibility and execution-free shell simulation.
As shown in
Section

4
, grammar-constrained synthesis shifts the synthesized distribution toward higher irreducibility and improves execution-free modeling performance.
Irreducibility filtering provides an additional data-quality signal for evaluating shell inputs.

4
Evaluation

We evaluate ShIOEnv-synthesized datasets by measuring the effect of grammar constraints on execution-free simulation.
Using datasets constructed under different synthesis regimes, we evaluate whether these mechanisms improve the performance of fine-tuned models predicting execution artifacts when conditioned on the shell input that produced them.
Finally, we slice each dataset by irreducibility to jointly measure the effects of grammar-constrained synthesis and sample irreducibility.

4.1
Experimental Setup

The system context for collecting execution artifacts is instantiated in a Firecracker microVM running Ubuntu 24.04 with 1 CPU core and 256 MB of memory
(
Agache et al., 2020
)
.
Four Dell R730s are used to create 200 Firecracker microVMs associated with a ShIOEnv environment
The microVM is snapshotted upon instantiation and reverted to its initial state after each execution.
This ensures a consistent operating environment for irreducibility calculations.
The host communicates with the microVM via a virtual socket created during boot using the Firecracker API.
This virtual socket enables communication between the host and the microVM for execution and for returning artifacts observed during execution.

We consider three data sources.
NL2CMD denotes commands adapted from the NL2CMD corpus by replacing generic placeholders with system-specific artifacts present in the target environment
(
Fu et al., 2023
)
.
UCS denotes unconstrained synthesis, in which arguments are sampled from all possible arguments in a command-agnostic manner.
GCS denotes grammar-constrained synthesis, in which each argument is generated from the active command grammar.

We evaluate the effectiveness of these data sources for preparing models to conditionally generate execution artifacts.
Specifically, we train encoder-decoder transformers initialized from CodeT5-base (220M parameters)
(
Wang et al., 2021
)
on datasets that differ in data source, volume, system context, and irreducibility.

We include existing execution-free baselines in our evaluation to ground the performance of models trained on ShIOEnv datasets.
Cowrie represents a rule-based SSH honeypot baseline
(
Cowrie, 2014
)
.
Its exposed filesystem and environment are modified to match the target execution context, thereby estimating the fidelity attainable with hand-specified interaction rules under the same environment.
We also evaluate GPT-4o-mini and GPT-4.1-mini as prompted, general-purpose language model baselines.
These models receive a serialized description of the system context and the input shell command, but they receive no task-specific post-training.
These models serve to separate the effect of task-specific, execution-annotated training data from that of general-purpose language-model prior knowledge.

We evaluate the performance of these methods using three complementary metrics.
Exact match (EM) measures the proportion of samples for which the predicted execution behavior is identical to the target behavior after canonicalization.
We define canonicalization as a deterministic normalization of execution artifacts that abstracts away incidental numeric values and formatting differences.
Specifically, each distinct numeric value is replaced by an ordered marker according to its first occurrence, so that the first distinct number is mapped to
<NUM_0>
, the next distinct number to
<NUM_1>
, and later occurrences of the same value receive the same marker.
Contiguous whitespace is similarly normalized to a standard whitespace representation.
This normalization is used to prevent incidental differences such as environment-dependent numeric values, identifiers, counters, and formatting variation from being scored as execution-behavior errors, while still preserving the structural pattern of repeated values.
Observable-output edit similarity (O-ES) measures canonicalized edit similarity between predicted and target observable outputs, including stdout and stderr.
Context-patch Jaccard similarity (
\Delta
-JS) measures overlap between predicted and target canonicalized patch operations.
Together, these metrics distinguish strict end-to-end correctness, partial observable-output fidelity, and latent state-transition fidelity.

All methods are evaluated on the same benchmark of 357 shell inputs drawn from honeypot logs
(
Ragsdale and Boppana, 2024
)
.
Each benchmark input is executed in the same system context to obtain the target observable output and context patch.
Training samples are generated independently of this benchmark, avoiding data leakage between training and evaluation.

5
Discussion

The results presented in
Section

4
demonstrate that grammar-constrained synthesis and irreducibility filtering improve execution-annotated shell input samples through complementary mechanisms.
Grammar-constrained synthesis improves the generated corpus by restricting arguments to command-specific grammar languages before execution.
This reduces invalid argument actions, repeated usage errors, and early failure modes that can obscure the contribution of later arguments.
As a result, GCS produces more inputs that reach utility-specific execution paths.

The Irreducibility metric helps select samples with shell inputs whose arguments are empirically coupled to execution behavior.
This distinction is important because executability does not guarantee behavioral informativeness.
High-irreducibility samples provide clearer supervision because changes in the input are more likely to correspond to changes in observable outputs or latent state transitions.
The performance observed by models trained on samples with higher irreducibility suggests that this form of argument-effect attribution improves the utility of the training corpus, particularly for exact behavior prediction and context-patch consistency.

The strongest results are observed in models trained on grammar-constrained samples with higher irreducibility.
This suggests that behavioral necessity, in the form of irreducibility and syntactic admissibility within grammatical constraints, functions as a supplementary control mechanism.
Grammar constraints reduce the number of invalid or degenerate samples during synthesis, while irreducibility filtering identifies samples whose observed behavior depends on the constructed arguments.

Low-irreducibility samples may still represent common user behavior, stable command outputs, and realistic error modes.
They may also be useful for learning shell input invariances.
A deployment-oriented corpus should therefore preserve some low-irreducibility samples to model invariant behavior, while using high-irreducibility samples to strengthen learning of argument-sensitive execution behavior.
Irreducibility should thus be interpreted as a complementary signal rather than a universal quality criterion.

Limitations and scope.

The grammar suite was constructed to provide a controlled and behaviorally diverse subset of the Linux command space, serving as a reproducible basis for evaluating grammar-constrained synthesis.
The suite covers 85% of commands observed in attacker logs.
Of those unsupported, about 13% are commands such as
sed
and
awk
, whose execution behavior is primarily driven by externally defined functionality that lies beyond the scope of command-line arguments.
The remaining 2% of commands comprise shell commands that involve multi-system interaction and whose execution behavior cannot be reliably captured.
The 86 grammars presented in this work are portable across system contexts, with differences in
L(G_{x,c})
for different system contexts
x
arising from system-specific productions (e.g., filenames, users).
Future work should investigate learned or semi-automated grammar-construction methods that expand command coverage while preserving the context-dependent terminals required for system-specific execution modeling.

The experiments are conducted on static microVM environments operating in fixed system contexts and should be interpreted as measurements of fidelity within evaluated system contexts.
Generalizing across system contexts would require models that condition on and maintain the active system context in addition to a given shell input.
The context patches collected by ShIOEnv provide a mechanism for maintaining such a representation.
Future work should design such architectures using datasets collected across diverse system contexts.
The focus of this work is on dataset construction, in which we use execution-simulation performance to measure dataset utility.

6
Conclusion

Execution-free shell modeling requires datasets that link shell inputs to both observable execution records and latent state transitions within a specified system context.
This paper introduced ShIOEnv, a Gymnasium-compatible data-generation environment for constructing system-specific, execution-annotated Bash shell inputs.
ShIOEnv executes a given input in a given system context and records stdout, stderr, exit status, and structured context patches.
ShIOEnv addresses the lack of system-specific execution annotations in existing shell corpora and provides a reproducible mechanism to construct supervised data for command-behavior modeling.

We introduced behavioral irreducibility as a data-quality signal for estimating whether input arguments are necessary for the observed execution behavior.
A fixed-budget Monte Carlo estimator provides a practical approximation to exhaustive ablation, enabling irreducibility to be used for corpus-scale analysis and filtering.
We also introduced grammar-constrained synthesis, which restricts argument generation to command-specific context-free grammars and reduces invalid, redundant, and error-dominated argument combinations.

We synthesized 2.1M execution-annotated samples spanning 86 Linux utilities.
The empirical evaluation shows that grammar-constrained synthesis produces shell inputs with higher behavioral irreducibility and improves execution-free shell simulation.
Models trained on grammar-constrained samples outperform those trained on unconstrained samples and on adapted NL2CMD samples.
Irreducibility filtering yields additional gains, particularly for exact behavior prediction and context-patch consistency.
These results indicate that syntactic admissibility and behavioral necessity address complementary sources of noise in execution-annotated shell data.

The results support the use of ShIOEnv as both a data generator and an evaluation instrument for system-specific command modeling.
The environment, grammars, execution artifacts, and generated datasets provide a framework for shell input-behavior mapping, data-quality filtering, and execution-free interaction.
Future work should extend grammar coverage to more expressive utilities, incorporate explicit environment-state conditioning, and study longer-horizon interaction settings in which context patches are used to update the modeled system state for multi-input sessions.
We release ShIOEnv, command grammars, and the generated datasets to support further research on data-centric methods for system-specific CLI modeling.

Broader Impact Statement

This work introduces ShIOEnv, a data-generation environment and execution-annotated Bash dataset for studying execution-free command-line simulation.
The primary positive impact is the development of safer, more reproducible methods for modeling command behavior without executing commands at inference time.
Such models can support cyber-deception systems, command-line assistants, and evaluation frameworks in which direct command execution may be unsafe, unavailable, or undesirable.
By releasing the dataset, command grammars, and execution artifacts, this work supports reproducible research on system-grounded execution-free simulation.

The work introduces potential risks.
The dataset contains command strings, system outputs, and behavior annotations that may help models generate more plausible command-line interactions that could be misused to improve automated reconnaissance, produce more realistic interaction traces, or support deceptive command-line emulation.
The produced dataset is intended for execution-free simulation, benchmark construction, data-quality analysis, and cyber-deception research.

The dataset does not intentionally contain personal data.
Because samples are grounded in a constructed system context, records may include synthetic file names, paths, environment variables, and command outputs that reflect the curated execution environment.
Researchers using this resource should treat these artifacts as system-specific annotations and should not infer human behavior, operational prevalence, or demographic properties from the command distribution.
The authors will maintain the public dataset release, document known limitations, and update the dataset card if substantive issues are identified.

Internally, ShIOEnv alternates between two phases: construction, during which the agent appends textual arguments to the current command, and execution, during which the constructed session is run from a fresh microVM snapshot to collect behavioral feedback.

B.1

The environment is fully observable, wherein the state representation and the observations returned to the agent are equivalent.
Each state observation is an immutable, padded 2

At reset, the first row is pre-initialized with

In the experiments conducted in

When either counter reaches its respective bound, the environment sets Gym’s

B.3
Action and Execution Handling

No executions take place in the environment until a sequence is complete and an executing action is received (
e=1
).
The environment then collects execution behaviors for the full input and each of its sub-inputs within the prescribed sampling budget.
Helper routines record the command’s standard output, exit status, and a structured snapshot of the system context (working directory, directory contents, environment variables, user groups, shell options, resource limits, and firewall rules) before and after execution to compute a context change patch.
These procedures document the value of each system feature both prior to and following execution, creating a context patch for each that change.
We use the produced observations in the presented sub-input contrasts.
When a sub-input produces observations equivalent to those of the full input, this signifies the removal of redundant arguments.

We classify behaviors as identical if the exit codes and post-execution context patch match and if the normalized edit similarity of the observable output exceeds a noise threshold
\beta

For our experiments, we collect

If the variance in observations is high, the threshold for edit-similarity-based redundancy will be low, requiring a greater content difference to safely classify an output as changed.
We find this over-punishment tolerable, as underestimating irreducibility ensures that fully irreducible inputs remain so.
