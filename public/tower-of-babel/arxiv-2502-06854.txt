Can Large Language Models Understand Intermediate Representations in Compilers?
Hailong Jiang, Jianfeng Zhu, Yao Wan, Bo Fang, Hongyu Zhang, Ruoming Jin, Qiang Guan

Abstract
Intermediate Representations (IRs) play a critical role in compiler design and program analysis, yet their comprehension by Large Language Models (LLMs) remains underexplored. In this paper, we present an explorative empirical study evaluating the capabilities of six state-of-the-art LLMs—GPT-4, GPT-3, DeepSeek, Gemma 2, Llama 3, and Code Llama—in understanding IRs. Specifically, we assess model performance across four core tasks: control flow graph reconstruction , decompilation , code summarization , and execution reasoning . While LLMs exhibit competence in parsing IR syntax and identifying high-level structures, they consistently struggle with instruction-level reasoning, especially in control flow reasoning, loop handling, and dynamic execution. Common failure modes include misinterpreting branching instructions, omitting critical operations, and relying on heuristic reasoning rather than on precise instruction-level logic. Our findings highlight the need for IR-specific enhancements in LLM design. We recommend fine-tuning on structured IR datasets and integrating control-flow-sensitive architectures to improve the models’ effectiveness on IR-related tasks. 1 1 1 All the experimental data and source code are publicly available at https://github.com/hjiang13/LLM4IR .

Introduction

Intermediate Representations (IRs) play a pivotal role in compiler design by structuring the compilation process into front-end, middle-end, and back-end phases
(
Reissmann et al., 2020
;
Webb et al., 2021
;
Sbîrlea et al., 2015
)
. Likewise, IRs enable efficient transformations, optimizations, and analyses that are independent of specific programming languages, thereby promoting portability across different architectures
(
Chow, 2013
)
.

Beyond their role in compilation, IRs are crucial for a variety of code intelligence tasks, including
vulnerability detection

(
Zhu et al., 2024
;
Jiang et al., 2024a
)
,
code comprehension and generation

(
Yuan et al., 2023
;
Jiang et al., 2024b
)
,
clone detection

(
Paul et al., 2024
)
, and
binary-to-source matching

(
Mao et al., 2023
;
Collyer et al., 2023
)
. Unlike high-level programming languages, IRs adopt an instruction-level format that encodes low-level details such as control flow dependencies, instruction transformations, and memory operations. These characteristics introduce unique challenges for
structural analysis
,
syntactic processing
,
semantic understanding
, and
execution reasoning
, making IR comprehension fundamentally distinct from modeling natural language or high-level source code.

:

Current IR processing methods, such as NCC
(
VenkataKeerthy et al., 2020
)
, represent IR instructions as linear sequences of tokens using Word2Vec-style embeddings
(
Church, 2017
)
, and BERT-style pretraining
(
Devlin, 2018
;
VenkataKeerthy et al., 2020
;
Niu et al., 2024
)
. However, these approaches lack an understanding of control flow structures and execution semantics, limiting their ability to generalize to IR-specific tasks such as
Control Flow Graph
(CFG) reconstruction, bug detection, and execution reasoning. Since IR execution is governed by low-level operational semantics rather than surface syntax, models that fail to capture control flow relationships often struggle with execution-aware IR tasks.

Our Study

Recently, with the remarkable advancements in LLMs for source code understanding and generation
(
Jiang et al., 2024c
;
Wang et al., 2023
;
Liu et al., 2023a
)
, a natural question arises:
Can LLMs understand IRs in compilers?

To investigate this, we systematically evaluate LLMs’ comprehension of IRs by assessing their performance across three dimensions. An overview of our evaluation framework and its alignment with the RQs is illustrated in Figure
1
.

We first investigate
whether LLMs can accurately reconstruct CFGs from IRs
(RQ1). We evaluate the structural understanding capabilities of LLMs, which are essential for program analysis and compiler optimization. To answer this RQ, Task 1 is designed to prompt LLMs to output CFG in DOT format based on a function’s LLVM IR.

We further examine
whether LLMs understand the syntax and semantics of IRs
(RQ2). This RQ targets both syntactic recognition and semantic comprehension, which are critical for understanding IR beyond its surface form. We evaluate this through two tasks: decompilation (Task 2: converting IR into high-level source-like code) and semantic summarization (Task 3: generating natural language descriptions of IR behavior).

Lastly, we investigate
whether LLMs can reason over IRs to simulate program execution and predict correct outcomes
(RQ3). This RQ probes the models’ capacity for dynamic reasoning—tracking control flow, variable states, and instruction effects under specific inputs. We design an execution reasoning task where LLMs are provided with IR code and input values, and are asked to determine whether assertions on output states will hold (Task 4).

In our experiments, we evaluate six state-of-the-art LLMs: GPT-4
(
OpenAI, 2023
)
, GPT-3
(
Brown et al., 2020
)
, DeepSeek
(
Guo et al., 2024
)
, Llama 3
(
Touvron et al., 2023
)
, Gemma 2
(
Team et al., 2024
)
, and Code Llama
(
Rozière et al., 2024
)
. All evaluations are conducted on a benchmark dataset derived from HumanEval
(
Zheng et al., 2023
)
, consisting of 164 C++ programs paired with their corresponding LLVM IRs. Each program is compiled using Clang at four optimization levels—
-O0
,
-O1
,
-O2
, and
-O3
—to generate a diverse set of LLVM IRs that capture both unoptimized and progressively optimized code structures.

Takeaway Findings

Our results reveal key limitations in current LLMs when interacting with IRs:

•

RQ1 (Task 1): LLMs can recover basic blocks and partial graph topology, but often misconstruct control flow edges—especially in branches and loops—revealing limited structural reasoning in CFG reconstruction.

•

RQ2 (Tasks 2 & 3): LLMs can parse IR syntax and identify basic structural patterns, but frequently skip critical instructions or rely on heuristic approximations when generating code or summaries—indicating a semantic gap in IR understanding.

•

RQ3 (Task 4): LLMs approximate execution reasoning through high-level semantic steps instead of simulating instruction-level behavior, leading to failures in tracking control flow, variable updates, and iteration logic—even with chain-of-thought prompting.

Contributions

The primary contributions of this paper are summarized as follows.

•

To the best of our knowledge, this is the first study on LLMs’ capacity to comprehend and reason over IRs, covering structural analysis, syntactic and semantic understanding, and execution reasoning.

•

We empirically evaluate SOTA LLMs across multiple IR-processing tasks, introducing targeted tasks, rigorous evaluation metrics, and systematic analyses.

•

Our findings pinpoint critical limitations—such as insufficient control flow awareness, shallow instruction-level semantics, and flawed execution reasoning—laying the foundation for future IR-specific model designs.

Preliminaries

LLVM and IRs

LLVM is a widely used compiler infrastructure that optimizes code via IRs
(
Lattner & Adve, 2004
)
. LLVM IRs are
low-level, statically typed
, and follow the
Static Single Assignment (SSA)
form, offering a language-agnostic representation. They support control flow analysis and enable custom compiler passes.

Figure
2
shows the hierarchical structure of a program’s LLVM IR, from modules down to individual instructions. An LLVM IR program consists of several hierarchical components. At the top level, a
module
encapsulates a set of related functions, serving as a compilation unit. Each
function
contains a sequence of
basic blocks
, which are straight-line instruction sequences with a single entry and a single exit. These basic blocks form the nodes in control flow graphs and are the fundamental units of control transfer. Inside each block,
instructions
define operations with explicit opcodes, operand types, and values, governed by LLVM’s strict static typing system.

Figure 2
:
Illustration of LLVM IR hierarchical structure.

Control Flow Graphs (CFGs)

A CFG is a fundamental program representation that captures all possible execution paths of a program. Each node in the CFG corresponds to a basic block—a straight-line sequence of instructions with a single entry and exit point—while edges represent possible control transfers between these blocks. CFGs serve as the backbone for numerous compiler and analysis tasks. In vulnerability detection, they help identify unreachable code, malicious branches, and control hijacks
(
Zhou et al., 2019
;
Anju et al., 2010
)
. In compiler optimizations, CFGs enable transformations such as dead code elimination, loop unrolling, and branch prediction
(
McConnell, 1993
)
. Additionally, in broader program analysis, CFGs support symbolic execution, slicing, and structural reasoning
(
Fechete et al., 2008
)
, making them indispensable for understanding and manipulating program semantics at the IR level.

3
Study Design

As shown in Figure
1
, to address our RQs (RQ1–3), we design four evaluation tasks (Task 1–4), each targeting a specific dimension of IR comprehension and aligned with the reasoning skills required to answer the corresponding research question.

3.1
Evaluation Tasks

CFG Reconstruction (Task 1)

This task evaluates whether LLMs can reconstruct the CFG from a given IR function. Since RQ1 investigates structural understanding, this task is a direct probe: constructing a CFG requires interpreting branches, loops, and control transfers—core aspects of IR structure. If a model can produce an accurate CFG, it demonstrates meaningful structural comprehension of the underlying code.

IR Decompilation (Task 2)

To answer whether LLMs understand the syntax of IR (RQ2), this task tests whether models can translate IR back into high-level code. Decompilation is a rigorous measure of syntactic comprehension: it requires recognizing code structure (e.g., loops, conditionals) from flattened IR, and mapping it to readable, high-level constructs. Successful decompilation suggests that the model understands IR syntax well enough to reconstruct valid source-level structures.

Code Summarization (Task 3)

This task complements Task 2 by focusing on semantic comprehension. Here, LLMs must generate concise natural language summaries of IR functions. Answering RQ2 requires more than surface parsing—it demands an understanding of what the IR does. Summarization tests whether the model captures behavior, intent, and output, revealing its ability to reason about function-level semantics.

Execution Reasoning (Task 4)

To address RQ3, we assess whether LLMs can simulate IR execution given specific input values. This task asks the model to predict whether assertions on output states will hold, requiring it to track control flow, data dependencies, and variable updates. Execution reasoning goes beyond pattern matching—it probes the model’s ability to reason over IR as a dynamic process.

Together, these tasks provide a comprehensive and structured benchmark aligned with the three core RQs, offering insights into how well LLMs can understand, interpret, and reason over compiler IRs.

3.4
Prompt Design

Effective prompt design is crucial for optimizing LLM performance
(
Liu et al., 2022
)
. Traditional single-turn prompts that embed role instructions and task descriptions into a single input often lack clarity and structured guidance. Recent studies
(
Liu et al., 2023b
;
Park et al., 2023
)
demonstrate that LLMs perform more reliably when treated as
expert agents
and are given detailed, domain-specific instructions.

To enhance response precision and consistency, we adopt an
Expert Meta-Template Prompt
format:

Prompt

You are an expert in [relevant field].

Input Data:
[IR snippet or relevant context]

Task:
[Task description]

Output Format:
[Expected output structure]

This template ensures that LLMs receive explicit role assignments, domain knowledge, task objectives, and output formatting requirements—collectively guiding them toward more accurate and well-structured responses.

For each of the four tasks (CFG reconstruction, decompilation, summarization, and execution reasoning), we iteratively refine prompts using strategies such as few-shot learning and chain-of-thought (CoT) prompting
(
Wei et al., 2022
)
. Multiple prompt variants are evaluated to maximize accuracy, consistency, and task alignment.

3.5
Implementations

Task 1: CFG Reconstruction

We prompt LLMs to generate CFGs from IR snippetsusing a structured meta-template that defines graph syntax and node semantics (see Section
3.4
). The prompt includes explicit guidance and iterative refinement.
Following
(
Ma et al.,
)
, we evaluate CFG reconstruction along multiple axes.
Node construction accuracy
measures the correctness of identified basic blocks, while
edge construction accuracy
evaluates the accuracy of control-flow edges. Based on these, we define two aggregate metrics.
Full CFG accuracy
refers to the case where both nodes and edges match the ground truth, whereas
partial CFG accuracy
applies when nodes are correct but edges contain errors.
To capture finer-grained structural reasoning, we additionally report
loop edge accuracy
, which measures correct reconstruction of loop structures (e.g.,
for
,
while
), and
conditional branch accuracy
, which evaluates the correctness of conditional branches (e.g.,
if-else
).

Task 2: IR Decompilation

We prompt LLMs to decompile IR into C++ source code and compare the results generated to the original ground truth. The task probes whether LLMs can recover syntactically valid and semantically faithful source code from IRs, across optimization levels (
O0
–
O3
).
Following prior work
(
Tan et al., 2024
;
Armengol-Estapé et al., 2024
;
Wong et al., 2023
)
, we evaluate decompiled outputs using three hierarchical metrics.
task completions
assesses whether the model produced a syntactically valid code.
execution completion
, checks whether the code compiles and runs. Among these, we distinguish between
re-execution success
(all assertions pass) and
re-execution mismatch
(at least one assertion fails).

Task 3: Code Summarization

We prompt LLMs with IR code snippets and request function-level summaries. To improve output quality, we apply expert-designed meta-prompts with few-shot examples and, where appropriate, chain-of-thought (CoT) guidance. The generated summaries are compared to ground-truth or human-curated references.
Following
(
Wu et al., 2024
)
, we evaluate summary quality using
BLEU

(
Papineni et al., 2002
)
for surface fluency,
ROUGE-L

(
Lin, 2004
)
for content coverage, and
METEOR

(
Denkowski & Lavie, 2014
)
for semantic alignment.

Task 4: Execution Reasoning

We present LLMs with IR snippets along with embedded assertion statements and prompt them to predict which assertions evaluate to “
true
.” This task requires the model to simulate program behavior through static reasoning over control flow and variable assignments.
We evaluate execution reasoning by checking assertion-level correctness: a
pass
if all are correct,
partial pass
if some are correct, and
failure
if none are. We also report the
overall pass rate
, the proportion of correctly predicted assertions across all cases.

4.1.1
Structural Reasoning over CFGs

From Table
2
, we observe that LLMs show significant variation in task completion and CFG accuracy. GPT-4 completes all 164 cases but only generates 39 fully correct CFGs. In contrast, DeepSeek R1 processes just 77 applications yet produces 57 fully accurate CFGs—indicating stronger per-instance reasoning. This performance boost is likely driven by its Chain-of-Thought (CoT) prompting, which explicitly encourages stepwise control flow reasoning. Other models, including GPT-3 (14), Gemma 2 (16), and Llama 3.1 (15), perform worse, while Code Llama fails to produce a single accurate CFG.

Structural errors further confirm these limitations. GPT-4 alone incurs 114 node-level mistakes, with GPT-3 and Gemma 2 each exceeding 100. Loop and conditional edge recovery remains poor across the board: GPT-4 reconstructs only 9 loops and 2 branches; DeepSeek R1 achieves 6 and 1, respectively, despite fewer inputs. These results highlight persistent difficulties in accurately identifying instruction boundaries and modeling control dependencies.

Finding 1:

LLMs can identify basic control instructions and construct partial graph structures, but often misrepresent branches and loops—revealing limited structural reasoning and poor control dependency understanding. Chain-of-Thought prompting improves accuracy by enabling stepwise CFG reconstruction.

4.1.2
Impact of Graph Density

Upon further analysis, we observe that applications in different performance groups exhibit distinct density patterns, suggesting that density influences model behavior and reconstruction outcomes.

Graph Density

Graph density quantifies how interconnected a CFG is, calculated as:

\text{Density}=\frac{\text{Number of Edges}}{n\times(n-1)}

(1)

where
n
is the number of nodes.

Figure
3
compares complete CFG accuracy (blue bars) and node construction error (orange bars) across density levels. The x-axis groups models by overlapping task success (e.g., ”GPT-4 only” or ”GPT-4 × Gemma 2”), while the y-axis indicates the average density of those programs. Error bars denote the density range per category. The distinct density patterns between successfully reconstructed CFGs and those with high node errors indicate that graph density strongly correlates with LLM performance. This insight can inform model selection. As shown by the two examples in the Figure
3
, CFG density appears to influence which models succeed or fail on the task:

Higher-density CFGs (avg. 0.11): GPT-4 and Gemma 2 succeed more often, while Llama 3.1 fails.

Lower-density CFGs (avg. 0.02): Llama 3.1 performs better, while GPT-4 and Gemma 2 struggle.

Finding 2:

LLM performance on CFG reconstruction varies with graph density, indicating its potential as a model selection heuristic in IR analysis.

In RQ2, we evaluate whether LLMs can comprehend both the syntactic and semantic aspects of IRs. We address this via IR decompilation and code summarization (Task 2-3).

4.2.1
Heuristic IR Reconstruction

We use the IR decompilation task to test syntactic understanding, where LLMs are prompted to reconstruct high-level C++ code from IR. Outputs are evaluated based on syntactic validity, execution behavior, and correctness of predicted assertions
(
Tan et al., 2024
;
Armengol-Estapé et al., 2024
;
Wong et al., 2023
)
. All experiments are conducted across optimization levels (
-O0
to
-O3
) to test robustness under compiler-induced IR variation.

Table
3
shows the number of applications in each category for different LLMs in decompilation task. From Table
3
, most task failures occur at
-O0
, where minimally optimized IRs are the longest (Table
1
), often exceeding model context limits. GPT-4 handles these cases best with only 3 failures, while Code Llama fails on 99 applications. Interestingly, re-execution success peaks at
-O1
and
-O2
, likely because they preserve structured control flow while reducing redundancy—making IRs easier for LLMs to interpret. In contrast,
-O3
’s aggressive optimizations (e.g., loop unrolling, instruction reordering) obscure control dependencies and degrade decompilation accuracy.

Across multiple examples, we observe that LLMs often omit IR segments—such as entire
if
statements nested within loops, resulting in incomplete or simplified decompiled code. Rather than following a strict instruction-by-instruction process, LLMs tend to reconstruct source code heuristically, relying on pattern recognition to infer missing logic. This heuristic approach limits their ability to capture fine-grained control flow semantics. Loops, in particular, are frequently approximated rather than faithfully reconstructed, leading to missing branches or partially handled conditions. Similar behavior is also observed in the Code Summarization and Execution Reasoning tasks (Section
4.3
), where LLMs fail to capture execution semantics fully. Figure
5
(Appendix
F.2
) illustrates this semantic drift, showing a GPT-4 output that passes re-execution checks despite omitting key logic.

Finding 3:

LLMs can partially generate syntactically valid C++ code from IR, but often rely on heuristic reconstruction, skipping critical instructions and misrepresenting control flow—revealing limited semantic understanding.

4.2.2
Pattern-Based Summarization Reveals Semantic Deficiencies

To evaluate LLMs’ ability to capture the broader semantics of IR, we prompt each model to generate natural language descriptions of IR-derived code snippets (Task 3). This task assesses whether LLMs can articulate a function’s purpose, inputs, outputs, and internal behavior. Generated summaries are compared to predefined golden references using BLEU, ROUGE-L, and METEOR. Higher similarity scores indicate stronger semantic comprehension and the ability to infer meaningful program behavior.

Table
4
presents model performance on Task 3. GPT-4 completes all 164 summaries, while GPT-3, Gemma 2, Llama 3.1, and Code Llama fail on 31, 76, 83, and 41 programs, respectively. However, high-quality summaries (score
>0.8
) are rare across all models. Each produces only one such case in BLEU. For ROUGE-L, GPT-4 leads with 9 high-scoring outputs, followed by Llama 3.1 (5), Gemma 2 (4), and others (1 each). GPT-4 also ranks highest in METEOR with 21 cases, ahead of Llama 3.1 (11) and Gemma 2 (7). In terms of average scores, DeepSeek R1 performs best overall, achieving the highest BLEU (0.42), ROUGE-L (0.64), and METEOR (0.705). Llama 3.1 and GPT-4 follow closely, while GPT-3 and Code Llama lag behind, reflecting weaker semantic modeling. These results highlight that while LLMs can generate summaries, their ability to capture fine-grained IR semantics remains limited.

These results suggest that while LLMs can identify surface-level syntactic features—such as function signatures, input/output types, and simple arithmetic—they struggle with deeper semantic elements. The scarcity of high-quality summaries (score
>0.8
across BLEU, ROUGE-L, and METEOR) indicates difficulty in capturing iteration patterns, conditional branches, and nontrivial data dependencies. This gap implies that current models rely more on pattern recognition than on reconstructing true program logic. One representative example is provided in Appendix
F.3
.

Finding 4:

LLMs demonstrate an initial understanding of IR syntax and semantics, yet their outputs often omit critical instructions, oversimplify control flow, and rely on shallow patterns—revealing limited sensitivity to fine-grained semantics and an incomplete grasp of underlying program logic.

true

Approximation in Execution Reasoning

summarizes LLM performance on execution reasoning for both IR and source code. All models complete most tasks successfully, with only one failure from Code Llama on an IR case—indicating that execution reasoning likely processes IR incrementally, step by step, rather than all at once as in structural or syntactic tasks. This interaction style may alleviate token limitations seen in earlier tasks. Despite this, a clear performance gap remains: LLMs consistently perform better on source code, suggesting they are more attuned to high-level constructs. These trends imply that IR-specific training may be essential to close the gap between source-level and IR-level reasoning.

In this task, we observe that LLMs often struggle with complex control flows, leading to inconsistencies between IR and source code execution. These failures reveal that LLMs do not simulate execution instruction by instruction. Instead, they approximate behavior using high-level semantic steps. Analysis of reasoning logs shows that models typically organize their execution into abstract phases—such as function understanding, input analysis, operation planning, and assertion comparison—rather than processing each instruction sequentially. This abstraction introduces gaps when reasoning over control dependencies, particularly in loops or conditionals.

We also observe granularity issues. LLMs can identify overall algorithmic intent (e.g., sorting), but miss critical details. In “CPP_149”, where the program deletes strings of odd length before sorting, the model correctly recognizes sorting but omits the filtering step—changing the outcome.

LLMs approximate program execution through high-level semantic steps rather than faithfully simulating instruction-level behavior, leading to failures in complex control flows.

4.3.2
Heuristic Inference under Uncertainty

Unlike source code, IR lacks explicit variable names and high-level semantics, making execution reasoning more ambiguous. When faced with such uncertainty, LLMs rarely express a lack of understanding. Instead, they often fall back on heuristic strategies—such as inferring behavior from function names or assertion patterns—rather than reasoning from instruction semantics.

This behavior frequently leads to incorrect outcomes. In 35 of 164 GPT-4 cases, we observe such pattern-based guessing. For example, in “CPP_120”, a function named
maximum
leads the model to assume that the IR computes top-
k
elements, even without evidence from the actual IR instructions. Similarly, in “CPP_109”, the model infers that a vector can be sorted through shifts simply because the assertion passes, without reasoning through the IR-defined shift operations.

These failures highlight LLMs’ inability to handle uncertainty in IR reasoning. Even with Chain-of-Thought prompting, models fail to track control flow, variable updates, or simulate intermediate steps. As a result, they often prioritize plausibility over correctness, revealing a fundamental limitation in operational semantic understanding. These behaviors reveal a potential limitation in how LLMs manage uncertainty during IR reasoning—a pattern further discussed in Section
5
.

Finding 6:

When facing ambiguity in IR execution, LLMs often rely on heuristics, such as function names or output patterns, rather than simulating operations, revealing challenges in semantic alignment.

5
Discussion

Our evaluation reveals fundamental challenges in LLMs’ ability to understand and reason over compiler IRs, particularly in control flow, execution semantics, and iterative logic. These difficulties stem from both the intrinsic properties of IRs, such as their verbosity and lack of high-level abstractions, and the limitations of current LLM architectures.

IRs typically produce longer token sequences per function compared to source code, intensifying context length constraints. This not only limits the model’s ability to retain global context but also disrupts its handling of structural dependencies. Even with full context, models frequently fail on tasks that require precise execution tracking or fine-grained semantic reconstruction. GPT-4 outperforms other models across tasks, consistent with prior findings on code understanding
(
Ma et al., 2023
)
, but still falls short on complex control and semantic reasoning.

These findings highlight three key limitations and corresponding opportunities for improvement. First, control flow comprehension remains brittle—LLMs often misrepresent branching and looping behaviors, undermining their structural accuracy. Second, models rely heavily on pattern-based heuristics rather than simulating execution. When uncertain, they infer logic from function names or assertion formats rather than expressing doubt or simulating operations faithfully, indicating a lack of uncertainty modeling in IR reasoning. Third, loop reasoning is particularly weak, with models failing to track induction variables, loop termination, or inter-iteration dependencies. Addressing these limitations may require instruction-level fine-tuning, execution-trace supervision, or uncertainty-aware prompting strategies.

Conclusion and Future Work

This study systematically evaluates the capabilities of LLMs in understanding IRs in compilers, across four dimensions: structural analysis, syntax comprehension, semantic reasoning, and execution simulation. Our findings show that while LLMs can effectively recognize static IR features and basic control flow patterns, they struggle with more complex constructs—particularly loop reasoning, precise control dependencies, and instruction-level execution behavior.
Furthermore, LLMs often omit key instructions during decompilation, misinterpret control structures, and approximate execution in coarse semantic steps rather than performing fine-grained simulation. These limitations contrast sharply with their performance on source-level tasks, suggesting that current models are more attuned to high-level abstractions, supposed to be due to code-centric pretraining.

To advance IR-level understanding, future work should focus on enhancing control flow awareness, developing multi-granularity semantic reasoning capabilities, and improving loop modeling accuracy. Incorporating IR-specific training, optimizing token-efficient IR representations, and leveraging graph-based neural structures may further strengthen LLMs’ ability to reason over IRs. Bridging this gap between source code comprehension and IR analysis is essential for applying LLMs to compiler design, program analysis, and binary understanding tasks.

Impact Statement

This work investigates LLMs’ ability to understand IRs, advancing research in code analysis, optimization, and automated reasoning. It may benefit software reliability, but it also raises concerns about automated program manipulation in security-sensitive contexts. We advocate for further ethical safeguards in applying LLMs to such domains.

Several limitations merit attention. Our study covers a limited set of models and HumanEval-derived IRs, which may not fully reflect the diversity of real-world IRs. While we employ expert meta-prompts, we do not explore advanced prompting techniques, which could affect performance. Moreover, though we identify key challenges in IR comprehension, we do not propose concrete solutions such as IR-specific fine-tuning or dataset augmentation. Future work should expand datasets, include newer models, and explore targeted adaptation strategies to improve LLM performance on both static and dynamic IR tasks.

Appendix B
Discussion on Dataset Scope and Generalizability

Although the HumanEval dataset consists of relatively short source programs (averaging fewer than 10 lines of Python code), their corresponding LLVM IRs exhibit substantial structural and semantic complexity. We selected this dataset to investigate fundamental challenges in LLM-based IR comprehension under controlled conditions. Our rationale is based on the following considerations:

(1) Controlled Complexity.
Despite the brevity of HumanEval source programs, their compiled LLVM IRs contain nontrivial structures—including nested loops, conditional branches, function calls, and memory operations—that typify core IR-level reasoning challenges. This controlled environment allows us to isolate and assess LLMs’ ability to understand structural and semantic aspects of IRs.

(2) Task Difficulty Beyond Code Size.
The difficulty of IR reasoning does not scale linearly with source code length. Even short programs can produce intricate IR patterns that demand nuanced comprehension of control flow, data dependencies, and low-level semantics. Our results show that LLMs often fail to capture these subtleties, despite the apparent simplicity of the original code.

(3) Evidence of Systemic Deficiencies.
Across multiple tasks—including CFG reconstruction, DDG extraction, and symbolic execution—we observe consistent failure patterns across various LLMs. These failures suggest fundamental limitations in LLMs’ ability to reason over IRs, reflecting broader architectural or training shortcomings rather than artifacts of dataset size.

While we agree that future work should expand to larger and more diverse datasets, our findings provide strong empirical evidence of systemic challenges in IR-level reasoning, even in simplified and controlled scenarios.

HumanEval Setups

Building on prior work
(

;
Tan et al., 2024
)

HumanEval, introduced by OpenAI, is a benchmark designed to assess the multilingual capabilities of code-generative models. It comprises 164 carefully handwritten programming challenges, each featuring a function signature, a natural language (NL) description, a function body, and a set of unit tests, with an average of 7.7 assertion statements per challenge
(
Chen et al., 2021
)
. In our experiments, these 164 C++ programs serve as the source code for IR analysis.

The compilation experiments were conducted on a Dell Workstation equipped with 32 Intel(R) Xeon(R) CPUs E5-2620 v4 @ 2.10GHz, running on an x86-64 architecture with a 64-bit system. For these experiments, we used Clang adapted for LLVM 13 on Ubuntu 18.04. The C++ source code were compiled into IRs (.bc files) using the following command:

clang++ -O{Opt-level} -emit-llvm {benchmark}.cpp -S -o {benchmark}.bc

We use LLVM’s built-in passes to generate golden CFGs with the
-dot-cfg
option to ensure accurate and consistent representations of the code structure. The golden code summarization is meticulously performed to ensure that the generated graphs and code representations faithfully reflect the original source code’s semantics. This process is critical for precise evaluations in subsequent tasks, such as static analysis, code summary analysis, and dynamic analysis. By employing these methodologies, we ensure that the golden datasets are of the highest fidelity, providing a solid foundation for assessing the granular understanding and representation of IRs by LLMs.
