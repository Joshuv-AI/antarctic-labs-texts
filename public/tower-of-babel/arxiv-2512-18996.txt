Modular Layout Synthesis (MLS): Front-end Code via Structure Normalization and Constrained Generation
Chong Liu, Ming Zhang, Fei Li, Hao Zhou, Xiaoshuang Chen, Ye Yuan

Abstract
Automated front-end engineering drastically reduces development cycles and minimizes manual coding overhead. While Generative AI has shown promise in translating designs to code, current solutions often produce monolithic scripts, failing to natively support modern ecosystems like React, Vue, or Angular. Furthermore, the generated code frequently suffers from poor modularity, making it difficult to maintain. To bridge this gap, we introduce Modular Layout Synthesis (MLS) , a hierarchical framework that merges visual understanding with structural normalization. Initially, a visual-semantic encoder maps the screen capture into a serialized tree topology, capturing the essential layout hierarchy. Instead of simple parsing, we apply heuristic deduplication and pattern recognition to isolate reusable blocks, creating a framework-agnostic schema. Finally, a constraint-based generation protocol guides the LLM to synthesize production-ready code with strict typing and component props. Evaluations show that MLS significantly outperforms existing baselines, ensuring superior code reusability and structural integrity across multiple frameworks.

Introduction

Background.

Front-end user interface (UI) development remains one of the most time-consuming stages of modern software delivery: developers translate pixel-level designs into hierarchical layouts, pick framework components, and iteratively debug style and structure.
Recent multimodal large language models (MLLMs) and vision-language models (VLMs) have made UI-to-Code feasible by conditioning code generation on screenshots or design mockups
2
;
17
;
10
.
However, a key practical requirement in real engineering settings is
framework-awareness
: production UIs are rarely written as plain HTML/CSS only, but instead rely on component-based ecosystems such as React, Vue, and Angular.

Problem.

Despite strong progress, existing UI-to-Code systems often produce
monolithic
outputs: long flat files where repeated patterns are expanded verbatim, component boundaries are implicit, and reusability is poor
17
;
18
.
Such code is hard to maintain (high duplication, weak typing), hard to reuse (no clean props or loops), and hard to port across frameworks (syntax differences leak throughout the output).
Empirically, even when the rendered UI is visually close, the resulting code can have low structural quality and low component-level reuse.

Prior work.

Prior directions include (i) end-to-end screenshot-to-code models
2
;
11
;
10
,
(ii) prompt-based or divide-and-conquer pipelines
18
,
(iii) layout-guided code generation
20
,
and (iv) benchmarks and evaluation protocols for UI2Code
17
;
7
;
21
.
However, these methods typically couple
layout understanding
,
reuse discovery
, and
framework-specific code emission
in a single step, making it difficult to guarantee modular outputs or portability.

Our solution.

We propose
Modular Layout Synthesis (MLS)
, a hierarchical framework that explicitly decomposes UI-to-Code into three stages:
(1)
visual-to-structure
—a lightweight visual-semantic encoder predicts a coarse DOM-like tree in a constrained serialized format;
(2)
structure normalization and component mining
—deterministic canonicalization and pattern mining isolate reusable blocks and repeated structures into a framework-agnostic intermediate representation (IR);
(3)
constraint-based multi-framework generation
—a framework-conditioned protocol guides an LLM to emit typed components, props, and repeat constructs without expanding duplicates.
We summarize our contributions:

•

We introduce MLS, a modular UI-to-Code framework that separates
layout parsing
,
reuse extraction
, and
framework-specific synthesis
.

•

We propose a normalization and component mining procedure (hashing + clustering + conflict resolution) that yields a portable IR capturing components, repeats, and typed props.

•

We design a constraint-based generation protocol enabling consistent code structure across HTML/React/Vue/Angular, improving portability and reusability in experiments.

3
Approach: Modular Layout Synthesis via Blueprint Compression

3.1
Notation and Output Contract

Let the input screenshot be
s\in\mathbb{R}^{H\times W\times 3}
and the target runtime be

\mu\in\{\textsc{HTML},\textsc{React},\textsc{Vue},\textsc{Angular}\}
.
Our goal is to generate a code bundle
\mathcal{Z}_{\mu}
that (i) visually matches
s
after rendering,
(ii) exposes explicit reusable components with typed properties, and
(iii) preserves repeated structures as loop constructs rather than expanded copies.

MLS is implemented as a three-module factorization:

\mathcal{A}=\Phi_{\alpha}(s),\qquad\Omega=\mathfrak{C}(\mathcal{A}),\qquad\mathcal{Z}_{\mu}=\Psi_{\beta}(\Omega,\mu),

(1)

where
\Phi_{\alpha}
produces a
layout arborescence

\mathcal{A}
,
\mathfrak{C}
compresses it into a
portable blueprint

\Omega
with motifs and typed fields, and
\Psi_{\beta}
realizes framework-specific code under hard constraints.

Layout arborescence.

We represent structure as a rooted ordered arborescence

\mathcal{A}=(\mathcal{V},\mathcal{E},\varrho)
.
Each node
u\in\mathcal{V}
carries a coarse category
c(u)\in\mathcal{G}

and an optional geometry anchor
g(u)\in[0,1]^{4}
(normalized
(x_{0},y_{0},x_{1},y_{1})
):

u\equiv\big(c(u),\,g(u),\,\kappa(u)\big),

(2)

where
\kappa(u)
is a payload placeholder (text/image/link/input etc.) stored out-of-band (Module B).

Portable blueprint.

The intermediate object is

\Omega\triangleq\big(\mathcal{S},\,\mathbb{M},\,\mathbf{X},\,\mathbb{T}\big),

(3)

where
\mathcal{S}
is a rewritten skeleton tree,
\mathbb{M}
is a library of mined motifs (reusable templates),

\mathbf{X}
is a table (or a set of tables) of instance fields for loops/components, and
\mathbb{T}
is a typing environment
(e.g., prop schemas and attribute types).

3.2
Module A: Screen-to-Arborescence Transduction

Module A predicts
\mathcal{A}
from screenshot
s
using a vision-semantic encoder-decoder.

Constrained serialization.

We encode
\mathcal{A}
into a bracketed topology string
\operatorname{br}(\mathcal{A})

that is guaranteed to parse under a simple grammar (balanced braces, fixed keys).
The generator defines an autoregressive distribution:

p_{\alpha}\big(\operatorname{br}(\mathcal{A})\mid s\big)=\prod_{t=1}^{T}p_{\alpha}\big(w_{t}\mid w_{<t},s\big),

(4)

where
w_{t}
is the
t
-th token of the serialization.

Geometry-aware objective.

Given training pair
(s,\mathcal{A}^{\star})
, we minimize

\mathcal{J}_{\mathrm{A}}(\alpha)=\underbrace{\sum_{t=1}^{T^{\star}}\big(-\log p_{\alpha}(w_{t}^{\star}\mid w_{<t}^{\star},s)\big)}_{\text{topology token loss}}+\lambda_{g}\underbrace{\sum_{u\in\mathcal{V}^{\star}}\ell_{\mathrm{box}}(g(u),g^{\star}(u))}_{\text{geometry loss}}+\lambda_{r}\underbrace{\sum_{u\in\mathcal{V}}\mathbf{1}\{\mathrm{area}(g(u))<\epsilon\}}_{\text{noise regularizer}},

(5)

where
\ell_{\mathrm{box}}
can be
\ell_{1}
or
(1-\mathrm{IoU})
, and the last term discourages tiny spurious nodes.

Stability constraints.

To make the downstream deterministic compression robust, we enforce a coarse vocabulary:

\mathcal{G}=\{\texttt{wrap},\texttt{row},\texttt{col},\texttt{text},\texttt{media},\texttt{ctl},\texttt{link}\}.

(6)

We also prune by depth and area:

\mathcal{V}\leftarrow\{u\in\mathcal{V}:\ \mathrm{depth}(u)\leq d_{\max}\ \wedge\ \mathrm{area}(g(u))\geq a_{\min}\}.

(7)

3.3
Module B: Blueprint Compression with Motif Harvesting

Module B converts
\mathcal{A}
into a framework-agnostic blueprint
\Omega
by (i) canonicalizing order and payload,
(ii) discovering repeated substructures (motifs), and (iii) inducing typed component schemas.

3.3.1
B.1 Canonical skeletonization and payload ledger

We split structure vs. content via

(\hat{\mathcal{A}},\ \mathcal{L})=\operatorname{Skel}(\mathcal{A}),

(8)

where
\hat{\mathcal{A}}
is a
skeleton
with all literal payloads replaced by typed holes,
and
\mathcal{L}
is a
payload ledger
that stores the removed literals keyed by canonical paths.

Canonical sibling order.

For a node
u
with children
(v_{1},\dots,v_{m})
, we reorder children by reading order:

(v_{1},\dots,v_{m})\leftarrow\operatorname{sort}\Big((v_{1},\dots,v_{m});\ \big(y_{c}(g(v)),x_{c}(g(v))\big)\Big),

(9)

where
(x_{c}(\cdot),y_{c}(\cdot))
is the box center. This ensures deterministic serialization for isomorphic subtrees.

Ledger addressing.

Let
\chi(u)
be the canonical path of node
u
after ordering (sequence of child indices).
We store payload attributes (e.g., text string, src, href, placeholder):

\mathcal{L}[\chi(u)]\triangleq\mathrm{payload}(u).

(10)

3.3.2
B.2 Motif fingerprints and near-match unification

We compute bottom-up fingerprints on the skeleton
\hat{\mathcal{A}}
.
Let
\zeta(u)
be a normalized node label (category + role tag):

\zeta(u)\triangleq\big(c(u),\ \rho(u)\big).

(11)

Define the digest
d(u)
recursively:

d(u)=\mathcal{H}\!\left(\zeta(u)\ \|\ d(\mathrm{ch}_{1}(u))\ \|\ \cdots\ \|\ d(\mathrm{ch}_{m}(u))\right),

(12)

where
\mathcal{H}
is a fixed hash, and
\mathrm{ch}_{i}(u)
are children after canonical sort.

Near-match signature.

Exact hashes miss “almost same” motifs (e.g., extra icon node). We therefore compute a lightweight signature

\sigma(u)\in\mathbb{R}^{p}
as a normalized histogram of labels in the subtree:

\sigma(u)=\frac{1}{Z(u)}\sum_{w\in\mathrm{sub}(u)}\mathbf{e}_{\zeta(w)},\qquad Z(u)=|\mathrm{sub}(u)|.

(13)

We merge motifs if cosine similarity exceeds threshold
\eta
:

\mathrm{sim}(u,v)=\frac{\langle\sigma(u),\sigma(v)\rangle}{\|\sigma(u)\|_{2}\|\sigma(v)\|_{2}}\geq\eta.

(14)

3.3.3
B.3 Template induction and typed field schemas

A motif cluster
\mathcal{Q}=\{u_{1},\dots,u_{k}\}
defines a reusable template
\mathfrak{m}_{\mathcal{Q}}
.
We create
holes
for varying payload positions and produce an instance table
\mathbf{X}_{\mathcal{Q}}
:

Hole collection.

Let
\mathcal{Holes}(\mathcal{Q})
be the set of ledger keys inside the motif where values differ across instances.
For each hole
h\in\mathcal{Holes}(\mathcal{Q})
, we gather observed values

\mathcal{U}_{h}=\{\mathcal{L}[\chi_{h}(u_{i})]\}_{i=1}^{k}.

(15)

Deterministic type assignment.

We infer a field type via a rule-based classifier
\operatorname{Type}(\cdot)
:

\tau(h)=\operatorname{Type}(\mathcal{U}_{h})\in\{\texttt{Str},\texttt{Num},\texttt{Bool},\texttt{Url},\texttt{Enum}\}.

(16)

This induces a prop schema for the motif:

\mathbb{T}(\mathfrak{m}_{\mathcal{Q}})=\{(h,\tau(h)):\ h\in\mathcal{Holes}(\mathcal{Q})\}.

(17)

Instance table.

We pack per-instance values into a table
\mathbf{X}_{\mathcal{Q}}\in\mathbb{D}^{k\times|\mathcal{Holes}|}
:

\mathbf{X}_{\mathcal{Q}}[i,h]=\mathcal{L}[\chi_{h}(u_{i})].

(18)

The complete motif library is
\mathbb{M}=\{\mathfrak{m}_{j}\}
and tables
\mathbf{X}=\{\mathbf{X}_{j}\}
.

3.3.4
B.4 Non-overlap selection as weighted packing

Motifs may overlap (nested candidates). We select a consistent set by weighted packing.
Each candidate motif
j
has occurrences
\mathcal{O}_{j}
and a size
\mathrm{sz}(j)=|V(\mathfrak{m}_{j})|
.
We define a compression score:

w(j)\triangleq(|\mathcal{O}_{j}|-1)\cdot\mathrm{sz}(j)-\gamma,

(19)

and solve the set packing (NP-hard) approximately by greedy:

\max_{\mathbf{z}\in\{0,1\}^{J}}\sum_{j=1}^{J}w(j)z_{j}\quad\text{s.t.}\quad z_{j}+z_{j^{\prime}}\leq 1\ \text{if}\ \mathcal{O}_{j}\cap\mathcal{O}_{j^{\prime}}\neq\emptyset.

(20)

We sort candidates by
w(j)
and insert if it does not conflict, yielding the final skeleton
\mathcal{S}
with

macro
and
loop
nodes.

Algorithm 1

Blueprint Compression
\mathfrak{C}(\mathcal{A})
(Module B)

1:

(\hat{\mathcal{A}},\mathcal{L})\leftarrow\operatorname{Skel}(\mathcal{A})

2:

canonical-sort siblings by box-center order

3:

compute digests
d(\cdot)
by Eq. (
12
)

4:

build clusters by exact
d(\cdot)
, then merge by Eq. (
14
)

5:

induce motifs
\mathbb{M}
and tables
\mathbf{X}
; infer types via Eq. (
16
)

6:

score candidates by Eq. (
19
) and greedily solve Eq. (
20
)

7:

rewrite skeleton into
\mathcal{S}
with
macro
/
loop
; build typing env
\mathbb{T}

8:

return

\Omega=(\mathcal{S},\mathbb{M},\mathbf{X},\mathbb{T})

3.4
Module C: Constraint-Driven Multi-Framework Realization

Module C realizes
\Omega
into framework-specific code
\mathcal{Z}_{\mu}
using an LLM under a hard protocol.

3.4.1
C.1 Realization map

We define a deterministic realization map
\pi_{\mu}
that translates blueprint nodes to framework constructs:

\pi_{\mu}:\ \{\texttt{wrap,row,col,text,media,ctl,link,macro,loop}\}\rightarrow\Lambda_{\mu}.

(21)

In particular, loops are realized natively:

\texttt{loop}\Rightarrow\begin{cases}\texttt{\lx@text@lbrace items.map((it)=\!>\!\ldots)\lx@text@rbrace},&\mu=\textsc{React},\\
\texttt{v-for="it in items"},&\mu=\textsc{Vue},\\
\texttt{*ngFor="let it of items"},&\mu=\textsc{Angular},\\
\texttt{(fallback) replicate nodes},&\mu=\textsc{HTML}.\end{cases}

3.4.2
C.2 Hard constraints as admissible-token filtering

Let the LLM emit a token sequence
y_{1:T}
describing a set of files
\mathcal{Z}_{\mu}
under a file-block protocol.
At decoding step
t
, we restrict tokens to an admissible set:

\mathcal{V}_{t}=\mathcal{V}^{\text{gram}}_{t}\cap\mathcal{V}^{\text{bind}}_{t}\cap\mathcal{V}^{\text{type}}_{t},

(22)

where:

•

\mathcal{V}^{\text{gram}}_{t}
enforces grammar/file-block structure and balanced tags,

•

\mathcal{V}^{\text{bind}}_{t}
enforces that every field in
\mathbf{X}
is consumed by exactly one prop binding,

•

\mathcal{V}^{\text{type}}_{t}
enforces prop types from
\mathbb{T}
(e.g.,
Url
only in
src/href
).

Decoding becomes

y_{t}\sim p_{\beta}(\cdot\mid y_{<t},\Omega,\mu)\ \text{masked to}\ \mathcal{V}_{t}.

(23)

3.4.3
C.3 Typed component contract

For each motif
\mathfrak{m}_{j}\in\mathbb{M}
, Module C emits a component signature

\operatorname{Sig}_{\mu}(\mathfrak{m}_{j})
.
For React, for instance:

\operatorname{Props}_{j}=\{(h:\tau(h))\}_{h\in\mathcal{Holes}(\mathfrak{m}_{j})},\quad\texttt{function }\mathrm{Comp}_{j}(\operatorname{Props}_{j})\{\dots\}.

(24)

Analogous contracts are produced for Vue/Angular with typed bindings.

Complexity.

Digest computation is linear in nodes:
O(|\mathcal{V}|)
.
Near-merge is bounded within sibling scopes and capped per bucket, giving near-linear behavior in practice.

5
Broader Impact

Automated UI-to-Code can democratize software creation and reduce repetitive engineering work, but may also lower barriers for producing deceptive web content at scale.
MLS emphasizes modular, auditable code structure and deterministic intermediate representations, which can support review and governance.
Future work should incorporate watermarking, safety filters, and provenance tracking for generated interfaces.

6
Conclusion

We presented MLS, a modular UI-to-Code framework that separates visual parsing, deterministic component mining, and constrained multi-framework generation.
By explicitly extracting reusable components and enforcing typed bindings, MLS improves code reusability, portability across React/Vue/Angular, and structural integrity.
We hope MLS encourages a shift from monolithic UI code generation toward component-oriented, maintainable synthesis.
