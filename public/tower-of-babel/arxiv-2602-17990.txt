WorkflowPerturb : Calibrated Stress Tests for Evaluating Multi-Agent Workflow Metrics
Madhav Kanda, Pedro Las-Casas, Alok Gautam Kumbhare, Rodrigo Fonseca, Sharad Agarwal

Abstract
LLM-based systems increasingly generate structured workflows for complex tasks. In practice, automatic evaluation of these workflows is difficult, because metric scores are often not calibrated, and score changes do not directly communicate the severity of workflow degradation. We introduce WorkflowPerturb , a controlled benchmark for studying workflow evaluation metrics. It works by applying realistic, controlled perturbations to golden workflows. WorkflowPerturb contains 4,973 golden workflows and 44,757 perturbed variants across three perturbation types (Missing Steps, Compressed Steps, and Description Changes), each applied at severity levels of 10%, 30%, and 50%. We benchmark multiple metric families and analyze their sensitivity and calibration using expected score trajectories and residuals. Our results characterize systematic differences across metric families and support severity-aware interpretation of workflow evaluation scores. Our dataset will be released upon acceptance.

Introduction

Large Language Models (LLMs) are increasingly used to generate multi-step, dependency-rich workflows for high-stakes settings, where failures can have real operational or scientific consequences. Such workflows now appear in scientific automation, biomedical information access, enterprise copilots, and cloud and DevOps assistants

. In these settings, correctness depends not only on wording but on ordered dependencies and the presence of critical steps.

Evaluating these workflows remains unexpectedly difficult. Existing workflow metrics each capture only a narrow slice of correctness: lexical metrics fail under paraphrasing, structural metrics may overlook semantic drift, and semantic metrics can assign favorable scores to workflows missing critical steps. A central practical challenge is calibration: it is often unclear what a score means in terms of functional risk. For example, does a drop from 0.90 to 0.84 reflect harmless rephrasing or the loss of an essential dependency? Without calibrated interpretation, metric values are difficult to use for regression testing, model comparison, or automated filtering.

With the widespread deployment of LLM-generated workflows in industry, incorrect or degraded workflows can have severe consequences. In cloud and DevOps settings, flawed orchestration may lead to outages or misconfigured infrastructure; in scientific and biomedical domains, subtle workflow deviations can alter analytical conclusions. Production systems are also dynamic: models are deprecated and upgraded, for example under Azure OpenAI model retirement policies

, orchestration libraries evolve, and engineers revise prompts and agent definitions. Each such change may alter workflow structure or semantics. This raises a core practical question: how can we determine whether a modified workflow remains functionally equivalent to a validated reference? How can such checks be integrated into CI/CD pipelines without manual review? At the heart of this problem lies reliable workflow evaluation.

To make this concrete, consider a validated production workflow for deploying a service, including resource provisioning, access controls, deployment, and observability configuration. An LLM-generated workflow may preserve terminology while omitting access hardening, compressing observability into a vague step, or reordering dependencies. Many metrics still assign high scores due to surface overlap or coarse structural similarity, leaving engineers uncertain whether deviations are benign or dangerous.

To address these challenges, we introduce
WorkflowPerturb
, a benchmark of over 44,000 workflows constructed through controlled perturbations. We generate three perturbation types, Missing Steps, Compressed Steps, and Description Changes, each applied at graded intensity levels of 10%, 30%, and 50%. These structured degradations enable systematic analysis of metric calibration under known severity, revealing which metrics are robust to benign edits, which fail under functional degradation, and how workflow scores can be interpreted more reliably in production settings.

2
Related Work

Agentic evaluation and tool-use benchmarks.

Recent work has focused on evaluating large language models in agentic and tool-using settings, where models must select, invoke, and sequence external functions. The Berkeley Function Calling Leaderboard (BFCL)
10
provides a standardized benchmark for evaluating LLMs on realistic function-calling tasks, emphasizing correctness of tool selection, and execution outcomes, and moving beyond single-turn generation to end-to-end task success in tool-augmented environments. While BFCL evaluates agent performance through execution success, it does not study how automatic evaluation metrics behave under different types or severities of workflow degradation.

Diagnosing agent failures from execution traces.

Several recent approaches analyze execution trajectories to diagnose and localize agent failures. AGENTRX
1
examines agent execution traces consisting of intermediate actions, tool calls, and environment feedback to identify failure causes and error propagation. TRAIL
4
similarly uses trace-based reasoning over structured action sequences and intermediate states to localize issues in agent execution. These methods operate on runtime execution traces and assume access to environment interactions and task outcomes. Our setting differs in that we do not rely on execution traces or success signals; instead, we study static workflow representations and evaluate how automatic metrics respond when workflows deviate from golden references in controlled and graded ways, enabling systematic analysis of metric calibration, sensitivity, and blind spots.

We model a workflow as a directed acyclic graph (DAG)
G=(V,E)
, where each node
v\in V
represents a step described in natural language and each edge
(u,v)\in E
denotes a precedence constraint. Given a golden workflow
G
and a candidate workflow
G^{\prime}
, an evaluation metric produces a score
s(G,G^{\prime})\in[0,1]
(or a normalized variant) intended to reflect workflow quality or similarity. Rather than proposing a new workflow generator, our focus is to analyze
metric behavior
: under controlled degradations of known severity, do metric scores change in an interpretable and calibrated manner? We study this question by introducing structured perturbation types, graded severity levels, and an expected score trajectory that characterizes how an ideal metric should respond as workflow quality degrades

3.1
Benchmark Construction

Source Data.

We begin with the set of workflows in WORFBENCH
11
and retain those with
\lvert V\rvert\geq 5
nodes. This threshold ensures each workflow has enough steps to meaningfully perturb and evaluate metric sensitivity.

Perturbation Patterns.

Through exploratory analysis of LLM-generated workflows, we identified several issues that degrade workflow quality, among which three recurring patterns emerged. We model these patterns as controlled perturbations applied to golden-standard workflows:

•

Missing Steps:
LLM-generated workflows often omit essential actions that are required for complete task execution.
Such omissions result in incomplete or truncated execution paths when compared to the golden workflow.

•

Compressed Steps:
Generated workflows frequently contain fewer nodes than their golden counterparts, condensing multiple fine-grained actions into a single broader step.
While this may preserve most of the content, it alters the structural properties of the workflow and leads to mismatches under graph-based evaluation.

•

Description Changes:
Even when workflows preserve the correct structure, step descriptions often differ syntactically from the golden reference.
This creates lexical variation that can confuse surface-level metrics while retaining semantic meaning.

Figure 2:
Visualization of
Missing Steps
perturbations applied to the six-node blog generation workflow.
At each level, a proportional number of nodes is randomly dropped: 1 node (10%), 2 nodes (30%), and 3 nodes (50%).
Higher perturbation levels result in increasingly incomplete workflows that diverge from the golden sequence.

Functional Implications of Perturbations.

Although
WorkflowPerturb
evaluates static workflow representations, the perturbations are designed to reflect realistic failure modes with potential execution-level consequences. Missing steps may eliminate required actions, leading to incomplete or failed task execution. Compressed steps can merge distinct tool invocations or dependency boundaries, potentially altering execution order or granularity. In contrast, description changes preserve structural dependencies but may introduce semantic ambiguity. Our objective is to study how automatic metrics respond to these controlled degradations; evaluating their downstream execution impact is complementary future work.

To systematically study the impact of these issues on evaluation metrics, we apply each perturbation type at three severity levels
\{10\%,30\%,50\%\}
of the nodes in the golden workflow are affected as illustrated in Figure
2
. These graded levels not only mimic realistic variations observed in practice but also allow us to probe the calibration of metrics, i.e., whether metric scores degrade proportionally with increasing perturbation severity.

Perturbation Generation and Validation.

For each workflow and perturbation configuration, we employ large language models to generate variants. To ensure correctness, each variant undergoes automated static validation checks:

•

Node Count Consistency:
Given a golden workflow with 10 nodes, applying a 10% removal perturbation must produce a workflow with precisely 9 nodes. Any deviation from this expected count is flagged as inconsistent. The nodes selected for removal are chosen randomly.

•

Change Count Verification:
For a
30\%
perturbation, exactly
3
nodes must be altered, either removed, compressed, expanded, or paraphrased. If fewer or more nodes are modified, the output is rejected. For removal and compression operations, the results are verified by comparing the number of nodes before and after the perturbation. For paraphrasing, we explicitly pass the specific nodes to be paraphrased to ensure that exactly the required number of nodes are modified.

These checks target the two most common generation failure modes: (i) deleting or merging too many nodes, and (ii) over- or under-applying paraphrasing. All prompt templates used in this stage along with our iterative refinement strategy are documented in Appendix
A
.

Structured Paraphrasing for Description Changes.

For the description-change perturbation, we do not rely on unconstrained paraphrasing, which often introduces hallucinations. Instead, we explicitly pre-select
\alpha\times|V_{\text{golden}}|
nodes (where
\alpha\in\{0.1,0.3,0.5\}
) for paraphrasing. The model is instructed to only rephrase the text of those nodes without adding or removing factual content. For example, a step such as
“Check server logs for errors”
may be paraphrased to
“Inspect the server log files for error entries”
, while the graph structure and node set remain unchanged.

Dataset Statistics.

The final
WorkflowPerturb
corpus contains approximately 4,973 golden workflows, and
44{,}757
perturbed variants spanning three perturbation patterns and three severity levels. All variants pass automated validation, and a subset was manually inspected to verify perturbation correctness.

Score Assignment and Perturbation Alignment.

Each workflow is assigned a score reflecting perturbation severity, with lower scores indicating deviation from the golden workflow. For
Missing Steps
and
Compressed Steps
, the score equals the remaining workflow fraction, computed as
1-p
for perturbation percentage
p
(e.g.,
p{=}30\%\rightarrow 0.7
,
p{=}50\%\rightarrow 0.5
). In the case of Compressed Steps, this decrease is justified by the loss of structural granularity: multiple fine-grained actions (often corresponding to distinct tool invocations) are merged into broader nodes, violating the one-tool-per-step abstraction and reducing fidelity to the golden execution graph. For
Description Changes
, the score remains constant across severity levels, since these edits affect only textual descriptions and not the underlying workflow structure.

4
Metrics

We evaluate seven metrics spanning structural, lexical, semantic, order-based, and judgment-based families. Structural metrics (Graph F1, Chain F1) measure topological consistency via subgraph matching and sequence alignment. Lexical metrics (BLEU, GLEU) compute n-gram overlap. BERTScore measures contextual embedding similarity. Kendall’s
\tau
evaluates rank-order consistency. LLM-as-Judge provides rubric-based holistic assessment. Full definitions are provided in Appendix
B
.

4.1
Structural Metrics

Chain F1.

Following
11
, predicted node chains are aligned with valid topological orderings of the golden workflow, and the longest increasing subsequence (LIS) is computed. Precision and recall are defined as

p_{\text{chain}}=l/|V_{\text{pred}}|
and

r_{\text{chain}}=l/|V_{\text{golden}}|
,
where
l
is the LIS length. The final score is their harmonic mean (F1).

Graph F1.

The predicted and golden workflow graphs are aligned using a Maximum Common Induced Subgraph (MCIS) algorithm. If the largest shared subgraph contains
k
nodes, precision and recall are defined as

p_{\text{graph}}=k/|V_{\text{pred}}|
and

r_{\text{graph}}=k/|V_{\text{golden}}|
. The score is their harmonic mean (F1).

4.2
Lexical Metrics

BLEU

9

is a precision-oriented
n
-gram matching metric with a brevity penalty, while

GLEU

8

balances
n
-gram precision and recall and is more robust for shorter or paraphrased step descriptions.

4.3
Semantic Metric

BERTScore

13

compares contextual embeddings of step descriptions from pretrained transformer models and computes precision, recall, and F1 via token-level cosine similarity.

4.4
Ordering Metric

Kendall’s
\tau

6

measures rank correlation between generated and gold step orderings, defined as

\tau=(C-D)/\bigl(\tfrac{1}{2}n(n-1)\bigr)
,
where
C
and
D
are the numbers of concordant and discordant pairs among
n
aligned steps. Scores range from
-1
to
1
.

4.5
LLM-as-Judge

To complement automatic metrics, we use an
LLM-as-Judge
evaluation with GPT-4o (Azure OpenAI). The model is prompted with the task description, golden workflow, generated workflow, and a rubric defining 0–5 scores covering correctness, completeness, ordering, and clarity, with anchor examples.

5
Results and Analysis

We evaluate metric behavior across perturbation types and severities, assigning each workflow a predefined degradation score for interpretability. All reported
LLM-as-Judge
scores are linearly normalized from the original 0–5 scale to the [0,1] range for comparability across metrics.

Overall trends.

Across all perturbation types, metric scores generally decrease as perturbation severity increases, confirming that the benchmark introduces progressively harder deviations from the golden workflows. However, degradation patterns differ substantially across metric families. Structural metrics (Graph F1, Chain F1) track structural distortions closely, lexical metrics (BLEU, GLEU) are highly sensitive to token-level variation, embedding-based similarity (BERTScore) is less sensitive to structural perturbations because it does not directly encode graph completeness, while ordering-based metrics (Kendall’s
\tau
) mainly change when perturbations alter relative step precedence (e.g., via compression or deletion). LLM-as-Judge captures broader notions of functional correctness and completeness.

Overall, no single metric captures all failure modes. Structural metrics reliably detect missing or compressed steps but remain insensitive to purely textual edits, whereas lexical metrics are highly responsive to paraphrasing yet can over-penalize structural deletions. Embedding-based and judgment-based metrics provide complementary signals with distinct calibration properties. A more detailed sensitivity analysis is provided in Appendix

6
Key Insights and Practical Guidance

Workflow validation under change.

In industrial settings, workflows frequently evolve due to model upgrades, prompt revisions, or orchestration library changes. Our results show that different metric families respond differently to structural versus textual changes. Structural metrics are reliable indicators of missing or compressed steps, making them suitable for detecting functional regressions when workflows are modified. Lexical metrics detect paraphrasing but may over-penalize deletions. LLM-as-Judge provides a holistic signal aligned with perceived workflow quality but introduces variance. These distinctions are critical when validating workflow updates.

CI/CD integration.

WorkflowPerturb enables severity-aware calibration of evaluation metrics, allowing practitioners to interpret scores relative to expected degradation patterns. In a CI/CD pipeline, candidate workflows generated after model or orchestration updates can be compared against approved golden workflows using a calibrated metric bundle. Deviations beyond empirically validated thresholds can automatically trigger review or rollback. By understanding which metrics are sensitive to which failure modes, automated validation pipelines can be configured to prioritize structural regressions while tolerating benign paraphrasing.

Metric selection in practice.

No single metric suffices across all perturbation types. We recommend reporting a compact bundle of complementary metrics and interpreting them jointly with respect to perturbation severity. WorkflowPerturb provides a controlled testbed for selecting and calibrating such metric bundles before deployment.

7
Conclusion

We introduced
WorkflowPerturb
, a benchmark for evaluating workflow evaluation metrics under controlled structural and textual perturbations. Our analysis reveals that commonly used metrics exhibit distinct sensitivity patterns and calibration gaps across failure modes. These findings highlight the importance of severity-aware interpretation when validating workflow updates in production systems. By enabling calibration and metric selection, WorkflowPerturb provides practical support for automated workflow validation in CI/CD pipelines and evolving LLM-driven platforms.

Appendix A
Prompt Templates

The following prompts were used to generate perturbed workflow variants. Placeholders in curly braces {} denote the specified perturbation type or severity level.

A.1
Missing Step Prompt

Given the following workflow, please
remove exactly {10%, 30%, 50%}
of its steps.
Return only the modified workflow as a numbered list of steps, preserving the order of the remaining steps.
Do not add or paraphrase any content.

A.2
Compressed Step Prompt

Given the following workflow, please
merge consecutive steps until exactly {10%, 30%, 50%}
of the original steps are merged.
Each merged step should concisely describe the actions of the combined steps.
Return only the modified workflow as a numbered list of steps.
Do not remove or paraphrase steps outside the merged groups.

A.3
Description Change Prompt

Given the following workflow, please
paraphrase the descriptions of exactly {10%, 30%, 50%}
of its steps.
Ensure that the meaning of each paraphrased step remains unchanged.
Do not remove, merge, or add any steps.
Return only the modified workflow as a numbered list of steps.

A.4
Iterative Refinement Prompt (Error Injection)

When a generated output fails validation, we re-inject the error message into the prompt. For example:

Your output had 8 nodes instead of 9 for a 10% removal.
Please regenerate the workflow and ensure that exactly one node is removed.
Return only the modified workflow as a numbered list of steps.

This process is repeated up to three times per model before escalation to a stronger model.

A.5
Iterative Refinement and Escalation

Variants failing validation enter a feedback-driven refinement loop. The validation error is explicitly injected back into the next prompt. For example:

“Your output had 8 nodes instead of 9 for a 10% removal. Please regenerate the workflow and ensure exactly one node is removed.”

If the corrected output again fails validation (e.g., paraphrased 4 nodes instead of 3), the process is repeated up to three times. After three unsuccessful iterations, the task is escalated to a more reliable generation method.

Appendix B
Detailed Metric Definitions

We present the formal definitions and implementation details of all evaluation metrics used in
WorkflowPerturb
. Where applicable, we include equations and illustrative examples showing how the scores are computed.

B.1
Chain F1

Suppose the predicted node chain is
C(V^{p})
and the gold workflow graph is
G(V^{g},E^{g})
.
From
G
, we can enumerate all possible topological orderings
\{C(V^{g})_{1},C(V^{g})_{2},\ldots\}
.
The predicted chain is compared against each ordering using the
Longest Increasing Subsequence (LIS)
:

l_{i}=\text{LIS}(C(V^{g})_{i},C(V^{p})),

and the longest valid subsequence length is taken as

l=\max(|l_{1}|,|l_{2}|,\ldots,|l_{n}|).

Precision and recall are then

p_{\text{chain}}=\frac{l}{|V^{p}|},\qquad r_{\text{chain}}=\frac{l}{|V^{g}|},

yielding

f_{1}^{\text{chain}}=\frac{2\,p_{\text{chain}}\,r_{\text{chain}}}{p_{\text{chain}}+r_{\text{chain}}}.

B.2
Graph F1

Given predicted graph
G(V^{p},E^{p})
and gold graph
G(V^{g},E^{g})
, we compute the Maximum Common Induced Subgraph (MCIS):

\displaystyle G_{mcis}(V_{mcis},E_{mcis})

\displaystyle=\text{MCIS}\!\Big(G(V^{p},E^{p}),

\displaystyle G(V^{g},E^{g})\Big).

If the largest matched subgraph contains
k=|V_{mcis}|
nodes, then

p_{\text{graph}}=\frac{k}{|V^{p}|},\qquad r_{\text{graph}}=\frac{k}{|V^{g}|},

and the final score is

f_{1}^{\text{graph}}=\frac{2\,p_{\text{graph}}\,r_{\text{graph}}}{p_{\text{graph}}+r_{\text{graph}}}.

This procedure captures both node correctness and edge consistency, providing a stricter evaluation than simple edge overlap.

B.3
BLEU and GLEU

BLEU
9
measures n-gram precision between candidate and gold step descriptions, with a brevity penalty to discourage very short outputs. GLEU
12
balances precision and recall over n-grams, making it more robust to short sequences. Both are computed at the step-text level and then averaged across workflows.

B.4
BERTScore

BERTScore
13
computes similarity between candidate and gold step texts using contextual embeddings (we use
all-mpnet-base-v2
). For each candidate token, the maximum cosine similarity with gold tokens is taken, yielding precision, recall, and F1. Scores are averaged across workflow steps.

B.5
Kendall’s
\tau

Kendall’s
\tau

6
measures the ordinal correlation between two ranked lists. For workflows, we treat the step ordering as a ranking and compute

\tau=\frac{C-D}{\tfrac{1}{2}n(n-1)},

where
n
is the number of aligned steps being compared, and
C
and
D
denote the numbers of concordant and discordant step pairs, respectively.
\tau
ranges from
-1
(complete disagreement) to
1
(perfect agreement).

B.6
LLM-as-Judge Prompts

For the LLM-as-Judge evaluation, we designed a rubric-based prompt that instructs the model to compare a generated workflow against a gold reference.
Workflows are formatted with explicit node and edge lists.

B.6.1
Rubric

•

0 = Completely Incorrect or Irrelevant

•

1 = Major Flaws (breaks core logic)

•

2 = Significant Issues (omits several key steps or adds wrong steps)

•

3 = Noticeable Errors (minor reorder or one extra/missing non-critical step)

•

4 = Very Good (only one minor step missing)

•

5 = Perfect Match (fully adheres, detailed, accurate)

B.6.2
Anchor Examples

We provide concrete anchors to calibrate the model’s scoring:

•

Example A (Score 4): Workflow missing one minor step.

•

Example B (Score 5): Workflow perfectly matches the gold.

•

Example C (Score 3): Workflow with minor reordering of steps.

•

Example D (Score 2): Workflow with extra irrelevant steps.

•

Example E (Score 0): Workflow completely incorrect relative to task.

B.6.3
Prompt Format

The model is instructed to:

1.

List nodes and edges from both workflows.

2.

Match nodes by content.

3.

Identify missing, extra, or reordered steps.

4.

Assign an initial score using the rubric.

5.

Perform a self-check: confirm if the initial score strictly follows the rubric.

6.

Adjust to a final score if necessary.

B.6.4
Expected Output

The model must return exactly one JSON object with the fields:

{
"ThoughtChain": "<step-by-step reasoning>",
"initial_score": <int 0–5>,
"self_check": {
"consistent": "Yes"|"No",
"final_score": <int 0–5>
},
"justification": "<one-sentence summary>"
}

B.6.5
Implementation Notes

We use GPT-4o via Azure OpenAI with temperature 0.0 to minimize randomness.
Each workflow pair is evaluated across multiple prompt templates, and scores are averaged to reduce variance.

C.1
Sensitivity Analysis

To quantify how rapidly each metric’s score degrades as perturbation severity increases, we define the
sensitivity
of metric
m
to leverage all available perturbation levels:

\displaystyle\Delta_{m}^{\text{avg}}

\displaystyle=\frac{1}{2}\Bigg[\frac{\bar{s}_{m}(10\%)-\bar{s}_{m}(30\%)}{0.20}

(1)

\displaystyle+\frac{\bar{s}_{m}(30\%)-\bar{s}_{m}(50\%)}{0.20}\Bigg]

where
\bar{s}_{m}(\alpha)
denotes the mean score of metric
m
at
\alpha
% perturbation (see Tables
1
,
2
,
3
).
This formulation averages the degradation rates across both the 10
\rightarrow
30% and 30
\rightarrow
50% intervals, providing a more stable and representative estimate of how sensitively each metric responds to perturbations.
By considering multiple intervals,
\Delta_{m}^{\text{avg}}
mitigates the effect of local non-linearities or noise and yields a smoother measure of robustness.
