Next Generation Cloud-native In-Memory Stores: From Redis to Valkey and Beyond
Carl-Johan F.M af Rosenschöld, Feras M. Awaysheh, Ahmad Awad

Abstract
In-memory key-value datastores have become indispensable building blocks of modern cloud-native infrastructures, yet their evolution faces scalability, compatibility, and sustainability constraints. The current literature lacks an experimental evaluation of state-of-the-art tools in the domain. This study addressed this timely gap by benchmarking Redis alternatives and systematically evaluating Valkey, KeyDB, and Garnet under realistic workloads within Kubernetes deployments. The results demonstrate clear trade-offs among the benchmarked data systems. Our study presents a comprehensive performance and viability assessment of the emerging in-memory key-value stores. Metrics include throughput, tail latency, CPU and memory efficiency, and migration complexity. We highlight trade-offs between performance, compatibility, and long-term viability, including project maturity, community support, and sustained development.

Related Work

The evaluation of in-memory databases
García-Muñoz et al. 2024
and in particular Redis alternatives has gained significant attention in recent years. This section reviews existing benchmarking studies, performance evaluation methodologies, and recent work on Redis alternatives.

Traditional Redis benchmarking studies have primarily focused on single-system optimization and comparison with other database technologies. Cao et al.
Cao et al. 2016
conducted one of the early comprehensive evaluations of NoSQL systems, including Redis, using the Yahoo! Cloud Serving Benchmark (YCSB). Their work established baseline performance characteristics but predated the emergence of modern Redis alternatives. Recent industry benchmarking efforts have employed more sophisticated methodologies. The memtier_benchmark tool
5
5

5

https://github.com/RedisLabs/memtier_benchmark
developed by Redis Inc. has become the de facto standard for Redis performance evaluation. This tool supports precise workload control, including read/write ratios and concurrency levels, making it particularly suitable for realistic performance assessment.

Academic research has established several key principles for in-memory database benchmarking. Chaudhari et al.
Chaudhari et al. 2025
recently presented a comprehensive study of persistence techniques of in-memory databases, emphasizing the importance of realistic workload simulation and multi-dimensional performance metrics. Their work highlights the critical role of recovery time and system efficiency under memory constraints. The use of Zipfian distributions for key access patterns has become standard practice in in-memory database benchmarking. Yang et al.
Yang et al. 2021
analyzed hundreds of cache clusters at X (formerly Twitter) and found that key-access patterns frequently follow Zipfian distributions with skew parameters
\alpha=1.4
for read-heavy workloads and
\alpha=0.9
for write-heavy workloads.

Technical comparisons have highlighted architectural differences between alternatives. Valkey’s enhanced I/O multithreading represents a significant departure from Redis’s single-threaded model, with reports of up to 1.19 million requests per second
Linux Foundation 2024
. Garnet’s implementation leverages modern .NET runtime optimizations and claims superior memory efficiency
Microsoft Research Blog 2024
.

Gap Analysis.

Despite growing interest in Redis alternatives, independent benchmarking remains limited, with most existing comparisons relying on vendor claims or narrowly focused use cases. Notably absent are studies that assess migration complexity, operational compatibility, and long-term viability alongside performance. This work addresses those gaps by offering a comprehensive, independent evaluation using standardized methodologies and realistic deployment scenarios, incorporating practical considerations critical for production environments, beyond raw performance alone. Furthermore, our work extends the Big Data benchmarking landscape by applying prescriptive performance analysis methodologies

Systems Architecture and Design

This section provides an overview of the architectural characteristics and design principles of the evaluated systems: Redis, Valkey, KeyDB, and Garnet. Understanding these fundamental differences is crucial for interpreting performance results and migration considerations.

The emergence of Redis alternatives has prompted several comparative studies. Industry analysis by RedMonk
RedMonk 2024
tracked Valkey’s adoption seven months after its release, noting significant community momentum and performance improvements. However, these analyses primarily rely on vendor-provided benchmarks rather than independent evaluation.

Redis Architecture.
Redis employs a single-threaded event loop architecture for command execution, which simplifies code complexity and avoids concurrency issues but can limit throughput on multi-core systems
Redis Inc. 2024b
. The system uses an in-memory data structure store supporting various data types including strings, lists, sets, sorted sets, hashes, bitmaps, and streams.

Redis’s persistence mechanisms include RDB snapshots and Append-Only File (AOF) logging. The system supports master-replica replication and Redis Cluster for horizontal scaling. Memory management relies on configurable eviction policies when memory limits are reached.

Valkey Architecture.
Originally a Redis fork, Valkey has significantly diverged since version 8.0, notably through enhanced I/O multithreading that leverages modern multi-core processors
Linux Foundation 2024
. Its redesigned threading model enables parallel I/O with data safety. Key improvements include: (1) a modern key-value store inspired by Swiss Tables, (2) improved cluster failover algorithms, and (3) experimental RDMA support for high-performance networking. While introducing these optimizations, Valkey retains full Redis API and protocol compatibility, making it a viable drop-in replacement.

KeyDB Architecture.
KeyDB features a multithreaded design that leverages multiple CPU cores
KeyDB Documentation 2024b
, while remaining fully compatible with the Redis protocol. Notable capabilities include: (1) multithreaded networking and query processing, (2) active replication for consistency, (3) FLASH storage for large datasets, and (4) subkey expiration for granular data control. However, limited recent development raises concerns about its long-term sustainability.

Garnet Architecture.
Garnet is a from-scratch Redis-compatible implementation built on the modern .NET runtime, optimized for high-performance use cases
Microsoft Research 2024
. Its key features include: (1) native multithreading with lock-free data structures, (2) advanced memory management with minimal garbage collection overhead, (3) async-optimized network I/O, and (4) an extensible design for custom operations and data types. Despite its strong performance, Garnet only partially supports the Redis API, posing challenges for migration.

4.2
Benchmarking Tool and Workload Design

We employed memtier_benchmark, the industry-standard tool for Redis performance evaluation, with modifications to support Zipfian key-access distributions. This tool enables precise control over workload characteristics while generating high-throughput load against in-memory key-value stores.

4.2.1
Key Access Pattern

Realistic production traffic was simulated using Zipfian key-access distributions, where a small number of "hot keys" receive disproportionately large numbers of accesses. Based on the large-scale study by Yang et al.
Yang et al. 2021
, we used skew parameters
\alpha=1.4
for read-heavy workloads and
\alpha=0.9
for write-heavy workloads.

The Zipfian probability mass function is defined as:

P(k)=\frac{1/k^{\alpha}}{H_{N,\alpha}}

H_{N,\alpha}

N

H_{N,\alpha}=\sum_{i=1}^{N}\frac{1}{i^{\alpha}}

4.2.2
Memory Pressure Configuration

Each system was pre-loaded with data to achieve approximately 75% memory utilization, following Microsoft’s benchmarking recommendations
Microsoft Azure Documentation 2024
. With 8 GiB available memory, 1 KiB value size, and assuming 300 bytes overhead per key, the number of keys was calculated as:

\frac{8\times 2^{30}\times 0.75}{1024+300}\approx 4,800,000

(3)

This configuration ensures realistic memory pressure during benchmarking rather than testing with mostly empty memory.

4.3
Workload Configurations

Two distinct workload patterns were evaluated to represent common production scenarios:

Workload A (Write-Heavy):
50% SET operations, 50% GET operations with Zipfian skew
\alpha=0.9
. This pattern simulates write-intensive applications such as session stores and real-time analytics pipelines.

Workload B (Read-Heavy):
5% SET operations, 95% GET operations with Zipfian skew
\alpha=1.4
. This pattern represents read-dominated scenarios typical of caching layers and content delivery systems.

Each workload was executed across concurrency levels ranging from 50 to 500 connections in increments of 50, representing light to heavy load conditions. Each test ran for 300 seconds with a 60-second warmup period to ensure stable measurements.

6
Discussion and Practical Implications

This section synthesizes our findings into actionable recommendations for different deployment scenarios, considering performance, compatibility, and long-term viability.

6.1
Migration Complexity Assessment

Valkey:
Offers the smoothest migration path with 100% Redis API compatibility. Organizations can perform drop-in replacement with minimal code changes. Configuration files are directly compatible, and existing monitoring tools work without modification. The strong community backing from Linux Foundation and major cloud providers ensures long-term support.

KeyDB:
Provides good compatibility (95% Redis API coverage) but requires testing of advanced features. The limited development activity raises sustainability concerns. Organizations should carefully evaluate the risk of adopting a system with uncertain long-term maintenance.

Garnet:
Presents the highest migration complexity due to 70% API compatibility. Applications using advanced Redis features require significant refactoring. However, for greenfield projects or systems using only core Redis operations, Garnet’s superior performance may justify the integration effort.

6.2
Deployment Recommendations

Based on our comprehensive evaluation, we provide the following scenario-specific recommendations:

For Redis Replacement in Existing Systems:
Valkey represents the optimal choice, offering performance improvements without migration risk. The full API compatibility enables seamless transition while delivering measurable throughput and efficiency gains.

For High-Performance New Deployments:
Garnet should be strongly considered when maximum performance is critical and API compatibility constraints are manageable. The 2x throughput advantage and superior resource efficiency can significantly reduce infrastructure costs.

For Multi-Core Optimization:
While KeyDB offers multithreading, Valkey provides better performance with lower complexity. KeyDB’s development uncertainty makes it difficult to recommend for production deployments.

For Cloud-Native Environments:
Valkey’s Kubernetes-friendly architecture and active development make it ideal for containerized deployments. Garnet is also well-suited for cloud environments where .NET runtime is already in use.

6.3
Performance-Cost Trade-offs

Our resource efficiency analysis reveals important cost implications. At equivalent throughput levels:

•

Garnet requires approximately 40% fewer compute resources than Redis

•

Valkey achieves 20-25% resource efficiency gains over Redis

•

KeyDB actually increases resource costs by 10-15% despite modest performance gains

For cloud deployments where compute costs dominate, Garnet’s efficiency can translate to substantial operational savings, potentially offsetting higher migration complexity costs within months.

6.4
Long-term Viability Considerations

Community and Governance:
Valkey benefits from Linux Foundation governance and backing from AWS, Google Cloud, and Oracle. This broad industry support suggests strong long-term viability. Garnet has Microsoft’s backing but narrower community adoption. KeyDB’s limited recent development activity raises sustainability concerns.

Development Velocity:
Valkey demonstrates rapid feature development with significant improvements in version 8.0. Garnet shows steady progress with regular releases. KeyDB’s development has slowed considerably, with minimal updates in recent quarters.

Ecosystem Compatibility:
Valkey maintains compatibility with the broader Redis ecosystem, including client libraries, monitoring tools, and operational practices. Garnet requires ecosystem adaptation, though Microsoft provides good tooling support. KeyDB’s ecosystem compatibility is good but may diverge as Redis evolves.

7
Conclusion and Future Work

This study presented a comprehensive, independent evaluation of Redis alternatives under realistic cloud-native deployment conditions. Our findings demonstrate clear performance and operational trade-offs among Valkey, KeyDB, and Garnet.

Key Findings:

•

Garnet delivers exceptional performance, achieving up to 108% throughput improvement over Redis with superior resource efficiency, but requires significant migration effort due to limited API compatibility.

•

Valkey provides the optimal balance of performance improvement (30-38% throughput gains) and migration simplicity through full Redis API compatibility, making it the most practical drop-in replacement.

•

KeyDB shows modest performance gains but raises sustainability concerns due to limited development activity and suboptimal resource efficiency.

Recommendations:
For organizations seeking Redis alternatives, we recommend Valkey for existing system migrations due to its compatibility and strong community backing. Garnet should be considered for new high-performance deployments where API constraints are manageable. KeyDB is difficult to recommend given its uncertain long-term viability.

Future Work:
Several directions warrant further investigation:

•

Cluster mode evaluation to assess horizontal scaling characteristics

•

Persistence mechanism comparison including RDB and AOF performance

•

Extended workload diversity including complex data structures and transactions

•

Long-term stability testing under sustained production-like loads

•

Cost-benefit analysis incorporating migration effort and operational expenses

As the in-memory datastore landscape continues to evolve, ongoing evaluation will be essential to guide architectural decisions in cloud-native environments.
