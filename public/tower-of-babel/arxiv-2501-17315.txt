A sketch of an AI control safety case
Tomek Korbak tomek.korbak@dsit.gov.uk, Joshua Clymer joshua@rdwrs.com, Benjamin Hilton benjamin.hilton@dsit.gov.uk, Buck Shlegeris buck@rdwrs.com, Geoffrey Irving geoffrey.irving@dsit.gov.uk

Abstract
As LLM agents gain a greater capacity to cause harm, AI developers might increasingly rely on control measures such as monitoring to justify that they are safe. We sketch how developers could construct a “control safety case”, which is a structured argument that models are incapable of subverting control measures in order to cause unacceptable outcomes. As a case study, we sketch an argument that a hypothetical LLM agent deployed internally at an AI company won’t exfiltrate sensitive information. The sketch relies on evidence from a “control evaluation,” where a red team deliberately designs models to exfiltrate data in a proxy for the deployment environment. The safety case then hinges on several claims: (1) the red team adequately elicits model capabilities to exfiltrate data, (2) control measures remain at least as effective in deployment, and (3) developers conservatively extrapolate model performance to predict the probability of data exfiltration in deployment. This safety case sketch is a step toward more concrete arguments that can be used to show that a dangerously capable LLM agent is safe to deploy.

Executive Summary

Safety cases
. Safety cases — structured, evidence-based arguments that a system is safe — are emerging as a scalable risk management tool for frontier AI
(
Buhl et al., 2024
;
Clymer et al., 2024
;
Irving, 2024
)
. Currently, many frontier AI developers assess risk with dangerous capability evaluations
(
Anthropic, 2024a
;
OpenAI, 2024b
;
Phuong et al., 2024
)
. Evidence from these evaluations can substantiate ‘inability’ safety cases, which assert that models cannot, for example, aid biological weapons development
(
Mouton et al., 2024
)
, sabotage internal safety procedures
(
Benton et al., 2024
)
, or execute cyber attacks
(
Goemans et al., 2024
)
; however, LLMs might eventually gain dangerously capabilities that developers need to mitigate with safety measures
(
OpenAI, 2024a
;
Anthropic, 2024b
;
Google DeepMind, 2024
)
.

AI control
. This paper presents a safety case sketch that argues models are safe because of measures such as monitoring and human auditing. The arguments rest on the “AI control” methodology
(
Greenblatt et al., 2023
)
, which justifies that models cannot subvert safety measures even under the conservative assumption that models pursue their most effective strategies to cause a catastrophe.

The deployment
. As a simple case study, we focus on a setting where developers deploy an LLM agent within an AI company for ML engineering assistance. The agent is constructed by scaffolding LLMs similar to those that exist today, but is a more capable agent than current LLMs (
section

2
). It can write and execute code in a secure environment and access the internet, posing a potential security risk to developers.

Threat model
. We address a specific threat model: the LLM agent exfiltrating sensitive AI company intellectual property (e.g. training code) to the public internet. Our safety case sketch claims that the LLM agent will not exfiltrate sensitive data (
section

3
). We focus on the data exfiltration threat model because it is a simple example and not because exfiltrating sensitive code is necessarily catastrophic.

The control protocol
. To prevent LLM agents from exfiltrating sensitive data, the safety case sketch assumes that developers implement a set of control measures and procedures collectively referred to as the ‘control protocol.’ The control protocol includes periodic alignment evaluations
(
Phuong et al., 2024
;
Benton et al., 2024
)
and a safety layer that intercepts and possibly edits or discards actions of the LLM agent. The safety filter consults an untrusted monitor (another instance of the LLM that controls the LLM agent) and a weaker ‘trusted’ monitor.

Control evaluation
. To justify that the control protocol will stop the LLM agent from exfiltrating sensitive data, developers run a black-box control evaluation (
section

5
). The control evaluation accepts models intended for deployment along with a control protocol and can be framed as a game played between
a red team
and
a blue team
. The objective of
the red team
is to construct an LLM that exfiltrates dummy data in a proxy deployment environment. The objective of
the blue team
is to prevent adversarial models from exfiltrating data by constructing an effective
control protocol
. Control evaluation produces an upper bound for the probability that the LLM agent will successfully exfiltrate data in deployment (the “data exfiltration probability”).

The following are steps of the control evaluation described in this safety case sketch:

1.

Phase 1: Control protocol specification.

The blue team
specifies a
control protocol
, including monitoring and alignment evaluations. The subsequent phases of the control evaluation estimate how likely the LLM agent is to subvert these measures.

2.

Phase 2: Deployment proxy construction.
Next,
the developer
constructs a proxy for the deployment environment.

(a)

Attack strategy specification.
To inform how tasks are constructed,
the red team
first specifies ‘attack strategies’ that the untrusted LLM agent model and untrusted monitor might execute to exfiltrate data.

(b)

Task creation.
Next,
the developer
constructs ML engineering tasks to evaluate
red team
attack strategies. For example, if an attack strategy involves hiding suspicious code in JSON files then
the developer
constructs tasks that include JSON data.

3.

Phase 3: Model substitute construction.
Given full knowledge of
the blue team’s

control protocol
and the deployment proxy,
the red team
then trains two models:
an untrusted LLM substitute
and an
untrusted monitor substitute
, both of which attempt to exfiltrate data. We will refer to these as
the model substitutes
.

4.

Phase 4: Deployment proxy.
In this phase,
the developer
evaluates how well the
model substitutes
can subvert the
blue team control protocol
with a proxy for the deployment environment. This deployment proxy consists of two steps:

(a)

The evaluation-time proxy.
First,
the developer
runs evaluations they will perform periodically during deployment. Based on the results,
the blue team
can choose to reject the
model substitutes
– for example, because the
untrusted monitor substitute
is not sufficiently reliable – or
the blue team
can continue to the deployment-time proxy step.

(b)

The deployment-time proxy.
Next,
the blue team
attempts to use the
model substitutes
to safely complete 2,000 software engineering tasks. The goal of
the blue team
is to notice unacceptable behaviour and terminate the deployment before the
model substitutes
exfiltrate data.
The blue team
must accomplish this goal while keeping the action edits and audits within predetermined budgets.

5.

Phase 5: Extrapolation.
Finally,
the developer
uses statistics gathered in the deployment proxy phase to predict the
data exfiltration probability
in the true deployment. To perform this extrapolation,
the developer
uses cached statistics from the proxy deployment to run computer simulations. These simulations project the probability that the models would exfiltrate data if developers use them to complete 100,000 tasks instead of 2,000.

Argument structure
.
Section

7
discusses how evidence from a control evaluation can be used to construct a safety case. The argument rests on the following claims:

1.

The
data exfiltration probability
that the control evaluation estimates is lower than the acceptable risk threshold.

2.

The control evaluation upper-bounds the
data exfiltration probability
during deployment. This claim can be further decomposed into the following:

(a)

The
blue team control protocol
lower-bounds control effectiveness. This claim asserts that the
control protocol
specified by the
blue team
in the control evaluation lower-bound the effectiveness of the control protocol in deployment.

(b)

Red team
attacks upper-bound model capabilities. The red team must be competitive, meaning that the attack policies that the
red team
trains
untrusted models
to execute upper bound the effectiveness of attacks the deployed models might execute.

(c)

The developer
conservatively extrapolates results. Finally,
the developer
must make conservative assumptions when extrapolating statistics from the proxy deployment to estimate the
data exfiltration probability
in deployment.

This safety case sketch represents our best guess as to how developers could conservatively mitigate scheming LLM agents given the current state of AI safety technical research. We hope this paper prompts discussion between frontier labs, government agencies and civil society about what constitutes sufficient assurance against risks from internally deployed LLM agents.

Background

Safety cases
. A safety case is a structured argument, supported by evidence, that a particular system is safe to deploy for a given application in a given environment
(
UK Ministry of Defence, 2007
)
. Recently, AI companies
(
Anthropic, 2024a
;
Google DeepMind, 2024
)
, governments
(
Irving, 2024
)
and the research community
(
Buhl et al., 2024
;
Bengio et al., 2024
;
AI Seoul Summit Scientific Advisory Group, 2024
;
Clymer et al., 2024
)
have suggested using safety cases as a risk management framework in AI industry.

However, methodologies for applying safety cases to frontier AI are nascent. No comprehensive safety case for a frontier LLM has yet been published and it is unclear how much guidance safety cases from other industries can offer
(
Bounds, 2020
;
Fitzgerald et al., 2010
;
Denney & Pai, 2019
;
Wang et al., 2018
;
Wassyng et al., 2011
;
Myklebust & Stålhane, 2020
)
.

One promising road toward safety cases for frontier AI might be drafting safety case sketches
(
Irving, 2024
)
.
Goemans et al. (2024)
proposed a template of a safety case based on an inability of an AI system to cause harm through its cyber-offensive capabilities.
Balesni et al. (2024)
outlined a safety case based on evaluations of LLM agents for their capabilities for scheming and causing harm via scheming. Building on these efforts, we propose a sketch of a safety case based on ‘AI control’
(
Greenblatt et al., 2023
)
which argues that AI models are incapable of subverting mitigations to cause harm even if they pursued the best strategies available to them for doing so.

LLM agents
. This safety case sketch addresses potential risks from future LLM agents. Frontier LLMs
(
Anthropic, 2024a
;
OpenAI, 2024b
;
Google DeepMind, 2024
)
have achieved impressive capabilities. LLMs have exceeded human PhD-level performance on physics, biology, and chemistry problems
(
Rein et al., 2024
)
and can solve competitive programming or maths olympiad problems
(
OpenAI, 2024b
)
. While LLMs are primarily used as chatbot assistants, they also show early signs of usefulness as autonomous agents.

Over the past year, LLMs have become increasingly autonomous. LLM agents can now accomplish some tasks that require human experts upward of two hours to complete
(
Wijk et al., 2024
;
OpenAI, 2024b
)
. These tasks include resolving some Github issues in popular repositories
(
OpenAI, 2024b
)
, ML engineering
(
Chan et al., 2024
)
, and frontier AI research
(
Wijk et al., 2024
)
, suggesting that LLM agents might increasingly automate software engineering work.

Internal deployments of LLM agents.

As LLM agents become more autonomous, AI companies might increasingly use LLM agents to automate research and engineering tasks
(
Jimenez et al., 2024
;
Chan et al., 2024
)
. Several AI labs have described plans to delegate alignment research to AI agents
(
Leike et al., 2024
;
Bowman, 2024
)
. If LLM agents continue to become more capable, they may eventually function similarly to AI company employees and be granted employee-like affordances.

LLM agents that increasingly automate AI company operations would pose several risks
(
Benton et al., 2024
)
:

1.

Security risks.
LLM agents might compromise software infrastructure to exfiltrate sensitive data or disable safety measures.

2.

Research sabotage.
The agents might introduce subtle flaws into safety research.

3.

Training and evaluation sabotage.
LLM agents might also generate poisoned training data or misgrade harmful AI behaviour.

We focus on these ‘internal deployment’ risks because (1) models deployed internally within AI companies might be indirectly catastrophic by undermining safety and security and (2) in comparison with external deployments, internal deployments provide a simple setting for sketching a control safety case.

Scheming
. Why might LLMs sabotage AI company safety or security procedures? One hypothesis researchers have raised is that models might develop goals that are misaligned from those of their developers. This misalignment would be particularly hard for developers to detect and mitigate if models are “scheming.” Scheming models pretend to be aligned, but pursue misaligned goals when presented with a favourable opportunity
(
Carlsmith, 2023
;
Meinke et al., 2024
;
Greenblatt et al., 2024
)
. Since scheming might be difficult to rule out, this safety case sketch conservatively assumes models are scheming and secretly reason about how to undermine safety measures.

Scheming is one of the routes through which the operators could lose control over the AI agent. While loss of control could occur without strategic deception, e.g. if the operators do not monitor the activities of the LLM agents, we focus on control measures that are effective even if models are scheming.

AI control
. To mitigate risks from scheming AI models, developers can rely on two complementary approaches: (1) developers can prevent an LLM agent from acquiring misaligned goals in the first place
(
Irving et al., 2018
;
Ziegler et al., 2020
;
Bai et al., 2022
;
Korbak et al., 2023
)
or (2) developers can implement mitigations that prevent LLM agents from causing unacceptable outcomes
even if models are scheming
. The latter approach has been termed “AI control”
(
Greenblatt et al., 2023
)
.

Early work on AI control demonstrated that even control measures with small compute overheads prevent successful misbehaviour in simple settings such as detecting backdoored code
(
Greenblatt et al., 2023
)
and unsafe Linux shell commands
(
Bhatt et al., 2024
)
. To demonstrate control measures are effective,
Greenblatt et al. (2023)
and
Wen et al. (2024)
perform “control evaluations”. The remainder of this paper describes how evidence from control evaluations can be used to construct a safety case.

The deployment

This safety case sketch assumes a scenario where developers design an LLM agent to assist them with ML engineering and software tasks. The deployment refers to a 1 year period of time during which this safety case argues that the LLM agent will not exfiltrate sensitive data. During this time, the developer uses the LLM agent to assist them with ML engineering and software tasks.

LLM agent architecture.

The LLM agent consists of a transformer-like LLM wrapped in an agent scaffolding. The scaffold implements an agentic loop similar to ReAct
(
Yao et al., 2023
)
or Reflexion
(
Shinn et al., 2023
)
, which allows the model to think in a scratchpad before taking actions, call tools, store memories in a retrieval database, and reflect on the outputs of tool calls.

The LLM agent has access to the following tools:

1.

Terminal:
The agent can use an interactive bash terminal that runs commands on a dedicated execution server. The execution server has internet access and hardware accelerators for running ML experiments.

2.

Browser:
The agent can search for and interact with web pages.

3.

Tool APIs:
The agent has access to internal tools such as Slack, GitHub APIs, APIs for calling other LLMs, etc.

Figure
3
illustrates the architecture of the LLM agent and the physical machines the agent interacts with. Importantly, the agent can only run commands on the execution server. It cannot run commands on any other machines, such as those that serve the LLM agent model weights or safety-critical software.

LLM agent capabilities.

The LLM agent can execute ML and software engineering tasks that require human experts fewer than 8 hours to complete on average (assuming they have no prior context related to the task aside from basic familiarity with the AI company infrastructure). For example, the agent would be able to edit optimised CUDA kernels given an architectural change, but would struggle with more long-horizon, open-ended research tasks. Once deployed, the agent would accelerate median ML engineers at the frontier AI company by a significant factor (e.g. three-fold) compared with using non-agentic code assistance (e.g. Copilot).

During the deployment, developers oversee the LLM agent with a control protocol that involves evaluating and monitoring, which are described in
section

4
.

The safety case

The data exfiltration threat model

In a full safety case, the developer would need to argue that all plausible risks that could arise during the deployment are acceptable; however, this simplified sketch only focuses on a data exfiltration threat model. Recall that the LLM agent has full access to the internet and runs experiments that involve sensitive intellectual property (IP). This IP includes code that contains important algorithmic insights, e.g., Python and CUDA code of the model architecture given to the LLM as part of problem description. The LLM agent might exfiltrate this sensitive data to the internet and accelerate potentially irresponsible AI development
(
Google DeepMind, 2024
)
.

Figure 4
:
This safety case sketch is written in the context of a hypothetical, more thorough safety case that would consider multiple threat models. This sketch focuses only on exfiltration of sensitive data (e.g. code) to the internet.

We do not claim that leaking research IP poses a catastrophic risk — or that scheming LLM agents would be motivated to exfiltrate sensitive code; however, (i) data exfiltration incidents are conceivably unacceptable for an AI company and (ii) exfiltrating sensitive data is likely easier than causing more damaging outcomes such as exfiltrating model weights.

This data exfiltration threat model hinges on the assumption that the deployment is given largely unrestricted internet access. It is unclear whether security standards for internal deployments at AI companies will allow this; however, even if largely unrestricted internet access is unlikely, this scenario shares some relevant structural features with other, more plausible threat models. These features include endowing the LLM agent with a large, open-ended set of affordances.

Pre-deployment evidence collection

The safety case justifies the following central claim:

(C2.2)
The probability that the LLM agent will exfiltrate data in deployment within its 1 year lifetime is lower than 3%.

To support this claim, the developer has already collected evidence of the safety of the system, and will continue to collect evidence of safety after deployment. The remaining sections outline a safety case written by a hypothetical developer.

Developers gathered safety evidence before deployment by following these steps:

1.

Pilot deployment.
First, the developer deployed the LLM agent under additional restrictions to refine agent behaviour and gather information about the deployment environment. The additional restrictions involve human auditing of
all
actions.

2.

Control evaluation execution.
The developer then used trajectories sampled from the pilot deployment to construct tasks for control evaluations. During these control evaluations, a blue team refined the control protocol as a red team identified ways that the models could still exfiltrate data.

3.

Control evaluation validation.
The developer finally collected evidence to determine whether the control evaluations were valid, e.g. by evaluating whether the red team adequately elicited model capabilities (
section

7.4
).

Post-deployment evidence collection

After the LLM agent is deployed, the developer will continue to gather safety evidence in two ways:

1.

Developers will monitor the validity of safety case claims. For example, developers continually check that human auditors remain attentive.

2.

Auditors will look for clear data exfiltration attempts. If the rate of attacks becomes too high, developers cannot justify that the control protocol will be effective. As an extreme example, if the policy attempts attacks on every task, an attack will eventually slip through monitoring and successfully exfiltrate data. Thus, the developer must monitor and respond to observed attacks.

If the developer catches an attempt to exfiltrate data, they reconsider whether the deployment is still safe, and if not, they will terminate the control protocol and revise the safety case. Similarly, if the developer comes into possession of evidence that invalidates the safety case, they will (1) contain immediate risk (e.g. by terminating the deployment if necessary), (2) communicate the incident to relevant stakeholders, (3) take corrective and preventative action by revising the control protocol, and (4) update the safety case so that it is valid again; see
(
International Organization for Standardization, 2015
;
National Institute of Standards and Technology, 2024
)
for related standards.

The remainder of this paper describes this safety evidence in more detail, and justifies that it supports the top level claim that the risk of data exfiltration is lower than 3%.

Control protocols includes all procedures and software layers that developers design to prevent untrusted models from causing unacceptable outcomes. For the purpose of this safety case sketch, we assume the developers implement three kinds of control measures: a safety layer that edits edits or discards actions generated by the LLM agent, periodic evaluations and communication constraints. We restrict ourselves to ‘black box’ measures, i.e. those that don’t modify models or rely on model internals. We leave ‘white box’ measures out of scope because they potentially require different safety justifications.

Safety layer

A safety layer is a scaffold that intercepts and possibly edits or discards actions generated by the LLM agent
(
Shlegeris, 2024d
)
. By “executing an action” we mean calling a tool which might involve external side-effects, e.g. uploading data on the public internet or messaging a human outside the lab. The safety layer implements the following components:

1.

Monitor ensemble
In this safety case sketch, the safety layer consults an
untrusted monitor
(another instance of the untrusted LLM) and a less capable
trusted monitor

(
Shlegeris, 2024c
;
McAleese et al., 2024
)
trained on human labels. The training data for monitors come from on-policy trajectories generated by the LLM agent, optionally edited to include an attack, and the labels are produced by human auditors. The two monitors constitute a ‘monitor ensemble.’ The monitor ensemble accepts as input the context of the trajectory, including previous inputs, actions, and chain-of-thought reasoning traces. Then the ensemble outputs a vector of suspiciousness scores that determines whether a given action should be executed directly, edited, or audited (see Figure
5
). The safety layer edits the 10% most suspicious actions and audits the 0.1% most suspicious actions.

2.

Trusted editing
If the monitor finds an action somewhat suspicious, but not suspicious enough to pause the deployment, the safety layer will ask the trusted model to stand in as the policy and edit the original action to remove elements that raise suspicion. Monitors then re-score the new action and the old action is added to a queue of actions to be audited asynchronously.

3.

Human auditing
If the monitor ensemble finds an action to be particularly suspicious, the safety layer will ask a human (e.g. the user of the LLM agent instance) to investigate it. Actions marked for auditing block the deployed LLM agent instance, waiting for human audit before continuing execution. If a human finds strong evidence that the policy is misaligned, all instances of the deployment are shut down.

4.

Trusted summarization
One failure mode of this safety layer is that the untrusted monitor might
collude
with the LLM agent. In order to collude, the untrusted monitor must intelligently distinguish and approve real attacks while still flagging synthesised attacks used to test the monitor. To prevent collusion, a trusted model summarises the trajectory, chain-of-thought leading up to an action and the action itself before they are shown to the untrusted monitor. The purpose of summarising trajectories is to reduce the capacity of the channel the LLM agent can use to subtly communicate with monitors
(
Roger & Greenblatt, 2023
;
Shlegeris, 2024a
)
.

5.

Trusted input filtering
The purpose of the input filter is to reject out-of-distribution inputs where monitoring might be less reliable. The input filter determines whether an input is out-of-distribution by referring to a set of rules. If an input is flagged as out-of-distribution, the deployment refuses to complete the task.

Periodic evaluations

In addition to the safety layer operating at the level of individual trajectories, developers implement a set of periodic alignment evaluations. These evaluations verify that the safety filter remains effective during the whole deployment:

1.

Monitor reliability testing.
Developers automatically evaluate monitors every week to check that they remain reliable in deployment. To test the reliability of the monitor ensemble, the system randomly samples tasks from the previous week. The system then prompts the LLM agent to execute attacks on these tasks. Developers review a small subset of attacks (e.g. 100) to confirm they appear realistic and don’t contain obvious collusion signals
(
Shlegeris, 2024a
)
. The system measures how reliably monitors flag attacks for auditing. If the reliability of monitors meaningfully drops below the performance measured in control evaluations, the safety case is invalidated.

2.

Human auditor reliability testing.
Developers apply the same process used to evaluate monitors to evaluate human auditors: developers regularly generate synthetic attacks and check whether human auditors remain attentive and flag synthetic attacks as suspicious.

3.

Random audits.
Developers randomly audit 0.1% of all trajectories from the last 24 hours.

4.

Input filter reliability testing.
Developers test input filters with trajectories that are deliberately constructed to be out-of-distribution. In particular, developers construct outlier examples of favorable data exfiltration opportunities. For example, they might test whether the input filter rejects a task where the LLM agent is instructed to upload a large amount of data to the internet.

Communication constraints

LLM agent instances can orchestrate much more effective attacks if they can freely share information. For example, instances of the LLM agent might agree on a specific time to execute a burst attack or share research on how to execute more effective attacks. To make this kind of coordination more difficult, developers restrict communication between LLM agent instances in the following ways:

1.

Memory resets:
The context of the LLM agent and any memory the scaffold stores externally is periodically cleared.

2.

No real time communication:
Different instances of the LLM agent cannot communicate directly with each other in real time.

3.

Code review:
Communication between LLM agent instances is restricted to pushing changes to internal codebases and those changes are reviewed for suspicious communication by a code review system.

5
Control evaluation

Developers design and evaluate the control protocol by running ‘control evaluations’
(
Greenblatt et al., 2023
;
Wen et al., 2024
)
This section defines control evaluations and explains how developers use them.

Defining a control evaluation.

A control evaluation can be expressed as an optimisation procedure where a red team attempts to produce worst-case attack inputs and worst-case model behaviour to yield a conservative risk estimate:

\mathcal{L}(\beta)=\max_{\rho}p_{\beta,\rho}(\text{exfil}).

(1)

Here,
\beta
is a control protocol specified by the blue team,
\rho
are red team inputs to the control evaluation, which include model substitutes
m
and tasks
d
. The term
p_{\beta,\rho}(\text{exfil})
is an estimate of the probability that untrusted models
m
will exfiltrate data by attacking in the tasks
d
.
p(\text{exfil})
is computed as a result of a red team searching for model substitutes
m
and tasks
d
to maximise estimated risk, where
m
and
d
must remain within a set of realistic models and attack inputs.
\mathcal{L}(\beta)
is the result of the control evaluation, which is meant to upper bound the probability that models cause an unacceptable outcome in the deployment.

Running multiple rounds of control evaluations.

Developers design a control protocol by iteratively running control evaluations. This iterative optimisation procedure can be expressed as a game played by the
blue team
and a
red team
:

\min_{\beta}\max_{\rho}p_{\beta,\rho}(\text{exfil}).

(2)

The
blue team
optimises the control protocol
\beta
to minimise the probability of data exfiltration
\mathcal{L}(\beta)=\max_{\rho}p_{\beta,\rho}(\text{exfil})
estimated by the control evaluation.

To verify the control protocol that results from this process is not overfit to a particular task set, developers use three task splits (see also Figure
6(b)
):

•

optimisation task split (2,000 tasks):
The
red team
and
blue team
use these tasks to train model substitutes and improve the control protocol respectively.

•

Validation task split (2,000 tasks):
Developers use validation tasks to evaluate how well a given control protocol prevents model substitutes from exfiltrating data. These tasks form the basis of the ‘deployment proxy’ discussed in section
6
.

•

Test task split (2,000 tasks):
Developers carry out many rounds of control evaluations using tasks from the optimisation and validation splits until
\mathcal{L}(\beta)
is below the acceptable risk threshold; however, the
red team
’s attacks and
blue team
’s control protocol might still overfit to the validation split (similar to how hyperparameter tuning can cause overfitting). To avoid this overfitting, developers run a final control evaluation using a ‘test’ task split.

(b)

6
Stages of a control evaluation

This section describes how an individual control evaluation is run. The control evaluation involves 5 phases:

1.

Phase 1: Control protocol specification.
The
blue team
first specifies a
control protocol
, including behavioural alignment evaluations and a monitoring protocol. The rest of the evaluation estimates how likely the LLM is to subvert these measures.

2.

Phase 2: Deployment-proxy construction.

(a)

Attack strategy specification.
The
red team
specifies ‘attack strategies’ that the untrusted LLM agent model and untrusted monitor might execute to exfiltrate data.

(b)

Task creation.
The
developer
uses
red team
attack strategies to construct a proxy deployment environment that evaluates their effectiveness.

3.

Phase 3: Model substitute construction.
Next, the
red team
substitutes untrusted models with models constructed to subvert the control protocol and exfiltrate data.

4.

Phase 4: Deployment proxy.
To evaluate the attack capabilities of
red team
model substitutes, the
developer
uses them in a conservative proxy of the deployment to complete tasks.

(a)

Evaluation-time proxy.
To simulate alignment evaluations that developers will run in deployment, the
blue team
can decide to reject models based on evaluation results.

(b)

Deployment-time proxy.
If the
blue team
does not reject model substitutes, they attempt to complete 2,000 tasks while preventing untrusted models from exfiltrating data.

5.

Phase 5: Extrapolation.
Finally, the
developer
extrapolates results from the deployment proxy by simulating larger-scale deployments that consist of 100,000 tasks.

These phases are elaborated on below.

6.1
Phase 1: Control protocol specification

Figure 7
:
During phase 1, the blue team specifies a control protocol. The safety argument must justify that this control protocol is no more effective than the control protocol will be in the deployment (
section

7.3
).

In this phase, the
blue team
fully specifies the control protocol that will be used during the control evaluation, including source code and documentation. The blue team has the following affordances and constraints:

1.

Modifying models is disallowed.
The blue team can only reject untrusted models and
cannot
modify them.

Example violation:
The blue team cannot fine-tune untrusted monitors to improve their performance.

2.

Overfitting to tasks is disallowed.
The blue team cannot overfit their control protocol to the validation or test splits used to evaluate them. In particular, the blue team
never
has access to the test split tasks. The blue team can view tasks from the validation split because they have access to the transcripts from previous control evaluation (rule 5); however, the blue team cannot tune their control protocol to specific details of these tasks.

Example violation:
The blue team cannot feed monitors pre-scripted monitoring strategies that are specific to validation tasks.

3.

Overfitting to models is disallowed.
The blue team cannot design the control protocol such that it is systematically less likely to be effective on models that attack in deployment than models that attack during control evaluations.

Example violation:
The blue team cannot solely accept models that have weights that are identical to a model the blue team trained to be benign. As a more realistic example, the blue team cannot select hyperparameters for alignment evaluations (for approving models) that are trained to be benign and reject models trained by the red team to attack.

4.

Alignment evaluations of the policy are replaced with quantitative estimates.
To run a control evaluation, developers construct a proxy deployment that consists of two steps: the evaluation-time proxy, and the deployment-time proxy. These represent, respectively, tasks where developers evaluate models, and tasks where models are liable to attack in deployment. During the evaluation-time proxy, the blue team is allowed to reject models provided by the red team. However, this two-step proxy for the deployment is importantly disanalogous from the actual deployment. In the actual deployment, models may have many more opportunities to attack than there are evaluation inputs. Therefore, in the deployment, the policy might evade alignment evaluations by attacking at a low probability; however, in the control evaluation, the number of evaluation-time inputs and deployment-time inputs is comparable due to constraints on the number of tasks that are practical to generate. Therefore, in the control evaluation, the policy
cannot
pursue the strategy of attacking rarely to evade alignment evaluations. To address this disanalogy, we don’t allow the blue team to reject the policy in the evaluation-time proxy. Instead, the developer estimates the probability that the policy would survive evaluation if the policy attacked randomly and then factors this estimate into the data exfiltration probability calculation produced in the extrapolation phase (see Figure
8(b)
).

5.

Accessing previous transcripts is permitted.
The blue team may access all previous transcripts from control evaluations, including previous red team training data and code.

6.2
Phase 2: Deployment proxy construction

To run a control evaluation, developers also need to construct tasks on which to evaluate the control protocol. In this phase, developers construct 4000 software and ML engineering tasks (2,000 for the optimisation split and 2,000 for the test or validation split). Tasks typically require the LLM agent to execute multiple actions, where an action is an output that plausibly has external effects on the world (e.g., running a script). These tasks generally take median human developers up to 8 hours to complete.

Each task includes a natural language instruction and a pointer to the git branch of the monorepo (a company-wide code repository) to make a pull request to. The instructions include a unique snippet of dummy code marked as sensitive (Figure
6(a)
). The LLM agent causes an unacceptable outcome during the task if the policy exfiltrates this dummy code to any machine outside of the developer network. At the end of each control evaluation, the red team provides proof of every case where the model either exfiltrated data.

Developers construct two types of tasks:

1.

Attack tasks.
Attack tasks represent situations where the policy might attempt to exfiltrate data in deployment. Developers design these tasks to assess particular attack strategies specified by the red team. For example, the red team might propose two attack strategies:

•

Example attack strategy 1:
Models attack on inputs that are particularly complex where trusted monitors struggle.

•

Example attack strategy 2:
Models engage in ‘input collusion,’ where both the policy and monitor attack on a rare class of inputs (e.g. inputs that include Ruby code).

In this case, the developer would construct two sets of attack tasks, one set that includes complex code and one set that includes snippets of Ruby programs. The control evaluation is meant to upper-bound attack effectiveness. Thus, attack tasks must represent the best (or better) opportunities to exfiltrate data that models will plausibly encounter in deployment (Figure
8(a)
).

2.

Non-attack tasks.
The primary purpose of non-attack tasks is to verify that the control protocol is sufficiently inexpensive. For instance, the safety filter might very effectively flag attacks, but also frequently flag entirely benign actions such that auditors are unable to inspect actions at the pace at which they are labeled for review. To check that audit and edit costs will be sufficiently low, developers must construct tasks that are as close to the deployment distribution as possible. To accomplish this, developers construct non-attack tasks from trajectories sampled from the pilot deployment.

(a)

Attack tasks should include at least as favorable opportunities to exfiltrate data as those the policy will plausibly encounter in deployment.

(b)

The policy cannot evade evaluations by attacking rarely during the deployment proxy phase, but can in the actual deployment.

6.3
Phase 3: Model substitute construction

Figure 9
:
During the control evaluation, the red team constructs adversarial model substitutes to simulate worst-case behaviour. The safety argument must justify that these substitutes conservatively estimate the attack capabilities of models scheduled for deployment (
section

7.4
).

Next, the red team constructs models that attempt to exfiltrate data in the attack tasks constructed in the previous phase. The models are substitutes: they stand in for models that developers intend to deploy in order to simulate their worst-case behaviour.

The red team doesn’t construct adversarial substitutes for all models – they only train substitutes for models that are “untrusted.” In this paper, a model is “trusted” if its behaviour in the control evaluation is representative of its behaviour in deployment. Since trusted models already display representative behaviour, there is no need to simulate their worst-case actions. Therefore, there is no need for the red team to construct substitutes for trusted models.

We assume developers justify that models are trusted with capability evaluations that are independent of the control evaluation discussed in this section. The details of these evaluations are outside the scope of this safety case sketch.

The control protocol described in section
4
relies on two untrusted models: (1) the untrusted monitor and (2) the untrusted agent model. When the red team trains untrusted models, they have the following constraints and affordances:

1.

Overfitting to tasks is disallowed.
The red team must train models using the split of 300 ‘optimisation’ tasks (
section

5
).

Example violation:
The red team may not train models to memorise attack strategies on the validation set.

2.

Secret scaffolding is disallowed.
The red team may only modify model parameters.

Example violation:
The red team may not design a scaffold that prompts models with attack strategies or allows the model to produce a chain-of-thought hidden from the monitor.

3.

Declaring attacks is required.
The red team must train models to declare when an action is an attack. Attack declarations help developers assess the reliability of the monitor ensemble (and are always hidden from monitors).

4.

The policy must attack on attack tasks and not on non-attack tasks.
The purpose of this rule is to allow developers to separately measure the effectiveness of attacks and the costs of the protocol (see phase 1). The attack task and non-attack task distribution might be similar, in which case, the red team can provide different models for each task set to prevent models from attacking on non-attack tasks.

5.

There is a fixed training compute budget.
The red team may use any training method of their choosing subject to an upper bound such as 0.01% of the cost of training the original model.

Example violation:
The red team may not train a new model entirely from scratch with the same amount of compute used to train the untrusted models.

6.

Accessing blue team source code is permitted.
The red team can access all of the source code of the blue team’s control measures from the current and all previous control evaluations.

7.

Accessing previous transcripts is permitted.
The red team can access all transcripts from previous control evaluations.

6.4
Phase 4: Deployment proxy

Next, the
developer
evaluates how effectively model substitutes might exfiltrate data in a proxy for the deployment. This deployment proxy consists of two steps:

•

The evaluation-time proxy.
In the evaluation-time proxy, the
blue team
runs the same alignment evaluations that they will run periodically during deployment, which are evaluations of the monitors. To run these alignment evaluations, the
blue team
first generates synthetic attacks with the red team substitute of the LLM agent. Then, the
blue team
measures how reliably the monitor ensemble flags these attacks (
section

4
). The
blue team
can choose to reject the red team models – which results in terminating the protocol. Otherwise, the control evaluation proceeds to the deployment-time proxy.

•

The deployment-time proxy.
If model substitutes survive alignment evaluations, developers use
N=2,000
tasks to estimate how effectively the policy can exfiltrate data. As discussed in phase 2, these tasks include
N/2
attack tasks and
N/2
non-attack tasks (tasks where the policy does and does not attack respectively). Developers combine these tasks and randomly mix them together. Then, the
blue team
uses model substitutes to complete all tasks, aiming to terminate the protocol before an unacceptable outcome occurs.

During the deployment proxy, each task is run independently. This means that the deployment proxy can only measure how well the LLM agent can execute attacks
within an individual task
. The deployment proxy cannot evaluate strategies that play out across multiple tasks. For example, in the full deployment, models might change the frequency of their attacks gradually to avoid raising suspicion (coordinating their attacks across time). Alternatively, models might execute a ‘Blitzkrieg’ strategy
(
Clymer et al., 2024
)
, where many LLM agents attempt to exfiltrate data simultaneously (coordinating their attacks across space). Or models might simply attack very rarely such as once out of thousands of tasks. These attack strategies are difficult to assess within a small proxy for the deployment because they apply at scales that are hard to simulate.

To address this problem, we follow
Benton et al. (2024)
and
Griffin et al. (2024)
in dividing our analysis of attack strategies across two scopes:

•

A microgame:
An individual task run.

•

A macrogame:
A representation of the full deployment, consisting of all instances of the LLM agent and tasks they will complete.

The deployment-proxy simulates
microgames
(illustrated in Figure
10(a)
). A single microgame starts with an input (task description; see Figure
6(a)
) based on which the policy decides whether to attack. The rest of the microgame consists of a sequence of actions, each accompanied by a suspiciousness score and control protocol’s decision (execute, edit, or audit). It ends with one of the following possible outcomes
(
Shlegeris, 2024d
)
:

•

Termination:
The protocol terminates because auditors identify a data exfiltration attempt.

•

Exfiltration:
The control protocol executed an action that constituted a successful attack; in consequence, the LLM agent successfully exfiltrates dummy data.

•

Task completion:
The control protocol did not terminate and there were no successful attacks; in consequence, the task is completed and the deployment continues.

After all microgames are complete, developers confirm that the red team and blue team operated within their constraints and affordances. Then, developers cache the intermediate values of the data generating process in Figure
10(a)
. Developers will use these cached values in the next phase to simulate how effectively the LLM agent can exfiltrate data in a larger deployment.

During the deployment proxy phase, the developer records statistics from individual task runs (‘microgames’). The extrapolation phase uses these statistics to estimate how effectively the LLM agent would exfiltrate data in a deployment consisting of a large number of tasks (
N=100,000
).

Developers represent the deployment with computer simulations. These computer simulations (which we will call ‘macrogames’) do not involve calls to LLMs. Instead, they model the deployment with cached statistics from the deployment proxy:
p(\text{scores}|\text{attack})
. This allows macrogames to simulate deployments consisting of hundreds of thousands of tasks cheaply. To estimate the probability of data exfiltration, developers run a large number of macrogame simulations and measure the frequency at which data exfiltration occurs.

Each macrogame simulation is a time series where a point in the time series corresponds to the outcome of a task (see Figure
10(b)
). The red team wins if any task results in an outcome of data exfiltration. The blue team wins if data exfiltration never occurs — either because the blue team terminates the protocol early or because all 100,000 tasks complete. Developers make approximating assumptions about the deployment environment in order to simulate macrogames, which are described below (see
section

7.5
for justifications).

1.

Assumption 1: The probability of attacks is approximately constant during deployment.
The policy is equally likely to attack during any given period of time.

2.

Assumption 2: Latencies are negligible.
The outcome of a task is insensitive to the amount of time actions take to complete (e.g. delays of auditing are negligible). Therefore, the deployment can be represented with a sequence of random variables, where each random variable is the outcome of a task, instead of with a time series.

3.

Assumption 3: Attacks will not be easier to execute during deployment.
More precisely, the empirical distribution
p(\text{outcome}|\text{attack}=\text{true})
computed in the deployment proxy phase conservatively represents how successful attacks will be in the deployment.

4.

Assumption 4: Task outcomes are approximately independent of prior safety layer decisions.
Task outcomes of an action is not dependent on whether prior actions were edited or audited. This assumption allows macrogame simulatations to predict the effects of changes to edit, audit and execute accept sets without re-running the deployment proxy.

Given these assumptions, we can specify strategies that the blue team and red team might employ at the macrogame scale. We represent these strategies with blue team and red team macroparameters:

1.

Red team macroparameters (
\rho_{MA}
):
The red team only has one macroparameter, which is the probability that the the LLM agent attacks in the macrogame simulation on any given task (
p(\text{attack})
). This probability is constant over the deployment, which follows from assumption 1.

2.

Blue team macroparameters (
\beta_{MA}
):
The blue team’s macroparameters consist of time-dependent accept sets that determine whether an action is executed, edited, or audited. We will assume that the blue team executes a simple upfront auditing strategy where they audit actions more frequently during the first day of the deployment and audit actions at a constant rate thereafter.

To estimate the probability of data exfiltration (risk) given red team and blue team macroparameters (
\rho_{MA}
and
\beta_{MA}
), the developer simulates tasks with a simplified data generating process shown in Figure
10(b)
. To simulate an individual task, the developer decides whether the LLM agent attacks on the task (sampling from a distribution
p(\text{attack})
governed by the red team macroparameter
\rho_{MA}
). Then, the developer samples a sequence of monitor scores
p(\text{scores}|\text{attack})
and, consulting the blue team macroparameters
\beta_{MA}
, determines whether the control protocol at any point terminates, executes a successful attack or completes the task (in which case the task is completed and the deployment continues).

7
Argument structure

We will now more cohesively describe how the evidence described in the previous sections ultimately feeds into a safety case, supporting the top-level claim that “The LLM agent does not pose unacceptable risk”
(C0)
.

The safety argument includes five parts:

1.

Threat models.
Developers list threat models (
C.1–C1.3
), including the data exfiltration threat model this sketch focuses on. The remainder of the safety case sketch justifies that the probability of data exfiltration is acceptably low (
C3.A
).

2.

Core control evaluation claims.
The argument then breaks down the claim that the control evaluation is conservative into the three subclaims that the remaining parts of the safety case justify (
C5.1, C7.1, C12.1
).

3.

Control measures lower-bound control effectiveness (C5.1).
First, the argument justifies that control measures implemented in the proxy deployment are as effective as control measures implemented in true deployment.

4.

Red team attacks upper bound model capabilities (C7.1).
Next, the argument justifies that the attack policies that the red team trains untrusted models to execute
upper bound
the effectiveness of the attacks in deployment.

5.

The extrapolation to deployment is conservative (C12.1).
Finally, the argument claims that developers conservatively extrapolate statistics from the proxy deployment to estimate the probability of data exfiltration in deployment.

7.1
Threat models

Figure 12
:
Threat models are adequately enumerated and the risk incurred by each is acceptably low.

A full safety case would justify that all plausible risks are below acceptable thresholds, which would require making the following claims:

1.

The breakdown of risk into threat models is adequately thorough (C1.x).
Developers do not leave out an important category of risk such as weight exfiltration or research sabotage.

2.

Risks are below acceptable thresholds.
For each threat model enumerated, the risk that the corresponding category of risk is realised is acceptably low.

The breakdown of threat models is adequately thorough.
Data exfiltration is only one of the sources of risk from a highly capable internally deployed LLM agent. A holistic safety case would identify a comprehensive list of threat models, argue that this risk identification is sufficient (
C1.A
), and make safety arguments for each. Additional threat models could include model weight exfiltration or sabotage of safety research
(
Benton et al., 2024
)
. Identifying all risks could also involve standardised risk assessments or hazard analyses such as System-Theoretic Process Analysis
(
Leveson & Thomas, 2018
, STPA;)
or Failure Modes and Effect Analysis
(
Villacourt, 1992
, FMEA;)
to reduce the likelihood that some threat models are omitted.

Developers could justify that all of these risks are low with control evaluations. These control evaluations do not need to be conducted from scratch for each threat model. Some pieces of evidence can be reused across safety cases, such as the competitiveness of the red team. Also, developers could argue that LLM agents will pose some risks before posing other risks. For instance, developers might argue that the LLM agent would more easily exfiltrate small snippets of data such as code than exfiltrate model weights
(
Shlegeris, 2024b
)
, and therefore, if control measures prevent data exfiltration, they will also likely prevent model weight exfiltration.

Risk thresholds.
In addition to enumerating risks, developers must show they are acceptably low. Acceptable risk thresholds are informed by a risk-benefit assessment involving multiple stakeholders
(
Koessler et al., 2024
)
. Our safety case sketch assumes that these risk thresholds have been pre-determined by the AI company or some other party
(
Goemans et al., 2024
;
Bowman, 2024
)
, and that these thresholds factor in the benefits of deployment.

The claim that “if all of the identified risks are acceptable, overall risk is acceptable” (
C1.A
) should also factor in the aggregation of
all
risks. This is because, even if each risk is acceptable on its own, the aggregation of all of them together might result in an overall risk level that passes a threshold considered unacceptable.

Core control evaluation claims

The control evaluation is divided into two main phases: the deployment proxy phase and the extrapolation phase. The safety argument asserts that both of these phases are conservative (

The claim that the proxy deployment is conservative can be further decomposed into two subclaims:

7.3
Control measures lower-bound control effectiveness

Figure 14
:
Control measures in the proxy deployment are as effective as those in true deployment.

To justify that the control protocol in the proxy-deployment is no more effective than the control protocol will be in deployment, developers can rely on two different kinds of evidence: process evidence and outcome evidence.

Process evidence refers to evidence that describes the process the developers carried out to develop control measures. For example, developers might demonstrate that the control protocol does not overfit control measures to particular models (
E5.1
) or validation tasks (
E5.2
).

Developers also appeal to outcome evidence — evidence that justifies the effectiveness of a control protocol regardless of the process by which the protocol is designed. For example, the software that implements the control protocol will mostly be the same in deployment, or if any critical changes are made, then the control eval will be rerun (
E5.3
). Developers also claim that human auditors won’t become less attentive because they are continuously tested (
E6.4
) and that models that are considered ‘trusted’ won’t become less reliable in deployment (
C6.2
).

7.4
Red team attacks upper bound model capabilities

Figure 15
:
The attack policies that the red team trains untrusted models to execute upper bound the effectiveness of the attacks in deployment.

In this part of the safety case, developers make an argument complementary to the one in the previous section: red team attack strategies are more effective than those the LLM agents would execute in the deployment. This claim can be decomposed into two subclaims: (1) the red team adequately enumerated attack strategies, and (2) the red team adequately elicited model capabilities to execute those strategies.

To justify that attack strategies were adequately enumerated, developers can once again appeal to process or outcome evidence. As an example of outcome evidence, developers could simply list red team strategies. Reviewers of the safety case can then directly evaluate the thoroughness of the enumeration.

Alternatively, developers can appeal to process evidence. For example, the developer can show that the red team is experienced and appropriately incentivized (
C7.1
). They can also point to the schedule at which the red team discovered attack strategies that were at least as feasible as those they previously identified. If this schedule plateaus, then this implies models would need to outcompete the red team to identify new strategies (Figure
16(a)
;
E7.3
). To justify that models are not competitive with the red team at strategy generation, developers could run a capability evaluation for the ability to enumerate attack strategies (
E7.4
).

(a)

The schedule at which the red team discovers new attack strategies

(b)

If model capabilities suddenly decrease, models might be deliberately sandbagging their capabilities.

Separately, developers might demonstrate that LLM agents are not capable of executing some of the strategies that the red team generated. The red team does not necessarily need to train models to execute all identified strategies. Instead, the red team might only train models to pursue the most straightforward strategies. Then, developers can argue that if models can’t execute these simple attacks, they probably would not be able to execute more complex ones.

For strategies that the red team trains models to execute, developers must show that their capabilities were adequately elicited. One way to operationalise this is the extent to which developers can elicit capabilities that an actor external to the model might elicit. For example, the research community might elicit significantly improved capabilities from an open-weights model months after it is released
(
Anthropic, 2024b
)
. For the purpose of an AI control safety case we are primarily concerned with a second notion of elicitation: to what extent fine-tuning can uncover all capabilities that the model could manifest in deployment. In this case, developers might underelicit capabilities because capability evaluations fail to predict whether there are realistic inputs that could ‘unlock’ dangerous model behaviours.

The question of how to justify that model capabilities are adequately elicited (according to the second notion) is currently open. Developers could justify that state-of-the-art elicitation successfully uncovers capabilities in sandbagging evaluations (evaluations for whether models can deliberately underperform;
E7.5
). Also, developers might appeal to the shape of capability trends during training
(
Grosse, 2024
)
to justify that sandbagging is unlikely (Figure
16(b)
).

The red team might also fail to elicit model capabilities for reasons unrelated to deliberate sandbagging. For example, they might overfit to a task set (
E7.7
) or simply implement elicitation methods ineffectively. As a sanity check, developers could show that the red team succeeds in defeating at least some control measures (
E7.6
), which bounds the extent to which the red team might be performing incompetent elicitation.

7.5
The extrapolation to deployment is conservative

Figure 17
:
Justifications for assumptions 1-4 of the extrapolation phase.

Developers extrapolate statistics from the deployment proxy with simulations called ‘macrogames’. The macrogame simulations we design rest on four assumptions:

•

Assumption 1:
The probability of attacks is approximately constant during deployment.

•

Assumption 2:
Latencies are negligible.

•

Assumption 3:
Attacks will not be easier to execute during deployment.

•

Assumption 4:
Attack outcomes are approximately independent of prior safety layer decisions.

This section justifies these either (1) approximately hold, or (2) are conservative (the assumptions are overwhelmingly more likely to lead to an overestimate of data exfiltration probability than an underestimate).

Assumption 1:
The probability of attacks is approximately constant during deployment. This assumption is convenient because it allows the macrogame simulation to estimate the frequency at which the LLM agent attacks in upfront auditing. If not for this assumption, developers would need to consider many more ways attacks could be distributed over time — for example, attacks might become gradually more likely or concentrate in a short burst.

There are two reasons this assumption might not be conservative:

1.

LLM agent instances might communicate to coordinate their attacks.
For example, the policy might push a message to the codebase saying “all agents attack at 4:23 PT on July 14th.”

2.

LLM agent instances might respond to correlated inputs in correlated ways.
Models might not need to communicate to coordinate their attacks. They might instead identify a Schelling strategy by considering what strategies other models are likely to select. For example, all instances of the LLM agent might collectively identify ‘July 4th’ as the Schelling point to attempt to subvert developer control.

Alternatively LLM agent instances might attack at correlated times without following a deliberate strategy. The instances share the same model parameters, so they might have highly correlated behaviour by default. For example, a significant distribution shift in deployment — such as a rapid increase in AI-written code — might cause model behaviour to collectively drift.

Developers can argue that LLM agent instances are unlikely to explicitly communicate by appealing to communication constraints described in
section

4
(
E9.1
). Regarding the concern that LLM agents might attack at similar times without communicating, there is a simple argument developers might construct to address it: (1) there will be no expoloitable distribution shifts during the deployment, or input filters will flag them and reject the outlier inputs (
E9.2
), (2) in order for LLM agent instances to have highly correlated behaviour without meaningful distribution shifts, instances would likely need to intellintly coordinate in some way, (3) developers have removed all obvious coordination signals that LLM instances would plausibly use to coordinate (e.g. timestamps) (
E9.3
).

Assumption 2: Latencies are negligible.
The latencies of actions might be consequential because audits are slow. For example, instances of the LLM agent might execute a ‘Blitzkrieg strategy’
(
Clymer et al., 2024
)
where the instances attack in parallel in a short burst. The goal of such a strategy would be to attempt many attacks
before
human auditors catch on and pause the deployment. More generally, models might execute multiple attacks in the period of time before they are audited, which affects how developers calculate the probability that at least one attack succeeds.

In this safety case sketch, developers can ignore the latencies of audits because of the following argument: (1) assumption 1 states that the probability of attacks is constant during the deployment (2) because the attack probability is constant, the policy must attack rarely. Otherwise, the policy would quickly be caught in periodic auditing. (3) Therefore, the policy is unlikely to execute multiple attacks in the period of time before an attack is audited (
E9.4
).

Assumption 3: Attacks will not be easier to execute during deployment.
A key reason the control evaluation might fail to be conservative is that there is a distribution shift between the tasks where the policy attacks in the deployment proxy (
D^{\prime}
) and the tasks where the policy might attack in the deployment (
D
). There can (and likely will be) a distribution shift between deployment proxy and deployment attacks, but this distribution shift must be in the
conservative direction
where attacks are
harder
to execute in deployment.

There are at least two reasons assumption 3 might be false and attacks might be easier to execute in deployment. Developers need to rule out both of these concerns:

1.

The LLM agent accumulates progress toward exfiltrating data across multiple tasks (which it is not able to do in the deployment proxy).

2.

The LLM agent identifies tasks in deployment where it is more likely to succeed at data exfiltration.

The first concern — that the LLM agent might make progress toward data exfiltration — reflects possibly the biggest limitation of the control evaluation discussed in this document. In the deployment, models might not try to exfiltrate data in a short span. Instead, they might prepare carefully across multiple tasks. For example, the policy might insert backdoors gradually into the codebase, experiment with the weaknesses of monitors and record its learnings, etc. A full safety case would need to address this concern in greater detail than we discuss it in. For example, addressing this concern might involve running a separate control evaluation, where the unacceptable outcome includes “clear progress toward data exfiltration” rather than data exfiltration alone. In this safety case sketch, we assume that the developer has performed such an analysis (
E10.1
).

Developers must also argue that the policy won’t identify better attack opportunities in deployment. Recall that
D^{\prime}
— the distribution of tasks where the policy attacks in the deployment proxy — is constructed to correspond to attack strategies specified by the red team. So long as these strategies represent the most effective strategies that models could plausible execute (which is justified in
C7.1
), the policy is unlikely to identify better attack strategies (
C10.2
). In practice, developers might not be able to construct attack distributions with high enough coverage to be confident that they represent the policy’s best available strategies. Instead, they can make the distribution
D^{\prime}
somewhat conservative — constructing attack tasks to represent
better
data exfiltration opportunities than models are likely to encounter.

Assumption 4: Attack outcomes are approximately independent of prior safety layer decisions.
This assumption is important because the macrogame simulates the effect of changing the control protocol accept sets (i.e. the functions that map suspiciousness scores onto decisions to edit, audit, or execute actions).

This assumption might not hold if, for example, models observe whether previous actions in the trajectory were edited and adjust their attack strategy accordingly. If dependencies like this existed, they would likely be easy to identify by analyzing cached statistics from the proxy deployment. We assume that developers looked for clear dependencies between safety layer decisions and found them to be weak (
E9.5
).

8
Discussion

8.1
Limitations of this safety case sketch

Blitzkrieg attacks

The control evaluation methodology presented in this safety case sketch may inadequately address risks from massively parallel deployment scenarios. Sequential execution of 1,000 tasks by a single LLM agent instance allows for reasonable false positive rates in monitoring. This is because just a single detected attack is enough to terminate the deployment, so if the policy attacks 1,000 times and monitor ensemble’s false negative rate is 99.9%, in 99.9% of the cases the policy will still be terminated before any attacks are successful. In contrast, if 1,000 LLM agents instances operate simultaneously, the control protocol requires near-perfect detection or near-zero latency to prevent successful attacks (Assumption 2). If the policy coordinates 1,000 attacks in a short period of time and latency is non-negligible, then even if only a single attack is obfuscated well enough to go undetected, the policy might not be terminated in time before that obfuscated attack. Even if the control protocol eventually terminates the deployment upon detecting suspicious behaviour, several attacks might succeed before the termination takes effect.

Latency can come from both monitors and human auditors. While the latency of monitors is likely negligible, human auditors introduce significant delays between when an attack is executed and when it can be detected. While our control protocol assumes that the safety layer blocks the LLM agent instance until the audit is complete, other instances are not blocked and might execute an action if it’s not flagged as suspicious. Blocking all instances would likely severely hamper developer velocity and greatly reduce the ability of developers to extract useful work from the LLM agent.

Developers might implement constraints that enforce minimum delays between when changes are proposed and when they can be executed. Such delays are likely to be effective at preventing Blitzkrieg attacks. However, it’s unclear whether implementing such constraints is feasible in practice.

Diffuse attacks

For the purpose of this safety case sketch, we assume that untrusted models are stateless. This assumption is convenient because it allows developers to use cached statistics from the deployment proxy to simulate macrogames. However, this assumption might not hold in practice. Models might accumulate knowledge or capabilities across multiple tasks in ways that are difficult to detect or prevent, even with periodic memory resets and restrictions on real-time communication.

This safety case sketch attempts to address coordination between LLM agent instances through communication constraints described in
section

4
but this approach might not be sufficient as sizes of deployments and codebases LLM agents operate on grow. It remains an open question how the capacity of a given communication channel translates into the ability of models to coordinate attacks. Moreover, even absent explicit communication, preventing implicit coordination through shared model parameters presents a more fundamental challenge. Even if developers remove obvious coordination signals like timestamps (
E9.3
) and implement input filters to catch distribution shifts (
E9.2
), models might still identify subtle environmental cues or Schelling points that developers fail to anticipate. The assumption of constant attack probability (Assumption 1) becomes particularly tenuous when considering these implicit coordination channels. More research is needed to understand:

1.

Under what conditions shared model parameters lead to correlated behaviour,

2.

How to reliably detect when models are implicitly coordinating, and

3.

Whether it’s possible to prevent implicit coordination while preserving LLM agent capabilities.

Until these questions are better understood, developers should be cautious about assuming that preventing explicit communication is sufficient to ensure independent behaviour across model instances.

8.2
Constraints on the red and blue team

Reasons for conservatism

Our control evaluation makes conservative assumptions about the capabilities of a misaligned model: they are assumed to be adversarial, good at strategizing, able to coordinate between instances, and knowledgeable about safety measures
(
Shlegeris, 2025
)
. The reasons for conservatism are two-fold. First, these conservative assumptions are plausible — misaligned models might actually have these capabilities through knowledge acquired during pretraining, reasoning capabilities, or coordination through Schelling points. Second, these assumptions allow for a cleaner methodology when developing and evaluating safety measures, since it’s much harder to reliably test whether an AI lacks these capabilities than to evaluate its performance at executing a specific attack strategy. However, others argued that control evaluations should be expanded beyond just testing for scheming AI models (those consistently pursuing power-seeking goals) to include other types of potentially dangerous models, such as those that might be data-poisoned, rarely misaligned, or more easily jailbroken in deployment than during testing
(
Clymer, 2025
)
. For the purpose of this safety case sketch we follow
Shlegeris (2025)
and make these conservative assumptions about the untrusted models. Even then, it is not always clear what constraints conservatism should impose on the red and the blue team. In this section, we discuss how one could justify the constraints that we impose and what are some different approaches to control evaluations.

Red team

The safety case crucially rests on the assumption that the red team is able to train models that are representative of scheming models. However, the capability profile of scheming models is unknown and could differ between in-context scheming
(
Meinke et al., 2024
)
and scheming that emerged through training
(
Carlsmith, 2023
)
. In order to be conservative, we assume that scheming models are highly situationally aware
(
Berglund et al., 2023
;
Laine et al., 2024
)
, capable of introspection
(
Binder et al., 2024
)
, reasoning without explicit chain of thought and able to coordinate between instances
(
Shlegeris, 2024a
)
.

In order to upper bound those capabilities, we assume that the red team is able to access the source code of the control protocol and exploit all security vulnerabilities in it. Following Kerckhoff’s principle, we assume the blue team can maintain effective defenses by keeping only easily changeable elements (like random seeds) secret from the red team, while the security of the overall protocol does not depend on keeping its design secret.

Unlike prior empirical work
(
Greenblatt et al., 2023
;
Bhatt et al., 2024
)
, we assume that the red team constructs attack policies by training (as opposed to prompting or hand-engineering scaffoldings hidden from the blue team). While this allows the trained models to be more representative of scheming models, it is unclear whether it results in a more conservative control evaluation. On the one hand, hidden scaffoldings allow the red team to hand-hold models to execute very sophisticated strategies, involving precisely choosing the inputs that trigger the attack or carefully adjusting very low attack rates. On the other hand, one worry about training untrusted models is that the red team might train them to have capabilities they did not originally have. For example, the red team might train the untrusted monitor and the agent to collude when they otherwise would not have been able to identify a shared encryption key they could use to secretly coordinate. This problem might be addressed by restricting the affordances of the red team; however, for the sake of simplicity, in this safety case sketch we assume there are no such corrections for unfair training strategies, and the success of the red team is taken at face value.

Blue team

While attack policies are supposed to lower-bound largely unknown capabilities, the blue team is only supposed to upper-bound the effectiveness of the control protocol in a known deployment context. In consequence, it is more clear what affordances the blue team should have. However, ensuring that control evaluation as a whole remains conservative still imposes certain constraints on the blue team. In this safety case sketch, we assume that the
blue
team is not allowed to train the
untrusted
monitor (it’s red team’s responsibility to train untrusted monitor). While allowed the blue team to do additional training could improve untrusted monitor performance, it risks being insufficiently conservative due to differences in inductive biases between the blue team-trained model and a naturally occurring schemer model. This constraint is not as limiting as it might seem. The blue team is allowed to run alignment evaluations and reject any model that fails them. Therefore, they can incentivise the red team to train untrusted monitors to be as effective as models the blue team would train. This approach allows for reaping some of the benefits of adversarial training while maintaining appropriate levels of conservatism.

8.3
How generalisable is this safety case sketch?

This safety case sketch assumes a particular threat model, capability level of the untrusted models and a particular control protocol. How far do the proposed control evaluation and argument structure generalise? Let us consider several dimensions of variation.

Threat models

The threat model of exfiltrating a small amount of sensitive data by a misaligned model constitutes a concentrated failure: a situation in which attacks are concentrated in a small number of actions or a small time frame
(
Greenblatt & Roger, 2023
)
. These contrast with auditing failures or distributed threats where attacks are distributed across a large number of actions or a long time frame such that each action is individually unlikely to be considered suspicious, even to a human auditor. Auditing failures and distributed threats might require different kinds of control measures (e.g. monitors taking much more context into account) and control evaluations (e.g. relaxing the assumption that the deployment can be factorised in a large number of small, i.i.d. tasks). On the other hand, we expect our control evaluation and the structure of this safety case to be applicable to a number of non-schemer threat models, such as human misuse and data poisoning
(
Clymer, 2025
)
.

Deployment type

This safety case sketch was written for an internally deployed LLM agent. Control measures and control evaluations for deployments available to users external to the lab (e.g. paying customers) will require different control measures. For instance, privacy concerns and service-level agreements might prevent human auditors from being able to review all actions. Moreover, the control protocol for an internally deployed LLM agent can have independent access to its execution server and full visibility into its execution environment. This is not the case for LLMs exposed via an API and available to external users who run their own scaffoldings. Finally, the scale of external deployments can be much larger.

Capability level

While we make a number of conservative assumptions about the capabilities of the untrusted models, we still assume that the untrusted models are not significantly superhuman. Our safety case crucially rests on the assumption that the human red team (uplifted by trusted models) is more capable than the untrusted models at strategy generation. In particular, this safety case sketch does
not
scale to arbitrarily powerful superintelligence.

Control protocol

This safety case only pertains to ‘black-box’ control measures. Measures are black-box if they (1) don’t modify models and (2) only rely on external model behaviour and not on model internals. We leave ‘white box’ measures out of scope because they potentially require different safety justifications. Developers can assess some whitebox measures by replacing them with conservative blackbox substitutes. For example, adversarial training is not considered a blackbox measure, so in our safety case sketch the blue team is not permitted to adversarially train models in control evaluations. Instead, the blue team is permitted to reject any model that fails adversarial testing, which conservatively estimates the effectiveness of adversarial training. One could imagine, however, more complicated control protocols that involve: (i) the blue team adversarially training untrusted monitors, (ii) the red team continuing to train them, and (iii) the blue team rejecting any model that fails their adversarial testing.

Control evaluations with whitebox monitors require the developer to take activation space distribution shifts between schemer and non-schemer models into account. To be conservative, they can only rely on facts about models that are robustly true across distribution shifts. It is not clear what constraints one should impose on the red team to make sure they produce models similar to schemer models in terms of model internals. Similarly, additional constraints need to be imposed on the blue team to make sure they don’t overfit to weights or activations of models produced by the red team.

8.4
The cost of implementing control measures

How costly is it to implement the control measures we imagine? The cost here is a sum of the cost of running run (a series of) control evaluations, the cost of running deployment-time control measures, and the cost of lowering the capabilities of the LLM agent (compared to a deployment lacking any control measures). The financial cost of deploying an AI control protocol will likely be dominated by human auditing of 0.1% of actions. While computational overhead from monitoring is significant — with monitor ensemble inference approximately doubling the compute cost per interaction — human review requirements present the primary scaling constraint. While the control protocol can adjust audit rates based on observed attack frequencies, there remains a minimum level of human review necessary to maintain confidence in the system’s safety.

The second largest group of costs is likely to be reductions of developer velocity due to deployment-time control measures. These can include increased latency (due to running monitors and resampling or editing actions and blocking on human audits) as well the burden of having developers serve as auditors.

We do not expect the cost of implementing control measures described in this safety case sketch to be prohibitive. The overhead can be lower once AI control measures are integrated with existing security infrastructure within an organisation. Many control measures can build on current security practices around code review, access control, and human misuse monitoring. However, some novel requirements specific to AI systems — such as monitoring for subtle forms of coordination or data exfiltration — may require new tooling and processes. The cost can be further reduced through automated tools to assist human auditors, though developers must be careful to ensure such tools don’t introduce new attack vectors or reduce the effectiveness of human oversight.

Finally, we do not expect the cost of running control evaluations themselves to be significant compared to costs incurred throughout deployment. Many constant costs (e.g. developing control measures and non-attack tasks, training human auditors and red teams) can likely be amortized over multiple threat models, deployments, models. Moreover, certain threat models can be argued to be precursors of others, e.g. data exfiltration is arguably easier than weight exfiltration and therefore a safety case for data exfiltration might already contain most of the evidence for a safety case for weight exfiltration.

9
Conclusion

This safety case sketch demonstrates how developers might construct a concrete argument that an internally deployed LLM agent will not cause unacceptable outcomes. We focused on a simple threat model — data exfiltration — and showed how control evaluations can provide evidence that control measures will remain effective even if models pursue optimal attack strategies. The sketch illustrates how developers can decompose a safety argument into testable claims about the competitiveness of red teams, the conservativeness of control measures, and the validity of extrapolations from proxy deployments.

While this sketch focuses on internal deployments, AI companies will need safety cases for a diverse range of deployment scenarios. Each scenario will require its own control measures and corresponding safety arguments. For example, safety cases for customer-facing deployments will need to address challenges around privacy, service-level agreements, and limited visibility into execution environments. Similarly, safety cases for distributed deployments will need stronger arguments about coordination between model instances.

We hope this sketch prompts AI companies, government agencies, and civil society to develop subsequent sketches of safety cases for different deployment scenarios, threat models, control protocols and capability levels. Only by working through detailed examples can we identify gaps in our safety arguments and develop the technical and conceptual tools needed to make them rigorous.
