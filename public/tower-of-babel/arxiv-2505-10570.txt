LongFuncEval: Measuring the effectiveness of long context models for function calling
Kiran Kate, Tejaswini Pedapati, Kinjal Basu, Yara Rizk, Vijil Chenthamarakshan, Subhajit Chaudhury, Mayank Agarwal, Ibrahim Abdelaziz, IBM Research

Abstract
Multiple recent studies have documented large language models’ (LLMs) performance on calling external tools/functions. Others focused on LLMs’ abilities to handle longer context lengths. At the intersection of these areas lies another interesting problem: LLMs’ abilities to accurately perform function calls in long context settings. Particularly, when calling tools, LLMs are encumbered by three predominant challenges: (1) a large catalog of tools, (2) long responses from the tool APIs, and (3) long multi-turn conversations. These challenges are particularly relevant to enterprise applications of LLMs which engage in multi-turn conversations with users to complete complex tasks that require a large catalog of complex tools. The literature contains multiple investigations of long context challenges such as lost in the middle or needle in the haystack for natural language tasks. In this paper, we make the first attempt to comprehensively study the long context understanding capabilities of these models in the tool calling setup. We modify existing benchmarks for challenge 1 and 3, and create a new evaluation set for challenge 2 to enable this analysis. We gradually increase the input context length and also vary the position of the answer in the input. When evaluated with several long context models, we observe a performance drop of 7% to 85% as the number of tools increases, a 7% to 91% degradation in answer retrieval as the tool responses length increases, and 13% and 40% degradation for as multi-turn conversations get longer. Our study shows that LLMs still struggle with long context in tool calling settings, motivating future research to drive further LLM improvements.

Introduction

Recent advances in large language models (LLMs) have led to exciting use cases in several domains such as coding, education, travel, and healthcare. However, they still face key challenges such as struggling with mathematical reasoning, accessing external knowledge, not having access to sensitive data for training (e.g., Personally Identifiable Information), and not having access to most up-to-date knowledge. To address the aforementioned limitations, researchers have focused on teaching LLMs how to utilize external resources via tool calling

This approach allows LLMs to tap into sensitive external data, use tools, reasoning systems, and code interpreters, and most importantly, retrieve up-to-date information — an essential capability for real-world applications.

In different use cases, besides tool calling, LLMs are used to solve complex tasks such as carrying on long conversations

Recognizing tool usage and long-context handling as essential capabilities of LLMs to build real-world applications, in this paper, we investigate LLMs’ performance in a long-context tool-calling setup. As tool calling evolved from using simple tools such as a calculator and a calendar to more complex scenarios, LLMs face multiple manifestations of the long context challenge that are specific to tool calling. The first relates to the
large number of tools
in the catalog (hundreds of tools for real-world setups). The second relates to the
long tool responses

The third relates to
dependent turns in multi-turn dialogues
, where information from one user turn or tool response is used in future turns, and long multi-turn conversations make it hard for the models to understand and retrieve relevant parts of the context to generate the next function call. Figure

In the tool calling literature, the long tool catalog challenge is mainly handled with independent tool retrievers
(
Lumer et al. 2024
;
Qin et al. 2024
)
, long responses are handled by truncating or parsing them
(

, and long multi-turn conversation settings are evaluated by existing benchmarks
(

Zhong et al. 2025

. However, none of the existing works study the behavior of LLMs on these tasks as the size of the context becomes larger. Additionally, there are no insights on whether the location of information in the context affects model performance for tool calling.

In this paper, we evaluate various SOTA LLMs that are popular for tool-calling and also support long contexts. Despite having 128K context length, we observe varying degrees of degradation across model families and model sizes. When varying the tool catalog size (from 8K to 120K tokens) and location of the correct tool, performance drops vary from 7.59% to 85.58% (excluding Mistral-large) across all the datasets, due to formatting issues and increased hallucination. When varying the length of the response (from 10K to 80K tokens), degradation in answer retrieval varies from 7% (GPT-4o) to about 91% (Mistral-Large). Finally, when varying the length of the conversation (from 10K to 80K tokens), between 13% and 40% degradation was observed.

Our contributions can be summarized as follows.
(1) To the best of our knowledge, we are the
first paper to comprehensively study the challenges in long context tool calling
. We identify three key challenges and design evaluation setups by extending public benchmarks to study LLM behavior for each challenge.
(2) We create a
new evaluation dataset for challenge 2
to evaluate LLM’s ability to handle long tool responses.
(3) We evaluate
six 128K context length tool calling open-weight models and one closed-weight model
and show that LLMs struggle with all three challenges.

2
Related Work

2.1
Tool Calling

Tool calling involves generating one or more function calls in response to a user query. A sub-task of tool calling is tool selection from a catalog.
While many papers have explored the tool selection problem, acknowledging the challenges related to catalog size, we did not find any studies that systematically documented the impact of tool catalog size on tool calling performance of LLMs. Some used small catalog sizes

(
Erdogan et al. 2024
)
, others relied on a tool retriever to shortlist relevant tools before selection
(
Patil et al. 2024
;
Qin et al. 2024
)
, even proposing novel retrieval approaches
(
Xu et al. 2024
;
Shi et al. 2025
)
.
(
Lumer et al. 2024
)
demonstrated a decline in a tool retriever’s performance as the number of input tools increased, but did not document impact on tool calling when all the tools are used in the tool calling prompt.

While most tool calling benchmarks include simpler tools producing simple responses, ToolLLM
(
Qin et al. 2024
)
proposes to handle long tool responses by asking GPT-4 to drop irrelevant keys and/or truncating it beyond a certain number of tokens. Another approach to handle long responses from REST APIs is to parse them using Python code
(
Song et al. 2023
)
. Recent benchmarks such as BFCL-v3
2
2

2

https://gorilla.cs.berkeley.edu/blogs/13_bfcl_v3_multi_turn.html
specifically evaluate model performance in multi-turn long context scenarios. Similarly, ComplexFuncBench
(
Zhong et al. 2025
)
is an evaluation dataset handling complex tools, long parameter values, and long multi-turn tool calling scenarios.

Unlike these works, our goal is to study whether LLMs can extract required information from API responses or recall information from previous conversation turns, especially as the context becomes larger. To the best of our knowledge, we did not find any systematic studies that explore the three long context tool calling challenges.

2.2
Long Context

Numerous datasets benchmark models in long context settings including Zero-Scrolls
(
Shaham et al. 2023
)
, Longgenbench
(
Liu et al. 2024b
)
, Loogle
(
Li et al. 2023a
)
, NoLiMa
(
Modarressi et al. 2025
)
, DENIAHL
(
Dai et al. 2024
)
.

LLMs struggle with long-context comprehension, particularly when key information is buried within large inputs. The “Needle-in-a-Haystack“ study showed that LLMs struggled to find key information when presented with content with large context
(
Kamradt 2023
;
Das et al. 2024
)
. Similarly, the “Lost in the Middle“ study found that model performance declines when the critical information is positioned at different points within the prompt, highlighting challenges in attention mechanisms
(
Liu et al. 2024a
)
. RULER studied the effective context length for models claiming to have at least 32K context length and found the actual context length was not always as claimed
(
Hsieh et al. 2024
)
.
These challenges arise primarily due to long term decay property of RoPE position embedding
(
Su et al. 2024
)
that is widely adopted in most of the recent transformers
and dispersion (difficulty) and scope (amount) of information retrieval tasks
(
Goldman et al. 2024
)
. While most of these studies focus on unstructured text, our work specifically investigates long-context challenges in structured tool-calling scenarios, where models must process and retrieve relevant information from complex, structured outputs.

3
Problem Definition

To concretely define the long context tool calling challenges, consider a travel planning agent which has to find available dates for all the participants, book the flights, hotels, rental cars, reserve tables at restaurants and recommend activities to do based on the group’s interest. This agent’s pipeline consists of the steps defined in Figure
1
. The agent must first access the group’s calendars and find suitable dates for their trip, then book flights, hotels, reserve restaurant tables, etc., interacting with the users at various steps to obtain their preferences. Towards successfully completing this task with real world APIs, an LLM is faced with the following three challenges:

3.1
Challenge 1: Large Tool Catalog

At each step, the travel planner must access a large catalog of tools. This catalog consists of tool names, their descriptions, and their input-output arguments. Depending on how rich and complex these tools are, a 128K token context window may not even fit all tools (see Table
3
in the Appendix); as seen in multiple benchmarks, catalog sizes can easily reach hundreds if not thousands of tools
(
Liu et al. 2024c
)
.

Formally, let
\mathcal{P}
denote the input prompt, which consists of a user query
u
and a list of available tools
\mathcal{T}=\{t_{1},t_{2},\dots,t_{n}\}
. The user query
u
is a natural language expression of a task or problem that needs to be solved. The tool list
\mathcal{T}
contains descriptions including parameter names, descriptions and types, each of which is represented as
t_{i}=(name_{i},description_{i})
, where
name_{i}
is the unique identifier of the tool and
description_{i}
is the detailed functionality of the tool. Given
\mathcal{P}=(u,p,\mathcal{T})
, the LLM generates a tool call
f
from the tool list
\mathcal{T}
that satisfies the user query
u
. Here,
p
is the position of tool/s in
\mathcal{T}
which correspond to the ground truth function call/s.

Our goal is to study how the size of the catalog
n
impacts the ability of an LLM (that can handle large contexts) to formulate the correct tool call. We also study how the location of the answer tool/s within the context impacts the model’s performance.

3.2
Challenge 2: Long Tool Responses

Once LLMs formulate a tool call (by selecting a name from a catalog of tools and determining the arguments’ values), the tool executor executes the tool. It is common practice to simply append the tool response to the prompt and send it back to the LLM to process the response and plan the next steps. For many real world tool calling scenarios, the tools are REST APIs
(
Qin et al. 2024
;
Zhong et al. 2025
;
Ruan et al. 2024
)
which return responses in JSON format. REST API responses are long and highly nested and existing approaches either compress or truncate the responses beyond a token limit
(
Qin et al. 2024
)
.

A REST API response typically returns an array of information, say a list of hotels, or flight paths. Each record in the array is usually a nested JSON object. In
tool response QA
, given the triplet
(\mathcal{Q},\ p,\ \{r_{1},r_{2},...,r_{n}\})
, where
\{r_{1},r_{2},...,r_{n}\}
is a list of records in the tool response, the task is to prompt the LLM to generate an answer to the question
\mathcal{Q}
based on the tool response. The index
p
corresponds to the location of a record within tool response which has the information to answer
\mathcal{Q}
.

Our goal is to study how well LLMs understand tool responses and whether they can retrieve correct information from them, especially when the responses are large and complex. To the best of our knowledge, no existing tool calling datasets enable evaluation of this aspect. We propose a new task called
tool response QA
, which creates question-answer (QA) pairs on tool responses from an existing benchmark
(
Zhong et al. 2025
)
3
3

3

We will make this dataset available to facilitate further research on tool response understanding.
.

3.3
Challenge 3: Long Multi-Turn Conversations

The travel planning task cannot be accomplished in a single conversational turn; in fact it requires multiple turns.
As multi-turn tool-use benchmarks become more prevalent, it is evident that even the best-performing models struggle in these settings
(
Yan et al. 2024
;
Wang et al. 2024
;
Zhong et al. 2025
)
. A key challenge that remains largely unaddressed is the ability to effectively handle scattered information across multiple turns, essentially managing long-context dependencies and retrieving relevant information when needed.

Specifically, we evaluate the long dependency problem
(
Yin et al. 2025
)
for multi-turn tool calling. The problem formulation has a set of user, LLM, and tool turns
\{u_{1},\ llm_{1},\ tool_{1},\ ...,\ u_{i},\ ...,\ u_{n},\ llm_{n}\}
where either
u_{i}
or
tool_{i}
contains information that is required to generate the function call
llm_{n}
on the user turn
u_{n}
. We increase the number of the turns
n
in these conversations and study if it affects the ability of the models to recall the information from the
i^{th}
turn to generate a correct function call.

4
Methodology and Experimental Setup

4.1
Challenge 1: Large Tool Catalog

To create large tool catalogs suitable for our study, the first step involves extracting all the unique functions from the BFCL dataset
(
Yan et al. 2024
)
. Let
\mathcal{D}
denote the dataset containing multiple sources of tools (such as
simple
,
multiple
,
parallel
,
live_simple
); each source containing a list of function descriptions. The extraction process identifies all unique functions
\mathcal{T}^{*}=\{t_{1},t_{2},\dots,t_{N}\}
from
\mathcal{D}
, eliminating duplicates. This is achieved by checking for uniqueness based on the function name.

Once the unique functions
\mathcal{T}^{*}
are obtained, the next step is to generate long context scenarios by introducing distractors. Distractors are functions that are not relevant to the user query
u
but are randomly added to the context to simulate a large tool catalog. The distractors are selected from
\mathcal{T}^{*}
and inserted into the tool list. The original function is then inserted at a specified position
p
of the distractor list, which is determined by a fraction
\alpha
of the length of the distractor list to the get the final tool list. This process is repeated until the token limit is reached. This insertion process ensures that the context length is increased while maintaining the original order of the functions.

This method was applied for various context lengths to systematically study the performance of the LLM. Specifically, we considered the following context lengths:
\{8,192;16,384;32,768;65,536;120,000\}
tokens
4
4

4

Although several models have a max context length of 131,072, we used 120,000 to account for the maximum number of additional tokens introduced by tokenization and the prompts introduced by all the models.
. Additionally, similar to
(
Liu et al. 2024a
;
Kamradt 2023
;
Mohtashami and Jaggi 2023
)
, we also choose different insertion positions of the original tools in the tool list. This is controlled by an insertion fraction
\alpha
which took one of the following values:
0.1,0.3,0.5,0.7,0.9
,
to explore the impact of different insertion positions on the long context generation. This comprehensive variation in context lengths and insertion positions allows for a detailed analysis of the LLM’s performance under different long context scenarios.

We used the
simple
,
live_simple
, and
multiple
subsets from BFCL
(
Yan et al. 2024
)
for this evaluation which have 858 samples in total. We evaluated 6 models with context 128K, Mistral-large, ToolACE-8B, BitAgent-8B, Granite-3.1-8b-instruct, llama-3-1-70b-instruct across the three datasets for all the positions. Owing to budget constraints, we ran GPT-4o-2024-11-20 for context lengths 8,192, 32,768 and 120,000 for positions 0.1, 0.5, and 0.9. Appendix
C.1
includes the exact details of the models. We used BFCL’s code
5
5

5

https://github.com/ShishirPatil/gorilla/
for the prompts and the evaluations and used the AST accuracy metric.

4.2
Challenge 2: Long Tool Responses

To evaluate an LLM’s ability to process tool responses, we created a QA dataset based on the API responses.
We use tool responses from ComplexFuncBench
(
Zhong et al. 2025
)
, a dataset that enables evaluation of complex function calling scenarios with multi-turn conversations and REST API tools. Our questions are based on five REST endpoints from booking.com
6
6

6

https://rapidapi.com/DataCrawler/api/booking-com15
spanning domains such as flight reservation, hotel booking, car rental, and tourist attractions.

Next, we manually create question templates for
\mathcal{Q}
and write code to parse the JSON to get answers to those questions by understanding the structure of these responses. The questions target three categories of response processing/understanding (as shown in Figure
2
): (1) extraction: extracting a single value for a key, (2) filtering: retrieving one or more entries based on some filtering criteria, or (3) aggregation: aggregating multiple entries by performing an aggregation operation to obtain the final answer (e.g., average, sum, etc.).

Figure 2
:
Examples of tool response question categories for challenge 2

The creation of such QA pairs is controlled by
p
which corresponds to the positional index of a record in the JSON corresponding to that QA pair. For example, for the extraction question in Figure
2
, the response contains information about different vehicles, and the value of
p
would decide what value gets substituted for
"vehicle\_id"
in the question template. This control allows us to vary the position of the QA pair and evaluate if the position matters similar to other such studies
(
Liu et al. 2024a
;
Kamradt 2023
)
.

To study the impact of the size of tool responses, we control the number of records
n
such that it reaches a token limit. This is done by merging responses of individual API calls in the dataset which simulates changing the original API call to have fewer filtering arguments.
For each API endpoint, we create 10 response samples such that the response with token limit
n_{1}
is a prefix of response with token limit
n_{2}
when
n_{1}\ <n_{2}
.
Appendix
A
includes details of the dataset created (which had a total of 566 samples).

We used zero-shot prompting with greedy decoding to get LLMs to generate the answers. For each question template, the evaluation metric depends on the type of ground truth. For example, a scalar value warrants an exact match but an unordered list would need to be matched discounting the order. From our experiments, we noticed that LLMs were very verbose in their responses even when prompted to output just the precise information. We added special instructions (e.g., ”show only the amount and no currency or currency symbol.”) at the end of the question to account for this. In addition, we also report results for a ”contains” metric which checks for membership of the ground truth in the generated answer in appendix
B.2
.

We conduct two experiments: one by varying the tool response token limits to
\{10K,20K,40K,80K\}
and by fixing
p
= 1, and second by fixing the tool response token limit to
80K
tokens and varying
p
from 1 to 8.
We used seven models for these experiments:
GPT-4o-2024-11-20,
Llama-3.1-70B-Instruct,
Mistral-large,
Llama-3.1-8B-Instruct,
Granite-3.1-8B-Instruct,
ToolACE-8B,
and BitAgent-8B.

4.3
Challenge 3: Long Multi-Turn Conversations

To construct a dataset for this evaluation, we leveraged multi-turn dialogs from ComplexFuncBench
(
Zhong et al. 2025
)
and synthetically created two distinct settings: (1) the user introduces additional information (e.g., office location) at the start of the conversation within the user query and later requests a tool call that relies on that information (e.g., retrieving weather details for the office location), as illustrated in Figure
1
; (2) similar to the first setting, but the required information is obtained through a tool call earlier in the conversation. The main distinction between (1) and (2) lies in how the necessary information is presented—setting (1) includes it in an unstructured format appended to the user query, while in setting (2), it is structured as a JSON-formatted response from a tool call. We applied both interaction types to 100 randomly selected conversations from ComplexFuncBench, resulting in 200 samples per token limit (10K, 20K, 40K, and 80K tokens).

We assessed six models for this task:
Llama-3.1-70B-Instruct,
DeepSeek-R1-Distill-Qwen-32B,
Llama-3.1-8B-Instruct,
Granite-3.1-8B-Instruct,
ToolACE-8B,
and BitAgent-8B.
To ensure consistency, we used BFCL’s code for both the prompts and the output parser. Our evaluation focused on AST accuracy based on the BFCL metric.

5.2
Challenge 2: Long Tool Responses

For the long tool response challenge, Figure
4a
shows that the performance drops for most models including GPT-4o as the tool response size goes from 10K to 80K tokens. A degradation of 7% for GPT-4o and a range of 91% (Mistral-large) to 30.5% (Granite-3.1-8b-instruct) for open-weight high performing models clearly confirms that LLMs struggle with long tool response understanding. Llama 8B is an exception to this trend and DeepSeek-R1-Distill-Qwen-32B performance for 10K is also an exception. For Llama 8B, we noticed that the model at shorter context lengths tries to generate json objects even though the task does not contain instructions to do so and this behavior is not observed at 80K context. In general, it can also be seen that the tool response QA as a task is not a trivial for LLMs, with the 10K token size performance ranging from 16% to 74% depending on the model. This challenges the current practice of appending the tool response to the current context for multi-turn tool calling, specially for large responses with complex structures.

6
Conclusion

In this paper, we studied the three main challenges that LLMs face in the long context tool calling scenario. For the large tool catalog challenge, we evaluate LLMs by gradually increasing the number of tools and varying the position of the correct tool within the catalog. To examine LLMs’ understanding of long tool responses, we construct a dataset by leveraging public APIs and vary the lengths of the responses. For the long multi-turn conversations, we evaluate the long dependency challenge due to a large number of conversation turns. Across all these tasks, we notice that LLMs’ performance deteriorated significantly as the context length increases. For challenge 1, we also observe that the position bias is more pronounced as the context length increases.

Future work will include diving deeper into the reasons behind this decline in performance by further analyzing the errors we encountered. We also plan on expanding the datasets to include more variations in each task. Finally, we plan on extending the analysis of Challenge 3 to structured text as well.

Ethics

For the study we performed on long context and function calling, we do not foresee any ethical concerns or opportunities to misuse this work. Furthermore, the data we used (and modified) to evaluate models does not contain any PII or harmful language.

Appendix D
Error Analysis

D.1
Challenge 1: Large Tool Catalog

Types of Errors:
As noted above, the number of errors increases with an increase in context size, for all models.
For most models, the most common errors are (1) invalid formatting (AST errors) (2) calling the wrong function and (3) calling the right function with the wrong parameters. There is a cascading effect, where models which perform poorly often make more AST errors, while the models which perform better often have the right formatting, but make errors in the function names and errors. It is interesting to note that even models that perform reasonably well as the context size increases (like GPT-4o, for example), also make formatting errors, albeit they are not most common type of errors. Similarly, when the context length is small, models make fewer formatting errors, and the most common errors are more subtle (for example, passing the wrong parameter).

Nesting Level of JSON Objects:
REST API responses are complex and highly nested. We wanted to understand if the nesting level has any impact on the performance of the JSON QA task defined in Challenge 2. Figure
9
shows how each model performs on the question-answer pairs based on nesting level. The nesting level here is calculated based on how many steps are required in the JSON traversal to get to the ground truth answer. It can be seen that even though nesting level of 7 corresponds to low performance across models, there is no clear trend based on nesting level. This can be attributed to the fact that we are not controlling nesting levels by keeping the API responses and question-answer pairs same. So the performance is also dependent on the API responses and questions.
